# B3 — Always-on agent infrastructure: what to adopt, what to ignore
**Researcher:** mesh subagent, ZABZ-TECH, 2026-09-30

## 1. Verdict
Do not adopt a durable-execution platform as the foundation now: each real one either adds services you must operate (Temporal's own Compose default is Postgres + Elasticsearch) or is cloud-only (Step Functions, Cloudflare Workflows, AgentCore) and cannot drive a PC on your LAN. The smallest change that kills "a dispatcher that can lose an answer" is to invert dispatch — the Windows node **pulls** work from a `runs` table on the authority, commits its result **before** releasing the lease, and is supervised by heartbeat/lease/reaper. Keep the queue in SQL (SQLite today, Postgres next), add one off-box dead-man switch and one cost ceiling that fails closed. Adopt vendor durable execution only when a workload outlives a laptop sleep or needs multi-day human-in-the-loop state you no longer want to model.

**Verdict:** on SQLite today, copy the *patterns* (step state in a DB you already run; DBOS/Inngest/Azure show the shape). Tomorrow, with Postgres on the same box: DBOS (in-process) or pg-boss/Graphile Worker/Hatchet (queue-first). Temporal/Restate only for HA across nodes or replay of long deterministic workflows. Cloudflare/Step Functions/AgentCore only if control plane *and* compute move there.

**Self-hosting isolation.** Firecracker = KVM microVM, needs `/dev/kvm` (bare metal or nested virt), hardware-grade isolation, small VMM. gVisor = user-space kernel, runs on any Linux and can back Docker via `runsc`, weaker than a microVM but far stronger than plain runc; the cost is syscall gaps that occasionally break browsers ([Northflank comparison](https://northflank.com/blog/firecracker-vs-gvisor), accessed 2026-09-30; gVisor's own docs host did not resolve here — see §10).

**Our pick.** On a home/office LAN the sandbox is not the bottleneck — the Windows desktop already is the boundary, and consumer internet is fine for cloud APIs. Use (a) **Fly Sprites/Machines as the always-on fallback node**; (b) **local Docker + gVisor** for in-house untrusted code; (c) a cloud agent sandbox only for many concurrent ephemeral containers. **Browser-profile persistence** needs a persistent writable disk holding Chromium's `user-data-dir`; only durable-storage options qualify (Fly volumes/Sprites, AgentCore session storage, E2B persistent/enterprise). No vendor page I read *states* logged-in-profile support — that is my judgement.

## 4. Reliability patterns worth copying
1. **Idempotency keys on every side effect.** The provider stores the first result and replays it instead of re-executing ([Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests); retention window not captured). Ours: `idempotency_key = run_id:step_index`, and insert into a local `effects(key UNIQUE)` **before** the call; a `UNIQUE` violation means "already done".
2. **At-least-once is the default — design for duplicates.** SQS says a copy may be redelivered and tells you to make apps idempotent ([AWS SQS](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html)). Graphile Worker: jobs are never lost, "each job will execute at least once", most exactly once, retried with exponential backoff ([Graphile Worker](https://worker.graphile.org/docs)). Never rely on the transport; dedupe at the effect boundary.
3. **Lease + heartbeat + reaper.** Claim = `lease_owner` + `lease_expires_at`; worker renews; reaper requeues expired leases. Step Functions formalizes progress liveness as `States.HeartbeatTimeout` (retriable, catchable) ([AWS](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html)); Kubernetes ships `Lease` for node heartbeats and leader election ([k8s docs](https://kubernetes.io/docs/concepts/architecture/leases/)). Lease expiry — not ssh exit status — defines a dead attempt.
4. **Checkpoint conversation *and* tool state per transition.** Azure checkpoints every state transition — LLM responses, tool-call results, control-flow decisions — and resumes without repeating completed LLM calls, explicitly to preserve token spend ([Microsoft Learn, upd. 2026-05-05](https://learn.microsoft.com/en-us/azure/durable-task/sdks/durable-task-for-ai-agents)). LangGraph gives the same shape at graph level (thread checkpoints, time travel, fault tolerance) ([LangChain docs](https://docs.langchain.com/oss/python/langgraph/persistence)). The resumable unit is the turn, not the run.
5. **Long-horizon runs need history management.** "No time limit" does not mean "one execution can accumulate forever": Temporal terminates at 51,200 events and offers Continue-As-New ([Temporal](https://docs.temporal.io/workflow-execution/event)). Cloudflare sleeps a step ≤365 days and excludes `waiting` runs from concurrency ([limits, upd. 2026-09-21](https://developers.cloudflare.com/workflows/reference/limits/)).
6. **The failure mode where the answer is the thing that gets lost.** The ssh-push signature bug: work finished, the tunnel died, and the dispatcher cannot distinguish "never ran" from "ran and lost the answer". Fix structurally: **commit the answer to durable storage the worker can reach, then let completion be observed from that storage** (ack only after effect + result commit; Temporal's completion is an appended event, not a socket return). A push channel must never be the only path for a result.
7. **Cost ceilings that actually bind.** Enforce where spend is recorded and **fail closed**. LiteLLM tracks spend in Postgres, rejects requests past `max_budget`, supports `budget_duration` resets and multiple concurrent windows ($10/day **and** $100/month on one key) — and states plainly that budgets need a DB, that they are unavailable without one, and that `litellm_settings.max_budget` **fails open** with only a startup warning on a DB-less deployment ([LiteLLM](https://docs.litellm.ai/docs/proxy/users)). Add a wall-clock and tool-call cap in the runner too; a cap the agent can bypass by calling the provider directly is decoration.

## 5. Scheduling: cron vs timers vs queue
- **cron** — universal, stateless: no retries, no concurrency control, no structured history, no dead-letter, no way to say "this run never finished".
- **systemd timers** — supervised units + journald, `OnCalendar=`, and the feature cron lacks: **`Persistent=true`** stores the last trigger and fires immediately after a missed run (power-down). Also `AccuracySec=` (default 1 min — coalescing, not precision), `RandomizedDelaySec=` to spread load, `WakeSystem=` to resume from suspend, and a documented rule that an already-active unit is not restarted ([systemd.timer, systemd 262](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html)). Near-zero adoption effort; still no retry, dead-letter, or queryable outcome.
- **Queue** — [pg-boss](https://pgboss.io/): Postgres 13+/Node 22.12+, `SKIP LOCKED` claims, rate limit/debounce/concurrency/priority, **dead-letter with redrive**, exponential backoff retries, cron/RRULE, dashboard, HTTP proxy for non-Node callers. [Graphile Worker](https://worker.graphile.org/docs): at-least-once, `job_key` dedupe, crontab, default 25 attempts over ~3 days, LISTEN/NOTIFY. [Hatchet](https://docs.hatchet.run/v1) (upd. 2026-09-29): Postgres-only for simple workloads, durable event log for replay, retries/concurrency/priority/cron, worker health checks, Prometheus + OpenTelemetry, MIT, Python/TS/Go/Ruby. Celery/RQ buy ecosystem at the cost of Redis/RabbitMQ + a Python fleet (not verified here).

**Recommendation (tens → hundreds/day).** No broker. Three layers: (1) **timers** on the Linux authority with `Persistent=true`, `AccuracySec=1us`, `RandomizedDelaySec=` so reboots and clock jumps cannot silently skip a tick; (2) a **SQL queue**: one `runs` table with `state ∈ {queued, leased, running, succeeded, failed, dead}`, `attempt`, `max_attempts`, `not_before`, `lease_owner`, `lease_expires_at`, `idempotency_key UNIQUE`, claimed by one atomic `UPDATE … RETURNING` (that is `SKIP LOCKED`-shaped today and pg-boss tomorrow); (3) a **worker loop** on the node that polls for work matching its capabilities. **Migration without rewrite:** the dispatcher's only surface is `enqueue(spec)` and `claim(node_caps)`, so swapping SQL for pg-boss/Graphile Worker changes two functions, not callers. SQLite → Postgres on the same box is the enabling step; do it at the first real concurrency limit, not before.

## 6. Node topology and failover
- **Capability advertisement, not hostnames.** Nomad expresses placement as constraints on node attributes/metadata ([Nomad constraint](https://developer.hashicorp.com/nomad/docs/job-specification/constraint)). Ours: each node heartbeats `{node_id, last_seen, capabilities:{code:repo@sha, creds:[…], browser_profile:…}, draining}`, and the claim query selects only nodes whose set ⊇ the run's requirements; version the capability so a stale node cannot claim work for code it no longer has.
- **Health-gated routing.** Only `last_seen > now() - interval` nodes are eligible; draining is a flag, not a row delete. This is what Consul checks / Nomad `check`+`check_restart` do for services — reproducible with two columns and no Consul.
- **Stuck-node detection.** Two signals: lease expiry (worker dead) and progress heartbeat (worker alive, agent looping). A run with no new step event for N minutes should be flagged and escalated to the dead-man switch, not silently killed. Step Functions models the split as `TimeoutSeconds` vs `HeartbeatSeconds`.
- **Laptop that sleeps.** Never place a run whose only capable node is a sleeping laptop unless it is `allow_interruptible`; `Persistent=true`/`WakeSystem=` cover scheduled ticks, but a mid-run suspend stalls the lease. The authority owns the timeout and requeues with backoff; keep ≥1 always-on capable node (Linux box or small cloud VM) so "the only node" is never a laptop.
- **Proportionality.** No Kubernetes/Nomad for two or ten nodes. `nodes` + `runs` + `run_events` plus one claim query reproduce placement, health gating and stuck detection.

## 7. Observability and an external dead-man switch
Instrument three things: (1) **`runs`** — one row per session (`run_id`, `spec_hash`, `node_id`, `capability_set`, `attempt`, `state`, `queued/started/ended_at`, `exit_reason`, `result_path`, `tokens_in/out`, `cost_usd`, `dead_letter_reason`); (2) **`run_events`** — append-only per step/tool call (`run_id`, `step_index`, `ts`, `kind`, `ok`, `tokens`, `cost_usd`, `duration_ms`), which is what makes "what did it do" answerable without transcripts; (3) **a trace per session** using [OpenTelemetry GenAI semantic conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/) (GenAI attribute registry; spec 1.44.0 at time of reading) — or write the same fields into `run_events` to stay portable. Cost/step comes from the gateway holding the key (LiteLLM per-key spend, or provider usage APIs), summed per `run_id`. Three numbers answer "is it working": queue depth/oldest age, 24 h success rate by node, cost per successful run.

**Dead-man switch must be off-box** — a self-hosted monitor dies with the thing it watches. The authority pings after every tick; the service alerts when pings **stop**.
- [Healthchecks.io](https://healthchecks.io/pricing/) (accessed 2026-09-30): Hobbyist **$0** (20 jobs, 100 log entries); Business **$20/mo** (100 jobs, 50 SMS/WhatsApp + 20 phone credits); Business Plus **$80/mo** (1,000 jobs, 500 SMS, 100 calls); 20% off annual; free Business for OSS/nonprofits.
- [Cronitor](https://cronitor.io/pricing) (accessed 2026-09-30): Hacker **$0** (5 monitors, 5-min fastest check); Business **$2/mo per monitor + $5/mo per user** (30 s checks, SMS, PagerDuty/Opsgenie/Datadog On-Call, 12-month retention); Enterprise from **$6,000/yr**.

Minimum wiring: (a) a "scheduler tick" check pinged every tick; (b) a "runs progressing" check pinged only when a run changed state in the window, so a wedged queue alerts while the box is up. Route to a phone call, not email.

## 8. The smallest set of changes (ranked: effort / risk)
1. **Pull instead of push** — worker claims from `runs`; a dead tunnel can no longer lose an answer (M / medium; new endpoint needs auth).
2. **Result-before-ack** — commit `result_path` + terminal event, then complete the lease (S / low).
3. **Lease + heartbeat + reaper** — requeue expired leases up to `max_attempts` (S / low; double-execution risk, mitigated by 4).
4. **Idempotency keys on side effects** — `run_id:step_index` unique in `effects`, honored at the target where supported (M / medium).
5. **Per-turn checkpointing** of conversation + tool state — resume without repaying tokens (M / medium; transcript growth, PII).
6. **External dead-man switch** — two checks, phone alert (S / very low).
7. **Cost ceiling that fails closed** — per-run and per-day caps in the gateway holding the key (S–M / low; gateway becomes an SPOF — supervise it).
8. **One outcome read** — `runs` view + one-screen summary (S / low).
9. **Node capability + health table** — placement gated by advertised caps; drain flag for the laptop (M / medium; version the cap).
10. **SQLite → Postgres on the authority** — concurrent writers, `SKIP LOCKED`, PITR backup; unlocks every queue option (M / medium).

## 9. Candidate improvements
- **IN-1 / TOPOLOGY / pull-dispatch** — WHAT: replace ssh-push invocation with a claim loop over a `runs` table. WHY: removes the one place where a killed hop loses the answer. EFFORT M. GAIN: top failure mode gone; retries possible. RISK: endpoint auth; non-atomic claim. SOURCE: [Graphile Worker](https://worker.graphile.org/docs) / [pg-boss](https://pgboss.io/) (accessed 2026-09-30). FIRST STEP: add `runs` + `claim_next_run(node_id, caps)` and call it from a 10 s loop, ssh as fallback.
- **IN-2 / RELIABILITY / result-before-ack** — WHAT: commit result + terminal event, then release the lease. WHY: "completed but unrecorded" becomes impossible. EFFORT S. GAIN: the answer can never be the lost thing. RISK: transaction must include the effect key. SOURCE: [SQS at-least-once](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html). FIRST STEP: one `BEGIN; INSERT effects…; UPDATE runs SET state='succeeded'; COMMIT;` on the worker exit path.
- **IN-3 / RELIABILITY / lease+reaper** — WHAT: `lease_expires_at` + 30 s renew + reaper query. WHY: automatic requeue of dead workers. EFFORT S. GAIN: self-healing runs. RISK: short leases duplicate work. SOURCE: [Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html), [k8s Leases](https://kubernetes.io/docs/concepts/architecture/leases/). FIRST STEP: add columns and a reaper tick.
- **IN-4 / RELIABILITY / idempotency keys** — WHAT: keyed, deduped effects. WHY: retries must not double-pay or double-send. EFFORT M. GAIN: at-least-once ≈ once. RISK: targets without key support need local pre-write. SOURCE: [Stripe](https://docs.stripe.com/api/idempotent_requests). FIRST STEP: `effects(key UNIQUE, run_id, step_index, created_at)` inserted before every call.
- **IN-5 / RELIABILITY / per-turn checkpoint** — WHAT: append messages/tool results as produced; resume from tail. WHY: no token re-spend; node death survivable. EFFORT M. GAIN: cheaper retries, longer horizon. RISK: growth/PII. SOURCE: [Microsoft Learn 2026-05-05](https://learn.microsoft.com/en-us/azure/durable-task/sdks/durable-task-for-ai-agents), [LangGraph](https://docs.langchain.com/oss/python/langgraph/persistence). FIRST STEP: append `{role, content, tool_calls, tool_results}` to `run_events`.
- **IN-6 / OBSERVABILITY / dead-man switch** — WHAT: external check pinged per tick, phone alert. WHY: only mechanism that catches the authority dying. EFFORT S. GAIN: silent stop becomes a loud alert. RISK: alert fatigue if too tight. SOURCE: [Healthchecks.io](https://healthchecks.io/pricing/), [Cronitor](https://cronitor.io/pricing). FIRST STEP: one check, period = 2× tick interval.
- **IN-7 / COST / fail-closed budget** — WHAT: gateway budget with daily + monthly windows. WHY: a loop cannot bill all night. EFFORT S–M. GAIN: hard ceiling. RISK: gateway outage blocks runs. SOURCE: [LiteLLM](https://docs.litellm.ai/docs/proxy/users) (documents DB-backed enforcement and fail-open without a DB). FIRST STEP: key behind the proxy with `budget_limits:[{24h,$X},{30d,$Y}]`.
- **IN-8 / SCHEDULING / systemd timers** — WHAT: `Persistent=true`, `RandomizedDelaySec=`, explicit `AccuracySec=`. WHY: no silent missed ticks after reboot. EFFORT S. GAIN: no lost ticks, spread load. RISK: unit-file error stops everything — verify with `systemctl list-timers`. SOURCE: [systemd.timer](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html). FIRST STEP: port one job, prove catch-up after reboot.
- **IN-9 / TOPOLOGY / capability table** — WHAT: `nodes.capabilities` + `last_seen` + drain. WHY: work lands only where code and credentials exist. EFFORT M. GAIN: fewer "not found"/"not logged in" failures. RISK: capability drift — version it. SOURCE: [Nomad constraint](https://developer.hashicorp.com/nomad/docs/job-specification/constraint). FIRST STEP: filter the claim query by required caps.
- **IN-10 / OBSERVABILITY / one outcome read** — WHAT: `runs_today` view + one-screen summary. WHY: answer "working / did what / cost" in one read. EFFORT S. GAIN: faster detection; feeds the dead-man switch. RISK: none material. SOURCE: [OTel GenAI semconv](https://opentelemetry.io/docs/specs/semconv/gen-ai/). FIRST STEP: view with queued age, success rate, cost/run, dead-letter count.
- **IN-11 / PLATFORM / SQLite → Postgres** — WHAT: move authority storage to Postgres on the same box. WHY: concurrent writers, `SKIP LOCKED`, PITR; unlocks all §5 options without caller changes. EFFORT M. GAIN: removes the scaling and backup cliff. RISK: migration weekend — keep a SQLite snapshot for rollback. SOURCE: [pg-boss](https://pgboss.io/) (PG 13+). FIRST STEP: Postgres in Docker, migrate `runs`/`run_events`/`nodes`.
- **IN-12 / SANDBOX / always-on fallback node** — WHAT: one Fly Sprite or small Fly Machine as fallback worker. WHY: a sleeping laptop must never be the only capable node. EFFORT S–M. GAIN: pipeline keeps moving. RISK: credential duplication — scope secrets per capability. SOURCE: [Fly.io sandbox pricing](https://fly.io/learn/ai-sandbox-pricing/) (2026-09-09; rates checked 2026-09-10). FIRST STEP: price the existing workload profile, register the node with a narrow capability set.
