# ZABZ-TECH: an engine on the wrong side of the version line — boot crash loop, empty workspace picker

Date: 2026-10-08 (EDT) · machine: `zabz-tech` · reporter: the owner
Status: **fixed and verified**; one residual defect recorded at the end (not introduced here).

## What the owner saw

> "i am trying to open dsh on zabz tech and getting this error then it opened and i can't pick a workspace"

with this from the launcher:

```
ensure: the engine on 3099 STARTED AND DIED during boot - it exited with code 1
ensure:   Error: dsh: plugin tree failed to load: failed to apply loader entry include (cordis:include)
ensure:   [cause]: Error [ERR_MODULE_NOT_FOUND]: Cannot find package '@deepseek-ai/dsh-agent-preset'
ensure:        imported from C:\Users\ezabz\.dsh\profiles\web\
```

## Root cause, in one paragraph

`zabz-tech` ran the **0.1.5** line and its configuration named the **0.1.7+/0.2.0** line. The machine had
no frozen engine pin (`C:\Users\ezabz\.dsh\engine` was ABSENT), so `multi-window/dshw.ps1`'s
`Resolve-DshBin` fell through its candidate list to the npx cache, which on that machine still held
`@deepseek-ai/dsh` **0.1.5-rc.1** — while `~/.dsh/profiles/web/cordis.patch.yml` carries the
`preset-<name>` rows generated by `scripts/make-preset-rows.mjs`, which import
`@deepseek-ai/dsh-agent-preset`, a package that exists only on the 0.1.7+ line. Every boot therefore
died inside the loader before the HTTP server bound, so the browser window the launcher opened had no
engine behind it: the app shell loaded, `/api` returned nothing, and the workspace picker was empty.
The window looked "open"; nothing was listening.

Measured on that machine, same command, two engines (`--profile web --dump-config`):

| engine | exit | stdout | stderr |
|---|---|---|---|
| `~/.dsh/engine` 0.2.0-rc.2 (after the fix) | 0 | 274,256 B | **0 B**, 7 preset rows in the dump |
| npx cache 0.1.5-rc.1 (what it was running) | 0 | 215,344 B | `patch: entry "agent-preset-registry" not found` |

and the same check the fleet's own guard runs:

```
$ python scripts/check-version-coupled-config.py --engine-root <npx cache>
summary: 3 MISSING -- @deepseek-ai/dsh-workflow-ptc, @deepseek-ai/dsh-agent-preset-registry,
         @deepseek-ai/dsh-agent-preset -- engine 0.1.5-rc.1 does not provide them
exit 1
```

## How long, and why nothing self-healed

- `~/.dsh/multi-window/logs/3099-<stamp>.err.log` counts on that machine: **20261006: 4, 20261007: 62,
  20261008: 639** failed boots, each 13,838 bytes of the same stack trace. The 1-minute engine
  watchdog retried all night.
- `%LOCALAPPDATA%\harness-config-autosync\autosync.log` shows the version guard **correctly refusing**
  on every 15-minute tick, from 2026-10-05T00:50:37Z onward:

  ```
  SKIPPED (not applied): presets: SKIPPED -- the repo config names @deepseek-ai/dsh-workflow-ptc,
  which the running engine (0.1.5-rc.1) does not provide; the live copies are left untouched |
  profiles: SKIPPED -- the repo config names @deepseek-ai/dsh-agent-preset-registry,
  @deepseek-ai/dsh-agent-preset, @deepseek-ai/dsh-workflow-ptc, which the running engine
  (0.1.5-rc.1) does not provide; the live copies are left untouched
  ```

  So the machine was in a **deadlock with a working guard**: the config it already had was too new for
  its engine, and the sync was (rightly) refusing to touch either. Nothing in the system upgrades an
  engine; only a human or a session does. This is the failure mode to remember: *a guard that refuses
  loudly is not self-healing.*

## The fix

1. Installed the frozen pin on `zabz-tech`, at the **same exact version** the rest of the fleet runs
   (`zabz-yoga`, `secratary`, the mac mini are all on 0.2.0-rc.2):

   ```
   C:\Users\ezabz\.dsh\engine\package.json
   {"name":"dsh-engine-pin","private":true,"dependencies":{"@deepseek-ai/dsh":"0.2.0-rc.2"}}
   npm install --no-audit --no-fund      # "added 536 packages in 1m"
   ```

   `dshw.ps1` probes `~/.dsh/engine` **first**, so this is the engine that now boots.

2. Backed the session store up before the change — 3,002 files / 903 MB copied to
   `~/.dsh/backups/sessions-pre-0.2.0-rc.2-20261008/` (robocopy, 4 s). The engine line moved
   0.1.5 → 0.2.0, which is a session-format migration, so this was not optional.

3. Killed the crash-looping engine and re-ran the launcher's own recovery
   (`Start-ScheduledTask 'DSH Engine Watchdog (1m)'`).

## Verification (what was actually observed, not what was configured)

  `"C:\Program Files\nodejs\node.exe" C:\Users\ezabz\.dsh\engine\node_modules\@deepseek-ai\dsh\lib\bin.js web --port 3099 --no-open`
  — the pin, not the npx cache.
- The engine printed its own startup line and the launch token was accepted:
  `GET /?token=... -> HTTP 303`, then a seeded cookie session -> `HTTP 200`,
  then `POST /api/agentPresets/list -> HTTP 200` (a protocol complaint about my hand-made body, not a
 401 and not a 500 — the gateway, the fence and the preset route are all alive).
- `--profile web --dump-config`: exit 0, **empty stderr**, 7 preset rows.
- A live child turn on the pinned engine from another node:
  `node <pin>/lib/bin.js --profile headless "Reply with exactly: TECH_OK"` -> `TECH_OK`, exit 0.
- New boot logs are **0 bytes** where the previous 639 were 13,838-byte crash traces.
- `check-version-coupled-config.py --engine-root ~/.dsh/engine` on that machine: 200 occurrences,
  29 distinct packages, **exit 0** — same as `zabz-yoga`.

## The same seam in the mesh, fixed with it

`packages/plugin-remote-fanout/lib/nodes.js` dispatched children to machines on the **old** line:
`zabz-tech` and `zabz-yoga-1` named the npx cache path (0.1.5-rc.1 on tech), and `secratary` named
`/home/zabz/dsh-engine` (0.1.5-rc.1) while that host's own engine runs `/home/zabz/dsh-current` ->
`/home/zabz/dsh-install/0.2.0-rc.2`. A mesh child is a real agent turn on that node; it should not
run a different engine line than the node it lands on. Those three rows now name the engine each
machine actually runs, each re-verified today with a live child turn (`TECH_OK`, `SEC_OK`) or with the
composition dump. `zabz-tech-linux` was measured and left alone with a dated note: its only install is
0.1.5-rc.1 and the headless profile composes fine on it, so dispatching there is not broken today.

## Residual defect — NOT fixed here, and not caused here

The 15-minute `PersonalSecretary-HarnessSync` on `zabz-tech` **still** skips the presets and profile
steps, naming `0.1.5-rc.1`, even though the machine now runs the 0.2.0-rc.2 pin. Run by hand, from the
same machine, the same guard resolves the right engine:

```
"engineResolvedBy": "running-process", "enginePid": 30396, "engineVersion": "0.2.0-rc.2",
"status": "ok", "missing": [], "conflictDetail": "the RUNNING engine is 0.2.0-rc.2 but
configuration names 0.1.5-rc.1 ($DSH_HOME/profiles -> ...\_npx\1e7f6d9597241db0)"
```

While the task's own log at 14:26:26Z reads `the running engine (0.1.5-rc.1) does not provide` with no
`WARNING --` suffix at all — a combination the checker only produces when it believes a **running
process** from the 0.1.5 root and finds *no* configured conflict.

Working hypothesis, with the code that supports it: `scripts/profile-gate.mjs` (task
`DSH Profile Gate (15m)`, same cadence as the sync) probes candidate `(node, bin)` pairs by executing
`node <bin> -V`; its `binCandidates()` list **does not contain `~/.dsh/engine`** — it tries
`~/dsh-engine`, `~/profiles`, `~/dsh`, then the **npx cache** — so on Windows it runs the 0.1.5 npx
bin. The guard reads the *live process table*, so a transient probe child from the wrong root is a
candidate to be read as "the engine that is running here", which pins the sync in a permanent skip.
Not yet isolated to a single observation; the next session should capture the guard's `--json` **from
the task's own context** and prefer a fix in `profile-gate.mjs`'s candidate list (add the pin first)
over any loosening of the guard.

Note also for whoever picks this up: `check-version-coupled-config.py` reads `--windows-json` defaults
of `<repo>/multi-window/windows.json` and `$DSH_HOME/multi-window/windows.json`, while `dshw.ps1`
reads `multi-window/machines/<COMPUTERNAME>.windows.json` when present — so a `dshInstall` written for
the launcher is not necessarily the knob the guard sees.
