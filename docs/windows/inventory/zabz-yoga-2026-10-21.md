## 3. The one number that does not reconcile — read this before quoting `code`

The per-directory measurements **sum to ~535 GiB on a 476 GiB disk**. Two independent methods
(robocopy `/L /XJ /BYTES` and a python `os.scandir` walk that skips reparse points) agree exactly on
every directory they were both run against — `Program Files (x86)` 10.50 GiB / 61,639 files,
`chumash-timeline` 493,161,921 bytes / 22,516 files, `ProgramData` 46.78 vs 47.10 — so this is not a
disagreement between tools.

Therefore some paths are counted at more than one location. The arithmetic below bounds `code` at
~172 GiB **if** the other rows are right — and the table after it shows that the obvious mechanisms
for such double counting do not hold up, so the bound is indicative, not proven.

```
used (fsutil)                                 449.14 GiB
less Windows 44.60 + ProgramData 47.10
   + Program Files 31.35 + Android 5.84
   + Recycle 3.48 + pagefile 3.50 + misc 0.50  -136.37 GiB
= ceiling for the entire user profile         312.77 GiB
less AppData 62.51 + Downloads 18.46 + .usearch 13.02 + .dsh 12.96
   + .transcript 8.09 + .cache 7.53 + .android 6.34
   + .platformio 2.44 + .gradle 2.06 + accounting 2.04 + rest ~5   -140.45 GiB
= ceiling for `code`                         ~172 GiB
```

**A historical explanation was drafted here and then retracted — do not resurrect it.** It claimed
`measure-space.ps1` had over-reported "on both dates", because the 2026-09-30 inventory recorded
732.97 GiB in a user profile on what looked like a 322 GiB drive. That comparison was between **two
different machines**: the 2026-09-30 document is a `ZABZ-TECH` inventory (§4), where `C:` is
~951 GiB, so 732.97 GiB is entirely plausible. Lesson `L12176` was filed on the retracted reasoning
and is corrected by `L12178`.

Ruled out as the cause, each by measurement:

| Hypothesis | Test | Result |
|---|---|---|
| NTFS compression | `compact /compactos:query`; attributes on sampled files | not in Compact state; `Archive` only |
| Hardlinks | `fsutil hardlink list` on 16 files across 4 repos | exactly 1 link each |
| Symlink/junction following by robocopy | `/XJ` vs `/XJ /XJD /XJF` on `Program Files (x86)`, `_fleet`, `_scratch` | identical every time |
| Reparse points inside `code` | counted every directory: **10,414** (`_scratch` 7,260, `_fleet` 2,399, `_worktrees` 353) | all sampled ones are `LinkType: Junction`, and robocopy skips them |
| The two tools disagreeing | python `os.scandir` (skips reparse) vs robocopy `/BYTES` on `_scratch`, 127k files, 7,260 junctions | **9,347,508,977 bytes both, to the byte** |

**Unresolved.** The mechanism is not links and not compression, and every directory checked agrees
between two independent tools. Treat every absolute figure from the profile walk as an upper bound;
the *ranking* is unaffected because each row came from the same method. The only trustworthy
absolute number in this document is `fsutil volume diskfree`.
