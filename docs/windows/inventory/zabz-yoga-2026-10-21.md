## 3. The one number that does not reconcile — read this before quoting `code`

The per-directory measurements **sum to ~535 GiB on a 476 GiB disk**. Two independent methods
(robocopy `/L /XJ /BYTES` and a python `os.scandir` walk that skips reparse points) agree exactly on
every directory they were both run against — `Program Files (x86)` 10.50 GiB / 61,639 files,
`chumash-timeline` 493,161,921 bytes / 22,516 files, `ProgramData` 46.78 vs 47.10 — so this is not a
disagreement between tools.

Therefore some paths are counted at more than one location. The arithmetic below bounds `code` at
~172 GiB **if** the other rows are right — and the table after it shows that the obvious mechanisms
for such double counting do not hold up, so the bound is indicative, not proven.

```
used (fsutil)                                 449.14 GiB
less Windows 44.60 + ProgramData 47.10
   + Program Files 31.35 + Android 5.84
   + Recycle 3.48 + pagefile 3.50 + misc 0.50  -136.37 GiB
= ceiling for the entire user profile         312.77 GiB
less AppData 62.51 + Downloads 18.46 + .usearch 13.02 + .dsh 12.96
   + .transcript 8.09 + .cache 7.53 + .android 6.34
   + .platformio 2.44 + .gradle 2.06 + accounting 2.04 + rest ~5   -140.45 GiB
= ceiling for `code`                         ~172 GiB
```

**A historical explanation was drafted here and then retracted — do not resurrect it.** It claimed
`measure-space.ps1` had over-reported "on both dates", because the 2026-09-30 inventory recorded
732.97 GiB in a user profile on what looked like a 322 GiB drive. That comparison was between **two
different machines**: the 2026-09-30 document is a `ZABZ-TECH` inventory (§4), where `C:` is
~951 GiB, so 732.97 GiB is entirely plausible. Lesson `L12176` was filed on the retracted reasoning
and is corrected by `L12178`.

Ruled out as the cause, each by measurement:

| Hypothesis | Test | Result |
|---|---|---|
| NTFS compression | `compact /compactos:query`; attributes on sampled files | not in Compact state; `Archive` only |
| Hardlinks | `fsutil hardlink list` on 16 files across 4 repos | exactly 1 link each |
| Symlink/junction following by robocopy | `/XJ` vs `/XJ /XJD /XJF` on `Program Files (x86)`, `_fleet`, `_scratch` | identical every time |
| Reparse points inside `code` | counted every directory: **10,414** (`_scratch` 7,260, `_fleet` 2,399, `_worktrees` 353) | all sampled ones are `LinkType: Junction`, and robocopy skips them |
| The two tools disagreeing | python `os.scandir` (skips reparse) vs robocopy `/BYTES` on `_scratch`, 127k files, 7,260 junctions | **9,347,508,977 bytes both, to the byte** |

**Unresolved — but the per-item numbers are now triple-verified.** Every large component of `code`
was measured three ways (robocopy `Total`, robocopy `Copied`, and `Get-ChildItem -Recurse`) and all
three agree to the byte:

So the items are right and the arithmetic is right, which left the **volume-level figure** looking
like the suspect premise. **RESOLVED 2026-10-22 — it is hardlinks, and the volume was never wrong.**

A full-volume pass with an NTFS file-ID scan (`_disk/scan-dedup.py`, 12,667,067 files, 1,720,873
dirs, 12 errors, 121 min) and a five-worktree sample pass agree:

| Measurement | GiB |
|---|---|
| every file by name (logical) | **541.36** |
| every file by name (allocated) | 539.95 |
| volume actually holds (`fsutil`, calibrated) | **~458** |
| **difference = the same bytes under several names** | **~83** |

The mechanism is pnpm. It installs one copy of a package into a content-addressable store
(`C:\Users\ezabz\AppData\Local\pnpm\store`, 1.55 GiB / 88,050 files) and **hardlinks** it into every
project that needs it. Measured directly: a `package.json` inside three different projects' `.pnpm`
trees reports **87 links**. Five worktrees scanned together read **7.63 GiB by name but 3.26 GiB
unique — 4.37 GiB shared across 359,953 of their 511,336 files (70%)**.

**Consequence for every tool in this estate: name-based sums overcount these trees by ~57%.** The
ranking is still valid; the absolute sizes of anything containing `node_modules` are not.

Two defects found in my own instruments on the way, both worth keeping:

* `DirEntry.stat(follow_symlinks=False)` returns `st_ino = 0` on Windows, so a dedup keyed on it
  reports "no sharing" with total confidence — a first full run gave `unique == logical == 541.36`
  on a 475.83 GiB disk, which is arithmetically impossible. Use `os.stat()`.
* `os.scandir("C:")` means *the current directory on drive C*, not the root; a run aimed at `"C:"`
  silently scanned `~/code` and reported 261.26 GiB as if it were the volume.

## 5c. A defect found in `measure-space.ps1` while doing this

`Measure-One` parsed the robocopy summary with `-split '\s+'` and a fixed index. Because the summary
line is indented, the split yields a leading empty element and **every index shifts by one** — it
read the `Total` column. For most trees `Total == Copied` and nothing shows, but on a tree with a
self-referencing junction robocopy counts every file twice:

```
C:\Users\ezabz\.cache   Files: 134   Bytes: Total 8,085,154,005 = Copied 4,134,303,446 + Skipped 3,950,850,559
Get-ChildItem -Recurse  : 134 files, 4,134,303,446 bytes (3.85 GiB)
```

So `.cache` was reported as 7.53 GiB when it is 3.85 GiB. Fixed 2026-10-21: the columns are now read
by named regex and `Copied` is used. Verification, not assertion: the fixed script run over
`C:\Users\ezabz\code\_scratch` reports **8.51 GiB in 71 folders over 0.01 GiB**, and that plus the
files sitting directly in the root reconstructs **8.71 GiB / 127,431 files**, which is exactly what
`Get-ChildItem -Recurse` reports independently for the same tree. Every future figure from this script should be slightly smaller
and correct. This defect does **not** explain the §3 discrepancy — `_fleet` (11.77) and
`_lpt-staff-kiosk` (1.60) report identical values under `Total`, `Copied` and `Get-ChildItem`.
