# The API wedge of 2026-10-28, and the WAL guard that now prevents it

**Owner's question, 16:14Z:** *"i just got a text and call from you that the comapny api is down"*

**Answer:** the API process was never dead. It was **alive and not answering**, and the text and
call were correct. Two orphaned processes had been burning a core since 26 October, one of them
was holding a read transaction on `/root/authority.db`, and that transaction made the write-ahead
log un-checkpointable. The WAL grew to 10.2 GB on a disk 91% full, and a disk that fills on this
box has already produced a SIGBUS before (2026-09-10, recorded in `H2789`).

## 2. Why a big WAL took the API down

SQLite cannot checkpoint past the oldest reader. PID 377634 held a read transaction open for 42
hours, so `PRAGMA wal_checkpoint(TRUNCATE)` returned `busy=1` the whole time and `(0,0,0)` the
moment it died. A WAL that can only grow is a disk-full event on a 225 GB volume holding a 34 GB
database, and it also makes every fresh read-only connection — which is what `/health` opens —
walk a 10 GB WAL.

The repair, in order, with the readings that proved it:

```
SIGTERM 377634, SIGTERM 585597
PRAGMA wal_checkpoint(PASSIVE)   -> (0, 78, 78)
PRAGMA wal_checkpoint(TRUNCATE)  -> (0, 0, 0)
WAL   10.2 GB -> 416 KB
disk  91% -> 86% (32 GB free)
/health  30 s timeout -> 200 in 0.16 s
https://api.abletelsolutions.com/health -> 200 in 0.9 s, from outside
```

## 4. The guard

`/usr/local/bin/authority-wal-guard.py`, installed from `scripts/authority-wal-guard.py`, run by
`authority-wal-guard.timer` every 10 minutes (units: `scripts/systemd/`).

**Rule A — hot orphan.** `cpu >= 90%` measured over two samples 10 s apart (not the lifetime
average) **and** `elapsed >= 6 h`. Every legitimate long-lived process on this box idles: the four
`ps_mcp_server` instances measured 0.0 / 0.0 / 0.2 / 0.0 %.

**Rule B — WAL pin.** Only when the WAL is `>= 2 GB` (normal range measured on this box:
0.4 MB – 12.5 MB; the four incident peaks were 1.0, 1.8, 17.3 and 10.2 GB).

1. `PRAGMA wal_checkpoint(PASSIVE)`.
2. If **no frames are left undrained**, the WAL is merely trailing → `TRUNCATE`, reclaim, no kill.
3. If frames are left, find what holds `authority.db` open, drop the allowlist, drop anything
   younger than `--pin-min-hours` (2 h), SIGTERM the oldest, re-ask, repeat (max 5).
4. `TRUNCATE` when the WAL drains; **exit 3** if it does not.

**Allowlisted, never killed:** the company API (`uvicorn app.main:app`), the three security
services, `esearch`, `sshd`, `systemd`, `tailscaled`, `cloudflared`, `fail2ban`, `phone-gate`,
`cron`, and the backup / offsite-push / integrity jobs that are *supposed* to hold the database
under `/run/lock/secretary-io.lock`.

**Exit codes:** `0` ran and did what was needed · `2` the guard itself is broken · `3` the WAL is
over the ceiling and still pinned after every candidate was removed. A guard that cannot fix
something must say so; `Result=failed` in `systemctl --failed` is the point.

### The measurement that had to be corrected by its own proof

The first version keyed on `PRAGMA wal_checkpoint(PASSIVE)` returning `busy > 0`. Its own test
refuted that: with an idle reader holding a transaction, SQLite returned `[busy=0, log=42,
checkpointed=0]` — busy zero, nothing drained — and only the later `TRUNCATE` reported `busy=1`.
A `busy`-based guard saw a healthy database and never looked for the reader at all.

The signal is **`log_frames - checkpointed_frames`**, frames that did not drain. That is what the
shipped guard uses.

## 5. Proving it, without touching the data

```
ssh secratary-cloud /usr/local/bin/test-wal-guard.py     # exit 0 = every assertion held
```

Part 1 runs against a **throwaway database** (`WAL_GUARD_DB`), because growing a WAL means writing
rows and test data must never enter the authoritative one:

1. a planted **idle** reader (0% CPU) holding a read transaction pins the WAL, and SQLite reports
   it as frames that did not drain;
2. the guard kills exactly that process and truncates the WAL to zero bytes;
3. a planted process whose cmdline is **allowlisted** is *not* killed, and the guard then exits 3
   rather than claiming success;
4. once nothing pins it, the next run truncates and exits 0.

Part 2 runs against production in **dry-run only**: the guard must see a planted holder as a
candidate, must never list the live API as one, and must kill nothing. It writes to its own state
directory so a test can never leave a misleading status file in `/var/lib/wal-guard`.

Measured 2026-10-28: `all assertions held`.

## 6. The alarm chain had three separate breaks, and two are fixed

| link | state |
|---|---|
| `estate-monitor` detects and records the CRIT | **worked** — 1048 consecutive runs |
| `estate-monitor` notifies a human | cannot, by design (`"NO outbound message of any kind"`) |
| `estate-alerts-to-journal` files a sustained CRIT as a journal `pain` entry | **broken two ways** |
| `r4-liveness-probe` texts and calls on a real outage | **worked** — that is how the owner heard |

The bridge's two defects:

1. **It returned 0 while filing nothing.** At 16:22:00Z it logged `FAILED public_health_status
   REFUSING to write P14347: this id is above everything this machine can see` and then `return 0`,
   so systemd recorded "Finished". Patched: any refused filing now exits 1, so
   `systemctl --failed` carries it. The id refusal itself self-heals on retry — the reservation is
   written before the refusal — but nothing retried while the exit code said success.
2. **The `authority_wal_mb` episode of 27–28 October was never filed at all**, because the id
   allocator was refusing and the exit code hid it.

Left deliberately alone: `disk_free_deficit_gb` stays a last-resort tripwire (`mode="alert"`,
warn below 8 GiB, crit below 4 GiB). This box normally sits at 86–91%, so raising the threshold
would manufacture noise without catching anything the WAL guard does not now prevent.

## 7. Two things found on the way, both fixed

* **The owner-text monitor was blind for nine hours.** `<app>/.env` was rewritten at
  07:23:53Z and `DATABASE_URL` came back *quoted*; `text-health.py` kept the quotes, so its
  prefix strip missed and it read a relative path — six checks failing with `unable to open
  database file`, and C1 failing on `int("'20'")`. `runs.log` pins it: 07:15:03Z was 0 FAIL,
  07:30:02Z was 8 FAIL. Fixed with `_dotenv_value()`; now **20 checks, 0 FAIL**. The app was
  never affected — `pydantic-settings` strips quotes — so only the instrument broke, which is
  the dangerous direction.
* **`dsh_session_ingest` replaced real errors with an `AssertionError`.** Sixteen times in thirty
  minutes, `assert last_exc is not None` fired on an error path where the retry loop had never
  run, so the log named the assert instead of the lock that failed. Now
  `raise (last_exc if last_exc is not None else exc) from exc`.
  **Takes effect at the next restart of `company-api`** — it is imported at start-up, and this
  change was made during shop hours on purpose.

## 8. Traps worth knowing

* **The repo tree and the deployed tree are the same file.** `app/services/dsh_session_ingest.py`
  resolves to inode 179595 under both `/root/personal-secretary-mvp/` and `/opt/company/`, and
  `[ file1 -ef file2 ]` says SAME FILE. Editing "the source" edits the running application's
  files, so a half-finished edit is a live defect. This is also why the ingest patch applied to
  the deployed path without a separate copy step.
* **`/opt/company` is not versioned, `journal.py` and the units are.** The guard's source of truth
  is this repo; `/usr/local/bin` gets it by `scp` and `chmod 755`. Re-install after a rebuild.
* **`busy` from a checkpoint is not a pin.** See §4.
* **A zombie is dead.** `terminate()` first reported `still-alive-after-sigkill` for a process
  that had been killed but not reaped; `/proc/<pid>` persists for a zombie and it holds no lock.
  Dead now means "no `/proc` entry **or** state `Z`".
