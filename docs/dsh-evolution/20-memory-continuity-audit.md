# 20 — The memory and continuity mechanism, audited

**Prepared:** 2026-10-13 · **Method:** one mesh child read the journal mechanism end to end and
returned an evidenced audit. Its numbers are reproduced here with its own caveat attached: it could
not fetch from `origin` (`git origin unreachable rc=128` on both trees, because `origin` fetches from
`secretary-ts` — **the frozen office box**), so it read the newest state the last fetch (2026-10-07)
preserved, plus every git ref it could reach locally.

**Subject:** the machinery that is supposed to make an agent with no continuous memory behave as one
coherent entity across sessions.

---

## 0. The headline

> **There is no one journal.** ~120 divergent git refs each carry a `journal/entries/` tree, and the
> checkout the audit was pointed at is the emptiest of them: **1,644 entries**, against **3,792** on
> `origin/diverged-ZABZ-TECH-20261013` and **3,550** on `origin/main`. The manager's own checkout
> (ZABZ-YOGA, `main`) holds **3,627 entry files**.

**Counts of "open pain" are therefore not reproducible across machines: 162 (the Mac checkout),
366 (`main`), 393 (the authority tree), 373 (what `journal.py status` printed on ZABZ-YOGA).** Every
session on this estate begins with "read `journal.py status` first" — and which record it lands on is
an accident of which checkout the machine happens to have.

**The union of the two largest lineages is 3,854 entries. No ref holds the record.**
Only on ZABZ-TECH: 304 · only on `main`: 62 · on the manager's `main` but missing vs upstream: 1,909
(including 277 pain and 611 handoff entries).

## 1. The mechanism, as built

**Write path.** `journal/entries/<kind>/<id>.md`, one file per entry; kinds
`handoff | lessons | pain | decisions | wins`. v1 marker `<!-- e:kind|ID|date|host|status -->`, heading,
body, optional `<!-- j2 tags= refs= alias_of= legacy_id= sha= -->`. **The only sanctioned writer** is
`tools/journal.py append KIND --title … --body …`, which allocates the id over `entries/`, the cache
and every git ref, and bumps on collision. Status is never an edit: `resolve ID --status … --why …`
appends to `journal/state/status.tsv`, merged by `effective_status()`.
The persona mandates the handoff body format: **CHANGED / IN FLIGHT / BROKEN / NEXT / EVIDENCE**.

**Read path.** `journal.py status` — the always-read page, hard cap `STATUS_BUDGET` = 6,000 B — prints
`NOW.md` (1,800 B cap) + live counts + 8 open pains + `state/owner-questions.md` (4,000 B cap) +
`state/in-flight.md` (`max(400, room//2)`) + drift + a cheap check. Then `newest handoff N`, `list`,
`show`, `search`, `backlinks`, `pairs`, `stats`, `check`, `doctor`, `costs`.
Cache: `index/entries.tsv`, `index/aliases.tsv`, `index/journal.db` (FTS5), `stamp.json`.

**State tier** — the only tier that is rewritten, not appended: `NOW.md` and `state/in-flight.md`
(hand-written); `state/open-pain.md` (generated by `journal.py state`); `state/owner-questions.md`
(generated by `journal.py questions`, a mirror of the authority's `owner_decision_queue`);
`state/status.tsv` (append-only).

**Owner path.** Authoritative: `owner_decision_queue` on the authority via `~/bin/owner-queue.py`
(`add defer next list stats lint resolve answer`). `journal.py` reads it from
`~/bin/owner-queue.py list --all --json`, else `ssh … secratary-ts` (the **frozen** box), 45 s timeout.

**Wake.** `scripts/wake.py` (`flag add claim heartbeat finish reap list stats pause resume await
awaits`), `wake-dispatch.sh` (cron `*/5`), `wake-flag.py`, `scripts/wake/dormant-handoff.py`,
`presets/zabz/skills/secretary-wake/SKILL.md`. Archive: `push-dsh-sessions.mjs` (hourly, row cursor,
at-least-once) + `transcript-archive-run.sh` (ALARM on gap / pull failure / check failure).

## 3. Where it loses things

1. **No single tree.** ~120 refs, never reconciled; the union exceeds every ref. A session on the Mac
   reads 162 open pains and 1,644 entries while the authority holds 393 and 3,792. **Every
   "read `status` first" rule lands on whichever lineage the machine happens to have.**
2. **The health instrument is blind to the dominant defect.** `check` → 0 errors while `pairs` → 121
   collisions and 3 byte-identical duplicates; `check --json` files them as **info**. `docs/mesh/117`
   measured **10** collisions on 2026-09-18 and prescribed the cure; by 2026-10-12 there are **121**.
3. **Stale state shown as fresh.** The local `state/owner-questions.md` says *"83 rows read, 19
   pending, generated 2026-09-17 04:40 UTC"* yet carries today's mtime, so `status` printed
   **"(mirror age 38 min)"**. `_maybe_refresh_questions` refreshes only when mtime > 60 min, and any
   checkout resets mtime — so the gate never fires. The authority holds **161** pending: an **8.5×
   undercount labelled current**.
4. **The state tier is stale, and one file has no reader.** `NOW.md` `Updated: 2026-09-14` (28 days)
   and still quotes 707 entries. `state/open-pain.md` written 2026-09-17 claiming "175 open of 212"
   (actual 393 of 503) — and `grep` finds it only in prose; the read path recomputes live and never
   opens it. `state/in-flight.md` `Updated: 2026-10-05` (7 days).
5. **The one-read page fits only by truncation.** Measured `status` = 4,957 B against a 6,000 B cap
   (`ok=yes`), but `state/in-flight.md` is **24,416 B** and is allotted `max(400, room//2)` — about
   **2% of the state of play**.
6. **Born-broken citations.** ~180 dangling refs and 10 orphan aliases; renumbering left citing entries
   pointing at ids nothing holds, so `backlinks` and `refs=` are unreliable.
7. **Probe and stub pollution left open** (`P2604`, `P2605`, `P2545`, empty-bodied `H83`).

## 4. The owner-question path, end to end, and where it leaks

`owner-queue.py add --question … --recommendation … [--options] [--from-json]` → a `pending` row on the
authority → `next` sorts *blocks-others, then severity, then age* → the owner answers → `answer`
records his words → `resolve` closes → the answer lands in `entries/decisions/`.
The journal side is read-only: `journal.py questions` mirrors pending rows into
`state/owner-questions.md`; the persona says never keep an owner question anywhere else, and the
mirror must not be edited.

**Read live: 447 rows read, 161 pending** — medium 114, high 38, low 9; asked 2026-09-16 → 2026-10-12;
age min/median/max **1 / 4 / 27** days; **96 of the 161 were asked on 2026-10-09 alone**. Oldest
unanswered: **#78, 2026-09-16** — the port of the line for his mother, four fields from a US Mobile
account, with a recommendation to obtain them and never write the PIN into a document.

**Five leaks:**
(a) **the mirror is per-machine** — 161 on the authority, 19 locally — so a session on another machine
can re-ask a pending question;
(b) **freshness is mtime**, so a stale mirror reads as fresh (§3.3);
(c) **duplicates are structural** — three *"lpt-apps-01 health check failed"* rows (#285, #311, #439)
and **six** *"The prepaid AI balance is low"* rows (#334, #429, #433, #440, #442, #444), while
`scripts/collapse-owner-queue-duplicates.py` already exists — i.e. it recurred after being fixed;
(d) **agent-decidable rows are parked on the owner** — health checks whose own recommendation is
"I fix it";
(e) **the always-read page prints only 3 of the 161.**

## 5. Gaps against a real specification

- **(a) Never lose an owner decision.** There is no append-only record of his words at answer time:
  `answer`/`resolve` update a row in place, and the only durable copy is a decision an agent later
  writes — so **a decision is lost exactly when the agent forgets**. Nothing reconciles answered queue
  rows against `entries/decisions/`.
- **(b) Never re-ask an answered question.** No content-based dedup key — six identical prepaid-balance
  rows prove it. And the read path can be 8.5× short while calling itself fresh, so the re-ask is
  invisible when it happens.
- **(c) Never re-commission an audit.** There is no queryable audit registry: the systems register is
  prose an agent must remember, there is no `audit` kind and no covered-area index. The evidence it
  fails: 66 both-live near-identical lessons and 9 both-live near-duplicate pains.
- **(d) Exact state of play in one read.** It does not exist. `status` cuts `in-flight.md` from
  24,416 B to a few hundred; `NOW.md` is 28 days stale; `open-pain.md` is 25 days stale and unread;
  the authoritative queue is on another machine and mirrored unreliably. **The numbers are live; the
  prose is up to a month old.**

## 6. Recommended changes, prioritised

1. **Make one lineage canonical.** Reconcile and retire the `diverged-*` refs; add a push gate that
   refuses any `entries/` id-set which is not a superset of the tip. Nothing else can be trusted
   first. At minimum, tell every checkout which ref is truth.
2. **Promote collisions and byte-identical duplicates to ERROR in `check`**, and put `pairs` into the
   always-read page's cheap check so it stops flattering the tree.
3. **Measure mirror freshness from the `generated`/`Provenance` line, never mtime**, and refresh on
   content age regardless of a fresh mtime.
4. **Reconcile answered queue rows into `entries/decisions/` both ways**; extend `owner-queue.py lint`
   to require a matching decision id for every non-pending row; add a question content-hash dedup key.
5. **Fix or delete the state tier.** Regenerate `open-pain.md` on a schedule, or drop it — nothing
   reads it. Give `status` a budget split that shows the head of `in-flight.md`, or add a required
   2 KB `state/now-next.md`.
6. **Repair citations before any further renumbering** — the ~180 dangling refs and 10 orphan aliases.
7. **Enforce the handoff contract at write time.** `append handoff` should warn or refuse without a
   mandated section (58.6% have `NEXT`; 33% have all five). `dormant-handoff.py` should key on a
   *session that ended without a handoff*, not only on the age of the newest one.

## 7. Honesty

**Read with output:** every count and age above (`status`, `stats`, `costs`, `doctor`, `check`,
`check --json`, `pairs`, `list --json`, `newest`, plus `git ls-tree`/`git show` across refs and an
extracted `origin/diverged-ZABZ-TECH-20261013` tree). Section-compliance, duplication and
actionability figures are the child's own regex/token analysis over entry files, **not** a `journal.py`
command.
**Inferred:** that a git operation reset the local mirror's mtime; that the 2026-10-09 owner-question
cluster was a bulk filing; that the Mac's pain ledger stopped on 2026-09-24.
**Refused / unavailable:** `journal.py costs` reports `git origin unreachable (rc=128)` on both trees,
so the estate's newest state could not be fetched — only what the 2026-10-07 fetch preserved. The
child ran no write command, so it cannot report the live `owner_decision_queue` contents, the live wake
store, or whether the deployed authority `journal.py` matches the copy in git.

## 8. FIXED AND VERIFIED, 2026-10-13 — the owner-question mirror was reading a stopped server

The finding in §4(c) — *"the mirror is per-machine: 161 on the authority, 19 locally"* — had a cause
nobody had looked for, and it was one line.

`journal/tools/journal.py`, `_queue_from_authority()`, hardcoded the ssh fallback to **`secratary-ts`**,
the **office box**. That box was the authority until 2026-10-11T05:43:36Z and has been **frozen**
since; the authority is `secratary-cloud`. So **every machine except the authority itself read the
owner's live question queue from a server that stopped at the cutover, and reported it as current.**

**Measured before and after, same command, same minute:**

| | open | closed |
|---|---:|---:|
| before the fix (`journal.py questions`) | 143 | 307 |
| after the fix | **162** | **326** |
| ground truth, `/root/authority.db` on `secratary-cloud` | **162 pending** | 326 (218 resolved + 71 dismissed + 37 answered) |

**The mirror now agrees with the authority exactly.** The difference is not a rounding: 19 rows were
invisible and **11 rows it showed as "waiting on him" were already answered** — so an agent on any
machine could have re-asked the owner a question he had already closed. That is §5(b), the "never
re-ask an answered question" gap, happening live.

**What changed:** the authority is tried first; the frozen box is tried **last**, so a machine that can
only reach it degrades rather than losing the queue — but the comment now says plainly that a reading
taken from the frozen box is a reading from a stopped server. Verified by running `journal.py questions`
and comparing its counts to a read-only `SELECT status, COUNT(*)` on the authority.

**The general defect, because it will recur:** a hardcoded fallback host is a *time bomb keyed to a
migration*. When a service moves, every script that reaches it by name keeps working — against the old
copy — and nothing fails loudly. `secratary` is a prefix of `secratary-cloud`, so a grep does not catch
it either. **When a host moves, grep every script for the old name and check what each one is for;
"it still works" is exactly what reading the frozen box looks like.**

## 9. The divergence, measured exactly — 2026-10-13 14:08Z

§0 said there is no one journal. Here are the numbers, counted by id across the two trees that matter
most. **Every figure below is a file count or an id-set difference, not an estimate.**

| | entry files | open pain | branch | head |
|---|---:|---:|---|---|
| **ZABZ-YOGA** (where this audit was written) | **3,663** | 373 | `main` | `c647e7cd` |
| **secratary-cloud** (the authority) | **3,478** | **336** | **`hk/28-refresh-deployed-sources-20261013`** | `04661ae` |
| `origin/diverged-ZABZ-TECH-20261013` | 3,792 | — | diverged | — |

**Ids only in one tree:** ZABZ-YOGA **334**, the authority **149**.
**Union: 3,812. Neither tree is a superset of the other.** So a merge is not a fast-forward in either
direction, and "3,663 entries" and "3,478 entries" are both true and both incomplete.

**Two facts fall out that are worth more than the counts:**

1. **The always-on machine is on a feature branch.** `secratary-cloud`, which runs the schedules that
   keep the estate alive, has its `harness-config` checked out at
   `hk/28-refresh-deployed-sources-20261013` — not `main`. Anything a session has merged to `main`
   since that branch was cut is **not on the authority**, which is the machine most likely to need it.
2. **Open pain differs by 37** between the two trees (373 vs 336) while the entry counts differ by
   185. The two numbers move independently, so neither can be used to predict the other: a tree can
   gain entries and lose open pain, or the reverse. **Any claim of the form "there are N open pains"
   must name the tree it was read from.**

**What a union would take, and why it is its own job.** The union is finite and knowable: copy 149
files one way and 334 the other, rebuild the index, then run `journal.py check`. The hazard is not the
copy — it is that **121 base-id collisions already exist** between lineages, so bringing two trees
together can make one id mean two entries in the same tree, and the repair (`repair-ids --apply`)
renumbers ids that other entries cite by name. That is a migration with a verification plan, not a
step in a session that is also doing something else. **It is the next session's first job, and
`P3164` is the live proof that code in this repo can diverge the same way.**
