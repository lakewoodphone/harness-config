# The Journal — the mechanism by which the CEO grows instead of restarting

**This is not documentation. It is the organ that makes continuity possible.** The previous
occupant of this seat named the problem and did not mechanize the fix:

> "If I forget to write notes for future-me, I literally cease to exist as a coherent entity."

It was right. Because nothing mechanized it, the same audits were commissioned repeatedly, the
same files were re-litigated, and 55 improvements piled up unapplied.

**Rewritten 2026-09-14 (v2).** `AUDIT.md` holds the measurements that forced it and `SPEC-v2.md`
the contract it implements. The one-paragraph version: v1's month-sharded logs reached **250 KB
per file**, the always-read page **overflowed its own budget and exited 1**, printing one entry
**read a quarter of a megabyte**, and **19% of the record was the same entry written twice** by
concurrent sessions. v2 is one file per entry, a cache that heals itself, and a query surface with
real flags.

## The tree

```
journal/
  FORMAT                 "2" — the format generation. Read by check and doctor.
  README.md              this file: the map and the rules.
  AUDIT.md SPEC-v2.md     what was wrong, measured; what replaced it, as a contract.
  NOW.md                 STATE. Rewritten, never appended. `status` prints a capped slice of it.
  state/                 STATE, small and mutable:
    open-pain.md           GENERATED by `journal.py state` — every pain without proof of being done
    owner-questions.md     GENERATED by `journal.py questions` — mirror of the authority's queue
    in-flight.md           hand-written: what is mid-work, what is broken, what is next
    status.tsv             append-only status corrections ("P46 is done, because ...")
  entries/               THE LOG. One file per entry: entries/<kind>/<id>.md
    handoff/ H1.md H2.md …     111 files
    lessons/ L1.md … L290.md   290 files
    pain/    P1.md … P93.md     93 files
    decisions/ D1.md … D102.md 102 files
    wins/    W1.md … W78.md     78 files
  index/                 GENERATED CACHE. Disposable: `entries/` is the truth.
    entries.tsv            one row per entry, v1's exact 12 columns (see "Compatibility")
    aliases.tsv            alias_id -> canonical_id, so a collapsed copy is still reachable
    stamp.json             the signature of entries/ this cache was built from
    journal.db             sqlite3 + FTS5 for search and backlinks (gitignored)
  log/                   FROZEN legacy shards. Read ONLY by `import-legacy` and `check`'s
                         drift test. Never by `status`, `show`, `search` or `list`.
  archive/               the pre-v2 record: the six flat files, moved duplicates, migration notes.
  reference/             topic documents, read on demand, not part of the log.
  tools/
    journal.py           v2 — the only *sanctioned* writer.
    selftest.py          240 checks: format, flags, budget, migration order, concurrency, LF.
    bin/j  bin/journal.cmd   convenience wrappers.
    archive/journal-v1.py    frozen v1, for the compatibility test.
```

An entry file is a **single-entry shard** in v1's exact shape:

```
<!-- e:lessons|L173|2026-09-14|ZABZ-YOGA|open -->
**L173 · The title**

The body, verbatim.
<!-- j2 tags=journal,provenance refs=L172,D50 sha=4f2a91c3 alias_of= legacy_id= -->
```

Line 1 is v1's marker untouched, line 2 is the heading, the body is everything between, and the
last line is optional metadata. That shape is why the migration is a *split*, not a rewrite:
`check` proves byte preservation by comparing whitespace-normalised source bytes with the blocks
written, and the proof currently reads **0 B of residue across all nine legacy shards**.

## The read path, with measured costs

| Question | Command | Measured (674 entries, 2026-09-14) |
|---|---|---|
| Where do I stand? | `journal.py status` | **5,986 B, 97 ms**, exit 0 even when a section is cut |
| What happened last? | `journal.py newest handoff 2` | 4.7 KB, 100 ms |
| What is that id? | `journal.py show P46` | one file opened, **9 ms** |
| Have I hit this before? | `journal.py search "<words>" --kind lessons --since 2026-09-14` | 105 ms, bounded snippets |
| What is open? | `journal.py list --kind pain --status open` | 96 ms, never prints bodies |
| What does the tree cost? | `journal.py costs` | the table above, measured live |
| Is the tree healthy? | `journal.py doctor` | format, cache, lock, drift, sqlite/FTS5, git |
| Is the record intact? | `journal.py check` | exits non-zero **only** on a real ERROR |

Every read takes `--budget BYTES`, `--limit N`, `--json`, and truncates during assembly with a
visible `… (+N more)` — a page is never long *and* silent. **Never read `entries/` or `log/` end
to end by hand**, and never `cat` a shard: the whole point of the tree is that no question costs a
context window.

## Flags

```
journal.py status   [--full] [--budget N] [--json]
journal.py list     [--kind K]... [--status S] [--since D] [--until D] [--tag T] [--host H]
                    [--limit N] [--sort newest|id] [--long] [--json] [--budget N]
journal.py newest   KIND [N] | -k KIND -n N [--full]
journal.py show     ID... [--full] [--refs] [--all]
journal.py search   PAT... [--kind K] [--since D] [--status S] [--tag T] [--limit N]
                    [--context N] [--regex] [--legacy] [--sort relevance|newest] [--budget N]
journal.py backlinks ID          # which entries cite this id
journal.py pairs                 # historical base-id collisions: one number, two entries
journal.py stats [--top N]       # counts, bytes, per-kind, per-month, biggest entries
journal.py kinds | state | questions [--offline] | index [--force] | next-id KIND
journal.py check [--fix] [--quiet] [--json] | costs | doctor | selftest
journal.py append KIND --title T (--body - | --body TEXT | --body-file F)
                    [--date D] [--host H] [--status S] [--tags a,b] [--refs X,Y]
                    [--alias-of ID] [--dry-run] [--no-fetch]
journal.py resolve ID --status done|open|retracted|superseded|blocked --why "..."
journal.py import-legacy [--apply]        # absorb log/** and the flats (also `import-flat`)
journal.py migrate-v2 [--apply]           # split log/** into entries/, then absorb the flats
journal.py dedupe [--apply]               # exact-identity duplicates -> archive/duplicates + alias
journal.py repair-ids [--apply]           # renumber an id that collides with different content
journal.py gc-legacy [--quiet-hours N] [--apply]   # freeze log/** into archive/ once quiet
```

Global: `--root PATH` (any journal tree, for tests and repairs), `--json`, `--budget`, `--quiet`,
`--no-color`. The wrappers are `journal/tools/bin/j` (sh) and `journal.cmd` (cmd/PowerShell).

## Writing rules

1. **Write for the self that wakes up with no memory of this.** Not a summary of the conversation —
   the transferable fact, with its evidence.
2. **The only sanctioned writer is `tools/journal.py append`.** It allocates the id over `entries/`,
   the cache and every git ref, and **never writes an id that already exists with different
   content** — it bumps and says so. Writing into `entries/` by hand is how the v1 tree got 220
   duplicate copies.
3. **Append-only.** An entry is never edited to look better in hindsight. A wrong entry is corrected
   by a *new* entry citing it; a status change is a row in `state/status.tsv`. The record of having
   been wrong is the most valuable thing here — the most expensive failures in this system's history
   were confident errors.
4. **The state tier is different.** `NOW.md`, `state/in-flight.md` and the generated files are
   rewritten. That is legal *only* there, and each carries `Updated:`.
5. **One source of truth per thing.** Owner questions: `owner_decision_queue` on the authority.
   Harness configuration: `harness-config`. Company data: the authority. Every generated file says so
   in its header.
6. **Ids are handles, not order.** `L41b` exists because two machines once chose 41 twice; it still
   means *that* entry and always will. Never renumber to tidy up — `repair-ids` only exists for an
   id that means two different things, and it leaves an alias behind.

## Integrity, and what to do when it complains

`check` is quiet on purpose: **0 errors** on a healthy tree, and an ERROR is always actionable.

| Symptom | Command |
|---|---|
| `check` reports a stale sha or a CRLF file | `journal.py check --fix` (re-emits those files in canonical form) |
| two entries with the same identity | `journal.py dedupe --apply` (moves the later copy to `archive/duplicates/`, records an alias) |
| one id, two different entries | `journal.py repair-ids --apply` (renumbers, records the alias) |
| something was written to `log/**` or a flat file by a stale machine | `journal.py import-legacy --apply` |
| the cache looks wrong | `journal.py index --force` — it is derived; deleting it costs nothing |
| a read is slow | `journal.py costs`, then look at the tree sizes it prints |

**Rebuilding from the legacy sources** (the procedure used on 2026-09-14, which lost nothing): park
the derived tree — `entries/` and the four generated files under `index/` — move it aside, run
`journal.py migrate-v2 --apply`, then carry back any entry whose identity is not in the legacy
sources (those are the entries written *after* the last migration). Verify with
`python _scratch/j-verify.py`, which parses the legacy sources with the **frozen v1 parser** and
proves every one of the 1,235 legacy entries survives by identity, that no id means two different
entries, and that the read targets in `AUDIT.md` are still met.

## Compatibility, because the fleet drifts

Three machines run this repo and they do not update at the same moment. So:

- `index/entries.tsv` keeps **v1's exact 12 columns**, and `line_start/line_end` point at the one
  entry file, so a machine still running v1 can `show` an entry and — more importantly — `next-id`
  correctly instead of restarting at 1 and recreating the collision scar. Verified by running the
  frozen v1 tool against the v2 index on every `j-verify` run.
- Entry files begin with v1's marker line, so a v1 reader sees them.
- An append that lands in `log/**` after the migration is absorbed, not lost. `check` reports the
  true drift count, computed by exact identity, and `import-legacy` closes it.
