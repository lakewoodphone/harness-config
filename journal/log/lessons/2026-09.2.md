**L223 · 2026-09-14 - The journal append path corrupted every non-ASCII body from Windows, and check cannot see it (root cause fixed with an end-to-end proof)**

**L · 2026-09-14 · The journal's own append path corrupted every non-ASCII character written from Windows, and `check` cannot see it**

Root cause, found by comparing code points rather than reading the console: in
`journal/tools/journal.py`, `append` read the body with `sys.stdin.read()`, which decodes using
the **platform's locale encoding** — cp1252 on Windows — while `main()` reconfigured only
`sys.stdout` to UTF-8. Every `—`, `·`, `→` and curly quote arriving on stdin was decoded as
cp1252 and then re-encoded as UTF-8 on write, so one character became three (`â€”` for U+2014).
43 sequences landed in the shards before it was caught. The same defect was in the
`--from-json -` path.

**Why it survived so long:** `journal.py check` validates ids, structure, ordering and the
state tier — it does **not** validate character encoding, so a corrupted body writes "cleanly"
and reports 0 errors. The corruption was invisible to every integrity gate the journal has.

**Fix:** a single `_read_stdin_utf8()` helper that reads `sys.stdin.buffer` and decodes UTF-8
explicitly, used by both stdin paths, plus `sys.stdin.reconfigure(encoding="utf-8")` in `main()`
alongside the existing stdout line. Nothing depends on the platform default any more.

**Proof, end to end, not by inspection:** the exact PowerShell pipe that used to corrupt the
text (`$body | python journal/tools/journal.py append wins --body -`) now stores
`0x2014, 0xb7, 0x2192, 0x201c, 0x201d, 0x2018, 0x2019, 0x2022, 0x2265` — 9 expected code points,
0 mojibake lead bytes. Entry **W42** is that probe; it exists only as this proof.

**Two mistakes were made in the *diagnosis* worth keeping:** the first repair script expected
U+009D as the third byte of the em-dash sequence when the real one is U+201D, and it scanned a
hard-coded shard list that named `handoff/2026-09.md`, which does not exist — the handoff shard
is split into `.1` and `.2`, so the newest entry was never examined. Both were corrected by
reading the actual code points from the file and globbing the file set
(`rglob("*.md")`). When repairing an encoding defect, never type the mojibake from memory and
never list the files by hand.

Kept: `harness-config/scripts/repair-mojibake.py` (report by default, `--apply` to write,
idempotent, and it deliberately does **not** touch a line containing the word "mojibake" so it
cannot corrupt its own documentation).

**L224 · A platform can accept a config rule and silently ignore it; prefer the one that complains**

A platform can accept a config rule and silently ignore it. Cloudflare Pages took my
`/api/* /api-not-available 404` rule without a single warning and served the SPA shell with
status 200 instead. The same rule on Workers Static Assets is refused loudly ("Valid status
codes are 200, 301, ..."). The loud rejection was the safer platform behaviour; the quiet one
is the dangerous one, and only probing the live deployment revealed it.

Rules:
(a) Absence of a warning is not acceptance. When a platform consumes a config file, verify the
 resulting BEHAVIOUR per rule, not the exit code or the parse log.
(b) Prefer the platform that complains. Given two hosts, the one that rejects an invalid rule
 is safer than the one that ignores it, because the failure mode of the second is a silent
 wrong answer in production.
(c) When a rule cannot be expressed in config, put the behaviour in code and scope it narrowly
 (here: a Pages Function on /api only, so it costs nothing and cannot affect page views).

AND A MEASUREMENT BUG IN THE SAME SESSION, worth its own line: I reported that the deployed
bundle was missing the Waze panel because I checked with
`$js.Contains('DRN fleet')` where `$js` was a PowerShell ARRAY of lines from curl, not a string.
Array `.Contains()` does exact-element matching, so every multi-word needle came back false. The
deployment was correct; my instrument was broken. Hash-comparing the live file to the local build
(identical sha256) settled it in one step. This is the third time in one session that the tool
doing the measuring was the thing that was wrong (see L207 and L212) - so:
(d) Before reporting an absence, prove the measuring instrument on a case where the answer is
 known to be PRESENT.

Also worth recording, because it briefly looked like a production outage I had caused: immediately

**L225 · A marketplace price column is not what it looks like: Swappa's 'Avg Price' is ASKING, not sold, and misreading it corrupted a margin model twice in one day**

**Rule: never assume a price table's column is what it looks like. Read the exact `<th>`, and check whether the
page renders two different price blocks.**

**Evidence — this cost two independent research passes the same wrong answer, same day.** Swappa's
`/prices/apple-iphone-*` pages show a per-carrier table whose column header is literally `<th>Avg Price</th>`,
meaning the average **asking** price of live listings. They also render a **price-trend chart** whose Y axis is
titled "Avg Price (USD)" and which carries monthly history. Reading the chart's Jul/Aug points as an achieved
**sale** column produced $136 for an iPhone 11 64GB where the table says $168. I built a margin model on that
misreading; a parallel research pass built a different margin model on a different misreading of the same page.
Both were confidently wrong, in opposite directions, on the number the whole recommendation rested on.

**Two lessons, not one:**
1. **Verify the header, then verify the value's *role*.** "Avg Price" on a marketplace can mean asking, sold,
 or a blend. Asking and clearing differ by **$31-$69** on these models, and the gap is *larger on the newest
 models* — so a misread lands hardest exactly where the conclusion is most sensitive.
2. **When a distributor's wholesale price is above the retail clearing price for the identical handset, stop
 and reconcile — do not average it away.** That contradiction is the single most informative signal in a
 sourcing dataset, because it means one of the two numbers is not what it claims. Here it resolved to a
 three-tier price list (dealer/bulk vs per-grade market quote vs certified-pre-owned) where only Tier 1 is a
 cost basis; using Tier 2 as cost was a silent **$23-$44/unit** error.

**Method that works:** put the probe to the model as a question with a named falsifier ("a distributor cannot
rationally charge more than the marketplace clears the same device for — which number is wrong?"), and require
a reconciliation with evidence rather than a hedge. Both errors above surfaced only when the contradiction was
stated as a hard question rather than smoothed into a range.

**L226 · A price page can carry TWO series; a truncated extraction silently hands you the wrong one**

EVIDENCE: while building a bulk-iPhone price report (2026-09-14), I built a margin model on
Swappa "/en/prices/<model>" figures read from the carrier table's "Avg Price" column. An
adversarial verifier pass reported that Swappa ALSO publishes a "Storage Prices" table with
"Avg list price" AND "Avg sale price" (actual completed transactions). My readability
extraction had truncated that second table, so I had only ever seen the asking series -- and I
had labelled it "average sale price" in a report whose whole section 0 promises no number is
invented. I then CHALLENGED the finding, arguing the 136/149 figures were trend-chart monthly
points. I was WRONG: fetching raw HTML with start_index into the late page body showed a table
captioned "Storage Prices for iPhone 12, Updated September 14, 2026" with headers literally
"Avg list price | Avg sale price".

IMPACT: the asking series overstated the resale ceiling by 11-33% on every row. Correcting it
moved the report's headline margin from "+16/unit, iPhone 12 is the sweet spot" to "-63/unit,
no profitable wholesale channel exists". The recommendation inverted.

RULE:
(1) A price page can publish TWO different series under similar labels. A truncated extraction
 silently hands you the wrong one and no error surfaces. On a long page, fetch raw HTML in
 start_index slices until the whole body is seen, or grep the raw bytes for markers like
 "Avg sale", "list price", "Updated" -- do NOT trust a readability extraction's tail.
(2) When someone challenges a number you read, re-fetch the SOURCE BYTES before defending it.
 My defence was plausible and wrong; the raw HTML settled it in one call.
(3) Distinguish asking from achieved EVERY time. A benchmark labelled "average price" is
 asking; only "sale" / "sold" / "completed" is achieved.
(4) 13% marketplace fees are charged on SALE PRICE, not on cost. My own report's prose said
 "sale" while its table computed on cost -- a label bug that would mislead anyone re-running
 it.
(5) A single wholesale quote is not a cost basis. The same SKU appeared at two very different
 prices on one platform on one day; quote twice, and record the SPREAD across sellers, not
 just a point value.

**L227 · journal.py append --body takes a FILE PATH or -, never inline prose**

EVIDENCE: on 2026-09-14 I tried `journal.py append lessons --title X --body 'some text'` and got
OSError/FileNotFoundError naming my literal text as a missing file. Source at line 731 shows
`Path(args.body).read_text(...)`, i.e. `--body` is a FILE PATH or `-` for stdin -- it is NOT an
inline string, and `append --help` does not say so (it just prints `--body BODY`).

The correct invocation is stdin:
 Get-Content body.txt -Raw | python $J append lessons --title '...' --body -
(Note the journal's own history: f344a71 "read stdin as UTF-8 so append cannot corrupt
non-ASCII bodies" -- so stdin is the supported path and is encoding-safe.)

SECOND FINDING, worth not re-deriving: a successful append still prints `journal.py check`
output and EXITS NON-ZERO, because check failures are pre-existing (60 duplicate ids, L1-L46
duplicated across log/lessons/2026-09.md and 2026-09.1.md). Documented already as P71: "The
journal is mid-merge with 213 duplicate-id errors, so its integrity check no longer..." So:
DO NOT read a non-zero exit from `append` as "my entry failed" -- confirm by searching for the
entry. My entry did land (L226) despite exit code 1.

RULE:
(1) `journal.py append <kind> --body` takes a file path or `-`; pipe the body via stdin.
 Never pass inline prose.
(2) A non-zero exit from `append` after the entry is written is the pre-existing duplicate-id
 debt (P71), not a failure of your write. Verify with `search`, not with the exit code.
(3) Do not shell-interpolate prose into a --body argument: PowerShell here-strings and double

**L228 · Workflow results cap at ~50KB and truncate silently - agents must write to disk and return an index**

WORKFLOW RESULTS HAVE A ~50 KB OUTPUT CAP, AND EXCEEDING IT SILENTLY DESTROYS THE ENTIRE RUN. A 12-agent research workflow whose agents returned verbose structured prose produced a 523 KB return value. The tool response was truncated AND the "full formatted result" spill file on disk was itself only 50 KB - so agent 1 survived, agent 2 was half-cut, and agents 3-12 (523 KB of paid-for research) were lost with no error. Two agents had already produced 24 and 50 verified prices that had to be re-bought.

THE FIX THAT WORKS: have every workflow subagent WRITE its full report to a file on disk and return ONLY a compact index (name/url/status/verdict + one line under 200 chars each + a report_path). The return value stays small, nothing truncates, and the depth survives on disk where it can be grepped selectively instead of read into context. Applied immediately on the retry: 12/12 agents succeeded, 13 report files totalling ~600 KB on disk, return value ~30 KB. Cost of the lesson: one full duplicate research run.

COROLLARY: the same pattern beats the cap for COST, not just safety. Reading 600 KB of reports would cost ~150k tokens; extracting only the pipe-table price rows with a Python pass and reading the 25 KB result cost ~7k. When a fan-out's job is to produce structured data, never read the reports - parse them.

EVIDENCE: session 2026-09-14, iphone-sourcing-run1 vs run2. Spill preserved at code/research/bulk-iphone/_partial-run1-class1a-class1b.txt.

**L229 · 2026-09-14 - Deploying by restarting manufactures work sessions, and they contaminate the failure rate**

**L · 2026-09-14 · Deploying by restarting the service manufactures work sessions, and they land in the failure statistics**

Noticed while reading the work queue: work sessions appeared at 15:30, 16:03, 16:09 and 16:13 — each
within about two seconds of an `systemctl restart secretary-api.service` I had just issued to deploy a
fix. Four of my six restarts that afternoon produced a session.

The mechanism is ordinary, not a defect: the autopilot loop starts with the process, `work_mode` is
one of the subsystems a tick runs, so the first tick after a restart processes the work queue and
creates a session. That session then runs while the process is still warming — memory pressure, cold
caches, a database WAL that was just checkpointed — and it is more likely than usual to exhaust its
budget without completing.

**Why this is a lesson rather than a footnote.** I measured "96.5% of the newest 400 sessions fail" and
used it as evidence that the work loop is broken for essentially every task. That conclusion survives
— 400 sessions over seven days cannot be explained by a handful of deploys — but the measurement is
contaminated by my own activity, and I would not have known if the timestamps had not lined up so
obviously. **A number I produced by acting on the system is not a number about the system.**

Two rules worth keeping:
1. When a fix is deployed by restarting, note the restart time, and exclude or flag the sessions that
 start within a minute of it before drawing a rate from the data. The `[NO-ACTION:]` marker and
 `output_log` make that filter possible; nothing else did.
2. Prefer a deploy path that does not restart the world. For the kernel it was free (a cron-run script
 picks up the change on its next run). For the API it is not, and that asymmetry should influence
 where a change goes.

This does not weaken the case that the work loop is broken: 75336 failed on the step budget under no
restart at all, and the pre-existing 400-session window is dominated by sessions nobody was deploying
during. It only means the exact percentage is not as clean as it looked.

**L230 · 2026-09-14 - An observability change that is not persisted is no change, and my measurements were the unreliable part**

**L · 2026-09-14 · An observability change that is not persisted is indistinguishable from no change, and I shipped one**

The `[ACTIONS:]` / `[NO-ACTION:]` markers went only into `accumulated_output`. That variable is an
in-memory accumulator feeding the next prompt; it is **never written to the database**. The persisted
text comes from a different argument entirely:

 update_work_session(..., output_append=f"Step {current_step}: {cleaned[:500]}")

So after deploying the instrumentation, **zero rows carried a marker**. I had already written a
journal entry explaining that the instrument would answer the question, and it could not have.

**How it was found, which is the point.** Not by re-running the probe, not by assuming a stale
process, and not by re-deploying. By grepping for the literal text the log actually contains — the
log says `Step 1: <prose>` while the line I had edited writes `--- Step N ---`. Two different formats
means two different lines, and the one that persists was not mine.

**Three durable rules.**
1. Before instrumenting, find the line that writes the artefact you want to read. Grep for the text
 the artefact *already* contains; do not infer the writer from the shape of the output you hope for.
2. A marker is only observable if it reaches the store a human or a query reads. In-memory
 accumulators, return values and log-only paths are not stores.
3. Verify an observability change the way you verify a data change: read back a row, not the source.

**The pattern behind this, stated plainly because it is now three rounds running.** My *measurements*
have been the least reliable part of this work, not my fixes:

| round | claim I made | what was actually true |
|---|---|---|
| 4 | "386/386 failed sessions executed no action" | the log field I searched never contained that text; a measurement artifact |
| 5 | "96.5% of sessions fail" as a clean rate | my own deploy restarts manufactured sessions inside the window |
| 6 | "deploying this instrument will answer the question" | it wrote to a variable that is never persisted |

Each was caught the same way — by checking the mechanism rather than believing the number — and each
correction came from the system's own record. The rule that keeps emerging: **a number produced by
acting on a system is not a number about the system, and a claim about what a tool will do is not
evidence that it does it.** The fixes themselves have held up under their tests; my confidence about
what I had measured had not earned the same.

**L234 · 2026-09-14 · Do the expensive reshaping in the engine, not in a Python loop**

To
de-duplicate 1,839,746 paths that differ only by case on Windows, I updated a key per row and deleted
duplicates one at a time. It burned **1,016 s of CPU without finishing** and I killed it. SQLite's
`COLLATE NOCASE` does the same job at the engine level, and rebuilding the table in one bulk
`INSERT ... SELECT ... GROUP BY LOWER(path)` finishes in seconds.
*Rule:* when a task needs a per-row loop over a large table, first ask whether the database can express
it as one statement. A loop that is "obviously correct" is the slow answer, and its slowness is easy to
mistake for the size of the job.

**L235 · 2026-09-14 · pytest crashes in its own tmpdir cleanup on ZABZ-YOGA, and the crash eats the result summary**

**L237 · 2026-09-14 · When an audit finds a security defect, reproduce the exact trigger before writing the severity — the loose phrasing changes what the fix has to be**

The backend audit reported that an empty `LPT_WEBHOOK_SECRET` "exposes every `/admin/*` route to anyone
who can reach it". I verified the branch myself and it was real, but the trigger was narrower: the
fail-open return sat *behind* the "no `Authorization` header at all" early return, so the caller needed
**some** Basic credential — `curl -u anything:anything`. A request with no header was already 401.
*Rules:* (a) "anyone who can reach it" and "anyone who sends any credentials" produce the same fix but
different urgency, different blast-radius arithmetic, and different evidence — read the code path to the
branch, then write the sentence; (b) my own first test encoded the loose version, failed, and was right
to fail: a test that fails because it repeats the audited claim's imprecision is the test doing its job,
and the correction belongs in the claim, not in the test; (c) state production exposure **separately**
from the latent defect with its own probe and timestamp, because "this is a breach" and "this is a
footgun that has not fired" call for different behaviour from the owner.

**L238 · 2026-09-14 - STOP SEARCHING was demonstrably present in the prompt and demonstrably ignored**

**L · 2026-09-14 · A prompt correction that is demonstrably present and demonstrably ignored: STOP SEARCHING did not work**

W61 deployed a correction that prepends, after two consecutive read-only steps:

 STOP SEARCHING - 2 consecutive steps only READ things.
 You have learned enough to start. Take a MUTATING action in this step:
 write or edit a file, create the artefact, update or close the task.
 If you genuinely cannot act, say why and include [WORK_DONE].

**The wiring is correct, and I verified it rather than assuming.** Building the real work prompt on the
authority with `_readonly_steps` set to 0, 1, 2 and 3 gives exactly the intended behaviour: absent at 0 and
1, present and **first line of the prompt** at 2 and 3.

**And it changed nothing.** Session **75343**, started 17:09:45 — after the deploy — ran five steps:

 Step 1 [ACTIONS: 2 (memory_search, list_dynamic_tools)]
 Step 2 [ACTIONS: 2 (memory_search, list_dynamic_tools)]
 Step 3 [ACTIONS: 2 (memory_search, list_dynamic_tools)] <- correction was in this prompt
 Step 4 [ACTIONS: 2 (memory_search, list_dynamic_tools)] <- and this one
 Step 5 The previous steps only ran memory_search and list_dynamic_tools without
 producing concrete output. Let me take decisive action: examine the memory
 system, identify optimization opportunities, and complete the task.
 [ACTIONS: 2 (memory_search, list_dynamic_tools)] <- and this one
 [STEP_BUDGET_EXHAUSTED]

Three consecutive steps were told, in the first line, to stop searching and take a mutating action. All
three searched. The model's step-5 text shows it *understands* the problem and still does the same thing —
which is the same pattern as 75341, where step 5 recognised that no test code existed and searched anyway.

**So this is a negative result, and it should be recorded as one.**
- It is **not** a wiring bug: proved by building the prompt on the live host.
- It is **not** a threshold problem: the correction was active for steps 3, 4 and 5.
- It is **not** the model failing to notice: its own text names the failure.

**What follows from that: this is not a prompt problem, so the next attempt must not be another prompt.**
The available moves are structural, and they are different in kind:
1. **Enforce rather than persuade.** When a step is read-only and the previous step was too, bind only
 mutating tools for that step, or reject a second read-only call and re-prompt with the rejection. The
 model then cannot do the thing it keeps doing.
2. **Convert the wasted budget into progress.** After N read-only steps, close the session as *unfinished*
 with the findings it gathered written into the task, and requeue, so the next session starts from the
 reconnaissance instead of repeating it. Honest, and it makes a stuck loop cost one budget rather than
 all of them.

Both cost something and both should be measured after deploying. **Neither should be attempted by guessing
which is better**; the cheap discriminating question is whether the model *can* mutate when the read-only
tools are simply absent, which is one experiment away.

**The broader point, which is the reason this is a lesson and not just a failed change.** I have spent this
session learning that the fix is usually sound and the *verification* is aimed at the wrong layer. This is
the complementary case: the change was verified at every layer I could reach and the **mechanism does not
exist at that layer**. A session log shows what the model was told and what it did; it does not show that
being told is enough. **Testing that an instruction arrives is not testing that it works** — and for this
model, on this task shape, arrival was not enough.

**L239 · 2026-09-14 - The offered tool list does not constrain what the model calls, so enforcement must be at dispatch**

**Training the discriminating experiment changed the answer: the offered tool list does not constrain what the model calls**

L238 named two structural alternatives for the read-only loop and one cheap experiment to choose between
them: *"test whether the model can mutate when the read-only tools are simply absent."* I ran it. **My first
verdict was wrong, and the corrected result points somewhere neither option anticipated.**

**What was run.** The real work prompt for the task shape that failed (session 75343's "audit agent memory
usage"), with the tiered classifier monkeypatched to offer **only** mutating actions:
`save_memory, update_task, close_task, create_task, code_edit, repo_run_command, github_write_file,
send_directive`. The patch was confirmed consulted, and the call path is
`select_tools_for_message(user_text)` → `allowed_actions` → `_build_tool_list(allowed_actions)` → `tools`
(`app/assistant_chat.py:4119-4124`, same shape at `:4338-4350`), so the offered set was those eight.

**What came back: `['repo_list_dir', 'repo_search']` — both read-only tools, neither of them offered.**

**My probe's own verdict line said "CAN mutate", and it was wrong** because I wrote a private read-only
predicate inside the probe instead of using the app's `_actions_are_read_only()`, and `repo_list_dir` does
not start with any of my `list_/get_/read_/search_` prefixes. The app's own classifier puts both names in
`_READ_ONLY_ACTIONS`, and the test asserting exactly that pair passes. **The lesson repeats: a measurement
tool that re-implements the thing it is measuring will disagree with the thing.**

**Why this matters more than the original question.** The intended fix was "bind only mutating tools so the
model *cannot* do the thing it keeps doing". This result says that **removing a tool from the offered list
does not stop the model naming it.** So enforcement has to happen at **execution** — validate the action
against the session's allow-list and reject a call that is not in it — not at binding. Binding is
persuasion with a smaller vocabulary; only a check at dispatch is enforcement.

**Stated with its uncertainty, because the premise rests on reading code rather than on the wire.** I did not
observe the actual `tools` payload sent to the provider. What would settle it in one step: log the bound tool
names immediately before the provider call and log the names the model returns, then assert the second set is
a subset of the first. If the returned set is not a subset, this finding is confirmed and the fix is a
dispatch-time check; if it is a subset, then the monkeypatch did not take effect where it mattered and the
experiment was never valid.

**And one honest note about the shape of this failure.** This is the **ninth** time this session that a
change or a measurement was sound while the *verification* was aimed at the wrong layer — here, at a
predicate I wrote rather than the one the system uses. The rule that keeps being earned: **use the system's
own classifier, constant, or check when measuring the system. A local re-implementation measures the local
re-implementation.**

**L240 · A model provider is a single point of failure until the ladder exists (2026-09-14 DeepSeek flash outage)**

2026-09-14: DeepSeek's flash tier went down platform-wide and the whole DSH fleet (3 machines + the phone engine on secratary) was pinned to it. The failure mode was a HANG, not an error: a live probe of deepseek-flash sat 180 s and never answered, while deepseek-v4-pro answered in 1.2 s and deepinfra deepseek-ai/DeepSeek-V4-Flash-0731 in 0.7 s. Unrelated users reported the same outage (r/opencode, dozens of confirmations across opencode/openrouter/raw API).

WHAT THAT PROVES, and must not be re-learned:
- The harness has NO cross-provider failover. dsh-llm-retry retries the SAME model at agent-step boundaries; always-mode would retry a dead provider forever. Cross-provider failover has to be built above the adapter.
- The COMMITTED settings/base.yaml is re-applied by autosync (Windows task + secratary cron) every 15 min. A manual model fix in ~/.dsh/settings.yaml is therefore undone within 15 minutes. That is the whack-a-mole the owner felt all day: fix the committed config, never the applied one.
- A hanging provider is worse than a failing one. dsh-llm-deepseek ships streamIdleTimeoutMs=300000 (five minutes), so a dead model presents as "nothing happens when I type". Now pinned to 60000 with retryPolicy normal/2 in base.yaml.
- An empty result is not health: a /models call still listed deepseek-flash while completions on it hung. Probe a COMPLETION, not the catalogue.

FIX SHIPPED: scripts/model-failover-watch.py (cron every 5 min on secratary) walks flash -> v4-pro -> deepinfra V4-Flash-0731, probes all three each run, fails down only to a tier that answered in THIS probe, and climbs back after N=2 consecutive healthy probes. Verified live: probe ok=[flash, pro, deepinfra] bad=[]. It owns settings/base.yaml via a single "# BRIDGE(" marker line; if the owner pins a model by hand and removes the marker, the script leaves it alone.

SCHEMA FACTS, read out of the installed harness rather than guessed:
- llm-deepseek config keys: streamIdleTimeoutMs (default 300000), retryPolicy (default normal/5), apiKeyEnv, baseURL. RetryPolicy schema is a union: {mode:'normal', maxRetries, retryableCodes[], backoff{initialDelayMs,maxDelayMs,jitterRatio}} or {mode:'always', backoff}. Unknown keys are REJECTED by name.
- A `llm-deepseek:` or `llm-pi-ai:` section in settings.yaml overrides the adapter live, with no restart, and is what the web Models page writes. The composition patch is NOT needed for this — and patching a composition row replaces that row's WHOLE config (the P48 trap: restating `config` without `trustedHosts` emptied the /api fence).
