started 2026-09-14T15:30:26Z, ran 5 steps, and failed with

the current state of these tools"* repeated across five steps — and it contains **no
`[DROPPED-ACTION-TAGS]` marker at all**. So the model emitted no `[ACTION:...]` tags; it
simply did not act, and the step budget ran out.

**What that means.** The dead-instruction defect was one contributing mechanism. The dominant
behaviour is broader: the work-mode model narrates intent instead of calling a bound tool.
Possible remaining causes, none of them established yet:
- the fast-tier model (`_work_mode_tier = "fast"`, `deepseek-v4-flash`) does not reliably emit
 tool calls under this prompt at all, so no prompt wording fixes it and the tier is the lever;
- the goals themselves are not actionable on this host — the sampled failures are Home Assistant

 (see **P18**, HA is on the office LAN and reachable from one machine);
- five steps is simply not enough for the task shapes the goal generator produces.

One session is not evidence, in either direction. The honest position: the stall rate is
**unmeasured after the fix**, and the next session must re-read
`work_sessions` by outcome **and** by marker before anyone calls this fixed. If
`[STALLED_REPEATING_OUTPUT]` disappears but `[STEP_BUDGET_EXHAUSTED]` does not, the fix worked
and the real problem is elsewhere — which is the more likely outcome.

The methodological point worth keeping: **a fix that is verified against the mechanism it
targets is not the same as a fix that is verified against the symptom.** I proved the
contradiction existed and that it is gone; I did not prove the symptom moved. Those are
different claims and only the second one matters to the business.
