## Ranked defects

**1. The always-read page cannot be bounded, by construction.**
`cmd_status` concatenates `NOW.md` (7.6 KB) and `state/in-flight.md` (3.4 KB) —
two hand-written, unbounded files — and only *after* building the text checks the
12 KB budget. So the page that every session must read is the page that overflows:
today it returns **exit 1** and 12,347 B. A budget that is checked after the fact is
not a budget.

**2. Reads are O(shard), not O(entry).**
`show` resolves an id through the index to a `(file, line_start, line_end)` triple and
slices it out, so printing one 1.2 KB entry reads a 249 KB file. Anything that wants
five entries pays five times.

**3. The monoliths are back.**
The split rule fires at `> 200_000` bytes *on append* and renames the month file to
`.1`, so the shards stabilise at ~200–250 KB each: the file the rule was written to
prevent is now the normal case. Nine files hold 1.39 MB. The owner's sentence
("getting longer and longer, not split up enough") is a description of this table.

**4. The index is a cache with no freshness proof.**
It is regenerated by every mutating command (`cmd_index` is called from `append`,
`import-flat`, `dedupe`, `split-shard`) — so in normal operation it is current.
But nothing *proves* it: a crash between writing a block and reindexing leaves a real
entry invisible to `status`/`newest`/`show` indefinitely, and a stale checkout running
`journal.py index` rewrites it from that checkout's shards alone. **Unproven which of
these has actually bitten; the missing check is the defect.**

**5. Two writers, live, today.**
While this audit was running, `log/lessons/2026-09.md` (17:44), `log/pain/*` (17:44),
`DECISIONS.md` (17:46), a handoff shard (17:49) and `index/entries.tsv` (17:49) all
changed mtime, and commits landed at 17:46 and 17:49. This is not a historical scar:
a second session was writing the same journal **during** the audit. Its scar is
structural — **409 lessons occupy a 224-number id space; 161 base ids name two
*different* lessons** (they are not duplicates; they are two entries that chose the
same number on two machines and got suffixed `a`/`b` afterwards). Cross-references in
the last week of prose are ambiguous by construction, and there is no repair command.

**6. The legacy flat files are simultaneously "frozen" and live.**
`HANDOFF.md`, `LESSONS.md`, `DECISIONS.md` and `open-pain.md` were all written within
the last 10 minutes. Meanwhile `check` claims `LESSONS.md` holds **1** entry the log
lacks; comparing by normalised heading+body finds **175** (plus 34 decisions, 21 pains,
16 wins). Both numbers come from this tree; the difference is that `check` uses a fuzzy
key and the audit used the exact one. So the absorption is incomplete by an unknown
amount and the tool under-reports it — the worst possible combination for a memory
system.

**7. Eight exact-duplicate handoffs** (same heading and body under two ids, 41,427 B
of duplicated content) from the merge, with suffixed ids and no repair path. Harmless
in size, but they are why `check` prints 30 warnings that nobody can act on.

**8. Signal is buried in scan cost and noise.**
`check` and `status` both call `verify()`, which greps the 798 KB of legacy flat files
for dangling `L…/P…/D…/W…` refs on every run — that grep is most of the 8.88 s. The
output is 30 warnings (28 of them "out of order" from merged shards) and 76 info lines.
A check that always prints 106 lines is a check nobody reads.

**9. There is no query surface and no flags.**
One verb takes one positional argument. No `--kind`, `--since`, `--status`, `--tag`,
`--limit`, `--budget`, `--json`, no backlinks, no `list`, no way to ask "every open
pain this machine owns since the 10th" without reading a 170 KB file. Entries have no
fields at all: no tags, no refs, no revision, no machine queryable except by grepping
the index.

**10. The write path cannot be conflict-free as long as a file holds many entries.**
Every append is a text merge into a shared file; git resolves it by interleaving, which
is exactly how the duplicates, the out-of-order blocks and the collided ids got in.

## What the replacement must beat (acceptance targets)

| Property | Target | Now |
|---|---|---|
| `status` output | ≤ 6,000 B, exit **0**, cap enforced *during* assembly | 12,347 B, exit 1 |
| `status` wall time | < 0.4 s | 8.88 s |
| `show` | exactly one file opened, < 30 ms | 0.41 s, whole shard |
| `search` | < 0.3 s, bounded snippets, real filter flags | 1.10 s, no flags |
| Largest history file | no file grows beyond one entry's size | 249,724 B |
| Index | a *cache* with a freshness stamp; a stale or wiped index self-heals on the next read | no proof, no heal |
| Writes | one file per entry — two machines cannot conflict | text merge into a monolith |
| Ids | never write an id that already exists with different content; bump and say so | collision possible, scarred 161 times |
| Legacy | every legacy entry absorbed with an exact-content proof, and `check` reports the true count | 175 lessons unaccounted; check says 1 |
| `check` | 0 errors, ≤ 5 explained warnings, no full-tree grep | 30 warnings, 76 info |
| Cost | `journal.py costs` prints this table from live runs, so the claim is re-measurable | no such command |

The design that meets those targets is `SPEC-v2.md`, in this directory. The rule it
keeps from v1, because it was right: **the log is append-only, the state tier is
rewritten, the index is generated, and the tool is the only writer.**
