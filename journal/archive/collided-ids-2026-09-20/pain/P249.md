## P249 — The deployed bench engine can lag the repo and nothing checks it; the case index's integrity check fails on 226+33+18 items of corpus drift

**P (2026-09-17) — the deployed bench engine can lag the repo, and only a human notice catches it.**
`lpt-hub`/`personal-secretary-mvp` `scripts/linux-pc/*` are the source of truth; the bench runs
`/usr/local/bin/{lpt-recover,lpt-recovery,lpt-recovery-manager,recovery-learn}`. Nothing compares
them. Found today: `recovery-sigscan.py` and `dedupe-recovery.py` were **absent from the bench
entirely** while the SD playbook calls their steps mandatory. Deploying them was a manual scp.
Ranked by what it costs: a stale/broken engine means a case runs on old logic and the operator has
no way to know — the 2026-09-05 deploy of a CRLF-broken `lpt-recover` is the same failure with a
different cause.
**What would fix it:** a `lpt-recovery doctor` (or `lpt-recovery-manager doctor`) subcommand that
hashes every `scripts/linux-pc/*` file in the repo against its `/usr/local/bin` counterpart and
prints MATCH / DIFFERS / MISSING, plus the tool-presence loop used today (ddrescue, photorec,
testdisk, sleuthkit, clamscan, mkfs.exfat, fatattr, ffprobe). Run it at case intake and let it be
part of the engine, not a habit.

**P (2026-09-17) — the case index's own integrity check fails, and the failure is corpus-wide
drift: 226 sync records with no case file, 33 cases with no sync record, 18 duplicate-phone
groups.** `python tools/case-index/lptcase.py check` exits non-zero on the live corpus today, so a
genuine new structural problem would be invisible inside the noise — the check has stopped being a
gate. This is mechanical, parallel, and file-partitioned: the right shape is a fleet (one agent per
N cases, `parallel-agent-orchestration`), not an afternoon of serial editing.
**What would fix it:** triage the 226 orphans first (most are probably renamed/legacy cases that
need the record's `sourcePath` corrected or an alias, a few are genuinely case-less records that
should be archived), then create the 33 missing records from the case front-matter the tool already
parses, then look at the 18 duplicate-phone groups by hand — a repeated phone is either a real
repeat customer (fine, needs a note) or a case filed twice (needs the read-only doubles detector
that already exists at `tools/customer/audit.py`). Owner involvement needed: none, except that
"duplicate" verdicts on real customers are a judgement call to record, not to delete.
