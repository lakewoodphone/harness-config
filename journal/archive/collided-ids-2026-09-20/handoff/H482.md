# H482 — round 3: repair tooling built and proven, and a LIVE unattended write of customer data to main stopped

## THE MOST IMPORTANT THING THIS ROUND

**The automated reconciler was writing customer case records STRAIGHT to the lpt-hub repo's `main`
branch, unattended, every 24 hours, with no PR and no human.** Fixed.

Verified chain, line by line:
- `daily_reconciliation.py:703-710` called the hub linker with
 `dry_run=bool(getattr(settings, "reconciliation_dry_run", False))`;
- `reconciliation_dry_run` is **False** (`config.py:340`);
- so `dry_run` was False, so `lpt_hub_link_orders.py:452` fell past `if dry_run: continue`;
- and reached `_gh_write_file(..., branch=_BRANCH)` where `_BRANCH = "main"` (`:35`, write at
 `:458-469`), through the GitHub Contents API;
- and the record carries the customer's **name, phone and device**.

That is the exact rule this company states and has paid to learn twice.

**The safe default already existed and was overridden.** `link_records_to_orders`' own signature is
`dry_run: bool = True` (`lpt_hub_link_orders.py:288`). So I removed the override rather than inventing
a mechanism: the linker now computes and reports what it WOULD link. Opt-in is
`lpt_hub_linker_write_to_main` (new, `config.py:395`, default **False**).

**I did not build the correct path** (branch + PR, like the phone-and-tech-full push gets). That needs
review, and inventing a new unattended write path in the same session that removed one would be the
wrong trade. Committed `1dd89830`, deployed, verified on the authority:
`lpt_hub_linker_write_to_main = False` and `dry_run=not _linker_may_write` present.

## REPAIR TOOLING — BUILT, APPLIED, AND PROVEN TO CLOSE THE LOOP

`tools/customer/repair.py` (lpt-hub `5779fbb1d`). Dry-run by default; `--apply`; `--list`.

**The rule it enforces:** a repair may ADD information, and may correct a value it can prove wrong
from the file's own content. It may never invent a value and may never delete customer data.

Applied to the 7 dead Secretary pointers (contact ids 626, 627, 628, 632, 633, 651, 654 — all verified
absent, sitting in real gaps in the id sequence). Each got one dated activity section recorded as
`NO LONGER RESOLVABLE`, appended through `store.update_case` — the single locked write path — so every
write took the exclusive lock, re-read under it, wrote atomically, preserved CRLF, and bumped
`updated`. Nothing deleted, nothing invented. **Idempotent, proven: the third run printed 7 skips and
left the tree byte-identical.**

**Then the loop still didn't close, and that is the finding.** The verifier re-reported all seven as
ERRORs, because the repair annotated the file and the check couldn't see it. A repair the verifier
ignores is not a repair. C04 now treats an annotated id as resolved (INFO, count kept visible) and
reads the marker through a shared `GONE_MARKER` so the two files cannot drift.

**Measured effect: C04 7 ERROR → 0 ERROR / 7 INFO; total ERRORs 14 → 7.** The 7 remaining are the
ones the tool deliberately does not touch, each a real human decision: 1 record to author (Gutterman),
3 orders belonging to **another customer**, 3 **promises revoked** (`READY_FOR_PICKUP → IN_REPAIR`).

## DIALPAD — THE COMMS SURFACE (owner asked for this explicitly)

`tools/customer/dialpad.py` (lpt-hub `c5cb55f72`). Answers what the other four surfaces cannot: did
this customer actually call, did we answer, what did we tell them. Verified live:

```
--case sd-card-czermak-7183147956-2026-09-02
 calls 20 | sms 1 | transcripts 17 | digital sessions 6
 most recent: "We got everything off the card - 497 photos and 22 videos."
```

Read-only and **cannot** send — no code path by which it could compose or dispatch anything. Asserts
`query_only=1`; if the Dialpad tables are missing it raises rather than returning empty lists,
because "no conversations" and "the surface has moved" must not look alike.

**The join columns, measured — `dialpad_call_full.contact_phone` is EMPTY** (the column that looks
right joins to nothing). Real ones: `external_number`, `phone_normalized` + `body_text`,
`customer_phone`, `contact_phone` + `order_id`, `transcript_text`. Both sides normalised to the
corpus's 10-digit form.

**It refuses to pretend**: `comms_identity_link` rebuilds with `DELETE ... WHERE source != 'manual'`
then reinserts, so all 31,806 rows carry `first_seen_at == last_seen_at` == one instant. "When did
this customer first contact us" is UNANSWERABLE from that table, and the output says so with the
reason rather than printing a rebuild instant as a first contact.
