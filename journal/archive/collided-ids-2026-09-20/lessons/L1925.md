# L1923 — I overwrote the live production sync tool with a 33 KB stale copy, because I edited the wrong lineage

## What I did

While adding two validation functions to `scripts/lpt-sync-to-production.py`, I read **my local copy**
on ZABZ-TECH, edited it, and deployed it to the authority with `base64 -d > the-path`. The deploy
reported `deployed` and the file parsed. I only discovered the damage when I ran the tool for an
unrelated reason and got:

```
lpt-sync-to-production.py: error: unrecognized arguments: --dry-run-all
```

**The authority's live tool was 89,945 bytes. My local copy was 28,797 bytes. I overwrote a 90 KB
production tool with a 33 KB one, and it silently lost `--dry-run-all`, the pre-create guard, and
`_GUARD_REFUSING_KINDS`.**

## Why it happened — the compound error

1. **I already knew about this exact divergence and still walked into it.** This session had
 established, and I had journaled, that `master` on ZABZ-TECH carries the 28,797-byte version while
 the authority carries the 89,945-byte one, with `git merge-base --is-ancestor 858ce073 HEAD`
 exiting 1 in **both** directions. I recorded it as a headline finding and then edited the file
 without ever asking which version I was editing.
2. **`base64 -d > path` deploys whatever you give it, unconditionally.** There is no size check, no
 content check, no "is the target newer than the source" check. Every deploy in this session used
 that pattern, and it is a footgun that has been harmless only because the files happened to be the
 right ones.
3. **A parse check is not a smoke test.** I verified `ast.parse` and the import, and reported
 success — twice. A 28 KB skeleton of a 90 KB tool parses perfectly. **The check I ran was
 incapable of detecting the failure.** The check that would have caught it was running the tool's
 own `--help` and looking for a known flag, which takes one second.

## What saved it

**Git on the authority held the correct file.** `git show HEAD:scripts/lpt-sync-to-production.py`
returned 89,081 bytes with `--dry-run-all` present (5 occurrences) and the guard intact. Recovery was:
fetch that blob, apply my two intended functions to **it** rather than to the old copy, and redeploy.

Without git holding it, the 89,945-byte working version (89,081 committed **plus an 864-byte
uncommitted fix**) would have existed nowhere on this machine — my rescue-branch commit `d9b33c9b`
turned out not to contain that path at all, and the `master` copies are all the old lineage.

## The rules

1. **Before editing a file whose lineage is in doubt, print its size and its `git log`.** In this repo
 the same path exists as a 28 KB and a 90 KB program; "the file" is not a single thing.
2. **Never deploy by `base64 -d > path` without a post-deploy check that can actually fail.** Size
 comparison plus a functional probe (`--help | grep <known-flag>`), not `ast.parse`.
3. **`ast.parse` proves a file is *parseable*, not that it is *the file*.** It is a syntax gate, and I
 used it as a content gate twice in one call.
4. **When a repo has a documented two-lineage problem, treat every file in that repo as suspect until
 its lineage is confirmed.** The finding I wrote up in round 3 was the warning for this incident,
 and I did not apply it to my own next action.

## Cost and outcome

The window was roughly 4 minutes. No data was written — the tool was only ever invoked in read-only
mode in that window, and the next unattended reconciliation was ~3.5 hours away, so nothing pushed.
Restored and verified: `--dry-run-all` returns `TOTALS: 383 record(s) — CREATE 7, SKIP 376, ERROR 0`,
and the new resolution logging works (`INFO: lpt-hub resolved: /home/zabz/repos/lpt-hub @ 8cb746a06`).

## Evidence

- The failure: `error: unrecognized arguments: --dry-run-all`.
- `git cat-file -s` on the authority: my deploy 33,419 → restored 92,973 (89,081 + my two functions).
- The recovery source: `git show HEAD:scripts/lpt-sync-to-production.py | grep -c 'dry-run-all'` → **5**.
- My local file has **zero** occurrences of `dry-run-all`.
