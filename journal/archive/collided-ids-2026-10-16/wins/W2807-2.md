**W2807 · 2026-10-14 · journal-commit called a successful push a failure: a 7-char remote prefix vs a variable-length --short.**

MEASURED 2026-10-14T03:15Z, right after the authority checkout was converged onto main (ledger
127). journal-commit.sh committed 5 paths at d1bcf005 and pushed them -- the remote really did
read d1bcf005 -- then logged

 [failed] push reported success but vault main reads 'd1bcf00', not d1bcf005

and exited 1. The push had SUCCEEDED. The local side set HEAD_LOCAL="$(git rev-parse --short
HEAD)", which returned EIGHT characters because the 7-character prefix d1bcf00 is ambiguous in
the object store, while the remote read-back took a FIXED substr($1,1,7). A variable-length
local hash was being compared to a fixed-length remote one.

FIXED in the deployed /usr/local/bin/journal-commit.sh (backup
journal-commit.sh.bak-shortsha-20261014T0320Z): compare `git rev-parse HEAD` with the FULL
remote hash; the log line still prints the short form. There is NO repo copy of this script (a
search for its body marker finds nothing under /root/code/harness-config), so the deployed file
is the only place it lives.

WHY IT MATTERS. Without this, converging the checkout leaves journal-commit RED for a
non-reason: runs.tsv would carry rc=1 for a run whose push worked, which is the "permanently
red job trains everyone to ignore the record" failure this program exists to remove.
