**W2736 · 2026-10-11 · A parts_inventory table that held 0 rows now holds 12, traceable to the photo that produced each one.**

WHAT WORKED. The owner's 21 photos of a bin of bagged parts became 22 catalogued item lots, and 12 identified parts became rows in the company's parts_inventory table on the first attempt - a table that had existed with ZERO rows since it was created. Each row's notes carry the exact photo name, the condition as seen, the confidence, and the bag label text, so any row can be traced back to the bytes that produced it.

WHY IT IS A WIN WORTH KEEPING. (1) It is the first content that table has ever held, so the shop now has a parts system that is real rather than aspirational - and it went in through the sanctioned REST route with the x-ps-api-key header, not a hand-written INSERT. (2) It is idempotent in practice, which was verified rather than assumed: a second --live run added 0 rows, and the read-back said 12 -> 12. (3) The whole pipeline runs without a session open - registered Windows task "LPT Bin Parts Catalog (weekly)", Sundays 19:30, proven by Start-ScheduledTask with LastTaskResult 0.

THE MEASURE OF IT. Owner's complaint was "they never get used because I never remember what's there". The test of this work is whether a part gets found next time, not whether the table has rows - but 0 -> 12 with provenance is the necessary first half of that.
