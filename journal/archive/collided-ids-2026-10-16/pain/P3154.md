## P3154 — orders.attentionReason is a stored column nothing recomputes, so the ATTENTION line a staff member reads first can be days stale and name a status the row no longer has

The shop's own readers show a stale attention flag on an order that was updated minutes ago. Measured
2026-10-12 on WO2607280003, immediately after writing note 3158 and setting READY_FOR_PICKUP:

```
lpt ticket WO2607280003
 WORK ORDER WO2607280003 (id 2346) [READY_FOR_PICKUP]
 updated 2026-10-12 19:33:17.86
 ATTENTION No update for 7 days (status IN_REPAIR).
```

The order was updated today, its status is READY_FOR_PICKUP, and `IN_REPAIR` has not existed on
this row since the 2026-10-07 migration `20261007230000_order_status_seven_states_apply` rewrote it.
The line is not a live computation: `needsAttention` / `attentionReason` / `attentionUpdatedAt` are
**stored columns** on `orders`, written by the app (visible in the same shape across the corpus, e.g.
"No update for 19 days (status AWAITING_PARTS)." on WO2607240002). So the flag was computed once,
before the migration, and nothing recomputes it when the row changes.

**Why it matters.** This is the field a staff member reads first - it is literally the ATTENTION
line. It can say "no update for 7 days" about a case that was updated an hour ago and name a status
the row does not have. A reader who trusts it chases the wrong cases and disbelieves the rest.

**Fix, cheapest first.** (a) Recompute `needsAttention`/`attentionReason` whenever
`website_db.update_order` writes a status or a note lands - the write path already exists and is the
only sanctioned writer. (b) Failing that, have `lpt ticket` compute staleness from `updatedAt` at
read time and print the stored string only as a labelled legacy field, so a stale flag cannot be
mistaken for a current one.

**Scoping note, learned the hard way the same minute:** `grep -r 'update for' lpt-ops/` matched
`app_orders_named.json`, a single-line ~200 KB data dump that contains the whole order corpus. That
one grep cost a large slice of the session's context for nothing. Scope content searches by file
type (`*.py`), and never point one at a data directory.
