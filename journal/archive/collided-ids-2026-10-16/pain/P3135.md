## P3135 — An lpt-hub case file can sit seven weeks behind production on a CLOSED job and no verifier notices

## A closed case file can sit seven weeks behind production, and nothing complains

Measured 2026-10-12 on the Lichtenstein SD card. `cases/lichtenstein-sd-card-recovery-2026-08-24.md`
read **"Status: Quote SENT — awaiting customer reply"**, front-matter `status: quoted`, `price: 750`,
dated 2026-08-25. Production said the customer **declined** the lab route on 2026-09-15, both orders
were closed (UNFIXABLE, and the duplicate now CANCELLED), and quoted = 0, collected = 0. Seven weeks
of drift, on the file a staff member would read to answer "where is my card".

## Why no verifier caught it

`audit.py` (four surfaces, 15 ERROR / 144 WARN on 2026-10-12) does not check this: C07 is *production*
status regressions, C03 is *two records, one case*, C11 is held-not-actionable. Nothing compares a
case file's own status/price front-matter against the production order that file names.
`sync-health-audit.py` compares sync records to production, not prose to production.

## The fix, and it is small

A check that reads every case file whose front-matter names a `work_order:`, resolves it in
`operational`, and flags a contradiction:

- front-matter `status` is an open word (`quoted`, `waiting`, `in_progress`, ...) while
 `orders.status` has been terminal (READY_FOR_PICKUP, CANCELLED, UNFIXABLE) for more than 14 days, or
- front-matter `price` > 0 while `orders.total` is null/0 and there are no SUCCEEDED payments.

No model, no judgement — two fields against two fields, and it belongs in `sync-health-audit.py`'s
output next to the reverse gap. It would have caught this one around 2026-09-22.

Not started. Same class as the note-drift defect already on the record (a finding that lived on the
customer file and not on the order) — this is its mirror image: the order is right and the case file
is stale.
