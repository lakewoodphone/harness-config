## P3153 — orders.description and orders.title have no sanctioned writer, so a corrected case can still show 'Awaiting customer approval' on the customer's own order

A corrected case can still show a promise we are no longer making on the customer's own order page.
Measured 2026-10-12 on WO2607280003 (Mrs. Vahab, LG Gram 16T90P).

The shop's record now says the repair was declined and the laptop is READY_FOR_PICKUP - production
note 3158 and an `order_status_history` row say so, and the case file agrees. But the order itself
still carries:

- `orders.title` = "LG Gram 16T90P (i7-1165G7, 16GB) - board replacement path"
- `orders.description` = "... Board replacement decided: donor DA0NLHMBAE0 REV:F 219.99 ... Total
 repair quote: 340 (board + labor, keeps all data). **Awaiting customer approval.**"

Nothing in the sanctioned write path can change those two fields. `bin/lpt-write` in lpt-ops does
exactly two things - `note add` and `status set` (`docs/writes.md` §8: "It cannot set a status
reason into order_status_history", and there is no description/title command at all). The
customer-visible alternative, `operational.portalSummary` in the sync record, does not help either:
this record's push decision is **SKIP** ("record already references live production order
WO2607280003"), so the corrected summary is never pushed. Verified this session with
`lpt-sync-to-production.py --dry-run-all`: 413 records, CREATE 2, SKIP 411, ERROR 0.

**Consequence:** a customer who looks at her order sees "Awaiting customer approval" for a decision
she made three days earlier, on a repair we are not doing.

**What would fix it.** Either (a) an operator-approved, audited path to update `orders.description`
and `orders.title` through the same single `website_db` writer, with the same ledger and read-back
that `lpt-write` gives notes and status; or (b) a verifier rule that treats an `orders.description`
still asserting a decided-against outcome as drift, so it surfaces instead of sitting there. (b) is
the cheap half and does not need a new writer.

Do not solve this by adding a second writer to `orders` - that is the defect `lpt-write`'s whole
design exists to prevent (`docs/writes.md` §2, incidents 2532/2538).
