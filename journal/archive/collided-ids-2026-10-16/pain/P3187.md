## P3187 — lpt-write status set writes a FALSE reason into production order_status_history

# `lpt-write status set` writes a FALSE reason into production's status history

Measured 2026-10-14, on two real status changes to customer orders.

Every deliberate status change made through `lpt-write` lands in `order_status_history` with the
reason string **hardcoded** by `update_order` in `app/services/website_db.py`:

 reason = f"Auto-updated by secretary reconciliation (confidence: {confidence})"

`writes.md` §8 already knows this and calls it a one-line fix that was not made, "because exactly one
change to that file was sanctioned and the missing `workOrderId` was the one that loses data". That
was a reasonable call at the time. It is not reasonable now that the tool is being used to correct
customer records on the owner's instruction, because the line it writes is **not merely vague — it is
untrue**, and it is untrue in the direction that matters.

## What it actually wrote

```
2026-10-14 12:49:30.738 READY_FOR_PICKUP -> CANCELLED
 reason='Auto-updated by secretary reconciliation (confidence: 0.95)'
```

That transition was **not** a reconciliation and was **not** automatic. The owner assessed that no
device had ever come in and that the order had been raised for no reason; the change was made
deliberately, by hand, on his instruction, and the true reason is written into the note that
accompanies it. An auditor reading only the history row would conclude the opposite of what happened:
that an automatic sync corrected the row, rather than that a human corrected a spurious order.

The same happened on `WO2604210130`, moved `READY_FOR_PICKUP -> AWAITING_PARTS` the same day with the
same false reason.

## Why this is worse than the missing workOrderId it was traded against

An absent field is a gap a reader can see. A **wrong** field is not. This estate's most common and
most corrected failure is `wrong-data` — acting on something that was not true — and the worst
incident in its history was a confident wrong report read out of a stale copy. A status history is
the one place a future reconciliation reads to decide what a human did. Teaching it to lie about
provenance makes every later automated decision worse, and it does so silently, because the string
is well-formed and looks authoritative.

## What to do

`update_order` should accept a `reason` and pass it through, with the current string as the default so
every existing caller is unchanged — the same backward-compatible shape as the `work_order_id`
addition. `lpt-write status set` already takes `--reason` and already records it in the audit ledger
and prints it in the read-back; the only thing it cannot do is put it where it belongs.

Until then: **any status change made through this tool writes a false reason into production.** The
mitigation is to put the true reason in the accompanying note, which is what was done here, and to
say so out loud rather than assume the history row is evidence of provenance.
