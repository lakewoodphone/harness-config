## P3170 — Hand patches to the engine's npm tree are invisible to dsh-update and are lost on the next update

A hand patch to a file inside the engine's npm tree is invisible to `dsh-update` and is silently
lost by the next engine update.

Measured 2026-10-14, while fixing the blank-window session bug: the fix lives in
`~/.dsh/engine/node_modules/@deepseek-ai/dsh-client-ui-workspace/lib/client.js`, and `dsh-update`
tracks patches to the *cordis composition* only (`cordis.patch.yml` rows; SPEC.md B3/B4, G2/G6 all
check `patchedRowIds`). Nothing in `dsh-update`'s lib or docs re-applies or verifies a patch to a
package file, and the vendored candidate trees plus `node_modules` are what an update replaces. So
the fix works until the owner updates the engine and then quietly stops working — the same failure
shape as the "silent fallback" incidents: the system looks healthy and behaves like the old bug.

This is not specific to this patch. `unpatched-store.mjs` / `session-list-ab.mjs` / the
`.bak-harness-` CSS in `dsh-web-frontend` are evidence of at least three earlier hand patches to this
same install with the same exposure.

Mitigations in place (not a cure): `multi-window/tools/patch-window-blank-isolation.mjs --check`
(exit 0 applied / 4 absent / 5 unverifiable) so a post-update step or a human can find out, `--apply`
to restore it, a dated `.bak-harness-` backup beside the file, and
`~/.dsh/engine/PATCH-NOTICE-window-blank-isolation.md` in the tree an updater is about to replace.

What would actually fix it: a checked-in patch registry that `dsh-update` verifies against a fresh
engine tree with the same rigor it applies to composition rows — assert the anchor text exists, apply
it, and fail the update if it cannot be applied. Until then every hand patch to this install is one
`npm install` from silence.
