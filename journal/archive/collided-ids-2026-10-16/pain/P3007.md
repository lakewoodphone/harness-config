## P3007 — GET /api/v1/shop/parts takes ~65 seconds, and a slow read silently became an empty inventory

WHAT HURTS. Measured 2026-10-11: GET https://api.abletelsolutions.com/api/v1/shop/parts returned {"ok":true,"total":12,...} in 65.4 seconds. The table holds 12 rows. The cost is not the query, it is connection acquisition against a 23.6 GB SQLite file with many concurrent readers and busy_timeout 10 s per handle.

WHY IT IS DANGEROUS, NOT MERELY SLOW. A client with a shorter timeout does not get an error a human will see - it gets an exception that gets caught, and the natural fallback is "empty". An empty inventory drives a dedup decision, so the failure mode is DUPLICATED DATA, silently. That is precisely what nearly happened here with a 30 s timeout, and the same class of bug was already recorded in this estate as believing a stale database copy.

WHAT WOULD FIX IT. (1) The parts list route should not need a fresh connection per call - a short-lived cache, or reading it from the same pool the dashboard uses. (2) Alternatively expose a cheap "count" or "version" endpoint so clients can detect change without the full list. (3) Every client must treat a failed read as a refusal; my own tool now does (tools/parts-catalog/tools/lptparts/inventory.py, READ_FAILED -> refuse to write blind), but the next client written will not know unless this is written down.

EVIDENCE: curl -m 120 against the live cloud route, http=200 time=65.368406s size=14204.
