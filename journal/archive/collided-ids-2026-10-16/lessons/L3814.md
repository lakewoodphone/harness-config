**L3814 · A basename exclude drops data at ANY depth: lpt-copy-userdata left 5.09 GB behind, including a QuickBooks company file in Dropbox's deleted-file cache and 209 MB under a folder named Windows**

**L · A basename exclude is not a path, and in the house copy tool it silently drops data at ANY depth. Two real losses found on one job.**

Measured 2026-10-14 on the Raitzik job (Seagate `ST3500413AS`, `Z2A9S4A5`). The copy reported success,
the tool's own manifest existed, and the destination held 61,729 files / 289.3 GiB. **A source-vs-
destination comparison then showed 13,098 files / 5.09 GB had been left behind**, and two of those
groups were not caches:

1. **`--exclude=Windows` is not "the C:\Windows folder".** rsync matches a pattern containing no `/`
 against the **final path component at any depth**. The dropped set included 113 files / **209 MB** at
 `Favorites/From Old Computer/Music/Hinder/Extreme Behavior/RegBackup/SHABSIRAITZIK/1.6.2015_4.29.50-PM/C/Windows/System32/Config/{software,components}`
 — a Windows registry backup that happened to sit inside a *music* folder backup. `Temp`, `tmp`,
 `Program Files`, `System Volume Information` and the rest of that exclude list have the same
 behaviour. **On a drive that holds a folder named `Windows` or `Temp` inside a user's documents,
 this loses user data without a word.** (Here the loss is genuinely useless — registry hives — but the
 mechanism is the finding.)
2. **`--exclude=.*` dropped `Dropbox/.dropbox.cache/` — 1,355 files / 1.36 GB of real documents.**
 Dropbox's cache of *deleted* files held
 `SAGE CUSTOM DESIGNS LLC Version updated (deleted 5843fed4…).qbw` at **136,630,272 bytes**, with its
 `.DSN`/`.ND` companions and ~1,270 QuickBooks report and template files. **"Deleted from Dropbox" is
 not "worthless"** — that was the only copy of that company's books on the drive. Rescued to the
 archive as a targeted top-up, with its own hash manifest, after the fact.

Where the rest of the 5.09 GB went, and it is all legitimately cache or system state:
`AppData/Local` + `AppData/LocalLow` 11,614 files / 3.52 GB (Explorer ETL log 428 MB, iTunes Cache.db
164 MB, Chrome cache, thumbcache, WebCache, a 123 MB Dropbox installer, a 47 MB Java MSI),
`NTUSER.DAT` 11 MB, `ntuser.ini`, `.oracle_jre_usage`, an empty `OneDrive`, and 11 files / 25 KB under
`Documents`.

**Two rules to carry forward:**

1. **After any exclude-driven copy, run the completeness check — both directions, by size AND path.**
 `comm -23`/`comm -13` over `find -printf '%s %P\n' | sort` from each root. It is metadata-only, costs
 seconds, and it is the only thing that makes "the copy finished" mean "the data is there".
2. **The house tool's `MANIFEST.sha256` is generated by hashing the DESTINATION**
 (`cd "$dest" && find . -type f -print0 | xargs -0 sha256sum > "$dest/MANIFEST.sha256"`,
 `lpt-copy-userdata` line 278). **Its existence is not evidence that the destination matches the
 source** — a truncated or corrupt file would be hashed and listed exactly the same way. Independent
 source-side hashing of the irreplaceable files, plus the size/path comparison, is what actually
 verifies a copy.

**And a note to my own future self, because both of my first two attempts at the verification were
wrong, in opposite directions:** attempt one never created the mount point, so the source list was
empty and it reported *all* 61,729 destination files as unmatched — a false alarm that would have
looked like a catastrophe. Attempt two wrote its list files as root and then, re-running as an ordinary
user, could not overwrite them, so it silently compared against a stale list and reported the same
61,729. **An empty or unwritable comparison input must abort the check, not print a number.** Check the
counts on both sides before believing any diff.
