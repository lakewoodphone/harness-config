## 2026-10-13 · Where the Telnyx 2FA backup codes are, and the exposure they carry

- The owner enrolled in Telnyx two-factor auth and pasted **six single-use backup codes** into a DSH
 session, asking for them to be stored safely. They are stored in TWO places, neither inside git:
 - `personal-secretary-mvp/deploy/waze-mdm/secrets/telnyx-2fa-backup-codes.txt` on ZABZ-TECH.
 **Proven** git-ignored, not assumed: `git check-ignore -v` reports `.gitignore:245:deploy/waze-mdm/secrets/`.
 Windows ACL reduced to this account (`/inheritance:r`).
 - `/root/.secrets/telnyx-2fa-backup-codes.txt` on secratary-cloud — directory mode 700, file 600,
 and `git rev-parse` confirms it is outside every repo. 1209 bytes, verified by line count.
- **EXPOSURE, stated plainly: they are in a session transcript on disk.** DSH sessions are files
 (`~/.dsh/sessions/` on any node that runs them, plus the session corpus), so the codes are readable
 by anything that can read a transcript. **The way to make that copy worthless is to regenerate the
 backup codes in the Telnyx portal** — said to the owner the same evening.
- **This is the same class as pain P13b** (a live API key printed into a transcript). The durable fix
 is a channel that is not the chat: **paste the secret into
 `%USERPROFILE%\.secrets-inbox\<name>.txt` on the machine you are on, say the filename, and I read it,
 store it properly and delete the drop.** Created 2026-10-13 with its ACL reduced to the owner's
 account. A secret that never enters a message never enters a transcript.
- Unrelated but adjacent, re-read 2026-10-13 20:30Z: the Telnyx **balance is still -0.01 USD with both
 SIMs blocked**. Being able to log in is not the same as being funded.
