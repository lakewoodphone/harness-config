**L3760 · Waze fleet onboarding: six defects and traps measured on DRN 2004-2008**

## 2026-10-13 · ZABZ-TECH · Five things that cost real time on the Waze fleet today

**1. `onboard.py` and `ota.py` never rendered wallpapers — every brand-new device failed at that step.**
Symptom: `POST /fleet/devices/<drn>/push-wallpapers -> 400 "Wallpapers not rendered yet. Call
/render-wallpapers first."` The PNGs are staged per DRN by `/render-wallpapers`; the onboarding path
assumed they already existed (true for the gemach fleet, never true for a new unit). **Fixed in
`scripts/waze/onboard.py`**: it now renders, reports the byte counts, and only then pushes. The
wallpaper label is derived from the site and the DRN's rank within it (`_wallpaper_label`), so these
LPT units read **`LPT 4` … `LPT 8`** on the home screen, not `DEVICE 2004`.

**2. Every VPP association on the maintained path was dead — and it failed *after* the device was
already locked down.**
Symptom: `ModuleNotFoundError: No module named 'app'` at the app-install step.
`_common.vpp_associate` did `sys.path.insert(0, REPO/"app")` and then imported
`app.services.apple_vpp_service`. That import is absolute, so the **repo root** has to be on
`sys.path` — `REPO/app` only makes it importable as `services`. **Fixed in
`scripts/waze/_common.py`**: both `REPO` and `REPO/app` are inserted. Note the blast radius: the
crash happened after clear-passcode, wallpapers and lockdown, so a half-configured device looked
like a completed run unless you read the exit code.

**3. The fleet CLI's Python dies on Git's msys `ssh.exe` under the DSH sandbox.**
Symptom: `*** fatal error - NtCreateDirectoryObject(\BaseNamedObjects\msys-2.0S5-…): 0xC0000022`,
raised from `subprocess` inside `_common.ssh_run`. Fix that works: prefix the PATH for the call —
`$env:PATH="C:\Windows\System32\OpenSSH;$env:PATH"` — so Python's `ssh` resolves to Windows OpenSSH.
Same class as the documented piped-stdio boundary; it is not a typo in the key.

**4. `POST /fleet/devices` creates a HALF row, and `renumber-v2` needs `new_drn` even to link an
enrollment.** Registration returns `ok:true` with `site` set but leaves `enrollment_id`,
`device_class` and the real `device_group` untouched — and **without `enrollment_id` every command
silently goes nowhere while the API keeps saying `ok:true`**. Link with
`POST /fleet/devices/{drn}/renumber-v2?new_drn={drn}&new_enrollment_id={eid}` — the parameter name
suggests renumbering, so a reader who trusts the docs omits `new_drn` and gets a 422. Then re-read
the row with `GET /fleet/devices/{drn}`.

**5. `fleet_devices.state` lies, and `diagnose.py devices <drn>` can hang.**
The five new rows went to `state='deployed'` **before anything was installed** (wallpapers `NO`, no
profiles) — some path writes that label without applying anything, so never report a device as
deployed from its state. Read the device's own `ProfileList` / `InstalledApplicationList` results
instead. Also: `diagnose.py devices <drn>` blocked past 200 s twice today; `ota.py diagnose <drn>`
answered immediately on the same device. Prefer the latter.

**Two smaller ones, same session:**

- `scripts/Invoke-SqlOnHetzner.ps1` is a **function file**, not a script — running it does nothing
 and returns nothing. Dot-source it (`. .\scripts\Invoke-SqlOnHetzner.ps1`) or use
 `scripts/waze/diagnose.py sql "…"`, which handles the SSH path itself.
- A device can **enrol in NanoMDM before it has a fleet row** (all five new units authenticated
 18:53-18:59Z, were absent from `fleet_devices`, and could be registered from the serial +
 enrollment pair read out of NanoMDM's own `devices` table). Do not conclude "not enrolled" from
 "no fleet row".
