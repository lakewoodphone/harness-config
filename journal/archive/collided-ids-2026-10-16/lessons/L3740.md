**L3740 · A surname-only link backfill gives one customer another's work order - and the last-10-digit phone test finds it in a minute**

A link backfill that matches on SURNAME ALONE will hand one customer another customer's work order,
and the phone-mismatch test catches it in about a minute.

MEASURED 2026-10-13. The 2026-10-03 sync-record link backfill wrote `WO2604210130` (order id 1430,
Perel Goldstein, +17329306285, the Sunbeam order) into THREE records:

 sunbeam-perel-goldstein-2026-03-23.json correct
 macbook-pro-13-a2338-goldstein-9177572354-2026-09-17.json WRONG - Sendy Goldstein, +19177572354
 sd-card-goldstein-8482104005-2026-09-17.json WRONG - Moshe Goldstein, +18482104005

Three different people, one surname. The two wrong records also had `workflow.ticketState: closed`
and `workflow.workOrderState: completed` copied from that order, and `linkedToProductionOrder:
true`. Every verifier read both cases as already linked to production, so they were invisible to
the reverse-gap count - the same shape that hid `weissman-ssd` for three weeks.

THE TEST, cheap enough to run whenever links are in doubt. For every sync record on origin/main,
read its own `customer.phone` and the phone on the order its `references.productionOrder` /
`workflow.orderNumber` names, compare the LAST TEN DIGITS, and report the disagreements.

 414 records, 294 claim an order, 19 disagree, 9 are true phone mismatches,
 2 provably another customer's order (both fixed), 10 carry no phone and cannot be checked.

Two traps in the measuring. `remote_sql.py` guards with a word-boundary regex over the whole
statement, so a customer SURNAME inside a `values` list can trip it - a case id containing
`yisroel-alter` was refused as a write with `refusing to run a statement containing the keyword
'alter'`. Put ordinals in the SQL, not names, and join back outside. And the DSN-free path is
`ssh <authority> "python3 ~/lpt-ops/lpt_ops/remote_sql.py --store operational"` with the statement
on STDIN - `lpt sql` takes its SQL as a command-line argument and dies with "The command line is
too long" a little past 20 KB.

FIXING IT: annotate, do not erase. `references.productionOrder` is a CLOSED schema block and
`linkWarning` is its documented key, so the wrong order stays visible with the reason; set
`operational.linkedToProductionOrder: false`; remove `workflow.orderNumber`/`orderId` so nothing
reads the false link as true; reset any state copied from the wrong order. Precedent:
`surface-laptop-4-1950-greenfeld`, 2026-10-12.

WATCH THE `syncHoldReason` LENGTH. It is `maxLength: 400` and only 2 of 414 records violated it -
so an over-length note is a NEW defect, not house style. It will not be obvious: the schema is
already invalid on ~300 of 414 records, so "the schema fails" is not a signal. Validate the
specific field, or diff the error list before and after.

AND `lptcase check` HAS A WARNING THAT PROVES THE ANNOTATION WORKED. After the fix the only delta
was two extraction warnings reading
`work-order-mentioned-only-as-a-known-wrong-link; order-id-mentioned-only-as-a-known-wrong-link`.
That is the tool saying it understood, and it is the read-back worth quoting.
