**L3816 · A paid order can read collected 0.00 (lpt-link-payment is the fix, and it will not run from Windows); and orders.paymentStatus is not a money indicator - 60 orders carrying money read PENDING**

Measured 2026-10-15 on the LPT `operational` store, while pulling up WO26101312747 (Ullman).

## 1. A paid order can read `collected 0.00` because nothing joins the money to the order

The Ullman order read **collected 0.00** while the customer had paid **53.31** two days earlier. The money was never missing: `payment_transactions` id **3312**, SUCCEEDED, 53.31, carried **`orderId` NULL** and `customerId` NULL. Two NULLs, and the shop's own case reads as unpaid.

`lpt-link-payment` is the fix, and it is dry-run by default:

```
python3 ~/bin/lpt-link-payment --order WO26101312747 --payment-id 3312 # plan
python3 ~/bin/lpt-link-payment --order WO26101312747 --payment-id 3312 --apply # write
```

Read back: **collected 53.31 across 1 SUCCEEDED row**. The row changed in exactly two columns.

**`lpt-write payment set` and `lpt-link-payment` are not the same tool and only one of them helps.** `payment set` needs a Stripe charge id, which a Terminal row does not carry; `lpt-link-payment` **attaches a row that already exists**. A case file written before 2026-10-14 recorded the link as *open because `payment set` cannot do it* — true of that tool, and stale about the estate.

## 2. `lpt-link-payment` does not run from Windows

From ZABZ-TECH it exits **1** — quote it exactly:

```
cannot read a DSN from /home/zabz/personal-secretary-mvp\.env
```

A **backslash** in a Linux path: the local path separator leaking into a path that is read on the remote host. Every other `lpt-*` tool runs fine from Windows because it hands the path over whole. This one builds it locally first. **Run it on the authority** (`python3 ~/bin/lpt-link-payment …`), which is what `lpt-ops/docs/writes.md` documents anyway. The one-line fix is on the Windows client side and is not made.

## 3. `orders.paymentStatus` is NOT a money indicator on this store — read `collected`, never it

The Ullman order now carries 53.31 collected and **still reads `PENDING`**. That is not a defect and not a signal. Measured on `operational` 2026-10-15, over every order carrying at least one linked SUCCEEDED payment:

```
select to_jsonb(o)->>'paymentStatus' as ps, count(*) as n, sum(t.amt) as collected
from orders o
join (select (to_jsonb(payment_transactions)->>'orderId')::bigint as oid, sum(amount) as amt
 from payment_transactions
 where status::text = 'SUCCEEDED' and to_jsonb(payment_transactions)->>'orderId' is not null
 group by 1) t on t.oid = o.id
group by 1 order by 2 desc;

PENDING 60 7588.40
CAPTURED 57 6660.76
```

**60 orders carrying money read PENDING.** Roughly half the shop's paid orders do. Money is `sum(payment_transactions.amount) where status='SUCCEEDED'` — the `collected` figure `lpt ticket` prints. `writes.md` already warns that `collected 0.00` is not evidence of non-payment; this is the same failure in the other direction — a status field that looks like it answers the money question and does not.

The query avoids the PowerShell trap (embedded double quotes are stripped before a native command sees them) by going through `to_jsonb(...)->>'orderId'` instead of `"orderId"`. That idiom is worth reusing for every camelCase column in this store.
