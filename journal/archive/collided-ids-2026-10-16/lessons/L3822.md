# I said a capability did not exist without checking `bin/` — and it had existed for two days

Measured 2026-10-14. This is the `repeated-work` failure, and it is the third most common one in this
estate's own audit. It was mine, and it cost real work in both directions.

## What I claimed

Across several notes written to production, and in a summary to the owner, I stated that a
`payment_transactions` row could not be created by us — that the figure would have to be "typed into the
website's counter page by a person". I wrote that sentence onto `WO26082712685`, `WO2609040001` and
`WO2609030001`, among others, as an instruction: *"DO NOT create a payment_transactions row from this
note."*

## What was already there

**`bin/lpt-record-payment`** — committed **2026-10-12**, six days before I wrote those lines. It records
a settled Stripe charge as a `payment_transactions` row, with guards: it refuses an unknown order, a
non-positive amount, a duplicate row, an amount greater than the Stripe charge, and an amount less than
the charge without `--refund` **and** `--refund-reason`. Its own docstring names the exact failure I was
writing into the record as unavoidable:

> `lpt-write payment set` proves a Stripe charge and records only the order's paymentStatus ... The
> consequence, found on the Kogel job: the order read CAPTURED while `collected` read **0.00** ...
> **That is the failure this tool removes.** There is no counter-page fairy; the someone is us.

And it quotes the owner: *"you are always the someone, never wait for someone else."*

## Why I missed it

I searched `docs/`. The tool lives in `bin/` with **no doc of its own** — `docs/` holds `writes.md`,
`sweep.md`, `audit.md`, `payrecon.md`, and nothing at all about payments. `install.ps1`'s
`$entryPoints` is what decides which `bin/` scripts become commands, and `lpt-record-payment` is not on
it (correctly — it is authority-side), so it was not on PATH either and could not be discovered by
tab-completion or by `lpt --help`.

**"Is there a tool for this?" is answered by listing `bin/`, not by searching `docs/`.** A directory of
executables is the inventory; documentation is a subset of it and was incomplete.

## What it cost, and what fixing it bought

Three orders had a **proven** Stripe charge while `collected` read **0.00** — the order claiming money
its own ledger showed none:

| order | charge | recorded |
|---|---|---|
| `WO26082712685` | 309.21 | `payment_transactions` 3319 |
| `WO2609040001` | 309.21 | 3320 |
| `WO2609030001` | 159.94 | 3321 |

Each read back as `collected <amount> across 1 SUCCEEDED row(s)`. Each is followed by a **corrective
note**, because the earlier note on that order said the opposite and a record that contradicts itself
is worse than either statement alone. The correction names the attribution basis **and its limit** — two
are amount-and-timing matches rather than name matches.

The original instruction was not wrong about the danger: a row invented from a prose claim IS the defect
this whole area keeps producing. It was **too broad** — it forbade the thing that was evidenced along
with the thing that was not. "Do not fabricate" must not become "do not record".

## The rules

1. **Before concluding a capability is missing, list the directory of tools.** `ls bin/`, check the
 launcher list, then read `docs/`. An absence of documentation is not an absence of the tool.
2. **A tool with no doc and no launcher is invisible.** `lpt-payrecon` had the same defect in the
 opposite direction: it had a doc and no launcher. Both now have the missing half, and the README
 carries a Tools table so the next session does not have to rediscover the inventory.
3. **When a rule has to be narrowed, the narrowing is a new note.** A correction by citation, never an
 edit — the record of having been wrong is the valuable part.
