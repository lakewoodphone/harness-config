**L3761 · A manifest built from an incomplete source passes its own truncation - plus exFAT 11-char labels and the pkill-f self-match on Windows**

**L3746 · A delivery manifest built from a not-yet-complete source file copies, verifies and PASSES against its own truncation — and two Windows traps that hid it**

MEASURED 2026-10-13, Greenfeld Dell delivery (WO26091712718). Three separate defects, all found inside one hour, all of which would have produced a **confidently green, silently wrong** result.

**1 · THE TRUNCATION (the dangerous one).** A scheduled tick built the delivery manifest minutes after the source hash pass reported `DONE`, and produced **9,050 files / 61.83 GiB** where the truth is **16,756 files / 175.16 GiB** — the missing 114 GiB being the customer's entire `Desktop`. It then began copying, and would have: copied 62 GiB, verified every file against *its own truncated manifest*, printed `VERDICT: PASS`, written the README and checksums, removed its own task, and been handed to a customer as "everything". **A verify proves the copy matches the manifest; it can never prove the manifest is complete.** The `DONE` summary and the file it describes are two different objects, and only a cross-check ties them together: the summary line carries `files=N`, so the manifest must hold N data rows before anything is built from it. That guard now exists, and a simulated 9,000-row input is refused with exit 3. Re-running the builder against the complete file is now byte-identical twice over.

**2 · exFAT LABELS ARE 11 CHARACTERS, NOT 32.** The medium was recognised by a volume label. `Set-Volume -NewFileSystemLabel 'GREENFELD-256'` (13 chars) fails with **"Invalid Parameter"** and `label.exe` says **"Invalid volume label"** — on exFAT. With the label as the only test, the second pass would have seen a non-blank, unlabelled volume, refused it as "not ours", and the copy could never have resumed after an interruption. **Recognise a medium by its DISK SERIAL, recorded on disk, and treat the label as decoration.**

**3 · `pkill -f` HAS A WINDOWS TWIN, AND IT KILLED THIS SESSION'S OWN SHELL.** Asking `Get-CimInstance Win32_Process` for processes whose `CommandLine` contains `greenfeld-copy.ps1` matches **the very command doing the asking**, because the pattern is in its own command line — the identical self-match already documented for `pkill -f <pattern>`. It killed its own shell (exit `4294967295`). Use `$_.ProcessId -ne $PID`, and build the pattern at runtime (`'greenfeld' + '-copy.ps1'`) so the literal never appears in the searching command line. This happened **twice in one session** with two different patterns.

**AND THE THING THAT MADE ALL THREE SURVIVABLE:** the copy was running as a detached, resumable process with its state on disk, so stopping it cost nothing — kill by PID, delete the partial copy from the medium (the source is untouched, so nothing is lost), fix, restart. **A long copy must be interruptible at any moment, or you cannot fix what you find.** Had it been a foreground command inside an agent session, the only options would have been "let the wrong thing finish" or "lose the work".
