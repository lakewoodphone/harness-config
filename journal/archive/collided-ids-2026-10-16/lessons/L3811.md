**L3811 · Just re-running it is NOT a resume: rsync --partial + --ignore-existing silently keeps a truncated file, and lpt-copy-userdata uses both flags**

**L · "Just re-run it" is not a resume. `rsync --partial --ignore-existing` keeps a truncated file — and the shop's own logical-copy tool uses exactly those two flags together.**

**Measured 2026-10-14 on `zabz-tech-linux`, on scratch data in `/tmp` — no customer file involved:**

```
source file 419,430,400 bytes
rsync --archive --partial --ignore-existing --bwlimit=20000 ... (sender killed after ~5 s)
after the interrupt, dst 102,629,376 bytes
re-run the IDENTICAL command dst STILL 102,629,376 bytes
cmp -> TRUNCATED FILE SURVIVED THE RESUME
then: moved the newest destination file aside, re-ran
cmp -> identical
```

**The mechanism, and it is the whole point:** `--partial` leaves the interrupted file at its
**destination name** (measured above — the partial was at `dst/big.bin`, not at a temp name).
`--ignore-existing` then tells rsync to **skip any file that exists at the destination**. So the
truncated file is treated as finished, for ever. Neither flag is wrong on its own; **together they
turn a resume into a silent corruption.** A "resume" that reports success and leaves 100 MB of a
400 MB file is the worst shape of failure this shop has: it looks complete.

**Where it bites here.** `lpt-copy-userdata` (the bench logical-copy tool,
`/usr/local/bin/lpt-copy-userdata`) runs verbatim:

```
rsync --archive --no-perms --no-owner --no-group --modify-window=2 --partial --ignore-existing --info=progress2 ...
```

and `docs/customer-operations/playbooks/hdd-recovery-playbook.md` §5 describes it as
*"idempotent+resumable"*. That line is now corrected in the file, dated. The **delivery** path is
genuinely safe by a different route — `verify_stick.py --repair` re-copies what is missing or wrong —
but the plain re-run has no repair step and no verify of its own.

**What any resume must therefore do — three rules:**

1. **Move aside (or delete) the destination's newest file before restarting.** That is the interrupted
 one. Renaming it within the same filesystem costs nothing and destroys nothing, and it is what makes
 the resume actually re-fetch the file.
2. **Verify by comparing every destination file's path AND byte size against the source.** This catches
 the whole class in one metadata-only pass, with no data read: a truncated file cannot match the
 source's size. `comm -23 <(dst list) <(src list)` over `find -printf '%s %P\n'`.
3. **Hash the irreplaceable files on both sides**, and treat `--size-only`/`--checksum` as a better
 resume mode than `--ignore-existing` when the transfer is large.

**Live implementation, and it is tested:** `/srv/recovery/cases/20261014-123456-raitzik-inspiron-one-2205/resume-raitzik-copy.sh`.
It finds the patient drive by **SMART serial, never `/dev/sdX`** (pattern from
`/usr/local/bin/lpt-resume-wx82a701t62z`, written 2026-10-07 after a resume guessed the wrong letter),
**refuses** if no drive reports that serial, if two do, if the archive destination is not mounted (the
system disk is 95% full — this is the guard that matters most), or if the device backs the destination.
Its idempotency guard was **tested against the live copy**: it printed `ALREADY RUNNING`, exited 0, left
the PIDs unchanged and moved nothing.
