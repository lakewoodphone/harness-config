**L3504 · CORRECTION to H3495: the live website reads operational, not app - and a stale label in lpt doctor is what made me say otherwise**

CORRECTION to journal H3495, which reported as BROKEN that "the website is not being updated" - orders frozen 2026-09-14, communications frozen 2026-10-06. **That was wrong.** The live LPT website reads `operational`, and `operational` is current.

WHAT SETTLED IT, and it is a reusable method. Do not infer which database a deployed service reads from a config file or a label - ask the service to publish its own schema history, and compare it. `GET https://api.lakewoodphoneandtech.com/api/health/migrations` is public and returns the backend's own Prisma ledger. Reproduced by me 2026-10-11T19:49Z:

 api.lakewoodphoneandtech.com latest migration 20261009010000_w12_perf_work_order_list_no_index @ 2026-10-09T02:06:25.770Z
 operational (_prisma_migrations) same name @ 2026-10-09 02:06:25.770760+00:00 <- same millisecond
 app (_prisma_migrations) stops at 20260909000000_add_google_identity @ 2026-09-10

`operational` holds 643 orders, 40 of them newer than 2026-09-14; `app` holds 595 and none newer than 2026-10-01. The 2026-10-06 cutover moved the site onto `operational`, and `app` (lpt_prod on Hetzner) is the retired archive. So `lpt-sync-to-production.py` calling `PHONE_TECH_FULL_DATABASE_URL` "the production website" was right all along.

ROOT CAUSE OF MY ERROR, and it is fixed in code: `lpt doctor` labelled `app` as "app (what the website serves)" (`lpt_ops/cli.py:224` and `:353`), `transport.py`'s docstring said the same, and `write_helper.py` repeated it. All four now say what was measured - operational is what the website reads, app is the retired archive. Commit `361b438` in lpt-ops, pushed.

THE GENERAL LESSON: a stale LABEL in a tool is as dangerous as a stale number, because it is read as provenance rather than as a claim. Every one of those four strings had been false since 2026-10-06 and nothing tested them. When a tool names what a remote system is FOR, that sentence needs a date and a proof, or it will eventually be the reason a session tells the owner something untrue.
