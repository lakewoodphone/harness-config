**L3807 · Two sessions editing one case file silently revert the front matter while the body survives - so re-read the head of a case file after appending to it, and stage only your own files**

**Two sessions editing one case file silently revert the head of it — and the head is what a human reads.**

MEASURED 2026-10-14 on `lpt-hub`, the Fisher case file (`sd-card-fisher-9145702075-2026-10-11.md`).

WHAT HAPPENED. I appended three entries to the file across the day and pushed each one. A parallel
session was editing the same file at the same time, and its commits interleaved with mine on the branch
(`829b3142d` and `45fe25cd0` landed between my pushes). The result: my **body** entries survived
untouched, but the **front matter** — the state block at the top, which is the part a staff member reads
first — was back to the 2026-10-13 state. It said "23 recordings" when the answer was 30, "two cards"
when the owner had put up three, and carried a stale `updated:` date. The body and the head of the same
file disagreed, and the head was the wrong one.

HOW I CAUGHT IT, and the check that is worth keeping: before editing I re-read line 1-32 of the file
rather than trusting that my last successful commit was the current state. `git show HEAD:<file>` then
proved the body was intact and that `HEAD` equalled the remote tip — so nothing was lost, only
overwritten at the top. Without that read I would have appended today's work under a head that
contradicted it.

WHY IT IS INVISIBLE BY DEFAULT
- **Nothing reports a conflict.** Both sessions pushed successfully; both were `0 0` against their
 upstream after pushing. A clean `git status` and a clean push are not evidence that the file's head is
 yours.
- **The revert is plausible-looking**, which is worse than an error. "23 recordings" was true on
 2026-10-13, so the reverted text reads as a normal case file rather than as damage.
- **It only hits the fields the other session rewrote.** Body entries are append-only in practice, so
 they survive; the front matter is a whole-block rewrite, so it does not.

THE RULE
1. **After appending to a case file, re-read its front matter before walking away.** One read. If it
 disagrees with what you just appended, you are the one who has to fix it.
2. **Before editing a case file, read the head first** — not because it may be stale, but because
 another session may be in it right now. `git fetch` and check whether the branch tip moved under you.
3. **Stage only your own files.** The working tree in this repo routinely carries other sessions' dirty
 case files (three of them on 2026-10-14). `git add <your two paths>`, never `git add -A`.
4. **If a count or a state appears in two places in one file, change both in one commit** — the front
 matter and the activity entry are the pair that drifts.
