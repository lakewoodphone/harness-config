**A third defect, found by disbelieving the tool's own output — and my first fix of it was also
wrong, which is the part worth remembering.**

`activation_lock_already_applied()` matches `fleet_alerts.message`, and the fleet-api writes **two**
forms: `Activation Lock enabled via DEP API (bypass code generated)` on a first enable, and
`Activation Lock confirmed already enabled via DEP API (repeat attempt)` on an idempotent re-run.
The matcher knew only the first, so **DRN 2002 was reported `activation lock: NOT APPLIED` in the
final diagnostic seconds after the step itself printed `applied`** — the lock was in fact applied on
2026-09-15. Fixed at `d8d497aa`; verified afterwards against all seven LPT DRNs, all `True`.

My first attempt at that fix set the pattern to `"Activation Lock%via DEP API"` — **no trailing `%`** —
and `LIKE` anchors BOTH ends, so it required the message to *end* with `via DEP API` and matched
nothing. The second run therefore still printed NOT APPLIED and I nearly recorded the fix as
ineffective. It was caught only by running the pattern variants against the same row
(`'Activation%'` 1, `'%DEP API%'` 1, `'Activation Lock enabled via DEP API%'` 1, mine 0). **A LIKE
pattern without a trailing `%` is an equality test on the tail of the string.**
