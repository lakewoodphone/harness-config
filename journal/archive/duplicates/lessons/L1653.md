**Two environment facts that beat the obvious fix, and a reminder that "flaky" is not a mechanism.**

Measured 2026-09-15, working the last residual failures of `pytest tests/`:

1. **The suite runs with the repo's `.env` loaded into `os.environ`.** Inside pytest,
 `os.environ["MCP_ENABLED"] == "false"`; in a clean interpreter it is `None`. So a test that
 constructs `Settings(_env_file=None, ...)` still reads the deployment's value -- an environment
 variable outranks a file, and `_env_file=None` only silences the file. The fix that works is to
 assert the **field default** (`Settings.model_fields[...].default`) when a test's subject is a
 default, and to treat "what is in the environment" as part of the fixture surface otherwise.
2. **"Flaky" is a label, not a mechanism.** I wrote that `test_worker_clears_in_flight_after_send`
 raced a thread; reading the code shows `_worker` is synchronous and the thread lives in its caller.
 The label cost a round of wrong reasoning and it is now corrected in the record. Two candidates
 remain for a genuinely intermittent failure and both are testable: a swallowed DB write under load,
 and a counter keyed to the current date.

Rule: before naming a cause for an intermittent failure, **read the code path and say where the
concurrency or the state actually is.** A hypothesis that cannot name the line is a hunch, and a hunch
written into a pain entry becomes a fact for the next session -- which is exactly what happened here
and cost a correction.
