**L3797 · The owner queue's filing doctrine cannot be enforced by a regex; two designs measured 0/161 and 3/137**

TWO DESIGNS, BOTH MEASURED AGAINST THE LIVE QUEUE, BOTH REJECTED. Nothing was deployed.

THE GOAL was to enforce what `owner-queue.py` already says about itself in its own docstring:
*"WHAT DOES NOT BELONG HERE -- anything I can fix. Fix it. A queue row is an admission that I could
not."* Nothing enforced it. Of 162 pending rows the open-work triage judged about **137
engineering**, so the one deadline that was genuinely the owner's sat under a hundred that were never
his.

**DESIGN 1 -- REFUSE, keyed on the recommendation's verb.** A row whose recommendation *promises* the
work ("I will fix it", "Let me implement that") is a to-do item wearing a decision's clothes. Built it,
dry-ran it against all 161 rows carrying a recommendation, and it would have refused:

 **0 of 161.**

And the reason killed the approach. The rows that ARE mis-filed open with **"I recommend merging PR
#1"** -- the SAME phrasing a legitimate row uses: **"I recommend adding disk"** (row #473, a real
money decision). The verb cannot separate them; a guard that refused the first would reject the
second.

**DESIGN 2 -- WARN, keyed on the SUBJECT.** Pull requests, CI, lint, refactors, schema migrations,
worktrees. Measured against the same 162 rows:

 would warn on 5 -- of which about 3 are genuinely mis-filed (#461 "Merge the ... branch",
 #474 "Merge PR #1", #485 "Promote PR #92"), 1 is ambiguous (#473, the disk question, which
 mentions a schema migration as an alternative), and 1 is a false positive (#469, a website
 hours question that references "PR 142").

**Recall roughly 3 of 137.** A regex that finds 2% of a class and calls itself the guard for it is
false progress, and shipping it would have made this look solved.

WHAT THAT MEANS, and it is the useful part: **the queue's filing discipline is a JUDGEMENT, not a
pattern**, and no rule I can write in that file will carry it. The triage made that judgement by
reading 393 entries; a regex cannot. So the honest position is the one the tool already had -- the
doctrine is stated, nothing enforces it, and the way it gets enforced is an agent deciding, per row,
which it is.

AND THE QUEUE'S PRESENTATION IS ALREADY CORRECT, which changes what needs fixing. `owner-queue.py
next` returns **#475**, the 2025 tax extension, two days out -- the four critical rows are all real
and all first. The owner is not being shown the wrong thing. What is wrong is that 137 rows that
should not exist are sitting in the same table, and the fix for that is at the moment somebody
writes the row, by a reader, not by a regex.

WHAT I DID INSTEAD: nothing to the tool. Two designs, two measurements, both rejected before
deployment. The tests are the record; the code is unchanged.
