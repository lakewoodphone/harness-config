**L1663 · A queue needs a terminal state for every outcome, or its length is a lie**

**A queue needs a terminal state for every outcome, or its length is a lie.**

Measured 2026-09-15. `evolution_log` had one terminal state, `applied`. So a proposal that was reviewed
and found worthless had nowhere to go: it stayed "unapplied", indistinguishable from one awaiting a
decision, and the count a reader saw (75) was nearly four times the number of real proposals (12). Two
of those classes were *structurally* dead -- targets the writer now refuses, and duplicates of a newer
offer -- so no amount of future diligence would ever clear them.

That is the same defect as the owner-message queue in round 36 (held forever, indistinguishable from
waiting) and the agent questions in round 37. A queue is only a queue if every row can reach an end, and
the ends must be honest ones: `dismissed` with a reason, not a fake `applied`.

Rules:
- **Enumerate the terminal states before designing the queue.** applied / dismissed / expired /
 superseded -- and if a class of rows cannot reach any of them, the queue is a log with a count that
 lies.
- **Dismissal carries a reason, in the row.** "dismissed: superseded by a newer identical offer" is
 evidence; a bare status is a shrug, and the next reader cannot tell a considered decision from an
 accident.
- **State the intent in the docstring and then test it.** I wrote "the newest copy stays open" and the
 code kept the oldest; the test I wrote for the stated intent found it in one run, and the corrective
 pass fixed the live rows so the record matches the intent.
