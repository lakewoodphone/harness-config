**L3615 · Never render an unknown age as 0 (liveness printed age_seconds=0 for a 51-minute-old tick); and a long read transaction freezes the WAL checkpoint horizon**

Two durable measurement rules, both earned 2026-10-12 on secratary-cloud.

1. A LIVENESS CHECK THAT WRITES `pkt.data_age_seconds or 0` CAN NEVER DETECT SILENCE.
 /root/ceo-kernel/ck/sentinel.py:452 does exactly that, and sources.scalar() leaves
 data_age_seconds None for a raw SQL scalar (its provenance prints `age=?`). So
 `age = 0`, `pkt.stale` stays False, and the check reported, twice, verbatim:

 metrics={"newest_tick": "2026-10-12T02:49:47.367604+00:00", "age_seconds": 0}
 summary="ticking: newest tick 0.0m ago"

 at kernel runs 2026-10-12T03:27:52Z and 03:40:46Z -- while the same DB, queried
 directly, gave the true age as 2427s and 3059s (~40 and ~51 minutes). With
 max_age_seconds=3600 the check would still say "ticking" at 59 minutes. It is a
 green light wired to a constant, and it is the ONE check whose whole job is to
 notice the company going quiet.
 RULE: never render an unknown age as 0. Print "age=?" / severity UNKNOWN, and
 verify any liveness reading against a direct SQL age before believing it.

2. A SINGLE LONG-LIVED READ TRANSACTION PINS THE WAL CHECKPOINT HORIZON AND THE WAL
 GROWS FOR THE WHOLE RUN.
 /run/authority-offsite/helpers/read-pages.py opens
 `file:/root/authority.db?mode=ro`, runs `BEGIN`, then streams all 5,917,128 pages
 of the 24 GB database through `sqlite_dbpage` in ONE read transaction (pid 377479,
 alive 28+ minutes). While it lives, /proc/locks shows its READ mark at shm byte
 124 and `PRAGMA wal_checkpoint(PASSIVE)` is pinned:

 03:25:49 (busy=0, log=21833, checkpointed=9279)
 03:33:30 (busy=0, log=23195, checkpointed=9279)
 03:40:11 (busy=0, log=37520, checkpointed=9279)
 03:41:30 (busy=0, log=38559, checkpointed=9279)

 `checkpointed` is FROZEN at 9279 for the entire run while `log` climbs; the WAL
 went 89,951,992 -> 158,863,112 bytes, ~2-3 MB/min, and `busy=0` throughout, so a
 PASSIVE checkpoint looks healthy while achieving nothing. Writers also pay for it:
 a WAL 38,000 frames deep is more work per commit and a longer lock hold.
 RULE: a long read snapshot and a write-heavy store do not coexist cheaply. Either
 bound the reader's snapshot (chunked consistent reads) or run it when the box is
 quiet -- and alarm on `log - checkpointed` growing, not on `busy`.
