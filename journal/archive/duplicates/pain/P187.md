## P187 — run_subsystem_once cannot run the five browser syncs, and only journal.py refreshes the mirror

**P-new -- the subsystem run-once endpoint cannot run the five browser syncs.**

`POST /autopilot/subsystems/{name}/run-once` exists to run one subsystem on demand, but its `known`
list omits `boa_sync`, `chase_sync`, `amex_sync`, `paypal_sync`, `amazon_sync` and `ebay_sync` --
exactly the subsystems that most often need a human (session expiry, MFA) and therefore the ones
worth exercising on demand. Measured 2026-09-15: two attempts to verify the sync-alert clear through
it returned `{"ok":false,"error":"unknown_subsystem", ...}`, and the verification only became
possible through the separate `POST /finance/{amazon,ebay}/sync` routes (which do route through
`record_subsystem_result`, and worked).

Fix: teach `run_subsystem_once` the sync names (dispatching to the same `_maybe_sync_*` bodies the
loop uses, bypassing their cadence gate), so the endpoint means what its docstring says. Until then
the honest description is "run one of fourteen subsystems", and a hook on any other subsystem is
unverifiable on demand.

**P-new -- the mirror refresh is now read-triggered, but only where the reader is `journal.py`.**
`_maybe_refresh_questions()` runs when the status page finds the mirror more than an hour old, which
fixes the case that bit (P130, a page printing an 11-hour-old count as current). Any other consumer
of `state/owner-questions.md` -- a hand cat, an editor, an agent reading the file directly -- still
sees whatever is on disk. Accepted deliberately: the file's own Provenance line carries its stamp,
and the alternative carriers were worse (autosync.sh never commits and reports a dirty tree).
