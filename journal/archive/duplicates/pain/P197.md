## P197 — Entry ids collide across machines when unpushed; the journal repos are 39/10 apart

## What hurts

**The journal's entry ids are not actually safe across machines, and the journal repos on
two machines have diverged by 39 commits in opposite directions.**

The id allocation was rebuilt to be collision-proof — "which allocates the id over the
index, the shards and every git ref so two machines cannot choose the same number twice."
That holds only if each machine can *see* the other's allocations, i.e. only after a
successful push. Offline or unpushed, two machines happily pick the same number.

Measured 2026-09-15 ~17:25Z on ZABZ-YOGA:

```
git rev-list --left-right --count origin/master...master -> 10 39
```
- origin/master (other machines) has 10 commits this laptop does not: `eb0c17f` (Eli
 Green case closed), `525d9b2`, `b947290`, `fb63b5d`, `0c70a5d`, `992a12f`, `a613801`, …
- local master has 39 the remote does not: journal rounds 54–59, including this round's
 `L1664`, `L1665`, `D190`, `H349`.
- Replaying the 39 on top (rebase) **collided on the first commit**: both sides had added
 `journal/entries/handoff/H322.md` and `journal/entries/lessons/L1637.md`, and both
 touched the generated `journal/index/entries.tsv`. Two genuinely different entries, one
 id, on two machines.
- The push was refused (non-fast-forward) and **nothing was forced**. The rebase was
 aborted and the working tree restored to exactly its prior state (39 commits, and
 another session's unstaged `packages/plugin-attention` files popped back).

Consequence while it stands: this laptop's six rounds of journal entries are **not visible
from any other machine**, and the round-59 continuity record exists in one place only.

## Why it will happen again

Nothing in the write path requires an id to be reserved against the remote, and nothing
detects a duplicate id across divergent histories — `journal.py check` validates the
*local* tree, so it reports 0 errors on a tree that collides with another machine's.

## What would fix it

1. **A reserve-then-write step**: fetch before allocating, and allocate from
 `max(local, all fetched remote refs)`, so an unpushed allocation is visible to the next
 allocator on this machine and a fetched one is respected. If the remote cannot be
 reached, allocate from a per-machine high-water band or refuse loudly rather than
 guessing.
2. **`journal.py reconcile`**: merge divergent journal histories deterministically —
 keep the id on the side whose commit is older, renumber the newer entry (and its
 heading, index row and any cross-references) to the next free id, and record the
 renumber in the entry so the change is auditable instead of silent.
3. **Make `check` able to see it**: compare ids against `origin/*` refs when they are
 present, and report a cross-history duplicate as an error, not as health.

## Evidence

- `git rev-list --left-right --count origin/master...master` → `10 39` (ZABZ-YOGA,
 2026-09-15).
- Rebase conflict output: `AA journal/entries/handoff/H322.md`,
 `AA journal/entries/lessons/L1637.md`, `UU journal/index/entries.tsv`.
- `git push` rejected with `hint: use 'git pull' before pushing again`; no force push was
 performed.
- Post-abort verification: `git log --oneline -1` → `5657efa`, working tree clean except
 the restored `packages/plugin-attention` modifications and untracked `_scratch/`.
