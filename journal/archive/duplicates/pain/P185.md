## P185 — Nothing asserts the app can narrate itself, and the journal has no explicit retention cap

**P-new — nothing asserts that the application can narrate itself, so the logging
regression can silently return.** The root logger sat at WARNING with zero handlers for
an unknown period; INFO appeared only when a third-party library happened to call
`logging.basicConfig()` first, which means the system's own narration was a side effect
of import order. `app/logging_setup.py` fixes it, but nothing notices if a future
refactor drops the call, changes the level, or replaces the handler. Fix: a kernel check
that reads the service journal and refuses (UNKNOWN) rather than passing if it cannot,
going HIGH when zero formatted INFO lines appear in twenty minutes while the loop is
running. That is the monitor for the monitor, and it is cheap: the journal is right
there.

**P-new — the journal is 916 MB with no explicit retention cap.** `journalctl
--disk-usage` reported 916.1 MB, `/etc/systemd/journald.conf` leaves `SystemMaxUse`,
`SystemKeepFree` and `MaxRetentionSec` at their commented defaults, and the filesystem
is 54% full (239 GB of 467 GB). The default cap is 10% of the filesystem, so this is not
urgent -- but turning INFO on app-wide raises the write rate, and the first minute alone
produced 124 lines. Fix: set `SystemMaxUse=` explicitly to a number chosen from the
measured rate, after a day of the new logging, rather than letting a default nobody read
decide how much disk the narration may take.
