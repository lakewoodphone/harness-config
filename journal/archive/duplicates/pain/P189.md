## P189 — The suite's 153 order-dependent errors were a descriptor limit; seven failures left, four of them quiet-hours

**P-new — the suite's 153 "order-dependent errors" were a file-descriptor limit, and the remaining seven failures look time-of-day dependent.**

P139 attributed the errors to whole-suite interference because `test_work_generation.py` passes 94/94
in isolation. Measured 2026-09-15, that explanation is wrong:

| run | result |
|---|---|
| `pytest tests/` | 6 failed, **74 errors**, 2635 passed |
| `pytest tests/` (random order) | 991 passed, **1726 errors** |
| `bash -c 'ulimit -n 16384; pytest tests/'` | 7 failed, **0 errors**, 2708 passed |
| `pytest tests/` after the conftest fix | 7 failed, **0 errors**, 2708 passed |

The soft descriptor limit on this host is **1024** (hard 524288). The suite creates more than a
thousand asyncio event loops, each opening a self-pipe -- two descriptors -- so it exhausts the limit
and every later test fails at fixture setup with `OSError: [Errno 24] Too many open files`, surfacing
as `RuntimeError: no running event loop`. Ordering does not cause the errors; it decides how quickly
the limit is reached, which is why random order produced 1,726 against 74. `tests/conftest.py` now
raises `RLIMIT_NOFILE` to 16384 at import (`c60f75b2`), so `pytest tests/` is a gate on a default
shell.

**Still open, and it is the deeper half:** the loops are not closed, so the leak is real and merely
bounded. A `pytest`-level cleanup (close lingering loops, or use `pytest-asyncio`'s policy) would
remove the need for the raised limit -- and until then, "raises the limit" is a mitigation on the
record, not a fix.

**Also open (7 failures, a set distinct from the nine that were fixed):**
`test_api_endpoints.py::test_twilio_sms_timeout_sends_async_followup_reply`,
`test_family_chat.py::TestAtomicDedupe::test_duplicate_webhook_deliveries`,
four quiet-hours tests in `test_family_chat_personality.py` (`TestQuietHours::test_overnight_span`,
`test_same_day_span`, `TestHardGates::test_quiet_hours_blocks`,
`TestWorker::test_worker_quiet_hours_no_send`) and
`test_phase3_modules.py::TestPhase3ConfigFlags::test_mcp_enabled`. Four of the seven are quiet-hours
gates and two runs produced 6 then 7 failures, so the leading hypothesis is a **wall-clock
dependence** -- they may pass or fail by the hour. That is one measurement away: run those four and
read whether they build their times from `datetime.now()`.
