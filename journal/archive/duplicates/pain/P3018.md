## P3018 — The secretary MCP backend refused every connection and mesh subagent children SIGKILL in 5s on ZABZ-TECH on a log-write PermissionError

**Both measured 2026-10-11 in one session on ZABZ-TECH.**

**(1) The whole `secretary` MCP toolset was unreachable.** `ps_search` (code, twice), `ps_health`, and
`ps_comms_search` each returned `{"ok": false, "error": "<urlopen error [Errno 111] Connection refused>"}`
— the MCP server process answers, its backend does not. `ps_search`'s own docstring advertises itself as
the way to search the estate; it is not, when it is down, and an agent that trusts it learns nothing
rather than learning "no match". Workaround used: local `read`/`grep`/`glob`, and `lpt sql --store
operational` for data questions (that path was healthy all session).

**(2) Every mesh subagent child died in ~5 seconds on ZABZ-TECH.** Two workers were dispatched; both
came back `exit=none, signal=SIGKILL, ms=5010`, `child produced no framed output`, with this on stderr:

```
mcp_launcher: cannot write C:\Users\ezabz\Code\personal-secretary-mvp\data\logs\mcp-launcher.log:
 PermissionError: [Errno 13] Permission denied
```

The mesh transport itself was fine — the broker placed both children, printed the placement, the
pressure reading (50.9 % committed), and released the lease with `ok=true`. **What died was the child
agent, on a log-write permission error, every time.** So a fan-out to that node silently costs its
children, and the failure is reported as a transport attempt ("node zabz-tech — structural"), which
reads like a network problem and is not. The work was done single-threaded instead.

**What would fix it:** make the launcher tolerate an unwritable log (fall back to stderr, or to the
session temp dir) so a logging path can never kill an agent; and make the dispatcher's report say
"child process failed to start" rather than classifying it as a node/transport fault.
