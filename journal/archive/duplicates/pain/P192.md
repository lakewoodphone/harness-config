## P192 — The residual flakiness is leaked fire-and-forget threads in the hub tests, poisoning the in-flight marker across tests

**P-new — the residual suite flakiness is leaked fire-and-forget threads in the hub tests, and the pathway is now named.**

Measured 2026-09-15, in this order:

1. The two `TestWorker` tests that flake in a full run fail **0 times in 24 isolated iterations** of
 exactly those two tests. So nothing is wrong with them; the interference comes from their
 neighbours in the same file.
2. `tests/test_family_chat.py` calls `hub.handle_inbound_sms(...)` dozens of times, and
 `app/family_chat/hub.py:664` calls `personality.maybe_respond(...)`, which is **fire-and-forget**:

 threading.Thread(target=_worker, args=(sender, text, media_urls), daemon=True).start()

 `_worker` is synchronous; the thread is the delivery mechanism. No test joins it.
3. `_worker` writes the in-flight marker through `db.set_setting("chip_in_flight_until", ...)`, and
 `db` resolves its path from `default_db_path()` **at call time** -- which each test monkeypatches to
 its own tmp file. So a thread spawned by test A that wakes while test B is running writes the
 in-flight marker **into test B's database**. Test B's worker then hits its own gate
 (`if _in_flight_until() > now: return`), returns early, and the assertions about sends and reply
 counts fail.

That fits every observation: intermittent, only when the hub tests run, and always in the tests that
assert a send happened.

**Two fixes, and I recommend the first:**

1. **A fixture in `tests/test_family_chat.py` that stubs `personality.maybe_respond` to a no-op.**
 That file tests the *hub* -- the webhook response, mutes, dedupe, outbox -- and its `sender.calls`
 assertions are about the hub's own fan-out, not Chip's LLM reply path (which is covered by
 `test_family_chat_personality.py`, where `_worker` is called directly and synchronously). Cheap,
 local, and it removes the leak at its source in those tests.
2. **Make `_worker` capture the database path when it is spawned**, so a slow worker can never write
 state into a different database than the one it was created with. This is the better *production*
 property, but it touches every `db.*` call in the worker, so it wants a round of its own.

Not done in this round on purpose: I have the mechanism and two candidate fixes, and a partial edit to
`_worker`'s data access at the tail of a round is exactly how a "fix" becomes next round's bug.
