Two of this round's wins were **real code bugs that the tests were right about**:

1. **`_decode_folder_uri` was Windows-only.** `file:///tmp/x` decoded to `tmp\x` -- the leading
 slash stripped and every separator backslash-ified -- so on this Linux authority every VS Code
 workspace `folder_path` was `home\zabz\code\...`, a string matching nothing. Per-workspace chat
 attribution silently found nothing while the extractor's output looked populated. Now decoded into
 the host's form (`C:\...` on Windows, `/home/zabz/...` on POSIX).
2. **The gateway's sensitive-path rule split segments with `Path.parts`**, so on POSIX a Windows path
 was one segment and the `appdata` rule never fired. The call was still blocked (by the
 chat-resource rule) -- nothing unsafe -- but the reason did not name what it should. Segments are
 now split on both separators.

**The remaining failure is one test, and now measured precisely:** four assertions in
`test_sanitize_tool_call_out_of_workspace` all encode Windows-host semantics (a Windows read root
makes a Windows path readable; a write root refused with its own message). On POSIX the guard blocks
in every case, which is the safe direction and the point of L1647. Rewriting it platform-aware is a
careful edit, not a regex in passing -- which I proved by breaking the file and restoring it from git
(L1649).
