**L3466 · A silent subagent is not a working subagent: the mesh one-shot died with exit 4294967295 and returned no message**

## What was attempted
`subagent` (the MESH provider — a real child on another node) was dispatched on 2026-10-08 ~22:07Z with a
self-contained brief: add four tailnet addresses to `harness-config/scripts/phone-gate-allow.txt`, commit,
push, and prove it at the gate with a before/after curl and a negative control.

## What actually happened
The job ran for ~30 minutes, `job_output` returned no interim output at any point (expected — a subagent
only returns its final message), and it finished as:

```
[status: failed, error; diagnostic: the remote one-shot exited 4294967295 and produced no final message;
 stderr tail: ] tools/list
[37240] [Remote→Local] 1
dsh: reasoning:
Inbox doesn't exist. I'm on zabz-tech (Windows). Let me start working, and write progress to outbox as I go.
...
There's an outbox.jsonl already with 1054 bytes. Let me read it — maybe from a previous turn of this thread.
```

Reading that: the child DID start (it saw the machine, tried to write progress to an outbox, and found a
pre-existing 1054-byte `outbox.jsonl` from an earlier run), and the **wrapper** died — `4294967295` is
`0xFFFFFFFF` = `-1`, the classic "no exit status" of a Windows process that was killed or never reaped —
returning no final message. Note the child noticed "Inbox doesn't exist": the remote one-shot expects an
inbox file and there was none.

## Effect: none, because the work was done directly
The authority's allow file was still the original (`e40d88ed…`) when I checked 30 minutes later, so the
child had changed nothing. I did the work myself: file written, sha matched both ends (`3274be6b…`), commit
`691af67e` pushed, and the gate proved it with no restart — the four new addresses 403 -> 200, the
employee's Mac still 403. Nothing in that report depends on the failed child.

## What to look at next time a mesh dispatch fails this way
1. The remote one-shot's own wrapper: `4294967295` is a *missing* exit status, not a failing command — the
 wrapper, not the child, is what failed.
2. The `inbox`/`outbox` files it mentioned on the target node. The child read an `outbox.jsonl` belonging to
 a previous run; if the one-shot's final message is written through the outbox and the run is re-entered,
 a stale outbox is a candidate for "first write wins" and the final message never arriving.
3. Whether the target node's `dsh` is the same version as the dispatcher's.

## The transferable rule
**A 30-minute silence from a subagent is not progress.** A subagent returns only at the end, so "running,
no output" is indistinguishable from "the wrapper died in the first minute" — and the only way to tell is to
look at the effect on the ground (here: the file's sha on the target). **Check the effect, not the status,
and when the effect is absent, do the work yourself rather than waiting.** On a job this small the delegate
cost 30 minutes and produced nothing; the direct route, including verification, took about ten.
