# Blocking video on Kyocera flip phones is already solved in-repo — search `docs/incidents` and `docs/devices` first

Owner instruction, 2026-10-08: *"we did this once, can't we find the info for how to do it, don't reinvent the wheel."*
He was right, and I had already started designing a solution before searching. The work exists:

- `lpt-flip-phone/docs/incidents/E4810_VIDEO_BLOCKING_ANALYSIS_2026-07-16.md` — five approaches tried and priced.
- `lpt-flip-phone/docs/devices/E4810_GALLERY_VIDEO_ARCHITECTURE.md` — the package/intent architecture.
- `lpt-flip-phone/docs/incidents/FENDEL_E4610_FILTER_ONLY_VIDEO_BLOCK_WORKFLOW_2026-03-25.md` — the E4610 case.

**The settled facts (do not re-derive):**

1. **No root on these phones** (system-as-root + dm-verity, no bootloader unlock). ADB runs as `shell`.
 So `pm disable` on an individual activity fails — re-measured 2026-10-08 on E4610 Android 7.1.1:
 `java.lang.SecurityException: Shell cannot change component state for <pkg>/<activity> to 3`.
 `appops` is package-scoped and cannot target video. **`pm disable-user --user 0` on whole packages
 is the only runtime control** — which is exactly what the deploy engine's `forced_disabled_packages`
 already does.
2. **The video player is `jp.kyocera.player.movieview.MovieView`, inside package `jp.kyocera.datafolder`**
 — the same package that holds the photo gallery (`jp.kyocera.gallery.GalleryActivity`), the image
 viewer (`RootPlayerActivity`), the file manager (`com.cyanogenmod.filemanager...`) and the crop tool.
 `com.kyocera.musicplayer` also registers video handlers (`VideoBrowserActivity`,
 `MediaPlaybackActivity`). `com.kyocera.videoplayer` exists on some E4610 units only.
3. **Therefore, on a live phone, blocking video costs the stock gallery, file manager and music player.**
 Verified 2026-10-08 on 616468703: with `jp.kyocera.datafolder` + `com.kyocera.musicplayer` disabled,
 `am start -a android.intent.action.VIEW -t video/3gp` returns *unable to resolve Intent*.
4. **Photos do NOT survive that block.** `jp.kyocera.cameraAFP/.PhotosVideosMenuActivity` is the camera's
 *mode* menu ("1. Camera / 2. Video"), not a gallery — do not claim photos stay viewable. That misread
 is exactly how the wrong product promise gets made.
5. **The gallery-preserving route is firmware-only.** A `MovieView`-stripped, signed APK already exists at
 `lpt-flip-phone/temp/DataFolder-novideo-signed.apk` (built 2026-07-16) and can only be baked into
 `system.img` before flashing. It cannot be installed on a live phone (`/system` read-only, no root).
6. The July doc's own recommendation was to encode the block in the tier config rather than one-off ADB,
 and the Fendel doc's takeaway says the same. That config fix was never applied — a `-NoVideo`
 profile is the honest shape when a customer accepts the cost.

**The transferable rule:** before designing any device-behaviour change on these phones, grep
`docs/incidents/` and `docs/devices/` for the model and the behaviour. This repo keeps priced,
measured answers to exactly these questions, and rediscovering them burns the owner's bench time —
the one resource this work exists to protect.

Evidence: the three docs above; E4610 616468703 measurements 2026-10-08 (component-disable refusal,
video intent unresolvable with the two packages disabled, camera mode menu screenshot).
