**L3458 · lpt sql loses double-quoted identifiers through the lpt.cmd shim - call python on the shim directly**

## The lesson

`lpt sql "<select>"` **cannot carry a double-quoted identifier when it is invoked through the `lpt.cmd`
shim under PowerShell.** The camelCase columns in the LPT production schemas (`"firstName"`,
`"orderNumber"`, `"createdAt"`, `"workOrderId"` …) need double quotes, and batch-file argument
parsing strips them: the server received `select id, firstName, lastName from customers` and answered
`UndefinedColumn: column "firstname" does not exist`. Two different calls, two different columns
named in the error, so it is a quoting loss rather than a schema surprise.

**The fix, measured 2026-10-08:** skip the shim and call Python on the shim file directly with the SQL
as its own argv element:

```powershell
$shim = "C:\Users\ezabz\AppData\Local\lpt-ops\_lpt_shim.py"
& python3.exe $shim sql 'select id, "firstName", "lastName" from customers where "lastName" ilike ''%senz%'' limit 20'
```

That returns rows with the identifier intact. Nested single quotes inside a PowerShell
single-quoted string are written by doubling them (`''%senz%''`), and that survives the hop to the
authority because `transport.py` base64-encodes the SQL before it goes over ssh
(`OperationalStore._via_authority`, `--sql-b64`) — so the quoting is only ever lost locally, in the
batch wrapper, never in transit.

**Why this matters beyond one session:** the shop's real columns are camelCase and every ad-hoc SQL
question about a case needs them. A session that hits this error and reads it as "the column does not
exist" concludes the schema is different from what it is and starts guessing column names. The error
message itself is misleading — `HINT: Perhaps you meant to reference the column "customers.firstName"`
is Postgres helpfully suggesting the column you *did* name, minus its case.

**Related, same session:** `lpt sql` takes exactly one statement — batch several by looping in
PowerShell, not by joining with `;`.
