# A failed adb pull let the previous handset's UI dump be reported as the new handset's state

Measured 2026-10-08, mid-deployment of a second E4610. A harness I had written earlier in the session
(AST-extracts `Invoke-Adb`/`Set-MatvtActivationKey`/`Test-VoiceAccessPrefs` from `ready-e4610.ps1` to do
the MatVT and Voice Access steps) had the **first phone's serial hardcoded**. Run against the second
phone it printed:

 MatVT activation key ... checked=True value='17' ok=True <- reported as VERIFIED
 Voice Access prefs pref_show_fab='adb.exe: device '616462586' not found' ok=False
 accessibility services adb.exe: device '616462586' not found

The first line was **false**. `Get-UiXml` writes to a fixed local path, the `adb pull` failed, the
function only checked that the file existed — so it parsed the *previous phone's* dump still sitting on
disk and reported a configuration for a handset it had never talked to. The same harness would have let
me pass `-VoiceAccessVerified` on the strength of someone else's phone.

**Guard that fixed it** (now in `_scratch/pre-finalize-check.ps1`): serial as a parameter; delete the
scratch dump directory before the run; after the dump, `throw` if the file is missing or older than
120 s; and check `adb devices` for the serial before anything else. A pull that fails must never leave a
previous artefact in place to be read as current state.

**Generalisation:** any helper that reads device state through a file (UI dump, screencap, logcat pull,
config pull) must prove the file is *this* device's and *this* run's before its contents are believed.
Existence is not freshness, and freshness is not provenance. This is the same failure family as reading a
stale database and reporting a crisis: the number looked right, so it was believed.

Evidence: the run above (2026-10-08, 17:1xZ, serial 616468703 while 616462586 was long gone);
corrected harness output with `dumpAgeSec=0` and the device's own date string.
