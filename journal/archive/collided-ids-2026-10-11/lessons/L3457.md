**L3457 · A Gmail send goes out as the account's default send-as alias, not the address passed as account - read the message back to verify From, body and recipient**

Title: A Gmail send does not go out from the address you pass as `account` - it goes out as that account's default send-as alias, so verify the From by reading the message back.

MEASURED 2026-10-08, sending the Golembick paid receipt (lpt-hub ticket 73896).

- `gmail_service.send_message(settings, account="lakewoodphoneandtech@gmail.com", to=..., subject=..., body=<html>, html=True)` returned `ok` with a real Gmail id and labels `['SENT']`.
- Reading that message back with `gmail_service.read_message(...)` showed `From: info <info@lakewoodphoneandtech.com>` - **not** the `lakewoodphoneandtech@gmail.com` address that was passed as `account`, and not the address I told the owner it would come from. The authenticated account's default send-as alias is the `info@` branded address, so Gmail rewrote the From.

RULES
1. There is no send-as argument being used here: `from_addr` is optional and was not passed. When it is omitted, the From is whatever that account's default alias is - so **never tell the owner or the customer which address a mail came from without reading it back**. The returned `labels` and the `SENT` label say nothing about From or about delivery.
2. Verify a send by reading the message, not by the send's return value: `read_message` gives `from`, `to`, `subject`, `date`, `snippet` and the body. Check the body for the numbers it was supposed to carry (here `PAID IN FULL`, `703.79`, `543.79`, the receipt number) - that is the difference between "Gmail accepted it" and "the right letter with the right figures went to the right person".
3. `MOCK_OUTBOUND_COMMS=True` silently turns every Gmail send into an intercept that still returns `ok: True`. Test it before sending and treat a `mocked: True` result as NOT SENT. It was unset on this send, checked in both `.env` and the shell environment.

RELATED, SAME HOUR
- The shop's branded receipt script `personal-secretary-mvp/scripts/send_lpt_receipt.py` recomputes NJ tax as `subtotal * 6.625 %`. On a job paid in two parts that invents money: a 670.00 subtotal would have printed **714.39** as the total when **703.79** was actually charged, because tax was charged on the 510 balance only. Prefer a generator that renders the amounts it is given (`lpt-hub/tools/receipts/receipt_email.py`) over one that recomputes them, and keep the receipt HTML as a file that the sender reads byte-for-byte rather than rebuilding it at send time.
