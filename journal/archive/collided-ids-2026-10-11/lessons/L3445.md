**L3445 · A lookup that returns nothing is a refusal, not a fact - and I set the flag that means never-publish**

**1. A lookup that returns nothing is a REFUSAL, not a fact.** I ran `lpt ticket 7324924311` on the
Niasoff drive case, it printed *"No work order matches in either store"*, and I wrote into the case
file that production had no record of this customer. **Production had held `WO26100812727` (id 3003)
for two hours.** `lpt ticket WO26100812727` finds it instantly. `lpt ticket Niasoff` misses too. So
**both** the phone and the name lookups fail for a customer whose row is correct and live.
**Rule: before reporting a negative about production, confirm it with a second, different key** — a
number, an order id, and a name are three independent questions, and one miss proves nothing about the
other two. This is the P3 failure mode exactly (reading the wrong data and believing it), and it is the
one that produced a crisis that never existed before. The read path is defective; the miss was not
evidence.

**2. `shouldSyncToWebsite: false` means NEVER PUBLISH.** The push tool's own source says so: *"a record
carrying operational.shouldSyncToWebsite == false is never pushed"*, and its sibling comment draws the
distinction the sync-records README blurs: *"shouldSyncToWebsite=false says 'never publish this';
syncHoldReason says 'this belongs on the website, publish it when the reason no longer applies'."*
I set `false` on a new record because the README told me to use it for "documentation-first until a
live work order is ready" — and that would have permanently blocked the record from ever reaching
production. **Use `syncHoldReason` for not-yet; reserve the boolean for never.**

**3. The push tool's guards are ORDERED, and an early one hides a later, more precise one.**
`shouldSyncToWebsite` → `syncHoldReason` → `references.websiteOrder` (already linked to a live order) →
token-overlap duplicate dedup. Setting a hold reason made the run SKIP with *"this case is deliberately
held"*, which is true but useless — the actual reason was the third rule. **When a tool refuses, make
it refuse for the most specific rule that applies, or the next reader learns the wrong lesson.**

**4. The status vocabulary moves, so read it every time.** `lpt-write status set IN_REPAIR` was refused:
the live `orders.status` set is now `AWAITING_DIAGNOSIS, AWAITING_APPROVAL, AWAITING_PARTS,
AWAITING_PAYMENT, READY_FOR_PICKUP, CANCELLED, UNFIXABLE` — seven values with **no in-progress
state at all**, and `CHECKED_IN`/`IN_REPAIR`/`COMPLETED` are gone from this store though an earlier
dialpad run-log listed them. The guard refusing was the system working. Had it been hardcoded, an
invented status would now be in the shop's data.

**5. A miss on the write side is not a miss on the comms side.** The SMS sent through
`scripts/send-lpt-sms.py` leaves **no `sms_log` row** (known gap P217), which makes it look unrecorded.
Production showed it linked to the work order as `2026-10-08 15:14:55 SMS OUTBOUND`, with the exact
approved text. **Check the order's own comms before concluding a send left no trace.**
