**D3042 · 2026-10-11 · Shop labels carry NO barcodes (owner 2026-10-09) - changed the tool default, not just a note: --ticket no longer adds one, and a label went from 40.6mm to 16.2mm of tape.**

**Owner instruction, 2026-10-09, verbatim:** *"put a note to stop printing them with barcodes we don't use barcodes anymore."*

## What was decided

**Shop labels carry no barcode.** The ticket number is still printed BIG as the heading — that is the part anyone reads — and nothing is encoded. The CODE128 strip had been added automatically to every work-order label and was never scanned by anyone.

## Why a code change and not only a note

The owner asked for a note. A note alone would not have stopped it, because `--ticket` added a barcode **by itself** — the next session printing a work-order label would have re-introduced one without deciding to. So the default was changed:

| | before | after |
|---|---|---|
| `work_order_label()` | `barcode=ticket` | `barcode=""` |
| `--ticket` | implies a barcode | does not; help text updated |
| passing `--barcode` | silently prints one | still works, but prints a NOTE to stderr saying the shop stopped using them |

**Measured effect:** the identical label fell from **40.6mm of tape to 16.2mm** — the barcode was more than half the label.

## The thing the owner actually wanted from a label, in the same message

*"it's for my secretary to read the labels also so she needs this info."* A label has to let the secretary **find the job and know what to hand over and what to collect.** I had printed one for Kogel with a name, a phone and two prices and **no ticket number, no device and no job identity** — unusable for that. The house format was already on disk as a previously printed label (`_labelprinter/out/ym_reitman_2652.png`) and I had not looked at it. **When the shop has already printed the thing you are about to design, print it again — do not design it.**

## Layout facts worth not re-learning (all measured today, from `lpt_ops/label_printer.py`)

- **With `--ticket`, positional `info` lines are IGNORED** — the tool switches to `work_order_label()` and builds its own lines. Passing both drops the info lines silently.
- **Lines are TRUNCATED, never wrapped** — a long `--issue` is cut mid-sentence.
- **The plain form takes `--heading` AND `--barcode`**, so a label can have the big ticket number and as many full lines as needed. (No barcode now — see above.)
- Long lines shrink to fit rather than being cut until the font floor, so **everything renders, unevenly sized**. Keep the important lines short.

## A trap hit while doing this, worth its own line

`cp -p x y-$(date -u +...)` run through PowerShell: `$(date -u …)` is **PowerShell** syntax, so PowerShell expanded it locally, failed, and passed a **trailing space** instead of a timestamp — producing a file named `label_printer.py.bak-no-barcode- `. `mv` then could not match it and reported *"No such file or directory"* for a name `od -c` had shown as clean. **`repr()` in Python found the trailing space; `ls` and `od` did not.** Two lessons: check a filename's bytes in a shell that does not normalise, and never use `$( )` inside a command destined for the remote shell — quote the whole remote command in single quotes so the remote shell does the substitution.
