**D253 · 2026-09-17 · Broker-driven placement is committed, and a row may never precede its code.**

## The decision

Broker-driven placement is committed as `263785d` (17 paths: `packages/plugin-remote-fanout/**`,
the `placement`/`brokerSsh`/`brokerUrl`/`queueWaitMs`/`remoteCommand`/`remoteCredentialEnvFiles` keys in
`profiles/web/cordis.patch.yml` and `profiles/mesh/cordis.patch.yml`, and `docs/mesh/105-placement-committed.md`).

## What was decided

* **The row is committed WITH the code, never before it.** A `placement:` key in a row whose code
 cannot read it is the inert-config illusion this program keeps correcting (`103` §3.4).
* **`profiles/mesh/cordis.patch.yml` came with it**, although the brief named only `profiles/web`.
 Reason: those keys are the same package's `remoteCommand`/`remoteCredentialEnvFiles` passthrough and
 were uncommitted too, and the mesh row is what the authority composes.
* **The mode rule stays in the package and its default stays `broker`.** Measured consequence: the
 desktop's own live row has no `placement` key at all and still resolves to broker, because the
 default is the package's. The row's key is documentation, not the mechanism.
* **A broker that cannot be reached rejects and dispatches nothing** — no silent fallback to `target`.

## Why it is host-plane, recorded because it was asked and one belief had already been wrong

The mode, the placer and the registered provider are built in `lib/index.js` `apply()` at **engine
start**; the per-child asking is `lib/provider.js` `start()`. So "is this engine broker-driven?" is a
boot-time decision that a preset edit cannot make. Evidence: `resolvePlacementMode(config)` runs in
`apply`, not per session.

## The thing that was not done

No engine was restarted: the laptop's pid 4880 (the owner's live work) and the desktop's pid 24556
(sibling streams) both still run their old registrations, so neither consults the broker yet.
