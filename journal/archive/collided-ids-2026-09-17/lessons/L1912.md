**L1912 · A profile check is evidence only for the logon class that ran it - --dump-config names no class**

**A profile check is evidence only for the logon class that ran it, and `--dump-config` names no
class.**

MEASURED 2026-09-17 on `zabz-tech`, same bytes, same minute, same machine:

 node <dsh>/lib/bin.js --profile web --dump-config # ssh-spawned reader
 exit=1 lines=16 Error: dsh: cannot resolve profile bundle "dsh-plugin-remote-fanout" …
 at resolveBundleDir (dsh-app-boot/lib/index.js:831)

 node <dsh>/lib/bin.js --profile web --dump-config # local Interactive-logon reader
 exit=0 lines=620

Neither output says which reader it was. This is a check that cannot fail in the direction that
matters: the process that runs a DISPATCHED CHILD is the remote class (sshd), and the check is run by
hand from the local class.

`docs/mesh/105` §7 recorded "exit=0 lines=620 — the two disagree, which is the finding" and blamed a
silent fallback to an older plugin. That blame is wrong, measured: from the passing reader the loader
resolves the junction ITSELF (`…\profiles\web\node_modules\dsh-plugin-remote-fanout`, version=0.2.0,
patchExists=true) and never a fallback directory; and 105's own 4382-byte / version=0.1.0 read is the
same file at revision `895114b`, two commits before the placement commit — 4382 bytes on disk is that
blob's 4296 characters with CRLF.

RULE: run the check as each logon class you care about, or it is a rubber stamp. The repo already
knows this in exactly one place — `mesh-run.mjs:229` refuses the whole dispatch when "this node's
sshd session cannot traverse a reparse point" — and `--dump-config` does not.
