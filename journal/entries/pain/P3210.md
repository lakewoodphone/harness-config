## PAIN (new, urgent) — `/root/authority.db` is 26.7 GiB and ~17 GiB of it is the fleet's own session archive stored TWICE; a VACUUM is already impossible and the recorded growth rate is wrong by 25x

**Measured** 2026-10-14 by the W2 worker, read-only (`sqlite3 -readonly "file:/root/authority.db?mode=ro"`).

**Composition.** `PRAGMA page_size` 4096, `page_count` 6,951,430 = 28,473,057,280 B exactly;
`freelist_count` 159, so **99.998 % of the file is live data** — not deleted-row bloat. 236 tables,
414 indexes (the documentation's "203 tables" is stale). **No media/blobs:** media live on disk and
the DB stores paths. Attribution:
- `dsh_session_events` — 2,276,251 rows × ~3,741 B (mean stable across three sampled 2,000-row
 windows) ≈ **8.5 GB**
- `dsh_session_events_fts` — an FTS5 table **with no `content=` clause**, so NOT external-content:
 it keeps its own full copy of `raw` in `..._fts_content.c3` (2,286,561 docs × ~4,136 B) ≈ **9.5 GB**,
 *plus* an inverted index of unmeasured size
- structural proof: `dsh_session_events` has rootpage 586,701, so **91.56 % of the file lies at or
 after it**; everything older fits in ~2.4 GB
- `procedural_experiences` 606 MB (33,592 rows × 18 KB — the embedding is stored as JSON **text**,
 31 KB/row of `state_embedding_json`)
- **the shop's own comms — calls, SMS, voicemail — are under 1 GB combined**

**Growth is ~25x the recorded number.** From five dated offsite readings
(`/var/lib/authority-backup/last-run*`, 2026-10-11 → 2026-10-14):
**55.2–88.6 MB/h, 1.4–2.1 GB/day, 3-day mean 57.9 MB/h.** The "~2.3 MB/h" in
`/root/sms-audit-20261013/journal-bodies/pain-disk.md:2` (repeated in `AUDIT-2026-10-13.md:208`) is
that number. At 2.3 MB/h the disk has 460 days; at 58 MB/h it has **19**.

**Why this is urgent, not a curiosity.**
1. **Free space is 25.0 GiB and growth is bursty by two orders of magnitude.** A live sampler caught
 **2.88 GB/h sustained, 5.85 GB/h over its last minute**, while this was being measured. At
 2.88 GB/h the remaining 25 GiB is **9.3 hours**. The offsite log already recorded only
 9,195,460 KiB free on 2026-10-13T05:21Z.
2. **A `VACUUM` is ALREADY IMPOSSIBLE**: `auto_vacuum 0`, so nothing else can shrink the file, and a
 VACUUM needs a second full copy — 26.53 GiB of database against 25.008 GiB free. There is no
 maintenance window that fixes this later; every day makes it less possible.
3. **Two live code paths read a multi-GB table.** `GET /api/v1/owner/dsh-sessions/stats` runs
 `SELECT COUNT(*) FROM dsh_session_events` (`services/dsh_session_ingest.py:565`, reached from
 `main.py:22925`) — an **8.5 GB B-tree walk on a request path**, while the same function one line
 away already avoids a `COUNT(*)` on the FTS vtab for exactly this reason. And the ingest's
 re-index `DELETE FROM dsh_session_events_fts WHERE rowid IN (SELECT id FROM ..._fts_content ...)`
 (`services/dsh_session_ingest.py:429-441`) scans the multi-GB content table **while holding the
 SQLite write lock**, which the file's own comment measures at 63.6 s idle / >90 s loaded.
4. **The WAL's danger is a pinned read snapshot, demonstrated:** during a deliberately bounded
 `dbstat` read the WAL went 64 MiB → **646,807,072 B** while the main file did not grow at all, and
 **2 s after the read was released** the WAL returned to exactly 64 MiB and the file jumped 126 MB.
 The API holds **15 simultaneous fds** on this database. This is the mechanism behind the estate's
 `database is locked` storms and quite possibly behind the API's own memory/IO wedges.

**What would fix it, in order:** (a) look at the `COUNT(*)` on the request path first — it is one line
and it is on a hot path; (b) make the FTS table external-content (`content='dsh_session_events'`) or
drop the duplicate copy — that is ~9.5 GB of pure duplication plus its index, the single biggest
recoverable block; (c) store `procedural_experiences.state_embedding_json` as a BLOB, not JSON text;
(d) only then is a VACUUM both possible and worth doing, and it will need free space that does not
exist today; (e) prune/rotate the archive deliberately — **not by a hurried `DELETE`**, because this
archive is the estate's own memory and it is the thing this session is using to exist.

**Do not read `/root/authority.db.new` as a copy of anything: it is 0 bytes, dated 2026-10-11.**
Same decoy shape as the 0-byte `/opt/company/data/accounting.db`.
