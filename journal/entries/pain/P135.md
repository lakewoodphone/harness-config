## P135 — A journal append takes 3 minutes and blocks the turn that needs it

Observed 2026-09-14: journal.py append lessons took 3m10s for the first call in a process, then ~26s and ~23s for the next two. A single foreground pwsh call carrying three appends was killed at 180s with NOTHING written and no error, which is the worst possible failure shape - it looks like success unless you go and check the entries directory. The cost lands exactly when the journal matters most, at the end of a long turn when the last thing you have left is the write. Cause is structural, not a one-off: every append rebuilds the index (journal/index/entries.tsv, aliases.tsv, journal.db, stamp.json) and touches git refs, and at least two other machines (SECRATARY, ZABZ-TECH) were writing entries at the same time - one concurrent merge allocated a duplicate id, which is what L1466 is about. WHAT WOULD FIX IT: an ppend --fast path that writes the shard and defers the index rebuild to a background/
eindex step, plus a per-host write lock so appends serialise instead of contending. UNTIL THEN: never run more than one append per foreground call, always run them in a background job, and verify by listing entries/ afterwards rather than trusting the exit code.
