## P178 — An unwritable /data crashes the fleet dashboard at startup and restart-loops it (init_db WAL pragma) - pre-existing

Ranked by the damage it can do. Pre-existing, NOT introduced by commit 1b0c91d6 — but the deploy
made it visible and it is one volume-permission change away from a real outage.

THE DEFECT: `DatabaseService.get_standalone_conn()` runs `PRAGMA journal_mode=WAL` (db_service.py
line 173) and `init_db()` runs it on an `@app.on_event("startup")` hook. If `/data` is read-only,
unwritable, or missing in a way the process cannot fix, the pragma raises
`sqlite3.OperationalError: unable to open database file`, FastAPI aborts with
`ERROR: Application startup failed. Exiting.`, and because the service is `restart:
unless-stopped`, Docker restarts it into the same wall forever. Observed, not theorised: a
throwaway container with the live DB copy mounted `:ro` exited with code 3 and that exact traceback.
The same WAL pragma exists in the OLD code (/opt/waze-mdm/fleet-dashboard/backend/main.py lines
82/91, `init_db` at 149), so this is not a regression from the honesty commit.

WHY IT IS WORSE THAN IT LOOKS: the container never becomes "unhealthy" — it dies at startup and
loops, so its healthcheck never even runs. The `*/5` watchdog's restart path is defeated by it
(`compose up -d` will keep restarting the same broken thing). And it fails at exactly the moment
an operator would want the dashboard most: a full disk, a read-only remount after a filesystem
error, or a volume-permission mistake.

WHAT WOULD FIX IT (one of two, both small, both need a decision to change shipped behaviour):
1. Make `init_db()` tolerant: catch `sqlite3.Error` on open/pragma, log it, do not raise. Then the
 process starts, `probe_database()` reports `ok: false` with the real reason, `/api/health`
 answers 503 and the container reads UNHEALTHY — visible, debuggable, not a crash loop. This is
 also the behaviour the healthcheck was designed for.
2. Drop `journal_mode=WAL` in favour of the default rollback journal, which needs no write for a
 read-only open. Cheaper, but silently changes write concurrency for the ingest path.

Recommendation: (1). It converts an unbounded restart loop into a single, named, unhealthy state.
Note the disk-pressure angle: `df` on / is already monitored by the same watchdog at 85%.
