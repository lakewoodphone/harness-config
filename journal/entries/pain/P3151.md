## P3151 — Two pricing paths, one column: the hand-set total carries no sales tax and is the path the shop uses

**P3142 · The shop has two pricing paths and only one of them collects NJ sales tax; the hand-set one silently charges zero, and it is the one the shop actually uses**

MEASURED 2026-10-12 on production (the RDS behind the deployed app, `d5oq83veii4rlb`).
I asked the app's OWN pricing summary, inside the production container, what each order's
subtotal, tax and total are, and compared that with what is stored on the order:

| order | `orders.total` | summary subtotal | tax | summary total | agree |
|---|---|---|---|---|---|
| 3020 | 149.00 | 139.74 | **9.26** | 149.00 | **yes** |
| 3019 | 165.00 | 0 | 0 | 0 | no |
| 3017 | 75.00 | 0 | 0 | 0 | no |
| 3037 | 100.00 | 0 | 0 | 0 | no |
| 3071 (my $2 test) | 2.00 | 0 | 0 | 0 | no |

`getTaxRatePercent()` returned **6.625**, so the rate is configured. Where the price went
through the pricing calculator the arithmetic is right and tax IS on top
(`139.74 + 9.26 = 149.00`). Everywhere else the summary is **all zeros** and the stored total
carries **no tax at all**.

**WHERE THE NO-TAX PATH IS, exactly:** `~/lpt-ops/lpt_ops/write_helper.py` `cmd_total_set`:

```
sql_update = 'UPDATE orders SET "total" = %s, "updatedAt" = %s WHERE id = %s'
```

It writes the raw amount. There is no tax in that file — `grep -i tax write_helper.py` returns
nothing. So `lpt-write total set --order K --amount N` puts a **tax-free** number into
`orders.total`, and that is the tool this estate reaches for when a price has to be put on a
work order.

**Why this is one bug and not three.** `orders.total` is treated as the FINAL amount by every
reader — the pay notice, the branded pay page, the Stripe link's `unit_amount`, the Zelle
sentence, the IVR. But the pricing path treats the same column as *subtotal + tax*, while the
hand-set path treats it as *the whole price with nothing added*. The two meanings share one
column, so:

1. **no tax is charged** on any hand-set price, by card or by Zelle, and nothing in the
 customer-facing flow adds it (`pay-notice.service.ts` says out loud that it adds no tax);
2. the pricing summary returns **all zeros** for those same orders, which is the most likely
 reason the work order page reads **"nothing owed"** on an order with a real balance — the
 summary and the stored total disagree and something treats the zero as authoritative;
3. the tax breakdown line never appears in the pay notice for those orders, because
 `readPricingMeta` only prints it when the recomputed summary AGREES with the stored total.

Filed while the full audit runs; the redirect-404 and the "nothing owed" chains are being
audited separately with file:line.
