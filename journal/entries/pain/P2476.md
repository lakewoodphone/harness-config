## P — A production work order keeps saying "model not recorded" after the model is known

**Impact:** measured today on order **WO26092412722** (order id 2940, customer 2743, Devorah Goldberg).
The order `title` was built from the case's *day-one* device string —
`Apple iPad (model not recorded) — charging port; the owner's intake note says "prob dead"…` — and it is
what the counter sees on the work order. After the owner supplied the model, I could set
`orders.deviceInfo` (now `{"model": "A2602", …}`) and add a linked customer note, but **the title cannot
be corrected through the safety layer**: `app/services/website_db.py` `ORDER_WRITABLE_FIELDS` (line 373)
contains `status, deviceInfo, needsAttention, description, paymentStatus, pickup_notified_at, total,
referredBy` and **not `title`**. So `update_order({"title": …})` is refused by `_validate_write`
("Field 'title' is not in writable set"). A one-line direct UPDATE would work and would bypass the
guardrail, which is exactly the kind of shortcut that later looks like the writes nobody can explain.

**Consequence:** the stale string wins over the corrected field for every human reading the WO, and it
says the opposite of what we now know. The note that carries the truth is on the WO timeline, but it is
below the wrong title.

**What would fix it:** add `title` to `ORDER_WRITABLE_FIELDS` with the same confidence gate the other
prose field has (`description` requires confidence ≥ 0.85), and have the sync path rewrite the title
when the case's device line materially changes. Until then, the only correct move is to correct it by
hand and say so — not to leave a wrong title in front of staff.

**Same family, smaller:** `website_db.insert_customer_note` has no `workOrderId` parameter, so every
"[Secretary Sync]" note the sync tool writes lands with `workOrderId = NULL` — on the customer profile,
not on the WO timeline. That defect is also recorded in `personal-secretary-mvp` docs
(`docs/operations/work-order-notes-audit-2026-08-12.md`: "All 40 `[Secretary Sync]` notes have
`workOrderId = NULL`"). Today's note was written with `workOrderId = 2940` explicitly so it shows on the
timeline, which means the tool is the thing that needs the fix, not the data.

**Evidence:** read-only production inspection 2026-09-24 (order 2940: `deviceInfo` NULL → set;
`title` unchanged; notes 2744/2745 with `workOrderId` NULL, 2747 linked to 2940); failure text captured
from `update_order` and `_validate_write` in `app/services/website_db.py`.
