## P177 — plain next build (Turbopack) panics in every junctioned worktree - and the committed fix for it does not work

RANKED: it makes the `npx next build` gate unachievable for every agent worktree in `chumash-timeline`,
and a false "verified fixed" claim about it was already committed to main once.

WHAT: plain `npx next build` (Turbopack, the default in Next 16) panics in any worktree whose
node_modules is a junction pointing outside the worktree:
 FATAL: An unexpected Turbopack error occurred
 Error [TurbopackInternalError]: Symlink [project]/node_modules is invalid, it points out of the
 filesystem root -> next build exit 1
Measured 2026-09-15 (ZABZ-TECH, worktree `_worktrees/chumash-timeline/chumash-gematria` whose
node_modules junctions to `C:\Users\ezabz\Code\chumash-timeline\node_modules`):
* plain build, cwd = worktree: exit 1. After rebasing onto main 76c377b ("drop turbopack.root so
 worktree-isolated builds work"): STILL exit 1. That commit does not fix it.
* plain build on the PRISTINE tree at 35a25c6, copied out of git with a junctioned node_modules:
 exit 1 (identical panic). So it predates any agent's code change.
* `npx next build --webpack` in the same worktree: exit 0, 14/14 pages, twice (before and after the
 rebase).

WHY: `node_modules/next/dist/build/turbopack-build/impl.js:85` -
 `const rootPath = config.turbopack?.root || config.outputFileTracingRoot || dir`
so Turbopack's filesystem root is the config value or the project dir, and Turbopack refuses to follow
a reparse point that leaves it. Auto-detection (package-lock.json) also lands on the project dir, so
dropping `turbopack.root` changes nothing: the old `root: process.cwd()` at least made the build work
when it was invoked from a directory above BOTH trees, because then cwd was the common parent
(measured: exit 0 with the old config, exit 1 after 76c377b). Next's own doc says the fix is to set
the root to "the parent directory of both the project and the linked dependencies"
(node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/turbopack.md:122).
There is no env var for it, and a hard-coded parent would be wrong for the main clone, for `next dev`
and for the Docker image (output: standalone).

WHAT WOULD FIX IT: use `npx next build --webpack` as the build gate inside worktrees (exit 0, proven);
or have the fleet create worktrees inside the main clone's tree / give each worktree a real install;
or set turbopack.root in an untracked local config. Do not "fix" it by deleting the root setting again.
