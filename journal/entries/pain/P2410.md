## P2410 — The phone question-card has been reported broken FOUR times and declared fixed three times, because every verification used a document that had never cached the layer

## P2316 · 2026-09-24 · Four reports, three "fixes", one variable never tested: a cached layer

THE RECORD. The owner has now reported the same failure four times on the same surface — an
agent's question card in the phone UI:
- 2026-09-11 "only part of it shows up, I can't scroll, and I can't click."
- 2026-09-14 23:2x "I can't scroll up enough to see the actual question. I just see the options for
 responses."
- 2026-09-16 (third report on the same surface; `assets/question-card.css` records it)
- 2026-09-24 14:5x, today: "I can't scroll normally and I can't see the question just to options for
 the response."

Three fixes shipped, each with a measurement: `question-card-check.py` (CSSOM reproduction),
`question-card-live-probe.py`, and the plugin's own `visualViewport` pixel repair. The phone UI
check at 2026-09-24T05:30Z reported `question_card PASS` and `question_card_live PASS` — the same
morning as the fourth report.

WHY THE FIXES AND THE REPORTS COULD COEXIST. Every verification loaded a FRESH document. A freshly
loaded document is served the current layer and is therefore always correct — it is precisely the
case a cache cannot break. The owner's phone is the other case: a tab that has been open since
before the change, which can only be reached by the version-token handshake. So the tests were
green and the reader was broken, indefinitely, and the green test was read as evidence that the
problem was solved rather than as evidence that a fresh document works.

THE ACTUAL FAULT, FOUND TODAY. `assets/question-card.css` was last changed on 2026-09-22 (commit
6d6f0a4 — the question detail box was swallowing the thumb gesture in its own 132px scrollport,
which is *exactly* the symptom he described again today). The layer's version token —
`phone-layer-version`, the ONLY mechanism by which an open tab learns a fix exists — was not bumped
with it. It still read `2026-09-16.3`. Every phone holding the 09-16 layer fetched the served layer,
compared tokens, found them EQUAL, and concluded it was current. The 09-22 fix existed on the
server and had never reached a single device that was already open.

WHAT FIXED IT TODAY (both verified against the live gate):
1. The token was bumped, so a cached tab now sees a different token and re-applies the layer.
2. The token is now DERIVED in `phone-gate.py` (`with_derived_layer_token`): the served value is a
 sha256 of the layer's own bytes, so any change to any file in LAYER_FILES changes the token by
 construction. There is no longer a human step to forget. Served token: `d9b4fddff742`, identical
 in the injected document and at `/dsh-phone-mobile.css`, and read correctly by the plugin's own
 regex.

WHAT WOULD STOP THIS CLASS OF PROBLEM. Any verification of a client-side layout fix must be run on
BOTH documents: a cold one, and one that has been holding the previous layer. A test suite that only
ever cold-loads is blind to the entire delivery path — which is where all four reports came from.
