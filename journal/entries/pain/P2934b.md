## P2934b — owner-ask rule 5 silently ate the only hours-drift question

WHAT HAPPENED
bin/hours-drift-check.py has reported exactly one disagreeing surface since 2026-10-07: the
Google Maps listing advertises Monday 10:30-5:30 when Monday is a no-walk-in day. The
consolidated owner row for it, owner_decision_queue #310, has been pending since
2026-10-07T04:09Z and was updated three times. It had never been put to the owner.

WHY: A FILTER FALSE POSITIVE
owner-ask.py pick() rejects a decision row whose question matches ALREADY_READABLE, with the
reason "answer is already readable - rule 5". That regex contains the bare phrase
google business profile. #310's question ended "...or give me Google Business Profile access
so I own the listing from now on?", so the row was rejected on sight. The phrase was put in
the regex for the GBP rating/review rows (#152/#153/#154, dismissed as engineering because
there is no GBP read path); it over-matches a legitimate owner decision that merely mentions
the listing.

PROOF (2026-10-10T12:40Z)
Loaded owner-ask.py as a module, bypassed ONLY in_hours(), called pick(reason=True): it picked
decision:248 and listed decision:310 under rejected with why "answer is already readable -
rule 5". A scan of all 156 pending rows found exactly ONE tripping ALREADY_READABLE, and it
was #310. So the guard silently ate the single hours question and nothing else.

WHY IT MATTERS
The drift is real and customer-facing: a customer can arrive Monday to a closed counter. The
checker escalates every 6 h (rc=3) and the escalation prompt says to file it in the owner
channel - and the owner channel refused to deliver it. A reading that cannot tell "the answer
is already readable" from "the question mentions Google Business Profile" is not a reading.

FIX APPLIED
Reworded #310's question and option B to drop the incidental phrase; the decision, options and
recommendation are unchanged and the row now survives the filter (kept 168 -> 169). Exact
pre-edit text backed up to ~/.owner-queue/row310-reword-20261010T123838Z.json. owner-ask.py
itself was NOT edited: it runs live every 30 min with --send, and the doctrine is to prefer a
separate process over changing the live send path.

LEFT OPEN (deliberate)
The regex's false-positive class still exists. The right fix is to match a DATA request (GBP
rating / review count / stats) rather than the bare phrase, with a test that proves an hours
question containing the phrase still reaches the owner. Not done here.

REFS
bin/hours-drift-check.py; bin/owner-ask.py; owner-queue #310; journal H3258, D2937.
