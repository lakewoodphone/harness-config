## P2609 — journal/index/* is generated state that is tracked in git: every host goes dirty by using the journal, and that is what blocked the fast-forward

The journal index is TRACKED GENERATED STATE, so every host's tree goes dirty by using it - and that is what froze ZABZ-TECH.

journal/index/journal.db (13 MB binary) and journal/index/stamp.json are committed to harness-config, but
journal.py REWRITES them whenever the index is stale. Measured 2026-09-28: on ZABZ-TECH the only two files
blocking a 56-commit fast-forward were journal/index/stamp.json and journal/state/owner-questions.md, and
neither had been touched by a human - ordinary use of the machine made them dirty, and git then refused to
overwrite them from the incoming commits.

This is a structural mismatch: a cache that lives in git AND is rewritten by the program that reads it
guarantees a dirty tree on any host that uses the journal, which guarantees a refused fast-forward the
moment upstream also touches those paths. It has already cost: 56 commits of configuration not reaching
ZABZ-TECH, a diverged-* preservation ref created on secratary, and a session's worth of forensics.

CANDIDATE FIXES (not applied - this is the journal's design, and the previous occupant documented why the
index is where it is, so it wants a deliberate decision rather than a drive-by):
 A. Untrack journal/index/ entirely (add to .gitignore + git rm --cached), since the README already says
 the cache "rebuilds itself" and "never blocks a read". Cost: a fresh clone starts cold.
 B. Keep it tracked but make it deterministic: journal.py writes the index only at EXPLICIT write time,
 never as a side effect of a read, and the file's content is normalised (no timestamps/paths that
 differ per host).
 C. Leave it, and rely on autosync step 2c (added today) to clear those two paths after backing them up.
 Cheapest, and it is what is running now - but it treats the symptom on every host forever.

RECOMMENDATION: A, in one deliberate commit, with the cache rebuilt once on each host afterwards.
