## P255 — send-lpt-sms.py prints the PREVIEW banner on a successful --send, so a session can read the top of the output and send a duplicate customer text

WHAT HURTS: scripts/send-lpt-sms.py prints its banner as "SMS PREVIEW - This is what will be sent" EVEN WHEN IT IS
CALLED WITH --send AND THE MESSAGE HAS ALREADY GONE OUT. The success line appears UNDER that banner:
 ==================================================
 SMS PREVIEW - This is what will be sent:
 ==================================================
 From: ... To: ... Body: ...
 - Daniel
 ==================================================
 OK SMS sent!
 Status: pending
 Message ID: 6376140727427072
WHY IT MATTERS: a session that reads the top of the output, or that greps for the word PREVIEW, concludes the
message was NOT sent and sends it again. On a customer text that is a duplicate message to a real person, and this
script path writes no sms_log row, so there is no second surface to notice the duplicate. The script's own preview
mode and its send mode are visually identical at the top.
MEASURED 2026-09-17 on the Goldstein A2338 quote text ($460 to +19177572354): the run that REALLY sent printed the
PREVIEW banner, then "OK SMS sent! Status: pending Message ID: 6376140727427072".
WHAT WOULD FIX IT: when --send is passed, print "SMS SEND - message is going out now" (or suppress the banner), and
print the preview banner only in dry-run. One conditional around the banner. Until then the rule for any session is:
READ THE BOTTOM OF THE OUTPUT, NOT THE TOP - the presence of "SMS sent!" plus a Message ID is the only evidence a
send happened, and its absence is the only evidence it did not.
Related, same runbook: the runbook already warns that this path writes no sms_log row, so the case-file record of
the message id is the only handle that exists.
