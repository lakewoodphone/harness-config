## P3002 — lpt ticket prints app=FOUND for a store that holds zero rows, hiding the divergence the tool exists to show

# `lpt ticket` prints `app=FOUND` for a store that holds nothing

**Found** 2026-10-09 while verifying a fix to a neighbouring defect. Reproduced by me, not taken on
report.

```
$ python3 bin/lpt ticket WO26100812727
store: operational=FOUND (212ms) app=FOUND (1592ms) <-- claims both stores answered

$ python3 bin/lpt sql "select count(*) as n from orders where \"orderNumber\" = 'WO26100812727'" --store app
{"n": 0} <-- the app store holds nothing
```

**Why this is the worst class of defect in this system.** `transport.py` exists so that a reading
always names which store answered, and the shop's skill says the divergence *is* the finding. Here the
tool asserts that the frozen store answered when it holds zero rows — so **the divergence is hidden**,
in exactly the direction that produced the reported crisis that never existed. A reading that cannot
be wrong is worth less than no reading at all.

**Mechanism, per the subagent's measurement (to be confirmed in the fix):** `case_sql` always returns
a non-empty `json_build_object` — its order key falls back to `{}` — so `_primary_case` and
`_store_line` treat an empty case as an answer, and the "this work order does not exist in that store"
line is nearly unreachable.

**Definition of done.** An order that exists in one store and not the other must print
`app=NOT FOUND` (or equivalent) naming the store that genuinely answered, and a test must prove it
against a case known to exist in `operational` only. `WO26100812727` is that case: 1 row in
`operational`, 0 in `app`.

**Until fixed:** never quote the `app=` half of an `lpt ticket` header as evidence. Read the store you
care about directly through `lpt_ops.transport`, or cross-check with `lpt sql --store <name>`.
