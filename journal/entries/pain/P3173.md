## P3173 — Two lpt-hub clones disagree about what the repo contains and neither says which one answered

Measured 2026-10-13, while correcting the Ullman case file. Two clones of lpt-hub disagree about what the repo contains, and neither one says which it is.

THE TWO CLONES.
- `secratary:/home/zabz/repos/lpt-hub` - remote origin = `https://github.com/lakewoodphone/lpt-hub.git`. main = `013569aad` at 2026-10-13 17:37:15 UTC, FETCH_HEAD 17:37:40. This is the clone the day's case work was AUTHORED in: its reflog shows `main@{1}: commit: Ullman Lenovo IdeaPad 3 ...` and then `main@{0}: pull --rebase -q origin main`. github main is now `d36c6acda` (2026-10-13 18:19), so this clone is behind by whatever landed since 17:37.
- `secratary-cloud:/home/zabz/phone/lpt-hub` - remote origin = `secratary-ts:/home/zabz/repos/lpt-hub`, i.e. the clone above, NOT github. HEAD = origin/main = `e2d705efd`, which is the commit BEFORE the Ullman work. `git reflog show main` has exactly one entry: `clone: from secratary-ts:/home/zabz/repos/lpt-hub`. There is no `.git/FETCH_HEAD`. `git cat-file -t 013569aad` fails - the commit is not in that clone at all - and `git ls-tree -r HEAD -- <the Ullman case file>` returns nothing.

THE PART THAT MAKES IT DANGEROUS. The six Ullman files ARE present on that clone's disk and in its index: `git diff --cached --name-only` lists all six (the case file, the sync record, the three case-media jpgs, the diagnostic log). They were put there by hand, never committed, and never fetched. So:
- a reading that comes from the working tree (most case tooling, `lptcase index`) sees the Ullman case;
- a reading that comes from HEAD, history or a diff against it does not.
Two answers, one machine, no note saying which one answered.

WHY IT MATTERS. The estate's verifiers are documented to run against the hub clone on the authority: `tools/customer/audit.py`, `scripts/sync-health-audit.py`, `tools/case-index/lptcase.py`. Pointed at this clone, a history-based check reports the day's case work as missing and a reverse-gap/divergence count becomes an artefact of the clone rather than a fact about the shop. That is the same shape as the two-production-databases defect and the stale `authority.db` copy: several things claim to be the same thing and none declares which is true.

NOT DONE, DELIBERATELY. Nothing was fetched, pulled or committed on either clone by this session. `secratary` is the FROZEN ROLLBACK ANCHOR (`settings/machines/host-posture.tsv`), and no service state, no cron and no repo state there was touched - reading only.

WHAT WOULD FIX IT. Make one clone authoritative per reader and publish which: either the cloud clone fetches from github on a schedule and reports its clone's HEAD and age in every verifier's output, or the verifiers are pointed at the secratary clone explicitly and the cloud clone is deleted rather than hand-patched. The hand-staged index is the thing to remove first - a case that exists only in someone's index is worse than a case that is missing, because it looks present to exactly one class of reader.
