## P3005 — The authority's SSH access is a single 105-byte file on the box with no second key and no guard, and it was replaced mid-deploy on 2026-10-11

MEASURED 2026-10-11: the company authority (secratary-cloud, root@178.156.194.1) accepts exactly ONE public key -- /root/.ssh/authorized_keys, 105 bytes, mode 600, mtime 2026-10-09 18:23 -- and something replaced it between 06:39Z and 06:40Z. Every workstream on ZABZ-YOGA lost its interactive access inside the same 7-minute window (06:34-06:41Z), while the company itself kept serving both public doors HTTP 200. The box's own doc (135-PARITY-AND-ROBUSTNESS.md 4.7) predicted loss of the LAPTOP; it did not predict the key being replaced ON THE BOX, which is worse because no local backup of a laptop key helps. Nothing in the estate can recover this from outside: the only paths are the Hetzner console (owner) or a session that still holds an open channel. WHAT WOULD FIX IT: (1) a second authorized key on the authority held on a different machine; (2) authorized_keys in cron-target-guard's critical.txt as a mode/owner/size/fingerprint check -- the single point of entry had no guard while ~90 cron jobs did; (3) a deployment rule that any write under /root/.ssh/ is announced and serialised (nine sessions were writing /usr/local/bin between 06:34 and 06:39Z). COST: four workstreams' deliverables are written but not copied to /root/out/migration-review/, and no ported job has a ledger row.
