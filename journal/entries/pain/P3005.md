## P3005 — The owner's notification gate was silently swallowing deadlines and DOWN alerts

2026-10-13. Found while clearing queue row #211, which was itself stale. The finding is bigger than
the row.

THE CHAIN. `owner_notifications.sms_may_reach_owner` compares a message urgency against
`owner_sms_min_urgency`, set to `urgent` on 2026-05-04 to cut noise. The urgency of an outbound
owner message is inferred by `tool_factory._infer_owner_update_urgency`, which matched only
`urgent`, `stuck` and `returned_payment` before defaulting to `normal`. So anything that did not
happen to contain one of those words was held.

WHAT WAS ACTUALLY HELD, read out of `owner_message_queue` where status='held':
 #2578 reason reminder:588 "Global Direct Parts dispute deadline is 2026-10-16. Owner approval
 required before then or the dispute window closes with NO SECOND WARNING."
 #2579 reason reminder:611 "T-3 reminder: Global Direct Parts dispute deadline - order #161898"
 #2574 Healthchecks.io "DOWN | secratary authority alive"
 #2572 "The company API is up but degraded: /health says DEGRADED, 3 checks in a row"
 #2568 Gov2Go "NJ Sales and Use Tax: ST-50/450 Notification"
 #2571 Telnyx "Low Balance Alert"
 #2583 T-Mobile "Restore full T-Mobile service"
Seven rows. A dispute deadline three days out that explicitly says there is no second warning, an
authority-DOWN alert, a degraded health alert, and a state tax notification - all classified
`normal` and held. The 300DDR reminder in row #211 that started this had reached **840 send
attempts** and expired.

FIXED THE CLASSIFIER, NOT THE GATE. Lowering `owner_sms_min_urgency` would have let the machine
heartbeats through as well, and those are what the gate was built to stop. Added two rules to the
inference instead: a message naming a deadline / due / expires / last day is urgent, and a reason
beginning `reminder` is urgent because the owner created it. Tested against real bodies:
 reminder:588 dispute deadline 2026-10-16 -> urgent
 reminder:611 T-3 reminder deadline -> urgent
 urgent_email Healthchecks DOWN -> urgent
 proactive_update Mesh node zabz-tech cannot take work -> normal (correctly still quiet)
The last line matters: the noise the guard exists for is still suppressed. Deployed and restarted
company-api, health-gated (healthy on attempt 4); the live settings object returns urgent for the
dispute reminder.

NOT DONE, deliberately: the seven held rows were NOT re-queued. Releasing them sends messages to
his phone, and sending is his to authorise per message. They are recorded here and the dispute
deadline is surfaced to him directly instead.

LESSON. A noise filter is a claim about what matters, and it decays silently: this one had been
holding real deadlines for weeks and every symptom of it was invisible because the whole point of
the gate is to make things invisible. The gate was measured; the classifier feeding it was not.
When a filter is suppressing something, measure WHAT it suppressed, not just the volume.
