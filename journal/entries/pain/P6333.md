## P6333 — POST /api/v1/actions/execute hangs for EVERY action (bogus names too) - ps_action is dead while /health and /tools/run/search answer normally

## Symptom

`ps_action(...)` returns the harness-level `Error: Request timed out` (the MCP row's
`toolCallTimeoutMs: 120000`). Reproduced twice in a row on 2026-10-14 ~12:03Z and ~12:07Z with
`action_name="search"`, params `{"what":"journal","query":"waze boxes"}` -- a read-only call.

## Isolation, measured

`ps_action` POSTs to `/api/v1/actions/execute` (`ps_mcp_server.py:789`). Called directly on the
authority with the real key read from `/opt/company/.env` (`DASHBOARD_API_KEY`; the value was never
printed):

 browser_session_list http=000 t=25.002827s
 zzz_bogus_action http=000 t=25.002304s
 search http=000 t=25.002080s
 search (-m 165) http=000 total=165.002244s

`http=000` = no response at all, and **uvicorn logs nothing** for these requests (it logs when the
response is sent). The API journal since 12:00 holds only two deliberately-unauthenticated probes
(`401 Unauthorized` returned in 2.5 ms) and one `/tools/run/search` `200 OK` in 442 ms.

CONCLUSION: it is not action-specific -- a **bogus** action name hangs identically, so the block is
before action lookup, in `execute_actions`' own entry path. The route is at `app/main.py:10612`
(sync `def`, so it runs in the AnyIO threadpool) and it delegates immediately:
`app/chat_actions.py:129 execute_actions(...) -> _runtime.execute_actions(...)`. The implementation
is therefore in the `_runtime` module (log lines name it `app.chat_action_runtime`), not in
`chat_actions.py`, which only forwards.

## Why this is worse than a timeout

The route is **synchronous**, so every hung request permanently occupies one AnyIO threadpool
worker (default 40). Hung calls accumulate until the API is unresponsive to everything.
`ps -o nlwp= -p 815621` -> **35 threads** (a uvicorn baseline is a handful), 14.7% CPU, State S.

Meanwhile the rest of the API is healthy: `/health` 200, `/tools/run/search` 200 in 442 ms
(journal index 4037 entries), and the DB-direct tools (`ps_db_query`) answer. So "the API is up" is
true and useless: what is dead is the **acting** surface -- send_sms, save_memory, create_task and
every other action, from every session and from the company's own agents.

## Condition it is running in

`_db_lock contended for key sqlite:////root/authority.db ... waiting...` appears **30 times in the
12 minutes** since the 11:58:34 restart. This is the same condition that made the 11:55:34 shutdown
need the whole `TimeoutStopUSec=3min` before SIGKILL (see the matching entry for the restart window).
The new process is 12 minutes old and already in this state, so the wedge is not inherited from the
old one -- it re-forms within minutes of boot.

## NEXT STEP, and what NOT to do

DO NOT restart `company-api` to "clear" it before a thread dump is taken: the restart destroys the
only evidence of which thread holds the block, and it will re-wedge within minutes anyway.

NEXT: `py-spy` is **not installed** on the authority (`command -v py-spy` -> nothing). Install it and
dump all thread stacks of the API pid, then read `app/chat_action_runtime.py`'s `execute_actions`
entry path and `app/database.py`'s `_db_lock` acquisition -- the aim is to name the holder of the
long-held lock and bound it. A hung action must not be able to hold a worker forever.
