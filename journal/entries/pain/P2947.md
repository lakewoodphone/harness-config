## P2947 — company-api has no memory ceiling on a box smaller than its own working set

WHAT HURTS (ranked 2)
company-api has no cgroup ceiling on a box one gigabyte larger than its own working set.
- Measured 2026-10-11: MemoryMax=infinity, MemoryHigh=infinity, MemorySwapMax=infinity; MemoryPeak
 7,165,288,448 B (6.67 GiB) reached by the incarnation started 05:47:35Z; ordinary autopilot tick peaks
 at 4,775,997,440 B (06:35:00Z); the pre-cutover incarnation died at anon-rss 7,544,976 kB (7.19 GiB)
 on a 7,742 MB box in a global_oom kill whose caller was fbs/sshd.
- The kill was CONSTRAINT_NONE/global_oom, i.e. the kernel chose the victim; nothing stops it choosing
 sshd, cloudflared or the process holding the database next time.
- Nothing monitors it: the public /health said ok:false "db check timed out (lock contention)" at
 06:43:18Z while another workstream's backup ran, and the app's own autopilot is in-process, so an
 OOM-stop is a tick outage that only the off-box dead-man switch (135 sec 6.7: still unscheduled) could see.

WHAT WOULD FIX IT
- Staged drop-in /root/company-api-memory.staged.conf: MemoryHigh=5500M, MemoryMax=6800M,
 MemorySwapMax=3072M, keeping OOMPolicy=stop + Restart=always + RestartSec=10, plus
 StartLimitIntervalSec/StartLimitBurst so a crash loop stops instead of spinning. Needs exactly one
 company-api restart, which needs the owner's agreement because it takes the public API down.
- Real fix: the measured working set does not fit; go CCX23 (4 vCPU/16 GB). That is a money decision.
- Cheap lever: AUTOPILOT_MAX_AGENTS_PER_TICK=20 is the only bound on the in-process agent fan-out that
 produced the fatal anon.
