## P2852 — The teardown cannot remove the SSH key line it added, so our public key survives in the customer's administrators_authorized_keys

**P — The teardown cannot remove the SSH key line it added, so our public key survives in the customer's `administrators_authorized_keys` after the access window is "closed".**

Measured 2026-10-05 by reading the finished component rather than trusting its report.

**The gap.** `teardown/Install-Destructor.ps1` deletes the session **key file** named in
`keyPathsToRemove`. Its only mention of the other half is a *detail string* at line 346:

```
346: -Detail 'session key file + its authorized_keys marker line; a directory is removed only when empty'
```

A search of the whole 868-line file for `authorized` (case-insensitive) returns **that line and nothing
else**. There is no code that removes the line. Meanwhile `transport/T1-LanSsh.ps1:221` writes our
public half into `C:\ProgramData\ssh\administrators_authorized_keys` and line 554 records the
revocation as `'authorized_keys line whose comment is ' + $keyComment` — i.e. the line we add is
identifiable, and nothing removes it.

**Why it matters:** it breaks R3 (temporary) and R4 (not reversible against us) for the one tier that is
supposed to leave *no secret at all* on the target. If the account deletion were ever the only thing
standing between a customer and a live key line we still hold the private half of, the window is not
closed — it is merely quiet.

**The second hole, in my own interface.** The destructor reads `sshdServicePreExisting` by name
(line 316) and, when true, STOPS AND DISABLES sshd instead of deleting it (line 317). `New-AccessWindow`
did not produce that field at all, so "may this be deleted?" was answered by a missing value. Get that
wrong in the permissive direction and the teardown **deletes a customer's own SSH service**. Fixed
2026-10-05: the field now exists and **defaults to TRUE** — never delete something we did not create —
and the transport must set it to `$false` only after checking. `authorizedKeysPaths` and
`authorizedKeysComment` were added to the same state contract at the same time, plus 14 assertions in
`tests/Test-AccessKitLib.ps1` that fail if any field the destructor reads by name is ever renamed on one
side only (55/55 passing).

**The pattern worth keeping.** A component that *describes* an action in its output is not a component
that *performs* it. The plan line read plausibly, the detail string read plausibly, and 11 dry-run checks
passed — because every one of them tested enumeration and refusal, and none tested that the named action
had an implementation behind it. **Test that each planned action has a code path, not just that it is
planned.**

**Blocked by this:** acceptance test A4 (post-reboot absence). No access window may be opened on any
machine until A4 passes, so this is the top blocker rather than a live exposure.
