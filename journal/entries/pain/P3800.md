## P3800 — The Dialpad SMS harvest is losing its cursor to a lock, and a customer text we sent has no cache witness because of it

WHAT HURTS. On 2026-10-14 I sent a customer text and could not witness it. The send was real —
Dialpad returned message id `6229866132054016`, status `pending`, and **production's
`communications` table carries it**: `createdAt 2026-10-14T16:12:39.965`, `direction OUTBOUND`,
`twilioSid = 'dialpad:sms:6229866132054016'`. But `dialpad_sms_cache` **on the authority,
`/root/authority.db`**, has no row for it and no row with that body, re-read at 16:04, 16:12, 16:15
and 16:18Z. **A 170.60-style hole in the only witness this estate treats as proof of a send.**

MEASURED CAUSE, from `/home/zabz/.sms-inbox/dialpad-sms-harvest.log` on secratary-cloud:

```
[2026-10-14T16:13:27Z] ok Failed to save backfill cursor: database is locked
                       {"read": 2, "stored": 2, "skipped": 0, "errors": 0}
[2026-10-14T16:14:27Z] ok Failed to save backfill cursor: database is locked
                       {"read": 2, "stored": 2, "skipped": 0, "errors": 0}
[2026-10-14T16:15:02Z] SKIPPED: previous sms harvest still running
[2026-10-14T16:15:27Z] ok Failed to save backfill cursor: database is locked
                       {"read": 2, "stored": 2, "skipped": 0, "errors": 0}
[2026-10-14T16:16:27Z] ok Failed to save backfill cursor: database is locked
                       {"read": 2, "stored": 2, "skipped": 0, "errors": 0}
```

The cursor row is **stuck**: `backfill_cursor('sms_backfill', '2026-10-14T15:43:15.837000', 5,
'2026-10-14T15:45:03Z')`. Every attempt re-reads and re-stores the same 2 rows, cannot advance the
marker, and the next tick finds the previous process still running and **SKIPS**.

The job is also running far more often than it is installed for: `dialpad-sms-harvest-cron` is
scheduled `15,45 * * * *`, yet its log shows runs at **16:13:27, 16:14:27, 16:15:27 and 16:16:27** —
four retries in four minutes against a 30-minute cadence. Whatever drives those retries is
contending with the shared SQLite writer it was deliberately off-phased from.

**WHERE IT HURTS NEXT.** The freshness monitor reads `MAX(fetched_at) FROM dialpad_sms_cache`, so
while the cursor is stuck that value is **the exact thing that cannot move** — the watchdog is
watching the broken instrument. This is P347's shape (a monitor reporting health while the data
under it has stopped) arriving on the customer-comms path.

**THE HONEST READING OF THE SESSION'S OWN EARLIER CLAIM.** At 15:43 I witnessed the first send and
reported "+2.7 s = a live capture, not a backfill". That was true and it was **luck**: the batch that
captured it landed at `fetched_at 15:45:03`, because the harvest tick runs at :15/:45. The real
capture cadence is **up to 30 minutes, in batches**, not seconds — so a fresh outbound can legitimately
have no cache row for half an hour, and the tool must say that rather than imply failure. The flow
document said "live, 2.1 s" and that is now corrected.

**WHAT IS STILL UNAMBIGUOUS:** the send went out. Production's webhook wrote it 6 s after the API
accepted it, with our message id on it. **Handset delivery remains unconfirmed** — no Dialpad API
exposes it. The witness failure is about *our* record, not about the customer.
