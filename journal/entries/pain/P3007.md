## P3007 — The authority lost SSH for every key we hold at ~06:40Z 2026-10-11, with no demonstrated way back in

## The authority (`secratary-cloud`) stopped accepting SSH from every key we hold, at ~06:40Z 2026-10-11

**What hurts.** At approximately 06:40Z on 2026-10-11 the new company authority stopped accepting SSH.
Every attempt returns `Permission denied (publickey)`, from every host and every key we have.

**Measured, so this is not a per-client problem:**

| attempt | from | key | result |
|---|---|---|---|
| 1-5 over 20 min | ZABZ-YOGA | `id_ed25519_hetzner` | `Permission denied (publickey)` |
| — | ZABZ-YOGA | `zabz-tech-ed25519` | `Permission denied (publickey)` |
| — | ZABZ-YOGA | `id_ed25519_lpt-apps` | `Permission denied (publickey)` |
| — | `secratary-ts` (office box) | its own `id_ed25519_hetzner` | `Permission denied (publickey)` |
| — | `lpt-apps-01` (vault) | `crosswatch_ed25519` | no hostname returned |

**It is the same machine, and it is alive.** The host key is unchanged — `ssh-keyscan -t ed25519
178.156.194.1` returns the exact entry already in `known_hosts` — and the office box's key has the
**same fingerprint as mine** (`SHA256:91iMQc2AFg+sSA1oscDHF9pz7jClBMynfHtRL4rmAKg mesh-hetzner-2026-08-31`),
so both are being refused by the box rather than one client holding a bad key. The public API answered
HTTP 200 throughout (`api.abletelsolutions.com/health` → `{"ok":true,...,"autopilot_enabled":true}`).

**Timeline clue.** `/root/.ssh/known_hosts` on the box was modified at 06:21Z (consistent with the
ported freshness monitor's `StrictHostKeyChecking=accept-new` learning the vault `2.28.33.58`),
`/root/.ssh/authorized_keys` is dated 2026-10-09 18:23 (105 B), and `/root/.ssh/id_ed25519_hetzner`
is dated 06:19. The refusal began within ~20 minutes of a second agent session working the same box.

**Why it hurts more than a devops nuisance.** It removed the only route for finishing this workstream:
the `/root/out/migration-review/133-OFFSITE-BACKUP.md` delivery could not be made, the run's own
`/var/lib/authority-backup/last-run` could not be read, and `verify-offsite-object.sh` (written and
deployed before the lockout) was never executed. It also means the authority has no operator access we
can demonstrate right now — if the API broke, nobody could get in.

**What would fix it / what to check first.** Establish whether this was a deliberate key rotation that
forgot to install the new key everywhere, or an unintended lockout:

```
ls -l /root/.ssh/authorized_keys
tail -50 /var/log/auth.log # look for "Accepted publickey" vs only "Connection closed"
grep -c . /root/.ssh/authorized_keys
```

If the file was rewritten, the old key's line is gone and a replacement must be installed through
whatever out-of-band route exists (Hetzner console, or the account-level access used at provision time).
**Then deliver:** `scp -i ~/.ssh/id_ed25519_hetzner ~/code/harness-config/docs/mesh/133-OFFSITE-BACKUP.md
root@178.156.194.1:/root/out/migration-review/133-OFFSITE-BACKUP.md`.

**The deeper issue.** The new authority — the machine the entire company now runs on — has exactly one
operator access path (one SSH key, installed by one script) and, as of this writing, that path is
closed with no demonstrated way back in. `docs/mesh/130-LIVE-STATE-*` records that the old authority
handed over a credential and a working key; a second, independent access route (console credentials held
somewhere other than on the machines themselves) is the thing that would have made this a non-event.
