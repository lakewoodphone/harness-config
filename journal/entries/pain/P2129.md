## P2129 — P2138 - the autopilot has been WEDGED by one hang: 5 run_once timeouts and 0 completions in 6 hours

**This is the most consequential defect found in the whole audit, because it explains why the company
looked quiet instead of broken.**

Measured 2026-09-20 on the authority:

 last 6 hours: run_once timed out after 600s = 5 run_once completions = 0

Five ticks in six hours, and every one was killed at its 600 s ceiling. No run completed. The
observable symptoms I had been reading as "the company is quiet this evening" - 5 work sessions in an
hour, 4 tool calls in 12 minutes - were not an idle company. **They were a company whose main loop
never finishes.**

**THE MECHANISM, and it is a latch.** `AutopilotController.run_once` sets
`self._run_once_active = True` on entry as a re-entrancy guard, and clears it in exactly two places -
the success path and the `except` handler. **There is no `finally`.** The loop runs `run_once` on a
`ThreadPoolExecutor` and waits 600 s; on expiry it logs

 "run_once timed out after 600s â€” killing and applying backoff"

and calls `_run_executor.shutdown(wait=False)`. **`shutdown(wait=False)` does not kill a running
thread**, so the message is false - nothing is killed and the thread keeps executing. But a run that
hangs INSIDE a blocking call reaches neither the success return nor the `except`, so the flag is never
cleared. Every later attempt then hits

 if self._run_once_active: -> "run_once skipped â€” previous run still active"

and returns `already_running` without doing anything. **One hang wedges the autopilot for the lifetime
of the process**, and the only log line it produces is the one timeout, which reads like a transient
failure rather than a permanent one.

**A guard with no `finally` is a latch, and a latch turns a transient fault into a permanent state.**
The original intent was sound - prevent a second run overlapping an abandoned one - but the guard was
placed so that the exact case it was meant to survive is the case that sets it forever.

**THE FIX, in two places (both deployed, 17:30Z):**
1. `finally:` inside `run_once`, so every exit path releases the guard. Verified structurally: a
 `try/finally` that is a direct child of `run_once`, clearing the flag; clear-sites went 2 -> 3.
2. The loop clears the flag when it stops waiting, because it has genuinely stopped waiting even
 though the thread runs on.
3. The log now says **"ABANDONING it (the thread keeps running; it cannot be killed)"** instead of
 claiming a kill that never happened. A false statement in a log is how this stayed invisible.

**Verification is in progress and cannot be instant** - a run may take up to 600 s, so the proof is a
`run_once` that *completes*: `~/company-reports/autopilot-recovery-*.log`, sampling
`autopilot_state.json`'s `last_run_at` (17:12:17 at fix time) and the timeout counter every 60 s.

**Why this deserves to rank above everything else I did today.** I fixed a completion predicate, repo
paths, a rate limit, a temp-file leak and a finder of findings - all real - while the loop that runs
them was executing perhaps once every 72 minutes and completing nothing. **A defect that stops the
system from running at all makes every other defect's measurement meaningless**, and I only found it
by asking why the traffic was low instead of accepting "quiet evening" as an answer.
