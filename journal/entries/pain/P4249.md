# The owner text channel still has no composer, and the only session that wrote one had it overwritten by a concurrent session an hour later

**State on 2026-10-15, so no future session mistakes partial work for a fix.** The audit is
`harness-config/docs/owner-text/OWNER-TEXT-AUDIT-2026-10-15.md`; the handoff is `H4872`.

**What works.** The daily digest text is off (systemd drop-in, `ExecStart` is `build`), the truncation
marker is retired with the cut now recorded in `/root/.owner-text/fit.log`, a cut no longer ends on a
dangling list marker, CFO asks end in a question mark so the one-at-a-time rule engages, a refused ask
stops retrying for 6 hours, and a standing-rules file is read on every send.

**What is still broken, and this is the point of the entry.** Every door still composes its own body.
Nine senders can put text on his phone, only two `door` literals have ever reached the relay
(`app` 23 attempts, `textsend` 6), sixteen length constants guard one channel, and one body can be cut
three times in a row (900 -> 400 -> 320) by three different components. **Retiring the marker makes a
half-message quieter; it does not stop one being half.** There is still no single agent that takes an
intent and returns one message for him.

**And the one attempt to build it was lost.** I wrote and deployed a composer that sends ONE item —
no counts, no file path, no marker, a daily cap and a standing-rules gate — and proved it on the live
queue (`send --dry-run` -> `Apple's own Apple Business Manager Agreement forbids what we are already
selling — Keep selling, but get the exposure measured by a lawyer before the camera product is
built`, 173 chars). At **14:46:16Z another session wrote the same file wholesale**, restoring the
`'N items, M urgent` head, with no merge conflict anywhere because it wrote the working tree of a
dirty repo and not a branch. Its version is preserved at
`/root/text-fix-20261015/owner_attention.CONCURRENT-SESSION-14-46.py` and mine in
`/root/text-fix-20261015/backup/`.

Its fix was not wrong and mine was not either: it measured that the 320-char digest carried four
decisions and **zero email items**, and reserved a slot for his own mail. A one-item composer must not
lose his mail either. **The merge is the work, and it is not done.**

**Why this is a pain rather than a lesson.** A lesson is a rule I can apply; this is an obstacle that
is still standing. Two sessions editing one live script will lose work again, because `/root/bin` is
not a git repository at all and `/opt/company` is written in place. **Nothing in the estate currently
detects it.** `P13` records the same defect for the repo; this is its recurrence on a deployed file.

**What would fix it:** a write-claim beside any live artefact (`<file>.claim-<host>` checked before
an edit), and a rule that a change to `/opt/company/scripts` or `/root/bin` goes into the repo and
rides the deploy rather than being written in place.
