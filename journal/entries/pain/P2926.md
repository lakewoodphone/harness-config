### 1. The Plaid pull fails most days and nothing alerts — and the failure is unreadable

6 of the last 8 nightly runs failed. The last complete success was 2026-09-29 04:30Z; the newest
Plaid-attributable ledger row at 15:50Z was dated **2026-09-27**. The error a human reads,
`module 'plaid.api' has no attribute 'ApiException'`, is the *handler* crashing on the way to reporting the real
error: `plaid-python 42.0.0` no longer exposes `plaid.api.ApiException`, and six clauses in `plaid_service.py`
catch it. **No Plaid API error can currently be read from the logs**, so a broken credential and a broken import
are indistinguishable. Second cause: 13.2 GiB SQLite write contention at 04:30, where the ingest connection sets
no `busy_timeout` and the service sets 10 s. Third: the wrapper prints `=== Nightly Plaid sync complete ===`
13 seconds after the Plaid step died, because Stripe still ran, and cron appends to a log nothing reads.

**What would fix it:** the six except clauses, one `busy_timeout`, a non-zero exit when any step fails, and one
kernel check that fails when the pull is older than 36 hours. Hours of work, and it is Stage 0.

### 2. A correct accounting pipeline that nothing runs

`books/report/__init__.py:21-24` states it: `automate.py` and `deploy/` were never built, so "there is no
scheduled run". The pipeline ran **once**, 2026-09-20T15:38Z. `books.db` is 10 days stale; `periods`,
`reconciliations`, `documents` and `parties` are empty; all **248 audit findings are `open`** because the runner
hard-codes `status='open'` and nothing implements the act that closes one — so the FAIL/WARN counts are a
cumulative union of every audit ever run, not the current state.

**What would fix it:** `automate.py`, a systemd unit and timer, and a closing act. Stage 1 and Stage 2.

### 3. The `cfo` project is registered, idle, and will stay idle

`cfo todo=0 running=0 done=7`, state file `"work_remaining": false`. A project with an empty queue never gets a
shift filed, so "the CFO is constantly working" is false for exactly one reason: nobody queued the work. The
carrier around it is healthy and cheap — 0.037 USD per closed item, 0.60 of a 25.00 ceiling spent today.

**What would fix it:** the recurring units as ledger items plus the sensors that file them. Stage 4.

### 4. It cannot learn, so every unanswered merchant is a permanent tax on the owner

Verified by grepping all of `books/**`: the only `created_by='owner'` rules are two seeded from a 2025 rulebook,
and there is no path from an answer to a rule. The owner's question list is a Python `dict` printed to stdout and
never written to a table; the schema has no state meaning "waiting for the owner". **Answering about a merchant
changes nothing and the same merchant returns to the same pile.** This is the defect that makes the owner's
request — "ask me while I still remember it" — pointless even when the ask succeeds.

**What would fix it:** a durable clarification record plus a writer that produces `created_by='owner'` rules,
which `engine.py` already gives the highest precedence. Stage 3.

### 5. The channel that would ask him is throttled to near-silence and cannot match an answer to a question

The kernel's own reading today: `owner_send_refusal_note: "held: urgency 'normal' is below the send threshold
'urgent'"`. Caps: `--max-sends 2` per 5-minute tick on the AI line, 2 owner SMS per UTC day on the app path, one
question per engagement by design. And no correlation exists — a ≤40-word reply closes **the oldest open promise**
for that number, so two outstanding questions mean the second answer lands on the first question. Of 13 pending
owner-queue rows, 3 were engineering faults routed to him anyway.

**What would fix it:** a reference on every question and matching before fallback, a money tier allowed at
`normal` urgency, and a numeric cap that is a number rather than a feeling. Stage 3 — and the cap needs the
owner's standing permission first, because it changes his own outbound hard stop.

### 6. Smaller, all cheap, one of them live

`"4258"` is defined twice in `PLAID_MASK_MAP`, killing the Amazon/Visa disambiguation. `_is_pending_twin` ignores
the incoming transaction entirely, so a same-day same-amount pair can overwrite the wrong row. Pending rows are
skipped with no tombstone (29 pending in the app DB). 90 Plaid transactions have no Plaid-attributable ledger
row, 61 of them unexplained. 19 of 36 accounting accounts have no Plaid provenance. `books.db` counts 212
NULL-category rows as classified in one section of its own report and not in another. The deployed kernel has an
`owner_queue` check its repo does not contain. ~150 KB of real analysis code in `scripts/finance/` is invoked by
nothing.
