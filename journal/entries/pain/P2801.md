## P2801 — Five cron jobs on the authority called programs that did not exist, and the failure looked like silence

Five crontab entries on the authority called programs that did not exist, and cron made the failure look like silence.

MEASURED 2026-09-30 15:23-15:35Z on `secratary`, by the first run of `~/bin/cron-target-guard.py` and
by the logs of the jobs themselves.

THE FIVE DEAD JOBS

 */30 scripts/dialpad-harvest-cron.sh the Dialpad CALL harvest
 15,45 scripts/dialpad-sms-harvest-cron.sh the Dialpad SMS harvest
 */5 scripts/dialpad-recording-gap.py voicemail recording backfill
 */10 scripts/dialpad-transcript-gap.py call transcript backfill
 */15 scripts/ha/check-security-absence.py the Home Assistant security-absence alarm

HOW THEY DIED, WITH EVIDENCE

The scripts were real and were running. `~/dialpad-harvest.log` records a healthy pass at
`2026-09-29T11:30:40Z`; the three trees preserved on 2026-09-28 (`~/_verify_co_20260928`,
`~/_verify_base`, `~/_verify2`) carry byte-identical copies of all five (`sha256sum` on the two
shell scripts is identical across all three: `cae43fd7…` and `a27c0a1d…`).

They lived only in the working tree. When the deployed checkout at
`/home/zabz/personal-secretary-mvp` was switched to `hk/20260929-w10-seed-bc28-date`, that tree
lost them — `git cat-file -e HEAD:scripts/dialpad-recording-gap.py` fails on that branch while
`origin/master` still carries the blob — and the crontab, which is not in git and was never
touched, kept calling them.

CONSEQUENCE, MEASURED

- `dialpad_call_full.fetched_at` had not advanced past `2026-09-29T11:30` for ~28 hours. The shop's
 calls were not being fetched. The first restored run stored **61 calls** in 42 s.
- The company's own check had gone red on exactly this: `comms_freshness` in `ck status` read
 "call harvest has not completed in 27.9h … Dialpad SMS harvest has not completed in 28.2h".
 That check reads the CONSEQUENCE, 28 hours late. Nothing read the schedule.
- The security-absence alarm — the one that would notice Home Assistant has no security system —
 had never run at all: `scripts/ha/` did not even exist.

WHY NOTHING SAW IT

cron writes one line per run into a per-job log. `~/dialpad-sms-harvest.log` had accumulated
twenty-five consecutive `/bin/sh: 1: …: not found` lines and nothing reads that file. The host has
no `mail` binary (`command -v mail` finds nothing — the same defect journal P167 recorded for the
database-corruption alarm). So a missing target produced an absence, and an absence has no
symptom until somebody needs the thing that stopped.

THE SAME GUARD'S SECOND FIND, WHICH IS THE SAME DEFECT WITH A DIFFERENT SHAPE

Two more cron targets existed but had lost their execute bit, so they too had never run:

 scripts/secretary-startup.sh last ran 2026-07-10; mode lost 2026-08-04
 scripts/site-uptime-check-cron.sh last ran 2026-09-06; mode lost 2026-09-06

The site uptime check — the only thing watching whether the shop's website is up — had been dead
for 24 days. A deploy replaced both files without their mode.

FIXED 2026-09-30, end to end, with the proof for each step

1. Restored all five files from `~/_verify2` (the newest surviving copy), `cp -p`, sha256 verified
 against the source — every one OK. Committed as `3796f668` on the deployed branch.
2. `chmod +x` on the two mode-less targets; committed as `c12d0a8e`.
3. Ran each restored job once and recorded its output:
 `[2026-09-30T15:31:39Z] ok {"read": 0, "stored": 0, "skipped": 0, "errors": 0}` (SMS) and
 `[2026-09-30T15:33:54Z] ok {"calls": {… "read": 61, "stored": 61, "errors": 0}}` (calls, after
 one retry on `database is locked`), and
 `RESULT: all endpoints up at 2026-09-30T15:34:49Z` (site uptime).
4. Installed the class-killer: `~/bin/cron-target-guard.py`, which parses every crontab job,
 resolves paths through `cd … &&`, `flock`/`timeout`/`nohup`, `~` and `$HOME`, strips output
 redirections so a log path is never mistaken for a program, and reports MISSING / UNREADABLE /
 NO EXEC BIT. Wired to cron hourly (`7 * * * *`) and to `sources/cron-targets.py`, so a failure
 becomes a ledger item rather than a log line.
5. FALSIFIED, both ways: clean run `ok: true, checked 56, missing 0, rc=0`; with one deliberately
 missing target injected into the crontab, `ok: false, rc=1` and the source printed
 `flagged cron-targets:1dd597dc4e`; with the crontab restored, `rc=0` and `quiet` again.
 `--selftest` asserts three known-missing paths are found and the present interpreter is not.

WHAT IS STILL OPEN, HONESTLY

The general form of this defect is not gone. The schedule is data outside version control, the
programs are code inside it, and only the PATH is now checked. A job that exists and fails every
run, a job whose arguments name a missing file, and a job that was deleted deliberately but left
in the crontab are all still invisible. The guard found the class that cost 28 hours; it is not yet
a general proof that every scheduled job works.
