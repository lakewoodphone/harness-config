## P212 — Journal ids collide by construction: max(seen)+1 means two machines writing concurrently pick the same number (measured 10/10)

## P — Journal ids collide by construction: id = max(seen) + 1, so two machines writing at the same time pick the same number

**Measured 2026-09-16, one session, ten for ten.** A session on `secratary` appended ten entries — `D163`, `D164`, `H259`,
`H260`, `L1548`, `L1549`, `L1550`, `L1551`, `P160`, `W135` — and **every one of them collided with a different entry written
by another machine in the same window**: upstream `D163` is Device Parts / DHL duty, `D164` is the AWS key deletion, `H259`/`H260`
are the `kf/append-only-review-decisions` and PART-122 handoffs, `L1548`–`L1551` are four unrelated lessons, `P160` is
plaintext credentials across the fleet, `W135` is D39-11 telemetry. The rebase onto `origin/master` surfaced all ten as
add/add conflicts plus one conflict in `journal/state/in-flight.md`.

**Why it is structural, not bad luck.** `cmd_next_id` computes `max(entries/ + index + log/** + flats, allocation ceiling,
origin)` and returns `best + 1` (`tools/journal.py:2810-2885`). Consulting origin raises the floor, but **two machines that
each compute "max + 1" while the other's commit is still in flight both get the same number** — a distributed counter race
with no reservation step. My local index said 911 entries when it allocated; the tree now holds **1,368**, i.e. the other
machines added ~450 entries while this session was running. Nothing the allocator could have fetched would have prevented a
write that landed after the fetch.

**What the collision costs.** An id is the only name an entry has across the fleet (`journal.py show P160` must mean one
thing forever). After this collision, `P160` meant *credentials* on ZABZ-TECH and *the API OOM* here; any cross-machine
reference written in between silently points at the wrong entry. That is the worst class of failure this journal was built to
prevent.

**How it was repaired (and the rule that decides which side moves).** The already-pushed side stays: all ten of mine were
re-appended with freshly allocated ids (`P211`, `W181`, `D210`, `D211`, `L1732`–`L1735`, `H389`, `H390`) and every reference
was rewritten in the entries, in `state/in-flight.md` and in the incident README. `journal.py repair-ids --apply` exists for
this, but it renumbers its own choice of side; when one side is already pushed and referenced fleet-wide, **the side that has
not been pushed moves** — so this was done by hand with the mapping recorded here. `check --fix` then re-recorded the five
sahas invalidated by the edits; `check` is back to **0 errors**.

**What would fix it.** Any one of: (a) a per-host id suffix (`D164-s2`), which makes collisions impossible and reads
naturally; (b) a single allocator — the authority already owns the company database, so `journal.py next-id` could reserve
from it atomically and the fleet would be correct by construction; (c) reserve disjoint id blocks per machine (cheap, ugly,
and bisectable by accident is fine); or (d) keep max+1 but have `append` push immediately and bump-and-retry on rejection,
which turns a silent collision into a visible retry. (d) is the smallest change that actually closes the race, since it makes
the git ref the lock.
