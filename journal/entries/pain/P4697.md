## P4697 — The authority journal has not been published off-machine since 2026-10-13T15:00:05Z: every vault push is rejected non-fast-forward

The authority's journal has not left the machine since 2026-10-13T15:00:05Z, and the job that does it
reports the failure every 15 minutes into a log nobody reads.

WHAT IT IS. `journal-commit.sh` (cron `*/15 * * * *`) commits the canonical journal checkout
`/root/code/harness-config` and publishes it to the `vault` remote
(`root@2.28.33.58:/srv/git/harness-config.git`). Every tick since 2026-10-13 15:00Z the push is
refused:

 ! [rejected] HEAD -> main (non-fast-forward)
 hint: Updates were rejected because a pushed branch tip is behind its remote counterpart.

MEASURED 2026-10-16 01:1xZ, read from `/root/.harness-config-autosync/journal-commit.log`:
 * 334 `[failed]` lines; the first vault failure is at line 209, `2026-10-13T15:00:05Z`.
 * the cron history agrees: `journal-commit` has 158 non-zero rows against 294 zero rows in
 `/root/.cron-status/runs.tsv`, and the last four rows are all `rc=1`.
 * `git ls-remote vault refs/heads/main` = `1214720467270b0deed5be4444280aafade561fe`
 (2026-10-14 18:50:46 +0000, subject "dictation: resolved - Whisper Small (English) is ~3s on his
 iPhone against ~15s for the 1.6 GB model"); the checkout's HEAD was `4704c817`.
 * `git merge-base HEAD 1214720` = `83bc260ba5511d6f29ba20bc1d9cf1a5e6a008b7`, so the two lineages
 are related and genuinely diverged, not unrelated histories.

THE MECHANISM, AND THE PART OF IT THAT IS NOT VERIFIED. The published tip is a WORK commit
("dictation: …"), not one of the job's own `journal: autocommit N path(s) …` commits. That is
consistent with a publisher that pushes `HEAD:$BRANCH` — with `BRANCH` fixed to `main` while `HEAD`
is whatever branch the checkout happens to have checked out. Under that design any later checkout
that is not a descendant of the last published tip makes every subsequent push non-fast-forward,
permanently, on the machine that is supposed to be the source of truth. **NOT VERIFIED: which branch
was checked out on 2026-10-14 18:50, and therefore whether this is the whole cause.** What is
verified is that the checkout's branch is `i359-contentless-waiting` today and that vault's `main`
is not its ancestor.

ALREADY DETECTED, ALREADY GIVEN UP ON. `/root/bin/sources/cron-failures.py` reads exactly this
signal and reports `cron-failing:journal-commit: suppressed:attempts`. So this is not an unseen
failure — it was flagged, sessions attempted it, and the wake loop is now suppressing it. Nothing has
been published in the meantime.

THE EXPOSURE. `origin` for this checkout is `/root/hc-main.bundle`, a bundle on the SAME disk, so it
is not an off-machine copy. That leaves the vault and the GitHub mirror (`journalpub`) as the only
copies that leave the building.

WHAT I DID, 2026-10-16 01:1xZ — PRESERVE, NEVER FORCE. The sanctioned action for this estate
(`scripts/autosync.sh` does the same thing) is a new, additive ref:

 git -C /root/code/harness-config push vault HEAD:refs/heads/authority-preserve-20261016
 * [new branch] HEAD -> authority-preserve-20261016
 git ls-remote vault refs/heads/authority-preserve-20261016
 -> 4704c8172701cbb681d42a825eea81ea4d3ec184 (matches HEAD)

No force, nothing merged, nothing rebased, `vault/main` untouched. The bytes are now off the machine.

WHAT REMAINS, AND WHY IT IS A DECISION AND NOT A SCRIPT. Reconciling the two lineages determines
what "the canonical journal" means on the remote — and the publisher's `HEAD:$BRANCH` behaviour has
to be settled too, or the next branch checkout will re-break it the same way. Three options, none
free: merge vault's `main` into the checkout's lineage; repoint the publisher at a journal-only ref
such as `refs/heads/journal` with no working-branch coupling; or accept the divergence and keep
publishing to a dated preserve ref.

CHECK (this returns 0 only when the canonical journal is published again):

 && echo PUBLISHED || echo NOT-PUBLISHED
