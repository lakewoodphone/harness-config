## P3205 — A brief I write with a wrong unit multiplies through a whole research stream

**A single wrong unit in a research brief contaminated an entire stream's arithmetic, 100x.**

The camera-research brief I wrote said the existing Telnyx data overage is "1.80 USD per MB". The shop's own
pricing authority says **18.00 per GB** — 1.8 **cents** per MB. The stream believed the brief, computed
"one 1 GB video = 1,800", and built a whole data-cost argument on it. The conclusion (photo upload must be
Wi-Fi-only) survived, but the magnitude was wrong by two orders and would have been published.

**What hurts:** a brief is the only thing a delegated agent knows, so an error in it is not corrected by
anyone downstream — it is *laundered* into a confident finding with sources attached. The agent could not
detect it, because it had no access to the number's origin and no reason to doubt the person who hired it.

**What would fix it:**
1. **Give a number a source path, not just a value.** "Overage is 18.00/GB per `PRICING-AUTHORITY-2026-10-12.md`
 section 1" invites the agent to read the file; "1.80 per MB" invites arithmetic on a rumour.
2. **State both units and check the cross-multiplication in the brief itself** — 1.8 cents/MB and 18.00/GB
 agree; 1.80/MB and 18.00/GB do not, and one line of arithmetic in the brief would have caught it.
3. **Manager-side rule that already exists and I did not apply hard enough: reproduce every load-bearing
 number yourself before publishing it.** I caught this one on review, which is the system working — but
 only because the file was being rewritten by hand. In a fleet where agents write the files directly, this
 error ships.

Measured once, 2026-10-14, on the Kamera research. Related: **P1** (the owner's attention spent on things
that are not his) is the same failure in a different direction — work arriving at a human without having
been checked.
