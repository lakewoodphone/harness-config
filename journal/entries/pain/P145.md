## P145 — An outcome settled on the telephone never reaches the case file, so the file looks like it is waiting on the owner

An outcome settled on the telephone never reaches the case file, so the file looks like it
is waiting on the owner when it is actually waiting on us.

MEASURED, 2026-09-15. Weissman SSD case: the file's last dated section was 2026-09-03 and
its NEXT line read "confirm which quoted price applies, then submit the Drop-Off or
Mail-In form". Both facts had been overtaken 11 days earlier by one phone call in which
Eliyahu quoted the customer and the customer accepted. Twelve days of a live, approved,
money-bearing case sat invisible because nobody hand-writes the phone call into a repo.
The gap was only found by querying dialpad_call_full for the customer's number.

WHY IT KEEPS HAPPENING. The owner works by voice and is terse. Every recovery case's
decisive step (quote delivered, approval given, customer changes their mind, customer
says "I'll bring it Monday") happens on a call, and the call transcript lands in the
secretary DB automatically while the case file only changes if a human or agent writes
to it. Case files are written eagerly at intake and thin out exactly where the case
gets decided.

WHAT WOULD FIX IT. A daily reconciliation: for every case whose front-matter is not
closed, look up calls/SMS for the customer's number(s) since the file's `updated` date,
and if there is a communication newer than the last dated section, surface it for the
case file. `lptcase.py stale` already computes the staleness; nothing joins it to the
comms store. This is a build, not a doc. Interim discipline (already recorded as a
lesson): check the call log before answering any live case question.

COST SO FAR. One case, 12 days, a customer told "two weeks" who has heard nothing since.
