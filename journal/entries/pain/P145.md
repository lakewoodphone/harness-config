## P145 — The production clone is a divergent lineage: master 61 ahead and 138 behind origin, so a fix exists on one disk only

**P-new — the production clone is a divergent lineage, so a fix can exist on exactly one machine.**

Measured 2026-09-15 on the authority: `~/personal-secretary-mvp` is on `master` **61 commits ahead
and 138 behind** `origin/master` (github.com/lakewoodphone/personal-secretary-mvp). Both of this
session's fixes (`a6b08392`, `85e97f17`) and the nine before them, back through the owner-SMS
kill-switch work, existed **only on the authority** -- a `git checkout`, a disk failure, or a fresh
clone would have lost them, and a fresh clone would have run 138 commits of other people's work as
if it were the same system. The laptop's clone of the same repo carries its own, differently
hashed commits with the same messages (`de925d742 owner digest: WHO IS WAITING ON A REPLY` here vs
`5a6c3b66` there), which is the signature of the same change being committed twice on two machines
rather than shared.

Mitigation applied now, not a fix: the 61 commits were pushed to a preservation branch,
`secratary-master-preserved-20260915` (verified by `git merge-base --is-ancestor` for both of my
commits; `master` untouched, no force, nothing rewritten). What is still needed is a decision about
**which lineage is the system**, taken once, deliberately: the authority is what actually runs and
the laptop is what tracks GitHub, and merging 138 remote commits into a production tree -- or
declaring the authority's history canonical and opening one PR -- is exactly the kind of call that
must not be made casually from inside a patch session. Until then, **every fix made on the
authority must be pushed to a named branch in the same turn it is committed**, or it does not
exist anywhere but one disk.
