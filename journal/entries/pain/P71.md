## P71 — The journal is mid-merge with 213 duplicate-id errors, so its integrity check no longer alarms on anything new

**Evidence, read 2026-09-14 ~15:45 UTC on ZABZ-YOGA:**
- `.git/MERGE_HEAD` exists — a merge is in progress and was left unfinished.
- `git diff --name-only --diff-filter=U` → `journal/log/wins/2026-09.md`, `journal/state/open-pain.md`.
 Each carries exactly 3 conflict-marker lines.
- `journal/log/lessons/2026-09.md` (213 KB, mtime 11:46:57) and `journal/log/lessons/2026-09.1.md`
 (200 KB, mtime 11:44:04) both contain ids L1-L46 with **byte-identical bodies** — the overlap the rebuild
 was supposed to end.
- `python journal/tools/journal.py check` → **213 errors, 218 warnings**. The `wins/2026-09.md` conflict is a
 *numbering collision*: HEAD has `W41`, the incoming side also has `W41`. The `open-pain.md` conflict has the
 same shape (`P66` on both sides, plus distinct P67/P68/P69 entries in each branch).
- **This state is new within the hour.** An earlier `journal.py status` this same session read
 "CHECK: 0 error(s), 14 warning(s)". So it was created by a concurrent write or merge during this session,
 not by anything this session did.

**What would fix it.** (1) Finish the merge on a machine that can see both branches, resolving the two files
by **renumbering rather than dropping** — every colliding entry's content exists on both sides and must survive
with a distinct id, which is the append-only rule. (2) Decide the relationship between `log/lessons/2026-09.md`
and `log/lessons/2026-09.1.md`: they are not a shard-and-continuation pair, they are two copies of the same
range, and one must be retired explicitly with a note rather than deleted. (3) Only then re-run `check`; a
green check that was achieved by deleting a side is worse than a red one.

**Why I did not just fix it.** The journal holds the four flat files as frozen inputs and has documented,
twice, that unguarded merges caused exactly these collision suffixes (P46/P46b/P46c, D41/D41b). Resolving a
213-error duplicate-id state by hand, in a repo another session was actively writing to minutes earlier, is a
change that cannot be undone once a wrong "latest" wins. Naming it is the honest move; guessing is not.

**Consequence to be blunt about:** `check` exiting non-zero is the mechanism that stops continuity rot, and it
is currently saturated. Until it is green, a genuinely new duplicate id introduced tomorrow will be
indistinguishable from the 213 already there — the alarm has been left ringing, which is the same failure class
as the sensors that reached nobody (P55).
