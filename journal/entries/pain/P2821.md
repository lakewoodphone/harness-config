## P2821 — secretary-backup runs 35-45 min every 6 hours at 94-98% iowait on 4 cores, during which the company API answers nothing; only backup that exists, and it is on the same disk as the database

## 2026-09-30 · The authority's four-times-a-day outage, and three mistakes I made finding it

**The finding, measured.** `secratary` (Dell OptiPlex 9020, 4 cores, one LUKS-encrypted PNY 500 GB
consumer SSD) runs `secretary-backup.service` every six hours. Observed 2026-09-30: the 18:00 job was
still running at 18:30, `%Cpu(s) 94.3 wa`, `/proc/pressure/io` `some avg10=98.70` and
**`avg300=88.78` — sustained I/O starvation for five minutes at a time**, load 19-24 on four cores.
During it `secretary-api.service` reports **active** and accepts TCP, but `/health` does not answer in
12-20 s even on loopback. The previous cycles' artefact timestamps (12:00 → 12:35, 06:00 → 06:45) put
the window at **35-45 minutes, four times a day**. The service's own watchdog agrees and says so in
its log: *"degraded #1: active but /health says DOWN"*, *"degraded #2: active but /health says
DEGRADED"*. The API's own log shows the mechanism — `_db_lock contended for key
sqlite:///data/secretary.db, waiting` — a 14.8 GB SQLite database on the same saturated device.

**So: the company API is effectively offline ~2.5 hours a day, and the thing taking it offline is its
own backup job.** It is not a code bug and it is not the watchdog (which reports and does not
restart — hypothesis raised and falsified in the same session).

**Mitigation applied** (does not disturb the running job; affects the next invocation):
`/etc/systemd/system/secretary-backup.service.d/10-yield-to-api.conf` on the authority with
`Nice=10`, `CPUSchedulingPolicy=batch`, `IOSchedulingClass=best-effort`, `IOSchedulingPriority=7`,
`CPUWeight=20`, `IOWeight=20` — the job keeps progressing but yields to the API instead of starving it.
Verified with `systemctl show`: `CPUWeight=20 IOWeight=20 Nice=10 IOSchedulingClass=2
IOSchedulingPriority=7`. The real fix is stream `S-F` (off-machine encrypted backup with far less
churn), not this drop-in.

### Three mistakes I made on the way, because the record of being wrong is the useful part

**M1 — I ran whole-tree reads against the production backup store while its backup job was running.**
`du -sh` over 216 GB, a `find` over the same tree, and `tar -tzf` on a 1.6 GB tarball, minutes into
the 18:00 window, on a box already at 94% iowait. Read-only is not the same as harmless: on a single
saturated encrypted SSD, reading 216 GB is a denial of service against your own business. **Rule:
never `du`, `find`, `tar -t` or `grep -r` across the authority's backup store. Ask for sizes from the
metadata you already have, or read it from a replica.**

**M2 — I wrote a monitor with no sleep in its loop.** It spawned an ssh every 1-2 seconds against the
box it was measuring, produced 489 log lines in twelve minutes, and added load to an already-starved
machine. A monitor that loads its subject is worse than no monitor. **Rule: every polling loop carries
an explicit interval and a bounded log; verify the interval from the output timestamps, not from the
code you think you wrote.**

**M3 — a heredoc with backticks went through ssh and bash executed the backticks.** The systemd
drop-in's comment line contained `` `secretary-api.service` ``, so the remote shell tried to run it
("command not found") and wrote a mangled comment into the config. The directives applied anyway, so
the outcome was right by luck. **Rule: never put backticks, `$()` or `$VAR` in a heredoc that travels
through ssh — pass file content by base64, as this estate already does for PowerShell.**

**Also corrected mid-session, in case an earlier draft is quoted:** I first said the API "was down" and
implied the watchdog was restart-looping it. Both were wrong. It *was* serving 200s at 18:14:17; the
stop at 18:18:44 is still unexplained; and the watchdog only reports. Later I said it "recovered"
because `is-active` returned `active` and the socket accepted — that was also too generous: a real
`/health` request still does not complete.
