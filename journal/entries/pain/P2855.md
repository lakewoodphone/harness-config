## P2855 — the malformed-tool-input fix is a local patch and can be lost three ways; our own session readers silently read one zstd frame

## Pain: the malformed-tool-input fix is a local patch, so it can be lost in three ways

Found and measured 2026-10-05 while fixing this exact failure. The fix itself works (86/86; see W2635), but
nothing in the fleet keeps it in place. Ranked by what it would cost.

1. **A version bump silently drops it.** `scripts/patch-dsh-malformed-tool-input.py` patches the pinned
 prefixes under `dsh-update/vendor/prefix/<version>/`. A new prefix (0.2.0-rc.3, 0.2.1) is a fresh tree the
 patcher has never touched. The patcher fails loudly when its anchors move — but only when someone RUNS it.
 Nothing runs it. This is exactly how `patch-dsh-settlement-crash.py` came to be absent from the live
 0.2.0-rc.2 runtime (checked 2026-10-05: no `MESHFIX:settlement-crash` in `dsh-agent-loop/lib/index.js` under
 any vendor prefix, only the npx-era trees carry nothing either). **Fix: a re-apply step in the upgrade
 switch that runs every `scripts/patch-dsh-*.py` and refuses the switch if any `--check` exits 1.**

2. **The other nodes are unpatched.** The patcher covers every runtime root on the machine it runs on;
 ZABZ-TECH, secratary, the Linux mesh worker and the VPS each need it run there, and the `candidate_roots()`
 list is the only thing that makes the Linux layout reachable (`/home/zabz/dsh-engine/...`).
 **Fix: run it as part of `provision-mesh-node.sh` / the mesh restart scripts, then `--check`.**

3. **A running engine keeps the old module until restart.** `dsh-hmr` watches profile patch files
 (`cordis.patch.yml`), not vendored `node_modules/@deepseek-ai/*/lib/*.js`, so an already-running process
 does not pick the fix up. Measured from its own source 2026-10-05. Not a defect in the harness, but it
 means "patched" and "in force" are different claims and a report must say which one it means.

Secondary, found by the same investigation and worth its own row:

4. **Our session-reading tools silently read only the first zstd frame** of `~/.dsh/sessions/**/session.v*.jsonl.zstd`
 (Node `zstdDecompressSync` / `createZstdDecompress`), returning the 198-byte header of a 227 KB log.
 `scripts/push-dsh-sessions.mjs`, `scripts/dsh-sessions.py` and this seat's own scanners were all suspects;
 the Node ones are confirmed wrong. **Fix: read through Python `zstandard.stream_reader` (proven on 2494
 files) or `zstdcat`; add a self-test that a known non-empty session yields more than its header.**
 Without this, "the ledger contains no X" is an untrustworthy statement about this fleet's own history.
