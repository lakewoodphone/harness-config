## P330 — The journal is measurably divergent on ZABZ-TECH and nine entry ids already mean two different entries

**P · The journal is measurably divergent on one machine and nine entry ids already mean two different entries — root cause found, fix designed, not yet applied**

MEASURED 2026-09-18 by workstream C on **ZABZ-TECH** (all figures below are that machine's unless stated).

WHAT IS WRONG, WITH NUMBERS:
- `master` = `f356be14ad9b021659593bb28939130c90e317a1`; `origin/master` = `d530b1cf4e046e2f46187bd1c6025acaf71e6d31`.
- autosync reports `ahead 7, behind 52`, `result: "attention"`, `id_collisions: 39`,
 `preserved_ref: refs/heads/diverged-ZABZ-TECH-20260918` `[read from status.json]`.
- **Nine entry ids mean two different entries right now**: `L1920`-`L1928` exist on BOTH `master` and
 `origin/master` with different blob hashes. `L1920` is `07963d0a…` locally and `f476355a…` on origin.
- Origin already carries seven `diverged-*` branches — the scar tissue of the same event repeating.

ROOT CAUSE, AND IT IS MECHANICAL, NOT CARELESS: autosync refuses to fast-forward a diverged history, so
that clone stays 52 commits behind, so `journal.py append`'s id ceiling cannot see the refs it has not
fetched, so it allocates numbers that are already in use upstream. The journal's own rule is "reuse is
forbidden, gaps are free" — the rule is right and the fetch it depends on is the part that fails. This is
a DESIGNED failure made likely by construction: the journal's own text says "offline a machine cannot see
the refs it has not fetched — so conflict is possible by construction".

SECOND CONSEQUENCE, MEASURED, AND IT IS QUIET: because the same fast-forward refusal blocks the config
apply, that node is running configuration from **2026-09-16 11:02** while origin is 52 commits ahead —
and the applied `~/.dsh/settings.yaml` carries **no commit sha, no `Updated:` field, no provenance at
all**, so nothing on the machine can tell a reader how old the configuration it is running is.

THIS MACHINE (ZABZ-YOGA) IS NOT AFFECTED, AND THAT IS WORTH RECORDING SO IT IS NOT
RE-INVESTIGATED: `journal.py check` -> **0 errors**, 95 warnings, 80 info, exit 0; `journal.py doctor` ->
cache fresh, lock free, origin reachable; comparing `git ls-tree -r HEAD` against `git ls-tree -r
origin/master` over `journal/entries` -> **0 paths present in both with different content**. It is
diverged by a small amount (ahead 7, behind 2) and that is a separate, lower-priority reconcile.

THE FIX IS DESIGNED AND COSTED, NOT GUESSED: `docs/mesh/112-single-source-of-truth.md` §6 carries the
eight-step reconciliation (preserve first to a `diverged-*` ref, detect by identity not by eye, classify
each divergence, repair ids with aliases and never renumber downward, re-fetch config, rebuild derived,
drain the backlog, prove convergence) and seven operations the reconciler MUST refuse — including
reconciling a shared clone out from under 16 live `node.exe` processes and a held `journal/.lock`, which
is what that node has. Its Phase 1 test is the one that matters: two clones from a common ancestor, 20
appends each with one never fetching, then merge — pass is **0 collisions, or the second append exits
non-zero naming the unfetched refs**. A run that reuses a number and exits 0 is a failure.

WHAT WOULD FIX IT, in order: wire `idguard.py` into the writer path with no silent `--no-fetch` (Phase 1);
apply the ORIGIN snapshot even when diverged and stamp the applied file with the commit it came from
(Phase 4); then clear the 39 existing collisions from a machine that can see both sides.

NOT DONE, and deliberately: no reconciliation was attempted. Every rule in the design says a machine that
cannot see both sides must not repair the record, and this session could see only one.
