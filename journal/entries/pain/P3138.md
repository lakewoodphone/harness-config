## P3138 — What the search audit did NOT fix: zabz-tech 27 days stale, data/tools still untracked, 95-vs-2 divergence, cold first touch, read-only nodes

**P-new · 2026-10-12 · ZABZ-YOGA/authority · What the search audit did NOT fix, ranked by what it costs when it is forgotten**

Filed from the search audit (journal H3571). Each item is measured, and each names what would close it.
The authority's search surface is working; these are the remaining ways it can silently stop.

**1. `zabz-tech`'s search index is 27 days stale and its scheduled task is failing.**
`~/.fsearch/index.db` **4,885,487,696 B, mtime `2026-09-14T17:42:12Z`**; `names.db` 713,154,560 B @
`2026-09-14T17:34:30Z`; state `last_run 2026-09-14T17:34:36Z`. Task `DSH search index refresh`:
`LastRunTime 2026-10-11T22:39:01Z`, **`LastTaskResult=1`**, `NextRunTime 2026-10-11T23:39:00Z`.
This is the **third** instance of the dead-search-clock class (P2899 D2, H3376) and it is on the
owner's primary desktop. **What would fix it:** read the task's own last error, fix or re-register the
trigger, and add a companion job that measures the index rather than assuming it — the pattern in
`harness-config/scripts/find-anything/check-faindex-freshness`.

**2. `data/tools/` is still gitignored, with 600 tool bodies outside version control.**
Restored, and now guarded by `tool-body-guard.py` on an hourly clock — but the *files themselves* are
still untracked and outside most backups. The guard catches a **loss**; it does not prevent one.
**What would fix it:** track them (or capture them the way `scripts/deployed/bin/` captures the text
line), so a future migration cannot drop them.

**3. The harness-config clones have diverged: 95 commits on the authority, 2 on GitHub.**
Measured 2026-10-12 on `secratary-cloud`. Neither clone's push is a fast-forward; the authority also
pushes to a `vault` remote (`lpt-apps`) that **did not answer** (`git ls-remote vault` timed out). This
session committed to both working trees and **refused to force anything**. **What would fix it:** an
explicit reconciliation session — nothing here is urgent, and a wrong move loses the 95.

**4. The cold first touch of the journal index is unmeasured and over budget.**
Warm `ps_search what=journal` is 1.5–1.9 s; the first query after an index rebuild measured **4.8–6.6 s**
(and 21.9 s when two rebuilds collided on the same cron minute — that specific collision is fixed).
This is the caveat H3411 recorded in its own words: *"do not claim the cold case is fixed until it is
measured."* **What would fix it:** measure a genuinely cold cache, then test `PRAGMA mmap_size` and a
warm-up step.

**5. Three nodes are `read-only` and carry the buggy index builder.**
`hetzner` and `lpt-apps` run `~/bin/build-indexes.sh`, which resolved `$H/harness-config` (a path that
exists on no host) and would write an **empty** index over a good one if its roots ever vanished. Their
current indexes are correct and tiny — 8 files, 8 entries — so this is latent, not broken.
`lpt-survivor-01` has no search surface at all. Per `settings/machines/host-posture.tsv` these are
`read-only`: **the fix needs a window the owner grants, not an agent's judgement.** The corrected
builder now refuses to write an empty result and exits 4, so deploying it is the whole fix.

**6. `mac-mini-ts` never answered.**
Tailnet and LAN both `Connection timed out`, TCP 22 closed. **Unreachable is not a negative** — its
search surface is UNKNOWN, not absent.

**7. `ps_search`'s registration is not asserted anywhere.**
P2868 recorded that the tool was committed on whatever branch production happened to be on. The body is
now on the trunk and in harness-config, and a guard asserts *bodies*. Nothing asserts that the MCP
server's tool list contains `ps_search`, so a checkout from another line could still remove it silently.
**What would fix it:** one assertion over the MCP server's registered tool names, in the same guard file.
