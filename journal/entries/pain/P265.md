## P265 — Three owner_decision_queue rows lost their amounts in storage (#79, #33, #86): \$+digits eaten before the INSERT

# Three `owner_decision_queue` rows have their amounts destroyed in storage — `$` + digits were eaten before the INSERT

Found 2026-09-18 while triaging the queue (28 pending rows). Rows **#79, #33 and #86** each lost
money to the same defect. **Row #79, severity `high`, is unreadable where it matters most: its
money.** The legal exposure it asks the owner to weigh cannot be priced from the row.

## The rule

Text written into `owner_decision_queue` must be inserted with **parameter binding**, never
built by interpolating a command line. Any `$`-bearing value — a price, a penalty, a band — can
be consumed by the shell or by PowerShell before SQLite ever sees it, and the loss is **silent**:
the row still reads like a sentence, so nobody notices that a number is missing. Two independent
writers have now done it.

## Row #79 — the amounts are gone (raw strings, exactly as stored)

Read with `sqlite3 "file:/home/zabz/personal-secretary-mvp/data/secretary.db?mode=ro"` — a
**read-only** connection, no shell in the path — so this is the stored value, not a quoting
artefact of how I looked:

```
1|dministers sukkahs by permit. EXPOSURE: 5:23-2.31(e)2 up to \,000 per violation for starting without a permit, each WEEK of non-compliance a separate
```

and from the same row's `context` / `options_json` / `recommendation`:

- `5:23-2.31(e)2 up to \,000 per violation`
- `The permit itself is CHEAP: min \ permit, \ min plan review, \ zoning permit, plus a cu-ft surcharge - roughly \-300 all in`
- `The \,500-\,000 stamping figure in this project corpus is corroborated by NOTHING`
- `Asking a neutral project question first ... costs \-75 and admits nothing`

`\,000` is `$` + a multi-digit number whose leading digits were consumed, leaving an escape
backslash behind. `min \ permit`, `\ min plan review` and `\ zoning permit` are three separate
permit fees that are now simply absent. **A `high`-severity row asks him to weigh a penalty of
"up to $X,000 PER WEEK of non-compliance plus a removal order" — with X gone, and with a
`$500-$1,000` figure it explicitly says not to repeat.** He is being asked to make a legal
exposure decision on a row that has lost its numbers.

## Row #33 — the same signature, a different row (this is why "second of this class" matters)

Also found today, and independently by the detector below:

- `options_json`, raw: `/device/mo + Stripe Price + webhook secret enabled (recommended)` — the
 price that should precede `/device/mo` is gone, so the option label now starts with a slash.
- `recommendation`, raw: `Option 1 (recommended): per device per month, set the Stripe Price` —
 **two consecutive spaces** where `$N` was.
- `question`, raw: `the exact per-device monthly price - the band you already set is -10` — the
 lower bound of the band was eaten, leaving `-10`.

Two rows, two writers, one class. The parent reported #79 as the second of this class found
today; #33 is the other, and its signature is the same one, so the two are consistent.

## Row #86 — a third row, and the one I nearly missed

Flagged by the backslash scan, and only when I looked at *where* the backslash sat. Raw
`resolution`, offset 213:

```
served deepseek-ai/DeepSeek-V4-Flash-0731 at \.00286/call x14,896 calls (100%% success). Fast-t
```

`\.00286/call` is **`$0.00286` per call**. The `$0` was eaten, so a cost claim that anchors a
whole routing decision now reads as an escaped fragment. #86 is `resolved`, so its damage is
already baked into a closed decision — and note it survived because it was only ever read for its
*verdict*, never for its arithmetic.

**Three rows, one class, and the counts in each are load-bearing.**

## A cheap detector: the union of two signals, and it catches all three

There is no single marker. `$` + digits can be eaten leaving **a bare backslash** (#79, #86) or
leaving **a double space** (#33). Run both:

```sql
-- (a) a lone backslash
select id, status from owner_decision_queue
 where instr(coalesce(question,'')||coalesce(context,'')||coalesce(options_json,'')
 ||coalesce(recommendation,'')||coalesce(resolution,''), char(92)) > 0;
-- 33, 38, 79, 86

-- (b) a double space
select id, status from owner_decision_queue
 where instr(question,' ')>0 or instr(coalesce(recommendation,''),' ')>0
 or instr(coalesce(options_json,''),' ')>0;
-- 33
```

Union = **#33, #38, #79, #86** — four rows flagged, of which three are real money losses. #38 is a
false positive (see below). Four rows out of 98 to review by eye is a usable lint, and (a) alone
would have missed #33 entirely while (b) alone would have missed #79 and #86.

## Separate, minor: literal `\n` stored instead of newlines

`#33 options_json` (offset 65) and `#38 options_json` (offset 52) contain the two characters `\`
and `n` where a newline belongs (`...(recommended)\nA different price in the -10 band`). Those rows
render as one long line in `owner-queue.py` output. This is the **false positive** in detector (a):
#38's backslash is cosmetic, and its text contains no money at all. Same cause though — text
arriving pre-escaped from a command line instead of bound as a parameter.

## What would fix it

1. **Bind, never interpolate.** `add --question/--context/--options/--recommendation` values must
 reach SQLite as bound parameters. The CLI already binds its INSERT
 (`owner-queue.py:130-135` uses `VALUES (?,?,...)`) — so the corruption is happening
 **upstream of the CLI**, in whatever builds the shell command that invokes it, and in any
 direct SQL writer.
2. **A guard on the way in.** Reject or warn on a lone backslash or a double space in
 `question`/`recommendation`/`options_json` at insert time.
3. **Do not "repair" the lost numbers from context.** The correct state of `$X,000` is unknown,
 and #79's own text says the `$1,500-$3,000` stamping figure is corroborated by nothing. The
 amount must be re-derived from the cited sources (NJAC 5:23-2.31(e)2, Lakewood UDO) and the
 row re-`add`ed — not guessed.

## Corroboration on the same day

Row **#99** arrived while this was being written: 70 of 325 inbound texts to the AI text line got
an HTTP 500 `database is locked` from the app. My own re-classification write hit the *same*
contention — `owner-queue.py` connects with `timeout=20`, which is too short under the live API's
write load, and the first attempt got one row through in 300 s. That one is fixed by
`PRAGMA busy_timeout`; the corruption in #79/#33 is not a contention problem at all, and needs
the binding fix above.
