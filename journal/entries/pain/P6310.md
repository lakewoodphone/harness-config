## P6310 — The read tool returned another file's contents once, for an explicitly-given path

**The read tool returned the contents of a DIFFERENT file once, for an explicitly-given path. Two readers of the same path disagreed, and one of them was wrong.**

Measured 2026-10-13 on ZABZ-TECH. Two sync records for one case sit in the same directory and differ only in where the date goes:

- `lpt-hub/docs/customer-operations/sync-records/q6-battery-7326783677-2026-08-24.json` — 1468 B, mtime 2026-09-01
- `lpt-hub/docs/customer-operations/sync-records/2026-08-24-q6-battery-7326783677.json` — 2139 B, mtime 2026-10-08

`read` on the **first** path returned the **second** file's contents — its distinct `caseId` ("q6-battery-7326783677-2026-08-24"), its `updatedAt` "2026-10-08T02:07:09Z", and a `portalSummary` string ("Replacement battery ordered; will be in touch when it arrives.") that **exists nowhere in the first file**. A later `read` of that same path returned the correct contents. In the same session `grep`, `Get-Item` (length + mtime) and `Select-String` agreed with each other and with the live file, both times.

I was one step from reporting the second file's `portalSummary` as the stale string in the first — a true sentence about a false file, which is exactly the shape of P3.

**The rule this earns.** For a record I am about to **edit** or **quote as evidence**, one reader is not enough: confirm with a second, independent one — a byte count and an mtime from the shell, a `Select-String`, or `git show <sha>:<path>` — *before* the sentence leaves me. Cheap here; the alternative was a wrong claim about the shop's own record.

**NOT RESOLVED.** The cause is unknown. It did not reproduce in two retries on the same path, so it may have been a one-off in the tool or in my own composition of the call, and I cannot tell those apart from the evidence I have. Treat it as unexplained, not fixed. If it recurs, capture the exact call and both readers' outputs side by side.
