## P4250 — A send loop re-submits the same two owner texts every 2-5 minutes for 20 hours and nothing notices, because the relay silently holds it

# A send loop has been re-submitting the same two owner texts every 2-5 minutes for 20 hours, and nothing notices because the relay silently holds it

**Found 2026-10-15T15:04Z while writing the owner-text audit up (`H4872`,
`docs/owner-text/OWNER-TEXT-AUDIT-2026-10-15.md` F8) - not by looking for it.**

`/root/.owner-text/relay.db` `attempt`:

```
30|2026-10-15T14:45:18Z|app|sms_service.send_message|SEND |ok |pending|I still have your message and I'm routing it now.
31|2026-10-15T14:45:18Z|app|sms_service.send_message|SEND |ok |pending|The charge posted on the 14th.
32|2026-10-15T14:50:22Z|app|sms_service.send_message|DEDUPE|dup-inflight|pending| ... same pair
34|2026-10-15T14:53:17Z| ... same pair
36|2026-10-15T14:54:04Z| ... same pair
```

The same two bodies were first submitted at **2026-10-14T19:55:10Z** (attempts 9 and 10) and are
still arriving **20 hours later**, every 2-5 minutes (attempts 9 -> 37; `owner-text status` at
15:04Z: attempts_total 37, verdicts_24h SEND 9 / DEDUPE 20). Every attempt is stuck at
`status='pending'`, because the door never calls `record_sent()`/`record_failed()`, so the relay's
dup-inflight window can never close and each repeat is held forever.

**Two facts, and the second is the pain.**

1. **The relay works.** 20 holds in 24 hours and `sms_log` shows **zero** outbound rows to the owner
 in the window. This is P3173's relay doing exactly what it was built to do.
2. **The loop under it is undiagnosed, and the relay is now load-bearing for a defect nobody has
 found.** Candidates, both `app/main.py`: line 3540 (`"Still escalating this to the owner now. If
 you can, text the exact blocker or location."`) and the receipt described at 3562. The second body
 has **no literal anywhere** in `app/`, `scripts/` or `/root/bin`, so it is probably model-generated.
 `textsend.py:1543-44` already names the class: *"a receipt: it buys him nothing"*. **The clock was
 not found and is not guessed at.**

**Why it is a pain and not a fix.** Nothing alerts on it. A hold is indistinguishable from health:
the relay reports the holds as correct decisions, every door's own doctor is green, and the only
symptom is 20 identical rows in a ledger nobody reads. That is the same blind spot P3173 recorded
about the relay itself - *"if he goes quiet, suspect the relay holding rather than the doors
breaking"* - arriving from the other direction. **What would fix it:** an alert when one
`body_hash` accumulates more than N `dup-inflight` holds (the loop's signature), and a door that
records its send outcome so a `pending` attempt cannot live forever.
