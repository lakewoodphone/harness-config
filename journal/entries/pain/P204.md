## P204 — journal.py check's verdict depends on unrelated code in its own file

## What hurts

**`journal.py check`'s verdict on the whole journal changes from 1 error to ~1090 errors purely
because unrelated code was added to `journal/tools/journal.py`.** The validation is therefore not
a function of the data it claims to validate, which means *"check: 0 errors" cannot be trusted as
a signal* — and that is the signal every session in this system has been leaning on, including
the one that authorised the journal rebuild.

## The measurements (same tree, same state, tool swapped between runs)

| tool state | `check` result |
|---|---|
| original | `1 error(s), 49 warning(s), 76 info` |
| + ~120 lines of helpers, `cmd_check` untouched | `1065 error(s), 49 warning(s), 9 info` |
| + helpers, with the `cmd_check` insertion **removed** | `1065 error(s), 49 warning(s), 9 info` |
| original again (same tree) | `1 error(s), 49 warning(s), 76 info` |
| + helpers, each function removed one at a time (7 variants) | `1090 error(s)` in **every** variant |

The errors are all `entries/<path>: heading does not match the <kind> heading form`, on ordinary
entry files, and the count **tracks the number of entries** (1065 → 1090 as other sessions added
entries). The `info` count collapses 76 → 9 at the same time, so the parser is not merely stricter:
it stops recognising headings it previously recognised *and annotated*.

## Hypotheses already falsified — do not re-test these

1. **The `cmd_check` insertion.** Removing it changes nothing, and with it gone none of the added
 functions is even called during a check.
2. **Any single added function.** Seven variants, one function removed each: all 1090.
3. **UTF-8 / interpreter decoding mode.** `PYTHONUTF8=1` gives the identical result.
4. **A stale committed index.** Rebuilding the index first (`journal.py index`, 29 rows added) and
 re-running changes nothing: 1 error before and after.

## What that leaves

The trigger is *the presence of added code in that file*, not what the code does — which points at
something in the tool that is sensitive to its own source: a self-referential table, a line-number
assumption, or a heading-form registry derived from the module. That is a guess and is recorded as
a guess.

## Reproduction, exactly

1. Keep a copy of `journal/tools/journal.py`.
2. Append any ~120 lines of new functions to it (no edits to existing code).
3. `python journal/tools/journal.py check` → ~1090 errors.
4. Restore the original → 1 error.

The patched and pre-patch files from this round are preserved at `%TEMP%\journal.patched.py` and
`%TEMP%\journal.py.bak`, and the bisect scripts are `%TEMP%\bisect_helpers.py` and
`%TEMP%\bisect_check.py`.

## Why it matters beyond tidiness

- It **blocked a real fix** (wiring `idguard`'s mint floor into `next-id`), and the workaround cost
 a peer module and an autosync change instead of a four-line edit.
- It means a session that extends the journal tool can be told its journal is broken by an artefact
 of its own edit. The most expensive failure in this system's history is a confident wrong number;
 this is a confident wrong verdict, delivered by the tool everyone trusts.
- Whoever fixes it should make `check`'s verdict depend only on `journal/entries/**` and the state
 tier — and then add a regression test that appends a function to the tool and asserts the check
 output is unchanged.

## Next step

Move the heading-form definitions (or whatever the parser reads from itself) out of the module and
into data, then re-run the reproduction above. Until then: **call `idguard.py` for id questions
rather than trusting `check`**, and treat a sudden mass of heading-form errors in `check` as this
defect before treating it as a data problem.
