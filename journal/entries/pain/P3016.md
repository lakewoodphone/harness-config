## P3016 — The two stores that hold every customer message disagree about WHEN by four hours, and one of them stores each message twice

**What hurts.** The shop's contact record is written to TWO stores that disagree about WHEN, and the disagreement is exactly 4 hours.

**Measured 2026-10-11, Chaim Margulies (347) 418-5638.** The same inbound message carries
`created_at = 2026-10-11T15:31:41.875Z` in the secretary store (`dialpad_sms_cache`, whose own
`fetched_at` is `15:31:45.654Z` -- the fetch cannot precede the message) and
`communications."createdAt" = 2026-10-11 19:31:41.875` in the production website store
(`PHONE_TECH_FULL_DATABASE_URL`, a `timestamp without time zone` column on a UTC session). Same content,
same phone, identical to the millisecond except the hour.

**It is not a global offset, which is what makes it dangerous.** For the day's newest SMS the two stores
agree to 1.5 s: cache `20:23:24.347Z` vs website `20:23:25.848`. And the website store holds the SAME
message twice with two different times -- e.g. "Hi I'm waiting outside your door are you open?" is stored
at `16:09:11.615` and again at `19:09:18.381`, and the four relay messages from (845) 825-6431 at
`16:34:15-16:35:31` are stored again at `19:09:17-19:09:18`. So there is a re-ingestion pass that writes
today's messages a second time stamped with its own clock, and the pairs sit 3-4 h apart. Independently,
the website's `PHONE_CALL` row for the 19:33:15Z call carries `createdAt 20:09:05` -- +36 min -- so that
column is a *finalisation* time, not an event time, and must never be read as "when the customer wrote".

**Why it matters.** The only reading a human ever makes from this record is "when did they contact us and
what did they say". A four-hour error moves an 11:31 AM text to 3:31 PM, which changes who was on shift,
whether we were open, and whether we were slow. It is the same class as P3 (read the wrong value and
believe it) and it is invisible: both stores answer without error.

**What would fix it.** One decided source of truth for communication timestamps -- the Dialpad message id
plus Dialpad's own created time -- with the other store derived from it rather than stamped at write
time. Until then, quote the secretary store's time and say the website store disagrees; do not silently
pick one. NOT RESOLVED which is correct for the 15:31/19:31 pair; the customer-waiting-outside message
at 16:09Z (12:09 PM ET, which matches the Sunday noon opening) is the only independent hint, and it
favours the secretary store's clock.
