## P6338 — The company API wedged a second time in one day; restarted and verified, with three of my own readings corrected - and ps_log_tail(tick) queries columns that do not exist

The company API wedged for the second time in one day; I restarted it through the posture guard and verified the recovery, and three of my own readings about it were wrong before I checked them.

**The fault, measured 2026-10-14 12:2x-12:34Z on `secratary-cloud`:**

 systemctl is-active active NRestarts=0
 ExecMainStartTimestamp 12:20:47Z
 memory.current / memory.high 5,998,612,480 B (5.59 GB) vs 5,767,168,000 B (5500M)
 memory.pressure some avg10=80.25 full avg10=80.14
 memory.events high 44,998 max 0 oom 0
 curl /health (30 s deadline) http=000, twice
 last log line 12:24:18Z "GET /health HTTP/1.1" 200 OK
 next log line none until 12:33

So the unit was **`active`, `NRestarts=0`, listening on 127.0.0.1:8002, and answering nothing**, with its cgroup 80 % unable to run for memory — the same signature `H3660` recorded at 11:58 (where `full avg10` was 84.64) and the reason that handoff's own lesson is *"a health check that asks 'is the unit active' cannot see a wedged process."* Another session had already diagnosed it and written `45-memory-headroom.conf` at 12:28 — raising `MemoryHigh` 4G → 5500M with a precise argument that the soft limit sat **below** the process's 4.26 GB working set — but that drop-in cannot un-wedge a process already stuck in reclaim, and the start timestamp was still 12:20:47.

**The action and the verification.** Posture guard first: `bash scripts/mesh/guard-service-state.sh --host secratary-cloud --op restart` → `ALLOW … (decided 2026-10-11T05:43:36Z: docs/mesh/131-MIGRATION-BRIEF.md Rule 2)`, exit 0. Checked no source file had been written in the previous ten minutes (only `autopilot.py` at 12:20:47, the edit the running process had already loaded and booted with). Then `systemctl restart company-api` → rc=0. After:

| | before | after |
|---|---|---|
| `/health` | http=000 at 30 s | **200 at 1.26-2.01 s**, three consecutive probes |
| `memory.current` | 5.99 GB | 1.91 GB, then **stable at 4.29 GB** across three readings 20 s apart |
| `memory.pressure` | full avg10=80.14 | **some avg10=0.00** |
| `/v1/models` | — | **degraded: 200 at 11.63 s once, then http=000 at 12 s**, three times |

`/v1/models` is therefore **not** fixed, and the recovery is stated as partial rather than complete.

**Three of my readings were wrong and I corrected them before reporting:**
1. I said the service had been down "about an hour". It had been down **~9 minutes** (12:24:18 → 12:33:09). I had assumed a clock rather than reading one; `date -u` settled it.
2. I said memory was growing at ~2.8 GB/minute and would wedge again in a minute. **It was mid-boot.** Three later readings were flat at 4.29 GB. A single rising pair is not a trend.
3. I said "0 ticks since 12:30 — work has not resumed". The tick cadence is **~10 minutes** (69 ticks in 12 hours), and the restart was only 4.5 minutes old, so that was **not yet a fault** — I was one data point away from reporting a second outage that did not exist. What *is* real: **hours 09 and 11 today had ZERO ticks** (00:2, 01:9, 02:11, 03:7, 04:4, 05:5, 06:5, 07:6, 08:8, 09:0, 10:6, 11:0, 12:6), so the tick loop stalls for whole hours as a pattern, and hour 11 is explained by this morning's wedge.

**The engineering fix is named and it is not configuration.** `45-memory-headroom.conf`'s own final paragraph says it: *"the process must fit in the bound in the first place. 82 threads with MALLOC_ARENA_MAX=2 and autopilot sharing this cgroup is the size that got here. Moving autopilot into its own process is the fix for that, and it is engineering, not configuration."* Measured now: 82 threads, `MALLOC_ARENA_MAX=2` correctly present in the running process environment, and the service holding ~4.29 GB with the autopilot thread inside it.

**A second, independent defect found while looking, verified:** the owner-facing instrument for tick activity is broken by a column mismatch.

 sqlite3 "PRAGMA table_info(tick_telemetry)" -> id, tick_id, agent_id, tick_number, step_id,
 goal_id, started_at, ended_at, llm_rounds,
 total_tokens, total_cost, tool_calls_json,
 autonomy_decisions_json, latency_ms,
 steps_completed, outcome, error, tick_quality
 ps_mcp_server.py:719 "tick": ("tick_telemetry", "agent_id, tick_type, quality, cost_usd, created_at")

`tick_type`, `quality`, `cost_usd` and `created_at` **do not exist** in that table (the real names are `tick_quality`, `total_cost`, `started_at`). So `ps_log_tail(log_type="tick")` — the tool a human uses to see whether the company is ticking — fails instead of answering. It is the same shape as everything else this session: **an instrument that reports about the wrong object.**
