## P2847 — ZABZ-TECH: the version-coupled config delivery is frozen by a junction Python will not traverse, and the engine starts twice at boot

## P(new) — ZABZ-TECH: the version-coupled config delivery is FROZEN by a junction Python will not traverse, and the engine starts twice at boot

RANKED, worst first, each with what would actually fix it.

**P1 — `sync.py`'s two version-coupled steps are SKIPPED on ZABZ-TECH, so presets and profiles are no
longer delivered from the repo at all.** Measured 2026-10-05 04:33Z with `python
harness-config\scripts\sync.py --dry-run`:

```
 presets: SKIPPED -- the version check did NOT run (check-version-coupled-config: ERROR OSError:
 [WinError 448] The path cannot be traversed because it contains an untrusted mount point:
 'C:\Users\ezabz\.dsh\profiles\node_modules\@deepseek-ai'), so this version-coupled step was not
 published; every other step of this sync still applies
 profiles: SKIPPED -- the version check did NOT run (same OSError)
```

Cause: on 2026-10-05 the anchor `~/.dsh\profiles\node_modules` was repaired from a stale real tree of the
OLD 0.1.5 packages to a **junction** pointing at
`C:\Users\ezabz\Code\harness-config\dsh-update\vendor\prefix\0.2.0-rc.2\node_modules` (H3161). The
running engine resolves through it correctly — all three presets mount, verified — but Python 3.13
refuses to `stat` a path containing that reparse point, so the guard that decides whether to publish
cannot resolve the engine and skips. **The fix that made the machine correct is the thing that switched
its config delivery off**; the repair therefore had to be pinned into the live home by hand
(`6d686e4`, live == repo by sha256) instead of arriving through sync.

FIX, in this order, because the second step is what makes the first safe:
1. Settle the profiles/web clobber question first (H3155 item 1, still open): live
 `~/.dsh\profiles\web\cordis.patch.yml` is 2666 lines / 147,374 B against the repo's 1638 / 117,182 B,
 and the live copy holds managed blocks (`mesh-provider-install`, and `preset-rows` written by
 `scripts/make-preset-rows.mjs`) that the repo copy does not. Publishing the repo copy wholesale over
 the live one may drop them — and the profiles step is re-armed by the same repair as the presets
 step, so they cannot be re-armed separately without a code change.
2. Then rebuild the anchor in the shape the guard can traverse — a REAL `node_modules` directory holding
 one junction per package, which is exactly what ZABZ-YOGA has and what
 `check-version-coupled-config.py:135-142` documents — and prove it by `sync.py --dry-run` moving from
 `SKIPPED` to a verdict, not by the engine still booting (the engine boots either way).
Nothing is urgent tonight: the live config is currently equal to the repo and correct for the running
engine. The cost of leaving it is that any future repo fix to presets/profiles silently stops reaching
this machine.

**P2 — the engine is started twice at boot and one start always loses.** Measured twice in 12 hours on
ZABZ-TECH: at 20:24:25 local (H3155 item 5) and again after the 00:22 restart, where pid 22224 bound
`127.0.0.1:3099` at 00:24:16 and pid 29276 (`--port 3099`, 12 s later) died with
`listen EADDRINUSE` / `dsh: startup failed: 2 required plugins did not activate` — **after** spawning its
own MCP bridges (two `mcp-fetch-server`, two `playwright` processes were live at once). The loser writes
an `err.log` that a later reader (correctly) finds hard to distinguish from a real outage; one of the two
starters is `DSH Multi-Window Launcher` and the other is in the watchdog path. FIX: a single-writer
start — an inter-process lock or a lock file holding the pid and start time, so the second starter waits,
or an explicit "is 3099 already answering" check before spawning, and the loser's err log labelled as a
superseded start rather than a failure.
