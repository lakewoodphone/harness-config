## P2731 — 0.1.7 renames settings.yaml to .imported then imports its sections; a partial import never repeats and logs nothing

## 0.1.7 RENAMES settings.yaml TO settings.yaml.imported and move its sections into the profile -- and a partial import never repeats

MEASURED 2026-09-28 (ZABZ-TECH), from the candidate's own code and from two isolated staged boots.
Full context: `harness-config/dsh-update/STATE-COMPAT.md`.

THE MECHANISM, in the engine's own words -- `dsh-settings/lib/index.js:343-363`:
```js
/** Move the sections of the removed `settings.yaml` into the active profile once the Loader has
 * settled every entry. The document is renamed before the first write, so a partial import never
 * repeats; a section the running composition rejects is logged and remains only in the renamed file. */
async importLegacyDocument() {
 const path = join(profile.home, "settings.yaml");
 if (!existsSync(path)) return;
 const imported = `${path}.imported`;
 await rename(path, imported); // <-- FIRST
 const sections = parse(await readFile(imported, "utf8"));
 for (const [section, values] of Object.entries(sections ?? {})) {
 const ns = LEGACY_SECTION_ENTRIES[section] ?? section;
 try { await this.update(ns, values); } // <-- per-section, throws are only logged
 catch (error) { logger.warn("settings: section %s of %s was not imported into entry %s", ...); }
 }
}
```
It is invoked once, from the `SettingsForms` constructor: `ctx.root.loader.await().then(() =>
this.importLegacyDocument())`. `LEGACY_SECTION_ENTRIES` maps only three names
(`ui-developer-tools`->`ui-settings`, `ui-onboarding`->`ui-settings-general`, `shell`->`pwsh-sandbox`);
EVERY other section name is treated as an ENTRY ID, so our `permission`, `agent-default-model`,
`agent-presets`, `llm-deepseek`, `llm-pi-ai`, `spend-guard`, `agent-loop` and `ui-conversation` each
have to correspond to a registered entry or that section is dropped.

WHAT IT MEANS FOR THIS DEPLOYMENT: from 0.1.7 the home-level `settings.yaml` is no longer a settings
SOURCE. It is a one-shot migration input, renamed away the first time an engine boots. Our whole
settings pipeline -- `settings/base.yaml` + `settings/machines/<host>.yaml` merged by
`scripts/merge-settings.mjs` into `~/.dsh/settings.yaml`, applied by `scripts/sync.py` every 15 minutes
-- now feeds an IMPORT rather than the engine, so a settings change takes effect at the next BOOT and
not before.

THE FAILURE I OBSERVED, and it is the reason this is a pain entry rather than a curiosity: in a staged
boot that ran 45 s past serving, `settings.yaml` WAS renamed, and NOT ONE of our sections was persisted
ANYWHERE -- the only file in the whole home containing `ceilingUsd`, `maxParallelToolCalls`,
`danger-full-access` or `busyEnter` was `settings.yaml.imported` itself. The engine logged NOTHING: no
`settings: section ... was not imported`, and not even its own INFO line
`settings: imported <path> into profile <name>`. So the rename happens even when the import does not
complete, and **because the rename precedes the first write, that boot can never be retried** -- the
import only runs `if (existsSync(<home>/settings.yaml))`.

WHY THAT IS DANGEROUS SPECIFICALLY FOR US: a partial import silently reverts spend ceilings,
concurrency cap, the permission preset, model routing, retry policy and compaction thresholds to
defaults. It is the same silent-loss class as everything else in `STATE-COMPAT.md`, except this one is
SELF-INFLICTED BY THE UPGRADE ITSELF on the first boot.

WHAT TO DO, and it is now part of the switch rather than an optional nicety:
 1. keep the settings document in the pre-switch backup, which `tools/backup-state.mjs` already does;
 2. after the FIRST boot on the new engine, READ BACK THE EFFECTIVE SETTINGS and compare against every
 key we set -- `lib/settings-effective.mjs` already does exactly this via
 `POST /api/settings/describe`, and its own notes say a key that is absent or different is `S1`/BREAKS;
 3. if any key is missing, RESTORE `settings.yaml` from the backup and reboot: the engine re-imports
 whenever the file exists, so re-creating it is the retry the engine will not do by itself;
 4. do not let the first boot be killed early. The import runs only after the loader settles, so a
 harness that kills the engine on the first successful HTTP poll tears it down mid-import -- which is
 exactly how I produced the partial state above. `tools/staged-boot.ps1` now takes `-SettleSec` for
 this reason, and the default is no longer an immediate kill.

The audit's earlier line "settings.yaml -- SAFE as a file: candidate never opens it" was WRONG and is
corrected by this measurement; it reasoned from the absence of a reader for the file as a settings
source, and missed the one-shot importer.
