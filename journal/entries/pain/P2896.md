## P2896 — 285 outbound sms_log rows carry the placeholder twilio_sid 'twiml-reply', so delivery can never be verified

# P — 285 outbound `sms_log` rows carry a placeholder `twilio_sid`, so their delivery can never be checked

Found 2026-10-09 while reconciling `sms_log` against Twilio's own record.

## The measurement

```
SELECT status, COUNT(*) FROM sms_log WHERE direction='outbound' GROUP BY status;
 suppressed 1979 | failed 1026 | sent 285 | delivered 278 | undelivered 15 | queued 4

SELECT substr(twilio_sid,1,12) FROM sms_log WHERE direction='outbound' AND status='sent' LIMIT 1;
 twiml-reply
```

Every one of the 285 rows still at `sent` carries the literal string **`twiml-reply`** as its
`twilio_sid`, spanning 2026-02-17 to 2026-10-08. `twiml-reply` is not a Twilio SID: a real one
is `SM` followed by 32 hex characters. Asking Twilio about it returns **HTTP 404**, which is
what the reconciler reported 287 times in its last pass.

The rows are otherwise ordinary real messages — a Topgolf answer, a "I got this and I am still
working on…", the `[Budget exceeded for : ceoreserveexhausted]` notice.

## Why this matters

`scripts/reconcile-sms-status.py` reads Twilio's verdict back and corrects our rows. For these
285 it **cannot**: there is nothing to ask about. So the reconciliation reports `fetch_failed`
and the row keeps claiming a status nothing ever confirmed.

This is the same family as the defect the reconciler was written for (rows claiming `sent` when
Twilio said `undelivered`), but a different mechanism: those were a status never updated, these
are a **fabricated identifier written at insert time**. A placeholder in an identity column
silently removes a row from every future check — which is worse than a wrong status, because
the row looks checkable.

## The fix (not yet done)

Find the writer that inserts `twiml-reply` into `sms_log.twilio_sid`. It is the inbound/
reply-capture path — the messages are replies of ours that something logged as outbound. Either
store a real SID, or store NULL/empty so the row is honestly un-verifiable and skips
reconciliation instead of failing it 287 times per pass. The column is already treated as
optional by the reconciler (`twilio_sid IS NOT NULL AND twilio_sid != ''`), so NULL is the
honest value.

## How to confirm it is done

```
SELECT COUNT(*) FROM sms_log WHERE direction='outbound' AND status='sent' AND twilio_sid='twiml-reply';
```
should be 0 for new rows, and the reconciler's `fetch_failed` count should stop being dominated
by this value.
