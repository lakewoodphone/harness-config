## P208 — list_agents has no deadline and re-scans every session file serially - ranked pain list for the DSH scale program

RANKED by how much work it destroys, not by how annoying it is.

1. **`list_agents` can hang forever, and the UI shows nothing.** It declares no `timeoutMs`, and
 `dsh-tool-call-timeout-policy\lib\index.js:123-124` returns `next()` untouched when the tool
 declares none — so there is no deadline and no cancellation. Every call also serially re-scans
 the whole session home (`dsh-session-persistence-jsonl\lib\index.js:2858-2888`: for each of ~372
 session dirs, readdir + open + read + `decompressZstdFrame` + `JSON.parse`, no cache, no index)
 on the shared event loop, and every concurrent caller re-pays it in full. Aggravating: a
 genuinely empty result renders as the text "(no subagents)", so the blank is the hang, not an
 empty fleet. WHAT WOULD FIX IT: a host plugin that (a) enforces a deadline and returns a clear
 partial/timeout result and (b) serves repeated calls from a short-TTL cache. A fix inside the
 installed package would be erased by the next npm update, so it must live in harness-config.
 (Workstream in flight: `_dsh-scale\90-plugin-health-governor.md`.)

2. **The journal append critical section is 41-98 s.** After the lock is taken, an append runs two
 full-repo `git grep`s (to find the id ceiling across every ref) plus a 6.4 MB `journal.db`
 rebuild. Under a fleet, writers queue for minutes and a caller killed at the harness limit
 leaves the work half-done. The lock itself is now correct, so this is pure work-inside-the-lock.
 WHAT WOULD FIX IT: cache the id ceiling, make the index rebuild incremental, and move the mirror
 refresh out of the lock — touching the id allocator, so it needs the 6-way concurrency selftest
 first.

3. **`owner-queue.py` takes the write lock to read.** It runs `executescript(SCHEMA)` DDL on every
 invocation (`harness-config\scripts\owner-queue.py:82-87`), so a *read* of the owner queue
 contends with 18 agents writing the 500 MB `secretary.db`. Its `DEFAULT_DB` is also the Linux
 authority path, so on Windows without `--db` it would silently create `C:\home\zabz\...` and
 report an empty queue. WHAT WOULD FIX IT: gate the schema behind `PRAGMA user_version`, resolve
 the DB path per host, and fail loudly instead of creating a phantom database.

4. **SQLite has no `BEGIN IMMEDIATE` on its read-then-write paths.** `busy_timeout` cannot fix a
 read-to-write upgrade race — SQLite returns `SQLITE_BUSY` immediately (`dsh_session_ingest.py`
 documents this at its own lines 242-255). The documented guarantee is the fix: after a
 successful `BEGIN IMMEDIATE`, no subsequent operation until COMMIT can return `SQLITE_BUSY`.
 Also: a WAL-reset corruption bug affected SQLite 3.7.0-3.51.2 (fixed 3.51.3) and needs exactly
 two connections writing or checkpointing on one file — this workload — so `sqlite_version()`
 must be checked in every stack.

5. **No health surface anywhere.** `GET /healthz` is 404, and the host code has no
 `process.memoryUsage|loadavg|cpuUsage|freemem|totalmem` call at all, so there is no way to see
 event-loop lag, commit pressure or the live count of runner/MCP processes from outside. Every
 diagnosis in this program had to be reconstructed from PowerShell counters and process
 command lines. WHAT WOULD FIX IT: the health surface in the plugin workstream.
