## P2474 — dialpad-sms-ws logs STORED for rows that are not written: the SMS write path swallows every failure and reports success

WHAT HURTS
`lpt-hub` and every agent session in it say "never claim delivery without evidence" - but there is no evidence path, and the one signal that looks like evidence is a lie.

MEASURED, 2026-09-24, on `secratary`
Sent an SMS through `personal-secretary-mvp/scripts/send-lpt-sms.py --send`. The script printed `Status: pending`, `Message ID: 4513655789494272`. The Dialpad websocket service (`dialpad-sms-ws.service`, pid 981145) logged:

 Sep 24 17:24:48 dialpad-ws STORED message_id=4513655789494272 direction=outbound phone=8482217775 lag_s=12.0
 Sep 24 17:24:58 dialpad-ws STORED message_id=4513655789494272 direction=outbound phone=8482217775 lag_s=22.0

The row is not in `dialpad_sms_cache`. Verified three ways, minutes later, on `/home/zabz/personal-secretary-mvp/data/secretary.db`: `message_id='4513655789494272'` -> 0 rows; `session_id LIKE '%4513655789494272%'` -> 0 rows; `body_text LIKE '%parts supplier%'` -> 0 rows. In the same minutes the table was being written live (rowids 1115416-1115431, 17:24:27 -> 17:29:45, fetched_at 1-2 s after created_at). So Dialpad delivered the event and our own process lost it.

THE DEFECT (server copy of the code, inlined)
`app/services/dialpad_service.py::_write_sms_cache`:
1. `if not session_id or not body_text: return` - a silent no-op.
2. `except Exception as exc: log.debug("sms cache write failed: %s", exc)` - every failure, including `database is locked` on an 11 GB WAL database with two writer processes (the API and the websocket) each holding their own in-process `_db_lock`, is swallowed at DEBUG.
`app/services/dialpad_webhook.py::persist_sms_event` then does `_write_sms_cache(...)` and `return {"status": "stored", **norm}` **unconditionally**. The websocket counters and the per-minute heartbeat inherit that: measured `stored=96 skipped=0 errors=0` while a row was missing. **"STORED" in the log is not evidence a row exists.**

WHY IT MATTERS
This is the mechanism by which a customer text can be invisible forever with every dashboard green. It also silently poisons the corpus `lpt-hub` builds customer cases from - at least two agent sends (Halon 2026-09-17 `4869076347822080`, Weitman 2026-09-17 `6462041063202816`) are on record as "unwitnessed" and are most likely this same drop, not failed sends.

WHAT WOULD FIX IT (small, surgical, no schema change)
1. `_write_sms_cache` -> `-> bool`: return False on the early return, `True` iff `cursor.rowcount == 1` after the `INSERT OR IGNORE`; on exception log at **warning** with the exception text and return False.
2. `persist_sms_event` -> only `status: "stored"` when the write returned True; otherwise `{"status": "skipped", "reason": "write_dropped"|"empty_body"}`.
3. Propagate: the websocket's `skipped`/`errors` counters must move, and `POST /webhook/dialpad/sms` must not answer 200/`stored` when the row was dropped - otherwise both intakes keep reporting health they do not have.
4. Re-derive the two "unwitnessed" sends by scanning the websocket journal (`journalctl -u dialpad-sms-ws`) for their message ids. That is a working witness for anything the service saw.

BLOCKER TO FIXING IT
The two checkouts have DIVERGED: the Yoga laptop clone is `ahead 61, behind 96` of origin/master; the `secratary` clone is `ahead 159, behind 176`. `app/services/dialpad_poller.py` (a designed fallback for the webhook going deaf, docstring and all) exists on the laptop and not on the server; the server instead carries `dialpad_sms_ws.py` (the live path) and a `.bak-smsloop-20260920` left by an earlier in-place edit. There is no `dialpad-poller.timer` on the server (`systemctl is-enabled` -> not-found), so the "insurance" was never deployed. Fix the divergence and the deploy path before editing either tree, or the fix lands on one machine only.
