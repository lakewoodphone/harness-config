## P2192 — sqlite_sequence on the family chat DB overstates message count by 110k, because ignored dedupe inserts burn AUTOINCREMENT ids

## What hurts

`messages.id` is `INTEGER PRIMARY KEY AUTOINCREMENT` in a table whose dedupe path deliberately re-inserts the same rows. SQLite consumes a sequence value on an **ignored** `INSERT OR IGNORE`, so ids are burned on every dedupe hit and `sqlite_sequence` no longer estimates how many rows ever existed.

Measured 2026-09-23 on the live DB: `select seq from sqlite_sequence where name='messages'` = **111,898** against **2,001 rows** - 109,897 ids unaccounted for. Isolated in a scratch table: two successful inserts plus two ignored duplicates left `rows=2, seq=4`, and a rolled-back transaction does NOT advance it. Sampled live over 150 s with no family traffic: seq climbed 111,898 -> 111,915 while the row count stayed flat, i.e. **~7 ids/minute burned at idle**. The mechanism is the 60-second catch-up loop, which re-fetches a 5-minute overlap window and calls `insert_inbound_message` for records the partial unique index on `twilio_sid` then rejects.

## Why it matters

It manufactures a data-loss scare. An independent audit of this DB (2026-09-23, a read-only subagent) concluded "~110,000 rows are missing from this table, the gaps sit inside live conversation, so any count is a lower bound and lost traffic is invisible" - and it was right to think so from the sequence alone. The next agent will reach the same conclusion, and the failure mode this system fears most is a confident report of a crisis that does not exist (P3). The measurement that separates the two readings (sample `seq` while the row count is flat) costs one minute and was not in the DB before tonight.

Secondary: ids are the join between a log line and a row ("why did Chip say that"), and a 100k-wide gap makes `id` useless as a rough time/volume signal.

## What would fix it

Either is small:
- Drop `AUTOINCREMENT` from `messages.id` (plain `INTEGER PRIMARY KEY` still autoassigns from `max(rowid)+1` and does not persist a sequence), via a table rebuild in a migration; or
- Have the catch-up path `SELECT 1 FROM messages WHERE twilio_sid = ?` before inserting, so the ignore never fires. (Slightly more code, zero schema risk.)

Neither is done: the fix belongs with a migration pass, not with the direct-address change that found it.
