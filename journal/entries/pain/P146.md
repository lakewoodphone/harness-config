## P146 — Journal ids collide when two machines allocate offline (H228/H229/L1510/P145 all doubled today)

FOUND 2026-09-15, while merging the Mac's journal commits into mine. This one will bite her machines,
so it is written down with the evidence rather than worked around.

SYMPTOM: `git pull --rebase` conflicted on journal/entries/handoff/H228.md. Both sides had created it,
with different content:
 mine <!-- e:handoff|H228|2026-09-15 14:11 UTC|ZABZ-YOGA|open --> a verification addendum
 origin <!-- e:handoff|H228|2026-09-15 14:11 UTC|LAKEWOOECHSMINI|open --> "Daily note from LakewooechsMini"
Both sides ALSO independently created H229, L1510 and P145. Four ids, two machines, same numbers.

CAUSE: `journal.py`'s `_next_free(kind, taken)` reserves against local entries, the index, AND every
git ref -- which is a sound design for one writer and for a machine that has fetched before allocating.
It cannot help when two machines allocate while each is unaware of the other's latest commit. The
existing collision guard ("id bumped X -> Y (collision avoided)") only fires when the collision is
visible locally; here it was not visible on either side at allocation time.

WHY IT MATTERS MORE FOR HER THAN FOR ME: the journal is append-only and every citation is by id, so a
duplicated id silently breaks the meaning of every reference to it -- and her two machines each run
their own daily journal job, so this is the NORMAL case for her, not an edge case. Her agent writing a
lesson on the Mac and another on the laptop in the same hour is exactly the collision scenario.

WHAT I DID NOT DO: renumber the four entries by hand. With two minutes of thought that is a coin flip
about which content owns which number, and the journal's own design note says a reused number destroys
every citation to it. `journal.py repair-ids` exists for exactly this and should be the tool used, with
the four pairs verified first.

WHAT WOULD FIX IT PROPERLY, in order of how much I would trust it:
 1. Allocate from the AUTHORITY (one writer, monotonic counter), which is the only scheme that cannot
 collide by construction. `owner_decision_queue`-style: a tiny `journal_next_id` endpoint or table.
 2. Or make the id carry the host: `H228.yoga` / `H228.mac`, so two machines can never choose the same
 number. Cheap, and it makes provenance visible in the id itself.
 3. Or have autosync detect a duplicate id after fetch and run repair-ids automatically -- treats the
 symptom reliably, but every push window still creates a window of ambiguity.
Until one of these is in place, a machine that writes to the journal must be told to fetch-and-allocate
in one step, and two machines must not be allowed to run their daily job in the same window.
