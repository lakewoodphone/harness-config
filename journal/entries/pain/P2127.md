## P2127 — P2132 - the authority has six writers on one 9.9 GB SQLite database and no scheduling, so ordinary contention becomes user-visible 500s

Measured 2026-09-20 on secratary.

`POST /api/v1/owner/dsh-sessions/ingest` returned **500 five times a minute** with
`database is locked`. The connection already had `PRAGMA busy_timeout = 30000`; `BEGIN IMMEDIATE`
still **failed after 10.022 s**, i.e. it waited the whole timeout. So the failure is not a transaction
shape that can be fixed in code - **some writer holds the write lock for longer than any sane
timeout.**

Who was writing at that moment:

 pid=3927280 uvicorn app.main:app (the API itself)
 pid=3929355 scripts/dialpad-recording-gap.py --limit 300 (batch)
 pid=3929418 /tmp/dialpad-sms-harvest-*.py (batch)

plus, over the same hour, `secretary-backup` (24 min wall, 6.3 GB peak, every 6 h),
`commsindex.py` re-indexing the whole 9.8 GB database, `mashgiach.daily_scan`,
`lifecycle_sweep` (every 120 s), the autopilot tick, and the mesh broker's neighbours.

**Six writers, one file, 4 cores, no scheduler.** SQLite serialises writers by design; that is
correct and not the bug. The bug is that nothing decides WHO writes WHEN, so a batch job with
`--limit 300` and an owner-facing API request contend as equals, and the API request is the one that
shows the owner an error.

**What I did NOT do, and why.** I did not raise the timeout - that converts a 500 into a 10-second
stall for the owner and makes it worse. I did not add more `BEGIN IMMEDIATE` - it demonstrably does
not help Cause B (L2131). Both would have been plausible-looking changes with no measured effect.

**The fix this needs** (design decision, mine to make, not yet made): give batch writers a
lower priority or a lease so they yield to request-path writes; schedule the six-hourly backup and
the full-text re-index to a quiet window instead of whenever they fire; and stop `--limit 300`
style batches running inside the API's write window. Alternatively, accept that this workload has
outgrown a single SQLite file and move the hot tables to a server database - which is the owner's
call because it is a real migration.

**Why this is worth recording rather than quietly patching:** the same 9.9 GB SQLite file is the
company's memory, and the pattern of "add a timeout" has now been tried twice on this file with no
effect. The next person to see `database is locked` should read this first.
