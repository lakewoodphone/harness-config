## P136 — The reconnaissance nudge can never fire: its counter resets every tick and each tick runs one step

PAIN: the reconnaissance nudge is dead code, because its counter resets every tick

WHAT: `_build_work_prompt` prepends "STOP SEARCHING - N consecutive steps only READ
things" when `self._readonly_steps >= 2`. But `self._readonly_steps = 0` is executed
at the top of every `_process_work_queue` call, and `autopilot_work_queue_poll_max_steps`
is 1 -- so each tick runs a single step and the counter can never exceed 1. The nudge
has therefore NEVER fired in production. Measured 2026-09-14.

WHY IT MATTERS DESPITE BEING IGNORED ANYWAY: an earlier measurement showed the model
ignores the nudge when it does appear (it was provably in the prompt at steps 2 and 3
of session 75343, and ignored). So the cost is not the missing nudge -- it is that the
code reads as enforcement and is inert, which is how I previously mistook making action
names visible for making the loop work. A signal that cannot fire is worse than no
signal, because it looks like one.

FIX WHEN PICKED UP: derive the count from the persisted step markers, which is exactly
what `_work_session_is_progressing` now does -- count consecutive trailing steps whose
[ACTIONS:] markers are all read-only, using `_action_name_is_read_only`. Then delete
`self._readonly_steps` and its resets so there is one source of truth. Note that the
accepted-remedy is dispatch-level enforcement, not a prompt; with `_handoff_action` and
the budget extension in place the nudge is the least important of the three.
