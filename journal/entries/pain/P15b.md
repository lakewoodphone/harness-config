## P15b — A cron job that succeeded every day and persisted nothing anyone could read

**Symptom.** The Waze MDM Telnyx billing snapshot ran daily at 04:30 on the Hetzner host, exited 0, and
logged `Persisted 2 per-SIM usage rows` — while **both** `fleet_telnyx_*` tables in the PostgreSQL that
`fleet_api` actually reads sat at **0 rows**, permanently and from inception. It was writing to
`/data/fleet.db`, a **SQLite** file left over from before the Postgres migration.

**Evidence.** Read live 2026-09-11: `psql` on `waze-mdm-postgres-1` -> `fleet_telnyx_sim_usage: 0`,
`fleet_telnyx_cost_ledger: 0`; `/var/log/telnyx-billing.log` -> a clean success report every day; and
`sqlite3 /data/fleet.db` inside the container -> 12 usage + 18 ledger rows. Detail in
`deploy/waze-mdm/docs/holdings-2026-09-11.md` section 3.1 and LESSONS **L34**.

**Cost.** Vendor billing history for a *launched* product did not exist anywhere the business could see
it — including a period where the Telnyx balance ran **negative (-$9.61)** and then recovered. Any
customer-facing usage *history* or billing audit would have been silently empty. The live usage number
was correct only because the portal endpoint calls Telnyx in real time.

**Fix.** Done and verified 2026-09-11: `_connect_db()` prefers Postgres, the missing `customer` column
self-heals, `persist_snapshot()` reports failure honestly (CLI exits 2), the stranded history was
migrated into Postgres (12 usage + 18 ledger rows), and `telnyx_usage_freshness.py` now runs in cron at
05:00 to fail loudly if the data goes stale again. **Remaining:** the manual `--report` path still
persists without an assertion, and the redundant `DB_PATH=/data/fleet.db` cron variable should be removed
now that it serves no purpose.

**The generalisable rule.** A write crossing a storage boundary must be verified by *reading the row back
from the store a consumer queries*. "The job ran" and "the job exited 0" are not evidence.
