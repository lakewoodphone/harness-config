## P3012 — ZABZ-TECH harness-config autosync frozen: 32 commits behind, 1 ahead, and every modified file collides with the incoming ones

The harness-config autosync on ZABZ-TECH is frozen and has been for hours: `autosync.ps1 -Status` at 2026-10-11T19:17Z reported `attention - histories diverged (32 behind / 1 ahead)`, HEAD 61a927b preserved on `refs/heads/diverged-ZABZ-TECH-20261011`. The consequence is that none of the 32 commits of configuration reach this machine, and it reads as healthy from the outside while frozen.

WHY IT CANNOT BE FORCED, MEASURED: `git read-tree -n -u -m HEAD origin/main` refuses on `journal/alloc/bands.tsv` and, more importantly, every one of the 11 modified tracked files is ALSO changed by origin/main (7 under journal/, 3 under packages/plugin-remote-fanout/, plus scripts/phone-gate-allow.txt). So `--autostash` would stash those, rebase, and conflict on pop - and the plugin-remote-fanout changes are another session's real work, not a cache. Nothing was reset, stashed or forced.

WHAT WOULD FIX IT (a quiet window, not a hero): confirm both local commits are content-duplicates upstream (61a927b's change is on origin/skill-intake-photos-correction; a cherry-pick of my equivalent commit applied with 0 deletions), then get those paths committed or handed over by their owner so the tree is momentarily clean for a `git pull --rebase`. Then the 32 arrive normally. Same shape as the 2026-09-28 incident this script already documents - which means the script's own blocker-clearing never gets to run, because it exits at the `ahead` branch before it ever evaluates blockers.

WHAT WOULD PREVENT IT: the `ahead` condition exits before the blocker machinery, so a machine with ONE stale local commit can never converge even when everything else is clean. Step 2c should be reachable when `ahead > 0` and the local commits are provably content-duplicates upstream (patch-id match), rather than only when `behind > 0`.
