## P2191 — Family-chat ledger keeps saying queued for messages the carrier already delivered, and nothing sweeps it

BURST SENDS LOSE THEIR STATUS CALLBACKS.

On 2026-09-23 an 11-member burst left 8 of 11 ledger rows at status `queued` while Twilio had all 11 `delivered` (per-SID API fetch, 20:23 UTC, error_code=None). The three that updated landed within ~45 s. Since 2026-09-20 the DB had 274 outbound rows at `delivered` and exactly 8 at `queued` - all 8 from that burst, so the callback path works normally and a concurrent burst is what loses it. Two candidate mechanisms, not separated yet: the callback can arrive before the ledger row is written, and 11 near-simultaneous callbacks contend on SQLite (the known database-is-locked class).

WHY IT MATTERS: this DB is the provenance record for "did the family actually get it". `queued` is indistinguishable from delivered to a future reader - the same shape as P3, in a system with a customer-facing history of believing stale data.

FIXED THIS TIME (targeted): re-applied carrier truth through the system own door, hub.apply_message_status(sid, status), for non-terminal rows whose Twilio status was delivered/read. 8 rows changed; ledger re-read 11/11 delivered.

WHAT WOULD FIX IT PROPERLY: a status sweep in the existing 30-minute cron (scripts/family_chat_watchdog.py or beside it) - for non-terminal outbound rows older than ~10 minutes, fetch carrier status per SID and apply it via hub.apply_message_status. reconcile_with_twilio already covers MISSING rows; it does not cover status drift, which is why this went unnoticed. Only non-terminal rows are fetched, so the cost is bounded.

EVIDENCE: data/family_chat.db messages 111823-111833; Twilio per-SID fetch same window; watchdog manual run silent, exit 0 (it prints only on problems), log quiet since 2026-09-19.
