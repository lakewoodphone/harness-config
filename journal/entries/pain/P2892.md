## P2892 — secratary /tmp is a 12 GB RAM-backed tmpfs - a shard copying a big DB into it exhausts host memory

# P — /tmp on the authority is a 12 GB RAM-backed tmpfs, and a shard copying a
# large database into it can exhaust the machine's memory

**Measured 2026-10-09 03:10–03:25 UTC on `secratary`.** This is the machine that runs
the live company. It was not theoretical and I caused it.

## What happened

Four local subagents were running a build against worktrees on `secratary`. Two of them
copied production databases into `/tmp` to test writes safely against a copy:

- `/tmp/w2_live_copy.db` — **4,451,942,400 bytes (4.4 GB)**
- `/tmp/w1-ledger-copy.db` — **2,443,960,320 bytes (2.4 GB)**

`/tmp` is **`tmpfs`, 12 GB, and it is backed by RAM**, not by disk:

```
Filesystem Size Used Avail Use% Mounted on
tmpfs 12G 12G 0 100% /tmp
```

At the peak, `/tmp` was **100% full** and the host's available memory had fallen from
16,684 MiB to **10,382 MiB** (and `/tmp` `shared` accounted for 8,684 MiB of it). On this
host the failure modes are worse than a full disk: a full tmpfs inside an allocation can
take the live app, the autopilot loop and every agent with it.

I found it by accident — a routine `base64` call in a shell pipeline returned
`base64: No space left on device`.

## What I did

1. Killed all four subagent jobs immediately, so nothing kept allocating.
2. **Verified the exact paths and that they were copies before deleting anything** — the
 originals (`data/secretary.db`, the accounting ledger) were untouched, and each worktree
 keeps its own copy. Deleted ONLY `/tmp/w1-ledger-copy.db` and `/tmp/w2_live_copy.db`.
3. Result: tmpfs 100% → **44%**, available memory 10,382 → **16,777 MiB**.
4. Verified no in-flight work was lost — the delivery worktree still holds its 347-line
 change and its untracked `scripts/reconcile-sms-status.py`.

I did **not** blanket-clean `/tmp`: `/tmp/lpt-reverify-w17b` (2.0 GB),
`/tmp/lpt-cold-store-w17a` (1.4 GB) and `/tmp/lpt-fresh-w17a` (915 MB) were left alone
because they are not mine and I have not established who owns them.

## The rule that follows

**On `secratary`, never copy a multi-hundred-MB database into `/tmp`.** It is RAM. Use the
worktree's own directory on `/` (which had 77 GB free) or a `--tmpdir` on disk. Before
running a fleet on this host, check `df -h /tmp` and `free -m` first, and check them again
when it finishes — a fleet can exhaust the machine it runs on without any single process
looking guilty, which is the same shape as the 2026-09-16 seventeen-session incident.

## Why this is worth remembering rather than apologising for

The work was correct and the intent was safety (test against a copy, never the original).
The environment punished the choice of directory. That is exactly the kind of fact a future
session cannot infer from the code and will otherwise rediscover the same way.
