## P2603 — The authority is 4x oversubscribed (load 16 on 4 cores) while serving as the autonomy control plane, and it cannot reach two of its own worker nodes

MEASURED 2026-09-28 18:32Z on the authority (secratary), the machine the whole operation is supposed to run on.

 load average 16.15 / 14.48 / 12.23 on FOUR cores (i5-4570). That is 4x oversubscribed.
 memory 23.4 GB total, 6.2 GB used, 17.2 GB available. Memory is NOT the problem.
 swap 46 MB used of 4 GB. NOT the problem. (The 2026-09-16 note said "swap at 99.9%";
 that is no longer true and must not be quoted again.)
 disk / 318 G used of 467 G (71%). The authoritative DB alone is 12.37 GB + 128 MB WAL.
 resident python 2.49 GB RSS (2331 s elapsed), python 600 MB, node 1.15 GB, node 86 MB,
 FIVE chrome processes, gzip.
 outbound reach zabz-tech OK; zabz-yoga-1 "Host key verification failed";
 lakewooechsmini "Permission denied (publickey)".
 inbound curl 127.0.0.1:8002/health did not answer within 5 s under that load.

WHY IT MATTERS. This is the CONTROL PLANE for the autonomy system - where the driver, the ledger and
the text line live - and it is being used as a WORKER. Chrome processes on the authority mean an
interactive or headless browser session runs there. Under load 16 an ssh banner takes long enough that
the connection times out, which is exactly the failure measured from the outside the same evening
(four "Connection timed out" to secratary.tail93e6e6.ts.net while the peer's own tailscaled reported
"active; relay nyc").

THE RULE THIS BREAKS. docs/mesh/20-placement.md already records the authority as "hopeless as a fleet
worker" and "a fine control plane". It is a fine control plane only if nothing heavy runs on it. A
control plane that is 4x oversubscribed cannot start work, cannot answer a text promptly, and cannot
tell the difference between "no work" and "I could not reach you".

WHAT TO FIX (engineering, not the owner's decision):
 1. Find and move whatever runs chrome/python/node interactive work on the authority to a worker
 node. Nothing interactive belongs on the control plane.
 2. Add a load guard: the driver refuses to start a local session above a load threshold and says
 so, rather than adding to a queue that cannot drain.
 3. Complete outbound ssh config for every node (zabz-yoga-1 fails host-key verification; the mini
 is refused). An activation system that cannot reach half its nodes is the session factory that
 does nothing - the exact thing this design exists to prevent.
