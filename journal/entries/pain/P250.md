## P250 — zabz-tech boots a 0.1.0 provider plugin behind an untraversable junction, and --dump-config cannot see it

## What hurts

`zabz-tech` is running a **0.1.0** copy of `dsh-plugin-remote-fanout` — a plugin that predates
placement — and nothing says so. Measured 2026-09-17 by a local one-shot task on that machine:

* `cmd /c type <DSH_HOME>\profiles\web\node_modules\dsh-plugin-remote-fanout\lib\index.js` →
 `The path cannot be traversed because it contains an untrusted mount point.` (exit 1), while the
 neighbouring `dsh-plugin-cost` junction lists and reads fine;
* node's own resolution from the profile anchor: `dsh-plugin-remote-fanout -> NOT FOUND`,
 `dsh-plugin-attention/-mesh-http/-cost -> found`;
* the engine nonetheless **boots** (`listening=True`, `healthz 200`) and loads
 `index.js` 4382 chars, version 0.1.0, `resolvePlacementMode=False`, `placement.js=False`;
* and `--dump-config` on that same machine **exits 0 with 620 lines**.

## Why it matters

The machine is one restart away from having to resolve that bundle at boot — the link it cannot
traverse — and the fallback copy it silently used until now may not be there. A composition check on
that machine cannot see the problem.

## What would fix it

Recreate the junction **at that machine's console, not over ssh** (`90` §6: an ssh-created junction is
the untrusted kind — that is how this one got here), then prove it by reading through it:
`cmd /c type <junction>\lib\index.js` must print the file. `Test-Path` is not a proof; it returned
`True` for the junction the whole time.

## The second half

`--dump-config` exit 0 is not evidence that a bundle resolves. The composition and the resolution are
two different questions and they disagreed on that machine for an unknown length of time.
