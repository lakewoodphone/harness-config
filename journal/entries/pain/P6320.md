## P6320 — The Telnyx APN profile never worked, and the runbook blamed the SIM

## 2026-10-13 ~20:40Z · ZABZ-TECH · The Telnyx APN profile NEVER worked, and the runbook blamed the SIM

**What was actually wrong.** Pushing `telnyx-apn` to DRN 2002 came back
`MCProfileErrorDomain 1000 "The profile 'LPT Telnyx APN' is invalid"`. The onboarding runbook's
pitfall list says Error 1000 on this profile *"almost always means **no SIM is physically in the
device**"*. **That was wrong for this case, and checking it cost time:** 2002's eSIM **is** installed —
Telnyx reports `esim_installation_status: enabled` for it and refuses to re-issue its activation code
exactly because it has been installed.

The full `ErrorChain` names the cause in its third entry:

 MCProfileErrorDomain 1000 The profile "LPT Telnyx APN" is invalid.
 MCPayloadErrorDomain 2000 The payload "LPT Telnyx APN" is invalid.
 MCPayloadErrorDomain 2002 The required field "Name" is missing.

**The APNs entry had `APN` but not `Name`, which the `com.apple.cellular` payload requires.** So the
profile was malformed from the day it was written (2026-09-09) and **no LPT unit could ever have taken
it** — the cellular half of the product would have failed at the bench, every time, with a message
that points at the SIM.

**Fixed and proven, not assumed:** added `Name = Telnyx` to `waze-telnyx-apn.mobileconfig`, deployed
to `/opt/waze-mdm/profiles/` after backing the live copy up (`.bak-before-name-field-20261013T203913Z`),
validated with `plistlib` **before** pushing, then pushed to 2002: the install returned
**`Acknowledged`** and the device's own `ProfileList` now shows
`LPT Telnyx APN — com.abletel.lpt.telnyxapn / .cellular`.

**Two traps inside that fix, both mine, both caught by validating before pushing:**

1. **An XML comment cannot contain `--`.** I added an explanatory comment to the profile; the plist
 stopped being well-formed and `plistlib` failed with *"not well-formed (invalid token)"*. I then
 wrote a note warning about `--`… which itself contained `--`. **The fix: a pushed profile carries
 no prose.** The explanation lives here instead.
2. **The repo copy and the live copy differed** (repo `F955ED21…`, live `995d95b3…`) — CRLF versus LF,
 not content. Diff before deriving from either; the runbook already says this for `shop-store`, and
 it is true generally.

**Two gaps in the provisioning path, both silent:**

- **`POST /telnyx/provision` stores `activation_code = NULL`.** It reads `sims[0]["activation_code"]`,
 and a Telnyx eSIM purchase does not put the code at that path — so the code that the *phone needs to
 install the SIM* is dropped at the moment of purchase. It is recoverable with
 `GET /sim_cards/{id}/activation_code` (documented as available only for an eSIM that has not been
 installed), which is how all five were recovered; they are now in
 `deploy/waze-mdm/secrets/telnyx-esim-activation-codes.txt`, on the authority, and in
 `fleet_telnyx_sims.activation_code`.
- **The data cap did not stick.** The endpoint's cap call is wrapped as "non-fatal"; Telnyx read back
 `data_limit: null` on all five after provisioning. The 800 MB cap is the only ceiling that bounds
 spend, so it was applied explicitly with `POST /telnyx/cap` and **verified by reading it back from
 Telnyx** (`{'unit': 'GB', 'amount': '0.8'}` on all five). **Always read the cap back; never trust
 the enqueue.**

**Also resolved this round, for the record:** the two pre-existing SIMs came back from `blocked` to
`enabled` the moment the account was funded, and DRN 2001's SIM is now **`disabled`** as instructed —
note that `POST /telnyx/standby` returns `404 Resource not found` for these SIMs (both while blocked
and while enabled), so the working path to park one is `/telnyx/suspend` (disable). The standby
action is simply not available on them.
