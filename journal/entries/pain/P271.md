## P271 — lptcase.py new has no filename-length guard and --device is a prefix, not a field

**`lptcase.py new` has no filename-length guard, so a long `--device` string silently produces a filename that violates the case-file standard's own <70-character rule.**

What happened, 2026-09-18: I ran

```
python tools/case-index/lptcase.py new pixel-6-screen-9086928082-2026-09-18 \
 --name "Unknown" --phone 9086928082 \
 --device "Google Pixel 6 (plain 6) - cracked screen, customer supplying their own screen"
```

and got a 130-character filename, because the tool builds the name as `<device-slug>-<slug>-<phone>-<date>` - it does NOT take the positional slug as the whole name. My slug already contained device+phone+date, so both were duplicated:

`google-pixel-6-plain-6-cracked-screen-customer-supplying-their-own-screen-pixel-6-screen-9086928082-2026-09-18-9086928082-2026-09-18.md`

Two separate defects, both worth knowing:
1. **The correct usage is `new <customer-slug> --device "<short device>"`** - the device is a PREFIX, not a field. Passing a full device sentence duplicates it into the slug. The tool prints the resulting path, so read it before trusting it.
2. **No length check.** `CASE-FILE-STANDARD.md` §1 says "Keep it under ~70 characters" and warns "do not rename an existing file to fix a bad slug", but the scaffolder will happily emit 130 characters, and `case_id` must equal the filename, so a bad name becomes the primary key of a real case. A one-line `len() > 70` warning at creation time would prevent the whole class.

Fix applied at the time: created the correct file with `new unknown --phone 9086928082 --device "Google Pixel 6 - screen"` (52 characters), and MOVED (not deleted) the two mis-generated artifacts to `lpt-hub/_scratch/lptcase-misinvocation-2026-09-18/`. Nothing was erased, because `rm` is hard-blocked without a per-action owner yes.

Also worth knowing for the next session: the scaffolder always writes a matching `sync-records/*.json`, but the SMS runbook §6 says a phone-only sync record is noise. So when there is no work order / order / ticket number you must set `sync_record: ""` and move the generated JSON aside, or `lptcase check` reports a `[sync-record-without-case]` orphan. The cost is that the case then appears under `[case-without-sync-record]`, which is one of the classes that makes `check` exit 1 - a genuine tension between `CUSTOMER-SMS-RUNBOOK.md` §6 and `AGENTS.md` §0 ("if check reports a case with no sync record, fixing it is part of the task"). I followed the runbook, because it is the more specific rule and a real precedent case (`samsung-tab-s7-screen-customer-2026-08-24.md`) also carries `sync_record: ""`. Note that `check` was already failing on ~226 pre-existing sync orphans and 18 duplicate phones before this case existed, so this case did not change its exit state.
