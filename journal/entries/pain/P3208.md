## P3208 — owner-queue.py answer hangs with zero output when the authority DB is write-locked

**`python3 ~/bin/owner-queue.py answer <id> --answer "..."` produced no output at all and did not commit within 90 seconds — twice — on 2026-10-14.**

Measured on `secratary-cloud`, 16:05-16:25 UTC. `list --all` and `next` (reads) work fine; the **write**
path blocks. The row was still `pending` after two attempts. `fuser -v /root/authority.db` showed **four
processes** holding it open and `ls -l /proc/*/fd | grep -c authority.db` returned **57**; the database is
**28,394,013,440 bytes** with a **64 MB WAL** and a `-shm`.

**The part that hurts is not the lock, it is the silence.** A direct `BEGIN IMMEDIATE` write with a busy
timeout reports `database is locked` immediately and honestly. `owner-queue.py answer` reports **nothing**:
no error, no timeout, no partial output — so there is no way to tell "it is still working" from "it is
wedged", and a session that trusts it will believe an answer was recorded when it was not. His answer is
the one thing in this system that must never be silently lost.

Note the tool already knows about this class of failure — `cmd_answer` carries a long comment about
`SQLITE_BUSY` on the read-to-write upgrade, with the measured note *"resolve failed four times in a row
before succeeding in a retry loop"* (2026-09-14). **The known fix was applied to the transaction but not to
the reporting**: the `SELECT` at the top of `cmd_answer` can still sit on a stale read snapshot, and when it
does, nothing is printed.

**What would fix it:**
1. Set an explicit `busy_timeout` on the connection and print `database is locked, retrying (n/…)` on each
 attempt, then a clear final failure with a non-zero exit.
2. Do the write with `BEGIN IMMEDIATE` **first**, then read — so a stale read snapshot cannot be the thing
 that wedges it.
3. Never let a write path exit 0 or hang silently: **a mutated-state tool that prints nothing is worse than
 one that fails loudly.**

**Worked around, not fixed:** the answer was recorded as journal entry **D3210** (the append-only copy,
which the tool itself describes as the authority if the row and the journal disagree), and a detached retry
loop was left running for 45 minutes to land the row when the lock clears.

**Worth a separate look:** a 28 GB SQLite database with four writers and 57 open descriptors on the
authority is the underlying condition, and it is the same one behind the 3,322 `database is locked`
journalctl events recorded in the 7 days to 2026-09-16.
