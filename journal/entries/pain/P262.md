## P262 — P0: claim-publish commits a tree with zero entries; merging that lineage deleted the journal

P0 — the claim-publish path commits a tree with ZERO journal entries, and merging that lineage deletes the journal.

WHAT HAPPENED (2026-09-17)
`journal.py claim` is the new allocator's publish step (from 95fcd61: a machine may only write inside a
window it reserved). Running `claim` on ZABZ-YOGA produced commits whose TREES carry no entries:

 afbd9f3a "journal(alloc): ZABZ-YOGA publishes the reservation ledger" parent 95fcd611 (2,432 paths, 1,732 entries) -> own tree 1,178 paths, 0 entries
 7b301b9, 627e75ad — same shape

Those trees reached origin, and when I merged origin/master the merge adopted the entry-less tree
WHOLESALE: my merge commit 3661c7c tracked **2** entry files where the last good commit 68b6eef8 tracked
**1,735**. The push published it, so for several minutes master's real state was the mass deletion.
95fcd61's guard ("parent AND tree come from one immutable commit") did not stop it; the defect class is
the earlier 79efb088 one, now on master.

MEASURED, BEFORE THE RECOVERY
 git ls-tree -r --name-only 3661c7c -- journal/entries | wc -l -> 2
 git ls-tree -r --name-only 68b6eef8 -- journal/entries | wc -l -> 1735
 git ls-remote origin refs/heads/master -> 3661c7c

RECOVERY, DONE (non-destructive, by design)
 git diff --diff-filter=A --name-only 3661c7c 68b6eef8 > list -> 1,841 paths
 git restore --source=68b6eef8 --staged --worktree --pathspec-from-file=list
 commit + push -> 3661c7c..b13debc (fast-forward) counts 0 0
No force, no history rewrite, nothing destroyed, and the bad merge stays visible in history. Verified
after: 1,734 entries tracked and on disk, `journal/tools/journal.py` present again,
`journal.py check` -> 0 errors, `idguard.py` -> 0 collisions. Nothing was ever actually lost — every
entry also exists in 68b6eef8 and 95fcd61 — but a machine that pulled in that window would have been
reading an empty journal and believing it.

WHY IT IS P0, NOT A BUG
The journal is the continuity record of an autonomous system whose only memory is this tree. A commit
that removes it, published to the ref every machine fast-forwards from, is the single most destructive
state this repo can reach. It happened through a *routine* verb, on the machine the owner works on.

WHAT MUST CHANGE (in this order)
1. `claim` must not commit a tree at all: it should publish ONLY the ledger ref/blob (bands.tsv), or
 refuse if the tree it would commit differs from its parent's tree outside `journal/alloc/**`. The
 guard must be "the tree equals the parent's tree except for the ledger", not "the parent and tree
 came from one commit".
2. A pre-push guard on master: refuse to push any commit whose tree has fewer `journal/entries/**`
 paths than its first parent — a mass deletion of entries is never legitimate.
3. `scripts/autosync.ps1` must not fast-forward onto an entry count that dropped. It already reports
 behind/ahead; the entry count is the invariant worth checking.
4. `idguard` must say UNCOMPARABLE (and `--strict` must fail) when the far side has no index blob —
 a ref with a truncated tree yields an empty far side, and `idguard` printed `collisions: 0` for it.
 That is a refusal printed as health, and autosync wrote that 0 into `~/.dsh-sync-status/status.json`
 every 15 minutes as `id_collisions`. Workstream `agent/idguard-harden` found this and is fixing it.

EVIDENCE
- The three commit trees, the two ls-tree counts, and the ls-remote output above; the recovery push
 line `3661c7c..b13debc master -> master`; post-recovery `check` 0 errors and `idguard` 0 collisions.
- Found by workstream `agent/idguard-harden` from a read-only worktree, reported as a claim, and
 reproduced before acting on it.
