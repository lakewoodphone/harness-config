## P6322 — update_order() hardcodes the status-history reason, so every deliberate human status change is recorded in production as 'Auto-updated by secretary reconciliation (confidence: 0.95)'

**MEASURED 2026-10-14 in production.** `lpt-write status set --order WO26100812739 --status READY_FOR_PICKUP` writes the transition correctly but inserts `order_status_history.reason = 'Auto-updated by secretary reconciliation (confidence: 0.95)'` - **a hardcoded string in `update_order()` in `personal-secretary-mvp/app/services/website_db.py`.** The tool's own dry run says so plainly: *"that reason string is hardcoded in update_order. Your --reason text is recorded in the audit ledger only."*

**Why it matters:** the tool exists so that deliberate, human-instructed changes can be made from any machine, and every one of them is then recorded in production as an **automated reconciliation with a 0.95 confidence score**. Measured on this shop's own data: 419 orders sit at `READY_FOR_PICKUP`, 100 `UNFIXABLE`, 89 `CANCELLED` - every status change in the history carries that template. The row's `fromStatus`/`toStatus` are true; its **provenance is false**, and provenance is what a later session or a dispute would rely on to decide whether a human or a process made the call.

**What I did rather than leave the false row standing:** the status change was applied (it is real and correct), and a note was appended to the order stating that the history reason for it is wrong, what actually happened, and that `update_order()` hardcodes it. The audit ledger holds the true reason (seq 422).

**The fix:** `update_order()` should take a reason and pass it through; the hardcoded string should only be the default when the caller is genuinely an automated reconciliation. Until then, **any change made through this tool writes a false provenance into production**, and a session that trusts the history will attribute a human decision to a machine.
