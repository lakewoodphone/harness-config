## P52 — The sentinel and my own alarm disagree about the same quiet machine

**Symptom.** After `check-dsh-freshness.py` v2 learned to stop alarming on an idle host (L167), the sentinel's
own `session_archive` check still reports the same situation as a fault: *"session archive is not current: 13
session(s) last seen 2.1d ago; 9 session(s) last seen 2.2d ago; 80 session(s) last seen 3.2d ago"* — HIGH, every
5 minutes. Two alarms now describe one idle fleet, and one of them is wrong.

**Evidence.** Sentinel `latest.json` 2026-09-14T01:55Z, finding `session_archive`, severity HIGH;
`check-dsh-freshness.py` on the same host at the same moment reports `nothing unarchived`, rc=0.

**Cost.** The digest's section 0 says all quiet while section 0a says HIGH — a reader cannot tell which to
believe, and the correct response is to start ignoring both. This is precisely the failure mode that produced
the three competing dismissal schemes in `owner_message_queue` (P6): noise, then ad-hoc suppression, then no
signal at all.

**Fix (proposed).** Teach the sentinel's `session_archive` check the same distinction: alarm only when a
machine has **local work newer than its last shipment**, and report an idle machine as context. One definition
of "stale archive", used by both, or delete one of them — two definitions of the same fact is the P3 shape
(three copies of a database, none authoritative) applied to a metric.
