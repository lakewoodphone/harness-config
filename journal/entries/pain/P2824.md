## P2824 — MCP tool loss is silent and permanent: the secretary's 14 ps_* tools vanish from a live engine after ~20 s of transport churn

OBSERVED 2026-10-02 10:56 local, ZABZ-YOGA, web profile, engine 0.2.0-rc.2.

The GUI showed "Tools updated / 14 removed" and the whole mcp__secretary__* set
(ps_health, ps_db_query, ps_ceo_chat, ps_task_list, ...) was gone from the live session.

WHAT IS PROVEN (each with its source):
1. The tools were unregistered by the harness's own MCP supervisor, not by the
 secretary. @deepseek-ai/dsh-mcp-client/lib/index.js:567-574 - after
 `maxAttempts` (default 10) consecutive failed reconnects it disposes every tool
 registration and STOPS: "tools unregistered; reload the plugin or restart the Host
 to reconnect". Its module doc (line 428) says disposal - HMR or a Host restart -
 is the ONLY way back. There is no automatic recovery.
2. The server end is healthy. Reproduced the configured stdio transport by hand
 (same ssh argv as the profile row, to secretary-ts): initialize answered in 2.3 s
 with serverInfo personal-secretary 1.27.0, and tools/list returned the full tool
 set. The server was still alive afterwards.
3. A live transport existed the whole time: ssh.exe pid 23784 (parent = the web host
 pid 11176) created 10:55:37, with sshd-session[1137759] + ps_mcp_server pid
 1137809 on secratary from 14:55:38, STILL OPEN. So the harness holds an abandoned
 MCP session while believing the server is down.
4. `failOnStartupError: false` on the row (profiles/web/cordis.patch.yml, mcp-secretary)
 is why nothing was reported to the owner as an error.

WHAT IS NOT PROVEN: the trigger of the closing. The only stderr we have is from a
SECOND boot that failed on EADDRINUSE 127.0.0.1:3099 at 10:54:52
(~/.dsh/logs/startup-2026-10-02T14-54-52.742Z) and logged "mcp-client(secretary):
connection attempt failed: SdkError: Connection closed" five times before it died.
That process never activated plugins, so it is not what removed the owner's tools -
but two boots 36 s apart against one profile is the shape most likely to have closed
the live host's session.

WHY IT HURTS MORE THAN IT LOOKS: the time to give up is bounded, not unbounded -
0.5+1+2+4+8+16+30+30+30 = 121 s of delays, so roughly two minutes of any transport
trouble is enough to lose the tool set for the life of the Host. The owner then works
with a hand that is quietly missing its company interface, and only an owner-visible
restart fixes it.

WHAT WOULD FIX IT:
1. Raise `reconnect.maxAttempts` (and `maxDelayMs`) on every MCP row so a short
 outage cannot exhaust the budget (a policy fix, profiles/web/cordis.patch.yml).
2. Notice the failure: the give-up is a ctx.logger.error that no one reads. It must
 surface as an owner-visible system message instead of / in addition to a tool
 removal.
3. A recovery path that does not need a full Host restart - an HMR/plugin reload
 trigger reachable from the agent itself.
4. Stop dual boots: the launcher has an ensure mutex (dshw.ps1 "ensure"), yet a second
 boot ran 36 s after the first and died on the port.
