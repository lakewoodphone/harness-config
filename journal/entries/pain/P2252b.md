## P2252b — Owner SMS sends leave no sms_log row, so the 3/day owner cap is inert

P — Owner SMS sends leave no audit row, so the 3/day cap cannot see them.

OBSERVED 2026-09-23, on the authority (`~/personal-secretary-mvp/data/secretary.db`
on secratary):
- journalctl: `INFO app.sms_service: SMS sent: SID=SM7bbd01e591b3cbbb62e0133c72382a1e
 to=+17325691594 status=queued segments=2` at 2026-09-23T00:36:52Z, plus a 201 from
 the Twilio API in the same second.
- `select count(*) from sms_log where created_at >= '2026-09-23'` = 0. Highest row id
 is 903, dated 2026-09-22T18:48Z.
- `sms_service.send_message` is wrapped by `@_audited_send`, whose docstring says it
 "guarantee[s] exactly one `sms_log` row for every `send_message` call".

WHY IT MATTERS: the owner daily quota is `SELECT COUNT(*) FROM sms_log WHERE
direction='outbound' AND to_number=? AND date(created_at)=?` compared against 3
(sms_service.py ~line 995). Sends that never land in `sms_log` are never counted, so
the cap is inert — the journal shows 11 SMS to the owner on 2026-09-22 alone, nearly
4x the cap.

STATUS: root cause not yet established. Mesh subagent job `subagent-95` owns the
investigation (file-partitioned to `app/sms_service.py`). Anything reported must be
reproduced against the live DB; a "guarantee" in a docstring is not evidence.

WOULD FIX IT: whatever the subagent finds (a path returning before the audit write,
or a swallowed exception), plus a test that asserts exactly one row per send attempt
including suppressed-by-policy ones.
