## P203 — CVE-2026-11822: FTS5 memory corruption in SQLite 3.49.1 (Yoga) and 3.46.1 (secratary); fixed in 3.53.2

**Both hosts run an SQLite with a known FTS5 memory-corruption CVE. Not exploitable here, but tracked.**

CVE-2026-11822 (CVSS 3.1 7.8 High): SQLite before 3.53.2 has memory-corruption bugs in the **FTS5**
extension — an out-of-bounds read in `fts5LeafSeek()` via an attacker-controlled loop bound, and a
heap buffer overflow write in `fts5ChunkIterate()` through a crafted continuation page. It is
exploitable when an **FTS5 MATCH query runs against a malicious database**.

Measured versions: **ZABZ-YOGA 3.49.1** (bundled with Python 3.12.10), **secratary 3.46.1**. Both
are below the fixed 3.53.2.

**Why this is not urgent here:** the only FTS5 databases the fleet searches are ones it built itself
from its own corpora. There is no path by which a third party supplies a database file. The threat
model is a supply-chain or a "search this file someone sent me" feature, neither of which exists.

**Why it is still recorded:** the fix is cheap and permanent — ship a SQLite >= 3.53.2, whose
official Windows x64 DLLs exist — and the whole search system is now built on FTS5, so the blast
radius of a future "let's index a file a customer sent" idea is large. Anyone reading this who is
considering indexing untrusted data must upgrade SQLite first.

**Separate and also mandatory:** the WAL-reset corruption bug spans 3.7.0 -> 3.51.2 (fixed 3.51.3)
and needs **two concurrent writer/checkpointer connections on one file** to bite. Rule for this
system regardless of version: **one writer connection per index database.** The adapters and
`usearch.py add` are the only writers; queries are read-only. Do not point a second writer at
`~/.usearch/index.db`.

Fix, when someone has the time: replace the bundled `sqlite3` DLL / use a Python whose `sqlite3`
module links 3.53.2+, verify with `python -c "import sqlite3;print(sqlite3.sqlite_version)"`, then
re-run `usearch.py check` on both hosts.
