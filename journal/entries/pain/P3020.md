## P3020 — Two agents edited one production dialpad script and the original is unrecoverable - and the cloudfix backup proves it by having the wrong mtime

Coordinator round 25, 2026-10-11 ~21:30Z. The dialpad pair: a concurrent editor, an unrecoverable original,
and an edit that fixed nothing.

`156-DIALPAD-GAP-TWO-JOBS.md` (child `20`, 374 lines) establishes three things that matter more than the
original traceback:

1. **A CONCURRENT WRITER IS ON THE SAME FILES.** A workstream calling itself **`cloudfix`** replaced
 `/opt/company/scripts/dialpad-recording-gap.py` and `dialpad-transcript-gap.py` at **21:13:30Z** -
 seven minutes before this child started - leaving a backup dir
 `/root/backups/cloudfix-20261011T211332Z/` with a crontab pair and both scripts.
2. **THE PRE-EDIT CONTENT IS NOT PRESERVED.** The scripts the cloudfix backup saved are dated
 **2026-10-07 16:07**, owner `1000:1000` - a *staged* pair, not the pair that was live in
 `/opt/company/scripts` at 21:12:59Z. So **the file that was actually failing before the edit exists
 nowhere that the child could find.** That is a finding in its own right: an edit was made to a
 production script without preserving what it replaced.
3. **THE EDIT DID NOT FIX ANYTHING.** After it, both jobs still fail. The traceback moved from line
 **199 to 224** - it is tracking the new file and failing at **the same code path**. Same failure,
 different line number, which is the classic shape of an edit that changed cosmetics rather than cause.

**MY CHILD REFUSED TO OVERWRITE, AND THAT WAS RIGHT.** It says so plainly - *"I will not overwrite either
file until I can show the cloudfix workstream is done"* - and it went on diagnosing instead. Two agents
editing one production script is how the second one destroys the first one's work; this is the third
collision of the session (`route.sh`, `AGENTS.md` on main, and now these two scripts), and the first one
where the agent on the receiving end could see it coming and stood down.

WHAT THIS MEANS FOR THE COORDINATOR
- **These two jobs now have two owners and one unrecoverable original.** Do not dispatch a third. Either
 find and talk to the `cloudfix` workstream or wait for it to finish; until then the correct move is
 read-only diagnosis, which is what the child is doing.
- **The unrecoverable original is the real damage here, not the failing job.** The failure was benign -
 these are gap-filler jobs that retry. Losing the pre-edit script while chasing a traceback is the kind
 of thing that turns a small problem into an archaeology exercise.
- **A rule worth adding to the estate's practice: never edit a production script without first copying it
 to a path named for what it was** (`<file>.pre-<what>-<stamp>`), and never accept a backup whose
 mtime does not match the moment of the edit. The cloudfix backup passes neither test.

FOR THE NEXT SESSION: check whether a `cloudfix` workstream artifact exists in `/root/out/migration-review/`
or in root's shell history on the cloud box, then decide one owner. Do not port or edit these two scripts
until that is settled.
