## P2877 — lpt: the publishable key had three disagreeing sources, and two deploy tests could never pass

lpt/phone-and-tech-full: publishable keys were wired in three places that disagreed, and two tests could never pass.

FOUND 2026-10-08 while splitting the Stripe keys per environment. Four distinct hurts,
each with the fix.

1. THE PUBLISHABLE KEY HAD THREE SOURCES AND THEY DISAGREED. The Cloudflare frontend
 build env had none; the recorded production backend env had pk_test_ next to a
 live secret; scripts/lib/frontend-deploy-config.mjs had none for production. Fix
 (done, branch lpt/w8-keys-20261008): each target's key lives in BASE_ENV, the
 target decides the mode, and the deploy refuses a mismatch. Also: the owner should
 know that the BACKEND carries its own STRIPE_PUBLISHABLE_KEY, separate from the
 frontend's VITE_STRIPE_PUBLISHABLE_KEY - two variables that can silently disagree
 and neither refuses. Nothing yet cross-checks backend against frontend.

2. TWO ASSERTIONS IN scripts/test-deploy-metadata.mjs COULD NEVER PASS. They scanned
 frontend-deploy-config.mjs for a quoted 'main' while also requiring
 BRANCH_LABELS.production !== 'main'. The label is DEFINED in that file, so any
 correct definition contains the literal. Red on origin/test before this work
 (31 passed / 2 failed). Rewritten to assert the property actually wanted. A check
 that cannot pass is worse than no check: it teaches everyone to ignore the suite.

3. process.env.REACT_APP_STRIPE_PUBLISHABLE_KEY IS DEAD IN A VITE APP.
 frontend/src/features/customer-portal/components/PaymentLink.tsx:19 and
 CustomerPayment.tsx:22 read it. vite.config.ts defines only process.env.NODE_ENV
 and process.env.VITE_API_URL, so this is never set; the string does not even
 survive into the built bundle (0 occurrences measured in the deployed test asset
 index-CYzifynZ.js). Those two components therefore always get an empty key and can
 never draw card fields. NOT FIXED (out of this job's scope and outside the
 counter-sale surface the owner reported). Fix: read loadEnv().STRIPE_PUBLISHABLE_KEY
 like PaymentMethodManager.tsx already does. This is a DIFFERENT defect from the
 per-environment split and needs its own build/test/deploy.

4. frontend/src/features/payments/context/StripeContext.tsx:106 FALLS BACK TO
 'pk_test_default' WHEN NO KEY IS SET. Not a valid key and not a valid mode; it
 means a production bundle can carry a pk_test_ literal. It is why the new bundle
 assertion requires a real key body rather than any pk_test_ substring. Left in
 place; harmless today, a trap for a future guard author.

WHAT WOULD FIX THE CLASS: one place that owns the Stripe mode per environment, read by
frontend build, backend runtime, and webhook config alike, with the pair checked at
deploy. Today each layer is consistent on its own and nothing checks across them.
