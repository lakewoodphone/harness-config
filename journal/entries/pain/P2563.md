## P — Every automated guard in kosher-filter-ai has been red on main for ten days, and nothing surfaced it

**Measured 2026-09-28 from ZABZ-YOGA with the GitHub CLI against `lakewoodphone/kosher-filter-ai`.**
`main` had not moved since 2026-09-18, and the last two pushes to it **both failed their own CI**:

```

completed failure Server CI main push 35023056531 12m20s 2026-09-15T21:00:34Z
... eight more, back to 2026-09-15T19:51

$ gh run list --repo lakewoodphone/kosher-filter-ai --workflow android-ci.yml --branch main --limit 6
completed failure merge: the Android tree now matches its packages (238 renames…) 35018288827 2026-09-15T20:13:16Z
completed failure chore(security): refresh the sign-off snapshot… 35013382508 2026-09-15T19:23:56Z

completed success compliance C-9: the phone now scrubs the frame before it leaves… 34815682763 2026-09-14T06:58:03Z
```

So both divisions went red on **2026-09-15** and stayed red: **13 days** for Android, **10 days** for
the server, with nothing anywhere reporting it.

**What was actually broken, from the run logs.**
- `android-unit-tests` — `InferenceTelemetryEmitterTest.flushIsBoundedByBatchSize` fails at
 `InferenceTelemetryEmitterTest.kt:106`; the run recorded `461 tests completed, 1 failed`. Reproduced
 locally on 2026-09-28: the test was the wrong side, not the code (see the accompanying entry).
- `postgres-runtime-tests` — **18 failed, 10 passed in 6.05 s**, of which **fifteen are one cause**:
 `alembic.util.exc.CommandError: The script directory has multiple heads (due to branching)` — two
 branches each added a migration and were merged without an `alembic merge`. Plus a separate drift:
 `test_postgres_storage_parity_audit_matches_surface` → `assert 283 == 279`.
- `server-tests` — a stale security-audit **SQL-surface snapshot** (a `422 | Validation Error |
 application/json` row diff), which this repo has regenerated twice before with a documented script.

**Why nobody noticed, and this is the part worth fixing.** Nothing in the session-start ritual reads
CI status, even though `gh` is installed and authenticated on this machine. The one workflow that HAS
been green every ~2.5 hours throughout is **Broker Monitor** — and that is precisely the trap: a
green light existed, it just measured a different thing (the broker's `/health` endpoint, not the
code), so the fleet's "is it healthy" sense was satisfied while both code guards were screaming.

**What would fix it.** One line in the wake/outcome path and at the top of substantial work:
`gh run list --repo lakewoodphone/kosher-filter-ai --branch main --status failure --limit 5`.
A red run on the trunk is the cheapest possible early warning and the most expensive thing to ignore;
it should be surfaced the same way a failing health check is. Until it is automated, it is a manual
step, which is the same "only if you look" weakness that made this last ten days.

**Evidence.** The two `gh run list` outputs above (verbatim), `gh run view 35305290066 --log-failed`
for the alembic and parity failures, and `gh run view 35018288827 --log-failed` for the Android test.
