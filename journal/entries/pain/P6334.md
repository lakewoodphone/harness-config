## P6334 — The journal cannot be consolidated: 59 ids mean two different entries, all minted today, because id allocation is unsafe across machines

The journal cannot be consolidated because its id allocation is not safe across machines, and it is diverging again right now, faster than it can be unioned.

Measured 2026-10-14 ~12:20Z, from ZABZ-YOGA, with the repo's own tool:

 python journal/tools/journal-union.py --remote secratary-cloud
 REFUSING: 59 id(s) exist on BOTH sides with DIFFERENT content.
 decisions/D3147.md … decisions/D3150.md
 handoff/H3626.md … H3641.md (and 38 more)
 secratary-cloud:/root/code/harness-config/journal/entries 4037 entries
 C:\Users\ezabz\code\harness-config/journal/entries 4050 entries
 only there : 18 only here : 31 both : 4019
 exit 3

**The refusal is correct and must not be worked around.** An id that means two different entries is not a merge problem, it is a corruption, and picking a winner by hand is exactly how one id comes to mean two things. `journal.py repair-ids` is the tool for it.

**Four journals exist, and none of them is the same record:**

| tree | entries |
|---|---:|
| ZABZ-YOGA (this laptop) | **4051** |
| secratary-cloud `/home/zabz/code/harness-config` | 4037 |
| ZABZ-TECH (Windows desktop) | 3907 |
| zabz-tech-linux | **3440** |

Measured by mesh child subagent-13 with `find journal/entries/<kind> -maxdepth 1 -name '*.md' | wc -l`, per kind. Authority vs zabz-tech-linux is a strict superset (597 only-authority, **0** only-linux). Authority vs ZABZ-TECH is genuinely divergent (371 only-authority, 241 only-ZABZ-TECH, **204 same-id-different-content**). Union of the three reachable trees = 4278, and this laptop is not among them.

**Root cause, named:** two sessions on two machines minted the same ids for different content. Everything in the collision list is from **today** — D3147–D3150 are today's decisions and H3626–H3641 are today's handoffs — so the allocator is diverging at the rate sessions write, not from some historical accident. `journal-union.py`'s own docstring records the identical failure on 2026-10-13: the trees were unioned by hand twice, "verified identical — 3,819 entries and 401 open pain on both trees. Hours later they were **13 entries apart again**, because both trees write and nothing moves entries between them."

**Consequences that have already bitten:**
- **Every count of the journal is tree-relative.** "Open pain" was 344, 437, 453 and 568 depending on which tree answered, and all four numbers were right. `status` on this laptop says 4,050 entries; the authority says 4,037.
- **`idguard` reports 0 collisions while 202 exist in working trees** — it compares generated indexes in refs, not working trees. A guard that answers about the wrong artifact is the same failure as a frozen database answering a question about now.
- Mesh children dispatched to read "the journal" land on the authority's 3,440-entry copy (zabz-tech-linux) or the 3,907-entry desktop copy and report a different history with full confidence. One did, in this session, and its "344 open pain" was correct for its tree and wrong for the record.

**The fix is allocation, not union.** A union run repeatedly is a treadmill. Required: (a) ids allocated from ONE authority, or a claimed id BAND per machine per session, so two machines cannot mint the same id — `journal.py` already ships `claim` and `next-id` subcommands and they are evidently not being used cross-machine; (b) `idguard` pointed at working trees, not refs; (c) `journal-union.py` and `repair-ids` run on a schedule by one owner, not by hand when someone notices; (d) the same treatment as the instruction surface — this is `P3178`'s shape in a second system, and two "no single source of truth" defects in one estate is a pattern, not two accidents.

**Not done, deliberately:** the union was NOT executed. Forcing it would have created 59 entries that mean two things. The collisions must be repaired first, and repairing them is a decision about which of two genuinely different entries keeps the id — that work belongs to a session that can read both versions, with the union tool's dry run in front of it.
