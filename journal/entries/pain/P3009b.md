## P3009b — The duplicate marker is not on this box: 2,099 marks with no reviewable rule behind them

2026-10-13. The code that marked 2,099 rows as duplicates is NOT ON THIS BOX, so the marks cannot be
reviewed where they live, let alone corrected by rule.

WHAT I WENT LOOKING FOR, and did not find. Two tools exist for this job and both are live:
 /opt/company/scripts/finance/audit/dedup-same-source.py
 /opt/company/scripts/finance/audit/dedup-cross-source.py
and NEITHER can produce an opposite-sign mark, because both key on direction:
 key = (account_id, transaction_date, abs(amount_cents), direction, source_system) # same-source
 key = (account_id, transaction_date, abs(amount_cents), direction) # cross-source
A credit and a debit of one amount can never land in the same group under either key. So the 196
opposite-sign pairs came from some other writer. I grepped /root/bin, /opt/company/app,
/opt/company/scripts, /opt/lpt-ops and harness-config for anything that both names
`duplicate_of_transaction_id` and issues an `UPDATE transactions` - the only hits were those two audit
scripts, plus copies of them inside fleet working directories. **The writer is not here.** It ran
somewhere else, or once, and left 2,099 marks behind it.

WHAT THE MARKS LOOK LIKE FROM THE DATA SIDE:
 ingestion_status: active 6,155 | duplicate 2,099 | archived 517 | migrated 6
 duplicate-marked rows by status: duplicate 1,999 | archived 117 | ACTIVE 66 | migrated 4
 source_system of the marked rows: Chase Credit Card CSV 773 | Heuristic CSV Profile 742 |
 Generic Three Column CSV 160 | legacy-json 140 | American Express CSV 134 |
 Bank of America Stmtpipe 101 | Chase Checking CSV 45 | plaid-api 36
So the marks came from CSV ingestion. Two things there are worth someone's attention and neither is
mine to decide: **66 rows are `ingestion_status='active'` AND carry a duplicate mark**, which is at best
an inconsistent pair of fields; and **100 rows are `ingestion_status='duplicate'` with NO mark at all**,
so the status and the pointer disagree in both directions.

WHAT THIS CHANGES ABOUT THE EARLIER FINDING. L3669 concluded that 12 of the 196 opposite-sign marks are
demonstrably wrong - `Payment to X` on one account and `Refund to X` on another, which are two movements
and not one event recorded twice, 2,363.97 in total. That conclusion stands on the descriptions
themselves and does not depend on knowing the writer. **What changes is the remedy**: I had proposed a
narrow detector rule, and a rule cannot be added to code that is not on the machine. So the twelve are a
DATA correction, not a code fix - and a data correction to the duplicate pointer is a write to the
ledger that no sanctioned writer currently covers, which is why I have not made it. It belongs with the
same kind of decision as the 66 active-with-a-mark rows: somebody should decide what the two fields
mean together before either is edited.

AND ONE THING THIS SETTLES FOR THE RECONCILIATION. The duplicate graph is not derivable on this
machine. Any future attempt to explain the 55,319.21 by re-running deduplication will re-run a rule that
is not the rule that produced the marks.
