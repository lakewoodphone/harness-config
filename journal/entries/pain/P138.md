## P138 — The budget extension tripled the cost of a failure without changing the outcome (task 25106: 15 steps, still failed)

PAIN: the extension tripled the cost of a failure without changing the outcome

EVIDENCE, secratary 2026-09-14/15, session 75415, task #25106 "File PayPal
item-not-received dispute for Global Direct Parts order 161898". The budget extension
(committed e6a28a6b) fired repeatedly and correctly:

 total_steps 5 -> 8 -> 11 -> 14 -> 15 (the absolute cap)
 steps taken 5 -> 7 -> 8 -> 10 -> 11 -> 12 -> 14 -> 15
 outcome: FAILED at 15/15, and session 75416 was created for the same task immediately.

Before the extension this shape cost 5 steps and failed. Now it costs 15 and fails. The
extension is verified working MECHANICALLY (75414 failed at 5/5 with ext=0; 75415 was
extended), but for this task it bought no outcome, only 3x the spend. 143 of 222 failures
in the previous 24h were this budget, so multiplying that by three is a real cost.

WHY, and what I now think is wrong with my own progress test: `_maybe_extend_work_session_budget`
extends when the last three steps contain ANY non-read-only action. A session can call
update_task, save_memory and schedule_reminder forever without changing the task -- those
are mutating verbs, so they satisfy the test while advancing nothing. "Took an action" is
not "made progress", and I conflated them.

WHAT THE PATTERN SUGGESTS, across three tasks in one night (#25105 pay a duty, #25106 file
a dispute, #25118 check CI/CD): the tasks that spin are the ones needing either owner
authority or an external system the agent cannot reach. #25105 called ask_owner in step 2
and was failed for it; #25118 tried to close itself twice and the task stayed open. So the
terminal states exist but are not being reached, and no amount of extra budget fixes a
missing terminal state.

WHAT TO DO NEXT (in order, and only one at a time):
 1. Bound the extension: cap the number of extensions per session (2 is enough to cross
 a genuine 5-step boundary) so the worst case is 11, not 15. Measure the failure mix
 before and after; if outcomes do not improve, more extension is pure cost.
 2. Replace the progress test for the SECOND and later extensions with "the session
 produced a new effect", not "it called a mutating tool" -- e.g. the task's own row
 changed, or a new artefact appeared. Otherwise update_task loops qualify.
 3. Then the retry ceiling: a task that has failed N times with the same terminal reason
 should not be re-claimed and re-run from scratch. #25106 has now been attempted five
 times (75405, 75406, 75407, 75415, 75416).

DO NOT claim the budget extension improved outcomes. It improved elapsed opportunity and
is verified only mechanically.
