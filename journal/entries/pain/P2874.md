## P2874 — ZABZ-TECH's 15-minute sync never converges: its version guard reads a transient npx probe as the running engine

The 15-minute PersonalSecretary-HarnessSync on ZABZ-TECH still SKIPS its presets and profile steps
after the machine was fixed, naming engine 0.1.5-rc.1 -- so that machine's agent presets and profile
patch layers do not converge from the repo.

WHAT IT HURTS: the machine boots, but repo-side changes to `presets/*` and `profiles/*` never reach
it, and the skip says nothing about the machine being frozen. It has been skipping since at least
2026-10-05T00:50:37Z (autosync.log), i.e. it outlived the outage it was guarding against.

THE MEASUREMENT THAT CONTRADICTS ITSELF. Run by hand on that same machine, the same checker resolves
the right engine -- `"engineResolvedBy": "running-process", "enginePid": 30396,
"engineVersion": "0.2.0-rc.2", "status": "ok", "missing": []` -- and a 60-second poll of every
node.exe on the host found exactly ONE process whose argv[1] is a `.../dsh/lib/bin.js`. The task's own
log line at 14:26:26Z says `the running engine (0.1.5-rc.1) does not provide`, with NO `WARNING --`
suffix, which the checker only produces when it believes a RUNNING PROCESS from the 0.1.5 root and
finds no configured conflict.

THE SUSPECT, WITH THE CODE THAT SUPPORTS IT: `scripts/profile-gate.mjs` (task "DSH Profile Gate (15m)",
the same cadence as the sync) probes candidate pairs by executing `node <bin> -V`, and its
`binCandidates()` list does NOT include `~/.dsh/engine` -- it tries `~/dsh-engine`, `~/profiles`,
`~/dsh`, then the npx cache, which on Windows resolves to the 0.1.5 install. The guard reads the LIVE
process table, so a transient `-V` child from the wrong root is a candidate to be read as "the engine
running here".

WHAT WOULD FIX IT: add `~/.dsh/engine` (and, on POSIX, `~/dsh-current`) to profile-gate's candidate
list FIRST, so nothing on the machine spawns the stale npx engine at all -- preferred over loosening
the guard, which exists to stop exactly this class of mistake. Then capture the guard's --json FROM THE
TASK'S OWN CONTEXT (a one-shot scheduled task writing to a file) to confirm, and re-run the sync.
