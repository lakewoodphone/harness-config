## P3155 — Stripe dead on the authority since the 2026-10-11 cutover: 1031.86 USD of charges beyond the ledger, and no stripe package installed to fix it with

## What hurts, ranked, with what would fix it

### 1. Stripe has been dead on the authority since the 2026-10-11 cutover, and by 2026-10-13 that was 1031.86 USD of missing revenue

Measured 2026-10-13 by read-only query (`probe_stripe_gap.py`, `GET` only):

- `scripts/finance/sync-stripe.py` is the sole writer of the `lpt-stripe` ledger rows — every
 one carries `source_document_id='stripe-api-ingest'`, the value that script stamps.
- It is scheduled **nowhere** on `secratary-cloud`: not the crontab, not a systemd timer, not an
 autopilot subsystem. The only thing that ran it was step 4 of the office box's
 `nightly-plaid-sync.sh`, and that box is a frozen read-only anchor since the cutover; its log
 stops at `2026-10-10T04:30:31Z`.
- 7 charges exist in Stripe created **after** the ledger's newest Stripe row: 40.00 + 2.00 +
 15.99 + 79.97 + 5.33 + 58.64 + 829.93 = **1031.86 USD**. Newest 2026-10-12T23:19:51Z. Refunds
 are ~7 weeks behind (ledger newest 2026-09-23).

**Blocker, also measured:** the `stripe` python package is installed **nowhere** on the cloud —
`/opt/company/.venv/bin/python -c "import stripe"` -> `ModuleNotFoundError`, `pip list` has no
stripe, and `find / -name stripe -type d -path "*site-packages*"` returns nothing. The office box
had it. So `sync-stripe.py` cannot run here at all until it is installed, and installing a package
is the manager's, not a fleet worker's.

**Fix, delivered not applied:** `/usr/local/bin/stripe-sync.sh` + a `cron-wrap` cron line at
`40 4 * * *`, in `/root/finance-fleet-20261013/money-clock/install/`, plus
`/opt/company/.venv/bin/python -m pip install stripe`.

### 2. Four pull lanes are dead on the authority with the same one-line cause

`paypal_sync`, `amazon_sync`, `ebay_sync` all record
`last_status='failed' consecutive_failures=2` with
`error='quickbooks-agent repo not found at /opt/company/domains/finance/quickbooks-agent'`.
Their ledger rows still look recent (2.9-5.9 days) because the **office** box fed them until
2026-10-10, so age alone cannot see it — this is why `finance-freshness` needs a pull axis.

Amazon/eBay ingest was explicitly a sibling's scope in this fleet, so I did not fix it. Something
must: it is one missing checkout at `/opt/company/domains/finance/quickbooks-agent`.

### 3. Three-three sources are 68-210 days behind and nothing said so

`lpt_twilio` 68.2 days (limit 45), `lpt_openai` 122.2 days (limit 45),
`quickbooks_support_cash` 210.4 days (limit 45), `lpt_amazon` 68.1 days (limit 14). Twilio and
OpenAI are "monthly vendor invoice capture" lanes with **no writer script anywhere** in
`app/` or `scripts/` — the only references to `twilio-billing` / `openai-billing` are the registry
and the analytics config. They are manual captures that stopped, and nobody noticed for months.

### 4. `app/services/stripe_service.py` is also broken

It does `import stripe` lazily, so it too dies on the same missing package. Fixing the package
fixes both.

### 5. `guard-registry-check.py` cannot admit a new guard without an owner-approval record

`guards.yaml` is sha256-pinned and changing it requires a record naming a real
`owner_decision_queue` row. That is a good design, and it means a new check has to ride a
different surface (cron + the wake-flag store) unless the owner is asked. Worth knowing before
designing the next guard.
