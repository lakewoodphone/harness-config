## P254 — laptopscreen.com - the shop's laptop-screen supplier - returns HTTP 200 with an EMPTY body to every machine on the shop and home networks, so no screen order can be placed from a browser

WHAT HURTS: from 2026-09-17 the shop CANNOT LOAD laptopscreen.com — its laptop-screen supplier — on any of its own
networks. Every request returns HTTP 200 with a ZERO-BYTE body. The owner discovered it in Chrome; it is not the
browser. This blocks every future laptop screen order, not just the one case that surfaced it.
EVIDENCE (measured 2026-09-17 by me):
 - A real Chromium on ZABZ-TECH navigates the URL, the network log shows [200], and document.body.innerHTML is
 0 characters with an empty title. So a genuine browser gets an empty document.
 - curl on ZABZ-TECH (Windows/schannel), on secratary (Linux, office LAN) and on the home laptop: all
 http_code=200 size_download=0.
 - Headers are the ORIGIN's own: Set-Cookie PHPSESSID, X-Powered-By PleskLin, Content-Type text/html,
 Transfer-Encoding chunked, Cache-Control no-store, cf-cache-status DYNAMIC, CF-RAY ...-EWR, Server cloudflare.
 So the request reaches Cloudflare and Cloudflare reaches the origin; the BODY is what is missing.
 - Ruled out: DNS (router resolver, 8.8.8.8 and 1.1.1.1 all return the same Cloudflare IPs), hosts file,
 proxy settings (direct, no proxy), TLS interception (no filtering root CA, real Cloudflare cert), browser
 extensions (a clean Chromium fails identically), and request shape (browser UA, Accept-Encoding, Referer,
 cookie jar, forced TLS1.2, HTTP/1.0, and a different page on the same site all gave 200/0).
 - From OUTSIDE those networks the same URL returns the full page: lpt-apps VPS 200 / 133,786 bytes. A Hetzner
 VPS gets 403 / 5,672 bytes (Cloudflare bot block) — so it is per-IP policy, not a site outage.
 - The shop paid laptopscreen.com order #1789406689 on 2026-09-14. It worked four days ago, so this broke
 between 09-14 and 09-17.
WHAT WOULD FIX IT: (a) immediate — order by phone, 1-855-630-1111, with the item IDs; (b) a browser tunnel out
through a machine that is not refused (`ssh -N -D 1080 lpt-apps` + Chrome against socks5://127.0.0.1:1080);
(c) find out whose IP is being refused and why — the shop's public IP is 71.104.140.242 (Comcast), the home
network is refused too, which suggests a range-level Cloudflare policy or a reputation hit rather than one IP;
a site-side cause is worth an email to the supplier, since they are a 65%-repeat-customer business and losing a
repair shop to a silent empty response is not deliberate. RE-TEST before concluding: a 200 with an empty body is
exactly the shape that also looks like a transient.
DO NOT treat this as "that site is down" - it is up and serving everyone else, and a future session that assumes
an outage will waste the same hour I just spent.
