## P2993 — The E4610 phone-leak gate (ready-e4610.ps1) shipped untested and died on its first real use

# The phone-leak gate shipped untested, and its first real run died immediately

`lpt-flip-phone/scripts/deployment/ready-e4610.ps1` was written 2026-09-18 for one reason: two
E4610s (615765621 on 09-17, 615291677 on 09-18) left the bench staged-but-not-finalized, so customers
kept the apps and lost the lockdown, blaster/launcher, wallpaper and the 15-check verify. The wrapper
was supposed to make that impossible ("prints READY only if all of it succeeded").

**Its first real use was 2026-10-08 on serial 616462586, in front of the owner, and it failed at the
first line of real work** — its adb helper declared `param([string[]]$Args)`, which never binds, so it
read adb's own help text as the device model and aborted. Every guard rail it was built from
(Tech Mode recovery proof, MatVT key = 17, Voice Access prefs assert, READY-only-on-success) had
therefore **never executed against a handset**. The tool that existed to stop a class of leak was
itself the broken thing, and no receipt, test, or note had ever shown it working.

**What would fix it (and the general case).**
- A wrapper whose entire value is "it only says READY when everything really passed" needs one
 recorded end-to-end run on hardware before it is trusted. Commit message + self-test on saved UI
 dumps is not that: the self-test covered the XML parsing, not the ADB plumbing.
- Cheap detector for this exact class: extract the helper function by AST from the shipped file and
 call it live, asserting a known device answer (`getprop ro.product.model` -> `E4610`). Anything
 that returns adb help, `null` or empty is a dead wrapper. That check takes one second and would
 have caught this before the owner did.
- Generalisation: **a script that shells out is not tested by its own dry-run.** The dry-run in this
 wrapper only printed a plan and exited before any adb call, so it passed while the tool was dead.
- Second-order: the two phones that leaked also produced `staged` receipts and nobody read them.
 A release-gate tool is worthless if the receipt state it writes is not the thing someone checks
 before handing over — the gate has to be the handover step, not an optional script.

Evidence: `logs/ready-616462586-20261008-112620.log` (the failure), the fix and live bind proof in
that same file's repo (helper now returns `E4610`), `docs/deployment/PREFILTERED-DEVICE-AND-E4610-MANUAL-STEPS-RUNBOOK.md`
§4 for the two leak cases.
