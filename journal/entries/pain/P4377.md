## P4377 — The authority's lpt-hub corpus is a stale clone and its documented path does not exist here

**The case corpus the authority's own tools read is a stale clone, and the path the tooling
documents does not exist on this box.**

Measured 2026-10-15 while looking up a customer (Pantoja, 732-890-7527) and before trusting a
negative:

- `/home/zabz/phone/lpt-hub` is a real clone and `tools/case-index/lptcase.py` runs from it.
 `git rev-list --left-right --count origin/main...HEAD` → **80 behind, 5 ahead**. The tool says so
 itself in its banner: "CORPUS IS STALE: this clone is 60 commit(s) BEHIND origin/main" and
 "UNPUSHED WORK: this clone is 4 commit(s) AHEAD".
- The harness-config refresh script documents the authority's clone as `/home/zabz/repos/lpt-hub`
 (its `LPT_HUB_REPO` default), and the sync service's docstring names a `/home/zabz/lpt-hub`
 symlink. **Neither path exists on secratary-cloud** (`ls -d` → No such file or directory), while
 the app directory the write tooling uses is `/home/zabz/personal-secretary-mvp`.
- Consequence: a case lookup from this box answers from a corpus 80 commits old, and `lptcase
 check`'s "FAILED - 3 structural problem class(es)" counts artifacts of the stale base (222
 sync-record-without-case, 99 case-without-sync-record, 21 duplicate-phone) as if they were
 current defects. **A negative lookup here is not evidence of absence** — production and
 origin/main have to be asked separately, which is what this session did.

What would fix it: point `LPT_HUB_REPO` / the service's `LPT_HUB_LOCAL_REPO_PATH` at the clone that
actually exists, then refresh it with the refresh script's rebase path — not a `git add -A` and not
a `reset --hard`, because that working tree carries **1381 unstaged deletions** belonging to another
session, and this session's case work was pushed from a temporary worktree off `origin/main` for
exactly that reason.
