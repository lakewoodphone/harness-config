## P2539b — A policy denial files a task nobody can act on: an owner-approved customer SMS still cannot be sent

**P · 2026-09-25 · ZABZ-YOGA — A policy denial files a task nobody can act on: the approval has no release valve, so an owner-approved action still cannot be executed**

**What hurts.** On 2026-09-25 the owner approved an exact customer text in conversation — *"Hi, quick update on your SSD - it's at the lab and in their repair queue now, work is underway. I'll come back to you as soon as I have a result."* — and the send was refused:

```
send_sms -> {"ok": false, "detail": "Policy denied: requires owner approval - task #26815",
 "policy_reason": "requires owner approval", "policy_tier": "critical"}
```

Measured consequences, in order:
1. **The override does not apply, by design.** `app/policy.py:81` defines Dialpad customer SMS with
 `approval_respects_unsafe_override=False`, so passing `unsafe_ok` cannot clear it. That is the right
 default — a customer text on the shop line should not be bypassable by the caller — but it means the
 *only* way through is an owner approval, and that path has to exist.
2. **The denial created a task, not an approvable item.** `action_approval_queue` — the table behind
 `GET /action-approvals` and `POST /action-approvals/{id}/approve` — is **empty**, `pending = 0`. The
 denial wrote `tasks` row **26815** (`APPROVAL: send_sms`, tags `["approval","policy","send_sms"]`,
 status `open`) and nothing consumes it: there is no retry, no queue entry, no endpoint that turns
 that task into a permission. The owner has nothing to tap.
3. **So the gate is one-way.** An owner who wants an approved action to happen has to either perform it
 by hand or turn the gate off — and turning off `dialpad_customer_sms_requires_owner_approval` removes
 the control for *every* future send. A safety control whose only release is its own removal is not a
 control; it is a wall.

**What would fix it.**
1. **One queue, written by every denial.** A policy denial should insert an `action_approval_queue` row
 carrying the action name, the exact parameters (here: recipient and body) and the requiring policy —
 in addition to the task, not instead of it.
2. **A retry that consumes the approval once.** `POST /action-approvals/{id}/approve` should mark the row
 approved, record who approved it, then execute the stored action **once** and store the result on the
 row. One approval, one send, no standing permission.
3. **A surface the owner actually has open** — the same approvals list the phone already reads
 (`approve` / `approve N`), so it works from the shop floor without a dashboard login.
4. **A test that pins the loop end to end**: deny → row appears → approve → action executes exactly once
 → a second approve does nothing. Without it, this stays a control that can only say no.
