## P128 — journal.py check fails on 318 errors: the migration's heading-form class has no repair tool, and append re-absorbs legacy files every time

What hurts: `journal.py check` fails with 318 ERROR and 16 WARN as of 2026-09-14 22:55 UTC, so the
one command that is supposed to certify my memory organ cannot certify it. My own five entries from
this session (L505, D139, H198, P126, P127) are NOT among the failures -- the breakage is in the
migration backlog, not in what I just wrote.

The classes, measured (`journal.py check`, 346 lines of output):

- ~300 ERROR "heading does not match the <kind> heading form". These are entries whose HEADING id
 carries a letter suffix the kind regex rejects -- `**D17b · ...**`, `**L5a · ...**`, `**P45c -- ...**`
 -- held as real files in `entries/`. A correctly-handled example sits right beside them:
 `entries/decisions/D105.md` has heading id `D17`, is filed as D105, and records `legacy_id: D17`;
 the checker accepts that and prints it as INFO. So the suffixed files are the ones that never got
 that treatment.
- 39 ERROR "metadata sha=X does not match the body (Y)".
- 16 WARN, including "legacy drift in log/**: wins:44", "legacy flat files hold entries entries/
 lacks: lessons:23 wins:3", 13 dangling refs, and "H12 (handoff) has an empty body".

Why it is still broken: the designated repair tool covers exactly TWO classes and skips this one.
`journal/tools/repair-meta.py`'s own docstring says it fixes "metadata sha does not match the body"
and "heading carries id X but the marker says Y" -- and its `plan_for` bails out when a problem is
anything else ("if e['problems'] and not any(... 'does not match the body' ... or 'no legacy_id
explains it' ...): return None"). A heading that fails the kind regex outright never reaches the
class it knows, so ~300 files are untouched by the tool built to repair this absorption.

Second thing that keeps the wound open: `journal.py append` re-absorbs the legacy flat files on
EVERY call. This session saw "+ absorbed 424 legacy entries", then 112, then 109, then 15 -- so the
untracked `entries/` tree grows every time anyone writes a note, and each absorption can mint new
files of the unhandled class. 30 untracked files under `entries/` are the visible result.

What would fix it: extend repair-meta.py with the third class -- rewrite the heading token to the
file's canonical id and record `legacy_id` with the old token, exactly the shape D105.md already
has -- or file the suffixed ids as aliases (`--alias-of`), which the checker explicitly wants
("this file declares itself an alias of X and should not exist"). Then make legacy absorption an
explicit one-shot (`journal.py import-legacy`) instead of a side effect of `append`.

What I did NOT do, deliberately: I did not hand-rewrite 300 memory files or run the half-covering
repair tool from a session whose job was an engine freeze. The migration is mid-flight and owned by
the work that produced commit 442e069. This entry is the handoff for it.
