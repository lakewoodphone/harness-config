## P — Every 300DDR email is flagged `needs_response` and filed as `personal`, so the flag is never consumed

**This is why lab news goes stale, and it is not a missing watcher.** The secretary already sees the
mail and already knows it wants an answer. Nothing acts on it.

**Measured 2026-09-25 on the authority, `email_thread_state`:**
- **18 threads whose last sender is 300DDR/repairshopr are sitting at `needs_response = 1`**, the
 oldest from 2026-04-01 and **nine of them from September 2026**.
- **Every single one carries `last_category = 'personal'`.**
- Their statuses: 8 `pending_review`, 8 `triaged`, 2 `needs_review`.

**Consequences that actually happened.** The 74048 arrival email sat unread for two days while the case
file and the owner queue both asserted the drive was lost in the shop. Ticket 73459 has had no reply
since 2026-09-14 and its pass-2 result is now overdue. And on the day the owner asked me to check Gmail
by hand, **today's 74114 "Thank you for your payment — your device is now in our queue" and 74115
"we have started to work" notices were both sitting unread** — 46 unread messages from this one sender
in total. A vendor the shop depends on for every chip-off job is classified as personal correspondence
and its questions expire unanswered.

**Why the flag does not save us.** `needs_response` is a *display* attribute; it drives no route, no
case write and no wake. With the category wrong, no downstream rule for "a vendor needs an answer"
matches either.

**What would fix it — cheap, and it uses what is already there.**
1. A sender-based rule: anything from `300dollardatarecovery.com` / `reply.repairshopr.com` gets
 `last_category = 'lab'` at triage, before any LLM step. No model required.
2. The same rule extracts the ticket number from `(message id: N)` / `Ticket #NNNNN` in the subject and
 writes the update into that ticket's case file and sync record — one fact, one authoritative place.
3. A standing work order on the authority (the table exists, `standing_work_orders`, with
 `department`/`task_type`/`schedule_type`) that runs the lab queue every few hours: list every lab
 thread with `needs_response = 1` older than N hours and raise it as work, so it cannot sit for
 eleven days again.
4. Register an await (`secretary-wake`) on any outbound to the lab, so the reply wakes a session.
 The Wilner case file already says the thread "has no monitor … register the await or the case rots
 again the way it did between 2026-09-19 and 2026-09-24."

**Verify with the same queries that found it:** zero 300DDR threads at `needs_response = 1` older than
the ticket's own turnaround, and zero with `last_category = 'personal'`.
