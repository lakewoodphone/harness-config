## P2859 — A session's in-flight subagent fleet can be re-keyed away mid-flight and its results become unreadable

**What hurts.** A session's in-flight subagent fleet can be re-keyed to a different session identity
mid-flight, after which its own jobs are unreadable (`job_output` → "belongs to another session",
`job_list` → "no background jobs", `list_agents` → "no subagents") — while the children may still be
running and writing files. The notification says "failed", which is the wrong reading.

**Measured 2026-10-06, ZABZ-YOGA.** Five `subagent_local` children were dispatched in one step at
02:59Z with a governor lease held. Within minutes all five were reported "finished [failed, error]";
`job_output` then answered `job subagent-56 belongs to another session` for every one, and both
`job_list` and `list_agents` were empty. A sibling instance of the same conversation was writing into
the same workspace directory with the same measurements and the same scratch filenames, and a foreign
brief for one of the threads arrived in the parent's context framed as if the parent were the child.
Lost: roughly ten minutes of four-way parallel research plus its results.

**Why it matters beyond the wasted work.**
- The failure is silent in the worst direction: "failed" invites the conclusion that nothing was
 produced, while another writer is actively producing files in the same paths.
- Two instances of the same agent writing one directory without coordination is how a package ends up
 with a false claim in one annex and its correction in another. Measured: annex B was corrected to
 "the authority is NOT backed up offsite" while annex C still asserted "6-hourly snapshot + restic to
 R2 | 24 h offsite" — the surviving false row was found by grepping the package, not by any warning.
- Same-name collisions in shared scratch space (`_scratch/orw-lesson2.md` written by both instances)
 make a plain `write` fail with "file has not been read", which reads as an error but is actually a
 collision signal.

**What would fix it.** (1) `job_output`/`job_list` should distinguish *orphaned but readable* from
*failed*; a job id should stay resolvable by the session that created it, at least for reading.
(2) On a session-identity change, in-flight children should be re-adopted or explicitly reaped, and
the event logged where `journal.py status` shows it. (3) If two sessions share a workspace, say so at
session start, so a fleet is partitioned by file *before* dispatch rather than discovered afterwards.

**Workaround used.** Before writing any deliverable, list the target directory and compare timestamps;
write only to a path no other writer has touched; record corrections in a separate verification file
rather than editing a document another instance may be rewriting; grep the finished package for any
claim you know to be false, because a correction in one file does not propagate to the others.
