## P2131 — P2138 - lifecycle_sweep fails with database is locked, and I wrongly attributed it to mashgiach

Measured 2026-09-20, and it corrects an earlier inference of mine.

 18:25:03 WARNING app.autopilot: Lifecycle sweep failed: OperationalError: database is locked

I had recorded (in W2140/W2136 and the surrounding handoffs) that `lifecycle_sweep`'s failures were
"the next instance of the same class" and then treated them as resolved when the `mashgiach` fixes
landed. **They were not resolved.** The sweep has its own copy of the defect:

 app/services/lifecycle_sweep.py::run_lifecycle_sweep
 conn = _get_conn(db_url) # ONE connection, no transaction
 ensure_task_lifecycle_metadata(db_url) # <- its own connection: SELECTs up to 1000
 # tasks, then writes metadata per task
 _close_completed_progress_tasks(conn, ...) # each helper commits independently
 ... 18 conn.commit() sites across the file ...

and the first write in the chain, `app/database.py::ensure_task_lifecycle_metadata`, is the same shape at
scale: **it reads up to 1,000 task rows and then writes lifecycle metadata on a connection that has
already read.** In WAL mode the write must upgrade that read snapshot; if the autopilot - which writes
continuously - committed in between, the upgrade is refused with `SQLITE_BUSY_SNAPSHOT`, which the busy
handler does not cover.

**Why the earlier attribution stuck.** `mashgiach` and `lifecycle_sweep` both fail at the same moment
with the same message, and `mashgiach` was the louder offender (62 errors a burst, where the sweep
produced 4-9). Fixing the loud one looked like fixing the class. It was fixing *a member* of the class.

**The correct disposition, not yet done.** `lifecycle_sweep` is structurally different from `mashgiach`:
18 write sites over one long, multi-phase routine that runs every 120 s. Wrapping the whole sweep in one
`BEGIN IMMEDIATE` would hold the write lock for the entire sweep on a 120 s cadence, which is the mistake
I already made once in `daily_scan` and corrected by narrowing the lock. The right change is per-phase:
each helper takes its own short transaction, or the reads are hoisted out of the write transaction. That
is design work, not a one-line patch, and it is the next significant item.

**Recorded because the failure is live and the record previously said it was handled.** A reader of the
earlier entries would believe lifecycle_sweep was fixed.
