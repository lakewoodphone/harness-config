## P3814 — LPT money record: 28.5k of collected payments attached to nothing, and 62 orders that read unpaid

Measured 2026-10-20 on the operational store while working case WO2605110002.

1. 280 SUCCEEDED payment_transactions rows carry orderId NULL (279 also customerId NULL), totalling 28,568.26. Newest created 2026-10-20 16:25 UTC - it is still happening.
2. 62 orders whose paymentStatus reads PENDING have SUCCEEDED rows totalling 7,791.71 against them, so staff reading the order see unpaid on money that was taken.
3. A third class the store cannot see at all: Stripe has charges with NO database row. Confirmed on WO2605130004 - bench note 'paid 150 card' 2026-05-20 21:30, no payment row anywhere, Stripe charge ch_3TZHinLnlgYj1gmT1sluxdvC 150.00 succeeded 21:32:09 UTC 'asus hinge'. Recorded as payment row 3410.

Mechanism: bench notes say 'paid 150 card' and nothing creates the row. lpt-write payment set only sets orders.paymentStatus and refuses without a ch_ id; Terminal payments carry only pi_, so the flag cannot be set either.

Tools: lpt-link-payment (attaches an existing orphan), lpt-record-payment (creates the row from a ch_ id), and new lpt-stripe-check (read only; lists Stripe charges for a window and with --match labels each already-linked / orphan / no-db-row). All three are authority-side and both older ones were unrunnable from Windows until this session fixed os.path.join on a POSIX path.

Fix next: run lpt-stripe-check --match over the whole book to find every charge with no row and every row with no charge; that is the only way to know whether the 28,568.26 is real money in the bank or stale rows.
