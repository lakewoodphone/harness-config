## The Dialpad harvest still writes message text verbatim, so the next card number re-creates the exposure

The masking on 2026-10-09 cleaned **everything held** (187 + 148 + 69 rows and 254 security codes;
`lpt-redact scan` reports 0 everywhere). It is the cleanup, not the cure.

The inflow is unchanged. Every inbound SMS body reaches `operational.communications.content`
unmodified by way of the production webhook
(`phone-and-tech-full/backend/src/services/dialpad/dialpad-sms-webhook.service.ts`), and the same
text is mirrored into the authority's `dialpad_sms_cache.body_text` and
`dialpad_ui_message_body_row.body_text`. So a customer who texts "here's my card 4266 8418 3159 7164"
puts it back in three stores, and the next sweep finds it again.

It is tempting to call this a customer behaviour problem. It is not: **a shop that asks for payment
by text is asking for a card number by text**, and the pay-link flow already sends Zelle and Stripe
links, which is the right answer. The harvest should not be a card store at all.

**What would fix it**, in order:

1. **A scrubber before the insert** in the webhook — run the same `find_card_numbers` /
 `mask_security_code` rules from `lpt_ops/redact.py` over the inbound body and store the masked
 text. The message stays readable; the digits never land. This is ordinary engineering and needs
 nobody's permission.
2. **The same for the authority's mirrors**, which are written by the Dialpad harvest jobs there.
3. **A test**: an inbound body carrying a PAN must not reach `communications.content`. Nothing in
 the repo currently fails if it does.
4. **Then say so in the inbox**: the auto-reply already tells customers the drop-off code and the
 hours; it should also tell them never to text a card number, and the counter's payment flow
 should not invite one.

Until (1) lands, `lpt-redact scan` is the check that says whether it has happened again, and it is
cheap enough to run on a schedule and fail loudly.
