## P4254 — Something restores files in /root/bin underneath a working session, and it did it twice in one hour

# Something restores files in `/root/bin` underneath a working session, and it did it twice in one hour

**Measured 2026-10-15, on `secratary-cloud`, to the minute.**

| time (Z) | event |
|---|---|
| 14:45:41 | `cfo-ask.py` deployed with two changes (a question mark on the CFO close, `REFUSAL_SILENCE_HOURS`); hash `60e23f03`, printed by `sha256sum` |
| 14:45:43 | `charge_msg.py` deployed with the same question-mark change; hash `06d1e8d7` |
| 15:08-15:11 | `merchant_resolve.py` deployed with two new evidence rungs; **all nine live merchants resolved**, printed from the live file |
| 15:09:43 | `order_evidence.py` deployed with the `Order <CODE> confirmed` arm |
| 15:2x | **`cfo-ask.py`, `charge_msg.py` and `merchant_resolve.py` are the PRE-CHANGE ORIGINALS**: mtimes back to `2026-10-14 03:11-03:13`, and `grep -c` returns 0 for every marker I added. `order_evidence.py` (mtime 15:09:43) survived |
| 15:16:40-43 | re-applied from the session's own working copies; all four compile and carry their markers |
| 15:17:20-15:21:50 | a 30-second hash sampler sees **no** further change (`/root/text-fix-20261015/watch-hashes.sh`) |

**Nothing admits to it, and I did not find the writer.** Checked and cleared, each with the command:

* root crontab — `lpt-deploy-drift` runs at minute 17 and its log names only `company-api` and
 `secretary-dashboard`;
* `cron-script-guard.py` — its log has **zero** `HEALED` and zero `ALERT` lines, and it names none of
 these files; it also only restores a script that is **MISSING**, and none was;
* the canonical copies under `/opt/company/scripts/cfo/cfo-ask.py` and `.../owner-intake/cfo-ask.py` —
 hash `7f855f9e`, equal to **neither** my version nor the reverted one;
* journald 15:05-15:30, filtered for the file names: nothing;
* `find /root -newermt "-40 minutes"` in `/root/bin`: only `owner_text_relay.py` and
 `order_evidence.py`, i.e. my own writes.

**The same class hit this session twice in one hour.** Earlier the *same hour*, another session
replaced `/opt/company/scripts/owner_attention.py` wholesale while this session held a verified change
to it (`L4771`). So this is not a one-off: **on this estate a file under `/root/bin` or
`/opt/company/scripts` can be replaced by something that leaves no log line, and a `sha256sum` taken
at deploy time is not evidence that the change is still there at the end of the session.**

**What made it survivable.** The session kept a copy of every edited file in its own working tree and
a `cp -p` backup per change, so re-applying took one `scp` per file. A session that edited in place
and moved on would simply have lost the work and believed it was live.

**What would fix it.** A write-claim beside a live artefact (`<file>.claim-<host>`), checked before an
edit; `/root/bin` under version control at all (it is not a git repository, so nothing here is
reviewable, blameable or restorable by intent); and — the cheapest of the three — **a verification
step at the END of a session that re-hashes every file the session changed and compares it to the
hash it recorded at deploy time.** Every claim in a handoff about a live `/root/bin` file should be
either un-asserted or re-verified at the end, because the window between "verified" and "true" is
apparently minutes.
