## P2872 — lpt-apps fills its disk because every deploy keeps a 4.44 GB image; deploys then fail with 'no space left on device'

Production deploys fail when lpt-apps fills its disk, and the cause is that nothing ever removes
the previous image. Measured 2026-10-08.

## The measurement

```
/dev/sda1 75G 70G 1.9G 98% / <- before
Docker Images 23 total, 45.56 GB, 30.18 GB reclaimable (66%)
lpt-lpt-backend:461e37c8d2a9 4.44 GB
lpt-lpt-backend:8c99290be12b 4.44 GB
lpt-lpt-backend:a1ccd7bf58d6 4.44 GB
lpt-lpt-backend:d53ac5fc05b9 4.44 GB
lpt-lpt-backend:a97371430862 4.44 GB
lpt-lpt-backend:392bd8681c19 4.44 GB
lpt-lpt-backend:8987667b9f0b 4.44 GB
lpt-lpt-backend:210538795e55 4.44 GB
```

Every backend deploy builds a **4.44 GB** image and keeps it. The deploy then dies like this:

```
failed to extract layer sha256:be47aea9...: no space left on device
FATAL: docker build failed (exit 2)
```

**The failure is not the code.** It looks like a build break and is not; the deploy script exits 2 and
CI would look green. Worse, it fails part-way, leaving a half-built image behind.

## The fix, and the line that must not be crossed

Remove superseded `lpt-lpt-backend:*` images, keeping the RUNNING one and `/opt/lpt/.previous-image`
(the rollback target), and prune the build cache. **Never `docker volume prune`** — the postgres data
lives in a volume, and that is the one irreversible thing on this box.

Result of one run: **1.9 GB -> 36 GB available, 98% -> 51%, images 45.56 GB -> 11.13 GB.**

Note: on this occasion `.previous-image` was the SAME tag as the running image, so there was no
distinct rollback target to preserve. Check that before assuming a rollback exists.

## What is still missing

**Nothing schedules this.** The disk will fill again on the same trajectory — roughly nine deploys at
4.44 GB each. The real fix is one of: prune superseded images automatically after a successful deploy
(the deploy script already knows the running and previous tags, so it is a few lines), or stop
shipping a 4.44 GB image when the useful part is a fraction of it.

Until then, if a deploy dies with "no space left on device": free disk first, then retry. It is not a
code problem and re-running the build without freeing space cannot work.
