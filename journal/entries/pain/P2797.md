## P2797 — Took the production API down for 4 minutes by killing the PID, and a copy-deploy had deleted a module the tree still imports

INCIDENT 2026-09-29 ~19:30 UTC on secratary. The production API (uvicorn app.main:app, port 8002) was DOWN for roughly 4 minutes and I brought it back.

WHAT I DID WRONG: I restarted by killing PID 1254415. The correct action was `systemctl restart secretary-api.service` -- the unit exists. Killing the PID meant the service came back only if the watchdog noticed, and it did not.

WHY IT DID NOT COME BACK: the tree could not import. `app/autopilot.py:28` imports `app.services.work_step_ledger`, and that file WAS NOT IN THE LIVE TREE. It exists in about twenty deploy snapshots (pre-copydeploy-*), and a stale `__pycache__/work_step_ledger.cpython-314.pyc` was still sitting in the live tree -- proof it had been there and was removed. A copy-deploy deleted a module that the tree still imports. The running process was serving pre-loaded code, so nobody noticed; the moment anything restarted it, the app was dead.

THE FIX APPLIED: copied app/services/work_step_ledger.py (5,695 bytes) from the newest snapshot, /home/zabz/pre-copydeploy-20260928T202359Z, into the live tree. Then gated the restart on `python -c "import app.main"` -- which printed IMPORT OK -- and only then started the service. health=200, pid 1904048.

STILL WRONG, AND IT NEEDS PRIVILEGES: `sudo -n systemctl restart secretary-api.service` is refused, so the API is now running as a MANUAL setsid process, NOT under the systemd unit. The unit is not managing the live service. If the unit or watchdog starts another instance there will be a port-8002 conflict. This must be reconciled by someone with sudo -- it is the single most important loose end from this incident.

THE LESSON THAT MATTERS: before restarting any long-running service, prove the tree imports. `python -c "import app.main"` is a 3-minute gate that would have turned a 4-minute outage into a decision. And restart the UNIT, never the PID.
