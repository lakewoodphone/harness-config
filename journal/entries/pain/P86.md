## P86 — Desktop URL/auth error was a supervisor race on port 3099 + a ready record naming a dead pid

The desktop (ZABZ-TECH) showed the owner "the URL is wrong or authentication or something" when starting the harness on 2026-09-14. Diagnosed from the box over Tailscale (desktop-ts) at ~21:50 UTC; nothing was changed.
WHAT ACTUALLY HAPPENED, from the machine's own logs:
- 15:02:48 watchdog.log: "ensure: engine on 3099 not answering - starting" (twice).
- 15:02:50 health.log: "health: 1 engine(s) down (3099) - restarting".
- 15:03:20 health.log: "port 3099 restarted, pid 32044".
- 15:05:50 watchdog.log: "ensure: start FAILED: server on port 3099 exited with code 1 ... EADDRINUSE address 127.0.0.1 port 3099".
So TWO supervisors own the same port (the health loop and the watchdog) and they raced: one had already bound 3099 while the other tried to start another engine, which died on EADDRINUSE. That is the window the owner opened into.
STATE NOW: port 3099 is held by pid 32044 and answers (a bare GET returns HTTP 401 - which is CORRECT and identical on this laptop, not a fault). ready-3099.json on the desktop still says {"pid":37064,...,"ok":true} and pid 37064 no longer exists: the ready record was never rewritten by whoever restarted the engine.
THE TRAP FOR NEXT TIME: do not read a 401 on 127.0.0.1:3099 as the bug. Compare against a known-good machine first (both return 401 without the browser's handshake). The bug is the supervision race plus a ready record that names a dead pid, which makes "is the engine up?" unanswerable from the record alone.
WHAT WOULD FIX IT: one supervisor per port (or a lock/leader between health and watchdog), the starter to reclaim a bound port deliberately (identify the holder, verify it is answering, kill only a wedged one), and the ready record rewritten on every (re)start and validated against a live pid before it is trusted.
