## P72 — 2026-09-14 - 230 journal entries exist only in working copies, in the shared repo nowhere

**230 journal entries exist only in working copies and are in the shared repo nowhere**

Measured 2026-09-14, not inferred:

| | count |
|---|---|
| `origin/master` shard markers (`grep -c '^<!-- e:'` over all six shards) | **489** |
| `origin/master` index rows | **489** |
| local shard markers | **719** |
| local index rows | **719** |

Both trees are internally **consistent** — index matches shards on each side, so this is not a
stale-index defect and not a corruption. It is a **distribution** defect: roughly **230 entries**
that exist in this machine's log exist nowhere in the shared repository, which is what every other
machine and every autosync consumer reads.

**Why this matters more than it looks.** The journal is the only thing that makes this role
continuous across sessions — the previous occupant of this seat said it plainly: if the notes are
not written down, the agent "literally ceases to exist as a coherent entity". A record that lives
only in one working tree has the same durability as the tree. The journal's own rebuild today
migrated ~400 entries out of flat files specifically so they could be read and searched; if 230 of
them never reach the shared repo, then a second machine reading `origin/master` sees a *shorter*
history and will re-derive, re-litigate and re-commission work that is already recorded.

**Mechanism, as far as it is established.** The rebuild happened while two sessions were appending,
and `import-flat` absorbed entries from the retired flat files that a second writer was still
adding to. Those absorbed entries landed in the local shards. Some of that was committed (my
`621256e` carries the repair); the rest appears never to have been pushed, and `origin/master` moved
forward independently (`c9f3a4b`) with a different, smaller set.

**Why it was not fixed in the same session.** Integrating my branch into master is exactly the
operation that created today's 217-id collision, and the other session writes this repo
continuously — files were being written 20 seconds before the integration attempt. A guarded merge
was tried and conflicted on four paths, two of them generated, and it was aborted rather than left
half-resolved. Forcing it would risk the same class of damage, this time against 230 entries instead
of 217 ids.

**What would fix it, in order.**
1. Stop the other writer (or wait for a quiet window; 157 s of quiet was observed once, not relied
 on twice).
2. `git fetch`, merge `origin/zabz-audit-20260914`, and resolve `journal/index/entries.tsv` and
 `journal/state/open-pain.md` by **regenerating** them (`journal.py index`, `journal.py state`)
 rather than hand-editing — they are derived files and hand-merging them is how the index and the
 shards drift apart.
3. Run `journal.py dedupe` **before** pushing, because a merge of two appending branches is
 precisely what allocates colliding ids.
4. Then verify the count on the shared repo, not locally: `git show origin/master:...` and count
 markers, the way this entry was measured.
5. Finally, address the cause rather than the instance: make `append` refuse to write unless the
 shard it targets is identical to the one it just read, or take a lock. Two writers appending to
 one log with read-then-write id allocation is a design that fails on every merge, and it has now
 failed twice in one day.
