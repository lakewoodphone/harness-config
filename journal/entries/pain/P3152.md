## P3152 — orders.total and the pricing summary disagree, every reader picks a side: nothing-owed, no tax, and a 404 after paying

**P3152 · `orders.total` and the pricing summary disagree, every reader picks a side, and the shop is charged neither the right amount nor any tax**

MEASURED 2026-10-12 on production. Three separate complaints from the owner — a 404 after
paying, no tax, "nothing is owed" on a real balance — are **one defect family**: the number a
human puts on an order (`orders.total`) and the number the pricing engine computes
(`WorkOrderPricingSummary.total`) are different numbers, nothing reconciles them, and each
reader trusts a different one.

**THE EVIDENCE THAT SETTLES IT** (the deployed service, run read-only in `lpt-backend`):

| order | `orders.total` | summary inputs | `summary.total` | what the screen said |
|---|---|---|---|---|
| 3018 | 75.00 | adjustment 70.34 | **75.00** | owed 75.00 |
| 2985 | 63.98 | adjustment 60.00 | **63.98** | owed 63.98 |
| 3071 | 2.00 | none | **0** | **NOTHING OWED** |
| 3019 | 165.00 | none | **0** | **NOTHING OWED** |
| 3037 | 100.00 | none | **0** | **NOTHING OWED** |
| 3014 | 25.00 | none | **0** | **NOTHING OWED** |

Whole table: **170 orders have a price; 102 of them (60%) have no pricing input at all**, so the
engine derives 0.00 while the stored total says otherwise. Last 60 days: 42 priced orders, **3**
with any pricing input.

1. **"NOTHING OWED" — `frontend/src/features/staff-intake/staff-order.surface.ts:459-460`:**
 ```ts
 const owedCandidate = summaryTotal !== null && Number.isFinite(summaryTotal) ? summaryTotal : owedFallback
 ```
 `summaryTotal` is `0`, which IS finite, so the fallback (`orders.total`) is **discarded** and
 `due = max(0, 0 - 0) = 0` → `StaffOrderChargePanel.tsx:339` *"Nothing is owed on this order."*
 The engine returns `0` for "no price recorded" (`pricing-summary.service.ts:604` recomputes
 from inputs it does not have), while the rest of the codebase is careful to keep those apart
 (`price-readiness.ts:213-231`: null → NO_PRICE, 0 → ZERO_WITHOUT_REASON; `pay-notice.service.ts`
 says "a null total is NO_PRICE, never zero"). **The screen is the only place that collapses them.**

2. **NO TAX — the house rule is PRE-TAX and tax on top, and almost nothing implements it.**
 The owner's own words, quoted in the repo (`staff-order.pricing.ts:215-221`, 2026-10-08):
 *"i entered 15, it should add tax to it automatically, with a checkbox to check sales tax
 included."* `docs/decisions/work-orders-edit-pricing-mvp.md` §6.3 makes PRE_TAX the default and
 `frontend/src/utils/pricing.ts:266` says *"PRE_TAX: Target is pre-tax amount (tax will be added
 on top)"*. But live:
 - **`lpt-write total set` writes the raw number** — `write_helper.py cmd_total_set`:
 `UPDATE orders SET "total" = %s …`; `grep -i tax` over that file returns **nothing**.
 - The raw total writes in `work-order-update-status.tool.ts:428-436` and
 `workOrderService.updateStatus` do the same.
 - **Nothing downstream adds tax** — the pay notice says so out loud
 (`pay-notice.service.ts:24-31`, "TAX IS ALREADY IN THE TOTAL … nothing here adds tax"), and
 the Stripe link is built with `unit_amount = amount * 100` and no tax rate.
 - **Proven on Stripe itself:** the live link for the paid order returns
 `line_items: unit_amount 200, amount_subtotal 200, amount_tax 0, amount_total 200` — one
 2.00 line and **no tax line at all**.
 - And where tax DOES exist it is **baked in, not added**: order 3020 is 149.00 with
 `adjustmentAmount 139.74` (139.74 × 1.06625 = 149.00, tax 9.26 INSIDE), because the
 booking-in/counter box treats the typed number as tax-INCLUDED
 (`repair-intake-case.service.ts:37-43`, `StaffSaleChargePanel.tsx:179` `taxIncluded = true`).
 That is the **opposite** of the owner's rule, and it is the newer of the two policies that
 have never been reconciled.

3. **THE 404, exactly.** `payment-link.service.ts:1588`, verbatim:
 ```ts
 after_completion: { type: 'redirect', redirect: { url: `${frontendUrl}/payment-success?payment_id=${payment.id}` } },
 ```
 Confirmed against Stripe: the live link's `after_completion.redirect.url` is
 `https://lakewoodphoneandtech.com/payment-success?payment_id=3307`. **There is no
 `/payment-success` route in the frontend** — `grep` over `frontend/src` finds the string
 nowhere; nginx serves `index.html` for it (HTTP 200) and React Router's catch-all
 (`MVPRouter.tsx:658`) renders `NotFoundPage`. Every other Stripe return URL in this repo points
 at a mounted route (`/kosher-waze/success`, `/intake?payment=success`) — this one does not.
 Secondary: `payment_id=3307` is the PENDING transaction, not the SUCCEEDED one (3308).

**NOT A DEFECT, worth saying:** the money itself works. The 2.00 payment produced transaction
3308 `SUCCEEDED`, `orders.paymentStatus = CAPTURED`, and `pickupReleasedAt` was stamped — the
release happened automatically. The failures are the messages and the numbers around it.

**FIXES, in the order that matters:**
1. `staff-order.surface.ts:459-460` — never let a finite summary total of 0 override a real
 stored total. A screen must not say "nothing is owed" when something is.
2. `lpt-write total set` (and every raw total write) must treat the typed number as the
 **pre-tax** price and let the tax be added, per the owner's own rule — or nothing the shop
 does will collect sales tax on a repair.
3. `payment-link.service.ts:1588` — point the return at the pay page itself with a success
 marker (`/pay/<uuid>?payment=success`), the smallest change that lands on a mounted route.
