## P2670 — sh -s with the script on stdin hangs when dispatched from zabz-tech, while the same shape works from ZABZ-YOGA - unproven cause, and it would kill half the mesh from the desktop

MEASURED 2026-09-29 by the load-experiment lane, from the office desktop. Every attempt to complete a REMOTE child turn from zabz-tech returned nothing: 180 s with a real brief, 45 s with a script that ran no child, 25 s hand-rolled. A plain ssh linux-pc-ts with hostname and echo DONE over the same file-descriptor shape exited 0 in 309 ms, so ssh itself was fine and the stdin-script delivery was not. It does NOT reproduce from ZABZ-YOGA: on the same day and the same fixed code, the same sh -s stdin shape completed real child turns from this laptop to zabz-tech-linux (exit 0, 5176 ms) and secratary (exit 0, 5080 ms), framed, with correct hosts. So the defect is a property of the dispatching client, not of the target, the generated program, or any quote character. NOT ESTABLISHED and not to be guessed: whether the cause is this Windows OpenSSH client, the remote sshd, or a hand-rolled probe that left stdin open. WHAT WOULD FIX OR SETTLE IT: reproduce from zabz-tech using the package own createSshTransport and buildPosixScript rather than a hand-rolled probe, and if it reproduces, deliver the POSIX program the way the Windows path already delivers its own - write the script to a file on the target and invoke the file - which removes stdin from the path entirely. Related: L1821 (Windows ssh.exe hangs on a stdout pipe), L3063, L3064, docs/mesh/123.
