## P12747 — I destroyed the LPT API refresh token by refreshing it twice without persisting the rotation

What broke, exactly. LPT_API_REFRESH_TOKEN in /opt/company/.env is a ROTATING refresh token, and auth.refresh revokes the one you present once it succeeds. At 2026-10-26T15:59:46Z I called POST /api/trpc/auth.refresh with the stored value and got 200 plus a new token pair. I kept the access token and threw the new refresh token away. At ~16:12Z I called it again with the now-stale .env value. The server read that as refresh-token REUSE and revoked the whole family for user 300 (agent-verification@lakewoodphoneandtech.com, MANAGER): refresh_tokens rows 3533 through 3538 all read isRevoked=t on the operational RDS.

The measured failure, not a guess. curl to https://api.lakewoodphoneandtech.com/api/trpc/auth.refresh now returns http=401 {"error":{"message":"Invalid refresh token","code":-32001}}. Consequence: every protectedProcedure is closed to automation - lpt-pay-notice can no longer mint or read a link, payments.attachPaymentToWorkOrder cannot run, so payment_transactions 3316 (500.00, Weitman, terminal) stays unlinked from order 3206 and that order keeps reading PENDING / 0.00 collected.

What still works. The Schreiber pay page minted at 16:00:50Z is a live Stripe artifact and is unaffected; it was created before the revocation and https://lakewoodphoneandtech.com/pay/852fd5f8-a962-47db-b237-9ee4bdbbcead returned 200 afterwards.

The rule this cost, and it is not obvious from the tool. A rotating token is a ONE-SHOT secret: whoever calls auth.refresh must persist the returned refreshToken before it does anything else, or it has destroyed its own credential and logged out the seat. Two calls are not idempotent - the second is a reuse attack by the server's own definition. Any script that touches this must (1) read the token, (2) refresh, (3) write the new token back atomically, (4) then use the access token, and it must refuse to refresh if a refresh is already in flight.

Recovery state. Revocation is per-family and irreversible from the DB side, so the seat needs a fresh login (password or admin reset in the dashboard) to mint a new token chain. Until the owner provides that credential, treat every LPT write that goes through the app API as unavailable - lpt-write (which uses the SSH helper and the DSN, not the API) still works, which is how notes 4647 and 4648 were written after the failure.

Cost. One agent seat logged out, one bookkeeping link deferred, and about forty minutes of this session. The customer-facing work was unaffected because the pay page and the SMS path do not use this token.
