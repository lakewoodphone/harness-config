## P2543 — dialpad_sms_cache is 88 percent synthetic duplicates - and it made me report a spam incident that never happened

## P — `dialpad_sms_cache` is 88% synthetic duplicates, and it made me report a customer-spam incident that never happened

**I was wrong, and the record of it matters more than the entry it retracts.** On 2026-09-25 I read
26 rows in `dialpad_sms_cache` for phone `8485258603` on `2026-09-20`, all carrying the *same body*,
26 *distinct* `message_id`s, first 03:17:05Z and last 20:09:15Z — and concluded the shop had sent one
customer the identical SMS 26 times over 17 hours. I wrote that up as a live customer-damage incident
(P2542) and was one step from reporting it to the owner. **It did not happen.**

**What disproves it, and it is one query away.**
- The `message_id` values are `ptf-comm-132606`, `ptf-comm-132727`, … — **our own backfill ids**
 (`ptf` = the phone-and-tech projection), not Dialpad message ids.
- The `session_id` is `ptf-thread-8485258603` — a synthetic thread, not a Dialpad session.
- `fetched_at` advances in lockstep with `created_at`, in ~30-minute passes. The row is *re-inserted*
 every pass, and each insert mints a fresh sequence id and stamps `created_at` with the projection's
 own clock — which is why 26 unique ids look like 26 deliveries.
- The decisive one: **the whole day is duplicated, not one customer.** On `2026-09-20`,
 `dialpad_sms_cache` holds **4,808 rows across 47 threads covering only 196 distinct bodies** — a
 **24.5x** duplication factor. Every phone in the shop shows the same ~26 copies.

**Scope, measured 2026-09-25 on the authority.**
- `dialpad_sms_cache`: **117,564 of 133,910 rows (88 %)** carry a synthetic `ptf-` `message_id`.
- Affected days run in the thousands of rows: 2026-09-01 2,254 rows / 662 bodies; 2026-09-02 2,005 /
 549; 2026-08-24 1,846 / 585; 2026-09-20 4,808 / 196.
- `count(DISTINCT message_id)` is **structurally meaningless** in this table: `msg_ids = rows_n` on
 every day, because the id is minted per row rather than per message.

**Why it hurts.** (1) Any agent that counts rows, or distinct ids, in `dialpad_sms_cache` gets a number
roughly 25x too high on affected days, and the obvious reading of that number is "we spammed our
customers" — which is what happened to me. (2) The projection overwrites `created_at` with its own
clock, so **the true send time is destroyed**, which silently breaks quiet-hours analysis, response-time
measurement and any "when did we last contact this customer" check. (3) It is indistinguishable from a
real incident to every downstream reader, including the comms-index and any owner briefing built on it.

**What would fix it.** Make the projection idempotent on a key that is stable across passes — the
Dialpad message id, or `(thread, body, original timestamp)` — never on a pass-scoped sequence number.
Preserve the source's own timestamp; do not stamp `created_at` at projection time. Add a `source`
column so a reader can separate real Dialpad rows from projected ones, and make the default view
exclude the projections. Then the check is one line: for any phone-day,
`count(DISTINCT body_text) = count(*)` should hold once duplicates collapse.

**The rule this teaches.** A unique-id count is only a delivery count if the id comes from the
*carrier*. Before reporting an outbound incident, verify the ids are the vendor's, and look at whether
the same shape appears across unrelated recipients — a pattern that hits everyone equally is an ingest
artefact, not human behaviour. Retracts P2542.
