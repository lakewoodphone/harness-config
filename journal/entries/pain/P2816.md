## P2816 — The autonomous spend cap cannot fire, and the number it would fire at was raised today without a record

THE AUTONOMOUS SPEND CAP CANNOT FIRE, AND THE NUMBER IT WOULD FIRE AT WAS RAISED TODAY
WITHOUT A RECORD.

MEASURED 2026-09-30 on secratary.
 /home/zabz/bin/wake.py WAKE_MAX_PER_DAY (500), WAKE_MAX_PER_SOURCE_PER_HOUR (12),
 WAKE_MAX_USD_PER_DAY (25.0) -- docstring says the USD cap
 is "the real limit"
 /home/zabz/bin/wake-dispatch.sh MAX_PER_DAY=500, MAX_USD_PER_DAY=70.00
 neither the environment nor the crontab sets any of them, so the DEFAULTS are what run
 the dispatcher's own comment from 2026-09-20 still reads "OWNER POLICY 2026-09-20: 4
 releases/day"
 wake_budget for 2026-09-30: 74 released, 19 failed
 no journal decision records the raise, which happened today

TWO SEPARATE FAULTS.

1. THE TWO FILES DISAGREE ABOUT MONEY. wake.py says 25.0 USD/day and the dispatcher says
 70.00. The dispatcher's own cap-consistency check compares them every run and warns that
 "the looser value wins" -- so today the effective ceiling is 70. Consequence: the ceiling
 the owner set and the ceiling the machine enforces are different numbers, and the only
 thing reporting it is a WARN line in a log.

2. THE GUARD CANNOT FIRE AT ALL. Every released session records `cost: not reported by this
 harness surface (dsh --profile headless prints no cost)`, and today's finished rows sum
 `cost_usd` to 0.0. A spend cap whose input is always zero is not a cap; it is a sentence
 in a docstring. The per-day release cap (500) therefore has nothing above it.

WHAT WOULD FIX IT: one number for the daily spend ceiling, read from one place by both the
store and the dispatcher; a release that records what it cost, or an explicit statement that
cost is unknowable here -- in which case the honest control is the release count, and the
USD cap should be deleted rather than left looking like a guard. Owner question #212 asks him
for the ceiling; the plumbing is ours.

WHY IT WAS RECORDED RATHER THAN QUIETLY FIXED: a cap that the owner set, raised by 125x in
the file, with two different values live, is exactly the kind of change that should never be
found by reading a diff. Whoever raises a ceiling should write down that they did.
