## P3807 — I called three working things broken on the Ullman laptop - a Windows status field is not an observation; and sweeping for that found two MORE live BitLocker keys on origin/main

## What I did wrong

On 2026-10-15 I reported **three faults on the Ullman laptop that were not there**. The owner checked them on the machine at the bench and corrected all three:

1. **"Touchpad is dead"** — taken from `I2C HID Device`, error code 10 "device cannot start", the only device problem across 272 PnP entities. **The touchpad works.** It was a Windows device-status reading captured at one boot.
2. **"Speakers aren't running"** — taken from the built-in speaker endpoint reporting `UNPLUGGED` (DeviceState 8). **The speakers work.** The capture's own verdict text calls that state *"the fault this check exists for"*, so this kit's audio check produced a **false positive on a working machine**.
3. **"The clock reads 2072"** — listed as a defect. It is not one: the machine has no internet connection and therefore no time sync.

All three went into a production note on WO26101312747, the `lpt-hub` case file and the archived run's README — and I then told the owner **"yes, four things wrong"** when the answer was **one**.

## The mistake, named

**A status field is not an observation.** All three came from a Windows query returning a *state*, and I promoted a state to a fault with nothing physical behind it. Everything that survived is something the machine wrote itself: the eleven Kernel-Power 41 / EventLog 6008 unexpected-shutdown pairs, the SMART counters, the battery capacities out of `powercfg`, the identity out of SMBIOS. Every one of the three that failed was of the form *"Windows thinks this device isn't running"*.

The rule this earns, and it generalises well past this kit: **before calling something broken, say what would have to be true physically and whether you observed that — or say plainly that you are reading a status field and that is not the same thing.**

It is the mirror of a rule this estate already carries: `COULD_NOT_READ` is never a pass. **A status of `ERROR` or `UNPLUGGED` is never automatically a fault.**

## Corrected everywhere the wrong thing had been written

- production note on WO26101312747, write ledger **seq 455**, citing the earlier note by what it said;
- `lpt-hub` case file **and** the archived run's README — commit **9d3ca2f35** on `origin/main`, **retracted rather than deleted**, so the next reader sees a reading that looked like a fault and was not;
- this entry.

## What looking for it turned up

While checking my own archive for leaked secrets — after a sibling commit (**5cd20bfe1**, 15:55:33Z) redacted a live BitLocker recovery key out of `wd-sn740-david-auman-2026-07-02.json` — I swept the **current tree** of `origin/main` for the 8x6 recovery-key form:

- **the archived Ullman run: 0 matches.** Clean, as designed.
- **four other files matched. Two are placeholders** (eight identical groups) — `compromised-windows-recovery-sop.md` and `research-documents/Hardware & Repairs/Windows 11 BSOD Driver Recovery.txt` — and were deliberately left alone.
- **two were real:** `docs/customer-operations/cases/dell-laptop-rabbi-shochet-2026-06-22.md` (2 occurrences) and `docs/customer-operations/cases/laptop-new-birnbaum-7326778482-2026-06-21.md` (1). Eight distinct groups each, no known placeholder form. **Two customers' live keys, readable on the default branch.**

**Redacted in commit 5e0855e32**, same shape as the sibling commit: field kept, value replaced, reason recorded, value never printed. Re-swept afterwards — the case files are clean and only the two placeholders remain.

**Neither redaction invalidates a key on its drive.** Rotating it there is a separate physical step, and history plus any pre-redaction PR still serves the pre-redaction blob until those are closed or deleted. **Three named customers now carry BitLocker recovery keys that have to be rotated: Auman (already known), Shochet and Birnbaum (neither previously on the list).**

## Two tool facts worth keeping

- `git grep -lE '[0-9]{6}(-[0-9]{6}){7}' <rev> -- .` sweeps a whole repo revision for recovery keys without checking anything out, and `-h` plus a Python classifier (distinct groups, known placeholder forms) separates a real key from a documentation example. Fingerprints beat printing the value.
- `lpt-write note add` caps at **4000 characters** and refuses rather than truncating — hit it once this session at 4421, rewrote to 3838, nothing written either time.
