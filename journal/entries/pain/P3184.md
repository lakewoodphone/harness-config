## P3184 — The autonomy gate is enforced on the worker path and advisory on the chat-action path - the verdict is assigned and never read

The company's graduated-autonomy gate is enforced on one action path and merely ADVISORY on another, so a corrected matrix alone would not stop an action from executing unattended.

MEASURED 2026-10-14 ~13:20Z on `secratary-cloud`, read-only. The gate is called from exactly two places in the whole tree:

 $ grep -rn "should_execute(" app/ | grep -v "def should_execute"
 app/chat_action_runtime.py:381: decision = should_execute(action_name, settings)
 app/services/agent_worker.py:2346: return should_execute(action_name)

`agent_worker.py:2346` is inside `_check_autonomy` (defined `:2335`), which IS consulted at `:2484` (`gate = _read_only_autonomy_override(...) or _check_autonomy(...)`) and `:4459` (`gate = _check_autonomy(tool_name, agent_id)`). **On that path the gate is enforced.**

`chat_action_runtime.py:375-384` is the other path, and there the verdict is computed and thrown away:

 from app.services.autonomy import (record_failure, record_success, should_execute)
 decision = should_execute(action_name, settings)
 _autonomy_action = decision.get("action", "execute")
except Exception:
 _autonomy_action = "execute"

 # Execute the action
 try:
 result = _dispatch_action_inner(action_name, action_params, settings=settings, agent_id=agent_id)

`grep -n "_autonomy_action" app/chat_action_runtime.py` returns **exactly two lines, 382 and 384 — both assignments.** The variable is never read. The code falls straight through to `_dispatch_action_inner`, so the decision has no effect, and the `except` clause sets the verdict to `"execute"`, so any error in the gate is fail-open.

**What this means for the fix that is ready to ship.** A tested rebuild of the matrix exists (150 rows; **31 actions moved to L0/L1**, including `delete_tool` at L0, plus `hire_department`, `fire_agent`, `reactivate_agent`, `dialpad_send_sms`, `gmail_send`, `gv_send_sms`, `create_customer`, `create_work_order`, `contact_update`, `calendar_delete`, `run_command`; 102 left autonomous deliberately because the owner wants autonomy; 34 levels changed, all downward; its regression test fails on the base and passes after). **Deploying it is a real improvement on the worker path and closes the fail-open default from `autonomy.py:376` — and it is NOT sufficient, because the chat-action path would still dispatch those same actions with no human.** A fix that ships alone here would be half-true, and half-true is the failure this estate measures most.

**Why it is also not deployed yet, which is a separate reason.** `company-api` must be restarted for Python to load the change, and **another session is mid-edit in `/opt/company/app/autopilot.py`** (1,413 insertions / 333 deletions against HEAD, observed changing at 12:20:47Z during a build). A restart now would load that session's unfinished production edit into a live service that serves the shop's customer communications — and this same service was found wedged for 50+ minutes earlier today (`H3660`). **Deploying the file without the restart would put the change in the tree and not in the process, which is exactly the "correct in git, absent where it runs" defect this round spent its morning on.** So the correct sequence is: finish the enforcement change, wait for the concurrent editor, deploy both together, restart once, and verify through `action_approval_queue` — which is the only witness that works (`tick_telemetry.autonomy_decisions_json` is empty in all 34,274 rows and `record_autonomy_decision()` has no caller).

**The general lesson: a gate is not a gate because it is called.** Count the call sites, and for each one check that the verdict reaches a branch. A decision variable that is assigned twice and read never is worse than no gate, because it appears in the audit trail as if the framework had considered the action.
