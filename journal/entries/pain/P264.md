## P264 — The authority's SQLite refuses writes under contention on the paths that matter - inbound SMS and the owner queue itself

**What hurts:** the authority's SQLite store refuses writes under contention, and it does so on the
paths that matter most. Measured 2026-09-18: `/webhook/twilio/sms` died with `Unhandled error …
database is locked` → HTTP 500 and Twilio does not retry (70 inbound texts lost, H536); and
`~/bin/owner-queue.py add` — the single place an owner decision can be recorded — raised
`sqlite3.OperationalError: database is locked` on the first attempt, succeeding only on retry. That
script already passes `timeout=20` to `sqlite3.connect` (`owner-queue.py:83`), i.e. a 20-second busy
timeout, and it still lost. Prior measurement in the same database: 3,322 distinct `database is
locked` events in 7 days in `journalctl -u secretary-api`, against 222 rows all-time in `error_log`.

**Why it matters more than a nuisance:** each failure is silent and looks like nothing happened. The
lost text looks like nobody texted. The failed queue insert looks like the decision was never raised.
Both were "recorded" only because a reconciler or a human retried by luck.

**What would fix it:** (1) find who holds the exclusive lock — a long write transaction, a second
process opening the same file, or checkpoint starvation in WAL; (2) confirm WAL is actually on for
every writer (`PRAGMA journal_mode` per connection, not once globally); (3) give every writer a real
`busy_timeout` **and** a retry wrapper, and make every webhook write-first-then-work rather than
work-then-write; (4) consider moving the hot ingest tables off the shared file. Not attempted yet:
the diagnosis needs a lock-holder trace under load, not a guess.

**Evidence:** H536, journalctl count above, `owner-queue.py:83`.
