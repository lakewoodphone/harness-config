## P218 — Production and laptop checkouts carry unlanded work; it blocks deploys and collides parallel agents

Two checkouts of `personal-secretary-mvp` are carrying uncommitted, unlanded work, and it is now blocking deploys.

SECRATARY (the production host), observed 2026-09-16 by a subagent and NOT independently confirmed by me:
- `/home/zabz/personal-secretary-mvp` is at commit `c239a9b1`, **which origin cannot fetch** - so production is running code that is not in version control.
- 20+ uncommitted modified files, **including `app/main.py`**, which is the file most feature work has to edit.
- Consequence, observed: a finished, tested, pushed fix could not be deployed, because deploying would have overwritten another workstream's uncommitted work. Correct call was made (don't deploy), but the reason it was correct is the problem.

ZABZ-YOGA (this laptop), observed 2026-09-16 by me directly:
- 36 modified/untracked entries in the working tree simultaneously.
- Branch left on `fix/recurring-reminders` rather than master.
- Several of these paths are shared hot spots that multiple workstreams need: `app/chat_action_runtime.py`, `app/main.py`, `app/services/department_tools.py`.

WHY IT MATTERS, beyond tidiness:
1. **Production runs unreviewed, unversioned code.** If that checkout is lost, the work is gone, and nobody can say what is actually running. This is the same class as the stale-database incident - a confident claim about production that the evidence cannot support.
2. **It blocks deploys**, so a tested fix looks "done" in the repo and is not running in production. Silent divergence between repo and runtime.
3. **Parallel agents collide.** I ran two agents in this repo at once and one left the tree on a feature branch while the other was still writing; the second had 36 files of other people's uncommitted work underneath it. I caught it and pinned the agent down (commit by explicit path only, never `git add -A`, never switch branches), but the hazard was mine to create and mine to prevent.

WHAT WOULD FIX IT:
- A first-class deploy path that never assumes a clean tree - e.g. deploy from a git archive / fresh clone of a pushed ref onto secratary, rather than from the long-lived dirty checkout. Then "the tree is dirty" stops blocking deploys entirely.
- A rule for parallel agents in one repo: one worktree per agent (the `parallel-agent-orchestration` preset already says this - I did not follow it and should have; the same checkout is not a safe shared working directory).
- A periodic check that reports drift between the commit the running API was started from and `origin/master` on that host.

Evidence: 2026-09-16, subagent 222d10e6 deploy refusal (secratary c239a9b1), and my own `git status`/`git branch` on ZABZ-YOGA showing 36 entries on `fix/recurring-reminders`.
