## P9873 — Filter reports PTT+ disabled from pm list packages -d while dumpsys says enabled=1

The filter's disable verification can report success on a package that is still enabled.

cli/lpt/deployment/bloatware.py:24-31 `_is_package_disabled()` decides success from `pm list packages -d`. On 615196187 on 2026-10-22 that list contained `package:com.verizon.pushtotalkplus` while `dumpsys package com.verizon.pushtotalkplus` reported `enabled=1` (ENABLED) with `lastDisabledCaller: android`. The disable had been rejected with SecurityException and the package had re-enabled itself; the -d listing still showed it.

Consequence: `_looks_like_disable_success` path at bloatware.py:42-46 returns True, `disable_bloatware` records the package as disabled, the deployment receipt says so, and a phone ships with the side/PTT button still bound to Verizon PTT+ talk-to-text instead of Voice Access. That is exactly the defect the owner reported, and the tooling has been reporting it as fixed.

Worse, the same -d list feeds the release gate: cli/lpt/deployment/verification.py:577-593 builds `disabled_packages` from `pm list packages -d` and compares against config.bloatware. So the gate can pass on a live package.

FIX DIRECTION
Verify disabled state from `dumpsys package <pkg> | User 0: enabled=` (3 = DISABLED_USER, 2 = DISABLED) and treat `enabled=1` as failure, instead of trusting `pm list packages -d`. Keep -d as a fast pre-check only. Any package that returned SecurityException must be re-verified by dumpsys before being counted as done.

Seen on E4610 615196187, Android 7.1.1, build 1.010VZ. Not yet reproduced on other models, but there is no reason the -d lag is model-specific.
