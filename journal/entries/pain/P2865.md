## P2865 — The mesh cannot start any child: a sandbox denial kills the MCP launcher before the agent turn begins

The mesh provider cannot start ANY child right now, and the failure is a sandbox denial, not ssh.

Symptom, identical on every dispatch (2026-10-08 ~01:20-02:00Z):
```
remote-ssh: the remote one-shot exited 1 and produced no final message;
stderr tail:
 File "...\mcp-launcher.py", line 148, in main
 with log_path.open("a", encoding="utf-8") as f:
PermissionError: [Errno 13] Permission denied:
 'C:\Users\ezabz\Code\personal-secretary-mvp\data\logs\mcp-launcher.log'
```
Four children died this way (subagent-7, subagent-9, subagent-10, and one earlier).

## What it is NOT — each ruled out by measurement

- **Not ssh or the host.** `ssh desktop-ts powershell ...` runs fine from this machine, and the
 diagnostic completed on ZABZ-TECH while the dispatches were failing.
- **Not the file's ACL.** `icacls` shows `zabz-tech\ezabz:(I)(F)` on both the file and its directory,
 and `[System.IO.File]::Open($p,'Append','Write','None')` succeeds — I opened it and closed it.
- **Not a stale lock.** The file's LastWriteTime is 2026-10-07 09:42, i.e. nothing has held or
 written it since, while children started successfully many times after that.
- **Not disk or memory.** The desktop reports ample free memory; the failures are instant, not slow.

## What it IS

The denial is **the DSH file policy on ZABZ-TECH** applied to the child's MCP launcher process. The
launcher writes that log before the agent turn begins, so the child dies before it can report
anything — the error never reaches an agent, only the transport. `mcp-launcher.log` is not the
cause; it is simply the first write that trips the policy.

## FIX DIRECTIONS, cheapest first

1. On ZABZ-TECH, raise the file policy for the `headless` profile (the dispatch log says
 `target profile = headless`) to at least `workspace-write`, or widen the workspace root so
 `C:\Users\ezabz\Code\**` is inside it. **This is the fix.** Do it in `~/code/harness-config` and
 sync — never edit `~/.dsh` directly.
2. If the policy must stay read-only, move the launcher's log path to somewhere inside the allowed
 root — but that treats the symptom.
3. **Do not diagnose this again from scratch**: the four bullets above cost a session.
