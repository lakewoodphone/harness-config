## P2800 — A safety mechanism that was deleted by a deployment, and the disk it was protecting

MEASURED 2026-09-30, and this is the most dangerous thing found in this session.

`personal-secretary-mvp` keeps runtime backups in /home/zabz/secretary-backups: 21
directories, 298 GB, written every six hours at about 18 GB each. Its retention lived in
`scripts/server/prune-backups.sh`. That file DID NOT EXIST, and its caller
(`scripts/server/backup-data.sh`) looks for that exact path and, when it is absent, prints

 WARN: prune-backups.sh missing; skipping pre-backup retention

and carries on writing. So retention had silently stopped.

The stakes are in that script's own comment, from an incident on 2026-09-10:

 retention used to live at the END of this script. With the disk full, the backup step
 failed, the script exited non-zero, retention ran -> disk stayed 100% full -> SQLite
 SIGBUS core-dumps every ...

Measured state when this was found: / at 99%, 7.6 GB free, with the 18:00Z backup two hours
away. A full disk does not degrade this system politely; SQLite core-dumps and the company
goes down.

WHY IT WAS DELETED, and why nothing noticed: it was UNTRACKED. `git status` cannot show a
missing file, and the deployment style here is a copy (`deploy_by_copy_v4.sh`), which removes
what the source tree does not contain. The same class of loss has hit this repository before
for other modules; the difference here is that the missing module was the one protecting the
disk.

FIXED: the script is restored from its documented policy, run (freed 82 GB, 99% -> 80%), and
COMMITTED with `git add -f` so a deploy cannot remove it again.

THE GENERAL RULE THIS IS AN INSTANCE OF: a safety mechanism that lives outside version
control is not a safety mechanism, it is a hope. The caller's `|| true` and its WARN line
mean the failure is visible only to somebody reading a log nobody reads.

SECOND INSTANCE, same session, same root cause: nine scripts in /home/zabz/bin own the
owner's phone - the sensor, the store, the context, the decider, the worker, the sender, the
responder, the mirror, the health audit - and /home/zabz/bin is NOT a git repository. A
mirror now exists at harness-config/scripts/text-channel/ with a README, but the live copies
are still untracked and still accumulate `.bak-*` siblings (60 of them beside six files).

WHAT WOULD FIX IT PROPERLY: make /home/zabz/bin a git repository with a remote, or move the
live scripts into a tracked path and symlink/install them. Either is a small, deliberate
change and neither has been done.
