## P241 — broker-driven placement exists in no commit, so every node still falls back to a named target -- and on zabz-tech that target is itself

RANKED, 2026-09-17.

1. BROKER PLACEMENT EXISTS IN NO COMMIT -- and it is the third time in one night that a night's work lived
 only on a disk. lib/placement.js (346 lines, per-child broker leases, bounded queue, a ledger), lib/nodes.js,
 lib/broker-client.js, and the profile row's placement/brokerSsh/brokerUrl/queueWaitMs are all working-tree
 only. The broker itself is LIVE and can name any node (secratary:3091, http 200, schema 1, nodes with
 capacity readings), so this is a commit gap, not a service gap. Consequence: every node still falls back
 to a named `target`, and on zabz-tech that target is itself.
 WHAT WOULD FIX IT: commit packages/plugin-remote-fanout/** and the row's placement keys, then one real
 dispatch from a session on a node. Until then, the mesh routes by a literal in a config file.
2. The same class as docs/mesh/99 §3.4 -- "silent capability loss" -- now with a measured instance:
 a node whose row is correct and whose code cannot read it looks configured and does nothing.
 WHAT WOULD FIX IT: a rule that a config key must be readable by the running code before it is set; and
 the compose-time check that says which placement mode actually resolved.
3. A remote (ssh) verification of a profile composition on zabz-tech is IMPOSSIBLE by construction, so
 every audit that verified it that way has been reading an artifact. WHAT WOULD FIX IT: the local one-shot
 task as the standard instrument (it exists now), named in the audit recipe.
