## P2999 — A lab ticket number is the weakest way to find a case - '73459' resolves at 0.80 WEAK body-text while the name and phone resolve at 4.00, and it is the handle the shop actually says

**Measured 2026-10-08**, `~/code/lpt-hub`:

```
lptcase.py find 'Kogel' -> [name-exact(kogel) -> 4.00]
lptcase.py find 'rabbi kogel' -> [name-exact(rabbi kogel) -> 4.00]
lptcase.py find '8485258603' -> [phone(8485258603) -> 4.00]
lptcase.py find '73459' -> [WEAK body-text -> 0.80] <-- the shop's own handle for the case
```

**The number the shop actually talks about is the weakest way to find the case.** `73459` is a 300DDR lab ticket; it exists only as prose in the case body, so the index returns it flagged as a guess (`WEAK body-text`) rather than as a fact. Every other handle - the surname, the production spelling, the phone - resolves at full confidence.

**Why it matters more than it looks:** for a lab case, the ticket number is the identifier on the box, in the lab's emails, on the lab's invoices and in the customer's own words on the phone ("ticket 73459"). A staff member who has the lab email open and nothing else will search exactly that string. At 0.80 the case *is* still found, so this is not a miss - but it is a guess where a lookup should be, and six live 300DDR tickets alone carry this shape.

**What would fix it:** a first-class optional front-matter key for a vendor/lab ticket number (the schema in `CASE-FILE-STANDARD.md` section 2 already allows optional keys - `phone_alt`, `brought_in_by` - so this is additive, not a rewrite), indexed by `lptcase.py` at the same confidence as `work_order`. Do not paper over it by putting the number in `aliases`: aliases mean "another spelling this customer has been recorded under", and a ticket number is not a spelling.

**Related, and not fixed by this:** the case's own slug is `usb-files-disappeared-tbd-2026-08-06` although the customer has been known since 2026-08-30. `CASE-FILE-STANDARD.md` section 1 explicitly forbids renaming an existing file ("old paths are referenced from recovery-index.md, sync records and other case files"), so the slug stays and the identity has to come from the `customer` field, `aliases` and the header instead. Both are now correct.
