## P2120 — The lpt-hub clone drifts tens of commits behind origin while OTHER sessions commit to it, so every push needs a rebase dance that can collide with their uncommitted work

> RENUMBERED 2026-09-20 (ZABZ-TECH -> trunk reconciliation). This entry was minted as
> `P262` on ZABZ-TECH while the trunk minted its own `P262`; both were live, so that id
> meant two different entries on two machines. The trunk keeps `P262`; this entry is now
> `P2120`. Body is unchanged apart from this note and pointers to its renumbered siblings.
> Alias recorded in `journal/index/aliases.tsv`.

MEASURED 2026-09-17 on ZABZ-TECH, mid-task. lpt-hub was **27 commits BEHIND** origin/main and had
a concurrent writer committing INTO it while I worked (a shlock commit landed between two of my
git commands; the lptcase tool was warning "CORPUS IS STALE" and, at another moment, "69+ commits
AHEAD of origin/main - case work that has not been pushed cannot be seen by any other machine").

What it cost to push one new case file:
1. Rebase refused: two files had unrelated UNCOMMITTED edits (CUSTOMER_CASE_SYNC_RECORD.schema.json,
 tools/customer/audit.py) that were not mine.
2. Rebase then refused again: three UNTRACKED files (FIND-AND-RECORD-ANYTHING.md,
 tools/customer/dialpad.py, tools/customer/repair.py) collided with upstream, which had since
 started tracking them.
3. Had to back them up outside the repo, diff them against upstream, delete the local copies
 (they were byte-identical -- verified), rebase, and then restore the two parked edits.
4. Restoring the parked edits CONFLICTED on the schema file, because upstream had rewritten it.
 I took upstream's version and LEFT THE OTHER SESSION'S EDITS IN THE STASH
 (stash@{0} "ZABZ-TECH 2026-09-17 18:4x: pre-existing uncommitted schema+audit edits...") rather
 than commit someone else's work or invent a resolution.
 **SOMEONE MUST `git stash show -p stash@{0}` ON ZABZ-TECH AND DECIDE ABOUT THEIR OWN EDITS.**

Why it happens: this repo is written by several machines and several concurrent sessions, the
case index warns about it constantly, and nothing pulls before a write.

WHAT WOULD FIX IT
- A pull-before-write guard: `git fetch` + reject the write if behind, with the exact
 `git pull --rebase` command in the message. The lptcase tool already KNOWS the clone is stale
 (it prints the warning) and then proceeds anyway - making that warning BINDING for write
 operations would have removed steps 1-4 entirely.
- Or a documented single-writer/serialisation rule for lpt-hub writes.

Severity: it did not break anything here, but it is the mechanism by which case work exists on one
machine and is invisible everywhere else - which is the same failure class as the stale-database
incident this system already treats as its worst.
