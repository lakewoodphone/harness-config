## P64 — Netlify deploy credits block every frontend release

**What hurts.** `netlify deploy` returns `403 Account credit usage exceeded — new deploys are blocked
until credits are added`, so **no frontend change can be published at all** — not to the test site
(`lakewood-phone-test`) and not to production. The last successful CLI deploy was `6aa78de5…` at
2026-09-14 06:02:13Z (another session); everything after is refused. The account's own API contradicts the
block (`credits.included = 300`, `used = 0`, `usages_exceeded = []`), so the surfaced numbers cannot be
used to predict when it lifts. `next_usage_period_start` is **2026-10-07**.

**Why it matters beyond this week.** Every frontend deploy in this repo's history goes through this one
path. The moment it is exhausted, work that is finished, tested and committed — this session's Waze DRN
panel — **cannot reach a human**. That turns an engineering completion into an unbounded stall with no
signal, because nothing in the repo notices: the push succeeds, CI is green, and only the deploy 403s.

**What would fix it.**
(a) **Owner: add credits or upgrade the plan** — raised as queue row #16. The only path that restores the
existing domain wiring with no engineering.
(b) **If refused or deferred:** stand up the frontend on the Hetzner `lpt-apps` box behind the Caddy that
already terminates `test-api.lakewoodphoneandtech.com`, so a deploy is rsync + a container restart we
control. Not technical — it abandons Netlify's existing DNS/wiring, so it should not be done around the
owner's back.
(c) **A guard so this is never silent again:** a cheap scheduled check that reads the account's deploy
capability and alerts when deploys become impossible, so the failure is known *before* someone waits on a
release. Today the only way it was found was by trying to ship.

**Evidence.** `403` body captured verbatim from the CLI; account object from `GET /api/v1/accounts`;
deploy history from `GET /api/v1/sites/99e0273a-…/deploys`. Read 2026-09-14.
