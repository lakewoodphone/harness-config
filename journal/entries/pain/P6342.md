## P6342 — I filled the authority's disk with a careless 29GB cp and broke the company for 20 minutes

**P · I filled the authority's disk with a careless `cp` and broke the company for ~20 minutes.**

2026-10-14, `secratary-cloud`. To "back up" a **one-row** database edit, I ran:

```
cp -a /root/authority.db /root/authority.db.bak-reminder636-$(date -u +%Y%m%dT%H%M%SZ)
```

`authority.db` is **29.4 GB**. The filesystem is **150 GB and was already ~84 % full**. I never ran
`df`. `cp` wrote **25.8 GB**, hit `ENOSPC`, failed (`rc=1`), and left the partial file behind. With zero
bytes free:

- SQLite reads from the authority began returning **`disk I/O error`**;
- `estate-monitor.service` died of **`Errno 28`** while writing its own state JSON;
- the owner noticed the company was off before I did: *"You screwed up the entire company. All the agents
 are messed up now because the authorities off."* and *"We always need to keep space on the cloud
 authority."*

**Recovered** the same session: verified `/root/authority.db` intact (29,390,688,256 B) before removing
my truncated copy, then confirmed 18 G free, live reads (`reminders=635`, `email_triage_log=4311`,
`dialpad_sms_cache=135784`), `company-api.service` active, `/health` 200, and `estate-monitor` running
clean again.

### THE RULE, in the owner's own words
**Keep space on the cloud authority. Run `df` before any large write, anywhere — and never take a copy
bigger than the change it protects.** A 28 GB copy "to be safe" was orders of magnitude more dangerous
than the one-row `UPDATE` it was guarding. The entire blast radius came from a safety measure.

### THE DEEPER DEFECT — still open, do not close this pain until it is fixed
`estate-monitor.service` exists precisely to watch **disk headroom** (warns at 90 %, crits at 95 %). It
would have caught this. It did not, because **it cannot write its own state file when the disk is full —
so it dies from the exact condition it is there to alarm on.** A disk-headroom alarm that needs free disk
to raise the alarm is not an alarm. **This is the second failure mode in the same class already recorded
in `AGENTS.md` §1: a monitor that fails silently and is then read as health.**

### WHAT I DID NOT DO, AND YOU MUST
A full `PRAGMA quick_check` on `authority.db` after the ENOSPC **was not run** — that box also showed
**4 OOM kills in 24 h**, so a heavy check needed a quiet window it did not get. Reads and writes work and
the counts are sane, but **integrity is unproven.** Run it at a quiet time.

### THE METHOD THAT KEPT IT RECOVERABLE
I deleted only after proving which file was which, by size, against an exact path:
`stat -c %s` → `29390688256` (real) vs `25794019328` (my truncated copy). Encode that check before any
`rm` of something that looks like a backup.
