## P9998 — The company API went alive-but-not-answering: two 40-hour orphans pinned a 10 GB WAL, and the monitor that saw it could only write to syslog

The company API wedged at ~16:10Z and the owner got a text AND a voice call at 16:13:12Z. He
asked whether the API was down. It was, for a window; the API PROCESS was never dead.

MEASURED, in order
 r4-liveness-probe: 16:09:05 ok=true; 16:11:05 consecutive_failures=1 (TimeoutError);
 16:13:06 consecutive_failures=2, escalated=true -> sms + voice_call, P0,
 to +18483897895. The escalation was CORRECT.
 /health at 16:16: 000 at a 30 s timeout. 54 connections queued on 127.0.0.1:8002 (Recv-Q 54).
 /root/authority.db-wal: 10,714,863,432 bytes (10.2 GB), growing; db 34 GB; disk 91% full,
 20 GB free, load 2.78.
 TWO ORPHANS, parent dead, state R:
 377634 /opt/company/.venv/bin/python -u - (from `bash -s`) elapsed 1d18h54m cpu 99.8%
 rchar 148 TB, 36.1e9 read syscalls, held authority.db + -wal + -shm, two deleted
 etilqs temp files. A read transaction open for 42 HOURS.
 585597 /opt/company/scripts/ps_mcp_server.py elapsed 1d16h33m cpu 99.5% rchar 174 TB.

THE CAUSAL CHAIN, which is the transferable part
 An abandoned read transaction is what makes a WAL unacceptable: SQLite cannot checkpoint past
 the oldest reader. `PRAGMA wal_checkpoint(TRUNCATE)` returned busy=1 while 377634 lived. On a
 225 GB disk holding a 34 GB database, a WAL that only grows is a disk-full event, and this box
 has an mmap SIGBUS history from a full disk (2026-09-10, recorded in H2789).

FIXED
 SIGTERM to both orphans (they are readers; WAL mode is crash-safe by construction, the same
 guarantee as a power cut). Then PASSIVE checkpoint (0, 78, 78) then TRUNCATE (0, 0, 0):
 WAL 10.2 GB -> 416 KB, disk 91% -> 86% (32 GB free), /health 200 in 0.16 s, public
 https://api.abletelsolutions.com/health 200 in 0.9 s from outside.
 The watchdog had independently restarted the API at 16:18 (ExecMainPID 2284771).

BUILT, because nothing reaped it: /usr/local/bin/runaway-process-reaper.py + a 10-minute timer,
in ~/code/harness-config/scripts/ (repo, committed). cpu>=90% measured over two samples 10 s
apart AND elapsed>=6h. Protects pid 1, systemd, sshd, tailscaled, esearch, cloudflared and the
API's own ExecMainPID; SIGTERM then SIGKILL after 20 s; after a kill it runs PASSIVE and
TRUNCATE-if-not-busy to reclaim what the dead reader pinned. Every action appends to
/var/lib/runaway-reaper/actions.jsonl.

PROVEN, not just run -- two planted processes, both killed (one busy loop, one holding
authority.db open and reporting holds_authority_db=true), checkpoint passive (0,1535,1535) then
truncate (0,0,0), and the live API kept PID 2284771 with health=200 throughout. The first
deployed version of the repair FAILED with `OperationalError: disk I/O error` because I opened
the DB mode=ro and a read-only connection cannot checkpoint; that is fixed and proven.

BROKEN / OPEN
 1. NOTHING identified the 42-hour inline script's author. It was `python -u -` under `bash -s`
 started ~2026-10-26 21:26Z, the same evening /root/bin/text-health.py was edited (22:46Z).
 A session most likely left it behind. The reaper is the net, not the cause fix: whoever
 streams scripts into `python -` should bound them.
 2. estate-monitor HAD the precursor and told no human. `CRIT authority_wal_mb=10218.38MB` was
 logged on 1048 consecutive runs from 2026-10-27T05:24Z (~35 h) and every one is recorded in
 /root/.estate-monitor/alerts.jsonl with `"transport": "syslog-only, no outbound message"`.
 By design only public_health_status and disk_free_deficit_gb may escalate, and
 disk_free_deficit_gb only fires below 10 GiB free, which 20 GiB never crossed. So the
 alarm fired correctly in its own room for a day and a half.
 3. estate-monitor's disk metric reported "0.0 GiB free" at 16:16 when df said 20 GiB, and its
 public_health_status note said the outside probe read 200 while the vault heartbeat read
 000 -- a disagreeing reading that deserves its own look.
 4. /livez returns 404 on this build even though H2789 records adding it.

LESSON FOR THE NEXT SESSION: "the API is down" and "the API process is dead" are different
sentences. Check ExecMainPID and ActiveState first, then time /health, then look at the accept
queue (Recv-Q) and the WAL -- an alive-but-not-answering API with a huge WAL points at an
orphaned reader, not at application code.
