## P3206 — lpt-hub's main checkout carries 1,381 uncommitted deletions that any git add -A would sweep

**The working checkout `/home/zabz/phone/lpt-hub` has 1,381 files deleted-and-unstaged, plus 4 untracked.**

Measured 2026-10-14, by `git status --short | awk '{print $1}' | sort | uniq -c` → `1381 D`, `4 ??`. The
deleted paths are almost entirely `artifacts/**` — customer evidence and MANIFEST files, i.e. exactly the
material the repo's artifact-governance rule says to keep out of git but which is still **tracked**, so a
local prune shows up as a deletion rather than as a clean state.

**Why this is a hazard and not cosmetics.** It is **P13** with the blast radius already loaded: `lpt-hub` is
the repository other sessions and other machines work in, and the standing rule there is *stage explicit
paths, never `git add -A`*. Any session that breaks that rule once commits 1,381 deletions of customer
evidence under its own name — and the deletion is the kind that is not recoverable from the shop's own
workflow, because the files were only ever in the working tree.

**I did not touch it.** This session's commit (`4d6d5fbd1`, branch `research/kosher-camera-delete`) staged
three explicit paths and nothing else, so the deletions are untouched and still exactly where they were.

**What would fix it, and it needs a decision rather than a reflex:**
- If `artifacts/**` is genuinely out of scope, **untrack it** (`git rm -r --cached artifacts` and
 `.gitignore`), which converts 1,381 phantom deletions into a clean tree and makes the rule enforceable by
 the tool instead of by discipline.
- If those files are the record, **restore them** (`git restore -- artifacts/`) before anything else touches
 this checkout.
- Either way it should not be left ambiguous, because the next session's first `git status` is a wall of red
 that reads as damage and invites a "fix" — and the two available fixes are opposite.
