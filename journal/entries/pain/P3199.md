## P3199 — The merge gate reports success over a red test suite, so CI-green means nothing about tests

**P · The merge gate reports success over a red test suite, so "CI is green" in this repo currently means nothing about tests.**

Measured 2026-10-14, reproduced from the workflow file at `origin/test` = `5ca5bd320` and independently
from 9 CI runs.

`.github/workflows/pr-precheck.yml` removed the `is_copilot_author` condition from the test JOBS on
2026-10-14 (the header at line 647-651 says so; `test-backend-copilot` at line 654-655 now runs for
every non-draft PR). But the aggregator still validates their results ONLY inside
`if [[ "$is_copilot" == "true" ]]` (lines 955-973). For a human-authored PR it takes the `else`, prints

 "Human PR - the backend/frontend test suites do NOT run anywhere in CI for a human PR"

and falls through. That sentence is now false. The required job `ci-validation-pr` (lines 1021-1068)
checks only `detect-changes.result` and `aggregator.result`, so it never re-checks the shards.

**Consequence:** `CI Validation (PR Pre-Check)` — the required context branch protection enforces —
goes green while `Test Backend` / `Test Frontend` shards are red. A child measured 9 runs on
2026-10-14 (PRs 426, 427, 428, 429, 430, 437) and every one shows shards red and the gate successful.

**Why it has not been fixed by simply removing the condition:** the frontend shards fail 36/36 on a
runner bug (`Error: write EPIPE` in vitest's forks-pool teardown; no frontend shard job has concluded
`success` in 7 days). Making the shards blocking today blocks every merge. The runner must be fixed
first, then the gate opened. Recorded so the fix is sequenced rather than guessed at.

This is the same class as L3781 (`is_copilot_author == 'true'` meant no tests ran at all) — that entry
fixed the RUNNING and left the VALIDATION. The lesson generalises: **removing a gate from a job is not
the same as removing it from the decision.**
