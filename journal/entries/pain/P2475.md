## P2475 — A customer's question can be answered by the WRONG template message and then sit unanswered for 16 days - nothing represents an unanswered question, and the SMS harvest hides real traffic under 36x duplicates

RANKED: medium-high. It is the same family as **`P2253`** (a customer text is answered by nobody until a human looks) but the mechanism here is worse than silence: **the automation answered the wrong message and left the real question standing, and nothing noticed for 16 days.**

**MEASURED, 2026-09-24, Wilner SD card case (`dialpad_sms_cache`, phone_normalized `7329664296`).** The customer's entire real thread is six messages, all 2026-09-08:

| Time UTC | Dir | Body |
|---|---|---|
| 18:32:51 | in | Yeah I wanna go ahead with it |
| 18:44:06 | in | Will all the pictures come back in the right order? |
| 18:44:51 | out | they should, but it's not guaranteed |
| **19:06:56** | **in** | **Also, how long Will it take to know if they could do it?** |
| 20:22:37 | out | Let us know if you want to go ahead with it |
| 21:36:06 | in | I Zelled you thanks so much, |

The 20:22 outbound **re-asks for an approval the customer had already given 110 minutes earlier, and ignores the question asked 76 minutes earlier.** Four numbers on this case then sat unread by the customer: the card shipped 9/15, arrived 9/15, was diagnosed 9/19, and their two-week expectation lapsed 9/22 — with **no text since 2026-09-08 and no call since 2026-09-08 20:43**. Their question is still unanswered as of today.

**WHY NOTHING CAUGHT IT.** No object in this system represents "a customer asked a question and has not been answered". A sent message is a row; an *unanswered* question is the absence of a row, and absence never alarms — the same INSERT-only trap that made `comms_freshness` report a dead poller on a quiet hour (D2325).

**SECOND DEFECT, SAME CASE — the harvest makes traffic unreadable.** `dialpad_sms_cache` holds **216 rows** for this number; **6** are real. The other 210 are re-harvest duplicates under `session_id='ptf-thread-7329664296'` with `message_id='ptf-comm-*'`, replaying the same six bodies across 9/15-9/17. Any count-based reading ("has this customer been texted? how many times?") is off by 36x here, and `id` ordering does not separate them from live traffic.

**WHAT WOULD FIX IT.**
1. Represent the question, not just the message: when an inbound is classified as a question/request, open a row that closes only when an outbound answers it, and alarm on age. Then "the customer asked how long and we never said" is a fact in a table instead of a thing a human has to notice.
2. Stop the template reply before it sends: refuse an outbound whose template matches a message already answered in the thread, and never let a template fire while an unanswered inbound is older than the one it is answering.
3. Tag re-harvest rows (`channel`/`session_id` already distinguish `ptf-thread-*`) so any count can exclude them, and say so in the runbook: **count distinct `message_id` values, not rows.**

**EVIDENCE.** `dialpad_sms_cache` on `secratary`, read 2026-09-24; `dialpad_transcript_cache` for the same number (last call 2026-09-08 20:43 UTC). Case file: `lpt-hub` `docs/customer-operations/cases/wilner-sd-card-7329664296-2026-08-31.md` §5, commit `db72fd8fc`.
