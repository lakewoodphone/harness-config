## P3804 — python.exe is denied file creation in some directories on ZABZ-TECH while PowerShell and git.exe write the same paths

## 2026-10-15 · ZABZ-TECH · `python.exe` is denied file creation in some directories while PowerShell and `git.exe` write to the same paths in the same second

**What happens.** A Python process cannot create a file in some directories under the session workspace, and CAN in
others. It is not the policy: the session runs under `danger-full-access`.

**Measured**, one interpreter (`C:\Users\ezabz\Code\lpt-hub\.venv\Scripts\python.exe`), `open(path,'w')` then
`close()` then `os.remove`, five paths, same second:

```
OK C:\Users\ezabz\Code\dispatch\_p.txt
OK C:\Users\ezabz\Code\lpt-hub\_p_root.txt
OK C:\Users\ezabz\Code\lpt-hub\index\_probe_hub.txt
FAILED C:\Users\ezabz\Code\tmp\_p.txt -> PermissionError [Errno 13]
FAILED C:\Users\ezabz\Code\_scratch\_probe_scratch.txt -> PermissionError [Errno 13]
FAILED C:\Users\ezabz\Code\_wt-senzer\_probe_root.txt -> PermissionError [Errno 13]
FAILED C:\Users\ezabz\Code\_wt-senzer\index\_probe_idx.txt -> PermissionError [Errno 13]
FAILED C:\Users\ezabz\Code\personal-secretary-mvp\_p.txt -> PermissionError [Errno 13]
FAILED C:\Users\ezabz\AppData\Local\Temp\_dsh_p.txt -> PermissionError [Errno 13]
```

**The control that makes it a real anomaly:** in the SAME directory, seconds apart, with the same file name shape —
- PowerShell `Set-Content C:\Users\ezabz\Code\_wt-senzer\index\_probe.txt` → **wrote and deleted fine**;
- `git worktree add` wrote **13,122 files** into `C:\Users\ezabz\Code\_wt-senzer\`;
- `(Get-Acl C:\Users\ezabz\Code\_wt-senzer\index).Access` shows `zabz-tech\ezabz FullControl Allow`.

So it is not the ACL, not the disk, not the path's link type (`Get-Item` reports plain `Directory` for `_scratch`,
`_wt-senzer`, `lpt-hub`), and not a blanket per-process restriction — it is per-executable AND per-directory, and
the pair that binds is not visible from the filesystem.

**What it broke.** `python tools/case-index/lptcase.py index` in the new worktree at
`C:\Users\ezabz\Code\_wt-senzer`:
```
File "tools\case-index\lptcase.py", line 1906, in _write_text_atomic
 with open(tmp, "w", encoding="utf-8", newline="\n") as fh:
PermissionError: [Errno 13] Permission denied: 'C:\\Users\\ezabz\\Code\\_wt-senzer\\index\\cases.json.tmp'
```
reproduced twice, so `lptcase show` / `check` could not run there at all. The impact is not this one tool: ANY
Python tool that writes a report, cache or index outside `lpt-hub` / `dispatch` fails, and it fails as
`PermissionError` rather than as a clear sandbox refusal, so a session is likely to misread it as its own bug or as
a full disk. The `diagnose-windows-sandbox-acl` skill exists for the sandbox-denial case; it was NOT loaded here —
the first fix to try next time is to run the tool from a directory python can write to
(`lpt-hub`, `dispatch`) or to redirect the output path, and to check whether the boundary is a fixed allowlist of
directories created before the session started (`_wt-senzer` was created DURING this session; `dispatch` and
`lpt-hub` are older).

**Not done:** root cause. The environment was not changed to work around it — the commit was made through
`git.exe`, which is unaffected.
