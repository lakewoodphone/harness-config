## P141 — Her laptop cannot join Tailscale, so it cannot reach the authority directly (IPv6 fixed, login still stalls)

MEASURED 2026-09-15 on her laptop, while trying to give it the same secretary MCP the Mac has.

SYMPTOM: `tailscale status` says Logged out / NeedsLogin, and `tailscale login` never completes -- it
hangs with an EMPTY AuthURL and writes nothing to stdout or stderr. An auth key from the repo's
TAILSCALE_AUTH_KEY did not change it.

ROOT CAUSE, from Tailscale's own health string (this is the useful part):
 "The last login error was: fetch control key: Get https://controlplane.tailscale.com/key?v=142:
 dial tcp [2606:b740:49::105]:443: connectex: The requested address is not valid in its context."
It resolved the control plane to an IPv6 address and the connection failed instantly. This network
BLACKHOLES IPv6 -- the same condition already documented for her launcher, which sets
--dns-result-order=ipv4first for exactly this reason. Tailscale is a separate process tree and never
inherited that treatment.

PARTIAL FIX APPLIED AND VERIFIED: pinned the control plane's A records in the hosts file
(192.200.0.102/.110/.108, marker `# dsh-ipv4-tailscale 2026-09-15`, backup hosts.bak-dsh-20260914-232140
kept beside it). After that `ping controlplane.tailscale.com` answers from 192.200.0.102 in 99 ms, so
the IPv6 failure is gone -- and login STILL does not complete, now with no error text at all.

SO IT IS NOT ONLY IPv6. Whatever remains needs either the desktop Tailscale app signed in by a human
at the machine, or an auth key that the tailnet accepts for this node. Recorded rather than ground
on, because it blocks nothing: the laptop reads the company archive over HTTPS via scripts/ps-system.mjs,
which works right now. The cost of leaving it is a thinner tool-belt on the laptop than on the Mac.

DO NOT re-derive the IPv6 part -- it is already fixed and the hosts pin is the fix.
