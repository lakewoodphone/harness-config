## P12107 — This checkout journal is 1,551 entries behind the authority and its own fetch cannot see the refs that fix it, so an append minted D9410 twice

**This checkout's journal is 1,551 entries behind the authority, and `journal.py`'s own fetch does not reach the refs that would fix it — so an append here mints ids other machines already used.**

**Measured 2026-10-23/25 on ZABZ-YOGA, `C:\Users\ezabz\code\harness-config`.**

**Symptom.** `journal.py append decisions` allocated **D9410** for a new entry. `D9410` already
exists and means something else entirely: *"Owner answer, queue row #870: Adeena: whose card was the
Home Depot charge on? Not hers."*, committed 2026-10-21 on `secratary-cloud`. Two different entries,
one id, exactly the failure the claim protocol exists to prevent — and the append did not warn,
because from this machine D9410 looked free.

**The arithmetic, counted on both sides:**

| kind | entries here | entries on the authority | reserved through (authority) |
|---|---|---|---|
| handoff | **1,451** | **1,992** | H13032 |
| lessons | 1,857 | — | L13373 |
| decisions | — | — | D9984 |
| **total index** | **4,899** | **6,450** | — |

So the local counter was allocating from a frontier **1,551 entries stale**.

**Why the tool's own fetch did not save it.** `append` fetches by default (`--no-fetch` is the opt
out), and its allocator reads `entries/`, the cache **and every git ref**. But this checkout's
remotes do not include the authority's lineage: `origin` fetches from `secretary-ts` (the FROZEN
rollback anchor) and pushes to GitHub, and the authority's own checkout is a *different remote* here,
named `cloud`. Until `git fetch cloud` was run by hand, no local ref carried the authority's newer
entries — so "every git ref" meant every ref this machine had, which was the stale set.

**The measurement that proved it.** After `git fetch cloud` (68 branches, including the authority's
checkout), the *next* append was not silently written — it was refused by the claim guard:

```
REFUSING to write H13033: this id is above everything this machine can see, and it has just
reserved H13033..H13096 LOCALLY -- no other machine can see that window yet, so writing now is
exactly how two hosts mint the same number. Nothing was written. … run `journal.py claim handoff`.
```

…then, after `journal.py claim handoff | claim lessons | claim decisions`, the appends landed as
`H13033`, `L13374`, `D10049`. **That is the difference: before the fetch the allocator wrote
D9410 without a word; after it, the guard had something to guard.** The one measurement I failed to
take is the local `next-id` *before* the fetch — so the exact stale frontier this machine believed is
unrecorded. That absence is itself part of the finding: I learned about the collision from its
outcome, not from a check, which is how a silent drift stays silent.

**What was done, and what is still wrong.**

* The three entries from that append were **re-written on the authority**, where ids are allocated
 against the true frontier: `H13033`, `L13374`, `D10049`. The stale-range local files were removed
 and the authoritative files copied back, so this checkout now holds the correct ids.
* `repair-ids` correctly reported *"no id collides with different content"* — it compares within one
 tree, so it **cannot see a collision that lives only in another machine's branch.** It is not the
 tool for this failure and should not be trusted to clear it.
* **Still wrong:** this checkout remains 1,551 entries behind. Every append here will keep being one
 hand-fetch away from a collision. The fix is for this node's journal fetch to include the
 authority's lineage (a remote that actually reaches `secratary-cloud`'s checkout, or the
 `refs/heads/journal` published ref), and to make a stale local frontier **visible** — a
 `journal.py status` line saying "this checkout is N entries behind the authority", because a number
 nobody prints is a number nobody checks.

**The transferable rule:** a monotonic id allocated from a local cache is only safe if the cache is
known-current, and *the tool cannot tell you it is stale* unless someone compares it to the authority
on every run. Fetch before you believe a "highest seen", and when a repo has more than one remote,
find out which one carries the numbering authority before you trust a counter.
