## P339 — The tailnet hop to the authority fails about one attempt in five, and it fails in the middle of writes

**P · The tailnet hop from ZABZ-YOGA to the authority fails about one attempt in five, and it fails in the middle of writes.**

Ranked as the CFO session's worst operational obstacle, 2026-09-20, because it is the *only* path to every
authoritative thing this seat needs: the money feed, the books store, and the placement broker that runs
the fleet.

**Measured in a single 40-minute window**, same host, same session, no load change attributable to me:

- four consecutive TCP-22 probes to `secratary.tail93e6e6.ts.net` succeeded, and `tailscale status` showed
 `secratary ... active; direct 71.104.140.242:41642`;
- then repeated failures: `ssh: connect to host secratary.tail93e6e6.ts.net port 22: Connection timed out`,
 `Timeout, server secratary.tail93e6e6.ts.net not responding`,
 `banner exchange: Connection to UNKNOWN port -1: Connection timed out`;
- **one `subagent` dispatch died at placement** with `remote-ssh: broker-unreachable: the placement broker
 could not be reached at secratary-ts:http://localhost:3091/place — ssh exited 255: connect ... timed out`;
- and a **seven-section remote update part-applied**: the three obligation writes landed, then the
 connection dropped during the queue section, leaving `owner_decision_queue` untouched while
 `books.db` said the work was done. A reader comparing the two would have concluded the queue update was
 lost; a blind retry would have double-applied the obligations.

**What fixes it, in order of value:**

1. **Precheck before any script that writes.** `ssh ... "echo READY"` in a retry loop with
 `ConnectTimeout=12 -o BatchMode=yes`; send the real payload exactly once, only after `READY`.
2. **Make every remote write idempotent and self-guarding.** The obligation writes above were safe to
 retry because `--set-status` is a set, not an append. The queue adds were made safe by checking for an
 existing row whose question matches on its first 70 characters before inserting. Retry safety is a
 property of the payload, not of the transport.
3. **Split writes from reads.** Reads can be retried freely; anything that mutates should be its own
 short call so a drop cannot strand half of it.
4. **Prefer one payload over N hops.** Base64 the text into the single bash script (`--from-json` on the
 queue tool even documents "text never passes a shell") rather than building seven ssh calls.

**Still unexplained and worth a later session:** *why* the direct Tailscale path to one node flaps while
the same node answers TCP fine moments later. It is not disk, not the authority's load (the ingest ran at
~20 MB/s of SQLite work across the same window), and not this laptop's memory. Until it is explained, treat
this hop as **unreliable by default**, and design every remote operation as if it will be cut in half.
