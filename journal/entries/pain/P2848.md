## P2848 — P: dialpad_sms_cache backfills in bursts, so a reading from it is only true for one minute

MEASURED 2026-10-05, same query, same window (created_at >= 2026-09-01), 19 minutes apart:

 15:10:56 UTC rows in window = 213 (I built an 84-conversation queue on this)
 15:29:34 UTC rows in window = 10,836 (108 conversations, 165 with inbound)

The window grew by a factor of 50 inside one session. The harvest writer was still
loading the 2026-09-20 bulk row set while I read. I published "84 unanswered" from
the first reading and had to correct it.

WHAT THIS COSTS
This is the exact failure mode behind P3 (reading the wrong data and believing it).
The cache is not a snapshot with a timestamp I can trust; it is a moving window.

THE FIX THAT WORKS
build_queue.py now stamps generated_at into the JSON and the doc that quotes the
number says the number is true only as of that stamp. Any surface that shows a
count from this table must show its build time next to it. Never quote a saved
queue.json figure without re-running.

SECOND OBSERVATION, same day: the file mtime of secretary.db advanced, and the
read-only WAL snapshot a python client sees can lag the live writer by a lot. A
read-only connection is not a stable view.

WHAT WOULD FIX IT PROPERLY
A row-count and max(created_at) probe recorded on every harvest write, so any
reader can see whether the window is still filling.
