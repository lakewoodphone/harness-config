## P4569 — Journal autocommit is committing onto an unpushed session branch — main's tip is 2026-10-10

Measured 2026-10-15 23:59-00:02 UTC on secratary-cloud, ~/code/harness-config:

- HEAD branch is `i348-closing-courtesy-20261015`, and `git rev-parse
 --abbrev-ref --symbolic-full-name @{u}` returns
 `fatal: no upstream configured for branch 'i348-closing-courtesy-20261015'`
 — the branch is not pushed anywhere.
- `git ls-remote origin refs/heads/main` returns
 ee3a7e2f01b7b9e2c259a052d2cc93992f62830a, identical to the local origin/main
 ref, whose tip is 2026-10-10 20:14. So main genuinely has NOT moved; this is
 not a stale local ref.
- `git log --oneline origin/main..HEAD` lists the journal autocommit commits
 from tonight (23:00, 23:15, 23:30, 23:45 ...) and every one carries the
 message "journal: autocommit N path(s) on main from secratary-cloud" — the
 script says "on main" while committing on whatever branch HEAD happens to be.

CONSEQUENCE: every journal entry written on this box since 2026-10-10 20:14 sits
on an unpushed branch. The journal index on the authority still sees them
(ps_search what=journal reported covers_through 2026-10-15 22:12 UTC and 4166
entries), so a session ON the authority reads a current record — but any machine
that converges from main is reading a five-day-old journal. Silent staleness,
exactly the failure the memory-continuity audit warned about.

NOT FIXED. Merging a session branch into main is not a thing to do blind from
inside an unrelated task, and the branch may carry another session's in-flight
work. Needs: find who left the shared checkout on that branch, decide whether to
push it or land it on main, and make the autocommit job refuse (or at least
label honestly) when HEAD is not main.
