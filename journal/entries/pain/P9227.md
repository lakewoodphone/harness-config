## P9227 — CORRECTION to P9099: the API was not left down by another session - I restarted it mid-VACUUM and aborted that session's 34 GB database compaction

## 2026-10-19 ~18:30 UTC · ZABZ-YOGA · CORRECTION to P9099: the API was not "left down" by another session — I aborted its database compaction

P9099 recorded that "another session stopped company-api and left it down for six minutes" and filed
it as an outage. **That is wrong in the part that matters, and the correction is mine.**

WHAT ACTUALLY HAPPENED, read from `ps` and the script itself:

1. Another session started `/root/bin/compact-authority-db.sh --apply` at **18:17:5x**. That script
 compacts the **34 GB** authority database by `VACUUM INTO` a copy, and it deliberately
 **stops every writer, company-api included**, because a copy taken with writers running cannot be
 trusted. Stopping the API is the script being CORRECT, not a fault.
2. I found the API inactive, read it as an outage, and **restarted it at ~18:14 and again at
 ~18:18:40 - both times while the VACUUM was copying.** I then stopped it again at ~18:22 to "get
 out of the way", which was right, but the damage was already done.
3. The script's own safety gate caught it: the copy no longer matched the database because writes had
 landed after the snapshot began, so it **refused to swap, cleaned up, and restarted the units**.

OUTCOME, verified: the database was **never replaced** (still 34,096,103,424 bytes), the compact-tmp
and any pre-compact file are **gone**, `text-health` is **18 checks 0 FAIL**, and `/health` answers
200 in 0.006 s. **No data was lost and nothing was corrupted.** What was lost was the compaction: ten
minutes of a 34 GB job, discarded.

THE RULE THIS COST. **A service that comes back stopped, or that is stopped with writers paused and a
database-shaped process alongside it, is a maintenance window - not an outage.** Before restarting
anything: `ps -eo pid,etime,cmd | grep -E "compact|VACUUM|backup|restore"`. The `estate-monitor` and
`r4-liveness-probe` did not escalate because the stop was clean and the unit was expected to return.

AND THE ONE THING I DID RIGHT: I read the cause before acting a second time, and stopped interfering
once I understood it. The first restart, though, was reflex - "the API is down" - and it cost a
session's work. P9099's headline is retracted; what remains true is only that a clean, deliberate
stop should be checked against a maintenance process before it is called an outage.
