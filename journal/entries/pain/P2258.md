## P2258 — ~/bin on secratary is unversioned: 50 operator scripts, including the only writer of the owner queue

## What hurts

`~/bin` on secratary is **not a git repository**: 50 scripts that operate the
company, unversioned, with no history and no remote. That includes
`owner-queue.py` -- the only writer of `owner_decision_queue`, the queue the owner
reads and the kernel prints -- and `textsend.py`, which carries the owner-SMS
kill-switch logic.

Anything in it can be changed or lost with no record of what it said before, and
no other machine can see it. It is also where the operator entry points for this
business live, so a lost file is a lost capability.

## Measured

2026-09-23: `cd ~/bin && git rev-parse --show-toplevel` -> "not a git repository";
`ls ~/bin | wc -l` -> 50; no cron or script references a versioned copy of
`owner-queue.py` (the journal and the MCP surface both shell out to this path).

## What would fix it

`git init` in `~/bin`, with a remote on the same bare repo host the other repos
use, plus a `.gitignore` for `__pycache__`. One commit of the 50 files is enough
to stop the loss; review of what is stale can come later. Cheap, and it removes a
class of silent, unrecoverable change.

## Why it is worth recording

This is the same defect as P8 (harness configuration drifts between machines) in a
directory nobody has looked at, and it is the single place in the stack where a
"one source of truth per thing" rule is not merely broken but unenforceable.
