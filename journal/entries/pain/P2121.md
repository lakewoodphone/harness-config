## P2121 — P347 - RESOLVED-in-part: the corrupt-task producer died on 2026-09-11, so this is legacy data, not a live bug

**Correction to my own earlier report.** I described the 1,650-1,660 corrupt task titles as
"escalating: Jun 65 -> Aug 1,010 -> Sep 507". The producer is dead, and the "Sep 507" is entirely
from 1-11 September.

Measured 2026-09-20 on the authority:

 newest corrupt title : 2026-09-11T01:09:27Z
 last 14 days, by day : all rows are 2026-09-06..2026-09-11, NOTHING after
 last 24 hours : 0
 tasks created in last 24 h : 192

So the write path that produced them stopped on 2026-09-11 - the same day as the completion-predicate
commit (`53739081`), which is likely not a coincidence. This is **legacy data**, not a live defect,
and I should have checked "is it still happening" before ranking it as an open bug. The lesson is
general: before ranking a defect, measure its *rate*, not its total.

What I did about the data: `~/migrations/ops/repair-corrupt-task-titles.py`, dry-run by default.
Of 1,681 rows matching the broad heuristic, **171 carried a recoverable real title** in their
embedded action payload - those were repaired and the old title preserved in `metadata_json` as
`recovered_title_from`, with an id/old-title CSV at
`~/code-backups/20260920T162023Z/corrupt-titles-backup.csv`. Examples now readable:
`Audit closed tasks for evidence (last 30)`, `P0 Fix world_context import error 'list_messages'`,
`Confirm T-Mobile security alert with owner - lock/reset if NO`.

**The other 1,510 were deliberately left alone.** Their only recoverable content is the model's
preambular prose ("I'll scan the live finance state before generating tasks") or nothing at all.
Rewriting JSON noise into prose noise would have been cosmetic - tidier to look at, no more
informative - and it would have destroyed the evidence of what went wrong. A recovery that cannot
recover a *meaningful* title should report the row, not decorate it. All 1,681 are `status='done'`
and none is open, so nothing is currently misled by them.
