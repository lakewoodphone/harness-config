## P2849 — P: build_tool is an unrestricted arbitrary-path file write and code-execution channel on secratary

DISCOVERED 2026-10-05 when a subagent had no shell on its host but needed to write a
file that lives on secratary.

WHAT THE ACTION DOES
The secretary action `build_tool` writes a Python module under
/home/zabz/personal-secretary-mvp/data/tools/ and the built tool is then executable
as an action by its own name. The caller''s payload is injected into the module body
byte-for-byte. Therefore: build_tool == run arbitrary Python on the authority, and
a module can write any path that process can reach. A child used it to write
/home/zabz/_scratch/dialpad/style-profile.md on secratary, which was otherwise
unreachable without a shell.

WHY THAT IS A PROBLEM
1. Any agent, from any lane, can execute arbitrary code on the authoritative host
 through an action that does not read like code execution.
2. It writes into the company repo tree (data/tools/), which is not a scratch area.
3. It is discoverable by accident. That is exactly how it was found.

DAMAGE THIS TIME
The child''s first exploratory module was named `probe`. If a tool named `probe`
already existed, it overwrote it and then deleted it during cleanup, and it cannot
restore it. Only files were removed; no registry rows. UNKNOWN whether `probe`
pre-existed. Check data/tools/ git history for probe.py.

WHAT WOULD FIX IT
- Either drop arbitrary module names and content from build_tool, or gate it behind
 the same per-action owner approval as other code-writing actions.
- Log every build_tool call with the module name, the caller lane and a content
 hash, so an overwrite of an existing module is detectable.
- Give lanes that legitimately need to place a file on secratary a narrow, named,
 path-constrained action instead of leaving code execution as the only route.
