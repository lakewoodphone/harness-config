## P2808 — Two family-chat tests are red on any non-UTC host: UTC/ISO timestamps compared against the local-time store

## P — Two family-chat tests are red on any non-UTC host, and they are red because two code paths compare a UTC/ISO timestamp against the store's local-time strings

MEASURED 2026-09-30, on ZABZ-TECH (UTC-4), in a clean worktree at the authority's own commit `49134262` — so these failures predate every change of this session and are NOT introduced by it:

```
FAILED tests/test_family_chat_robust_hubrecord.py::TestReconciliation::test_sidless_row_is_matched_by_recipient_and_time
FAILED tests/test_family_chat_robust_storage.py::test_list_pending_outbox_picks_up_legacy_iso_rows
2 failed, 624 passed
```

THE CONVENTION, FROM THE CODE'S OWN COMMENT (`db.py:147-174`)

The family-chat store has exactly ONE stored timestamp format: space-separated **local** time (`_TS_FORMAT = "%Y-%m-%d %H:%M:%S"`, written by `db._now()` = `time.strftime` = local). `_canonical_ts()` converts any tz-aware caller value to local naive. This is deliberate and documented; it exists because a UTC ISO string ("…T18:35:00+00:00") once sorted *greater* than every same-day local `_now()` — 'T' > ' ' — so no outbox retry was ever selected until midnight, and 18 messages were dropped.

WHAT BREAKS OFF-UTC

1. `list_pending_outbox` compares `next_retry_at <= <_now()>` **textually**, and a legacy row written in the old ISO form still contains 'T', so it sorts after every same-day local stamp and is never due. The test writes such a row on purpose and asserts it is picked up — it is not. Fix: canonicalise the candidate rows on read (a `LIMIT`ed SELECT plus a Python filter through `_canonical_ts`), not just on write.
2. `reconcile_with_twilio` matches a SID-less local row against Twilio's `date_sent` (UTC) by recipient and time; on a non-UTC host the two are hours apart and nothing matches. Fix: convert one side explicitly (`_twilio_local_ts` exists for exactly this) before comparing.
3. A third instance was fixed on 2026-09-30 while working on the hub: the status-reconciliation cutoff had been `gmtime` while the rows it selects are local-stamped, so on a non-UTC host every row younger than the UTC offset was skipped. That one was caught only because `tests/test_family_chat_reconcile.py` writes its row with `time.gmtime` — and that test only passes on a UTC host. The test now stamps the store's convention.

WHY IT IS NOT AN EMERGENCY, AND WHY IT IS STILL MINE

The authority's clock **is** UTC (`date` reports UTC), so local == UTC there and all three coincide in production. The cost is different and real: **the suite is red on a laptop**, so the next person to run it cannot tell a genuine regression from these two, and a red gate is a gate nobody reads.
