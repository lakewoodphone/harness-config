## 96% of the SMS table is copies of other rows, and the dedupe key cannot see it

Measured 2026-09-20 ~20:15Z on the authority, from `dialpad_sms_cache`:

- last 24h: **4,637 rows, 201 distinct (phone, body) pairs, 4,637 distinct message_ids**.
- One body from Levi (732-575-4823) has **61 rows** since 2026-09-16 -- 50 of them in the last 24h.
- Every `message_id` is distinct, so the writer's `INSERT OR IGNORE` on
 (session_id, message_id) never suppresses anything.

Mechanism, read from p&t-full Postgres `communications` (the harvest's source): each row
carries `metadata.source='dialpad_sync'` and `metadata.external_ref =
'dialpad:sms:ptf-comm-<another communications row of the SAME message>'`, e.g.

 id 137158 -> ext ptf-comm-137105
 id 137106 -> ext ptf-comm-136811
 id 136812 -> ext ptf-comm-136759

So the writer copies its own output back into the table, one generation per cycle, each
copy registering a fresh id. `metadata` holds only `external_ref` and `source` -- no
Dialpad message id and no customer send time -- so nothing in the chain carries a stable
identity to key on.

Consequence: rows are not messages. Every consumer that treats a new row as a new message
sees each customer text roughly 23 times. That is the shape of the duplicate-task churn
around Levi: 10 tasks over four days, all marked done, and no reply ever sent.

It hurts because (a) freshness and volume read from this table are wrong by ~25x; (b) a
genuinely new message cannot be told from a copy, so a dead upstream and a healthy one look
identical; (c) it is accelerating -- 61 copies of one message in four days, 50 of them today.

What would fix it: stop the self-referential write in the p&t-full `dialpad_sync` writer,
then key our harvest on the true Dialpad message id (the webhook rows already carry one,
e.g. 4981260336799744) instead of the ptf row id. Until an identity exists our side can
only de-duplicate on (phone, direction, body) plus first-seen, and must say it is guessing.
