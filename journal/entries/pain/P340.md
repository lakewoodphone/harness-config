## P340 — The authority is a 4-core box with ~19 cron jobs and a live API, so ssh to it times out under load - and retry storms make it worse (corrects P339)

**P · The authority is a 4-core box running ~19 cron jobs and a live API, so `ssh secratary-ts` times out under load - and retry storms make it worse. This CORRECTS the diagnosis in P339.**

**Why this entry exists:** P339 (written 2026-09-20, same session) recorded the failures and said the
cause was *"still unexplained... treat this hop as unreliable by default"*. That was incomplete. An hour
later the same host was measured properly and the cause is not the tailnet at all.

**Measured on the authority, 2026-09-20 15:26-15:28 UTC:**

```
nproc : 4
uptime : load average: 10.76, 14.71, 13.33 (and 8.77, 13.24, 12.96 two minutes later)
free -m : total 23421, used 4470, free 314, available 18951 <- memory was NOT the problem
tailscale ping secratary -> pong ... in 44ms <- the network path was healthy the whole time
sshd : 8 established connections, 14 sshd-session processes
```

**What is loading it.** Not one runaway process - a *population*:

| Load source | Evidence |
|---|---|
| uvicorn API `app.main:app` on :8002 | 7.5 % of 23 GB = ~1.7 GB resident, 6.5 % CPU, restarted 15 min earlier |
| Next.js dashboard | `next-server (v16.1.6)`, 12 min old |
| A second DSH engine | `dsh-engine/.../bin.js web --port 3089`, **3 days 8 h uptime** |
| Headless Chrome bursts | sampled at 00:00 elapsed using **72 % CPU** each; 10 chrome processes at that instant, **0 two minutes later** - something spawns them and they exit |
| **~19 crontab entries**, several sub-10-minute | including `serve-phone.sh` **every 2 minutes**, mesh-health / uvicorn-watchdog / ceo-kernel-sentinel **every 5**, node-agent / owner-digest / git-health / dialpad-harvest **every 30** |

Four cores cannot absorb that. Load 9-13 on 4 CPUs means every new TCP connection waits, which is exactly
the symptom: `Connection timed out` and `banner exchange: Connection to UNKNOWN port -1` **while
`tailscale ping` answers in 44 ms**.

**The second half of the finding, which is about me rather than the host:** the failure pattern is
*load-sensitive and self-reinforcing*. A single connection attempt after a pause succeeded **three times
in a row**; a precheck loop firing every 3-4 seconds failed **3 attempts of 10 retries each**. Each
attempt spawns an `sshd-session`, and the box was already at 14. **My retry storm was part of the
outage.**

**So the rule is the opposite of what P339's pattern recommended:** against a *saturated* host, do not
poll. Pause 30-45 s and make **one** attempt. Use a retry loop only against a host that is up but
flaky - and never with a 3-second cadence.

**The fixes, in order of value, none of them applied yet (this is production automation on the company's
authority and it is not this seat's to change unilaterally):**
1. `serve-phone.sh` every 2 minutes is the densest job on the box; find out whether it needs to poll at
 all (it looks like a keep-alive) and move it to a systemd unit or a 15-minute cadence.
2. The second DSH engine on :3089 with 3+ days of uptime - confirm it is wanted; if it is idle it is
 ~1 GB and a permanent CPU cost.
3. Count the Chrome spawns over a 10-minute window and find the caller; a screenshot loop that launches a
 fresh headless Chrome per call will look exactly like this.
4. Only then consider moving the books pipeline to the authority as a nightly job - **it is fine to run
 there, but not during a browser burst**.
