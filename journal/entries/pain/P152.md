## P152 — 64 caseIds carry two sync records; the phone bundle builder reads that directory authoritatively, so projection is a coin flip

MEASURED 2026-09-15 (ZABZ-TECH, script over docs/customer-operations/sync-records/*.json): **378 files, 313 distinct caseIds, 64 caseIds with more than one file.** 104 of those files are legacy-named duplicates of a canonical `<caseId>.json`.

Why it is not cosmetic: `docs/customer-operations/CROSS_REPO_CUSTOMER_SYNC_CONTRACT.md` says the phone repo bundle builder reads `docs/customer-operations/sync-records/*.json` FIRST and that "the structured sync record is authoritative for projection fields". Two records with the same `caseId` therefore project NON-DETERMINISTICALLY -- whichever the loader reads last wins, and the loser's staleness is invisible. Worked example: `2026-08-06-usb-files-disappeared-tbd` had a canonical record carrying `labState: chip-off-pass1-partial-retry-running` (2026-09-15) and a legacy record still carrying `labState: shipped-in-transit` (2026-08-12).

Root cause: the 2026-09-10 canonicalization wrote `<caseId>.json` everywhere it could but never retired the ad-hoc-named file it superseded (e.g. `usb-files-disappeared-tbd-2026-08-06.json`, `dell-latitude-7400-bachrach-brother-2026-08-04.json`). Two ad-hoc retirement conventions have already been invented by hand -- `.json.bak` (`sd-card-ellman-2026-06-01.json.bak`) and `.json.localdup-122521` (`apple-macbook-air-a1932-yechezkel-yanofsky-2026-09-07.json.localdup-122521`) -- which is the tell that this keeps being rediscovered instead of mechanized.

Fix design (executable, not done yet): a script that (1) groups by `caseId`, (2) for each group keeps the file whose basename equals `<caseId>.json` and MERGES any field present in the loser but absent from the keeper (never blind-delete -- a loser may hold the only copy of a field), (3) renames the loser to `<name>.json.superseded-<YYYY-MM-DD>` so it stops matching the `*.json` glob while staying readable, (4) re-runs `lptcase.py index` and asserts each caseId appears exactly once. Then `lptcase.py check` should drop the `[sync-record-without-case] 226` class materially -- that class is very likely mostly these same duplicates matched to case files by the old basename heuristic.

Also worth fixing at the same time: `lptcase.py check` currently has no `duplicate-caseId` problem class at all, which is why 64 of them accumulated silently. Add one.
