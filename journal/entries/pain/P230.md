## P — the deployed fleet-api and the repo copy have forked in both directions

Measured 2026-09-17 while doing the Screen Time practice. `/opt/waze-mdm/fleet-api/fleet_api.py` on Hetzner (348,219 bytes, mtime 2026-09-15 21:38Z, the file the running container actually serves) is md5 `ABA5F091269311E6EF68EEB2CA989B21`. The repo copy `personal-secretary-mvp/deploy/waze-mdm/fleet-api/fleet_api.py` (318,014 bytes) is `3741035E8D34548D0B3ECEACF611474D`. Both define 255 functions/endpoints, but **each has seven the other lacks**:

- deployed-only: `_redact_dsn`, `missing_integration_config`, `_iso_utc`, `_ever_replied_state`, `_device_row_to_dict`, `_stuck_alert_like`, `_raise_alert(...) -> tuple[int,int,int]` — the liveness/alerting work.

**Why it hurts:** editing the repo copy and deploying it would silently remove the deployed liveness/alert behaviour; and reading the repo copy to predict production behaviour is simply wrong — it already produced one 404 on an endpoint I intended to use for verification.

**What would fix it:** reconcile both copies into one file (union, resolving `_raise_alert` to the 3-tuple version and updating its callers), commit the merged file, then deploy and verify `/health` and `/fleet/alerts` before anything else, and make deploying-from-repo the only path. Not done — it is a production-facing change and was outside the owner's Screen Time task.
