## P2539 — The Shabbat power-down has hard-cut Home Assistant every week - the graceful stop has never worked

**The Shabbat power-down has hard-cut Home Assistant every week — the graceful stop has never worked.**

`_power_down_critical` asks HA to stop cleanly before the Shelly plug opens, so its
recorder DB is flushed. Measured 2026-09-25: the call had been answered
**HTTP 400** on every run since go-live —

```
2026-09-25T21:03:59 WARNING app.services.home_assistant: Graceful HA shutdown failed:
 400 Client Error: Bad Request for url: http://homeassistant.local:8123/api/services/homeassistant/shutdown
```

— because the service name was hardcoded for a version of HA this install does not
expose (HA 2025.10 running as a container). The orchestrator logs and proceeds, so
the failure was invisible in every report; only the journalctl line carried it.

FIXED 2026-09-25 (code deployed, tests green): `shutdown()` now tries
`homeassistant.stop` → `homeassistant.shutdown`, returns ok only for the one that
answered, names it, and carries every failed candidate's error. **Still unverified
against a live HA** — the household is mid-run until Sunday 2026-09-27 ~20:28 EDT,
so the first real proof is the next power-down (Fri 2026-10-02 15:37 EDT, offset
180). Until then the honest statement is "the 400 is explained and handled", not
"HA now stops cleanly".

Second, smaller hole closed in the same change: because the 400 meant HA was always
still UP at the pre-cut re-verify, that gate had never once been exercised in
production against a *stopped* HA. A working stop would have aborted every
power-down. Verified with tests, not with hardware: `tests/test_shabbat_orchestrator.py`
now covers unlocked / locked / unreadable-after-requested-stop / unreadable-with-no-stop.
