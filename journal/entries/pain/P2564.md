## P2564 — P-two-sessions-one-production-tree: concurrent deploys silently revert each other, and 'anchor missing' reads as 'already applied'

Two DSH sessions deployed to /home/zabz/personal-secretary-mvp within seven minutes of each other on 2026-09-28 (mine at 16:09-16:14, another session's 'W1/W6/FU1/FU2/FU3' branch co/merged@f980fa4c2 at 16:09:24 and 16:16:31, journal H2782). The other deploy restored app/autopilot.py from /home/zabz/pre-deploy-20260928T161631Z, silently REVERTING my patches C and E in that file and leaving patch A. Nothing errored; nothing logged it. It was found only because I grepped for edits I expected to be there.

WHY IT IS DANGEROUS: the reverted edit was the delivery-target fix (patch D's autopilot half) plus the shortening and refusal-split logic. A revert of a safety fix looks exactly like a healthy tree.

THE COMPOUNDING FAULT, which is mine: my anchored patch scripts print 'ALREADY APPLIED or anchor missing, skipping' when an anchor is absent. After a concurrent revert, an absent anchor means the opposite of already-applied. That message is a false negative that reads like success.

WHAT WOULD FIX IT:
 1. After applying, VERIFY by grepping for a marker the edit introduces, and fail loudly if absent. Never infer presence from an absent anchor.
 2. A deploy lock on the production tree (flock on a file), so a second deploy waits or refuses.
 3. Record the tree's per-file hashes in a manifest at deploy time, and check them at the start of the next session, so a revert is visible instead of silent.
