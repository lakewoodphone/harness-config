## P2858 — The interior door's only actuator is the dead server, and two docs disagree about whether it locks on Friday

**What hurts.** A physical safety interlock — the interior maglock between LPT/control room and the
house — has exactly one actuator, and it is the machine that is currently dead. Worse, the repo's own
two records of that mechanism contradict each other, so the system cannot currently say whether this
Friday's automated power cut will lock a door.

**The mechanism, as the docs describe it.**
- The Shabbat power-down sequence is `unlock interior maglock → graceful HA shutdown → plug off`
 (`docs/operations/security-program/shabbat-power-automation.md:52`).
- The release is the secretary's job, not the plug's: *"The plug alone can never release the
 maglock, because the maglock is on separate power"* (`:53`).
- Therefore a dead secretary + an on-device OFF schedule = a locked door that nothing can unlock
 until the plug's own ON time, ~28.6 hours later.
- This has happened: `docs/postmortem/2026-09-11-shabbat-powerdown-lockout.md`, severity high.

**The contradiction that makes it un-assessable from here.**
- `shabbat-power-automation-hardening.md` (defence-in-depth table): *"Fail-safe executor | if the
 secretary is down, nothing is cut (no device-side off-schedule)"*.
- `shabbat-power-automation.md` (status LIVE, 2026-09-25): the on-device schedule is *"the fallback:
 dated one-shot OFF/ON per power-down block. Fires even if the secretary or HA is down"*, and it
 records a real power-down firing at 17:04:09 EDT on 2026-09-25 with the plug's ON jobs *"untouched,
 so power returns even if the secretary is down"*.

Two live documents, both marked as current, disagreeing about whether a door can be opened. Neither
can be believed alone, and the resolution requires the shop LAN (`Schedule.List` on the plug) or the
Shelly Cloud app — both unavailable while the site is offline.

**What would fix it, in order of durability.**
1. **Take HA off the Shelly** (`shabbat-power-automation-hardening.md` "Path A — rewire"): cameras
 alone on the plug, HA on permanent power. Then no power-down can ever remove door control.
2. **Fit a mechanical hold-open / keyswitch** so the door does not depend on any computer at all.
3. **Make the arming interlock refuse to write an OFF schedule unless a hold-open is proven**
 (the code already refuses on `DoorNotVerified`; what is missing is the fallback it is checking
 for), and record the proven state in one place the docs cannot contradict.
4. **A single source of truth for the door's state** — the current situation is two prose documents
 in the same repo asserting opposite things about a physical lock.

**Why it is ranked here.** Not because it is the most likely failure, but because it is the only one
in this system with (a) a deadline, (b) a human consequence rather than a business one, and (c) a
recovery that cannot be done remotely.
