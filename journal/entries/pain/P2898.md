## P2898 — OWED: rotate LPT_SSO_SHARED_SECRET on prod and test, coordinated with the rentals and chumash SSO clients

# OWED: rotate LPT_SSO_SHARED_SECRET on production and test, because I printed it

On 2026-10-09 I ran an env probe over ssh to `lpt-apps` that echoed `"$k = $v"` instead of the
length, and wrote the live shared SSO secret for BOTH the production and the test backend into the
session transcript. The lesson recording the idiom is L3442.

WHY IT IS NOT A ONE-HOST EDIT
That secret is the credential the rentals (`rentals.lakewoodphoneandtech.com`) and chumash
(`chumash.lakewoodphoneandtech.com`) apps present to `POST /api/auth/sso/assert` as
`x-lpt-sso-secret`. `app-registry.ts` (`:133`, `:180`) records both as `session: 'shared'`. Rotating
it means: generate a new value, set it on both LPT backends AND both consumer apps, restart, then
verify an assert succeeds - and the window between the two is a window where cross-app sign-in fails.

State at the time of writing: prod and test carry DIFFERENT values (so a rotation is already two
independent acts), both are >= 16 chars, and `POST /api/auth/sso/assert` with no cookie returns
`403 sso:forbidden` on both - i.e. it is configured, fail-closed and live.

WHAT WOULD FIX IT
A `docs/operations/SSO-SECRET-ROTATION.md` that names all four holders and the order, plus a single
script that rotates the LPT side and prints the value the two clients must be given. The rotation
itself is a scheduled, low-traffic-window change, not a hot fix.

HONEST NOTE
The exposure is this conversation and whatever logs it, not the public internet. The secret was
never served to a browser and the endpoint is fail-closed. That lowers the urgency; it does not
remove the obligation, and it is written here so it cannot be quietly forgotten.
