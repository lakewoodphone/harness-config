## P2894 — No mesh subagent can start: the child engine dies on a failed MCP mount (mcp.jina.ai ENOTFOUND) before it reads its task

MEASURED 2026-10-09, twice, from ZABZ-YOGA. I delegated a self-contained engine
fix with `subagent` (the mesh provider). Both attempts returned:

 status: failed, error; the remote one-shot exited 1 and produced no final message
 Error: getaddrinfo ENOTFOUND mcp.jina.ai
 at async fetchWithMcpHeaders (.../mcp-remote/dist/chunk-CGVEK4Z7.js:32228:20)
 errno: -3008, code: ENOTFOUND, syscall: 'getaddrinfo'

The child never read the prompt. Its ENGINE died while mounting an MCP server, and
a failed MCP mount is FATAL to session startup rather than a soft, reported
degradation. So on any node that cannot resolve mcp.jina.ai, the whole fan-out
plane is unusable -- not degraded, unusable -- and the failure arrives to the
parent as an opaque "exited 1, no final message" with the real cause buried in a
stderr tail.

WHY IT MATTERS BEYOND THIS TASK: the standing instruction is to DEFAULT to a fleet
on any larger job. A silent, total fleet outage means every such job quietly
becomes serial again and nobody learns why. Two delegations were spent, and the
work was then done single-threaded, which is exactly the fallback the instruction
says should NOT be the default.

WHAT WOULD FIX IT: (1) an MCP server that fails to connect must degrade -- the
session starts, the tool is absent, and the failure is published, which is the
same fail-soft rule the gateway already follows for models; (2) the child's
launcher should surface the first stderr line as the diagnostic rather than a
truncated tail; (3) `subagent` should try another node when a child dies before
its first step, since the cause is node-local DNS; (4) the parent should be told
"the mesh could not start a child" as a distinct, one-line outcome so the
fallback is visible rather than inferred.
