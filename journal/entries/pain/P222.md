## P222 — §4.5's kill-the-gate step can only be satisfied by breaking S7's own never-kill-a-foreign-process rule

WHAT HURTS
§4.5 as written cannot be executed honestly by the stream that owns it. Its kill half says "kill the
chosen node's gate mid-run", but the only gates running on a real node were deployed and started by
another stream, and stream S7's own brief says "never kill a process that is not a gate you started".
Two rules from the same program, pointing opposite ways, with a green acceptance box in between.

This is the failure mode the program exists to prevent, one level up: an acceptance criterion that can
only be satisfied by breaking a safety rule will eventually be satisfied by breaking it, quietly, by
whoever is under pressure to make the box green.

WHAT WOULD FIX IT
Name the exception before it is needed. Either (a) state in §4 that the kill test targets a stub gate
the harness itself started - which is what S5b does today, and it proves the same broker-side property
(reclaim within TTL, next placement elsewhere with no repair) - or (b) have the manager authorise one
named pid on one named node, in writing, so the kill is a decision rather than an improvisation.
Until then S7 skips the step and says why, which is the honest answer and the cheap one.
