## P179 — parallel worktree agents share one node_modules; local DB measurement needs a tunnel

1. The shared node_modules junction is a single point of failure for seven parallel agents.
What hurts: at 18:04 on 2026-09-15 another process ran an npm operation in C:\Users\ezabz\Code\chumash-timeline and every worktree's node_modules (a junction to that directory) lost typescript, vitest, react-dom and the whole .bin directory. npx stops working inside a worktree and `npx next build` cannot be run at all, with no local remedy (npm install is forbidden in a worktree).
What would fix it: a per-worktree install (or a shared read-only store that agents never write to, e.g. pnpm's store plus per-worktree node_modules), and a rule that nobody runs npm install/ci in the main clone while worktrees are live.

2. A long-lived SSH tunnel to the office Postgres is required to measure anything locally, and it inflates every round trip by ~110 ms.
What hurts: before/after endpoint numbers are not comparable to the live host, and any claim built on them has to carry the caveat. My first tunnel also lost a port to another agent's stale tunnel on 15432 (two listeners, ECONNRESET on every connect) — the fix was to just pick another port.
What would fix it: a documented scratch-DB tunnel convention (per-agent port range) in the repo, or running the measurement server on the DB host.

3. The product rule "empty is not failure" is only enforceable while the data layer keeps throwing on failure.
What hurts: src/lib/server/feedback-db.ts still returns null/false for write failures and swallows the underlying error, so /api/feedback and /api/submissions can only answer "the store did not accept the write" without knowing why.
What would fix it: have those functions throw (StoreUnavailableError for a missing store, the pg error otherwise) so the route can report the real cause.
