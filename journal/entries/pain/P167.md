## P167 — The database corruption alarm has no transport - it could never alert, and that is why the integrity check ran twice

MEASURED 2026-09-15 (secratary, ZABZ-TECH session).

FINDING: the database corruption alarm cannot alarm. The cron
`*/15 * * * * ... PRAGMA integrity_check ... | mail -s "SECRETARY DB CORRUPTION DETECTED" root`
has been the corruption tripwire for the 4.48 GB authoritative store. `command -v mail` on secratary
returns NOTHING -- there is no mail binary. So the alert has never been deliverable.

SECOND-ORDER EFFECT, and this is how it was found: because `mail` did not exist, the first pipeline exited
non-zero, which tripped the `||` fallback and made the cron run `PRAGMA integrity_check` a SECOND time.
Measured: the cron's real cost was 49.3 s every 15 minutes (~78 min/day of full-store reads on the live DB)
and it was ~5.4% of wall time -- all of it caused by an alert path that could not work.

FIXED (manager), verified: rewrote the line to a single run that keeps working when mail is absent --
`out=$(sqlite3 ... "PRAGMA integrity_check;" 2>&1); case "$out" in ok) ;; *) printf "%s\n" "$out" | mail -s "..."
root 2>/dev/null; echo "DB corruption detected at $(date)" >> ~/secretary-db-errors.log ;; esac`.
Verified under POSIX `/bin/sh` (cron's shell, not bash): exit 0, `cronline_wall=22.53s`. Note `quick_check` is
NOT the fix here -- measured 16.2 s vs 20.3 s, only ~20% cheaper; the win was the double-run.

STILL OPEN, and it is the honest part: `~/secretary-db-errors.log` now receives the write, but NOTHING READS
IT. The tripwire still cannot reach a human. What would fix it: route the corruption line into the existing
attention surface (the harness phone badge / owner-attention-digest, which already carries other checks), or
into the CEO kernel's check set -- and then prove it by making the check fail deliberately and observing the
alert arrive. Until that is done, do not describe database corruption as monitored.

Corollary worth carrying: an alert path with no transport is worse than no alert path, because the code
reads as if the case is handled. This is the same species as the `/health` endpoint that returns HTTP 200 on
a failed write path and the `error_log` that records 114 of 7,461 lock errors.
