## P3808 — I printed a live BitLocker recovery key into the archived transcript - I masked the hyphenated form by PATTERN and the file also carries the same key as 48 bare digits

## What I did

While displaying the proof run's readable report, I masked the BitLocker recovery key by **pattern**:

```
-replace '\d{6}(-\d{6}){7}', 'XXXXXX-XXXXXX-...'
```

That matches the hyphenated 8x6 form only. The same file also carries **the same key as one continuous 48-digit number**, because a technician needs one form at a recovery screen and `dislocker` takes the other. The mask did not match it. **The recovery key printed in full, into a session transcript that is archived forever** — AGENTS.md section 1: raw archive on `secratary`, parsed into `secretary.db`.

So a live customer credential is now in the estate's own permanent record, put there by me while I was trying to be careful with it.

## The rule this earns

**When masking a secret, mask every form of it — not the form you happen to be looking at.** A BitLocker recovery password has at least two written forms (hyphenated 8x6, and continuous 48 digits) before you even get to the raw bytes. A pattern mask that matches one leaves the other.

The safe pattern, and what I should have done from the start:

1. **Do not print the file.** Extract the value once and print only a **sha256 fingerprint** — that is what proves a copy is intact and it is safe to publish.
2. If a whole file genuinely must be shown, mask **by value**, not by pattern: `$text.Replace($key, 'REDACTED')`. The value is known, so there is no excuse for a pattern that only sometimes matches.
3. Assume any secret has more than one encoding. Check the mask by searching the masked output for **any** 6-digit run, not just for the pattern that was replaced.

## Consequence, stated as a range and not as a reassurance

- The key is **not** in git and **not** public. It **is** in the internal session archive, readable by anyone with authority-box access and copied into `secretary.db`.
- The value is a **live unlock key for a customer's 512 GB BitLocker volume** (Ullman, WO26101312747). The drive is 100% XTS-AES128 encrypted and that key is the only way in if the board finally dies.
- **Rotation is available and safe**: `manage-bde -protectors -add <vol> -RecoveryPassword`, then delete the old protector, then re-capture. It needs the machine, and it makes the stored copy stale until re-captured — so it is the owner's call, not mine.
- Fingerprint of the exposed value, safe to write down: **`79bc71baee75802b`**.

## The wider point

Earlier the same day I handled a different customer credential correctly: the Windows sign-in PIN was never written into any note, file or repository, only its location. This is the first time I have put a secret into the archive myself - and it happened in the very step where I was thinking hardest about protecting it. **Care taken at the point of capture is not care taken at the point of display**, and display is the step with an audience.
