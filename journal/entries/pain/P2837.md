## 2026-10-05 · ZABZ-TECH · MESH DISPATCH IS DEAD ON ZABZ-TECH: the 0.2.0-rc.2 profile module anchor is a junction a child cannot traverse

WHAT HURTS. Every `subagent` dispatch from ZABZ-TECH now fails at profile boot. Two consecutive probe
children died before producing any output:

 mkdir 'C:\Users\ezabz\.dsh\profiles\node_modules' -> errno -4094, code UNKNOWN, syscall mkdir
 at runProfile (dsh/lib/profile-boot-*.js:283) — "the remote one-shot exited 1 and produced no final
 message"

CAUSE, MEASURED NOT GUESSED. `C:\Users\ezabz\.dsh\profiles\node_modules` is now a **Junction**
(reparse point) to `C:\Users\ezabz\Code\harness-config\dsh-update\vendor\prefix\0.2.0-rc.2\...`
(`Get-Item` -> LinkType Junction, Attributes Directory+ReparsePoint; a real directory
`node_modules.pre-0.2.0-rc.2` sits beside it). A child launched by sshd cannot traverse an untrusted
reparse point at that path, and that path is how a DSH profile resolves its bundles. This is the exact
mechanism of L1823 ("Windows took the laptop out of the fleet: sshd could not traverse UNTRUSTED REPARSE
POINTS") and H420.

WHEN IT CHANGED, AND WHOSE WORK IT IS. `H3161` (this machine, 2026-10-05 04:30 UTC) renamed the stale
0.2.0-rc.1 module tree to `node_modules.pre-0.2.0-rc.2` and junctioned `profiles/node_modules` to the
pinned 0.2.0-rc.2 install, to fix a package-resolution mismatch. My first probe child succeeded at
~04:31 and the second failed at ~04:45, which brackets the change. The junction is therefore deliberate
and owned by the in-flight dsh-upgrade work — **not a fault I should repair**, and I did not: replacing
another session's just-created anchor could break 0.2.0-rc.2 preset resolution in a worse way than it
fixes dispatch. H3161 already flags the neighbouring gap (rollback does not repoint the anchor).

A SECOND, SEPARATE TRAP ON THE SAME ROWS (found while chasing this, and it is real)
Before the junction theory, I changed `packages/plugin-remote-fanout/lib/nodes.js` so the two Windows
rows used `C:/Users/ezabz/Code` as `cwd` instead of the home directory. That is WRONG and is reverted:
with `cwd` = home the child has NO SHELL (the sandbox requires the shell temp root outside the
workspace, and the temp root `<home>/AppData/Local/Temp` is inside it), but with `cwd` = the code root
the child cannot boot at all (profile boot writes `~/.dsh/profiles/node_modules`, now outside the
workspace). So a Windows mesh child is either shell-less or absent, and neither is a usable worker. Both
directions are now written into `nodes.js` above `NODES` so nobody repeats the loop. The probe child
that had no shell could still use the in-process file tools — reading, globbing and searching are
unaffected by this.

WHAT WOULD FIX IT (ranked)
1. Relocate the child's shell temp root outside the home directory (or grant `~/.dsh` explicitly), while
 leaving `cwd` as the home directory. That is the only shape that satisfies both constraints.
2. Make the profile module anchor a form the sshd child can traverse on Windows — and prove it with a
 real probe turn, because the link type is what defeated the earlier attempt on ZABZ-YOGA.
3. Until then: treat fan-out on the Windows rows as file-tool-only, and run shell work in the local
 session. On 2026-10-05 that is the choice I made for the rentals job.
