## P153 — The residual suite failures: corrected mechanisms, and the one measurement that would name them

**P-new — the residual suite failures: what is known, what is corrected, and the one measurement that would name the mechanism.**

State on 2026-09-15 after this round: `pytest tests/` is **2,711 passed, 0 errors**, and a small
varying set fails (one to four per run). `tests/test_phase3_modules.py::TestPhase3ConfigFlags` is
fixed (it was deterministic -- the suite exports the repo's `.env`, so `MCP_ENABLED=false` reached a
Settings instance; it now asserts field defaults, 45 passed).

**Corrected from P152:** the claim that `test_worker_clears_in_flight_after_send` races a thread is
**wrong**. `_worker` is synchronous; the `threading.Thread(target=_worker, ...)` call is in its caller.
Four repeats of `tests/test_family_chat.py tests/test_family_chat_personality.py` gave 137, 136, 136,
137 with `test_worker_extracts_memory` and `test_worker_clears_in_flight_after_send` alternating, and
both run through that synchronous path.

**The one measurement worth doing next:** `_worker` wraps its body in `except Exception:
log.warning("Family Chat: ...")`, so a DB write that fails under suite load disappears into a log
line and the test then fails on a missing row or a stale marker. Run those two tests in a loop with
logging captured (`caplog` at WARNING, or `-W error::UserWarning`) and see whether a warning is being
swallowed exactly when the assertion fails. That names the mechanism in one measurement, instead of
the three guesses that produced the wrong answer this round.
