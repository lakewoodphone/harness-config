## P131 — The comms index has no ingestion watchdog, and recent voicemails index as a phone number

## The comms index has no automated *ingestion* watchdog for its own inputs

The index now proves it is complete *with respect to the database*. It says nothing about whether
the database is still being fed. If the Dialpad SMS webhook stops delivering, or the harvest cron
dies, every check here stays green — `comms-refresh: ok — 0 missing` — while the newest
communication quietly ages. The kernel's `comms_freshness` check partly covers this (it reads the
newest SMS fetch, the call-capture lag median and the count of voicemails with no transcript in the
last 14 days), but it does not know about the index, and it does not fail on index staleness.

**Fix.** Either add an index-age metric to `ck/sentinel.py:check_comms_freshness` (read
`~/.fsearch/comms-state.json`, fail above ~2 h), or wire `comms-refresh.py --check` into the
existing owner-attention digest. Both are small; `--check --json` already emits exactly the fields.
Detected while building this: the index was 6.7 h stale and **nothing anywhere said so**.

## Recent voicemails index as a phone number and nothing else

`dialpad_call_full` proves a voicemail arrived (that is how the 3-month gap was closed), but Dialpad
does not transcribe voicemail audio for this account, and the recording is not downloaded: the four
voicemails from 2026-09-13/14 index as

```
[voicemail, no transcript] (863) 384-0569 8633840569
```

so a customer's actual words are unreadable. 223 voicemail recordings exist on disk, newest
2026-07-21 — the download path stopped a month before the transcripts did.

**Fix.** Download the voicemail audio for calls with `voicemail_link` (the harvester already knows
the URL) and run it through the same `transcribe_downloaded_recordings` path the call backfill uses.
That is the same ~$0.006/min, and voicemails are 30–60 s each — cheap. The kernel already counts
these (`voicemail_without_transcript_14d`), so the number to drive it exists.

## The index database itself is outside git and outside the backup that protects `secretary.db`

`~/.fsearch/comms.db` is 334 MB of derived data on the authority. It is rebuildable from the source
in 29 s, so losing it is cheap — but nothing records *that* fact next to it, and `comms.db` squats
in the same directory as `index.db` (8.1 GB, the file index) with no retention story. Worth one line
in the journal and one in `~/.fsearch/README`, not a project.
