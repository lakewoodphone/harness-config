## P2810 — The system retries failures that can never succeed - an over-length reminder retried 22 times and was reported to the owner as 'held'

**The system retries failures that can never succeed, and the retry hides the failure.**

Measured 2026-09-30, while clearing the kernel's `attention_debt` finding. The badge said *"1 urgent
message(s) held"*. The held message was `owner_message_queue#2060` — the Elantra's physical-damage
cover reminder, urgency `urgent` — with **22 send attempts** and this last error:

 [suppressed] owner_text gate refused (too_long): is 455 chars, over the 320-char limit for one text

**It could never have sent. Not at attempt 23, not ever.** The message is 455 characters and the gate's
limit is 320. The content was never going to change between attempts, so every retry was guaranteed to
fail, and the only thing the loop produced was a number that made a genuine problem look like a
delivery outage. The owner was told, twice through the badge, that a message was "held" — language
that means *waiting its turn*. Nothing was waiting. It was refused.

**The rule this is an instance of.** A retry loop is for **transient** failure: a lock, a timeout,
a 502, a busy port. A **deterministic** refusal — too long, a missing field, a path that does not
exist, an invalid id — will produce the identical answer every time, so retrying it converts one
visible failure into an invisible flood. The two have to be told apart at the point of refusal.

**What the fix looks like:**

1. **Distinguish the two at the gate.** A validation refusal should mark the row **terminally failed**
 (its own status, with the reason), not `held`. `held` must mean only "not sent yet, would send
 later".
2. **Never re-attempt a message the validator has already rejected for content.** Prefer truncating or
 splitting an over-length body into numbered parts — the information is real and the limit is
 arbitrary — and only then mark it failed.
3. **Surface a deterministic refusal to the owner as a decision, not as delay.** An over-length
 reminder is not a delivery problem he can wait out.
4. **A retry count is not evidence of an outage.** Read `last_send_error` before believing a held row
 is a transport fault — this one had been telling the truth in plain words for 22 attempts.

**Handled today:** #2060 dismissed with that reasoning in its `status_note`; it was also superseded,
because reminder 530 now carries the same Elantra item in a shorter body for 2026-10-14 09:00 ET. No
held or queued urgent rows remain.

**Same family, still open:** `agent_dead_weight` reports two live agents at **0 completions in 14
days** — `cross_domain_synthesizer` (41 ticks) and `frontier_risk_board` (38 ticks) — still being
scheduled. A tick that cannot complete is the same shape of waste as a send that cannot succeed: it
consumes budget and reports activity. Neither has been retired or fixed yet.

**Evidence:** `owner_message_queue` rows 2060 (held, 22 attempts, the quoted error), 2036 (dialpad
capture stale, normal, below the send threshold) and 2057 (Fishman tickets 74114/74115, normal,
0 attempts); kernel `latest.json` 2026-09-30T16:30Z, checks `attention_debt` and `agent_dead_weight`.
