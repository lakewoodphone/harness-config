## P174 — A working behaviour was reversed for a day on a premise nobody measured, and the wrong premise was written into the code as fact

WHAT HURTS: commit 4d9a0ad (2026-09-14) replaced the tokenized launch URL with the clean origin and
asserted, in a comment that reads like a finding, that the token "burns a one-time exchange" and that
the redirect is "a NEW document whose bootstrap finds no session". Neither was measured; both are
false. The cost was a dead "new window" for a full day. The owner clicked three times on 2026-09-15
(17:00:35, 17:02:37, 17:03:46, profile `w9`) and got the same 401 page each time, and nothing in the
fleet noticed, because the failure is invisible from the machine side: the 401 is rendered inside the
browser, and the launcher logs a successful launch either way.

WHAT WOULD FIX IT (mostly applied):
1. Reversing behaviour that WORKS requires measuring the premise FIRST, and the measurement belongs in
 the commit. The false "one-time exchange" claim was checkable in five minutes by exchanging the same
 token twice.
2. A comment that asserts how another component behaves should cite `file:line` or a measurement, never
 a plausible mechanism story. A wrong narrative in a comment is worse than no comment: the next
 session reads it as established.
3. `dshw doctor` now probes the auth path and reports a non-303 as a blocker, so the class is
 machine-detectable without a human opening a window.

STILL OPEN: nothing watches for "a window is sitting on the auth page". The only machine-visible signal
is the window TITLE (`EnumWindows` -> "dsh web authentication required - DeepSeek Harness"). Cheap next
step: let `dshw health` enumerate window titles and close/reopen a window that is showing the auth page,
so this failure self-heals instead of waiting for the owner to report it.
