## P143 — The app repo has three lineages and the live one is the least published

MEASURED 2026-09-15 13:52Z on secratary, `git fetch` completed first so these are not
stale-ref artifacts:

 HEAD 5581569d (now d8603d17, after I committed one hunk)
 origin/master bdf39e52
 commits on the authority that origin/master does not have: 57
 commits origin/master has that the authority lacks: 136
 `git branch -r --contains HEAD`: EMPTY -- the authority's commits are on no remote
 working tree: 75 modified files

So the machine that runs the company is running code that exists on one disk, and is
missing 136 commits of merged work. Both halves are the same fact: the live checkout is
a third lineage, beside origin/master and beside this laptop's clone.

WHAT IT COST TODAY, concretely: I could not copy `app/main.py` there -- its committed
copy differs from mine, so a whole-file scp would have reverted 57 commits of other
sessions' work. I had to write a guarded single-hunk patch (exact literal, assert one
occurrence, atomic replace) instead, and I still could not tell which lineage a commit
was supposed to land in, so I committed the identical change to both (d8603d17 there,
8d4968d21 here).

WHAT I DID ABOUT THE DANGEROUS HALF, and this is the part that was urgent: the 57
commits are no longer single-copy. Pushed to origin as
`backup/secratary-checkout-20260915` (rc 0, verified present via ls-remote). Nothing was
rewritten, no branch moved, no shared state changed -- a new branch name is the cheapest
possible insurance against losing work that exists nowhere else.

WHAT WOULD FIX IT: one dedicated session -- on that checkout, fetch; merge origin/master;
resolve the 136 commits' worth of divergence; run the suite; push. That is real work with
real conflict surface and it is NOT a side effect of any other task, so it must not be
done as a drive-by while 75 files are dirty underneath it. Until then: never scp a whole
file into that checkout, and prefer the guarded-patch route (`/tmp/pt.py` pattern).

RELATED: H222 is the same disease in the journal repo (secratary's harness-config holds
477 identities against origin's 742, 382 colliding ids, and the allocator does not consult
origin/*, so no entry can be safely appended there). Two repos, one cause: the server
checkout drifts and nobody reconciles it.
