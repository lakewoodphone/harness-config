## P4314 — STEP_BUDGET_EXHAUSTED: the largest failure class is 30 turns and 2 tool calls producing a 2 KB trace - nothing in the loop notices a session that is not working

THE LARGEST FAILURE CLASS, diagnosed 2026-10-15. Measured over 7 days: 335 sessions across 149 distinct tasks carry STEP_BUDGET_EXHAUSTED -- more than TOOL_LOOP_DEADLOCK (176). It is not one runaway task: the worst task has 6 attempts and only 1 of the 149 has two byte-identical attempt logs, so the attempts differ in content while being identical in SHAPE.

WHAT THE SHAPE IS. Two recent attempts of task 28733 (78862, 78868), read in full:

 1,979 bytes of trace (11 lines)
 30 model turns
 reached 27/20 work steps
 [TOOL-SIGS: github_read_file#b57c373aa1=1, qb_status#14251d65fc=1] <- TWO tool signatures
 last checkpoint: 'I'll take the mutating action now: write the fix decision record into the repo via GitHub'

So 27 action steps were spent on TWO tools, and the whole session produced 11 lines. Both attempts differ from each other only in the attempt counter and the memory line quoted -- the work is identical. The task is a CODE FIX ('QB tool resolution must use QB_AGENT_URL/GitHub source, not local repo path') and the session's own checkpoint says it will write A RECORD ABOUT THE FIX rather than make it, in a session whose repo tools cannot succeed because the repo is not on that host.

WHY NOTHING CATCHES IT. The identical-failure guard needs the same failure 3/3 times and these retries vary their arguments; the reconnaissance guard watches READ-ONLY tools and these are actions; the give-up ceiling counts 'failed' and these end 'paused' (and counting 'paused' as a strike is refuted -- 5 of 13 such tasks go on to complete). So the session is allowed to spend 30 turns, produce 2 KB, and pause, and then be retried tomorrow.

THE REMEDY, BOUNDED AND NAMED: a LOW-OUTPUT guard, sibling to the reconnaissance budget in app/autopilot.py (the block that carries _RECON_SOFT_LIMIT / _RECON_HARD_LIMIT). The predicate is measurable and cheap: after N steps, if the session's accumulated trace is under ~3 KB AND the distinct-tool count is under ~3, it is not working -- close it BLOCKED with the tool names, instead of pausing for another identical attempt. The recon guard's own comment says its job is 'to force the decision'; this is the same job one shape over.

MEASUREMENT TO PROVE IT MOVED: the count of sessions per 7 days carrying STEP_BUDGET_EXHAUSTED (335 today) against the count carrying the new BLOCKED marker.
