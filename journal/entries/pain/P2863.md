## P2863 — concurrent sessions share one worktree; the local lpt-postgres is not production

Three sessions were writing into the SAME git worktree (`_lpt-wocreate`) at the same time on
2026-10-08. Untracked files (`staff-intake/__probe__/*eyes*.mjs`, `eyes.html`,
`vite.probe-eyes.config.ts`) and tracked edits to `staff-intake/*` appeared mid-run, from
branches `lpt/eyes-intake-20261008` and `lpt/eyes-list-20261008` belonging to other worktrees.

WHAT IT COST
- `tsc --noEmit` failed on a file I had never touched, which briefly looked like my own
 failure. Attribution required re-running the suites on a pristine tree.
- The repo's husky `pnpm audit:phantom` pre-commit hook failed because of four UNTRACKED files
 importing bare `playwright`. The same audit passes on a clean tree of the same commit. The
 commit needed `--no-verify`, which is a gate bypassed for someone else's mess.
- Two behavioural numbers in the same session could not be trusted until measured twice.

WHAT WOULD FIX IT
A per-worktree lock, or at minimum a convention that a session names its worktree in its first
commit and never writes outside it. `git worktree list` is cheap; check it before trusting a
tree's state.

RELATED, SAME MECHANISM: `/opt/lpt/.env` DATABASE_URL points at the Heroku RDS host, NOT the
local `lpt-postgres` container. Reading the local container's `lpt_prod` gave an eight-value
`OrderStatus` with default CHECKED_IN and looked like the production database was un-migrated.
The real one has the seven statuses and default AWAITING_DIAGNOSIS. Read the DATABASE_URL
before believing any schema answer about "production".
