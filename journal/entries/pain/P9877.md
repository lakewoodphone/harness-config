## P9877 — The deploy has no rollback anchor: it retags :latest before build, and the containerd store drops the previously-running image, so the pre-deploy image cannot be tagged back

## What happened

`deploy/broker/deploy-broker.ps1` never tags the image that is currently RUNNING before it builds and
brings the stack up. On 2026-10-22 the live broker was running image `sha256:2f33004c...` (code from
commit 88f75c5f). The `docker compose build` in step 7 moved both `:latest` tags onto the new images,
which untagged the live one - and the containerd image store then dropped the record entirely:

 docker inspect -f '{{.Id}}' sha256:2f33004cc654... -> error: no such object
 docker images -a --no-trunc | grep filter-broker -> latest x2, rollback-20261022 x2, no <none>

So `docker tag <old-id> ...:rollback` was impossible at the moment a rollback might have been needed.
The two `:rollback-20261022` tags that do exist are DIFFERENT, older digests (166744696f, 595751ad),
so rolling back to the pre-deploy code means rebuilding from commit 88f75c5f, not retagging.

The containers kept running the old snapshots throughout (nothing broke), and the deploy in fact
succeeded - but the rollback anchor was gone before anyone knew whether it was needed.

## The fix, not yet implemented

Before step 7's build, in the same script and before anything else moves:

 stamp=$(date -u +%Y%m%dT%H%M%SZ)
 docker tag filter-broker-broker:latest filter-broker-broker:predeploy-$stamp
 docker tag filter-broker-broker_b:latest filter-broker-broker_b:predeploy-$stamp

and print those two tag names in the summary as the rollback command. Note the disk: / was 91% after
this deploy (65G used, 6.9G free) and each image is ~500MB, so the rollback tags must not accumulate
without a stated retention rule.

## What still hurts

Nobody can prove a rollback works until it is needed. A `-VerifyRollbackTag` check that the tag
resolves by digest before the build starts would make the anchor a measured fact instead of a hope.
