## P3011 — lpt-write records a hardcoded, false reason in order_status_history for every status change

`lpt-write status set` records a FALSE reason in `order_status_history`. Every status change written
through it lands as `Auto-updated by secretary reconciliation (confidence: 0.95)`, whatever actually
happened, because that string is hardcoded in `app.services.website_db.update_order`'s history insert;
the tool's own `--reason` reaches only the audit ledger (`bin/lpt-write` says so at write time).

Evidence, 2026-10-11: `lpt-write status set --order WO26100812738 --status UNFIXABLE --apply` wrote a
deliberate, evidence-backed change (a completed non-invasive scan) and the shop's own history now reads
`AWAITING_DIAGNOSIS -> UNFIXABLE reason='Auto-updated by secretary reconciliation (confidence: 0.95)'`
(ledger seq 315; read back with `lpt ticket 7185017418`).

Why it matters: `order_status_history` is the record a staff member or a dispute reads to find out *why*
an order moved. A reason that is wrong by construction poisons every status change made through the
tool - there were 313 ledger lines before this one - and it looks authoritative while doing it. It is the
same failure class as the invoice that compared against a hardcoded 0.0.

Fix (small, but it is the app's own code, so it is a production deploy and not a laptop edit): thread
the caller's reason through `update_order(..., history_reason=...)` and use it in the
`order_status_history` insert, falling back to the current string only when none is supplied. Located in
`~/personal-secretary-mvp/app/services/website_db.py` on the authority (sha256
`25f5c98787294494...` measured 2026-10-11), reached through `lpt_ops/write_helper.py`.

Until it is fixed: treat `order_status_history.reason` as untrustworthy for every row written by
`lpt-write`, and read `lpt-ops/audit/writes.jsonl` for what was actually intended.
