## P249 — A child that runs on zabz-tech-linux and delegates further dies MISSING_CREDENTIAL (open, same class as 102)

A child that runs ON `zabz-tech-linux` and then delegates further fails, twice, with
`MISSING_CREDENTIAL` — and the node itself is fine. Reported, not diagnosed: it is not in the paths
the 2026-09-17 session owned.

WHAT HAPPENS. `node bin/mesh-run.mjs -Prompt 'Delegate this to a subagent using the subagent_remote
tool: …' -Node zabz-tech-linux` returns exit 0 for the OUTER turn (`run-end exitCode 0`, 24504 ms,
stdoutBytes 1798) and then fails verification with `only 0 MESH-HOST lines for 1 children`. The
child's own final message, verbatim:

 The remote delegation failed — twice, identically — so I have no `MESH-HOST` value to report.
 placement = FIXED TARGET — "zabz-tech-linux" from configuration
 transport cwd = /home/zabz
 target profile = headless
 dsh: MISSING_CREDENTIAL: llm-deepseek: no API key for provider route "deepseek-official";
 store DEEPSEEK_API_KEY through the credentials service (the web Models page writes it),
 or export DEEPSEEK_API_KEY in the launching environment
 exit = 1 (~3 s)

WHY IT LOOKS LIKE docs/mesh/102 §4 run 3 ONE LAYER OUT. That failure was an inner dispatch through the
INTERPRETER form with no credential source (`102` §2, §4 run 3). The same shape here, except the
dispatch is node→node rather than parent→node.

WHAT WAS NOT ESTABLISHED (so a future session measures instead of assuming): which machine ran the
inner dispatch and where its plugin came from. The node's `headless` profile declares only
`dsh-base` and `dsh-headless` (`~/.dsh/profiles/headless/package.json`), and
`/home/zabz/code/harness-config/packages/plugin-remote-fanout/lib/nodes.js` does not exist on that
machine — which is `docs/mesh/103` §3.4's fact one node over: the placement/broker wiring and
`lib/nodes.js` exist in NO COMMIT, so a checkout synced from the branch does not have them.

WHAT IS ESTABLISHED. It is NOT the node's v1 dispatch: the same node, minutes later, ran a child that
executed `hostname` and returned the right name, and `mesh-dispatch.mjs -Transport v1` returned exit 0
with a verified `MESH-HOST:` line.

WHAT WOULD FIX IT. The inner dispatch must resolve the EXECUTOR form, which means the code and the row
that carry it have to exist on that machine: commit `packages/plugin-remote-fanout/**` + the row
(`103` §8 item 1), sync the node, and re-run `node bin/install-mesh-profile.mjs` there (`102` §8 item
3 — a child engine boots its own provider from its own profile). Then re-measure this exact prompt.

EVIDENCE: `_scratch/104-mesh-run-linux.log` (the whole run), `…/2026-09-17T14-53-36-223Z.out` (the
child's message), docs/mesh/104-node-enabled.md §4.1.
