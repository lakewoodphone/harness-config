## P2669 — Mesh fan-out succeeds 23 percent of the time and the losses decompose into three named mechanisms

## P-new — Mesh fan-out succeeds 23 % of the time, and the losses decompose into three named mechanisms, all now identified

MEASURED 2026-09-29 ~18:30Z on ZABZ-YOGA, from the provider's own placement ledger at
`~/.dsh/mesh/placements/*.json` — one file per child, written by `plugin-remote-fanout` itself. Window:
the 70 ledgers with a modification time inside the previous 48 hours. Counted with a script, one row per
ledger, reading `node`, `state`, `stopReason` and `code` from the JSON.

### The headline

| outcome | count | share |
|---|---|---|
| **completed** | **16** | **23 %** |
| error | 33 | 47 % |
| never placed (the attempt ended before a node existed) | 11 | 16 % |
| aborted | 2 | 3 % |
| still dispatching / no outcome recorded | 8 | 11 % |

### By node — and this is where it stops being noise

| node | completed | error | aborted | verdict |
|---|---|---|---|---|
| `zabz-tech` | **16** | 12 | 0 | 57 % success — the only node that ever works |

### Mechanism 1 — `secratary` cannot produce a host identity, and nothing stops children going there

19 of 70 placements went to `secratary`, and **all 19 died**. The cause is now identified exactly and
verified with a raw diagnostic: `remote-script.js:252` captures the target hostname with
`printf -v fanout_host '%s' "$(hostname)"`, which is a **bashism**. The POSIX program is delivered as
`ssh <node> sh -s` (`ssh-transport.js:64`), so it runs under `dash`, which is `/bin/sh` on both Linux
nodes. `dash` prints `printf: Illegal option -v` and leaves the variable empty, so the transport records
`host: ""` and `provider.js:574` refuses the run — *after the child has done its work*. See **L3061**.

So the mesh is not degraded on that node, it is *guaranteed* to fail there, and it fails in the one way
that also discards the result.

### Mechanism 2 — eleven placements never got a node at all

`broker-unreachable`, 11 of 70. There is **no retry** anywhere in `broker-client.js`, and the wording of
the failure is identical to a real outage, so a transient 30 s timeout at placement reads as the mesh
being down (pain **P2668**). Placement happens before any work, so these 11 cost nothing to redo — which
is exactly why they should be retried automatically.

**And the retry is not a one-liner, which is why it has not been done.** The broker's `normalizeTask`
(`mesh-broker/lib/broker.js:79-124`) accepts `kind`, `children`, `prefer`, `exclude` and `worktreeGiB`,
and **no request identity**. `POST /place` issues a lease (`leases.issue`, `:732`). So a naive retry
after a timeout can issue a **second lease** for work that was already leased — the first placement is
then leaked and a node's slot is consumed forever until the 900 s TTL. A correct retry therefore needs
an idempotency key on `POST /place` and a short-lived request-id to placement map in the broker, so a
repeated request returns the SAME lease instead of a new one.

### Mechanism 3 — the ranking demotes healthy nodes for a cold-start latency miss, and promotes the node that cannot work

Read from a placement rationale recorded at 18:20Z, verbatim from the ledger:

- `secratary: 1 free slot(s) of 24 ... swap 100% used (>= 90%)` and
 `secratary: transport v1 (ssh --profile headless) UNMEASURED - not a claim that it works`
- `zabz-tech: 10 free slot(s) of 24, ... 18 effective, 9 after 1 child(ren), SLOW (1738 ms door-to-door,
 first attempt missed the deadline): a cold-start miss, not proof of congestion`
- `laptop` and the other two: same `SLOW ... cold-start miss` wording
- and the outcome line: `chosen from 5 configured node(s) ... chosen secratary`, `score 1`.

The broker's read deadline is **1500 ms** (`/nodes` reports `readTimeoutMs: 1500`). Every Windows node
missed it at 1732-1887 ms because the cache had gone cold, and the mis-named-as-SLOW nodes were then
ranked **below a node with one slot and a full swap area whose own transport the broker has never
measured**. That is how a 2-core-remaining authority box wins a placement over an 18-slot desktop — and
then dies to Mechanism 1. This is the same mis-placement class recorded in `docs/mesh/111` §6, where
three dispatches all believed to be aimed elsewhere landed on the owner's laptop.

### Mechanism 4 — children land on the machine the owner is using, and fail there

4 placements on `zabz-yoga-1`, 0 completed. `preferRemote` is on for this hostname, so the broker is
being asked not to choose it, and the ledger shows it was chosen anyway in these four cases. The
window during which the owner's machine can be selected is not closed.

### What this costs, stated plainly

Three of every four fan-out attempts produce nothing. A fleet that the house rule says to prefer over
serial work is, as it stands, worse than doing the work serially — and worse in the way that wastes
money, because the child usually *runs* before it is thrown away (Mechanism 1 discards after the work,
Mechanism 3 discards before it).

### What would fix it, in order of value

1. **The one-line POSIX fix** (`fanout_host=$(hostname 2>/dev/null || uname -n)`) plus a test that runs
 the generated script under `dash`, not under bash. This alone removes 19 of the 54 failures.
2. **Stop the broker ranking a node whose transport is UNMEASURED above nodes measured working**, and do
 not let a cold-start read miss demote a node: warm the cache before dispatch, or treat a timeout as
 an unknown band rather than a penalty (`docs/mesh/111` §3 rule 1 already says a reading that could
 not be made must never change a decision — the code disagrees with the rule it wrote down).
3. **Idempotency key on `POST /place` + bounded retry in `broker-client.js`**, with distinct error text
 for `broker-timeout` (retryable, may have landed) against `broker-unreachable` (could not reach).
4. **A per-node cap for fleet-kind placement**, so four children never share one desktop.
5. **Demote the model's `MESH-HOST` marker to a note** and keep the transport's own recorded host as the
 authoritative proof, so a child that simply forgot a formatting line does not have its answer thrown
 away (pain **P2667**, lesson **L3059**).
