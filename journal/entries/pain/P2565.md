## P2565 — The company asks the owner to do work it could do itself - a missing tool is reported as a question, not as a gap

## PAIN — the company asks the owner to do work it could do itself, because a capability gap is reported as a question

**Measured 2026-09-28 on the authority, from `owner_decision_queue` (23 pending rows).**

The queue's own help text states the rule:

> **WHAT DOES NOT BELONG HERE** — anything I can fix. Fix it. A queue row is an admission that I
> could not.

At least four of the pending rows are admissions of that kind:

| row | what it says | what it actually is |
|---|---|---|
| **#172** | *"Could you please provide the current Google Business Profile rating and review count for Lakewood Phone and Tech? **I don't have the fetch_url tool to call it.**"* | an allow-list omitting a tool that **two other departments already have** |
| **#173** | *"Could you share your LabCorp results (2026-09-23) and the requisition list? I need them to proceed."* | a duplicate of **#170**, which already answers it. Resolved this session. |
| **#176** | *"I need to pay the overdue T-Mobile bill, but **I do not have access to browser tools** to process the payment."* | a missing capability, framed as a request for guidance |
| **#177** | a work-order quarantine notice naming a broken prerequisite | informational; the fix is engineering |

The mechanism is visible in #172's own wording: an agent that lacks a tool **does not report the
gap — it asks the owner to fill it.** The failure is not that the question is unclear; it is that
the question was asked at all.

**This is the measured failure the whole rule set exists for**: *"595 messages reached him as
'waiting for the owner' when 383 of them were engineering faults that were never his."* The pipeline
was supposedly fixed; it is still producing them.

**The evidence that #172 is our fault and not a missing capability:**
```
DEPARTMENT_TOOLS — 17 departments
 dept_business_ops 30 tools has: web_search, gmail_list, memory_search
 MISSING: fetch_url
 dept_research 11 tools has: fetch_url, web_search, memory_search
 dept_comms_relationships 21 tools has: fetch_url, gmail_list, memory_search
```
`fetch_url` exists and two departments already call it. One missing string in one allow-list
produced: a work order that can never succeed, a failed run every day, **and an owner question asking
a man to fetch a number his own machine could have fetched.**

**What would fix it, in order of how much it buys:**
1. **Close the allow-list gaps** (workstream `co/fu7-allowlist`, dispatched this session). It removes
 the cause of #172, #176 and several work-order failures at once.
2. **Classify before filing.** An agent question whose content is *"I do not have tool X"* or *"the
 path does not exist"* is an engineering fault and must be routed to the engineering queue, never to
 the owner's. `owner_notifications.machine_facing_why` already classifies this for *messages*; the
 `ask_owner` → `owner_decision_queue` path needs the same judge. **Not yet built.**
3. **Make the queue's own rule executable.** The help text states the standard; nothing enforces it.

**Provenance:** `owner_decision_queue` on `secratary`, read 2026-09-28T17:2xZ; `DEPARTMENT_TOOLS`
probed live on the same box; the allow-list consequence was independently established from the other
end in `docs/co/W4-FINDINGS.md`.
