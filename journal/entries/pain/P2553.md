## P2553 — P2560-disk-100pct: secratary is full, the backups are failing, and today there is NO valid backup

# What is filling `secratary`, and what to do about each

Measured 2026-09-28 03:35 UTC on `secratary` (the authority).

`df -h /` → **467 G total, 447 G used, 17 MB available, 100 %**.
`/home/zabz` = 434 G of it; `/usr` 4.1 G and `/var` 4.1 G are normal.

## The single fact that explains most of it

`/home/zabz/personal-secretary-mvp/data/secretary.db` is **12.17 GB**
(`stat -c %s` = 12,170,194,944).

Every backup copies that whole file. So a complete snapshot is ~16 GB, the
6-hourly cadence produces four a day, and the retention policy keeps **all**
snapshots younger than three days. Twelve snapshots × 16 GB = **192 GB in the
"keep everything recent" bucket alone**, on a 467 GB disk, before the dailies.
345 GB of backups is therefore the policy's *steady state*, not a leak.

## The five biggest, with what to do about each

### 1. `~/secretary-backups` — 345 GB (77 % of the disk)

27 snapshots, 2026-08-30 → 2026-09-28. Sizes grow with the database: 6.0 G
(Aug 30) → 14 G → **16 G** (Sep 25-27). Each snapshot holds a full copy of
`secretary.db`, `chromadb` (2.3 G), `mem0` (263 M), a
`personal-secretary-runtime.tgz` (1.5 G), a code tarball (25 M) and a
QuickBooks state tarball (21 M). There is no "small" variant — a snapshot is
all of it or nothing.

**It is failing right now.** From `journalctl -u secretary-backup`:

```
Sep 28 00:00:01 snapshots total : 27 deleted : 0 space freed : 0.00 GB
Sep 28 00:02:02 SKIP secretary.db: database or disk is full
Sep 28 00:02:02 OSError: [Errno 28] No space left on device:
 '.../20260928T000001Z/sqlite/data/chromadb'
Sep 28 00:02:02 secretary-backup.service: Failed with result 'exit-code'
```

The `20260928T000001Z` snapshot is 4.9 GB and contains **only** a 5.16 GB
`secretary.db` — truncated from 12.17 GB — and no tarballs at all. It is not a
usable backup. The last complete one is `20260927T180001Z` (16 GB, 18:23
yesterday). This is the 2026-09-10 incident the script's own header describes,
recurring.

What to do:
- tighten retention to keep 24 h of 6-hourly snapshots, one per day for 7 days,
 one per week for 30 days → roughly 150 GB instead of 345 GB, with no loss of
 daily-or-better coverage;
- while the database is 12 GB, *every* snapshot is 16 GB, so the database has
 to shrink too (see #2);
- prune currently runs daily at 05:20 from cron and does nothing, because the
 policy keeps everything inside the window. It prints `deleted : 0` every run.

### 2. `~/personal-secretary-mvp/data` — 20 GB

The live application data. Breakdown:

| Path | Size | What it is |
| --- | --- | --- |
| `data/secretary.db` | **12.17 G** | the authoritative database |
| `data/chromadb` | 2.9 G | vector store |
| `data/google_voice_profiles` | 2.3 G | two Chrome profiles |
| `data/neshama` | 1.2 G | agent soul documents |
| `data/mem0` | 0.96 G | memory extraction store |
| `data/dialpad` | 0.89 G | crawler cache/profiles |
| `data/briefings` | 113 M | audio/text briefings |

What to do:
- **`VACUUM` `secretary.db`.** A 12 GB SQLite file in an app whose own docstring
 says holding a lock during SQLite calls caused API hangs is a problem in its
 own right, and it is the multiplier on every backup. It needs free space equal
 to the file, so it has to come *after* step 1. On a database that has had
 tables dropped and rows rewritten this routinely recovers most of the file.
- **the two Google Voice profiles (2.3 G) are for an account with 7,321
 consecutive authentication failures since 2026-07-02.** The repair is a
 browser login on a headless host, which cannot be done. They are dead weight;
 deleting them is safe once someone confirms nothing else reads them.

## Probability of getting worse

- The backup timer fires every 6 hours; the next attempt is 06:00 UTC and will
 fail the same way, leaving another partial snapshot.
- At 17 MB free, SQLite is already reporting *"database or disk is full"* to the
 backup process. When an mmap fails in the live API, it does not degrade
 gracefully — on 2026-09-10 it core-dumped the API every ~45 minutes for days
 and produced 109 bogus work-order failures a week.

## Recommended order of action

1. ~14 GB of pure junk (crash dumps, search index, journal) — no data at risk.
2. Tighten the backup policy, then prune: 345 G → ~150 G.
3. `VACUUM` `secretary.db` after step 2 frees the working room.
4. Look at `recon-20260915` and `quarantine-debris` (~11.6 G more).
5. Confirm the Phoenix offsite copy; then decide about `~/repos`.
6. Fix the *monitoring*, not just the space: nothing alerted that the backup had
 stopped producing complete snapshots, and `monitor-hetzner-backups.sh` writes
 to `/var/log/monitor-hetzner-backups.log`, which does not exist.
