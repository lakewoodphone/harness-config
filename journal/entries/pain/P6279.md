## P6279 — The dead-man switch reports GREEN while the offsite backup is stale, if a stale 'running' marker exists

## The dead-man switch reports GREEN while the backup is stale, if a `running` marker is left behind

**What hurts.** The authority's external dead-man switch (`authority-deadman.py`, systemd timer every
5 min) is supposed to fail the Healthchecks.io check when the offsite copy goes stale. It does — unless
`/var/lib/authority-backup/running` happens to exist, in which case it returns success unconditionally:

```python
def freshness_verdict():
 if os.path.exists("/var/lib/authority-backup/running"):
 return True, "backup_running=yes" # <-- every other check is skipped
```

That file is written at the start of a run and removed **only on success**
(`authority-offsite-backup.sh` line 589: `[ "$RC" -eq 0 ] && rm -f "$STATE_DIR/running"`). So a run that
is killed, crashes, or is left by an older version keeps it — and the switch goes permanently green for
the exact condition the marker was supposed to describe.

**Reproduced, not inferred.** Two probes with an identical 3-day-stale `last-run` fixture, varying only
the presence of that file, so the difference cannot be anything else:

```
with the marker: ping http 200 :: offsite=ok age=282841s sent=yes verified=ok backup_running=yes
without the marker: fail ping http 200 :: offsite=ok age=282842s sent=yes verified=ok offsite=STALE age=282842s
fresh control: ping http 200 :: offsite=ok age=0s sent=yes verified=ok offsite=fresh age=0s
```

A second wrong reading from the same cause: a fixture reading `status=failed database_sent=no` still
returned the **success** endpoint while the marker existed.

**Real-world impact, measured.** From the 2026-10-11 05:43Z authority cutover until 06:46:57Z, the newest
offsite copy of the company database was **25 hours old** (the 10/10 object), and the external switch was
green the whole time. A stale `running` marker from the killed v1 run (started 06:01:38Z, orphaned and
left in state `T`) was present for part of that window.

**What would fix it.** Believe the marker only when the process it names is alive, and cap its age:

```python
def _run_in_flight(path):
 try:
 pid = None
 for line in open(path):
 if line.startswith("pid="):
 pid = int(line.split("=", 1)[1])
 if pid and os.path.isdir("/proc/%d" % pid):
 return True
 except Exception:
 pass
 return False
```

…in place of the bare `os.path.exists(...)`, plus "marker older than 4 h ⇒ treat as dead" (a run has
never taken more than an hour). With that, the first case above takes the fail branch.

**Why it is not already fixed.** The change belongs to the session that owns `authority-deadman.py`, and
by the time I had the reproduction the authority had stopped accepting SSH from every key we hold (see
the companion pain entry). A four-line change, unapplied.

**Class of failure, worth generalising past this file.** A "job is in flight" exemption that trusts a
file rather than a process converts a self-verifying monitor into a presence detector. The estate's own
lesson — a job that reports success while shipping nothing is worse than a visible failure — applies to
the monitors as much as to the jobs.
