## P270 — A browser page that survives an engine restart keeps a stale background-job list

**P · A browser page that survives an engine restart keeps a stale background-job list, so the header shows a job that no longer exists and none of the ones that do**

MEASURED 2026-09-18 on ZABZ-YOGA, chasing the owner's *"it still doesn't show any subagents running here?"*
against a header reading `1 background job`.

THE HOST IS RIGHT, AND I CHECKED IT RATHER THAN ASSUMING:
- the engine's own process tree had three `ssh.exe` children of pid 20724, all to `desktop-ts`, created
 11:07:25-26 — the three mesh children were genuinely alive;
- `job_list` reported `subagent-1/2/3 running`;
- `dsh-tool-subagent/lib/index.js:536-555` registers a real job per background child with
 `kind: "subagent"`, `owner: parent`;
- `dsh-api-session-controller/lib/index.js:1096-1098` `jobsFor(agent)` returns `jobs.list(agent)`, i.e.
 every job owned by that session's agent — so the subagent jobs ARE in the list;
- `baseline()` (`:1055-1069`) sends `jobs[session.id]` for EVERY session, and `onJobsChanged` (`:1081`)
 broadcasts a `jobs` frame whenever jobs change;
- the client stores exactly that (`lib/client.js:2676-2689`): a `jobs` frame replaces the session's entry,
 and a reconnect CLEARS the map and repopulates it from `baseline.jobs`.

SO A CONNECTED CLIENT MUST SHOW THREE. The observed client shows one, and the wording it chose is
`count.idle.one` — "1 background job", not "1 background job running" (`dsh-client-ui-jobs/lib/client.js:233-236`)
— i.e. its store holds ONE job and NONE of them is live. That is exactly the state of the OLD engine at
the moment it was stopped: one job in this session, the finished `pwsh-1` inventory. The new engine has no
record of `pwsh-1` at all.

CONCLUSION: the page in the owner's window is holding the pre-restart control baseline. The conversation
stream reconnected (his messages reach the agent and the model's text streams back), but the control
stream that carries `jobs` did not, so the chip is showing the engine that no longer exists.

WHAT WOULD FIX IT (not done): the client should treat a control-stream re-establishment as authoritative
and either re-request the baseline or drop its local job map until one arrives. Showing a job list that
belongs to a dead engine is the same class of failure as the stale-database incident this repo keeps
citing: a confident reading of something that is no longer true. The cheap operator workaround — reload
the page — is not a fix, because the next restart will reproduce it and the owner will again be told
nothing is running while three children work.

SEPARATE AND ALSO OPEN: even with a fresh page, the SUBAGENTS chip cannot show a mesh child at all
(P269) — different chip, different cause, both live at once, which is why "I can't see my subagents" has
been so hard to pin down.
