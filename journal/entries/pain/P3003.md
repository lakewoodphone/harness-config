## P3003 — The authority stopped accepting its only SSH key at 06:44Z - no in-band path to the box holding the company's only live database, and the Hetzner API token is invalid so the console is the only route

WHAT HURTS. At **2026-10-11 06:44Z** the authority `secratary-cloud` stopped accepting the only SSH key it
has, in the middle of the migration programme. Last good command 06:40:03Z; every attempt since returns
`Permission denied (publickey)`, still refused at 07:00Z after a deliberate 15-minute quiet period with
no connection attempts.

WHY IT IS BAD.
 * The box holds the company's **only live copy** of a 23.7 GB database (135 §4.1: the office copy is a
 frozen snapshot 1.5 h older, the R2 object was 25 h stale).
 * `135` §4.6 recorded the interactive path as a single point of failure with a count of **one key**, and
 §4.8 recorded the Hetzner **API token as invalid** (`401 unauthorized`). So both documented recovery
 paths are gone: the key is not accepted and the API cannot start/rebuild/snapshot the server.
 * Consequence for this workstream: `docs/mesh/137-PORT-SYSTEMD-TIMERS.md` **could not be copied to
 `/root/out/migration-review/`**, and three metrics it had just installed could not be re-read.

WHAT IT IS NOT, MEASURED. Not a per-source ban: the same key is refused from the **office** WAN as well
as the home WAN (`secratary-ts` holds the identical keypair, fingerprint
`SHA256:91iMQc2AFg+sSA1oscDHF9pz7jClBMynfHtRL4rmAKg`), TCP/22 is reachable from here
(`Test-NetConnection … -Port 22` → True), and the handshake completes to `userauth` — fail2ban DROPs, it
does not reject keys. Not a burst artefact of one session either: this session's ssh calls succeeded at
06:34:35, 06:36:02 and 06:40:03Z, inside the window a sibling report (`135-PORT-FRESHNESS.md` §9) dates
its own block to. Not the box being down: `https://api.abletelsolutions.com/health` → **200** and
`https://ai.abletelsolutions.com/health` → **200** throughout.

WHAT WOULD FIX IT. Out-of-band access to the Hetzner Cloud **web console** (the owner's account — the
token in `/opt/company/.env` is invalid, so the API is not a route). Then, in this order:
 1. `ls -la /root /root/.ssh /root/.ssh/authorized_keys` and `cat /etc/ssh/sshd_config.d/*.conf` —
 **read before concluding.** The three candidates that produce these exact symptoms are: the key was
 replaced instead of appended to (most likely — `135` §4.6 explicitly recommends *"Add a second key
 from `zabz-tech`"*, and a `>` where `>>` was meant is exactly this); an `sshd` config or `Match`
 change; or `StrictModes` refusing on ownership/mode.
 2. **Append** `ssh-ed25519 … mesh-hetzner-2026-08-31` back; `chmod 600 authorized_keys`,
 `chmod 700 /root/.ssh`, and `/root` not group- or world-writable.
 3. `sshd -t && systemctl reload ssh` (reload, not restart).
 4. Immediately add the **second** key §4.6 asks for, from `zabz-tech`, so this is never a one-key
 estate again.
 5. **Re-issue `HETZNER_API_TOKEN`** and store it somewhere reachable when the company is down — not
 only inside the company's own `.env`. §6.2 already says this and it is still true.
 6. Then `scp docs/mesh/137-PORT-SYSTEMD-TIMERS.md root@178.156.194.1:/root/out/migration-review/`.

RANKED. This is the top open pain in the estate right now, above every migration gap: it is the
difference between a company that can be operated and one that can only be watched from outside.
