## P156 — Policy approval tasks have no honored path: approving one cannot unblock the action (task #25399 proves it)

MEASURED 2026-09-15 (personal-secretary-mvp on secratary): the policy approval path cannot authorize anything. `action` denials create an approval task, `approve_item` sets a flag, and no code reads it. Proof: sending one owner-approved customer SMS produced task `#25399`; approving that task would not have allowed the send, because `PolicyEnforcer._requires_approval` (app/policy.py ~319) consults only `settings` attributes — never the tasks table.

Consequence: every policy-gated action (`dialpad_send_sms`, and `send_sms` while `unsafe_actions_enabled` is false) is a PERMANENT NO with a queue row that says otherwise. The bot keeps generating approval tasks the owner cannot act on, which is exactly the failure this queue was built to avoid — the same shape as `owner_message_queue` filling to 595 undelivered rows.

Fix design (not done; needs a deploy to secratary):
1. When a policy denial creates an approval task, persist the action + params + target in a dedicated table (`policy_approval_grants`), keyed by task id.
2. `approve_item` (or a dedicated `/approvals/{id}/approve` branch for type=`policy`) writes a grant row: `(action_name, target, granted_at, expires_at, task_id, granted_by)`.
3. `PolicyEnforcer._requires_approval` allows when a live, unconsumed grant matches `(action_name, target)`; consume it on use (single-shot).
4. Keep `dialpad_customer_sms_live_sends_enabled` as the hard agent kill switch — it is deliberately separate and must NOT become grant-able. That preserves "agents never text customers unprompted" while making an explicitly instructed, owner-approved send executable from any surface.
5. Add `lptcase`-style hygiene: expire grants (24h) and record consumption in `activity_log`.

Also fix the approval task body: task #25399's description truncates params at 300 chars, so the held draft SMS is not fully readable in the queue.
