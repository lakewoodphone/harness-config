## P2562 — Frontend package lint is unboundedly slow in a fresh worktree and stalls the agent running it (measured 40+ min, twice)

**P-level: high — `pnpm --filter phone-and-tech-frontend lint` is unboundedly slow in a FRESH worktree, and it stalls the agent that runs it**

Measured 2026-09-28 on ZABZ-YOGA, worktree
`_worktrees/phone-and-tech-full/lpt-more-apps` created from `origin/test` that morning.

WHAT HURTS
A frontend worker's definition-of-done included `pnpm --filter phone-and-tech-frontend lint`. It
finished writing all ten of its files in the first ~7 minutes, then spent **more than 40 minutes** in
that one command and never returned. I killed it and ran the gates myself; the work was fine, the lint
gate was the only thing not done.

Measured from the process table, not inferred:
- `node ...eslint\bin\eslint.js src --ext ts,tsx --cache` — first run PID 5640, 1,715 MB, killed at
 427 s; a second run PID 10308 appeared and reached 496 s at 857 MB. Two full passes, neither finished
 inside 8 minutes.
- The machine was healthy throughout: engine loop p50 4 ms, 13.7 GB physical available, 22 cores. This
 is not a starved machine; it is a slow command.
- The same session's `pnpm --filter phone-and-tech-backend lint` **did** finish, in about 8 minutes,
 and `pnpm --filter phone-and-tech-frontend typecheck` finished comfortably.

WHY IT IS THIS SLOW, AND WHY IT LOOKS FAST IN THE DOCS
`frontend/AGENTS.md` says lint is fast because of "ESLint `--cache`" and "ESLint type-aware split".
Both are true **once the cache exists**, and `.eslintcache` is per-working-directory. Every fresh
worktree — and this fleet created one — starts cold and re-lints all ~11,000 files, with `project: true`
type-aware rules enabled for `src/services/`, `src/hooks/`, `src/trpc/`, `src/types/api/`. The repo's
own performance note is a statement about the warm path and reads as a statement about the command.

THE DAMAGE IT DOES BEYOND WALL-CLOCK
An agent that is 90 % done and stuck in a lint run cannot report, cannot be steered (`subagent` mesh
children are not addressable at all — see L2617), and holds a fleet slot. The measured failure in this
system's history is agents that stop and need restarting; this is the same cost with a different cause.

WHAT WOULD FIX IT (in order of preference)
1. **Do not put the package-wide lint in an agent's definition-of-done for a fresh worktree.** Gate on
 `typecheck` + the focused tests, which are the gates that can actually fail because of the change,
 and run the package lint once on the INTEGRATION tree where the cache is warm. What a worker needs is
 a gate that can fail fast; lint here cannot.
2. **Warm the cache once when the worktree is created** — one background `pnpm --filter
 phone-and-tech-frontend lint` at fleet setup, so every later run is a cache hit. Cheap, and it turns
 the gate back into what the docs claim.
3. **Scope the lint to changed files** (`eslint $(git diff --name-only --diff-filter=ACM HEAD~1)` or an
 equivalent), which is what the `--cache` was for in the first place.
4. If none of those: **cap it** and state the cap. `pwsh -File scripts/local-run.ps1 -Lint -TimeoutMs
 60000` exists in this repo for exactly this, and 60 s of lint that reports "not finished" is worth
 more to the next session than 40 minutes that reports nothing.

NOT FIXED YET. Recorded so the next fleet does not spend another 40 minutes rediscovering it.
