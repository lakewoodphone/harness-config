## P2937 — The mesh broker is down and the failover placer is not in effect, so no session can fan out to another machine at all

## The mesh provider calls a broker port that nothing answers, so no fleet can be dispatched at all

Measured 2026-10-11 from ZABZ-YOGA.

The harness's mesh provider (`subagent` / `subagent_remote`) places children by POSTing to the placement
broker at `secratary-ts:http://localhost:3091/place`. Every dispatch fails:

```
remote-ssh: broker-unreachable: the placement broker could not be reached at
secratary-ts:http://localhost:3091/place — ssh exited 7:
curl: (7) Failed to connect to localhost port 3091 after 0 ms: Could not connect to server
```

**The failure changed shape, and that is the diagnostic.** Earlier the same day it was
`ssh exited 255 … connect to host secratary.tail93e6e6.ts.net port 22: Connection timed out` — ssh
itself was dead, which is the I/O-starvation signature (`P2936`, trap 2 in the systems register: sshd
stops answering while `tailscale ping` still replies). **Now ssh SUCCEEDS and the far side runs `curl`;
exit 7 is curl failing to connect.** So the network and the box are fine. **What is missing is the
broker itself.**

### Why it is missing — and why "just restart it" is forbidden

* `mesh-broker` is one of the units the 2026-10-11 authority cutover **stopped and disabled** on the
 office box. `docs/mesh/130` lists it among the stopped units, and
 `docs/mesh/000-SYSTEMS-REGISTER.md` states that restarting any of them *"creates a SECOND WRITER
 against a database the cloud box is now serving — the one condition this whole design exists to
 prevent."* So restarting it on `secratary` is **forbidden**, not merely risky.
* The new authority **`secratary-cloud`** (`ssh -i ~/.ssh/id_ed25519_hetzner root@178.156.194.1`) has no
 broker. `ss -lntp` shows only `22`, `53`, `127.0.0.1:20241` (cloudflared), `127.0.0.1:8002`
 (company-api) and `127.0.0.1:3087` (phone-redirector). **No `:3091`.** `/opt/company` is present and
 running, but `systemctl list-unit-files | grep -iE 'mesh|broker'` is **empty** — no unit exists there.
* Moving it was the documented intent and was **never done**. `docs/mesh/122` §4b: *"mesh-broker.service
 on the new box; 4b is the one that removes today's outage class."* `docs/mesh/126` §1 measures it:
 *"the broker is still only on the office box, loopback :3091; 122 never says the broker's nodes.json
 roster must move with it."*

### The designed mitigation is not in effect

`packages/plugin-remote-fanout/lib/failover-placer.js` is supposed to make the broker *"an optimisation,
not a veto"* by reading every node's `/mesh/health` directly when the broker is unreachable
(`docs/mesh/111`, `docs/mesh/119` §2.3, and the `estate-systems` skill all assert this). **It did not
run** — the provider returned `broker-unreachable` and gave up. That matches `docs/mesh/123` §3, which
records: *"Does the resident engine use the failover placer? — NOT VERIFIED — takes effect on next
engine start (P210)."*

### Consequence

From 2026-10-11 **no session on this estate can fan work out to another machine.** Rule 1b's default —
orchestrate rather than grind serially — is therefore unexecutable, and every fleet dispatch degrades
silently to local work. A fallback nobody can see is a claim about where work ran that is not true.

### What would fix it, in order

1. **Deploy `mesh-broker.service` on `secratary-cloud`** (the authority now), **with its `nodes.json`
 roster** — doc 126 §4b warns the roster must move with it or the broker knows no nodes. Do **not**
 touch the office box.
2. **Or confirm the failover placer is actually loaded** in the running engine (P210), so an unreachable
 broker stops being fatal. Cheaper, and the design already claims it.
3. Either way, **make the failure legible**: both failures arrived as "the subagent failed", which reads
 like the child's problem. A broker-unreachable dispatch must say so at the point of dispatch.

### Verify with, rather than trusting this entry

```
ssh -o BatchMode=yes secratary-ts 'curl -s -m 5 http://127.0.0.1:3091/healthz' # empty = down
ssh -i ~/.ssh/id_ed25519_hetzner root@178.156.194.1 'ss -lntp | grep 3091' # empty = absent
```

**Not fixed by this session.** The office box is the frozen rollback anchor and the cloud authority is
another workstream's live cutover, so this was recorded rather than acted on. It is infrastructure for
orchestration, not the search-and-indexing work it was found during.
