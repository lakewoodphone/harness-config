## P2886 — lpt-write note add --title is accepted, planned, and thrown away - all 111 sweep notes are untitled

## `lpt-write note add --title` is accepted, planned, and then thrown away - every sweep note is untitled

Measured 2026-10-09 after writing 111 notes with `title="Work-order sweep 2026-10-09"`:

```
select count(*) from customer_notes where title = 'Work-order sweep 2026-10-09' -> 0
select id, title from customer_notes where "createdAt" >= '2026-10-09' limit 5 -> title = None, five times
```

The plan prints the title (`write_helper._note_plan_lines` line 668: `title {title or '(none)'}`),
the request carries it, and it never reaches the row. The cause is visible in `docs/writes.md` §2,
which quotes the statement `insert_customer_note` actually issues:

```sql
INSERT INTO customer_notes (uuid, "customerId", "workOrderId", type, content, priority,
 "authorId", "createdAt", "updatedAt")
```

**No `title` column.** The table has one; the writer does not use it. So a caller can pass a title,
see it accepted, and find it silently absent — which is worse than a refusal, because it looks like
it worked and the only evidence otherwise is another query.

The direct cost: **the 111 notes the 2026-10-09 sweep wrote cannot be found by title.** They are
findable by their text and their type, and the sweep's own marker phrases are what to search for
(`Record correction 2026-10-09`, `Status moved from …`, `Billing: the completion note records …`),
but a staff member filtering on a title sees nothing.

**What would fix it:** add `title` to the `INSERT` in `app/services/website_db.insert_customer_note`
(one column, and the parameter is already threaded through), or make the helper **refuse** a title it
cannot store instead of planning one it will drop. A silently dropped field is the failure shape this
estate has paid for repeatedly.
