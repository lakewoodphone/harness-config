## P2822 — Child-parent messaging is structurally impossible for a remote child; a provider flag would fake it and be worse

MEASURED 2026-09-30. The owner asked for constant back-and-forth between a parent and its children, and for children to spawn their own children.

WHAT IS ALREADY TRUE. A remote child (dsh --profile headless on another node) CAN spawn its own children, locally and in-process, because dsh-base binds the subagent tool to the spawn provider in the headless profile. No work needed.

WHAT IS STRUCTURALLY BLOCKED. Parent->child and child->parent messages. The SubagentProvider contract's continuable-creation capability (prepareContinuable) is documented as 'DATA, never a capability': it may only contribute whether the child session is seeded with parent history, while the continuation manager itself owns identity reservation, composition, Agent creation, prompt delivery, cold resume, ownership and disposal (types.d.ts:360-375). So a remote child can never be continuable, because there is no in-process Agent for the manager to own. README.md:170 names the gap: 'remote providers need an Activation ownership contract before they can support continuable children.'

WHY THE OBVIOUS WORKAROUND IS A TRAP. Adding prepareContinuable() { return {} } to RemoteOneShotProvider would pass both gates and then make the manager compose the child LOCALLY, while the parent believed the mesh placed it. That is a silent wrong-machine run: strictly worse than today's loud UNSUPPORTED_CAPABILITY refusal.

WHAT WOULD FIX IT. A message relay over the existing transport: a mailbox directory on the target node, written by the parent before/after dispatch and by the child between its own steps, so messages cross on the transport the platform already has. It needs (a) a durable mailbox convention, (b) a pair of tools so a model can send and collect, (c) the dispatch to place and read it. Not a provider flag, and not a one-off script.

INTERIM RULE. Until it exists, the parent has one-way conversation: the child writes files, and a follow-up dispatch that tells a NEW child to READ the previous child's artifacts is the honest way to continue a thread. Do not claim two-way messaging.
