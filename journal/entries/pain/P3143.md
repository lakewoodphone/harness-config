## P3143 — One customer's 389 communications are really 16 - 373 duplicate dialpad rows, and the retired store dates the same SMS 11 days earlier

One customer's "389 communications" are really 16, and the two stores date the same SMS 11 days apart.

Measured 2026-10-12 on Chezky Shwartz (+17326204948), order 2631:

- `lpt ticket` reported `comms_for_customer 389` with `comms_duplicate_rows 373` folded away by the reader. The single message that decides the case — "the phone still won't turn on, there's no more repair path left on it, so it's ready to be picked up, the charge on it is $50" — exists in `dialpad_sms_cache` as **20+ rows between 2026-09-09 and 2026-09-20**, roughly 30 minutes apart, each with a different ref (`ptf-comm-135694`, `ptf-comm-135684`, …) and the identical body.
- The retired `app` store (`lpt_prod`) carries that same message dated **2026-09-09**; the live `operational` store carries it dated **2026-09-20**. Its `communications` table is kept warm by the half-hourly push job, so freshness there is not freshness of the case.
- Consequence 1: "when did we tell this customer X" cannot be answered from row counts or `max(createdAt)`; it needs a fold by (phone, direction, body) and then an explicit choice of store.
- Consequence 2: a re-cached row moves the apparent date forward or back without any human action, so a case timeline built from these rows silently drifts.

Fix direction: deduplicate at write time (the harvester already knows the Dialpad message id — that is the natural key) or make the fold part of the table rather than the reader, and stamp each row with the store's own fetch time separately from the message's send time.
