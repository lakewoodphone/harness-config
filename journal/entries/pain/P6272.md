## P6272 — Mesh nodes cannot reach the cloud authority, and that killed a whole fleet

Ranked by damage. Measured 2026-10-13.

WHAT HAPPENED. I dispatched six children over the mesh. Five of them (all that finished or were
killed) landed on `LakewooechsMini` and could NOT reach the authority `secratary-cloud`. Every one
returned COULD NOT ASK after the three prescribed hops:

 1. `ssh secratary-cloud hostname` -> exit 255, `Connection refused` (Tailscale name, port 22)
 2. `ssh root@178.156.194.1 hostname` -> exit 255, `Permission denied (publickey)`
 3. `ssh -i ~/.ssh/id_ed25519_hetzner …` -> exit 255, key file does not exist on that node

That node's `~/.ssh/` holds `id_ed25519_laptop`, `id_ed25519_lpthub`, `id_ed25519_psm-deploykey`,
`id_ed25519_yocheved-mac-mini`. I tested all four against the authority myself: **all four are
rejected.** There is no working credential on that machine.

COST. The entire first wave produced zero work. Five children, ~50 minutes of mesh time, discarded.

FIXED, PARTLY. `zabz-tech-linux` DOES hold `~/.ssh/id_ed25519_hetzner`; it simply had no `Host
secratary-cloud` stanza, so the alias fell through to default keys. I appended the stanza
(`~/.ssh/config.bak-fleet-20261013T015205Z` is the backup) and verified
`ssh secratary-cloud hostname` -> `secratary-cloud`, `ALIAS-OK`. That node is now fleet-capable.

STILL BROKEN. The mac mini needs a private key that reaches the production authority, and it is the
machine an employee uses. That is a security-posture decision, not a dev decision, so I did not take
it — it is a question for the owner, not a script for me to run.

WHAT WOULD FIX IT. Either (a) the owner's call on whether the authority key belongs on that machine,
or (b) a broker placement rule that refuses to place a cloud-dependent child on a node with no
authority credential. (b) is the better fix: the failure is silent until a child burns its whole
budget discovering it.

LESSON. The mesh reported "the run succeeded" for all five — transport success is not task success.
A fleet brief must include a target-access check as step 0, and the manager must verify the access
from the node the broker ACTUALLY picks, before dispatching the other five.
