## P2889 — Mesh subagent dispatches die at MCP init (ENOTFOUND mcp.jina.ai) so delegated work cannot run

WHAT HURTS: the mesh subagent provider cannot run a child at all. Delegation - the default for any larger job per the owner's 2026-09-15 instruction - is dead, so every job falls back to serial grinding by one session.

MEASURED, twice, 2026-10-09 on ZABZ-YOGA:
- subagent (mesh) dispatch 1: "the remote one-shot exited 1 and produced no final message".
- subagent (mesh) dispatch 2, same hour, same result.
- Both stderr tails end identically: mcp-remote/dist/chunk-CGVEK4Z7.js:32228:20 at fetchWithMcpHeaders -> StreamableHTTPClientTransport._send -> FetchError, cause Error: getaddrinfo ENOTFOUND mcp.jina.ai (errno -3008, hostname mcp.jina.ai). The npx path in the stack is C:/Users/ezabz/AppData/Local/npm-cache/_npx/705d23756ff7dacc/node_modules/mcp-remote.
- So the child engine starts, the MCP client for the jina server fails to resolve its host, and the failure takes the whole run down instead of degrading. No child ever reached a first step.

COST: on 2026-10-09 a real job (the SNAP evidence pack - a 12-month P&L, a shelter-cost search and a signed loan statement) had to be re-dispatched to subagent_local, i.e. on this machine, and its results must be reported as LOCAL. The rule that says fan out by default has no working substrate.

WHAT WOULD FIX IT, in order of cheapness:
1. Make an MCP server that fails to start NON-FATAL for a child run - degrade to the remaining tools instead of exiting 1. This is the real defect: one optional web-fetch MCP can kill every delegated job in the estate.
2. Until then, keep a local fallback and LABEL it. subagent_local works; the failure is only in the remote provider.
3. Decide whether the jina MCP row belongs in the composition that mesh children inherit at all.
