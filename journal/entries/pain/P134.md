## P134 — The journal itself has forked: SECRATARY holds 936 entries that exist on no other machine, and ZABZ-YOGA holds 304 that SECRATARY has never read

**Measured 2026-09-14 23:30 UTC on SECRATARY**, comparing the local `~/harness-config` (HEAD
`325f86b`) with `origin/master` (`3f05205`, after which I pushed entries only):

| | local (SECRATARY) | origin (ZABZ-YOGA lineage) |
|---|---|---|
| `journal/entries/**` files | **1307** | **675** |
| entries present only here | **936** | — |
| entries present only there | — | **304** (126 lessons, 57 pain, 43 decisions, 42 wins, 36 handoff) |
| `journal/tools/journal.py` | 1091 lines behind | the new one, plus `repair-meta.py` |
| journal design | month-sharded `log/*.md` + `state/` (the v2 rebuild described in the local README) | one file per entry, `FORMAT`, self-healing index (the design `origin`'s README describes) |
| `journal/index/journal.db` | **tracked** | **gitignored** |

**Cost:** the journal is the only organ that makes a session continuous. Two divergent journals means
two partial memories: work recorded on one machine is invisible on the other, and the owner gets
"we already decided that" and "we never decided that" from the same system depending on where the
session landed. `origin`'s auto-sync refuses to act on this by design — its log says
`[attention] local commits ahead of origin (1) — this checkout is not a place to commit; needs a human`
— so nothing will fix it by itself and it will silently get worse with every session that writes here.

**Why it happened (evidence, not a guess):** the v2→one-file-per-entry migration and the new tooling
landed on `origin` (commits `1f47ec2`, `fc72ad1`, `3f05205` carry the new `journal.py`, `FORMAT` and
`.gitignore`), while this machine kept its own older v2 tree and kept appending to it. Local commits
`ff45068` ("idempotent legacy absorption … and the lineage divergence this exposed") already named a
lineage divergence the same day and did not resolve it.

**What would fix it, in order** (this is a dedicated session's work, not a side-edit):
1. Take `origin`'s `journal/tools/journal.py` (they have `migrate-v2`, `absorb`, `dedupe`,
 `repair-ids`, `reconcile-questions` for exactly this) and run it on this tree; do not hand-merge the
 936 entries.
2. Its `duplicate id, different content` cases are the dangerous part: the older numbering here and
 the global allocator on `origin` disagree (`H206` here vs `H204` on origin). `repair-ids` exists for
 that, and the outcome must be verified by counts, not by trusting the tool — the two earlier
 migrations silently dropped 37 and then 7 entries and were only caught by counting against the source.
3. Stop `journal/index/journal.db` from being tracked (it is a cache; `origin` gitignores it). The
 index must be rebuilt on both sides and the counts differenced.
4. Verify from a second machine that all 1307 + 304 entries resolve, then leave the auto-sync able to
 fast-forward again.

**Until then:** a session here should write its entries (they are recoverable by `absorb`) but must not
assume the journal it reads is the whole picture, and should say so when it cites an id.
