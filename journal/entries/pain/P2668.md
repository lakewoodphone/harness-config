## P2668 — Mesh placement returns broker-unreachable on a transient timeout, and it reads exactly like a real outage

Measured 2026-09-29 on ZABZ-YOGA, four lanes in one batch.

Four mesh children (subagent) each settled as failed with, verbatim:
 "remote-ssh: broker-unreachable: the placement broker could not be reached at secratary-ts:http://localhost:3091/place - no answer within 30000 ms"

The mesh was NOT actually down. Checked immediately afterwards:
 ssh secratary-ts -> SSH_OK, hostname secratary
 curl -m 8 -o /dev/null -w '%{http_code}' http://localhost:3091/place -> 405
405 is the expected answer for a GET on a POST-only endpoint, so the broker was up and listening the whole time.

So this is a transient dispatch-time failure that is reported with the same wording as a real outage, and it fires at placement, before any work happens. The four lanes it killed had to be re-dispatched by hand; the identical briefs then all started clean on the first retry (jobs 55-58), and four lanes dispatched minutes earlier in the same session (jobs 47-50) kept running throughout.

What would fix it: retry placement once or twice inside the provider before returning, and distinguish "broker did not answer in 30 s" from "broker is down" in the error text - one is worth retrying automatically, and the current wording sent me looking for an outage that was not there. Related: P2667 (MESH-HOST marker) and L3059.
