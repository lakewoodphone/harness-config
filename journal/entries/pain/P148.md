## P148 — The company API's write path returns a fast 500 'database is locked' under harvest contention while /health still says 200 (new measurement on P48)

**New measurement on P48 (who holds the write lock on `secretary.db`), 2026-09-15.**

While verifying the `ps_mcp_server.py` fix I made ten consecutive writes to `PATCH /ceo/tasks/24658`. **Every one
returned `HTTP 500 {"ok":false,"error":"internal_error"}` in 0.02–0.04 s**, and `journalctl -u secretary-api` gave
the same line each time:

```
ERROR app.main: Unhandled error on /ceo/tasks/24658: database is locked
```
```
File "/home/zabz/personal-secretary-mvp/app/database.py", line 4713, in update_task
 cur = conn.execute(f"UPDATE tasks SET ... WHERE id = ?", params)
sqlite3.OperationalError: database is locked
```

Four one-second-apart retries from a separate process failed identically. **The same request had succeeded three
times in a row minutes earlier (200, 0.00–0.01 s)**, so this is contention, not a broken route or a broken body.
The likely writer is the Dialpad harvest — `dialpad-harvest.log` (15:04), `dialpad-recording-gap.log` (15:25) and
`dialpad-transcript-gap.log` (15:20) were all live in the same window.

Two things this adds to P48 that were not there before:
1. **It is not only a long-hang problem — it is an ordinary write failure with a fast, wrong answer.** The endpoint
 returns 500 in 30 ms with no `error_id` in the body, so a caller cannot tell "DB busy, retry" from "your request
 was malformed". `capture_error` appears not to have populated `error_log` for these either (the response carried
 no `error_id`), so the self-healing pipeline never saw them.
2. **The failure is invisible at the API's own health check.** In the same window `GET /health` returned **200 in
 0.043 s**. A caller that probes health and then writes will be told the system is fine and then fail.

**What would fix it, cheapest first:**
- Set a real `busy_timeout` on the API's write connections (and on `ps_mcp_server.py`'s `_db()`, which opens the
 company DB read-write and never closes the connection — `with _db() as conn:` commits but does not close). A 5 s
 default is what is biting; 30 s would absorb these windows.
- Make the lock failure self-identifying: return **503 with `Retry-After`** and a distinct error code for
 `database is locked`, so callers retry instead of reporting a hard failure.
- Record it in `error_log` — right now these 500s leave no row.

**Blast radius:** any agent action that writes during a harvest window. This session it cost a false "the tool is
broken" conclusion before the log was read — the correct reading is "the write path is not contention-safe".
