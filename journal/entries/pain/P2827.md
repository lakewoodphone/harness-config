## P2827 — A check that matches nothing reports 'no data', which reads like 'no problem' -- LIKE with a leading wildcard silently returns zero on this SQLite build

# P — a check that matches nothing reports "no data", which reads exactly like "no problem"

**Measured 2026-10-02, on the authority (secratary), Python 3.14 sqlite3.**

I wrote the first `text-ledger-audit.py` to compare the owner's inbound texts in the
channel store (`~/.sms-inbox/inbox.db`) against the app's copy (`secretary.db.sms_log`).
It filtered the owner's number with:

 from_number LIKE '%84897895%'

and got **zero rows**. On the same database, same connection mode:

 select count(*) from sms_log where from_number = '+18483897895' -> 252
 select count(*) from sms_log where from_number = '18483897895' -> 3
 select count(*) from sms_log where from_number like '%84897895%' -> 0
 select count(*) from sms_log where from_number like '%8489%' -> 0
 select count(*) from sms_log where from_number like '%+18483897895%' -> (also 0)
 -- with no `direction` filter at all, still 0

`from_number` is TEXT. `+18483897895` contains `84897895`. The pattern does not contain
`%` or `_`. There is no COLLATE or case subtlety. **LIKE with a leading wildcard is not
dependable in this build**, and it fails *quietly*: no error, no warning, just an empty
result set.

**Why this is a pain entry and not a curiosity.** The consequence is not a missing row.
It is that the check reported *"the app has no owner activity"* — a **passing** verdict
on the very thing it existed to catch, with honest-looking evidence beside it. This is
the same class as the failures this system keeps paying for: the check's *silence* was
indistinguishable from health, and it took a second, deliberately different measurement
(`= '+18483897895'`) to expose it.

**The rule.** When a filter decides whether a check has any data at all, the filter must
be **exact** (`IN` on the literal values), never a fuzzy match — because a fuzzy match
that finds nothing is reported as an empty population, and an empty population is not
evidence of health (this system's own standing rule: *"an empty result is not evidence
of health — it is a refusal"*). Where a fuzzy match is genuinely needed, the check must
also assert that it found **something** and FAIL loudly when it did not.

**Corollary, measured the same day:** `run_extra` in `text-channel-check.sh` builds the
names of failing checks by grepping `^FAIL`. The audit's own trailing summary printed
`FAIL <name>` lines too, so the log line read `D1 …;D3 …;D1 …;D3 …`. A helper that
derives names by grepping a shared prefix will duplicate them if the instrument also
prints that prefix. Emit the marker **once, per finding**, and let the last line be the
exit status.

**Where the fix lives:** `~/code/harness-config/scripts/text-ledger-audit.py`
(`OWNER_NUMBERS` + `_OWNER_IN`), verified against the real database —
`from_number = '+18483897895'` → 252 rows, and the D1 check now reports the real gap
(store newest 2026-03-25, app newest 2026-10-02, 225 owner rows parked past the mirror's
7-day window).
