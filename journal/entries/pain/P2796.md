## P2796 — The journal id allocator is LOCAL-ONLY: two machines handed out L3060 the same hour, and check cannot see it

## The journal id allocator is LOCAL-ONLY, so two machines can hand out the same id

**What hurts.** `journal.py append` writes locally and cannot move a ref (H2850, after it reverted
`origin/master` on 2026-09-17). That made writes safe, but it also means the allocator computes the
next id from **the local tree only**. Two machines writing in the same hour both pick the same
number, and nothing detects it until the trees merge - at which point one id means two different
entries, which is the single thing the journal must never contain.

**Measured 2026-09-29.** On ZABZ-YOGA I appended a lesson and got **L3060**. Minutes later, on
`secratary`, a different lesson was appended and also got **L3060**:

 * ZABZ-YOGA L3060 · "A double-quote in a mesh subagent prompt kills the remote one-shot"
 * secratary L3060 · "A compiled file is not a running file: I crash-looped the live owner path"

Local `journal.py check` reported **0 errors** at the time, because it can only see its own tree.
`doctor` reported the cache fresh. Neither tool has any way to notice a collision that exists only
across machines.

**How I worked around it, this time only.** I renumbered my local entry to **L3100** - well clear
of the authority's maximum, so the two trees merge without a conflict and no id means two things.
The rename then produced a second error of its own, worth recording because it is a trap:
renaming the file and the heading changes the BODY, so the trailing
`<!-- j2 ... sha=... -->` line no longer matches, and `check` fails with
`metadata sha=4ea80f9a1b35c9e4 does not match the body (2ba75b332d769cff)`. **The fix is to rewrite
the sha in that trailing metadata line**, and it is NOT fixed by rebuilding `index/` - I deleted
`journal.db`, `entries.tsv` and `stamp.json` and forced a full rebuild first, and the error
survived, because the sha is stored in the entry, not the cache. Recompute the body sha and write
it back.

**What would fix it properly.** One of:
1. `append` consults the converged index before allocating - read the authority's `entries/` (or a
 cheap `git ls-remote` of an id counter file) and take `max+1` across machines.
2. A single writer: an append RPC on `secratary` that every machine calls, so ids are allocated in
 one place. This is the same shape as the owner-queue living only on the authority.
3. At minimum, `check` should be able to compare against a remote tree (`--peer host`) and exit
 non-zero on a cross-machine collision, so the failure is caught the next time anyone looks
 rather than at merge time.

**Ranked: high.** It is silent, it corrupts the one structure that gives me continuity, and it will
recur every time two machines write in the same hour - which is now normal, because the wake fleet
writes to the authority while I work on the laptop. Note also that **all autonomy-driven journal
writes should go to the authority**, not to whichever machine happens to be awake.
