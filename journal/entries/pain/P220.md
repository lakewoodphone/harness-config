## P220 — One anonymous GET through the tailnet signs into the owner's engine, and every device shares one identity

MEASURED 2026-09-16 by the security pass, and it is a consequence of the gate design rather than a
new bug: phone-gate.py's complete_login() performs the token exchange on the visitor's behalf, so
`GET /` through a node's tailnet name returns 200 with a session cookie and NO credential. That
cookie drives /api and the WebSocket mux, i.e. full engine control, i.e. a shell as the owner --
on secratary that is code execution as `zabz` on the company authority. secratary's gate has
behaved this way since 2026-09-11; today it was extended to ZABZ-YOGA and ZABZ-TECH.
The bound is tailnet membership, and the ACL is default allow-all: `tailscale debug netmap`
shows Srcs = 100.64.0.0/11 + fd7a:115c:a1e0::/48, Dsts = 0.0.0.0/0 ports 0-65535, every node
AdvertiseTags null, Caps [].
THE FIX THAT NEEDS NO ADMIN CONSOLE, measured 18:06:48: `tailscale serve` forwards the caller's
identity to its backend -- `Tailscale-User-Login`, `Tailscale-User-Name`, `X-Forwarded-For`,
`X-Forwarded-Proto`. BUT the login header does not separate the owner from anyone else: all six
devices on this tailnet are enrolled under ONE Google identity (user 2701425880688073), including
the employee's Mac at 100.126.146.121. So the control must be the DEVICE IP in X-Forwarded-For.
Being implemented in phone-gate.py as scripts/phone-gate-allow.txt (allow-list; a non-listed
caller gets a friendly 403 naming its own address, not the engine's plain-text 401).
WHAT WOULD FIX IT PROPERLY: a default-deny Tailscale ACL allowing tcp 443/3086 only from the
owner's devices. It needs the admin console, so it is the owner's -- and it is the only control
that also covers a device added tomorrow.
