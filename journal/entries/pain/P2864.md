## P2864 — git push origin main in harness-config can land on the authority and be rejected by GitHub in the same command, while the local ref reads as success

## P-new · `git push origin main` in harness-config can succeed on the authority and be rejected by GitHub in the same command, and the local ref looks successful either way

**Measured 2026-10-08 ~01:2xZ on ZABZ-YOGA, harness-config.** `origin` is a single remote with a fetch
URL on the authority (`secretary-ts:/home/zabz/harness-config.git`) and TWO push URLs:
`https://github.com/lakewoodphone/harness-config.git` first, then the authority. `git push origin main`
ran, printed `remote: Create a pull request for 'main'...`, and updated my local `origin/main` — which
reads as success. It was not: GitHub rejected the same push as a non-fast-forward, and a later
`git fetch origin` then showed a **"forced update"** of `origin/main` from my commit back to the
authority's `d2b22079`, which looks exactly like the authority destroying a laptop's push.

**Neither reading was true.** The authority had never lost anything: `d2b22079`'s parent is `f2e51c40`,
the same commit my branch was based on, so it was an ordinary 2-vs-1 divergence, and the "forced update"
was `fetch` moving my *local* ref backwards. The commit was on GitHub and not on the authority, while
the local ref said otherwise. A session that trusts that ref will stop looking for its own work — or
report a data loss that never happened, which this estate has done before.

**What actually works:** push to the authority by its own URL (`git push secretary-ts:/home/zabz/harness-config.git main`),
or give the two destinations separate remote names so a rejection from one cannot masquerade as a result
for the other. **What would fix the class:** reconcile GitHub's `main` with the authority's, then make
the mirrors read-only from the laptop side (push to the authority, let the authority mirror out).

Verified after the fact: authority `main` = `6edd546b`, my commit, and `fa journal vahab` on the
authority returns H3315/H3317 from an index that now says `3142 entries through 2026-10-08 01:23 UTC`.
