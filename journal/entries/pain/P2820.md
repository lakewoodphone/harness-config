## P2820 — The company database has no off-machine copy: 216 GB of backups on the same 82%-full consumer SSD as the live 14 GB database

## P2820 — The company database has no copy off the machine it lives on

**What hurts.** `secratary` holds the authoritative 14 GB SQLite database at
`/home/zabz/personal-secretary-mvp/data/secretary.db`. Its backup system writes **15 snapshots,
216 GB, every six hours** to `~/secretary-backups` — on `/dev/mapper/ubuntu--vg-ubuntu--lv`, **the
same filesystem as the live database**, on a single PNY 500 GB consumer SSD with no RAID, no second
drive and no network mount. `backup-data.sh` contains no `rsync`, `scp`, `sftp`, `rclone`, `b2`,
`aws s3`, `gsutil` or `github` call. No restic, borg, rclone, duplicity, kopia or borgmatic is
installed, no tool config exists, and no cloud-storage credential is present in `.env`. **One disk
failure destroys the database and every one of its backups in the same second, and nobody would find
out until a restore was attempted and there was nothing to restore from.**

**Why it is worse than "backups are on the same box".** The 216 GB is not just redundant, it is
*misleading*: it looks like a backup posture, so nobody asks the question. It also actively consumes
the resource that protects the original — the disk is **82 % full** (467 GB used, 82 GB free) with
216 GB of that being these same-disk snapshots, so the failure mode is not only "both die together"
but "the backup stops silently and then the database cannot write".

**Second half: the backups are unencrypted and contain credentials.**
`personal-secretary-runtime.tgz` contains `.env`; `personal-secretary-code.tgz` contains `web/.env`
and `hetzner-tokens.env`. Combined with `F5` — the LUKS unlock key sitting in a plain file on the
unencrypted `/boot` partition of that same machine — a stolen server yields the database, all 15
backups and the keys, in plaintext. `grep` for `*.gpg`, `*.enc`, `*.age` anywhere under
`~/secretary-backups` returns nothing.

**What fixes it.** Built as stream `S-F` on 2026-09-30 (`docs/briefs/SF-backup.md`):
1. A consistent SQLite online snapshot (`VACUUM INTO` / `.backup`), never a `cp` of a live WAL
 database, verified with `PRAGMA integrity_check` before it is trusted.
2. Encrypt before anything leaves the machine (openssl with a 0600 key file; `age` if present). No
 plaintext artefact may exist outside the source.
3. Push to a **second physical location** over Tailscale — the owner's house laptop, and/or the
 Hetzner box, which is acceptable *because* the artefact is encrypted.
4. **A restore test that runs on the schedule and fails loudly**, including a deliberately corrupted
 artefact case proving the test can fail. An untested backup is a belief.
5. A guard on artefact age, source free space and destination free space, so this can never go quiet.

**Interim rule until `S-F` lands.** No new work should assume the database is recoverable. If the
authority's disk fails before this is installed, the loss is everything since 2026-09-24 — the
newest surviving artefact is a stale 1.7 GB replica on the office desktop (see `F25`).
