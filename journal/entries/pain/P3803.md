## P3803 — P3800 update: the witness was 66 minutes behind, not lost - the harvest cursor unstuck itself, and the two-surface check is what settles a send

UPDATE 2026-10-14 17:40Z, same session, and it is a relief rather than a fix.

The next send witnessed cleanly: message id `4776732163612672`, cache row `created_at`
2026-10-14T17:39:40.880Z -> `fetched_at` 17:39:43.265Z, **+2.4 s**, body read back verbatim; and
production carried the same id at 17:39:45.159. So the pipeline is capturing again.

**What actually happened, measured:** the cache was NOT dead between 16:04 and 17:39 - it was
**behind**. The 16:04:36Z inbound was captured only at `fetched_at` 17:10:59Z, a **3,983-second
(66-minute) lag**, and my 16:12 send appears finally to have been ingested in a later batch. So the
true statement is: **the harvest is batched (scheduled `15,45 * * * *`) and its cursor was stuck on a
lock long enough to build a ~66-minute backlog, which then drained.** A fresh outbound can have no
row for up to ~30 minutes normally and over an hour under contention - and it will appear later.

**The defect stands, restated without overclaiming:** a stuck backfill cursor is silent, the freshness
monitor reads `MAX(fetched_at)` from the very table that stops moving, and from inside a session a
slow ingestion is indistinguishable from a lost message. What I got wrong at 16:20 was calling it a
lost witness; what I got right was refusing to say the customer text had not gone out, because
production's own row carried the message id 6 seconds after the API accepted it.

The two-surface check is the fix for a session, and it is what settled this: **cache row OR
production's `communications` row with `twilioSid = dialpad:sms:<id>`**. Read both before reporting a
send as unwitnessed.
