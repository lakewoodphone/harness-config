## P2607 — journal.py append crashes visibly on Windows cp1252 while succeeding silently - the tool's own write path corrupts the operator's trust in it

MEASURED 2026-09-28, ZABZ-TECH (Python 3.13 on Windows). Three consecutive `journal.py append pain`
calls printed a UnicodeDecodeError traceback on stderr and produced the "Exception in thread Thread-N
(_readerthread)" noise, and each time the caller saw NO success line - so the entry looked lost.

 UnicodeDecodeError: 'charmap' codec can't decode byte 0x9d in position 46363

ROOT CAUSE, read from the traceback and the source: git subprocesses in journal/tools/journal.py are
spawned with `text=True` and no `encoding=`, so Python decodes git's output with the Windows locale
codec (cp1252) instead of UTF-8. The journal tree legitimately contains UTF-8 bytes cp1252 cannot map,
so the READER THREAD dies while the main thread continues. The write itself SUCCEEDS (exit 0, entry and
id allocated) - which is worse than a clean failure, because the visible symptom is a crash and the
durable symptom is silence.
Exact sites: journal.py:2985 `_git()` (`subprocess.run([...], capture_output=True, text=True,
timeout=45)`), and the same pattern at journal.py:2871, 2878, 2885, 2906, 2911, 2973, and
idguard.py:56.

TWO SEPARATE DEFECTS, and the second is the more important one:
 1. The decoding bug. One-line fix per site: add `encoding="utf-8", errors="replace"` (journal.py:2106
 already does exactly this, so the fix is in-house style, not an invention). A test that appends an
 entry whose body contains a cp1252-unmappable character would have caught it.
 2. A successful append that prints a traceback is indistinguishable from a failed append. Whenever
 that happens the operator's natural response is to retry, which in an append-only id-allocating
 store is how duplicate ids are born. `journal.py check` exists for exactly this and should be the
 arbiter - run it after any append whose output did not parse.

WORKAROUND THAT WORKS NOW: set PYTHONUTF8=1 in the environment before calling the tool; both appends
then succeed with clean output (verified on P2606 and L2848 in this session).
