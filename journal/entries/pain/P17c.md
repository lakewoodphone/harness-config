## P17c — A shared append-only ledger allocates IDs by read-then-increment, so concurrent writers collide

**Symptom.** `journal/LESSONS.md` contains **seven duplicated lesson numbers** (L34, L35, L36, L37, L39,
L40, L51). Each duplicate pair is two different lessons, so a reference like "see L35" is now ambiguous.

**Evidence.** Counted 2026-09-11 after a collision in this session: my own entry was written as L35, which
already existed twice, and was renumbered to L52. High-water mark was 51.

**Cost.** Every lesson in this file is *cited by number* — in `HANDOFF.md`, in `PAIN.md`, in
`DECISIONS.md`, and in the persona. An ambiguous number silently breaks the citation, which is how a
lesson stops being actionable. This is the exact failure mode that left 55 improvements unapplied: records
that cannot be referenced reliably do not get acted on. The concrete loss here is small so far; the
mechanism is the problem.

**Fix.** (1) A rule is now at the head of `LESSONS.md`: never guess the next number, take max+1, allocate
in the 100s to leave collision room, never renumber another writer's entry, prefer a timestamp per entry.
(2) **Not built, and the real fix:** the allocator should not be discipline. Any ledger with multiple
writers needs either an atomic allocator or an identity that cannot collide — a timestamp, a uuid, or a
one-line script (`next-lesson-id.sh`) that does the max+1 scan so nobody has to remember to. Discipline
across sessions that cannot see each other is not a mechanism.
