## P2122 — P2126 - the per-step tool rate limit starves repo_search, and my classifier mislabelled it as a missing tool

Measured 2026-09-20 on the authority, last 7 days of `tick_telemetry.tool_calls_json`:

 total tool calls 6,279 blocked 834 (13.3%)

**Correction to my own earlier figure.** I previously reported "31% of tool calls never execute
(565 of 1,813)". That came from grepping the raw JSON for `"executed": false`, which missed calls
recorded in other shapes. The accurate count over a proper 7-day window is **834 of 6,279 = 13.3%**.
The 31% was wrong and should not be reused.

Classified by cause:

| class | count | % of blocked | nature |
|---|---:|---:|---|
| unclassified (mostly rate limit + task-state) | 438 | 52.5 % | mixed |
| "TOOL_MISSING" | 138 | 16.5 % | **mislabelled by my own classifier** - see below |
| POLICY_REFUSAL | 115 | 13.8 % | correct by design |
| MISSING_CONFIG | 48 | 5.8 % | `alibaba_onetalk_automation`: `onetalk_url is required` |
| PREREQUISITE_GATE | 40 | 4.8 % | a step requires an earlier tool that is unavailable |
| APPROVAL_PENDING | 31 | 3.7 % | waiting for the owner - a queue, not a failure |
| TOOL_ERROR | 15 | 1.8 % | |
| DEPENDENCY_DOWN | 9 | 1.1 % | |

**Two of my own classification errors, both worth recording.**
1. I labelled `update_task` / `repo_read_file` blocks as "TOOL_MISSING - the tool does not exist".
 Wrong: reading the actual result text, the real causes are
 `repo_search: Rate limit: called 7x this tick (limit 6)` (~94 calls), and
 `repo_read_file: File not found: <path>` (45 calls). A tool that exists but is refused is a
 different defect from a tool that does not exist, and my keyword classifier collapsed them.
 **A classifier's bucket name is a hypothesis, not a measurement** - read the raw text before
 labelling a class.
2. `APPROVAL_PENDING` was hiding inside "OTHER": `Action 'X' requires approval (level 2,
 request_approval). Queued as approval #<id>.` That is the system working - it is work waiting on
 the owner, and it must not be counted as a failure, or the failure rate is inflated by design.

**The real rate-limit defect.** `app/services/agent_worker.py`:

 _PER_TICK_ACTION_LIMIT = 6 # line 216
 _tick_action_counts: dict[str, int] = {} # line 1882, comment: "persists across all LLM rounds
 # so the limit is enforced per tick, not per round"

The counter is per **step** (local to the step function) and persists across that step's LLM rounds.
So an agent gets **six calls of any one tool per step**, then that tool is refused for the remainder
of the step. For `repo_search` on a codebase, six searches is easily exceeded, and the agent then
burns its remaining rounds being told to "spread remaining calls across future ticks" - which it
cannot do, because its step is the thing running out.

**Not changed this session, deliberately.** Raising a blanket limit is a tuning decision that trades
against the runaway protection it was installed for, and the mechanism is worth understanding before
the number moves. Recorded with the exact line numbers and the measured distribution so the decision
is cheap and informed. Recommendation: a per-tool override for the read-only repo/search tools
(they cannot mutate anything, so the runaway risk is cost, not damage), rather than raising the
global cap for every tool including the mutating ones.
