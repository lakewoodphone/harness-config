## P2829 — A dry run was recorded as a delivered message: the money-ask store said the owner had been told, consuming the cap and burning the merchant

# P — a dry run recorded as a delivered message: the record said he was told

**Measured 2026-10-02, on the authority. Found while trying to answer "will his charge
question actually reach his phone?"**

`cfo-ask.py --why` is the documented dry run: "choose, compose, print, send nothing."
Its provider reply is unambiguous:

 ok=True channel=twilio-ai-line dry_run=True sid=None
 detail: DRY RUN - nothing sent. would send 209 chars from +17324447361 to +18483897895.

`provider_accepted()` returned **True** for that, and `record(..., sent=accepted)` wrote
**`sent=1, provider_ok=1`** for a message nobody received (ask #15).

**The function's own docstring already contained the correct rule** — "Did the PROVIDER
accept the message? Not 'did we ask it to send'." A dry run is the strongest possible
case of *we did not ask it to send*, and it was the one case not checked. `dry_run` was
read by `send()` (it is a key in the very dict passed in) and then ignored by the verdict.

**Three consequences, all silent, all measured:**
1. **The daily cap is consumed by nothing.** `sent_today` counts `sent=1` rows, so the dry
 run made the next genuine ask skip itself: `nothing to ask right now: only 8 min since
 the last ask (floor is 45)` at 17:01Z, when no message had been sent.
2. **The merchant is burned forever.** `asked_merchants` reads the same flag, so `data
 reclos` would never have been asked about again — the one merchant the owner had
 already answered a question about.
3. **The store asserts he was informed.** Anyone reading `~/.cfo-asks/asks.db` — or a
 future me rebuilding state after a context loss — concludes the owner was told
 something he was never told. That is the same failure as `P2828`: a confident record,
 produced by a check whose arithmetic was wrong.

**Corrections that must accompany this class of bug:**
- Fix the verdict **and** repair the rows it already wrote. The false row (#15) was set
 back to `sent=0, provider_ok=0` with the original detail preserved beneath a note
 saying what was wrong and why — never silently deleted, so the error stays legible.
- **A dry run must be recorded as a dry run**, in a column of its own if the store wants
 history. Today `asks.db` has no way to say "composed but deliberately not sent", so a
 dry run can only be represented as a wrong `sent` value or an absent row.
- **Any "accepted" verdict must be derived from the one field that distinguishes intent
 from delivery.** Here the provider hands over `sid` when it really accepted: ask #13,
 which was genuinely sent, carries `provider_sid=SMe73f56d228beb6be912d5965102e07c4`.
 A missing sid with `ok=True` is a dry run.

Recorded the same session; `cfo-ask.py.bak-drynotsent-20261002T170258Z` is the backup.
