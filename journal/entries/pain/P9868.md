## P9868 — The authority was un-writable for ten minutes and the queue's own answer command hung on it

THE AUTHORITY COULD NOT BE WRITTEN FOR AT LEAST TEN MINUTES, AND THE CAUSE WAS THE API FIGHTING ITSELF.

Measured 2026-10-21 20:05-20:18Z on secratary-cloud:
- every external write to /root/authority.db failed with `database is locked (5)`, including a trivial create/insert/drop probe with an 8s and later a 20s busy timeout;
- `owner-queue.py answer 887` HUNG: exit 124 after a 60-second timeout, twice. The owner channel's write path does not bound its wait, so a locked database looks exactly like a slow command;
- the API's own log named it: `_db_lock wait exceeded 5.0s ... the process is busy with itself; no SQLite lock was involved`, 129 lock/warning lines in 12 minutes, `dsh_session_ingest` retrying to exhaustion (retry 5), `behavioral_rules: Rule consolidation failed: database is locked`;
- one process (company-api, pid 3175280) held the database, up 4h43m, 34% CPU, database 34 GB with a 65 MB WAL.

THE FIX: `guard-service-state.sh --host secratary-cloud --op restart` -> ALLOW (posture writable), `systemctl restart company-api`, then health 200 and the write probe succeeded. The queue answer then landed through its own CLI: #887 answered at 20:19:23Z, pending 24 -> 23.

WHAT TO CARRY FORWARD
1. An external "database is locked" on this box is NOT evidence of a big transaction. Read `journalctl -u company-api` first: an in-process lock (`_db_lock`) saturating inside one Python process produces the identical exterior symptom.
2. A CLI that waits forever on a lock is a silent failure of the owner channel. `owner-queue.py answer` needs a bounded wait and a clear error, or a locked database will quietly eat an answer the owner gave.
3. The restart is the right remedy only because the host is writable and the guard said ALLOW. It was recorded here; the same action on the frozen office box would have been the 2026-10-11 incident again.

Also landed this session: owner queue #887 answered (D43), ledger 815 dropped, and the journal's own id reservation collided once on the cloud (`REFUSING to write D9601 ... reserved locally`) and recovered on its retry.
