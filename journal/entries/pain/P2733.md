## P2733 — LIVE INCIDENT: version-coupled config reached the live home while the old engine ran; switch rollback restores the engine but not the config; guard trusts a transient dshInstall

## LIVE INCIDENT 2026-09-28 19:32Z: the version-coupled config reached the live home while the OLD engine was running. Restored from a recorded pre-state; two real defects found in my own switch

WHAT HAPPENED, reconstructed from timestamps and the artifacts themselves.

The live `~/.dsh` config was rewritten at **15:32:08 local**: all three `presets`/`.agent-presets/*`
and `profiles/{web,mesh,headless}/cordis.patch.yml` began naming `@deepseek-ai/dsh-workflow-ptc`,
`@deepseek-ai/dsh-agent-preset-registry` and `@deepseek-ai/dsh-agent-preset` -- **none of which exist
on the 0.1.5 engine that is still running (pid 26856, up since 14:09)**. `dshInstall` was NOT set and
`state/pin.json` still read `0.1.5-rc.1`, `managed: false`. So the home was in the half-applied state
this entire effort exists to prevent: new sessions on `zabz`/`yocheved`/`cordis-bg` would fail to
resolve a row at mount, while every already-running session kept working.

THE MECHANISM, and it is a defect in MY design rather than in the guard's implementation. The switch
script ran three times at 19:30:09Z, 19:31:29Z and 19:31:53Z -- all three against FIXTURES
(`PRE-STATE.json` records `"mode": "fixture"`, `"targetIsLive": false`), so the switch itself did NOT
write the live config. What did was the **sync timer**: `PersonalSecretary-HarnessSync` ran at
15:32:01 (autosync -> sync.py) and applied the new config, ~40 s after a switch run had transiently set
`dshInstall` during its promote and then rolled it back.

The version guard resolves its engine root from `$DSH_INSTALL`, then **`dshInstall` in windows.json**,
then the live profile tree. `dshInstall` is set by `promote` and removed by `rollback`, so there is a
window during which a concurrent sync believes the candidate engine is the running one, PASSES the
version check, and installs version-coupled config onto a host still running the old engine. **A
transient configuration knob is not evidence of which engine is executing.**

THE SECOND DEFECT, and it is why the state persisted: the switch's ROLLBACK restored `pin.json` and
`windows.json` and re-ran `sync.py` -- but `sync.py` then correctly SKIPPED the coupled steps (the old
engine was back), so nothing reverted the config files the apply step had already written. **The
rollback restored the engine and left the config behind.** The switch had recorded every one of those
files with its sha256 in `state/switch-*/config/...` and simply did not restore them.

REMEDIATION, done immediately and verified: all six live config files were restored to the exact
sha256 recorded in `state/switch-20260928T193153Z/PRE-STATE.json`; the newer (0.1.7-shaped) files were
**moved** to `~\_live-config-quarantine-20260928T1932`, never deleted; and the restored state was
checked against the running engine -- all three presets name `dsh-workflow-worker-thread` again and the
mesh patch names `agent-presets`, so 0.1.5 can mount them. The live engine was never stopped or
restarted (pid unchanged).

WHAT MUST BE FIXED BEFORE ANY SWITCH IS RUN AGAIN:
1. The version guard must resolve the engine from the RUNNING PROCESS, or from the pin, and must NOT
 accept a transient `dshInstall` as proof of what is executing. Better still, sync should refuse to
 apply version-coupled config whenever the running engine's own version disagrees with the pin.
2. The switch's rollback MUST restore every config file it recorded, and must verify the restored
 sha256s. A rollback that reverts only the engine is not a rollback.
3. The switch must refuse to run while the sync timer can fire mid-sequence (or must take a lock), so a
 promote window cannot be observed by a concurrent sync.
4. The checker's fail-OPEN behaviour on its own error (exit 2 -> warn and proceed) is wrong for a
 VERSION guard specifically: a broken checker must not apply version-coupled config to a mismatched
 engine. Failing closed on the two coupled steps only -- never on the whole sync -- is the right
 shape.

LESSON: every one of these is the same error in a different costume -- treating a *configured* value as
a *measured* one. `dshInstall` is configuration; the running process is evidence. LESSONS L51/P22/P2732.
