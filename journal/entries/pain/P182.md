## P182 — Journal entries written on the mac mini cannot be published; entry IDs collide across machines

**Pain · 2026-09-15 · lakewooechsmini · Journal entries written here cannot be published — the harness-config checkout will not converge.**

APending H261 and L1550 worked, the local commit `9ce176a "journal: daily handoff from
lakewooechsmini"` was made, and then `git push origin HEAD` was REFUSED: the checkout reads
`## master...origin/master [ahead 4, behind 6]`. `git pull --rebase --autostash` (the
autosync's own procedure) conflicted and was ABORTED, because the collisions are not
mechanical:

- `journal/entries/handoff/H261.md` and `journal/entries/lessons/L1550.md` exist on BOTH
 sides with different content — other machines allocated the same IDs while this checkout
 was offline. Choosing a side would silently discard somebody's entry, so nothing was
 resolved.
- `journal/index/entries.tsv` also conflicted, but that one is regenerable.

WHAT WOULD FIX IT
- A collision-free entry ID (host or timestamp suffix) so two machines cannot mint the same
 ID, and/or a small reconcile tool that renames a duplicate ID, regenerates the index, and
 reports what it moved. The index should be regenerated, never merged.
- Until then every journal entry written on this machine stays local-only: the learning
 exists, but the owner's machine and the archive cannot see it. Three older local commits
 are stuck behind the same wall, so this is not new — the checkout has been unable to
 publish since at least 2026-09-15.

EVIDENCE
- `git -C ~/code/harness-config status -sb` -> `## master...origin/master [ahead 4, behind 6]`
- rebase output: `CONFLICT (content): Merge conflict in journal/index/entries.tsv` then
 `CONFLICT` on D153.md / L1510.md (`AA`), abort returned the tree to its prior state.
- `git diff --name-status HEAD origin/master -- journal/entries` shows origin adding
 H262-H275 while this machine holds H261/L1550.

RECONCILED 2026-09-15 20:05 UTC (same session, on Yocheved's instruction "make sure you are
fully git synced")
- Merged `origin/master` instead of rebasing. Only four paths conflicted, all mechanical once
 looked at: H261/L1550/P160 (add/add — origin's entries kept, THIS machine's three re-written
 through `journal.py aPend`, which allocated the free IDs H276 / L1567 / P182) and the
 generated `journal/index/entries.tsv` (taken from origin, then rebuilt with `journal.py
 index`). Nothing was discarded: the displaced entries still exist in commits c9a7ccf and
 9ce176a. D153.md and L1510.md were byte-identical on both sides, so they were no loss at all.
- The merge also produced a working superset of `scripts/repo-sync.mjs` (origin's read-only
 clone handling and case-insensitive de-dup, plus this machine's wider MANAGER_REPOS profile).
- STILL WORTH FIXING: the ID allocation is what caused this, and the 62 pre-existing base-id
 collisions `journal.py pairs` reports show it is chronic. Suffix or timestamp the ID at mint
 time and this class of conflict disaPears.
