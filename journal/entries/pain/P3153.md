## P3153 — A routine lpt-write read command claims to push the local helper over the authority's newer one

The local C:\\Users\\ezabz\\code\\lpt-ops\\lpt_ops\\write_helper.py was 175 lines BEHIND the deployed helper on the authority, and lpt-write printed '(pushed just now)' for that file on a doctor run. Three different sha256s measured for the same file in one session: local 8422bd9b, authority 6d592722, doctor's claimed push 97171e56. The authority's copy survived (it still carried its 175 extra lines: lpt-record-payment, 0e6160c), and the local checkout is now synced and committed, so the immediate risk is gone. THE RISK IS NOT: nothing prevents the next lpt-write run from pushing a stale copy over the deployed helper and destroying that work. Fix directions, cheapest first: (1) make lpt-write refuse to push when the destination is newer than the source - compare both sha256s and stop, printing both; (2) never push on a read command at all, and make 'lpt-write deploy' the only path that writes the helper; (3) have the client pull the authority's copy first and refuse if it differs from the local. WHAT IT WOULD HAVE COST: 175 lines of another session's work on a production tool, with no backup and no warning.
