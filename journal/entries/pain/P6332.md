## P6332 — ps_action/ps_ceo_chat/ps_search return urlopen Errno 111 for the whole company-api restart window (2026-10-14 11:55:34Z-11:58:34Z)

## Symptom

`ps_action("search", {"what":"journal","query":"waze boxes"})` returned, verbatim:

 {"ok": false, "error": "<urlopen error [Errno 111] Connection refused>"}

...and this is a **tool-level** failure delivered with `isError: false` (the mcp.rows.yml security
note warns exactly about this), so a client cannot tell success from failure by the flag alone.
Errno 111 is a Linux errno: the MCP server process doing the `urlopen` runs on a Linux host.

## Cause, measured

Every `ps_*` tool that routes through `_api()` POSTs to `http://localhost:8002`
(`ps_mcp_server.py:93` `API_BASE = os.environ.get("SECRETARY_API_BASE", "http://localhost:8002")`,
used at `:221`). On the authority the only listener there is `company-api.service`
(uvicorn `--host 127.0.0.1 --port 8002`, `/opt/company`, `DATABASE_URL=sqlite:////root/authority.db`).
When that unit is stopped, **all** of them return the error above.

TIMELINE, 2026-10-14 (all UTC, `journalctl -u company-api --no-pager`):
- 11:55:34 `Stopping company-api.service`
- 11:56:24 `INFO: Shutting down` <- 50 s after the stop was requested
- 11:58:34 `Killing process 355300 (python) with signal SIGKILL` <- TimeoutStopUSec=3min expired
- 11:58:34 `Started company-api.service`; 11:58:35 `Started server process [815621]`
- 11:58:44 `GET /health 200`

DURING that window, from the authority itself:
- `systemctl is-active company-api` -> `deactivating`, SubState `stop-sigterm`
- `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8002/health` -> **000**
- `ss -ltn | grep 8002` -> **NO_LISTENER_8002**
- and, in the SAME instant, `ps_db_query` answered (`pragma_database_list` -> `/root/authority.db`)
 because the DB-routed tools do not go through the HTTP API.
AFTER: `active`, health **200**.

## Why this restart was 3 minutes and the earlier ones were not

The four earlier stops today each completed in under a second (01:43:59, 02:05:53, 02:38:57,
04:20:22 -> `Stopping` and `Shutting down` in the same second, restart immediately after). At
11:55 the process was already wedged. Its own log for the preceding hour:
- `app.autopilot: run_once timed out after 600s — ABANDONING it (the thread keeps
 running; it cannot be killed) and applying backoff`
- `app.workforce: Worker tick for dept_comms_relationships exceeded 150.0s — abandoned`
- `app.database: _get_conn: _db_lock contended for key sqlite:////root/authority.db ... waiting...`
- `app.autopilot: Lifecycle sweep failed: OperationalError: database is locked`
- apscheduler jobs missed by up to 15 min; `maximum number of running instances reached (1)`
- `activity_log`: last `company_tick` 11:10:26 took **1283.93 s** for 20 agents, against 31.55 s at
 08:51:36 — the company had already slowed ~40x before the restart.

So the app cannot finish its lifespan shutdown while its own abandoned worker threads hold the
database, and systemd waits the whole `TimeoutStopUSec=3min` before SIGKILL.

## WHAT WOULD FIX IT

1. **Why the lifespan shutdown hangs** while abandoned worker threads hold the DB -- a restart
 should cost about a second, not 180. This is the real fix and it is unstarted.
2. **The memory ceiling**: 4 OOM kills in 24 h and 67% swap on a 15.6 GB box with a 27.7 GB
 database. Bounding the in-process agent worker threads would remove both symptoms.
3. Only a *mitigation*: a shorter `TimeoutStopUSec` shortens the outage window but force-kills
 in-flight SQLite writes sooner. Not to be done without reading the shutdown path.
