## P3139 — The authority API waits on its own process-wide database lock ~2.4 times a minute

# The authority API waits on its own process-wide database lock, ~2.4 times a minute

**Measured 2026-10-12, first by a mesh child (04:00–04:11Z) and then independently by me (04:13Z).**
This is the mechanism underneath two other findings, and it is not the SQLite file lock that the
`db_writable` check probes — it is the application's own in-process lock.

## What it is

`app.database._db_lock` is a **global, process-wide** lock keyed per database URL, serialising every
connection acquisition inside `company-api`. Under load its waits are logged:

```
2026-10-12T04:13:40+0000 WARNING app.database: _get_conn: _db_lock contended for key
 sqlite:////root/authority.db:135065136768704, waiting...
```

**71 such warnings in 30 minutes** (04:13Z reading, `journalctl -u company-api | grep -c`). The API's
PID 332682 had been up 2 h 51 m, 36 threads, RSS 1.4 GB.

## What it costs, measured — and what it does NOT cost, also measured

| reading | when | value |
|---|---|---|
| `GET /v1/models` (loopback) | 04:00–04:11Z | **did not return within 60 s** (the child's probe) |
| `GET /v1/models` (loopback) | 04:13:41Z | 200, **4.1 s** |
| `GET /health` | 04:13Z | 200 in 0.72 s, `ok:true, database ok` |
| `GET https://api.abletelsolutions.com/health` | 04:13Z | 200 in 0.38 s |
| the same catalogue built by a **fresh interpreter** | 04:11Z | **0.5 s** |

So the honest statement is **intermittent stalls on a chronic queue**, not a persistent outage. The
child's window caught a 60 s stall and a degraded `/health`; mine caught 4 s and a healthy one. Both
are true, and the difference is why "reproduce the claim yourself" is a rule and not a courtesy: a
transient reported as a constant is the same defect class as a constant reported as a transient.

## Where it shows up elsewhere — the same lock, three symptoms

- the kernel's `db_writable` check reported **HIGH "the authoritative database refuses writes"** for
 hours; an independent probe showed the *file* lock is contended but never stuck (30/30 acquires under
 a 25 s timeout), and `BEGIN IMMEDIATE` failing at 5 s is exactly what a queue behind this lock looks
 like from outside;
- `docs/mesh/140-PORT-CORE-AND-GAPS.md` recorded `/health` answering *"db check timed out (lock
 contention); api still responsive"* on 2026-10-11 at 06:43Z — the same thing, a day earlier;
- the gateway's catalogue read (`/v1/models`) is an in-process consumer of the same lock, which is why
 the kernel's `model_lane_health` flipped to a **false HIGH** before it was hardened with a
 fresh-process fallback that builds the catalogue locally in 0.5 s.

## What would fix it

Not identified yet, and that is the honest state: **the holder of the lock was never named** — only the
queue it creates. The next probe is inside the process, not beside it: a `py-spy dump` (or an
`faulthandler` watchdog) on PID 332682 while a probe is stalled, to see which thread holds the key and
what it is doing. Candidates worth testing in that order: a caller that acquires the connection and
then does slow non-DB work while holding it; a batch job (the offsite backup, `comms-refresh`, the
dialpad harvesters) whose long read is being serialised through the same global lock; and the
`read-pages.py` reader that child workstream 241 found holding one read transaction for ~30 minutes.

**Do not "fix" it by shrinking a busy timeout or restarting the process.** A restart may clear a
transient queue and will not touch a design that serialises every connection behind one global lock at
2.4 waits a minute.
