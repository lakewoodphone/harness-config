## P2866 — ssh -n with the payload on stdin writes an EMPTY file - I did it to three nodes at once

## P-new · `ssh -n` with the payload on stdin writes an EMPTY file — I did it to three nodes at once

**What happened, 2026-10-08 02:33Z.** Deploying `find-anything` to `linux-pc`, `hetzner` and
`lpt-apps-01`, I wrote the loop as:

```bash
ssh -n -i "$key" "$target" 'T=$HOME/bin/find-anything; cp -p "$T" "$T.bak-$TS"; cat > "$T" && chmod 755 "$T"' < "$NEW"
```

`-n` redirects the remote ssh client's stdin from `/dev/null`, which **overrides the `< "$NEW"` file
redirect on the same command line**. All three remote `cat > $T` calls therefore read EOF immediately and
installed a **zero-byte `find-anything`** — the tool itself, blanked, on three machines. The md5 gave it
away at once: `d41d8cd98f00b204e9800998ecf8427e` is the digest of an empty file.

**Why it did not become an outage.** The same loop had made a timestamped `.bak` of the live file *before*
`cat` ran, so `[ -s "$T" ] || cp -p "$(ls -t "$T".bak-* | head -1)" "$T"` restored all three, and the
redeploy verified md5 + size per node.

**Rules.** (a) When stdin carries the payload, never pass `-n` (or `</dev/null`) — they are mutually
exclusive by construction and `-n` silently wins. (b) A deploy is not done until it prints the md5 and
the size it landed, per target, and the operator compares them to the source: "no error" is not evidence
when the failure mode is an empty file. (c) Back up in the same action that overwrites — the backup being
one line earlier is what made the mistake a five-minute repair.
