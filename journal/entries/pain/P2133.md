## P2133 — P2140 - lifecycle_sweep fails 10 times in 3 hours, with TWO distinct causes

Measured 2026-09-20 on the authority. `Lifecycle sweep failed` appears **10 times in 3 hours** (it runs
every 120 s, so it fails on a large fraction of runs), and the failures are **not one defect**:

 18:09:41 Lifecycle sweep failed: ProgrammingError: Cannot operate on a closed database.
 18:25:03 Lifecycle sweep failed: OperationalError: database is locked
 18:44:49 Lifecycle sweep failed: OperationalError: database is locked

**Defect A - the lock (P2131, already recorded).** `run_lifecycle_sweep` uses ONE connection with no
transaction and calls 18 helpers that each commit independently; the first write in the chain,
`app/database.py::ensure_task_lifecycle_metadata`, reads up to 1,000 task rows and then writes metadata
on a connection that has already read. In WAL mode the write must upgrade the read snapshot, and
`SQLITE_BUSY_SNAPSHOT` is not covered by the busy handler. Same family as the four `mashgiach` defects.

**Defect B - NEW, and a different kind of bug.** `ProgrammingError: Cannot operate on a closed
database` is not a contention problem at all. It says a helper used `conn` AFTER something closed it.
This matters for the fix: making the lock correct (Defect A) would not address B, and B would then be
the remaining failure - so anyone reading only P2131 would fix the wrong thing and see the sweep keep
failing.

**Why the two were easy to conflate.** Both surface as the same single line, `Lifecycle sweep failed:
<exception>`, from the same caller. The exception type is the only discriminator, and it is easy to read
one instance and generalise - which is what I did earlier when I wrote that the sweep's failures were
"the same class" as `mashgiach`'s.

**Not yet diagnosed:** which helper closes the connection and which one then uses it. `conn.close()`
does not appear in `run_lifecycle_sweep` itself, so it is either inside a helper (some helpers take
`db_url` and open their own connection - `ensure_task_lifecycle_metadata`, `_rollup_completed_goals`),
or a helper closes the shared `conn`. The next step is to correlate the timestamp of a
`Cannot operate on a closed database` failure with the last phase that logged before it, which narrows
it to one of the ~18 helpers.

**Ranking:** this is one sweep, every 120 s, and the phases inside it (owner-message expiry, stale-claim
release, retry scheduling, goal rollup) are exactly the machinery that keeps the company's backlog from
rotting. Failing on most runs means those phases are silently skipped at that cadence. It ranks with the
wake-hop defect rather than below it.
