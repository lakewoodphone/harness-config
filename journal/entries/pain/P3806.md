## P3806 — A Quick run on a customer laptop (YZ-PINTER-LAPTO 2026-10-12) was never journalled, and its own folder disagrees about whether it left an admin account behind

Found 2026-10-15 while looking for a quick diagnostic on the shop USB (`D:`, label `USB321FD`, FAT32, 57.7 GB).

## What is on the stick

`D:\LPT-Runs\_launcher-log.txt`:

```
2026-10-12 15:42:50 | mode=Quick | host=YZ-PINTER-LAPTO | admin=True | exit=2 | 86s | quick scan, capture only
```

`D:\LPT-Runs\20261012-154253_YZ-PINTER-LAPTO\` — 41 sections, **40 OK / 1 COULD_NOT_READ** (`09-disk-chkdsk-results`). The capture itself worked.

## The defect: two files in ONE run disagree about the access window

**`handoff.txt` says no window exists.**

```
transport = T4 NOT_READY
account =
port = 0
absence check = NOT_CHECKED at
blockers:
 - filter present, no usable outbound channel
```

**`access-window.json` says a window was prepared, with a live credential.**

```
"account": "lptwinrlapto"
"port": 47567
"sshdServicePreExisting": true
"firewallRuleName": "LPT-Access-20261012-154253YZ-PINTER-LAPTO"
"revokedAt": ""
"destroyedAt": ""
```

So the *decision* record says no channel and no account; the *window* record carries a generated admin account, a port and a firewall rule, and is marked neither revoked nor destroyed. **Which one the machine actually carries is NOT KNOWN from here** — and the run's own absence check reads `NOT_CHECKED`, which is not a negative.

The kit's own rule (README rule 2, and lesson **L3324**) is explicit: *a window is not closed because the destructor ran; it is closed when the post-reboot absence check says PASS.* `teardown\Test-Absence.ps1` has never been run for this run.

## Why this was never caught

**Nothing about this run is in the journal.** `journal.py search "YZ-PINTER"` → no match. `journal.py search "lptwinrlapto"` → no match. The 2026-10-12 run left a folder on a USB stick and no record anywhere else.

## The consequence, stated as a range not as a claim

**Not claimed:** that the account exists. `T4` is the transport tier for *no usable channel*, and the design says that if the teardown cannot be armed **no window is opened at all**.

**If it was created:** a local administrator named `lptwinrlapto` on a customer's laptop, whose password is written in plaintext in `access-window.json` on a shop USB stick — the same stick that carries `D:\Brooks-Recovered`, a customer's recovered data. That stick travels between machines. This is the P2852/P2851 class: the old kit's promise of a reboot-cleanup that was never implemented.

## What would settle it, and why it cannot be settled now

Any of: `teardown\Test-Absence.ps1` against this run's own state file, on that machine; or a re-capture if `YZ-PINTER-LAPTO` is ever in hand again; or `net user lptwinrlapto` on it. **The machine left the shop on 2026-10-12 and has not been seen since.** Until one of those happens this stays an unanswered question, not a pass.

## Two side findings

- **`access-window.json` holds a plaintext credential on travelling media.** Whatever happens about the account, that file should not simply ride along on the stick. Flagged, not changed — deleting evidence before the absence check runs is the wrong next move.
- **The kit's repo copy is not findable from here.** `Deploy-LptAccessKit.ps1`, `Ingest-LptAccessKit.ps1`, `Lpt-Launch.ps1`, `Run-LptAccess.ps1` and `lpt-access-kit` all return **NO MATCH** in the estate file index. The README says *"this folder is the only source of truth… never hand-edit the stick"* — but if the repo copy is gone, the stick **is** the only copy, which is the thing that document exists to prevent.
