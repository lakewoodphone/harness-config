## P3132 — Chip's tool surface is armed by a code default, and it carried a channel from the family chat into the CEO agent; the cutover left the hub's watchdog behind for a day

## P — Chip's tool surface was enabled by a code default, not by a setting anyone looks at, and it carried a channel from a family group chat into the CEO agent

**What happened.** `app/config.py:329` declares
`family_chat_ai_secretary_tools: str = "ceo,calendar"`, so `config.ai_secretary_tools()`
returned `['ceo', 'calendar']` from the day it was written. The DB setting that
is supposed to override it (`chip_secretary_tools`) was simply absent, so the
code default won — and nothing that a person looks at mentions the tool surface
at all (verified 2026-10-12: `grep -i SECRETARY_TOOLS /opt/company/.env` returns
nothing, and the setting did not exist in the family-chat settings table).

**Why it is worse than a wrong default.** Those two tools are a read channel out
of the company and into the family group chat:
- `secretary_ask_ceo` POSTs a family member's question to the CEO agent — the one
 component that holds the whole business.
- `secretary_calendar` calls `/calendar/events` with `all_accounts=True`. The
 live probe on 2026-10-12 returned *"T-3: Global Direct Parts dispute deadline
 (#161898, $167.96)"* — a vendor dispute and a dollar figure, in a group chat of
 eleven family members. The module's own docstring says the tool surface is
 "deliberately small and guarded" and that it keeps owner-private data out of the
 group chat; the calendar call as configured is not family-safe.

**And the calendar half has never worked**, so nobody ever saw it: every call
raised `AttributeError: 'str' object has no attribute 'get'` because
`/calendar/events` returns `start` as a plain ISO string and the code assumed
Google's nested `{"start": {"dateTime": …}}`. `run_secretary_tool` catches
everything and returns a short string on purpose, so the failure reached only the
model — which then invented calendar answers ("Nothing on the calendar for the
next week") into the family chat. A silent outage with a friendly UI.

**Mitigated 2026-10-12**: `settings.chip_secretary_tools = ""` (live, no
restart), the rendering bug fixed with 13 tests. **NOT fixed**: the default in
`app/config.py` is still `"ceo,calendar"` — the only thing keeping the tool off
is a row in one SQLite file on one box.

**What would fix it properly.** The default should be `""`, and a test should
assert the delivered tool set for the family chat is empty unless a setting
explicitly turns it on. Today, deleting one row from `settings` re-arms both
tools silently — there is no test between a family group chat and the CEO agent.

## P — A migration moved the application and left its watchdogs behind for a day, and nothing noticed

The 2026-10-11 authority cutover moved the family chat to `secratary-cloud`,
where it served traffic correctly — and the office box's 30-minute drift
watchdog (the thing that exists to catch a silently broken hub: carrier-vs-ours
reconciliation, `L1572`/`P165`) was masked at the freeze and did not move. From
2026-10-11 05:47Z until 2026-10-12 00:55Z the live hub had **no** automatic
detection of exactly the failure mode that tool was written for, and nothing in
the cutover's own verification noticed, because the runbook checked the service
and the database and not the cron layer.

It was found only because this session pulled the system up by hand and ran
`crontab -l`. Ported and proven the same night (`runs.tsv` rc 0 on a real
`*/30` tick).

**What would fix it.** A cutover checklist item that compares `crontab -l`
before and after and names every entry that did not move. The office crontab is
already saved at `/home/zabz/cutover/crontab.before` (168 lines) — the
comparison is a `diff`, and it was never run. Note also that the audit that
produced `000-SYSTEMS-REGISTER.md` already knew the cron layer "never moved"
(H3408, BROKEN 1 and NEXT 4), so this is not a discovery failure — it is a
*not acted on* failure, which is the more expensive kind.
