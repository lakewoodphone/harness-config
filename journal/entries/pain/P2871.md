## P2871 — unattributable production deploy; deploy script cannot record a tripped-probe deploy; prod sign-in fails

RANKED, with what would fix each.

1. A PRODUCTION BACKEND AND FRONTEND CHANGED WITH NO RECORD AND NO OWNER.
 When this session started, lpt-backend was running lpt-lpt-backend:8c99290be12b, built
 2026-10-08T03:25:16Z and started 03:38:23Z, and the live bundle was already index-Dpcc2HPG.js
 — while /opt/lpt/.deployed.json still named a1ccd7bf58d6 and the brief handed to this session
 stated the same stale pair. So something promoted and deployed main@8c99290be to production
 about five minutes before this session began and left NO trace on the box: `who` empty, no
 tmux or screen sessions, no bash history. It cannot be attributed from the host at all.
 WHY IT MATTERS: every downstream task starts from a state it cannot verify, and "production is
 at X" becomes a guess. This is the same failure the `.deployed.json` file was created to kill.
 WHAT WOULD FIX IT: (a) make the deploy script write the record even when the guard probe trips
 — see 2; (b) have a pre-task check read `.deployed.json` AND `docker inspect` AND say plainly
 when they disagree, instead of trusting the brief.

2. `deploy-backend.sh` CANNOT RECORD A DEPLOY WHOSE GUARD PROBE TRIPPED, EVEN WHEN THE DEPLOY
 SUCCEEDED. Step 9 writes .deployed.json; step 8 `exit 3`s before reaching it. The script's
 comment says it records "never on a failed deploy", which is right in spirit — but a probe
 that fires on a known-false condition is not a failed deploy, and the result is that the ONE
 artifact the next operator reads is the OLD commit. Measured: production ran 461e37c8d2a9 while
 the record said a1ccd7bf58d6, and the same had happened to the previous operator, who wrote a
 paragraph into `guardProbe` explaining why he had to fix it by hand.
 WHAT WOULD FIX IT: write the record BEFORE the guard probe, with `guardProbe` set from the
 probe's actual result afterwards; or move step 9 ahead of step 8. PR #308 fixes the verb that
 makes the probe trip at all, so the practical pressure is gone — but the ordering defect is
 still there and will bite the next time a real guard fails.

3. PRODUCTION STAFF SIGN-IN HAS FAILED FIVE TIMES AND NOBODY KNOWS WHY.
 eliyahu@lakewoodphoneandtech.com / shopcounter2026 returns the app's own "The email or password
 you entered is incorrect." That is a real authentication refusal, not a network or CORS error
 (0 page errors, 0 failed /api responses). So either the account does not exist on production,
 or the password is not what the brief believes. Nobody can answer this from the codebase.
 WHAT WOULD FIX IT: a read-only check of whether that user row exists and is active on the
 production database — which is the owner's to authorise, and which is why it is still open.
