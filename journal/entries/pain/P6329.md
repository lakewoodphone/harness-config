# Open on the owner-text channel after the 2026-10-14 relay work: three things not yet true

Recorded so the next session does not read installation as proof.

**1. `textsend`'s owner texts are still not capped at 320 — by choice, and it is a real gap.**
`textsend` submits exactly the bytes it posts (the transport fit, up to 930), and the relay records
`too-long` rather than refusing. So its owner texts can run to ~930 chars. The app door — the loud one,
roughly 400 of 502 owner-bound sends in 30 days — **does** fit through `relay.fit()` to 320. Unifying
`textsend`'s two ceilings (`fit_owner_body`/`OWNER_TEXT_MAX_CHARS` = 320 versus
`fit_to_segments`/`SOFT_LIMIT` = 930) is a **separate, tested change** and was deliberately not made
while the record was already unreliable. Do it with the same judged==posted==recorded proof.

**2. The app texted the owner the SAME approval question three times and the live suppression is
unobserved.** Outbound rows at `01:54:51Z` (delivered), `02:35:15Z` and `02:38:42Z`, all the same
`ask_owner` body ("A question for you: Seeking approval to send the following status update SMS via
Dialpad regarding Case #4485 (Felder - Seagate BUP Slim 2TB data recovery)"). The relay recorded only
the **first** (`attempt_id=1`), because the app was still running pre-restart code for the other two —
`company-api` was restarted at `02:38:57Z`, fifteen seconds after the third. After the restart nothing
new reached him within the 90 s watch, and **no `suppressed_by_relay` row exists yet**, so the mechanism
that should now catch it (submit → `DEDUPE` → queue row marked terminal) is **in place and
unit-tested but not observed on live traffic**.

**Read this first if he complains that the same question reached him twice again:**
```
sqlite3 -readonly 'file:/root/.owner-text/relay.db?mode=ro' \
 "SELECT attempt_id,at,door,subsystem,verdict,verdict_reason,status,length(body) FROM attempt ORDER BY attempt_id;"
sqlite3 -readonly 'file:/root/authority.db?mode=ro' \
 "SELECT id,status,substr(status_note,1,70) FROM owner_message_queue WHERE status_note LIKE 'suppressed_by_relay%';"
```
Rows in the first with `verdict='DEDUPE'` mean the bell worked; **zero rows** mean the resend is not
going through the relay at all and the bypass is the thing to hunt.

**3. Door 3 was fixed on two read-only hosts on the owner's instruction, and this is the record of it.**
`company-heartbeat.sh` on `waze-mdm-01` and `lpt-apps-01` (both `read-only` in
`settings/machines/host-posture.tsv`) got two changes: `exec 9>"$STATE_DIR/.heartbeat.lock"` + `flock -n 9`
after `mkdir -p "$STATE_DIR"` (four cron lines fire into one `STATE_DIR`; at minute :00 both the `*/2`
and `*/15` lines run, and the mark was written *after* the POST), and `${down_since}Z` → `${down_since}`
(the doubled Z — `down_since` comes from `now_iso`, which already ends in Z). Both proven: the live
files had `flock` count 0 and exactly 1 `down_since}Z`; the installed files have 1 and 0; `bash -n` OK;
a sandboxed run with a stubbed `curl` exited 0 with no stderr. `sha e37fa87c…` → `0b6702c3…` on both.
**Mode changed 755 → 700** (tightening) — noted because it was more than the minimum.
Backups: `/var/lib/door3-<pid>/company-heartbeat.sh.bak` **on each host**; revert is
`cp -p <that file> /root/company-heartbeat.sh`.

**I was wrong in my first report about this door**, twice, and both corrections matter:
(a) I proposed routing the heartbeat through the relay. That is **architecturally wrong** — the
heartbeat's whole job is to alert when the company API is down, so routing it through the company's own
API would break it exactly when it is needed. Its independence is a feature.
(b) I listed the "17 duplicate COMPANY IS BACK" texts as a live defect. They are **historical**: the
deployed 2026-10-09 revision already demotes everything except `down` and `guard-exposure` (C4), and
line 789 says "recovery is never an SMS". What was actually live was only the doubled Z and the unlocked
race.
