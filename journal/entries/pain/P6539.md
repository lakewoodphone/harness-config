## P6539 — My own diagnostic runs consumed the production loop's daily ceiling, and the loop refused to run for the rest of the day

Measured 2026-10-16 on secratary-cloud, in cfo-shift-cron.sh's own log: '2026-10-16T03:00:04Z daily ceiling reached: 15/14 shifts already ran on 2026-10-16; skipping' and again at 03:22:38 with 20/14. The ceiling is the burn guard (14 cron shifts a day, written against a crash loop) and it counted every row in ~/.cfo/shifts.jsonl for the UTC day - including the twelve verification shifts this session ran to prove each fix. So the loop that exists to clear the backlog stopped running because the audit that was clearing it had spent its budget. Nothing was lost: 20 shifts of real work had already run and it resumes at 00:00 UTC. Fixed in two anchored edits: the shift row now records origin (cron|manual, from CFO_SHIFT_ORIGIN, default manual because an unqualified invocation is a diagnostic) and the ceiling counts only cron rows, with existing rows counted as cron because we cannot prove they were not and the conservative choice is safer. Verified three ways: a counter unit test on a scratch log gave 2 of the 4 rows (the intent); a live cron-path run wrote origin=cron; a live manual run wrote origin=manual and the ceiling excluded it (21 of 22 rows counted). The general lesson, same family as the metric-window lesson: when a guard counts a population, check which processes write into that population - a diagnostic that shares a production counter silently spends production budget.
