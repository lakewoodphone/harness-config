## P2997 — The case index reports 329 mismatches and a 278-vs-279 count gap, so every session inherits an obligation it skips and the warning is now noise

**Measured 2026-10-08** from `~/code/lpt-hub`, `python tools/case-index/lptcase.py check`:

```
WARNING - CASE COUNT MISMATCH: 278 case file(s) on disk, 279 tracked by git.
4 problem class(es) across 278 case files:
 [sync-record-without-case] 224
 [case-without-sync-record] 105
```

The AGENTS.md section 0 rule is explicit - "if `check` reports a case with no sync record, or a sync record with no case file, **fixing it is part of the task**" - so every session that runs `check` is now carrying a 329-item obligation it does not act on, and the warning has become noise that a reader skips. The 105 include obvious non-cases that should simply be excluded by rule, not "fixed": `_credentials-*` case files (6 of them at least) and dated name-phone slugs.

**Why it hurts:** the case index is the first thing every case lookup runs through. A count mismatch is the one signal that a reparse point or a partial clone has silently swallowed cases, and it is currently indistinguishable from ordinary backlog. Real loss and routine drift look identical.

**What would fix it, in order:**
1. A reconciliation pass that classifies all 329 pairs and acts per class: true orphans (a deleted case, a renamed slug) get the missing side regenerated or the orphan archived with an alias; `_credentials-*` and other non-case slugs get an explicit exclusion list in the index config so they stop counting as failures.
2. Resolve the 278-vs-279 git/disk gap first, because until it is explained the "4 problem classes" number is not trustworthy either - a partial clone would produce exactly this warning shape.
3. Only then re-run `check` and require it to exit clean, so a nonzero result means something again.

Not a Kogel/73459 problem and not fixed by that case's write-back; recorded because the same session hit it and it will be hit again.
