## P2992 — lpt ticket cannot find a customer by phone or by name, and the miss reads exactly like the truth

# `lpt ticket` cannot find a customer that exists

**Found** 2026-10-08 by believing it. Measured on `WO26100812727` (order id 3003, customer Niasoff
id 2799, phone `(732) 492-4311`), a live order created that day.

| query | answer |
|---|---|
| `lpt ticket WO26100812727` | **found** — full case, customer, notes, comms |
| `lpt ticket 7324924311` | *"No work order matches '7324924311' in either store"* |
| `lpt ticket Niasoff` | *"No work order matches 'Niasoff' in either store"* |

**Why this is the worst kind of defect.** The miss is indistinguishable from the truth, it reads as a
confident negative, and it is the query an operator reaches for first: a customer walks in, you type
their number. It cost a false statement in a customer's case file — I wrote "there is still no
production record for this customer" while the order sat there. It is the P3 failure mode with a tool's
authority behind it.

**What to fix.** `lpt_ops/queries.py` / `cli.py` resolution for `lpt ticket`. The `lpt-production-case-work`
skill already records the trap: *production stores `+17325036608`, so a naive string compare matches
nothing — compare the right ten digits*
(`right(regexp_replace(coalesce(phone,''), '[^0-9]', '', 'g'), 10)`). The name path needs the same
treatment (case, punctuation, and the customer/order join).

**Definition of done.** These three all answer with order 3003: the `WO` number, the phone in any
format (`7324924311`, `(732) 492-4311`, `+17324924311`), and the surname in either case. Add that as a
regression case, because it is a live order and it is already known to fail.

**Until it is fixed:** never report a production negative from `lpt ticket` alone. Ask a second key —
and prefer the order number or a direct `select` through `lpt_ops.transport`.
