## P261 — lpt-hub is one shared working tree across concurrent sessions, so staged files get swept into another session's commit

MEASURED 2026-09-17. In lpt-hub on ZABZ-TECH at least three sessions are working simultaneously in ONE working tree (untracked _scratch files from a Rosenberg session and a Shlock session appeared mid-task).

WHAT HAPPENED: I ran git add on my own files, then git commit. Between the two, another session committed - and its commit (624798d08, 'shlock(as-built): both footing rows documented') swallowed my staged files. My work is safe and present in HEAD, but publish.py and deploy.py are now recorded as having been added by a commit about wind loads, and my commit message with the whole rationale is gone from the history. Nothing is lost (the rationale lives in the files' own docstrings and in H530/L1964) but the record is misleading and a future reader bisecting will be confused.

ALSO: the clone is DIVERGED - 62 local commits against 26 on origin/main, so git pull --ff-only refuses and nothing can be pushed. This work is INVISIBLE to every other machine until that is resolved. An untracked _scratch/journal-pain-clone-diverged.md from another session suggests someone is already on it - check before opening a duplicate.

WHAT WOULD FIX IT (in order of value):
1. Do not share one working tree between sessions. One git worktree per session (git worktree add) removes the sweep entirely and is the mechanism already used for agent fleets.
2. If a shared tree must stay: hold the index across add+commit with git commit -o -- <paths> (commit only the named paths, ignoring what else is staged), or git stash push -- <paths> then commit from the stash. Both narrow the race to a single command.
3. Resolve the divergence so work can actually reach origin. That needs a human decision about the 62 vs 26, or a rebase owner.

SEVERITY: low for data (nothing lost), high for trust in the git history of a repo whose whole purpose is being the durable record.
