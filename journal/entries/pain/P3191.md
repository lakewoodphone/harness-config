## P3132 — The company API wedges - active but never answers, no log lines, 23GB SQLite with persistent lock contention; watchdog fuse is 30min

**P — the company API wedges: it accepts TCP and never answers, and the watchdog
that exists for it is threshold-based rather than prompt. NOT caused by the
Shabbat work; found while verifying it.**

## What was measured (2026-10-09, 21:00-21:06Z)

```
/health http=000 time=20.0s 0 bytes received
/shabbat/status http=000 time=20.0s 0 bytes received
/shabbat/safety http=000 time=20.0s 0 bytes received
ss -lntp LISTEN 0 2048 0.0.0.0:8002
systemctl ActiveState=active SubState=running
journal no new lines for several minutes
load average 1.24 (so not load)
/home/zabz/bin/health-gate.sh -> DOWN
```

A hung process, not a busy one: the port accepts connections, the unit reports
healthy, and nothing is logged. Nothing detected it in a way that acted.

It did **not** recover on its own over 6+ minutes. Restarting
`secretary-api.service` fixed it immediately.

## Why it matters beyond the API

It is the substrate for everything, including the thing I was verifying: at
20:04 Saturday the Shabbat power-up needs this process to relock the interior
door and re-assert the ceiling light. 90 minutes earlier I had already seen the
same symptom once — `/shabbat/status` timed out at 20:17Z and answered instantly
after a restart at 20:14Z. So this recurs within a single evening.

The new `recover_incomplete_power_up` mitigates it for this specific case: it
retries every minute until the API answers, so a wedge delays the door relock
rather than losing it for a week. That is the correct behaviour and it is why the
retry round matters more than it looked.

## The underlying condition, still present

`/health` returns HTTP 200 with

```json
{"ok": false, "database": {"ok": false,
 "error": "db check timed out (lock contention); api still responsive"}}
```

on **4 of 4 samples**, and `data/secretary.db` is **23 GB** with a 64 MB WAL on a
filesystem at 81%. The API deliberately answers degraded rather than failing, so
this alone is not the hang — but it is persistent, it is the same subsystem, and
a 23 GB SQLite under WAL is the obvious place to look next.

## What I did NOT conclude, and why

I nearly wrote that the watchdog was broken because my hand-run got
`Permission denied` writing its state file. The facts say otherwise:
`secretary-api-watchdog.service` sets **no `User=`**, so its timer runs as root
and can write those files; the denial was an artifact of running the script as
`zabz`. It had in fact noticed the wedge (`degraded #2: secretary-api.service is
active but /health says DOWN`) — it simply had not reached its restore threshold
(6 readings, ~30 min). **Running a component as the wrong user is not a
measurement of that component.**

## What would fix it properly (its own session, not this goal)

The failure to target is "active but not answering", and the response should be
prompt. Options in rough order of value: (1) make the wedge itself rare by
addressing the SQLite lock contention and the 23 GB database; (2) have the
watchdog escalate on *responsiveness* with a shorter fuse than 6 readings when
the gate says DOWN; (3) have the API log a heartbeat so "no new lines" is itself
an audible signal. This is the company's own substrate and deserves its own case,
not to be folded into the Shabbat work.
