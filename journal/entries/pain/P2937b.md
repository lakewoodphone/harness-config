## P2937b — the journal has two disjoint id namespaces: 276 entries, including every id the master records cite, exist on one machine only

## 2026-10-12 05:35 UTC · ZABZ-YOGA · the journal's ids are two disjoint namespaces, so every master record written tonight cites entries a reader on the authority cannot open

**Measured 2026-10-12 05:30Z by hashing every entry file on both machines** (`journal/entries/**/*.md`,
sha256 both sides, then compared filename sets):

| reading | value |
|---|---|
| entries on ZABZ-YOGA | **3,511** |
| entries on secratary-cloud (the authority) | **3,262** |
| filenames present on both | **3,235** - same heading, different bytes on every one (they are the same entries; 240 of the laptop's files carry CRLF, the authority's are LF, so the two trees were written by different paths) |
| **on ZABZ-YOGA only** | **276** |
| **on the authority only** | **27** |

**The damage is not a two-entries-one-id collision.** Both trees are internally consistent (the
laptop's `journal.py check` = 0 errors), and `P1` on one machine really is `P1` on the other. What is
broken is that the two **id allocation spaces have drifted apart**, and the entries in the delta are
exactly the ones tonight's work cites:

 journal.py show H3568 -> present on ZABZ-YOGA, ABSENT on the authority
 journal.py show L3736 -> present on ZABZ-YOGA, ABSENT on the authority
 journal.py show P3139 -> present on ZABZ-YOGA, ABSENT on the authority
 journal.py show W2738 -> present on ZABZ-YOGA, ABSENT on the authority
 journal.py show D3050 -> present on ZABZ-YOGA, ABSENT on the authority

Those five ids are cited by `docs/mesh/170`, `171`, `172` and `173` respectively - **the four master
records of this night's work.** A reader standing on the authority, which is where the company's
agents run and where the search index (3,259 journal entries) is built, cannot open any of them. The
same document reads differently depending on the machine.

**Root cause.** Every machine allocates its own journal ids from its own counter. Two machines writing
for a day produce two disjoint spaces with no error raised anywhere, because each tree is only ever
checked against itself. This is the class `117-journal-divergence.md`, `P13` and `163` already record,
and the tooling to repair it exists and is unapplied: `journal.py repair-ids --apply` (renumbers a
collision and records the alias), `dedupe --apply` (exact duplicates to `archive/duplicates/` with an
alias), `import-legacy --apply` (absorbs a stale writer's entries).

**What is missing is not a tool - it is a decision.** Convergence needs one machine named as the
single allocator of journal ids, and until there is one, every future repair re-drifts. The candidate
is the authority, for the same reason it is the sole writer of the company database: it is always on,
it is where the agents and the search index are, and it is where the reader who needs the citation
actually stands. **Not made here - it is an estate decision and it belongs with the same class as the
canonical-remote migration (`162`, D3034).**

**The cheap diagnostic that should exist and does not:** one command that reports the entry-set delta
between two machines (present here, absent there, same-id-different-bytes counts). Tonight it was a
hand-run pair of sha256 manifests and a python set intersection. It belongs in `journal.py doctor`
next to `legacy drift`, whose whole point is the same question for the frozen flat files.
