## P2554 — The mesh subagent provider fails deterministically - fleets must run LOCAL and say so

## PAIN — the mesh `subagent` provider fails deterministically; the fleet had to run local

**Measured 2026-09-28, twice, from ZABZ-YOGA.** Both `subagent` calls failed with the provider's own
diagnostic, verbatim:

> `the transport reported host "", which is not one of the hostnames the placement named
> ("secratary" may be secratary) — refusing to report work from a node the broker did not name`

Corroborating readings, same hour:

- `curl -s 127.0.0.1:3091/nodes` from the authority: `zabz-tech` **HTTP 502**;
 `zabz-tech-linux` and `lakewooechsmini` **timed out after 4000 ms (hard wall-clock deadline)**;
 only `zabz-yoga-1` (12 slots) and `secratary` (1 slot) reachable.
- `ssh secratary-ts 'which dsh'` returns **nothing** — `dsh` is not installed on the authority, which
 is the likeliest reason a placement naming that node cannot produce a host identity.

**Impact.** Rule 1c says never fan out locally while the mesh is reachable. The mesh was not
reachable, so the fallback was taken and every result of that fleet is marked **LOCAL**. The code
under test was still production (branched from a snapshot of the live tree), but the computation ran
on this laptop.

**What would fix it.** (1) Install the DSH runtime on `secratary`, or point `MESH_TARGET_NODE` at a
node that has it — the mesh profile defaults to `laptop-ts`. (2) Repair `zabz-tech`'s HTTP 502 —
it is the office desktop with the most headroom and it is unusable. (3) The broker's own
`readFailures` counter stood at **995 of 1,653 reads** when read today, which says this is not a new
condition.

**Why this is a company problem, not only a harness one.** The secretary company dispatches work to
this same mesh (its owner queue is full of `Mesh node '…' cannot take agent work` rows). While the
mesh is degraded, the company's fan-out silently degrades with it — and its own `proactive_update`
rows show it noticed and told the owner *54 times* instead of fixing it.
