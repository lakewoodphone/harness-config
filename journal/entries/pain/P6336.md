## P6336 — Two sessions edited the live company autopilot at once; only a stop-clause in a brief prevented a silent revert

Two agent sessions were editing the same live production file at the same time, and the only thing that prevented a silent revert was a stop-clause written into a build brief.

MEASURED 2026-10-14. A build child began the repetition-guard change correctly: it read the live `/opt/company/app/autopilot.py`, confirmed md5 `30a4a185a8e28395092032fc4d367f36` (522,614 B), copied it, and committed the copy as the preserved base (`e674edd`). **Then the live file changed underneath it at 12:20:47Z** to md5 `2c78b91c6cf0b5f838063f05678ad33b` (524,114 B), a delta that removes `from app.database import _db_lock, _get_conn` and every `with _db_lock:` block — another session's database-contention fix, recorded in `/opt/company`'s git as `M app/autopilot.py` with **1,413 insertions / 333 deletions**. The child stopped, as its brief told it to, and did not build on a moving target. **Result: the change is implemented, the patch is prepared and verified applicable, and nothing was deployed.**

What exists now, and what it is worth: preserve commit `e674edd` on branch `evolve3/repeat`; a prepared patch at `/tmp/evolution-v3/P3c-prepared.patch` (4,913 B, 3 hunks) for which `git apply --check -p1` exits **0 against the frozen base AND 0 against the current live file** — the concurrent edits lie outside the hunks, so applying it would not revert them; and `/root/work/evolve3-repeat/REPORT.md`. **It is UNTESTED**: no test was run and the regression test is only specified, not written. Under this estate's own rule — never merge a change whose tests you have not run — that patch is a draft, not a fix.

**The hazard, named:** `/opt/company` is a live tree carrying ~110 uncommitted files that belong to several different sessions, and at least one of them is editing `app/autopilot.py` heavily while another is reading it as a base. **Every deployment therefore races every other session, and the failure mode is silent: a patch that applies cleanly can restore a block another session just deleted.** Nothing in the estate serialises these edits — there is no lock on the live tree, no claim on the file, and no record of who is mid-edit except an incidental `.bak`.

**What would prevent it, in the smallest form:** a claim file for the live tree (`/opt/company/.editing-lock` holding the session id, the file, and a timestamp), taken before an edit and released after, that a deploy script checks and refuses on — the same single-flight discipline `wake-fanout.sh` already implements for its dispatchers and `agent-fleet` implements for worktrees. **This estate has solved this exact problem twice for its own automation and has no answer for its live application tree.**

Two smaller facts from the same session, recorded because they are the kind of thing that gets lost: the child's import check wrote `/opt/company/app/__pycache__/autopilot.cpython-314.pyc` (478,227 B) into the live tree — a bytecode artifact, no source, DB or service touched, and it disclosed it rather than hiding it; and the child had to be **rerouted** because the broker first placed it on `zabz-tech` (Windows) where the work was impossible, which cost a transport attempt before it landed on `zabz-tech-linux`.
