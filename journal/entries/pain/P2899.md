## P2899 — unified-search: 112 s cold query, a 21-day-dead refresh, and 74% of the index is duplicate scratch copies

## unified-search: the indexed surface the owner is asking for already exists, and it is broken in five measured ways

Measured on ZABZ-YOGA, 2026-10-09, local index `C:\Users\ezabz\.usearch\usearch.db` (8.53 GB).

**What it is.** `unified-search` (`C:\Users\ezabz\code\unified-search`) is a federated FTS5 index over
seven corpora — files, chats, git, journal, localdb, secretary, comms — holding **389,026 documents /
2,884,529 chunks** on this laptop. Built 2026-09-15, audited 2026-09-16, 459 tests. Architecturally it
already satisfies the owner's criterion ("under 5 seconds from any of our files anywhere"). **It is not
what agents are told to use.** The `fast-search` skill and `presets/zabz/agent.cordis.yml` both point at
`fa` / `ps_action("search")`, a different and weaker system with no content index for code. Three
parallel search surfaces exist; the best one is undiscoverable.

### D1 — a query that should be 0.16 s takes 14 s
`python scripts/usearch.py query "dialpad transcript"` = **14,020 ms internal, 14,616 ms wall.**
Measured components of the same query, same interpreter, same file:

| component | measured |
|---|---|
| raw `rowid, rank` over `chunks MATCH` | 73 ms |
| the tool's exact SQL (join + full projection + `c.text` + `bm25`) | **163 ms** |
| `match_estimate()` — vocabulary lookup per term | 18 ms |
| `fts5vocab` GLOB over the prefix (`dialpad*`) | 7.5 ms |

So the SQL, the join, the projection, the `bm25` ranking **and** the vocabulary lookup are each fast,
and the function that contains them is not. The remaining candidate is the cold-cache first touch of an
8.5 GB index — the 163 ms figure was taken warm, after earlier probes had paged it in. Whatever the
final answer, the first query after idle is over budget and it is not the query plan.

Compounding, and independently true: `usearch.py:1247-1255` sets
`max_ranked = max(200, int(total_chunks * 0.02))` — **the guard threshold scales with the corpus**, so
it can never protect a latency budget as the index grows. At the 273,108 chunks the audit measured, 2%
was 5,460 chunks; at today's 2,884,529 it is 57,690. The audit's "two terms = 4.8 ms" was measured on
an index 10x smaller than this one.

### D2 — the refresh has been dead for 21 days and nothing noticed
Task `DSH unified-search refresh`: `LastRunTime` 2026-09-18 08:44:05, **`LastTaskResult=1`**,
**`NextRunTime` EMPTY**. Cause found: its trigger's repetition pattern is `Duration=P1D,
Interval=PT30M` — it fired every 30 minutes *for one day* and then the pattern expired. That is exactly
where the runs stop. Registered by `scripts/install-sync.py`.
This is the **second** time this class of failure has landed; the audit already records a previous
"next run: NONE — a task with no next run time will not fire".
Also: `ExecutionTimeLimit=PT1H` while `db:localdb` alone measured 834-1,150 s per run, so a full run
cannot fit inside the limit — L1814's orphan-holds-the-lock failure is one step away.

### D3 — 74.2% of indexed file documents are throwaway duplicates
Of 158,056 indexed file documents, **117,319 are under top-level `_` scratch directories**:

| bucket | docs | share |
|---|---|---|
| `_fleet` | 33,414 | 21.1% |
| `_scratch` | 17,416 | 11.0% |
| `_lpt-w6-wt` | 11,629 | 7.4% |
| `_pt_hours` / `_pt_deploy` / `_pt_faqfix` / `_pt_clients` / `_pt_w6_base` | ~52,511 | ~33% |

Those five `_pt_*` directories are **five near-identical ~10,500-document copies of the same repo**.
`SKIP_DIR_GLOBS` (`adapters/files/sync.py:116`) covers `*workingtree* *_archive* *_snapshots*
*backup* *_worktrees* *_old*` — it does not cover `_*`. The measured consequence: one query returned
the same file three times, from `_scratch/`, `_fleet/probe-endpoints/` and `_fleet/loop-close/`.
Meanwhile `phone-and-tech-full` — a whole monorepo — has **75** documents indexed; the full-corpus pass
never finished.

### D4 — there is no way to call it
Nothing is on PATH on Windows: no `usearch`, no `usearch-mcp`, no `fa`. The only way to query is
`python scripts/usearch.py query …` from one specific directory. `~/.usearch/bin/` holds only
`usearch-refresh.cmd`. A new agent on a Windows node cannot discover or call the indexed surface at all.
The scheduled task also runs **Python 3.12** while everything on PATH is **Python 3.10** — two
interpreters; the index's SQLite is 3.40.1, below the CVE-2026-11822 fix (needs 3.53.2, P203).

### D5 — sources that fail every run, or redo all their work
- `files:local` fails **every** run: `adapter exited 3: source=files:yoga state=…files.json`. The
 registry entry named `files:local` passes `--source files:yoga`, so the index holds both a
 `files:local` (132,214 docs) and a `files:yoga` (25,842 docs) corpus, colliding.
- `db:localdb` re-ingests **153,232-163,115 documents on every run** and takes **834-1,150 s**. It is
 not incremental. That is why the index reached 8.53 GB.
- `journal_size_limit` reads **-1 (unbounded)** although `docs/AUDIT.md` states the WAL is bounded.

### What would fix it, in order of effect on the criterion
1. Locate and remove the real 14 s (instrument `search()`; the query plan is exonerated).
2. Make the guard's threshold an **absolute** cost bound, not a fraction of a growing corpus.
3. Add `_*`, `.lptwork`, `.tmp-*` to `SKIP_DIR_GLOBS`; prune the 117,319 already-indexed scratch
 documents; `VACUUM`. Results stop being duplicates and the index shrinks by most of its size.
4. Re-register the refresh with an **indefinite** trigger and an `ExecutionTimeLimit` that fits a real
 run (or make `db:localdb` incremental first).
5. One command, on PATH, on every OS, `--json` everywhere, provenance on every answer.
