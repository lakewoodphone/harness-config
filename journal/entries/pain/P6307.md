## P6307 — The label printer can be stuck in ERROR with the right roll loaded, and from a remote session that is neither diagnosable, clearable nor provable

**Measured 2026-10-13, from ZABZ-YOGA, printing the Schreiber price label for ticket 2657.**

The Brother QL-820NWB (serial `H3G354844`, firmware 1.25, 192.168.50.60) reported **Device Status ERROR** on its own status page while reporting **Media Status "Not Empty", Media Type 29mm / 1.1"** - the correct endless roll, tape present. `lpt-label find` therefore exits **2** ("READY" or "PRINTING" are the two states that mean we may send work), and the tool was right to. The dry run still rendered (25.4 mm earlier, 27.9 mm for this label) and the print still reported `sent ... 27.9mm of tape`, but the state was ERROR **before and after** the send, so **whether tape came out is unverifiable from anywhere but the printer**.

**What hurts.** There is no path from a remote session to (a) find out what the error is, (b) clear it, or (c) prove a print. The HTTP status page names only "Device Status ERROR" - it does not say media error, cover, cutter or jam - and the 9100 status register is not answered on this model. So a label requested from home (or from any session not standing in the office) is a job whose outcome nobody can check, and the only remedy known to work is a **physical power cycle at the office** (already recorded: the 2026-10-12 freeze the owner had to clear by hand).

**What would fix it.** Three things, in order of value: (1) a `lpt-label status --why` that prints the Brother status frame's own error code rather than the page's single word, so ERROR can be classified instead of guessed; (2) a documented remote-clear attempt (a job on the matching media, or the device's own initialise) BEFORE concluding a power cycle is needed - the current state is indistinguishable from a stuck queue; (3) a second print path that a remote session can verify end-to-end, because the office LAN printer is reachable only from the office box. Until then: after any send, the honest sentence is "accepted by the transport, tape unproven", and a session must say what it observed rather than reporting a print.

**Evidence:** `lpt-label find` -> `state ERROR`, media `Not Empty 29mm`, exit 2; `curl http://192.168.50.60/general/status.html` (device-rendered text) -> `Device Status ERROR`, `Media Status Not Empty`, `Media Type 29mm / 1.1"`; the send line `sent to 192.168.50.60 (Brother QL-820NWB, state ERROR, roll 29mm) - 27.9mm of tape, image /tmp/lpt-label-20261013T154832.png`; state re-read ERROR after it.
