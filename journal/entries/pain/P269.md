## P269 — The mesh provider never tells the parent it has a child, so the Subagents UI can never show one - structural, not a config flag

**P · The mesh provider never tells the parent it has a child, so the Subagents UI can never show one — this is structural, not a config flag**

MEASURED 2026-09-18 on ZABZ-YOGA, immediately after the engine reload, with THREE background mesh
children demonstrably running (`job_list` -> `subagent-1/2/3 running`). This session's own projection
rows, read from `~/.dsh/storages/session_projcache/sessions/<id>.json`:

```
subagent (seq 478): {}
subagentCatalog (seq 478): {"inheritedEventCount":0}
subagentTiming (seq 478): {"descriptorSeen":false,"settledMs":0,"pendingTurnStart":...}
```

`subagentCatalog` has ZERO entries while three children are alive. The UI chip the owner watches
(`dsh-client-ui-subagent`, registered on `conversation.session.header.lineage`) computes its text from
`descendants.runningCount`, which is folded from `subagentCatalog` — so it renders "N subagents" and
never "N subagents running", no matter how many mesh children exist.

WHY, and it is not a bug in the UI: the catalogue is written by `establishCatalogChild` in
`@deepseek-ai/dsh-subagent/lib/types/catalog.js:86`, which appends a `subagent/catalog` event to the
PARENT session when a CHILD SESSION is established in the parent's own engine. That is exactly what the
`spawn` (local) and `fork` providers do. The `remote-ssh` provider establishes the child session on
ANOTHER MACHINE — that is the whole point of it — so the parent's engine never sees a child session and
never writes the event. The UI is faithfully reporting "no children I know about", and the parent
genuinely does not know about them.

CONSEQUENCE, and it is the owner's own words twice over: *"if a bunch of subagensts are running why
doesn't the top left subagents tab show anything running"* (2026-09-18), and *"it is supposed to take a
second to call and then i see it here on the top left"*. Turning on `enableRunInBackground` (L1999) fixed
the BLOCKING half — the tool now returns a durable id at once and the children appear in the background
JOB list. It does not and cannot fix the CATALOGUE half, because the catalogue is about child SESSIONS
and a remote child is not one.

WHAT WOULD FIX IT, and it is a real code change, not a setting: `packages/plugin-remote-fanout` should,
at the moment it places a child, append a catalogue fact to the parent session — the child's id, the node
it was placed on, and the lease id the broker returned — and withdraw it at settle. The fact must come
from the provider (it is the only party that knows the node and the lease), and it must be honest about
being remote: a mesh child is not a session this engine can open, so the row should say so rather than
pretend to be a local child the UI could navigate into. Until that exists, the background JOB list is the
only honest place a mesh fan-out is visible, and any surface that claims otherwise is showing a
count that is not a count.

NOT DONE YET. Recorded so it stops being rediscovered, and because "the UI doesn't show my subagents" is
the single most repeated complaint in this seat's history.
