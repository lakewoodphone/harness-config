## P4185 — The estate has no single journal view: every machine reads its own branch, a negative is silent about which tree it searched, and id L4512 is already allocated to two different entries

Measured 2026-10-15. The estate has no single journal view, and a journal read on any one machine can be a false negative about another.

 ZABZ-YOGA HEAD = incident/deepseek-spof-20261015 113 ahead of main, 1 behind
 secratary-cloud HEAD = hk/182-wake-family-key 125 ahead of main, 0 behind
 main last commit a0987e61, 2026-10-14T04:00Z - so both machines are ahead of a stale trunk

Consequences actually observed in one session:
- `journal.py search "MTU"` on ZABZ-YOGA returned "no match" (exit 1) while the entry existed on the authority's tree. The negative looked like absence and nearly became a reported continuity loss.
- id L4512 is allocated to TWO different entries: on the authority it is the house-network MTU lesson; on ZABZ-YOGA it is the DeepSeek outage lesson. The id space has already collided across trees.
- H4553 is absent from ZABZ-YOGA entirely.

What hurts: a reader on any node cannot tell from the tool's output which tree it searched, and the write side (a session appending from a remote node) lands wherever that node's checkout is. Every "I searched and found nothing" in the record is therefore conditional on a branch that is never printed.

What would fix it: make journal reads report the tree (branch, commit, entry count, newest entry id) in the same line as the negative, and stop allocating ids from a per-checkout counter. The merge itself is a separate, larger job - the 113 and 125 commits have to be triaged first, and they are not all real work.
