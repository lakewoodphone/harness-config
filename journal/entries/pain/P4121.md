## P4121 — DSH has a provider single point of failure: one pinned model literal across three machines, no automatic fallback, and nothing watches provider health

The DeepSeek outage of 2026-10-15 00:11Z proved a single point of failure that is STILL OPEN: the owner's DSH has no automatic provider fallback, so when DeepSeek stops answering, every session on every machine he uses stops with it, and the harness retries the dead provider until the policy is exhausted.

The mechanism is one literal shared by three machines. `settings/base.yaml:58-60` pins `agent-default-model: {provider: deepseek-official, model: deepseek-flash}`; ZABZ-TECH, ZABZ-YOGA and SECRATARY machine files carry ZERO override rows. The same value is stated again at `profiles/web/cordis.patch.yml:1739`. A second provider, `llm-pi-ai` with DeepInfra, is already MOUNTED (`cordis.patch.yml:1742`) and is never automatically used. There is no fallback code to find in `@deepseek-ai/dsh-llm` or `dsh-llm-pi-ai`.

What it cost, measured: 20 sessions across zabz-tech, zabz-yoga and zabz-tech-linux; 28 `llm/retry` events all naming `deepseek-official`; 5 sessions with a turn that started and never ended; a 23-minute-3-second model timeout and four 15-minute parallel calls returning no choices; and 0 ticks in the 01:00Z hour. The company itself survived on its own gateway chain (Gemini flash-lite), so the outage was survivable and was not survived — the failure is in DSH's model path alone.

Two things make it worse than it needs to be. First, the owner has ALREADY PAID for the backup: `claude-haiku-5-5` returned HTTP 200 in 1079 ms on a live probe at 02:41Z, the key is present in `~/.dsh/.credentials.yaml`, and it is wired to nothing. Second, ARM NOTHING DETECTED THIS. The outage was discovered by the owner from a status page two and a half hours in; nothing in this estate watches provider health and nothing announced it. The next one will be found the same way until a watcher exists.

WHAT WOULD FIX IT, in order: (1) provider-layer failover in DSH triggered by connect error / 5xx / timeout with no human edit and no restart; (2) defined ONCE in `settings/base.yaml` and reaching every node by the existing sync, never per-machine; (3) both stating surfaces moved together (`base.yaml:58-60` and `cordis.patch.yml:1739`); (4) model ids resolved at runtime from the provider catalog, never hardcoded; (5) a money cap on the fallback tier because Haiku 5.5 inverts to roughly 7-10x per call above 100k prompt tokens and our loops sit near 217k; (6) an alert on primary-provider death so the machine tells us instead of the owner finding out. Full evidence and the design constraints: `docs/mesh/177-DEEPSEEK-SPOF-INCIDENT-2026-10-15.md`.
