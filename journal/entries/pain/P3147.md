## P3147 — The label tooling lives on a read-only box, so it drifts a revision behind

The only host that can reach the shop's label printer is the frozen rollback anchor, so the label
tooling there cannot be updated the normal way and every improvement has to be run by hand out of a
git checkout on a read-only box.

Measured 2026-10-12: `secratary` (= `secratary-ts`) is posture `frozen`/READ-ONLY in
`harness-config/settings/machines/host-posture.tsv`; `secratary-cloud`, the authority, cannot reach
192.168.50.60 at all (`curl` -> 000) and has no `lpt-label`; the deployed `~/lpt-ops` on the anchor is
a plain copy one revision behind the repo, so the `!` headline marker prints literally and short
lines are sized per-line. A session that deploys the fix breaks the freeze; a session that does not
prints with the old renderer.

What would fix it, in preference order:
1. A writable always-on host on the office LAN that owns the labeler - the office desktop `zabz-tech`
 is on that LAN but is not always on, which is why the tool came to rest on the anchor in the first
 place.
2. Keep printing on the anchor and treat "run it from the checkout with PYTHONDONTWRITEBYTECODE=1"
 as the permanent, documented convention (works today, needs no write, gives current code).
3. An explicit, named-yes deploy of `lpt-ops` to the anchor - only with the owner's approval for that
 exact file, recorded, and reverting the freeze decision's scope on purpose rather than by accident.

Do not let a future session "fix" the stale renderer with an unannounced deploy; that is the mistake
this entry exists to prevent.
