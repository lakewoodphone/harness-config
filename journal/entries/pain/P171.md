## P171 — W3's whole-suite numbers do not reconcile: 11 failed post-fix against 10 at base, with the extra one claimed pre-existing

OPEN QUESTION, 2026-09-15. W3 reports two whole-suite numbers that do not reconcile:

 post-fix: 11 failed, 2750 passed
 base: 10 failed, 2571 passed

It states "the 10 pre-existing failures are identical" and separately states that the one failure in its targeted file set (`test_get_all_candidates_prefers_route_primary_first`) is environmental, caused by `No LLM provider API key found`, and that it PROVED this by running it on the base commit in an isolated worktree.

Those two claims are in tension: if that failure pre-exists and was proven on the base commit, it should be inside the base's 10, and the counts should be 10 vs 10. A delta of +1 is therefore unexplained. It is most likely a counting artefact -- the two runs have different test totals (2571 vs 2750) because W3 added tests, and a parametrised or environment-dependent test can appear in one run and not the other -- but that is an explanation I am inventing rather than measuring.

WHY IT IS WORTH ONE COMMAND: this session's recurring discovery is that green (and red) test signal in this repo is weaker evidence than it looks. Every fleet worktree lacked `.env`, so all fleet test output was measured under DEFAULTS rather than production config; one branch's tests pass 30/30 in a worktree and kill the process on live; and a suite here has a known flaky pair that races a background thread (`elapsed < 0.6`). So "one extra failure, probably environmental" is precisely the kind of claim that should be settled rather than absorbed.

SETTLE IT WITH: run the whole suite on the base commit and on W3's branch with an identical `--basetemp`, capture both failure ID lists, and diff the two ID sets rather than the counts. The counts are confounded by +179 new tests; the ID sets are not.
