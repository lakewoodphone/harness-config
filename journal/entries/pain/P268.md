## P268 — The fleet has been unable to read or write any Dialpad office configuration since 2026-06-14 - the admin tooling replays a three-month-old captured session

MEASURED 2026-09-18 03:2xZ on the authority.

scripts/dialpad_ivr_admin.py authenticates against Dialpad's INTERNAL API (https://dialpad.com/api/group/...) by REPLAYING browser XHR headers captured from the Dialpad UI. It loads them from the secretary DB table dialpad_ui_xhr via _load_captured_headers(). That table's newest row is 2026-06-14T16:01:43Z - over three months stale - so every call 401s. Confirmed: the run failed with "Failed to fetch Dialpad group state: HTTP 401", and the captured rows are only GETs against /api/group (no write or media endpoint was ever captured).

WHY IT IS EASY TO MISDIAGNOSE: the real DIALPAD_API_KEY in ~/personal-secretary-mvp/.env is VALID and returns 200 on GET https://dialpad.com/api/v2/offices (and /zones, /r2/buckets on the Cloudflare side). So "the Dialpad credentials work" is true and irrelevant at the same time: the public API v2 does not expose ivr_menu_script, the media library, or the SMS auto-reply, and the internal endpoint needs a session, not a key. Anyone testing with the key alone will conclude the tooling is fine.

SECOND DEAD END: data/dialpad/chrome_profile is EMPTY (total 8, only . and ..), so there is no persistent session to launch either. The crawler's own docstring says Google SSO blocks Playwright automation ("This browser or app may not be secure"), and login_interactive() therefore shells out to a REAL Chrome window for a human to sign in - which cannot work on a headless server.

CONSEQUENCE: nothing in the fleet can read or write the Dialpad office configuration - IVR menu script, media library, business hours, auto-reply - and has not been able to since 2026-06-14. That is why the wrong walk-in hours survived on the phone for weeks after the website was corrected.

FIX, in progress 2026-09-18: the owner agreed to supply a Dialpad login once. ~/bin/dialpad-login.py (staged, syntax-checked) signs in headlessly at dialpad.com/login with the account's own Dialpad password into the persistent profile, so the crawler and dialpad_ivr_admin.py work again afterwards. Credentials are read from a file outside the repo and are never printed. RISK, stated honestly: if the account is Google-SSO-only there is no Dialpad password to use and this route fails; the script reports "NO PASSWORD FIELD" and says so rather than guessing.

WHAT MUST NOT BE "FIXED" WHILE IN HERE: Dialpad's office business hours (mon-thu 00:00-01:00 and 09:30-23:55, fri 09:30-18:00, sat 21:00-23:55, sun 00:00-01:00 and 09:30-23:55) are PHONE hours, not walk-in hours, and are deliberate - see L1983.
