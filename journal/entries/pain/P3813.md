## P3813 — The journal has 73 colliding entry ids across two harness-config lineages, so an id does not identify one entry

# The journal has 73 colliding entry ids across two lineages, measured 2026-10-20 - my memory is not one record

Found while testing whether `harness-config`'s remotes can be reconciled (ledger item 643). They cannot, and the
reason is worse than a merge chore.

## Measured, with the commands
```
git -C harness-config fetch --all
git diff --name-status origin/main offsite/main -- journal/entries/ -> M (collisions) 0 A 0 D 689
git diff --name-status origin/main mirror/main -- journal/entries/ -> M (collisions) 73 A 203 D 312
git merge --no-commit mirror/main -> "Merge conflict in journal/entries/decisions/D3034.md" ... 80 conflicts
```

- **`offsite` (the GitHub backup) is a strict ancestor in entries**: it holds nothing we lack, and it is missing
 689 entries. Its merge conflicts (6) are generated journal indexes plus one real content conflict in
 `presets/zabz/skills/fast-search/SKILL.md`. That one is reconcilable.
- **`mirror` (linux-pc) is a fork, not a lag.** 203 entries exist only there, 312 only here, and **73 entry ids
 exist on both sides with different content**. `D3034`, `D3035`, `H3443` and seventy others each name two
 different documents depending on which lineage you read.

## Why this is the serious one
The journal is the only continuity this system has: every session starts blank and the tree is the self. An
append-only record whose ids are not unique is not an append-only record - "D3034" is not a fact, it is a
question about which machine you are on. It also means `journal.py check` passing on this machine says nothing
about whether the id it prints resolves to the same entry anywhere else.

The cause is structural: ids are allocated from a per-checkout maximum (`index/entries.tsv` is a cache that
rebuilds from the tree), so two machines that each added entries without seeing the other allocate the same
next id. Nothing detects it, because the conflict only surfaces when the two histories are compared - which
nobody does, because the remotes have been diverged for weeks.

## What NOT to do
- Do not force-push either remote. The mirror's 203 entries exist nowhere else.
- Do not resolve the 73 collisions by taking one side: that destroys one of two different documents under each
 id, which is precisely the data loss this estate has suffered from before.
- Do not run `journal.py import-legacy` or `check` and treat a clean result as evidence about the other lineage.

## What a fix looks like
Reconciliation needs a rename pass: pick the older id as the keeper by file mtime and content, renumber the
other with `--alias-of`, record the mapping, then merge. That is a human-reviewed operation on the shared record,
not a drive-by merge, and it belongs with item 643. Until it happens, **a citation of a journal id is only
guaranteed to resolve on the machine that wrote it** - which is worth knowing before quoting one as evidence.
