## P3000 — E4610s vanish from ADB during the finalize bloatware phase, and the receipt blames 26 packages that were never actually asked

# E4610 handsets vanish from ADB during the finalize bloatware phase, and the receipt blames packages that were never actually asked

Twice now, on two different units, the finalize has died in the same place:

- **2026-09-18, serial 615291677** — recorded in `docs/deployment/PREFILTERED-DEVICE-AND-E4610-MANUAL-STEPS-RUNBOOK.md` §4: "the handset dropped off USB during the finalize's `bloatware` phase and was handed to the customer before the tail ran". `ready-e4610.ps1` was later written to fail closed on exactly this.
- **2026-10-08, serial 616468703** — bloatware phase reported **26 packages "Failed to disable"**, then `launcher` failed on `pm enable jp.kyocera.kyocerahome` and `verify` on `getprop ro.product.model`, both with `adb.exe: device '616468703' not found`. Receipt `success: false`, `sellable_release: false`. After the run, Windows had **no Kyocera device on the USB bus at all** (only a Logitech composite receiver, VID_046D); `adb devices` empty.

**Why this is worse than it looks:** the receipt's failure text says 26 named packages "failed to disable",
which reads like a package-manager refusal. In fact the device was already gone and every subsequent shell
call failed. A future reader (me included) would chase the wrong thing — the config list — instead of the
USB path. The correct model is three distinct outcomes: *disabled*, *refused*, *device gone*.

**What would fix it, in order of value:**

1. **Distinguish "device gone" from "package refused"** in the bloatware phase, and abort the phase with that
 reason instead of accumulating phantom failures. `DeviceConnectionError` already carries the difference —
 the phase just folds it into the generic failure list.
2. **A liveness probe between disables** (`pm list packages -d` or `get-state` after each package, cheap on
 ADB) so the last package before the drop is named. That is the only way to find out whether a specific
 disable kills USB on this platform — a real possibility given the list contains `com.verizon.mdm.xvlte`,
 `jp.kyocera.vzwextension.service` and a run of `com.qualcomm.qti.*` packages, and given that a *fresh*
 unit is the case where all of them are still enabled (on units previously filtered, the phase has almost
 nothing to do and never drops).
3. **Make resume safe and obvious**: re-running finalize is idempotent, and the phone is left unlocked when
 the drop happens before the `security` phase — so recovery is "replug, re-run", and the runbook should say
 that instead of leaving the operator to guess.

Also worth knowing at the bench: the micro-USB port on these handsets is a known weak point (the 2026-10-08
unit was not on the bus at all), so "replug and watch `adb devices`" is the first move, and only if it drops
again is it a platform/package problem.

Evidence: the receipt `cli/logs/deployments/deployment-receipt-616468703-20261008-211831.yaml`; the runbook's
615291677 case; `Get-PnpDevice -PresentOnly` output with no VID_0482 present; the finalize log
`logs/finalize-616468703-20261008-171525.log`.
