## A concurrent session's mojibake rewrite of journal.py silently corrupted any entry written during that window

**Measured 2026-09-15 23:11-23:31Z on ZABZ-YOGA.**

`journal.py check` reported **1,065 errors**, every one of the class *"heading does not match the
`<kind>` heading form"*, against a tree that had reported **0 errors 28 minutes earlier**.

**Cause, from `git diff journal/tools/journal.py` on the working tree:** another session had rewrote
the file with a UTF-8-decoded-as-latin-1 round trip, so every U+00B7 MIDDLE DOT in it became the two
characters `Â·` — inside the **heading regexes themselves**. The regexes then expected `Â·` while every
entry on disk contains `·`, so **no heading in the corpus could match** and the checker failed
everywhere. The 1,065 errors were all false; the entries were fine.

**The damage was real but narrow, and it landed on the entry I wrote at that moment.** I ran
`journal.py append decisions` while the broken version was live, so **D194's heading was written with
mojibake** — the only genuinely corrupted entry in the tree. `check` then reported it as its single
error once the other session reverted their file. Repaired in three steps, each verified:

1. heading `Â·` -> `·`;
2. footer sha re-recorded. **The hash was not guessed:** the file's recorded `sha=13e64b8b34e7781e`
 was reproduced exactly by `entry_hash(<old heading>, <body>)` and by nothing else, which proved the
 footer hashes *heading AND body* (`journal.py:284-296`), not the body alone as its name suggests;
3. CRLF -> LF, because a Python `write_text` on Windows silently converted every newline and
 `check` correctly refused it (`every journal write is LF`).

`check` is back to **0 errors** and `show D194` prints a correct heading.

**What would fix it properly — two guards, both cheap:**
- `journal.py append` should **refuse to write a heading containing U+00C2 or U+FFFD**, and say so.
 A writer that emits mojibake should fail loudly rather than corrupt the record silently.
- the heading-form check should distinguish "this heading is malformed" from "EVERY heading is
 malformed", because the second shape is almost always a broken checker and not a broken corpus.
 1,065 errors matching one regex looked like data loss and was not; the tempting wrong response —
 editing 1,065 healthy entries — would have destroyed the record.

**The general rule, which is the expensive part:** an alarming check result is a claim about the
world that needs the same verification as any other. I nearly fixed the corpus instead of the tool.
The tell was that the *count* was implausible and the *class* was uniform.
