WHY IT MATTERS, concretely. Today I registered an await for Moshe Mintz (+17328647786,
WO2609010004 - a disposal notice that expires 2026-10-26). With no dispatcher that await is
**inert**: his reply would be filed and never released, and the case would be scrapped on a timer
with nobody reading the answer. More generally the project loop, the flag store, and every
"wake me when X replies" built since 2026-09-18 stopped at once - and a stopped heartbeat reads
exactly like a quiet queue, which is the failure the skill warns about in its own first line.

WHAT WOULD FIX IT. Port the loop to `secratary-cloud` as **systemd timers** (the 139 port already
chose systemd/timers over cron for node-local work): `run-wake-sources.sh`, `wake-fanout.sh`,
`wake-dispatch.sh`, `wake.py`, plus the heartbeat writer. Port the **dispatcher and sources**, which
are engineering. Two things are NOT pure engineering and must not be smuggled in:
1. `sms-responder.py --send` texts customers from the cloud with no human in the path - that is an
 outbound-comms decision, not a port.
2. The prompt-transfer path to `zabz-tech-ts` was **already failing on the cloud before the cutover**
 (the 06:39 release never started a session), so a port that copies the dispatch script will
 reproduce a loop that claims releases and starts nothing. Fix it and prove one real session
