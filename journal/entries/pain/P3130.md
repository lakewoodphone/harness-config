## P3130 — The graceful HA stop was dead code - every Shabbat power-down hard-cut HA and lost the recorder flush

**P — the graceful HA stop was dead code, so every Shabbat power-down hard-cut
HA and lost the recorder flush. FIXED 2026-10-09, pending one production run.**

## The hurt

`app/services/home_assistant.py` `shutdown()` treated "the stop service returned
`ok`" as the only success. On this install `homeassistant.stop` returns **504
Gateway Timeout while Home Assistant is genuinely going down** — measured
19:16:56Z, where the very next call to the same host was connection-refused. So:

- `shutdown()` returned `ok: False` on every Shabbat,
- the orchestrator logged *"the plug cut will be a HARD power cut; the recorder
 DB is not flushed"*, and
- the plug cut power immediately after.

The module's own comment at line ~387 already recorded it: *"this graceful step
had never once worked — HA was hard-cut whenever the Shabbat plug opened."*
Known, written down, and not fixed for weeks.

## Why it became urgent today

The owner asked for the ceiling light to be held ON across Shabbat. That works by
**persisting the light's state across the HA reboot** — which is exactly the
write an unflushed recorder loses. A cosmetic-sounding defect turned into the
thing standing between the owner and the behaviour he asked for.

## The fix (deployed 2026-10-09 19:15Z)

`shutdown()` dispatches the stop, then polls up to
`shabbat_ha_shutdown_settle_sec` (45 s) for the connection to drop, and accepts a
stop whose HTTP reply was lost to a gateway timeout — naming the basis
`detected_unreachable`. The poll is gated on having **dispatched** a stop, not on
one being **accepted**; see lesson L3469, because gating on `accepted` made the
recovery branch unreachable in precisely the 504 case.

## What is still unproven

The fix is tested (5 new tests, Shabbat suite 59 passed) but has not yet run in
production: today's power-down had already fired when it was committed. The
**next real run is Fri 2026-10-16 13:15 EDT**. Success looks like a
`ha_shutdown` step with `confirmed_down: true` and no "HARD power cut" error in
`journalctl -u secretary-api.service`.

## What would have caught it sooner

An assertion that the power-down result reports `confirmed_down` — i.e. test the
*outcome the automation claims*, not just that the steps ran. Every existing test
mocked `shutdown()` to return `{"ok": True}`, which is the one shape production
never produces.
