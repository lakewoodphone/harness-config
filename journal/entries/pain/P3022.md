## P3022 — The always-read in-flight page silently reverted six days; the update was uncommitted and a third session's write was rejected

The journal's always-read page, `journal/state/in-flight.md`, silently went six days backwards on
2026-10-11 and nobody would have noticed except by comparing two reads of the same file.

**What was measured.** At ~22:35Z a session read it and got *"Updated: 2026-10-11 20:30Z (ZABZ-TECH,
Dialpad-after-the-cloud-move session — H3497)"*, 327 lines, carrying the cloud-cutover state. Twenty
minutes later the same file read *"Updated: 2026-10-05 21:5xZ (ZABZ-TECH, Weinberg settlement session —
H3215)"*, 288 lines — and `git status` showed it **clean against HEAD**, i.e. HEAD already held the old
version. The H3497 update had sat uncommitted in the working tree and was replaced by a checkout/restore
from git (the tree also carries a `RECOVERY: restore 1,841 paths deleted by the broken merge` commit,
same family). A third session's edit attempt was rejected with *"file changed since it was read"*, so
at least three sessions were touching the same file inside half an hour.

**Why it matters.** `in-flight.md` is the one document every session is told to read first and the one
the harness rewrites. A page that can silently revert to six-day-old state is worse than a stale page,
because the session that wrote the update believes it published, and the next session reads an old
world with no indication that anything is missing. The content itself was not lost — H3497 still exists
as a journal entry, because handoffs are one-file-per-entry and append-only — but the layer that is
supposed to summarise them was.

**What would fix it.** (1) When a session rewrites a state file, **commit it in the same turn** — an
uncommitted state rewrite is a rewrite waiting to be reverted by any restore. (2) Have the journal
**reject or warn** on an `in-flight.md` whose `Updated:` line is older than the newest handoff entry,
so a revert is detected by the tool rather than by a session happening to read the page twice. (3) One
writer per state file, or a lock the same way `append` already takes one — the lock is what made the
entry tier safe here, and the state tier does not have it.

Recorded rather than fixed by me on 2026-10-11: another session held the file, a third write risked
clobbering whatever it publishes next, and my own state was already durable in H3532.
