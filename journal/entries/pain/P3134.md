## P3134 — An unreachable-but-listed node costs ~4 s on every cold mesh placement

WHAT HURTS: `lakewooechsmini` (Yisroel's Mac) is in the broker roster but cannot be read from the
broker's host, so every COLD placement pays its 4,000 ms hard wall-clock deadline. Measured
2026-10-12: broker `POST /place` 6,768 ms cold against 856-1,211 ms warm; `/healthz` 747-896 ms warm.
The whole difference is one node that cannot answer.

WHY IT IS STUBBORN: the machine is not actually down. `tailscale status` says `offline, last seen 4m
ago`, ssh to it times out at 12.4 s (exit 255) — and yet its gate answers `GET /mesh/capacity` with a
LIVE document (`at: 2026-10-12T03:24:02Z`, load1 1.45, freeMiB 7059) to a device its allow-list knows.
Its own `phone-gate-allow.txt` does not list the authority, so the broker (on the authority) gets 403
or a timeout while the laptop gets a fresh reading.

WHAT WOULD FIX IT, in order of preference:
1. one line in that machine's `phone-gate-allow.txt` (needs shell access; ssh currently times out);
2. a broker-side fast-fail/backoff for a node whose last N reads failed, so a node that is off costs
 ~600 ms instead of 4,000 ms on the first attempt and is retried at full budget on a schedule.
 NOT DONE — `packages/mesh-broker/lib/broker.js` is 64 KB of scoring/lease logic and a change there
 needs its own tests, not a post-migration audit;
3. remove the row while the machine is unreachable — rejected, because that is how real capacity gets
 silently forgotten (journal W209 is the precedent).

A second, smaller pain in the same area: `POST /done` costs 1,391-1,618 ms of ssh per child, so a
fan-out of N children pays N extra hops just to release leases.
