**The running `company-api` imports these files. `origin/master` does not contain them.** The repository
is not a description of the system: a deploy from `origin/master` today would silently revert 6,160 lines
of live behaviour, and **no clone of the repository can reproduce what is currently serving customers.**

**How I found it.** I was verifying that *this* session's work was durable - `git status` on every repo
holding something running. Four of my own deliverables were committed and pushed; someone else's 56 files
were not, and were not mentioned in any of the four master records written the night before.

**What I did, and what I refused to do.**

* **Preserved, not laundered.** The full drift is committed on branch
 **`preserve/uncommitted-20261012-unreviewed`** (commit `42109f4a`, pushed to origin). The branch message
 states plainly that it is unreviewed, must not be merged without a reviewer confirming each hunk, and
 was not written by the session that preserved it.
* **`master` left alone.** The running tree and `master` were returned to a clean, matching state, so
 nothing about production history was rewritten and no unknown change was laundered into the trunk as
 if it had been reviewed.
* **Not reviewed, and said so.** I read the three smallest diffs properly (`agent_bus.py` - the Shabbat
 plug program becomes a 15-minute poll inside a 3-hour window because the single daily attempt failed on
 a ConnectTimeout 3 mornings in 7; `autopilot.py` - owner briefings go through `fit_for_transport()`
 instead of a bare slice whose own ellipsis is outside GSM-7 and halved the budget it was respecting).
 **I did not read 6,160 lines**, and the record must not imply I did.

**Also established: the service is not editing itself right now.** Two `git status` samples 45 seconds
apart produced identical hashes, and no self-edit process is running. The drift is *frozen work never
committed*, not live churn. That distinction matters because it means the fix is a review-and-commit
exercise, not a race against a moving target.

**The rule this produces, and it belongs in `AGENTS.md` next to the one-writer rule.** *A repository is
not the source of truth until it has been diffed against what is running.* The estate already has this
lesson in code form - the 599 tool bodies that were gitignored (`172`) and the 89 uncommitted lines in
`find-anything` (`L3743`) - and it has now recurred at **56 files** in the production application itself.
**The check is one command per host: `git status` on every repo that holds something running, and it
should be routine rather than a lucky find during an unrelated verification.**
