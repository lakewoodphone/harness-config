## P180 — The tree-level guard test has two blind spots: an allowlisted WRITE looks like a read, and publicProcedure is counted as guarded

1. guard-coverage.test.ts cannot see that an allowlisted PUBLIC procedure is a WRITE. PUBLIC is a bare
 map of name -> reason string with no read/write field, and the scanner compares NAMES ONLY, never bodies.
 faq.incrementView is allowlisted with the reason "the audit records this as an unauthenticated write" -
 the write is acknowledged in prose and invisible to the assertion. Would fix: give each entry an explicit
 read|write classification and fail when a WRITE is listed without one.
2. guard-coverage.test.ts cannot see publicProcedure. BARE = /...:\s*procedure(?!...)/ matches only the
 literal token; GUARDED matches 'publicProcedure'; and publicProcedure === procedure (context.ts:620). So
 `x: publicProcedure.query(...)` is an unauthenticated declaration that satisfies GUARDED and fails
 nothing. Would fix: add publicProcedure to the BARE alternation, or delete publicProcedure outright - it
 is declared 0 times in router files, so it is an alias with no users and deleting it is strictly better.
3. Both are the same class as the defect the file was written to catch: a declaration-level property with no
 assertion. A guard test that can be satisfied by a rename is a naming convention, not a control.
