## P2932 — A queue/task status write through the app dies at 30 s and fails silently, while the same write succeeds on retry a minute later

## P2932 — A queue or task status write through the app dies at 30 s, so an agent's follow-through fails silently while the same write succeeds a minute later

Measured 2026-10-09 15:1xZ, recording the Weinberg payment. Two sanctioned writers failed on the same rows for the same reason:

- `python3 ~/bin/owner-queue.py resolve 162 …` — hung past 60 s (backgrounded, then killed).
- the MCP `ps_task_update` path — `timed out after 30s`, twice.
- A direct `sqlite3` connection with `PRAGMA busy_timeout` proved why: `BEGIN IMMEDIATE` → `OperationalError: database is locked` after a 5 s timeout, on a **23 GB** `secretary.db` with seven live python FDs on it.
- The same five statements, retried a few minutes later through a plain `sqlite3.connect(timeout=180)` loop, all succeeded **on the first attempt**.

**Why it matters more than the lock itself (P2127 names the cause, this is the symptom):** the failure is *fast and silent to the caller*. A session that trusts the tool's error and moves on leaves the owner queue asking him to pay a bill he has already paid, and a task showing `in_progress` for work that finished — the two records a later session reasons from. I only caught it because I read the rows back; the tool had told me nothing about whether anything was written.

**What would fix it:** the app's write paths (and the CLI wrappers) should retry a locked write on a bounded backoff before reporting failure, and should report *which* statement failed — never a bare timeout. Cheap interim discipline, which worked: **after any status write, read the row back; if the tool timed out, retry the exact statement with a 180 s busy timeout before believing it.**
