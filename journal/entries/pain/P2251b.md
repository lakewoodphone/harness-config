## P2251b — The project loop wakes a session every day and integrates nothing: 32 commits of finished website work sit unmerged while every release counts as done when the session exits 0

Measured 2026-09-23 on the authority, after the owner asked "isn't the system supposed to reactivate you
to work on it every day?"

WHAT HURTS: the autonomous project loop DOES wake a session per project per day (wake #26, website,
1426 s, exit 0 at 00:58Z today), and **none of that daily work reaches the site.** Each shift ends with a
pushed branch plus a line in `/home/zabz/.wake-projects/<project>.json` saying "the next worker must merge
this" - and nothing merges it. Live inventory of website work built and unmerged right now:

 origin/project-keepalive/lpt-truthful-20260922 4 commits (hours/FAQ/absolute Google link, in source)
 origin/integration/lpt-20260916 28 commits (customer-login allowlist fix, systemLog guard)
 origin/fix/holiday-closure-notice (the closure work, hot-deployed to prod from a worktree)

`origin/test` has meanwhile moved 69 commits past the oldest of them, so every day of "progress" makes the
merge harder. The loop converts time into unmerged branches.

WHY IT PERSISTS: the flags ARE released and the shifts DO run - the wake system's own metrics look
healthy (`released_today: 4`, `failed_today: 0`), so nothing alarms. There is no completion signal for
"the work actually shipped", only for "a session ran". A release is counted as done when the session
exits 0, whatever it left behind.

THE SECOND HALF, which made me give the owner a wrong answer an hour earlier: **the loop's state is
invisible to the journal.** The shift writes `/home/zabz/.wake-projects/<project>.json` and the dispatch
log; a human session reading `journal.py status`/`search` sees a silent project and concludes it stalled.
The one page every session reads does not know the loop exists.

WHAT WOULD FIX IT, in the order I would do it:
1. Make **"merged to test, or a named blocker"** part of a project shift's definition of done - a shift
 that ends with a pushed branch must either merge it or record the exact gate that stops it, and the
 project's state file's first line must be that verdict, not a list of unmerged branches.
2. Surface the loop in the always-read path: `journal.py status` should print one line per project -
 last shift, branch left unmerged, flags waiting - so no session can mistake autonomy for silence.
 (Partially done today: the `secretary-wake` skill now says where the state lives.)
3. Count integration, not releases, in the digest: "4 releases today, 0 of 3 unmerged branches landed"
 is the honest scoreboard for a loop whose output is branches.

COST: unknown and unmeasured - `dsh --profile headless` reports no usage (wake-dispatch logs
`cost=none`), so 4 releases/day has no dollar figure attached to it. Stated, not estimated.

NOT A REASON TO STOP THE LOOP: the shifts are producing real, correct work (the FAQ/Google-link/hours fix
is good and is on a branch as of this morning). The failure is purely that nobody integrates. The fix is
an integration step, not fewer wakes.
