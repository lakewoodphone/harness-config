## P9870 — No sanctioned path records a CASH payment, so a settled cash order cannot carry a total

There is no sanctioned path to record a CASH payment against a work order, and that leaves order 2817 permanently unable to carry its price.

Measured 2026-10-22. Order 2817 (WO26082712678, Binyamin Kaufman) settled at 117.29. The only payment row for it is `payment_transactions` id 3236 in the RETIRED app store: 117.29, SUCCEEDED, metadata {"offlineMethod": "CASH"}, stripeChargeId null, description "Offline payment". The operational store - the only store the counter reads, and the only one with a writer - has no payment row for it at all, so `collected` there is 0.

Consequence: its total cannot be set. Every screen sums payments by orderId (note 4538 states this in the app's own words), so setting total 117.29 with collected 0 would show 117.29 owed on money that was collected in September. Its current state (total null, note 3976 recording the settlement) is the least wrong one available.

Why the tools cannot fix it:
 - `lpt-record-payment` REQUIRES `--stripe-charge ch_...`; there is no cash mode.
 - `lpt-write payment set` only writes orders."paymentStatus" and by design never touches payment_transactions.
 - `lpt-link-payment` links an EXISTING row; there is no row in the live store to link.
 - raw SQL is refused by the one-writer rule (app.services.website_db).

The fix is a code change to lpt-record-payment: an `--offline-method CASH|ZELLE|CHECK` mode that writes the same row with metadata.provenance naming the source (store, payment id, date) instead of a Stripe id. Until then, every cash job recorded in the old store is stuck the same way.

Second half of the same pain, measured the same day: `lpt-pay-notice preview` REFUSES the price gate on a null total ("No price recorded - set the final price before this device can be released"). A settled-by-cash order therefore blocks its own handout, and there is nothing to set the price with.
