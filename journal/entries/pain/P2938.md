## P2938 — I printed live credential values into the session transcript with a name-pattern-masked env diff

I LEAKED CREDENTIAL VALUES INTO MY OWN SESSION TRANSCRIPT and it must not happen again.

What I did. To diff the office and cloud `.env` files BY KEY ONLY, I wrote a helper whose value-mask was a case pattern over key names: `*_PATH|*_DIR|*_FILE|*_JSON|*_URL|*_DB|*_DATABASE|AH_*|HA_*|GOOGLE_*|MEM0_*|FLEET_*|QB_*|AI_GATEWAY_*`. The intent was that only paths would print. But `*_FILE`, `*_URL`, `*_DB`, `GOOGLE_*`, `HA_*`, `FLEET_*`, `QB_*`, `AI_GATEWAY_*`, `MEM0_*` are broad enough to select `*_API_KEY`, `*_TOKEN`, `*_SECRET`, `*_PASSWORD` and a full `postgres://user:password@host` DSN. It printed them, from `/opt/company/.env` on the cloud box, straight into the session transcript.

Why it matters. The transcript is archived forever by our own standing rule (AGENTS.md §1), and DSH session archive is a training corpus. A card number in a training corpus is not recoverable. I did not merely fail to redact; my tool's whole purpose was to avoid printing values and it printed the most sensitive ones.

Why the guard failed. A name-based allow-list on a 300-key `.env` is not a redaction mechanism. `*_DIR` is safe; `*_DB` is not; `GOOGLE_*` is not. The pattern was wide because I wanted recall, and I priced the risk at zero.

THE RULE. Never select env keys by a broad name family when printing values. Select by an ALLOW-LIST of exact key names, or by a strict suffix set that a secret cannot match (`_PATH`, `_DIR`, `_ROOT`, `_REPO_PATH`, `_TOKENS_DIR`, `_STORE_DIR`), and then ASSERT on the shape of the value before printing it: a path starts with `/` or `~/` or `data/` and contains no `://` and no `@` and is under 200 chars. If a value fails the shape assert, print `<withheld>` and its length, never the value. Belt and braces, because the allow-list is the part that failed here.

Numbers: the leak was live API keys for several providers and at least one database DSN with an inline password. Office box clean: this was all from the cloud box's `/opt/company/.env`, which is mode 600 and root-owned, and I read it as root.

Follow-through: rotation of the affected keys is the owner's call and is not something I can do from here. Recorded in `docs/mesh/136-ESTATE-INVENTORY.md` §1 and §5 so it cannot be lost with this session.
