## P175 — Chumash Timeline signed-in features are dead in production and the failure is self-concealing

## P — The Chumash Timeline's signed-in features are dead in production, and nothing noticed

**What hurts.** `https://chumash.lakewoodphoneandtech.com` advertises "Sign in to vote, rate, and
comment" on every page. **No user can sign in, and never could.** Clicking Sign in issues a 307 to
`https://lakewoodphoneandtech.com/api/auth/google/start`, which returns **404** with the body "This
deployment does not serve or proxy /api … A relative /api request is therefore a bug" — the base URL
points at the Vite frontend host rather than the API host. Compounding it, the app presents the *test*
backend's shared secret while the live identity provider expects a different one, so even with the
right host every assertion would be rejected with 403.

**Why it is worse than a bug.** The failure is *silent and self-concealing*. The app renders the 403
as `?oauth=error&code=assert_failed` and the API answers `401` for signed-in endpoints — which is
exactly what a signed-out user looks like. So the login path has been broken for the entire life of
the deployment with no error, no alert, and no log line that a person would see. The container logs
no request lines at all, which means **an empty log is not evidence of health here — it is a
refusal.** The one signal that existed (a 403 from the identity provider) was indistinguishable from
normal unauthenticated use.

**What would fix it permanently.**
1. **A deploy-time configuration check that fails loudly**: on boot, probe the SSO base URL and the
 assertion endpoint; if unreachable or 403, refuse to advertise sign-in and log a single
 unmistakable line. A config mistake must not be able to look like "no one is signed in".
2. **Per-app credentials instead of one shared secret** — the estate has one secret for every app, so
 no app can be revoked individually and a rotation at the provider silently orphans whichever
 consumer nobody remembered. This is the same class as the secret baked into the image: the source
 of truth is a file, so nothing enforces propagation.
3. **A synthetic sign-in check** in whatever monitoring exists, because this is a user-facing revenue
 path (community feedback) that has never once worked.

**Ranked alongside.** This sits below the wrong-parsha and wrong-gematria defects in *frequency* but
above them in *character*: those show a wrong number, this shows nothing at all and says so
confidently. A product that silently disables a feature it advertises is worse than one that shows a
wrong figure, because there is no evidence to find.
