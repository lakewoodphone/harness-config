## P2942 — The frontend deploy check fails intermittently on a bundle sha256 and blocks every promotion to main while red

**P2994 · 2026-10-12 · The frontend deploy verification fails intermittently on the bundle sha256 check, and because it is a REQUIRED check it blocks a promotion to main while it is red.**

**Symptom.** `Deploy frontend + verify` ends in `VERIFICATION FAILED` on `check 4`:

```
 check 4 : FAIL - index-DgwD5xNF.js
 live sha256 6e64da1f… (8055 bytes)
 build sha256 b91f8773… (3851374 bytes)
 byte lengths differ: the host is serving a DIFFERENT artifact.
```

**It is not the deploy.** Checks 1, 2, 3 and 5 pass in the same run: the entry asset changed, the live
backend reports the required commit, the live bundle is stamped with that commit, and there are no 22P02
errors. Fetched by hand seconds later, `https://test.lakewoodphoneandtech.com/assets/index-DgwD5xNF.js`
is the **full 3,851,374 bytes** — the exact build length check 4 said was missing. 8,055 bytes is the size
of the SPA shell, so the edge answered an asset request with `index.html`.

**Measured today on both deploys:** it failed on the test deploy (`38285675719`, 2026-10-12) and again on
the **production** deploy (`38288966283`), and **both succeeded on attempt 2** with no change.

**Why it costs more than a re-run.** "Deploy frontend + verify" is one of the four required status checks
on a promotion PR, so while it is red the promotion to `main` is refused outright
(`405: 4 of 4 required status checks have not expected`). Promoting a tested change to production
therefore costs an extra re-run and a wait every time, and the failure reads like a broken deploy to
anyone who does not open the log — which is the same class of harm as a false alarm that teaches people
to ignore alarms.

**What would fix it, in order of cheapness.** (1) Treat a byte-length mismatch where the fetched body is
the SPA shell as a **propagation race** and retry for the same bounded window the script already uses for
the entry asset, rather than concluding "a DIFFERENT artifact" on one read. (2) Fetch the asset with a
cache-busting query or `Cache-Control: no-cache`. (3) At minimum, retry once on a transient mismatch and
print which read won. Whatever is chosen, the check's own message should stop asserting "the host is
serving a different artifact" from a single sample.

**Not diagnosed further here** — the fix belongs to whoever owns `scripts/verify-deployed-commit.mjs`.
The finding is recorded because it recurs every deploy and I chose the re-run over editing a verification
script during a payment-code promotion.
