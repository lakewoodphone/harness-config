## P2188 — secratary-ts ssh alias used a key not in secratary's authorized_keys; all mesh ssh to the authority failed

STATUS: fixed 2026-09-22 on ZABZ-YOGA, not yet verified from other hosts.

WHAT HURT: every 'ssh secratary-ts ...' from this laptop failed 'Permission denied (publickey)', including the documented way to read the owner decision queue (rule in the system prompt). The alias pinned IdentityFile ~/.ssh/id_rsa_linux_pc with IdentitiesOnly yes. That key (SHA256:ZZDZXXxZ9R80da0Z2tX3jvSsDZI+CgoLOR34gt1nZuE, comment server-to-linux-pc-repo-commands) is NOT in secratary's 4-line authorized_keys. The key that IS authorized is ~/.ssh/ha-mesh-key (SHA256:lP11vBJcO8IzYJHrVUE3ugeMbE5RAnwSiKtpN2v12Oo, zabz-tech-linux-mesh-2026-05-25).

FAILURE MODE: it looked like the machine was down or tailscale was broken. It was a wrong key. The alias had been wrong long enough that mesh access to the authority machine read as unreachable.

FIX APPLIED: ~/.ssh/config, secretary-ts/secratary-ts block now IdentityFile ~/.ssh/ha-mesh-key. Backup at ~/.ssh/config.bak-secretary-key-20260922-235758. Verified: 'ssh secratary-ts hostname' -> secratary; 'python3 ~/bin/owner-queue.py next' returns queue #128.

DELIBERATELY NOT DONE: id_rsa_linux_pc is still the key for desktop-ts, linux-pc-ts, mac-mini-ts, laptop-ts in the same file and I did not test or change those. Only the secratary-ts alias was touched.

REMAINING RISK: the same id_rsa_linux_pc may be unauthorized on other mesh targets too. laptop-ts and desktop-ts both answered post-quantum-KEX warnings without confirming a hostname. Worth a loop over all *-ts aliases from each host.

WOULD FULLY FIX: stop carrying per-host key pins that rot - let the mesh aliases offer ha-mesh-key plus the machine key, or push id_rsa_linux_pc.pub into secratary authorized_keys. Also this config is NOT in harness-config, so the fix does not propagate to the other machines; each host has its own ~/.ssh/config.
