## P2257 — The CEO asks the owner for data the company should fetch itself (GBP stats, Yelp inbox)

## What hurts

The CEO agent stalled on two questions it should have answered itself and turned
both into questions for him, which is how they entered the SMS queue that never
sends:

 * **Google Business Profile** -- three of the ten owner questions filed on
 2026-09-23 (`owner_message_queue` 1851, 1854, 1856) were the same ask in three
 wordings: "provide the current GBP rating / review count / new reviews /
 unanswered reviews". The agent said so itself: *"The web search tool is not
 returning the actual text of the results."* The last snapshot in the record is
 5.0 stars / 4 reviews, with no date.
 * **Yelp** -- `owner_message_queue` 1846: the agent cannot reach the Yelp Inbox,
 so a customer's tablet-support quote request became a question for the owner.

## Why it matters

He is the bottleneck for data the company can fetch. Every one of these becomes a
queue row he has to answer by hand, and a question with an obvious machine answer
is exactly the class that erodes his trust in the queue.

## What would fix it

1. A read path for the profile: the Google Business Profile API (Business Profile
 Performance / Reviews) on the `lakewoodphoneandtech` account, or, if that
 account is not API-eligible, a Places/SERP lookup keyed on the shop's place_id
 refreshed nightly into a table the CEO reads. Fixes all three rows at once.
2. A Yelp business route: Yelp for Business inbox access (or the shop's Yelp
 notification address) so a quote request is a work item, not a question.
3. Until then the CEO's prompt/action should route "I could not read X" to
 engineering, not to `ask_owner` -- the same fix as the routing leak that made
 these invisible in the first place.

## Evidence

`secretary.db`: `owner_message_queue` ids 1846, 1851, 1854, 1856, all `held`,
reason `ask_owner`, filed 2026-09-23 03:27-15:25 UTC; routed to
`owner_decision_queue` 150, 152, 153, 154 on 2026-09-23 23:3x UTC.
