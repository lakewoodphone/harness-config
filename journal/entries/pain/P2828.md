## P2828 — A check whose arithmetic is wrong reports a confident falsehood -- MAX() over a column two writers fill with different date formats

# P — a check whose arithmetic is wrong reports a confident falsehood

**Measured 2026-10-02, on the authority, in a check I had just written and already
reported to the owner.**

`text-ledger-audit.py`'s D1 exists to compare the owner's inbound texts in the channel
store (`~/.sms-inbox/inbox.db`) with the app's copy (`secretary.db.sms_log`). Its first
working version used SQL `MAX()` on `messages.date_sent` — and reported:

 store newest 2026-03-25 · app newest 2026-10-02 · the store is 4590.3 h behind

I repeated that to the owner as the bigger of the day's two findings: **225 of his
messages parked, the store months behind, "every store-based report understates this
channel".**

It was false. `messages.date_sent` holds **two formats**:

 '2026-10-02T14:18:00.492540+00:00' -- written by sms-inbox.py (ISO, from the carrier)
 'Wed, 25 Mar 2026 08:01:06 +0000' -- written by mirror-owner-sms.py (RFC 2822)

`MAX()` over that column sorts the strings, and `'W' > '2'`, so the RFC-2822 March row
always wins. The true comparison, parsing each value and taking the maximum, is:

 store newest 2026-10-02T14:18+00:00 · app newest 2026-10-02T14:18+00:00 · gap 0.0 h

**Both stores hold the same newest message.** There is no live loss and the store is not
behind. What IS true, and smaller: 272 of the owner's inbound rows are in the store, and
225 app rows older than the mirror's 7-day window were never carried across — and of the
18 that would actually be inserted, the newest are **test messages from February**
(`'Hello there'`, `'Hey whatsapp'`, `'test_e2e_tunnel'`). So the backlog is mostly test
traffic, not the owner's real conversations, and the "parked backlog" is a far smaller
thing than I said.

**The rule, and it is the same rule as `P2827`, one layer down.** A check has two ways
to be wrong: it can fail to find data, or it can compute the wrong answer from data it
found. The first is silence, which reads as health. **The second is worse — it produces a
confident, precise, entirely false number, and precision is what makes it believed.**
`4590.3 h` looked like a measurement. It was an artifact of a string sort.

**What to do about it:**
- **Never `MAX()`/`MIN()` a timestamp column an unknown number of writers write.**
 Parse and compare, or normalise on write. Two writers in one column is the norm here
 (`sms-inbox.py` and `mirror-owner-sms.py` both write `messages`).
- **When a check reports a dramatic number, confirm it with a second, independent
 measurement before reporting it upward.** Here one `select` of the newest 5 rows by
 `date_sent DESC` would have shown October dates sitting right there.
- **State the second measurement in the check's own evidence** so the next reader does
 not have to reconstruct it: D1 now shows both timestamps side by side.

Evidence: `text-ledger-audit.py` (D1, fixed), the probe that caught it comparing parsed
maxima per store, and the correction recorded in the same session against the handoff
that had reported the false figure. See also `P2827` (LIKE matching nothing) — same day,
same check, same class.
