# The mesh fan-out of five children died in the transport hop, with a bare 4294967295

Measured 2026-10-14, ~11:59-12:09 UTC, from ZABZ-YOGA. Five `subagent` (mesh) children were launched
together for a read-only dossier job. **All five failed identically:**

 the remote one-shot exited 4294967295 and produced no final message
 ORPHANED - the child started and was NOT re-dispatched; its work may exist on the node and
 only its report was lost

`4294967295` is `0xFFFFFFFF` / `-1` — the remote one-shot's exit code, not a provider error message.

## What was established, and what was not

* **The children did start and did work.** The stderr tails show each one mid-reasoning ("let me
 check the REVISION.txt and case files dir, and run lpt doctor"), and two of them created their
 work subdirectories (`_w3_tmp`, `_w4_tmp`) before dying.
* **Nothing survived that was usable.** No dossiers file was produced by any of the five. So the
 fan-out cost ~10 minutes and produced zero artefacts other than those two empty temp dirs.
* **It is not a mesh-placement problem.** The broker placed all five on **ZABZ-YOGA itself**, from a
 pool of one eligible node, and pressure was OK (52.4 % committed). So the mesh had nowhere else to
 put them, and the local node was already where they ran.
* **`subagent_local` works.** A probe returned normally and fast. So the break is in the
 ssh-to-`laptop-ts` hop that the mesh transport uses to reach a node, **not** in the agent runtime.

## The trap this is, for the next session

`4294967295` from the mesh transport is **indistinguishable in shape from a store being down**: a
few minutes later a single plain `ssh secratary-cloud hostname` also returned `exit=0` fine, and an
earlier one-off `lpt` query returned `ssh exit 4294967295`. So this code can mean "the mesh transport
broke", "this particular ssh was refused under contention", or "a transient connection fault" — and
it will look the same. **A bare `4294967295` from ssh on Windows is a launch/termination fault, not
the remote command's own exit status.** Never read it as the remote program's verdict.

## What to do differently (the durable part)

**Do not have children reach the database themselves.** The failure mode disappears when the parent
fetches the evidence once and children analyse **files**: no ssh in the child, no per-child process
spray, far fewer tool calls, and every child's claim is checkable against the same bytes. On this job
the parent fetch of 91 work orders (`closeout/fetch_orders.py`) replaced what five children were
each trying to do over ssh, and it ran with 6 workers in about two minutes.

Serial cost, measured: **~14 s per work order** because `lpt ticket` deliberately asks **both**
stores and the `app` hop is 2-3 s. 91 orders serially is ~20 minutes of nothing. Six workers was the
number that finished it without tripping anything — one transient `ssh exit 4294967295` was seen
when a query raced the serial fetch, which is what set the worker count rather than a guess.

Also: **check for salvageable output before re-running a failed fleet.** Two children had written
directories; that is how I know they ran at all, and it is the difference between "the transport
dropped the report" and "the work never happened".
