**D2658 · 2026-09-28 · Contention fix plan: bound _get_conn's second acquire, give the health probe a dedicated connection, separate busy from broken, cap watchdog restarts.**

Ordered by certainty, each with its evidence.

1. BOUND THE ACQUIRE -- app/database.py:1060. _db_lock.acquire() with no timeout, under a comment
 claiming it does not hang forever. Bound it and raise on persistent failure. Smallest, highest
 certainty fix; removes the permanent worker leak.
2. DEDICATED PROBE CONNECTION -- the /health DB probe must stop calling _get_conn. A fresh
 short-lived read-only connection measured 0.2 ms on the same database while the shared-lock path
 timed out at 2000 ms. The probe must not share a lock with the work it inspects.
3. BUSY IS NOT BROKEN -- /health already returns 200 with a degraded marker; make that explicit
 (database.busy) and add a liveness endpoint that touches no database at all, for the watchdog to
 use. Liveness and depth are different questions.
4. WATCHDOG POLICY -- restart only on a real failure (process gone, port closed, explicit
 unhealthy), with a cooldown and a restart-rate cap. 13 starts today cost ~5 minutes of outage
 each because shutdown blocks on threads that cannot exit.
5. BOUND THE AUTOPILOT TICK -- it abandons a thread that 'cannot be killed' (4x today). Nothing on
 a timer may leave unbounded work behind.
6. SQLITE CONFIG -- busy_timeout, cache_size, mmap_size, WAL checkpoint sizing (measurement pending
 from the config audit).
7. MISSING INDEXES on the multi-hundred-thousand-row tables (measurement pending from the query
 audit).

VERIFICATION, not assertion: /home/zabz/_audit/contention-sampler.py samples read latency, health
verdict, WAL size and open-pid count every 5 s. Baseline measured 2026-09-28 16:53-16:57Z:
32 samples, read_ms p50 0.2 / p95 0.7 / max 1.0, health ok:false 4 times. The fix must move the
health-failure rate to zero under the same load, and the sampler is how that is judged.
