**D78 · 2026-09-14 · A control implemented on one storage backend is a control that disappears on the other.**

The consent gate and the parent's deletion right were built against the SQLite path. The Postgres parity audit failed and named exactly five missing methods — `record_phone_consent`, `list_phone_consents`, `has_active_disclosure_consent`, `delete_screenshot_reviews`, `purge_screenshot_reviews_older_than` — and it is right to insist: this product's whole privacy position rests on a gate, and a deployment that switched databases would have silently lost it while every SQLite test stayed green. All five now exist on both paths with dispatch entries, and the pinned parity counts moved 271→276 (with the reason written next to the pin, which is what that pin is for).
*Two smaller versions of the same lesson, both found by running the whole suite rather than my slice:* removing the review table from the archive-and-prune registry left `screenshot_review_retention_days` with **no consumer**, which the settings-usage audit flagged as dead configuration (deleted, with the reason recorded where the field was); and the storage SQL surface moved **334 → 341** dynamic call sites, all seven from the Postgres implementations — the count moves because the audit models a call to the `_execute*`/`_fetch*` helpers as a call site regardless of the literal it is handed, and the digest history now records each move with its reason.
