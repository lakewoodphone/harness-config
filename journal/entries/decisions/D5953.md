**D5953 · 2026-10-16 · The LPT deploy path moves to GitHub-hosted runners; every alternative barred by posture or measurement.**

**DECIDED 2026-10-16 by the dev seat, not the owner.** The LPT website's one deploy path moves from a
self-hosted GitHub runner on `secratary` to **GitHub-hosted runners (`ubuntu-24.04`)** with
credentials in **GitHub Actions secrets**. Branch `lpt/ci-github-hosted-runners-20261016`, PR #453.
Every alternative was measured, and two were barred by the estate's own rules - this is the record.

THE FAILURE THAT FORCED IT. `secratary` was frozen 2026-10-11 as the rollback anchor
(`settings/machines/host-posture.tsv`) and is now off the network (`ssh secratary` ->
`Connection timed out`). The runner `secratary-lpt` has been offline since run #91
(2026-10-15T15:14:39Z; `gh api .../actions/runners` -> status=offline, confirmed 2026-10-16), so
nothing merged to `test` could deploy. The credentials lived in ONE place - that box's
`/etc/lpt-deploy/env`. There was no second copy: searched the authority, the deploy target,
both desktops, the company `.env`, `authority.db`, and GitHub's own 13 secrets - no
`CLOUDFLARE_API_TOKEN` anywhere reachable.

THE ALTERNATIVES, AND WHY EACH WAS REJECTED - all measured, none assumed:

| option | measured verdict |
|---|---|
| runner back on `secratary` | the box is FROZEN by `host-posture.tsv` ("Do not start, stop, mask, unmask, enable, disable or restart anything on it") and is unreachable. This is the failure, not a fix. |
| runner on `lpt-apps-01` | **BARRED BY POSTURE**: `lpt-apps-01\|read-only\|... "Do NOT add load; service changes here need the owner"`, 14 containers at ~90% disk. It is also the deploy TARGET, so it looked attractive (the image build and the container run would co-locate). The rule decides, not the attraction. |
| runner on `secratary-cloud` | 4 cores / 15 GB, sole writer of `/root/authority.db` (30.5 GB), swap already 5451/8191 MB used (`free -m`). Both estate guidance and plain risk say no; it would also co-locate a deploy credential with the company database. |
| runner on `zabz-tech-linux` | unreachable (`ssh` -> Connection timed out), same as `secratary`. |
| poll-and-deploy daemon | the workflow's OWN named fallback ("it is what to reach for if the CI path is ever blocked"). Rejected because the CI path was never blocked - the RUNNER HOST was. A merge is an EVENT and GitHub delivers events natively; a daemon re-introduces a moving part to monitor and another always-on host dependency. |
| **GitHub-hosted runners** | **CHOSEN.** |

WHY GITHUB-HOSTED IS THE RIGHT ANSWER, MEASURED:
 * **It removes the class of failure, not the instance.** No estate host is needed at all, so no
 box can be frozen, repurposed or powered off and stop deploys.
 * **The cost is affordable and known**: a deploy is a median **12.6 minutes** (last 8 runs,
 8.7-17.9) and this repo deploys about 37 times a month -> about **465 of GitHub's 2,000 free
 private-repo minutes**. The runner was never the heavy part: `scripts/deploy-backend.sh`
 `scp`s a SOURCE tar and the TARGET builds the image (`docker build` runs over ssh).
 * **The credential store is already the repo's system of record** and already holds 13 secrets
 for this repo (AWS keys, `ENCRYPTION_KEY`, JWT secrets), so the old objection - "storing the
 token in GitHub makes every GitHub account with repo access a path to production" - was
 already inconsistent with the repo's own practice.
 * **It is verifiable by a session**, which the old path was not: `workflow_dispatch` plus a PAT
 with `repo,workflow` scope (already present at `/root/.git-credentials`) lets any session prove
 a deploy without waiting for a human or a box.

HARDENING THAT GOES BEYOND THE OLD DESIGN (this is a security improvement, not a relocation):
 * the deploy identity is a **dedicated CI key** (`id_lpt_ci_deploy`), not the operator's and not
 the shared `id_ed25519_hetzner`; it is installed on the target alone and is revocable on its own;
 * the Cloudflare token should be created **scoped to Pages:Edit** - the old one could also delete
 Pages deployments;
 * the host key is PINNED from a connection the authority had already made (`ssh-keygen -F
 2.28.33.58`), never taken from `ssh-keyscan`.

WHAT WAS DELIBERATELY NOT DONE:
 * `STRIPE_SECRET_KEY_PRODUCTION` is NOT in GitHub - a LIVE key. Moving it there is the owner's
 decision, not a side effect of fixing test, so a production deploy refuses at preflight and
 names it. Correct behaviour for an unattended production path.
 * the offline `secratary-lpt` registration is **left in place**. Nothing targets its labels any
 more (verified: only `deploy-env.yml` referenced `lpt-deploy`, and it is changed), so it costs
 nothing, and it preserves the rollback: powering `secratary` back on restores the old path.
 * `deploy/runner-provision.sh` is **marked SUPERSEDED with a banner, not deleted** - it is the
 rollback path, and a reader who found it first would otherwise recreate the exact coupling
 that broke.
