**D6212 · 2026-10-16 · An unanswered question comes back after 48 hours, once, then stops - the CFO's never-ask-twice predicate removed in both askers.**

Owner, 2026-10-16, on being told the CFO design never re-asks and an unanswered question is therefore dead: "why not, it can ask a day or 2 later."

THE RULE: an unanswered question comes back after the re-ask window, once, and then stops. 48 hours and two attempts total — one ask plus one retry.

WHERE THE OLD RULE LIVED, and it was one predicate. `next_question()` in `/root/bin/cfo-ask.py` built its suppression set with `WHERE sent = 1 OR ...`, with no clock on the `sent = 1` clause: a single sent question silenced that merchant for ever. Measured: 9 distinct merchants were suppressed that way, 3 of them by an ask older than 48 h that is still unanswered. The docstring stated it in words too — "NEVER THE SAME MERCHANT TWICE".

THE SECOND STOP ON THE SAME PATH, which would have made the fix a no-op: `cfo_clarify.open_cluster_keys()` returns every cluster with a clarification in state `asked`, and the selector skips those as "already have a question waiting". 7 were waiting, so expiring the ask rows alone changed nothing. Used the module's OWN `expire_stale(hours=48)` rather than a special case: 3 rows moved `asked` -> `expired`, waiting 7 -> 4. The relay now files new asks with `ttl = CFO_ASK_TTL_HOURS`, which is derived from the same window, so the two stops cannot drift.

THE MIRROR RULE, fixed because the same wrong thing was in a second place: `/root/bin/owner-ask.py::_cfo_asked_merchants()` read the CFO store with `WHERE sent=1` and no clock — the same permanent silence, seen from the other asker. Now bounded by `CFO_REASK_AFTER_HOURS` (same env var), 29 -> 4 merchants suppressed.

A DEFECT I INTRODUCED AND CAUGHT IN THE SAME SESSION: `owner-ask.py` already defines `REASK_AFTER_HOURS` = 24 h for its own retry ladder ("at most 1 retry, >=24 h later, then stop", WS6). My new line reused that name and shadowed it, which would have silently moved owner-ask's own ladder to 48 h. Renamed to `CFO_REASK_AFTER_HOURS` and verified by import: owner-ask's ladder reads 24.0, the mirror window reads 48.0. Caught because the import test printed both numbers rather than only the one I was changing.

THE NUMBERS, and why these: 48 h matches his words ("a day or 2 later"); the SHAPE (one ask, one retry, then stop) is copied from the ladder `owner-ask.py` has used since 2026-10-11 rather than invented, so the two askers now agree. Knobs: `CFO_ASK_REASK_HOURS`, `CFO_ASK_MAX_ASKS_PER_MERCHANT`. Caps unchanged: 3/day, 45-minute gap.

VERIFIED: with the 45-minute floor relaxed, `next_question()` now returns `pass` 135.33, asked 2026-10-14T03:01:25Z and unanswered, and `compose()` produces "135.33 at Pass on 1 Oct, card ending 2005. / Statement says: PASSNY TOLLBYMAI." NOT YET OBSERVED: the actual send. The floor blocks until ~15:59Z, so the 16:00Z tick is the first that can send it.

BACKUPS: `/root/bin/cfo-ask.py.bak-reask-20261016T151833Z`, `.bak-ladder2-20261016T152049Z`, `/root/bin/owner-ask.py.bak-reask-20261016T151945Z`, `.bak-shadowfix-20261016T152000Z`, `/root/crontab.bak-cfo-parked-20261016T151414Z`.

HONEST GAP: before expiring the 3 clarification rows I looked for the store path under the names PATH / DB / STORE / CLARIFY_DB / DB_PATH and found none, so NO file backup was taken. The change is the tool's own routine sweep — 15 rows had already reached `expired` the same way — and it is a state transition, not a deletion.
