**D5933 · 2026-10-13 · Joe Fishman now exists in production: customer 2873, order WO26101312746, total 1060 - and the two things deliberately NOT written.**

DECISION 2026-10-13 - Joe Fishman now exists in production, and the shape of the record chosen.
Written because this was a first-of-its-kind write through a brand-new code path and the next
session needs to know the numbers are deliberate rather than defaults.

WHAT WAS WRITTEN (all against `operational`, the only store lpt-write writes to), via the new
`customer create` / `order create` operations added the same day in lpt-ops a08ad44:
 customer 2873 Joe Fishman +13475346208 status ACTIVE
 order 3072 / WO26101312746 ticket 2709 READY_FOR_PICKUP total 1060
 notes 3171 GENERAL (full case state), 3172 BILLING (the payment-row gap)
 ledger seq 387, 388, 389, 390 read back via lpt ticket -> operational=FOUND app=absent

WHY total = 1060 AND WHY THAT IS NOT ARBITRARY. It is the one figure that makes the order
self-consistent with what has actually been paid. The deal is 900 on the recovered 2TB and 700 on
the failed 1TB, success-only, with a 160-per-drive deposit that IS CREDITED against the price. So
the customer is charged 900 for the 2TB work of which 160 was prepaid, plus the 160 retained on
the failed drive: 900 + 160 = 1060. He has paid 320, so the balance is 740 - which is exactly the
number the case file and the order note both carry. Setting total = 900 would have shown a 580
balance and understated what he owes; setting it to the 1600 that some records used to claim would
have been wrong twice over. 1060 is also the value the case file's front-matter `price:` already
carried, so nothing new was invented.

WHY status = READY_FOR_PICKUP. The work is finished and both drives plus the recovered data are
physically in the shop; nothing is being worked on. It is also one of the seven statuses the store
actually carries. NOTE, found by the build: the operational enum is AWAITING_DIAGNOSIS,
AWAITING_APPROVAL, AWAITING_PARTS, AWAITING_PAYMENT, READY_FOR_PICKUP, CANCELLED, UNFIXABLE - but
website_db.ORDER_STATUSES also offers CHECKED_IN, COMPLETED and IN_REPAIR, none of which the enum
has, and create_order's DEFAULT is CHECKED_IN. So create_order's default cannot be written to this
store at all and an explicit --status is mandatory. The new command checks both gates and refuses
with both sets printed.

DELIBERATELY NOT DONE, AND THIS IS THE PART TO NOT "FIX" LATER WITHOUT THINKING.
1. The 320 was NOT recorded as a payment. `lpt-write payment set` requires a Stripe charge id and
 verifies it against Stripe; this deposit has no such reference (it was taken 2026-09-17 as the
 per-drive deposit, not through Stripe that we can point at). Inventing a charge id to make the
 order look tidy would have been the wrong-data failure in its purest form. So production shows
 collected 0.00 while the shop holds 320, and note 3172 on the order says exactly that, in those
 words, so nobody reconciles it wrongly. If someone later finds the real reference, write the
 payment then.
2. The 12 historical communications rows were NOT attached to customer 2873. There is no lpt-write
 operation for re-linking communications, and doing it by raw SQL against production is not a
 move this estate makes casually. Named as an open gap rather than silently left.
