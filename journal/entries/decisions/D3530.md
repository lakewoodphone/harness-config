**D-c7 · 2026-10-14 · The wake ceiling is now derived from the balance (runway-aware), and the pause the guard could not clear is fixed.**

THE DIRECTIVE. The owner, 2026-10-14 ~23:47 UTC, refusing a request to top up prepaid AI credit,
verbatim: *"i won't keep rasing the money, it should learn to work within it's budget"*. That is an
instruction to change the software, not a refusal to decide. The company was STOPPED at that moment:
`/root/.sms-inbox/WAKE_PAUSED` existed, so `wake-fanout.sh:138` started nothing and `wake.py paused()`
refused every claim.

THE THREE DEFECTS, all confirmed by measurement on `secratary-cloud` before any change:

1. A ONE-WAY DOOR. Pause below `floor` 10.00; auto-resume required `floor + hysteresis` = 15.00
 (`wake-balance.py` args and the old `body.startswith(MARK) and bal >= floor + hysteresis` test).
 At a 7.84 balance it was a state nothing could leave without a human.
2. THE PAUSE FILE THE GUARD COULD NOT CLEAR. `wake-balance.py:250` used `open(PAUSE, "w")`, which
 truncates the destination BEFORE a byte is written. On 2026-10-14T22:41:02Z that run died with
 `OSError: [Errno 28] No space left on device` (root filesystem at 88%) and left the file at
 0 bytes - `stat` read `size: 0, mtime 2026-10-14 22:41:02`. The resume test then required
 `body.startswith("low-balance")`, so the guard could not recognise - or clear - its OWN pause at
 ANY balance. Auto-resume was impossible, not merely hard.
3. A FIXED ABSOLUTE CEILING. `ceiling()` returned 25.00 in `wake-balance.py:80-86`, in
 `wake-value.py:25-31`, and as a literal on the `wake-fanout` crontab line. The guard's own log
 printed it on every run: *"WARNING: the daily ceiling (25.00) is larger than the balance (5.70) -
 it cannot bind."* The script's own docstring condemns exactly this.

WHAT WAS BUILT. `cap = clamp(balance / runway_days, min_daily, configured_max)`, and never more than
the balance. One new module, `/root/bin/wake_budget.py`, holds the whole arithmetic and the state file
`~/.sms-inbox/wake-budget.json` written ATOMICALLY on every guard run; the other readers defer to it.
`runway_days = 3.0`, `min_daily = 0.25`, `count_max = 150`, `COST_PER_RELEASE_USD = 0.0639`
(measured: `spend_today_usd` 9.587016 over 150 releases on 2026-10-14, inside D3125's 0.036-0.068
band). Measured burn from `wake-balance.log` (46 readings to 2026-10-14T23:41Z): 120.73 -> 5.70,
115.03 over 43 hourly intervals = median 1.86/h (~45/day), mean 2.70/h (~65/day).

WHY 3 DAYS, AND WHY IT AGREES WITH 75.00. `configured_max (25.00) x runway_days (3.0) = 75.00`, which
is the `--warn 75` the guard is ALREADY run with. Above 75 the runway cap cannot bind, so 75 is the
boundary between `ok` and `conserve`; below `min_daily x runway_days = 0.75` it is `stop`. The three
things that used to be separate numbers are now one relation. OPTIMISED FOR BINDABILITY: cap <=
balance at every balance, which is the property whose absence was the bug. The floor refuses a cap
that buys nothing.
