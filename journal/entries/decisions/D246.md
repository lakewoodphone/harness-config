**D246 · 2026-09-17 · In the zabz preset subagent IS the mesh; the local tool is renamed subagent_local.**

DECISION (2026-09-17, ZABZ-YOGA, delegated session): in the `zabz` preset the tool NAME `subagent` is bound to the `remote-ssh` provider, so fan-out is the mesh by default with no change to any prompt. The local spawn tool is NOT deleted; it is renamed `subagent_local` (one-shot, not continuable). `subagent_remote` is kept as an alias row bound to the same provider, so the three scripts that name it by string (`mesh-provider-install.ps1:239`, `mesh-restart-at-0700.ps1:706`, `mesh-e2e.ps1:1457`) and every prompt written before today keep meaning the mesh. `subagent_fork` is unchanged.

WHY: the routing, not the transport, was the defect. `docs/mesh/82-e2e-run.md` §3.2 measured a parent told to "fan the work out" choosing the LOCAL tool (the child reported `MESH-HOST: zabz-yoga` — its own machine) while a parent told the tool's name produced 6-of-6 remote children three times; `journal/entries/wins/W196.md` records the same 0-of-1 → 6-of-6. A tool is chosen by NAME, so the name is what changed.

OPTIONS REJECTED, with evidence. (1) "Make the remote provider the default provider and keep the tool's name" is not a mechanism: `ctx.subagents` is a named-provider registry with no default (`dsh-subagent/README.md:69`) and the tool's config makes `provider` mandatory (`dsh-tool-subagent/lib/index.js:252-254`). Two rows sharing one `toolName` in one scope THROW (`tool "X" is already registered in this scope`, `dsh-tools/lib/index.js:2538`), so the local row cannot simply be left beside it either. (2) Deleting the local tool outright was rejected on the stated constraint that a single point of failure is worse than local execution: it would leave a session with the office desktop unreachable — or a node where the bundle is not mounted — unable to spawn any child at all. (3) A prompt-level norm was rejected as the mechanism because §1 of the new doc IS that trial; it survives only as the failure protocol.
