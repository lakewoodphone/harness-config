**D144 · 2026-09-14 · The journal is one file per entry with a generated cache that heals itself.**

The owner's complaint was that the journal was "getting longer and longer and not split up, split up enough, not indexed enough, not set up properly with proper flags". Measured on 2026-09-14 (AUDIT.md), he was describing real numbers: 9 shard files holding 1,386,869 B of history, the largest 249,724 B; `status` produced 12,347 B against its own 12,000 B budget, exited 1, and took 8.88 s; `show P46` took 0.41 s and read a quarter-megabyte to print 1,178 B; the index was 150,131 B for 781 rows because it stored line offsets into monoliths; and no command had a single filter flag.

Decided: the log is one file per entry, `entries/<kind>/<id>.md`; `index/` is a generated cache that rebuilds itself when a signature of `entries/` changes and never blocks a read; every read command has real flags (`--kind --since --until --status --tag --host --limit --budget --json`) and truncates during assembly with a visible marker.

Rejected: bigger shards with a byte-offset index (still one write target per kind, so two machines still merge text and collide); a database as the source of truth (unreadable in a diff, and this fleet's machines drift); keeping the flat files as the record (they are what grew unbounded in the first place).

Consequences, all verified: status 5,986 B / 97 ms / exit 0; show opens exactly one file, 9 ms; search 105 ms; newest 100 ms; the largest single history file is now one entry. `index/entries.tsv` deliberately keeps v1's exact 12 columns and entry files begin with v1's marker line, so a machine still running v1 can `show` an entry and `next-id` correctly instead of restarting at 1 and recreating the collision scar. Evidence: AUDIT.md, SPEC-v2.md, `journal.py costs`, `_scratch/j-verify.py`.
