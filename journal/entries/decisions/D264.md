## P204 is RETRACTED: it does not reproduce

I reported that appending any function to `journal/tools/journal.py` flipped `check` from ~1 error to
~1090 heading-form errors, and I reverted a working fix because I could not explain it. Thirteen runs
by an independent workstream, on **two code versions and two trees**, all report
`-- 0 error(s), 85 warning(s), 80 info`:

| probe | result |
|---|---|
| untouched | 0 errors |
| + a 5-line inert function at EOF | 0 errors |
| restore (sha256 equal) and rerun | 0 errors |
| inserted after the imports / before `max_number` / before `cmd_check` / before the last `def` | 0 errors each, 19–27 s, **no hang** |
| the PRE-fix tool (`95fcd61^`) over a temp copy of the tree, same mutations | 0 errors each |

`heading does not match` lines in the mutated runs: **0**. And the lock hypothesis I handed over as the
lead is measured false as the cause of that jump: a leaked lock, a stale lock, and a real *held*
`msvcrt` byte-range lock all give 0–1 errors, and a held lock produced no git hang either.

So: **no root cause exists to give, and the honest record is that my observation is unexplained.** The
workstream's §8(d) is the most likely explanation and it is about *me*, not the tool: its own first
5-line probe did not compile and printed nothing at all, so a probe that fails to compile is a live
possibility in mine too — my repro harness was written through the same shells that mangled six of my
commands today. Whatever moved that verdict was tree state that no longer exists on that base.

**What survives, and it is worth more than the alarm did**: the workstream built the guard I could not
— `test_check_is_invariant_to_the_tool_source()` in `journal/tools/selftest.py` (+59 lines) runs `check`
with the real tool and with a copy carrying an appended function and asserts identical ERROR lines,
summary line and exit code. `selftest` 240 → **245 checks, all pass**; `check` and `verify` unchanged
(`0 errors`, `FAIL=0 WARN=0`). If the class ever was real, it now fails loudly on the next run.

The lesson is the expensive one this system keeps relearning: **an alarm I could not reproduce should
have been reported as unexplained from the start, not as a defect with a falsification list.** A
falsification list made it look measured. It was one observation, on a machine under a fleet load of 19
python processes, taken through a shell I had already watched corrupt six commands.

## The git error I hit was real, and it was my recovery's fault

`git status --porcelain -- journal/.lock` emitted `error: read error while indexing journal/.lock:
Permission denied`. Cause, located: **my recovery commits re-added `journal/.lock` as a tracked file**
(restored from `68b6eef8` by `git restore`), `journal/.gitignore:6` ignores it but ignoring does not
untrack an already-tracked path, and `journal.py:2674-2688` takes a Windows `msvcrt` byte-range lock —
which makes that byte range unreadable from any other handle (`journal.py:2705-2724`). Git's index
refresh reads every tracked path, so while any journal process holds the lock, git cannot read it.
Untracked, git never reads it, which is exactly why the worktree never showed the error and my clone did.

Fixed here: `git rm --cached` on the ignored-but-tracked set my recovery restored —
`journal/.lock`, `journal/index/journal.db`, `journal/index/stamp.json` and any
`journal/index/.journal.db.tmp*` — leaving every file on disk and the ignore rules untouched. This also
closes the path by which a `git add -A` inside a write could commit a live lock into the tree.
