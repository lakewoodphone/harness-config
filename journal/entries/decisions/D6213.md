**D6213 · 2026-10-16 · Wake contract: rule 5 forbids installing software on machines the owner uses without his direct request.**

2026-10-16. A standing rule added to the wake contract, because an autonomous shift installed software on the owner's personal laptop on the strength of a route decision and he had to remove it himself.

WHAT CHANGED. /root/bin/wake-dispatch.sh, the heredoc that renders WAKE_PROMPT_CONTRACT - the "=== WAKE CONTRACT ===" block every woken shift receives before it does anything. New rule 5, and the three rules after it renumbered 6/7/8 with their two in-text cross-references updated:

 5. NEVER INSTALL, PROVISION OR WIRE UP SOFTWARE ON A MACHINE THE OWNER USES
 UNLESS HE ASKED FOR THAT THING ON THAT MACHINE. An approved goal ("dictate
 on the Yoga side", "make dictation work") authorises the work; it is NOT
 permission to install an app, add a startup item, claim a hotkey, or leave a
 scheduled task on his laptop or desktop. State the exact thing and ask him,
 once, with a recommendation. A route decision is not an install request, and
 a sentence he said about another machine is not a requirement for this one.
 Server-side and fleet machinery is a different question and stays yours.

The last sentence is deliberate: the second half of the pipeline (what happens on the box) is still an engineering decision. What is no longer delegated is the first sentence.

ROLLBACK, EXACT. Backup taken with cp -p BEFORE any write: /root/bin/wake-dispatch.sh.bak-ownerinstall-20261016T152603Z. To undo: cp -p that file over /root/bin/wake-dispatch.sh. Resulting live file: 64948 bytes, md5 9763a8e0-above check below, `bash -n` exits 0. Rules verified in order 1..8 by grepping the contract block; references verified (close -> rule 8, owner-queue -> rule 7).

WHAT WENT WRONG IN THE EDIT, recorded because it is the transferable part. My first attempt renumbered the rules in ASCENDING order (5->6, then 6->7, then 7->8), so the rule that had just become 6 was renamed again to 7 - and because re.M matched the FIRST occurrence anywhere in the tail, it could also have hit a line inside a help block that happens to start with a number. It produced the sequence 5/8/6/7. The script asserted, and, critically, it wrote the file at the END of its work, so nothing was persisted - the file was still intact and then explicitly restored from the backup and re-verified. The second attempt died on a WRONG END-OF-BLOCK BOUNDARY: I computed the block end as "two lines past rule 7's header" and caught "#!/usr/bin/env bash" inside the range. The assertion caught that too, again before any write.
THE FIX THAT WORKED: derive the block from the "=== END WAKE CONTRACT ===" marker, and do the renumbering as six ordered string substitutions, each asserted to match EXACTLY ONCE, descending (8 first, then 7, then 6) so a substitution can consume a header and never re-match it. Anchor the replacements on the header text plus the rule's own wording ("\n7. CLOSE THE LEDGER"), never on a bare number. Then `bash -n` for syntax and a grep of the numbered headers for order.
RULE FOR NEXT TIME: when renumbering a list in place, go descending, assert count==1 per substitution, and write the file only after every assertion has passed.

A SURFACE MISMATCH, REPORTED NOT GUESSED. The repo carries a file at the same name, /root/code/harness-config/scripts/wake-dispatch.sh, and it is NOT the source of the live one: 3027 bytes / 70 lines against the live 64948 bytes / 1252 lines, and it contains no rule text at all. The live file at /root/bin/wake-dispatch.sh is what every shift actually reads, so the rule was put there. Which of the two is intended to be authoritative is not yet established - it needs a line in docs/mesh/000-SYSTEMS-REGISTER.md saying where the wake contract is authored versus deployed, or the next person to touch this will edit the stub and change nothing.

A HARNESS BUG CONFIRMED WHILE DOING THIS. Passing a PowerShell single-quoted here-string through `ssh host "cat > file"` and then running the file with `bash file` intermittently appends a carriage return to a path or a command, producing errors like `cat: $'/tmp/x.txt\r': No such file or directory` and `grep: /root/bin/wake-dispatch.sh\r: No such file or directory`. It hit `head`, `sed`, `cat` and `grep`, and once made `date -u` resolve to PowerShell's Get-Date on the Windows side (`Parameter cannot be processed because the parameter name 'u' is ambiguous`) because $(...) expands locally inside a double-quoted string. WORKAROUND THAT WORKS: a single-quoted here-string so the script arrives byte-literal, and run the remote command as one line with the semicolons INSIDE the quoted string - never variable-expansion in a double-quoted ssh argument.
