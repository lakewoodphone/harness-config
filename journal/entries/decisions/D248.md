# Decision: the mesh transport order, and how a node's concurrency ceiling is derived

Decided 2026-09-17 by the transport-concurrency session. Record: `docs/mesh/93-transport-concurrency.md`.

## 1. THE TRANSPORT ORDER

**v2 (the HTTP route) is the default — for a single child AND for a fleet. v1 (ssh) is chosen only
when one of three stated conditions holds, and never because a node is busy.**

Why the ORDER and not a fallback chain: the two transports now have different shapes, so which one
runs is a decision that must be visible in the record. `bin/mesh-dispatch.mjs` writes
`preferredTransport` and a `transportPlan` sentence into every run's `start` line.

v1 wins when:
1. the node has no route, or has one with no secret (measured 2026-09-17: `secratary`,
 `lakewooechsmini`, `zabz-tech-linux` all answer 404 on `/mesh/health`);
2. the caller deliberately wants a node oversubscribed past its own measured ceiling — the only way to
 run 55 children *simultaneously* rather than in ~4 waves. This is now explicit (`-Transport v1` /
 `-PreferV1`);
3. the route cannot be reached at all (gate down, relay dropping).

**Explicitly NOT: a busy node.** v0.1.0 fell back to ssh when `runner.busy === true`. With a queue,
that would move a child to another machine for no reason — the duplicate `70` §4.2 exists to prevent.

## 2. THE CEILING IS DERIVED, NOT CHOSEN

`limit = max(1, min(cpu, mem, declared, hard))` where
`cpu = floor(logicalCpus × 0.42 ÷ 1.68)`, `mem = floor((availableMiB − max(2048, 12 % of physical)) ÷ 403)`,
`declared` is the node's own `accepts.maxChildren`, `hard` is the governor's 24.

Every constant is a measurement from `84-calibration.md` and every one is published in
`GET /mesh/health` beside the number it produced, so a reader can check the arithmetic without reading
the source. **The units matter**: `84` measured `CPU_PER_TURN` in LOGICAL CPUs and validated `0.75 ×
physical cores` in physical ones, and §6.6 records that the conversion between them was never measured
— a first version of this file mixed the two and produced 14 instead of 8.

Measured result per node: **zabz-tech 8 · zabz-yoga-1 5 · secratary 1 · zabz-tech-linux 3 ·
lakewooechsmini 1** (the last is limited by memory, not cores: 236 MiB free physical).

A node whose fleet is known to be model-bound raises its own limit with one environment variable —
`MESH_HTTP_CPU_PER_TURN=0.62` takes `zabz-tech` from 8 to 12 — and the arithmetic is re-published.
No code change, no redeploy, and the default is the conservative (worst-turn-class) direction.

## 3. THE ROUTE REFUSES NOTHING FOR CAPACITY

A request beyond the limit joins a FIFO, gets a position, and is served in arrival order; the position
and the wait appear in its own answer (`queue: {position, waitedMs, limit}`). The one remaining `429`
is `node-queue-wait-exceeded` — a wait budget (780 s default, deliberately shorter than a
dispatcher's own 900 s POST budget so the node always answers first), not a capacity refusal.

`refuseWhenFull` restores v0.1.0's behaviour and defaults to **off**.
