**D · Remote child turn cap raised from 300 s to 1800 s; shared-profile window count no longer uses the profile directory**

Decided 2026-09-18 (ZABZ-YOGA) while taking over the blocked mesh goal from session e34dd061.
Both are engineering decisions, taken without asking, and recorded with their evidence.

1. `packages/plugin-remote-fanout` child turn cap: `300000` -> `1800000` (five minutes -> thirty).
 Files: `profiles/web/cordis.patch.yml` (managed by the mesh-provider install block) and
 `profiles/mesh/cordis.patch.yml`. `MESH_CHILD_TIMEOUT_MS` still overrides both.
 WHY 1800 s and not "unbounded": thirty minutes bounds a runaway child while letting a real
 workstream finish inside one turn; it is also 2x the transport's own `DEFAULT_TIMEOUT_MS`
 of 900_000, so the transport (which receives this value explicitly) is never the binding
 constraint. WHY NOT 900 s (matching the transport): the point of the change is that a child
 should not be cut off while it is still making progress, and a heavy build step can exceed
 fifteen minutes.
 CONSEQUENCE ACCEPTED: a wedged child can now hold a slot for half an hour. The governor and
 the broker lease are what bound concurrency, not this timeout.

2. `multi-window/dshw.ps1` `Get-WindowCount`: the `--user-data-dir` fallback now returns 0
 immediately in shared-profile mode (`if ($shared) { return 0 }`).
 WHY: in that mode the profile directory is the SAME for all sixteen slots, so the fallback
 reported every slot occupied from a single window, and `dshw new` refused with no window, no
 error and no log line. The origin-port check above it is the correct per-slot identity.
 CONSEQUENCE ACCEPTED: with the origins proxy down AND the process scan blind, a live window
 on a non-first origin can read as absent, so `new` may open an extra window rather than
 refusing. The comment at `Get-WindowOriginPorts` already records that the proxy leg is the
 load-bearing one; a duplicate window is a far cheaper failure than a control that does
 nothing, which is exactly the trade the 2026-09-15 comment chose.
 NOT DONE, and deliberately: no change was made to `Open-SlotWindow`, to the slot table in
 `windows.json`, or to the hidden `-WindowStyle Hidden` registry command. The hidden command
 is worth revisiting (its silence is what hid this for hours) but that is a separate change
 with its own verification.
