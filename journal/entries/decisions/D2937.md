**D2937 · 2026-10-05 · Android release signing is fail-closed by default; keystore at ~/.lpt-keys/lpt-release.jks and its custody is the owner's.**

Android release signing in kosher-filter-ai is now fail-closed, and the keystore exists.

WHAT WAS WRONG. `LPT_STRICT_RELEASE_SIGNING` defaulted to false, and with it false the `release`
build type simply had no `signingConfig`, so AGP wrote `app-release-unsigned.apk` and the build
reported SUCCESS. That is the only Android artifact this repo had ever produced (2026-09-06), and
nothing prevented another one.

THE DECISION, and why each part:
 * strict signing defaults to TRUE - signing is not optional, because an unsigned APK cannot be
 installed on a real phone, so producing one is never a useful outcome. Same fail-closed default
 `LPT_BUILD_STRICT` already uses.
 * enforced IN THE TASK GRAPH, not at configuration time. A configuration-time throw fires for
 every task in the module including `testDebugUnitTest`; that exact defect is already recorded for
 the old LPT_BUILD_STRICT shape in docs/audits/kf0928/android-enrolment.md section 2.2. Scoped to
 assembleRelease/bundleRelease/packageRelease/installRelease/publishRelease*.
 * a property PRESENT but pointing at a missing file counts as NO signing config. Otherwise the
 failure is deferred to AGP's package task as a cryptic keystore error. This is the part that
 makes the control real rather than intended: it refused the branch's own first release build on a
 mangled path, which the old code would have turned into a silent unsigned APK.
 * two escape hatches, both explicit, neither silent: `LPT_SIGN_RELEASE_WITH_DEBUG` (installs, not
 shippable, now prints a warning saying so) and `-PLPT_STRICT_RELEASE_SIGNING=false`.
 * `keystore.properties`, `*.p12`, `*.pfx` added to .gitignore. `keystore.properties` is NOT read by
 this build (it reads local.properties, -P properties and the environment) but it is the name
 everyone reaches for when told to store a keystore password, and it was not ignored. A tracked
 password file is the one mistake here a later commit cannot undo.

KEYSTORE. `C:\Users\ezabz\.lpt-keys\lpt-release.jks`, alias `lpt-release`, RSA 4096, PKCS#12,
valid 2026-10-05 to 2056-09-27 (10,950 days), cert SHA-256
47:0F:F7:55:70:58:D2:FD:8F:22:78:76:66:21:B4:E9:17:FB:90:F3:C9:EB:36:84:17:2E:1E:6D:8C:41:8E:34.
Outside the repository, on purpose. Passwords live only in `~/.lpt-keys/keystore.properties` (the
durable copy) and the worktree's gitignored `android/local.properties` - never in a tracked file,
never in the journal.

CUSTODY IS THE OWNER'S DECISION, and it is a real one: this file is a root of trust for the app's
identity. Lose it and no update can ever be published to an already-published app, because Android
refuses an APK whose signature changed. It survives this session only because it lives outside the
repo, in a directory nobody has been told to back up. Nothing is published yet (versionCode 1, never
shipped), so there is no live install base to strand - which is exactly why now is the cheap moment
to decide where it is backed up and who holds a copy.

PROVISIONING IS A SEPARATE AXIS, and I deliberately did not "fix" it. The build also refuses a
release artifact without LPT_BROKER_WS_URL / LPT_BROKER_AUTH_TOKEN / LPT_PHONE_ID. I did NOT go
looking for the real broker token to bake in: the repo ships `broker_auth_token` EMPTY on purpose
(android/README.md:225, docs/ANDROID_PROVISIONING_GUIDE.md:39) precisely so a global bearer token is
not distributed inside every customer APK, and a per-phone `LPT_PHONE_ID` cannot belong in a fleet
artifact at all. Supplying the real token at build time would have been a security regression dressed
as thoroughness. The signed artifact was therefore built with the documented production URL
(`wss://broker.lakewoodphone.com/ws/phone`) and openly bench-marked token/phone-id.
