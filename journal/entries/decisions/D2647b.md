**D · 2026-09-25 · ZABZ-YOGA — Customer card data is scrubbed from the SMS log and cannot be stored again (owner-approved)**

**The finding.** While double-checking what we had texted a customer, the thread contained his own message of 2026-09-15: *"Pls charge 5129 9252 3138 5389 Exp 05 30 cvv 378 zip 08701 Ty Yoel Weissman"*. Across the whole table: **141 rows, 4 customers, carrying a full PAN *and* a CVV in plain text, the oldest 2026-02-09**. Storing the CVV post-authorisation is prohibited, and this is a live customer card on a machine whose backup runs nightly. P336 had the design; H610 listed it as *"designed, not built"*.

**The decision (asked as one question, answered by the owner 2026-09-25):** *"Scrub the 141 rows and build the ingest redaction."* Both halves were done.

**Executed and verified.**
- `~/bin/redact-stored-cards.py --apply`: **142 rows rewritten** — 141 in `dialpad_sms_cache.body_text` plus 1 in `tasks.description` — scanned across ten tables and every text column discovered by `PRAGMA table_info`, not a hard-coded list. Rows were updated one-per-commit with retries, because a single batched transaction hit `database is locked` instantly (see L on the write-lock outage).
- **Verification: 0 rows still match card + CVV.** Sample, masked: `Pls charge ************5389 Exp [redacted] cvv [redacted] zip 08701` — the message stays readable, the last four survive for reconciliation, the PAN/CVV/expiry do not.
- `app/services/payment_card_redaction.py` (commit `f4626ecc`) with 12 tests: masks 13–19 digit PANs **on shape, not Luhn validity** (a mistyped PAN is still a PAN, and a validity-gated redactor fails exactly when the customer fat-fingers a digit); removes a labelled CVV outright rather than masking it; leaves a long digit run inside a URL path alone so a tracking link still works. Not applied to the session archive or the journal — those are append-only records and scrubbing them is a separate decision, reported rather than taken.

**Irreversibility, stated plainly.** The removed digits are not kept anywhere by the scrub: a backup holding them would recreate the exposure it closed. **Nightly database backups still contain the pre-scrub copy until they age out of retention** — the owner was told this when he approved.

**What remains.** New writes still need the redactor wired into every ingest path (dispatched to a mesh child; reported separately). The archive and the journal have not been scanned for the same text.
