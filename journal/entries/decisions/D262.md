**D262 · 2026-09-17 · Monitor fixed at the source: a dead collector was printing a confident 0.**

## The defect, corrected by measurement

The audit said the monitor "answers a different question than its own label asks". The workstream
found something worse and more precise: **it was a dead collector answering nothing, while printing a
confident 0.** `app/services/next_stage_runtime.py:319-320` globs `docs/ai-company-next-stage/*.md`
NON-recursively, and that directory's only child is the gitignored `generated/`, so the glob matched
ZERO files. The artifact said so itself: `packet_file_count: 0`, `status_headers: {}`. Zero input
produced zero in every field, printed under the label "Pending owner decision rows".

That distinction changed the fix: **re-source the count, not rename the label.** The label was right.

## The fix, on `agent/monitor-label` (ac26eb04), NOT YET MERGED

- `pending_decision_rows` now comes from `SELECT status, COUNT(*) FROM owner_decision_queue GROUP BY
 status` → `pending`, read through the `conn` both call sites (`:393`, `:1680`) already had.
- The dead packet tally is retained but renamed `packet_pending_rows` / `packet_decided_rows`, so it
 stays visible without impersonating the queue.
- An unreadable or absent queue yields `None`, never `0`; renderers print `unknown`. This is the same
 rule as everywhere else in this system: **a refusal must not be able to render as health.**
- One test added (`tests/test_next_stage_runtime.py`), which asserts the rendered line equals the
 queue and that an unreadable queue renders `unknown`. It would have caught the defect: it asserted 0
 before. `6 passed`; `import app.main` OK.

Verified agreement in one window, three sources: queue table 16, code 16, label 16 — `AGREE: True`,
cross-checked against the independent `owner-queue.py stats` (16).

## What integration must do, and what it must not

1. **Merge `agent/monitor-label` into the authority's master.** Until then the DEPLOYED monitor keeps
 saying 0 — proven live: the artifact rewrote itself at 2026-09-18T02:10:41Z and still said
 `Pending owner decision rows: 0`, because the running checkout has the unfixed code.
2. **The generated artifact must NOT be committed.** It is produced hourly by `run_world_index()`
 (`:433-434`) and is gitignored (`.gitignore:268`). It regenerates itself; there is no manual step.
3. **Do not run the generator to "prove" the fix.** `run_world_index()` inserts a
 `next_stage_world_events` row and commits — a DB write. The workstream correctly refused and
 evidenced the fix by calling the fixed function and renderer directly against the live DB
 read-only. That refusal is the right one.
4. The authority's shared checkout holds ~166 uncommitted files belonging to another session, so the

## The larger fix, identified and deliberately not built

`owner_decision_queue` is created and owned solely by `~/bin/owner-queue.py` (`SCHEMA`, lines 53-71).
**The FastAPI app neither creates nor migrates that table** — `grep owner_decision_queue` across
`app/` returns nothing. So on any database where the CLI has never run, the new count degrades to
`unknown` rather than a true `0`, and the company's own database is not authoritative for a table the
company's own reports depend on. Making the app own the table (creation, migration, and reconciling
the `journal/state/owner-questions.md` mirror against it) is a schema change, so it is described here
as a separate workstream instead of being smuggled into a label fix.
