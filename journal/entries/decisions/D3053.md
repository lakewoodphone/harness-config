**D3053 · 2026-10-12 · Landing the pay-before-pickup notice: draft-not-send, explicit connector, one page per transaction, a replay re-asserts.**

**D3053 · 2026-10-12 · Four decisions taken while landing the pay-before-pickup notice, each with the reason it went that way**

1. **A pay notice is DRAFTED automatically and SENT by a person, and the screen
 makes the send a second, deliberate press.** The machine writes the message the
 moment a job goes `READY_FOR_PICKUP` with money owed; nothing sends on its own.
 The owner's standing rule is draft → show → a per-message yes, and the counter
 screen puts the two buttons a thumb-width apart, so the first press arms and the
 second sends. Rejected: an unattended sender. It would be the owner's call to
 make, and it is not needed to fix the thing that was broken.

2. **An explicit `STRIPE_PAY_CONNECTOR` is honoured exactly, and `NODE_ENV` only
 supplies the default.** `NODE_ENV=production` is true on the test stack (it
 serves the production build), so it cannot say which deployment a process is;
 the old interlock read that pair and handed test the LIVE connector, where one
 call would have charged a real card. The refused direction that remains is a
 non-production process being handed the live connector. A production host
 explicitly configured with the test connector now takes no money at all, which
 is loud at the customer instead of silent in the bank — logged as a warning.

3. **One payment transaction has exactly one payment page, and a blank second
 call returns the first.** `payment_pages.paymentTransactionId` is UNIQUE, so the
 old unconditional `create` did not create a second page — it threw, after the
 operator had already read and approved the words. Reuse is limited to an
 `ACTIVE` page; a page the system already stopped raises a named
 `PaymentValidationError` rather than being resurrected, because resurrecting a
 paid order's page is how a customer pays twice.

4. **A replayed phone callback RE-ASSERTS the order instead of doing nothing.**
 The insert, the `orders.paymentStatus` write and `releaseForPickup` are three
 statements; a crash between them left a paid order reading PENDING with the
 device unreleased, and Twilio's retry was the only event that ever arrives
 afterwards. Both writes are derived from the ledger and `releaseForPickup` will
 not move a stamped timestamp, so re-running the tail cannot double-apply — and
 it is the rail's only self-healing path. Two existing tests asserted the old
 "a replay applies nothing" contract and were rewritten to the new one, with a
 new test that simulates the crash and proves the repair.
