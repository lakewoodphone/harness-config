## 2026-10-22 17:47 UTC · Automatic DNS failover is live, and the backups are readable from a second machine

**The token was already on the mesh.** `/opt/company/.env` on `secratary-cloud` carries `CF_API_TOKEN`
(40 chars) with **write** access to the `abletelsolutions.com` zone — the same credential
`company-dns-failover.py` uses. Verified by creating and deleting a TXT record: `success: true`. The
token on the MDM host can only *read*, which is why the controller does not live there. Nobody had to
issue anything new.

**Built: `/root/bin/doh-failover.py` on the authority.** Three consecutive primary failures move the A
record for `mdm.abletelsolutions.com` to the second origin; one healthy run moves it back; before any
move it asks the standby a real DoH question over TLS validated against the real hostname and **refuses
to move onto an origin that does not answer**. State in `/var/lib/waze-doh-watch/failover.json`, every
move one line in the watcher log. Called by the watcher every two minutes with the primary's verdict.

**Proven end to end, 17:44Z.** `--force standby` moved the record `87.99.141.172 → 178.104.210.131`;
1.1.1.1 resolved the new address after ~20 s (TTL 60); the standby answered the fleet's query
`http=200 tls=0 rcode=0 answers=1`; `--force primary` moved it back and 1.1.1.1 followed within ~20 s.
The threshold was proven separately without moving anything: two simulated failures produced
`waiting, failures 2`, and one healthy run reset to `failures 0`.

**And the backup is no longer hostage to one host.** The recovery review found `/root/.restic-env` —
the credentials for the restic repository holding the PostgreSQL dump — existed **only on
`waze-mdm-01`**. If that host died, the offsite copy would have been unreadable. Copied to
`secratary-cloud` (600), `restic` installed there, and the repository opened read-only from that second
machine: **55 snapshots, newest 2026-10-22 03:30**. That is the difference between "we have backups" and
"we can restore".

**What the account looks like now**: ten DNS records aside, four servers in **one** Hetzner account
(`waze-mdm-01` ash, `lpt-apps-01` fsn1, `lpt-survivor-01` fsn1, `secratary-cloud` ash) plus the new
`dns2-abletel-01` (cx23, fsn1, 178.104.210.131). Two of the five are in a different region and a
different network path from the MDM host; none is in a different account, so an account-level suspension
would still take everything — that is a second-account decision, not a server one.

**Live state after this work**: primary + standby both answering and both watched; DNS moves
automatically within ~3 minutes of a sustained primary failure and back within ~2 minutes of recovery;
the certificate and PAC on the standby refresh themselves daily; the fleet's own state (which devices
carry `AllowFailover=false`) is still unknown and the 58-device sweep is still held.
