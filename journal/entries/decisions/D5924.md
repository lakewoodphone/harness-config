## The phone platforms lead the ledger queue, and the dead daily push is retired

**Asked by the owner, 2026-10-09:** "the kosher AI filter system that you build every day automatically — is it progressing, is it advancing, is it getting fully built out for android and iOS?"

**The measured answer was no**, and the mechanism was two structural faults, both now fixed.

### Fault 1 — the queue could never reach Android or iOS

`work.py _pick_next` orders by `priority ASC, project-oldest-todo, created_at`. Measured over the
14 days to 2026-10-09, from `~/work/work.db` on the authority:

| class | attempts | newest attempt |
|---|---|---|
| Integrate | 162 | 2026-10-06 |
| Windows | 90 | 2026-10-09 |
| Server | 5 | 2026-10-05 |
| Infra | 5 | 2026-10-02 |
| Android | **3** | **2026-09-29** |
| iOS | **0** | **never, ever** |

The eight open Android/iOS items (519, 520, 533, 530, 535, 542, 543, 551) sat at priority 5–7.
Every shift that discovered Windows work filed it at priority 1 — two items were filed at p1 on
2026-10-08 and two more on 2026-10-09 — so the fixed phone backlog was never reached. The loop was
not idle; it was busy on the wrong platform, permanently.

**Decision.** Android and iOS items are now priority 1, and the three p1 Windows fires dropped to
priority 2. The tie-break is `created_at ASC`, so an older phone item also beats a newly filed p1
item — the starvation cannot silently return. Verified: `kaf-loop-status.py` now prints those eight
items as "QUEUED FOR THE NEXT SHIFT", Android first.

**Rule added to the shift contract** (`~/bin/sources/project-keepalive.py`,
`standing_contract()` STEP 5): priority 1 is reserved for a production outage or a
customer-facing break; a discovery made mid-shift is filed at priority 4 or lower; the phone
platforms are the product and must not be preempted by routine Windows or integration work.

### Fault 2 — `seed_eng_filter_ai_daily_push` could never succeed once, in any run

The thing the owner believed was building the product. From `work_order_executions`: **30
executions 2026-09-12 → 2026-10-08, 0 successes, 0 artifacts, quarantined twice** (2026-10-01,
2026-10-06) and revived each time. The last three sessions (2026-10-08) each ended at
`[COMPLETION BLOCKED: artifact-required work reached a completion path without evidence;
reason=planned_step_budget_reached_without_artifact]` after spending all five steps on
`github_list_dir` / `repo_search` / `repo_map`.

Root cause: a work session with **read-only** repo and GitHub tools, **no shell and no write**, a
**5-step** budget, and an **artifact** requirement — against a repository of 259 Kotlin files, 234
server test modules and 21 Swift files. It could not have succeeded on any day.

**Decision.** Retired, in both places that matter: the live row (`is_enabled=0`,
`last_run_status='skipped'`, one `work_order_executions` row carrying the diagnosis) and the seed
source (`app/services/work_orders.py`, commit `ce2a0586`), where a seed may now declare itself
`retired` — inserted disabled and forced disabled on every bootstrap, so a fresh environment cannot
resurrect it. Its replacement is the mechanism that actually works: `roadmap-supply.py` →
`ledger-keepalive.py` → a woken shift that claims an item → `work.py` attempt with a proving
command, watched by `kaf-loop-status.py --check --stale-hours 6` every 30 minutes.

### main had been frozen for 3.5 days

`origin/main` was `3696a11` (2026-10-05 17:50) while remote branches carried 2026-10-06..08 work.
The cause was a rule I wrote earlier (`fix-integration-push-rule.py`): "a shift never promotes into
main". Promoting a *green, deletion-guard-empty* branch is ordinary engineering, and that rule is
what turned six branches into invisible work and made the ledger refile the same integrate item
four times (488, 494, 498, 500). Promoted the docs-only one (one file, +15/-1, zero deletions, its
tip green on both suites): `origin/main` is now `2d9585d`. Ledger item 500 closed with the push as
its proof. The two Windows branches (560, 561) were **deliberately not merged here** — their suites
are .NET and this host has no `dotnet`, so merging them would be a claim I could not reproduce.

**Recorded.** Owner-queue #298 and #280 resolved (both were dev decisions, and #280 was already
satisfied by events — `27f42b0` is an ancestor of main).
