**D3036 · 2026-10-08 · The shop counter devices' password AutoFill was disabled by their own MDM profile; both keys are now true and pushed.**

## What was wrong
The shop's three MDM-enrolled counter devices — DRN 2001 iPhone 11, DRN 2002 iPhone 11, DRN 2003 iPad Air 5
(site `lpt`, `device_class: store_device`, profile `com.abletel.lpt.shopstore`) — had password AutoFill
switched off **by their own profile**, in two keys:

```
com.apple.applicationaccess allowPasswordAutoFill : false
com.apple.applicationaccess safariAllowAutoFill : false
```

So "normal password autofill" was not a Safari setting on the device and not a website change: it was an
MDM restriction, which is why nobody could find it on the device. Deliberately left alone:
`allowCloudKeychainSync` (already true), `forceAuthenticationBeforeAutoFill: true` (autofill stays behind
the device passcode — normal iOS), and `allowPasswordSharing` / `allowPasswordProximityRequests` (AirDrop
password sharing, a different feature).

## What changed
Both keys set to `true`. Derived **from production**, not from the repo (the repo's copy was stale on
2026-10-07 and cost a session an hour; see `deploy/waze-mdm/docs/lpt-shop-device-runbook.md` §3).

- served profile: `/opt/waze-mdm/profiles/shop-store.mobileconfig` on `waze-mdm-01` (87.99.141.172),
 sha256 `674bd74e8c56d068fa3a0881db9d18be733c6b14e6aaa3d9aabde61e73f4422a`
- backup of the previous file: `shop-store.mobileconfig.bak-before-autofill-20261008T220805Z`
 (sha `2d213d96…`, the 2026-10-07 filtered + Maps build)
- the change script is `enable-autofill.py` (textual edit + full plist diff; it refuses unless the *only*
 value differences anywhere in the profile are those two keys — measured: 2 diffs, same five payload
 identifiers, same order)
- tracked copy `personal-secretary-mvp/deploy/waze-mdm/profiles/shop-store.mobileconfig` now equals the
 served file byte for byte (same sha). It was **not committed**: that repo's tree carries another
 session's uncommitted work (`app/direct_service*`, untracked `deploy/systemd/`, …) on branch
 `integrate/dialpad-reconcile-20261007`, and `git add -A` there is exactly trap P13.
- pushed with `POST /api/fleet/devices/<drn>/install-profile?profile_type=shop-store`:
 DRN 2001 `InstallProfile 3F6D7866…` **Acknowledged**, DRN 2002 `0A9B4DA1…` **Acknowledged**,
 DRN 2003 `509683EB…` **NotNow** at 22:10Z (the iPad is asleep/idle). The queued command for the iPad
 was decoded back out of `commands.command` and carries the new payload:
 `allowPasswordAutoFill: True`, `safariAllowAutoFill: True`, five payloads unchanged.

## What is NOT yet proven
The two iPhones acknowledged the install, which means the profile was accepted — it does **not** prove the
AutoFill UI is offering saved passwords. That needs one tap on a real device. On the iPad the install is
queued, not applied. Acknowledged ≠ a live behaviour test (runbook §6).
