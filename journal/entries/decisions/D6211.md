**D6211 · 2026-10-16 · Handy on ZABZ-YOGA is agent-installed; its Win+H binding is why Win+H stopped opening Talk to Text.**

2026-10-16, ZABZ-YOGA. The dictation tool Handy 0.9.8 got onto this Windows box, and the reason Win+H stopped opening Windows voice typing, are the same event.

WHO AND WHY, from the work ledger on the authority (item 288, project housekeeping): owner-queue row 262 was answered 2026-10-15 with "stay on Chrome Remote Desktop and dictate on the Yoga side", chosen over rebooting ZABZ-TECH to get RDP microphone passthrough. The DoD for item 288 was "Handy with local Whisper installed on the Yoga, one toggle hotkey pasting text". A wake-contract shift installed it (preset danger-full-access, deepseek-flash); the session ran from ZABZ-TECH.

WHEN: 2026-10-16 04:45:26 local, when C:\Users\ezabz\AppData\Local\Handy was created. winget ran at 04:45:13 (winget install --id cjpais.Handy --exact --silent, the official package; it pulled Handy_0.9.8_x64-setup.exe from github.com/cjpais/Handy/releases plus KhronosGroup.VulkanRT 1.4.363.0 and Microsoft.VCRedist.2015+.x64). Handy was launched interactively at 05:46:53. The installer's own scratch files survive in %LOCALAPPDATA%\Temp as 14 files named _hk288_*.ps1, written 04:39-04:59. There is NO runbook in git for this: the only committed Handy document is docs/talk-to-text-lakewooechsmini.md, which is the MAC MINI. If those scratch files are deleted the install has no record anywhere.

WHY IT BROKE Win+H: ledger attempt 885 set the binding deliberately, writing "transcribe binding super+h (the Windows-key position - this shift's reading of his 'i need it to start when i push windows h')". But that quoted ask is dated 2026-09-15 and belongs to the OWNER'S WIFE'S Mac mini (decision D161), not to any Windows request. The same ledger entry also flagged the risk and left it unresolved: "whether the OS's own Win+H voice typing keeps the shell shortcut (L1537's blocking guarantee was proven on macOS only)". Consequence measured on Windows 11 Home 26300: HKCU\Software\Microsoft\Windows\CurrentVersion\VoiceTyping does not exist, and Talk to Text never opened.

FIX APPLIED 2026-10-16, reversible: rebound Handy's transcribe action from super+h to ctrl+space (Handy's own default for that action) and restarted the app; verified from its log, "Registered handy-keys shortcut: transcribe -> Hotkey { modifiers: Modifiers(CTRL_LEFT | CTRL_RIGHT), key: Some(Space) }" at 14:53:20. The CMD_LEFT|CMD_RIGHT + H registration line does not recur after the restart.

STILL OPEN, FOR WHOEVER TOUCHES IT NEXT:
1. The installer HARDCODES current_binding = super+h. Re-running _hk288_provision.ps1 or _hk288_settings.ps1 re-breaks Win+H, and so would a future agent copying that script. The live route is now ctrl+space.
2. Ledger item 288 is "blocked", not done, held by owner-queue row 539 (the Chrome Remote Desktop acceptance leg) and row 277 (whether to buy Windows 11 Pro for the Yoga). Both are the owner's, not engineering gaps.
3. The stray scheduled task "hk288-handy" is still registered (ready 23:59 daily) as an artefact of the install. Handy has its own autostart via HKCU Run, so that task is redundant.
4. The owner has not yet said which app he wants Win+H to fire on Windows. If he wants Handy on Win+H, Windows voice typing can never have that chord on this machine; the two cannot coexist.
