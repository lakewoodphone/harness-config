**D234 · 2026-09-14 · Supplier orders get a ledger row, a contact and a documented record; journal import identity is content-based.**

Three decisions made while documenting two supplier money problems on 2026-09-14. Each was mine to make (development / record-keeping, not money, not customers), so none of them was routed to the owner.

**1. A direct supplier order lives in three places, and each has one job.**
- `purchases` in `personal-secretary-mvp/data/secretary.db` is the **ledger** row, so the order can be matched against the bank/Plaid transaction and counted. New `source` values are the vendor slug: `deviceparts`, `globaldirectparts`. Until 2026-09-14 this table had only `ebay` and `amazon` rows, which is exactly why a 167.96 USD PayPal-paid supplier order could vanish.
- `contacts` + `contact_interactions` (ids **635** Cici / Device Parts, **636** Global Direct Parts) hold the **relationship**: who to write to, on which channel, and what was said.
- `lpt-hub/docs/procurement/YYYY-MM-DD-<supplier>-<subject>.md` holds the **narrative and the evidence** — every claim with its Gmail id or Plaid row. A doc is for the record and for a future session; it is never something to hand the owner to read.

**2. The journal's legacy-import identity is content, not the exact hash.**
`entry_hash` stays exact — the stored `sha=` footer and the append alias check depend on it — but deciding whether a legacy entry is *already in the tree* now uses `absorb_key` (= `content_key`: body text with structural lines dropped, heading only as the fallback). The exact hash could not do this job: an absorbed entry is written back with a newly allocated id in its heading, and the migrated copy's title was normalised, so every pass re-imported the same lessons. Measured before: two consecutive `append` calls each imported 189 lessons a second time (378 duplicate files, removed, backup at `/tmp/journal-dup-backup/`). Measured after: 0 unabsorbed, and `append` absorbs nothing.

**3. `pain`, `decisions` and `wins` are now migrated into `entries/` on this machine.** They had never been: the entries tier held only `handoff` and `lessons`, and `state/open-pain.md` had been generated by an older tool that read `log/pain/`. That was a live trap — the current `state` command builds that file from `entries/pain/`, so the next run would have written an **empty pain table** over 25 KB of ranked pain. `import-legacy --apply` absorbed 188 entries (pain 60, decisions 81, wins 47) and `state` now regenerates 58 open pain rows from the canonical tier.

**4. Correction, found the same hour — do not trust the ids in this entry's siblings.** Committing the above exposed that this checkout is on a **divergent journal lineage**. `origin/master` is 3 commits ahead with its own migration of the same flat files: measured 2026-09-14 23:20, of the entries both trees have, **82 of 83 handoffs, all 241 shared lessons, all 54 shared pains, all 76 shared decisions and all 46 shared wins differ byte-for-byte** — the same logical entries, re-written by two migrations. Origin reaches H203/L1085/P131/D141/W106; this checkout reached H115/L1022/P71/D85/W48 before today. `git_max(fetch=True)` did not see origin's ids, so three entries written here collided with different content and were renumbered by hand: **H116→H204, D105→D142, P92→P132**. Nothing was merged: two lineages of the same record cannot be merged blind, and the reconciliation is a deliberate job with the entry files as the unit, not `git merge`. **Until it is done, a journal id is only unambiguous within one machine.** Recorded as pain (the divergence hazard H115 named, now measured).
