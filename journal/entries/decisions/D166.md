**D166 · 2026-09-15 · LPT Google return leg now points at api.lakewoodphoneandtech.com (the apex 404s every /api path).**

## D-AUTH-01 - The LPT Google return leg now points at the host that serves it (2026-09-15)

**Decision.** `GOOGLE_OAUTH_REDIRECT_URI` on the identity authority is now
`https://api.lakewoodphoneandtech.com/api/auth/google/callback`, not the apex
`https://lakewoodphoneandtech.com/...`.

**Why.** The apex is the Cloudflare-fronted storefront and it *deliberately* refuses every `/api`
path (its own 404 body says a relative API request "is therefore a bug"). Google was therefore
delivering every authorization code to a 404, so no Google sign-in of any kind - storefront customer
login or rentals SSO - could complete. The api host serves the route (verified: 302 without params)
and the owner added that exact URI to the OAuth client's authorized redirect URIs
(`776339186207-uf3o15qgm099f79tqt1abibnn4kpi4m2`, client "LPT Customer Portal"): Google now returns
the consent screen instead of `redirect_uri_mismatch` (verified before and after).

**Verified after the change:** `/opt/lpt/.env` backed up to `.bak-redirecturi-20260915T194732Z`;
`lpt-backend` recreated (env_file changes need recreation, not restart); container env shows the new
value; container `running healthy`; `api.lakewoodphoneandtech.com/api/health` 200;
`api.lakewoodphoneandtech.com/api/auth/google/start` now emits
`redirect_uri=https%3A%2F%2Fapi.lakewoodphoneandtech.com%2Fapi%2Fauth%2Fgoogle%2Fcallback`; storefront
200; rentals 200.

**Open finding for whoever owns the storefront frontend (NOT fixed - it is a live customer site and
another session was in that repo today):** the live bundle
(`https://lakewoodphoneandtech.com/assets/index-yK4ovZOA.js`, 3.3 MB, fetched 2026-09-15) contains
`href:"/api/auth/google/start"` - a *relative* URL on the apex, where `/api` 404s. So the customer
portal's "Sign in with Google" still cannot even start, independently of the redirect-leg fix above.
Source: `phone-and-tech-full/frontend/src/features/customer-portal/auth/CustomerPortalAccess.tsx:524`.
The fix is one line (use the absolute `VITE_API_URL` base), but it is a storefront deploy, so it
belongs to the owner of that repo - recorded here rather than done unilaterally.
