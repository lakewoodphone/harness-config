# D-new — The secretary is the always-on half; a FLAG is how it revives a session, and only a registered promise may raise one

**Decided 2026-09-18.** The owner's ask, verbatim: *"this might be one of the final pieces in making you
actually autonomous where you create the secretary server to be your brain when you are not alive,
because no one typed into the GUI … and then when it needs to fully reactivate you in a full dsh
session, it could run you in headless mode back on the desktop … just raise a flag … make sure it
doesn't sit there spawning hundreds of DSH sessions for no reason."*

## The architecture, decided

Three layers, deliberately separate, because they fail in different ways:

| layer | mechanism | who owns it |
|---|---|---|
| **CAPTURE** | `sms-inbox.py` reconciles every text from Twilio every 5 min. The carrier is the log of record. | cron on secratary |
| **ROUTE** | `sms-responder.py`: `auto` → answer now; otherwise one owner-decision row. | cron on secratary |
| **FLAG → WAKE** | anything raises a flag; a dispatcher releases **one** flag as a real headless DSH session on the always-on desktop. | cron on secratary → ssh → ZABZ-TECH |

The reactivation primitive is `dsh --profile headless "<task>"` — one task, printed result, exit.
Verified end to end; the session runs where DSH is installed, never on the server.

## The rule that keeps it from becoming a session factory

> **A flag is raised only by something that knows there IS work. Nothing on a timer may raise one.
> A dispatcher releases; it never invents.**

The sharpest expression of that rule is `await`: **when we send something and expect something back,
we register WHAT TO DO WHEN THE ANSWER ARRIVES.** A promised reply is the one signal that is
unambiguously work. Everything else — a text from someone who is not cleared, a monitor crossing a
threshold — is a *decision for the owner*, and belongs in the owner queue, not in a session.

**Decided:** `await` is the flagship flag source. Other sources must earn their place by showing that
a human would otherwise do nothing and that a session would actually change the outcome.

## The guards, and why each exists

Dedup by subject (one live row per issue) · cooldown per subject · daily cap on releases ·
per-source hourly cap · night gate for low priority · a kill-switch file · a lease so a dispatcher
that dies does not strand a row · an attempts cap so a failing subject stops forever · a heartbeat so
**"nothing needed waking" is distinguishable from "the wake system died weeks ago"**.

That last one is the guard this operation needs most: its oldest failure is reading a live-looking
thing as work-happening. A silent wake system is the end of autonomy, and it would look exactly like
peace. So the dispatcher writes a heartbeat on every run including the quiet ones, and the owner
digest reports liveness **before** it reports the queue.

## Honest limit, decided

Per-release spend is **unmeasured**: `dsh --profile headless` exposes no usage or cost output.
Therefore the dollar cap is inert and the release-count cap is what actually protects the machine
until spend is measurable. Recording the number we cannot measure would be the same lie as the
stale-database crisis (H33/L165 class), so it is recorded as unmeasured.

## Evidence

Live, not configured: Weinberg replied at 03:02:55 on 2026-09-18, the server filed a flag, the
dispatcher ran a headless session on the desktop with nobody at a keyboard, and the session's output
came back (H549). The flaw it exposed — the session answered nobody — is why the await prompt now
requires a reply to the human.
