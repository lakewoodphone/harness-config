**D82 · 2026-09-14 · 2026-09-14 · Ghost-agent mappings, hand-port as the interim deploy method, and how the credential-named path is blocked.**

**D · 2026-09-14 · The four ghost agent ids map to `dept_home_life` / `orchestrator`, and `dept_executive_assistant` maps to the orchestrator rather than to a department**

The reconciliation audit produced evidence for each mapping, and I added four entries to
`_LEGACY_ASSIGNMENT_AGENT_ALIASES`: `dept_home_and_life` and `dept_personal` →
`dept_home_life`; `dept_ceo` → `orchestrator`; `dept_executive_assistant` → `orchestrator`.

The first three are not guesses: the alias dict already mapped the sibling `home_life` →
`dept_home_life`, and the system had itself reassigned `dept_home_and_life` → `dept_home_life`
on 2026-09-11 (`activity_log` 303889). `dept_ceo` follows the established
`executive → orchestrator` precedent.

`dept_executive_assistant` is the one real judgement call, and I decided against the audit's
own recommendation. The evidence pointed to `dept_home_life` (the work is personal, medical),
but the single live row it would capture is the CHEMED/radiology owner-review plan. Routing
owner-review material of that kind into an autonomous department that can *act* is worse than
routing it to the orchestrator, which is where owner escalation already lives; and the item is
separately tracked as an owner question, so nothing is lost by not auto-assigning it to a
department. Conservative mapping wins where the failure mode is "an agent acted on medical
material it should have escalated".

Also decided in the same change: `workforce.delegate_task` now canonicalizes the target agent
at the write boundary. The root cause was that nothing between the LLM's invented department
name and `goal_plans.assigned_agent` validated it — only a reactive alias dict cleaned up
afterwards, which is why the seven names patched on 2026-08-31 stopped appearing and these four
did not. Prevention belongs at the single writer.

**D · 2026-09-14 · Hand-porting into the live checkout is the sanctioned interim deploy method, and every hand-port must carry a per-anchor gate**

`deploy.sh` cannot run on a diverged HEAD, so there is no pull-based path. Hand-porting is
consistent with **D41b**, which already recorded that the only way to edit some files is
directly on production.

The method is fixed from here: back up the touched files, apply edits by exact string
replacement where **every anchor must match exactly once or the script refuses and writes
nothing**, compile-gate every touched file, restart, poll `/health` until 200, and record the
deploy in `.runtime/deployed-commits.log`. Both ports are kept in
`harness-config/scripts/port-work-mode-fix.py` and `port-ghost-fix.py` as the reusable pattern.

Rejected: `git apply --3way` against this tree. It reported "Applied ... with conflicts. Falling
back to direct application" while `--check` exited 0, and wrote conflict markers into a live
file. The compile gate caught it; the check was not a check.

**D · 2026-09-14 · The credential-named path is blocked with `.git/info/exclude`, not a tracked `.gitignore`**

A junk directory at the repo root is literally named
`postgres:/<rds-user>:<password>@<host>:5432/<db>`. Listing it in `.gitignore` would put the
credential into a **tracked** file, making the cure a new leak. Added `postgres:*` to
`.git/info/exclude` instead: it is untracked, local to the checkout, and verified to work
(`git check-ignore -v "postgres:"` matches; the path is gone from `git status`). Deleting the
directory is destructive and is not done without an explicit per-action yes on that exact path.
