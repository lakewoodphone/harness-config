**D — ZABZ-TECH keeps Fast Startup OFF, and a rebooting machine gets driven from a machine that is not rebooting.**

Two decisions taken 2026-09-20 while resolving the Windows Hello / slow-restart fault on ZABZ-TECH.

**1. Fast Startup stays disabled (`HiberbootEnabled = 0`).** Session 1 set it `1 → 0` to force a genuine cold boot so a staged firmware capsule would apply; the original value is saved at `C:\Users\ezabz\Code\_diag\hiberboot-enabled.orig` (=1) and restoring it is a one-value registry change. I am keeping it off because on this box a full cold boot is what keeps VSM/Hello state deterministic, and because the owner's actual symptom was about *restarts* (where Fast Startup is irrelevant anyway) and about a pre-bootmgr firmware delay that Fast Startup does not touch — that delay is now 25 s, down from 166–178 s. Accepted trade-off: a shutdown→power-on start no longer resumes from hiberfil, so it is slower by roughly the Windows boot time. Reversible, recorded, and nothing else depends on it. This is a dev/ops call, not an owner call.

**2. When a fix requires rebooting a machine, drive it from a different machine.** The first attempt at this fault ran *on* ZABZ-TECH, so every reboot killed the agent mid-fix and it could never observe the boot it had just caused — which is precisely the class of boot the fault lives on. Taken over from ZABZ-YOGA over Tailscale (`ssh zabz-tech-ts`), the driver survives the target rebooting underneath it and can schedule a restart, wait for the machine to come back, and read the post-boot evidence in one uninterrupted turn (startup task `ZabzTech-BootWatch` logs the state, a poll-from-here background job collects it). **Adopt this as the default for any machine-repair work whose method involves reboots**: never be a passenger on the machine you are restarting.

Recorded, with the full evidence trail, in `harness-config/docs/mesh/117-zabz-tech-hello-and-boot.md`.
