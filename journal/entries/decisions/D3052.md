**D-new A · 2026-10-12 · ZABZ-YOGA/secratary-cloud · The search subsystem's canonical home is `harness-config/scripts/find-anything/`, and the engine is never to live only in `~/bin`.**

Decided 2026-10-12 during the search audit (journal H3571, lesson L-new-A).

**Why.** The whole surface existed on exactly one disk. Measured: the engine
`/home/zabz/bin/find-anything` was **89 lines ahead of its own git ref** — the deployed improvements
existed in no commit anywhere — and the index builder and the tool body were in equally untracked
places (`data/tools/` is gitignored). `harness-config` reached every machine; the search system was on
one. H3565 had already paid for this lesson once with `commsindex.py`, which existed only on the box
being frozen and had to be restored byte-identically from a `.bak`.

**The decision.** `harness-config/scripts/find-anything/` is the source of truth: `find-anything` (the
engine), `build-indexes.sh`, `search-tool.py` (the `data/tools/search.py` body),
`register-search-tool.py`, `install.sh`, `check-faindex-freshness`, `make-crontab-fragment.sh`. Nodes
are provisioned from it with `install.sh` (repo → host, sha-verified, `.bak` before replace), the same
direction `scripts/guards/install.sh` and `scripts/wake/sources/` already use. **Editing the copy on a
node is not a deploy**; the repo copy is what a future node gets.

**Consequence accepted.** The office box's copy is now behind the canonical one (it is frozen, so it
will not be updated). The authority's copy is the reference.

**D-new B · 2026-10-12 · Journal search means "every term, somewhere in the entry". `--all-words` is the opt-in strict reading.**

Decided 2026-10-12 (journal H3571, lesson L-new-C). Supersedes the previous silent default, which
required every query term **on the same line** and therefore answered `exit 1 — the scope was searched
and holds nothing` for ordinary multi-word queries. D2983 recorded that defect on 2026-10-09 as a
reason to prefer `unified-search`; it is now fixed at the source rather than worked around.

**The default** is entry-level AND over whitespace-split terms, because a query arrives as one argv
element from `ps_search` and as several from a shell, and both must mean the same thing.
**`--all-words`** keeps the strict line-level reading for a caller who genuinely wants words on one
line, and **`--regex`** remains the tool for adjacency. Verified: the D2983 pair now returns hits, a
genuine negative still exits 1, `journal.py check` reports 0 errors, and latency is 399–490 ms.

**Not decided, and flagged as open.** Whether to point the `fast-search` skill at `unified-search`
instead of `find-anything` — the sequence D2983 and H3411 both describe as "only after the criterion is
met". This session did not reopen it, because the shipped skill still points at `find-anything` and
that surface was, until today, entirely broken on the authority.
