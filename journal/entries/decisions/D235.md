**D235 · 2026-09-14 · 2026-09-14 · Supplier orders are ingested before they are watched, and evidence must name its own order.**

Two development decisions made on 2026-09-14 while closing the hole that let a 167.96 USD supplier order go missing for 148 days. Both are mine (engineering and record-keeping, not money or customers), so neither was routed to the owner.

**1. Ingest before watching — the ledger must be fed, not hand-filled.**
`supplier-delivery-watch.py` can only age orders it can see, and `purchases` had only ever been fed by eBay and Amazon order mail, so the order that went missing had to be typed in by hand. The pipeline is now `supplier-order-ingest.py` (Gmail → `purchases`, per-supplier regexes, one account per supplier, PayPal transaction id captured) and then `supplier-delivery-watch.py` (purchases → age → verdict → task). Cron runs ingest at `10 */6` and the watch at `17 */6`, in that order, and the ingest's exit code is non-zero when a confirmation cannot be parsed, because an unparsed confirmation is an order the watch cannot see.

**2. Evidence must be tied to ITS order, and a task is finished by its action.**
- `contact_evidence` matched off-mail tracking on the SUPPLIER, so order 62415's DHL waybill was attached to order 60779 as well. Both belong to Device Parts; only one shipped by DHL. A false "shipped" hides a loss where a miss is merely visible, so tracking is now accepted only from an interaction that names the order number. The same rule retired the amount-as-evidence habit: the amount is still searched (it is what proved delivery before any of this existed), but a transaction id, written by the ingest and unique to the order, is searched first and recorded as the match.
- A watch run whose evidence could not be gathered exits **2**, not 0. An empty result is a refusal, not health — enforced by the exit code so a timer cannot mistake it for a clean pass.
- The work-session step mirror no longer writes `progress_pct=100` into its task (capped at 99). Otherwise `lifecycle_sweep` closes the task the moment the session ends, which is how #25106 was retired 26 minutes after creation with nothing sent (pain entry of the same date; owner question #8's shape).
