## 2026-10-08 · Three decisions taken while repairing the shop's money & customer reporting

None of these were routed to the owner: all three are engineering decisions inside the mandate, and
each is recorded here so it is not relitigated. Each carries the evidence that chose it.

### 1. A "finished job" means `orders.status = 'READY_FOR_PICKUP'`, stamped by `completedDate`

CHOSEN from the data, not from taste. Candidates measured per month, Apr-Oct 2026:

| candidate | monthly yield | why not |
|---|---|---|
| `status = 'COMPLETED'` | 0 every month | the value does not exist in the live enum |
| `completedDate IS NOT NULL` alone | 44,76,73,78,**188**,22,8 | set on `UNFIXABLE` (93/96) and `CANCELLED` (83/87), so it counts abandoned work as done (August 114 vs 89 real) |
| `pickupReleasedAt IS NOT NULL` | 0 every month | only 2 rows all-time |
| `paymentStatus = 'CAPTURED'` | 16,5,5,1,3,0,0 | only 54 of 319 payment rows carry an `orderId`; unusable per order |
| **`READY_FOR_PICKUP` + `completedDate`** | **23,70,73,77,63,16,3** | **chosen** |

Adverse closures (`CANCELLED`, `UNFIXABLE`) are excluded by name, and the exclusion set is resolved
from the live enum at run time. Where a period cannot be placed because `completedDate` is absent
(53 orders), the report says "Jobs done is a lower bound" rather than silently counting them as zero.

### 2. Weekly cadence, Sunday 05:35 — not daily

Installed in the authority's crontab as `35 5 * * 0` via `cron-wrap.sh lpt-business-report`, payload
verified byte-for-byte against the original command, crontab backed up to
`~/crontab.bak-lptreport-20261008T224141Z`.

Sunday 05:35 sits after the 04:30 nightly Plaid sync and after the 05:00 daily-finance-sync, so the
week's money has landed before the report is drawn. Weekly rather than daily because the report grain
is monthly, the owner's own recorded view is that *"daily briefings are completely useless"*
(`shift-report.py` docstring), and the on-demand `lpt-analytics.py today` view now covers the
same-day question without a second scheduled job. A daily run stays available if the Plaid lag
turns out to need it.

### 3. One Linux runner in the repo, and every report tool remains independently runnable

`scripts/lpt-business-report.sh` (new) replaces `scripts/lpt-monthly-analysis.ps1`, which is
PowerShell and therefore cannot run on `secratary` — the machine that holds the accounting DB, the
venv and the production DSN. A runner that cannot run where the data lives is why five weeks passed
unnoticed.

It is written so that **a failing step does not stop the pass** (a report tool that dies on the first
error tells you nothing about the other ten), and it separates a **crash** from a **finding**: an
audit that exits 1 because it found an anomaly gets status `findings`, not `FAIL`, because crying
wolf every run is how a status column stops being read.

Deliberately NOT done: no step was folded into a single "do everything" script. Each tool keeps its
own entry point so a failure can be reproduced in isolation, and the old PowerShell file was left in
place rather than deleted, since the Windows machines are still in the estate.
