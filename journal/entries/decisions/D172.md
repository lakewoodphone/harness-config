**D172 · 2026-09-15 · P164 root cause found: IP Helper crashes and takes Tailscale with it, and a 5-minute watcher now repairs both.**

2026-09-15, ZABZ-TECH. The evening's two misdiagnoses were one fault.

ROOT CAUSE, MEASURED
- sc.exe qc Tailscale and Get-Service both show Tailscale's required services as Dnscache,iphlpsvc,netprofm,WinHttpAutoProxySvc. IP Helper is a HARD DEPENDENCY of Tailscale.
- System event log: 'The IP Helper service terminated unexpectedly. It has done this 1 time(s). The following corrective action will be taken in 120000' at 2026-09-15 15:40 local. iphlpsvc's configured recovery restarts IP HELPER ONLY (RESTART, 2 min) - it never restarts the dependent.
- So from 15:40 local: IP Helper crashed, Windows stopped Tailscale as its dependent, IP Helper came back two minutes later, Tailscale did not, and from then on EVERY *.tail93e6e6.ts.net name failed to resolve on this machine. That is why ssh secratary-ts, the harness-config git remote and the hop to ZABZ-YOGA all failed, and why I first wrote 'yoga is unreachable' about a laptop that was fine.
- Reproduced deliberately at 16:56 local: Stop-Service iphlpsvc -Force (which also stops dependents) dropped the LAN health endpoint to 'refused' and left Tailscale stopped - the same signature.

FIX, IN harness-config SO EVERY NODE CAN TAKE IT (not in ~/.dsh, which is not the source of truth)
- scripts/ensure-mesh-prereqs.ps1: repairs IP Helper FIRST, then Tailscale (repairing the dependency before its dependent is the only order that converges in one pass), then re-adds the missing netsh portproxy entry that publishes the secretary API on 192.168.50.138:8002. It writes ~/.dsh-sync-status/mesh-prereqs.json in the same idiom as autosync, logs to mesh-prereqs.log, exits 1 only when something is still broken, and never stops a service or touches application state.
- scripts/mesh-prereqs.json holds the per-host config; ZABZ-TECH is the only host with iphlpsvc + portproxy entries today.
- Installed on ZABZ-TECH as the scheduled task 'DSH Mesh Prereqs (5m)' (S4U, highest, every 5 minutes, 3650-day repetition). Verified two ways: a clean run reports iphlpsvc:running tailscale:running portproxy:present, and a deliberately broken run (iphlpsvc stopped by force, LAN refused) came back 'result=repaired' with LAN /health 200 afterwards.
- STILL TO DO, and the reason P164 stays open: only ZABZ-TECH has the task. ZABZ-YOGA, ZABZ-TECH-LAPTOP, the mac mini, the linux PC and the authority have no equivalent check, and yoga is the machine whose tailnet name people notice first.
