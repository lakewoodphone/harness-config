**D232 · 2026-09-16 · Acceptance-harness rules: the one FAIL/SKIP test, a hermetic mesh for controllability, and why the frozen scoring formula is not asserted.**

DECIDED 2026-09-16, stream S7 of the mesh program (scripts/mesh-e2e.ps1, docs/mesh/78-acceptance.md).

1. FAIL vs SKIP has exactly one test: does the capability exist ANYWHERE in the fleet yet? No -> SKIP
 and name precisely what would have to exist. Yes -> every gated node must have it, so a node that
 lacks it is a FAIL. Written once, in the script, so it cannot drift. A node with NOTHING published
 on :443 is a SKIP (it is not a gated node yet); a node whose gate ANSWERS but does not serve the
 route (404) or whose published URL has no backend (502) is a FAIL.

2. An acceptance test that must prove controllability gets its own hermetic mesh. §4.2 says "force
 that node's capacity to 0" and §4.6 says "a mesh with 5 slots" - neither is possible on a live
 office desktop. So steps 2/3b/5b/6 start a REAL broker (packages/mesh-broker) against REAL stub
 gates on port 0. A second, non-obvious reason: an EMPTY BODY is not the only way to corrupt a
 test - 30 placements fired at the DEPLOYED broker would leave 30 live leases on real nodes for 15
 minutes and mislead every other stream. The live broker gets exactly one question, and the lease
 is released immediately (asserted, not assumed: `released=true`).

3. The scoring formula frozen in §2.2 is NOT asserted by the harness, deliberately. broker.js grew
 coreSlots/swapApplied/"effective slots" and cites an "AMENDMENT 4" that appears nowhere in
 docs/mesh/. If §2.2 was amended, the doc must say so; if it was not, that is interface drift. But
 encoding the frozen formula as a new assertion would be inventing an acceptance criterion beyond
 §4 - the same class of error as redefining success. Report it to the manager; do not silently
 strengthen or weaken the spec you were handed.
