**D2325 · 2026-09-22 · A deferral the owner states must be recorded in the queue, or the kernel counts it as a missed deadline.**

Two kernel findings came in on the badge (2026-09-22 14:51Z): HIGH `comms_freshness`
and HIGH `owner_queue`. Both were **false**, both in the same way — a metric was
read as a fact about the system when it was only a fact about a row — and both
are now fixed and verified. Final report: **15/15 ok, attention 0** (was 13/15).

## 1. `comms_freshness` — the poller was fine, the inbox was quiet

Claim: *"email triage stale 3.1h (expected < 2h) — the Gmail poller has stopped
classifying new mail."* The poller had not stopped. At the moment of the alert,
`data/autopilot_state.json` on secratary showed `subsystem_health.gmail_decisions
.last_ran_at` 19 minutes earlier with `last_status=ok` and 0 consecutive
failures, and `last_gmail_poll_at` 0.3h old against a 900s interval. Poll cadence
measured over the last 10 runs: one every 50-60 minutes, no gaps, every one `ok`.

The check read `MAX(email_triage_log.created_at)`. That table is written only
when a message **is** triaged, so a quiet hour ages its newest row exactly as a
dead poller would. It is the same INSERT-only trap that `dialpad_call_full
.fetched_at` and `dialpad_sms_cache.fetched_at` already had heartbeats added for
— the third instance of one mistake.

Fixed (ceo-kernel `e2fbaec`): email triage left the staleness loop and is judged
on the poller's own persisted heartbeat plus a real backlog count — entries the
poller has held longer than the window with no triage row. A heartbeat cannot see
a poller that runs and whose classification never completes; the absent row can.
`SENTINEL_AUTOPILOT_STATE_FILE` lets tests point at a copy, so no test writes live
state. Seven cases run against a copy in /tmp, all correct: healthy ok; poll 9.3h
stale -> HIGH naming the poller; status=failed -> HIGH; 2 held messages + 1 fresh
-> HIGH and counted exactly 2; poll time missing -> HIGH; state absent -> HIGH;
state unparseable -> HIGH.

## 2. `owner_queue` — a deferral he stated is not a missed deadline

Claim: *"15 owner decision(s) queued, 2 blocking item(s) past 3d."* Both of the
two were items he had already seen and put off **in his own words**, and the
queue had no field to record it:

- **#100** Weitman laptop — "i'll look into this tomorrow" (2026-09-22), 4.5d
- **#127** Wilner SD card — case file: "deferred by the owner until after Yom
 Kippur", 2.0d

The row could only say "unanswered and old": true of the row, false of him. No
answer could clear the finding — it would have stayed high for the length of his
own deferral, which is how a real item gets buried.

Fixed in two halves, because the field had to exist before anything could read it:

- `~/bin/owner-queue.py` on secratary gained `defer <id> --until <date|tomorrow|+3d>
 [--note]` and `--clear`, plus `deferred_until` / `deferred_at` / `defer_note`.
 `CREATE TABLE IF NOT EXISTS` never alters an existing table, so `connect()` now
 runs a `PRAGMA table_info` migration. Backup:
 `owner-queue.py.bak-deferral-20260922`.
- ceo-kernel `f5db058` reads the column **only if PRAGMA says it exists**, so an
 older database cannot fail the read. Deferred rows stay pending, sort last, and
 are reported as "deferred by him and excluded from the overdue count". The
 exclusion covers `blocking_over`/`over_age` only — a deferral that has **expired**
 is its own reason to raise, ahead of the others.

Deferred, with the reason kept in `defer_note`: **#100** -> 09-23, **#127** ->
10-02 (after Yom Kippur), **#78** (mother's line port, whose own text says it is
needed "in about a week") -> 09-29. Three rows only, and **no row was answered,
resolved or dismissed to make a number go green** — the journal mirror still lists
all 15 as open, and the next live decision is #128 (Golembick, 2.0d).
