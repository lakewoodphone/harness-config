**D203 · 2026-09-16 · Program rule: remove waste first, reduce capability last - so the capability knobs stay untouched.**

## The operating rule for this program (owner's words, 2026-09-15)
"Focus on getting rid of waste. If reducing power at the end of the day is needed in order to make
the system run smoothly, then we'll have to reduce power, but that just isn't the first thing we're
going to do. First we're focusing on reducing waste as much as possible, and then if it's still not
enough, we can do whatever is needed and actually reduce power. And we want to do as least as
possible of that."

Corollary for every change in this program: **queue rather than amputate.** An admission-governed
budget that delays work is acceptable; a smaller cap on what an agent may do at once is not, unless
measurement proves it is the only remaining lever.

## Changed (waste only) — 2026-09-15
1. **Journal lock → OS lock** (`journal\tools\journal.py`): removes the unlink-based stale-break race
 that produced the 161-collided-id incident; "stale" no longer exists because the kernel releases
 the lock on process death. Verified: 3 writers zero overlap; a force-killed holder released in
 0.00 s. Also: the read path (`status`) no longer triggers the mutating `questions` refresh, so
 reads cannot create writer contention.
2. **MCP direct-node + stable install** (`presets\zabz\agent.cordis.yml`, `mcp_launcher.py`,
 `C:\Users\ezabz\.dsh\tools\mcp`): four process layers per server → one; no npm registry resolve
 per start; the child DSH spawns is now the server, so killing it works.
3. **`dsh-reap.ps1`** reaper for parentless harness processes and stale MCP generations (applied: 4
 generations reaped, engine protected, 0 false positives).
4. **`NODE_COMPILE_CACHE`** machine-wide: cold 1608 ms → warm 446 ms per Node start.
5. **`LOCK_WAIT_SEC` 240 → 110 s**: below the 120 s harness kill, now safe because a killed holder
 releases the lock.

## Deferred, in the order I would do it (with the reason for the order)
1. The **append critical section** (two full-repo `git grep`s + a 6.4 MB `journal.db` rebuild inside
 the lock): the biggest remaining journal latency, and the only item whose fix touches the
 id-allocator — so it needs the 6-way concurrency selftest before it lands. Do not rush this one.
2. **Persistent shell** (`dsh-tool-pwsh-persistent`, installed but not mounted) — removes a ~57 MB
 runner process plus a shell spawn per tool call. Waiting on the parameter-by-parameter
 behavioural diff so no capability is lost.
3. **A tool deadline + short-TTL cache for `list_agents`** and a **health surface** — no
 `timeoutMs` on that tool means it can hang the UI forever, and every call re-scans ~372 session
 files serially on the shared event loop. Being built as a host plugin so an npm update cannot
 erase it.
4. **SQLite**: `BEGIN IMMEDIATE` for every read-then-write, gate `owner-queue.py`'s schema
 bootstrap behind `PRAGMA user_version`, and check `sqlite_version()` (a WAL-reset corruption bug
 affected 3.7.0-3.51.2, fixed 3.51.3, and needs exactly two connections writing or checkpointing
 on one file — this workload).
5. **Cost**: prefix stability for the provider's context cache, MCP tool-schema size, retry policy,
 compaction threshold — only after the token accounting is measured rather than guessed.
6. **Capability budget, only if 1-5 are insufficient** — and then as a queue, not a cap.
