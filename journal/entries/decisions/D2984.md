**D2984 · 2026-10-09 · Always-on authority moves to a rented Ashburn CCX13; compute stays on the machines he owns.**

## D — The always-on server becomes a rented box; compute stays home

DECIDED 2026-10-09 by the owner, from the analysis in docs/mesh/121-always-on-server.md
and provisioned per docs/mesh/122-cloud-authority-provision.md.

THE DECISION: one Hetzner CCX13 in Ashburn (ASH1) - 2 DEDICATED vCPU, 8 GB RAM,
80 GB - at $50.99/mo + $0.60 IPv4 = $51.59/mo, plus object storage (~$2/mo) for the
201 GB backup archive. It becomes the always-on authority: secretary.db, secretary-api,
the dashboard, mesh-broker.service and a DSH engine with /mesh/health. The office
`secratary` box stays as a compute worker and is not deleted. The office DB is frozen,
not deleted, as the rollback.

WHY THIS SHAPE AND NOT MORE HARDWARE (the arithmetic is in 121 §4 and was already
measured before this decision): the mesh is NOT short of compute. The laptop alone
covers ~135 concurrent turns by memory; non-laptop free memory sums to 70.3 GiB
~= 172 turns; the largest fleet ever actually run is 3 children; and the real ceiling
is ~10 reliable dispatches (5 nodes x 2 children). Renting agent compute would buy
capacity 10-13x above what binds. docs/mesh/118-hardware-plan.md rejected exactly
that in eleven places and it is right. What DOES need to be always-on is the 22.9 GB
database, the API and the broker - state, not compute.

WHY ASHBURN AND DEDICATED CORES, over the cheaper CX43 (8 shared / 16 GB / 160 GB
/ ~$18): the office is in New Jersey, so Ashburn is 10-20 ms against Falkenstein's
90-100 ms (79 §3.1); and the box serves a database with a documented 8,290
"database is locked" events per week, so shared vCPUs are the wrong saving on a
machine chosen BECAUSE the complaint is speed.

THE SECOND DECISION, and it is the one that stops this recurring: the authority must
never again be the only door. docs/mesh/119 made the placement broker optional for
dispatch; this moves the control plane off a box whose power is a coin flip; and
Stage 6 of 122 adds a watchdog OUTSIDE the office that reports WHICH HOST ANSWERED.

OPEN, and it gates the final disk size: the DB measures 22.9 GB against a documented
490 MB on 2026-09-14 (47x in under a month, unexplained). If it is a runaway writer,
fix that BEFORE moving it. If the growth is real, CPX42 (8/16 GB/320 GB, $81.99) is
the honest size instead of 80 GB. db-growth.mjs is sampling it.
