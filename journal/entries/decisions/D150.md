**D150 · 2026-09-14 · Her agent's learning: one shared journal, her machines append to it, provenance by host.**

DECIDED 2026-09-15, on the owner's instruction that her agent must be "fully self learning adapting and getting better", not merely able to read the company's history.

THE SHAPE: her machines check out the SAME harness-config repo as every other machine, so her agent gets the whole journal tree -- lessons, pain, decisions, handoffs, wins -- and the same journal.py I use. One learning substrate, not a parallel one that would rot.

WHY A SHARED CHECKOUT RATHER THAN A COPY: a copy cannot be appended to in a way anyone else sees. The repo is the only structure in this fleet that already survives a session, and her agent's lessons have to reach the brain that later sessions read.

PROVENANCE, WHICH IS THE OWNER'S ACTUAL BOUNDARY: journal entries carry a host field (the tool records it), so an entry her agent writes is stamped LAKEWOOECHSMINI or DESKTOP-FGV6KMH and is distinguishable from mine without any convention. Same mechanism as the session archive (source_machine inside a PRIMARY KEY) and the git trailers (Dsh-Machine). Labelling, not restriction -- exactly as instructed.

DELIVERY, MEASURED: the Mac mini can git clone/pull from secratary-ts:/home/zabz/harness-config.git and can reach https://api.abletelsolutions.com. Verified by doing it: clone succeeded, fetch --dry-run succeeded, harness-sync --dry-run verified. Her laptop has no Tailscale (logged out) but reaches the public API, so its copy is delivered through the exec channel instead.

HER AGENT CAN ALREADY READ MY CHAT HISTORY: ps-system.mjs search "cost pill" run ON the Mac returned rows from MY secratary sessions. That is the "access to our logs systems and sessions and chat history" requirement, demonstrated rather than configured.

WHAT REMAINS: scheduling the pull-and-apply so this stays current without me, and the session-ingest schedule on the laptop.
