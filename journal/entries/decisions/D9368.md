**D · 2026-10-22 · Door codes rotate every 14 days, the message is part of the rotation, and the apartment door is inside it.**

Owner, verbatim: *"they are supposed to be rotated evry 2 weeks, they can only rotate if we get a text
update with the nw pin and the apartment door pin has to be part of it"*. This supersedes the staging
note in D3148, which rotated three helpers and explicitly did not touch the deadbolt.

## What the audit found (live, this session)

- **The rotation was already every 14 days in one place and never in another.** Live HA
 `house_access_pin_auto_reset` (access_control.yaml:1372) had been changed on 2026-10-18 to
 `now().timetuple().tm_yday % 14 == 0`, not the `% 3` the 2026-10-18 session recorded — the live
 file is the truth and the note was stale. It fires 03:15 and notifies `notify.mobile_app_zabz_waze`.
 Everything else — admin, parent, Yocheved — had not moved since 2026-10-17T23:58Z, because
 `/opt/phoenix-pin-rotation` was staged inert and nothing ever enabled it.
- **The apartment door was outside the rotation.** `lock.0x002446fffd0a4705` is Zigbee2MQTT
 (Z2M), `99140-031`. `Deadbolt - PIN Sync and Activity Logger` (on) syncs admin→slot 1 and
 worker→slot 2 only. Slots 2 and 3 hold unrecorded random codes from 2026-10-18; **slot 4 held a
 code last used by an unidentified user on 2026-10-01** — a live credential nobody could rotate.
- **The staged script would have texted a stranger.** It sent to +17326747491 as "the father". The
 comms record says otherwise: 4 communications, and the last inbound reads *"I believe you sent
 this message to the wrong number"*; the June call transcript has the holder saying he bought the
 phone from someone else. 732-674-5878 IS the mother (106 communications, address book "Mom
 Zabrowsky"). A father number therefore has to be supplied, not assumed.
- **The write path was unverified.** Nothing proved a deadbolt code had been accepted. Measured
 tonight: publish `pin_code {user:3}` → 5 s later the lock fires `commandSetPinCodeRsp status 0`
 and Z2M republishes `action: pin_code_added, action_user: 3`; `sensor.apartment_door_smart_lock_action_user`
 moved to `3` with `action_source_name: rf` at 2026-10-22T22:30:23Z. That sensor is the proof the
 authority can read; `sensor.0x…_pin_code` never updates and is not usable.

## What was changed

1. `/opt/phoenix-pin-rotation/rotate.py` — rewritten. Rotates parent (4), room (4), admin (6),
 Yocheved (6) in one run; writes deadbolt slot 1 = admin and slot 4 = the parents' code; verifies
 each slot from the lock's own event; sends mother + owner; rolls back EVERY helper and BOTH slots
 on any write, confirm or delivery failure. `--dry-run` and `--no-send` now write nothing (the
 previous `--no-send` wrote codes and skipped the messages, the worst of both).
2. `phoenix-pin-rotation.timer` — daily 13:40 UTC tick (was 04:15) because a rotation now texts
 people; the script still owns the 14-day gate. `TimeoutStartSec` 180 → 420 so a slow lock answer
 cannot be killed mid-rotation.
3. Live HA `house_access_pin_auto_reset` set `initial_state: false` (backup
 `access_control.yaml.bak-pinowner-20261022`), reloaded, now reads `off`. ONE owner per credential:
 `/opt/phoenix-pin-rotation`. Two writers on one code means two values and a text that is wrong
 within a day.
4. `README.txt` rewritten so the next person reads what the script actually does.

## Still his

The father's number (`PHOENIX_FATHER_PHONE` in `/opt/company/.env`) and the one activation command,
which sends the first messages: `systemctl enable --now phoenix-pin-rotation.timer`.
