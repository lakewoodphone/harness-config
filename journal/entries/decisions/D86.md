**D86 · 2026-09-14 · The filter gets its own website on an LPT subdomain, signing in with LPT identity through a server-side BFF — and a missing configuration value must close a door, never open one.**

Full record: `kosher-filter-ai/decisions/38-web-app-and-onboarding.md` (D38-01…D38-05), plan in
`docs/WEB_APP_AND_ONBOARDING_PLAN_2026-09-14.md`, evidence in `docs/ENGINEERING_STATE_AUDIT_2026-09-14.md`.
The owner's instruction: *"audit what still has to get done and write engineering docs to plan it out then
integrate into the lpt signin flow, but it will be its own website, also make sure there is a full good
onboarding flow for users and more."*

*The decisions, each with the fact that forced it.*
1. **The site is a separate application, on a `*.lakewoodphoneandtech.com` subdomain, with a server-side
 BFF.** The subdomain is not cosmetic: LPT's `lpt_refresh` cookie is scoped `Domain=.lakewoodphoneandtech.com`
 and LPT's `return_to` allowlist covers its subdomains, so a subdomain choice is inside both circles and the
 primary integration needs **no LPT-side change**. The broker hostname does **not** move — it is baked into
 already-provisioned phones — so the site takes a new subdomain. Direct browser→broker cross-origin was
 rejected: it needs `SameSite=None`, credentialed CORS and CSRF defence across a 338-route API never designed
 for it, i.e. more work *and* a worse posture.
2. **LPT is the identity, and the broker's household-admin account is an inner machine-held session.** The one
 surface is `POST /api/auth/sso/assert` — shared secret, server-to-server, reads `lpt_refresh`, non-rotating
 by design. There is no OIDC, no JWKS, no scopes and no consent screen, and a shared user table is neither
 possible nor wanted. Both the LPT path and the site's own email+password+TOTP path sit behind one
 `identify(request) -> LptUser or None`, so the shim is the only thing that changes.
3. **`lpt_operator_session` and `lpt_refresh` share a name prefix and nothing else** — different cookies,
 signature schemes, secrets and scope. Recorded because the coincidence invites exactly the wrong assumption.
4. **Onboarding is a product surface with two halves, not a bench runbook** — nine stages, derived from server
 state so it is resumable, with stage 5 (see it block something, and see it fail *closed*) and stage 7 (the
 expectations and limits) mandatory.
5. **No page may assert anything the code does not do.** The site's copy joins the existing public-claims test,
 so no accuracy percentage, the deny-first sentence present, the privacy framing structurally honest.
6. **Operator auth now denies by default.** `app/auth.py:405-431` granted `super_admin` to any caller whenever
 `LPT_WEBHOOK_SECRET` was empty, before reading credentials — the trigger being *any* Basic header
 (`curl -u anything:anything`). Production was **not** exposed (`/admin` → 401, probed 2026-09-14 11:42Z), so
 this was a latent footgun rather than an incident. The old behaviour survives only behind an explicit,
 default-off `LPT_ALLOW_INSECURE_DEV_ADMIN`, and startup logs the consequence either way. Verified: 19 passed,
 0 failed.

*The general rule this establishes, and the reason it is a decision rather than a bug fix:* **a missing
configuration value must close a door, never open one.** Every future surface is held to it.
