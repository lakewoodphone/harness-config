**D137 · 2026-09-14 · Browser automation on the authority runs headed on a persistent Xvfb display.**

The authority runs browser automation against a persistent Xvfb display, not headless.

WHY: chrome-headless-shell segfaults (signal 11) on the anti-bot interstitial that
Amazon and eBay serve — proven with a two-arm control, and --disable-gpu does not
help (L320). A display costs nothing here and the full chromium build passes.

SHAPE: xvfb-login.service (enabled) holds :99; DISPLAY=:99 lives in
personal-secretary-mvp/.env so the API process and every subprocess inherit it; the
downloaders go headed when process.env.DISPLAY is set and the platform is not win32,
and stay headless elsewhere so the Windows machines are unaffected.

REJECTED: passing --visible (it forces slowMo 100 on every action), and implicitly
keying off DISPLAY alone (a .env copied to a Windows box would ask for a display the
machine does not have).
