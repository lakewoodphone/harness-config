## Upgrading DSH is gated on a composed-tree diff plus a real boot, and promotion never restarts the engine

DECIDED 2026-09-23 (ZABZ-TECH). New subsystem at `harness-config/dsh-update/` (SPEC.md is the
frozen interface). The owner asked for a repeatable flow that pulls a newer `@deepseek-ai/dsh`,
detects anything conflicting with this deployment's customizations BEFORE applying it, and does not
silently break anything.

THE DETECTOR is two independent comparisons plus a boot, because each catches what the others cannot:
- **Composed-tree diff** -- `node <bin.js> --profile web --dump-config` prints the fully composed
 plugin tree (163 rows, ~180 ms, exit 0) with each row annotated `# == <layer>` and, when a user
 patch applied, `patched by <path>`. Diffing baseline vs candidate, and specifically diffing which
 rows carry `patched by`, detects the worst case: **a patch that silently stopped applying**. No
 error is raised for that by anything else.
- **Contract diff** -- per-package `package.json` (version, `exports` subpaths, `dsh` config) plus
 file hashes, cross-referenced against an inventory of every upstream string this deployment names
 (preset rows, profile bundles, subpaths, service names in `isolate:`, settings keys, CLI
 subcommands, our plugins' imports).
- **Boot gates** -- `--dump-config` does NOT read the user settings document (a lesson already
 recorded in `scripts/merge-settings.mjs`), so a rejected settings key is invisible to it. Only a
 real boot catches settings-schema drift. Gates: tree composes; every patch target still applies;
 all 11 of our plugins resolve; the settings document is accepted; a headless agent turn completes.

PROMOTION is a one-line, revertible change to a mechanism the launcher already supports:
`dshInstall` in `multi-window/windows.json` (or `$DSH_INSTALL`) is an npm prefix whose
`node_modules/@deepseek-ai/dsh/lib/bin.js` is the engine (`dshw.ps1` ~L249-293). `promote` installs a
candidate into `dsh-update/vendor/prefix/<ver>/`, verifies, writes the pin and that knob, and backs
up the file first.

**`promote` never restarts the engine.** It takes effect at the next boot. The engine serving the
session that runs `promote` would be killed by a restart -- including that very session. `promote`
also refuses unless a `verify` passed for the exact same `contractSha256`, and no flag bypasses
that.

EVIDENCE TIERS ARE ENFORCED IN CODE: manifest data and engine exit codes are AUTHORITATIVE; data
recovered by regex from built JavaScript is ADVISORY; a `BREAKS` verdict may only rest on
authoritative evidence. A `SAFE` verdict must carry a populated "not checked" list -- SAFE with a
silent gap list is a lie.
