**D151 · 2026-09-15 · One party-resolution helper for search and thread, and it always reports whom it resolved.**

DECIDED 2026-09-15 (ZABZ-YOGA). `_party_filter(con, party, persons)` in
`comms-search.py` is now the single definition of "match this party", used by both
`search()` and `thread()`.

WHAT IT DOES: resolves the name/number/email through the person layer, ALWAYS OR-s in the
literal `counterparty LIKE` / address-digits match beside the resolved identifiers, and
returns `party_resolved`, `party_matched_by`, `party_confidence` (exact|estimated) and
`other_candidates` (the other people sharing the name, up to 4).

WHY THE LITERAL MATCH IS ALWAYS INCLUDED: resolution picks one Dovid. `thread Dovid`
resolved to Dovid Solof and returned 0 records, while `search --party Dovid` returned
Dovid Kramer's messages -- the two modes disagreed about who a name was, so the mode
built for "what did this customer say" was the one that could not. A person's own name is
on their records; trusting resolution alone throws that away.

WHY thread PASSES persons=1 AND search PASSES 3: a thread is a claim that these words are
ONE conversation, so unioning every Dovid across three identities invents a correspondent
who does not exist (D146: a wrong merge is worse than a missing one). A search is a
filter, so breadth is cheap there. When a name is shared, thread says so rather than
silently merging -- an agent must not read a merged thread as one customer when it is
three.

RULE THAT GENERALISES: any resolution an agent will act on must report whom it resolved
to and how confident it is. "We matched a number exactly" and "we guessed a
half-remembered spelling" are different claims and the caller has to be able to tell
them apart.
