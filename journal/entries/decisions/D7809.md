**D7809 · 2026-10-19 · The authority joins the mesh as a caged worker (supersedes the blanket no-heavy-work rule).**

## Decision — `secratary-cloud` joins the mesh as a caged worker (2026-10-19)

**Decided by:** this session, on the owner's instruction of 2026-10-19: *"we update the secretary
cloud to 240gb and 32 gb of ram which makes it quite powerful so make sure it is optimized to use all
this power properly and also maybe it's time to include it in the mesh as a place to send research and
subagents and workers to."*

**The rule this changes.** The estate carried a standing instruction — `estate-systems` skill,
pains `P3136`/`P3140`/`P2947` — **"no heavy work on the authority"**, written when the box was 4
cores / 15 GB, swapped at 95-99 %, and took 11 OOM kills in 24 hours. That instruction was correct
and its reason is still correct. It is now superseded **conditionally**, not deleted: the hazard was
unbounded work on a small box, and the answer to an unbounded workload is a ceiling, not an
abstention.

**What is decided**
1. The authority may run agent turns **only** inside `dsh-mesh.slice` (`MemoryMax=6G`,
 `MemorySwapMax=1G`, `CPUQuota=400%`), so the kernel kills a runaway turn inside its own cgroup.
2. It may run them **only** with `DSH_HOME=/root/.dsh-worker`. `/root/.dsh` belongs to
 `phone-engine.service` and one engine per home is the rule `docs/mesh/71` freezes. The executor
 `/usr/local/bin/dsh-mesh` refuses any other value rather than trusting an environment.
3. It may run them **only** from `/opt/dsh-mesh-runtime` (pinned dsh 0.2.0-rc.2), never
 `/opt/dsh-phone`, because that path is the phone product's promotion target and a phone promotion
 must not silently change the worker.
4. The roster carries `maxChildren: 2` — the node's own CPU-bound governor value (4 physical cores ×
 0.75 ÷ 1.68 per turn) — not the broker's coreSlots 3 and not the gate's memory-only 12.
5. The broker reads it at `http://127.0.0.1:3086`. **Loopback, deliberately:** this node's gate does
 not allow its own tailnet address, so a tailnet read answers 403, and adding the authority to
 `phone-gate-allow.txt` would grant a 30-day engine cookie on the box that holds the database.

**Evidence it works** — four independent measurements, in
`docs/cloud-audit/2026-10-19-cloud-and-storage-audit.md` §3.3: a real turn returning
`MESH-HOST: secratary-cloud` exit 0 (both locally and over ssh from a dispatcher), the worker home
gaining exactly 1 session while the phone home stayed at 6, `GET /nodes?fresh=1` → `state=ok`, and
`POST /place` with the other five nodes excluded → position 0 `tier=fits`.

**What would make this wrong, stated so it can be checked:** if `dsh-mesh` is ever replaced by the
provisioner's `/usr/local/bin/dsh`, or if `provision-mesh-node.sh` is ever run on this host (it writes
`Environment=DSH_HOME=$HOME/.dsh`), the collision returns and the node must come out of the roster the
same day. The register carries that instruction in §2.3.

**Supersedes:** the blanket "no heavy work on the authority" reading of `P3136`/`P3140`. It does not
supersede the reasons behind them: no unbounded job, no recursive `du`, no `dbstat`, no full-table
scan, no build or test suite on this host. Those stand.
