**D · 2026-09-25 · ZABZ-YOGA — What the badge may call "no channel is carrying it", how a day-old owner message earns a text, and the default policy for agent correspondence**

Three decisions, all measured, all recorded so they are not relitigated.

**1. `delivery`: a held message that is not an owner *question* is carried by the surface.**
Measured 2026-09-25: the check reported HIGH — *"owner questions are not being routed to him: 1 other
held message(s) older than 24h (oldest 1.5d) that no channel is carrying"* — and the single row behind it
was `circuit_breaker:Agent probe_loop circuit-broken`, urgency **low**, an internal operator notice the
sender never texts by design, while the badge payload was **1.2 minutes old** and carried it. That is the
same false-alarm shape as the old `session_archive`: a fact about one channel reported as a fact about the
owner. The clause now requires `not surface_live` — i.e. it fires only when the surface he reads is also
stale, which is exactly when the CRITICAL "unreachable" branch would say so. Only `ask_owner` is a question
nothing carries, and that branch is unchanged. Commit `ceo-kernel` on secratary; backup
`ck/sentinel.py.bak-delivery-surface-20260925`; verified live → *info ok=True, "owner delivery flowing
(newest 6.6h ago, app surface last written 0 min ago)"*.

**2. `attention_debt`: the 12 pending agent questions were ANSWERED, not reclassified.** The count was
true — the questions were really piling up — and reclassifying them would have hidden a live defect rather
than fixing it. All 12 now carry answers written with bound parameters (`~/bin/agent-questions.py`), the
three Google Business Profile ones answered with the honest finding that the figure is not observable from
here (search returns other businesses; Maps blocks automated reads; a dispatched child spent a whole turn
on it and observed nothing) and the instruction to record "not observable" rather than re-quote the old
5.0/4 snapshot. The check now reads *"attention debt within bounds (0 recent question(s) …)"*.

**3. A day-old owner message earns a text — narrowly.** Measured 2026-09-24/25: r415 (a PayPal case with a
2026-09-26 deadline) and r471 (the New Jersey resale-tax exemption REJECTED, which taxes every Newegg
order until it clears) sat 15–17 hours having reached him only as the badge line *"⏰ Reminder: Newegg NJ
resale tax exemption is REJ..."* — because the dispatch files reminders `held` on purpose, the gate refuses
anything under `urgent`, and the in-app reader is a truncated summary. The flush now escalates a held
message to `urgent` **once**, after **24h with no action**, and only for the two reasons that are the
owner's own business: `ask_owner` and `reminder:*`. Operator notices and briefings are excluded on purpose
— they are what his "only text me for truly important things and don't overdo it or spam me" instruction
(2026-09-22) was about. Quiet hours are honoured above the call, the existing flood ceilings still apply
below it, and no row escalated at the time of the change (none was 24h old), so this sends nothing that was
not already waiting. Commit in `personal-secretary-mvp`; backup `app/autopilot.py.bak-escalate-20260925`;
API restarted 2026-09-25T02:08:30Z, health 200 after 20s, `NRestarts=0`.

**Also decided, not asked:** the conservative default for agent correspondence — outbound email/SMS/calls
to customers, vendors or partners are drafted, never sent, unless it is a pre-approved transactional
template or the owner approved that specific message. It is the answer given to the recurring question that
nine duplicate tasks were built on, and it stops that loop. If he wants a wider autonomous lane for routine
replies, that is a new decision by him, not a default anyone should assume.
