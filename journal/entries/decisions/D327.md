**D · A bound that severs live work must never be charged to the subject it severed**

CHANGED 2026-09-20 in `/home/zabz/bin/sources/wake-tuner.py` (the governor for the wake/reactivation
system). Backup at `wake-tuner.py.bak-rc124-20260920`.

THE FAULT. The wake dispatcher revives a headless session for every release, and a release is judged
"empty" when it produces no outcome. `wake-tuner`'s rule R2 then raises that subject's cooldown, and R3
DISABLES it after three consecutive empties. But releases #8, #9, #11 today were empty for a reason that had
nothing to do with their subjects: `exit=1 runner_code=124` — killed by the runner's own bound at 840 s,
which was cutting sessions that had burned 5.3M-9.7M tokens. **The tuner charged a platform fault to the
work.** Left alone it would have backed off, and eventually disabled, the most productive subjects on the
system, and reported that as tuning.

THE CHANGE. Before the "non-zero exit is empty" verdict:

 if runner_code == "124": return False, "COULD NOT ASK: the runner's own bound killed the session ..."

A bound-kill now **holds** instead of raising, and says why in the reason string.

PROVEN, not asserted — five cases run against the real function:
 rc=124, no tokens -> NOT EMPTY (holds) COULD NOT ASK: the runner's own bound killed the session
 rc=0, exit 1, no outcome -> EMPTY (raises) correct, this IS the subject's fault
 exit 0, no outcome -> EMPTY (raises) correct
 exit 0, real outcome -> NOT EMPTY (holds) correct
 rc=124 with burned tokens -> NOT EMPTY (holds) correct

HONEST LIMIT OF THAT PROOF: the fifth case was meant to exercise the pre-existing "burned N tokens"
branch, but my synthetic event omitted `release_id`, so the cost lookup keyed on 0 and missed — it proved
the new rule, not the token rule. The token branch is unchanged and sits ABOVE my insertion; it was not
re-tested here.

WHY IT IS THE SAME RULE THE WHOLE MESH RUNS ON: a timeout is a fact about **the bound**, never about the
thing being measured. This is the fifth instance in two days — the 300 s child-turn cap, the 843 s wake
bound, `ConnectTimeout` on a handshake, a blank `node -v` read as "no runtime", and `git apply --check`
against the wrong tree. Every one produced a confident verdict about the wrong subject, and the fix is
always to ask **what the measurement was actually about** before acting on it.

AND THE SYSTEM THAT PRODUCED THIS: a session — woken by a flag I filed hours earlier, with no human in the
loop — diagnosed the 843 s severance, raised the dispatcher's bounds (TURN_CAP 1800 / TIMEOUT 2160 /
runner self-bound 2100, replacing 900/840), lowered the release cap to 4, and built this tuner. It even
documented the rc=124 trap in its own docstring. **The reactivation loop works, and it paid for itself the
same night it was built.**
