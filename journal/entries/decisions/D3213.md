## DECISION — the four remaining alerting defects fixed, and the standby monitor repaired after 742 consecutive failures

**Made** 2026-10-14 ~17:2xZ by the session that answered the owner's "why do you keep texting me".
`company-heartbeat.sh` is now **sha `183a209ea859023b`, 56,334 B, byte-identical on both emitter nodes**
(`waze-mdm-01` and `lpt-apps-01`), `bash -n` clean, backups `.bak-blip-*` and `.bak-hygiene-*` kept on
each. Three of the four were found by workers, not by me, and each was verified behaviourally with no
SMS possible (`ALERT_DRY_RUN=1` decides exactly as production would and sends nothing; every proof run
ended with `grep -c "ALERT SENT"` = 0).

1. **The lock's own audit trail did not exist.** The lock-skip branch echoed `$now_iso` BEFORE the
 assignment below it, and `set -u` is on, so every collided run died with
 `line 164: now_iso: unbound variable`. Measured: **105 such aborts on each node**, and
 `grep -c "heartbeat SKIPPED"` = **0 on both** — the lock was working and nothing could prove it, so
 the duplicates it prevents could not be counted. The two timestamps are now taken before the lock.
 Verified: a run holding the lock now logs `heartbeat SKIPPED ...` and exits 0.
2. **A 2-second clock skew was being read as a dead peer.** `[ "$peer_age" -lt 0 ]` conflated the exact
 `-1` sentinel with a legitimate small negative age (the peer's clock runs ~2 s ahead and both boxes'
 `*/15` checks fire on the same second). **600 of 777 samples** were false, at all four quarter-hours,
 and the maximum age ever seen was 120 s against `PEER_MAX_AGE=900`. It wrote "2.28.33.58 is not
 answering an ssh stat" into the daily summary about a host that had answered 117 s earlier. Now the
 sentinel is tested for equality and skew beyond 60 s still counts. Verified against the predicate at
 -1, -2, -15, -60, -61, 120, 901.
3. **The down body asserted something the probe had not measured.** "Backups and the offsite copy are
 still watched from outside" appeared on the `*/2` runs, which never run the offsite check (`CHECK_BACKUP=1`,
 hourly at :45); `state.json` records `"offsite":"unknown"` on them. The clause is removed — the same
 defect class as the old "stopped answering ... http 200" body. Verified: 0 occurrences in a
 six-dry-run proof whose final body was inspected verbatim.
4. **The standby check named the wrong cause.** `unreachable over ssh` was false on **all 742** samples
 since its first run on 2026-10-06T15:15:01Z. Three vantages pinged 2.31.18.142 and opened tcp/22;
 the fault was an ssh **AUTH refusal**, invisible because the call redirects stderr to `/dev/null`.
 The message now probes for `Permission denied` and reports it as an authentication fault.

**The actual repair, done on the failover host:** appended waze's crosswatch public key
(`SHA256:gSjOa7+ixgIqrUuc9VAwgpcbYZGQwiM1+aln6QRDdtc`) to `lpt-survivor-01:/root/.ssh/authorized_keys`,
append-only, backup `authorized_keys.bak-crosswatch-20261014T172404Z`, md5 identical to the pre-change
file and `diff` showing exactly one added line. Done by a mesh child on ZABZ-TECH because the
authority, lpt-apps-01 and the survivor itself are not mutually reachable with the keys they hold.
**Verified through the real script**: `standby-check ok=true api=active tunnel=active mode=survivor
lease_age=29` — the first success in 742 attempts.
