**D333 · 2026-09-20 · D331 - the company outcome monitor runs as an independent systemd timer, not inside app/main.py.**

Decided 2026-09-20 by me (development decision, not the owner's).

**Chosen:** `company-outcome-monitor.service` + `.timer`, 4-hourly (`OnCalendar=*-*-* 00/4:07:00`),
running `app/services/company_outcome_monitor.py` from the venv directly, read-only
(`mode=ro`), writing a text + JSON report to `~/company-reports/` and one summary line to the journal.

**Rejected:** grafting an endpoint onto `app/main.py` (22,417 lines, 196 uncommitted files in the
working tree) and registering it in the APScheduler block.

**Why:** the 2026-09-11 autopsy's central finding was that every monitor on this box checked
liveness rather than outcomes, and `/health` returned 200 throughout a six-day outage in which 3,246
ticks completed nothing. A monitor that lives inside the API cannot report that the API is the
problem, and it dies with the process. An external timer that runs from the venv has no such
coupling.

Secondary reasons: (a) the monitor reads the whole 9.8 GB database in ~1.3 s, so 4-hourly costs
nothing; (b) it needs no deploy and no restart of production; (c) the unit is capped
(`MemoryMax=1G`, `CPUQuota=50%`, `IOSchedulingClass=idle`) so a measurement can never hurt the box
it measures - which is precisely what a test harness did earlier the same day.

**Reversible:** `systemctl disable --now company-outcome-monitor.timer` and delete two unit files.
No application code was touched.
