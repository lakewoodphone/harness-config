**D2838 · 2026-09-28 · Version-coupled config gets a SYNC-TIME precondition, not discipline; sync skips only the coupled steps and fails open.**

## A routine 15-minute timer can push committed config into the live home: a version-coupled change needs a sync-time precondition, not discipline

MEASURED 2026-09-28 (ZABZ-TECH).

THE MECHANISM. Task `PersonalSecretary-HarnessSync` runs `scripts/autosync.ps1` every 15 minutes.
`autosync.ps1:464` makes a temp snapshot, `:473` runs `git archive --format=tar ... HEAD` into it, and
`:483` runs `python <snapshot>\scripts\sync.py`. `sync.py` copies `presets/` and
`profiles/<name>/cordis.patch.yml` into `~/.dsh`.

WHY THAT IS SAFE TODAY, AND ONLY BY CONSTRUCTION: `git archive HEAD` exports COMMITTED state, so the
timer cannot see a dirty working tree. That is the ONLY thing protecting the running engine right now,
because the working tree holds a version-coupled change -- rows naming `@deepseek-ai/dsh-workflow-ptc`,
`@deepseek-ai/dsh-agent-preset-registry` and `@deepseek-ai/dsh-agent-preset`, none of which exist on
`0.1.5`. Confirmed: `sync.py --dry-run` before the guard said
`preset cordis-bg: WOULD UPDATE` / `profile mesh: WOULD UPDATE` / `profile web: WOULD UPDATE`.

THE FAILURE IT WOULD HAVE CAUSED: commit those files and the next tick copies them into the live home.
A composition row naming a package that is not installed fails to resolve AT MOUNT -- in a preset that
breaks NEW SESSION CREATION, in the mesh host composition it can take the boot down. Existing sessions
keep working, so it surfaces hours later when somebody opens a chat, with nothing pointing at a sync
timer. That is the silent-loss class this whole effort exists to prevent, arriving through the one door
nobody watches.

THE FIX, and the shape to reuse: a PRECONDITION, not a convention. `scripts/check-version-coupled-config.py`
extracts every `@deepseek-ai/*` name from `presets/*/agent.cordis.yml` and
`profiles/*/cordis.patch.yml` (skipping comments) and resolves each against the RUNNING engine's
install. `sync.py` calls it before writing presets and before writing profile layers, and on failure
**skips those two steps only**, loudly, naming the missing package -- everything else still syncs,
because the blast radius must not be the whole sync (a stalled sync has frozen machines here before).
Measured: 0.1.5 -> exit 1 naming three packages; 0.1.7-rc.2 -> exit 0; a checker error (exit 2) fails
OPEN so a bug in the checker can never stop convergence.

ORDERING FALLS OUT OF IT, which is the elegant part: the checker's default engine root is
`$DSH_INSTALL`, then `dshInstall` in `windows.json`, then the live profile tree. So `promote` (which
sets `dshInstall`) makes the check PASS and the config applies; running `sync.py` before the promote
makes it SKIP and the live copies are untouched. The safe order is therefore self-enforcing rather than
remembered.

ONE INTEGRATION TRAP, caught only by reading the caller: the skip message must not contain the word
`WOULD`. `autosync.ps1:496` verifies convergence with `-not ($verify -cmatch 'WOULD')`, so a `WOULD` in
a SKIPPED line would record "apply did NOT converge", skip the push and exit 1 on EVERY tick -- the
stalled sync this guard was written to avoid.
