**D141 · 2026-09-14 · comms: refresh cadence, agent access, and a bounded transcript-gap spend.**

## The communications index is refreshed by cron on the authority, with coverage as the gate

**Decided 2026-09-14.** `7,37 * * * * /usr/bin/python3 /home/zabz/.fsearch/comms-refresh.py` on
`secratary`, logging to `~/.fsearch/comms-refresh.log`.

Why: the index existed and nothing ran it. It was 6.7 hours stale within hours of being built, and
the failure mode is the fleet's most expensive one — an index that is quietly behind answers
yesterday's question confidently. `:07`/`:37` is five minutes after the Dialpad harvest at
`:00`/`:30`, so the rebuild reads freshly harvested data instead of racing it. A full rebuild is
29 s, so 30-minute freshness costs ~1.6% of the window.

The refresh refuses to overlap itself (flock), records `~/.fsearch/comms-state.json`, and **exits
non-zero when coverage is incomplete** — so its own failure is observable by cron, by an
`--check`, or by `ps_comms_health`. Tools are installed into `~/.fsearch` by
`comms-refresh.py --install`, which records the git commit it copied from; before this, every
install was done by hand and the authority had three `.bak` generations of `commsindex.py` beside
the live one.

## Agents reach the index through the API, not through SSH

**Decided 2026-09-14.** Retrieval is `POST /tools/run/comms_search` (the app's existing dynamic
tool runner) with `comms-search.py` symlinked to `data/tools/comms_search.py`, wrapped for agents
as `ps_comms_search` / `ps_comms_thread` / `ps_comms_health` in the ps MCP server.

Why this shape: the index lives on the authority and agents run on Windows machines, so the only
path that works everywhere is the API that is already up on every machine. It needed **no change
to the 22,000-line `app/main.py`** and no restart — the dynamic-tool mechanism was already there
and its name normalization (`comms_search`) and `run(**kwargs)` contract are what the reader
implements. One implementation, versioned in `harness-config`, reachable three ways: CLI, HTTP,
and MCP.

## Transcript gap: spend up to $15 once, on the calls that have no transcript at all

**Decided 2026-09-14.** `scripts/dialpad-transcript-gap.py` transcribes the **1,117** calls that
have a downloaded recording and no transcript whatsoever — 2,125 audio-minutes, ~**$12.75** at
`whisper-1`'s $0.006/min, hard-capped by `--max-minutes 2400`.

Why not the whole backlog: 4,298 recordings have never been re-transcribed, but 3,181 of those
calls already carry Dialpad's own readable transcript. For those, a re-transcript is a quality
improvement; for the 1,117 it is the difference between searchable and invisible — today they
index as `[no transcript] inbound call 102s state=hangup`. Newest first, idempotent, and it
records the same rows the existing pipeline uses (`dialpad_call_retranscript`), so it continues
rather than duplicates.

Deferred, deliberately: the 3,181 softer replacements (~$44) and downloading the 1,375 recordings
that have a `recording_url` but no local file (34.7 audio-hours).
