**D191 · 2026-09-15 · Cross-machine id collisions: the convention, the 98, and the defect still underneath.**

## What was decided

**Journal id collisions are resolved by convention now, not by taste: the upstream side keeps
every contested id, the local lineage is renumbered above the merged high-water mark, and both
sides are staged on disk before anything moves.**

### Why the ids collided (98 of them, not 3)

Two machines numbered entries from the same base. `git diff --name-status 919cfa64 613ee55 --
journal/entries` shows **98 paths with different content on each side**:

| kind | count | ids |
|---|---|---|
| handoff | 28 | H228–H255 |
| lessons | 29 | L1510–L1538 |
| pain | 15 | P145–P159 |
| wins | 20 | W129–W148 |
| decisions | 6 | D153–D158 |

Commit `613ee55` (ZABZ-TECH) resolved **three** — H276, L1567, P164 — because those were the only
conflicts *its* merge produced. It never saw these 98. So "the collisions are resolved" was true of
one merge and false of the repo. That distinction is the whole reason this entry exists: a fix
scoped to one merge is not a fix.

### The convention (follow this on the next collision)

1. **Stage both sides first.** `git show :2:<path>` and `git show :3:<path>` for every conflicted
 entry, into a scratch directory. Nothing is resolved until both versions exist somewhere.
2. **Upstream keeps the id.** Other machines have already seen it and may have cited it. The local
 lineage moves to fresh ids above the merged high-water mark per kind.
3. **Renumber with a record.** Rewrite the id token in the header, remap `refs=` pointing at other
 moved entries (only ids inside the move set — an id that also exists upstream is a *different
 entry* and must not be touched), and leave one audit comment per file naming the old id. Write
 the whole old→new map to a file, not into prose.
4. **Rebuild the generated index, never hand-merge it** (`journal.py index`). `status.tsv` is
 append-only, so its conflict resolution is the **union** of both sides, not one side.
5. **Regenerate the state tier** (`journal.py state`, `journal.py questions`) — a state file taken
 from upstream silently omits every local entry, which is how a fixed merge still leaves a wrong
 `open-pain.md` behind (measured: 0 rows for P183–P197 until `state` was run).
6. **Prove it**: `journal.py check` (0 errors) and `journal.py verify` (FAIL=0 WARN=0).

### The defect underneath, still unfixed

**Ids are minted without any knowledge of what other machines have minted.** `next-id` reads the
local index and local refs, so it is collision-proof only after a successful push — offline or
merely unpushed, two machines pick the same number with confidence. `journal.py check` validates the
local tree and reports 0 errors on a tree that collides with another machine's, so this class of
fault is invisible until a merge.

Both pain entries that describe it (P182 upstream, P197 here) agree on the fix and neither has been
built: **mint collision-resistant ids** (host or timestamp suffix, or a reserved band per machine),
and give the tool a reconcile verb so a duplicate can be renamed, the index rebuilt, and the move
reported. Recording it again is not fixing it; this is the second time this machine has written the
same pain entry.
