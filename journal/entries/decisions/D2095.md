**D2095 · 2026-09-20 · D337 - lifecycle_sweep: fix the lock by giving each writing phase its own short transaction, not by one sweep-long lock.**

The dominant `lifecycle_sweep` defect (39 occurrences/24 h) and the exact shape, established this round
by reading the deployed code.

**The structure.** `run_lifecycle_sweep` (~289-368) opens ONE connection and runs **18 phases** through
it, each of which commits independently:

 conn = _get_conn(db_url) # 296 - one connection, no transaction
 ensure_task_lifecycle_metadata(db_url) # 319 - its OWN connection; reads up to 1000 task
 # rows, then WRITES metadata per task
 _close_completed_progress_tasks(conn, ...) # 321
 _sync_active_task_progress_from_goals(...) # 326
 _ensure_priority_task_goal_coverage(...) # 331
 _close_expired_drafts(conn, lock) # 336
 _expire_stale_owner_messages(...) # 337
 _expire_stale_agent_questions(...) # 338
 _release_stale_claims(conn, lock) # 339
 _retry_failed_steps / _reopen_stale_blocked_steps / _rollup_completed_goals /
 _detect_stuck_goals / _cleanup_superseded / _expire_stale_approvals /
 _cleanup_terminal_waiting_steps # 340-356
 _watch_customer_stalls(db_url) # 360 - its OWN connection
 _close_stale_tasks / _release_stuck_work_orders# 361-365
 # 18 `conn.commit()` sites across the file

**The cause is the same one, one level up.** A phase reads with `conn`, commits, and the NEXT phase
writes with the same `conn`. Between the two, the autopilot writes to the database. The next write must
upgrade a snapshot that is now stale, and `SQLITE_BUSY_SNAPSHOT` is refused instantly - the busy handler
does not cover it. It is the `mashgiach` defect (W2137/W2149) reproduced across a longer routine.

**The rejected fix, and why.** One `BEGIN IMMEDIATE` for the whole sweep is the obvious move and it is
the wrong one: it would hold the write **lock** across 18 phases on a routine that runs every 120 s, and
that is precisely the mistake I made in `daily_scan` (62 lock errors) and corrected by narrowing the lock
to the write. Wrapping the sweep would turn 39 failures of the sweep into failures of everything else.

**The recommended fix: a short transaction per writing phase.** Each phase that writes takes
`BEGIN IMMEDIATE` at its own start and commits at its own end, so the lock is held for one phase rather
than for the sweep. That is the same narrowing that worked twice in `mashgiach`, scaled to 18 call sites.

**Why it is not applied yet.** 18 edits across the file that runs the company's backlog maintenance,
where a mistake in `BEGIN`/`COMMIT` pairing either holds the lock too long or silently discards a
phase's work. This session has already produced five self-inflicted near-misses from exactly this kind of
hurried multi-site edit, and each was caught only because the patch asserted on structure. The edit is
mechanical but it is 18 of them, and it wants a session with its own tests - ideally a per-phase test
that asserts each derived transaction starts and commits exactly once.

**The measurement that motivated it, restated because it is the justification:**
`OperationalError: database is locked` 39 times in 24 h against a 120 s cadence, and every failure
silently skips the remaining phases of that sweep.
