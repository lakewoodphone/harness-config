**D · 2026-10-16 · The kiosk's Stripe return path is fixed at the ROUTE, not at the env var, and the counter shows the kiosk's payment as evidence rather than overwriting the shop's own fee state.**

Two decisions taken while fixing the seven defects the owner raised from two live self-serve kiosk tests. Both are recorded here because each had a second, plausible alternative and the reason for the choice is the part that would be lost.

## 1. `/kiosk` is a second MOUNT of the kiosk page, never a redirect — and the env var is not the fix

The return URL Stripe was given comes from `resolveKioskPublicUrl()`
(`backend/src/services/kiosk-intake/kiosk-intake.service.ts:363-369`): `KIOSK_PUBLIC_URL` if set, else `FRONTEND_URL + '/kiosk'`. The page is mounted at `/intake`. So a paying customer was returned to a path no route serves — measured live this session: `/kiosk?intake=…&payment=success` lands on `/login?expired=true` logged out, and on `NotFoundPage` signed in.

**The tempting fix is to set `KIOSK_PUBLIC_URL=https://lakewoodphoneandtech.com/intake` on the backend host.** It is one line, needs no deploy, and works. It was rejected as the *whole* fix because the landmine stays armed: every other environment (a fresh test backend, a rebuild from `.env.production.template`, the next person who reads the function's own docstring) resolves back to `/kiosk`, and the failure is silent — a paying customer on a sign-in page and a `KioskIntakePayment` row stuck at `PENDING` for ever.

**Decided:** mount `KioskIntakePage` at `/kiosk` **and** `/intake` in `frontend/src/App.tsx`, permanently, with the reason in the comment block above the route table. Explicitly **not** a `<Navigate>`: the return URL carries `intake`, `ref` and `payment`, the page's resume reads them via `pendingIntakeFromSearch`, and a redirect that does not preserve the query string loses the payment resume — which is the defect, one layer in. Two `<Route>` elements cost nothing.

`KIOSK_PUBLIC_URL` may still be set to `/intake` for tidiness. It is no longer load-bearing.

## 2. A paid kiosk row and `diagnosticFeeState` are shown side by side; neither writes the other

The kiosk writes a real `KioskIntakePayment` (`status: 'PAID'` at `kiosk-intake.service.ts:742`) and the API returns it on the case as `kioskPayment`. The counter drew only `diagnosticFeeState`, which the kiosk never writes and which therefore reads back `NOT_PAID`. The owner, on a case whose customer had just paid by card: *"the work order i just did for 50 does not say paid"*.

**The tempting fix is to set `diagnosticFeeState: PAID` from the kiosk row.** It was rejected. `WAIT_TO_SPEAK` and an in-person deferral are both kiosk states in which the customer did **not** pay, and a blind derivation would silently mark those paid — a guess in the direction that loses the shop money, made by a screen, about money, with no person in the loop.

**Decided:** the two facts are about different things and both are true at once. `kioskPayment` is EVIDENCE of what the customer did on the card at the shop's own tablet; `diagnosticFeeState` is the SHOP'S OWN record of the fee. The counter now draws the kiosk's own line, directly under the fee control, using `describeKioskPayment` (the renderer that already existed for `RepairIntakeCasesPage`, imported rather than rebuilt), with the kiosk's own label saying which state it is in. Nothing on that screen writes `diagnosticFeeState`. If the shop wants the fee marked paid, a person presses the button.

## Not decided here, and deliberately left to the owner

- Whether an untouched kiosk intake should be created `NEEDS_REVIEW` at all — it is the reason the counter demanded a "reason summary" from a case nobody had reviewed. Owner queue row **541**; ledger item **505** carries the change gated on the answer.
- Whether a cancelled intake keeps the 50 non-refundable fee, and whether `CANCELLED` becomes a real terminal status. Same row 541.
