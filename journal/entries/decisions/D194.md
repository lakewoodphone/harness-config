**D194 · 2026-09-15 · Reconciliation decisions 2026-09-15: repoint not backfill; view not delete; every apply behind a proven gate; reporter not auto-writer; origin/main authoritative but not a superset.**

**Five decisions taken in the 2026-09-15 production reconciliation, with the measurement behind each.**

**D-new-1 · The canonical direction for the comms lineages is REPOINT, not BACKFILL.** Five read
surfaces are repointed at the Dialpad tables; the Twilio lineage is kept, because it is the live AI
line, not legacy. `call_log`/`sms_log` are NOT a stale copy of the Dialpad corpus: `call_log.to_number`
is `+17324447361` ×50 (the secretary's own AI line) against the Dialpad business line
`+17326552355`, and `sms_log.id=882` says so in its own error text. ID-level intersection with every
Dialpad id column: **0 of 70, four ways**; the only working key is
`dialpad_call_link.call_id -> dialpad_call_full.call_id` (4,873/4,873). A backfill would need to invent
a `dialpad:<id>` namespace for a `CA…` primary key and would inject 128,444 rows into a write path that
already logs 3,322 lock events a week. Rejected on measured grounds; the backfill is recorded as an
operation with `reversible:false` so no applier ever runs it.

**D-new-2 · The deduplication operation is a VIEW. Nothing is deleted.** 2,441 of the 12,029 collapsed
rows carry facts no other row carries; **2,282 are the two legs of one call, each holding a DIFFERENT
recording** (operator vs admin) — 0 pairs have byte-identical media columns, 1,382 each hold a
recording the other lacks, 99.9% are joined by an exact operator/entry-point call id. For
`dialpad_sms_cache` the reverse holds (2,744 groups differing only in `session_id`, 0 with differing
body text) — and it is still a view, because the honest output of a reconciliation is not a delete.

**D-new-3 · Every apply goes through a gate, and the gate is proven before it is trusted.**
`apply/recon-apply.py`: kind whitelist, row pre-image captured before any UPDATE/DELETE,
`--confirm-op <id>` demanded per destructive operation, an unbounded UPDATE/DELETE refused, and a plan
op with no `affected` count or no evidence refused outright. Proven on a synthetic plan built to be
refused (4 refused, 1 awaiting confirmation, 2 dry-run and rolled back), then production was re-read to
confirm the gate had written nothing.

**D-new-4 · Reconciliation is a REPORTER on a clock, never an auto-writer.**
`/home/zabz/bin/lpt-recon-check.sh` asks the push tool what it would create (read-only) and runs
`lpt-recon.py`, records state, and exits non-zero. It does not create customers, and it sends no email
(the owner's rule: nothing outbound without his per-message instruction). The 2026-08-27 run was a
manual one-off with no failure surface, which is exactly why 71 records accumulated un-noticed.

**D-new-5 · origin/main is authoritative for lpt-hub, but it is NOT a superset; do not merge the
desktop clone.** secratary's checkout = origin/main (372 records / 174 case files, clean). The office
desktop holds **9 records origin has never seen**, two carrying quoted money for a customer already in
production, and its clone is 48 ahead / 2,775 behind with a front-matter case format origin has never
seen. A merge would re-introduce 2,775 commits and is not a fast-forward. Reconcile file-by-file, by
name; and read origin's copy of a record, never the desktop twin — origin's
`2026-09-14-lenovo-ideapad-slim3-15abr8-screen.json` and desktop's
`lenovo-ideapad-slim3-15abr8-screen-8484805115-2026-09-10` are the SAME case, and pushing both fires a
duplicate order for a $180 job.
