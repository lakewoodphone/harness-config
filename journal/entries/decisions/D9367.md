**D9367 · 2026-10-22 · Computer sales: own work order, total = the deposit until priced, request row is the intake of record.**

How a customer computer sale is booked in production, decided 2026-10-22 on the Schreiber laptop.

1. The intake of record is the website's `computer_requests` row (reference CR-XXXX, e.g. CR-SHRB22CA),
 not a note and not a memory. `handoffStatus SKIPPED` + `handoffAttempts 0` means the shop text was
 held and NOTHING was sent to the customer. The owner's own refinement of the requirement goes into
 `answersJson.ownerSpec` with the date, so the row states the real requirement and supersedes the
 form where they differ.

2. A sale gets its OWN work order for the machine - never a second line on the repair order, and never
 a note-only record. On Schreiber: WO26102212770 (order 3205) for the laptop, separate from
 WO26100812737 (order 3016) for the dead machine and its 60 data job.

3. THE TOTAL IS THE DEPOSIT UNTIL A MACHINE IS PRICED. `lpt-write order create --total` takes a
 PRE-TAX figure and stores the tax-inclusive one, so passing 75.00 stores 79.97 - which is exactly
 what Stripe had charged. Setting a total to a price nobody has agreed invents a commitment; leaving
 it NULL means the order can never be charged. When the machine is chosen, RAISE the total to the
 customer-facing price and leave the deposit collected, so the balance is what shows. Do not open a
 second order and do not re-quote the deposit as the price.

4. A card charge is booked with `lpt-record-payment --stripe-charge ch_... --amount <net> --apply`
 run ON the authority with the venv python (it refuses to run from a Windows checkout because it
 reads the authority's .env). That writes `payment_transactions`. Then `lpt-write payment set
 --stripe-charge ...` verifies the charge at the processor and sets `orders.paymentStatus`; it
 deliberately does NOT write payment_transactions and refuses a `--payment-id` row that has no
 Stripe payment intent. Both steps, or the order reads CAPTURED with 0.00 collected.

5. NEVER leave a charge unbooked because no order exists. An orphaned Stripe charge is how this store
 came to hold 28,568.26 of collected money attached to nothing. Opening the order the same day is
 the fix; the note must say what the total represents.

6. The sourcing brief lives in the hub, not in a chat: `lpt-hub/non-device/Computer-Sourcing/customers/
 <customer>.md`, with the money model taken from `deals-log.md` (Weitman 2026-09-22: bought 362.51
 landed, sold 500 out the door, ~137 gross). The machine actually bought goes in `deals-log.md`.
