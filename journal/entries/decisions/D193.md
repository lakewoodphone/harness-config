**D193 · 2026-09-15 · AI writes off in production: decided, done, verified, with the claim measured against the build.**

## The decision

**AI writes are OFF in production in the lpt backend. I decided this myself, on the owner's
explicit delegation ("analyze this really well and figure this out fully and decide for yourself,
you are in charge of my life and company"), and I did it rather than queueing it.**

## Why

The asymmetry decides it:

- **On**: the AI can change real business records and text real customers with no approval, and its
 undo ledger is written *after* the act. The first sign of harm is therefore a customer complaint,
 and some of the harm is not undoable at all.
- **Off**: the capability to act unattended is lost. That is a capability, not data, it is restored
 by one flag, and the AI keeps reading, planning and proposing throughout.
- **Timing**: applied 23:01Z = 19:00 local, shop closed, cheapest possible moment to restart a
 customer-facing service.

## What was done

- `/opt/lpt/.env`: `FEATURE_AI_AUTOPILOT=true` → `false`, `AI_AUTOPILOT_WRITES_ENABLED=true` →
 `false`, exactly once each (the edit refused to run unless each key matched exactly once).
- Backup first: `/opt/lpt/.env.bak-aiwritesoff-20260915T230154Z`.
- `cd /opt/lpt && docker compose up -d lpt-backend` — a plain `restart` would have reused the old
 container's environment, so the change would have been invisible.
- Verified, in this order: live container env now reads both `false` (re-read independently a
 second time); container `running healthy` since 23:01:58Z; no error lines in the log;
 `https://api.lakewoodphoneandtech.com/health` → **200**; site root → **200**.
- Rollback, exact: restore that backup over `/opt/lpt/.env` and re-run `docker compose up -d
 lpt-backend`.

## What row #62's claim actually is, measured against the deployed artifact

The build, not the source, is the evidence — and the build says:

- the autopilot token appears in `dist/services/ai-tools/*` and `dist/trpc/routers/adminSettings.js`,
 and in **no file under `dist/services/ai-workspace/`** → *the switch does not gate the workspace.
 Claim verified.*
- the workspace module really holds `ai-workspace-quote-apply`,
 `ai-workspace-work-order-note-apply` and `ai-workspace-work-order-customer-sms` → *claim verified.*
- **but** every workspace write path is reachable only through
 `dist/trpc/routers/ai-workspace.router.js`, whose sampled procedures were 8/8 `protectedProcedure`
 (authenticated); no `setInterval`/`cron.schedule` matched inside the workspace services; and the
 customer-SMS path's only caller is the workspace prompt-planner, itself reached from that router.
 → *the implied hazard — writes proceeding with nobody in the loop — is not established.* With the
 flags off, there is no unattended AI write path left in this backend.

So the row was right that the switch is partial, and wrong about what the uncovered part does
unattended. That distinction is the whole difference between an emergency and a robustness task.

## What remains, and why it is not done today

1. **One flag, read by every AI write path** — so hitting the switch can never again leave a path
 writing. This is the real fix and it is *not deployable today*: the current source tree is
 un-deployable (D179 — `smsService` was left on a NoOp, so a rebuild would silently break
 repair-status SMS, payment links, MFA). It lands with that migration, before any autonomy is
 re-enabled.
2. **The server-side approval step** — the thing that makes writes safe to turn back on.
3. **Rate limit + incident control on the workspace apply procedures** — they are authenticated but
 otherwise unguarded.
4. **D191's finding, in passing**: `/opt/lpt` holds `docker-compose.yml.bak-incident-$ (date
 +%Y%m%d-%H%M%S)` — a literal, unexpanded `$(date ...)` in a filename, from a deploy whose backup
 step did not expand. Cosmetic, but it means one backup in that directory is not identifiable by
 time.
