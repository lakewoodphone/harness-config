**D6146 · 2026-10-16 · The backup-dir guard watches the directory, not the filesystem percentage - and the writer that filled the disk is a session or a systemd unit, not cron.**

Decided and installed 2026-10-16 after the disk filled and the ledger writer stopped. ROUND 41. The writer that produced the 28.72 GB authority copy could NOT be identified from cron: everything between 04:35 and 04:46 in runs.tsv is the estate normal per-minute traffic and no entry corresponds to the 04:44:59-04:45:48 write. authority-offsite-backup.sh header says it is started by a systemd unit or under setsid, so the writer is a session or a unit - and I did NOT patch a script I only suspect. Instead the guard went where the directory is mine: cfo-backup-dir-guard.py, scheduled */15 through cron-wrap.sh, reporting three conditions and exiting 3 - free space on the mount below the highest declared floor (8192 MiB), any single file above 200 MB, and the directory total above 4096 MiB - naming the offending file in each case. VERIFIED LIVE while the condition holds: 595 files, 32665 MiB total, 1586 MiB free, with the 28.72 GB authority copy named, and the literal crontab line run under a cron-like environment returned rc=3 with the run recorded. THE REASONING THAT MATTERS: the estate disk alarm is a percentage threshold sampled on a cadence, and one write can cross more of the disk than the sample interval can see - a 28.7 GB write is 19 percentage points on a 150 G disk, so the disk went from 76.7 percent ok to 100 percent between two samples and never passed through warn. The only guard that works on a step change is a pre-write check on the size of the write; space-guard.sh is that guard, its floor is 8 GiB, its exit 3 is a refusal - and it was not called. An uncalled guard and no guard look identical from the outside, so the CALL SITE is what to verify, not the guard existence. What remains mine to do: wire space-guard.sh into the authority backup call site once the writer is identified, and set the pre-write backup retention count so a directory with a 2 GiB floor cannot grow to 33 GB again.
