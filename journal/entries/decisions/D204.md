**D204 · 2026-09-16 · Cost round 3: compaction trigger fixed and pruner tightened (76.7% -> 66.6% kept, measured); MCP un-mounting deferred as a capability call for the owner.**

## Decided and implemented (round 3, from `60-cost-audit.md`)
The audit measured the money instead of guessing: DSH *does* record real provider usage locally
(99.1% of prompt tokens are cache hits — the caching works), and the bill is dominated by
re-billing history: **82% of spend is re-reading context**, and tool output is 82.5-95.8% of
prompt tokens in the long sessions that were half of the $54 day.

1. **Compaction trigger fixed** — `compaction-basic` now sets `thresholdRatio: 0.7`
 (threshold 700k, under the credential's 792,576 legal ceiling). The trigger ignored the
 256,000-token completion reservation, leaving a 7,424-token band where DSH refuses to
 compact and the API rejects the request; 10 `CONTEXT_WINDOW_EXCEEDED` failures were recorded,
 each forcing an emergency whole-history compaction. Capability: unchanged — it respects a
 limit it already had. File: `presets/cordis-bg/agent.cordis.yml`.
2. **Tool-result pruner tightened** from 8192/4096/1024 to **5000/2500/700**.
 Measured on the same 12,597,690-char corpus: kept **76.7% -> 66.6%** (suppressed 2.94M ->
 4.21M chars, ~317k more tokens in that corpus alone). Deliberately NOT the audit's
 aggressive 2000/800/400, which measures 42.6%: over-tightening forces an extra read call,
 and every extra call re-sends the whole context, which can cost more than the bytes it
 saves. Head+tail are preserved and the full output still goes to the spill file.
 The remaining 24 points are available and sized if the owner wants them.
3. **The measurement tool was the weak link.** `tool_sizes.py` hardcoded 8192/4096/1024, so it
 reported 76.7% both before and after — a tool that copies the config it measures cannot
 verify a change. It now reads the thresholds from the live preset (with `--threshold/--head/
 --tail` for what-ifs), which is how the numbers above were produced.

## Deferred, deliberately — and these are the owner's calls, not mine
- **Un-mounting the overlapping web-retrieval MCP servers** (firecrawl 27 tools + jina 22 +
 fetch 6 = ~28-29k tokens of schema on every request). Estimated $2-3 over six days at
 measured cache-hit rates, or 15-20% in any re-pricing where input weighs more. The audit's
 own words: capability risk "small, **not none**" — the survivor must actually cover the work.
 The owner's rule is capability last, so I did not remove tools from every session on my own
 judgement. This goes to him as one question with the numbers, when the authority queue is
 reachable again (the network is down, so it cannot be queued properly yet).
- **"More sessions, shorter" as the default operating rule** (measured as potentially the
 largest single item: a session of S steps at mean context C re-sends S×C prompt tokens, and
 the three most expensive sessions were 52.5% of the day). It costs no capability — the
 mechanism it replaces conversational memory with is exactly the written handoff this system
 already uses — but changing how every session behaves is a behaviour change I will land with
 the instruction block, not as a surprise.
- **Lowering the compaction threshold to 400k** (the owner's own suggestion): the audit's
 arithmetic says it fires 2.5x as often and the net effect is genuinely ambiguous, possibly
 negative. Do items 1-3 first, re-measure, then decide with numbers.
