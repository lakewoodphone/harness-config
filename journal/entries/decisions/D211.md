**D211 · 2026-09-16 · API runaway: cgroup containment applied (5G/8G) and the incident evidence archived in git; the allocator hunt stays open with capture armed.**

**D · 2026-09-16 · The API memory runaway is contained (cgroup limits on the unit) and its evidence is archived in git; the hunt for the allocator stays open, with the capture script armed.**

**D1 — Containment, not a claim of a fix.** `secretary-api` had no memory limit at all, so a runaway reached ~20 GB and the
kernel's *global* OOM killer chose the victim: 8 kills on 2026-09-15 and 23 on 2026-09-16, every one
`constraint=CONSTRAINT_NONE … global_oom`, plus a SIGBUS on 09-16. A drop-in now sets **`MemoryHigh=5G`, `MemoryMax=8G`,
`MemorySwapMax=1G`** (`/etc/systemd/system/secretary-api.service.d/20-memory-guard.conf`, also archived with the incident).
Rationale: the app's healthy warm footprint measured 1.8–3.6 GB and the runaway goes to 20+ GB, so 8 GB keeps ~15 GB of
headroom on the 23 GB host and makes the failure local, cheap and observable instead of box-wide. The subagent's prepared
file argued 3G/6G; I chose 5G/8G because the API's real working set passes 3 GB within an hour of a restart.
**Reversible in one command** — delete the file and `systemctl daemon-reload` (no restart needed to apply or remove) — and it
was applied at runtime with `set-property --runtime` as well, so the running unit is covered without a restart.
*What it is not:* a fix. It caps the damage and shortens each death; P211 stays open.

**D2 — The evidence lives in git, not on the scratch desk.** `~/phone/` is deliberately not load-bearing, so the whole
incident — the 30 KB diagnosis report, the reviewed-but-unapplied `hard_heap_limit` patch, the containment drop-in (proposed
and as applied), the soak/counter/RSS series, the kernel per-task table from the 23:00 kill and the py-spy dump showing 35 of
36 threads parked in the health probe — is archived at
`harness-config/docs/incidents/2026-09-15-secretary-api-oom/` with a README that carries the numbers, the ranked hypotheses and
the exact commands to catch the allocator. Sixteen megabytes of raw profiling leftovers (an extracted py-spy wheel, page-map
dumps) were deliberately left out; the curated 180 KB is what a future session can actually read.

**D3 — The default when a fix is provisional is `NEXT: read the watcher`, not silence.** Both 09-15 fixes were real and
insufficient; the kill count proves it (H390). So the handoff entry must name the artefact that decides it
(`~/phone/oom-evidence/soak.tsv`, `burst-catcher.log`) and what result overturns the claim. A capture script
(`burst-catcher.sh`, 2 s polling, py-spy dumps at 5 GB) is armed for six hours and must be given **hours, not minutes** —
with a 30–60 minute failure interval a 40-minute watch is a coin flip (L1735).
