**D7629 · 2026-10-18 · Estate search decisions D-A..D-G recorded; sessions queried in place, not copied.**

**D — 2026-10-18 — estate search: one query surface on the authority, sessions indexed in place, hosts push deltas**

Decided by me (development architecture, not an owner decision) in response to the owner's
2026-10-18 requirement: every document in every repo and every session on every machine searchable
from one place, under three hours stale, in seconds. Plan and measurements:
`unified-search/docs/ESTATE-SEARCH-PROGRAM.md`.

**What the survey found, measured this session:**
- `secratary-cloud:/root/authority.db` already holds **8,587 sessions / 2,640,513 events**, ingested
 12:05Z today, with `dsh_session_events_fts` answering `dialpad` in **0.04 s** (66,592 hits) and
 rowid agreement **5,000/5,000**. Sessions are centralised; no agent surface reaches them.
- `unified-search` is live on ZABZ-YOGA with **452,700 docs / 9.1 GB**, and on the authority with
 **118,468 docs** that are mail only.
- The laptop refresh task `\DSH unified-search refresh` returns **rc=1** every run: `files:local`
 fails its own age gate (`adapter exited 3 … state=…\files.json`), and `comms:secratary` /
 `journal:secratary` ssh to the **frozen office box** and time out. `docs:local` last succeeded
 **2026-09-16**.
- **ZABZ-TECH has no index at all** (`reach: "skip"`, no `~/.usearch`): 197 dirs in `~/code`,
 1,527 live + 3,507 archived session files.
- `config/corpus-registry.json` still names `secratary` / `secratary-ts` as the authority, 7 days
 after the cutover to `secratary-cloud`.

**Decisions:**
- **D-A** One surface: `esearch`, a read-only service on `secratary-cloud:3095`, `/search` + `/health`,
 merging `authority.db` and `estate.db` by reciprocal rank fusion. `ps_search` calls it.
- **D-B** Sessions are queried **in place** in `authority.db`, never copied into `estate.db`: raw
 text is ~10.9 GB (mean 4,120 B × 2,640,513) and a copy would be a second truth on a disk with
 22 GB free.
- **D-C** One central `estate.db` on the authority, written only by the service, fed by **deltas**
 from each host's local index. `db:localdb` (215k rows of per-host SQLite dumps, incl. 120k SMS
 duplicating authority comms) is excluded centrally. Central budget **≤6 GB**, guarded.
- **D-D** Freshness is the age of the **newest document per source**: host sync hourly, alarm at
 150 minutes, `/health` fails at 180. A job that ran is not a job that indexed.
- **D-E** Build on workstations; the authority only serves reads, with a `MemoryMax` ceiling. No
 crawl, ingest or test suite on the company-DB host.
- **D-F** Windows hosts **push** over HTTP; the authority never pulls, because a Windows node's ssh
 shell is PowerShell and that is why the registry's ssh reach could not work.
- **D-G** `fa` is retained unchanged for `symbol` and `--fresh`; `esearch` marks indexed answers
 `live:false` so an index is never mistaken for a verified definition.

**Consequence accepted:** the answer surface is one API and one command, but it reads two SQLite
files. "One database" is honoured as *one authoritative store per corpus class, one query path* —
not as a single file, because the alternative duplicates 10.9 GB of text and creates a second
session truth.

**Also recorded, not acted on:** `dsh_session_events_fts` is a *contentful* FTS5 table, so the
authority database holds the event text twice (~10.9 GB duplicated; `page_count` 8,054,139 ≈ 33 GB).
Recreating it as `content='dsh_session_events'` would free ~10 GB, but it is a multi-hour rebuild of
a live authoritative table and is therefore an owner-visible operation, not a side effect of this
program.
