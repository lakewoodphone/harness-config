## 2026-10-09 · Decisions taken while making the shop's money & customer tracking survive long-term

All engineering decisions, taken under the standing rule that architecture, tooling and sequencing
are mine. Recorded so the next session does not relitigate them, and so each can be overruled on
evidence rather than on feeling.

### 1. The long-term series is append-only, and a re-measurement is a NEW row

`~/.lpt-reports/tracking.db`. Never overwrite a historical observation. When a feed catches up and a
day's figure changes, BOTH observations survive and `v_latest_observation` resolves to the newest —
so the change itself is visible. Value-derived identity was rejected: it cannot distinguish "we
re-measured, nothing changed" from "nothing happened", and it splits one period into two rows the
moment a feed catches up.

Also fixed by construction: `observed_at` is when the numbers were TRUE, not when we recorded them.
This is what stops a backfilled artifact from being ranked above a live measurement.

### 2. NULL is not zero, and money is INTEGER cents

An unmeasured metric is NULL with a reason in `detail_json`; the reports print `-`. Measured reason
this matters: a wrong DB path silently produced an empty database and a report full of confident
zeros. Zero-that-was-measured and zero-nobody-looked-for must never render the same.

### 3. A period that still contains today is `[part-period]`, and its percentages are suppressed

Measured 2026-10-09 00:45: `trend` printed `card_takings -960.64 (-100.0%)` for a day 45 minutes old.
Correct arithmetic, false statement. The absolute move is still shown, marked; the percentage is
removed. The clock had not made that comparison.

### 4. The guard runs daily for a weekly job

`lpt-report-freshness.py` at `45 7 * * *`, while the report runs `35 5 * * 0`. Copied deliberately
from `~/bin/lpt-audit-freshness.py`. A guard inside the weekly job cannot report that the weekly job
never ran — that is precisely how five weeks passed unnoticed. It asks three SEPARATE questions
(did it run / did the store advance / are the sources alive) because a pipeline that runs but records
nothing is still broken.

### 5. One implementation of each rule, and duplicate rule copies are a defect in their own right

`dbsource.py` (DB/enum helpers) and `config.py` + `classify.py` (classification) are now the only
implementations. The duplication was not merely untidy — four copies had already drifted apart and
disagreed on 6-16 rows every month, silently. **A forked copy of a business rule is a defect even
while both copies are still correct**, because nothing detects the day they diverge.

### 6. The runner reports `findings`, not `FAIL`, for a tool whose exit code is a finding

`partner-referral-audit.py` exits 1 when it *finds* an anomaly. Recording that as a failure would cry
wolf every single run, and a status column that always shouts is a status column nobody reads. Crashes
still fail the run.

### 7. The work was pushed on a branch, in an isolated worktree, never to `master`

`lpt/business-reporting-longterm-20261009`, built in `~/code/_worktrees/lpt-reporting-20261009` and
committed with an explicit pathspec list. The shared checkout is dirty with another session's work
and `master` is badly diverged from origin (local 118 ahead, origin 279 ahead). Integrating is a
separate, deliberate act — not something to do at the tail of a build.

### 8. The dead Windows runner was left in place, not deleted

`scripts/lpt-monthly-analysis.ps1` cannot run on the authority, and `lpt-business-report.sh` replaces
it. It was left because the Windows machines are still in the estate and deleting another session's
file at the end of a long build is how work disappears. Flagged as a next step instead.
