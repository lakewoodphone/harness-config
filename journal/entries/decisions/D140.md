**D140 · 2026-09-14 · The broker can start a subscription - and does it by writing nothing to tenant_billing_state, because that upsert is a full-row replace.**

**D69 (repo: `decisions/38` is the record; this is the journal copy) — The broker can start a subscription, and it does so by writing nothing to `tenant_billing_state`.**

The gap this closes, measured: `grep -i 'checkout|subscribe'` over `server/app/` returned only a dashboard WebSocket message type. There was a webhook, a portal for an *existing* customer, seat counting, usage metering and a grace period — and **no way to become a customer**. `plan_code` defaulted to the literal string `'beta'` and `billing_seat_price_cents` to `0`.

**Built** (`e2888d8`): `app/billing_checkout.py` (customer creation + Checkout session + a pure readiness payload), `POST /owner/billing/checkout` registered in `app/route_security.py`, and the site's `POST /billing/subscribe` which hands the provider's redirect to the browser without following it server-side.

**Three decisions inside it, each removing a failure mode rather than adding a feature:**

1. **The tenant id rides on `client_reference_id` AND `subscription_data[metadata][tenant_id]`.** The second is the key `billing._extract_stripe_tenant_id` already reads, so a subscription started here is attributed by the **existing** webhook with no new event handling. Asserted field-by-field in a test, because if that key moved a real payment would arrive with no tenant attached and nothing would crash.
2. **A customer is created, never adopted.** Finding an existing customer by email is the obvious convenience and it is a cross-tenant leak: it would attach a paying household to whatever customer row happens to share that address. Stripe permits duplicate emails, so creating is safe.
3. **The route writes nothing to `tenant_billing_state` — deliberately.** The natural call is `upsert_tenant_billing_state(tenant_id=..., external_customer_id=...)`, and it is **wrong**: that method is a **full-row replace**, `ON CONFLICT(tenant_id) DO UPDATE SET status=excluded.status, current_period_end_ts=excluded.current_period_end_ts, plan_code=excluded.plan_code, ...`. Passing only a customer id would **erase the subscription status, the period end and the plan code** on an existing subscription, silently and with no error. Instead Stripe creates the customer from `customer_email` and the webhook records the id — the only writer that already writes a full row.

*Rule this establishes, and it generalises past billing:* **a function named `upsert` that behaves as a full replace will be misused by the next caller, and the misuse is silent.** When adding a field to a row, either merge-read-modify-write with every existing value carried forward, or use a purpose-built narrow writer — never a full-row upsert with one field populated. This was one call away from erasing real subscription state, and it was caught by reading the SQL rather than the signature.

*Second rule, from the same round:* when a digest-pinned audit goes red after an unrelated change, **read the control before regenerating the snapshot.** `automated_failed` was `0` and no control had failed — only `http_route_count` (335 → 336) and the coverage digests had moved, because a route was genuinely added. Refreshing the sign-off was then correct, and it was refreshed as an honest attestation (`reviewer: zabz-agent`, `method: automated`, notes stating **no manual review was performed**). Regenerating first would have been the same act with the evidence unread.

**Dormant by default:** no price and no webhook secret ship as defaults (`test_defaults_keep_checkout_dormant` pins it), so an unconfigured deployment cannot charge anyone.

**Still needed from the owner, and it is the last mile:** the exact per-device price (band already decided), a Stripe Product+Price id, and `LPT_BILLING_STRIPE_WEBHOOK_SECRET` — currently **empty while the secret key in the same file is live-mode**, so the webhook 503s while the key is live.
