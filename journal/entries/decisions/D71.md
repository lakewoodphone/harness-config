**D71 · 2026-09-14 · The frontend hosting target becomes Cloudflare Workers Static Assets.**

The owner asked whether Netlify is the best option and, when given options, said: analyse
what works best, is easiest for an AI agent to maintain robustly and control, and is
cheapest, then implement it. This records the choice and why.

DECISION: the frontend hosting target becomes Cloudflare Workers Static Assets. Both
sites (lakewood-phone-test, lakewood-phone-prod) run the same artifact with different
build-time env, exactly as the Netlify contexts did.

WHY, against the three criteria he named:

1. Cheapest. Cloudflare charges nothing for static asset requests - "Requests to static
 assets are free and unlimited", no storage cost (Cloudflare docs,
 workers/static-assets/billing-and-limitations, updated 2026-04-23). Netlify charges 15
 credits per production deploy against a 300-credit free allowance, which is 20 deploys a
 month for a repo that deploys ~37 times a month; measured burn is ~555 credits/month, and
 the alternative is 108 USD/year (Personal, about 66 deploys) or 240 USD/year (Pro). At
 ~97% of Netlify's burn being the act of deploying, paying would buy a bigger metre, not
 remove it.

2. Easiest for an agent to maintain and control. No plan, no quota, no per-deploy metering,
 no dashboard step: `wrangler deploy` is a command, the config is a file in the repo, and
 the artifact is the same `frontend/dist` we already build. The failure mode that blocked
 this release - a vendor allowance silently exhausted - cannot recur, because there is no
 allowance. Rollback and versioning come from Workers' own versions rather than from a
 bespoke script, which is also why this beat self-hosting on Hetzner: self-hosting would
 have meant writing and owning atomic deploys, rollback and cert renewal myself.

3. Robust. Static assets on Cloudflare's edge, with no server of ours in the path. Self-
 hosting would have put the site's availability on the same box as the API. Our DNS is
 already Cloudflare, so this adds no new vendor to the trust surface, and the cutover is
 reversible by moving one origin.

REJECTED, with reasons: Netlify paid tiers (metered per deploy, and the metre is the
problem); self-hosting on lpt-apps (we would own the machinery, and the site would ride on
the API box); Vercel (meters everything, 100 GB transfer guideline, plan terms reportedly
restrict commercial use); GitHub Pages (needs a paid plan for a private repo, no SPA
fallback, cannot proxy).

STATUS: built and verified, not cut over. The live sites still serve from Netlify. Cutover
needs a Cloudflare API token (none exists on any machine - only cloudflared tunnel tokens)
and a DNS change per hostname. Both are the owner's to grant.

Verified on the real Cloudflare runtime against the real build: deep links and unknown deep
routes return the SPA shell, `/phone-repair` serves at its own path, `/privacy-policy` 301s,
`/api` is refused with a 404, security headers apply, hashed assets get the right content
type, and both `_redirects` and `_headers` parse with zero invalid rules. The Netlify path
is untouched and regression-checked.
