## DECISION — an owner "COMPANY IS DOWN" text now requires 10 minutes of continuous non-answer, not 4

**Changed** 2026-10-14 ~17:17Z on BOTH emitter nodes, byte-identical
(sha `7546181920e4f9d6`, 56,334 bytes): `waze-mdm-01:/root/company-heartbeat.sh` and
`lpt-apps-01:/root/company-heartbeat.sh`, `FAIL_THRESHOLD=3` → `6`. Backups kept on each node as
`company-heartbeat.sh.bak-blip-20261014T171712Z`. `bash -n` clean on both.

**Why.** The composer probes every 2 minutes and fires `(N-1)*2` minutes after `down_since`, so N=3
texted the owner **4 minutes** into an outage. His own messages that day were about a 4-minute blip
and a 73-minute freeze. With `company-api-liveness.timer` now healing the API in ~6 minutes, a
6-minute rule would text him about outages the estate repairs by itself; N=6 = **10 minutes of
continuous non-answer** is the smallest bar that is honestly silent about everything we fix
unattended. Unchanged: the 6-hour re-alert timer, the 1-per-30-min floor, the 6-per-24-h ceiling and
C1 (recovery is never texted) — those already bound repeats. `FAIL_THRESHOLD` gates only the `down`
class; the peer, standby and guard-exposure checks do not read it.

**Verified behaviourally, with no SMS possible.** Against a dead endpoint in a sandbox state dir
(`HEARTBEAT_STATE_DIR=/tmp/hb-proof`, `HEARTBEAT_URL=http://127.0.0.1:9/health`), six dry runs
(`ALERT_DRY_RUN=1`, which decides exactly as production does and sends nothing) produced
`consecutive_failures` 1,2,3,4,5,6 and **zero** alert decisions at 1-5 and exactly one at 6;
`grep -c 'ALERT SENT'` = 0. Under the old threshold that same sequence would have texted at run 3.
