**D247 · 2026-09-17 · Remote children are placed by the broker; the fixed target is an explicit opt-in.**

DECIDED 2026-09-17 (development decision, mine, recorded not escalated). Where a remote child runs is now ASKED FOR, not configured, and the rule lives in the package so no deployment file has to be read to know it: packages/plugin-remote-fanout/lib/index.js `resolvePlacementMode()` -> `placement` from the row, else MESH_PLACEMENT, else MESH_TARGET_NODE set by hand => fixed, else BROKER. A broker that cannot be reached is a reported `broker-unreachable` rejection from start(), never a fall back to the fixed target; the fixed path still exists as the explicit opt-in and logs a warn line at registration naming the broker as unconsulted. One placement per child (`POST /place` before each child, `POST /done` at settle), because that is what makes the broker's own count of accepted jobs true; `task.exclude` is wired as config and defaults to EMPTY, because excluding a node per sibling would be inventing a spread policy the broker does not have and would send a child to a 4-slot node while the desktop had 15 free. The queue is surfaced through a durable per-child ledger file (<DSH_HOME>/mesh/placements/<id>.json), the engine log, and the child's own report - `position > 0` means the child has NOT started and it is not published to ctx.subagents while it waits. Evidence: docs/mesh/92-provider-placement.md.
