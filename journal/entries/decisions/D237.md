**D237 · 2026-09-15 · Stills for the vanished camera entities come from the NVR channel; the recorder stops journalling presence sensors.**

**Decision (2026-09-15): stills for the two views whose Home Assistant camera entities no longer exist now come from the NVR channel directly, and the recorder is no longer journalling the two presence sensors.**

**The two dead still streams.** `scripts.yaml` asked `camera.snapshot` for `camera.cam_waiting_room_main` and `camera.cam_deserted_exit_main`. Neither entity exists — the Dahua config entries behind them are `disabled_by: user` — and each call sat behind a guard testing for `unknown`/`unavailable`, so the failure was completely silent. Measured from the files: the `waiting_room` and `exit` still labels stopped dead on **2026-09-14** while `doorbell`, `interior` and `hallway` continued, and nothing noticed for a day and a half.

Fixed by calling `phoenix_still_waiting_room` / `phoenix_still_control_room_exit`, which fetch one JPEG from the verified NVR channel (ch5 and ch1) and address the camera by channel rather than by an `entity_id` that can rot. Both verified: HTTP 200 in ~2 s, 205,894 and 333,338 bytes, 2560x1440. Detached, because they are fired from snapshot scripts and HA kills a shell_command at 60 s.

Rejected alternative: re-enabling the disabled config entries. It would have restored the two entities, but it also brings back each entry's whole entity set (including the noisy `cam_*_motion_alarm` binary sensors, none of which ever transition), and it depends on the entity_id being recreated without a `_2` suffix. Addressing the channel is smaller and cannot drift.

Not fixed, deliberately: the `snapshot_latest_with_retries` calls that feed the public `/local/snapshots/latest_*.jpg` tiles still name the dead entities, so those two tiles are stale. Visible tile work, not evidence, and the tiles exist for notifications.

**The recorder.** There was no `recorder:` block at all, so every entity in the installation was journalled. Two presence sensors dominated it:

 binary_sensor.control_room_hub_control_room_moving_target 27,720 state changes / 7 days
 binary_sensor.presence_sensor_motion 22,059 state changes / 7 days

That is ~50,000 changes a week of noise sitting in the same history someone has to read to answer "what happened at 3pm" — which is the complaint the audit started from. Both are now excluded via `entity_globs`, `purge_keep_days` raised from the default to 30 so the review window is longer than a week and a half.

Checked before changing anything: neither entity is referenced anywhere in `/config`, and every `history_stats`, `statistics` and `trend` platform in the live config lives in `climate_health.yaml` reading climate sensors — so the exclusion removes clutter and no dependency. Excluding an entity from the recorder does not stop automations reacting to it; the state machine is separate.

Verified after the restart: both entities produced **0** rows in the following 3 minutes, while `binary_sensor.phoenix_outside_door_contact` recorded 3. (A naive 15-minute window showed 92 and 63 rows — all from before the restart. Restart-boundary discipline matters when checking a recorder change.)
