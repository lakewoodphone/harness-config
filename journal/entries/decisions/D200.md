## What this round did about it

**`journal/tools/fix-encoding.py`** — a peer tool (not a change to `journal.py`, which is blocked by
the pain recorded as P204):

- **Round-trip repair, per line**: `line.encode("cp1252").decode("utf-8")`. Only lines that are
 *wholly* a cp1252 artefact survive it. A plain ASCII line is unchanged; a line carrying a
 **legitimate** `·` or `—` fails the round trip (U+00B7 is not valid UTF-8 as one byte) and is left
 alone; a line mixing real non-ASCII with damage also fails and is reported rather than mangled.
 That safety property is why this is not a hand-written find-and-replace table.
- **A sequence pass** for the mixed lines, built *from the transformation* rather than typed by hand
 (`ch.encode("utf-8").decode("cp1252")`), for the artefacts that are unambiguous wherever they occur.
- **Dry run by default**, `--apply` to write, `<file>.bak-encoding` left beside each repair, and
 `LOSSY` reported as unrepairable when the byte is already gone (U+FFFD): a decode that has lost the
 byte cannot be inferred here, and pretending otherwise would invent content.

Result on `entries/`: **6 files repaired, 0 mixed, 0 lossy.** Diff verified line by line before
