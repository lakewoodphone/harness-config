**D2648b · 2026-09-25 · 2026-09-25 - the authority's comms push will NOT be changed to fill Communication.transcription yet: the body already carries the transcript, and it is a production writer.**

Decided 2026-09-25 while the transcript work was fresh. Recorded so it is not re-opened as an oversight.

The authority's `website-comms-push.py` -> `app/services/website_db.py:insert_communication()` writes the
Dialpad call body, which EMBEDS the transcript under `[Retranscript]` / `[Transcript]` / `[Dialpad ASR]`,
but it never writes the website's `Communication.transcription` column - which is why that column is empty
on all 123,592 production rows. The website now reads the body instead (`extractTranscriptFromBody`, shipped
and verified live: 22 of one customer's 32 calls render their transcript).

I am deliberately NOT changing the push path now. Reasons, in order:
1. It is a writer against the PRODUCTION website database on a cron; the column being empty costs nothing
 today because the body already carries the same text and the console reads it.
2. The change is not one line: `insert_communication()` has no transcription parameter, and there is a
 dedup/attach path (`_ref_existing_rows`, `_attach_communication_to_customer`) that must stay correct.
3. Verifying it needs a real new call (dedup skips every existing row), so it cannot be proven tonight.

WHEN TO DO IT INSTEAD: the moment someone wants to search across call transcripts, or report on them -
i.e. when a query needs the text as DATA rather than as prose. At that point it is worth doing properly:
add the parameter, populate it for calls that have a transcript, backfill by re-deriving from `content`
for the 1,609 rows that already carry one, and prove it against a fresh call.
