**D66 · 2026-09-14 · Retention starts when we hold the data, not when the device says the moment was.**

The first version of the review-record purge keyed on `ts` — the timestamp the phone supplies. A test caught the consequence immediately: a row whose capture time was months old was deleted the instant it arrived, and two pre-existing tests (which use fixed 2026-02-26 timestamps) failed because their rows vanished. The same thing would happen to a real customer with a wrong clock, or to a device that had queued uploads offline. *Rule:* a retention period that starts at an unverified, client-supplied time is not a period we can state honestly in a parent notice — so the purge keys on `received_ts`, the moment we took the data, and the test now pins that.
