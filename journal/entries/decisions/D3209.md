**D3209 · 2026-10-14 · The counter status selector has two scopes (OPEN/ALL), one rule read by request and row filter - and a monitor may not call a capped system dead.**

**D · 2026-10-14 · The LPT counter's status selector has TWO scope values, `OPEN` and `ALL`, because a label and a value that differ is the defect the owner reported.**

Decided and implemented in `frontend/src/features/staff-intake/staff-intake-status-scope.ts`. The owner's report (2026-10-14, ledger item 216) is a control labelled **All statuses** that behaved as **Open**: one value (`'ALL'`) behind two controls, mapped by the request builder to the four open statuses, so the three finished statuses were never in the payload and no search could reach them.

The decision, and the parts that are load-bearing:
1. `OPEN` = the four statuses in which the device is still with the shop, **and the default**, so the counter's default screen shows exactly what it showed before — a fix to a filter must not silently change what the shop sees when it opens the page.
2. `ALL` = all seven, and it goes to the **server** (`queueStatusesFor` → `workOrders.getAll statuses`), because the list queries are bounded at 100 rows each and a client-side "search everything" is a page, not a search.
3. **ONE rule, two readers**: `statusFilterSet` is read by both the request builder and the row filter. Two copies of that rule is exactly how the request and the screen came to disagree; a second copy is also how the old counter offered `IN_REPAIR` months after the status was deleted.
4. An unreadable `?status=` falls back to the **default scope**, never the widest one — `?status=DROP%20TABLE` must not become a search over the whole history.
5. A search miss under a narrowed scope **names the scope and the control that widens it**, instead of pointing at a queue that returns the same empty screen.
6. The two scopes are stated **on the screen** (each radio says what it means; the summary line says `open jobs only`; the sr-only note states both), because the whole defect was a screen that said one thing and did another.

Not decided here, and left to the roadmap: whether any OTHER control on the site has the same label/behaviour gap. That is the class row filed unchecked in `docs/website/ROADMAP.md` (OWNER-FILED P3), which is where the owner-feedback contract wants the class rather than the one button.

**D · 2026-10-14 · A monitor may not call a capped system dead.** `autonomy-status.sh`'s first PROBLEM was `the dispatcher heartbeat is 183.4 minutes old (>15) - nothing can revive work` while the dispatcher was alive and correctly idle under a spent daily cap (150/150). The release heartbeat is written BY a release, so it ages whenever nothing is released — a reading that cannot distinguish "dead" from "capped", which is the class of defect that has cost this estate the most. Fixed by measuring `wake-fanout.log` (appended every minute) alongside it and saying which gate is in force; the dispatcher is only called dead when BOTH are stale.
