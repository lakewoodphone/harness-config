**D3037 · 2026-10-08 · Production session lifetimes: access token 7d -> 30d, refresh 7d -> 90d, secret untouched.**

## The change
Production `/opt/lpt/.env` on `lpt-apps-01` (the file the live `lpt-backend` container reads):

```
JWT_EXPIRES_IN=7d -> 30d
JWT_REFRESH_EXPIRES_IN=7d -> 90d
```

Applied 2026-10-08 ~22:09Z by recreating the container with the image it was already running
(`LPT_BACKEND_IMAGE=lpt-lpt-backend:1e6a6ee8c234 docker compose up -d --no-deps --force-recreate
lpt-backend`, working dir `/opt/lpt`). `JWT_SECRET` was **not** touched and was verified unchanged by
sha256 before and after (`e640ee40…`), so no existing session was invalidated by this work. Backup:
`/opt/lpt/.env.bak-before-jwt-ttl-20261008T220837Z`. Health after: `healthy`, db 120-237 ms.

**The compose gotcha that cost the first attempt:** `/opt/lpt/docker-compose.yml` defaults the image to
`lpt-lpt-backend:local`, which does not exist on the box, so a plain `docker compose up -d` tries to PULL
it and fails (`pull access denied`), leaving the running container on its old config. The real tag comes
from `LPT_BACKEND_IMAGE` (set by `scripts/deploy-backend.sh`). Check `.deployed.json` for the live tag.

## Why (the owner's words: "keep getting signed out … for some reason")
The pair was **7 days for both**, and they are minted at the same instant, so the moment the access token
dies the refresh token dies with it and no refresh can rescue the session. On top of that the client is
not allowed to try: `frontend/src/lib/trpc.ts` calls `handle401Error()` on **any** 401 (lines 425-426,
443-444, 478-479, 496-497), which deletes `accessToken`/`refreshToken` and redirects to
`/login?expired=true`. Proven in the live database, not inferred — user 299 (`chevedy@gmail.com`, MANAGER)
has three refresh tokens, all `isRevoked = false`, created 2026-10-06, 10-07 and 10-08, and exactly three
`sessions` rows dated at those three logins: **she has logged in fresh three days running and has never
once completed a refresh.** A 401 `auth.validate` at 17:48:09Z on 2026-10-08 was followed by a failed
login attempt at 17:50:22Z (`Invalid email or password`, same account) and a successful one at 17:51:02Z —
a password typed by hand, and mistyped once, forty seconds before succeeding.

With `access = 30d` a device that is opened at least monthly never sees a 401 at all, so the wipe path
never fires; with `refresh = 90d` the session can also be renewed without a password once the client defect
is fixed. `sessions.expiresAt` is derived from the ACCESS ttl (`auth.service.ts:333,890`), so session rows
now live 30 days; a refresh mints a new session row, so renewal is unaffected.

## Known, not fixed here
The client defect itself. Left deliberately: it is the live login path of the shop's production site, the
symptom is already gone with the TTL change, and a bad edit there locks staff out. The exact fix is
recorded in the handoff, in this session's journal entry, for a change that can be deployed and watched.
