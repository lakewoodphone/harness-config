**D198 · 2026-09-15 · idguard: collision-safe ids as a peer module, consumed by the sync.**

## What was built

**`journal/tools/idguard.py`** — a separate, read-only module that answers two questions the
journal could not answer about itself, and is now wired into the 15-minute autosync so it runs
unattended on every machine:

1. **`--floor`** — the next free id per kind, taken from the working index **and every ref**
 (`git show <ref>:journal/index/entries.tsv`, one blob read per ref). Measured
 2026-09-16: `decisions=D198, handoff=H364, lessons=L1681, pain=P204, wins=W174`.
2. **collisions vs divergences** — per id, between the working tree and a ref:
 - **collision**: same id, different **host**, **date** or **heading** → two different entries
 wearing one id. Renumber one.
 - **divergence**: same id, same host/date/heading, content differs → the *same* entry edited
 on both sides. Merge it; do **not** renumber it.

`--strict` exits 1 when any collision exists, so it can gate a script.

## Verified, with the ground truth rather than an assertion

The collision of 2026-09-15 left two refs behind that are a known answer:

```
python journal/tools/idguard.py --local-rev 919cfa64 --refs 613ee55
 -> collisions: 98 divergences: 0
git diff --name-status 919cfa64 613ee55 -- journal/entries -> 98 paths
```

Exactly the set, none missed, none invented. Against the live converged tree: **0 collisions, 0
divergences**. `--strict` on the colliding pair exits 1; on the live tree exits 0.

The host/date **plus heading** rule is deliberate. Judged by content hash alone, every ordinary
edit looks like a collision. Judged by host/date alone, `W148` was misclassified — a real
collision where both machines recorded the same host *and* the same date — which is why the
heading is part of the test. That single id is the difference between a detector that reports 97
and one that reports the true 98.

## Why a separate module, and why the sync is the consumer

**Separate module**: the journal's own tool could not be extended. Adding ~120 lines to
`journal/tools/journal.py` flipped `check` from **1 error** to **~1090 errors** (`heading does not
match the <kind> heading form`, on real entry files), and that is recorded separately as a pain
entry because it is a defect in `check`, not in the addition. A capability that can only be
delivered by destabilising the continuity tool is not worth delivering that way; a peer module
delivers it with zero risk to `check`.

**The sync as the consumer**: the fault is invisible to both `journal.py check` (compares ids
within the working tree) and to a fast-forward (`autosync.ps1` never merges). So the one place it
is *guaranteed* to be seen is the sync itself — it fetches every 15 minutes, on every machine, and
already writes a machine-readable status that the attention plugin and the CEO kernel read.
`id_collisions` is now a field of that status: `-1` = not measured, `0` = measured and none, never
a null. A collision is recorded, not turned into a sync failure: the sync may still be perfectly
able to fast-forward, and only the resolution of a collision needs a person.

## What is NOT yet done, stated plainly

- `journal.py next-id` still computes its floor from `git_max`, whose docstring claims *"Highest
 number visible in any local or remote git ref"* while the code greps only the working tree and
 `HEAD`. **So the mint path is still blind** — `idguard --floor` gives the right number, but
 nothing calls it from the allocator yet. Fixing that means editing `journal.py`, which is
 blocked by the pain recorded this round.
- Detection is wired; **resolution is still manual** by design. Renumbering an entry changes a
 reference other machines may hold, so it stays a deliberate act, documented in D191/D193.

## Evidence

- `python journal/tools/idguard.py` → `collisions: 0 divergences: 0` (live tree vs upstream).
- Ground truth run above: 98 / 0 against `613ee55`, matching `git diff --name-status` exactly.
- `~/.dsh-sync-status/status.json` and `%LOCALAPPDATA%\harness-config-autosync\status.json` both
 carry `"id_collisions": 0` after a hand-run of `scripts/autosync.ps1` (exit 0, `[clean]`).
- `scripts/autosync.ps1` unchanged in behaviour otherwise: same result line, same exit 0.
