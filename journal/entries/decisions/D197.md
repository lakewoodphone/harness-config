**D197 · 2026-09-15 · Reconciliation runs as a reporter on three named clocks (push, website-freshness, whole-set check); never auto-creates customer records; one PCI message deliberately withheld; a check that is red every run is decoration.**

**D195 · 2026-09-15 · The reconciliation is a REPORTER on three named clocks, and it never auto-writes
customer records.**

Decided while ending the 12-hour website silence. Three cron entries, installed at
`5,35 * * * *`, `*/15 * * * *` and `23 */4 * * *` (backup `~/crontab.backup-20260915T234441Z`,
43 → 46 lines, nothing removed):

1. `website-comms-push.py` — pushes what the harvest collected, by calling the application's own
 idempotent functions with the application's own windows. No new matching logic, no SQL of its own.
2. `production-comms-freshness.py` — fails when the WEBSITE's clock is stale, measured from
 `website_sync_cursor.last_synced_at` and the website's own newest row.
3. `lpt-recon-check.sh` — the whole-set check: asks the push tool what it *would* create (read-only)
 and runs `lpt-recon.py`.

**Every one of them was executed exactly as cron runs it, not merely installed** — rc 0, rc 0, and
rc 1 with `push_would_create=7`. And the schedule itself was then observed firing:
`CRON[463225]: (zabz) CMD (... production-comms-freshness.py ...)` at `23:45:01`, with that run's status
file written. "It is configured" is not evidence; a cron line that has never fired is a hypothesis.

**The design constraints, each with its reason:**

- **No email, ever, from these.** The owner's rule: nothing outbound without his explicit per-message
 instruction. They write status files under `~/.lpt-recon/` and exit non-zero; the existing
 owner-attention digest is what surfaces them.
- **The push never creates a customer from an unmatched phone.** `website_db.py` already refuses
 (`if not customers: continue`), and that refusal is *correct* even though it is also why 74 of the
 111 missing messages still cannot reach the website. Widening it is a business decision about
 manufacturing customer records from unknown numbers, not an engineering cleanup — so it is left
 alone and named (axis G's G-008) rather than quietly "fixed".
- **One message is deliberately NOT reconciled.** `dialpad_sms_cache` message_id 6252044111880192
 carries a full card number, expiry, CVV and ZIP. It is withheld from the push until the owner
 answers queue 67 (`--include-pci` overrides). A reconciliation that blindly makes two stores agree
 would have copied card data into a third place.
- **A check that is red every run is decoration.** `dedup.dialpad_sms_cache` failed on a row count that
 axis D proved benign (2,744 groups differing only in `session_id`, 0 in `body_text`); it now fails
 only on a genuine text conflict. `identity.gap` counts unnormalised addresses and is labelled
 informational with axis C's authoritative 1,463 stated beside it.

**Result:** `lpt-recon.py` reads `16 ok · 0 FAIL · 0 could not measure` — and the green is worth
something only because every FAIL it showed today was real, was investigated, and was either fixed
(the website silence, 116,558 → 116,685 rows, newest message 11:34:24Z → 23:43:48Z) or shown to be a
false alarm of the checker's own making.
