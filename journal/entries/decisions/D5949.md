**D5949 · 2026-10-14 · DSH window origins move from 3200 to 19200, because the OS dynamic range owned 3200.**

**Decision:** the DSH multi-window origin base is **19200** (band 19200..19223), not 3200. `multi-window/windows.json` -> `origins.basePort`. Commit f73d521d.

**Why:** 3200-3223 sits inside the Windows dynamic port range on every machine that runs this launcher (1024..15000 on both ZABZ-TECH and ZABZ-YOGA), so Windows itself can reserve the block — and on ZABZ-TECH on 2026-10-14 it did, refusing 360 binds with EACCES for seven minutes after boot, which is the whole of the owner's "dsh is unreachable" (L3809, P3183). 19200 is outside the dynamic range and outside every excluded range on both machines; 24/24 binds were verified before the change. Dev decision, mine, no owner input needed.

**Consequences, all of them paid for on 2026-10-14:**
- The base is part of a window's ORIGIN, and `localStorage['dsh.sessions.current']` is keyed by origin. Moving it resets which session each window was last on: the owner picks his session again once per window. That is the price of a working GUI at boot, and it is the smaller one.
- The window registry (`~/.dsh/multi-window/windows-registry.json`) rows for the old ports are closed by `rule=port-mismatch` and the working set has to be re-recorded. Done on ZABZ-TECH by marking one live slot open and running `dshw restore`, whose own tail records every live slot (verified: rows `1 - main`, `2`, `6`, `7` -> 19200/19201/19205/19206).
- A machine still running the old proxy is a **stray**, not a fault: `Test-OriginsProxy` asks the configured base, finds nothing, and `Start-OriginsProxy` starts the new one (PATH 1 refuses a stale hidden wrapper, PATH 2 re-registers). Verified on ZABZ-YOGA: 19200 came up 24/24 with the old 3200 proxy still serving an existing window, which is why yoga's window was not disturbed.

**Applied:** ZABZ-TECH (proxy restarted, 4 windows live on the new base) and ZABZ-YOGA (new base up; old 3200 proxy left running so the open window keeps working — it dies at the next reboot; yoga never hit the EACCES itself). DESKTOP-FGV6KMH is unaffected: its machine config has no `origins` block, so it opens windows directly against the engine port.
