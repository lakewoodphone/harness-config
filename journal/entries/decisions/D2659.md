**D2659 · 2026-09-28 · Production schema migration is HELD - per-migration classification, and the A2P campaign-sample question that decides it.**

**D-level: production migration is HELD, and here is the per-migration classification that decides it**

Decided 2026-09-28 (ZABZ-YOGA). Production's schema is NOT migrated tonight. `lpt_test` IS (verified
`Database schema is up to date!`). This entry exists so nobody re-litigates it and nobody runs
`prisma migrate deploy` against production believing it is a formality.

I read every `migration.sql` in the five pending files. The set is NOT uniform, which is why "the copy
worked, so run it on prod" is not a good enough argument:

| migration | what it actually does | risk |
|---|---|---|
| `20260922000000_waze_billing_metering` | three `CREATE TABLE IF NOT EXISTS` (`waze_billing_periods/_reports/_runs`) + indexes | **additive, safe** |
| `20260925130000_add_laptop_preference_forward_markers` | `ALTER TABLE laptop_preferences` adding columns | **additive, safe** |
| `20260925120000_fix_laptop_preferences_condition_column_case` | column-case fix on `laptop_preferences` | **mechanical** |
| `20260914120000_unify_budget_tiers_add_condition_preference` | RENAMES three live `BudgetTier` enum values (`VALUE_200_400`→`MID_600_750`, `ALL_AROUNDER_400_700`→`UPPER_MID_750_900`, `POWER_700_PLUS`→`HIGH_900_1200`), adds a fourth, adds `laptop_preferences.condition_preference` | **semantically meaningful, but intended.** Postgres enum renames keep the OIDs so no row is rewritten — but the LABEL a live row carries changes meaning. That is the point (an owner decision of 2026-09-04 to unify the bands), and it is written idempotently. Not a fault; not nothing. |
| `20260925120000_fix_a2p_auto_reply_shop_hours` | sets the column DEFAULT and then `UPDATE`s every `a2p_auto_reply_config` row whose template contains the stale clause `Sun-Thu 6-11 PM` | **THE ONE THAT MATTERS — it rewrites the automatic SMS every first-time texter receives.** |

THE REASON THAT LAST ONE IS HELD, and it is not caution for its own sake: this is A2P 10DLC traffic. The
campaign is registered with the carriers and a registration declares SAMPLE MESSAGES. If the live
auto-reply text stops matching the registered samples, carriers can filter or block the traffic — and the
commercial meaning of that is that **customers who text the shop get nothing.** Nothing has yet checked
whether the corrected text still satisfies what the campaign declares. That is being researched; the
answer decides whether the whole five can go as a set, or whether four go and one waits.

Also held because it would not have bought anything visible: the computer-finder funnel has a SECOND
blocker — `laptopPreference.upsertMy` returns **401 "Customer authentication required"** and
`getForCustomer` 401 "Authentication required" — so the missing column was never the thing a customer
would hit. Fixing production's schema tonight would have carried every risk for no visible gain.

PRODUCTION IS NOT TOUCHED AND NOT DAMAGED. Full dump taken and kept:
`/root/lpt-prod-20260928T164420Z.sql` (117 MB). The reconciliation that DID work on the copy was:
trim the five orphan `_prisma_migrations` bookkeeping rows (they record migrations whose EFFECTS are
already present, so nothing is dropped), then `prisma migrate deploy` for the five real ones. One orphan
row literally carries the checksum `0000_applied_manually`, which is how it got this way.

WHAT WOULD MAKE PRODUCTION SAFE TO MIGRATE, in order:
1. The A2P answer above.
2. A rehearsal of the exact sequence against `lpt_test` — which is already up to date, so a rehearsal
 needs a fresh clone of prod into a scratch database, not a re-run on the copy.
3. Confirmation that production's DEPLOYED backend was built against this migration set (production's
 code is older than `test`'s, and applying migrations a live process was not built against is a guess
 about that process).

EVIDENCE: the five `migration.sql` files quoted above, read 2026-09-28; `prisma migrate status` on
`lpt_test` → `Database schema is up to date!`; the 401s quoted verbatim from a live call. The
post-reconciliation verification and the `/apps` render are in H2788.
