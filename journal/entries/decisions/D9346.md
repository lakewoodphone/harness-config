**D9346 · 2026-10-21 · A CI gate watcher now runs on the authority, not on GitHub, because the old one died with the fuse it watched.**

**Decided and installed 2026-10-21 on `secratary-cloud`: a CI gate watcher that runs on the authority, not on GitHub.**

## Why
The check built to catch a refused job (#569, "the daily check reads job annotations, so billing cannot look quiet") runs on `ubuntu-latest`. During the 2026-10-21 outage it was refused too — maintenance run 39557157587 failed at 06:43Z with three 0-second refusals. **A watchdog on the fuse it watches is not a watchdog.** The detector had to move somewhere that does not depend on the thing it detects.

## What
- `/root/bin/ci-gate-watch.py` (installed, syntax-checked, exercised through `cron-wrap.sh`).
- Cron: `*/15 * * * * /usr/local/bin/cron-wrap.sh ci-gate-watch <b64>` — added to root's crontab; the diff was one line, and the prior 265 lines were preserved.
- State and output under `/root/.ci-watch/`: `status.json` (every run), `state.json` (processed run ids, dedupes across invocations), `ALARM` (written only while firing; renamed to `ALARM.cleared` when it clears), `run.log`.
- Token: read from `/root/.git-credentials` (scopes gist, read:org, repo, workflow). The value is never printed by the script.

## The signal, and why it is the only unambiguous one
A refused job is `conclusion == "failure"` AND `steps == []` AND `runner_name == ""` AND a hosted label. A real test failure always has steps; a skipped job is `skipped`; a cancelled job is `cancelled`. **And a refused job bills zero minutes, so no cost report can ever show it** — which is why an alarm is the only instrument that sees it. Verified both ways: silent on the healthy state, and it fired on 10 known-refused jobs in the 10:17–10:20Z window with the same job ids I had already confirmed by hand (119168024631, 119168024883).

It also flags a second silent failure: a run `queued` for more than 10 minutes.

## The rate-limit lesson, built in
The script's first version refused to run when the token's bucket was low. That is wrong — the token is shared with the whole estate, so refusing means going blind exactly when the estate is busiest. It now **degrades**: below 400 remaining it checks the newest 3 runs instead of 20, and only gives up below 40. Measured while installing: budget 341, it ran in degraded mode and reported cleanly.

## What it does NOT do
It does not send anything to the owner. It writes `ALARM` and `status.json` on the authority. **A file nobody opens is the same failure mode as no alarm**, so the remaining step is a channel — SMS through the company's existing path — and that is outbound, so it needs the owner's explicit per-message approval. Recorded as open, not as done.

## Verification
`cron-wrap.sh` recorded `ci-gate-watch-now 0 2` in `~/.cron-status/runs.tsv`; `status.json` written with `ok:true, budget:340`. The cron line is installed and visible via `crontab -l | grep ci-gate-watch`.
