**D266 · 2026-09-17 · Multi-window model: one shared browser profile + one loopback origin port per window; per-window profiles stay as an escape hatch.**

DECIDED 2026-09-18, ZABZ-YOGA. windows.json gains browser.profileMode ("shared" default | "per-window") and an `origins` block (enabled, basePort 3200, count 24, script dshw-proxy.mjs, ttlMs 15000).

WHY NOT THE ALTERNATIVES the brief listed:
 (b) lazy creation of windows on demand and (c) a bounded restore set were both REJECTED as the primary model because they BUY MEMORY BY REMOVING SOMETHING THE OWNER ASKED FOR. He asked (2026-09-11 brief) for at least 8 independent windows reopening after a restart; capping how many come back is a behaviour regression dressed as an optimisation. The shared tree gets the memory without touching that.
 (a) alone was therefore chosen: one browser process tree, one window per slot, N distinct origins.

WHY THE ORIGIN AND NOT JUST THE PROFILE: per-window session identity is localStorage["dsh.sessions.current"], keyed by origin. Sharing the profile without giving each window its own origin would make all sixteen windows share ONE session slot, last writer wins on reload - the exact limitation the private profiles existed to avoid.

MEASURED COST OF THE DECISION: the browser process is now a single point of failure for every window (a renderer crash still takes only its window). That is the accepted price, and it is why profileMode is a config key rather than a deletion - "per-window" restores the old behaviour exactly, including its 9 processes / ~892 MB per window.

NOT CHOSEN BUT RECORDED: the engine'"'"'s own listArtifacts() walk (681 dirs, 5.9 s raw, no cache) was NOT made faster, because that needs a server-side change and therefore an engine restart, and the engine serves the owner'"'"'s live work. Paging or trimming the stored sessions was rejected too: all 681 are from the last 7 days and are his working history.
