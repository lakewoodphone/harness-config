**D2973 · 2026-10-08 · W2 order-status verdict - the code is right, six test suites were stale (D1-D5).**

## Decisions taken in W2, 2026-10-08 (ZABZ-YOGA)

**D1 — A status enum rename is not a licence for a find-and-replace in tests.** Where the old list was
`['CHECKED_IN','AWAITING_DIAGNOSIS','AWAITING_PARTS','IN_REPAIR']` and the new one is
`['AWAITING_DIAGNOSIS','AWAITING_APPROVAL','AWAITING_PARTS','AWAITING_PAYMENT']`, the substitution
maps two old names onto one new one and deletes the fourth, so a mechanical rewrite silently *shrinks*
the set. Every status-set assertion must be re-derived from `ACTIVE_ORDER_STATUSES` /
`CLOSED_ORDER_STATUSES` in `services/work-orders/order-status.ts` and the *count* checked, not just the
spelling. Evidence: `getOverdueOrders`/`getUpcomingOrders` in `query.service.test.ts` expected two
states where the shop means four.

**D2 — An array status filter is passed through, not de-duplicated, at the query layer; the router
de-duplicates at its own boundary.** `WorkOrderQueryManager.findMany` hands `status: [...]` to Prisma as
`in: [...]` verbatim (`query.service.ts:369`) — that is what "should handle array filters" means and
what the test now pins. The tRPC router de-duplicates deliberately while preserving order
(`normalizeStatusFilter`, `workorders.ts:213-219`) because it is the layer that folds legacy aliases
onto live values and should not emit `in: ['X','X']`. Two layers, two answers, both intentional.

**D3 — Written together, or not at all: `status` and `isApproved`.** `updateStatus` writes
`isApproved: approvalProjectionFor(status)` in the same statement as the status, because under the
seven-state model the boolean is the status's projection and a job is un-approved if and only if it is
`AWAITING_APPROVAL`. Tests that pin the `updateById` write object must include it. `record a change
that makes this fail again` — do not re-assert the old two-key object.

**D4 — A `$0.00` total out for pickup needs a closeout reason, and a balance still owed needs a
`completionReason`; these are two different rules at the same transition.** A test whose title says
"without reason" must say *which* reason and must not have the other rule in play (settle the mocked
payments, or pass the reason). Conflating them is how `mark-as-paid-deprecation` and
`status-transition-reason-enforcement` both came to assert something untrue about `READY_FOR_PICKUP`.

**D5 — In this lane the production code was never the wrong side.** Six files, eleven failures, all
assertion mismatches; nothing allowed a release or a charge in a state it should not be. Recorded so
the next session does not reopen the status model looking for a bug that is not there.
