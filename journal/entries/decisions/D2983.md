**D2983 · 2026-10-09 · unified-search is the system of record for indexed search; find-anything is retained only for live symbol lookups.**

**D197 · `unified-search` is the system of record for indexed search across this estate; `find-anything` is retained only where an index must not be trusted**

Decided 2026-10-09, ZABZ-YOGA, measured against the owner's standing requirement: *"all of them fully
indexed and super fast … any information an agent needs should always be his fully in under 5 seconds
from any of our files anywhere."*

**The three surfaces that exist today:**

| surface | how called | indexed? | Windows? | status |
|---|---|---|---|---|
| `unified-search` (`usearch.py`, `use.py`) | `python scripts/usearch.py query …` | yes — FTS5, 7 adapters, federated across hosts | **cannot be called at all on Windows** | architecturally correct, currently broken |
| `find-anything` (`fa`) | `fa <mode> <query>` | path index, ctags index, journal index; **code content is a live ripgrep** | no | good tool, narrower, and the one agents are told to use |
| `ps_action("search")` MCP | from any OS | proxies the above on the authority | yes | unavailable when the authority is offline |

**Decision.** `unified-search` is the surface everything should call. It is the only one designed for the
job — a corpus registry, seven adapters emitting one document contract, idempotent per-document ingest,
staleness recorded per source, and a federated query path. `find-anything` is not deleted and not
deprecated as a tool: it keeps the modes where an index must never be trusted — `symbol` (always live,
because you may be about to edit that definition) and `--fresh`. What is retired is the *instruction*:
the `fast-search` skill and `presets/zabz/agent.cordis.yml` must stop telling agents that `fa` is the
primary search surface, because it cannot answer a content question at all and returns confident false
negatives on ordinary multi-word queries.

**Why this is a decision and not a preference.** Measured on the same query, same machine, 2026-10-09:
`usearch.py`'s own SQL answers in **163 ms warm**; `fa journal "lpt website deploy"` returns **exit 1,
no match**, while `fa journal "lpt website"` returns 11 hits — a false negative manufactured by the query
shape. The owner's criterion is about *complete* answers under 5 s, and a fast wrong answer fails it
harder than a slow right one.

**Consequences accepted.** (1) unified-search has **no git remote** — it is a local-only checkout on
ZABZ-YOGA deployed to the authority by copying, so it has one point of failure and cannot be
coordinated across machines; that must be fixed before the estate depends on it. (2) Its index is
**8.53 GB on this laptop** and one query cold measured **112 s**, so "the system of record" is a claim
about architecture, not about current behaviour — the defects in the accompanying pain entry are
prerequisites, not follow-up work. (3) `fa`'s cross-node `fa-estate` remains the only cross-machine
search for now, and `unified-search`'s federated `use.py` path is untested from a Windows node.
