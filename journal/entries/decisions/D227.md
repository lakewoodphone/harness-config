**D227 · 2026-09-16 · Placement wave: serve-phone runs a second engine on one DSH_HOME (verified); a network-shared DSH_HOME is impossible; the mesh capacity tables already exist; secratary is 4 cores.**

Three findings from the placement wave (20-placement.md), and what each settles.

1. CONFIRMED BY ME FROM SOURCE - a live second-engine defect on the iPhone path.
`scripts/serve-phone.ps1:16-18` says, verbatim: "The engine here is DEDICATED and on its own port,
because `--trusted-host` is a startup setting and changing it means restarting the engine - which
would kill every session in the one you are using. It shares DSH_HOME, so it is the same agent: same
preset, same tools, same session store." `$Port = 3085` (line 27). That is the one-writer rule
violation `multi-window/windows.json:5` calls UNSUPPORTED: two `dsh web` processes on one home have
been observed writing duplicate sequence numbers into one session log and making the whole history
unloadable. Mitigating fact: the per-session write lease is a kernel semaphore in the `Local\`
namespace, so two engines on the SAME machine do exclude each other on that path - the risk is
narrower than "it will corrupt", but it is real and unnecessary.
THE FIX (handed to the transport wave, which owns this domain): launch the PRIMARY engine with the
tailnet `--trusted-host` authority (a launcher change in dshw/windows.json, per node) and then
`tailscale serve --bg 3099` publishes the existing engine. One engine per DSH_HOME, phone access,
no second process. Preference when they conflict: an unroutable phone beats a second engine.

2. IT IS NOT A POLICY, IT IS IMPOSSIBLE - a network-shared DSH_HOME cannot be made to work.
Read from code: the session write lock is a named kernel semaphore in the **`Local\`** namespace
(`dsh-session-persistence-jsonl/lib/index.js:555-557`), i.e. per-MACHINE by construction, so two
hosts sharing an SMB path cannot exclude each other; atomic publish is
`MoveFileExW(..., MOVEFILE_WRITE_THROUGH)` with **no cross-volume fallback** (`:452`, `:534-543`;
ERROR_NOT_SAME_DEVICE -> EXDEV); and identity is decided by `realpath` (`:3241-3254`).
CONSEQUENCE: session state must be node-local. Any "spread the writers across the mesh" design has
to be about stores OTHER than session state (the journal, the DB, artifacts) - not about a shared
DSH_HOME. Record this as settled so it is not re-proposed.

3. DO NOT BUILD A NEW CAPACITY REGISTRY - the data already exists server-side.
`personal-secretary-mvp/app/services/next_stage_runtime.py:173-185` already has
`next_stage_node_reports` (PK `source_machine`; role, os, hostname, uptime, disk_json, services_json,
repos_json, reported_at), plus `:156-167` `next_stage_machine_access_checks`, aggregated by
`run_mesh_world_index` (`app/autopilot.py:3827-3831`). The placement queue should EXTEND that table
rather than introduce a parallel source of truth. A mesh-wide grep found no lease/heartbeat/placement
table, so the queue itself is genuinely new work.

4. MEASURED, and it contradicts an easy assumption: **the authority (secratary) has only 4 cores and
23.4 GB RAM** (`ssh secratary-ts "nproc; free -m"` -> 4; 17,404 MB available). It must be the control
plane, never the fleet host. That is also the number behind the owner's "upgrade the secretary
server" question.
