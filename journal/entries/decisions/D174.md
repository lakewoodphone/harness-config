**D174 · 2026-09-15 · Window URL policy: tokenized first, clean origin last; recover the token from the engine log; prove it in doctor.**

DECISION (2026-09-15, ZABZ-TECH): every DSH window opens the engine's TOKENIZED launch URL.

ORDER OF RESOLUTION (`Resolve-WindowUrl` in `harness-config/multi-window/dshw.ps1`):
1. `state.json`'s recorded `url` for that port, but only if it validates as
 `http://127.0.0.1:<that port>/?token=<non-empty>` (`Test-LaunchUrl`).
2. Otherwise the LAST `dsh web: <url>` line in the engine's newest log for that port
 (`<port>.log`, else the log named in the state record) that validates the same way. This matters
 because the token changes on every engine restart and `state.json` can lag it (adopted engine, or a
 restart that died before saving).
3. Only if neither yields a token: the clean origin `http://127.0.0.1:<port>/`, which then depends on
 that browser profile already holding a session cookie.

WHY THE TOKEN, NOT THE COOKIE: the token authenticates regardless of the cookie jar, so a brand-new or
expired profile can never land on the 401 page; the cookie path is exactly what broke for a day. A stale
token is harmless -- the server 303s an already-cookied browser to `/`.

WHAT IT COSTS: each window URL carries the launch token in its command line, which is already visible in
`windows.log`, the engine log and `state.json`; `dshw doctor` prints it redacted. The token is per
process, not per window, and is bound to `127.0.0.1`, so this does not widen the exposure.

VERIFICATION THAT SHIPS WITH IT: `dshw doctor` -> "window url ... (tokenized)" and an HttpClient probe
with redirects OFF that must return 303 (PowerShell's `Invoke-WebRequest -MaximumRedirection 0` throws
on this, and a following client reports a harmless 200 -- both are wrong instruments).

REVERSES: commit 4d9a0ad (2026-09-14), which opened the clean origin on an unmeasured premise.
