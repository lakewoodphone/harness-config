**D147 · 2026-09-14 · The dead camera path had three stacked causes - wrong port, empty channels, orphaned entity names.**

**D (2026-09-14) - The dead camera evidence path had three independent causes stacked on one symptom, and only the first one looked like the problem.**

Proven end to end at 20:37 ET: `script.snapshot_entry_cameras` and
`script.snapshot_control_room_cameras` both ran with **`Dahua snapshot failed` = 0** and wrote
**three real JPEGs** -- `verify443b_doorbell.jpg` (37,792 B), `verify443b_hallway.jpg`
(152,473 B, NVR channel 5) and `verify443b_intrusion_control_room_interior.jpg`
(318,906 B, NVR channel 6). Before this: roughly 500 failures an hour and no evidence at all.

**Cause 1 -- wrong port in all six config entries.** `port: "80"`. The component's rule is
`protocol = "https" if int(port) == 443 else "http"`, so it built `http://…:80`, the NVR answered
**302** to `https://…:443`, and aiohttp **drops the digest authorization** when the scheme and port
change. Every snapshot therefore arrived unauthenticated and the NVR answered 500. Fixed by setting
the six entries to `"443"` (`.storage/core.config_entries`, backed up, JSON validated, then
`ha core restart` -- a config entry's `port` has no reconfigure flow, the Dahua flow returns nothing
for `entry_id`).

**Cause 2 -- three entries pointed at NVR channels with no camera.** Channels 0, 2 and 4 return
`Error / Bad Request!` while 1, 5, 6, 7 and 8 return JPEGs. Those three entries were *guaranteed*
failures on every sweep, and every failed login feeds the NVR's illegal-login lockout
(`LockLoginTimes=10`, `LoginFailLockTime=1800`) -- which is what kept the HA host's IP blocked and
made a **correct password look like a wrong one for days** (L262). Entries disabled, not deleted:
re-enable them if those cameras come back.

**Cause 3 -- the scripts referenced entity ids the component had orphaned.** The Dahua component
changed its `unique_id` scheme from a hash (`43d946db242577fe15fd239f3e5db8e5_5_Main`) to the NVR's
serial number (`8C03EA3PAZC4C2D_5_Main`). Home Assistant could not reuse the old entity ids, so it
created a second generation (`_main_2`, `_sub_4`, `_sub_2_2` -- a third generation) and left **96
orphaned entities** registered and permanently `unavailable`. The scripts use the clean names
(`camera.cam_front_hallway_main`), which were held by the dead generation, so
`snapshot_latest_with_retries` hit its own "camera unavailable" guard and **stopped silently** --
zero files written with no error logged. Fixed for the three live cameras by removing the dead
entity and renaming the live twin onto the clean name (`config/entity_registry/remove` then
`config/entity_registry/update` with `new_entity_id`).

**Why the third cause mattered most for diagnosis:** it is the only one that fails *silently*. The
port bug and the empty channels both logged errors; this one produced nothing at all, so the script
looked like it had run. A `stop:` inside a script is invisible unless you read the trace.

**Still owed:** the other ~93 orphans (the audit's "114 collision suffixes") want the same treatment,
properly, with the entity and device registries both considered. Not done here -- this was targeted
at the evidence path, on a live security system, late.

**Recorded as the general trap (L262):** a device answering **500 with no `WWW-Authenticate` header,
even to a request carrying no credentials**, is refusing the *source*, not the credentials. Five
credential-shaped theories died against that one observation tonight.
