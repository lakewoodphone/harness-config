**D72 · 2026-09-14 · The computer-finder questionnaire is a customer-facing feature, so it is gated by `customerProcedure` — and its budget bands are the four the owner decided, not the three the code had.**

Phase 3 of the LPT account plan, done and live on **test**. Two facts, both measured:
(1) `laptop-preference.ts` used `protectedProcedure` for all three procedures, and `protectedProcedure` throws FORBIDDEN when `role === 'CUSTOMER'` (`backend/src/trpc/context.ts`) — so the questionnaire's own audience could never submit it. With the page also unrouted, the feature was dead twice over. All three are now `customerProcedure`, which requires a CUSTOMER linked to a Customer record and guarantees the `customerId` the row is keyed on.
(2) The tiers were `$200-400 / $400-700 / $700+` while the retired Google Form said `Under $400 … $1200` and the sourcing parser said `Basic/Good/…` — three sources, three answers. Unified on the owner's decided set: `$600-750 / $750-900 / $900-1200 / $1200+`, and `conditionPreference` (new / refurbished / open-box / none) was added, because the Google Form asked it and the sourcing workflow treats it as a hard filter while the website form never asked it at all.
*Rule this establishes:* a customer-facing surface is gated by the procedure whose audience it is for. `protectedProcedure` means **staff-only** in this codebase; reaching for it because a route happens to require login produces a feature that is reachable and unusable, which is the most expensive kind of dead code because every screenshot and test of the UI looks fine.
