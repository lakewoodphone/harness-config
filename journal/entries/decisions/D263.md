## Two of my briefs were wrong, measured

1. **The `L1680` "encoding collision" was fabricated by idguard itself, not by damaged bytes.** The
 committed index blob is valid UTF-8 (`C2 B7` → U+00B7). `subprocess(..., text=True)` decodes with
 the **locale** codec — cp1252 on this machine — so `index_at()` produced `Â·` for the ref side while
 `index_on_disk()` produced `·` for the same value. Two readers, two encodings, one invented
 collision. Fixed by decoding git output as UTF-8 explicitly. **So D200's premise is corrected**: the
 six entries I repaired really were damaged (verified by diff), but the *collision* I attributed to
 encoding damage was my tool's decoding bug. Same class of failure as everything else in this system:
 a reading taken through the wrong lens, reported confidently.
2. **The ground-truth set is 98 *M* ids, not the 312 paths I put in the brief.** `git diff
 --name-status 919cfa64 613ee55 -- journal/entries` lists A 212, D 2, M 98. An added or deleted id
 exists on one side only and cannot collide with anything; the collisions are exactly the M ids. The
 self-test asserts the M subset and prints the A/D counts so the filtering is visible. Comparing
 against all 312 would have failed — my brief would have produced a broken test.

## What idguard now does (`be153e5` on `agent/idguard-harden`, unmerged)

- `--selftest` with the known answer: **98/98, missed 0, extra 0**, exit 0. Non-vacuity measured:
 against a ref that does not hold the pair it reports `97/99, missed L221, L223`, exit 1; against a
 missing ref it prints **"REFS ABSENT … THIS IS NOT A PASS"** and exits **3** — a code distinct from 0
 and 1, so "cannot verify" can never be read as a pass.
- **UNCOMPARABLE is now a state.** A ref whose committed index does not exist is named as
 uncomparable instead of yielding an empty far side and printing `collisions: 0`; `--strict` exits 1
 on it; a run with no upstream falls back to `refs/remotes/origin/master` rather than comparing
 nothing. That was the bug that fed **`0` into `~/.dsh-sync-status/status.json` every 15 minutes** —
 a refusal published as health, which is the exact failure shape this system exists to kill.
- `--floor` now reads the claim ledger the way the writer does: local `journal/alloc/bands.tsv` UNION
 the blob at `refs/remotes/origin/master:journal/alloc/bands.tsv`. Measured wrinkle: the local file
 holds **2** rows, the published ref holds **5** — reading the file alone would have called three
 kinds unclaimed while this host holds them. It prints both numbers (the "above every ref" floor and
 what `journal.py append` would write) and states which rule produced them, and never blurs
 claimed / exhausted / unclaimed.

## The P0 root cause, located (shape measured, line suspected)

`afbd9f3a`'s **root tree is the repository root with `journal` removed and `alloc` added** — the whole
tree is shifted one level, so `journal/` holds what the repo root held and the entries vanish
(2,432 → 1,178 paths). Suspect: `_build_claim_tree` (`journal/tools/journal.py:3314-3337`) walks
`range(len(parts) - 2, -1, -1)` but calls `_list_tree(new_tree)` on the tree at the **current** level,
and its `depth == len(parts) - 2` branch keeps only `meta.endswith(" blob")` entries — which
structurally cannot carry a subtree. Not proven line by line: the shape is measured, the code is the
suspect.

**Guards designed, not built** (both belong in `journal.py`, which is where the defect is):
resolve each level from the ORIGINAL parent tree by path prefix instead of the rebuilt one; never
filter out `tree` entries; and before any push assert the new tree differs from its first parent in
exactly one path — `git ls-tree -r <new> | wc -l == parent_paths ± the one ledger file` — refusing
otherwise. That is the pre-push guard `P262` says does not exist.
