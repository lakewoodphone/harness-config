## 2026-10-12, ZABZ-TECH. Owner: *"find the flow... we did a lot of work to make a very robust usb
flow, i don''t want it lost"* then *"yes land it"*.

### THE APPRAISAL THAT FOUND IT
The kit was **not on disk anywhere**: `tools/lpt-access-kit/` did not exist in
`personal-secretary-mvp` (the checkout sat on `integrate/dialpad-reconcile-20261007`), not in
`lpt-hub`, not in `harness-config`. It was **not on `secratary-cloud` and not on `zabz-tech`**.
It existed as git objects only, on four refs: `origin/zabz/usb-kit-hardening-20261005` (tip
`df642e9f`), `safety/local-master-20261007`, `fix/dialpad-backfill-cursor-20261006`, and a stash.
**31 files, and nothing newer than `df642e9f` (2026-10-05) exists on any ref.**

Its dev evidence was still on this machine - `C:\Users\ezabz\.dsh\tmp\lpt-A2-realrun-134721`,
`lpt-A6-deep-135412`, `lpt-accept-140059` and more - which is how the work was identified as real
rather than abandoned.

**The index was pointing at a path that did not exist.** `lpt-hub/docs/customer-operations/
FLOWS-INDEX.md` names `personal-secretary-mvp/tools/lpt-access-kit/RUNBOOK.md` as the canonical
entry point for "the remote USB flow", and calls `lpt-diagnostics-kit` superseded. The superseded
one was on disk; the canonical one was not. That is the defect class `harness-config/AGENTS.md`
section 0 exists for - an index that is not a fact.

Worked on `origin/master` in an isolated worktree so the in-flight branch was never touched:
`C:\Users\ezabz\Code\_worktrees\psm-master-land`, branch `land/lpt-access-kit`.
**All 25 kit commits cherry-picked, clean, in order** (`e235a583` ... `df642e9f`). They are purely
additive to `tools/lpt-access-kit/`, so the retired-kit files at their other paths never collided.

Verified before pushing, on master:
- **31 files present**, all four launchers among them.
- **`tests/Test-KitIntegrity.ps1` -> `KIT INTEGRITY: ALL 9 CHECKS PASSED`** (no credential used; no

**Pushed: `2cacc735..c0f9673f HEAD -> master`**, and confirmed by re-fetching `origin/master` and
counting 31 kit files in its tree. Every machine that pulls master now has the flow.

machine that pulls. A dead laptop no longer takes it.

the account when next at those machines."* Those machines still carry the retired account.
**Also unchanged:** the `FLOWS-INDEX.md` row still points at the right path - that part was correct,
the path simply had no files behind it until now. Re-verify the index still matches reality.
