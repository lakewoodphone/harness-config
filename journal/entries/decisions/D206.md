**D206 · 2026-09-16 · Persistent shell rejected for now: it loses run_in_background, escalation, the spill file and Job-object cleanup; the runner's 135 ms and its cleanup guarantee are the same purchase.**

## Decision: do NOT adopt `dsh-tool-pwsh-persistent` for now
The gain is real — ~660 ms per call (warm ConPTY round trip measured at ~34 ms against ~540-700 ms
cold) — and the price is capability, which the owner's rule puts last. Read from source, it
loses:

| Lost | Consequence |
|---|---|
| `run_in_background` | every long build goes back to the 120 s foreground cap — the exact failure in L1566, where a foreground call was killed mid-restart and left the API down |
| `sandbox_permissions` / `justification` | a denial becomes final; there is no same-turn escalation path |
| the spill file | output is cut at 16,000 chars **keeping the head and dropping the tail**, with no path to the rest — today the tool keeps a 64 KB tail in memory and spills 64 MB to a named file |
| per-call `workdir` | absent; a `cd` prefix leaks the cwd into later calls |
| `timeoutMs` | fixed at plugin level, not per call |
| `description` | presentation only, minor |
| separate stdout/stderr | ConPTY merges them; a command's streams cannot be told apart |
| **Windows Job containment** | ConPTY is explicitly outside Job containment (`dsh-subprocess-local\lib\index.js:1025`); cleanup reverts to descendant enumeration + signals, which the code itself documents as not guaranteeing termination — the class that produced ~2 GB of MCP residue (L1701) |

It also **cannot mount today**: it declares `inject = ["tools", "terminals"]` and nothing in this
profile provides `ctx.terminals` — `dsh-terminal` is mounted by `dsh-sdk-minimal` only, not by
`dsh-base` and not by the `web` profile.

The runner's ~135 ms and its cleanup guarantee are the **same purchase**: the Job object is what
makes `TerminateJobObject` kill every descendant unconditionally, and `ChildProcess.kill()` does
not kill a tree on Windows. Removing it to save 135 ms trades a bounded, measured overhead for an
unbounded leak this business has already paid for twice. The tool-call audit's own words:
*"the Job owner is load-bearing for cleanup and must stay."*

## What would change this decision
1. **Upstream the missing parameters** into the plugin (a ~30-line change): `workdir`,
 `run_in_background`, per-call `timeoutMs`, `description`, and the escalation pair. This is the
 only path with no permanent capability loss. Not available offline.
2. **A pipe-based persistent shell instead of ConPTY** — OpenHands ships exactly that on Windows
 in production: one `powershell -NoLogo -NoProfile` over pipes with JSON metadata between
 prompt markers, which keeps stdout/stderr separable and avoids the ConPTY owner. Worth
 prototyping before paying for ConPTY.
3. **The gate test, if either is tried:** start `Start-Sleep 300` in the background, kill the
 owner, then confirm **no surviving `pwsh`**. If children can outlive the engine, the persistent
 path needs a Job-owning spawn, not a preset change.

## Interim
Mounting `pty` + `terminal-pwsh` into the owned host layer (additive, zero latency effect, turns
the persistent path into a one-flag experiment) is the audit's recommended first step. It is
**not** done: it requires editing `~/.dsh/profiles/web/cordis.patch.yml`, which is outside
harness-config and therefore outside the sync that keeps both machines identical — a change that
lives on one machine only is worse than no change. It belongs in harness-config with the sync
extended to carry it, which is its own small task.
