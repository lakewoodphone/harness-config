## 2026-10-05 17:51 UTC · ZABZ-TECH · lpt-access-kit: the first real run found the seam bug the 165 unit checks could not - one run is now one folder

CHANGED
- THE PIPELINE HAS NOW RUN ON REAL HARDWARE, for the first time. Every agent that wrote it reported SHELL: DEAD, so nothing in it had ever executed; I had only ever dry-run the entry point. Running it capture-only on ZABZ-TECH is acceptance test A2, and it immediately found a real integration defect that all 165 unit checks had missed.

THE BUG THE REAL RUN FOUND: the collector ALWAYS creates its own <stamp>_<host> folder inside -OutRoot (it wants a ROOT, not a run folder), while the entry point pre-created a sibling folder for the window state and the handoff. First real run produced TWO folders - one holding access-window.json, decision.json and handoff.json, the other holding the 41 captured sections. So the window record and the captured state were in different folders, and Ingest would have reported NO_HANDOFF and an UNVERIFIED WINDOW on EVERY run. A false alarm on the one warning that matters would have trained everyone to ignore it.

THE FIX reorders the steps and is better for it: CAPTURE FIRST, then decide, arm, open. The capture must reflect the machine BEFORE we touched it - not after we added an account, a firewall rule and a service. The run folder is then identified by DIFFING the root before and after the capture, not by parsing console text. The safety order is unchanged: the teardown is still armed before any access exists, and if it cannot be armed the window is not opened.

A2 EVIDENCE (real run, unelevated, Quick, on ZABZ-TECH):
 1 folder under the root, holding run.log, SUMMARY.md, manifest.json, report.json, decision.json
 41 section files, EVERY ONE with a STATUS header: 35 OK, 6 COULD_NOT_READ, 0 with no header
 transport decided T1 READY from a REAL probe (shop LAN, filter absent), not a synthetic one
 exit code 2 = completed with unanswered sections, reported honestly
The 6 unanswered are all elevation-gated - BitLocker state, the BitLocker recovery key, powercfg, the
minidump folder, SMART reliability, chkdsk results - each naming its reason. That is the designed
behaviour: a section that could not be read says so rather than writing an empty file that reads as clean.
