## 2026-10-19 01:50 UTC · ZABZ-YOGA · Anti-reset build round 5: the evidence store exists and proves a wipe in a test; nothing writes to it yet

Goal round 5 of the anti-reset objective. The store that makes a wipe provable now exists and is tested.

BUILT: server/app/phone_evidence.py - an append-mostly phone_identity_evidence table created on demand,
with record() and merge_into_row(). Three rules are the design: previous_android_id is captured BEFORE
android_id is overwritten in the same statement; an empty/older report never erases evidence a newer
client supplied; and a replayed heartbeat cannot manufacture a change, so a retry can never page a parent
for a wipe that did not happen. latest() returns None on a missing table rather than raising, because a
store that has not been created is "no evidence", not a monitor crash.

WHY ITS OWN TABLE, not new columns on phones: the phone row is written by log_hello (benchmarks only) and
log_heartbeat (the real per-beat writer); adding five columns there means editing two section modules, the
protocol, both backends and a migration. Evidence also has a different lifecycle - it must survive the
phone row being deleted and re-created.

VERIFIED on zabz-tech: 27 tests green (8 evidence-store + 19 classifier). The last evidence test is the
point: a stored android-id change produces WIPE_CONFIRMED at level 4 from the real row shape.

TWO TEST EXPECTATIONS WERE WRONG on the first run and were fixed in the tests, not the code: the first
report of a new id IS a change, and a row with no evidence has no android_id key at all.

PUSHED f7ba27d (store), 1fb89eb (doc) on agent/kf-counter-install-nonwipe, plus the test fix.

THE REMAINING GAP, written into the design doc: nothing calls record() from the heartbeat path yet, and the
monitor does not call merge_into_row(). Until those two calls exist the detector still classifies silence
only - the store is ready and unused. That is the whole of the next round's work, and it is small.
