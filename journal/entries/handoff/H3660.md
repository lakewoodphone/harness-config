## The live emergency the queue did not contain

While checking the authority for the reading above, `company-api.service` on `secratary-cloud` was found
**wedged**: every endpoint (`/health`, `/docs`, `/openapi.json`, `/v1/models`, `/v1/chat/completions`)
returned `http=000` at an 8-second timeout, and `/v1/models` earlier returned `http=000` at 25.0 s.

Cause, measured not inferred:

- `memory.high` = 4 GiB (drop-in `30-memory.conf`), `memory.current` = 4.65 GiB, `memory.max` = 6 GiB.
- `memory.events`: `high 1321123` soft-limit throttling events, `max 433`.
- `memory.pressure`: `full avg10=84.64` — 84.6 % of the previous 10 s the cgroup spent unable to run.
- Main thread and the `autopilot` thread both in state `D` at `__mem_cgroup_handle_over_high`.
- Same fault as the kernel log entry of 2026-10-14 05:35:26Z: 14.3 GB anonymous, killed by the **global**
 OOM killer.

The fix for exactly this (`40-malloc-arena.conf`, `MALLOC_ARENA_MAX=2`, item 165) was authored on
2026-10-14 and **its own comment says it is effective at the next restart only — and no restart had
happened.** So it had never been tested, and the process still carried 31 of a possible 32 glibc arenas.

**Action:** snapshot the production tree to `/root/company-api-restart-20261014T115527Z/`, run the posture
guard (ALLOW, exit 0), `systemctl restart company-api`. Result, all read back: readiness in **2 probes /
~10 s**; `MemoryCurrent` 4.65 GB → 1.26 GB; `/health` t=6.0 s→0.0057 s; `/v1/models` t=25.0 s→0.0026 s;
`memory.pressure full avg10` 84.64 → 0.00; `MALLOC_ARENA_MAX=2` now present in the process environment
(and proved EFFECTIVE, which the drop-in's author could not do without a restart).

## A kernel finding that was WRONG, and it matters

`app_voice` fired HIGH with *"its INFO narration is suppressed (root logger level or handlers), so nothing
it says can be read."* That is false. The logging setup was never broken; the loop was stalled, so the app
had nothing to say. The check's own docstring names both causes (*"a logging regression ... or a wedged
loop"*) — the summary text carries only the first, so the report sent its reader to logging configuration
instead of to the process. **A diagnosis that is 100 % confident and 50 % wrong is the `wrong-data` failure
this estate measures most.** Fix pending in `/root/ceo-kernel/ck/sentinel.py`.

## Lesson

**A health check that asks "is the unit active" cannot see a wedged process.** `company-api` was
`active`, had `NRestarts=0`, and had been answering nothing for over 50 minutes — and the only reason it
was found is that the API was needed for something else. Every check in the kernel's 19 reads the unit's
*state*; almost none read whether it *serves*. The next check worth adding is one request with a deadline
against the service's own endpoint, not a status line.
