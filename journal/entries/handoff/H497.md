## THE MISTAKE — a rebase I should not have started

Pushing the digest commit from ZABZ-TECH was rejected, and I reacted by running `git pull --rebase` on
**the authority's** `harness-config`. That conflicted on **`journal/state/owner-questions.md`** and left
the repo mid-rebase with an unmerged file. I aborted, verified clean (no rebase, 0 unmerged, 0 dirty),
and re-verified the live digest was untouched.

**Three things I should have done differently:**

1. **Check whether the remote already had a newer version before rebasing.** A rebase is a decision, not
 a reflex to a rejected push.
2. **Recognise the conflicting path.** `journal/state/owner-questions.md` is **generated** — `journal.py
 questions` rewrites it. Rebasing a repo whose *generated* state is owned by another machine's commit
 is a fight with a writer, not a merge. The journal store in this repo has a documented
 contested-ids problem across machines (the authority's own log shows a commit titled *"move THIS
 machine's lineage off the 18 contested ids"*), so the right move was to leave the push to the
 authority's own convergence — which is exactly what the earlier lesson L2104 said about the owner's
 checkout, applied to a different repo one hour later.
3. **Not spend the round on it.** The deliverable was already live the whole time. I kept pushing for a
 version-control copy after the functional fix had landed, and burned a large part of this round on
 it. **Live-and-correct beats committed-and-argued**, and I got that backwards.

**Where my commit stands:** `cb6c109` on ZABZ-TECH. Not on the remote. The change is nonetheless
deployed, regenerated, and recorded here — so it is not lost, only uncommitted upstream.
