## 2026-10-05 17:31 UTC · ZABZ-TECH · lpt-access-kit round 3: the teardown was 46 percent unimplemented and the tests could not see it; collect delivered

CHANGED (all on origin, branch `zabz/usb-kit-hardening-20261005`)
- **The teardown actually removes things now.** `Install-Destructor.ps1` dispatched on `$Action.Action`,
 but the plan builder sets `-Action` to a VERB (`RemoveFile`, `StopAndDeleteService`,
 `RemoveFirewallRule`, `RemoveMarkerBlock`) and `-Kind` to a NOUN (`KeyPath`, `Service`,
 `FirewallRule`, `SshdConfigBlock`). **Seven of thirteen planned actions matched no case** and fell to
 `default`: the key file, the token file, the firewall rule, sshd and the `sshd_config` marker block
 were all reported FAILED while removing NOTHING. Fixed by resolving the verb against BOTH fields
 before dispatch, with an explicit known-verb list and a loud failure for anything unresolvable.
 Proved: all **11** distinct verbs the plan emits now resolve; a run with no unresolved verbs passes.
- `lib/AccessWindow.psm1` now emits the field names teardown reads BY NAME: `sshdServicePreExisting`
 (defaults **TRUE** - never delete a service we did not create), `sshdConfigPath`, `authorizedKeysPaths`,
 `authorizedKeysComment`. 14 assertions fail if any of them is renamed on one side only.
- **My `sshdConfigPath` default was wrong** and the test caught it: Windows OpenSSH keeps its config at
 `%ProgramData%\ssh\sshd_config`, NOT under `System32` (that is the binaries). Pointed at the wrong file,
 the marker block would be written where sshd never reads it.
- **`lib/Handoff.psm1` false positive fixed**: the 32+ base64 blob rule rejected a genuine
 `SHA256:` OpenSSH fingerprint, so the natural T1/T2 revocation id could never be written to a handoff.
 The transport stream had worked around it by splitting fingerprints with spaces. Fingerprints are now
 exempt; a non-fingerprint blob is still refused, and both cases are asserted.
- **`lib/Guard.psm1` `Get-GuardedSummary`** declared `[object[]]`, and a caller passing a
 `List[object]` - what a collector naturally accumulates - threw "Argument types do not match", so the
 collector reported its outcome counts as UNAVAILABLE. Now coerces.

LESSON OF THIS ROUND
A plan that names an action is not a remover that implements it; a helper that describes an outcome is
not a helper that reports it. **Both defects this round were the same shape** - a correct-looking
component whose linkage to the thing it named was never tested. The dry-run suite passed 11/11 across a
destructor that removed nothing, because every check asserted on the PLAN. Test the link, not the
description.
