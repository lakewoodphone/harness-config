## 2026-09-15 19:07 UTC · ZABZ-TECH · Both LPT units Activation-Locked; the endpoint had SIX defects and the SUCCESS/FAILED semantics are inverted

CHANGED — both LPT units are now Activation-Locked, and the feature actually works.
- **DRN 2001 (FFYGNQ8AN72J) and DRN 2002 (FFXGT23HN72J) are locked.** Apple's DEP API returned
 `SUCCESS` on first contact for each; every repeat since returns `FAILED` (nine across the two).
- There were **SIX independent defects** in `/fleet/devices/{drn}/activation-lock`, none visible from the code, each
 fatal alone, each measured against the live NanoDEP daemon:
 1. fleet-api env omitted `NANODEP_URL`, `NANODEP_API_KEY`, `NANODEP_DEP_NAME` (so it called DEP with no auth header)
 2. wrong path — `/v1/device/bypasscode`; the real route is `/v1/bypasscode`
 3. wrong response field — read `bypass_code`; the response carries `{raw, code, hash}`
 4. wrong auth scheme — sent `X-API-Key`; NanoDEP wants **HTTP Basic** `depserver:<key>`
 5. wrong verb — sent `PUT`; NanoDEP answers **POST** (PUT and GET → 405)
 6. **no `User-Agent`** — httpx sends none and NanoDEP rejects that with `400 USER_AGENT_INVALID`; curl always sends
 one, which is exactly why the archived script worked and the app never did
- **The semantics are inverted from the obvious reading:** first contact → `SUCCESS`, every repeat → `FAILED`, and an
 unknown serial → HTTP 200 with `NOT_ACCESSIBLE`. So `FAILED` means ALREADY ON. The original code treated anything
 but SUCCESS as an error, which would have made the endpoint fail permanently after its first successful use. It now
 treats FAILED as already-locked, still rejects `NOT_ACCESSIBLE` with 502, always writes the `fleet_alerts` idempotency
 marker, and never takes a bare 200 as success.
