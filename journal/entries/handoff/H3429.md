### BROKEN — the duplication is LIVE, and the fix script's safety premise is now FALSE

`dsh_session_events_fts` is declared **without `content=`**:

```
CREATE VIRTUAL TABLE dsh_session_events_fts USING fts5(
 source_machine UNINDEXED, session_id UNINDEXED, ordinal UNINDEXED, raw)
```

So FTS5 keeps its own copy of every `raw` value. **Measured: `dsh_session_events_fts_content` holds
1,876,538 rows — exactly equal to `dsh_session_events`.** `sum(length(raw))` over 20,000 rows is
82,416,786 B (~4.1 KB/row), so across 1.88 M rows that is roughly **7.7 GB of duplicated session text**.
`/root/fts-convert.sh`'s own header states the arithmetic: *"events 7.28 GB, fts_content 7.20 GB,
fts_data 2.92 GB = 17.40 GB of a 20.61 GB database. The corpus is stored TWICE."*

**The fix was already written, run, and VERIFIED — and did not reach production.**
`/root/fts-convert.out` (2026-10-09) records `FINGERPRINTS MATCH - the conversion preserved search
results`, `after VACUUM: 14023524352 bytes` (13.06 GiB), `integrity ok`, `WAL mode restored`,
`verdict=ok`. `docs/mesh/126` §1 measures the converted copy as **230 tables**, missing
`dsh_session_events_fts_content`. The **live** `/root/authority.db` is **23,764,770,816 B (22.1 GiB),
231 tables, `_content` present** — so the converted database is not the one serving.

**⚠️ THE SCRIPT'S PRECONDITION IS STALE AND DANGEROUS.** Its header says: *"Safe to run because
`/root/authority.db` is a DISPOSABLE copy: the authority still lives on the office box and a fresh copy
can be made at any time."* **Both halves are now false.** The office box is frozen as the rollback
anchor and `/root/authority.db` **is** the authority, with no fresh copy obtainable. Anyone running
`fts-convert.sh` today would `DROP TABLE dsh_session_events_fts`, rebuild it, and `VACUUM` the live
company database — believing they were on scratch. **Fix the comment before the script is ever run
again**, and treat running it as a production change requiring a window.

**Not done by this session, deliberately.** A schema change plus a `VACUUM` on the database serving

The freed pages do not return to the filesystem without the `VACUUM`; a `DROP`+`CREATE` alone would
stop the growth and let the freed space be reused, but would not reclaim the 7.2 GB.
