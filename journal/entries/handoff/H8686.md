## 2026-10-18 · ZABZ-YOGA · Estate search round 32: three audit scripts, three artefacts, one correction

## What H8685 got wrong

It reported `verification-register-2026-10-16.md` as a **genuine coverage gap — 0 rows in the index**.
Checked properly this round:

 the file is TRACKED in /root/code/waze-fleet (origin /root/code/waze-fleet.git)
 it exists ONLY in the authority's own checkout — no workstation has it
 /root/code on the authority is deliberately NOT indexed (checkouts duplicate the workstations)
 the index holds 497 waze-fleet documents, so the repo IS covered

**Not a gap.** The audit sampled a root the system was explicitly told to ignore, then reported its
absence as a defect in coverage. The fourth time this programme has produced a measurement artefact, and
the second time the artefact came from not asking which root the sample was drawn from.

## Two more, in the same round

- The **ranking audit** queried documents by filename stem with underscores and hyphens intact, so the
 query was one impossible token: **0/20 found**. Tokenised properly, the same documents queried in 4 s
 each because their stems are full of dates — a pathological query, not a pathological index.
- The **"every repo" audit** compared paths with `os.path.basename()` on Linux, which does not split
 Windows backslashes, so every comparison failed regardless of what the index returned.

## What survived as a real measurement

Because the artefacts kept pointing at digits, one question was worth asking directly — do the business's
own identifiers resolve? They do, and quickly:

 7326204948 2 hits 130 ms → chezky schwartz case file
 732-620-4948 2 hits 133 ms
 WO26081312596 2 hits 160 ms → the matching journal entry
 2026-10-16 2 hits 3143 ms → a bare date matches thousands of documents

Rare tokens are fast; an extremely common token (a date) is slow but still inside the deadline. That is
the shape a person actually experiences, and it had never been measured directly before.

## The lesson, and it is about instruments

**An audit script is code, and it needs the same scepticism as the thing it audits.** Across this
programme, every alarming number that survived investigation came from the instrument rather than the
system: different populations compared as a ratio, a file count against a session count, a basename that
does not split backslashes, a sample drawn from an excluded root, a query built from an un-tokenised
filename.

The rule worth keeping: **before believing an audit, ask what it sampled and what its query actually
sent.** One `set -x` on the request would have caught three of these. And when an audit produces a
number that indicts the system, the cheapest next step is not a fix — it is to print the raw request and
the raw response for one case and read them.
