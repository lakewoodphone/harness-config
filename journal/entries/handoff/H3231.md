## 2. THE ONE ROOT CAUSE, WITH EVIDENCE

**The application has no single source of truth for its own state. Every surface re-derives the
numbers independently, and at least two surfaces use different definitions of the same word.**

`getAnsweredCount` and `getPlannedQuestionCount` are called from **eight sites in five files**:

```
components/assessment-launchpad.tsx:889, 1129 "X / Y answered" (twice, same screen)
components/assessment-scores.tsx:124 Object.keys(session.responses).length <-- SECOND DEFINITION
components/assessment.tsx:424, 488, 490 progress object
components/participant-column.tsx:883, 2787-2789 "Question N of Y" + percentage
components/participant-column.tsx:2995 "Question N of Y" (again)
lib/assessment/ai-payloads.ts:661-662 sent to the model
```

`assessment-scores.tsx` does not call the shared helper at all — it counts `responses` keys
itself. **Two definitions of "answered" is the defect behind every number complaint in the
walkthroughs:**

- Four progress numbers on one screen, one labelled (`107 / 116 answered`, `Question 108 of 116`,
 `7 of 15`, true `129`) — each surface deriving its own.
- `getPlannedQuestionCount` re-derives the total **on every render** from the started modules'
 item lists, so the total can only rise: **88 promised, 129 delivered, revised eleven times**
 (ALPHA). The bank holds **174** items (`question-bank.ts` throws unless core = 96 and adaptive
 = 78), so the honest answer is that the product *cannot* know the total in advance.
- The save chip is **optimistic**: it reflects local state, not what the server acknowledged.
 Header read `127 / 129 answered`; a reload read `107 / 116`. Against the promise *"Your answers
 save to your account as you go."*
- The report said *"128 of your answers were needed"* on a 127-question run and `128 / 127` in a
 header — the second definition again.

**Every other CRITICAL in the list is a different symptom of this same absence**, which is why
they cannot be fixed independently and why patching them one at a time keeps producing new ones.

## 3. THE SECOND ROOT CAUSE: THE REPORT IS NOT DERIVED FROM ANYTHING CHECKABLE

The report generates prose, and the prose is never reconciled against the structured findings it
claims to describe. Measured consequences:

- **It invents facts the customer never supplied.** BRAVO: told he had *"ruled out door-to-door
 sales"* and quoted as saying *"the unpredictability wore me down"* — he had merely **clicked an
 option**. Prose quotes typed text correctly and selected text as if it were typed.
- **It contradicts its own printed numbers.** *"Low autonomy (1.5) means he prefers clear structure
 and direction"* while the ratings panel prints **Structure Preference 2.8**.
- **Its structured half disagrees with its prose.** Prose: profile is **CIR**. The six job cards:
 **CIE, RIC, IRC, IRC, ICR, RIC** — none is CIR. Nothing reconciles them.
- **Five of six recommendations ship with a printed caveat saying they conflict with a stated
 constraint** — *"a degree-program path, which conflicts with his no-formal-training answer"*.
- **It reports the instrument's own failure as a trait**: an offered option *"I still cannot tell
 which of those is most accurate"* becomes a finding titled **"Self-Knowledge Gap."**
- One card is written by a different author: *"RIASEC code … matches **the user** profile shape"*,
 and it **repeats its opening sentence verbatim as its closing line** (both BRAVO and CHARLIE,
 independently).

The report has no grounding obligation. That is a **concept** defect, not a copy defect: the
product promises a personalised reading and has no mechanism that prevents it asserting something
unsupplied.

and must be **carried forward, not rewritten**:

| `recommendations.ts` | Matching logic behind the job cards. |
| `assessment-persistence.ts` + its CAS tests | The store, proven under concurrency today. |
| The identity work (SSO assert, per-person namespaces) | Verified working today, end to end. |
| `report-quality.ts`, `ai-payloads.ts` | The gates and the model contract. |
| `runtime.ts`'s **routing** | The adaptive engine's decisions. Only its *number derivation* is wrong. |

**A from-scratch rewrite would take weeks, would keep the product broken meanwhile, and would
reproduce the same defects because the cause is architectural, not local.** The overhaul that
actually fixes this is a rebuild of the two layers that cause it, preserving everything above.

## 5. THE TARGET ARCHITECTURE

**One derivation, one direction of data flow.**

```
 session (the only mutable thing)
 |
 v
 lib/assessment/session-view.ts <-- THE ONLY place that computes:
 | answeredCount, totalDisplay, currentIndex,
 | progressFraction, saveState, modulePosition
 +--> a single frozen `SessionView` object
 |
 +--------------+--------------+---------------+
 v v v v
 question card launchpad scores panel AI payloads
 (renders only, reads the view, computes nothing)
```

Rules the rebuild enforces:
1. **No component may compute a count, a total, a percentage or a save state.** They are read from
 the view. A lint rule or a test can enforce this: grep for `responses.length`, `Object.keys(`
 and `/ ` arithmetic in components.
2. **One word, one definition.** "Answered" means exactly what the server acknowledged, and there
 is one function that decides it.
3. **The total is never promised.** The assessment is adaptive; the honest display is
 `Question N` plus an estimate with its uncertainty stated once — never `of 88` followed by 129.
 If the product cannot compute a number in advance, it must not print one.
4. **The save state is derived from acknowledgement, never from intent.** Three states only:
 *saved* (server confirmed), *saving*, *not saved* — with the last one visible when it is true.
 The launchpad and the question card read the same state.
5. **The report is assembled from structured findings and cannot state what it cannot cite.**
 Prose is generated from a findings object; every sentence that interprets a number carries that
 number; every quote must come from typed text, with selected text labelled as a choice. A gate
 rejects any claim whose cited data contradicts it — the existing `report-quality.ts` gates are
 the beginning of this, not a substitute.
6. **No control ships unless it does something**, and no internal concept (construct names,
 "checkpoints", "reflections", "the user") reaches a participant's screen.

## 6. THE PHASES

**Phase 1 — the foundation (this is the piece that unblocks everything else).**
`lib/assessment/session-view.ts`: the single derivation, with the honest total, the single
definition of "answered", and the three-state save model. Fully unit-tested against the real
session shape, including the cases the walkthroughs produced (a 129-answer run; an optimistic
count rolled back by a reload; a response map with keys but no acknowledged save). Nothing in the
UI changes yet, so this cannot break the live product.

**Phase 2 — the question card.** Rebuild `participant-column.tsx` as composition: a question
component, an answer component, a progress component that reads the view, a sync chip that reads
the view. Answer options in the first viewport; Continue below them (already fixed as an interim
measure); no dead controls; no internal labels.

**Phase 3 — resume.** One control, one name, resume-on-load when exactly one draft is unfinished.
Four controls with three names currently resume one attempt and none works from a cold load.

**Phase 4 — the report.** Assemble from findings; enforce citation; reconcile the structured half
with the prose (CIR vs the cards); stop quoting a selection as if it were typed; delete the
"Self-Knowledge Gap" reading of an offered non-answer.

**Phase 5 — the front door.** Self-serve signup that creates an account for a person the shop has
never seen, and email-only signup if that is wanted (it needs a decision: `users.phone` is NOT NULL
and unique today).

**Phase 6 — re-walk.** A fresh user goes through the whole thing again, and the notes should be
about taste, not arithmetic.
