## 2026-10-19 21:10 UTC · ZABZ-TECH · The search system held 1.3% of the corpus with a green health check; the centre is at 361k documents and still climbing, and the push resumes itself

Owner asked, after resizing the authority (2 vCPU/7.7 GB/75 GB → measured **8 vCPU / 30 GB / 225 GB,
97 GB free**), for an audit of the search system and for it to be made "absolutely up to par".

### The headline

`esearch` on the authority was fast and answering — and it was answering from **18,682 documents when
the corpora held ~1.4 million**. Journal 76 of 4,071. Mail 39 of 118,617. Comms 0 of 181,182. VS Code
chats 0 of 3,638. `/health` was `ok: true` throughout, because freshness was judged by the newest row
in the whole store and any one push refreshed it.

**Cause, measured:** every adapter is watermarked and every push is teed from adapter stdout, so a push
carries only what that run emitted. The centre was rebuilt at `2026-10-19T08:23:16Z`; the watermarks
survived; every source re-emitted almost nothing and reported `ok`. `sync.json` carried the proof —
`comms:authority … docs_written 181182` against 0 rows. There was no backfill path.

### Still running / next

1. **Two detached backfills** (`bf-tech.cmd` on ZABZ-TECH, `bf3.cmd` on ZABZ-YOGA) are pushing the
 remaining file corpora. They are resumable via `~/.usearch/state/backfill.json`; killing and
 re-running is safe (idempotent on `(source,id)`). When they finish, `/health` should be green.
2. **`/health` will stay red until they finish, and that is correct** — it names
 `files:zabz-tech holds 100263 document(s), floor is 150000`. Do not lower the floor to make it green.
3. **The ~50,000 documents pushed under the old policy are still in the centre** (data/, journal
 copies). There is no prune API on `/ingest`; the next piece of work is a `prune-central` that
 deletes by deny-path against the live index, dry-run first.
4. **git history is not pushed** (62,891 + 35,132 commits available). `--source git:local` when there
 is time; deliberately last.
5. **Cold start is not measured** — restarting the service would abort the in-flight push. One
 restart and one timed query, after the push.
6. **Archived Copilot sessions are in no index** (`estate:copilot-archive REFUSED` on every answer).

### What I learned (also filed as lessons)

* A rebuilt index does not reset adapter watermarks — the state that describes a store has to be
 thrown away with it (`L-lesson` filed this session).
* `SELECT text FROM chunks WHERE doc_id=?` is a corpus scan; and the 482,596 documents I blamed it on
 had no chunks at all — I wrote and pushed the wrong cause before running the tool that falsified it.
* A colon-space in a skill's YAML frontmatter removes the skill from the catalog **silently**; my
 `fast-search` edit did exactly that for a few minutes mid-session.
