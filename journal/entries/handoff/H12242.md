## The four habits, in the order they earned their keep

**1. A mutation test is the only proof a test is a test.** Three times this session a green test guarded nothing: a teeth-check that broke Kotlin syntax and failed to *compile* (which reads identically to "test failed"); a selftest fixture whose `produced` key used a Windows backslash where the lookup used the document's `rel`, so it never took the path; and a fixture writer that never read the clock, so the code under test was skipped entirely. All three looked green. Mutate the thing and watch the assertion go red, or you have written decoration.

**2. Read the DoD before calling a row blocked.** For three rounds I told the owner "everything left is hardware-bound". It was false: A-P4-10, A-P5-04, S-P4-01, X-P6-09 and A-P5-06 were each already satisfied in code, and five of them needed only a register correction. I also called A-P4-02 "infrastructure, not mine" twice when `caddy/Caddyfile` and a `Caddyfile.mtls.example` were sitting in the repo. **Five rows this session had drifted rather than being blocked** — that is why 1159 exists.

**3. A gate message, a commit subject, and a subagent report are all claims.** I filed a defect (1160) on a checker's own sentence and had to disprove it by running the writer twice — the writer was deterministic, and the checker was comparing two samples with my own edit between them. The loop's commit subject said a private key was gone; I re-read the path myself before believing it (it was gone, and stricter than claimed).

**4. When two agents fix one defect, the merge must preserve both tests' entry points.** The parent-release branch and the loop's #154 independently fixed the same two broker defects. The merge only worked because the child's stricter store guard was kept *under the name main's route test imports* (`_speaks_sqlite`) while its household-scoped guard replaced the loop's marker function. Renaming a symbol in a merge breaks a test you did not write.

## The mechanics that cost the most time, so you do not rediscover them

- The wake loop merges every 5–10 minutes and **advances no roadmap row**. Every PR needs 1–3 sync-and-merge cycles; expect `gh pr merge` to answer "Base branch was modified" and just retry.
- After every sync: recompute **all** `scripts/facts/*.py` by *running each script* (`server\.venv\Scripts\python.exe scripts/facts/<name>.py`) and putting its number in `VALUE` with `MEASURED`. Never hand-edit a number to make a gate green.
- `FM-STALE` compares a document's `updated:` against the **last commit** touching it, so a gate run *before* committing is green and the same files go red after. Verify main on a fresh checkout, not your working tree.
- **A roadmap item must not restate a suite count** — `check_testing_matrix` fails it ("13 passed"). Point at `docs/testing-matrix.md` instead. I made this mistake twice.
- `check_docs_index --write-index` and the other writers must run **last**, and `--write` covers only the checkers that declare a writer.
- Each `pwsh` call is a **fresh process**: a variable set in one call does not exist in the next. I lost a document body to that.
- Do not commit on a detached HEAD in a worktree — `gh pr create` answers "not on any branch". Create the branch at `worktree add` time.

## The one job I would start with

**Ledger 1159**: a checker that marks a roadmap row STALE when the code its DoD names has landed since the row was last advanced. Design that avoided the noise: join each row's `ledger:` id to the work ledger's state (a `partial` row whose ledger item is `done` is drift, full stop), and separately flag cited paths whose last commit is newer than the row's `updated:`. That pair is deterministic and would have caught all five of this session's drifts. Without it this treadmill continues, and a reader of `docs/ROADMAP.md` cannot tell "waiting on hardware" from "waiting on a decision" from "already done" — which is the exact question the owner asked the roadmap to answer.
