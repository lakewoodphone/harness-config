## 2026-10-19 20:58 UTC · ZABZ-TECH · Computer finder round 5: accessibility audited - zero axe violations, contrast above AAA, focus no longer stolen on load

## 2026-10-19 22:5x UTC · ZABZ-TECH · Computer finder round 5: the accessibility audit. One real defect fixed, one false alarm caught before it caused a bad "fix". PR 482 is 14 commits.

METHOD. Chromium via Playwright at 393x852 against the dev server at `1e5d3ede8`, plus a new `vitest-axe` suite that runs with the rest of the frontend tests. Report: `rounds/05/ACCESSIBILITY-AUDIT.md`.

MEASURED, and it is all clean:
- **0 axe violations** on the intro, all eight question screens, the contact step, the review and the confirmation. The suite contains a deliberately inaccessible fragment it must flag, so a pass proves the harness works.
- **Tab order from a cold load** goes header first: `Lakewood Phone & Tech` -> `Call (732) 655-2355` -> `Start`.
- **200% zoom** (197x426 CSS px): `scrollWidth` equals `innerWidth`, no horizontal scrolling, nothing clipped.
- **Text contrast, resolved to real sRGB pixels**: the lowest pair on the page is 7.58:1; the floor notice is 13.53:1. All above WCAG AAA for normal text.

THE DEFECT FIXED (`d1eeab9d3`): focus was stolen on load. The page focused its own h1 on mount, so the first Tab landed inside the form and the header — the shop name and the phone number that round 2 added because customers could not find them — was reachable only by tabbing right round the document. Focus now moves only when the step actually changes. The first attempt used a "first render" boolean and DID NOT WORK because React StrictMode double-runs effects; the fix is a comparison against the previous step, and the before/after `activeElement` readings are in the audit.

THE FALSE ALARM, worth remembering. My first contrast pass parsed `oklch(...)` strings with a numeric regex and reported the floor notice at **1.41:1** — a serious failure on the owner's most important sentence. The measurement was wrong, not the page: Tailwind v4 emits oklch and reading those numbers as sRGB channels is nonsense. Re-measuring by drawing each colour into a one-pixel canvas and reading the actual pixels gave 13.53:1. Had I trusted the first number I would have "fixed" a contrast problem that does not exist and made the design worse. **Rule: a colour measurement that parses a CSS colour string by hand is not a measurement.**

NOT COVERED, and stated rather than claimed: real screen-reader output (NVDA/VoiceOver), a full keyboard-only completion walk of all ten screens, and reduced-motion / forced-colours modes. That is round 5b.

ENVIRONMENT TRAP, new: running `vitest` in a worktree while `vite dev` watches the same tree kills the dev server with `EBUSY` on vitest's `.tmpdir` — the watcher dies and later captures fail with a confusing connection error. Run the dev server and the tests at different times, or on different trees.
