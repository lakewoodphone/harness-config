# H520 — round 33: verify-deploy could not do the thing one of its own entries claimed, and said OK

## WHAT HAPPENED

Adding the gateway detector to the deploy manifest, I noticed the harness-config copy of the owner digest was
**21,478 B** while the live file was **22,815 B** — genuinely stale — **and the check passed.**

The entry read *"harness-config COPY of the digest must match what is live"*, but the mechanism behind it was
a **marker string**, which a marker proves *which* version, not that two copies are *the same* version. **A
marker appears in both when one is merely older.**

**An entry that claims to detect a difference and reports success instead is worse than no entry**, because
it converts an unknown into a false assurance. That is the same shape as the digest line corrected in round
27 (*"every hub record has a production order"* for a number that measured something else) — and as the
`sync_to_production` key I asserted in round 27 without checking.

## THE FIX, AND IT WORKED FIRST TIME

Paired copies are now compared by **sha256**, byte-for-byte. On its first run the check reported exactly the
drift it was written for:

```
🔴 COPIES DIFFER owner-attention-digest.sh (834a8e24fe37) != owner-attention-digest.sh (59d8c473f991)
 the repo copy is NOT the file that runs — the gap this script exists for
🔴 1 of 17 artefact(s) are the WRONG VERSION on the host
```

The repo copy was then realigned to live, and it goes green:

```
=== PAIRED COPIES (byte-for-byte) ===
 ✅ owner-attention-digest.sh == owner-attention-digest.sh (834a8e24fe37)
✅ all 17 deployed artefact(s) carry their expected marker
```

**The marker-only entry that claimed to make this comparison was REMOVED** rather than left in place
looking reassuring — a check that cannot fail is decoration.
