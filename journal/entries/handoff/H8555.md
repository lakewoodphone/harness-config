## The token does not guard the tailnet path — membership does

Reading `token_ok()` and then the listener:

 peer in ("127.0.0.1", "::1") -> return True # before any header is read
 ss -ltnp | grep 3095 -> 127.0.0.1:3095 (one row, loopback only)

`tailscale serve` proxies to `127.0.0.1`, so **every** tailnet request arrives as a loopback peer and
the bearer token is never presented, never checked, never exercised. `ESEARCH_TOKEN` sits in
`/etc/esearch.env` (0600 root) looking like a control.

The real boundary is **tailnet membership**: a loopback bind, one path in through `tailscale serve`,
enrolled devices only. That is a genuine boundary — but it is not the one the code appears to
implement, and the difference matters the day someone adds a Cloudflare route or a 0.0.0.0 bind.

Written into the function and the runbook, with the instruction attached to the place it will be needed:
strengthen `token_ok()` **before** any non-tailnet exposure goes live. A control people believe in is
worse than no control, because nobody re-examines it.

## Why this belongs in a search program's record

The objective says "monitored, self-healing". A search surface that answers every enrolled device with
no authentication is a monitoring blind spot of a specific kind: nothing in `/health` would ever
mention it, because nothing is broken. It is a property, and properties have to be written down or they
are discovered by the wrong person.
