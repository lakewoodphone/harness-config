## The software fault this shift did find: the watchdog re-woke the same physical fault

`ha-watch:DOOR_STUCK_OPEN` was first released as wake #1217 at 00:00Z and finished `done` at
00:07Z. It was then **re-filed at the next 30-minute tick** (row `created_at` 00:37:02Z) and
released again at 01:07Z for this shift. The cause is structural, not a one-off:

- `wake.py` dedupes only while a row is **live**; the cooldown is 1800 s, and a `done` outcome
 resets the attempt ledger, so a persistent finding re-files every 30 minutes for ever.
- The watchdog's own docstring claimed "one persistent fault files once, not every 30 minutes."
 It did not, for any fault that stays true.

That turned a reed the owner had already been asked about (queue #714, pending, deferred to
2026-10-19T23:59Z) into an hourly woken session whose only possible action was to re-confirm the
same magnet. That is the session factory the wake contract exists to prevent.

## What changed

`/root/bin/ha-watch.py` only (backup: `ha-watch.py.bak-20261019T0115Z`; `py_compile` clean).
New `owner_decision_for(entity)` reads `owner_decision_queue` read-only and returns the id of a
**pending** row whose question or context names that exact entity. `flag()` now skips the WAKE for
`DOOR_STUCK_OPEN` when such a row exists, and returns a reason that says so.

Deliberately narrow:

- only the `DOOR_STUCK_OPEN` code is affected; every other finding wakes exactly as before;
- only an exact entity id match counts; any queue-read failure returns `None`, i.e. fail open
 toward waking, so a broken queue can never silence an alarm;
- **the finding is still recorded every run**: `latest.json` keeps `ok:false`, `history.jsonl`
 keeps the code, `ALERT.txt` still gets the line. Only the DSH session is not spent;
- only `pending` suppresses. Once the owner answers/resolves/dismisses #714, the wake returns
 automatically if the contact is still open.

No HA, Zigbee2MQTT or alarm change. Forcing the contact closed or muting the check would blind the
alarm's main entrance; that remains the owner's repair (queue #714), as the audit §3.3/§5 row 1 and
H8937 already said.
