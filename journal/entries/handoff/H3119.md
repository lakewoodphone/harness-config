## ROUND 4 — the audit now runs itself, and it found the real fault in the store

**New `~/code/harness-config/scripts/text-ledger-audit.py`**, wired into the existing
runner `~/bin/text-channel-check.sh` (backup `.bak-ledgeraudit-*`) as a fourth
instrument, following that file's own pattern. Cron `*/15` was already there, so this

carries it:

 ledger-audit rc=1 D1 the channel store holds the owner's own inbound texts;
 D3 the order feed can name an item for a recent charge

Three checks, each one for a fault that was found by hand on 2026-10-02 and was
invisible to every check then running:

- **D1** the channel store (`inbox.db`) versus the app: the store's newest owner text is
 **2026-03-25**, the app's is **today** — the store is 4,590 hours behind.
- **D2** nothing unanswered is holding the channel shut.
- **D3** the order feed can name an item for a recent charge.

**The audit immediately caught a bug in itself, which is the point of running it.** Its
first version matched the owner's number with `LIKE '%84897895%'` and returned **zero**
rows on this host even though `from_number = '+18483897895'` returns 252 — LIKE with a
leading wildcard is not dependable here. A check that silently matches nothing reports
"no data", which reads exactly like "no problem". It now matches by exact value against
every form the stores use. **Do not build a check on LIKE in this SQLite build.**

**What D1 measures, precisely (this is the actionable finding).** The app holds 252
owner inbound rows; **225 of them are older than the 7-day window**
`~/bin/mirror-owner-sms.py --days` will carry, and **0 of them lack a `twilio_sid`** —
so they CAN be mirrored safely, because the mirror's only dedupe key is the sid. They
were simply too old on the run that would have carried them, and each run they get
older. Consequences and non-consequences:

- **NOT live loss**: no new owner text is being dropped; a text from today would be
 carried by the next 5-minute mirror tick.
- **The store's own reporting is wrong for this channel and always has been**:
 `sms-responder.py report` prints "0 to decide" and counts 369 held rows against a
 channel with 252 owner messages it cannot see (225 of them permanently parked). Every
 decision made from that store — including anything that reads "who is waiting on us" —
 is made on a months-old picture.
- **The remedy is a one-time controlled backfill** of those 225 rows into
 `inbox.db.messages`, marked so the responder does not answer months-old conversations
 as if they were new (the store already has a `state` column and a `reason` column;
 historical rows use `decided_by='backfill'` as precedent). Decide the marking BEFORE
 inserting, not after.
