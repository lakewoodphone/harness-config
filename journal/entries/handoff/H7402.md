### 3. THREE SHIFTS KILLED BY A LOCK (s63) — and it was not my edit

```
04:17:51Z ERROR lease for wake #1170 not renewed - killing the session: unknown
04:19:40Z ERROR exited (rc=2) with wake #1169 still claimed - closing as failed
04:21:21Z ERROR exited (rc=2) with wake #1123 still claimed - closing as failed
```
Earlier warnings (01:50, 03:15, 04:10) show the cause: `wake: database error: database is locked`, retried
until the lease margin ran out. Three defects made it lethal:
1. **5 s patience** — `wake.py:connect()` used Python's default busy timeout. Now `busy_timeout=30000`,
 verified live. (Not invented: `sms-inbox.py` already sets the same value on the same store.)
2. **Exit-code contract broken** — `cmd_heartbeat` returned 2 for `not-claimed` where the dispatcher's own
 contract says 1. Now 1, verified `REAL rc=1`.
3. **The kill message threw away `_LEASE_LAST_ERR`** and printed `unknown`. Now included.

### 4. THE HOLDER (s64) — item 565 CLOSED

`reconcile-sent-status.py` issued `UPDATE messages` **inside a loop that makes one Twilio HTTP call per row**
and committed only **after** the loop, so Python's implicit transaction held the wake store's write lock
across every remaining round-trip — the same store the dispatcher renews leases on, every 10 minutes.

Mechanism proven on a throwaway db (`scripts/wake/tests/prove_lock_mechanism.py`): an uncommitted UPDATE leaves
`BEGIN IMMEDIATE` failing `database is locked` for the whole 4 s sleep and succeeding the instant the child
commits. Fixed to **commit per row**; one inode covers both `/home/zabz/bin` and `/root/bin` (2079928).

Survey of the class: ten scripts contain both HTTP and DB writes, but the dangerous shape is interleaving —
`sms-inbox.py` (5-minute cycle) is fetch-then-write and safe, and it already set `busy_timeout=30000`.
