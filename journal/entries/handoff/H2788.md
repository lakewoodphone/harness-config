CLOSED: THE TEST DATABASE'S MIGRATION DIVERGENCE
A workstream reconciled it on the copy. The cause was not lateness: the history had been built by
applying migrations **from branches that never merged** and by hand — one `_prisma_migrations` row
literally records the checksum `0000_applied_manually`. Three orphan names were the losing half of two
competing device-type implementations deleted by branch-sync commits; two came from
`origin/feat/portal-repair-status-eta-D10`, which is not an ancestor of `origin/test`; and five files had
no row because they had genuinely never been applied. `resolve` cannot fix a DB-only row (P3017), so the
five bookkeeping rows were trimmed and the five real migrations deployed.

**I reproduced the outcome myself: `npx prisma migrate status` on `lpt_test` → `Database schema is up to
date!`** (151 migrations found). The funnel's failing layer was also exercised for real — an
INSERT/read-back/DELETE through the container's own Prisma Client, the exact layer that was producing
*"The column laptop_preferences.conditionPreference does not exist"*, and it passed. That is narrower than
a live tRPC call: **the agent could not authenticate** — `laptopPreference.upsertMy` returns 401
*"Customer authentication required"* and `getForCustomer` 401 *"Authentication required"*. So the funnel
has a SECOND blocker and the schema was not it.

PRODUCTION WAS DELIBERATELY NOT MIGRATED — and this is a decision, not an omission
`lpt_prod` has the same divergence and the same missing column. I did **not** apply the reconciliation to
it, for three reasons that each stand on their own:
1. **It would not fix the funnel.** The live call above shows the customer path 401s for authentication;
 the missing column is not the blocker a customer would hit. Fixing prod's schema would buy nothing
 visible while carrying every risk.
2. **The pending set is not purely additive.** One of the five is
 `20260914120000_unify_budget_tiers_add_condition_preference` — "unify budget tiers" reads like a
 DATA change, not a column addition, and production is the live customer database. That is exactly the
 class the standing rule covers: *no dropping tables, no destructive schema change, without an explicit
 per-action yes for that exact command on that exact thing.*
3. **Production's deployed code is older than `test`'s.** Applying migrations a live app was not built
 against is a guess about the running process, and I could not verify that process.

Full production dump already taken and kept: `/root/lpt-prod-20260928T164420Z.sql` (117 MB). What prod
needs, in order, is: read the five migrations and classify each as additive vs data-mutating (nothing has
done this yet); then decide production separately. **The copy is the place to do that reading, and the
copy is now up to date and reproducible.**

TWO MORE REAL SCHEMA DEFECTS, FOUND AND NOT YET FIXED
1. **`DeviceType.CAMERA` is declared in `schema.prisma` and NO migration adds it to the enum.** So the
 Camera option has no valid enum value in any database built from migrations — a real, live gap, and
 the fix is one new migration file (which the workstream was correctly told not to author).
2. **Foreign-key actions disagree between the database and the model**: `payment_transactions.customerId`
 and `order_status_history.changedBy` are `ON DELETE RESTRICT` in the DB but `SET NULL` in
 `schema.prisma`. The database is the stricter one, so nothing is currently at risk — but the model
 lies about it, and a future `migrate diff` will keep reporting it.
Both belong in the owner queue's engineering half or the next shift's list, not in a schema change made
tonight.
