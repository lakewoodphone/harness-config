**What that threatens:** time, and `CHECKSUMS-SHA256.txt` (never written — finisher #2 was still waiting
for #1). **What it does not threaten: the delivered bytes**, for the reason above.

**Recovery, armed as a background job (`pwsh-5`) that polls for the bench and then acts.** When the bench
answers it re-scps every script (because **a reboot clears `/tmp`, where they lived**) and runs
`/tmp/state-after-outage.sh` and `/tmp/_rearm-if-needed.sh`. The re-arm rule, in that script, is: mount
check first; **if the verify already PASSED, do not re-run it**; if a verify is already running, leave it
alone; otherwise re-run it detached. The checksums step is re-armed only if the file is absent from the
medium. **Both scripts are also in the case folder on ZABZ-TECH:
`_state-after-outage.sh`, `_rearm-if-needed.sh`, `_bench-finisher.sh`, `_finish-stick.sh`,
`_finish-checksums.sh`.**

**The lesson, and it is the general one:** the tail of this job lived on ONE machine, and that machine is
a single point of failure for the whole delivery. The **copy** was safe because it was on the customer's
medium; the **proof** was not, because it needed a second pass on the bench. When a verification pass is
going to take hours, either do it on the medium itself or accept that an outage costs you the proof and
not the data — and say which one you are choosing, in advance.

**Still open, in order:** bench reachability → the verify verdict → the checksums file → then, and only
then, it is a delivery. Journal `H3645` carries the pre-outage state.
