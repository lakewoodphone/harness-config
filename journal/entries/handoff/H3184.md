## 2026-10-05 05:35 UTC · ZABZ-TECH · Offsite backup of the authority DB to R2 is LIVE and verified by round trip; the blocker was my own search failure; a master token was leaked into a transcript

DONE AND VERIFIED 2026-10-05: offsite backup of the authority database to Cloudflare R2.

THE BLOCKER WAS A SEARCH FAILURE, NOT A CREDENTIAL GAP - and I had already written the
wrong conclusion into the queue. I told the owner no R2 credential existed and asked him for
a dashboard action. He pushed back: "we made a bunch of keys you just have to find them, and
we have a master token that can create other tokens." He was right.

 The privileged token was in an EXTENSIONLESS file: secratary:/home/zabz/.secrets/
 cloudflare-api-token (mode 600). A search that filters by extension walked past it twice.
 ODQ 74's own resolution already names this exact cause: "a credential search that filters by
 extension will miss the credential store." Read the resolution of a closed row before
 re-deriving its lesson.

 Verified it can create R2 buckets AND create API tokens (probes returned 400 "JSON not well
 formed", not 10000 Authentication error - authorised, given an empty body).

WHAT WAS BUILT
 bucket lpt-authority-backups
 an R2 API token scoped to THAT BUCKET ONLY - access key a18595b0...1acf
 ~/.lpt-r2.env (mode 600): R2_ACCESS_KEY_ID = the token id, R2_SECRET_ACCESS_KEY = the
 SHA-256 of the token value, per https://developers.cloudflare.com/r2/api/tokens/
 /home/zabz/bin/push-db-offsite.sh - daily 05:10Z via cron-wrap, single-flight flock,
 gzip -1 then upload, plus a .sha256 sidecar object

DECISIONS I MADE (dev, mine, recorded so they are not relitigated)
 - DAILY, NOT SIX-HOURLY. The local six-hourly snapshots already cover short-term recovery;
 a six-hourly offsite push would put 4x the bytes through the office uplink for little
 gain. RPO for machine loss is 24h. Change the cron line to raise it.
 - One compressed copy at a fixed key, not every snapshot, so bucket size does not grow.

COST, now measured rather than estimated
 The bucket holds 4.9 GB and R2's free tier is 10 GB-month ACROSS THE ACCOUNT. Known usage
 elsewhere: psm-backups restic 342 MB, customer-backups and its test bucket empty,
 rentals-media a couple of images. Total is well inside the free tier, so this very likely
 costs NOTHING. My earlier 0.10-0.20/month figure assumed the uncompressed 17 GB and was
 too high. R2 also charges nothing for egress, so restoring is free.
 R2 bills TOTAL stored volume across buckets, not per bucket - so the owner's question
 ("are we paying for a new bucket") has the answer: no, a new bucket is not a new charge.

HOW I BROKE MY OWN RULES TWICE ON THE WAY (recorded so the shape is recognisable)
 1. Two failed attempts at the token creation lost the one-time token value, because I put
 the API response through a pipe AND a heredoc on the same stdin - the heredoc wins and
 python parsed the script as JSON. Then a second attempt failed on a Python f-string
 referencing a bash variable. Both strays had to be DELETED and the token recreated.
 A value shown once must be written to a file in the same call that fetches it.
 2. Use `--data @file` and `-o file`, never a pipe, when the consumer is a heredoc script.

A CREDENTIAL WAS LEAKED INTO A TRANSCRIPT BY THIS WORK, AND IT IS NOT MINE TO FORGET
 The search subagent printed FULL live values twice: the master token from
 ~/.secrets/cloudflare-api-token, and CLOUDFLARE_API_TOKEN from
 phone-and-tech-full/backend/.env on the laptop. Causes it named: a generic `awk -F=` over an
 extensionless file with no `=`, and an unbounded `Select-String -List` that echoed the whole
 matching line. The master token (id 9bb798dfe16ab840dd6a249b5f210426) is therefore a
 ROTATION CANDIDATE and ODQ 271 is still pending. Two rules for future sessions:
 never run a field-splitter over a file whose format you have not read, and always bound a
 search's output with a capture group rather than dumping the line.
