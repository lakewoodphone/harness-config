## 2026-10-05 · ZABZ-YOGA · one malformed tool call was killing whole turns; fixed in the adapter, with the corpus to prove it

### What the owner saw

`This turn failed DeepSeek Messages stream: tool input is invalid JSON MALFORMED_RESPONSE`, repeatedly,
and then: *"you keep gettting this response, you are doing something wrong, investigate it fully and
thoroghly and get it fully fixed"*.

### The cause, from the provider's own bytes

`@deepseek-ai/dsh-llm-deepseek/lib/index.js` validates every tool-call block at `message_stop` with a bare
`JSON.parse(content.arguments)`; a failure is `malformed("tool input is invalid JSON")` → `LlmError(...,
"MALFORMED_RESPONSE")` → the agent loop ends the turn with `turn/end {kind:error}`. One malformed tool call
discards the whole turn, including the tool calls that were fine.

The model emits tool arguments that are ONE corruption away from valid JSON. Four observed shapes, all four
in this machine's own ledger:

| shape | real example | count/86 |
|---|---|---|
| object value emitted as a bare token | `{"url": https://davkawriter.com/products/davkawriter-7, "question": "..."}` | 14 |
| a bracket the model never closed | `{"formats": ["json"], "jsonOptions": {"prompt": "..."}` | 20 |
| a quote left unescaped inside a string | `{"query": "iPod Nano 7" screen replacement ..., "num": 6}` | 24 |
| a value cut off mid-string | `{"file_path": "...", "content": "# Trampoline Parks ..."` (14 KB) | 28 |

### CHANGED

1. `scripts/patch-dsh-malformed-tool-input.py` — idempotent patcher for the pinned runtime, four edits, with
 anchored drift failure and `.meshfix-bak` backups. Applied to the live tree and all three other prefixes
 (0.1.7-rc.1, 0.1.7-rc.2, 0.2.0-rc.1, 0.2.0-rc.2); the two 0.1.5 trees are refused loudly because their
 adapter predates the validation this fixes.
 - it adds `repairToolInput()` and a `emitToolInput()` helper, and moves the emit through the helper so the
 arguments are settled BEFORE the block is emitted.
2. `dsh-update/tests/tool-input-repair.test.mjs` + `dsh-update/tests/tool-input-repair-corpus.json` — the test
 imports the repair engine out of the patcher's own embedded source (so it tests what ships) and then runs
 the INSTALLED, patched `translate()` over all 86 real cases.
3. `settings/base.yaml` + `profiles/{web,mesh}/cordis.patch.yml` (+ the live copies in `~/.dsh/profiles/*`) —
 `MALFORMED_RESPONSE` added to `llm-deepseek.retryPolicy.retryableCodes`, so even an unrecovered case costs
 one retry instead of the turn.

### The measurement

```

```

86 of 86 now finish. 34 are repaired byte-exactly (only syntax characters added: verified by requiring every
byte of the original to survive into the repair in order). 52 are content-truncations that CANNOT be repaired
without inventing content, so they are refused and the tool call proceeds with `{}` — the tool layer answers
`invalid arguments: ...` (`dsh-tools/lib/index.js:812`) and the model corrects itself in the same turn.

### BROKEN / still open

- **The running engine has the old module in memory.** PID 21072 (the `dsh web --port 3099` process) loaded
 the adapter at mount; the patch reaches a running process only if `dsh-hmr` reloads it, which is NOT
 verified. Treat the fix as taking effect from the next engine start until someone proves otherwise.
- **The other nodes are not patched.** The patcher covers every runtime root it can find on the machine it
 runs on. ZABZ-TECH, secratary, the Linux worker and the VPS each need it run there.
- **`~/.dsh/sessions/**.jsonl.zstd` are CONCATENATED zstd frames**, and `zlib.zstdDecompressSync` silently
 returns only the first frame — 198 bytes of header out of 227 KB. Both of this machine's own session-reading
 tools had this bug, which is why "no session contains this error" was almost reported as evidence. Python
 `zstandard.stream_reader` walks all frames correctly. See lessons.
- The two 0.1.5-rc.3 runtime trees carry an older adapter (2089 lines) with no such validation; the patcher
 refuses them by design rather than guessing.
