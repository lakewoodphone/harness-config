### THE LIVENESS PROBE IS INSTALLED AND RUNNING (22:38Z), and running it found two real defects

The code was deployed at 20:16Z; the systemd units were not, so nothing ran. Installing them exposed
faults that only appear when the thing actually executes:

1. **`main()` returned `0 if result["ok"] else 1`**, so a probe that ran correctly and DETECTED a
   wedge exited 1 and marked `r4-liveness-probe.service` **failed** (`systemctl is-failed`). The unit's
   failure state therefore stopped meaning "the probe broke" — on every real outage systemd would
   shout about the probe, and a genuine probe crash would be indistinguishable from the condition the
   probe exists to report. It also parks an expected condition in `systemctl --failed`, which is how an
   alarm is taught to be ignored. Fixed (`60b1f676f`, merged `4b750e5aa`, deployed, md5 verified):
   the exit code now answers *did the probe complete a check*, the verdict lives in `state.json` where
   the consecutive-failure count and the escalation outcome already are. Regression test
   `tests/test_r4_probe_exit_code.py` fails on the unpatched file (1 failed, 1 passed) and passes after
   (2 passed); the pre-existing suite unchanged at 10 passed. **Verified live: a wedged URL now gives
   exit 0 with `ok:false`.**
2. **The probe read the PUBLIC url from `.env`.** `TELEPHONY_HEALTH_HTTP_PROBE_BASE_URL` is in
   `/opt/company/.env` and the resolver prefers it over the loopback default, so under systemd the
   probe called `https://api.abletelsolutions.com/health` and got **403 Forbidden** — it would have
   alerted on the wrong endpoint forever. The unit now pins `COMPANY_API_BASE_URL=http://127.0.0.1:8002`
   (systemd `Environment=` beats `EnvironmentFile=`), and with **`R4_LIVENESS_FAIL_ON_FINANCE=0`,
   the owner's choice**: service-dead only, so the quiet BoA/Plaid feed (false since 2026-10-09) does
   not ring his phone.
