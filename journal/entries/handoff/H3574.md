### RULED OUT — do not re-investigate these

1. **The trigger.** `MSFT_TaskTimeTrigger`, `Enabled=True`, `StartBoundary=2026-09-14T01:39:00`,
 `EndBoundary` empty, `Repetition: Interval=PT1H Duration='' StopAtDurationEnd=False`. This is the
 *healthy* shape — the opposite of P2899 D2, whose pattern expired after one day. `NextRunTime` is
 populated. **The clock is not the defect here.**
2. **The historical `IndexError`.** `refresh.log` (962 B, frozen 2026-09-14T16:47:38Z) holds a traceback
 from `refresh.py:239`, `"".splitlines()[-1]` → `IndexError`, in the *failure-reporting* generator. But
 the **file on disk was fixed at 2026-09-14T17:06:22Z** and its own line 324 documents the guard
 ("previous version did `splitlines()[-1]` unguarded here"). `refresh-state.json` records
 `last_success: 2026-09-14T17:34:36` — a successful run **after** the fix. **That traceback is
 historical; do not report it as the live cause.** I nearly did.
3. **The launcher, the interpreter and the paths.** The task runs
 `wscript.exe //B //NoLogo …\hidden-tasks\DSH_search_index_refresh.vbs`, which runs
 `cmd /c C:\Python313\python.exe C:\Users\ezabz\.fsearch\refresh.py >> refresh.log 2>&1` and returns
 its exit code. `python -> C:\Python313\python.exe` exists; `refresh.py` exists. All present.
4. **A hang.** Running `refresh.py` directly with `-u` produced **no output for 110 s** — but that is
 *expected*, not a hang: a full refresh takes **1044 s** (`last_seconds: 1044.3`, with the `fsearch`
 sub-step alone at 990 s) and the script captures its sub-processes' output instead of streaming it.
 Two short-cap runs read as "hung"; they were working. **Any conclusion here needs a ≥20-minute
 window and output redirected to a file, then read.**

### WHAT IS ESTABLISHED

* The task fires hourly and returns **1**, while **nothing writes to `refresh.log` and
 `refresh-state.json` has not moved since 2026-09-14T17:34** — so runs are failing in a path that
 records nothing. That combination (a job that runs, fails, and leaves no trace) is the estate's
 recurring shape, and it is why the fix needs a **measured** companion, not just a working script.
* The refresh's own sub-steps are `fsearch`, `names`, `chatindex`, `comms`; the last known good state has
 all four at `rc: 0`. So the failure is in exactly one of them, or in the reporting around them.
* `refresh.lock` sits in the `.fsearch` dir and is written by a run in progress. It **self-heals a dead
 holder** (my own killed run's lock was overwritten by the next run), so a stale lock is not the cause —
 but it is how you tell whether a run is live.
