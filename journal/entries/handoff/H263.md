## 2026-09-15 19:20 UTC · ZABZ-TECH · PART-124: a guardrail's docblock says it preserves the current session and its code revokes every refresh token for the user - so every identity change logs the customer out

CHANGED
- **PART-124 (account linking and the strand guard) written and committed: `361378020`** on
 `audit/lpt-account-2026-09-15`. `docs/audits/account-audit/parts/124-account-linking-and-strand-guard.md`.
- Part 124 is the **7th of the 15** new account parts (117–124 documented; 125–131 remain).

THE FINDING: A GUARDRAIL'S COMMENT CONTRADICTS ITS CODE
- `account-change-guard.ts:5-7` states the helper's purpose: *"destroy every OTHER session + revoke their
 refresh tokens so a leaked/stale token can not persist"*.
- It **does** destroy the other sessions (`:63-68` — fetch, filter out the current one, delete the rest), and
 then calls `RefreshTokenDbService.revokeAllForUser(userId)`, whose implementation is
 `updateMany({ where: { userId, isRevoked: false } }, { isRevoked: true })` — **no exception for the current
 session** (`database.service.ts:544-550`).
- Consequence: every security-sensitive account change revokes **the refresh token the customer is still
 using**, and with a **7-day access token** (PART-122 F-1) they are signed out at the next refresh. Comment
 and code disagree about the same sentence, and the code is wrong.
- **Fires from four shipped paths**, so it is in the shared helper every identity change depends on, not in
 one place: `google.unlink` (`:168`), `google.setPassword` (`:200`), `customerAccount.changePassword`
 (`revokeOtherSessions` defaults to **true**, `customer-account.ts:106`), and `customerPortal` twice
 (`:478`, `:582`).

ALSO FOUND
- **F-3:** `setPassword` writes a password but **never sets `isVerified`** — and `isVerified` is what the
 strand guard reads (`:154`) and what `createVerifiedCustomerSession` requires (`auth.service.ts:567`). So
 the two predicates disagree about what "can sign in" means.
- **F-7:** `unlink` clears `googleId`/`googleEmail`/`googleLinkedAt` but records no `SecurityEvent` or
 `AuditLog`, so "when was this Google identity detached?" has no answer (consistent with PART-119 F-4).
- **F-8:** the rate limiter is a per-process in-memory Map. Correct today (production runs one container),
 silently multiplied per replica the moment it scales.

RECORDED AS GOOD, SO IT SURVIVES
- The **strand guard is real and meets ADR-002**: `unlink` refuses unless the account has a password or a
 non-placeholder phone, **and** requires `isVerified`, and the refusal message names the consequence — *"or
 you would not be able to sign in again"*.
- `unlink` demands an exact case-insensitive email confirmation before the destructive write.
- **Correction I made while writing the part:** `hasVerifiedRealPhone` does **not** read `isVerified` — it is
 `return !!phone && !phone.startsWith('oidc-')`, presence and the placeholder prefix only. So the composite
 check is right while the helper's **name over-claims what it does** — the same pattern as PART-119's
 `requireAdminPass`... specifically `requireAdminRole` (PART-120 F-8). I caught this by reading the function
 instead of trusting its name, after having written F-5 to say something more generous.

NEXT — THE QUEUED CODE CHANGE SET, in this order
1. **Assert the reuse revocation** (PART-122 F-3): the test stubs a revoked token and asserts only
 `success === false`; delete the session-deletion loop and the suite stays green.
2. **Preserve the current session while deleting the others** (PART-122 F-2 + this part's F-1): give
 `revokeAllForUser` an exception, or revoke per-session rather than per-user. Note the access token's JWT has
 a `sessionId` but the refresh-token row does **not** — so the exception must be by token, or the two tables
 need linking.
3. **Shorten `JWT_EXPIRES_IN`** from `7d` to the code's own `15m` default — **unblocked since PART-122
 retracted F-7**.
4. Then `setPassword` should set `isVerified` (F-3), or the strand guard should read the same predicate the
 session creator reads.
