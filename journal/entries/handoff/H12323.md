### The lesson that changes every future merge

`VersionGuardInventoryTest` fails whenever the *set* or *count* of version guards changes — which is
exactly its purpose (it forces somebody to look up a guarded symbol's real API level before choosing a
threshold), and it fires on **every lane that merely touches a guarded file**. Four lanes in one fleet
made that a per-merge chore, and I broke it three times in a row because **my local gate
(`docs_check.py`) does not run the Android unit suite** — so a branch could be "gate green" and still be
CI-red on a test.

Measured examples of what the re-measure found:
- `hardening` removed `DisplayMirroringDetector`'s only guard (the `FLAG_PRIVATE` split), so that file
 now counts **zero** — the tempting "add it back" is a defect.
- `bt` on main removed one `AntiEvasionPolicyManager` guard: 4 → 3.
- `hardening` added the full-screen-intent gate: `BrokerHeartbeatService` 9 → 12.
- `diagnostics` adds three lines matching the pattern, and **none of them is a guard**: one is
 `sdkInt = Build.VERSION.SDK_INT` in a record, two are KDoc comments that *mention* it. **The
 inventory's regex counts comments**, which is a real imprecision in the check worth fixing at the
 source — the same class as the "nudenet in a docstring" false reading that cost me earlier.

**Tooling written to make this cheap and repeatable:** `C:\Users\ezabz\Code\_kf-lanes\remeasure_guards.py`
re-measures the map from the tree, rewrites the counts, **prints every new guarded file loudly** so the
"look it up" step is not skipped silently, and names any file that has reached zero. Run it in a lane
after any change that touches `android/app/src/main`, then run the full suite — not just the gate.
