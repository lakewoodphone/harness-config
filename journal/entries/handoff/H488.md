# H488 — round 8: the disagreeing fail-open defaults fixed, and the restart situation corrected

## 1. CONTENT-SANDBOX FAIL-OPEN — FIXED (`personal-secretary-mvp 83b2be20`)

This was on my own open list since round 1, and reading it properly found something worse than what I
had recorded.

**What I had recorded:** "`content_sandbox_enabled` fails open." True, and incomplete.

**What is actually there — TWO fail-open defaults that DISAGREE:**

```
content_sandbox.py:110 getattr(settings, "content_sandbox_enabled", True)
event_triage.py:183 getattr(settings, "content_sandbox_enabled", False)
```

The same missing configuration meant **"run the sandbox"** on one path and **"skip it"** on the other,
and nothing anywhere recorded which had happened. Because the setting is always present in practice,
the fallback only bites when configuration is missing or unreadable — exactly when a security decision
should not be made by whichever default happens to be permissive.

**And the silent path returned a clean-looking answer.** `parse_untrusted_content` returns `None` when
the sandbox is off, and `None` is also what it returns when there is nothing to report — so a caller
cannot distinguish *"the content was screened and was fine"* from *"prompt-injection defence did not
run."* **A security control that is merely OFF looked identical to one that PASSED.** That early
return now logs at **WARNING**, not debug: a defence that is not running is an operational fact, not a
trace detail.

**The fix:** `CONTENT_SANDBOX_ATTR` and `CONTENT_SANDBOX_DEFAULT` defined once, in `app/config.py`,
used by both call sites. `False` is chosen so an unreadable setting resolves to "do not claim
protection you may not have" — it does **not** change current behaviour, because a present setting is
read rather than guessed (`content_sandbox_enabled = True`, so the sandbox still runs).

**Why `config.py` and not `content_sandbox.py`:** the latter imports `app.assistant_chat`, which is
heavy and is precisely why `event_triage` defers its import of the sandbox into a function body.
Exporting the constants from `content_sandbox` would drag `assistant_chat` into every importer, and
importing them at module level in `event_triage` from there would have created a circular import.
`config.py` is the leaf module everything already imports.

**Verified:** all three files parse on both hosts; `from app.config import ...` → `('content_sandbox_enabled', False)`;
`import app.services.event_triage` succeeds (**no circular import** — the risk the placement avoids);
and no `getattr(settings, "content_sandbox_enabled"` literal fallback survives anywhere in
`app/services`. This closes the third of the three genuine fail-opens the audit found.
