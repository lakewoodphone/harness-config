# H (2026-10-20, round 19) - the duplication object is real, its declarations are right, and every RCW call to it faults

## Runs eight and nine, both reverted before anything was committed
**Eight: the pointer is a genuine DXGI COM object.** Dumped the vtable of the pointer `DuplicateOutput` returned:

```
ptr=0x29F831A6E20 vtable=0x7FF95730EB48
[0]=dxgi.dll [1]=dxgi.dll [2]=dxgi.dll [3]=dxgi.dll [4]=dxgi.dll
[5]=dxgi.dll [6]=dxgi.dll [7]=dxgi.dll [8]=dxgi.dll
```

Every slot resolves inside `dxgi.dll`, so it is not a garbage pointer - it is a DXGI interface with a real vtable.

**Nine: it still will not answer as a duplication object.** `AcquireNextFrame(0)` is the discriminator, because it returns
`DXGI_ERROR_WAIT_TIMEOUT` only for an `IDXGIOutputDuplication`. It raises `AccessViolationException` instead.

## What the SDK header rules out, so nobody re-checks it
- `IID_IDXGIOutputDuplication` = `191cfac3-a341-470d-b26e-a864f428319c` ✓ matches the interop.
- `IID_IDXGIOutput1` = `00cddea8-939b-4b83-a340-a685226666cc` ✓ matches the interop.
- `IDXGIOutputDuplication`'s member order in `dxgi1_2.h` is GetDesc, AcquireNextFrame, GetFrameDirtyRects,
 GetFrameMoveRects, GetFramePointerShape, MapDesktopSurface, UnMapDesktopSurface, ReleaseFrame - exactly the C# order.
- `IDXGIOutput` has 12 members and `IDXGIObject` 4, so `IDXGIOutput1::DuplicateOutput` is at vtable 22, which is where the
 declaration puts it (`dxgi1_2.h` line 2197, fourth member of that interface).

So: right IIDs, right member orders, right struct sizes, a real COM object - and every RCW call through it faults. That
combination is not a declaration bug, which is what eight runs have now established at the cost of eight console windows
on the owner's desktop.

## The decision this forces
**Stop probing inside xunit.** The next attempt must be a standalone minimal repro - a small console app (or plain C++)
that calls `DuplicateOutput` and `GetDesc` through raw function pointers with no RCW, no xunit and no product code. That
separates "this interop layer" from "this machine and session". Only if the standalone repro also faults is the
environment implicated, and then the answer is about the desktop it is running on rather than the code.
