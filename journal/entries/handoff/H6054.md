## 2026-10-14 00:50 UTC · ZABZ-YOGA · H - Yocheved's laptop: the click asked the wrong question, and her box never had the instruments

MEASURED 2026-10-13 on DESKTOP-FGV6KMH (Yocheved's laptop), from her exec API and her own session archive.

## What was actually wrong

The owner said the assistant "keeps stopping to work". The assistant itself was fine: her last session
(2026-10-05, `6c9c1ce4`) ran six real turns to completion and produced print-ready PNGs. The engine
answered HTTP 200 / 28800 bytes, and a live end-to-end model completion returned `MANAGER_READY`.

The fault was the CLICK PATH, and it was one wrong question asked in the wrong place.

`DESKTOP-FGV6KMH.open.cmd` asked `DESKTOP-FGV6KMH.windowcount.ps1` -- "how many msedge `--app=`
processes carry a URL under the profile root" -- and treated any non-zero answer as "she already has a
working assistant". That is a statement about PROCESSES. What she needs is "is the page inside it
authenticated against the engine running NOW". The engine mints a NEW launch token on every start and
a window keeps the token it was born with, so a window that outlived one engine restart renders
`dsh web authentication required` and was still counted. `windowcount` cannot tell the difference,
and `windows-registry.json` shares the same flaw (`open: true` is never invalidated).

Then the click took the "already open" branch: it ran an engine health check, printed one line, and
stopped. It opened nothing and RAISED nothing. dshw's dispatch has 24 verbs
(`up down restart status windows new ensure restore plan open stop logs health watchdog tasks-export
tasks-import autostart doctor help`) and NOT ONE of them focuses, raises, restores or reloads an
existing window -- so nothing in the entire estate could bring her assistant to the front.

And the branch is a pure function of the count, which does not change, so clicks 2..N did the same
thing. She could not recover by clicking again.

## The smoking gun

Measured in her own session: `focuswindow.ps1 -List` returned **`8652 minimized`**.

Her assistant window was MINIMISED. She clicked, got a three-second console flash saying "already
open", over a window she could not see. That is "it keeps stopping to work".

## The second, larger fault: she was dead for ten days and nothing said so

Her engine could not boot at all from 2026-09-18 to 2026-09-28 (a profile bundle name that stops the
boot). The repair is recorded in `journal/reference/yocheved-laptop.md` section 12.

The instruments that would have caught it already existed -- and her box had NONE of them:
`DSH Engine Watchdog (1m)`, `DSH Window Fleet Watchdog`, `DSH Profile Gate (15m)`, `DSH Engine Vitals
(5m)` were registered on ZABZ-YOGA and ZABZ-TECH and absent here. So this was not a missing
capability; it was an uninstalled one. Same shape as the L2609 lesson, one layer up.

The alarm gap survives today and is measurable: her shipper heartbeat is ALIVE
(`desktop-fgv6kmh:hb:... received 2026-10-14T00:02:58Z`, `session_count 0`) while her newest session
is 8.2 days old. `check_session_archive` cannot flag it -- its HIGH branch needs a
`next_stage_node_reports` row, and `PRESENCE_ALIASES` has no `desktop-fgv6kmh` entry -- so she can only
ever land in `quiet`, reported as `severity=INFO, ok=True`. That is the same sentence that was true
for ten days. A shipper that is alive is not an engine that is alive.

## What was changed, and what proved it

1. `multi-window/machines/DESKTOP-FGV6KMH.windowstate.ps1` (new) -- takes each window's OWN token and
 makes a REAL HTTP request to the engine. 401 = dead, refused connection = UNREACHABLE (which is
 "cannot tell", never "dead", so a healthy window is not duplicated). `total live dead unreachable`
 on one line.
2. `multi-window/machines/DESKTOP-FGV6KMH.focuswindow.ps1` (new) -- raises the window. Narrow by
 design: only root `msedge` processes with `--app=` under THIS machine's profile root, and it never
 counts, kills or launches anything.
3. `DESKTOP-FGV6KMH.open.cmd` -- a live window is now RAISED; a stale one is reported honestly and
 replaced; only a genuinely live window suppresses a new one. Engine-down is handled first so a
 good window is never mistaken for a dead one.
4. `scripts/yocheved-install-instruments.ps1` (new) -- drives the three EXISTING installers plus dshw's
 own watchdog registrar, and verifies each by EXECUTION (a task that reports success while never
 running is this fleet's most-repeated trap).
5. `dsh-new://` registered in CHEVE's hive, pointed at `DESKTOP-FGV6KMH.launch.cmd new`. It was not
 registered at all, so the `+` control was inert; and `sync.ps1`'s own value points at `dshw.ps1`
 directly, which loses the launcher's environment and violates D208.

**Verified, not claimed:** all four instruments `state=Ready`, each proven to have EXECUTED
(results 0 at 20:45:40 / 20:45:53 / 20:46:07 / 20:46:20), `engine-vitals.csv` being written, and the
real click path run inside her session printing
`Brought your assistant to the front. (1 working window(s))` / `open.cmd exit=0`.

## Decisions taken (dev decisions, mine)

- **Do NOT upgrade her engine tonight.** Her `@deepseek-ai/dsh` is `0.1.5-rc.1`; the fleet pin is
 `0.2.0-rc.2` (`dsh-update/state/pin.json`, pinned 2026-10-05). The upgrade is a one-way door
 (session format v3 to v4, no down-migration codec) and is coupled to a config migration and a
 15-minute sync window. It works today; introducing a version change now would confound the
 verification of the self-healing change and could strand her on the very traps recorded in H3107
 and H3161. Do it later, as its own backed-up operation, once the instruments have proved the box
 stable.
- **No change to `dshw.ps1`.** It is 209 KB, shared by every machine, and already carries the token
 probe and window liveness logic its own callers use. The whole fix above lives in her machine-local
 files, so fleet risk is zero. A `wake` verb in dshw would be tidier and was the audit's
 recommendation; it is recorded as a future improvement, not taken.
- **The alarm sink must be a queue row or journal entry, never SMS** (AGENTS.md section 4; L174b is
 the worked example of the opposite).
- **The engine upgrade path must not be run from a scheduled task without the launcher's environment.**
 `registry.npmjs.org` is reached through the Techloq MITM, so `NODE_EXTRA_CA_CERTS` and
 `NODE_OPTIONS=--dns-result-order=ipv4first` must be in the process that runs the install; a bare
 task does not carry them. Reachability of `registry.npmjs.org` from her box is NOT verified.
