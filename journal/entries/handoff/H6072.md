## I WAS WRONG ABOUT WHY THE PIN FAILED

H3635 said: "version-coupled SETTINGS: ~/.dsh/settings.yaml is a 0.1.5-shaped file, so on 0.2.0 the
deepseek-proxy route does not resolve and calls fall through to api.deepseek.com, which the Techloq
filter blocks."

MEASURED 2026-10-14, `--profile web --dump-config` on BOTH engines, and they are IDENTICAL:

The same three lines resolve for `--profile headless` on both engines as well. **So the route is not
the problem, her settings are not mis-shaped for the route, and the pin is not falling through to
api.deepseek.com.** Do not repeat that claim.

What IS measured: a `--profile headless` one-shot completion on the PIN exits 1 with
`dsh: TRANSPORT: DeepSeek Messages transport failed`, and the same command on the 0.1.5 tree exits 0
(RESTORED_OK). The failing transport is the **Anthropic Messages** one (`/anthropic/v1/messages`),
which is what the SEARCH provider uses -- and the dump shows `searchProvider: deepseek-official` on
both engines, whose default host api.deepseek.com is Techloq-blocked. So the most likely reading is
that the pin's 0.2.0 search plugin does not honour the same env name that `launch.cmd` sets for the
0.1.5 line (`DEEPSEEK_SEARCH_BASE_URL`), and the failure surfaces as a transport error even for a
prompt that needs no search. **That is a HYPOTHESIS, not a finding.** It was not tested.
