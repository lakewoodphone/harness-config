## THE REAL BLOCKER WAS NOT THE PIPELINE

Nine rounds of engineering, and delivery has not started because ONE approval is outstanding
and that approval existed only in a chat window. Chat is not a durable surface -- that is the
premise of this entire queue -- so putting the gate there made it invisible to every mechanism
the estate has for reaching him.

So the approval is now a ROW in `owner_decision_queue`:
 * source `decision-channel-approval`, kind `approval`;
 * severity high, and `blocks` set to what it actually blocks ("the delivery of every one of
 the 56 triaged questions"), which the queue's own ranking weighs at +200;
 * after that it RANKS FIRST in `owner-queue.py next` (score 960 vs #877's 781), so it is the
 item he meets when he next opens the queue rather than something buried on page three;
 * visible in `brief` too (verified).

## THE CHANNEL CANNOT TEXT A QUESTION ABOUT ITSELF

New CONTROL disposition: the triage classifies this row CONTROL, so `decision-deliver` can
never pick it. A channel that texts "may I text you?" would be absurd, and if the answer were
no it would have spoken when told not to. Verified in the live counts: CONTROL 1, and the
deliverer only selects SEND_NOW.

## HIS ANSWER, WHEREVER HE GIVES IT

`decision-approval-watch.py` turns his answer into the sentinel, from EITHER surface:
 * the queue row marked `answered` (he told whoever he was talking to);
 * an explicit approval TEXT after the row was filed -- because text is the surface he
 actually uses, and refusing to hear the answer there would repeat the original mistake.

EXPLICIT ONLY, AND REFUSAL WINS. A bare "yes" is not enough: he says yes to many things, and a
misfire here sends him up to 56 messages. PROVEN on throwaway stores, all four paths:
 explicit approval by text -> sentinel created
 explicit refusal by text -> sentinel absent, row closed with his words
 a stray "yes that's fine" -> NOT approved (the safety case)
 answered in the queue -> approved
On approval it also raises one wake flag instructing a session to watch the FIRST sends
specifically, verify the body reads as a real question, verify the answer lands back on the row,
and REMOVE the sentinel and report if anything goes out he would not have wanted.

WIRED into run-wake-sources.sh every 30 min, and it logs on EVERY run including "still
waiting", because a gate that is silent is indistinguishable from a gate that is broken.
First live line: "awaiting his answer: approval row #899 is pending, 0 text(s) since it was
filed, none of them an explicit approval or refusal".

question at a time, in his hours, with the shared ledger and the learning loop already behind it.
