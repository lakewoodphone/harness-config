`autonomy-status.sh.bak-heartbeat-alive-20261014T142657Z` is still `-rwxr-xr-x` while the live file
was not. Timestamps match to the second.

files use `os.replace`; 8 have no `chmod`, but only this one targets an executable (the others
replace JSON data, where 0644 is correct) — **not overclaimed.**

## Round 4 — the credential search was wrong twice, and the second test was the one that mattered

**The owner was right: a Cloudflare credential does exist.** `/opt/company/.env` carries
**`CF_API_TOKEN`** (40 chars) and `CF_ZONE_ID`. I had reported for three rounds that no Cloudflare
credential existed anywhere reachable. What I had actually measured was that none existed **under the
name `CLOUDFLARE_API_TOKEN`** — the name the website's own docs use. The estate stores it as
`CF_API_TOKEN`. **A negative is only as wide as the search that produced it**, and I stated the wider
claim from the narrower evidence.

Then I made a second, subtler error. Having found two tokens, I tested them against **token
management** — `/accounts/{id}/tokens/...`, `/user/tokens/...` — got 403 on every one, and reported
that neither could create tokens. But **the deploy does not need a token that can create tokens.**
That framing came from my own queue wording, not from the deploy. The deploy needs a token that can
reach **Pages**, and I had never tested that. The correct probe was one call:

| endpoint | `/opt/company/.env` (40 ch) | `waze-mdm-01:/opt/waze-mdm/.env` (53 ch) |
|---|---|---|
| `/user/tokens/verify` | 200 active | 200 active |
| `/accounts/{id}/pages/projects` | **403 code 10000** | **403 code 10000** |
| `/accounts/{id}/r2/buckets` | 403 code 10000 | 403 code 10000 |
| `/accounts/{id}/workers/scripts` | 200 (0) | 200 (0) |
| `/zones/{zone}/dns_records` | 200 (1) | — |
| `/accounts/{id}/tokens` | 403 code 9109 | 403 code 9109 |

**Both estate tokens are scoped to Workers + DNS. Neither can reach Pages.** So the token question is
real — but I only know that now, and it took one probe of the right endpoint.

Two further facts worth keeping:

* **The account is confirmed twice, independently** — the `abletelsolutions.com` zone resolves to
 `3fe00f424ec43810af16b55df54200a3`, and `CUSTOMER_BACKUP_R2_ACCOUNT_ID` on the deploy target gives
 the same value.
* **`lakewoodphoneandtech.com` is not visible to this token** — `GET /zones?name=…` returns 200 with
 an empty list, and the token sees exactly one zone. That is expected of a zone-scoped token, so it
 is *not* evidence the website lives in another account; it does mean the account id above is
 inferred (from the R2 credential) rather than read from the website's own zone. When a token with
 Pages access exists, `GET /zones?name=lakewoodphoneandtech.com` will settle it in one call.
* **Every token is nameable without printing it** — `/user/tokens/verify` returns the token's own id:
 `9520cec800b9994e6ec42a8a55d1265f` for the company one, `a7537bf3ffd4555e8710ccf16b03d419` for the
 waze one. Worth using whenever a token has to be discussed.

**THE TWO RULES THIS ROUND ADDS.** *Test the capability the task needs, not a proxy for it* — "can it
manage tokens" is not "can it deploy Pages", and neither is "is it valid". And *when reporting an
absence, report the scope with it* — the name searched, the hosts searched, the pattern used — so a
real negative can be told from an unsearched corner. Filed as **L6718**; queue **#533** amended so
nobody answers with the token we already have.
