## 2026-10-22 02:19 UTC · ZABZ-TECH · Kosher filter 1096: the obvious fix (feed the broker level into the ladder) is a POLICY change on two different scales - 1..3 vs 1..8 - and would not have failed a test

## 2026-10-22 03:00 UTC · ZABZ-TECH · Kosher filter: 1096 diagnosed, and the obvious implementation would have silently changed what children can see

No code shipped this round. `origin/main` unchanged at **c0446f7**. Ledger 1096 returned to `todo` with the design
corrected; new item **1108** filed.

### Why the discovery was worth the round

Ledger 1096 says "the device ladder has no level to run on… the broker already knows the level
(`filter_levels.py`) and already sends the knob keys; it sends no level." The obvious fix reads as plumbing:
send the broker's level, parse it, pass it to `classify(ladderLevel = …)`.

**That fix is wrong, and it would not have failed a test.** Measured:

- `filter_levels.py:56` — `LEVEL_PRESETS` keys are **1, 2, 3** (knob bundles).
- `owner_level.py:89` — `LEVEL_KEY = "modesty_level"`, validated in **[1, 3]**.
- `CascadeOrchestrator`'s own docstring — `ladderLevel` is **1..8**, and `modesty_meter.LEVELS` carries ten rungs
 with **9 and 10 RETIRED**, leaving eight live.

So a household level of 3 and a ladder rung of 3 are **different scales**. Any mapping (1→3, 2→5, 3→7) is a
**policy decision** — it changes what a child can see — and it would have looked exactly like plumbing in a diff.
Instead 1096 now requires a **separate optional `ladder_level` (1..8), absent by default**, which also satisfies
its own dod clause "the legacy fused path remains the default for a household with no level."

### What is verified

- `grep ladderLevel` over `android/app/src/main` returns hits **only inside `CascadeOrchestrator.kt`** — the
 declarations, the null check at 287, the call at 524. No production call site supplies it, so `classifyWithLadder`
 never runs. 1096's claim holds.
- **The wire already exists, and that is the good news**: `routers/phones.py` already reads
 `get_household_rules` and merges it through `build_effective_rules(base_rules, tenant_payload,
 household_payload, overrides)`. A household key needs no new transport — only a declared key, validation
 against the eight live rungs, and a device-side reader.
- **Six production call sites** must pass it: `ContentNotificationListener:179`, `ImageShareInterceptActivity:152`,
 `LockdownAccessibilityService:1375`, `NsfwPrefilter:50`, `MitmWsBridgeServer:378`, plus the orchestrator's own
 wrapper. That is why this is a next-round job, not a tail-of-round one.

### New item 1108 (p3): one asset, two parsers

`ml/LadderRungLevels.kt` declares `internal object ModestyLevels` and parses
`assets/modesty_levels.json` into `LadderRung.Table`; `modesty/ModestyLevels.kt` declares a **second**
`internal object ModestyLevels`, different package, parsing the **same file** into its own shape. Both are
tested, so this is not a live bug — it is a divergence waiting for its first one-sided edit: change one reader
and one consumer's policy moves while both test suites stay green. Same class as the estate's one-source-of-truth
rule, except the *asset* is shared and its *interpretation* is not.

### Traps paid for here

- **"The broker already knows the level" is true and misleading.** Two things called a level, on different
 scales. Before wiring A to B, print both ranges — `LEVEL_PRESETS` keys versus `LadderRung.LIVE_RUNG_COUNT`.
- **A PowerShell `Select-String -Pattern "modesty_level|modestyLevel"` is case-INSENSITIVE** and matched the
 `ModestyLevel` *class name*, making it look as though six Kotlin files already parsed the wire key. Re-run with
 `-CaseSensitive` before concluding anything from a grep whose pattern mixes camelCase and snake_case.
