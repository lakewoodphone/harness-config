**The outage, because it is the most important thing I did wrong today.** I merged a lane that added
two routes (`/updates/android/...`) without a rule in `route_security.py`, and `validate_startup`
refuses to boot on an unclassified route. The deploy built and `up -d`'d the new image, both brokers

pre-deploy anchors the script had just tagged (`5cd27ec43d5b`, `4676f910f116`) and `/health` returned
200. Then: classified the routes, and added **deploy step 10**, which starts the application inside the
new image in a one-off container and refuses the deploy if the startup audit fails, before anything
running is replaced. Redeploy proved out of the running containers: 37 migrations, 361→389 paths,
healthy, anchor tagged. **A route the classifier has not been told about does not degrade — it stops
the process**, and a lane's green unit tests never start the lifespan.

**Two integrator bugs of the same family, both worth remembering.** The updates router was mounted in
`main.py` only, so every app the tests build from `include_default_routers` lacked it and the
route-security audit reported the paths as *missing*; registering it in the registry as well then
served each path twice (391 served against 389 known). **One router, one registration point.**

**The finding that changed the programme's shape.** With a release target, `DISALLOW_DEBUGGING_FEATURES`
turns adb off at the seal, `DISALLOW_INSTALL_APPS` blocks installing the test APK afterwards, and R8
strips the Kotlin runtime out of the minified test APK. So the seven release-only restrictions **cannot
be asserted over adb on a sealed phone** — and a proof that needs an unsealed phone describes the wrong
phone. Decision `D-20261023-01`: **the phone attests to itself** — read the policy back from
`DevicePolicyManager` at seal and on every boot, keep a dated history, show it on diagnostics, send it
on the existing heartbeat (not a new route: see the outage). Row `A-P5-18`, lane live.

**The release channel is live and proved end to end.** `GET /updates/android/manifest.json` → 200 with
`versionCode 100` and `sha256 e29f489a…`; the APK is served at 58,102,707 bytes; the digest of the
bytes fetched over the public URL equals the digest the manifest declares. Publishing is
`deploy/broker/updates/publish-update.ps1 -Publish`, which reads the version from AGP's own
`output-metadata.json` and never types a digest. **A local-machine quirk to know:** fetching that `.apk`
from ZABZ-YOGA's network returns a 404 with a broker-shaped JSON body, while the same URL from the host
returns 200 — the local path mangles `.apk` downloads, and it cost an hour of chasing a bug that did
not exist. Verify downloads from the host, not the laptop.
