## New tool: `Get-BitLockerKeyProof` — `lpt-hub` commit 5f7ba5561

`scripts/Get-BitLockerKeyProof.ps1` + `.cmd` in the repo, and the same two files on the shop stick in `D:\LPT-KeyCheck\`. **sha256 verified equal in both places** (`f18a7eb7…` and `2adcfaf5…`).

What it does, in order:

1. reads the recovery password **out of the volume's own protector list** with `manage-bde` — not from a file, not from a copy;
2. **SHAPE** — 48 digits in 8 groups of 6;
3. **OWNERSHIP** — the protector id the key came from is listed by **this** volume as `RecoveryPassword`. This is what makes it this machine's key;
4. **identification field** — computed independently and compared with BitLocker's own, recorded as **INFO and never a failure**, because the derivation is not official;
5. writes the key and a JSON record beside itself, then **reads its own output back off the stick**.

Exit codes: **0** proven capture · **2** the volume carries no recovery password (nothing lost — there was nothing to capture) · **4** read-back mismatch, **the file must not be trusted**.

**Read-only against the target:** no protector added, removed, enabled or disabled; the volume is not locked or unlocked; nothing written to the machine's own disk. The `.cmd` self-elevates (`net session` + `Start-Process -Verb RunAs`), and the `.ps1` self-elevates as a fallback for a direct run.

## Verified before it went near the customer's machine

- **Parsing tested against REAL `manage-bde` output from that exact machine**, held in the archived capture: `Conversion Status`, `Protection Status`, `Identification Field`, `Encryption Method` all matched, and both real protector ids parsed (`{341D1FAC…}` and `{35EB0031…}`).
- The 48-digit regex finds **0** in the archived capture — correct, because the collector withheld the key — and exactly **1** in a synthetic protector list in the real `manage-bde` format, shape check passing, 48 digits.
- Both files parse **clean** under the Windows PowerShell 5.1 parser and are **pure ASCII**, because 5.1 reads a BOM-less `.ps1` as ANSI and one non-ASCII character silently breaks it. That trap is written down in the LPT-Access kit's README; it is now also respected here.
- Two bugs were caught and fixed before shipping: `$PScriptRoot` (a typo — the real automatic variable is `$PSScriptRoot`, and the fallback chain is now three deep), and an unguarded `$fingerprint.Substring(0,16)`, which would have thrown on an empty hash.
