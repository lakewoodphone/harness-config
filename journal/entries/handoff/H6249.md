## 1. The verification found a real failure, and the job found it itself

```
[03:10:57Z] entries 5145 -> 5146 (+1) pull rc=0
[03:11:01Z] check: -- 1 error(s), 329 warning(s), 82 info
[03:11:01Z] [failed] check exited 1 AFTER the pull -- the added files are still there and must be read
status.json: {"result":"check-failed","detail":"check rc=1 after adding 1","added":1}
```

```
ERROR entries/lessons/L6657.md: metadata sha=ea37b84f235cfecf does not match the body (6f9db4f13532ce58)
```

**Root cause.** `sha` is computed over the heading AND the body. When the pull RENUMBERS an arriving
entry — because its id is already taken by a different entry — it rewrites both, and the sha the sending
machine recorded is left stale. `L6657` was the first arrival that collided since the job existed.

**It is fixed in the pull, not in the job.** The job's `check` is deliberately strict and has NO
`--fix`: a second writer touching an entry the pull has just landed would hide the next bug of this class
instead of failing on it. So `converge-pull.py` now recomputes the sha on the renumber path.

**AND THE FIX IS PROVEN, not asserted** — the path only fires on a collision, which ordinary traffic does
not supply on demand, so one was built deliberately on a COPY of the record:

```
copy of the real tree: 5,146 entries
source entry: same id, different body -> TO ADD: 1 t1 lessons L6657 -> L6658 (id taken)
landed: entries/lessons/L6658.md sha=ab88d954fa74d0fb
check, on the copy: -- 0 error(s) exit=0
```

The record itself was repaired once (`check --fix` -> 0 errors) and the job re-run clean.
