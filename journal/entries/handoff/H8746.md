## What the divergence check found

Every change in this programme was deployed the same way: `scp` the file to
`/root/code/unified-search/server/esearch.py`, restart the service, verify the behaviour. It worked every
time, and it hid this:

 git log -- server/esearch.py -> (nothing)
 git status --short server/ -> nothing, because the file was UNTRACKED

The authority's clone sits on an older commit whose tree **does not contain `server/` at all**. So the
running search service has been executing a file that appears in no commit on that host, protected only
by my having put it there. Nothing in `/health`, `/integrity`, the timers or the journal would ever have
mentioned it, and a later `git pull` by anyone could have replaced it with something older without a
single error.

Fixed for the path that matters: `git checkout origin/main -- server/` on the authority, verified
identical to origin, service restarted, and the behaviour re-checked. The rest of that working tree
belongs to other agents and was left alone.

**The rule, now in `deploy/README.md`:** deploy with `git fetch` + `git checkout origin/main -- <path>` +
restart, and afterwards confirm two things — that `git log -1 -- <path>` names a commit, and that
`git diff --stat origin/main -- <path>` is empty. *A file that appears in no commit is a file nobody can
restore.*
