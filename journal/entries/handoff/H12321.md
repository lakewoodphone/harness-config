Bar 1 says "behaviour is uniform at 30, verified by running the suite on emulator images at API 30, 34
and 36". I built the missing API-30 image (`system-images;android-30;google_apis;x86_64`), created

| Image | Result |

| `Medium_Phone_API_30` (Android 11) | **14 tests, 5 failures, 6 skipped** |

**The failures are real assertions, not a harness error, and the most important one is:**

```
java.lang.AssertionError: dpm.getPermittedAccessibilityServices(admin) returned null, which means NO
allowlist is installed: every accessibility service on the phone is permitted, so any app the user
enables can read the screen the filter is supposed to be watching
 at AccessibilityAndFrpTest.theAllowlistPermitsThisPackageAndNothingElse(AccessibilityAndFrpTest.kt:49)
```

The other four are the same shape — `restrictionsThatApplyInEveryBuildAreApplied`,
`ourOwnForceStopAndClearDataAreNotTheUsersToPress`, `theFilterCannotBeUninstalled`,
`unknownSourcesUsbTransferAndOverlayWindowsAreBlocked`. All five say *the seal policy was not applied*.

**What is established and what is not.** Established: `dumpsys device_policy` reports
`Device Owner: admin=ComponentInfo{.../deviceowner.AdminReceiver}` on that AVD, so ownership was in
place. Not established: whether the product failed to apply, or whether the
`ACTION_DEVICE_OWNER_CHANGED` apply path behaves differently on API 30, or whether the second run's
"device owner is already set" means the broadcast never fired in that session. **I am not calling it a
product defect until it is diagnosed** — filed as ledger **1183**, priority 1, claimed.

**A second, independent finding from the same run, and this one is certain:** `dpm list-owners` does
**not exist on Android 11**. It answers `Error: unknown command 'list-owners'` and prints a usage list
that does not contain it. The shop's install verification reads ownership with that command, so on every
Android 11 phone it would report no owner. That is roadmap row **A-P5-04** ("counter_install: read
ownership from dumpsys device_policy, not only dpm list-owners", state `partial`) proven live — and it
means the counter script's own success check is wrong on the floor version.

Third small one: **the JUnit XML carries no assertion text under `<failure>` as an attribute**, so a
reader who prints `.message` gets five blank failures. The text is in the element body. Any future
triage of a device run must read the raw element, not the attribute.

### The fleet rule settled this round

Every lane commits **its own** generated docs and fact numbers, in a separate commit, and the manager
re-runs `--write` after each merge. The usual advice is "never merge a generated file from a branch";
it is wrong here because **a red PR hides real failures** — if every lane is red for the same
known-stale reason, the next genuine regression is indistinguishable from the noise.

And the specific trap, learned three times tonight: **`docs_check.py --write` alone does not fix
`FACT-STALE`.** The hand-written `VALUE` in `scripts/facts/android-test-files.py` (and its kotlin
sibling) must be bumped from the script's own output, and after all merges the correct value is the
**merged** count, not any one lane's.

### Integration lessons added

1. **A failed inline `python -c` inside PowerShell can leave conflict markers committed.** I committed
 `scripts/facts/android-test-files.py` with `<<<<<<<` in it and did not notice until the next read.
 Write the resolver to a file, and verify the result parses (`ast.parse`) before committing.
2. **`connectedDebugAndroidTest` does not accept `--tests`.** Per-class filtering is
 `-Pandroid.testInstrumentationRunnerArguments.class=...`. My diagnostic run produced no test output
 because of it — a wasted emulator cycle.
3. **A relative link from `docs/roadmap/items/` needs `../../`** — third occurrence, caught by the gate
 each time.
4. **`gh pr create`/`--body` with backticks in a PowerShell double-quoted string mangles the body**;
 always `--body-file`.
