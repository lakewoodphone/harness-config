## ROUND 14 — the block record now says WHY, and says it readably

Three linked fixes to `~/bin/textwork.py`, each verified by running the block path with a
stub rather than by reading the patch:

**(a) An injected `llm=` can no longer raise out of `do()`.** It caught exceptions from the
real decider but not from an injected callable, so a stub that raised — which is how the
failure paths are tested, and a gateway 502 is exactly such a raise — propagated out
instead of becoming a block. Both branches now catch and note.

**(b) `_evidence()` keeps the reason instead of discarding it.** It returned the bare string
`"nothing was read"` whenever no tool had run, so a block caused solely by an HTTP 502
recorded those three words and threw the error away — the same shape as `L3234`, and the
reason the three blocked owner texts from 2026-09-30 could not be diagnosed. When there is a
note explaining the failure, the note IS the evidence.

**(c) Repeats are folded, not repeated.** `do()` deliberately retries a no-usable-JSON
reply, so a systematic failure repeats identically and the first version of (b) produced a
wall: the same 502 three times. Notes are now deduplicated by text, first occurrence in
order, with a count.

Verified output, end to end:

 _evidence(["contacts"], ["contacts: ok"]) -> read via: contacts (contacts: ok)

That is the case that could not be diagnosed before: a job blocked by a dead gateway now
carries the gateway's own words, condensed, and still raises the question for the owner.

## ROUND 15 — an independent Amazon order path, from the owner's own mail

The ledger's order feed stops at 2026-09-10 and **12 Amazon charges arrived after it**, so
every one was a charge it could not name an item for. The owner's instruction was that these
accounts are readable; scraping needs a login, but **his own Gmail does not**:

 search_messages(account='lakewoodphoneandtech@gmail.com',
 query='from:amazon.com after:2026/09/15 before:2026/10/03')
 -> 10 messages, including orders placed TODAY, each with a real order id
 (111-5561267-3146639, 112-2469213-6984228, ...)

So `charge_msg` now falls back to the mail when the ledger cannot name an order.
**What it gives:** an order id and the day. **What it does NOT give: the amount.** Checked
five order confirmations in full — Amazon's mail carries **zero** machine-readable `$`
amounts — so this path cannot pick between several orders on one day.

**Four defects found and fixed while building it, and the first is the one that mattered:**

1. **`NameError: name 'sys' is not defined`.** `charge_msg` used `sys.path` and never
 imported `sys`, so **every** call raised inside the lookup — and the bare
 `except Exception: continue` swallowed it, making the whole fallback return `""` and look
 exactly like "no Amazon mail in this window". This is the **third** silent fallback found
 in this engagement, after the composer wrapper and `app_db_query`. Found only by making
 the exception visible.
2. **One order id printed against three different charges.** Three charges on 2026-09-28
 each got `order 112-7603884-6857046`. Since the mail has no price, a multi-order day
 cannot tie one order to one charge — the confident-falsehood shape of `P2828`. The rule is
 now: **name an order only when the day holds exactly one**, otherwise say how many there
 are and name none.
3. **The fallback attached to non-Amazon merchants** — `data reclos` and `newegg` were both
 given "5 Amazon orders that day". Nonsense on its face. It is now gated on the merchant
 being Amazon, which is correct by construction (it searches `from:amazon.com`).
4. **Length.** The honest version ran ~230 chars and pushed bodies past the 300 ceiling.

**Verified end state, every body re-measured:**

 data reclos 192 chars card, statement line, sibling, no invented guess
 amazon 275 chars + "3 Amazon orders that day - cannot tell which from mail"
 amazon order total 234 chars + "4 Amazon orders that day - cannot tell which from mail"
 the home depot 257 chars + the real vendor email and order line
 newegg 169 chars + "newegg.com order #419077624"
 polka dot 115 chars clean

Because every sampled Amazon charge has 3-6 orders on its day, this fallback currently
**abstains rather than guesses** — which is the honest answer and leaves the ledger (needing
his login) as the only source that can name an item for an Amazon charge. It is a safety net,
not a replacement.

Also found and recorded: `email_triage_log` holds **1** `from:amazon` row since 2026-08-01
while Gmail holds 10 just in a two-week window, so the app's triage ledger is not a usable
source for order mail; Gmail is.
