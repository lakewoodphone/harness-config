## THE LESSON FROM ROUND 16 IS NOW A MECHANISM

Round 16 recorded L11967: an answer that asks for work must become work. I implemented it by
hand that round (cfo#941), which works only while a session is watching -- the exact failure this
estate keeps fixing. It is now in `decision-answer-capture.py`:

 * every answer it records is checked for an INSTRUCTION ("make sure", "document", "send me",
 "call", "order", "file", "walk me through", and the rest of an explicit list);
 * a hit files a ledger item, idempotently keyed on `source=owner-answer:<row>`, so a re-run
 cannot file the same instruction twice;
 * finance words in the question route it to the `cfo` project, everything else to
 `housekeeping`;
 * the item's `why` quotes his answer verbatim, so the work carries its own provenance.

TESTED against his real answer and five negatives:
 "Make sure all the information is fully documented and ready for me to file ..." -> files
 "Call them and book the appointment for Tuesday" -> files
 "Order the part and send me the receipt" -> files
 "No, don't call them, leave it for now" -> creates NOTHING
 "Yes go ahead" -> creates NOTHING
 "no" -> creates NOTHING
The third negative is the one that matters: a REFUSAL can name an action ("don't call them") and
must not be read as a request to do it.

## MY CRON LINE WAS SILENTLY DEAD, AND I FOUND IT BY READING THE WRAPPER

`cron-wrap.sh` reads its payload from **$2**. When I added the rate to the crontab I put
`DECISION_DELIVER_MAX_PER_DAY=6` in that position -- not base64 -- so cron-wrap refused the line:
"payload for decision-deliver is not valid base64". The ONLY reason anything still sent is that
the previous line was still there at the time. That is a silent stop waiting to happen.

Fixed properly: the env lives in `decision-deliver-cron.sh` (with his quote as the reason), and
the crontab payload is the estate's own wrapped form. PROVEN by running cron-wrap with the real
payload by hand: rc=0, no stderr, and the wrapper logged a normal LIVE run.
