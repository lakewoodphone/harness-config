## 2026-10-14 · ZABZ-YOGA · The counter's "All statuses" meant "Open", so the owner's search could not find a finished job — fixed, PR #441

**What the owner reported, verbatim** (filed through `owner-feedback.py` as ledger item 216, which also raised a HIGH flag and put an `OWNER-FILED (P3)` row at the top of `docs/website/ROADMAP.md`): the search in the website "only searches within whatever filters currently set ... when you do all on the filter ... it only searches open work orders. It doesn't search any of the other statuses ... you have to click every type of filter in order to search that type. There's no global search for real."

**ROOT CAUSE, read in the source at origin/test 73a4380.** `frontend/src/features/staff-intake/staff-intake-list-queue.ts` had ONE scope value (`StaffStatusFilter = WorkOrderStatusKey | 'ALL'`) behind TWO controls: the `Open` chip and the `All statuses` radio both set `'ALL'`, and `queueStatusesFor()` in `staff-intake-list-query.ts` mapped `'ALL'` to `WORK_ORDER_OPEN_STATUS_VALUES`. So the control labelled ALL STATUSES asked `workOrders.getAll` for the four open statuses; `READY_FOR_PICKUP`/`CANCELLED`/`UNFIXABLE` were never in the payload and no client-side filter could reach them. The search box searches within the scope in force, so it inherited it. Which page: `/work-orders` is the Counter (`App.tsx` mounts `CounterPage` there and shadows `MVPRouter`'s own `/work-orders`, which holds `WorkOrdersHub` — that hub does NOT render at that path).

**THE FIX (commit 9d6815ce1, branch `lpt/counter-all-statuses-20261014`, PR #441 into `test`).** `OPEN` (four statuses, the DEFAULT — the default screen is unchanged) and `ALL` (all seven) are two values; one new `statusFilterSet()` is read by BOTH the request builder and the row filter so they cannot drift; `All` is a chip one tap from the search box; each scope states what it means; and an empty search under a narrowed scope now names the scope that emptied it and the control that widens it. `filterTotalFromServer`, `describeQueueSummary` ("open jobs only"), `describeEmptyQueue` and `readStatusParam` (unreadable → the DEFAULT, never the widest) all follow. `isOpenIntakeCase` keeps every open counter ticket under both scopes.

**PROOF.** `pnpm --filter phone-and-tech-frontend typecheck` → exit 0. Suites green: `staff-intake-list-queue.test.tsx` 72 passed, `StaffIntakePage.test.tsx` 67 passed, plus `staffOpenListDesktop`, `counterStatusNames` and `CounterPage` (97 passed across the four). A FRESH WORKTREE NEEDS `pnpm worktree:setup` FIRST or every suite that imports `@phone-and-tech/shared-types` fails to resolve — that was the whole of the initial 15 "failures" in `CounterPage.test.tsx`, and it is also the likely explanation for ledger item 170's "4 tests are RED at HEAD 42e80ec".
