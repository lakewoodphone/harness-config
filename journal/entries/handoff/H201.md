## 2026-09-14 22:52 UTC · ZABZ-YOGA · The filter can take money: Checkout built, and the upsert that would have erased every subscription status

**Owner said "whatever you can do without me do, whatever needs my input tell or ask me."** So this round took the revenue blocker, because it was the biggest thing I could finish alone.

**CHANGED** — `kosher-filter-ai` @ **`e2888d8`** (pushed, verified in sync with `origin/main` by SHA after fetching).

**The broker could not charge anyone. It can now — with three values configured.**

- **`server/app/billing_checkout.py`** (new): `create_stripe_customer`, `create_stripe_checkout_session`, and a pure readiness payload. The tenant id travels on `client_reference_id` **and** `subscription_data[metadata][tenant_id]`, which is exactly the key the *existing* webhook reads — so a subscription started here is attributed with **no new event handling at all**. A customer is **created, never adopted**: looking one up by email would attach a paying household to whatever customer row shares that address.
- **`POST /owner/billing/checkout`** — registered in `app/route_security.py`, rate-limited.
- **Site: `POST /billing/subscribe`** — passes the provider's redirect to the browser **without following it server-side** (following would fetch the provider's page from our server and hand the parent a URL that is not ours), requires the session CSRF token, and surfaces a broker refusal instead of bouncing the parent to a page that says nothing. The account page offers billing only when it is actually open, and says *"Nothing is charged until you complete it there."*

**THE TRAP AVOIDED, and it is the kind that loses data.** The obvious way to record the new customer id is `upsert_tenant_billing_state(...)` — except that method is a **full-row replace** (`ON CONFLICT(tenant_id) DO UPDATE SET status=excluded.status, current_period_end_ts=excluded.current_period_end_ts, ...`). Calling it with only a customer id would **erase the subscription status, the period end and the plan code** on every existing subscription, silently, with no error. So the route writes **nothing**: Stripe creates the customer from `customer_email`, and the existing webhook records the id — the only writer that already knows how to write a full row. (The general hazard is now recorded: a method named `upsert` that behaves as a full replace will be misused by whoever calls it next.)
