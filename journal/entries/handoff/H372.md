## 2026-09-15 22:44 UTC · ZABZ-TECH · 2026-09-15 close: all five workstreams integrated on origin/test 89e5ff81d - the portal fixes exist but are not deployed

ALL FIVE audit workstreams are integrated. Final refs: phone-and-tech-full origin/test
89e5ff81d, personal-secretary-mvp origin/master 4c3ab1e8, lpt-hub origin/main 10fec5f12.

The last two commits on test: 2963311be (frontend robustness) and 89e5ff81d (the guard
alignment below).

WHAT THE FRONTEND WORKSTREAM CLOSED (35 new tests, 13 of which were red before):
- CustomerSettings had NO error branch, so a failed profile read rendered blank fields as fact
 and the next Save wrote the customer's address as JsonNull. Now: a load-failure panel instead
 of the form, Save disabled while either read is in error, and the address is only sent when it
 has content. This was silent customer-data destruction on a page that never said anything was
 wrong - the highest-consequence finding of the whole audit.
- Forgot-password awaited both mutations with no try/catch, so a rejected request left the
 recovery page completely silent.
- The 4xx retry predicate grepped error MESSAGE text for "status 4NN", so it never matched and
 every 4xx was retried three more times; the account-change endpoints count before validating,
 so one mistyped code consumed four of five attempts and a second typo locked the customer out
 for ten minutes. Now it reads error.data.httpStatus, on the query predicate too - the same bug
 existed there, outside the brief's line range.
- The staff fleet page rendered "No LPT devices yet." / "No unresolved alerts." / "0 devices
 across 0 locations" whenever a fetch failed. Now an explicit required state (loading|error|
 empty|ok), and "not configured" is only claimed when the status query actually SUCCEEDED.
- WazeDevice printed the literal string "null GB"; now "unavailable".

DECISION I MADE FROM THE MISMATCH THAT WORKSTREAM REPORTED (89e5ff81d): all 16 wazeFleet
procedures are adminProcedure, but the nav entry said roles ['admin','staff'] (MANAGER -> 'staff')
and the route guard accepted ['ADMIN','MANAGER'] - so a manager was offered a page where every
query 403s, and the page then showed an empty-but-calm fleet. I narrowed the offer instead of
widening the guard: these actions are fleet-wide (lockdown, lost mode, queue prune, renumber,
across 65 devices) and that is not a manager's blast radius. Making a page look consistent by
handing a manager fleet-wide destructive actions would have been the wrong direction.

TWO CONSEQUENCES ACCEPTED, recorded rather than hidden:
1. The blank-address guard also makes INTENTIONALLY clearing an address impossible from that form
 (the backend does support writing null). Safer than erasing by accident; an explicit "clear my
 address" affordance is the fix if the owner ever wants it.
2. WazeDevice's usage bar still draws 0-width when percentUsed is null while the band is known.
 Left as-is rather than widening scope.

WHAT IS NOT DONE: nothing in this audit is deployed to the portal yet. The API-level fixes are
live (fleet-api liveness, dashboard honesty); origin/test carries the portal-side fixes and needs
a deploy (backend image on lpt-apps-01 plus the Cloudflare Pages frontend bundle) before a
customer or a staff member sees any of it. The frontend bundle is the half that makes the "null
GB" and "0 MB" renders disappear.
