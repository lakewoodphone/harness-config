# H486 — round 6: the corpus-behind problem now ANNOUNCES itself, in both places it was silent

## WHAT WAS WRONG

Two silent-by-default failure modes were hiding the corpus's real state. Neither is fixed by a
bigger number; both are fixed by **saying so**.

## FIX 1 — `lptcase.py` now warns when the corpus is incomplete or stale (`8cb746a06`)

The canonical finder gained `corpus_integrity_warnings()`, run on **every read command** and printed
to **stderr** so a warning can never be mistaken for the answer or for a result row. It checks:

- **a reparse point on the path to the corpus.** `personal-secretary-mvp\lpt-hub` WAS a junction to
 `Code\lpt-hub`. ripgrep **and** .NET both descend nothing through it when the search root is an
 ancestor, and both **exit 0** — so a search for a customer who exists returns a clean, empty answer.
 Reproduced: the same token gave **1 hit** from the psm root and **10** from the hub root;
 `rg --files` at the psm root listed 2,807 files and **zero** under the junction, while addressing
 the junction directly listed **10,539**. The content was never absent.
- **on-disk case count vs `git ls-files`.** A gap is exactly what a partial copy or a reparse point
 looks like.
- **drift from origin, in BOTH directions.** Behind origin = stale. Ahead of origin = unpushed case
 work that **no other machine can see**, including the digest and the drift verifier.

**Verified both ways, and the second half is the important one.** On the ZABZ-TECH checkout it prints
the stale + unpushed warnings, and its `find` surfaces the new `Goldstein` case the authority cannot
see. On the authority clone, clean at `0/0`, it prints **nothing**. A warning that fires when nothing
is wrong is noise, and noise gets ignored.

Best-effort throughout: a failure to measure reports `UNMEASURED`, never clean.

## FIX 2 — the digest states the corpus freshness and admits its blind spot (`45bc301`)

The digest reported `383 records` and discarded `behind`, `head` and `origin_main` — which
`lpt-hub-refresh.sh` had **already been writing** into its status file. Nothing new had to be collected
to make the page honest; it was throwing the facts away.

Measured earlier the same session: the authority clone reported `behind: 0` against origin while
ZABZ-TECH held **3 unpushed commits** and a corpus of **187 cases / 384 records** against the
authority's 186 / 383. The digest was reporting a corpus one case stale and nothing said so, because
the refresh pulls from **origin** and cannot see work that was never pushed.

The published page now reads:

```
── 9. CUSTOMER CORPUS ↔ PRODUCTION ──
Corpus records: 383 in the authority clone at 9ed3018c1 (refresh: ok, behind origin: 0)
Corpus push gap: 🔴 7 record(s) in the hub but NOT in production (measured 0.0h ago)
 NOTE: 'would create' is not 'should create'. Records held for a
 documented reason are counted here too; the record schema has no
 field in which to say 'held, and why' (operational is
 additionalProperties:false). Do not read this as 7 broken jobs.
 BLIND SPOT, stated: unpushed commits on another host are invisible to
 this check. Run 'git status' on the machine that does the case work.
4-surface verify: 🔴 7 drift finding(s), 73 warning(s) (last run 4.9m ago)
```

Three things this changes: a clone falling behind origin now counts as a **PROBLEM** with the commit
count instead of quietly lowering every other number; the gap no longer implies 7 broken jobs; and the
blind spot is stated **where the reader is** rather than being left for an agent to rediscover — the
blind spot that hid a 1-case lag today.

**The page also demonstrates the mechanism honestly:** it printed `at 9ed3018c1` while the clone was
already `8cb746a06`, because the refresh status it reads is up to 15 minutes old. It reports the head
it actually read rather than implying currency. That is the correct behaviour, not a defect.
