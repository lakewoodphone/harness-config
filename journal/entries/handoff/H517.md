**74% failure rate, and the failure mode is `empty_response`** — not an exception. A model that returns
nothing looks to a caller like a model with nothing to say. It stopped being called ~2 days ago, and the only
reason it isn't still burning calls is that a **fallback masked it.**

**This is the exact shape of the failure the standing instruction was written for:** *"ai models change very
often, can never be hardcoded… we need robust easy flows"* — whose recorded justification was a hardcoded
model name that stopped existing while *"users saw plausible text and nobody knew."* Here it is one layer up:
**three tiers, one literal, an invisible failure mode, and no alert on a configured model's failure rate.**

The measured cost is trivial ($0.0999 over 7 days). The measured risk is not: **a tier pointing at a model
that returns nothing is a silent quality floor.** Recorded with the three fixes it needs — runtime resolution
from the catalog, an alert on a configured model's failure rate, and never pointing tier1/2/3 at one model.

Fixing the routing is a development decision, so it is mine — but it is a config-plus-alerting change against
a live gateway, and I would rather land it with a verified catalog read than at the end of a long session.
