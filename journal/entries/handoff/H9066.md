 could never fire. Now: server app/models.py Hello accepts android_id, boot_count and uptime_ms (all
 optional, extra="ignore" preserved so a phone sealed last month keeps checking in), and the app sends

 Verified: 16 server tests green on zabz-tech (13 classifier + 3 transport contract), Android suite 588
 tests / 0 failures on zabz-yoga.

2. A FINDING THAT CORRECTS THE DESIGN, found by building it: the client default phone_id IS the android
 id (android/.../util/PhoneId.kt). So a phone with no per-device override comes back from a wipe as a
 BRAND-NEW phone id and the old record simply goes silent. "Same phone, new android id" - the only
 CONFIRMED wipe - exists only on phones sealed with a stable override (LPT_PHONE_ID). Without it the
 best verdict is WIPE_SUSPECTED at level 4: a real alert, not proof. Recorded in
 docs/design/ANTI-RESET-ARCHITECTURE.md section 6 with the consequence: minting and verifying a
 per-device phone id is part of the seal, not an optional build flag. A test pins the weaker behaviour.

3. A compile error caught by running, not reading: the third hello-shaped payload sits in a nested scope
 with a Context parameter where the Service contentResolver is not visible. Fixed; suite green.
