## 2026-10-20 18:16 UTC · ZABZ-TECH · round 16: the duplication hardware blocker was a session artefact plus a COM vtable-order bug that killed the test host

# H (2026-10-20, round 16) - the "hardware" blocker was a session artefact and a COM vtable bug that crashed the test host

## What the register said, and what was true
W-P3-01 was blocked on hardware: "the wake session on ZABZ-TECH has no attached output, so
IDXGIAdapter::EnumOutputs(0) returns DXGI_ERROR_NOT_CURRENTLY_AVAILABLE". Two measurements took that apart.

**1. It is the session, not the host.** A process started over ssh runs in **session 0**: `query session` shows
`services` = 0 Disc and `console` = 1 **Active**. Session 0 has no desktop, so EnumOutputs fails there. Run from a
process inside the console session - a one-shot `/it` scheduled task, deleted afterwards - the output is found and
the duplication **opened**.

**2. `IDXGIOutput1`'s methods were in the wrong vtable order.** `DuplicateOutput` was declared LAST, after
`GetDisplayModeList1` / `FindClosestMatchingMode1` / `GetDisplaySurfaceData1`, and `DuplicateOutput1` and
`GetFrameStatistics1` were missing entirely. So the CLR's computed slot was `GetFrameStatistics1`, which writes a
`DXGI_FRAME_STATISTICS1` through the `out IntPtr` and returns `S_OK` - a successful call into the wrong function.
The next call, `GetDesc`, then faulted with `AccessViolationException` and **killed the test host**.

Fixed by declaring the real order. The AV is gone. CI's `windows-unit-tests` passed on the PR (2m27s), and the
full suite locally is `Passed: 374, Failed: 0, Skipped: 12, Total: 386` - exactly the matrix row.

## What is still wrong, and it is now named instead of hidden
The open fails **cleanly** at `0x80004003: NullReferenceException` - a COM call returns `S_OK` with a null
out-interface, and `OpenCore` checks `hr < 0` but never checks the interface. Filed as **ledger 813**. The
suspects are named in it: GetAdapter, EnumOutputs and DuplicateOutput all have that shape.

## Merged
PR #76 -> `b0d8ae2`. Items 814 (the vtable fix) closed with proof; 813 open for the null interface.

Register now honest and static: **52 items, 0 open, 18 blocked, 34 done**. W-P3-01 says blocked on *code*, not
hardware; X-P6-04 says `blocked` rather than `open`. Nothing is startable by a shift until a blocker clears, which
is the truthful state rather than a queue of ghosts.

## Lessons
- **A recorded hardware blocker deserves one run.** "No attached output" was true of the process and false of the
 machine, and behind it sat a defect that would crash the capture path on any real desktop.
- **A COM interface declared out of order fails by succeeding.** The AccessViolation appeared in `GetDesc`; the
 cause was three methods earlier.
- **Scheduled tasks are the tool for session-bound proofs.** `schtasks /create ... /it` runs in the logged-on
 user's session; the task is deleted immediately after. It flashes a console window on the owner's desktop, which
 is a real cost and worth naming.
