## HANDOFF — round 4b: the vector backlog repair was itself broken, and is now running

**2026-09-28 ~17:20Z. Live `co/merged@78745c5d0`.**

### THE FINDING: the function that repairs the memory index could never run
The brain's semantic recall is dead for 21,283 of 21,886 memories (97.3 % have no vector). W8
shipped `reindex_missing_vectors()` to repair exactly that. It does not work in a fresh process:

```
reindex_missing_vectors("sqlite:///data/secretary.db", limit=50)
-> {"ok": false, "error": "no such module: vec0", "scanned": 0, "indexed": 0, "failed": 0}
```

while on the same box, same connection type: `_load_vec_extension(conn) -> True`,
`_probe_vec(conn) -> True`, `_check_vec(conn) -> True`.

**Cause — ordering, not absence.** Its own SELECT filters with
`NOT EXISTS (SELECT 1 FROM memory_vectors v WHERE v.memory_id = m.id)`, and `memory_vectors` is a
**vec0 virtual table**. The extension was only loaded later, *per row, inside the loop*, so the
first statement raised `no such module: vec0` and the function returned early having indexed
nothing. It only ever worked inside the long-lived API process, where some earlier call had already
loaded vec0 onto the same cached connection.

**Fixed (FU6, `78745c5d0`):** `_check_vec(conn)` is now called immediately after the connection is
obtained and before the first query, with a named reason when unavailable. Two regression tests pin
the ordering without needing a vec0-free process: with the extension unavailable the call must
return the *named* reason and the query must never run; with it available the query must run.
`tests/test_co_fu6_reindex_order.py` + `tests/test_co_w8_acceptance.py` → **31 passed**; broad gate
on the authority → **1129 passed, `GATED SHA 78745c5d0f6182c9fab8420b8338e42a796d9801`**.
