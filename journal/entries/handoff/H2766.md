**Exactly ONE active metered price and it is $18.00/GB.** My own first pass printed "*3 active metered prices - INVESTIGATE*" because my filter matched any price whose product name contained "waze" - **a base LICENSED price and an unrelated product are not metered prices, and computing "$/GB" on them is meaningless.** Worth keeping: **an automated verdict is only as good as its filter, and mine over-matched.**

**THE REAL LANDMINE, NOW FIXED AT SOURCE.** The creation script still carried `unit_amount: 1800`, so **a fresh run would have created another $18,000/GB price** - and I had written in the journal on 2026-09-23 that repairing the script was on me and was not done. It is now:
- `unit_amount_decimal: '1.8'` with the reasoning in the source (Stripe's `unit_amount` is an INTEGER of cents and **cannot express 1.8**; 18 there is $180/GB and 1800 is $18,000/GB, **both wrong values had to be archived by hand**),
- the two log lines that printed `unit_amount` (null for a decimal price) corrected to `unit_amount_decimal ?? unit_amount`,
- **and a new `assertEffectiveRate()` that RECOMPUTES dollars-per-GB from what Stripe actually stored and THROWS if it is not $18.00** - so a wrong unit can no longer be created quietly by this script.
**Verified by running it: `metered price: REUSED price_1UIhCBLnlgYj1gmTGzhuHpPX 1.8 usd active=true` then `verified: 1.8 cents/MB = $18.00/GB`.** Idempotent - it reused every object and created nothing.
