THE OUTAGE I CAUSED, and its cause is worth more than the fix: I appended `DEEPSEEK_API_KEY: <value>` to
~/.dsh/.credentials.yaml to satisfy verify's G4/G5. That file's keys must be "<scope>/<id>", so the engine's
credentials include threw `credential key "DEEPSEEK_API_KEY" must be "<scope>/<id>"` and systemd restarted it every
~60 s (17 restarts). The file was VALID YAML — which is why my "it parses OK" check cleared it, and why the
pipeline's credential reader (which searches for a nested key of that NAME) happily ran G4/G5 while the engine it was
judging could not boot. Two readers, two rules, one file. Restoring the backup brought it up at 03:41 with 401.
This node gets its model key from `EnvironmentFile=/etc/dsh-worker.env`, so it never needed a credentials entry.

LESSON FOR THE NEXT HOST: never edit a credential store to satisfy a gate. Read the schema the ENGINE enforces
(`<scope>/<id>` here), and if the key already arrives by EnvironmentFile, the gate's own credential expectation is
what should change — not the store.
