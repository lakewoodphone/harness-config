**Addendum 2 2026-09-16 00:45Z — the OOM leak has a fix applied; verification running.**

The API OOM-died a seventh time at **23:19:18** (pid 364647, "19.2G memory peak" over only **15 minutes**) while the
subagent was measuring it, which settled the diagnosis: sampling `/proc/<pid>/smaps` every 20 s caught RSS going
2.5 → 3.5 → **12.5 GB in 21 s** with a single **7.4 GB anonymous mapping**. That is a *burst*, not a leak.

**Applied (`44e3f8e8` on the authority, `app/database.py`):** `PRAGMA cache_size` 64 MB → **8 MB** per connection (60 DB
fds were open, so 64 MB each was a 3.8 GB floor) and `PRAGMA temp_store` MEMORY → **FILE** (the unbounded term: one big
ORDER BY/GROUP BY materialising in one allocation). Both env-overridable (`PS_SQLITE_CACHE_KB`, `PS_SQLITE_TEMP_STORE`)
so rollback is a restart with a variable, not a code change. Verified at runtime on a fresh connection:
`cache_size = -8000`, `temp_store = 1 (FILE)`. The service was restarted at 23:24Z and answered `/health` 200 about 40 s
later. **A 25-minute RSS sampler is watching it at `~/phone/oom-evidence/rss-after-fix.tsv`** (flags `GONE` if the process
disappears) — read it first, before believing the fix; the falsification test is "does RSS still reach ~19 GB with
temp_store=FILE", in which case the giant mapping is Python-level, not SQLite's.

**Subagent report (independent, arrives at the same primary cause):** `~/phone/api-oom-report-2026-09-15.md` (24 KB, every
claim marked OBSERVED vs INFERRED) and a patch `~/phone/api-oom-fix.patch` that is **superseded** by `44e3f8e8`. Its ranked
secondary causes are **not fixed and are the next session's work**:
1. **`/health` probe storm.** `py-spy dump` caught **35 of 36 threads parked in the `/health` DB probe**, all blocked on the
 connection-cache lock, because `asyncio.wait_for(run_in_threadpool(_db_check), timeout=2.0)` cannot cancel a thread
 already inside `run_in_threadpool` — so probe load *adds* threads and connections instead of being shed. Memoising that
 probe (a few seconds) is the cheapest next lever.
2. **Unbounded abandoned `wf-tick` workers.** `app/workforce.py:1417` builds a fresh `ThreadPoolExecutor` every company

3. **DSH-session ingest retries** (`/api/v1/owner/dsh-sessions/ingest`, `Cannot operate on a closed database` at 23:13:28)
