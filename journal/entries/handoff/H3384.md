CHANGED — THE PHOTOGRAPHS ARE IN PRODUCTION
- `repair_intake_case_photos` went from **1 row** (a staff test) to **4**: ids 17, 18 on case **1282**
 (Senzer / WO26100812736) and id 19 on case **1283** (Schreiber / WO26100812737). Objects sit at
 `repair-intake/<case-uuid>/<position>.jpg` in the app's R2, sha256 identical to the files committed
 in `lpt-hub/docs/customer-operations/case-media/2026-10-08-intake-notes/`.
- Both cases are `PROMOTED`/`SYNCED` with `promotedOrderId` = the order, which is the link
 `StaffOrderPhotosCard` walks (order number -> intake case -> photos), so the counter now sees the
 pictures on the work order. Each was fetched back through the app's own API: **HTTP 200** at
 863,867 / 637,739 / 650,654 bytes.
- **`lpt-photo`, a new command in lpt-ops** (`bin/lpt-photo`, `lpt_ops/photos.py`,
 `lpt_ops/app_scripts/intake_photos.mjs`, `docs/photos.md`, commit `2865c9e`). It drives the app's
 OWN services inside its own container — `RepairIntakeCaseService.createCaseIdempotent`,
 `RepairIntakeCasePhotoService.attachPhotos`, `WorkOrderService.updateWorkOrder` (writing
 `serviceDetails.repairIntakeCaseUuid`) and `promoteToWorkOrder`, which returned
 `orderAction: 'match'` and created **no second order**. No SQL of its own against a table the app
 owns. Dry run by default; sha256 proven both for the staged script and every staged photo;
 idempotent (a photo whose sha256 is already on the case is skipped).
- Nothing was deployed to the app: the code was ALREADY in the running image (revision
 `1e6a6ee8c234f40a2d9541d47c0f9b1cc70699f2`); the disk checkouts were behind it.

CHANGED — THE DIALPAD HALF
- Every `communications` row for both numbers carried `customerId NULL`, so nothing joined them to
 the customer: not the customer page, not the work order timeline, not the `lpt` case reader, which
 answered "0 communications for the customer". Now **Senzer 2803 -> 16 rows**, **Schreiber 2804 ->
 7 rows**; `lpt ticket WO26100812736` reads "16 for the customer".
- Cause, and it recurs: the sync stores a message with no customer when no customer exists yet (4,752
 rows are shaped that way) **and its getters only look back 7 days**, so a conversation older than
 the window is never revisited when the customer finally appears. Fixed at the source by a new
 `attach_communications_for_customer` in the app's own `website_db.py` (backup:
 `website_db.py.bak-comms-attach-20261008T190530Z`), which moves a row only FROM no-customer TO this
 customer and only on a matching ten-digit phone.
