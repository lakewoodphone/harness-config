## The card numbers are gone from every store we hold, and the security codes with them

Owner's approval, 2026-10-09: *"you can mask them but do so carefully not to destroy or mess up any
other data."*

### CHANGED

- **Masked, and verified at zero.** Every payment-card number in every store the company holds was
 replaced in place by `[card number removed]`; every card **security code** beside one was replaced
 by `[security code removed]`. Re-read afterwards: **0 rows matching a card pattern anywhere**.

 **Nothing was deleted.** Every message is still there; the digits inside it are not. Row counts

 `scan` counts, `plan` shows the exact changes with masked samples, `apply` does it. Committed

### THE DECISION THAT MADE IT SAFE

**It replaces by exact value, never by pattern.** The obvious implementation — an UPDATE with
`content ~ '[0-9]{16,19}'` — matched **6,087 of the 6,194 rows in
`dialpad_ui_message_body_row.raw_attrs_json` and 36,436 "occurrences"**, every one of them an id
inside a captured HTML blob. Six thousand customer messages would have been corrupted by the
straightforward version. So a message column is *scanned* for cards and a blob column is only ever
masked with the numbers found in the same row's message.

Three more rules, each with a test: fifteen digits is **not** a match (that is an IMEI); a run
preceded by `Dialpad`/`call_id`/`ticket`/`imei`/`stripe` is an identifier; and a bare three-digit
number is **never** touched, which is why the security-code rule is anchored to the literal word
`sec`/`cvv`/`cvc`/`security` rather than to a shape.

**The expiry is counted and left.** 136 messages in `operational` still show `02/28`-style dates.
An expiry is not sensitive authentication data, and its shape collides with ordinary dates — that is
the line between removing card data and damaging a customer's message.

### IN FLIGHT / NEXT

### EVIDENCE

- `lpt-redact scan` after the run → `rows: 0` for `operational`, `app` and the secretary mirrors.
- Independent re-reads (not the masking script's own): `select count(*) ... where content ~
 '[0-9]{16,19}' or content ~ 'dddd dddd dddd dddd'` → 0 in both Postgres stores; the same scan over
 SQLite → 0.
- The masking script's plan, per store, printed masked samples before each write; the SQL files
 carried only the *new* values, so no card number was ever written to a file.
