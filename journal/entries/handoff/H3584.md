Post-commit verification, specific rather than general: `agent_bus.py` carries the 15-minute Shabbat poll,

**THE MISTAKE, and it was mine.** To inspect the drift I ran `git checkout preserve/...` and then
`git checkout master`. **The second checkout reverted all 56 files in the working tree to master's
version.** The running process was unaffected (it holds its code in memory and had been up since 14:14),
and the work was safe on the branch - but the moment that service restarted, it would have loaded
master's code and **lost 6,160 lines of live behaviour**, and the untracked working tree that held the
only other copy would have been overwritten.

Caught it in the next verification command, by comparing the branch back against the working tree and
finding **0 of 59 files matching**. Restored immediately with
`git checkout preserve/uncommitted-20261012-unreviewed -- app/`, re-verified **59/59 matching**, and the
identity-store patch confirmed intact.

**The rule, and it is a sharp one.** *A `git checkout <branch>` over a dirty tree is a destructive
operation that reports success.* It is the `git reset --hard` hazard wearing a friendlier name: it does
not delete commits, so nothing warns you, but it overwrites uncommitted work in the working tree - and in
this case that work was **the only copy of the code production was running**. On a live tree, either
commit first or never switch branches in it. This belongs beside `L3622`-class hazards in the estate's
rules, because the estate's most expensive failures are the silent ones.

**Related, and worth stating because it changes what "done" means for this class of work:** a repository
is not a description of a system until it has been diffed against what is running. The same defect has
now appeared four times in one week at four scales - 599 gitignored tool bodies (`172`), 89 uncommitted
lines in `find-anything` (`L3743`), 72 migration artefacts in no git (this session), and 6,160 lines in
the production application (`P2940`). **The check is one command per host - `git status` on every repo
holding something running - and it should be routine rather than discovered by accident.**
