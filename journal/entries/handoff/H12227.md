**Full step log, evidence and revert paths: `personal-secretary-mvp/deploy/waze-mdm/docs/2026-10-22-dictionary-redownload-investigation.md`.** Read that first; this entry is the state and the next move.

### Proven (each with the command that produced it)
- The 2026-10-21 location work took the filter allowlist 51 → 89 names (`comm` of live container env vs `docker-compose.yml.bak-20261021T004033Z`: 38 added, 0 removed) and rewrote the PAC (8,246 B, mtime 00:46) so Apple CDNs that were blackholed are now `DIRECT`.
- The 38 added names are not all location: they include `iphone-ld.*`, `appldnld.*`, `updates.cdn-apple.com`, `updates.g.aaplimg.com`, `bag.itunes.apple.com`, `get-bx`, `cdn-h3`, `world-gen`.
- `doh_filter.py:186-195` checks **allow before block**, so `iphone-ld.apple.com` sat on the blocklist and still answered (551 log lines). Blocklist entries on allowlisted names do nothing; `PRE_ALLOWED_BLOCKED_DOMAINS` only covers `*.waze.com` and is derived at import.
- The dictionary download **requires network**: airplane mode on → spins, never completes (owner, DRN 2007).

### Not proven — do not restate as fact
- Which host serves the dictionary. `iphone-ld` and `updates.cdn-apple.com` were both blocked and the owner's retest still downloaded. Neither is confirmed; neither is cleared either, because every one of those tests ran with a warm resolver cache.
- Whether the fetch consults our resolver at all.

### The next action (one test, then the fix)
Cut the allowlist to the 42-name skeleton, **reboot 2007** (a reboot, not an airplane toggle — the toggle does not flush the resolver cache), tap one dictionary, then read `docker logs waze-mdm-dns-filter-1` **before** restoring or recreating. If it still downloads with every Apple name refused after a reboot, the resolver is not the gate: next tools are a PAC path rule (`FindProxyForURL` sees the full URL) and then a Network Extension content filter.

### Mistakes I made, recorded so they are not repeated
1. `docker compose up -d --force-recreate dns-filter` **deletes the container and its log**. I did it twice, and the second destroyed the exact tap window the owner had just produced. Dump the log to a file first.
2. Every DNS block was tested against a phone holding a warm cache and a live connection to the same CDN. Those "still downloading" answers were not measurements of the block. Cache-invalidating reboot or nothing.
3. Reported `iphone-ld` as "applied and verified" on a name list rather than on the owner's retest. Wrong, and it cost him three extra taps.
4. PowerShell here-strings arrive as CRLF and the remote bash fails on `head -N\r`; `docker exec -i` swallows the rest of a `bash -s` script.
