## Follow-up evidence: the $299 model on the authority includes the case; the owner's $285 model does not

Read on secratary-cloud, 2026-10-16, after `H6762`. This closes the loop on WHICH of the two pricing
documents the running system actually implements, and the answer is neither cleanly.

- `backend/src/services/waze/waze-checkout.service.ts:20` — the device line is documented as
 "a one-time payment (hardware + **rugged case** + cable + packaging)".
- `waze-checkout.service.ts:451` — the Stripe line item description reads
 "Kosher Waze phone in a rugged case, with charging cable and packaging."
- `waze-checkout.service.ts:692` — the checkout payload sets `ruggedCase: true` as part of the device.
- `env.config.ts:642` — `devicePriceCents` doc: "One-time: the device — hardware, **rugged case**, cable, packaging."
- **There is no case add-on line anywhere**: no `CASE_PRICE`, no `casePrice`, no second sellable line
 (grep over `backend/src/services/waze/*.ts` and `env.config.ts`, read-only).

So the live system implements the OLD model exactly: one all-in 299.00 that includes the case. The
owner's 2026-10-05 decision — 285 device-only with the case as a separate 20.00 add-on — exists only in
prose. Consequences if a counter sale is rung up in this system today:
 * the customer is charged 299.00, i.e. **14.00 more than the owner quotes**; and
 * the case is treated as included, so selling it as a 20.00 add-on has nowhere to go, and a customer
 who declines the case still pays for it.
Neither is live today only because `checkoutEnabled` is false (`purchasable:false`,
`unavailableReason:"checkout_disabled"`) — the product is sold in person at the counter.

**This is not a sign problem and it was not fixed by editing anything.** It is raised with the owner as
a single question with a recommendation. What is still needed is a decision, then a code change in
`phone-and-tech-full` (env defaults + the checkout line description + an actual case line item), which
is a separate, larger job than the sign.
