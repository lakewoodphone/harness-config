THE FINDING IS ABOUT MY OWN TEST, and it is the sharpest version of a lesson this run keeps meeting.
 I wrote the first test for /admin/reports/{report_id}/approve assuming a site report is a customer pleading for a site to be ALLOWED, so approval would add the domain to allow_domains. To be safe I asserted the domain appeared in EITHER list - allow or deny - and the test passed.
 Then I tightened it to allow_domains only, and it FAILED. Reading the handler: update_rule_for_scope(..., allow=False), status becomes "blocked". **Approving a report approves the block.** The union-of-two-lists assertion had looked careful and was worthless; it would have passed if the rule had been inverted, which is exactly the failure mode this whole run has been chasing in checkers.

 THE LESSON, sharper than last time: an assertion loose enough to accept either outcome is the thing that HIDES a misunderstanding, including the author's. The test now asserts deny + the exact status, and its docstring records the wrong assumption so the next person does not repeat it.
