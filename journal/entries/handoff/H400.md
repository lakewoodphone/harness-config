## 2026-09-16 19:17 UTC · ZABZ-YOGA · unified-search round 3 audit: machine load is not search, the registry was naming a file that never existed, batching fixed and measured

unified-search round 3: full audit, the registry fixed, batching fixed and measured, and the honest limits

Round 3 was an audit round. Two independent read-only audits were run (machine load; the search
system from the outside), plus a harness review. What follows is what they found and what changed.

## THE MACHINE IS NOT SLOW BECAUSE OF SEARCH — established with counters, not opinion
An independent audit measured, on ZABZ-YOGA at 17:22-17:45Z:
* search program's CPU share: **0.05 of a core, 0.2%**
* **129 MS Edge processes** holding 9.7 GB and ~37% of all CPU (a live 5 s delta: Edge 40.8 CPU-s,
 node 9.2, System 6.3, python 5.2 of which uvicorn 4.9, SearchIndexer 3.6, Defender 2.25)
* 24-25 concurrent agent loops and 15 tool-call runners on 22 logical cores
* Windows Search 2,540 CPU-s since boot; Defender 1,336
* **paging ruled out**: page writes/sec 0.0000, pages output 0, pagefile usage 2.9-3.5%, commit
 32.4 GB of a 43.1 GB limit, 10.7 GB headroom
So loop lag p95 of 4.8-6.5 s is **concurrency starvation, not memory and not the index**. Its real
cost was captured too: `list_agents` blew its 8 s deadline and served a **32-minute-old** listing.

## ONE WEDGED PROCESS OF MINE, FOUND BY THAT AUDIT
PID 18984 — my chat JSONL ingest — had been running **five and a half hours** with **zero CPU delta
and zero bytes of I/O across a 25-minute window**, holding a write lock on the 1.67 GB index. Every
other source's refresh failed behind it with `database is locked`, which I had misread as contention
from other sessions. Killed, along with two idle husks (34964, 36764).

Cause: `ingest_jsonl` committed **one document per transaction**. Measured in isolation:
 21 MB / 3,000 docs: per-document 71.5 s batched 16.1 s (4.4x)
 73 MB / 20,000 docs: per-document 379.2 s batched 149.1 s (2.5x, 134 docs/s)
Fixed: `batch` on the ingest path, `in_transaction` on `add_document`, and `--bulk` defaults the
batch to 2000. The tradeoff is in the code: a crash mid-batch loses that batch, which the adapter's
state file re-emits.

**The honest limit, measured after that fix:** re-ingesting the 2,418-document chat corpus (65.6 MB,
39,863 chunks already in the index) took **2,463 s = 41 minutes**. Batching did not fix that, because
the cost is not the commit — it is `add_document` issuing a DELETE for a document that already exists
before inserting it, and an FTS5 delete is expensive. 148 docs/s is the number any next change must
beat. The right fix is architectural rather than incremental: the adapters should emit only what
changed, and there should be a bulk path that skips the delete for documents that are new.

## THE REGISTRY WAS A LIE, AND THAT IS THE WORST THING THIS ROUND FOUND
Every one of the thirteen sources named **`adapters/<name>/adapter.py`** — a filename no adapter has
ever had, because they are all `sync.py`. So the refresh reported "adapter not found" for every
source and did nothing, while `sync.py --list` showed a correctly scheduled pipeline. A registry that
names a path nobody has run is worse than no registry: it is a claim of coverage.

Rewritten from each adapter's own `--help`. Seven sources are enabled (files:local, git:local,
chat:vscode, db:localdb, journal, comms:secratary, journal:secratary) and six carry `enabled: false`
with a note naming the real obstacle, so the gap is visible in `--list` instead of absent. Two
entries were not merely misspelled but wrong: `db:secretary` pointed at `adapters/localdb/sync.py`,
which does not read the server database at all, and `mail:gmail` is blocked by something upstream —
`email_catalog` has **0 rows**, so Gmail bodies were never fetched and there is nothing to index.

## STILL OPEN, ranked

 pre-delete for documents that do not exist yet.
2. **`usearch.py check` did not return within 120 s on the 1.67 GB index.** The integrity check is
 supposed to be runnable from a monitoring job; if it cannot finish it is not a check. Likely the
 `--sample` re-hash of 200 documents from disk, but that is inference and it needs measuring.
3. The files full-corpus pass is still incomplete (~26k of ~141k documents) and is resumable from
 its state file.
4. `db:secretary`, `db:prod-postgres`, `files:secratary`, `git:secratary` disabled pending the
 secretary adapter being moved into the repo checkout from `~/.usearch/secretary-repo/`.
5. Gmail: upstream connector work, not search work.
6. ~17 GB of superseded index (`index.db` 2.76 GB + its WAL) still on disk, awaiting the owner's
 explicit yes to delete.
7. SQLite below 3.53.2 on both hosts (CVE-2026-11822, P203).
