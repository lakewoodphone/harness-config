## 2026-09-16 16:38 UTC · ZABZ-YOGA · LPT website redo audited: every public surface read first-hand; the sign-in block is an allowlist, not the flag

**Found by auditing the LPT website redo, 2026-09-16. Every public LPT surface was read first-hand; nothing was
taken from a subagent report without reproduction.**

**The one finding no prior document had:** the customer sign-in is blocked by a five-line path allowlist, not by
the portal feature flag. `backend/src/trpc/context.ts:106-116` refuses a CUSTOMER token for any request path not
containing `customerPortal.` / `/customerPortal` / `customerAccount.` / `/customerAccount` / `auth.refresh`.
The portal's own sign-in calls are `auth.customerLogin`, `auth.requestCustomerLoginCode`,
`auth.verifyCustomerLoginCode`, `auth.registerWithPhone`, `auth.requestPasswordReset`, `auth.resetPassword`,
`auth.logout`, `auth.googleRefresh` (`CustomerAuthContext.tsx:96-111`) - **none match**. So even with the portal
flag on, no customer can log in, and none can log out. W4 filed only `auth.googleRefresh`; W2 filed only the
flag; neither connected it to the login path.

**Second: the Google button 404s regardless.** `CustomerPortalAccess.tsx:524` hardcodes the relative
`/api/auth/google/start`, which resolves to the apex host, and the apex 404s every `/api/*` path (verified live,
three times). The absolute `api.lakewoodphoneandtech.com/api/auth/google/start` answers 302 to Google.

**Third: the live homepage publishes a fabricated street address.** "123 Main Street ... Highway 99 ... blue
storefront" renders in the FAQ block beside the correct "1001 W Kennedy Blvd". `useFaqs.ts:72` calls
`faq.getPublished.query()` with no argument; the backend requires an object, so it 400s and the catch returns
`getMockFaqs()`. Verified: those three strings appear exactly once each in the live production bundle. One-line
fix. Same block also publishes unverified financing and service claims.

**Fourth: the seven SEO service pages are invisible to search.** `/`, `/screen-repair`, `/data-recovery`,
`/kosher-flip-phones` each return byte-identical 6,653-byte HTML with one `<title>` and
`canonical=https://lakewoodphoneandtech.com/`. Per-page SEO is applied at runtime in React; the build has no
SSR/SSG/prerender. `sitemap.xml` is 638 bytes listing three URLs, none of them the service pages. `robots.txt`
disallows `/faq` and `/contact`. `curl` returns a distinct title on none of them.

**Fifth: the computer-finder is dead at five independent points** (form cannot leave section 1 - 16
non-nullable backend fields vs null-initialised state; the allowlist; `conditionPreference` vs
`condition_preference` - the pre-existing table uses camelCase everywhere and the new migration added a
snake_case column; production has no `SECRETARY_COMPUTER_FORM_WEBHOOK_URL` so a saved row goes nowhere; and no
staff view reads the table). Net effect: **the Google Form is still the live intake and nothing processes it.**

**Sixth, correcting the master index:** its §8 conclusion that "the customer portal is shipped in production" is
wrong. The feature flag is read at runtime so both branches always ship in the bundle, and every SPA path returns
200 - both of its probes are invalid. Reproduced: `/this-page-does-not-exist-12345` -> 200. Portal is OFF in
prod; every `/customer-portal/*` URL lands on the homepage.

**Seventh, on deployment:** production's frontend was direct-uploaded from `44c99ea07`, an ancestor of
`origin/test` but NOT of `origin/main` (verified), and Cloudflare records it as `branch=main` because
`deploy-frontend-cloudflare.mjs:40-42` hardcodes the label and deploys with `--commit-dirty=true`. `origin/main`
is 102 commits behind and has never received a PR. The production BACKEND has no commit identity at all -
`/opt/lpt/src` is not a checkout and six security guards live only inside the image.
