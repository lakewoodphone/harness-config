session on any computer (ZABZ-TECH, ZABZ-YOGA, the Mac mini, the iPhone 15), searchable from one
place, one database, up to date within three hours, answers in a few seconds, long term and not a
one-off. Plan of record: `unified-search/docs/ESTATE-SEARCH-PROGRAM.md` (committed `d76d8a4`).

### What exists now, verified by command

 `127.0.0.1:3095`, `MemoryMax=600M`, `systemctl is-active` → `active`. `/health` and `/search` both

5. **ZABZ-TECH has a checkout and a running first build** (it had *no index at all*): cloned from a

### The five measurements that decided the design

| measurement | number | why it matters |
|---|---|---|
| session query joining `dsh_session_events` | **52 s** | 66k scattered 4 KB blobs out of 11 GB. FTS5 alone ranks the same matches in **0.15 s** |
| the same query reading the FTS's own columns | **68–234 ms** | `session_id`, `source_machine`, `ordinal` are UNINDEXED columns on the FTS table; the join bought nothing |
| `MAX(created_at)` in `/health` | **>30 s, hung the endpoint** | no index on it; the last row by rowid is the honest freshness reading |
| a scope the index does not hold (journal, before the fix) | **3,496 ms, no hits** | fell through to a full LIKE scan. A missing source must refuse in µs and name what the index holds |
| first query after a service restart | **3.4 s** vs **54 ms** warm | page cache, not the query; a boot warm-up now pays it |

### Two facts that change what the next session should do

- **`dsh_session_events_fts` is a CONTENTFUL FTS5 table**, so authority.db holds every event's text
 **twice** — `page_count` 8,054,139 ≈ 33 GB, of which ~10.9 GB is duplication. Recreating it as
 `content='dsh_session_events'` would free ~10 GB on a disk with 22 GB free, but it is a multi-hour
 rebuild of the live authoritative table: **owner-visible, not a side effect.**
- **The iPhone needs no adapter.** `phone-engine.service` runs on the authority with
 `DSH_HOME=/root/.dsh`, so phone sessions land in `authority.db` like any other. `config/hosts.json`
 records this, and records the frozen office box as `push:none` so nothing ever queries it again.

### What hurt

The registry was the whole bug, twice: `corpus-registry.json` and `sources.json` both named the
frozen box as the authority, and the refresh had been exiting 1 on every run while the schedule
looked correct. A schedule that runs and fails reads exactly like a schedule that runs.
