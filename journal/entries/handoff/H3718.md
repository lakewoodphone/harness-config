## 2026-10-20 19:04 UTC · ZABZ-TECH · round 26: freshness is falsified too - the defect is stale prose in a recently-written file, so the fix is discipline not detection

# H (2026-10-20, round 26) - the freshness rule is falsified too, and the reason is the one that matters

## Measured before building, as the last round's lesson demanded
Two candidate rules, run across every project that has a live state file (9 of them), joined to ledger counts:

| rule | fires on |
| --- | --- |
| "claims work and the ledger has no `todo`" | **4** - lpt-sync, cfo, personality-system, rental-system |
| "claims work, ledger has no `todo`, and the file is >48 h old" | **1** - personality-system (121.3 h) |

So freshness discriminates far better, as predicted. And then the file that carried the real defect killed it:
`kosher-ai-filter.json.bak-20261020T185715Z` has a **mtime age of 2.8 hours**, so the freshness rule does not fire on
it at all.

**The reason is the finding.** The file had been *rewritten recently* while its `remaining` **content** was eight days
stale - a shift copies the previous list forward without refreshing it. So file freshness is not claim freshness, and
neither mechanical signal can see claims that are merely old *text* inside a recently-touched file.

## What that leaves
No monitor over state-file contents is sound here. The defect is stale prose, not a stale count and not a stale mtime.
The two real fixes are:

- **the mechanism one** - stop a blob-driven source being able to file against a ledger verdict that proves nothing is
 startable. That is the owner's choice (a flagship that can never go quiet, versus a wasted shift) and it remains open;
- **the discipline one** - a shift must **rebuild** `remaining` from the ledger on every run instead of carrying the
 previous list forward. That belongs in the shift contract as a numbered step, not as a hope, and it is the fix that
 would actually have prevented tonight: the file would have been rewritten from the ledger and said "9 blocked".

## A useful side-observation
`kosher-ai-filter` now reads `todo=1 / non-terminal=10` - filing this item made the project startable again. So it went
quiet only between round 22 and now, which is exactly right: it had nothing startable and then it did. The loop's own
view has been consistent; the stale blob was the anomaly.

## Next
`personality-system` at 121.3 h with claims and no `todo` is the live example to examine - either its state file is
carrying forward a stale list (the same defect, found before it cost anything) or it has work the ledger has never been
told about. One read decides which.
