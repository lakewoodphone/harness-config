## HANDOFF — the platform seam, the iOS core finally compiling and passing, a signed Android artifact, and four workstreams integrated as PR #22

## CHANGED — `integrate/platform-customise-20261005` (PR **#22**), from `main` `635471e`

Four lanes, each verified before merge, plus the integration fixes they needed.

**1. A client platform is ONE module.** The requirement is that this must not be an Android-and-iOS
product. Adding a platform was four unrelated edits: a tuple in `routers/client_profiles.py`, an
`if platform == ...` chain, a pydantic `Literal` on `Hello.platform`, and **one hand-written Bloom
route per platform for a payload that router's own docstring calls platform-agnostic**. Now
`app/platforms/` auto-discovers providers; a new platform is one file calling `register()`. The three
Bloom **paths** are deliberately unchanged (generated from the registry with the same operation ids),
because the frozen inventory in `route_security.py` and the generated API reference both record them.
A test registers a platform that did not exist at import and shows the whole surface accept it — and
it caught a flaw in my own design, a frozen `SUPPORTED_PLATFORMS` left in the router that made a
late-registered platform 404.

**2. iOS: the core compiles and its 86 tests run — for the first time ever.** `Package.swift` always
claimed the core was host-agnostic; nobody had run it. Four compile fixes (two conflicting
`FilterDecision` declarations, one of them a fail-open stub; `URLRequest` without
`FoundationNetworking`; a shadowed `stride`; a Swift 6 argument-order error; Apple-only targets now
under `#if os(macOS) || os(iOS)`). Then **three real product bugs**, fixed:
- **a gated frame reset the cascade decision** — the stage-0 battery/thermal gates returned a hard
 `SKIP` while a verdict existed, so a page that had merely repainted was un-blurred;
- **the perceptual-hash fixture was degenerate** (a rising ramp is the all-zero case for a difference
 hash; the implementation matches `DroidDHashCache.kt` byte-for-byte, the fixture was wrong);
- **the DNS root name `.` could not be encoded** (RFC 1035 §3.1 wants one zero byte).
**86 tests, 0 failures**, with a deliberate break-and-restore proof. How it runs, and why not here, is
now in the repo: `ios/docs/running-the-core-tests-on-linux.md`.

**3. Android can ship.** The only artifact was an **unsigned** release APK. Now `app-release.apk`,
254 MB, **v2-signed**, `apksigner verify --print-certs` exit 0, `applicationId
com.lakewoodphoneandtech.filterai`, versionCode 1, 565 unit tests pass. It also closed a **silent
fallback**: `LPT_STRICT_RELEASE_SIGNING` defaulted false, so a plain `assembleRelease` quietly
produced `app-release-unsigned.apk`; strict is now the default and enforced in the task graph, and an
unresolvable keystore path counts as *no* signing config rather than as signing. Keystore:
`C:\Users\ezabz\.lpt-keys\lpt-release.jks`, outside the repo, passwords only in a gitignored file.

**4. The parent can see their own level.** The site could set it and not read it, and said so on the
page. `GET /owner/api/level` is the read half; four UI gaps fixed. **The biggest finding is a missing
concept, not a bug: there is no "person" in the data model** — scopes are tenant/community/household/
phone, so two children sharing one phone cannot have different settings. That is the single thing
standing between this and "customizable according to the person".

**Integration fixes.** Two assertions tested the environment rather than the behaviour: a literal
`broker_base_url`, and a two-character unanchored substring search for `"h1"` over a page containing
`<h1>` and a random CSRF token — which passed with the file alone and failed when
`tests/test_account_pages.py` ran first. Both now assert the property, and the leak check is proven
non-vacuous by injecting a real leak and watching it fail naming the value. `docs/API_REFERENCE.md`
and `docs/ARCHITECTURE_DIAGRAMS.md` regenerated in the same branch so the CI doc-diff stays clean.

## THE DEFENDER QUESTION, ANSWERED

The owner reported Windows Defender popups about Swift. It is **not Defender antivirus**: **Smart App
Control** is enforced (`VerifiedAndReputablePolicyState = 1`) and Code Integrity **blocks the Swift
driver launchers** from loading the unsigned `BlocksRuntime.dll`, so `swift.exe`, `swiftc.exe`,
`swift-test.exe` die instantly with **`0xC0E90002`** while the 165 MB `swift-frontend.exe` runs fine.
**Smart App Control has no exclusion list**, so no script and no UAC approval can fix it, and the
Defender path exclusions that already exist (`C:\Users\ezabz\code` among them) are why it looked like
it should work. I routed around it instead of asking for the machine to be weakened: the core's tests
are host-agnostic by design, so they run on the Linux host, which also **demonstrates** the
platform-independence the product needs.
