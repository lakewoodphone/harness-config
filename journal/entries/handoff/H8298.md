### The long-term claim now has a result behind it

A **scheduled** run of the laptop's refresh (not typed by me) completed:

```

```

That is the whole chain unattended — index, push, heartbeat, and an honest `PARTIAL` for a source that
indexed with two unreadable files.

### Fixed

1. **Both refresh tasks repeated every 2 hours, not hourly** (measured on both machines; the plan says
 60 minutes). Now `PT1H`, `Interactive` principal, `IgnoreNew` so a run cannot overlap itself.
2. **One unparseable line failed a whole delivery.** 1,551 documents delivered and one bad line among
 them marked the push failed and kept the spool — which would have re-sent it, and re-rejected that
 line, on every run forever. A rejected line is dropped and counted now; the push succeeded if
 anything was delivered.
3. **A quiet corpus was being called stale.** `chat:vscode` read 69 minutes old through an hourly sync
 that had run and had nothing new to send — with nothing to send it is never pushed, so neither its
 ingest row nor its newest document moves. A pushed corpus is now as fresh as the most recent of:
 its own ingest, its newest delivered document, and **the last push any host made**. A host that has
 genuinely stopped still shows, because per-host push state is reported separately.

### A latent defect noticed and NOT fixed, deliberately

`files:local` and `docs:local` share one adapter state file (`~/.usearch/state/files.json`), because
neither passes `--state`. Their roots are disjoint so the paths do not collide, but the `roots` field
does. Giving each its own state file is one line — and would trigger a full re-read of 250,000 files
on the next run, which is the two-hour walk that has already been interrupted three times. It is
written down here rather than done at the wrong moment.
