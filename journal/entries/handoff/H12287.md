### Scope grew, and the growth is the finding

Started this round to "add four missing methods to the Postgres backend". Measured before writing
anything:

```
Select-String alembic_scripts/versions/*.py -Pattern "household_e2ee_keys|e2ee_retention_deletions|e2ee_key_id"

```

**PostgreSQL has no E2EE schema at all** — not the two tables, not the four `screenshot_reviews`
columns. `server/migrations/030_e2ee_image_retention.sql` is the only place those objects are created,
and Postgres is built from Alembic, not from those `.sql` files. **This is the same defect class as
`inference_events` (ledger 1099, PR #107)**, which is now twice in two features: SQLite migrations are
written, Alembic mirrors are forgotten.

So 1097 is two halves, and adding methods without tables would have been a green parity audit over a
runtime that throws.

### Delivered: the schema half

New Alembic revision **`20261021_05`** (`down_revision 20261021_04`) mirrors migration 030 in raw SQL:
the four `ADD COLUMN IF NOT EXISTS` statements, the `e2ee_key_id` index, `household_e2ee_keys` with its
partial unique active-key index, and `e2ee_retention_deletions` with the proof columns.

Verified without a database: 24 revisions, **one head** (`20261021_05`), walking
`05 <- 04 <- 03 <- 02 <- 01` with no gap. This branch stacks independently of PR #107's `20261021_02a`;
once both land the chain stays linear.

### Still owed: the backend half

A `postgres_storage_sections/e2ee_retention.py` with the four functions against
`backend._execute` / `backend._fetchone` and `:named` parameters, the four names added to
`_POSTGRES_SECTION_DISPATCH` (which the installer `setattr`s onto the class), and the runtime actually
exercising them.

**Two mechanics already located, so the next round does not hunt for them:**

- **`INSERT ... RETURNING id` via `_fetchone`** is the established pattern for what SQLite does with
 `cur.lastrowid` — `activity_rollups.py:450` and `communications.py:158` both do it.
- **The four SQLite bodies to mirror** are `app/e2ee_image_retention.py:186-444`, and the pure
 validation (`normalize_key_envelope`, `envelope_fingerprint`, `_looks_like_plaintext_image`) is
 backend-agnostic and should be imported rather than reimplemented, so the crypto rules keep one
 source of truth.

### Traps paid for here

- **`git commit -m` with a `"` inside a PowerShell double-quoted string silently fails.** Round 11 lost
 a commit this way: the string ended at `relation "inference_events"`, git took the tail as pathspecs,
 the push then succeeded with an empty branch. Long messages go to a file and `git commit -F`, and
 check `git rev-list --count origin/main..HEAD` before pushing.
- **A migration file that looks valid Postgres is not evidence the object exists.** Only a revision
 that creates it is. Twice now.
