## NEXT ROUND: THE TAX FIX, SPECIFIED

**The rule is the owner's and it is written down:** a price a human sets is **pre-tax** and the
tax is added on top (`staff-order.pricing.ts:215-221` quotes him, 2026-10-08; `docs/decisions/work-orders-edit-pricing-mvp.md` §6.3, PRE_TAX default; `frontend/src/utils/pricing.ts:266`).

**The leak, by file:**
- `backend/src/services/work-orders/work-order.service.ts:2147-2149` and `:1597` —
 `updateData.total = input.total` with no tax. **This is the one to fix first.**
- `backend/src/services/ai-tools/work-order-update-status.tool.ts:428-436` — same shape.
- `~/lpt-ops/lpt_ops/write_helper.py` `cmd_total_set` — `UPDATE orders SET "total" = %s`, and
 `grep -i tax` over that file returns nothing. **A different repo, on the authority.**
- Nothing downstream adds tax: `pay-notice.service.ts:24-31` says so out loud, and Stripe's own
 line item for the paid order reads `unit_amount 200, amount_tax 0`.
- Meanwhile the counter/booking-in boxes treat the typed number as tax-INCLUDED
 (`StaffSaleChargePanel.tsx:179` `taxIncluded = true`, `repair-intake-case.service.ts:37-43`) —
 the opposite rule, which is why orders 3020 (149.00) and 3018 (75.00) have the tax BAKED IN
 (139.74 and 70.34 of pre-tax base).

**The shape of the fix, and why it is this one:** `orders.total` is DEFINED as tax-inclusive —
`pricing-summary.service.ts:603-604` computes `total = discountedSubtotal + taxAmount` and
`saved-final-total.service.ts:51-55` writes it. So a human's number must be interpreted as the
pre-tax base and taxed before it is stored. The mechanism already exists: write
`adjustmentAmount = preTax` and let `workOrderSavedFinalTotalService.syncFromPricingSummary` (already
called at `work-order.service.ts:1174` and `:1942`) produce the total. That keeps ONE tax
computation instead of adding a second one, which is exactly the drift `pricing-summary.service.ts:383-390`
warns about.

**Expect test churn, and read each one before changing it:** tests that assert
`updateById(1, { status: 'READY_FOR_PICKUP', completedDate, total })` are asserting the old
"store the typed number" contract. Changing them is the point of the fix, but each change must
say which model it now pins.

**Also on the list, lower priority:** the counter's `taxIncluded: true` default contradicts the
rule (D2 in the audit); the receipt infers tax by subtraction over `order_items`, which are empty
on every repair, so it prints the whole total as tax (`receipt.service.ts:83-85`); the rate is
re-hardcoded as `6.625` in four places instead of `getTaxRatePercent`.
