## 2026-10-26 02:55 UTC · ZABZ-YOGA · Policy refusals are no longer booked as failures - 6.1 shipped and verified, and its published diagnosis was wrong

Continued `HANDOFF-TO-NEXT-AGENT.md` §6.1 (the keystone) on 2026-10-26 02:39–03:15Z, ZABZ-YOGA → secratary-cloud. It is implemented and verified. **Three of the claims published in that handoff are false, and I measured all three before touching the code** — do not carry them forward.

## The diagnosis was wrong, and here is the measurement

1. **A policy refusal never called `autonomy.record_failure` — before my change.** Probe against the deployed code: `_dispatch_action` with `should_execute` forced to L2 → `record_failure` calls **0**. Mechanically it is stronger than that: at L4 **and** L3 the gate returns `execute=True`, so the `L4→L3` (02:20:38) and `L3→L2` (02:20:45) demotions *cannot* have come from a refusal — no refusal exists at those levels.
2. So §6.1's "its permission is walked L4→L2 for obeying the rule" and `OWNER-QUESTIONS` Q8b are **false**. `repo_read_file` was demoted by ten **genuine execution failures**. The refusal is a *downstream symptom* of that erosion, not its cause. The cause was invisible because the failure detail was never logged; it is now (`Autonomy: recorded a real execution failure for <action>: <detail>`).
3. **"A duplicate approval task is queued on every attempt" is also false as written.** `database.create_task` already dedupes by fuzzy title (80%, agent-agnostic) and returned one id — 30090, created **2026-10-23** — for three days of refusals. The real defect was the *opposite*: that key ignores the resource, so two different repo paths collapse onto one approval and the owner would approve one path believing he approved the other.

## What was true, and is now fixed

Four files in `/opt/company`, every one deployed by atomic rename (new inode, `py_compile`ed, backups `*.bak-refusal-20261026T024918Z` and `*.bak-refusal2/3-*`):

1. `app/chat_action_runtime.py` — the refusal branch now sets `data["policy_refused"]=True` (+level, reason, task id, dedupe key) and logs `POLICY_REFUSED action=… key=…`; added `_is_policy_refusal()` and `_policy_refusal_key(action, agent, params)`; `execute_actions()` **breaks** instead of retrying a refusal; the circuit breaker no longer counts one; every real failure now logs the reason it was recorded.
2. `app/chat_action_notifications.py` — `_create_approval_task(..., dedupe_key=)`; `dedup_threshold=0 if dedupe_key else 80` because the fuzzy match silently won and stole the exact key; a non-positive id from `create_task` (`-1` = ceiling) returns **None** instead of printing "approval task -1".
3. `app/chat_action_policy.py` — deterministic denials carry `policy_refused=True` and their own per-resource key.
4. `app/services/agent_worker.py` — `_execute_tool_dispatch` returns a third element (the refusal's approval task id); `_execute_tool_with_autonomy` does **not** call `_note_tool_failure` for a refusal — the test is `is not None`, because `""` means "refused and no task could be written", which is still a refusal — and returns the id so the step suspends as `approval_pending` instead of dying.

## Evidence, all read in this session

- **Live, in the running process (3790104):** three `POST /api/v1/actions/execute` of `repo_map` (L0_SHADOW) → exactly **1** `POLICY_REFUSED` per request, **0** `Action … failed (attempt`, **0** `recorded a real execution failure`, **0** `tool-loop deadlock`, **0** `Autonomy DEMOTED`. Same resource twice → same task (30679). Different resource → a different key (`fbc4a9374fce` vs `bd25895f5bf8`) and, because the ceiling is full, no task at all (not `-1`).
- **Worker, 5 consecutive refusals** of `managed_workflow_report` → `_note_tool_failure` called **0** times, strikes **0**, `deadlock_open` **0** against limit **3** → the step no longer stops. **Contrast:** a genuine failure (`repo_read_file` on a nonexistent path) still counts **1** strike, so failure detection was not blunted.
- **Regression:** `system_health` through the same endpoint → `ok=True, success=True`.

## Two new findings, measured, deliberately NOT fixed

**A. The company is at its task ceiling and can file nothing.** `active_task_ceiling()=300`, `count_active_tasks_for_capacity()=300` → `create_task` returns `-1` for **every** new task: work orders, findings, approvals. **106 approval tasks are open.** This is why my third test request could not record an approval.

**B. 24 of 75 `autonomy_levels` rows sit below L3, none of them in `CURATED_MATRIX`, and `_cleanup_stale_overrides()` only walks `CURATED_MATRIX`.** A demoted non-curated action can never succeed (it is refused) and therefore can never be re-promoted: `get_current_datetime` L2, `ask_owner` **L0** (the company's own channel to the owner is in shadow mode), `repo_map` L0, `gmail_accounts` L2, `dialpad_pull_sms` L2, `ledger_status` L2, `task_hygiene` L2, `lpt_hub_sync_cases` L2. Six of the 24 have `last_demoted_at=NULL`, so they came from another path and carry no demotion evidence.
Not changed on purpose: restoring authority to 22 actions is a **grant**, not a repair, and one of them is how the company asks the owner anything. Proposed fix — evidence-gated, mirroring the `COOLDOWN_RESTORE_SECONDS` recovery that already exists in memory: in `get_level`'s DB branch restore to matrix default only when `current_level < default` **and** `last_demoted_at` is older than the cooldown; leave NULL-timestamp rows gated and report them.
