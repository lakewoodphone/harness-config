## 2026-10-08 03:51 UTC · ZABZ-YOGA · Stripe audit: 127 of 129 settled charges have no order attached - but the board's own payment state is mostly right, and my first two readings of this were wrong

CHANGED — the Stripe audit, and two corrections to my own claims

**What I built.** `lpt-stripe-audit` (a read-only tool; source staged at `/tmp/lpt-stripe-audit.py`,
output saved to `~/lpt-ops/audit/stripe-unlinked-20261008.txt`). It reads the processor's own succeeded
charges for a window and classifies every one against the shop's `payment_transactions`, then looks for
candidate orders. It never writes; it prints the exact command that would settle a row.

**The measured picture, 60 days:** 129 succeeded charges totalling **13,811.53**. Only **2** are linked
to an order. **47** sit on a local row that names no order. **80** have no local row at all.

**I CORRECTED MYSELF TWICE, and both corrections matter more than the finding.**

1. **"127 charges are money the board cannot see" was wrong.** My first version joined on
 `stripeChargeId` alone — and a terminal payment's local row carries `stripePaymentIntentId` and
 leaves the charge id NULL, so every one of them looked invisible. The join key was wrong, not the
 data.
2. **"We are chasing paid customers at scale" was also wrong.** My candidate matcher attributed charges
 to orders by amount and produced one customer — Mrs Birnbaum — as having paid **six times** for a
 single 75 order. The matcher's own docstring promised a date window and the code never implemented
 one. Fixed, and then made to require INDEPENDENT corroboration, not just an amount.

**And the honest conclusion after the fixes:** a terminal charge carries real corroboration — its
description is the customer's NAME ("kruger", "levi", "niasof", "e4610 charging port taplin"), plus
`metadata.staffNote` and a cardholder name. When the audit requires that corroboration, **zero orders
read unpaid with a settled charge behind them.** Most of those 127 charges belong to orders the board
already shows as CAPTURED, or to sales and subscriptions that are not repairs at all.

So the real defect is narrower than I first said: **the LINK is missing, the STATE is mostly right.**
`payment_transactions` rows exist but name no order, and 80 charges have no row — so the *collection*
figure on the website (which sums SUCCEEDED rows) is largely meaningless, while `orders.paymentStatus`
(what the counter looks at) is usually correct. Anyone reporting on collected money from that table is
reporting a fraction.

**Two bugs in my own tool, both the same class and both worth remembering:** it swallowed a failing SQL
call and reported the empty result as data ("129 invisible"), and it documented a date filter it never
implemented. A derived number that cannot distinguish "nothing found" from "the query failed" will
confidently report the wrong world — the same failure as the mesh probe reading healthy, and the same
as the comms row count standing in for contact.

BROKEN / OPEN
1. `payment_transactions` does not link to orders for terminal payments — 47 rows are unlinked, 80
 charges have no row. The website's payment flow is where that belongs.
2. The audit's attribution is only as good as the description; where a charge has no name and no staff
 note, nothing can be attributed, and it must not be guessed.
3. `~/lpt-ops/audit/stripe-unlinked-20261008.txt` is the raw run.

NEXT

 is the one-line fix that makes collected money real.
2. Re-run the audit with corroboration required (the current version) before trusting any attribution.
3. Everything else from the board walk stands as recorded in H3330.
