## HOW I DID IT — by reading, not by re-deriving

**I deliberately did NOT re-implement the held rule in the shell script.** The verifier already decides
which records are held and why; a second implementation in shell would be the same mistake that made
C11 emit 40 false errors — a proxy for another program's logic outranking that program. So the reporter
**reads** the verifier's published `records_held_total` instead of guessing it, and there is exactly one
implementation of the rule.

## THE BUG I WROTE AND CAUGHT

`bash -n` failed with `syntax error near unexpected token '(' at line 180` — pointing at a Python line
that was obviously fine. The real cause was **line 178, two lines earlier**: my comment said *"the
verifier's own number"*, and **the apostrophe closed the single-quoted bash string** that wraps the
entire embedded Python block. Everything after it was evaluated as shell, so the error surfaced at the
next line rather than at the apostrophe.

Fixed, and the trap is now documented **inside** the block: *"NO APOSTROPHE ANYWHERE IN THIS BLOCK."*
I also scanned every embedded-Python block in the file for the same hazard; the rest are balanced.

**What caught it:** `bash -n` against a **test path** (`/tmp/da.sh`), never straight onto the live
script. That is the same discipline that would have caught round 9's overwritten sync tool, where I had
mistakenly trusted `ast.parse`.
