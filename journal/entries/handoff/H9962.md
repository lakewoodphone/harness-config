WHAT I GOT WRONG, IN TWO PLACES, AND THE DAMAGE:
 docs/ARCHITECTURE_DIAGRAMS.md said `generated-by: unrecorded`. In round 2 I read that as "nothing produces it", changed its status to live, and DELETED its snapshot table as a duplicate of the facts register - while server/scripts/generate_architecture_diagrams.py sat there writing exactly that table, the router inventory and the package roots. I destroyed generated content with an argument about ownership.
 docs/API_REFERENCE.md had the same front-matter, so I WROTE A NEW GENERATOR for it: 250 lines duplicating server/scripts/generate_api_reference.py, which DEVELOPMENT.md documents. Worse, the two disagreed - the schema exposes 333 paths / 357 operations, the application object serves 337 / 365 - so the estate briefly had two programs producing one document with different numbers in it. That is precisely the duplicate-implementation defect the handoff's second test names, and I introduced it while fixing a citation.

THE ROOT ERROR was procedural, not technical: `generated-by: unrecorded` is a claim that NOTHING writes this document, and I treated it as evidence instead of as a statement to check. Twenty seconds of `grep -r "ARCHITECTURE_DIAGRAMS" server/scripts/` would have ended it.

REPAIR: both documents belong to their pre-existing generators again; mine is deleted; both generators emit their own front-matter (no `updated:`, because a generated doc is checked by re-running its writer and comparing bytes); the API generator defers its app imports into main() so its generated-by command runs from any cwd, which check_generated_docs requires. The 337/365 facts are retired and replaced by server-openapi-paths/server-openapi-operations = 333/357, computed from the same schema the documents render from. Neither number was ever wrong - only misnamed: one is what a client discovers, the other is what the app serves.

NEW MECHANISM, aimed exactly at the mistake: PROVENANCE-UNOWNED - a document that a script in this repo writes, whose status is not `generated`. It found 3 real ones immediately, including the dead-citation register, which scan_dead_citations.py --write produces while declaring status: live (now generated). First version of the rule reported 26 because it counted a path LISTED in an index as a path WRITTEN by a generator; it now requires a write marker within a few lines of the path, and a document a checker merely names declares `provenance-reviewed:` with the reason.

LESSON WORTH KEEPING: "the front-matter says nobody generates this" is a claim, not evidence. Search for a writer by the document's own filename before concluding, and never delete generated content on the strength of a missing attribution - restore the attribution instead.
