## 2026-10-15 17:12 UTC · ZABZ-TECH · Ullman WO26101312747: the BitLocker key is captured, PROVEN (two tools, two reads, fingerprint 79bc71baee75802b) and stored in three places incl. authority.db credentials 0->1; the store finally has a reader

The owner ran `Get-BitLockerKeyProof` on the Ullman laptop from the shop stick and brought it back. **The recovery password is captured, proven, and stored in three places — none of them removable media alone.**

## The proof

**Two independent tools read the same protector and agree byte for byte.**

| read | fingerprint |
|---|---|
| proof script JSON record | `79bc71baee75802b` |
| proof script readable file | `79bc71baee75802b` |
| the 2026-10-15 state capture's INTERNAL file | `79bc71baee75802b` |

48 digits, 8 groups of 6, shape check passing. The protector id the key came from is `{341D1FAC-0FA0-4C05-BD02-61904A525961}` — the same one the collector saw, and the UUID and serial match the machine.

**The verification habit that mattered:** my first pass compared the three fingerprints and printed `True` for all of them — but the comparison function had thrown (`New-Object System.IO.MemoryStream (bytes)` is parsed as N arguments), so `null -eq null` was `True`. **A comparison that "passes" because both sides failed is not a comparison.** Redone with `[System.IO.MemoryStream]::new()`, it genuinely passes.

The stored value's fingerprint was read **back out of the database** and matches the file.

## The store now has a reader

`/root/bin/lpt-cred` on the authority — `list`, `find <term>`, `get <service>`, `show <service>`. Fingerprints by default, the value only on `show`. `find PF3F2810` and `find WO26101312747` both return the row.

This is the half that was missing all along: a credentials table with 0 rows and no reader is **worse than a file**, because a write into it feels like having recorded something. It is no longer that.

## Three defects the first live run exposed — all fixed, commit 04e4a3c28

1. **Ownership gave a false `INCONCLUSIVE` on a correct id.** `manage-bde` prints the protector id braced and upper-case; `Get-BitLockerVolume`'s `KeyProtectorId` is not guaranteed to be either, and a raw string compare failed. Ids are normalised now, and a type-only match reports as a distinct PARTIAL rather than a failure.
2. **The fingerprint came out blank** — `New-Object System.IO.MemoryStream (bytes)` is parsed as N arguments.
3. **The JSON record carried a UTF-8 BOM.** Windows PowerShell 5.1's `-Encoding UTF8` writes one, and ingesting the record threw `Unexpected UTF-8 BOM (decode using utf-8-sig)`. Now written with `UTF8Encoding($false)`. **This is the same 5.1-encoding trap the LPT-Access kit documents in its own README** — it is worth remembering that "UTF8" means two different things in 5.1 and 7.

Also: **exit 4 is now reserved for a failed shape check or a failed read-back.** An inconclusive ownership check is a warning. The first live run exited 4 on a perfectly good key, and a false 4 sends someone away from the only way into a drive.

## The decision it serves

**50 for diagnostics, no board repair, a route to the data.** `orders.total` = 53.31 (50 + 3.31 tax) against 53.31 collected, so the order reconciles. The key is why that is now a real deliverable rather than a hope: the customer's data is recoverable whether or not that board ever boots again.

Open, and it is the honest caveat: **rotation**. The key is now in a session archive as well as the stores (see the pain entry filed alongside). The value remains a live unlock key for a customer's 512 GB volume, so whether to rotate it is a real decision with a real cost — rotating means the stored copy goes stale until it is re-captured.
