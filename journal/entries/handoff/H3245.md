## HANDOFF — where the product stands, and the three things that are actually left

Written because this session has run long enough that a fresh session is cheaper than continuing in
it. Everything below is verified; nothing below is inferred. `main` = `1175287`, and **production
matches it**.

## WHAT IS DONE AND LIVE

**The platform seam.** Adding a client platform used to be four unrelated edits. It is now one module
under `server/app/platforms/`; a platform is a file that calls `register()`, and its profile, its
Bloom route, its name in the served set and its acceptance in `Hello.platform` all follow. Proven by a
test that registers a platform which did not exist at import time. The three Bloom **paths are
deliberately unchanged** — the frozen route inventory and the generated API reference record them.

**iOS: the core compiles and its 86 tests pass.** `Package.swift` always claimed the tests "run on any
host"; nobody had run them. Four compile fixes and three real product bugs (a gated frame resetting
the cascade decision instead of holding it, a degenerate perceptual-hash fixture, an unencodable DNS
root name). The Apple-only targets are now under `#if os(macOS) || os(iOS)`, so the portability claim
is enforced. How to run it, and why not on this laptop (Windows Smart App Control blocks the Swift
driver and has no exclusion list), is in `ios/docs/running-the-core-tests-on-linux.md`.

**Android: a v2-signed release artifact exists**, `apksigner` verified, and a **silent unsigned
fallback** was closed (a plain release build used to emit an unsigned APK). 565 unit tests pass.

**Latency, measured.** The decision itself was 0.7 % of the request; the cost was three fsyncs per
decision, now two. My own numbers: laptop p50 11.47 → 10.88 ms, p95 17.85 → 13.32; **production box
p50 10.04 ms**. Inside the product's own budget (<50 ms rule path). A further ~3.5 ms is available by
relaxing SQLite durability — **decided against, recorded in `D2938`** with the arithmetic.

**The person concept, and its enforcement.** The scoping model stopped at the phone, so two children
on one tablet could not differ. There is now a person: tables, a rules layer shaped like the existing
four, nine owner routes, and `base → tenant → household → phone → PERSON → community floor`. The
delegated branch passed 17 tests and **filtered nothing** — the composer every SOCKS decision goes
through did not consult the person layer. Fixed, and proven by break-and-restore: removing the step
fails exactly the tests that depend on it and nothing else. **Live**: 65 tables, 330 routes,
`/owner/api/people` answers 401.

**Boot fragility.** The second broker instance failed its first boot on two separate deploys with
`Integrity anchor chain verification failed at startup: access_requests, decisions`, and Docker's
restart policy absorbed it invisibly. The guard now re-reads the anchor file and re-verifies (4
attempts, ~1.5 s apart) before failing closed; a mismatch that persists still refuses to boot, which
is asserted. Merged and CI-verified.

**The blocklist was two-thirds loaded.** One of two default URLs was a jsDelivr URL the CDN refuses on
size (403, 150 MB limit). Fixed: **474,178 → 646,700 domains**, verified on production.

## THE THREE THINGS THAT ARE ACTUALLY LEFT

1. **A real device, for both platforms.** This is now the gating item for the objective's "100 %
 working on Android and iOS" and it cannot be done from here. Specifically: install the signed APK
 on a phone and watch a decision; and on iOS obtain a Mac plus a developer account for signing,
 entitlements, the Network Extension and `NEURLFilterManager` — whose `setConfiguration(pirServerURL:)`
 is **non-optional**, so a PIR server is needed before the iOS URL filter can run at all. The person
 layer, the platform seam and the latency numbers are all proven by tests and loopback measurement
 and **none of them has been observed on a device**.
2. **The CI wall** (`P2856`). Jobs that cross ~15 minutes come back `cancelled` with **zero steps
 recorded**; `server-tests` at 14m10s passes, `build-image` and `postgres-runtime-tests` at 15m0x do
 not. **No workflow declares `timeout-minutes`.** The plausible cause is Actions minutes on a
 user-owned private repo, but the billing endpoint answers 404 with this token, so **it is not
 verifiable from here** — that is the owner's to look at, and it may explain the whole thing in one
 glance. The code-side fix regardless: shard the suite or cache the image so no job sits on the line.
 **Until it is fixed, read `conclusion` from the API — never the word "fail" from `gh pr checks`.**
3. **Two-instances-one-SQLite-file.** The same root as the anchor race, the 3,322 `database is locked`
 events in 7 days, and the intermittent boot failure. Worth the owner's attention as an architecture
 question; every symptom traced back to it today.
