## 2026-10-11 13:40Z · THE TAILNET JOIN IS DONE; WHAT IT DID AND DID NOT BUY

The owner supplied a `tskey-api-` key. That is a **full-scope TAILSCALE API key**, not an auth key -
`tailscale up` refuses it (`key cannot be used for node auth`), but it authenticates the API, so the
auth key was MINTED from it rather than asked for again:

```
POST /api/v2/tailnet/-/keys {"capabilities":{"devices":{"create":{"reusable":true,
 "ephemeral":false,"preauthorized":true}}}}
-> key kAii8m4D9e11CNTRL (tskey-auth-...), expires 2027-01-09
```

First attempt was refused `400 keys: description had invalid characters` - the description contained
the characters my own text had, so the second attempt used an alphanumeric-only description. Worth
knowing: the API rejects punctuation in that field.

## WHAT IT DID NOT BUY, AND WHY - MEASURED, NOT GUESSED

1. **The node gates answer HTTP 403 with the body `Not signed in`.** `tailscale serve` on each node
 fronts its own HTTP surface, and that surface is behind **Cloudflare Access** - so an unattended
 host gets a login page, not a capacity reading. The Tailscale ACL is `{"src":["*"],"dst":["*"],
 "ip":["*"]}` (read through the API), so this is NOT a tailnet permission problem and no ACL edit
 fixes it. The placement broker reads `/mesh/capacity` on exactly those URLs, which is why
 `install-authority-cloud.sh` correctly REFUSED to leave the broker enabled there (`SUMMARY ok=0`,
 all five nodes `unreachable`) - the self-refusal I built into that installer earned its keep on its
 first real run. **The broker stays on the office box**, where it works and has a proven dispatch.
 Moving it needs those node surfaces to answer an unauthenticated or service-token request.
2. **The archive pull still cannot reach the other machines, and the reason is NOT the network now.**
 Measured per machine: `zabz-tech` has the archive client (I installed it at
 `C:\Users\ezabz\code\harness-config\scripts\archive-transcripts.py`, and it answers `--list --json`
 correctly), and I added the authority's public key to that machine's `authorized_keys` (10 keys
 now, previous file kept as a backup). The authority's ssh to it still ends in
 `Permission denied (publickey,password,keyboard-interactive)`. **The likely cause, and the next
 step:** on Windows OpenSSH an administrative account prefers
 `C:\ProgramData\ssh\administrators_authorized_keys`, which has its own ACL requirement, so a key
 appended to a user's own file is ignored for admin users. `zabz-yoga` and `zabz-tech-linux` have
 not had the client placed at all yet; `lakewooechsmini` does not answer ssh (it is asleep).
3. The `desktop-ts` alias does not exist in the authority's `~/.ssh/config` (only `zabz-tech` etc.),
 so any script keyed on that alias fails there with a name-resolution error. Worth aligning.
