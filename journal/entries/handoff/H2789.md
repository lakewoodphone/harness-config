## 2026-09-28 17:09 UTC · ZABZ-YOGA · Contention root cause fixed and measured: unbounded _db_lock acquire leaked threadpool workers; probe timeouts 32% -> 0

ROOT CAUSE (proven, not inferred)
 app/database.py `_get_conn` took the process-global `_db_lock` with a bounded wait and then
 an UNBOUNDED one: `_db_lock.acquire()` with no timeout, under a comment one line above saying
 "don't hang forever". The same function also ran `conn.execute("SELECT 1")` and `conn.close()`
 inside that lock under a comment saying "(no lock held for this)". Two comments describing the
 intended design; code doing the opposite of both. 197 `with _db_lock:` sites wrap real SQL,
 including five full-table COUNT(*) aggregates in `db_stats` on a 12.17 GB database.

 `/health` ran its DB probe in `run_in_threadpool` under `asyncio.wait_for(timeout=2.0)`.
 `wait_for` cannot cancel a threadpool task, so every timeout reported the database as down AND
 parked a worker on that unbounded acquire for the life of the process. Leaked workers consume
 starlette's finite threadpool tokens; once spent, the app is bound to its port and answering
 nothing -- the observed 5-minute outage.

 PROOF IT WAS NEVER SQLITE: sampler over the same file, read_ms p50 0.2 / max 1.0, while 32% of
 /health DB probes failed. Across hours: hour 16 had 27 probe timeouts and 0 real
 `database is locked` errors; hour 03 had 15 and 147. The symptom does not track SQLite locking.

CORRECTION TO MY OWN EARLIER CLAIM (important)
 I first said "a busy database is being treated as a dead service, and the watchdog is restarting
 a healthy API". An audit REFUTED that: the watchdog runs `curl -fsS`, which reads only the status
 LINE, and both of /health's degradation branches return HTTP 200. `{"ok": false}` was never
 visible to the watchdog. The 16:31:09 restart was CORRECT -- the service served zero requests
 from 16:27 to 16:36. My proposed "make busy report healthy" change would have fixed nothing.

CHANGED (scripts/contention-fix-2026-09-28.py; backups *.contentionfix-20260928-170737)
 1. database.py: bound the second acquire -> raises sqlite3.OperationalError after
 PS_DB_LOCK_WAIT_S (5 s) instead of blocking forever. Removes the permanent worker leak.
 2. database.py: db_stats' five full-table COUNT(*) aggregates moved out of `_db_lock`.
 3. database.py: PS_SQLITE_MMAP_MB knob, DEFAULT 0 (off) -- this box was at 100% disk today and
 its own history records an mmap SIGBUS when the disk filled (2026-09-10).
 4. main.py: the /health DB probe uses its own short-lived read-only connection, not `_get_conn`,
 so it cannot be blocked by the lock it was inspecting. Budget 2 s -> 10 s, matching the
 connection busy_timeout.
 5. main.py: `/livez` -- liveness touching nothing (no DB, no lock). Needed because `/ping`,
 `/livez`, `/readyz`, `/healthz` all 404'd and only `/health` did real work.
 6. agent_bus.py: `reminder_check` gets max_instances=1, coalesce=True (it logged "maximum number
 of running instances reached (1)" 5 times today).
 systemd drop-in /etc/systemd/system/secretary-api.service.d/30-contention.conf:
 StartLimitIntervalSec 0 -> 900 and StartLimitBurst 5 -> 3 (there was NO rate limit at all, and
 12 different actors restarted this unit today: 5 watchdog + 7 human/agent);
 MemoryHigh 5G -> 7G (the cgroup was pinned at its throttle ceiling -- 8 of 15 instances today
 peaked at exactly 5G) with MemoryMax left at 8G;
 TimeoutStopSec 300 -> 180 (measured clean stops are 0-133 s; the three hangs each burned 300 s
 = 900 s of the day's 1674 s of downtime). NOT 60 s, which would SIGKILL clean stops.
