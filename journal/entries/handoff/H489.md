## 2026-09-17 16:40 UTC · zabz-tech · Round 9: I overwrote the live production sync tool (fixed, L1925) and landed hub-root validation - the two lineages remain unreconciled

# H489 — round 9: I broke the live production sync tool and fixed it. Also: the root validation landed.

## THE INCIDENT — mine, in this round

While adding two validation functions to `scripts/lpt-sync-to-production.py`, I read **my local copy**
on ZABZ-TECH, edited it, and deployed it to the authority with `base64 -d > path`. It reported
`deployed` and passed `ast.parse`. I found the damage only by running the tool for another reason:

```
lpt-sync-to-production.py: error: unrecognized arguments: --dry-run-all
```

**The authority's live tool was 89,945 bytes. My local copy was 28,797. I overwrote a 90 KB production
tool with a 33 KB one, silently removing `--dry-run-all`, the pre-create guard, and
`_GUARD_REFUSING_KINDS`.**

### The compound error, and why it is worse than a slip

1. **I already knew about this exact divergence and still walked into it.** This session had
 established — and I had journaled as a headline finding — that `master` on ZABZ-TECH carries the
 28,797-byte version while the authority carries the 89,945-byte one, with
 `git merge-base --is-ancestor 858ce073 HEAD` exiting 1 in **both** directions. I wrote the warning
 and then edited the file without asking which version I was editing.
2. **`base64 -d > path` deploys whatever you give it, with no check of any kind** — no size, no
 content, no "is the target newer". Every deploy this session used that pattern; it was harmless
 only because the files happened to be the right ones.
3. **`ast.parse` proves a file is parseable, not that it is the file.** A 28 KB skeleton of a 90 KB
 program parses perfectly. I used it as a content gate **twice in one call** and reported success
 both times. The check that catches this is running the tool — `--help | grep --dry-run-all`, one
 second — and it would have failed immediately.

### What saved it

**Git on the authority held the correct file**: `git show HEAD:scripts/lpt-sync-to-production.py` →
89,081 bytes, `--dry-run-all` present (5 occurrences), guard intact. Recovery: fetch that blob, apply
my two intended functions to **it**, redeploy. Verified by the tool's own functional output.

Had git not held it, the 89,945-byte working version (89,081 committed + an 864-byte uncommitted fix)
existed nowhere on this machine — my own rescue-branch commit `d9b33c9b` turned out **not to contain
that path at all**, and every `master` copy is the old lineage.

Recorded as **L1925**. Four rules, in order of how much they would have saved: check the size and
`git log` before editing a file whose lineage is in doubt; never deploy without a post-deploy check
that can actually fail; `ast.parse` is a syntax gate, not a content gate; and when a repo has a
*known* two-lineage problem, treat every file in it as suspect until confirmed.

## WHAT LANDED — `lpt-sync-to-production.py`, authority `47c19986`

Two things, and the restoration matters more than the feature:

1. **Restoration** from this repo's own git, then the intended change applied on the correct base.
 This commit does **not** reconcile the two lineages — it restores the live tool and records that
 the split is still open.
2. **Root validation.** `_resolve_lpt_hub_root()` accepted any candidate where `(p / "docs").is_dir()`.
 It now also requires `.git` present **and** `git rev-parse --show-toplevel` equal to the candidate
 — proving the directory **is** the repository, not a mount into another nor a partial copy.
 Without it, a directory holding a plausible `docs/` tree passes and every downstream decision,
 *including which records get pushed to production*, is made against the wrong corpus in silence.
3. **It now says which candidate won and how fresh it is** (`_describe_hub_root`), because the
 resolution was invisible: three resolvers, three candidate shapes, each working on one host by
 accident, none saying which. Freshness in both directions — behind = stale, ahead = unpushed work
 no other machine can see. Rejected candidates are logged with their reason.

**Verified by function, not by parse:** `--dry-run-all` → `TOTALS: 383 record(s) — CREATE 7,
SKIP 376, ERROR 0`, and `INFO: lpt-hub resolved: /home/zabz/repos/lpt-hub @ 8cb746a06`.

**The landmine is also removed on ZABZ-TECH**: its working copy was still my wrong 33 KB file, which
a future deploy could have pushed again. It now holds the correct 92,973-byte tool (`dry-run-all` ×5,
`_GUARD_REFUSING_KINDS` ×2), and `--help` lists the flag. The `M` there is now a *correction* against
its old-lineage `HEAD`, not a regression.
