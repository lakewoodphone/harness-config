## 2026-09-17 13:35 UTC · ZABZ-YOGA · Closing out: the check caught three real defects — a 681 MB WAL from a leaked reader, a refresh clock dead 9.6 h on a missing exec bit, and my own check reporting that as fresh

CHANGED

- **A9 — the SQLite WAL was 681 MB and growing ~1 MB/min (67 MB/hour).** A leaked read snapshot pinned
 it: `PRAGMA wal_checkpoint(RESTART)` returned **`busy=1`**, so **11,310 pages** could never fold back
 into the database, and a long-lived reader in the API process (up since 10:36) held the snapshot.
 Measured growth: 680,187,312 → 681,027,792 bytes in 45 seconds.
 **Fixed:** restarted the API to release the reader, then `wal_checkpoint(TRUNCATE)` →
 **681,106,072 → 0 bytes**, result `(0,0,0)`, database intact (**222 tables, 628 contacts**), API
 healthy in 25 s. `db.wal_bytes` now reads **57,712 B**, OK.
 **Not durable:** the leak will recur. Finding what holds the snapshot is the real fix and is open.

- **A10 — the lpt-hub corpus refresh has been DEAD since 03:45 and my check called it fresh.**
 `scripts/lpt-hub-refresh.sh` is mode **100644 in git** while every sibling script is 100755, so cron
 died with `/bin/sh: 1: .../lpt-hub-refresh.sh: Permission denied` **every 15 minutes** into a log
 nobody read. The file's mtime (03:55) matches the last successful refresh exactly.
 **Fixed:** `chmod +x` on secratary (the refresh now runs; `lpt.refresh_age_min` → 0.20 min) **and the
 mode restored in git** via `update-index --cacheinfo 100755` so the next sync cannot undo it
 (`harness-config` master `c764dee2f5aa`).

- **A11 — and then the refresh runs but CANNOT do its job.** `status.json` reports
 `"fast_forward":"refused"` because the local clone is `ahead 1, behind 1116`. **My check was green
 while measuring only the script's timestamp** — and the script writes `status.json` on every run even
 when it refuses to update the corpus. That is the same "measures the wrong artifact" defect I have now
 fixed three times (absolute age → lag; `collapsed_duplicates` → split metric; and now this).
 **Fixed:** a refused fast-forward is a FAIL in its own right, with its own row naming the branch.
 **Open:** the clone itself needs a real reconciliation — 1 stray superseded commit, 1,116 behind, and
 2 dirty sync-records written by another process. **It must NOT be `reset --hard`.**

THE PATTERN WORTH KEEPING

All three were invisible on their own and the **check found every one of them** — not reading, not
reasoning. Two of the three were defects in the surface *reporting* on the defect:
`synced` counted no-ops as writes, and `lpt.refresh_age_min` counted a refused update as freshness.
**A green check is only as good as the artifact it measures**, and the failure mode of this system is
consistently "runs, reports success, does nothing".
