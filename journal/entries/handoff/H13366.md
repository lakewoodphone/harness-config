## Decision 1 — the approval backlog / task ceiling (three defects, not one)

The ceiling was full at 300/300, so `create_task` returned `-1` for **every** task: work orders, findings, approvals. 106 approval tasks open. Causes, each measured:

1. `_close_stale_tasks`'s approval branch matched `status IN ('in_progress','pending','blocked')` — every approval task this company creates is `open`, so it had **never** closed one.
2. Of 164 tasks past the 7-day window, **160 were exempted as "customer work" and all 160 fired one marker: `customer_word`** — a substring test for "customer" in the description. `Approve action: github_list_issues` was protected like a customer's repair. That single over-broad test disabled the reaper.
3. `_expire_stale_approvals` promoted the action to **L4** on every 2h expiry (1288 rows in the table). "Owner did not answer" → "then run it". This is also why actions kept reappearing at L4 after demotion.

Fixes: `approval`-tagged tasks are never customer work (that tag is written only by `_create_approval_task`/`_enforce_action_policy`; customer intake never writes it, so no real customer job can carry it — every other marker still protects the D2907 cases); the approval branch matches `open` with a 48h `STALE_APPROVAL_TASK_HOURS`; expiry grants nothing; `create_task(..., bypass_ceiling=True)` for approvals only, bounded by the exact per-resource key + 48h expiry.

**Measured after deploy, running service:** `Auto-closed 88 stale tasks`; `Left 96 customer task(s)/stall flag(s) open`; `Left 5 owner/money/deadline task(s) open`, including #29278 which carries a money amount — correctly the only approval still open past 48h. Active **300→212→207**, approvals **106→20**. With ceiling forced to 1 and active to 10,000: normal create → **-1**, approval create → real id, same `dedupe_key` twice → same id.
