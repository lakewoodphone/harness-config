### THE VECTOR REINDEX DIED FROM A FILE-DESCRIPTOR LEAK — worked around, cause unconfirmed
A single long-lived process indexed ~3,255 memories then failed every subsequent one with
`[Errno 24] Too many open files`, and because the process had exhausted its descriptors, the *next*
call surfaced as `unable to open database file` — a misleading error that reads like corruption and
is not. State when it died: **3,855 vectors of 21,891 (17.6 %)**.

**Worked around, not fixed:** `reindex_loop.sh` runs each pass in a **separate short-lived process**,
so descriptors reset every iteration, and it pauses rather than dies when the database is briefly
unreadable. Relaunched detached (pid 627639 at launch; log `/home/zabz/reindex2.log`).
**The leak itself is unconfirmed** — it is in either the embedding client inside
`unified_memory._embed` or in a connection taken per call. **Finding it is a follow-up**; whoever does
it should note that the *symptom* it produced (`unable to open database file`) in no way points at
the real cause.
