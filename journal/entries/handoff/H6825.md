## 2026-10-16 ~17:0xZ · ZABZ-YOGA · The kiosk's paying customer was being dropped on the sign-in page; all seven of the owner's reports are fixed on a branch, PR 459 is open, and the wake system is alive but cap-gated

The owner ran two live tests of the self-serve kiosk (`/intake`) and reported seven defects. **Every one of them was the same shape: the kiosk WRITES something and nothing READS it.** Diagnosed in source, all seven fixed, branch pushed, PR open.

### The root cause under four of them

The card customer was returned to a page that does not exist. Stripe's `success_url` is `resolveKioskPublicUrl()`, which returns `KIOSK_PUBLIC_URL` else `FRONTEND_URL + '/kiosk'` — and the page has only ever been mounted at `/intake` (`git log -S'path="/intake"'` = one commit, `da93b3172`; `git log -S'"/kiosk"'` = nothing).

Measured live this session: `/intake` renders the kiosk; `/kiosk?intake=…&payment=success` lands on `/login?expired=true` logged out and `NotFoundPage` signed in.

So the kiosk page never ran after payment, therefore never polled `GET /api/kiosk/intake/:uuid/status`, never saw `paid`, and never called `submit` — **the ONLY place `KioskIntakePayment.status` becomes `PAID`** (`kiosk-intake.service.ts:742`). The card was charged; the work order said "Not paid yet" permanently. That single break explains the owner's 404, his "does not say paid", and his missing ticket number (the confirmation screen that shows the reference never rendered).

### What still hurts

**Mesh dispatch is unreliable and it cost this session two subagents.** `subagent` routed the frontend brief to `zabz-tech-linux` twice; the child started and the transport faulted (`banner exchange: Connection to UNKNOWN port -1: Connection timed out`), so the run was ORPHANED and the first report was lost. **The cause is mechanical and known: the worktree is at a Windows path (`C:\Users\ezabz\code\_w34-kiosk`) and the broker placed the child on a Linux node that cannot see it, while the local node that CAN see it was never tried on the retry.** `subagent_local` did the job first time, and the backend child ran fine on `zabz-yoga-1`. Until placement is pinned to a node that shares the path, a brief naming a Windows worktree path will silently fail ~half the time — and the failure mode (orphaned, no report, work possibly half-applied) is the dangerous one. This is worth a flag of its own; it was not raised from here because raising flags is the dispatcher's job.
