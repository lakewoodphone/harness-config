THE HEADLINE IS A CONFIGURATION MEASUREMENT, NOT A CODE READING
**Production issues 7-day access tokens.**
- `JWT_EXPIRES_IN=7d` in `/opt/lpt/.env` **and** `/opt/lpt-test/.env` (measured via
 `docker exec lpt-backend printenv` and by reading both env files).
- The code default is **`15m`** — `backend/src/config/security-env.config.ts:37-40`, `.default('15m')`.
- Effect measured against data, not argued from config: **every one of the 287 sessions in `lpt_prod` has a
 TTL of exactly 168.00 h** (`SELECT round(extract(epoch from ("expiresAt" - "createdAt"))/3600.0,2), count(*) ... GROUP BY 1`).
- That is **672×** the intended access-token lifetime.

**Deliberately NOT fixed yet.** Shortening the window before the refresh-reuse branch is repaired
(PART-117 F-7) would trade a security defect for a customer-visible logout bug. The correct sequence —
fix F-7, then F-3, then set the TTL — is recorded in the part's §6 as C-119-1.

OTHER FINDINGS (open, assigned)
- **F-2 High — MFA is configured as required for admins and never enforced.** `SessionSecurityService`
 defaults `requireMfaForAdmin: true` (`session-security.service.ts:38`) and implements the check (`:175`),
 but the class is **exported and never instantiated** anywhere; `createLoginSession` (`auth.service.ts:613-668`),
 through which every successful sign-in passes, has **no MFA branch at all**; `grep mfaService.` outside
 `routers/mfa.ts` returns nothing. `user_mfa_settings` is 0 rows.
- **F-3 High — `changePassword` and reuse-revocation do not invalidate access tokens.** Both call
 `revokeAllForUser` only; neither deletes sessions (`:1004`, `:1136`). `validateToken` authorises on the
 **session row** (`:930-946`, reached from `trpc/context.ts:153`), so an undeleted session keeps working —
 for up to 7 days given F-1. `revokeOtherSessions` **does** delete them (`:1102-1106`), so the correct
 pattern is one method away.
- **F-4 Medium — the service writes zero audit rows.** Exactly one `securityEvent.create` in the file, inside
 the broken reuse path (`:1138`); zero `auditLog.create`. This is the direct cause of PART-117 F-9.
- **F-5 Medium — every session is created with `userAgent: 'unknown'`, no IP, no device hash** (`:424-425`,
 `:642-645`). Nothing in the service receives request context. This is why `sessions.deviceHash` is NULL on
 287/287 and why device/geo/secure-session features are unreachable by construction.
- **F-8 Low — `loginUser` is dead code and the only login method with no role check.** `loginStaffUser` and
 `loginCustomerUser` both gate on `UserRole`; `loginUser` accepts any ACTIVE user with a valid password.
 Nothing calls it (call-site grep), so it is latent, not live.
- **F-9 Low — the reset-code attempt guard is built and unreachable.** `incrementAttempts` is implemented at
 `services/auth/database.service.ts:647` on `PasswordResetTokenDbService` (`:570`) — the object injected
 into this service — and `git grep` finds it referenced only by its own definition and two generated `.d.ts`
 files. So `attempts` is permanently 0 and `attempts >= 3` can never fire.

TWO CORRECTIONS TO MY OWN EARLIER CLAIMS (kept in the record, not edited away)
1. I had written that "logout is not enough" because sessions were probably not checked. **Wrong.**
 `validateToken` really does read the session row, check `expiresAt`, and re-check user status on every
 authenticated request. Logout and suspension do kill live tokens. The true defect is narrower: the one
 place that does not benefit from that check is `changePassword` (F-3).
2. I had written that reset codes have "no lockout and no failure signal". **Half wrong.** `resetPassword`
 enforces `attempts >= 3` and `isUsed` (`:1769-1780`). The accurate defect is a **dead check**, not a
 missing one (F-9).

WHAT IS CORRECTLY BUILT (part §4b, so a later pass does not "improve" it away)
bcrypt at write and verify with `'[REDACTED]'` before any object leaves the service; deliberate
anti-enumeration (one flat message, and `success: true` with a fake expiry for an unknown reset destination);

SSO does not trip reuse-detection; and edge rate limiting at `security.config.ts:162-163`.
