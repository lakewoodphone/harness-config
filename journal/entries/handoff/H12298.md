## 2026-10-22 07:55 UTC · ZABZ-TECH · Kosher filter: removed a false security claim, and refused to replace it with an unverified one

`origin/main` = **e985d74** (merge of PR #128). Ledger **1075 done** on its third branch; new **1128** filed
for the hardware question.

### The false claim

`AntiEvasionPolicyManager` said, twice, that third-party screen recording was prevented:

```kotlin
// Third-party screen recording is prevented by DISALLOW_CREATE_WINDOWS
// and the accessibility service whitelist.
```

Neither can do that. `DISALLOW_CREATE_WINDOWS` stops an app drawing **overlays**;
`setPermittedAccessibilityServices` stops other accessibility **services**. An app that records the display
does neither. So capture is **enabled**, a third-party recorder works on a sealed phone, and the comment
told a reader the opposite — in the summary list and again at the call site. Both corrected; the gap is
referenced there so it is findable from the code that owns it.

### What I refused to write

The tempting fix was to say "the restriction has no device-owner exemption". I checked the
`setScreenCaptureDisabled` and `DISALLOW_SCREEN_CAPTURE` reference pages: they say the restriction is
**user-wide**, but **neither says whether the device owner's own capture survives it**. So the comment now
records the belief as *unverified — never tried on a device*.

**Replacing a false claim with an unverified one is the same mistake in a nicer font.** That is the whole
lesson of this round, and it is why 1128 exists rather than a confident sentence.

### What 1128 asks for

On the physical handset, with the control applied: does our own `MediaProjection` still work? If yes, ship
it on. If no, either toggle the policy around our capture windows, or state the limitation in
`docs/FEATURES.md` **where a purchaser reads it**. Whichever branch, recorded as observation, not
inference.

### Worth noting about this item

Its DoD offered three branches and I took the least satisfying one — because the other two need hardware
and I could not honestly claim either. A green PR that closes an item while the gap stays open is only
acceptable when the record says so in the same breath, which is what the ledger entry and the code comment
both now do.

No behavioural change: the call still passes `false`, and `docs/` had no second copy of the claim to fix.
