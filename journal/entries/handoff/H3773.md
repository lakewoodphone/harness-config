## 1. THE 20 PHYSICAL CHECKS: tested, and the walk is real

Round 7's lesson was that a category label is not a finding — a row labelled "unverifiable cash" had its
figures on the order all along. So the 20 shelf checks were tested the same way: can the RECORD answer
any of them without a walk? Three things would settle one — the customer acknowledging collection, the
shop recording a hand-over, or a message saying the device is not held.

**Result: of 25 checked, only 2 had anything, and both are questionable.** One is a four-month-old
reconciliation note citing the *owner* ("device is no longer in shop") on a row already resolved by the
concurrent session; the other is a note saying the *case* is resolved with no charge, which is not the
same as the device having been collected. **18-20 genuinely need eyes.** The walk stands.

**And the first version of that test was wrong in an instructive way.** It counted the shop's own
*"your device is ready for pickup"* notice as evidence of collection and produced **six false
"settled" verdicts out of seven**. A notice we send is not a hand-over; it is the same mistake as
reading a null `pickup_notified_at` as *"never told"* — **a record of an action is not the action**. The
test was tightened to inbound-only customer acknowledgements and explicit shop statements of hand-over,
and only then did it report what it reports.

## 2. THE 283: a list, not a number

Round 3 measured that 283 orders rest at `READY_FOR_PICKUP` with a failed completion notice and nothing
successful after it. That is the number behind the owner's open question about re-notifying — and a
number is not enough to decide with. The list now exists with order, customer, phone, device, and the
date each notice failed:

**283 orders. Oldest failed notice 2025-12-25, newest 2026-10-09.**
Bands: **131 over 120 days, 119 between 60 and 120, 33 under 60.**

It carries its own caveat in the file, because this is exactly where a floor gets mistaken for a
population: **only about 1.3 % of `communications` rows carry an `orderId`** (the rest carry only a
`customerId`), and a customer may have been telephoned — the dialer records calls against the customer,
not the order. So *"no successful message recorded"* is **"no written notice we can prove"**, not
*"never told"*. A zero would have meant no-evidence; this is not zero.

The concentration is explained by F4: the failures begin when Twilio stopped answering.

## 3. A WRONG LABEL IN A DURABLE ARTEFACT, CAUGHT AND FIXED

The first version of the list said *"the oldest failed notice is 2026-10-09; the newest is
2025-12-25"* — **inverted**, because the query orders oldest-first and I indexed the list as if it were
newest-first. The file now reads **oldest 2025-12-25, newest 2026-10-09**, which is the truth. A wrong
label in a document that outlives the session is worth more attention than a wrong label in a console
line, and this one was in the document.
