## 2026-10-18 · ZABZ-YOGA · Estate search round 11: three surfaces agents read were lying, and both monitors are now green on purpose

Continues **H8234**. Commits `d897e0e`, `c2555e65` (harness-config), plus this round's `integrity` fix.

### Fixed this round — all three are things an agent or a monitor reads

1. **The `ps_search` docstring listed scopes that did not exist** and omitted the ones that did:
 `code | data | journal | files | symbol | auto`. An agent asking about a session, a document or
 the comms corpus had no way to know those scopes exist — the tool would have answered, but nothing
 told anyone to ask. Now: `sessions | data | journal | docs | files | code | symbol | all`, with
 what the labels mean (`live=false`, `degraded:`, `did_not_answer`). Verified end to end:
 `ps_search(what="docs", "invoice template")` → 221 ms, three real documents.
2. **The fallback crashed instead of degrading.** With esearch pointed at a dead port on a Windows
 node, `_fa` raised `FileNotFoundError` straight out of the tool body — Windows has no
 `find-anything` at all, so the degraded path could never have worked there. A traceback is the one
 answer a search tool must never give. It now returns `ok=false, searched=false` and the sentence
 that matters: *NEITHER ENGINE IS AVAILABLE … nothing was searched — this is a refusal, not a
 negative.*
3. **`/integrity` went red on 4,071 documents and every one was a 0-byte file** (empty `__init__.py`,
 empty XML stubs). The failure that check exists for is the opposite shape — a document that HAD
 content and produced no chunks. The reading now separates them: **empty files 4,071 ·
 content-without-chunks 0 · chunk gap 0 · session-FTS 2000/2000**, `ok=true`.

### Also

- **Merge now fuses per document, not per chunk.** The key was the locator, which carries a line
 range, so one file came back as two hits at lines 197-271 and 124-210. A document is the identity;
 the other places are recorded in `also_at`. Checked against live data: two same-named hits that
 looked like a duplicate were **genuinely different files** (`phone-and-tech-full/archive/...` and
 `phone-and-tech`), so the fix did not hide real data.
- **The laptop's local prune removed 66,400 documents** (87,847 by path, 37,685 by extension
 identified) and was stopped when it slowed to 16 s of CPU in ten minutes. It is cosmetic: nothing
 in the agent path reads that index — `code` queries go to the authority, `fa` is a live scan — so
 it does not get another hour. The index stands at 186,045 documents with the remainder prunable by
 the same script.
