**THE AUDIT WAS THE HIGHEST-VALUE OUTPUT.** A read-only child (`_fleet/waze-audit/UX-AUDIT.md`) found the pattern in one line: *this codebase is rigorous about failure where data is FETCHED and leaky about it where data is RENDERED* - the last hop throws away honesty the server already built. Top findings, all with file:line:
- `unresolved` is built by `customerPortal.ts:909-931` and dropped by `WazeDevice.tsx:598` - a customer with two devices, one unreadable, saw one card and no warning.
- "(404/502/503 collapsed)" - the router deliberately separates them (`wazeFleet.ts:198-223`) and `WazeDevicePanel.tsx:177-182` re-collapses them, so an outage reads as "no device found".
- **F9, would have broken a real purchase:** the Stripe success path defaulted to `/store/waze/success`, which is NOT mounted; the store is at `/kosher-waze/*` and unmatched paths redirect to `/`. So a customer who had just paid was dumped on the homepage. **The cancel path was wrong the same way.**
- A raw service enum including the literal `unknown` rendered inside a green "healthy" chip.
- Alerts rendered no `dnr`, so staff could not tell which of ~65 phones an alert concerned.
- It also listed **14 things worth protecting** so they would not be churned.

**WHAT EACH WORKSTREAM FOUND OR BUILT**
- **Nav:** added `waze-fleet` + `waze-billing` to `MVP_NAVIGATION` (group `utility`, `roles: ['ADMIN']` - deliberately narrower than neighbouring `ADMIN, MANAGER` items so a MANAGER is not shown a page whose every query 403s), and correctly **refused** to add a provisioning entry because that route did not exist (a 404 behind a click). Found the customer nav ALREADY had `My Waze Device`, and that public/SEO pages appear in no nav by house convention - so the storefront was left as a direct link, correctly.
- **Provisioning queue (new):** my brief assumed `serialNumber: null` marked an unprovisioned device. **That was wrong and the child proved it.** The checkout writes two rows that do not reference each other - `Order.deviceInfo.provisioning = {required, serialAssigned, drnAssigned, simAssigned}` (`waze-checkout.service.ts:566-573`) plus a `Device` row with a null serial (`:606-625`) - and `Device` has NO FK to `Order`. Nothing ever writes a serial onto that row, so a null serial stays null **after** the bench finishes too; keying on it "would have re-provisioned sold phones and shown wrong work". It used the order's marker instead. **Unresolved and stated:** with no `orderId`, a device is correlated by `customerId` alone, so a multiple-device customer is flagged `ambiguous` and the UI says the phone is "a hint, not a match". The clean fix is `Device.orderId` (schema change, forbidden to the child). Also honest: **nothing yet flips `serialAssigned`**, so the queue is correct about work not done but is not self-clearing.
- **Customer journey:** confirmed the headline defect with the base-commit line - a customer who had just paid was shown *"You do not have a Waze device linked to this account yet"*, because `getMyWazeDevices` filters serial-less devices. Fixed using the checkout's EXISTING marker (no invented field), trusted **only while no device is linked**, because nothing ever flips it back and showing it unconditionally would call a worked phone "being prepared". "No devices" is now three states: with the bench / could-not-check (with retry) / genuinely none. Added a "what happens next" block with a test asserting it contains **no `$` amount, no day/week/month window, and no return or warranty term** - it refuses to promise what the business has not settled.
- **Billing + checkout:** fixed F9 by changing the BACKEND, because the frontend was right - `DEFAULT_SUCCESS_PATH` and `DEFAULT_CANCEL_PATH` both moved off the unmounted `/store/waze/*`. Loading state fixed. The allowance contract's backend half fixed (`toNullableNumber`, typed `number | null`). Demonstrated two fixes by breaking them and showing the exact failing lines.

**INTEGRATION - done and gated.** Merged `waze/nav-staff`, `waze/customer-completeness`, `waze/billing-fix` and `waze/provisioning-queue` into `waze/verify-integration` on my own worktree; every merge exit 0, and a conflict probe showed **no file touched by two agents**.
