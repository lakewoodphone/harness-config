WHAT THAT MEANS, and it corrects two parts at once. PART-078 and PART-108 independently reported that
RealtimeContext authenticates Ably with a build-time VITE_ABLY_* key inlined into the public bundle, so
an anonymous visitor could read it and reach the unscoped staff channel phonetech:admin:all. Both
explicitly flagged the value as UNVERIFIED and called it the single most consequential unknown. It is
now answered: the value is ABSENT in the deployed build, so that half is LATENT, not live. The code path
is unconditional; the value simply was not set at build time.

The LIVE half is the other one, and it stands: POST /api/ably/token is authenticated (JWT-only, no role
check) and hands back the RAW globally-scoped key, so any authenticated caller - including a CUSTOMER -
can obtain a publish-capable key for the whole realtime channel. That is the thing to fix, and hardening
the endpoint is sufficient for the endpoint; the bundle half becomes real the moment someone sets
VITE_ABLY_*.

LIMITATION, stated: only the one bundle referenced by index.html was fetched. A lazily-loaded chunk not
referenced there would not have been scanned - but the Ably wiring itself IS in that bundle, so an
inlined key would have been too.
