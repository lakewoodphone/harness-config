## 2026-10-20 18:57 UTC · ZABZ-TECH · round 23: the wasted shift came from a pre-register state file; work_remaining=true against a six-day-old snapshot

# H (2026-10-20, round 23) - the wasted shift came from a stale state file from before the register existed

## The third source, found
`project-keepalive.py` flags a project from its per-project STATE FILE, not from the ledger or the register. For
kosher-ai-filter: `/home/zabz/.wake-projects/kosher-ai-filter.json` held `work_remaining: true` and an **11-entry
`remaining` list of notes dated 2026-10-14 to 2026-10-16** - before the roadmap register existed. Their headline,
"docs/cross-platform-filter-master.md section 7 still has 23 unchecked rows", stopped being true on 2026-10-20 when
section 7 was archived and the register became the one owner. So the source was faithfully re-filing a paid shift
every cooldown against a snapshot six days old.

Fixed with a backup (`kosher-ai-filter.json.bak-20261020T185715Z`): `work_remaining=false`, `remaining=[]`, and two
dated notes recording the measurement (register 34 done / 18 blocked / 0 open, supply `new=0`, ledger 9 non-terminal
all blocked with future revisits) and why the cleared entries were stale.

Verified: `project-keepalive.py --dry-run` now prints
`kosher-ai-filter quiet no work remaining (state file says the work is done)` and files no flag.

## Checked, and it was stale too
One of those notes named a real-looking defect: several Windows DoDs saying `dotnet test windows/DnsRelayService`. The
directory exists, `docs/testing-matrix.md` already records that it holds no test project, and **no roadmap item names
it any more** - it was fixed when the register absorbed those DoDs.

## The deeper cause is a policy, and it is the owner's
`projects.json` sets `ignore_blocked_ledger: true` for kosher-ai-filter, with reason "ledger item 142: exempt from the
new 'no shift-startable ledger work' suppression", granted 2026-10-14 when the state file named untracked roadmap
work with no ledger row. That exemption is why a `blocked-future` ledger verdict only ANNOTATES (`[ledger: ...]`) and
never suppresses.

It is not a bug to fix silently: removing it makes the owner's always-on flagship able to go quiet on its own, which
trades wasted shifts against a silent stall if the supply ever stops filing. Put to the owner in plain chat with a
recommendation (keep the exemption, but make "a shift that finds nothing leaves `remaining` empty" a rule the shift
contract enforces, plus a monitor for `remaining` non-empty while the ledger is blocked-future).

## Ledger state after this round
kosher-ai-filter: 9 blocked, 0 todo, 0 running; roadmap register 52 items (34 done, 18 blocked, 0 open). 819 closed.
The lesson: **the register being clean does not make the loop quiet - the loop reads a state file, and that file has
its own history.**
