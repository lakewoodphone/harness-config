### The design decision, and why it cost a round

The obvious implementation was to feed the broker's `modesty_level` into the ladder. It is 1–3 knob
bundles; the ladder is 1–8 attribute rungs. Mapping them (1→3, 2→5, 3→7) is a **policy change that alters
what a child can see**, and it would have passed every test and read as plumbing. Round 15 spent itself
finding that instead of shipping it; round 16 landed a validated, optional, absent-by-default rung; this
round delivered it to the device. Three rounds for what looked like two lines — and now the scale confusion
is a **test** (`theHouseholdFilterLevelIsNotARung`) rather than a paragraph someone must remember.

### Traps paid for here

- **`@'...'@` vs `@"..."@` in PowerShell**: a backtick inside a double-quoted here-string is an escape, so a
 PR body containing markdown code spans dies with "The Unicode escape sequence is not valid". Write the body
 with a file tool instead of composing it in the shell.
- **I pushed nothing before building.** The first Android run reported `pathspec
 'feat/ladder-level-device-1096' did not match any file(s)` — the branch existed only on this machine, so
 the build ran against an old commit and failed for the wrong reason. Commit and push *before* asking
 another host to verify.
- **A merge can change the shape of a line a scripted replacement depends on.** `IMPLEMENTED-VS-DESIGNED.md`'s
 counters line came back from the merge in a different form than my regex expected, so `subn` returned 0 and
 I read the line and edited it by hand against freshly measured numbers.
- **Not every CI job applies to every PR.** This one touched only `android/`, `docs/`, `scripts/`, so Server
 CI and the Postgres job correctly never ran. "Only two checks reported" is right here, and was a false
 alarm the other way round in round 13 when a conflict suppressed them.
