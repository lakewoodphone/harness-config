## 2026-09-17 13:13 UTC · ZABZ-YOGA · unified-search complete and audited end to end (H400-series): coverage, speed, permanence recorded; ingest throughput named as the one weakness

**unified-search is complete as a system: 148,266 documents on the laptop, 699,704 on the authority,
459 tests green, and one honest weakness named. The full audit is `docs/AUDIT.md` in the repo.**

## What it delivers against the ask
One query surface over every corpus that exists: `scripts/use.py` federates across hosts and merges
with reciprocal rank fusion, naming any host that did not answer. Coverage is measured per corpus:
repos and code 46,080 documents, chat 2,418 (nine months of the owner's reasoning, 59,771 messages),
journal 261 on a live schedule, Dialpad comms 167,159, production Postgres 119,050, git history
18,555. **Email is partial and the gap is upstream, not search** — `email_catalog` has 0 rows, so
Gmail bodies were never fetched into the database and there is nothing to index.

## Speed
0.6-16.8 ms in-process for every ordinary query class; a common word 1,644 ms with the degradation
guard (was 8,817 ms); gibberish 34 ms (was 52 s); `stats` was 157 s and is now under 1 s. The CLI
adds ~200 ms of interpreter start, which is why a long-lived process or an MCP tool is the right
shape for an agent and the CLI is right for a human.

## It stays true
The schedule is installed on both hosts and read back, and it was **observed working unprompted** —
it added git and file documents by itself while other sessions worked. Freshness is a measured gap
between the newest document and the newest item in the source, not "the job ran". `usearch.py check`
exits 0/1/2 so "I checked and it is fine" can never be confused with "I could not check".

## The one thing that is not good enough
**Ingest throughput.** 134 docs/s batched on new documents, but **2.7 docs/s re-ingesting the real
chat corpus** (200 documents / 21 MB took 74.1 s). A parallel session removed the chunk-delete index
scan and the number barely moved, so the cost is in chunking plus the FTS5 insert itself, not in
commits or locking. A first load of the whole fleet would take hours. This is named in the audit with
its measurement rather than glossed, and the numbers are the baseline any fix must beat.

## What auditing bought, which is the point of this round
I asked for two independent read-only audits and both found real things I had wrong or hidden:
* **My own wedged process** — a 69 MB ingest running five and a half hours with zero I/O, holding a
 write lock that failed every other source's refresh. I had misread its symptom as contention from
 other sessions. Cause was one commit per document; now batched and measured at 2.5-4.4x.
* **A registry naming `adapters/<name>/adapter.py`** for all thirteen sources — a filename no
 adapter has ever had. The refresh did nothing for every source while `--list` printed a correctly
 scheduled pipeline. Fixed from each adapter's own `--help`; six entries now disabled with reasons.
* **The machine's load is not search.** 0.2% of a core. It is 129 Edge processes, 24 agent loops,
 Windows Search and Defender, with paging ruled out by counters. Loop-lag p95 4.8-6.5 s is
 concurrency starvation, and its cost was captured: a `list_agents` call served a 32-minute-old
 listing.
* **A schema comment containing a statement separator** silently took the migration path out of
 service on exactly the databases that hold data, while fresh files worked — which is why every
 test passed.

## Lesson worth carrying
Self-assessment is not audit. I had reported this system as working and it was; I had also asserted
"the index is locked by other sessions" when the lock was my own stuck process, and I would not have
found that by looking again — I found it because a reader with no stake in the answer measured the
process's CPU and I/O deltas over 25 minutes and saw zero.
