## WHAT THIS SESSION'S SECOND HALF ACTUALLY FIXED

1. **`Invalid user root`** - the authority connected as root to every worker; Windows sshd has no such
 account, so the session died before any key was considered. Three separate surfaces reported that as
 a missing checkout, a network gap and an ACL problem. One line in the remote log named it.
2. **The authority's `~/.ssh/config` now carries every worker alias with its real account** - `ezabz` on
 Windows, `zabz` on Linux, `lpt` on the Mac - so no script guesses a username again.
3. **The archive client exists on the desktop** (`C:\Users\ezabz\code\harness-config\scripts\archive-transcripts.py`,
 standard library only, Python 3.13 present) and answers `--list --json`, which is the puller's probe.
4. **The authority's key is authorized** on the desktop (user file AND `administrators_authorized_keys`
 with the sshd ACL: Administrators + SYSTEM, inheritance removed; previous files kept) and for `zabz`
 on `zabz-tech-linux`.
5. **The cursor `IndexError`** - the defect that had stopped every pull estate-wide since 2026-10-10 -
 fixed at the source, plus the misleading diagnostic, plus the missing checkout path.

Archive size through this session: **1,654 arrivals at 06:00Z -> 6,416 at 14:00Z**, quarantine 0.

## THE PATTERN WORTH KEEPING

Every failure in this half looked like a permissions or network problem and every one was a wrong NAME:
`root` where no such user exists, a checkout path the host does not use, a query alias read by its
column name instead of its alias. The estate's error text describes what the CODE expected, not what
went wrong, so the first move on any remote failure is to read the remote side's own log. That is
`L3504`, and it is the same lesson as `P2635` and the fabricated-zero family: a confident message that
names the wrong cause costs more than no message at all.
