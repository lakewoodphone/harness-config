## 2026-09-17 13:20 UTC · ZABZ-YOGA · unified-search FINISHED and audited: four defects the audit found, one weakness named, schedule and query verified on both hosts

APPEND to H400/H446 — 2026-09-16/17, after the audits. The job is finished and documented; four real
defects were found by auditing rather than by building, and every one of them made a working-looking
system that did nothing.

## THE FOUR DEFECTS THE AUDIT ROUND FOUND

1. **The registry named a file that has never existed.** All thirteen sources pointed at
 `adapters/<name>/adapter.py`; every adapter is `sync.py`. So the refresh reported "adapter not
 found" for all of them and ingested nothing, while `sync.py --list` printed a correctly scheduled
 pipeline with per-source staleness limits. Rewritten from each adapter's own `--help`; seven
 enabled, six disabled with a written reason.

2. **A wedged process of mine held the write lock for five and a half hours.** A 69 MB chat ingest
 at one commit per document, with **zero CPU delta and zero bytes of I/O across a 25-minute
 window** — found by an independent read-only audit measuring process deltas, not by me looking
 again. I had misread its symptom as contention from other sessions. Fixed: `batch` on the ingest
 path, `in_transaction` on `add_document`, `--bulk` defaulting the batch to 2000. Measured 2.5-4.4x:
 73 MB / 20,000 docs went from 379 s to 149 s.

3. **The authority tried to ssh to itself.** `host_is_local` compared hostnames exactly;
 `socket.gethostname()` on the server returns `secratary.tail93e6e6.ts.net` against a registry
 entry of `secratary`, so the comparison failed and every server-side source took the remote path
 and died with `Permission denied (publickey)` — a host has no key for itself. And then a second
 layer of the same bug: even after `host_is_local` was fixed, nothing consulted it, because
 `sources_of` set `host_name` straight from the registry string. Both fixed. **Proven on the
 authority: `2/2 source(s) ok, 649 document(s) written`.**

4. **A schema comment containing a statement separator** silently truncated `executescript`, so
 `migrate()` aborted with the misleading `no such column: source` on any database created by an
 earlier version — exactly the databases with data — while a fresh file worked, which is why every
 test passed.

## AND ONE THING THE AUDIT CLEARED ME OF
The machine's sluggishness is **not** the search program. Its CPU share was **0.05 of a core
(0.2%)**. It is 129 MS Edge processes holding 9.7 GB and ~37% of CPU, 24-25 concurrent agent loops
with 15 tool-call runners on 22 logical cores, Windows Search at 2,540 CPU-s since boot and Defender.
Paging was ruled out with counters: page writes/sec 0.0000, pages output 0, pagefile usage 2.9-3.5%,
10.7 GB commit headroom. The cost of the real problem was captured too: a `list_agents` call blew its
8 s deadline and served a **32-minute-old** listing.

## THE ONE WEAKNESS, NAMED AND MEASURED
**Ingest throughput.** 134 docs/s batched on new documents, but **2.7 docs/s re-ingesting the real
chat corpus** (200 documents / 21 MB in 74.1 s). A parallel session removed the chunk-delete index
scan (`ee2f829`, `82c4c26`) and the number barely moved, so the cost is in `chunk_document` plus the
FTS5 insert itself, not in commits or locking. A first load of the whole fleet would take hours. If
anyone fixes it, these are the numbers to beat: **134 docs/s (new, batched)** and **2.7 docs/s
(re-ingest, real chat corpus)**.

## THE LESSON
Self-assessment is not audit. I had reported this system as working, and it was — while a scheduled
job did nothing, the server could not run its own sources, and a stuck process of mine was holding
the only write lock. I would not have found any of those by looking again, because I was reading my
own intentions. I found them because two readers with no stake in the answer ran the commands.
