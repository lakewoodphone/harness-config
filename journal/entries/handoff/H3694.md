## What landed, on the authority, verified
`roadmap-supply.py` (the source that turns a project's roadmap into ledger work) now decides an id-keyed
row from `docs/roadmap/items/<ID>.md` instead of from the TEXT of a checkbox. Five edits, each with a
`.bak-*` beside the live file, `py_compile` rc=0 after every one:

1. `parse_item_front()` - the four fields the source needs from an item file (state, dod, ledger, title).
2. The decision block: an id-keyed row is `done`/`blocked`/`dropped` -> nothing filed; `open`/`partial`
 -> a candidate, with the item's own `dod` preferred. A row with NO id keeps the checkbox path
 unchanged, which is why lpt-website behaves exactly as before (measured: id_keyed=0 text_keyed=22).
3. `--check-ids` - every mapping row's `roadmap_id` must resolve to a file that declares it.
4. `stale_mapping_rows` no longer counts an id-keyed row (the id resolves whatever the box says).
5. Coverage (`uncovered`) is computed over text-keyed boxes only.

Two counters had to be narrowed because the switch made them lie, and both were caught by running the
dry-run rather than by reading the diff:
- counting every id-keyed row in `matched` made `mapped=41` against 26 unchecked boxes and manufactured
 `uncovered=10`, which would have filed a spurious authoring item on the next real run;
- `uncovered` itself then reported 10 as genuine, and it was: ten `filed` rows whose ledger item is
 neither live nor done - the seven rows that lost their link to a reworded title plus the dropped ones.
 The old code masked them by marking every one of them `pending`. With item-keying they are not
 uncovered at all, because their path exists as a file.
