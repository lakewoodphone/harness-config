## 2026-10-08 04:09 UTC · ZABZ-YOGA · MONEY: 257 payment rows totalling 27,384.00 settled at Stripe and never recorded as received - the production webhook endpoint did not exist before 2026-10-07

CHANGED — the money defect, fully traced. This is the largest single finding of the night.

**One sentence:** 257 payment rows totalling **27,384.00**, dating back to 2025-12-31, were settled at Stripe
and left `PENDING` in the shop's own database, so the shop's "collected" figure has understated its
takings by that much for ten months.

**The chain, each link measured.**

1. **The production Stripe webhook endpoint did not exist before 2026-10-07.** Stripe's own record:
 `we_1UNzjALnlgYj1gmTorg8lhoB`, `api.lakewoodphoneandtech.com/webhooks/stripe`,
 `payment_intent.succeeded` enabled, **created 2026-10-07**. Before that date there was no endpoint,
 so a payment intent that succeeded had nothing to notify and the shop's row could never be settled.
 A card payment writes the row as PENDING when the intent is created; only a webhook moves it on.
2. **So every card payment before 2026-10-07 is stuck at PENDING for ever**, whether or not Stripe took
 the money. Measured now: **257 rows settled at Stripe, still PENDING here, 27,384.00.**
3. **The route itself is healthy and was never the problem.** An unsigned POST to the live endpoint
 returns `400 {"error":"Missing stripe-signature header"}` - mounted, live, rejecting correctly.
4. **Where the payments come from, from the code:** `terminal.service.ts:372-377` threads an order into
 the intent metadata **conditionally** (`...(input.orderId && {...})`), and
 `payments.ts:147-190` accepts **"orderId OR staffNote"**. The live charges carry
 `{readerId, staffNote, transactionType}` and **no orderId** - so the counter takes the card without
 selecting an order, and the free-text note ("Button", "diagnosing fee", "Shabsi charger for dell") is
 the only identification. **The link works; the counter does not choose an order.**

**What is fixed by itself and what is not.**
- *Forward:* the endpoint now exists and the route works, so payments taken from 2026-10-07 onward should
 settle. NOT PROVEN - it needs the next real counter payment to confirm.
- *Forward, still broken:* those payments will settle but stay **unlinked**, because the order is still
 optional at the counter. That is a workflow change in `phone-and-tech-full`.
- *Backwards:* the 257 rows need a one-off reconciliation from Stripe's own record. That means writing
 `payment_transactions`, which `website_db` cannot do - so it is a decision, not a step.

**A confound I checked and discarded:** the backend container on `lpt-apps` restarted at
2026-10-08T04:04:45Z and its log held only 126 lines, so "zero webhook lines in 72h" would have been an
artefact of the restart and is NOT evidence about whether webhooks arrive. Do not cite it.

**Tools built tonight, all read-only or fail-closed:**
- `lpt-stripe-audit` - classifies every settled charge against the shop's records; attribution requires
 independent corroboration, never amount alone.
- `lpt-payment-backfill` - DRY RUN ONLY; reports PENDING rows whose intent Stripe settled. Writes nothing.
- `lpt-write payment set` - settles ONE order, after verifying the charge back from Stripe (committed,
 `13d0af6`).

NEXT
1. The owner decision: settle the 257 historical rows. If yes, the reconciliation must be per-row
 verified against Stripe, dry-run first, with a ledger - and it must be built where the payments table
 can legitimately be written, not bolted onto `lpt-write`.
2. Make the order mandatory when taking a card at the counter (workflow, `phone-and-tech-full`).
3. Prove the forward path with the next real terminal payment, then re-run the audit.

EVIDENCE
- Stripe: `GET /v1/webhook_endpoints` (the 2026-10-07 creation date), `GET /v1/events` recent intents,
 `GET /v1/payment_intents` per row for the backfill.
- Live route probe: unsigned POST -> 400 with Stripe's own message.
- Ties to H3333 (the audit and its two corrections), H3335 (the code root cause), L3392.
