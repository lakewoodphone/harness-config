## 2026-10-20T00:33Z · ZABZ-YOGA · the levers re-ranked: prompt trimming beats routing beats scheduling, and the cache question is what proved it

### What changed it

The owner asked whether every provider offers the same cache discount, "because we hit 99.9 % cache usually".
Both halves of that turned out to be measurable and true:

- two live DeepSeek calls, seconds apart, identical 4,039-token prefix: `cached_tokens 0` then **3,840 (95 %)**;
- `model_usage` says the company's autonomous ticks hit **0.86 %**, because each tick rebuilds its prompt;
- the reason, now fully attributed: `agent_worker` **re-sends the whole accumulated message list every round**,
 `TOOL_RESULT_TRUNCATE` is **12,000 characters per tool result**, a tick runs **3.57 rounds** and makes
 **7–14 tool calls**. Working memory (143 chars avg) and step results (under 3k chars) were measured and ruled out.

Prompts are therefore **27k–43k tokens around a ~700-token stable head**, which caps any prefix cache at ~2 %.
The cache discount is real and 50× deep; this workload simply cannot reach it in its current shape.

### A second defect found on the way

`tick_telemetry.total_tokens` averages **11,503 per tick** while `model_usage` records **42,625 average prompt
per call** for the same agent — a **~9× disagreement**. `model_usage` is what the provider bills against, so
**`tick_telemetry.total_tokens` is not a cost surface** and any dashboard reading it understates spend.

### The habit worth keeping

Three times this stretch the ranking moved because a *question* arrived that I had not asked myself — the owner
asking about caching, the arithmetic refusing to reconcile, and a rehearsal printing a number that contradicted
its own design. None came from reviewing my own work. **Write the prediction down before the event, and insist
the numbers add up afterwards; those two habits found every real defect in this body of work.**
