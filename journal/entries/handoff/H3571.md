## 2026-10-12 · ZABZ-YOGA + secratary-cloud · the search system was dead on the cloud authority; it is now working, tracked, guarded and clocked

### CHANGED — all on `secratary-cloud` (the authority), committed there as `1c88848`

**1. THE HEADLINE: `ps_search` — the tool the `fast-search` skill tells every agent to use — was
answering `Tool search not found` on the authority.** Reproduced first, then traced to one line:

 $ curl -sX POST localhost:8002/tools/run/search -d '{"query":"battery","what":"data"}'
 {"ok": false, "error": "Tool search not found"}

`run_tool()` (`app/tool_factory.py:705`) returns exactly that string from
`if not tool_path.exists()`, so **"the registry says this tool exists" and "the tool does not exist"**
were indistinguishable to every caller. `ps_comms_search` failed identically. Cause: `data/tools/` is
in `.gitignore:58`, and **599 of the authority's 607 registered tool bodies were missing** — the only
copies in existence were on the office box that the cutover was freezing. No deploy from any branch
could ever have carried them.

**2. Restored 593 tool bodies** from the frozen office box (`data/tools/*.py`, 3.87 MB) — excluding
`help.py` (the authority's is a *different* implementation, kept) and `comms_search.py` (a symlink,
repointed to `/root/.fsearch/comms-search.py`). 7 of the authority's 8 pre-existing bodies were
**cloud-only** and were left untouched. Before-image: `/root/.search-port/before/data-tools-*.tgz`.

**3. Installed the engine.** `find-anything` existed on the authority nowhere. Installed to
`/usr/local/bin/find-anything` + `fa`, from a **byte-verified copy** (sha256 `64ecacc7…`) of the office
box's *working tree* — which carried **89 uncommitted insertions that exist in no git ref**. Indexes
built: 6,897 paths, **82,899 symbols**, journal 3,243 entries. Installed `ripgrep 15.1.0` and
`universal-ctags 6.2.1` — `code`/`symbol` had been silently falling back to `grep -r`.

**4. Fixed the false negative that D2983 recorded and nobody fixed.** `journal.py` required every
query term **on the same line**. So:

| query | before | after |
|---|---|---|
| `journal.py search "lpt website deploy"` | **exit 1 — "no match"** | exit 0 |
| `journal.py search "cloud migration secretary"` | **exit 1 — "no match"** | exit 0 |
| `journal.py search zzqqnosuchterm9931` | exit 1 | exit 1 (still a real negative) |
| `journal.py search battery` | exit 0 | exit 0 |
| `--all-words` | strict | strict (unchanged) |

`search.py` rendered that exit 1 as `NO MATCH (exit 1: the scope was searched and holds nothing)` —
a **confident false negative on an ordinary two- or three-word query**, which is the one failure the
owner's "complete answers" criterion cannot tolerate. Now: entry-level AND over whitespace-split
terms, so one argv element (`ps_search`) and many (a shell) mean the same thing. `--all-words` keeps
the strict line reading, `--regex` keeps adjacency. 399–490 ms, `journal.py check` **0 errors**.

**5. Made the whole subsystem reproducible from git.** New canonical home
`harness-config/scripts/find-anything/`: engine, index builder, tool body, registration, installer,
freshness clock guard, crontab fragment generator. The two hardcodings that broke at the cutover are
gone — the engine resolves its checkout (`$FA_CHECKOUT` → probe → `/opt/company`) and the tool body
resolves the engine (`FIND_ANYTHING_BIN` → `fa` on PATH → legacy paths).

**6. Three clocks, on minutes nothing else uses** (`install-crontab-fragment.sh`, de-duplicated by
job name, before-image `/root/crontab.before-20261012T033202Z`):

 8,23,38,53 * * * * fa-index-refresh (builds the indexes; also the journal index)
 22 * * * * fa-index-freshness (MEASURES the indexes; exits non-zero when stale)
 47 * * * * tool-body-guard (every ACTIVE tool must have a body)

The first cut used `*/15` and `:37` and **collided** with the pre-existing `journal-commit` `*/15`
and `comms-refresh` `:37`, which measured a `ps_search what=journal` at **21,902 ms** — two journal
cache rebuilds on the same minute. Hence the odd minutes.

**7. New guard, `scripts/guards/tool-body-guard.py`** — every `status="active"` registry tool must
have `data/tools/<name>.py`. Exit `0` ok / `1` missing bodies / **`2` could not check, which is never
a pass**. `--selftest` proves it fails on a broken registry, passes on a fixed one, ignores
`deprecated` tools, and raises on an unreadable registry. Marked 7 phantom entries (registered
`active`, no body on **either** box — pre-existing self-programming noise, not migration loss)
`deprecated`. Result: **601 active tools, 601 with a body, 0 without.**

**8. Added the search subsystem to `docs/mesh/000-SYSTEMS-REGISTER.md`** as §2.5. It was absent, which
is why the cutover carried none of it and why the next agent would rebuild it (AGENTS.md §0).

**9. Registered `search`** in the tool registry (609 tools now). It was never registered even on the
office box — callable only by name via the dispatcher's `_exec_dynamic_tool` fallthrough, and
invisible to every agent that had not been told.
