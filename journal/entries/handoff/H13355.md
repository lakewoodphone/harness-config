### The four defects a device found that a desk could not
1. **The update alarm was never re-armed after a reboot.** `ensureScheduled` trusted the stored
 `nextCheckAtEpochMillis` and returned early while `AlarmManager` had forgotten the alarm at reboot —
 a sealed phone that restarted once would never check for updates again. Fixed with
 `ensureScheduled(force = true)` from `BootReceiver` and `FilterApp`; proved on an emulator
 (`APP_UPDATE_PERIODIC_CHECK` present after a reboot, no UI launch).
2. **The seal needs a settled device.** `dpm set-device-owner` right after install is refused with
 "already some accounts" while `dumpsys account` says `Accounts: 0`; it succeeds ~30 s later. The
 runner retries at 0/10/20/30 s, re-clearing the flags, and records which attempt landed.
3. **A sealed app that was never opened has no runtime state** — no VPN service, no alarm, no records.
 The runner opens the app after sealing.
4. **The boot broadcast lands tens of seconds after `sys.boot_completed`** — the alarm was genuinely
 absent at +25 s and present minutes later, so a single `dumpsys alarm` read was a false FAIL. The
 runner polls for a minute.

### Operational lessons worth carrying
- Emulators on this machine die under load and leave stale `*.lock` files in
 `~/.android/avd/<avd>.avd`; clear them, and expect `emulator-5554 offline` after a heavy fleet.
- `adb shell dumpsys alarm | grep` must be pulled to the host and searched there — `shell grep` on a
 redirect fails (`Bad address`).
- A run record written into the repo is a **document** to the docs gate. The acceptance record now goes
 to the OS temp directory.
