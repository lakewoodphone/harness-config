# H (2026-10-20, round 18) - the manual-vtable probe rules out CLR marshalling; the pointer itself is now the suspect

## What run seven did
Item 813's remaining question was "why does `GetDesc` fault against a non-null duplication pointer". The decisive
discriminator is whether the fault is the CLR's marshalling or the pointer/slot. So a temporary probe called
`GetDesc` through a **manual vtable pointer**:

```
IntPtr vtbl = Marshal.ReadIntPtr(duplicationPointer, 0);
IntPtr slot = Marshal.ReadIntPtr(vtbl, 3 * IntPtr.Size);
var fn = Marshal.GetDelegateForFunctionPointer<ProbeGetDesc>(slot);
fn(duplicationPointer, out desc);
```

Result: `Test host process crashed : Fatal error. System.AccessViolationException`, with no PROBE line - the fault
happens at the manual call itself. **So it is not the CLR's marshalling of `GetDesc`.** That shifts the suspicion to
the pointer: a non-null pointer returned by a call that returned `S_OK` can still be garbage if the slot called was
not `DuplicateOutput`.

The probe was removed before anything was committed; the tree is clean and the suite is unchanged
(`Passed: 374, Failed: 0, Skipped: 12, Total: 386`).

## The next probe is specified, and it must be one run
Each interactive run costs a console window on the owner's desktop, and seven have now been spent. The next one
should answer several questions at once: dump `vtable[0..8]` addresses of the returned pointer, resolve each to the
**module** it lives in (DXGI or something else), and print the raw pointer value. If those slots are not in
`dxgi.dll`, the pointer is not a duplication object and the suspect is the vtable index this declaration resolves
`DuplicateOutput` to - which means re-counting `IDXGIObject` and `IDXGIOutput`'s members against `dxgi.h` rather than
trusting either the C# or my memory of it.

Hard constraint recorded on the item: **do not reorder `IDXGIOutput1` again.** `dxgi1_2.h` puts `DuplicateOutput`
