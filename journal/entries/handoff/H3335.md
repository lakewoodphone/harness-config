## 2026-10-08 03:55 UTC · ZABZ-YOGA · Root cause of the unlinked card payments: the order IS threaded into the Stripe intent, but the counter never selects one - and the webhook that should settle the row never does

CHANGED — the root cause of the unlinked payments, located in the website repo (read-only)

**The chain, from the code, not from inference.**

1. **`backend/src/services/payments/terminal.service.ts:372-377`** builds the Stripe payment intent:
 ```js
 metadata: {
 ...input.metadata,
 ...(input.orderId && { orderId: input.orderId.toString() }),
 readerId: input.readerId,
 transactionType: 'terminal',
 },
 ```
 The order IS threaded through - **conditionally**. If the caller supplies an orderId it lands in the
 intent metadata and everything downstream can link.

2. **`backend/src/trpc/routers/payments.ts:147-190`** makes it optional by design: the input schema
 takes `orderId` and `staffNote` as optionals, and the only validation is
 `if (!value.orderId && !value.staffNote?.trim())` - i.e. **an order id OR a free-text note**.

3. **What the live charges actually carry:** `{"readerId": "tmr_GavzfgCDIyZ9pN", "transactionType":
 "terminal", "staffNote": "Button"}` and, on others, `"staffNote": "diagnosing fee"`, `"diagnosis"`,
 `"e4610 charging port taplin"`. **No orderId.** So the counter is taking card payments with a
 free-text note and no order selected - which is exactly why 47 of 129 settled charges in 60 days sit
 on a local row that names no order.

**SO THE ROOT CAUSE IS A WORKFLOW, NOT A BUG IN THE LINK.** The link works. The counter does not
choose the order, because it does not have to. Anything that fixes this has to make the order part of
taking the money, or make the note a picker instead of free text.

**THE SECOND HALF, and it is the one that makes the numbers meaningless:** these rows sit `PENDING`
while Stripe says `succeeded`, and a webhook for exactly that exists -
`backend/src/services/payments/webhook.service.ts` handles `payment_intent.succeeded`,
`payment_intent.payment_failed` and `charge.succeeded`. So the settlement path exists on paper and does
not settle these. Either the endpoint is not receiving these events, or the handler does not match
rows created this way. **That is where to look next, and it is testable in one query**: take one
PENDING row with a known-succeeded intent and trace whether the event ever reached the backend.

NEXT (for whoever picks this up - do NOT start editing: another session has
`phone-and-tech-full` checked out on `feat/owner-text-gate` with dirty files)
1. Query the webhook/event log or the backend's own logs for `payment_intent.succeeded` around
 2026-09-24 19:55Z (charge `ch_3UJIjWLnlgYj1gmT1urGuywt`) and see whether it arrived.
2. If events arrive and rows stay PENDING, the handler's row-matching is the defect - a one-file fix.
3. If events never arrive, check the Stripe endpoint configuration and its secret against the deployed
 backend. That single fault would explain every PENDING row found tonight.
4. Then, separately, make the order a required part of taking a card at the counter.
