## WHY THE FREEZE TOOK 2 h 40 min INSTEAD OF 25 min

1. **My own outage first (02:14-02:40).** A 14.2 GB / ~200k-file `rsync` of `data/` run on the
 office box WHILE IT WAS SERVING took load to 52 on 4 threads, 99 % iowait, sshd silent while
 `tailscale ping` answered, API 502 for 20 min. See `H3406`, `P2936`. **The rule "never run heavy
 DB work on the office box" is a property, not a list of four commands, and a bulk read is on it.**
2. **`systemctl mask` cannot work here.**
 `Failed to mask unit: File '/etc/systemd/system/secretary-api.service' already exists` - mask
 symlinks the unit NAME in /etc/systemd/system and the unit file already lives there. `disable` is
 what does the job.
3. **The watchdogs restarted the services.** After the first stop, `secretary-api` was
 `ActiveState=active` again 90 s later with a new MainPID. The timers AND their `.service`
 siblings must both be stopped and disabled.
4. **The units are NOT the writer set - this is the expensive one.** With every unit down, four
 free-standing jobs still held the database: `presence-runtime/sampler.py`, `store-write-check.py`,
 `/tmp/dialpad-harvest-*.py`, `dialpad-call-fresh.py`. They are spawned by the **crontab, whose
 ~90 jobs carry base64 command blobs** - which is also why `cron-target-guard.py` reports
 "ok / 0 missing": it never decodes them. **Stopping cron is the actual boundary of a freeze.**
5. **A `sqlite3 .backup` wedged** against those writers: output stopped growing at 4,741,529,600 B
 while its mtime kept advancing, because the backup API restarts whenever the source changes
 under it. Re-run on a quiet box it took 1,495 s and produced SIZES EQUAL.
6. **The IPv4/IPv6 loopback trap, which the whole post-check missed.** The tunnel's ingress said
 `service: http://localhost:8002`. `/etc/hosts` maps `localhost` to `127.0.0.1` AND `::1`, and
 cloudflared picked **`::1`**. The dashboard survived because `next start -p 3000` binds `*` (both
 families); uvicorn binds **`127.0.0.1` only**, so the tunnel dialled a socket nothing listened on
 and Cloudflare answered **502 while the API was perfectly healthy on its own loopback**. Pinning
 every origin to `127.0.0.1` fixed it instantly. **`ai./health` is served by the dashboard's own
 proxy, so it answered 200 the whole time and could not have caught this** - only `api.` could, and
 only after the pin.
