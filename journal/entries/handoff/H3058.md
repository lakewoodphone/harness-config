**B1 — the tuner spent ONE SESSION PER SUBJECT.** Measured: the wake store held **14** rows with
`source=wake-tuner` in one day — one `wake-cost-digest:<day>` plus **twelve** `wake-cost-tune:<subject>`.
A release is a whole headless session, measured at ~0.026 USD and ~1.4 M tokens, so that was 13-14
sessions a day to deliver one tuning report.
*Why the obvious fix is wrong:* the finding cooldown is `WAKE_TUNER_MAX_COOLDOWN_SEC` = 604800 (7
days), so simply re-filing the digest when a change appears returns `suppressed:cooldown` and the
change is **silently lost** — the exact shape this system keeps getting hurt by.
*What was done instead:* the tuner runs every 15 minutes and `persist()` absorbs each movement into
`subjects` immediately, so a movement is visible to exactly ONE run. Changes are therefore CARRIED:
`collect()` emits ONE finding per day, whose prompt carries a `THRESHOLD CHANGES SINCE THE LAST
DIGEST` section built from `changes_unreported` + this run; once the day's digest has gone out,
`collect()` returns no findings at all and `persist()` keeps them carried for the next digest. The
delay is safe by construction — the change is applied through the state file, and the flag is only
the REVIEW.
*Reproduced, not assumed:* `_recon/test-tuner-one-flag.py` — (A) digest already emitted → **0**
findings (was one flag per changed subject); (B/C) digest not emitted → **exactly 1**, carrying a
change the digest had not yet reported; (D) zero `wake-cost-tune:*` subjects anywhere; (E)
`_merge_changes` dedupes to ONE entry per subject and takes the LATEST. **VERDICT: PASS.**
Live: `wake-tuner.py --dry-run --force` printed `flagged wake-cost-digest:20260929` — one finding —
with **127 wake rows before and 127 after**, so nothing was filed in a dry run. Regression re-run
after the B4 edit: still PASS.

**B2 — the daily cap was TWO numbers.** The module docstring said `WAKE_MAX_PER_DAY (12) guard 3`;
the code sets `DEFAULT_MAX_PER_DAY = 500` and live stats reported `max_per_day 500`. A reader would
believe the loop was capped at 12/day when it is capped at 500 — a 41x error in the direction that
HIDES a runaway. The comment beside the constant already names the real limit: the owner set a 70
USD/day spend ceiling himself, *"But it's not like how many times."* Volume is not the limit; waste
is. The docstring now reads 500 and says it is not the limiting guard.
*After:* `released today: 134/500` with `max_per_day 500`, and the docstring agrees.

**B3 — `released_today` was a session counter sitting among work counters.** It reads
`wake_budget.released`, incremented once per release. **I quoted that number as throughput in this
session's first report before checking it** — 132 — while the dispatch log named only 41 distinct
wake ids and `project:lpt-website:20260929` went out **20 times, all exit=0**. That is the
misreading this fix exists to stop. The counter is now named where it is defined, in the JSON
payload (`released_today_means`) and in the human line.
*After:* `released today: 134/500 [SESSIONS started, not work done - one row can be released many

**B4 — TWO NUMBERS FOR ONE DAY, and nothing said which to believe.** At 18:57Z
`wake.py stats --json .spend_today_usd` = **1.224594**, which I reproduced by hand as the sum of
`cost_usd_or_unsourced` over the **41** `type=release` rows whose `started_day` is today. The
tuner's digest reported **0.997373** over "37 priced" — its own `type=spend_today` SNAPSHOT row,
written by an earlier `wake-cost.py` run. The gap is **staleness, not arithmetic**, and the live
sum is what the 70 USD/day cap enforces, so it must stay live.
*I nearly reported this as a double count and was wrong:* `spend_today()` keys on `started_day`,
and my first pass counted the `day` field, which is absent on release rows. Reproducing before
claiming is what stopped a false finding.
*Fix:* name the authority rather than add a third sum — the digest now prints `cost source .......`
