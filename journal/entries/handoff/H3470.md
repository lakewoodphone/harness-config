## THE BUG FOUND AND FIXED THIS ROUND

`run_power_up` did no restoration at all when the plug already read ON — and
that is the path that actually runs at motzei, because the plug turns itself on
from its own device schedule before the one-minute watchdog looks. On that path
it silently skipped:

 * the interior-door relock,
 * re-enabling `automation.phoenix_interior_maglock_tamper_restore`, and
 * the ceiling-light re-assert.

All three are exactly what a Shabbat run leaves undone, and **nothing retried
them until the following Friday**. So the interior door could have stayed
unlocked and the owner's own tamper automation stayed switched off for a week —
a security defect found while working on a lighting requirement.

Fix: `_power_up_critical` now restores power only if it is not already on, and
then ALWAYS relocks the door, restores the guard rails and re-asserts the light.
`run_power_up` is a plain delegation, so no path can skip that work. The entire
sequence is idempotent.

## PROVEN TO DISCRIMINATE (the check I failed to run in round 3)

Round 3's lesson was that a regression test passing without the fix proves
nothing. This round I ran the discriminating check explicitly, in-process with an
argument list and no shell quoting:

```
WITH fix exit=0 1 passed
WITH OLD behaviour exit=1 1 failed
restored exactly: True
```

The test that previously asserted the OPPOSITE for the door
(`relock.assert_not_called()`) is replaced — that assertion *encoded* the bug, by
treating "the plug is on" as evidence the door work was done or unnecessary.
