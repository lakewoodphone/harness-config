Different date, different host, different subject. A session that opens H3393 learns one story or the
other depending on which checkout it happened to land on -- and the journal's whole contract is that
an id means ONE thing.

WHY MY EARLIER UNION MISSED IT, AND WHY I OVERCLAIMED. In this program's first pass I merged 149
entries that existed only on the authority and 341 that existed only here, and for each I verified
that the added id had no base id already present. **That is a guarantee about the entries I ADDED. I
never compared the content of the ~3,300 ids present on BOTH sides** -- which is where all 122 of
these live. Then I reported "the journal is one record" three times, on the strength of a count that
matched.

So the correction is stronger than H3623 said. It is not only that the consolidation is not
self-maintaining. It is that **the consolidation was incomplete when I declared it, and the number I
quoted as proof was the one number that could not show it.**

WHY NOTHING HAS CAUGHT IT: `journal.py check` validates ONE tree. An id that means two things is
exactly the error it exists to catch ("one id meaning two different entries"), and it reports ZERO
errors on both trees -- correctly, because this defect is only visible when the two trees are compared.
No check in this estate compares them. `journal-union.py` now does, and refuses.

WHAT IS **NOT** AT RISK: no entry has been overwritten or lost. Union only adds. Both texts still
exist, one per tree. The damage is that they are filed under one name.

THE FIX, for a session that can do it carefully: 122 ids need renumbering with aliases recorded --
which is what `journal.py repair-ids --apply` does, and it must be run per tree with the OTHER tree's
text treated as the alias holder, not as a duplicate to drop. 122 renumbers is not a thing to attempt
at the end of a long session, and guessing which copy is authoritative for each would manufacture
exactly the confusion this finding is about.

RECORDED, NOT FIXED. Handoff, not a claim.
