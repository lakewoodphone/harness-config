### What the session got right, so a successor does not dismiss it

The scheduling gate is **live and correct**. Pre-registered `kept=7 / deferred=25` at 23:53Z; the
first in-peak tick at 01:25:57Z and the second at 02:26:38Z both matched exactly. Its own verifier,
run by me at 04:00Z, agrees: **250 deferrals across 10 activity rows, `agents_ticked=7`, MATCHES.**
Cost accounting is exact (93 of 98 rows to 1e-9). It refused three times to "fix" something it
could not explain and wrote the gap down instead.

### The four lessons worth carrying, in the order they cost time

**1. An instrument that has never emitted a single line is not evidence of absence.** The session
instrumented the wrong place twice, diagnosed that correctly, moved the instrument to the shared
callee (`ai_gateway.prepare_request`) — and that one emitted **zero lines in all time across 53
calls**, with the flag proven in `/proc/<pid>/environ`. Measured now: deploy mtime
`03:37:04.0626`, process start `03:37:03.760` (**303 ms earlier**), `startup complete` 03:37:09,
1,296 journal lines in 25 min, `agent_worker:3806` is the only model call site and it does call
`prepare_request`. Two possibilities remain and nobody has distinguished them: stale module, or
`print()` not reaching the journal from this process. **Run one positive control before reading
silence as a finding.**

**2. A restart is a policy change.** The measured block was 01:00–04:00Z. `company-api` restarted
at **03:15:25, 03:17:27, 03:20:58, 03:27:37 and 03:37:04** — five times inside it. The session had
the discipline to refuse to switch the priority ladder inside the window ("it would mix two
policies") and then deployed four files, enabled pruning and restarted anyway. Its own verifier now
prints `CONTAMINATED … Do NOT read the deltas above as a result.` **The only controlled comparison
it spent four hours building is void.** Do not deploy *code* inside a window you are measuring.

**3. Deployed-and-inert is not progress.** Twelve artefacts landed "built, tested, deployed,
inert". After six hours, exactly **one** production behaviour changed: `SCHEDULE_MODE=cheap-first`.
That is not 100 % of anything, and it was the mandate the owner gave at 02:56Z.

**4. The real prize was 7× the stated one.** The brief aimed at the clock (42.6/month measured).
At round 31 the session found every call carries a **34k–45k token prompt at a 0.01 % cache hit**
around a 700-token stable head — its own arithmetic put that lever near **300/month**. It located
the cause and never fixed it. When a project's stated prize is small, check what the measurement
that produced it also found.

- `LLM_DAILY_BUDGET_USD=5.0` is real and **unenforced on most calls**: ~16/day book-priced,
 ~35/day on the counter the budget reads. Owner-queue **#860**, open.
- **The branch `feat/cheap-hours-routing` has 80 commits and no remote.** `git branch -r --contains
 HEAD` is empty. It exists only on ZABZ-YOGA.

### Defects found in the session's own tools, by running them

- `peak_verification.py` reads `SCHEDULE_CHEAP_SHARE_TARGET` **from the shell it runs in (0.8)**
 while production runs **0.86** — it reads the wrong source.
- The same tool prints `cheap input share 0.00 % NOT MET` while measuring a window that lies
 **entirely inside the peak band**, where 0 % is the definition of the window, not a failure.
- Its docstring names the control window `2026-10-12` and calls it "also a Monday"; the code
 correctly computes `2026-10-13`. Code right, comment wrong.
- At 01:12 the tool recorded **0 ticks and a −87.1 % cost delta** — an incomplete window that reads
 exactly like a huge saving. Its own guard text is the only thing that stopped that.
