## 2026-10-18 21:05 UTC · ZABZ-YOGA · Estate search round 21: scoped searches were returning false negatives; two clever fixes measured and thrown away

## 2026-10-18 · ZABZ-YOGA · Estate search round 21: every scoped search was returning false negatives; fixed, and two clever fixes thrown away

Continues **H8493**. Commit `27ff430`.

## The bug, and how bad it was

`printer` exists in 24 journal chunks. `scope=journal` returned **zero**. The same for `disk` and
`customer`. The cause: a scoped search asked the core for the **global** top 240 hits and filtered them
to the corpus afterwards — so a journal document lost to 200,000 file documents before the filter ran,
every time. Any corpus small relative to the files index was effectively unsearchable through a scope.

**Fixed by running the search scoped**: a prefix naming one source is passed through as that source; a
prefix naming several (mail:) is searched once per source and merged, so each corpus contributes its
own best.

Verified, before → after:

 printer / journal 0 -> 3 42 ms
 disk / journal 0 -> 3 706 ms
 customer / journal 0 -> 3 3436 ms
 refund / data 0 -> 3 143 ms
 zzqqxxnotaterm / all 0 -> 0 15 ms (negative control still zero)

## Two fixes I built, measured, and removed

Both are recorded in the file so nobody rebuilds them:

1. **An OR fallback** for questions phrased as sentences. An OR **with a source filter** costs
 **13.7 s**: SQLite walks the whole posting list and joins it against one corpus. AND with a filter
 costs 10 ms. The fallback never shipped.
2. **An exact-match gate** to skip the core's unranked scan. The same SQL ran in **10 ms** against
 SQLite directly and **5–10 s** through the service — three consecutive calls: 10.3 s, 5.0 s, 8.4 s.
 A second slow path dressed as an optimisation. Removed, with the measurement written where it was.

**What remains, honestly:** a three-term AND that matches nothing in one large corpus costs about 5 s
inside the core's own scan, and a common single term (`customer`) costs 3.4 s on a small corpus.
Ordinary one- and two-word queries are 15–250 ms. That is inside "answers in seconds" but it is the
slow corner, and it lives in `usearch.py`, not in the service.

## The pattern worth keeping

Three times this round I shipped a fix before measuring what it cost, and each time the fix was slower
than the bug. The measurement that settled it was always the same shape: run the candidate SQL directly
against SQLite and time it, *then* decide. The 10 ms / 13.7 s table took one script and five minutes;
the three deploys before it took forty.
