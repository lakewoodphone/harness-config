## CHANGED (all verified by running, not by reading)

**1. `test_client_parity_goldens.py` — the filter wire format is now guarded on all three clients.**
One format, four implementations (Python serves it; Swift and Kotlin decide from it). Two guards
existed and **nothing ran either**: `ios/tools/bloom_golden_vectors.py` (emits the server's own
answers; has `--check`) and `ios/tools/prefilter_golden_vectors.py` (cross-checks MurmurHash3
against `mmh3`, and **refuses to write when mmh3 is absent — and mmh3 was in no requirements file**,
so in CI it could not run at all). The Android goldens were three server payloads hardcoded into
`DomainBloomFilterPayloadTest.kt` with nothing re-deriving them. The new test runs both iOS checks
and re-derives the Android payloads from `build_bloom_payload`, and asserts the Kotlin goldens were
actually FOUND so it cannot pass vacuously. `mmh3==5.3.1` added to `requirements-dev.txt`.

Proven non-vacuous twice, and the first attempt taught something: changing the builder's *default
seed* left everything green — correct, because the payload is self-describing and a client reads
`params.seed`. Swapping the two hash halves (which changes the bytes) turns 3 red, including the iOS
check. **A second trap: my first hash break used `return (lo, hi)`, which does not exist in that
file — the replace silently did nothing and the "pass" meant nothing. Count the pattern before
believing the result.**

**2. `deploy/broker/ops/verify-broker.sh` — it cried outage on every restart.** Immediately after
`up -d` it printed `health FAILED`, `CONNECT FAIL 1080/8443` and an unreadable route count against a
broker that was merely still binding (healthy 11s later). The README tells you to run it right after
the swap, so this happened *every* deploy, and it invites somebody to "fix" a healthy system. It now
waits for readiness first and says when a failure is real. **The first version of this fix put the
wait too low and the route count — read further up — still raced; the restart round trip caught it.**

**3. `canary.py` — the deny check probed the one port where refusal is not how denial works.**
Production logged every hour: `Canary probe failed: domain=pornhub.com reason=denied_domain_connected`
— the filter's own alarm claiming a leak. It was false. Measured on the live box, two independent
probes:

| target | result |
|---|---|
| `pornhub.com:80` | `0x00` granted, then `HTTP/1.1 302 Found` → the block page |
| `pornhub.com:443` | `0x02` DENIED by ruleset |
| `bet365.com:443` | `0x02` DENIED |
| `example.com:443` | TLS completed, real `200 OK` (allow-listed) |
| `wikipedia.org:443` | `0x02` DENIED (`default_policy` is DENY, so correct) |

The broker's own code says why: `if dst_port == 80: serve_block_page_redirect(...) else:
send_reply(rep=0x02)`. The check probed 80 and read only the reply code, so it was **structurally
incapable of passing** — it turned every real prevention into an apparent leak. That is worse than a
noisy alarm: it destroys the signal, so nobody could tell a genuine bypass from the standing false
positive, and the one control that answers "is blocking working?" had never once answered it. Now it
probes 443; a test pins the port. **After deploying the fix, the new container logs no canary failure
at all** (every previous start logged one).

## THE FINDING THAT MATTERS MOST, AND IT IS NOT FIXED

`lpt_filter_ai_api_b` **failed its first boot after the swap** and only Docker's restart saved it:

```
File "/app/app/startup_validation.py", line 594, in validate_startup
 raise RuntimeError(msg)
RuntimeError: Integrity anchor chain verification failed at startup: access_requests, decisions
```

16:55:54 died → restarted → 16:56:06 came up. The file itself is clean afterwards (`ops/anchor-order.py
probe`: 380 rows, no inversions, no record_count regressions), the twin is a non-writer
(`LPT_INTEGRITY_ANCHOR_ENABLED=false`) and the primary has never failed it.

My first two explanations were both wrong and the evidence killed them: it is **not** the blocklist
DownloadTimeout (that is a separate, caught traceback at 16:57:06), and it is **not** a torn tail —
a partial last line becomes an `invalid_json` record which the verifier skips, not a chain mismatch.

What the code and the timing point to: **two instances share one SQLite file.** The primary publishes
an anchor for the tables that receive writes at boot (`access_requests`, `decisions` are exactly what
startup logs into), the twin verifies concurrently against the same file, and the comparison at the
anchored prefix sees a prefix that does not yet include what the anchor was computed over. It is
deterministic once writers quiesce, which is why the second boot passed. This is consistent with the
3,322 `database is locked` events already recorded as a pain.

**Cheapest correct fix, not yet done:** retry the startup verification a few times with a short
backoff before failing closed. A real tamper still fails every attempt; a race resolves. That
preserves the fail-closed property exactly and removes a boot that depends on luck. Then the
architecture question — whether HA should mean two processes on one SQLite file at all — deserves the
owner's attention, because it is the same root as the lock storms.
