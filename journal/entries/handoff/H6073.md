## 2026-10-15 · ZABZ-TECH · E4610/E4810 "data messaging is slow or dead": diagnosed, calibrated, plan written, test NOT yet run

**Read first:** `lpt-flip-phone/docs/incidents/E4610_E4810_MMS_DIAGNOSIS_AND_AB_PLAN_2026-10-15.md`
(new, untracked — written 2026-10-15). It carries the inventory, the evidence table and the A/B plan.
**Correction to H3634:** that entry implied the E4610 device YAML makes the deployer write Message+ as the
default SMS app. It does not. `e4610.yaml:sms_app` feeds only the *verification* acceptable-set
(`verification.py:330`); the actual write happens via `message-plus.yaml:29-33`'s `set_default_sms` action,
which is scoped `devices: [E4810, E4811]` — so **E4610 is never written at all** and simply inherits Message+
from the factory. The conclusion survives; the mechanism in H3634 was wrong.

### The verdict, calibrated against outside evidence
The delayed/never-sent picture-MMS failure on these handsets is **real, and not invented by our filter**: it is
documented by outside users on **stock, unfiltered, Verizon-direct** E4610s and Cadences since at least
2025-04, with the community cause named as Message+ app state plus Verizon MMSC device verification (mms
User-Agent / unrecognised MMS profile). But we aggravate it on E4810 and we hide it everywhere:

- **`cli/lpt/deployment/engine.py:633-635`** disables the configured fallback (`com.android.mms`, from
 `message-plus.yaml:33`) right after setting Message+ as default. **Live from 2026-08-31** — bracketed by
 receipts (`...-20260827-191311.yaml` reads `(fallback:com.android.mms:probe-failed)`, and from
 `...-20260831-181241.yaml` onward every one reads `stock fallback disabled (com.android.mms)`).
 **7 receipts across 4 E4810 serials** (558800024668/558800182088/558800238329/558800639218). Newest 2026-09-07.
- **The owner's 2026-09-09 rule "NEVER disable stock Messaging" is enforced only in the manual script**
 (`scripts/deployment/Set-E4810Messaging.ps1`, WT, the line removed with a comment citing the decision) and
 **violated by `engine.py`, which is what automated deploys run.** `cli/configs/tiers/standard.yaml:13` still
 installs `message-plus`, so the uncommitted `e4810.yaml` fix does not take effect.
- **E4610 ships NO `com.android.mms` at all** (only `MmsService` + `VZMessages`), and `standard-lite` never
 touches the SMS default → Message+ is unavoidable and the only remedy (clear app data) is the one our filter
 makes hard. Verified in `data/device-profiles/E4610/packages_all.txt`.
- **Cleanest single proof the deploy makes the switch:** same E4810 serial 558800298976 — factory 2026-02-26
 `com.android.mms`, after our deploy 2026-05-27 `com.verizon.messaging.vzmsgs` with `com.android.mms` disabled
 (`logs/diagnostics/e4810-558800298976-20260527-120536/`).

### The harness cannot test what he asked for — do not run it as-is
`scripts/utilities/{New,Invoke,Export}-MmsForensicRun.ps1` has **zero pass/fail logic** (`-Expected` is echoed,
never compared: `Export:44`), **records no send time** so it cannot compute a latency, **requires three phones**,
and **crashes whenever it finds evidence** — `Export-MmsForensicReport.ps1:76` uses `${step_id}` where the loop
var is `$s.step_id`, which throws under `Set-StrictMode -Latest` (`:18`). `data/mms-forensics` does not exist
and no run artefact exists anywhere → appears never completed a run. Fix those four things first.

### Durable facts worth not re-deriving
- **A prior E4610 filter-vs-control comparison is junk evidence:** `docs/testing/results/2026-03-23-e4610-filter-vs-control.md`
 is a PASS built on "no obvious slowdown", with **all 33 timing cells "Not recorded"**. Never cite it as proof.
- **The repo's test suite is red on the working tree: 7 failed / 24 passed** (`cli/tests/test_device_configs.py`
 + `test_config_loader.py`, repo's own `.venv`). One failure is provably the uncommitted `e4810.yaml`.
 The clean-HEAD comparison **could not be measured** — a fresh clone's pytest dies with
 `FileNotFoundError: No usable temporary directory` even with TEMP/TMP/TMPDIR set and a basetemp given.
 Unresolved; do not claim HEAD is green *or* red.
- **There is no sales ledger.** `products` has 0 Kyocera SKUs; `SALE` orders = 7 lifetime (617 REPAIR);
 `donor_phones`/`inventory_items`/`offline_transactions` = 0. So "how many phones" has **no denominator** —
 the honest answer is "cannot be counted", never a guess.
- **`Set-E4810AttApn.ps1` writes an AT&T/H2O APN** (MCC/MNC 310/410, `mmsc.mobile.att.net`), has **no caller**,
 refuses unless the SIM is 310410, and drives the APN editor blind (can overwrite an existing row). Its
 verification reads only the *data* APN, so it can print green with MMS dead. Not excluded — second candidate.
- **`docs/sms-restrictions/**` points at `scripts/utilities/set-messageplus-incoming-only.ps1`, which does not
 exist there** — the only copies are in `legacy/`. The documented procedure is unrunnable.
- **Twilio MMS IS available**: `+17324447361` has `mms:true`, two `MediaUrl` senders exist, inbound replies are
 readable. `send_sms` is owner-only by policy (`app/config.py:1039`) and `TWILIO_FROM_NUMBER` is unset — pass a
 sender explicitly. **Group MMS cannot go through it** (one recipient per message); Dialpad documents a `media`
 param but our code has never sent media and no MMS has ever been observed on it.
- **Complaint population:** 13 distinct customers / 16 contacts, 2026-08-04 → 2026-10-14, peak week 2026-10-05
 (6). One customer ((313) 648-0853, 2026-10-11) was **never called back** — an open loop worth closing.
