# H507 — round 23: three more defects found by trying to enable F04 — so F04 stays off

## THE HONEST HEADLINE

I set out to re-enable F04 against a known-11 set. **Each attempt to enable it found a NEW defect in the
surrounding wiring**, not in the matcher that everyone — including me — was watching:

**1. A fix was reading another check's rows.** F04 declared `check: C14` but built its payload from rows
whose evidence is **C02-shaped** (`{case_id}`, no `matched_case`). Result: **208 proposals**, each
carrying the record's own `sync-records/*.json` path as the "target". **One `--apply` would have
rewritten 208 customer records to point at nothing.** The binding between a fix and its findings is now
enforced at the point of use, not trusted to a registry field.

**2. A partial match was treated as a pair.** C14 states its own ratio ("1/4 name tokens match") and F04
acted on those too — proposing `asus-vivobook-f512ja-klein` → `asus-w202na-kaplin-2026-08-12.md` because
both contain the token **"asus"**. A repair firing on 1 of 4 tokens is not a repair. The ratio must be
**n/n**.

**3. A dry run was writing to disk.** F04's backup was created *before* the `if not apply: continue`
exit, so a dry run that changed nothing else still littered the corpus with **226
`*.sourcepath-backup` files**. They were untracked, so `git status` showed a clean tree at commit time
and the litter survived **two rounds unnoticed**. Moved after the exit; the 226 files deleted.

**Effect of (1) and (2): proposals 208 → 15.**

## AND ONE I DID NOT FIX

**The orphan-vs-orphan guard does not work.** Two orphans can target the *same* case —
`2026-08-24-kaplan-laptop.json` and `laptop-kaplan-2026-08-24.json` both point at
`kaplan-laptop-data-retrieval-2026-08-24` — and the `claimed` set only covers cases that *already
resolve*, so neither is claimed and both pass. I added a shared-target pass to demote them to
collisions; **it is not taking effect**, and 4 duplicate targets survive in the proposed set
(11 measured repairable where F04 proposes 15).

`lpt-hub 1c33b37b6` → `e05ba6f59` → `2ce97fd69`, all pushed, tree clean.

## F04 STAYS `writes: False` — THIRD ROUND HELD

Not because of the matcher any more, but because **enabling writes has been attempted three times and
each attempt found a *different* defect in the surrounding wiring.** A fix that has been wrong three
times, in three different places, has not earned a write.

**The order is fixed: make the duplicate-target guard work → re-measure → then enable.** Holding it costs
nothing — the diagnosis is shipping and the finding is on the page either way.

## THE PATTERN WORTH KEEPING

Three rounds on one repair have produced: a 226-file diff, a 183-correction over-fire, a 208-proposal
mis-binding, a partial-match false pair, dry-run litter, and an ineffective guard. **Every one was found
by attempting the action rather than by reasoning about it.** The matcher — the thing I kept fixing — was
never the only problem.

That is the argument for the discipline I have been applying: **the fix and the enable are separate
steps, and the second one needs its own evidence.**
