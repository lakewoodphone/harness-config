`app/services/lpt_hub_sync.py` — the authoritative lpt-hub resolver, strengthened and made audible.

**Why this is the right target:** this module is the resolver everything else imports
(`lpt_hub_link_orders.py:304` imports `fetch_sync_records` from it), and its
`_candidate_local_repo_roots()` already does the one thing that makes it work on both hosts —
`Path(raw).resolve()`, which canonicalises a **Windows junction** and a **Linux symlink** alike. That
is why this resolver always worked while
`scripts/lpt-sync-to-production.py` (hardcoded `C:/Users/ezabz/Code/lpt-hub`) and
`chat_agent_review.py` (bare CWD candidates) each worked on exactly one host by accident.

**Two checks were missing, and all three resolvers had the same hole:** every one of them already
verified that the sync-records subpath existed. Added:
- `git rev-parse --show-toplevel` must equal the root — proves the directory **IS** the repository,
 not a mount *into* another one nor a partial copy;
- `.git` must be present — catches a tree copied without its history, which would otherwise resolve
 happily and serve stale content forever.

**Rejections are now logged, not swallowed.** A candidate that fails validation is the interesting
case, because that is where a wrong-corpus bug comes from; each rejection says which check failed, and
an unresolved corpus logs its **full candidate list** rather than returning a bare `None`.

**Freshness is reported in both directions.** `describe_local_repo_root()` gives the path, the commit
and the drift from origin — because `lpt-hub-refresh.sh` pulls from **origin**, so a clone that is
**ahead** holds case work no other machine can see, and one that is **behind** serves stale content.
Neither was observable from the application before.

Verified on both hosts, same canonical repo:

**Scope, stated rather than implied:** this consolidates and validates the **authoritative** resolver.

## A CORRECTION TO MY OWN EARLIER FRAMING — the junction is NOT the sync cause

I had been carrying "the junction causes the two-corpora problem". **That is wrong, and checking it
was worth the round.** `lpt_hub_link_orders.py:458` writes through `_gh_write_file`, a **GitHub
Contents API** call against `lakewoodphone/lpt-hub` — the **REMOTE**. No local checkout is involved,
so the junction is irrelevant to that writer, and the direct-to-main write is already disabled by
default (`1dd89830`).

The accurate position, separated into two things I had been conflating:
- **The sync defect is fixed** — the unattended write of customer records to `main` is off.
- **The junction is a LOCAL FILESYSTEM VISIBILITY hazard**, not a sync one: `rg` and .NET descend
 nothing through it from an ancestor root and exit 0. That is what `lptcase.py` now warns about
 (`8cb746a06`), and it is what my own earlier searches were silently subject to.

This is the third time this session that verifying a claim I was about to build on changed it. The
cost was one round; the alternative was designing against a cause that does not exist.
