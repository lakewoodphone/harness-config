## 2026-09-15 21:15 UTC · ZABZ-TECH · New windows open the tokenized URL; the 2026-09-15 auth-page failure is fixed and verified

CHANGED
- `harness-config/multi-window/dshw.ps1` (commit 4acbc7a): every window now opens the engine's
 TOKENIZED launch URL. New `Test-LaunchUrl` / `Resolve-WindowUrl`; the token is recovered from the
 engine's own `dsh web: <url>` log line when `state.json` is stale (the token changes on every
 restart); the clean origin is the last resort. `dshw doctor` gained a "window url" line and a live
 303 probe that reports a non-303 as a blocker.
- `docs/multi-window/ANALYSIS-AND-DECISION.md` §4 records the reversal and the measurement behind it.

WHY IT MATTERED
The owner's "open a new window" produced "dsh web authentication required; reopen the URL printed by
dsh web" three times on 2026-09-15 (17:00:35, 17:02:37, 17:03:46, profile `w9`). Commit 4d9a0ad
(2026-09-14) had opened the clean origin, which authenticates only through a per-profile cookie, and
nothing ever seeded that cookie.

VERIFIED
- `dshw doctor` -> "window url : http://127.0.0.1:3099/?token=<redacted> (tokenized)",
 "auth probe : token exchange -> 303 (accepted)", "no blockers".
- `dshw new` opened profile `w10` at the tokenized URL; its window came up titled "DeepSeek Harness"
 (the app), not the auth page. A window-title enumeration immediately after showed exactly one window
 still on the auth page: pid 47760, profile `w7`, launched 15:35 -- i.e. before the fix.
- A throwaway profile launched twice at the tokenized URL kept ONE window root and the SAME session id
 (`session-ea10e311`) both times, which is what the old comment claimed was impossible.

IN FLIGHT
Nothing of mine. The repo carries uncommitted journal entries from another session (D173, H295, H296,
L1602, L1603, P173) -- left untouched, not mine to commit.

BROKEN
Windows already displaying the auth page (at least pid 47760 / profile `w7`, plus the three `w9`
windows from 17:00-17:03). They cannot be repaired in place: that profile holds no cookie, so a reload
returns the same 401 page. Closing them is the fix; opening a window in `w9`/`w7` through `dshw` now
seeds the profile, after which a reload would also work.

NEXT
1. Push `harness-config` so ZABZ-YOGA and the rest get the launcher: any profile created after
 2026-09-14 on those machines has the same latent 401.
2. Machine-side detection: have `dshw health` enumerate window titles and close/reopen a window titled
 "dsh web authentication required - DeepSeek Harness" (see the pain entry for this session).
3. Remember the shipped-UI limitation: session choice is the profile's own
 `localStorage["dsh.sessions.current"]`, so a restored window shows that profile's last session and a
 brand-new profile can land on an empty session even though it authenticates.

EVIDENCE
`windows.log` 17:00:35 / 17:02:37 / 17:03:46 (three clean-origin launches on w9); headless screenshot of
a fresh profile = the 401 page; the same profile's LevelDB after two tokenized launches =
`session-ea10e311` both times; `dshw doctor` output quoted above.
