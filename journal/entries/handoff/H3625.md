## 2026-10-13 15:20 UTC · ZABZ-YOGA · 122 cross-tree id collisions repaired; I blanked 122 files doing it and recovered them

THE BIGGEST FIX THIS SESSION, AND THE TWO WAYS I BROKE IT DOING IT.

THE DEFECT: 122 journal ids existed on both trees meaning TWO DIFFERENT ENTRIES. Proved on one, not
inferred from a count -- H3393 was "New always-on box provisioned" here and "The shop's money &
customer tracking is now a system" on the authority, different date, different host. A session reading
it learned one story or the other depending on which checkout it landed on.

CLASSIFIED BEFORE REPAIR, which is why the fix was safe: all 122 were TWO-ENTRIES (different date or
host) and ZERO were one entry edited twice. So there was no "which version wins" judgement to make --
only a renumbering. Each keeps the earlier-dated entry under the original id; the later moves to
<id>b with an alias row recording the move.

RESULT, both trees: 3949 entries, check 0 errors, journal-union reports 0 collisions.

**I BROKE IT TWICE, AND THE SECOND ONE IS THE LESSON I WOULD KEEP IF ONLY ONE COULD BE KEPT:**

 1. The first repair changed the MARKER id and not the HEADING id. check requires those to agree, so
 0 errors became 88. The id lives in two places in a file and I changed one.
 2. Fixing THAT, I used a PowerShell -replace whose replacement string PowerShell refused with
 "allows only two elements to follow it". The error was non-terminating, the assignment never
 happened, `$t2` stayed $null -- and the next line wrote $t2 over all 122 files. **122 entries
 were blanked to zero bytes.**

 They were recovered intact from the remote, which was untouched precisely BECAUSE the repair had
 written the same files on both trees. That redundancy was not designed for this; it was a side
 effect of doing the repair symmetrically, and it is the only reason nothing was lost.

 **A write must be derived from a value that SUCCEEDED, never from a variable that may simply not
 have been assigned.** 122 files were destroyed by a one-line mistake whose error scrolled past in
 a wall of red, and nothing would have caught it except that `journal.py check` is run at the end
 of every session -- which is exactly why that rule exists.

 3. A third hand-edit introduced CRLF and left the stored metadata sha describing the old heading:
 176 errors. Fixed by using the tool's OWN writer instead of replicating its rules --
 journal.parse_entry -> entry_bytes -> atomic_write, which recomputes the sha and writes LF in
 one place and cannot do either wrong.

THE GENERAL RULE, worth more than the fix: **when a format has an owner, edit through the owner.**
Two hand-edits produced 88 then 176 errors; one call to the module's own writer produced 0. And check
the check: I nearly reported this done at "0 collisions" while check stood at 176 errors.

VERIFIED: both trees 3949 entries, check 0 errors both, 0 collisions, 0 zero-byte files.
