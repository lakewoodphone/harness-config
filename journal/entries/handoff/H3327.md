## DEFECT A — a successful phone payment left the order marked UNPAID (FIXED, unverified)

`paymentStatus` stayed `PENDING` while a SUCCEEDED payment existed. The Stripe-link path sets it
(2997 went to `CAPTURED`); the phone path did not.

**Root cause, found by V5:** `pay-before-pickup-webhook.service.ts:608-616` writes
`paymentStatus: deriveOrderPaymentStatus({total, amountPaid})` inside the settlement transaction.
The phone rail has three writers and none of them was that one — `recordPhonePayment` inserts the
transaction only, and `releaseForPickup` is deliberately the sole writer of `pickupReleasedAt` and
touches nothing else. So the money and the release were written and the status was not.

Fix: `syncOrderPaymentStatus(db, orderId, balance)` in `pay-by-phone-call.service.ts`, called from
`handleSuccessRequest` on the `recorded` outcome. Idempotent twice over — the value is derived from
the ledger rather than incremented, and it sits behind the same `recorded` gate as
`consumePayCode` and `releaseForPickup`.

## DEFECT C — the branded `/pay/<uuid>` page CANNOT TAKE A CARD, and never could

**`StripePaymentProcessor` in `frontend/src/features/payments/pages/PaymentPage.tsx:629-682` is a
STUB.** Its only action logs a line and displays *"Card payment processing is not available at this
time. Please use Zelle or contact the shop directly."* No Elements, no publishable key, no confirm.
The production bundle has no `pk_` key **because there was nothing to use one**. Every customer who
ever tapped "Pay with Card" got that error. The owner hit it live.

**And the page stays ACTIVE after payment** — he paid the same link twice. A paid link that still
takes money can take it twice; this is the more dangerous of the two.

**DECISION (mine, stated to him): finish the branded link, do not fall back to a raw Stripe link.**
`payment_pages.metadata.stripePaymentLinkId` already holds a real Stripe link
(`plink_1UO5nkLnlgYj1gmTxttmV7fe` for the test page) created by `createPaymentLink`. That hosted page
is the path already proven live — the first real payment went through it. So the card button should
REDIRECT there, and the page must deactivate when the balance settles. Small, certain, and it keeps
the shop's own page plus the Zelle option.

## DEPLOY ORDER IS LOAD-BEARING

**The frontend must deploy BEFORE the backend.** The IVR prompts are MP3s served from
`frontend/public/ivr/`; the backend emits `<Play>` URLs pointing at them. A missing `/ivr/*.mp3` on
this domain returns **HTTP 200 `text/html`** (the SPA), not 404 — so a missing file is silent and
undetectable at call time, which is why the coverage test exists. `PAY_VOICE_AUDIO_BASE_URL` is the
switch: unset = the production host (correct), and it is set to the test host on test.

## STILL OPEN — the reason his first message looked thin

**`buildPayNotice` has NO production caller.** `backend/src/services/payments/pay-notice.service.ts`
renders the real customer message — device line, ticket reference, amount with tax breakdown, the
`/pay/<uuid>` link, the phone code, Zelle — and it is fully tested. Nothing calls it. **I searched
every file.** So every customer text about a repair being ready has been hand-written by an agent,
which is how the photo-ID-style problems reached the owner unfiltered. Wiring it up is the single
highest-value remaining piece.

It cannot be called raw: `defaultFindLiveLink` → `PaymentLinkService` → `validatePermissions`
(`payment-link.service.ts:1207-1212`) only checks `this.context.userId`. Construct the service with
a context, or inject deps — that is how the real notice for order 2998 was rendered. The link the
product produces is the SHOP's own page (`FRONTEND_URL + /pay/<uuid>`), NOT a `buy.stripe.com` URL.
