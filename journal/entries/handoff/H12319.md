### The fleet rule I had to decide, and why it is the opposite of the usual advice

`hardening` asked whether it may commit regenerated docs, since adding test files makes `FACTS.md`,
`REACHABILITY-CLIENTS.md`, `INDEX.md` and the dead-citation audit stale, and CI runs `docs_check.py`
without `--write` on every PR.

**Answer: yes — every lane commits its own generated docs, in a separate commit, and I regenerate once
after each merge.** The usual rule is "never merge a generated file from a branch, regenerate once on
main", and that rule exists to avoid four-way conflicts. It is wrong here, for a reason worth recording:
**a red PR hides real failures.** If every lane's PR is red for a known-stale-docs reason, the next
genuine regression looks identical to the noise and I lose the ability to trust the check at all. A
green PR plus one conflict I resolve with `--write` is the better trade.

The condition I attached: separate commit, and the report shows the authored `git diff --stat` apart from
the generated one, so nothing authored can hide inside a regeneration.

### Integration lessons added this round

1. **A relative link from `docs/roadmap/items/` needs `../../`, not `../`.** Third occurrence of this
 exact off-by-one; the gate catches it every time, which is why it is a cheap mistake rather than a
 shipped one.
2. **`git merge --ff-only` aborts on a dirty tree**, and resolving a merge conflict by stripping markers
 can leave two assignments where the file expects one — the second silently wins (I hit that on
 `android-test-files.py` and had to dedupe by measurement).
3. **`gh pr merge` works with pending checks when the repository does not require them**, but check
 `mergeStateStatus` first: `CLEAN` is the only state worth acting on.
