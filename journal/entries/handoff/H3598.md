## I REPORTED A FALSE BLOCKER, AND THE SECOND PROBE DID NOT SAVE ME

Last round I reported to the owner, as a serious finding, that **the Counter renders no work orders**.
**It was wrong.** The screen renders twenty-five rows:

```html
<ul data-testid="staff-open-rows" data-row-count="25">
 <li><button data-testid="staff-open-case-1427" data-kind="case" data-status="NEW"
 class="min-h-20 w-full touch-manipulation rounded-xl …">
 <span data-testid="staff-open-case-1427-identifier-phone">Ticket 1427</span>
```

The walker's locator was `'table tbody tr, [role="row"]'`; the Counter is a `ul` of 80px
`touch-manipulation` buttons, i.e. a **good** phone list. Nothing matched, so it called a blocker.

**The worse half:** I wrote a second probe specifically so I would not be repeating an unverified
claim — and it searched for `WO\d{6,}`. The open queue holds **tickets** (`Ticket 1427`). Both methods
believed the same two things (it is a table; the rows are work orders), found nothing for the same
hidden reason, and I called their agreement confirmation. **Two methods that share an assumption are
one method counted twice.** Recorded as **L3763**.

## FIXED — PR 391

- `tableRows()` in `e2e/personas/lib/locators.ts` now matches what the counter renders, plus the
 table/role cases other screens use.
- New **`declaredRowCount(page)`** reads the screen's own `[data-row-count]`, so *"the walker matched
 nothing"* and *"the page is empty"* can never again be the same finding. The markup was carrying
 `data-row-count="25"` the whole time and nothing read it.
- The roadmap's `T1` rewritten with the truth; the change-log row **struck through rather than
 deleted**, because the record of having been wrong is the useful part.

**What that invalidates: the walk's 8 blockers and 20 majors are now suspect** and must be re-run
before any is believed. Findings that are *measured numbers* rather than lookups survive — the 956px
table in a 1920px window, and the phone-vs-laptop asymmetry on the same jobs.

## FIXED — PR 392, THE RACE THAT LEFT PRODUCTION BEHIND MAIN

`required-checks-gate.mjs` read a **still-running** required check as a failure, twice tonight, and
the second time production stayed on `202c52784` while `main` was `2bcf92ddc`. Now it waits up to

failure message says which it is and tells the operator to raise the budget or re-run, rather than

three `PASS` and exited 0 — the settled path unchanged. **The waiting path itself is NOT yet proven
on a live race**; the next promotion is what proves it.
