## 2026-10-22 16:35 UTC · ZABZ-TECH · The dictionary is blocked by a host list after all; the failover key was the hole; the fleet's real state is unknown

Owner's question this session: "did you pull up all the research on how we once blocked dictionary? it must be going through somewhere." Answer: yes, and the missing fact was a single key.

**The answer, in one line.** A dictionary is a MobileAsset whose payload comes from `updates.cdn-apple.com` (255 of 523 assets), `appldnld.apple.com` (149) and `updates-http.cdn-apple.com` (119) — verified by fetching Apple's own catalog (`mesu.apple.com`, HTTP 200, 909,016 B). Our resolver refuses all three. What let the download through was the DNS profile's `AllowFailover=true`, which permits the phone a second resolver; it was flipped from false to true on 2026-10-21 00:47:49. With it set false, on DRN 2004 at 16:07:18Z, the payload host stayed refused and the download stopped while everything the kiosk needs kept resolving. **The resolver was always the gate.**

**What changed in production:** one key in `/opt/waze-mdm/profiles/waze-siri-filter-dns.mobileconfig` (md5 `481195f9…` → `ac241679…`), pushed to DRN 2004 only (command `F93B7BD5-…`, Acknowledged 16:07:18.993749). Backup `/root/waze-siri-filter-dns.allowfailover-true.20261022T160716Z.bak`. Nothing else changed: `.env`, PAC, `doh_filter.py`, Caddyfile, compose and containers all carry their old hashes and no other device received a command. Revert = restore the backup + re-push the same endpoint.

**What is NOT known, and must not be asserted:** which of the other ~59 devices carry true or false. `device_profiles` is empty fleet-wide, a device's ProfileList does not expose payload keys, and only 2 devices ever acknowledged the true profile (2026-10-21 00:47:49) while 8 of 62 checked in within two days and 54 have not checked in for a fortnight. The fleet cannot currently be described as filtered. Also untested: what a resolver outage does to a device with failover off — the semantics say no DNS at all, and because the profile is unremovable we cannot push a fix either.

**Next actions, in order** (full statement and evidence in the doc, §8):
1. Make the resolver survivable — two independent DoH origins behind one name, plus a health check that alerts (cron already runs `filter-parity.py` and `dns-chain-canary.py` every 15 min into a log nobody reads).
2. Then sweep `AllowFailover=false` to all 62 and count acknowledgements; that is the fix and the measurement at once.
3. Fix the PAC: delete `updates.cdn-apple.com`, `updates-http.cdn-apple.com`, `appldnld.apple.com` from `DIRECT_DOMAINS` lines 2-4; add them to the parity manifest.
4. `apply-location-fix.py` (69-71, 87-90) still re-adds `iphone-ld.*` and the asset family on the next `--apply`.
5. Location audit: prove every positioning name is allowed on both gates and remove asset/store names wearing a location badge (the 38 added 2026-10-21 are not all location).
6. Production device definition + bench card, with dictionary removal as a mandated bench step.
7. Card-level fix independent of all of it: `com.apple.configuration.keyboard.settings` + `AllowDefinitionLookup=false` (`D9352`), delivery via KMFDDM.
