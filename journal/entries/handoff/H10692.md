THE ASSERTIONS ARE MOSTLY ABOUT REFUSALS, deliberately: these are the shapes where a mistake leaks data instead of returning an error.
 no token -> 401 on all three; a stranger's token -> 401;
 **ws_auth_mode set to anything but per-phone -> 400, NOT 200** - a 200 there means the token check is not running at all, and the failure message says so;
 a phone's own token -> a dict from each;
 the trust view -> 401 without operator credentials, 404 for a phone that does not exist, so an unknown id cannot come back as "a healthy phone with no events".

TWO PROPERTIES THAT ONLY A TEST COULD HAVE SHOWN, both now written into the file:
 `POST /admin/households/{hid}/phones` writes ONLY the household mapping. The phones row is created by the hello/heartbeat path (storage.ensure_phone), so a phone that has been "assigned" still 404s on any per-phone route until it checks in. That is a real property of the system - the difference between an assigned phone and a live one - and nothing in the documentation said it.
 The self endpoints take the token in a QUERY PARAMETER, not a header, and they refuse outright when LPT_WS_AUTH_MODE is not per-phone.
