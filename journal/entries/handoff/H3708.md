## 2026-10-20 18:24 UTC · ZABZ-TECH · round 17: my IDXGIOutput1 reorder was wrong - the header says DuplicateOutput is fourth; the fault is pinned to GetDesc

# H (2026-10-20, round 17) - the duplication fault is pinned to ONE member, and my first "fix" was wrong

## The correction first, because it is the lesson
I reordered `IDXGIOutput1` and announced it as the cause of the AccessViolation. It was not. The SDK header on disk
(`dxgi1_2.h`) puts `DuplicateOutput` **fourth**, exactly where the file already had it, and my reorder moved it into
`GetDisplayModeList1`'s slot - which returned `S_OK` with a null pointer and turned a crash into a different failure.
I had reasoned from memory instead of opening the header that ships with the SDK on this machine.

What the header DID prove wrong: `IDXGIOutput1` declares **six** methods and the file had four - `DuplicateOutput1`
and `GetFrameStatistics1` were missing. That is now corrected, in the header's order.

## What six interactive runs established, in order
1. ssh lands in **session 0**, which has no desktop: `EnumOutputs` fails with `DXGI_ERROR_NOT_CURRENTLY_AVAILABLE`.
 From an `/it` task in the console session the duplication **opens**. "No attached output" was a session fact.
2. Wrong declaration order → `S_OK` with `duplication=0x0` (reported, not thrown, because the caller now checks).
3. Header order restored → `DuplicateOutput` succeeds with a **non-null** pointer, and
 `IDXGIOutputDuplication::GetDesc` faults with `AccessViolationException`.
4. The header declares `GetDesc` as `virtual void STDMETHODCALLTYPE` - it returns nothing. Both `void` and
 `[PreserveSig] void` fault identically, so the fault is inside that member's ABI.

## What shipped
PR #77 -> `37ede73`. `DuplicateOutput` now returns `out IntPtr` and is checked; both failure paths include the
first in-repo stack frame, which is what located the fault at all. Full Windows suite green throughout:
`Passed: 374, Failed: 0, Skipped: 12, Total: 386`, and `windows-unit-tests` passed in CI.

## What is left on it, stated so the next attempt does not repeat mine
One question: why does `GetDesc` fault against a valid duplication object when its slot (first after IUnknown) and
its parameter (36-byte struct, pinned by a passing ABI test) both look right. Next probes, cheapest first: call
`GetDesc` through a manual vtable function pointer over the raw pointer to separate marshalling from slotting, and
print `vtable[3]` to confirm it is not a thunk. **Do not reorder IDXGIOutput1 again** - the header settles it.

## Method note worth keeping
`schtasks /create ... /it` is how a session-bound proof gets run, and the cost is real: a console window flashes on
the owner's desktop for ~40 s, six times tonight. That is a lot of flashing for one defect, and it is the reason
the next step should be a probe that answers more than one question per run.
