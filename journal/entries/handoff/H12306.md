### The fourth false claim, and the cheapest to fix

The phone told the customer *"The filter was released on <date>. **You can now uninstall the app.**"*

Measured before changing anything — `SelfRelease.release` (`SelfRelease.kt:185-200`) calls
`setUninstallBlocked(admin, package, false)`, clears `DISALLOW_APPS_CONTROL`, and calls
`setUserControlDisabledPackages(admin, emptyList())`. **`clearDeviceOwnerApp` and `removeAdmin` appear
nowhere in `android/` or `server/`**, so the app remains device owner after a release — and whether
Android will uninstall a device-owner app is a device test nobody has run.

Corrected to what is true: *"**The block on uninstalling it has been lifted.**"* Three Robolectric tests
pin it — must **not** contain "can now uninstall", **must** say the block was lifted, **must** still name
the date. The DoD's first branch (prove it on a bench phone) needs the handset; the second branch is
available now and is what I took.

The test's own docstring records the exit: if a bench phone later proves the app *is* uninstallable, amend
the test **with the device evidence** rather than quietly restoring the old wording — so the claim can
only come back through a change that says why it is allowed to.

### Four of a kind this session

| what it said | what it did |
|---|---|
| MITM CA install succeeded | installed nothing, HTTPS never inspected |
| Play Integrity: device failed | build was unprovisioned |
| screen recording prevented | capture is enabled |
| you can now uninstall the app | app stays device owner |

Same shape every time: **the code does something adjacent to what the words say.** Three were fixed by
making the code tell the truth; this one by making the words match the code. All four were found by
reading one file against its own claim, and none by a failing test — which is the argument for a
public-claims gate, and part of why 1137 asked for one.
