## 2026-10-14 03:01 UTC · ZABZ-YOGA · H - SOLVED: yocheved mode vanished because 0.2.0 needs generated preset-rows in cordis.patch.yml and hers had none -- installed, verified, engine boots clean on the pin

SOLVED 2026-10-14. THE CAUSE OF THE MISSING `yocheved` MODE, PROVEN END TO END.

## THE ANSWER

`scripts/make-preset-rows.mjs` generates one `preset-<name>` ROW per user preset and splices them into
`profiles/web/cordis.patch.yml` between a pair of managed-block markers. **0.1.5 discovered presets by
scanning `~/.dsh/.agent-presets/`; 0.2.0 requires those generated rows.** Her `cordis.patch.yml` never
carried the block, so ZERO user presets registered.

The tool says it about her box, verbatim:

 --check: DRIFT -- the `preset-rows` managed block is absent from profiles\web\cordis.patch.yml;
 the generated rows are not in any layer the engine loads. Run with --install.

and its own header states the consequence exactly:

 "Upgrading WITHOUT this conversion leaves `settings.agent-presets.default: zabz` naming a
 [preset that does not exist] -- silently, with no error."

That IS the reported symptom: `settings.yaml` says `agent-presets: default: yocheved`, no such preset is
registered, and the engine falls back to `standard` with nothing on screen.

**So the yocheved mode did not "disappear" for a mysterious reason -- it disappeared BECAUSE of the
0.1.5 -> 0.2.0 move, which is precisely the migration that script exists to perform.** The owner's own
`zabz` still works because his profile HAS the block.

## THE FIX, APPLIED AND VERIFIED

1. `node scripts/make-preset-rows.mjs --install` on her box: emitted
 `preset-cordis-bg order=10`, `preset-yocheved order=11`, `preset-zabz order=12`; self-check PASS;
 "created the managed block in profiles\web\cordis.patch.yml (patch entries 2 -> 5, 1208 lines
 between the markers)"; wrote `presets.generated.patch.yml` (69,214 b).
2. It writes into the REPO, and the engine loads `~/.dsh/profiles/web/`. **harness-sync did NOT deploy
 it** -- repo had 9 `preset-` rows, the live file still had 0 after running `PersonalSecretary-HarnessSync`.
 So the artefacts were copied into the LIVE profile by hand (backup `cordis.patch.yml.bak-20261013-2300`).
3. VERIFIED in the config the engine actually boots:
 dump exit=0, lines 2939 (was 1355)
 preset-yocheved 1, preset-zabz 1, preset-cordis-bg 1
 - id: preset-yocheved
 name: '@deepseek-ai/dsh-agent-preset'
 config: { id: yocheved, order: 11, plugins: [ { id: persona ... } ] }
 -- i.e. declared EXACTLY the way `standard`/`ptc`/`minimal`/`cordis` are.
4. Engine bound on 3099 as the 0.2.0-rc.2 pin with **0 bytes of stderr** (the first clean boot of the night;
 previous boots wrote 136 / 990 / 1126 b).

## WHAT STILL MUST BE DONE, and it is a real gap

**Her sync does not carry the preset-rows block.** `harness-config-update.cmd` + `harness-sync.mjs` on
her box left the live `cordis.patch.yml` at 2,411 b / 0 rows while the repo file had 9. So either:
 (a) her lineage's sync never runs `make-preset-rows.mjs`, or
 (b) it runs but does not deploy `profiles/web/cordis.patch.yml` + `presets.generated.patch.yml`.
Fix THAT, or the rows are lost the next time the profile is regenerated. Run
`node scripts/make-preset-rows.mjs --check` in CI (the script says it is designed for exactly this) and
add the deploy step.

## THE INSTRUMENT LESSON, paid for five times over

Everything I got wrong tonight came from one of two habits I skipped:
 * **Never reason from a truncated body.** I `.slice()`d the roster JSON and spent four rounds
 believing `yocheved` was absent from a list I had cut at 240 characters.
 * **Check a machine where the thing WORKS before theorising about why it fails.** The owner's `zabz`
 registering with an IDENTICAL `preset.yml` shape killed four of my hypotheses in one look.
 * And: **a tool that documents its own failure mode should be read FIRST.** `make-preset-rows.mjs`'s
 header describes this exact silent fallback, and it was in the repo the whole time.
