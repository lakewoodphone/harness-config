## 2026-10-08 03:23 UTC · ZABZ-YOGA · The Kosher filter was REMOVED from ZABZ-TECH by the owner's instruction: what was installed, what was re-enabled tonight, and what is verified gone

CHANGED - the Kosher filter was REMOVED from ZABZ-TECH, by the owner's explicit instruction
("yes remove it for good", 2026-10-08).

WHAT WAS THERE, AND WHERE IT CAME FROM
- Installed against the product's own stated bound. `kosher-filter-ai/docs/audits/kf0928/windows-merge.md`
 §4 says: "The service runs as an installed Windows service (`sc create` + start) ... UNVERIFIED ...
 not attempted: registering/installing a service on the owner's laptop is outside the rules of
 engagement." It was installed anyway: `C:\Program Files\KosherFilter` created 2026-09-28 17:33,
 `C:\Program Files\KosherFilterRelay` created 2026-09-30 20:51. The same table flags the exact rule
 that was live - "the unrestricted production filter udp.DstPort == 53 or udp.SrcPort == 53" - as
 needing a maintenance window because "an interrupted run breaks the host's own DNS".
- It had been switched OFF at some point (both services read start type `disabled`), which is why the
 owner believed it was already gone. On 2026-10-07 at 20:27:22 and 20:27:43 local, something flipped
 both **from disabled to demand start**, and the WinDivert kernel driver was registered at 20:27:44
 from `C:\Program Files\KosherFilter\WinDivert64.sys` (System log 7045). The relay's own application
 log then filled with `Broker DNS forward failed for ...; answering SERVFAIL` from 22:07 to 22:52,
 and the machine resolved no public name at all.
- WHO turned it back on is NOT established. The log records the change and the driver registration,
 not the actor. Do not guess it.

REMOVED (verified on the machine, admin session, 2026-10-08)
- `sc delete KosherFilterDnsRelay` -> DeleteService SUCCESS
- `sc delete KosherFilterService` -> DeleteService SUCCESS
- `C:\Program Files\KosherFilter` deleted (47 files, 3.3 MB)
- `C:\Program Files\KosherFilterRelay` deleted (41 files, 2.4 MB) - this also removed the deployed
 `appsettings.json` holding the relay's per-device broker token; the token itself is NOT copied into
 this journal.
- No WinDivert driver service was registered by the time of removal, and none remains.
- No native-messaging host, scheduled task or Run key referenced the filter.
- Three orphaned inbound firewall rules (`KosherFilterAI Broker 8443 TCP`, `KosherFilterAI SOCKS 1080
 TCP`, `KosherFilterAI SOCKS 1080 UDP`) were removed in a second pass.

VERIFIED AFTER
- Both services gone, both directories gone, no loaded WinDivert driver, no listener on 1080/8443.
- DNS: `api.deepseek.com` -> 3.173.21.63, `github.com`, `google.com`, `registry.npmjs.org`,
 `dialpad.com` all resolve. Before the removal the same machine answered NXDOMAIN for every one of
 them while the filter ran.

NOT DONE, ON PURPOSE
- Nothing was removed from the kernel driver package beyond the service registration, because none
 remained. Nothing was touched in a browser profile. The product source is untouched in
 `C:\Users\ezabz\code\kosher-filter-ai` on ZABZ-YOGA.
- The owner's laptop, secratary and zabz-tech-linux were each checked and never had it installed.

NEXT
- If the Windows port is to run on a real machine again, it needs a maintenance window and the owner's
 explicit authorisation, and the audit's line 246 asks for exactly that. A machine whose DNS is
 hijacked by an unreleased filter is not a test target, it is an outage.
