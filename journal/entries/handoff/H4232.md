## 2026-10-14 · ZABZ-YOGA · authority disk audit: the fills were discrete 25 GB writes, and the alarm was broken in four places

Five-stream mesh fleet (all children on ZABZ-TECH), commissioned by the owner after I filled the
authority's disk. Full record with an evidence index per claim:
`harness-config/docs/operations/authority-disk-audit-2026-10-14.md`.

### THE HEADLINE — my incident was the third fill of the same day, not the first

Measured from `disk-guard`'s own log and the estate monitor: the authority hit **zero bytes free at
2026-10-14 00:15:03Z (98.5 %)** and again at **14:45:04Z (97.6 %)**, with a zero-free window running
**2026-10-13 20:15 → 2026-10-14 00:45**. The steepest bracket is **33.63 GiB → 11.01 GiB in 6.733 h =
−3,440 MiB/h**. My 22:39 copy was the straw; the bale was already there.

**So "how did it fill so fast" has a real answer and it is not growth.** `authority.db` grows at
**51.9 MiB/h over four days** (98.8 MiB/h most recently) — 185 h to fill the current free space. **The
fills are discrete large writes.** One write, a whole-database `VACUUM INTO`, was **25.63 GiB = 18.4 % of
the entire disk in one operation.**

### THE ALARM WAS BROKEN IN FOUR INDEPENDENT PLACES

1. `disk-guard` (every 15 min, WARN 90 / CRIT 95) **only measures and records** — `INVOKE_RETENTION`
 defaults `"0"`; no prune, no reclaim, no owner page.
2. **A wrong path.** `sources/disk-space.py:47` defaults `GUARD` to `~/bin/disk-guard.py`, which **does
 not exist**; the real binary is `/usr/local/bin/disk-guard.py` and `DISK_GUARD` was set nowhere. Since
 19:37 it failed every 30 minutes: `SIGNAL UNREADABLE -- the disk guard itself is missing`. **The thing
 watching the disk was reporting it could not find itself, and nothing read that either.**
3. **By design, disk can never escalate.** `estate-monitor` state:
 `"conditions_allowed_to_escalate": ["public_health_status"]`, `disk_used_pct` `mode="log"`, transport
 `syslog + alerts.jsonl + ESCALATED file — NO outbound message of any kind`.
4. **Every stage of the alarm must write to the filesystem whose exhaustion it alarms about** —
 `status.json`, `guard.log`, `runs.tsv`, and `estate-monitor.save_json` (`:1432`, no `try/except`, runs
 *before* the verdict). At zero free the write raises `ENOSPC` and the alarm is lost. Measured:
 `status.json.tmp` **0 bytes at 23:15**; no `guard.log` line for 22:45 or 23:15.

Plus: **the monitor was blind for 8 hours across the fill** (verdict lines per hour `14 → 22`, then
nothing until `22 → 5`), and the only cron pruner (`prune-backups.sh`) is scoped to one root holding
**1.4 MB and 1 entry**, so a preservation register is what actually protected the 25.63 GiB from it.

### "ARE WE BACKING UP ONTO THE SERVER?" — precise answer

**Not the offsite job.** `authority-offsite-backup.sh` streams to R2 with **`peak_extra_disk_bytes=0`**;
two earlier designs that wrote a local snapshot first were deliberately removed. Offsite is real and
**17.6 h old** at audit time (R2 bucket `lpt-authority-backups`, `authority/secretary.db.gz` 7.39 GB).
**But copies ARE written onto the same filesystem by three other paths:** whole-DB `VACUUM INTO`
rollback copies, git packs/bundles, and un-pruned directories. **It is not "too many backups" — it is
copies with no retention on the disk they are protecting.** Coverage gap: ~11.4 GB offsite against
~55 GB on-host; `chromadb` (2.4 GB) is explicitly excluded, and `archive/lpt-transcripts` (7.1 GB),
`mail-archive` (2.6 GB) and `.usearch` (741 MB) have no offsite mechanism found.

### THE FINDING THAT MOST CHANGES WHAT WE BELIEVE

**`/opt/company`'s 7.5 GiB git pack is NOT bloat** — 99.95 % of object bytes are reachable; ~4.7 MB is
unreachable. What fills it is **`archive/lpt-transcripts` committed INTO git: 8,275,360,838 B = 90.5 % of
reachable bytes**, including a **1,049,538,560 B blob that now exists nowhere else** (it is off disk). A
1 GB binary in a git object store on the sole-writer volume. Do not propose a repack to reclaim it.

**And the 25.63 GiB copy's own DO-NOT-DELETE marker is false:** it claims to be the pre-remediation
rollback point, but its content is **post**-remediation (tasks 3132/27907/28550 = `done`, identical to
live). The genuine revert source is `rows-before-remediation-….json`, **32 KB, present**. No executable
consumer exists (grepped across all four system paths + `crontab -l`).

### FIXED THIS SESSION (one line, verified)

`ln -s /usr/local/bin/disk-guard.py /root/bin/disk-guard.py` → the source's path check now passes and the
guard returns real JSON (`used_pct 84.1`, `free_bytes 19,070,242,816`). **A monitoring chain that had been
dead for hours, restored by one symlink.** Next three, all zero-risk: move the verdict off `/` before any
write; add disk to `conditions_allowed_to_escalate`; add a `df` headroom check to large-write paths.

### STILL THE OWNER'S

Reclaim **25.63 GiB** by removing the marked copy (→ ~70 % used); a retention policy for the copy
producers (`~/.cfo/backups` 185 files / 1.3 GiB, `checkout-health-preserved` 33 dirs / 1.1 GiB); and an
**ext4 project quota on `/root`** to bound it structurally. **Never touch:** `git-rescue-20261012`
(delete was already recommended once in #484 and would have destroyed unique work — `P3163`),
`hc-main.bundle` (it *is* harness-config's origin URL), the stash-only bundles r2/r13/r14/r15/r16, and the
51 linked worktrees (13.1 GiB; the same unstaged edit appears in 8 of them).

### NOT VERIFIED

`PRAGMA quick_check` on `authority.db` after the ENOSPC (**integrity unproven**); no `git gc --dry-run`,
so every git reclaim figure is "likely" never "safe"; the producer of the 25.63 GiB copy **not found**;
what removed ~83 GB at ~01:15Z **unattributed**; R2 versioning `AccessDenied`; no `sar` filesystem
history; **other hosts not audited** (`lpt-apps-01` is documented at 90 % full).
