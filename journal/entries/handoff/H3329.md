## 2026-10-08 03:03 UTC · ZABZ-YOGA · The mesh was down for hours and the instrument said healthy: three stacked defects fixed, a node-measurement loop built, and the wake layer is paused for want of 6.90 of balance

CHANGED — the mesh, and the reason the whole fleet went silent

**What was actually wrong.** Every mesh dispatch died, so every session did its work locally on the
laptop the owner was trying to work on. Three defects stacked, and each one alone would have been
survivable:

1. **`mcp_launcher.py` died on a logging failure.** It opened
 `C:\Users\ezabz\Code\personal-secretary-mvp\data\logs\mcp-launcher.log` unconditionally after
 computing which keys were missing from a repo `.env`. Under the mesh child's execution context that
 open raised `PermissionError`, and the one-shot **exited 1 with no completion frame**. The file
 itself was writable (a plain ssh session appended to it; ACL grants FullControl) — the failure
 belonged to the child's context. One unguarded `open()` turned a missing-key warning into a dead
 node. **Fixed**: every log open now goes through `_open_log()`, which returns a write-nothing
 stand-in instead of raising, and still prints to stderr. Node copy backed up
 (`mcp_launcher.py.bak-prelogfix`); repo fix committed and pushed on branch
 `fix/mcp-launcher-never-die-on-log-write` (`fc65be23d`).
2. **The retry classifier refused to reroute a dead child.** `retry-plan.js` answered
 `child-ran-transport-fault` — which means *harvest, never re-dispatch* — for **any** non-zero exit
 with no completion frame. Its comment justified that as "the child's last moment was never captured,
 it may have done work". True for a transport fault; false for a child that **died**, whose process is
 gone. So one broken node absorbed **100%** of dispatches while a verified-good node sat idle.
 **Fixed**: a non-zero exit that produced *nothing at all* — no frame, no answer, no transport fault,
 and no marker of its own on stdout — is now `node-specific`, i.e. reroute. The stdout test preserves
 the anti-duplication guard: a child that emitted `FANOUT_BEGIN`, a transport host line or a
 `MESH-HOST:` line is still harvested, never re-run. **180 tests pass, 0 fail** (including the
 started-child end-to-end guard, which caught my first, too-broad version).
3. **Nothing ever re-measured a node.** `mesh-broker/nodes.json` carries `dispatch.v1` — "can this node
 accept v1 work" — and ZABZ-TECH's row still said `true` from a **2026-09-16** measurement 22 days
 later, while every dispatch to it failed. A measurement that is never renewed is not a measurement,
 it is a memory. **Fixed**: `~/bin/mesh-node-probe.sh`, cron'd every 15 minutes, runs a **real
 headless child turn** against every roster node and files a wake flag whenever a node's measured
 state disagrees with the roster — in either direction, so a node that comes back is flagged too.

**Verified, not asserted.** ZABZ-TECH re-measured `MESH-OK-ZABZTECH`, exit 0, after the launcher fix.
The probe then read every node: `zabz-tech ok=true 6000ms`, `zabz-tech-linux ok=true 4000ms`,
`lakewooechsmini ok=true 3000ms`, `zabz-yoga-1 ok=true 15000ms`, `secratary` correctly skipped as
never-measured — `OK every probed node agrees with the roster`. Roster deployed
(`/home/zabz/mesh-broker/nodes.json` sha `f51d7d60`, backup `nodes.json.bak-20261008T024918Z`),
`mesh-broker.service` restarted, and a live dispatch landed on the node the broker named with the
target's own `transport host` line.

**Two of my own errors, both caught and corrected in-session:**
- I declared "`dsh` is not recognized, found it" far too early. ZABZ-TECH legitimately has no `dsh` on

 `lakewooechsmini` does not resolve from the authority; the roster's fanout row says `mac-mini-ts`,
 which answers `Mac`. I did not publish that flag — corrected the probe, re-ran, `ok=true 3000ms`.
