## 2026-10-20 15:50 UTC · ZABZ-TECH · WO26101812752 paid in full; terminal payments land with NULL orderId; lpt-backend broken by a CLOSED status

The question was "did that Stripe charge actually go through", and the answer took four surfaces to
prove. The durable facts a future session needs:

**A payment row with `orderId` NULL makes a paid job read as unpaid, and the terminal path writes them
that way.** WO26101812752 (order 3138, Zombeck, Kyocera E4610 top-half) reads 106.63 collected on a
159.94 total, so the counter says 53.31 still owed. The 53.31 was paid on 2026-10-18 17:53:41 on the
reader — `payment_transactions` id 3400, SUCCEEDED, charge description "Zomback", staff note
"Diagnosis fee for water damage" — with `orderId` and `customerId` both NULL. 53.31 + 106.63 = 159.94
exactly, and both figures carry their own tax (3.31 and 6.63 = 9.94 = the tax inside the total). The
job was paid in full and the note that said the 50 diagnosis fee was cash with no row (note 4140) was
wrong on both counts. Corrected in production by note 4416.

**All six terminal payment rows from 2026-10-18 (3400–3405: 53.31, 15.99, 106.63, 90.63, 58.64,
213.25) have orderId and customerId NULL.** So this is a write defect in the counter-sale/terminal
path, not one case's bad luck. Nothing on the board can attribute reader money to a job.

**How to prove a Stripe fact on this estate.** The live key is in `lpt-backend` on `lpt-apps`, and
`lpt-apps` has python3/jq/curl: `ssh secratary-cloud 'ssh lpt-apps "docker exec lpt-backend printenv
STRIPE_SECRET_KEY"'`, then `GET /v1/payment_intents/<id>?expand[]=latest_charge.balance_transaction`.
`status=succeeded` alone is not enough — read `amount_received`, the charge's `captured` and
`amount_captured`, and the balance transaction's fee/net. "Not in the Payments tab" meant the tab was
loaded before the charge: `payment_intents?limit=8` returned it first. Payments = intents;
All activity = balance transactions, and the Type column there reads `charge` or `payment` by funding
route, not by status.

**Reading production SQL from Windows is a quoting trap.** `lpt sql` goes through a `.cmd`, and
PowerShell/cmd eat the double quotes around `"orderId"`. The working shape is
`to_jsonb(p)->>'orderId'`, which needs no quoted identifiers — or, better, `~/bin/pgsql-ro` (installed
this session on the authority: a read-only psycopg2 runner taking a file or `-`, DSN from
`~/personal-secretary-mvp/.env`, one JSON line per row).

**The website is erroring in production right now.** `docker logs lpt-backend --since 60m` held 112 ×
`order.groupBy(): Value 'CLOSED' not found in enum 'OrderStatus'` and 87 × the same on
`repairIntakeCase.findMany()`, 562 since the container started. Cause: the write path accepted a
status (`CLOSED`, written to WO2601150002 on 2026-10-20) that Prisma's generated enum does not have,
so every count query and the intake list now fail. The reader's vocabulary and the writer's vocabulary
are not the same list.

**The counter's Stripe description carries the row id.** `useStaffOrderChargeActions.ts:275-277` builds
`Charged on the counter page for work order ${workOrderId}` from `order.id`, which is why the dashboard
says "work order 3138" for WO26101812752. Stripe is read by the accountant and the customer, so it
should carry the WO number.

Still open: linking row 3400 to order 3138 (a money-row change, deliberately not made), the
