## A REAL ESTATE PROBLEM FOUND WHILE VERIFYING (NOT caused by this work)

**The company API wedges: it accepts TCP and never answers.** Measured
21:00-21:06Z: `/health`, `/shabbat/status` and `/shabbat/safety` all timed out
(20 s, 0 bytes) while `ss` showed LISTEN on 8002 and the process sat at
`ActiveState=active, SubState=running`. No journal lines were produced for
several minutes — a hung process, not a busy one. `/home/zabz/bin/health-gate.sh`
agreed: verdict **DOWN**.

It did not recover on its own in 6+ minutes; I restarted `secretary-api.service`
at 21:08Z and it came back (new pid 195899), after which `/shabbat/status`
answered normally. **This matters directly**: at 20:04 Saturday the power-up
needs the API to relock the door and re-assert the ceiling light. If it is wedged
then, the new `recover_incomplete_power_up` retries every minute until it answers
— the right behaviour, but it means the door can stay released longer than
planned.

**Underlying cause, still present:** `/health` reports
`database ok:false, "db check timed out (lock contention); api still responsive"`
on 4/4 samples, and `secretary.db` is **23 GB** with a 64 MB WAL. The API stays up
and answers with the degraded body, so this is not by itself the hang — but it is
persistent and it is the same subsystem.

**Two owner-independent facts measured, to avoid a wrong report:** the watchdog
state files are `root:root`, and `secretary-api-watchdog.service` sets **no
`User=`**, so its timer runs as root and CAN write them. A `Permission denied` I
saw came from running the script by hand as `zabz` — that is an artifact of the
manual run, **not** a broken watchdog. It had in fact noticed the wedge
(`degraded #2: secretary-api.service is active but /health says DOWN`) but had not
yet reached its restore threshold (6 readings / 30 min), and it had no incident
file at that point.

## MY OWN BUG, FIXED

`verify-shabbat.sh`'s executor check was wrong twice: it false-failed on the
first run after a restart, and it stored SECONDS in a variable named `up_min`
compared against a minutes threshold, so the "too soon" guard only fired within 4
seconds and the reading said "113m" when it meant 113s. Fixed with
`ps -o etimes=` and a real rate test. **Honest limit: the live negative control is
inconclusive** (the "too soon" band short-circuits it while the process is young);
the FAIL direction is proven by simulation, not by a live red.
