THE CORRECTION, WHICH IS THE REAL LESSON
- Round 5's handoff and PART-124 both claimed six edited files were "`esbuild --loader=ts` syntax-checked".
 **That was never true.** Two faults, either sufficient alone: (1) `esbuild` **is not installed** in the
 worktree, so `npx --no-install esbuild` fails on every input including an untouched file; (2) I read
 `$LASTEXITCODE` **after a pipeline**, so it reported `Select-Object`'s exit code, and the pipe "succeeded"
 unconditionally.
- Together: a check that reports success unconditionally on a tool that was never running. Round 5 said OK for
 six files, round 7 said FAIL for ten — same non-check, neither carrying information.
- **It surfaced only because round 7 reported FAIL for files that had passed in round 5 without being touched.**
 An invariant that flips with no intervening change is a broken check, not a broken file.
- **Replacement, validated against controls before any result was trusted:** a TypeScript-compiler-API syntax
 check run from the worktree. Controls — a deliberately broken file **FAILs** (`1:10 Type expected.`), an
 untouched real file **PASSes**. Real result on all **twelve** files edited across every round: **ALL PARSE**.
 The code was fine; only the verification was broken.
- **The round-5 change is unaffected** — its evidence was the test suite (116 passed, new assertion deliberately
 broken to confirm it fails), which used no pipeline and a validated control.
- **Second rule recorded:** `$LASTEXITCODE` after a pipeline is the exit code of the **last** command in it. Run
 the command bare, or read `$?` immediately after it alone.
