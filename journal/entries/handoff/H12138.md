## 2026-10-21 02:07 UTC · ZABZ-YOGA · Second hop opened for location/clock at DNS only, ten Apple names, PAC untouched; the cert evidence says the line is policy not identity

The owner asked the right question and told me to decide it: can we unblock what the phone needs for location without weakening the filter, or is that a contradiction?

**Analysis, evidence first.** The hops still refused behind cl2/cl3/iphone-ld were checked by certificate: `cl2-cdn.origin-apple.com.akadns.net`, `cl2.g.aaplimg.com`, `cl3-cdn...`, `iphone-ld.g.aaplimg.com` AND the deliberately-blocked `appldnld.g.aaplimg.com` and `mzstorekit.g.aaplimg.com` all present the **same** Apple certificate (`CN=images.apple.com`) on the same /48. One CDN. So identity cannot separate location from the iOS-update path - only Apple's chosen names do, which is a policy line, not a security boundary. Saying otherwise would have been the confident-but-wrong move this tree keeps recording.

**Why it is still not a weakening:** the filter exists to stop arbitrary web and app content; none of these hosts serve any. What would weaken it is a general-purpose host, a broad zone, or a second resolver - and the proof tests exactly those.

**Change applied (filter, DNS layer only):** ten named hosts, PAC untouched, so app HTTP to them stays blackholed while daemons that bypass the proxy can resolve them. Names: cl2-cdn/cl3-cdn.origin-apple.com.akadns.net, cl2.g/cl3.g/iphone-ld.g.aaplimg.com, configuration.ls.v.aaplimg.com, time.g.aaplimg.com, gsp1.apple.com.edgesuite.net, configuration.g.aaplimg.com, ocsp-a.g.aaplimg.com. Allowlist 78 -> 88.

**Proof before applying** (corpus = 93 names the fleet asked for in the preceding hour): 10 changed, all to allowed, 0 policy regressions. **Live after:** appldnld.g, mzstorekit.g, bag-cdn, gateway.icloud.com, guzzoni, example.com, www.google.com, youtube.com and the Akamai edge a1507.w154.akamai.net all still REFUSED; cl2.g and time.g allowed. `cl2.apple.com` and `cl3.apple.com` now resolve end to end - all three hops that were refused this morning answer.

**The line that genuinely bites:** `gsp1.apple.com` (allowed since August) resolves to `a1507.w154.akamai.net`, a shared Akamai edge. Left refused on purpose - that is generic infrastructure, not an Apple name. If the phone still cannot locate, that is the next candidate and it needs a different decision, not a speculative opening.

**Note for the record:** the filter is shared, so this reached the DRN production fleet too, at the DNS layer only, with no device touched.
