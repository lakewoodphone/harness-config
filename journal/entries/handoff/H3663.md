## The correction first, because I earned it

I told the owner at 11:58 that the API was back and the cause was memory-cgroup throttling. It answered
`http=200` for about **nine minutes** and then went dead again (11:05–11:55, recovered 11:58, dead again
by ~12:07). **"Fixed" was wrong and it was wrong twice.** What was true: the restart cleared a *layer* of

## The mechanism, traced by a mesh agent to file and line, with a reproduction

`run_once` is **not** on the event loop — it is a separate `autopilot` daemon thread
(`app/main.py:1200` → `app/autopilot.py:2498`), and `run_once` runs in a `ThreadPoolExecutor(max_workers=1)`
awaited with `result(timeout=600)` at `app/autopilot.py:7910`. So it cannot stall the loop by running Python
on it. It reaches the serving path through **`_db_lock`**:

- `_db_lock` is a `threading.RLock` (`app/database.py:27`) whose own docstring says it guards **only the
 `_connections` dict, never a SQLite call**. The live code takes it unboundedly at `app/database.py:1110`.
- Autopilot held that lock **across `conn.execute(...)`** in six places (`app/autopilot.py:436, 687, 9231,
 9991, 10333, 10746` in the live worktree), the worst being an unindexed
 `SELECT MAX(created_at) FROM activity_log WHERE action IN (...)` at `:8357`.
- The serving path needs the same lock, and two async routes call it **directly on the event loop**
 (`app/main.py:6998` fleet_location_history, `app/main.py:1545` health).
- Each blocked thread can allocate a fresh connection with a **64 MB page cache**
 (`PRAGMA cache_size=-64000`, `app/database.py:87`) — the pile-up the health comment at
 `app/main.py:1456` already documented, which is how one slow run becomes gigabytes of RSS.
- The timeout wrapper abandons the unkillable thread and resets `_run_once_active=False`, so runs overlap.

**Reproduction, controlled:** a FastAPI async endpoint calling `_get_conn` on the loop, while a real
`AutopilotController` method runs against a deliberately slow `execute` (6 s). Pre-fix HEAD: **5.700 s**.
On the fix branch: **0.0014 s**. That is the channel, measured both ways.

**Branch, not deployed:** `fix/autopilot-db-lock-shared-resource-20261014`, commit
`875962a3839d2f525e150a9b64570747ad63bbac`, test `tests/test_autopilot_db_lock_not_held.py` — **3 failed
before, 3 passed after**; adjacent suites 38 passed, 2 pre-existing unrelated failures. Apply with
`git apply /root/work/autopilot-fix/autopilot-live-fix.patch` (sha256
`3eb7c429…ea271e`, `git apply --check` OK). It also adds a circuit breaker: 3 consecutive abandoned
`run_once` calls disable the loop.

**What the agent could not prove, and said so:** the memory-cgroup throttle is not removed. Autopilot still
shares the API process's cgroup. True isolation needs a separate process/unit, untested.

## Lesson

**A health check can be right about the symptom and wrong about the cause, and I did both.** I measured
memory-cgroup throttling, it was real, and I reported it as the cause before I had shown it was *the* cause
— then called it fixed without watching it stay fixed. The `db_writable` check caught the relapse I missed.

**And the queue's real shape is one defect, not 158 questions.** 80 of its rows are one bulk job; ten of
those collapse to two real questions; the shop's own written conventions answer others. Before working a
queue row: read the order's newest note, check whether it was already reconciled, and look for the shop's
own rule — in that order.
