## THE SELF-IMPROVEMENT LOOP IS CLOSED -- this was the objective's "improves itself" clause

THE GAP. `owner_queue_feedback` held 802 rows and every one came from a close a human or a
session happened to perform. The queue could record that a question was SENT and nothing
recorded what came back, so the learning profile -- which decides what rises and what sinks --
could never learn from the only class of question the channel actually asks. Delivery was a
dead end.

THE FIX. `decision-answer-capture.py`. For each row in `decision_sent`, find the first inbound
message from the owner that arrives after that send and before the next one, and write it onto
the row as the answer. Then `owner-queue.py learning --backfill` copies the close into the
profile.

WHY THE ATTRIBUTION IS SOUND AND NOT A GUESS ABOUT MEANING. Two texts ten minutes apart
cannot be told apart by content. But the channel's own rule -- the owner's, 2026-09-25: "one
question at a time" -- means at most ONE decision question is open at any moment. An inbound
message that arrives after a send and before the next is therefore the answer to it. The
pacing IS the attribution key. This is the first thing in the programme that the one-at-a-time
constraint actively buys.

It refuses to write unless all of these hold: the row was delivered; it is still `pending`;
an inbound message exists inside the window (72 h); the message is not an opt-out and not a
bare acknowledgement. It never overwrites a row someone else closed, never rewrites a
question, never deletes.

PROVEN ON THROWAWAY STORES, not on production:
 * three sends, three replies -> rows 1 and 2 attributed to the right text;
 * "Thanks" correctly REJECTED as not-an-answer (a bare acknowledgement is not a decision);
 * a fourth send with no reply -> left alone;
 * an already-`dismissed` row -> untouched when a reply existed;
 * the full chain: capture writes "local only, no cloud" onto the row, backfill reports
 "learned from 1 close(s)", and `owner_queue_feedback` gains
 (item_id=1, action=answered, answer="local only, no cloud").
Each test used a temp DB and removed it afterwards, per the rule that a test writing to a real
store must clean up.

WIRED. Added to `run-wake-sources.sh` (every 30 min), running BEFORE the queue-health line so
health sees updated answers. It went to silence-on-zero first and I changed it: a source that
writes a line only when it acted is indistinguishable from a source that stopped running, which
is the failure this estate keeps rediscovering. It now always reports, e.g.
`answer-capture delivered questions still pending: 0 with an inbound reply inside the window: 0`.
