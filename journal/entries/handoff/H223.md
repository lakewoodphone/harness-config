## 2026-09-15 13:56 UTC · ZABZ-YOGA · She can now order parts and update customer cases, and every write is signed with her machine

BUILT AND VERIFIED 2026-09-15, on the owner's requirement: when she orders a part or moves a repair
along, the customer's case must actually be updated, with everything from her machines signed.

WHAT WAS ADDED
* scripts/ps-shop.mjs -- drives the company's OWN shop routes over the API: customer-intake, parts
 (order), parts/quantity (stock), parts/link (attach to a repair), repair-status, send-update,
 check-uncollected. Deployed to and exercised from BOTH her machines.
* Server-side provenance. Every write sends `x-ps-source-machine`, and the authority now RECORDS it on
 the thing that changed, via a new `_provenance_machine(request)` helper in main.py threaded into the
 parts routes (shop_ops.py gained a `source_machine` parameter that appends to the record's notes).
 `customer_intake` already persisted a `source` field, so that path was covered already.

VERIFIED BY DOING IT, not by reading the code:
 POST /api/v1/shop/parts with x-ps-source-machine: desktop-fgv6kmh
 -> notes read back: "provenance verification\n[added from desktop-fgv6kmh]"
 PATCH /api/v1/shop/parts/quantity with x-ps-source-machine: lakewooechsmini
 -> notes read back: "...\n[added from desktop-fgv6kmh]\n[stock changed from lakewooechsmini]"
 The verification row was then deleted by name match (parts_total back to 0), and the API was
 restarted so the change is live.

WHY THE API AND NOT THE DATABASE, which the owner asked about by implication:
A direct DB write skips the logic that makes a change CORRECT -- status validation, SMS scheduling,
task history, cost recording -- and puts a second writer on a store this company has already lost data
from twice. The API keeps one writer and is reachable from any network. That last point is decisive
for her laptop: it reaches api.abletelsolutions.com from anywhere, and reaches the authority's network
not at all.

STILL OPEN, and named rather than hidden:
* The header is recorded on the PARTS routes. repair-status and parts/link carry their attribution in
 the payload instead (`notes` gains "[from MACHINE]", which ps-shop adds), so those are labelled but
 not yet via the header.
* Full Dialpad and the production database are reachable the same way, through the API's own routes
 (`/api/v1/dialpad/sms/send`, `/api/v1/dialpad/webcrawler/*`) rather than by direct connection, so
 nothing needs to be opened up. Not yet wired into her toolbelt.
