## THE TOOL CAUGHT A SCOPE ERROR IN THE WORK IT WAS WRITTEN TO DESCRIBE

Its first version scoped itself to notes that said **`COULD NOT BE RECONCILED`** — the failed verdicts —
and found **50** recordable orders. But the question is *"which orders claim a card payment with no
payment row behind it"*, and that is **just as true of an order whose verdict said `PROBABLE`**. Scoped
to every reconciliation note it finds **60** and **7693.03**, which is what was actually recorded.

**A tool that disagrees with the action taken is worse than no tool.** Had this been written first and
trusted, the number recording would have been 50 and 10 orders would have stayed reading `collected
0.00` for money that was taken. The docs now say to check the tool's total against the database:

```sql
select count(*), sum((to_jsonb(payment_transactions)->>'amount')::numeric)
from payment_transactions
where to_jsonb(payment_transactions)->>'metadata' like '%lpt-record-payment%';
```

## THE WINDOW, AND WHY IT IS MEASURED IN DAYS

A day **either side**, counted in **calendar days rather than elapsed hours**. Both choices WIDEN the
window, and widening is the conservative direction for an argument concluding *"this money is this
order's"*: same-day matching would reject a real pair where a charge was taken late one evening and
noted the next morning, and counting by calendar day means a same-amount charge on an ADJACENT day
**disqualifies** the match.

**Measured, and load-bearing:** 30 hours apart is **1 day** on the calendar and **more than 1** in
elapsed time. That single case flips a match into a non-match, and a test pins it — the test failed
first and the code was aligned to the behaviour the 60 recordings actually rested on, not the other way
round.
