## 2026-10-06 05:06 UTC · ZABZ-YOGA · Survivor inbound proven: captures, answers nothing, logs truthfully - after two real bugs found by firing a signed inbound

GOAL ROUND 11. (c)'s SURVIVOR IS NOW INBOUND-VERIFIED, and it took three runs because each fix revealed the next hole. NEW HARNESS: deploy/hosting-migration/survivor-conformance/fire-inbound-sms.py fires a REAL signed Twilio inbound at a locally-booted survivor (signature computed with the app's own twilio.request_validator against the configured webhook base; from=+15550000000, a reserved number Twilio cannot deliver to; plus SURVIVOR_MODE and MOCK_OUTBOUND_COMMS as belts). BUG 1: the survivor AUTO-REPLIED to the customer via TwiML - '<Message>I still have your message and I'm routing it now...</Message>' - because TwiML is delivered by Twilio and never passes through send_message, so the survivor gate never saw it. FIX: a _twiml_response() helper gating all 14 TwiML return sites in app/main.py (and the helper's own internal return was restructured to avoid self-recursion). BUG 2: after that, the reply was suppressed but sms_log still gained an OUTBOUND/SENT row for it, because the reply branches persist before handing text to TwiML - a log claiming a customer was answered, which could make a returning primary skip answering them forever. FIX: the survivor gate moved to the TOP of the inbound handler, after the inbound row is written and before any reply branch. VERIFIED: empty <Response></Response>, sms_log +1 (inbound/received only), outbound_buffer flat, 60 tests still passing. ALSO THIS ROUND: the promotion orchestrator's --standby-url path was tested against a REAL survivor for the first time - '[PASS] standby answers mode=survivor: http://127.0.0.1:8011/health -> mode=survivor' alongside '[FAIL] target has an active connector: 0 connector(s)' and a clean REFUSAL, which is exactly the intended behaviour: it recognises a genuine survivor and still refuses to promote to a tunnel with nothing behind it.
