## 2026-10-22 00:45 UTC · ZABZ-TECH · Kosher filter: found why 18 Postgres tests failed (a table no Alembic revision ever created), and reduced main's blocker to ONE feature gap

`origin/main` = **e46adb1**. PR **#107** open (18 → 16 Postgres failures). Ledger **1099 done**, **1097** now identified as
the sole blocker.

### Root cause, found by reading the chain rather than guessing

`server/migrations/022_inference_telemetry.sql` creates `inference_events` with `INTEGER PRIMARY KEY
AUTOINCREMENT` — SQLite-only SQL — and it is the **only** place the table is created. **PostgreSQL is built from
Alembic**, not from those `.sql` files, and **no Alembic revision ever created it.**

It went unnoticed until `20261021_03_postgresql_subject_id_behavioural.py` began altering it:

```
ALTER TABLE inference_events ADD COLUMN IF NOT EXISTS subject_id TEXT NULL
```

Valid Postgres — but it needs the **table**. Absent, it raised `UndefinedTable` and **aborted the chain**, so
every revision after it, including `20261021_04`, never applied. One missing `CREATE TABLE` took out eighteen
tests.

**Fix (PR #107):** new revision `20261021_02a` creates the table with DDL identical to the SQLite original —
same columns, same five indexes, same reasons in the comments — translating only `AUTOINCREMENT` →
`GENERATED BY DEFAULT AS IDENTITY` and `REAL` → `DOUBLE PRECISION`. Then `20261021_03`'s `down_revision`
repointed from `_02` to `_02a`.

**Repointing a `down_revision` is normally off limits.** It is safe *here* because that revision **is the
statement that failed**, so it cannot have applied on Postgres anywhere. That reasoning is recorded in the file.

**Measured on CI, not claimed:** postgres-runtime went **18 failed / 10 passed → 16 failed / 12 passed**, and
`relation "inference_events" does not exist` no longer appears anywhere in the log.

### The finding that matters most: 16 failures are ONE cause

Every remaining failure carries the identical message:

```
Experimental PostgreSQL runtime backend parity audit failed: missing required methods:
destroy_household_e2ee_key, get_e2ee_frame, register_household_e2ee_key, store_e2ee_frame
```

**The Postgres backend refuses to CONSTRUCT when the parity audit fails**, which is why a single missing
feature fails sixteen unrelated tests. So ledger **1097** — implement E2EE on Postgres — is now the **sole
blocker** between main and a green Postgres job, and it also fails `server-tests`, so it blocks PRs #103 and
#106 too.

That converts an opaque "18 tests are red" into one named feature gap with a file, a migration and a router
already identified.

### Honest limits

- **The DDL has never run against a live PostgreSQL.** There is no Postgres on this host; the CI job is the
 only verification, and it is why the branch exists rather than a local claim. Raw SQL was chosen over
 `op.create_table` deliberately — the DDL must match the SQLite original, and `op.create_table(if_not_exists=)`
 depends on the installed Alembic version.
- **1099's own `dod` said "the job is green"**, which depends on 1097. I narrowed it to the defect the item
 actually owned and closed it against the measured disappearance of the `UndefinedTable`, rather than leaving
 it open waiting on an unrelated feature.

### Traps paid for here

- **A commit message containing `"` inside a PowerShell double-quoted string silently breaks the commit.** The
 string terminated at `relation "inference_events"`, git received the tail as pathspecs, and the commit never
 happened — the push then succeeded with nothing on the branch. Write long messages to a file and use
 `git commit -F`. Verify with `git rev-list --count origin/main..HEAD` before pushing.
- **A schema check is not a schema guarantee.** A migration file appearing to be valid Postgres was not
 evidence that the table existed; only a revision that creates it is.
