THE DEFECT (high): AN UNRELATED EDIT SILENTLY DE-VERIFIED A LISTING
- Method: /listing/[id]/edit promises "Only what you change is saved — everything else on the listing
 is left exactly as it is." I changed ONE field through the real UI and diffed the whole owner-shaped
 listing before/after. The promise held for every field except `address_verified`, which flipped
 true -> false.
- Cause: PATCH called `updateListingAddressVerified(id, geo.verified, ...)` with a FRESH geocode result,
 while carefully preserving the PIN when the address had not changed (DATA-33). DATA-33 was
 half-applied. So any edit whose re-geocode failed — quota, network, no key — silently dropped the
 "verified location" badge and the ranking signal. **On production the key IS set, so this bit exactly
 when Google failed: intermittent and invisible.**
- Fix: one testable definition, `repository.nextAddressVerified(stored, addressChanged, geocoded)` — an
 unchanged address may IMPROVE the flag, never worsen it. Unit test covers six cases; verified end to
 end with the UI too (listing 1 marked verified -> edit Move-in only -> nothing else moved, row still
 address_verified=1 with its pin).
