## 2026-10-19 15:39 UTC · ZABZ-YOGA · Owner text channel overhaul round 1: topic ledger live, preask deployed and proven on his own complained-about questions, baseline 52% dead

## 2026-10-19 ~15:45 UTC · ZABZ-YOGA (with deploys to secratary-cloud) · owner text channel overhaul, round 1

The owner asked for the texting system to be made "way better and way smarter": too much of it
is stupid, too much of it he does not need, and the CFO asks questions it could have answered
itself. This session audited the whole channel against its own history and shipped three
changes to production. **The baseline number to move is 52% dead texts.**

### What is now LIVE on the authority (all hash-verified, `verify-owner-text.sh` rc=0, 21 files)

1. **`/root/bin/owner_topic.py`** (new, `d3fade…`→`b186c0…`) + the topic ledger in
 `/root/.owner-text/relay.db`. A key derived from what a message is ABOUT — `money:597.29`,
 `case:WO2602180002`, `task:26089`, `reminder:52` — with per-family cooldown windows
 (reminder 20 h, ask 72 h, alert 1 h, status 6 h). Two distinct answers: `topic_cooldown`
 (later) and `topic_closed` (not until something changes). 32 unit checks pass on the
 authority (`scripts/text-channel/mirror/test-owner-topic.py`).
2. **`owner_text_relay.py`** (`f6ed313f` → `2b159432`) — the ledger is consulted as Rule 1d
 inside `submit()`, and recorded **after** its `COMMIT` on its own connection, so it can
 never hold the relay's write lock. Proven on a throwaway store: two differently-worded
 reminders for the same $597.29 → `SEND` then `SUPPRESS / topic_cooldown`.
3. **`app/owner_text.py` + `app/tool_factory.py`** — the same ledger as **M1c** inside
 `gate()`, exempting `interrupt` (a person in danger must never be silenced by a cooldown),
 and recorded after a successful send. Loader fails OPEN. API restarted, `/health` 200.
4. **`/root/bin/preask.py`** (`321619c2`) — deployed for the first time; it had been absent
 from `/root/bin` with nothing calling it.
5. **`/root/bin/cfo-ask.py`** (`7e078303` → `4d30f992`) — the ladder now runs inside the
 resolve loop, before a question is composed, and its evidence is merged into the ask.
6. **`scripts/text-channel/owner-text-scorecard.py`** (new) — the outcome instrument.
7. **`deploy-owner-text.sh`** — now stages to a sibling, verifies the hash there and `mv`s
 (new inode). `install` truncated running files in place, which AGENTS.md §8 forbids.

### What is NOT done — the next session starts here

1. **The ladder is deployed, wired, and PROVEN against the two questions he complained about.**
 `run_ladder()` — the exact function the CFO loop calls — was driven with real merchant
 records: Polka Dot $299 → `owner_answer solved` in 8 ms ("you told me on 2026-10-13: 299 at
 polkadot was my wife buying a dress for the holiday") → `do_not_ask`; Newegg $362.51 →
 `owner_answer solved` in 8 ms from memory → `do_not_ask`; an unknown $123.45 merchant → all
 rungs `not_found`, `allow_ask`, and the ask carries 2 evidence clauses ("no prior answer
 that names 123.45", "no purchase row within 0.02 of 123.45"). That is both halves of his
 2026-10-16 rule working.
 **Honest limit: 2 of the 5 rungs are inert.** `docs` skipped ("no doc root configured") and
 `web` skipped (`PREASK_WEB_CMD` unset). Wiring those, or recording them as deliberately
 out of scope, is a next-session job. Also unproven end-to-end through the CLI: today had no
 unasked merchant above the $25 floor, so `cfo-ask.py --why` never reached the loop.
2. **Reminder staleness is not implemented.** §C of `docs/owner-text/OVERHAUL-2026-10-19.md`:
 a reminder still fires because it is DUE, not because it is still TRUE. The two stale
 reminders in the corpus (PayPal deadline delivered after the deadline, Telnyx false balance)
 would still send. The topic ledger stops repeats of the same amount; it does not re-measure.
3. **The conversational agent still cannot see its own last outbound** ("I don't have the
 question you're reacting to in front of me. Which one are you calling out?" 10-19 05:48).
 That is a context bug in the reply path, not a gate, and it is the single most-visible
 "stupid" thing left.
4. **The weekly audit still measures the channel, not the outcome.** `owner-text-audit.py` runs
 (wake #1207, exit 0, 812 s) and files a flag; the scorecard now supplies the outcome number
 and `--flag`, but nothing has yet been told to run it or to act on its worst family.
5. **The app process holds the pre-fix `owner_topic` module in memory** (deployed at 15:27,
 loaded at 15:13). Its `case:WORKING` false positive is fixed on disk and the bad row is
 deleted from the ledger; the running process picks the fix up on its next restart.
