## THE DEFECT, NAMED

`task_lifecycle_governor` reads a *task row* that is still open, ages it, and emits
"…N days silent"; `dept_business_ops` then composes a **customer-facing message** from that signal
alone, without reading the case file. On Felder it produced: *"recovery on this drive has not
progressed and it has been sitting too long without an update from us"* — for a job completed
2026-06-25 whose drive had been collected. Task `28554`, raised by the governor **14 minutes after**
`28536` was cancelled, added *"On decline: close case #4485 with return-drive disposition"*, which
would have told the customer to return a drive he had already collected.

Two structural facts worth carrying:
1. **The draft is GENERATED, not templated.** `grep` for the phrase across `/root/bin` and
 `/opt/company` finds nothing but vector stores. That is also why a resend produced *different text
 each attempt* — the owner could have approved one message and a different one reached the customer.
 **An approval whose payload regenerates is not an approval.**
2. `READY_FOR_PICKUP` is where **420 of the shop's orders** rest. It is a terminal resting state, not a
 queue, so order status was never the stall signal — the stale *task* was.
