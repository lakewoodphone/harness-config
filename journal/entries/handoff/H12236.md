## 2026-10-22 09:28 UTC · ZABZ-YOGA · Reload conflict measured 13/13: the boot read is served a snapshot that predates an aborted write's commit - merge-forward rule being implemented

## 2026-10-22 ~09:2xZ · The reload conflict, measured 13 of 13: the page is handed a stale answer to an honest question

Aimed reload-race measurement, 13 fresh staging identities, 476 answers, 196 `/api/persistence` exchanges, evidence in `_pt_race/logs/` and `docs/verification/race-409-2026-10-22.md`.

**Result: 13 of 13 attempts produced exactly one 409, always on the first write after the reload.**

The chain, identical every time: a save is in flight (`expectedRevision=5`) → the person reloads → the page kills the request (`net::ERR_ABORTED`) but the server's transaction commits anyway (library to revision 6) → the resumed page's boot read is **answered with revision 5**, because it was served from a snapshot taken before that uncommitted write landed → the first write is issued with the read's own answer 34 ms later and is refused, `currentRevision=6`.

Classification: the first post-reload write preceded the boot read's answer **0 of 13**; it carried the boot read's own value **13 of 13**. So the fence from `5589583` works exactly as specified and cannot close this: a fence on "the read answered" is useless when the read cannot see an uncommitted write that is slower than the read (PUT 1.0–3.8 s, boot read 0.9–1.1 s).

**Rate caveat that matters:** every reload here was AIMED at a save open ≥500 ms. The earlier "2 of 13" was almost certainly un-aimed reloads. So this bounds reachability under the condition that produced the original failure, not a person's odds of hitting it by chance.

**The fix, and why it is safe:** the intervening write at revision 6 was this same device's own aborted save of this same attempt, so the server holds strictly older state; replacing it is not a lost update. A merge-forward is therefore allowed exactly once, and only when all three are provable — `currentRevision == expectedRevision + 1`, the server's library names this same record id, and the server's answered count is ≤ the browser's. Any failure of a condition keeps today's behaviour: surface, stop writing, never overwrite. Three negative tests, one per condition.

**Also learned:** the queue already models "this device issued a write and got no verdict" for transport failure (`unconfirmedIssueRevision`, `conflictAttribution: this-device-unconfirmed-write`) — the knowledge simply dies with the page. A durable marker written before the PUT and cleared on a settled answer, or a server-side idempotency key, would make the suspicion survive a reload; the merge-forward derives the same conclusion from server evidence and needs no new storage.

**Deploy plan** written to `_pt_status/DEPLOY-PLAN.md`: what ships, the preconditions, the exact steps (image tag → verify the rollback image exists → deploy with a gate that can fail → read its own line), post-deploy verification, the rollback command that now actually runs, and the known limits stated rather than discovered later.
