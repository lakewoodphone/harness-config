## BROKEN / CORRECTED - read this before believing the lock errors are fixed

**`busy_timeout` did NOT fix the `database is locked` errors.** After the fix was live and the
service restarted, a burst of **62 errors at 16:41:00Z**, all from `app.services.mashgiach`. Cause:
`daily_scan` runs SELECTs and then per-finding `INSERT`+`commit` on the same connection, so the write
must upgrade a read transaction - `SQLITE_BUSY_SNAPSHOT`, which the busy handler does NOT cover and
which fails **instantly**. Full mechanism in **L2124**.

Next action for this, precisely: in `mashgiach`, take `BEGIN IMMEDIATE` before the reads that precede
writes and batch the findings into one transaction, instead of 20 individual commits. Do not reach
for a bigger timeout - it cannot help this failure mode.
