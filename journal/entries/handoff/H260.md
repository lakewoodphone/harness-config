- **It retracts PART-119 F-7**, which three parts of this record had carried as a production defect.

THE RETRACTION, AND THE EXPERIMENT THAT PRODUCED IT
- The claim was: "reuse detection fires, the revoke-all it triggers throws, and the suite stays green",
 evidenced by a suite warning `Failed to fully revoke sessions after refresh-token reuse /
 Cannot read properties of undefined (reading 'map')`.
- **The throw is the test harness's own mock, not production.** `mockSessionDb.findByUserId` is declared
 `vi.fn()`, returning `undefined`, so `.map` throws. In production the method is
 `prisma.session.findMany`, which returns an array — and I confirmed the method is present in the deployed
 bundle (`dist/services/auth/database.service.js:315`), which is what made the mock the only consistent
 explanation.
- **Three states, one line changed, same code:** suite as written → 41 passed + warning; mock changed from
 `vi.fn()` to `vi.fn(async () => [])` → 41 passed, warning gone; reverted → 41 passed + warning back.
- **What survives and is still worth fixing:** *no test asserts that the revocation happens.* The test stubs
 a revoked token and asserts only `success === false`. Delete the session-deletion loop tomorrow and the
 suite is still green. So the accurate finding is "the security response is unasserted", not "it is broken".
- I did NOT resolve this by re-reading code. I made the smallest change that would disprove the claim and
 read the result. It cost one line and one run, after three parts of believing the message.

REAL FINDINGS THIS PART
- **F-2 High:** `changePassword` and reuse-revocation revoke refresh tokens but **do not delete sessions**, and
 `validateToken` authorises on the session row — so a stolen access token survives a password change for up
 to 7 days. `revokeOtherSessions` **does** delete them (`:1102-1106`), one method away.
- **F-4 Medium:** every session is created with `userAgent: 'unknown'` and no IP or device hash
 (`:424-425`, `:642-645`), because `AuthService` receives no request context. Device trust, geo-anomaly and
 "revoke this device" are unreachable **by construction, not merely unimplemented**. `sessions.deviceHash`
 NULL on 287/287; `user_devices` 0 rows.
- **F-5 Medium:** `logoutUser` revokes every refresh token for the user, not the current session's.
- **F-6 Medium:** `registerUserWithPhone`, `loginWithPhonePassword` and `loginWithPhoneCode` write Session +
 RefreshToken **inline** with a hardcoded 7-day TTL instead of calling `createLoginSession`, so the choke
 point is bypassed and a TTL change has four places to miss.
- **F-7 Low:** **six places** encode how long a session lasts (`SESSION_TIMEOUT_MS`, `JWT_REFRESH_EXPIRES_IN`,
 three literals, the production env override) and nothing asserts they agree.
- **F-8/F-9 recorded as correct, so they are not "improved" away:** the `lpt_refresh` cookie is exactly right
 (HttpOnly, Secure in prod, SameSite=None, domain-scoped, access token in the body and never in the cookie),
 and rotation is done in the right order — revoke the old token, then create the new one, with the new session
 first, so a crash mid-rotation cannot leave two live refresh tokens.

WHY IT MATTERS BEYOND THE CORRECTION
**The 7-day access token fix is now UNBLOCKED.** PART-119 recorded it as blocked on F-7 and deliberately did
not apply it. F-7 turned out to be a test gap, so the block is gone, and the correct sequence is now:
assert the revocation (F-3) → delete sessions on `changePassword` (F-2) → then shorten `JWT_EXPIRES_IN` from
`7d` to the code's own `15m` default. Doing the TTL first would make F-2 worse, not better.
