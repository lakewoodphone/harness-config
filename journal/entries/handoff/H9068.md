## 2026-10-19 01:46 UTC · ZABZ-YOGA · The authority-disk report was unsafe to execute: 90-day prune deletes 0 rows, the archive is missing a machine and pre-9-Oct history, the lossless lever is the 11.3 GiB FTS duplicate - and I nearly filled the disk auditing it

## 2026-10-19 02:00Z · ZABZ-YOGA · The authority-disk report was unsafe to execute; the lossless lever is the FTS duplicate, and I nearly filled the disk auditing it

### What the job was

The owner handed over `docs/incidents/2026-10-19-authority-disk-96pct.md` — a previous session's
report saying the authority was at 96% and asking another agent to execute it — and said:
*"analyze and audit this end to end and figure it out… solve any problems robustly without losing
any information."*

### The three findings that change the answer

1. **The report's central step is a no-op.** Its §6 Step 4 prunes `dsh_session_events` older than
 90 days. Measured in one streaming pass (`/root/retention-bytes.txt`): the corpus starts
 `2026-09-11T19:19:34` and is 38 days old, so **90 days deletes 0 rows / 0 bytes**, and 60 days
 deletes 0 too. 30 days would delete 574,739 rows / 2.39 GiB; 14 days 1,214,389 / 4.87 GiB.
 Every reclaim figure in the report is arithmetic on a deletion that cannot happen.
2. **Pruning at any window that would delete rows is unsafe for a reason nobody had checked.**
 The packed archive holds **nothing before 2026-10-09T02:52:27Z** while the database reaches
 back to 2026-09-11, so a 30-day prune destroys the only copy of 574,739 events. It has also
 **never pulled `desktop-fgv6kmh`** (42 sessions, 7,822 events, database only). And it is a
 *redacted derivative*: `--read` reports `ok:true` while 16.5% of records fail to parse because
 the card rule rewrites 13-digit epoch-ms timestamps into `"time":[REDACTED:card]`.
3. **The lossless lever is the FTS duplicate, not retention.** `dsh_session_events_fts` has no
 `content=` clause, so it stores a verbatim second copy of every `raw`: ~11.3 GiB of the 31.2 GiB
 file, corroborated by the table's own 10.47 GiB of raw text. Converting to external content
 (`content='dsh_session_events', content_rowid='rowid'`) plus triggers loses **nothing** — the
 text stays in the base table. It needs **no free disk space**: the pages go to the freelist and
 future writes reuse them, so the file stops growing for ~11 GiB of new data (~7 months at
 1.5 GB/day). Blockers: `dsh_session_ingest.py:435-447` inserts with auto-assigned rowids and
 deletes via `dsh_session_events_fts_content`, both incompatible with external content, so it is
 a code change + API restart + rebuild, not a SQL one-liner.

### What I changed on the box (the only write I made)

`/usr/local/bin/disk-guard.py:133` was `pct = (used / total * 100.0)`. With ext4 reserving 5%
(`total = used + avail + reserved`, reserved measured at 6,571,532,288 B) it under-reported by ~4
points: `WARN 90` meant df 93.8%, `CRIT 95` meant df 99.0% — i.e. unreachable before zero, and
this filesystem reached zero on 2026-09-27 and 98.7% on 2026-10-13. Changed to
`used / (used + free)` and deployed by atomic rename; verified live at 89.0% against `df` 90%.
**Trap:** `/root/bin/disk-guard.py` is a *symlink* to `/usr/local/bin/disk-guard.py`; my first
`mv` replaced the symlink with a regular file and the fix went nowhere. Symlink restored, fix
applied at the target. Cron runs `/usr/local/bin/disk-guard.py --write-status` every 15 min.

### What I broke, and how it was contained

I ran unindexed aggregates — `GROUP BY substr(created_at,…)` and `COUNT(DISTINCT session_id)` — over
`dsh_session_events`, and dispatched five agents whose briefs authorised the same. With no index on
`created_at`, each builds a sorter and SQLite writes it to `/var/tmp/etilqs_*` **on the database's
own filesystem**: measured spills of 5.8 GB, 4.0 GB, 5.0 GB, 1.8 GB. Free space went
**6.44 GiB → 1.41 GiB in seven minutes and was falling 100 MB/s**. The file is unlinked, so `du`
never sees it — only `lsof -nP +L1` does — and `SIGKILL` was not delivered because the process sat
in `D` state. Recovered with `truncate -s 0 /proc/<pid>/fd/6`. Filed as `L9214` / `P8396`.
**Safe shape, verified spill-free (2m11s, whole table):** `count(*)`, `sum(length(raw))`,
conditional `sum(case when … end)` — no sorter. Also spill-free: `group by source_machine,
session_id` (covering index) and `rowid between X and X+199999`.

### Facts worth not re-deriving

* Disk is **not leaking, it thrashes**: 6.93 GiB free (96%) at 01:22 → 1.41 GiB (100%) at 01:30 →
 16.7 GiB (90%) at 01:46. Guard log shows flat 9.7 GB from 23:00 to 00:00 then a step. Any plan
 built on one `df` reading is built on a number that no longer exists.
* `authority.db` 33,507,471,360 B; pages 8,180,535 × 4096 = exactly that; freelist 1,421 (not
 bloated). Growth +1.2 GB in 19.5 h (~1.5 GB/day).
* `usearch.db` 10,851,082,240 B (derived, regrows; the 2026-10-18 record measured it at
 **5.8 GB/h** during a bulk push — that is the documented killer, not the DB).
* **`/opt/company/scripts/dsh_session_events_retention.py` already exists** (dry-run only) — use it,
 do not build another. But its `per_day()` does `GROUP BY … ORDER BY`, so running it against the
 authority **spills and reproduces the incident** (measured: 18.0 → 13.4 GiB free).
* **The alarm fired and was suppressed**, not missing: `sources/disk-space.py` logged
 `disk-space:90: suppressed:attempts` on wake guard 9 (`max_attempts` 2), `guard-registry-check`
 exits rc=3 "condition, not fault" which files no repair, `guard.log` has no reader. The owner's
 row **711** ("reclaim 13.2 GB of worktrees, or grow the disk?") has been `pending` since
 2026-10-18T19:21:07Z.
* **A sibling agent emptied six worktrees under `/root/work` at 01:34:57Z** (~6 GB, 12.8 GB freed
 in that 7-minute window) while row 711 was still pending — unattributed, `auditd` and `acct`
 inactive, non-interactive ssh leaves no history. `r4-loop` still shows
 ` M scripts/ha/check-security-absence.py` + untracked `CHECKPOINT.md`. A lock will not stop a
 racer that is another agent; use `flock` plus a `ps` check for sibling sessions.
* Quiet window **02:30–04:00Z = 22:30–00:00 New York**. Long SQLite jobs: cap at **4 GB**
 (`MemoryMax=12G` on company-api; four pythons OOM-killed at ~12.5 GB on 2026-10-18). WAL grew
 from 64 MiB to 322 MiB under load in 20 minutes.

### What is now different, and what is next

Different: the report is marked superseded with a banner; `…-AUDIT.md` is the current record with
every number and its command; the disk guard tells the truth. **Nothing was deleted and no database
byte was changed.**

Next, in this order — none of it started:
1. Prove the external-content FTS migration on a small copy (DDL + triggers + rebuild), then deploy
 in a quiet window with a `flock` and a sibling-session check. Zero information loss, ~11.3 GiB.
2. Pull `desktop-fgv6kmh` at least once, and fix `CARD_SHAPE` so it stops destroying epoch-ms
 `time` fields — the archive is silently corrupting the training corpus at ~1 record in 7.
3. Backfill pre-2026-10-09 history from the source machines if their local stores still hold it.
4. Only then is a prune safe, and only then is `VACUUM INTO` worth its 16–20 GiB peak.
5. Retune the guard thresholds (one variable, separately): 90/95 now mean 93.8%/99.0% df.

### What still hurts

The authority's own **read-only** queries can fill its disk, `temp_store` is unbounded, `/var/tmp`
is on `/`, and the only check that sees the spill is `lsof +L1`. Nothing has been changed about
that; any future audit of this box will hit it again unless the brief says "streaming aggregates
only, free-space check first".
