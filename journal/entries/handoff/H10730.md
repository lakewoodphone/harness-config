THIRD BATCH. /admin/export/{proxy_phone,runtime_phone,trust_phone,trust_overview}.json had no test. These are how an operator takes a phone's history off the system, so an export is the one place where a mistake LEAVES THE BUILDING - it becomes a file on somebody's laptop.

THE ASSERTIONS ARE ABOUT THE FILE, NOT THE STATUS CODE:
 Content-Disposition: attachment - an export not offered as a download is a page, and a 200 carrying text/html would be FastAPI answering with an error page and calling it a file;
 the JSON parses and is an object;
 **the phone's API token appears nowhere in the body** - if it did, whoever holds the downloaded file could speak as that phone. Nothing in the code suggested it would leak, which is exactly why asserting it is worth the four lines;
 an unknown phone is 404, so an empty export cannot be mistaken for a quiet phone;
 401 without credentials, before anything is read.

All four passed first time. That is the happy case, and also the case where the assertion earns its keep: the leak test is now permanent and costs nothing to keep.

THE PATTERN ACROSS THREE ROUNDS OF TEST-WRITING: every module taught me something no document said. Feature flags: the body is the flags object itself, not {"payload": ...}. Self-audit: an operator session from a previous request authenticates the next one, so "no header" is not "unauthenticated"; and POST /admin/households/{hid}/phones writes only the mapping, so an assigned phone 404s until it checks in. Exports: attachment disposition and the token-leak property. Four facts about this system that lived nowhere until a test was written, and one of them - assigned vs live phone - is a distinction an operator could get wrong at the counter.
