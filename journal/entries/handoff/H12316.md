### The finding that matters most: the reset anchor is never armed on the adb seal route

I verified this in the source myself rather than taking a lane's word:

- `ResetProtectionAnchorStore.arm(...)` is called at `deviceowner/AdminReceiver.kt:97` — **inside
 `onProfileProvisioningComplete` only**, reason `"profile_provisioning_complete"`.
- The route the shop actually uses is `dpm set-device-owner` (`scripts/counter_install.ps1`), which
 **does not deliver `PROFILE_PROVISIONING_COMPLETE`** — the app's own comment at
 `AdminReceiver.kt:31-33` says so. That route fires `ACTION_DEVICE_OWNER_CHANGED` (`:34`) and
 `onEnabled` (`:57`), both of which call `applySealPolicy` → `SealPolicy.applyAtSeal` →
 `PolicyApplier.apply`, and **neither arms the anchor**.
- `PolicyApplier.kt:575-579` then reads the store, finds nothing, falls back to
 `R.string.frp_google_account` (empty — `strings.xml:735` "Leave blank to skip FRP"), and sets no
 FRP policy. The app logs exactly that: *"FRP policy not set: no reset-protection anchor was armed
 at setup"*.
- `dpm set-device-owner` also **requires no accounts on the device**, so there is no generic FRP
 either.

**Consequence: on every phone the shop seals today, a factory reset leaves a phone that anyone can
set up again.** The design's central promise — D-20261021-05, the reset anchor is the chaver's
account, ours when there is none — has no implementation on the one route in production. This is the
highest-value defect found so far and it was invisible in 839 green unit tests and in the readiness
audit.

Second, independent FRP fact from the emulator: `dpm.getFactoryResetProtectionPolicy` throws
`UnsupportedOperationException: The persistent data block service is not supported on this device` —
so FRP cannot be exercised on an AVD at all. It needs hardware *and* the arming fix.

### Four more findings from that lane, each changing something

1. **D35-04 / the enrolment route.** Plain `dpm set-device-owner` on a provisioned device fails with
 `IllegalStateException: Not allowed to set the device owner because there are already some
 accounts on the device` while `dumpsys account` reports `Accounts: 0`. The words are DPM's shared
 refusal text; the real gate is `device_provisioned=1` / `user_setup_complete=1`. It succeeds only
 after zeroing both and rebooting — so the unprovision-and-reboot step in
 `scripts/emulator_full_provision.ps1:341-356` is **load-bearing, not defensive**.
2. **A debug build is not "nothing enforced".** `AntiEvasionPolicyManager.expectedUserRestrictions`
 applies `no_install_unknown_sources`, `no_usb_file_transfer`, `no_create_windows`,
 `no_modify_accounts` unconditionally, so they are set on debug builds too. The readiness audit's
 "a debug build locks nothing down" is true only of the eight release-gated restrictions.
3. **A contradiction between a decision and the code.** `D-20261022-02` §3 says
 `DISALLOW_BLUETOOTH_SHARING` is **withdrawn** as an idea. The code still applies it at
 `AntiEvasionPolicyManager.kt:269-271` for `sdkInt >= 34`, and the instrumented run confirmed
 `no_bluetooth_sharing` is in the enforced set on API 34. **The owner's instruction is that we do
 not block Bluetooth file sharing**, so the code must drop it — that is a live customer-facing
 defect on every Android 14+ phone today, and a decision the code does not obey.
4. **`connectedDebugAndroidTest` targets attached physical phones unless `ANDROID_SERIAL` is set.**
 Two real devices (`616202539`, `616574160`) are attached to ZABZ-TECH. Running the suite blind
 would install a **debug** filter on real handsets. Every future run sets `ANDROID_SERIAL`.

Also unexplained and recorded as unexplained: `settings get secure always_on_vpn_lockdown` reads `1`
on a debug build although `PolicyApplier.kt:644` passes `lockdown = !BuildConfig.DEBUG`. Cause not
established. And the AVD carried state from an older package name
(`com.kosherfilter.client/...LockdownAccessibilityService` still in `enabled_accessibility_services`)
before `-wipe-data`, which is a plausible stale-state hazard on a re-sealed handset.

### Integration hazards learned, to apply every round

- **Sync each lane with `origin/main` before merging, never after.** Every lane branched at
 `37aa6bac`; after #168/#169 the unsynced diff showed my new `docs/` files as *deletions*. Merging
 without syncing would have silently reverted them.
- **`git worktree` does not inherit gitignored `android/local.properties`** — write
 `sdk.dir=C\:\\Users\\ezabz\\AppData\\Local\\Android\\Sdk` before a lane's first Gradle call.
- **A flag with no consumer is worse than no flag**, and a test whose name contradicts its assertion
 is the same defect in the suite (the monitor lane renamed
 `browserProfilesSkipAccessibilityMonitoring` → `browserProfileLeavesTextToTheProxyAndJudgesImagesOnDevice`).
- **`gh pr create` with backticks in a PowerShell double-quoted string mangles the body** — use
 `--body-file`.
- Durable findings list with severities: `C:\Users\ezabz\Code\_kf-lanes\findings.md` (F1-F12 and
 growing). Read it at the start of the next round.
