## 2026-10-22 07:20 UTC · ZABZ-TECH · Kosher filter: Play Integrity accused the phone when the build was unprovisioned — fixed (8903ae2), 769 tests green

`origin/main` = **8903ae2** (merge of PR #127). Ledger **1078 done**. 769 Android tests, 0 failures.

### The defect

`maybeRefresh` did this when the cloud project number was absent:

```kotlin
) ?: run {
 clearError(context) // and the reason for the silence goes with it
 return
}
```

So an unprovisioned build left `latestToken` **null** *and* `latestError` **null**, and `evaluateVerdict`
turned that pair into `verdict="fail", reason="integrity_token_unavailable"`. **A correct, unrooted,
bootloader-locked phone reported FAILED INTEGRITY**, with nothing anywhere saying the cause was a missing
build property rather than a compromised device.

### The fix

The decision became a pure function with four distinct reasons, because each has a different fix:
`empty` (property not set), `not_a_number`, `not_positive` (a placeholder). `maybeRefresh` now **records**
the reason instead of clearing it, so the verdict carries it.

The existing `play_integrity_request_failed:*` is untouched and deliberately **does not share the prefix**:
that one means Play was asked and refused, which is a **device** question. Those two must never be
confused again.

Both now-dead private helpers were removed rather than left to make the old behaviour look reachable.

### What this does not do

It does not provision Play Integrity. A release still needs `LPT_PLAY_INTEGRITY_CLOUD_PROJECT_NUMBER` at
build time — that number comes from a Google Cloud project, which is an account-level decision, not a code
change. What changed is that an unprovisioned build now says so instead of accusing the phone.

### The trap that cost a CI cycle, and is now understood

**PR checks run on the MERGE ref, not on the branch.** My counter said 140 because that was right for my
tree; CI computed 141 because **main added `AssetReaderAgreementTest.kt` while the branch was open**. Same
reason three generated documents were stale. So: **counters and generated docs must be produced on a merge
with current main**, not on the branch — a local `docs_check` green is not evidence about CI. Merge main,
recount, regenerate, then push.

Second, smaller: editing a file moves its last-change date, so `docs/IMPLEMENTED-VS-DESIGNED.md`'s
`updated:` front matter went stale the moment my own script rewrote its counters line. Bump it in the same
commit.
