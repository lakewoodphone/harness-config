# What the automation IS (one paragraph)

`company-api` on **secratary-cloud** (the authority) owns it. Two APScheduler jobs: `shabbat_program`
(every 15 min, acts only 10:00–13:00 local) writes the plug's OWN power-on schedule for the coming
weeks, and `shabbat_execute` (every minute) fires the actions. At the cut it does, in order:
hold the interior maglock relay released and PROVE it (`switch.smart_switch_l4` over Zigbee2MQTT,
`on` = LOCKED) → force the ceiling light on and read it back (`switch.deserted_house_lights`) →
ask HA to stop gracefully → cut the plug, which powers Home Assistant and the cameras together.
The door is a HARD GATE: without a proven release it refuses to cut and says so. Motzei is
device-side (the plug's own ON schedule), then the relay relocks, the tamper automation is
re-enabled and the light is re-asserted, with an every-minute recovery for anything incomplete.

1. **`verify-shabbat.sh` was lying.** The schedule-drift check compared the device against ONE
 window computed from "tomorrow 10:00" for both directions, so it called a job MISSING the day
 before the programmer was due to create it — measured today: `FAIL 27 18 7 11 *` on a correct
 device, because 7 Nov only enters the 14-day lookahead at tomorrow's run (window end moves
 2026-11-05 → 11-06). Create-check now uses the last program run's window, stale-check the next.
 Same live state, before: 1 FAIL. After: 20/20 PASS.
2. **The reprogram could fail silently.** 15-minute retries, every failure log-only — that class
 already cost three mornings in seven (P3131). Now alerts the owner, once per local day.
3. **`scripts/shabbat/preflight-shelly.py` (new), on root cron every 15 min.** Acts only inside
 the 3 h before a cut. Checks the plug, Home Assistant, the REAL maglock relay (via
 `get_interior_maglock_state` — not `shabbat_interior_lock_entity`, see below), the same
 interlock the executor uses, and the API's own scheduler. Alerts the owner ONCE per cut.
 It is deliberately outside the API process: a wedged API (P3005/P3006, which is what the
 Oct 18 alert cannot see) is invisible to every check that lives inside it. Tested in three
 states: healthy → exit 0 silent; broken path (plug/HA/API pointed at a dead port) → names all
 five and exit 1; outside the window → exit 0. Run under `env -i` to prove cron can start it.
