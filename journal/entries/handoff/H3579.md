## THE FINDING THAT MATTERS MOST

**`COMMUNICATION_PROVIDER` is UNSET in production, and the factory defaults an unset
value to `noop` — a provider that logs and does not send.**
(`backend/src/providers/communications/factory.ts`: `process.env.COMMUNICATION_PROVIDER || 'noop'`.)
The Dialpad key and `BUSINESS_PHONE=+17326552355` are both present; only the switch is off.

So the pay notice **cannot reach a customer** until that is decided, and neither can
anything else routed through that factory. The text reached the owner only because I set
the variable **for the single `docker exec` process** — `docker exec -e COMMUNICATION_PROVIDER=dialpad` —
so nothing else on the host changed. Before that, `approvePayNoticeDraft` refused with
`SENDER_NOT_CONFIGURED` and sent nothing, which is the correct behaviour.

Proof this is not theoretical: production recorded `communications` **140784** at
19:21:49 — the automatic completion text for WO2610120002, status **FAILED**, error
`Twilio has been removed or is not configured in this environment`. Exactly the dead
completion rail the 2026-10-12 audit reported, now with a row instead of an inference.
That row is also the reason the pay notice exists at all.

## MY OWN MISTAKE, ON THE RECORD

I ran `docker exec lpt-backend printenv COMMUNICATION_PROVIDER DIALPAD_API_KEY …`. **Give
`printenv` several names and it prints VALUES ONLY, with no `NAME=` prefix** — so my
masking never matched and the full Dialpad API key came back into this session. This is
the P13b shape again.

- `rg -F <key> ~/.dsh/sessions` → **no match**, so it is not (yet) sitting in a session
 file on this laptop. It IS in the live transcript this session will persist.
- The key's legitimate homes: `/home/zabz/personal-secretary-mvp/.env` on the authority,
 `/opt/lpt/.env` and `/opt/lpt-test/.env` on lpt-apps.
- The remedy is a rotation, which needs the Dialpad admin console. Filed as owner question
 **#450** with the recommendation: he creates a new key, I replace it in all three env
 files, recreate both backends, verify a send, and only then is the old key deleted —
 so the shop never has a window with no working business line.

**RULE FOR THE NEXT SESSION, and it costs nothing to follow:** never `printenv` a secret
by name into a transcript. To learn only whether a variable is SET:
`docker exec c sh -c '[ -n "$VAR" ] && echo SET || echo UNSET'`. To read a value, mask it
in the same shell that reads it, and never let the raw value reach stdout of the caller.
