**TWO PRODUCTION DEFECTS FOUND AND FIXED — the first is the serious one.**
1. **The live database was inside the container's writable layer.** The deployed `.env` carried `LPT_DATA_DIR=C:\Users\ezabz\Code\kosher-filter-ai\server\data` — a **Windows** path copied from a local machine — with a relative `LPT_DATABASE_PATH`, so inside Linux the app opened `/app/C:\Users\...\server\data/broker.sqlite3`. The mounted `/data` volume held a stale file nothing read, and **the documented deploy (`docker compose up -d --build`) would have silently destroyed the database with the container.** Fixed to `/data`; the live DB was checkpointed and copied onto the volume *first*, with every previous file kept under `/opt/filter-broker/backups/`. This is the third time this business's data has been one command from loss, and the first time it was caught before the command.
2. **The image was three weeks behind and its `migrations/` folder older still**, so `migrate.py` reported "No pending legacy SQL migrations" while `phone_consents` (migration 021 — the parental-consent ledger, COPPA §312.5(a)(2)) **did not exist**. The folder that matters is the one **baked into the image**; copying `migrations/` to the host changes nothing until the image is rebuilt. Now applied and verified: `phone_consents: True`, newest migration `021_phone_consents.sql`.

**AND THE FACT THAT MADE BOTH SAFE, WHICH NOBODY HAD MEASURED: production holds no customer data at all.** `phones`, `tenants`, `households`, `operator_accounts`, `phone_households`, `tenant_billing_state` and `heartbeats` are **every one of them 0**, and no heartbeat has ever been recorded. The non-empty tables are proxy metrics (1,198 events / 514 buckets) and a uniform **164** rows in `decisions` / `canary_probes` / `access_requests` / `entity_graph_events` — probe-shaped, not traffic. **The product has no live customer yet.**
