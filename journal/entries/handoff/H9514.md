## Addendum to H9513 (same session, round 2) — the loop can now measure whether the fix is holding, and two claims in H9513 are now sharper

### What changed after H9513

1. **The scorecard gained a CONFORMANCE census** (`scripts/text-channel/owner-text-scorecard.py`,
 commit `78711657`). Dead-text rate answers "did this text do any work" and moves over weeks,
 which makes it useless for "are the guards holding". The census takes every text that actually
 reached him in the window and asks the guards that are live now whether they would refuse it.
 **First reading, 14-day window: 18 of 77 delivered texts (23.4%) — 16 internal prose, 2
 credential requests.** That is the number that should go to zero. The wake source
 (`/root/bin/sources/owner-text-scorecard.py`) loads this file by path; verified by importing the
 source and confirming it resolves to the patched file and that the module exposes
 `conformance()`.
 It dedupes by sid before counting, because `sms_log` records one send twice.

2. **`[Budget exceeded for <agent>: <reason>]` no longer exists as a reply** (`/opt/company`,
 commit `c46ed9755`). It was delivered to his phone twice on 2026-10-08. The composer is
 `run_assistant_chat`, which serves ANY channel — including customer-facing ones that the relay
 guard does not cover. `reply` is now a human sentence; `budget_blocked` stays True and the exact
 agent id and reason moved to `budget_detail`. API restarted, `/health` 200 at 0.033 s.

### Corrections to H9513, measured in round 2

- **"Two paths deliver the same text" is wrong and was already corrected in the audit doc; the
 measured truth is stronger.** Duplicate *deliveries* do exist in the corpus — 14 distinct bodies
 — but **the newest is 2026-06-12**. All fourteen are March–June 2026, i.e. before the relay
 existed. Duplicate delivery is historical; what was live until today was one delivery recorded
 twice (27 extra rows over 300 real sids) and a suppression recorded as a failure. Do not quote
 "duplicate sends" as a current defect; quote the record, not the delivery.
- **Family-chat contamination is historical and cannot block.** 22 `owner_text_turn` rows carry
 `reason='family_chat_owner_leg'`, newest 2026-10-18T01:12. The string does not exist anywhere in
 the code (the live agent id is dotted: `family_chat.owner_leg`), so nothing produces it now, and
 **0 of those rows hold a turn open** — so they consume no part of the one-at-a-time budget. The
 live harm was the operational notices, which are now silenced.
- **Two turns are open right now** (152 at 16:42, 151 at 14:12), both `send_message`. Not blocked —
 a text went out at 16:42 — so this is the class-based coexistence the gate allows, not a wedge.
 Worth reading before assuming "one open turn" is an enforced invariant.
- The relay guards produce the reason code `credential_request` while the guard function
 `credential_request()` returns the MATCHED PHRASE (`login`). A check written as
 `got.startswith("credential")` on the function's return value is wrong; read the code off
 `submit()`'s verdict/reason, not off the guard's return.
