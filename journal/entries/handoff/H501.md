# H499 — round 17: a customer was made visible, and the exposure that created was closed

## THE FINDING THAT MATTERED MOST

`lp140wfh-screen-gutterman-2026-09-01.json` was in the **old format** — `record_type: "sync_record"`,
snake_case keys, no `caseId` — so the sync reader **discarded it**. **The customer was invisible to the
company.** This was `GAPS-2026-09-16 §D4`, the one audit finding that meant a real person could not be
found by the system.

The record carried real data: a **Dell Latitude 3450** (chassis P169G, Service Tag 5RHB184), a
confirmed 14-inch FHD matte IPS panel designated **LP140WFH**, a **paid** order from laptopscreen.com
(order 1788799299, $65.84, lifetime warranty, panel shipped B140HAN04.6), and two sourcing options.

## WHAT I DID, AND WHAT I DELIBERATELY DID NOT

Converted to the canonical envelope, **every value taken from the old record or the case file — nothing
invented.** The schema's blocks are mostly `additionalProperties: false`, so material with no canonical
home went where it could live honestly:

- the device narrative became `device.summary`;
- the service tag, sourcing options and cost basis are recorded in `pricing.note`, **explicitly
 labelled** so nobody reads the $65.84 PayPal payment as a customer charge;
- **`pricing.quoted` is OMITTED** rather than set to `null` or `0`. The schema types it as a number and
 there is genuinely no customer quote in the legacy data. Omitting says "not recorded"; `null` fails
 validation and `0` would assert a free job. **That is the difference between "unknown" and "zero", and
 the validator caught my first draft at exactly this point.**

The original is preserved at `docs/customer-operations/_legacy/…legacy.json` — **moved out of
`sync-records/`**, because that directory is indexed as `*.json` by both the case indexer and the push
tool, and a stray legacy file there is a second malformed record waiting to confuse the next reader.

**Validated before writing:** jsonschema → VALID.

## THE EXPOSURE THIS CREATED, AND THAT I CLOSED

**Making the record readable made it look pushable.** The tool reported:

```
CREATE lp140wfh-screen-gutterman-2026-09-01.json
 would CREATE a new order and a new customer row
```

…for a case whose replacement panel had been **ordered and paid for but not yet arrived**. Cause: the
tool read `shouldSyncToWebsite` and **nothing else** — `grep -c syncHoldReason` → **0**. So a record
could state exactly why it was waiting and be pushed anyway, which is **worse than saying nothing,
because the reason was ignored on purpose.**

Fixed in `personal-secretary-mvp defc35d5`: **Rule 0b** placed immediately after Rule 0 (same kind of
statement, one level less absolute — `shouldSyncToWebsite=false` says "never publish"; `syncHoldReason`
says "publish when this no longer applies"), plus `sync_hold` added to **`_GUARD_REFUSING_KINDS`**,
whose own comment says it is the ONE place the kinds live *"so a new rule cannot be reported as SKIP by
the dry run while a real run quietly writes anyway."*

**A gate that only holds in the dry run is a gate that fails open in production.**
