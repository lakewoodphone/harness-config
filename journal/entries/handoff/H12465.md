## 2026-10-26 00:10 UTC · ZABZ-TECH · LPT counter money path: test promoted to main and deployed to production, verified live

**What the owner asked for, and what happened.** He could not charge a card on the LPT counter sale page, and said he had reported it a week earlier. Investigation found three independent defects and two environments that had drifted apart.

**1. The order number collided — that is what stopped the sale.** `docker logs lpt-backend` showed `Unique constraint failed on the fields: (orderNumber)` twice at `19:59:36Z` before the third attempt landed; the Stripe intent the sale opened (`pi_3UUXZtLnlgYj1gmT0JWKTiu3`) is still `requires_payment_method`, and order `WO2610250003` (#3241, 10.66) was left open and unpaid. Root cause: two generators for one column. `work-orders/work-order.service.ts` wanted a four-digit suffix and used `orderBy desc`; `services/workOrderService.ts` derived the number from `prisma.order.count()` (every order ever written, padded to four), which is where `WO26102512773` came from. The first generator read that five-digit suffix as "no number today", restarted at `0001`, and collided once per order already issued. Both services now ask `work-orders/order-number.ts` (PR #657).

**2. A settled sale threw its receipt away.** `handleCreateCase(keepFormOpen)` shared one branch with "create with no work order", so a sale that had taken money closed the sheet and navigated — in the counter that is "it went back to the work order page" (PR #656). And closing an unused card box left a payable Stripe intent and an open SALE order behind for ever: production was carrying three (#3142 15.99 on 2026-10-20, #3009 and #3011 at 15.00 on 2026-10-08) and nothing had ever mentioned them. `payments.abandonCardCharge` now cancels the intent and releases the order (PR #658).

**3. Nothing compared Stripe to our books.** `scripts/ops/reconcile-card-money.mjs`, installed as a 30-minute cron on `lpt-apps`, reports: a charge our backend created with no ledger row; a charge Stripe holds that the website did not create; an abandoned card box whose sale order is still unpaid; an intent naming an order we do not have; an unpaid SALE order untouched for 90 minutes. **Measured on its first run: 9 findings, and it named the 2026-10-20 failure nobody had noticed.** Verified as a scheduled path, not just a manual one: log headers at `20:26:05Z` (mine) and `20:30:06.845Z` (cron), matching `CRON[4003367]` in syslog at `20:30:01`.

**The environments had drifted, and CI could not say so.** Production serves Cloudflare Pages + Hetzner `lpt-apps`; it does not auto-migrate. `main` was 100 commits behind `test` and three migrations existed only on `test`; production's `_prisma_migrations` had a row for one of them and neither `repair_intake_cases.deviceId` nor `repair_parts.partTier` existed as columns. Deploying main as it stood would have had the new code select two columns the database did not have. Both were applied deliberately first (`20:44:59Z`, `20:45:00Z`, checksums `f9d2d33e…`, `f6100f6d…`, recorded in `_prisma_migrations` so a later `migrate deploy` sees them as done), then the code followed.

CI had been red on every push to `test` for longer than anyone noticed, at the database step, and each fix uncovered the next: `relation "payment_pages" does not exist` (no migration creates it) → build from `schema.prisma`; `operator class "gin_trgm_ops" does not exist` → declare `extensions = [pg_trgm]` + `previewExtensions` in the schema, because `db push --force-reset` drops a schema-level extension created before it. Then the first run that actually executed the suite found **12 failing tests**: D16 shipped without updating its seven ai-tools tests, and my own `findMany` change broke five in `create-order.test.ts`. All named, all fixed (#665). A frontend shard then caught that I had added a PROCEDURE to the hook without adding it to every suite's trpc mock (#667).

**What is still open, so the next session does not re-derive it.**

- **The typed card never reaching Stripe was never reproduced.** No Chromium can launch on ZABZ-TECH (`Your computer has run out of resources` — a session-level handle limit, not disk or RAM); the browser probes ran on `zab-tech-linux` instead, and the Stripe CardElement in a headless run never reported `complete`, so the submit button stayed disabled and the submit path could not be exercised. The fix here is the numbering plus the receipt/orphan handling, not a proven cure for that specific client-side failure.
- **Three unpaid sale orders still sit on the books** (#3142, #3009, #3011) and today's #3241. The monitor now reports them every 30 minutes; cancelling them is a business act, not a code fix.
- **The estate has a concurrency problem worth naming:** two sessions merged into `test` throughout this work, and `strict` branch protection means every merge invalidates every other open PR. Several merges took 15-20 minutes of polling. Worth a rule: batch a session's PRs, merge them in one window, and expect `gh pr merge` to fail with "the base branch policy prohibits the merge" while a required check is merely *queued*.
