## 2026-09-15 · ZABZ-TECH · The LPT sign-in button never worked, and now it does as far as it can

**Owner directive D38-08:** *"use the lpt sigin flow, it should be the same account as everything else lpt offers."*
Built the site-side half. Commit **`5b4717b`**, pushed, verified in sync with `origin/main` by SHA.

**THE DEFECT, and it is a good one.** `identify_lpt` was imported into `web/server/app/main.py` and **never
called** — grep across the site found only its own tests as callers. So the "Continue with Lakewood Phone & Tech"
button sent the browser to LPT, LPT authenticated the parent and redirected back with the `lpt_refresh` cookie,
and the site **ignored the cookie**. The button had silently done nothing since it was written. This is the same
class as P78 (1,836 lines with zero callers): a wired-looking surface with no wiring, which no test could catch
because nobody asked what the button was supposed to achieve.

**Now:** with LPT configured, `GET /login` returns **303 straight to**
`https://api.lakewoodphoneandtech.com/api/auth/google/start?return_to=https://<site>/login`; with the
`lpt_refresh` cookie present it calls `identify_lpt` and records the identity; `?local=1` renders the password
form as the fallback; and an error is rendered rather than bouncing back to LPT, so a reason is never swallowed
by a redirect.

**The rail, tested by name: a verified identity does NOT become a sign-in.** The LPT subject is stored on the
session as `lpt_subject` and the page refuses with a precise reason, because **the broker has no endpoint that
accepts an asserted identity** (`sso`/`assert` appear nowhere in `server/app`). `account` means "may act on a
household"; `lpt_subject` means "we know who this is" — held in separate fields deliberately, so the first
cannot be inferred from the second. A session that looked signed in and failed on every page would read to a
parent as a broken product.

**Also corrected:** the login page said *"there is no self-service reset yet"*. Once the account is LPT's that is
untrue — LPT ships `/customer-portal/forgot-password`, which I saw render on test. The sentence now points there
(D38-04: no page may assert what is not so).

**Testability note worth keeping.** The LPT client is now injected and reused (`app.state.lpt`) instead of being
built inside the request. A client built per request reaches the real network from a test, which is precisely why
the cookie path had no coverage. Same reason the broker client was already injected.

**Verified:** **49 passed** (was 39), no warnings. Both postures smoke-tested against the real app object: LPT
unconfigured → `/login` 200 with the form; LPT configured → `/login` 303 to the google/start URL with the correct
`return_to`, `?local=1` 200 with the form, landing and `/healthz` 200. The config refusal was also observed live:
`create_app()` without `SITE_SESSION_SECRET` refuses to start, which is D38-05 working.

**NEXT, and it is the whole remaining half:** the **broker** endpoint that maps an asserted LPT subject to a
household and returns a machine-held session. Two design questions are open in it and neither may be guessed:
(a) **what binds an LPT subject to a household, once** — creating on first sight risks a duplicate household for a
family that already has one, and the repo has a documented history of wrong-row/wrong-data failures; and (b)
**does `/api/auth/sso/assert` assert that the email is verified?** If it does not, first-sight creation trusts an
unverified string, which is the exact hole W-BACK-058/059 existed to close. Reading the assert response shape is
the first step of that increment.

**Also still open in this lane:** the Playwright E2E (W-BACK-057) has no coverage of any of this.
