### The last unreachable feature

`complete_release` has always required an **open, dated request event**. The only route that created one
was the phone's own `/self/reset-protection/release-request` — **which nothing that ships calls**, in the
app, the web client or the scripts. So completion always refused with *"a release needs an open, dated
request first"*, and the thirty-day anchor was a record-keeping surface whose first step nobody could
reach.

Added the operator half of the pair, symmetric with the completion route that already existed:

```
POST /phones/{phone_id}/reset-protection/release-request
```

**It does not shorten the floor.** `request_release` still raises `ReleaseTooEarly` until
`release_eligible_at`, so an operator can open the request at the right moment but **cannot move that
moment** — D-20261021-05 is that thirty days are never shortened by staff. What it adds is *who asked and
why*, recorded earlier than before. The customer-asks-the-shop path is now walkable.

**Four tests, and the first two are the point:** completing **without** a request still refuses (the
stuck state, pinned so the defect cannot quietly return), and the operator request **opens the gate
`complete_release` reads** (the DoD). The fourth asserts the route is **mounted on the app** — because a
store method with no route *was* the whole defect, so a store-only test would have passed while the
feature stayed unreachable.
