THE REMAINING PRESSURE SOURCE, AND WHY IT IS NOT PATCHED LIVE
 `dsh_session_ingest.py:391` runs, per changed session and INSIDE `BEGIN IMMEDIATE`:
 DELETE FROM dsh_session_events_fts WHERE source_machine = ? AND session_id = ?
 FTS5 has no index on those columns, so it is a full virtual-table scan that HOLDS
 THE WRITE LOCK for the whole scan -- measured 1,610 ms warm, 17,421 ms loaded, once
 per changed session, on a `*/30` cron. Any hold over 2 s guarantees a probe timeout
 and queues every other writer.
 The correct fix is to make the FTS external-content
 (`content='dsh_session_events', content_rowid='rowid'`) so the delete is by rowid,
 or to align the fts rowids with the base table. The repo's own audit already found
 fts rowid != base rowid in 23.5% of rows, so this is a migration with a full
 805k-row rebuild plus `ANALYZE` (which has NEVER run -- `sqlite_stat1` is empty, so
 the planner has been guessing). That needs a maintenance window, NOT a live patch:
 a rebuild of that size competes for exactly the I/O that is causing the incident.
