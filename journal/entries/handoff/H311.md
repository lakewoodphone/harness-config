## 2026-09-15 21:54 UTC · ZABZ-TECH · 2026-09-15 21:45Z: dashboard honesty integrated (healthcheck trap caught), liveness live, three workstreams still out

Two of the five audit workstreams are integrated and pushed (origin/master 1b0c91d6), one of them
live, and a third is being deployed now.

DONE AND LIVE - fleet-api liveness (03e7fb50, deployed 95c562ba): the fleet's liveness is
measurable for the first time; 50 replied / 13 never-replied / 2 cannot-tell across 65 devices.

DONE AND PUSHED - fleet-dashboard honesty (1b0c91d6, NOT yet deployed). The dispatcher dashboard
was lying about the one thing it must not lie about: erase and lock toasts fired on an ok:false
response, because commands.py answered HTTP 200 for a failed enqueue and the UI never read the
body; bulk lock/restart reported ok:true/total_devices:65 after zero dispatches; /poll claimed
"N devices polled" without reading a single result; /api/health was a hardcoded ok:true; and the
overview page read three endpoints its own backend did not expose (404 -> "—" forever, with a
fresh timestamp every 30s). Now: 502 on a failed dispatch (207 partial), attempted/succeeded/
failed counts, real /api/health probe returning 503 when a required dependency fails, the three
endpoints implemented from the dashboard's own data with unmeasurable values null and NAMED in an
`unavailable` list, and fleet-wide destructive buttons requiring a typed confirmation with the
device count. Evidence is real HTTP request/response pairs from a local uvicorn with NanoMDM
stubbed to fail, not assertions in prose. 37 dashboard tests + 179 fleet-api tests green on the
integrated tree.

THE TRAP I CAUGHT BEFORE SOMEONE ELSE DID: the same commit changes the container healthcheck from
probing `/` to probing `/api/health` with `assert r.status == 200` - but that endpoint
deliberately returns 503 when a required probe fails and 200+"degraded" when a dependency is
merely unverified. On the deployed config (standalone mode, possibly empty SQLite volume, NanoMDM
probe unverified) that healthcheck can mark the container permanently unhealthy. The deploy agent
is instructed to determine what /api/health actually returns on the live config FIRST and, if it
is 503, to relax the healthcheck to "answers with parseable JSON" and say why: a healthcheck
measures liveness, so requiring 200 on an endpoint that uses 503 to report degradation makes the
container look dead whenever a dependency is down.

DEPLOY CAVEAT worth keeping: deploy/fleet-dashboard/backend/frontend-dist/ is untracked and
gitignored, and the agent who changed the frontend did NOT rebuild it - so a container rebuild
without first running the frontend build serves a STALE UI. The deploy agent must build the bundle
and record the entry-file hash so the deployed UI is identifiable. This is the same class as the
box-local Dockerfile.production: the artefact that ships is not the artefact in git.

STILL OPEN elsewhere: the staff portal needs deploying before any of the fleet-api liveness shows
up in a UI, and the portal collapses JSON null -> false so the 2 no-enrolment devices would render
as "No reply on record" rather than "cannot tell".
