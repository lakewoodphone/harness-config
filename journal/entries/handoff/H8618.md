## The number that made this necessary

A question took **9.2 s** while the stores answered in 389 ms (sessions), 17 ms (memories) and 18 ms
(chats). The reply was waiting for the one store still ranking — and the caller had no way to know
that most of the answer was ready within half a second.

## What changed

- **The stores run concurrently.** They were called one after another, so the cost was the SUM of
 independent work. Each `Store` already keeps one connection per thread, so this is safe.
- **A 4-second deadline per store.** Whatever has not answered is named in `did_not_answer`, with the
 sentence that matters: *its hits are missing from these results, not absent from the corpus.* A
 silent timeout would be a lie; this is a bounded, labelled partial answer.

## Two traps, both measured, both mine

1. `as_completed()` **raises** on timeout instead of stopping, so the first version turned a slow store
 into a failed request — two of the owner's questions returned **nothing at all**.
2. `with ThreadPoolExecutor(...)` exits with `shutdown(wait=True)`, so it **waited for the store the
 deadline had just abandoned**: the deadline fired at 4 s and the reply still took 9.2 s. The pool is
 now shut down without waiting.

Both are the same species as everything else this program has learned: a control that looks like it is
working, measured only by its own reassuring name.
