## 2026-10-20 18:44 UTC · ZABZ-TECH · round 21: the duplication fault was RDP's indirect display - a native repro cleared the code and the test now skips with the reason

# H (2026-10-20, round 21) - the duplication fault was the RDP display all along; a native repro settled it and the code was innocent

## The repro that ended it
`C:\Users\ezabz\Code\_tmp\dup-repro` - a standalone console app with **no RCW, no xunit and no product code**. Every COM
call is a raw vtable function pointer, slots computed from `dxgi1_2.h`/`dxgi.h`:
GetAdapter at 7, EnumOutputs at 7 on the adapter, DuplicateOutput at 22, GetDesc at 3, AcquireNextFrame at 4.

Run at the console (via an `/it` task, deleted after):
```
D3D11CreateDevice hr=S_OK -> GetAdapter hr=S_OK -> EnumOutputs(0) hr=S_OK -> DuplicateOutput hr=S_OK
QueryInterface(IDXGIOutputDuplication) -> the SAME pointer
Fatal error. System.AccessViolationException
```
`GetDesc` and `AcquireNextFrame` were run in **separate processes** so one fault could not hide the other: both fault.
`IUnknown` on the same object works; every DXGI member faults.

**The cause is the display.** `Get-PnpDevice -Class Display` on ZABZ-TECH lists *Microsoft Remote Display Adapter*
(`RDPIDD_INDIRECTDISPLAY`) for sessions 1-6 - the session is Remote Desktop and its output is an **indirect display**,
which DXGI does not duplicate. It grants the session and then faults every call.

So the estate's interop was innocent: the IIDs, the member order and the struct sizes were verified correct against the
SDK headers, and three rounds of suspicion were aimed at the wrong target.

## A bug in my own repro, worth recording
The first repro run faulted in `AcquireNextFrame` because I declared `out IntPtr frameInfo` where DXGI writes a 48-byte
`DXGI_OUTDUPL_FRAME_INFO` - my own stack corruption, not DXGI's. It is the same class of mistake as the product's, and
it is why a repro must use correct types before it can accuse anything.

## What this cost and what it bought
Ten interactive runs, ten console windows on the owner's desktop. What it bought: the estate now knows that the last
Windows path is blocked by a *session type* rather than by our code, and the test says so instead of crashing. The
lesson to keep: **when a fault reproduces outside your own layer, stop reading your own layer.**
