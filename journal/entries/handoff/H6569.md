## The token question - "why do we need so many?" - measured, 16 user tokens

The answer is four causes, and none of them is a good reason:

1. **Cloudflare creates a tunnel token every time a tunnel is created and nobody deletes the old one.**
 Five `Cloudflare Tunnel API Token` entries, byte-identical in permission and resource, for the ONE
 tunnel this estate runs (`3e62916c-…`). Two of the five have **never been used at all**
 (`last_used_on` empty). Four are pure duplicates.
2. **Three overlapping tokens can each mint more tokens** - `dsh global token`, `secretary global
 token`, `dsh yoga laptop new token` (plus `lpt-r2-bucket-setup`, which carries Memberships Write and
 User Details Write). Any one of them is a full-account compromise if it leaks; the other two are
 additional attack surface for the same power.
3. **Two broad catch-alls nobody can attribute to a job**: `copilot-full-access` (DNS Write, **Pages
 Write**, R2 Write, Zone Write, on ALL accounts and ALL zones) and `dsh yoga laptop new token`.
 **`copilot-full-access` carried Pages Write the whole time** - it is the token the owner meant, and
 it existed only in the dashboard, never in a file. That is why six rounds of searching the estate
 found nothing: **the dashboard is part of the credential surface and was not in my inventory.**
4. **Nobody wrote down what each token is for.** The narrow ones are self-documenting
 (`rentals-lakewood-dns-edit`, `lpt-frontend-deploy (Pages:Edit)`); the broad ones are not, which is
 exactly how a Pages-capable token goes unnoticed for months.

Worth keeping, as designed: the single-purpose R2 buckets (`lpt-authority-backups-s3`,
`lakewood-rentals-media-rw`, `lakewood-rentals-photos-rw`, `psm-restic-backups`, `phone-and-tech-*`),
`rentals-lakewood-dns-edit` (DNS Write on exactly one zone), `ha-access-admin`. Likely stale:
`lpt-customer-backups-test-heroku` (Basin SQL - Heroku is gone), `Edit zone DNS` (generic, 7 months
