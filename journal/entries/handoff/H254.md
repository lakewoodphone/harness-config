## 2026-09-15 19:05 UTC · ZABZ-TECH · CRITICAL found and fixed: the terminal router (12 procedures) and a2pAutoReply (5) had NO auth and were reachable from the internet - connection tokens were minted unauthenticated

CHANGED
- **FOUND AND FIXED A CRITICAL PRODUCTION EXPOSURE, live on the public internet.**
- PART-120 (the tRPC guard chain) documented:
 `docs/audits/account-audit/parts/120-trpc-auth-router-and-guard-chain.md`. Committed
 **`b5ad03826`** on `audit/lpt-account-2026-09-15` (the source fix itself is `489fd3165`).

THE EXPOSURE — measured before the fix, from a normal internet connection, with no token
- `GET https://api.lakewoodphoneandtech.com/api/trpc/terminal.getReaders` -> **HTTP 200** returning the
 reader **serial number `WSC51F509005728`** and its **LAN IP `192.168.50.247`**.
- `terminal.getLocations` -> **200** with the shop's business address.
- `POST terminal.createConnectionToken` -> **200** minting a **live `pst_live_…` Stripe Terminal
 connection token**. That token authorises the Stripe Terminal SDK to talk to physical card readers and
 to create/process payment intents.
- The same router also had `createTransaction`, `processPayment`, `getTransactionStatus`, `registerReader`,
 `cancelReaderAction`, `createLocation`, `getReader`, `getDefaultReader`, `isDefaultReaderOnline` open.
- **Controls in the same session, same call shape:** `adminTasks.list` -> **401**, `auth.sessions` -> **401**.
 So this was one unguarded router, not a broken system.
- **Second one, same sweep:** `a2pAutoReply.updateConfig` was a **PUBLIC WRITE** of the customer-facing SMS
 auto-reply configuration (`getConfig` also returned the live template and business hours). A stranger
 could have turned the shop's auto-reply off or rewritten what customers receive.

FIX APPLIED AND VERIFIED
- Source: all 12 `terminal` procedures and all 5 `a2pAutoReply` procedures changed from bare `procedure` to
 `managerProcedure`, including the import. Committed `489fd3165`; the repo copy and `/opt/lpt/src` are
 byte-identical.
- Deployed and verified: all 17 endpoints now return **401 `UNAUTHORIZED`**, both on the host and over the
 **public internet**. Public-by-design paths still open: `auth.requestPasswordReset` -> 200,
 `customerAccount.requestClaimCode` -> 400 (input validation, i.e. reachable). Nothing else broke:
 portal login 200, `/api/auth/google/status` `{"enabled":true}`, `/health/live` 200, container healthy.
- **Deployment method that mattered:** the production image has **no `src` tree and no
 `backend/package.json`**, so it cannot be rebuilt in place, and the running dist was emitted on 09-10 by a
 compiler not on the host. The change is two tokens of JS, so the **emitted** files were patched directly,
 `node --check`ed, backed up to `/opt/lpt/<file>.js.orig-<stamp>`, and the container restarted. The source
 tree at `/opt/lpt/src` was edited too so the next real build carries it.

THE TWO RULES THIS EARNED
1. **A census must parse declarations across everything, not read the router under audit.** The guard
 chain's own file (`context.ts`) looks correct; the hole was in which builder 43 other files chose.
2. **An audit probe must be chosen so it cannot change state.** I sent a malformed body for every mutation
 for exactly this reason. My first sweep still sent `{}` to `updateConfig` by mistake — which is why the
 config was re-read and compared. Probing a write endpoint by calling it is how an audit becomes an
 incident.
