## 2026-10-20T03:40Z · ZABZ-YOGA · close-out: the ceiling is missing, 44k per call is blind, and I instrumented the wrong loop

**This supersedes `H10347`.** Read `docs/cost/HANDOFF.md` first — it now opens with the four facts that matter.

### The two findings that outrank every optimisation in this work

**1. There is no working spend ceiling.** `LLM_DAILY_BUDGET_USD=5.0`; measured spend ~16/day book-priced and
~35/day on the counter the budget itself reads. On 2026-10-19 cumulative spend crossed 5.00 at **02:00** and
kept going for twenty-one more hours to **37.50** — 7.5x the cap. The check is real (`check_budget` in
`agent_worker:2789`, 38 blocked skips all-time) but sits in a loop that is not where the money goes.
`app/services/spend_guard.py` is built and tested for the choke point, **inert pending owner-queue #860.**

**2. 44k of every 45k-token call is invisible to every instrument in the code.** Measured: `build_focused_prompt`
produces **826 tokens**; production tool schemas 1,053; the provider counts **45,119**. The mass appears
downstream of both, and it is on the **cheap** model while the pro path runs at 2.8k with 95 % cache.

### The mistake worth remembering

**I spent hours instrumenting the loop I could read, not the path that runs.** 28 LLM calls from
`agent_worker`-type agents produced **zero** diagnostic lines, and warnings were proven to reach the journal in
the same window — so the code path was never taken. `agent_worker` is 5,285 lines and has more than one place
that calls the model. That single mismatch explains four separate dead ends at once: the budget check missing
most spend, pruning measuring zero, the 45k being invisible, and hours of instrumentation moving nothing.

**The correct instrument for a question like this is the callee every caller shares, not the caller you happen
to be reading.** `prepare_request` in the gateway is that place, and it now logs `GATEWAY-SHAPE` (message count,
chars, tool-schema size — no content) behind `AGENT_LOG_PROMPT_SHAPE`. It is deployed and waiting for the first
call since a restart that has not yet happened.

### What is genuinely done

- Model names come from `.env` only (`LLM_MODEL_FAST/MID/CEO` -> `deepseek-flash`, served by V4.1-Flash-1017).
 28 rows verified after the change, all priced exactly, 0 mismatches. `deepseek-v4-flash` — 96.6 % of past
 traffic — is **not in DeepSeek's live catalogue**.
- `savings_audit.py` deployed and both guards validated: INCONCLUSIVE under 7 days, real verdict at 7.
- Follow-up timer live, next run 2026-10-26T09:00Z, runs once already and reported a missing dependency as a
 finding rather than a pass.
- Priority ladder built, tested (25), priced at every setting (dial 0 = 12.9 %, dial 1 = 6.0 %, current gate =
 10.2 %), deployed **inert** pending a dial choice.
- The gate itself works: two deferrals, both exactly `7 agents ticked, 25 deferred`, against a pre-registered
 prediction.

### What is deliberately not done, and why

- **Ladder not switched**: dial 1 is a regression; dial 0 is the setting, and switching inside a measured
 window would mix two policies into one result.
- **Gemini not moved**: ~17/month for company traffic, but `model_usage` cannot say whether a call needed
 vision, and breaking image work to save 17 would look like a saving right up until it didn't.
- **v4-pro price not "fixed"**: DeepSeek docs say pro auto-routes to V4.1-Flash at Flash rates, so correcting it
 to the book would overstate. Verify against the invoice first.
- **Budget number not changed**: that is #860 and it is the owner's.
