## THE MEASUREMENT (mine, not a child's)

A live billing tick asks the fleet API's usage ledger for a window ending at **now**. I called it myself:

```
GET /api/waze/billing/usage?since=2026-10-05T03:00:00Z&until=2026-10-12T23:00:00Z

{"ok":true,
 "coverage":{"from":"2026-10-05T03:14:54.069404Z","to":"2026-10-12T23:00:00.000000Z","complete":false},
 "devices":[{"serial":"FFYGNQ8AN72J","consumed_mb":0.93,...},{"serial":"FFXGT23HN72J","consumed_mb":0.29,...}]}
```

The newest reading is `2026-10-12T22:25:41Z` — **35 minutes before the `until` I asked for**, well inside
one hourly snapshot interval — and `complete` is still **false**. The ledger computes

```python
tail_covered = bool(newest_for_sim) and newest_for_sim >= until_iso
```

so completion requires a reading **at or after** the window's end. A live tick passes `until = now` and
can never satisfy it. There is no reachable window a live tick can call complete, which is why the billing
service refuses every run with `refused_incomplete_coverage` and **no Stripe meter event has ever been
emitted in either environment**. The ledger itself is healthy: 372 hourly rows, 7.3 days deep, both SIMs.

Consequence, stated plainly: a customer over the 250 MB allowance would be told the overage costs 18.00 per
GB and **never be billed**. It fails in the customer's favour, so it is not urgent for tomorrow — but it is
the last unproven link in the product and it was hiding behind production's `WAZE_BILLING_SCHEDULER_ENABLED`
being off (now armed, so it will at least refuse out loud and leave a `waze_billing_runs` row).

A fix child (`C9-LEDGER`) is in flight with the guard's intent preserved — do not bill a window whose end
you cannot see — and the brief explicitly forbids deleting the check, because widening it until it always
passes converts a safe refusal into a silent under-bill. **If it has not landed, read
`C:\Users\ezabz\_wazecli_check\LEDGER-COVERAGE-FIX-2026-10-12.md` on ZABZ-YOGA first.**
