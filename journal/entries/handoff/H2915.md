The change is one line: `TickOutcome.status` was `"completed" if retry_state is None else "error"`,
and `retry_state` is set only in the **post-processing** block at line 3286 while FU4's deadlock
returns early at 2259 — so a deadlock would have been recorded as a **completed** tick, the exact
opposite of its purpose. `_finalize_step(result, *, outcome)` only logs; it sets nothing.

**But two of FU4's claims do not survive measurement, and I am recording that:**
1. *"a tick whose LLM call failed is returned with status completed"* — **false for the normal path.**
 Data, last 24 h: `outcome=complete → step=completed` (75), `outcome=error → step=skipped` (23),
 `outcome=escalate → step=skipped` (5) / `blocked` (1). **Zero** completed ticks sit beside a failed
 step, and LLM errors already carry their text. The normal path sets `retry_state` at 3286.
2. *"the step is written `failed`"* — the data shows `skipped`, not `failed`.
So the fix is correct but **latent**: it protects the deadlock path (which has never fired — 0
occurrences) and any other early `action="error"` return. It is not a repair of an active fault, and
I will not describe it as one.
