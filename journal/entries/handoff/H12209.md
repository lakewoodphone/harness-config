## What to know before touching journal.py again

* **Two things on the write path are load-bearing and easy to break.** `ensure_reservation()` never touches the network or a remote ref, by design — it is what makes an id safe; `git_max` is only a cross-check. Do not "simplify" by pushing a claim inline: an earlier version did that and reverted `origin/master` by 1249 paths.
* **`stamp.json` has two writers.** `rebuild_cache()` must keep carrying forward every key it does not own (`setdefault`). It was deleting `ledger_ceiling` — other hosts' claimed windows — on every append, and that is a collision risk, not a tidiness issue.
* **Do not re-run a fetch inline from a write.** It cannot finish on this repo and its timeout orphans `ssh`/`index-pack`. `spawn_ceiling_refresh` + `journal.py refresh` is the only sanctioned path, and `refresh --all` is the escape hatch that takes minutes.
* **`journal/index/journal.db` and `entries.tsv` are untracked now.** `git rm --cached` only; the files are still on disk. If a machine reports them deleted, it has an old index and a `journal.py index --force` fixes it.

## Next, in order

1. **Stage C** — put the journal in its own small repo (~15 MB) instead of inside the 4.85 GB code repo. That is the structural fix: it makes fetch trivial and makes stage B unnecessary rather than urgent. Needs decision on the remote and on every host's `--root`.
2. **Stage B** — allocate id windows from a counter on the authority instead of `bands.tsv` replicated through refs. Removes the last network dependency from a write.
3. **Stage E** — `append --batch`, a `recent.tsv` tail, per-kind lock sharding.

## What still hurts

* An append is **4.3 s**, and ~1.4 s of that is recomputing the tree fingerprint (7,615 `stat` calls) to prove the index is fresh. That is the honest cost of not rebuilding; a cheaper fingerprint (max mtime + counts per kind) is worth measuring.
* `reserved_through_others` is 0.67 s per process because each append is a fresh process and the ledger read is not cached across them. A tiny on-disk memo keyed by the ref fingerprint would take it to ~0.
* The record is 4,762 files and every `check` still walks them (16.4 s). Fine for now; it is the one place that is legitimately O(N).
