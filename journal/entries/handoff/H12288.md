### What the job actually needed — three defects, not one

1. **`inference_events` had no PostgreSQL creation at all.** Created only by `022_inference_telemetry.sql`
 (SQLite-only `AUTOINCREMENT`); PostgreSQL is built from Alembic. `20261021_03` then ran
 `ALTER TABLE inference_events ADD COLUMN IF NOT EXISTS subject_id` → `UndefinedTable` → **the migration
 chain aborted**, so every later revision never applied.
2. **The E2EE tables had no Alembic revision either.** `Select-String alembic_scripts/versions/*.py` for
 `household_e2ee_keys|e2ee_retention_deletions|e2ee_key_id` → **0 matches**. Same defect class, second
 feature running.
3. **The four E2EE methods had no Postgres implementation**, which made the parity audit fail — and the
 backend **refuses to construct** when that audit fails, so one absent feature failed sixteen unrelated
 tests.

Measured progression: **18 failed → 16 → 1 → PASS.**

### The structural finding: the CI jobs are entangled, so one PR was the honest unit

- `#107` alone (create the table): 18 → 16.
- `#108` alone (E2EE backend): parity gate gone, then `inference_events` missing.
- `#108` + `#107`: 18 → 1.
- `#106` excluded: `server-tests` **7 failed / 1851 passed, all seven exactly #106's fixes.**

Neither PR could go green alone, so merging them separately would have meant merging a deliberately-red PR
to reach the second. **#107 and #106 were folded into #108**, which merged green.

### Three gates I had not met before, all found by running the suite

- **`app/sql_surface_audit.py` pins a dynamic-SQL count and digest.** My new module added **eight** call
 sites (373 → 381). One pin produced **574 failed, 1263 passed** — not 574 defects. Notably the SQLite twin
 of this feature stayed at 373: that was a property of *its* idiom (literals passed to `conn.execute`), not
 of the feature. The Postgres idiom passes SQL through `_execute_in_transaction`/`_fetchone` so it can run
 inside the caller's transaction and read `INSERT … RETURNING id`, and the audit correctly counts those.
- **`EXPECTED_POSTGRES_TABLES`** in `test_postgresql_migrations` — 63 → 65. My three tables, plus main's
 `privacy_erasures` and `privacy_subject_identities`, which arrived while the branch was open. Names read
 from the job log's `Extra items in the left set`, never guessed.
- **The sign-off covers `sql_surface_audit` itself**, so editing that file staled its digest and needed a
 refresh naming the cause — the control still *passed*; only the approved snapshot predated the change.

### The GitHub race, now understood rather than suffered

Main moved under the branch **four times**. The consequence is not just conflicts: a **CONFLICTING PR has no
merge ref, so no `pull_request` workflows start at all.** A watcher then sees `docs-check` pass and nothing
else — indistinguishable from "the rest were fine". `mergeable: UNKNOWN` after a push is the same trap.
Every cycle: take origin/main on the generated docs, `docs_check.py --write`, re-verify, push, poll until
`MERGEABLE`, then watch.

### Traps paid for here

- **`git commit -m` with a `"` in a PowerShell double-quoted string silently fails** (round 11 lost a
 commit that way; the push then succeeded with an empty branch). Messages go to a file, `git commit -F`.
- **A migration that looks like valid Postgres is not evidence the object exists.** Only a revision that
 creates it is — twice now.
- **A conflicting PR looks like a passing PR** in `gh pr checks --watch`.
