- **One long-standing open item CLOSED.** The `LPT_SSO_SHARED_SECRET` placeholder warning, carried since the
 pivot and still listed in the master index §3, is **satisfied in production**: the container holds a real
 **43-character** secret that does not begin with `CHANGE_ME_`. `docker exec lpt-backend printenv` (length

THE ENDPOINT IS WELL BUILT, AND I CONFIRMED IT LIVE RATHER THAN BY READING
- **Fail-closed**: 503 when unconfigured (`configEnabled()` requires ≥16 chars).
- **Constant-time comparison** over SHA-256 digests of both sides, so length is not leaked either.
- The refresh token is read from the **HttpOnly cookie**, never the body; the response identity is built
 **field by field** (`userId`, `email`, `phone`, name, `customerId`, `role`, `status`, `isVerified`,
 `createdAt`) — so no password and no token can leak.
- The token is deliberately **not rotated or consumed**, which is what makes a shared cross-app cookie usable
 without tripping reuse detection.
- Live probes (`localhost:3001/api/auth/sso/assert`): no secret → **403**, wrong secret → **403**, 2-character
 secret → **403** (all `sso:forbidden`); `GET` → **404** because the route is POST-only.

A WORSE ITEM OPENS: **F-1, the single shared secret**
- `LPT_SSO_SHARED_SECRET` is **one value serving every app**. There is no app identity in the request and no
 registry of authorised consumers. Three consequences: **(a) any app's leak is total** — the holder can
 assert any customer's identity; **(b) revoking one app is impossible** without rotating every app's
 credential, so a departed partner, a compromised app or a decommissioned one cannot be cut off
 individually; **(c) the header cannot distinguish a legitimate consumer from any other holder.**
- **F-3:** `assertRefreshToken` never checks **role**, so the same secret yields a **PARTNER or staff**
 identity as readily as a customer one — role enforcement is pushed onto each consumer, which inverts the
 point of a single identity authority.
- **F-4 is the consumer-side proof:** the filter site's LPT path is written and **dark**, explicitly pending "a
 secret issued for it rather than the one already shared with other relying apps". The record already
 recognises that the current model cannot issue per-app credentials.
- Recommendation recorded as C-123-1: move to a per-app secret with an app-id header and a registry table,
 **not yet filed** to the owner queue — it has a clean default I can implement, and the only outward-facing
 step would be re-issuing a credential for a live partner. It becomes his if that step is needed.
