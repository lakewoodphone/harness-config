# The wake dispatch bound is fixed and the daily cap is single-sourced — but a real release has not yet run under it

2026-09-20 ~03:15Z. Written after three mesh children died on the same transport, so this is the state
of the wake dispatcher as I verified it **with my own eyes on the authority**, not as a child reported it.

## 1. The bound defect: FIXED, and the diagnosis was already written into the file

`/home/zabz/bin/wake-dispatch.sh` (backup `wake-dispatch.sh.bak-20260920-030446`) now carries:

```
TURN_CAP=${WAKE_TURN_CAP_SEC:-1800} # the mesh's child-turn cap, raised 2026-09-18
TIMEOUT=${WAKE_TIMEOUT_SEC:-$((TURN_CAP + 360))} # -> 2160
RUNNER_TIMEOUT -> 2100 # forced up to TURN_CAP when the outer bound has room
```
and a `MEASURED DEFECT, 2026-09-20` comment recording the root cause: the inner bound used to be
`TIMEOUT-60 = 840 s`, **below the length of a real turn**, so it killed sessions that were still
working — wake #8 and #10 were cut mid-sentence at **841 s with 218 KB and 378 KB of live reasoning**,
the runner reported **124**, ssh returned 1, and the dispatcher recorded `ssh hop failed (rc=1)`: *a
bounded-and-killed hop wearing a network failure's name.* Sibling release #6 finished at 715 s, i.e.
**85 % of the old bound**, which was never derived from anything but "a bit less than 15 minutes".

Verified by me: file present, backup present, `bash -n` clean, and `--dry-run` renders the real command:
`timeout -k 30 2160 ssh ... -TimeoutSec 2100` with `hard timeout 2160s, runner self-bound 2100s,
child-turn cap 1800s`.

**NOT PROVEN: that a long release now survives.** Today's release budget is spent (see below), so the
first release after 00:00Z is the proof. My own hand-run hop probe was cut off by my harness timeout
before the result came back, so the transport is *not* independently proven either. Do not record this
as "the hop is fixed and verified" — record it as "the bound no longer cuts a working session, and the
next real release is the test".

## 2. The daily cap was being enforced at 8 while wake.py said 4 — the same number in two places

`wake-dispatch.sh:77` had its own `MAX_PER_DAY=${WAKE_MAX_PER_DAY:-8}`. I had changed only wake.py's
default to 4, so **the live gate kept releasing on 8** and **five releases went out today** against the
owner's 4/day. The looser copy won, silently.

Fixed: the dispatcher now defaults to 4 (backup `wake-dispatch.sh.bak-cap4-20260920-030849`), the number
is documented as owned by `wake.py:399`, and a **cap-drift check** runs on every dispatch: it reads the
store's own cap and warns loudly when the two disagree (backup `wake-dispatch.sh.bak-driftsay-20260920-030918`).
The warning goes to **both** `say` and `log`, because `log` is deliberately suppressed during a dry run
and a warning nobody can see is exactly how this drift survived the first time.

Evidence: `--dry-run` now prints `dry-run: daily cap reached (5/4) - would release nothing` (before the
fix it said `releases today 5/8`). The comparison logic was proven in isolation with a forced mismatch:
`store says 4/day, dispatcher says 8/day -> RESULT: DRIFT DETECTED`.

**Consequence to expect:** no wake will be released until 00:00Z, because five already were today.

## 3. Why three children died, and what to do differently

- job 10 (website) — `exited 255 ... Connection timed out`.
- job 8 (this hop fix) — `the remote turn did not finish within 1800000 ms and the ssh client was killed`.
 **It died of the very cap it was working on, while waiting for a scheduled tick to observe a release.**
- job 2 (Dialpad) — same marker rule, different cause (my brief's fault, see L2070).

The rule this produces: **never give a mesh child a task whose completion depends on waiting for a
scheduled event.** The mesh turn cap is the same 1800 s the dispatcher is bounded by, so a child that
must watch a 5-minute cron tick and then wait for a session can exceed it and die with **no report at
all** — and its work is then unattributed, as this fix nearly was. Either do that class of work in a
session that is not under the cap, or make the child's deliverable verifiable without waiting.
