## 2026-09-18 04:25 UTC · ZABZ-YOGA · DSH watchdog re-enabled: liveness on every origin, window recovery, and the open selector collision

CHANGED
- multi-window/dshw.ps1 (ZABZ-YOGA, working tree; harness autosync has been committing the tree
 every few minutes, so check `git log -- multi-window/dshw.ps1` rather than trusting a clean status):
 * `Get-OpenOriginPorts` now returns the UNION of three liveness signals instead of only asking the
 proxy in shared mode: (1) the proxy's per-port live-connection count at `/__dshw/open`, (2) a
 process scan keyed on each window's `--app=http://127.0.0.1:<port>` ORIGIN (which covers ports
 3200-3223 AND the engine port 3099, in any profile mode), (3) two extra 600 ms samples when the
 first sample is empty, to catch a window that is still connecting. `Get-WindowOriginPorts` and
 `Get-EnginePortWindowCount` are new helpers for (2).
 * `Get-WindowCount` consumes that union, so it answers "this slot has a live window" in every shape
 the launcher can produce one, and no longer depends on profileMode or on the proxy being up.
 * `Invoke-WindowRecovery` added, called at the end of `Invoke-Health`: restores a window the registry
 says was open and the liveness check says is gone. Five guards (registered open; RECORDED port ==
 the slot's origin now, which excludes all legacy `port: 3099` rows; origin has a listener; origin
 not in the live set; 600 s per-slot cooldown via `window-recovery.json`) plus at most 2 opens per
 run. `dshw health` now always prints `windows: live origins [...]; registry-open-and-missing N;
 reopened M; held for the next run: ...`.
 * `dshw open <slot>` FIXED: the 'open' branch did `$slot = $null`, and PowerShell is case-insensitive
 so that clobbered the `$Slot` parameter; it binds to `$slotCfg` now. Also `Open-SlotWindow` reads
 `$slot.port` via `Get-Prop` (a raw config row has no `port` key, and `Set-StrictMode` evaluates the
 name even on the branch not taken).
- Task `DSH Window Fleet Watchdog` RE-ENABLED (`Enable-ScheduledTask`; same action/trigger/settings,
 State=Ready, LastTaskResult=0). It had missed 9 runs while disabled and fired immediately on
 re-enable (00:12:14).
- docs/multi-window/MEMORY-AND-SESSION-LIST.md §7 and §8: the liveness change, the watchdog facts, the
 raw before/after counts, the slot-by-slot restore plan, and what only a reboot can test.
- journal L1995 (the `$slot`/`$Slot` collision, plus the dot-sourced-copy probe mistake).

BROKEN / NOT VERIFIED
- The registry holds 12-14 entries with `open: true` whose recorded port is the legacy `3099`; no slot
 can claim them, recovery skips them by guard 2, and **a `dshw restore` would open 12 or 14 windows**
 in one go. Do not run `restore` before that registry is reconciled. `restore` was deliberately not run.
- The owner's five on-screen windows are that legacy shape. The launcher can neither count them per slot
 nor recover them per slot; it only knows "some window is live on 3099".
- **The logon task does not restore windows.** `DSH Multi-Window Launcher` runs
 `dshw.ps1 up -WindowsMode no` (start engine only). The desktop `DSH.lnk` targets `dshw.cmd up`, and
 `dshw-launch.cmd` (the file that does `ensure` then `restore`) is **not referenced by any task or
 shortcut on this machine**. So after a reboot the engine comes back and the windows do not, until
 someone runs `dshw restore` or clicks the OneDrive "DSH" shortcut. This contradicts a claim in the
 §0 table of the doc ("Restore after a reboot: kept") and is the reason JOB 2's proof matters.
- Shared-profile window lifetime is NOT established. A shared-profile browser launched by the launcher
 was gone twice within 3-5 minutes, with no Crashpad dump, no Application-error event, and a clean-exit
 `Last Browser` write; five minutes of passive sampling found no shared window to watch. Cannot yet say
 whether shared-profile windows are stable.
