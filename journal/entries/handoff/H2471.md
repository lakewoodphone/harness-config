## 2026-09-23 04:32 UTC · ZABZ-YOGA · Both counter-sale gaps closed and deployed: customer search (reusing the existing lookup) and the arrears read - and expectTypeOf is vacuous repo-wide

**CHANGED - both counter-sale gaps are CLOSED on the backend and deployed. One rewiring step remains.**

**Customer search existed and was REUSED, not forked - and the real gap was narrower than I described.** `CustomerQueryManager.search` (`services/customers/query.service.ts:360`, via `CustomerService.searchCustomers`) already did partial name and email. Its phone match was `{ phone: { contains: <raw typed string> } }`, so **`(732) 555-1234` could not find a row stored `17325551234`** - which is exactly what happens at a counter where a number is spoken. Fixed by normalising to last-10 digits and matching that.

**Two procedures added to the EXISTING router, so `trpc/index.ts` needed no change:**
- `searchCustomers` `{query, limit?}` -> candidates with name, phone, email and `ownsWazeDevice`/`wazeDevices`. **Never a best guess; ambiguity returns every match.** A wrong customer attached to a subscription means a real person billed for someone else's data.
- `arrears` `{limit?}` -> `{readable:true, rows, emptyReason, unusableRowCount}` OR `{readable:false, reason}` **with no `rows` key at all** - the house fail-closed shape. Reuses `wazeBillingLedger.listPeriods/listRuns`; the last *report* per period is read directly because the ledger interface exposes failed reports only, and an acknowledged one must not read as absent. Row keys match the UI's `WazeArrearsRow` field-for-field plus five additive, so **no frontend file was changed.**

**THREE DEFECTS THE AGENT FOUND IN ITS OWN WORK, two by tests and one by the typecheck:**
1. An `endsWith` applied to a PARTIAL key tested the wrong end of the number - a stored `(732) 555-4321` typed as `7325554321` was not found.
2. The prefilter never asked for the country-code-stripped form, so `+1...` would miss.
3. **The typecheck found the third: `CustomerQueryManager.search` does not select `serialNumber`, so a NAME match would have reported `ownsWazeDevice: false` for a customer who actually owns a Waze device.** Serials are now read for the whole candidate set. A staff member searching by name would have been told the wrong thing about whether someone is already a customer.

**A FINDING WORTH KEEPING, repo-wide:** the agent reports that **`expectTypeOf` is VACUOUS in this repository.** It deliberately broke one assertion and the suite still reported `4 passed` - because vitest transpiles without typechecking, so a type-level assertion never runs. **Any test in this codebase that rests on `expectTypeOf` proves nothing.** Cross-package `import type` is also impossible here (`rootDir: ./src`, measured TS6059), which is why the wire shape had to be pinned by asserting against the real returned object at runtime instead.
