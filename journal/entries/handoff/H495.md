# H495 — round 13: the record schema can now say "held, and why" — and it turns out the schema was never enforced

## THE FIX THE REPORTER NEEDED

The reconciliation reporter showed `would_create = 7` with `rc=1` on **every** run from
2026-09-15T23:45Z to 2026-09-17T16:23Z — 16.5 hours of a number that never moved. Round 5 established
that none of those 8 records was an unsynced gap: each was held for a documented reason.

**The reporter could not tell the difference, and could not be taught to, because `operational` is
`additionalProperties: false` with five properties and none of them can hold a reason.**
`shouldSyncToWebsite: true` says the case *belongs* on the site; it does not say the case is *ready* to
be. Now it can:

```
operational.syncHoldReason: string, max 400, ABSENT MEANS NOT HELD
```

The schema description carries the **reading rule**, because the next person to look at a CREATE list
needs that more than they need the type.

**Populated on 7 records, each reason traced to measured evidence — not a guess:**

| record | why it is held |
|---|---|
| `data-recovery-347-534-6208` | no phone captured; **$320 deposit paid**, $900/$700 agreed |
| `iphone-13-14-mordecai` | no first name captured; parts ordered 2026-05-04 |
| `laptop-weingarten` | **duplicate: TWO production rows (2547, 2548) on one phone** |
| `lp140wfh-screen-gutterman` | supplier stub: `recordType`/`caseId`/`device` all null |
| `pixel-6a-bloch` | no phone; device **HELD by owner**, must NOT be factory reset |
| `qin-battery-halon` | production order WO2608170003 is **CANCELLED**; customer asked 09-16 |
| `samsung-tab-s7-customer` | customer recorded as unknown/TBD |

**Why the reasons are specific:** "held" as a value would be a second way of saying nothing. Each
names a fact a person can act on or dismiss — and two of them (Weingarten's duplicate customer rows,
Gutterman's null record) are themselves defects, now recorded where the next reader finds them instead
of buried in report output.

**Idempotent:** re-running the writer reports `already set` for all seven and changes nothing.
`lpt-hub c35d4459c`, pushed, `0 0`.

## A FINDING THAT MATTERS MORE THAN THE FIX

Checking whether my change broke anything — the question I should ask every time — produced this:

| revision | records | held | **INVALID** |
|---|---|---|---|
| `HEAD~1` (before my change) | 383 | 0 | **315** |
| `HEAD` (my change) | 383 | **7** | **315** |

**315 of 383 records — 82% — fail this repo's own schema, and did so before I touched anything.**
Specific examples: `14in-laptop-weitman` carries `communications`, `evidence`, `issue`, `nextAction`,
`rootCause`; `2026-05-13-asus-vivobook-f512ja-klein` carries `outboundMessages`;
`2026-06-08-sx740-c-david` has a `null` where a string is required; two records are missing a required
`partnerName`.

**So `additionalProperties: false` has never been a load-bearing constraint.** It is an aspiration the
corpus outgrew, and nobody knew, because nothing reports it. My 7 added fields broke **zero** records —
the count is identical at both revisions, which is the check that answers the question honestly rather
than the diffstat (620+/586- looked alarming and was git counting long single-line summaries).

**And the push tool does not validate against the schema at all** — 3 incidental mentions, no
`validate()` call. `--dry-run-all` still reports `TOTALS: 383 — CREATE 7, SKIP 376, ERROR 0`,
unchanged. So the schema is documentation that a reader may consult and a machine never checks.

**This is worth stating plainly because it changes what the schema means:** until something validates,
adding a field is a convention, not a constraint, and a future reader who trusts
`additionalProperties: false` will be misled. Either a validator should be added and the 315 legacy
records brought into line, or the `false` should be dropped and the block documented as open — the one
thing that should not continue is a schema that is 82% wrong and says nothing about it.
