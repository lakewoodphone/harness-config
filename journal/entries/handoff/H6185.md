**Its safety properties are properties of the tool, not promises:** the pull never edits, renumbers,
moves or removes an entry already in the canonical tree (only the incoming one can change id, and only
when its id is taken); it is single-flight on `flock`, so two runs cannot interleave id allocation; it
refuses to start below 2 GB free, because the staging tars land on the same filesystem as the database;
it runs `check` afterwards and **exits non-zero on any error**, so a bad run appears in
`~/.cron-status/runs.tsv` instead of being silent; and it writes a status file on every outcome.

**One bug, and the way it failed is the point.** The first run died on `$2: unbound variable` — the
local-directory argument was in `TAR_C` but `collect()` read `$2`. `set -u` turned it into `rc=1`, no
status file, and nothing half-written. A job that fails loudly on an incomplete argument is worth more
than one that guesses.
