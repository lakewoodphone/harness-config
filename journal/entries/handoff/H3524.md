## 2026-10-11 21:32 UTC · ZABZ-TECH · Coordinator round 29: guards.yaml cannot be copied - the checker pins the office file's exact hash while the file references office paths, and the file itself forbids the shortcut. This one needs the approval path it defines

Coordinator round 29, 2026-10-11 21:31Z. `guards.yaml` CANNOT be ported by copying it, and the reason is
the guard system working as designed.

THE FACTS, all measured
- The office has the registry: `secratary-ts:/home/zabz/bin/guards.yaml`, **2,463 B**, sha256
 **`91ea76998a893eb7d232307abdfb84597d3f7abc37b9da04feecc738f65d4483`**.
- The cloud has **no copy anywhere** (`/root/bin/guards.yaml` absent; `find /root -name guards.yaml` empty).
- The cloud's checker pins exactly that hash:
 `/usr/local/bin/guard-registry-check.py:108 BOOTSTRAP_REGISTRY_SHA256 = "91ea7699..."`
 So it expects the registry to be **the office file verbatim**.
- **But the registry references office-only paths**, and on the cloud those things live elsewhere:
 `command: /home/zabz/bin/<guard>.py` -> actually `/usr/local/bin/<guard>.py` (all three exist there and
 RUN: `cron-target-guard` ticked at 21:30:02Z, `disk-guard` rc=0 at 21:30:02Z);
 `status_file: /home/zabz/.cron-targets/status.json` -> actually `/root/.cron-targets/status.json`
 (present), `/root/.disk-guard/status.json` (present), `/root/.db-integrity/status.json` (**absent**).
- **`guards.approval.json` is ABSENT** on the cloud.

**THE BIND: the registry cannot be both hash-valid and path-correct on the cloud.**
- Copy it verbatim -> hash matches, the checker proceeds, but every `status_file` points at a path that
 does not exist -> findings that are wrong and would be blamed on the guards.
- Translate the paths -> correct on the cloud, but the hash changes, and the file's own header says
 *"Any other hash is a CHANGE and makes the checker exit non-zero unless `guards.approval.json` carries a
 record for that exact hash naming a real owner-queue row."*

**AND THE FILE FORBIDS THE SHORTCUT ITSELF**, in its own words: *"Do NOT 'fix' a red checker by editing the
pin in the checker: that is disabling the guard, which is precisely the self-modification this exists to
stop (journal SI-5: a guard verified by the same process that could disable it is not a guard)."* It also
notes *"editing this file is itself a guarded act."*

**SO I DID NOT INSTALL IT, AND THIS IS THE ONE CASE TODAY WHERE STOPPING IS THE CORRECT ENGINEERING, NOT
HESITATION.** The guard system defines its own sanctioned path - a translated registry plus an approval
record naming a real owner-queue row - and taking that path is a deliberate act that the design says must
be visible. Doing it quietly is the exact behaviour this file exists to prevent, and it would leave a
guard whose own protection I had disabled while telling everyone it was green.

THE TWO HONEST OPTIONS, with my recommendation:
1. **Translate + approve (recommended).** Install a cloud-path registry, compute its hash, and open the
 owner-queue row the approval must name. Cost: one deliberate decision. Benefit: the registry is correct
 on the cloud, the guards it lists are already running there, and the approval trail is intact.
2. **Retire the check.** Defensible only if the registry is judged an office concept - but the child found
 three independent reasons it is not, including a live owner question naming the registry. I do not
 recommend this.
Either way **the cloud's `/root/.db-integrity/status.json` is absent**, so `db-integrity-check` has never
written a status on the cloud - that is a separate gap and the registry would report it.

WHAT THE NEXT SESSION SHOULD DO, in order: (a) decide 1 or 2; (b) if 1, translate the three `command:` and
three `status_file:` paths to their cloud equivalents (verify each exists first), install, hash it, and add
the approval record naming the owner-queue row; (c) then watch `guard-registry` go rc=0 in the ledger.
