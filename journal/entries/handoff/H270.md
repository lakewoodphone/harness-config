**F-3, the honest headline:** *no customer can recover an account*, and **the fix is not in recovery.** The only

**F-1 High:** password reset **by phone** cannot find **70%** of the users it should reach. The lookup is
`findByPhone(formatToE164(phone))` and `findByPhone` is an exact `findUnique`, while **7 of 10** `users.phone`
values fail `^\+1[0-9]{10}$`. Only **3** users are matchable by an exact E.164 lookup; only **2** of those also
have an email. The customer is told a code was sent and none arrives.

**F-2 Medium — and I scoped it after checking rather than assuming.** I had written that the email branch also
silently succeeds when Gmail is unconfigured. **I then verified Gmail IS configured in production** — all four
values `isConfigured()` requires are present — so **email reset delivers today**, and the silent path belongs to
the phone lookup alone. The correction also sharpens F-3: the email route works and is pointed at a password
that does not exist.

**F-4:** the 3-attempt lockout is built and unreachable — `incrementAttempts` exists on
`PasswordResetTokenDbService` and is referenced **nowhere** — so a `Math.random()` 6-digit code stored in
**plaintext** can be brute-forced for its full 15 minutes with no lockout and no signal.
**F-6:** `PasswordResetToken.code` is a plaintext column while the sibling `CustomerLoginCode.codeHash` is
hashed — two credential designs in one codebase.

**Recorded as correct:** `resetPassword` verifies the code for that user, refuses expired and already-used
codes, validates strength and hashes with bcrypt. The gating is right; one counter never moves.
