## 2026-10-20 19:24 UTC · ZABZ-TECH · round 30: blocker classes are enforced - the register said 18 blocked but only 14 named their kind

# H (2026-10-20, round 30) - blocked paths now have to name WHAT KIND of blocker, and the count was wrong before

## The measurement that made this round
The register said 18 items were blocked. Their `blocked-on` prefixes summed to **14** - hardware 9, host 2, owner-money
2, owner-decision 1. So four blocked paths named a blocker without naming its class, and the register's most useful
question - "how much of this is waiting on hardware?" - had an answer (9) that nothing could check and that was
incomplete.

## What shipped: PR #86 -> `773c86f`
`check_roadmap.py` reports **RM-CLASS** when a `blocked-on` does not begin with one of five classes, and the fifth is
new because it was missing from the vocabulary rather than forgotten by an author:

| class | waits on |
| --- | --- |
| `hardware:` | a part, a device or a fixture |
| `host:` | a machine in a particular state, or a console session |
| `owner-money:` | the owner to spend |
| `owner-decision:` | the owner to choose |
| `recurrence:` | a symptom to happen again before it can be diagnosed |

The four unclassified were classified from their own text: S-P0-01, S-P0-04 and S-P1-01 are `owner-decision`;
X-P6-05 is `recurrence`, which is exactly what it has been since it failed to reproduce in 240 attempts. Decision
D-20261020-02 records the fifth class and the reason it exists.

Proved three ways: a selftest case plants `blocked-on: waiting for somebody` (13 cases now); the real register passes;
and a bad class planted by hand on W-P4-02 produced the finding against the live tree before being reverted.

## A process failure worth naming
The first attempt at this commit **did not commit**: `git add` failed on a path I passed, I had piped its error to
`Out-Null`, and the branch I pushed therefore pointed at an already-merged commit - GitHub said "no commits between
main and agent/kf-824-blocker-classes". Re-staged with the error visible, then committed properly. The lesson is the
one in the surface: **never pipe away the exit status of a `git add`**, because a commit that follows a failed add
looks exactly like a commit that followed a successful one.

## Why this matters more than it looks
The register is the plan now, and a plan's value is that its questions can be ANSWERED rather than argued. "How much
of this is waiting on hardware" was answerable by reading 52 files; now it is answerable by counting, and a path that
tries to dodge the classification fails the gate. That is the difference between a machine-checked plan and a
well-formatted one.
