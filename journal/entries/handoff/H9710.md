## Addendum 19 to H9513 (round 21) — 2,780 texts refused because the gate was broken, and nothing said so

A thread from round 1 of this programme that I had never closed. `owner_text_decision`, read:

| code | allowed | rows |
|---|---|---|
| `ok` | 1 | 3,827 |
| **`gate_error`** | 0 | **2,780** |
| `awaiting_reply` | 0 | 1,315 |
| `too_long` | 0 | 1,273 |
| `rate_floor` | 0 | 49 |

**Every one of the 2,780 is in the first five days of October**, and every one carries the same
sentence:

> *"the owner-text ledger is unreadable (TypeError: getattr expected at most 3 arguments, got 7);
> refusing to send rather than sending blind"*

So **one internal bug** — a `getattr` called with seven arguments in the gate's body — made
`app/owner_text.gate()` raise on **every** owner send for five days. The broad `except Exception`
around the gate is deliberate and per message the direction is right: refuse rather than send blind.

**In aggregate it was a channel outage.** What went missing was `urgent_email` (2,564) and
`reminder:N` (216). Nothing escalated — not the liveness probe, not the estate monitor, not a wake.
*A gate that is broken and a gate doing its job look identical from outside: both produce refusals
with a reason.* That is the measurement rule's exact failure mode, in the estate's most-used gate.

No seven-argument `getattr` exists in the code now, so the bug is history. **What was missing is the
detection**, and that is K3:

```
OK K3 the owner-text gate is not refusing because it is broken
 0 gate_error decision(s) in the last 1 day(s); 2780 all-time. Most recent: the owner-text
 ledger is unreadable (TypeError: getattr expected at most 3 arguments, got 7); ...
```

`ok`, `awaiting_reply`, `too_long`, `rate_floor` and `similar_hold` are the gate **working**.
`gate_error` is the gate **broken**, and it now has its own invariant — window-scoped like J1 and K1,
so the historical 2,780 are reported on every run and only a fresh one fails.

**19 checks, 0 FAIL.** Mirror IN SYNC, 21 files. Commit `04563775`.
