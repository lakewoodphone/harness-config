## 2026-09-28 03:56 UTC · ZABZ-YOGA · The waze CLI is built and I ran it: 27 subcommands, eight states with unreadable distinct from empty, and it found that the billing engine can record an all-unlinked night as status ok

**THE `waze` CLI EXISTS AND I RAN IT. This is the interface the owner actually uses - his workflow is through an agent, not a browser - and it was the thing missing from everything built so far.**

**Verified by running it, not by reading a report.** `waze doctor` from a bare checkout produced, in order:
- **`✖ UNREADABLE - this is NOT an empty result`** - the headline doing exactly what it promises.
- `FAIL env-config`: *"env.config.ts refused to load the environment ... Every check below therefore reads raw process.env, and NOTHING that depends on the validated config can be trusted."* - **it refuses to claim anything it cannot back.**
- `FAIL fleet-config` / `FAIL fleet-token`; **`SKIP fleet-reach`** - *"Not attempted: the fleet-api is not configured"* - **`skip` is a distinct status from `pass`.**
- `WARN stripe-key`: *"A LIVE key is configured (prefix "sk_live_", length 107). Nothing here PRINTS the key, and every check below is read-only - but a real billing sync against this key moves real money."*

**THE DESIGN TURNS ON ONE THING, and it is the right thing.** Every command lands in exactly one **state** - `ok`, `empty`, `not_found`, `unreadable`, `refused`, `unsupported`, `confirmation_required`, `error` - with `0` as the only success exit code (3 config, 4 unreadable, 5 refused, 6 not found, 7 missing flag, 8 unsupported). **`data` is `[]` for empty and `null` for unreadable, so an agent that ignores `state` still cannot confuse them.** Given that "we could not read it" rendering as a zero or an empty list is this codebase's signature defect, encoding the distinction in two independent places is the correct defence.

**27 subcommands + 4 aliases, `--json` on every one, no new dependency** (hand-rolled parser, envelope and redaction). 111 tests across four suites (`cli` 20, `destructive` 43, `unreadable` 26, `why-not-billing` 22), typecheck exit 0. The destructive suite asserts the **call log** - a gated command must refuse *before* the mutation - across 9 commands x 2.

**`why-not-billing <serial>` walks 14 links and names the first broken one with its fix - AND IT EARNS ITS PLACE BECAUSE THE ENGINE'S OWN TRAIL CANNOT DO THIS.** The agent found that `findLinkedSubscription` returns a single `unlinked` for a missing **device, customer or subscription** alike, and **`deriveRunStatus` counts refusals by the string prefix `refused` - so a night where EVERY device is unlinked records status `"ok"`.** **The billing engine can report a healthy run while billing nothing.** That is a money-truth defect in the ENGINE (backend), not in any screen, and it is now on the list.

**SIX COMMANDS REPORT "not supported by the backend" RATHER THAN FAKING IT** - wipe, locate, lock, message, retire, and marking a provisioning step - each naming what would have to be added. `provisioning mark-step` is the interesting one: provisioning states are **recomputed on every read and nothing is persisted**, so there is genuinely nothing to write. That is an architectural gap, now named rather than hidden.

**IT CORRECTED MY BRIEF WITH EVIDENCE.** I listed "not in a billing period" as a broken link in the diagnosis chain. It is **not** a break: the engine creates the period row **lazily** via `upsertPeriod()`, so an absent row is a **symptom** of an earlier break and never its cause. **Reporting it as broken would have sent someone to fix a row that is supposed to be absent.** Shown as `info` with the reasoning attached, and a test pins it.

**THREE BUGS IT FOUND BY RUNNING RATHER THAN TESTING:** `doctor` **crashed on a broken machine** (it called `stripe.availability()` unguarded and the degraded port throws from every method - found by running it, fixed, 3 regression tests); an empty argv element became a command (pnpm on Windows passes `""`, so a bare `waze` said "unknown command" instead of printing help); and `device show` blamed `FLEET_API_URL` when the real cause was a failed environment validation, **reporting a symptom as the cause**.

**HONEST LIMITS, as it states:** no `.env`, no `FLEET_API_URL`, no `DATABASE_URL` on that machine, so fleet/Stripe/DB are unreachable **by definition** and the happy paths are **NOT VERIFIED**; the pasted output is the graceful failure, labelled, with stdout and stderr shown separately. It deliberately did not attempt `billing sync --confirm-billing-sync` (moves money) or any action on real hardware.
