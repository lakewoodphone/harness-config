**W2413 · 2026-09-28 · The outcome monitor was starving itself on IOSchedulingClass=idle - fixed via drop-in, ran in 5s instead of timing out at 6m40s.**

## WIN — the outcome monitor was starving itself; fixed live and verified in 5 seconds

**Measured 2026-09-28 on `secratary`, before and after.**

### Before (the failure nobody saw)

```
company-outcome-monitor.service, 04:07 run:
 04:07:00 Starting ...
 04:13:40 start operation timed out. Terminating.
 04:13:40 Main process exited, code=killed, status=15/TERM
 04:13:40 Failed with result 'timeout'. Consumed 1.544s CPU over 6min 40.039s
 -> outcome-20260928T040700Z.txt 0 bytes
 -> outcome-20260928T040700Z.json 0 bytes
```

1.544 s of CPU across 6 min 40 s is a process that was **blocked, not busy** — and 6 min 40 s is
exactly the unit's own `TimeoutStartSec=400`.

### The cause, read off the unit file

```
[Service]
IOSchedulingClass=idle
Nice=10
CPUQuota=50%
MemoryMax=1G
```

`IOSchedulingClass=idle` means **"use the disk only when nothing else wants it."** On a box whose
database is 12.17 GB and which logs 1,847 `database is locked` events a week, "nothing else wants it"
never arrives. **The unit was designed to stop the monitor hurting the box, and the side effect was
that the monitor was guaranteed to starve precisely when the company was busiest** — which is when
outcomes matter most. The protective configuration created the blind spot it was built to prevent.

### The fix (a drop-in; the shipped unit file is untouched)

```
/etc/systemd/system/company-outcome-monitor.service.d/20-finish-budget.conf
 [Service]
 TimeoutStartSec=900
 IOSchedulingClass=best-effort
```

`Nice=10`, `CPUQuota=50%` and `MemoryMax=1G` remain, so it is still a good citizen and still cannot
hurt the box. The original unit was copied to `/home/zabz/unit-backups-20260928T045706Z/`. Removing
the drop-in directory reverts the whole change.

### After — run for real, not asserted

```
TimeoutStartUSec=15min IOSchedulingClass=2 (best-effort)
start rc=0 wall=5s
Result=success ExecMainStatus=0
outcome-20260928T045706Z.txt 25036 bytes
verdict=WARN [WARN] 46.5% of work sessions fail
```

**It took 5 seconds.** So the timeout was never an expensive query — it was scheduling. The monitor
was correct all along about the company's condition (46.5% failing, matching the independent
`scripts/co/scorecard.py` reading of 50.9% completed); it simply could not get to the disk to say so.

**Provenance:** `systemctl show company-outcome-monitor`, `journalctl -u company-outcome-monitor`,
and `ls -la /home/zabz/company-reports/`, all read on `secratary-ts` at 2026-09-28T04:57Z.

**What is NOT fixed by this:** the monitor still cannot tell the difference between "the company is
fine" and "I produced a zero-byte report". That is the self-measurement workstream's job
(`co/w5-measurement`), and this entry is the evidence it needs.
