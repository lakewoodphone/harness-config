**W2742b · 2026-10-13 · The owner's outflow figures were understated by 11,752.54, and I was part of the cause.**

Found and fixed 2026-10-13. Measured before and after on the live ledger.

THE INVARIANT, in the app's own words
(`app/services/finance_amount_semantics.py::direction_semantics_note`):
 "Standard convention (applied 2026-08-03/04 sign normalization): amount_cents is always
 positive and direction carries the sign. direction=debit means money out ... direction=credit
 means money in ... This applies to ALL accounts, including American Express."

WHAT WAS TRUE. **578 of 8,769 rows carried a NEGATIVE `amount_cents`** - 526 of them with
`direction='debit'`. A negative debit is not a cosmetic oddity here:
`economic_outflow_cents_sql` computes `case when direction='debit' then amount_cents else 0 end`,
so a negative amount SUBTRACTS from the owner's total spend. `cfo-balances.account_flow_cents`
applies the direction sign a second time, so the same row is wrong in the reconciliation chain
too.

MEASURED EFFECT, Apr-Oct 2026 window:
 BEFORE outflow 404,398.57 inflow 337,803.51 negative rows 523
 AFTER outflow 416,151.11 inflow 338,163.51 negative rows 0
 DELTA outflow +11,752.54 inflow +360.00

HOW I WAS PART OF IT. The statement importer I deployed this session was written to its OWN,
self-consistent convention: it stored the signed value and derived `direction` from it. So my TD
import wrote 55 rows with `debit`/negative where Plaid writes `debit`/positive - the ledger's
convention. That is the failure a worker's report called out in the same file and I did not check:
I verified the importer's OUTPUT COUNT and the idempotence, not its OUTPUT CONVENTION.

FIXED, three places.
1. `statement_csv_import.py` now has `stored_amount_cents()` returning the magnitude, the INSERT
 uses it, and `compute_canonical_hash()` hashes the absolute amount so the dedup key cannot
 depend on which convention a caller used.
2. The 55 rows I wrote were normalised and their hashes recomputed. Verified idempotent: a
 re-import now reports `inserted 0, skipped_existing 95, skipped_cross_source 2`.
3. The remaining 523 pre-existing rows (Heuristic CSV Profile 233, legacy-json 119, Generic Three
 Column CSV 106, Chase Credit Card CSV 54, BOA Stmtpipe 9, stripe-refunds 2) were normalised the
 same way, after checking that `direction` is populated on 100% of the ledger (0 null/empty) and
 that `canonical_hash` carries no unique index, so no constraint could be violated.

TWO THINGS THIS DID NOT EXPLAIN, stated so nobody assumes otherwise: the account-month
reconciliation output was UNCHANGED at 21 disagreements before and after, because the affected
rows mostly fall outside the 2026-07..2026-10 window that has balance snapshots at all. And the
`canonical_hash` values of the 523 normalised rows changed, which is correct for the new
convention but means an old dedup key no longer matches them - the `ABS(amount_cents)` cross-source
guard still catches them, which is why the re-import test above passes.
