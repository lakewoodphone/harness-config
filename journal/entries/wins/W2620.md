**W2620 · 2026-09-30 · One global cooldown clear was filing the same mesh message 81 times a day; it is now 3.**

One line in the placement monitor was spending the owner's attention 100 times a day.

MEASURED FIRST, 2026-09-30, from `owner_message_queue` and the monitor's own state:

 100 rows in 24 hours with reason='proactive_update'
 81 of them the SAME sentence: "Mesh node 'lakewooechsmini' cannot take agent work: timed out
 after 4000 ms (hard wall-clock deadline)"
 actual intervals: 30, 60, 35, 45, 40, 15, 15, 30, 15, 25, 35, 45 minutes
 configured cooldown: 7200 s, i.e. at most 12 a day

THE CAUSE WAS ONE LINE:

 if ok:
 alerts.clear()

`ok` is the AGGREGATE. A node whose probe times out intermittently makes the aggregate flip between
ok and not-ok, so every healthy pass WIPED the cooldown for every node and the next bad pass alerted
again. A per-node cooldown cleared by a global reading is not a per-node cooldown; one flapping node
keeps resetting it. This is journal P2260's "self-healing telemetry filed as an owner message", and
the entry's own recorded complaint was that it happened every one to two hours -- it was worse than
that, and the reason was structural rather than a threshold set too low.

WHAT CHANGED (anchored patch, bak-p2260 backup kept)

1. A node's alert entry is cleared only when THAT node is good, and only after it has been good
 **twice in a row**. One lucky probe does not reset a cooldown.
2. Repeated alerts for the same node back off exponentially -- 2 h, 4, 8, 16, capped at 24 h -- so a
 chronic condition costs a couple of messages a day while a NEW outage still alerts immediately.
3. The state shape is unchanged (`alerts` stays `{node: epoch}`; counts live in a new `alert_counts`
 key), so a state file written by the old version is read without migration.

PROVEN, with the notify endpoint pointed at a closed port so nothing reached the owner while testing:

 run 1 alert #1, counts=1
 run 2, immediate no alert (cooldown holds)
 aged 2h01m no alert -- the first repeat window is now 4 h
 aged 4h01m alert #2, counts=2, next window 8 h
 steady state 3.0 messages/day for a permanently bad node, against 81 measured

and a real run against the real state file alerts nothing (the 16:55 cooldown is live).

WHAT IS NOT FIXED, honestly

The other half of P2260 is the READING, not the rate: the probe still reports a node as unable to take
agent work on a `fresh=1` read that times out under load -- the class its own docstring warns about
and journal P342 recorded as "a false broker-unreachable". Today it reported `secratary` itself and
`zabz-tech` as unable to take work, which they are not. This change means that when the reading is
wrong, the owner hears about it three times a day instead of a hundred; it does not make the reading
right. That stays open, with its check.
