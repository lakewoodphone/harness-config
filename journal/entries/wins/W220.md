**W220 · 2026-09-19 · The launcher can restart its own origins proxy - root-caused, fixed, and proved.**

**W · The launcher can restart its own origins proxy — root-caused, fixed, and proved, on the machine where the outage happened (W219).**

W219 recorded the outage and left the `Access is denied` unexplained. This entry closes it, fixes the launcher, proves the streaming fix, and records the two deploys it took to make the running proxy the fixed build.

THE ROOT CAUSE, WITH THE EVIDENCE I ACTUALLY HAVE. `Ensure-OriginsProxy` (dshw.ps1) calls `Start-OriginsProxy`, and that function's FIRST write was an unconditional `Register-ScheduledTask -TaskName 'DSH Origins Proxy' ... -Force`, followed by `Start-ScheduledTask`. On ZABZ-YOGA — the laptop the outage was measured on — registering a scheduled task without elevation is denied; `D230` (measured 2026-09-16) records exactly that, `Register-ScheduledTask` failing with "Access is denied" because the account is an administrator holding a UAC-filtered token with `BUILTIN\Administrators` marked "Group used for deny only". So `ensure` threw on the re-registration BEFORE it ever tried to start the proxy that was already registered and working, the catch printed only `$_.Exception.Message`, and every origin port stayed dead. The task was never the problem; the launcher's insistence on rewriting it was.

THE W219 HYPOTHESIS WAS WRONG, AND I CHECKED RATHER THAN REPEATED IT. W219 blamed "a base64-wrapped child with its own environment". There is only one `-Environment @{ DSHW_PAYLOAD = ... }` launch in the file (`Start-SlotServerParallel`) and it has NO callers — `ensure` cannot reach it. `-Environment` exists in this pwsh (7.6.6) and is used by the live hidden-task path. `-WindowStyle Hidden` is not in the origins path. The suspects I could test were tested on ZABZ-TECH with a Medium-IL task token that really does carry `BUILTIN\Administrators ... Group used for deny only`: registering a `Highest` task, re-registering one while it is RUNNING, re-registering a wscript-wrapped task, starting a `Highest`/`HighestAvailable` task, and registering into `\Microsoft\Windows\UpdateOrchestrator\` all SUCCEEDED. That is the useful half of the result: the denial is a per-machine policy, not a bad parameter, which is exactly why the fix must not depend on Task Scheduler at all.

THE FIX (three independent ways to start the proxy, in order).

1. The task is already registered and points at the current hidden wrapper: **just `Start-ScheduledTask` it.** No registration write. This is the outage fix — starting an existing task needs no permission to rewrite its definition.
2. Otherwise register the hidden (wscript) task and start it. The origins task now uses the same `New-HiddenLauncherVbs` wrapper as the watchdog tasks, so it does not flash a console.
3. If both scheduler paths fail, start the proxy **detached via WMI `Win32_Process.Create`**, hidden through the same wrapper — the escape hatch `Start-EngineDetached` already uses. It needs no Task Scheduler and no elevation, and a duplicate is harmless because the proxy refuses to bind when base 3200 already answers and its own lock file is held by a live pid.

`ensure` now also REFUSES rather than lying: if all three paths fail it exits 3 and says so, instead of continuing as if healthy while every window's door is shut. The catch records the real exception object (type, HResult, category, errorId, script stack, inner) to `~/.dsh/multi-window/origins-start-errors.log`, so the next occurrence is diagnosable without a repro. The full command line lives in `Get-OriginsNodeArgument`, so the three paths cannot drift.

PROVED, ON THIS MACHINE, BOTH WAYS.
- Cycle 1 (the exact outage scenario): stopped the running proxy, ran `dshw ensure`; it came back **through the already-registered task** (`[origins] proxy up ... (registered task)`), 24/24 ports listening, `origins.pid` updated, in 5 s.
- Cycle 2 (the ZABZ-YOGA condition, forced): `DSHW_ORIGINS_NO_SCHEDULER=1` so paths 1 and 2 are skipped; `dshw ensure` started it via **WMI direct** (`(direct, pid 94576)` → node 109412), 24/24 ports, `origins.pid` updated, in 4 s. The scheduled task stayed `Ready`, proving the fallback is independent of it.
- Before each cycle `Get-NetTCPConnection -LocalPort 3200 -State Listen` was checked and after each cycle it held 24 listeners; the engine answered through the proxy.

THE STREAMING FIX IS VERIFIED (`multi-window/tools/verify-splice-keepalive.mjs`). The committed `setKeepAlive(true, 15000)` is on the running build now — and the proxy that was RUNNING before this session was the PRE-FIX build (the local file had no `setKeepAlive`), because the fix had only ever been committed to `origin/master`. The test reads the real `splice()` source out of `dshw-proxy.mjs`, compiles it with stub sockets, and asserts `setKeepAlive(true, 15000)` and `setNoDelay(true)` on BOTH legs; a negative control removes the loop and confirms the pre-fix splice sets neither, so the harness discriminates. End-to-end, an isolated proxy (ports 3590/3599, fake engine) served a spliced stream, the engine-side socket was killed mid-stream, the client observed close in **2 ms** (not a hang), and a fresh client reconnected and was served. A true packet-level silent drop cannot be staged on loopback without a packet filter; the silent-drop half is therefore proved at the socket-option level, the close/reconnect half end-to-end.
