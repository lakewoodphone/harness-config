**W2820 · 2026-10-14 · Three company fixes deployed and verified: the repetition guard redirects, 13 timestamp windows corrected, and a serving probe that can actually fail.**

Two more company defects are fixed, deployed and verified on the live service, and the failure I had to discover twice by accident now announces itself.

**1. The repetition guard redirects instead of ending the session.** `autopilot.py` closed a work session the moment it saw near-identical output twice in a row — the company's **largest residual failure class, 10 of 26 sessions (38 %)** in the 07:23–11:50 window. It now injects a directive at repeat 2 and continues, ends only at repeat `>= 4` **and only after a redirect was already given**, reports the true count (the old code said `_repeat_count + 1` while firing at `>= 2`), and keeps the `artifact_required` path. `git apply --check` exit 0, applied cleanly, backup `app/autopilot.py.bak-repeat-20261014T130359Z`, and — the strongest available check — **the applied file's md5 is `e5d8eac5c3a113f8b4ecd5a2287572dc`, byte-identical to the tree the test suite passed 19/19 against.** Reproduced by me on the deployed tree: `19 passed in 0.49s`. On the preserved base the same test gives `14 failed, 5 passed`, one of the failures behavioural (`recorder.closes == []`), because the base guard really does close at the second repeat — so it is a regression test, not a snapshot.

**2. Thirteen timestamp-window defects across eight files.** The estate compared `T`-format timestamps against `datetime('now')`, whose output is **space**-separated, so `col > datetime('now','-N days')` covered **N+1 days**. The worklist I handed over was **19 sites, not the 20 I stated** — one was wrong — and of the 19, **13 were genuine defects and 6 were already correct**: `overhaul_contract.py:335/:685/:742` normalise with `datetime(replace(substr(col,1,19),'T',' '))` and `lifecycle_sweep.py:1213/:1220/:1276` use `datetime(col)`. Those six were left untouched, with control measurements proving equivalence (`3214 = 3214`, `14113 = 14113`, `6 = 6`) rather than assumed. Two columns are genuinely **mixed-format** — `anomaly_log.detected_at` (326 `T` / 212 space) and `google_voice_secretary_log.item_timestamp` (186 / 1) — which is why `julianday()` is the right fix rather than a `strftime` literal.

**3. The wedge now announces itself.** `company-api` wedged **twice** on 2026-10-14 and neither time did any check say so: `active`, `NRestarts=0`, listening, and answering nothing. The one probe that deadline-checks the service's own endpoint — `ai-gateway-health.py`, every 30 minutes — is by its own docstring *"a NOTE, never a fault ... a monitor that turns its own optional probe into a red job is a monitor that gets ignored."* That reasoning is sound for a secondary reading and its consequence is that an unresponsive API exits **0**. So `/usr/local/bin/company-api-serving-probe.sh` now runs every 5 minutes on the estate's own `cron-wrap` convention (crontab backed up, 184 → 185 lines, the appended line verified clean of CR, and its base64 payload decoded to check). It reads a **trivial** endpoint with **no key, no database, no model call**, so the only way it can fail is the service not serving; it exits **nonzero** so `cron-wrap`'s frozen TSV records it; and it never restarts anything. **Proven on all three paths:** live service `OK http=200 in 0.0063 s` exit 0; dead port `FAIL curl rc=7` exit 1; live port with a wrong endpoint `FAIL http=404` exit 1.

**What is not claimed.** The repetition change's two known caveats are recorded, not hidden: the close fires on the 4th counted repeat rather than the 5th, and `_repeat_count` / `_last_work_output` / `_repeat_redirect_session` are never reset at session start, so a session inheriting a spent counter and a redirect flag cannot close on repetition (bounded by the 20-step and 60-turn caps — it falls back to budget exhaustion). The timestamp fix's known cost is that **`julianday()` is not sargable**: `EXPLAIN QUERY PLAN` flips `model_usage` from `SEARCH … USING INDEX idx_mu_created_at` to `SCAN`, 0 → 23 ms at 262,513 rows, and the index-friendly `strftime` literal measured exactly equal but is **wrong on the mixed columns**. And nothing here is yet shown to have moved the 38 %.
