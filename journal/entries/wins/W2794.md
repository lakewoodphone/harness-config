**W2794 · 2026-10-13 · The loaded instruction surface was two days stale on both machines; it is now checkable and correct.**

THE DEFECT THAT HID EVERYTHING ELSE, now fixed and checkable.

WHAT WAS WRONG. Four times in this program an edit was correct in git and absent where it runs: the
archive script (W2758), two `main` lineages of harness-config (P3164), `scripts/owner-queue.py` 8.7 KB
behind its deployed copy, and -- the worst -- **the instructions themselves.**

MEASURED 2026-10-13:

 secratary-cloud /root/.dsh/.agent-presets/zabz/agent.cordis.yml
 57,970 B, mtime 2026-10-11 20:14 -- two days old, still shipping the
 single-brace `{cwd}` bug, with none of the rules written that week.
 `/root/.dsh/skills/` DID NOT EXIST -- not one skill was installed.
 ZABZ-YOGA loaded `zabz` was 58,677 B against the repo's 56,297; the loaded
 `parallel-agent-orchestration` was 10,802 B against this repo's 13,275.

So a session could write a rule, verify it in the file it edited, report it fixed -- and every
session on every machine would keep loading the old one. **The rules this program wrote were not
running anywhere.**

FIX: `scripts/preset-drift.py` -- compares what a machine LOADS against what the repo says, for the
per-preset files and the shared skill catalog, and installs with `--apply` behind timestamped
backups. Exit 0 clean / 1 drift / 2 could-not-run, the same contract as its sibling
`assert-bin-matches-repo.py` (which answers the same question for a different, remote surface -- this
one is deliberately local so every machine can check itself with no ssh and no manifest to keep in
step).

TWO DESIGN ERRORS OF MY OWN, FOUND BY THE TOOL AND WORTH KEEPING:
 1. The skill catalog is ONE namespace shared by every preset, and the presets carry DIFFERENT
 versions of the same skill. The first cut compared each preset's copy separately and would have
 let whichever ran LAST win.
 2. The second cut matched "equals any preset's copy" -- and `parallel-agent-orchestration` then read
 MATCH while the catalog held `cordis-bg`'s 10,802 B version WITHOUT the three rules `zabz`'s
 13,275 B copy carries. **"Matches something in the repo" is not "matches the surface this preset
 loads."** The standard is the designated source, and the repo disagreeing with itself is now
 reported separately as DIVERGENT.

RESULT, VERIFIED BY READING THE LOADED FILES BACK:
 ZABZ-YOGA 15 compared, match=15, drift=0
 secratary-cloud 15 compared, match=15, drift=0, **9 skills installed where there were none**
 both single-brace `{cwd}` = 0, the wrong-data rule present, `secratary-cloud` named
 in the preset, and all three `parallel-agent-orchestration` rules loaded.

STILL OPEN, AND IT IS THE POINT OF THE WHOLE FINDING: nothing RUNS this check on a schedule. The
tool exists and is honest; the step that would have caught two days of stale instructions is still a
thing a session has to remember. Scheduling it -- or folding `--check` into a job that already runs --
is the next move. The estate's `lpt-production-case-work` and `parallel-agent-orchestration` are also
genuinely different across presets, which is a repo-tidiness job rather than a deploy one.
