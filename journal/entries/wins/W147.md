THE FINDING THAT MATTERS MOST, and it was not in any audit: the committed build context
`context: ../fleet-dashboard/backend` is correct for the REPO layout (deploy/fleet-dashboard is a
sibling of deploy/waze-mdm) but resolves to the non-existent /opt/fleet-dashboard/backend on the box,
where the tree is nested. So `docker compose build fleet-dashboard` FAILED - meaning the deployed
dashboard image had been frozen at 2026-07-05 and every dashboard change in this repo since July was
written, reviewed, and never shipped. The running staff interface was four months old. The agent
fixed it in place (./fleet-dashboard/backend) and proved the one-line deviation: reverting it makes
the box compose hash byte-identical to the repo blob. I have now documented the override in the
compose file itself and pushed it (12aa9e1f) so the next person does not rediscover it.

Second trap, same family: `git archive` from a Windows workstation delivered every .py, .ts and .json
as CRLF, because .gitattributes has rules for *.sh/*.yml/*.ps1/Dockerfiles but none for Python. The
deploy only achieved byte-identity with the reviewed commit after normalising 21 files by hand. The
*.py eol=lf rule is already present on origin/master (checked), so the specific gap is closed; the
general lesson is that "the file I copied" and "the file that runs" are different claims until a
hash says otherwise - and this estate has now been bitten by that three times in one day (Caddyfile
inode, frontend-dist never rebuilt, CRLF on upload).

HEALTHCHECK DECISION, kept as committed, with the measurement that justifies it: on the live config
/api/health returns 200 "degraded" (db probe verified, nanomdm reachable, fleet_api unverified), so
the binary 200-assert cannot misfire on partial degradation; it returns 503 only when the DB stops
being queryable, which is the one failure that makes this dashboard useless. And there is no restart
loop: docker does not restart on unhealthy, and the */5 watchdog only restarts services that are NOT
RUNNING.

FILED AS PAIN P178 (pre-existing, not from this change): an unwritable /data makes the app EXIT at
startup (init_db -> PRAGMA journal_mode=WAL -> sqlite3.OperationalError), and `restart: unless-stopped`
loops it forever while the healthcheck never gets to run, so the container never reads unhealthy. The
old image has the same pragma. Recommended: catch sqlite3.Error in init_db so the process starts and
/api/health answers 503 with the cause - which also makes the healthcheck adopted today do its job.

HYGIENE DISCLOSURE AND WHY I AM NOT RE-ROTATING ON IT: an early `docker compose config` in that
session interpolated and printed the NanoMDM API key and the Postgres DSN before the agent switched
to `config -q`. Both values are the CURRENT ones (rotated 19:52 and 20:14 tonight). The output landed
in a local session log on this workstation - which already holds both values in the .env mirror at
deploy/waze-mdm/.env, so the log discloses nothing that this machine does not already have in
plaintext. That is a same-trust-boundary mistake, not a crossing, so I am recording it rather than
consuming another rotation window: the two proven scripts are /tmp/rotate-keys.sh (nanomdm+nanodep)
and /tmp/rotate-pg.sh (postgres), each ~2 minutes with verification, if the owner wants them dead
anyway. The rule it re-confirms: `docker compose config` without -q prints secrets that live in .env.
