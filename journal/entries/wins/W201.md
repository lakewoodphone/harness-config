**W201 · 2026-09-17 · The before-state of a live roster flag, measured in process against the real fleet.**

The BEFORE state of a live-service flag can be measured IN PROCESS, against the real fleet, without
disturbing the service or reverting a deploy.

Used 2026-09-17 to show that `dispatch.v1` is the only difference between a start and a queue
(docs/mesh/104-node-enabled.md §2.5): materialise the shipped `nodes.json` (here, byte-exact, fetched
from the authority's deployed copy — sha256 `6f46131a…`), `createBroker({ nodes: rows.map((n,i)=>
({...n, index: i})) })`, `await broker.nodes({fresh:true})` to prime readings, then
`await broker.place({ task })` with the SAME body the live broker was just asked. No listener, no port,
no service, no `systemctl`, nothing to clean up — the process exits.

Result: BEFORE `node=zabz-tech-linux position=1 score=4 tier=transport eligible=1 blockedBy=["transport"]`
versus, live and one minute later on the same mesh, `position=0 score=4 tier=fits eligible=1 blockedBy=[]`.
Same disk reading (21 GiB vs 21 GiB required), same 4 free slots.

WHY IT IS WORTH KEEPING: `docs/mesh/98` §2.5 did this with STUB gates to compare two code states;
pointing the same technique at the REAL gates compares two CONFIG states on one code state, which is
what a roster flag is. And it answers the question a deploy cannot: "if I had not changed this, what
would the fleet have done?" — remembered because a future session will want it for the next flag
(`secratary`'s `v1: null` is the obvious next one, and it needs a credential measurement first).

Driver: `_scratch/104-before-contrast.mjs`; output `_scratch/104-before-contrast.log`.
