**W2763 · 2026-10-13 · 93 phantom conflicts were holding back real rows: every rule claimed a category the other entity does not have.**

2026-10-13. Six rules were holding back real rows because of a phantom conflict, and the phantom came
from one line that gave every rule a category name the other entity does not have.

THE SYMPTOM. `cfo-resolve --apply-rules` reported "held back by conflicts with existing rows (never
overwritten)" for six rules. `retire_counts` over all 49: matched 1,734, uncategorised 55, conflicts
**1,160**. The heaviest were broad merchant rules - `stripe` 687, `twilio` 262, `openai` 110.

THE CAUSE, and it is one line of `cfo_rules.learn_rule`:
 cats = {"default": category}
so a rule learned on ONE entity also claimed that category name as the `default` for every other
entity, and `category_for_entity` falls back to `default` when the row's entity has no entry. But
`categories` is PER ENTITY and the names differ. The live resolver says it plainly for twilio:
 entity 'personal' has no category named 'Software & Online Services'; this entity's own
 'Subscriptions' means the same thing
so a rule learned on `lpt` as "Software & Online Services" made every PERSONAL twilio row a conflict.

MEASURED BEFORE TOUCHING ANYTHING. Recomputing `retire_counts` with `default` stripped from every
rule, in memory:
 as stored : matched 1734 uncategorised 39 conflicts 1160
 default removed: matched 1734 uncategorised 39 conflicts 1067
and three rules cleared completely - `us mobile` 40 -> 0, `github` 27 -> 0,
`amazon markeplace na pa` 2 -> 0 - while `uncategorised` did not move at all. So the 93 removed
conflicts were **phantom**, and each one had been holding back a real row. A rule that conflicts
retires NOTHING, so a false conflict is not a harmless warning: it is the reason the row stays
unexplained.

FIXED IN TWO PLACES. `learn_rule` now sets `{"default": ""}` and names only the entity it was learned
for, so a row of another entity gets "" and is reported as a gap rather than misfiled or falsely
conflicted. And the 46 stored rules that carried the phantom default were corrected through
`cfo_rules.write_rule` itself - the sanctioned append-only, last-wins path, not by editing the file -
each carrying a `repair` evidence line saying what was changed and why. File backed up to
`/root/.cfo/rules.jsonl.bak-phantomdefault-<ts>`; `cfo_rules.py` to `cfo_rules.py.bak-defaultcat-<ts>`.

THE PAYOFF, measured:
 conflicts 1,160 -> 1,067
 unexplained 547 -> 537 pct_clear 91.20 -> 91.36
 rules 49, clusters 2, rows written 10
Held back is now four rules rather than six - the two that cleared (`github`, `amazon markeplace na
pa`) retired their rows immediately.

WHAT REMAINS, and it is genuinely mixed rather than buggy. Four rules still conflict:
`CR-0ee104ca7f81` "bank of america" x9, `CR-bbd00c23da88` "dov waidenbaum llc" x4,
`CR-adce0b3df424` "soundiiz" x3, `CR-796bef623a84` "twilio" x2. These are clusters whose rows
legitimately carry more than one category - `bank of america` covers a mobile DEPOSIT (revenue) and
ordinary bank activity (not revenue) under one key, so no single rule can be right for all of it -
and the tool refusing to overwrite is the correct behaviour, not a defect. A per-entity key or a
per-row decision is what those need, and neither is a rule-shaped fix.

ALSO NOTED: `/root/.cfo/rules.jsonl` is 95 lines for 49 live rules. That is the append-only last-wins
design working as intended (46 corrections appended, the reader takes the last per rule_id), but it
means the file grows with every correction. A compaction that keeps only the winning line per rule_id
would be safe and is worth doing before it gets large.
