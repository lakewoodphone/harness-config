**W2746b · 2026-10-13 · The orders with no total: 19 were already on the box, 125 are a source limit worth naming.**

2026-10-13. 144 of 671 marketplace orders carried no total. They split cleanly, and the split changes
what the right next move is.

WHY THEY HAD NO TOTAL, diagnosed rather than guessed. The parser matched SHIPPING notifications -
"OUT FOR DELIVERY: ...", "ORDER DELIVERED: ...", "Your package is now with its carrier!" - which
never contain an amount. Read directly: three linked emails for one such order, bodies 51-80 KB,
not one line matching `total`. The order confirmation that does carry the total was never linked to
these order ids.

THE SPLIT, measured:
 has every line item priced -> 19 the amount was ALREADY on the box, just not added up
 no line items at all -> 125 nothing to derive from

FIXED, durably. `marketplace_order_sync._total_from_items()` sums an order's own line items when
no total was parsed, and refuses to return a partial sum when ANY item is unpriced - a total that
omits a line is not the order's total, and the matcher would spend it against a card charge. The
19 existing rows were backfilled with the same rule and `total_kind='derived_from_items'`. It is
safe against later runs: `upsert_orders` already refuses to let a NULL from a new parse erase a
value an earlier run found ("a NULL from this run never erases a value an earlier run found").

MEASURED EFFECT, via the systemd unit:
 orders with a total 527 -> 546 of 671
 orders matched to a card 408 -> 418
 orders with NO amount 144 -> 125
 service exit 0, ok: true, evidence written 10 / 408 already present

THE 125 THAT REMAIN are not a code defect and not a data-repair job: the emails in hand contain no
amount. Closing them means finding each order's CONFIRMATION email by item title rather than by
order id - bounded, ~125 Gmail searches, and worth doing only if the owner wants per-order amounts
for used DVDs and parts. Recorded here so nobody re-derives the diagnosis, and so nobody mistakes
the 125 for a parser bug.
