The kernel's own `history.jsonl` on secratary records the whole repair as a trend,
which is worth keeping because it shows the findings falling one at a time rather
than a single green reading replace a red one:

 14:55:53 exit=1 attention=1 checks=["owner_queue"]
 14:58:44 exit=0 attention=0 checks=[]

What made that possible, and what is worth reusing:

**1. When a health check fires, first ask what the number it read is a fact
*about*.** Both findings this session were true statements about a row and false
statements about the system: a log that ages when idle, and a queue row that ages
when the owner defers. Neither could be cleared by answering the question it
implied, because neither was about a fault at all.

**2. Prove the check can fail before believing it when it passes.** The new email
logic was run against seven crafted cases, all of which it had to flag: stale
poller, failed poller, held-but-untriaged messages, missing poll time, absent
state file, unparseable state file, plus a healthy baseline it had to leave alone.
It counted exactly 2 of 3 in the mixed case. A check that has only ever been seen
green is untested.

**3. Test against a copy, never the live artifact.** The first version of that
test wrote to `data/autopilot_state.json`, the live autopilot state, in a loop.
Caught before it ran and changed to `SENTINEL_AUTOPILOT_STATE_FILE` pointing at
/tmp; the live file's mtime and parseability were then verified unchanged. The
reason to make the path injectable was not tidiness — it was that the harness for
proving the fix was safe was itself mutating production state.

**4. Check what the remote already has before overwriting a file.** `scripts
/owner-queue.py` looked absent from `harness-config`, so the deployed `~/bin` copy
was about to be committed over it. `git log origin/master -- scripts/owner-queue.py`
showed the repo's copy was from 09-16 while `~/bin` carried four later commits, so
committing the deployed file was a legitimate refresh and not a revert — but the
same check on a different day would have silently destroyed someone's work. The
rebase also conflicted in five journal files, all of them generated caches, and
the right resolution was to take the upstream side and let the cache rebuild
(`journal.py check` -> 0 errors afterwards), not to merge index files by hand.

**5. Fixing a false alarm must not mean silencing the alarm.** The owner_queue
check still goes HIGH the moment a deferral expires, ranked ahead of every other
reason; a stale poller still goes HIGH; only the reading that genuinely could not
distinguish idle from dead was replaced. Deferring three rows closed nothing —
all 15 remain pending and open in the journal mirror.
