**W2877 · 2026-10-14 · The two stall classes now have distinct names (stalled_no_tool_call vs stalled_repeating_output) and the retry-context reader learns the new one - behaviour deliberately unchanged, so the population can finally be counted.**

The two stall classes now have distinct names, so the population can be counted instead of guessed — and I deliberately did **not** change behaviour to get there.

**What was wrong was the label, not the logic.** Having read the no-tool-call path (`autopilot.py:5145-5198`) I found it considered and reasoned: it records `[EMPTY-TURN: ...]`, waits for two consecutive silent turns, then issues **one** explicit re-prompt naming the exact JSON envelope the prompt documents, and closes only if that fails. Its close site's own comment says *"The session stopped calling tools. **This is NOT a spent work budget**"* — so **the code already knew it was a different cause and still wrote `stalled_repeating_output`**, the name belonging to the near-identical-output guard I fixed in round 20.

**So the change is a rename plus a reader fix, not a behaviour change:**

 line 5190 empty_turn_reason = "stalled_repeating_output" -> "stalled_no_tool_call"
 line ~3811 the retry-context reader's alternation -> learns STALLED_NO_TOOL_CALL too

The second half is the one that matters: `_prior_attempt_context` builds a later attempt's failure from those markers, so a rename that stops there would have **silently dropped the reason a session died for** from its successor's context. House precedent for distinct reasons already existed (`no_action_step`, `planned_step_budget_reached_without_artifact`), and the marker is derived from the reason, so the two names stay paired by construction.

**Verified:** `import app.main` OK; the receipt suites **9 passed**; restart rc=0; probe `OK`; backups `autopilot.py.bak-stalllabel-20261014T153256Z` and `.bak-stalldoc-*`; and the class check now returns **three separable numbers** rather than one:

 STALLED_NO_TOOL_CALL 0 STALLED_REPEATING_OUTPUT 15 EMPTY-TURN-REPROMPT 14

The 0 is expected — only closes *after* this deploy carry the new name — and **14 sessions issued an envelope re-prompt today**, which says the no-tool-call path is common rather than marginal. **From now the two classes can be counted against each other**, which is what round 33's finding requires before anything is changed about the behaviour.

**And the trap this avoided, which is the reason for writing it down.** A rename can *look* like a fix: had I stopped at line 5190, the `stalled_repeating_output` count would have fallen on the next count — and a falling number invites the conclusion that the class shrank. **Updating the reader and checking that both names are emitted is what makes the change a measurement instead of a cosmetic one.** That is the same failure the estate already has twice over: the contention counter that greps a string the app does not write, and the health endpoint whose body says `ok:false` while its status code says 200.

**Still not established, and next:** which class dominates the 38-40 % that motivated the original work. The marker that number came from was this mixed one, so the figure needs re-deriving from the split data rather than being carried forward. **And the behaviour question — whether a session that has stopped calling tools should spend its remaining steps trying a different route rather than closing — is now answerable from data instead of from an argument.**
