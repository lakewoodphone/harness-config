WHAT WAS BUILT - scripts/engine-vitals.mjs (+ scripts/install-engine-vitals-task.ps1)
Reads the engine's real health surface (bootstraps the auth cookie from the window
token in multi-window/state.json, then GET /healthz) and records one CSV row per
pass: pid/uptime, loop p50/p95/max, live sessions, agent loops, heap, rss,
governor slots in use, health-probe cumulative spawn count, disk free %, corpus
dirs/MB -> ~/.dsh/metrics/engine-vitals.csv.

WHY IT WAS NEEDED, MEASURED
/healthz needed 8,687 ms to answer. Loop p50 57 ms / p95 2,200 ms / max 16,854 ms
with 10 agent loops in one engine process. On 2026-09-25 the same engine at 2
loops showed p95 15 ms / max 348 ms. Nothing recorded load against latency, so
"decay with uptime or just load?" had no answer. It now can.

THE RESULTING DIAGNOSIS, AND IT IS A CAPACITY FACT NOT A BUG
The current slowness is 14 concurrent agent loops sharing ONE Node event loop on
a 22-core laptop. That is at the ~13-14 concurrent-session ceiling measured on
this machine on 2026-09-16 (L/? - the 2026-09-16 overload session). The engine is
not broken; it is at its concurrency limit.

AND THE PRECISE REASON THE GUARD DID NOT PREVENT IT
`admission_governor` derives its budget from FREE MEMORY: at the time of
measurement it reported 24 slots with 10.3 GB free while the event loop was
16.8 s late. Memory was never the binding constraint. The governor also shows
14 agent loops vs 1-2 leased slots, i.e. agent loops do not take slots at all.
A memory-derived guard cannot see event-loop saturation, so it reported "plenty
of room" during the worst stall of the week. engine-vitals now prints this
mismatch as a note on every pass, so the gap is at least visible from a file.
