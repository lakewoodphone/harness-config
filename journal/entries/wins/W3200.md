**W3200 · 2026-10-15 · ps_circuit_breakers fixed: it queried five columns that exist in no table, and the honest answer is a different question from the one it asked.**

`ps_circuit_breakers` -- the CEO's own tool for reading breaker state, and the one I was using to investigate the deadlock -- returned `{"error": "no such column: action_name"}` on every call. Fixed and proven.

THE BUG: it ran

 SELECT action_name, state, failure_count, last_failure, cooldown_until
 FROM circuit_breaker_events ORDER BY last_failure DESC LIMIT 30

and **not one of those five columns exists in any table**:

 circuit_breaker_events(id, agent_id, event_type, reason, spend_at_event, created_at) 20 rows
 circuit_breaker_state(agent_id, state, cooldown_until, tripped_at, reason,
 failure_count, cooldown_sec, updated_at) 0 rows

WHY THE OBVIOUS FIX WOULD HAVE BEEN WRONG: correcting the SELECT to those columns would answer a DIFFERENT question, because the breaker the docstring promises -- per ACTION -- is not in the database at all. `app/chat_action_resilience.py:16` holds it in process memory (`_circuit_breaker`, threshold 10, cooldown 120 s). The two tables are per AGENT. A tool that returns a confident, well-formed, irrelevant answer is worse than one that errors, because nobody looks again.

WHAT IT DOES NOW: reports the agent-level state and the 20 recent events, states in the payload that the action-level breaker is per-process and unreadable from SQLite, and hands over the query that does answer it (count `temporarily disabled` in work_sessions.output_log).
