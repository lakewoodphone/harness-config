## THE FINDING, MEASURED RATHER THAN BELIEVED

The walk reported `[major] The order table is 956px wide in a 1920px window - 964px (50%) of the screen
is not used by the list`. Because the harness had **just been proven unreliable at lookups**, this was
re-measured directly. Live page, 1920x1080:

| what | measured |
|---|---|
| viewport | 1920 x 1080 |
| `[data-counter-content]` and `main` | `max-width: 1280px` -> width 1280, x=448, so **640px unused** |
| the first row | **955px inside that 1280px container** -> another **325px unused** |
| rows rendered | **125** |
| content height | **1984px** in a 1080 viewport |

**Roughly half of a 1920px window is not used by the list**, and a 125-row work queue is rendered in a
column that wastes it. Fix direction: raise or drop the 1280px cap for the hub at large breakpoints and
let the row fill its container. **It is a taste question as much as a technical one**, so the numbers
are the argument and the decision gets recorded when made, with a before/after from the same probe.

**THIS IS THE FIRST FINDING THE LOOP PRODUCED THAT SURVIVED INDEPENDENT VERIFICATION.** Walk ->
verify -> document -> rank -> work. That is the whole intended shape, and it happened.
