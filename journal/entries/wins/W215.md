Three separate things are confirmed by that output, each of which could have failed silently:

1. **The policy mounted and is ON.** The line is emitted by `decidePressure`'s new branch, so the config

2. **The raised connect timeout is live** — `-o ConnectTimeout=25` is on the actual hop, not just in the
 file.
3. **It behaved correctly when it was not needed.** The broker named the desktop, so the policy added no
 exclusion and said so; it did not re-ask, did not release a lease, and did not perturb a placement that
 was already right. That is the branch a policy like this most often gets wrong.

AND THE EXPRESSION ITSELF, checked directly rather than assumed: `COMPUTERNAME = 'ZABZ-YOGA'`, so
`preferRemote = True` on this machine and false on the Linux and macOS nodes by construction — no list to
rot, which was the point of keying it on `COMPUTERNAME` rather than on a node table.

complaint and can be seen working in the output of an ordinary dispatch. It cost one engine reload, it is
reverted by one line, and it is justified by a measured 1.05 GiB and 25 processes rather than by an
argument. The claim it does NOT make — that DSH now *feels* faster — remains unmeasured, and a second
workstream is running specifically to try to measure it under CPU-active load rather than the sleeping
