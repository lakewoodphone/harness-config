**W207 · 2026-09-17 · One browser tree for every DSH window: 9 processes / ~892 MB per window -> 1 process / ~60-296 MB.**

MEASURED 2026-09-18, ZABZ-YOGA, engine pid 4416 on 3099 never restarted.

BEFORE (7 windows, one --user-data-dir each): 74 msedge processes, 6804 MB. Per profile: 9 procs and 692-1064 MB, mean 892 MB.

AFTER (shared profile + one loopback origin port per window): two runs of the same experiment
 baseline 66 procs/6927 MB -> window A 76/7562 (shared tree+1 renderer) -> window B 77/7858 (shared tree unchanged, +1 renderer/+296 MB)
 baseline 65 procs/6499 MB -> window A 74/6941 (9 shared procs/612 MB) -> window B 74/7000 (9 shared procs/764 MB, +59 MB)
Total for N windows is now tree + N*renderer instead of N*tree; the 8-window projection is 17 processes against 72.

WHY IT IS SAFE: localStorage["dsh.sessions.current"] is keyed BY ORIGIN (dsh-api-session-controller/lib/client.js:3058), so a distinct loopback PORT is a distinct session slot. The engine binds 127.0.0.1:3099 only and the /api fence 403s w1.localhost but accepts ANY 127.0.0.1:<port> (401 = fence passed). So per-window isolation is bought with a port alias instead of a whole browser.

WHAT THE OWNER LOSES: nothing he uses - separate windows, one per slot, own session slot, restore after reboot all kept. The real cost is blast radius: the browser process is now a single point of failure for all windows (a renderer crash still takes only its window). profileMode "per-window" in windows.json restores the old behaviour exactly.
