**DEFECT 1: every single-account Gmail search silently truncated at 500.** `list_messages` (`gmail_service.py:599`) made **one** call to `list_messages_page` and returned `page["messages"]`. Gmail's `users.messages.list` caps a page at **500** — documented — so `max_results=2000` returned exactly **500**. Proof: the receipt sync asked for 2000 with the whole inbox in range and reported `"listed": 500`; with the fix it lists **583**. **This is not a receipt bug.** `search_messages` is the ordinary search path, so *every* single-account caller with `max_results > 500` has been truncating — the harvests, comms searches, anything that pages. The multipl-account path already handled it (it returns `next_page_tokens`); the single-account path dropped the token. **Fixed** by following the token until `max_results` is met: +930 bytes, `import app.main` OK, **9 tests pass** across the merchant and write-path suites, backup `gmail_service.py.bak-paginate-20261014T150130Z`. **A cap that is never announced is the same failure mode as an empty result reported as health.**

**DEFECT 2: the backfill's state pins the id list, so it can never see a message that arrives after its first listing.** Measured: with the pre-existing state it reports `"listed": 500, "already_done": 500, "remaining": 0` — it re-lists the *cached* ids and finds nothing to do; with a fresh state the same code lists **583**. So the fix above appeared not to work until the state was cleared, and I nearly recorded a false negative (*"the pagination didn't help"*) because of it. **A discovery cache that outlives discovery turns every later fix into a no-op.**
