**W · The fifth node is calibrated and every node on the mesh now has a unit cost — with three different metrics, which the table says out loud**

MEASURED 2026-09-18 by workstream M; consolidated in `docs/mesh/114-node-capacity.md`.

`lakewooechsmini` (macOS, 10 cores, 16 GB, the node that was off the mesh for two days until a wrong-scheme
probe was falsified): **159 MiB per concurrent agent turn** (CI 142-176, R² 0.961) by the macOS
commit-analog, and **229 MiB** (CI 193-264, R² 0.949) by the resident cross-check on the same runs. 70
children launched, **70 exited 0**, none left behind.

THE NUMBER IS TWO NUMBERS, AND BOTH ARE REPORTED. The resident figure is HIGHER because the host is
swap-pressured — 54.1 % of swap was already used at the start, so adding children **evicts other
processes' pages**, and aggregate commitment grows by less than the children's own footprint. The child
reported both rather than choosing the tidier one.

THE METRIC IS NOW THREE METRICS, NOT TWO, AND THAT IS THE MOST IMPORTANT THING IN THIS ENTRY:
- Windows desktop and laptop: `GlobalMemoryStatusEx` commit charge.
- Linux (`zabz-tech-linux`, `secratary`): `/proc/meminfo` `Committed_AS`.
- macOS: **neither**, because `GlobalMemoryStatusEx` does not exist there and has no counterpart. The
 figure is an analog from anonymous + wired + compressor pages, with `swapUsed` pinned at a constant
 1,743,582,658.56 B across 1,300+ samples so it cancels in every delta. Every raw component of every
 sample was preserved so an alternative metric can be recomputed.
**Method-identical within a platform, merely suggestive across platforms.** Every cross-node comparison in
the table is now labelled directional, because nobody has shown any two of these count the same quantity.
A table that silently presents three different measurements as one column is exactly the kind of confident
wrongness this programme has spent the day finding and correcting.

A DEFECT THE CHILD FOUND IN ITSELF AND DISCLOSED, worth keeping because it is a general trap: its first
sampler slept with `Atomics.wait`, which **blocks the event loop**, so Node never reaped its children — they
finished at ~2 s and became **unkillable zombies** (`remainingAfterKill:[75031]`). Rewritten async, after
which every child exited properly. A parent that cannot reap its children cannot clean up after itself, and
"the children hung" was the sampler's fault, not the node's.

AND THE HONEST WEAKNESSES, WHICH THE CHILD VOLUNTEERED: the plateau is **one sample** in every K>0 run
(children finish in 1.4-1.8 s against a 250 ms poll grid), and `alive == K` does **not** guarantee K children
still hold memory — two K=2 runs plateaued with one child's worth of RSS, which is the source of the bimodal
K=2 values. No run at K=1, so the low end of the line rests on the K=0 control alone.

CLEANUP, ON A MACHINE THAT BELONGS TO SOMEONE ELSE: pid 12458 (their engine) alive and never signalled,
port 3099 still listening, swap byte-identical before and after (`used = 1662.81M free = 1409.19M`), no
files created on the mac (all payloads were base64 piped to `node -e`), and the only divergence in its
before/after snapshot is `freeMiB` 6550 -> 6937 and load 1.44 -> 1.49.

THE LAST MEASUREMENT STILL RUNNING IS THE ONLY ONE THAT SPEAKS TO THE OWNER'S ACTUAL WORD: responsiveness on
the laptop under load. Everything above is memory and capacity; **none of it is speed.**
