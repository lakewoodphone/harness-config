**Half the owner queue was the same message repeated: 328 held rows were 158 findings, now deduped without deleting one row**

**The measurement.** Of 328 rows sitting `held`/`queued` in `owner_message_queue`, only **158 were
distinct findings**. The difference was pure repetition:

| reason | rows | distinct bodies |
|---|---|---|
| `ask_owner` | 96 | **95** |
| `sync_breaker:ebay_sync` | 74 | **1** |
| `sync_breaker:amazon_sync` | 74 | **1** |
| `owner_briefing_evening` | 25 | 24 |
| `owner_briefing_morning` | 21 | 19 |
| `urgent_email` | 16 | 10 |
| `financial_alert:reversal` | 10 | **1** |

A repeat is one finding observed again, not a new finding. That half-a-queue of duplicates is what
made an all-or-nothing kill switch look necessary (**P51**): the switch was "sane" only because the
queue looked like noise, and the queue looked like noise because nothing counted repeats. This is the
first half of what P51 prescribes.

**Fixed at the writer.** `enqueue_owner_message` no longer inserts when the same `reason` and `body`
are already undelivered; it bumps `repeat_count` and `last_seen_at` on the existing row and returns
its id. Keying on the (reason, body) pair is deliberately narrow — every one of the 95 distinct
`ask_owner` questions survives.

**Backfilled, and nothing was deleted.** The 170 pre-existing duplicates were collapsed by marking
the older copies `superseded` (an existing status value, already used by 45 rows) and putting
`repeat_count` on the newest survivor. Measured on the live database:

| | before | after |
|---|---|---|
| `held`/`queued` rows | 328 | **158** |
| rows deleted | — | **0** |
| total rows in the table | 1738 | **1738** |

Every row is still present, so the audit trail of when each finding was raised survives and the
change is reversible by a status update.

**Verified on real data, not fixtures.** On a temp database seeded with the *actual* production body
(`sync_breaker:ebay_sync`), 74 enqueues produced **1 row with `repeat_count=74`**, and all 74 calls
returned the same id. 9 unit tests pass on the authority's own tree, including a legacy database
created without the new columns being migrated on first use — which mattered, because SQLite has no
`ADD COLUMN IF NOT EXISTS` and `CREATE TABLE IF NOT EXISTS` does not alter an existing table, so
without `_ensure_owner_message_columns()` the dedup would have raised `no such column` on the 3 GB
production database and never worked at all.

**The residual, named because it is real.** Dedup by (reason, body) assumes an identical body means
the same finding. For `urgent_email` the body is only `From:` + `Subj:` + `Acct:` — no message id, no
received date — so two *different* emails that share a sender and subject line would collapse into
one row. The live case that exercised this was benign (7 copies of the same Telnyx low-balance alert,
2026-09-06..09, correctly one finding with `repeat_count=7`), but a "Re: your order" pair would not
be. The fix is to put the message id or received timestamp in the body so the key is exact; it is not
done here.

**Still not built:** the **rate limit** half of P51, and the delivery itself. Dedup makes the queue
readable; it does not make it read. 158 findings still sit `held` with the newest `sent_at` at
**2026-07-19T02:32Z** — including 10 held `urgent_email` rows whose content is genuinely the owner's
(a Netlify "action needed" from today, a Deep Infra failed payment).
