**W2761 · 2026-10-13 · The estate monitor's critical conditions now reach someone: a consumer, not a louder producer.**

THE "ALARM WITH NO TRANSPORT" CLASS — the live instance is fixed, and the fix respects the design.

WHAT WAS WRONG. `estate-monitor.py` on secratary-cloud is a good instrument and it works. At
14:04:01Z its verdict was **critical, 4 crit / 1 warn / 1 nodata**, including:

 oom_kills_24h crit 11.0 streak=708 (23.6 HOURS critical)
 disk_used_pct crit 86.74% streak=224
 api_rss_gib crit 6.309 GiB streak=121
 swap_used_pct crit 83.47% streak=49
 disk_free_deficit_gb warn 3.157 GiB streak=260

Nobody was told. And that is **by design, and the design is right** -- the monitor's own rule 3:

 "IT CANNOT TEXT THE OWNER. Nothing here opens a socket to a person. The only escalation is
 syslog(daemon.err) + alerts.jsonl + an ESCALATED flag file ... Everything else is log-only."

A disk reading is not the owner's to triage, and flooding him destroys the signal of the alerts that
are. So the fix was never a louder producer.

THE DEFECT WAS TWO HALVES, AND BOTH ARE NOW CLOSED.
 1. **No consumer.** `alerts.jsonl` had THREE rows, all one metric (`public_health_status`), and
 nothing read them. Syslog and an ESCALATED flag file are where a message goes to die.
 2. **A filter that kept the truth out of the stream.** Only `public_health_status` carries
 `mode="alert"`; the eleven OOM kills never entered `alerts.jsonl` at all, so even a consumer of
 that file would not have seen them.

FIX: `scripts/estate-alerts-to-journal.py`, deployed to `/usr/local/bin/` and scheduled by
`estate-alerts-to-journal.timer` every ten minutes at :02,:12,:22,:32,:42,:52.

It reads `state.json` -- which carries the state of **every** one of the 31 metrics, not just the one
allowed to escalate -- and files **one journal `pain` entry per episode** for each metric that is
critical and has held that state for N consecutive runs. That is the estate's existing channel for
work a session picks up: a journal entry, not a message to a person. It does not modify the monitor,
its thresholds or its escalation list. Rule 3 is kept exactly.

FILED IMMEDIATELY: P3021-P3024, the four critical conditions nobody had been told about.

VERIFIED IDEMPOTENT, in both paths: the manual run and the first scheduled run both report
"nothing to file -- every critical metric is either below the streak or already filed". An episode
ends when the metric clears, so a RECURRENCE files again -- a recurrence is information.

WHAT THIS DOES NOT DO, deliberately: it never texts, emails or calls. If a condition ever genuinely
belongs to the owner, that is the owner queue's job, one question at a time.
