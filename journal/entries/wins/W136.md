**The guard was fail-open.** `_resolve_tool_path()` did `if not candidate.is_absolute(): candidate =
approved_roots[0] / candidate`. On the Linux authority `C:\Users\ezabz\Downloads\file.txt` is not
absolute, so it was silently rooted inside the workspace and the subpath test answered "inside
approved roots" -- the call was allowed, not merely mislabelled. The same in reverse on Windows with
`/etc/passwd`. Traversal (`../../etc/passwd`) was already handled by `candidate.resolve()`. It now
fails closed for any path that is absolute on another platform, verified by hand:

 C:\Users\ezabz\Downloads\file.txt -> gateway_blocked_tool_call
 /etc/passwd -> gateway_blocked_tool_call
 ../../../../etc/passwd -> gateway_blocked_tool_call
 README.md -> read_file (in-root, untouched)

**I did not relax it to satisfy the last assertion, and that is the deliberate part.** The remaining
`test_sanitize_tool_call_out_of_workspace` failure is its cross-platform case: it approves
`C:\Users\ezabz\Downloads` as a gateway root and expects a Windows path under it to be preserved. I
implemented exactly that and it took the file from 1 failure to 3, because the two sibling tests
approve a Windows root and still expect blocking. The suite is internally inconsistent about
cross-platform paths -- it was written on Windows, where those paths behave differently -- so the
guard keeps the safe direction and the test is the thing that needs fixing (make it platform-aware),
not the guard.
