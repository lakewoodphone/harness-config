**W136 · 2026-09-15 · The company was restarting itself every 70 seconds - two logic errors in one watchdog, fixed and verified.**

**What was wrong.** The company API was restarting itself roughly **every 70 seconds**. Measured:
`journalctl -u secretary-api --since "7 days ago" | grep -c "Started secretary-api.service"` → **339 starts
in 7 days**, per day 2/3/23/32/11/43/51/**174** (Sep 8→15), median inter-start gap **70 s**, 65% of gaps
under 120 s. The watchdog's own log recorded **292 restarts in 25.5 h — 145 `secretary-api` and 147
`secretary-dashboard`**.

**The cause, in code, two independent errors in one 300-line script.**
`scripts/server/access-watchdog.sh`, run by a systemd timer every 60 s:

1. `ensure_enabled_active` tested `systemctl is-active --quiet`, which is **false while a unit is
 `activating`**. A cold start takes ~15 s, so the watchdog would find the API mid-startup, restart it,
 and kill the startup it had just requested — forever.
2. `check_http` used `curl --max-time 8` on `/health` and restarted unconditionally on failure. `/health` is
 normally **7 ms**, but it stalls to **25.2 s**; 1 of 25 samples exceeded 8 s, so on the order of 58
 timeout-triggered restarts a day. The same lines restarted `secretary-dashboard`, which the API restart
 itself made unhealthy — the log shows four restart events in 62 seconds, alternating api → dashboard →
 api → dashboard.

**Why it was invisible.** `/health` returns 200 whenever anyone asks. The failure was never that the service
was down — it was that it was **never up for long**. Every restart destroyed every in-flight tick and agent
run, which is a leading cause of the 7,450 `database is locked` errors in 7 days and of work that gets paid
for twice.

**The fix, and how it was verified before being believed.** Four guards: `activating`/`reloading` now count
as **alive**; an HTTP failure must repeat `HEALTH_FAIL_THRESHOLD=3` consecutive times; a per-service
`RESTART_COOLDOWN_SECONDS=900` cooldown that also breaks the api↔dashboard oscillation; and a
`WATCHDOG_DRY_RUN=1` mode. `CURL_TIMEOUT_SECONDS` 8 → 15.

Verification actually performed: uploaded and normalised line endings → `bash -n` clean; ran the new script
under `WATCHDOG_DRY_RUN=1` with an isolated `STATE_DIR` and confirmed it logged `access watchdog ok` and
performed **no** systemctl action; recorded a pre-fix baseline (292 watchdog restarts, 190 API starts/24 h);
backed the original up to `access-watchdog.sh.bak-restart-storm-20260915-194301`; installed and re-ran
`bash -n`. A background sampler then watched the restart counter for 16 minutes.

**Reusable result.** Two one-line logic errors, both of the same species — *treating "not yet ready" as
"dead"* — cost this system ~339 restarts a week and an unknown amount of re-done work. Any health check in
this system should be audited for that species: does it distinguish **slow/starting** from **dead**?
