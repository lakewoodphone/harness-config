**W2757 · 2026-10-13 · sessions.mjs could not see the authority: the session reader had no secratary-cloud node.**

MEASURED AND FIXED 2026-10-13, the second instance of the same defect in one hour.

scripts/sessions.mjs DEFAULT_NODES held ONE authority-ish row -- 'secratary' -> 'secratary-ts', the office box -- and no entry for 'secratary-cloud' at all. The authority moved to secratary-cloud at 2026-10-11T05:43:36Z and the office box has been frozen since, so every session read aimed at the authority landed on the stopped box, and the authority's own 571 sessions were INVISIBLE to the tool every skill and every child was told to use.

FIX: secratary-cloud added FIRST; the historical names kept, because the frozen box still holds sessions written before the cutover and those are real history.

VERIFIED: node scripts/sessions.mjs nodes now reads SIX nodes -- local, secratary-cloud (571 sessions), secratary (529), zabz-tech (3932), zabz-tech-linux (458), mac-mini (271). Before the fix the authority was not in the list.

WHY THE CLASS MATTERS: a hostname hardcoded in a fallback is a time bomb keyed to a migration. When a service moves, every script that reaches it by name keeps WORKING -- against the old copy -- and nothing fails loudly. 'secratary' is a prefix of 'secratary-cloud', so grep does not catch it either. Found twice in one hour: journal.py _queue_from_authority() and sessions.mjs DEFAULT_NODES. When a host moves, grep every script for the old name and check what each one is FOR.
