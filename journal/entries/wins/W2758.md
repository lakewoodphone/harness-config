## 1. The guard is now running, not just committed

`scripts/transcript-archive-run.sh` now refuses to start a pass whose staged tars would not fit, and
re-checks the floor before every round. It was deployed to the file the hourly unit actually executes
(`/opt/company/archive/tools/transcript-archive-run.sh`, previous copy backed up as

The guard did not obstruct a pass that fits (7.43 GB free against 2.5 GB needed), which is the
behaviour that matters: a guard that blocks healthy work is worse than no guard.

## 2. The deploy had to be manual, because nothing deploys this

The deployed file's mtime was 13:34 and the repositor's commit for the same fix was 13:40 -- the fix
reached the host by someone copying it, not by any deploy step. So `harness-config` is the record and
`/opt/company/archive/tools/` is what runs, and **the two can drift with nothing to notice.** That is
the same shape as the two-main-lineage pain (P3164) and as the anchor that carried none of the six
documents governing it.

WHAT WOULD FIX IT: a deploy step with a `--check` mode that compares the repo file against the
deployed one and reports drift, or -- cheaper and enough -- the rule in AGENTS.md section 6.1: before
editing a script that runs somewhere, hash it against the host that runs it. Until one of those
exists, a commit here is not a fix there, and the difference is invisible from either side alone.
