**W2795 · 2026-10-13 · The presets were not deploying because sync.py was correctly refusing: a guard nobody reads.**

THE ROOT CAUSE OF "THE INSTRUCTIONS WERE NOT DEPLOYED", AND IT WAS A GUARD DOING ITS JOB.

I nearly wrote a deployer. `sync.py` already is one -- "Apply this harness-config repo onto the local
~/.dsh", copying presets into `.agent-presets/` and mirroring the skill catalog into `~/.dsh/skills/`
with a documented 2026-10-08 measurement of exactly why the preset-local skill dirs never reached a
fresh agent's catalog. **It is already scheduled**: `PersonalSecretary-HarnessSync` on ZABZ-YOGA.

So it runs, and the presets were still two days stale. Why:

 $ python scripts/sync.py --dry-run
 profiles: SKIPPED -- the committed generated preset rows are STALE:
 --check: DRIFT - profiles/web/presets.generated.patch.yml does not match what the converter
 would write
 --check: DRIFT - the `preset-rows` block in profiles/web/cordis.patch.yml does not match

`sync.py` **refuses** to install the profile layer when the committed generated rows disagree with
what `make-preset-rows.mjs` would write -- and they did, because they embedded `yocheved`'s
PRE-correction sha (`ee9fd507...`) while the generator now produces the corrected one
(`9bc0cf44...`). **The guard was right. The staleness was the defect.**

So every preset fix this program made was silently blocked from deploying, and the only thing that
said so was one line in `sync.py`'s output that nothing surfaces.

FIXED: `node scripts/make-preset-rows.mjs --install` regenerated both artefacts
(`presets.generated.patch.yml` 79,920 -> 78,660 bytes, and the managed block in `cordis.patch.yml`).
`--check` now exits 0, `sync.py` proceeds past the profiles step, and a real run reported
`preset zabz: applied (3 file(s))`, `profile mesh: cordis.patch.yml applied`, `profile web:
cordis.patch.yml applied`, `sync complete`.

THE LESSON, AND IT IS THE SAME ONE THIS PROGRAM KEEPS MEETING: **the estate did not lack a deployer,
it lacked a reader of its own guards.** A guard that refuses correctly and reports into a log nobody
reads is indistinguishable from no guard at all -- which is the `P2`/silent-failure class, in the
deploy path this time. The detector written earlier (`scripts/preset-drift.py`) found the symptom;
the estate's own guard held the cause; neither is a substitute for the other, and both are now
documented in each other's terms.

CAVEAT CARRIED IN THE TOOL: `preset-drift.py` is a BYTE comparison and line endings are bytes, while
`sync.py` normalises them deliberately. If the detector reports DRIFT and `sync.py --dry-run` says
"up to date", **believe sync.py** -- the comparison is what is wrong.
