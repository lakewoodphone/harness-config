**W2156 · 2026-09-20 · ZABZ-TECH pre-bootmgr 166-178s to 25s, and Hello survives reboots, by bringing firmware current.**

**Measured, same machine, same day: ZABZ-TECH's pre-bootmgr window went 166–178 s → 25 s, and Windows Hello survived consecutive reboots, by bringing firmware current.**

Before (ZABZ-TECH, 2026-09-20, from the boot watcher's own `off-window` = shutdown-start → bootmgr-start):

| Boot | off-window | VSM blob | Hello |
|---|---|---|---|
| 12:48 (firmware chain) | 251 s | `BlobSize=0`, corrupt=1 | `7002 0xD000A002` → container deleted |
| 15:02 (first boot after BIOS flash) | 1295 s † | `BlobSize=0`, corrupt=1 | `7002 0xD000A002` |
| **15:33** | **25 s** | **`BlobSize=723`, corrupt=0** | **`8002 State: Okay`** |
| **15:38** | **25 s** | **`BlobSize=723`, corrupt=0** | **`8002 State: Okay`** |

† power-off the owner started by hand 21 minutes later; not a POST measurement, shown only for completeness.

What was done: the three Lenovo firmware updates Windows Update kept offering and never applying were installed one per boot — `System Firmware 1.0.0.92`, `ME Firmware 16.1.30.2330`, `TPM Firmware 15.24.18954.0` (Infineon, `15.23.17664.0 → 15.24.18954.0`) — taking BIOS from `M4WKT56A` (2025-06-02) to `M4WKT5CA` (2026-07-07). Afterwards Windows Update offers **zero** firmware and all firmware devices report `problem=0`.

Why this is a win rather than a note: the symptom was *two* things the owner reported separately — "takes a long time to turn back on" and "I have to reset the PIN" — and they turned out to be the same event on the same boots, with one fix. Both halves are now measured as fixed on two consecutive boots, not asserted.

Caveat carried deliberately: two consecutive clean boots is strong evidence, not proof, because the failure was intermittent and tracked firmware-application boots. If it recurs, the first question is whether any firmware or Secure Boot DBX update landed recently. See `harness-config/docs/mesh/117-zabz-tech-hello-and-boot.md`.
