2026-09-30 round 33. After three text searches produced three different wrong answers about what the owner pays for, I built the probe that answers it at runtime instead: it reads each credential from the provider env by NAME, calls a real endpoint, and reports WORKS or FAILS with the http code and latency. RESULTS, quoted. tavily WORKS http 200 in 1497ms. exa WORKS http 200 in 1949ms. spider WORKS http 200 in 903ms. firecrawl WORKS http 200 in 124ms. jina WORKS http 200 in 845ms. deepseek WORKS http 200 in 358ms. brave WORKS http 200 in 433ms returning 80810 bytes. perplexity returned http 400. AND THAT LAST ONE IS THE IMPORTANT RESULT: perplexity is NOT broken, and a naive reader would have retired a working credential. The body reads max_tokens must be at least 16 - a complaint about MY request, not about the key. A credential that is accepted enough to receive a specific parameter validation error is a live credential; 401, 403 and 429 are credential and quota problems, 400 with a field complaint is the caller being wrong. So the probe as written has a false-FAIL mode, and it demonstrated the exact error the script own footer warned about, in the same run. REFINEMENT REQUIRED, recorded so the registry does not inherit it: classify by meaning, not by status class - 2xx WORKS, 401 and 403 CREDENTIAL BAD, 429 QUOTA, 400 with a validation body WORKS BUT CALLER WRONG, anything else UNKNOWN, and never print FAILS for something not established. CONSEQUENCE FOR THE MONEY QUESTION, and it changes it: every credential I can probe is LIVE. Nothing here is dead. So the question is not which keys are broken but which paid capability overlaps another and is unused in practice - and that needs the provider billing pages, not a probe. Script saved at scripts/probe-credentials.sh so the probe is reproducible rather than a one-off command.
