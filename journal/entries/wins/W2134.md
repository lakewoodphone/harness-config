**Why this is the right evidence and the earlier readings were not.** Until now every check I ran was
either the absence of a bad log line or the presence of subsystem chatter, and neither distinguishes a
healthy loop from a wedged one. The state file is written on every exit path of `run_once`, so
`run_count` advancing is a positive statement that a run reached its end. That is the difference between
"nothing looks broken" and "the thing works".

**How the latch would have behaved at this same moment.** The run took roughly 8 minutes - longer than
the 300 s interval and close to the 600 s ceiling. Under the old code a run that exceeded 600 s was
abandoned with `shutdown(wait=False)` (which cannot kill a thread) while `_run_once_active` stayed True,
and the next iteration would log "previous run still active" and do nothing - for ever. **This run came
within about two minutes of producing exactly that outcome**, which is how a system ends up looking
merely quiet while running once every 72 minutes and completing nothing.

**Honest limits.** One completed run does not establish a rate. The loop is demonstrably iterating and
clean for the current window; whether `run_once` routinely exceeds its ceiling is a separate question
the next healthy hour will answer. And the ~8-minute duration is itself worth watching - `run_once` is
slow, which is consistent with the 9.8 GB database and the write contention recorded as P2132/P2127.
