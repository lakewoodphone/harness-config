**W2755 · 2026-10-13 · Session tiering finished end to end: two real tool defects fixed (stale locks, mismatched verification), four machines tiered, and it is now a daily schedule.**

FINISHED END TO END, AND IT UNCOVERED WHY THE TOOL HAD NEVER WORKED. The owner asked to
finish the session tiering; doing so exposed TWO real defects in scripts/session-corpus.mjs,
either of which alone made the tool unable to archive anything on a machine that has lock
files -- which is every machine.

DEFECT 1 -- A STALE LOCK WAS A PERMANENT HOLD.
 `if (f.name === 'active' || f.name.endsWith('.lock')) { guarded = true; }` and the report
 line "N session(s) carry a lock/active marker and will NEVER be archived".
 MEASURED: every session directory on zabz-tech-linux carries a **0-byte session.lock dated
 2026-09-16/17** beside data from the same day -- a month old. The tool therefore reported
 "excluded 107 ... will not move / selected 0 of 447", and would have said that FOR EVER,
 however old the sessions became. lakewooechsmini: the same 107, same cause.
 FIXED: a lock now holds a session only while it is RECENT (LOCK_FRESH_MS, 24 h). `active`
 stays an unconditional hold, and the move-time re-check still refuses any session written
 since selection, so the guard is not weakened -- only the false hold is removed. An
 unreadable lock is treated as stale so a corrupt marker cannot pin a session for ever.

DEFECT 2 -- THE POST-MOVE VERIFICATION USED A DIFFERENT PREDICATE THAN THE SCAN.
 The scan counted only non-marker files (1). The destination check counted ALL files (2).
 So every move with a lock file present failed with "file count 2 != 1" and was ROLLED BACK.
 MEASURED: 107/107 on zabz-tech-linux and 107/107 on lakewooechsmini reported exactly that,
 and the live corpus never shrank by a byte. That is why the tool had "deliberately never
 been run" and had never actually archived anything.
 FIXED: the destination count and byte sum now use the same predicate as the scan (exclude
 `active` and `*.lock`).
 IMPORTANT AND WORTH KEEPING: the tool ROLLED BACK rather than leaving a half-moved session.
 The safety design was correct; only the comparison was wrong. A tool that had been less
 careful would have "succeeded" here and lost data.

THE TIER NOW, all four writable machines, verified by sessions.mjs's own fleet report:
 zabz-yoga 1793 total = 621 live / 1172 archive (was 1793 live, 850.7 MB)
 zabz-tech 3896 total = 1405 live / 2491 archive (was 3749 live)
 zabz-tech-linux 447 total = 340 live / 107 archive
 mac-mini 252 total = 145 live / 107 archive
 secratary 528 live / 0 archive -- CORRECT: frozen rollback anchor, a rename inside
 ~/.dsh is still a write, and its sessions are already in the byte archive.
 Every machine kept a manifest and the tool prints its own restore command each time.

MADE ROUTINE, which is the part that stops it regressing. New
`/root/bin/session-tier-run.sh` on the authority tiers all four machines over ssh with the
per-platform invocation each needs (PowerShell on Windows, absolute /usr/local/bin/node on
macOS because node is NOT on a non-interactive ssh PATH there, plain node on Linux), logs a
one-line summary per machine to /root/.session-tier/tier.log, and is installed as
`17 6 * * *` via cron-wrap.sh under the marker `175-session-tier`. First end-to-end run:
3.0 seconds, all four rc=0, and it moved 42 further sessions on the laptop that had aged past
the boundary since the manual run.

A FOURTH "A MATCH IS NOT A MEANING", caught before reporting: checking the crontab for
duplicate jobs, `grep -oE "cron-wrap.sh [a-z0-9-]+"` reported `records` three times. All three
are COMMENT lines containing the prose "cron-wrap.sh records one row per run". There is no
duplicate job. Same shape as `grep -i oom` matching "room" (L3758) and the pytest fixtures
(L3762) -- the match was real, the meaning was invented. I have now made this catch four
times in one session; the discipline that is working is printing the matched line before
putting the count in a sentence.
