**W2138 · 2026-09-20 · W2154 - run_once now reports its own duration: the timing instrument is live.**

D336 designed this; it is now deployed and working. The blocker on the autopilot cadence decision
(D2093) was that nothing recorded how long a run takes, so "make the tick fit" had no target.

**What is live** (autopilot.py, deployed 18:34Z, healthy in 40 s, `NRestarts=0`):

 _RUN_ONCE_RECENT = 5 # class constant: rolling window size
 self._run_once_recent: list[dict] # instance state
 _run_once_started = time.monotonic() # at entry, next to the latch
 # ...and in the EXISTING finally:
 _elapsed = round(time.monotonic() - _run_once_started, 3)
 self._run_once_recent.append({"at": now, "reason": reason, "duration_sec": _elapsed})
 if _interval and _elapsed > _interval:
 logger.warning("run_once took %.1fs, longer than its %ss interval - a run cannot fit "
 "its own schedule at this cadence (recent: %s)", ...)

**Why the `finally`, deliberately.** The duration is recorded on the success path, the exception path,
and when the loop abandons the run at 600 s. **An abandoned run is the most important one to measure
and the only one that never reaches a `return`** - so a `return`-side instrument would have been blind
to exactly the case that matters. The latch fix from an earlier round turned out to be the right home
for this.

**What it will settle.** Whether the 480-600 s is one dominant subsystem or several mediocre ones, and
whether the duration tracks the write contention (P2132). The warning fires on its own the moment a run
exceeds 300 s, which at current behaviour is essentially every run.

**Why whole-run timing rather than per-subsystem.** There are **95 `_record_subsystem(...)` call sites**
and 20+ subsystem blocks. Wrapping each is 95 edits to the file whose failure mode is "the company stops
working", for a question a whole-run number plus the existing per-run subsystem results already answers.
Per-subsystem timing remains the finer instrument and is still worth doing; it is not what unblocks the
cadence decision.

**Four of my own bugs were caught by the patcher's own assertions before any file was written**, and
they are worth naming because three were the same mistake - anchoring on text that occurs more than once:
1. Anchored on the full latch comment, which failed on a character-encoding difference in the comment.
2. Used `rfind` for the flag clear, which found a LATER occurrence elsewhere in the file and produced a
 syntax error at L6449 (`expected 'except' or 'finally' block`).
3. The check `recorded_in_finally` used `rfind` too, so it reported False while the patch was correct -
 a check that was wrong, not a patch that was wrong.
4. A one-line PowerShell replacement mangled the dict literal into invalid Python.
**The lesson that keeps repeating: anchor on something unique, and when a check fails, verify the check
before the work.** Each of these cost a round-trip; none reached the authority.
