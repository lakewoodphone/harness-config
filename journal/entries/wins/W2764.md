**W2764 · 2026-10-13 · 35 purchase totals were lost to a regex anchored at column zero, found by reading the mail.**

2026-10-13. Clause 2's missing totals were a one-character bug in a regex, and there is no path that
re-reads the mail to apply the fix.

THE BUG. 35 purchases sat with no amount, every one `amount_rank=1` (items found, total not) and
every one Amazon. `cfo_rules`-style reasoning could not find it; reading the actual email did. Message
`19e5b2981830440e` contains, verbatim:
 ' Order Total: $89.99'
 ' Order Total: $242.94'
and the parser's patterns were anchored at column zero:
 re.compile(r"^Order Total:?...")
Amazon's HTML-to-text conversion INDENTS the label, so `^Order Total` never matched. Measured on that
text: all four label patterns fail; counted directly, "Order Total" appears **0 times at column 0 and
2 times indented**. With `^[^\S\n]*` in front of the label, `order_total` matches both amounts.

FIXED in `/opt/company/app/services/receipt_parser.py` - five patterns (the four label patterns plus
the legacy `AMAZON_TOTAL_RE`) now tolerate leading whitespace, which still requires the label to be the
first non-whitespace on its line, so it cannot start matching mid-sentence. Backup
`/root/receipt_parser.py.bak-indenttotal-<ts>`. Verified on the real message: before, 4 records all
`total=None rank 0`; after, the same 4 records with
 order 114-9558675-0893047 -> 8999 order_total rank 4
 order 114-8921306-5847460 -> 24294 order_total rank 4
rank 4 being the most authoritative tier the parser has.

HOW THE HARD PART WAS REACHED, because the detours are the lesson. `read_message` refused three times
before it would answer: it needs `settings` positionally, `message_id=` as a keyword, and a real
`account` - and then STILL refused with "account not authenticated" until I ran from
`/root/personal-secretary-mvp`, because the service sets `WorkingDirectory` there and the token path is
resolved relative to it. Four wrong calls, each of which looked like a real fault in the system rather
than in my invocation.

AND THE FIX DOES NOT REACH THE EXISTING ROWS. Re-running the service wrote 0 and reported
`skipped_existing: 419`, and `no_amount` stayed 125. The ingest keys on the Gmail MESSAGE id, so a
message already recorded is never re-parsed - the fix will apply to mail that arrives from now on and
to nothing already in the store.

NEXT UNIT, precisely scoped so it can be picked up cold: a backfill that re-reads `gmail_message_ids`
for stored orders where `amount_rank = 1` and `total_amount is null`, runs the now-corrected
`parse_amazon_orders_from_email` over them, and updates `total_amount`/`total_kind`/`amount_rank`
through the same sanctioned writer the ingest uses. Every input it needs is already in the row: the
`marketplace_orders.gmail_message_ids` column, the account `lakewoodphoneandtech@gmail.com`, and the
token at `/opt/company/data/gmail_tokens`. The join trap to avoid: `marketplace_order_items.order_id`
is the marketplace ORDER NUMBER ('111-0032200-9576275'), not `marketplace_orders.id`.
