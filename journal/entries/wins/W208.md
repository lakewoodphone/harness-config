**W208 · 2026-09-18 · Window liveness as a union of signals, and an auto-restore loop with a rate limit and five guards.**

MEASURED 2026-09-18/19, ZABZ-YOGA, raw counts only.

WHAT WORKED: making the window-liveness answer a UNION of independent signals instead of one
mechanism. Before, `Get-WindowCount` asked the proxy only in shared mode and otherwise scanned for the
slot's `--user-data-dir`; a window on the engine port, or any window while the proxy was down, read as
"empty" - which is how `new`/`restore` came to reopen windows that were already open (229 open events
in `windows.log`). The union is: proxy per-port live connections, PLUS a process scan keyed on each
window's `--app=http://127.0.0.1:<port>` origin, PLUS two more 600 ms samples if the first is empty.

WHY IT IS BETTER: each signal alone has a hole that the others cover, and the answer no longer depends
on profileMode, on the proxy being up, or on which code path opened the window. 12 consecutive runs of
the re-enabled 5-minute watchdog task (00:12:14-00:22:14) left the open-event count at 235 - nothing
opened - while a single run opened exactly one window for a slot that had been deliberately closed, and
every second consecutive run opened nothing.

AND THE RECOVERY DESIGN, which is the transferable part: putting a rate limit AND a negative-evidence
requirement on an auto-restore loop is what makes it safe to enable. `Invoke-WindowRecovery` requires
five independent facts before it opens anything (registered open; the RECORDED port equals the slot's
origin now; the origin has a listener; the origin is not in the live set; 600 s per-slot cooldown) and
opens at most 2 windows per run. In the same session the union found 2 genuinely missing windows, so
the loop is not vacuous - but it could not have produced the 229-event stampede that caused this task
to be disabled by hand.
