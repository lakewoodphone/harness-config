The owner-SMS kill switch was enforced at three call sites out of more than a dozen

MEASURED on secratary 2026-09-15. `data/OWNER_SMS_KILL_SWITCH` exists, created 2026-07-14 by
Copilot at the owner's request, and its own text says what it is for:

 "While this file exists, ALL owner SMS are blocked.
 The CEO was stuck in a loop sending 28+ 'URGENT' texts."

It was checked in exactly three places -- autopilot._maybe_flush_owner_message_queue,
services/notification_manager, chat_action_owner -- while `send_message` is called from more than
a dozen (chat_action_gmail, chat_action_runtime, main.py x3, tool_factory, anomaly_detector, the
sms_service wrappers). So "ALL owner SMS are blocked" was not true: two urgent owner messages
went out at 00:59 that morning with the switch in place.

FIX: `send_message` already calls itself "the central choke point -- catches ALL paths" and
already computes the owner's recognised numbers there for the daily quota, so the switch now
lives in that same branch, through a testable `owner_sms_kill_switch_active(path=None)`. Scoped
to owner numbers, so customer SMS is unaffected. Commit 5581569d, four tests.

THREE SILENT LAYERS CLOSED IN THE SAME PATH, each recorded nowhere before:
 * a send that failed (no log, no counter, no status change) -> send_attempts + last_send_error
 and a WARNING, commit abb7a1d8;
 * a message refused by the urgency threshold -> the same columns now record WHY it is held;
 * an exception inside the flush itself -> was logged at DEBUG, a level the service journal does
 not show; now WARNING with a traceback.

AND THE CORRECTION THAT MATTERS MOST: none of this was a bug in the flush. The 162 held rows and
the 42 sendable ones are held because the OWNER DELIBERATELY TURNED OWNER SMS OFF. I had built a
"42 urgent alerts are being starved" story on the assumption the flush was broken, and the only
reason I found the truth was looking up the path the code actually checks instead of the path I
had assumed.
