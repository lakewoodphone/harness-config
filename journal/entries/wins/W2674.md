**W2674 · 2026-10-08 · sessions.mjs -- any session, any machine, first try; doctor all-green across 5 nodes / 5,553 sessions.**

BUILT 2026-10-09 (ZABZ-YOGA) after the owner said plainly: "when i ask you to read
sessions you many times have problems, that is not good at all, you should anywyas
build robust tooling and docs for this to be set up properly."

WHAT IT REPLACES. Three half-tools that each failed a different way:
read-session.js (correct decoder, local only, no fleet/archive/cache);
dsh-sessions.py (local only, and Python stream_reader silently returns the header
frame of a multi-frame session); ps_db_query on dsh_session_events (times out,
reports ingest time). None of them could answer "the session I had on my phone".

VERIFIED, not configured:
- `sessions doctor`: all checks pass -- local zstd, a two-frame round-trip through
 its own splitter, index cache writable, every node's inventory, and an
 end-to-end read of the newest live chat (2,496 events / 1,562 frames /
 0 failed / origin=main).
- 5 nodes answered: local zabz-yoga 1,449 files, zabz-tech 3,164, secratary 517,
 zabz-tech-linux 214, mac-mini 209 = 5,553 session files. mac-mini needed the
 explicit node search (its zsh has node only in an interactive PATH).
- It found the target: the owner's phone session about LPT money/growth is
 99f5c499-3f8e-4fa1-9445-95ec6601a7ae on secratary, 1.4 MB, 1,716 events,
 mtime 01:42Z -- by a factor of 20 over the next candidate (score 443 vs 21), and
 the same search now reads 107/107 candidates where the first attempt read 4/107.
- `list` is 37 ms from cache; it prints titles, sizes, GUI-chat vs subagent.

WHY IT WILL KEEP WORKING: decoding is local so no node needs a zstd binding; the
remote is reached by a node program over stdin so Windows/POSIX shells do not
matter; search is one ssh per host, not per session; and every reading prints
host, path, mtime, size, events, frames, FAILED frames and inventory age, so a
partial or stale answer announces itself instead of looking like a fact.
