**W2779 · 2026-10-13 · The marketplace sync had no clock, and scheduling it would have erased the item merge.**

2026-10-13. Clause 2's pipeline has never run on a clock, and a daily run would have silently erased the
item merge I made an hour earlier.

THE ERASURE I ALMOST SHIPPED. `marketplace_order_sync.upsert_orders` ends each order with
 DELETE FROM marketplace_order_items WHERE marketplace=? AND order_id=? AND line_no>=?
 (order.marketplace, order.order_id, len(order.items))
whose comment explains why: a shorter authoritative parse must not leave a tail behind. But `len(order.items)`
is ZERO whenever the fold found no line items - which is the NORMAL case for Amazon's 2026 confirmation
layout, where the mail carries a category rather than products - and `line_no >= 0` then deletes EVERY item
row for that order. So scheduling this sync unchanged would have wiped the 83 item rows backfilled from the
legacy scraper tables, silently, with a green exit. **A parse with no items says nothing about where a
longer parse ended, so there is nothing to trim to; the guard is now `if order.items:`.**

THE BIGGER FINDING. `/usr/local/bin/marketplace-orders-sync.sh` is a careful script - flock single-flight,
three attempts with a 25-second sleep because a transient lock is not a reason to lose a day, retry, a
status JSON so a health check never parses a log, and it documents its own schedule in its header:
"SCHEDULE. 05:10 UTC. ... Gmail arrives when it arrives, so the only requirement is that the run is after
the day's mail; 05:10 leaves room for the 04:30 Plaid sync so the charge side of the match is already in
the ledger." **No crontab entry existed for it and `.cron-status/runs.tsv` had never recorded a run.** So
the pipeline that reconstructs Amazon and eBay purchase history from Gmail and matches it to card charges
advanced only when a person ran it - and that is precisely why matching sat at 419 for weeks and reached
484 the moment I invoked it by hand. The gap and the fix were in the same file, ten lines apart.

FIXED AND VERIFIED WITH A REAL RUN, not a dry one:
 status=0 | matched=484 | evidence skipped_existing=484
 marketplace_order_items 725 BEFORE and 725 AFTER
so the guard holds against an actual sync, which is the only proof worth having for a delete.
Scheduled `10 5 * * *` via cron-wrap.sh; 56 jobs now. Backups:
/root/marketplace_order_sync.py.bak-delguard-20261013T070142Z and a crontab copy.

AND THE PATTERN, FOURTH TIME TONIGHT - so let me name it. The tax calendar ran and wrote to a file nobody
read. The forward view worked and had never been run. The CFO's ears matched replies and nothing on a clock
fed them. Now the marketplace sync is well built and unscheduled. **In every case the artifact existed,
the code was good, and the connection to a clock or a reader was missing** - and in every case the thing
looked healthy, because a job that never runs and a job that runs correctly print nothing different. The
cheap check that found all four: for every capability, ask WHEN IT LAST RAN; for every artifact, ask WHO
READS IT. Neither question is asked anywhere in this estate's tooling, and it should be.
