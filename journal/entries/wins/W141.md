**W141 · 2026-09-15 · The fleet-api silent-failure fixes are deployed, verified by in-container hash, and behaving live.**

Deployed 2026-09-15 20:22 UTC to waze-mdm-01, and verified by hash rather than by
hope: the running container's /srv/fleet_api.py now hashes e88c3054 (6384 lines) - the
exact file that passed 146 tests locally. The previous in-image copy was c6147cc8
(6154 lines), identical to the host copy, so the delta was only the reviewed change set.

Pre-flight that made this safe: before touching anything, sha256 the file INSIDE the
container and compare it with the host and the repo. Without that step a rebuild can
silently pick up months of unreviewed drift - which is how this system regressed a live
Activation Lock fix once already.

Live evidence after the deploy:
- /health 200; TLS /api/fleet/devices 200 (65); /api/waze/device/FFYGNQ8AN72J 200;
 public :8003 still connection-refused.
- POST /fleet/monitor/run now returns alert_errors and history_errors, and answered
 complete: true / alert_errors: 0 - the flag is now computed from the thing that can
 actually fail.
- GET /fleet/alerts: internal markers like "[stale_crit:44]" no longer reach staff output
 (leak count 0).
- A healthy device's usage is unchanged (consumed_data_mb 5.6, percent_used 0.7,
 cap_band ok); a failed read now says usage_known: false with null fields instead of
 "0 MB / ok".

Two consumers were told, in writing, about the changed contracts: usage fields can now be
null (null-check before arithmetic) and monitor/run can answer complete: false.

Also fixed while deploying: the cron that runs telnyx_usage_freshness.py was updated to
pass PG_DSN explicitly, because that script no longer ships a password default. A first
read of "it still works without PG_DSN" looked like the hardening had failed - it had not:
compose injects PG_DSN into the fleet-api container, verified with printenv, and the
refusal branch is present in the deployed file.

Rollback is one command and was printed by the deploy script; the pre-deploy file is
