**W172 · 2026-09-15 · Unblocked her Mac: a journal id collision had stopped the machine taking any updates at all.**

MEASURED 2026-09-15 on her Mac. The cost of a journal id collision is not the collision -- it is that
the machine STOPS RECEIVING UPDATES, silently.

WHAT IT LOOKED LIKE: her Mac was 13 commits behind origin and would not pull. `git pull --ff-only`
answered "Please move or remove them before you merge. Aborting". The cause: her agent had written four
real entries (L1568, L1569, P165, P166) and left them UNTRACKED, while origin's lineage had assigned the
same four ids to different content. Git will not overwrite an untracked file, so the whole pull was
refused -- meaning no configuration, no tools, no fixes, indefinitely. Nothing on the machine said so.

WHY THIS IS WORSE THAN THE COLLISION ITSELF: a collision is a data problem in one directory. This is a
machine that cannot be updated, and every failure mode that follows -- stale settings, a model that was
switched days ago, a fix that never arrives -- looks like something else entirely. Her machine was
"working" the whole time.

FIXED with scripts/unblock-journal-sync.sh, which backs up first, moves the blocked entries aside,
takes the incoming generated index, pulls, then re-adds each entry through journal.py append so it gets
a fresh id and a correctly derived hash. Result on her Mac: four entries re-added as L1666, L1667, P198,
P199; machine went to 0 behind / 0 ahead; journal check 0 errors; tree clean.

AND ONE THING I GOT WRONG IMMEDIATELY AFTER: I "tidied" the recovered headings to drop the repeated old
id, which invalidated their metadata hashes and produced two NEW integrity errors. journal.py has no
rehash command, so the correct move was to revert my cosmetic change -- the committed versions were
already hash-correct. Cosmetic tidying is never worth an integrity error.
