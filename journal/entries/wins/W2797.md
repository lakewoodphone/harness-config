**W2797 · 2026-10-13 · The deploy guard that hid two days of staleness now files a journal entry when it refuses.**

THE GUARD THAT HID TWO DAYS OF STALENESS IS NOW AUDIBLE.

WHAT WAS WRONG. `scripts/sync.py` -- the estate's deployer, scheduled as
`PersonalSecretary-HarnessSync` -- REFUSES to publish the profile patch layer when the committed
generated preset rows are stale, and it refused correctly: they embedded `yocheved`'s pre-correction
sha while the generator produced the corrected one. It printed ONE LINE into its own output.

The consequence, measured this week: **two days in which every corrected instruction sat in git and
was absent from every machine that loads one.** sync ran the whole time. Nothing surfaced the line. A
guard that refuses correctly and reports into a log nobody reads is indistinguishable from no guard
at all -- which is `AGENTS.md` section 1's own finding about the archive alarm, in the deploy path
this time.

FIX: `report_generated_step` now files **one journal `pain` entry per distinct refusal**, deduplicated
by signature so it fires once per reason and not on every tick. The entry names the fix
(`make-preset-rows.mjs --install`), the checker (`preset-drift.py`), and the date this first happened,
so a future session reading it knows it is not the first time.

BEST EFFORT BY DESIGN: a sync must never fail because a secondary report failed. And it always PRINTS
what it did -- "filed to the journal", "already filed", or "NOT FILED -- <why>" -- so the fix does
not introduce the silent failure it exists to end.

VERIFIED IN ISOLATION, NOT ON THE LIVE JOURNAL. `scripts/test_sync_alarm.py` builds a throwaway repo
containing a real copy of `journal.py`, imports sync from it, and calls the refusal path directly:

 refusal, stale rows -> files an entry, returns False (profile layer NOT published)
 the same reason again -> "already filed", still 1 entry (deduplication works)
 a DIFFERENT reason -> files again, 2 entries (a new reason is new information)
 a clean run -> returns True, files nothing
 the real journal -> entry count UNCHANGED at 3,817

A test that writes to a real store is the defect `secretary-wake` names; this one is built not to.

DEPLOYED to the desktop's own checkout (sync.py 41,017 B, `_alarm_once` present, its dry run showing
`profiles: generated preset rows UP TO DATE`), because each machine's scheduled sync runs its own
copy. A guard fixed only on the laptop would be the same defect one more time.
