**2026-10-16. The LPT website can deploy again. The owner supplied the one credential, and this records
exactly where the resulting token lives, because the whole six-round stall happened because a
credential existed in exactly one place and that place went away.**

WHAT THE OWNER SUPPLIED: a User API Token holding `API Tokens Write` - the capability to mint others.
He asked, reasonably, *"why do we need so many?"* and pasted his dashboard lists. He was right on both
counts: a token that could create tokens did exist, and there are far too many tokens.

WHAT WAS MINTED FROM IT, and why it is narrow on purpose:

```
name : lpt-frontend-deploy (Pages:Edit) 2026-10-16
id : 5ff80b9f732abd4455bdba5ec5286887
policy : Account.Cloudflare Pages -> "Pages Write" (group 8d28297797f24fb8a0c332fe0866ec89)
resource: com.cloudflare.api.account.3fe00f424ec43810af16b55df54200a3 (ONE account)
proven : GET /accounts/{id}/pages/projects -> 200, 2 projects: lakewood-phone-test, lakewood-phone-prod
```

The token it replaces was described in the repo as able to "deploy AND delete Pages deployments". This
one can write Pages in one account and nothing else. TEARDOWN-ABLE: delete token id
`5ff80b9f732abd4455bdba5ec5286887` and the deploy path is powerless again.

WHERE IT LIVES - deliberately more than one place this time:
 * **GitHub repository secret `CLOUDFLARE_API_TOKEN`** in `lakewoodphone/phone-and-tech-full`
 (confirmed written, `updated_at 2026-10-16T10:33:01Z`) - the durable, off-machine, backed-up copy
 the workflow reads. This is the one that matters.
 * `/root/.lpt-pages-token` on `secratary-cloud`, mode 600 - a convenience copy for a manual deploy.

**THE FIVE THINGS THAT WENT WRONG IN THE SEARCH, because they are the transferable part and they cost
six rounds:**
 1. I searched for the NAME a document uses (`CLOUDFLARE_API_TOKEN`) and reported the absence of the
 THING. The estate stores it as `CF_API_TOKEN`. **A negative is only as wide as the search.**
 2. I tested a capability the task did not need (can it manage tokens) instead of the one it did
 (can it reach Pages), and reported from the proxy.
 3. I inferred "cannot create" from a `GET` that 403'd. Only the `POST` settles it.
 4. I read a Cloudflare Access `302` as proof a tunnel origin was alive. **Access answers at the edge,
 before the tunnel** - that status says nothing about the connector.
 5. The token that would have worked in one call - `copilot-full-access`, which carries
 `Pages Write` on all accounts - was in the owner's dashboard the whole time and nowhere in the
 estate. **The dashboard is part of the estate's credential surface and was not in my inventory.**
 Added to the sweep that should have existed from round one: enumerate credentials where they are
 MANAGED, not only where they are USED.

TWO MORE FACTS WORTH KEEPING:
 * `POST /user/tokens` is the endpoint for a User-scoped admin token; `/accounts/{id}/tokens` is for an
 Account-scoped one. Aiming at the wrong one returns 403 code 9109, which reads exactly like
 "this token cannot do it" and is not.
 * the permission group is called **"Pages Write"** in the API and "Account.Cloudflare Pages" in the
 UI, and its id is `8d28297797f24fb8a0c332fe0866ec89`. A filter written against the UI wording
 matches zero groups and looks identical to "not permitted".
