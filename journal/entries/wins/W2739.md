**W-new · 2026-10-12 · The search surface on the cloud authority went from entirely dead to every mode working under budget — and the fix is reproducible from git.**

Measured on `secratary-cloud`, 2026-10-12T03:0x–03:4xZ (journal H3571).

**What was true before this session.** `ps_search` — the tool the `fast-search` skill tells every agent
to use — returned `{"ok": false, "error": "Tool search not found"}`. So did `ps_comms_search`. The
engine `find-anything` was installed nowhere on the box, `ripgrep` and `ctags` were absent, and 599 of
607 registered tool bodies had no implementation. A search for anything, in any mode, failed.

**What is true now.**

| | before | after |
|---|---|---|
| `ps_search` any mode | `Tool search not found` | `exit_code 0`, `searched true`, provenance on every mode |
| `ps_comms_search` | `Tool comms_search not found` | real rows, 179,608 indexed records, index 0.24 h old |
| registered tools with a body | 8 of 607 | **601 of 601 active, 0 without** |
| `fa symbols` | exit 4 (no ctags index) | 82,899 symbols, query 12–22 ms |
| `fa journal "lpt website deploy"` | **exit 1 — "no match"** | exit 0 |
| `journal.py search "cloud migration secretary"` | **exit 1 — "no match"** | exit 0, 399–490 ms |
| negative control | — | still `exit_code 1` (a real negative, not a refusal) |
| `journal.py check` | — | **0 errors** |
| clocks | none | refresh + freshness guard + tool-body guard, on non-colliding minutes |
| source of truth | one disk, 89 lines ahead of git | `harness-config/scripts/find-anything/`, committed `1c88848` |

**Why this counts as a win rather than a fix.** Three properties hold that did not before:

1. **Every door is exercised, not assumed.** Both the MCP tool (`ps_search`) *and* the action path
 (`ps_action("search")`) were called in all five modes, plus a negative control, and the exit-code
 contract was read rather than the prose.
2. **The failure is now detectable by something other than a human noticing.** `tool-body-guard.py`
 exits non-zero when an active tool has no body and exits 2 when it cannot check — with a `--selftest`
 that proves it fails on a broken registry. `check-faindex-freshness` exits non-zero when an index is
 stale. Both run on their own clocks and record into `~/.cron-status/runs.tsv`.
3. **The correction did not cost performance.** The first version of the journal fix measured 4.7–5.8 s
 against a 5 s budget; the shipped one is 399–490 ms, and warm `ps_search what=journal` ended
 *faster* than before the change (1.5–1.9 s vs 1.9–2.5 s).

**The counter-example worth remembering.** A mesh child's fleet inventory reported that `hetzner` and
`lpt-apps` ran "a green timer over an empty index". Counting the files disproved it: `/root/bin` holds
exactly 8 files and the index holds exactly 8 entries — a correct, tiny index. **A plausible finding
nobody tests is how a false alarm becomes a work item.** The one claim in that report I could check in
one command was wrong; the rest was good, and the correction is in the handoff.
