**W2739 · 2026-10-13 · One line unblocked 35 percent of the CFO backlog that could never have been reached.**

Fixed 2026-10-13, verified against the live loop.

THE BUG. `cfo-scoreboard.py` names a descriptor cluster with a `desc:` prefix when a charge has
no merchant string (`cfo_rules.cluster_key`): `desc:zelle payment from meir`. `cfo-shift.py` then
re-keyed every cluster through its own `merchant_key()` before handing it to the resolver, and that
normaliser strips the colon - `desc:zelle payment from meir` becomes `desc zelle payment from meir`.
`cfo-resolve.py` and `cfo_rules.key_from_cli` both recognise a descriptor cluster by the literal
`desc:` prefix, so a stripped key is no longer a descriptor at all: it is treated as a MERCHANT NAME
and searched for as one. The resolver therefore found no rows and answered
`no live charge in this ledger carries the merchant 'desc zelle payment from meir'` - a sentence
that reads like a data problem and was actually a string-normalisation bug.

THE MEASURED COST. Across the backlog, 136 of 408 clusters (207 transactions, 35%) are `desc:`
keys, and **0 of 17 such clusters in the sampled batch resolved** while 10 of 23 merchant-keyed
clusters did (43%). Every one of the four shifts before the fix retired **0 transactions**; the
fixes plus this change retired **38** in one shift.

THE FIX, one line in `cfo-shift.py::clusters_from_scoreboard`:
 key = _raw if _raw.startswith("desc:") else merchant_key(_raw)
matching what `cfo_rules.key_from_cli` already documented: "anything already shaped like a key
(including the `desc:` prefix) passes through".

THE LESSON. A normaliser applied to a value that is ALREADY a key destroys the key's type tag.
Where one part of a system mint an identifier with a prefix, every other part must treat the
prefix as load-bearing - and the failure mode is not a crash but a plausible-sounding reason
string that sends the reader hunting for missing data that was never missing.
