The machine designated primary was running the PRE-ROUND-1 instructions, this was found by installing the detector rather than by reading the repo, and it is now fixed and verified.

MEASURED, 2026-10-14 ~12:15Z. `scripts/preset-drift.py` existed on **no machine but ZABZ-YOGA**, so it was copied to all four (see below) and run on each. On **ZABZ-TECH** it exited **1 with seven drifts**, of which the load-bearing one was:

 DRIFT zabz/agent.cordis.yml repo=506dc5066592 loaded=7c79b04f237a [56297B vs 58677B]

58,677 bytes is the **pre-round-1** text — the size round 2 itself measured as carrying the `{cwd}` bug and none of the wrong-data rules. **Round 2 reported this fixed and verified at 2026-10-14T01:35Z; by 12:15Z it was wrong again.** Nothing about the content was in dispute: a dry run of the machine's own `scripts/sync.py` said `preset zabz: WOULD UPDATE -> ~ agent.cordis.yml` plus five skills — i.e. the corrected text was already sitting in that machine's own checkout, and nothing had deployed it.

**The fix, and why it was done this way.** `sync.py` has no narrow mode (`--dry-run`, `--hostname`, `--engine-root` only) and it printed a **DANGEROUS STATE** warning — the *running* engine is 0.2.0-rc.2 while configuration names 0.1.5-rc.1 and `$DSH_HOME/profiles` points into an npx cache — so a full sync would also rewrite `profiles/web/cordis.patch.yml` and reinstall client plugins on the owner's primary workstation, where a bad profile patch is a recorded way to stop the engine booting. So the deployment was narrowed to exactly the instruction surface: the `zabz` persona and five skills, copied from that machine's OWN repo to its loaded path, each with a timestamped `.bak`.

**A first attempt was wrong and is worth recording.** The copy was done by reading the file as text, replacing CRLF with LF, and writing it back — and `preset-drift` still reported DRIFT afterwards, because the backtick escapes in the line-ending replacement did not survive the pipe into the remote PowerShell, so the replacement silently became a no-op on the literal string `rn`. **A byte-exact `Copy-Item` is the correct operation**, and it is also the honest one: the loaded surface should equal what the repo says, byte for byte, or the detector cannot say anything.
