**W · prefer-remote is implemented, tested green, and OFF by default — the local node is now excludable when the broker has somewhere else to put the work**

BUILT AND VERIFIED 2026-09-18. This is the fix for the defect behind three dispatches landing on the
owner's laptop while a 32-core desktop sat free (P331), and it exists as a POLICY because no sensor does.

HOW THE PATCH ARRIVED, AND WHY THAT MATTERS: workstream F returned a unified diff, and **the delivered
message was truncated** — 3404 bytes omitted, and the `placement.js` hunk was visibly spliced mid-line
where the omission fell. Applying the printed text would have written a broken file. The full result had
been spilled to disk, so the diff was extracted from the spill file programmatically (`_scratch/extract-patch.cjs`),
which reported 5 blocks / 43,004 bytes, and `git apply --check` then passed on all five files before
anything was written. **Never apply a diff you read out of a chat message; take it from the artefact.**

THE DESIGN, in one paragraph each:
- **A policy, not a sensor — and no sensor was invented.** `agentsRunning` is the ENGINE's census of
 executing loops, so an idle human with two background loops and a busy human with none are the same
 number to it; `plugin-health`'s snapshot has memory counters and a process list and no input-idle time.
 A real signal would be `GetLastInputInfo`, which nothing samples and which would cost a `pwsh` spawn
 (~540-700 ms) on the very path this module exists to keep cheap.
- **It reads the broker's own answer.** `/place` answers with `eligible`, the size of the pool it ranked.
 When the broker named THIS machine from a pool holding another node, the local reservation is released
 UNSPENT (`/done ok:false`, before the second ask, so the lease cannot skew the next ranking) and the ask
 is repeated with the local node excluded.
- **Unreadable means unchanged.** `tier: 'queued'` builds its pool from every placeable node, so its count
 is not an eligible set; a missing count, an unnamed node or an untranslatable hostname are all
 `known: false`. In every one of those cases nothing is re-asked, no lease is released, and the reason
 says so. This module's own rule — a reading that could not be made never changes a decision — has been
 violated four times on this mesh in one day.
- **Default OFF** (`preferRemote: true` in the row, or `MESH_PREFER_REMOTE=1`), logged at boot either way.
 Justification, one sentence: today's defect is that a *default* treated a machine a human is using as an
 ordinary worker, and silently turning that default around on every machine — including the three nodes
 nobody sits at, where it trades a local start-now for a remote queue — without a measurement that the
 trade is net-positive is the same mistake pointing the other way.

PROOF: `npm test` in `packages/plugin-remote-fanout` -> **112 tests, 112 pass, 0 fail**, including the
eight new cases (alternatives present / no alternatives / eligible set unknown / mesh unreachable /
default-off / already-remote / the pure helper / the check line).

AND THE SUITE CAUGHT SOMETHING MY OWN ROSTER CHANGE EXPOSED, which is worth recording because it is the
test doing exactly its job. Adding `lakewooechsmini` to the broker roster made it a v1 node for the first
time, and `nodes.test.mjs` then failed: its dispatcher row in `plugin-remote-fanout/lib/nodes.js` declared
**no credential source**, and a POSIX interpreter row must name one or record that it was checked. I
confirmed the failure predated the patch (it reproduced with the patch stashed) and fixed it by MEASURING
rather than guessing a marker: `/Users/lpt/.dsh/.credentials.yaml` exists (mode 600, 277 B) because that
machine runs its own DSH engine, while `/etc/dsh-worker.env` and `~/.dsh-install/.credentials.yaml` are
both absent. So the row now carries `['!self-store']` and a new `resolveNodeInvocation` branch that says
the node supplies its own credential — a different sentence from "checked and has none", because printing
the wrong sentence about a real, local credential is the kind of quiet wrongness this programme keeps
paying for.

NOT DONE, DELIBERATELY: the policy is **not enabled anywhere**. Turning it on is a deployment decision
that should follow a placement ledger showing what it would have done, and it is a one-line change in the
row (`preferRemote: true`) plus an engine reload.
