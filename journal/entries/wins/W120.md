**W120 · 2026-09-14 · Proved a production write-path fix read-only, by asserting on call shape and on which rule fired.**

2026-09-15. lpt-sync defect A (duplicate customer rows) is a WRITE-path bug and
the mandate forbade any production write, so a naive verification was impossible.
It was still proved, and the shape generalises:

 1. stub the DB layer (a recording website_db whose create_customer issues a NEW
 id on every call -- i.e. it mimics the real blind INSERT for an unmatchable
 phone) and assert on the CALL SHAPE, not on database contents:
 * exactly one id was ever issued by one push,
 * create_order received customer_id == that id,
 * result["customer"]["id"] == the order's customer == that id.
 Six unmatchable-phone shapes parametrised ('482612269', 'unknown', 'PENDING',
 '', None, '123').
 2. for the guard/rule defects, assert on WHICH RULE fired and on the reason
 string naming the live order, then isolate the rule under test by stripping
 the other rule's inputs in memory (a new DB-backed test does this, because
 the pre-existing linked_order refs would otherwise mask the sibling rule).
 3. keep a server-enforced read-only session for the live assertions: production
 opened with options="-c default_transaction_read_only=on", plus a test that
 proves the session REJECTS a write (ReadOnlySqlTransaction on CREATE TEMP
 TABLE) -- read-only by the server, not by convention.
 4. control snapshot of customers/orders/tickets/status_history/customer_notes
 counts AND max ids before and after every dry run: identical, so "nothing
 was written" is a measurement rather than a claim.

What made this work was asserting the INVARIANT (one customer per push; the
reported id is the order's) instead of an outcome that needs production. The
statements "nothing was written" and "the write path does the right thing" were
both measurable without a single row changing.
