Tasks were being marked done on the strength of failure alone

WHAT: measured on secratary 2026-09-15. Task #25106 had FIVE failed work sessions and ZERO
successful ones and was set to status 'done' with a completed_at. It is a real $167.96
PayPal item-not-received dispute (tx 0R263141ND1344239) with a hard deadline of 2026-10-16,
and its own description says it CANNOT be completed autonomously -- step 1 needs per-message
owner approval for a relationship-sensitive vendor email, step 2 is time-gated to 2026-09-18.
Its goal plan had gone to 'failed'. The task was closed anyway. Task #25118 (three failed,
none successful) likewise. An entire recent wave -- tasks 25103-25120 -- is 'done', including
every one whose sessions all failed.

MECHANISM, partly identified: #25118's goal_plans row is status 'completed' with updated_at
matching the task's completed_at to the microsecond, so a goal rollup closed it. #25106's
goal plan was 'failed', so a different path closed that one; the candidates are
lifecycle_sweep's completed-progress phase (tasks whose progress_pct >= 100) and its
stale-task phase. I did not need to pin it, because the fix is at the writer.

WHY IT IS THE WORST CLASS OF BUG HERE: nothing retries a task that is done, and nothing
raises. The session record was honest -- five failures, plainly -- and the task row still said
done, so the lie had simply moved up a level. This is the same defect the 2026-09-14 work
fixed for sessions (_close_unfinished_work_session) and that 53739081 fixed for the
hard-ceiling path.

FIX: `_task_close_would_be_a_lie` in app/database.py, consulted by update_task whenever the
requested status is a completed one. It refuses only when all three hold: no work session is
ACTIVE for the task, at least one recent (24h) session FAILED, and NONE completed. An active
session is the [WORK_DONE] path legitimately closing its own task; a completed session means
real work succeeded. A check that cannot run returns "" and never blocks a close. Committed
e88dccff, 7 tests, deployed 01:06:37.

ALSO DONE: owner queue row #37. The task was closed as done, so the fact that it was waiting
on the owner was invisible -- the vendor email has been drafted and unapproved since
2026-09-14. The queue row carries the question, the recommendation, and the reason it arrived
late.
