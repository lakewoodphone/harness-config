**W50 · 2026-09-14 · 2026-09-14 - RETRACTED: 664 failed sessions with done tasks is NOT evidence the work finished.**

**RETRACTED: "664 of 679 failed sessions had already finished their work" — the task-done status is not evidence of success**

**This is the third retraction and the most consequential one, because the claim it withdraws was my
"largest finding of the audit".**

**What I claimed (W48).** Work sessions joined to their task showed 664 `failed` sessions whose task was
`done`, against 15 failed-and-task-open. I concluded the loop "does the work and then records it as a
failure", that the real failure count was ~15 rather than 664, and that the owner's headline goal churn
probably had the same shape.

**Why it is wrong.** I treated `tasks.status = 'done'` as independent corroboration. It is not. There are
**nine** writers of that status, and three of them write it as *housekeeping*:

- `lifecycle_sweep.py:916` — **auto-closes stale tasks** as `done`. Its own log line is *"Auto-closed N
 stale tasks (>D days old: in_progress+open, or expired approvals)"*. That means "we gave up and closed
 it", not "it succeeded".
- `lifecycle_sweep.py:1196`, `workflow_engine.py:879`, `agent_worker.py:1396` — mark the **parent task
 done when a GOAL completes**. A goal is a different unit of work from a work session, so a completed
 goal can mark a task done while that task's session failed.

**The live case that settles it.** Session **75338** ran five steps, executed actions every step
(`system_health`, `list_tasks` — `[ACTIONS: 2 (system_health, list_tasks)]` at step 5), **never called
`update_task`**, and was failed with `[STEP_BUDGET_EXHAUSTED]`. Its task was set to `done` **31 seconds
later**: session updated 16:24:21Z, task updated 16:24:52Z. The task was still open while the session
ran, so

1. `tasks.status='done'` here reflects a later rollup, not the session's work, and
2. my round-7 fix — `_task_is_closed()` evaluated inside the step loop — **could not have fired for
 this case**, because at every step the task was still open.

**What the round-7 change is and is not.** It is not the fix I claimed and it does not address the 664
rows. It is not harmful either: it only completes a session when the *agent itself* closes its task
mid-run, which is a legitimate completion signal. It stays, described honestly, rather than being
reverted to protect a story.

**What is actually established, and it is genuinely useful.** The company keeps **three levels of
accounting that disagree**: `goal_plans` (the unit the churn metric counts), `work_sessions` (what the
loop reports), and `tasks` (what the queue shows). A session can fail while its task is closed by a goal
rollup, and a goal can be marked `failed` while carrying `progress_pct = 100` (W49, which is a separate
and confirmed defect). Nobody has reconciled the three, so **every headline number this system reports
about its own productivity is suspect** — including the 16,796/11,588 churn figure, in whichever
direction it turns out to be wrong.

**The next decisive measurement, stated so it is not re-guessed.** For a sample of failed sessions,
determine *which writer* closed the task and *when* relative to the session's last update, and whether
the mechanism is the goal rollup. That distinguishes "the work succeeded and was scored wrong" from
"the work failed and the task was tidied away", and the two demand opposite fixes. Until that is
measured, the honest statement is that **664 failed sessions sit next to 664 `done` tasks and the
relationship between them is unknown**.

**The pattern, now three retractions deep, stated plainly.** Each time the fix held up and the
*evidence* did not:
1. W46 — searched a log field that never contained the text (an artefact).
2. W48 — read a status as corroboration without asking who wrote it.
3. W49 — the same mistake one round later, in the same shape: the writer of the `100%` was the writer
 of the `failed`.

The rule that would have prevented all three: **before a field is used as evidence for a claim, find the
statement that wrote it and check whether that statement also wrote the claim.** If it did, the field is
the claim restated, and there is no second fact.
