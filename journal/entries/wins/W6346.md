**W — `journal.py check` was re-parsing every entry three times; memoising two pure functions made it 9.8x faster and `status` 51x faster**

Measured 2026-10-12 on ZABZ-YOGA. The owner asked whether the cloud box being an order of magnitude
faster meant something was wrong with the setup, because a journal append had just taken over five
minutes. He was right that something was wrong; the profile found it, and it was not the machine.

`python -m cProfile -s cumtime journal.py check`:

```
cmd_check 48.020 s
 load_entries (3 calls) 37.465 s <- the SAME 3,464 entries parsed three times
 parse_entry (10,392) 32.303 s <- 10,392 parses for 3,464 entries
 norm_body (34,140) 17.608 s <- about ten normalisations per entry
```

**78% of one function, `load_entries`, doing the same work three times.** Not git, not the disk, not
CPU speed, not the network. Two memo caches, and the correctness argument for each matters as much as
the speed:

* **`norm_body` is a pure function of its argument** -- no filesystem, no clock -- so a dict cache can
 never serve a stale value. Safe by construction.
* **`load_entries` is keyed on the TREE'S OWN STATE** (entry count + newest `st_mtime_ns`), not on an
 invalidation call. A write changes the key, so the next read re-parses. There is no "remember to
 clear it" step for a future session to forget, which is the failure mode that makes most caches a
 liability in this estate. A tree that cannot be walked returns a unique key, i.e. **never cache** --
 the fast path must never be the one serving an unverifiable answer. Callers receive deep copies, so
 editing a returned entry cannot corrupt the cache.

**MEASURED AFTER, same tree, same verdict:**

| | before | after |
|---|---|---|
| `check` | 164.7 s | **16.8 s** (12.3 s on a second run) |
| `status` | 46.0 s | **0.9 s** |
| verdict | `0 error(s), 186 warning(s), 83 info` | **identical** |

`py_compile` clean; `show H3565`, `search "mesh broker" --kind pain`, and
`list --kind pain --status open` all return correct content.

**The diagnostic lesson, and it cost three swings.** My first hypothesis was a slow `git fetch` to the
frozen office box: **measured 2.1 s, wrong.** My second was "one `git grep` per git ref, 148 refs,
~103 s of subprocesses": **wrong too** -- my own A/B script looped over all 148 refs while `git_max`
caps its loop at 25, so I was measuring my script, not the tool. Only the profiler found it. The rule
this reinforces (already twice in the journal): **do not theorise about why something is slow -- take
a profile, which names the function and the call count.** And when an A/B shows a number, check what
the code actually does before quoting it.

**What this does NOT fix, and is worth knowing:** this laptop has **148 git refs** (96
`remotes/origin`, 36 local heads, 10 `remotes/offsite`, 6 misc) against the cloud copy's **3**. One
`git grep HEAD` is 2,128 ms here versus 382 ms there -- 5.6x, so the box really is faster, and
`git for-each-ref` is 246 ms against 7 ms. `git_max` greps up to 25 refs on every writer path, so
ref count is a standing tax. Pruning stale remote-tracking refs would cut it, **but that is a
separate change with a real hazard**: id allocation reads remote refs precisely so two machines do
not mint the same number, so pruning can in principle drop an id that exists only on a deleted
branch. Do that as its own measured change, never as a tidy-up.
