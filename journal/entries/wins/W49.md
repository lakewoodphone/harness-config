**W49 · 2026-09-14 · 2026-09-14 - RETRACTED: the failed goals did fail; the writer certified success on failure.**

**RETRACTED: the failed goals did fail. The defect is that the failure handler also certified success.**

**The retraction first, because it is the more valuable half.** In W48 I wrote that the owner's headline
churn — "16,795 failed goals vs 11,563 completed" — probably had the same shape as the work-session
defect, that 16,796 goals carrying `progress_pct = 100` and a `completed_at` were "finished goals
labelled failed", and that the real failure count was probably near zero.

**That is wrong.** I have retracted it in favour of the evidence.

**Why it was wrong, and it is the same trap as every other error this audit.** I read `progress_pct = 100`
and `completed_at` as **independent** corroboration that the work finished. They are not independent:
one statement writes all three fields together. The writer is `agent_worker`, which logs *"Goal %s
failed with %d residual steps; terminalized remaining work"* and then ran:

 UPDATE goal_plans
 SET status = 'failed', progress_pct = 100, completed_at = ?, updated_at = ?
 WHERE id = ?

A field written by the failure handler cannot testify that the work succeeded. The 16,796 goals with
`failed` + 100% + `completed_at` are **16,796 goals that genuinely failed**, and the churn is real.

**The contrast that makes the distinction usable.** In the work-session case the corroboration was
genuine, because `tasks.status = 'done'` is set by a *different* actor — `update_task`, invoked by the
action the agent chose to run — while the session status was set by the loop. Two writers, so two
independent facts, so "664 of 679 failed sessions had finished their work" stands. Here one writer set
every field, so there was never a second fact. **Before treating a field as corroboration, find out who
wrote it; if it shares a statement with the claim, it is the claim restated.**

**Why the contradictory row still had to be fixed.** A row that says *failed* and *100% complete* and
*completed at a timestamp* does not merely look untidy: it fabricated a confident wrong conclusion in
its reader, and the reader was me, one round after I had written a rule about exactly this. That is what
a self-contradictory record does, and it is worth more than the field's tidiness.

**The fix.** Both writers stop asserting 100% on failure: `agent_worker` (16,796 rows) and
`lifecycle_sweep` (same shape, never fired — zero rows carry its timeout message). `completed_at` is
deliberately **kept** in both, because `autopilot.py` queries `status = 'failed' AND completed_at > ?`,
so in this codebase the field means "terminal at", not "succeeded at". A completion path in the sweep
that legitimately sets `status = 'completed', progress_pct = 100` is untouched.

Deployed at 16:25:00Z; 4 tests pass on the authority's own tree; compile gate green; `/health` 200; the
forced `progress_pct = 100` confirmed gone from the failure paths.

**Still open, and not to be confused with this:** the *volume* of failed goals remains 16,796, and
whether that number is right is a separate question from whether the rows lie. What this fix changes is
that future failures will stop carrying a false completion certificate — so the next measurement of goal
health will be the first one taken on honest rows.
