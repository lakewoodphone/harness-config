**W2827 · 2026-10-14 · The company's budget knob was ONE DB row (.env said 5.0, the effective value was 25.0); raised to 37.5 and verified by the first session running 3 steps where an hour of them had paused at 0.**

The owner authorised raising the company's budget caps with a condition — *"as long as it's productive and not just token and money burn"* — so this is recorded as a bounded experiment with a baseline, a revert command, and a commitment to undo it if the failure rate does not move.

**The knob, and it is exactly one row.** `app/services/llm_budget.py` derives both caps from one daily figure: `dept_pool = daily × 0.8` and `agent_soft_cap = dept_pool / 6 × 2 = daily × 0.2667` (`DEPT_AGENT_COUNT = 6`, `CEO_RESERVE_PCT = 0.20`, `AGENT_SOFT_CAP_MULTIPLIER = 2.0`). `_resolve_budget_limits` reads `.env` first and then **DB overrides**, and the DB won:

 .env LLM_DAILY_BUDGET_USD=5.0 <- overridden, and therefore misleading
 DB row settings_overrides.llm_daily_budget_usd = 25.0 (set 2026-06-15)
 effective daily 25.0 -> dept_pool 20.0000 -> agent_soft_cap 6.6667

Those three derived numbers **match the pause messages to four decimal places** (`dept_pool_exhausted $20.0051/$20.00`, `agent_soft_cap $6.6694/$6.67`), which is what made the diagnosis certain rather than plausible. **`.env` said 5.0 and the effective value was 25.0** — a second instance of this estate's recurring defect: a configuration surface that reads as if it were in force and is not.

**The change.** One row, backed up first:

 sqlite3 -readonly … "SELECT key||char(9)||value_json FROM settings_overrides WHERE key LIKE '%budget%'"
 -> /root/settings-overrides-budget-backup-20261014T133721Z.tsv
 UPDATE settings_overrides SET value_json='37.5' WHERE key='llm_daily_budget_usd' -> 1 row
 verified: daily_limit 37.5000 dept_pool 30.0000 agent_soft_cap 10.0000

So **both caps rose 50 %** (20.00 → 30.00 and 6.6667 → 10.0000) for **+12.5 USD/day of exposure** — less than the ~17 I quoted, because the two are not independently settable and 37.5 is the single number that satisfies both.

**The verification, and it is the strongest kind — a before/after on the same measure.** Every session since 13:05 had been `paused` at `steps_completed = 0` within 0.2 s of starting. The first session after the raise:

 id 78722 status=active steps_completed=3
 "Step 1: I'll start by testing whether HA access is actually restored r…"
 since the raise: 1 session, 0 paused, 1 progressing; 0 BUDGET-PAUSED messages

**No restart was needed** — the limit is read per session (the pause message prints the live spend against it), so the change took effect on the next tick. Revert is one command:

 UPDATE settings_overrides SET value_json='25.0' WHERE key='llm_daily_budget_usd';

**The baseline the experiment is measured against, today to 13:37Z:**

| window | sessions | completed | failed | paused | stalled | budget | deadlock |
|---|---:|---:|---:|---:|---:|---:|---:|
| today, pre-raise | **111** | 36 | 48 | 27 | 13 | 38 | 20 |

**And the commitment the condition demands, stated as the test.** The point of the spend is to answer whether today's eight fixes moved the failure rate off ~64 %. So the measure is the **mix**, not the completion rate: `stalled_repeating` and `STEP_BUDGET_EXHAUSTED` should fall, and the 38 % stall class in particular was the target of the redirect. **If a window of real work shows the mix unchanged, the caps go back to 25.0 and the loop stops being changed.** A completion rate that rises because more sessions run is not evidence of anything, and I will not report it as if it were.
