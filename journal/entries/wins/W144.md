**W-new · 2026-09-15 · The evolution loop can no longer re-offer the same change, nor offer a vendored file.**

| reading | measured before | now |

| unapplied offers on `app/services/activity_sync.py` (7 days) | **18** | none can be added |
| rows behind them, all unapplied | 38 rows, **ONE** description, 38 proposal ids | keyed on the content |

| `node_modules` rows, all time | 19 | no new ones |

The engine mints a **fresh `proposal_id`** every time it re-offers a change it has already offered, and
`log_evolution` recorded each one faithfully. So the kernel's `check_evolution` — which reads exactly
that — has read HIGH for weeks: *"18 duplicate offers on [...] activity_sync.py; 1 target file(s) inside
node_modules"*. That is spend and a loop that never closes (P4), and the vendored target had no filter
at all.

Two guards at the single writer `log_evolution` (`05d46f23`, 6 tests, deployed):
- a target inside `node_modules`/`.venv`/`site-packages`/`__pycache__`/`.next`/`dist`/`build`/`.git` is
 dropped from the list — a mixed offer keeps its real source file, and an offer with nothing left is
 not recorded and says so in the log;
- an identical **unapplied** offer is not recorded twice, keyed on
 `(change_type, files_changed, description)`. An application always inserts, because applying
 something is a fact and not an offer.

The check will keep reading HIGH until the old rows age out of its 7-day window on **2026-09-20** — that
is its deliberate design ("no code change can alter a logged row"), so the verification here is that no
**new** duplicate or vendored row can be written, which the six tests and the four hand-run probes show.
