**W113 · 2026-09-14 · Journal lock detects a dead holder: 600s of blocked writes became 0.02s.**

The journal lock now detects a dead holder instead of waiting out its timeout

MEASURED COST: an append was killed mid-write on 2026-09-14, leaving
`.lock` = "append 8996@zabz-yoga:...". The pid was dead within seconds, but
LOCK_STALE_SEC is 600 -- sized for the slowest possible command -- so every journal
write was refused for ten minutes and a `resolve` had to be retried repeatedly
before it landed.

FIX: acquire_lock already had the pid and host in the lock text, so it now asks
whether the holder is alive instead of inferring from age. `_lock_holder_is_dead`
returns False whenever the answer is unknown (a remote host, an unparseable lock, a
process we cannot inspect), so the age rule still governs those.

VERIFIED, two-arm: a lock naming a dead pid on this host is broken in 0.02s (was
600s); a lock naming a live pid is still refused; a lock naming another host still
falls back to the age rule. On Windows it deliberately does NOT use os.kill(pid, 0)
-- signal 0 is not a liveness probe there and can terminate the target; it uses
OpenProcess instead.
