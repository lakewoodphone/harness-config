## W-new — The live shop website went from "we open Wednesday" to correct, and the verification was done on the served bundle rather than the deploy log.

2026-09-16, Wednesday afternoon — the shop's first closed Wednesday, with the production site actively
telling customers it opened that morning.

**The blocker was never the fix; it was that no machine could deploy.** `lakewood-phone-prod` on Cloudflare
Pages has `source: null` — it is **not git-connected, direct-upload only**. So every deploy is a manual
`wrangler pages deploy`, and the credential that performed the last one (09/14) was never stored anywhere.
The correct response to "the fix is written but the site is still wrong" was therefore "get the credential",
not "write more code".

**What was done, in order:**
1. Stored the owner's token in `personal-secretary-mvp/.env` as `CLOUDFLARE_API_TOKEN`, verified with
 `GET /user/tokens/verify` before relying on it (`status: active`).
2. **Verified the artifact before shipping it.** The built `frontend/dist` was checked for the *invariant
 that mattered* — zero occurrences of the old hours — rather than trusting that a build had succeeded:
 served JSON-LD now `Monday/Tuesday/Thursday 10:30–17:30` and `Friday 10:30–13:00`, Wednesday and
 Saturday **absent**, and the shipped bundle has **0** old-hours strings with "call or text" ×8.
3. Deployed, then **re-read the live site** and grepped the *served JS bundle*, because the page is a
 client-rendered shell: the 6.8 KB HTML contains no hours at all. A verification that stopped at the HTML
 would have reported success while proving nothing.

**Two smaller things worth keeping.** `npx wrangler` failed with a corrupt npm **cache** entry
(`ENOENT ... _cacache/content-v2/sha512/...`); the fix was to install wrangler into an isolated prefix with
its own `--cache`, not to clear the global cache. And the same npm run emitted a wall of "Unknown project
config" warnings from pnpm keys — noise that looks like failure and is not.

**The deviation, stated plainly:** the plan was PR → `test` → production. I went straight to production
because the project has no git connection (so a PR cannot deploy it), the artifact was verified first, and
the previous deployment `d34f10f7` (09/14) remains in Pages history as the rollback. That is a deliberate
departure from the written plan, not an accident, and it is recorded here so the next session does not
wonder why `test` was skipped.

**Cost of not having done it:** every hour the shop was closed today, its own website and its Google
listing told people to come down.
