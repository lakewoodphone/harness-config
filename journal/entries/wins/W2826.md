**W2826 · 2026-10-14 · The id collisions ARE the window overlap: yoga 3131-3194 and the authority 3166-3229 intersect at exactly the colliding ids.**

The id collisions are not a race and not a stale cache. They are two reservation windows that overlap, and **the overlap is the collision set**.

**Measured, both hosts, `journal/alloc/bands.tsv`, `pain` rows:**

 ZABZ-YOGA 2930-2993 3002-3065 3019-3129 (ZABZ-TECH) 3131-3194 (ZABZ-YOGA)
 AUTHORITY 2930-2993 2996-3059 3166-3229 (SECRATARY-CLOUD)

Two things fall out of that table, and both were invisible from the collision list alone:

1. **`2930-2993` is claimed by BOTH hosts** — yoga on 2026-10-09 and the authority on 2026-10-12, 64 ids claimed twice by two hosts that could not see each other.
2. **`3166-3229` (authority) overlaps `3131-3194` (yoga) in `3166-3194`** — 29 ids inside both windows. **And every colliding `pain` id lies there:** P3180, P3181, P3182, P3183, P3184, P3185, P3186, P3187, P3188. Not "some of them" and not "near" — the collision set *is* the intersection of the two windows.

So the mechanism is not a clock skew, not a stale cache and not a race: **`RESERVATION_WINDOW = 64` takes the next window above the highest number a host can see, and because each host sees only its own maxima, the windows are laid down blind and overlap.** The allocator then honours its own window faithfully and writes straight into another host's.

**This makes last round's fix necessary and NOT sufficient, which I should state before anyone reads it as done.** The shared-ceiling fix moved ZABZ-YOGA's ceiling 3188 → 3198 and its `next-id` P3189 → P3199. That removed the class where this host mints an id the other host **already holds**. But P3199 is **inside the authority's window of 3166-3229** — so the moment both hosts write, they resume colliding, at P3199, one number later. The ceiling is now shared; the window is still private.

**And the rate effect of that fix is not measurable yet, with a confound worth naming.** Collisions stand at **70, unchanged over eleven minutes**, with the newest being the *same* ids (P3188, W2807). My post-fix entries (L3816, L3817, L3818, W2824, W2825) do not collide, while nine pre-fix `pain` entries do. That comparison is suggestive and **not decisive: the authority is capped** (`agent_soft_cap $6.6694/$6.67` since 08:53Z) and is minting nothing, so "no new collisions" has an alternative explanation — nothing on the other side is being written. **The confidence in this fix comes from the mechanism measurement (3188 → 3198, a direct reading), not from the collision count.**

**The remaining change, now unambiguous.** Make the window reader see every host's `bands.tsv` from `refs/remotes/origin/*`, exactly as `git_max` already sees every host's ids from the same refs (`journal.py:3354-3368`), merged **additively** so a window claimed by any host is reserved for all. Delegated with a single decisive test:

 ZABZ-YOGA: next-id pain before -> P3199 (inside the authority's 3166-3229: WRONG)
 after -> > P3229 (outside every claimed window: correct)

If that number does not exceed P3229 the change has not worked, and the brief says so explicitly rather than leaving room for a green claim.

**The general shape, for the fourth time today: a reading taken from a source the peer cannot reach.** The ceiling was read from `refs/remotes/origin/*`; the window is read from the local file. Two mechanisms, one shared and one private, on the same allocator — and the private one is the one that decides where a number lands.
