**W · The responsiveness probe returned a NULL result, and the null is the finding: the noise exceeds the effect, so "lagging" is still unquantified**

MEASURED 2026-09-18 by workstream R. Full tables in `docs/mesh/113-laptop-under-fleet.md`.

WHAT WAS BUILT: the same four conditions (A baseline, B 3 children on the desktop, C 3 on the laptop, A2
baseline again), 90 ticks each, with the cost of a fixed pinned native operation timed every tick —
`Measure-Command { cmd.exe /c exit }`. The probe's own baseline cost is p50 28.1 ms / p95 49.0 ms, present
identically in all four conditions.

THE RESULT, AND WHY IT IS "NOT DISTINGUISHED" RATHER THAN "NO EFFECT":
- A→C: p50 28.1 → 25.7 ms, i.e. **2.4 ms FASTER**.
- A→B: the same 2.4 ms faster.
- **A→A2: −3.9 ms, LARGER than either effect.** The laptop also drifted within A alone (p50 25.2 ms over
 ticks 1-30, 31.5 ms over ticks 61-90) while A2 was flat.
**The baseline drift is bigger than the thing being looked for.** A single baseline cannot carry this, and
the A2 control is the reason that is known rather than suspected.

WHAT IT DOES SHOW: the memory result **reproduces exactly** — C is +1.05 GiB commit and +25.2 processes
against earlier +1.081 GiB / +25.9 — and C's process delta is precisely 3 children, so no foreign fleet
contaminated the windows. Placement was confirmed from the children's own hostnames, all six alive through
window end, and cleanup verified on both machines.

WHAT IT DOES NOT SHOW, and this is the sentence that matters: the load was three **memory-resident,
sleeping** children on a 31.6 GiB machine with 15.2 GiB free. **A null result at N=3 says nothing about
N=30, and nothing at all about a CPU-active load** — which is the case that would actually cause lag. So the
owner's word *"lagging"* **remains unquantified**, and the next probe must either raise N or make the
children work rather than sleep. Reporting this as "the fleet does not slow the laptop" would be a
measurement of the wrong quantity presented as the answer, which is the error this programme has spent the
day correcting.

CONSEQUENCE FOR `prefer-remote`, stated precisely because the distinction is load-bearing: it is justified
on **memory and process count**, which are measured and reproduced — about 1.05 GiB and 25 processes
returned to the machine the owner uses, whenever an eligible alternative exists — and **not** on a measured
speed improvement, which this work does not show. Enabling it on that basis is honest; enabling it as
"this will make DSH feel fast" would not be.

AN INSTRUMENT DEFECT WORTH MORE THAN THE NULL RESULT, because it is a pure instance of the day's recurring
error: driven from Windows PowerShell **5.1**, the load generator declared
`COULD NOT ASK: ssh laptop-ts hostname` with an **empty exit code** on a **healthy** ssh — 5.1 returns an
empty `Process.ExitCode` for `Start-Process -PassThru` with redirected output, while PS 7 returns 0. A
blank was read as a fact about the far end when it was a property of the near end. **The instrument must be
driven from PS 7**, and that belongs in its header rather than in a report.
