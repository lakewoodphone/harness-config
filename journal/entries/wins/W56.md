**W56 · 2026-09-14 · 2026-09-14 - owner-queue.py could not be written under load (4/5 failures, now 0/5) and is tracked in no repo.**

**The owner-queue CLI could not be written to under load, and the owner-reachability tool is in no repo**

**The defect, and it is a familiar one.** `~/bin/owner-queue.py` — the only way to read from and write
to the owner decision queue — does a `SELECT` then an `UPDATE` in one transaction, in both `_close` and
`cmd_answer`:

 row = con.execute("SELECT id, status FROM owner_decision_queue WHERE id=?", (a.id,)).fetchone()
 con.execute("UPDATE owner_decision_queue SET status=?, ... WHERE id=?", ...)

Python's sqlite3 opens a **deferred** transaction on the SELECT, so the UPDATE has to upgrade a read
transaction to a write one; if any other connection committed in between — and the API writes to this
database continuously — SQLite returns `SQLITE_BUSY` **immediately**. The connection's `timeout=20` cannot
help, because waiting cannot make a stale snapshot current. Measured 2026-09-14: `resolve` failed **four
times in a row** with `database is locked` before succeeding inside a retry loop I had written by hand.

This is the same defect, with the same one-line fix, already diagnosed in
`app/services/dsh_session_ingest.py`: **close the read snapshot with `con.commit()` before writing.** Fixed
in both sites. Verified: **0 of 5 failures after, 4 of 5 before**, no retry loop.

**Second finding, and it is P47 again.** `~/bin/owner-queue.py` is **tracked in no repository** — not in
`harness-config`, not in `personal-secretary-mvp`. The mechanism that is the single source of truth for
reaching the owner, and the only writer of his decision queue, exists on one disk with no version control
and no review path. Its location (`~/bin/` on the authority) is deliberate per the standing brief; its
being untracked is not. Left as found and named here, because moving it into `harness-config` would create
the second drifting copy that `docs/badge/README.md` already warns about — the right fix is to make
`harness-config` the source of truth and have the authority's copy installed from it, which is a deploy
decision rather than a copy.

**And a mistake I made while verifying.** I tested the fix by looping `resolve 19` five times, which
**overwrote the `resolution` text of the owner's decision row** with "re-verified after the snapshot fix
(5/5)". His decision survives in `answer` and in **D85**, so nothing was lost, and I have restored the
resolution text to the correct content. The rule it earns: **never use a live record as a test fixture** —
a test that writes to production data can pass perfectly and leave the record wrong anyway. That is the
seventh instance this session of a sound change with a verification that damaged or could not see
something.
