**W2756 · 2026-10-13 · The owner-question mirror was reading the frozen box; fixed and verified against the authority.**

FOUND AND FIXED 2026-10-13, in the same session that measured it.

`journal/tools/journal.py` -> `_queue_from_authority()` hardcoded its ssh fallback to the OFFICE
box `secratary-ts`. That box was the authority until 2026-10-11T05:43:36Z and has been FROZEN
since; the authority is `secratary-cloud`. So every machine except the authority itself read the
owner's live question queue from a server that stopped at the cutover -- and reported it as
current, because the call succeeded.

MEASURED, same command, same minute:

 before: journal.py questions -> 143 open, 307 closed
 after: journal.py questions -> 162 open, 326 closed
 truth: /root/authority.db -> 162 pending; 218 resolved + 71 dismissed + 37 answered

19 rows were invisible and 11 rows shown as "waiting on him" were already answered -- so an agent
on any machine could have re-asked the owner a question he had closed. That is the memory spec's
"never re-ask an answered question" gap, live, on every machine but one.

THE FIX: try `secratary-cloud` first, keep the frozen box LAST so a machine that can only reach it
degrades instead of losing the queue, and say in the docstring that a reading from the frozen box
is a reading from a stopped server.

THE GENERALISABLE RULE: a hardcoded fallback host is a time bomb keyed to a migration. When a
service moves, every script that reaches it by name keeps WORKING -- against the old copy -- and
nothing fails loudly. `secratary` is a prefix of `secratary-cloud`, so grep does not catch it
either. When a host moves, grep every script for the old name and check what each one is FOR;
"it still works" is exactly what reading the frozen box looks like.

Second instance of the same shape found in the same hour: `sessions.mjs`'s DEFAULT_NODES maps
`secratary` -> `secratary-ts` and has no `secratary-cloud` at all, so every session read on the
estate is pointed at the stopped box. Not yet fixed.
