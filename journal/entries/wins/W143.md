**W143 · 2026-09-15 · Diagnosing a browser-side failure from the machine: headless screenshot, LevelDB evidence, window titles, cmdline window roots.**

WHAT WORKS AND IS WORTH REUSING: a browser-side failure can be diagnosed and *proved* from the machine
without touching the owner's desktop, with four instruments that all worked here:

1. `msedge.exe --headless=new --user-data-dir=<scratch> --window-size=900,600
 --virtual-time-budget=4000 --screenshot=<png> <url>` -> a PNG of what the page actually renders.
 Reproduced the 401 page on a fresh profile in one command; `--dump-dom` produces NO output on Edge
 152 (both old and new headless), and a URL that 303-redirects makes headless exit without writing a
 screenshot -- so screenshot + `--virtual-time-budget` is the form that works, and only for pages that
 settle.
2. A scratch profile's `Default\Local Storage\leveldb\*.ldb` is plaintext: grepping it for
 `dsh.sessions.current` proves whether the app booted at all (the 401 page writes nothing) and which
 session it selected. That is how "the tokenized URL keeps the same session" was measured
 (`session-ea10e311` twice).
3. `EnumWindows` + `GetWindowThreadProcessId` (P/Invoke) lists every visible window with its title and
 rectangle. A DSH window on the auth page is titled "dsh web authentication required - DeepSeek
 Harness", which makes the broken window identifiable at a glance -- this is the only machine-visible
 signal for that failure.
4. Command-line matching on `msedge.exe` (`--user-data-dir=<profile>` + `--app=` + not `--type=`) counts
 the real window ROOTS per profile, which is how "one window, not two" was checked.

ALSO: a cookie jar cannot be read while its browser runs (Edge holds `Network\Cookies` with no share),
so any profile-level cookie check must happen with that profile closed. And on this machine Edge/Chrome
silently no-op some headless invocations while other instances are running -- treat "exit 0, no output,
no artifact" as "did not run", never as "clean result".
