## THE THREE, EACH WITH ITS EVIDENCE

**(1) The post-payment 404.** The Stripe Payment Link's `after_completion` pointed at
`/payment-success`, a route `frontend/src` has never contained. Verified against Stripe's own record
of the link he paid, and fixed to return to the shop's pay page with a marker the page renders.
**Proven on test by reading the return URL back out of a NEW link the deployed code created:**
`https://test.lakewoodphoneandtech.com/pay/<uuid>?payment=success`.

**(2) No sales tax.** The house rule is pre-tax with tax on top (his own words, quoted in
`staff-order.pricing.ts`). It was implemented almost nowhere: `work-order.service.ts` stored a price
tax-free, `lpt-write total set` wrote a bare number with no tax in the file at all, and nothing
downstream added it — the paid order's own Stripe line item read `unit_amount 200, amount_tax 0`.
**Proven end to end on the deployed test code against the deployed database:** price 2.00 before tax
→ stored total **2.13**, notice `Balance due: $2.13 / (Subtotal $2.00 + tax $0.13` and
`Zelle $2.13`, page amount 2.13. The helper's arithmetic was cross-checked against the app's engine
first (139.74 → 9.26 → 149.00 is order 3020's real numbers).

**(3) "Nothing owed" on a real balance.** A finite `summary.total` of 0 overruled the order's own
total, so `due` became 0. **102 of the 170 priced orders on the live database read that way.** Fixed
narrowly — a zero from the engine no longer wins, a real price still does. My first attempt was wrong
and the shop's own tests caught it.
