**W2743 · 2026-10-13 · The duplicate graph was wrong in BOTH directions, and the worse half was the hidden transactions.**

Found and fixed 2026-10-13 by censusing the whole ledger instead of the one account a worker flagged.

THE CENSUS, same account + same date + same |amount| across all 8,769 rows:
 collision groups 1,982
 NONE marked duplicate 693 <- rows counted twice
 exactly one marked 1,080 <- correct
 ALL rows marked 209 <- the transaction is INVISIBLE

I had gone looking for the first defect only. The worker's report named it: `lpt-chase-5578`
double-counts itself from two sources. Inside that account alone the split was 12 groups with
neither side marked and 3 with BOTH marked - so the same rule that fails to mark a duplicate also
over-marks a survivor elsewhere. The second defect is the more serious one: a group where every row
is marked duplicate has no surviving member, so a real transaction sits in the ledger and counts
for nothing.

FIXED, in three passes, each with a backup and a measured before/after.
1. `lpt-chase-5578`: 12 double-counts resolved, 3 fully-excluded groups given a survivor back.
 All 91 of its collision groups now hold exactly one survivor.
2. Cross-source duplicates ledger-wide: 95 groups considered, **84 resolved**, and **13 deliberately
 LEFT ALONE because the two sides have different directions** - a charge and its refund on the
 same day for the same amount are not duplicates, and marking one would have destroyed a real
 refund. The resolver uses a source precedence (plaid-api and stripe-charges first; Heuristic CSV
 Profile last) so the live feed always wins over an import.
3. Orphaned groups: **97 groups where every row was marked duplicate**, each given back its most
 authoritative member. Also checked that 0 rows point at a duplicate target that no longer exists.

MEASURED EFFECT, start to finish:
 non_duplicate 6,263 -> 6,279 (more real rows in the books)
 unexplained 556 -> 597 (the restored rows are genuinely uncategorised)
 pct_clear 91.12 -> 90.49 (the rate FELL)

The falling rate is the correct outcome and worth stating plainly: 97 transactions that were being
hidden are now visible and need classifying. A clear rate computed over a population that excludes
real transactions is not a better number, it is a smaller one. The CFO loop will work the 41 new
rows off on its own clock.

WHAT IS STILL OPEN, measured, so nobody re-derives it: 611 collision groups remain with NEITHER side
marked. They are SAME-SOURCE (same day, same amount, same importer), where two identical genuine
charges cannot be told apart from one duplicated row by shape alone - 598 of the original 693 were
same-source. Resolving those needs a non-shape signal (a receipt, an order id, the other leg of a
transfer), not a broader version of this rule.
