**The shape, stated once so it is recognisable next time:** a write attempted on a connection that has
already read. SQLite in WAL mode refuses to upgrade a read transaction (`SQLITE_BUSY_SNAPSHOT`), and the
busy handler does **not** cover that condition - so no `busy_timeout` value can fix it, which is exactly
why my first attempt (a 10 s timeout) changed nothing. The fixes are: take the lock before the first
read, OR - better - keep the lock window as small as the write itself.

**One of my own tests had gone stale, and the new test caught it.** `test_mashgiach_write_lock.py`
still asserted `lock < first read` - the design I had deliberately replaced one round earlier when
holding the lock across the reads produced 31 lock errors. Two of my tests were contradicting each
other, and the new file surfaced it. The old test is revised, and its docstring now records *why* the
revised invariant is the right one:

 the lock is held when the write happens, and the write is the only thing it covers

**That is worth more than the fix.** A test written against a fix can pin the fix's shape rather than
the property it was protecting, and then block the next correction. When a measurement invalidates
the shape, the test has to move with the reason - not be deleted, and not be left failing.
