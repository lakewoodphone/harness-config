## The 0.1.5 -> 0.1.7-rc.2 upgrade is NOT destructive to stored state, and the logs rollback is a file delete

MEASURED 2026-09-28 (ZABZ-TECH) by reading both installs' code, then verified against the real corpus.
Full audit: `harness-config/dsh-update/STATE-COMPAT.md`.

HEADLINE: the candidate is **LAZY (new sessions only)**. It writes a NEW SIBLING file
`session.v4.jsonl.zstd` next to the v3 log; the v3 original is never opened for write, truncated or
unlinked. Establishing code, `dsh-session-persistence-jsonl@0.1.7-rc.2/lib/index.js`:
`assertGenerationPaths:1895-1902` (source and target are different files),
`writeSyncedTemp:1952` -> `publishPreparedMigration:2077` (writes `session.migration.<token>.tmp` then
publishes to `session.v4.jsonl.zstd`; the only `rm` calls, `:2012`/`:2020`, remove the `.tmp`),
`requireStoredLog:2603-2627` and `prepareStoredMigration:2680-2740` ("decode one historical generation
WITHOUT publishing a successor"). Publication happens only inside `open(..., "write", ...)`, whose one
production caller is `dsh-agent-loop/lib/index.js:1929`. Boot, listing and workspace startup do not
migrate (`dsh-workspace/lib/index.js:893` calls `.list()` only; `dsh/lib/bin.js:100-136` has no
`migrate` subcommand).

CONSEQUENCE, and this is the useful part: **the rollback for logs is deleting the v4 sibling**, because
v3 is intact. Once a v4 file exists the old engine prefers it (`resolveGenerationInDirectory:3185`) and
either silently hides that session or hard-fails with "upgrade the harness" — so a rollback that
leaves v4 files behind looks like data loss while the data is actually all still there.

PER-STORE VERDICTS (all measured against the live home):
 sessions/ ONE-WAY, additive only. 1,256 files, all v3, all decoded.
 storages/session_projcache SAFE -- unit version 7 in both builds; invalidated by a strict identity
 match (`3 !== 4`) and silently rebuilt. Slower first open, no loss.
 storages/workspace.json SAFE -- version 2 both builds; candidate only adds defaulted fields.
 attachments/ SAFE -- same root `~/.dsh/attachments/v1`, sha256 content-addressed,
 append-only; v4 still carries `attachmentId`.
 .credentials.yaml SAFE -- `dsh-credentials*` byte-identical, still accepts version 1, and is
 NOT rewritten on boot.
 profiles/, settings.yaml SAFE -- no version marker read or written; the candidate never even opens
 `<dsh-home>/settings.yaml`.
 .agent-presets/ SAFE and INERT, not deleted -- `.agent-presets` has zero occurrences in any
 candidate `.js`; all 17 files still present.
 health/, spend-guard/, governor/, mesh/, multi-window/, tools/, logs/
 OUT-OF-SCOPE -- zero upstream references; owned by this deployment's own
 plugins and by browser profiles.

CORPUS CHECK, not a sample: all 1,256 logs decoded -- **192,468 frames / 353,230 events / 141,190
message slots** -- with **zero** constructs v4 refuses to migrate and zero messages lacking a valid
`source.kind`.

METHOD TRAP WORTH KEEPING: each log is ~150 SEPARATE zstd frames, one per record, and
`zlib.zstdDecompressSync` (and `createZstdDecompress`) return ONLY FRAME 0. Two independent scans
reported a clean, meaningless `1 record` before this was noticed; an early restore test of mine made
the same mistake and under-claimed. The honest decode is frame-by-frame: split on the zstd magic
`28 B5 2F FD` and decompress each slice. Re-measured that way on the BACKUP: 315 frames, **731 JSON
events, 0 frames undecodable**.

WHAT REMAINS UNCERTAIN (recorded in STATE-COMPAT.md section 4, eight gaps): the codec was not
EXECUTED against a live log, so "every log migrates" is a strong inference from two independent
code-derived properties rather than a run; and the exact RATE of lazy conversion is less certain than
its direction.
