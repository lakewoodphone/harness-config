**W2821 · 2026-10-14 · The serving probe is proven against an accepted connection that never answers - all four paths verified, closing L3814's gap.**

The serving probe now catches the exact failure mode it exists for, proven against a service that accepts the connection and never answers.

**Why this needed its own proof.** `L3814` recorded that the probe was verified on three paths — live `OK` exit 0, dead port `curl rc=7` exit 1, wrong endpoint `http=404` exit 1 — and **not** on the accept-and-hang case, which is the one that matters: `company-api` wedged twice on 2026-10-14 by *listening, accepting, and answering nothing*, so a probe that only catches "nothing is listening" would have caught neither incident. An earlier attempt to test it opportunistically failed because the restarts had cleared the hang I meant to use as the subject. So it was built deliberately.

**The test.** A listener on a spare port that accepts one connection and then sleeps 35 s without writing a byte, self-limiting under `timeout 40` so it cannot outlive the test:

 socket.bind(("127.0.0.1", 8099)); socket.listen(5); c, a = s.accept(); time.sleep(35)

Control, proving the subject really is a hang rather than a closed port:

 curl --max-time 4 http://127.0.0.1:8099/health -> http=000 t=4.002835

The probe against the same subject:

 COMPANY_API_PROBE_URL=http://127.0.0.1:8099/health COMPANY_API_PROBE_TIMEOUT=4 \
 /usr/local/bin/company-api-serving-probe.sh
 -> 2026-10-14T13:08:59Z FAIL company-api did not serve
 http://127.0.0.1:8099/health within 4s: curl rc=28 http=000 elapsed=4.002449s
 exit=1

And the live service in the same breath, so the test cannot pass by failing everything:

 /usr/local/bin/company-api-serving-probe.sh
 -> 2026-10-14T13:09:03Z OK company-api served http://127.0.0.1:8002/health http=200 in 0.006975s
 exit=0

**`rc=28` is curl's operation timeout** — the connection established and the transfer never completed — which is the signature the two real wedges produced. So the instrument distinguishes *serving* from *listening*, and it is now proven on all four paths: healthy, nothing listening, a wrong endpoint, and an accepted connection that never answers.

**What this buys, stated in the terms the two incidents used.** At 12:2xZ the unit was `active`, `NRestarts=0`, listening on 127.0.0.1:8002, its cgroup 80 % unable to run for memory, and answering nothing — and it was found only because the API was wanted for something else. With this probe on a `*/5` schedule and exiting nonzero into `cron-wrap`'s frozen TSV, that state now produces a recorded failure within five minutes instead of an accidental discovery. **Detection only: the probe restarts nothing, deliberately.**

**Still not measured, and worth saying:** no work session has run since the deploys, so the effect of the repetition-guard and timestamp fixes on the company's failure mix **cannot be judged yet**. The measurement to take, once there is a window, is the mix — `stalled_repeating` versus `STEP_BUDGET_EXHAUSTED` — not just the completion rate, because the whole point of the change is that it moves failures from one class to another.
