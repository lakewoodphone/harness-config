## How to get a clean pre-flight verdict: point the gates at a STAGED migrated DSH_HOME

MEASURED 2026-09-28 (ZABZ-TECH). A version-coupled config change cannot be validated against the live
config, because the live config has not been migrated yet -- so every gate correctly reports BREAKS
against it and you cannot tell "the fix is incomplete" from "the fix is not applied yet".

The technique that separates those two, and it is cheap:

1. Build a staged `DSH_HOME` under `%TEMP%` holding the MIGRATED copies: `settings.yaml`,
 `.agent-presets/<name>/**` from `harness-config/presets/`, and the changed
 `profiles/<name>/cordis.patch.yml`. (Copy only named profile dirs -- `~/.dsh/profiles` contains a
 full 187-package engine tree and a recursive copy walks into it.)
2. Run the gates against that home instead of the live one. `lib/consumed.mjs`, `lib/preset-gate.mjs`
 and the `preset-gate` verb all take `--dsh-home`; the CLI verb uses `$env:DSH_HOME` when set.

RESULT for the two 0.1.7 renames, same candidate contract, only the config differing:
```
live config preset-gate -> BREAKS BREAKS=1 RISKY=2 INFO=1
 (the BREAKS named @deepseek-ai/dsh-workflow-worker-thread and its evidence said,
 correctly, "only the INSTALLED copies name it ... a replacement has been written
 down and has not been synced into the live home")
staged migrated preset-gate -> SAFE BREAKS=0 RISKY=0 INFO=0, 6 preset files
 consumed: dsh-workflow-worker-thread not referenced at all;
 dsh-workflow-ptc 6 refs; dsh-agent-preset-registry 3 refs
```
That pair is the proof the rename work is COMPLETE rather than merely started -- and it is the same
discipline as the known-good fixture rule (LESSONS L2373): you need the healthy input to read SAFE,
not just the broken one to read BREAKS.

RESIDUAL, and it is honest rather than a defect: one `unverified` entry remains for
`@deepseek-ai/dsh-agent-presets`, because `profiles/mesh/cordis.patch.yml` still MENTIONS that name in
an explanatory comment. The gate deliberately does not treat a comment as a consumer, so it reports a
gap instead of inventing a BREAKS -- which is the correct behaviour and the opposite of the false
positive this pipeline produced on its first run.

RULE: when config and engine must move together, prove the change on a staged copy, then apply both
in one step. A gate run against the un-migrated live config is not evidence about the migration.
