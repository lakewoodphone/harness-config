**W2605 · 2026-09-30 · The authority disk filled twice in four days with no alarm on its own filesystem; disk-guard is now wired and falsified.**

The authority's own root filesystem had no alarm, it filled twice in four days, and the mechanism that bounds it is checked by nothing.

MEASURED ON `secratary`

 2026-09-27 09:0xZ / at 100%, 17 MB free. Backups stopped producing complete snapshots:
 "there is NO valid backup today" (journal P2553)
 2026-09-30 14:5xZ / at 99%, 7.6 GB free. `secretary-backups` held 298 GB across 21
 directories, and the retention script that bounds it had been DELETED by a
 copy-style deployment whose caller printed
 "WARN: prune-backups.sh missing; skipping pre-backup retention" (P2799)

Not one check on the machine watched its own root filesystem. What existed was
`~/bin/box-health-check.sh`, which runs DAILY and watches a DIFFERENT box (`lpt-apps-01`, the
Hetzner app server). So the disk that actually filled had no reader at all -- and a daily check
would not be fast enough even if it did: one backup directory is ~18 GB, a fifth of the free space
that existed at 15:23Z, with a backup every six hours.

WHY IT MATTERS THAT THIS IS THE SECOND TIME

A full root filesystem on this host does not fail loudly. The company database (14 GB of SQLite) and
the family chat both write there, and the recorded 2026-09-15 incident is the shape of the
consequence: 117 of 140 stored inbound rows unreadable, a month undetected. The first fill produced
"no valid backup"; the second was minutes from the same.

WHAT WAS BUILT, 2026-09-30

`~/bin/disk-guard.py` -- three signals, each chosen because it is a thing that actually went wrong:

1. FREE SPACE on `/` and `/tmp`, sampled every 15 minutes (warn 90%, critical 95%, `/tmp` 80%).
 Fifteen minutes because the growth rate is 18 GB per backup and the threshold is only useful
 above the rate of growth.
2. THE RETENTION SCRIPT EXISTS AND IS EXECUTABLE. This is the specific mechanism whose absence
 caused the last fill, and it is NOT a crontab target -- `backup-data.sh` calls it and degrades
 to a warning when it is gone, so `cron-target-guard.py` cannot see it. Checked here, because the
 file is the difference between 216 GB and 298 GB of backups on a 467 GB volume.
3. WHERE THE SPACE WENT, only when over threshold: `du -sxm` over the eight paths that have actually
 grown (backup root, repo data, quarantine-debris, phoenix-evidence, repos, accounting-data,
 recon-20260915, /tmp), biggest first.

`~/bin/sources/disk-space.py` is the escalation: at or above a threshold it files a wake flag whose
prompt carries the measured numbers, the F7 retention policy IN FULL, the three safe reclaims, and
one absolute rule -- never delete a backup directory beyond the policy without the owner saying so
in the conversation, because that is the one loss here that is irreversible.

WIRED

 */15 * * * * /home/zabz/bin/disk-guard.py --write-status >> ~/.disk-guard/guard.log 2>&1
 sources loop: cron-targets disk-space

PROVEN, BOTH WAYS

- `disk-guard.py --selftest` -> `SELFTEST OK (/ at 76.5%, retention script exists=True)`.
- Live -> `ok - / at 76.5% (91908.2 MB free), /tmp at 48.5%, 15 backup dir(s)`, exit 0.
- Threshold forced below current usage -> full alarm block with the eight consumers, exit 1.
- Retention script hidden -> `ok: False | findings: ['RETENTION SCRIPT MISSING: ...']`.
- The source is `quiet` on a healthy disk and prints `flagged disk-space:75` when the threshold is
 forced; the full sources loop still exits 0 with the new source in the list.

ONE BUG FOUND IN MY OWN FIRST VERSION, AND KEPT IN THE RECORD

The first build reported `backup_root` with `statvfs()`. The backup root is on the SAME filesystem
as `/`, so the reading said "backups: 365680 MB" next to "biggest consumers: 220534 MB" for the same
path -- a reading that cannot distinguish two states, which is the exact defect this journal keeps
recording. Replaced with `du -sxm` over the directory. Caught before wiring because the falsification
printed both numbers side by side.

WHAT IS STILL OPEN

The root cause of the growth is not fixed: 216 GB of backups is bounded by a policy, not by a
well-behaved producer, and `quarantine-debris` (27 GB), the twenty-plus registered worktrees
(~40 GB) and `recon-20260915` (5.2 GB) are all still there. The guard makes the next fill visible
and actionable; it does not make the disk smaller.
