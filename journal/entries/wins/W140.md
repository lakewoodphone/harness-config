**W140 · 2026-09-15 · Phantom work generation stopped, verified in the data: 25 tasks/day about two subsystems that do not exist went to 0.**

**What was happening.** The company generated **~25 tasks/day** about two subsystems that do not exist —
`boa_sync` and `spending_report` — 1,820 task rows in total, of which 1,816 were marked done. LLM agents
(`dept_evolution_reliability` 26, `orchestrator` 23, `cross_domain_synthesizer` 14 in three days) were told
to investigate them by a prompt block that treats `consecutive_failures >= 3` as live work.

**The mechanism, measured.** No task creator made them. `data/autopilot_state.json` held **frozen** failure
entries: `boa_sync` at **114 consecutive failures** (last attempt 2026-07-21) and `spending_report` at
**38**. Both subsystems are switched off in `.env` (`BOA_SYNC_ENABLED=false`, `CHASE_SYNC_ENABLED=false`,
`AMEX_SYNC_ENABLED=false`, `BALANCE_CAPTURE_ENABLED=false`), `select count(*) from sqlite_master where
name like '%boa%'` returns **0**, and the spending-report script does not exist. **A disabled subsystem
never runs again, so the counter could never clear** — and every reader treats the counter as live.

**Fix (W4, `79fe326d`, integrated by the manager).** Evidence-based presence probes; retirement to
`disabled_superseded`, which is a status the consumer already skips; and — the part that stops recurrence —
`_record_subsystem` now **refuses to record a failure for a subsystem that is not installed on the host**.

**VERIFIED EFFECT, not a passing test.** After integration and restart:
- `data/autopilot_state.json`: 37 entries, **0 with `consecutive_failures >= 3`** (was 2). All three
 phantom entries `disabled_superseded`.
- Phantom tasks created since the fix landed: **0**.
- The hourly histogram of phantom-task creation runs 2026-09-13 → **2026-09-15T19 (2 tasks)** and then
 **stops**: the 20:00 hour is absent.
- W4's own tests on the **live tree** with the repo venv: **20 passed in 1.35s** (run by me).

**The gap I caught before believing it — and this is the transferable part.** The code logged
`retired 'boa_sync'`, `retired 'balance_capture'`, `retired 'spending_report'` on startup, and the tests
passed — so it read as done. But the state file's mtime was still from **before** the restart and it still
said `failed / 114`. The retirement had happened **in memory only**: it is wired *"before every state save"*
and no save followed, while `autopilot_interval_sec` defaults to **3600 s**. The consumer reads the **file**,
so the phantom generation would have continued for up to an hour **while the log said retired**. I applied
the three retirements the code itself had already decided, in its own shape, with a backup and a guard that
refuses to write a truncated state file. **The log said retired, the file disagreed, the file was right.**

**And it is a RECURRENCE, which is the structural lesson.** The consumer's own comment at
`app/assistant_chat.py:2294-2305` explains that stale failure entries for `amazon_sync` and `ebay_sync`
**already** caused phantom tasks once before, and were "fixed" by skipping the same three statuses. So this
bug was fixed for two subsystems and these two were missed. The previous fix treated the **symptom** (skip
these statuses); W4's record-time refusal treats the **source** (a counter that cannot clear for something
that cannot run). When you fix a data-shaped bug by teaching a reader to ignore a status, ask what writes
that status — and whether it can still write it for a thing that does not exist.
