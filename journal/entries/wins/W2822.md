**W2822 · 2026-10-14 · The repetition guard's state is now per-session, deployed and verified - and my own del bug was caught by the identical-to-base failure count.**

The repetition guard's state now belongs to one session, which removes the containment hole the build child pinned — and getting there caught a bug in my own patch.

**The hole.** The guard accumulated `_last_work_output`, `_repeat_count` and `_repeat_redirect_session` on `self` and never cleared them when a session changed, while `_process_work_queue` **resumes** an active session on every loop pass. So the state had to survive across passes within a session *and* clear when the session changed — a blanket reset would have destroyed the guard's memory mid-session, and no reset at all let a new session inherit a spent counter. A session inheriting `_repeat_count >= 4` plus a stale redirect flag could **never** close on repetition, falling back to budget exhaustion (the 20-step / 60-turn caps).

**The fix keys the state to the session id**, placed exactly where the guard reads it: if `_guard_session_id != session_id`, clear the three attributes and record the new id. `session_id` was confirmed in scope at that anchor before the edit.

**Then the `del`, which is the instructive part.** The first version set `_last_work_output = None` and then `del`-ed it. The suite returned **`14 failed, 5 passed` — identical to the base**, which is exactly what a broken change looks like. The cause was mine: the guard's very next line is `and self._last_work_output`, so deleting the attribute raised `AttributeError`. Setting it to `None` is sufficient *and* correct — the attribute must exist, and `None` makes the first step of a new session uncountable as a repeat, which is the desired semantics.

**And one earlier reading of mine was wrong in an instructive way too.** The first run of the suite against the changed file also failed 14/5, and I attributed that to my `del`. It was two causes at once: the `del` **and** a harness gap. The child's `_FakeSession` sets the guard's state directly but never declared which session that state belonged to, so the reset fired on the first call and wiped the fixture. The production loop always knows its session id; the harness had to say so. Adding `self._guard_session_id = session_id` where the harness prepares that state is a **contract update, not a test weakening** — its assertions are untouched.
