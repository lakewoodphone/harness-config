THE TEST. `sms-inbox.py sync --all`, which its own docstring calls "FULL history, every page Twilio
has", run against the live line with a copy of the store taken first:
 inbound: 412 from Twilio, 0 new

 true range 2025-09-02T06:19:25+00:00 .. 2026-10-13T05:00:17+00:00
**Zero new.** A complete walk of everything Twilio holds adds nothing, so the store is not missing a
message. That is the whole of "full history synced", measured rather than asserted.

AND THE ORDERING DEFECT, IN THE TOOL'S OWN WORDS. The same run prints:
 (ORDER BY date_sent would claim 2026-09-18T02:36:58+00:00 .. Wed, 30 Sep 2026 16:44:20 +0000)
against a true range beginning 2025-09-02. So ordering the thread by the RAW `date_sent` column gets
the bounds wrong by a year - which is precisely the complaint the owner made: "I want you to read the
threads from Twilio back and forth and you'll see that it needs to be ordered". The cause is that
`date_sent` is text in more than one format. The fix is the canonical `date_sent_utc`, and it is present
on all 12,319 rows with none missing. The thread is ordered by that column; ordering by the old one is
now visibly wrong rather than quietly wrong.

A CHASE THAT WENT NOWHERE, recorded so the next reader does not repeat it. The store has almost nothing
before 2026-02 (2025-09: 5, 2025-10: 12, then NOTHING for November, December and January, then 2026-02:
481 and 2026-05: 9,046). That looks like a three-month hole in a shop that texts constantly, and I
treated it as one. The full walk disposes of it: if Twilio held those messages, `--all` would have
brought them, and it brought zero. So the gap is either Twilio's own retention or the line simply not
being in service on this number yet - NOT a defect in the sync. The honest statement is "the store holds
everything Twilio has", not "the store holds the shop's whole history".

ONE ANOMALY LOOKED LIKE AN ORDERING BUG AND IS NOT. `reply_sid` is populated on ONE row of 12,319, and
that row is a reply whose own timestamp (2026-09-08) is ten days EARLIER than the message it points at
(2026-09-18). Reading both bodies settles it: the inbound asks about a car that will not start and the
outbound answers about a battery, so the LINK is right and the shop answered ten days late. Not a
mis-ordering; a late reply, correctly linked. `reply_sid` being nearly empty is worth knowing though -
thread structure rests on timestamps, not on reply linkage.

CLAUSE 6, THEREFORE: full history synced (a complete walk adds nothing) and correctly ordered (on a
canonical timestamp present on every row, with the raw column's failure documented by the tool itself).
