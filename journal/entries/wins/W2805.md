**W2805 · 2026-10-08 · WhatsApp recovery landed on the customer's phone: merge the rows into an app-created store, never replace the file.**

Sara Kramer's WhatsApp Business history — 17,662 recovered messages plus her contacts, calls and the
whole media set — is LIVE inside WhatsApp Business on her new iPhone 16 (iOS 27), verified off the
device: store 21,716,992 bytes, Z_UUID the app's own, integrity ok, 782 chats, 19,167 messages,
17,057 media rows, newest message minutes old, 16,857 media files present.

**How it landed, and this is the transferable part: NOT by replacing the store.**
A whole-file graft of her ChatStorage.sqlite was accepted by WhatsApp Business build 1082919065 (on
the iPhone 11) and REFUSED by build 1086504165 (the iPhone 16, iOS 27) with "couldn't update - check
for updates in the App Store"; Core Data's `lost_and_found` table in the app's copy was the tell. The
store was byte-identical in metadata (same model 2.12.14, same hashes) and schema (74/74 tables, zero
column differences) to one the app writes, and the App Store offered no update. So the refusal is the
app's conversion step, on that build, for a store it did not create.

The route that works, and it is reusable: let the app create its OWN store (clean install + register),
then write the customer's rows into it — primary keys remapped, every foreign key rewritten, chats
RECONCILED onto the app's own chat rows by JID rather than appended. Built as
`lpt-hub/scripts/ios-whatsapp/merge-whatsapp-stores.py`; her 17,662 messages went in beside the app's
own 1,510, and Z_METADATA was never touched.

EVIDENCE: case file + run log in lpt-hub (commits 7d2831ed6, 12399e1fa); device verification backup
`~/ios-backups/kramer-final` on the shop Mac.
