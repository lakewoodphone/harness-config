**W2805 · 2026-10-14 · W — A production change proved in a throwaway container on the production host, before deploy.**

**What worked, measured, 2026-10-14 — and worth reusing rather than reinventing.**

**Prove a production change in a throwaway container ON the production host, before the production
service sees it.** For the DoH filter the rig was one `docker run --rm` of the same
`python:3.13-alpine` image the service uses, running the candidate file from a bind mount on a spare
port, with the upstream pointed at `192.0.2.1` (TEST-NET-1 — a guaranteed black hole) or at
`1.1.1.1`, and a tiny 30-line DoH client posting queries at it:

| Case | Upstreams | `waze.com` |
|---|---|---|
| the code that was live | one, black-holed | **SERVFAIL** |
| the candidate | dead + `1.1.1.1` | **NOERROR, 1 answer** |
| the candidate | `1.1.1.1` + dead | **NOERROR, 1 answer** |

and in all three, `ads.waze.com` stayed NXDOMAIN and `www.icloud.com` stayed default-blocked, which
is what proves the **filtering** was untouched rather than merely the resolver being fixed.

Why this is the shape to keep: the defect (a lost UDP datagram becoming a device-wide name-resolution
failure) cannot be reproduced on demand in production, and the change could not be justified by
reading code alone. `192.0.2.1` makes the failure deterministic; the spare port makes it harmless;
the same image makes the environment honest. **No production traffic was harmed, nothing was
deployed on trust, and the before/after is a measurement rather than an argument.**

Same pattern, cheaper: the live **public** endpoint was re-queried after the restart
(`waze.com`, `ctilesgcs-am.waze.com`, `rt-xlb-am.waze.com`, `search.waze.com` → NOERROR;
`ads.waze.com`, `www.icloud.com` → NXDOMAIN; `/health` → ok), and the file was hashed **inside the
container** to prove the running file is the file that was installed. "The deploy succeeded" is not
evidence; the container's own hash and the container's own answers are.
