**W2773 · 2026-10-13 · Two item stores: 55 of the 95 unitemised purchases are itemised one table away.**

2026-10-13. There are TWO item stores for the same Amazon orders. The marketplace store says 95
purchases are unitemised; 55 of them are itemised in the other one.

HOW I GOT THERE. L3679 concluded that 95 unitemised purchases were Amazon's own layout change and that
itemising them needed an order export. Both halves of that were right and the conclusion was incomplete,
because the export had ALREADY BEEN DONE: `scripts/finance/account-scrapers/` is a toolset that "logs
into the business and personal Amazon accounts plus the eBay account, and pulls item-level purchase
history as JSON", its README says all three accounts scrape successfully as of 2026-09-10, and its
OUTPUT is sitting on this laptop at
`C:\Users\ezabz\code\personal-secretary-mvp\scripts\finance\account-scrapers\out\` -
`amazon-personal-2026.json` with 136 orders and `amazon-business-2026-browser.json`, each order carrying
`items[]` with title, asin, price and quantity. It was never brought to the authority.

AND THE LEDGER ALREADY HOLDS IT ANYWAY. Four tables carry a `scraped_at` column:
 amazon_orders 469 rows
 amazon_order_items 768 rows <- item_name, quantity, unit_price, line_total, asin
 ebay_orders 204 rows
 ebay_order_items 193 rows
so the scraped item detail is not a missing file, it is a table nothing reads. Measured against the 95:
 covered by `amazon_order_items` 55
 covered by `ebay_order_items` 0
 still uncovered 40
Sample, order 111-0113128-1745073: 'Superer Charger Fit for Lenovo Laptop, Ideapad 1 3 5' qty None
unit 15.99 asin B08X4M4LBR.

THE REAL CLAUSE 2 PICTURE, then: 585 purchases, and the marketplace store's own 490 itemised rows
UNDERSTATE the truth, because 375 of the 585 have keys in `amazon_order_items` - a table with the same
purpose, populated by a different pipeline, that the marketplace store does not join to. Of the 95 it
calls unitemised, 55 are itemised one table away.

WHY THIS IS WORTH MORE THAN THE 95. The objective says "itemised and matched to card charges". The
matching work this session moved 419 -> 484 by reading ONE store. Anyone measuring itemisation from
`marketplace_orders` alone will keep reporting a gap that is 58 per cent smaller than it looks, and
anyone debugging the item extractor will be debugging a parser whose output for those orders already
exists elsewhere. **Before building a fix for a gap, measure the gap against every store that could
hold the answer, not just the one the report came from.**

WHAT REMAINS GENUINELY MISSING: 40 purchases have items in neither store. For those the mailbox has no
items (the layout change is real) and the scraper has no rows (its 2026 run covered what it covered),
so an Amazon order export is still the only route - which is exactly the fallback ladder the scraper's
own handoff, `docs/finance/account-scrapers-handoff-2026-09-10.md`, already sets out at section 6.
