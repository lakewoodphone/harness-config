**W39 · 2026-09-14 · The retention purge the test caught: an old clock would have deleted a record on arrival.**

The review record had no lifetime at all — `screenshot_retention_days` governs the *picture*, and with its default of zero the picture is never written, so the verdict, the timestamp, the capture score and a site tag sat there attached to a phone indefinitely. COPPA § 312.10 requires a stated period, so the row got one (180 days, `e0ee08b`), purged on the same write path as the image so no scheduler has to be remembered, with per-label counts surviving as the anonymous aggregate that keeps calibration possible.
*The catch:* keying the purge on `ts` — the device-supplied capture time — deleted a row the instant it arrived when the timestamp was old. Found not by reasoning but by two pre-existing tests that use fixed 2026-02-26 timestamps: their rows vanished and the assertions came back empty. The same thing would hit a customer with a wrong clock or a device with a queue of offline uploads. It now keys on `received_ts`.
*Measured:* `tests/test_parent_deletion_and_reason_hygiene.py` 11 passed, `test_screenshot_accountability.py` 10 passed, plus a new `test_compliance_defaults.py` (5) that pins the shipped defaults — escalation off, provider off, images not stored, frames scrubbed, fail-closed — because a default is what an unnoticed change would move.
