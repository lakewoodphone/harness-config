**W2762 · 2026-10-13 · Learned rules had no clock: 55 rows sat unapplied, now applied and automated.**

2026-10-13. The store of learned rules had no clock attached to it, so every rule the CFO learned sat
unapplied until somebody remembered to run it by hand.

THE GAP, measured. `cfo-resolve.py --apply-rules` is the tool that retires everything the stored rules
already cover (`cfo_rules.retire_counts` -> the sanctioned writer, after a VACUUM INTO backup). A grep
of the crontab for it, for `cfo-rules` and for `apply-rules` returned **nothing** - it was not on any
clock. So the pipeline was: the shift learns a rule, appends it to `/root/.cfo/rules.jsonl`, and
nothing ever files the charges that rule was learned for. Measured before I ran it: 55 uncategorised
rows worth 12,290.58 were already covered by stored rules and being counted as unexplained.

RAN IT, and the numbers moved:
 before: unexplained 563 of 6217 pct_clear 90.94
 after: unexplained 547 of 6217 pct_clear 91.20
 rules 49, clusters 13, rows written 17
 backup: /root/.cfo/backups/accounting-20261013T052253Z.db.gz
and 28 further rows were HELD BACK, correctly, by six rules that disagree with rows already in the
book - the tool never overwrites an existing categorisation, it reports the conflict and skips.

PUT IT ON A CLOCK so this cannot rot again: `7,37 * * * * cron-wrap.sh cfo-apply-rules ...` appended
to the crontab (cron-wrap jobs 51 -> 52), backed up first to
`/root/crontab.bak-applyrules-<ts>`. Verified by running it exactly as cron will: exit 0, recorded in
`~/.cron-status/runs.tsv` as `cfo-apply-rules 0 1`, and its own log confirms idempotence -
"rules 49, clusters 0, rows written 0 ... no uncategorised charge is covered by a stored rule that
agrees with the rows already in the book". It takes a backup only when it writes, so the 30-minute
cadence costs nothing on a quiet run. From now on a learned rule takes effect within the half hour.

WHAT IS STILL OPEN, found by the same measurement and worth more than the fix. `retire_counts` over
all 49 rules:
 matched 1,734 rows
 uncategorised 55 <- what a rule would retire
 conflicts 1,160 <- where a rule DISAGREES with a row already in the book
The conflicts are concentrated in broad merchant rules - `stripe` 687, `twilio` 262, `openai` 110 - and
they are mostly benign: a merchant like Stripe legitimately carries several categories (payout
clearing, fees, receipts), a `key_exact` rule can only name one, and those rules retire 0 rows anyway.
But SIX rules are currently holding back 28 real rows, and the tool's own contract is that such a rule
is "a rule to review" rather than something to overwrite. Those six are the next unit: CR-0ee104ca7f81
x9, CR-796bef623a84 x2, CR-8658fabe0567 x3, CR-acf330614982 x7, CR-adce0b3df424 x3, CR-bbd00c23da88 x4.

EARLIER CLAIM CORRECTED. W2760 and W2761 said the remaining backlog was "throughput, not correctness"
and that raising the batch would retire it "with no new rules". That is wrong for the rows that remain:
`uncategorised` is 55 in total across every stored rule, so the rest of the 547 genuinely has no
covering rule and does need work. Raising the batch buys research, and research is the owner's money,
which is why the daily ceiling exists at all.
