**W106 · 2026-09-14 · Six finance status endpoints and auto-categorize were dead on Linux: hardcoded Windows ledger path..**

WHAT: /finance/{boa,chase,amex,paypal,amazon,ebay}/status all answered
{"ok":false,"error":"accounting.db not found"} on secratary. Cause: the ledger
path was hardcoded as "C:/Users/ezabz/accounting-data/live/accounting.db" in
8 places in app/main.py and 1 in app/services/auto_categorize.py. On Linux that
is a relative path that does not exist. Every caller only checked .exists() and
moved on, so nothing ever raised.

FIX: new app/accounting_paths.py — accounting_db_path(), honouring
ACCOUNTING_DB_PATH, defaulting to Path.home()/"accounting-data"/"live"/
"accounting.db". 8 main.py sites + auto_categorize.py repointed. Guard test
tests/test_accounting_db_path.py walks app/ with ast and fails if any code
string literal contains the Windows path. My first version of that test failed
on the module that documents the bug, because it scanned raw text — a guard has
to understand what is code, so it now ignores docstrings.

BEFORE -> AFTER, same endpoints, same minute:
 all six -> {"ok":false,"error":"accounting.db not found"}
 boa -> *7930, 271 tx, latest 2026-08-30
 paypal -> 690 tx, latest 2026-09-09
 amazon -> 236 tx, latest 2026-09-10
 ebay -> LPT eBay Marketplace, 161 tx, latest 2026-08-04, earliest 2021-03-11
Deployed 2026-09-14T22:07:37+00:00, health 200, logged in .runtime/deployed-commits.log.

WHY IT MATTERS BEYOND THE ENDPOINTS: this was a monitor that could not see. Any
kernel or autopilot check reading finance health through those endpoints was
reading a fabrication, and auto-categorisation had never run on the authority.
The ebay figure also dates the real eBay outage: transactions stop at
2026-08-04, which is when the feed died, not when it was noticed.
