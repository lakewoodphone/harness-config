**W3006 · 2026-10-14 · company-api-liveness no longer marks itself failed on a condition - SuccessExitStatus=3, proved with a control.**

FIXED 2026-10-15 ~00:20Z on secratary-cloud. A reader of systemctl --failed would otherwise think the guard is broken.

WHAT WAS WRONG. /usr/local/bin/company-api-liveness.sh follows this estate tri-state exit convention (its own header, lines 99/154/189): exit 0 = healthy or a restart performed; exit 1 = a FAULT in the check itself; exit 3 = a CONDITION (the unit is not active, so systemd owns recovery; OR fewer than FAIL_THRESHOLD bad probes, so nothing is actionable yet; OR a restart was suppressed by cooldown). systemd does not read that convention, so EVERY exit 3 landed as 'Failed with result exit-code' and put the unit into systemctl --failed. Observed 2026-10-14 23:20:10: a SINGLE 1-of-3 probe failure marked the guard failed roughly two minutes BEFORE that same guard correctly detected the wedge and restarted company-api at 23:22:02. A working guard looked like a broken one, and I misread it that way myself at first.

THE CHANGE. New drop-in /etc/systemd/system/company-api-liveness.service.d/10-condition-exit.conf: [Service] SuccessExitStatus=3. Applied only after scripts/mesh/guard-service-state.sh --host secratary-cloud --op restart returned ALLOW (rc=0). Exit 1 is deliberately left a failure.

PROVED WITH A CONTROL, not asserted. My FIRST attempt was invalid: I used systemd-run --collect, which removes the unit before it can be queried, so both arms read inactive and the experiment proved nothing. Redone without --collect:
 systemd-run --wait --unit=prove3-control /bin/sh -c 'exit 3'
 -> Result=exit-code ExecMainStatus=3 is-failed: FAILED
 systemd-run --wait --property=SuccessExitStatus=3 --unit=prove3-test /bin/sh -c 'exit 3'
 -> Result=success ExecMainStatus=0 is-failed: inactive
 systemctl show company-api-liveness.service -p SuccessExitStatus -> SuccessExitStatus=3
 systemctl start company-api-liveness.service -> rc=0, Result=success
 systemctl --failed -> empty
Both transient units were reset; they touched nothing.

NOT YET OBSERVED end-to-end: a real exit-3 from this guard under systemd since the change, because forcing one means breaking the live API. The directive is in effect and its semantics are proved on this systemd; that is the honest state.
