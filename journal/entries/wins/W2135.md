**W2135 · 2026-09-20 · W2145 - weekly_report: 62 lock errors per run to 0, and 31 department scores now actually persist.**

The last unfixed member of the `mashgiach` transaction family, and the one with the largest single
burst.

**Measured.** `weekly_report` produced **62 `database is locked` errors in one minute** (17:44), logged
one per agent:

 WARNING app.services.mashgiach: Mashgiach score failed for reliability_verifier: database is locked
 WARNING app.services.mashgiach: Mashgiach score failed for proposal_evaluator: database is locked
 ... about 31 departments, twice

**Cause.** It opened a connection with **no transaction** and looped over ~31 departments, each
iteration doing FIVE SELECTs then an INSERT:

 for dept_id in _scorecard_agent_ids():
 SELECT ... tasks (x2), activity_log, memories, error_log
 INSERT OR REPLACE INTO mashgiach_dept_scores ...
 conn.commit()

With no explicit transaction, each iteration opened a read snapshot on the SELECTs and the INSERT had to
upgrade it; the autopilot commits continuously, so the upgrade failed - `SQLITE_BUSY_SNAPSHOT`, which
the busy handler does not cover. That is why the errors came in a batch of ~31 rather than singly.

**Fix.** `BEGIN IMMEDIATE` once before the loop, the per-department commit removed, ONE commit
immediately before the close. Identical in kind to the fix that worked for `daily_scan`.

**Two of my own patch bugs were caught by the patch's own checks, before anything was written:**
1. The first version removed the per-department commit and added none, leaving `weekly_report` with
 **zero** commits - so the `BEGIN IMMEDIATE` would have been rolled back by `close()` and every
 department score silently discarded. A bug worse than the one being fixed. The assertion
 `commit_before_close` refused the write.
2. The patch script itself had a stray stub that made it a syntax error - caught by compiling the
 patcher, which is why I compile patch scripts now.

**Verified:** `py_compile` on the authority; behaviourally on a fixture - `ok=True`, **31 departments,
31 score rows PERSISTED** (the property that matters: the commit runs before the close); LIVE 9.8 GB
database - `ok=True`, 31 departments, **0.093 s**; **lock errors 62 before the deploy, 0 after**.
Backup `~/code-backups/20260920T162023Z/mashgiach.py.before-weeklylock` (sha `521ac8dd10634cd4`).

**The mashgiach transaction family is now complete.** Four defects, one function at a time:

| function | defect | fix |
|---|---|---|
| `daily_scan` | per-finding commits -> findings silently lost | batch + one commit |
| `daily_scan` | lock held across four reads -> 62 errors | lock moved to the write |
| `weekly_report` | no transaction -> 62 errors, scores at risk | `BEGIN IMMEDIATE` + one commit |
| `create_proposal` | read-then-write | still open, low frequency |

Three of the four were the SAME defect wearing different clothes: a write attempted on a connection that
had already read. It is worth stating plainly because it took four separate measurements to see it.
