## 2026-10-12 18:05 UTC · ZABZ-YOGA · the mesh parent/child channel WORKS now, measured mid-run - and one thing remains impossible by engine design

**The owner asked for mesh subagents to work "just as well as doing subagents locally" - the parent
speaking to the child, the child to the parent, and failures visible right away. Here is exactly how much
of that is now true, with the evidence.**

**What was broken.** The mailbox thread - the one designed channel for a child to report progress - was
never usable, because **nothing created its directory at dispatch**. A child's report said
`0 message(s)` while its conversation was silently empty, which is the worst possible failure: it looks
like a child that had nothing to say.

**What works now, re-verified independently on real remote nodes.**

| measurement | value |
|---|---|
| thread directory created at dispatch, before the child writes | **`PRESENT 0 message(s)`** at 16:37:51 |
| messages appearing WHILE the child was still running | **2 at 16:38:05, 3 at 16:38:11** (child closed 16:38:16) |
| the parent's final report | `mailbox = 5 message(s)` **plus the full conversation thread** |
| a child told to write nothing | `mailbox = EMPTY - the thread directory exists ... and the child wrote nothing` - **not** `0` |
| a live reader | `bin/mesh-thread.mjs` tails the thread: exit 0 read / 3 ABSENT / 4 READ FAILED |

**Failure visibility, which is the half the owner cared most about.** Before: line 1 was
`MESH-HOST: (not reported)`, the actual reason sat at the bottom, and an unreachable node produced
`mailbox = 0 message(s)` - **indistinguishable from a silent child**. Now line 2 is a headline:
`FAILED - the remote one-shot exited 255 and produced no final message`, and a child that exits 0
without a completion frame gets `FAILED - the remote process exited 0 but printed no completion frame`.
The thread line says `mailbox = UNREADABLE` rather than pretending to be empty. Tests: **179 pass / 5
fail / 24 cancelled, against a 170/5/24 baseline on a clean worktree of the same tree** - the 9 added
tests all pass, and the failing 5 are pre-existing.

**What is still impossible, and it is an engine shape rather than a bug.** **Parent -> child mid-turn.**
A remote child is never a *resident continuable activation*, so while it runs `list_agents` returns
`(no subagents)` and `send_message` refuses. What exists is a **durable one-way file channel plus a
turn-boundary inbox**. Real two-way conversation needs the engine to give remote providers an Activation
ownership contract. **This is now a named, bounded engine change rather than an unexplained absence** -
which is the difference between a finding and a wish.

**Two incidental proofs worth keeping.** (1) The reroute path works for real: this child was refused by
`zabz-tech` as node-specific and **rerouted to `zabz-tech-linux` in 17,843 ms** on a fresh reading, then
succeeded - the retry budget behaving exactly as designed. (2) The child's own message arrived **twice**:
in-band in the conversation thread *and* in its final report, which is what "the child can speak to the
parent" now actually means.

**Evidence:** `docs/mesh/186-MESH-PARENT-CHILD-CHANNEL.md` (334 lines), written on `zabz-tech-linux`
(commit `d5621aa2`), carried to the authority because that node's `main` is 3 ahead and **unpushable**
(a third instance of the same delivery defect this session), committed **`c923075`**, pushed to the vault.
