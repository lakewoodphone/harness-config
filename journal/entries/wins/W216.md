**W · The authority's swap is not a leak and not a process — it is 4 GiB of swapped-out `/tmp`, and the prior note about it was wrong**

SOLVED 2026-09-18 by workstream SW, read-only on `secratary`.

THE PRIOR NOTE SAID the swap is "`/tmp` — a tmpfs". **That is wrong.** `swapon --show` names
`/swap.img`, a **4 GiB regular file on the ext4 root LV** (`/dev/mapper/ubuntu--vg-ubuntu--lv`). `/tmp` *is*
a tmpfs, but a tmpfs cannot be a swap device — the kernel requires a block device or a signature-bearing
regular file. The note named the right directory for the wrong reason, and it had been read as fact.

THE HOLDER IS NOT A PROCESS, WHICH IS THE ACTUAL FINDING. Ranked **by swap** rather than by RSS, the
largest single process owns **14 MiB** (`unattended-upgrades`) and *all* processes together own **63 MiB of
the 4,093 MiB used**. Not a PID-namespace artifact: PID 1 is `systemd --system`, `/.dockerenv` is absent,
`systemd-detect-virt` says `none`, `ps -e` sees 189 processes.

**The swap is swapped-out tmpfs pages.** The arithmetic closes: `/tmp` holds **7.2 G**, only **3.19 GiB**
of shmem is still resident, and **7.2 − 3.19 ≈ 4.0 GiB ≈ the 3.999 GiB used**. cgroup v2 attributes
**3,965,038,592 B to `user-1000.slice`** — user `zabz`, the owner of every large `/tmp` entry — plus
327,708,672 B to `system.slice`.

FULL AND FLAT, NOT LEAKING: `SwapFree` was **980 kB** with **zero movement across ten samples over 90 s**
and `SwapCached` constant. (Marginally better than the 712-716 kB measured earlier — 268 kB was reclaimed.)

AND NOTHING IS FAILING: no `oom-killer` and no swap error anywhere in the 7-day kernel log; both
`secretary-api` and `mesh-broker` are `active`. The `status=9/KILL` lines in the unit logs are external
SIGKILLs — called external only because no `oom-killer` line accompanies them, which is stated as the
distinction it is rather than as an identified killer.

WHAT THE FIX WOULD BE, AND WHY IT IS THE OWNER'S CALL: prune the stale `/tmp` content. Because `/tmp` is
tmpfs, deleting a file whose pages are swapped out **releases those swap slots immediately** — it reclaims
both ~4 GiB of swap *and* RAM, and it attacks the holder rather than the symptom. Measured to make the
decision concrete: `/tmp` has **5,216 entries, 3,751 older than two days, only 551 modified in the last
24 h**; the largest are **3-4 days old with no file inside touched in six hours** —
`/tmp/mob` 204M (Sep 14), `/tmp/comms-test.db` 186M (Sep 14), `/tmp/wt-green` 141M (Sep 15), `/tmp/ins`
139M (Sep 16), plus `/tmp/elantra-wt` 81M and two `hc-*` merge scratch dirs at 120M each.
**But `/tmp/wt-green` and `/tmp/elantra-wt` are git worktrees and `/tmp/comms-test.db` is a database —
deleting them destroys data, and that is not mine to decide.** Secondary and non-destructive: an ~8 G swap
file on `/` (142 G free) buys margin but removes nothing; `swappiness` is already 10 and should be left
alone. A reboot clears both — and loses `/tmp` — which is the zero-effort option and also a change.

THE RULES: a note that names the right place for the wrong reason is still a wrong note, and this one had
been treated as settled; **"swap is full" is a statement about pages, and asking which PROCESS holds them
is the wrong question when the holder is a filesystem**; and a 4 GiB swap that is 100 % full with **no OOM
kill in seven days** is a different severity from the same number with kills, so the number alone was never
the finding.
