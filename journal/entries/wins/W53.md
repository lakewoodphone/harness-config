**#8 concluded: three of the four "sick syncs" need the owner's interactive login, not a code fix — and that is why six tasks were closed without fixing them**

The four finance syncs were investigated as my work (owner question #8, resolved as mis-filed). Each cause
is now measured, and none of them was what the task titles assumed.

| sync | enabled | measured cause |
|---|---|---|
| `boa_sync` | **No** (`BOA_SYNC_ENABLED=false`) | `npm error Missing script: "boa:download"` — downloader exists only in an **untracked** June copy; `_qb_repo()` needs one repo with *both* `boa:download` and `ingest:inbox`, and no checkout has both. Switched off 55 days ago after 114 failures. |
| `amazon_sync` | Yes | **`needs_mfa`** — *"Amazon login requires MFA. Open the Amazon download script manually and complete the verification in the browser window."* |
| `ebay_sync` | Yes | **`Authentication failed`** — expired session. |
| `spending_report` | flag **absent** | `spending_report_enabled` **is not defined in `config.py` and not set in `.env`**, so `getattr(..., False)` is permanently False. It has never run deliberately. |

**The finding that matters.** Amazon and eBay are not broken and not misconfigured — they need a **human
to complete a browser login**, and one of them needs MFA from the owner's own device. No code change,
cooldown, breaker reset or cron wrapper can satisfy that. The breaker cooldown I deployed last round does
its job — both can probe daily again — but they will keep returning `needs_mfa` and `Authentication failed`
until somebody logs in.

**Which is the answer to the question the owner actually asked in question #8.** He wrote that the same
four syncs had at least six tasks created to fix them, "every one marked completed while the failures are
unchanged". Now it is legible why: **the tasks were assigned to agents, but the work requires the owner's
interactive login, so no agent could ever complete them.** An unactionable task cannot be resolved; it can
only be closed. That is the mechanism behind the churn — and it is the same shape as the goal churn
(16,796 failed) and the work-session failures: **work that needs a human gets routed to an agent, fails,
and is tidied away.** The audit's earlier finding that 1,831 tasks closed `done` in nine days while the
named problems persisted is this mechanism seen from the other end.

**Second finding, and it is a defect rather than a decision.** `spending_report_enabled` does not exist in
`config.py` or `.env`. A subsystem gated on an undefined setting cannot be turned on by editing
configuration — only by editing code. Whether the report *should* run is a product question, but its off
state is currently an accident of a missing definition rather than a choice, and nothing in the system
says so.

**What stands from this thread.** The `daily-finance-sync-cron.sh` execute-bit fix is verified: the finance
snapshot is fresh for the first time since 2026-09-07 (24 accounts, $293,791.88 credits, $352,450.79
debits). The breaker cooldown is a real fix for a real latent trap, and I corrected my over-claim that it
would restore all four (W52).

**What the owner has to do, and only he can.** Complete the Amazon login/MFA and the eBay login. The
command the service names is
`cd /home/zabz/repos/quickbooks-agent && npm run amazon:download` — run where a browser window can be seen,
which the headless authority cannot provide, so this likely wants his machine or a remote-desktop session
rather than a script I can fire.
