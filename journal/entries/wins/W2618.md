**W2618 · 2026-09-30 · A three-state health gate, a watchdog that judges health, CRLF detection, and one canonical home for every guard.**

Three mechanisms that make a degraded system say so, and one canonical home for them.

**1. A THREE-STATE HEALTH GATE (P170, P66).** Every gate that decided whether production was up used
`curl -fsS`, and `-f` fails on an HTTP error status while this API answers **HTTP 200 with
`ok:false`** when degraded. So the gate could not tell "came back" from "came back broken", and the
reverse reading could not see degraded at all. `scripts/server/health-gate.sh` is now the one place
that decides: HEALTHY (2xx and `ok:true`), DEGRADED (2xx with `ok:false`, or an unparseable or absent
`ok` field -- an unknown health is not health), DOWN, with exit codes 0/2/1. `restart.sh`,
`verify-production.sh` and `status.sh` now ask it instead of guessing. Landed as the SAME anchored
edit on both sides of the personal-secretary-mvp divergence (authority `9780dd8f`, repo clone
`37a8ae6e`) so the fix does not widen the 177/200 gap; the four shell scripts were also normalised to
LF, because a CR turns every line of a shebang script into `command not found`.

**2. THE API WATCHDOG NOW JUDGES HEALTH, NOT JUST LIVENESS (P66).** Measured 2026-09-30 16:39-16:49:
it printed `ok: secretary-api.service is active` every five minutes while `/health` was answering
200/`ok:false` ("db check timed out (lock contention); api still responsive") and two of five probes
took the full 10 s. `systemctl is-active` cannot see that and nothing else was looking. It now reads
the gate on every pass, counts consecutive bad observations, records the third in
`~/.api-watchdog-degraded.log` and tells the owner once, and recovers once at the sixth (30 minutes)
under the existing hourly cooldown. Thresholds on purpose: a restart on the first bad reading is how
a watchdog becomes a restart loop. Falsified: three deterministic DEGRADED observations produced
`degraded #1/#2/#3` and a recorded incident.

**AND I WROTE THE SAME BUG I HAD JUST BUILT A GATE AGAINST.** The first version read
`hs="$(timeout 20 "$GATE" show "$HEALTH_URL" || echo DOWN)"`, and the gate exits **2** for DEGRADED by
design -- so `||` fired and a DEGRADED reading became `"DEGRADED\nDOWN"`, which the incident log
recorded as `DEGRADED / DOWN`. A caller that cannot distinguish two states, twenty minutes after
building the gate whose entire purpose is that distinction. Fixed by reading the exit code and then
one line of output; re-falsified on all three branches.

**3. A SHELL SCRIPT WITH CRLF IS NOT A SCRIPT.** `scripts/server/install-backup-timer.sh` carried CR
bytes in the repo, and the estate already has a trail of `.crlf-bak` files from the last time this
bit. The cron-target guard now reports CRLF shell scripts for **both** crontab targets and critical
paths, independently of the execute bit (the first version checked the mode first and `continue`d, so
the CRLF case was never reached -- caught by the guard's own selftest). Falsified on a real CRLF
script and on a script with no execute bit.

**4. THE MECHANISMS NOW HAVE A HOME THAT REACHES EVERY MACHINE.** All of the above lived only in
secratary's `~/bin`, which is one disk. `harness-config/scripts/guards/` is now the source of truth
(seven guards plus four flag sources), with `scripts/guards/install.sh` copying them to `~/bin` and
`~/bin/sources` on any host -- sha256 verified before and after every copy, CR stripped, existing
files backed up, `--dry-run` supported -- and the cron lines, sources-loop membership and systemd unit
listed as notes rather than applied, because each is a per-host decision. Pushed as `e8a5440`;
verified on the authority by dry-run, where every file reported `already current` with a matching
hash.
