**W59 · 2026-09-14 · 2026-09-14 - P4 is not a bug: auto-apply is off by config, and the kernel alarmed about a setting for 10 weeks.**

**P4 is not a bug: the improvement loop is configured not to apply, and the kernel was raising a permanent HIGH alarm about a setting**

**The answer to "why are 72 proposals unapplied", and it is not a defect.** `app/evolution.py` gates the
apply path on a setting:

 wants_auto_apply = bool(getattr(settings, "code_edit_auto_apply", False))

`code_edit_auto_apply` is **declared `False` in `config.py:803` and set `False` explicitly in the
authority's `.env:123`**. `evolution_log` confirms it took effect at the right moment: **102 applied, newest
2026-07-04**; 72 unapplied, oldest 2026-06-30, newest today 08:43. The last application is the day the
switch went off. **Autonomous code self-application is deliberately disabled, and 72 queued proposals is the
system working as configured** — proposing for human review, not self-applying.

**The real defect is upstream of that, and it is the reason nobody noticed for ten weeks.** The `evolution`
subsystem's own health record reads:

 successes 611 · failures 0 · consecutive_failures 0 · last_status ok · last_detail (empty)

611 successes against zero failures, while the loop had applied nothing for ten weeks. **It counts "the cycle
ran" as success**, with an empty detail, so a subsystem producing nothing reports perfect health. That is the
honest-completion defect again, one layer up: not a wrong status on a session, but a wrong *health* on the
mechanism that is supposed to police everything else.

**And the alarm was wrong in the opposite direction.** `check_evolution` reported *"evolution loop not
closing: 72 proposals unapplied"* at **HIGH** and put it on the owner's badge as needing attention — an
alarm about a setting, permanently, forever. P52 already records that a sentinel and an alarm disagreeing
teaches the owner "to start ignoring both"; an alarm that is permanently wrong does the same job more slowly.

**Both fixed in the kernel** (a cron-run script, so no service restart):

1. `check_evolution` now reads `CODE_EDIT_AUTO_APPLY` from the app's `.env`. With auto-apply off, unapplied
 proposals are reported as **INFO with a reading** — *"evolution proposes but does not self-apply:
 auto-apply is off in configuration, so 72 proposal(s) are queued for review (102 applied historically)"* —
 instead of a fault. Duplicates and node_modules targets keep their severity, because those are real.
2. The duplicate scan is **bounded to the last 7 days**. Historical duplicates are history: no code change
 can alter a logged row, so scanning all of them pinned the check HIGH forever and made it
 indistinguishable from a broken check. Verified: with the window the count reads **22 recent duplicates
 instead of 38 all-time** — still above the threshold, correctly, because my W57 fix landed twenty minutes
 ago and the window still contains pre-fix rows. **The alarm will clear on its own after seven clean days
 and return if duplicates come back.**

**What I did not do, so this is not read as more than it is:** I did not enable auto-apply. Whether the AI
company should edit its own code unattended is a **governance decision about autonomous self-modification**,
not an engineering one, and the setting is already off by explicit configuration — which is the safe state.
The 72 proposals now sit in the record as *queued for your review* rather than as a fault, which is what they
actually are.
