**W2804 · 2026-10-08 · A synthetic C:\Users tree plus a subst drive as a fake SD card caught three real defects in one unattended tool before it touched a customer machine.**

**What worked.** A synthetic `C:\Users` tree plus a **`subst` drive** standing in for an SD card, and
stub scripts for the failure paths, caught **three real defects** in an unattended data-copy tool
before it ever touched a customer machine - including one (`->` inside an `echo`) that made the
fallback copy die with robocopy exit 16 and look like a robocopy problem.

**The rig** (`lpt-hub/_scratch/lpt-sd-test/`, built and run 2026-10-08):

- two profiles, hidden files, `Documents` / `Desktop` / `Pictures`
- `AppData\Local\Google\Chrome\User Data\Bookmarks` and `AppData\Local\Microsoft\Outlook\mail.ost` -
 the things that must NOT be missed
- `AppData\Local\Temp\junk.tmp` and a `Public` folder - the things that must be skipped
- an `NTUSER.DAT` stand-in, which is what caught the scanner counting files the copier was told to skip
- **a directory junction pointing back at its own parent**, to prove the walker cannot loop
- **`subst X: <folder>`**, so `%~d0` reports a real drive letter and the tool's "is this actually a
 card?" guard is exercised for real rather than reasoned about
- a **stub `lpt-copy.ps1` that exits 42**, to drive the fallback path without copying the real `C:\Users`

**Tested, therefore known-broken-then-known-fixed:** clean copy → `VERIFIED`; destination on `C:` →
refused with nothing created; running from `C:` → refused; missing source and missing card → aborted;
forced tool failure → fell back to a plain `robocopy` that worked.

**Why this generalises.** The cheap way to make a destructive-capable tool trustworthy is to hand it a
fake world small enough to run in seconds, and to test the failure paths on purpose instead of hoping.
The pass/fail matrix went into the tool's README so no future session has to re-derive it - which is
the difference between a tool this system owns and a script somebody once wrote.
