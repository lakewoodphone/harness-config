**W138 · 2026-09-15 · Closed an unauthenticated public surface: customer receipts, bank accounts, the device fleet and outbound SMS were on the open internet.**

**What was wrong.** The company's FastAPI backend was reachable on the public internet with **no
credential at all**, exposing real customer data and remote device control. Measured by me, 2026-09-15
~20:10 UTC, from `https://api.abletelsolutions.com` with no headers:

| route | before | after |
|---|---|---|
| `GET /api/v1/receipts` | **200, 92,986 bytes** (customer receipts) | **401** |
| `GET /api/v1/reconciliation/proposals` | **200, 67,367 bytes** | **401** |
| `GET /api/v1/plaid/accounts` | **200, 5,288 bytes** (bank accounts) | **401** |
| `GET /api/v1/fleet/devices` | **200, 4,224 bytes** | **401** |
| `GET /api/v1/comms/by-phone/<any>` | **200** (arbitrary arg accepted) | **401** |
| `POST /api/v1/dialpad/sms/send` | reachable uncredentialed — **outbound SMS to any number, as Lakewood** | **401** |
| fleet Activation Lock / Lost Mode / lockdown | unauthenticated remote device control | **401** |

A per-route scan of the live `app/main.py` found **190 guard-exempt routes, 141 with no auth call in the
handler**. The auditor's summary: `/etc/cloudflared/config.yml` maps `api.abletelsolutions.com ->
localhost:8002` (raw FastAPI), and the same paths are safe on `ai.abletelsolutions.com`, which goes through
Next.js `getServerSession` and returns 401.

**Root cause, in one line of code.** `_api_access_guard` (`app/main.py:361-366`) exempts **everything**
starting with `/api/v1/` *before* any key check, on the stated theory that "handlers authenticate
individually". 141 of them do not. A helper that already expressed "this path needs a key" —
`_dashboard_path_requires_api_key()` — existed at `:318` and **the middleware never called it**. So the
guard's own docstring described an intent the code did not implement, and read as if the case were handled.

**The fix, and why it is safe.** Two changes: the middleware now consults the helper first, so a named
prefix falls through to the existing key check; and nine sensitive prefixes were added
(`/api/v1/fleet/`, `/api/v1/dialpad/`, `/api/v1/receipts`, `/api/v1/plaid/`, `/api/v1/reconciliation/`,
`/api/v1/comms/`, `/api/v1/shop/`, `/api/v1/projects`, `/api/v1/uploads/`). It is **additive**: loopback is
trusted at the top of the guard, so internal callers are untouched — verified after deployment, loopback
still returns 200 for `/api/v1/fleet/devices` and `/api/v1/receipts`, and `/health` is still a public 200.
Remote callers are not locked out; they need the dashboard or gateway key.

**The mistake I made inside the fix, and what caught it.** My first attempt **silently did nothing**. Its
idempotence check was `if "/api/v1/fleet/" in src: → already patched`, which matched the *route decorators*
(`@app.get("/api/v1/fleet/devices")`) somewhere in 22,066 lines, not the constant I was adding. So the
middleware was patched to consult a helper that still returned False for those paths — a change that reads
as a fix, compiles, and changes no behaviour. **The predicate self-test I wrote for exactly this caught it**
(8 of 10 cases failed), I re-keyed the check on the exact tuple tail, and re-proved 17/17 cases before
deploying. Same species as `P167` and the `/health` degraded-200: a guard that reads as if the case is
handled.

**Verified after deployment** (not assumed): all six dangerous public routes 401; `POST /api/v1/dialpad/sms/send`
401; loopback 200 for the same routes; `/health` 200; API healthy 16 s after restart.
Backups: `app/main.py.bak-unauth-20260915-201401` and `.bak-unauth2-20260915-201413`.

**Still open from the same audit, not fixed:** webhook verification on `/webhook/github`, `/webhook/event`
and `/webhook/ha/*` is `if secret:` = **fail-open**, and `GITHUB_WEBHOOK_SECRET`, `EVENT_WEBHOOK_SECRET`,
`HA_PTT_KEY`, `SECURITY_API_KEY` are all **unset**; billing charges have **no idempotency key** so a retry
double-books; the backup estate at `/home/zabz/secretary-backups` is mode **0644** and contains plaintext
`.env`, Gmail/Calendar tokens and browser sessions with no offsite copy; and one IAM user
(`github-actions-deployer`) still holds **AdministratorAccess** with an Active key. Closing only the named
prefixes leaves the other ~130 unguarded `/api/v1/` routes reachable — the real fix is inverting that
exemption to deny-by-default with an explicit allowlist, and that needs tests and a workstream, not a
hotfix.
