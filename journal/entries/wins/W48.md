**664 of 679 "failed" work sessions had already finished their work: the loop was scoring completed work as failure**

**The measurement that reverses the picture.** Work sessions joined to their task, 2026-09-07 onward:

| session status | task status | sessions |
|---|---|---|
| **failed** | **done** | **664** |
| completed | done | 819 |
| failed | in_progress | **15** |
| completed | in_progress | 3 |

**664 of the 679 failed sessions that had a task had that task marked `done`.** Genuinely unfinished
work accounts for **15** sessions. So the work-session "failure rate" I reported for three rounds —
"96.5% fail", "essentially everything fails regardless of shape" — was measuring **the accounting, not
the work**. The loop does the work and then records it as a failure.

**The cause, and it took a working example to see it.** Completion was judged only by the model
emitting the `[WORK_DONE]` token. Session **75337** is the live case: its steps 3 and 4 logged
`[ACTIONS: 2 (save_memory, update_task)]` and `[ACTIONS: 1 (update_task)]` — it marked the task done —
and it never emitted the token. Every earlier attempt to see this was blocked by the same
invisibility: action results went to `proactive_actions` (the tick's notes) rather than the session log,
which is what W46 and the `[ACTIONS:]` marker fixed. **The observability fix is what produced this
diagnosis**; without it, the sixth session in a row would have looked like six more stalls.

**The fix.** `_task_is_closed()` reads the task row, and the loop completes the session when the task's
own status is done/completed/closed, keeping the artifact gate and keeping `[WORK_DONE]` as a valid
signal. The task row is the authoritative statement of whether the work is done; the token is a
convention the model does not reliably follow. Deployed at 16:21:58Z; 35 tests pass on the authority's
own tree.

**Two bugs in my own first version, both caught by the tests I wrote for it.** `get_task` is imported
*locally* inside `_process_work_queue` and not at module level, so calling it as a global raised
`NameError`; and my `except Exception: return False` converted that into "the work is not complete" — a
plausible answer, therefore invisible, which is the fourth instance of the same pattern in four rounds.
The read failure now logs, and two tests exist specifically because a predicate that silently never
fires would have looked like a working deploy.

**What this means for the owner, stated carefully.** The company's headline churn — the "**16,795
failed goals vs 11,563 completed**" that task #24956 exists to fix — has the same shape as this defect,
and it should not be read as 16,795 pieces of work that failed until someone checks the goal rows the
way the task rows were checked here. The evidence for *that* is not in yet, and the honest position is
that a scoring defect of this kind, in a system that has one, is a better prior than a genuine 60%
failure rate.

**Verification point, named.** Session **75338** was created at 16:21:55, three seconds before this
fix landed, with its task still `open`. The first session whose task gets closed mid-run should now be
recorded `completed` with a `[COMPLETED: the task itself is closed]` marker and a `task_closed` job
reason. Until a row shows that, this is a well-evidenced fix rather than a demonstrated one.
