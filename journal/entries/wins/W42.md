**W42 · 2026-09-14 · 2026-09-14 - Work mode verified end to end on the DEPLOYED prompt: 2 executable actions parsed, 0 dead tags.**

**The work-mode fix is verified end to end, on the deployed prompt, by the real parse path**

This corrects the "unmeasured" in the previous correction to H85. The measurement is now in, and
it is positive.

**What was tested.** Not a hand-written prompt and not a unit test: the authority's own
`AutopilotController._build_work_prompt` was called to produce the *exact* prompt the live work
loop builds, that string was passed through `run_assistant_chat(tier="fast",
call_type="work_mode")` — the same call the work loop makes — and the reply was put through
`parse_actions()`, which is the function the work loop uses to decide what to execute.

**Result.**
- Prompt guards: the dead instruction is absent, the tag warning is present, the per-step tool
 requirement is present.
- The model produced **2 executable actions**: `list_dynamic_tools {"query": "goal quality
 gate"}` and `task_hygiene {}`.
- `parse_actions` parsed both. **Zero** `[ACTION:` tags in the reply.
- Model: `deepseek-ai/DeepSeek-V4-Flash-0731` (the `fast` tier the work loop uses).

So on the deployed prompt the work loop now has something to execute instead of prose to repeat.
Before the fix the same tier, asked to act via a syntax the parser discarded, produced nothing.

**A finding that changes the mental model.** The model does not use the native `tool_calls` channel
here — it answers with the structured JSON block
(`{"reply": "", "actions": [{"name": ..., "params": {...}}]}`), and `tool_choice="required"`
does not change that (probed both `auto` and `required`: identical shape, `tool_calls: 0` in both).
The structured-JSON fallback is therefore not a fallback in practice — it is the primary channel
for this model, and `_parse_structured_actions` is load-bearing. Any future change that drops or
narrows the structured-JSON path will silently break work mode even though native tool calling
"works".

**A second finding, not yet acted on.** The work prompt is **41,225 bytes** (~10k tokens) before any
conversation, because it inlines the full tool summary, the owner context and the previous step's
output tail. That is paid on every one of five steps for every session, and the measured
`model_usage_today` for the fast tier is hundreds of millions of tokens. It is also a plausible
contributor to the model losing the instruction among the context. Worth measuring the cost and
the completion rate with a leaner prompt; not changed here, because the current shape works and
changing two things at once would confound the result.

**Honest limit of this evidence.** It proves the mechanism works for one representative task shape.
It is not a completion-rate measurement. The claim it supports is narrow and real: the prompt the
live system builds now produces executable actions where it previously produced none.
