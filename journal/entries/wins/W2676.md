## WHAT WAS WRONG, stated in one line
The probe required a healthy *body* from an endpoint whose HTTP status already proved it was
serving, and made two curl calls to get them — so `/health` answering **200 with `ok:false`**
(its own DB check timing out under lock contention) was reported to the owner as "stopped
answering". **18 down texts in three days**; the four newest each carried `http 200`.

## EVIDENCE IT IS FIXED — live, not a dry run
- Pre-install, the OLD code at 03:20:01Z logged `TRANSITION ok=false ok_raw=false http_code=200
 consecutive_failures=1` — i.e. still counting a 200 as a failure — and at **03:24:01Z it tried
 to send the 7th alert**, which the global ceiling caught:
 `ALERT SUPPRESSED (global SMS ceiling: 6 owner text(s) already in the last 24h (max 6))`.
 That is the old behaviour captured on the wire one minute before the install.
- Post-install, the patched script ran on its own schedule repeatedly and never once
 mis-classified: `03:26:01`, `03:32:01`, `03:34:01`, `03:36:01` — each
 `answered=True degraded=False http=200`, `consecutive_failures=0`, latency 0.098–0.492 s.
- **Zero `ALERT SENT` after 03:25:00Z.** The state file carries the new fields
 (`answered`, `degraded`, `degraded_reason`, `latency_s`, `slow`), which is how a future session
 can verify at a glance rather than inferring from the log.
- The fixture test that reproduces the historical failure (a stub answering 200 + `ok:false`)
 yields `degraded=True consecutive_failures=0` with **0 alert attempts**, against the old code's
 counter increment.

## CORRECTION TO MY OWN EARLIER CLAIM
I first told the owner the endpoint was taking 9.5 seconds and implied the alerts were pure
noise. Both were overstated. Six clean probes: `200 0.214 / 200 0.258 / 200 0.367 / 200 0.246 /
200 0.110 / 200 0.074` seconds. The endpoint is fast; the multi-second readings came while this
host was loaded by my own fleet, so **some of those alerts were load-induced and the load was
partly mine.** The narrower claim is the true one: the probe called an answering API "down",
18 times, because it demanded a healthy body as well as a successful status.
