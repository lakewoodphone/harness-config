**W179 · 2026-09-16 · Both machines now pass the same 10-check verifier.**

## The milestone
`harness-verify.ps1` reports **10 ok, 0 failed, exit 0 on both machines** — ZABZ-YOGA and
ZABZ-TECH — running the same script from the same commit. That was the objective's second half, and
it required three separate things to be true at once: the history integrated, the config deployed,
and the per-machine provisioning done.

## How ZABZ-TECH got there (the whole sequence, since it is repeatable)
1. **The integration.** `master` was diverged (laptop ahead 19, behind 12) and the remote's 12
 commits collided with the laptop's journal entries as **add/add conflicts on the same 18 ids** —
 two machines, one number, different records. Resolved with a new script,
 `scripts/resolve-journal-merge.py`: the entry with the **earlier timestamp keeps the id** (the id
 was allocated then), the other is renumbered to the next free number for its kind with its
 self-references rewritten, and an **alias row** is written so `resolve_alias()` still maps the old
 id. Nothing dropped — 18 collisions resolved as D207/D208, H378-H386, L1720-L1724, W177/W178.
 `journal.py` itself needed no hand-resolution: their `git_max` fix (which now reads
 remote-tracking refs, so a fetched machine sees the other's numbers before choosing its own) and
 my lock/append work auto-merged.
2. **The renumbering broke 9 stored footer hashes** (`check` 0 -> 9 errors), because rewriting an
 id inside an entry changes the text its hash describes. Fixed with **their** `rehash.py --apply`,
 which recomputes a hash from the entry's own heading and body and touches nothing else. `check`
 back to **0 errors**, 51 warnings — identical to before the merge.
3. **Pushed and levelled.** Merge `7c1a317` to `master`; the laptop fast-forwarded to match
 (`## master...origin/master`, no divergence).
4. **Deployed.** On the desktop: `git merge --ff-only` -> `sync.py` (presets, skills, profile patch,
 client plugins) -> `harness-verify.ps1`. The first run answered honestly: **6 ok, 4 failed** —
 no stable MCP install, no reaper task, no `NODE_COMPILE_CACHE`, and **10 stale MCP generation
 chains**.
5. **Provisioned the machine-local parts.** A new `scripts/provision-mcp-tools.ps1` (idempotent:
 installs the five MCP packages into `~/.dsh/tools/mcp` only if the entry points are missing —
 they are what the preset's direct-node rows point at, and with `failOnStartupError: false` a
 missing install fails silently). Plus the compile-cache env var, the reaper task, and a reaper
 run that **killed 10 stale generations**. Then: **10 ok, 0 failed.**

Details worth keeping: the desktop's `npm install` of 316 packages took **12 s** against ~4 minutes
on the laptop, and its `pages_in/s` read **53** before provisioning, **3298** during it (load), and
**44.3 GB commit of 63.6 GB** after — so on that machine memory is not the constraint either.

## The rules this produced
- **A merge of two machines' records is a data problem, not a git problem.** Never resolve an
 add/add conflict on an entry by choosing a side; renumber and alias, or the record loses a fact.
- **Renumbering is a content change**: any tool that stores a hash of an entry must be re-run after
 it, and the repair tool must be one that cannot alter the record while repairing it.
- **Per-machine provisioning is part of a deployment.** A config that names an absolute path is only
 deployed when that path exists; otherwise it fails silently behind `failOnStartupError: false`.
 That is what `provision-mcp-tools.ps1` exists for, and what the verifier's `stable install
 present` check catches.
- `harness-verify.ps1` is portable as written: the same script, unchanged, produced a truthful
 before-and-after on a machine it had never run on.
