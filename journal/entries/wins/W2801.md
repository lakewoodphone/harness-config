**W2801 · 2026-10-13 · The script half now has a drift check, and it recovered two pieces of work from the running location.**

THE SCRIPT HALF HAD NO CHECK. It does now, and the check found more than the thing I was chasing.

WHY IT EXISTS. `preset-drift.py` checks the instruction surface a machine LOADS.
`assert-bin-matches-repo.py` checks one curated manifest of text-line scripts. **Neither checks the
ordinary scripts the authority actually executes out of `/usr/local/bin`** -- which is exactly where
`journal/tools/journal.py` turned out to be two fixes behind, called by four deployed tools.

WHAT IT FOUND, MEASURED 2026-10-13 on secratary-cloud:/usr/local/bin:

 61 files in the directory
 8 resolve to a repo path: 7 MATCH, 1 DRIFT
 52 are in NO repo path at all
 1 explicit exclusion (`transcript-archive-pass.sh`, a wrapper that sets TRANSCRIPT_* and calls
 the repo runner -- supposed to differ, and its reason is written down rather than hidden)

TWO PIECES OF REAL WORK RECOVERED, because the tool names the DIRECTION: in both of these the
DEPLOYED copy was the newer one, which is the direction nobody looks for -- the running copy works,
so nothing is broken and nobody checks.

 * `production-comms-freshness.py` repo 8,345 B vs deployed 16,420 B. The deployed copy carries the
 2026-10-11 cloud port (workstream 135): paths environment-overridable, the cloud box reading
 `/root/authority.db` **read-only**, and a docstring that says why a monitor must never be a second
 writer against the single live authority.
 * `stripe-key-watch.py` repo 9,373 B vs deployed 9,125 B. The deployed copy has the corrected
 key-backup path and an honest note that it is ABSENT on the authority, so that source reads as
 unreadable and is REPORTED rather than faked.

Both brought home after proving neither deployed copy lacked a function the repo had (0 in both
cases). This is the reverse of `P3164` and `W2800`: work that landed only in the running location.

STILL OPEN, AND DELIBERATELY NOT ACTED ON: `phone-gate-allow.txt` drifts with the REPO ahead
(6,417 B vs 3,274 B). **I did not deploy it.** An allow-list is a security surface, the deployed copy
being the SMALLER one may well be deliberate, and "the repo is bigger so deploy it" is exactly the
reasoning that this program has now been wrong about five times. It needs a human read of both lists,
not a copy.

AND THE FINDING BEHIND THE FINDING: **52 of 61 files in `/usr/local/bin` exist in no repository.**
Much of this estate's machinery is deployed rather than versioned, so the authority can run code that
nothing in git describes. Not every one of those 52 is estate code, and the tool says so rather than
claiming a number it cannot support -- but the ones that are (sentinel-freshness-check.py,
prune-backups.sh, report-offsite-age.sh, tmpfs-reaper.sh, verify-offsite-object.sh ...) are the
estate's scheduled work, and they are the next thing to bring under version control.
