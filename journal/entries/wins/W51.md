**#8 solved at the root: a sync breaker that could never clear itself had wedged the bank feed for 55 days**

Owner question #8 was resolved as mis-filed and taken as my work. The root cause is found, fixed and
deployed, and the evidence is unambiguous.

**The measurement that settles it.** The breaker state is persisted in
`data/autopilot_state.json`, and reading it after the fix gave:

| sync | consecutive failures | **last attempt** |
|---|---|---|
| `boa_sync` | 114 | **2026-07-21T03:00 — 55 days before this session** |
| `amazon_sync` | 42 | 2026-09-06T04:00 |
| `ebay_sync` | 42 | 2026-09-06T04:15 |
| `spending_report` | 38 | 2026-09-03T05:30 |

`boa_sync` was blocked on 21 July and **has not been attempted once in 55 days**. That is not a failing
sync; it is a disabled one. This is the same class as the Telnyx balance going negative unnoticed: the
system knew, and told nobody.

**The defect.** `_finance_sync_blocked_by_breaker()` skips a sync once consecutive failures reach a
threshold, and its docstring said it "stays paused until a successful run (clears the counter) or an
explicit manual reset". But the check runs **before** the sync, so a tripped sync never ran, never
succeeded and never cleared — and `subsystem_health` is persisted, so it survived every restart as well.
A lock, not a breaker. Only a human editing `autopilot_state.json` could ever unwedge it.

**The fix.** A cooldown: after `_SYNC_BREAKER_COOLDOWN_MIN` (360) the sync gets **one probe attempt**.
Success clears the counter; failure re-trips the breaker and restarts the cooldown. The owner is still
told exactly once on the trip, and the threshold logic is unchanged. Deployed 16:35:34Z; 8 tests pass on
the authority's own tree; compile gate green; `/health` 200.

All four are far past the cooldown, so **all four get a probe attempt on their next scheduled run** —
`boa_sync` at 03:00, `spending_report` at 05:30.

**A test I wrote caught a gap in my own first version.** I first handled only a *readable* timestamp, so
an entry with `last_ran_at` missing was still blocked forever — the identical permanent-lock defect in a
different disguise. The fix now treats "unknown" as "allow one probe", and two tests cover the missing
and unparseable cases.

**What is NOT established.** The breaker was *one* cause and it is removed. Whether `boa_sync` then
succeeds depends on the original failure — likely browser automation or credentials, since the setting
is `boa_sync_enabled` and the subsystem shells out. **Un-wedged is not fixed**, and the next reading is
whether they succeed on the next scheduled run. Claiming the bank feed is restored because the lock is
gone would be exactly the confident wrongness this session has produced five times already.

**One more thing in the same family, already fixed:** the deterministic cron that exists *because* the
agent-driven `daily-finance-sync` work order failed 169+ times (`scripts/daily-finance-sync-cron.sh`)
was tracked in git as `100644` — no execute bit — while its sibling was `100755`. Cron invoked it
directly, so it died with `Permission denied` and last succeeded 2026-09-07. Fixed in git
(`130c0cd71`, so it survives every clone) and run: **24 accounts, $293,791.88 credits, $352,450.79
debits, 50 recent transactions, "OK: finance sync completed"** — the first fresh snapshot in six days.

So the finance pipeline had **two independent failures stacked**: a cron that could not execute, and
four subsystems locked out by their own breaker.
