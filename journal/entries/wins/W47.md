**W47 · 2026-09-14 · 2026-09-14 - Probe acts, production narrates: the loop now records what it received, and the verification point is named.**

**The probe acts and production narrates: I stopped guessing and made the loop say what it received**

**The contradiction, stated exactly.** Same code path, same `fast` tier (`autopilot_work_mode_tier`
is `"fast"`, not overridden), same real `_build_work_prompt`, same settings — and:

- A direct probe of `run_assistant_chat` with the deployed prompt returns an executable action
 **for every agent id tried**: `dept_engineering`, `evolution_architect`,
 `cross_domain_synthesizer`, `dept_mashgiach`, `model_ops_evaluator`, `orchestrator` → one parsed
 action (`list_tasks`) each.
- Production sessions narrate instead. Session **75336** ran five steps of *"Let me list the
 in-progress tasks to identify the stale one"* and failed with
 `[STEP_BUDGET_EXHAUSTED: reached planned 5/5 work steps without [WORK_DONE]]`. No tool call in any
 step, and no `[ACTION:]` tag either.

**What was ruled out, each by measurement rather than reasoning.**
- **The department tool allow-list.** `get_department_tools()` returns `[]` for any agent id absent
 from `DEPARTMENT_TOOLS`, and `evolution_architect` is absent — an attractive cause. It is **not**
 it: the probe returns an action for that same agent id, and `agent_worker.py` (the only place that
 builds tools from the allow-list) contains no `output_log`, `create_work_session` or `work_sessions`
 reference at all, so it does not run these sessions. They are autopilot's `_process_work_queue`.
- **The work-mode tier.** `"fast"` in production, `"fast"` in the probe.
- **Provider routing to a tool-less path.** The dominant fast-tier model is
 `deepinfra/deepseek-v4-flash` (3071 calls since 2026-09-13) — the same model the probe was served
 by.
- **The repetition guard as the cause of this failure.** 75336 shows no `[STALLED_REPEATING_OUTPUT]`
 marker; it failed on the step budget. So the round-4 guard fix did not cause and did not prevent
 this one.

**So the loop was made to answer it instead.** The log recorded only the model's prose, which is the
one thing that cannot distinguish the two remaining possibilities: the model returned *no*
tool call, or it returned an envelope that the parser dropped. Each step now writes one of:

 [ACTIONS: n (names...)] the step did work
 [NO-ACTION: reply=3452c cleaned=210c envelope=no tags=0 head=...]

`envelope=yes` with no actions means a parser defect; `envelope=no` means the model produced prose
and the question moves to routing. That single field decides it, and it is in the record from now on
rather than in a probe harness that does not reproduce the production path.

**Deployed** at 16:13:50Z (backup `handport-no-action-marker.py.pre`); 25 tests pass on the
authority's own tree; `/health` 200.

**THE VERIFICATION POINT, and it is not yet met.** Session **75337** was created at 16:13:47 — three
seconds *before* the instrumentation landed — and had executed zero steps when this round ended. The
first session to run steps entirely under the instrumentation is the one that answers the question,
and nothing before it can. This round deployed the instrument, not the cure; calling the work-loop
problem solved now would be exactly the confident-wrongness this journal exists to prevent.

**What the answer will mean.** `envelope=no` → the model is not emitting tool calls on the production
path, so the lever is the provider/routing or the prompt's effect on this model, and the probe is
mismatched in some way I have not yet identified. `envelope=yes` → `_parse_structured_actions` is
dropping well-formed envelopes, which would also explain the 41 briefing envelopes failing the same
way, and the fix is in the parser.

**Unchanged fact worth restating:** 96.5% of the newest 400 sessions fail. Whatever the remaining
mechanism is, the company is spending real money on work that does not land.
