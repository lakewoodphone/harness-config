**W6362 · 2026-10-14 · The authority's peer visibility wired and scheduled: two ssh remotes landing the Windows nodes under refs/remotes/origin/, plus a */15 ceiling refresh - because one side of the two-sided mechanism had never been connected.**

The authority now has the peer visibility it never had, and the refresh is scheduled — so the ceiling stops ageing into uselessness.

**The asymmetry that caused the whole defect.** ZABZ-YOGA refreshes its view on its own **writer path**: `git_max` runs `git fetch --all`, and this machine has a remote whose refspec lands the authority under `refs/remotes/origin/`. **The authority had no peer remote at all** — its `origin` is a local bundle (`/root/hc-main.bundle`) — so it allocated against a picture that never changed, and grew **70 -> 83 collisions in three hours** while my own 34 post-fix entries collided **zero** times (`L3936`). **One side of a two-sided mechanism was working; the other had never been wired.**

**The fix, and the design choice that matters.** The authority is the always-on host and it can reach both Windows nodes over ssh, so **it pulls from them** — no scheduler is needed on Windows. That is the whole point: a fix requiring ZABZ-YOGA to push on a timer would need a Windows scheduled task and would break whenever the laptop is off.

 git remote add yoga zabz-yoga-ts:C:/Users/ezabz/code/harness-config
 git remote add tech zabz-tech-ts:C:/Users/ezabz/code/harness-config
 git config remote.<name>.fetch '+refs/heads/*:refs/remotes/origin/<name>/*'
 */15 * * * * cron-wrap.sh journal-ceiling-refresh <fetch both, then re-note the ceiling>

The refspec target is not cosmetic: **`git_max` reads only `refs/remotes/origin/*`** (`journal.py:3356`), so the peers must land there. And the job re-notes the **cached** ceiling, because `allocation_ceiling` reads `stamp.json:git_ceiling` — a fetch alone changes nothing until a writer path runs `git_max` to refresh the cache. **Both halves, or neither works.**

**The remote path form took three attempts, and the failure messages were informative:** the scp-like form with a Windows drive works — `zabz-yoga-ts:C:/Users/ezabz/code/harness-config` resolved to `1e568a2f…`, my current commit — while both `ssh://zabz-yoga-ts/C:/...` and `zabz-yoga-ts:/c/Users/...` fail with *"does not appear to be a git repository"*.

**Verified:** both fetches `rc=0`; `refs/remotes/origin/` now carries `yoga/*` and `tech/*`; the refreshed ceiling reads `handoff 3778 lessons 3935 pain 3204 decisions 3209 wins 2877`, with **`lessons 3935` being my own ids** — so the authority can now see this machine; `allocation_ceiling(pain) = 3206`; and the wrapper returns **rc=0**. Crontab backed up twice (`crontab.bak-ceiling-20261014T154003Z`, `crontab.bak-ceilfix-20261014T154341Z`).

**And I broke it once and caught it, which is the part worth keeping.** The first cron line embedded a `python -c "…"` inside a double-quoted shell argument, so the shell split on the inner quotes: **the wrapper returned rc=1 and the job would have failed silently every 15 minutes forever.** The fix is single quotes inside the double-quoted argument — and the method now applied is the one that should have been applied first: **prove the inner command runs and returns 0 *before* scheduling it** (`rc=0` printed above the install, not after).

**What this does and does not yet change.** The authority's **current** window is still `reserved through P3229` and it cannot un-claim it, so its next ~23 ids may still land in the legacy overlap with mine (3199-3229). **The fix binds from its next reservation**, which will be chosen against a picture that now includes this machine — and that reservation is the test to watch, not the ceiling number.
