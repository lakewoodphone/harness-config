**W2604 · 2026-09-29 · Deploy gate: three checks that would have caught all seven deleted modules, verified by breaking a tree on purpose.**

BUILT AND VERIFIED 2026-09-29: scripts/deploy-gate.py in personal-secretary-mvp. It refuses to call a deploy good unless three independent checks pass:
 [1] IMPORT python -c "import app.main" succeeds
 [2] MISSING every app.* module referenced anywhere in the tree resolves to a file
 [3] ORPHANS no bytecode exists for a STILL-REFERENCED app/ module whose source is gone

Design details that matter, each learned by measurement rather than taste:
 * (2) exists because (1) cannot see imports that sit inside a try/except or a function body - which is exactly how seven deleted modules stayed invisible.
 * (3) is the copy-deploy fingerprint: a .pyc whose source is gone proves the file WAS there and was removed. It is what identified the seven.
 * SEVERITY SPLIT. The first version failed on every orphan, including ~80 retired test .pyc files, so it failed on a healthy tree. A gate that always fails gets ignored - the same alarm fatigue that let seven modules vanish. Now: an app/ orphan that something still references is FATAL; an app/ orphan nothing references is a warning; stale bytecode outside app/ is a warning.
 * No side effects: it does not import application code, write anything, or touch the database. --skip-import gives a fast static pass for CI.

EVIDENCE IT WORKS: deleting app/direct_request.py from a copy of the tree made it refuse, naming BOTH the missing module and its referencing file, and separately flagging the orphaned bytecode. Run against the live tree it went from 7 fatal problems to "DEPLOY GATE: PASSED".

STILL TO DO: it only helps if something RUNS it. It is not yet wired into the deploy script (an audit of that script was in flight) and nothing schedules it. That is the next step, and until then it is a tool rather than a control.
