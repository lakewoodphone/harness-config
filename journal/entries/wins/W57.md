**W57 · 2026-09-14 · 2026-09-14 - P4s release valve was manufacturing the duplicates: stall reset cleared the exact-hash guard.**

**P4's mechanism: the release valve was manufacturing the duplicates it exists to prevent**

**Measured first, from the kernel's own evolution check:** *"evolution loop not closing: 72 proposals
unapplied; 38 duplicate offers on [app/services/activity_sync.py]; 1 target file(s) inside node_modules"*,
with 102 applied. Two causes, both found in the code and both fixed.

**Cause 1 — the stall reset cleared the exact-duplicate guard.** `_maybe_reset_stale_dedup()` fires when
nothing has been applied for 48 hours, which is *precisely* the stalled state P4 describes, and it cleared
all three dedup buffers:

 _instruction_hashes.clear() # exact instruction matches
 _instruction_prefixes.clear() # coarse prefix matches
 _recently_targeted.clear() # per-file cooldown

Clearing the **prefixes** is the function's legitimate purpose: they deadlock the engine, because if every
new instruction looks "similar" to recent history nothing can ever be proposed. Clearing the **exact
hashes** is not — an exactly-repeated instruction is never acceptable, however long the engine has stalled.
So a stalled loop wiped its own memory, re-proposed the same change, stalled further, and did it again:
**38 offers for one file.** The release valve manufactured the duplicates.

Fixed: keep `_instruction_hashes`, clear `_instruction_prefixes` and `_recently_targeted`. A stalled engine
may re-examine a file, but it may not repeat a proposal verbatim.

**Cause 2 — vendor trees were not excluded.** `_EVOLUTION_EXCLUDED_TARGETS` held only `app/evolution.py`
and `app/autopilot.py`, matched by **exact path**. So the engine aimed 18 duplicate proposals at
`web/node_modules/flatted/python/flatted.py` — a third-party file npm overwrites, whose change can never
survive, so it can never be "applied". That is a proposal that *cannot* count as progress, inflating the
unapplied count while looking like an engine failure. `_is_excluded_target()` now rejects vendor and
generated trees at any depth (`node_modules`, `.venv`, `site-packages`, `__pycache__`, `/dist/`, `/build/`,
`/.next/`), normalises Windows separators, and refuses an empty path; all six call sites use it.

**Verified and deployed:** 6 exclusion sites rewritten, `_instruction_hashes.clear()` confirmed gone from
the live file, 10 tests pass on the authority's own tree, `/health` 200, deployed 16:58:54Z with a backup at
`handport-evolution.py.pre`.

**What this does NOT fix, stated because the distinction is the whole point of P4.** It stops the engine
manufacturing duplicates and aiming at files it must not touch. It does **not** make proposals apply.
**72 unapplied proposals remain**, and the question of *why an applied proposal does not land* is
untouched by this change. P4 stays open: the loop now stops lying to itself about how much unique work it
has, which is a precondition for fixing the closure — not the closure.

**Worth noting for whoever takes the next step:** one commit on the authority, `cd25a430`, is titled *"fix
(evolution): make the self-improvement loop able to close at all"*. It sits on the local `master` and on
`origin/ops-evolution-loop`, and it is **not** on `origin/master`. So the one change aimed at the real
problem may itself be unapplied — which would be a fitting shape for this particular bug.
