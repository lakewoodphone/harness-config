**W6427 · 2026-10-16 · lpt-deploy-status.py: one read-only call answers can-the-website-deploy, including the DEPLOYED bundle stamp.**

**BUILT 2026-10-16: `~/bin/lpt-deploy-status.py`, the instrument that was missing.** Read-only, exit 0
whenever it could do its job (exit 2 = it could not reach GitHub, never "the deploy is broken").

WHY. Answering "can the LPT website deploy, and what is stopping it" took a whole session:
`projects.json`, the workflow file, the runner list, the run history, the secret list, the branch
head, the deploy target's `.env`, a four-machine search for a credential, and two live fetches. Every
one of those is a single API call or file read, and every future session and every woken shift would
pay the same cost again - the same fault `autonomy-status.sh` exists to prevent for the wake system.
The instrument now prints the gate, the reason, the evidence, and the next action in one call.

IT ANSWERS AN OUTCOME, NOT A LIVENESS QUESTION. "Did the workflow run" is not the question. The gate
(`CLOUDFLARE_API_TOKEN` present or not) is printed FIRST because that is what decides, and `--live`
reads the **DEPLOYED** bundle stamp off the site and compares it to the `test` head. MEASURED
2026-10-16: test serves `06ff1f45b1ee` while `test` head is `c3d0ce0fdd` - the check sees real drift,
which is what makes it a verification and not a decoration.

TWO THINGS HAD TO BE MEASURED TO MAKE IT WORK, AND NEITHER WAS GUESSABLE:
 * Cloudflare answers a default `urllib`/`curl` User-Agent with **HTTP 403** on both site hostnames.
 The fetcher must present a browser-shaped agent or it reports a site fault that does not exist.
 * the build commit lives in the **entry asset** (`/assets/index-*.js`, ~3.8 MB), NOT in the HTML
 shell - and a raw fetch of an SPA path returns the shell, which is the trap a shift recorded on
 2026-10-15 when it concluded the site was dead.

IT IS DELIBERATELY NOT A WAKE SOURCE. From 2026-10-16 the deploy is EXPECTED to be red until the owner
mints the token. A source keyed on "the last deploy failed" would file a paid wake every cooldown for
a known, owner-blocked condition - the loop manufacturing its own noise. It is an instrument for a
human or a session to read, like `autonomy-status.sh`. **Do not wire it into `run-wake-sources.sh`.**

IT CARRIES TWO DRIFT CHECKS THAT WOULD OTHERWISE FAIL SILENTLY: a workflow re-introducing
`self-hosted` runner labels (which would make a job QUEUE rather than fail), and a `runs-on` gone back
to an unpinned `-latest` (which is how GitHub's own "ubuntu-latest migrates to Ubuntu 26 on
2026-10-19" notice would have moved the deploy platform unannounced).

AND THE POINTER IS WHERE IT MATTERS: the lpt-website registry note now says to run it before
theorising about the deploy, so the next shift asks one command instead of re-deriving the chain.

CHECKED AND NOT USED, recorded so nobody grabs them: `scripts/deploy-prod-direct.mjs` and
`scripts/deploy-prod.mjs` are **Netlify** paths - the system the Cloudflare migration replaced, whose
credit allowance ran out on 2026-09-14 - and `scripts/deploy-preflight.mjs` is **Heroku**-oriented.
All three are dead and superseded; `scripts/deploy-frontend-cloudflare.mjs` is the live one.
