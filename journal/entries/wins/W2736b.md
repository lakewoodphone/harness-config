### Method - and why nothing could be lost by accident

1. **Inventory before touching anything** (`/tmp/probe-inventory.py`): classified all 5,221 by walking
 each one, recording size, file count and every credential artefact found, and wrote
 **`/root/probe-prune-manifest.json` (231 KB)** - the manifest names each directory removed, so the
 deletion is auditable after the fact rather than a `rm -rf` nobody can reconstruct.
2. **The inventory's split, which is the safety property:** 5,205 disposable, **4 carrying a credential
 artefact (`Cookies`, `Login Data For Account`)**, 12 touched within 6 hours. The 4 were kept
 outright; the 12 were kept because a probe may still be running.
3. **Prune with per-item guards, not a pattern** (`/tmp/probe-prune.py`): each path re-validated
 immediately before removal - must be a direct child of ROOT, must appear by name in the manifest's
 disposable list, must not be a symlink, must be older than the floor, and must contain **no**
 credential file. Anything failing a guard was **skipped and reported**, never worked around.
4. **Removal log: `/root/probe-prune-removed.txt` (202 KB)**, every name.

### The source fix - and why `finally` was not the answer

There *is* a `finally: shutil.rmtree(probe_dir)` at both call sites. It is not sufficient, and that is
the whole finding: **`finally` does not run when the interpreter is SIGKILLed**, and this process is
killed routinely - systemd stops, restarts, and **three OOM kills on 2026-10-11 alone**. Every kill
between `mkdtemp` and the `finally` leaked a directory permanently. Four months produced 5,221 of them,
the oldest from 2026-06-05.

A cleanup that only runs on the happy path cannot fix a leak whose cause is abnormal termination. So
the fix is `_reap_orphaned_profiles(profiles_root)` in `app/services/google_voice.py`, called
opportunistically from the probe path - idempotent, best-effort, age-ordered, and **conservative in
every direction**: an archive holding a credential artefact is **never** removed (it may be the only
source of a working session - retention for those stays with `_prune_archived_profiles`), an unreadable
archive is treated as credential-bearing, a symlink or a non-direct-child is left alone, and anything
unclassifiable is kept and logged. **A refusal, not a guess.**

**Committed `cd6ca1c1`, pushed to origin.** Service healthy - `/health` 200, `active`.

### I made three mistakes on this, each caught by a check I had built

1. **My first patch broke the file.** It replaced both probe call sites with the same 8-space
 indentation; the second is nested deeper, so the module stopped compiling with
 `IndentationError: expected an indented block`. Reverted from the backup the patch itself took, then
 re-applied preserving each site's own indentation. **The backup-before-edit is why this cost minutes
 instead of an outage.**
2. **My reaper had the age guard before the emptiness check** - so a *recent empty* probe survived, and
 that is precisely the shape a SIGKILL leaves (`mkdtemp` ran, the copy never did). The end-to-end
 test I wrote caught it: `VERDICT: FAIL - behaviour is not what the docstring promises`. Fixed, and
 the four behaviours now pass: old-without-credentials removed, old-WITH-credentials kept, recent
 kept, recent-empty removed.
3. **Two rounds of my patch script failed to match the source** because I wrote the old text from
 memory instead of reading the file. The fix was to `sed` the exact block first. **Do not author a
 patch against remembered text.**

**The general rule.** *A cleanup that only runs on the happy path does not fix a leak caused by
abnormal termination.* If a process can be SIGKILLed - and this one is, routinely - the durable fix is
an idempotent sweep with an age floor, not a tighter `finally`. And **the sweep's own safety must be a
refusal by default**: "I could not look" must never become "safe to delete".

**Left honest:** the reaper is committed but **not live** - it needs a `company-api` restart, which was
not taken (the box has been restarted three times today and a fourth was not obviously worth it). Its
live haul would have been ~20 MB, because the 6.2 GB backlog was removed by the prune. Its job is
prevention, and it will run from the next restart.
