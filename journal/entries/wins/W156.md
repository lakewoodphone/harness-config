**W156 · 2026-09-15 · The run-once endpoint can now force a sync, and a refusal names its gate.**

**W-new · 2026-09-15 · The endpoint built to run a subsystem on demand can now run the syncs, and says which gate refused when it cannot.**

| call | before | after |
|---|---|---|
| `POST /autopilot/subsystems/ebay_sync/run-once` | `{"ok":false,"error":"unknown_subsystem"}` | `{"ok":true,"ran":true,"status":"ok"}` in **16 s** |
| `POST /autopilot/subsystems/boa_sync/run-once` | same | `{"ok":false,"error":"disabled","detail":"boa_sync_enabled is False, so this sync will not run"}` |
| `ebay_sync_time` after a forced run | -- | **04:15**, unchanged |

One table (`_finance_sync_specs`) now feeds both the dispatch and the advertised `known` list, so
the drift that *was* P187 cannot recur. The enable flag and the failure breaker still apply, and a
refusal names its gate instead of returning a silent success. 5 tests.

The first attempt at this fix was wrong in a way worth recording: it cleared only the in-memory day
guard and returned `{"ran": false, "status": "ok", "detail": "eBay sync complete -- 0 new
transactions"}` -- the **previous** run's detail, quoted as if it were this one's. Each sync has
three gates (in-memory day guard, persisted `last_ran_at`, scheduled hour), and the force now
clears all three and restores them when the run did not happen, so a manual attempt cannot move the
daily schedule.
