The loop's defect was not the backlog: `applied` was its only terminal state, so a proposal could be
*neither applied nor dismissed* -- 18 offers against a vendored file the writer now refuses could never
leave the queue, and 45 were older copies of a newer identical offer. The kernel counted every unapplied
row as `queued_for_review`, so it reported 75 where the honest number is 12. Marking them applied would
have emptied the queue with a false claim in the record.

`evolution_log` now carries `status` ('open'/'applied'/'dismissed') and `status_note`, with the migration
filling existing rows from `applied` and every dismissal recording why (`1d134a90`). The kernel reads
`open` and reports `dismissed` in metrics, falling back to `applied` on a database the app has not
touched (`f515b78`). 6 new tests, 12 with the guard tests.

**The test caught a real bug in my own helper**: the first drain kept the *oldest* row of each duplicate
set because the SELECT had no ORDER BY, contradicting the docstring. Fixed, and a corrective pass swapped
the 4 inverted sets on the live rows rather than leaving a wrong note on them.
