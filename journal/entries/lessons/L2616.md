## LESSON — `output_log LIKE '%[WORK_DONE]%'` is a FALSE POSITIVE; the failure marker contains the success marker

**Measured 2026-09-28, live `secretary.db` on `secratary`, 9-day window.**

```sql
-- naive: reports a healthy company
select count(*) from work_sessions
 where started_at >= datetime('now','-9 days')
 and output_log like '%[WORK_DONE]%';
-- 693 of 735 -> 94%

-- truth
select count(*) from work_sessions
 where started_at >= datetime('now','-9 days') and status='completed';
-- 376 -> 51%
```

**Cause.** The loop's own failure marker embeds the success marker verbatim:

```
[STEP_BUDGET_EXHAUSTED: reached planned 5/5 work steps without [WORK_DONE]]
```

So every session that dies at the step budget matches a search for the completion marker.

**The rule.** Any completion metric must exclude `STEP_BUDGET_EXHAUSTED`. Correct predicate:

```sql
output_log like '%[WORK_DONE]%' and output_log not like '%STEP_BUDGET_EXHAUSTED%'
```

**Why it matters past this query.** The completion rate of this company is the number every other
judgement rests on — whether to keep the department layer, whether a model is good, whether a
workstream helped. A metric that reads 94% while the company fails half its work is the exact
"confident wrong number" class that this estate treats as its worst failure mode. I made a first
pass in this session that read 693/735 and nearly reported it as a recovery; the tail of the failing
rows is what caught it.
