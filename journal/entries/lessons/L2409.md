**L2409 · A hand-maintained version token is a silent-failure generator: derive it from the content it versions**

## L2383 · 2026-09-24 · Derive the version token; do not type it

`assets/mobile.css` opens with `phone-layer-version: <token>`, and `dsh-plugin-mobile` uses it to
decide whether an already-open tab is rendering a stale layer. The comment above it said, in
capitals, "BUMP THIS TOKEN whenever anything in the phone layer changes." It was still `2026-09-16.3`
after `assets/question-card.css` changed on 2026-09-22. The fix was deployed on the server and had
never reached the owner's phone; he reported the same bug again on 2026-09-24.

This is the second time this exact token was forgotten (2026-09-16 is why the token exists).

THE RULE. When a value is load-bearing and hand-maintained, and forgetting it produces NO error —
only a stale client and a repeated bug report — derive it from the thing it versions. It is now a
sha256 prefix of the layer bytes, recomputed on every request in `phone-gate.py`. Property to
verify: a one-byte change to any layer file changes the served token, and two calls are identical.
Both checked.

SECOND RULE, about where the fix belongs. The obvious alternative was "add a check that fails when
the content changed but the token did not", which needs a stored baseline and reports the fault
AFTER it has shipped. Deriving removes the fault instead of reporting it. Prefer making a mistake
impossible over making it loud, when the cost is the same.

THIRD RULE, about the verification that missed it three times. Cold-loading a document proves the
layer is correct; it proves NOTHING about delivery. `question-card-check.py` and the live probe both
cold-load, and both passed on the morning of the fourth report. Test the cached path too — that is
where every report came from. (See P2316.)
