**L1558 · Worktree the DEPLOYED branch, not the checked-out one: a stale base made an agent silently revert live fixes**

I created four fleet worktrees using `git rev-parse HEAD` of each repo's checked-out branch. For
personal-secretary-mvp that gave `4397f1d0` — local `master`, which is **71 commits behind `origin/master`** and
predates a day of live repairs. The agent built on that stale base, and because it rewrote `fleet_api.py` wholesale
it **reverted my DEP fixes**: `/v1/bypasscode` (real route) went back to `/v1/device/bypasscode` (404), HTTP Basic
`depserver:` auth went to 0 occurrences, and the `response_status` SUCCESS/FAILED semantics disappeared. The deployed
file still has all of them, so merging that branch as-is would have broken Activation Lock on live devices.

What saved it was measuring instead of trusting the report: I grepped the same patterns in the agent's version, in
`origin/master`, and in the deployed `/srv/fleet_api.py`. Three versions, one conflict, and it took three greps to
see it.

The rule: **a worktree base must be the branch that is DEPLOYED, not the branch that is checked out.** On this
machine several repos have a local branch far behind its remote — personal-secretary-mvp by 71 commits, lpt-hub by
2,446 — so "HEAD" is the wrong answer for anything that will be integrated or released. Check
`git rev-list --left-right --count origin/<branch>...HEAD` before creating a worktree, and branch from
`origin/<branch>`.

Corollary worth keeping: an agent that rewrites a whole file rather than editing it can silently revert fixes it
never saw. Briefs should say "edit, do not rewrite" when the file may have moved, or the base must be current.
