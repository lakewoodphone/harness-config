**L1583 · A green suite lied 3 ways: stale module copy on sys.path, CWD-dependent tests, pre-existing red tests**

Lesson, measured 2026-09-15, personal-secretary-mvp + waze-mdm/fleet-api.

Three ways a *green test suite* lied to me in one session. Each one looked like success.

1. `import fleet_api` resolved to a STALE copy on a different sys.path entry, and I read the stale copy's output as
 my own code's behaviour. A probe I ran from the repo ROOT printed `percent_used = 0.0, cap_band = 'ok'` for a
 case my edited file was supposed to answer `None / 'unknown'` — and I nearly "fixed" working code, then nearly
 reported a discrepancy that did not exist. Running the identical probe from the file's own directory printed the
 real answer. **Always verify which module you are testing**: print `fleet_api.__file__` (or the equivalent) before
 trusting any result, and re-run one probe from a second cwd when a result surprises you.

2. Tests that depend on the process CWD pass or fail depending on where pytest was invoked. Three existing tests in
 this repo read `pathlib.Path("fleet_api.py")`, so `pytest deploy/waze-mdm/fleet-api` from the repo root produced
 `FileNotFoundError` failures that had nothing to do with the code. One of them,
 `test_no_dict_row_antipattern_in_fleet_api`, silently proved nothing. Fixed with a `conftest.py` that puts the
 directory on `sys.path` and pins the CWD. A test whose verdict depends on invocation is worse than no test,
 because it is counted.

3. Pre-existing red tests are information, not noise to be silenced. `test_fleet_monitor.py` had three failures on
 master asserting `fleet_api._strip_alert_marker` — a function that DID NOT EXIST. That is a bug report sitting in
 the suite, not a stale assertion: the consequence was alert messages reaching the staff UI still carrying their
 internal `[stale_crit:44]` de-duplication marker. Before "updating" a red assertion to match current behaviour,
 read it as a claim about intended behaviour and check which side is wrong. (Contrast: `_raise_alert`'s 2-tuple
 assertion WAS a stale assertion, correctly updated to 3 because the contract deliberately changed — the
 difference is whether the old behaviour was a bug.)

Corollary for the "prove it fails before, passes after" requirement: `git stash` is the wrong tool (see the other
lesson); a patch file or a copy outside git's reach is the right one.
