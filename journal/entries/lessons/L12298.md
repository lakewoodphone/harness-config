**L12298 · Caddy's passive health check is the only safe one on a single upstream, and a scratch container on the running image proves a log format before it ships**

Caddy's PASSIVE health check is the one you want on a SINGLE upstream, and `fail_duration` is the switch that turns it on. Restoring a health check without the outage amplifier is four lines, and I proved the log format end to end in a scratch container instead of shipping a config I had only read.

WORKED 2026-10-23 on ZABZ-YOGA (pwsh, Windows) in C:\Users\ezabz\Code\_pt-inst, branch fix/instrument-the-502, commit ba4e37c off 274f695. Three changes, no product logic, no gate, no scoring file.

1) PASSIVE HEALTH CHECK. `reverse_proxy` docs: "`fail_duration` is a duration value that defines how long to remember a failed request. A duration >0 enables passive health checking; the default is 0 (off)." `max_fails` default 1. `unhealthy_latency` and `unhealthy_status` are UNSET by default, which is the whole point: with them unset nothing inspects how long a request takes, so a 17.0 s report synthesis cannot be counted as a failure, and there is no periodic probe at all to fire mid-synthesis. That is the answer to the defect in L12272 / 19b053d: an ACTIVE probe on a single upstream is an outage amplifier whatever its interval, because there is no second upstream to carry traffic; passive checking only ever learns from a request that really failed. I chose `fail_duration 5s` / `max_fails 2`: two visitors must already have failed before the upstream is marked down, and the 503 window is then bounded at 5 s, against the 60 s ceiling L12272 measured. State the tradeoff honestly: for ONE upstream this does not remove restart errors, it bounds and labels them (a bodiless 503 meaning "the edge knows" instead of a per-request 502).

2) WHERE CADDY LOGS GO ON THIS BOX. `docker inspect caddy` shows exactly three mounts: /etc/caddy/Caddyfile (ro), caddy_data, caddy_config. THERE IS NO LOG VOLUME, so `output file /var/log/...` lands in the container's WRITABLE LAYER — dies on the next `--force-recreate`, unrotated. `output stdout` goes to Docker's json-file log on the host and is read with the same `docker logs caddy` the five retained 502s came from. Check mounts before choosing a log path; the repo's Caddyfile had no `log` directive anywhere to copy a pattern from, which is why the rate was never measurable in the first place.

3) `log_append` IS SAFE FOR REQUEST-SCOPED PLACEHOLDERS. modules/caddyhttp/logging/logappend.go: `ServeHTTP` calls `addLogField` on the way BACK UP the chain unless `early` is set, and the placeholder is documented as "evaluated when the log is written". So `{http.reverse_proxy.upstream.hostport}` fills in even if the directive sorts ahead of `reverse_proxy`. No `Early` needed. Confirmed empirically: the emitted line carried `"upstream_hostport":"personality-test:3000"`.

4) THE TECHNIQUE WORTH KEEPING: prove an edge config's OUTPUT without touching the live edge. I ran a second container from the SAME image ID as the running Caddy (`docker inspect caddy --format "{{.Image}}"`), on the same docker network, config bind-mounted from /tmp, port published only on 127.0.0.1:18080, proxying one real request to the live app, then read `docker logs`. The default image CMD runs `caddy run --config /etc/caddy/Caddyfile --adapter caddyfile`, so no command is needed. Cost: about 20 s and no risk to live traffic. This turned "the format should record X" into the literal line: `"method":"POST","uri":"/api/assess","Content-Length":["26"],"bytes_read":26,"size":66,"status":401,"duration":0.010705523,"upstream_hostport":"personality-test:3000"`.
 Two traps in that trick: `docker inspect --format "{{range $k,$v := .NetworkSettings.Networks}}{{$k}}{{end}}"` CONCATENATES every network name with no separator (it produced "caddy_defaultlpt_defaultpersonality-test_default" and `docker run` failed) — name the network directly; and the image's adapt/validate run will log a health-checker line for OTHER vhosts (I saw one for lpt_filter_ai_api_b:8443) that is an artifact of the checker being torn down at the end of validate, NOT evidence that broker is down.
 Also verify the parsed config, not just the text: `caddy adapt --adapter caddyfile` and grep the JSON for the handlers. "Valid configuration" proves syntax; adapt proves the directive became a handler and did not land in a comment.

5) THE ROUTE LINE. One `console.warn` as the FIRST statement of `POST`, before the session read: `[assess] request arrived: <method> <path> content-length=<declared|absent> body-read=<request.bodyUsed>`. The diagnostic contract from the diagnosis holds: a 502 with no such line never reached the route (edge/socket death); a line with nothing after it means it arrived and died inside the handler. Wrap the `new URL(request.url).pathname` in a try/catch — the line exists to survive a dying request, so it must not itself be the statement that throws. Carries no body, token, cookie or participant text.
