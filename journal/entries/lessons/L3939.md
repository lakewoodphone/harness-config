## LESSON — `Restart=always` cannot restart a process that never exits; a wedged-but-alive service had no owner

**Evidence** 2026-10-14, secratary-cloud. `company-api.service` (Restart=always, RestartSec=10) was
`active (running)` from 16:05:51Z while **every** route timed out — `/health`, `/ready`,
`/openapi.json`, `/favicon.ico` — for 73 minutes. Proved before touching it: cgroup
`memory.current` 5.12 GB with `file 0`; one thread in kernel state `D` in
`mem_cgroup_handle_over_high`; journald's last line 16:05:51Z; `/proc/<pid>/status` VmRSS 5,063,908 kB
/ VmSwap 2,093,488 kB, 40 threads. A survey of `/usr/local/bin`, `/root/bin`, `/opt/*/bin` and both
crontabs found **nothing anywhere that restarts a unit on a health failure** — the only
`systemctl restart` references were inside a comment and in the vendor `cloudflared` binary. The
owner learned about it from a text message; the operator learned about it from the owner.

**The rule:** for every long-running service, ask "who restarts it if it is alive and answering
nothing?" If the answer is "nobody", the monitoring is decorative. Build the answer BEFORE the
monitor, or the monitor will just be telling a human about a machine's job.

**The fix shipped in the same session:** `/usr/local/bin/company-api-liveness.sh` +
`company-api-liveness.{service,timer}`, probing `http://127.0.0.1:8002/health` every 2 minutes and
restarting `company-api.service` after 3 consecutive bad probes (~6 minutes), with a 30-minute
cooldown, a 6-per-24h loop brake (then backoff to hourly + a `NEEDS_HUMAN` marker), a skip when the
unit is not `active`+`running` (systemd owns that case), and a 5-minute minimum process age so a
booting API is not called dead. It sends nothing to the owner.
**Verified by 5 self-tests against a throwaway unit, not by argument:** a failing probe restarted it
(pid changed); a healthy probe caused no log line and no restart; an inactive unit was skipped with
rc=3; with FAIL_THRESHOLD=3 the restart happened on the **3rd** consecutive failure and not before
(rc=3,3,0); and the cooldown suppressed the next restart with rc=3. **NOT verified:** that it catches
a genuine kernel-level freeze of the real API — proving that would mean deliberately wedging
production, so the honest claim is "the probe→count→restart state machine is proven; the real
freeze behaviour is argued from the identical probe path".
