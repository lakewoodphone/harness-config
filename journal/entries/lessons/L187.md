**L187 · An overlay that restates a config deletes every key it does not restate**

**2026-09-14 · secratary.** `dsh-web-app`'s own bundle patch says it in as many words — "A patch
replaces the targeted row's whole `config`, so each row below restates every key it owns" — and
`harness-config/profiles/web/cordis.patch.yml` broke exactly that rule. It restated the
`connection` row's `config` to add the reconnect policy, and the row it replaced carried
`trustedHosts: !!js ctx.webRuntime.trustedHosts`, which is where `--trusted-host` lands and the
**only** input to the `/api` browser-trust fence.

**Measured: two scratch engines, same build, same flags, one file different.**
`POST /api/agentPresets/list` with `Host: secratary.tail93e6e6.ts.net` returned **403 forbidden**
with the patch and **401 unauthorized** without it. 401 is correct — the fence passed and only the
cookie was missing. The authenticated round trip through the fixed engine then returned 200.

**Why it hid for three days.** The fence trusts a **loopback** Host by construction, and every
workstation browser uses one, so on a desktop the missing key changes nothing. It bites only where
the browser reaches the engine at the deployment's own name, which is the phone. The symptom was
maximally misleading in the other direction too: **documents served** (the index route is not
fenced) while every `/api` call and the WebSocket upgrade were refused — the page loaded, and was a
shell.

**The rule.** When an overlay restates a config, it owns every key in it: read the row being
replaced and carry forward anything not deliberately deleted. And when the same code works on one
machine and not another, look for the **layer that differs by machine** before blaming the feature.
Corrects **L152b**, which concluded the refusal came from no plugin — true, but it stopped one layer
too early and never named our own profile patch.
