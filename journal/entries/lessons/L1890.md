**L1890 · A tRPC hooks client has no .query(): ~14 frontend reads never executed, and graceful error handling hid it**

**Recorded 2026-09-17. Found while fixing the FAQ fetch on the LPT storefront; measured, not inferred.**

`frontend/src/lib/trpc.ts` exports TWO clients:

- `trpc` (line 55) = `createTRPCReact<AppRouter>()` - the **hooks** client. It exposes `useQuery`,
 `useMutation`, `useUtils`, `Provider`. It does **not** have `.query()`.
- `vanillaTrpcClient` (line 462) = `createTRPCProxyClient<AppRouter>({...})` - the **imperative** proxy, which
 is what `.query()` / `.mutate()` belong to.

**~14 call sites invoke `.query()` on the HOOKS client**, which throws at runtime:

```
TypeError: e[i] is not a function
 at Object.apply (<bundle>:84:36880)
 at queryFn (<bundle>:825:127282)
```

The proxy does `let i = r.pop(); ... return e[i](r, a, s)` - and `e[i]` is undefined, because a hooks client
has no such method. **The request is never sent**: no entry appears in the browser network log at all. This is
not an HTTP failure, a CORS failure or a 400 - it dies in JavaScript before the network layer.

Examples found: `features/faq/hooks/useFaqs.ts` (now fixed), `components/orders/CustomerOrderHistory.tsx`,
`components/orders/OrderTimeline.tsx`, `components/payments/TransactionHistoryTab.tsx`,
`components/customer-notes/CustomerNotes.tsx`, `components/customer-notes/CustomerActivityTimeline.tsx`,
`features/admin/faq/hooks/useAdminFaqs.ts`, `features/customers/pages/CustomersPage.tsx`,
`components/inventory/components/ProductEditModal.tsx`, several under `__archived__/`.

**What this explains, and it is the important part:** the LPT customer portal has a documented history of
"failed reads" and pages rendering as if data were absent. An earlier session produced a whole branch titled
`fix/portal-ui-robustness` whose commits say *"stop failed reads rendering as fact; stop 4xx retries burning
rate limits"*. The cause is not a flaky API and not a 4xx - **the calls were never made**. Any fix that handled
errors more gracefully would have left the root cause untouched, and retries "burning rate limits" is
impossible if no request goes out.

**The FAQ case is the proof:** the homepage's FAQ list could never load in any build. Every failure was
swallowed by a catch block that returned hardcoded mock data - which is how an invented street address
("123 Main Street ... Highway 99 ... blue storefront") came to be published on the live homepage next to the
real address, where it sat undetected. After fixing BOTH the wrong client AND the missing argument, the live
page renders 28 real published questions with zero console errors.

**The generalisable rule:** a build can be green, the API can be healthy, and a page can render plausible
content while the fetch has *never once executed*. The way to catch that class is to open the real page and
read the network log - not to read code, and not to trust that a fallback rendering looks fine. **A fallback
that produces believable content is a silent failure generator.**
