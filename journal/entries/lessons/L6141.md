**L6141 · The authority's backup is healthy - and the script that reports its age could tell the vault a lie**

2026-10-13. Went to verify the authority's backup, twice thought it was missing, and was wrong both times
- then found a real defect that could make the estate's own backup reading false.

FIRST, THE INTEGRITY CHECK MY LIVENESS TOOL FLAGGED. `db-integrity-check` (weekly, Sunday 04:17) has no
run recorded, and the reason is in its own log:
 04:46 FAILED TO CHECK - not enough free space for a consistent copy: 8.9 GiB free, 33.6 GiB required
 05:49 ok - /root/authority.db answered 'ok' in 703.3s (25488613376 bytes) [live-readonly(in-place)]
**So the authoritative database is NOT corrupt - 25.5 GB answered `ok`** - and it was checked by reading
the live database read-only in place under the shared I/O lock, bounded to 1800 s. The copy-based path can
NEVER work here: the database is 23.7 GiB and the gate needs 1.25x plus a 4 GiB margin on a 75 GB volume
that is 90 per cent full. `DB_INTEGRITY_ALLOW_INPLACE` defaults to 1 and the script was updated at 05:49
today, so the next weekly slot will now succeed rather than refuse.

SECOND, `prune-backups rc=4`. Its log: "FLOOR BREACHED - only 8057340 KB free on the backup volume (floor
12582912 KB). Pruned NOTHING ... 0 entry/entries present." **Zero local backups and below the floor** - which
looks alarming until you ask where the backups actually are.

THIRD, MY TWO WRONG ANSWERS, each caught by checking rather than reporting.
 (a) "The authority has no backup." FALSE. `authority-data-offsite.timer` had run 33 minutes earlier and
 `authority-offsite-backup.timer` 1 h 45 m earlier, both Finished. The monitor I first read,
 `monitor-hetzner-backups`, watches TWO OTHER BOXES - waze-mdm-01 and lpt-apps-01 - both reporting
 "all backups fresh"; it says nothing about the authority, which is why I could not find the answer
 in it.
 (b) "The offsite age report is broken - no boto3." FALSE as a scheduled job. The systemd unit sets
 Environment=VENV_PY=/usr/bin/python3, which HAS boto3 1.40.72, and the service runs every 30
 minutes, Finished and Deactivated successfully.

AND THE REAL DEFECT, which (b) exposed. The SCRIPT's own default is
`VENV_PY=$HOME/personal-secretary-mvp/.venv/bin/python`, and that venv has NO boto3. So the scheduled run
works only because of the systemd override, and a hand-run fails - **not quietly, but by reporting
`{"key": "authority/secretary.db.gz", "error": "no boto3"}` TO THE VAULT, overwriting a true reading of
the backup's age with a false one.** My own hand-run did exactly that before I saw it. The default now
tests each candidate interpreter for boto3 and picks one that works.

VERIFIED, and it produced the figure nobody had: with a working interpreter the vault now holds
 {"key": "authority/secretary.db.gz", "bytes": 6800010637, "last_modified": "2026-10-13T05:41:08+00:00"}
**A 6.8 GB offsite object, 1.5 hours old. The backup is real and fresh.** So the honest position is that
the authority's data is protected, the integrity check will pass weekly, and the thing that was actually
broken was the reporting path - which is the same shape as everything else tonight, and this time it was
the reading that was false rather than missing.
