**L1674 · A phone system's business-hours setting may be a ring policy, not the business's hours**

## L-new — A phone system's "business hours" setting may be a ring policy, not the business's hours. Read the routing chain before you "correct" it.

Measured 2026-09-15 23:20 UTC by reading the LIVE Dialpad office group with the stored UI auth headers
(`scripts/dialpad_ivr_admin.py backup` on ZABZ-TECH; captured headers dated 2026-09-01).

The live hours table for the LPT main line is:

| Day | Value |
|---|---|
| Mon–Thu | `00:00–01:00` **and** `09:30–23:55` |
| Fri | `09:30–18:00` |
| Sat | `21:00–23:55` |
| Sun | `00:00–01:00` **and** `09:30–23:55` |

The shop's actual walk-in hours are Mon/Tue/Thu 10:30–17:30, Fri 10:30–13:00, Wednesday and Saturday
unstaffed. `first_action: operators`, `no_operators_action: scripted_ivr`. So the 24/7-ish window is
**deliberate**: it keeps the line "open" so `first_action` rings operators, and each user's Personal
Working Hours decide who actually rings. The shop's hours are not encoded in that table at all.

The trap this creates: the obvious "fix" — set Wednesday to closed so callers are told the shop is shut —
would instead stop every Wednesday call from ringing anyone and dump all of them straight into the
"we're closed" script. A plan written from the docs alone (`docs/operations/dialpad-ivr-audio.md:23`,
`dialpad-after-hours-bachrach-plan-2026-09-06.md:32`) would have made exactly that mistake; every one of
those docs states the shop's hours as Dialpad's hours.

RULE: before changing a telephony hours/schedule setting, read the whole routing chain
(`first_action`, `no_operators_action`, both route targets and their DTMF maps, and every user's Personal
Working Hours) and work out which element actually decides what the caller experiences. The setting whose
NAME matches the fact you are changing is often not the setting that CARRIES it.

Corollary, and it is the same lesson as the audio one: an undocumented live configuration is worse than a
wrong one, because nothing in the record contradicts it. Nothing in the repo, the docs or the journal
mentioned this window.
