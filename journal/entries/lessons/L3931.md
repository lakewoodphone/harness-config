**L3931 · git commit and git push in one shell prints 'Everything up-to-date' while the commit is still being written**

# `git commit && git push` in one shell prints "Everything up-to-date" while the commit is still being written

Hit twice on 2026-10-14, in the same session, on the same repository.

## The shape

A pre-commit hook that takes a few seconds — here `scripts/audit-phantom-deps.mjs`, run by `github`'s
hook wiring — plus a `git push` issued in the same command means the push can be evaluated **before the
commit object exists on the branch**. `git push` then finds nothing to send and reports:

```
🔍 Checking for phantom dependencies...
> phone-and-tech@1.0.0 audit:phantom C:\Users\ezabz\code\_wt-notify
Everything up-to-date
```

`Everything up-to-date` is the *success* message for a push that sent nothing. It reads as confirmation
and it is not one. The commit was present locally, the remote was one commit behind, and the only
reason it was caught is that the remote SHA was checked afterwards:

```
git rev-parse HEAD -> 6d29446f79d3ed6...
git rev-parse origin/lpt/dialpad-sms-send-path-20261014 -> 32b006ea3e2a7e4... # behind
```

## What to do

1. **Separate the two.** Commit as one call, verify `git log --oneline -1` shows it, and push as another.
2. **After any push, read the remote back**: `git fetch origin && git rev-parse origin/<branch>`, and
 compare it with `git rev-parse HEAD`. A push is a claim; the remote SHA is the evidence.
3. **`Everything up-to-date` is not success.** It means "the remote already has what I was asked to
 send" — which is only reassuring if you know what you asked it to send.

## Why this is worth a journal entry for two occurrences

The estate's most common failure is `wrong-data`: reporting something that was not true. This is a
mechanism that manufactures exactly that — **a success message that is not evidence of the thing
succeeding** — and it is invisible unless the remote is read back. It bites hardest on a machine where
hooks are slow (Windows, a monorepo, an audit script), which is precisely where a session is likely to
be batching commands to save process start-up.

The general rule, same as everywhere else in this tree: **the tool's own message is not the result. The
read-back is the result.**
