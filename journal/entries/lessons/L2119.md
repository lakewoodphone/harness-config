**L2119 · L2102 - a rate limiter whose state lives only in RAM is not a rate limiter**

Measured 2026-09-20 on the authority. `owner_message_queue` held **64 `sync_breaker:ebay_sync` and
63 `sync_breaker:amazon_sync` rows in 7 days** (166 and 165 in 30) - 127 of ~196 rows in a week from
two failing syncs. The code that emits them has a debounce:

 _SYNC_BREAKER_THRESHOLD = 5
 now_m = time.monotonic()
 last = getattr(self, "_last_sync_breaker_alert_at", {})
 if last.get(name) and (now_m - last[name]) < 24 * 3600:
 return

That is a correct 24-hour per-subsystem window. It is held in an **instance attribute**, and the
service was restarting roughly thirteen times a day - systemd SIGKILLing it at a 90 s stop timeout
while the app needed minutes to boot and shut down. Every restart emptied the dict, so the limiter
fired again on the next tick.

**Rule: a rate limiter, a debounce, a cooldown or a "already alerted" flag must be persisted if the
process can restart for any reason.** In-memory state is a binding to the lifetime of a process you
do not control. The symptom looks like "the debounce is broken" but the code is fine; the *substrate*
is wrong.

Fix: the timestamp now lives in `settings_overrides` (an existing generic key/value table, so no
schema change) via `upsert_settings_override` / `list_settings_overrides_entries`, with the in-memory
dict kept as a degraded fallback if the store is unreadable - a store problem must not degrade into
unbounded paging.

While fixing this, the same session found the identical shape one file over: `identity_store._save`
leaked 299 temp files and 6.8 GB because a cleanup path only ran on success (L2098). **The same
instance attribute was also the direct cause of a 90-minute debugging detour in this very session: I
replaced an in-memory debounce, then broke it by referencing a class constant off an instance.**
