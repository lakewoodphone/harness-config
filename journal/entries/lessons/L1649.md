**L1649 · Path code written for one platform is silently wrong on the other -- a wrong path compares unequal, it does not raise**

**Path code written for one platform is wrong on the other -- and it fails silently.**

Measured 2026-09-15, twice in one hour, in two components:

1. **URI decoding.** `_decode_folder_uri` stripped `file:///` (taking the leading slash) and replaced
 `/` with `\`. On the Linux authority every workspace path became `home\zabz\code\...`. No error, no
 warning: the extractor produced a populated-looking list whose `folder_path` matched nothing. This
 is the shape to watch for -- **a wrong path is not an exception, it is a string that quietly
 compares unequal.**
2. **Segment splitting.** `Path.parts` on POSIX gives one part for `C:\Users\...\AppData\...`, so a
 rule that looks for an `appdata` segment never fires. The guard still blocked (a different rule
 caught it), which is luck: the rule meant to protect that directory was inert.

Rules:
- **Split paths on both separators when the input may come from another platform; never rely on
 `Path.parts` for a foreign path.** `re.split(r"[\\/]+", str(path))` costs nothing and behaves on
 every host.
- **A path bug is silent.** It will not raise; it will produce a string that matches nothing. So a
 component whose output is a path needs a test that asserts equality against a real path on this
 host -- which is exactly what the vscode test did, and why it was failing.
- **Never edit a file with a regex without a syntax check in the same breath.** I replaced an
 assertion inside a multi-line `assert (...)` and broke collection; `git checkout --` restored it and
 I re-measured. The rule is: patch structurally, compile immediately, and if a file has to be
 restored, restore it rather than patching the patch.
