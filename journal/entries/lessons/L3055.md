**L3055 · The archive's own index maintenance was the lock that stopped the archive: an UNINDEXED FTS5 DELETE held the SQLite write lock for 63 s**

MEASURED 2026-09-29 on the authority (`secratary`), while `check-dsh-freshness.py` reported
`secratary: local session newer than the last shipment by 326 min - the shipper is not sending`.

The shipper was running every 30 minutes and heartbeating. It was not broken. The authority's DSH
ingest (`app/services/dsh_session_ingest.py`) could not acquire the SQLite write lock:
`BEGIN IMMEDIATE` raised `database is locked`, the 95 s ingest budget expired, the endpoint returned
500, the shipper's batch was REFUSED, and the fail-closed cursor did not advance - so `849b9be9`
(and one new row in `88acd0f6`) stayed only on that machine.

WHY THE LOCK WAS HELD. Every changed session is re-indexed with
`DELETE FROM dsh_session_events_fts WHERE source_machine = ? AND session_id = ?`, inside that
session's write transaction. `source_machine` and `session_id` are declared `UNINDEXED`, so FTS5
answers that predicate by scanning the whole 905,692-document virtual table. Measured on the live
13 GB database: **63.6 s** for the vtab predicate (and >90 s under load) versus **1.7 s** for the
identical predicate against the FTS5 content shadow table (`dsh_session_events_fts_content`, columns
`id,c0,c1,c2,c3`). For that minute the write lock was held continuously - `/proc/locks` showed a
POSIX WRITE lock on `secretary.db-shm` owned by the API process itself - so every other writer got
`database is locked`: the dialpad harvest's runs went 36 s -> 118 s, autopilot and memory lost rows,
and the next ingest could not even begin. The archive was being starved by its own index.

THE FIX. Delete by shadow rowid:
`DELETE FROM dsh_session_events_fts WHERE rowid IN (SELECT id FROM dsh_session_events_fts_content WHERE c0=? AND c1=?)`.
Same documents, same meaning, ~37x cheaper. Deployed to the authority and the API restarted;
committed as `020a4da1` (authority `master`) and pushed as branch
`fix/dsh-ingest-fts-scan-20260929`. FTS held exactly: `dsh_session_events`,
`dsh_session_events_fts_docsize` and `dsh_session_events_fts_content` all read **909681**.

PROOF. Before: `secratary` 214 sessions / `MAX(updated_at)=2026-09-28T22:35:41Z`, `849b9be9` absent
from `dsh_sessions`. After the fix the scheduled shipper delivered: 216 sessions,
`MAX(updated_at)=2026-09-29T04:22:20Z`, and `849b9be9-3a90-4f6b-a89a-e80bd161571b` present with 869
rows; `dsh_session_events` moved 909455 -> 909681. `check-dsh-freshness.py` now exits 0 with
`secratary newest local work is 0 min from shipment`.

RULES.
1. An index that is not indexed is a full scan. `UNINDEXED` in an FTS5 declaration is a promise about
   search, not about the cost of a `WHERE` the ingest writes.
2. Measure the write-lock HOLD, not the statement's row count. The offending DELETE touched one
   session's documents; it cost 63 s because of what it had to scan to find them.
3. `database is locked` printed by many unrelated services is one writer's long transaction, not many
   slow ones. `/proc/locks` on `<db>-shm` names the holder in one line.
4. The freshness alarm was right. The finding was real; only its name ("the shipper is not sending")
   pointed at the wrong half of the pipe. Read the endpoint's own error before blaming the sender.
