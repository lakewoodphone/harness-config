**L12267 · CORRECTION to L12262: the 615196187 PTT fix was LP&T Keys 4.0.0->4.2.0, not the package disable**

CORRECTION to L12262. That entry says the PTT fix on E4610 615196187 was "grant WRITE_SECURE_SETTINGS then pm disable-user pushtotalkplus". The grant was necessary but it was NOT the fix. The customer came back with the same fault.

ACTUAL ROOT CAUSE
The handset was running LP&T Keys (com.android.cts.keysminimal) vc4 / 4.0.0, built 2026-03-13. That build declares NO com.kodiak.intent.action.PTT_BUTTON receiver — only BootCompletedReceiver and MinimalService. PTT+ was therefore the ONLY listener for the side button's broadcast, at mPriority=1000000. Disabling PTT+ does not hand the button to us; it removes the only listener. No package-disable could ever have fixed this phone.

Proof measured on the handset:
- vc4: `PTT_BUTTON in dumpsys package com.android.cts.keysminimal` = NO
- after deploying vc6 / 4.2.0: Receiver Resolver Table shows
 com.kodiak.intent.action.PTT_BUTTON -> com.android.cts.keysminimal/.PttButtonReceiver, mPriority=2147483647

THE FIX THAT ACTUALLY SHIPPED
Run the normal customer flow, which installs LP&T Keys 4.2.0 as part of staging:
 .\scripts\deployment\ready-e4610.ps1 -DeviceSerial 615196187
 # stops at step 4/5 on a handset whose Tech Mode recovery was never set up:
 # Tech Mode status did not prove recovery: 'Device Admin: Disabled Accessibility: Disabled ...'
 # then, once those are fixed:
 .\scripts\deployment\finalize-e4610-standard.ps1 -DeviceSerial 615196187 -VoiceAccessVerified -RecoveryVerified
Finalize returned exit 0: all 10 phases success, verify 17 checks passed, security phase applied.

TWO PREREQUISITES THIS HANDSET WAS MISSING (both needed by ready-e4610's Tech Mode proof)
 adb shell dpm set-active-admin com.android.cts.techmode/.LptDeviceAdminReceiver
 # Device Admin was Disabled on this unit; dumpsys device_policy listed no admins at all.
 # Then append Tech Mode's service to the existing list, never replace it:
 # ...matvt MouseEventService:voiceaccess JustSpeakService:keysminimal MinimalService
 # :com.android.cts.techmode/com.android.cts.techmode.LptAccessibilityService
 adb shell settings put secure accessibility_enabled 1
After both: status_text read back 'Device Admin: Enabled / Accessibility: Enabled / Technician Window: Active'.

CLASH CHECK (asked before re-deploy; it is clean and worth repeating)
Compare repo APK versionCode against installed for every cli/configs/apps/*.yaml entry before re-deploying onto a phone that already has apps. Zero downgrades on this handset, so installer.py's _recover_from_update_incompatible uninstall path could not fire. Everything was equal-versionCode in-place update (firstInstallTime stayed 2026-03-13) except keysminimal 4 to 6 and wazelauncher 4 to 2026030201. A downgrade or a cert mismatch is the only way that path removes an app.

POST-FINALIZE VERIFICATION IS IMPOSSIBLE WITHOUT TECH MODE
The security phase initialises USB protection and the handset leaves ADB. All post-finalize reads returned 'device not found'. Do not report a post-finalize state that was not read. To re-verify, unlock Tech Mode first (code from IMEI + install id) and then read. The physical side-button press is the only proof of PTT routing and it needs a human finger.
