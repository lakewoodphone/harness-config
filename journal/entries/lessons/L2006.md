**L2006 · The stage/finalize release leak: ready-e4610.ps1 does the whole job in one command**

Context: pain P256 ("the stage/finalize split has no release gate, so a half-hardened phone left the
shop") recurred the next day — E4610 615291677 was staged 2026-09-18, its finalize died mid-run when
the handset dropped off USB, and it was handed to the customer before the tail ran.

Fix shipped: `scripts/deployment/ready-e4610.ps1` (commit b831f5e0, lpt-flip-phone). One command that
composes what the operator was expected to do in two sittings:
 preflight (DCS, unknown sources, awake) -> `stage-e4610-standard.ps1` -> scripted manual steps over
 ADB (MatVT Override Activation Key = 17 via tap/uiautomator; Voice Access pref_show_fab asserted)
 -> Tech Mode recovery proof (launch MainActivity, require "Device Admin: Enabled" and
 "Accessibility: Enabled" in its status text) -> `finalize-e4610-standard.ps1 -VoiceAccessVerified
 -RecoveryVerified` -> prints READY.
It fails closed: any failed step throws with the reason, and `-SkipFinalize` explicitly says the phone
is not releasable. Every phase is idempotent, so re-running after a device drop is safe.

Why this is the right shape (and what is still missing):
- The two-phase split existed because the manual steps were believed to be hand-only. That is no longer
 true (see the sibling lesson: injected taps reach the E4610 view tree, and `uiautomator dump` gives
 exact bounds), so the pause no longer has to be an operator decision at all.
- Still missing from P256's fix list: a machine-readable "staged, not finalized" marker plus a shop
 check that lists such handsets (`lpt history --pending`-style). The wrapper removes the *need* for
 that check; it does not *forbid* running stage-* alone. P256 stays open until that or until the shop
 habit is demonstrably the wrapper.
- Also worth fixing in the engine: a device that vanishes mid-finalize currently surfaces as an
 adbutils traceback out of `bloatware._get_disabled_packages`, with no partial receipt and no
 "device lost" verdict naming which phases completed.

Verification available without a phone: `ready-e4610.ps1 -SelfTest` runs the XML parsing and bounds
maths against saved dumps from the 2026-09-18 handset and exits 0/1. It caught a real bug on the first
run (PowerShell concatenated the bounds digits as strings, so the tap point came out 7612,106118) —
evidence that a cheap self-test against real captured data is worth writing before the next handset.
