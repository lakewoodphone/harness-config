# The LPT read path was broken by a one-word asymmetry, and the installer lied about deploying

Measured 2026-10-14 on ZABZ-YOGA. Two independent defects, both of which made `lpt doctor` report
the shop's live store **DOWN** on a laptop that reaches it fine. Journal H3659 recorded the symptom
as a loose end and attributed it to "transport.py's hop" — the symptom was right, the cause was not
either of the two things actually wrong.

## Defect 1 — the read path and the write path disagreed about which python is "the" python

`lpt_ops/transport.py` hardcoded `python3` for the authority-side read helper:

 cmd = f"python3 {helper} --store operational --sql-b64 {payload}"

On `secratary-cloud` that is the **system** interpreter, and it has **no psycopg2**. So every read
died with `ModuleNotFoundError: No module named 'psycopg2'` — while `lpt-write` worked perfectly,
because `writes.py` has always used the app's venv interpreter (`APP_PYTHON =
/home/zabz/personal-secretary-mvp/.venv/bin/python3`, Python 3.14, which does have psycopg2).

**The asymmetry was the bug.** The two halves of one tool disagreed, and the failing half reported
itself as a store being down. It looked like a network or credential fault; it was an interpreter
choice. Note the authority's venv `python3` is a *symlink to `/usr/bin/python3`* and still has the
venv's packages — a venv resolves `sys.prefix` from `pyvenv.cfg` beside the symlink. Do not conclude
from the symlink that a venv is empty.

**Fix** (lpt-ops `07a84cb`, branch `fix/lpt-read-path-and-install-tilde-20261014`, pushed):
`AUTHORITY_PYTHON` env-overridable constant defaulting to the app venv path, used by
`_via_authority`, and the route string now **names the interpreter** so a reading carries the fact.
Deliberately **no** silent fallback to `python3` — that is the configuration this replaced.

## Defect 2 — a quoted tilde does not expand, so the installer deployed to a directory named `~`

`install.ps1` defaults the remote dir to `~/lpt-ops/lpt_ops` but **quotes every path in its remote
commands**. The sha probe ran `if [ -f '~/lpt-ops/lpt_ops/remote_sql.py' ]`; a tilde inside quotes
does not expand, so it tested a literal directory named `~`, reported `MISSING`, and the deploy
happily wrote the helper to **`/root/~/lpt-ops/lpt_ops/remote_sql.py`** while printing
`helper: deployed`. The installer said it had deployed and had not — on a fresh machine the read
path would never have worked and the installer would have reported success.

**Fix:** resolve `$HOME` on the authority once and use an absolute path; refuse with a reason if it
cannot be read. Verified: now prints `remote dir resolved to /root/lpt-ops/lpt_ops`, correctly
reports `helper already identical (sha256 c960ade8...)`, and `doctor` PROVES both stores reachable.

**Consequence to know about:** the accidental `/root/~/lpt-ops/lpt_ops/remote_sql.py` still exists on
the authority — a ~4 KB duplicate of the real helper at a misleading path. Nothing reads it. It was
not removed because deleting on the authority needs the owner's explicit word; **remove it with his
yes.**

## Defect 3 (found while fixing, minor) — the read helper's own SELECT guard

`remote_sql.py` on the authority refuses any statement whose first characters are not
`select`/`with`, and separately refuses anything containing the word `comment`. A statement with a
leading `--` header comment — the natural way to document a query — is rejected as "not a SELECT",
and any note explaining the query trips the keyword blocklist. Both err toward **refusal**, so they
are safe, but they make well-documented SQL impossible to run. Workaround: put the explanation
**after** the query, and never write the word `comment`. A durable fix would parse past comments.

## The transferable rule

When one half of a tool works and the other half of the same tool does not, **the difference between
the two halves is the bug** — not the network, not the credentials. Compare the working code path to
the failing one line by line before measuring anything else. And an installer's "deployed" is a
claim, not evidence: verify the artefact at the path the *consumer* reads, not the path the
installer says it wrote.
