## L1558 - In PowerShell, a piped native command's output becomes TEXT - so `tar czf - | ssh` destroys the archive

**What happened, 2026-09-15.** My first deploy script synced the app with
`$tar = tar czf - @files; $tar | ssh box "tar xzf - -C /opt/..."`. The remote side answered
`gzip: stdin: not in gzip format / tar: Child returned status 1 / Error is not recoverable`. Nothing
was written to the box (verified: 0 files modified in 20 minutes), so no damage - but the script
printed `OK synced 12 paths` and carried on to build, because I checked `$LASTEXITCODE` of `tar`
(the archive did build locally) and never checked the remote extract. The build then failed for an
unrelated-looking reason and the drift check was the only thing that revealed the box still had the
old source.

**The rule.** PowerShell converts a native command's stdout to `[string]` when it is captured or
piped, so binary output through a PS pipeline is corrupted. Never pipe a native command's binary
output into another process from PowerShell. Create the file, then copy the file:
`& tar czf $tmp @files; scp $tmp box:/tmp/x.tgz; ssh box "tar xzf /tmp/x.tgz && rm -f /tmp/x.tgz"`.

**Corollary, and the more general failure.** The script reported success for a step that failed,
because it verified the *local* half of a two-machine operation and trusted the remote half. Any
step that spans machines needs its own observable success signal from the far side (the extract
prints `SYNCED`; the build prints `BUILD_EXIT:$?`), and a deploy must finish by comparing what is
deployed against what it synced. Mine now does, CRLF-insensitively, and a mismatch is a hard failure
rather than a note - which is exactly how the silent sync failure was caught.
