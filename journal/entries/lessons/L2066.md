**L · A worker's checkout is not the base: two correct patches failed because they were cut against a stale tree**

MEASURED 2026-09-18, on the mesh, twice in one evening.

WHAT HAPPENED. Two workstreams were asked to produce a patch for a package in `harness-config`. Both
produced **correct, well-argued, dry-run-verified patches**. Both failed on the receiving machine:

- **Attempt 1** arrived **truncated mid-hunk in the message** — `git apply --check` reported
 `corrupt patch at line 749`. The delivery channel, not the work.
- **Attempt 2** arrived as a **file with a matching SHA-256** (`PATCH_BYTES=44797` matched exactly),
 and its own dry run was green. On the target: `error: patch failed:
 packages/plugin-remote-fanout/lib/provider.js:545` / `patch does not apply`, exit 1. Nothing applied.

THE CAUSE, and it is mine as much as theirs: **the mesh child's `harness-config` clone is ~52 commits
behind `origin/master`**, and the receiving tree additionally carries a different patch to the same two
files (`prefer-remote`, which touched `provider.js` and `index.js`). A diff cut against the working tree on
that node therefore has the **wrong base**, and its hunks carry context that does not exist where the patch
must land. The earlier dry run passed **in the tree that produced it** — which is not evidence about the
tree that will receive it.

WHY THIS IS THE SAME ERROR CLASS AS THE REST OF TODAY, wearing project-management clothes: `git apply
--check` answered **exit 0** and was read as "this patch is good". It was answering a question about **one
tree**. `repair-ids` answered "nothing to do" about one tree. `journal.py check` answered "0 errors" about
one tree. `node -v` answered about one PATH. **Four different tools, four confident green answers, all about
the wrong subject**, and the fix is the same in every case: ask what the tool was looking at before
believing what it said.

THE RULE, now in the mesh brief template as **H6**:
> **Your working tree is not the base. `origin/master` is.** `git fetch origin` first, materialize every
> file you patch with `git show origin/master:<path>` into a scratch directory, edit those copies, and
> generate the diff against them — never from a file read out of the working tree. Then **prove the base**:
> `git apply --check` against a pristine copy materialized from `origin/master`, and report that exit code
> as the result. **A green check against your own working tree is not evidence and must not be reported as
> if it were.**

AND THE SAME RULE INVERTS FOR THE ORCHESTRATOR, which is the half I got wrong: I fetched the file, verified
its hash, and **read the first ten lines of a `--verbose` check whose exit code I had already mis-attributed
to the pipeline rather than to `git`.** The hash proved the file arrived intact; it proved nothing about
whether it applied. **A matching hash is a statement about transport, never about correctness** — and the
full check, run without truncation, exited 1.

THE DELIVERY RULE, which survived this and should be used for any patch from a child: **never print a diff
in a message.** Write it to a file, print `PATCH_PATH` / `PATCH_BYTES` / `PATCH_LINES` / `PATCH_SHA256` /
`BASE_REF` / `APPLY_CHECK_AGAINST_ORIGIN=exit <n>`, and let the orchestrator fetch the file and verify the
hash itself. Attempt 2 proved the hash-and-fetch half works; attempt 3 needs the base half.
