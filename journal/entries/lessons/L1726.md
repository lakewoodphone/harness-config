**L1726 · A loader entry's activation order is not its tree order: ctx.get() in apply() can be empty, and the failure is silent**

A loader entry's ACTIVATION ORDER is not its order in the composed tree. A plugin row that is LAST in `dsh web --dump-config` output can still be applied BEFORE the row that provides the service it wants, so a bare `ctx.get('webServer')` inside `apply()` returns undefined, an `if (webServer !== undefined)` guard skips the contribution, and the plugin looks mounted while contributing NOTHING — with no error anywhere, because skipping was the designed behaviour.

Evidence: dsh-plugin-health, 2026-09-16. The bundle composed correctly (`# == dsh-plugin-health` + its row in the dump), the engine booted (so `assertEntriesActivated` passed), and the empty-stdio process probe proved `apply()` ran — yet `GET /healthz` returned 404 from the SPA fallback and no route was in the exact table.

Two wrong fixes, rejected: (1) hard `inject: ['webServer']` — a headless profile that never mounts a webserver would then leave the fiber pending and `assertEntriesActivated` would fail the whole boot, so a health plugin could stop an engine from starting; (2) accept the skip — invisible by construction.

The right idiom, and the one the shipped plugins use (`dsh-pwsh-local` for `settings`): `ctx.inject(['webServer'], (webCtx) => { webCtx.effect(() => webCtx.webServer.register({...})) })`. It starts a CHILD fiber that waits for the service and whose effects die with the parent; a child fiber is not a loader entry, so it can never fail the boot.
