**L4000 · CORRECTS L3933: the force-exit race is falsified - the force-exits never ran, so they cannot be the CI shard crash**

**FALSIFIED my own hypothesis twenty minutes after writing it: the force-exit race is NOT the CI shard crash. The logs say the force-exits never ran.**

This entry CORRECTS `L3933`, written earlier the same day. L3933 claimed the cause was "TWO force-exit
calls racing vitest's pool teardown". **That is wrong, and the disproof is in the same shard logs I had
already downloaded.** I tested the hypothesis against evidence instead of shipping it as a config
change, which is the only reason it cost nothing.

THE DISPROOF — grep the two failed shard logs on PR 440 for the force-exit machinery's own output:

```
 shard 1/4 shard 2/4
'CI Force Exit Reporter' lines 0 0
'CI Global Teardown' lines 0 0
'Test run ended with reason' 0 0
'Forcing process.exit' 0 0
```

Both `global-setup.ci.ts` and `force-exit-reporter.ts` print before they exit, and **neither printed
anything in either log.** They never executed. A mechanism that never runs cannot be the cause.

WHAT THE LOGS ACTUALLY SHOW — two variants, same ending:

```
shard 2/4 14:20:29 vitest starts
 14:21:46 [vitest-pool]: Timeout terminating forks worker for .../Card.test.tsx
 14:22:16 [vitest-pool]: Failed to terminate forks worker ... Timeout waiting for worker to respond
 14:22:16 Error: write EPIPE errno: -32 <- 0.4s later

shard 1/4 14:20:14 vitest starts
 14:22:36 Error: write EPIPE errno: -32 <- NO terminate timeout first
```

So: **a forks worker becomes unavailable mid-run**, and vitest's pool teardown then `send`s to a dead IPC
channel, the `error` event is unhandled, and **the process dies before any summary is printed.** Variant
(a) the worker wedges and survives the 30 s `teardownTimeout`; variant (b) the worker is simply gone
before the timeout is even reached — which is what an externally-killed or self-exited worker looks like.
Both are the same class: worker lost, vitest dies without reporting.

ALSO RULED OUT BY MEASUREMENT, not by argument:
- `--reporter=hanging-process` **is** in the CI reporter list and produced **no output at all** before the
 crash, so it does not name the wedge. (An earlier count of "27/30 hanging-process lines" in these logs
 was only the command line echoing `--reporter=hanging-process`; there is no reporter output.)
- `poolOptions` removal is a no-op — see L3933's other half, still correct.
- No OOM strings, no executed step timeout (L3820 / child 43).

NEXT EXPERIMENT, and it must be run in CI because the crash does not reproduce locally (it is
intermittent: on PR 439 `Test Frontend (Shard 1/4)` passed in 5m58s while shards 2-4 crashed):
1. Capture whether the *named* test file is meaningful or incidental. The name varies
 (`Card.test.tsx`, `NumericRangeSlider.test.tsx`, `DataTable.test.tsx`, `badge.test.tsx`, ...), and
 each `Failed to terminate` line always *follows* the 30 s timeout — so the named file is what the
 worker was holding, not proven to be the cause.
2. Reduce worker pressure on the runner (`maxWorkers: 2` in CI) and read the shard logs. This is the
 cheapest single change and it is reversible.
3. Only then consider the open gate (`P3199`).

**THE LESSON THAT GENERALISES, and it is the one worth keeping: I wrote a confident mechanism claim into
the journal and had, in the same session, already downloaded the log that falsifies it — I simply had not
grepped it.** A hypothesis is not a finding until it has been checked against the evidence you already
hold. Check first; write second.
