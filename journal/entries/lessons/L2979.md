## CORRECTION to P2730: the spend-guard failure is a RACE, and the settings.yaml correlation I first suspected is REFUTED

MEASURED 2026-09-28 (ZABZ-TECH). P2730 recorded the spend-guard activation failure and, in its
"observed rate" table, paired it with whether the legacy `settings.yaml` was present -- which read as
though the settings import and the guard failure were associated. **That association does not exist.**

A controlled experiment varied ONLY that one variable, four consecutive boot-to-quiescence runs of the
same staged home against the candidate `0.1.7-rc.2`:
```
 A-no-settings settings.yaml=False failed-to-import=0
 A2-no-settings settings.yaml=False failed-to-import=1
 B-with-settings settings.yaml=True failed-to-import=1
 B2-with-settings settings.yaml=True failed-to-import=0
```
The variable has no effect. **It fails about half the time, whatever is varied** -- so it is a RACE, and
the earlier pairing was a coincidence read as a cause. Recorded here rather than edited into P2730,
because the record of having been wrong is worth more than a tidy history.

WHAT THE RACE MOST LIKELY IS, marked as inference and not established: the generated
`packages/plugin-cost/lib/guard.js` resolves its single external dependency at MODULE LOAD time through
a hand-rolled anchor, `createRequire(<DSH_HOME>/profiles/web/package.json)`, i.e. it depends on
`<DSH_HOME>/profiles/node_modules` EXISTING at the moment the module is loaded. The engine appears to
build or repoint that anchor during boot, so a plugin loaded before it exists dies. Supporting evidence
that this class has already bitten once, from the package's own build header: *"the checkout has no
`node_modules` of its own -- measured 2026-09-17: ... a cold boot of the engine then died with
MODULE_NOT_FOUND and exit 1 (docs/incidents/2026-09-17-dsh-engine-boot-failure). Do not reintroduce a
`Schema` import in `src/guard-entry.mjs`."* Importing `lib/guard.js` by hand succeeds in every condition
constructible manually, which is why the cause points at ORDER rather than at resolution being
impossible.

THE LESSON, and it generalises past this plugin: **a module-level `require` of anything resolved by a
path the host builds at boot is a load-order dependency, and it will fail intermittently rather than
never.** A protective plugin must not be able to die while looking for a library. The fix removes the
failure mode rather than racing it: no external dependency on the guard's load path at all, and if any
runtime resolution is kept, multiple candidate roots with shape validation (the pattern
`scripts/merge-settings.mjs`'s `loadYaml()` already uses) plus a failure that is impossible to miss.

PROCESS NOTE worth keeping: I had a plausible, tidy causal story and it was wrong. Four cheap runs
refuted it. Believe a hypothesis only after trying to break it.
