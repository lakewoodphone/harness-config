**L1510 · Verify after the change point, never in a window that can contain the before**

**Verify after the change point, never in a window that can contain the before.**

Measured on 2026-09-15, minutes after fixing the six-month-dead `_run_reminder_poll`. I restarted
the service at 14:07:56 and then asked journalctl for the last six minutes -- a window that still
held the 14:05:21 failure from the previous process. The check printed "STILL FAILING" and I nearly
reported that my own fix had not worked. Re-running with `--since "$(systemctl show secretary-api -p
ActiveEnterTimestamp --value)"` gave the true answer: 0 failures, with the next 5-minute tick
covered.

The rule: a restart, a deploy, a config reload, a migration -- each one defines a *point*, and
evidence gathered on either side of it is evidence about different systems. Ask `systemctl show -p
ActiveEnterTimestamp`, the commit time, the file's mtime; never "the last N minutes", because N
minutes ago is a duration, not a boundary. Same family as the three hand-typed timestamp filters
earlier this session: the tool answers exactly the question asked, and "recently" is not a question
about the change.
