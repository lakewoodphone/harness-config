**L2410 · Never type a journal id you have not been given: the allocator decides, and two guessed ids were wrong in the same session**

## L2410 · 2026-09-24 · Guessed journal ids, twice in one session

In this session I put a journal id into a document BEFORE appending the entry, twice, and got it
wrong both times:

- handoff H2596 said "Journal: L2405/L2406/L2407/L2408" — the allocator issued **L2379-L2382**.
 Corrected by H2597.
- `assets/mobile.css` said "see P2316" — the allocator issued **P2410** for that entry, and
 **L2383** (not L2409) for the lesson. Fixed in the file directly, since a stylesheet is not an
 append-only record.

WHY IT HAPPENS. The ids look sequential, so they feel predictable. They are not: `append` allocates
over `entries/`, the cache and every git ref, and it bumps when an id already exists with different
content. Guessing is a coin flip that costs a correction entry every time it loses.

THE RULE. `journal.py append` FIRST, read the id it prints, and only then cite it — in a document, in
a commit message, in a stylesheet comment. Never cite an id that has not been allocated yet. If a
citation must precede the entry (a file written by the same change), cite the title, or cite nothing
and add the id afterwards.

SECOND RULE, for the same reason. A wrong pointer in an append-only record is corrected by a NEW
entry citing the old one — never by editing the old entry. `journal.py check` stores a sha of every
body, so an edit shows up as a malformed/corrupt entry, which is exactly the check that exists to
catch a rewritten record.
