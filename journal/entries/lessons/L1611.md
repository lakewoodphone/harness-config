**L1611 · A runtime secret manager would have prevented both live credential failures in this audit**

## A cloud secret manager would have stopped the two live credential failures found in one audit

**The failure, twice in one session.** (1) Production secrets were **baked into a Docker image**:
`next build` copies the project `.env` into `.next/standalone/`, and the Dockerfile shipped it to
`/app/.env`. The image layer therefore holds `DATABASE_URL`, `LPT_SSO_SHARED_SECRET` and
`CHUMASH_SESSION_SECRET` — `docker diff` showed 0 lines and `Mounts` was `[]`, proving the file was
baked at build time, not mounted at runtime. Rotating a secret required a rebuild, and anyone who
could pull the image could read them. (2) An application's **sign-in was dead for every user** because
a shared SSO secret had been rotated at the identity provider and the consumer was left holding the
old (actually, the *test*) value — with the only symptom a `403` that the app rendered as "the user
just isn't signed in".

**The mechanism to adopt.** A **runtime secret manager** (the cloud-native one: a managed secrets
service with IAM and versioned rotation — AWS Secrets Manager / SSM Parameter Store / GCP Secret
Manager / Azure Key Vault, or Vault for self-hosting) rather than secrets distributed as files. That
single change to the source of truth eliminates the entire class:
- **No secret in a build artifact**, because the build never has one; the container fetches at
 runtime under an identity — so `docker history`, image pulls and CI logs are all clean by
 construction, not by a `.dockerignore` rule someone must remember.
- **Rotation is one operation, not N.** Rotation becomes a new version in the manager; consumers
 either fetch per-request or subscribe to a rotation event. The failure mode observed here — an
 operator rotates at the provider and one consumer keeps the old value, silently — becomes
 impossible when no consumer *stores* the value.
- **Per-consumer identity replaces one shared string.** The audit confirmed the estate's SSO is a
 single shared secret with no per-app identity and no registry, so any app's leak is total and no
 app can be revoked without rotating everyone's. With per-app credentials issued by a manager, each
 app is individually revocable and every use is attributable to a caller.
- **Fail-closed is enforceable centrally**: a missing/invalid secret throws at startup rather than
 degrading into an unauthenticated-looking state.

**Immediate mitigations, which are not the same fix** (and are what was actually specified for this
codebase): add a `.dockerignore`, stop copying `.env` into the runtime image, validate the session
secret for emptiness and minimum length, and **add a deploy-time configuration check that fails loudly
when an assertion is rejected** — because the rot here was invisible, not just inconvenient.

**The transferable rule.** When the *same* class of mistake (a secret in the wrong place, or a
rotation nobody propagated) appears twice in one audit of one small surface, the answer is not two
patches — it is moving the source of truth. **A secret stored in a file is a secret that will be in a
build artifact, a backup, a git history and a support bundle, because nothing prevents it.** Also:
a rotation that nothing verifies is not a rotation, it is an outage with a delay.
