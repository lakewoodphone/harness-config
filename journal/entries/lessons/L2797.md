**L2797 · A duplicate alembic revision id is a P0, not a test failure, and alembic merge cannot repair it**

## L — A duplicate alembic revision id is a P0, not a test failure, and `alembic merge` cannot repair it

**What was true, measured 2026-09-28 on `kosher-filter-ai` `main` (`6e65a73`).**

Two migration files shared one revision id:

```
server/alembic_scripts/versions/20260915_01_postgresql_operator_password_resets.py
server/alembic_scripts/versions/20260915_01_postgresql_screenshot_review_decisions.py
```

Alembic loads both, warns `Revision 20260915_01 is present more than once`, and
`get_current_head()` raises:

```
$ python -c "from app.alembic_support import get_alembic_head_revision; print(get_alembic_head_revision(Path('.').resolve()))"
CommandError: The script directory has multiple heads (due to branching). Please use get_heads(),
or merge the branches using alembic merge.
```

**Why that is a P0 and not a CI annoyance.** `app/alembic_support.py:59` calls
`script.get_current_head()` from `get_alembic_head_revision`; `stamp_alembic_head` (`:81`) calls that;
`run_configured_migrations` (`:98-115`) calls *that* on the **SQLite path at startup**. So the trunk
**could not start a SQLite deployment at all**. It had been in that state since **2026-09-15**, and it
was invisible only because the deployed broker image is roughly three weeks behind — the defect was
waiting for the next deploy, not for a customer.

**The two traps, both of which cost time.**

1. **`alembic merge` is the wrong tool here and says so badly.** `alembic merge -m x heads` exits
 `FAILED: Duplicate head revisions specified`. Two files sharing one id is *not* a branch — there is
 nothing to merge. The fix is to give one of them a unique id and chain it with an honest
 `down_revision`. This matters because "the script directory has multiple heads" is the error text
 that sends you to `alembic merge`, and the error text is wrong about the cause.
2. **A duplicate revision id is caused by a merge, and nothing detects it.**
 `alembic_scripts/versions/` is not scanned by `app/sql_surface_audit.py`, no test asserts
 `len(script.get_heads()) == 1`, and the app imports fine — the failure is at *startup*, so an
 import-based smoke test cannot see it either.

**What would have caught it, and should exist.** One test:
`assert len(ScriptDirectory.from_config(cfg).get_heads()) == 1` — it needs no database, runs in
milliseconds, and it is the only cheap guard for a defect that stops the app booting. Until it exists,
every migration added by two branches that are later merged is a P0 risk, and `Server CI` was the only
thing that noticed — which was itself red for ten days (`P2563`).

**Also learned, cheaper:** a security sign-off snapshot records a digest of the whole audit report, so
the component-inventory snapshot must be refreshed **before** the sign-off snapshot. Doing it in the
other order leaves `report_digest_match: false` and the audit fails with `overall: partial` even
though every control passes.

**Evidence.** `python -m alembic heads` → `20260915_01 (head)` twice before, `20260915_02 (head)`
after; the `CommandError` above, reproduced; the fixed branch returns `20260915_02`. Full report:
`docs/audits/kf0928/server-ci.md`.
