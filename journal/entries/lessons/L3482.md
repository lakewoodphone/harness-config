**L3482 · An intake photograph is a row in repair_intake_case_photos plus an object in R2 - 'no pictures' was said from the wrong table twice**

An intake photograph is a ROW plus an OBJECT, and the row is in `repair_intake_case_photos`.

**Ask that table, or do not answer.** The link from a work order is
`repair_intake_cases."promotedOrderId"` (plus the customer, for a case never promoted). The bytes are
in Cloudflare R2 under `repair-intake/<case uuid>/<position>.<ext>`, written object-first so a row
implies an object existed at write time.

**What is NOT a photograph store, and was mistaken for one twice:**
- `issue_intake_screenshots` — an older, session-keyed feature. 21 rows, all soft-deleted, no
 mounted upload volume, no bytes on the server (journal P2860 named this — it is about THAT table
 only, and the estate then over-generalised it to "there are no pictures anywhere").
- `customer_notes.attachments` (non-null on 976 rows), `orders.attachments` — empty arrays or null.

**Measured 2026-10-11, both defects, same root cause (a tool reading a store the data is not in):**
- `lpt ticket 7185017418` printed `PHOTOS 0` for work order WO26100812738, which carries **four**
 intake photographs (case 1284, sha256 `26cd6db3..`, `825f3a46..`, `7dcd8421..`, `8d1735a0..`).
 `lpt photos <key>` printed "no photograph exists in this store." Cause: it read only
 `issue_intake_screenshots`. Fixed in lpt-ops `bc88ca6` (counts + `intake_photos_sql` +
 `PHOTOS n on the intake case`).
- `bin/lpt-storage-audit.sh`, run alone on `lpt-apps`, counted **19** row keys against **35** objects
 and reported **16 orphans**; all 16 are referenced, by the `operational` store, which that host
 cannot read. So the one check whose job is to notice a photograph that has gone could not see 16 of
 the shop's 17 real intake photographs. Fixed in lpt-ops `96ca8dd`: `--extra-rows` plus
 `lpt photos --audit`, which collects the union from **both** stores and stages it on the app host.
 After the fix: rows=35 objects=35 orphans=0.

**The transferable rules**
1. A `none` from one table is not evidence of absence. Name the table in the answer, always.
2. A checker that cannot read the store where the data lives is not a checker — it is a machine for
 printing green. A cross-store question needs a tool that can already reach both stores
 (`lpt_ops/transport.py`), not a script that runs where the credential happens to be.
3. An empty union is a refusal, not health: comparing a bucket against zero keys reports every object
 as an orphan and reads as a clean warning. `photo_audit.run()` returns 2 instead.
4. `lpt photos --audit` is now the standing check; it needs no credential off the app host.
