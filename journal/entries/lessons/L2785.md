**L2785 · pgrep -f 'git ' cannot answer 'is this checkout lock held', and /proc can**

MEASURED 2026-09-28T17:15Z on secratary, while diagnosing why both project
checkouts (/home/zabz/repos/phone-and-tech-full, /home/zabz/repos/kosher-filter-ai)
had sat for weeks with a 0-byte .git/index.lock and no git process behind them:

 pgrep -f 'git ' -> 3 matches, and NONE of them was a git process
 (a dsh node session whose task text contained "git",
 a `bash -c` script body, a `grep` whose pattern did)

A liveness test built on `pgrep -f` therefore answers "a git process holds this
lock" whenever ANY unrelated session merely mentions git - the one wrong reading
that keeps a crippled checkout crippled, because the fix is only taken when
nobody owns the lock. Comm is what says a process IS git; a command line is a
text field anyone can write "git" into.

WHAT TO USE INSTEAD, and it is what sources/checkout-health.py does:
 * exact: a process whose /proc/<pid>/comm is `git`/`git-*` with
 /proc/<pid>/fd -> <gitdir>/index.lock open (that is what holding the
 lock means);
 * broad: a git process whose /proc/<pid>/cwd is inside the repo;
 * fallback: if /proc cannot be scanned at all, the lock's AGE decides and an
 unowned lock younger than the grace (300 s) is never called stale.

PROVEN both ways on 2026-09-28 (see the project's handoff entry):
 * lock held by a real git process (`tail -f /dev/null | git update-index
 --index-info`, pid comm=git, fd 3 -> index.lock) -> source reports
 `lock=held`, files NOTHING;
 * SIGKILL that process -> same lock file, orphaned, age 4 s -> `lock=young`,
 still nothing;
 * age the same lock to 2026-09-20 -> `lock=stale 8.1 days` -> flagged.
