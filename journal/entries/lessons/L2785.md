## L — The iOS blocker was never "a Mac": the recorded plan and the code are two different products, and the URL layer needs a server the plan says not to build

**Source.** Fleet child `kf0928/ios-truth`, 2026-09-28, branch `kf0928/ios-truth` (`ae84657`, 21 files,
+4,832), working from `ios/`, `docs/IMPLEMENTATION_BACKLOG.md` Phase 3 and
`docs/ENGINEERING_STATE_AUDIT_2026-09-14.md`. Four findings, each checkable in the tree.

**1. There is no tunnel target, and the scaffold implements a design that was abandoned.**
`ios/FilterApp/Package.swift:19-60` declares **six targets, none of them a tunnel**. I-BACK-030..036
describe a TLS-terminating `NEPacketTunnelProvider` plus an MDM-installed CA (the 2026-08-30 analysis,
locked as Q20 on 09-06); the `ios/` code written 2026-08-28 is built around `NEURLFilterManager`
instead. So the code implements neither the architecture that was decided nor a usable version of the
one it was written for. The blocker line *"macOS + Xcode + real iPhone"* hid this completely.

**2. Apple's URL filter cannot be configured without a PIR server.**
`setConfiguration(pirServerURL:…)` has one signature and `pirServerURL` is **non-optional**. Q22's
*"defer the PIR server"* is therefore **not implementable on iOS as written**: either a PIR server gets
built, or `NEURLFilterManager` is not the URL mechanism. This is the finding most likely to change the
plan, and it is older than this session — nothing surfaced it because the item was filed as
"hardware-blocked".

**3. The broker's Bloom payload is in a format Apple's filter cannot consume.** `bloom_filter.py` uses
**BLAKE2b-128**. `NEURLFilterPrefilter` requires **32-bit FNV-1a + 32-bit MurmurHash3 with double
hashing**. The failure is **silent** — the filter loads, answers, and simply never matches — which is
the worst class of defect this product can ship. A `PrefilterHash` implementation in Apple's format
plus golden-vector generators now exist on the branch.

**4. Three of five `mdm/*.mobileconfig` files carry keys Apple does not define.** Profiles ignore
unknown keys, so each of those is a control that does nothing while looking installed. One valid file's
*"all DNS through our resolver"* claim is false on cellular, by Apple's own documentation.

**And the honest gap.** Seven Swift files (2,000+ lines: `Blake2b`, `BloomFilter` byte-parity with the
server, `BloomPayload`, `UrlClassifier`, `DohClient`, `CascadeOrchestrator` = I-BACK-033,
`PrefilterHash`) plus 86 tests were written and **never compiled** — the Swift toolchain install
stalled. The Python reference implementation *was* executed and verified. So this is real work with a
named next step, not a deliverable.

**Why this is a lesson rather than a status note.** A blocked item was filed as one hardware sentence,
and that sentence stopped six weeks of reasoning. Two of the four findings above are *design* problems
that need no Mac at all, and would have been found the day someone opened `Package.swift` and compared
it to the backlog. **Rule for future sessions: when an item is marked blocked on hardware, the first
task is to re-derive the blocker from the code — a blocker line is a claim, not a fact.**
