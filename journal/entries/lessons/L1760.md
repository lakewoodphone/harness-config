**L1760 · Never glob/grep from C:\Users\ezabz\code - measured 322,355 files and >60s, which is a guaranteed 30s tool timeout**

MEASURED 2026-09-16 on ZABZ-YOGA with rg:
- rg --files C:\Users\ezabz\code\lpt-hub\docs ................. 2.7 s
- rg --files C:\Users\ezabz\code (with node_modules/.git/.venv excluded) ... 60.4 s
- rg --files C:\Users\ezabz\code (no exclusions) .............. 322,355 files, >120 s
The glob and grep tools budget 30 s. So ANY recursive glob/grep pointed at the code root is guaranteed to time out. It happened three times in one session:
'**/customer-operations/*.md', '**/FLOWS-INDEX.md', and '**/*{sms,template}*' under phone-and-tech-full (which carries node_modules). A Get-ChildItem -Recurse -Depth 4 from the code root to find one file also burned 120 s.

RULE: scope every glob/grep to ONE repo, never to C:\Users\ezabz\code. For shell searches pass -g '!**/node_modules/**' -g '!**/.venv/**' -g '!**/case-media/**'. If you need a cross-repo answer, ask the question per repo, or use a repo-local index (lpt-hub has docs/customer-operations/FLOWS-INDEX.md).

WHY IT COSTS MORE THAN TIME: a timed-out tool call returns nothing, so the reflex is to retry with a narrower pattern - which is the right move but only after paying the timeout twice. Knowing the shape up front skips both.

Same rule for in-process grep: grep with path=<one repo> returned in well under a second every time this session (lpt-hub, personal-secretary-mvp). The only failures were path=<code root>.
