**L13515 · Read the writer, not the diagnosis: refusals vs failures, falsy sentinels, and a fuzzy dedupe that steals an exact key**

Four rules, each paid for on 2026-10-26 while fixing the policy-refusal defect on the authority.

**1. A diagnosis in a handoff is a claim, not evidence — and the fastest refutation is to read the predicate.** I was handed "a refusal demotes the agent's autonomy for obeying the rule". It is false. One probe (force the gate to refuse, count `record_failure` calls) answered it in two minutes, and a mechanical argument answered it without running anything: the demotions happened at L4→L3 and L3→L2, and at both of those levels `should_execute` returns `execute=True`, so **no refusal can exist at the moment the demotion occurred**. Before acting on any "because X, therefore Y" in a handoff, find the line that writes Y and check that X reaches it. The previous session had the log lines but not the writer.

**2. When the reason a counter moves is not logged, every later reader invents one.** `Autonomy DEMOTED: repo_read_file L4 → L3` was true and useful; the *cause* was nowhere, so a session attributed it to the most visible adjacent event (the refusals) and published that. Fix: log the detail at the moment the counter moves (`Autonomy: recorded a real execution failure for <action>: <detail>`). An unattributable state change is an invitation to fabricate history.

**3. "No value" and "no row" are different answers, and a falsy sentinel merges them.** Three separate instances in one change:
- `create_task` returns **-1** when the active-task ceiling blocks it. Passed through unexamined it printed *"Queued for approval as task -1"* — a queue entry that never existed.
- A refusal that could not write a task returns `""`, and `elif refusal_task_id:` treats `""` as "not a refusal", so the strike counter — the exact thing being fixed — would have fired anyway. The test had to be `is not None`.
- `database.create_task`'s fuzzy title dedupe (80%, agent-agnostic) **silently wins over an exact `dedupe_key`** when the exact key finds nothing, because the fuzzy branch runs after it and returns the old title-only row; the resource-specific key is then never written at all. Measured: three refusals across two different repo paths all returned task #30267, created three days earlier with no key. Fix is the estate's own existing pattern — `dedup_threshold=0` alongside the exact key (`drn_reliability_api.py`).

**4. A deliberate decision must be a distinct class from a failure in the type system, not in the wording.** A refusal returned `success=False` with a human sentence saying "NOT EXECUTED", and every consumer downstream — the retry loop, the circuit breaker, the tool-strike counter — read `success=False` and did the failure thing: three identical refusals, a deadlock, and a step that ended having done nothing. The sentence was honest and ignored. The fix is one structured field (`data["policy_refused"]`) that every consumer reads, plus a predicate `_is_policy_refusal()` so there is one definition of it.

**Corollary, for the next agent:** the same shape exists elsewhere in this estate. Anywhere a *policy* outcome and a *technical* outcome share one `success=False`, the caller will eventually punish the agent for obeying. Check `_enforce_action_policy` (also fixed), `department_tools.is_action_allowed` (already correct — it returns before the counter), and anything that returns a sentinel number instead of `None`.
