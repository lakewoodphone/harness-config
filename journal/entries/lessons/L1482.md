**L1482 · Correction: the suite's failures are stably 8 but their victims shift, and its error count varies 153-1735**

CORRECTION to P139's error figure, and the shape of the instability made concrete.

P139 said "8 pre-existing failures, 153 order-dependent errors". Both halves need
refining, and the refinement is the useful part:

FAILURES are stable at 8, and they are genuinely pre-existing -- verified in a worktree at
commit 32a912a6:
 test_ai_gateway 3, test_config_contract 3, test_vscode_chat_extractor 1,
 test_assistant_chat_prompt_profiles 1.
But that last file does not fail on the same TEST twice: one run failed
test_get_all_candidates_prefers_route_primary_first, a later run failed
test_call_fast_model_simple_emits_shared_routing_telemetry and
test_run_assistant_chat_emits_prompt_and_routing_telemetry. Same file, same count, different
victims -- so the count understates the instability.

ERRORS ranged 153 -> 1735 across identical invocations (`pytest tests/ -q`), with the pass
count swinging 2404 -> 843 -> 845. A swing that size is not one flaky fixture; it looks like
a resource that is sometimes available and sometimes not.

HYPOTHESIS, NOT VERIFIED: the running secretary-api service holds the same SQLite file(s),
and my own `systemctl restart secretary-api` calls during these runs changed the lock
contention. I have not tested this. The cheap test is to run the suite twice with the
service stopped and compare the error count; if it is stable and small, the cause is
contention with the live service and the suite needs its own database paths.

DO NOT restate P139's "153" as the error figure. The honest statement is: 8 stable
pre-existing failures whose victims shift, and an error count that varies by an order of
magnitude between identical runs.
