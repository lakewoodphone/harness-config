**L1858 · I armed Lost Mode on a live production phone by calling the wrong verb - a command's name is not its effect**

## Incident — I armed Lost Mode on a live production device by calling the wrong verb

2026-09-17 ~04:23Z, device **DRN 48** (serial `DL6Y9R6VNH`, a driver's phone, and the device the Screen Time practice is running on).

What happened: while verifying a guard I had just added to `scripts/drn-api.ps1`, I ran `drn-api.ps1 lost-mode 48` as a "should refuse" test. It did not refuse — because `lost-mode` is its own switch arm, separate from the `location-command` alias I had guarded — and it enqueued **EnableLostMode + DeviceLocation** and pushed APNs. Device acknowledgements, from `command_results`:

- `EnableLostMode` **Acknowledged 04:23:41Z**
- `DeviceLocation` Acknowledged 04:23:52Z
- `DisableLostMode` **Acknowledged 04:24:03Z** (sent as soon as I saw the output)

So the phone held the "reported missing" lock screen for about 22 seconds. The device is back to normal (`state=deployed`, check-in 04:24:24Z) and no data was lost, but a driver may have seen it.

Two lessons, and they are not the same lesson:

1. **A command's name is not its effect.** `location-command` read like a read and posted `/lost-mode`; `lost-mode` reads like a state change and does lock the phone; the safe read is `location`. Before firing an operator command at a production device, **read the handler** — the endpoint's own code was two files away and would have told me in ten seconds. I had the audit finding in hand and still hit the other verb.
2. **Guard the destructive direction, not just the misleading one.** I guarded only the alias. The right rule for a fleet CLI: every command that changes what a driver sees (lost mode, erase, wallpaper, lockdown) requires an explicit `-Confirm<Action>` switch, so a scripted "should-refuse" test cannot be a live action. `lost-mode` and `location-command` now both require `-ConfirmLostMode`; `lost-mode-disable` is deliberately left unguarded so recovery is never blocked.

Cost: ~22 seconds of a driver-facing lock screen. Recovery was one command and it was acknowledged. Reported to the owner the same turn.
