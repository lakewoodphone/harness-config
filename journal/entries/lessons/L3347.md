**L3347 · The plain <port>.log is written once, at the first start of that port - read the newest log, not the plainest name**

**The plain `<port>.log` is written once, at the FIRST start of that port — the live engine's token is in the
newest `<port>-<date>.log`, and reading the plain name first hands the caller a dead token.**

Measured 2026-10-06 on ZABZ-YOGA while adding a new phone to the tailnet. `~/.dsh/multi-window/logs/3099.log`
(mtime 2026-10-02 11:08) held a token from an engine that had died that day, and `3099-20261005-011920.log`
(2026-10-05 01:19) held the running engine's. `live_token()` in `scripts/phone-gate.py` checked the plain names
in each directory before the timestamped ones, so it returned the dead token; the login exchange answered **401**
and **every** phone sign-in on that node failed — the owner's already-listed iPhone 15 Pro as much as the newly
added device. Proof, both ways against the engine on 127.0.0.1:3099: stale token -> 401, live token -> 303 +
Set-Cookie. Fix: build every `{port}*.log` candidate across `ENGINE_LOG_DIRS`, sort by mtime descending, take the
first that yields a token. The running engine appends to its own stdout log, so its file is always the freshest —
that is a guarantee, not a heuristic.

**Two generalities worth keeping.** (1) A "new device cannot get in" report is a hypothesis about the device, not
a finding — test an already-working device first; here the same 401 came back for a device that had been listed
for three weeks, which moved the fault from the allow-list to the token. (2) A named `<thing>.log` beside a
rotating `<thing>-<date>.log` is a trap in any tool that reads logs by name; order by mtime, never by how plain
the filename looks.
