**L3832 · orders.passcode has no writer - and the LPT-Access kit already collects the USB evidence, behind a gate that forbids opening a window**

**2026-10-15, ZABZ-TECH, WO26100812736 (Senzer HP EliteBook 840 G3).** Two things this session learned that a
future session cannot re-derive cheaply.

**1. `orders.passcode` is read by the app, is checked by the write guard, and has NO writer.**
- `lpt-ops/lpt_ops/write_helper.py` `ORDER_SELECT` selects `passcode` **from `orders`**, and `redact(text,
 order["passcode"])` **refuses** a note containing it. So the shop's own surface treats `orders.passcode` as the
 authoritative device login.
- `lpt-web call workOrders.getById --input '{"id":3015}'` returns `"passcode": "<redacted>"` at the top level of
 the order — the app reads it.
- **Nothing writes it.** Every `workOrders.*` route was listed from `lpt-web routes`; there is no passcode route.
 `aiWorkspace.applyWorkOrderDeviceDetails`, the device-details route, names its **complete** required set —
 `sessionId`, `workOrderId`, `deviceInfo`, `issueDescription`, `conditionNotes`, `expectedWorkOrderUpdatedAt` —
 and carries **no passcode key**. `workOrders.updateDetails` accepts `orderId` and silently ignores `passcode`
 (the call returned 200 and the column stayed NULL, re-read by SQL).
- **How to set it, until a route exists:** one scoped UPDATE from the authority, through the app's own env DSN,
 verified by read-back —
 ```
 ssh secratary-ts 'cd /home/zabz/personal-secretary-mvp && .venv/bin/python3 -' # script on stdin
 UPDATE orders SET "passcode" = %s, "updatedAt" = now() WHERE id = %s AND "passcode" IS NULL RETURNING id
 ```
 Read back `("passcode" is null) = False, length = 9, title/description unchanged`. Record it as a **hand write**
 in production, not an app write.
- **Transport trap, measured the same hour:** piping a here-string into `ssh ... 'python3 -'` from PowerShell
 produced `SyntaxError: invalid question`/`invalid syntax, perhaps you forgot a comma`. Base64 the script
 (`[Convert]::ToBase64String([IO.File]::ReadAllBytes(path)) | ssh host "echo B64 | base64 -d | python3 -"`) and it
 runs first time. This is the same family as the PowerShell double-quote trap already on record, and it costs a
 reference to `L3399`.

**2. The shop's LPT-Access bench kit tells you what to do with a machine, and it has a hard gate.**
- Stick `D:` on ZABZ-TECH (`__USB321FD`, FAT32, PNY) is the deployed kit: `LPT-Access\` (four numbered icons),
 `LPT-Runs\<runid>\`, `LPT-KeyCheck\`. `1-QUICK-SCAN` and `2-FULL-CAPTURE` change nothing;
 `3-OPEN-ACCESS` **must not be run** — its README says *"Until A4 passes on a real machine, do not open a window
 on anyone's computer"*, and A4 is the reboot-plus-absence test on a real laptop, never done.
- **The USB evidence is already a section of the capture:** `sections\20-usb-devices.txt` is every USB device ever
 attached to that machine — which is how "a virus from a USB" gets an answer — plus `25-startup-autoruns.txt`,
 `27-installed-programs.txt`, `39-boot-events.txt`. Run the kit before reasoning about "the USB".
- The stick also carries **another job's BitLocker recovery key** in the clear
 (`LPT-KeyCheck\BITLOCKER-KEY-PF3F2810-20720311-000459\`) for a LENOVO IdeaPad 3 serial `PF3F2810` whose clock says
 **2072**, and that record says in its own words that the real date of the run must be recorded by hand on
 arrival. Nobody has. A customer's recovery key with no true date and `ownership_pass: false` is an open item, not
 a stored asset.
