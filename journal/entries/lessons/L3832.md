**L3681 · Owner corrections 2026-10-12: foreground delegation, over-asking, and the SMS gate**

## 2026-10-12, ZABZ-TECH, session with the owner (Dialpad + customer queue)

Five corrections in one session. Each is a behaviour, not a fact.

### 1. NEVER run a blocking delegation while the owner may want to talk
He said: *"i tried to send you a new message but i couldn't cuz you were running this subagent in
teh foreground, which is a bad habit youve fallen into in the past week"*.
The call was `subagent` with the default `run_in_background: false`. It was placed on ZABZ-YOGA
via ssh, ran **679 s**, and was SIGKILLed having produced only its transport preamble — no result,
and his message blocked the whole time.
RULE: pass `run_in_background: true` on every `subagent` / `subagent_remote` call unless my *next
action literally cannot proceed without the result*. The `subagent` tool docs default to
background for `subagent_fork` only; the others default to foreground, so this must be explicit.

### 2. Answer the customer's question; do not lecture or price-stack at a stranger
First draft to a new customer offered three prices (50 / 65 / 130) to a man whose **device model
was unknown**, had a formal *"Hi Yosef - this is Lakewood Phone & Tech"* opener, an em dash, and
two numbered ask-lists.
The owner: *"so ask him what model, no? isnt that the smartger thing?"* — and he is right. The
model decides the price; asking for it is one line. `lpt-hub/docs/customer-operations/
CUSTOMER-SMS-RUNBOOK.md` §2 already said: no `Hi <FirstName>`, sign `- Daniel`, plain hyphens, one
idea per paragraph, and a first-contact price is a number I cannot honestly give without the device.

### 3. Pull the full record BEFORE recommending anything
Asked to "pull up the full dialpad info", I gave him a 27-row waiting table plus a sync dashboard
and only then, on his push, went and read the actual call rows. His reply: *"now what's the history
and context of yosef hoff, you didn't give me enough info"*.
The call rows held what mattered and were one query away: both calls **never connected**
(`date_connected_ms` null, 7.8 s and 21.5 s), dialled the **office** line at 15:18Z = **11:18 EDT
Sunday, before the 12:00 open**. "Missed calls" was my word; "rang out because the shop was shut"
was the fact.
RULE: the customer's own rows are cheap. Read them before summarising, never after being asked.

### 4. A live UI is not an unsaved draft
I saw the auto-reply text in our sent-message records without the address, saw the Dialpad settings
box WITH the address, and concluded "the edit was never saved". He had **just made that edit**.
His words: *"to clarify i just changed the message to the one i showed you, it wasn't like that
before"*.
RULE: when config and behaviour disagree, the honest statement is *"the record shows X as of
<timestamp>; if you changed it just now it has not been exercised yet"*. Never narrate a
difference as a defect in his work.

### 5. Two SMS send paths — and the gate is real
`ps_action send_sms` was refused: `Policy denied: requires owner approval - task #28371`, with
approval prompts disabled in the session, so the tool path is closed.
The approved path is the runbook scripts:
`personal-secretary-mvp/scripts/send-lpt-sms.py --to <E164> --message-file <file> [--send] [--force]`
Run it **without** `--send` first: it prints From / To / Body **including the auto-appended
`- Daniel` signature**, which is how the body is shown to the owner before sending. It exits 1 on
its money-validator warning ("mentions money but contains no numbers"), which is a **false
positive** when the text deliberately asks for the model before pricing; read the reason and pass
`--force`. It appends the signature by default — do not pass `--no-signature`.

### Delivery evidence, stated honestly
`Status: pending` + message id proves Dialpad accepted it. The witness that it exists on our side
is a `dialpad_sms_cache` row with `fetched_at` 1-2 s after `created_at` (live capture; a backfill
shares one `fetched_at` to the millisecond). Measured for message id 6590970955866112:
created 17:22:45.012Z, fetched 17:22:47.113Z, phone 8456712943. Delivery to the handset was NOT
confirmed and no API can confirm it. Never write "he received it".
