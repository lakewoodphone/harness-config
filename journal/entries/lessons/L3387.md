## CORRECTION to L3385: the filter's DNS break was the SECOND fault on that node, not the cause of the dispatching failure

L3385 said the Kosher filter's DNS hijack was why mesh children placed on ZABZ-TECH died. That is
over-attributed, and this entry corrects it rather than editing L3385.

**What was actually fatal to a child, per another session's fix (H3329, 2026-10-08 03:03Z):**
`scripts/vscode-update/mcp_launcher.py` opened `data/logs/mcp-launcher.log` unconditionally; under the
mesh child's execution context that open raised `PermissionError`, the one-shot exited 1 with no
completion frame, and `plugin-remote-fanout/lib/retry-plan.js` classified ANY non-zero exit with no
frame as `child-ran-transport-fault` - harvest, never re-dispatch - so one broken node absorbed 100% of
dispatches while a good node sat idle. Both halves were fixed and ZABZ-TECH re-measured
`MESH-OK-ZABZTECH`, exit 0. The probe record confirms it: `zabz-tech ok=true exit=0 6000ms at
2026-10-08T03:02:59Z`. My two dead dispatches carried the SAME stderr as that defect, so the launcher
crash - not DNS - is what killed them.

**What remains true, and is independently measured.** While the filter's services ran (22:07-22:52
local), ZABZ-TECH resolved no public name at all; with them stopped it resolves again. Measured by me
either side of the change: 11 public names NXDOMAIN and `example.com` OK while it ran; api.deepseek.com,
github.com, google.com and registry.npmjs.org all resolving once it stopped. So it was a real second
fault stacked on the same node, and any child reaching the model API through that machine would have
died on it too.

**How the filter got there, which is the part that matters.** The product's own audit,
`kosher-filter-ai/docs/audits/kf0928/windows-merge.md` §4, states it in its own words: *"The service
runs as an installed Windows service (`sc create` + start) ... UNVERIFIED ... not attempted:
registering/installing a service on the owner's laptop is outside the rules of engagement."* And the
same table calls `"the unrestricted production filter udp.DstPort == 53 or udp.SrcPort == 53"` -
verbatim the rule that was live on that host - *"UNVERIFIED - needs a maintenance window ... an
interrupted run breaks the host's own DNS"*. It was installed anyway: `C:\Program Files\KosherFilter`
created 2026-09-28 17:33, `C:\Program Files\KosherFilterRelay` 2026-09-30 20:51, both services flipped
**from disabled to demand start** at 20:27:22 and 20:27:43 on 2026-10-07, and the WinDivert kernel
driver registered at 20:27:44 from `C:\Program Files\KosherFilter\WinDivert64.sys` (System log, 7045).
The relay's own application log then filled with `Broker DNS forward failed for ...; answering
SERVFAIL`. No journal entry records the install or authorises it, and the owner's own reaction on being
told was that he believed it had already been removed - which the disabled start type supports.

**A future session should read this before touching that machine.** The two services are Stopped now
and DNS is verified working. Nothing was removed - the files, the service registrations and the
WinDivert driver service are all still there, so a start type change is all that stands between the
owner's desktop and the same outage.
