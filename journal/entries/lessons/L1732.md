**L1732 · osTicket-class vendor portals: read/prepare/post mechanics, and a wrong attachment field posts the message while silently dropping the file**

**L · 2026-09-16 · A vendor support portal is a second mailbox, and posting to it needs the live page's own field names — a wrong attachment field posts the message and silently drops the file.**

How to read and answer a RattleByte-style osTicket portal (verified end to end on ticket #188880, 2026-09-15/16):

1. The portal is `https://rattlebyte.com/support/` (discoverable from the vendor's own notification mail or by probing
 `/support/`; `/osticket/` and `/helpdesk/` 404). **No password is needed** when the ticket's user address is a mailbox we
 can read: `POST /support/login.php` with `__CSRFToken__`, `lemail`, `lticket` → "Eliyahu - access link sent to your
 email!", and the link arrives at the ticket's user address (`info@lakewoodphoneandtech.com` here, which forwards into the
 connected `lakewoodphoneandtech@gmail.com`). Changing a password was never necessary.
2. The access link 302s to `tickets.php?id=<internal id>` (#188880 → 2553) and sets the session cookie; the page carries the
 full thread, the status, and the reply form.
3. Attachments: `POST ajax.php/form/upload/ticket/attach` (multipart, field **`upload[]`**, CSRF token) → `{"id":N}` — that
 file id is what the reply then references.
4. The reply is a multipart `POST tickets.php?id=<id>` with `a=reply`, the page's **message textarea name**, and the file id
 under the page's **attachment field name**.

**The trap, measured:** both field names are regenerated on every page load (`8a6a7dfc8205cb`, `1d52141adf0cd6` for the
textarea; `c600c0e7233513[]`, `4522f75063ba6b[]` for the attachment), and the file input in the markup has **no `name`
attribute at all** — the name is created by the `filedropbox({...})` JS in the page. That config contains two similarly
named keys: `paramname: 'upload[]'` (the *upload endpoint's* field) and `name: '<token>[]'` (the *form field* for the posted
id). A regex for `name:` matches `paramname:` first, so the first post carried `upload[]=1654`. osTicket **accepted the
message, replied "Message Posted Successfully", set the ticket Open, and silently dropped the attachment** — there is no
error, no warning, nothing in the thread.

**Rules that follow:**
- Parse the field names from the live page immediately before posting, and match the form field with a negative lookbehind
 (`(?<!param)name:`) or by taking the last `name:` inside the `filedropbox` block.
- **Verify a portal post by re-fetching the ticket and looking for the attachment filename and size in the thread**, not by
 reading the POST response. "Message Posted Successfully" says nothing about the file.
- When the attachment misses, a short follow-up message carrying only the file is cheaper and more honest than pretending the
 first message said it all ("My previous message posted without this file").
- Keep the exact text that was sent as a file on disk (`~/phone/rattlebyte-ticket-reply-2026-09-15.txt`); the portal's HTML
 is not a durable record we control, and this vendor's human reply never reached a mailbox at all (L1512).
