**The four `journal.py` copies differ in the id reservation machinery — measured, 2026-10-16.**

The pin-one-journal.py decision looked like a version pick. It is not: the copies differ exactly where
the cross-machine collision defence lives.


**The command surface is identical** — 27 `cmd_` functions on both sides of the cloud/yoga comparison,
the same set, no command in one and not the other, and the same `CACHE_VERSION = 2`. So nothing a
session types is missing on either side.

**Why this decides something.** One of the two options for the writer model is "keep local writes and
make the id reservation ledger actually work" — the ledger is what stops two machines minting the same
number. The code for it is on the **canonical** tree and is **not** in the copy the other machines run.
So that option is not "configure the ledger"; it is "deploy the canonical `journal.py` to every other
machine", which is the pin. The measurement turns a vague choice into a bounded one: 177 lines of
difference, one direction only, same command surface, so a copy is a version change rather than a
behaviour change for anything a session types.

**And the pin is not mine to take while the writer model is open**, because it is the same decision
seen from the other side: pinning the canonical copy onto the other machines gives them the ledger —
which is only useful if they keep writing locally.
