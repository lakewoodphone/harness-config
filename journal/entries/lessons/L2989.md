**L2989 · A dismissed row is not an answered one: a session read the system's own recommendation as the owner's decision, and the work that recommendation named had never been filed**

MEASURED 2026-09-28 19:49Z. A session dropped the priority-1 item I had filed about the production
checkout, and its reasoning was GOOD WORK WITH ONE OVERSTATEMENT. Both halves are worth recording.

WHAT THE SESSION GOT RIGHT, and it is genuinely impressive:
 * "NONE of the 163 ahead-of-master commits is missing from the remotes" - `git rev-list HEAD --not
 --remotes | wc -l` = 0. So nothing in that checkout is lost; the work lives on a remote ref.
 * it verified HEAD is an ancestor of origin/authority-20260928 (merge-base --is-ancestor -> 0);
 * it filed NO duplicate owner row, moved NO branch, and restarted NO service;
 * it found that the divergence had been raised before (owner row 89) instead of re-asking.

WHAT IT OVERSTATED, and this is the part that matters:
 it reported row 89 as "closed 2026-09-18 with DECISION RECORDED: leave master alone". Row 89's own
 status is `dismissed` and its own resolution text begins "NO LIVE OWNER DECISION." What the row
 carries is the SYSTEM'S RECOMMENDATION ("Leave master alone for now"), not the owner's answer.

WHY THAT DISTINCTION IS NOT PEDANTRY. If a recommendation nobody answered can be read as a decision,
then every unanswered question becomes invisible for ever - which is precisely the failure the owner
described when he said problems "just vanish". The rule: A ROW IS ANSWERED WHEN IT CARRIES HIS WORDS,
NOT WHEN IT CARRIES A RECOMMENDATION. `dismissed` is not `answered`.

AND IT EXPOSED A REAL HOLE. Row 89 recommends a tooling-only merge and names the exact files
(app/services/lpt_hub_sync.py, scripts/lpt-sync-to-production.py, taking the authority side). That work
had NEVER been filed - so a recommendation that was never executed looked handled. Filed now as item
#43, with the two files named, the worktree requirement (the live checkout serves a running service),
and an explicit prohibition on touching the 70 personal-insurance documents or the 7 family-chat files,
because row 89 says personal records must not be resolved by a tool default.

WHAT I DID NOT DO: I did not re-open row 89 to the owner. The recommended action ("leave master alone")
is safe, his not having answered changes nothing about the safe path, and the engineering half is now
in the ledger where it belongs. If he wants the per-domain merge he can say so; nagging him about a
question he dismissed is not work.
