**L3476 · A regression test that passes without the fix proves nothing - and four verification methods that lied about it**

**Lesson, measured 2026-10-09, round 3.** I was wrong three times in a row and
only caught it because I insisted on proving a regression test could fail.

## What I claimed

That `shabbat_orchestrator._power_down_critical` raised `NameError` when
`shabbat_graceful_shutdown` is False, because the post-stop pause reads
`sd_res.get("confirmed_down")` while `sd_res` is assigned only inside the
`if settings.shabbat_graceful_shutdown` guard.

**It was false.** The read sits at 8 spaces of indentation — *inside* that
guard — so it is unreachable when the stop is disabled and `sd_res` is always
bound when it runs. I added a default assignment and a comment asserting the
read was unconditional. Both were invented, and the only reason the falsehood
was caught is that I demanded the new test fail without the fix.

## The rule

**A regression test that passes without the fix does not prove the bug exists —
it proves the test does not test it.** Before believing any red/green claim,
make the test fail first and read the failure. If it will not fail, the claim is
unfounded, whether or not the change "looks right".

## Four verification methods that lied to me this round

Each of these reported success while testing nothing. They are worth naming
individually because each felt like evidence:

1. **`pytest` through a PowerShell here-string.** The heredoc injected a blank
 line, so pytest reported `ERROR: file or directory not found: <nodeid>` — and
 my `Select-String -Pattern 'passed|failed' | Select-Object -Last 3` tail still
 printed a line that looked like a result. A collection error masqueraded as a
 pass for several iterations.
2. **`git stash push -- <file>`** to get a baseline. I assumed it stashed the
 change under test; it did not cover what I was comparing, so the "baseline"
 run was the modified file.
3. **A print marker vs a line trace** over "the same" file gave opposite answers
 about which branch executed, because one run used a copy that an earlier step
 had already edited. Two contradicting observations, one stale input.
4. **Reading a tail of pytest output as a verdict.** `-q` prints a single dot for
 a pass; a collection error prints `ERROR:` and no test. Both are one short
 line, and I was filtering for the word I wanted.

The common cause is the same as everything else that went wrong today: **I
trusted a summary instead of reading the thing.** The fix is mechanical:

 * run pytest **in-process or with a plain argument**, never through a shell
 here-string;
 * assert the node id **collected** (`collected 1 item`) before reading any
 verdict;
 * for a bug claim, run the test with the fix **removed** and require failure;
 * pass files between steps by path and re-read them, never by assuming the
 working tree is still what it was.

## Mechanism worth keeping

The decisive check was 20 lines of Python that copied the file, ran pytest via
`subprocess.run([...])` with an argument **list** (so no shell parsing at all),
then did the same with the assignment stripped, and restored the file in a
`finally`. That is the shape to reach for whenever a shell quoting layer sits
between me and a test result. It also made the outcome reproducible in one line:
`WITH fix -> exit 0 | 1 passed`, `WITHOUT fix -> exit 0 | 1 passed`.
