**L3779 · LPT case work: the CLI is on Windows not the authority, lpt-write cannot create an order, and the sync-record schema is closed at the root and on device**

Everything below was measured on 2026-10-13 while working one real walk-in case
(Dell Latitude 5420 will not charge, customer Klein). None of it is in the
lpt-production-case-work skill, and each item cost calls or a failed validation.

1. WHERE THE LPT TOOLS ACTUALLY LIVE. `lpt`, `lpt-write` and `lptcase` are Python
 entry points in C:\Users\ezabz\Code\lpt-ops\bin\ on the Windows checkouts. They
 ARE NOT ON secratary-cloud: `which lpt` there answers "lpt: command not found",
 and a fa code/files search for lpt-ops returns only SKILL.md lines. Do not hunt
 the authority for them. Run them as `python bin\lpt <cmd>` (python is
 C:\Python313\python.exe). `lpt doctor` from the Windows checkout reaches BOTH
 stores and names the route:
 OK operational operational (the shop's work orders; the LIVE WEBSITE reads this)
 db=d5oq83veii4rlb route: ssh secratary -> psycopg2 readonly
 OK app RETIRED archive, orders frozen 2026-09-14
 db=lpt_prod route: ssh lpt-apps -> docker exec lpt-postgres

2. lptcase.py new DERIVES THE FILENAME FROM THE DEVICE STRING. I passed a long
 device description and got a 160-character filename, well past the standard's
 ~70-character limit. Pass a SHORT device string. Renaming afterwards is safe only
 while nothing references the file - but the scaffolder also creates the sync
 record, so rename both and keep case_id == filename.

3. lpt-write HAS NO `order create`. `python bin/lpt-write --help` lists exactly:
 doctor, deploy, vocab, note, status, total, payment, audit, probe.
 The lpt-production-case-work skill (section 7) says orders are created "the other
 way - lpt-write order create, as all of that day's were", and lpt-ops/docs/photos.md
 says the same. Both describe a subcommand that does not exist in this checkout; a
 `git log --all -S"order create"` finds no commit that ever added it.
 CONSEQUENCE, and it is the important one: an AGENT CANNOT CREATE A WORK ORDER.
 When a walk-in has no order - this customer had no order, no customer row, no
 intake case, no ticket and no payment row in the operational store - the case file
 is the ONLY record an agent can write, and the write-back duty in the skill is
 BLOCKED until a human creates the order. Say that plainly rather than reporting a
 write-back that did not happen.

4. THE SYNC-RECORD SCHEMA IS STRICTER THAN IT READS.
 docs/customer-operations/CUSTOMER_CASE_SYNC_RECORD.schema.json sets
 additionalProperties: false at the ROOT and on `device`.
 Legal root keys are ONLY: $schema, caseId, customer, device, labEscalation,
 operational, pricing, production, recordType, references, referral, sourcePath,
 updatedAt, version, workflow.
 `device` allows ONLY `summary`.
 Ad-hoc detail belongs in `references` and `pricing` - both are explicitly
 "documented but NOT closed". I failed validation twice: a top-level `fault` block,
 and serviceTag/serviceTagNote/warranty inside `device`. What validated clean was
 folding the fault facts into `operational.internalSummary` and putting the
 tag/warranty/fault notes in `references`. Always validate before committing:
 jsonschema Draft202012Validator, then print each error's absolute_path - the raw
 ValidationError dump is tens of KB of schema echo and useless.

5. A CASE COUNT MISMATCH IS NOT NECESSARILY YOURS. `lptcase.py check` reports 5
 problem classes across 285 case files (201 sync-record-without-case, 37
 case-without-sync-record, 52 sync-record-deliberately-absent, 22 duplicate-phone,
 143 extraction-warnings) and exits FAILED on 3 of them. All pre-existing. Check
 whether your case is named in the output before treating it as a regression.

6. THE MAIN CHECKOUT IS USUALLY ON A DIVERGED BRANCH - COMMIT VIA A WORKTREE.
 ZABZ-YOGA's lpt-hub was on shift/lpt-sync-20261013-linker-parity, 18 commits
 BEHIND and 18 AHEAD of origin/main, with unrelated modified files in the tree. A
 commit there is invisible to every other machine. The pattern that worked, and
 that also worked for harness-config onto vault/main:
 git fetch origin
 git worktree add --detach <sibling-dir> origin/main
 copy the files in; git add; git commit; git push origin HEAD:main
 git worktree remove --force <sibling-dir>
 Then PROVE it: `git ls-tree origin/main --name-only -- <path>`.
 lpt-hub's origin is https://github.com/lakewoodphone/lpt-hub.git.

7. THE CUSTOMER'S NAME IN THE SHOP'S SYSTEMS IS NOT THE HOUSEHOLD'S NAME.
 216-789-4450 is stored in Dialpad as "Mikaylah Stern"; the voicemail greeting on
 that line says "you've reached OE Klein"; production has NO customer row for the
 number and five unrelated Klein customers; `lpt ticket 2167894450` returns
 "No work order matches ... in either store". Put EVERY spelling in `aliases` and
 say in the body which name each system uses, or the next session will either
 conclude the customer is unknown or file the case under the wrong family.

8. ONE TECHNICAL RULE WORTH KEEPING OUTSIDE ANY SINGLE CASE: a USB-C reading tells
 you nothing until the equipment is eliminated. 5.0 V at 0.22 A is what a healthy
 laptop looks like behind a non-PD charger, a cable with a broken CC wire, OR a bad
 inline meter - an inline meter is a passthrough dongle that measures volts and amps
 and cannot see the PD negotiation layer. Put the same charger, the same cable AND
 the same meter on a known-good PD laptop before condemning the machine.

9. A LONG base64 PAYLOAD THROUGH `ssh host "echo <b64> | base64 -d | bash"` SILENTLY
 DOES NOTHING. A ~6 KB script sent that way exited 0 and printed the base64 back
 while running none of it, and the journal write it was supposed to perform simply
 did not happen; only `git log vault/main` revealed it. Short scripts are fine that
 way. For anything large, write the payload to a file and send the file:
 Get-Content -Raw local.txt | ssh host "cat > /tmp/body.txt"
 then run a SHORT remote command against it - and verify the effect, not the exit code.
