**L2446 · LPT comms live only on secratary: query dialpad_sms_cache over single-hop ssh; created_at is harvest time, not send time**

Read the live comms for an LPT customer from any machine that is not `secratary`: the Dialpad tables live only in `/home/zabz/personal-secretary-mvp/data/secretary.db` on `secratary`, so the documented tool `lpt-hub/tools/customer/dialpad.py` REFUSES off that host (measured 2026-09-24: "REFUSED: secretary database not found at /home/zabz/personal-secretary-mvp/data/secretary.db", exit 1) and `lpt-hub` is not checked out there either (`~/code` on secratary holds only `_worktrees`, `harness-config`, `unified-search`). Working recipe, used to find the unrecorded 2026-09-23 Halon inbound: pipe SQL over a single-hop ssh to avoid the quoting trap -

```powershell
$sql = @'
.mode list
SELECT substr(created_at,1,19) || ' | ' || direction || ' | ' || substr(body_text,1,200)
FROM dialpad_sms_cache WHERE phone_normalized LIKE '%8482217775%' ORDER BY created_at DESC LIMIT 20;
'@
$sql | ssh -o ConnectTimeout=10 secratary-ts "sqlite3 /home/zabz/personal-secretary-mvp/data/secretary.db"
```

Two columns that lie: `dialpad_sms_cache.created_at` is the HARVEST time, not the send time (the same message reappears at each harvest, so one thread held 256 rows for ~12 real messages, clustered at ~30-minute harvest ticks), and `dialpad_call_full` has no `started_at` (use `date_started_ms/1000` with `datetime(...,'unixepoch')`); its `contact_name` does carry the Dialpad caller ID, which is where the spelling "Halon Gali" comes from while the production customer record says `ms halon`. Consequence to carry forward: an inbound message can sit in the authority for days without ever reaching a case file, because nothing harvests it into `lpt-hub` automatically. Read the comms surface before trusting a case file's newest entry, and date a message from the harvest tick it first appears in, never from the column itself.
