**L3842 · SD card that 'says format': three 512-byte USBC records, not a dead card - find the BPB by scanning, extract by FAT, carve last**

## A card that "says format" is not a dead card — it can be three 512-byte sectors

Measured 2026-10-18 on the Bauman Transcend 8 GB SD card (case
`/srv/recovery/cases/20261018-123115-bauman-7322329552`, WO26101812751).

**Symptom.** Every host offered to format the card; photos were not viewable. The obvious reading
— "capacity collapse / counterfeit / dying NAND" — was wrong. The card read at **19.1 MB/s with
zero errors** for the whole 7.51 GiB (`ddrescue -n`, 100 % rescued in 7m 02s, 0 bad areas).

**What was actually wrong.** Three separate 512-byte records beginning `USBC` had overwritten:

| structure | image LBA |
|---|---|
| volume boot sector | 8192 |
| first sector of FAT1 | 12540 |
| first sector of FAT2 | 14462 |

Everything else survived — including a valid copy of the BPB one sector later at LBA 8193 (its
`hidden sectors` field still says 8192, which is how it was identified as a moved copy, not a
different volume) and the FAT32 backup boot sector at 8198. The partition table, the directory
tree and every file's data were intact behind the damage. A host cannot mount a volume with no
boot sector, so it offers to format; nothing about the media was failing.

**The method that found it, in order — reuse this, do not guess the geometry:**

1. **Never assume the filesystem starts where the partition entry says.** Scan the image for the
 filesystem's own type string (`FAT32 ` / `FAT16 ` / `EXFAT ` / `NTFS ` at offset 82 / 3)
 and decode every candidate. That is what surfaced a *valid* BPB at 8193 when 8192 held rubbish.
2. **Then test each candidate layout empirically** rather than reasoning about it: compute
 `data_offset = boot + reserved + nfats*fatsz` for each candidate and read the cluster at the
 root-cluster number. A correct layout yields a directory (`DCIM`, `SYSTEM~1`); a wrong one yields
 random bytes. Here LBA 8193 mounted cleanly and produced a garbage directory (one bogus 1.59 GB
 entry, names of random bytes) while LBA 8192-relative geometry produced **`DCIM`** — so the
 boot sector had been *copied* forward one sector while the rest of the volume had not moved.
3. **Trust the copy of the BPB, not the partition entry**, once the root directory agrees.
4. **Overwrite damage is not shift damage.** Proof: content at the predicted FAT1 offset began
 `81000000 82000000…`, not the `F8FFFF0F` sentinel — i.e. the sector after the clobbered one was
 FAT *sector 1*, so the table had been overwritten in place, and only its first 512 bytes (cluster
 entries 0-127) were lost.

**The extraction that beat carving.** Because only the first FAT sector was gone, the directory
tree and every file's start cluster were intact. A ~150-line reader (`bin/extract-fat-named.py`)
walked the tree, followed the real FAT chain, and fell back to *assumed-contiguous* only when the
chain entry was inside the destroyed sector — 12 of 1,245 files. Result: **1,245 files / 5.18 GiB
written, 1,239 verified decode-clean (4.49 GiB), 0 duplicate hashes**, with the card's own names
(`DCIM/837___03/IMG_2184.JPG`, `MVI_*.MOV`) and its folder structure. PhotoRec was started in
parallel as a fallback and was still running hours later on the same image; the named path was
finished in ~25 minutes. **Carving is the fallback, not the plan, whenever the directories survive.**

**Two name traps.** (1) 55 files came out with a destroyed long-name suffix (`…jpg\xff\xff\xff`)
while their bytes were fine — re-derive the extension from the file's own magic and rename; do not
deliver those names. (2) A DCIM listing can contain entries whose first byte is `0xE5` (deleted):
they must be skipped by the named reader and pursued only by the carve.

**Verification is what makes it a recovery:** PIL decode + 64×64 variance > 5 for images,
`ffmpeg -v error -i … -f null -` for video, then report the verified count only. Six files failed
and were named as failures; one had an unknown type and was not claimed.

**Reusable scripts** (on `zabz-tech-linux`, installed into the case's `bin/`): `sd-intake.sh`
(baseline/detect by diffing `lsblk`, never by guessing `sdX`), `image-card.sh` (refuses the two
customer-media serials on the bench and anything not ~8 GB), `analyse-image.py` (MBR + boot-sector
hunt + signature census), `scan-fs.py` (whole-image filesystem-record hunt — this is the one that
found the real BPB), `fat-probe.py`, `extract-fat-named.py`, `repair-names.py`, `verify-named.py`.

**Reader discipline paid off:** the card went in a `05e3:0749` Genesys reader — one of the two the
playbook has positively controlled — and the 19.1 MB/s read rate exonerated it in one `dd` instead
of an argument. The quarantined `14cd:1212` was not involved.
