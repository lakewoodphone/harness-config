**L3660 · Five wrong answers today, all from assuming a data shape: the cross-check caught them, not the query**

2026-10-13. Five wrong answers in one session, all from the same cause: I assumed the SHAPE of data
instead of looking at it. Recorded as a rule with a tool, not a resolution.

THE FIVE, in order.
1. `i.order_id = o.id` for marketplace items - matched 0 rows, and I reported "581 of 581 purchases
 unitemised" before catching it. The key is `marketplace_orders.order_id`, the marketplace's own
 number ('111-0032200-9576275'), not its integer `id`.
2. `e.detail` on `transaction_evidence` - no such column; the columns are id, transaction_id,
 source_document_id, evidence_type, source, reference, confidence, notes, created_at.
3. `e.reference = o.order_id` - matched 0 rows. The reference is PREFIXED: 'amazon:111-3987908-1529009'.
 The correct join is `e.reference = o.marketplace || ':' || o.order_id`. I very nearly reported 555
 purchases with no link, against a store that only holds 585.
4. Divided `sum(total_amount)` by 100 - the column is REAL dollars, not integer cents, so 10,093.80
 read as 100.94 and looked like a rounding artefact rather than a finding.
5. Earlier the same day: passed the asks store as `acct_db`, and every category lookup failed, which
 made a working answer-resolver look completely broken.
None of these was a subtle bug. Every one was answerable by printing three values.

WHAT ACTUALLY CAUGHT THEM. Not care - arithmetic that could not be true against a figure I had already
measured: 581 of 581 unitemised against 642 known item rows; 555 unlinked against 585 total purchases;
10,093.80 against an average order value near 200. **The cross-check caught it, not the query.** That is
the transferable part: a number derived from an unfamiliar shape should be sanity-checked against a
number derived some other way, and when two of my own figures disagree, the fault is in the query until
proven otherwise.

THE RULE, written as a tool so it is not merely an intention:
`/root/bin/db-shape.py <db> <table> [--col C] [--join OTHER:LEFT=RIGHT]` prints the column names and
TYPES, a few sample values from each side, and the row count a proposed join actually returns. Run it
before any join or aggregate over a table whose shape is not already established in the same command.
It is deliberately dumb: it prints, it does not judge.

USEFUL FINDINGS FROM THE SAME WORK, each independently verified.
- `marketplace_orders.payment_card_last4` is populated on only **97 of 585 purchases (17 per cent)**.
 Reading real emails shows why, and it is not a parser gap: the card is simply NOT in the mail. Three
 Amazon order confirmations (111-1224637-0971421, 111-7011510-1744229, 111-8907809-1144219) contain
 no "ending in", no card brand, no masked digits at all. So extracting a card cannot improve matching
 and `payment_card_last4` should be treated as sparse by design.
- **116 purchases with a total have NO order-to-transaction evidence: 10,093.80**, spanning
 2020-05-10 to 2026-10-12, most in 2026 (38) and 2025 (60). This is the honest figure for "orders whose
 charge I could not find in the ledger", and it is NOT the same as "money missing from the books":
 some are Amazon gift-card balances, some are eBay orders settled through PayPal, and the matcher's own
 `ambiguous` state is a candidate that exists without a confident link. Establishing which is which is
 the next unit, and it needs the ledger's side examined order by order rather than counted.
