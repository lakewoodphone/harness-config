**L12252 · Reading a DoH refusal off a Caddy log (size equals query length) - and what it shows: 12 minutes of all-negative asset answers across a reboot**

## How to read a DoH refusal off a Caddy log: blocked replies echo the question, so size equals query length

Measured 2026-10-22 15:25-15:33 UTC on waze-mdm-01. Technique worth keeping; result worth keeping. Supersedes nothing, sharpens `L12251`.

**The technique.** Caddy logs the DoH `uri` with the base64url DNS message; `doh_filter.py` answers a refused name with `_response(message, 3)`, which echoes the question and appends no records, and answers an allowed name by forwarding the upstream reply. iOS pads its DoH queries to 128 bytes, so a refused query is `len(uri-message) == len(response)` and an allowed one is longer. The Caddy record carries `size`, so **the verdict for any query is computable from the access log alone, including for windows where the filter's own log was destroyed.** Validated on the 26 device rows that overlap the surviving filter log: 26/26 join on (second, name), 0 mismatches.

**The result, for the device that was on the bench (172.59.214.144, ~0.75 confidence: only client in the window carrying the full 12-host Apple asset set, two iOS boot sequences, one 301-second dark span bracketing the 14:48 reboot).** Between 14:39:53 and 14:52:23 — twelve minutes, across a reboot — every asset host was refused: `mesu.apple.com` 12, `gdmf.apple.com` 15, `bag.itunes.apple.com` 12, `updates.cdn-apple.com` 9, `cl2.apple.com` 6, `cl3.apple.com` 6, `configuration.apple.com` 6, `apps.mzstatic.com` 6, `fpinit.itunes.apple.com` 6, plus the location CNAMEs. **No name ever received a positive answer while it was blocked.** Positives in that window were only `time.apple.com`, `init.push.apple.com`, `ocsp2.apple.com` and `time.g.aaplimg.com`. The device re-tried the whole asset set every 85-370 seconds (gdmf at +85/+94/+136/+364 s; mesu at +168/+100/+365 s) and got its first positive on `mesu.apple.com` at 14:52:56, nineteen seconds after the restore.

**What that means.** A client that keeps retrying the same names for twelve minutes is a client that is not getting what it asked for from us. So the download the owner reported completing at those taps was **not** obtained through our resolver. Two branches remain and only a device test separates them: (a) iOS fell back to the carrier resolver — the documented `AllowFailover` path, which we cannot see in this log at all, and which was switched on 2026-10-21 00:47:49; (b) no bytes moved and the asset was locally retained, with the tap merely re-enabling it after an unsuccessful catalog check. Airplane mode spinning is consistent with both and discriminates neither.

**Corollary for the fix.** `AllowFailover=false` is the only change that closes branch (a) from our side, and it also makes branch (b) visible: if the download still completes with no resolver available at all, it was never a network fetch and no network control will ever close it.
