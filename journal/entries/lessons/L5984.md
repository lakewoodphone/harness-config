**L5984 · The rescue, the audit and the CP1252 write all forget the same field: ask what WROTE it**

Measured 2026-10-16 on the CFO ledger, three instances in one session. (1) transaction_categories.justification held 40 rows written as CP1252 - all 40 on one day, 2026-03-12T17:39:02, one import, one em dash (byte 0x97). A default read of that column CRASHES on them, so every consumer of a justification is already decoding lossily or broken, and nothing noticed for seven months. H614 had already recorded the same class on 2026-09-20: the legacy ledger's TEXT is CP1252 and one en dash silently killed the entire legacy seed. (2) 871 transaction_categories.id values are NULL because a legacy importer wrote the row without its TEXT primary key; filtering tc.id IS NULL therefore matches 607 rows where only about 200 are actually uncategorised, overstating unexplained money by 56,863.48 USD. (3) A WAL-mode sqlite file's sha256 does not change while its visible rows do, so a fingerprint taken from the file is not a fingerprint of the data. The rule that catches all three: before trusting a field, ask what WRITES it, and whether the value you are reading is the thing you think it is. Repair for (1): re-encode under flock after a backup, verified by comparing the INTENDED text on both sides - 7,696 rows, 7,696 preserved, 0 changed, 40 CP1252 rows to 0.
