**A customer's newest inbound can exist in the LIVE store only. Read BOTH stores before writing "no reply has gone out".**

Measured 2026-10-12 on Halon / 8482217775 (`lpt ticket 8482217775`, both stores asked in one call):

| store | newest comms row for this customer |
|---|---|
| `operational` (live) | **2026-10-06 22:09:27** SMS INBOUND, `communications` id 139553 - "Hi, I got a battery. Can I swing by some time for you to put it in?" |
| `app` (retired archive) | **2026-09-24** SMS OUTBOUND, id 126831 |

The newest inbound did not exist in `app` at all. The two stores are read in the same command and printed under separate headings, so the divergence is visible - but a session that reads only one of them, or that reads `ps_comms_person` alone, gets a **12-day-stale "the last thing that happened was ours"** picture, and would have told the owner nobody was waiting when the customer had been waiting 5.8 days.

**Rules:**
1. `lpt ticket <key>` asks both stores and labels each. Read both blocks; a row present in one and absent in the other IS the finding (case-work skill section 1).
2. `ps_comms_waiting` was the tiebreaker that made this unambiguous: it listed party `8482217775` at **139.9 h** waiting, index age 0.05 h. It reads the live surface. Use it to corroborate, never as the only source.
3. Never infer "we replied" from the absence of an inbound row in one store. Absence in a store whose `orders` froze 2026-09-14 is not absence of the message.

**Why this is worth an entry:** the failure mode is reporting health from a stale store - the estate's most expensive documented error (P3, and the Otter class). Here the stale store made us look *good* (nothing unanswered) rather than bad, which is exactly how it slips past review.
