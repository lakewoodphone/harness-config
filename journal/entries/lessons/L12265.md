**L12265 · Driving the LPT assessment end-to-end: five item types, stable testids, and where the report payload lives**

Driving the personality assessment end-to-end (personality.lakewoodphoneandtech.com) without touching product code. Measured 2026-10-22 on the split-synthesis build 4c44fc5.

THE FIVE ITEM TYPES, and why a naive role=radio driver stalls:
1. 5-point Likert - real [role=radio] buttons (Strongly unlike me ... Strongly like me). Text labels change per module (appealing / important / agree), so answer by INDEX, not label: index 3 of 5 is the "mostly" positive end on every 5-point scale here.
2. 3-option forced choice - also [role=radio]; rotate the index.
3. Multi-select "choose up to four" - plain <button aria-pressed> toggles, NOT radio. Continue silently no-ops until enough are selected, so it looks like a dead button, not an unanswered item. Detect via the card text "N of M chosen".
4. Free text - a <textarea> with no testid; set value through the native setter and dispatch input+change.
5. Checkpoint cards - text "…is finished — writing your checkpoint" auto-advances, but the summary card then waits for an explicit "Continue <name>" click.

STABLE ANCHORS (use these, not body text scanning): article[data-testid="question-card"], [data-testid="question-answer-options"], [data-testid="question-continue"] button, [data-testid="question-progress-overall"] ("Question 102 — at least 96, up to 174"). Scanning the whole document for aria-pressed finds toggles OUTSIDE the card and produces clicks that do nothing.

STATES THAT LOOK LIKE BREAKAGE AND ARE NOT: the app drops to the library screen mid-run (the resume CTA is "Continue my assessment — N answered" / "Carry On From Where I Stopped"), and "New Attempt Without Previous Context" RESUMES the existing attempt rather than starting clean. Clicking via element.click() after scrollIntoView beats locator clicks here; locator clicks were landing on overlays.

WHAT THE REPORT EXPOSES (useful for future verification): POST /api/assess returns the whole final-report payload including meta.reportParts (five entries with status written), meta.modelUsed, meta.fallbackUsed, meta.executionMs, meta.reportQuality. Reading that payload is far more reliable than scraping the DOM for the banner. GET /api/persistence returns the full session with responseHistory createdAt per item - that is the honest source for "how long did the run take", not my own stopwatch.
