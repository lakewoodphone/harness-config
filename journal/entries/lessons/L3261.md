**L3261 · docker inspect prints env VALUES - a name-matching filter on it leaks the secrets; use the deploy script's presence checker**

## 2026-10-05 · ZABZ-TECH · `docker inspect` prints env VALUES - never grep its output for variable names

WHAT I DID WRONG. To confirm that recreating the container had not dropped the `R2_*` variables, I ran:

 ssh lpt-apps-01 "docker inspect lakewood-rentals" | Select-String -Pattern '"R2_|"ADMIN_|"PHOTO_CONTENT'

The filter matched **the whole line**, and every env line is `"NAME=value"`. So the output was the
actual values: the Google AI key, `R2_SECRET_ACCESS_KEY`, `R2_ACCESS_KEY_ID`. I leaked live
credentials into this session's transcript with a command whose entire purpose was to check that
credentials were intact. Precedent: P13b ("I leaked a live API key into the session transcript").

THE RULE. `docker inspect` (and `docker compose config`) print secrets by design. Never pipe them to a
matcher that can capture a value.
- Names only, from inside the container: `docker exec <c> sh -c 'env | sed "s/=.*//"' | sort`
- Names only, from the host, with no shell quoting hazard at all:
 `docker inspect <c> --format "{{range .Config.Env}}{{println .}}{{end}}"` **piped into a local
 `ForEach-Object { ($_ -split "=")[0] }`** — the split must happen on the LOCAL side of the pipe.
- Presence-only assertions: `docker exec <c> sh -c 'test -n "$R2_BUCKET" && echo SET || echo MISSING'`.
- The repo already had the right tool and I should have used it first: the rentals deploy script's env
 stage reports "`R2_BUCKET is set in the container`" for 22 variables and never prints a value. When a
 script exists whose job is this check, run the script.

SAME SESSION, SAME CLASS, SECOND INSTANCE. An earlier command in this session tried the reverse trick
(`grep -oE '^[A-Z_]+=' file | tr -d '='`) and it worked on a `.env` — the mistake was specifically
using a line-filter on `docker inspect`, whose output is not a `.env`. Know which format you are
looking at before you filter it.

WHAT MUST BE ROTATED. The leaked values: `GOOGLE_API_KEY` (the system-wide Google AI key, shared with
personal-secretary-mvp — rotating it is a cross-service change, not a one-repo fix) and the
`R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` pair (already the subject of owner-queue #47, which the
owner dismissed on 2026-09-15; the bucket is now the dedicated `lakewood-rentals-media` but the
credential's scope is still unverified). Reported to the owner in the same turn, plainly.
