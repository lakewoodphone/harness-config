**L10431 · Phone engine 0.2.1 refused to start (status 2) because the profile anchor holds its own 487-package 0.2.0 pnpm tree - the script rolled the whole switch back and the phone stayed up**

ATTEMPTED AND ROLLED BACK 2026-10-20 00:24Z on secratary-cloud (`phone-engine.service`, the owner's phone).

WHAT WAS DONE: installed 0.2.1-rc.2 at /opt/dsh-phone-0.2.1 (615 packages, node22 confirmed: `--version` prints
0.2.1-rc.2 and the module imports), corrected the /root/.dsh config for 0.2.1 with the service stopped (7 lines:
`ctx.webRuntime` -> `ctx.webStartup`, three preset `{{cwd}}` suffixes), and PROVED the correction with a compose
before touching the service: `rows=421 ctx.webRuntime=0 {{cwd}}=0`, exit 0. Then swapped the trees by rename and
started the unit.

WHAT HAPPENED: the new engine exited with **status=2/INVALIDARGUMENT** on every start attempt (restart counter went
to 6). The script's ladder did what it was written to do -- it moved the candidate aside to
`/opt/dsh-phone.failed-20261020T002419Z`, restored /opt/dsh-phone and the config backups, and started the old
engine. Verified after: service **active**, version **0.2.0-rc.2**, port 3089 answers **HTTP 401** (up, token
required). Nothing was deleted and the phone kept working.

THE CAUSE, read from the engine's own stdout log, and it is NOT the config:
 scope: TWO COPIES - /opt/dsh-phone/node_modules/@deepseek-ai/dsh-scope vs
 /root/.dsh/profiles/web/node_modules/.pnpm/@deepseek-ai+dsh-scope@0.2.0-rc.2_.../node_modules/@deepseek-ai/dsh-scope
 (every prompt will be rejected as session/agent-busy)
`/root/.dsh/profiles/web/node_modules/.pnpm` holds **487** packages, a complete pnpm dependency tree pinned at
0.2.0-rc.2. On this box the profile's own module anchor is a real vendored tree, not links to the engine, so a
0.2.1 engine loads 0.2.0 copies of its own packages and refuses to run. That is the same class as P2837 (a module
anchor a child could not traverse) and the stage-home anchors measured on 2026-10-19 -- the anchor is part of the
engine version, not independent of it.

WHAT WOULD FIX IT, in order of preference:
 1. rebuild that anchor against the candidate (`pnpm install` in /root/.dsh/profiles/web with the 0.2.1 engine
 root), then repeat this exact script -- everything else is proven;
 2. or replace the anchor with links into /opt/dsh-phone/node_modules (what the Windows machines do), and accept
 that the profile then follows the engine;
 3. or leave it: the phone engine is a separate, working 0.2.0 install and nothing else depends on it.

THE PART WORTH KEEPING: the switch was a script with a ladder -- stop, fix config, PROVE the config by composing
with the candidate binary, swap by rename, start, verify, and roll back the tree AND the config on failure. It
failed safely, unattended, and left the owner's phone working. That is the pattern to copy for every service
switch on this estate.
