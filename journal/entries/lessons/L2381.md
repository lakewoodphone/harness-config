**L2381 · Guard rule 1 short-circuits, so 'matched customers=[none]' in a dry run is NOT evidence the customer is missing**

## L2407 · 2026-09-24 · Reading a guard's summary line as a finding

On re-running the dry run after a successful push, `lpt-sync-to-production.py` printed:

```
Decision: SKIP
Reason: record already references live production order WO26092412720 via workflow.orderId
Guard: db_opened_read_only=True, matched customers=[none], orders considered=0, sibling records compared=0 (rule could not fire)
```

`matched customers=[none]` looks like the guard failing to see a customer that had just been created
for exactly that phone — the "defect A" class the code's own comments warn about. It is not. Rule 1
(does the record already name a live production order?) returns at line 938, BEFORE Rule 2 does the
phone lookup at line 956, so those fields are simply the untouched defaults in the decision dict.

CHECKED RATHER THAN CONCLUDED: calling `_customers_by_phone` directly on the same read-only
connection returned 2741/2742/2743 for the three phones. So the matching is intact.

RULE. When a tool prints a summary of a decision it made, work out WHICH rule reached first before
treating a zero in that summary as a measurement. A zero produced by a short-circuit is not a
reading. (This is the same disease as the "empty result is a refusal" rule: the fix is to name the
rule that fired, and this tool already does — the `Reason:` line names `workflow.orderId`. Read the
Reason before the Guard block.)
