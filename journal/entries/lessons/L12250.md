## Waze dictionary: the payload host is named and our own PAC tells the phone to go round the block

Read 2026-10-22 15:55-16:05 UTC on ZABZ-TECH against waze-mdm-01. Corrects the open item in `L12249` (which listed the serving host as unknown) and the store-family guess. D9352 (declarative key) still stands and is still the card-level fix.

**The catalog, fetched and parsed by me.** `https://mesu.apple.com/assets/com_apple_MobileAsset_DictionaryServices_dictionary2/com_apple_MobileAsset_DictionaryServices_dictionary2.xml` → HTTP 200, 909,016 bytes. Asset type `com.apple.MobileAsset.DictionaryServices.dictionary2`, 523 assets. Distinct payload hosts across the whole catalog: `updates.cdn-apple.com` 255, `appldnld.apple.com` 149, `updates-http.cdn-apple.com` 119, `www.apple.com` 1. **Matches for `itunes` or `mzstatic`: 0.** So the store/App Store family in the DoH log is background, not the dictionary; `iphone-ld` (819 refusals) was never the host either — `ld` is language data for Siri.

**Both of our gates say no, and one of them says yes.** Live filter env: `updates.cdn-apple.com ALLOWED=0 BLOCKED=1`, same for `updates-http.cdn-apple.com` and `appldnld.apple.com`; `mesu.apple.com` and `gdmf.apple.com` are ALLOWED (catalog and MDM). The served PAC (`/opt/waze-mdm/proxy/waze-webtrap.pac`, byte-identical to what the URL serves, blob `3f5956ee…`) carries all three payload hosts at **lines 2-4 in `DIRECT_DOMAINS`**, which is evaluated before every block list. So the resolver refuses the payload host and the PAC instructs `DIRECT` for it. That disagreement is exactly what `filter-parity.py` exists to catch, and its manifest never covered these three hosts.

**Therefore the address came from somewhere that is not our DoH.** The device asked (`updates.cdn-apple.com`, 219 refusals in the decision log) and got NXDOMAIN, then downloaded. The only documented mechanism that permits this is the DNS payload's own escape hatch: `AllowFailover=true` (`profiles/waze-siri-filter-dns.mobileconfig:34`), which Apple's DNS-settings documentation describes as allowing failover to the default system DNS resolver. That is the one untested branch, and it was open in all four of yesterday's tests.

**The test that closes it, and its two outcomes.** Deploy the DNS payload to one device with `AllowFailover=false`, remove the three payload hosts from the PAC's `DIRECT_DOMAINS`, reboot, tap one dictionary.
- Fails to download → mechanism confirmed; the fix is the profile key plus the PAC correction, no entitlement and no money, and the OS-update catalog can stay reachable if `mesu.apple.com` is left alone (255 of 523 payloads come from `updates.cdn-apple.com`, so blocking payloads alone is sufficient for dictionaries).
- Still completes → DNS is not the gate at all and the asset is either already local or fetched over a path we do not control; the packet-level view (existing IKEv2 tunnel + `WAZE_VPN_EGRESS` LOG rule, see `L12249`) becomes the only instrument worth building.

**Do not repeat:** `gateway.icloud.com`, `bag.itunes.apple.com`, `apps.mzstatic.com`, `iphone-ld.*` — none of them appears in the catalog. Any further host list must be derived from a catalog fetch, not from the DoH log.
