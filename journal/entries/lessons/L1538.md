**L1538 · A detached worktree at my own commit made rebase republish 30 stale commits; and 'Everything up-to-date' is not success**

While landing the activation-lock fixes I set up a worktree with `git worktree add --detach <wt> <my-commit>` and then
ran `git rebase origin/main` inside it. That reconstructed the LOCAL branch's history from my commit, so the rebase
replayed 30+ local-only commits of a stale master onto origin's tip — and the subsequent `git push HEAD:main`
published one of them (a Lenovo IdeaPad case commit) to origin/main before anyone noticed.

Damage assessment, measured: exactly one commit and three files reached origin, all of them **additions** — `git diff
--name-status` showed three `A` entries, so nothing existing was overwritten and no newer work was regressed. I then
confirmed those three files were a customer case file (new, from another machine) and a device-sourcing doc
(pre-existing) — two different documents, not a duplicate, so nothing needed deleting. Net harm: a stale commit from
this machine is now in the shared history. Recoverable clutter, not data loss, but only by luck.

The rule that prevents it: **a detached worktree at commit X means `rebase` will rebuild X's ancestors.** To land one
commit on a moved remote tip, either cherry-pick it onto an `origin/<branch>` worktree, or — when the tree keeps
moving under you — copy the changed files onto the fresh tip and commit *there*. Never rebase inside a worktree whose
HEAD is your own commit on a diverged branch. The push was the moment it became unrecoverable; a `git log --oneline
origin/main..HEAD` before pushing would have shown 30+ commits queued and stopped it.

Second rule, same incident: I reported "pushed" twice when the output said `Everything up-to-date` and a
cherry-pick had actually conflicted. **`Everything up-to-date` is not success** — it means nothing was sent. Verify
the content is on origin with `git show origin/main:<path>` and grep for the text, never trust the push line alone.
