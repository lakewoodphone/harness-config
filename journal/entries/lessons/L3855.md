**L3855 · A transferred customer drive: probe writes inside a folder not at the root, and the profile ACL is the handover blocker - not the drive**

Three measured traps from the Schreiber data-handover job (ticket 2657, WO26100812737), all of which cost calls and two of which nearly produced a false claim.

1. A FAILED WRITE AT THE ROOT OF A HEALTHY VOLUME IS NOT EVIDENCE OF WRITE-PROTECTION.
`Set-Content E:\.probe` returned "Access to the path is denied" on a drive that was in fact perfectly writable. A Windows system volume's root ACL grants BUILTIN\Users "create folders / append data" but NOT "write files", so a root-level FILE write fails for any non-elevated user while the volume is fine. Correct probe: `New-Item -ItemType Directory E:\<name>` then write a file INSIDE it. The wrong probe would have had me report the customer's drive as read-only and start hunting for a bridge write-protect switch that does not exist.

2. A TRANSFERRED WINDOWS PROFILE IS ACL-BOUND TO THE ORIGINAL SID, AND THAT IS THE HANDOVER BLOCKER, NOT THE DRIVE.
On the Schreiber drive (mounted E: on ZABZ-TECH 2026-10-19), `E:\Users\User` returns "Access is denied" and `Get-Acl` on it fails "Attempted to perform an unauthorized operation", while the volume itself reads and writes normally. Its permissions name the old account's SID, which exists on no other PC. Consequence for handover: an ADMINISTRATOR account on the new PC gets the standard "you don't currently have permission" prompt and one Continue click opens it; a STANDARD account cannot open it at all. Test handover readiness by listing the customer's own profile folder as a non-admin, never by testing the volume root. Clearing it needs elevation (`takeown /F E:\Users /R /A /D Y` then `icacls E:\Users /grant *S-1-5-32-545:(OI)(CI)(RX) /T /C`) and an unelevated DSH session cannot do it: `whoami /groups` shows BUILTIN\Administrators as "Group used for deny only" and approval prompts are disabled, so this is an escalate-to-owner item, not a retry.

3. CASE WORK LANDS ON A PER-SESSION BRANCH AND IS INVISIBLE UNTIL IT REACHES MAIN — AND BOTH CLONES WERE OFF MAIN.
Measured 2026-10-19: the ZABZ-TECH clone of lpt-hub was on `shift/lpt-sync-520-dup-phone-nonstructural`, 108 behind / 164 ahead of origin/main with 244 dirty files; the authority's clone at /home/zabz/repos/lpt-hub was on `shift/lpt-sync-313-shande-pricing-held-20261015`, 33 behind / 1 ahead with 8 dirty. Committing to either branch does not put the case where `audit.py`, `sync-health-audit.py` or another machine can see it, and merging 164 diverged commits is not a safe incidental. The cheap correct route, verified this session: `git diff --stat HEAD origin/main -- <files>` to prove the committed file content is identical, then `git worktree add /tmp/x --detach origin/main`, `git cherry-pick <commit>`, `git push origin HEAD:main`, remove the worktree. That moved the Schreiber case onto main as 691bc47ed without touching either dirty clone. Check `git rev-parse --abbrev-ref HEAD` BEFORE editing a case file, not after.

Two smaller ones, same job. `lpt-write note add` refuses any note over 4000 characters and says so - count before composing, not after (mine was 4206 and had to be rewritten). And `lpt-write total set --amount` is PRE-TAX: to land a customer-facing 60.00 pass 56.27 (56.27 + 3.73 tax at 6.625%), which the dry run prints back as "60.00 to pay" - so dry-run the total and read that line rather than trusting the flag's own help text, which says "what the customer owes".
