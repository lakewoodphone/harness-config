**L3449 · A hostname in a URL is not a host - api.lakewoodphoneandtech.com is the Hetzner VPS, not secratary**

## L — A hostname in a URL is not a host: I proved the wrong machine was up and sent the owner to the office

MEASURED 2026-10-09. The owner asked "is the secretary still down? why don't you fix that also", then
"if it's off you are supposed to be able to lan wake it, we set up systems for this, what the hell is
going on".

WHAT I DID WRONG, exactly. `curl https://api.lakewoodphoneandtech.com/health` answered HTTP 200 with
`"uptime":33264`, database healthy, redis healthy, twilio healthy. I read that as "secratary is up and
has been up 9.2 hours", told the owner the machine was running and that Wake-on-LAN therefore did not
apply. Both statements were FALSE. `api.lakewoodphoneandtech.com` resolves to **2.28.33.58 — the Hetzner
`lpt-apps-01` box**, not secratary (verified: Resolve-DnsName; and the response carries Caddy's
`Via` header). The 33,264 s was the VPS's uptime. **secratary was genuinely powered off**, and the owner
had to drive to the office and switch it on at 17:37:39.

THE DISCRIMINATOR I DID NOT RUN, and it costs five seconds: secratary's OWN API on loopback answers a
DIFFERENT SHAPE — `{"ok":true,"time":...,"database":{...},"autopilot_enabled":...}` with no `uptime`
field at all. Different shape = different program = different host. A single `curl 127.0.0.1:8002/health`
ON the box would have settled it.

RULE: an HTTP 200 from a URL is evidence that SOMETHING answered, never that THE BOX YOU MEAN
answered. Before using a health endpoint as proof of a machine, resolve the name and read which host
produced the body — or ask the machine itself on its own loopback. This is pain P3, the same class as
the stale-database crisis that this estate already paid for once; it was re-earned here, not newly
learned.

WHAT IT COST: a trip to the office that a five-second check would have made unnecessary. The
correcting document is docs/mesh/120-office-offline.md, which the owner's own correction produced.

SECOND, SMALLER FINDING FROM THE SAME EVENT: the WoL path is real and correct — MAC
34:17:eb:9f:f5:e0, target 192.168.50.77, BIOS WoL enabled 2026-09-02,
/etc/systemd/network/10-eno1.link WakeOnLan=magic — BUT `wake-secretary.ps1` exists ONLY under
`_fleet/co2026/*/scripts/`, which is scratch and not version-controlled. A wake tool that lives outside
the repo is one `rm -rf _fleet` away from not existing.
