**L3766 · A negative is not a finding until you describe the positive you expected and look for it by name - I did this twice in one session**

MEASURED 2026-10-13, twice in the same session, on the same screen.

**Two claims I made and then had to withdraw:**

1. *"The Counter renders no work orders."* The screen renders twenty-five. I measured `tableRows: 0`
 and `document.querySelectorAll('a[href*="/work-orders/"]').length === 0` and concluded the list was
 missing. It was a `ul` of 80px buttons.
2. *"The counter wastes half a 1920px window."* The row is 955px inside a 1280px container, so I
 called the remaining 325px unused. It is a `<aside data-testid="work-orders-side-panel">` —
 "At the counter", ready-for-pickup and waiting-on-parts counts. Deliberate, useful layout.

**Both are the same error: I measured one thing and concluded another.** I measured a *box* and
concluded *emptiness*. I measured *zero matches* and concluded *absence*. Neither conclusion follows
from the measurement.

**And in both cases I had a second, "independent" check that failed the same way**, because it was
built on the same missing step. The first shared the walker's assumption about the shape of a work
order. The second measured the same box and inferred the same emptiness. **Running a second method is
worthless if neither method asks what the number MEANS.**

**THE RULE, and it is the version of this lesson that would actually have caught both:**

> Before reporting a finding that says **something is missing, empty, unused or broken**, name the
> thing you expect to be there and go and look for it **by name**. "No table rows" must be followed by
> "what IS the list?" "325px unused" must be followed by "what is in that 325px?" A negative is not a
> finding until you have described the positive you expected to find and shown it absent.

This estate's own vocabulary already says it — *an empty result is not evidence of health, it is a
refusal* — and I had it in front of me. What was missing was the corollary: **an empty result is also
not evidence of a defect.**

**COST:** a false "the shop cannot see its work orders" reported to the owner as serious, at the top of
a roadmap; then a second false finding, opened as a PR, one round later. Two rounds of work spent
retracting instead of building. **The instrument that produced them is the same instrument the daily
loop depends on**, which is why fixing the instrument (PR 393: read the screen's own `data-row-count`)
matters more than any single finding it produces.
