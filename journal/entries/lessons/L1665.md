**L1665 · A derived column that nothing refreshes is not provenance**

## Rule

**A column that is derived and never refreshed is not provenance — compute the value
from the event that carries the timestamp, and report the drift.**

## The case

`owner_decision_queue` holds both `asked_at` (when the row was inserted) and `age_days`
(a bare integer). The CLI's `next` sorts on the stored `age_days`. Measured
2026-09-15:

| id | stored age_days | asked_at | true age |
|----|-----------------|----------|----------|
| 15 | 0 | 2026-09-14 05:43 | 1.5d |
| 14 | 3 | 2026-09-14 05:43 | 1.5d |

Two rows inserted in the same batch, from the same retired `QUESTIONS.md`, carry
different stored ages, and neither matches the timestamp beside it. The stored value is
carried-over text from a queue that no longer exists. Any surface trusting it tells the
owner a different age than another surface does for the same question — and the queue's
whole purpose is that he can trust the age.

## What to do instead

1. Compute age from `asked_at` and say so in the code comment.
2. Keep the stored column only as a fallback for rows with no timestamp.
3. Report a mismatch of a day or more in the metrics (`age_column_stale_ids`) instead of
 silently preferring one number. The drift is itself a finding; hiding it produces two
 surfaces that disagree and look equally confident.

## Second instance of the same class, same round

`settings_overrides.use_dynamic_registry` said `true` (2026-03-06); `.env` said `false`;
the chat gate reads the `.env` value. Two stores, one question, no single source of
truth, and the stale one was the only place anybody had ever stated an intent. Aligned
rather than deleted, because `app/main.py` loads these overrides and every reader had
not been traced.

## Evidence

- `check_owner_queue` metrics on 2026-09-15T17:14Z: `next_age_days: 1.5`,
 `age_column_stale_ids: [15, 14]`.
- Kernel commit `9962993` in `~/ceo-kernel`.
