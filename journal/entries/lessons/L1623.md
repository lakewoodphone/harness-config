**L1623 · Turbopack root must enclose both the project and the real node_modules; removing turbopack.root does not fix a junctioned worktree**

Turbopack confines symlinks to its "filesystem root" and the root MUST ENCLOSE BOTH the project directory and the real, resolved location of its node_modules. This breaks git-worktree isolation whenever a worktree's node_modules is a junction/symlink to the main clone.

So "just remove turbopack.root" does NOT fix it, and it is not a no-op either: with the setting absent, Next auto-detects the root from the nearest lockfile, a worktree has its own package-lock.json, so the detected root is the worktree and node_modules escapes it. Deterministic failure.

Measured 2026-09-15 in the chumash-timeline repo, worktree at _worktrees/.../chumash-deploy with node_modules -> C:\Users\ezabz\Code\chumash-timeline\node_modules:
 root REMOVED -> FATAL TurbopackInternalError "Symlink [project]/node_modules is invalid, it points out of the filesystem root", exit 1 (reproduced twice)
 root = common ancestor C:\Users\ezabz\Code -> Compiled successfully, exit 0
 root REMOVED + `next build --webpack` -> Compiled successfully, exit 0
The accepted fix derives the ancestor at config load: if node_modules is a symlink, walk up until an ancestor contains realpathSync(node_modules); otherwise return the project dir, so a normal clone and the container are unaffected.

Side effect worth knowing: widening the root also changes the standalone output layout. `output: "standalone"` writes paths relative to that root, so a worktree build produces .next/standalone/_worktrees/<...>/server.js with the traced node_modules as a SIBLING, which is not runnable in place. Harmless for the deploy path (in the image node_modules is real, so root=/app and the output is flat at /app/server.js), but a worktree cannot produce a runnable standalone artifact.
