**L1527 · Fire-and-forget threads make tests order-dependent, and a path resolved at call time turns a leaked thread into cross-test state**

**Fire-and-forget threads make tests order-dependent, and the pathway is the database path resolved at call time.**

Measured 2026-09-15. The residual suite flakiness (`TestWorker::test_worker_extracts_memory` and
`test_worker_clears_in_flight_after_send`, alternating between runs) had survived three explanations,
two of them wrong. What settled it was measuring the *right* unit:

- those two tests in isolation: **0 failures in 24 iterations** -- so the fault is not in them;
- the same tests inside their file: intermittent -- so the fault is the *interaction*;
- reading the interaction: `hub.handle_inbound_sms` -> `personality.maybe_respond` -> a daemon thread
 that no test joins, writing `chip_in_flight_until` through a module whose database path is resolved
 **at call time** and monkeypatched per test.

So a worker from test A wakes during test B and sets B's in-flight marker, and B's worker returns
early.

Rules:
- **Measure the unit that fails.** Isolated, then in-file, then in-suite: the first measurement ruled
 out the test, the second localised it to the neighbours, and only then was reading the code useful.
 Two of my three earlier hypotheses died precisely because I reasoned across that boundary.
- **A fire-and-forget thread is a test-order dependency unless the test joins it.** Any test that
 exercises a path spawning one should either stub the spawn or wait on it; leaving it running makes
 the *next* test's outcome depend on timing.
- **Resolving a path at call time turns a leaked thread into cross-test state.** The DB fixture
 monkeypatches the path per test; the thread reads it whenever it wakes. Capturing the path at spawn
 would make the leak harmless -- the better property, and the one written up for next round.
