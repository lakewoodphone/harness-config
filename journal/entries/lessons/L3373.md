**L3373 · The fence asked 'does this file claim validity' when the question was 'is this host still being renewed' - a lease untouched for two hours still made me a leader**

GOAL ROUND 19. I went looking for a dependency nobody had checked and found one: TIME. A lease is arithmetic on clocks, so I read app/services/leadership.py and found read_lease() comparing ONE number - an absolute expires_at written by the local renewer - against the local clock, and asking 'does this file claim to be valid?'. The question that matters is 'is this host STILL BEING RENEWED?'. MEASURED ON THIS BUILD: a lease file with expires_at 27 hours away whose mtime was TWO HOURS OLD returned may_send()=True (lease-held) and epoch_is_fresh(4)=True. A host that had not spoken to the arbiter in two hours still believed it led and would have kept draining the outbound queue - TWO WRITERS in a two-host company, which is the exact failure the whole lead/follow design exists to prevent. It needs nobody to be careless: a box booting with a wrong clock (the office machine had been off for seven hours that night, which is what made me look), an NTP step, or a renewal written while the clock was wrong. FIX - THREE CONDITIONS INSTEAD OF ONE: (1) a named holder; (2) expires_at in the future AND not beyond a one-hour horizon, so an impossible claim is refused even when the file is fresh; (3) the file refreshed within COMPANY_LEASE_MAX_AGE (300s = two and a half missed renewals of the 2-minute renewer) AND an mtime that is not in the future - an mtime ahead of now means the clock moved backwards and freshness cannot be established at all. Condition 3 is deliberately RELATIVE (now minus mtime, one clock), so a single clock step cannot fake it in the unsafe direction. VERIFIED FROM BOTH SIDES, 7 cases: renewed 10s ago True; 4 min ago True; not renewed for 10 min False; claims 27 hours False; mtime in the future False; expired False; empty holder False; no file False. Ten of them are now regression tests. AND ONE THING I GOT WRONG, caught by my own test: I asserted that with COMPANY_FENCING off the host would refuse; it failed with (True, 'fencing-disabled') == (False, 'no-lease') because fencing off is the CURRENT production default (fencing is armed only when a second host exists) and the contract there is the pre-fencing one. The code was right, my assumption was not, and the test now pins the real contract with the correction written into it. RULES: (a) for any coordination primitive, ask what makes the participant believe it still holds the role - 'the file says so' is not an answer; (b) freshness must be measured RELATIVE to one clock, never by comparing one host's timestamp against another host's clock; (c) when a security-relevant check has exactly one condition, that condition is the whole attack surface - enumerate the states that make it lie.
