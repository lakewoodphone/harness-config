**L2852 · A branch nothing has measured is a branch that is always "unreachable in practice"**

A BRANCH THAT NOTHING HAS MEASURED IS A BRANCH THAT IS ALWAYS "UNREACHABLE IN PRACTICE".

autosync.ps1 carried this comment above its refused-pull handler: "Unreachable in practice while step 2b
stands: with $ahead -eq 0 a refused pull cannot be a divergence." It was reached every 15 minutes for
days. ZABZ-TECH sat 56 commits behind while each tick wrote "histories diverged (55 behind / 0 ahead) and
step 2b preserved nothing. Needs a human." - and the human was not there, so the machine stayed frozen and
LOOKED like it was reporting honestly.

WHY IT WAS REACHED, exactly: git refuses `merge --ff-only` when a locally MODIFIED tracked file is also
modified by the incoming commits. Two of those files were GENERATED (journal/index/stamp.json - the index
cache; journal/state/owner-questions.md - a mirror the tool regenerates). Ordinary use of the machine made
them dirty; the next pull refused; the run called it a divergence.

THE METHOD THAT FOUND IT, worth reusing:
1. Read the state the run itself wrote (~/.dsh-sync-status/status.json and the per-host status.json). The
 frozen machine had been saying what it thought, accurately, for days - nobody read it.
2. Reproduce the refusing condition in a scratch fixture rather than arguing about it. Two throwaway repos
 under %TEMP% and a stub scripts/sync.py reproduced BOTH outcomes without touching the real repo.
3. Before trusting a fix, run the fixture in the OTHER direction too: the case that must still refuse
 (an untracked file that DIFFERS from the incoming blob) is what proves the fix is not a delete-everything.

TWO MECHANICS THAT COST REAL ATTEMPTS AND WILL COST THEM AGAIN:
- `git read-tree -n -u -m HEAD <tip>` is the read-only way to ask what a fast-forward would refuse, and it
 names exactly ONE blocker per call. Clearing one file does not clear the tree: loop until a pass reports
 nothing (measured: three passes for three blockers).
- The detector and the action must run under the SAME config. Measured on the fixture: with the detector on
 the repo's `core.autocrlf=true` and the pull on `-c core.autocrlf=false`, the detector reported the tree
 clean and the pull still refused on the same paths, because under a different eol config every CRLF file
 reads as locally modified. Copy the flags from the pull.
