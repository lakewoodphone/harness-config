**L12379 · lpt sql from PowerShell truncates at the first newline: L3690's file workaround needs the newlines collapsed, and communications.createdAt is ingestion time**

**L-note · `lpt sql` from PowerShell fails two ways, not one — the second is newlines, and L3690's "write it to a file first" does not fix it**

Measured 2026-10-26 on ZABZ-TECH while pulling a case for a customer who exists only in Dialpad.

Trap 1 is already recorded in **L3690**: a double-quoted identifier inside a double-quoted PowerShell string
is split by the shell and the SQL arrives truncated (`unrecognized arguments`, or `column "createdat" does
not exist`). L3690's remedy 2 (`to_jsonb(x)->>'camelCase'`, no double quotes anywhere) is correct and I used it.

Trap 2 is not in L3690 and it bit me **after** I had already avoided trap 1:

```
lpt sql --store operational (Get-Content -Raw C:\...\_scratch\q1_customer.sql)
 -> lpt: the operational remote helper failed: SyntaxError: syntax error at end of input
 LINE 1: SELECT to_jsonb(c)->>'id' AS cid,
 ^
```

The statement is correct and contains no double quotes. **The helper truncates at the first newline**, so a
multi-line `.sql` file sent as one argument arrives as its first line only, and Postgres reports the empty
rest as "syntax error at end of input" while printing a caret at a spot where the SQL is perfectly valid.
L3690 closes with "or write it to a file first" — that advice is what fails here. Writing to a file first is
fine **only if the newlines are collapsed**:

```powershell
$q = ((Get-Content -Raw .\_scratch\q.sql) -replace "`r?`n", ' ')
lpt sql --store operational $q
```

Read the error's caret, not just the message: a caret at the end of text that plainly continues tells you the
statement was cut, not that the syntax is wrong. Chasing the "syntax" costs three queries; collapsing the
newlines fixes it in one.

Also measured the same hour, and worth knowing before trusting a timestamp: production `communications."createdAt"`
is the **ingestion** time, not the call time. The 205-second call that starts at `2026-10-25T16:57:50Z` is
stamped `17:09:01.859` in `communications` — an 11-minute gap. Take call times from `dialpad_call_full.date_started_ms`
and use `communications` only for the body and the recording link.
