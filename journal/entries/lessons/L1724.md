**L1724 · The id allocator fetched the remote and then never read it - fourteen ids meant two entries**

**L· 2026-09-15 · The id allocator fetched the remote and then never read it - fourteen ids meant two entries**

MEASURED on ZABZ-TECH, 2026-09-15, and PROVED both ways rather than reasoned about.

THE SYMPTOM: `git pull --ff-only` in `C:\Users\ezabz\code\harness-config` was refused -- 61 commits
behind origin and immovable. Fourteen untracked local files existed in origin/master too, with different
content: **D185, D186, H322, H323, H324, H325, H326, H327, H328, L1637, L1638, L1639, W149, W150**. Each
of those ids meant two different entries. Local headers said ZABZ-TECH; origin's said ZABZ-YOGA.

THE CAUSE, in `journal/tools/journal.py`: `cmd_append` is *designed* to consult the remote --
`remote, _rev = git_max(kind, fetch=True)`, then `base = max(max_number(kind), allocation_ceiling(kind),
remote)`. But `git_max` fetched, and then ran `git grep -h -E <pattern>` with **no ref** (which greps the
WORKING TREE) and again with **HEAD**. It never greps a remote-tracking ref. So the fetch it performed
was never read, and a number that existed only on origin was invisible to the allocator. Two machines
that had both just fetched both chose the same next number.

PROOF, both directions, at a HEAD that predates the recent ids (`d905c44`, where origin's ceilings are
L1685 / H366 / D200):

 old allocator: next-id lessons -> L1500 <-- collides with origin
 fixed allocator: next-id lessons -> L1686 <-- above everything

THE FIX (720bcb0): `git_max` also greps every `refs/remotes/origin/*` ref, bounded to 25 so a writer
path cannot hang on a hub with hundreds of refs. Ids only ever move UP, so this can never reuse a
number; it can only skip one, and a gap costs nothing.

WHAT WAS DONE WITH THE FOURTEEN, by the convention the record already carried (the entries themselves
say "renumbered H234 -> H328" and "renumbered D153 -> D185"): origin keeps the id, the later allocator
renumbers its own entry, appends a one-line note naming the old id, re-hashes, and records an alias.
The originals were **moved** to `journal/archive/collided-ids-2026-09-15/`, never deleted -- a renumber
that silently removed the original would be worse than the collision. `check` went from 6 errors to 0.

THE SECOND HALF, and it is the part that would have kept `check` red forever: those six errors were
**stale hashes** on entries that `fix-encoding.py` had correctly repaired -- the bodies were clean, the
`sha=` metadata was simply never recomputed, and **no command existed to recompute it**. An alarm that
cannot be cleared is an alarm nobody reads. `journal/tools/rehash.py` now exists: by default it repairs
a hash that MISMATCHES and deliberately does not backfill entries that carry none (`--include-missing`
does that on request, because it is a hundred-file diff across a shared append-only log).

*Rule:* a cache that claims to have been refreshed must be shown to have been READ. `fetch=True` in a
signature is a promise about behaviour, not about outcome, and the difference here cost fourteen ids and
a frozen checkout.
