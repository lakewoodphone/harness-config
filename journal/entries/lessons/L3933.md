**L3933 · CORRECTS L3820: poolOptions is a red herring for the CI shard crash - two racing force-exit calls are the mechanism**

**Correcting the CI-runner lead I recorded earlier today: `poolOptions` is a red herring; the real mechanism is TWO force-exit calls racing vitest's pool teardown.**

This entry CORRECTS `L3820` (the "Lead not yet tested" bullet in L-B), which said the likely cause of the
frontend shard crash was `test.poolOptions` being removed in Vitest 4. **I checked it, and it cannot be
the cause.** A future session must not spend an afternoon on it.

WHY THE LEAD IS DEAD — read `frontend/vitest.config.ts` (150 lines, at `origin/test` `0f4c2b0f8`):
- line 77 already sets `maxWorkers: resolvedMaxWorkers` at the TOP LEVEL, which IS the Vitest 4 way;
- `poolOptions.forks.isolate: true` (line 59) is also already the Vitest 4 default;
- so the removed `poolOptions` block (lines 55-61) is a **no-op**. Vitest 4.1.10 does print
 *"`test.poolOptions` was removed in Vitest 4"*, but the block is not load-bearing. Moving it would
 change nothing observable.

THE BETTER HYPOTHESIS, and it is a designed-in race. The repo contains **two independent
`process.exit()` calls**, both added to stop the suite hanging, both firing ~500 ms after the run ends:
- `frontend/src/global-setup.ci.ts` — the global teardown, `process.exit(0)` after 500 ms;
- `frontend/src/reporters/force-exit-reporter.ts` — `onTestRunEnd`, `process.exit(0 or 1)` after 500 ms.

Vitest's pool shutdown runs *after* the run ends and its `PoolRunner.stop()` talks to the workers over
the child-process IPC channel. **Forcing exit while that is in flight is one way to break that channel,
and the observed error is exactly the shape of it** — from two shard logs I read myself on PR 440:

```
[vitest-pool]: Timeout terminating forks worker for test files .../Card.test.tsx.
[vitest-pool]: Failed to terminate forks worker for test files .../Card.test.tsx. Error: [vitest-pool-runner]: Timeout waiting for worker to respond
 <then the process dies with:>
Error: write EPIPE errno: -32 syscall: 'write'
 at ChildProcess.target.send (node:internal/child_process:751:19)
 at ForksPoolWorker.send (.../vitest/dist/chunks/cli-api.BK8pd4xc.js:3081:13)
 at PoolRunner.stop (.../vitest/dist/chunks/cli-api.BK8pd4xc.js:2960:27)
```

The 30-second gap between those two lines is `teardownTimeout: 30000` (line 73) doing exactly what it
says. So: a worker wedges, vitest waits 30 s, then `send` on a dead pipe throws, the `error` event is
unhandled, and the whole process dies **before printing any summary**.

WHAT TO DO NEXT, AND WHAT NOT TO DO:
1. **Do NOT ship a speculative config change.** I could not reproduce the crash locally — it is
 CI-only and INTERMITTENT (on PR 439, `Test Frontend (Shard 1/4)` passed in 5m58s while shards 2-4
 crashed; on PR 440 and 442 all four crashed). A local green proves nothing, so a fix can only be
 verified by CI, one ~10-15 minute cycle each.
2. The experiment to run, cheapest first: **remove ONE of the two force-exits** (start with the
 reporter, since `global-setup.ci.ts`'s teardown runs last and only after "All tests completed") and
 read a shard log. If the shards start printing a summary, that was it. If vitest then hangs instead,
 that is also a result — it means the force-exits are load-bearing and the wedge is upstream.
3. **Do NOT open the aggregator's gate before the runner is fixed** — see `P3199`. Making the shards
 blocking today blocks every merge.

PATTERN WORTH KEEPING: **a repository containing two "force exit" escape hatches for the same hang is
evidence that the hang was never diagnosed, only suppressed.** Every such hatch is also a new way for
the process to die in an unhandled place, which is what happened here.
