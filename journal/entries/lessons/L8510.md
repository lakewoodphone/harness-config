**L8510 · A learning loop wired to a table nobody writes: a read-only connection plus a quiet return 0 became a false fact**

**L · A learning loop wired to a table nobody writes is not a learning loop, and a read-only connection makes its failure look like an empty database.**

Auditing the owner queue on 2026-10-18 I found `owner_queue_feedback` holding **2 rows** against
**553 closed queue rows**. The cause chain, and every link of it looks like health:

1. `learning` was in the `readonly` tuple in `main()`, so the backfill's INSERT raised.
2. The backfill caught the exception and `return 0`.
3. `cmd_learning` printed "No feedback yet: nothing has been answered, dismissed or snoozed."

Three layers, and the third is a sentence that is *true about the table* and false about the world.
The owner had closed 553 things. The tool said nobody had ever answered anything.

**The rule this generalises to:** when a counter reads zero, ask what WRITES it before believing the
zero, then ask whether that writer is allowed to write. A guard whose failure path is a quiet
`return 0` converts a permissions bug into a fact claim -- and the fact claim is the one thing a
reader trusts.

Same shape, same session, twice more: `mail read everything` reported no run because a local variable
`now_iso` shadowed the module function of the same name (`TypeError: 'str' object is not callable`,
swallowed by the same "never raise" wrapper). Both are loud now: the backfill prints its errors, and
`learning` prints how much of its evidence comes from a channel that still writes.
