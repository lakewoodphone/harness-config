**L6463 · The fork is FROZEN: 336 colliding ids in two captures 35 min apart, +6 ids and +0 collisions - and the ledger reads a remote frozen since 2026-10-11**

**The journal fork is NOT growing — measured 2026-10-16, two captures 35 minutes apart.**

Same instrument, same tree set, source-against-source (`fork-size.py`, identity = `journal.py`'s own
`entry_hash`, the same function its intra-tree `check` uses). The canonical tree is excluded from both
runs on purpose: it was REPAIRED between the two captures, so including it would compare a repaired
tree with an unrepaired one and report the repair as growth.

```
 01:54 capture 02:29 capture
trees 8 8 (yoga tech mac item221 mfx p1evidence hcd linux-r6)
ids seen 4,591 4,597 (+6)
ids in every tree 1,276 1,276
COLLIDING IDS 336 336 (+0)
surplus bodies 340 340 (+0)
by kind decisions:22 handoff:131 lessons:119 pain:51 wins:13 (identical)
odd tree out tech:179 yoga:96 mac:30 hcd:15 mfx:10 p1evidence:6 (identical)
```

**Six new ids, zero new collisions.** The machines have drifted into non-overlapping id ranges, so
they are no longer colliding with each other; the 336 are the residue of the period when they were
(round 6's five-tree measure was 363 the day before, the same magnitude). **This is a one-time repair,
not a bleeding wound** — and it corrects the "the fork keeps growing until one is chosen" framing in
`H6121` and `L6402`, which was an inference I had not measured.

**What it does NOT say.** 35 minutes is a short window, and a machine whose ceiling is stale can re-enter
another's range: `+6 ids` in the same window shows minting continues. The right reading is "no
measurable growth over 35 minutes", not "this can never grow".

**THE LEDGER, AND WHY OPTION A IS TWO CHANGES AND NOT ONE.** The canonical `journal.py` carries the
cross-host reservation machinery the other copies lack (measured: 177 of 5,517 lines, cloud-only). It
reads other hosts' windows from here:

```
rc, out = _git("show", "refs/remotes/origin/master:journal/%s/%s" % (ALLOC_DIRNAME, RESERVATION_FILE))
```

On ZABZ-YOGA that ref **exists and is stale by three weeks**:

```
$ git -C ~/code/harness-config show origin/master:journal/alloc/bands.tsv | head -6
kind reserved_from reserved_through host stamp rev
decisions 2096 2159 ZABZ-YOGA 2026-09-20 19:44 UTC -
decisions 2097 2223 SECRATARY 2026-09-22 03:09 UTC -
decisions 2325 2388 ZABZ-TECH 2026-09-22 15:00 UTC -
decisions 2325 2388 ZABZ-YOGA 2026-09-22 08:44 UTC -
```

`origin` is `secretary-ts` — the office box **frozen on 2026-10-11**. And **the last two rows are the
collision mechanism written down in the ledger itself**: `decisions 2325..2388` claimed by ZABZ-TECH
and by ZABZ-YOGA, the same window twice.

The live canonical checkout IS reachable from ZABZ-YOGA as the `cloud` remote
(`secratary-cloud:/home/zabz/code/harness-config`, and `/home/zabz/code` is a symlink to `/root/code`),
and **nothing reads it** — the tool asks `origin/master`.

**Therefore "deploy the canonical journal.py" is not sufficient.** It is: deploy the file AND point the
ledger's reader at a remote that actually advances (`cloud`, or `vault`). Without the second half the
ledger would read September forever and prevent exactly nothing.
