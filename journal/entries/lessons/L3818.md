**L3818 · A restriction key needs a reachable control surface; 4 looked like Wi-Fi levers, 1 was real, 2 do not exist**

**L · A profile "setting" and a profile "surface" are different things, and only one of them was true**

The Waze kiosk had `allowBluetoothModification = true` (owner decision 2026-10-13, pushed to six
devices, verified sent and installed) and **no customer could reach Bluetooth**. It also had no way
to reach Wi-Fi. The reason: `blockedAppBundleIDs` carried the Settings panes themselves -
`com.apple.wifi`, `com.apple.wifiSettings`, `com.apple.BluetoothSettings` - and
`allowListedAppBundleIDs` is `["com.waze.iphone"]`, so Waze was the only launchable app and there was
no second route in.

**The generalisable rule: a restriction key controls a behaviour; the app/bundle block list controls
whether the user can reach the control at all. Setting a key does nothing if the surface that
exercises it is blocked, and MDM reports the install as `Acknowledged` either way.** When a device
"still will not let me do X" after a restrictions change was verified applied, check the block list
for the Settings pane, not just the `allowXModification` key. The block list is a whitelist attack on
Settings and it defeats keys silently.

Evidence: `deploy/waze-mdm/docs/wifi-bluetooth-switching.md`; the block list was added deliberately in
`38ecfb260` (2026-06-30) to suppress the Settings surfaces, and it did exactly what it said.

**L · Four keys looked like levers; one was real, two did not exist, one blocked the door**

Measured against Apple's own `Restrictions` payload reference
(`https://developer.apple.com/documentation/devicemanagement/restrictions`, the JSON behind it at
`https://developer.apple.com/tutorials/data/documentation/devicemanagement/restrictions.json` - the
HTML page is JS-rendered and returns a title only, which is itself worth knowing):

| key in our profiles | real? | what Apple says |
|---|---|---|
| `forceWiFiPowerOn` | yes | "prevents turning off Wi-Fi in Settings or Control Center, even by entering or leaving Airplane Mode. It doesn't prevent selecting which Wi-Fi network to use." |
| `allowBluetoothModification` | yes | "prevents modification of Bluetooth settings" |
| `allowWiFiModification` | **no** - absent from the payload | ignored by iOS |
| `allowWirelessModification` | **no** - absent from the payload | ignored by iOS |

`allowWiFiModification` appears **zero** times in Apple's Restrictions payload. It is not a key. It
sat in a dozen of our profiles for years reading like the Wi-Fi lever, and more than one session
tuned it. Rule: before treating a profile key as a lever, grep Apple's payload JSON for it. A key
that does not exist cannot be the cause of, or the fix for, anything.

**L · Hard-coded PayloadUUIDs make a device's own ProfileList useless for proving which VERSION is installed**

`waze-layered-kiosk.mobileconfig` carries fixed UUIDs (`F7FF22CA-…` top, `C542A1C1-…` restrictions)
that were **identical before and after a content change** - verified by diffing the pre-fix backup
against the post-fix file. So a device's `ProfileList` showing the kiosk installed proves *which
profile*, never *which revision of it*. Any "verify the change landed" step that leans on ProfileList
here is vacuous, and would have passed on the broken config too.

What did carry proof: decoding the base64 payload out of the `commands` table (`InstallProfile`
rows) shows exactly what was sent; and the RemoveProfile+InstallProfile pair being acknowledged in
one batch shows the device tore off the old copy and took the new file. The final "the OS is applying
it" step has no MDM read at all and needs a human looking at the screen. Rule for this fleet: when
the profile content changes but the UUIDs do not, say so, and do not dress up ProfileList as
confirmation.

**L · An empty list is a refusal, and the fleet API will hand you one**

`GET /fleet/devices/{drn}/profiles?wait=true` returned `{"ok": true, "profiles": [], "count": 0}` for
all six units. That is not "the device has no profiles" - the same devices' raw `command_results`
rows listed fourteen profiles each. The API's structured field is not populated here. Read the
device's own `ProfileList` result out of `command_results` instead. This is the house rule (an empty
result is a refusal, not evidence of health) firing on a *new* tool, and it is worth repeating because
`ok: true` makes it look like an answer.

**L · The 2026-10-13 Bluetooth decision was one branch away from being lost**

The work existed only on `origin/hk/item85-ssh-large-capture-20261013` - a branch named for an
unrelated task - and was **not on master**. Its `nanomdm_service.py` default and its profile changes
would have been reverted by any session working from a clean master checkout. Found by grepping what
master actually contained, not by trusting the commit message. Rule: a change that a live fleet
depends on must be on the branch everyone else builds from; "it is committed" is not the same as "it
is on master".
