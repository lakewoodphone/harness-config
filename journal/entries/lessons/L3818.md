**L3506 · Push from a worktree, not from the shared clone - cherry-picking onto a moved origin leaves the clone 1 ahead and unable to fast-forward**

When you must push a commit from a shared checkout whose remote has moved, make the commit **inside the worktree**, not in the shared clone.

Measured twice on 2026-10-11, in `harness-config` and again in `lpt-ops`: the shared clone had other sessions' uncommitted changes, so `git pull --rebase` refused; I committed in the shared clone, then pushed via `git worktree add --detach <tmp> origin/main` + cherry-pick + `git push origin HEAD:main`. The push worked both times - and both times it left the SHARED CLONE **1 commit ahead of origin with the same content under a different sha**, which is exactly the state that makes a `git pull --ff-only` refuse for ever after. The harness-config autosync was already frozen for that reason and I added a second copy of the problem to lpt-ops.

The order that avoids it: create the worktree first, make the edit and the commit THERE, push from there, remove the worktree - and never touch the shared clone's HEAD. A cherry-pick on top of a moved origin is what creates the duplicate sha.

If it has already happened: the duplicate commit cannot be dropped safely while other sessions hold modifications (a rebase refuses, and `--autostash` conflicts precisely on the files origin also changed). Leave it, record it, and drop it in a quiet window. Do not `git reset --hard` - the tree holds another session's work.
