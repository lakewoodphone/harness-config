# L — A block that carries no question cannot be told apart from a bug

**Measured 2026-10-02, on the owner's AI text line.**

Three of the owner's texts (2026-09-30) ended as `jobs` rows in `state='blocked'`. What
he received for them was: a NJ DOL form instruction, then an unrelated *"Chumash
Timeline … Who redeploys the container?"* question, then *"Understood - I'll handle it"*
followed seven minutes later by a message asking him for the answer. He had written
*"It was shop supplies / It was 2 hard drives, 2 TB each, generally used for lab work"*
— a direct answer to a charge question — and none of the three replies was about it.

**Two mechanisms, both bad, both invisible:**

1. The structured owner question (`textwork`'s `escalated` payload) was built **only
 when the block reason matched a prose regex**
 (`needs the owner|his (decision|money|call)|commit`). A block caused by anything
 else returned `escalated=None`, and the responder fell to its generic
 `queue_for_owner(..., "I could not resolve it")` — a vague row with no trace of the
 question.
2. The four **fail-fast** blocks never built a payload at all — including
 `the model returned no usable JSON`, which is the exact shape a gateway 502 takes.
 So the most common real failure was also the most silent.

**The rule.** *Every* terminal outcome of a bounded investigation must carry, in the
result object, the question a human would have to answer to unblock it — not a log
line, not a verdict string, and never gated on prose. If a blocked job cannot produce
that question, the block is a bug report about the investigation, not a question for
the owner.

**Corollaries, both paid for:**

- **A regex over a reason string is wrong for classifying, right for phrasing.** It may
 decide *how* to word the recommendation; it must never decide *whether* there is one.
 Prose is user-facing text and changes without notice; the regex silently rots, and the
 failure mode is a missing question, not an error.
- **When a verdict is recorded for later diagnosis, record the reason, not the
 verdict.** `_evidence()` wrote `app_db_query: FAILED`, and a day later nobody could
 tell a database lock from a 502 from a malformed query. One line of the error text is
 worth the whole audit that follows.
- **Test the fallbacks by running them.** Two silent fallbacks in one day — an undefined
 name and a raw `sqlite3.connect` returning tuples — each produced *plausible output*
 (the old bare message) and looked exactly like success. Both were found by executing
 the deployed path, not by reading it.

Evidence: `journal H3111` (audit), `H3117` (tools and composer), `H3118` (this fix),
`~/bin/textwork.py` backups `.bak-esc-*` and `.bak-allblocks-*`.
