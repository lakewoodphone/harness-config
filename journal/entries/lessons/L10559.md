**L10559 · zabz-tech-linux reaches GO on 0.2.1 after four real pipeline bugs were fixed; its switch still waits on the same profile-anchor rebuild that stopped the phone engine**

MEASURED 2026-10-20 on zabz-tech-linux, after four pipeline bugs were fixed to get there.

`preflight 0.2.1-rc.2` on the Linux worker: **GO, 7 blocking guards green**, with 7 verify gates RUNNING (G1-G5,
GFULL, G8) where the machine could previously run only 4.

WHAT HAD TO BE FIXED IN THE PIPELINE, all real, all found by pointing the tool at a host that is not a Windows
workstation:
1. `cli.mjs` passed `--root REPO_ROOT` to the consumption scan, silently overriding `DSH_CONFIG_ROOT`. So G2 judged
 this worker against the REPOSITORY's profile patch -- which it never deploys -- and reported three patch targets
 that "were not rows". The host's own patch is 217 bytes and contains `[]`. Honouring the override turned a
 fabricated BREAKS list into `RISKY=1` and dropped the unchecked-gap count from 339 to **5**.
2. `verify.mjs::otherDshWebProcesses()` spawned `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe`
 unconditionally, so `--full` failed with ENOENT on every POSIX host. It now uses the CIM query on Windows and
 `ps -eo args=` elsewhere; GFULL runs on Linux for the first time.
3. G2 treated "no patch targets for this profile" as a failure. An empty patch layer cannot lose a patch, so it now
 passes WITH a note that nothing was attributed -- and still fails when no consumed source could be read at all.
4. `backup-state.mjs` treated an absent store as a failed backup. This worker has no `.agent-presets` at all; a
 machine that never had a store is not a machine whose backup failed. Absent is now a note when the home is real
 (profiles/ or sessions/ present) and a problem when it is not.

ALSO DONE THERE: disk 99 % -> 45 % (259 GB) under the owner's 30-day rule with a committed manifest; tooling
installed; pin bootstrapped from the running 0.1.5-rc.1; 0.2.1 fetched (85 s) and its baseline snapshotted;
model credential added to the credential store by the stdin pattern (verify went from refusing G4/G5 to running
them); verified backup ok=True, 994 files.

THE ONE THING THAT STILL BLOCKS THE SWITCH, and it is the same root cause as the phone engine:
`~/.dsh/profiles/node_modules` is a real tree of **187 entries including `@deepseek-ai`** -- the profile anchor
carries its own copy of the engine's packages, which is what makes a newer engine exit 2 with "TWO COPIES ...
every prompt will be rejected as session/agent-busy" (measured on the phone, L10431). `profiles/web/node_modules`
is empty, so the risk is the shared anchor only. Swapping the tree without rebuilding that anchor would very likely
reproduce the phone failure; and NOTHING on this box restarts the engine (the crontab entries are session-push and
usearch-sync only), so a failed start leaves it down until someone notices.
So the switch is: stop pid 1326 -> rebuild the anchor against the 0.2.1 engine root -> install-engine -> start the
engine by hand with its exact original command line -> verify -> roll back everything on failure. That is a
scripted window, not a step in a bigger turn.
