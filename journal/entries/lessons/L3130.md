**L3130 · P2806 measured again: the fetch failure was transient, the design defect is not**

ROUND 14, 2026-09-30 16:00Z, same machine, same command shape that crashed twice twenty minutes ago. Test: journal.py append lessons --title probe --body x --dry-run. It SUCCEEDED, printed (dry-run) would write entries/lessons/L3130.md, and completed the pre-write fetch that had aborted twice. This entry itself was then written through the same path without --no-fetch. So the SYMPTOM WAS TRANSIENT - a momentary failure of the remote fetch - and P2806 should not read as a currently broken tool, which is the whole point of re-measuring an item before acting on it: an item is a statement about the world at FILING time, and the next shift must not spend its opening minutes chasing a ghost. THE DEFECT ITSELF STANDS and is unchanged in kind: an append aborted with a bare traceback and no visible cause, while the identical call with --no-fetch wrote instantly, so the fetch is a hard dependency of a LOCAL write. A transient network failure is sufficient to block the only memory this seat has, and that should not be possible - the entry should land locally, be marked unfetched, and reconcile on the next successful fetch, the way the index cache already heals itself. Severity downgraded from active blocker to latent robustness defect; priority unchanged, because the cost of it firing at the wrong moment is a session that cannot write and therefore cannot exist. WORKAROUND unchanged: pass --no-fetch if an append ever dies like that, and note --no-fetch is only accepted by some subcommands.
