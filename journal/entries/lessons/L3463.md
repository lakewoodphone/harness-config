**L3463 · Fail2ban locked the whole fleet out of the new authority, and retrying is what extends it**

## WHAT HAPPENED

Between 06:20 and 06:35Z on 2026-10-11, six parallel workstreams and the manager session all reached
`secratary-cloud` over ssh from the same public address, each with several short-lived connections. At
06:34Z the box began answering `Permission denied (publickey)` to a key it had accepted a minute
earlier - and to a key a sibling workstream had itself recorded as the only entry in that box's
`authorized_keys`. The autoritative reading: `https://api.abletelsolutions.com/health` stayed 200, so
the host was healthy; only the ssh path closed. That is fail2ban's per-source ban, not a key change.

## WHY IT LASTED LONGER THAN IT SHOULD

Two causes, one of them mine:
1. A workstream retried every 1-3 minutes for half an hour. With a recidive-style rule each new denial
 re-arms the window, so a self-inflicted lockout can be extended indefinitely by the very act of
 retrying. The correct behaviour is to stop, wait past the ban window, and then reconnect ONCE.
2. The manager added two more single attempts minutes apart while diagnosing it, which is the same
 mistake in smaller form.

## WHAT TO DO ABOUT IT, IN ORDER

1. **Stop all ssh to the affected host for at least 15 minutes.** Do not "just check" - each check is
 another denial in the log.
2. Then reconnect once. If it fails, do NOT retry: read the ban state from the only path that does not
 need ssh - the provider console - and clear it there, or wait a full ban window.
3. On the box, put the estate's own addresses in fail2ban's `ignoreip` (the public address of ZABZ-YOGA
 and ZABZ-TECH, plus the tailnet range), so that legitimate agent traffic can never be mistaken for
 the brute-force that is also hitting this box (11,671 failed password attempts in 24 h, 30 bans, so
 fail2ban is aggressive there BY DESIGN and correctly so).
4. Longer term, this is an argument for the tailnet join that is already owner question 445: agent
 traffic should reach the authority over a stable private address that fail2ban can whitelist as a
 range, rather than from a residential public address that changes and looks like an attacker.

## THE COST

Eight workstreams were mid-flight. The four whose work is complete but uninstalled (families 3/9, the
systemd timers, ingestion, owner channel) cannot finish until ssh returns; their artifacts are on disk
and on the box, and the crontab fragments are pre-generated. Nothing was lost - the cloud box's own
services were never touched - but the program's critical path gained a delay with no engineering value.
