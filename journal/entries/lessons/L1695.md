**L1695 · HA rest_command never retries, so a brief secretary outage makes a security alarm page nobody**

Home Assistant `rest_command` does not retry, and `continue_on_error` leaves `response_variable` UNSET. So a brief outage of the secretary API means a security alarm pages NOBODY and nothing visible happens.

MEASURED 2026-09-16. Three intrusion pages fired; only one reached a human.

- 23:35:15Z — `journalctl` on the server: `Failed to proxy http://localhost:8002/webhook/ha/security-alert Error: connect ECONNREFUSED 127.0.0.1:8002`
- 00:20:34Z — same ECONNREFUSED
- Home Assistant logged both, twice:
 `WARNING (MainThread) [homeassistant.components.rest_command] Error. Url: https://ai.abletelsolutions.com/webhook/ha/security-alert. Status code 500. Payload: b'{"event": "intrusion", "detail": "Extreme intrusion triggered - nobody expected present"}'`
- 00:43:58Z — `POST /webhook/ha/security-alert HTTP/1.1" 200 OK`, and the Twilio API confirms all four
 roster recipients received it, `status=delivered`.

So 2 of 3 alarms were silent. The API process was restarting, not the network; a retry seconds later
would have succeeded.

Also note what a 500 from this webhook means: the endpoint catches its own exception and returns 500,
so HA's `rest_command` records an error — but HA raises no notification, no persistent notification,
and no automation trigger. The only trace is a WARNING line in `home-assistant.log`.

Rules:
1. Anything safety-critical behind `rest_command` needs an explicit retry loop. HA supports
 `response_variable` + `continue_on_error`; a FAILED call with `continue_on_error` leaves the
 variable UNBOUND, so "not defined" is your failure signal:
 - if: "{{ page_result is defined and page_result is mapping and page_result.get('ok') }}"
2. Add a visible failure signal that does not depend on the remote service (a persistent notification
 and a logbook entry). A silent failure is worse than a loud one, because everyone believes they
 are covered.
3. `sms_log` does not record this send path, and `sms_media` had 0 rows. Do not use the absence of a
 row there as evidence that an alert was or was not sent — query Twilio directly.
4. Diagnostic order that settled it in minutes: HA core log -> journald on the API host ->
 `GET /2010-04-01/Accounts/{sid}/Messages.json` on Twilio. Do this BEFORE theorising about
 credentials, kill switches or transports. In this case a recorded audit string
 ("Twilio outbound retired ... owner SMS kill-switched") was sitting in `sms_log` and was mistaken
 for the cause; it applies to the CEO-chatter path, not the security path, and the security path was
 in fact healthy.
