**L3348 · Tunnel liveness is an out-of-band sensor; an empty Access list is a refusal**

Cloudflare tunnel liveness is the cheapest out-of-band sensor for a site you cannot reach.

**Rule.** When a site you own goes dark and you have no route in, read the Cloudflare API's
tunnel objects before concluding *what* is down:

 GET /accounts/{account_id}/cfd_tunnel?is_deleted=false # every tunnel: status + times
 GET /accounts/{account_id}/cfd_tunnel/{id}/connections # live connectors (origin_ip is masked)

Each tunnel carries `status`, `conns_active_at` and `conns_inactive_at`. A connector's TCP to
Cloudflare is maintained continuously and dropped within seconds when it dies, so a tunnel that
reads `healthy` with an `active_at` older than the outage proves that **host** had power and
internet throughout it — a fact no ping, no Tailscale peer list and no phone call can give you
when the site's own machines are silent.

**Evidence, 2026-10-06 (H3250).** All four office machines read offline in Tailscale, two of the
secretary's tunnels had gone inactive inside the same 10 seconds (22:57:33Z, 22:57:43Z), and
`https://ai.abletelsolutions.com/health` returned 530 — a picture that reads as "the shop lost
its internet". The same API read showed tunnel `homeassistant` `healthy` with
`conns_active_at=2026-10-05T01:04:38Z` and no inactive time: an office-LAN host continuously
connected for 25.7 h. The shop had power and internet the whole time; what died was four wired
machines sharing one upstream device. One API call replaced a wrong story with a right one.

**Corollary — tunnel liveness is not application liveness.** That same call proves the *connector*
is alive; it says nothing about whether the app behind it answers, and an Access-gated hostname
will not tell you either (every path 302s to the identity provider). Say "the host has power and
internet", never "the service is up", unless a request came back.

**Corollary 2 — check the token's scope before trusting a 403-free list.** `CF_API_TOKEN` in
`personal-secretary-mvp/.env` returns `success:true` with `result: []` on `/access/apps` while
policies for a known app id return 403 `auth.forbidden`. An empty list is a refusal, not an
absence: the same account plainly has Access apps, because the login redirect names its team
domain. Do not read an empty result as "nothing is configured".

**Corollary 3 — a service token is per-app.** `CF_ACCESS_CLIENT_ID`/`_SECRET` authenticate to
Yocheved's app and are rejected by the HA app (`service_token_status:false`). A service token is
not an account-wide key.
