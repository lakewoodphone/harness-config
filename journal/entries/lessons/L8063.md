**L8063 · A fix in the implementation but not in the argument parser is not a fix**

## L· a fix that lands in the implementation but not in the argument parser is not a fix

MEASURED 2026-10-18, on the wake system's own ledger tool. Doc section 27 recorded
"`edit` CAN NOW CORRECT `blocked_on` (3rd attempt, works)". The implementation was real:
`_EDITABLE_FIELDS` at `work.py:701` lists `blocked_on`, the change branch at `:754` compares it, the
UPDATE at `:774` writes it. The `edit` subparser never defined `--blocked_on`, so the CLI answered:

 work.py: error: unrecognized arguments: --blocked_on TEST

Three "attempts", a verification claim, and a documented success — and the verb was unusable the whole
time. The class is the doc's own §1 pattern turned inward: *a correct mechanism wired to nothing*, inside
the sensor that exists to find exactly that.

**The rule this earns:** when a claim says a CLI verb works, run the verb. Not the function, not the
module, not the test around it — the verb, with the flag, on a store you can throw away. A verification
that exercises the implementation while the caller uses a different entry point proves nothing about the
caller. On this estate that gap is where `Path.home()` under cron, `--hours 48` against 41 older rows,
and this parser all live: the code is right and the wiring is not, and the wiring is the thing that runs.

Corollary for the reader of any handoff: "shipped and proven" is worth nothing without the command and
its output line, because the next session cannot tell a proven fix from a plausible one.

Refs: docs/mesh/178 §46 (the patch and its proof), §27 (the false claim), H7337.
