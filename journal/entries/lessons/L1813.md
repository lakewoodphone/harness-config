**L1813 · An unindexable predicate turns a per-row update into a full-table read, and the mapping usually already exists**

Measured 2026-09-16 in unified-search. `DELETE FROM chunks WHERE doc_id=?` on an FTS5 table
could not use an index -- doc_id is unindexed -- so SQLite ran `SCAN chunks VIRTUAL TABLE
INDEX 0:` and read the whole 1.27 GB table for EVERY document re-indexed: 1,379.7 MB per
document, 237-387 MB/s sustained, 3,366 GB lifetime from one process, and a full sweep of
111 TB against a 30-minute tick. It had failed 28 runs out of 28 and never once succeeded.
The fix was not a new index: `chunks_meta.chunk_id` IS the FTS rowid, and the correspondence
was already a bijection (988,332 = 988,332, both directions verified). Deleting through it:
statement 1.391 s -> 0.0004 s, end-to-end add 1.56 s -> 0.34 s.
RULE: when a write costs time proportional to the table, ask what already maps to the row
rather than adding an index to the thing that cannot have one. And GUARD the fast path against
the mapping being incomplete -- a stale row is a wrong answer, a slow delete is only slow.
