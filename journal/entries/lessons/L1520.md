**L1520 · A path guard fails closed, and a Windows-written test is not a specification for POSIX**

**A path guard fails closed, and a Windows-written test is not a specification for POSIX.**

Measured 2026-09-15 on the Linux authority. `_resolve_tool_path()` treated any non-absolute string as
relative to the first approved root, so `C:\Users\ezabz\Downloads\file.txt` was resolved to
`/home/zabz/personal-secretary-mvp/C:\Users\ezabz\Downloads\file.txt`, found "inside approved roots",
and allowed. A security guard that answers "allowed" for a path it cannot interpret is worse than one
that is merely wrong about the label: the model's file tool calls go through it.

Rules:
- **When a check cannot interpret its input, it refuses.** Foreign absolute paths, unparsable
 arguments, and unresolved roots are all refusals, not passes. `_sanitize_tool_call` already
 returned the call unchanged when args failed to parse (`args = {}` then no keys collected) --
 another fail-open on the same path, worth the same treatment when someone next touches it.
- **Do not relax a security rule to make one assertion green.** I tried the "honour a foreign root
 when it is explicitly approved" rule because the test asked for it; it broke two sibling tests and
 fixed one. Three assertions that contradict each other are evidence about the *test suite's*
 assumptions, not about the code -- and when the code is a guard, the disagreement resolves toward
 the safe direction.
- **A test written on one platform asserts that platform's semantics.** `C:\...` and `/etc/passwd`
 are not the same kind of string on POSIX and Windows, so a test that treats them interchangeably
 is not a specification; it is a recording of the author's machine. The right fix is a
 platform-aware test, and that is now on the record rather than in someone's head.
