**L1767 · The frontend deploy had a second silent failure mode: npx dies with ECOMPROMISED, so the documented deploy could not run at all**

*(Re-appended 2026-09-16 after an id collision. This record was first written under id `L1745` on a checkout that was nine commits behind `origin/master`, so that id already meant a different entry written on another machine. `journal.py` allocated a fresh id rather than let one id mean two things; the content below is unchanged apart from this note.)*

**Recorded 2026-09-16 during the LPT website-redo session. Measured on ZABZ-YOGA (Windows, Node v24.12.0, pnpm 10.26.1).**

`scripts/deploy-frontend-cloudflare.mjs` — the only documented way to publish the customer-facing site —
shells out to `npx --yes wrangler@4 pages deploy …`. On this machine that dies before any upload:

```
npm error code ECOMPROMISED
npm error Lock compromised
npx --yes wrangler@4 pages deploy frontend/dist --project-name lakewood-phone-prod … exited 1
```

The npm cache lock is compromised, so **`npx <anything>` cannot run**, which means the frontend deploy path had
been silently unusable in exactly the same way Netlify's credit exhaustion made it unusable before the migration
on 2026-09-14. A second, independent way for the fleet to become unable to ship its own website — and nothing
reported it, because the failure surfaces only when someone finally tries to deploy.

**The fix that worked, verified:** bypass npm entirely.

```
pnpm add -D -w wrangler@4 # resolves through the pnpm store, not the npm cache
node_modules/.bin/wrangler pages project list # authenticated with CLOUDFLARE_API_TOKEN
# -> listed both projects (lakewood-phone-test, lakewood-phone-prod) correctly
```

Wrangler 4.132.0 installed from the pnpm store, authenticated with the token, and enumerated both Pages
projects. **So the deploy is now possible; the script is not.**

**Two follow-ups this implies, both recorded:**
1. The deploy script should call the locally pinned wrangler binary (`node_modules/.bin/wrangler`) rather than
 `npx wrangler@4`, so a broken npm cache can never again silently disable the deploy path. npx also
 re-resolves a floating version every run, which is its own hazard.
2. `npm cache verify` itself hangs on this machine (>120 s, killed) — the npm cache is not merely locked, it is
 unusable, and it should be cleaned rather than trusted.

**The generalisable rule:** a deploy path that depends on a package runner's cache is a single point of failure
with no alarm. Pin the tool, and prove the deploy works before you need it — the cost of finding this on the day
a customer-facing fix must ship is the whole fix staying unsent.
