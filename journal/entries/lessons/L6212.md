**L6212 · STANDING RULE: anything doable on the website must be doable from the CLI - a capability that exists only as a button is one the machine cannot use, so sessions improvise a worse version at the boundary they can reach**

**STANDING RULE, owner, 2026-10-14, verbatim:** *"anything that is done on the website you have to be able to do from the cli as well, if this isn't possible with current tools then build this robustly for the long term."*

**Why he had to say it.** On 2026-10-14 a session had to send a customer a "your data is ready, here is what you owe" text. The website has a live, robust rail for exactly that - `payNotices` (`/payments/notices`, "Ready to text"), which drafts itself when an order reaches `REPAIR_COMPLETED` and sends only on a manager's second approval, plus `payments.prepareOweNotice`, which reads the balance from the order and reuses-or-mints exactly one payment link. **No session could reach either of them from a shell** - no CLI, no MCP action, nothing. The shop's MCP exposes only a raw `send_sms`. So the session did what the tooling forced it to do: it copied a **static payment link out of an old case file** and hand-wrote the message. The owner rejected the draft in one line - *"that is some old flow not the robust new one we created"* - and then removed the excuse entirely.

**The rule, as it must be applied:** a capability that exists only as a button is a capability the machine cannot use, and every session that needs it will improvise a worse version at the boundary it can reach. **So every website capability needs a CLI path, and the parity claim must be CHECKABLE, not promised** - a list that is compared against the API's own procedure inventory, failing when a router gains a procedure no CLI can reach.

**The two failure modes this rule exists to kill, both measured on the same afternoon:**
1. **A live flow in no index.** Both payment rails had been in production for weeks and neither appeared in `FLOWS-INDEX.md`, the page whose own first line says "start here" - so the search for "the payment flow" led into case files, where an older pattern was lying in plain sight.
2. **A stale checkout answering confidently.** `git grep` in a working tree at `c333338ec` while `origin/test` was at `d352362ce` returned "no match" for code that was live - and the honest reading of that empty result is *"the scope was searched and holds nothing"*, not *"this does not exist"*. **When the question is whether a capability is live, grep the branch tip; compare `git rev-parse HEAD` with `git rev-parse origin/<branch>` before believing either.**

The build is `lpt-web` in `lpt-ops` (design + progress in the same repo's docs), and the parity checklist is its acceptance test.
