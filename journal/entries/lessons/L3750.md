**L3578 · `NODE_ENV=production` is not "this is the production deployment", and a payment connector read that way charges real money**

MEASURED 2026-10-12, `lpt-apps-01`:

```
docker exec lpt-backend printenv NODE_ENV STRIPE_PAY_CONNECTOR -> production / Stripe_Connector_live
docker exec lpt-test-backend printenv NODE_ENV STRIPE_PAY_CONNECTOR -> production / Stripe_Connector_test
```

`resolveStripePayConnector` in `backend/src/config/payment-window.ts` treated
"production process + test connector" as a forbidden combination and **returned the
live connector**. So on the TEST host, one call to the pay-by-phone line would have
charged a real card, silently; the first person to notice would have been the
customer's bank statement. The function had no unit test at all.

THE RULE. `NODE_ENV` describes how the process was built, not which deployment it
is. This shop runs its test stack with `NODE_ENV=production` because it serves the
production build. When a value decides whether real money moves, take it from an
explicit, operator-set variable and honour it exactly — and make the DEFAULT the
safe direction, not the clever one. An explicit `STRIPE_PAY_CONNECTOR` now wins;
only a non-production process is still refused the live connector; and
`stripePayConnector()` warns when the two signals disagree, because a production
host handed the test connector takes no money at all — that fails loudly at the
customer rather than quietly at the bank.

CHEAPEST DETECTOR: for every "which environment am I" branch in money code, ask
what the OTHER deployment's env actually contains. `printenv` on the two
containers answered it in ten seconds. And: a safety interlock with no test is a
comment.
