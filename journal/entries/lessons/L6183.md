**L6183 · Not-rendered-yet meant your file was just deleted; one device_class caused three wrong answers**

## 2026-10-13 ~20:10Z · ZABZ-TECH · "Not rendered yet" meant *your file was just deleted*, and two things share a name

**The production behaviour that wasted the most time, and it is neither in git nor in any doc.**
`_wallpaper_paths(drn)` — which `POST /push-wallpapers` calls before its existence check — **deletes**
a staged `drn-device-<drn>-{home,lock}.png` whose pixel size is not the panel's native size:

```python
if _store_device_rank(drn_number):
 want = _device_screen_size(drn_number)
 for stale in (lock_path, home_path):
 if stale.exists():
 got = _wallpaper_png_size(stale)
 if got and got != want:
 stale.unlink()
```

Note the gate: **this only happens for a store device.** So on DRN 2002 — still
`device_class='store_device'` after I had "converted" it — my correctly staged 720×1280 LPT wallpaper
was silently deleted on the way to the check, and the API then answered
**`400 "Wallpapers not rendered yet. Call /render-wallpapers first."`** That message blames a step that
had already been done, and the file it complains about existed seconds earlier. **A message that names
the wrong cause is worse than no message.**

**Two volumes, nearly the same name:** `waze-mdm_wallpaper_data` (mounted at `/data/wallpapers`) and an
unused `wallpaper_data`. The host path is
`/var/lib/docker/volumes/waze-mdm_wallpaper_data/_data`. **A host `ls` showing your file is not proof
the container can see it** — verify with `docker exec waze-mdm-fleet-api-1 ls /data/wallpapers/`.
I asserted "staged" from a host listing twice before checking the container's own view.

**One `device_class` caused three separate wrong answers on the same device.** DRN 2002 carried
`store_device` from its life as a shop counter phone. Because of that single field:

| Behaviour | With `store_device` | After reclassifying to NULL |
|---|---|---|
| canonical device name | **`LPT STORE 2`** (applied *and verified on the device*) | `LPT 2002` ✓ verified |
| `_wallpaper_paths` | deletes a non-native-size render | keeps it |
| wallpaper artwork | the shop's "STORE DEVICE" art | the LPT art, as staged |

Fix applied: `device_class = NULL` and `device_group` `test` → `production` (guarded by drn + serial),
then the wallpaper re-staged and pushed, then the name re-derived. **The name was already wrong on the
device and the fleet API calls names immutable — that immutability protects against *arbitrary* names,
not against re-deriving the canonical one, so it was recoverable. Good to know before it is not.**

**Device names, now verified from each device** (`ota.py device-name` reads the name back out of the
device rather than trusting the enqueue): 2002 `LPT 2002`, 2004 `LPT 2004`, 2005 `LPT 2005`,
2006 `LPT 2006`, 2007 `LPT 2007`, 2008 `LPT 2008`. Wallpapers pushed to all six with the LPT art:
home 524,889 B, lock 517,495 B.

**Still the owner's to settle (pain P3167):** whether a sold unit's wallpaper should carry the fleet
number at all (SOP + packaging spec say yes; the LPT template and `upload.py`, which stages one image
for every DRN, say no), and whether "Kosher Waze" may appear on a customer-facing screen at all
(journal D96 says customer-facing copy carries LPT NAVIGATION™ only, and the shipped sticker carries
KOSHER / Waze).
