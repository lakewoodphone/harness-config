**L6657 · A remedy reported for nine rounds that cannot fire in the case it was written for: measure the guard, not the intent**

Measured 2026-10-16 on the CFO shift. From round 3 onward I reported the same open item: when cfo-resolve.py times out inside the shift, retry once instead of recording an error. In round 12 I finally implemented it - a single retry guarded by 'remaining - timeout >= 5'. The very next shift recorded retries 0, timeouts 1, with 'cfo-resolve.py returned no JSON for cluster nj motor vehicle (timed out after 25s)'. The guard was false BY CONSTRUCTION: when the timeout is the floor, remaining is already below it, so the retry is dead in exactly the situation that produces the timeout. The lesson is not 'the retry was a bad idea' but that a guard written from intent rather than from the failure's own arithmetic is untested code that looks like a fix, and it survived nine rounds of being reported because it was never run. What the data actually said: both observed timeouts sat just above the floor (25s and 28s) while the resolver answers ordinary clusters in about a second, and the same cluster answered in 1s by hand - so the floor, not the retry, was the remedy. RESOLVE_MIN_TIMEOUT 25 -> 60, and the shift now records resolver_retries, resolver_timeouts, resolver_timeouts_floor, resolver_timeouts_budget and per-result timeout_source, so the rate is measurable instead of argued. First shift after: 16 clusters, 11 resolved, 0 timeouts, 0 errors, against 1 and 2 resolved in the two shifts before.
