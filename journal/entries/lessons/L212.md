**L212 · Piping a body through PowerShell double-encodes it; keep piped bodies ASCII and check the stored bytes**

PowerShell's pipeline re-encodes the bytes, so piping a UTF-8 body into a CLI on the
other side silently double-encodes every non-ASCII character. My two pain entries
arrived with 14 mangled em-dashes ("a-hat-euro-quote" instead of a dash): the file was
read as UTF-8, written to the pipe in the console codepage, and decoded as UTF-8 again.

Rules that follow:
(a) When a body is passed through a shell pipe, keep it ASCII. A dash is a dash; there is
 no reason to spend a character on a typographic one and then have to repair it.
(b) When non-ASCII is genuinely needed, do not pipe it. Have the tool read a file with an
 explicit encoding, or pass a path rather than the content.
(c) Check the STORED bytes, not the console rendering. The corrupted text looked like a
 display artefact in the terminal output and was in fact written to disk - the same
 mistake as L195 (the instrument reporting its own transform as the data), one layer
 lower. Both times the fix was to read the raw bytes.

Cost: two journal entries written corrupted and then repaired; a repair script had to be
written and reasoned about, which is strictly more work than typing a hyphen.
