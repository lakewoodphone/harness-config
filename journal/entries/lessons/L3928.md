**L3928 · LPT website: /work-orders is the Counter, fresh worktrees need worktree:setup, and the owner has his own feedback channel**

**L · On the LPT website, "the work orders page" is the COUNTER at `/work-orders`, not `WorkOrdersHub`.** `frontend/src/App.tsx` mounts `CounterPage` at exactly `/work-orders`, ABOVE `MVPRouter`, so `MVPRouter`'s own `'/work-orders': <WorkOrdersHub />` never renders. The counter is the shop's front door and it owns the queue, the search box and the status filter. Measured 2026-10-14 from the owner's report: his "All" filter is the counter's `All statuses` radio / `Open` chip in `frontend/src/features/staff-intake/components/StaffOpenListFilters.tsx`. So a report about "the website's search" should be routed to `features/staff-intake`, and a fix in `pages/WorkOrdersHub` would have been a fix to a screen nobody sees.

**L · A fresh `phone-and-tech-full` worktree needs `pnpm worktree:setup` BEFORE any test.** `packages/shared-types` ships a gitignored `dist/`, so every file that imports `@phone-and-tech/shared-types` fails as `Failed to resolve import` and whole suites (e.g. `routes/__tests__/CounterPage.test.tsx`) fail 15/15 with what looks like a code failure. Measured 2026-10-14: 15 failures before `pnpm worktree:setup`, 0 after, no source change between. Likely also the truth behind ledger item 170's "4 tests are RED at HEAD 42e80ec".

**L · `ssh host "…$(cmd)…"` from PowerShell runs `cmd` LOCALLY.** PowerShell expands `$(...)` inside a double-quoted string before ssh sees it, so `ssh box "git log --format=$(git rev-parse HEAD)"` asked the LOCAL repo and printed `${git ...}` errors. Use a SINGLE-quoted PowerShell string for the whole remote command. The same class: base64 his text into a variable (`T=$(echo <b64> | base64 -d)`) when passing multi-line or quoted text to a remote CLI.

**L · Owner feedback has its own channel: `owner-feedback.py add --text "<his words>"`.** On the authority. It files the report as a priority-3 `lpt-website` ledger item (above the whole roadmap), raises a HIGH flag so a shift starts now, and its prompt asks for the CLASS the complaint belongs to, not the one control. Filing the same complaint by hand with `work.py add` produces a second item for one defect (I did, then dropped item 215 as superseded by 216) and no flag.

**L · `autonomy-status.sh`'s `PROBLEMS: dispatcher heartbeat is N minutes old` is AMBIGUOUS, not a death.** `~/.sms-inbox/wake-heartbeat` is written only when a RELEASE happens; when the daily cap is exhausted the loop is alive and idle but that file stops ageing while `wake-fanout.log` keeps writing a line every minute. Measured 2026-10-14 14:19Z: heartbeat 183.4 min (last release 11:16Z), `wake-fanout.log` current to the minute with `gate: daily-cap, daily_cap: 150/150 releases today`, `sources-heartbeat` 12 min old. Read `wake-fanout.log` (or the `IDLE:` line) before believing that line — the two states it cannot distinguish are "the dispatcher is dead" and "the day's cap is spent".
