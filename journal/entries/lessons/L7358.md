**L7358 · Reading a live product price, and why pricing must not run beside sourcing (accessory sourcing, 2026-10-16)**

Four transferable findings from the accessory sourcing of 2026-10-16. Each one cost real time this
session, and each one will recur the next time anything is bought for this business.

## 1. Reading a live product price from secratary-cloud: `/gp/aw/d/` and the BUY BOX

- Plain `curl` (browser UA, `--compressed`) **and** `google-chrome --headless=new --dump-dom` are **both**
 served a ~3.5 KB bot wall by amazon.com from this host. Neither errors — both return **HTTP 200** with no
 `<title>` and no price. A 200 here means nothing at all.
- `web_fetch` on `https://www.amazon.com/dp/<ASIN>` returns **HTTP 200 with the real page but truncates
 before any price**. What it does give is the **real product title**, which is enough to prove a link is
 live and points at the right product. That is worth having: it is how five links were confirmed here.
- **The working automated read is the mobile endpoint — `https://www.amazon.com/gp/aw/d/<ASIN>` via
 `web_fetch`.** Both sourcing agents converged on it independently, after the desktop and search endpoints
 returned `503` with an `api-services-support@amazon.com` interstitial.
- **Read the buy box, not the page.** A price string anywhere on a page is not an offer. The independent
 verifier found the claimed `14.99` for an Anker charger occurred **exactly once**, inside a *related-items
 carousel* (`ref_=dp_prsubs`), while the buy box read **"Currently unavailable. We don't know when or if
 this item will be back in stock."** with an empty `offerListingID` and `merchantID`. A recommended
 runner-up was **dead stock** and only the adversarial pass caught it.
- **`browser_use_run` is not a fallback.** It is in **L0_SHADOW** and returns
 `NOT EXECUTED … requires owner approval … Queued for approval as task 28737`. Nothing on this host can
 render an anti-bot page on demand.
- **Review bodies are unreachable** — `data-hook="review-body"` counted **0** on all five product pages and
 every reviews endpoint returned HTTP 200 with a 2,343-byte "Page Not Found" shell. The verifier correctly
 refused to write "no negative reviews found": **a walled endpoint is not a clean bill of health.**
- `r.jina.ai` is blocked for amazon.com (`AbuseAlleviationError`, anonymous access refused).

## 2. A pricing workstream cannot run in parallel with the sourcing workstream

Four agents ran at once — charger, mount, magnet interface, pricing. The pricing agent could not know the
part numbers because they did not exist yet, so it costed the field at **3.80** (read from a *search-result
title*, self-flagged as "the weakest number in this document") and **5.00** (an admitted independent
estimate). It proposed **10.00** and **20.00** with grosses of 6.20 and 15.00.

The actual picks cost **8.99** and **15.99**. At the proposed prices the real grosses are **1.01** and
**4.01** — the mount earning *less than the case* on a part with fitment and support risk. The agent's own
sensitivity paragraph had warned the recommendation "does not survive a cost above 20.00"; it did not
survive 15.99.

**Price the SKU you are going to buy.** Pricing sits on the dependency chain of sourcing: fan out the
sourcing, then cost it. A margin built on an estimated cost basis is a guess wearing a table, and it is
worse than no number because it looks decided.

## 3. N agents hitting one retailer concurrently get rate-limited, and it looks like "blocked"

The pricing agent lost **every** retailer it tried — Amazon 403, Walmart 412, AutoZone, O'Reilly, Advance,
Best Buy, Target, Newegg, eBay, B&H — in the same minutes that the two agents beside it were reading Amazon
successfully. The likeliest cause is concurrency, not policy. Give each agent a **different source**, or
stagger them, and treat "403 from retailer X" as **unproven until retried alone**.

## 4. The MDM's own health endpoint is a false pass; a data route is the evidence

- `GET https://mdm.abletelsolutions.com/api/health` → **HTTP 200, body `Waze MDM is online`** — and the tree
 already records that **Caddy answers 200 for any unrouted path**, so this proves nothing about the service.
- `GET https://mdm.abletelsolutions.com/api/fleet/devices` → **HTTP 401 `{"detail":"Invalid token"}` in
 0.02 s**. A real route answering with its real auth error **is** positive evidence the API is up.
- No token was available in this session, so **no device data was read** — and the 200 was not reported as
 health, because it is not.
