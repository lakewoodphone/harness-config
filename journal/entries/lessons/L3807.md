**L3807 · autosync ships git archive HEAD, not the working tree - so an uncommitted correction never deploys, and a hand-fix is transient**

The estate's deployment ships `git archive HEAD`, not the working tree — so a correction an agent makes to a file and does not COMMIT can never reach the machine it is meant to fix, and the load side will silently keep the old text forever.

FOUND 2026-10-14 by a mesh child's census and confirmed by me at the source. `scripts/autosync.ps1` on ZABZ-TECH, around line 497-520:

 # snapshot of HEAD exported to a temp directory: committed changes land, and nobody's in-flight work
 $snapshot = Join-Path $env:TEMP ("harness-config-snap-" + (Get-Date -Format 'yyyyMMdd-HHmmss'))
 & git -C $gitDir archive --format=tar --output=$tarball HEAD
 & tar -xf $tarball -C $snapshot
 $apply = (& $python (Join-Path $snapshot 'scripts\sync.py'))
 $verify = (& $python (Join-Path $snapshot 'scripts\sync.py') --dry-run)

**Why this is the root cause of a fault that has now been reported fixed three times.** ZABZ-TECH's `presets/zabz/agent.cordis.yml` working tree held the CORRECTED persona (56,297 B, sha `506dc5066592`, the same bytes as the authority's loaded copy and as the blob at `remotes/zabz-yoga/main` `de0796c1`), while `~/.dsh/.agent-presets/zabz/agent.cordis.yml` loaded the **pre-round-1** text (58,677 B, `7c79b04f`), missing the entire "The one you must not get wrong" section, still naming the frozen office box as the authority, still saying `zabz-tech-linux` is "a macOS mini for his employee Yisroel", and carrying three literal `{cwd}` tokens against the corrected two. Round 2 reported this fixed and verified at 2026-10-14T01:35Z. It was never deployed, because the correction sat in the working tree and the deployer only ever exports HEAD.

**The trap this creates for an agent, stated plainly: `sync.py --dry-run` reads the WORKING TREE and says `WOULD UPDATE -> ~ agent.cordis.yml`, while the deployed pass reads HEAD and ships the old file.** Two different sources of truth for the same operation, and the diagnostic tool reports the optimistic one. That is why the dry run looked like a fix waiting to happen and the machine kept loading the old text.

**And it makes a hand-fix transient.** I corrected the loaded surface on ZABZ-TECH directly (byte-exact `Copy-Item` from its own repo; verified `compared 15 match=15 drift=0`). **The next autosync pass will overwrite it from HEAD and restore the 58,677-byte text.** The durable fix is to get the correction COMMITTED on the lineage that machine's sync pulls (`$syncRemote/$branch`), which is the instruction-convergence job — 6 files need a hand-merge, and `lpt-production-case-work` is the one that does not (ZABZ-TECH's 18,009 is a strict superset of the reference, +79/-0).

**The general rule:** *a deployer that sources from a commit and a validator that sources from the working tree will disagree, and the disagreement looks like health.* Before believing that a configuration change is deployed, establish (a) what the deployer reads, (b) what the validator reads, and (c) whether they are the same object. Here they were not.

**A second, narrower lesson from the same fix.** My first correction copied the file as text and converted line endings; it reported success and `preset-drift` still said DRIFT, because the backtick escapes in the PowerShell replacement did not survive being piped into a remote PowerShell over ssh — the replacement became a no-op on the literal string `rn`. A **byte-exact copy** was both the correct operation and the only one the detector could accept. **When a tool compares bytes, fix bytes — and never pipe a script containing escape characters through an ssh stdin boundary without verifying the escapes arrived.**
