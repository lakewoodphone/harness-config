**L3843 · The "unfiltered network" bypass for the dictation model cannot work — the DoH profile is pinned device-wide, not per-network.**

**What I corrected:** `05-test-plan.md` §4e.3 (in the voice-input dossier, and cited by the new Waze source of truth) offers a cheap route to the missing dictation model — *"Get the device onto an unfiltered network now, enable dictation, confirm a sentence dictates, then run the test."* **That route is dead while the DNS profile is installed**, because the profile pins DoH for every network the device joins.

**Read this session (2026-10-15 ~20:2xZ), from `waze-mdm-01`, the served profile — not the repo copy:**

```
ssh hetzner 'sed -n 1,80p /opt/waze-mdm/profiles/waze-siri-filter-dns.mobileconfig'
```

- `PayloadType` `com.apple.dnsSettings.managed`, `PayloadIdentifier` `com.abletel.waze.sirifilterdns.settings`
- `DNSProtocol` = **HTTPS**, `ServerURL` = `https://mdm.abletelsolutions.com/dns-query`
- `AllowFailover` = **false**, `ProhibitDisablement` = **true**, `PayloadRemovalDisallowed` = **true**
- **No `OnDemandRules`, no `SupplementalMatchDomains`, no SSID scoping** — there is nothing in the payload that makes it conditional on the network.
- File: 1,552 bytes, mtime `Jul 21 02:03`.

**Consequence:** every lookup from the device goes to our resolver on any Wi-Fi or hotspot, and that resolver answers NXDOMAIN for `updates.g.aaplimg.com` (the CNAME target of the allowed `updates.cdn-apple.com`). Measured live at the same time, `docker logs --since 24h waze-mdm-dns-filter-1`: **509 allowed** for `updates.cdn-apple.com`, **299 blocked** for `updates.g.aaplimg.com`, newest pair both at `[15/Oct/2026 20:21:12]`. And the fix is still not applied — `grep -n 'mobileassets\|APPLE_UPDATE_HOSTS' /opt/waze-mdm/proxy/waze-webtrap.pac` returns nothing, md5 `18e81bc82dc64ccbf53c81c2a435b764`, unchanged from the 15:0xZ read.

**So the only two real routes are:** (1) the filter fix — PAC path rule DIRECT for `/mobileassets/` plus the three CNAME targets, in one window (else the fleet gets an OS-update path); or (2) remove the DNS profile from a **test** unit (2003 or 2001 — never a production unit), provision on an unfiltered network, then reinstall. `Remove profile` is an MDM-side action because the phone cannot disable it.

**Also worth knowing, and it cuts against the network theory:** a sibling device on the *same* filter — the 2003 iPad — reportedly dictates (journal `H4040`, a doc read, flagged as not re-tested). So the model **can** exist behind this filter on a device that already has it; what the block plausibly stops is a **new** download. The discriminator is therefore "has this unit's asset", not "can this network reach Apple" — which is exactly the comparison `05-test-plan.md` §1b (shop phone beside a kiosk) exists to make, and it costs nothing.
