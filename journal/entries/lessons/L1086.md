**L1086 · A Windows path in a Linux column reads as corrupt audio; and supervise idempotent jobs**

## A Windows path stored in a column is read on Linux as "the file is corrupt"

`dialpad_media_file.local_path` held `data\dialpad\recording\<call_id>.mp3` for 1,933 of 4,694
rows — written by runs on the Windows workstation, read by the pipeline on the Linux authority.
The file was there the whole time, under `/home/zabz/personal-secretary-mvp/data/dialpad/recording/`;
only the string was wrong.

The failure did not look like a path problem. `_audio_file_problem()` opened the path, found
nothing, and recorded `invalid_local_audio:file_read_failed`, so on 2026-09-14 a transcript backfill
turned **1,107 calls into terminal "failed" rows in four minutes** and, because the selector treated
`failed` as terminal, they would never have been retried. Every symptom said "this audio is
unreadable"; one `ls` said otherwise.

Two rules:
* **A path is data.** A path written on one platform and read on another is a defect that hides
 behind every consumer's error handling, and it will be reported as the *content* being bad. When a
 batch fails uniformly and instantly, compare the failing rows against the filesystem before
 believing anything about the payload.
* **A terminal failure needs a reason you can re-open.** `failed` with no classification meant a
 wrong string in one column silently became permanent data loss. `scripts/dialpad-media-path-repair.py`
 fixes the stored paths (2,200 rows repairable, exact reversal written to a JSON backup) and
 `dialpad-transcript-gap.py --retry-failed` re-opens the terminal rows.

## Idempotent jobs should be re-run by a supervisor, not made transactional

The same backfill then died with `sqlite3.OperationalError: database is locked` — the pipeline opens
its own connection per row with no busy timeout while the app writes to `secretary.db` continuously
(autopilot ticks plus the 30-minute harvest). Rather than re-engineer the pipeline's transactions,
the job is wrapped in a small loop that re-runs it: it is idempotent (every call already transcribed
is skipped), so each re-run is a *continuation*, and a lock costs one cycle instead of the whole job.
**A 40-attempt supervisor around an idempotent job beats a redesign that must be verified against a
live database** — and it leaves the record of how often it was actually blocked.

This is the second time in the journal that concurrent writers on the authority killed a long job
(see the search-index refresh, 2026-09-14). It is a pattern, not an incident: the authority's SQLite
is written by the app, the harvest, the kernel and now these tools, and only some of them set a busy
timeout.
