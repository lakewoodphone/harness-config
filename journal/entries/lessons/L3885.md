**L3885 · SerpAPI exhausted every month: four call sites, a no-op guard, and a health table wired to nothing**

The owner's question was "why do I keep getting emails that serpapi is exhausted". The answer was not the plan; it was four call sites and a monitor that never existed.

## What was actually draining 250 searches a month

1. `scripts/collect_ebay_listing_images.py:259` called `_via_serpapi(url, product_id)` **once per eBay listing**, unconditionally, before Firecrawl/Jina/Playwright. Any sourcing run over more than 250 listings consumed the whole month in one sitting.
2. `scripts/procurement/scrape.py` had `_CHAIN = [_via_serpapi, _via_firecrawl, _via_jina, _via_playwright]` — the metered provider FIRST, ahead of providers already paid for or free.
3. The guard meant to limit the second one was a **no-op**: it computed "not a product page, skip SerpAPI", the comment said "skip bare clicks", and the body was `pass`. SerpAPI was called for every URL.
4. The plan is **Free: 250 searches a month**, renewing on the 20th (measured `plan_renewal_date = 2026-11-20`).

## The blind spot, which is the part worth remembering

`scripts/procurement/providers.py` `record_success`/`record_failure` wrote only to a module-global dict and `data/procurement/providers_state.json`. **Nothing under `scripts/procurement/` imports `app.services.provider_health`.**
The only production caller of `record_provider_outcome` was `app/services/ai_gateway.py:4065` — model providers. So `provider_health_events`' two `provider='google'` rows were Gemini calls, and SerpAPI had **no observer at all**.

**A health table that looks like monitoring and only watches one class of provider is worse than no table**, because its emptiness reads as "nothing is failing". When you are asked "why did nobody see this", the answer is usually that the recorder was never wired to the thing that broke.

## What landed (measured, both merged to master)

- **PR #98** (`ec3ce003`, `a8dae067`, `3c122a2b`) — chain reordered so SerpAPI is last; the guard is a real `continue` via `_serpapi_applicable()`; a single choke point `scripts/procurement/serpapi.py`; a durable, fail-closed quota ledger (`scripts/procurement/quota.py`, ceiling 250, reserve-before-request, alert line per period); `providers.py` now writes the real `provider_health_events` row with `strict=True` and a loud failure log; all four call sites routed, including the eBay one.
- **PR #99** (`6016db21`, `origin/master` HEAD) — the quota period default was day 1, which reset the ledger up to 19 days early and handed back allowance the account did not have. Default is now **20**, the real renewal day, and the test that pinned 1 now pins 20.

Verified by me, not taken from the agent's report: `tests/test_procurement_serpapi.py` **20 passed**; `test_provider_health + test_model_ops_monitor + test_tool_contracts` **137 passed**; `app.__file__` resolved to the worktree, so the tests were not secretly running against the main checkout.

## Still open — do not read the above as "finished"

1. **`app/web_access.py:316` still calls `serpapi.com` directly** from the live API's own `web_search` chain (`["brave","tavily","serpapi",...]`). It is the same vendor and the same 250-search allowance, and it is **unguarded**. Deliberately not half-fixed by the agent; it is the next unit of work.
2. **The fix is merged, not deployed.** The live API runs on `secratary-cloud`; nothing here reached it. Until it does, the emails can still arrive via the API path.
3. **The ledger starts at 0** and does not know the 2 searches already spent in the current cycle.
