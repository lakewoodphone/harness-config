**L12238 · lpt-write total set takes a PRE-TAX amount; passing the tax-inclusive figure double-taxes the customer**

Measured 2026-10-21 on WO2608190005 (mrs woldiger, S20 FE charging port). Owner: "it's 85 plus tax, so put that on the work order."

`lpt-write total set` takes a PRE-TAX amount and adds tax itself.

 --amount 90.63 -> "total 0.00 -> 96.63 ... the figure given is BEFORE tax: 90.63 + 6.00 tax at 6.625% = 96.63 to pay"
 --amount 85 -> 85.00 + 5.63 tax = 90.63 stored in orders.total

So the customer's tax-inclusive figure must never be passed: 90.63 would have stored 96.63 and overcharged her six dollars. Pass the number the owner quotes. `orders.total` is tax-inclusive; the tool does the 1.06625, you do not.

RULE: always dry-run `total set` and read the `tax` line before `--apply`. The plan prints both the stored total and "N to pay", so the double-tax is visible before it is written. Same applies to any money write - the plan is the proof, the header is not.

SECOND FAILURE, same hour, worth its own line: I edited a sync record whose replacement text contained RAW DOUBLE QUOTES inside a JSON string, then ran the validator and LET THE SCRIPT CONTINUE past the failure, pushing an unparseable sync record to main (commit 4a7f7c47f, fixed in 79d028a2b). A validation step that does not abort is decoration.

RULE: capture the validator output and exit non-zero BEFORE any git operation. Pattern that worked:
 $v = python -c "..." # prints VALID or INVALID <msg>
 if ($v -notmatch '^VALID') { exit 1 }
and re-validate the pushed copy by reading it back out of origin/main, not the working tree - the working tree is what you just asserted about, so it cannot also be the evidence.
