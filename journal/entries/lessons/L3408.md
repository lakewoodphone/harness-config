**L3408 · A literal in code is a time bomb — this time the bomb was a Postgres enum value**

MEASURED 2026-10-08, on secratary. Six Lakewood money/customer report scripts asked for
`orders.status = 'COMPLETED'`. The live `OrderStatus` enum has NEVER contained that value — it is
AWAITING_DIAGNOSIS, AWAITING_APPROVAL, AWAITING_PARTS, AWAITING_PAYMENT, READY_FOR_PICKUP,
CANCELLED, UNFIXABLE. PostgreSQL rejects the whole statement:

 psycopg2.errors.InvalidTextRepresentation: invalid input value for enum "OrderStatus": "COMPLETED"

Consequence: `lpt-growth-report.py`, `lpt-master-analysis.py`, `lpt-consolidated-export.py` and
`finance/partner-referral-audit.py` could not run at all, and nobody noticed for five weeks because
the only runner was a Windows PowerShell file that cannot execute on the authority where the data
and the venv live. The last consolidated business analysis was 2026-09-01.

The same class of defect, same session, three more times:

1. `finance/lpt-monthly-pnl.py` defaulted to a Windows path with no platform fallback. On Linux
 `sqlite3.connect("C:\Users\ezabz\...")` does NOT fail — it CREATES a 0-byte database with that
 literal filename, and the script then reports `no such table: transactions`. A wrong path reads
 as missing data. One such junk file was created during this session and removed after confirming
 it was empty.
2. `finance/lpt_analytics/customers.py` compared status to "COMPLETED" and a broad `except` swallowed
 the mismatch into a hard 0 — the "Done" column read 0 for every period and looked plausible.
 It was not a dead metric: the 2026-08-28 report shows Done = 29/62/75/79/57.
3. `finance/partner-referral-audit.py` counted 0 completed jobs for a partner with 81 orders sitting
 at READY_FOR_PICKUP, i.e. it reported ZERO commission owed while money was owed.

THE RULE, and it is the same rule as the model-name failure (L1606): a value that lives in a
database, an API or a vendor catalogue must be RESOLVED AT RUNTIME; when it cannot be resolved the
code must report null/unknown and say so — never a confident zero. `status_workflow_config` in
production still lists a `COMPLETED` status with isFinal=true; that stale vocabulary is the source.

HOW IT IS FIXED NOW: every affected script reads `enum_range(NULL::"OrderStatus")` from the live
catalogue and picks from a documented preference list; when no live value means "finished" they
return null and print that they could not measure it. `finance/lpt_analytics/orderstatus.py` is the
engine-side resolver.

CHEAPEST DETECTOR for the next instance: `grep -rnE "status *= *'" scripts/` against a
database-backed column. It found all four sites in seconds.
