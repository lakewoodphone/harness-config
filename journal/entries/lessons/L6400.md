**THE CAVEAT, which matters more than the number.** After the landing, the canonical tree IS the
repaired union. Where two trees held one id with two bodies, the survivor keeps the id and the loser
was RENUMBERED — so the live tree is *by construction* different from the raw sources at every one of
those ids. **587 is that repair, not a new fork.** The pre-landing fork measured 524 on the same
instrument. **So the post-repair baseline is not 0, and a future session must read this as a baseline
and watch for GROWTH in the count, never for zero.** A monitor that alarms on non-zero here would be
the same false-positive class as the instrument fixed earlier tonight — a strict test whose reading
gets acted on.

**The patcher is a generator, not an edit**, so the other trees can take it:
`scripts/evolution/apply-cross-tree.py`. It refuses when the anchors are missing or when `cmd_check`
does not use the `errors`/`infos` accumulators, is idempotent, keeps a timestamped backup, and writes
through a temp file plus `os.replace` so a session reading the tool mid-patch sees one version or the
other.

**Two bugs in it, both caught by reading output rather than by the tests passing:**
1. It inserted the three blocks top-down. Inserting at a low index shifts every index above it, so the
 `--cross-tree` argument landed four lines ABOVE the `check` subparser and attached to a different
 one. The file compiled, `check` still passed 0 errors, and the patch looked successful. Only
 printing `check --help` showed it. Fixed by inserting in DESCENDING index order.
2. `Path.open(newline=...)` is not dependable before Python 3.10 and the mac mini runs 3.9.6; switched
 to builtin `open()`.
