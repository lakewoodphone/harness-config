**L11262 · On the authority, lpt reads need the app venv interpreter - and the missing psycopg2 silently degraded lpt-write's last guard**

Measured 2026-10-20 on secratary-cloud (the authority).

WHAT HAPPENED: `lpt doctor` reported `DOWN operational - LPT_DB_A_DSN is set but psycopg2 is not installed on this machine`, and `lpt ticket <WO>` failed the same way. /usr/bin/python3 here is PEP 668 externally-managed, so `pip3 install psycopg2-binary` refuses ("override with --break-system-packages"). The app venv already has psycopg2: `/home/zabz/personal-secretary-mvp/.venv/bin/python3` -> `lpt doctor` reports operational OK in 55-75 ms, both stores reachable.

THE PART THAT MATTERS MORE THAN THE INCONVENIENCE: `lpt-write` runs every successful write through `confirm_via_read_path()` - "a second opinion through the read path the shop actually uses" - and that read uses the SAME broken import. So after every successful insert it printed `the second opinion and it disagrees. Re-run lpt ticket before trusting either.` That sentence reads like a data problem. It was an import problem. I hit it three times in one session on three successful writes.

FIX APPLIED: `/usr/local/bin/lpt` (mode 755), a two-line launcher that execs the venv interpreter against `/root/code/lpt-ops/bin/lpt`, with the reason in a comment. Verified: `lpt doctor` OK, both stores. `bin/lpt` in the repo is mode 644 and is not on PATH, so before this there was no `lpt` command on the authority at all.

GENERAL RULE: a "verification failed" message is not evidence the write failed. Read what the verifier could not do before believing what it said. And when a tool ships a second-opinion guard, make sure the guard CAN run on the host the writes originate from, or every success looks like a disagreement.
