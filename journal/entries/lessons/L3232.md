**L3232 · Registering a scheduled task unelevated: -LogonType S4U is Access denied, Interactive + the current user succeeds**

Measured on ZABZ-YOGA 2026-10-02, non-elevated PowerShell 7 (WindowsIdentity says ZABZ-YOGA\ezabz,
IsInRole(Administrator) false):

 Register-ScheduledTask ... -Principal (New-ScheduledTaskPrincipal -LogonType S4U)
 -> "Access is denied." Task NOT registered.

 Register-ScheduledTask ... -Principal (New-ScheduledTaskPrincipal -UserId <current user>
 -LogonType Interactive -RunLevel Limited)
 -> succeeds. Probed with a throwaway task (registered, then unregistered), then used to
 register the real one.

The repo already said half of this: dshw.ps1 notes that the non-elevated token which runs this
harness "CANNOT re-register it, cannot delete it" for tasks created by the elevated context, and
harness-verify.ps1 notes the Tasks file is owned by BUILTIN\Administrators with read-only grants
for the running user. What was missing is the way FORWARD without elevation, which is the
Interactive logon type plus the current user's SID.

Consequences to design around:
1. An installer that only works elevated is an installer that silently does nothing in the hands
 of the agent that actually runs in this harness. Prefer Interactive + current user as the
 DEFAULT; make S4U the opt-in from an elevated shell.
2. Interactive means the task runs only while that user is logged on. On a workstation the owner
 works at, that is the honest scope: when nobody is logged on, nobody can see the thing the
 instrument reports. Where the instrument must run headless (an office machine with no console
 user), it needs elevation, and that is an owner action, not a code fix.
3. Never verify registration by the absence of an exception alone: drive one pass (-RunNow) and
 read back LastTaskResult. This repo has been bitten twice by tasks that registered "fine" and
 never ran (L174, trigger queued because -At was in the future).
