**L2345 · A writer and a watcher on two checkouts of one repo: how the journal diverged 102 commits while its monitor said clean**

**What happened.** On 2026-09-22 the journal on secratary was found 5 commits ahead and **102 behind**
`origin/master`, three days after P2185 first described the same thing. The cause was not the merge —
it was that **secratary held two separate checkouts of the same repository**, and the machine watched
the wrong one:

| checkout | who writes it | who monitors it |
|---|---|---|
| `~/code/harness-config` | every session — this is where `journal.py append` writes | **nobody** |
| `~/harness-config` | nothing (it was clean at `origin/master`) | `scripts/autosync.sh`, every 15 min |

`autosync.sh` could not have caught it even if pointed correctly, for two independent reasons, both by
design:

1. **it never commits.** So entries written by a session sat as *uncommitted files*, and autosync
 reasons entirely in commits (`git rev-list --left-right --count origin/BRANCH...HEAD`).
2. **its dirty count excludes untracked files** (`git status --porcelain --untracked-files=no`), and a
 newly appended entry is an untracked file. So the divergence was invisible twice over.

Meanwhile autosync reported, every fifteen minutes, `{"result":"clean","detail":"at 6a48b11; nothing to
apply","behind":0,"ahead":0}` — a confident reading of a checkout that was genuinely fine, while the
journal checkout rotted. This is the same failure class as the stale-database crisis: **a true number
about the wrong thing, reported as health.**

**The fix, applied and verified 2026-09-22.** (1) `~/harness-config` is now a **symlink** to
`~/code/harness-config`, so there is one checkout and autosync watches the tree sessions actually
write; the old clean checkout is kept at `~/harness-config.pre-unify-20260922`. (2) A new
`~/bin/journal-commit.sh` runs immediately before autosync in the same cron line and commits changes
**under `journal/` only** — never `git add -A` (that is what swept 1728 files into one commit on
2026-09-17), never push/merge/rebase/reset/force, and it stands down if a `MERGE_HEAD`, `REBASE_HEAD`,
`CHERRY_PICK_HEAD` or `index.lock` is present so a session mid-operation always wins. Verified
end-to-end: the committer made `0c271d7`, autosync pushed it, and `master...origin/master` is level.

**Rule to keep.** When a system has a writer and a watcher, check that they are the *same instance* of
the thing — not just the same repository. "Same origin, two checkouts" is enough to make a monitor
green and the data stale, and it will look healthy for as long as nobody compares the two paths.

**Caveat found while verifying, not fixed:** autosync captures `BEHIND`/`AHEAD` *before* it pushes and
writes those numbers into `~/.dsh-sync-status/status.json` afterwards, so a run that successfully
pushed still reports `ahead: 1`. Nothing reads `ahead` today (the sentinel that would is explicitly
unbuilt in the script), but a monitor built on it would see a permanently-frozen machine.
