**L12354 · A resumed attempt has no revision of its own - it inherits the page watermark from the boot read, which is why a second device's first write was refused stale 300 ms and one round trip late**

Branch fix/stale-first-write on _pt-409, commit 3fca94a (parent 252509d). Closes open defect 4 of H12458 and
the measured defect in L12301: the returning device's first write refused 409 at 11.5 s.

WHERE THE RESUMED REVISION CAME FROM, because this is the part a future session will need. A resumed attempt
never had a revision of its own. It used the page watermark (assessment.tsx:819), written on a second device
only by the boot read (assessment.tsx:1178 via applySharedStateToUi) and by settled writes
(assessment.tsx:869-870), and read by the queue at ISSUE time (persistence-write-queue.ts:983). The resume
handler issued no read, so the click at 11.5 s carried whatever the boot read left - a revision the library
had already passed. THE FENCE DOES NOT COVER IT AND IS NOT MEANT TO: noteReadInFlight parks a write until a
read answers and then LATCHES OPEN for the rest of the page's life. That is correct for a page answering
questions and wrong for the one moment the page is handed an attempt it has not touched since load.

THE FIX: src/components/attempt/resume-read-first.ts states one rule - opening a resumed attempt is a READ then
a WRITE, and the write is issued from the copy the read delivered - and resumeDraftOnFirstClick goes through
it via the same refreshStoredRegistry every other read uses. It also means the attempt now opens at the state
the ACCOUNT holds, not the state the browser remembered.

THE TRAP THAT WOULD HAVE MADE THIS A SILENT OVERWRITE. The read MUST be loadSharedAssessmentLibraryState
(content-comparing, raises bootConflict -> queue.enterConflict), never readSharedAssessmentLibrarySnapshot
(bare revision). A bare revision read raises the watermark to the newer revision and lets this device's older
copy replace a newer one - the exact silent replacement every rule in persistence-write-queue.ts exists to
prevent. Test 5 pins it: server holds MORE answers for the same attempt, nothing is re-issued, the library
keeps its copy.

THE VERDICT AFTER A 409, traced and already correct before this change: drain re-reads once, planMergeForward
proves the intervening write was this device's own aborted save of the same attempt, one re-issue at the
revision the refusal reported, and the queue resolves the caller with THAT verdict - "All saved" on success.
Proof fails -> conflict surfaced, nothing written. Re-issue gets no verdict -> "unreachable" -> the copy says
the account has not confirmed it. It can never read "All saved".

ONE DEFECT FOUND AND LEFT ALONE, because src/lib/assessment/* was out of scope: in drain, after a PROVEN
merge-forward whose re-issue gets no verdict, unconfirmedIssueRevision is computed from the FIRST write's
revision (persistence-write-queue.ts:1071), not the re-issue's one-past. A later 409 would then be attributed
"unattributable" or "another-writer" when it was this device's own. Narrow, and it only affects the sentence.
