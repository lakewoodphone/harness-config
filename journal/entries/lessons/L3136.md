**CORRECTION to L3135 — "a dead-weight agent is a broken model chain" was wrong. The model chain was fine; the agent was stuck reading its own note saying it was stuck.**

Written 2026-09-30, three hours after L3135, because the evidence that followed contradicts it. L3135
said the two dead-weight agents were failing on LLM calls and that the remedy was to repair their
department model candidate list. **That was an inference from their `agent_working_memory` summary
alone, and the summary was the thing lying to me.**

**What the trace data actually says.** I then read their own telemetry:

- `model_usage` for `frontier_risk_board`: **`success = 1`**, on `deepseek-v4-pro` at 15:54:06 and on
 `deepseek-ai/DeepSeek-V4-Flash-0731` at 15:47-15:48, with 300-784 completion tokens each. The calls
 were **working**, that day, minutes before I diagnosed a model failure.
- `gateway_trace_span`: `status = ok`, detail `{"error": null, "success": true}`, canonically routed with
 `candidates_eligible: 3` and a real `decision_id`.
- `tick_telemetry`: `outcome = escalate`, `tick_quality = empty`, `tick_number = 0`. **The tick is what
 fails, at step zero, every time** — not the call inside it.
- `DEPT_MODEL_CANDIDATES` was `("deepseek-v4-flash",)` mapping to
 `deepinfra/deepseek-ai/DeepSeek-V4-Flash-0731`, which is exactly what the gateway serves for
 `secretary-auto`. Nothing was broken there.

**The actual mechanism, and it is a nastier one.** `agent_worker` injects
`agent_working_memory.context_summary` into **every** prompt (`agent_worker.py` around line 3753 reads
it and `build_focused_prompt` receives it). That summary read:

> *"Step failed (escalate): Cannot execute. The working memory indicates this step was previously
> attempted and failed with three consecutive LLM call failures, and the recorded failure reason
> references an owner physical act..."*

**The model read that, concluded it could not execute, and escalated.** So the agent was blocked by a
sentence it had written about itself, re-injected on every tick, and the block was self-confirming:
every failure wrote a fresh failure note, which guaranteed the next failure. It ran 38 and 41 times that
way. The model chain was the one thing doing its job.

**The general rules this leaves behind.**

1. **An agent's self-report is not evidence about its dependencies.** Working memory is a prompt input,
 and a prompt input that says "you are stuck" causes the next escalation. Read `model_usage`,
 `gateway_trace_span` and `tick_telemetry` — the traces — before believing a failure narrative.
2. **A poisoned summary is a latch, not a state.** Nothing in the retry path cleared it, because the set
 of things that clears it is chosen by the model reading it. Any self-description fed back into the
 prompt needs an independent expiry, or a reset that does not depend on the agent agreeing.
3. **The right unit is the tick, not the call.** `outcome` and `tick_quality` are where a stall shows;
 the call statuses were green throughout.

**Fix applied:** both summaries replaced with a short factual note explaining what the previous one was
and that no prior failure is claimed, old text preserved verbatim at
`/home/zabz/agent_working_memory_before_20260930.json`. **Still to verify:** that a tick after
2026-09-30T16:41Z does not come back `escalate`/`empty`. If it escalates again it will be a **real**
escalation with a specific ask, which is a different and legitimate outcome — not dead weight.

**Evidence:** `model_usage` and `gateway_trace_span` rows for `frontier_risk_board` on 2026-09-30;
`tick_telemetry` `outcome='escalate'` / `tick_quality='empty'` / `tick_number=0`; `agent_working_memory`
before-and-after; `app/services/agent_worker.py` line ~3753; kernel `latest.json` `agent_dead_weight`.
