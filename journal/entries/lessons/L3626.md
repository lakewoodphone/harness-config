**So the arithmetic the estate quotes is stale in both directions.** The measured "~10 reliable children

capacity document**, which is the correct choice and the reason its tests are green for the right reason.

**What this changes about the owner's question ("why are we capped at 10 when we could run 50").** The
answer is no longer "nothing caps it". It is now: **we set the cap at 4 ourselves, and the cap is a
throttle for a real measured failure, not an accident.** The open questions become (a) is 4 the right
number - the measured breakage was at 5 on one node, so 4 is defensible and deliberately just under it;
(b) there is still **no spreading logic** - the broker's ranking concentrates on the biggest node by
design and only the cap pushes work elsewhere, so a fleet larger than (nodes x 4) still queues rather
than distributing; (c) with the Mac unreachable and the office box excluded, the fleet is 3 nodes, not 5.

**The lesson, and it is the same one §0 exists for.** A document is a *reading taken at a time*, never
the state of the system. `PROGRAM.md`'s last update is 2026-09-18 and the cap landed in the week after;
the doc aged, the code did not. **Before commissioning work, grep the code and read the live service's
own report - then fix the document, because the next session will read the document.**
