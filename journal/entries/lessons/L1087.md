**L1087 · An allocator that only looks at the new store steals ids the old store already owns**

An id allocator must take its ceiling over EVERY source that can claim an id, not over the store it is writing into. The v2 migration's first live run computed `max_number()` from `entries/` and the cache only, while the real numbers (L1..L325, H1..H117, ...) lived in `log/**` and the flat files. So a flat entry claiming a taken id was bumped to a number the *legacy* record already owned: the flat file's L162 text landed in `entries/lessons/L170.md`, and the real L170 was later bumped elsewhere. Result: 563 files whose name, marker id and heading id disagreed, in a tree that then became the ceiling for the next run.

Fix, and the rule: one `allocation_ceiling(kind)` over `entries/`, the cache, every `log/**` marker, the flat sources and every git ref; never return a number at or below it; and build the full claim set from all sources BEFORE assigning any id, so a candidate's own id is not a conflict with itself.

Evidence: 563 disagreeing files measured by `_scratch/j-classify.py` before the rebuild; 0 after; `selftest.py` includes a partial-then-full migration case that asserts no allocated number is below the legacy ceiling.
