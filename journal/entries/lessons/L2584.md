**L2584 · Shared clone: origin/test moves under you - check deletions against your merge-base, not the live ref**

In a monorepo checkout with several git worktrees, `origin/test` is a SHARED ref and it moves under you while you work: sibling worktrees run `git fetch`, which updates `refs/remotes/origin/test` for every worktree of that clone.

Measured on ZABZ-YOGA 2026-09-25 (worktree `_worktrees/phone-and-tech-full/lpt-cust-ui2`, branch cut from `origin/test` = f7de90a5e): 90 minutes later `git checkout --detach origin/test` landed on 598d3d64a, four commits further on, because other agents in the same clone had fetched a sibling branch merge.

Consequence for a "did you delete anything?" acceptance check written as `git diff --diff-filter=D --name-only origin/test HEAD`: it reported `docs/business-workflows/lpt-repairs-portal-payments/FIELD-USAGE-2026-09-25.md`, deleted by `0ed792184` / `20fca49d6` / `8ac438b4f` on `origin/lpt/field-usage-20260925` — NOT by me. Against my actual base the same check is empty.

Do this instead: (1) record the base sha when the branch is cut; (2) run the check as `git diff --diff-filter=D --name-only <base> HEAD` AND as `... origin/test HEAD`; (3) when they disagree, run `git merge-base HEAD origin/test` and `git log --oneline <base>..origin/test` + `git log --oneline <base>..origin/test -- <path>` to name the upstream commit that made the difference. Report both readings with the evidence rather than either claiming a clean diff or "fixing" a deletion you did not make. Never rebase onto the moved ref to make the check pass: that pulls other workstreams' unverified commits into your branch.
