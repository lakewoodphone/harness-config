**L3784 · nohup and setsid are not durable for long remote jobs on the authority - a systemd transient unit is**

MEASURED 2026-10-14 four attempts at running one three-way pytest comparison on secratary-cloud from an ssh command. One: the first run had two bugs of my own. Passing the stop-on-first-failure flag to pytest halted the suite at the first PRE-EXISTING failure and hid every test after it; and piping pytest into tail made the shell status variable the exit code of TAIL, so a run with failures printed exit zero. Both are recorded in the harness own comments so they are not re-introduced. Two: the relaunch died with the ssh session, and the OLD result files were still on disk, which is how a stale artefact passed for a fresh one. Three: a pkill whose pattern matched its own command line killed its own ssh command - use the bracket form. Four: setsid combined with nohup from a non-interactive ssh still left nothing running. WHAT WORKED: systemd-run with a unit name and the collect flag, running the script. It reported ActiveState=active and SubState=running, it survives the session, its output goes to the journal, and collect removes the unit when it exits. THE RULE FOR THIS ESTATE: any job that must outlive the command that starts it goes into a systemd timer or a transient unit, never nohup, never setsid, and never a scheduled task on a workstation. This is the same lesson as the transcript archive: the estate has repeatedly trusted a launcher instead of a system that owns the job.
