**L1478 · A feature wired to the wrong branch is not tested by testing its helper: find every site that makes the decision**

A feature that is wired to the wrong branch is not tested by testing its helper

Twice in one night, in the same file, the same mistake in different clothes:

 * the budget extension was attached to the pre-tick guard, while the check that
 actually fires lives inside the step loop. 39 tests passed; the feature never ran.
 * the reconnaissance nudge read a counter that is reset every tick, so its threshold
 was unreachable. It had never fired in production.

Both looked present in the source and both were inert. What finally caught them was
EXECUTION: a live session's failure marker ("reached planned 5/5 work steps") named the
site that fired, which was not the site I had edited. Reading the marker's wording was
worth more than the test suite.

HABITS THAT FOLLOW:
 1. When patching a decision, find EVERY site that makes that decision. Grep for the
 outcome, not for the code you already wrote: `grep -n "budget_exhausted"` would
 have shown two reasons, `budget_exhausted` and `step_budget_exhausted`, in two
 places.
 2. Prefer one helper with N callers over N copies of a condition, so a missed site is
 a visible absent call rather than a subtly different copy.
 3. Assert the wiring structurally (does the loop consult the helper at every site?)
 separately from the helper's logic. Those are two different failure modes and the
 unit tests only cover the second.
 4. A feature is not verified until it has been OBSERVED doing its job in production.
 My own words two rounds ago: an unverified fix is worse than an unimplemented one,
 because it looks like progress.
