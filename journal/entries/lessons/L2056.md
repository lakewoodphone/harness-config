**L2056 · mesh-run -Node does not run the prompt on that node - it runs it locally**

**L · `mesh-run -Node <node> -Prompt <p>` does not run `<p>` on `<node>` — it runs it locally, and the flag only sets where that local child will dispatch**

MEASURED 2026-09-18 on ZABZ-YOGA while trying to prove the fifth node could take work.

WHAT I DID: `node packages/plugin-remote-fanout/bin/mesh-run.mjs -Node lakewooechsmini -Prompt 'Run
hostname and reply MACNODE-OK host=<hostname>'`, expecting the command to run on the mac mini.

WHAT CAME BACK: `exitCode: 0`, `timedOut: false`, `ms: 15258`, and the child's own answer —
**`MACNODE-OK host=zabz-yoga`**. The laptop. The dispatch had not left the machine.

WHY, from the source: `bin/mesh-run.mjs:355` calls `sshRunLocal(dshBin, options.prompt, env, …)`, and
`sshRunLocal` (`:437`) does `spawn(process.execPath, [bin, '--profile', 'mesh', 'headless', prompt])` —
a LOCAL dsh turn. The `-Node` value travels only as environment (`MESH_TARGET_NODE`, `MESH_NODE_EXE`,
`MESH_DSH_BIN`, `:328-339`), so the local child's OWN dispatch is aimed at that node. The ssh calls in
this script are the broker request and the reparse-point traversal probe; they are not the run.

WHY IT IS A FOOTGUN AND NOT MERELY MY ERROR: the script is named `mesh-run`, its flag is `-Node`, and
its run log prints `node`, `alias`, `invocation` and `targetVerified` — four signals that all say the
work is going to that node. The one thing that says otherwise is the child's answer. A reader who
skims the log concludes the mac mini ran the turn; only the hostname contradicts it.

THE GOOD NEWS, AND IT MATTERS: **the tool caught it itself.** Its verify phase runs after every run and
scored `ok:false`, `reason: "only 0 MESH-HOST lines for 1 children"`, `outcome: "failed"`, exit 1 —
because it looks for the tokens a real remote child emits. A dispatcher that verifies the CHILD'S OWN
REPORT of where it ran, rather than trusting its own intent, is the pattern that caught the
`laptop-ts`-resolves-to-the-desktop scare on 2026-09-17 too. Keep that phase.

HOW TO USE IT CORRECTLY: give the local child a prompt that asks it to DISPATCH — e.g. "dispatch exactly
one subagent with this prompt: … and report its output" — so that the env-carried target is actually
exercised. A prompt that asks for local shell work tests the dispatcher's machine, which is not what
anyone wants to know.

THE GENERAL RULE: when a tool's name, its flags and its own log can all agree on a target while the work
happens somewhere else, the only trustworthy evidence is the child naming its own host. `109` and `111`
already require a `hostname` in every hop for this reason; this is the same rule one layer up, applied
to the dispatcher itself rather than to the network.
