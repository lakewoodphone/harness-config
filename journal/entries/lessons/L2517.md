**L2517 · Sukkos was a day early in shalom_zmanim.py and the live power automation ran on it**

## The repo's Hebrew calendar had Sukkos a day early, and the live security automation ran on it for weeks

Found 2026-09-24 while computing the Dialpad closure calendar. Two defects, both real, both fixed.

**The bug.** `app/services/shalom_zmanim.py` `is_chag_yom_tov` listed Shmini Atzeret /
Simchat Torah as `(7, 21), (7, 22)` Tishrei, and `is_chol_hamoed` stopped Sukkot Chol HaMoed
at 20 Tishrei. Correct: Sukkot has **five** days of Chol HaMoed (17-21 Tishrei), Shmini Atzeret
is **22**, Simchat Torah is **23** (chutz la'aretz).

**Proof.** `pyluach`: 15 Tishrei 5787 = 2026-09-26, so 17 = Sep 28, 21 = Oct 2, 22 = Oct 3,
23 = Oct 4. Two independent witnesses agree: Dialpad's own LPT holiday list holds "Sukkot II
September 27, 2026" (16 Tishrei) and "Simchat Torah October 4, 2026" (23 Tishrei); and the
owner's Sukkos closure window (closed 25 Sep, reopen 5 Oct) is exactly 14-23 Tishrei.

**The consequence, which is why this mattered.** With the old values the Shelly plug would have
powered Home Assistant and the cameras **down on Fri 2 Oct 2026 (21 Tishrei — an ordinary Chol
HaMoed working day)** and left them **up on Sun 4 Oct 2026 (23 Tishrei, Simchat Torah)** — a
fail-open on Yom Tov, in the code path whose entire job is to not do that. `SHABBAT_AUTOMATION_ENABLED=true`
on `secratary` and the service was active, so this was live, not theoretical.

**Fixed and deployed.** `shalom_zmanim.py` + `tests/test_shalom_zmanim.py` corrected (47 tests
pass locally, 17/17 on the host), the security-program doc's calendar section corrected, the two
files scp'd to `/home/zabz/personal-secretary-mvp` (not `git pull` — that checkout is diverged and
carries uncommitted work), `secretary-api.service` restarted, and `POST /shabbat/program` run to
rewrite the on-device schedule: it reported `deleted: 2` and now carries `[2026-10-03, 2026-10-04]`
with ON at 2026-10-04T20:13 instead of the old wrong block.

**Why nobody caught it.** The wrong dates were consistent across the code, the unit tests and the
runbook, so every internal check agreed with every other one. A test that encodes the same wrong
fact as the code it tests is not a check. The thing that exposed it was an *external* constraint —
a third-party system (Dialpad) holding the real date and the owner stating a closure window that
only fits 14-23 Tishrei.

RULE: for calendar/date logic, cross-check against a **second, independent** source (another
system's data, or a human-stated window), not against your own tests and docs. And when a fix
touches a live safety system, prove it on the running service afterwards — here by importing the
module on the host and printing the computed blocks, not by assuming the copy took effect.
