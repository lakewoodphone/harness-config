**L6202 · Six things learned changing one restriction on a live MDM fleet**

## 2026-10-13 ~22:45Z · ZABZ-TECH · Six things learned changing one restriction on a live MDM fleet

**1. iOS applies the MOST RESTRICTIVE value across installed profiles — so a one-file change can be a
no-op.** `/lockdown` installs `LOCKDOWN_PROFILES = ["layered-kiosk", "layered-kiosk-phase1",
"webtrap", "siri-dns"]` (`nanomdm_client.py:70`). Flipping `allowBluetoothModification` in
`layered-kiosk` alone would have left `layered-kiosk-phase1` holding Bluetooth off, the device
unchanged, and the change looking like it failed. **Before changing any restriction, read
`LOCKDOWN_PROFILES` and change every profile in it that carries the key.**

**2. A profile install does NOT apply while the phone's screen is off — the commands just queue.**
Measured: DRN 2004 had **160 commands sitting in NanoMDM's `enrollment_queue`** and had not drained
them, while DRN 2007 had 1 and had checked in 90 seconds earlier. For 2004 the `/lockdown` endpoint
answered `ok` with *"4 install / 4 remove ok, 0 failed"* and **nothing reached the `commands` table at
all**. 2004 was the first unit through the bench; its screen had been off since the work moved to the
next phone. **`ok` from a lockdown is an enqueue, never an application — and a sleeping device is the
common reason a run looks successful and changes nothing.**

**3. A "current state" query without timestamps mixes history with now, and manufactures a false
failure.** My first pushed-payload check printed the last ten `InstallProfile` commands per device
with no `created_at`; it showed `bluetooth=False` for two units that *had* just been pushed correctly,
because the new rows and the old ones were indistinguishable. Adding `cr.created_at` and asserting on
**the newest** row turned the same data into a clean pass. **Every query meant to answer "what is true
now" must be ordered by, and print, its timestamp.**

**4. iOS's `ErrorChain` is where the answer is; the first line is a symptom.** `MCProfileErrorDomain
1000 "The profile is invalid"` hid `MCPayloadErrorDomain 2002 "The required field Name is missing"` two
entries down — and the runbook attributed that 1000 to "no SIM present", which sent me after the SIM
for a profile that was simply malformed. **Read the whole chain before acting on the headline.**

**5. This repo's `.venv` cannot run `pytest` at all.** It is a **Microsoft Store Python** whose child
processes cannot create a file *or a directory* anywhere: `tempfile` raises
`FileNotFoundError: No usable temporary directory found`, and Playwright dies at
`mkdtemp ... EPERM`. So the honest verification of a code change here is to **call the changed function
and read the result** (`make_waze_layered_kiosk_profile(...)` → `allowBluetoothModification=True`,
verified), and to run the test suite on a Linux node. **`C:\Python313\python.exe` is a normal CPython
3.13 that can write and already has playwright/PIL/requests** — use it for anything that writes.

**6. A pushed mobileconfig carries no prose.** An XML comment cannot contain `--`, and I broke the
profile twice in a row with a comment *about* that rule before dropping comments entirely. The
explanation belongs in a doc and a commit message, not inside the payload iOS has to parse.
