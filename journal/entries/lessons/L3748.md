**L3748 · A mesh child's final report is not in its mailbox - recover it from the child's own session**

**Measured 2026-10-13, a seven-child extraction fleet on ZABZ-TECH.**

Seven mesh children were briefed to read one document tranche each and RETURN a defect register as
their final message. Four arrived whole. Three arrived truncated — 438 B, 2.5 KB and 4 KB where the
child had in fact written 50-69 KB of findings. The child had done the work; the transport lost the
completion frame.

The mailbox is `C:\Users\ezabz\.dsh-mesh-mailboxes\remote-<thread>\outbox.jsonl`, and it holds only
what the child CHOSE to write as messages — usually a short progress line per milestone. The final
report travels in the completion frame and is **not** persisted there. `job_output` does return it
(and spills it to `.dsh\tmp\dsh-spill-*\...job_output.txt` when large), but reading it spends the
parent's context, which is the cost the whole fleet exists to avoid.

**Recovery that works.** The child is a real session in the local store, even though it ran over the
mesh. `node scripts/sessions.mjs list --since 90m --sub` finds it — note that mesh children appear as
`role main` under project `--C-Users-ezabz--` with the title `=== mesh mailbox (read this`, not as
`sub`. Then `show <id> --host local --max-chars 400000 --out <file>` writes the whole report to disk
with zero context cost. Identify which dump is which child by grepping each for a distinctive id from
its own report (`sess-283e3002.md` was the 2026-09-23 tranche because it contained
`pole-horizontal-capacity-vs-tow-load`).

**The fix is in the brief, not the tool.** Every extraction child should be told: *write your report to
this absolute path; do not rely on returning it.* Then the transport cannot lose it and the manager
never pays to collect it. This session re-ran one child purely because its report had been lost, and
recovered three more off the session store by hand.
