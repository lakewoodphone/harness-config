**L1932 · lpt-hub's sync-record schema is closed at the root, so the nearest existing record is not a valid template**

CUSTOMER_CASE_SYNC_RECORD.schema.json is CLOSED at the root (additionalProperties: false). Two things that look
natural and that exist in real records FAIL it: a root-level `issue` block, and references.productionOrder: null
(the schema types productionOrder as an object, so null breaks it).
Measured 2026-09-17: docs/customer-operations/sync-records/sd-card-goldstein-8482104005-2026-09-17.json carries
BOTH and therefore does not validate. Copying the newest record as a template - the obvious move - would have
propagated the defect into a brand new record.
RULE: author a new sync record against the schema's own property list, never against the last file written.
Allowed root keys, exactly: $schema, recordType, version, caseId, sourcePath, customer, device, references,
workflow, referral, operational, pricing, labEscalation, production, updatedAt.
Verify with json.load plus a set-diff against schema["properties"] - jsonschema is NOT installed in the lpt-hub
venv, so there is no one-line validator and the check is manual.
And when a record is real but genuinely unpushable, put the reason in operational.syncHoldReason. The schema
documents that field precisely so a deliberately-held case is not counted as an unexplained sync gap and chased
for hours. Used exactly that way on this case.
