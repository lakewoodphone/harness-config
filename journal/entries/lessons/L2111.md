**Lesson (2026-09-17, Goldstein microSD, second pass): four cheap checks that together separate "dead
card" from "formatted card" — and one of them is pure arithmetic that needs no hardware at all.**
Companion to L2109, which covers the basic signature. These are the tests that survived an adversarial
review of my own verdict.

**1. Count DISTINCT blocks, never "is there a filesystem".**
`blkid`/`fsstat` returning nothing tells you only that you cannot address the medium — "empty is a
refusal". The measurement that discriminates is *how many distinct 512-byte blocks the device
returns*: 1 of 248,320 here. Do it on the image in Python (a `Counter` of sha256 per 512 bytes) and
also record the smallest repeating period. A formatted card still has hundreds of thousands of
*different* blocks; this had one.

**2. RAW SCSI, with the kernel bypassed — `sg_raw -b` and `sg_dd`, not `dd`.**
`sg_raw` without `-b` prints hex to **stderr** and nothing to stdout, so `sg_raw -r 512 … | sha256sum`
hashes *empty input* and returns `e3b0c44298fc1c14…` — the SHA-256 of nothing, which looks like a real
result and is not. With `-b`, READ(10) CDBs (`28 00 <LBA:4> 00 00 <len:2> 00`) at explicit LBAs prove
the device itself honours the address field. Here every LBA returned the identical block, which removes
the block layer, the page cache, and any filesystem abstraction from the argument in one step.

**3. Read PAST the reported end — the test that identifies a fake.**
A canned-response (fake/counterfeit) controller answers *any* address. A device with real range
enforcement rejects what it does not have. Ours returned `Check Condition / Illegal Request` for LBA
248320, 250000, 300000, 500000, 1000000, 4000000 — so it is not a canned responder, and the "fake
card" hypothesis died here. Always run this before concluding anything from uniform data.

**4. THE ARITHMETIC TEST — free, no hardware, and it is the strongest single piece of evidence.**
A valid **SDHC/SDXC (CSD v2.00)** user capacity is always `(C_SIZE+1) × 512 KiB`, i.e. an exact multiple
of **524,288 bytes**. Divide the reported capacity by 524,288:
- integer → could be a genuine modern card;
- **not an integer → it cannot be a real modern-card geometry at all**, so the controller is serving a
 default, not a measurement.

Ours: `127,139,840 / 524,288 = 242.5` — **not an integer**. And it *is* exactly a legacy **SDSC (v1.0)**
geometry (`C_SIZE=484, C_SIZE_MULT=7, READ_BL_LEN=9` → 485 × 512 × 512). A modern card presenting a
legacy-SDSC geometry is precisely the "boot-mode shadow of a card". One division, no tools, and it beats
any amount of arguing from symptoms.

**5. The power-cycle drift test — what the replayed block tells you.**
Capture the same LBA across several USB port power-cycles (`echo 0 > /sys/bus/usb/devices/<dev>/authorized`,
sleep, `echo 1`) and measure Hamming distance between captures. Across four cycles ours drifted
**121–150 bytes, 140–173 bit errors (3.4–4.2 %)**, while the 32-byte `55 AA` prefix stayed byte-identical
and the capacity never moved. A canned buffer changes completely; media changes according to what was
written; a **fixed internal buffer carrying volatile state** drifts by a few percent while its structural
prefix holds. That is a third category, and it tells you nothing about the NAND in either direction —
which is exactly why it is not evidence of recoverability.

**Cross-checks worth doing before blaming a card:** isolate the reader — **and do it with a KNOWN-GOOD
card in the SAME reader, not by argument.** This is the sharpest lesson of the whole case: a
Genesys `05e3:0749` is a **GL3224-class USB3 card-reader controller with its own 8051 CPU and firmware**
that presents a SCSI LUN, and **it is capable of fabricating a response itself**. So "the same reader
read other cards before" does not exonerate it, and neither does a correct 0 B on the empty slot. Put a
known-good card in the same slot: if it reads normally the bridge is cleared; if it *also* returns one
repeated block, the bridge is the fault and the customer's card may be perfectly fine. One card, one
minute, and it is the difference between "dead card" and "dead reader". A second, different-model reader
is the backup test.

Also confirm the bridge exposes no card identity (VPD pages 0x00/0x80/0x83 only, `REPORT LUNS`
unsupported, vendor opcode 0xE1 rejected → CID/CSD need a **native** SD host, which is what
`lpt-hub/scripts/data-recovery/sd_capture.sh` is for). Note that **RTS5129/RTS5139/RTS5179-based USB
readers are real MMC hosts** — they appear as `/dev/mmcblkX`, not a SCSI LUN, and expose
`cid`/`csd`/`scr`/`manfid`/`serial`/`date` in sysfs; a ~$10 reader of that class is the cheap way to get
identity from a card whose data path is dead, because **CID is served from the controller register in
identification mode and does not traverse the NAND**. And never read health from a USB bridge —
`smartctl` said "SMART Health Status: OK" on a device whose media is unaddressable.

**Never send an unknown vendor opcode to a customer's card.** There is no way to know a vendor command is
read-only before it executes, and one of them could be a write/format primitive. That is a line, not a
judgement call. Same for the "obvious" fixes: SD Card Formatter's size adjustment, MPTool-class vendor
tools, and any capacity restore all **write fresh translation structures**, which is exactly what severs
the mapping a lab needs.
