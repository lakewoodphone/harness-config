**L10238 · A config that restates an upstream surface is an assumption: 0.2.1 renamed the connection row's injection (webRuntime->webStartup) and dropped the {{cwd}} prompt token, and both failed live after a GO preflight**

MEASURED 2026-10-19 on ZABZ-TECH, on the owner's machine, AFTER a preflight that said GO on all 7 blocking guards,
a compose smoke test that said 421 rows, and a patch audit that said clean. The upgrade was fine; three of OUR
ASSUMPTIONS about upstream were not, and each failed in his hands rather than in a guard.

THE CLASS: **our config restates an upstream surface, and nothing checks the restatement against the candidate.**
Two instances, both one-token fixes, both total outages of a feature:

1. `ctx.webRuntime` -> `ctx.webStartup`. Our web patch restated the `connection` row config with
 `trustedHosts: !!js ctx.webRuntime.trustedHosts`. 0.2.0's default row injects [webRuntime]; 0.2.1's injects
 [webStartup] (both read from `--dump-default-config`). The cordis loader throws "cannot get property
 <name> without inject", `dsh-client-connection` is a REQUIRED plugin, so it did not activate and the client UI
 reported 20 entries "pending (waiting for service: remoteAccess)".
2. `{{cwd}}`. Preset persona suffix said `Your working directory is {{cwd}}.` 0.2.1 registers only `provider` and
 `model`; every turn died with `unknown prompt variable "{{cwd}}" in section "deployment:persona-suffix"`.

WHY NO GATE COULD SEE THEM. `patch-effect` and G2 compare our patch's config VALUES; a `!!js` expression is
compared as source text against our own intent, never evaluated against the candidate's injection surface. And
nothing anywhere looked at prompt tokens. `SPEC.md` B11 predicted the shape ("a patch replaces the row's whole
config, so a new upstream default is swallowed silently") — this is its expression-level twin.

THE CONTROL NOW: `dsh-update/tools/config-assumptions.mjs`. For a given engine root and config home it parses the
candidate's own `--dump-default-config`, then fails on (A) any `ctx.<svc>` in our `!!js` expressions whose row does
not inject `<svc>` in that candidate, and (B) any `{{token}}` outside the registered set. It prints file:line, the
row, and what the row actually injects. Proven both ways the same night: PASS against 0.2.1 after the fix, and
against 0.2.0 it FAILS naming `cordis.patch.yml:68 row "connection" ctx.webStartup`. Run it after every install
(DELIVERY.md §8) before declaring the upgrade done.

TWO SUPPORTING LESSONS, both about *how* I was misled:
- **A boot is not a boot test.** A spare-port boot of the new engine produced an empty error log; loading the
 CLIENT PAGE against the same tree produced the activation failure. The client composition happens on the page
 request. Any "it boots clean" claim from a server-only start is worth nothing.
- **A staged home that cannot resolve our own bundles makes every composition gate lie.** `stage-home.mjs` skips
 `node_modules`; the engine then SKIPS an unresolvable bundle silently (exit 0) and the tree lost 11 rows. The
 staged home composed 410 rows vs the live 421, and `patch-effect` reported BREAKS=3 against the candidate that
 were artifacts of the staging. `tools/link-anchors.mjs` recreates both anchors; preflight then went 3/7 -> 7/7.

ALSO: 0.2.1 stopped reading the nested `~/.dsh/.credentials.yaml` shape (2026-09-11). Its error names the two
supported routes; `DEEPSEEK_API_KEY` at user scope is the one that works, and a headless turn is the check.
Processes started before that variable exists keep the old environment — their children keep failing until they
restart, which is why a "fixed" credential can still look broken from a long-lived dispatcher.
