**L3251 · A dedup predicate on a status the pipeline immediately moves the row out of can never fire**

A dedup check whose predicate is a status the same pipeline moves the row OUT of can never fire,
and it fails SILENTLY - it produces duplicates, not errors.

MEASURED 2026-10-05 (secratary, proactive_insights): the error-cluster branch of
`synthesize_insights()` skipped a new insight when one with the same title was
`status = 'pending'`. But `_store_insight()` writes the row 'pending' and a consumer -
app/services/behavioral_rules.py:648 - immediately marks it `'applied', acted_on = 1`. So the
next pass searched a state no row is ever left in. Result: 602 rows titled "Errors in system",
26 in the last 24 h, one about every 45 minutes, EVERY ONE `status='applied'`, `delivered=0`,
priority 1. Noise that was marked applied and never delivered.

THE ONE-QUERY TEST FOR THIS CLASS OF BUG - run the OLD predicate against the real rows:
 SELECT COUNT(*) FROM proactive_insights WHERE title='Errors in system' AND status='pending';
 -> 0, while 602 rows carry that title. A predicate that matches 0 of the rows it is meant to
 suppress is not a strict dedup, it is no dedup.

A/B on an in-memory replica of the real schema - one pre-existing row already marked 'applied',
then three synthesis passes: old predicate -> 4 rows (3 duplicates added); new predicate -> 1 row
(0 added). Build the replica; do not "reason carefully" about a live table.

THE FIX: dedup on "same title, recent" (12 h), status-blind. Age is computed in PYTHON, not in
SQL, because this table holds two timestamp shapes - `2026-10-05 02:05:02` and
`2026-03-23T09:45:53.392555+00:00` - and SQLite compares TEXT lexicographically, so 'T' (0x54) >
' ' (0x20) and the two do not interleave. That is why a window filter built on `strftime()`
silently matches the wrong rows; the module's own `_age_days` docstring says so, and it is right.

Generalisation: when you write a dedup/"already told him" guard, ask which status the row is in by
the time the NEXT pass looks - not which status your own INSERT used. If a consumer mutates the
row you just deduped on, key the guard on the immutable thing (title + time), never on the mutable
status.
