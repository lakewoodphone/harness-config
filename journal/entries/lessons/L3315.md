**L3315 · Dialpad sms_cache: session_id is a codeline, not a conversation**

Measured 2026-10-05 on the authoritative store /home/zabz/personal-secretary-mvp/data/secretary.db on secratary.

WHAT IS TRUE
- dialpad_sms_cache holds ~133,935 rows, 5,287 distinct session_id, but only 3,409 rows where message_id == session_id.
- The live feed writes ONE ROW PER MESSAGE and names the row after the message id. So "latest row per session" is meaningless and silently returns an arbitrary message.
- 124,327 rows have session_id LIKE 'ptf-thread-<phone>' (898 threads) - the deep UI harvest, covering ~2025-12 to 2026-09-20.
- 6,194 rows are 'ui-feed-<base64>' (975 threads), covering 2025-10-19 to 2026-06-19.
- The numeric session_ids are the thin live feed, 2026-04-23 onward, one message per row.

THE ONLY CONVERSATION KEY IS phone_normalized. Group by it, take the newest created_at per phone, and the conversation is unanswered when that newest message is inbound.

THE TRAP INSIDE THAT
The 2026-09-20 bulk ingest duplicated messages and staggered their timestamps in 30-minute steps: message "Are you open now ? No-one answering" is stored 7 times between 18:10 and 20:09; "Hi how can I add more data to my phone plan?" is stored 12 times. 61 of my 84 "unanswered" conversations were that single evening. Timestamps from 2026-09-20 are not trustworthy for ordering anything.

LIVE FEED IS REAL-TIME: fetched_at trails created_at by ~0.7 s on every recent row.

HOW TO USE IT
- Rebuild the unanswered queue with _scratch/dialpad/build_queue.py (read-only, 0.09 s).
- Never order or prioritise by the 2026-09-20 timestamps.
- Never treat a single session_id as a thread.
