**L6206 · A DSH window with no session selected has no composer at all - and that is what 'no text box' was**

A DSH window can end up with NO COMPOSER AT ALL, and the app has exactly one state that looks like that: no session selected. Measured 2026-10-13/14 on ZABZ-YOGA (engine pid 10668, port 3099, dsh 0.2.0-rc.2) while restoring the owner's text box.

WHAT IS TRUE (measured, not inferred)
- With a session selected the composer renders at every width and on both paths - direct 3099 and the dshw-proxy origin 3200. Tested 1582x1086, 1064x1382, 791x543, 700x440, 600x700, 532x691, 430x800, 1200x800, 900x700, 768x700: the composer was fully on screen every time in a fresh client. The missing box is NOT width, NOT layout, NOT the session, NOT the engine.
- The composerless state is "Choose a workspace to start" - an empty/restoring selection. It keeps the last transcript on screen, which is what makes it look like a rendering bug rather than a missing session.
- RECOVERY, both measured: a page reload with a stored session restores the composer, and from the composerless state clicking any session row in the left sidebar brings it back. The sidebar's New session (Ctrl+Alt+N) is reachable with no composer, which is why it is the better instruction. docs/multi-window/WINDOW-BLANK-ISOLATION.md already documented this door for a doubled window.
- WHAT PRECEDED IT: the only client file changed on that machine that night is the hand patch window-blank-isolation to node_modules/@deepseek-ai/dsh-client-ui-workspace/lib/client.js, mtime 21:01:03, whose own notice says a WINDOW RELOAD is required; the web profile patch was rewritten at 21:17 with patchReload: live. The owner's windows had lost the box by 21:50.
- HIS OWN STORAGE proves the doubled state was real: origins 3207 and 3213 both held dsh.sessions.current with the SAME session id, and NO origin in that profile had dsh.sessions.ownedBlank - windows that adopted a shared blank and never recorded owning one. That is exactly the state the patch detaches on the next load.
METHOD THAT WORKED (cheap, reusable): ssh -L 4099:127.0.0.1:3099 -L 4100:127.0.0.1:3200 to the far machine, then drive the live GUI with Playwright and measure the DOM (contenteditable, aria-label "Send message", getBoundingClientRect) at several viewports. A client-side UI fault cannot be read out of log files; measuring the real DOM settles it in one call.
ALSO MEASURED, STILL OPEN: plugin-mobile injects <link href="/dsh-phone-mobile.css"> and that asset 404s on BOTH machines on the direct 3099 path, so the phone layer the plugin promises is absent from every window. Not the cause of this incident; still a real defect.
NOT PROVED: which exact line of the patch stranded those windows. I did not reproduce a composerless state with a stored session present - my reproductions were a client with no selection yet.
