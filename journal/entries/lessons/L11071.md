**L11071 · deepseek-flash has vision - a gateway 400 and a 1x1 pixel both made me say otherwise, and both were my error**

**The owner said V4.1 Flash has vision. I said it did not. He was right; I was wrong, twice, and both
errors were mine — not the model's and not the gateway's.**

Measured direct to `api.deepseek.com` with a 64x64 solid-colour PNG:

```
red -> reply='Red'
blue -> reply='Blue'
yellow -> reply='Yellow'
```

Through the in-process gateway, same kind of image: `reply='Orange\n\nVision confidence: high'`.
And DeepSeek's own 422 on a malformed payload names the struct it expects —
`OpenAICompletionImageUrl` — which is positive proof the image path exists in its API.

**My two errors, recorded so nobody repeats them:**

1. **A 400 seen *through the gateway* was read as "the model cannot do vision".** The gateway was not
 at fault either — with a good payload it forwards the image and the model answers correctly. A
 rejection on one path is not a capability verdict on the model. Isolate the variable before
 concluding anything about a vendor.
2. **A 1x1 pixel image is too weak a test to prove anything.** It returns an **empty string, not an
 error**, because this model spends completion tokens on reasoning *before* it answers: at
 `max_tokens=16` the usage was `completion=16, reasoning=16` and the content was `''`. I read that
 emptiness as incapacity. Use a real image and a generous `max_tokens` — 512 for a description.

**What it changed:** `sms_media.analyze_mms_image` and `browser_vision._get_vision_llm` now try
DeepSeek first. Verified with the real functions, not a reconstruction — the MMS path described a
green square and a blue square in prose, and browser vision reported `selected arm: call_deepseek`,
`reply: 'Yellow.'`.

**Why it mattered operationally:** MMS vision had **no working arm at all**. Its two arms were
DeepInfra (no key ever) and Google (key revoked — a direct `generateContent` answers *"API key not
valid"*, and every Google row after ~14:19Z carries 0 prompt tokens, which is what a failed call looks
like). A customer texting a photo of a damaged device was getting no description.

**The modality line to remember:** DeepSeek serves text **and vision**. It does not serve audio — so
`whisper-1` (OpenAI, 226 transcriptions in 7 days) is still a real dependency, and that is the only
key worth keeping beyond DeepSeek itself.
