**L1841 · Events are not states: I said HA had never seen a code entry, and it had - 74 of them**

I claimed in this session that Home Assistant has no record of a code ever being entered, and used it to conclude the owner rule could not be implemented. THAT WAS WRONG, and the reason is worth more than the claim. The keypad and RFID reader arrive as ESPHome BUS EVENTS - esphome.access_control_keypad_entry (53 occurrences, last 2026-09-14 03:19:52Z) and esphome.access_control_rfid_entry (21, last 2026-09-15 19:54:39Z). Bus events are not entity states, so they never appear in /api/history/period and my state-only measurement could not see them. automation.phoenix_access_control_master_presence (on) matches the code and writes both a rolling input_text and a DURABLE Logbook entry, giving 76 attributable rows from 2026-09-05 14:57:57Z to 2026-09-15 19:54:39Z, e.g. Owner Access at Interior. LESSON: before concluding that a system cannot see something, check the event bus and the logbook, not just the state history. This is the second confident wrong number of the session; both came from measuring the wrong surface rather than from bad arithmetic. CODE-ENTRY DEFECTS found at the same time: the event payload carries door_name plus code or tag_uid but NO identity, so authorization must match the code against the role table. The wife tag 9994885 logs as Owner Access, indistinguishable from the owner (access_control.yaml:163,171). Klein and Montrose can never match at all - the role template (:56-73) omits both, so their tags fall through to Unknown RFID tag (:582) AND count toward lockout (:593), meaning legitimate people are treated as intruders. Montrose has no working credential: the PIN helper holds the literal string unknown. Wife and tenant are offered in the UI but rejected as invalid (:713). 17 slots are wired (11 PIN, 6 tag); guest_pin_1 (set, enabled) and family_pin (set) are referenced by nothing; 16 of the 76 log rows came from a code that is no longer any role PIN, i.e. an orphan code that still grants access. Lockout works and was verified firing on 2026-09-09 00:47:40Z (counter to 5, cleared 120s later), but the threshold uses == not >=, attempts while latched are not counted or extended (:227), and the counter lacks restore: true so a restart clears it. binary_sensor.security_hub_status and sensor.security_hub_* mean the Security Hub offline/recovery/reboot alerts are enabled but can NEVER fire - the dead-man alarm does not exist either. 86 of 155 automations are unavailable (the whole old access_control_* generation plus 43 keymaster_*).
