**L3103 · …1594 is NOT the owner's phone - it is a monitored inbox, and a delivered text there is a silent failure**

THE RULE, stated once so it is never rediscovered: **…1594 is NOT the owner's phone.** It is an inbox that only the secretary monitors. The owner has said this repeatedly and he NEVER sees texts sent there. Outbound owner texts go to **OWNER_NOTIFY_NUMBER (…7895)**. Twilio will happily report "delivered" to …1594 - the failure is completely silent, which is exactly why it keeps recurring.

THE TRAP: `.env` holds three owner-ish numbers side by side, and the WRONG one is named "OWNER_PHONE_NUMBER":
 OWNER_PHONE_NUMBER=…1594 <- monitored inbox. NOT him.
 OWNER_NOTIFY_NUMBER=…7895 <- where he actually reads. USE THIS.
 OWNER_ALT_PHONE_NUMBERS=…7895
 FAMILY_CHAT_ADMIN_NUMBERS=…7895
Picking the variable whose name looks right ("OWNER_PHONE_NUMBER") is what produces the error. The name is not the semantics. Check what a number IS, not what it is called.

WHAT I DID on 2026-09-29: sent the evening itinerary to …1594 via POST /sms/send. Confirmed "delivered". He saw nothing. His reply: "how many times do i have to tell you i won't see texts to 1594, that's an inbox that only you monitor."

SECOND BUG, same send, and independent of the first: POSTing to /sms/send is an AUTONOMOUS send path, so the owner daily quota (3/day) applies and blocked the corrected resend to …7895 with "Owner SMS quota reached (3/day). The owner has complained about too many texts." But the owner's own ruling of 2026-09-16 says the opposite: *"there's a difference between automated texts and direct requests, the kill switch does not apply to direct requests."* The code agrees - app/sms_service.py line 947 - and the distinction is carried by `direct_owner_request`, which comes from app/direct_request.py's `owner_direct_request(origin)` context manager and is set ONLY by interactive owner entry points (owner_chat, owner_api_action, owner_phone_chat, owner_voice, owner_sms). app/main.py:3528 shows it being set from the verified `is_owner` flag, never from message text. So: **a raw POST to /sms/send cannot send a text the owner asked for if he is already at 3 that day.** The right call is an owner-interactive entry point. Two wrong doors on one message: wrong number AND wrong entry point.

WHAT I CHANGED (2026-09-29): inserted a loud warning block in personal-secretary-mvp/.env immediately above OWNER_PHONE_NUMBER, naming …1594 as a monitored inbox, pointing at OWNER_NOTIFY_NUMBER, and explaining that the failure is silent. The .env is gitignored, so this warning is machine-local - this journal entry is the durable, cross-machine copy.

FIX THAT IS STILL OPEN: the variable is named wrongly for what it holds. `OWNER_PHONE_NUMBER` should not be a number the owner never reads. Renaming it (e.g. SECRETARY_MONITORED_INBOX_NUMBER) and pointing OWNER_PHONE_NUMBER at …7895 would delete the trap at its source - but it touches config across the whole system and must be done deliberately, checking every reader first. Not done, and should not be done as a side effect of this.
