## A hand-merged Core Data store is verified by its ALLOCATOR and its PER-CHAT ORDERING COUNTERS, never by its row counts

The Kramer WhatsApp Business job (kramer case, WO 2026-10-06) shipped on 2026-10-08 as "LANDED", verified by
counting rows on the device: 19,167 messages, 782 chats, 16,857 media files, integrity ok. Every one of those
numbers was true. The customer came back on 2026-10-13 saying *"she sends a message and it shows up way
earlier in her history because it registers in her phone as being sent like a month ago."*

**Two faults, both in the row-level merge we wrote, both invisible to a row count.**

1. **Core Data's object-id allocator was never raised.** `Z_PRIMARYKEY.Z_MAX` is where the next `Z_PK` comes
 from. After the merge it read `WAMessage Z_MAX = 1511` while the store held messages up to `Z_PK` 19,173
 (`WAChatSession 26` vs chats reaching 782; ten entities short). Cause in our own tool:
 `merge-whatsapp-stores.py` ran `UPDATE Z_PRIMARYKEY SET Z_MAX=? WHERE Z_NAME=?` with the **SQL table name**
 (`ZWAMESSAGE`) — and `Z_NAME` holds the Core Data **entity** name (`WAMessage`), so **all eleven bumps
 matched zero rows**. On the phone the allocator then moved 1511 -> 1519, i.e. it handed out ids our imported
 rows already occupy; the store read back off the device has **5 fewer messages** than we injected and
 **3,243 more profile-picture rows**.
 RULE: derive the entity name from `Z_PRIMARYKEY` itself (`'Z' + Z_NAME == table`), never from the table
 name — and after any row-level write assert `MAX(Z_PK) <= Z_PRIMARYKEY.Z_MAX` for every entity.

2. **`ZWACHATSESSION.ZMESSAGECOUNTER` is the app's next-`ZSORT` allocator, and the merge never updated it.**
 `ZWAMESSAGE.ZSORT` is a **per-chat ordinal** and the UI orders a conversation by it (`#Pepperspray` occupies
 ZSORT 1..9,187 for 10,195 messages). Measured on the rows the app wrote itself before the merge —
 separable because they are `Z_PK <= 1510` and ours start at 1511 — `counter == MAX(ZSORT)+1` in **20 of the
 22** chats that had any app row. The merge refreshed `ZLASTMESSAGE`/`ZLASTMESSAGEDATE`/`ZLASTMESSAGETEXT`/
 `ZUNREADCOUNT` and left the counter alone, so **39 chats** number a message sent afterwards *inside* the
 history: `That Jewish Family` counter 4 against max ZSORT 67; `Joys Jewish Toys` 5 vs 39; `Vendor listings`
 3 vs 83; `#Pepperspray` 1013 vs 9187. In a conversation going back to August, position 5 of 70 IS "a month
 ago". "Sometimes" is exactly the ten-of-six-hundred pattern.
 RULE: a merge must leave every per-chat ordering counter above that chat's true maximum, and it must be
 proven **by sending a message on the device and watching where it lands** — that is the only verification
 that reaches this fault.

**The transferable sentence:** a row count proves the rows arrived. It says nothing about whether the app can
*use* them. Where the target is a Core Data store, the completion criteria are the PK allocator, the per-chat
ordering counters, and one live message observed landing in the right place.

`lpt-hub/scripts/ios-whatsapp/repair-merged-whatsapp-store.py` (validated on a copy: ten `Z_MAX` raised, 39
counters repaired, `Z_METADATA` unchanged, quick_check ok).
