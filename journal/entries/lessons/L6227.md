**L6227 · A rotating refresh token that is never persisted gives a credential exactly ONE use - and it fails in the worst shape: 'no credential' while the credential file is correct**

**MEASURED 2026-10-14, on the shop's own live API, while provisioning `lpt-web`.** `auth.refresh` **rotates** the refresh token: the token it returns differs from the one sent, the old one is invalidated, and reusing the old one is answered with HTTP 401 - which, because reuse is the signature of a stolen token, **revokes the token family** (after one reuse attempt the freshly issued token was dead too).

**The consequence, in one line: a rotating refresh token that is never persisted gives a credential exactly ONE use.**

**How it bit, twice, in twenty minutes.** (1) The provisioning script verified the token by refreshing it *before* storing it - so the value written into the authority's environment was already spent, and the very next command reported `NO CREDENTIAL` against an env file that looked perfectly correct. (2) Even stored fresh, the CLI's `web_helper` mints an access token on every invocation and never writes the rotated refresh token back, so call one succeeded (`payNotices.listPending`, identity id 300 MANAGER) and call two failed with `Invalid refresh token`.

**The fix, and it is a rule for anything here that holds a refresh token:** after **every** refresh, persist the newly returned token atomically before returning (0600); **never verify a token by using it** - store first, check afterwards, and tolerate the rotation the check causes; and **prefer the access token for its 15-minute life** rather than refreshing per invocation, which turns a working credential into a single-use one even when the write-back exists.

**Why this is a lesson and not an incident:** the failure mode is *the worst shape* - the credential file is right, the key name is right, the length is right, and the system says "no credential". An operator reading that message looks at the wrong thing. Anything that can report "unauthorised" while the evidence of authorisation is present deserves a test that exercises it **twice in a row**; a single successful call is not proof that a credential works, it is proof that it worked once.
