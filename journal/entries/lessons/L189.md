**L189 · A PowerShell script with any non-ASCII byte needs a UTF-8 BOM, or the edition that runs it will not parse it**

**2026-09-14 · found by converging the office desktop with `powershell.exe` rather than `pwsh`.**

```
At C:\Users\ezabz\code\harness-config\scripts\autosync.ps1:225 char:53
+ else { "apply did NOT converge <mojibake> a second run stil ...
Unexpected token 'a' in expression or statement.
```

The file is UTF-8 **with no BOM**. Windows PowerShell 5.1 decodes a BOM-less file as ANSI, so every
em-dash inside a string literal mangles the line it sits on and the script does not parse at all —
while PowerShell 7 (which defaults to UTF-8) reads the same bytes happily. Measured with the
language parser in both editions on the same file: **5 parse errors without the BOM, 0 with it.**

Five scripts carried non-ASCII and no BOM: `multi-window/dshw.ps1` (1,416 bytes of it, in the
banner), `scripts/autosync.ps1` (46), `scripts/Install-Autosync.ps1` (9), `scripts/serve-phone.ps1`
(14), `scripts/Install-DshArchive.ps1` (3). All five now carry a BOM; all five parse with 0 errors
under 5.1 and 7, and the desktop's sync then converged cleanly under 5.1 (`[clean] at 670261e`).

**Why this matters more than it looks.** The file that broke is the **sync mechanism itself** — so a
machine whose task ran `powershell.exe` could not pull the fix for the file that would not parse: a
deadlock that only an out-of-band `git pull` breaks, which is exactly what I had to do. And the
failure is silent to anyone reading the machine's own status record, because the record is written
by the script that died.

**Rule.** A `.ps1` containing any non-ASCII byte **must** carry a UTF-8 BOM, because which PowerShell
edition runs it is not the author's choice. A BOM rather than stripping the characters, because most
of those bytes are deliberate box-drawing and prose. The `.sh` twins are unaffected — UTF-8 is the
default there — which is why this is a Windows-edition trap and not an encoding problem in general.
