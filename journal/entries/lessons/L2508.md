**L2508 · A detector must be run against a known-GOOD input, or it reports crises that do not exist**

## A detector must be run against a known-GOOD input too, or it reports crises that do not exist

MEASURED 2026-09-23 (ZABZ-TECH), first end-to-end run of the new `dsh-update` pipeline.

`analyze 0.1.5-rc.3` returned `verdict: BREAKS`, `counts BREAKS=2`, with two findings whose
`evidenceTier` was `AUTHORITATIVE` and whose `why` read: *"the row exists and the engine starts, so
nothing errors -- but our override is applied to nothing, and the setting we depend on silently
reverts to upstream default."* It named a real file and a real line
(`~/.dsh/profiles/web/cordis.patch.yml:248`).

THE CLAIM WAS FALSE. Checked by hand before anything was reported:

```
candidate 0.1.5-rc.3: present=true disabled=true patchedBy=false
baseline 0.1.5-rc.1: present=true disabled=true patchedBy=false
candidate exit=0 rows=163 | baseline exit=0 rows=163
row ids added: (none) | row ids removed: (none)
```

All four of our patch targets are identical across the two versions. `0.1.5-rc.3` breaks nothing.
The candidate was then confirmed bootable: a real headless agent turn from an isolated `DSH_HOME`
returned `exit=0`, `OK`, empty stderr, 22.2 s.

THE MECHANISM OF THE ERROR, because it generalises: the detector asserted on the `patched by`
comment the engine prints next to a patched row. That comment is emitted only for certain patch
shapes. A patch that sets only `disabled: true` applies perfectly and prints **no** annotation -- so
the detector read "no annotation" as "the patch stopped applying". The signal was incomplete, and
the code treated its absence as evidence of a fault. Two independent findings were emitted for one
cause, and the count was reported as `BREAKS=2`.

WHY THE TEST SUITE DID NOT CATCH IT: the regression fixtures were all deliberately-broken inputs
proving the detector *fires*. Nothing asserted that the detector **stays silent on a healthy
pair**. A suite of only-negative fixtures cannot distinguish a working detector from one that
always answers "broken".

WHAT TO DO INSTEAD, and this is the durable rule:
- Every detector needs a **known-good** fixture asserting **zero** findings, alongside the
 known-bad ones. The false-positive test is the one that matters, because it is the one whose
 absence produces a crisis report.
- Prefer an assertion on an **effect** over an assertion on a **report of the effect**. Here: compare
 the composed row against `--dump-default-config` (the same tree without our layer) and assert the
 patch's own `disabled`/`config` values are what the composed row actually carries. Never assert on
 an explanatory comment.
- When a check cannot be made, say so (`unverified`) rather than inferring a fault from absence.
 Absence of evidence is not evidence of a fault, just as it is not evidence of health.
- Before reporting any BREAKS-class finding to the owner, reproduce it by hand against the real
 artifact. This is LESSONS L51 / PAIN P22 again in a new costume.
