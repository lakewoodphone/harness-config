**L1594 · Landing an auth guard silently breaks every test written before it**

2026-09-15, phone-and-tech-full. Cherry-picking five guard commits (procedure -> managerProcedure/protectedProcedure on 5 routers) turned 19 previously-passing tests red, and nothing in the guard workstream noticed because the FULL backend suite was never run. terminal.error-handling.test.ts drove the router with createCaller({}) because the router had no guard when it was written. ui.test.ts drove CUSTOMER contexts into a procedure that is now protectedProcedure, which explicitly throws FORBIDDEN for role CUSTOMER - so the change also silently removed a capability the router was designed to have. Rule: a guard change is never a one-file change; run the whole suite and diff the failure set against a clean baseline worktree before calling it verified. Baseline-vs-branch set diff is the only way to tell your reds from the pre-existing ones.
