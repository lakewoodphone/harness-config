**L1939 · Diagnosing a page that will not load: six cheap measurements in order, and a 200 with a zero-byte body is a refusal**

A page that will not load is usually diagnosed by guesswork. This is the sequence that actually settled it, and it
took six cheap measurements rather than one expensive assumption. Use it in this order next time:
1. ASK A REAL BROWSER ENGINE ON THE AFFECTED MACHINE, and read the DOM, not the screen. Playwright's Chromium
 navigated the URL, the network log showed [200], and `document.title` was "" with `document.body.innerHTML`
 of length 0. That single fact kills "your browser is broken", "it is an extension" and "you pasted it wrong"
 at once, and it takes one call.
2. CURL THE SAME URL FROM TWO DIFFERENT HOSTS AND TWO DIFFERENT OSES. Windows/schannel and Linux/OpenSSL both
 returning `http_code=200 size_download=0` rules out a local TLS or client-stack quirk.
3. DUMP THE FULL HEADERS, not just the status. `curl -D -` showed the ORIGIN's own headers (Set-Cookie PHPSESSID,
 X-Powered-By PleskLin, cf-cache-status DYNAMIC, CF-RAY ...-EWR). That said the request reaches the edge and the
 edge reaches the origin and ONLY THE BODY IS MISSING - which is a completely different problem from "blocked",
 and it is the header dump, not the status code, that says so.
4. RULE OUT THE USUAL SUSPECTS IN ONE PASS: DNS from the router vs 8.8.8.8 vs 1.1.1.1, the hosts file, WinHTTP and
 per-user proxy settings, and the root certificate store for a TLS-intercepting CA. All four are one command each
 and each one, if positive, is the whole answer.
5. TEST A DIFFERENT PAGE ON THE SAME SITE AND A CONTROL SITE. A different page on the same site failing while
 example.com and amazon.com return megabytes proves it is the site's policy toward this client, not the network
 being down.
6. TEST FROM A MACHINE OUTSIDE THE AFFECTED NETWORKS - and test MORE THAN ONE. Two datacenter boxes gave opposite
 answers (lpt-apps 200 with the full page, Hetzner a 403 bot block). One outside test would have produced a
 confident wrong conclusion; the pair showed it is PER-IP policy.
COROLLARY RULE: a 200 with a zero-length body is a REFUSAL, not an empty page and not a success. It is the single
most misleading response a monitor can check, and it is worth grepping for `size_download=0` alongside status codes
in any health check that only asserts 200.
