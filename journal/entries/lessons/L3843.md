**L3843 · Identifying an unlabelled Kyocera E4610 on the bench (and the case-index trap it exposed)**

Identifying an unlabelled Kyocera E4610 on the bench, without guessing. Measured 2026-10-18 on ZABZ-TECH,
adb serial 616062485, and it ends with a case file fix that generalises.

**The identifiers, and which command actually produces them on this build.**
- Serial: `getprop ro.serialno` = the same 9-digit number `adb devices` prints (616062485).
- MEID: `adb shell service call iphonesubinfo 1` → parcel of UTF-16 chars → 99000616062485.
- IMEI: `service call iphonesubinfo 4` → **990006160624853** = MEID + Luhn check digit 3. That is the number the
 shop records; compute the Luhn digit yourself and check it against the parcel, do not paste the MEID as an IMEI.
- `dumpsys iphonesubinfo` printed **nothing at all** on Android 7.1.1 (1.406VZ.52.a), and `dumpsys telephony.registry`
 matched none of mLine1Number/mIccId/mDeviceId. The empty output is not a failure — the service-call codes are the
 only path here.
- `READ_SMS` and `READ_CALL_LOG` are **denied to shell (uid 2000)** on retail 7.1.1: `content query` on
 content://sms and content://call_log throws SecurityException. So SMS/call history is not the identification path
 on this family of device, no matter how much you want it.
- Contacts **are** readable: `content query --uri content://com.android.contacts/data/phones`. And
 `content://com.android.contacts/contacts --projection display_name:times_contacted:last_time_contacted
 --sort "times_contacted DESC"` ranks the owner's own people — on a child's handset the parent lands in the top
 five (here MOMMY, 1391 calls). Detail level that matters: `last_time_contacted` is epoch **milliseconds** and is
 the cheapest way to date a handset's last real use without touching a single file.
- `content://telephony/siminfo` keeps one row per SIM **ever inserted**, with `icc_id` and sometimes `number=`:
 11 rows here spanning Verizon, Cellular Israel x3, T-Mobile UK(234/20), AT&T — a travel history, and a fast
 tell that the phone has been in more than one household/country.
- `pm list packages -3` returning nothing (140 packages, all stock) + no Google account + a stock Verizon build =
 this handset has never had a sideloaded app. Do not read "no apps" as "wiped": /sdcard still held 2023-2025
 photos, 48 Music folders and a contacts VCF.
- `adb shell find /sdcard -newermt "YYYY-MM-DD" -type f` dates last use. Here: nothing since 2026-03-01, and the
 newest artefact was a VCF written 2026-02-16 00:05:56 — which is why a "dead since February, dropped off in
 September" story held together.

**The lookup failure that would have wasted the session.** `lpt ticket 7324473805` returns **0 candidates in both
stores** and a full-text search of orders for the number, the serial and the IMEI returns **0 rows each**. That is
not evidence the customer does not exist — it is evidence no work order was ever created. The record lived in
`lpt-hub/docs/customer-operations/cases/ring-unknown-7324473805-2026-09-24.md` and `lptcase find "447-3805"`
answers in 74 ms. Case-first, production-second; production only ever holds jobs somebody opened.

**The generalisable fix: a case that names another customer's order gets that order as its own identity.**
With `work_order: ""` in front matter, the extractor promotes every `WO\d{6,}` token in the prose to the case's
identity surface (that is ledger item 60/219 behaviour, and it is deliberate). This case says "Not it: the other
Kyocera in the shop is WO2608310005 … do not hand this customer that device" — so `lptcase show` reported
`wo WO2608310005`, i.e. the index was pointing this customer's case at rabbi shereshevsky's device. That is exactly
the wrong-handed-phone failure the warning exists to prevent.
Fix, verified: add `work_orders_mentioned: [WO2608310005]` to the front matter. The mention stays searchable, it can
never become the case's own key, and the warning honestly becomes `other-work-orders-mentioned-not-owned:1`.
After: `show` prints no `wo` line at all. **Any case whose prose says "not this order" needs that line**, or the
index will re-inject the number the sentence exists to exclude.

**And the placement trap.** The commit landed on branch `shift/lpt-sync-520-dup-phone-nonstructural`, which is
107 ahead / 147 behind `origin/main`, and `origin/main` still carries the OLD version of this case (device
`unknown`, updated 2026-10-05). So "pushed" is true and "visible to the drift verifier, which reads main" is not.
Pushing a branch is not landing case work; say which branch, and say when main still holds the stale copy.
