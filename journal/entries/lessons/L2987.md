## CORRECTION to P2733's root cause: the sync-time guard was NOT IN HEAD, so "the guard trusted a transient dshInstall" is NOT established as what caused the live incident

MEASURED 2026-09-28 (ZABZ-TECH) by the workstream that hardened the guard. `git status` on
`harness-config` shows:
```
 M scripts/sync.py (modified in the working tree, uncommitted)
?? scripts/check-version-coupled-config.py (untracked -- it exists ONLY in the working tree)
```
So at committed HEAD there is **no version precondition in `sync.py` and no checker at all**. The
15-minute task applies **`git archive HEAD`** through `sync.py` (`autosync.ps1:464-483`), i.e. it runs
the COMMITTED `sync.py`, which has no guard to consult.

WHY THIS MATTERS: P2733 asserted, as an established finding, that the live config was overwritten
because the guard resolved its engine root from a transient `dshInstall` and therefore passed. **That
cannot be right if HEAD's `sync.py` has no guard in it at all.** The mechanism I published was a
plausible reconstruction, not a measured one, and I labelled it too confidently. The honest statement
is: the live config reached 0.1.7 names at 15:32 while the 0.1.5 engine ran, and **the path by which the
timer applied it is NOT established** -- in particular it is not established that the guard was involved,
because the version of `sync.py` the timer executes contains no guard.

WHAT IS STILL TRUE AND STILL WORTH FIXING, independently of that:
 * the guard, once committed, WOULD have had the `dshInstall` weakness -- that is now fixed and verified
 (the running process wins; the DANGEROUS STATE banner names both engines; exit 2 on ambiguity;
 fail-closed on its own errors so only the two coupled steps skip);
 * the switch's rollback genuinely did not restore the config it had written, and is being reworked;
 * the config change reached the live home at all while the old engine ran, which is the failure that
 matters and which is now guarded from at least two directions.

A SECOND CONSEQUENCE, and it is a live footgun: **an uncommitted guard does not protect anything.** The
timer runs HEAD, so every fix in `scripts/` and in the config is inert until it is COMMITTED. That cuts
both ways: it is why the incident could happen, and it is also the only reason the version-coupled config
has not been re-applied since the restore. Whoever integrates must know that the safety story currently
depends on the working tree staying dirty, which is not a property anyone should rely on.

ALSO RECORDED FROM THE SAME WORKSTREAM: another session is writing in this repo concurrently
(`scripts/wake/fix-integration-push-rule.py` appeared mid-session), and two engines on different install
roots now make the checker exit 2, so while another engine is up the timer will report both coupled steps
SKIPPED each tick rather than picking one. That is the intended fail-closed behaviour, and its cost is
stated rather than hidden.

LESSON, the fourth instance today of the same error: **I published a reconstruction as a finding.** The
guard's weakness was real and independently worth fixing; whether it CAUSED this incident is a different
claim, and I did not have the evidence for it. Say what was observed and what was inferred, separately.
