**L3811 · http=000 is not 'no answer': /v1/models delivered the full correct body and never closed the transfer**

A client that reports `http=000` has not necessarily been told "no answer" — on this estate it was handed the complete correct body and the transfer never ended.

MEASURED 2026-10-14 ~12:40Z on `secratary-cloud`, `company-api` (up, restarted 12:33:09Z, `active`, `NRestarts=0`, 51 threads, RSS ~1.94 GB):

 curl -s -o /tmp/m.json -w "http=%{http_code} t=%{time_total} bytes=%{size_download}\n" \
 --max-time 60 http://127.0.0.1:8002/v1/models
 -> http=000 t=60.002496 bytes=0

and then, in the file that curl reported as empty:

 {"object":"list","secretary_catalog_version":1,"default_model":"secretary-auto",
 "data":[{"id":"secretary-auto","object":"model","created":1791963104,
 "owned_by":"personal-secretary","description":"Chea... }

So the endpoint **computed and delivered the full, correct catalogue** and the response **never completed** — hence `000`, hence `bytes=0`, hence every deadline-based check calling it down. Narrowed, same minute: `Connection: close` → still `000` at 20 s (not a keep-alive artefact); `HEAD` → **405 in 0.0019 s**; no response headers within 15 s; and for contrast `/health` 200 at 2.0 s, `/docs` 200 at 0.0009 s, `/openapi.json` 200 at 0.128 s. **I could not isolate why it hangs, and am recording that rather than guessing.**

**Why this matters beyond one endpoint.** The standing instruction on this estate is to resolve AI models from the gateway's own catalogue — `GET $SECRETARY_API_BASE/v1/models` — precisely so that model ids are never hardcoded. **A client with a deadline sees this endpoint as unreachable and falls back**, silently: the fallback produces plausible text, which is the exact failure that quietly broke every live AI call in `personality-system` for a week. So a catalogue that answers slowly and never closes is worse than one that is honestly down.

**The general rule, and it is the fifth instance of this shape in one session:** *"no answer" and "an answer that never closed" are different sentences and must never be the same one.* A deadline probe measures **completion**, not **provision**. Before reporting an endpoint as down, check whether the body arrived — `-o` to a file and `size_download` disagree here, and only one of them is telling the truth about whether the data existed.

**The four earlier instances, for the pattern:** a search predicate that matched the *denial* (`L3796`); a rolling window that straddled two timestamp formats and covered an extra day (`L3801`); a measurement split on a file mtime rather than when the running process loaded the code (`L3803`); and a renumbering rule resting on a rewrite timestamp (`L3806`). **Every one was a number that looked right and a predicate nobody read.**
