**L1981 · A credential search that filters by file extension will miss the credential store - and a credential row on the owner queue is stale within hours**

MEASURED 2026-09-18 02:5xZ on the authority. Owner queue row #74 asked the owner for a Cloudflare API token because "the token that did the migration was never stored on any machine". He answered "you already have a few", and he was right: ~/.secrets/cloudflare-api-token has existed since 2026-09-16 16:59Z, mode 600.

THE TRAP, exactly: the original sweep searched for files matching .env*, *.json, *.toml and *.txt. The credential store is an EXTENSIONLESS file in a dot-directory, so the sweep walked past it and the row was filed against a false premise. It then sat on the owner's queue for two days, and I re-asked him for it tonight after re-running the same shape of search on the authority.

RULE: before asking the owner for any credential, list ~/.secrets/ first and read the token with a real API call. Do not conclude "no credential exists" from a filename-pattern search. Concretely: ls -l ~/.secrets/ ; curl -s -H "Authorization: Bearer $(cat ~/.secrets/<name>)" <verify endpoint>.

ALSO: a queue row about a missing credential has a shelf life of hours, because the credential gets created while the row is still open. Re-verify every credential row against the filesystem before it is put to him - the row here was falsified the same day it was filed.

WHAT I LEFT IN PLACE: ~/.secrets/cloudflare.env (mode 600) exporting CLOUDFLARE_API_TOKEN, CLOUDFLARE_ACCOUNT_ID (3fe00f424ec43810af16b55df54200a3) and both zone ids, verified by calling the Pages API through it. The token covers Pages:Edit, Zone DNS:Edit and R2:Edit and is NOT a master key (accounts/{id}/members -> 403).
