**L2526 · Search for the convention, not the artifact - and re-run a generator from the branch you committed it to**

## Searching for the artifact you want misses the convention that makes it — search how the existing ones are made

Measured 2026-09-24 on ZABZ-TECH, building the Sukkos closure door sign.

The owner said "the same setup as our other signs". I had already built a sign and looked for "our
other signs" by searching for signage: a `store-signage` folder, files matching
`sign|flyer|poster|door`, a `signs` directory in the repos. Found nothing, invented a folder
(`lpt-hub/docs/operations/store-signage/`), invented a toolchain (HTML rendered by headless Chrome),
and shipped it. It was wrong in two ways at once: wrong place, and a generator that matches nothing
else in the business.

The other signs were found only by asking a different question — not "where are the signs" but
"how does this business make a sign". One grep for the *verb* (`door sign|signage`) in the docs
returned the registry line that names everything:

 | **Walk-in hours door sign (8.5x11)** | `docs/marketing/assets/walkin-hours-sign.png` + `.pdf`
 (generate via `scripts/make-walkin-hours-sign.py`) |

From there the whole convention is 30 seconds of reading: a PIL script per sign, 2550x3300 at
300 DPI, palette from `docs/marketing/assets/brand-palette.json`, the mascot mark, outputs PNG+PDF
in `docs/marketing/assets/`, and registration in `docs/marketing/google-business-profile-management.md`.
Two siblings already existed (`make-review-sign.py`, `make-walkin-hours-sign.py`).

RULE: when the owner refers to something as established ("our other signs", "the usual way we…"),
the search target is the **convention**, not the object. Look for the generator, the asset folder
and the registry first — a folder named after the noun is the least likely place to find it, and
inventing a convention next to an existing one is worse than having none, because now there are two.
Cost of the wrong guess here: a whole sign designed twice, plus a `SUPERSEDED` banner and a pushed
commit that has to be walked back.

## A committed generated artifact is not evidence the generator works — run it from the branch

Same session, same day. The sign's PNG/PDF were committed to a branch that had been cherry-picked
onto `origin/master`. Re-running `scripts/make-sukkos-closed-sign.py` in a worktree of that branch
produced a **different mark**: the shared mascot asset (`docs/marketing/assets/walkin-hours-logo.png`)
lived only in a sibling commit (`52d29ed2`, "walk-in hours door sign") that was itself unreleased, so
the branch's copy fell back to the vector mark. The committed PNG would not have been reproducible
from the branch it was committed to.

Caught by the only check that finds this: re-run the generator in a clean checkout of the branch and
`git status` it — the PNG came back byte-identical (clean tree) and the PDF differed only because
PIL embeds a creation timestamp in PDFs (`/CreationDate`), which is expected, not a defect. Cherry-pick
the sibling commit too, and the branch becomes self-contained.

RULE: a generated binary in git proves nothing about its own provenance. After committing an artifact
on a branch, regenerate it **from that branch** and compare. If the generator has inputs that live in
another commit — a logo, a palette, a font — those inputs are part of the change, whether or not the
diff mentions them.

CONVENTION NOTE for future signs: PNG output from these scripts is byte-reproducible; PDF output is
not (timestamp). So compare PNGs by hash and treat the PDF as "regenerate, do not diff".
