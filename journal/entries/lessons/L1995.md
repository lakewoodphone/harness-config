**L1995 · PowerShell is case-insensitive: a local dollar-slot IS the parameter dollar-Slot**

MEASURED 2026-09-18 on ZABZ-YOGA, and it had been live for hours: `dshw open <slot>` exited 1 having
opened nothing, with `no slot matches ''`.

CAUSE: PowerShell variable names are case-INSENSITIVE, so `$slot` and `$Slot` are THE SAME VARIABLE.
The 'open' branch of the dispatch switch began `$slot = $null` before parsing its selector; that
assignment therefore blanked the script's own `$Slot` PARAMETER, and the next line reported an empty
selector. `dshw new` takes no selector and worked, which is why nobody saw it.

PROOF (do this, not a read): print the parameter at the top of the script and again just before the
switch. It read `Slot=[3]` at both points and `Slot=[]` inside the branch - the clobber was inside the
branch, in the one statement that looked like a harmless local init.

FIX: name the local `$slotCfg`. Verified: `dshw open -Slot 3` -> `opened window for slot '3'`,
`windows.log` `open slot=3 profile=w3 origin=3202 pid=5372`, `GET /__dshw/open` ->
`{"ports":[3202],"live":{"3202":2}}`.

THE GENERAL RULE, and the reason this is worth an entry: in a script with a `$Name` parameter, never
introduce a local called `$name` (or any other case variant of it). `Set-StrictMode` cannot catch this
- the variable EXISTS, it is just the wrong one.

AND THE SECOND LESSON, which cost an hour: my first diagnosis ("Get-SlotCfgByPortOrLabel returns the
selector string instead of a slot") came from a probe that dot-sourced a CUT COPY of the launcher. A
script dot-sourced from inside a script resolves `$PSScriptRoot` to the COPY's directory, so it read a
different `windows.json` and returned rows for a fleet whose slots never matched the selector. A probe
that does not reproduce the production call path is not evidence. Test the real entry point.
