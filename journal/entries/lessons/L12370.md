**L12370 · A vibrator PASS built on a service request is a false claim - lpt-flip-phone**

2026-10-25, ZABZ-TECH bench. Owner: "one of the phones is missing the vibrator, the earpiece jack,
one of the speakers - did you pick up on that, it should be something your systems would see right
away." It did not. `audit-phone.ps1` printed PASS on the Vibrator row for both handsets, reading
"vibrator service logged the request from com.lpt.bench". A handset with no motor at all prints that
line: the vibrator service accepting a 700 ms request proves the command path, not the transducer.
Same shape as every failure in this repo: the PASS was built on the weakest available evidence, in
the one row where strong evidence is impossible on this hardware.

Three things were invisible to the flow, and only one of them is software-fixable here:

1. Vibrator - neither model has an accelerometer (measured 2026-10-19), so no software on the device
 can sense motion. The honest answer is "not provable by software, feel it", never PASS.
2. Earpiece receiver - the bench APK loopback plays at max MEDIA volume out of the loudspeaker into
 the microphone. It proves loudspeaker + mic + codec together. It never touches the receiver above
 the screen, so a dead earpiece still reads PASS on that row.
3. Headset jack - "Input devices: ... Headset Jack, Button Jack" is a DECLARATION by the snd-card,
 not a plug-detect event. No leg plugs anything in, so nothing can fail.

Fixed the same hour (bench.py, audit.py, audit-phone.ps1):
- `bench.vibrator` now reports STATUS_UNMEASURED, value "request logged; motor not sensed", with the
 reason in the detail, blocks_sale=False so it is a note and not a gate (no software can close it,
 so gating on it would block every E4610 forever).
- HUMAN_CHECKLIST gained explicit items: earpiece-vs-loudspeaker ("the software loopback only ever
 plays out of the loudspeaker, so a dead earpiece reads PASS in the table"), vibrator-feel, and
 headset-jack-with-a-real-headset.
- `audit-phone.ps1` now PRINTS that checklist to the console after the table, read out of report.md.
 This is the deeper defect: the list already contained "Earpiece: make a call or play the tone" and
 nobody saw it, because it lived inside a file the operator never opens.

Verified by re-running the audit leg on 616498311 (run 616498311-20261025-203854): the row reads
UNMEASURED "request logged; motor not sensed", the verdict stays SELLABLE_WITH_NOTES, and the
checklist printed to the console.

Still open: an earpiece loopback in the bench APK (MODE_IN_CALL + STREAM_VOICE_CALL tone, measured
with the same Goertzel as the loudspeaker) would make the receiver a measurement instead of a listen.
The jack cannot be automated without somebody plugging a headset in.
