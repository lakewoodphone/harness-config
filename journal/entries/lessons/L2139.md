**L2139 · L2153 - the autopilot interval is 300s and a run can take 600s+, so the schedule is impossible and every long tick is abandoned**

The measurement that resolves P2130/P2137, taken 2026-09-20 18:27Z on the authority.

 AUTOPILOT_INTERVAL_SEC = 300
 a run that completes takes ~480 s (17:38 -> 17:46)
 a run that does not is abandoned at 600 s (18:14:13 -> 18:24:46, load 1.4)

**The configured interval is shorter than the run it schedules.** Every tick that is not fast is
therefore still executing when the next one is due, and the loop - correctly - refuses to start a second
run (`_run_once_active`). After 600 s it abandons the run and applies a 300 s backoff. So the effective
cadence is not 300 s; it is "one abandoned run per ~15 minutes, at best", which matches what was
observed: **`run_count` advanced from 1 to 2 in a two-hour window (17:12 -> 17:46).**

**And the work is happening anyway, through other paths.** In the same 6-hour window:

 work sessions 110
 ticks (tick_telemetry) 237
 total tick time 8,422 s = 2.3 hours of work inside 6 hours
 p50 tick 29 s, p90 65 s, max 384 s
 autopilot run_count 2

Two completions of the top-level loop, and 110 sessions of real work. **So `run_once` is not the engine
of the company - it is a periodic wrapper, and the work is driven by the reminder poll, the work-queue
poll and APScheduler jobs that run on their own threads.** That is worth knowing before tuning anything:
scaling `run_once` up would not scale the work.

**The arithmetic a person can check.** 8,422 s of work in a 21,600 s window is 39 % utilisation IF the
work were serialised, and the real figure is higher because much of it overlaps. On 4 cores with a
9.9 GB SQLite database and six writers (P2132), a 300 s cadence for a scan that includes several
100 s-plus subsystems was never going to hold.

**What to do is a design decision, not a constant to nudge, and the options are genuinely different:**
 - raise the interval to match reality (say 900 s) - cheap, and it stops the abandon/backoff churn, at
 the cost of a slower reaction to external events;
 - make each subsystem inside `run_once` cheaper or skippable, so a run fits - the honest fix, and the
 one that needs a per-subsystem timing instrument this system does not have;
 - let `run_once` delegate to the queues that are already doing the work, since it evidently is not the
 engine.
I am NOT choosing unilaterally between these in this round, because the choice changes how responsive
the company is to the owner, and that is closer to taste than to engineering. It is recorded as a
decision with a recommendation instead.

**Also recorded from the same measurement:** the latch fix is load-independent and doing its job - the
600 s timeout fired with **0 `previous run still active` skips** and the loop continued. Before the fix,
that same timeout is where the company went permanently quiet for six hours.
