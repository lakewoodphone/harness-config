**L1625 · A 503-capable health endpoint does not make a container unhealthy if the live config answers 200 - measure before relaxing**

The trap was real as a shape and not real as a state — and only a measurement could tell them apart.

THE CONCERN (raised in H311 and in the deploy brief): commit 1b0c91d6 changed the container
healthcheck from probing `/` to probing `/api/health` with `assert r.status == 200`, while the new
`/api/health` deliberately answers 503 when a REQUIRED probe fails. If the deployed config produced
503, the container would be marked permanently unhealthy.

WHAT I MEASURED on the live config (waze-mdm-01, 2026-09-15 ~21:57Z), by running the new code in
throwaway containers against a COPY of the live SQLite file — nothing live was touched:
* exact live config (db present, 0 rows): **HTTP 200**, `{"ok": false, "status": "degraded"}`. The
 committed healthcheck command, run verbatim, **passed** (exit 0).
* fresh/empty volume (db file and tables absent): **HTTP 200**, degraded — because
 `DatabaseService.init_db()` runs `CREATE TABLE IF NOT EXISTS` for both required tables at startup.
* live copy with the two required tables dropped AFTER startup: **HTTP 503**, unhealthy, and the
 committed healthcheck then FAILS (urllib raises HTTPError). This is the only reproduced 503, and
 it is reachable only when the DB stops being queryable at runtime.

WHY 503-ONLY-IF-BROKEN IS CORRECT AND NOT A MISFIRE: the endpoint's own contract is
`status_code = 503` ONLY when `probe_database(...)["ok"]` is false; a merely unverified or empty
dependency yields `status: "degraded"` with **HTTP 200**. So "unverified" never trips a healthcheck
that requires 200, and a genuinely unreadable database does. That is the right binary for liveness.

THE RESTART-LOOP FEAR IS UNFOUNDED, VERIFIED TWO WAYS:
* Docker does not restart a container for being unhealthy — `restart: unless-stopped` acts on exit.
* The only watchdog on the box, `/opt/waze-mdm/operator-tools/health-check.sh` (cron `*/5`), restarts
 services not in `docker compose ps --status running` — i.e. NOT RUNNING, never "unhealthy". Grep
 for `fleet-dashboard|9020` across `operator-tools/` returns nothing, so no monitor keys off it.

DECISION: keep the healthcheck exactly as committed. No healthcheck change, no commit, no push.
A healthcheck must measure liveness, but this one accidentally still does: the failure it catches
(database unqueryable) IS a liveness failure for a dashboard whose only job is reading that database.

GENERALISED: before "fixing" a healthcheck to accept a degraded status, run the endpoint on the live
config. "The endpoint can return 503" and "the container will be unhealthy" are different claims, and
the gap between them is exactly one measurement wide.
