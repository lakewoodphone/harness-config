**L1991 · state.json held a DEAD launch token and doctor had been reporting it as a blocker nobody read**

MEASURED 2026-09-18, ZABZ-YOGA, and it was live. dshw state.json recorded slot 3099 as pid 29116 / startedAt 13:45:30, while the engine actually serving 3099 was pid 4416, started 21:39.
 recorded token -> HTTP 401
 token from the engine'"'"'s own newest `dsh web:` log line -> HTTP 303
`dshw doctor` had been printing "auth probe: token exchange -> 401 (EXPECTED 303)" and adding "the launch token for port 3099 was refused with HTTP 401" to its BLOCKERS list - correctly - while nothing acted on it. Test-LaunchUrl only ever validated a token'"'"'s SHAPE (scheme/host/port/path/token=), never whether it worked, so a new window would have been handed the dead token and landed on "dsh web authentication required". That is the 2026-09-15 w9 incident again, one layer down.

WHY IT MATTERS MORE NOW: under the shared-profile model every window shares one cookie jar, so the first window to authenticate fixes the rest - and the FIRST window after any engine restart is the one that eats the 401. A stale token used to cost one window; it now costs the machine'"'"'s first impression.

FIX: Resolve-WindowUrl collects candidates (recorded URL first, then each `dsh web:` line newest-first) and returns the first that answers 2xx/3xx to a real request with redirects off. If none answer, it prefers the engine'"'"'s OWN log token over the recorded one: a token that was never current cannot become current, whereas a busy engine will accept a live one in a moment.
RULE: a probe that reports a blocker must be read by something that acts on it. doctor had been right for hours.
