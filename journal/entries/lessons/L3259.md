**L3259 · Four column shapes on secretary.db that return zero rows and read like silence (tasks.status, call state, dead dialpad_ui_*, bills.due_date)**

﻿MEASURED 2026-10-05 on secratary against data/secretary.db. Four column shapes
that make a plausible query return ZERO ROWS and read like silence -- the exact
failure this estate keeps paying for.

1. tasks.status is FREE TEXT with 11 observed values. `done` holds 27,296 rows;
 `completed` holds 25. Filtering `status != 'completed'` -- which is what
 "status not completed" reads like -- reports 27,296 finished tasks as open
 work. Use an explicit closed-set: done, closed, cancelled, canceled,
 completed.

2. dialpad_call_full.state is 'hangup' for ALL 13,327 rows. There is no
 `missed` and no `voicemail` state in this lineage, so a query keyed on those
 states returns nothing and looks like a quiet channel. A missed call is
 `direction='inbound' AND COALESCE(duration_seconds,0)=0`.

3. dialpad_ui_voicemail_row is DEAD -- last captured_at 2026-06-14 (3,036 rows).
 dialpad_sms_cache and dialpad_call_full are LIVE (2026-10-05). The live
 `dialpad_ui_*` family is the trap; the `*_cache` / `*_full` tables are the
 live lineage.

4. bills.due_date is NULL on all 11 rows, so the bills table can NEVER raise a
 due-date finding. Read it as "no bills due" and the sweep reports a clean
 finance channel that is blind. Report the column emptiness as the finding.

Rule: before trusting a channel, select MAX(timestamp) from it AND count the rows
the filter would actually match. An empty result is not evidence of health.
