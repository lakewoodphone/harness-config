**L3729 · gmail_search defaults to the WRONG mailbox, and a customer's 'second number' that is our own line matched the entire shop**

TWO QUERIES THAT RETURNED A CONFIDENT WRONG ANSWER TODAY, AND THE CONTROL THAT CATCHES BOTH.
Found 2026-10-13 while pulling the Fishman/Weissman 300DDR cases on ZABZ-TECH. Both are the
wrong-data failure, both looked like real results, and both would have been reported as fact.

1. ps_action("gmail_search") DOES NOT DEFAULT TO THE SHOP MAILBOX.
 Called with only a query, it searches chevedy@gmail.com and returns that account's mail. My
 first search for the return tracking number 9334620845500046516968 came back with ONE result -
 a 2026-06-25 personal email from eliyahuzabrowsky@gmail.com about a researchgate profile - and
 the result envelope said "count: 1, account: primary", which reads like a finished answer.
 The shop's entire 300DDR correspondence, its USPS notices and its Informed Delivery digests live
 in lakewoodphoneandtech@gmail.com.
 FIX: always pass account="lakewoodphoneandtech@gmail.com". The tool echoes the account it
 actually used in the reply - READ THAT FIELD, not just the count.

2. A CUSTOMER'S "SECOND NUMBER" WAS OUR OWN LINE, SO THE QUERY MATCHED THE WHOLE SHOP.
 Joe Fishman's sync record carried (732) 655-2355 as a second number for him. It is not. It is
 +17326552355, the shop's own DIALPAD_SMS_FROM_NUMBER (the Fishman case file had already
 corrected this on 2026-09-30; the sync record still carried it).
 So a query matching `phoneNumberFrom`/`phoneNumberTo` on last-10 '7326552355' matched every
 outbound SMS the business has ever sent. It returned 20 rows of complete strangers - ids 1..20,
 numbers like +17325036608 and +18483291230 - presented as rows about Fishman. On the same table
 with the customer's OWN digits only, the true answer is 12 rows.
 FIX: never match a customer's number against the shop's own number, and when a result set looks
 like "everything", count the table as a control before believing it.

THE GENERAL CONTROL, and it is the thing to carry forward. The column trap underneath both: I
first tested Fishman's absence with to_jsonb(communications)->>'phone', but the column is
`contactPhone`. Every row returned NULL, the WHERE matched nothing, and the query returned a clean
zero - a VACUOUS zero that "proved" an absence nothing had measured. An empty result is a refusal,
not health. So, in order: (a) confirm the column exists in information_schema before believing any
zero; (b) run a control count of the whole table (126,460 rows here); (c) if the row count equals
either zero or the table size, the query is wrong, not the data.
