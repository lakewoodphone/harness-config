**L4961 · Both journal trees reserved the SAME window (through P4376) - a per-tree reservation makes cross-tree collisions GUARANTEED, and I created one live**

Measured 2026-10-15 ~15:5xZ, and it happened to me while I was working.

 ZABZ-YOGA journal/entries/pain/P4314.md "The friction vocabulary has no id for 'the agent was silent'"
 secratary-cloud journal/entries/pain/P4314.md "STEP_BUDGET_EXHAUSTED: the largest failure class is 30 turns and 2 tool calls..."

Two different entries, one id, created minutes apart by one session, because I appended on whichever tree was nearest. Then the allocator on EACH tree:

 ZABZ-YOGA # pain: reserved through P4376 for ZABZ-YOGA
 SECRATARY-CLOUD # pain: reserved through P4376 for SECRATARY-CLOUD

BOTH TREES HOLD THE SAME RESERVATION WINDOW FOR THE SAME KIND. So the `claim` mechanism is correct within a tree and blind across trees, and its effect across a fork is the opposite of what it is for: rather than preventing collisions it ENSURES that the next ~62 pain ids minted on each tree collide with the other. This is not a stale mess that was measured once; it is a defect that manufactures new duplicates every session that appends on a non-authoritative tree, and the union candidate built earlier today is already stale because both trees wrote after it.

WHAT THIS MEANS, and it is the reason the switchover is now unambiguously the first job:
 * the reservation window is the proof that "append on the authority only" is NOT a fix -- it is half a
 switchover, because the other four trees keep minting from the same window until they are consumers;
 * the same applies to every kind (D/H/L/W), not just pain: `sort -n | tail -1` reports the same ceiling
 on both sides;
 * a merge is not a one-off cleanup but something that must be RE-RUN at the moment of the switch,
 because the source keeps moving.

THE LESSON, wider than the journal: a reservation is only a reservation if there is ONE reader of the
ledger. `journal/alloc/bands.tsv` was read per tree and written per tree, so a mechanism whose entire
purpose is to make an id unique made it non-unique. When you add a coordination mechanism, name the
single writer before you trust it.
