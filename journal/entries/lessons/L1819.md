**L1819 · dsh-plugin-health's /healthz is a permanent 503 off Windows, and mesh-health scores 503 as FAIL**

MEASURED 2026-09-16 23:19-23:26Z on zabz-tech-linux, by mounting dsh-plugin-health into a fresh
Linux engine's web profile and then removing it again.

`/healthz` answers 503 on ANY non-Windows node, permanently. packages/plugin-health/lib/index.js:793 is
 const status = readout.processes.available && !readout.processes.stale ? 200 : 503;
and `processes.available` can never be true off Windows because the sampler,
packages/plugin-health/lib/snapshot.ps1, P/Invokes kernel32 CreateToolhelp32Snapshot and says in its own
header that it uses "only what Windows already ships". Confirmed on the node: system.probe.supported
= false, processes.available = false, probe.shell = "pwsh", and macOS behaves the same way (mac-mini
has plugin-health in its profile bundle list and /healthz still answers 404 because its running engine
predates the bundle — a bundle cannot hot-load).

This matters because scripts/mesh-health.ps1:130-134 maps **404 -> WARN** but **anything else -> FAIL**,
so the plugin actively makes a Linux node look WORSE:
 without it: WARN: GET /healthz -> 404 (plugin-health not mounted on this node) -> degraded
 with it: FAIL: GET /healthz (with the cookie from GET /) -> 503 (unexpected status) -> a FAIL line
secratary produces the first line today. So "not mounting plugin-health" is the correct configuration
on Linux, not an omission — do not "fix" a Linux node by mounting it.

Two one-line fixes exist and neither is in S2's files:
 - mesh-health.ps1: treat a 503 from a node whose /healthz `identity.platform` is not win32 as a WARN
 with the reason attached;
 - plugin-health index.js:793: decide 200/503 on whether the probe is SUPPORTED on this platform,
 not on whether it has produced a snapshot yet.

Also measured in the same window, and a live contract change worth knowing: gate revision ec17db22
answered `"governor": null, "accepts.fleet": false, maxChildren: 0` on a node with no governor lease
directory, while revision 24b442ab on the SAME node three minutes later answered
`"governor": {"budgetSlots": 24, "inUse": 0, "queued": 0}, "accepts.fleet": true, "maxChildren": 12`
with the honest reason "slot budget computed from memory; no governor lease directory on this node, so
inUse is reported as 0 and is not measured". Any broker arithmetic built on `accepts.fleet` changed
meaning between those two revisions.

Evidence: docs/mesh/73-linux-pc-node.md sections 1.3 and 4.
