**L1633 · A row count is not a timestamp: prove WHEN state changed before reporting data loss (second false alarm of this class)**

## L - A stale timestamp read as current: the same false alarm has now fired twice

**Two instances, both 2026-09-15, both nearly acted on.**

1. Earlier history: a stale copy of a database was read and believed, and a crisis was reported that
 did not exist. That is why "provenance, always" is a standing rule.
2. Tonight: a persistence workstream reported that the live personality-system library **"was already
 destroyed today"** - revision 38 with 0 records, 0 participants and all 38 snapshots holding the
 empty registry - and inferred that a save had overwritten production between its read and an
 earlier one. It was a reasonable inference from row counts and it was wrong.

**What the check actually showed** (`_scratch/witness3.sql`):

 newest snapshot write : 2026-09-07T18:17:39Z
 most recent write of any kind : 2026-09-07T18:17:39Z
 now() : 2026-09-15T22:11:42Z
 snapshots made in the last 24h : 0

**Zero writes in eight days.** The library had been in that state for over a week; nothing touched
it. And the "0 records" was never the alarming thing it looked like: participant data lives in
`current_session_cache_json` (19,543 bytes, present and intact), while `registry_json` at a constant
97 bytes is the *empty registry*, its normal shape. The totals were consistent across all 38 rows,
which is itself the tell - a fresh destructive write would show a *drop* in one row, not uniformity.

**The rule.** A row count is not a timestamp. Before calling anything destroyed, changed, or newly
broken, ask *when* it changed and prove it with a column, not with an inference:

 SELECT max(<time column>) FROM <table>; -- and SELECT now();

If the newest write predates the change you are about to report, there is no incident - there is a
pre-existing condition, and the report is about state, not about an event. Uniform values across
every row mean "this has been like this", not "this just happened".

**Why it matters more than a normal false alarm.** This business lost customer data twice, so a
data-loss report triggers immediate action: recovery attempts, restore drills, possibly a restore
over live data. Acting on a false one can cause the very damage it claims to report. The cost of the
extra query is one SELECT; the cost of skipping it is potentially irreversible.

**Also worth keeping:** the two agents involved were honest and their reports were carefully
"labelled" - the failure was not deception or laziness, it was inference where a measurement was
available. Do not respond by trusting reports less; respond by adding the one measurement to the
checklist, so the next report carries it.
