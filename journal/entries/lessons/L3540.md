**L3540 · Check your own run history before you call a configuration dangerous - and never let a compaction summary outrank an artifact**

A session told the owner that registering a different number "is the one thing most likely to
make WhatsApp reset the local store", refused to try it, and made "her SIM" the blocker on a
customer job — while the run it had itself recorded one day earlier had done exactly that and
worked: the iPhone 11 was registered to the owner's 848-389-7895, the customer's Shop Jasmyn
container was injected over it, and the chats displayed. The store contains **0** occurrences of
848-389-7895, so the display provably does not depend on the registration matching.

MAKE THIS A RULE:
1. **Before calling a configuration dangerous, search the run history for that exact
 configuration.** `journal.py search`, the case file, and the session transcript are the
 evidence; a plausible mechanism ("the database carries the account it belongs to") is not.
2. **A compaction summary is not the record.** When the owner's memory and a summary disagree
 with the artifacts, go to the artifacts — files on disk, manifest rows, tool output — and say
 which one you read. Conceding a correct claim to end an argument costs an hour of wrong work.
3. **Name the identity you are gating on, and read it.** Two commands settle what the agent
 argued about for an hour: the account's own number is the `ZWACHATSESSION` row whose
 `ZPARTNERNAME` is "You" (JID `18482101881@s.whatsapp.net` = +1 848 210 1881), and the phone's
 number is `Info.plist → "Phone Number"` inside its own backup (+1 848 210 1881). The gate the
 agent invented was the customer's CONTACT line (732-998-0915), which is not the account.
4. **Attribute the precedent correctly.** The proven rehearsal was the iPhone 11 (LPT STORE 2,
 iOS 26.5). The same session called it "the iPad" repeatedly, because an unrelated MDM stream
 ran alongside it. A mislabelled precedent is how a wrong method gets "proven".
