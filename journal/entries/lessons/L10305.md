**L10305 · A guard is only real at the call site that runs it: the exemption list keyed on the wrong identifier**

## Found 2026-10-19T23:50Z, seventy minutes before the first peak block, by a rehearsal whose result contradicted the design

### The defect: an exemption list keyed on the wrong identifier

`schedule_policy` had `BUILTIN_EXEMPT_KINDS` — `customer_reply`, `payment`, `owner_message`, `voicemail`,
`healing`, `alert`, and so on — with a comment explaining that these are the paths where a delay is
observable outside the company. It was documented, it had tests, and `is_exempt()` read it correctly.

Then `_filter_by_schedule` called `decide(aid)` with an **agent id**: `dept_comms_relationships`.

No agent id is in a list of work kinds. So `is_exempt()` returned `False` for **every** department, and the
peak filter held back all 31 of them, including the ones that carry customer messages, commitments and the
owner's own life. Two protections were designed — "only departments are gated" and "exempt kinds always
run" — and only the first one existed. The second was decoration.

**It had tests. They passed. They tested `decide("customer_reply", …)` directly, which is not how anything
in the live path calls it.** A test that constructs its own input proves the function, not the wiring.

### How it was caught

Not by review. By writing a prediction down before the event and noticing that the number was wrong:

```
PEAK kept=1 deferred=31 <- but the design says customer-facing departments are exempt
```

If I had only looked at 01:00 and seen 31 departments deferred, I would have explained it: "well, they are
all departments". **The prediction made it impossible to accept a wrong result quietly.**

### What I did about it, in order

1. **Turned the schedule OFF** (`SCHEDULE_MODE=legacy`, verified in `/proc/<pid>/environ`). A behaviour
 whose safety rests on a mechanism that never fires is not safe; it is lucky. Stop first, fix second.
2. Added `BUILTIN_EXEMPT_AGENTS`, derived from `company_blueprint.py`: the orchestrator plus business ops
 (work orders, inventory, customer_service channel), communications, scheduling, home & life, research
 (customer sourcing) and devices. `is_exempt()` now consults **both** lists, because the two callers
 differ: a work item carries a kind, the tick carries an agent id.
3. Rehearsed again: `kept=7 deferred=25`, with the exempt set exactly as intended.
4. Re-enabled, and wrote the corrected prediction down.

### The transferable rule

**A guard is only real at the call site that runs it.** When two subsystems are joined by an identifier —
an agent id, a task kind, a model name — the guard must be keyed on the identifier the *caller* actually
passes, and there must be one test that exercises the real caller end to end. My tests proved the policy
function; the bug lived in the join. The end-to-end test now exists
(`test_the_tick_gate_keeps_exempt_departments_and_holds_the_rest`) and would have failed before the fix.

### And the kill switch earned its keep

On at 22:31Z, off at 23:39Z, on again at 23:41Z — each state read from the running process's own
environment. That is what it was built for: not a hypothetical, but a real defect found late and stopped
in under a minute without touching code. **The reason to ship a behaviour change with an off switch is not
caution, it is that you will need it and you will need it fast.**
