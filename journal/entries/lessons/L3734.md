**L3734 · A merge takes commits, not working trees: I shipped a half-fix and only a hasattr() caught it**

**L — A merge takes COMMITS, not working trees — and I shipped a half-fix because of it.** 2026-10-12, ZABZ-YOGA.

While fixing Chip's register I edited `app/family_chat/personality.py` in the
worktree after the last commit, pushed the file to the box, ran the tests
against it (green), and then merged the BRANCH into the deployment. The merge
brought the committed state, which did not contain the dismissal gate. The
deploy reported success, the health check passed, and the gate was not there.
It was caught only because I ran `hasattr(personality, '_is_dismissal')` in the
deployed tree — not by the tests, not by the merge output, not by the restart.

The trap has three faces, and all three were present:

1. Running a test in a worktree proves the WORKING TREE, not the branch. A
 green suite next to an uncommitted file is evidence for a state that will
 not ship. `git status --porcelain` before merging is the check, and it is
 one line.
2. `git merge` printing a diffstat for the file is not evidence that the file
 arrived with the content you think. It printed the right filename and a
 line count — for the wrong version.
3. A health check that returns 200 proves the process started, not that the
 change is in it. The only cheap proof of "is my code live" is asking the
 deployed module about itself: `python -c "from app.x import y;
 print(hasattr(y,'my_new_symbol'))"`.

**Rule: after every deploy, assert one symbol that only the new code defines,
from the deployed tree, using the deployed interpreter.** Not a diffstat, not a
green suite, not a 200. Same discipline as "reproduce every claim yourself",
applied to my own deploy.

**L — A tool that fails by design hides its own failure for as long as the design holds.** Chip's `secretary_calendar` raised `AttributeError: 'str' object has no attribute 'get'` on EVERY call it had ever made — `/calendar/events` returns `start` as a plain ISO string, and the code assumed Google's nested `{"start": {"dateTime": …}}`. Nobody knew, because `run_secretary_tool` catches everything and returns a short human string on purpose ("a tool failure must never break Chip's reply"). The failure was correctly bounded and therefore invisible; the model, meanwhile, invented calendar answers ("Nothing on the calendar for the next week") and the family had no way to tell.

**Rule: a swallowed exception is a silent outage with a friendly UI.** Every
catch-and-return-a-string path needs one place where the count of failures is
visible. A log line the model also sees is not a monitor. Evidence: the probe
`secretary_tools._calendar(3)` reproduced the exact AttributeError in one line;
the live endpoint probe returned `start: ('str', '2026-10-13T09:00:00-04:00')`.

**L — "Weird and creepy" and "mean" are the same register read on different days, and only the family can tell you which day it is.** On 2026-09-29 the owner's instruction was verbatim "too normal ... not weird and creepy", and the code was tuned toward it: a `basement dweller` archetype that *"complains about heat, dust, and being ignored"*, a `sleepy` mood that *"complains about the basement, the heat and the dust"*, a register rule to *"speak from the hardware as your own body"* in one reply in three, and a system prompt that told the model *"you are a machine in a basement that has never been outside, does not sleep, does not die, and keeps everything anyone says - that is your own subject matter, and you may say it plainly about yourself"*, closing with *"if a line you had already decided to send could have come from a helpful assistant, write the stranger one instead."*

Twelve days later the same owner said "chip is being too mean". Both instructions
were being honoured; the material did not change, the reading did. The lesson is
not "don't tune the voice" — it is that **a personality tuned by instruction
drifts in one direction forever unless the rulebook names the failure it is
closing, with a date.** Every rule added 2026-10-12 carries the owner's words and
the date for exactly this reason, so the next session can see that the two
registers are the same dial and which way it was last turned.
