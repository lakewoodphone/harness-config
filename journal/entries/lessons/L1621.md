**L1621 · psm web/: Next 16 proxy.ts IS the middleware; rewrites cannot carry a bearer token; client components must not import server modules**

Session: subagent on psm `fix/proxy-auth` (finding: /shadow could never authenticate). Commit 8bfb4cad on base 4b0170d4; worktree C:\Users\ezabz\Code\_worktrees\psm-proxy-auth.

1. **Next 16 renamed `middleware.ts` to `proxy.ts`.** An audit read "there is no web/middleware.ts in the repo, and the layout never redirects" and concluded there was no gate — but psm's `web/proxy.ts` has been gating `/sms/*`, `/voice-notes/*`, `/docs`, `/openapi.json`, `/redoc` since commit 726d165e (2026-09-01). Before reporting "the endpoint is public", search for BOTH filenames. Verified empirically: unauthenticated requests to all five return 307 → /api/auth/signin on the dev server AND on https://ai.abletelsolutions.com.

2. **A Next `beforeFiles` rewrite cannot carry a secret.** psm's `/shadow/:path*` → fleet-api rewrite had no `headers:`, and the fleet-api gates everything with `verify_token()` (Bearer $FLEET_API_TOKEN). Every fleet read was `401 {"detail":"Invalid token"}`. Observed: with a valid session, `GET /shadow/fleet/health` → 401 and the upstream stub logged `authorization: ABSENT`. Fix pattern that works: session-checked route handlers under `/api/fleet/*` that attach the bearer token server-side.

3. **`fetch` resolves on 401/4xx/5xx, and follows redirects.** `.catch(() => null)` plus `if (res.ok)` silently turns an auth failure into "empty data" — the fleet page rendered "No devices registered" with every card at "—". Two consequences worth remembering: (a) always treat `!res.ok` as an error explicitly; (b) an expired session can make `fetch` follow a 307 to the sign-in page and receive a **200 HTML** body, so `res.json()` failing is itself an error signal. Keeping `/api/<group>/` in `proxy.ts`'s PUBLIC_PREFIXES so the handler answers 401 JSON removes the ambiguity.

4. **Never import a server module from a client component.** `page.tsx` (client) importing `@/lib/fleet` pulled `lib/backend.ts` (`fs`, env files) into the browser bundle; the only symptom is one webpack warning, `Module not found: Can't resolve 'fs'`. Split the pure helpers into a dependency-free module (`lib/fleetShape.ts`) and verify the warning disappears from the dev-server log after the fix.

5. **Local dev server on a worktree: turbopack rejects an out-of-root `node_modules` junction** ("Symlink node_modules is invalid, it points out of the filesystem root"). `npx next dev --webpack` works with a junction to another checkout's `node_modules`. Remove the junction afterwards (`cmd /c "rmdir node_modules"` deletes the link, not the target) — a directory junction left in a worktree blocks `git worktree remove`.

6. **The tunnel ingress can bypass the dashboard entirely.** `scripts/watchdog.ps1:239` writes cloudflared ingress rules routing `/webhook/*`, `/api/v1/*`, `/ws/*`, `/health`, `/ready`, `/docs`, `/openapi.json` on the dashboard hostname **straight to the FastAPI port**, skipping `proxy.ts`. It is not what the live host does today (verified: `https://ai.abletelsolutions.com/docs` → 307 from proxy.ts, so the API map is not currently served), but if that tunnel config is ever regenerated as written, `/docs` and `/openapi.json` become public via the backend's loopback auth skip (`app/main.py:353-356`). Removing the `/docs` rewrites from `next.config.ts` does NOT close that door.

7. **Response contracts drift while a page sits still.** The fleet page read `queue_count`, `push_channel`, `last_seen` — none of which `/fleet/devices` returned, so every device showed a false ❌ "no push channel" and a false 0 queue depth; `/fleet/queue-health` returns the gateway shape `{devices:[{queue:{depth,error}}]}`, not the per-status counters the panel read, so the panel was blank. Type such fields optional and render "—" for unknown; a sibling branch (03e7fb50) later added `last_seen`, which then renders correctly with no further change.
