**L1900 · Never rewrite ~/.dsh/profiles/web/cordis.patch.yml as a whole file - it holds !!js expressions**

Measured 2026-09-17 on ZABZ-YOGA trying to hot-mount a plugin row into the live engine.

That file is a YAML flow sequence whose entries carry !!js tagged values (trustedHosts: !!js ctx.webRuntime.trustedHosts, and the whole remote-fanout config). yaml.parse resolves an unknown tag to null and warns TAG_RESOLVE_FAILED, so parsing and re-emitting the file (even as JSON) DESTROYS every one of those expressions. The engine boots with null in place of the JS expressions and the /api browser-trust fence loses trustedHosts - the same failure docs/pain P48 records.

An automated editor of that file must be a SURGICAL TEXT INSERT (find the last ']' and splice the new entry before it), and must keep a .bak beside it. Measured recovery: copy the .bak back and verify sha256 matches.

Related, and still unproven: whether dsh-web's patchReload:live watcher (dsh/lib/profile-boot-*.js:321-338 -> watchUserPatches -> hmr.registerConfig on the profile patch path and on \/cordis.patch.yml) actually mounts a BRAND NEW loader entry on a running engine. A surgical insert of a new row was made and no state file appeared within ~10 s; the file was restored byte-identical and the engine (pid 4880) was never restarted. Treat hot-mounting a new row as UNVERIFIED on this build.
