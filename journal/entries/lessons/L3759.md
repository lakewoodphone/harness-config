**L3759 · A helper that returns its errors as a value makes them invisible: the real shape of P2926 item 1**

## What I expected vs what was there

journal **P2926 item 1** says: six `except` clauses in `app/services/plaid_service.py`
catch `plaid.api.ApiException`, which plaid-python 42.0.0 no longer exposes, so **no Plaid
API error can be read from the logs**. The brief told me to verify rather than trust it.

Measured 2026-10-13, cloud authority, `/opt/company/.venv`:

- installed version is `plaid-python` **45.0.0**, not 42.0.0.
- `hasattr(plaid.api, "ApiException")` -> **False**. True as stated.
- but the code never said `plaid.api.ApiException`. It says `except plaid.ApiException`, and
 `hasattr(plaid, "ApiException")` -> **True**, `plaid.ApiException is
 plaid.exceptions.ApiException` -> **True**.
- drove a real 400 from a loopback Plaid-shaped server through the real code path: the
 `except plaid.ApiException` clause **caught it**, and the message reached the log at ERROR
 with `error_code: INVALID_API_KEYS` and the `request_id` intact.

So the stated defect does not exist. `probe_plaid_apiexception.py` reproduces this.

## The real defect, one layer up

`plaid_service.sync_transactions()` catches **every** exception and **RETURNS**
`{"error": ...}` instead of raising. `AutopilotController._maybe_sync_plaid_transactions`
then does:

```
result = sync_transactions() # -> {"error": "Plaid not configured"}
added = result.get("added", 0) # -> 0
self._record_subsystem("plaid_sync", success=True, detail="0 added, 0 modified, 0 removed")
```

Proved with the real method body (`probe_plaid_pull_error_is_success.py`,
`--autopilot-source base/autopilot.py --scenario no-credentials`): the production recorder
wrote `last_status='ok'`, `last_error=None`, `successes=1`, `failures=0`.

**The rule.** A helper that swallows its exceptions and returns an error *value* does not
make errors readable — it moves them somewhere the caller must remember to look. When a
caller reads a count off such a return value, a total failure and a quiet day become the
same number. **Verify the error-reporting chain end to end, not the `except` clause.** A
correct `except` upstream of a caller that discards the result is indistinguishable from no
`except` at all.

Second-order rule, same shape: `subsystem_health.<name>.last_ran_at` advances on a **failed**
run too. A pull broken for a week still reports a fresh timestamp. Freshness must read the
newest **successful** run, and the failure must be reported on a separate axis.

## Where it landed

The autopilot's error handling is not rhetorical: the same helper is why four pull lanes
(paypal, amazon, ebay, stripe) could be dead on the authority with the health record reading
`ok`. Fix shipped as patch `0002-autopilot-plaid-error-is-failure.patch` (+26/-1 in
`app/autopilot.py`): treat `result.get("error")` as the pull's own verdict.
