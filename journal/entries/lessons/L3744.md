**L3744 · A case-sensitive hex comparison fails EVERY file - Get-FileHash is uppercase, hashlib is lowercase**

**L3741 · A case-sensitive hex comparison fails EVERY file — PowerShell's Get-FileHash is uppercase, hashlib is lowercase, and the verify tool compared them raw**

MEASURED 2026-10-13 on the Greenfeld Dell delivery, and it was caught only because the copy/verify pair was exercised on a 50-file slice before the real job started. The manifest was built from a source hash pass run in PowerShell (`Get-FileHash -Algorithm SHA256`, **UPPERCASE** hex). `verify_stick.py` computes its digests with Python's `hashlib`, which returns **lowercase**, and compared them with `got != digest`. Result on a copy that had just succeeded:

```
 verified byte-identical : 50
 MISSING : 0
 WRONG BYTES : 50 <-- every single file
 VERDICT : INCOMPLETE
 repaired (re-copied) : 50
 re-run this command to re-check
```

and the re-check said 50 wrong again. On the real payload that is **175 GB copied, then 175 GB re-copied by `--repair`, then still INCOMPLETE** — on a 5-minute scheduled retry, for ever, with nothing wrong with the data. The same latent defect sat in `copy_to_stick.py --verify`.

**FIXED IN TWO PLACES, deliberately:** the digest is lowercased when the manifest is built (the producer should emit one canonical case), AND both shared tools now compare case-insensitively — because a hex digest is the same digest whatever case it was written in, and the next manifest may come from either language. `copy_to_stick.py` and `verify_stick.py` in `lpt-hub/scripts/customer-operations` carry a comment saying why.

**RULE:** never compare a hash, a UUID or any hex string case-sensitively across two languages or two tools. Normalise on one side, compare case-insensitively on the other, and **exercise a copier/verifier pair on a small slice before committing it to a multi-hour job** — this one only surfaced at file 1 of 16,756, and the 2-minute slice test is what found it.

**THE SECOND HALF OF THE SAME LESSON, same file, same afternoon:** the orchestrator originally wrote a `greenfeld-copy.claimed` marker at the stick root so a later pass would recognise the medium. `verify_stick.py` counts *any* file on the target that is not in the manifest as EXTRA, and any EXTRA makes the verdict INCOMPLETE — so the marker alone would have failed every verify for ever. **Nothing of ours is written to the medium before the verify now**; the medium is recognised by the **volume label** we set on it, which is also what the shop's own delivery doc prescribes. Our two generated artefacts (`README.txt`, `CHECKSUMS-SHA256.txt`) are deleted before a re-verify and regenerated after it.
