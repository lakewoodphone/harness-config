**L1504 · A loose FTS match ordered by recency is indistinguishable from no search**

MEASURED 2026-09-15 on the real corpus (166,939 records). The query an agent actually
types is a sentence:

 "when did we last talk about a cracked iphone screen"

As a conjunction it matches nothing -- nobody says that sentence. As a disjunction its
stopwords match EVERYTHING, and the top hit was `It's a iPhone 16 pro max` (2026-09-15,
sms), because the loose fallback was still ordered by `c.ts DESC`. The result was a
correct, recent, completely irrelevant answer, which is the worst kind: it looks like a
working search. The same query, after the fix, returns
`do you repair cracked iphone screens?` and `how much is it to fix cracked iphone screens`.

THE RULE: any search that has loosened must do three things.
 1. Be relevance-ordered (bm25), never date-ordered. A loose match sorted by recency
 is indistinguishable from no search at all.
 2. Say that it loosened, and name the terms it actually used, so the reader knows the
 match is loose rather than exact. (`match_mode`: all-terms | any-term | filter-only.)
 3. Drop the empty words -- but ONLY on the loose path. If the conjunction matched, no
 word is ever removed from the query.

COROLLARY, measured in the same pass: never let caller text reach the query parser.
`screen replacement?` was an FTS5 syntax error. Tokenise every query and quote every
piece (`_fts_terms` + `_match_expr`), then explicit `"phrases"` survive and nothing else
can be syntax.
