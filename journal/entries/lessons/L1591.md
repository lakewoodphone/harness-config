**L1591 · The prompt-caching saving was never real - 0 cached tokens on 18,803 calls means the prefix is unstable, not that a key is missing**

MEASURED 2026-09-15 by W3, cross-checked against live data. Three corrections to what the audit had recorded.

1. THE PROMPT-CACHING SAVING DOES NOT EXIST AS DESCRIBED -- AND THE REAL FINDING IS BETTER. DeepInfra caching is automatic-by-prefix (docs.deepinfra.com/chat/prompt-caching). The explicit retained-window marker (`prompt_cache_options`) supports only Nemotron-3-Ultra and Kimi-K2.7-Code and explicitly bills unsupported models as standard input, so `deepseek-ai/DeepSeek-V4-Flash-0731` has no marker saving to claim. What WAS fixed is the measurement: `prompt_prefix_hash` was NULL on 124,025 / 212,079 rows and the internal path now records it.

 THE FINDING WORTH KEEPING: **0 cached tokens across 18,803 orchestrator calls on the workhorse model, while MiniMax-M3 on the SAME DeepInfra account hits 60%.** So the pipe caches and the workhorse PREFIX IS UNSTABLE -- something in front of it changes on every call, which is why caching never hits. That is a different and more tractable defect than "a cache key is missing", and the new prefix hash makes it measurable. **Do not book the ~$39/month; do not repeat the "45% boilerplate" premise as established** -- it was never verified, and this evidence points the other way.

2. THE BRIEF'S FILE MAP WAS WRONG, so future briefs must be checked against the tree before they are issued. `app/smart_router.py` does not exist -- the router is `app/services/smart_router.py`. `app/pricing.py` exists but is NOT where `_estimate_cost` / `_GOOGLE_MODEL_RENAME` live -- those are in `app/services/ai_gateway.py`. I took those paths from an earlier audit report instead of opening the files, and repeated them into a workstream brief. W3 caught it and used the real paths; a less careful agent would have edited files nothing imports. **Rule: every path that goes into a brief gets verified with a `test -f` before the brief is sent.**

3. A DUPLICATE OF THE SAME PRICING BUG STILL EXISTS, UNFIXED: `app/services/agent_worker.py` (~line 2635) has its OWN `_estimate_cost` carrying the same Google-rename mismatch as the one W3 fixed in `ai_gateway.py`. Two implementations of one rule, so fixing one silently misses the other -- exactly the pattern the earlier PART-125 work recorded for the account-mutation rate limiter. Neither W3 nor W1 owned that file, and it is currently at the checkpoint state after W1's revert, so the bug is live.

ALSO CONFIRMED BY W3, with live proof: the D4 pricing fix works -- the `gemini-3-flash` lane (271 calls) was logging a stale $0.60/M while actually billing as `gemini-3.5-flash` at $9.00/M; recorded cost now moves 0.15 -> 1.5 per Mtok-input. And W3 declined to reproduce two figures from the audit brief: it labelled the $1.1317/$18.2519 and $1.3183/$13.3604 pairs as reconstructions rather than inventing token counts to match them, because their ratios (16.13x, 10.13x) do not match the catalog price ratios (15x, 2.14x). That is the right call and the discrepancy should be treated as unresolved, not as two correct data points.
