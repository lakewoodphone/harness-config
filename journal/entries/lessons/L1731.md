**L1731 · Autosync junctioned client plugins into a TEMP snapshot - every reboot left both machines' engines unable to resolve their bundles and unable to boot**

## What was wrong
`autosync` applies harness-config **from a snapshot of HEAD under `%LOCALAPPDATA%\Temp`
(`harness-config-snap-<timestamp>`)**, not from the working tree — a deliberate property so a dirty
tree is neither published nor lost. It then runs `install-client-plugins.ps1`, and that script
computed its source root as `Split-Path -Parent $PSScriptRoot` — **which is the snapshot**. So every
plugin junction it created pointed into `…\Temp\harness-config-snap-…\packages\…`, and when the
snapshot was cleaned up minutes later, every junction dangled.

The engine then cannot resolve its own bundles and **refuses to boot at all**:

 Error: dsh: cannot resolve profile bundle "dsh-plugin-cost" from the dsh installation or
 C:\Users\ezabz\.dsh\profiles\web

**Measured on both machines.** Physical evidence from the desktop: `LinkTarget =
…\Temp\harness-config-snap-20260916-113202\packages\plugin-cost`, `package.json: False`,
`require.resolve('dsh-plugin-cost/package.json')` -> `MODULE_NOT_FOUND`. ZABZ-YOGA was in exactly the
same state (`…snap-20260916-114704…`, resolution failing) and was **one restart away from being
unbootable** — its engine was healthy only because it had started before the sync re-junctioned the
links.

**The trigger is any restart after a sync, which is why a reboot produced it.** The desktop's
`PersonalSecretary-HarnessSync` task runs at logon, so every boot re-junctioned to a fresh snapshot
and then deleted it. Its own engine watchdog could not recover it (`result=2147946720`) because the
fault was deterministic.

## The fix
The installer now refuses to link into a transient directory: if its own root is under `%TEMP%` and
the real checkout exists, it prints a note and links to `~/code/harness-config` instead. **A junction
must point at the checkout, the only copy that persists, no matter where the script was invoked
from.** Verified both ways: from the real checkout it is silent and all six bundles report `ok`; run
from a copy under `%TEMP%` it prints the note and links to the checkout.

## Why this mattered more than it looks
This is a machine-wide, reboot-triggered "the assistant will not start" failure, caused by the
delivery mechanism itself, present on both machines, with a symptom (an engine that exits on boot)
that points at nothing obvious. The logs named the bundle, never the cause. It would have read to
the owner as "the desktop is broken again".

## The rules
- **A link to a transient directory is a delayed outage.** Anything installed by a periodic job must
 resolve to a path that outlives the job.
- **A snapshot is a source of *content*, never a target of *references*.** Applying from a snapshot
 is right; junctioning into it is not.
- When an engine will not start and reports an unresolvable dependency, **check where the links
 actually point** (`Get-Item -Force | Select LinkTarget`) before believing any tool that reports the
 package as installed. `Test-Path` returns True for a dangling directory reparse point, which is how
 this stayed invisible.
