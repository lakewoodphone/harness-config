**L2795 · An unbounded lock acquire behind a bounded timeout: the health probe blocked on an in-process lock and reported the idle database as dead**

THE DEFECT, found 2026-09-28 in `app/database.py:1057-1060` on the production tree:

 acquired = _db_lock.acquire(timeout=2.0)
 if not acquired:
 # Lock is held by another thread doing connection setup.
 # This is rare -- only happens on first access per thread.
 # Block briefly but don't hang forever.
 _log.warning("_get_conn: _db_lock contended for key %s, waiting...", key)
 _db_lock.acquire() # <-- NO TIMEOUT. Blocks forever.

The comment says "don't hang forever" and the next line does exactly that, forever.
`_db_lock` is an `RLock`; a thread entering that line waits with no bound.

WHY IT BECOMES AN OUTAGE, not a slow query:
 1. `_get_conn` is called by the `/health` DB probe inside `run_in_threadpool` and wrapped in
 `asyncio.wait_for(..., timeout=2.0)` (`app/main.py:1508`).
 2. **`asyncio.wait_for` cannot cancel a task already running in a threadpool.** It cancels the
 awaitable; the thread keeps running. So on timeout the probe reports `ok: false` -- and the
 thread is STILL on that line, blocked.
 3. Every contended probe therefore leaks one worker into a permanent block. Starlette/anyio's
 threadpool has a finite token budget, so those leaked workers are consumed, and once they are
 gone **every other `run_in_threadpool` call in the app stalls too** -- including SMS
 persistence (`app/main.py:6354`, `6396`) and the telephony health endpoint (`:1680`).
 The service is then bound to its port and answering nothing, which is exactly what was
 observed: port 8002 LISTEN on the old pid, `curl` returning HTTP 000, for five minutes.
 4. `_db_lock` is also held across connection *setup*, which on a 12.17 GB database means
 `sqlite3.connect` + PRAGMAs + a reaping pass -- easily longer than 2 s under load. So the
 contention is not rare; it is caused by the same 12 GB database the probe is trying to verify.
 5. Three consecutive `ok: false` results make the access-watchdog restart the service. The restart
 does not fix the leak -- it reaps the threads -- but the next burst reproduces it, hence 13
 starts in a day and a five-minute shutdown (threads blocked in an uninterruptible acquire do
 not exit on SIGTERM).

THE MEASUREMENT THAT PROVES THE PROBE IS THE PROBLEM, NOT THE LOAD (sampler, 32 samples):
 read_ms p50=0.2 p95=0.7 max=1.0 <- a fresh connection doing SELECT 1, on the SAME db
 health ok:false 4 times, one at 2020 ms, two at 8003 ms, one schema query at 29261 ms
The database was idle. A trivial read took 0.2 ms. The app's probe still declared the database down.
So "the database is slow" was never true. **The probe was blocked on an in-process lock, not on
SQLite** -- and it reported that as a database failure.

GENERALISED LESSONS:
 * An unbounded lock acquisition behind a bounded timeout is worse than no timeout: the caller
 looks protected and the worker is not. Bound every acquisition, or do not claim a bound.
 * Never wrap a threadpool call in `wait_for` and treat the timeout as a verdict about the
 resource. The timeout says the *thread* is stuck, not that the database is broken.
 * A health check that shares a lock with the work it is checking cannot report on it. Use a
 dedicated path that cannot be blocked by the thing being measured -- here, a fresh short-lived
 read-only connection, which measured 0.2 ms while the shared-lock path was timing out at 2 s.
 * When a comment and the line under it disagree ("don't hang forever" / `acquire()`), trust the
 line. Two of this system's worst failures have been confident comments over wrong code.
