**L3618 · A monitor that reads the app over HTTP inherits the app inner lock**

A monitor that reads an app over HTTP inherits every blocking point inside it. On secratary-cloud, GET /v1/models is lock-bound behind app.database._db_lock; while the lock is held the endpoint hangs for minutes even though a fresh interpreter builds the same catalogue in 0.5s. Any check that decides "is this lane selectable" from that endpoint will false-alarm during those windows, so give it a fallback that does not share the app's in-process lock and record in provenance which path answered. Second rule: an "unreadable catalogue -> not-retired == selectable" fallback is only honest if it cannot fire on rows that are not model ids at all (the 2026-10-07 `unknown` sentinels); otherwise a transient read failure looks like a live HIGH.
