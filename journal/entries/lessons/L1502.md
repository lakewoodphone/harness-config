**L1502 · Four ways a launcher silently fails: bootstrap-only .env keys, param() placement, the wrong entry point, and session 0**

MEASURED 2026-09-15, on Yocheved's laptop, at the cost of a dead engine for part of an evening.

1. An environment key in ~/.dsh/.env STOPS THE HARNESS BOOTING.
 `dsh-app-boot` classifies a set of names as bootstrap-only and aborts the boot when any appears in a
 discovered .env: "... which only the launching environment may set (it decides how this process
 starts, where its code and instructions load from, or how it reaches the network); export X instead
 of putting it in a .env file". The harness-home .env is exempted for HTTP(S)_PROXY/NO_PROXY ALONE.
 I wrote DSH_SESSION_INGEST_TOKEN there to give ps-system a credential and took her engine offline.
 Put credentials in the repo's own .env, or export them in the launching process. Never in ~/.dsh/.env.

2. `[CmdletBinding()]` and `param()` MUST be the first statements in a PowerShell script.
 I placed an executable block above them; that is six parse errors, and the launcher is what the
 desktop shortcut runs. I had pushed and delivered it before checking.
 The verification that would have caught it is running the script, not parsing it -- I now do
 `dshw doctor` on my own machine, because "parses cleanly" and "actually runs" are different claims
 and only the second one protects the user.

3. An interactive task must run the entry point that carries the environment.
 Task Scheduler ran `dshw.ps1 new` directly, while the environment lived in the machine's
 launch.cmd -- so the engine never inherited it, and the launcher was dead code on the path that
 mattered. Two sources of truth for one environment variable is the same defect as two sources of
 truth for anything else.

4. Running the launcher from a SYSTEM-context remote channel starts the engine in SESSION 0, where the
 user cannot see it. "Port 3099 is listening" said yes while she had no window. Session matters as
 much as liveness.
