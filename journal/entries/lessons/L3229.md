**L3229 · When the ps_* tools vanish, the server is almost never the fault: reproduce the stdio handshake over the row's own ssh argv before touching anything**

Rule: a missing mcp__secretary__* set is a HARNESS state, and the first thing to do is
not to restart anything - it is to reproduce the transport by hand and separate the
three ends.

The three ends and how each is checked in under a minute:
1. Server - run the row's exact argv over ssh with </dev/null (no protocol traffic):
 a clean exit with empty stdout/stderr means the module imports and the process is
 fine. For a real answer, drive one initialize + notifications/initialized +
 tools/list by hand on the same ssh argv; a reply with serverInfo+instructions and a
 tools array means the server end is healthy and the fault is on the host side.
2. Transport - find the harness's own connector: Get-CimInstance Win32_Process filtered
 on ssh.exe whose ParentProcessId is the web host, then `ps -eo pid,ppid,lstart,cmd`
 on the remote filtered for ps_mcp_server. A connector older than the failed reconnect
 window means the harness holds an ABANDONED session while believing the server is down.
3. Host - the supervisor gives up on a bounded budget. dsh-mcp-client: default 10
 attempts, delays 0.5/1/2/4/8/16/30 s then 30 s to the cap => ~121 s of delays, i.e.
 about two minutes of trouble is enough to unregister the whole tool set until the
 Host is restarted or the plugin is reloaded. Its own log line names that state:
 "giving up after 10 consecutive failed reconnect attempts - tools unregistered".
 `failOnStartupError: false` (our profile rows) means the owner is never told.

Corollary that cost time here: an MCP call cannot be used to test whether the tools
exist, and neither can the GUI's popup - but "Tools updated / N removed" in the GUI is
the client rendering the registry delta, so it is evidence that N registrations were
disposed, not that a server refused.

Corollary two: the EADDRINUSE startup log in ~/.dsh/logs is the log of a boot that
FAILED and died. Its warnings are not the running engine's history - reading them as
such sends you after the wrong trigger. The live host's own stderr is not in that file.
