**L2988 · An item is a statement about the world at filing time: my priority-1 'authority overloaded' item stopped being true within two hours, and a woken session would have chased a ghost**

 top consumers: python 2.49 GB, python 600 MB, node 1.15 GB, FIVE chrome processes
 `curl 127.0.0.1:8002/health` did NOT answer within 5 s

I filed a priority-1 item on the first reading ("the authority is 4x oversubscribed while serving as
the control plane, and its ssh banner timeouts take the whole wake/dispatch system down"). The reading
was true. The condition did not hold.

THE LESSON, and it is about how an item is written rather than about the machine: AN ITEM IS A STATEMENT
ABOUT THE WORLD AT FILING TIME, and a session that wakes for it has no way to know the world moved. It
will spend its first minutes rediscovering the current state, and might then "fix" a crisis that is not
there - the exact waste the owner named ("don't do stupid work or the same work over and over"). So when
a measurement moves, the item must move with it, and the item should say WHICH PART of it survives.

WHAT SURVIVES HERE, and it is the part worth doing: NOTHING PREVENTS THE NEXT OVERLOAD. The specific
danger is unchanged and asymmetric - a saturated control plane makes an ssh banner slow, the wake
dispatcher times out, and the failure presents as a network error while the real cause is load. The
item's definition of done was rewritten so the DELIVERABLE IS THE GUARD (refuse or report rather than
add work when saturated) and not a post-mortem of an incident that has passed.

A NOTE I CANNOT YET EXPLAIN, stated honestly: the load fell without any action of mine that accounts
for it. At 18:32 the top item was a 2.49 GB python with 2331 s elapsed - consistent with a heavy
one-off, possibly a test suite running on the control plane. I have NOT identified it, and I am not
going to write a cause I did not measure. What I can say is what the readings say.
