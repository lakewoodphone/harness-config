**L3468 · A delta metric whose baseline resets itself can never be computed - the office estate-monitor's disk_util_pct was dead for 38.9 h and blamed its source**

WHAT. Two metrics in the office box's own silent-failure monitor could NEVER have been computed, and its
`monitor.log` proves one of them had been dead for 38.9 hours. Both are the same defect: **a baseline
that resets itself, so the metric that depends on a previous sample can never see one.**

THE DEFECT, in `/home/zabz/bin/estate-monitor.py` (the office file, and the shape was copied into my
port before I caught it). The io_ticks baseline was written **only inside the branch that required a
baseline to already exist**:

 if prev_t and prev_ds: # <-- needs last run's sample
 if dt_ms >= 10000:
 ... compute disk_util_pct ...
 facts["diskstats"] = dict(cur) # <-- baseline written only here
 facts["diskstats_at"] = t
 if "diskstats" not in facts:
 facts["diskstats"] = prev.get("diskstats", {}) # <-- {} on every run
 facts["diskstats_at"] = prev.get("diskstats_at")

On a fresh install `prev_ds` is `{}`, the first branch never runs, `{}` is persisted, and the second run
sees `{}` again. It deadlocks itself. Measured on the office box, from its own log:

 estate-monitor: … disk_util_pct=5.0 for_runs=2) age=140038s src=/proc/diskstats (io_ticks delta)
 -- reading stopped arriving (no usable previous io_ticks sample …)

`age=140,038 s` = **38.9 hours of a permanently unmeasurable metric**, reported as "reading stopped
arriving" — i.e. the monitor blamed a source that was never broken. The identical shape was latent in
`authority_db_growth_mb_h`, where anchoring the rate on the *previous run* would have made the interval
permanently ~120 s against a 600 s minimum, so the rate would never once be emitted.

THE FIX. Advance the baseline **unconditionally when the collector succeeded**, and use only the
*previous* baseline for the delta. For a rate with a minimum window, give it its **own anchor** that
advances only when a rate is actually emitted. Measured after the fix on the authority:
`disk_util_pct = 56.54 %`.

THE RULE. Any metric of the form "delta since last time" needs its baseline advanced on the path where
the delta was NOT usable, or it can never start. And any metric of the form "per hour" needs an anchor
decoupled from the run cadence, or the cadence silently sets the window. **Test it by reading the second
run, not the first** — the first run of a delta metric is always NODATA and that is correct, which is
exactly why the defect hides there.

SIDE LESSON, same file: the office monitor's `disk_used_pct` is **device busy %**, not space, and its
space guard was a separate cron job. A port that carried only `disk_util_pct` would have left the
authority's binding constraint — 26 GB free against a 23.7 GB database — unmeasured. Read what a metric
is computed FROM, not what it is called.
