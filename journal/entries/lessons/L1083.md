**L1083 · A relative 'started_label' is not a timestamp, and a dedup key without a date merges everything**

## Before believing "source X stopped, so the data is missing", ask which other table already holds it

The standing belief was that all voicemails since 2026-06-14 were lost, because the Playwright UI
crawl froze that day and it was documented as the only voicemail source. It was wrong. The
half-hourly REST harvest had been writing **every voicemail as a call row all along** — 916 of them,
the newest from that same afternoon, each carrying `voicemail_link`
(`https://dialpad.com/v/<call_id>`), a recording id and often a transcript. They were filed under
`kind=call`, so nothing that asked for voicemails could find them.

The gap was a *labelling* gap, not an ingestion gap, and it closed with one extra extractor — no new
API work, no browser, no cost. Three months of "missing" customer messages were already on disk.

Corollary, paid for in duplicates: when two tables describe the same events (here
`dialpad_call_full` and `dialpad_transcript_cache`), the index must decide which is authoritative
*before* indexing both, or every event appears twice and search looks broken. Measured: 2,425 groups
of Dialpad calls are one conversation stored as two records (two legs, one carrying the recording) —
2,433 redundant rows, each returned twice by a search for "battery".

## A crawler's `started_label` is not a timestamp

`dialpad_ui_*` tables carry `started_label` values like `"4 days ago"` and `"99 days ago"`. `_ts_from`
cannot parse them, so keying rows on `started_label OR captured_at` left thousands of rows with **no
date at all** — unfindable by date — and, worse, made every one of them look like the same day to the
de-duplication key: **2,525 voicemails collapsed into 371**. `captured_at` is the real timestamp; a
relative label belongs in `subject`, never in a timestamp column.

Two rules: a dedup key that can fall back to an empty date is not a dedup key, it is a
merge-everything — require the date. And when a column is named like a timestamp but holds prose,
the failure is silent in the schema and only visible in the data.
