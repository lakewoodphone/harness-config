**L1564 · A zero from a grep that matches nothing is not a measurement**

**Rule.** A zero returned by a `grep` that matches nothing is not a measurement. Before a count of `0`
changes what you believe, run the command bare, confirm the pattern can match at all, and check that the
command's exit code is not being read through a pipeline.

**Evidence, 2026-09-15.** Hunting whether the company API restarts, I ran:

 journalctl -u secretary-api --since "7 days ago" | grep -c "Started Personal Secretary API" -> 0

and nearly concluded "the API never restarts". The real journal line is
`Started secretary-api.service - Personal Secretary API (FastAPI).` — this systemd puts the **unit name
first**, so my pattern could never match. The same query with the correct pattern returned **339 starts in
7 days, 174 of them in one day**. The zero was a property of my regex, not of the system.

**Second, same session, same family of error.** My gap statistics printed
`min 1946s ... 42 gaps under 30s` — impossible together — because I read `gaps[0]` and `gaps[-1]` from an
**unsorted** list. Sorting first gave min 0 s, median 70 s, max 72772 s. My earlier handoff H269 records the
sibling of this: `$LASTEXITCODE` read *after a pipe* reports the last command in the pipeline, so a check
reported success unconditionally.

**Why it is dangerous here specifically.** This is a system where the recorded failure mode is confident
wrongness, and a `0` is the most confident-looking wrong answer available. A zero that means "the pattern
did not match" is indistinguishable in a summary from a zero that means "the event did not happen".

**How to apply.** For any count that will change a decision: print the pattern next to the number; run a
positive control (grep for something you know exists) in the same command; put the total row count beside the
filtered count; and read exit codes bare, never through `|`.
