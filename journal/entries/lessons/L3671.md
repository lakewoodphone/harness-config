**L3671 · FAT32: a valid 8.3 filename collides with another file's generated short name - one directory entry, both paths resolve, Test-Path true for both, and a real document is one overwrite from being lost**

**Measured 2026-10-11**, delivering 149,381 files to a customer's FAT32 USB stick.

## The failure

The verify reported **1 file missing** while `Test-Path` insisted it existed. It did exist — as the
**short name of a different file**:

```
source : _NTITL~1.DWD 165459 bytes sha256 ed8546e2…
source : _NTITL~1 1.DWD 165459 bytes sha256 09cea4e1… <- different documents
FAT32 : only ONE entry in the directory listing, and BOTH paths resolve to it
```

`_NTITL~1.DWD` is itself a valid **8.3 short name**. FAT32 generates a short name for every long
name, and Windows derived `_NTITL~1.DWD` for `_NTITL~1 1.DWD` — the same name. Two files, one
directory entry. 160,151 of the 165,459 bytes differ, so these are **not duplicates** and one
document was genuinely at risk.

## The fix: create the 8.3 name FIRST

Windows only reuses a short name that is not already taken. If the real 8.3 name exists first,
the long name gets a different generated short name and **both coexist**:

```powershell
Remove-Item "<stick>\dir\_NTITL~1 1.DWD" # our copy; the source is intact
Copy-Item "<source>\dir\_NTITL~1.DWD" "<stick>\dir\_NTITL~1.DWD" # the true 8.3 name FIRST
Copy-Item "<source>\dir\_NTITL~1 1.DWD" "<stick>\dir\_NTITL~1 1.DWD" # then the long one
```

Result: both entries present, both hashes matching the manifest.

## The trap this creates for the repair path

A `--repair` pass that re-copies the "missing" file **reintroduces the collision** — copying
`_NTITL~1.DWD` onto a directory that already holds `_NTITL~1 1.DWD` simply overwrites it, which
is how the file went wrong in the first place (a "wrong hash" on one and a "missing" on the other,
which is what the first verify reported). **So: after fixing one of these by hand, re-verify
READ-ONLY.** Do not let a repair pass run against it again.

## The rule

**On FAT32, a file whose name is already a valid 8.3 short name can collide with the generated
short name of another file in the same folder, and the filesystem will silently keep one entry
while both paths resolve to it.** `Test-Path` returns True for both, so it cannot be detected that
way. It shows up as: *a file is missing from the directory listing yet present to every path
check*, and *a sibling in the same folder has the wrong hash*.

Detect it by comparing **directory listings** (not path existence) against the manifest, and check
for a sibling of the same size. Fix by recreating the true 8.3 name first. Avoid the whole class by
using **exFAT or NTFS** for customer media where the tooling allows the choice.
