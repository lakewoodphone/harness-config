**L3406 · Retry belongs in the tool when the path is idempotent - and name what makes it safe first**

**When a write path is idempotent, RETRY is the correct answer to weather - and the way to make a
fragile path usable is to make its idempotency explicit, then lean on it.** 2026-10-08: filing four
photographs onto one work order failed four times in a row - twice `P2028: Transaction already closed:
A query cannot be executed on an expired transaction ... 14440 ms`, twice `Can't reach database server`,
while a TCP connect to that same host from that same container took 153 ms and the app's own health
endpoint answered 200. Cause, from the app's own source: `RepairIntakeCasePhotoService.attachPhotos`
uploads the object to R2 **inside** a Prisma interactive transaction with a 5-second budget, and the app
host reaches both R2 and the Heroku-era RDS over the public internet. A 600 KB upload that takes one
second usually and fifteen seconds occasionally cannot live inside a 5-second transaction.

Fix chosen, and the reasoning matters more than the code: **retry, in the client, up to four times with
backoff.** That is safe only because every step of the operation is already idempotent - the intake case
is adopted by `sourceReference` (and by a unique index on `idempotencyKey`), a photograph whose sha256 is
already on the case is skipped, and `promoteToWorkOrder` on an already-promoted case returns
`orderAction: 'match'` instead of creating a second order. So a retry cannot double-write; it can only
finish. Proven the same hour: the next job that needed it succeeded on attempt 2.

The general rule: **before retrying anything, name what makes the retry safe.** If a step is not
idempotent, retrying it is a coin flip on duplicate data, and the correct fix is at the other end. If it
IS idempotent, then a client that gives up on the first transport error is choosing flakiness for no
reason - and the retry belongs in the tool, not in a human who happens to be watching.

The real fix is still owed to the app: the R2 upload should happen before the transaction, not inside
it. Recorded as such in `lpt-ops/docs/photos.md`.

Evidence: `lpt-ops/lpt_ops/photos.py` retry block; commit `d466f52`; H3388.
