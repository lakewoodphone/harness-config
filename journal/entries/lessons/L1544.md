**L1544 · Six fatal defects in one endpoint, invisible in the source: diff the wire request, and never infer a status word's meaning**

Six independent defects hid in one 30-line endpoint, and reading the code found none of them. Each had to be measured
against the live daemon; each was fatal alone. The last one is the instructive one: httpx sends no User-Agent by
default, NanoDEP rejects that with 400 USER_AGENT_INVALID, and curl always sends one — so the *archived script that
worked* and the *rewritten call that never worked* differed by a convenience the rewrite silently dropped.

The generalisable rule: when a working implementation is ported to a new client, the port can lose behaviour that was
never written down — a default header, basic auth, a slash in a path, a verb. "Same endpoint, same body" is not the
same request. When a port of something known-good fails, diff the actual wire request, not the source.

Second rule, about return values: the obvious reading of this API was inverted. `SUCCESS` on first contact and
`FAILED` on every repeat means FAILED is the already-applied signal, and an unknown serial returns HTTP 200 with
`NOT_ACCESSIBLE`. A 200 is not success, and a status word is not self-explanatory — three repeat calls on a device in a
known state is what settled it. Measure the semantics; do not infer them from the name.
