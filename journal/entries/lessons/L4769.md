## A mesh child cannot see the authority's filesystem, and its negative readings about it are fabrications

**Measured 2026-10-15 on `secratary-cloud`.** A topology probe dispatched with the mesh `subagent`
tool executed on **`ZABZ-TECH` (Windows)**, not locally. It was asked to read four paths under `/root/`.
It reported all four as absent or empty, including this startling one:

> "Remote `/root/authority.db` exists but is **0 bytes** (`-rw-r--r-- … 0 Oct 15 14:43`, mtime
> `2026-10-15 14:43:24 UTC`, i.e. created inside this session's window); output
> `Error: in prepare, no such table: waze_mdm_devices`."

**The truth, read directly on the authority in the same minute:** `/root/authority.db` is
**29,876,543,488 bytes**, mtime `2026-10-15 14:36`, and `select count(*) from waze_mdm_devices` returns 2.
`/root/personal-secretary-mvp/deploy/` also exists. Both "absences" were false.

**Mechanism.** On Windows a POSIX absolute path is not absent, it is *relative to the current drive*:
`/root/authority.db` resolves to `C:\root\authority.db`. The 0-byte file with a mtime inside the probe's
own window was created on the Windows side. So the child did not read a remote file and find it empty —
it read a file it had itself materialised, and could not tell the difference. Note the child *did*
successfully `ssh hetzner`, so it was not simply offline.

**Why this is expensive.** The failure is silent and its output looks like a legitimate measurement: an
exact byte count, an exact timestamp, a plausible sqlite error. An agent that trusted it would conclude
the company's authoritative database had been truncated, and would act on that. This is `P2477`'s shape
— a label describing what we did, not what happened — in a new place.

**The rules that follow.**

1. **`subagent` (mesh) and `subagent_local` are not interchangeable when the data is path-dependent.**
 Measured the same session: `subagent` → `ZABZ-TECH`, `subagent_local` → `secratary-cloud`. Partition
 work by **where the data is**: authority-local paths go to `subagent_local`, Windows-only repos go to
 `subagent`. Never brief a mesh child on a `/root/...` path.
2. **A negative from a mesh child about an authority path is not evidence.** Verify it on the authority
 before repeating it, and never relay it as a finding.
3. **If you must reach across, make the hop explicit** — `ssh secratary-cloud 'cat /path'` works from
 `ZABZ-TECH` and lands as root, and the nested form `ssh desktop-ts "ssh secratary-cloud '…'"` works
 from the authority. An explicit hop has an obvious failure mode; a silent path remap does not.

**Corollary for any worker report:** when a child says a path does not exist, ask *which filesystem it
resolved that path on* before believing it. `pwd` and `hostname` are part of the evidence.

## Correction to `L3937` — "every key the lock-down depends on is on Apple's deprecation path"

`L3937` overstates it. Measured against Apple's schema at `Release-v27.0` (commit `09f249a0`,
2026-09-17) by intersecting the **179** restriction keys our served profiles actually set:

| | count |
|---|---|
| keys **removed** at 27.0 | **0** |
| keys deprecated | 27 |
| keys current on iOS | 111 |
| not applicable / absent from schema | 7 / 34 |

Apple's iOS 27 enterprise note (published 2026-09-14) mentions `allowListedAppBundleIDs` — the key the
lock-down's app gate depends on — exactly once, **as a bug fix to its AirDrop behaviour.** A removed key
does not get a bug fix. `allowPhotoStream`, deprecated at 17.0, is still in the schema today.

The dated change is real but it is a *different* one: *"Legacy software update management no longer
functions in all 27.0 operating systems"* — four keys removed at 27.0, and we carry none of them.

**So the durable rule is not "deprecated means doomed".** It is: *read the schema for `deprecated` vs
`removed`, and read the release note for what actually stopped working.* The genuine gap this exposed is
that every modern replacement is **declarative**, and NanoMDM serves no declaration path (its `Caddyfile`
routes no `/declaration` endpoint) — which is a funding decision, not a deprecation emergency.

## The Waze fleet's own structure, since three different names were being used for one thing

Read from `fleet_devices` on `waze-mdm-01` (`site`, `device_group`), 71 rows, 2026-10-15:

- **the DRN fleet *is* the Waze Gemach** — a free-loan desk lending a navigation phone to a driver for
 a day. Sites `lakewood`, `monsey`, `chicago`, `baltimore` = **62 rows. No money changes hands.**
- **the LPT fleet** is the product we sell = **5 kiosks**, all `site=lpt`.
- **the shop/counter fleet** is **3 devices (DRN 2001, 2002, and 2003, an iPad)** and it is *inside*
 `site=lpt` — there is no `shop` site, which is why it kept going missing.
- 71 rows cover **70 physical phones** — DRN 21 and DRN 41 are the same iPhone.
- The gemach's ledger numbers them `WAZE0001–WAZE0045`; the MDM numbers them `DRN 1–55`. The two series
 mostly coincide and are **not the same series** (13 ledger numbers are absent from the registry).

## The fragmentation, in one reproducible measurement

```
ssh hetzner 'cd /opt/waze-mdm/profiles && sha256sum *.mobileconfig' # 28 files
cd personal-secretary-mvp/deploy/waze-mdm/profiles && sha256sum *.mobileconfig # 13 files
```
**28 served, 13 in git, 15 in no repository at all** — nine of them a single day's `waze-callblock-*`
A/B experiment from 2026-07-14 that was never cleaned up. **Two of the thirteen shared names are
deployed with different bytes than git holds, and one of them is `waze-layered-kiosk.mobileconfig`, the
lock-down profile itself.** Eleven of the 28 share one `PayloadIdentifier`. **Any rebuild from git
silently reverts the live lock-down profile** — fold the served file into git first.

This is the concrete form of `P3178` and `P3203`, and it is the reason a "single source of truth" for
this business has to record *served* as well as *committed*.
