**L2007 · A byte-pattern spot test writes a valid MBR by accident: 0x41 across LBA 0 fabricates 4x522GiB partitions - suspect the tool before the hardware when state changes between your own two observations**

Rule: a spot test that writes a repeated byte across LBA 0 fabricates a partition table, and it will look like a drive defect. Write zeros, or a pattern that cannot form a valid MBR, and always re-read the partition state after any spot write.

Evidence, 2026-09-18. Verifying two new Samsung 870 EVO 2TB transfer drives on zabz-tech-linux. The first lsblk showed both drives with NO partitions - genuinely blank. I then ran a full-capacity spot test that wrote 1 MiB of the letter "A" (byte 0x41) at offset 0. The next lsblk showed FOUR partitions on each drive, 522 GiB each. That is exactly the shape a reader would interpret as a counterfeit or a factory layout, and I started down that path before checking the bytes.

What actually happened: the MBR partition table lives at bytes 446-509 of LBA 0. Four entries of all-0x41 parse as start=0x41414141 and size=0x41414141 sectors each. 0x41414141 sectors x 512 B = 522 GiB. The kernel reported four perfectly plausible 522 GiB partitions created entirely by my test pattern. The drives were fine; I had written the table.

Confirmation method worth keeping: check whether the drive SHIPPED blank by reading the LAST 1 MiB. A factory-blank drive has zeros there, and a GPT would leave a backup header in the final 33 sectors. Both were all zeros, which proved there was never a partition table and the 4x522 GiB was mine. Zeroing the first and last 64 MiB cleared it and lsblk returned to "no partitions".

Second trap from the same session: blkdiscard does not work through this USB bridge. `blkdiscard /dev/sdc` returns "BLKDISCARD: ioctl failed: Operation not supported" even though smartctl reports "TRIM Command: Available, deterministic, zeroed". The bridge drops the ioctl, so wipe with `dd if=/dev/zero` over the first and last 64 MiB (which clears both a primary MBR/GPT and a backup GPT) rather than trusting blkdiscard.

Generalisation: when a tool you just ran changes the machine's observable state, suspect the tool before suspecting the hardware. In this case the change appeared BETWEEN two observations five minutes apart, on hardware that had just passed a health check - that ordering was the tell, and I nearly read past it.
