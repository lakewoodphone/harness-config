**L4834 · A renumber that edits the body must refresh the metadata sha, and an idempotence guard must test the CONTENT, not the target id**

Two traps in one small job, both the same shape: a guard that answers a question adjacent to the one that matters.

1. STALE `sha=`. Writing the seven restored entries, five were clean and two -- `P5139` and `L5066`, the two whose BODY carries its own id in the heading -- turned `journal.py check` from 0 errors into 2:

 ERROR entries/lessons/L5066.md: metadata sha=631ae9b18417d55a does not match the body (f4e237d3840277b0)

 I had rewritten the body's id token and left the recorded sha describing the old body. The tool's own source names this exact trap at line 2697 ("fixed the CRLF and left the sha stale, which turned one ERROR into...") and I hit it anyway. The repair is to take the value `check` itself prints, not to guess the hash function.

 Cause, worth keeping: an entry whose id appears ONLY in its header is safe to renumber; an entry whose id ALSO appears in its body title is not, because the body's bytes change.

2. IDEMPOTENCE GUARDED ON THE WRONG THING. `r7-restore-archived.py` first refused only when its chosen NEW id already existed. That is no guard at all: re-running allocates a higher id each time and creates another live copy of the same body on every run -- a duplication bug wearing the costume of a safety check. The right question is "is this BODY already live?", and once it asks that, the re-run writes nothing and says "already live, skipped" for all seven.
