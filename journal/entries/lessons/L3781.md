**L3781 · Verify a production claim with the reader, not with intent - attached as order evidence was never true**

Measured 2026-10-13 on the Ullman case (WO26101312747, Lenovo IdeaPad 3 NM-D471, order id 3073).

The lpt-hub case file for this case asserted, inside the same section that ends "Verified, not assumed", that three intake/bench photographs were "attached as order evidence" and that `lpt ticket WO26101312747` "shows ... the three photographs". Both statements were false, and the second one was labelled verified.

MEASURED through the shop's own reader, not from memory:
- `lpt photos WO26101312747` - 0 rows in `repair_intake_case_photos` in BOTH stores, 0 rows in the older `issue_intake_screenshots` path, and `orders_with_attachments` 0 store-wide on `operational`.
- `lpt ticket WO26101312747` prints "no photograph reaches this work order".
- The write ledger has no attachment operation for this order (seq 395 the create, seq 396/397/400 the three notes), and `lpt-write` has no attach command at all - its whole surface is note add, status set, total set, payment set, customer create, order create. So the sentence could never have been true. It was written because the photographs had been put in the repo, which is a different act from putting them on the order.

TWO TRANSFERABLE RULES.
1. A statement about what production shows is a measurement, not a summary of intent. Run the reader and paste what it printed. "Attached" and "committed to the repo" are not the same verb and must not be used for each other.
2. "Verified, not assumed" is a promise, and it is the highest-value sentence to re-check. Here it sat directly beside two unmeasured claims. Never let that phrase attach to anything that was not run in front of you.

WHAT WAS TRUE, AND IS UNCHANGED: the three photographs are real and their sha256 in the case file are correct - verified with `sha256sum` against `case-media/2026-10-13-ullman-lenovo-nm-d471/` in lpt-hub and `/home/zabz/phone/wo-ullman-2026-10-12/evidence/` on secratary-cloud. Only the location claim was wrong.

ALSO WRONG IN THE SAME FILE, found while correcting it: the ledger link `../../../lpt-ops/audit/writes.jsonl` resolved nowhere, because lpt-hub carries no `lpt-ops/` directory. The real ledger is `~/lpt-ops/audit/writes.jsonl` on `secratary` - which is the host `lpt-write` itself names, in its dry run, as `ledger /home/zabz/lpt-ops/audit/writes.jsonl`. Note that `/opt/lpt-ops/audit/writes.jsonl` on secratary-cloud is a DIFFERENT, stale ledger that stops at seq 377 on 2026-10-12T20:13 and contains none of the 2026-10-13 writes; a session that finds that one will conclude the day's writes were never logged.

FIXED: case file and sync record corrected and pushed, lpt-hub origin/main `d36c6acda` (verified with `git ls-remote`); production note 3185 on WO26101312747 records where the photographs actually are. The sync record had also kept the intake misread battery FRU `5B10W86937` - which is not a Lenovo battery FRU - after production note 2 had already corrected it, so a structured field was carrying a wrong identifier that the prose had withdrawn.
