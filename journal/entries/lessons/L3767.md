## A mis-pointed Core Data object-id allocator does not raise an error — it silently REPLACES the customer's rows, one per object the app creates

Follow-up to L3764, found the same evening. The merge left `Z_PRIMARYKEY.Z_MAX` at 1511 while the store held
messages at `Z_PK` 1511..19,173 — all of them the customer's recovered history. Core Data's object id IS
(entity, Z_PK) and it faults a row in by primary key, so the app's next new object does not collide and fail:
it **takes an id that already holds one of her messages and overwrites it.**

Measured on the `ChatStorage.sqlite` read back OFF the customer's iPhone 16 (2026-10-08 22:12, twenty minutes
after the app was installed, allocator eight ids into the range):

| Z_PK | what we injected | what is on her phone |
|---|---|---|
| 1512 | "these can be full color like that-…" | **empty** |
| 1513 | "No worries, thanks." | **empty** |
| 1515 | "I just started uploading products to…" | **empty** |
| 1516 | "Hi everyone! We're excited to present…" | **empty** |
| 1517 | "Hi, just following up!" | "Over 70 items available in the Prime Day sale…" |

Four messages blanked, one replaced by a different message. **Nothing raised an error. `quick_check` was `ok`.
No log said anything.** The phone has been running for five days since that snapshot.

**So the rule from L3764 is not a tidiness rule, it is a data-safety rule:** `MAX(Z_PK) <= Z_PRIMARYKEY.Z_MAX`
for every entity, every time, after any row-level write into a Core Data store. Where it is violated the
damage is silent, continuous and proportional to how long the app runs.

**And the second lesson, which cost nothing because it was a measurement rather than an argument:** the
plausible story for the customer's *"it randomly sends a piece as a reply to messages"* was a corrupted
`ZPARENTMESSAGE` — a reply attached to the wrong message, so a fragment of an old message renders as the quoted
snippet. I tested it across her source store, the store we injected, and the store off her phone:

 replies in her ENTIRE history: 9. dangling: 0. cross-chat: 0. parent-blank: 0. parent-newer: 0.
 all 9 survived the merge with their parent intact (parent DROPPED: 0).

**The plausible mechanism was false, and it took one query to know that.** A mechanism that explains the words
is not a mechanism that explains the data; go and look before it gets written into a case file.

Evidence: lpt-hub case file + run log DO-NOT-REPEAT #19 (committed and pushed to `main`);
`_scratch/kramer-reply-audit.py`, stores on `mac-mini-ts`.
