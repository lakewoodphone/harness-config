**L3417 · Chromium: an identical --app URL into a shared profile opens NO window, and MainWindowTitle cannot count windows**

Measured ZABZ-YOGA 2026-10-08, both by controlled test.

(a) RELAUNCHING THE SAME --app URL CREATES NO WINDOW. With one
 `--app=http://127.0.0.1:3099/?token=...` window open in the shared profile
 `C:\Users\ezabz\.dsh\multi-window\browser\_shared`, launching that identical command again changed
 nothing a person can see: titled windows 1 before and 1 after; msedge processes 22 before and 23
 after (the extra one is the exiting stub). Chromium hands the launch to the running browser process
 and focuses the window that is already there. A DISTINCT url - a different origin port - DOES open
 a new window (same session, 20:52: `dsh-new://open`, a new 700x440 window, proxy
 openPorts:[3200]). So any fallback that puts several windows on ONE url opens exactly one window,
 and every later click on it is a no-op that still looks successful to whatever started it.

(b) `Get-Process msedge | Where MainWindowTitle` RETURNED ONE WINDOW WHILE FIVE EXISTED. A Chromium
 browser process reports a single MainWindowTitle for the whole tree, so neither the count nor the
 title identifies a window, and a before/after test built on it cannot see a window open or fail to
 open. Counting windows needs EnumWindows + GetClassName == 'Chrome_WidgetWin_1' + GetWindowRect;
 the launcher's own windows are recognisable by their 700x440 geometry and by --window-position
 (slot 1 at 0,0, slot 2 at 700,0). Verified: 4 windows before dsh-new://open, 5 after, the new one
 at x=0 y=0 w=700 h=440.
