**L12169 · A tool that is not scheduled is not a mechanism - four wake-system defects, measured and fixed**

## The audit found four defects, and three of them were "the mechanism exists and nothing calls it"

Measured on `secratary-cloud` 2026-10-21 21:45-22:00Z. Full numbers and commands:
`docs/wake-autonomy-audit-2026-10-21.md`.

**1. A tool that is not scheduled is not a mechanism.**
`work.py due --reopen` (the only transition out of `blocked` for a date-gated item) and `work.py
resweep` (re-tests CI-billing / merged-PR / deploy / service blockers) were both written on
2026-10-21 and referenced by **no cron, no source and no script** — `grep -rn` over `/root/bin/*.sh`,
`/root/bin/sources/*.py` and `/etc/cron.d/*` returned nothing. Meanwhile `run-wake-sources.sh` ran the
READ-ONLY `work.py due` every 30 minutes and printed `8 item(s) past their revisit time` **179 times**,
the oldest 62.9 h overdue, and `lint-refs` reported `STALE=22` (blocked items citing an owner row that
is already resolved). Both were findings with no consumer.
*So: for every scheduled read, name the writer it feeds. If the answer is "the log", it is not a
mechanism.* Fixed by scheduling both and adding `sources/ledger-blockers.py`, which spends **one**
release a day on the residue and forbids the failure itself: an item may not be closed `blocked` with
the same `blocked_on` text it already had.

**2. Two different failures wore one word, and the item paid for it.**
2026-10-21 13:08:19Z and 13:08:20Z: two releases died in 13 s because the desktop's model resolver
returned no model (`model: FAIL-LOUD UNRESOLVED … HttpClient.Timeout of 8 seconds`). The dispatcher
recorded `ssh hop failed (rc=1) … but the session's out-file was recovered`, and
`_retryable_reason()` excludes that shape on purpose — so **no work was attempted and the item still
spent one of its two attempts**. A gateway outage of minutes can permanently kill items nobody looked
at. Fixed with a dedicated branch: a boot refusal now reads `the session never started: …`, is
retryable, and backs off 1800 s instead of the transport's 600 s (a fleet fault, not an item's).
*So: when two causes share a phrase, one of them is being charged to the wrong account.*

**3. A bound set at the p99 truncates good work.**
Parsing all 1231 release lines: 1149 done (median 356 s, p90 933 s), **seven successes between 1800 and
2090 s**, and **sixteen failures at 2100-2104 s** whose own logged cause is "the bound cut the session
while it was working". The envelope was 1800 s (hard 2160, runner 2100) — i.e. the wall sat inside the
distribution it was supposed to sit above, and a timed-out shift is re-run from zero after a 600 s
retry. Raised to 2700 s (hard 3060, runner 3000, proven from the dispatcher's own `--dry-run` plan
against a throwaway store copy).

**4. A label that cannot separate two states is not a reading.**
`autonomy-status.sh` printed `dispatcher heartbeat 10.2 min` for a file written **when a release
happens** — so a quiet, correctly gated dispatcher and a dead one printed the same number. It now says
`last release 2.3 min ago | fan-out tick 0.5 min (LIVENESS) | sources 20.0 min`.

**5. Unbounded staging.** 4,944 files / 237.5 MB of `wake-prompt-*` / `wake-out-*` on ZABZ-TECH
(`~300/day`) that the dispatcher's own log line says "need no cleanup". `wake-prune.ps1` +
`wake-staging-prune.sh`, 30-day retention, at most weekly; first run removed 28 files older than
2026-09-21 (1.9 MB). The content duplicates the archived session.

**Verified end to end, not assumed:** the new flag `#1415 ledger-blockers:20261021` was filed
21:58:11Z, released 21:59:03Z, claimed with `attempts=1` — 52 seconds from filing to a session on
ZABZ-TECH.
