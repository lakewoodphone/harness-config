**L1601 · verify-secret-move.py - the tested tool for proving a secret moved layers unchanged**

Adds scripts/verify-secret-move.py, a tested version of the one-off helper used on waze-mdm-01 today (see L1599 and L1600 - this entry points to L1600 rather than replacing it).

WHY A TOOL AND NOT JUST THE LESSON: L1600 records five traps, and every one of them is a check I had to get right under time pressure on a live server. Re-deriving them next time is how the fourth trap gets missed. The tool encodes them:

 envval <.env> KEY -> sha256 + 12-hex fingerprint of a dotenv value
 ctrenv <container> KEY -> same for the value the container actually holds
 fp <file>|- -> distinct/occurrence count + fingerprint of the bcrypt hash in a config or from stdin (Caddy admin API: wget -qO- http://127.0.0.1:2019/config/)
 composecheck <.env> -> MATCH/MISMATCH against `docker compose config --format json`, unescaping the $$ rendering
 guardtest <.env> -> exits 0 only if compose REFUSES to render with the variable removed
 stdinsha -> sha256 of stdin

It prints no secret value ever - comparisons are sha256 equality, output is MATCH/MISMATCH and a 12-hex fingerprint safe to quote.

VERIFIED, not assumed: run against the live state of waze-mdm-01 on 2026-09-15 after the credential move - envval and ctrenv both returned sha256 0090e2ba79dc56315978dd9320b393e4e6e223a65cc40ededb31fb62a95b9e9d, the running Caddy config fingerprinted fp=0090e2ba79dc (identical to the pre-change fingerprint, so the same password), composecheck MATCH, guardtest fired. One bug was found and fixed on first live use (cmd_envval unpacked a stray format argument); it is now exercised end to end.

CAVEAT: `guardtest` hardcodes the variable name DASHBOARD_PASSWORD_HASH and the caddy service; generalising it waits for a second real client.
