**L3819 · A shared default is a blast radius; and ask the owner in plain prose, not the question tool**

**L · A shared default in a shared builder is a blast radius, and reading the source does not show it**

Flipping `force_wifi_power_on` on `make_restrictions_payload()` looked like a one-line change. That
function is called by **five** profile builders, so the "obvious" edit would have also changed:

- `mdm-quarantine` (a containment payload for a device pulled out of service)
- the soft kiosk
- the owner's personal-phone profile

None of those are the Waze kiosk fleet, and none of them were in scope. The decision was about
customer kiosk units. Flipping the shared default would have shipped two unrequested policy changes
to other device families in the same breath.

**The rule: when a decision applies to ONE artifact family, do not express it by changing a default
that other families inherit. Keep the shared default, pass the value explicitly at the call site.**
And make the caller pass it explicitly too (`generate-profiles.py` passes
`force_wifi_power_on=False` with the reason), so a later change to the shared default cannot silently
re-pin the fleet.

**How it was caught, and the generalisable part: by building each artifact and reading the key back,
not by reading the source.**

 make_waze_layered_kiosk_profile(...) forceWiFiPowerOn = False
 make_waze_soft_kiosk_profile() forceWiFiPowerOn = True
 make_mdm_quarantine_profile() forceWiFiPowerOn = True
 make_owner_personal_phone_profile() forceWiFiPowerOn = True

A source read said "I changed one line in one function". A build-and-read said which four profiles
moved. **When you change a value in a shared code path, enumerate its callers and then prove
behaviour by generating each output** - for MDM that means build every profile and read the key.

Evidence: commits `ee3c5e979` (the unblock) and `e03037362` (this correction) on
`fix/waze-wifi-bluetooth-switching-20261014`; `wifi-bluetooth-switching.md` §6b.

**L · `ask_user_question` is unusable on the owner's phone - ask in plain prose**

The owner, 2026-10-14: *"Remember you can't use the ask a question tool on iPhone. I can't see the
whole question with all your options So just ask it to me as plain text."*

The tool rendered a truncated question with unreadable options. He answered anyway, but he had to
explain the tool was broken to do it. Rule for this estate: **when the question is for the owner,
write it as plain text in the reply** - the question, the consequence of each choice, and the
recommendation as a sentence. Do not use `ask_user_question` for owner decisions. This is the same
lesson as the money-rendering one (a pair of dollar signs becomes a formula): the transport renders
some things badly, and the artefact has to arrive readable rather than merely be sent.
