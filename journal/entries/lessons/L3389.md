**L3389 · A forced staleness ceiling defeats the journal's coverage test**

**The MCP search wrapper passed `--max-age 1200` on every call, which silently defeated the
journal's own freshness design.**

`fa journal` decides staleness two different ways on purpose: with **no** `--max-age` it compares the
index's entry count against the tree on disk and the newest entry it covers (**content coverage**);
with an explicit `--max-age` it falls back to an **age test**. The comment in the source says why the
age test is wrong as a default: the journal index "is written when the journal CHANGES and is
otherwise left alone", so a healthy but quiet index always looks old.

The wrapper always passed the flag, so it always forced the age test. Measured live: `ps_search
what=journal` returned `STALE: the index is behind` with `stale:true` at `index_age_s` 2000-2218,
while the index held **3157 of 3157 entries - complete coverage**. The CLI, with its own default,
said `journal index current (3157 entries)`. A false alarm that fires whenever the journal is quiet
for 20 minutes - exactly the "false-alarm machine" the source comments warn about.

**Rule: when a caller passes a parameter "to be helpful", check whether omitting it is itself the
feature.** The wrapper now omits `--max-age` unless the caller sets it.

Related, same file: it read only `rc == 3` and returned `ok:true, "(no hits)"` for exits **1, 2, 4
and 5** alike - so a refusal ("NOTHING was searched") arrived as an empty result, and the stderr that
explained it was captured and never looked at. Proved with a stub backend: exits 4, 5 and 1 all
returned `{"ok": true, "result": "(no hits)", "stale": false}`. It now returns `exit_code` and
`searched`; `searched:false` means a refusal.
