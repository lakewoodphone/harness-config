**L2792 · Setting TEMP on the engine changed the temp of every tool it spawns - and my cleanup filter still described the old intent**

Fixing the ENGINE's temp on 2026-09-25 changed the temp of the whole TOOLCHAIN, and I did not see it
for three days.

The crash fix was: stop the engine's spill directory living in %TEMP%, because Windows cleanup
deletes %TEMP% out from under a running process. The obvious implementation is to set TEMP/TMP for
the engine process to DSH_HOME/tmp. What I did not follow through: the engine is the ANCESTOR of
every build and test an agent runs, so children inherit TEMP, and so do their children. Measured on
ZABZ-YOGA 2026-09-28, a few hours in: DSH_HOME/tmp held hundreds of directories belonging to tools
with nothing to do with DSH -- MSBuildTemp, NuGetScratch, VBCSCompiler, robolectric-*, pytest-of-*,
NativeImage-*, hsperfdata_*, WinGet, and dozens of bare tmp*.

Two failures stacked, and the second is the one I keep repeating:
1. I reasoned about the process I was fixing and not about its DESCENDANTS. An environment variable
 set on a parent is a change to every process it will ever spawn.
2. The pruner I wrote for that directory matched only `dsh-spill-*` / `dsh-subprocess-*`, so
 everything else accumulated forever -- a pile created by the fix, guarded by a filter that
 described the fix's ORIGINAL intent rather than its actual blast radius. Same shape as the 900
 health-*.log files I had criticised hours earlier.

RULES
1. When you change an environment variable on a long-lived parent, enumerate what that parent
 spawns before you call it contained. "The engine's temp" was never the unit of change.
2. A cleanup filter must describe what the directory ACTUALLY receives, not what you intended to put
 there. If a fix widens a directory's population, the cleanup widens with it in the same commit.
3. The safety analysis survives the widening and must: only directories, only directly under the
 target, kept while ANY entry inside was touched in the last 12h, kept unconditionally if a file
 name embeds a LIVE pid, and age consulted last. Filenames of build tools carry no pid, which is
 why the activity test exists as well as the liveness test.

ALSO, and separately useful: a "crash" that is not one. After the owner rebooted, TWO engine
launches raced; one bound 127.0.0.1:3099 and the other died with EADDRINUSE, exit 1, writing a
5 KB stack trace into 3099-*.err.log and marking the launcher task result=1. The watchdog already
recovers ("3099 answers now - treating it as up"), so nothing was broken -- but a port collision
wore the costume of an engine crash, and I spent a diagnostic pass hunting a crash that does not
exist. When a machine reports "the engine crashed", check for EADDRINUSE BEFORE reading a stack
trace as a fault: a start race is the cheapest explanation and the easiest to rule out.
