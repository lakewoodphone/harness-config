**L3339 · Before fanning out read the node table: Windows mesh rows are file-tool-only, and ssh.exe on ZABZ-TECH is not an orphan**

**L3338 · Before fanning out, read `packages/plugin-remote-fanout/lib/nodes.js` — the Windows mesh rows are file-tool-only, and it says so in the file.**

**Measured 2026-10-05 (ZABZ-TECH), by me, the hard way.** I dispatched two mesh children with a shell-heavy brief. The
engineering-analysis child (file tools only) delivered. The transcript child needed `ssh` to the authority and a
Whisper call; it wrote a long report saying its shell was dead — every `pwsh` call failing *before execution* with
`Windows ACL temp root must be outside the workspace: workspace=C:\Users\ezabz; temp=C:\Users\ezabz\AppData\Local\Temp`
— could not run `git`, could not push, and then its own transport died with `the remote one-shot exited 1 and produced
no final message`.

**This was not news.** `harness-config/packages/plugin-remote-fanout/lib/nodes.js` lines 71-92 carry the measurement and
the remedy, written earlier the same day:

- workspace = the home directory (what `NODES['zabz-tech'].cwd` sets, `C:/Users/ezabz`): the sandbox needs the temp
 root *outside* the workspace, but `<home>/AppData/Local/Temp` is *inside* it → a child with **no working shell**.
- workspace = the code root: the shell works, but profile boot writes `~/.dsh/profiles/node_modules`, now outside the
 workspace → the child dies before it starts (errno -4094).
- **The fix is not a `cwd` choice**: relocate the child's shell temp root outside the home directory, then verify with
 `doctor` and a real probe turn. Until then: **treat the Windows rows as file-tool-only (reading, globbing, searching
 are unaffected) and run anything needing a shell on this machine's own session.**

**The rule.** Fan-out is still right; the *partition* has to respect the node. Read the node table before writing the
brief. A child on a Windows row can write a document into a checkout and nothing else — so never give it a brief whose
definition of done includes git, tests, a network call through a shell, or a push. I lost ~40 minutes and one child to
a documented trap; the work it was meant to do took me one script.

**Also measured in the same hour, and worth not repeating:** the `ssh.exe` processes visible on ZABZ-TECH are **not
orphans**. Their parents are `node.exe ...\@deepseek-ai\dsh\lib\bin.js web --port 3099` (the engine's own transport)
and live `powershell.exe` calls, and they churn every few seconds. I killed four by PID before checking the parent, and
two of them were in flight. **Identify the parent before killing a process** (`Get-CimInstance Win32_Process` →
`ParentProcessId`); a `ssh` child on this box belongs to something alive.
