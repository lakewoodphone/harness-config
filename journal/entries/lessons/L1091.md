**L1091 · A repair has to go through the same path a write does**

`check --fix` rewrote the one CRLF entry with a raw text replace and did not recompute the `sha` recorded in its metadata line. The next `check` therefore reported a stale sha on a file the tool had just "fixed": one ERROR turned into another, and the repair looked like damage. Re-emitting the file through the same `entry_bytes` a write uses - parse, canonical heading, recomputed sha, LF - fixed both in one pass.

Rule: a repair is a write and must go through the write path. Any repair that edits bytes directly will drift from the invariants the writer maintains, and the field it forgets is the one nobody checks until it does.
