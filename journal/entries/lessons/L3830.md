## Two "empty result" readings that both meant "wrong query", measured 2026-10-12 on the 300DDR sweep

Both of these look exactly like *"there is nothing there"* and neither one is evidence of absence. Together they
took a live vendor thread from invisible to fully read, so they are worth never rediscovering.

### 1. `gmail_search` silently searches SOMEBODY ELSE'S MAILBOX unless `account` is passed

```
ps_action gmail_search {"query": "from:300dollardatarecovery.com newer_than:14d"} -> 0 results
ps_action gmail_search {"query": "300dollardatarecovery", "max_results": 40} -> 0 results
ps_action gmail_search {"query": "helpdesk3"} -> 0 results
ps_action gmail_search {"query": "in:inbox"} -> 10 results, all to chevedy@gmail.com
ps_action gmail_search {"query": "newer_than:2d", "account": "lakewoodphoneandtech@gmail.com"} -> 10 results, incl. today's lab mail
ps_action gmail_search {"query": "from:300dollardatarecovery.com newer_than:12d", "account": "..."} -> 18 results
```

**The default `account` is `primary`, and `primary` is not the shop's mailbox.** Three queries returned a clean,
confident, empty answer about a mailbox that does not contain the vendor at all. The tell was that `in:inbox`
returned a family Gmail account's newsletters.

**Rule: every `gmail_search` and `gmail_read` on shop business passes `account: lakewoodphoneandtech@gmail.com`
explicitly.** A zero from a search whose account you did not name is **not** a negative; it is an unanswered
question. Worse than a plain error, because it reads as a fact.

### 2. `tools.usps.com` answers this fleet has HTTP 403

```
web_fetch https://tools.usps.com/go/TrackConfirmAction?tLabels=9334620845500046516968 -> empty
playwright same URL -> Page Title: "Access Denied", HTTP status: 403
```

So **parcel position cannot be read from the tracking page at all**, from any machine here. It has to come from
the mailbox's own USPS notices plus the Informed Delivery daily digests:

- `USPS Tracking <auto-reply@tracking.usps.com>` — out-for-delivery and expected-delivery notices, with the
 tracking number in the subject line.
- `USPS Informed Delivery <USPSInformeddelivery@email.informeddelivery.usps.com>` — *"You have N inbound
 package(s) arriving soon"*, one per day. **A run of zero-package digests is the real signal that a parcel has
 not landed**, and it is only trustworthy once every package the other digests *did* count has been accounted
 for by name.

**And a missing delivery notice is not proof of non-delivery either** — USPS does not always email. State the
provenance: *"no delivery notice in the mailbox and the 10-10 and 10-11 digests both read 0 packages"* is a
reading; *"it has not arrived"* is a claim the inbox cannot fully support.

## Corollary that cost an hour: a vendor's auto-notice is not always what it says on the tin

300DDR sends the **same** *"Please confirm that you received our shipment and that it's okay to delete our
backup"* body about a week after every shipment. It reads like a request for information. **It is a
backup-deletion clock**: the notice itself says that silence for 14 days is taken as confirmation and the clone
is deleted. So it is not a signal that something is wrong, and not replying is not damage — but the reply is the
only cheap way to keep a second copy of an unrecovered-by-us raw image. Classify it by what it does, not by what
it asks.
