**L12239 · LPT: a customer diagnostic document, the cash-payment write that does not exist, and the Gmail send path**

Three things measured 2026-10-21 while answering "pull up the Semah case, they paid cash, they want a document about the PC".

1. A CUSTOMER-FACING DIAGNOSTIC DOCUMENT DID NOT EXIST, and there is no prior art for one.
lpt-hub/docs/customer-operations holds SOPs, case files, templates for lab forms and delivery READMEs,
but no generator or template for a report written for a customer's insurance company, and FLOWS-INDEX
has no row for it. Built once: HTML, then `msedge --headless --disable-gpu --no-pdf-header-footer
--print-to-pdf` (Edge is the only PDF rasteriser on the Windows nodes; PyMuPDF in system python gives
page counts and preview PNGs, which is how the PDF was actually looked at before it went anywhere).
Letterhead facts come from phone-and-tech-full `frontend/src/brand/brand-assets.ts` BRAND_CONTACT
(Lakewood Phone & Tech, 1001 W Kennedy Blvd Lakewood NJ 08701, (732) 655-2355,
info@lakewoodphoneandtech.com) - that file is the canonical shop identity; do not retype an address
from a case file, several of which carry the 08701-1264 ZIP or a different phone.
First render stranded the disclaimer on a third page; @page margin 15mm with body 10pt/1.36 got it to
two clean pages. Source: `_scratch/semah/diagnostic-report.html`, output
`_scratch/semah/Semah-Diagnostic-Report-WO26101812753.pdf`.

2. NO TOOL IN THE ESTATE CAN RECORD A CASH PAYMENT. That is a missing write, not a wedged one.
`lpt-record-payment` requires `--stripe-charge ch_...`; `lpt-write payment set` requires the same.
Both are Stripe-shaped, so a counter cash sale has no path into `payment_transactions`. Measured
consequence: the owner took 95.96 cash, handed over the laptop and the data stick, and production still
read paymentStatus PENDING / total 95.96 / status AWAITING_APPROVAL with zero SUCCEEDED payments. The
one payment row, 3425, is status PENDING with metadata `source: owe_notice` - the online pay-link
placeholder, which is not money. Never read a PENDING row as a receipt, and never let a cash sale sit
unrecorded because the tooling only speaks Stripe: surface it to the owner as a defect.

3. THE EMAIL SEND PATH THAT WORKS, from the authority, verified by message 1a15f9e4c2710820.
`cd /home/zabz/personal-secretary-mvp && PYTHONPATH=/home/zabz/personal-secretary-mvp
./.venv/bin/python3 <script>`, importing `app.config.settings` and
`app.services.gmail_service.send_message(settings, to=..., subject=..., body=..., account=..., attachments=[{'path','filename','mimetype'}])`.
Three traps, each hit for real: (a) a script run from /tmp cannot import `app` at all - ModuleNotFoundError
- so PYTHONPATH is not optional; (b) `app.services.shadow_outbound.is_mock_outbound_enabled()` returns
True when MOCK_OUTBOUND_COMMS=True and send_message then returns `{'id': 'msg_mock_shadow'}` with ok=True,
so check that flag before sending or you will report a send that never happened (the module is
`shadow_outbound`, not `mock_outbound`); (c) the From header reads `info <info@lakewoodphoneandtech.com>`
even though the account is lakewoodphoneandtech@gmail.com, so a claim about the from-line must be read off
the message header, not off the account name. Read the sent message back with
`users().messages().get(userId='me', id=..., format='full')` and print To, Subject, labelIds and the part
list - that is the only way to know who it actually went to.

4. PowerShell CRLF bites `send-lpt-sms.py --message-file`. `Set-Content -NoNewline` still ends the line
CRLF, so the file arrives with a trailing CR (`cat -A` shows `^M$`). `sed 's/\r$//'` did not strip it;
`tr -d '\r' < f > tmp && mv tmp f` did. Verify with `cat -A` BEFORE the send, not after.
