# A stalled TASK is not a stalled JOB: one stale open row invented a customer status and asked the owner to send it

**Rule.** When a system infers "the work is not done" from "a tracker row is not closed", it will
eventually write that inference into a customer-facing message. Measured 2026-10-14 on LPT case #4485
(Felder, Seagate BUP Slim 2TB data recovery):

- The recovery **completed 2026-06-25** — exFAT boot sector rebuilt from the intact backup boot
 region, MD5 `2f7ebd59adb238bcf2361060a81303e4` verified, 19,122 files / 271 GB rsynced to a
 Corsair SSD. Case file `closed`, order `WO26082712689` `READY_FOR_PICKUP`, customer told and he
 agreed to proceed.
- **Two twin tasks were created 16 seconds apart** (`4485`, `4486`). `4486` was closed that day;
 **`4485` was left open** and sat `in-progress` for 111 days.
- The stall detector fired `CUSTOMER STALL: #4485` on 2026-09-15, 09-22, 09-29, 10-06 and 10-13 —
 five times — because the *task* was open, not because the *job* was unfinished.
- On 2026-10-14 it escalated to `OWNER APPROVAL: Send status-update SMS to Felder re case #4485 —
 110 days`, and the drafting agent — which knew only "stalled 110 days" and never opened the case
 file — composed a customer message saying *"recovery on this drive has not progressed… that's on
 me"* and offering to **return the drive as-is**.

**The second, worse half.** Resending the same approval **regenerated the draft each attempt**. Three
texts went to the owner: one saying nothing had progressed, and one claiming the raw image had just
finished and a file-system rebuild would complete "tomorrow afternoon". They contradict each other.
The owner could have approved one message and a different one reached the customer — the exact hazard
`docs/outbound-comms-hard-stop.md` exists to prevent, arriving through the approval mechanism itself.

**What a false stall signal costs, concretely:** a fabricated claim about a customer's data, an
approval request built on it, five wasted escalations over a month, and 111 days of a finished job
reading as abandoned.

**Apply this.**
1. **Never derive work status from tracker state alone.** Ask the record that owns the work (case file
 and order) and make the tracker row cite it. A closed twin and an open sibling is the signature.
2. **A generic status must not be read as a signal.** `READY_FOR_PICKUP` is where **420 of the shop's
 orders** rest; it is a terminal resting state, not a queue. Check the population before treating a
 status as meaningful.
3. **An approval that regenerates its own payload is not an approval.** The body the owner approves
 must be frozen and sent byte-identical. Anything that re-composes at send time has to be fixed
 before it is allowed to ask for a yes.
4. **Write the correction where the next reader looks**, and name the stale artefact that caused it, so
 the same row cannot re-derive the same falsehood.

**Fixed:** task `4485` closed and false approval `28536` cancelled (both with explanatory notes);
production notes `3190` (WO26082712689) and its twin on `WO26082712651`; both lpt-hub case files
corrected (`f68f796a`, published as branch `docs/felder-case-correction`). The money is genuinely
**unverified** — no `payment_transactions` row exists and cash leaves no bank row — so `payment_state`
is `unknown`, not `uncollected`.
