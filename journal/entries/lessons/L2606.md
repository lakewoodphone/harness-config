**L2606 · A stale generated Prisma client fabricates backend type errors (and had earlier hidden a real one) - regenerate before believing any backend typecheck result**

Measured 2026-09-25 on ZABZ-YOGA, twice in one session, in opposite directions.

WHAT HAPPENED
1. `pnpm --filter phone-and-tech-backend typecheck` failed with
 `error TS2353: 'forwardAttemptedAt' does not exist in type LaptopPreferenceUpdateInput`.
 The schema HAS the field (`forwardAttemptedAt DateTime?`), the migration
 `20260925130000_add_laptop_preference_forward_markers` exists on disk, and the service code is
 correct. **The generated Prisma client in that worktree was stale** - `forwardAttemptedAt` had
 ZERO hits in `node_modules/.pnpm/@prisma+client*/node_modules/.prisma/client/index.d.ts`.
 Fix: `cd backend && npx prisma generate` (5.6 s) then typecheck exits 0.
2. The opposite had already happened earlier in this same session: a stale client HID a real
 schema/DB drift so typecheck was green while a query died at runtime.

THE RULE
**A backend typecheck result is only trustworthy if the generated Prisma client was regenerated
after the last schema change.** `backend/scripts/ensure-prisma-client-for-typecheck.mjs` SKIPS
regeneration when it believes the client is current, and a worktree that was created from a base
which later received a schema commit will hold a client from before it. So:
- When a backend typecheck error names a *field that the schema declares*, regenerate before
 believing it. Do not "fix" the code.
- When a backend typecheck is GREEN in a worktree whose base is behind `origin/test`, do not trust
 it either - a green result can be a stale client agreeing with stale code.
- The cheap, deterministic move for an integrator worktree is `npx prisma generate` once after the
 first merge, then typecheck. It costs 6 seconds and removes a whole class of phantom failures.

ALSO MEASURED, same session: `pnpm --filter phone-and-tech-frontend typecheck` fails on a CLEAN
`origin/test` checkout with `TS6305: Output file 'frontend/src/lib/shop-closures.d.ts' has not been
built from source file ...` because `frontend/tsconfig.json` is `composite: true` with a reference to
`frontend/tsconfig.node.json` (which includes `vite.config.ts` and `src/lib/shop-closures.ts`), and
the referenced project's emitted `.d.ts` files are not tracked and not built by `typecheck`.
`pnpm build` passes because it builds references first. Fix: `cd frontend && npx tsc -b
tsconfig.node.json`, after which typecheck is clean. Two independent agents hit this and both spent
time proving it was not their code.
