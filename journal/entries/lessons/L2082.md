# Stripe live-mode events cannot be re-delivered through the API, and the filter app's billing is unlinked end to end

Measured 2026-09-20 ~08:35Z by a mesh child working on the Hetzner host `lpt-apps-01` (2.28.33.58).

TWO FACTS THAT CORRECT A STANDING OWNER-QUEUE ROW (it was #115, and its recommendation was wrong).

1. **`POST /v1/events/{id}/retry` refuses live mode.** All four attempts returned HTTP 400,
 `{"error":{"message":"You can only retry Events in test mode"}}`. There is no API path to re-deliver a
 live-mode event; the `stripe` CLI is not installed on that host; the only route is the Stripe Dashboard
 -> Developers -> Webhooks -> endpoint -> event -> **Resend**, in live mode, one at a time. Any plan that
 says "replay the events via the API" for live mode is wrong before it starts.

2. **The endpoint being healthy was never the problem.** Re-posting the true event JSON with a valid
 signature (HMAC verified - a bad signature is 401, these were 400) returned
 `{"detail":"Stripe event does not include metadata.tenant_id"}` for all four. The handler
 (`/opt/filter-broker/server/app/billing.py:545-549`) HARD-REQUIRES `metadata.tenant_id`, and every
 metadata bag on both customers, both subscriptions, both subscription items, the price and both
 invoices is **empty**. So the 27x400 in the delivery log is consistent with payload rejection, not with
 the "transient signature failures during the 09-15 key roll" the row asserted.

3. **The filter app has no tenants at all.** Deployed DB `/opt/filter-broker/server/data/broker.sqlite3`
 in container `lpt_filter_ai_api`: `billing_provider_events` 0 rows, `tenant_billing_state` 0 rows,
 `tenants` 0 rows, `admin_actions` 0 rows. So even with a tenant_id the handler would 404
 (`billing_provider.py:110-118`, "Unknown tenant_id"). **This integration has never successfully
 processed a single event**, while Stripe is charging two live customers $11.00/month each
 (`cus_UtGnay57jGv70Y` "avrohom newman", `cus_UoUJNy50JY7HbJ` "mrs greenwood", both `livemode=true`,
 both invoices `status=paid`).

It IS at-least-once safe on the rare chance a delivery does get through: the store short-circuits on a
seen event id (`storage_sections/billing.py:259-267`, plus `billing_provider_events.event_id` as PRIMARY
KEY) and the only state written is a snapshot upsert keyed by `tenant_id` with no counter and no amount
column, so re-delivery cannot duplicate a row or double-count revenue.

**Where the filter app actually lives** (a topology fact worth not rediscovering): NOT on secratary.
secratary has no docker, no postgres, no filter unit, and its tunnel serves only
ai/api/dialer.abletelsolutions.com. The filter app is the Docker HA pair `lpt_filter_ai_api` /
`lpt_filter_ai_api_b` on **lpt-apps-01**, source `/opt/filter-broker/server`, SQLite at
`/opt/filter-broker/server/data/broker.sqlite3`. A rollback point was taken before the attempt:
`/root/filter-broker-pre-replay-20260920T083548Z.sqlite3`, md5 `2a9826e47681c27e1c5f415bcf58dfdd`.
