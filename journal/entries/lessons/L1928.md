**L1928 · Never build a commit on a ref you have not just read -- a journal append reverted origin/master by 1249 paths**

**THE RULE: never build a commit on a ref you have not just read, and never let a writer move
a shared branch.** Two failures on 2026-09-17, both silent, both exit 0.

**1. A journal `append` reverted the fleet's `origin/master`.**
`journal.py append` had been given an inline claim-and-push, so recording a journal lesson
pushed a commit. The commit was `79efb088`, parent `53cf517`, and its diff against its parent
was **2,425 files changed, 1,176 remaining -- 1,249 paths deleted, every one of the 1,728
journal entries gone.** It exited 0. Nothing looked wrong.

Mechanism, and it is the transferable part: the parent COMMIT was resolved from the
just-fetched remote tip, but the parent TREE was resolved from the mutable local name
`refs/remotes/origin/master`, which in that worktree was **622876e -- 13 commits behind** and
pre-dating the whole 107 convergence. So the claim commit's tree was not its parent's tree, and
a commit whose tree is not its parent's tree IS a mass deletion. Measured:

 622876e tree : 36ec672cde068fc005ca13c42e9b095b0805616f <- what the tree was built from
 79efb088 tree: db4298514a11547d6c3aac7f88c9cff19b44696a <- what was committed
 53cf517 tree : 5684ffdb0f294fa2737bb9716844d144581c030c <- what the parent holds

Restored the same evening with the owner's explicit authorisation for that exact command:
`git push --force-with-lease=refs/heads/master:79efb088... origin 53cf517:refs/heads/master`
(a plain push is refused as non-fast-forward; `--force-with-lease` naming the exact old value
is what makes a restore safe). Content-verified afterwards, not just hash-verified: 1,728 .md
entries under `journal/entries/` and `journal.py check` = 0 errors, matching the figure the 107
convergence recorded.

**The fix, and it is a separation rather than a patch.** `append` now writes LOCALLY and is
incapable of moving any ref -- proved by reading the remote ref before and after three appends.
Publishing is a separate, explicit command. `journal/tools/verify-alloc.py` asserts this
directly, so a future change that reintroduces an automatic push fails a test.

**2. The generalisation, which is what makes it a lesson rather than an incident report.**
This is the same class, in a sixth costume: **a value read from a name that can be stale while
the thing that matters is read from a name that is current.** The others, all measured before
this one: five contested ids git called clean because it compared the working tree against an
unchanged upstream path; 23 entries that existed in no commit because an untracked file is not
a committed one; `--dump-config` returning 0 locally and 1 over ssh; and the 107 convergence's
own near-miss, where a deletion upstream had never touched would have been honoured silently.
The rule that covers all six: **prefer an immutable identifier (a commit hash, a blob id, a
sha256) over a mutable name, and when they must be mixed, resolve the whole unit from the same
reading.**

**3. When a mechanism is a safety mechanism, its failure must be loud.**
Three separate git plumbing calls failed silently while this was being built, each producing a
working-looking result that could have shipped:
 * `git mktree` refuses an entry whose name contains a slash (`fatal: path ...? contains
 slash`) -- a nested path needs one call per level;
 * a temporary index (`GIT_INDEX_FILE` + `read-tree` + `update-index --index-info` +
 `write-tree`) SILENTLY DROPS the new file: `update-index` prints `Ignoring path ...` and
 `write-tree` returns the parent tree unchanged, so a commit lands, exits 0, and does not
 contain what it was supposed to;
 * `git_max()` returns a `(number, rev)` tuple, and passing it into `max()` raised a TypeError
 inside a guarded call -- the reservation was computed and then ignored, and two machines
 reserved the SAME window while every individual call looked correct.

**4. The lock leak was TWO bugs, and the second only appeared after the first was fixed.**
`release_lock` proved ownership with `token in _rl(lock)`, and on Windows `msvcrt.locking` makes
the locked byte range unreadable from any other handle, so `_rl` raised PermissionError, the
bare `except OSError` turned it into `""`, and the test was False for EVERY command -- `questions`,
`import-legacy`, `index`, `state`, `append` all leaked `journal/.lock`. Fixing the read was not
enough: `os.open` takes no FILE_SHARE_DELETE, so the open HANDLE blocks the unlink, and
`unlock, then unlink` still fails with WinError 32. Only `unlock, close, unlink` works.
`selftest` 239 of 240 -> **240 of 240**.
