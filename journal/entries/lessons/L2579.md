**L2579 · The first logged-in walk of the staff console found a 500 on the customer page that four green test suites could not: orders.estimatedCost does not exist in EITHER database**

2026-09-25 ~04:05Z. The first time any session has walked the staff console as a logged-in user on the
test site (seeded admin `admin@test.com` / `password123`; the SPA keeps a session, so /login lands on
/work-orders). It found things no test had.

VERIFIED WORKING, live against the test database
- Left nav renders exactly Work Orders + Customers + Waze (ADMIN); Settings is in the header; nothing else.
- Work Orders hub: real tickets, "41 open / 2 ready for pickup / 20 awaiting parts", filters, per-row actions.
- Counter customer search: typing `8483291566` returned **1 MATCH** - "mr david - 8483291566, no email on
 file, 1 open work order, last in 9/3/2026" - i.e. phone match with any formatting, with enough on the
 card to disambiguate. Clicking it opens /customers/2610.
- Customer page: portal account block works and is honest ("Passwordless account, account #1223, re-send
 email/SMS invite, revoke sessions, disable access").
- **The transcript fix works end to end.** On /customers/2431 the coverage line moved from "32 call(s)
 have no transcript text" (before the fix) to "**10** call(s) ... have no transcript text" - 22 of 32 now
 count - and expanding a call renders the real transcript: `Dialpad call (inbound, 20.476132s)`,
 `[Dialpad ASR]: Eliyahu: Hello. ...`, `[Recording]: ...`, then a `Transcript` block. The text itself is
 Dialpad ASR noise (`ai_csat_reboot_ineligible`, `call_purpose_category`) - the plumbing is right, the
 source quality is Dialpad's business.

FOUND BROKEN, and this is the value of the walk
1. **The customer page's work-order list was 500ing** -
 `Invalid prisma.order.findMany() invocation: The column orders.estimatedCost does not exist in the
 current database`. The consolidation migration dropped `estimatedCost`/`actualCost` from `orders` and
 left `total`, but `prisma/schema.prisma` still declares both, so ANY query naming them dies.
 **Measured: neither column exists in PRODUCTION either** (information_schema, 2026-09-25). This is not
 a test-only problem, and it is one `findMany` away from any other surface that names them.
 Fixed where it was found: `customer.service.ts`, its summary type, the page's local type and its amount
 fallback, and `customerPortal.ts`'s `getMyOrders` select + mapper (the same drift, one customer click
 from a 500). `backend/src/services/work-orders/orders-schema-compat.ts` and
 `work-order-total-resolver.ts` exist precisely to handle this drift - the customer path had bypassed them.
2. **Two search boxes on one page.** `/customers` renders the new counter search AND the legacy table
 search ("Search customers by name, email, or phone...") side by side. Exactly the "too many things"
 pattern the owner complained about; not yet fixed.
3. The transcript note claimed "the conversation is not stored in this console" while 22 transcripts were
 on screen. Rewritten to distinguish none/some/all, with `callsOnRecord` and `callsWithTranscript` now
 in the coverage payload.

THE RULE THIS REINFORCES: **component tests cannot see a runtime Prisma error.** Every gate in this session
was green through four merges while the customer page's work-order list was failing on a missing column,
because the tests mock the DB. A logged-in browser walk is not a nicety; it is the only thing that catches
schema drift.
