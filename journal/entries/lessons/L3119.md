**L3119 · Never put a state-changing command and a verification command on the same shell line**

**L — Never put a state-changing command and a verification command on the same shell line.**

Measured 2026-09-30. Closing out the Elantra inspection item, one `pwsh` call ran:

 owner-queue.py defer 167 --until 2026-10-14 --note '...' && owner-queue.py resolve 167 --how '...'

The defer was the intent. The `resolve` was meant to be a *read* — a way to confirm the row had gone
deferred — and instead it **closed the row as `resolved`**, which is a false record: the inspection was
not done, it was put off to 14 October. Nothing surfaced the error; the command printed
`#167 -> resolved` and exited 0. It was caught only because the next line printed the row and the
status was wrong.

The row was repaired by hand (status back to `pending`, `resolved_at` and `resolution` nulled, deferral
kept) and read back to confirm. No owner-visible harm, but a queue row briefly asserted work was
finished that had not been.

**Why it happened, and the rule.** `defer` and `resolve` are both writers against the same table by the
same CLI, so a "check" written from the same vocabulary as the change becomes a second change. The
failure mode is not a race or a lock — it is that the verification step had a *side effect by design*
and nothing distinguished it from a read.

**The rule:** to verify a state change, **read it back** — `list`, `--json`, a `SELECT` — never re-issue a
sibling command that happens to print the state. And when a shell line mixes a mutation with anything
else, write the mutation alone first and verify in a separate call.

**Corollary for the owner queue specifically:** `resolve` means the question is answered or the work is
done. "He put it off to a named day" is `defer`, and `defer` is not a lesser `resolve` — it is the
correct record for a date he named.

**Evidence.** `owner_decision_queue` row 167 (before: `status=resolved`, after: `status=pending`,
`deferred_until=2026-10-14T23:59:00+00:00`); repair script `/tmp/q167_repair.py` on `secratary`;
reminder id 530 on the authority, scheduled 2026-10-14T13:00Z.
