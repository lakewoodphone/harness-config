**L1525 · CORRECTION to P152: the worker is synchronous; and the suite loads .env into os.environ, which beats _env_file=None**

**CORRECTION to P152, and one more deterministic failure removed.**

P152 listed three mechanisms for the residual failures; **the first one I named is wrong**. It said
`test_worker_clears_in_flight_after_send` was a race because "the worker starts a thread". Measured:
`_worker` is **synchronous** -- the `threading.Thread(target=_worker, ...)` call sits in its *caller*,
one function above it, and the test calls `_worker` directly. There is no thread in that test, so
there is no race in it, and the mechanism has to be found elsewhere.

What this round did establish, deterministically:

| reading | before | after |
|---|---|---|
| `tests/test_phase3_modules.py` | 1 failed / 44 passed | **45 passed** |
| `test_mcp_enabled` | failed on this host, passed elsewhere | asserts the field default |

`test_mcp_enabled` was catalogued as "flaky, most persistent". It is **deterministic here**: the
suite runs with `MCP_ENABLED=false` in `os.environ` (measured inside pytest:
`PROBE MCP_ENABLED env: false`), and the authority's `.env` sets that. An instance therefore reads
False while the test asserts True -- and `_env_file=None` cannot help, because **an environment
variable beats a file**, which is why my first attempt at the fix changed nothing even though it
works in a clean interpreter. The class claims to verify *defaults*, so its seven assertions now read
`Settings.model_fields[...].default`.

And the flakiness that remains is real, just not what I said: four repeats of
`tests/test_family_chat.py tests/test_family_chat_personality.py` gave **137, 136 (memory), 136
(in-flight), 137** -- the same pair of `TestWorker` tests, intermittently, in a synchronous code path.
Candidates now, in order: a DB write that fails under suite load and is swallowed by the worker's own
`except Exception: log.warning(...)`; the `daily_reply_count()` counter keyed to the current date; and
the in-flight marker interacting with the `_now_ts()` gate.
