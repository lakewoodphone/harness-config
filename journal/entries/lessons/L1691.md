**L1691 · Dialpad internal API: workflow bodies are unreachable; /api/media 200 is a false positive**

EVIDENCE gathered 2026-09-15/16 during the 7-agent Dialpad map (slice S1-S2), all read-only.

WHAT I TRIED: 26 candidate internal endpoints to read the scripted-IVR workflow bodies WF101048590-1268826451 (office open) and WF101048590-4155869469 (office closed), plus the greeting audio assets:
/api/workflow/{id}, /api/workflows/{id}, /api/workflow_engine/{id}, /api/workflow_engine?workflow_id=, /api/ivr/{office_id}, /api/scripted_ivr/{id}, /api/ivr_workflow/{id}, /api/callflow/{id}, /api/ivr_menu/{id}, /api/callrouter/{office_id}, /api/company/101048590/workflows, /api/workflow?key=, /api/workflow?id=&target_key=, /api/group/{key}/{workflow,ivr,hours,operators,audio,media,scripted_ivr,departments}, /api/office/{id}, /api/office/{id}/{settings,holidays,routing_options}, /api/department?office_id=, /api/routing_option?target_key=, /api/audio_file?office_id=, /api/sounds?office_id=, /api/media?office_id=.

RESULT: every one returned 404 (a Next.js HTML error shell - content-type HTML, not JSON) or 500 ("Could not decode key 5695945642065920", "Protobuf key ... has a wrong format"). There is NO known endpoint for a workflow body or for greeting audio.

THE TRAP: /api/media?office_id=... returned HTTP 200 but the body was the Next.js APP SHELL, not JSON. A bare status-code check reports this as a hit. Always assert the body parses as JSON and looks like the expected shape before calling an internal Dialpad GET a success - Dialpad's web layer can serve the SPA shell with 200 on unknown /api paths. Same lesson shape as the stale-database crisis: a 200 is not evidence; the body is the evidence.

ALSO DEAD: public API v2 hides action_target (workflow ids), default_dtmf, scripted_ivr_fallback, enable_enh_department_hold_queue, ivr_menu_script, caller_id, failover_phone, vm_disabled and recurring events - internal-API-only. But *_hours, first_action, no_operators_action and ring_seconds ARE public read AND public write, so a public-API-only integration can rewrite the ring window and never see the IVR it drives.

THE ONE WRITE PATH PROVEN: dialpad_ivr_admin.py only ever writes https://dialpad.com/api/group/{office_key}. It can write hours_on, {day}_hours, no_operators_action, ivr_target, after_hours and ivr_menu_script.{open,closed}. There is NO holiday / recurring-event write path in the toolchain. Holidays are UI-only from what is proven.

CONSEQUENCE FOR PLANNING: any task needing to change or verify holiday closures, or to verify what the IVR greeting actually SAYS, cannot be done through either API. It needs the Dialpad UI or a live test call. Budget for that instead of re-probing 26 endpoints.

BONUS TRAP: 7 parallel agents shared C:\Users\ezabz\code\_scratch\dialpad-map. Sibling files (probe2.py) were already taken, and write refused with "file has not been read". Namespace every fleet agent's scratch files (I used s1s2/). This is a real cost of the default fan-out pattern.
