**L8319 · Correction to L8318: the ZABZ-TECH build was NOT hung — I measured once and concluded**

**L8318 is wrong on its central claim and this entry is the correction.** It said the ZABZ-TECH refresh 'sat at 6.8 s CPU for seven minutes with the database file unchanged … that is a hang'. It was not a hang. The rule in that same entry — *check CPU delta and the file's mtime twice, a minute apart, before saying a build is progressing* — is correct, and I did not apply it to the case I wrote it for.

**The measurement that settles it** (ZABZ-TECH, 2026-10-18, \python scripts/sync.py --source files:local\):

 t+0 usearch.db 30.34 MB (journal only)
 t+10m usearch.db 1,441.77 MB wal 46.41 MB state 23.4 M chars
 python CPU 92.8 s and 128.8 s, two processes, both climbing

It was walking ~200k files and reading every text file for the first time. A first full pass on a workstation is **tens of minutes**, not seconds, and CPU can sit low while the adapter is I/O-bound on a cold cache — which is exactly what a hang looks like from the outside.

**What is still genuinely unknown**, and must not be assumed either way: the earlier *full* run (\sync.py --no-remote\, all sources) showed flat CPU at 6.8 s over seven minutes, and I stopped it before a second reading. I do not know which source it was on. The way to find out is to run the remaining sources one at a time in the foreground, which is what the next round does.

**Also honest:** stopping that task killed a run that may have been making progress. Nothing was corrupted (ingest is idempotent per document), but the time was lost.
