**L1492 · A baseline sweep artifact can hide whether your fix works: check what rule already caught the record**

2026-09-15, lpt-sync sibling-rule fix. The task said the 3 false-CREATE records
"now SKIP with a reason naming the sibling's live order". The obvious reading is
"compare before/after on those 3 records".

That reading would have proved NOTHING. In the baseline I was handed
(/tmp/lpt-sweep-after.json, taken ~30 min before I started), all three ALREADY
said SKIP -- but via kind=linked_order, not sibling. Reason: the tool had been
push-run the same night for two OTHER records (weichbrud -> WO26091512711,
david -> WO26091512710) and the write-back that ran had PATCHED THE 3 SIBLING
RECORDS TOO (WO26072412522, WO2608130006, WO2608140001 gained
workflow.orderId), because those siblings are themselves in the corpus and were
among the records pushed. So Rule 1 caught them first and the sibling rule was
never exercised.

Before/after on those 3 would have shown SKIP -> SKIP and looked like success
while the actual defect -- the sibling rule being blanked out by an
unnormalisable phone -- remained completely unverified.

WHAT I DID INSTEAD. Wrote a test that strips the linked-order references IN
MEMORY (workflow={}, references={}) and asserts the SIBLING rule is the one that
fires and names the order. That isolates the rule under test from a rule that
was masking it, and it is now a permanent regression test
(test_the_sibling_rule_fires_for_them_even_with_the_link_removed).

RULE: when a fix changes WHICH RULE produces a decision, verify by kind, not by
decision string -- and check whether the baseline already produced the target
decision through a different path. A before/after diff of decision strings is
blind to exactly that. Ask "which rule fired?" and "did the rule I changed
actually run?", and if it did not, construct the state in which it must.
Corollary: my sweep now PRINTS how many records the sibling rule actually ran on
(16/368), because a check that cannot fire is worse than no check.
