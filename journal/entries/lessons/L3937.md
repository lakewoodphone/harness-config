**L3937 · The quiet loop was a STALE budget-tier stretch: interval_sec 900 (economy, from a squeeze hours earlier) persisted across restarts and is never recomputed when the tier returns to normal - so every budget episode ratchets the loop slower**

The company's quiet loop was not a wedge, not the cap and not the disk. It was a **budget-tier interval stretch that persists across restarts and is never recomputed when the tier improves** — so a temporary squeeze had permanently slowed the loop to a third of its configured cadence.

**The mechanism, read from the code.** `_tier_from_pct` (`llm_budget.py:665`): `>=95 % -> survival`, `>=85 % -> economy`, `>=70 % -> cost_aware`, else `normal`. The stretch maps those to multipliers `1 / 2 / 3 / 5` of `autopilot_interval_sec` (default **300 s**) and assigns `self._interval_sec = base * multiplier`. **And the boot path loads it back from disk** — `autopilot.py:1313` reads `data.get("interval_sec")` — so the stretched value is **persisted**.

**What that produced, measured:**

 earlier today daily window 23.13 of 25 = 92.5 % -> tier economy -> interval 900 s (correct then)
 now monthly 220.23 of 750 = 29.4 % -> tier normal
 daily 68.6 % -> tier normal
 the APP'S OWN get_budget_summary: {"tier": "normal"}
 ...yet runtime state interval_sec = 900 s (300 x 3, the economy value)

**A restart did not fix it:** `interval_sec` read **900 before and 900 after** a restart, because the boot restores it rather than deriving it. So the loop was ticking once per **15 minutes** instead of once per **5** — and **that is exactly what round 37 recorded as "unexplained": 1 tick in ten minutes, 0 `run_once` lines, no abandon, no error, with 20 in-progress and 31 open tasks on the books.** The idle loop was a throttle, and the throttle was stale.

**Fixed and verified at the value:** `data/autopilot_state.json` `interval_sec` 900 -> **300**, then a restart so the boot loads it — read back as **300**, service `active`, backup `data/autopilot_state.json.bak-interval-20261014T155040Z`. **The cadence itself is the pending verification** (ticks over the next window should be ~3x denser), and I am not calling that done until it is read.

**The defect is the persistence, not the stretch.** Stretching during a squeeze is right. What is wrong is that the value is a **stored decision** rather than a **derived one**: whichever path computes the tier writes the interval and nothing recomputes it on the way back up, so **every budget episode ratchets the loop slower and only a human resetting the file brings it back.** The same shape as the two other label defects this estate carries — a stored value that has outlived the condition that justified it, indistinguishable from a current one. **The fix is to derive the interval at each loop pass from the current tier rather than restoring it**; until that is done, this is a maintenance trap, and one worth watching because it is invisible: everything reports healthy while the company runs at a third speed.

**And it is the third "the company is idle" cause found today, each with a different owner:** the **cap** pauses sessions, the **disk** wedges the scheduler, and the **stretch** slows the tick. All three present as the same symptom and none of them is a failure of the code that appears to be idle.
