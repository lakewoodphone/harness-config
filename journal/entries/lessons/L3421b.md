**L3421b · Gmail full-body reads segfault under threads on this box; sweep serially and parallelise by account**

MEASURED 2026-10-13 on secratary, building the first full-corpus email sweep.

The failure: `python3 -X faulthandler lpt-email-sweep.py --days 10 --workers 3` died with
`Fatal Python error: Segmentation fault` after ~30 messages, at `workers=1`, 3 and 8 alike.
It was NOT the data and NOT recursion: the SAME 181 messages fetched serially through the same
`google-api-python-client` / `httplib2` service object completed with zero errors, twice.

The cause is the Gmail client's HTTP stack, which is not thread-safe in this deployment; the
shared httplib2 transport gets corrupted when several threads drive one service object.

The rule: fetch Gmail on ONE thread. Parallelise by ACCOUNT instead - one process per account,
each serial. Five accounts in parallel finished 1113 full messages in ~2 minutes, and each
account's JSONL landed as that account completed, so the corpus could be read mid-run.

Second trap in the same script: the app's own `gmail_service._extract_body` recurses over
`payload.parts` with no depth bound. A marketing MIME tree can be thousands of parts deep. A
body extractor should walk an explicit stack, never recurse.

Third trap, cheaper but real: `messages().get(format="full", metadataHeaders=[...])` silently
IGNORES metadataHeaders, so From/Subject/Date come back empty and every message looks
untitled. Read the headers off `payload.headers` yourself.

The working tool is `~/bin/lpt-email-sweep.py` on secratary. It is now installed as
`lpt-email-sweep.timer` writing to `/home/zabz/accounting-data/email-sweep/`.
