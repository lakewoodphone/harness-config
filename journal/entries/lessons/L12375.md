**L12375 · Pulled-drive erasure: a guard that compares a disk to itself proves nothing, and Windows cannot sanitize an SSD**

Pulled-drive erasure is now a named flow with a guard, and three of its facts were only discoverable by reading this bench rather than reasoning about it.

## What exists now (written 2026-10-26, ZABZ-TECH)
- SOP: `lpt-hub/docs/customer-operations/sops/PULLED-DRIVE-ERASURE-AND-VERIFICATION-SOP.md` — STEP 0 identify, guard, SSD/HDD split, verification, what software cannot prove. Wired into `FLOWS-INDEX.md` (priority row + SOP-index row + maintenance-log row).
- Guard: `lpt-hub/scripts/wipe-guard.ps1` — `-Mode Identify|Guard|Verify`. Contains **no destructive cmdlet**; refuses on the OS disk and on its baseline list by **serial**, not by disk number, because numbers are reassigned per boot.

## The three facts that make this flow different from "just zero it"
1. **`MediaType` is not trustworthy behind a USB bridge.** `Get-PhysicalDisk` said `Unspecified` for the USB stick and `SSD` for the internal NVMe; `SpindleSpeed` was 0 for both. `Get-StorageReliabilityCounter` read `Temperature 57` on the internal NVMe but `Temperature: 0` and blank `PowerOnHours` on the USB disk — **SMART largely does not traverse USB.** So an arriving customer drive in an enclosure will probably read `Unspecified`, and SSD-vs-HDD must be decided from the **model number** and the drive's label, never from the storage stack.
2. **ZABZ-TECH cannot do the correct SSD erase.** `where.exe` rc=1 for `nvme`, `hdparm`, `smartctl`, `sdelete`, `shred`, `dd`; no vendor tool (the only `C:\Program Files\Samsung` content is SmartSwitch, a phone app); `wsl -l -v` → "no installed distributions". ATA Secure Erase and NVMe Sanitize are simply absent. Verified present on **zabz-tech-linux** instead: `/usr/sbin/nvme` (nvme-cli 2.8 / libnvme 1.8), `hdparm`, `smartctl`, `blkdiscard`, `shred`, and `sudo -n` works (rc=0). That box is the instrument for a provable SSD erase — and native port is a hard precondition, because NVMe admin and ATA security commands do not cross a USB bridge.
3. **A guard can be circular.** If the "expected serial" is copied from `Get-Disk`, the guard compares the disk to itself and passes for every disk. The SOP requires the expected serial/model/capacity from an **independent** source (the drive's printed label, the service documentation, the customer's own statement). This is the single easiest way to build a guard that looks rigorous and guarantees nothing.

## Measured baseline (this machine, so a future session can recognise an intruder)
- Disk 0: Micron MTFDKBA1T0TGD-2BK15ABLT, serial `00A0_7501_4E57_B582.`, 1,024,209,543,168 B, NVMe, `IsBoot=True IsSystem=True` — **the OS disk, FORBIDDEN**.
- Disk 1: PNY USB 3.2.1 FD, serial `0B7F19C250B0`, 62,026,416,128 B, USB — the LPT boot stick (D: Win11, E: UEFI_NTFS) — **FORBIDDEN**.
- Elevated: `Mandatory Label\High Mandatory Level`, `S-1-5-32-544` enabled. Windows 11 Pro 26200, pwsh 7.6.9, Lenovo `30H10010US`, no battery. SATA AHCI controller present (`PCI\VEN_8086&DEV_7AE2`, status OK) and one NVMe controller (`stornvme`). `NewDiskPolicy=OnlineAll`. **C: has 6.4 GB free of 951.6 GB** — no room to image a drive locally.
- Journal precedent that this is not a new problem class: **H230/H232** (Weissman WD SN740 512 GB out of a water-damaged machine, went through a **Sabrent RTL9210** enclosure to 300DDR) and **H243** (Newman flash wipe, but that one ran on **zabz-tech-linux**, not Windows).

## Honest gaps — do not let a future session assume these were tested
- The guard's **PASS path is untested**: no unrecognised disk was attached, so only the refusal paths were exercised (`Identify` rc=0 with `FORBIDDEN = Disk 0, Disk 1`; `Guard` rc=1 on missing candidate and rc=1 on missing expected values; `Verify` rc=1 on Disk 0 and on Disk 1).
- `-Mode Verify` against an actually-wiped disk is untested. Its **read mechanism** was proven read-only against the non-OS USB disk: `\\.\PhysicalDrive1` returned `41 4B 45 4F FC 31 C0 FA …` at LBA 0, `MBR sig 55AA present = True`, `GPT 'EFI PART' at LBA1 = True` — so a zero read would mean zeros, not a silent failure.
- `diskpart clean all` was **not run** (correctly — preparation only), so its zeroing behaviour on this build is documented behaviour, not something measured here.
- How many free SATA ports / M.2 slots the board exposes cannot be read from software. Only that a SATA AHCI controller and one NVMe controller are live.

## Transferable rules
- **A disk number is never stable; a serial is.** Address a disk by the serial that a guard printed, and take the number from that same printed line.
- **On an SSD, one overwrite pass is a logical claim, not a physical one** — FTL remapping, an over-provisioning pool the host cannot address, and DRAT/DZAT (a trimmed block reads back as synthesised zeros without touching NAND). Multi-pass does not fix it and costs a full P/E cycle per pass. The correct operations are ATA Secure Erase (SATA) and NVMe Sanitize (NVMe), and neither exists on a Windows box without a vendor tool.
- **Say which claim was earned.** "Logically blank, verified by read-back" and "vendor sanitize completed, log attached" are different sentences and must never both become the word "wiped".
- **Verification means reading the medium afterwards.** "diskpart said it succeeded" is a statement about the controller acknowledging writes.
