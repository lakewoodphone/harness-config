**L3453 · A newest-directory-wins backup pusher uploads partials and byte-count verification gives a false green**

## L — A "newest directory wins" backup pusher will upload a partial, and byte-count verification cannot catch it

FOUND 2026-10-09 by a fleet workstream (W3) that was killed mid-run; verified by me directly.

THE CHAIN OF FAILURE, all measured:
 1. An interrupted backup left a partial directory: 20261009T181506Z/sqlite/data/secretary.db
 = 300,740,608 bytes, and sqlite3 answers "file is not a database". A 1024-byte
 -journal file sits beside it, the marker of a hot, mid-copy artifact.
 (I created it by stopping secretary-backup.service at 18:15 to relieve disk pressure.)
 2. push-db-offsite.sh selects the source with: ls -1d */ | sort -r | head -1
 There is NO completeness marker and NO "is this a database" check. The partial sorts
 FIRST because its name is the newest stamp.
 3. So at 05:10 UTC it would have gzipped the 300 MB non-database, uploaded it as
 authority/secretary.db.gz, OVERWRITTEN the good 6,623,505,863-byte object, written a
 fresh .sha256 sidecar, and reported OK.
 4. WHY IT REPORTS OK: the verification compares remote bytes to the bytes it just sent.
 It proves the UPLOAD is faithful. It proves NOTHING about the SOURCE. A corrupt
 source produces a faithfully-uploaded corrupt object and a green light.
 5. company-offsite-push.sh has the same shape: it picked the same partial directory and
 stamped it company-offsite = TRUSTED, because a faithfully-stored partial tar passes
 its byte check. The freshness monitor then reported the company's offsite copy as
 fresh, which is a FALSE GREEN.

RULES
 * A backup producer must write a COMPLETENESS MARKER as its LAST act, and every consumer
 must require it. Directory mtime or name order is not completeness.
 * "Bytes sent == bytes stored" is an integrity check on the TRANSPORT, never on the
 CONTENT. Verify the artifact is what it claims to be: open it, run
 PRAGMA integrity_check / schema_version on it, or compare a table count.
 * When a backup job can be interrupted, the interruption leaves a directory that looks
 like a backup. The default must be "untrusted until marked", not "trusted because it
 exists".
 * A freshness monitor that reads only the tag timestamp cannot see a corrupt payload.
 Freshness and validity are different questions; ask both.

DONE: removed 20261009T181506Z (verified: one 300 MB non-database + one journal, nothing
else). push-db-offsite now selects 20261009T120001Z, 22,981,234,688 bytes, readable.
STILL OPEN: no completeness marker exists yet on either pusher; the race remains.
