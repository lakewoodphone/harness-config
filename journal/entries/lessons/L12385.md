**L12385 · shell_command has no shell, and continue_on_error does not catch a FileNotFoundError - the intrusion page died on 'for' for weeks**

**L-style lesson · 2026-10-26 · `shell_command` in Home Assistant has no shell, and `continue_on_error` does not cover it**

`shell_command` runs `asyncio.create_subprocess_exec(*shlex.split(rendered_command))`. There is no shell,
so the first word must be an executable on PATH. `for`, `find ... | ...`, `if`, `>` all fail.

Measured, not inferred: every intrusion in the 43 h HA keeps in `/api/error_log` died with

```
ERROR (MainThread) [homeassistant.components.script.phoenix_intrusion_evidence_and_page]
Phoenix: Intrusion Evidence And Page: Error executing script.
Unexpected error for call_service at pos 5: [Errno 2] No such file or directory: 'for'
```

42 such lines across 6 episodes, 2026-10-24 22:25 -> 2026-10-26 14:03. The command was
`for f in {{ files }}; do if [ -s "$f" ]; then echo ...; fi; done`.

Two things worth carrying:

1. **`continue_on_error: true` is not a try/except.** It covers *service* errors (entity missing, service
 raises `HomeAssistantError`). A `FileNotFoundError` raised inside the service aborts the whole script.
 So a step that "cannot fail" because it is guarded aborted the paging path for weeks.
2. **A failure handler placed after the failure is not a handler.** Step 7 of the same script created
 `persistent_notification` "SECURITY PAGE FAILED - intrusion not delivered". It never ran, because it
 sat downstream of the step that raised. Fail-loud code must be on a path the failure cannot skip.

Correct form (BusyBox-safe; the HA container's `find` has no `-printf`, measured 2026-10-26):

```yaml
shell_command:
 phoenix_verify_evidence_files: >-
 bash -c 'for f in {{ files }}; do if [ -s "$f" ]; then echo "PHOENIX_EVIDENCE_OK $f"; fi; done'
```

Single-quote the argument so `shlex.split` hands bash exactly one argv element. Verify a shell_command by
calling it with a response: `POST /api/services/shell_command/<name>?return_response` and read `stdout` +
`returncode` - do not infer success from the absence of an error. (`phoenix_verify_evidence_files` now
returns `PHOENIX_EVIDENCE_OK <path>`, rc 0; `phoenix_prune_intrusion_evidence` took 48 files with a 40-day-old
one down to 42 with none older than 14 days.)

### How this was found, so it can be found again
The owner heard a siren, not an error. The path was: HA logbook (who armed it) -> the script YAML (which
step) -> `/api/error_log` (what the step said) -> `sms_log` on the authority (whether the page ever left).
**Read the outbound table before believing any "the alert fired" claim:** `sms_log` has 4,507 rows back to
2025-09-02 and zero intrusion pages, while a September note in the code asserted Twilio had confirmed four
recipients. The absence of a row is the fact; the comment was a belief.
