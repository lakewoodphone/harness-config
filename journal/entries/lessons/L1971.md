# L-new — The carrier is the log of record: reconcile against it, and count what the app is missing

Measured 2026-09-18 on the secretary's own Twilio line (`+17324447361`).

**70 inbound texts reached Twilio and never reached the app.** 325 inbound total. Among them:
*"Call me now"*, *"I tried to call you and you were just quiet"*, *"Open the front door for Mattis
Klein for 10 minutes"*, *"My car is not starting"*, and two separate people asking the system to stop
auto-replying at them. Months of silence, to real people, that no table recorded.

**Mechanism:** `Unhandled error on /webhook/twilio/sms: database is locked` → HTTP 500. Twilio does
not retry an inbound SMS webhook after a 5xx, so the message was destroyed at that instant — not
queued, not deferred, gone. The failure was intermittent (7 in the last six weeks) which is exactly
why nobody noticed: `sms_log` simply had no row, and an absent row looks like nobody texted.

**The rule.** For anything delivered by a carrier or a third party — SMS, calls, voicemail, email,
webhooks — **the provider's own API is the log of record, and the local table is a cache.** So:

1. Keep a reconciler that walks the provider's API on a timer and upserts by the provider's id.
2. Store a per-row flag for *did we get this one?* (`app_has_it`) and compute a **gap count** from it.
 A gap count is a real number that goes up; "no rows" is not evidence that nothing happened.
3. Never treat a 5xx to a webhook as "it will be retried". Check the provider's retry semantics
 before assuming anything is safe to drop. Twilio: no retry on inbound SMS.

**Why this beats fixing just the lock.** The lock is one cause of loss. The reconciler is cause-
agnostic: it also catches a webhook pointing at a dead host, a deploy that lost its route, and a
process that was down. It found 70 — far more than the six the logs showed.

**Corollary, learned the same hour:** the first version of this was going to be a change to
`app/main.py`. The authority's deployed tree turned out to be 119 commits ahead / 176 behind origin
with uncommitted edits to that exact file, so the sensor went into `~/bin` as a standalone script and
shipped in an hour instead of being blocked on a repo whose git story is itself an open owner
question (#89). **Check what is actually deployed before deciding where a fix must live.**

**Evidence:** `~/bin/sms-inbox.py` (`harness-config/scripts/sms-inbox.py`, commit `a99fa0c`);
`report`/`gaps` subcommands; `~/.sms-inbox/inbox.db`; cron `*/5 * * * *`.
