## LESSON — the instrument manufactured the conclusion: a module-level singleton read from a fresh process reports zero

**What I claimed, wrongly.** In `H3242` I wrote that production's community blocklist was empty
(`blocklist._domains = 0`) and had "never worked". That went to the owner too.

**What is true.** It held **474,178 domains** at the time. It was working. It now holds **646,700**
after the fix below.

**The instrument that lied.** I ran:

 docker exec lpt_filter_ai_api python -c "from app.blocklist import blocklist; print(len(blocklist._domains))"

`docker exec` starts a NEW process. `blocklist` is a module-level singleton, so in that process it
has never run a refresh and `_domains` is the empty frozenset it was constructed with. The command
cannot return anything but 0. It is not a measurement of the server; it is a measurement of a fresh
interpreter, and it wears the server's clothes - the container, the image, the same module.

**Why it is worth recording rather than quietly fixing.** This is the exact failure mode the
constitution names: a confident wrong number, from a source that felt authoritative. The rule that
would have caught it - *if you cannot state where a reading came from and when it was written, do
not report the number* - was satisfied in form and violated in substance, because I could state the
container. The missing question was narrower and would have caught it: **whose process is holding
this state?** A singleton's value belongs to one interpreter. Reading it from another is not a
measurement.

**The fix, which is the real lesson.** Make the running process report its own state, so the question
has an answer that cannot be faked: `Blocklist.snapshot()` (enabled, urls, domain_count,
refresh_count, last_refresh_age_seconds, failed_urls) is now on the deep health payload. `H3242`'s
claim is corrected by this entry, which is how the record is meant to work - the wrong version stays
visible.

**Two real defects were hiding behind the wrong number**, and they were smaller than what I claimed
but real:

1. The first of the two built-in default lists was a jsDelivr URL and jsDelivr refuses the upstream
 repository outright - `403 Forbidden, "Package size exceeded the configured limit of 150 MB"`.
 Half the intended coverage had been contributing nothing while the list looked healthy.
 Replaced with `raw.githubusercontent.com/.../wildcard/multi.txt`. Measured, merged:
 **474,178 -> 646,700 domains (+36%)**, both URLs succeeding, verified on production after deploy.
2. A list in a format the parser cannot read fetches 200, parses to ZERO domains, and was logged as
 `loaded 0 domains from ...` - a success line. Measured on `dnsmasq/multi.txt` (173,214 lines of
 `local=/domain/`): 0 domains, 1.3 s, no error. Now a warning naming the format, and an ERROR when
 a refresh ends empty while enabled.

**Transferable rule:** when a value lives in a long-running process - a singleton, a cache, a
connection pool, a counter - read it from THAT process (an endpoint, a metric, a signal), never by
importing the module in a new one. A fresh interpreter answers every such question with the
constructor's default, confidently.
