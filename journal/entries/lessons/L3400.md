**L3400 · lpt sql cannot carry a double-quoted identifier from a Windows shell**

## L — `lpt sql` cannot carry a double-quoted identifier from a Windows shell

Measured 2026-10-08 on ZABZ-YOGA. `lpt sql 'select id, "orderId" from payment_transactions limit 5'`
reaches Postgres as `select id, orderId from payment_transactions limit 5` and fails with
`UndefinedColumn: column "orderid" does not exist`. The quotes are gone before the SQL leaves the
client. Escaping them with backticks, with `[char]34`, and with `\"` all failed identically, and the
error prints the statement with the quotes stripped — which is how you can tell it is the transport
and not the query.

**What to do instead:**
- Use `select *` and filter the rows afterwards, in the shell or the JSON. Column names then never
 appear in the statement at all.
- Or run the query on the authority, where a heredoc keeps the quotes: a `python3 - <<'PY'` block or
 `psql` over ssh.
- **The wider trap this exposes:** a `lpt sql` that *succeeded* with a stripped identifier would have
 answered a different question than the one asked. Here it errored, which is the good outcome. Before
 trusting any `lpt sql` result on a Windows host, ask whether the statement that ran is the statement
 you wrote.

**Same class, same fix:** any other `lpt`/`lpt-write` argument that has to contain a literal quote.
Pass it through a variable, and prefer a body with no double quotes in it at all — which is how the
production note written to `WO26100812731` was composed.
