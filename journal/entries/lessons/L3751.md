**L3579 · A semantic merge that compiles cleanly can silently disable the feature it is landing**

MEASURED 2026-10-12, `phone-and-tech-full`. Landing the pay-notice pipeline
(`pbp/w1-notice`, commit `5e8583354`) onto `origin/test` reports exactly ONE
textual conflict, and the naive resolution type-checks and builds:

- `origin/test` replaced the awaited notification block with a deferred helper,
 `scheduleStatusNotification`, which calls
 `repairNotificationService.handleStatusChange(orderId, fromStatus, toStatus)`.
- The new work added a FOURTH parameter, `actor?: AuthenticatedActor` — optional,
 so the 3-argument call compiles.
- With no actor, `draftPayNotice` returns early by design. **No draft is ever
 written, from any staff path, and nothing says so.**

The whole feature would have shipped dead, and every signal a merge normally
gives — clean merge, green typecheck, green focused tests — would have been green.

THE RULE. `git merge-tree` finds textual conflicts; it cannot find a semantic one.
After merging a branch that ADDS AN OPTIONAL PARAMETER, grep every call site of the
function it was added to and ask which of them relied on the default. That is one
`git grep`, and it is the difference between "merged" and "works".

SAME SESSION, SAME SHAPE, second instance: the same branch's trigger is only
reachable when the actor is threaded, and the branch's own test asserted the
4-argument call — so the test would have gone red and been "fixed" by relaxing it
if nobody had looked at WHY the 4th argument was missing.
