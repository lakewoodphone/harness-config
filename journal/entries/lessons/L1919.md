**L1919 · Stage the path the journal tool printed - a guessed id range sweeps other sessions' entries (I did it twice in one session)**

**Take the path from the journal tool's own output. Never guess an id range when you stage it.**

I wrote L1914 earlier today: "in a shared checkout, an uncommitted edit is not yours, and another session's `git commit -a` can sweep your files into its commit." Two hours later I did the same thing to six other sessions - while trying to avoid it.

What happened, measured: my appends printed `+ H480`, `+ L1918`, `+ P248`, but I staged with a **guessed range** (`journal/entries/**/{H47[5-9],L191[5-9],P24[7-9]}.md`) because that glob was written before the appends ran. Five handoffs (`H475`-`H479`) and two lessons (`L1916`, `L1917`) written by other sessions in the same window matched it, and `commit` reported **9 files** where I intended 3. Their content is intact and now on the remote; only the commit boundary and the attribution are wrong. Nothing was lost, and this is on `master` after a push, so it is not being rewritten.

The mechanical fix, and it costs nothing:
- `journal.py append` prints the entry it created (`+ H480 -> entries/handoff/H480.md`). **Capture that line and `git add` exactly those paths.** `--json` makes it parseable.
- After `git add`, read `git status --short` on the exact paths, and after `git commit`, read **`git show --stat HEAD`**. A commit that reports more files than you staged is the only warning you get, and it is unambiguous.
- A guessed range is a range that will match the next session's work, because ids are allocated in the order sessions finish, not in the order they start - the whole point of a shared append-only log.

Note the failure mode is asymmetric: over-staging is invisible and harmless-looking, while under-staging silently drops your fix. So the range instinct ("better to include too much") is exactly backwards in a shared repo.
