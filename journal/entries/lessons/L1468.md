**L1468 · A capability nobody can discover is a capability nobody has (register the tool, then verify through the agent surface)**

## A capability nobody can discover is a capability nobody has

The comms reader became reachable the moment `data/tools/comms_search.py` existed: the
action dispatcher falls through to `_exec_dynamic_tool(action_name, params)`
(`app/chat_action_runtime.py:1427`) → `run_tool(...)`, so any agent that emits an action
named `comms_search` runs it. That is real access and it was not the same thing as
availability.

`list_tools()` returns **builtins plus registry entries with status `active`**
(`app/tool_factory.py:432`), and `get_tool_summary()` is what is put into the LLM's
context. A dynamic tool that exists on disk but is not in `data/tool_registry.json` is
invisible to every agent that was not told about it by hand — the fleet had 517 registered
tools and mine was number 518, deliberately.

So the last step of shipping a capability to other agents is not the code, it is:
1. put the file where the dispatcher looks,
2. **register it**, with a description written for an agent rather than for a human
 ("USE THIS BEFORE answering anything about a customer"),
3. verify through the same surface the agent uses — `GET /tools/list` and
 `GET /tools/summary` — not by reading the database.

Verified: `comms_search in list: True`, `total tools: 518`, and the summary contains the
description. Two earlier attempts at this same shape exist in the journal (`ps_health`
returning 90 KB and poisoning context); discoverability and payload size are both part of
whether a tool actually gets used.
