**L3756 · An OOM in the kernel log is an event, not a failed job: ask the unit and ask the consumer (two wrong alarms, one session)**

THE RULE: a kill line in the kernel log is an EVENT. Whether it MATTERED is a separate
measurement, and it is not made by reading the kill line harder. Ask two other parties:
 1. THE UNIT ITSELF -- `systemctl show <unit> -p Result -p ExecMainStatus -p NRestarts`
 and the unit's own `Finished`/`Consumed ... memory peak` line.
 2. THE CONSUMER -- the thing the job feeds has its own freshness check. If the consumer
 says it is current, the kill did not matter, whatever it looked like.

TWO CASES FROM ONE SESSION, BOTH MINE, BOTH WRONG, FILED 2026-10-13 01:4xZ AND CORRECTED
BY 02:1xZ:

CASE 1 -- the transcript archive (P3154, now RETRACTED). I read
`oom-kill:...oom_memcg=/system.slice/transcript-archive-pull.service` and concluded the
mandated permanent archive was failing hourly and falling behind, and I told the owner it
was a data-loss risk. The measurements that would have stopped me, taken 25 minutes later:
 17 successful `Finished transcript-archive-pull` lines in 3 days vs 8 OOM events;
 Result=success, ExecMainStatus=0;
 the 01:23Z run: "Finished ... Consumed 16.568s CPU over 2min16.072s, memory peak 266.5M",
 having ingested 8 tarballs ok=1 and freed 12.6 MB of spool;
 and the archive's OWN check exits 0 -- ok:true, 47199 objects, 37.26 GB raw in 6.61 GB
 stored, 53881 arrivals, 0 quarantined, last_arrival 2026-10-13T01:25:02Z, i.e. current to
 the minute.
The 8 OOMs also CLUSTER: 2026-10-12 14:31, 15:27, 16:32, 21:29, 22:29 twice, 23:29, then
00:29 -- a backlog drain that ended, not a standing condition. Looking at the TIMELINE
rather than the count would have shown that.

CASE 2 -- a count that was mostly a substring. `journalctl -u company-api | grep -icE
"oom|killed"` returned 21 and I repeated "21 OOM lines in 7 days" as evidence the cloud is
memory-unreliable. Inspecting the matched lines: 15 are real (`Failed with result 'oom-kill'`
/ `Main process exited, code=killed, status=9/KILL`) and ALL THREE KILLS ARE ON 2026-10-11
(05:47, 07:10, 15:17) -- BEFORE the box was resized to 16 GB. The rest match `oom` inside
ordinary words: one is a family-chat line containing the word "**r**oom". `grep -i oom`
matches "room".
`systemctl show company-api -p NRestarts -p ActiveEnterTimestamp` -> NRestarts=0,
ActiveEnterTimestamp=2026-10-12T14:14:39Z: the unit has not been killed since it started
after the resize. So the honest sentence is "three OOM kills on 2026-10-11, before the
memory resize; none since", not "21 OOM lines in 7 days".

THE GENERAL FORM, which is why this is a lesson and not an apology:
 * A LOG LINE IS NOT AN OUTCOME. Pair every kill/failure reading with the unit's own
 Result/ExecMainStatus and with the consumer's freshness check, in the same breath, or
 do not report it.
 * A COUNT IS NOT A TREND. Print the timestamps. Clustering is the difference between a
 standing fault and a drain that finished.
 * A CONFIGURATION CHANGE RESETS THE POPULATION. Kills before the resize are evidence
 about the OLD machine, not the current one. Find the last change and bound the window
 by it.
 * A SUBSTRING MATCH IS NOT A SEMANTIC MATCH. `grep -i oom` matched "room". Read the
 matched lines, at least a sample, before you put a number in a sentence.
 * AND: I did this to the owner -- I told him a permanent archive was at risk of data loss.
 A confident wrong alarm spends exactly the trust that a correct one needs. The cost is
 not the correction; it is that the next correct alarm is harder to hear. Prefer the
 smaller true sentence.

Citing: P3154 (retracted), H3591 (whose "BROKEN item 2" carries the same wrong archive
claim), and journal P3 "Reading the wrong data and believing it" -- the same class as the
stale-database crisis, in the opposite direction (a crisis invented instead of a crisis
missed).
