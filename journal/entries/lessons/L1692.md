**L1692 · Cloudflare Access on the HA public host defeats any third-party media fetch (200 but text/html)**

The public HA host is behind Cloudflare Access, so NO third party can fetch a snapshot from it.

MEASURED 2026-09-16. `GET https://ha.abletelsolutions.com/local/snapshots/latest_intrusion_control_room_interior.jpg`
returns **200 with `Content-Type: text/html`, 33,480 bytes**, and the body is
`<title>Sign in ・ Cloudflare Access</title>`, redirecting to `dawn-cell-26a7.cloudflareaccess.com`.
The same is true of `/manifest.json` and `/auth/providers`: every unauthenticated path on that host
returns the Access sign-in page.

Consequence: `ha.abletelsolutions.com` can never be a media URL for Twilio (or any external service).
And the alternative base URL, `phoenix_external_base_url = http://192.168.50.34:8123`, is RFC1918 and
equally unusable externally — though it DOES serve a real `image/jpeg` (251,139 bytes) to a machine on
the office LAN.

So both candidate bases are dead ends, and no amount of URL-verification alone finds this: the request
succeeds with HTTP 200. The tell is the Content-Type and the byte length, not the status code.

The working design: the secretary (which sits on the office LAN and already holds HA_URL + HA_TOKEN)
fetches the private LAN URL, rehosts the bytes, and hands Twilio a public URL. The only publicly
reachable, unauthenticated surface on `ai.abletelsolutions.com` is the `/webhook/*` prefix — measured:
`GET /webhook/event` -> 405 from the FastAPI app, `GET /webhook/ha/security-media/probe.jpg` -> 404
from the app (route absent, so the request reached it) — whereas `/`, `/media/...`, `/local/...`
return the Next.js HTML shell and `/api/v1/health` returns 401.

Rule for any future outbound-media feature: a URL is only usable by a third party if an
UNAUTHENTICATED fetch from outside the LAN returns the right Content-Type. Test that explicitly.
