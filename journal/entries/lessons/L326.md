**L326 · Correction to P127: the tailnet was never down -- the unprivileged tailscale CLI reports NoState for a healthy tunnel, and MagicDNS resolution was the real fault**

CORRECTION to P127. I reported that Tailscale on ZABZ-YOGA was "dead since boot" and "logged out".
That was wrong, and the elevated read taken before I restarted it proves it.

What I believed: `tailscale status` (non-elevated) said "Tailscale is starting. Please wait." and
"unexpected state: NoState"; `tailscale up` said "You are logged out. The last login error was: fetch
control key: Get https://controlplane.tailscale.com/key?v=138: context canceled". I concluded the
daemon had lost its login at boot and could not reconnect.

What was true: `tailscale status` **as admin**, at 19:01:41 and BEFORE any restart, listed the whole
tailnet with a live connection to `secratary 100.84.72.88 active; direct 71.104.140.242:41642,
tx 1146600 rx 2460616`. The tunnel had been up the entire time.

What was actually broken, and both are fixed by `Restart-Service Tailscale -Force`:
 1. MagicDNS name resolution. `Resolve-DnsName secratary.tail93e6e6.ts.net` -> "DNS name does not
 exist"; the per-interface DNS servers were only 192.168.12.1 and there was NO NRPT rule for the
 tailnet. That is what broke `ssh secratary-ts` and produced the 15 repeated
 `ssh: Could not resolve hostname secratary.tail93e6e6.ts.net: No such host is known.` lines in
 the engine's stderr. Connectivity was never the problem -- resolution was.
 2. The UNPRIVILEGED tailscale CLI/LocalAPI path, which reported NoState and "logged out" while the
 daemon was healthy. Told the truth again the moment the service came back.
After the restart: the name resolves to 100.84.72.88, the NRPT rule `{5abe529b-675b-4486-8459-25a634dacc23}`
-- the SAME GUID Windows flagged as "corrupted" at 17:20:30 -- is present and working, unprivileged
`tailscale status` lists the tailnet, and `ssh secratary-ts "python3 ~/bin/owner-queue.py next"`
exits 0 with queue #12.

THE LESSON: on Windows, `tailscale status` run without elevation is NOT evidence about the tunnel.
It reads the LocalAPI in the user's own context and will say "NoState / logged out / starting" for a
tailnet that is fully healthy. Before concluding the network is down, take ONE elevated read, or
better, test the thing you actually need -- resolve the name, connect to the peer. Reporting a
healthy system as dead cost time here; the inverse (the stale-database incident this repo keeps
citing) is the same failure class, and a reading that can report ill health for something that is
fine is worse than no reading.

Also worth knowing: this recurs. The 2026-09-11 entry H2 records the same shape -- "CorpDNS: false,
MagicDNS was off, so secratary.tail93e6e6.ts.net did not resolve" -- with `tailscale set
--accept-dns=true` as the fix. Next time it happens, that is the first thing to try, and it does not
need a UAC prompt if the user is set as a tailscale operator.
