**L3392 · A tool that cannot tell 'nothing found' from 'the query failed' will confidently report the wrong world: my own audit did it twice in ten minutes**

Recorded 2026-10-08 while building lpt-stripe-audit. Two self-inflicted versions of the same defect, both caught before anyone acted: (1) the SQL helper parsed only lines starting with '{' and ignored errors, so a failed query returned an empty list and the audit reported '129 charges have no local row' as a FINDING - the join key was wrong (a terminal payment's local row carries stripePaymentIntentId and leaves stripeChargeId NULL); (2) the candidate matcher documented a date window and never implemented one, so any charge of a common price landed on whichever order shared that total - one customer was reported as having paid SIX times for a single 75 order. Fixes: raise on a failed read and on an empty result for a query that cannot be empty; implement the filter the docstring promises; and require INDEPENDENT corroboration (a name in the description) before calling anything a match, because an amount alone is a coincidence waiting to happen in a shop where prices repeat. The transferable rule: an empty result is a refusal, not a finding, and a matcher must state its confidence rather than imply it. Same class as the mesh probe reading healthy while the fleet was dead.
