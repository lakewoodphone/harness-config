**L2087 · The legacy accounting.db is CP1252, and one bad byte silently kills the entire legacy seed**

**L · The legacy `accounting.db` is CP1252, and one bad byte silently kills the entire legacy seed. Read text defensively from ANY pre-2025 store on this fleet.**

Measured 2026-09-20, on the first real `python3 -m books.ingest` against the authority:

```
legacy seed failed: Legacy seed failed: Could not decode to UTF-8 column 'justification' with text
'Food delivery (Grubhub) charged to Escape101 Amex *6304. Categorized as Meals & Entertainment
<0x96> these are business meals for staff/contrac'
```

Byte `0x96` is a CP1252 en dash. Python's `sqlite3` default `text_factory` is strict UTF-8, so it
raises on that byte and **the exception aborted the whole legacy half of the run**. The Plaid half had
already succeeded, so the failure arrived *beside a green-looking report*: the store held 1,662 rows,
0 categorisations, 0 evidence rows, and the report said the legacy seed had failed in one line while
everything else printed normal numbers.

What was lost until it was fixed: **8,198 ledger rows, 4,387 categorisation rows, 4,015 evidence rows**
- including every written justification, which is the reason any categorisation in that database is
believed at all. That is the most valuable data LPT owns about its own money.

**The fix** (both copies, because `books/ingest/remote.py` is deliberately a standalone stdlib module
with no package imports):

```python
def _lenient_text(raw: bytes) -> str:
 if isinstance(raw, str): return raw
 try: return raw.decode("utf-8") # honest reading for anything that is UTF-8
 except UnicodeDecodeError:
 try: return raw.decode("cp1252") # what actually wrote those bytes
 except UnicodeDecodeError: return raw.decode("utf-8", "replace")
conn.text_factory = _lenient_text
```

plus `tests/test_ingest_encoding.py`, which writes **real CP1252 bytes** into a fixture with
`CAST(x'466f6f2096626172' AS TEXT)` and asserts an en dash comes back as an en dash, and that a byte
undefined in *both* encodings degrades to U+FFFD rather than raising.

**The transferable rule, stated so it applies beyond this repo:** when a text column comes from a
Windows-authored SQLite file, assume it may be CP1252 and set `text_factory` before the first read. A
strict decoder turns one character into a total data loss, and it does it *quietly*, because the failure
surfaces as one line in a report whose other lines are all fine. **Never read a legacy store with the
default text factory, and never let a per-row decode error abort a bulk import.**
