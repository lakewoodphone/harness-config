**L1551 · When you add the assertion that closes an audit finding, deliberately break the thing it protects and confirm the assertion fails**

**Evidence, 2026-09-15 (round 5).** Implementation run for the queued code change set from PART-122/124. Unlike the audit rounds, this one changed behaviour, so the interesting part is the verification.

## What was fixed

`revokeOtherSessions` promised in its docblock to destroy *"every OTHER session"* and then called `revokeAllForUser(userId)`, which revoked **every** refresh token for the user — including the session it had just spared. With a 7-day access token, every security-sensitive account change signed the customer out at their next refresh. Four shipped paths: `google.unlink`, `google.setPassword`, `customerAccount.changePassword`, `customerPortal` twice.

**The constraint that shaped the fix:** `RefreshToken` carries only `userId`. No `sessionId` column, and `Session` does not reference a refresh token. So "the other sessions' tokens" is not a query the schema can express — which is *why* the original fell back to revoking by user. The raw `lpt_refresh` cookie value is the only handle that identifies the current session.

**The fix:** `revokeAllForUser(userId, exceptToken?)` revokes `where userId, isRevoked false, token != exceptToken`; both `revokeOtherSessions` implementations take `exceptToken` and return **`currentSessionSpared`**; `currentRefreshTokenFromRequest(req)` was added and three call sites now pass the caller's own token.

## The verification that matters — three parts

1. **Tests pass:** `116 passed` across 7 files (was 115), exit 0.
2. **One existing assertion changed, and I know why:** the second argument is now passed explicitly as `null`, so `toHaveBeenCalledWith(1)` became `toHaveBeenCalledWith(1, null)`. I updated it rather than loosening it to `toHaveBeenCalled()`.
3. **The new assertion was proven to bite.** I added a test that asserts the *spare* actually happens, then deliberately removed the threading and re-ran: **2 tests failed**. Restored, and back to 116 passing. A test that has never been observed failing is a hypothesis.

**Rule this establishes:** when you add the assertion that closes an audit finding, deliberately break the thing it protects and confirm the assertion fails. The audit had just spent a round discovering that a suite full of green tests did not notice a real defect (PART-122 F-3, a test that asserted only `success === false` while the revocation could have been deleted). Adding an unverified assertion would have repeated the same mistake one level up.

## Honest limits

- **The degraded path still exists, and now says so.** `customerAccount.changePassword` reaches the guard through a service that holds a **session id, not the cookie**, so it still revokes all tokens. Its return value now reports `currentSessionSpared: false` instead of being indistinguishable from a correct call. Fixing it properly means threading the cookie through the router signature — noted, not done.
- **Nothing was deployed to production.** This is a source change on the audit branch; production still runs the old hand-patched build. The deployment gap (PART-120 F-3c) means this fix is not live.
- **No typecheck** was run (the worktree's `tsc` fails on pre-existing `@phone-and-tech/shared-types` resolution in unrelated files, 22 errors, none in files I touched); I used `esbuild --loader=ts` on each of the six edited files, which checks syntax, not types.
- Also found and not fixed: `google.ts` defines its **own** copy of the rate limiter (`assertAccountMutationRateLimit`, lines 36-59) instead of importing `assertAccountChangeRateLimit` from the same module it already imports `revokeOtherSessions` from — two implementations of one rule, so changing the shared limit silently misses this router.
