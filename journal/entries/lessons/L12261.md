**L12261 · E4610 615196187: PTT+ self-heals, techmode reinstall is cert-safe, -d list lies**

Serial 615196187 (E4610, VZW_E4610, Android 7.1.1, build 1.010VZ) - the one filtered phone of three on the bench, 2026-10-22. Others on the bench that day (616202539, 616574160) are unfiltered and must not be touched.

FACTS MEASURED THIS SESSION
- `pm list packages -d` listed com.verizon.pushtotalkplus as disabled, but `dumpsys package` said enabled=1 (ENABLED) with lastDisabledCaller: android. The -d list was wrong; dumpsys was right. PTT+ self-heals after the disable is rejected, so never trust -d for this package.
- `pm disable-user` on PTT+ still returns `SecurityException: Shell cannot change component state ... to 3` even after `settings put system ptt_application_enabled 0`. Taking the route down at runtime is NOT enough to make the disable stick; the route had already come up at boot. The engine's pre_install ordering (disable before the route is ever enabled) works on a fresh deploy. It does not retrofit a phone whose route is already live. Untested next move: set route 0, reboot, disable, then set route 1.
- com.verizon.verifypttapitestpreload disables cleanly (disabled-user).
- PTT+ registers com.kodiak.intent.action.PTT_BUTTON at mPriority=1000000, which is why it wins the side button over LP&T Keys.
- com.android.webview is enabled=3 DISABLED_USER (lastDisabledCaller shell:2000) on this handset, though cli/configs/bloatware/full.yaml lists it under preserve_packages for SmartList. This phone's filter predates that rule.
- Every LP&T app on it was installed 2026-03-13 14:56-14:58. The whole stack is the March 13 deploy, while the repo carries newer artifacts.
- Tech Mode = 2.0.0 / versionCode 20, DEBUGGABLE, TechnicianModeReceiver + LptAccessibilityService registered. agent/lpt-techmode/app/build.gradle is ALSO versionCode 20 / 2.0.0, built APK 2026-09-08 17:29. Same version string, different artifact (installed 27,900 B vs repo 43,555 B).
- Tech Mode reinstall is SAFE: the v2 signing cert is byte-identical between the pulled installed APK and the repo build, sha256 4e179bf78616553df676f268c06fbf01ebac5fd2a13b4953af82e31410b96b1b. No uninstall needed.
- ADB was never at risk on this handset: `adb get-state` = device, adb_enabled=1, development_settings_enabled=1.

HAZARD WORTH KNOWING
cli/lpt/adb/installer.py `_recover_from_update_incompatible` does `pm uninstall` then install when a reinstall raises INSTALL_FAILED_UPDATE_INCOMPATIBLE or INSTALL_FAILED_VERSION_DOWNGRADE. On a handset where the app IS the recovery path (LP&T Tech Mode), an uninstall followed by a failed install removes the unlock. That is the real lockout vector in a re-deploy, not the security phase. Compare signing certs before ever letting a re-deploy touch techmode.

TWO TOOL TRAPS
- A PowerShell helper function named R silently resolves to the Invoke-History alias; every call fails with "Cannot locate the history for command line ...". Never name a function R in pwsh.
- `journal.py append` takes `--body` / `--body-file` and a positional kind. `--text` is not a flag (exit 2), and a failed append exits non-zero while still echoing the body, which looks like success.
