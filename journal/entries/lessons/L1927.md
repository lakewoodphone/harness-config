**L1927 · The journal id allocator now requires a reserved window -- and the first journal write on any machine will push**

**The allocator no longer mints from `max(visible)+1`.** `journal/tools/journal.py` now
requires a RESERVED WINDOW before it will write a new id. Full design, the three candidate
shapes and the two rejected, and every measurement: `docs/mesh/108-id-allocation.md`.
Proof, repeatable: `python journal/tools/verify-alloc.py` -> 11 checks, 0 failures.

**What a future session must know before the first journal write on any machine.**

1. **The next `append` on a machine performs a `git push`.** It claims a window
 (`journal/alloc/bands.tsv`, 64 ids) and pushes it to `origin/master` so the other machines
 can see it. That is the whole mechanism; an unpushed claim is worthless.
2. **If it cannot push, it writes NOTHING and exits 4.** Fail-closed is deliberate. The live
 tree currently has NO reservation, so the first write is in this state -- expected, not a
 fault.
3. **Within its window a machine works offline**, including `--no-fetch`. At the edge of the
 window with no origin it refuses. Measured.
4. `journal.py claim [kind]` reserves explicitly; `journal.py claim` with no kind does all five.
 `next-id KIND --plan` says whether a write would be allowed and exits 4 if not.

**Scratch/fixture trees are unaffected**: no ledger anywhere and no origin ref means a
single-machine tree and the old behaviour. That is why `selftest` needs no change.

**The lock leak was TWO bugs, and the second looked like the first.** `release_lock` decided
ownership with `token in _rl(lock)`, and on Windows `msvcrt.locking` makes the locked byte range
unreadable from any other handle, so `_rl` raised `PermissionError`, the bare `except OSError`
turned it into `""`, and the token test was False for EVERY command. **All** mutating commands
leaked `journal/.lock` -- `questions`, `import-legacy`, `index`, `state`, `append` -- not just
the two that were reported. Fixing the read was not enough: `os.open` takes no
FILE_SHARE_DELETE, so the open HANDLE blocks the unlink; `unlock, then unlink` still fails with
WinError 32 and only `unlock, close, unlink` works. Order is now prove-ownership -> drop lock ->
close fd -> unlink. `selftest` 239 of 240 -> **240 of 240**.

**Three git plumbing facts that each produced a silent failure.** `git mktree` refuses an entry
whose name contains a slash (`fatal: path ...? contains slash`) -- a nested path needs one call
per level. A temporary index (`GIT_INDEX_FILE` + `read-tree` + `update-index --index-info` +
`write-tree`) SILENTLY DROPS the new file: `update-index` prints `Ignoring path ...`, and
`write-tree` returns the parent tree unchanged, so the commit lands, exits 0, and does not
contain the file -- the worst possible shape for a safety mechanism. And `git_max()` returns a
`(number, rev)` TUPLE: putting it straight into `max()` raised a TypeError inside a guarded
call, so the reservation was computed and then ignored and two machines reserved the SAME window
while every individual call looked correct.

**`note_git_ceiling()` is no longer dead code** -- it is called from `git_max`, guarded by
`if nums:` so an empty read can never lower a ceiling. `allocation_ceiling()` therefore still
reads a real measured ceiling instead of an always-empty `{}`.

**Still true, recorded not fixed:** `check` cannot see a cross-tree collision (single-tree by
contract; the cheap fix is `git hash-object --stdin-paths` locally + `git ls-tree -r
origin/master` upstream, and the right home is `idguard`, not `check` -- `check` is on the read
path), and `idguard` undercounts because it reads a generated cache a committing writer must
remember to rebuild.

**Not verified:** nothing was run on ZABZ-TECH, secratary, zabz-tech-linux or the VPS. The
two-machine proof is a simulation on this machine. A rejected `git push` under genuinely
simultaneous claims was not forced, so the retry loop is reasoned about rather than exercised.
