**L3140 · R-Studio listing grammar (combinedTree + _fld_ arrays) and how to audit a 300DDR recovery listing**

TWO R-Studio export formats arrive from 300DDR, and neither parses the obvious way. Measured 2026-09-30 on tickets 74115 and 73459.

FORMAT A — "combinedTree" (T74115-fishman-2TB.zip): the zip holds a SHELL `*-File-Listing.html` (81 KB, carries only the page furniture) plus `data.js` (~45 MB) which is the actual data. `data.js` is one line starting `const combinedTree = {...};` then a `console.log`. Strip the `const` and trailing statement, `json.loads` from first `{` to last `}`. It is a genuine nested tree: folder nodes `type:"folder"`, files carry `name, size, good_size, bad_size, status, date`. `root.stats` is a manifest you can reconcile against: my walk reproduced total_files/folders/total_size/good_size/bad_size EXACTLY. Always do that reconciliation — it is free proof the listing is not padded.

FORMAT B — "Dynamic HTML Report" (T73459, self-contained ~65 MB HTML): there are NO `<tr>` rows. Data is `var _fld_NNNNNN = { 'p': BigInt('<record id of parent>'), 'n': "<folder name>", 'c': [[BigInt('id'),A,B,epoch,"DD.MM.YYYY HH:MM:SS","name",flag], ...] };` — one object per folder. In the 256GB case: 26,941 `_fld_` objects, 711,309 record tuples.
 * B is the discriminator: B=1 => file (684,369), B=0 => folder entry (26,940). It equals the count of `_fld_` objects minus the root, which is how you verify it.
 * A is a size in bytes for files. Do NOT add A over all rows and call it recovered volume: on T73459 that summed to 764.8 GB against a 256 GB device, i.e. impossible, because a multi-pass carve reports the same content many times over. Say that plainly instead of reporting the impossible number.
 * epoch is a Unix SECONDS value; the file's own DD.MM.YYYY string agrees with it within timezone (verified 0 mismatches >1 day in 200k samples). Either is usable as authority.
 * The tail of the file is pure UI script (`function st(n,v){...}`) — ignore it.

PYTHON REGEX TRAP that cost me a run: `((?:[^\"\\]|\\.)*)` is WRONG for a quoted JS string — the greedy `*` binds to the `\\.` alternative and the group swallows the closing quote, the comma and everything after. It matched 14 folders instead of 26,941 and produced silently absurd output. It must be non-greedy: `((?:[^\"\\]|\\.)*?)`. When a parser returns a suspiciously round small number, check the regex before trusting the result. Also: `grep` over a single 65 MB one-line HTML returns 250 truncated matches and is useless — write a streaming Python pass instead.

EVIDENCE OF GENUINENESS worth looking for in any drive listing, all of which were present on 74115 and made the call easy: the manufacturer's own root bundle (`Start_Here_Win.exe`, `Start_Here_Chromebook.pdf`, `Warranty.pdf`, `Start_Here_Mac.app`), `.dropbox.device`, `winamp_metadata.dat/.idx`, `$RECYCLE.BIN`, `System Volume Information`. Counter-evidence to look for: true 8.3 short names (`name~N.ext`), `<3 chars>~N.ext`; Unicode private-use bytes where `(`/`)` belong (U+F028/U+F029) — both present on 73459, 408 and 425 records respectively; `file WxH_NNNNNN.jpg` carving names; epoch-0 timestamps on hex-named files (`02F2AC20.ai`).

DEDUP IS THE PAYING QUESTION. `(basename,size)` collapses 90+ slides named `Slide1.JPG`, `Thumbs.db`, `desktop.ini`. For a carve, normalise copy markers first (`(N)` suffix, leading `~`/`_`, `_NNNNNN` suffix, `file WxH_` prefix), then count unique keys. On 73459 that moved 684,369 records -> 252,804 unique keys and 764.8 GB -> ~490.9 GB. Do NOT count as duplicates what is merely the same filename in two different folders: 74115 had 84,358 records whose NAME repeats but **zero** exact duplicates within the same folder, which is a clean tree.
