**L1975 · A comment asserting a premise is not evidence for it — and "it works" after a rebuild proves nothing until the process restarts**

RULE. Two things that read like knowledge and are not.

1. A COMMENT ASSERTING A PREMISE IS NOT EVIDENCE FOR IT.

`packages/plugin-cost/scripts/build.mjs` carried a comment saying the `createRequire` anchor "only
has to be a real file", because `createRequire` was believed to serve `node:` builtins only. Ten
lines below it, in the same file, `importBindings()` bound a BARE package specifier
(`@deepseek-ai/schemastery`) through that same anchor — and the generated file required it at line
22. With `DSH_HOME` unset the anchor became `C:\Users\ezabz\profiles\web\package.json`:
`USERPROFILE`, which is the PARENT of the DSH home and not a stand-in for it. The plugin tree failed
to load and the engine exited 1. Read the code the comment describes, not the comment.

2. "IT WORKS" AFTER A REBUILD PROVES NOTHING UNTIL THE PROCESS RESTARTS.

The rebuild was at 10:45. The engine that then ran all day (pid 4880) had the PRE-guard tree in
memory and never loaded the broken module, so DSH looked healthy for eleven hours. The fault was
ARMED, not live. It detonated at 21:31 on an unrelated reboot and the owner could not start DSH at
all. A live-reload junction (`~/.dsh/profiles/web/node_modules/dsh-plugin-cost` -> the checkout) is
what makes this so easy to do: whatever was built last is what the profile mounts, with no install
step and no version to compare against.

WHAT TO DO INSTEAD — both measured on 2026-09-17/18 on ZABZ-YOGA:

* For (1): assert the BEHAVIOUR, not the shape. `packages/plugin-cost/test/cold-boot.test.mjs`
 extracts the emitted `requireAnchor()` and RUNS it with `DSH_HOME` cleared, then compares the
 result to the machine's real profile. It goes red against the old generator on any machine,
 whether or not DSH is installed there, because nothing is loaded to make the point.
* For (2): test the path the process takes when it STARTS, not the one it takes while running.
 Appendix B of the incident — "load the module with DSH_HOME cleared" — is a one-line reproduction,
 and it is now the `coldboot` check in `test/verify.mjs`, run immediately after `build`. A build
 that is in sync with a generator that emits a bad anchor is still an engine that cannot boot.
* And commit the work: the uncommitted artifacts were live in the profile the whole time, which is
 the other half of why nobody could see it coming.

EVIDENCE: `docs/incidents/2026-09-17-dsh-engine-boot-failure/` (README "Closing addendum",
`diagnosis-report.md` §4 and §8, and `engine-boot-failure-stderr.log` — line 5 is the fault, line 63
is `Node.js v24.12.0`). Red-then-green proof: `%TEMP%\plugin-cost-oldgen` with the old fallback
rebuilt → 9 of 12 checks FAILED, discriminator `FAILED: MODULE_NOT_FOUND`.
