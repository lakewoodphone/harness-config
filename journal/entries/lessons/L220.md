**L220 · Multi-part research: fan out to subagents, verify only the spine yourself; reddit .rss atom feed is the way in**

L232 · Research method that worked at scale, and the one that failed

WHAT FAILED (do not repeat): having the coordinating agent do the research itself. I spent my first
stretch on web_search/web_fetch by hand for what became 10 mastered facts, and it consumed a large
share of the context window. The correct split is: subagents do the breadth, the coordinator does
only the load-bearing facts.

WHAT WORKED, and is now the pattern for any multi-part research deliverable:
1. ONE subagent per sub-question, all launched in a single message so they run concurrently. Eight
 agents covered four task areas with room for overlap — the overlap is a feature, because two
 agents independently hitting the same fact is free cross-verification (it is how the PayPal
 resale-exclusion and the escrow card-fee tier got caught as errors in my own draft).
2. Every subagent gets: a named output FILE path, the requirement to cite a real URL per claim, an
 explicit "INFERENCE:" label for reasoning, and — the highest-value instruction — an explicit
 demand to state what it could NOT find. That last one is what produced the honest negative
 findings (no FTC action, no state AG action, no case law on point) instead of padding.
3. Tell each subagent its summary must be short and that the file carries the detail. Then the
 coordinator never reads the 40-80 KB files end to end: read the returned summary, and use
 grep for '^#{1,3} ' for the structure and grep for URLs to lift citations.
4. The coordinator re-fetches ONLY the facts the final report's spine depends on. That is what
 caught the biggest error in this whole job: a subagent reported the New Jersey bill as enacted,
 I had written it as pending from the bill text's own "as amended" wording, and a single live
 fetch of the chaptered-law URL (pub.njleg.gov/Bills/2024/AL25/154_.HTM) settled it — it is
 P.L. 2025, c.154, approved 2025-10-20. A bill URL and a chaptered-law URL are different evidence
 and the difference changed the advice.

TOOLING FACTS worth keeping:
- reddit.com blocks ordinary fetches, but the ATOM feed works:
 https://www.reddit.com/r/<sub>/comments/<id>/<slug>/.rss?limit=100 returns the post body AND
 ~100 comments verbatim with timestamps. Only ONE such request per batch or it returns
 "unsupported content type". Older threads: web.archive.org/web/<year>id_/old.reddit.com/<path>.
 Direct reddit HTML, .json, pullpush.io, howardforums, bbb.org and fbi.gov all 403.
- web_fetch on escrow.com returned the whole fee table only through the MCP fetch tool with an
 explicit max_length; the built-in web_fetch truncated it. Same for the truncated "content
 truncated" pages. When a page's key numbers are in a table, use mcp__fetch__fetch_txt with
 max_length rather than giving up on the source.
- law.cornell.edu serves full statute text to a plain fetch and is the fastest route to exact
 statutory language (better than summarising a secondary source).
- The FTC's own press-release pages 403 a scripted fetcher while remaining live; a search result
 for the exact title is still usable evidence of existence, but the body must be labelled
 unverified rather than quoted.
