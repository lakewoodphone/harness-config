## The office desktop resolves almost nothing, and every mesh child it receives dies

MEASURED 2026-10-08 ~02:50Z (22:50 local) from ZABZ-YOGA, over ssh to `desktop-ts`.

**What is true.** On ZABZ-TECH these names all answer `DNS name does not exist`: apple.com,
cloudflare.com, microsoft.com, google.com, github.com, api.deepseek.com, api.openai.com,
registry.npmjs.org, www.wikipedia.org, amazon.com, stackoverflow.com. `example.com` DID resolve
(172.66.147.243). The same queries against the router (192.168.50.1), 8.8.8.8, 1.1.1.1 and
100.100.100.100 all fail identically, so the fault is the host, not the upstream.

**The control that proves it.** `secratary`, on the SAME LAN with the same configured DNS server,
resolves both: `dig api.deepseek.com @192.168.50.1` -> d3bbv8sr76az5s.cloudfront.net, and
`curl https://api.deepseek.com/v1/models` -> 401 (reachable). Network and router are fine.

**The cause.** `C:\Program Files\KosherFilter\appsettings.json` has `DnsInterception.Enabled: true`,
`Filter: "udp.DstPort == 53 or udp.SrcPort == 53"`, `BrokerHost 127.0.0.1:1080`; the companion
`KosherFilterRelay` forwards to a remote filter upstream at 2.28.33.58:1080 with a per-device
credential (do not copy it). Both services are Running and the upstream accepts TCP. Everything not
permitted comes back NXDOMAIN.

**What it costs the mesh, measured twice.** A `subagent` dispatch placed on zabz-tech returned, both
times byte-identically: *"the remote one-shot exited 1 and produced no final message; stderr tail:
... PermissionError: ... personal-secretary-mvp\data\logs\mcp-launcher.log ... dsh: TRANSPORT:
DeepSeek API request to https://api.deepseek.com failed"*. The node was identified because its own
`data/logs/mcp-launcher.log` was written at 22:47:24, inside the dispatch window.

**The broker already knows.** `GET /nodes?fresh=1` on the authority (ssh secratary-ts,
http://localhost:3091) reports **zabz-tech `transport.v1: false`, measured 2026-10-08**, while
`zabz-tech-linux` is true and `secratary` is unmeasured. A direct `POST /place` with the laptop
excluded chose **zabz-tech-linux** and ranked zabz-tech as "transport v1 MEASURED BROKEN".

**And with that, dispatch works.** A live child returned `MESH-HOST: zabz-tech-linux`, exit 0 in
17.6 s, `placement = broker`, `pressure = HIGH (85.1% of physical committed)`.

**What a future session must do with this.**
- Do NOT read "the mesh is down" from a failed dispatch. Print the per-node transport table first:
 `ssh secratary-ts` then `curl -s "http://localhost:3091/nodes?fresh=1"`.
- Capacity and usability are different axes: zabz-tech had 18 free slots, 38 GiB free RAM and
 242 GiB free disk, and no DNS. 18 slots of a node that cannot call the model is zero capacity.
- Do NOT touch the filter to make a node work. It is the owner's content-filtering policy and it
 holds a credential; whether a given host may reach the model API is the owner's decision, not a
 routing decision.
- This is not only a mesh problem: the office desktop currently cannot reach the model API, npm or
 github from any process, including the 8 sessions that report live there.
