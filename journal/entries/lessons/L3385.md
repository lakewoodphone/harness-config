**L3385 · Worktree brief constraints can contradict their own definition of done — do the reachable part and say which half is unreachable**

Session: fixing the work-orders status defect in worktree C:\Users\ezabz\code\_lpt-staff-intake-api, branch lpt/wo-status-20261006, commit 2b04eac15 (2026-10-06).

The brief said 'Work ONLY in _lpt-staff-intake-api' and 'Do not touch frontend/', but two of its three findings were resolved ONLY in frontend code (the detail page normalising AWAITING_DIAGNOSIS/IN_REPAIR to CHECKED_IN before the call, and the header CTA testing for 'IN_PROGRESS', a value that is not in OrderStatus). The definition of done named only backend test commands, so the brief was internally inconsistent.

What worked: fix everything reachable inside the named scope, pin the reachable half with tests that would fail against the old code, and report the unreachable half with exact file:line plus the stopping reason — do not silently widen the scope and do not report the defect as fixed.

The reachable half was real and was the root cause on the API side: backend/src/types/work-orders.ts kept a six-value WORK_ORDER_STATUS_VALUES while the Prisma OrderStatus enum and packages/shared-types both list all eight, so orderStatusSchema rejected the two statuses outright and the frontend's normalisation was papering over a server-side gap.

Rule: when a brief's scope and its definition of done disagree, the scope wins for edits and the definition of done wins for evidence. State both counts — what is fixed, what is a documented follow-up.
