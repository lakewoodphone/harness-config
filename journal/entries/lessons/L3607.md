**L3520 · Read the CALLER before judging a deployed script — its default is not its invocation, and its comment may be true in context**

Measured 2026-10-11 on the authority. I found `/root/fts-convert.sh` with the header *"Safe to run
because `/root/authority.db` is a DISPOSABLE copy: the authority still lives on the office box and a
fresh copy can be made at any time."* Since the office box is now FROZEN and `authority.db` **is** the
authority, I concluded the premise was dangerously stale, recorded it in **H3429** as a hazard, and was
one step from inserting a warning block **into the deployed script**.

**The grep for the caller showed the opposite.** `harness-config/scripts/mesh/cutover-authority.sh`:

- `:33 FTS_CONVERT="${CUTOVER_FTS_CONVERT:-/root/fts-convert.sh}"`
- `:31 CLOUD_FINAL="${CUTOVER_CLOUD_DIR:-/root/cutover}/final-src.db"` ← the conversion target
- `:229 hdr "4f — convert the shipped copy (never in place on the serving copy)"`
- `:230 c_run "$(convert_script)"` … `:231 case "$OUT" in *verdict=ok*) pass …`
- `:235 diff_check()` — which **explicitly expects** the table count to differ, `pass "differs as
 EXPECTED: the conversion reclaims duplicated FTS content"`

So the script is **always** invoked with `DB=<a shipped copy>`, never bare. Its `DB=/root/authority.db`
default is a footgun but it is not the invocation, and the comment is true **for how the tool is used**.
And the ~7.2 GB live duplication I "found" is an **expected intermediate state** of a cutover that is
still mid-flight (`docs/mesh/129` = stages 0–2 done, next is the freeze; `docs/mesh/130` = freeze
applied, snapshot running; `docs/mesh/128:48` already records the conversion as **proven** at
21.4 GiB → 13.06 GiB).

**This is rule 0's third face.** Rule 0 is written about *building* something that already exists. This
was the same error pointed the other way: **reporting a defect that already has an owner, a plan, a
proven implementation and a scheduled stage.** "Read the register before you design" has a twin —
*read the caller before you judge* — and the cost of skipping it is a confident false alarm plus a
unilateral edit to someone else's live tooling.

**RULES.**
1. **Find the caller.** `grep -rl <script> ~/code` costs seconds and would have prevented this
 entirely. A deployed script's default is not its invocation; a deployed script's comment is not a
 claim about the current world, it is a claim about the world it was written for.
2. **The repo copy is the truth about intent.** `/root/fts-convert.sh` is deployed; the harness that
 drives it, its expected table diff and its rollback live in `harness-config/scripts/mesh/`. Read the
 repo, not the deployment.
3. **Never edit a deployed copy of another workstream's live tooling** — least of all mid-cutover,
 where a script asserts on its output. An append to the journal is the right instrument, never a
 `sed` on their box.
4. **"Mid-flight" is a state, not a defect.** Before calling something broken, ask what stage it is in.
 A half-applied migration and a broken migration look identical from one reading.
5. A default that points at production is worth fixing — **by the workstream that owns the tool**.

**Corrective to H3429**, which states the premise is a live hazard: it is not. The premise holds for
the documented invocation. What remains true and useful from that entry: the duplication is real and
measurable (~7.2 GB), the converted 13.06 GiB artifact is not what serves, and the cutover stage that
removes it has not been run against a fresh copy yet.

Evidence: `harness-config/scripts/mesh/cutover-authority.sh:31,33,229-231,235-241`;
`docs/mesh/126-authority-cutover-runbook.md:186`; `docs/mesh/128-HANDOFF-complete-the-cutover.md:48`.
