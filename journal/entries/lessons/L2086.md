# L1926 — the schema was 82% wrong and nothing said so, because nothing validated

## The measurement

Adding one optional string field to the sync-record schema, I checked whether my change broke any
record. It had not — but the check produced a number nobody had:

| revision | records | invalid against the repo's own schema |
|---|---|---|
| before my change | 383 | **315** |
| after my change | 383 | **315** |

**315 of 383 records — 82% — fail the schema in the same repo they live in.** Examples:
`14in-laptop-weitman` carries `communications`, `evidence`, `issue`, `nextAction`, `rootCause`;
`2026-05-13-asus-vivobook-f512ja-klein` carries `outboundMessages`; one record has a `null` where a
string is required; two are missing a required `partnerName`.

The immediate consequence: `operational` is declared `additionalProperties: false`, and 82% of the
corpus violates that. So the declaration is **aspiration, not constraint** — a comment wearing a
machine-readable costume.

## Why nothing caught it

Nothing validates. The push tool mentions the schema three times incidentally and calls no
`validate()`. The drift verifier did not check it either. So the schema's only reader is a human who
happens to open it, and a human reading `additionalProperties: false` will believe something is
enforced when nothing is.

## The rules

1. **A schema with no validator is documentation, and it must be labelled as such.** If the file does
 not say "nothing enforces this today", it is actively misleading — worse than no schema, because it
 creates false confidence in constraints that do not exist.
2. **When you add a field to a closed schema, MEASURE how many existing records violate it.** The
 answer changed my commit message: I had written "the schema now permits X", which implies the rest
 was conformant. It is not, and saying so is the difference between a change and a lie.
3. **Check for breakage before claiming success, and compare against the PRIOR revision.** Running the
 validator only at `HEAD` would have shown 315 invalid records and left me unable either to claim or
 deny that I caused them. Running it at `HEAD~1` as well is what produced the honest answer in one
 command.
4. **A large diffstat is not a large change.** This commit showed 620 insertions / 586 deletions for ONE
 added line per record, because git counts the long single-line `internalSummary` values as rewritten
 hunks. Reading the actual diff (one line: `true` -> `true,` plus the field) is what confirmed the
 change was surgical. Diffstat is a size signal, not a content signal.

## What should happen next, and the choice is real

Either (a) add a validator and bring 315 legacy records into line — real work, and it would have to
decide whether those extra keys are meaningful or debris — or (b) drop `additionalProperties: false`
and document the block as open, as the sibling `pricing` block already is (its description says
legacy records carry ad-hoc keys and the block is "documented but not closed"). The one thing that
should not continue is a schema that is 82% wrong and silent about it.

## Evidence

- `jsonschema.validate` over 383 records at `HEAD~1` and `HEAD`: 315 invalid at both.
- The push tool: `grep -cE 'jsonschema|validate\(|schema'` -> 3, all incidental; `--dry-run-all` report
 unchanged at `CREATE 7, SKIP 376, ERROR 0`.
- The sibling `pricing` block in the same schema file already documents its openness — so the repo
 knows how to do this, and simply did not do it for `operational`.
