**L3442 · Printing a secret's LENGTH is the probe; printing its VALUE is the leak - \, never \**

MEASURED 2026-10-09, ZABZ-YOGA. Auditing the LPT auth config, I ran over ssh:

 for k in PAY_CODE_HASH_SECRET LPT_SSO_SHARED_SECRET ...; do
 v=$(docker exec $c printenv $k); if [ -n "$v" ]; then echo "$k = $v"; fi
 done

The intent was presence and length, to answer "is this secret configured on the test box".
The effect was that the LIVE LPT_SSO_SHARED_SECRET for production AND for test was written into
the session transcript, and from there into every log of this conversation.

THE RULE
When probing an environment for whether a secret exists, never let the value reach stdout. Print a
presence flag and a length, and nothing else:

 if [ -n "$v" ]; then echo "$k: SET len=${#v}"; else echo "$k: MISSING"; fi

`echo "$k = $v"` is the mistake. `${#v}` is the fix. On PowerShell the same trap is
`Write-Output $env:SECRET` versus `($env:SECRET).Length`.

WHY THIS IS WORSE THAN A NORMAL MISTAKE
The value I leaked is shared: it is the same secret the rentals and chumash apps present to
POST /api/auth/sso/assert. Rotating it is therefore not a one-host edit - it is a coordinated
change across three systems, with a window where SSO asserts fail. I turned a 10-second config read
into a cross-system change.

RELATED, ALREADY ON RECORD
P13b is the same family (an API key leaked into a transcript). That entry did not prevent this one,
because it recorded the incident and not the shell idiom. This entry records the idiom.

SECOND MEASURED FACT, SAME SESSION
The identical probe is safe for non-secrets: NODE_ENV, CUSTOMER_PORTAL_ENABLED and
CUSTOMER_ACCOUNT_CREATION_MODE were printed by value and that was the point of the check. The rule
is about secrets, and the way to obey it without thinking is to print length by default and opt in
to a value.
