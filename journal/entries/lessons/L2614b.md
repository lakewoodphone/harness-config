**L2614b · Existence is not enough to resolve a tool (probe the (node,bin) PAIR), and the exec API corrupts non-ASCII in scripts**

TWO SMALLER TRAPS FROM THE SAME HOUR, both worth more than they cost.

1. EXISTENCE IS NOT ENOUGH TO RESOLVE A TOOL. My profile gate looked for the first dsh bin.js that
 EXISTED and ran it. On secratary that was `~/.dsh/profiles/node_modules/@deepseek-ai/dsh/lib/
 bin.js` - a vestigial 9 KB copy - launched with `/usr/bin/node` v20. That pair exits 0 with NO
 OUTPUT for every argument including -V (L173's entry-point no-op), so the gate declared a healthy
 machine CANNOT-BOOT. The install that machine really uses is `/home/zabz/dsh-engine/...` with
 `/home/zabz/node/bin/node` v22.
 The fix generalises: probe CANDIDATE PAIRS (node, bin) and take the first that ANSWERS, not the
 first whose path exists, and report which pair produced the verdict. And when nothing answers,
 say REFUSAL - "I could not exercise it" is not "it is broken". A gate that cries wolf gets
 ignored exactly when it matters, which makes it worse than no gate.

2. THE exec API CORRUPTS NON-ASCII IN UPLOADED SCRIPTS. A PowerShell script containing an em-dash
 came back as mojibake (`-` -> `?\"`) and failed to PARSE on the target, which looks like a script
 bug in a script that is correct on disk. Keep every script sent through that channel to 7-bit
 ASCII. This is a sibling of the already-recorded rule about `&&` chains and quoting: the channel
 rewrites bytes, so do not send anything you would not send through a 7-bit pipe.
