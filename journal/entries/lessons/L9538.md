**L9538 · Deployed script vs repo vs staging: three copies, one executable, and staging was oldest**

Lesson: the deployed copy was the truth and the repo was a day behind - and a stale installer
almost made that fatal.

Measured 2026-10-19 while committing a fix to the owner queue:
 /root/bin/owner-queue.py 171,327 B, 2026-10-19 <- what RUNS
 harness-config/scripts/owner-queue/owner-queue.py 161,320 B, 2026-10-18 <- what the repo had
 /root/_staging/files/owner-queue.py 40,661 B, 2026-10-11 <- what the installer copies
docs/mesh/139-install-tools.sh copies /root/_staging/files/* -> /root/bin, so an install from that
staging dir would have REVERTED four days of queue work, not just my fix. The same shape appears
in precondition: premise-check.py was 25,891 B in the repo and 43,904 B deployed (four days).

What to do about it, in order, whenever you edit a script that runs on a host:
1. hash the deployed file and the repo file BEFORE editing (stat -c %s is enough to see drift);
2. if they differ, the deployed one is the truth of what has been running - copy it INTO the repo
 and commit that as its own step, so your change is a small readable diff on top;
3. check the installer/staging path too, not just the repo: 139-install-tools.sh stages from
 /root/_staging/files, which was older than both.
4. After committing, grep the file you just copied for credentials - a live script can carry
 config the repo copy never had.

The trap is that this estate has three candidate "sources" for the same script (repo, staging,
deployed) and only one of them is executable. The one that runs is the one to compare against.
