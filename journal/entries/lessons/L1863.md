**L1863 · Pushing a file over an ssh stdin pipe does not deliver identical bytes; base64 does**

MEASURED 2026-09-17 while pushing `scripts/mesh-hygiene.sh` to the Mac mini (whose tailnet path is
relayed and flaky, 81 §2).

`Get-Content -Raw <file> | ssh <host> "cat > /remote/path"` does **not** deliver identical bytes: the
file arrived 2 bytes larger with exactly one `\r` in it, so `shasum -a 256` did not match the local
file (53216 vs 53214 bytes; local `e5127a59…`, remote `d9922b96…`) even though the script ran
correctly. PowerShell appends one CRLF when it pipes a string to a native command's stdin.

Byte-identical delivery, and it survives the relay as well as the pipe did:

 $b64 = [Convert]::ToBase64String([IO.File]::ReadAllBytes((Resolve-Path scripts\mesh-hygiene.sh).Path))
 $b64 | ssh -o BatchMode=yes -o ConnectTimeout=15 mac-mini-ts "base64 -d > /tmp/mesh-hygiene.sh"

Verified: remote `wc -c` 53214, `shasum -a 256` `e5127a5946017fa8232fa9450387b50e7b1ec97abf7582372
81432015cc93ee0` — identical to the local file. `scp` to a Linux host delivered identical bytes in
this session (`sha256sum` matched), so the pipe is the specific danger, not the relay.

Two rules follow. When the destination machine will RUN the file, a trailing newline is harmless; when
the point is that two machines hold the same artifact, prove it with a hash and use base64. And do not
conclude "the push worked" from "the script runs" — a one-byte difference is invisible until something
else compares hashes.
