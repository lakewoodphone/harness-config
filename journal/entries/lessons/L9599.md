**L9599 · Correction to L9598: webhook_events is not a delivery log, it is the pay-before-pickup idempotency table**

L9598 said the Stripe webhook is enabled but not landing, and that payment status therefore moves only on the nightly reconciliation. THE SECOND HALF IS WRONG. Corrected here, citing L9598 and W2752b.

What is true, read in the deployed backend on lpt-apps (/app/backend/src/services/payments/): a webhook_events row is written only by the pay-before-pickup handler, for its single event type checkout.session.completed, as layer 1 of its idempotency. Every other delivered event is handled without touching that table. So webhook_events is a record of processed online checkouts, not a delivery counter, and "two rows" means two online checkouts, not two deliveries.

W2752b had already settled this on 2026-10-13 - webhook delivers, route works, the 400-without-signature probe passes - and it names the exact trap I repeated: the backend logs errors only, so absence from the log is not absence, and the same holds for a table that records one event type out of five subscribed ones.

The transferable rule, which is the measurement rule again: before treating an absence as evidence, ask what WRITES the thing you are looking at, and whether that writer ever writes on the path you care about. Two different questions - "did anything arrive" and "did anything of this kind get processed" - and only the second one has a table.

Consequence for the actual case: the correction makes "he has not paid" stronger, not weaker. A successful card payment through the pay link would have been processed by that webhook within seconds and marked SUCCEEDED; the PENDING row would not survive a real payment. The independent proof stays Stripe's own object (amount_received 0, requires_payment_method).
