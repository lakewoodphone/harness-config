**L3433 · All DSH sessions and all VS Code Copilot chats are archived forever, off-machine - the rule, where the archive is, and the four traps**

**The owner's words, 2026-10-09:** *"remember we need copies of all vscode copilot chats and all dsh sessions forever for data and training data, and those a copy always needs to exist of this should be documented, did you know those rules"*

**The rule.** Every DSH session and every VS Code Copilot chat is archived **forever**, and a copy must always exist **off the machine that wrote it**.

**Why.** It is the company's training data and its institutional memory. A conversation on one laptop is one disk failure, one theft, or one `pm clear` from gone. This business has lost customer data twice. This rule exists so its own reasoning cannot be lost the same way.

**Recorded where it will be found:** `harness-config/AGENTS.md` § 1, plus this entry. It is written in AGENTS.md because that file is *demonstrably read* — it was injected into the session that wrote it, unprompted, the moment the file appeared.

**Where the archive actually is — and what I got wrong on first reading.** The brief I was given said the DSH archive might be stale and the Copilot archive appeared never to have been done. Both halves were wrong, and the correction matters more than the original belief:

- `secratary:/home/zabz/dsh-archive/dsh-archive.db` (354 MB, mtime 2026-09-11) is **frozen by design** and says so in its own `RETIRED.md`. Reading it as the live archive is exactly how a non-existent crisis gets reported. It is not a gap; it is evidence of a migration.
- The live DSH archive is in the authoritative DB: `secretary.db.dsh_sessions` **5,424 rows**, `dsh_session_events` **1,766,713 rows**, newest per machine 2026-10-09T01:15Z (zabz-yoga, 1.1 h old). `check-dsh-freshness.py` passes, exit 0. **Not stale.**
- The Copilot half **did** exist: `vscode_chat_sessions` 1,608, `vscode_chat_messages` 4,373, `vscode_chat_exports` 286.
- But the Copilot half is **21 days stale** — newest export `2026-09-18T07:26Z` — and its hourly task `PersonalSecretary-PushVSCodeChats` reported `LastTaskResult=0`, **success**, every hour throughout. That is the failure this rule now guards against.

**Four traps, each measured, each now written into AGENTS.md:**
1. A frozen store is not a gap. Check `RETIRED.md` before declaring staleness.
2. A workstation-side scheduled task that reports success cannot distinguish "nothing to send" from "I am broken". The pull is driven from the always-on host.
3. `scripts/vscode_chat_extractor.py` silently skips any chat file over 50 MB (`_MAX_JSONL_BYTES`). On ZABZ-YOGA, **14 files exceed 50 MB** and are in no store anywhere. Archive bytes, never a lossy projection.
4. Redaction changes bytes, so a cursor keyed on the *stored* hash re-sends every redacted file forever. The cursor is keyed on `source_sha256`.

**Secrets.** Credential stores are refused by name: VS Code `state.vscdb` (its `ItemTable` *is* the encrypted secret store), the Copilot CLI `session-store.db`, `.env`, `id_*`, `*.pem`, `*.key`. Card numbers and credential shapes inside text are redacted and re-scanned on arrival, so a client's redaction is verified rather than trusted. Precedent: **P13b**, 2026-09-11 — *"I leaked a live API key into the session transcript."* A conversation missing a card number is recoverable; a card number in a training corpus is not.
