**L12371 · A local typecheck passed against a stale Prisma client while the container build failed**

**Measured 2026-10-25, on `lpt/abandoned-card-box-20261025` (PR #658).** I wrote `order.status === 'COMPLETED' || order.status === 'CLOSED'` and ran `pnpm --filter phone-and-tech-backend typecheck` locally: exit 0, and the repo's own `validate-order-status-members.ts` printed *"8 members declared, 1253 source files scanned, 0 stale references"*. The Docker image build then failed:

 src/services/payments/card-payment-in-page.service.ts(691,11): error TS2367:
 This comparison appears to be unintentional because the types 'OrderStatus'
 and '"COMPLETED"' have no overlap.

**The reason is the client, not the source.** `OrderStatus` lost `COMPLETED` when `CLOSED` was added (migration `20261020170000_order_status_add_closed`), but `node_modules/.prisma/client` in a long-lived worktree is only regenerated by `prisma generate`. A stale client still declares the old union, so `tsc` is answering a question about a schema that no longer exists. The Dockerfile runs `prisma generate && pnpm run build`, so CI had the truth and my machine did not.

**What to do:** before trusting a local typecheck that touches a Prisma enum, model or field, run `pnpm --filter phone-and-tech-backend exec prisma generate` first. Better, wire it into `worktree:setup` so a worktree cannot sit on a stale client at all — `worktree:setup` currently builds `shared-types` and the tsconfig project but says nothing about the generated client.

**Generalisation worth keeping:** "typecheck passed" is a claim about the client that was installed, not only about the code. The same shape applies to any generated artefact a build regenerates and a dev tree caches.
