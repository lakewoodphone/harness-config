**L1693 · A Dahua HTTP 401 proves nothing about the password - implement Digest before blaming the credential**

A Dahua HTTP 401 proves NOTHING about the password. Implement the Digest handshake before concluding a credential is bad.

MEASURED 2026-09-16 on NVR 192.168.50.170, run FROM the HA host with the credential stored in the
Dahua config entry (`admin`, 10-char password):

 https getDeviceType -> 200 type=N41C2P2
 https getSoftwareVersion -> 200 version=4.003.0000000.1.R,build:2024-05-15
 http getDeviceType -> 200 type=N41C2P2
VERDICT: AUTH OK

The device is a Dahua N41C2P2, firmware 4.003.0000000.1.R (build 2024-05-15), reachable on 80, 443,
554 and 37777. The stored credential is valid.

Why this matters: a recorded concern held that "the Dahua NVR rejects admin/Hello@1234 even after 40
minutes". That is 10 characters — the same length as the stored password — so it was almost certainly
a PROBE DEFECT, not a credential failure. A broken Digest handshake and a wrong password present
identically: HTTP 401. I nearly repeated the mistake myself: my first probe crashed inside the hash
step (`hashlib.md5` needs `.encode()` in Python 3) AFTER receiving a correct 401 challenge, which
reads exactly like "bad password" if you only look at the status.

Rules:
1. Dahua requires HTTP **Digest** (realm + nonce + qop, MD5) on `/cgi-bin/magicBox.cgi`. A Basic-auth
 attempt will 401 and tell you nothing.
2. Before blaming a credential, prove the handshake works. A 401 from a digest device is evidence
 about your client until proven otherwise.
3. Never brute-force and never rotate a device credential to "fix" a 401 you have not diagnosed.

Corollary that generalises: when a probe reports failure, suspect the probe first. This system's
most expensive historical failure was believing a stale reading; this is its sibling — believing a
broken reader.
