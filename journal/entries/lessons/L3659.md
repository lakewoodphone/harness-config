**L3659 · Clause 2 measured properly, and the join key I did not check made it look empty**

2026-10-13. Measured clause 2's actual coverage for the first time, and made the same mistake twice
inside one round doing it.

THE NUMBERS, from the sync's own status file `/root/.marketplace-orders-status.json` and the ledger:
 671 marketplace rows = 581 purchases + 90 notification-only
 match_status_counts: matched 419 no_candidate 44 amount_only 30 ambiguous 53 no_amount 125
 purchases with a total : 546 of 581 (35 have none)
 purchases with items : 490 of 581 (91 have none; 642 item rows in all)
 evidence rows : 545, every one carrying a transaction_id
So clause 2 is not thin: 419 orders are linked to a card charge, 546 carry an amount and 490 are
itemised, from 2018-10-21 to 2026-10-12. The genuine remaining gap is 35 purchases that parses to no
amount at all - and an order with no amount cannot be matched to anything, which is why `no_amount`
is 125 once the 90 notifications are counted in.

THE SYNC'S CLOCK IS REAL AND HEALTHY. `lpt-marketplace-orders.timer` ran at 04:00:32 and again at
05:11:35, both exit 0, ~81s each, `evidence` written 1 with 418 skipped as already present - so it is
incremental and it is keeping up.

ONE REPORTING GAP, worth knowing so its absence is not read as a fault: the service prints
`orders=None new=None changed=None`. `orders_parsed` is taken from the ingest step's JSON and that
step does not emit an `orders` key, so the run cannot say how many orders it looked at. It is a
reporting hole, not a silent failure - `evidence.written` and `skipped_existing` carry the real
signal, and the status file holds the full match breakdown.

MY OWN ERROR, TWICE IN ONE ROUND, and this is the part to keep. I asked how many purchases lack line
items and wrote `where i.order_id = o.id`. It returned 0 for every row - which I should have read as
"suspicious", since I had already measured 642 item rows that morning. I reported 581 of 581
unitemised before catching it. The correct key is `marketplace_order_items.order_id` JOIN
`marketplace_orders.order_id` (the marketplace's own order number, e.g. '111-0032200-9576275'), NOT
`marketplace_orders.id`, which is a small integer. Joining on `o.id` matches nothing at all and
returns a confident zero.
Two rounds ago the same shape of error made a WORKING answer-resolver look broken: I passed the asks
store as `acct_db` and every category lookup failed. Both times the code was right and my query was
wrong, and both times the false result was internally consistent, which is what made it convincing.
RULE: a join key and a database path are both CLAIMS. Assert them - `select count(*)` on the join,
or print what the parameter resolved to - before believing any number derived through them. A query
that returns zero everywhere is describing itself, not the data.
