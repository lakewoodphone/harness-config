**L1722 · A launcher default that is only correct when every caller remembers a parameter is not a default**

**L1639 · 2026-09-15 · A launcher default that is only correct when every caller remembers a parameter is not a default**

MEASURED on Yocheved's laptop (DESKTOP-FGV6KMH), 2026-09-15 21:20-22:20 EDT. The report was "the
desktop shortcut opens a command window for a few seconds but dsh doesn't actually open".

THE CAUSE WAS NOT THE WINDOW CODE. IT WAS ONE DEFAULT.

`harness-config/multi-window/windows.json` is the OWNER's fleet config; `server.stateDir` in it is
`C:\Users\ezabz\.dsh\multi-window`. `dshw.ps1` defaulted `$ConfigPath` to that file. Two entry points on
her box invoked the script WITHOUT `-ConfigPath`:
 * the scheduled task's payload: `pwsh -File dshw.ps1 new`
 * the `open.cmd` -> task chain
Her box HAS a correct per-machine file, `machines/DESKTOP-FGV6KMH.windows.json`, and nothing used it.
Her box also carries a stale `C:\Users\ezabz` profile directory, so the wrong state dir did not fail with
"path not found" -- it failed with **access denied** on the first write.

WHY THE CLICK PRODUCED NOTHING VISIBLE IS THE SECOND HALF, and it is the part worth remembering:
`dshw.ps1` runs with `$ErrorActionPreference = 'Stop'`, and the first thing the recovery path does is
`Add-Content -LiteralPath ...\watchdog.log` / `engine-recovery.log`. That throw ABORTED THE LAUNCH
before `Open-SlotWindow` was ever reached. So the diagnostic write killed the operation it was
narrating, and the only record of it was a log the launcher could not write.
EVIDENCE: `C:\Users\cheve\.dsh\multi-window\logs\open.log` 09:44:14 -- both the `ensure` and `restore`
sections end in "Access to the path 'C:\Users\ezabz\.dsh\multi-window\...' is denied" -- while her engine
answered on 3099 as pid 2404, in session 1, all day, and `dshw status` reported **0 window(s) open**.

THE FIX, and the general form of it:
1. `dshw.ps1` now selects `machines/<COMPUTERNAME>.windows.json` when it exists and falls back to the
 shared file only when a machine has none. `doctor` prints the config and state dir it resolved. A
 fault that stays invisible for a day is the fault that costs the day.
2. Log writes go through a shadowing `Add-Content` that warns and never throws -- every write of a log
 line in that file already used `Add-Content`, so one function covers all 16 sites, including ones a
 later edit would add. Directory creation stays a hard check, so an unusable state dir is still caught.
 **Failing to narrate a run must never be what ends the run.**
3. `launch.cmd` built `%DSHW%` as `%~dp0dshw.ps1` while living in `machines\`, i.e. it pointed at
 `machines\dshw.ps1`, which does not exist. It now resolves `%~dp0..\dshw.ps1` and passes
 `-ConfigPath` to BOTH invocations (ensure and the verb).
4. `open.ps1` became a one-line delegator to `launch.cmd` instead of a second, incomplete copy of the
 launch sequence. A second copy is a second place to forget.

*Rule:* when a wrong default can silently select ANOTHER PERSON's paths, the default must resolve from
the machine itself, and the resolved value must be printed by the tool's own health command. Adding the
parameter to every current caller fixes today and loses to the next caller.

VERIFIED AFTER DEPLOY, on her box, by artifact -- not by exit code:
* no `-ConfigPath`: `dshw doctor` prints `config : ...\machines\DESKTOP-FGV6KMH.windows.json`,
 `dir ok : C:\Users\cheve\.dsh\multi-window`, and no `C:\Users\ezabz` path anywhere.
* `schtasks /run /tn "Yocheved DSH Window"` -> Last Result 0, then
 `Get-CimInstance Win32_Process -Filter "Name='msedge.exe'"` shows exactly one `--app=` process:
 **pid 5964, session 1**, `--app=http://127.0.0.1:3099/?token=<redacted>`, profile
 `C:\Users\cheve\.dsh\multi-window\browser\w1`; `windows.log` has the matching 22:16:18 open line;
 `DESKTOP-FGV6KMH.windowcount.ps1` returns 1.
* nothing under `C:\Users\ezabz` was touched after the fix (newest write there: 22:10:33, before deploy).
