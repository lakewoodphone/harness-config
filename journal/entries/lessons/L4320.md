**L4320 · com.apple.cellular has no APN key — the APN string is Name, and ours held the label 'Telnyx' instead of data00.telnyx**

**L — `com.apple.cellular` has NO `APN` key: the APN string goes in `Name`, and ours held a label**

**The owner found this, not me, and it is the whole of the LPT cellular fault.** On DRN 2007 he
opened Settings → Cellular → *plan* → Cellular Data Network and photographed it: the **APN field
read `Telnyx`**, with a "Settings for this carrier have not been verified by Apple" note. His words:
*"It looks like the APN is basically empty... could that be the reason?"*

**Apple's schema, read directly**
(<https://raw.githubusercontent.com/apple/device-management/release/mdm/profiles/com.apple.cellular.yaml>),
for each item of the `APNs` array:
`Name` (**required** — "The name for this configuration"), `AuthenticationType`, `Username`,
`Password`, `ProxyServer`, `ProxyPort`, `AllowedProtocolMask`, `AllowedProtocolMaskInRoaming`,
`AllowedProtocolMaskInDomesticRoaming`, `EnableXLAT464`.

**There is no `APN` key. The APN string is the `Name` value.** Our profile had:

```
<key>Name</key><string>Telnyx</string> <- iOS uses THIS as the APN
<key>APN</key><string>data00.telnyx</string> <- not a key Apple defines; silently ignored
<key>AllowedProtocolMaskInInternationalRoaming</key><integer>1</integer> <- also not a key
```

So every device wearing that profile has been asking the network to attach with an APN literally
called **"Telnyx"**, never `data00.telnyx` — which is exactly what Telnyx's own troubleshooting page
says must be set. The bearer comes up (any APN string is accepted) and then carries nothing, so
**iOS's connectivity probe fails and the LTE indicator drops after about half a second.** That is
the owner's own description, and it is the signature of a wrong APN, not of a dead SIM.

**Why it hit some phones and not others — the timeline, not a mystery.** The `Name` key was added to
the served profile on **2026-10-13 20:39Z** (the host still holds
`waze-telnyx-apn.mobileconfig.bak-before-name-field-20261013T203913Z`). Before that the profile had
`APN` only, so iOS had **no** managed APN and fell back to the network default — which works. Devices
set up after 20:39Z (2005, 2006, 2007, 2008) got the label as their APN; 2002, set up earlier, kept
working. **A "fix" applied on 13 October introduced the fault, and it looked like an improvement
because it satisfied a schema requirement.**

**Fixed 2026-10-14 23:59Z:** `Name` set to `data00.telnyx`, the bogus `APN` key removed,
`AllowedProtocolMaskInInternationalRoaming` removed and the valid `AllowedProtocolMaskInRoaming`
added. Host profile backed up as `*.bak-before-apn-key-fix-<ts>`; pushed to DRN 2007 and
`Acknowledged` at 23:59:23. Fleet-wide push held until the owner confirms on the device.

**The transferable rules.**
1. **A config profile key that is not in Apple's machine-readable schema is not a key.** This is the
 third time in this estate (L1873's `LocationServices`, L3788's `allowDataRoamingModification`,
 now `APN`) — and this one carried a real fault for a day while looking like a fix.
2. **A profile's *displayed* value on the device is the cheapest possible verification** and I never
 asked for it. One screenshot of Cellular Data Network would have ended this on the first night,
 instead of twelve hours of carrier, blocklist, filter and IMSI theories. When a fault is
 "no data", **look at what the device says its APN is before theorising about anything else.**
3. **I banned a network and stripped a filter to chase this.** Both were reversible and both were
 wrong. The correct first question was "what is on the screen", and the owner had to ask it for me.
