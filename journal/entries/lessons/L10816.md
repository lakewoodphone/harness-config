**L10816 · DeepSeek serves two ids and 'V4.1-Flash-1017' is a release name - deepseek-flash IS that model**

**Measured 2026-10-20 against the live gateway and against DeepSeek's own API.**

DeepSeek's own `/models` endpoint returns **exactly two ids**:

```
deepseek-flash
deepseek-v4-pro
```

A one-token call with `model=deepseek-flash` comes back naming `model = deepseek-flash`, with
`prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` reported separately. **So "V4.1-Flash-1017" is
a release name, not an API id — `deepseek-flash` IS that model.** Anyone looking for an id containing
"4.1" or "1017" will not find one, and should stop looking.

Verified in the RUNNING service (`/proc/1298973/environ`, not a shell): all three tiers resolve
uniformly through `app.services.model_ids` —

```
fast model=deepseek-flash canonical=deepseek/deepseek-flash
mid model=deepseek-flash canonical=deepseek/deepseek-flash
ceo model=deepseek-flash canonical=deepseek/deepseek-flash
catalogue http://127.0.0.1:8002/v1/models -> 33 ids, deepseek-flash present
```

**But the environment being right is not the same as the traffic landing there.** Measured today:
68 calls went to `deepseek-v4-pro` and 64 to `gemini-3.5-flash`, because the smart router picks its
own escalation rather than honouring the pinned tier model. And **98 calls went to
`deepseek-v4-flash`, an id DeepSeek does not advertise at all** — a latent breakage that has not
failed yet.

**The rule this implies:** pinning a tier must be a hard preference, not a starting point. If the
operator says every tier is `deepseek-flash`, no routing policy may silently substitute pro or Gemini
for company traffic; escalation belongs behind an explicit opt-in variable, not inside the chooser.
