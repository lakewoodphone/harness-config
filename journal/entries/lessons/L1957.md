**L1957 · A repo-wide '*.jpg' ignore means 'saved it in the repo' can be silently false - git check-ignore -v is the only proof**

**The trap.** `lpt-hub/.gitignore` line 44 is a bare `*.jpg` (and `*.png`, `*.jpeg`, `*.gif`, `*.webp`, `*.mp4`, `*.mp3`, `*.wav` alongside it). The owner said of 39 site photographs: *"Saved them in the repo and named them properly."* `git add` on that folder would have silently added **nothing** — 27 MB of converted photos dropped on the floor with no error, and `git check-ignore -v` was the only thing that said so. The same rule also left `.HEIC` uncovered, so the 105 MB of camera masters would have gone *into* git while the usable JPEGs stayed out — the exact inverse of what is wanted.

**Why this is the project's own recurring wound.** This project has already lost its entire April 2026 photo set (~240 MB of HEIC) because it lived in a gitignored `_scratch` folder. L1848 recorded that disaster. The ignore rule here is not a bug — it is a deliberate rule to keep binaries out of a repo whose pack is already 1.18 GiB — but it is indistinguishable, from the agent's side, from success.

**The rule.** When asked to put media into a repo, the task is not finished at `git add`: **run `git check-ignore -v` on one file from the set and confirm the answer is "not ignored"**, and verify the same for the set you intend to EXCLUDE. A `!`-exception must be added next to the rule that excluded it, with the reason in a comment, and the ignore line for the excluded set written explicitly — never left to a rule that happens to not match. Fixed here by `.gitignore` lines 62-77, which carry the full reason.
