**L2510 · Three lesson ids meant different entries on ZABZ-TECH and on secratary: the id bands overlap AND this host never pushed, and nothing can see a collision until a merge**

**Three lesson ids on this machine and on secratary meant different entries, and the merge process could not see it.**

**WHAT HAPPENED, MEASURED 2026-09-24 (ZABZ-TECH).** Pushing my own journal entries required merging `origin/master` first, and the merge reported `AA` (added on both sides) for `journal/entries/lessons/L2372.md`, `L2373.md` and `L2374.md`. Reading both sides showed **completely different entries under the same ids**:

| id | ZABZ-TECH, written 2026-09-23 | secratary, written 2026-09-24 |
|---|---|---|
| L2372 | A DSH install is a set of versions; `dsh --version` reports only the launcher | A document's claim that an owner-queue row is open is a pointer, not a fact |
| L2373 | A detector must be run against a known-GOOD input, or it reports crises that do not exist | Yocheved's health facts live in `docs/wedding/` |
| L2374 | 0.1.7-rc.1 adds a v3-to-v4 session-format codec and no reverse codec | Norethisterone/Aygestin duration: the supported band is up to ~6 months |

**WHY: TWO CAUSES, BOTH ALREADY KNOWN, COMPOUNDING.**
1. **The bands overlap.** `journal/alloc/bands.tsv` grants `lessons 2253-2376` to **ZABZ-TECH** (stamped 2026-09-21) *and* `lessons 2318-2381` to **SECRATARY** (stamped 2026-09-22). Ids 2318-2376 are inside both bands, so both hosts had a legitimate-looking claim on 2372. The allocator's whole purpose is to make cross-host collisions impossible; on this range it did not.
2. **ZABZ-TECH never pushed.** The three entries sat untracked in the working tree for a day. secratary's allocator therefore never saw them, allocated the same ids, and its 15-minute autocommit published them to `origin/master` - the exact `local_commits_preserved` failure already recorded in H2339's BROKEN section (autosync writes a pre-push `ahead` count, and nothing escalates on it).

**WHY NOTHING CAUGHT IT.** `journal.py check` compares entries *within one tree*, where one file per id is normal; and `journal.py repair-ids` looks for the same thing. Neither can see "the same id means something different on the other machine". The collision only becomes visible at merge time, as `AA`, on a machine that happens to have both sides. A reader on either machine alone would have seen a clean journal.

**WHAT I DID, AND WHY IN THAT ORDER.** The published secratary entries keep `L2372/73/74` - other machines and published entries (H2594, P2313) cite them. The three local ZABZ-TECH entries were renumbered into this host's own lessons band to **L2507, L2508, L2509**, with an id note inside each recording the old id and the reason. Nothing was deleted: at every step both texts existed on disk. **The three entries that cite the old ids (H2531, P2261, W2253) were left exactly as written**, because rewriting a published body breaks its recorded sha - the append-only rule did its job. Their `L2372`/`L2373`/`L2374` references are therefore read as `L2507`/`L2508`/`L2509`; that mapping lives here and in the id note inside each renumbered entry.

**THE RULES.**
- **An id collision is invisible per-machine; only the merge sees it. Run `journal.py check` after every merge, and expect `AA` on `entries/` as the signal.**
- **Never resolve an `AA` id collision by deleting one side.** Keep the published entry at the id, renumber the unpublished one inside the host's own band, and write the mapping into the entry itself - text references are not rewritten by any tool.
- **A host that does not push its journal makes duplicate ids, not just stale ones.** Unpushed entries are invisible to every other allocator. This is a correctness bug, not a freshness nit, and it is the strongest argument yet for fixing `local_commits_preserved`.
- **When resolving, ask which id the published entries cite, not which host is "right".** Both hosts were right about their own allocation; the band arithmetic was wrong.

**EVIDENCE.** Merge of `origin/master bffbd7c9` into ZABZ-TECH `master`, 2026-09-24 19:0x UTC: `AA journal/entries/lessons/L2372.md L2373.md L2374.md`, `UU journal/alloc/bands.tsv`. Both sides kept at `journal/entries/lessons/L25{07,08,09}.md` (id note appended) and in this commit's history. Bands proving the overlap: `journal/alloc/bands.tsv` lines for `lessons 2253 2376 ZABZ-TECH` and `lessons 2318 2381 SECRATARY`.
