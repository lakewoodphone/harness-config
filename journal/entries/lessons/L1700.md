**L1700 · Journal lock: the unlink-based stale-break was a real race - fixed with an OS lock plus an inode check**

**L1699 was written by an interrupted append and its body is a placeholder.** This is the real
content of that finding, recorded per the append-only rule rather than by rewriting L1699.

## The defect
`journal\.lock` was created with `O_CREAT|O_EXCL`; "stale" was decided by `mtime > 600 s` OR a
dead holder PID; and a stale lock was broken by `unlink()` **on the path**, using a token read
a moment earlier. Two writers that both read the same dead token both judged it stale, both
unlinked, and both entered the critical section. `release_lock`'s compare-and-swap protected
release only, so the loss of mutual exclusion was **silent** — this is the mechanism behind the
161-collided-id incident of 2026-09-14 (duplicate ids from the read-then-write allocator, lost
alias rows). Two more holes: the `age > 600 s` branch broke a *live* slow writer with no
liveness check, and a kill between `os.open` and `write` left a zero-byte lock that was neither
dead nor stale, so every waiter burned the full 240 s wait.

## Measured before the fix (2026-09-15, 3-4 live sessions on ZABZ-YOGA)
- Real `journal.py append` critical sections held the lock **41 s, 41 s, >=89 s, >=98 s**.
- A `journal.py check` was **killed at the harness 120 s cap** while an append held the lock.
- Two journal python processes outlived the reported timeout.
- At 22:48:40 the lock named `append 42088@zabz-yoga:1789526758` while pid 42088 was already
 gone — the stale-break path ran routinely, i.e. the race window opened routinely.

## The fix (journal.py, 2026-09-15)
`acquire_lock` now takes a real OS lock: `msvcrt.locking(fd, LK_NBLCK, 1)` on Windows,
`fcntl.flock` on POSIX. Consequences: the kernel releases it when the holder dies, so **"stale"
no longer exists as a concept**; after acquiring, the fd's inode must still be the path's inode,
so a v1-style process that unlinks-and-recreates the file cannot hand the lock to two writers
(back off and retry instead); release unlinks only its own inode; the wait is bounded and
jittered; `LOCK_WAIT_SEC` is 110 s (below the 120 s harness kill — safe to keep long now that
dying releases the lock); `JOURNAL_LOCK_WAIT` lets a caller bound its own wait.

Same session, second defect: `status` — the always-read page — called `_maybe_refresh_questions`,
which spawns the **mutating** `questions` command, which takes the global write lock and holds it
across `ssh secratary-ts` (45 s). **Reads were creating writer contention for every other
session.** Now the refresh is skipped when the lock is held (the page honestly prints the mirror's
age) and gets `JOURNAL_LOCK_WAIT=15` when it does run.

## Verification (not configuration — observed)
`_dsh-scale/lock_stress.py`, real child processes:
- 3 concurrent writers, 2 s hold each: acquire/release timestamps c0 → c1 → c2, **zero overlap**.
- A writer force-killed with `taskkill /T /F` mid-hold: the next process took the lock in
 **0.00 s**.
- Under live load afterwards: lock free, `acquire 0.00 s`, no lock file left between holders.

## What is still slow, and it is NOT the lock
An append still runs **two full-repo `git grep`s** to find the id ceiling plus a **6.4 MB
`journal.db` rebuild** inside the critical section. That is why appends queue for minutes under a
fleet. Fixing it means caching the ceiling and making the index incremental — the same id-allocator
path that produced the collided ids, so it needs the 6-way concurrency selftest before it lands.
