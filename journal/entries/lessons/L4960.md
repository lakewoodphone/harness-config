**L4960 · open(path,w) truncates before it validates its arguments - a failed write destroyed a live production file**

# L — `open(path, "w")` TRUNCATES the file before it validates its arguments, so a failed write is a destroyed file

**2026-10-15, and this one took a production file to zero bytes.**

## What happened

I wrote a patch script that ended:

```python
shutil.copy2(P, backup)
io.open(P, "w", encoding="utf-8", newline="\\n").write(src)
```

The `newline` argument was wrong — `"\\n"` is the two characters backslash+n, not a newline, and
`io.open` rejects it with `ValueError: illegal newline value`. **The script crashed on that line.**

**And the file was 0 bytes.** Because `open(path, "w")` builds the underlying `FileIO` — which opens the
path with `O_CREAT|O_TRUNC` — *before* the text layer validates `newline`. The truncation happened, the
constructor then raised, and nothing was ever written:

```
-rw-r--r-- 1 root root 0 Oct 15 15:40 /opt/company/scripts/owner_attention.py
e3b0c44298fc1c14… <- sha256 of the empty string
```

This was the file the `lpt-owner-attention` timer executes. A failed write became a destroyed file, and
the failure looked like a traceback about a *string argument*, which points nowhere near the damage.

## What saved it

Two backups existed because both scripts took one **before** touching the target:
`cp -p "$P" …AS-FOUND-…` in the shell, and `shutil.copy2(P, backup)` in the Python. Restored from the
`AS-FOUND` copy: 43,591 bytes, sha `880ef1b7`, compiles, and its dry run again produced the one item it
had produced before. **Nothing was lost because the backup was taken on the previous line.**

## The rule

**Never open a destination with mode `"w"` and write into it.** Write to a temporary file in the same
directory and then move it into place atomically:

```python
tmp = P + ".new"
with open(tmp, "w", encoding="utf-8", newline="\n") as fh:
 fh.write(src)
os.replace(tmp, P) # atomic on POSIX: the reader sees old or new, never empty
```

`os.replace` also fixes the *other* half of the problem, which this session hit four times: a reader (or
a concurrent writer) can observe a half-written or empty file. With a temp file and a rename, the only
observable states are the old content and the new content.

## Why it belongs beside the concurrent-session lessons (P4313, L4897)

All three are the same shape: **a shared live file, written casually.** One session's stash pop, one
`git checkout HEAD --` that discarded uncommitted work, one wholesale overwrite three times over, and now
a truncate-on-error. None of them was carelessness about the content; each was a *mechanism* that turns a
small mistake into destroyed work. The mechanisms, not the intentions, are what have to change:

- take the backup on the previous line, always;
- write to a temp file and `os.replace`;
- diff the live file against your base, and look for a claim marker, before writing at all.

**And the corollary for patching someone else's file: assert every anchor and validate the whole script
BEFORE you open the destination.** My script asserted all six anchors correctly — and then destroyed the
file at the last line. Assertions prove the *patch* is right; they say nothing about whether the *write*
can succeed.
