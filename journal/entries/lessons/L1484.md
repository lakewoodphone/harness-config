**L1484 · When the work is already paid for, the row write must not be able to lose it**

## When the work is already paid for, the row write must not be able to lose it

Same defect class as **L1479**, third and most expensive instance: a row write that fails with
`sqlite3.OperationalError: database is locked` and takes its result down with it. The three
writers, in order of how much they cost when they fail:

1. `dialpad_media_file` — the file is on disk, the row is lost, so the call looks un-fetched and
 is downloaded again forever.
2. `dialpad_media_download_attempt` — bookkeeping killing the batch that was doing real work.
3. **`dialpad_call_retranscript`** — the row write happens *after* Whisper has transcribed the
 audio and DeepSeek has cleaned the text. A failure discards a transcript that has already
 been paid for, and the next pass pays for it a second time. Measured: 32 transcripts in a
 12-minute tick, then a crash that threw the whole batch away; a later tick added 0.

All three now retry on a fresh transaction, because a **read-snapshot upgrade** is the case
`busy_timeout` cannot help with (see `app/services/dsh_session_ingest.py:247` — waiting would
break snapshot isolation, so SQLite refuses immediately rather than waiting).

Verified after the fix: **313 → 350 transcripts in a single tick (+37)**, and the batch finished
instead of dying at the last row.

**The rule worth carrying:** put the retry on the write that *records* expensive work, and
measure the job by what it produced, not by how it exited. Three times today a job reported
success while its output was thrown away — the file was on disk but unrecorded, the crop of
transcripts was paid for and discarded, the batch ran to completion with nothing to show.
