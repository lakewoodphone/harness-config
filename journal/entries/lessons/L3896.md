**L3896 · Correction to L3895: ntfsls -R does not recurse - mount with ntfs3 and reconcile against the volume**

## The correction to L3895, written the same afternoon it was published

**L3895 said:** when a filesystem reports a placeholder it cannot resolve, *read the filesystem's own
index instead — `ntfsls -f -R -l -p <path> <image>`*. **That remedy is wrong, and worse than useless: it
made a 38 GB error look verified.**

- **`ntfsls -R` does not descend into subdirectories.** On the Semah drive (WO26101812753) it reported
 `Desktop` 8 files / 0.05 G, `Documents` 23 / 0.01 G, `Pictures` 19 / 0.16 G. The truth, via the kernel
 driver, was **`Documents` 3,442 files / 19 G** and **`Pictures` 3,278 files / 19 G** — the mass sat in
 subdirectories (`nikon camera` 13 G, `fig pics` 5.9 G) that the tool printed as directories of size 0.
- **The right remedy is the kernel driver:** `sudo mount -t ntfs3 -o ro,loop <dislocker-file> <mnt>`
 traverses cloud reparse points and lists the tree normally. `-o loop` is required because the
 dislocker output is a file, not a block device.
- **And the remedy that catches the class of bug regardless of driver: reconcile.** Profiles + system +
 pagefile + hiberfil must equal `df` used. It read 129 GB used against an 18 GB profile, and the gap was
 38 GB of the customer's own files. I explained it as Windows instead of chasing it.

## The transferable rules

1. **An instrument you have not validated on nested data is a blind instrument.** `du` and `ntfsls` both
 returned success; neither has an exit code for "I could not see this". "Lower level" is not "more
 correct" — a recursive-looking flag that does not recurse is more dangerous than an obvious blind spot
 because it feels authoritative.
2. **When two readings of the same medium disagree, the disagreement IS the finding, and the number to
 doubt is yours.** Mount vs volume, index vs directory, copy report vs source count. Three of these
 must agree before a size is quoted, a medium bought, or a customer described.
3. **A guard that is prose is not a guard.** The rule "measure the payload" was written in three
 documents while I broke it. What stops the repeat is a script that refuses: see
 `lpt-hub/scripts/customer-operations/payload-measure.sh` (refuses unenterable mounts; fails when the
 reconciliation gap exceeds tolerance), tested both ways on this drive.

Postmortem with the full failure chain: `lpt-hub/docs/customer-operations/postmortems/2026-10-20-payload-understated-onedrive-reparse.md`.
