**L3504 · Invalid user root: three reports named the wrong cause and the answer was one line in the remote log**

## 2026-10-11 13:45Z · WORKER ACCESS: THE REAL CAUSE WAS AN INVALID USERNAME

Follow-up to `H3447`. The archive pull could not reach any worker machine, and after the tailnet join
the reason was NOT the network. Read from the desktop's own OpenSSH log:

 sshd: Invalid user root from 100.73.176.126 port 55434
 sshd: Connection closed by invalid user root 100.73.176.126 port 55434 [preauth]

The authority was connecting as **root** to every worker. Windows sshd has no such account, so the
session ended before a key was ever considered — and every script above it reported the failure as a
missing checkout or a network gap. **The estate's accounts are different per machine**: `ezabz` on
Windows, `zabz` on Linux, `lpt` on the Mac. The authority's `~/.ssh/config` now carries all of them
(with the previous file kept as a timestamped copy), and the desktop immediately accepted the
authority's key:

 sshd: Accepted publickey for ezabz from 100.73.176.126 ssh2: ED25519 SHA256:EpoPBa4Nsw3...

`secratary-ts` (the office box, as `zabz`) also authenticates. `linux-pc-ts` and `laptop-ts` still
answer `Permission denied (publickey,password)`: their `authorized_keys` does not hold the authority's
key yet, which is now a one-command fix per machine rather than a mystery. `mac-mini-ts` does not
answer ssh at all (asleep).

## WHAT WAS DONE TO GET THIS FAR

- The archive client was placed on the desktop at
 `C:\Users\ezabz\code\harness-config\scripts\archive-transcripts.py` (standard library only, python
 3.13.5 present) and it answers `--list --json` correctly, which is exactly the probe the puller runs.
- The authority's public key was added to that machine's user `authorized_keys` **and** to
 `administrators_authorized_keys` with the ACL sshd requires (Administrators + SYSTEM only,
 inheritance removed). Whether the admin file was needed is unresolved — the username was the real
 blocker — but both are correct now and the previous files are kept.
- `zh` aliases: `desktop-ts`/`zabz-tech-ts`, `linux-pc-ts`, `laptop-ts`, `mac-mini-ts`, `secratary-ts`,
 each with its correct user, so no script has to guess an account again.

## THE LESSON, WHICH IS THE SAME ONE THIS ESTATE KEEPS PAYING FOR

Three surfaces reported this failure and all three named the wrong cause: the puller said
"harness-config is not synced", I first suspected the tailnet, then Windows SSH ACLs, then key format.
The actual answer was one line in a log nobody had read — `Invalid user root`. The diagnostic I added
earlier (name both causes, say how to tell them apart) would have shortened this, but the stronger
version is: **when a remote action fails, read the REMOTE side's log before forming a theory.** The
failure text the estate generates is not evidence about the failure; it is evidence about what the
code expected.
