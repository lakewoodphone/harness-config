**L3809 · A flat total hides the tax: the order stored 75 with subtotal/tax NULL, the composer back-computed a split from it, and the customer text asked for the wrong money - the fix is in the ORDER CREATION path, which never applied the tax the update path already computes**

**FOUND 2026-10-14 while sending the Weinreb payment text, from the owner's own correction:** *"no tax comes after 75... its supposed to be computed automatically you shouldn't have to manually put it in."*

**The measured chain.** The order `WO26100812739` (id 3018) stored `total = 75.00` with **`subtotal`, `tax` and `taxRate` all NULL**. The shop's pay-notice composer then **back-computed** a pre-tax split from that total - `75 / 1.06625 = 70.34` subtotal, `4.66` tax - and the customer text read *"Balance due: 75.00 (Subtotal 70.34 + tax 4.66)"*. The tell is that the two numbers add to the total exactly: that means the tax was derived FROM the total rather than added TO a price. The owner priced it 75 + tax, so the correct total is **79.97** (75 + 4.97 at 6.625%).

**Where the defect is, and where it is NOT.** `lpt-write total set` **already computes the tax automatically** - its dry run prints *"the figure given is BEFORE tax: 75.00 + 4.97 tax at 6.625% = 79.97 to pay"*. So the mechanism exists and works. The gap is one step earlier: **the order was CREATED with a flat total that never passed through that computation**, which is why the three split columns are NULL and the composer had to invent one. **Fix the creation path (`order create`, and any other writer of `orders.total`) to use the same tax logic as the update path.** Blaming the composer would have been the wrong fix: it was faithfully presenting a stored number that was already wrong.

**The manager's own error, recorded because it is the instructive part:** setting the corrected figure, the manager passed the **tax-inclusive** 79.97 into the **pre-tax** field, so the tool taxed it again and wrote **85.27**. Caught from the tool's own dry-run line and corrected inside a minute; ledger seq 433 (wrong) then 434 (right). **A field whose convention is "pre-tax" and a human who is thinking "total" is a mismatch the tool should refuse, not silently tax twice** - worth a guard.

**And the guard that DID work, which is the whole reason for this build:** the freshly-corrected draft made the tool refuse the older one - *"STALE: the draft asks for 75.00 and the order's own balance is now 79.97. Sending the draft would ask the customer for the wrong money."* That refusal is exactly what was missing at 15:00 today, when a session hand-wrote a message with a pasted link and no balance check at all.
