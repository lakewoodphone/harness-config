**L3926 · /health returns 'degraded 200' so my serving probe reads it as healthy; the lock counter misses its own events by wording; and the BoA warning I called a false positive is a TRUE one about a different database**

Three findings from one `/health` response, and two of them are corrections of things I said minutes earlier.

**1. `/health` returns 200 while degraded, and my own probe reads that as healthy.** The exact log line:

 2026-10-14T14:08:59+0000 WARNING app.main: Health DB probe timed out — SQLite lock contention; returning degraded 200

The body is honest -- `{"ok":false,"database":{"ok":false,"error":"db check timed out (lock contention); api still responsive"}}` -- so only the HTTP **code** fails to express it. **Every one of my 2.0-second `/health` readings today was a probe timeout**, not slowness: five consecutive calls returned `0.005s` while the log showed the timeout at 14:07:29, 14:08:03 and 14:08:59, roughly every 30-60 seconds. By hour today: `03:1 04:2 05:21 07:8 11:1 12:32 13:2 14:6` -- **~71 events, 32 of them in the noon hour.** So `company-api-serving-probe.sh` is a **serving** check and not a **health** check: it answers "does it respond", correctly, and cannot see `ok:false`. That is a real limitation of it, now stated rather than assumed.

**2. The contention counter misses its own events by wording.** `journalctl | grep -ci "database is locked"` returns **0** for the same window in which the app logged three timeouts, because the message says **"SQLite lock contention"**, not "database is locked". The estate's documented 27x undercount (`ps_db_query`'s docstring, measured 2026-09-16) has a *second* cause beyond the handled-versus-unhandled one it names: **the grep pattern does not match the string the app writes.** A counter that greps for a phrase nobody emits reports zero, and zero reads as health.

**3. The finance warning is a TRUE positive, and I called it a false positive.** Reading the health body's last field -- `"finance":{"ok":false,"warnings":["BoA (Plaid) last txn 5d ago: 2026-10-09"]}` -- I checked `plaid_transactions`, found the BoA business account (`Business Adv Fundamentals`, mask 7930) current through **2026-10-13** with all 14 accounts refreshed at `04:30:12` today, and concluded the warning was wrong. **It is not.** `main.py:1546` does not read Plaid at all:

 acc_db = str(accounting_db_path()) # /root/accounting-data/live/accounting.db
 c.execute("SELECT MAX(transaction_date), COUNT(*) FROM transactions WHERE account_id='lpt-boa-checking'")

A **different database**. And in that one, `lpt-boa-checking` holds 646 transactions with newest **2026-10-09** -- five days, exactly as warned. `plaid_ledger_ingest.py:30` maps Plaid mask `7930` to `lpt-boa-checking`, so these are the same account, and Plaid has four days the ledger does not.

**The error is worth naming precisely, because it is the failure this system rates #1.** I had a reading (`plaid_transactions` is current), I had a claim (the warning is stale), and I connected them without asking **what writes the field I was reading against and what the warning reads**. A number that is true of one store tells you nothing about another store with a similar name. The check that would have caught it takes one command: read the code that produces the warning before judging the warning.

**And the gap itself is real and unexplained, with the ingest running.** Today at `04:30:12`: `plaid_ledger_ingest: Plaid ingest complete: 8 ingested, 2 skipped` and `autopilot: Plaid ledger ingest ok — 8 transactions`, plus `capture_plaid_balances: 15 captured, 0 skipped`. So the bridge ran and carried eight transactions -- and `lpt-boa-checking` still ends at 10-09. **Either those four days were among the "2 skipped", or the mapping matches the account on a key that has changed.** Not established, and I am not guessing: the unexplained part is specific and testable, and it sits in the CFO's own pipeline, which is what the owner cares about.
