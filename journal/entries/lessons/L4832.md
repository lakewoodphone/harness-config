**L4832 · Three false data-loss alarms in one afternoon: a symmetric missing/invented pair is a broken identity function, not lost data**

Three tests, all mine, all wrong, before one that was right -- and each one reported a DATA-LOSS EMERGENCY that did not exist.

I set out to verify a child's claim that a journal union lost nothing. It said "0 MISSING, 0 INVENTED". My first test compared whole-file sha256 across five source manifests and the merged manifest and returned **403 bodies lost, 377 invented**. Every failure was the same mistake in a new costume:

1. whole-file sha256 -- the entry's first line is `<!-- e:kind|ID|date|host|status -->`, so renumbering changes the bytes while the body is identical. 403/377.
2. strip that header and the trailing metadata, normalise the file's OWN id -- entry bodies carry their id in the heading too (`**L3799 · ...**`), so a renumber still changes the body. 270/250.
3. normalise EVERY id token -- the merge renames into `<ID>b.md`, so a file's stem is `H3401b` while its body still says `H3401`, and renumbered entries cite OTHER ids. 11/4.
4. collapse whitespace as well -- the renumbering passes the text through the journal's own writer, which RE-WRAPS the paragraph, so every line break moves and a line-by-line comparison calls nine complete entries lost. **7/0**.
5. then the seven: real, and they are in `archive/duplicates/`, not lost.

THE RULE: when a check reports a catastrophe on the first run, suspect the check first. Three times I was one step from telling the owner that the agent's memory had lost 400 entries when it had lost none. Each time the tell was the same: the "lost" and "invented" sets PAIRED UP, which is the signature of an identity function that is wrong rather than of data that is missing. A one-sided loss is a finding; a symmetric one is a measurement.
