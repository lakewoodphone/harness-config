**L7296 · Counter dead ends: reason summary is a server gate with no input, no CANCELLED status or delete exists, and Call-only is stored and never drawn**

**L · Four counter defects with one shape: a field the kiosk writes and the counter never draws, a box the counter draws and the server never receives, and no terminal state on the intake case at all.**

Measured 2026-10-16 in the source, from the owner's two live kiosk tests.

**1. The reason summary is a server GATE with no input on the screen that trips it.**

The kiosk creates its case as `NEEDS_REVIEW` — hardcoded:

```
backend/src/services/kiosk-intake/kiosk-intake.service.ts:577
 status: 'NEEDS_REVIEW',
backend/src/services/repair-intake-cases/repair-intake-case.service.ts (STATUSES_REQUIRING_REASON)
 ['NEEDS_REVIEW', 'WAITING', 'ON_HOLD', 'BLOCKED']
backend/src/services/repair-intake-cases/repair-intake-case.service.ts:2854 assertReasonRequirement
 -> TRPCError BAD_REQUEST `A reason summary is required when the intake case is ${status}.`
```

So an intake that has never been touched is already in a state where the server will refuse a save
without a reason. And `StaffCaseDetailView.tsx` renders `operatorSummary` (labelled **Summary**) but
**no `reasonSummary` field at all** — `grep 'reasonSummary' frontend/src/features/staff-intake` finds
it in the types and in the update mutation, never in a control. The staff member's only route out is
to leave the screen and change the status somewhere that does not exist either (see 3).

Two legitimate fixes, and they are not the same decision: render a reason field on the case detail
view, or stop creating kiosk cases in `NEEDS_REVIEW` and let the reason gate belong to the transition
that needs it. The second is probably right — a case nobody has reviewed is not yet in need of a
review reason — and it is the one that does not add a box to a screen.

**2. The Summary textarea is `rows={2}` with no auto-grow.**

```
frontend/src/features/staff-intake/components/StaffCaseDetailView.tsx:515-523
 <textarea id="staff-detail-summary" rows={2} value={form.operatorSummary} className={TEXTAREA_CLASS} />
```

The kiosk's own summary is a full sentence — `OPERATOR_SUMMARY_BY_PATH` writes
"Self-serve kiosk (shop tablet): customer created this intake and chose to pay the 50 USD diagnostic
fee by card. The fee is not accepted as paid until Stripe confirms the Checkout Session for this
intake is paid." — into a two-row box. The issue description beside it gets `rows={4}`. **Measured
in the owner's screenshot: the box shows about three lines with a scrollbar, and the text it is
hiding is the sentence that says whether the customer paid.** Fix: `rows={4}` to match its
neighbour, plus auto-grow (`onInput` setting `height = scrollHeight`) because a summary is unbounded
and this one is generated.

**3. There is no way to cancel an intake case, and no cancel affordance to find.** The statuses are:

```
backend/src/trpc/routers/repairIntakeCases.ts:27
 ['NEW','INCOMPLETE','NEEDS_REVIEW','READY_TO_PROMOTE','WAITING','ON_HOLD','BLOCKED','PROMOTED','CLOSED']
```

No `CANCELLED`, no `delete` mutation anywhere in the router, and the queue row
(`StaffOpenListRow.tsx`) has exactly one control: `onOpen`. `CLOSED` is the only terminal value and
it is reached through neither the detail view nor the row. **So "how do I cancel it" has the honest
answer "you cannot, from any screen"** — which is a defect, not a missing button: a customer who
walks out mid-intake leaves an untouchable row in the shop's queue forever.

**4. "Call only — don't text" is stored and never shown.**

```
backend/src/services/kiosk-intake/kiosk-intake.service.ts:593
 contactPreference: input.callOnly ? 'CALL' : null <- the kiosk WROTE it
frontend/src/features/staff-intake/components/StaffNewIntakeView.tsx:387-394
 checked={choices.callOnly} ... 'Call only — don't text' <- the counter FORM can write it
grep 'contactPreference' frontend/src/features/staff-intake/components/ -> only StaffNewIntakeView
```

The value is in the case row and in the read the detail view renders (`staff-intake.utils.ts:747
callOnly: repairCase.contactPreference === 'CALL'`), and `StaffCaseDetailView` draws no field for
it. The counter can create the preference and can never see one. **This is the one that has a real
cost** — it is the difference between phoning a customer and texting them, on a case whose whole
point is that the customer told us which.
