**L1992 · PS 5.1 Start-Process reports an EMPTY ExitCode (false success), and fixed staging filenames are shared memory between runs**

Two measured Windows/ops traps found while verifying the wake release path (W2).

1. UNDER WINDOWS POWERSHELL 5.1, Start-Process -PassThru RETURNS A PROCESS OBJECT
 WHOSE .ExitCode IS EMPTY - even after WaitForExit(), even after WaitForExit()
 with no arguments. Measured on ZABZ-YOGA 2026-09-18:
 $p = Start-Process node -ArgumentList '...process.exit(7)' -RedirectStandardOutput f -PassThru
 $p.WaitForExit(60000) -> True ; $p.ExitCode -> [] (empty, not 7, no exception)
 Consequence in a wrapper that does `exit $code`: an empty value exits 0, so a
 FAILED child is reported as success - a false completion, the failure class this
 system pays most for. Fix: build the Process yourself
 ([System.Diagnostics.Process]::new() with ProcessStartInfo, UseShellExecute=$false,
 Redirect*=$true), start it, drain BOTH pipes concurrently with
 StandardOutput/Error.ReadToEndAsync() (a sequential read deadlocks once a buffer
 fills, and dsh streams reasoning), WaitForExit(ms) for the bound, then read
 .ExitCode from YOUR object - reliable on both 5.1 and 7. And keep the guard: a
 code that cannot be read is 1, never 0.

2. A FIXED STAGING FILENAME IS A SHARED MEMORY BETWEEN RUNS. On the authority,
 wake #2 was claimed 03:08:28 and finished 03:18:05 while wake #3 was claimed
 03:10:01 - two dispatchers, both using C:\Users\ezabz\bin\wake-prompt.txt and
 wake-out.txt. #2's recorded outcome is the task text echoed back, not an answer:
 it read the other run's bytes. Two independent fixes, because either alone is
 still one mistake away from the same corruption: (a) the single-instance lock
 held from before reap to process exit, so the loser exits 0 without even
 reaching reap; (b) a staging name unique per release
 (wake-prompt-<row>-<utcstamp>-<pid>.txt). Corollary for verification: an scp
 that returns 0 and prints nothing can still have copied nothing - compare the
 sha256 on both sides before believing the artifact you tested is the artifact
 you committed. It happened twice in this session.
