**L13564 · Diagnosing 'the assistant stops working every few days': engine-vs-config version coupling, the 0-byte launcher log, and why --dump-config lies**

A machine that "stops working every few days" is usually a machine whose CONFIG is newer than its ENGINE. The failure is dated by the engine's last restart, not by the day the config landed, so it presents as a machine that looks idle rather than broken -- and a running engine proves nothing, because the profile is read at boot.

Four instruments, in this order, settle it in minutes. (1) Read the LAUNCHER's own log before the app's: a 0-byte `3099-<stamp>.log`/`.err.log` pair means the process never got far enough to print anything -- do not read silence as "no error". (2) Reproduce the boot BY HAND with output captured (`Start-Process -RedirectStandardOutput`, NOT a nested `cmd /c ... 1> ...` inside a quoted argument, which produced 0 bytes twice here), because the throw is what names the missing package. (3) `--dump-config` is NOT a boot test: on DESKTOP-FGV6KMH it exits 0 and prints 2,326 lines while the real boot throws `Cannot find package`. Any boot-gate built on dump-config is blind to the one failure that matters. (4) Compare the engine's version against the packages the profile names: `@deepseek-ai/dsh-agent-preset` exists on 0.2.0-rc.2 and does not exist on 0.1.5-rc.1, which is the whole fault, and `grep` of the installed packages answers it in seconds.

Two traps worth carrying forward. A HALF-DONE ENGINE BUMP IS WORSE THAN NONE: after installing 0.2.0-rc.2 the boot still failed because the profile's package layer is junctions, and 349 packages it needs had no junction; the version said new, the tree was not. And COUNT PROCESSES, NOT PORTS: `Get-NetTCPConnection -LocalPort 3099 -State Listen` said "something is listening" while eight `node ... web --port 3099` processes were alive, one bound and none serving, because four supervisors race `ensure` on timers. The count is the reading that shows the race.
