**L1725 · I took ZABZ-TECH's engine down for 20 minutes: piping a spawning script into ssh, then killing a service without proving the restart path - and the sync that left an unbootable bundle list**

## What I broke, and how
Two mistakes, both mine, both on ZABZ-TECH, in the space of ten minutes:

1. **I piped a script to `powershell -Command -` over ssh, and that script spawned children.** The
 children inherit the pipe as their stdin, so the sync step inside the script consumed the rest of
 the script (or blocked waiting for input). The ssh call sat for the full 10-minute cap and never
 reached the restart. Nothing had happened yet — but the *next* attempt is where it hurt.
2. **I killed the desktop's DSH engine believing I could start it again.** The start "worked" (the
 engine printed its URL and exited), then died when my ssh session ended: a child started with
 `Start-Process` over ssh lives in that session's job object. **The engine was down until I fixed
 the real problem and used the machine's own launcher.**

The outage was ~20 minutes on a machine the owner uses, and the machine's own watchdog was failing
to recover it (`result=2147946720`) because the underlying fault was deterministic.

## The underlying fault, which was also mine
The interrupted sync had run `install-client-plugins.ps1`, which **appends the plugin names to the
machine-local bundle list and then junctions the packages**. It appended the names and was killed
before finishing the junctions, leaving `~/.dsh/profiles/web/package.json` claiming five
`dsh-plugin-*` bundles that did not resolve. The engine then refused to boot at all:

 Error: dsh: cannot resolve profile bundle "dsh-plugin-attention" from the dsh installation or
 C:\Users\ezabz\.dsh\profiles\web

Reading the engine's own error log is what identified it; the machine's log said exactly which
bundle and which two roots it searched. Running the keeper again repaired all five junctions, and
`dshw ensure` brought the engine back through Task Scheduler, which is the only way an engine
survives the shell that started it (its own source says so: *"a child started directly by this
script dies with the job object that owns it"*).

## The rules
- **Never pipe a script that spawns children into `powershell -Command -`.** Write it to a file and
 use `-File -NonInteractive`; stdin then belongs to the script alone. This cost ten minutes and
 hid the fact that nothing had run.
- **Never stop a service without first proving you can start it.** Not "the command exists" —
 prove it, then stop. The restart path here is the machine's launcher/Task Scheduler, never
 `Start-Process` over ssh, because that child dies with the session.
- **A step that mutates machine-local state must be atomic or resumable.** `sync.py` now runs the
 plugin installer, which appends to the bundle list and then junctions packages; killing it in
 between leaves a profile that cannot boot. Either it should verify-and-repair at the end (it does
 when re-run, which is why re-running fixed it) or the two halves should be one transaction. Worth
 treating as a real defect, not a lesson: **the failure mode is an unbootable engine with a
 machine-local cause and no obvious symptom.**
- When diagnosing a dead engine: **read its own log first.** Its message named the bundle and both
 search roots; my process-level checks (port, pid, MCP counts) could not.

## The result that came out of it
ZABZ-TECH now measures **10 ok, 0 failed** on the same verifier, its engine is up through Task
Scheduler, its reaper task has run (`11:12:01`, result 0), and it idles at **zero MCP server
processes** against the 46 processes / 15 `npx` shims it held around the clock before — because the
restarted engine composes MCP servers only when a session does, and it now composes them as direct
`node` processes from the stable install.
