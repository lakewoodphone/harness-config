**L1996 · A shared browser profile is not per-slot identity: one window counted sixteen times and the new-window control failed silently**

**L · A shared browser profile is not per-slot identity: one window counted sixteen times, and the `+`/`⧉` new-window control failed silently for hours**

MEASURED 2026-09-18 on ZABZ-YOGA, from the owner's own report ("when i try to click the new window
for dsh nothing happens").

WHAT HE SAW: clicking the new-window control did nothing. No window, no error, no line in
`~/.dsh/multi-window/windows.log` (its last entry was 07:26:00, ~3.5 h earlier).

WHAT WAS ACTUALLY HAPPENING, in the production call path:
- the control is a button in `packages/plugin-windows/lib/client.js` that runs
 `window.location.href = 'dsh-new://open'`;
- `HKCU\Software\Classes\dsh-new\shell\open\command` runs
 `pwsh.exe -NoProfile -WindowStyle Hidden -File ...\multi-window\dshw.ps1 new`
 — **hidden**, so anything it prints is invisible;
- `Invoke-New` (`dshw.ps1:2429`) picks the first enabled slot whose `Get-WindowCount -eq 0`;
- `Get-WindowCount` had no free slot, printed `all 16 window slots are already open. Add another row
 to windows.json.` and **exited 0**.

PROOF (run it, do not read it): `pwsh -File dshw.ps1 status` printed SIXTEEN rows, every one of them
`windows 1`, `787.00` MB, profile `_shared`, and "16 window(s) open" — while exactly ONE Edge window
existed (`msedge.exe --app=http://127.0.0.1:3200/`, pid 47016). One browser tree, counted sixteen
times. The identical `mem_mb` on every row is the tell.

ROOT CAUSE, one missing guard. `Get-WindowCount`'s last resort (`dshw.ps1:1189-1204`) matched the
slot's own `--user-data-dir`. In shared-profile mode EVERY slot carries the same
`--user-data-dir` (`_shared`), so one live window satisfies that match for all sixteen slots. The
comment forty lines above already states the rule it broke — "IN SHARED-PROFILE MODE THE PROFILE NO
LONGER IDENTIFIES A WINDOW ... The ORIGIN PORT is the per-slot identity now" — but the fallback was
left in place. The origin-port test above it was correct and returned the right answer; the fallback
overrode it.

FIX: `if ($shared) { return 0 }` before the profile-dir fallback. Verified in the same production
path: `status` then showed slot 1 `windows 1`, slots 2-16 `windows 0`, "1 window(s) open"; `dshw new`
printed `new window: slot '2' (profile _shared, origin :3201)`, wrote the `windows.log` line at
10:55:59, and `GET http://127.0.0.1:3200/__dshw/open` returned
`{"ports":[3200,3201],"live":{"3200":3,"3201":2}}` — the second window is genuinely live.

THE GENERAL RULES:
1. A hidden launcher that exits 0 on failure is indistinguishable from a broken button. If a control
 the owner presses can fail, its failure must reach a log he can be shown.
2. When a fallback is added under a check whose own comment says the fallback's assumption is invalid,
 the comment is not the fix. Read the code below the comment you just wrote.
3. A shared resource is not an identity. Sixteen identical `--user-data-dir` values cannot
 distinguish sixteen windows, and any code that treats them as distinguishing is wrong by construction.
