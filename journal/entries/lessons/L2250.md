**L2250 · The first boot after a BIOS/firmware flash is never a valid test - a flash erases the UEFI variable store**

**The first boot after a BIOS/firmware flash is NEVER a valid test: a flash erases the UEFI variable store, so a missing VSM blob on that boot is the expected consequence of the flash, not a recurrence of the fault.**

Measured on ZABZ-TECH, 2026-09-20. Reading the VSM key state at each boot is how this machine's Windows-Hello-wiped-on-every-restart fault is judged: healthy shows `BlobFromUefiVariableSize: 723` and `UefiBlobIsCorrupt: 0` in `Microsoft-Windows-Kernel-Boot/Operational` event 85, broken shows `0` and `1`.

The first boot after the BIOS flash (15:02:26) read `BlobSize=0 / UefiBlobIsCorrupt=1` — and was read as "the firmware update did not fix it". That reading is wrong. The VSM key lives in a **UEFI variable**, and flashing the BIOS clears that store, so on the first boot afterwards there is nothing there to read and something is *required* to be re-sealed. The fix only becomes testable on the SECOND boot: measured at 15:33 and again at 15:38, `BlobSize=723 / corrupt=0`, VSM cached-copy unseal `0x0`, and Windows Hello loading `State: Okay`.

This is why the fault stayed open across a whole day of firmware work: each flash produced a boot that looked like a failure, and each of those was taken as evidence the approach had not worked, so it was retried. It was also confounded the other way — *applying firmware is itself a PCR/state change*, so every boot that applied one wiped the container **again**, and those wipes were likewise read as the fault recurring rather than as the cost of the remaining firmware updates draining.

THE RULE, generalised: when you change firmware or anything that owns a persistent variable store, the immediately following boot is inside the change, not after it. Take the reading one boot later, and say which boot you measured. And when a fix is applied across several boots (one firmware update per boot, deliberately, to avoid a simultaneous multi-PCR change), expect the symptom to keep appearing until the *last* one lands — a recurrence during a multi-step fix is not a refutation of the fix.

Related and corrected in the same pass: `L2184` (2026-09-20, ZABZ-TECH) recorded "firmware driver installed != firmware applied: check Get-PnpDevice problem codes and the hardware version, not the Windows Update result code". That lesson is sound and this entry endorses it — the body of L2184 leaked a scratch file path instead of the text, so the substance is restated here. Both halves are the same shape: **a success code is not the state you care about; measure the state, and measure it at a moment when it is meaningful.**
