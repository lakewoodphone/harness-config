**L3367 · A monitor cannot alert on a switch it cannot read - and test it on the platform it runs on**

GOAL ROUND 14, following the launch-flag finding with the obvious question: what OTHER protections live in configuration rather than code? The dangerous sibling is MOCK_OUTBOUND_COMMS. With it set, send_message logs an intercept and returns {'ok': True, 'sid': 'SM_mock_shadow'} for every SMS and email - the company appears to answer customers and NOTHING LEAVES. High severity, low probability, completely silent, and customer-facing rather than a data exposure. It is absent from production today, which is exactly why it needed a monitor. TWO HALVES, AND THE FIRST WAS THE MISSING ONE: (1) nothing outside the process could see it - the only surface that reports it (_build_safety_modes_summary in communications_contract.py) is behind the API key, which an external watchdog cannot present, so /health (the unauthenticated liveness surface) now carries 'outbound_mock' next to 'mode', with the reasoning in app/main.py::_outbound_mock_flag; (2) company-heartbeat.sh reads the whole /health body and raises a distinct MUTE alert, exempting a survivor because mock mode is its safety belt and 'mode' says so. GENERAL RULE: a monitor cannot alert on a switch it cannot read - if a silent switch has no unauthenticated observable, the monitoring work begins with exposing it, and that is a code change, not a config change. AND A FLAW IN MY OWN METHOD, worth more than the feature: my first verification ran the heartbeat locally on the Windows laptop through git-bash, where python3 is NOT usable - so every python parse in the script silently returned 'unknown' and the state file looked like a broken monitor. The script was fine; the TEST was invalid. That same invalidity had already happened in an earlier round, where I saw loop_running_ok: unknown from a live instance and EXPLAINED IT AWAY instead of asking why a parse would fail. All four cases were re-run on the Hetzner box where the monitor actually runs, and only those results are quoted: primary+mock ON -> MUTE alert fired; primary+mock OFF -> silence; survivor+mock ON -> 'survivor-exempt', silence; primary+guard-not-enforcing -> SECURITY alert fired. SECOND RULE: test a shell monitor on the platform it runs on, because a degraded interpreter on the test host produces exactly the output a broken monitor would, and 'unknown' is the one value that cannot tell you which of the two you are looking at.
