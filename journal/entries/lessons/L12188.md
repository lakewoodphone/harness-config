**L12188 · Erase-then-redirect: the page's unload writer puts the copy back**

A CLEAR THAT IS FOLLOWED BY NAVIGATION IS UNDONE BY THE PAGE'S OWN UNLOAD WRITER.

Measured in personality-test @ 0ec1466 (worktree _pt_wt/fx-signout), sign-out defect: the dialog promises "clears the answers and the report kept in this browser", the POST succeeds, and the localStorage keys are still present afterwards (two independent readiness runs, same result).

Ruled out, by reading rather than guessing: sign-out DID call the clear (`signOutAndClearThisBrowser` -> `clearAssessmentSessionRegistry`), and the clear DID compose the right key (`<baseKey>:<fingerprint>` from the identity the gate published) — not the legacy bare keys, not another namespace.

The cause: `AccountBar.signOut()` returns straight into `window.location.assign("/")`. That navigation fires `pagehide`/`beforeunload`, and `assessment.tsx` mirrors the still-live attempt to localStorage on both events (`mirrorVisibleSessionToLocalCache` -> `persistAssessmentSessionRegistry`). The page's LAST write lands after the erase and puts the copy back. A clear followed by a redirect therefore proves nothing about the bytes after the redirect.

Fix shipped (6d7eafc): `sealAssessmentSessionRegistry()` — clear, then close the namespace for the rest of the page's life; every writer refused at the single choke point (`persistAssessmentSessionRegistry`). Only a page load releases it. The plain clear stays plain on purpose: "Clear the saved assessments in this browser" keeps the person in the app, so sealing there would turn a clear into a dead assessment. Test pins both halves.

TRANSFERABLE RULE: when a delete or clear is asserted by a browser verification, check the keys AFTER the navigation the control causes, not after the call returns. Any "erase then redirect" control needs its writers closed, not just its removal performed — and the way to find them is to grep for every `localStorage.setItem` plus every `pagehide`/`beforeunload`/`visibilitychange` handler, because an unload handler is the one writer that always runs last.

Also worth keeping: a pre-fix RED inside the repo (assert the invariant with the current API, watch it fail with the real key present) is stronger evidence than a test that fails only because a new symbol does not exist yet.
