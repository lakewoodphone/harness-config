**L1626 · Driving a Linux host from Windows PowerShell: scp the script, never inline it, never heredoc into bash -s**

Three failed remote commands in one deploy, all the same mistake. Each has one fix.

1. INLINING A SCRIPT IN A DOUBLE-QUOTED `ssh` COMMAND. `ssh hetzner "docker exec X sh -c \"grep … |
 uniq -c\""` fails in PowerShell because `\"` is NOT an escape in a PowerShell double-quoted
 string — the string ends at the `\"` and the rest (`| uniq -c`) becomes a PowerShell pipeline
 ("uniq: The term 'uniq' is not recognized"). Use single quotes for the remote command, or better:
 write the script to a file, scp it, run it by path. Cost: silently ran the wrong thing locally.

2. HEREDOCS INSIDE A SCRIPT FED TO `bash -s`. `Get-Content -Raw script.sh | ssh hetzner "bash -s"`
 looks clean, but bash reads the script from stdin, so a `<<'PY'` heredoc in that script fights for
 the same fd: the heredoc body arrived EMPTY and `docker run … python3 -` printed nothing, with no
 error. Silent no-op is the worst failure mode. Fix: no heredocs — ship the Python as its own file
 (`scp probe.py` then `python3 /probe/probe.py`), or `ssh -c` a single command.

3. PILLING `$?` THROUGH POWERSHELL. `ssh host "… > log 2>&1; echo BUILD_EXIT=\$? > …"` printed
 `BUILD_EXIT=True` — PowerShell had already expanded `$?` to its own Boolean. Exit codes must be
 captured remotely as `$?` with the escaping actually verified, or read from a file the remote
 shell wrote itself.

WHAT TO DO INSTEAD, always: author every remote script locally with the `write` tool, `scp` it, then
`ssh host "bash /tmp/<name>.sh"`. It is shorter than one clever quoting attempt, it is re-runnable,
it is reviewable afterwards, and it cannot half-execute locally by accident.
Also strip CRLF before sending a shell script that will run on Linux: check with
`grep -c $'\r' file` and send `((Get-Content -Raw f) -replace "`r","")`.
