**L3252 · Mesh dispatch: a task that starts with '-' is an option, and ONE '--' does not fix it (dsh launcher vs dsh-headless)**

**DURABLE RULE.** When a mesh child reports `failed ... the remote one-shot exited 1 and
produced no final message`, the FIRST thing to read is the node's stderr tail — it is
usually one line of CLI diagnosis, not a transport fault. Four separate defects were
hiding behind that one message (measured 2026-10-05 on ZABZ-TECH, `plugin-remote-fanout`):

1. **A task that begins with `-` is an OPTION, and ONE `--` does not fix it.**
 `dsh` is a LAUNCHER: `@deepseek-ai/dsh/lib/bin.js:85` declares it with
 `.allowUnknownOption().passThroughOptions().enablePositionalOptions()`, and the task
 is read by a SECOND program, `@deepseek-ai/dsh-headless/lib/startup.js:21`
 (`.argument("[task...]")`, no `allowUnknownOption`). commander consumes a single `--`
 as the LAUNCHER's own end-of-options marker, so it never reaches the app.
 Measured: `… headless '--- x'` → exit 1 `unknown option '--- x'`;
 `… headless -- '--- x'` → exit 1 (the `--` was eaten);
 `… headless -- -- '--- x'` → exit 0.
 **Emit TWO `--` before the task.** The mailbox brief began `--- mesh mailbox …`, so
 this fired on 100 % of mailbox dispatches — and the frame still closed with an honest
 exit code, which is why it read as a transport fault.
 Also worth knowing: a leading SPACE on the task defeats the `-` test too, but the
 double separator leaves the task text untouched, so prefer it.

2. **The exit code in the placement ledger is the SSH CLIENT's, not the child's.** `state:
 settled`, `exitCode: 1`, `meshHost: null` and `classification: structural` all look
 like "the child ran and decided something". They can equally mean "the child never
 started". `structural` + empty `meshHost` + `framed: true` = the remote program ran and
 the child inside it did not.

3. **Windows PowerShell 5.1 eats `"` in a native argument.** `& 'node' 'bin.js' … '<val>'`
 loses every embedded double quote, because PS 5.1 splices the value into a command line
 the C runtime re-parses. Measured via `node -e` echoing `process.argv`:
 `has "double" quotes` → `has double quotes`; `MESH_MAILBOX={"dir":"C:/x"}` →
 `MESH_MAILBOX={dir:C:/x}`. So EVERY prompt to a Windows node was silently losing its
 quotes, and the mailbox manifest was invalid JSON. Fix: escape with the MSVCRT rule
 (`"` → `\"`, doubling the preceding backslash run; trailing run doubled) — verified to
 round-trip. A quote-free channel (base64url) is the belt-and-braces version and is now
 shipped alongside the JSON manifest.

4. **`printf -v` is a BASH builtin; the POSIX program runs under `/bin/sh`.** On a dash
 node it prints `sh: 3: printf: Illegal option -v` and `FANOUT_TRANSPORT_HOST` is written
 EMPTY — so the placement proof (the transport's own record of which machine ran the
 child) is silently void while the child still answers. Use `name=$(hostname)`.

5. **Derive a remote path with the TARGET's separator.** `path.join` on a Windows
 dispatcher turns a POSIX node's `/home/zabz` into `\home\zabz`. `mailboxPaths` /
 `defaultMailboxRoot` now take `separator` (`path.posix.join` / `path.win32.join`).

6. **A mounted bundle cannot hot-load (P210).** The junction
 `~/.dsh/profiles/{web,mesh}/node_modules/dsh-plugin-remote-fanout` →
 `~/code/harness-config/packages/plugin-remote-fanout` means editing the REPO is the right
 and only place to edit — but a running engine keeps the module it imported at BOOT. After
 fixing it, the resident engine's `subagent` tool still emitted the OLD quote-stripped
 diagnostic, which is the proof it was stale. Restart (`multi-window/dshw.ps1 stop` then
 `up`) or use a fresh `--profile mesh` process.

PROOF SHAPE THAT ACTUALLY DISCRIMINATES: `--profile mesh headless "<task>"` answers its own
task LOCALLY — a returned answer proves nothing about the mesh. Check
`~/.dsh/mesh/placements/` for a record: `meshHost` non-empty, `exitCode: 0`,
`stopReason: completed` is a real dispatch; no new record means no mesh dispatch at all.
