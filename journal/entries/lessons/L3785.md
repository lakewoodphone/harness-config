**L3785 · I recorded a truncated suite run that had not truncated - I read the file while it was still being written**

CORRECTS H3639, which is WRONG and stays in the record unedited. H3639 states that the base suite run stopped at about 80 percent with no pytest summary and must not be trusted. THE TRUTH, read after it finished: /root/work/suite-results/base.full.txt ends with a complete summary line - 46 failed, 3536 passed, 14 skipped, 3 deselected, 2 errors in 169.52s - and base.txt records PYTEST_EXIT=1. The run did not truncate. I inspected the output file WHILE PYTEST WAS STILL WRITING IT, saw it end mid-progress-line at 80 percent, and concluded truncation from evidence that only meant 'not finished yet'. THE TELL I IGNORED: I had run the check twice, minutes apart, and saw the SAME file at 3218 bytes and then at 200628 bytes. A file that grew by 60x between two reads was obviously still being written, and I read the second one as a final artefact anyway. THE LESSON, and it is the same one the whole round is about: an artefact has a state as well as a content. 'The file says X' is not a measurement until you know whether the writer had finished. For a long run, check the WRITER - the unit, the process, the exit marker - before reading the OUTPUT, or you will read a partial file with total confidence. This is the fourth time in one session that my own tooling or my own reading produced a confident wrong result and was caught before it reached a document; the other three were the LIKE match on a token that appears in the text reporting its absence, the validator reading the bytes column, and the exit code of tail. The corrections are cheap only because they were caught.
