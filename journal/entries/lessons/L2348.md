**L2348 · An INSERT-only log's newest row cannot tell a quiet inbox from a dead poller -- the third time this fleet made that mistake**

An INSERT-only log's newest row ages during a quiet period exactly as it would if the
writer had died, so it can never answer "is the job running?".

Measured 2026-09-22 14:51Z: the kernel raised HIGH `comms_freshness` on
`MAX(email_triage_log.created_at)` = 3.1h, concluding "the Gmail poller has stopped
classifying new mail". The poller had not stopped. On secratary at that moment,
`data/autopilot_state.json` carried `subsystem_health.gmail_decisions.last_ran_at`
19 minutes earlier with `last_status=ok` and `consecutive_failures=0`, and
`last_gmail_poll_at` was 0.3h old against a 900s interval. Ten consecutive runs,
50-60 minutes apart, no gaps, every one `ok`. The inbox was simply quiet: the
newest unread mail was 0.6h old and every message older than 2h already had a
triage row.

This is the **third** instance of one mistake in this system, which is what makes
it a lesson rather than an incident:

- `dialpad_call_full.fetched_at` — INSERT-only, so `MAX(fetched_at)` was replaced
 by `~/.dialpad-harvest.last_run`.
- `dialpad_sms_cache.fetched_at` — identical shape, honest signal is
 `~/.dialpad-sms-harvest.last_run`.
- `email_triage_log.created_at` — the same, and the last one still being read as
 if it measured the writer.

The rule: **judge a scheduled job by a heartbeat the job writes on every completed
pass, not by the newest row it happened to produce.** Keep the log age as a
reported metric so the change is auditable, but never as the health test.

And the corollary, because a heartbeat is necessary but not sufficient: a poller
can run perfectly and still never complete its work. The only claim an empty
result cannot fake is a thing that is *still* not done — so the email check now
also counts messages the poller has held past the window that have no triage row.
The absence of the row is the evidence; nothing is inferred from subject lines.

## How it was verified, because "the check is green now" is not evidence

Seven cases against a copy of the state file in /tmp, never the live one — the
check reads `SENTINEL_AUTOPILOT_STATE_FILE`, so a test cannot write production
state. Healthy baseline -> ok. Poll 9.3h stale -> HIGH naming the poller. Poller
`status=failed` with 4 consecutive failures -> HIGH. Two held messages with no
triage row plus one fresh -> HIGH, counting exactly 2 and not 3. Poll time missing
-> HIGH. State file absent -> HIGH. State unparseable -> HIGH. All seven correct.

A check that has only ever been seen green has not been tested. When you change a
health check, feed it the failures it exists to catch and watch it fail.
