# A shared crontab is a read-modify-write, and it will eat your line

**Measured 2026-10-12 on `secratary-cloud`, within 30 minutes, and it was my own line that vanished.**

## What happened

`run-sentinel` — the job that computes every "Company findings" item in the owner's attention badge —
was installed into root's crontab at **03:15:36Z** using the estate's standard shape:

```
{ crontab -l | grep -v run-sentinel; echo "*/5 * * * * /usr/local/bin/cron-wrap.sh run-sentinel <b64>"; } | crontab -
```

At **03:44Z** a mesh child reported it was not there. Measured: `crontab -l | grep -c run-sentinel` →
**0**; nothing in `/etc/cron.d/`; no systemd timer. And the ledger — which `cron-wrap.sh` writes one row
per run — held exactly one `run-sentinel` row, `03:15:36Z`, which was my own **manual** wrapper test. So
the cron path had never fired at all, and nothing reported the loss.

## Why

Three sessions edited root's crontab in half an hour: mine at 03:15:36, another session's spool write at
**03:15:47**, another at 03:44:10. Every edit is `crontab -l | <change> | crontab -`. If a session's read
predates another session's write, its write-back **deletes** the addition — and each session's own
verification passes, because each verified *its own line*, which is the one line that is definitely in
the file it just wrote.

The loss is invisible from every direction afterwards: the producer runs when invoked by hand, its
state file is valid, its check output is correct. Only the schedule is missing.

## What to do instead

1. **After any crontab edit, count every job name you care about — not the tail.** I "verified" by
 tailing three lines and seeing my own new line. That check cannot see a lost line anywhere else in
 the file. `for n in a b c; do crontab -l | grep -cE "cron-wrap.sh $n( |$)"; done` is the honest one.
2. **Prove a schedule with a ledger row, not with the file.** Run the job once through the wrapper
 (`cron-wrap.sh <name> <b64>`) and read `~/.cron-status/runs.tsv`. A line in a file is a claim.
3. **Prefer `/etc/cron.d/<name>` for a critical job.** A separate file cannot be clobbered by anyone
 else's `crontab -l | … | crontab -`. `model-failover-watch` was ported that way on the same night
 for exactly this reason.
4. **Monitor the schedule, not only the producer.** `sentinel-freshness-check.py --expect-cron NAME`
 reads root's crontab *and* `/etc/cron.d/`; an unscheduled job is an absence finding on the same
 alarm path as a stopped one. `--expect-cron run-sentinel` caught this state against the real machine
 (`unscheduled … the schedule is GONE`, rc=2) before the re-install.
5. **The tool the error message names does not exist on this host.** `cron-wrap.sh` refuses with *"run
 ~/bin/wrap-crontab.py --install"*; that script lives on the office box (`/home/zabz/bin/
 wrap-crontab.py`, 177 lines) and is absent on the authority. An error message pointing at a missing
 tool is a small lie that costs the next operator ten minutes; either port the tool (`WRAPPER` needs
 to become `/usr/local/bin/cron-wrap.sh`) or change the message.

## Why this is worth a lesson and not just a fix

It is the third instance of one shape in a single night: **the broken thing was adjacent to the thing
being watched.**

| symptom the owner saw | what was actually broken |
|---|---|
| a badge reading `stale 6h ago`, growing | the producer had moved to another host and nobody moved it back |
| `config_sync` reporting "cannot tell" | the writer of the status file had not been ported |
| a stale badge about to happen again | the cron line had been deleted by a concurrent edit |

None of the three produced an error. Each looked like the layer above it. A monitor that only measures
the producer, the check, or the job will keep blaming the wrong layer — so measure the *link* as well
as the endpoint.
