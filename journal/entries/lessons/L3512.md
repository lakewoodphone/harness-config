**L3512 · Do not use robocopy onto a customer's FAT32 stick: ERROR 87 'Changing File Attributes' plus /R:2 /W:2 cost 29 hours, and two confounded measurements hid the cause**

**Measured 2026-10-11**, copying a 207 GiB recovered-data delivery onto a customer's FAT32 USB stick. It cost hours and produced three separate wrong conclusions before the real cause was found.

## The failure

```
ERROR 87 (0x00000057) Changing File Attributes F:\Organized\Audio\11E118A0.mp3
ERROR: RETRY LIMIT EXCEEDED.
```

with `robocopy /E /COPY:DAT /DCOPY:DAT /R:2 /W:2`. **`/R:2 /W:2` turns each failure into ~6 seconds of retrying**, so a class of files poisons the entire run.

## What it was NOT — every one of these was tested, not reasoned about

| hypothesis | test | result |
|---|---|---|
| FAT32 can't store the file's attributes | `Get-Item .Attributes` | **just `Archive`** — ordinary |
| the file data didn't copy | compared byte counts | **identical** (45,836,288 = 45,836,288) |
| attribute *copying* is the problem | `/COPY:DT` (no `A`) | still fails |
| it's the FAT timestamp granularity | `/FFT` | still fails |
| it's copying attributes at all | `/COPY:D` — data only | **still fails** |
| the source can't have attributes changed | `attrib -A` at a prompt on that very file | **succeeds, exit 0** |
| robocopy is simply slow here | `shutil.copy2` on the same file | **14.5 MB/s** |

So it is robocopy's own post-copy attribute handling against this source/target pair. **The fix is not a flag; it is a different copier.** `copy_to_stick.py` uses `shutil.copy2` per file.

## The measurement error that hid it, twice

1. **"The stick writes at 15.6 MB/s."** That was a 200 MB write — which only measures the **write cache**. A 1.5 GB sustained write came in at 5.71 MB/s, and a single 3.2 GB file at 19.79 MB/s. Three numbers, all "the write speed", all different, because each measured a different regime. **State the transfer size and the regime with any throughput number, or it is not a measurement.**
2. **"`/MT:16` is the problem."** It looked like it — `/MT:16` ran ~2 MB/s and a single-stream file test ran 19.79 MB/s — and I changed the design on that basis. The real cause was the attribute retries, present in **both**. **An A/B where one arm changes two things proves nothing about either.**

## Design rules that survive this

- **Resume on size, per file.** `if dest exists and getsize(dest) == expected: skip`. Measured: 2,119 files / 10.77 GiB skipped instantly on a restart. No ledger to corrupt, no state file to lose, and it works after a reboot, a killed process or an unplugged stick.
- **Never a mirror.** The copier has no delete path at all. A copy tool that can remove files is a copy tool that can remove the wrong files.
- **Single stream on cacheless media.** Concurrency needs a write cache to reorder into; without one it manufactures random writes.
- **Log an ETA from the observed rate**, not from a hoped-for rate. The first estimate here was 4 hours and the truth was 29.
