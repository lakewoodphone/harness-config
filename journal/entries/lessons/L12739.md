**L12739 · one headless child on the working machine falsified 'the mesh node has no credential'; and a mounted credential service removes the environment fallback**

## L — "the mesh node has no credential" was the estate having no credential: three commands that separate the two, and one that proved it

MEASURED 2026-10-21. A fleet of six `subagent` calls all died at startup and the session concluded "the mesh node has no model credential", fell back to six local children, and moved on. The diagnosis was wrong in its subject and right in its symptom, and the wrongness is what made it feel finished: it named a machine, so nobody asked whether the other machines were fine.

THE FACTS, in the order they were cheap to get.
1. THE FAILURE IS ONE LINE, AND IT DOES NOT NAME A MACHINE: `dsh: MISSING_CREDENTIAL: llm-deepseek: no API key for provider route "deepseek-official"; store DEEPSEEK_API_KEY through the credentials service ... or export DEEPSEEK_API_KEY in the launching environment`. That message offers two mechanisms. Read it as an invitation to find out WHICH ONE is missing, never as a statement about the host it happened to print on.
2. RUN THE SAME COMMAND ON THE MACHINE THAT WORKS. `node <engine>/@deepseek-ai/dsh/lib/bin.js --profile headless "Reply with exactly MESH-PROBE-OK and nothing else."` on ZABZ-TECH — whose web GUI had been answering all morning — exited 1 with the identical error. One command moved the blast radius from "the laptop" to "every headless child on the estate", and changed the fix from a node repair to a composition repair. A control on a known-good machine is the cheapest falsification available and it took 30 seconds.
3. `--profile headless --dump-config` PRINTS THE ANSWER: `- id: credentials` / `name: '@deepseek-ai/dsh-credentials-local'` / `disabled: true`, under a `# == @deepseek-ai/dsh-base, patched by @deepseek-ai/dsh-headless` marker. The web profile's dump has the same row with no disable. `disabled: true` on a row that resolves credentials IS the bug, and it is visible without running anything.

WHY IT WAS INVISIBLE FOR SO LONG: the web GUI authenticates fine, so the estate looked healthy; only a one-shot child hits the disabled row. And the dispatcher's own report printed `credential = the interpreter inherits its credential from the dispatching process environment` — a sentence that reads like a supplied credential and was true only while the parent engine was launched with the key in its environment. When the key moved into the managed store, that sentence became a lie nobody re-measured. `nodes.js` now records `!self-store` for the Windows rows and `remote-script.js` says the interpreter form passes NO credential file at all. LESSON: a diagnostic string is a claim, and an unmeasured claim in a report is worse than no report, because operators cite it.

THE DESIGN TRAP, which is the part to remember: mounting a credential service REMOVES the environment fallback. `dsh-llm-deepseek-api-key` is `if (credentials !== void 0) { const hit = await credentials.resolve(ref); if (hit !== void 0) return ... } else { ...ambient... } throw MISSING_CREDENTIAL`. A node with an empty store and a mounted service is worse off than one with no service at all. `zabz-tech-linux` is exactly that node (no `refs:`, key in `/etc/dsh-worker.env`), so the row is `disabled: !!js process.platform === 'linux'` and the comment says which measurement justifies removing the gate. Any future "make this uniform across the fleet" instinct must read that gate first.

HOW TO VERIFY THE WHOLE FLEET IN ONE PASS, read-only: for each node, `--dump-config | grep -A2 'id: credentials'` (is the service mounted?) and `grep -c '^ DEEPSEEK_API_KEY:' ~/.dsh/.credentials.yaml` (is its store able to answer?). Mounted + no ref = broken; unmounted = needs the environment; mounted + ref = correct.

RELATED, NOT THE SAME: P249 (a child ON zabz-tech-linux that delegates FURTHER dies MISSING_CREDENTIAL). That is the nested-dispatch case and stays open; this entry is about the first hop.
