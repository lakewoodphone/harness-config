**L12670 · LPT SSO enabled: the secret already existed across six services - check for existing holders before asking anyone to issue a credential**

## LPT SSO: the credential already existed fleet-wide, and asking for it would have been wrong

Resolved 2026-10-21. owner-queue #912 and ledger 931 had both been framed as "LPT must issue a
site-specific secret". Neither was true.

### What was actually true

`/opt/lpt/.env` `LPT_SSO_SHARED_SECRET` existed at **48 characters**, and the **identical value**
(sha256 prefix `3d4e5cd380`) was already held by five other services on `lpt-apps`:

`/opt/lpt` (issuer) · `/opt/lakewood-rentals` · `/opt/chumash-timeline` · `/opt/personality-test` ·
`/opt/personality-test-test`

`/opt/filter-site` was the **only** consumer left empty. So enabling LPT sign-in was an *alignment*
with an existing credential, not a request to a counterparty. No message was sent to anyone.

### The method worth reusing — before asking anyone to issue a credential, look for existing holders

`grep -rl '<KEY_NAME>' /opt --include=*.env --include=*.ts --include=*.py | grep -v node_modules`
then compare values across holders **by sha256 prefix, never by printing them**. That one pass turned
a "blocked on an external party" item into a five-minute configuration change, and it simultaneously
revealed the thing that made a *rotation* unsafe: five services share the value, so rotating it is a
six-service window.

> An earlier audit (`LPT_SIGNIN_AND_ACCOUNT_AUDIT_2026-09-14.md`) recommended rotating this value as
> a "dev value". That recommendation is now known to be a fleet-wide operation. Do not act on it as a
> one-liner.

### The system surface

- The site sends `x-lpt-sso-secret: <SITE_LPT_SSO_SHARED_SECRET>` to
 `POST https://api.lakewoodphoneandtech.com/api/auth/sso/assert`.
- LPT accepts only if it equals its own `LPT_SSO_SHARED_SECRET`.
- **The diagnostic is 403 vs 401.** 403 = secret missing/wrong; **401 = secret accepted, cookie
 failed**. Measured: no header 403, wrong secret 403, our secret with no cookie 401, our secret with
 a junk cookie 401 `sso:invalid`.
- `GET /login` when configured and no LPT cookie → **303** to LPT's `google/start`, whose signed
 state carries `returnTo` (so the allowlist is proven to accept `filterapp.lakewoodphoneandtech.com`).
- `GET /login?local=1` → **200** with the paper-password form. The password form is deliberately
 hidden otherwise (`web/server/app/main.py` ~477-480), because LPT is the account (D38-08).
- **The broker is not involved.** `lpt_filter_ai_api` has no SSO environment variable at all; #912's
 instruction to restart it was unnecessary. Only the compose service `site` was recreated.

### Consequence to keep an eye on

`/login` now sends every visitor to Google. A parent holding a paper password must know about
`?local=1`; if support calls start, the fix is a visible "use a password instead" link — a product
change, not a defect.

### Still unverified, and it must be said that way

A real Google sign-in round trip. Nobody has completed Google consent and landed on `/account` with a
live session. Everything up to Google's screen and everything downstream of the redirect is proven,
including the repo's cross-service smoke test (`2 passed in 4.24s`). The human step is not
automatable and was not attempted with owner credentials.
