**L3115 · A leftover Python directory with loose .py files imports SILENTLY as a namespace package, so a test can import the ORIGINAL module by accident**

MEASURED 2026-09-30, during the gateway fix, and it nearly made me report a working patch as
broken.

I copied `app/services/ai_gateway.py` to `/tmp/ai_gateway_patched.py`, edited it, and imported
it by path with `importlib.util.spec_from_file_location`. The test then reported the PATCHED
module WITHOUT the new attribute, while a diff and a grep both showed the change present.

CAUSE, in two parts, and the second is the trap:

 1. `spec_from_file_location("app.services.ai_gateway_patched", path)` executes the file, and
 the file does `from __future__ import annotations` plus module-level imports from the app
 package. Fine.
 2. But `sys.path` already contained the app root, and a LEFTOVER `ai_gateway_patched.py` in
 the services directory was importable by name. Worse, an earlier run had left it there, so
 a later `import` resolved a DIFFERENT file than the one under test, and because there was
 no `__init__.py` in the scratch directory, Python treated it as a namespace package and
 imported it happily instead of raising.

THE RELIABLE PATTERN, used for the rest of the session:
 * Write the scratch module INTO the package directory that its relative imports expect, so
 `Path(__file__).parents[2]` and sibling imports resolve as they do in production, then
 DELETE it in a `finally`.
 * Copy the LIVE file into the scratch path rather than writing a fresh one, so the test
 exercises exactly what is deployed.
 * Assert on the ORIGINAL, not on a paraphrase: `"in flat"` checks failed twice because the
 source kept the quote characters between adjacent string literals. Normalise with
 `.replace('"', ' ').replace("'", ' ')` before searching for a phrase that spans lines.
 * When a check reports a failure, first ask whether the CHECK can distinguish the two states
 it claims to. Three of the six FAILs this session were the checker's fault, not the code's.
