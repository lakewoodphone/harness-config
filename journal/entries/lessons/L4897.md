# L — I destroyed a concurrent session's draft by writing a live file I had not diffed

**2026-10-15. This one is mine, and it is the third self-inflicted trap of the session.**

## What happened

Another DSH session wrote a **one-item owner-text composer** and deployed it to
`/opt/company/scripts/owner_attention.py`. Minutes later I deployed my own fix — the personal-mail
tier and the reserved slot — **to the same file**, and overwrote theirs. Their drop-in note records it:
*"was then OVERWRITTEN by a concurrent session editing the same file (written 14:46:16Z)"*.

Their own preservation attempt also failed: the file they filed under
`owner_attention.CONCURRENT-SESSION-14-46.py` is byte-identical to **my** version (`9a383127a2a8`), and
the draft they name at `backup/owner_attention.py.pre` is byte-identical to the **tracked repo copy**
(`5adb53c449a5`, 25253 B, mtime 2026-10-13) — the pre-change original, not the draft. So the draft
exists nowhere on the authority and has to be re-authored from its description.

## Why my checks did not catch it

* `git status` in `/opt/company` compares against the tree's HEAD. **A concurrent session's live edit is
 indistinguishable from the original when both differ from HEAD**, and the tree was already 36-files
 dirty, so one more modified file proves nothing.
* I hashed the file **before and after my own install** and confirmed they differed — which only proves
 *I* changed it. It says nothing about whether the content I was replacing was someone's work.
* For `shadow_learning.py` I *did* diff the live file against my base and saw exactly my guard. I did
 not repeat that for `owner_attention.py`, because by then I had a working pattern and stopped applying
 it. **The check that works is the one I skipped on the second file.**

## The rule

**Before writing any live file, diff the live file against the base you intend to replace it from, and
read the diff.** If it contains anything that is not yours, stop: another session is editing it. A hash
proves existence, not authorship; `git status` is blind to a peer's uncommitted work in a shared tree.

Applies to `/opt/company` and to every shared checkout on this mesh. The alternative is
`install`-with-backup *plus* a diff, never a bare overwrite.

## What it cost, and what recovers it

Cost: one drafted composer, about to be re-authored (ledger item 346). No customer data, no money, no
outage — the digest it feeds is silenced by the owner's own instruction, so nothing regressed in the
interim. Recoverable because the drop-in describes the draft's contract precisely: one item, no counts,
no file path, no truncation marker, plus a daily cap and a standing-rules gate.

## And the same shape in the queue

Lesson `L4704` L-1 said "after resolving rows, sweep the ledger for stranded `owner_row` references".
Three rounds later I filed item 345 against row 520 **and resolved 520 in the same breath**, turning
`lint-refs` red immediately. **A lesson written and not read at the point of the next similar action is
decoration.** The fix is not to write better lessons; it is to run the check as a step, not as a memory.
