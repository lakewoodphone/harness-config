**L2314 · Alert channels fragment one obligation into N rows, and that fragmentation is the owner-attention debt**

## LESSON 2 — every alert channel in this company fragments the same obligation into N rows, and that fragmentation IS the owner-attention debt (measured 2026-09-22 00:20Z)

THE MEASUREMENT. Three separate ledgers, one identical defect:

- `reminders`: **464 rows all-time, 38 pending**. One obligation — the PayPal case `PP-R-VHU-644541358` / Global Direct Parts order 161898 ($167.96, deadline 2026-10-16) — is **16 separate pending rows** (ids 388, 390, 409, 410, 411, 412, 413, 414, 415, 417, 418, 419, 421, 425, 430, 432, 434, 447-450, 462, 463), each generated by a different run, each worded slightly differently, all still pending. Same shape for the Elantra IVT fluid service and the post-Yom-Kippur health follow-up.
- `owner_message_queue`: **13 rows `status='held'`, 0 `send_attempts`**, including **2 `urgent`** — the 2026-09-21 morning and evening briefings, which therefore never reached him — plus 8 `proactive_update` rows that are all the same mesh-node event (see LESSON 1).
- `owner_decision_queue`: 22 pending, 3 blocking past 3 days.

WHY IT MATTERS, IN THE OWNER'S OWN TERMS. The whole reason `owner-queue.py` exists (its own docstring) is that `owner_message_queue` had reached **595 undelivered rows and had sent nothing since 2026-07-19 — 54 days** — because it "fills with briefings, sync-breaker alerts and freshness notices, so it became noise and then it became invisible." That is the same end state as 16 identical PayPal reminders: a list that shows one obligation sixteen times is a list that does not get read. **A channel that can only add rows and never collapse them is a channel that is guaranteed to be ignored.**

THE FIX SHAPE (not yet complete). Cluster by the underlying obligation, keep ONE row — for reminders, the soonest-scheduled one, so deliberate early-warning rows beat repeats — and mark the losers `superseded` with a `superseded_by` pointer, never delete. `scripts/dedupe_reminders.py` is the first application (dry-run by default, deterministic, idempotent, fixture-tested before it touches live data).

THE TRANSFERABLE RULE. When the badge says "attention debt", do not treat it as a count to be reduced by hand, and never as a list to re-show the owner. Find the generator that could not collapse its own output and fix that. Every "N urgent messages held" figure I have seen in this system traced to a producer that appends and never dedupes, never re-checks, and never expires.
