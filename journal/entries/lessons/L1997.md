**L1997 · The mesh provider capped a child turn at 300 s while its own transport allowed 900 s**

**L · The mesh provider capped a child turn at 300 s while its own transport allowed 900 s — this is what killed five fleets in one night**

MEASURED 2026-09-18 on ZABZ-YOGA from the failing session's own transcript (session-e34dd061,
turn 155-156). Five `subagent` calls, five identical results:

```
Error: subagent run failed
Diagnostic: the remote turn did not finish within 300000 ms and the ssh client was killed
```

WHY THE EARLIER DIAGNOSIS WAS WRONG, and how easy it was to be wrong: the session that hit this spent
its last two turns attributing the cap to `llm-deepseek.streamIdleTimeoutMs`, on the strength of that
key's *shipped default* of 300000. That key governs the idle gap on ONE LLM STREAM and is set to
60000 in `settings/base.yaml:88`; it has nothing to do with a remote child turn. The number matched,
so the guess stuck. A number matching is not a mechanism.

THE ACTUAL SOURCE, found by the provider's own wording: `packages/plugin-remote-fanout/lib/provider.js:559`
renders exactly that sentence with `${this.timeoutMs ?? 'the configured'}`, and it printed **300000**.
`this.timeoutMs` is set once in the constructor from config (`provider.js:346`), and the config is:

- `profiles/web/cordis.patch.yml:178` — `timeoutMs: ... : 300000`
- `profiles/mesh/cordis.patch.yml:97` — the same

MEANWHILE the transport beneath the provider `packages/plugin-remote-fanout/lib/ssh-transport.js:49`
declares `export const DEFAULT_TIMEOUT_MS = 900_000` — fifteen minutes. So the provider was **three
times stricter than its own transport**, and the comment on that constant says the transport is
"willing to wait three times longer than the harness lets a remote child live".

CONSEQUENCE, which is the whole reason the owner spent a night being told "not done yet": every
orchestrator that fanned out got children that did real work for five minutes and were then severed
mid-stride. The briefs, the partition and the agents were all fine. One number, two layers above the
thing everyone was fixing, made long fan-out structurally impossible.

FIX: default raised to 1800000 (thirty minutes) in both profile files, `MESH_CHILD_TIMEOUT_MS` still
overrides. Thirty minutes keeps a bound on a runaway child; five minutes forbids a fleet.

THE GENERAL RULES:
1. When a component declares a tolerance, anything above it that is STRICTER is a bug, not a choice.
 Grep for the constant and compare — the transport said 900_000 in a file nobody had opened.
2. A provider is the right place to look for a provider's own error string. Search the exact sentence
 the user saw; it identified the file and the line in one grep.
3. Config that needs a restart is config that is not yet in effect. `provider.js` reads `timeoutMs` in
 its constructor, so this fix lands only when the engine that orchestrates is restarted. Measured
 pain P11 says the same thing about presets.
