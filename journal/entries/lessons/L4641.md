**L4641 · House link 2026-10-15: single-flow download swings 44-122 Mbps minute to minute with 0% loss, so the router stack is not the slowdown - the four defects it does cause, and the MTU A/B that could not run**

Measured 2026-10-15 14:17:45-14:23:00 UTC on ZABZ-YOGA (6 GHz Wi-Fi to the Verizon CHR30A, behind a T-Mobile TMO-G4AR gateway, double NAT). 24 rounds, ~13 s apart, 20 MB each from speed.cloudflare.com.

 single-flow download: min 44.3 max 121.7 mean ~84 Mbps
 packet loss in the same rounds: 0% pings to 8.8.8.8: avg 18-56 ms, occasional 283 ms spike
 four parallel flows, same session: 269 Mbps aggregate
 same battery last night (2026-10-14): single flow 160 wired / 219 Wi-Fi; four flows 237 aggregate

So the path is LOSSLESS and its aggregate capacity is unchanged or better, while a single flow swings 3x within minutes. An Ookla-style speed test takes one sample from that distribution, which is exactly why the owner reports "the speed test is very good but YouTube keeps freezing" and "the internet slows" in the same hour. The T-Mobile gateway's own radio read at the same moment: n41, 4 bars, SINR 28 dB, RSRP -89 - a healthy link. T-Mobile Home Internet is the lowest-priority traffic class on a shared tower; this is what that looks like. Do not "fix" it with router settings.

RULED OUT the same session, with numbers: bandwidth (269 Mbps aggregate), loss (0% in ~250 pings), DNS (warm 1-27 ms; the 694 ms and 1692 ms outliers are the first lookup after hours idle and the very next lookup to the same name is 2 ms), Wi-Fi signal (RSSI -24 dBm, 2402 Mbps PHY, WPA3-H2E), the second router's latency (crossing into the T-Mobile hop costs 0-1 ms).

THE SECOND ROUTER DOES COST FOUR THINGS, all measured, none of them the slowdown:
 1. IPv6 dies. The gateway reports hasIPv6 true; on the Verizon's LAN no interface has a global v6 address and there is no v6 default route at all (ping -6 -> "transmit failed. General failure"). Every device behind the second router is IPv4-only while DNS still returns AAAA.
 2. Path MTU is 1436 (payload 1408 passes, 1410 fails) while both adapters are configured 1500. Not silent - 192.0.0.1 returns ICMP type 3 code 4, so PMTUD works.
 3. Double NAT: no inbound, no mDNS/SSDP across the boundary.
 4. The T-Mobile gateway's own Wi-Fi is still broadcasting on 5 GHz channel 157, the same channel as the Verizon's 5 GHz radio - two APs in one house on one channel.

THE EXPERIMENT I COULD NOT RUN, stated as such: an A/B of fresh-connection TLS/TTFB with the interface MTU at 1500 versus 1436. `netsh interface ipv4 set subinterface` needs elevation, the shell is not elevated (Administrators is deny-only), so BOTH phases ran at 1500 and the 26-172 ms difference between them is noise between two identical conditions - a null, not a negative. Measured handshake times are in fact normal (connect 0.08-0.15 s, TLS 0.26-0.41 s), which does not support a PMTUD stall. Treat the MTU as a latent defect with a cheap fix, not a cause.
