## L — Do not run a full copy, VACUUM or filesystem scan on secratary: it stalls sshd and takes the box down

MEASURED 2026-10-09, by me, three times in one session. Each is a different mistake with the
same shape: an expensive read against a 22.9 GiB database on a 4-core 2013 box whose only disk
is a LUKS-encrypted SATA SSD.

1. `sqlite3 ... SELECT ... FROM dbstat GROUP BY name` — a full scan. Left a process in D-state
 for 11 minutes and added ~6 to the load average.
2. `du -sb /home/zabz/personal-secretary-mvp/data` over 35 GB on encrypted storage. Same.
3. `sqlite3 SRC ".backup '/path/probe.db'"` to test an FTS conversion on a copy. This is the
 worst of the three because .backup COPIES 22.9 GB: it drove I/O pressure to
 `some avg10=96 full avg10=94`, put **11 processes in D-state**, and **sshd itself stalled** —
 `ssh: connect to host secratary port 22: Connection timed out` twice, while `tailscale ping`
 still answered. A cluster. Recurse is not needed: the box was unreachable by ssh.

THE RULE, and it is not "be careful":
 * NEVER run on secratary: `dbstat`, a recursive `du`, a full-table `SELECT min()/max()` over
 an unindexed column, `.backup` of the whole database, or `VACUUM`.
 * Size the DB with `PRAGMA page_count * page_size` (instant). Never dbstat.
 * The backup job is ALREADY the I/O event, and its own drop-in 20-io-ceiling.conf records the
 same symptom ("sshd stalling with them, which is why the transport flakes"). Do not add to it.
 * Put any heavy database work on an IDLE box. This is exactly what the new dedicated
 secratary-cloud box is for: copy the database there ONCE, do the conversion and the VACUUM
 there, and never make the production office box do either.

THE TEST THAT MATTERS: `tailscale ping` answered while `ssh` timed out. A saturating disk, not a
network fault, is the commonest cause of "secratary flaked off the network" on this estate.
