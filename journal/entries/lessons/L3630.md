**L3630 · the API slowness was a 37.5 MB JSON identity file re-parsed twice per request - not the database, and Postgres would not have fixed it**

## 2026-10-12 14:20 UTC · ZABZ-YOGA · the slowness was a 37.5 MB JSON file re-parsed on every request - root cause found, fixed, measured, and pushed as 17febcd5

**The chain, each step measured and each step narrowing the last.**

1. **The symptom.** `/status` p50 was **972 ms at one concurrent request**, and **10,379 ms at 32**
 (`/tmp/latency-probe.py`). A near-perfect serial queue: N callers wait ~N x the cost of one call.
2. **The first wrong answer, corrected by measurement.** I had said `_db_lock` (a process-wide RLock,
 815 acquisition sites) was the explanation. **`/health` queues identically - x13.8 from concurrency
 1 to 32 - and it never opens the database.** So the queue is the single Python process, not the lock,
 and not SQLite.
3. **What the request is waiting on.** With 8 concurrent `/status` calls, the machine's load average did
 not move at all (0.65 throughout) and its CPU time barely ticked. **It is waiting, not computing.**
4. **What it waits for.** Timing the two functions `/status` calls, in-process, read-only:
 `ensure_agent` **156 ms warm**, `operations_overview` **312 ms warm** - **~470 ms of work before the
 endpoint answers anything.** Both take file paths.
5. **THE CAUSE.** `data/agent_identities.json` is **37,538,643 bytes - 37.5 MB** - of which the `agents`
 key is **31.83 MB** for **126 agents**. Loading it costs **20.1 ms to read + 146.5 ms to json-parse =
 166.7 ms**, and `_load()` is called **40 times** in `app/identity_store.py`. **Every request re-read and
 re-parsed the whole 37.5 MB file, twice.**

**The fix** (`/opt/company/app/identity_store.py`, commit `17febcd5`, pushed to origin/master):
a **stat-keyed cache** on `_load`, keyed on `(st_size, st_mtime_ns)` so any writer invalidates it,
cleared explicitly in `_save()` **inside the existing `_store_lock`** so this process never serves its
own stale data, caching the post-migration dict, and returning a `copy.deepcopy` on every hit so a
mutating caller cannot corrupt it. **No call signature changed**, so all 40 call sites benefit with no
edit, and nothing is held open.

**Measured effect, same probe, before -> after:**

| endpoint | conc | p50 before | p50 after | |
|---|---|---|---|---|
| `/status` | 1 | 972 ms | **857 ms** | |
| `/status` | 32 | **10,379 ms** | **5,101 ms** | **2.0x faster** |
| `ensure_agent` warm | - | 156 ms | **67 ms** | 2.3x |
| `operations_overview` warm | - | 312 ms | **153 ms** | 2.0x |
| `/health` (no JSON, no DB) | 32 | 116 ms | 77 ms | unchanged shape, x13.2 |

**And the honest residue.** `/health` still queues at x13.2 and it touches neither the database nor the
identity store, because **this is one Python process and the GIL is the floor.** The cache removed the
JSON parse from the request path; it cannot remove the serialisation. Raising the worker count remains
**blocked** - `app/main.py:1200` starts the autopilot inside the startup hook, so N workers means N
autonomous companies (`L3625`).

**Correctness verified, not assumed:** identity store intact (126 agents, valid JSON), the API healthy
with `NRestarts=0`, a caller's mutation does not leak into the cache, the autopilot still running, **no
new errors** (the only ERROR line is the pre-existing Shabbat-plug timeout to the private address
192.168.50.103, which the cloud cannot reach by design), and **zero temp-file leaks** - the defect that
produced 299 orphaned `.tmp` files on 2026-09-20.

**The lesson.** *"The database is slow" was the wrong frame for the whole of this.* The database was
never the queue: a 37.5 MB identity file was being re-parsed on every request, and because the process
is single-threaded, that cost serialised everything behind it. **A large JSON file on a request path is
a database that nobody has indexed**, and the way to find it is to time the functions a slow endpoint
calls, not to reason about the storage engine. **Postgres would have fixed nothing here.**

**Worth a follow-up, named rather than implied:** why is the identity store 37.5 MB for 126 agents -
is something appending unboundedly to an agent record? Caching hides the cost; it does not answer that.
