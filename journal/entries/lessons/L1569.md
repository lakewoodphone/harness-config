**L1569 · Remote-editing a server checkout: hash-guard the write, echo the changed lines, and never restore from a backup you made after the change**

TOOLING RULE (cost me ~30 minutes on 2026-09-15)

The file tools here are resolved against the Windows host, so a checkout on the
Linux authority cannot be edited with edit/write. What worked:

1. Write the script locally, pipe it over: Get-Content x.sh -Raw | ssh host "cat > /tmp/x.sh && bash /tmp/x.sh". PowerShell mangled '<' redirection and nested quotes; a piped heredoc-written script does not.
2. Normalise line endings on the far side first: sed -i 's/\r$//' file. CRLF silently broke an exact-text Python replace (the pattern had LF, the file had CRLF, count=0) and PowerShell ate backslashes inside a Python string, producing '\"e\"' and a SyntaxError.
3. Address edits by LINE NUMBER after grep -n proves the line is unique, and echo the before/after lines. Exact-text replacement is better when you can guarantee byte equality; when you cannot, line-number sed plus a before-check that refuses on mismatch is the safe form.
4. After every remote write: py_compile, then MD5, then the A/B test run.

THE MISTAKE THAT COST THE MOST
I verified the fix with a script that (a) reverted the file, (b) copied a backup
over it. The backup had already been overwritten with the reverted version during
an earlier run, so 'restore' restored the BUG. Two subsequent A/B runs were then
measuring a file whose state I had inferred rather than read, and I reported
'A: 4 passed / B: 4 failed' off a contaminated sequence.

RULES FROM IT
- Never restore from a .bak you created after the change you are reverting. Use
 git checkout -- path (or a backup whose provenance is a committed revision).
- Print the changed lines and the file hash as the LAST output of every run;
 assert on them, do not remember them.
- Check exit status per step: with set -e a noisy pipeline returned 1, which
 aborted the script before its restore step, and I did not notice.
- When a test result contradicts a mechanism you can demonstrate, believe the
 mechanism and re-read the test. My probe proved the context rendered
 'Eliyahu: ' under the broken code while the test still passed; the test was
 wrong (a bare substring matched a forwarded '[out]' copy), not the probe.
