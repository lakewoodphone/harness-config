# The Q3 ST-50 figure is stable, re-measured — and it contains one trap worth naming

**Verified 2026-10-15T~16:0xZ against the live ledger** (`/root/accounting-data/live/accounting.db`,
`transactions` table, file mtime 2026-10-15 15:41 — so this is the current store, not a copy).

Row #465 hands the owner a figure he will file a tax return on: **gross receipts 25,671.84, tax
1,700.76**, computed on 2026-10-13. **A row's premise decays**, so I re-ran the same computation rather
than trusting a two-day-old number.

## The Stripe half reproduces EXACTLY

| month | row's figure | recomputed from the live ledger |
|---|---|---|
| Jul 2026 stripe-charges | 6,040.70 | **6,040.70** (66 rows) |
| Aug 2026 stripe-charges | 6,772.78 | **6,772.78** (65 rows) |
| Sep 2026 stripe-charges | 7,347.69 | **7,347.69** (61 rows) |
| refunds, all three months | 346.54 + 150.00 + 494.52 | **346.54 + 150.00 + 494.52** |

Sum 20,161.17 gross less 991.06 refunds — unchanged. Q3 ended 30 September, so only late-posted entries
could move it, and none have. **The figure is stable and safe to file from.**

## The trap: an owner loan booked as a Zelle credit

The ledger holds, in August, **`manual-owner-zelle-loan`, credit, 2,700.00** — the owner's own loan to
the business. Row #465's Zelle line is 1,915.00 + 2,170.00 + 159.00 = **4,244.00**, which correctly
excludes it.

**But a reconstruction that summed all Zelle credits for the quarter would add 2,700 to gross receipts
and overstate the tax by roughly 179.** The row is right; the method that produces it is one careless
query away from being wrong. Anyone re-deriving this must exclude `manual-owner-zelle-loan`, and the
same class applies to any owner-to-business transfer — a loan is not gross receipts.

## What I could NOT re-verify, stated as such

The **in-store sales (1,567.73) and cash deposits (690.00)** components are not separable from this
table by source_system alone — they sit inside `plaid-api` and `Generic Three Column CSV` aggregates
alongside expenses. So of the 25,671.84 total, **20,161.17 minus refunds is verified to the cent and the
remaining 6,501.73 rests on the original reconstruction.** That is the honest split, and it belongs
beside the figure rather than behind it.

## Why this matters more than another increment

The prompt's most common measured failure is `wrong-data`: acting on, or reporting, something that was
not true. A two-day-old tax figure handed to a man with a filing deadline is exactly that risk, and the
cost of being wrong is a wrong return to a state tax authority, not a corrected cell in a spreadsheet.
**Re-measuring it was worth more than anything else left on the list.**
