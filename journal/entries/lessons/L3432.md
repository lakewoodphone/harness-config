**L3432 · PowerShell cannot pipe a heredoc into ssh - base64 the script instead; and two accounting.db traps**

LESSON 1 — PowerShell cannot pipe a heredoc into ssh. Measured 2026-10-09 on ZABZ-YOGA.

`ssh host "bash -s" << 'EOF' ... EOF` is not even valid PowerShell (no heredoc operator, and
`<<` is a redirection parse error). The working substitute — a here-string piped to ssh —
ALSO fails, and fails in a way that looks like the remote rejecting the command: pwsh's native
stdin encoding appends CR to every line, so the terminator arrives as `EOF\r` and bash reports
`$'EOF\r': command not found`. Confirmed causally: the local script file contained 0 CR
characters, and the remote still saw `EOF\r`. `-replace "`r`n","`n"` before writing does NOT
help, because the CR is added by the pipe, after the file is written.

The fix that works, every time: base64 the script and decode it on the far side.

 $x = [Convert]::ToBase64String([IO.File]::ReadAllBytes($scriptPath))
 ssh host "printf '%s' '$x' | base64 -d > /tmp/x.sh && bash /tmp/x.sh"

Base64 has no characters bash or ssh can mangle, so multi-hop quoting stops being a hazard
entirely. For a large file (a document, not a script) use `scp` and then quote the destination
path — that is what was used for the 24 KB pack, and the remote sha256 matched the local one.

Corollary: `$env:TEMP` inside pwsh is NOT the same directory the harness `write` tool sees
(pwsh got C:\Users\ezabz\.dsh\tmp, the tool wrote to C:\Users\ezabz\AppData\Local\Temp).
Do not mix the two; keep script and document scratch files in one explicit absolute path.

LESSON 2 — In accounting.db, `direction` is the sign authority and `amount_cents` is NOT.
Credits carry negative amounts (-8,789 seen) and debits carry negative amounts (-250,000 seen);
the negatives are reversals and refunds that are meant to net inside their bucket. `sum(...)`
grouped by `direction` is therefore correct; `sum(abs(...))` silently overstates. Related trap:
a CASE-based classifier must test `coalesce(catname,'')`, because `catname NOT IN (...)` is
NULL — not TRUE — for an uncategorised row, which silently drops every uncategorised row from
the bucket. That cost a wrong monthly cost table in this session before it was caught by the
totals not tying to 105,311.75.

LESSON 3 — The duplicate rule that reproduces the owner's own figures is
`duplicate_of_transaction_id IS NULL`, not `ingestion_status='active'`. Both agree on eight of
nine categories, so a single agreeing category does not validate a rule; Cost of Goods Sold is
the discriminator (19,506.70 vs 20,798.79). Always find the row that distinguishes two
candidate rules before adopting one. And when a raw monthly figure is quoted without a
population filter, test the no-filter sum before assuming a disagreement — "May 2026 credits
59,778.85" was exactly the all-status total, duplicates included, and that one query turned an
apparent contradiction into the cleanest paragraph in the pack.
