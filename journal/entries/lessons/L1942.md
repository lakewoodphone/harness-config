# L1939 — model_tier1/2/3 are all set to a model that returns empty, and the fallback hid it

## The finding

`app/config.py` sets **`model_tier1`, `model_tier2` and `model_tier3` all to the same literal**
`deepseek-v4-flash`, and `.env` carries the same for `MODEL_TIER1/2/3` plus `FAMILY_CHAT_AI_MODEL`.

MEASURED from `model_usage` on the authority, 2026-09-17:

| window | calls | failed | error |
|---|---|---|---|
| 7 days | 890 | **655** | `empty_response` x655 |
| 24 hours | **0** | — | last run `2026-09-15T21:26:27Z` |

**74% failure rate, and the failure mode is `empty_response`** — not an exception, not a timeout. A model
that returns nothing looks to a caller like a model that had nothing to say. It stopped being called about
two days ago, but nothing in the suite reports "the configured default is broken", so the only reason it is
not still burning calls is that a fallback path is serving them instead.

## Why this is the exact failure the standing instruction exists for

The instruction (2026-09-15): *"ai models change very often, can never be hardcoded and get changed and
updated all the time so we need robust easy flows for that."* Its recorded justification: every live AI call
in `personality-system` failed for over a week because a **hardcoded model name stopped existing**, and the
deterministic fallback hid it — *"users saw plausible text and nobody knew."*

This is that same shape, one layer up: **three tiers, one literal, an empty-response failure mode, and a
fallback that makes the outage invisible.** The measured cost is low ($0.0999 over 7 days) because the broken
model is cheap and was quickly bypassed. The measured RISK is not: a tier pointing at a model that returns
nothing is a silent quality floor, and nothing alerts on it.

## What should happen (not done this round — recorded so it is not rediscovered)

1. **Resolve models at runtime from the gateway catalog**, per the standing rule, rather than three literals.
2. **Alert on the failure rate of a configured model.** `empty_response` at 74% over 890 calls is a signal
 that needs one alert, and there is currently no check that would have raised it.
3. **Never point tier1, tier2 and tier3 at the same model.** Three tiers exist to give three behaviours; one
 literal collapses them and removes the redundancy that would have surfaced this.

## Evidence

- `config.py`: `model_tier1/2/3: str = "deepseek-v4-flash"`; `.env`: `MODEL_TIER1/2/3=deepseek-v4-flash`,
 `FAMILY_CHAT_AI_MODEL=deepseek-v4-flash`.
- `model_usage`: 890 calls / 655 failures / `empty_response`; `MAX(created_at)` = `2026-09-15T21:26:27Z`.
- 11 distinct models served the `fast` tier in 7 days, which also means no name-based ceiling holds.
