**L10370 · Audit every knob for a real reader: three inert controls in one night, and a backup file that answered a grep**

## 2026-10-20T00:05Z · ZABZ-YOGA · audit every knob for a real reader, not for a mention

Two inert controls on two consecutive rounds stopped looking like bad luck. So every `SCHEDULE_*` and
`ROUTING_*` variable was audited against the code **production** runs, asking one question per knob: *is there a
call site that reads it, or only a function that nobody calls?*

### Found

- `SCHEDULE_CHEAP_SHARE_TARGET` - read by `cheap_share_target()`, which **nothing called**. The value existed
 to validate itself.
- `ROUTING_FALLBACK_CHAIN` - read by `fallback_chain()`, which **nothing called**.
- The setter was also a **third** inert knob in one night, after the exemption list and `ROUTING_QUALITY_FLOOR`.

### Wired

- `peak_verification` now reads the target and prints `MET` / `NOT MET` against the measured cheap share, so
 the policy target is a thing that can fail rather than a comment with a number in it.
- The equivalence yield orders same-weights alternatives by the declared chain, then by price. And it now
 promotes **exactly one** alternative: promoting several tied them at `direct + 0.001` and handed the
 tie-break back to list order, which would have made the chain decorative even after wiring it.

69 tests in the file.

### What the audit caught about me

The grep reported `SCHEDULE_CHEAP_SHARE_TARGET` as *read in 4 files*. **One of those four was
`schedule_policy.py.bak-<ts>`** - a backup from an earlier deploy, sitting inside `app/services/`.

Nothing imports a `.bak` file, but it is inside the source tree, so it answers a grep confidently and it
contains a stale copy of the very function under examination. **The audit nearly accepted a retired file as
evidence that a setting was live** - the same class of error as reading a frozen store and calling the estate
broken. Backups move to `/opt/company/backups/<ts>/` from now on, and greps exclude `*.bak*`.

### And a deploy deliberately not made

The router change needs a restart. Restarting production **45 minutes before the first peak observation** -
for a change that cannot take effect until a DeepInfra key exists - is churn with no upside and a real
downside: it risks the one window in which the scheduling behaviour can be seen for the first time. Committed,
tested, **deployed after 04:00Z.**
