**L1472 · A verifier that only runs under pwsh 7 cannot see Windows PowerShell 5.1 faults (four of them, measured)**

## What I did not know at the start

A fix that only ever runs under pwsh 7 cannot prove it is correct. Two faults in
`scripts/autosync.ps1` were invisible to a pwsh-only verification harness and
both fired the first time the script was run the way a human types it:

1. **Windows PowerShell 5.1 reads a BOM-less `.ps1` as ANSI.** Every em dash in
 the file (I had added several) made `powershell -NoProfile -File
 scripts\autosync.ps1` refuse to parse the script at all - 10 parse errors,
 exit 1, nothing ran. pwsh 7 defaults to UTF-8 and was happy. Keep `.ps1` pure
 ASCII, or add a BOM (commit 670261e chose the BOM for the rest of the tree;
 ASCII-only is the safer choice for the file a scheduler and a human both run).
2. **5.1 does not populate `$PSScriptRoot` while evaluating parameter defaults.**
 `[string]$Repo = (Split-Path -Parent $PSScriptRoot)` therefore died with
 "Split-Path: Cannot bind argument to parameter 'Path' because it is an empty
 string" under 5.1 only. Default it in the body from `$PSCommandPath`.

Two more shell traps of the same family, both measured today:

3. **5.1 converts a native command's stderr into a terminating error** when
 `$ErrorActionPreference = 'Stop'`. Any `git ... 2>&1` that emits a warning
 (CRLF advice) aborts the caller. Capture with `2>$null` or relax the
 preference around native calls.
4. **`tr -c 'A-Za-z0-9._-' '-'` turns the trailing newline of `$(hostname)` into
 a `-`.** `hostname | tr -c ...` yields `secratary-`. Strip it first
 (`tr -d '\n' | tr -c ...`). The shell's own `$( )` hides the bug because it
 removes the newline; a pipeline does not.

Evidence: `_scratch/verify-autosync.ps1` and `_scratch/verify-autosync.sh`, both
green under pwsh 7, powershell.exe 5.1 and Linux bash. Run a Windows script
verifier under BOTH interpreters - the difference is not theoretical, it is the
difference between "verified" and "never tested".
