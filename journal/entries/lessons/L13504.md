**L13504 · eBay accepts a wrong filter key and returns an unfiltered answer - a filter that filters nothing looks like a working one**

**eBay accepts a wrong filter key and returns an unfiltered answer — so a "filter" that filters nothing is indistinguishable from a working one.**

**Measured 2026-10-25, the first hour the eBay Browse API worked here.** The client sent
`filter=conditions:{2010}` (Excellent - Refurbished). eBay answered `200` with **2,671 matches** and
every returned item was condition `3000` (Used). The correct key is **`conditionIds`**:
`conditionIds:{2010}` returned **138** matches, all `2010`.

**Why this is the dangerous shape, not just a bug.** A wrong *value* fails loudly. A wrong *key* does
not: eBay dropped the unrecognised filter and answered the unfiltered query with a normal-looking
result set, a normal `total`, and correct item records. Nothing in the response says the filter was
ignored. My own selftest passed throughout — it asserted the string the client *built*, which was
exactly as wrong as the client.

**The consequence in this business, concretely.** `L2386` says grade and price are not monotonic and a
sourcing sweep must price eBay's refurbished ladder (2000/2010/2020/2030). With `conditions:`, a sweep
would have reported "2,671 refurbished laptops under 200" when the real refurbished population was
138 — a 19x overstatement on the exact tier the profit model depends on, delivered with a straight
face and a saved JSON file. It was caught only because the *condition column in the output* disagreed
with the filter I had asked for, and I read the rows instead of the total.

**The rule.** Assert on the vendor's behaviour, not on your own request. Concretely:

* after any filtered call, check that returned records satisfy the filter — `{returned conditionIds}
 ⊆ {requested}` — and fail when they do not;
* a `200` with a plausible `total` is not evidence the query was constrained; log what came back, not
 what you sent;
* treat "the total looks high" as a signal to inspect rows, not to trust the number;
* and when a filter is load-bearing for money, put the check in `doctor`, not in a comment — `doctor`
 now asks for 2010, asserts every `conditionId` is 2010, and exits **7** when the filter is ignored.

**Also worth keeping.** The first ladder read returned a `122.22` "Excellent - Refurbished" hit that
was a **motherboard**, not a laptop, because the query was a bare model name. Title relevance is a
second silent filter: a keyword that matches the model number will happily match its parts. Query
hygiene (exclude motherboard/board-only/for-parts terms) is part of the reading, not a nicety.
