**L4898 · A stdio MCP server holds the module it spawned with - a tool fix cannot be verified by calling the tool in the session that made it**

Measured 2026-10-15, in one session, minutes apart:

 direct invocation: /opt/company/.venv/bin/python3 -c "... import ps_mcp_server as m; print(m.ps_circuit_breakers())"
 -> valid JSON, no error, 20 recent events, and the action_level note
 the SAME session's MCP call to ps_circuit_breakers
 -> {"error": "no such column: action_name"} (the pre-fix behaviour)

Both are correct. An MCP server over stdio is spawned once per session/profile and holds the module it loaded at spawn; editing the file on disk does not reload it. So **a tool fix is verified by invoking the function in the interpreter the server runs under, and takes effect for a session only after the server respawns.** A session that fixed it and then called it would otherwise conclude its own fix had failed and "fix" it again -- which is the definition of repeated work.

WHY THIS IS WORTH WRITING DOWN: the natural verification of a tool fix ("call the tool") is the one verification that CANNOT work in the session that made the fix. Verify the function; state the respawn caveat; do not re-edit.

Also noted while verifying: the company's loop is ticking (session 78876 `active` at 15:25:24, 78875 `completed` at 15:20:30) and the deadlock post-check reads **1 session since the fix, 0 deadlocks, 0 `temporarily disabled`** -- one session is not a measurement, and it is recorded as such rather than as a pass.
