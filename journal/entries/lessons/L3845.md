**L3845 · lpt-write order create refuses every status but the create-time one, while its own plan line validates against the full live enum**

**Measured 2026-10-18 on WO26101812753 (Semah, Dell P137G), ZABZ-TECH.**

`lpt-write order create --status AWAITING_APPROVAL` was REFUSED:

```
REFUSED - nothing was written.
 the app's writer refused: Invalid order status: AWAITING_APPROVAL
```

...even though the same run's own plan line had just printed `status AWAITING_APPROVAL (validated against the live enum: 7 values)`, and `lpt-write vocab` lists `AWAITING_APPROVAL(8)` read live from `orders` via `select status::text, count(*) from orders group by 1`.

## Two validators, and the plan uses the wrong one

- `write_helper._live_order_statuses(cur)` reads the statuses **in use**. That is every one of the 7.
- `app.services.website_db.create_order` validates against its own **create-time** list, which is narrower and does not include AWAITING_APPROVAL.

So the helper decides the printed plan and the app decides the write, and they disagree. The plan's "(validated against the live enum)" therefore says nothing about whether a CREATE will succeed.

## The route that works

Create with no `--status` (defaults to AWAITING_DIAGNOSIS), then move it:

```
lpt-write order create --apply ... # -> AWAITING_DIAGNOSIS
lpt-write status set --apply --order WO... --status AWAITING_APPROVAL --reason "..."
```

This is also what the Zombeck order (WO26101812752) did an hour earlier, so it is the established route rather than a workaround invented here. It leaves an honest history: `None -> AWAITING_DIAGNOSIS` from creation, then `AWAITING_DIAGNOSIS -> AWAITING_APPROVAL` with the reason.

**Rule:** treat a create plan's status validation as advisory. Only `status set` validates against the live enum in a way the write path honours. Not fixed - it is a reader/writer disagreement inside `lpt-write` and it wants the app's create-time list read explicitly rather than a guess at it.
