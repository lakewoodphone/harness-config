**L3263 · A verification script that stamps production state is not a verification; unattributable state gets re-broken (Shabsi, 34 hours)**

**L3311 · A verification script that stamps production state is not a verification; and state nobody can attribute will be re-broken. Shabsi was out of the family chat for 34 hours because a docstring said "copy".**

WHAT HAPPENED. On 2026-09-30 16:04:50 UTC a session on `zabz-tech` wrote and ran a script to
demonstrate the family chat's new removal flow. Its own docstring promised:

> *"Start Shabsi's hour, then show — on a COPY of the database — exactly what he will get. The live
> database is only touched to stamp the removal; every reply text below is rendered from a copy…"*

and its body did the opposite of what that sentence implies:

```python
print("== live: stamp the removal ==")
print("mark_removed ->", hub.mark_removed(SHABSI))
db.set_setting(hub._mute_key(SHABSI, "at"), str(int(REMOVED_AT.timestamp())))
```

`REMOVED_AT` was 2026-09-30 15:50:40 UTC — so the removal stamp it planted had already expired by
the time the person next texted. It ran against the production database at
`/home/zabz/personal-secretary-mvp/data/family_chat.db`.

MEASURED COST. Shabsi, the owner's brother, was out of the family group text for **34 hours**. From
his seat: he texted, the chat told him he had been removed, he came back with `#start`, and later it
removed him again. The owner's report — *"he keeps getting removed no matter what"* — was exactly
right. The reason it could not be investigated is the second half: `fc_mute_by` and `fc_mute_at`
were set *alongside* `muted` but were *separate* from it, so `!list` printed only `MUTED`,
indistinguishable from his own `#mute` and pointing at nothing. There was no author and no readable
timestamp on the state, so the state could not be questioned.

WHAT IT COST TO FIND. A session had to search the whole shipped session archive and
`dsh_session_events` to identify which session had called `mark_removed()`, because nothing else
recorded it.

THE DURABLE RULES.

1. **A preview renders from a copy, and then asserts the live database is unchanged.** Reading a
 file copy is not the property; *not writing the live one* is. Any script that demonstrates live
 state must end by comparing the live store's relevant rows or mtime+sha against what it read
 first, and must fail loudly if they moved. A docstring is not a control.
2. **Production state changes carry an author and a timestamp, or they cannot be debugged.** This
 is now `member_events` (`phone, name, action, actor, reason, created_at`), written by
 `db.log_member_event()`, which never raises because a failed audit must not block the state
 change it describes. `mark_removed(phone, actor=…, reason=…)` and the admin CLI carry it
 through; anything not a human asking for a removal must pass its own name.
3. **Prefer a state that expires to a state that is set.** A removal is now a one-hour cooldown
 (`hub.expire_removals_due()`, released lazily on the inbound path and by the resilience loop),
 so a stray write self-heals and a silent member is still released. A latch that only a human can
 undo will be left latched.
4. **A self-mute is never swept and never timed out.** Nobody may trap themselves, and nobody
 else's timer may undo their own choice.

EVIDENCE. `personal-secretary-mvp/docs/family-chat/2026-10-02-removal-cooldown.md` (the full
incident, with the ledger rows 133225–133228); commit `107dd4a1` *family chat: a removal is a
cooldown, and every removal names its author*; `tests/test_family_chat.py`
`TestRemovalIsACooldownNotAState` (5 tests) and `TestMemberStateAudit` (4 tests). **This lesson
exists because that incident was never journalled** — for four days it lived only in the repo, and
the owner's question on 2026-10-05 was the first thing to pull it back out. See H3164.
