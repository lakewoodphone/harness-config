**L3797 · ps_db_query answering proves the DB is reachable, not that the company API is up - and the bridge host is proven by the DB path it reports**

Two questions that tool output conflates, and how to separate them in one call each:

**(1) Which host does the MCP bridge reach?** Proven by the database path it reports:
`ps_db_query` on `pragma_database_list` returns `{"file": "..."}` -- `/root/authority.db` means the
authority (`secratary-cloud`); `/home/zabz/personal-secretary-mvp/data/secretary.db` would mean the
FROZEN office box. This is cheaper and harder to get wrong than reading ssh aliases, because it is
read from the process that is actually serving the tool. MEASURED 2026-10-14: `/root/authority.db`.

**(2) Is that host's API serving?** Ask the host, never the tool:
`systemctl is-active company-api; curl -s -w '%{http_code}' http://127.0.0.1:8002/health; ss -ltn | grep 8002`.

WHY IT MATTERS -- MEASURED 2026-10-14, one instant, the authority:
- `systemctl is-active company-api` -> `deactivating`; `ss -ltn | grep 8002` -> nothing;
 `curl http://127.0.0.1:8002/health` -> `000`.
- `ps_db_query` **answered normally**. So the DB-routed tools keep working straight through an API
 outage, and "the ps_* tools respond" is **not** evidence that the company API is up.
- The API-routed ones all fail with `<urlopen error [Errno 111] Connection refused>`:
 `ps_action`, `ps_ceo_chat`, `ps_health`, and -- importantly -- **`ps_search`**, which routes
 `_api("POST", "/tools/run/search", ...)` (`ps_mcp_server.py:596`, call at `:630`). So during an
 API window there is no indexed estate search through the MCP at all, even though the `fast-search`
 skill names `ps_action("search", ...)` as the cross-OS entry point; fall back to
 `ssh secratary-cloud fa <mode> <query>` or to the local file tools.
- `Errno 111` is a Linux errno: it also tells you the *server* side is Linux, which is how the
 frozen-office-box hypothesis was excluded here.
