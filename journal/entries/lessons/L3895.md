**L3895 · A tool's error is often about your argument, not your data - and a reparse point is not an empty folder**

## Two failures, one shape: the tool said the data was wrong, and the data was fine

Measured 2026-10-20 on a BitLocker customer drive at the Linux bench (WO26101812753, Semah / Dell P137G).

**1. Three ways a correct 48-digit key was reported as a wrong one.** `dislocker 0.7.3` answers
*"None of the provided decryption mean is decrypting the keys. Abort."* for every one of these, and the
message names the key, not the command line:

- `-p 670252-…` — **`-p` takes an OPTIONAL argument**, so with a space the password arrives empty,
 dislocker tries to prompt, prints `Cannot open tty`, and dies. The value must be attached:
 `--recovery-password=…`.
- 48 contiguous digits, correctly attached, are **refused**. Only the **hyphenated 8-groups-of-6**
 form is accepted by this version.
- After `sudo dislocker`, a `test -e …/dislocker-file` run as the normal user reports the file
 missing: **a FUSE mount is visible only to the uid that mounted it**. The volume had been mounted
 the whole time; only the check was blind.

**Rule:** before concluding an input is wrong, enumerate the argument contract the tool actually has
(`--help`, and the shape its parser expects) and keep "refused" and "not visible to me" as separate
branches in your own code. A refusal that shares its message with a self-inflicted bug costs the
customer round-trips — here it would have sent the owner back to ask for a key the customer had
already supplied, and to tell him it was no good.

**2. A directory that prints `unsupported reparse tag 0x9000701a` is neither empty nor absent.** On a
Windows 11 volume whose known folders are redirected into OneDrive, `Users/<user>/OneDrive` is a
**cloud reparse point**. `ls` shows a dangling symlink, `du` silently omits everything behind it, and
**rsync copies nothing out of it while reporting success**. That profile measured 18 G, of which 15 G
was AppData; the folders a customer means by "my files" were invisible in that number — present on
the disk, behind the tag.

**Rule:** when a filesystem reports a placeholder it cannot resolve, read the filesystem's own index
instead of the mounted view — `ntfsls -f -R -l -p <path> <device-or-image>` reads NTFS indexes without
resolving the tag — and treat "the copy said it was fine" as unproven until a source count from an
independent reading equals the destination count. Two tools walking the same broken view are one tool.

**The general form of both:** `du` measures what the mount can see, not what the medium holds, and
an error message is a claim that has to be attributed before it is believed. Any number used to size
a job, quote a customer or buy media must name the view it came from and the command that produced it.
