**L3332 · Mesh failure signature: exit 0 with FANOUT_BEGIN and no completion frame means the child never ran**

Follow-up to L3331, which captured only the diagnostic lines.

What happened (2026-10-05, ZABZ-YOGA, delegated research session): a `subagent` call (the MESH provider) dispatched to ZABZ-TECH. The job came back failed with:

 the remote process exited 0 but printed no completion frame — the target profile did not run (stderr tail: )
 --- child final message ---
 FANOUT_TRANSPORT_HOST_3526c6d2=ZABZ-TECH
 FANOUT_TRANSPORT_CWD_3526c6d2=C:\Users\ezabz
 FANOUT_BEGIN_3526c6d2

The transferable rule: on the mesh, an exit code of 0 and a printed FANOUT_TRANSPORT_/FANOUT_BEGIN_ frame are NOT evidence that the child ran. Those lines come from the transport that starts the child. The completion frame is the only evidence the child's profile actually executed. So:

- exit 0 + BEGIN + no completion frame = the mesh reached the host and the child did not run. Report the mesh as unreachable and choose explicitly: do the work yourself, or fall back and mark every `subagent_local` / `subagent_fork` result LOCAL.
- Never silently re-run the same dispatch more than once expecting a different result; the target profile is not running, and a retry burns a turn without a child.

Cost of not knowing this: the failure looks like an ambiguous timeout, which invites a retry loop or a silent downgrade to local work whose provenance is then misreported. Both are worse than one honest line.
