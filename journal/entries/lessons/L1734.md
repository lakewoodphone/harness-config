**L1734 · SQLite memory is per-connection x per-thread; temp_store=MEMORY made a 10 GB burst that read like a leak - measure the shape first**

**L · 2026-09-16 · SQLite memory in this app is per-connection and per-thread, and `temp_store=MEMORY` turns one big sort into a 10 GB allocation. An OOM that looks like a leak is a burst — measure the shape before hunting a leak.**

What the measurements showed on `secretary-api` (2026-09-15, ~20 GB RSS → OOM, six kills in a day, the last two 15 minutes apart):

- **It was a burst, not a leak.** Sampling `/proc/<pid>/smaps` every 20 s while it happened: RSS 2.5 GB → 3.5 GB → **12.5 GB in 21 seconds**, with one anonymous mapping of **7.4 GB**, then the kill. A leak hunter following a slow-growth curve would have spent the night in the wrong place. The shape of the curve — flat, then a cliff — is the first thing to measure.
- **`PRAGMA cache_size=-64000` is 64 MB *per connection*, and this app opens one connection per live thread.** 60 DB file descriptors were open when sampled: a **3.8 GB floor** that exists whether the cache is used or not. Now `-8000` (8 MB), overridable by `PS_SQLITE_CACHE_KB`.
- **`PRAGMA temp_store=MEMORY` is the unbounded term.** It lets any `ORDER BY` / `GROUP BY` / `DISTINCT` / `UNION` materialise its whole intermediate result in RAM — on a database of 1.36M pages that is a multi-GB single allocation, which is exactly the 7.4 GB mapping. Now `FILE`, so sorts spill to `/tmp` (`PS_SQLITE_TEMP_STORE` to roll back).
- **The thread count is not bounded by the request rate either.** A `py-spy dump` caught **35 of 36 threads parked inside the same `/health` DB probe**, all blocked on the connection-cache lock, because `asyncio.wait_for(run_in_threadpool(_db_check), timeout=2.0)` **abandons the await but cannot cancel a thread already inside `run_in_threadpool`** — a slow DB does not shed probe load, it *adds* parked threads, and each new thread gets its own connection (and its own cache budget). Memoising that probe is the next lever (open item on P211).
- **`shutdown(wait=False)` does not cancel running futures.** `app/workforce.py:1417` builds a *fresh* `ThreadPoolExecutor` on every company tick, and a tick that exceeds its 150 s budget is "abandoned (continues in background)" — so abandoned ticks accumulate, each holding its own thread, connection and LLM conversation history, with nothing bounding how many. The kernel blamed a `wf-tick_0` thread for the first OOM of the day.
- Kills were `constraint=CONSTRAINT_NONE … global_oom`, i.e. the box's OOM killer, not a cgroup limit: the API was 84 % of all anonymous memory on the machine. A `MemoryMax=` would contain the blast radius.

Rules that follow for anything in this fleet that talks to SQLite from a thread pool: **know the per-connection budget and multiply by live threads**, **never leave `temp_store` at `MEMORY` on a database bigger than RAM**, and **bound the number of concurrent workers before blaming the queries**.
