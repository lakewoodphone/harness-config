**L2582 · ssh host bash -s piped from PowerShell sends CRLF, and the \r lands inside the last argument of each line**

**L2xxx · `ssh host "bash -s"` piped from PowerShell sends CRLF, and the trailing \r lands inside the last argument of every line.**

Measured 2026-09-25 (ZABZ-YOGA), cost one failed run.

WHAT HAPPENED. A multi-line script here-string piped as `$sh | ssh host "bash -s"` executed mostly correctly — `cd`, `git`, `grep`, `git diff` all behaved — and then failed on exactly one line:

```
.venv/bin/python /tmp/index-health-panel.py
→ .venv/bin/python: can't open file '/tmp/index-health-panel.py\r': [Errno 2] No such file or directory
```

The `\r` is **inside the final argument**, so it is not a harmless trailing character on the line: bash treats it as part of the path. The same pipe had already worked on shorter commands, which is what makes it a trap rather than an obvious failure.

WHY IT IS EASY TO MISS. The script is otherwise fine and the failure looks like a missing file, so the first instinct is to re-check the `scp` rather than the pipe. It is not the transfer; it is the pipe.

THREE FIXES, cheapest first:
1. **Run the remote program as a single-quoted single-line ssh command instead of through the pipe** — `ssh host 'cd ~/x && .venv/bin/python /tmp/y.py'`. No CRLF reaches the remote shell. This is what worked.
2. **`sed -i 's/\r$//' /tmp/script.py` before invoking it** (fixes a transferred *file*, not the *pipe*).
3. **Normalise the pipe**: `$sh -replace "\r\n", "`n" | ssh host "bash -s"`.

RULE. For anything longer than a couple of commands, or anything whose last argument is load-bearing, **prefer the single-quoted single-line form or `scp` the script and run it** — which is what the repo's own AGENTS.md already says ("multi-hop anything: write a script, SCP it, run it"). This failure is the single-hop version of the same lesson.
