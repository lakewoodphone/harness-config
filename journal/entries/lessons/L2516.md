**L2516 · A Dialpad holiday is two objects - creating only the recurringevent changes nothing**

## A Dialpad holiday is TWO objects, and creating only the first does nothing

Measured 2026-09-24 on ZABZ-TECH against the live LPT office (office 5695945642065920,
group `agxzfnViZXItdm9pY2VyEwsSBk9mZmljZRiAgJ-F642PCgw`), replaying the stored UI headers.

A closure day needs both:

1. **`POST /api/recurringevent`** — `{"target_key":"Office:5695945642065920","name":...,
 "recur_type":"no_repeat","start_on":"YYYY-MM-DD"}`. Returns the event with
 `observing_groups: []`.
2. **`POST /api/observedholiday/<group_key>/<recur_event_id>`** —
 `{"hours":["00:00","00:00"],"routing_options":{"closed":{...},"open":{...}}}`.

Only step 2 sets `observing_groups`, and only an observed holiday overrides main-line
routing. Step 1 alone leaves `observing_groups: []` and **the main line keeps ringing** —
a silent no-op that looks like success. Verified by counting
`GET /api/observedholiday/<group_key>?extended=1` before and after: 8 -> 8 after step 1,
8 -> 9 after step 2.

Endpoint shapes worth not rediscovering:

| purpose | call |
|---|---|
| read every closure | `GET /api/observedholiday/<group_key>?extended=1` — each row has `details.hours`, `details.routing_options`, `start_on`, `name` |
| read office holidays | `GET /api/recurringevent?target_key=Office%3A<office_id>` |
| create office holiday | `POST /api/recurringevent` (body above) |
| observe it (this is the one that closes the line) | `POST /api/observedholiday/<group_key>/<recur_event_id>` |
| un-observe | `DELETE /api/observedholiday/<group_key>/<recur_event_id>` |
| delete the holiday | `DELETE /api/recurringevent/<recur_event_key>` |

`hours: ["00:00","00:00"]` means **closed all day**, not open 24h — proof: the row's
`routing_options.closed` is what the engine selects, and every pre-existing LPT holiday uses
exactly that pair. A holiday whose date matches a built-in Dialpad catalogue entry gets a
catalogue *name* (creating one for 2026-09-25 produced a custom event **and** an unrelated
observed "Erev Sukkos"), so match on `start_on`, never on name.

Also: the UI's date-picker is a masked React input. Setting `.value` + `input` events changes
what you see but **not** what React submits — a `Create New Holiday` written that way posted
`start_on: 2026-09-24` (the default) while the box read `10/02/2026`. Never trust a form's
rendered value; read back what the API stored. The API path avoids this entirely.

RULE: when a vendor write spans two objects, prove which one carries the effect by reading the
state between the two calls. "It returned 200" is not "the phone system changed".
