**3. Why the allowlist is wider than it reads.** `_domain_matches` is suffix-based (`doh_filter.py:105-108`), so one entry `itunes.apple.com` allows `bag.`, `fpinit.`, `init.`, `mzstorekit.`, `amd-infra.` and every future subdomain. Same for `mzstatic.com`, `mesu.apple.com`, `gdmf.apple.com`. That is the surface the dictionary could ride on, and it is deliberate for managed app installs and MDM check-in.

**4. The device's identity is NOT established.** `fleet_devices` says DRN 2007 = serial `C7CD7NG7N72K` (the investigation doc transcribes it `C7CDNG7N72K`), enrollment `00008030-000E38E9227B802E`, last seen `2026-10-21 00:53:40`. `enrollments` has **0 rows** seen since 2026-10-22 and the Caddy log has **0** `/mdm` or `/checkin` requests in twelve hours, and `device_profiles` is **empty for the whole fleet**. So the server cannot say which public IP was 2007, nor which profiles it holds. Any claim that "the device uses our DoH" is an assumption, not a measurement.

**5. The estate owns a packet-level gate it has never used.** strongSwan is running on waze-mdm-01 (charon on 500/4500, uptime 29 days) with `conn waze-ios`: IKEv2, PSK, `leftsubnet=0.0.0.0/0`, pool `10.66.0.0/24`, `rightdns=87.99.141.172`. dnsmasq on that address resolves only the 63 domains in `/opt/waze-mdm/dns/waze-vpn.conf` and adds each answer to `ipset waze_vpn_allowed`; `iptables` chain `WAZE_VPN_EGRESS` accepts only established, TCP 80/443 and UDP 443 to that set plus DNS to the server, and then `-j REJECT --reject-with icmp-port-unreachable`. A device on that tunnel cannot reach an address our list did not produce — the one thing neither the DoH answer nor the PAC can guarantee. **Security associations ever established since 2026-08-01: 0. Currently up: 0.** The client half already exists in code: `app/services/nanomdm_service.py:1723` `make_always_on_vpn_payload` builds `com.apple.vpn.managed`, `VPNType=IKEv2`, `OnDemandEnabled=1`, `Action=Connect` (built for the VoIP call-block path, never deployed — no profile in `deploy/waze-mdm/profiles/` carries a VPN payload).

**6. Four live defects found while reading, each cheap and each capable of wasting another night.** (a) The served PAC still returns `DIRECT` for `updates.cdn-apple.com`, `updates-http.cdn-apple.com`, `appldnld.apple.com` in `DIRECT_DOMAINS` (lines 2-4), checked before the block list — the "eight names removed" edit did not touch them. (b) `doh_filter.py` checks allow before block, and three names are in both lists right now: `gsp1.apple.com`, `gsp10-ssl.apple.com`, `gsp53-ssl.apple.com` (live env, counted today). (c) The DNS payload sets `AllowFailover=true`, so any DoH failure silently returns the device to whatever resolver the carrier hands it. (d) `deploy/waze-mdm/scripts/generate-profiles.py:67` still passes `allow_definition_lookup=True` ("Phase 1: allow dictionary access").

**7. The method this points to.** A gate that the device evaluates is not a gate you can measure. The order that costs least and settles most: log `X-Forwarded-For` in `doh_filter.py` so a tap can be attributed to a device; set `AllowFailover=false` on the test device so a refusal cannot be bypassed by a second resolver; then put that one device on the existing IKEv2 tunnel with a tight ipset and a `LOG` rule in front of the `REJECT`, tap once, and read the destination IPs out of the kernel log. That answers "where does it go" for flows that ignore DNS and PAC alike, and it uses kit already built. The harm itself can be removed independently of all of it: `com.apple.configuration.keyboard.settings` with `AllowDefinitionLookup=false` (iOS 26.4+, supervised, default true) — delivery needs a DDM server (KMFDDM beside NanoMDM), not an entitlement. See `D9352`.

**What is still not known, and must not be asserted:** which host serves the dictionary; whether the device's DoH payload is in force at all; whether the "download" moves any bytes or merely re-enables a retained asset after a catalog check.
