**L1537 · handy-keys blocks registered hotkeys, so Command+H is fair game on macOS (from the crate docs)**

Command+H is safe to use as a global hotkey on macOS because Handy swallows it -- verified from the
library's own documentation, not inferred.

Handy registers shortcuts through `HotkeyManager::new_with_blocking()` from the `handy-keys` crate
(handy-computer/handy-keys, module handy_app_lib::shortcut::handy_keys). docs.rs for handy-keys 0.3.4
documents that constructor as: "Create a new HotkeyManager with blocking support ... Registered hotkeys
will be blocked from reaching other applications." The plain `new()` is the non-blocking variant. That is
the whole reason a shortcut that collides with a system shortcut (macOS Cmd+H = Hide) does not misbehave.

The binding string format, from src-tauri/src/settings.rs: lowercase modifier tokens joined with "+", where
macOS uses "command" / "option" / "ctrl" / "shift" / "fn"; e.g. "command+h", "option+space". Handy's own UI
recorder writes the side-specific form ("command_left+h"), and Handy's parser accepts both -- with
"command+h" the log shows it registered as Modifiers(CMD_LEFT | CMD_RIGHT), i.e. both Command keys.

EVIDENCE: docs.rs/handy-keys/latest (0.3.4, published 2026-08-07); Handy log 2026-09-15 18:43:41
"Registered handy-keys shortcut: transcribe -> Hotkey { modifiers: Modifiers(CMD_LEFT | CMD_RIGHT), key: Some(H) }".
