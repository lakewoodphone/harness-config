**L3139 · A mesh child writes to whichever node the broker picks, so unpushed work scatters across machines**

MEASURED 2026-09-30. Three children were dispatched to do file work on this machine. The broker placed subagent-126 on ZABZ-YOGA, the laptop, because this machine was at 85.2 percent commit - the transport line reads pressure HIGH route-remote, the LOCAL option was declined, and the child own report named ZABZ-YOGA. Consequence: it created profiles/mesh-browse/ on the LAPTOP filesystem, and this machine had no such directory (Test-Path returned False). Nothing was wrong with the work; the work was simply somewhere else, unpushed, on a machine that may be asleep tomorrow. Two rules follow. FIRST: when you fan out file work, state in the brief that the artefact must land in the shared repo and be pushed, because you cannot know which node will run it and an unpushed file on a laptop is indistinguishable from work not done. SECOND: verify an artefact by its PATH on the node that claims to have made it, then by ls-tree against the remote - never assume the child edited the tree in front of you. DONE HERE: the child created 4 files (cordis.patch.yml, cordis.yml, package.json, pnpm-workspace.yaml), I read package.json and cordis.patch.yml directly on the laptop to confirm the content, then had the laptop commit and push them so they belong to the repository rather than to a laptop, and confirmed with git ls-tree that all four are now in origin/agent/deployed-truth. STILL UNVERIFIED, stated rather than assumed: the composition claim of plus 5 rows over 87 was the child own dump-config output and I did not reproduce it; and a grep for the MCP row lines in the committed patch returned nothing, which is probably a formatting difference but I did not resolve it, so the row content is confirmed only by the child report.
