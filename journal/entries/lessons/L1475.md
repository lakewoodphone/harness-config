**L1475 · A namespaced action name puts the verb second, so a prefix rule read reconnaissance as work**

A namespaced action name puts the verb second, so a prefix rule reads reconnaissance as work

MEASURED on secratary 2026-09-14, from the action names real work sessions actually
executed in the previous 24 hours (count in parentheses): list_tasks(125),
system_health(63), ha_states(56), ha_status(34), repo_search(29), web_search(27),
close_task(25), task_hygiene(23), memory_search(22), gmail_list(21), gmail_search(20),
qb_search(19), repo_read_file(18), repo_list_dir(17), calendar_list(15),
ha_entity(15), github_list_prs(14), update_task(12), save_memory(10), qb_query(10),
qb_status(7), contact_lookup(4), contact_search(4).

The classifier tested for a read-only VERB PREFIX at the start of the name:
("list_", "get_", "read_", "search_", "show_", "view_", "check_", "find_", "query_").
In a namespaced name the verb is the second word, so thirteen of those -- every
gmail_*, qb_*, ha_*, calendar_list, contact_*, memory_search, github_list_prs -- were
classified as WORK. The consequence was not cosmetic: that signal feeds the
reconnaissance nudge, so a session doing nothing but exploring was told it was making
progress, and the same signal would have let exploration earn the new budget extension.

FIX: decide from EVERY token, with a mutating verb anywhere taking precedence --
update_task_status is work, qb_status is reading. Unknown names count as work, so the
nudge never suppresses a mutating tool it has not seen. 39 tests parameterised over the
real observed names, committed a23cb985.

THE TRANSFERABLE PART: classify by structure (every token), not by position (the
first one). A rule that reads the leading token is a rule about naming style, and it
silently mis-serves every name written in a different style. This is the third time
tonight that a text/positional shortcut failed where a structural check was available
(the docstring regex, the "import re" substring, and now the verb prefix).
