**L2859 · wake.py held its own daily cap twice with two different defaults: stats reported 12, claim enforced 4, and nothing ran while everything looked healthy**

MEASURED 2026-09-28, on the authority, while trying to make the autonomous system actually wake work.

THE BUG, in one line: `~/bin/wake.py` read its own daily release cap in TWO places with TWO
different hardcoded defaults, in the same file.

 wake.py:399 "max_per_day": _env_int("WAKE_MAX_PER_DAY", 12) <- what `stats` REPORTS
 wake.py:455 if released_today(conn) >= _env_int("WAKE_MAX_PER_DAY", 4):
 return "daily-cap" <- what `claim` ENFORCES

The morning's patch raised only the reported one. So `wake.py stats` printed
`"max_per_day": 12` while `wake.py claim` answered
`{"ok": true, "row": null, "blocked_by": "daily-cap"}` - and the dispatcher, whose own gate read
12 happily, got nothing from the store and exited 0 having released nothing.

THE COST OF IT: the system could not wake a single session, every reading said it was healthy, and
I spent ~40 minutes chasing the wrong layer. The evidence that finally located it was a direct
`wake.py claim --by probe --json`, not any log: the dispatcher wrote NOTHING on that path (neither
success nor refusal), `bash -x` showed it exiting at its lock line with rc=0, and only strace showed
it was a clean exit_group(10) from `wake.py claim` returning the "capped" JSON.

THE CLASS OF FAILURE, and the reason this is a lesson rather than a bug report: **a limit that is
declared in more than one place is not a limit, it is a coincidence.** The same number was found in
five places that evening - wake.py (twice), wake-dispatch.sh:82, checkout-health.py:811, and
DEFAULT_GLOBAL_MAX_PER_DAY in project-keepalive.py:133 - and the dispatcher's own comment admits the
failure mode in advance: "The looser value wins." Nobody had made the authority the authority.

RULES:
 1. One constant, read by every consumer. A file that needs a guard's number reads the guard's
 constant; it does not restate it.
 2. Any patch to a guard is exercised, not merely written: import the module and CALL the guard.
 (The same evening, a second patcher edited `_env_float("WAKE_MAX_USD_PER_DAY", 3.0)` to
 reference a new constant and silently failed to define it - caught only because that patch's
 own proof step imported the module and read the caps.)
 3. When a reading says "healthy" and the behaviour says "nothing happens", believe the behaviour
 and go one layer down until they agree. Ask the component directly (`claim`), do not read its
 report (`stats`).
 4. A component that exits 0 silently on a no-op is undiagnosable. wake-dispatch.sh needs to log
 which exit path it took and with what numbers; that is filed as ledger work.
