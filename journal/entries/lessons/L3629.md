## 2026-10-12 14:20 UTC · ZABZ-YOGA · MEASURED: the company API queues almost perfectly - 32 concurrent requests take 10.4 seconds each, and the queue is NOT the database lock

**Zero errors at every level.** Nothing failed, nothing refused. The server absorbed all of it and simply
made everyone wait.

**Two findings, and the second is the one that corrects my earlier explanation.**

1. **`/status` p50 grows almost exactly in proportion to concurrency**: 972 ms at 1, 2,468 at 4 (x2.5),
 4,080 at 8 (x4.2), 6,377 at 16 (x6.6), 10,379 at 32 (x10.7). That is the textbook signature of a
 **serial queue**: N callers are served one after another, so each waits approximately N x the cost of
 one call. Nothing here is parallel.
2. **`/health` queues too, and it does not touch the database.** It is 200x faster (4.8 ms against 972),
 but from concurrency 1 to 32 its p50 rises **13.8x** - the same shape. **So the queue is not primarily
 `_db_lock`.** It is the single Python process: one interpreter executing one thread's bytecode at a
 time, so every request queues behind every other regardless of what it does.

**What this means for the owner's question, corrected and final.**

- **Postgres cannot fix this.** The database engine is not holding the queue: `/health` never opens the
 database and queues identically. Moving to Postgres would be a large, risky migration that leaves the
 measured shape unchanged.
- **The database lock is a second-order term, not the cause.** My earlier statement that the 815-site
 `_db_lock` was the explanation was **too strong**; this measurement says the lock adds to a queue that
 already exists for every request. Same correction applies to the 2-second `BEGIN IMMEDIATE` probe: it
 waits because it is behind a process that is busy, not because SQLite is stuck.
- **The fix is parallelism, and the missing parallelism is the PROCESS, not the engine.** Viable in this
 order: (a) confirm the app is genuinely I/O-bound in its slow paths, so the GIL yields often, then raise
 worker processes - which is BLOCKED until the autonomous loop is moved out of the startup hook
 (`app/main.py:1013`, `AutopilotController` at `:546`, recorded as L3625 - N workers means N companies);
 (b) move the genuinely blocking, non-yielding work off the request path; (c) only then consider a second
 process or a database move.

**The number to quote, because it is the one that matters operationally:** *at 32 concurrent requests a
`/status` call takes **10.4 seconds**, and the server returns no error - it just makes the caller wait.*
That is what "the box is slow" feels like, and it is why an agent fleet hammering this API degrades
everything on it.
