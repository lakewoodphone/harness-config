**L1553 · CloudTrail plus queue depth is what turns 'rotate the leaked key' into a decidable plan**

MEASURED 2026-09-15. A secret found in a repo tells you nothing about whether deleting it breaks production. Three cheap read-only calls with the leaked credential answered it:
- cloudtrail.lookup_events(LookupAttributes=[{AttributeKey: AccessKeyId, AttributeValue: <id>}]) shows every management event the key ever drove inside the 90-day window. The leaked key showed 0 events other than my own probe; the sibling key 0. That is what made 'delete it' a low-risk call rather than a gamble.
- sqs.get_queue_attributes on each queue gave both message counts (0) and LastModifiedTimestamp, which dated the last real activity to 2025-07-20 / 2025-08-14 - a year of idleness in one call.
- s3.list_objects_v2 per bucket gave object counts, bytes and the newest object date, which is how 'nothing of value is at risk' became provable (the customer-backups bucket is empty).
- git grep across every repo for the key id proved which files reference it (exactly one), so the blast radius was enumerable.
DO THIS FIRST, every time a credential is found in a repo: usage evidence, then decide. Read-only, minutes, and it is the difference between a plan and a panic.
