**L2383 · Remote commands with text arguments must go through a script FILE - shell quoting through ssh failed three times in one session**

**Rule:** when a remote command carries a non-trivial text argument, write it to a script file, `scp` it, and run the file. Do not fight nested quoting. For a python CLI that accepts JSON, prefer `--from-json <file>` on the remote over piping stdin through `ssh`.

**Measured 2026-09-22, three failures in one short stretch against `secratary-ts`:**
1. `ssh host 'python3 ... resolve 137 --how "long text with punctuation"'` -> **silently did nothing and printed nothing**. Pending count unchanged; the failure was only visible by reading the row back. Cost two attempts.
2. `Get-Content -Raw f.json | ssh host "python3 ... add --from-json -"` -> **hung and timed out at 240s**. `scp` of the same JSON then `--from-json /tmp/f.json` worked immediately and the row landed.
3. `ssh host "echo EXIT=\$?"` -> printed `EXIT=True`, because **PowerShell expanded `$?` locally before ssh ever ran**. The diagnostic itself was therefore a lie about the remote exit status.

**Also measured:** the owner-queue SQLite DB returns `sqlite3.OperationalError: database is locked` intermittently; it cleared on its own and a later identical call succeeded. A lock is transient - retry once, but **verify by reading the row back, never by the exit code**, because failure (1) above exited 0 in spirit and changed nothing.

**The generalisation:** an exit status you captured through another shell is not evidence about the remote command; and a command that prints nothing is not evidence that it worked. Read the state back.
