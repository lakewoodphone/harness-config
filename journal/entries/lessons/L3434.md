**L3434 · A required status check must never be path-filtered - the filter goes INSIDE the job**

A branch-protection required status check must produce a check run on **every** pull request. Anything that can stop the workflow from running, or stop the job executing, means the required context never appears — and a required context that never appears can never be satisfied. `strict=true` does not help; it only makes the block permanent.

**A `paths:` filter on `pull_request:` is the trap.** It does not skip a job, it stops the *workflow*, so no check run is created at all. `gh pr checks <n>` simply does not list it.

Measured 2026-10-09, repo `lakewoodphone/phone-and-tech-full`, branch `test` requiring 3 contexts with `strict=true` + `enforce_admins=true`:

- `Build image and assert the sha label` comes from `validate-backend-image.yml`, which carried a `paths:` filter on `pull_request:`.
- PR #142, 15 changed files (backend lib/migrations/tests, docs, frontend), none matching the filter: `CI Validation (PR Pre-Check)` reported (fail), `Check for Phantom Dependencies` reported (pass), `Build image and assert the sha label` produced **no check run**. Frontend-only and docs-only PRs were permanently unmergeable.
- Reproduced live on PR #343, a docs-only PR with one changed file, against unfixed `test`: same pattern, the context absent.

**The correct shape — the filter inside the job:**

1. `on.pull_request:` carries no `paths:` / `paths-ignore:`.
2. The job that carries the required `name:` has no falsifiable `if:` (only `always()`).
3. A first step computes relevance from `git diff --name-only "$base...$head"` and writes `relevant=true|false` to `$GITHUB_OUTPUT`; it must never fail, and every unmeasurable case (unreachable base sha, non-PR event, git error) resolves to `true`.
4. Expensive steps carry `if: steps.relevance.outputs.relevant == 'true'`. Cheap non-Docker steps stay unconditional, so a frontend-only PR still gets real signal rather than a rubber stamp.
5. Use a **three-dot** diff. With `strict=true` the base branch moves under the PR, and a two-dot diff then attributes base-only changes to the PR.

Verified: relevance logic extracted from the YAML and executed under `bash` against real git diffs — frontend-only → `false`; deploy-script change → `true`; base advanced with a Dockerfile change → `false` (three-dot, correct); unreachable base sha → `true`; non-PR event → `true`. All exits 0.

Same class, other two required checks: job-level `if: ... draft == false` (`phantom-dependency-check.yml`) likewise leaves a draft PR with no check run — gate the steps, not the job. And `types:` excluding `reopened` means a reopened PR can never obtain a new check run; both `pr-precheck.yml` and `phantom-dependency-check.yml` were missing it.

Repo: `docs/development/required-checks-must-always-report.md` (added in PR #342) is the durable write-up and audit checklist.
