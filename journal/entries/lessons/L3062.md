**L3062 · A mesh child has no durable identity, so it cannot be seen or steered: reproduced live with four running children**

**L-new · A mesh child has no durable identity, so it cannot be seen or steered: reproduced live with four running children**

MEASURED 2026-09-29 on ZABZ-YOGA, at the start of the mesh-fan-out audit.

Four children were dispatched through the `subagent` tool (the mesh provider, `remote-ssh`). While all
four were RUNNING, two readings were taken:

```
list_agents (scope children) -> "(no subagents)"
job_list -> 4 rows, kind subagent, status running
```

So the four children were real and alive — the broker had placed them, they held leases, they were
consuming node slots — and the engine's own child catalogue reported nothing. This is pain **P269** and
`docs/mesh/110-subagent-visibility.md` reproduced: `dsh-subagent` only catalogues a child when the
provider returns a `localAgent`, and our remote provider returns `localAgent: undefined`
(`provider.js:639`) and declares no `prepareContinuable`.

**What follows from it, and this is the part the owner feels.** Because there is no durable child id:

- `list_agents` cannot list a mesh child;
- `send_message` has no address to steer it, so a child mid-flight can never be corrected, re-scoped or
 given a fact it turns out to need;
- `interrupt_agent` cannot stop one, so a runaway child is bounded only by the 1800 s provider timeout;
- a child has no channel to ask the parent anything mid-flight, so a brief has to be perfect or the
 child guesses;
- the Subagents surface in the UI is legitimately empty and looks broken while work is running.

**The engine's own model, read from source.** `dsh-subagent`'s continuable path requires a durable
Session that THIS engine owns plus at most one process-local execution
(`@deepseek-ai/dsh-subagent/lib/index.js:1555`, and `startContinuable` at `:1643` calls
`host.prepareContinuable(provider, …)` at `:1669`). A remote child satisfies neither half: it has no
local Session and its execution belongs to another machine's process. So the absence is not an
oversight in our provider — it is the seam honestly reporting that this provider cannot fulfil the
continuable contract as written.

**What that means for the fix.** Restoring two-way mid-flight talk needs one of two things: a provider
that owns a durable local Session and mirrors a remote execution into it (a relay, which is a real
build), or a durable child record with an inbox and an outbox that the parent can address with its own
tools. The second is available without an engine change and without a restart, and it restores the
capability the owner asked for: a child can be messaged, stopped, and read mid-flight, and it can write
back to a store the parent reads.
