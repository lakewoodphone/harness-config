**L3061 · A bashism in the POSIX child script made every mesh child placed on a Linux node fail and be thrown away**

**L-new · A bashism in the POSIX child script made every mesh child placed on a Linux node fail and be thrown away**

MEASURED 2026-09-29 on ZABZ-YOGA, verified with a raw diagnostic on both Linux nodes.

`packages/plugin-remote-fanout/lib/remote-script.js:252` builds the POSIX transport script and captures
the target's hostname with:

```sh
printf -v fanout_host '%s' "$(hostname)"
```

**`printf -v` is a bashism. It does not exist in `dash`**, and `dash` is `/bin/sh` on both Linux nodes in
this mesh. The transport delivers the POSIX program as `ssh <node> sh -s` with the script on stdin
(`ssh-transport.js:64`, `remoteArgv`), so it runs under `dash`, where the line fails:

```
$ readlink -f /bin/sh
/usr/bin/dash
$ printf -v x '%s' abc; echo PRINTF_V_GOT=[$x]
sh: 1: printf: Illegal option -v
PRINTF_V_GOT=[]
```

`fanout_host` therefore stays EMPTY, so the host frame is written as
`FANOUT_TRANSPORT_HOST_<nonce>=` with nothing after the `=`, `parseFanout` records `host: ""`, and
`provider.js:574` refuses the whole run:

> the transport reported host "", which is not one of the hostnames the placement named
> ("secratary" may be secratary) — refusing to report work from a node the broker did not name

**This was reproduced live on 2026-09-29 at the start of this session**, verbatim, on a mesh child the
broker had placed on `secratary`. It is the measured content of pain **P2554**, whose date says the
provider "fails deterministically" — this is the mechanism, and it was not identified then. The prior
note in P2554 blamed the missing `dsh` on secratary; that is a separate, real defect, but it is not this
one, and the empty-host string is what the refusal actually quotes.

**The cost.** Every mesh child placed on `zabz-tech-linux` or `secratary` is refused and DISCARDED, even
when the child ran perfectly and produced a correct answer. The refusal happens after the work is done,
at the location check, so the compute is spent and the result dropped. It also silently removes two of
the five nodes from the fleet in a way that looks like a mesh outage and is not one.

**The fix, one line.** POSIX-correct, no bashism, with a fallback for a `hostname` that is not on the
non-interactive PATH:

```sh
fanout_host=$(hostname 2>/dev/null || uname -n)
```

Verified working under dash on both nodes: `HOSTNAME_GOT=[zabz-tech-linux]` and `HOSTNAME_GOT=[secratary]`.

**The durable rule.** A generated program must be written in the dialect its SHELL is, not the dialect
the author's shell is. `sh -s` means POSIX `sh`, which on Debian and Ubuntu is `dash`, not bash. The
generated script is a second dialect surface that no test on Windows exercises, and its failure is
silent: the shell prints a diagnostic to stderr that nobody reads, the frame still closes, and the run
is reported as a location failure rather than as a script failure.
