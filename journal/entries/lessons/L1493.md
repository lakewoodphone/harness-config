**L1493 · The lpt-sync write-back owns references.websiteOrder; references.productionOrder is not ours**

2026-09-15. lpt-sync-to-production.py's idempotency write-back used to overwrite
references.productionOrder and workflow.orderNumber IN PLACE. On
2026-09-03-hp-15-fd0095wm-shimmy-weichbrud.json those two fields held the eBay
SUPPLIER PO for the screen:

 references.productionOrder = {system: "ebay", orderNumber: "09-15137-18879", orderId: null, linkedAt: "2026-09-07"}
 workflow.orderNumber = "09-15137-18879"

The 2026-09-15 live push replaced BOTH with WO26091512711 / orderId 2876 and
destroyed the supplier link. (Oddly references.orderNumber at the top level still
holds "09-15137-18879" -- that is the surviving copy, and it is why the field
cannot be treated as a production-order slot either.)

THE INVARIANT, now encoded in the tool and its tests:
 * the tool writes its website order to references.websiteOrder ONLY -- a key it
 owns;
 * references.productionOrder is written only where it is ABSENT (a fresh
 record), never where it holds something;
 * each of workflow.orderId / workflow.orderNumber is decided on its own: filled
 when absent/empty/equal, left intact otherwise (with a loud log line);
 * the guard (_iter_production_order_refs) reads references.websiteOrder so a
 re-run still sees the link, and _known_production_order_id prefers it.

GENERAL RULE: a field that other systems also write is not yours to overwrite.
Add your own key. "Idempotency" justifies a write-back that ADDS a link; it never
justifies replacing a link you did not create.

STILL OUTSTANDING, and it is data, not code: weichbrud's record on disk in the
lpt-hub corpus still has references.productionOrder replaced by the website
order. The pre-push state is recoverable from lpt-hub git 75e78012^ . Repairing
that record file was outside the mandate of the session that found it.
