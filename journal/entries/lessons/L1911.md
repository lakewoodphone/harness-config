**L1911 · Windows file-lock primitives: four measured gotchas (os.open vs io.open sharing, denial-mode locks, text mode, replace-vs-reader)**

Building a cross-process lock in tools/customer/lock.py (lpt-hub, worktree w4-lock) hit four Windows behaviours that cost most of the session. All four are measured on ZABZ-YOGA, not inferred.

1. os.open and io.open have OPPOSITE sharing defaults. os.open requests
 FILE_SHARE_READ|WRITE|DELETE; io.open / builtins.open narrow sharing to
 read-only. Consequence: while one process holds a file open for writing via
 io.open, another process cannot open it AT ALL. Contention surfaces as
 PermissionError, not as a clean "busy"; and a dead holder's lock file cannot
 be read, so stale reclaim becomes impossible. For anything another process
 must inspect while you hold it, use raw os.open and do NOT wrap it in a
 FileIO object.

2. msvcrt.locking is a DENIAL-MODE lock: it blocks READS of the locked byte
 range from other processes, not just writes. Verified: reading byte 0 from
 a second descriptor gives EACCES [Errno 13]; reading byte 64 does not.
 So do not hold the lock over the metadata you want strangers to read --
 put the holder line in a different file (or a different offset).

3. os.open defaults to TEXT mode on Windows: os.O_RDWR == os.O_RDWR|os.O_TEXT
 is False, and writes translate \n to \r\n. Pass O_BINARY for byte-exact
 content. (io.open/mkstemp are already binary, so write_atomic was fine and
 only the raw-fd sidecar was corrupted -- a nasty asymmetry to debug.)

4. os.open with O_EXCL on an EXISTING file that another process holds open
 raises PermissionError on Windows, not EEXIST. Code that treats EEXIST as
 "someone else created it, carry on" breaks. Use O_CREAT without O_EXCL and
 let the OS lock decide ownership.

Also: os.replace onto a target that a reader holds open can fail with
WinError 5. Retrying works against a scanner, but a reader polling in a tight
loop with io.open holds the rename off indefinitely -- no finite retry budget
beats it. That is a property of the READER; test readers should use raw
os.open (full sharing). Documented in the module and the test.

Design conclusion worth keeping: the lock file is NEVER deleted. Deleting it
lets a third process create a new file at the same name while an existing
holder still holds the old inode -- two processes then hold "the lock"
simultaneously. Keep the lock file permanent (1 byte, empty) and keep the
holder pid/timestamp in a separate stamp file that IS removed on release.
