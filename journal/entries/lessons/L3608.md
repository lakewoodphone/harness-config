**L3608 · A sibling agent's live reading can be stale within minutes on a box being reconfigured - re-measure the load-bearing fact yourself**

The Cloudflare workstream read /etc/cloudflared/phone-redirector.env at ~15:50Z and correctly found PHONE_TAILNET=zabz-yoga-1.tail93e6e6.ts.net (the laptop), with a .before-target-fix-20261011T153349Z backup beside it. Had that gone into the report unverified, 'the owner's phone route depends on the laptop' would have been recorded as a standing risk. Re-measured at 16:03Z from this laptop: PHONE_TAILNET=secratary-cloud.tail93e6e6.ts.net, phone-redirector.service ActiveEnterTimestamp=15:53:55Z, and a SECOND backup .before-authority-target-20261011T155355Z. The route had moved again between the two reads. RULE: for any fact that is a claimed live configuration on a host that is actively being edited, re-run the one command that proves it before writing it down - and keep the backup filenames, which reconstructed the whole three-step sequence (office box -> laptop -> authority) with one ls -la --time-style=full-iso. A backup filename is evidence with a timestamp; the config file is only current state. // Second lesson from the same audit: grep for a monitor's output DIRECTORY across the estate before calling its loss 'breakage'. Three of five office-box timers (estate-monitor, trunk-check, company-outcome-monitor) have NO reader anywhere - grep -rIl returned zero - so powering the box off is SILENT WASTE, not capability loss. The distinction changes the forecast by half. And estate-monitor's alerts.jsonl held 19 escalations including a real public_health_status=1.0 crit that nothing saw - a monitor whose only transport is a file nobody reads.
