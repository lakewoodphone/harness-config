**L3497 · An orphan cache label is not proof of deletion, and verify an extraction against the container's own arithmetic (correction to L3495)**

Owner asked "are you absolutely sure? is everything you found on the phone fully there and not just
something you found". Ran verification (tools/phone-scan/verify_cache_extraction.py). Two things to carry
forward, both about how the technique must be stated:

1. **An orphan label is NOT proof of deletion.** 8 of the 121 orphan frames match a SURVIVING photo at
 0.90-0.99 - what a rename/re-index (MediaStore assigns a new _id, the old id dies) or a near-identical
 burst frame looks like. So "121 ids with no surviving row" must never be reported as "121 deleted
 files". L3495 as written could mislead exactly that way; this is the correction. The VIDEO cases are
 unaffected because they were tested against content: none of the six matches any surviving file.

2. **Verify an extraction against the container's own arithmetic, not against your own re-count.** What
 made this airtight was not that 1,259 labels looked plausible, but that (a) the index header's
 activeEntries and activeBytes matched the data file to the byte, (b) all three of region-0's non-free
 slot count, the label count and the carved count were 1259, and (c) the cache's own Adler-32 validated
 every blob's (label + JPEG) payload. A count that agrees with itself proves nothing; a count that
 agrees with a structure written by DIFFERENT code proves something.

Also: the 8-byte BlobCache header key is NOT crc64/Jones of the label (0/1259, CRC self-tested against the
published check value). Recorded so a future session does not assume the key is solved - the label lives
inside the checksummed payload and the offset/length/checksum fields all validate, so the key is not needed.
