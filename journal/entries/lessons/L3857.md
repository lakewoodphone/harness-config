**L3857 · CORRECTION to L3856: the Continue click is what granted WriteDAC - and 'it opens here' is never proof it opens on the customer's PC, because a local SID does not travel**

CORRECTION to L3856, one turn after writing it. L3856 got the mechanism wrong, and the owner caught it with one sentence: "it obviously works from this computer because I already gave it the whole continue with permission thing."

WHAT L3856 CLAIMED. "Write-DAC is a per-object right, not a property of the token. A filtered, medium-integrity, non-elevated administrator token can still hold WRITE_DAC on an object whose own DACL grants it, and **a Windows profile folder is exactly such an object**."

WHY THAT IS WRONG HERE. The profile's DACL did not grant this account anything before the owner acted. The measured sequence:

1. `Get-ChildItem E:\Users\User` -> "Access to the path is denied"; `Get-Acl E:\Users\User` -> "Attempted to perform an unauthorized operation". The DACL named only SYSTEM, BUILTIN\Administrators, the ORIGINAL machine's account SID, and an app-container SID. Nothing for `zabz-tech\ezabz`.
2. The owner clicked Continue in Explorer on "you don't currently have permission to access this folder". Windows then wrote `zabz-tech\ezabz: FullControl` into that folder's DACL. That entry is visible in the ACL afterwards, and it is the only explanation for it - nothing else in this session wrote it.
3. My `icacls E:\Users\User /grant *S-1-5-32-545:(OI)(CI)(RX)` then returned exit 0 **because** that DoDAC granted Write-DAC. Without step 2 it would have been exit 5, exactly like the same command on the parent `E:\Users`, which is still refused.

So the "filtered admin token held WRITE_DAC anyway" story is unsupported. It succeeded because a human granted it interactively first. L3856's bullet "attempt the operation rather than infer a blocker from whoami" remains true and is still worth keeping: attempting the operation is how the truth came out. What must be struck is the claim that the object already granted the right.

THE LESSON THAT ACTUALLY MATTERS, AND IT IS THE ONE THE OWNER WAS ASKING ABOUT. **"It opens on this PC" is not evidence that it opens on another, because the ACE that makes it open here may be a machine-local SID that does not exist anywhere else.** On this profile the entries were:

| ACE | travels to another Windows PC? |
|---|---|
| `BUILTIN\Administrators` FullControl | yes, if the account is an administrator |
| `BUILTIN\Users` ReadAndExecute | **yes, for ANY account - this is the one to add** |
| `NT AUTHORITY\SYSTEM` | irrelevant to a user sitting at the machine |
| `zabz-tech\ezabz` FullControl | **no** - a local account on THIS PC only; this is what the Continue click created |
| `S-1-5-21-3841120224-...-1001` FullControl | **no** - the old machine's account SID |
| `S-1-15-3-65536-...` Traverse | no - app-container capability |

The practical rule, and it should be the first check after any permission change on customer media: **list the DACL and classify every ACE as a well-known SID (`BUILTIN\*`, `NT AUTHORITY\*`, `Everyone`, `S-1-5-32-*`, `S-1-1-0`) or as a machine/account-specific SID, and then say out loud which of them is doing the work.** An interactive "Continue" click silently adds a specific SID, so it fixes the machine in front of you and proves nothing about the customer's. Only a well-known SID - `BUILTIN\Users` here - makes the fix portable. And check the far side for DENY entries too, because a Deny for Users or Everyone would override the Allow and the drive would open here and refuse there.

The generalisable form: a permission fix is not verified by demonstrating access on the machine where it was applied. It is verified by showing that the granting ACE is one the destination machine will also understand.
