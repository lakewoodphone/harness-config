**L2127 · L2131 - instant lock failures and long lock waits look identical in the log and need opposite fixes; time the acquisition to tell them apart**

Same message, two unrelated causes, opposite remedies. Measured 2026-09-20 on secratary.

**Cause A - snapshot conflict.** A connection reads, then writes on the same connection. In WAL mode the
write must upgrade the read transaction, and if another writer committed in between, SQLite refuses
with `SQLITE_BUSY_SNAPSHOT`. The busy handler does **not** cover it, so a 10 s or 30 s
`busy_timeout` buys exactly nothing. **Fails instantly.** Fix: `BEGIN IMMEDIATE` before the first
read - remove the upgrade.

**Cause B - genuine lock wait.** Another connection holds the write lock for longer than the timeout.
The busy handler retries the whole time and then gives up. **Fails after the full timeout.** Fix:
shorten or serialize the heavy writer. A larger timeout makes it worse, not better.

**They produce the same log line.** The only reliable way to tell them apart is to TIME the failing
acquisition:

 t0 = time.monotonic()
 try:
 conn.execute("BEGIN IMMEDIATE")
 ...
 except sqlite3.OperationalError as e:
 print(f"failed after {time.monotonic() - t0:.3f}s")

Under a second means Cause A. Equal to the timeout means Cause B. Measured on this host:
`BEGIN IMMEDIATE` on an ingest connection **failed in 10.022 s** against a 10 s busy_timeout - so
Cause B, and my `BEGIN IMMEDIATE` patch was irrelevant to it. I had diagnosed Cause A from the code
shape ("it reads then writes, so it must be a snapshot upgrade") and the code shape was consistent
with both. **The measurement, not the shape, decided it.**

What was actually holding the lock: `scripts/dialpad-recording-gap.py --limit 300` and
`/tmp/dialpad-sms-harvest-*.py` running concurrently with the API - long batch writers on the same
9.9 GB database. That is a capacity and scheduling problem.

**The generalisable rule.** When a fix based on a plausible mechanism does not work, the mechanism was
wrong, and the next step is a measurement that DISCRIMINATES between the remaining candidates - not a
bigger hammer. I reached for `busy_timeout` once (no effect), then `BEGIN IMMEDIATE` (no effect), and
only then timed it. The timer should have been the first instrument, not the third.
