**L · A mesh subagent shows nothing and blocks the turn, because backgrounding was off — that is the whole of "it just sits there"**

The owner, watching a `subagent` call on 2026-09-18: *"as you can see it's sitting on your subagent tool. it is
supposed to take a second to call and then i see it here on the top left, what is happening now?"* He is right,
and the cause is a configuration value, not a bug in the mesh.

WHAT HAPPENS WITH `enableRunInBackground: false` (`presets/zabz/agent.cordis.yml`, the `tool-subagent` and
`tool-subagent-remote` rows, until today):

1. A mesh child is a real agent turn **on another machine**. It creates no local process and no local
 session, so there is nothing in the local agent list to move — the UI has nothing to show, ever.
2. The parent's tool call is FOREGROUND, so it blocks for the child's entire turn. The composer sits on
 "subagent" and the only way to tell working from hung is the clock.
3. Because it blocks, the parent turn is hostage to the child. That is why a five-child fan-out held the
 parent open for the full remote-turn timeout and then died with it (L1997), and why the owner's
 experience of a fleet was always a long silence followed by a report.

PROOF IT IS NOT THE TRANSPORT: a trivial `subagent` probe returned `MESH-HOST: zabz-tech`, `transport host =
ZABZ-TECH`, `exit = 0 in 5787 ms`. Five seconds for a trivial task is exactly the "second" the owner
expects. The blocking is only visible when the task is long, which is precisely when a fan-out is needed.

FIX: `enableRunInBackground: true` on both mesh rows, synced to `~/.dsh/.agent-presets/zabz/agent.cordis.yml`
(verified present at lines 367, 377). With it on, `subagent(..., run_in_background: true)` returns a durable
child id immediately and the child appears in the job list the owner is looking at. The local fallback row
stays `backgroundMode: one-shot` and stays quiet, for the reason its own comment gives.

MEASURED ON MYSELF, THE SAME HOUR, AND WORTH ADMITTING: I then made this exact mistake by hand. I gave a
child a four-minute measurement brief as a FOREGROUND `subagent` call, and it ended as
`subagent run was cancelled` after 115,611 ms having reported only that it had started
(`FANOUT_BEGIN_75e0e87a`) — while the owner watched the composer do nothing. A brief's length and the
call's modality have to be chosen together: anything that can outlive a minute goes to the background, and
that is true of a subagent exactly as it is of a shell command.

THE GENERAL RULE: when a tool's work happens somewhere the UI cannot see, the tool MUST be able to return
a handle. A tool that can only answer synchronously makes every long task look like a freeze, and the
person watching has no way to tell the difference — which is the failure this whole session was called to fix.
