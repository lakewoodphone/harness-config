**L2055 · On CAN, 'I am only reading' is false by default — a filtered node still ACKs, so silence is a firmware choice**

**L · "I'm only reading, so I'm passive" is FALSE on CAN — a node with ID filters still transmits ACK
bits. On an OBD-II device that difference is the entire engineering, because the manufacturer blames the
transmission.**

Measured 2026-09-18 while designing a no-subscription vehicle logger for the owner's 2022 Hyundai Elantra
(VIN `5NPLP4AGXNH073821`). The finding that changed the design:

**Hyundai TSB 24-GI-011H (July 2024), "AFTERMARKET DONGLE INSTALLED AT DATA LINK CONNECTOR (DLC)"** is
scoped to *"all vehicles equipped with a Data Link Connector"* — i.e. this car. It attributes to
aftermarket DLC dongles: 12 V battery drain when parked several days, loss of CAN communication, CAN
errors causing temporary/historical DTCs, Bluelink/OTA failures, and false codes. It states that damage
attributed to an aftermarket DLC device is not warranty-covered. GM's equivalent bulletin names the
mechanism: **the device keeps the bus awake, so the car drains itself.**

The engineering fact that makes this solvable rather than fatal:

- **ESP32 TWAI in `LISTEN_ONLY` mode transmits no dominant bits at all — no data frames, no ACK bits, no
 error frames** (Espressif TWAI docs, read directly). It is electrically invisible.
- **Espressif also documents that an ordinary CAN node with ID filters STILL SENDS ACKs for frames it
 filtered out.** So passive-by-intent is not passive by default; **silence is a firmware choice.**
- **Every commercial OBD dongle (WiCAN, Freematics, ELM327) polls by design.** It does the thing the
 bulletin blames. That, not price, is the real reason to build custom here.

Two more generalisable points from the same session:

1. **A parts problem can be the top risk even when the protocol work is done.** The odometer, the hard
 protocol question, was *broadcast* on CAN ID `0x5B0` (`CLU12`, `CF_Clu_Odometer`, bytes 0-2
 little-endian, 0.1 km — identical in three commaai/opendbc DBC files). The actual project risk was
 **standby current**: a naive ESP32 dev board in "deep sleep" burns 1.5-15 mA because the USB-UART
 bridge and LDO keep running, and 15 mA depletes a 60 Ah battery in ~2 weeks. A bare module with a
 low-quiescent buck and a load-switched transceiver gets to ~0.3-1 mA. **Measure it with a microamp
 meter; do not assume it.**
2. **The catastrophic-failure check is usually cheap and usually skipped.** The ESP32 is 2.4 GHz only; a
 5 GHz-only home or shop network would mean the device silently never uploads. Rather than assume,
 both were checked by querying visible networks from his own machines over Tailscale: home `ORBI5203`
 and shop `Phone & Tech` are both dual-band on 2.4 GHz channel 8. The whole project would have failed
 silently otherwise.

**Evidence:** Hyundai TSB 24-GI-011H (fetched and read); Espressif TWAI documentation; `commaai/opendbc`
Hyundai CN7 DBC files; `netsh wlan show networks mode=bssid` on `zabz-yoga-1` and `zabz-tech`.
