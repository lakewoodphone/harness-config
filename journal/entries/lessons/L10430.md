**L10430 · I leaked a live SerpAPI key into the transcript by running a provider-chain probe: httpx puts the full request URL (with api_key) in its error message, and the estate logs it**

WHAT HAPPENED, and it was my doing. 2026-10-19, on the authority, while verifying that the company's web_search
chain would pick up DeepSeek first: the chain tried SerpAPI, which returned HTTP 429, and httpx's exception
message contains the FULL REQUEST URL — including `api_key=`. The estate's own `log.info` printed that string, my
probe printed it, and a LIVE SerpAPI key is now in this session's transcript.

The key is live: SerpAPI answered 429 (authenticated, throttled) rather than 401. It must be ROTATED by the owner;
redacting the copy does not un-leak it (P13b, and the estate's own rule: when a secret is in a transcript the fix
is rotation, not redaction of the copy).

ROOT CAUSE, fixed the same night in `app/web_access.py::_search_serpapi`:
 response = client.get("https://serpapi.com/search.json", params=params)
 response.raise_for_status() # <-- httpx puts the full URL, with the key, in the message
`params` carries the api_key, so any 4xx/5xx put the secret into a log line. It now raises a message built only
from the status code and the response body, neither of which can contain the request URL. py_compile gated the
replace; the API was reloaded and reports health 200.

WHAT THIS IS AN INSTANCE OF, and the rule to carry: **an error message is an output surface, and providers' error
messages are written by people who do not know what our logs keep.** The other providers in the same file matter
for the same reason — `_search_tavily`, `_search_brave`, `_search_jina`, `_search_firecrawl` all pass their keys
in headers or params, and any of them can surface a URL or a header in an exception. When adding a provider, or
when a provider starts failing, read the error path first; do not run a probe against a live key until you know
what its failure prints.

ALSO A LESSON ABOUT MY OWN HABIT: I ran an end-to-end probe against production keys to prove a wiring change, and
the proof cost a credential. A cheaper proof existed — call the new provider function directly with the key (no
provider chain, no other providers' failures), which is exactly what I did AFTER the leak to diagnose it. Prove the
new path in isolation first; only then run the chain.
