**L3184 · Fleet placement is not guaranteed remote; ssh hangs after printing; Windows Home has no encryption path; armed rollback for remote firewall changes**

## 2026-09-30 · Mesh dispatch, ssh hangs, and Windows Home encryption

**L — The `subagent` tool does not guarantee a remote node; measure placement, never assume it.**
Measured this session: a single-probe dispatch landed on **ZABZ-TECH** (the dispatching machine —
the broker's own report said *"under no pressure: the local node was NOT excluded"*), and a
five-child fleet dispatched minutes later landed on **zabz-tech-linux**, a different Linux node,
where every brief's Windows worktree path was absent. Two of those children failed with
*"the transport reported host "", which is not one of the hostnames the placement named ... refusing
to report work from a node the broker did not name"*; two more exited `4294967295` with no final
message. **Consequence for every future fleet:** a brief must carry its own bootstrap — either state
"clone the repository from `<authority>` into a temp dir that exists on the node you are on", or the
fleet must be dispatched with `subagent_local` and every result marked LOCAL. A brief that assumes
`C:\Users\...` or `/home/...` is a brief that fails on the next dispatch. Verify with one cheap
probe dispatch that reports `MESH-HOST: <hostname>` before spending five children on a guess.

**L — `ssh <host> <cmd>` from the shell tool can print its output and then never exit.** Measured
3/3 on `ssh secratary-ip hostname`: the hostname printed, then the call was killed by the harness
timeout with no exit code (120 s, 60 s and 45 s caps). The identical invocation detached
(`Start-Process ssh -ArgumentList ...`) returned `exited=0` with the same stdout in 4/4 trials, and
redirecting to a file (`ssh ... *> file`) also works. This matters beyond convenience: the autonomy
channel dispatches work over ssh, so an ssh that never closes its handles is a hang, not a slow
call. Rule: redirect every ssh whose output you do not need interactively, and never put a bare ssh
at the end of a chain.

**L — Windows 11 Home has no reachable encryption path, and that is a money decision, not a bug.**
`manage-bde -status C:` on the laptop reports `BitLocker Version: None`, `Key Protectors: None
Found`, and `dsregcmd /status` shows `AzureAdJoined: NO`, `WorkplaceJoined: NO` — a Home edition with
a local-only account. Device Encryption on Home is gated on a Microsoft/Entra identity for recovery
escrow, so there is no CLI route and no free route. The honest options are: upgrade to Pro (paid,
full BitLocker, key stays local), link a Microsoft account (free, key held by Microsoft, the login
changes), or leave the disk readable. Do not spend a session hunting for a workaround; check
`manage-bde -status` for `BitLocker Version: None` and escalate the money decision immediately.

**L — A firewall change on a remote box needs an armed rollback, not a careful hand.** What worked on
the public Hetzner box: snapshot `iptables-save`, the nft ruleset and `sshd_config` to a stamped
directory; write a `rollback.sh` in that directory; schedule it with `at now + 15 minutes`; validate
`sshd -t` **before** touching the firewall; only then enable UFW; verify from a genuinely different
vantage point (a key-only SSH from another public IP, a password attempt that must now be refused,
and the application answering 200 from the internet); then `at -r` the job. Docker's published ports
bypass UFW through the `DOCKER-*` chains, so UFW alone never covers a container host — the
verification step is what proves it did not break anything.
