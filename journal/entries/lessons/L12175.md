Corrects **H12222** (same session, ~40 minutes earlier). That entry listed nine Android paths the register
did not name and implied all nine were genuine gaps. **Two were duplicates of work already done**, and
one sentence I gave the owner was false. Both corrections are recorded here rather than edited into the

## What I got wrong

**1. I told the owner "the trunk also already fixes the seal: onEnabled now calls PolicyApplier.apply".
That is false.** The trunk branch `item-1005-e2ee-image-retention` (973e8cd) has `onEnabled` at L48-51
as a log line only, with `PolicyApplier.apply` at L86 inside `onProfileProvisioningComplete`. `main` is
where seal-time policy exists: `AdminReceiver.kt:57-63` calls `applySealPolicy(context, "admin_enabled")`
and `:34-35` applies on `ACTION_DEVICE_OWNER_CHANGED`, through `SealPolicy.kt`.

**How I got it wrong, because the mechanism will recur.** I ran
`git show <ref>:AdminReceiver.kt | Select-String "onEnabled|PolicyApplier.apply|ResetProtection"`. That
prints only matching lines, so the closing brace and everything that would have shown which method a
line belongs to were stripped, and `ResetProtectionAnchorStore.arm(` (in `onEnabled`) and
`PolicyApplier.apply(context)` (in a different method) appeared adjacent. I read adjacency as nesting.

> **Lesson: never infer block structure from a filtered grep.** `Select-String`/`grep` on source is
> evidence of *presence*, never of *scope*. To know which method a line is in, read the enclosing
> method with line numbers (`Get-Content | Select-Object -Skip N -First M` with an index counter), or
> grep for the signature and then read the block. This cost a false statement to the owner and one
> wasted subagent task.

**2. Items 1072 and 1073 duplicated ledger items 927 and 928, both marked `done` before I filed
anything.** 927 is "Ship a signed release build from every customer-facing installer, and refuse a debug
APK"; 928 is "Apply device-owner policy at seal time instead of at first launch", and 928's own attempt
naming `SealPolicy.kt` was already in the ledger. I filed from the readiness audit without running
`work.py list` first.

> **Lesson: an audit finding is not evidence that the work does not exist.** Before filing an item from
> an audit, search the ledger for the same defect (`work.py list --project X | grep <subject>`) and the
> roadmap for an existing path. Two of nine filed items were duplicates; the other seven survived
> scrutiny (the accessibility allowlist overwrite, screen capture, boot re-arm, mirroring, Play
> Integrity, the level on the phone, the MITM CA).

**3. A smaller one, same shape.** I verified the release flag with `git grep -c -- "-Release"` and read
zero hits for `guided_phone_installer.ps1`, concluding it did not pass it. It does —
`:304 Release = $true` — as a **hashtable key**, not a CLI argument. A grep for a flag string cannot see
a hashtable key.
