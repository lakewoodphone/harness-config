**L3470 · A store label must come from the thing you asked for, never from the query returning a row**

**A store label must be derived from the thing that was asked for, never from the fact that the query
returned a row.** `lpt ticket` printed `app=FOUND` for an order the app store holds zero rows of,
because `case_sql` is a single statement that always returns one row: it wraps the whole case in
`json_build_object(...)`, with `'order', coalesce((select row_to_json(x) from (...) x), '{}'::json)`.
With no matching order the scalar subquery yields nothing, the `order` key becomes `{}`, `counts` is
still populated — and the statement still answers. The caller tested "is the case non-empty", which is
always true. Three layers, each locally reasonable, combining into a confident false statement about
which database answered.

**Why that particular wrongness is the expensive kind.** This system's worst recorded failure was a
reported crisis that did not exist, caused by reading a stale store and believing it. `transport.py`
exists to make every reading name its store, and the shop's own skill says the divergence between the
stores *is* the finding. A label that says FOUND for an empty store does not merely lose information —
it destroys exactly the information the tool was built to carry, and it does so in the direction that
manufactures false alarms.

**Rules, with the evidence.**
1. **`coalesce(x, '{}')` inside a row-returning statement is a lie about existence.** If a statement
 must return a row, the row must carry an explicit existence signal, and the caller must test *that*,
 not the container's emptiness. Measured before the fix: `{"casefile": {"order": {}, "customer": {},
 "notes": [], "counts": {"notes_total": 0, ...}}}` from the app store for order 3003.
2. **When fixing a reporting defect, fix the label layer, not the shared query** — `case_sql` also has
 another consumer (`writes.py`), so changing its cardinality would have broken a file I was not
 allowed to touch. The narrow fix: a `_case_order()` that requires a non-empty dict, then both the
 primary-case choice and the store line go through it, and the casefile is still kept (under
 `case_without_order`) so nothing is discarded.
3. **Two stores can hold the same order under DIFFERENT ids** (operational 2996 = app 2861 for later
 orders). `lpt ticket` looks both up by the operational id, so `app=absent` is *legitimate* for
 recent orders and was previously masked by the false FOUND. When a fix makes a divergence visible,
 read the newly visible line as information, not as a new bug.
4. **A test that fakes a dependency as `[]` can hide a defect that the real dependency's shape
 creates.** The test double answered the casefile query with an empty list; production answers with
 one row containing `order: {}`. The fix had to change the fake to production's actual shape before
 the new assertions meant anything.

**And the meta-rule this session keeps earning:** both defects in this tool were found by *verifying a
subagent's claim myself* rather than accepting its report, and one of them — the false `app=FOUND` —
was found by the child while verifying something else. Reproduce the parent's evidence; the second
defect is often on the same code path as the first.
