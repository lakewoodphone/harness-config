**L1598 · tsx hoists imports above module-scope env assignments, so test DB overrides silently do nothing**

# tsx hoists imports above module-scope env assignments — tests silently hit the real database

**Host:** ZABZ-TECH · **Repo:** `personal-secretary-mvp`, `apps/rentals` · **When:** 2026-09-15

## The rule

In this repo a test file is compiled to **CommonJS** by `tsx` (the `apps/rentals`
package has no `"type": "module"`). esbuild reorders **every `import` to the top
of the emitted module**, above the module body. Therefore:

```ts
process.env.RENTALS_DB_PATH = path.join(tmpDir, "test.db"); // module body
import db from "../lib/db/schema.sql"; // HOISTED above it
```

is emitted as `require("../lib/db/schema.sql")` **before** the assignment.
`lib/db/schema.sql.ts` read `process.env.RENTALS_DB_PATH` into a module-level
`const` at import time, so the override never applied and
`apps/rentals/data/rentals.db` — the real database — was opened instead.

This is not theoretical. `tests/integration.test.ts:14` and `tests/sso.test.ts`
both set the env var this way. Their isolation was nominal; any run wrote into
the real dev database.

## The fix that works

A **side-effect module imported first**:

```ts
// tests/marketplace.env.ts — no imports except node:*
const tmpDir = fs.mkdtempSync(path.join(os.tmpdir(), "rentals-marketplace-"));
process.env.RENTALS_DB_PATH = path.join(tmpDir, "marketplace.db");

// tests/marketplace.test.ts
import { TEST_DB_PATH } from "./marketplace.env"; // MUST be the first import
import db from "../lib/db/schema.sql";
```

esbuild preserves import **order**, so the env module's body runs before the next
import's `require()`. Add a regression assertion in the suite itself:

```ts
assert.equal(repo.DB_PATH, TEST_DB_PATH);
assert.equal(repo.DB_PATH_IS_OVERRIDE, true);
assert.equal(fs.existsSync(path.join(process.cwd(), "data")), false);
```

Top-level `await` is a hard transform error under this config, so
`mock.module(...)` cannot be installed before hoisted imports either — that is
why route-level HTTP tests need the module-mock flag *and* a lazy import
structure, and why the same `next/headers` mocking problem appears here.

## Second-order consequence: `next build` created the database

`next build` imports every route; every route imports the repository; the
repository imported `schema.sql.ts`, which ran `mkdirSync(data)` and
`new DatabaseSync(...)` **at import time**. So a *build* created
`apps/rentals/data/rentals.db`, and the test-isolation assertion ("a test run
must not create data/rentals.db") then failed on an artifact the build itself had
just produced — `npm run gate` passed on a clean tree and failed right after any
build.

Fixed by making the connection lazy: `getDb()` memoises on first use, `DB_PATH` is
resolved without touching the filesystem, and the default export is a lazy Proxy
so `import db from "./schema.sql"; db.prepare(...)` keeps working. Verified:
3 consecutive `npm run build` runs, all exit 0, `data/` absent after each.

## Related trap found on the way

**Which database a failing test is talking to is not obvious.** Repeated
`FOREIGN KEY constraint failed` on `INSERT INTO sessions` while the referenced
user was provably present — with the insert working when run by hand — was
entirely an artifact of the suite writing to the *real* database (rows deleted
mid-run by another suite's `wipe()`, ids drifting across runs). Do not debug the
SQL; print `repo.DB_PATH` first. Hours were spent on the SQL.

## Diagnostic that would have ended it in one step

Add this to the module under suspicion, before touching any other hypothesis:

```ts
try { /* the failing operation */ }
catch (err) { console.error("FAILED", { dbPath: DB_PATH, isOverride: DB_PATH_IS_OVERRIDE }); throw err; }
```
