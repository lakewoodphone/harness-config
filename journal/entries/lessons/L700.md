**L700 · Authority DB: the real faults are verbatim transcript ingest, a stuck WAL checkpoint, and connection growth**

THE AUTHORITY DB: what is actually wrong, and what is not. Read-only audit, 2026-09-14 22:02-22:30 UTC, sqlite 3.46.1, `sqlite3 -readonly`.

NOT WRONG, and both were asserted wrongly earlier in the day:
- Corruption: `PRAGMA quick_check` = ok, exit 0, well inside 300 s. The "DB corruption detected" lines every ~6h for a week are Chrome PROFILE messages; 0 database-corruption events ever.
- The stale key: 0 rows in any TEXT column of all 203 tables, 0 byte-matches in the 3.76 GB db and its WAL, 0 in the Aug 16/23 backups. The "occurrences" were ingested transcript text written by the audit conversation itself (see L320). No rewrite is warranted.

WRONG, in order of consequence:
1. THE INGEST PIPELINE STORES TRANSCRIPTS VERBATIM. dsh_session_ingest.py and vscode_chat_ingest.py write session text into dsh_session_events.raw (+FTS mirrors) with no secret filter, so ANY key typed in ANY session is permanently in the authority DB and in /home/zabz/.fsearch/index.db. Measured live: the audit conversation searching for a key prefix wrote 386 byte-matches in 23 minutes and grew the DB 173 MB. FIX: a redaction filter at the existing `_row_text` boundary - `sk-[A-Za-z0-9_-]{20,}` -> `sk-***REDACTED***` - proved by a synthetic-key probe that expects 0 matching rows and >=1 REDACTED row. This is the highest-value fix in the audit because it removes the CLASS, not the instance.
2. WAL CHECKPOINTING WAS STUCK. `-wal` measured 280,452,552 B against a configured journal_size_limit of 67,108,864 (4.2x over cap, which is definitional proof checkpoints were not completing); main-db mtime 19:13 vs -wal mtime 22:02 = no successful checkpoint for ~2h49m. A restart cleared it to exactly 64 MB. ACTIONABLE MONITOR: `-wal` > 64 MB is an alarm and `-wal` == 64 MB is healthy - a far better health signal than the flapping /health. A long read can delay checkpointing, so treat the monitor, not a guess.
3. CONNECTION GROWTH. uvicorn pid 3607150 held 135 DB FDs (P48 recorded ~24) plus ~50 WAL FDs, RSS 4.86 GB. `_get_conn` (database.py:263) is thread-keyed and NEVER evicted; `cache_size=-64000` per connection; 160 sqlite3.connect sites. Restart is not a fix: 6 lock errors in the 3 minutes after the 22:07 restart against 15 in the 10 minutes before. 1,343 "database is locked" in 24 h, continuous (173 in the 15:00 hour). Newest from ingest: `INSERT OR REPLACE INTO dsh_session_exports` (dsh_session_ingest.py:200), exactly what P48 already records.
4. THE CONFLICTED CHECKOUT IS NOT A BROKEN FILE. `app/autopilot.py` is UU with NO MERGE_HEAD/REBASE_HEAD/CHERRY_PICK_HEAD/sequencer and NO conflict markers; the working file hashes to none of the three index stages, and the unmerged index entry has been held ~6h30m. It is a hand-resolved version that was never `git add`ed, and the running service deliberately executes this tree (its __pycache__ matches the dirty source). RESOLVE BY: keep the working version, prove nothing was dropped against both stage blobs, then `git add` + commit explaining it resolves the earlier merge. NEVER checkout --ours/--theirs, never reset --hard, never re-run the merge; leave the 6 stashes alone.
5. THE OLD DEEPSEEK KEY IS INERT, so no owner decision is needed: it answers HTTP 401 "Authentication Fails, Your api key ****96cf is invalid" on both flash and pro. The ~15 plaintext copies on disk (11 inside the deployed repo, plus /home/zabz ones and the fsearch index) are dead credentials - cleaning them is tidying, not risk reduction. The LIVE risk is the current key, which this session printed into its own transcript; that is why queue #31 exists.

CAVEAT RECORDED HONESTLY: the audit was read-only but heavy (3.9 GB DB scans, ~20 GB file search), and a sibling agent restarted the API four times at 22:06-22:10 while mid-deploy (matching .runtime/deployed-commits.log 22:07:37Z). Do not interleave a commit into that repo until it settles.
