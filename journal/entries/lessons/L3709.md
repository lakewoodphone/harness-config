## L — A production status change can exist with no trace of who made it

Found 2026-10-12 while attributing a false `READY_FOR_PICKUP` on order 2880.

`app/services/website_db.py::update_order` is the app's only writer for `orders`, and it does two
things in the same block: it writes the `order_status_history` row with the hardcoded reason
`Auto-updated by secretary reconciliation (confidence: N)` (line ~772), and it calls `_log_write` into
`website_write_log`. So a history row carrying that reason should always have a companion log row.
This one does not:

 orders."status" flipped 2026-09-18 11:00:55, history reason = 'Auto-updated by secretary reconciliation (confidence: 0.9)'
 website_write_log rows for order 2880: create 2026-09-15 (cli_lpt_sync_to_production), update 2026-10-12 (lpt-write, mine)
 -> nothing on 2026-09-18
 reconciliation_runs on 2026-09-18: id 267 only, started 11:34:16 - 33 minutes AFTER the flip
 website_write_log rows written 2026-09-18: 251, all source='dialpad_sync'

So the log was demonstrably working that day, the string can only have come from that one function,
and the caller is still not establishable. The honest reading is **unattributable**, which is a
different and worse answer than "the reconciliation did it" - and it is the answer a session
reaches only by checking, never by reading the reason string and believing it.

**Rule.** A reason string is a claim the writer made about itself, not evidence about what invoked it.
Before attributing any production change, look for the companion `website_write_log` row and the
matching run row. If they are absent while the log is otherwise busy, say unattributable.

**Where the data actually lives (this is why the first attempt looked like a dead end):** the
authority for `website_write_log` and `reconciliation_runs` is `secratary` (the office box), whose
`/home/zabz/personal-secretary-mvp/data/secretary.db` is ~23.7 GB and is the DB `lpt-write` writes
through. The Windows checkout's `data/secretary.db` (~1.79 GB) is a stale other deployment with
**zero** rows on 2026-09-18 - reading it would have produced a confident false negative. Provenance,
always: name the host and the file, not just the table.
