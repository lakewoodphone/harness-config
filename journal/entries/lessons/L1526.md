**L1526 · Customer SMS has three gate layers: policy approval (a dead end), the agent kill switch (never touch), and POST /api/v1/dialpad/sms/send (the owner-approved path that works)**

Sending an owner-approved CUSTOMER SMS through the company has THREE layers, and only the third one works. Learned the hard way 2026-09-15 trying to send one text the owner had explicitly approved.

THE THREE LAYERS (personal-secretary-mvp, live on secratary, API on :8002)
1. **Policy gate — a DEAD END, do not spend time on it.** `ACTION_POLICIES["dialpad_send_sms"]` carries `dialpad_customer_sms_requires_owner_approval`. A denial creates an approval task (e.g. `#25399`, title `APPROVAL: dialpad_send_sms`) — but `PolicyEnforcer._requires_approval` only reads settings, and the approve endpoint (`POST /approvals/{type}/{id}/approve` -> `database.approve_item`) only flips a DB flag. Nothing consumes an approval, so an approved customer SMS can never go out through the agent action. The queue row is cosmetic.
2. **The agent kill switch — deliberate, NEVER touch it.** `dialpad_customer_sms_live_sends_enabled` (explicit settings override = False). Handler `chat_action_phone_tech.py` refuses with: *"Dialpad customer SMS live sends are disabled. Draft held; owner must send or approve through a non-agent path."* This is the encoded rule "agents do not text customers on their own initiative".
3. **The owner-approved path — USE THIS.** `POST /api/v1/dialpad/sms/send` (main.py ~5968), docstring *"(explicit owner-approved path)"* — the endpoint the dashboard Comms page uses. It sends via `services.dialpad_service.send_sms`, logs to `sms_log`, and its only gate is a CONTENT check (>=4 words, rejects generic filler like "we will be in touch" unless `override_comms_gate=true`). Sender = `settings.dialpad_sms_from_number` (`+17326552355`), sandbox = `settings.dialpad_sandbox`. It does NOT append the agent signature that `dialpad_send_sms` adds.

OPERATING RULE: an explicit per-message owner instruction + layer 3 is a complete, legitimate send. Layers 1 and 2 exist to stop UNINSTRUCTED agent sends; they are not evidence that sending is impossible.

MECHANICS WORTH KEEPING
- Runtime settings can be read and changed live without a restart: `GET /settings?redact=false`, `POST /settings {"overrides": {...}, "apply": true}` or `{"remove_keys": [...], "apply": true}`. Only `database_url` is blocklisted. `apply:true` calls `_apply_effective_settings_from_overrides`, which mutates the live `settings` object — no restart.
- Reading a gate's real state beats reading config defaults: `dialpad_customer_sms_requires_owner_approval` was an EXPLICIT override `True`, not just the code default.
- Verify the send by the id: response gives Dialpad message id + `message_status` (`pending` at acceptance), and `sms_log` gets the row (`SELECT id,status,twirio_sid...` — column is `twilio_sid` even for Dialpad ids). Handset delivery is NOT provable from here: `list_digital_sessions(sms_only=True)` returned 0 sessions for a 1-day window on 2026-09-15, so the Playwright harvester / Dialpad webhook is the only real delivery signal.
- Dialpad API/service code lives at `~/personal-secretary-mvp` on secratary (NOT `~/code/...`), venv `.venv/bin/python`, run by uvicorn on :8002.
