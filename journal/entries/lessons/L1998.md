THREE FACTS THAT CHANGE PLACEMENT, AND WHY THE EXISTING TABLE WOULD HAVE GOT THEM WRONG:

1. **`secratary` is nearly out of commit — 3.4 GB free on a 22.9 GB box.** It is the authority every
 node queries AND the always-on company engine (18 agents, ~300 ticks/day). It is the LAST place to
 put a child, yet it is the one node the docs repeatedly recommend ("prefer it for anything that must
 not depend on a laptop being awake"). That advice was about *availability*, and it is being read as
 advice about *capacity*. Both are true statements; only one of them was measured.
2. **`mac-mini-ts` has NO node on PATH today.** Its `lib/nodes.js` row records the interpreter form
 "re-confirmed 2026-09-17" against `/usr/local/bin/node`. So either the row is stale or the runtime
 was removed. A node that claims a capability it does not have is the same failure class as the
 `zabz-tech-linux` "no Node runtime yet" note this repo already had to retract.
3. **`dsh` on PATH is false on the laptop, the desktop and secratary** — those three use the
 interpreter form by design. So `command -v dsh` must never be used as a capability flag.

AND THE ONE THING THAT IS GENUINELY GOOD NEWS: **ZABZ-TECH has 38.8 GB free and 39.5 GB commit free**
against the laptop's 13.7 / 20.8. The broker already prefers it — a probe child dispatched today landed
there and returned in 5.787 s while the laptop stayed flat. Offloading is not an aspiration to build;
it is a policy to keep, and the laptop's cost is what happens when the desktop is unreachable.

THE GENERAL RULES:
1. A node list is a list of NAMES. Reachability, capacity and capability are three separate readings and
 each has to be taken. Collapsing them is how a "preferred" node becomes the broken one.
2. Availability advice ("prefer the always-on box") and capacity advice ("that box has room") are
 different claims. Quote the measurement, not the reputation.
3. Measure before designing a scheduler: I now have per-node free memory, which the design needs, and
 `sshMs` — a floor on the cost of reaching each node — which the design also needs and did not have.
