**L5280 · A verifier that cannot find its input exits 0: the authority cannot run the lpt-sync dry-run at all (P4377, exact rejected candidates)**

**Measured 2026-10-15 20:17Z. The tool that decides whether a case is pushed CANNOT RUN ON THE AUTHORITY AT ALL — and it exits 0 while saying so.**

After pushing a case update to lpt-hub `main`, backfilling `references.productionOrder` into a sync
record, the verification contract for a customer case says to run the authoritative per-record push
decision on the authority:

```
ssh secratary-cloud 'cd /root/personal-secretary-mvp && \
 python3 scripts/lpt-sync-to-production.py --dry-run-all'

WARNING: lpt-hub UNRESOLVED. Rejected candidates:
 /opt/company/C:/Users/ezabz/Code/lpt-hub (no docs/);
 /opt/company/lpt-hub (no docs/);
 /opt/company/lpt-hub (no docs/);
 /opt/lpt-hub (no docs/)
ERROR: Cannot find lpt-hub repo
```

**Exit code: 0.** That is the part worth keeping. A verifier whose input is missing reports it in a
line and returns success, so `| tail -40` in a shell pipeline and `&&` in a script both see a
verdict — and a reader skimming for `ERROR` finds it only if they read every line. Compare the
inverse rule already in the surface: a non-zero exit is an open item. This is the mirror of it, and
it is more dangerous, because nothing about the call looks failed.

**The mechanism is visible in the rejected list.** The first candidate is a **Windows** path —
`C:/Users/ezabz/Code/lpt-hub` — glued to a Linux prefix `/opt/company/`. So the resolution is
`LPT_HUB_LOCAL_REPO_PATH` (or a persisted config) carrying a Windows path on a Linux box, and every
candidate after it is a directory that has no `docs/`. This is **P4377** with the concrete rejected
list P4377 did not have: it recorded that the documented path does not exist and that the corpus
clone is 80 commits stale, not that the resolver has a Windows path in it.

**What it costs.** The three-command verification contract in the customer-case skill cannot be
completed on the authority today: `sync-health-audit.py`, `lpt-sync-to-production.py --dry-run-all`,
and `tools/customer/audit.py`. `--dry-run-all` is the one that **decides** — the skill says its
verdict outranks `audit.py`'s over-reporting C11 proxy — so when it cannot start, a case that was
just pushed can only be verified by reading the pushed refs from a second machine, which is what
happened instead. That is a real but weaker check: it proves the bytes landed, not that the linker
would have made the right decision.

**The rule.** Before promising a verifier's verdict, prove the verifier can start — and treat a
success exit code as carrying no information about whether it did. `journal.py check` (exit 0 and
one line), `lpt-write doctor` (one screen), `lpt doctor` (lists each store and says FOUND or absent)
are the cheap proofs; this tool has no equivalent, which is why it failed silently into a success.

Evidence for the open pain **P4377**; not a new pain. Not fixed here — the fix is a decision about
where the authority's corpus clone lives, not a command.
