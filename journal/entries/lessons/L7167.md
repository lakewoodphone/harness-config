**L7167 · The channel is the decision - an urgency rule that lives on one branch of an if/else is not a rule**

Two branches, one reminder, opposite outcomes. `personal_ops.py` sends a due reminder either through `send_owner_update` (channel `sms`/`both` -> `_infer_owner_update_urgency` -> reason starts with `reminder:` -> `urgent` -> passes the gate) or into the badge queue via `enqueue_owner_message(status="held", urgency=` the reminder's own priority column). The 2026-10-13 fix that says the owner's own reminders must not be suppressed by his own noise guard was written for the first branch only, and the second is the default.

GENERALISE: when you fix a classification rule, grep for every PRODUCER of the same object, not every caller of the function you edited. `_infer_owner_update_urgency` had exactly one caller, so "did I update every call site" answered yes — while the other producer never called it and so never got the rule.

SECOND, and the reason this cost a real anniversary: `reminders.status='sent'` and `last_delivered_at` are written when the message is handed to the QUEUE, not when a human receives it. A reminder can read `sent`, `delivery_attempts=1`, with a clean timestamp, and have reached nothing the owner looks at. Read the queue row, not the reminder row, before saying a reminder was delivered. "No answer" and "an answer that never closed" are different sentences.

THIRD: the refusal is recorded only by the flush path. Rows enqueued directly as `held` write no `activity_log` line, which is why `owner_sms_held` fell from 58-79/day (1-5 Oct) to 1-5/day (11-15 Oct) while the queue still filled. A hold count that counts only logged holds is not a hold count — and a falling number that means "the hold moved to a quieter code path" reads exactly like a fix.
