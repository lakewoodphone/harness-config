**L3500 · A resume needs a stable job identity: a timestamped job folder is a resume that never resumes**

A copy tool that must survive the machine dying needs a **stable job identity**. The first
version of the shop's SD-card copier named its job folder `LPT-<machine>-<timestamp>`
(`hardware-diagnostics/sd-data-copy/GO.BAT` + `lpt-copy.ps1` over robocopy, 2026-10-08). A
machine that died mid-copy therefore produced a NEW folder on the next run and copied the
whole disk again — a resume that never resumes. It looked finished and it was wrong in
exactly the scenario it existed for.

The same version verified by asking only "is there a file at this path", so a file
truncated by a power cut counted as **arrived**. The check could not fail on the one
failure it existed to catch.

What replaced it (`GO.EXE`, `src/lptcopy.cs`, 2026-10-11):
- job folder `<card>\LPT-<machinename>`, no timestamp, ever;
- a ledger `<job>\state\copied.tsv`, fsynced in batches, living on the destination;
- per-file order: write bytes → `Flush(true)` → set the source's timestamp → then the
 ledger line. A file carrying the source timestamp is a file whose data was flushed;
- adoption: right size AND timestamp means done even with no ledger line, so it can finish
 a copy started by an older tool;
- verify pass on size + timestamp for every file (`--deep` adds sha256), then a **repair
 pass** that re-copies what did not match before anyone is told the copy failed;
- an unreadable *folder* downgrades the verdict: it is data that is not on the card.

Measured: `test/run-tests.ps1` (51 checks) kills the process with `Stop-Process -Force`
mid-copy after real work is on the card — 75 ledger entries survive, the next run finishes
`VERIFIED`, and there is still exactly ONE job folder on the card.
