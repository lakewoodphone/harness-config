**L3426 · one click pays four cold starts: where the launcher's 20 seconds actually go, and that load is 25x of it**

Measured ZABZ-YOGA 2026-10-08/09 on the owner's "+ new window takes 20-25 seconds".

WHERE A CLICK'S TIME GOES, with phase markers now in windows.log:
 1. shell hop, click -> launcher `new: begin` : 5-14 s, wildly variable
 2. `new: begin` -> `edge-launch` (this script's work) : 4.0-5.5 s
 3. `edge-launch` -> window verified live through proxy : 0.75-1.3 s
Inside (2): cold WMI process scan ~2.7-3.2 s, first cold HttpClient call ~1.7 s, netstat table ~0.5 s,
slot loop and token probe the rest. Fixed in this session: netstat replaced Get-NetTCPConnection
(3,462 -> 275 ms) and the WMI scan is now read once, not twice (it was called by Invoke-New AND by
Get-WindowOriginPorts with no argument).

THE PART THAT IS NOT IN THE SCRIPT, and the reason numbers move so much: every click starts a COLD
PowerShell. Measured: `pwsh -NoProfile -Command exit` 1,230-1,418 ms on a quiet moment; parsing this
204 KB / 3,400-line file 284 ms for a first parse in one process and 7,195 ms for the same parse in
another process eleven minutes later; `Get-CimInstance Win32_Process` 2,755 ms cold. In between those
two measurements the machine was running TWELVE agent loops (engine_health: p95 event-loop lag
1,252 ms, max 7,191 ms, 27 sessions, 403 processes, memoryLoad 69 %). So on this laptop a cold start
is not a constant - it is whatever the fleet load makes it, and that is the owner's 20 s.

CONSEQUENCE FOR ANY FUTURE LATENCY CLAIM HERE: measure the load with the latency. Two identical
commands, same file, 11 minutes apart, differed 25-fold. A single reading on this machine is not
evidence.

THE FIX THAT FOLLOWS, not done here: a resident launcher. The work of opening a window is 4-5 s of
already-warm logic plus a browser spawn; everything else is process start-up paid per click. A small
process started by the watchdog that is already parsed and already knows the slot origins would take
a click to ~1-3 s independent of load. That is a designed change (process lifetime, a loopback
trigger, how the control reaches it) and it must not be half-built at the end of a long session.
