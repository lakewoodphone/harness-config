**L3505 · The blind guard, the guard whose flags differ from its twin, and the anchor that measurement would destroy**

## WHAT WAS LEARNED, SO IT IS NOT RE-DERIVED

**L3608 — the blind guard had one wrong index, and it is a class.**
`cron-script-guard.py:decode_wrapped()` began `if os.path.basename(toks[0]) == WRAP`. On a real
crontab line `toks[0]` is the SCHEDULE (`*/5`), so the wrapper was never recognised: measured
2026-10-11 on the authority, 24 of 24 crontab lines are `cron-wrap.sh`-wrapped while the guard's own
status said `cron_scripts_watched: 0, present: 0` and it exited 0. A blind guard with a green light is
worse than no guard, because it is cited as coverage. Fixed by searching the whole token list for the
wrapper, re-basing name/payload on that index: now `wrapped_cron_lines: 24, payloads_decoded: 24,
cron_scripts_watched: 4, present: 4`. Its twin `cron-target-guard` had the same class of defect and
was fixed earlier the same day (`--write-status`/base64 awareness). **When a guard reports "0 of
anything watched", the guard is the suspect, not the estate.**

**L3609 — a guard that takes different flags than its twin is its own trap.**
`cron-script-guard.py` accepts `--json`; `cron-target-guard.py` accepts `--write-status`. Running the
first with the second's flag exits 2 with `unrecognized arguments` and writes nothing, so
`/root/.cron-scripts/status.json` was stale by hours and read as current. **Verify a guard by running
it the way its OWN crontab line runs it**, not the way its sibling is run.

**L3610 — the anchor: reading a WAL database changes it, and that is why the plan must not hash it.**
A read-only inspection checkpoints the WAL into the main file. The office working copy's SIZE was
unchanged after the re-freeze while its mtime moved and its WAL went to 0 bytes - logical content
intact, bytes different. Therefore: verify a frozen copy LOGICALLY (row counts, a dump hash) or verify
against it by hashing the FILE WITHOUT OPENING IT, and never both. The anchor is the one artefact on
this estate where measurement destroys evidence.

**L3611 — the anchor has a second home now, and its own file is the record.**
`/home/zabz/cutover/office-frozen.db` (23,622,823,936 B, mtime 2026-10-11T04:27:31Z - before the
05:43:36Z cutover) is the exact cutover-point state and the whole rollback plan. It existed on ONE
consumer SSD in a 2013 desktop with no UPS and - measured - **no provider snapshot, because that host
is physical, not cloud** (`lpt-survivor-01` is the Hetzner standby, a different machine). Every other
copy of that state had been overwritten: R2's office-era object was replaced in place by the
authority's own daily backup. Nothing on the estate had room for 23.6 GB (authority ~20 GB free, vault
4.6 GB, office disk 34 GB against the file itself), so it was streamed gzip -> 64 MiB multipart into
object storage with **zero local copy and without ever opening the database**
(`scripts/mesh/anchor-to-r2.py`, which imports no sqlite3 and runs no query). Result, verified from
R2's own side:

 anchor/office-frozen.db.gz 6,282,136,085 bytes 2026-10-11T23:55:34Z
 sha256(uncompressed) 0224e427534aba902331f44ba012972bacc8761fc2df4cd668f1cdb5ed649e71
 source_bytes 23,622,823,936
 source_mtime 2026-10-11T04:27:31Z
 sidecar agreement object size matches the sidecar

Its `--verify` mode states plainly what it does NOT prove: that the compressed bytes decompress to
that hash (that needs a download and a decompress). Do not let a future session read "verified" as
more than it is.

**L3612 — a broker that answers is not a broker that works.**
The authority's `mesh-broker` answered `/healthz` 200 while reporting all FIVE nodes `unreachable`
(`readFailures 5/5`). A provider asks the broker first; a reachable-but-blind broker therefore returns
no eligible node and the dispatch dies - where an ABSENT broker triggers the provider's direct-probe
failover. **Blind is worse than missing.** `install-authority-cloud.sh` refuses to leave a blind
broker enabled for exactly this reason and it earned its keep; the lesson is that the refusal must be
believed rather than worked around. The working broker is on the OFFICE box (the one host that can
read the node surfaces), now `enabled` so a reboot cannot kill it - and that is a **deliberate,
documented exception to the freeze**: it reads node health and touches no database. A future session
that finds a running service on a frozen box must read this before "cleaning it up".
