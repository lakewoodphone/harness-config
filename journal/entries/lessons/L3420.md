**L3420 · communications stores every message ~14x with IMPORT timestamps - never conclude from message ordering**

**`communications` stores every message about fourteen times with IMPORT timestamps. Never conclude
anything from message ordering, from a count, or from a message looking unanswered.**

Measured on production 2026-10-09: **116,675 rows on customer files hold 8,361 distinct
(customer, channel, direction, text)** — about thirteen copies of each. One customer (id 1753) has
**10,049 rows for 44 messages**; customer 68 has 240 rows for 28 texts, the same December-2025
conversation re-imported at least nine times, each block stamped an hour or more later than the last.
Up to 2026-07-09 the table is essentially 1:1 (34 rows / 34 distinct); the duplication begins
2026-07-10. This is journal P2862, and the number is the point: the defect is not "some duplicates",
it is that **the send time of almost every message older than a month is gone.**

It has already produced a confident wrong answer. On 2026-10-09 the first pilot analyst wrote a note
on order 2 saying the customer's *"Should I bring it to someone else"* had **no reply on the record**.
Production holds the replies: *"we're working on it. we got it to turn on but the display is not
working yet"* and *"we were not successful I don't think its fixable. you can come pick it up,
sorry."* (message 28133). A second analyst reached the same shape of conclusion about order 299,
where the shop had in fact written *"Really sorry to hear that! Please bring it in and we will reglue
it."* (message 27204). Both read a duplicated block and treated its import stamps as the truth.

So, and these are now enforced in `lpt-sweep` rather than remembered:

- Read the message **text**. It is real.
- To recover the conversation, keep the FIRST row per `(type, direction, text)` and order by `id` —
 the insertion order within one import block is the real order. `lpt_ops/sweep.py` briefs and
 `verify_order.py`-style readers must do this; the raw table must not be read straight.
- The analyst contract forbids ordering claims outright (rule 9), and `default_review_policy`
 **holds** any verdict whose words rest on "no reply / unanswered / ignored".
- Cross-check a "no reply" claim against the whole customer thread before believing it. Every time
 this was checked on 2026-10-09, the reply existed.
