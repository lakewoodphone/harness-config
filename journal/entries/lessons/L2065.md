**L2065 · When a fleet agent regresses: steer with failing test ids, forbid weakening, offer an honest exit**

## What happened
The voice-engine agent initially regressed two of its own tests mid-run and I could see it
in live test output (test 5 flipped pass -> fail at 20:28). I did not kill it and did not
take over. I sent it one message naming the exact failing test ids, forbidding it from
weakening the assertions, and telling it that if it could not make `formant` measurably work
it must REMOVE the parameter rather than leave an inert knob.

It came back with a genuine fix: the `mix=0` failure was a real DSP defect (one-pole smoothing
is asymptotic, so mix never reached a bit-exact dry path), and it replaced all parameter
smoothing with fixed-rate slewing. It also found two defects nobody asked about (linear
interpolation costing 1.76 dB; a formant bandpass bank draining 8-10 dB, one preset 19.5 dB
down) and fixed them with measured per-preset gain.

## The rule
A fleet agent that regresses is not automatically broken - mid-run regressions are normal while
it is mid-refactor. The question is whether it can SEE the regression. Steer with exact failing
test ids plus a hard prohibition on the lazy fix (weakening the assertion), and give it an
honest exit (remove the feature) so it is never incentivised to fake a pass. That worked here.

## Corollary
Ask for a machine-checkable map when the deliverable is meant to drive a UI. I asked for
"which params each preset responds to"; it produced PRESET_CONTROLS plus a test that renders
all 50 preset x param pairs and asserts a param is listed IF AND ONLY IF it moves the output.
That converts my guesswork about wiring sliders into a fact, and my verify.js now cross-checks
the UI's fallback copy against it.
