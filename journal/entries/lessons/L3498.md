**L3498 · Fully synced means writing the order link in six homes; and two measurement traps that produced wrong answers**

"Fully synced" is a claim about six places, and a verifier that reads only one of them will call a correct case missing. Measured 2026-10-11: WO26100812739 had a case file, a live order, a schema-valid sync record and notes on the order, and `sync-health-audit.py` still reported it as a recent active prod order with no lpt-hub case.

Rule: when a case is linked to a production order, write `workflow.orderNumber` AND `references.orderNumber` AND `references.productionOrder` AND `references.websiteOrder` AND `references.workOrderId`/`ticketNumber` AND the case file front-matter `work_order:`. `references.websiteOrder.orderId` is the one the push tool's duplicate guard reads, so omitting it makes a push capable of creating a second order for the same job.

Two measurement traps found in the same hour, both cost a wrong answer before they were caught:
- PowerShell strips embedded double quotes from an argument passed to a native command, so `lpt sql --store operational 'select max("createdAt") from orders'` returns `column "createdat" does not exist`. Use `to_jsonb(orders)->>'createdAt'` or run the SQL from a file. A query that errored is not a measurement.
- Reading a directory of sync records with `open(f, encoding='utf-8')` crashed on a record that a `utf-8-sig` read handled; when checking a batch, read with `utf-8-sig` and report the failures rather than stopping at the first one.
