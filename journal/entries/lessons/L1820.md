## A measurement gap on a counter is not a reason to refuse work

Evidence, 2026-09-16 23:20Z-23:40Z, mesh stream S1 (docs/mesh/72-capacity-contract.md §2, journal
H416).

**What happened.** The first build of `GET /mesh/capacity` required the governor's lease directory
before it would report a slot budget, so `zabz-tech-linux` and `secratary` — the two nodes the mesh
was built to use, 24 computable slots each — answered `accepts.fleet: false` with the reason "no
governor lease directory on this node, so its slot budget cannot be measured". The broker respected
the answer, correctly, and the fleet-eligible mesh collapsed to the two Windows machines. The
defect was invisible to my own checker: `mesh-capacity-probe.ps1` validated the schema, saw a
well-formed refusal with a reason, and printed **PASS** on every node.

**The rule.** A refusal is only correct when the thing that cannot be measured is what the decision
needs. Here the *budget* is pure arithmetic on `mem.freeMiB`, which was measurable everywhere; the
lease directory only supplies `inUse`. Two different conditions had been collapsed into one:

* **unmeasured budget** (no readable free memory, or no engine) → refuse, with that as the reason;
* **unmeasured counter** (`inUse` with no lease directory) → accept, report the computed budget with
 `inUse: 0`, and name the inference in `reason`.

So the fix in the route: `budgetSlots` is computed whenever memory is measurable, `inUse`/`queued`
are `0` when no directory exists (an inference from the absence — the governor creates its layout
before it grants anything, `governor.js:100`), and `accepts.reason` distinguishes **blockers**
(which set `fleet: false`) from **notes** (which do not).

**The transferable part, which is wider than this route.** `reason` is a note as well as a
restriction: any payload whose meaning depends on "derived" versus "measured" has to say which. And
a schema validator cannot catch a wrong *policy* — it only catches a wrong *shape*. Every target
passed while half the mesh was excluded, so measuring the consequence (the broker's own counts) was
the only thing that found it. When a route reports a decision rather than a number, the check has to
be the decision's outcome, not its syntax.

**Also corrected:** the probe's default node list still named three nodes after a fourth had a gate
deployed, so a probe run could not have covered `zabz-tech-linux` at all. A hardcoded fleet list in
a checker goes stale the moment the fleet grows.
