**L550 · Do not fix source by pattern: regex matched prose in a docstring, and an apply script must plan before it writes**

Two failure modes from fixing paths by pattern instead of by structure

1. A REGEX ON SOURCE TEXT DOES NOT KNOW WHAT A DOCSTRING IS.
I inserted imports by anchoring on the last line matching
 ^(import|from) [A-Za-z0-9_., ]+$
In app/services/amazon_bank_service.py that matched a line of PROSE inside the module
docstring, so the import was written into the docstring as inert text. Every syntax
check passed -- it is a valid string -- and the failure surfaced only at runtime as
NameError: name 'code_root' is not defined, in three of nine files.
Use ast. `ast.parse(src).body` filtered to Import/ImportFrom gives the real import
block and the real insertion line. Verify the repair the same way: re-parse and assert
an ImportFrom with module == "app.paths" exists, rather than grepping for the text.

2. AN APPLY SCRIPT MUST VALIDATE EVERYTHING BEFORE WRITING ANYTHING.
My first run replaced 14 string sites, then hit an assertion on the 15th (a file
contained an import twice, not once) and aborted -- leaving the tree half-applied:
modules calling code_root() with no import. Compile passed for the files I had listed
and the app still imported, so nothing shouted. Build the whole plan, assert on every
step, and only then write. The cost of finding this later is a NameError in whatever
code path touches the half-applied file first.

Both are the same underlying error: verifying at a weaker layer than the thing that
can break. Compilation is not importation; text search is not the parse tree.
