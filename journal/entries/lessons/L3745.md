**L3745 · Requiring every query term on the same line manufactures confident false negatives - and the fix must still fit the budget**

**Measured on `secratary-cloud`, 2026-10-12, and recorded but never fixed since D2983 on 2026-10-09
(journal H3571).**

`journal.py`'s search required **every query term on the same line**. Every tool above it inherited
that rule, and every tool above it reported the resulting exit 1 — whose own message is *"the scope was
searched and holds nothing"* — as a real negative:

 fa journal "lpt website" rc=0 8 hits
 fa journal "lpt website deploy" rc=1 "no match" <-- the words are lines apart, not absent
 fa journal "cloud migration secretary" rc=1 "no match"

`search.py`, the MCP tool body, rendered that exit code to agents as
`NO MATCH (exit 1: the scope was searched and holds nothing)`. **A confident false negative on an
ordinary two- or three-word query is worse than a slow answer**, because the agent stops looking and
writes down the negative. D2983 cited exactly this pair as the reason to stop telling agents that
`fa` was the primary search surface, and then the defect was left in place for three days.

**The rules.**

1. **The unit of matching is the term, not the argv element.** A query arrives as ONE argument from an
 MCP tool (`search.py` passes the whole query as a single string) and as MANY from a shell. Both must
 mean the same thing, so split every pattern on whitespace and require every *term* — never the
 literal phrase, and never on one line.
2. **"All terms in the entry" is the default; "all terms on one line" is an explicit opt-in.** A
 strict reading is a legitimate tool (`--all-words`), but it must not be the silent default of a
 search box.
3. **Test the exit code, not the prose.** The failure here was not a crash — it was exit `1` with a
 confident message, and a reviewer reading the output would have believed it.

**Fix and its verification** (`journal/tools/journal.py`): entry-level AND over whitespace-split terms,
in a single bounded pass; `--all-words` preserved for the strict reading; `--regex` for adjacency.

 "lpt website deploy" exit 1 -> 0
 "cloud migration secretary" exit 1 -> 0
 "zzqqnosuchterm9931" exit 1 -> 1 (a real negative stays one)
 "battery" exit 0 -> 0
 --all-words "cloud migration" still strict
 journal.py check 0 errors
 latency 399-490 ms (below the 5 s budget)

**The trap in fixing it.** The first version recomputed `text.lower()` per candidate to test the entry
level, which cost an extra full-text pass per entry and measured 4.7-5.8 s — **the fix breached the
budget it was meant to protect.** The second version derives the entry-level test from the terms
already seen while scanning lines (one pass) and caps the collected lines at what can be shown. Warm
latency ended *better* than before the change (1.5-1.9 s vs 1.9-2.5 s). Correcting a false negative is
only half the job; the corrected query must still fit the budget.
