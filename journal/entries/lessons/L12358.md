**L12358 · A shop ticket number can be a number nothing answers to - print the work order instead**

Case dell-latitude-5520-duestch-7325036369-2026-10-20 carries references.ticketNumber 12763 in its sync record and the 2026-10-20 label was printed with it, but no store answers to 12763. Measured 2026-10-25 on the operational store: tickets holds 676 rows with max id 12516, and select count(*) from tickets where id=12763 returned 0; the same query on the app store returned 0 rows; orders.ticketNumber and repair_intake_cases.ticketNumber are both null for order 3167. The number was written by a session and then propagated into a label and a sync record. Rule: when a ticket number cannot be produced from a store, print the WORK ORDER number on the label - lpt ticket accepts it, every tool agrees with it, and a number the secretary cannot look up is worse than no number. Second, smaller trap from the same session: the installed lpt advertises 'lpt note add' in its helptext but its parser rejects the subcommand (choices are doctor, ticket, case, wo, order, customer, cust, sql, photos) - the write path is lpt-write note add --order ... --text ... --apply in lpt-ops, and lpt sql fails with a syntax error if a result column is aliased 'at' because AT is reserved.
