**L7295 · Kiosk photos live in kiosk_intake_photos and the counter reads repair_intake_case_photos - two tables, one case, no screen reads both**

**L · The kiosk writes a customer's photos into `kiosk_intake_photos` and the counter reads `repair_intake_case_photos`. Two tables, one relation, and no screen reads both — so every photo a customer takes on the shop tablet is invisible at the counter.**

Measured 2026-10-16 in the source, after the owner attached pictures to a kiosk intake and the
counter said "The server has no photos for this job yet."

**The write — the kiosk:**


`intakeId` is a foreign key to `RepairIntakeCase`, so the kiosk's photo row points at the SAME case
the counter opens. The rows are there, attached to the right case.

**The two services are deliberate mirror images that were never joined.** `schema.prisma:6227` says so
in its own comment — *"Mirrors `KioskIntakePhoto` on purpose, because the two features write the same
kind of object into the same Cloudflare R2 bucket"* — and mirroring the TABLE is exactly what makes
the customer's photos unreachable from the counter. Same bucket, two key prefixes
(`kiosk-intake/...` and `repair-intake/...`), two tables, one case row between them.

**The fix is a read, not a migration.** `listPhotos(caseReference)` must union the two tables for
the case (or the counter must call a new `getStaffCasePhotos` that does), and `toSummary` must sign
a URL for whichever prefix the row's `storageKey` carries. No data is moved, no customer photo is
copied, and the existing rows start appearing immediately.

**The ownership question the owner has to answer** is whether the kiosk's photos should also be
*attached* to the case in the counter's own table when the case is promoted to a work order — that
determines whether a later "Add photos" write and the kiosk's read stay one list or two.
