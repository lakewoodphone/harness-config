**L2796 · A space-separated time literal sorts below every ISO T row - this database silently returns the whole day**

## LESSON — `'2026-09-28 16:16:00'` (space) sorts BELOW every `2026-09-28T16:16` row. Filtering this database by a time literal without the `T` silently returns the whole day.

**Measured twice on 2026-09-28, same database, same trap, two different sessions.**

The live `secretary.db` stores timestamps as ISO-8601 with a `T` and an offset:
`2026-09-28T16:16:00.123456+00:00`. A SQL literal written with a space separator —
`'2026-09-28 16:16:00'` — is compared **as a string**, and at position 10 the space `' '` (0x20)
sorts **below** `'T'` (0x54). So `started_at >= '2026-09-28 16:16:00'` is true for **every** row of
that day, whatever the hour.

**Measured, as a control:**

```
started_at >= '2026-09-28 16:16' -> 58 sessions (the whole day)
started_at >= '2026-09-28T16:16' -> 3 sessions (the window)
today total by LIKE '2026-09-28%' -> 58
```

**What it nearly cost.** I used the space form to ask "did W1 change the verdicts after it landed?"
and got 58 sessions with **15** step-budget failures, which reads as *the fix did not work*. Every
one of those failures predated the deploy. The corrected answer is **3 sessions, all completed,
zero step-budget failures**. I was one step from reporting a working fix as broken — and the same
sentence, written by W9 a few hours earlier, records the identical defect from the other direction:
`proactive_engine._now()` wrote `%Y-%m-%dT%H:%M:%S` while SQLite wrote `%Y-%m-%d %H:%M:%S`, so every
`strftime()` window in that module silently excluded the rows it had written itself.

**The rules.**
1. When filtering this database by time, **use the stored format**: `'YYYY-MM-DDTHH:MM'`, never a
 space.
2. **Run the control.** Query both forms and print both counts. If they differ, the comparison is
 doing something you did not intend. One extra line makes the difference between a measurement and
 a guess.
3. Prefer a bounded window (`>= X AND < Y`) over `>= X` when the intent is a window, and never trust
 a count whose filter you have not seen behave.

This is the estate's recurring failure one more time: a number that looked like proof and was not.
It is also, precisely, why the standing rule is *no claim without provenance* — the count was real,
the query was real, and the question it answered was not the question asked.
