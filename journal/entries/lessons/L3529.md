**L3529 · The journal's one-id-one-thing invariant holds per machine and FAILS BETWEEN them - journal.py check reports 0 errors while 12 ids mean two different things across the mesh. Allocate ids against the shared ref**

Journal collision analysis, 2026-10-11 22:35Z. Owner: *"analyze this really well and get it solved robustly with
everything in sync and no data lost."*

WHAT THE COLLISION ACTUALLY IS - measured, not the child's count.
- **12 collisions, not 47.** `decisions/D3032, D3033, D3039-D3046` and `handoff/H3501, H3502` - a local
 UNTRACKED entry that also exists on `origin/main` with a **different body**. One further path is an exact
 duplicate.
- **`journal.py check` reports 0 ERRORS** - and that is the important finding. Within this machine each id
 maps to exactly one file, so the collision is INVISIBLE locally. **It exists only between machines.** The
 integrity checker cannot see the failure mode that matters; the invariant "one id means one thing" holds
 per-machine and fails across them.
- 236 untracked local entries vs 3,440 upstream. Only these 12 collide; the rest are simply new.

WHAT A DECISION EVEN LOOKS LIKE - the sample settles it:
 LOCAL D3032 "ADB helper contract in lpt-flip-phone" written on ZABZ-YOGA
 UPSTREAM D3032 "Three decisions ... shop's money & customer reporting" written on secratary
Same id, same date, **genuinely different entries from two machines. Both are real. Neither is garbage.**
So the resolution is NOT "pick a winner" - it is **both survive under their own ids.**

THE RULE, and it is unambiguous: **the PUBLISHED copy keeps the id** (other machines' refs already cite it);
**the local UNPUBLISHED copy is renumbered** with an alias recorded so citations still resolve.
`journal.py repair-ids` exists for exactly this. Nothing is discarded - that is the "no data lost" clause.

ROOT CAUSE, worth fixing beyond the repair: **id allocation happens locally against local refs.** Two
machines that append without syncing both allocate the same next id. The durable fix is to make allocation
collision-proof across machines (allocate against a fetched shared ref, or check the remote before
committing to an id) - otherwise this recurs every time two machines write while apart, which is exactly the
normal state of this mesh.

THE HAZARD THAT DEFEATED THE LAST ATTEMPT, and how it is handled: this checkout has a **LIVE WRITER** - the
DSH journal autocommit rewrites `journal/alloc/bands.tsv`, `index/*` and `state/*` after every append, and it
created `L3527.md` mid-operation last time. **A checkout being written to during a rebase is a data-loss
shape.** So the repair and the git operation are to run as one tight sequence with no journal appends between
them, and **the standing order if it fights is to leave the repo a few commits behind rather than risk the
entries.**

things, then stash/rebase/pop with abort-on-conflict, and report proof that all 236 local entries still exist
somewhere. It is instructed to use the journal's own tooling and to STOP rather than hand-improve 12
