**L2005 · Tech Mode Install ID drifts on a phone with no RTC/SIM: read it, compute, type it in one session**

Measured 2026-09-18 on E4610 serial 615291677 (no SIM, `gsm.sim.state = ABSENT`, no network time).

What the device does: the clock starts near zero at every boot (`date +%s` = 417 while `/proc/uptime`
= 436; the display read "1970" with `persist.sys.timezone = Asia/Shanghai`). Tech Mode's Install ID is
just that clock read at app start, and `TechModeManager.initializeState` self-heals any stored value
below MIN_VALID_TIMESTAMP (2024-01-01) to "now" — which on this phone is always true, so **the Install
ID is rewritten on every app start**.

Observed: Install ID **56** before our staging (support code 379441, worked), then **661** after our
staging reinstalled the Tech Mode APK (support code 948512). Device Key stayed 990006152916770.
The phone's epoch was 827s at 14 minutes of uptime, so the next session would have shown a different
Install ID again.

Rules that follow:
1. Never store or reuse a Tech Mode code for a device whose clock is not network-set. Read Device Key
 and Install ID off the Tech Mode screen, compute the code, and type it **in the same screen session** —
 the activity reads the timestamp once in onCreate and compares against that same field on submit.
2. `adb shell date -s` / positional `date <set>` both fail with EPERM (shell has no CAP_SYS_TIME), and
 `setprop persist.sys.timezone` does not stick either, so the clock cannot be fixed from the shell;
 it settles by itself once the phone has an active SIM / network time, and then the Install ID becomes
 a normal stable 10-digit timestamp.
3. A phone with a zero clock will fail TLS-dependent apps (Waze, weather) even with correct permissions —
 check the date before blaming the app, and expect it to come right once the customer's line is in.
