**L3726 · A tool that puts SQL in an ssh command line silently truncates: lpt ticket was dead for every work order**

**Lesson: a tool that puts SQL in an ssh command line is a tool that silently truncates, and `lpt ticket` was dead for every work order.**

Measured 2026-10-13 on ZABZ-YOGA. `lpt ticket WO26100812738` answered `lpt: order 3017 matched but no store returned a case` — exit 1. That sentence reads as *the case file is missing*, which is the one thing this shop cannot afford to be wrong about. The order was in `operational` and perfectly reachable; `lpt customer` on the same machine worked.

The cause was in `lpt_ops/transport.py::OperationalStore._via_authority`, which sent the statement as
`python3 ~/lpt-ops/lpt_ops/remote_sql.py --store operational --sql-b64 <payload>` in the **ssh command line**. The payload arrived truncated: a receiver on the far side reported the base64 cut to **8,056 characters**, decoding to **6,042 bytes of SQL** against **7,811 sent**. PostgreSQL's answer was then completely honest — `SyntaxError: syntax error at end of input, LINE 92`, pointing at `queries.py` line 189 — because the statement really did end there. `case_sql` grew past the cut point on 2026-10-11 when the `repair_intake_case_photos` count block was added, and `lpt ticket` has been broken for every order since. `lpt customer` kept working because its statement is small: **the bug was size-dependent, so it looked like a data problem on one order rather than a broken tool.**

Fixed by sending the statement on **stdin** (`run_ssh(AUTHORITY_SSH, cmd, stdin=sql.encode("utf-8"))`), which is how the `app` store has always sent its SQL and for exactly this reason. Pinned in `tests/test_transport.py`. Commit `0a739f6` on lpt-ops main.

**What was NOT established, and must not be claimed:** the cut is at a fixed point in the *base64* rather than at a fixed total command length — two invocations with prefixes 59 characters apart were cut identically — and the mechanism behind that was not identified. The fix removes the limit rather than explaining it.

**Rules that follow, and they generalise past this tool:**

1. **Never put a payload of unknown size in a command line.** argv has limits that stdin does not, they are not documented where you are standing, and the failure is silent truncation — the worst shape, because the far side answers confidently about a statement that is half missing. If a tool's own docstring already says "SQL arrives on stdin so it is never re-quoted", that is the house rule and every other route to the same helper should follow it.
2. **A truncated statement produces a *plausible* error, not an obvious one.** `syntax error at end of input` at a comment line was the only clue, and it was buried in a `[:300]` truncation of the helper's own error body. When a remote helper returns an error, print the whole body, not the first 300 characters.
3. **"Matched but no case" is a sentence that must never be produced by a transport failure.** A store that could not be asked and a store that holds nothing are different answers; the CLI collapses a truncated query into the same message as a genuinely absent record.
4. **When a tool that reads production returns something surprising, check the tool before believing the data.** This was 40 minutes of diagnosis that would have been 40 minutes of wrong conclusions about a customer's order — and the answer (`case_sql` is 7,811 bytes) was one `len()` away.
