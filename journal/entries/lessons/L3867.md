**L3864 · measured 2026-10-19 · The LPT computer-finder has been dead twice over since it shipped: a first-time customer cannot leave Section 1, and no stranger can find the form.**

Read first-hand from ZABZ-TECH; four-agent recon plus my own reads. Nothing below is from a report.

WHAT IS DEPLOYED (live, 19:02-19:05Z)
- Frontend is a Vite SPA, one bundle `assets/index-7P4dFGfH.js` (3,858,418 B). Every path returns HTTP 200 with the same 8,055-byte shell, so **a 200 proves nothing** — `/this-route-does-not-exist-xyz` returns 200 too.
- The questionnaire is mounted exactly ONCE in 3.86 MB: `path:"computer-finder"` as a child of the `RV` auth guard, i.e. `/customer-portal/computer-finder`. A second mount does not exist.
- Anonymous request to that URL is `Navigate`d client-side to `/customer-portal/login`. API agrees: `GET .../laptopPreference.getMy` unauth -> 401 "Customer authentication required".
- Live budget bands are the four from D72: $600-750 / $750-900 / $900-1200 / $1,200+. Grep of the live bundle: `$400` 0 hits, `$500` 0 hits, `Under $` 0 hits.
- No public page links to it. The homepage's anchors are Contact, Portal, Staff, Start a repair (/intake), plus footer services. Sitemap has three URLs: /, /privacy, /terms.
- `test.lakewoodphoneandtech.com` is a real separate deployment (bundle `index-BV498yTA.js`, API `test-api...`), same guarded route. `staging.` and `dev.` do not resolve.

THE BLOCKER, EXECUTED NOT INFERRED
- `LaptopQuestionnaireForm.tsx` `handleSectionComplete` called `savePreferenceAsync(formData)` on every Continue and advanced AFTER the await, inside the same try.
- At the end of Section 1 the payload carries every later answer as `null`; `laptopPreferenceInputSchema` refused it, so the promise rejected, the catch alerted "Failed to save your progress", and `setCurrentSection` never ran. A first-time customer could not reach Section 2, so could not submit.
- Proved by running, both ways: the new `LaptopQuestionnaireForm.test.tsx` fails 2/3 against `origin/test` and passes 3/3 against the fix. The refusal itself is pinned by `laptop-preference.budget-floor.test.ts`, which shows the Section-1 payload rejected on `budgetTier`, `usageProfile`, `batteryExpectation`.
- Why it could never have worked as designed: every required column of `LaptopPreference` is NOT NULL (schema.prisma:5172), so a partial save cannot create the first row either. Auto-save was structurally impossible, not merely buggy.

THE RECEIVING SIDE (same day)
- `POST /webhook/computer-form` on the authority: 401 unauthenticated (fail-closed; the secret IS configured — journalctl shows "Invalid computer-form webhook secret").
- It writes NO database row. `/root/authority.db` has zero tables matching computer/laptop/intake/preference/form/questionnaire/finder/lead. On success it creates a contact + a CEO task over localhost HTTP and writes three files under a CWD-relative `lpt-hub/` that does not exist on `/opt/company`.
- Newest `Computer form lead` task is id 5301 at 2026-07-01T04:36Z; newest `computer-form` contact id 523 at 2026-07-01T04:34Z. `/opt/company` was created 2026-10-10. **Zero website intakes since the cutover.**
- `app/services/computer_form_intake.py:119` maps an unknown `budgetTier` to `""`, so the research plan is generated with no budget cap and still returns 200 — the same silent-fallback family as P213.
- No cron or systemd timer pulls anything (checked crontab + `systemctl list-timers` on secratary-cloud).

THE LEGACY FORM IS STILL OPEN AND STILL OFFERS SUB-$500
- `https://docs.google.com/forms/d/e/1FAIpQLSfHZ5QEW00dPEaWpJ59dpwbcnuxN58dTR6ehX45eYiIrp679Q/viewform` -> HTTP 200, "Find Your Perfect Computer - Lakewood Phone & Tech", budget choices `Under $400 / $400-$600 / $600-$800 / $800-$1000 / $1000-$1200 / Not sure`. Three of five are at or below $500.
- It is linked from nowhere in the repos or the live bundle, and nothing ingests its responses.

RULE: "deployed" and "works" are different claims and this funnel failed both in opposite directions. The deployed one is unreachable and un-completable; the retired one is reachable, offers prices the shop now refuses, and feeds nothing. Verify the *path a stranger walks*, not the artifact's presence — and when a form saves progress, check that the progress payload is one the schema accepts, because a rejected save that sits before the advance is a form that cannot be filled in.
