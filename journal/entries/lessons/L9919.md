**L9919 · A generator that silently deletes, a hash from memory, and an exit code hidden by a pipe**

Three failure shapes hit in one session on kosher-filter-ai, all cheap to avoid and all invisible when they happen.

1. A GENERATED DOCUMENT SILENTLY ATE HAND-WRITTEN PROSE. I wrote a "Why C11 is partly" section into docs/ACCEPTANCE.md, then ran the generator's --write, and the section was gone: render() is the whole file, so anything not in the template ceases to exist on the next regeneration. Nothing failed, no checker complained, the file was simply different afterwards.
 Rule: never hand-write into a document whose front-matter says `generated`, not even a section that feels permanent. The prose goes in the generator. And after any --write, read the document back and diff your expectation against it - the only detector is looking.
 Related: this is why `check_generated_docs.py` restores the original bytes and reports rather than fixing - a check that silently rewrites is a check that silently deletes.

2. A COMMIT HASH TYPED FROM MEMORY IS A FABRICATION. Twice in one session I wrote a hash into a document before reading it: 7cb1a5c/0c0d586 (real: b3d643e/6af47c9) and 0b6f3c1 (real: f4f851c). Both caught only because I ran `git log --oneline -1` afterwards to check.
 Rule: never type a hash until the line printing it is on screen. It is the same discipline as a number: the source is the command, not the memory.

3. `Select-Object -Last N` MASKS THE EXIT CODE. `dotnet test ... | Select-Object -Last 15; "EXIT=$LASTEXITCODE"` reported EXIT=-2147450725 while the harness recorded `[exit code: 0]` for the job, because the pipeline's exit status came from the last command in it. A failing suite can therefore look like a passing job.
 Rule: when a command's exit code matters, capture output first and the code second, or run without a pipe and read the code the tool reports. On this harness an in-pipeline failure is invisible twice over.

4. AND ONE THAT WORKED, worth repeating: `gradlew :app:testDebugUnitTest` printed `UP-TO-DATE`, `BUILD SUCCESSFUL in 29s`, `1 executed, 28 up-to-date` - green, and it ran no tests at all. `--rerun-tasks` forced the real run (588 tests, 7m 42s). Always parse the XML result counts; never trust the build tool's exit code for "the tests passed".
