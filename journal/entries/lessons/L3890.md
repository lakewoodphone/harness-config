# Journal writes land in a working tree, not in the record - 19 entries of a whole session existed nowhere else

Measured 2026-10-20 at the end of a long session. Every handoff and lesson written during the day had been
appended to the PRIMARY checkout of `harness-config`, which is checked out on branch
`fleet/search-api-20261019` with 43 uncommitted journal paths. Checked id by id:

```
git cat-file -e origin/main:journal/entries/handoff/H3702.md -> fails
git cat-file -e origin/main:journal/entries/lessons/L3889.md -> fails
 ... 19 of 19, local=True onmain=False
```

So an entire session's record existed on one machine, in one working tree, on a branch nobody reads. Nothing was
lost, and nothing was shared either. `journal.py append` prints `+ H3702 -> entries/handoff/H3702.md` and exits 0,
which reads like the record was made. It was made **in that tree**.

## Why this is the dangerous kind
The failure is silent and it is flattering: `status` counts entries (4144 on that tree), `check` returns 0 errors,
`search` finds what you just wrote. Every reading is consistent because they all read the same unshared tree. The
gap only appears when you ask a question that crosses machines - and the question that crosses machines is the
one a fresh session asks.

It is also the same shape as `P3813`: a record that looks written and is not shared. An append-only journal whose
writes do not reach the shared lineage is a diary.

## The rule
**After appending anything you will need tomorrow, confirm it is on the shared branch.**
```
git -C ~/code/harness-config cat-file -e origin/main:journal/entries/<kind>/<ID>.md && echo published
```
If it is absent, copy the entry file onto a branch cut from `origin/main`, run
`journal.py --root <that worktree>/journal check`, and push to every remote the estate has.

Two things that make the copy safe, both learned the hard way tonight:
- **Check the id is free on the destination first, id by id.** Nineteen copies were safe because all nineteen were
 absent from `origin/main`; this estate has already had 73 cases where an id was not free and the collision was
 silent.
- **Rebuild the index on the branch you publish** (`journal.py --root ... index --force`) and commit it. A
 committed cache that disagrees with the tree is what made a merged journal of 4106 entries report `0 errors`
 while carrying 65.
