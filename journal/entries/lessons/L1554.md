**L1554 · When you wire an uncalled route, the new field's DEFAULT is the security decision**

Wiring an existing-but-uncalled route is the point at which a missing field becomes a security default, so the field's default IS the deliverable.

Evidence: server/app/routers/account_owner_lpt.py refused unless is_verified, and the site read past LPT's isVerified, so LptUser.is_verified had to exist. Chosen as `identity.get("isVerified") is True`, not `bool(...)`: LPT publishes a boolean, and `bool("false")` is True — a relying site that coerces would present an unverified address as verified to a route that binds by email. Cost asymmetry decides it: refusing a verified parent costs a phone call; accepting an unverified one can attach a household to the wrong family. Pinned by a parametrised test over None/False/"true"/1/"yes"/""/0.

Second rail: refuse on the near side, not by trusting the far end. The broker also refuses lpt_identity_not_verified, but the site refuses before the call, so the safety property cannot depend on the broker deployment being current. Same shape for the shared secret: unset means no call at all, rather than a call the broker answers 503 to.

Where I read the contract, so a future session does not re-derive it: server/app/routers/account_owner_lpt.py (body {lpt_subject, email, is_verified}, header x-lpt-site-secret, refusal codes lpt_subject_required 400 / lpt_identity_not_verified 403 / lpt_identity_not_linked 403 / lpt_identity_not_household_admin 403, 503 lpt_site_not_configured, 401 wrong secret), and decisions/38 D38-09a.
