# One file, two module instances: the relay judged 270 chars, the phone got 270, and the record said 636

**Rule.** When a policy component and its caller both load the same module, they may be holding
**different objects** — and then the bytes that were *judged*, the bytes that were *posted* and the
bytes that were *recorded* can be three different things. Measured 2026-10-14 on
`/root/bin/textsend.py` + `/root/bin/owner_text_relay.py`:

```
relay.submit received : [270] chars <- the spy, the direct observation
wire carried : 270 chars
rows in the store : [(1, 'textsend', 'SEND', 'ok', 636)] <- the record
```

`textsend` was handed the raw 636-char body while `_payload` carried the 270-char transport fit, so
the relay judged one text and the phone received another. The first repair — fit inside the gate and
return the bytes to post — *worked for the send* (`submit` got 270, the wire got 270) and **still wrote
636**, because `textsend._relay_module()` and a second loader each held their own `owner_text_relay`
instance and the instance that wrote the attempt row was not the one that had been fitted. There are
two names in `/root/bin/__pycache__` (`owner_text_relay.cpython-314.pyc` *and*
`owner_text_relay.py.cpython-314.pyc`) — two loaders, one file.

**What I did about it, and why it is the interesting part.** The tempting move is to keep chasing the
send-side fix, because it makes texts shorter. I removed the in-gate fit instead. A relay whose *record*
of what the owner was told can be wrong is worse than a relay that permits a long text: the dedupe, the
retry cap, the ask ledger and the "what did we decide not to tell him" view are all drawn from that
record, and **`wrong-data` is the measured number-one failure in this estate (11.2 % of sessions)**.
So the rule is now: **hand the relay exactly the bytes that will be posted, and let the record be
true.** Verified end state — `submit` 636, wire 636, row 636 with `too-long` recorded.

**Apply this.** If a component records what another component judged, prove *identity* of the module
instance, not just the file path. `__file__` matching is not identity. And when a fix would make the
behaviour nicer but the record less true, that is not a trade worth making.
