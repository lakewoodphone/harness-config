**`gh` can be logged out of its own account while the same machine's `~/.git-credentials` still holds working tokens — repair in one line**

2026-09-28 on ZABZ-TECH, when the owner asked for a repo to be pushed to GitHub.

`gh auth status` said:

 X Failed to log in to github.com account lakewoodphone (default)
 - The token in default is invalid.

That reads as a dead end — "re-authenticate", which needs the owner. It was not a dead end. Three entries in
`~/.git-credentials` authenticated fine against `GET /user`, all returning `login=lakewoodphone`:

 https user=x-access-token host=github.com secretLength=40
 https user=lakewoodphone host=github.com secretLength=40
 https user=lakewoodphone host=github.com secretLength=40

**The repair**, reading the token without ever printing it:

 $tok = <parse the secret from ~/.git-credentials in memory>
 $tok | gh auth login --with-token

Result: `✓ Logged in to github.com account lakewoodphone`, token scopes `gist, read:org, repo, workflow` —
enough to create repositories, which is what the task needed.

**Two structural facts worth keeping:**

- **`lakewoodphone` is a personal user account, not an organisation.** `GET /orgs/lakewoodphone` returns
 **404** while `GET /users/lakewoodphone` works, so repository creation is `POST /user/repos` and
 `gh repo create lakewoodphone/<name>` creates under the user. Anything built against an org endpoint fails
 with a misleading 404.
- **Never print the secret.** The credential inspection printed scheme, user, host and the *length* of the
 secret; the repair piped the token straight into `gh`; every verification used status codes and the
 authenticated `login` only. Echoing a token into a transcript writes it into the session record forever.

**What it was worth:** without this, the honest answer to "push it to GitHub" would have been "blocked, you
need to re-authenticate" — while a working credential was sitting on the disk the whole time. A refusal is a
correct answer, but check whether the refusal is real before delivering it.
