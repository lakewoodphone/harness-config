**L2123 · date_sent holds two date shapes in one TEXT column, so every SQL comparison on it lies -- including MAX**

**Measured 2026-09-20 on the live AI-line store (`~/.sms-inbox/inbox.db`) on secratary.**

`messages.date_sent` is `TEXT` and holds **two different formats**:

```
Fri, 18 Sep 2026 03:29:39 +0000 <- Twilio's RFC-2822, from the sensor's sync
2026-09-18T04:02:51+00:00 <- ISO, written by our own senders
```

Every SQL text comparison on that column is therefore wrong, and wrong **silently**:

- `MAX(date_sent)` returned `Wed, 29 Jul 2026` while the true newest message was
 `Fri, 18 Sep 2026` — a **2-day-old store measured as 53 days stale**, because SQL was
 sorting by weekday name.
- `ORDER BY date_sent` in the responder's worklist answered people in a non-chronological
 order.
- `WHERE date_sent > '2026-09-20T15:30'` counted rows from `08:...` as later than `16:...`,
 because `T` (0x54) sorts above a space (0x20).

**The rule.** A TEXT column that holds dates from more than one producer is not a date
column; it is a string. Parse it before comparing — `email.utils.parsedate_to_datetime`
with an ISO fallback — and sort in Python. Better still: never let a second producer write
its own format. This is the same family as `journal P12` (a reading whose freshness is
asserted rather than measured): the number looks fine, and it is measuring the alphabet.

**Where it was fixed:** `sms-inbox.py` (`parse_dt`, `probe`, `report`),
`sms-responder.py` (`worklist`), `textctx.py` (reports `store_freshness` separately so
sensor staleness stays visible). `textsend.history` still orders by the raw column, which is
cosmetic ordering of a display list only.
