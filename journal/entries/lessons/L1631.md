**L1631 · A shebang on a test-imported module makes Vite skip the whole test file while node --check still passes**

## L - A `#!` shebang on a test-imported module silently deletes that file's tests under Vite

**What happens.** A `.mjs`/`.ts` file that starts with `#!/usr/bin/env node` parses fine under
`node --check` and runs fine as a script. But if a **test imports it**, Vite's transform parser
throws `SyntaxError: Invalid or unexpected token` and Vitest reports the *importing test file* as
a failed **suite** - not a failed test. The output then reads like a flake:

 Test Files 1 failed | 27 passed (28)
 Tests 297 passed (297)

297 tests passed, so it looks almost fine. In reality one whole file contributed **nothing**, and
`node --check` on the offending file passes, so every "does it parse?" check you would naturally
reach for says the tree is healthy. Node strips a shebang (ESM spec, hashbang comment); Vite's
parser does not accept one in a non-entry module.

**Measured twice on 2026-09-15**, both in `personality-system`:
1. `scripts/verify-model-chain.mjs` - hid 22 tests. Original symptom recorded as "1 failed | 19
 passed, Tests 201 passed", which I first assumed was flakiness.
2. `scripts/assessment-db-admin.mjs` - hid an entire new 4-test backup file.

**The rule.** A module that any test imports must NOT have a shebang. Either drop it (run the file
as `node script.mjs`; executable-bit convenience is worth less than the tests) or keep the
executable entry point as a thin wrapper that imports the real module.

**How to detect it.** Do not trust `node --check`. Check for the pattern directly:

 # any file with a shebang that is imported by a test or src file
 grep -rl '^#!' --include='*.mjs' --include='*.cjs' --include='*.ts' . | while read f; do
 git grep -l "$(basename "$f")" -- 'src/**/*.test.ts' 'src/**/*.mjs' || true
 done

Cheaper: after any `vitest run`, count `Tests` against the number of files and check for
`Failed Suites`. A failing *suite* with 0 failed *tests* is nearly always a parse error, not a test
failure - read the error text literally instead of re-running and hoping.

**Also fix the generalisation:** when a test count goes DOWN or a suite fails with zero failed
tests, treat it as a parse/transform failure until proven otherwise, and never dismiss it as a
flake just because it does not reproduce. The invisible-parse-error class is exactly what makes a
green suite lie.
