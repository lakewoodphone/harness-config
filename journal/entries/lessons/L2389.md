**L2389 · Twilio status 'sent' is not delivery - check sms_log.to_number before believing the owner's account of a failed send**

Measured 2026-09-22, owner asked me to re-send a CVS-thermometer text 'to my personal line instead' because the version sent to his wife's phone had not gone through.

What the record actually showed: sms_log id 902, written 2026-09-22T17:57:24Z, from +17324447361 to +17325691594, status='sent', error_message=NULL. I checked .env on the authority: OWNER_PHONE_NUMBER=+17325691594. So the 17:57 copy was ALREADY addressed to the owner's own personal line, not to his wife. His account of the failure (her phone/service) and the row's to_number disagreed, and the to_number is the authoritative one.

Two transferable rules:
1. Twilio's 'sent' means handed to the carrier at the API boundary, not delivered to a handset. A row that says 'sent' with a NULL error_message is therefore consistent with the owner never seeing the message - do not argue with him from that column. Resending is the correct action and costs a duplicate at worst.
2. Before acting on 'send it to X instead', read sms_log.to_number for the original. Here the action was identical to what was already recorded, which is worth knowing: it means the earlier attempt was not mis-addressed, so the real fault is downstream of the API (carrier/handset/AI-line routing), not in the address.

Send path used: scripts/ps_mcp_server.py ps_action('send_sms', {to, body}) -> POST /api/v1/actions/execute -> app/chat_action_runtime.py:_exec_send_sms (Twilio; owner-only guard honours OWNER_PHONE_NUMBER). Result: SID SM243c88b54e539d5817e6cbb03247a685, detail 'Sent to +17325691594', verified as sms_log id 903 at 2026-09-22T18:48:43Z status='sent'. format_agent_sms_body appended '- Daniel' automatically - do not add the signature by hand or it doubles.

Separate defect found while reading the path, NOT fixed: ps_mcp_server.py on the authority defines ps_action without the owner_direct_request flag (grep for 'owner_direct_request' in that file returns nothing), while main.py:10153-10173 documents that the MCP ps_action tool sets it. So an owner-initiated send through MCP is executing as a non-direct request and is subject to the 10-minute near-duplicate suppression in _exec_send_sms (chat_action_runtime.py:1917), which returns success=True with data.dedup=true while sending nothing.
