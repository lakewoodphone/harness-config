**L6253 · E4610 outbound MMS measured live: send fails and receive works because the submit has no MMS user agent - and how I twice published a cause the next measurement refuted**

**L · 2026-10-15 · ZABZ-TECH · E4610 outbound MMS: a live handset measured end to end, and the one mechanism that survived every elimination**

Context: owner brought a customer E4610 (serial 615387849) that "cannot send picture messages", relayed the customer's
clarification that **receiving always worked and it was only sending that was hard**, and gave explicit permission to
test against it. Everything below was measured on that handset, read-only except two stated changes.

**Eliminated, with evidence:**
- Not the network / data plane: validated LTE, `VZWINTERNET` + `VZWIMS` + `VZWAPP`, working DNS.
- Not the MMS APN: it comes up on every attempt and gets an IP (`registerNetworkAgent ... VZWAPP`).
- Not the SIM or the number: reproduced on the old US Mobile SIM and on a **direct Verizon SIM**.
- Not our filter's messaging disables: `com.android.mms` is absent from E4610 by design, Message+ is enabled, not
 stopped, and holds `RECEIVE_MMS`/`READ_SMS`/`SEND_SMS` as `granted=true SYSTEM_FIXED GRANTED_BY_DEFAULT`.
- Not our modified app: the installed APK hashes to the pristine `tools/apks` copy (`DD7551D3DB5BCED1`).
- Not the app version or a corrupt install: force-stop did not change the behaviour.

**What the phone actually does when you press send:** Message+ requests the MMS network and **releases it ~1.05 s
later** — on US Mobile, three attempts at 1.05/1.09/1.08 s, once releasing *before* the APN had finished coming up.
On the direct-Verizon SIM the same calls were held **16.7 s** and one stayed held past **50 s** against a 60 s socket
timeout. So the two carriers differ, and a held-then-timeout request is a different failure from an instant abort.
It accumulates orphaned MMS network agents — **10 at one point**, against a healthy 1; a reboot took it to 4.

**The mechanism that survived every elimination — the device profile is empty:**
```
MmsService: mms config for sub 4: Bundle[{ ... userAgent=, uaProfUrl=, uaProfTagName=Profile, ... }]
CarrierConfigLoader: mConfigFromCarrierApp = null
 mConfigFromDefaultApp = PersistableBundle[{ ... uaProfTagName=Profile, ... no userAgent, no uaProfUrl }]
```
Empty on the MVNO **and** on direct Verizon. `MmsConfig.loadUAFromTelephony` (smali `MmsConfig.smali:1987-2003`) sets
the UA and UAProf **only if both are non-empty**; the hardcoded fallback `vzmmms1.0` (`:1880-1882`) is reached only
on a **non**-VZW device. So on this Verizon device the submit goes out with **no MMS user agent and no x-wap-profile**,
while a *download* needs neither — the notification carries a pre-authorised URL. That is the only mechanism found
that separates send from receive, which is exactly the customer's complaint. `com.android.carrierconfig` is present,
enabled, and in **neither** bloatware list, so this is a device/carrier-config property, not our doing.

**Not proven:** that the MMSC actually refuses the submit for want of the profile. The one-second cycle is too fast
for a 60 s timeout, which fits a fast refusal, but no wire capture exists. The decisive test remains a **second
E4610 on the same MVNO** attempting the same send.

**Corrections made to my own tooling and claims, all caught by running it:**
- My device-state check threw "not in device state" at a phone adb reported as `device` — the pattern demanded
 whitespace before the serial while `adb devices` is TAB-separated with the serial leading. Fixed in both scripts.
- `date +%s%3N` is unsupported on Android 7 toybox (emits a literal `N`), so my "clock skew" was a parse artefact;
 the phone's clock was correct all along. Fixed.
- I twice attributed the failure to something the next measurement refuted: the `com.android.smspush`
 "no receiver app found" line (it appears once per MMS notification and Message+ still requests the network itself,
 so it is the legacy path), and then the user-agent theory (I called it weakened when the abort was fast — it is
 now the surviving explanation). **On a live diagnostic, one observation is a hypothesis, not a finding.**

**Transferable rules:**
- When the symptom is "send fails, receive works", the differentiator is the *submit* — which is the only MMS step
 that needs the device profile. Check the MMS user agent / UAProf before anything else.
- Read `dumpsys carrier_config` when an MMS profile is missing; `mConfigFromCarrierApp=null` plus a default bundle
 without the UA key names the cause precisely.
- Count the orphaned network agents for the APN in question (`dumpsys connectivity | grep <APN>`). A healthy phone
 holds one; ten means wedged telephony state, and a reboot is the fix.
- On Android 7, `content://mms` and `content://carriers` are unreadable from shell (`SecurityException`, needs
 `READ_SMS` / APN write permission), so the message store and APN table have to be inferred from logs.
