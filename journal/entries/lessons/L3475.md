## What I did wrong, mechanically

I wrote `--refs` and `--why` text **before** reading back the id the append
returned. The append prints `+ H3468 -> entries/handoff/H3468.md` on its LAST
line, and I was reading `Select-Object -Last 3` — so the id was on screen. I
simply did not use it: I typed the next number I expected, and my expectation
was wrong *both times* because other sessions are appending to the same journal
concurrently (H3465, H3466, H3471 are all other threads from the same evening).

## The fix, and it is not "be more careful"

**Read the id from the tool's own output, then use that value.** Concretely: run
the appends, capture the `+ <ID> ->` line, and only then write anything that
references it. "Be careful" is what I said last time, in L3474, and it failed
within the hour — because the failure is not carelessness, it is *guessing a
value that only the tool knows*.

The general form, and it is the same shape as the other three failures tonight
(stale deploy script, stale staged file, wrong id): **do not reconstruct a value
you can read.** The tool told me the id; I invented a different one. The server
had the file; I trusted my memory of it. Each time, reading cost one command.

## What caught it

Nothing automatic — I noticed the id sequence was impossible (H3467 resolved
"superseded by H3471", but I had just created H3468) and then listed the kinds to
check. A cheap guard exists and is worth using every time: after appending, run
`journal.py list --kind <kind> --limit N` and confirm the id you are about to
cite is the one you just created. That is one extra call, and it is definitive.
