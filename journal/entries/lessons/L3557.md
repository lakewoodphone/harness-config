**L3557 · Organizing a recovered drive: three dedupe signals are needed (hash, name+size, size alone for large files), readability outranks folder pedigree, and set membership is not content equality**

**Measured 2026-10-08** on the Kogel set (300DDR ticket 73459, `D:\73459`, 684,365 files / 764.801 GB recovered from one 256 GB device). Four separate traps, each of which produced a wrong deliverable until it was caught, and each of which will recur on the next recovery job.

## 1. Three dedupe signals are needed, not one — and the second is the one everybody misses

| signal | what it catches | what it cannot see |
|---|---|---|
| sha256 equality | the same file found again | the same file **re-read** with different bytes |
| normalised name + exact size | the same file re-read | the same file under a **genuinely different name** |
| exact size alone, large files only | carve-named twins | small files, where a size match is coincidence |

hash-dedupe alone left **438.15 GB of "distinct" content off a 256 GB device** — physically impossible, which is the tell. Adding (2) took it to 247.56 GB; adding (3) for video took it to 240.83 GB. The device capacity is the error bar: **if your "unique" total exceeds the source device, your dedupe is wrong.**

The lab wrote several reconstructions of one 3,368,736,448-byte film into one folder and disambiguated the names itself: `~VI_8842.MP4`, `~VI_8842(1).MP4`, `_VI_8842.MP4`, `_VI_8842 1.MP4`, `_VI_8842 2.MP4`, `_VI_8842 3.MP4` — six files, six different hashes, one film. A hash cannot see it.

## 2. Normalisation is where you silently destroy data

Stripping a trailing digit to catch the lab's ` 1`/` 2` disambiguation suffix **must be restricted**, and the separator matters. `UND = re.compile(r"[_ ](\d+)$")` matched the underscore inside `VI_8842` and collapsed `VI_8842`, `VI_8583`, `VI_8749`, `VI_8588`… into a single family of **334 different videos**. Space only (`r" (\d+)$"`) is correct: the lab's suffix is `_VI_8842 1.MP4`. **Always print the largest families your rule produces and eyeball them before trusting it** — that check is what caught this.

## 3. Prefer the copy that OPENS, before any folder pedigree

The first build ranked copies by "did it survive with its original name and folder" and only then by content. Result: **583 families kept a re-read that does not open while throwing away one that does**, including the largest videos. Golembick's organizer had this right (it preferred intact JPEGs); this build omitted it.
Order that is now used, first key first: **(1) opens / unknown / does not open, (2) original-name-and-folder pedigree, (3) shorter path.** Kept-readable went 1,547 → 2,130 of 3,478 merged families.
Also gate the check to multi-member families only — running it per scheduled copy (167,926 of them) turned seconds into minutes.

## 4. Set membership is not content equality — the repair bug

A repair compared the built tree with the corrected plan **by path**: `missing = new − old`, `remove = old − new`. Where the new plan wanted a *different file at a path the old build had already filled*, the path was both "present" and "planned", so neither branch fired and the superseded file stayed. Verification caught it: **171 files holding the wrong bytes**, while reporting 0 missing and 0 unplanned.
**A reconciliation must compare the intended content hash, not merely that a path exists.** This is the same shape as the estate's worst historical failure — a reading that was true of the index and false of the thing.

## 5. Count large trees with `os.walk`, never `Get-ChildItem -Recurse`

PowerShell's recursive count returned **163,085** where `os.walk` returned **163,086** on the same tree, and 135,415 vs 135,416 for one folder. Python was right and PowerShell was the one lying; a `-ErrorAction SilentlyContinue` hid whatever it tripped on. Any count used to prove "nothing is missing" must come from a tool you have cross-checked against a second one.

## 6. Verify, then do not be surprised that verification failed

The two-sided hash verification ran 2,023 s and returned **FAIL, 171 files wrong**. That is the process working. A build that has never failed a check has not been checked hard enough — and the failure was in *my repair*, not in the underlying data, which is exactly the class of error a hash comparison exists to find.

## 7. Photo libraries and document archives want different structures

Golembick's set was a family photo library → filed by year taken. Sampling Kogel's 309,874 images found `Slide104.JPG` (PowerPoint), `MX-M753N_20110905_235640_Page_08.jpg` (a Sharp copier scan), `WorkCentre 7132 …tiff` (Xerox scan), `shutterstock_*` and `BEBEGGSCLP.JPG` — a Torah publishing and teaching archive, not photographs. **Year folders would have scattered one library across meaningless dates**, since most of those files have no EXIF at all. The right move was to **preserve the customer's own recovered folder names** (185 of them, e.g. `Rebbe Files`, `ספר בראשית`, `Class coloring '86`, the parashah sheets, the melachos) and file only the folderless material by type. **Sample the content before choosing a taxonomy.**
