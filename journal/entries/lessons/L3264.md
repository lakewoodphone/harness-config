**L3264 · Deployed and healthy is not advertiseable: four checks before telling the owner something is ready**

## L — "It's deployed and healthy" is not "it can be advertised"

Measured 2026-10-05 on `chumash.lakewoodphoneandtech.com`, an app that was genuinely finished: 0
`og:` tags, 0 `twitter:` tags, no canonical link, no `og.png`, `/robots.txt` 404, `/sitemap.xml`
404, and no record anywhere of whether a single human had ever loaded it.

None of that is visible from a health check, a test suite, or `docker compose ps` — all of which
said, correctly, "healthy". The gap is between *the app works* and *the app can be announced*, and
it is a checklist, not a judgement call:

 1. Does a link to it preview with a title, a description and a picture? (`og:` + an image)
 2. Can a crawler find and index the pages? (robots, sitemap, canonical)
 3. Is there a number to check afterwards? (any page-view counter at all, and *where the traffic
 came from* — a count with no referrer cannot tell you which post worked)
 4. Will anyone find out if it goes down while money is being spent pointing at it? (uptime)

Four items, all cheap, all invisible to a green test suite. Run them before telling the owner a
public-facing thing is ready to advertise — and run them by *fetching the live URL and reading the
response*, because three of the four were only discoverable there.

Second lesson from the same session: **a cron that logs is not a cron that alerts.** The
deterministic site-uptime check had been running hourly and writing `RESULT: all endpoints up`,
and the site it did not cover could have been down for a week without a single human noticing. When
adding coverage, add it to the monitor that already exists — one monitor, one place — and prove it
ran by reading its log, not by trusting the edit.
