**L3245 · dsh-update: a verdict that does not name the config it judged can gate this deployment, and on 2026-09-28 one did**

MEASURED 2026-10-05. `state/candidates/<version>/*.json` is where every verdict about a candidate
lands. The pipeline is DESIGNED to judge a staged config, so the same filenames are written by a real
run and by a test run — and nothing recorded which home a verdict came from.

On 2026-09-28 a test suite pointed `DSH_HOME` at
`%TEMP%\switch-rework-20260928T203232Z\staged-home` — a synthetic home built from fixtures — and
overwrote the authoritative artifacts. The stored `patch-effect.json` still reads today:

 our patch layer C:\Users\ezabz\AppData\Local\Temp\switch-rework-20260928T203232Z\staged-home\
 profiles\web\cordis.patch.yml entry 2 targets row id "remote-fanout"

`status` then reported `0.1.7-rc.2 verify=FAIL`, `preflight` reported NO-GO, and
`tests/switch/README-rework.md` recorded that the repository's real preflight was NO-GO "for reasons
that have nothing to do with the switch". Every one of those statements was about a fixture, presented
as a statement about this machine. That is the P3 failure mode — reading the wrong data and believing
it — built into the tool: an anonymous judgment cannot be checked, only believed.

FIX. `lib/artifact-provenance.mjs` stamps a `configIdentity` into every artifact a judging verb writes:
`{schemaVersion, dshHome, liveConfigHome, kind, temporary, profile, host, at}`. `cli.mjs` `main()`
stamps in ONE place, so a new verb cannot be added without it. `kind` is DERIVED (live iff `dshHome`
resolves to `~/.dsh`), never passed — a caller that could label its own run `live` could launder a
fixture verdict. Re-stamping an artifact with a DIFFERENT home throws, so two verdicts about two configs
cannot become one because they share a filename.

`promote` gained condition 5, and `preflight` a blocking `artifact provenance` guard: artifacts must
name a home, must agree with each other, must not be under a temp root, and preflight's must name the
home preflight ran with.

"Under a temp root" deliberately checks SEVERAL roots. Measured 2026-10-05: a DSH child process sees
`os.tmpdir()` as `C:\Users\ezabz\.dsh\tmp` (the engine redirects TMP/TEMP into its own home) while the
fixture sat at `C:\Users\ezabz\AppData\Local\Temp\...`. Keying on one root would make the detector
answer differently depending on which process asked, and a fixture detector that varies with the caller
is not a detector.

HELD BY: `dsh-update/tests/guards/provenance.mjs`, 28/28 assertions.

EARNED IMMEDIATELY, in the first real run after the fix: `preflight 0.1.5-rc.3 --full` showed that
0.1.5-rc.3's stored `verify.json` was STALE (contract on disk had changed since it was produced) and
carried only SIX gates — G1, G2, G3, G4, G5, GFULL, with no G8 at all — i.e. it was produced by an
older `verify.mjs`. `FINDINGS.md` still described that candidate as "SAFE, verify pass=true"; the
pipeline now refuses it. A verdict recorded as good can be quietly invalidated by a change to the
pipeline that produced it, and only a recorded contract hash plus a gate-set check catches that.
