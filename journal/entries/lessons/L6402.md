**A machine being unreachable is not the same as a machine being unreachable from where you stand.**
`ssh zabz-tech` from ZABZ-YOGA resolves to `192.168.50.138` — the office LAN — and times out, while the
same name from `secratary-cloud` connects over Tailscale. The two are on different networks and
Tailscale is the only path between them, so the authority is the jump, not the laptop. **The first
attempt tonight recorded "ZABZ-TECH is unreachable" from the machine that cannot see it, which is the
same defect as reporting a path you did not check as an absence.** It was reachable the whole time.

**The patch is applied by `scripts/evolution/apply-cross-tree.py`, run with the authority as the jump
host** (`bash /root/work/r8/patch-tech.sh`). Inner `ssh` calls use `-n`, because an inner ssh that
inherits a script's stdin eats the rest of the script and the run stops silently partway — measured
earlier tonight, and the reason that script is a file on disk rather than a heredoc.

**Nothing runs this on a clock yet.** The rule's whole value is that a forked store cannot answer
0 errors, and it only does that when somebody passes `--cross-tree DIR`. Choosing to schedule it —
and against which trees — is part of the writer-model decision, because the set of trees to compare
against is the set of writers.

**And the reading depends on the baseline.** 587 on the canonical tree is the repair's renumbering
measured against pre-landing snapshots, not a fresh fork; the pre-landing fork was 524 on the same
instrument. ZABZ-TECH's 64 and the mac's 128 are differences against *other local checkouts of older
dates*. **None of these numbers is "the fork size" unless it is measured source-against-source on the
same day** — the count only means something as a change from a stated baseline.
