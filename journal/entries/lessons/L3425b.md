**L3425b · The authority moved to the cloud on 2026-10-11; installing on the office box put the work on the rollback anchor**

MEASURED 2026-10-13. `sentinel-freshness-check.py`'s own header on
`secratary-cloud` records it: *"The company's authority moved from the office box
to the cloud box at 2026-10-11T05:43:36Z ... [the office box] was then frozen as
the rollback anchor."*

That single fact invalidated the shape of a whole night's work. I built the
owner-attention pipeline, the email sweep and the books timer on `secratary` -
because that is where `books.db` lives (28 MB), where the app's `secretary.db`
is (18.5 GB), and where the kernel could actually read a database. All of it was
correct, scheduled, and **running on the rollback anchor**.

HOW THE TWO BOXES ACTUALLY DIFFER, measured:

| | office `secratary` | cloud `secratary-cloud` |
|---|---|---|
| role | frozen rollback anchor | the live company |
| cron | `cron.service` masked 2026-10-11T20:23Z | running |
| work loop | last tick 2026-10-11T20:17Z, nothing since | ticking |
| comms index | 29.6h stale (frozen) | 0.13h fresh |
| company SQLite | `/home/zabz/personal-secretary-mvp/data/secretary.db`, 231 tables | `/root/authority.db`, 231 tables |
| books store | `/home/zabz/accounting-data/books.db` | **absent** |
| `uptime` | 1 day 23h | 12h |

THE TELLS I SHOULD HAVE READ EARLIER. The kernel said *"reading the authoritative
database on secratary"* while `ck` on the cloud said *"no usable database
found"* - two kernels disagreeing about which box is the authority is not an
ambiguity to work around, it is the finding. And the kernel claimed `liveness
[ok] ticking: newest tick 0.0m ago` on a box whose newest tick was a day and a
half old: a liveness check reading a **production database that a frozen process
was the last writer of** answers a different question than the one asked.

WHAT TO DO WHEN THERE ARE TWO OF SOMETHING. Do not pick the one named in the
instruction. Find who writes, and read the writer's clock:
`systemctl list-timers --all`, the newest row in the busiest table, and any
script whose own header describes the migration. Then deploy where the writer is,
and say plainly in the report which host got what and why.

THE PRACTICAL CONSEQUENCE, now handled: the cloud has no books store, so the
digest's `from_obligations()` reads the `obligations` table from the office box
over ssh into a small local mirror, refreshed on every digest run by an
`ExecStartPre`. `books_mirror.py` rebuilds from scratch each time and prints the
row count and the newest `due_on`, so a stale mirror cannot be read silently -
which is the failure this estate has paid for more than once.
