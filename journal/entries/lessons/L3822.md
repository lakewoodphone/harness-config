**L3822 · A repo that configures a live filter is not the filter that is running**

**L · A repo that configures a live security filter is not the filter that is running — read the container**

WHAT HAPPENED, measured 2026-10-14 while working out why Waze voice input fails. `deploy/waze-mdm/dns/doh_filter.py`
and `docker-compose.yml` in `personal-secretary-mvp` list the broad Google roots as blocked — `googleapis.com`,
`gstatic.com`, `googleusercontent.com`, `ggpht.com`, `gvt1.com`, `gvt2.com`, `app-measurement.com`. The running
container on `waze-mdm-01` (`docker exec waze-mdm-dns-filter-1 env`) blocks **none of them**, and *allows*
`gsp1.apple.com`, `gsp10-ssl.apple.com` and `gsp53-ssl.apple.com` which the repo lists as blocked. It also allows
`bag.itunes.apple.com`, `ls.apple.com`, `location.services.apple.com` and `gs-loc.apple.com`, which appear in
neither repo list.

Consequences: the production filter was hand-tuned away from the repo and never written back, so the file that
documents the filter is a description of a device that does not exist. And it changed a diagnosis — a Google-hosted
Waze speech recogniser looked blocked *by the code* and is probably not blocked at all.

RULES:
1. **For anything that is a live control surface — a filter, a proxy rule, a firewall, an allowlist — read the
 running instance, not the file.** State which one you read; they are different facts.
2. Drift between a repo and its production instance is not a docs bug, it is an **unrecorded change to the
 security posture**, and it belongs in the record with a date.
3. Where drift exists, it invalidates every argument that reasons from the file, including arguments already made
 by other sessions and by the docs in the same tree.

EVIDENCE: `deploy/waze-mdm/docs/voice-input/evidence/live-dns-filter-20261014.md` vs
`deploy/waze-mdm/dns/doh_filter.py` (master `f585413b9`); read live 2026-10-14 14:32Z.
