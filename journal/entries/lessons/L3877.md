**L3877 · Three deployments reported success and never landed - git merge was blocked by scp'd files and I piped its error away**

**Three deployments reported success and never landed, because `git merge` was blocked by files I had scp'd and I piped its error away.**

On 2026-10-19 I shipped three changes to the search service and measured each one: a name-coverage
prior, a multi-word name index lookup, and a name band. **All three were no-ops.** The benchmark that
measured them did not move — hit@1 1/12, hit@3 2/12, three times in a row — and I explained each null
result as "the prior is too weak", which was true and irrelevant, because the code had never reached
the running process.

What actually happened, read afterwards from `git reflog`:

```
81553b1 HEAD@{0}: merge origin/main: Fast-forward <- the last merge that ever happened
```

The commands I ran were:

 cd /root/code/unified-search && git fetch -q origin && git merge --ff-only origin/main 2>&1 | tail -1; echo rc=$?
 … Updating 81553b1..c26e784 # <- this line came from `git fetch`, not from `git merge`

`git fetch` prints `Updating <old>..<new>` when it moves a remote-tracking ref. The merge itself was
refused — `error: Untracked working tree files would be overwritten by merge` — because I had `scp`'d
`scripts/prune-central.py`, `scripts/relevance-eval.py` and `config/eval-questions.json` onto the box
*matching* files that the merge wanted to create. `2>&1 | tail -1` showed me the fetch line and hid the
refusal, and I never looked at `$?`.

Three rules, all of which this violated:

1. **`2>&1 | tail -1` on a command whose exit code matters is the same mistake as not checking at all.**
 The pipe makes `$?` the exit of `tail`. Capture the code with `PIPESTATUS` or run the command
 plainly.
2. **Never `scp` a file into a path that a repository tracks.** It creates an untracked file that
 blocks every subsequent fast-forward, silently and permanently, until someone moves it. Copy to
 `/tmp`, or commit and deploy by git — which is what `deploy/README.md` has said since 2026-10-18.
3. **"Deployed" is a claim about the process, not about git.** The check is
 `git log --oneline -1` **in the checkout the unit runs from**, plus one grep for a string the new
 code introduced. `grep -c "A NAME IS NOT ALWAYS ONE WORD" server/esearch.py` returns 0 on old code
 and 1 on new — one command, and it would have caught all three.

The tell was there in the data: **three different code changes produced byte-identical scores**. One
null result is a hypothesis; three identical null results are a broken measurement, and the
measurement to check first is whether the change is running.

Refs: journal H3668; `unified-search` commits `64d0a1c`, `c26e784`, `4df8566`, `7341eab`; the
blocking files were moved to `/root/_blocked-merge-20261019/`.
