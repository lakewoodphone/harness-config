**L3378 · An idempotence claim that was never tested is not a claim: the second import sent the customer the same message twice**

GOAL ROUND 24. I built the missing half of the survivor's promise. 'Capture inbound, queue outbound' was verified on both halves - an inbound SMS is recorded, a send is held - but BOTH land in the survivor's OWN copy of the database, and the office has a DIFFERENT file. Nothing carried the capture back, so a customer message received during an outage would have been answered by nobody and noticed by nobody: the promise was half built, and the missing half decides whether the customer ever hears back. company-handoff.py closes it: export the inbound sms_log rows and the unsent outbound_buffer rows from the survivor, import them into the authority, and deliberately REFUSE to move outbound sms_log rows (a survivor does not send, so such a row records something it did not do - importing it would tell the primary 'already answered' and stop it answering, which was itself a bug found in round 11). THE REHEARSAL FOUND TWO BUGS, AND THE SECOND ONE IS THE LESSON. (1) sms_log.updated_at is NOT NULL, so a row carrying only created_at failed the insert - losing the capture. Fixed by backfilling NOT NULL columns SEMANTICALLY: updated_at from created_at, and next_retry_at to NOW, because a held send must become SENDABLE at the authority - filling it with created_at or refusing the row would send it late or lose it. (2) I wrote the dedup check for sms_log only, so re-importing the same file INSERTED THE HELD SEND AGAIN: the customer gets the same message twice. I only caught it because I ran the import a SECOND time - the first import looked perfect, and a single-run test of an idempotence claim proves nothing at all. Fixed by building the existing-key set generically for every table in the map. VERIFIED: import 1 -> 2 inbound + 1 held send inserted; import 2 -> 0 inserted, 3 duplicates skipped. RULES: (a) if you claim idempotence, the test IS the second run - run everything twice; (b) a dedup check must cover every table it is supposed to protect, because a check that covers one of two is a bug waiting for the second; (c) when you move rows between two copies of a database, key on a NATURAL key, never on rowid - rowids collide between copies of a seeded file; (d) a data path between two hosts is not finished when both ends work, only when the data ARRIVES and is provably not duplicated.
