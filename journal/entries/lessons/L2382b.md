**L2382b · 48 tests passed while typecheck failed - a green suite is not evidence the build compiles**

**Rule:** a green unit-test suite is NOT evidence that the code builds. Always run the typecheck (or compiler) separately, and treat a non-zero exit as the failure even when every test passes.

**Measured 2026-09-22, W1 Stripe metered-billing engine (`phone-and-tech-full`, branch `waze/stripe-metered-billing`, WIP commit 03df5467f):**
- `pnpm test:backend:one -- backend/src/services/waze/waze-billing.service.test.ts` -> **`Tests 48 passed (48)`**.
- `pnpm --filter phone-and-tech-backend typecheck` -> **`exit status 2`**, three real errors, one of them fatal in production:
 `error TS2339: Property 'createUsageRecord' does not exist on type 'SubscriptionItemsResource'`.

The 48 tests mocked the boundary, so the suite never touched the Stripe client's real shape. The code called a **legacy Stripe API that does not exist in the installed SDK (stripe 19.2.0)** - so on a live run the usage report would have thrown. The agent that wrote it had been told to verify the installed version rather than assume, and did not.

**Also measured:** `stripe.subscriptionItems.createUsageRecord` is **gone** in v19; the supported path is **Stripe Billing Meters** (`stripe.billing.meterEvents.create`, present at `node_modules/stripe/cjs/resources/Billing/MeterEvents.js` and `Meters.js`). A meter needs an `event_name` configured in the Stripe account, so metered billing is not a drop-in swap - it needs an account-side object plus config.

**The order of verification that catches this:** typecheck FIRST, then tests. I ran tests first and got a green line, which is exactly how a false success is manufactured. The `--filter ... typecheck` also needs `pnpm --filter @phone-and-tech/shared-types build` first in a fresh worktree or it fails with 22x TS2307 and looks like a different problem entirely.

**Generalisation:** mocks make a suite green about *your* logic; only the typechecker and a real integration call tell you the boundary exists. For any code calling a third-party SDK, verify the SDK version and the method's presence in `node_modules` before believing a test.
