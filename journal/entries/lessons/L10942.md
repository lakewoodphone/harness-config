**L10942 · Phone 'agent preset invalid' fixed: on 0.2.1 a preset is a ROW and one unstartable row breaks the whole preset - dsh-tool-ralph and dsh-mcp-client were transitive in the 0.2.0 profile and vanished when it was reinstalled at 0.2.1; pin them explicitly and the registry is clean (proven by session/create ok:true)**

CAUSE AND FIX, 2026-10-20 13:04Z. The phone refused new sessions with "agent preset invalid" because the engine's
preset registry reported every local preset as BROKEN:

 zabz broken: mcp-secretary-linux (@deepseek-ai/dsh-mcp-client): never started
 tool-ralph (@deepseek-ai/dsh-tool-ralph): never started
 yocheved broken: mcp-secretary (dsh-mcp-client): never started, tool-ralph: never started
 cordis-bg broken: tool-ralph: never started

On 0.2.1 a preset is a ROW whose `config.plugins` is that preset's own row list, and if ANY row in it cannot start the
whole preset is marked broken and the UI refuses to open a session with it.

WHY THOSE TWO ROWS DROPPED: `@deepseek-ai/dsh-tool-ralph` and `@deepseek-ai/dsh-mcp-client` were present in the
0.2.0 profile tree as TRANSITIVE dependencies — they were never named in the profile's package.json. When the profile
was reinstalled at 0.2.1 from its own dependency list, they were not part of it, so the rows resolved to nothing and
"never started". The packages exist in the ENGINE tree at 0.2.1; the profile just could not resolve them.

THE FIX, and it generalises to any host: enumerate every `name: "@deepseek-ai/..."` inside the `preset-rows` block,
check which of those the PROFILE tree cannot resolve, and pin exactly those at the engine's version
(`npm install` then re-create the canonical dsh-scope path the unit's ExecStartPre gate needs). Done here:
`dsh-mcp-client` + `dsh-tool-ralph` at 0.2.1-rc.2. The registry now reads:

 standard no · ptc no · minimal no · cordis no · cordis-bg no · yocheved no · zabz no (default)

PROVEN END TO END, not inferred: through the phone gate, with the visitor cookie it signs for a cold client,
`session/create` returned `ok:true` and `{sessionId: session-55aabbd7…, agentPreset: zabz}`. A new session opens.

THE DIAGNOSTIC WORTH KEEPING: `agentPresets/list` through the gate is the fastest way to see this class of failure —
each preset's `broken` field names the row and the package that did not start, which is far more useful than the
"agent preset invalid" the UI shows. Reach it with:
 curl -c cj -o /dev/null http://127.0.0.1:3086/ ; then POST /api/agentPresets/list with
 {"type":"client-request","rpcId":"1","method":"agentPresets/list","payload":{"args":{}}} and the cookie.
Two empty test sessions were left behind (session-55aabbd7…, session-6a2805a6…) because there is no
`session/dispose` endpoint; they are empty and harmless.
