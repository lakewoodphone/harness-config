**L2059 · A passing test suite is not a build - 196 green host assertions, and it had never compiled for the chip**

**L · A passing test suite is not a build. 196 green host assertions told us nothing about whether the
firmware compiles for the chip it is meant to run on — and it does not.**

Measured 2026-09-18 on the 2026 Elantra vehicle logger. A subagent delivered 56 files and ~17k lines
with **196 assertions passing across three host suites, 0 failures**, and reported honestly that it had
never been compiled for the ESP32 because no toolchain was on the machine. When the toolchain was
installed and `pio run -e esp32dev` was actually run: **126 errors.** Nothing about the logic was wrong.
The thing had never been built.

Four build-stoppers the host tests structurally could not see:

1. **A root `CMakeLists.txt` calling `idf_component_register` made CMake run with the *system* compiler**
 and never load ESP-IDF's toolchain. PlatformIO generates its own project CMakeLists for
 `framework = espidf`; adding one overrides it and breaks toolchain selection silently.
2. **A dependency was never declared.** LittleFS is **not** bundled with ESP-IDF, so `store.cpp` could
 not compile. It also is **not in the PlatformIO registry**, so the usual `owner/name` form fails with
 `UnknownPackageError` — a git URL was required.
3. **A stale header name** (`esp_vfs_littlefs.h`; the maintained component ships `esp_littlefs.h`).
4. **Two namespace errors** (`trip::Aggregates`, `pids::MonitorRow` — both live in `vt`).

And one environment trap worth remembering: **PlatformIO 6.2.0 imports `pkg_resources`, which modern
setuptools removed**, so the build dies before compiling anything unless `setuptools<81` is installed.

**The rule.** A host test suite validates logic. It says nothing about whether a program *builds* for its
target, and those are different failures with different discovery costs. On any cross-compiled
deliverable — firmware, a mobile build, a container image — **run the target build first and treat a
green host suite as a bonus, not as evidence.** The subagent did the right thing by stating plainly that
it had not built for the device; that honesty is the only reason this was found in the same session
rather than after someone tried to flash it.

**Second-order:** a fix that lands in the wrong configuration scope is not a fix. A
`-Wno-error=stringop-overflow` was added to PlatformIO's shared `[env]` section while `[env:esp32dev]`
declared **its own** `build_flags`, which *replaces* rather than extends it — so the flag never reached
the compiler and the same error appeared on the next build. Scope the override where the build reads it,
and verify by re-running the thing that failed.

**Evidence:** `personal-secretary-mvp/firmware/vehicle-logger/BUILD-STATUS.md`, branch
`elantra-2026-09-18` @ `d6b95094`; `pio run -e esp32dev` → 126 errors; the three host suites still
196/0.
