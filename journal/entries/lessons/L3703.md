**L3703 · grep on a raw disk image OOM-kills, and a killed search is not a negative result**

MEASURED 2026-10-12 on zabz-tech-linux while identifying an unclaimed 16 GB SD card.

A line-based reader on a raw disk image is not merely slow, it is UNSAFE and it LIES.
`sudo grep -abi -c "BEGIN:VCARD" sdcard.img` on a 15.9 GB image was KILLED by the OOM
killer: the image has long runs of zeros with no newline, so grep buffers a "line" of
gigabytes. The pipeline printed nothing, which reads exactly like a clean negative.

Rule: a search that was killed is not evidence of absence, and a tool that cannot finish
must not be allowed to answer. Use a chunked scanner with overlap that reads fixed blocks
and uses bytes.find, so memory stays bounded and every hit carries a byte offset. That
scan then returned a definitive 0 hits across all 15,931,539,456 bytes for fisher,
fischer, fishel, 9145702075, steinfeld and begin:vcard - an answer worth having.

Same trap, generalised: when a search tool is OOM-killed, SIGPIPE'd or truncated, its
empty output must never be reported as "none found". Check the exit status and the bytes
scanned, and if the tool died, say so rather than reporting its silence.
