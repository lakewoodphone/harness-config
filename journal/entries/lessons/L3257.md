**L3257 · Dedup: use app/owner_question_dedupe, then OR a supplementary entity signal -- never reimplement it, never trust it alone**

﻿MEASURED 2026-10-05, building app/services/owner_attention_sweep.py.

I reimplemented question de-duplication three times before noticing that the
estate already has it: `app/owner_question_dedupe` (three similarity signals --
token Jaccard, content-word Jaccard, and content-word CONTAINMENT guarded by
MIN_SHARED_SALIENT), and `~/bin/owner-queue.py` refuses a duplicate `add` by
delegating to it. My versions all measured worse:

 * bag-of-words Jaccard: the true duplicate "ABLETEL SOLUTIONS LLC entity
 standing" vs pending #251 scored 0.205, while an unrelated pair scored 0.088.
 Too small a separation to threshold on.
 * "subject coverage" (>=2 shared non-boilerplate tokens): matched the live
 "Elantra - New York toll bill collection" finding against #110, the Elantra
 TRANSMISSION question, on the single word `elantra` -- a FALSE POSITIVE that
 would have silently swallowed a real toll-collection item -- while MISSING
 the correct match, answered row #166, which the real module scores at 0.83.

THE RULE: before writing a matcher, look for the module that already matches.
Then use it, and let it be the single source of truth.

BUT do not trust it alone either. Used on its own, `find_open_duplicate` has a
measured FALSE NEGATIVE: it accepted "Obligation OVERDUE: ABLETEL SOLUTIONS LLC"
as a new question (#267) while #251 was pending and asks about the same two LLC
filings, and accepted the BC28 obligation (#268) against pending #206. Long
human-written rows and short generated ones dilute each other's token sets.

So the shape that actually works is a UNION, biased one way on purpose: the
system module OR a supplementary entity/identifier signal. A false positive
costs one skipped candidate (the sweep moves to the next finding); a false
negative puts a duplicate decision in front of the owner. The owner's rule is
explicit -- the same finding must not raise a second question while one is
pending -- so dedup signals are OR-ed, never AND-ed.

EVIDENCE: sweep run #15 filed nothing and reported exactly why for each of the
four question-worthy obligations, including "ALREADY ANSWERED #166 ...
similarity 0.83: PAID 2026-09-30 by the owner: 135.33 against Tolls by Mail".
