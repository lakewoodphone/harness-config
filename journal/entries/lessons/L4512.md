**L4512 · House network: T-Mobile path MTU is 1436, CGNAT 192.0.0.1 returns ICMP frag-needed; QUIC test via headless Edge is unreliable**

Measured 2026-10-14 on ZABZ-YOGA (Wi-Fi 6 GHz to the Verizon CHR30A, Ethernet on the same LAN), via ssh from secratary-cloud.

TOPOLOGY READ OFF THE MACHINE, not assumed: Wi-Fi 192.168.1.5 and Ethernet 192.168.1.3, both gateway 192.168.1.1 (Verizon CHR30A). traceroute 8.8.8.8 = 192.168.1.1 -> 192.168.12.1 -> 192.0.0.1. So the T-Mobile gateway is 192.168.12.1 (its default LAN) and is UPSTREAM, the Verizon is a second router behind it (double NAT), and 192.0.0.1 is T-Mobile's carrier CGNAT hop. Useful tell for future sessions: if hop 2 is 192.168.12.1, the T-Mobile is upstream.

PATH MTU = 1436. Method: ping -f -l N (DF set) to 8.8.8.8 and dl.google.com, bisected: payload 1408 OK, 1412 FAIL, so the largest passing packet is 1436 bytes (1436-1439). Both Yoga adapters are configured 1500. Crucially the failure is NOT silent: the reply is "Reply from 192.0.0.1: Packet needs to be fragmented but DF set", i.e. T-Mobile's CGNAT does return ICMP type 3 code 4, so PMTUD works and endpoints adapt. Fix for any router downstream of the T-Mobile: set its WAN MTU to 1436.

BUFFERBLOAT, same session: idle 22-63 ms; sustained 10 Mbps -> max 57; 16 Mbps -> max 110; four unthrottled streams -> max 259 ms, mean ~87. Zero packet loss in 110 pings. Single flow 160 Mbps wired / 219 Mbps Wi-Fi; four flows ~237 Mbps aggregate. So "speed test great, video stalls" here is latency inflation and a 64-byte MTU gap, not bandwidth or loss.

QUIC TEST - DO NOT TRUST: headless Edge with --enable-quic --origin-to-force-quic-on=cloudflare.com:443 --dump-dom on https://cloudflare.com/cdn-cgi/trace reports the negotiated protocol (http=http/3 vs http/2). One run returned http=http/2 (i.e. QUIC did not establish, fell back to TCP); two later runs with fresh profiles and the same flags returned an EMPTY dom, and a verbose-log run wrote 0 bytes. So this rig is 1-of-3 reliable and cannot be used to declare QUIC blocked or working. Curl on Windows (8.21) has no HTTP/3 either. A QUIC verdict needs a different method.

WORKING REMOTE-DIAGNOSTIC RECIPE on Windows nodes: `scp` to zabz-yoga-1 fails with "Connection closed"; instead base64 the .ps1 locally, pipe a small PowerShell snippet over `ssh node "powershell -NoProfile -Command -"` that does [IO.File]::WriteAllText from [Convert]::FromBase64String, then run it with `powershell -NoProfile -ExecutionPolicy Bypass -File`. Piping the whole script through `-Command -` stdin executes but produced no stdout and no output file; -File is reliable. Do not run two of these concurrently on the same box (profile/instance collision).
