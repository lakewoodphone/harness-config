**L6199 · Testing the Web GUI's client behaviour without touching the owner's windows: isolated contexts, the mtime-keyed bundle, and three traps**

How to test the DSH Web GUI's own client behaviour WITHOUT touching the owner's open windows — and
the three traps that cost time on 2026-10-14.

1. TWO ISOLATED PLAYWRIGHT CONTEXTS ARE TWO WINDOWS. `browser.newContext()` gives separate storage
 and a separate JS context against the one engine; that is exactly a window slot, and its
 `localStorage` is in-memory, so nothing is written into the owner's real profile. Each context
 opens the engine's tokenized URL from `~/.dsh/multi-window/live-url.txt`; a GET of that URL
 exchanges the launch token for the signed auth cookie (dsh-client-connection/lib/index.js
 `BrowserAuth.authorizeIndex`, 303 + set-cookie bound to host:port). Use `--origin-port 3215` to
 move the same token onto a slot origin served by `dshw-proxy.mjs`, which is the owner's real path.
 NEVER print the token; read it from the file inside the tool.

2. THE CLIENT BUNDLE IS SERVED PER REQUEST, KEYED ON mtime. `dsh-client-modules/lib/index.js`
 re-reads a client bundle when its mtime/ctime/size changed ("Unchanged mtime, ctime and size
 preserve the graph without reading the bundle"). So a client-side fix needs only a WINDOW RELOAD —
 do not restart the engine, and do not believe a fix "did not apply" because the old code ran:
 reload first. (The cache also means each served bundle carries an mtime-derived rev — no
 cache-busting query is needed.)

3. THE PLAYWRIGHT IN `~/.dsh/tools/mcp` WANTS A BROWSER BUILD THAT IS NOT INSTALLED. Measured
 2026-10-14: playwright 1.64.0-alpha-2026-09-14 expects `chromium_headless_shell-1244`, the
 ms-playwright cache tops out at 1243, and a bare `chromium.launch()` dies with "Executable
 doesn't exist" — which reads like a broken harness, not a version skew. Pass
 `executablePath` at `%LOCALAPPDATA%\ms-playwright\chromium_headless_shell-1243\
 chrome-headless-shell-win64\chrome-headless-shell.exe` (the newest build present) and it works.

Also learned: `workspace/archiveSession` takes ONE wire parameter named `request`, so the args field
is `{ request: { sessionId } }` — `{ sessionId }` is refused with `missing "request"; unexpected
"sessionId"`. And run the existing `multi-window/tools/probe-session-list.ps1` under **pwsh 7**, not
Windows PowerShell 5.1: 5.1 has no `System.Net.Http.HttpClientHandler` and fails with TypeNotFound.

Tools written from this: `multi-window/tools/verify-window-session-isolation.mjs` (snapshot /
windows / archive) and `multi-window/tools/patch-window-blank-isolation.mjs` (check / apply / revert).
