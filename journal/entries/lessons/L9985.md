**L9985 · Correcting L9983: bin photo bytes never go in lpt-hub git - two machines plus the ledger sha256 is the evidence rule**

CORRECTION to L9983, same day, after reading the repo's own rules instead of inferring them from
what was missing on disk. L9983 said the 2026-10-10 batch had "no photos/ directory" and concluded a
new batch must "be committed with its photos". That advice is wrong for lpt-hub and would break two
standing rules:

- `lpt-hub/.gitignore:44` is a bare `*.jpg` (and png/jpeg/webp/heic alongside it), so photo bytes are
 excluded on purpose.
- `lpt-hub/AGENTS.md` section 9, Artifact Governance: "Keep binaries out of git" and prefer
 references, checksums and storage notes. `reports/contact-sheet.jpg` IS tracked, because it is the
 report's one image, and that is the established precedent in every batch directory.

So the correct habit is not to commit photos, it is to put the evidence on two machines and let the
ledger prove it: `ledger.json` carries `sha256` and `source_sha256` per photo, so anyone holding the
bytes can verify them against the record without the bytes being in git. Done 2026-10-19 for batches
2026-10-19 (11 photos) and 2026-10-18 (2 photos): each now sits under
`tools/parts-catalog/data/bins/<date>/photos/` on ZABZ-YOGA and on the authority clone
`/home/zabz/phone/lpt-hub/...`, and every file's sha256 was checked against its ledger line
(2/2 and 11/11 match).

Second finding, and the reason a note file now exists: batch 2026-10-18 held two photographs of the
INSIDE of an opened laptop (a 512GB M.2 SSD, copper heat strip, battery label
`13N4-0ZB0201 0A 0VV0 225K 06D9`), not bagged parts. That is the second time a non-stock drop became
a bin batch (first: 2026-10-11, P3145). `weekly.py` guards against re-ingesting the same bytes by
content hash; a hash says nothing about whether a photograph is of stock, so only a reader can catch
it. The reader's verdict now lives in `data/bins/2026-10-18/NOT-BIN-PARTS.md`, committed, with the
statement that 0 items were applied deliberately and `catalog.jsonl` must not be created from it.

Practical sequence that worked end to end on ZABZ-YOGA, in order: `python tools\weekly.py --from
"<zip>"` from the worktree `C:\Users\ezabz\code\_worktrees\parts-catalog\tools\parts-catalog` (the
main checkout is on an older branch and has no parts-catalog) -> read every converted JPEG myself ->
write one `results/<stem>.json` per photo -> `apply --strict` -> `report` -> `contactsheet.py` ->
`open-questions` -> `export` dry run -> commit metadata to main -> copy photos to the authority.

One more measured trap: this laptop's clone has NO remote named `github` (only `origin`); asking git
for `github/main` returns rc=128 with "Please make sure you have the correct access rights", which
reads exactly like a credential failure and is not one. The authority's clone does have `github`.
