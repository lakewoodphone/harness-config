**L3465 · A monitor that hardcodes another machine's unit name reports a fabricated zero - resolve the name at runtime and never let 0 stand for 'could not look'**

WHAT. A monitor that hardcodes another machine's systemd unit name reports a FABRICATED ZERO, and it
looks exactly like a healthy reading.

MEASURED 2026-10-11 on `secratary-cloud`, before the fix. `/opt/company/app/services/
company_outcome_monitor.py` reads the only honest count of `database is locked` events from
`journalctl -u secretary-api`. `secretary-api` is the OFFICE unit name; the authority runs the company
as `company-api.service`. Its output:

 lock_contention_7d
 source=systemd journal (secretary-api) + error_log floor
 journal_command = journalctl -u secretary-api --since '7 days ago' --no-pager -o cat
 journal_provenance = `journalctl -u secretary-api …` -> 0 matching lines
 journal_events = 0
 undercount_factor = 0.0

Measured reality on the same box: `journalctl -u company-api --since '7 days ago' --no-pager -o cat |
wc -l` → **2,615** lines. And the function's own docstring says the whole reason it exists *"rather than
a bare number"* is that a monitor reporting a zero it did not read is blind. It was reporting exactly
that, in the instrument built to catch it.

THE RULE. Never let a monitor hardcode a name it does not own. Resolve it at runtime, in this order:
an explicit deployment override (`COMPANY_OUTCOME_JOURNAL_UNIT`) → a probe for each candidate
(`systemctl cat <unit>`, whose exit status distinguishes "exists" from "does not") → and if nothing
resolves, return **UNREADABLE and say so**, because `None` and `0` are different answers and only one of
them is a finding. Applied here; and the same shape should be looked for in every ported script that
names a unit, a path or a service owned by the machine it came FROM.

THE ESTATE'S PATTERN, not a one-off. This is the third recorded instance of "the name moved and the
monitor kept reporting health": `order-feed-refresh` and `text-line-check` (rc=127 for 8 runs, script
long gone), `cron-target-guard` (never decodes its base64, so ~60 of its "checked" targets are one
wrapper), and now this. **A ported job must have every office-owned literal translated, and the
translation must be verified by reading the job's OUTPUT for the new name — not by reading its exit
code.** Exit code 0 was true in all three cases.
