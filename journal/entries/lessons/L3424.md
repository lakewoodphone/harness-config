**L3424 · the launcher's 25-second window click was Get-NetTCPConnection: netstat gives the same table in 275 ms instead of 3,462 ms**

Measured ZABZ-YOGA 2026-10-08, cold, in-process and end to end.

THE CALL: `Get-NetTCPConnection -State Listen` - one filterless call, inside Get-ListenTable, with two
retries - 3,462 ms measured on its own, 5,893 ms as the function ran. Worse than the number: it pulls
the NetTCPIP module into a fresh `pwsh` before anything else in the launcher can happen. The
replacement, `netstat -ano -p tcp` plus a parse, is 275 ms and returns the same rows with the same
pids (checked row by row on all 52 listening IPv4 ports against the slow call: 3099 -> 10668, 3200 and
3201 -> 4056).

END TO END, cold, this machine, `dshw.ps1 new` timed to the window becoming visible:
 before this change: 14.8 s (owner's report: "like 25 seconds")
 after: 3.4 s (launcher exits at 4.3 s)

WHAT ELSE THE MEASUREMENT RULED OUT as the cause: Get-CimInstance Win32_Process 378 ms, pwsh startup
800 ms, parsing 200 KB of dshw.ps1 151 ms, proxy /__dshw/stats 26-349 ms, token probe 264 ms,
Get-EdgePath 20 ms, Ensure-OriginsProxy 34 ms. None of them is seconds. TWO LAUNCH COSTS DOMINATED:
the port table, and PowerShell's own start-up. So when a launcher command feels slow, time the port
table first - and never measure it warm, because the 5-second memo in Get-ListenTable hides it.

THE GAP I ACCEPTED: netstat does not list IPv6-only listeners (it missed tailscaled on
fd7a:115c:a1e0::7a2e:a206:51622, 53 ports in the slow table against 52 in netstat's). Fine here
because every port the launcher asks about is 127.0.0.1, and the empty-read retry plus the old reader
stay as the fallback. Recorded in the function's comment so nobody re-discovers it as a bug.
