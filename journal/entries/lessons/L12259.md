**L12259 · A policy flag is only as good as its consumer: the browser image hole**

A policy FLAG is only worth what its CONSUMER does with it. Before claiming such a hole is closed, grep every read of the flag. In this lane `monitorImages` had exactly two readers, both in LockdownAccessibilityService, both behind `category == AppCategory.BROWSER` early returns: flipping the browser profile alone judged no pixel while RuleRepository.kt:889 (`resolved_monitor_images`) would have reported coverage the device did not deliver - a lie emitted by the product itself, which is the worst kind of fix to ship.

Second, that same early return was the ONLY rate limiter on the path: deleting it as instructed would have run collectText(root,2000) + TextAnalysisEngine.analyzeText on every content-changed event in a browser, unthrottled (the file's only throttle, TEXT_SCAN_INTERVAL_MS, lives in a different function). Check what a guard is load-bearing for before removing it.

Third, `AppCategory.BROWSER` is not "a browser": SmartAppProfileManager.detectWebView marks any app with a webview-ish activity enableMitm=true and resolveCategory turns that into BROWSER, so keying behaviour on the category alone silently turns costs on for every app with one WebView screen. The decision also asks isCuratedBrowser().

Result: browser frames go through requestAccessibilityScreenshot (1500 ms cooldown, single-thread classifier, tier at :1388), never the per-event tree walk. Residuals left open and named: HTTPS text in an allowed domain, video, FLAG_SECURE black frames, uncurated WebView apps, and API 29 devices where takeScreenshot is inert while minSdk = 29 (build.gradle.kts:153) - the "floor is API 30" belief is not what the manifest says. Battery cost and perceived speed were NOT measured; no device on that lane.
