**L1635 · I crash-looped production with a token replace that duplicated an import binding - a token count is not a parse check**

INCIDENT, 2026-09-15 ~22:30 UTC, lpt-apps / lpt-backend. Duration: about 3 minutes. Caused by me.

WHAT HAPPENED
I applied a consolidated production guard patch to close the anonymous pricing exposure. The new image
built fine and the compose recreate ran. lpt-backend went UNHEALTHY and crash-looped (restartCount 6).
The script detected it and printed FATAL: unhealthy. I rolled back immediately to
lpt-lpt-backend:searchmobile-guard-20260915-221641 via 'docker compose up -d lpt-backend'. Service
restored in ~15s: health=healthy, /health/live -> 200, guard-check.sh POSTURE INTACT.

ROOT CAUSE, from the container logs
 file:///app/backend/dist/trpc/routers/repair-job.router.js:6
 import { protectedProcedure, protectedProcedure, router } from '../context.js';
 SyntaxError: Identifier 'protectedProcedure' has already been declared
I patched by replacing every occurrence of the token 'publicProcedure' with 'protectedProcedure'. That
file ALREADY imported protectedProcedure, so the swap created a duplicate binding in the import list.
Node refuses to parse the module, the process exits, Docker restarts it, loop.

WHY MY VERIFICATION MISSED IT
The script's check counted 'publicProcedure' occurrences and asserted zero. Zero was TRUE and the file
was still broken. I verified the property I was changing (the builder token) and not the property that
matters (does the module still parse). The image check repeated the same mistake.

THE RULE, and it is the third time this class has bitten in this session
 A patch script must SYNTAX-CHECK what it wrote before the thing is deployed. For Node,
 'node --check <file>' is the gate, run inside the container, on EVERY patched file, BEFORE the image
 is built. A token count is not a parse check.
 Also: replacing a token inside an import list can create a duplicate identifier. Dedupe the specifier
 list, and never assume the file did not already import the target name.

WHAT WAS FINE
The rollback path worked exactly as designed: a named rollback tag existed, the compose image line was
the only thing changed, and reverting it plus one 'up -d' restored service with no rebuild. The
halt-on-unhealthy behaviour in step 6 is what limited this to ~3 minutes instead of a silent crash loop.
Verifying 'before' states and having a control (search.globalSearch 401) is why I knew the rollback had
restored the security posture too.

WHAT REMAINS UNDONE, DELIBERATELY
The pricing exposure is STILL OPEN: repairJob.list returns HTTP 200 with the real price matrix to
anonymous callers; motherboardSwap and settings.getDefaults are equally unguarded in production. I chose
NOT to re-attempt in the same session with limited context - a rushed second attempt on the live
customer site is how one outage becomes two. Source is already guarded for all three (settings.getDefaults
guarded via protectedProcedure; repair-job and motherboardSwap guarded earlier). The corrected script is
docs/audit/patch-priceguards-prod.sh and needs ONE change: dedupe the import specifier list and add
'node --check' as a hard pre-flight gate on all three files before 'docker build'.
Severity stays High, not Critical: pricing data, no customer PII, no money movement.
