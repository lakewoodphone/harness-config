**L188 · A document is a delivery mechanism that a cache can delete without a trace**

**2026-09-14 · secratary, at 393x852 on the live URL.** The phone layer reaches the client by
**rewriting the document** the gate serves, so a client that already holds that document runs a
shell with no layer — and nothing reports a fault: the server's answer is correct, the probe is
green, and the phone is wrong.

**Measured in the same minute.** A cold browser rendered the layer exactly as documented — frame one
`393px` column, sidebar off-canvas at `-340`, toggle pinned `44x44`, `html, body` overflow hidden —
while a warm browser in the same session rendered the app with the layer absent. A
`fetch("/", {cache:"no-store"})` from that warm client returned the engine's **raw 28,141-byte
document**, un-injected. The engine sends its document with **no `Cache-Control` at all**, which is
what a phone is free to reuse without asking.

**Two fixes, because one is not enough.** The gate now sends `Cache-Control: no-store` on every
document it serves and drops validators, so a client may not reuse a shell it was never given. The
layer is *also* served at `/dsh-phone-mobile.css` and linked by `dsh-plugin-mobile`, which a cache
cannot strip and an app rewriting its head cannot drop — proven by deleting the injected `<style>`
in a live browser and watching the layout hold.

**The rule, which is P42 generalised from cookies to caches.** An acceptance test for something the
owner touches must run with the same *dirty state* his device has: the same warm cache, the same
stale cookie, the same accumulated storage. A cold profile is the one client that cannot reproduce
his bug. And when behaviour is delivered by mutating a response, ask what happens when the response
is never requested — for the owner's phone, that was the whole difference between a working UI and
the one he complained about.
