**L3484 · The QL-820NWB answers only on its own EWS, and a naive strip-and-grep of it returns an empty value that reads as 'nothing printed'**

## L — The shop's label printer answers only on its own web page, and a naive strip-and-grep of it returns an EMPTY value that reads as "nothing printed"

The Brother QL-820NWB (192.168.50.60, OUI `4c:d5:77`) never answers reads on port 9100, so
`brother_ql`'s `did_print` is always false and `lpt-label print` exits 0 whether or not tape comes
out. The only remote proof a job printed is the printer's own EWS flipping **READY -> PRINTING**.

**The trap, measured 2026-10-11.** On `http://192.168.50.60/general/status.html` the state is:

```html
<dd><div id="moni_data"><span class="moni moniOk">READY </span></div></dd>
```

Strip tags with `sed -e 's/<[^>]*>/ /g'` and run `grep -o 'Device Status [A-Z]*'` and it returns the
literal string `Device Status` with **nothing after it** — 26 samples, every one empty, on a print
that DID happen. If you only count non-empty samples, that is indistinguishable from "the printer
never printed", which is exactly the confident-wrong reading this system must not produce.

**The extraction that works** (poll at 0.15 s while the send runs):

```sh
curl -s --max-time 2 "http://192.168.50.60/general/status.html" \
 | tr -d '\n' | grep -o -E 'moni moni[A-Za-z]*">[A-Za-z ]+' | sed -e 's/.*>//' -e 's/ *$//'
```

Observed during one `lpt-label` send, 2026-10-11 17:57:36-17:57:52 UTC, ticket 2652:
`READY -> BUSY -> PRINTING (5 samples) -> READY`. Script: `_labelprinter/verify_ym_2652b.sh`.

**Corollary 1 — the device SLEEPS and its absence is not a fault.** Asleep it drops off the LAN
entirely: no ICMP, no ARP entry for its MAC, mDNS `BRW4CD5775ED835.local` does not resolve, and a
/24 sweep of TCP 9100 finds only the office MFP. `lpt-label find` then says "no QL-820NWB found".
The cached address `.60` was correct the whole time. Ask the owner to wake it; it re-associated
inside a minute and the next `find` resolved instantly.

**Corollary 2 — TCP 9100 on this LAN is not unique to the label printer.** The office
Brother MFC-J4335DW sits at 192.168.50.243 and also answers 9100. Confirm identity on the web page
(model string) before printing to a swept address, exactly as `lpt-label find` already does.

**Corollary 3 — a re-send is the cheap, self-healing verification.** Printing the label a second
time while polling costs ~32 mm of tape and either proves the pipeline or produces the one label
that was wanted anyway. It is strictly better than reporting an unverified "printed".
