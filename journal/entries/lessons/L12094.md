**L12094 · Her mode was never set as the default, would have died on {{cwd}} if it had been, and her pinned model is no longer in the proxy catalog**

DESKTOP-FGV6KMH, 2026-10-21 02:45-02:56Z. The owner reported two things after the engine came back: it opens in `standard` instead of her mode, and the default model must be the proxy's 4.1/1017 ("fully updated").

1. WHY IT OPENED IN `standard`, MEASURED. `--dump-config` composed `- id: agent-preset-registry, config: default: standard` — the ENGINE's own default. Nothing in her profile patch set it, and although `settings.yaml` said `agent-presets: default: yocheved`, the row that carries it is generated from settings by the sync, and her sync has been frozen for weeks (`LOCAL COMMITS EXIST HERE … nothing was changed`). So the setting existed and never became config. Fixed with the same shape TECH uses: `- { id: agent-preset-registry, config: { default: yocheved } }`, added to her live patch. Verified: the composed row now says `default: yocheved`.

2. HER OWN MODE WOULD HAVE FAILED ON ITS FIRST TURN. `preset-yocheved`'s persona carried `suffix: "Your working directory is {{cwd}}."`. Her engine (0.2.0-rc.2) assembles exactly `{...assembled.variables, provider, model}` in `dsh-agent/lib/index.js` — there is no `cwd` prompt variable — so every turn in her mode would die with `unknown prompt variable "{{cwd}}"`, L10238 for the third machine. Removed from all three preset rows in her patch (yocheved, zabz, cordis-bg) and from the repo sources on a branch off master (`fix/yocheved-preset-mode-and-model`, 2d07adf5, pushed to offsite).

Her default is now `deepseek-flash` on `deepseek-proxy`, in the live patch and in `settings.yaml`; the repo overlays for her and the mini carry the same change on the branch.
 WHAT I CANNOT SAY: the API does not expose the BUILD. A completion returns `"model":"deepseek-flash"` and `system_fingerprint: e72d3c7f663d3e1383b00b3884cb4501` — no 1017 anywhere. 4. THE ORDER THAT COST AN HOUR, AND IT IS DOCUMENTED (L10302): THE RUNNING ENGINE OWNS profiles/web/cordis.patch.yml AND REWRITES IT FROM MEMORY. My first edit (made with the engine up) was gone 90 seconds later — the file shrank from 121,653 B to 119,532 B and the model went back to the retired id. The correct order, which then held: stop every engine → edit → start one → verify the composed tree. Any future remote edit to a profile patch must be done in that order, or it is a no-op that reads like a success.
