**L1616 · tRPC createCaller bypasses createContext, so a test can encode a context HTTP cannot produce**

Evidence: backend/src/trpc/routers/__tests__/ui.test.ts built CUSTOMER contexts with
uiRouter.createCaller(ctx) and passed for months. But createContext (backend/src/trpc/context.ts:155-168)
throws FORBIDDEN for a CUSTOMER token on any path outside an allowlist of customerPortal.*, customerAccount.*
and auth.refresh. ui.* is NOT on that list, so no CUSTOMER could reach ui.navigationContext.get over HTTP.
Switching it from the bare `procedure` builder to protectedProcedure broke exactly 16 tests -- all of them
asserting a context HTTP can never produce. ui.ts:883 and :986.

RULE: tRPC createCaller bypasses createContext. A createCaller test therefore proves something about the
RESOLVER, never about reachability. When you tighten a guard and tests break, ask first whether the test is
asserting an impossible context rather than assuming you broke something.

RULE: before weakening a guard to satisfy a test, check whether the capability is already covered at a lower
layer. Here the CUSTOMER nav filtering lives in the pure function filterNavigationByRoles and its suite was
36 passed (36) throughout. Nothing was lost by converting the router tests into rejection pins.

RULE: convert such a test into a REJECTION pin (assert FORBIDDEN) rather than deleting it. The rejection is
the property worth keeping, and it is stronger than the assertion it replaces.
