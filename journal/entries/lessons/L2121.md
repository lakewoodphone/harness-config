**L2121 · L2124 - busy_timeout does not cover SQLITE_BUSY_SNAPSHOT, so a read-then-write without BEGIN IMMEDIATE fails instantly**

Measured 2026-09-20 on secratary, and it is the reason a fix I applied did NOT work as claimed.

**What I did.** `app/services/mashgiach.py::_db_connect` opened `sqlite3.connect(path)` with no busy
handler, so I added `timeout=` and `PRAGMA busy_timeout=10000` - the same 10 s the pooled connection
in `app/database.py` uses. Verified behaviourally: a connection from that function reports
`PRAGMA busy_timeout` = 10000.

**What still happened.** After the fix was live and the service restarted (16:31:45Z), a burst of
**62 `database is locked` errors at 16:41:00**, every one of them from `app.services.mashgiach`, one
per agent, all inside the same second.

**Why.** `daily_scan` opens ONE connection, runs several SELECTs against it, and then calls
`_log_finding`, which does a single-row `INSERT` followed by `conn.commit()` - repeated once per
finding, 20 times per query (`LIMIT 20`). In WAL mode a connection that has read starts a read
transaction; the write that follows must **upgrade** it. If another writer committed in between, the
upgrade is refused with `SQLITE_BUSY_SNAPSHOT` - and per SQLite's own documentation that condition
is **not** handled by the busy handler: retrying could not produce a serializable result, so it fails
immediately, however large `busy_timeout` is.

**So `busy_timeout` is not a general cure for SQLite contention.** It covers lock *waiting*. It does
not cover snapshot conflicts, and those are produced by exactly the pattern this code uses: read,
think, then write on the same connection. A large timeout bought me nothing.

**The right fix (recorded, not yet applied).** `BEGIN IMMEDIATE` before the read that precedes a
write, so the write lock is taken up front instead of upgraded later; and batch the findings into one
transaction rather than committing per row. Either removes the upgrade entirely.

**How to tell the two apart in future.** A busy-handler case shows *waiting* - the operation
eventually succeeds, latency rises. A snapshot-conflict case fails **instantly** and in a *burst*,
one error per row in the same second. That burst shape is the tell: it means the failure is
structural, not congestion.

**Correction to my own earlier claim.** I described this as fixed when the timeout went in. It was
not fixed; the symptom persisted after deploy. The lesson is procedural as much as technical - I
verified the *setting* and should have verified the *effect*, which the very next hour's log would
have told me. I checked it only because I went looking, and I nearly did not.
