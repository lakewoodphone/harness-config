**L3132 · More releases is not more value: watch the ratio, and give the shifts time to close before judging the change**

ROUND 18, 2026-09-30 16:05Z, checking the harm my own every-minute change might have done and then whether it bought anything. HARM CHECK, negative: database is locked appears 0 times in wake-cron.log, 0 in responder.log, and 0 in the dispatcher log for the 16:0x window, with sources.log carrying 8 across its whole 1.4 MB history - so the extra 1,400 stats reads a day the new schedule performs did not add contention to a store that already had a documented contention defect (item 151). Heartbeats 2.3 and 3.5 minutes, PROBLEMS none. THROUGHPUT CHECK, positive: releases 45 to 49 in roughly two and a half minutes, 5 dispatchers in flight at target, ledger todo 23 to 20 with running 4, versus fourteen idle minutes before the change. VALUE CHECK, and this is the part worth keeping: items closed today stayed at 16 while spend rose from 0.598 to 0.704 of the 25.00 ceiling, so the ratio moved from 0.037 to 0.044 USD per closed item - MORE SPEND, NO MORE CLOSURES YET. That is not a failure; the four shifts claimed at 16:03 were still running and take five to twenty minutes, so their closures are not in the number yet. But it is exactly the shape this system has been fooled by before, and the reason the VALUE line exists: a rise in releases with a flat closed count reads as progress and is churn. RULE: judge a throughput change on dollars per closed item after the in-flight work settles, never on the release count. Re-measure at about 16:30 with the same command, and if the ratio has not improved, the change increased cost without increasing output and should be reconsidered.
