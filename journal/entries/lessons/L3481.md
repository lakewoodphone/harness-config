**L3481 · A timeout reported as an empty result is the worst kind of wrong: it duplicates data**

THE BUG. A client read https://api.abletelsolutions.com/api/v1/shop/parts with a 30 s timeout. The endpoint was MEASURED at 65.4 s that day (small table, 23.6 GB SQLite file, many readers, busy_timeout 10 s per handle). urllib raised, the exception was caught, and the caller reported "0 existing rows". The tool then wrote 12 rows it believed were new. It happened to be correct only because the table genuinely was empty.

WORSE, SAME FAMILY. Even with a fast answer it was still wrong: the route returns {"ok":true,"total":12,"parts":[...]} and the parser only understood a bare list, so it fell through to `return True, []` - an unrecognised envelope read as "no rows". Same outcome, different cause.

WHAT GOOD LOOKS LIKE. (1) An empty result must be a POSITIVE statement from the far side: only a well-formed answer with total==0 counts as none. (2) An unrecognised shape returns None -> treated as FAILURE, never as empty. (3) Retry the read. (4) Generous timeouts where the endpoint is known slow, with the measurement written next to the constant. (5) Refuse to write when the read failed, and say so: "READ FAILED ... REFUSING to write blind".

APPROVAL GATE. Any write that depends on a read (dedup, upsert, reconcile) must abort when the read fails. A failed read is a refusal, not a fact about the world - the estate has already lost a day to believing a stale copy of a database.
