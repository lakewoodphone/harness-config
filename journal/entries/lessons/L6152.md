## 2026-10-13 — a case file minted from traffic is not a case file; resolve it, do not add beside it

`lpt-hub` carries dozens of case files minted from Dialpad traffic and named `Unknown`, with device
lines like "unknown — no device has been identified". When production already knows the customer and
a real work order exists, **the fix is to make that file the case**: front-matter and header take the
production identity, the device text is rewritten, and the original artifact is kept verbatim
underneath. It is *not* to create a correctly-named second file beside it.

Why: `CASE-FILE-STANDARD.md` §1 forbids renaming (old paths are referenced from sync records and
`recovery-index.md`), and two case files for one work order is exactly the duplicate defect
`doubles.py` exists to catch. Measured 2026-10-13 on the drebin cameras: resolving the existing file
moved `lptcase check` `case-without-sync-record` **37 -> 36** and left every other count unchanged;
a second file would have added one to `doubles` instead.

Two corollaries, both measured the same day:

- **`customer:` is what makes a file findable by name; `aliases` is what makes it findable by the
 string that will actually be typed.** Adding the second camera's label (`Ungarischer`) to
 `aliases` is what makes `lptcase find ungarischer` return the drebin case; without it the search
 scores 1.20 (WEAK) and the case reads as absent.
- **A label number that matches nothing is a real negative only if you name the query and the
 stores.** "No match" from a `customers` query alone is not the same claim as **0 rows across
 `customers`, `orders` and `communications`, in both stores, on the last ten digits.**
- The work-order field in case front-matter is worth writing even when the file name is a traffic
 artifact: `lptcase find WO2609010006` scored 4.00 and found the case, which is how a staff member
 holding the paper ticket reaches the file.
