## L — "lock contention" on secratary is really disk I/O starvation, and the health check is the liar

MEASURED 2026-10-09 on secratary, over ~30 min. The company API reported:
 {"ok":false,"database":{"ok":false,"error":"db check timed out (lock contention); api still responsive"}}
for 20+ minutes straight. That message is WRONG and it cost a long detour.

WHAT IS ACTUALLY TRUE, all measured at the same moment:
 curl -o /dev/null -w '%{http_code} %{time_total}' http://127.0.0.1:8002/health
 -> 200 in 0.006s <- the API ANSWERS, fast
 sqlite3 secretary.db 'select count(*) from sqlite_master'
 -> 654 in 0.104s <- the DB is FINE
 cat /proc/pressure/io -> some avg300=62.8 full avg300=59.5 <- the DISK is saturated
 cat /proc/pressure/cpu -> some avg300= 1.75 full avg300= 0.00 <- the CPU is IDLE

THE MECHANISM: app/main.py:1503-1518 runs a DB probe inside
asyncio.wait_for(..., timeout=2.0). A 2-second budget is generous on an idle box and
too small on a box whose disk is 60% "full" per PSI. So the probe times out, the
endpoint reports "lock contention", and it is a *label* not a measurement - nothing
was locked. It is HTTP 200, i.e. DEGRADED by design, not an outage.

RULES TO KEEP
1. On this fleet there is NO sqlite3 client binary that reports a lock; verify a lock
 claim with /proc/pressure/io and a timed trivial query before believing it.
2. Read /proc/pressure/{io,cpu} before blaming a DB. io full high + cpu full zero is
 disk starvation, every time.
3. A SATURATED DISK IS WHY THE TRANSPORT "FLAKES": the drop-in beside the backup unit
 (20-io-ceiling.conf, 2026-10-07) records sshd stalling with the backup, which is the
 same root cause behind "secratary falls off the network". One cause, two symptoms.
4. NEVER run `sqlite3 ... dbstat` or a recursive `du` on this box: a 22.9 GB dbstat
 scan left a process in D-state for 11 min and a du over the encrypted 35 GB data/
 both added real load. I did this and had to kill my own work. Use page_count x
 page_size for size, and never full-scan a live 23 GB DB.

CONTRIBUTORS TO THE PRESSURE (not the sole cause): backup-data.sh copying 22.9 GB
every 6 h, and scripts/dialpad-call-fresh.py running as THREE concurrent instances.
