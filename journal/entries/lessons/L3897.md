**L3897 · exFAT recovers WITH names; a card whose files 'disappeared' was a shortcut worm, not data loss**

Case Werner 7326840351 (WO26102012764, customer 2985). A 128 GB exFAT SD card where the customer said 'all the files disappeared' after Ctrl+A/Ctrl+C. Measured read-only: 10,882 files / 93.29 GB present and named, boot sector and both FATs intact, 28.9 MB/s, 0 errors. The apparent loss was a live USB shortcut worm: Microsoft/MicrosoftSecurity.exe is PE32 AutoIt importing GetFileAttributesW/SetFileAttributesW (that is the folder-hiding mechanism) with Microsoft.a3x beside it, written 2026-10-18 18:40, plus 17 live .lnk lures. Nothing was executed. LESSON: an intact filesystem plus 'the files disappeared' means mount read-only and count BEFORE any carve - a carve would have produced a nameless copy of files the filesystem could still name.

The repo had no exFAT walker (extract-fat-named.py is FAT12/16/32 only, scan-fs.py only locates 'EXFAT '), so I wrote scripts/data-recovery/exfat-named.py. THREE PARSER TRAPS, each of which silently dropped real files, all found on this card:
1. SecondaryCount is ZEROED when exFAT deletes a file (0x85 sec=2 becomes 0x05 sec=0) while the secondaries remain - so 'advance by nsec+1' lands mid-set.
2. A deleted entry can be ORPHANED: it still claims sec=2 but its secondaries have been REUSED by the next live set. Jumping nsec+1 therefore stepped straight over the live DCIM/916CANON - 1,302 files. With no valid stream extension, consume exactly ONE entry.
3. File-name entries are entries[j+2 .. j+nsec] because SecondaryCount INCLUDES the stream extension; range(2, nsec) is empty for every one-name file, so every name came back blank and was skipped.

Deletion on exFAT clears bit 7 of the entry type byte only: name, FirstCluster and DataLength survive, and the data is not zeroed - only the FAT chain is freed. So read the file CONTIGUOUSLY from FirstCluster and record per file that you assumed it; StreamExtension.flags & 0x02 (NoFatChain) means the card itself declares it contiguous. Recovered 1,298 deleted-but-named entries here.

THE ONLY COMPLETION GATE THAT COUNTS: diff the walker's live list against a read-only mount, file-for-file and size-for-size. Final: 10,882 / 10,882, zero difference in either direction. Anything short of that is a claim, not a measurement.

Bench discipline: do NOT walk a card that ddrescue is imaging. My own read-only directory walks and sha256 passes starved it and made it skip 10 areas (retried later, 0 errors); the skips were my interference, not the medium.
