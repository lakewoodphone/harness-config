**L2093 · L2087 - 31 percent of tool calls in the company never execute, and the error class conflates three unrelated causes**

Measured 2026-09-20 in `tick_telemetry.tool_calls_json`, last 7 days: **565 of 1,813 tool calls carry
`"executed": false`** - 31%. Three completely different things land in the same bucket:

1. **Broken prerequisite.** `"This step requires one of these tools first: browser_use_run. Do not
 call delegate_task before satisfying that requirement."` The step-gating logic requires tool A
 before tool B, and A itself is unavailable.
2. **Unreachable dependency.** `ha_status, ha_doors, ha_climate` blocked - Home Assistant is
 configured to `http://homeassistant.local:8123` (`app/config.py:682`), a name that does not
 resolve from the authority. `seed_home_sensors` failed 95 times in 7 days and is a standing work
 order with `last_run_status=success`, because the failure lives in the task layer while the
 schedule layer records its own outcome.
3. **Configuration gap.** `"onetalk_url is required"` for `alibaba_onetalk_automation` - the tool is
 registered, advertised to the model, and permanently unusable because a required parameter has no
 default and no config value.

Plus a fourth that is policy, not failure: `repo_run_command` refuses
(`Command not allowed. Safe prefixes: git, pnpm, npm, ...`) and is counted as a blocked attempt.

The company also reports these honestly - the tick error text says
`No tool call executed successfully. Invalid or blocked attempts: ha_status, save_memory, create_task`
- and nothing reads it. That is the whole gap: the system knows and cannot tell anyone.

**Rule: "blocked" is not a diagnosis.** Split it into (a) broken dependency, (b) unconfigured tool,
(c) policy refusal, and alert separately. Case (b) is the cheapest to fix and the most embarrassing
to leave: a tool that no input can ever satisfy should be removed from the model's tool list.
