**L3414 · A slow counter screen is usually round trips, not plans - count statements first**

An index cannot fix a round-trip problem. Measured on the LPT production counter 2026-10-08: `workOrders.getAll` executed 35 SQL statements whose TOTAL in-database time was 178 ms, inside a 2452 ms request; `workOrders.getById` executed 16 statements totalling 231 ms inside 1403 ms. Every EXPLAIN plan involved was already sub-millisecond (list 0.494 ms, job-open 0.045 ms) on a 641-row table. WHAT THAT MEANS FOR THE NEXT SESSION: when a Postgres-backed screen feels slow, measure the STATEMENT COUNT and the per-round-trip latency BEFORE reading plans or reaching for an index. The per-statement time can be trivial while the count is what hurts, especially when the app server and its database are in different regions - here one round trip is ~115 ms, so 16 statements is 1.8 s of pure latency with almost no database work. Method that worked, reusable: diff `pg_stat_statements.calls` per `queryid` across exactly one HTTP call to get the statement count; the LPT live DB is reachable read-only from `lpt-apps-01` as `docker exec lpt-postgres psql "$(docker exec lpt-backend printenv DATABASE_URL)"`. Second lesson, and the expensive one: I "fixed" the batched read three times before a differential test against the live database passed - `SELECT *` leaked three columns Prisma never returned, a bare timestamp lost its `Z` and its trailing zero millisecond (a real behaviour change for anything comparing dates), and `ORDER BY` on a projected text column sorted strings. A field-for-field parity harness over real rows, run against the live database, found all three in one run and would have found nothing by inspection.
