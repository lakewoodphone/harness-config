**L2248 · L2156 - rank the two failure types before chasing the rarer one: 39 locked vs 3 closed-database**

Measured 2026-09-20 over 24 hours of `Lifecycle sweep failed`:

 OperationalError: database is locked 39
 ProgrammingError: cannot operate on closed db 3 (04:19:08, 06:16:56, 18:09:41)

**A 13:1 ratio.** I found the closed-database error this round, it was new to me, and it is a more
*interesting* bug - a `conn` used after something closed it is a logic error, where a snapshot conflict is
a concurrency error. My instinct was to chase it.

**That instinct was wrong, and the count is what corrected it.** The locked failures happen ~13x as
often, on a routine that runs every 120 s, and the phases it skips (owner-message expiry, stale-claim
release, retry scheduling, goal rollup) are the machinery that stops the backlog rotting. Fixing the
rare one first would have left the dominant failure in place and consumed the round.

**Rule: when two error types share one log line, count them separately and fix the frequent one first.**
The exception class is the only discriminator between them - both print as
`Lifecycle sweep failed: <exception>` from the same caller - so the count is not visible without
deliberately separating them, which is exactly why the rarer, more interesting one gets picked up first.

**And a caution about the 18:09:41 instance.** It landed 1 second before a service restart at 18:09:42,
which made "shutdown race" look like the explanation. But the other two (04:19:08, 06:16:56) have no
restart near them, so the coincidence explains at most one of the three. **One correlation out of three
is not a mechanism** - I nearly generalised from the single instance that happened to sit next to a
restart, which is the same error as generalising the lock failure from one `mashgiach` burst earlier
today.

**Still unexplained for the closed-database case:** there is no `conn.close()` anywhere in
`lifecycle_sweep.py`, so it comes from a helper - most likely one of the two that open their OWN
connection from `db_url` (`ensure_task_lifecycle_metadata`, `_watch_customer_stalls`) interacting with the
shared `conn`, or the shared `conn` being closed by `_get_conn`'s pool. Three occurrences is too few to
diagnose from logs alone; it needs a reproduction. It stays recorded and ranked BELOW the lock.
