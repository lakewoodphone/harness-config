**L3439 · A success counter that never reads the database is a claim, not a measurement (INSERT OR IGNORE + unconditional += 1)**

# CORRECTION to W2678 — the categorizer was reporting attempts, not writes

Append-only correction, 2026-10-09. W2678 reported "1,323 transactions categorizable"
and later "categorized 1,323 / 994". **Those numbers came from the counting bug described
below and were not the number of rows written.** W2678 is not rewritten; this is the
correction, and the wrong number stays on the record because the fact that I believed it
is the useful part.

## The bug, proven on the live ledger

`app/services/auto_categorize.py` did this:

```python
conn.execute("""INSERT OR IGNORE INTO transaction_categories ...""")
conn.commit()
categorized += 1 # <-- unconditional
```

`INSERT OR IGNORE` turns a constraint violation into a **silent no-op**. The code then
incremented `categorized` without ever reading the result. So the counter measured
ATTEMPTS, and a run that wrote nothing reported success.

Measured end to end:

```
[auto-categorize] categorized 602 of 2268 uncategorized (skipped 1666, errors 0)
rows before=7390 after=7390 DELTA=0
```

And the mechanism, isolated on one genuinely uncategorized row:

```
attempt 1 (INSERT OR IGNORE) : no exception raised. rowcount=0 <-- 0 means nothing written
attempt 2 (the same INSERT) : SQLITE SAYS: IntegrityError: UNIQUE constraint failed:
 transaction_categories.transaction_id
```

## The second, larger defect: the SELECT over-reported by 810 rows

The query used `LEFT JOIN transaction_categories tc ... WHERE tc.id IS NULL`, which says
**2,268** uncategorized for lpt/personal while the honest predicate says **1,458**. The
810-row difference is rows that DO have a category, so every run attempted inserts that
could only fail, and each failure was counted as a success. `NOT EXISTS` is both the
honest predicate and the one the rest of this codebase already uses.

This is why a categorizer that "works" left a 5.6-year backlog and looked healthy in
every log: it reported progress, and the ledger never moved.

## Fixed

- `NOT EXISTS` replaces the LEFT JOIN (no more doomed candidates).
- `cur.rowcount` is read; `rowcount == 0` is counted as a new `already_categorized`
 field, never as a write.
- The CLI (`scripts/auto-categorize.py`) surfaces it. Verified after the fix:
 `categorized 0 of 1458 (skipped 1458)` and **delta 0**, twice in a row — honest and
 idempotent.

## One more thing this invalidates

`transaction_categories.justification` carries **2,075 `auto_rule:` rows** whose
confidence labels (`conf=0.95`, `conf=0.99`) are fine, but the historical population
predates the fix — so any past claim about "how many transactions the auto-categorizer
handled" that was read off the counter is unreliable. Read writes from
`assigned_at`/row counts, never from that log line.

## Lesson

**A success counter that does not read the database is a claim, not a measurement.**
`INSERT OR IGNORE` plus an unconditional `+= 1` is the specific shape to grep for across
this estate: it reports progress where nothing happened, which is worse than a failure
because a failure gets investigated.
