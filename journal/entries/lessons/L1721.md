**L1721 · Verified both conditional headlines: the AI kill switch is fail-open and misses ai-workspace; Elasticsearch was never deployed**

TWO HEADLINES VERIFIED BY THE MANAGER, 2026-09-15/16. Both close an open item an agent flagged as its
own most consequential unknown, and both were settled with one read of the deployed host rather than
with more reading of source.

1. AI WRITE KILL SWITCH - PART-043's CLAIM CONFIRMED, so owner question #62 stands.
 Repo-wide grep for AI_AUTOPILOT_WRITES_ENABLED in backend/src (non-test):
 services/ai-tools/ai-tool-execution-policy.service.ts:68,112
 services/admin-settings.service.ts:187
 trpc/routers/ai-orchestrator.router.ts:834
 trpc/routers/adminSettings.ts:147 (merely exposes the value)
 And a grep of backend/src/services/ai-workspace for AI_AUTOPILOT|AUTOPILOT|FEATURE_AI returns NOTHING.
 So ai-workspace has no autonomy-flag read anywhere, and its 40 write procedures are ungated exactly
 as PART-043 reported. Production confirms both switches are ON
 (FEATURE_AI_AUTOPILOT=true, AI_AUTOPILOT_WRITES_ENABLED=true), re-checked in the same command.
 NOTE THE SHAPE while you are here: every read site is `!== 'false'`, so the switch is FAIL-OPEN -
 anything other than the literal string 'false' permits writes, including an unset variable. A kill
 switch that has to be explicitly set to a magic string in order to kill is not a kill switch.

2. ELASTICSEARCH IS NOT CONFIGURED IN PRODUCTION - PART-073's question ANSWERED.
 `docker exec lpt-backend printenv | grep -iE 'ELASTIC|SEARCH_'` returns NOTHING, and
 `docker ps` shows no elasticsearch/opensearch container. PART-073 could not settle this from the
 worktree because the repo contradicts itself: backend/.env.production has no ELASTICSEARCH_URL,
 .env.production.template:120 points at http://elasticsearch:9200 on a host
 docker-compose.production.yml never defines, and the only compose that defines ES is dev-only with
 xpack.security.enabled=false.
 CONSEQUENCE: the 7 of its 12 findings that depend on ES being live are LATENT, not live - the
 unescaped highlight XSS sink, the client-controlled filters/sort.field, and the wildcard
 pattern-broadening. That is not a dismissal: the code is wrong and would be live the day someone sets
 the variable, and PART-073's two carry-overs from PART-052 are confirmed at path:line.
 It also explains why PART-073's "no writer exists" finding is coherent rather than alarming:
 indexDocument and bulkIndex have zero call sites, so the search path has never been exercised
 against a real cluster.

PRODUCTION. Two independent agents reported the Ably key as a live Critical and one fetch of the public
