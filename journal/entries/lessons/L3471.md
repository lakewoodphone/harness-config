**L3471 · A predicate that cannot distinguish two states is not a reading - I hit the same bug twice in one evening (dispatched/accepted, then activating/active)**

**Lesson, measured 2026-10-09.** The graceful HA stop had never once worked, and
the reason it stayed broken is that the branch that would have recovered it was
unreachable.

## The rule

**Gate a recovery poll on having DISPATCHED the request, never on the request
having been ACCEPTED.**

I added a settle window to `home_assistant.shutdown()` so HA could flush its
recorder before the plug cut power. I wrote:

```python
went_down = False
if accepted and settle_sec > 0: # WRONG
 ...poll for the connection to drop...
```

On this install `homeassistant.stop` returns **504 while HA is genuinely going
down** (measured 19:16:56Z: the next call was connection-refused). So `accepted`
was never set, the poll never ran, and the `if went_down:` branch below it could
not be reached by construction — the exact failure it existed to handle.

Correct:

```python
if dispatched and settle_sec > 0: # a dispatched 504 is still a stop request
```

## Why this class of bug is expensive

It is invisible to tests written against the code's own vocabulary: my first
test still failed *after* the fix, which is how I found the second bug. A branch
guarded by a flag that the failing case never sets is dead code that reads like
working code, and it will pass a review by anyone who assumes `accepted` means
"we asked".

The tell: a comment saying "recovery", a guard saying "success". When you write
a fallback, ask *what is true in the case this fallback exists for* — and make
the guard that thing.

## ADDENDUM 2026-10-09, later the same evening — I then wrote the same bug myself

Worth recording because it proves the rule is about a *habit*, not one incident.
While waiting for a deploy to fire, I wrote a watcher:

```bash
if ! systemctl is-active --quiet shabbat-5h-deploy2.service; then break; fi
```

It reported "deploy finished" **instantly, three times**, because a systemd unit
whose target time has not arrived reports `ActiveState=activating`, and
`is-active` is **false** for it. "Our deploy is still waiting" and "our deploy
has finished" are different states, and the test could not tell them apart — the
identical defect, in a different medium, found by the same question.

Correct:

```bash
while [ "$(systemctl show -p ActiveState --value U)" = activating ]; do sleep 30; done
```

**So the generalised rule is not "use dispatched not accepted".** It is: *any
boolean you branch on must be false in exactly the cases you mean, and you must
name those cases.* `is-active` is a convenience predicate that silently folds
`activating` into "not active". `--quiet` makes the distinction invisible.
Ask what the predicate returns in the state your code exists to handle — and if
the answer is not obvious, read the state itself instead of the predicate.

## The wider defect

`ensure_interior_door_unlocked` and `_power_down_critical` were rewritten after
the 2026-09-11 lockout and after Erev Shmini Atzeret 2026-10-02, and the stop
path was left alone. The module's own comment said the graceful step "had never
once worked" — it was known, written down, and not fixed, so every Shabbat
power-down was a hard cut with the recorder unflushed. **A documented known-broken
step is still a broken step.** Writing it down is not the fix; the file records
it, the code has to honour it.
