**L2784c · A full tmpfs /tmp kills shell heredocs silently: thirteen hours of missed calls, reported as a freshness metric**

**A full tmpfs /tmp kills shell heredocs silently, and the symptom looks like a broken harvester, not a full disk. Measured 2026-09-28 on the authority (secratary).**

`/tmp` is a tmpfs sized 50% of RAM â€” 12 G on this host. At 03:22Z something wrote
`/tmp/livecopy.db`, a 9.8 GB SQLite copy of the live database, and the tmpfs filled at 03:23Z.

From 03:23Z to 16:20Z, every run of BOTH Dialpad harvest scripts failed like this:

```
cat: -: Disk quota exceeded
FAILED rc=0 on attempt 1/3; output=<empty>
```

and the kernel reported the consequence, not the cause: *"call harvest has not completed in
11.7h ... incoming texts are not being fetched"*.

**The mechanism, which is the transferable part.** The scripts write their Python worker with
`WORKER="$(mktemp /tmp/...py)"; cat > "$WORKER" <<'PYEOF' ... PYEOF`. When `mktemp` succeeds but
`cat` cannot open the target, `cat` exits immediately WITHOUT reading stdin. The shell is then
blocked writing the heredoc into a pipe nobody reads, so the `timeout 600 python ...` on the next
line is never reached and the job sits until cron's own timeout. That is why the log says
"produced no output" rather than a timeout or an error, and why nothing named the disk.

**The fixes, cheapest first.**
1. Never leave a multi-gigabyte file in tmpfs. A 9.8 GB copy in a RAM-backed /tmp is a
 delayed-action failure for every job on the host, not just its creator.
2. Check the temp-file creation explicitly and exit with a named error, rather than letting a
 later `cat` fail in a way that hangs. Both harvest scripts now do (`exit 3`, logged), proven
 by running them with `mktemp` replaced by a failing stub: `rc=3` and a FATAL line in the log.
3. Prefer a temp location on the filesystem that has room. Both scripts now create their worker
 under the database's own directory when it has space, and only fall back to `/tmp`.
4. Wrap the worker body in `try/except` that prints the traceback: a failure before the first
 stage is then a named error in the log instead of an empty output.

**What this cost.** Thirteen hours of missed calls and texts, invisible on the surface, reported
only as a freshness metric. The old reading was right; its stated cause was wrong.

**Correction to a claim I made in the same session** (kept because the record of being wrong is
worth more than a clean history): I first "fixed" this class by inserting `set -euo pipefail` at
the top of the Python worker bodies. That is not valid Python â€” the deployed scripts never had
such a line â€” and it broke both workers with `SyntaxError: invalid syntax`. It failed loudly and
fast (`rc=1`, traceback in the log, marker untouched), which is exactly the fail-loud behaviour
fix (2) was for, and a second patcher removed it and added the real guard.
