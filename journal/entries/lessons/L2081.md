**L2081 · Windows Hello PIN reset every boot: read 0xD000A002 + UserOOBEBroker, correlate with the VSM key unseal**

Symptom "I have to reset my PIN every time I restart" is diagnosable to the exact event in
`Microsoft-Windows-HelloForBusiness/Operational` (needs elevation to read):

 Id 7002 Failed to load an existing Windows Hello container. ID: {GUID} Error: 0xD000A002
 Id 3611 Windows Hello container deletion started from UserOOBEBroker.exe.
 Id 8611 Windows Hello successfully deleted the container.
 Id 5702 ... PIN protector = true <- re-provisioned, empty

`UserOOBEBroker.exe` is the REMEDIATION, not the cause: Windows deletes a container it cannot load and
provisions a fresh one, which is why the owner must set the PIN up again. Do not chase the broker.

Find the cause in `Microsoft-Windows-Kernel-Boot/Operational` ids 45/51/85 for the SAME boot:
 good: "Unsealing cached copy status: 0x0", BlobFromUefiVariableSize: 723
 bad : "Using cached copy status: 0xC0000225" (STATUS_NOT_FOUND),
 "Read and Unseal Master Key Array Package Status: The object was not found",
 BlobFromUefiVariableSize: 0
The VSM master key's sealed package is ABSENT from its UEFI variable at early boot, so the key rotates
and everything sealed to the old one - including the Hello container - is dead. Only matters where
VSM-protected Hello is on: `HKLM\SYSTEM\CurrentControlSet\Control\DeviceGuard\Scenarios\WindowsHello`
Enabled=1. `dsregcmd /status` then reports `NgcSet : NO`.

Measured on ZABZ-TECH over 13 boots: the 166-178 s off-windows are exactly the VSM-key-lost boots
whose Hello container got wiped; the 63-96 s boots had the key and the PIN survived.

Do NOT accept the widely-cited "Secure Boot DBX + firmware update changed several PCRs" story
(jpwinsup blog) without testing it: it predicts BitLocker failure too, and BitLocker there is bound to
the same PCRs 7,11 and never asked for a recovery key. Blob absent != PCR mismatch. Say so when the
evidence disagrees with the popular explanation.

Split boot timing with `Diagnostics-Performance/Operational` event 100, never elapsed wall clock: its
`BootStartTime` IS the bootmgr/kernel start, so `MainPathBootTime` is core boot, and
`BootStartTime - previous Kernel-General 13` is shutdown-tail + power-off + firmware POST (those three
are NOT separable from logs - say that instead of pretending). ZABZ-TECH numbers: core boot
9.5-23.6 s, total 30-103 s. The "slow boot" was never Windows.

Differential control is cheap and decisive: read the same keys/logs on a healthy machine
(ZABZ-YOGA had no 7002, no 3611, no IsOOBEInProgress). Two stale flags present only on the sick
machine is a finding; the same value on both is a red herring.
