**L6222 · I reported a customer as unpaid from another session's note, and the money was 170.60 in our own store — the payer name was in `description`, and the answer was one division away**

## 2026-10-14, ZABZ-TECH. Answering waiting customers. Six mistakes on one case, and every
one of them was avoidable with a read I already knew how to run.

### 1. I repeated a conclusion I did not produce, and it was wrong

I told the owner: *"no payment from him appears in Stripe."* I had not queried anything. I was
quoting **note 3181** on work order `WO2608060002`, written by a session on 2026-10-13:

> *"the money was hunted in Stripe (77 payment intents, 2026-08-01 to 2026-09-01; every counter
> sale is a Stripe Terminal charge whose metadata is only a readerId and a short staff note, so
> **no payer name exists anywhere in Stripe**) … no payment from this customer appears in either."*

**The payer's name was in our own store, in `description`, reading literally `Pruzansky`.**
`/root/accounting-data/live/accounting.db` → `transactions` id `873cd124-760e-4f95-b12b-1794eec08099`,
`source_system stripe-charges`, `amount_cents 17060`, `transaction_date 2026-10-13`,
`external_transaction_id ch_3UQD9yLnlgYj1gmT1BOxhIjw`.

Three separate faults in that one sentence of mine:
- **I did not run the query.** The rule is mine and it is written down: a claim carries the
 command and its output. "Somebody else searched" is not a source.
- **The note's own premise contradicted itself and I did not notice.** It said Terminal metadata
 holds `readerId` and `staffNote` — and I measured **0 rows** in that store containing either
 string. It was describing Stripe's raw payload, not our ingested rows, and concluded from the
 fields it *chose* that no name existed. It never looked at `description`.
- **The row did not exist when that session ran.** Every Stripe charge of 2026-10-13 has
 `created_at 2026-10-14 04:40:05Z` (all nine of them) — ingested by `stripe-sync` hours after
 the note was written. So the conclusion was not merely wrong, it was **unknowable**, and the
 note should have said `UNVERIFIABLE` instead of `none`.

**THE RULE, and it is the expensive one: a search whose scope you did not define is not
evidence.** Run it yourself, name the store, name the fields, name the time the store was last
written, and if the store was not being written when the claim was made, the correct answer is
*unverifiable*, never *absent*.

### 2. A numeric discrepancy is a hypothesis to test against the shop's own conventions, not a mystery

I found 170.60 charged against a 160 quote and brought the owner a question about it — *"the
recorded scope is 160, he was charged 170.60, which is settled?"* — and a story about a staff note
reading *"and motherboard"*. He answered with a question: ***"isn't it tax? are you stupid"***.

**170.60 / 1.06625 = 160.00, exactly.** 6.625% is the shop's own recorded sales-tax rate and
`total` is documented as **tax-inclusive** (`lpt-ops/docs/writes.md`; the same `/1.06625`
conversion as the Greenfeld 150.00 → 140.68 entry in the ledger). The answer was **one
division**, it was in a document I had already read this session, and I turned the shop's
standing tax convention into an owner question.

**THE RULE: before reporting a money discrepancy, divide.** Try the sales tax, try the recorded
quote, try the deposit. `X / 1.06625` and `X * 1.06625` cost nothing and settle most of these.
A discrepancy that survives the conventions is a finding; one that does not was arithmetic.

### 3. Three drafts in a row did not answer the message that was sent

- **Klein:** her message said *"we'd like to pick up the laptop"*. My draft was *"it is out for
 pickup … if we are not in, you can pick it up from the 24-hour secure drop-off."* The owner
 struck the conditional: *"not if we are not in, we are not open today, just say it's out for
 pickup."* **2026-10-14 is a Wednesday — drop-off only, nobody behind the counter.** "If we are
 not in" implies someone might be there.
- **9176855761** — *"Hi I see I got a miss call from you"*. My draft re-sent the drop-off
 address and hours **he had already been given 1.5 h earlier** and answered a question he had
 not asked. His reply: *"didn't you say he already got a response that he can drop it off, why
 would we send it again?"* The message earned one sentence: we called, we missed him.
- **Pruzansky** — *"Thank you Mr Bot I already knew that"*. The honest reply is not more
 information; it is that a human read him and the shelf phone's backup clock runs out in three
 days.

**THE RULE: draft the answer to the sentence they actually sent, and check what we have already
told them in the same thread before writing a word.** Conditions and instructions we have
already sent are not new information, they are noise, and he reads them as not listening.

### 4. I typed a phone number from memory into a message to the owner

I wrote the customer's number as `9168855761` when it is **`9176855761`**. Caught by reading it
back, corrected in place, and sent nowhere — but a number I typed was a number he could have
acted on. **Copy phone numbers from the read, never through my own fingers.**

### 5. Quoting and encoding, both already in the runbook and both hit again

- A multi-line `git commit -m` through PowerShell returned **exit 1 with no output** and committed
 nothing; `git add` alone was fine and the commit needed `-F <file>`. After a failed chained
 command, **verify what actually landed before assuming which step failed.**
- `respond.py` crashed printing the send script's own output with `UnicodeEncodeError: 'charmap'`
 — **after** the send had succeeded. The runbook says the script prints emoji and Windows stdout
 is cp1252. It is now `reconfigure(encoding="utf-8")` at the top of the tool.

### 6. I showed the owner a `To:` in a format the API never receives

`send-lpt-sms.py` prints the raw number (`2167894450`); `dialpad_service._to_e164` prefixes `+1`
before the request. He approves **what the API gets**, so the tool now prints E.164. A number
displayed in one form and sent in another is the same class of defect as `SENT` describing what
we did rather than who received it.

### What was right, and worth keeping

- **The fresh-cache correction earned its place immediately**: the authority's waiting verdict
 named 90 parties and **7 had already been answered** (the index preceded the reply). That
 correction is now inside `build-response-queue.py` rather than in a session's memory.
- **The witness discipline held**: message id `6629167026970624`, cache row id `1125505`,
 `created_at` 15:43:12.336Z → `fetched_at` 15:43:15.035Z (+2.7 s = a live capture), and the
 honest statement that handset delivery is not confirmable by any Dialpad API.
- **The one thing I refused to do was right**: I did not punch a price into production or invent
 a total. That refusal is why the tax error cost a sentence instead of a wrong record.

### The tool this produced

`lpt-hub/_scratch/respond/find-stripe-payment.py` — searches **every text column**, not the
metadata keys anyone remembers, and is written to be run before a money claim is made rather
than after. Its docstring carries the incident so the next session cannot re-derive the wrong
lesson from it.
