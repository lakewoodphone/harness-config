**L1476 · A supervisor that reports rc=0 forever is not a job that works**

## A supervisor that reports rc=0 forever is not a job that works

The transcript backfill ran under a supervisor for twenty minutes. Its log looked healthy:
`attempt 1 rc=0`, `attempt 2 rc=0`, `remaining without a transcript: 1054` — and it did
**nothing at all**. Two independent defects sat behind that:

1. **`--retry-failed` widened my selector but not the pipeline.** Every row in the queue had
 a terminal failure recorded against it, and `transcribe_downloaded_recordings` skips those
 unless `force=True`. So the batch called the pipeline with 1,054 call ids and the pipeline
 skipped all of them and returned success. The flag now reaches the pipeline.
2. **The selector joined `dialpad_media_file` and stopped there.** All 1,054 rows had a media
 **row** and no **file** on disk: instant failure, every pass, zero cost, plausible-looking
 output. `os.path.exists` is the only thing that says there is audio to transcribe.

With both fixed the honest number appeared for the first time: **zero calls have real audio
and no transcript**. The 1,054 was phantom. (The 74 rows that do have files then failed in
0.0 s — they are HTML/JSON saved with an `.mp3` name, which is exactly why the downloader now
uses the *same* `_audio_file_problem` check to decide whether a recording is worth keeping.)

Three rules, and the third is the one that generalises furthest past this job:

* **A media row is not a media file; a stored path is not content.** Verify the thing, not the
 record of the thing. (L1086 said this about a Windows path; it was true again one layer down.)
* **A flag has to reach the layer that does the work.** Widening a query while the callee
 silently filters is how a retry becomes a no-op that returns success.
* **A supervised job must assert that work happened, not that the command exited 0.** The
 supervisor now counts the remaining rows each pass and, after three attempts with no
 movement, stops and says *why* — "the command is running but doing no work; check whether
 the pipeline is skipping every selected row". Exit code was the only thing it watched, and
 exit code was the one thing that never changed.

The same shape is worth checking anywhere else in this fleet where a cron entry wraps an
idempotent script: does anything measure that the *subject* of the job moved?
