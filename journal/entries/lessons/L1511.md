**L1511 · A customer search by the number as she types it returns nothing — normalise before you search**

Yocheved identifies customers by phone, and she types the number from memory, not from the record. On 2026-09-15 she asked for '848336341'. The real number on the customer's record is +1 848-333-6341 (Weitman). She dropped one digit out of the run of three 3s, so:
- grep for '848336341' across ~/lpt-hub -> ZERO hits (the only apparent matches were coincidental substrings in a different number).
- ps-system search '848336341' -> found: 0.
- contacts table LIKE '%848336341%' -> 0 rows.

The customer existed the whole time. Searching the literal string the manager types is the WRONG FIRST MOVE for a phone number.

WHAT WORKS, in order:
1. dialpad_sms_cache in the secretary DB is the fastest customer-by-phone index and it stores digits only, no punctuation: SELECT ... WHERE phone_normalized LIKE '%<last 6-7 digits>%'. That one query found this customer in one shot and also produced the entire live SMS thread.
2. Search on the STABLE TAIL of the number (the last 6-7 digits: '336341', '3336341'), not the head. Area code plus exchange (848-333) is shared by thousands of numbers; the tail is what identifies a person.
3. Only then fall back to file search. Note that ~/lpt-hub on the Mac mini is BEHIND the authoritative copy: the laptop-sale case file for this customer (cases/14in-laptop-weitman-8483336341-2026-09-14.md) does NOT exist locally and only exists at C:\Users\ezabz\Code\lpt-hub on desktop-ts (ZABZ-TECH). A miss in the local repo is not evidence the customer has no file — check the owner's desktop through ps-mesh.

EVIDENCE: dialpad_sms_cache row id 774860, phone_normalized=8483336341, inbound 2026-09-15T15:05:13Z. Case file read via 'ps-mesh file desktop-ts' 2026-09-15.
