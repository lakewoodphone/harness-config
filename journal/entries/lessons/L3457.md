**L3457 · A file in your directory is not necessarily yours - attribute a write by evidence, and read the session corpus on every node**

## A file in your directory is not necessarily yours, and a session on another machine is still the owner

Measured 2026-10-11, on the Yanofsky profile.

**What happened.** Building the profile, I found three files in my working directory that I had not
asked any worker to write: `CORRESPONDENCE.md`, a `correspondence/` folder with five audio recordings
and transcripts, and a one-line edit to my own `README.md` with a `.bak` beside it. I attributed all of
it to "a fleet worker that went beyond its brief" and wrote that attribution into `SOURCES.md` §5 as
part of the honesty record. **It was wrong.** The session log shows it was the owner's *own* iPhone
session running on the secretary (`--home-zabz-phone--`, cwd `/home/zabz/phone`), which had ssh'd into
this laptop, read the profile README to learn the layout, chosen a new path so as not to race the fleet,
scp'd the recordings in, verified sha256 on both sides, taken a byte-exact backup before editing the
README, and recorded a decision in the journal.

**The two rules this cost.**

1. **Attribute a write by evidence, not by plausibility.** The evidence was one command away the whole
 time: `node scripts/sessions.mjs find "<distinctive word>" --since 1d --all`, scoped by
 `--host <node>`. I reasoned instead — "only my workers could have done it" — and the reasoning was
 wrong because a *second concurrent session by the owner on another machine* was writing into the same
 directory, over ssh, at the same minute. **Always check the session corpus before naming who did
 something**, and check the nodes that are NOT yours too: my first search missed it because it covered
 three reachable nodes and the author was on a fourth.
2. **A head read is not a whole read.** The same search first returned "no match" twice — 374 sessions
 scanned, nothing. That was a *false negative*: `find` reads the first 256 KB of each session, and the
 phrase I searched for sat deeper than that in the multi-hundred-KB transcripts. A "no match" from a
 bounded read is a refusal, not evidence, and the tool says so in its own output. I nearly reported
 "nobody did this" on the strength of it.

**The correction is in the record, not deleted.** `SOURCES.md` §5 now carries both the wrong claim and
the right one, because a document whose honesty rests on being checkable has to survive its own author
being wrong.

**Corollary that generalises.** The owner runs sessions from his phone, from the desktop, from the
cloud — several at once. A directory under `code/` is not a private namespace, and "the fleet is the only
writer" is an assumption, never a fact. Before touching a file another agent may be writing, check who
has it open, and prefer a **new path** over an edit to a shared one — which is exactly what the phone
session did, and the right instinct to copy.
