**L2254 · A row count is not a message count**

## A row count is not a message count -- check rows against distinct payloads before believing any freshness or volume number

Measured 2026-09-20: `dialpad_sms_cache` held **4,637 rows for 201 distinct (phone, body)
pairs** in 24 hours, every row with a distinct `message_id`. The kernel's `comms_freshness`
check, whose entire job is to notice when a channel stops, read `MAX(fetched_at)` and a
"real-time lag" off that table and reported both as if they described messages.

Two cheap queries separate real traffic from a replication loop, and belong in any freshness
check that reads a mirrored table:

 COUNT(*) vs COUNT(DISTINCT phone||'|'||body)
 COUNT(DISTINCT message_id) vs COUNT(DISTINCT phone||'|'||body)

If rows are far more numerous than distinct payloads, the table is not a log of events; it
is a log of writes. Read the ratio **per day**, not once: the healthy history here was
rows == distinct (2026-09-08..09-14: 36/36, 22/22, 26/26, 15/15, 37/37), and the divergence
is recent, so a single snapshot of a busy day would have looked plausible.

The same mistake produced a false statement to the owner. Owner-queue row 116 said a
customer "sent the SAME message 13 times". He sent it **once**. The 13 was a copy count.

Corollary: when a duplicated table is the input to a freshness metric, the metric measures
the writer, not the world. Our own Dialpad webhook delivered 2 genuine events on 2026-09-20
while the table looked busier than any day in its history.
