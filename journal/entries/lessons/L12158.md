**L12158 · P1: every journal write paid ~9 minutes of git grep, and every read during a write parsed 4,764 files**

**Every journal write was paying ~9 minutes inside git, and every read taken during a write was parsing 4,764 files.** Measured on ZABZ-YOGA 2026-10-21 02:30–03:20 UTC, on the one tree all six live sessions share. This is the whole of the "all the agents are frozen" report: nothing crashed, nothing was corrupt, and no id was lost. The write path did work that was not needed, at a cost that grew with every session that did it at the same time.

## What was actually being run, per append

`cmd_append` called `git_max(kind, fetch=True)`. `git_max` ran, in order:

| step | cap in code | measured |
|---|---|---|
| `git fetch --quiet --all` | 25 s | never completed (repo is 4.85 GB, 128 packfiles) |
| `git grep -h -E '^## L[0-9]+ '` (working tree) | 60 s | **332.6 s** — killed at its cap, nothing returned |
| `git grep ... HEAD` | 60 s | killed at its cap, nothing returned |
| `git for-each-ref` then one `git grep` per ref, up to 25 | 60 s each | **15.1 s each x 25 = 377 s** |

So one append spent roughly **nine minutes** before it wrote a word. Six sessions were doing it at once, which is why the box showed `load1=0` and 22 idle CPUs while the processes sat there with 0.3–6.8 s of CPU each over sixteen minutes: they were not computing, they were waiting.

Two things made it worse than arithmetic suggests:

* **`subprocess.run(timeout=)` kills the child, not the tree.** The 25 s cap killed `git.exe` and left the `ssh` and `git index-pack` beneath it running. Every timed-out append handed a live fetch to the next one — seven `git.exe` processes and 128 packfiles were standing on the box.
* **The fetch was useless as well as slow.** It could not finish inside the cap, so `stamp.json:fetch_rc` recorded 124 and the recorded `git_ceiling` (lessons 10177) stayed behind the local maximum (11968). The ceiling that was supposed to see other machines had not been refreshed by this path at all.

## The ids were never in the file contents

An entry's id IS its filename: `entries/lessons/L1776.md`. `max_number()` already relied on that locally. So `git ls-tree -r --name-only <ref> -- journal/entries/<kind>` answers exactly what the content grep was asked:

* `ls-tree`, one ref: **0.20 s** (vs 15.1 s for `grep` on the same ref)
* 25 refs: **4.74 s** (vs 377 s)

and it can be memoised on a fingerprint of every ref, so a write that moved no ref costs one `for-each-ref` (0.13 s) and no scan at all.

## The read fallback was the other half

`ensure_cache()` returned False the instant the lock file existed, and `catalog()` then fell through to `load_entries()` — 4,764 markdown files. Quiet machine: **15.4 s**. With six appends grepping: one `journal.py status` measured **774 s (12.9 minutes)**. That is the freeze the owner actually experienced, and it fires *because* a write is happening, so writers and readers amplified each other.

## What changed (same commit, journal.py)

1. **No content grep anywhere on a ceiling.** `git_max` reads filenames from a tree listing per ref, memoised on a ref fingerprint in `stamp.json:remote_ids`.
2. **No fetch inside a write.** `spawn_ceiling_refresh()` starts a detached `journal.py refresh` and returns; the append is answered from what is already recorded. The refresh has a 300 s budget because nobody waits on it, is single-flight (marker) and rate-limited (`fetched_at`, 120 s). The old inline fetch was replaced, not merely bounded.
3. **Kill the tree, not the child.** `_kill_tree()` uses `taskkill /T /F` on Windows and `killpg` elsewhere, and `_run_bounded()` is the only way this tool starts a slow subprocess.
4. **Reads wait 3 s before giving up, then answer from SQLite.** The critical section is a file write, so the lock clears in milliseconds; and the fallback tier is now `index/journal.db` (4,764 rows, one query) instead of a file walk, reported as `CACHE stale` so the page never claims freshness it does not have.
5. **`reserved_through_others` reads 25 ledgers in one `git cat-file --batch`** instead of 25 `git show` calls: 6.49 s -> 0.67 s, verified row-for-row identical to the old reader (2930 = 2930, zero missing, zero extra).

## The latent bug this uncovered, which was not a slowdown

`rebuild_cache()` rewrote `stamp.json` from a fresh dict and carried forward only the keys it knew about. Two of the keys it silently deleted were `ledger_ceiling` — the highest window **any other host** has claimed, which `allocation_ceiling()` reads as a term — and `remote_ids`. So on 2026-10-14 the fix that made the id ceiling see other hosts' windows was being erased by the next append. `setdefault` now carries forward every key the rebuild does not own. A field a rebuild erases is not a memo, it is a race.

## After

| path | before | after |
|---|---|---|
| append, cold process, no ref moved | ~522 s | **9.96 s** |
| append, first run (spawns refresh) | ~522 s | 37 s, then 10 s |
| `status` while a write holds the lock | 774 s | 3 s cap + one query |
| `check` | 70 s | unchanged |

The remaining 10 s of an append is cold-process cost that is not git: `reserved_through_others` 0.67 s, `max_number` 0.6 s, `cache_fresh` 1.9 s, and process start. It is worth another pass — `index/journal.db` is 27.9 MB of tracked binary that makes every rebuild write a new git blob into a repo that is already 4.85 GB with 128 packfiles, and `journal.py`'s own docstring says that file is gitignored when it is not.

Rule for the next session: **a write path may not run a repo-scale grep or wait for a network fetch.** If a number needs refs, read the tree, not the bytes; if the refs need to move, move them in a detached child and say when they last moved.
