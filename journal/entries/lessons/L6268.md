# L — a human-formatted date column compared to `datetime()` returns EVERYTHING

**Hit twice in one session, and both times it would have produced a confident false headline.**

`/root/authority.db` `email_catalog.date_text` holds `"Wed, 7 Oct 2026 23:23:54 +0000"` and
`/root/.sms-inbox/inbox.db` `messages.date_sent` holds `"Wed, 30 Sep 2026 16:44:20 +0000"`. Both are
**strings that begin with a weekday**. So:

```sql
WHERE date_sent >= datetime('now','-30 days') -- 'W'(0x57) > '2'(0x32) for every row
```

is **true for every row that has ever existed**. The query returns an all-time count, labelled as a
30-day count, and nothing in the result says so.

**Measured 2026-10-15:** `SELECT COUNT(*) ... to_number LIKE '%83897895%' AND date_sent >= date('now','-30 days')`
returned **1,435**. The same question against the ISO column returned **524**. The first number would
have been a 3x overstatement presented as fact.

**The fix, and it is not "be careful":** use the ISO audit column when the table has one
(`messages.date_sent_utc`, ISO-8601). When it does not, say **which** column you filtered on and print
the MIN and MAX of that column beside the count, so the window is visible in the output rather than
assumed. A count without its window is not a measurement.

**Why this is the same lesson as the journal's existing ones:** "print the raw value next to the
predicate, so the number that decided the branch is visible", and "a window's end is when the running
process loaded the code". This is the third form — **the window's start was never applied** — and it
fails silently in the direction that makes a story better.
