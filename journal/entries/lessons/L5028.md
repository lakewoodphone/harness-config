**L5028 · A journal body with backticks written through a double-quoted shell string loses them silently - use --body-file**

A journal body containing BACKTICKED tokens must never be passed through a double-quoted shell
string. I wrote one that way and the remote bash executed every backticked word as a command
substitution, so L5025 was stored with those tokens deleted -- `update_task`, `close_task`,
`repo_*`, `github_*`, `qb_*`, `github_read_file`, `_NON_FATAL_CB_FAILURE_PATTERNS`, `d43a75a37`
and `qb_snapshot` all came back as `command not found` and vanished from the body. The table
survived because its cells were not backticked; the prose around it did not.

Symptom to look for: the append SUCCEEDS, the id is minted, `check` is clean, and the entry reads
almost right. Nothing reports the loss. It is only visible in the file.

THE FIX, and it is the general one: `journal.py append --body-file <path>`. Write the body to a
file first and pass the path. No shell quoting layer exists between the text and the record, so
nothing in it can be reinterpreted, and the same method removes the class of failure for quotes,
newlines, dollar signs and brace expansions at once.

Same family as the round-4 lesson about a PowerShell here-string wrapping a base64 cron payload
into a different token (`L4065`): the boundary between a harness and a shell edits the text, and it
does not say so. When a value's exact bytes matter, hand it over as a file.
