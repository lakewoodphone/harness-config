**L1568 · ps-mesh file is not byte-faithful - it silently mangles non-ASCII (scp is)**

`ps-mesh.mjs file <host> <path>` is NOT byte-faithful. It shells out to `cat "<path>"` over ssh,
and on the Windows hosts that flattens non-ASCII characters. It is safe for reading something to
look at, and dangerous as the read half of a read-modify-write.

Measured 2026-09-15 on a 46 KB customer case file on desktop-ts (ZABZ-TECH):

- 112 non-ASCII characters were altered, silently and with no error.
- em dash U+2014 (83 occurrences) -> ASCII hyphen `-`
- en dash U+2013 (8), arrow U+2192 (7), multiplication sign U+00D7 (6), ellipsis U+2026 (6),
 greater-or-equal U+2265 (2) -> U+FFFD replacement character
- The re-uploaded file was otherwise textually intact, which is what makes it dangerous: the
 corruption was invisible in review and only showed up as 97 "changed" lines in `git diff` for
 text nobody had edited.

DETECTION. Never eyeball this. In git, an edit of a few lines that reports ~100 changed lines is
this bug, not a real diff. For an uncommitted file, compare the non-ASCII character census:
`collections.Counter(c for c in text if ord(c) > 127)`. A count that drops to ~0 means the text
passed through a lossy path.

FIX / CORRECT WAY. `scp` is byte-faithful in both directions - verified this session: SHA256 of the
local file equalled `Get-FileHash -Algorithm SHA256` on the remote, before and after the move into
place. Cross-check with a hash every time; a matching hash is the only proof that matters.

 scp -o ConnectTimeout=20 ./file.md desktop-ts:'C:/Users/ezabz/AppData/Local/Temp/'
 shasum -a 256 ./file.md # local
 node ps-mesh.mjs run desktop-ts "... (Get-FileHash 'C:\...' -Algorithm SHA256).Hash"

Related traps in the same area:
- On a Windows host, `git show <sha>:<path> > file` in PowerShell writes UTF-16, corrupting the
 blob further. Recover objects with `git cat-file`/`git show` and write bytes explicitly, or just
 `scp` the working-copy backup.
- When rebuilding a file whose original had CRLF, normalise to LF, edit, then restore CRLF, and
 assert `text.count('\r\n') == text.count('\n')` before and after. A mixed-ending file shows as a
 whole-file rewrite in git.

REPAIR PATTERN that worked: do not patch the damaged file. Take the pristine pre-edit copy, re-apply
the intended edits to it from scratch, then assert that every line of the original survives except
the ones deliberately replaced, and that the non-ASCII census is unchanged-or-greater.
