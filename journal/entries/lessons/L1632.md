**L1632 · A seed migration re-runs on every migrate deploy and would re-activate a known-password ADMIN that someone deliberately suspended**

FINDING, verified against production (lpt_prod on lpt-apps, 2026-09-15), read-only.

backend/prisma/migrations/20251104_seed_admin_user/migration.sql seeds a KNOWN-PASSWORD account:
 email admin@test.com, bcrypt hash for 'password123' (:23), phone '+1-555-0001' (:26),
 role ADMIN, status ACTIVE, isVerified true.
and its conflict clause is a REWRITE, not a no-op:
 ON CONFLICT ("phone") DO UPDATE SET email, firstName, lastName, role, status, isVerified, updatedAt (:33-40)
Note what that UPDATE does NOT include: password. So an existing account at that phone keeps its own
password and gains role=ADMIN, status=ACTIVE, isVerified=true, while its EMAIL IS REPLACED with
admin@test.com - which redirects any password-reset flow for that account to the test address.

PRODUCTION STATE:
 users WHERE phone='+1-555-0001' -> EXISTS. role=ADMIN, status=SUSPENDED, isVerified=true,
 email is the seed address (not a real person), createdAt 2025-10-19, updatedAt 2025-12-08.
 total users = 10 (ADMIN 6, MANAGER 3, CUSTOMER 1).

So: the account exists AND SOMEONE DELIBERATELY SUSPENDED IT. The migration's DO UPDATE sets
status='ACTIVE', so a future 'prisma migrate deploy' RE-ACTIVATES a publicly-known ADMIN
credential whose password is 'password123'. The owed production rebuild runs exactly that command.

NARROWER THAN THE RAW FINDING, AND THAT MATTERS: it is not currently live. The row's updatedAt is
2025-12-08, unchanged - so today's TWO container restarts did NOT re-run migrations. That proves the
container start does not run 'migrate deploy' on this host; the Procfile's heroku-release line is a
Heroku path this deployment does not use. The trigger is an explicit migrate deploy: the rebuild, or
a Heroku release, or a hand-run command.

DO NOT EDIT THE MIGRATION. Prisma stores a checksum per applied migration; editing an applied one
makes 'migrate deploy' fail with a checksum mismatch. The durable fix is a NEW migration ordered
AFTER 20251104 that neutralises the account on every deploy (delete it, or leave it SUSPENDED).
Deleting alone is NOT sufficient: with the row gone the old migration INSERTs a FRESH admin with the
same known password, so the new migration must run after it, every time.

SECOND VERIFIED FACT, same query: 153 migrations are recorded applied and prod DOES contain
webhook_events, time_adjustments and partner_accounts - the three tables PART-068 found created by NO
migration. So production's schema was created out-of-band and the migration history would NOT
reproduce it. Newest applied: 20260909000000_add_google_identity (2026-09-10). That is a THIRD
independent reason the rebuild is dangerous, alongside the SMS migration and the checksum risk.

RULE: a migration containing INSERT ... ON CONFLICT DO UPDATE is a WRITE that re-runs on every
deploy. Read the DO UPDATE list as carefully as the INSERT - and note what it omits (here, the
password), because the omission is what makes it a silent privilege grant rather than a reset.
RULE: production evidence can settle a question that reading cannot. 'updatedAt' is unchanged since
2025-12-08, which is how we know the restarts did not run migrations - one query, no speculation.
