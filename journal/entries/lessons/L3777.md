**L3777 · The sync record is DERIVED - never hand-write it; and workOrderState can silently close a case**

## The rule

**`docs/customer-operations/sync-records/*.json` is a DERIVED artifact. Never hand-edit it.**

`tools/customer/record.py::build_record` generates it **from the case file's front matter**, and
`lpt-hub/tools/customer/` (store.py / record.py / lint.py / lock.py) is the one sanctioned write path
for both the case file and its mirror. Hand-writing the JSON means writing a shape the tool will
overwrite.

`record.py` is explicit about the contract:

- `SCHEMA_ROOT_KEYS` is the **closed** set the generator may write: `$schema`, `recordType`,
 `version`, `caseId`, `sourcePath`, `customer`, `device`, `references`, `workflow`, `referral`,
 `operational`, `pricing`, `labEscalation`, `production`, `updatedAt`. Anything else is **drift a
 scheduled projection may or may not survive** — so legacy root keys (`issue`, `status`, `notes`,
 `date`, `case_file`, `diagnosis`, `part_ordered`, `repair`) are ephemeral even when present.
- `CASE_OWNED_FIELDS` (from the case, never from the old record): `caseId`, `sourcePath`,
 `customer.name/phone/aliases`, `device.summary`, `operational.nextAction`, `updatedAt`.
- `PRESERVED_KEYS` (carried over untouched, NOT derivable from a case — dropping them is data loss):
 `references`, `workflow`, `referral`, `labEscalation`, `production`, `pricing`, `$schema`.

## Measured, 2026-10-13

- **The root `additionalProperties: false` rule is aspirational.** 190 of 427 records carry root keys
 the schema forbids; the generator itself writes only the legal shape. So a hand-written record is
 invalid *and* ephemeral, while the derived one validates.
- **A derived record validates where a hand-written one does not.** Regenerating gave
 `jsonschema: VALID`, dropped 8 forbidden keys with no information loss (that content lives in the
 case file, which is the source of truth), and normalised `customer.phone`, `sourcePath` and
 `updatedAt` for free.
- **`customer edit` short-circuits on nothing-to-do.** It warns
 `nothing-to-do: no front-matter keys, no activity and no next_action were supplied` and returns
 `record: null` **without checking drift** — so its documented read-only drift check is unreachable
 from a bare call. Passing `--regenerate-record` alone DOES regenerate.
- **`--device` exists on `new` but NOT on `edit`.** To correct a case's front-matter `device:` you
 must call `store.update_case(repo, q, fm={"device": ...}, regenerate_record=True)` directly — still
 the one store, just not reachable from the CLI. Use `expect_digest=` as the concurrency guard.
- **Front matter is load-bearing for the mirror.** This case's `device:` held the ISSUE
 ("Screen replacement - screen was ordered") rather than the device, so the derived
 `device.summary` named no device at all. Fix the front matter, then regenerate; don't patch the JSON.

## The trap that prices a device it cannot see

**`workflow.workOrderState` in `("closed", "completed", "cancelled")` makes lptcase mark the case
CLOSED** (`lptcase.py`, `closed-by-sync-record-workflow.workOrderState`). It only fires when the prose
gives no usable status, but it is a real closure signal from a mirror field. This record said
`"completed"` for an order production calls **READY_FOR_PICKUP** with money still owed — exactly the
shape that hides an uncollected device. Set it to the store's own status vocabulary.

**`tickets` has NO state column in either store** — `id, number, createdAt, updatedAt` only
(checked in `operational` and `app` on 2026-10-13). So a record's `workflow.ticketState` is a claim
nothing holds; measure before writing one, in both stores.
