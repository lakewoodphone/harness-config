**L3817 · The journal's id collisions grow ~7/hour because ZABZ-YOGA's git fetch source is the FROZEN box - the allocator reserves blind**

The journal's id allocator is not broken. Its **visibility** is, and one host's visibility is structurally empty because its fetch source is the frozen rollback anchor.

**The growth, measured.** Collisions between ZABZ-YOGA's journal and the authority's: **63 at 12:20Z, 70 at 13:20Z — about 7 new colliding ids per hour**, with the newest being `P3182`-`P3188` and `W2805`-`W2807`, the ids minted in that same hour, including ones I wrote myself. So **repairing the backlog is a treadmill**: 70 today, ~170/day. The fix has to be the allocator.

**And the allocator turns out to have a mechanism already.** `journal.py next-id pain` prints, on each host:

 ZABZ-YOGA # highest seen: P3188 (entries/ + index + log/** + flats P3188, git @ 0f9e6a16 P3188)
 # pain: reserved through P3194 for ZABZ-YOGA -> next P3189
 secratary-cloud # highest seen: P3198 (entries/ + index + log/** + flats P3198, git @ 3d565e81 P3198)
 # pain: reserved through P3229 for SECRATARY-CLOUD -> next P3199

There **is** a per-host forward reservation (`claim_map()`), and it **is** recorded in git (`git @ <sha> P3198`). It cannot work, because it is blind: each host reserves forward from the highest number **it can see**, and neither host can see the other's recent entries.

**Why the visibility is empty, and this is the part worth acting on.** The mechanism is `git_max(kind, fetch)` — *"Highest number visible in any local or remote git ref"* — which runs `git fetch --all` and then searches refs (`journal.py:3294`, and the `fetch` at `:3306`). Cross-host safety therefore requires the checkouts to share a ref. Measured, they do not, and one of them cannot:

 ZABZ-YOGA origin = secretary-ts:/home/zabz/harness-config.git (FETCH)
 offsite = https://github.com/lakewoodphone/harness-config.git (push)
 secratary-cloud origin = /root/hc-main.bundle (fetch and push)
 vault = root@2.28.33.58:/srv/git/harness-config.git

**ZABZ-YOGA fetches from `secretary-ts` — the FROZEN rollback anchor, which is masked precisely so that nothing writes to it and therefore can never receive a new commit.** So every `git fetch --all` this machine performs is guaranteed to bring nothing that changes the ceiling. It is not a slow ref or a stale one; it is a ref that is *designed never to move*. The authority, symmetrically, fetches from a local bundle whose contents are whatever that bundle last held.

**So the two hosts are each correctly reserving forward, blind, from their own maximum, and the reservations overlap whenever the two maxima are within the stride of each other — which they have been all day, because both are around P3180-P3200.** A reservation scheme with no shared clock is not a reservation scheme.

**The fix, and it is configuration rather than code.** Every host that allocates ids must fetch from **one live remote that every host pushes to**. The estate already has candidates — `offsite` (GitHub), and `vault` on `lpt-apps` — and `AGENTS.md` §6.1 already records that `origin` is a *diverged two-URL remote* that fetches from the frozen office box and pushes elsewhere, which is exactly the shape that produced this. The smallest correct change: point each host's **fetch** at the shared remote, have each host **push its journal** there on the existing schedule, and only then is `git_max`'s ceiling a shared clock. **Until that exists, no id band, stride or repair will hold**, and I am deliberately not inventing one tonight.

**What I am not claiming:** I have not verified that a push of the journals to a shared remote would make `git_max` see them — that needs a fixture, not an argument. And the backlog of 70 collisions still needs reading, pair by pair; the difference is that once the clock is shared, the backlog stops growing while it is read.
