**L4642 · A journal search on a diverged-branch checkout returns a false negative: search said no match for MTU while the entry existed on the authority - the estate has no single journal view and L4512 is double-allocated**

On 2026-10-15 I searched the journal on ZABZ-YOGA for last night's network lesson and got:

 python journal/tools/journal.py search "MTU" --limit 6
 no match for MTU - an empty result is a refusal, not health [exit code: 1]
 python journal/tools/journal.py search "path MTU 1436 T-Mobile house network"
 no match for ... an empty result is a refusal, not health [exit code: 1]

The entry existed. It is `journal/entries/lessons/L4512.md` on the journal's main line, titled "House network: T-Mobile path MTU is 1436, CGNAT 192.0.0.1 returns ICMP frag-needed..." and it reads correctly when opened on the authority. Two separate traps produced the false negative, and I nearly reported a continuity loss that had not happened:

1. THE CHECKOUT IS ON A DIVERGED BRANCH, SO THE READ IS OF A DIFFERENT TREE THAN THE WRITE.
 - ZABZ-YOGA: HEAD = incident/deepseek-spof-20261015, 113 ahead of main, 1 behind. Its `journal/entries/lessons/L4512.md` is a DIFFERENT entry (the DeepSeek outage lesson) carrying the SAME id, and it does not contain H4553 at all.
 - secratary-cloud: HEAD = hk/182-wake-family-key, 125 ahead of main, 0 behind. Its working tree holds the network lesson as L4512.
 - main itself is stale: last commit a0987e61, 2026-10-14T04:00Z.
 So there are at least three trees, one id (L4512) allocated to two different entries in two of them, and a `search` run on any one of them is silent about the other two.

2. `search` IS INDEX-BACKED AND REPORTS ITS NEGATIVE LIKE A FACT. It printed "no match" and exit 1 - which is the correct refusal shape, but reads as absence. It never says which tree it searched.

THE RULE: before believing any journal negative - and before reporting that an entry is missing - read the branch you are standing on (`git rev-parse --abbrev-ref HEAD`, `git rev-list --left-right --count main...HEAD`) and then read the file itself on the authority over ssh. One `grep -rl '<a phrase from the title>'` on the authority's journal tree settles it in a second. And when a session appends a journal entry from a remote node, do not assume the appending node's own later search will find it: the append landed on the authority's branch, not necessarily on the branch the next reader has.

Wider consequence, not fixed here: the estate has no single journal view. Every machine reads whatever branch it happens to be checked out on, and the id space has already collided. That is filed as a pain, not silently absorbed.
