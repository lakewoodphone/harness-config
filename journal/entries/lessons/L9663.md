**L9663 · the kosher suite is 1667/0/17 and the chunk-1 crash is the long-lived process, not a test**

Corrects H9388 on one point, and closes the suite measurement it left open.

H9388 said "Chunk 1's crash: 32 test files ... Leading candidates: test_screenshot_classifier_benchmark.py,
test_websocket_benchmark.py (a hypothesis, not measured). Bisect it". That instruction was wrong in
its premise: there is no crashing test to bisect.

MEASURED 2026-10-19, same checkout, same interpreter, same 32 files:
- One process, 232 tests: dies with `Windows fatal exception: access violation` in CPython's
 platform.win32_ver() -> platform.py:327 _wmi_query, after roughly half an hour.
- `--collect-only` over all 32 files: 232 tests collected in 21.98 s, exit 0. So it is not import.
- The same 32 files re-run as EIGHT processes of four: 45, 23, 13, 34, 23, 41, 18, 35 = 232 passed,
 0 failed, 0 error, 0 skipped, every process exit 0.

CONCLUSION: the crash belongs to one long-lived process, not to any test. WHOLE SUITE, first complete
measurement this repo has had: 1684 collected, 1667 passed, 0 failed, 17 skipped, over 250 files,
assembled from 15 processes (7 chunks + these 8 groups). Recorded in docs/testing-matrix.md with the
method named, so nobody quotes 1667 as if one run produced it.

The CAUSE of the access violation is not established and I did not name one: a one-off native WMI
failure, an accumulation across 232 tests in one interpreter, and a thread left running by an earlier
test are all consistent with the evidence. Reproducing it deliberately is the open item.

THREE METHODS THAT FAILED ON THE WAY, so the next session does not repeat them:
1. `pytest -v > log` and then reading the tail: Python block-buffers when redirected, so a crash
 truncates exactly the lines naming the test. `-u` did not fix it through pytest's writer either.
 Per-process splitting identifies the culprit by *which process died*, which no buffering can hide.
2. `$Error` is a read-only automatic variable in PowerShell; a driver that assigns to it dies at the
 assignment, after the work is done and before the summary. (Same family as `$env:TEMP` resolving
 differently between tool calls - pass absolute paths.)
3. `Get-ChildItem -Include *.ps1` without `-Recurse` or a wildcard path matches nothing, and an empty
 result reads exactly like "there are no such files".
