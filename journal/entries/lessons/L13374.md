**L13374 · A documented script is not an existing script, a legacy host can be NXDOMAIN, and a format check written from memory will blame the owner for your bug**

**L — A documented script is not an existing script, a legacy host can be NXDOMAIN, and a format check written from memory will blame the owner for your bug.**

**Measured 2026-10-23 on ZABZ-YOGA, in one session, all five of these:**

1. **A README is not an inventory.** `lpt-hub/docs/customer-operations/sourcing/README.md`
 documented four scripts — `find-flip-deals.py`, `ebay_laptop_search.py`, `laptop_sourcing.py`,
 `collect_ebay_listing_images.py` — with usage examples and a tool table. **None existed.** Not in
 `git log --all -- <path>` on any ref, not in the estate file index. The only places the names
 survived were the README and a transcript of a previous session already looking for them. *Check
 a documented path with `git log --all -- <path>` and the file index before believing it, and when
 you correct the doc, say in it which paths were proven absent and how.*

2. **"Deprecated" is not the same measurement as "unreachable", and neither is 410.** Three
 different failures, three different commands:
 * `open.api.ebay.com` — **DNS: no such host**. The Shopping API hostname no longer resolves, so
 `laptop_sourcing_order_executor.py` cannot succeed no matter what the code does.
 * `api.ebay.com/ws/api.dll` — **HTTP 410 Gone**. The host answers; the API is retired.
 * eBay sold/completed — **login-gated**, a 200 for a login page if you do not check the body.
 Probe the *host* first. A DNS failure and a 410 are not the same defect and do not get the same
 remediation.

3. **Before you tell the owner his input is malformed, read the vendor's own format.** I wrote a
 Cert ID validator from memory demanding `PRD-` + `12-4-4-4-12` (36 hex). It met the owner's value
 — `PRD-` + `12-4-4-4-4`, 32 characters — and produced a confident sentence: *"TRUNCATED: last
 group has 4 of 12 hex characters, so 8 characters are missing."* The owner's value was canonical.
 eBay's own docs, [apitut](https://apitut.com/ebay/oauth.html) and
 [ebaymcp](https://ebaymcp.com/authentication/client-credentials) all show a 4-character final
 group. **The validator was the defect**, and had I not checked, the next thing the owner heard
 would have been a demand to re-paste a secret that was already correct. A shape check that only
 knows one legal layout is a machine for blaming the wrong party.

4. **`invalid_client` cannot localise which half of a credential pair is wrong, and must not be
 made to pretend it can.** eBay returns it for a wrong client id AND a wrong secret, and no probe
 distinguishes them — the Trading API asymmetry that used to (`X-EBAY-API-APP-NAME` vs
 `X-EBAY-API-CERT-NAME`) died with the 410. The honest output is: the pair is rejected, the
 request shape was accepted (a malformed grant returns `invalid_request` /
 `unsupported_grant_type`), here is what is checkable locally, here are the three likely causes in
 order. Anything more specific would be invention.

5. **A job table is the only evidence that a pipeline is alive.** `research_dispatcher.py` is 130 KB
 of working machinery and looks healthy from the filesystem. `research_jobs` on the authority says
 the newest submission was **2026-07-08T05:40:32Z**: 324 complete, 70 queued, 51 failed, 3 rows
 still `running` since 2026-07-03. Nothing alerted, because nothing asserts freshness — the same
 defect class `tool-body-guard.py` and the search-index freshness job exist to end. *When you are
 asked whether a pipeline works, read its job table, not its source file.*

**Corollary for credentials:** a credential test cannot test code and a code test cannot test
credentials. Write both, and report which one you ran. `ebay_api.py selftest` is 17/17 against a
local stand-in; that says nothing whatever about the keyset, and `doctor` is the one that says the
keyset is not accepted yet.
