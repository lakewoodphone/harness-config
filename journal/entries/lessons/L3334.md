**L3334 · A delegated subagent has no delegation: mesh children fail with 'target profile did not run' and local depth-2 is refused**

MEASURED 2026-10-06, ZABZ-YOGA, from a depth-1 delegated subagent session.

WHAT I TRIED: fan out four independent research pieces using the `subagent` tool (the mesh provider), then a local fallback when that failed.

WHAT HAPPENED, in order:

1. Four `subagent` calls with run_in_background. All four failed with the provider's own diagnostic, quoted exactly:
 "the remote process exited 0 but printed no completion frame -- the target profile did not run"
 Child messages contained only the transport preamble:
 FANOUT_TRANSPORT_HOST_<id>=ZABZ-TECH / FANOUT_TRANSPORT_CWD_<id>=C:\Users\ezabz / FANOUT_BEGIN_<id>
 So the transport reached ZABZ-TECH but the child profile never launched there. This is not an ssh failure and not a target-down failure.

2. Fallback to `subagent_local`. Both retries failed instantly:
 "SubagentDepthError: subagent depth 2 exceeds maxDepth 1"

WHY DEPTH 2 IS REFUSED: this session was itself started as a delegated subagent, so it is already at depth 1. maxDepth is 1. A subagent therefore cannot delegate AT ALL -- not remotely, not locally, not by fork. `subagent_fork` is unusable in that position too.

THE RULE, so a future me does not spend steps rediscovering this: if you are a delegated subagent and the task needs fan-out, check first whether this session was started by another agent. If it was, plan single-threaded from the start and say so in the reply, so the delegating agent can fan the work out at ITS depth, where it does have children. Do not burn a dozen tool calls proving you have no fleet.

SECOND RULE, about honest provenance: when the mesh fails, quote the provider diagnostic, say in one line that the mesh was unreachable, and label every result that came from a local fallback as LOCAL. Here no fallback ran at all, so the correct statement was the opposite of a LOCAL mark -- "nothing came from a subagent" -- and that is just as important to say out loud.

THIRD OBSERVATION: job_list showed these children as "running" for a while before the failure notice arrived, but they had never started on the target. Do not treat "running" from job_list as evidence a child is doing work on the mesh; `mesh_children` is the tool that reports real remote state.

EVIDENCE: job_list entries subagent-43 through subagent-48; job_output for each; the two distinct diagnostics above, quoted verbatim.
