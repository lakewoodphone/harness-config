**L2137 · L2151 - the watchdog was innocent: my own load test starved the API past its health timeout, and the watchdog restarted it correctly**

Measured 2026-09-20, and it is a lesson about attributing causes to the last thing that acted.

**What I saw.** Twelve restarts of `secretary-api` in 90 minutes, three of which I had not caused
myself (17:54:06, 18:09:42, 18:13:02). A one-minute timer (`secretary-access-watchdog.timer`) and a log
line claiming "access watchdog ok" sat next to them. The obvious reading was "the watchdog is
restarting the API in a loop" - and `access-watchdog.sh`'s own header describes a previous version of
exactly that bug (339 API starts in 7 days, median gap 70 s).

**What was actually true.** The watchdog's own log:

 18:06:05 API health failed at http://localhost:8002/health (2/3 consecutive)
 18:07:17 API health failed (3/3 consecutive)
 18:07:19 restarting secretary-api after 3 consecutive health failures
 18:09:42 secretary-api health check failed but it activated only 0s ago (grace 600s); not restarting
 ...then "access watchdog ok" every minute

It restarted the API **once**, after three consecutive confirmed failures, and then correctly *declined*
to restart again inside its 600 s startup grace. The script carries five guards (activating counts as
alive, a 3-failure threshold, a per-service cooldown, a startup grace window, and an flock
single-flight) and every one of them behaved.

**The cause was me.** At 18:01 I started the full test suite to satisfy the objective's "verified by
tests". On a 4-core box it drove load to 7.88, free memory to 500 MB, and `/health` past its 15 s
timeout. **The API was genuinely unhealthy, and the watchdog was right.** I stopped the suite at 18:08;
the watchdog has logged "ok" every minute since.

**The generalisable rule.** When something is acting repeatedly and badly, check whether it is *reacting*
to a condition you created before concluding it is the fault. The tell here was in the script's own
documentation: it describes a guard set that exists precisely to prevent the failure I was about to
attribute to it, which meant the odds were good the guards were working and something else was driving
them. A component with five named guards is worth reading before accusing.

**Second-order lesson about my own verification.** This is the second way my test suite harmed the
system today (the first: it made `run_once` exceed its ceiling and be abandoned). **A verification step
that degrades the system is a load test, and a load test needs its own budget and its own machine.** It
should have gone to ZABZ-TECH (32 cores) from the start; I had already recorded that and then ran it on
the authority anyway.
