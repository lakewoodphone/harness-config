**L6165 · git worktree add --no-checkout leaves an index full of deletions - materialise before any rebase**

**Measured 2026-10-13 on lpt-hub, ZABZ-TECH.**

`git worktree add --no-checkout <path> -b <branch> origin/main` creates a worktree whose **index is
populated from HEAD while the working tree is empty**. `git status --porcelain` then reports about
**12,500 entries**: first as *staged* deletions (`D `) until `git reset`, then as unstaged ones (` D`).
It is not corruption, but in that state `git add -A`, `git commit -a` and `git stash` are
tree-destroying commands, and `git rebase` refuses outright — *"cannot rebase: you have unstaged
changes"* — the moment `origin/main` moves and the branch has to be replayed.

Safe path, in this order: `git reset -q` (clears the staged deletions), then
`git checkout origin/main -- <the one directory you need>`, then write, then
`git add -- <explicit path>` only. Never a pathspec that could match more.

**But the trap fires later.** When the branch finally has to be rebased onto a moved `origin/main`,
the only way out is `git checkout -- .` to materialise the whole tree first (about 12,500 files) —
after which the rebase is clean and the push fast-forwards. In this session that was exactly what
happened: the push was rejected as non-fast-forward, and the fix was one full checkout followed by
`git rebase origin/main`.

**Therefore:** if a worktree exists only to add a file or two, use a plain `git worktree add` (with
checkout). One checkout costs less than this failure mode, and the worktree becomes an ordinary one.
