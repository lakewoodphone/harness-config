**L3250 · A batch job that holds the SQLite write lock across network I/O is the outage; measure in_transaction at every network boundary**

A `database is locked` that lands on the FIRST write of a batch job is almost never a missing
busy_timeout. On this estate the timeout was already 10 000 ms (app/database.py:99) and a 60 s
retry helper (`commit_retry`) was sitting there unused. The real shape was:

 * the job borrowed app/database.py's CACHED per-thread connection via `_get_conn` and then
 closed it - the closure is recorded by that module as `closed_on_handout`, and measured on a
 real run the connection came back with `_ps_closed_reason=explicit_close_by_owner`; and
 * it opened a write transaction on its first upsert and held it until the final commit, ACROSS
 every subsequent network call.

MEASURED 2026-10-05 (secratary, personal-secretary-mvp): `sync_email_catalog` reproduced
`sqlite3.OperationalError: database is locked`, sqlite_errorcode 5 = SQLITE_BUSY, after 10.6 s,
traceback landing on app/services/email_intake.py:500 - the `INSERT INTO email_sync_runs`.
With a 16 s lock held by a second process (`BEGIN IMMEDIATE; sleep; ROLLBACK`, zero data change)
it failed every time.

THE RECIPE THAT FOUND IT - instrument, do not read the code and theorise:
 * monkeypatch the module's own connection factory to capture the connection object;
 * monkeypatch the network function it calls;
 * print `conn.in_transaction` at every network-call boundary.
BEFORE the fix: 4 of 5 Gmail calls entered with `in_transaction=True` - 11.1 s of the ONE write
lock this database has, spent on sockets, while every other writer on the box (the autopilot,
every HTTP handler) waited on it and, past 10 s, failed.
AFTER: 0 of 5.

WHY IT GENERALISES: the same store records 900-902 s LEAKED write transactions
(error_log 2026-10-05T02:26:41Z, `db_contention kind=leaked_transaction`), so a 10 s busy wait is
nowhere near enough on this box. Any batch job that holds the write lock longer than the busy
timeout of EVERY OTHER WRITER has itself become the outage.

THE FIX SHAPE (committed 4fed4a6d, app/services/email_intake.py): own the connection
(`connect_db`) instead of borrowing the cached one; a longer busy timeout (15 s) for the batch
job; statement-level SQLITE_BUSY retry with capped backoff bounded by the same
LOCK_RETRY_TOTAL_BUDGET_S the commit path uses; `commit_retry()` on every commit so a give-up is
RECORDED; and a batch commit every N upserts plus one after each network pass. Batch size is the
lock-hold bound: it is what keeps the lock out of the socket.

Counter-check worth keeping: a trivial INSERT+commit from a fresh process SUCCEEDED on this same
box at the same minute. "It works when I run it" is not evidence that contention is absent - it
is evidence that you ran it when the lock was free.
