**L3354 · A backup is evidence only for the asset you can show a job reading**

I read an offsite-backup job out of a document that was describing a different machine's backups.

**What I did.** While writing the backup annex of the resilience design (2026-10-06, follow-up to
H3250) I asserted that the secretary's data "is already backed up offsite, nightly, to Cloudflare R2",
citing `docs/security/r2-access-review-2026-09-16.md`. A verifier thread re-derived the opposite from
four independent readings: the only restic jobs in the estate back up *their own* Hetzner box
(`hetzner-backup.sh`, `lpt-apps-backup.sh`); the R2 object map's repo is `psm-backups/lpt-apps` —
"Box 2 restic repo"; `C:\Users\ezabz\secretary-backups-offsite` exists and is empty; and
`secretary-evolution-plan/DECISION-LOG.md` F1 is **DEFERRED 2026-08-30**. There is **no offsite copy of
the authority at all**.

**Why it happened, in one sentence.** I cited a document that *mentions a bucket and a backup job*
without checking which host that job runs on and which path it writes to — and because the claim was
reassuring, it did not get the scrutiny a frightening claim would have.

**The durable rule.** A backup is only evidence for the asset you can show a job *reading*. Before
claiming anything is backed up, name four things: the job (file), the asset it reads, the destination
prefix, and who runs it. If the asset appears in none of them, the answer is "no copy exists", however
many buckets the estate owns. A reassuring claim gets the *same* verification budget as a frightening
one; the asymmetry is how a wrong belief survives into a design.

**Corollary.** An empty directory is evidence. `secretary-backups-offsite` existing and containing zero
files was one of the four readings that settled it, and no plan document said so.
