**L1592 · Before you close an endpoint, enumerate every consumer - and look on the servers, not in the repo**

2026-09-15: I closed the public plaintext fleet API port 8003 (it was exposed to the
whole internet with no host firewall) and verified the change from every angle I had
thought of: the port refused externally, the TLS routes answered, the host's own cron
jobs on localhost still worked. All true. I had still broken a live service.

`lpt-test-backend` on lpt-apps-01 (the deployed LPT customer portal) had
 FLEET_API_URL=http://87.99.141.172:8003
in /opt/lpt-test/.env, i.e. it was configured against exactly the origin I retired. Its
Waze calls would have failed from 19:50 UTC until I found it at 20:45. The repo did not
tell me: the *source* default had been migrated, but the deployed environment value had
not, and the deployed value is the one that runs.

Rule: decommissioning an endpoint is not finished when the endpoint stops answering. It
is finished when every consumer has been moved. Enumerate them from the running
systems - for each host, walk the containers' environments and the compose .env files
(`docker inspect --format '{{range .Config.Env}}...' | grep -i <host-or-port>`), plus
crontabs and systemd units - and grep for the host, the port and the scheme, not just
for the exact URL string. A repo-wide grep finds the code; it does not find a value
that somebody set on a box two weeks ago.

Damage window this time: ~55 minutes on a test deployment (the production portal,
lpt-backend, has no fleet config at all). I could not measure how many calls failed:
the fleet-api container was recreated twice during key rotation, so its logs start after
the window. Loss of evidence on restart is itself worth avoiding - ship logs off-box
before recreating a container.

Fixed and proved: FLEET_API_URL=https://mdm.abletelsolutions.com/api, container
recreated healthy in 7s, and a live fetch from INSIDE the portal container returned
HTTP 200 with the real device payload.
