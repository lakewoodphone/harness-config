**L1907 · A mesh-synced repo can DIVERGE, not just lag - prove it by hash before pulling**

The lpt-hub repo on ZABZ-YOGA was on a **parallel lineage**, not a stale clone. Measured 2026-09-17:

- `git rev-list --left-right --count HEAD...origin/main` = **50 ahead / 4862 behind**. The merge-base (29931cf8) *was* an ancestor of origin/main, so this was a true divergence, not a shallow-clone artefact.
- It is **the same workstream duplicated by the ps-mesh sync, not independent work.** Proof, not inference: `docs/customer-operations/cases/14in-laptop-weitman-8483336341-2026-09-14.md` is **byte-identical** on both sides under different SHAs (local `71baaffe4` "case(weitman): blank line before the UPDATE heading" vs origin `293211cee` "case(weitman): whitespace fix only - blank line before the UPDATE heading"). The waze audit + system-analysis files were byte-identical too, verified by SHA-256, not by line count.
- **Neither side contained the other.** 50 local commits uniquely held `tools/case-index/lptcase.py`, `docs/customer-operations/CASE-FILE-STANDARD.md` and `scripts/customer-operations/` — `git log origin/main -- tools/case-index/lptcase.py` is **empty**: the tool had never existed on origin. Meanwhile origin had 4,862 commits of customer-ops corpus, the `CUSTOMER-SMS-RUNBOOK.md`, and the production-order linking.

**So "pull to get the newer info" is the wrong model when the two histories have diverged.** The right first move is to determine *which history holds what*, then merge — a plain `git pull --rebase` would have replayed 50 commits onto 4,862 and produced conflict noise across 256 files.

**Method that worked, in order:**
1. `git rev-list --left-right --count HEAD...origin/main` — is this behind, or diverged?
2. `git merge-base --is-ancestor <base> origin/main` — distinguishes divergence from a shallow clone.
3. Compare a file **both** sides touched, by **hash** (`git show HEAD:f | Get-FileHash` vs origin's) — identical content proves duplicated lineage; this is what settles "is my work already upstream?" in one command.
4. `git merge-tree --write-tree HEAD origin/main` — a **dry run** that lists conflicts without touching the working tree. Do this before committing anything. (Caveat: it predicted the Fishman case file would auto-merge cleanly, and the real merge then conflicted there — the dry run bounds the risk but does not replace resolving for real.)
5. `git bundle create <backup>.bundle HEAD` (1.2 GB here) plus copies of the specific files, before any merge.

**Conflict resolution needed judgement, not a side-picker.** 10 files conflicted. Two were `updatedAt`-only (take the newer). The rest had genuinely different content on each side and were resolved by *checking a third source* (the authority DB, or the calling machine) rather than by preferring a side:
- eli-green + panasonic: origin's side was the **later, authoritative** state (case CLOSED / mod RESOLVED 2026-09-16) — kept as current, with my older blocked state retained as the earlier record.
- weissman + newman: my side held the accurate workflow state and richer notes; origin's held payment records and production links — unioned, with the contradicting claim **flagged** rather than silently picked.

After resolving: `git grep -n -E '^(<<<<<<< |>>>>>>> )'` for leftover markers (only a *documentation example* of git conflicts remained, in a `.txt` — that is a benign match, do not "fix" it), all 381 sync-record JSONs parse, and `lptcase.py check` shows only pre-existing corpus drift.
