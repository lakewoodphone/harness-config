**L2252 · dsregcmd NgcSet is a workplace/Entra flag, not evidence about a local Microsoft-account Hello container**

**`dsregcmd /status` `NgcSet` is a workplace/Entra flag and is NOT evidence about a local Microsoft-account Windows Hello container. Do not cite it either way.**

Found 2026-09-20 auditing ZABZ-TECH. `dsregcmd /status` on that machine reports `NgcSet : NO`, `AzureAdJoined : NO`, `WorkplaceJoined : NO`, while at the same moment the `Microsoft-Windows-HelloForBusiness` log shows `[8002] Successfully loaded an existing hardware Windows Hello container … State: Okay`, `PIN protector = true`, `Has Cached Logon Key: true`, and the user is signing in with a PIN.

`NgcSet` answers "has a Windows Hello for Business container been provisioned for a *joined* identity". With no Entra join and no domain there is no such identity, so it reads NO regardless of the state of the local MSA container. It read NO on ZABZ-TECH's known-healthy boot of 2026-09-17 too.

Why this matters enough to be an entry: `NgcSet : NO` had been written into `docs/mesh/117-zabz-tech-hello-and-boot.md` as corroborating evidence that Windows had deleted the container. It is not evidence of that, and a future reader would have used it to conclude the container was still missing *while it was demonstrably loaded and healthy* — the exact shape of the "stale reading, believed, reported as a crisis" failure this journal exists to prevent.

THE RULE: for local Windows Hello state, use the `Microsoft-Windows-HelloForBusiness/Operational` log — `8002 … State: Okay` with `PIN protector = true` is a usable container; `7002 … 0xD000A002` followed by `3611` is a destroyed one. Anything from `dsregcmd` describes the *joined-identity* picture and must not be substituted for it. Corrected in place in doc 117.
