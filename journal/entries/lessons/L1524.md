**L1524 · A repo status line and a DNS lookup are not deploy state - a loopback-bound container behind an unreloaded proxy is deployed and invisible at once**

## L — A repo status line is not deploy state; probe the host

**The error.** On 2026-09-15 I told the owner the filter's customer website was "built, never
deployed", because (a) `filterapp.lakewoodphoneandtech.com` did not resolve and (b) the repo said
W-BACK-056 was "AUTHORED 2026-09-14, not yet applied". Both were true. The conclusion was false.

**What was actually true** (verified by me on the host the same hour): `ssh lpt-apps` ->
`lpt_filter_site Up 4 hours (healthy) 127.0.0.1:8080->8080/tcp`; `/opt/caddy/Caddyfile:47` carries
the `filterapp.lakewoodphoneandtech.com` block; loopback `/healthz` 200 and `/` 200. Caddy itself
had been up 5 days, so it is genuinely holding pre-block config — the missing pieces are a
Cloudflare A record and one `caddy reload`, nothing else.

**Why it happened.** A DNS NXDOMAIN proves the *name* does not resolve. It does not prove the
*service* is absent. A loopback-bound container behind an unreloaded reverse proxy is deployed and
invisible at the same time, and "does not resolve" is exactly what a not-yet-deployed service looks
like too — so the observation cannot distinguish the two cases. I let a repo doc break the tie, when
the doc was written from a different machine that had no docker.

**The rule.** Deploy state is read from the host: `docker ps`, the reverse-proxy config, and a
loopback probe. A repo's status line and a DNS lookup are both hearsay about deployment. When they
are the only evidence, the honest answer is "I have not checked the host", not a conclusion.

**Relation to existing lessons.** Same family as L219 ("check the actual value, not a pattern that
happens to match") and H207's correction of its own earlier report (measured the variable's length
instead of trusting a regex that matched).
