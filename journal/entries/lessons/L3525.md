**L3525 · Three ways I nearly fooled myself verifying a card: string Length, counting matches instead of lines, scratch inside a wiped directory**

Three separate ways I nearly fooled myself while checking a returned SD card on 2026-10-11.
None of these is exotic and all three cost real time.

1. **`$f.Length` on a string is the path's length, not the file's.** In a PowerShell file
 validator, `if ($f.Length -lt 16) { continue }` and `($off + 8) -le $f.Length` where `$f`
 came from `EnumerateFiles` are both comparing against the number of CHARACTERS IN THE
 PATH (~90). The atom-walk loop therefore never ran once, and the check reported the files
 as invalid rather than as unchecked. Use `(New-Object System.IO.FileInfo $f).Length`.
2. **Counting regex matches is not counting lines.** A file listed once in
 `DID-NOT-ARRIVE.txt` contains its own path twice — once as the source path, once inside
 Windows' own "being used by another process" message. `[regex]::Matches($t,'locked\.dat')`
 returned 2 and the test reported a duplication defect that did not exist. Count matching
 LINES.
3. **Do not keep scratch files inside a directory a test harness wipes.** `run-tests.ps1`
 removes and rebuilds `C:\_lpttest` on every run; a validator script parked there was
 deleted mid-flight, and the next edit failed with "file no longer exists". Durable tools
 go in the repo's `test/` directory, which is where `validate-card-content.ps1` now lives.

The common thread: each of these produced a confident statement about something I had not
actually measured. Read the number back, and prefer the reading that can be wrong in the
direction of "I did not check" over the one that reads as a verdict.
