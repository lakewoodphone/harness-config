**L10494 · reminders.scheduled_time is compared as a STRING: write UTC or it fires hours early**

Found while scheduling the owner's SNAP interview reminder (case C202417015, 2026-10-23 08:00 EDT).

`list_due_reminders` (app/database.py:11410) selects `scheduled_time <= ?` against
`_now_iso()` = `datetime.now(timezone.utc).isoformat()`. **That is a STRING comparison in SQLite,
not a datetime comparison.** An offset suffix is therefore invisible to it.

Measured, both forms, now = 2026-10-23T10:44:00+00:00:

 2026-10-23T10:45:00+00:00 due? False <- correct: 10:45 UTC = 06:45 EDT
 2026-10-23T06:45:00-04:00 due? True <- WRONG: fires at 06:45 UTC = 02:45 EDT, 4h early

So a reminder written in local time with a real offset fires at the wall-clock digits it displays,
in UTC. Six live rows in `reminders` carry `-04:00` (e.g. 674 '2026-10-18T11:00:00-04:00'), so this
has silently delivered early before.

Rule: **every row written to `reminders.scheduled_time` must be UTC with `+00:00`.** Convert the
owner's local intent yourself and put the arithmetic in the reminder's own record.

Two more things proven the same night, worth not re-deriving:
- `compose_reminder_sentence` rewrites the body at send time and appends a period to EACH `. `-
 separated sentence, so "case C202417015. Be up" arrives as "case C202417015.; Be up". Write one
 clause chain, no internal full stops, and test the exact string through the composer first.
- `process_due_reminders` demotes any channel='sms' reminder whose text matches
 `lpt-hub|docs/|/home/|~/\.md|\.py|task \d{3,}` to a HELD dashboard message. A reminder containing a
 file path never reaches the phone and says nothing about it.
