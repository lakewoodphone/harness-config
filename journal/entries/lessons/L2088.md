**L2088 · A mesh fleet can build on a repo that exists on ONE machine - clone from the authority, deliver a bundle, and precheck the link**

**L · A mesh fleet can build on a repo that exists on only ONE machine - clone from the always-on authority, deliver as a git bundle. And the manager must check the link before sending a script that writes.**

Measured 2026-09-20 (ZABZ-YOGA, CFO session). The facts that shaped the design:

1. **The repo existed only on the laptop.** `lpt-books` had **no remote at all** (`git remote -v` empty)
 and eight fleet branches plus five live worktrees under `C:\Users\ezabz\code\lpt-books-wt\`. The broker
 places `subagent` children on **ZABZ-TECH** by default (verified by a placement probe: the child
 reported `zabz-tech`, `C:\Users\ezabz\code\lpt-books = missing`). So a mesh child could see neither the
 repo nor its worktrees, and pinning placement would have needed `MESH_TARGET_NODE` plus an engine
 reload - i.e. restarting the session doing the dispatch.

2. **The fix is one bare repo on the always-on node.** `git init --bare ~/repos/lpt-books.git` on
 `secratary`, then `git push authority --all` from the laptop. Every node already has the
 `secratary-ts` ssh alias, so **any** node can `git clone secratary-ts:/home/zabz/repos/lpt-books.git`
 and `git ls-remote` it - verified from ZABZ-TECH before any child was dispatched.

3. **Delivery without letting an agent push.** Children commit to their own `fleet/<ws>` branch and then
 `git bundle create wsN.bundle fleet/wsN` + `scp` the bundle to a drop directory on the authority
 (`~/accounting-data/fleet-incoming/`). The manager collects and integrates. The "never let an agent
 push" rule survives intact, and a bundle still carries the full branch.

4. **The data went to the children, not the children to the data.** Rather than have each child ssh into
 a 5.5 GB live database, the manager ran the ingest ONCE on the authority against the real store and
 published a **19 MB snapshot** of the populated `books.db`. Every child then worked against real data
 with **zero** ssh dependency: no live feed, no locks, no flake. This is generally the right split -
 the manager does the expensive, remote, authoritative read once and hands out a frozen copy.

5. **The trap that cost two dispatches: the tailnet hop to the authority is intermittent.** Measured the
 same hour: `ssh secratary-ts` succeeded on 4 consecutive TCP-22 probes, then failed with
 `Connection timed out` / `banner exchange: Connection to UNKNOWN port -1` on roughly 1 attempt in 5
 over the next 30 minutes, and it killed one `subagent` dispatch outright
 (`broker-unreachable: ... ssh exited 255`). It bit hardest on a **multi-write** script: a 7-section
 remote update ran sections B/C/D to completion and then died mid-section E, leaving the queue updates
 un-applied while the obligation updates had landed.

 **The rule that comes out of it:** before sending a script whose sections WRITE, prove the link with a
 cheap `ssh ... "echo READY"` in a retry loop, and only then send the real payload once. A blind retry
 of a write script is how you get state applied twice or half-applied. The working pattern:

 ```powershell
 for ($i=1; $i -le 12; $i++) {
 $p = ssh -o ConnectTimeout=12 -o BatchMode=yes secratary-ts "echo READY" 2>&1
 if ($LASTEXITCODE -eq 0 -and "$p" -match 'READY') { $live = $true; break }
 Start-Sleep -Seconds 5
 }
 if (-not $live) { 'AUTHORITY UNREACHABLE - nothing sent'; exit 1 }
 ```

6. **Line endings, again.** Piping a `.sh` written on Windows into `ssh host "bash -s"` injects CR into
 every line; bash reports `$'\r': command not found` at the first heredoc terminator and can otherwise
 corrupt the payload. Strip it at the source: `(Get-Content f.sh -Raw) -replace "`r","" | ssh ...`.
 Heredocs *do* work inside a piped script - the CR was the only problem.
