**L3787 · The lpt-hub clone on secratary-ts is two days stale and answers like a complete case - grep a case file by date before quoting it, and know that pushed and on-main are different questions**

**The lpt-hub clone on the authority line is the STALE one, and it will hand you a two-day-old case silently.**

MEASURED 2026-10-14, asked to pull up the Fisher case (WO26101112743). Three copies of the same case file
exist in this estate and two of them are old:

| where | what it held | how I know |
|---|---|---|
| the laptop clone, `C:\Users\ezabz\Code\lpt-hub` | the CURRENT file - 490 lines, sections through 2026-10-13/14 | `read` on the file; commit `910483a65` pushed to `origin/shift/lpt-sync-item41-wo-relink-20261014` |
| `ssh secratary-ts:/home/zabz/repos/lpt-hub` | 231 lines, ends at the 2026-10-11 park | read it first; `grep -c '2026-10-12\|2026-10-13'` = 0; mtime 2026-10-12 17:39 |
| `origin/main` | 231 lines too - the same old file | `git show origin/main:<path>` |

The trap is that the authority line answers instantly and confidently, and its answer looks like a
complete case: a front matter, a status, a list of options, a "NEXT". Nothing in it says *two days of work
are missing*, because the missing part is the newest part. Had I written the report from that copy I would
have told him the case was last understood on 2026-10-11 and that the 50 park was the whole story - while
the customer's own account, the candidate card and the withdrawn clearance all sit in the newer sections.
That is a `wrong-data` report made out of a perfectly healthy-looking file.

WHY IT IS THIS WAY, not breakage: lpt-hub's current case work lands on `shift/lpt-sync-*` branches and is
PUSHED there - `git branch -r --contains 712c24c80` finds `origin/shift/lpt-sync-20261013-linker-parity`,
and `git rev-list --left-right --count HEAD...@{u}` on the laptop reads `0 0`. So "is it pushed" is a real
yes; "is it on main" is a real no; and those are different questions that read as the same one.

HOW TO NOT GET BITTEN
1. For any case, the file you read must be one whose mtime and line count you checked, and the sections
 you need must be grepped for BY DATE (`2026-10-13`) - an old copy is a plausible-looking prefix.
2. On a Linux node, `~/repos/<repo>` may be an abandoned clone. The path existing is not the repo being
 current. `git log -1 --format='%h %ci %s'` on the file you are about to quote is one call and settles it.
3. The case index is a better first stop than a file: `lptcase.py find "<name>"` reads the clone it runs
 in, so run it where the work happens and heed its own two warnings - it prints STALE and UNPUSHED in
 capitals, and it was right on both counts here.
4. Never report a case from a single copy. Name the copy, its mtime, and whether the remote carries it.
