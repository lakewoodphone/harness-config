**L1523 · A path in a handoff is not a delivered file - published work goes to a repo and gets pushed**

A handoff that names a file path is not a file. Verified 2026-09-15: H86, H89 and H90 (all 2026-09-14, ZABZ-YOGA) each
cited concrete report paths — `lpt-hub/docs/customer-operations/sourcing/waze-fleet-iphone-sourcing/REPORT.md`,
`~/code/reports/bulk-iphone-sourcing-2026/PRICE-BASELINE-AND-TECHNICAL-SPEC.md`,
`~/code/reports/_iphone-bulk-sourcing/` — and every one of those paths was absent on ZABZ-TECH. The reports were real
but existed only on the machine that wrote the handoff. A reader who trusted the entries would have concluded the work
was done and never re-researched it, while the actual evidence stayed unreachable from every other machine.

Rule: a deliverable that must be found from another machine goes into a git repo and gets pushed, in the same session
that writes it. A path in `~/code/` outside a repo is machine-local and does not exist for anyone else. The handoff
should name the push, not the path.

Second, mechanical: scp to the laptop fails with "subsystem request failed on channel 0" (no sftp-server on that host).
The transfer that works is base64 over ssh — compress on the far side, write the base64 to stdout, redirect locally,
decode, expand. Reading the result back through `[Convert]::FromBase64String` avoided every binary-encoding hazard of
piping a tarball through a PowerShell stdout pipe.
