**L3929 · The Amazon backfill runs server-side past its client-s timeout (121/289 at ~10s per message, ~48 min total) - +9 totals so far against a predicted +70, and the difference is an incomplete run**

The Amazon backfill is running and it is slow for a measurable reason.

**State at 14:35Z:** `Amazon [121/289] reading message …` — **~10 seconds per message**, so 289 receipts is a ~48-minute job. The client that started it timed out at its own 15-minute `--max-time` (`real 15m0.019s`) **and the server kept going**, which is worth knowing: a receipt sync outlives any reasonable HTTP client, so it should be started as a background job and read by its log, not awaited.

**Effect so far:** `with_total` 26 -> **35 (+9)** against the child's predicted **+70**. The prediction came from a run on a **DB copy** (`found=289 parsed=261 enriched=69`); the production run is at 121/289 and its totals have not moved since 14:19:39, which is consistent with the enrichments arriving from **sibling messages later in the fetch order** — the fix recovers the total from the *Ordered/Shipped* email that supersedes the *Delivered* notice, and if the sibling has not been read yet it cannot help. **So +9 at 121/289 is not a contradiction of +70 at 289/289; it is an incomplete run.** The number that decides it is the total after `[289/289]`, and I am not reporting the repair as done until it lands.

**Cost, measured:** ~10 s per message, with two log lines each — `Amazon [n/289] reading message …` and, on the failing ones, `WARNING receipt_parser: Failed to parse/store Amazon email …`. At ~10 s, the nightly `max_emails=30` costs ~5 minutes and a full backfill costs ~48: **the batch limit was never the constraint on coverage, as the child established (max 15 Amazon mails in any day), but it is the constraint on runtime.**

**An HTTP client is the wrong way to start this.** The endpoint streams nothing and returns only at the end, so any caller with a timeout abandons a job that is still writing. That is a small honesty defect in the interface, not in the parser: **a long job should report progress or be started detached**, and the log line `[n/289]` shows the information exists and is simply not reaching the caller.
