**L3632 · Windows ssh cannot multiplex (Win32-OpenSSH, open since 2016) - but an MSYS2 ssh is already on the machine; and the mesh has exactly one transport with the fallback built and unwired**

## 2026-10-12 17:45 UTC · ZABZ-YOGA · researched: the Windows ssh multiplexing limitation, and the WIRED answer on the machine itself - plus the mesh has exactly one transport and no fallback

### 1. The Windows ssh limitation, researched rather than assumed

**It is a decade-old, intentional limitation of Win32-OpenSSH - not our configuration and not our build.**

Online research (`search_web` / GitHub issues / Super User / Stack Overflow):

* **`PowerShell/Win32-OpenSSH` issue #405, opened 2016-11-13**: *"Setting ControlPath makes OpenSSH
 fail, as it is not supported on Windows."*
* **Issue #1328, `Support for Control Master`, 2019-01-23**: still open; the top workaround offered is
 *"using wsl ssh"*.
* **Stack Overflow 20959792**: *"the conclusion after much searching is that currently it is NOT
 possible."*
* The exact sentence our child measured is reproduced verbatim in the wild:
 **`getsockname failed: Not a socket. ControlPath and Control* is not supported on Windows`**
 (Reddit r/vscode 2023; fleexlab blog 2020; and a 2026-06 issue in another agent harness whose SSH
 backend hardcoded ControlMaster and broke on native Windows OpenSSH).
* **Measured on both machines here**: `OpenSSH_for_Windows_10.0p2 Win32-OpenSSH-GitHub, LibreSSL 4.2.0`.

**Why it fails:** the multiplexing client must create an `AF_UNIX` socket for the `ControlPath`. The
Win32-OpenSSH client does not implement that path on Windows.

**THE ANSWER IS ALREADY ON THE MACHINE.** `AF_UNIX` support is in Windows 10+ *and* MSYS2/Cygwin
OpenSSH builds implement it, so a POSIX-layer ssh on the same box should multiplex. Found by searching
the machine rather than the internet:

| ssh on `ZABZ-TECH` | |
|---|---|
| `C:\Program Files\OpenSSH\ssh.exe` | the broken one (also `C:\Windows\System32\OpenSSH\ssh.exe`) |
| **`C:\Program Files\Git\usr\bin\ssh.exe`** | **present - Git for Windows bundles an MSYS2 OpenSSH** |
| **`C:\msys64\usr\bin\ssh.exe`** | **present - standalone MSYS2** |
| `wsl.exe` | present, Default Version 2 |

So the fix path is concrete and needs no new software: **point the dispatcher at an MSYS2 ssh instead of
the Win32 one.** The dispatcher already has exactly one place to do it - `bin/mesh-pressure-proof.mjs:60`
hardcodes `sshExe: process.platform === 'win32' ? 'C:/Program Files/OpenSSH/ssh.exe' : 'ssh'`, and
`lib/ssh-transport.js:23` already carries a comment that *"on Windows, ssh.exe does not exit when its
stdout is a PIPE"* - i.e. this layer already knows Windows ssh is special. **Whether the MSYS2 build
actually multiplexes is being measured now, not assumed; the result decides it.**

### 2. Does the mesh have a Cloudflare fallback? NO - and the fix is built and switched off

**Measured and verified on the authority after the child's report:**

* **There is no transport fallback for the mesh at all.** One `ssh` route per node, all MagicDNS names.
 If Tailscale fails, a mesh dispatch simply fails - and this already happened once (2026-09-28).
* **The fallback mechanism exists and is not wired in.** `plugin-mesh-http` serves a per-node HTTP
 surface, and I verified it answers **HTTP 200 on all three reachable nodes**
 (`zabz-tech`, `zabz-yoga-1`, `zabz-tech-linux`). Nothing calls it. This is the same defect class as
 the 599 tool bodies and the 6,160 uncommitted lines: **capability present, connection absent.**
* **All five peers are DIRECT, none relayed** - so Tailscale is not currently on a slow path, and the
 risk is availability, not speed.
* **Cloudflare's role is the public API and dashboard, not the mesh.** `cloudflared` is live on the
 authority with tunnel `3e62916c-04ac-421b-b4a4-9af0852d8024`, and the promotion path
 (`company-promote.py` on `lpt-survivor-01`) moves the public hostnames. **That is a *company*
 failover, not a *mesh* one.** A mesh fallback has to be built, not pointed at something existing.
* **Two live hazards found:** a `secretary-ssh` alias whose connector is dead (`bad handshake`) while
 the name still resolves and is offered, and a `-cf` wrapper that **DELETEs live tunnel connectors** -
 not run, and it should not be run without reading it first.

**Ranked single points of failure, top four:** (1) one transport for the whole fleet; (2) the mesh HTTP
plugin built but unwired; (3) `phone-gate`'s allow-list, which caused total mesh blindness once and
**fails open if empty**; (4) the broker is a single loopback instance.

**Evidence:** `docs/mesh/187-TRANSPORT-ROBUSTNESS-AND-FALLBACK.md` (394 lines), carried from the
`zabz-tech` checkout - whose branch was 4 ahead / 22 behind and therefore **unpushable** - to the
authority and committed **`6d63b32`**, pushed to the vault. The child also wrote `route-mesh.ps1` and
11 verified out-of-band ssh address aliases, both reversible and both left in place.
