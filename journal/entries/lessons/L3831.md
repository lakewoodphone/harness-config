**L3680 · git add and git commit must be ONE shell call - explicit paths do not protect staged work on a shared tree, and the tell is 'nothing to commit' when you staged something**

## `git add` and `git commit` must be ONE shell call — explicit paths are not enough on a shared working tree. Measured 2026-10-12.

The existing rule on this repo is *"never `git add -A`; add explicit paths"*, because a concurrent session's
files otherwise ride into your commit (P13). **That rule is not sufficient**, and here is the measurement.

```
call A (me): git add <5 explicit paths> -> staged: 5 files, correct, no-one else's
call B (other session): git commit -m "Weitman: ..." -> committed MY 5 staged files inside ITS commit 50b2848e1
call C (me): git commit -m "<my message>" -> "nothing to commit" - my message never reached the log
```

The other session did not even use `-A`. **`git commit` commits the whole index**, and on a shared working tree
the index is shared. So a correctly-scoped `git add` is only safe for the duration of one shell invocation.

**Rule: `git add <explicit paths> && git commit -m/-F <msg>` in a single `pwsh` call.** Verified fixed — the next
commit I made this session (`d27cfcfbb`) used that shape and landed under its own message.

**If your commit says "nothing to commit" and you *know* you staged files, do not re-edit or re-stage first.**
Check whether a concurrent commit already took them:

```
git log --oneline -3
git show --stat --oneline HEAD # are my files in somebody else's commit?
git cat-file -e HEAD:<my path> # is my content actually in HEAD?
git log --oneline origin/main..HEAD # is it pushed?
```

In this case the reply was: files present in HEAD, pushed, work intact — **only the message was wrong**, so git
log could not find the work. The correct repair is a **follow-up commit whose message describes what the other
commit carries**, naming the hash. Do not rewrite the other session's commit and do not re-commit the content.

**The durable fix is one working tree per session** (git worktrees, the parallel-agent-orchestration pattern),
not more care. On a shared tree, care narrows the window; it does not close it.
