**L11326 · A value is not unused because the code does not mention it - count the rows first**

On 2026-10-20 I spent a round arguing that production's eighth OrderStatus value, CLOSED, was a stray that nothing wrote or read, reverted a change that added it, and filed an owner question recommending its removal. Then I counted the rows: CLOSED 468, CANCELLED 91, READY_FOR_PICKUP 55, AWAITING_DIAGNOSIS 18, AWAITING_PARTS 15, UNFIXABLE 8, AWAITING_APPROVAL 6, AWAITING_PAYMENT 4. **468 of 665 orders carry it.** It is the largest group in the book by an order of magnitude; removing it would have orphaned seventy per cent of the shop's order history.

THE MISTAKE, precisely. My evidence was a grep of backend/src that found no writer and no reader, plus production's pg_enum showing eight values where the repository declared seven. Both facts were true and the conclusion was still wrong, because I asked 'does the code mention it' when the question was 'does the data carry it'. A status the application never sets can be the status of most of the history - written by a reconciliation, an import, or a person on another tool - and the code being silent about it proves only that the code is silent.

WHAT TO DO INSTEAD, and it is two commands, not a round of reasoning:
 select status::text, count(*) from orders group by status order by 2 desc; -- is it used?
 grep -rn '<VALUE>' -- backend/src frontend/src -- who writes or reads it?
Data first. The grep answers a different question, and its silence is not evidence of absence when the writer may live outside this repository - which for this shop it demonstrably does (a reconciliation process, and historically direct SQL).

WHY IT MATTERED: the recommendation I filed (#880) was to REMOVE the value unless the owner could define it. He had not answered when a shift landed the opposite decision (#557, declare it) and a later round of mine tried to revert it. Had the revert reached production with a migration, 468 rows would have been left holding a value the code rejected. The near-miss was mine and it came from a measurement that felt complete because it was precise.

Filed alongside: the roadmap changelog carries a correction row citing the original, and #880 now asks only for the wording of what CLOSED means, not whether it exists.
