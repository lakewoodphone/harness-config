**L2008 · The Shabbat door probe measured our own tamper automation, not the relay**

# The Shabbat door probe was measuring our own automation, not the relay

`app/services/shabbat_safety.py:check_persistent_unlock` decided the single
question every Shabbat power-down rests on — "can the interior maglock be HELD
unlocked?" — by releasing the relay and watching it. But it released the relay
**without disabling** `automation.phoenix_interior_maglock_tamper_restore`, the
owner's own automation whose entire job is to re-assert the lock. So what it
observed was our guard rail re-locking the door, and it reported that as
hardware fact: "the relay is momentary/inching, ~91 ms, cannot be held."

Two places in the codebase then asserted that conclusion as established
(`shabbat_safety` module docstring, `home_assistant.set_interior_maglock`
docstring) while a third contradicted it —
`home_assistant.hold_interior_door_open`, which disables the automation first,
has held the same relay released for a full minute (2026-09-13).

Durable rule: **when a probe disagrees with the implementation, suspect the
probe first.** A measurement taken with a known confounder active is not
evidence about the hardware; it is evidence about the confounder. The 91 ms
trace (2026-09-11 log excerpt) is real but carries that confound, so the cause
of the re-lock is *unresolved*, not settled — and the code now says so instead
of picking a side.

Fix: the probe now delegates to `hold_interior_door_open` (one implementation
of disable-automations → release → watch → prove) and calls
`restore_door_automations` before returning, so a probe never leaves the
owner's guard rails switched off. Tests: 3 added in
`tests/test_shabbat_safety.py`; 51 passed across the four Shabbat suites.

Note the safety argument never depended on resolving this: keep HA running and
stop the cameras in software wins on cost and reversibility either way.
