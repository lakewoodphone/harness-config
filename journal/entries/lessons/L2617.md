**L2617 · A subagent brief naming a machine-local path is a landmine - the broker picks the node, and that node's disk is not yours**

**L2616 · A `subagent` brief that names a machine-local path is a landmine: the BROKER picks the node, and that node's disk is not yours**

Recorded 2026-09-28 (ZABZ-YOGA), after a three-child fleet lost ~13 minutes to it.

WHAT HAPPENED
I dispatched three mesh `subagent` children, each with a brief whose first line was a Windows path:
`C:\Users\ezabz\code\_worktrees\phone-and-tech-full\lpt-more-apps`, branch
`lpt/managed-apps-20260928`. The broker placed all three on **`secratary`** (Linux).

The placement record `~/.dsh/mesh/placements/remote-b110f6ff-27f7-40ad-a23d-d5a47498d37f.json`
says so unambiguously:
```
"node": "secratary", "ssh": "secratary-ts", "meshHost": "secratary",
"cwd": "/home/zabz/code", "shell": "posix",
"reportedHost": "", "stopReason": "error", "ms": 730130, "exitCode": 0
```
That child burned **12 minutes 10 seconds**, did the work somewhere, and its result was thrown away
because it reported host `""` instead of `secratary` — the message the harness shows is
*"the transport reported host "", which is not one of the hostnames the placement named"*.

THE TWO FACTS THAT MAKE THIS A LANDMINE RATHER THAN A GLITCH
1. **The node has no such checkout, and no such path shape.**
 `ssh secratary-ts "ls -d /home/zabz/code/phone-and-tech-full"` ->
 `No such file or directory`. `/home/zabz/code` holds only `_worktrees`, `harness-config`,
 `unified-search`. The repo on that box is at **`/home/zabz/repos/phone-and-tech-full`**, on branch
 `test` — a completely different checkout, on a different branch, from the worktree my brief named.
 A child that "recovers" by finding the nearest matching directory would have edited the authority's
 unrelated tree, unverified, on the wrong branch.
2. **The tool name does not tell you where it will run.** `subagent` (and `subagent_remote`) are the
 mesh and will route to whichever node the broker ranks highest — `prefer-remote` is ON, and the
 broker explicitly EXCLUDES the local node when any other node is eligible
 (`"excludedLocalNode": true, "excludeSentToBroker": ["zabz-yoga-1"]` in the newer records). So the
 default is *away from the machine whose files you just described*.

WHY IT IS NOT "THE MESH IS DOWN"
It is not. The broker answered, ranked, placed, queued, and dispatched. The mesh worked. **The brief
was written for the wrong computer.** H2768 the same night recorded the same `reportedHost: ""`
diagnostic and concluded the mesh was unreachable — that reading was too strong: the placement logs
show healthy placement and dispatch, with the node named. What broke was the report's provenance, not
the route.

THE RULE
Before dispatching a `subagent` whose work touches files, establish **which node it will run on** and
that the path in the brief exists there. `~/.dsh/mesh/placements/*.json` is the record: it names the
node, the ssh alias, `cwd` and `shell`, and it is written before the child starts, so it answers the
question in advance. It is also the only place that says where a child actually ran.

- **If the work is in a worktree on THIS machine, use `subagent_local`.** It cannot be misrouted. Say
 so in the brief ("running LOCALLY on this Windows machine") so the child does not try to be portable.
- **If you do want the mesh, write the brief for the target OS and path** — a Linux brief names
 `/home/zabz/...` and posix commands, and you must confirm the checkout (branch included) is there
 first. A brief naming `C:\...` will never be right on `secratary`.
- **Never let a child infer the repo from its surroundings.** Both briefs here said, in capitals, that
 the scope was absolute and that anything else was forbidden — which is what kept the authority's
 `test` checkout clean. The full check afterwards: `git status --porcelain` on
 `/home/zabz/repos/phone-and-tech-full` returned ONE line, `reconciliation_plan.json`, dated
 **2026-09-20** (eight days before the dispatch), and neither `backend/src/services/managed-apps` nor
 `frontend/src/features/managed-apps` existed there. **Nothing my fleet wrote landed on the authority.**
 Verify that; do not assume it.

EVIDENCE
Placement records `remote-b110f6ff-…json` (childIndex 2, settled, `reportedHost: ""`),
`remote-513cbde4-…json` (childIndex 1, same diagnostic, 156 s);
`ssh secratary-ts "ls -d /home/zabz/code/phone-and-tech-full"` -> no such file;
`find / -maxdepth 5 -type d -name phone-and-tech-full` -> `/home/zabz/repos/phone-and-tech-full`;
that tree's `git status --porcelain` -> 1 pre-existing line, `stat` mtime 2026-09-20 23:15:20 UTC.
All read 2026-09-28 ~04:45-04:56 UTC on ZABZ-YOGA.
