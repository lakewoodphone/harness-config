**L1873 · waze-mdm fleet API: which routes 404, which 'succeed' while doing nothing, and Caddy's 200-for-any-path trap**

## Lesson — which waze-mdm fleet-API routes actually answer, and why "200" means nothing there

Measured live 2026-09-17 (probes 03:56–04:02Z against the running build, md5 `aba5f091…`).

**Routes that do not exist** (404) even though scripts and docs hand them to operators:
`GET /fleet/devices/{drn}/command-history` · `GET /fleet/devices/{drn}/profiles/observed` · `POST /fleet/devices/{drn}/profiles/refresh` · the whole `/fleet/observability/*` family (`metrics`, `stale-devices`, `check-stale`, `reconcile`). `scripts/drn-api.ps1` ships all five as first-class commands; the repo also contains the three profile routes as *newer* code that was never deployed.

**Routes that exist but lie.**
- `GET /fleet/devices/{drn}/profiles?wait=true` returns `{"ok":true,"profiles":[{"error":"Failed to parse plist: b'…'"}],"count":1}` — for every device, always. Cause is upstream of the parser: `PGDeviceInspector.get_command_results` truncates with `substring(cr.result::text from 1 for 500)` (`nanomdm_client.py:370`), and every real ProfileList reply is longer, so `plistlib` always throws mid-element. `count` is `len([the error])` = 1, and a caller reading `profiles[0].identifier` gets nothing. The working parser (`parse_profile_list_result`) already exists in the repo and is not deployed. Also: `?wait=false` and the timeout path return **no** `profiles` key at all, so "device silent" and "nothing installed" are the same absence.
- The 18 routes that reference `MDM_GATEWAY_URL` are **not** dead (I nearly deleted working code over this): `gateway` is the compat shim whose client intercepts the path and talks to NanoMDM directly. Only its unmatched-path fallback still dials the deleted host.
- `POST /fleet/devices/{drn}/screen-time` and the `LocationServices` item used by `edit-window-open`/`locked-edit-open` build `Settings` commands with items Apple does not define. Apple's valid Settings items are exactly 20 (AccessibilitySettings, AppAnalytics, ApplicationAttributes, ApplicationConfiguration, Bluetooth, DataRoaming, DefaultApplications, DeviceName, DiagnosticSubmission, HostName, MaximumResidentUsers, MDMOptions, OrganizationInfo, PasscodeLockGracePeriod, PersonalHotspot, SharedDeviceConfiguration, SoftwareUpdateSettings, TimeZone, VoiceRoaming, Wallpaper). Enqueueing cannot fail, so these endpoints report `ok: true` and "location enabled" for commands iOS will reject.

**The trap underneath all of it.** Caddy's `Caddyfile` proxies only `/api/fleet/*` to the fleet API; every other path falls through to `handle { respond "Waze MDM is online" 200 }`. So `/api/health`, `/api/healthz`, `/api/readyz`, and any typo return **HTTP 200 with 18 bytes of plain text**. The fleet API's real `/health` — the one designed to return 503 when NanoMDM is down or an integration is missing — is unreachable, because the only vhost that exposes it (`mdm-api.abletelsolutions.com`) does not resolve and port 8003 is loopback-bound. **Monitoring cannot detect this service being down.** Trail-slash trap on top: `GET /api/fleet/devices/` returns 307 to `http://mdm.abletelsolutions.com/fleet/devices` — TLS downgraded, `/api` stripped, landing on the dashboard's basic-auth 401 for any client that follows redirects.
