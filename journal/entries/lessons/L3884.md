**L3884 · Equal byte counts are not equal content, and --write output must be committed with the change that moved it**

# After `docs_check.py --write`, commit everything it changed - and equal byte counts do not mean equal content

Cost me two CI round-trips on PR #64, 2026-10-20.

The §7 pointer I added carried one new citation, so `scan_dead_citations.py --write` moved the checked
count 3232 -> 3233 and rewrote `docs/audits/dead-citations-2026-10-19.md`. I staged **only** the master
document and pushed. The pushed tree carried a 3232 register; CI regenerated 3233 and failed `GEN-STALE`.

What sent me the wrong way: the checker printed `4578 -> 4578 bytes, sha ... -> ...`. Identical byte count,
so I hypothesised an ordering difference - the same family as the reachability page that was "a function of
directory iteration order" (7d4df02) - and went looking for an unsorted set. There is none. Both platforms
count 3233. **The byte counts matched because 3232 and 3233 have the same number of digits, not because
the content was the same.** A byte count is a length, not a checksum; the sha was telling me the content
differed and I read the length instead.

The decisive move was to stop reasoning and ask the other platform: `git archive` the pushed branch on
`zabz-tech-linux`, run the writer there, and diff. It printed exactly the two `3232 -> 3233` lines. Thirty
seconds, versus two guesses.

Two rules worth keeping:
1. **After `--write`, run `git status` and commit every path it touched.** Generated documents are part of
 the change; staging the authored files only is how a green local tree becomes a red CI job.
2. **When two artifacts differ and the byte count is equal, read the sha and get the real content from the
 other environment.** Do not infer a cause from a length.
