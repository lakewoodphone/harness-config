**L3366 · A protection that lives in a launch flag and not in code is an invisible dependency - measure it or lose it**

GOAL ROUND 13, and the most consequential thing found in the whole session. app/main.py's _api_access_guard protects ~350 endpoints with an API key and TRUSTS LOOPBACK, returning early for any request whose peer is 127.0.0.1 - and it never inspects X-Forwarded-For or CF-Connecting-IP. What makes that safe is NOT application code: it is UVICORN, whose proxy-header handling (default forwarded_allow_ips=127.0.0.1) rewrites request.client from the forwarded header so a proxied request stops being loopback. MEASURED, same build, same request, only the flag changed: GET /sms/log with X-Forwarded-For: 203.0.113.9 returns 401 under 'uvicorn app.main:app' and 200 under 'uvicorn app.main:app --no-proxy-headers' (same for /sms/threads and /tasks). That 200 case is the company's SMS log readable by anyone, because the DASHBOARD PROXIES /sms/* FROM LOOPBACK (web/next.config.ts). And the flag was pinned NOWHERE: every launch line in the repo - .github/copilot-instructions.md, .github/prompts/deploy.prompt.md, docs/**, scripts/mesh/sync-env.sh, and my own conformance boot script - is a plain 'uvicorn app.main:app --host ... --port ...'. The protection has been an undocumented, untested default since the guard was written to fix the 2026-09-01 exposure its own docstring describes. FIXED BOTH WAYS: (a) deploy/hosting-migration/company-api.service pins --proxy-headers --forwarded-allow-ips=127.0.0.1 explicitly, with the two measured lines in a comment so nobody removes it as noise; (b) the invariant is now MONITORED from outside - company-heartbeat.sh asks a protected path with a forwarded header every 2 minutes and alerts unless it is 401/403, naming the flag to check. Verified on BOTH sides against a live instance: the no-proxy instance gave 'api_guard: false:200' and fired the SECURITY alert; the correctly-launched instance gave 'api_guard: true' and stayed silent. RULE: when a security property depends on how a process is STARTED rather than on what the code DOES, the code cannot enforce it, the tests cannot see it, and the next person to change a startup flag will not know they are removing it - so pin it where it is started AND monitor the invariant from outside, where it is observable. Also disclose: my own first guard probe reused the heartbeat's 'code' variable, so the state file reported the guard's 401 as the health endpoint's status; found by reading the output rather than the pass/fail.
