**L3935 · The stall class is TWO classes sharing one marker: I fixed the near-identical-output guard and the surviving stalls are the NO-TOOL-CALL path, which closes with 12/20 steps unspent**

The stall class I have been treating as one thing is two things wearing one label, and I fixed one of them. The evidence is a session log and two call sites.

**The log that exposed it** (session 78729, `failed`, 8/20 steps used):

 [STALLED_REPEATING_OUTPUT: 3 consecutive model turns produced NO TOOL CALL after 8/20
 work steps, including one envelope re-prompt; the step budget is untouched]

That is not near-identical output. It is the model **stopping calling tools**, and the session was closed with **12 of its 20 steps unspent**.

**The two call sites, same marker:**

 line 5038 _text_similarity(cleaned, self._last_work_output) > 0.85 <- the guard I changed to redirect
 line 5102 reason="stalled_repeating_output" <- that guard's close
 line 5190 empty_turn_reason = "stalled_repeating_output" <- the NO-TOOL-CALL path's close
 line 5480 f"{ledger.empty_turns_in_a_row} turn(s) with no tool call after "

And `autopilot.py:2999` records that a prior analysis found *"failures (40%) carried [STALLED_REPEATING_OUTPUT]"* — **a marker count, not a cause count.** So the 38-40 % class I have been reporting, and that my P3c/P3d work targeted, is a **mixed population**: some sessions repeat identical output (fixed — it now redirects), and some stop calling tools (untouched — it closes, budget unspent).

**This is why the measured signal looked good and the class did not go away.** In the post-raise window 2 of 5 sessions still ended as `stalled_repeating_output`, and the two I earlier watched survive a redirect hit the *other* detector. **My fix landed on the smaller half and I read its marker count as my population.**

**The lesson is the one this session keeps relearning, now about my own measurement:** a predicate over a log string is not a definition of a failure mode. `output_log LIKE '%stalled_repeating%'` counts **every writer of that marker**, and there were two. Before changing behaviour *for a class*, read the code that writes the marker — which is exactly the check I applied to other people's numbers all day and did not apply to my own headline one.

**The unfixed half, stated precisely so the next attempt can start from it:** three consecutive turns with no tool call, **one envelope re-prompt already issued**, then a close — with 12/20 steps unspent. The similarity guard's treatment (a redirect that spends the step rather than ending the session) is the obvious shape to mirror, because the same argument applies: *a session that has stopped calling tools has not exhausted its budget.* **Whether the no-tool-call path even has a redirect available is the first thing to check**, and I am not assuming it does.

**And a second reading that qualifies my disk conclusion.** Contention returned after the disk was freed: **21 `lock contention` events and 1 `ABANDONING`/`run_once timed out` since 14:47**, against zero in the minutes immediately after the free. **So the disk was a major contributor to the contention, not its only source** — freeing 23 GB took it to zero for a while and it has come back. The loop is still advancing (`last_run_at 14:58:06`, `run_count 1`) and there are **0 `error_log` rows** since the free, so the service is not wedged; the contention is a recurring symptom whose remaining cause is unmeasured. **What I will not do is keep calling the disk the root cause now that its relief has worn off.**
