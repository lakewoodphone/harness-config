**L1985 · Wake W2: prompt-as-argv on Windows, inner-vs-outer timeouts, and inherited flock**

Three durable rules from building the wake release path (W2), each paid for by a
concrete failure.

1. ON WINDOWS, A PROMPT MUST NEVER TRAVEL IN A COMMAND LINE.
 The v0 desktop runner did `& cmd /c "npx dsh --profile headless `"$($prompt -replace '\"','')`""`.
 That deletes every double quote in the prompt (silent data loss) and hands the rest to
 cmd.exe as live syntax, so newlines and quotes break the command. The rule: carry the text
 as a FILE and pass it to the process as ONE argv element - start node.exe directly (never a
 .cmd shim, never cmd /c) and escape each element with the MSVCRT rule set
 (backslashes before a quote doubled, quote escaped, whole element quoted when it holds
 whitespace or a quote). Verified: the argv the child received hashes identical to the
 prompt file under pwsh 7.6 and Windows PowerShell 5.1, with quotes, newlines, tabs,
 backslashes, backticks, $, % and Hebrew in the prompt.
 Also: read with [IO.File]::ReadAllText(..., UTF8) and write with a no-BOM UTF8Encoding -
 PS 5.1's `Out-File -Encoding utf8` puts a BOM at the head of the file, which the v0 runner
 did and which corrupted the first line of the wake out-file.

2. A DERIVED TIMEOUT MUST NEVER BE CLAMPED LARGER THAN ITS PARENT.
 `RUNNER_TIMEOUT=$((TIMEOUT-60)); [ $RUNNER_TIMEOUT -lt 60 ] && RUNNER_TIMEOUT=60` is
 correct at TIMEOUT=900 and inverted at TIMEOUT=30, where the inner bound (60s) outlives
 the outer ssh `timeout` (30s) - the exact orphan-session case the inner bound exists to
 prevent. Caught by S2 of the verification suite, which asserted the printed command.
 Fix shape: derive 80% first, then take the bigger of the two only when it is still
 strictly smaller than TIMEOUT.

3. A CHILD INHERITS THE flock FILE DESCRIPTOR, AND FOR A RELEASE PATH THAT IS A FEATURE.
 `exec 9>lock; flock -n 9` leaves fd 9 open in every child. If the dispatcher is killed
 while its ssh child is still running, the lock stays held until that child exits, so the
 next cron tick skips instead of starting a second session for the same flag. The cost is
 that a verification harness must clear the lock between scenarios
 (`pkill -f stub-ssh` then poll `flock -n lock true`), or later scenarios silently no-op.
 What the dispatcher must still do on the way out: kill the in-flight session, so the
 window closes immediately and the row is closed as failed.
