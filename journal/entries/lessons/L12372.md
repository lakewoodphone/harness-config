**L12372 · An index lagging a rebuild is not a failed send; and dialpad_sms_cache lives live only in authority.db**

An index that has not caught up is not evidence that an action failed, and the same table name can live in two databases with only one of them populated.

Measured 2026-10-26 while recording an SMS sent to a customer on work order WO26102312771. The send returned message id 6650452636377088 and status pending. Three checks then all looked like failure:
- ps_comms_thread for her number returned 0 results since that date - the comms index rebuilds every 30 minutes, and the send was seconds old.
- sqlite3 on /root/personal-secretary-mvp/data/secretary.db SELECT ... FROM dialpad_sms_cache returned nothing, and then count(*) returned 0.
- The same query against /root/authority.db returned the row immediately: message_id 6650452636377088, phone_normalized 8483336341, direction outbound, created_at 15:37:51.433Z, fetched_at 15:37:54.118Z.

So: dialpad_sms_cache exists in BOTH databases on the authority. secretary.db holds 0 rows; authority.db holds 136,411 and is the live one. And fetched_at 2.7 seconds after created_at is itself the proof the row was captured live rather than backfilled.

What transfers:
- Before concluding a send or a write did not happen, ask what WRITES the surface you are reading and how fresh it can be. A rebuild lag and an empty mirror look identical to a failure.
- Two stores with the same table name is the estate's recurring defect; name the database in the same breath as the query.
- The row, read back with its id and timestamps, is the evidence. The tool's own "sent" line is not, and neither is an empty index.
