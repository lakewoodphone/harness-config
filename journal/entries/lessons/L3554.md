**L3554 · A 401 must never delete credentials: the website clears its refresh token on ANY 401, so an expired access token costs a hand-typed password**

**Where.** `phone-and-tech-full/frontend/src/lib/trpc.ts`, four identical fetch wrappers (staff httpLink
lines 423-429, staff batch link 441-447, vanilla client 476-482 and 494-500):

```ts
if (response.status === 401) {
 handle401Error() // deletes accessToken + refreshToken, then navigates to /login?expired=true
}
```

`handle401Error` (lines 161-210) is unconditional: it does not know whether the 401 came from `auth.login`
(a real credential failure), `auth.validate` (an *expired access token*, which is exactly what a refresh
token is for), or a batch of ordinary queries. So a device holding a perfectly good refresh token is
turned into a password prompt.

**The evidence it is this and not a guess.** In the live database, user 299 has three refresh tokens, all
unrevoked (created 10-06, 10-07, 10-08) and three `sessions` rows at those three login times — i.e. fresh
logins on three consecutive days and **zero** refresh-created sessions. Reuse detection never fired:
`security_events` holds a single row all-time (2026-05-26, `CONFIGURATION_CHANGE`), and
`data_retention_policies` is empty, so nothing is deleting sessions on a schedule either. The 401s in the
backend log are `context.js:298 "Authentication required"`, preceded on 2026-10-08 by a hand-typed
password (failed 17:50:22Z, accepted 17:51:02Z).

**Why iOS devices show it and a desktop does not.** The token pair is minted together and lives the same
7 days, and the client's proactive refresh is a 30-second `setInterval` while the page is open
(`hooks/useAuth.ts:328-340`). A backgrounded iOS tab has its timers frozen, so the counter iPad/iPhone
routinely reach the site *after* the access token expired — the one moment the 401 fires and the refresh
token is thrown away.

**The fix (not yet deployed, deliberately):** do not clear the session on a 401 from `auth.validate` /
`auth.refresh` (the URL carries the procedure even for batches: `/api/trpc/<procedure>?batch=1`), let
`useAuth`'s existing refresh path run first, and only treat a *failed refresh* — not a failed request — as
a logout. Also give the refresh path single-flight, because `refreshAccessToken`
(`backend/src/services/auth.service.ts:836-917`) rotates: it revokes the presented token and creates a new
session, so two concurrent refreshes from one browser would present an already-revoked token and trigger
`revokeUserSessionsOnReuse` (auth.service.ts:1125-1155), which revokes **every** session for that user.
That path has never fired here — keep it that way.

**Rule:** a 401 means "this request was not authenticated". It never means "forget the credentials". Only
an explicit logout, or a refresh the server has actually rejected, may destroy a session.
