**L12193 · The 5589583 write fence is working and the reload 409 still fires 13 of 13**

Measured 2026-10-22 against fx-race @ 5589583 (branch verify/race), local production build on :3219, staging DB through an ssh tunnel, 13 fresh minted identities, one aimed reload each (reload taken only while a PUT had been open >=500ms).

RESULT: 13 attempts, 13 conflicts, one 409 per attempt, and in 13 of 13 it was the FIRST write after the reload. Assertion 1 fails; the conditional full funnel run was not performed.

THE CHAIN IS NOT A QUEUE JUMP. analyse.cjs over logs/chain-analysis.json: the first post-reload write was issued BEFORE the boot read answered in 0 of 13, and carried the boot read's own value in 13 of 13. The fence in persistence-write-queue.ts does exactly what the commit says: it parks the write until the read answers and then issues it with that answer (24-279ms later, mean 48ms).

WHAT ACTUALLY HAPPENS. The PUT in flight at reload commits server-side after the resumed page's boot read took its snapshot. Read answers N, library is N+1, the write carries N, CAS refuses. Attempt 1: PUT exp=5 issued t=23254, reload t=23775, ERR_ABORTED t=24267, boot GET issued t=24487 answered current=5 at t=25379, first write exp=5 at t=25413, 409 current=6. assessment.tsx:1069 calls noteReadAnswered() when no boot upload is owed, which latches the fence OPEN for the page's life, so the promotion commit goes out at the mirror's stale revision.

WHY NO FENCE CAN FIX IT: the read cannot see an uncommitted write, and the write is slower than the read (PUT 0.5-3.8s vs boot read 0.9-1.1s). The queue already models this case for transport failure (unconfirmedIssueRevision, conflictAttribution this-device-unconfirmed-write, persistence-write-queue.ts:139/:340) - the gap is that the knowledge dies with the page. A real fix needs a marker written before the PUT and cleared on a settled answer, so the resumed page knows its mirror is suspect; or a server-side idempotency key per write.

METHOD FACTS WORTH KEEPING: (1) capture /api/persistence on the browser CONTEXT, not the page - the write in flight at reload produces net::ERR_ABORTED and a page listener loses it; (2) on this tunnel natural PUT latency is 0.5-3.8s, so the 'save open >=500ms' reload condition needs NO injected delay - do not add one, it would be a fidelity cost for nothing; (3) a write issued as the browser context closes still commits, so an exchange count is a floor by at most one per attempt (db revision ended one past the last captured exchange in 6 of 13, library updated_at within 1s of attempt end); the CONFLICT count is unaffected; (4) 'next start' materialises a real directory named 'personality test/' inside the worktree next to the node_modules junction - fsutil reparsepoint query exits 1 'not a reparse point', so move it out and never delete it.

RATE CAVEAT: every reload here was AIMED at a save open >=500ms, which is what produced the original failure. The earlier '2 of 13' was almost certainly un-aimed reloads. Aimed: 13 of 13.
