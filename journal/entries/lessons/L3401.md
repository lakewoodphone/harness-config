**L3401 · In the operational store a note that says paid is not a payment row**

## L — In the operational store, a note that says "paid" is not a payment row

Measured 2026-10-08 while working the Gestetner SX740 HS screen-hinge case. `WO2609010002`
(2026-09-01, order id 2973) carries a status note **and** a status-history reason that both read
*"paid $75 via card"*, while the read path reports `total 0.00`, `paymentStatus PENDING`, an empty
`payments` array and `comms_succeeded_payments 0`. A table-wide scan for `amount = 75` returns four
rows; none is dated 2026-09-01 and none is linked to customer 2781 or order 2973.

**So these are two different statements, and only one of them is the money record:**
- money received = `sum(payment_transactions.amount) WHERE status = 'SUCCEEDED'` — the existing rule;
- a note that says paid = a human's memory, and it can exist with no row behind it.

**Consequences:**
- Never report such an order as **unpaid**, and never report it as **paid**. Say
 **money-unrecorded**, give both readings, and cite the note id.
- The cause is visible in the same table: the terminal-card payments all land with `orderId` and
 `customerId` **NULL** and only a free-text `staffNote` (measured on the 40 newest rows,
 2026-10-08). A payment that is not linked to an order cannot be seen by any per-order read, so
 `lpt ticket` will show `collected 0.00` on jobs that were in fact paid at the counter.
- The same shape is already in the owner queue as separate rows (#327, #328, #332) for other jobs, so
 this is a pattern and not one bad row.
