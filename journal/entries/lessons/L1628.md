**L1628 · A security control tested with the wrong subject: the allowlist only ran for CUSTOMER users, so an anonymous probe proved nothing**

Evidence: context.ts's isCustomerAccessibleTrpcRequest is consulted from exactly one place, inside
`if (user && user.role === 'CUSTOMER')`. PART-120 tested the bypass with an ANONYMOUS probe
(auth.me?x=/customerPortal.) and recorded the result as "tested-and-held". It could not have detected the
bypass: without a customer token the branch is never entered, so the outcome was predetermined by the
ABSENCE OF A SUBJECT rather than by the strength of the control. The bypass is real (query decoy, batch,
router prefix, auth.refresh substring) and PART-066 found it by driving the real createContext WITH a
CUSTOMER token.

RULE: before trusting a security test, state the SUBJECT it needs and confirm the test supplies it. "The
request was refused" means nothing if the code path that would refuse it was never reached.
RULE: when a control is only exercised for one kind of principal, a probe with any other principal is a
tautology, not evidence.

Related instrument fault, same session: my first check of production's dist reported the allowlist ABSENT.
The grep had been mangled passing through a PowerShell quoting layer and the shell error was not read. The
file was read directly and the answer was the opposite. RULE: a negative result whose command printed an
error is not a negative result.
