**L1590 · A count that moves without a code change is a claim about the instrument: fixing 19 tests raised the failure count from 21 to 38, because the suite is non-deterministic**

**Evidence, 2026-09-15/16, round 16.** I was greening a test suite. Fixing 19 tests made the failure count **go up** — 21 to 38 — and that single impossibility is what exposed the real problem.

## The measurement

Four files that fail in the full suite, run **alone**, each in its own vitest process:

| File | Alone | Full suite |
|---|---|---|
| `communications-phone-threading` | **4 passed** | 1 failed |
| `workorders.debug-logging` | **8 passed** | 2 failed |
| `inventory.debug-logging` | **15 passed** | 2 failed |
| `workorders-create-service-errors` | **3 passed** | 2 failed |

All four pass in isolation and fail in the suite, across unrelated areas. They are not stale assertions against changed code — **their result depends on what else ran.**

## The rule

**A number that moves when the code has not is a claim about the instrument, not the subject.** I had been treating "21 failures" as a fact about the tests. It was a fact about **that run**. The tell was not subtle once I looked: I removed 15 stale assertions and the count rose.

**And the corollary that cost me credibility in my own record:** my earlier scoped measurements — "7 files, 115 passed", "3 files, 39 passed" — were **true measurements of narrower commands**. I quoted them as evidence about code. They were evidence about *three files run together*, and under the full suite the same code may fail. Every test summary this session produced by a scoped run needs that qualifier, and did not have it.

## What this is, in the series

This is the ninth instrument fault found, and the first that makes the **whole** instrument unusable rather than one measurement inside it. The earlier ones — a warning about a fixture, an empty queue read as health, mention counts read as reachability, a census from a stale tree, a check that could not fail, a red suite hiding a new test, a rename that inverted a negative test — were each local. This one means **no pass/fail claim about this repository can be trusted until it is bounded**, including mine.

## The two rules worth keeping

1. **When a count moves without a code change, stop and re-measure before explaining.** I had a ready explanation ("the full suite exposes more stale tests") that would have been wrong and would have sent me fixing interference as though it were staleness.
2. **Report the two classes separately.** `N stale + M interference`, never one number. Stale failures are fixable assertions; interference is a suite-hygiene bug needing a different investigation. Merging them produces a number that changes on the next run and takes whoever quoted it down with it.
