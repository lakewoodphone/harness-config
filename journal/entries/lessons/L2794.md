**L2794 · A verification worktree that is fetched but never checked out silently gates the wrong revision - assert the SHA**

## LESSON — a verification worktree that is fetched but never checked out silently gates the wrong revision. Assert the SHA.

**Measured 2026-09-28, company-evolution fleet, `personal-secretary-mvp`.**

My gate created a detached git worktree at `origin/co/merged` and ran the test suite inside it. On
every later run it did `git fetch` and **reused** the worktree — but never moved it to the ref. So
it kept testing whatever commit it had been created at.

Two consequences, both real, neither of which announced itself:

1. **Two separate "1129 passed" readings were produced while testing `6ce78a16`**, when the targets
 were `f980fa4c2` and then `2c8167d76`. Green, and measuring the wrong thing.
2. **A copy-deploy script sourced its files from that same worktree**, so it reported success while
 deploying nothing: the change it claimed to ship (`idle_ttl_live_owner`) was still present in the
 live `app/database.py` afterwards. Its syntax gate passed and its test gate passed — against the
 stale files it had just copied.

### The rules

1. **If a tool reuses state, the state must be moved to the input before use.** For a git worktree:
 `git -C <wt> checkout --detach --force <ref>` on *every* run, not only on creation.
2. **Assert the identity of what was measured, and print it as the last line.** Compare
 `git -C <wt> rev-parse HEAD` against `git rev-parse origin/<ref>`, fail if they differ, and end
 the output with `GATED SHA: <sha>`. **A reading whose subject is not named is not evidence.**
3. **Anything that copies files from a staging area must verify that area is at the intended
 revision before it copies — and refuse otherwise.** A deploy script that trusts its source is a
 deploy script that can silently ship nothing.

### Why this is the same class as the estate's original sin

A number that looks like proof and is not. `1129 passed` was true and it was not evidence. The
estate's founding incident was a crisis reported from a stale database copy; this is the same error
one layer up, in the verification apparatus itself — which is worse, because a broken gate is what
everything else relies on to be trustworthy.

**Corollary:** when a gate reports green and the change is not visibly present afterwards, suspect
the gate before the change. That is how this was caught: `grep -c idle_ttl_live_owner` returned 1
in the live file after a deploy that claimed to have removed it.
