**L6252 · E4610 ships Message+ and has no alternative; E4810 ships stock and Message+ is our sideload - plus a hand-applied rebuilt Message+ that no script or receipt records**

**Correction · 2026-10-15 · ZABZ-TECH · The E4610/E4810 messaging architecture, and the rebuilt Message+ we applied by hand — owner was right, I had the architecture under-specified**

The owner said: *"E4810 does not come with the message plus and we try to install it and it didn't work so
well. So we went back to the stock messaging. The E4610 doesn't have a different messaging app. The stack
messaging app on it is message plus… maybe trace that back [a script replacing the installed message plus
with a different version]."* **All of it confirmed.**

**Architecture, from the factory package lists (not from memory):**

| | factory `com.verizon.messaging.vzmsgs` | factory `com.android.mms` |
|---|---|---|
| E4610 | **present** (`/system/priv-app/VZMessages/VZMessages.apk`) | **absent** |
| E4810 | **absent** | **present** |

So Message+ on E4810 is always **our sideload**, never a factory app; and on E4610 Message+ is the only
messaging app there is, so picture MMS must pass through it and there is nothing to fall back to. I had been
writing about "Message+ on E4810" without that distinction, which blurred the two completely different cases.

**The replacement version is real, and it is recorded nowhere.** `build-tools/lpt-message-plus/` rebuilds
Message+ v6.4.5 (versionCode 116) and `patch_msgutils.py` null-guards `MessageUtils.getContentTypeFromUri`
so photo-attach cannot NPE. Hash evidence that a rebuilt copy reached a handset:

| file | sha256 (16) | bytes |
|---|---|---|
| `build-tools/lpt-message-plus/lpt-message-plus-shimv2-v2signed.apk` | `B1A49B0D29072915` | 53,777,483 |
| `_scratch/installed-vzmsgs.apk` — pulled off a device 2026-09-09 12:38 | `B1A49B0D29072915` | 53,777,483 |
| `tools/apks/message-plus-e4610-v6.4.5.apk` (pristine) | `DD7551D3DB5BCED1` | 54,089,271 |
| APK pulled off customer E4610 serial 615387849 | `DD7551D3DB5BCED1` | 54,089,271 |

**The gap that matters:** a repo-wide search of `scripts/`, `cli/` and `docs/` for `shimv2`,
`lpt-message-plus`, `patch_msgutils`, `installed-vzmsgs`, `message-plus-shim` returns **zero** hits. The
deploy config still points at the pristine APK and no receipt mentions the shim. **The modified app was
hand-applied and is therefore unattributable — we cannot say which serials have it.** Any hand-applied app
swap on a customer handset must leave a record naming the serial, the APK hash and the date; otherwise a
later MMS complaint cannot be traced to it, which is precisely what happened here.

**The live unit is NOT running the modified app.** Customer E4610 serial 615387849, APK hash
`DD7551D3DB5BCED1` = the pristine factory file. So its failure reproduces on the unmodified app, and the
modified build is not the cause on that handset.

**What the live unit does show:** Message+ is default, enabled, not stopped, holds `RECEIVE_MMS`/`READ_SMS`/
`SEND_SMS` granted, and declares `PushReceiver` for `application/vnd.wap.mms-message` — the PackageManager
resolves it. Yet `com.android.smspush` (pid 5189) logs
`W/WAP PUSH: no receiver app found for 4:application/vnd.wap.mms-message` when an MMS arrives, and the
dedicated `ApnContext:mms` connection (which comes up successfully, `SETUP complete type=mms, reason:connected`)
is released ~4 s later with nothing consumed. Data plane is validated on `VZWINTERNET`. So: not the filter
(28 disabled packages, none messaging/telephony/WAP), not the data plane, not the app being disabled — the
hand-off from the WAP-push dispatcher to the app is what fails. Observed once; no rate measured.

**Corroboration from the same 2026-09-09 session:** `_scratch/send-window.txt` is a logcat window from an
attempted send, showing the messaging app polling `getMobileDataEnabled()+ subId=2 ... retVal=true` over and
over with **no MMSC transaction at all** — the same "waiting on data, never reaching the MMSC" shape.

**Transferable rules:**
- Read the *factory* package list before describing which app a model ships with. Two models in one product
 line can have opposite messaging architectures, and a sentence that blurs them makes every later
 conclusion wrong.
- Anything hand-applied to a customer handset needs a record: serial, APK sha256, date, who ran it. A build
 directory with no references and no receipt is a future unanswerable question.
- Hash, do not size-compare, when identifying which APK is on a phone — and pull the file off the handset
 rather than reasoning from the build tree.
- My own tooling had two bugs that only hardware could reveal (a device-state regex that demanded whitespace
 before a tab-separated serial, and `date +%s%3N` on toybox emitting a literal `N`). Run the tool on a real
 device before trusting its evidence.
