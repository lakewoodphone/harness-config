**L3635 · One text column holding two date formats silently destroys ordering and every year bucket**

Measured 2026-10-13, on two independent systems in this estate, within one hour. Treat it as a
class of defect, not two incidents.

CASE 1 — `/root/.sms-inbox/inbox.db`, `messages.date_sent`.
2,323 rows: **2,189 are RFC-2822** ("Wed, 30 Sep 2026 16:44:20 +0000") because Twilio's REST API
returns that, and **134 are ISO-8601** ("2026-09-28T22:43:10.210640+00:00") because
`mirror-owner-sms.py` maps the app's `sms_log.created_at` onto the same column.
SQLite compares those strings byte by byte, so:
 * `ORDER BY date_sent` sorts every day-name row ABOVE every digit row, and compares
 day-of-month before month, so `max(date_sent)` returns `Wed, 30 Sep 2026 16:44:20 +0000`
 while the true newest message is `2026-10-12T16:25:01+00:00`;
 * the claimed range (`2026-09-18 .. Wed, 30 Sep`) is nonsense; the TRUE range is
 `2025-09-02T06:19:25+00:00 .. 2026-10-12T16:25:01+00:00`.
The owner reported this as "it needs to be ordered". He was right, and it was worse than he said.

CASE 2 — `/root/authority.db`, `purchases.order_date` (3,973 rows, Amazon/eBay receipts).
Same mix. `substr(order_date,1,4)` — the obvious way to bucket by year — returns
`'Fri,' 502, 'Mon,' 896, 'Sat,' 203, 'Sun,' 205, 'Thu,' 1,023, 'Tue,' 825, 'Wed,' 313, '2026' 6`.
Any per-year or per-month report over this table is garbage, and it looks like data.

RULE. Any column named `*_date`, `*_time` or `*_at` holds ONE canonical sortable format — ISO-8601
UTC — and any raw heterogeneous value is kept in a separate column beside it. Normalisation is
additive and must be idempotent and self-healing (safe to run on every start), because a
half-migrated store is worse than an unmigrated one.

THE TRAP, MEASURED THE SAME HOUR. The `GAP:` lines in `~/.sms-inbox/sync.log` did not mean what they
looked like. A GAP is emitted only when a sid is missing from the APP's `sms_log`
(`sms-inbox.py:311-322`) — never "missing from the store". Of 406 GAP lines in one run, **405 were
already in the store**, and the app's `sms_log` held 0 rows, so every inbound printed as a GAP on
every run: 513 runs, 207,025 lines, 24 MB of noise. The REAL gap printed nothing, because a
`--pages 3` x PageSize 200 window cannot see it. **A log line that always fires carries no
information, and believing it hid real loss.** Twilio held 11,903 outbound against the store's
1,914 — 9,989 messages invisible, back to 2025-09-08. One of my own sibling children reproduced the
mixed-format defect inside its own comparison code within the hour of reporting it, which is the
strongest possible evidence that this is a habit and not an oversight.
