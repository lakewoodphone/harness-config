**L2615 · The staff console advertises an EMPLOYEE role that cannot exist - and the frontend type is what hides it**

**L2783 · The staff console advertises an EMPLOYEE role that cannot exist — and the frontend type is what hides it**

Recorded 2026-09-28 (ZABZ-YOGA) while building the LPT `More apps` staff surface.

MEASURED, from the database rather than from the source:

```
select string_agg(enumlabel, ',' order by enumsortorder)
from pg_type t join pg_enum e on e.enumtypid = t.oid
where t.typname ilike '%role%';
-- UserRole | ADMIN,MANAGER,CUSTOMER,PARTNER
```

That is the production Postgres enum on `lpt-apps-01` (`docker exec lpt-postgres psql -U lpt -d lpt_prod`).
`backend/prisma/schema.prisma:2926` agrees. The test DB agrees. There is no `EMPLOYEE` member, and
`select role, count(*) from users group by role` shows the only roles in use: ADMIN 6, MANAGER 3,
CUSTOMER 1 (prod); MANAGER 4, CUSTOMER 530, PARTNER 1, ADMIN 6 (test).

THE FRONTEND TYPE DISAGREES WITH THE DATABASE.
`frontend/src/types/auth.ts:6` is `'CUSTOMER' | 'EMPLOYEE' | 'MANAGER' | 'ADMIN' | 'PARTNER'` — it has
EMPLOYEE and lacks nothing, while the real enum has no EMPLOYEE. Because the frontend's own type
permits it, every consumer typechecks, and `tsc` can never catch this.

WHERE IT IS WRITTEN AS IF REAL (all inert):
- `frontend/src/config/navigation.ts:110` — the Waze sidebar entry is
 `roles: ['ADMIN','MANAGER','EMPLOYEE']`, with a comment saying *"the counter person sells, so they
 must see this entry"*. It renders for ADMIN and MANAGER only.
- `frontend/src/routes/MVPRouter.tsx:554` — `ProtectedRoute roles={['ADMIN','MANAGER','EMPLOYEE']}`.
- `backend/src/schemas/navigation.ts:9` and `backend/src/trpc/routers/ui.ts` — EMPLOYEE nav sets and
 role labels for a role no session can carry.
- Several backend tests build callers with `role: 'EMPLOYEE'` and pass, because they construct the
 context directly instead of authenticating.

AND THE SYSTEM CONTRADICTS ITSELF ABOUT WHAT AN "EMPLOYEE" IS.
`backend/src/trpc/routers/adminSettings.ts:219` says it in as many words:
*"Map EMPLOYEE to CUSTOMER role (Prisma only has ADMIN, MANAGER, CUSTOMER)"* — the admin UI offers
"Employee", the write path stores `UserRole.CUSTOMER`, and `backend/src/trpc/context.ts:583` then
REFUSES customers on every staff procedure. So an admin who creates an "Employee" creates a user who
cannot open any staff screen, while the sidebar and route guards still claim the role exists.

WHY THIS KEEPS HAPPENING: a hand-written union type that is a SUPERSET of the database enum is
invisible to the compiler. `tsc` checks every use against the type, and the type is the thing that is
wrong. The bug lives in the gap between the type and the column, and nothing in this repo compares
them.

WHAT TO DO (not done in this session — recorded, not fixed):
1. Do not add `'EMPLOYEE'` to new role lists. The `More apps` registry
 (`backend/src/services/managed-apps/app-registry.ts`) uses only `['ADMIN','MANAGER']` and says why.
2. The real fix is one direction of truth: derive the frontend `UserRole` from the backend enum (or
 from a shared-types constant) so a role that cannot exist cannot be named. Until then, every
 role-gated surface in this app is unverified by the compiler.
3. Decide the business question underneath it: does the shop want an employee tier below MANAGER? If
 yes it needs a real enum member and a migration; if no, `adminSettings.ts` must stop offering
 "Employee" and the nav/route guard lists must drop it. Either way the current state — offered,
 stored as CUSTOMER, and refused — is wrong.

EVIDENCE: enum query output above; `schema.prisma:2926`; `frontend/src/types/auth.ts:6`;
`navigation.ts:110`; `MVPRouter.tsx:554`; `adminSettings.ts:219`; `context.ts:583`; the two
`select role, count(*)` outputs above. All read 2026-09-28 on ZABZ-YOGA.
