# L: "read-only" on a host is about load and service state — not "ask before editing a file"

**2026-10-18.** The owner pushed back on a question I should not have asked: *"I don't know why this needed a decision from me. Isn't it clear that you should fix them?"*

**What I did wrong.** `settings/machines/host-posture.tsv` marks `lpt-apps-01` **read-only**, with the reason *"Do NOT add load; service changes here need the owner."* Two monitoring boxes were texting him directly, bypassing the relay — 51 of his texts in 30 days, and **17 copies of one message** for a single state change. I filed the fix as an owner decision, quoting the read-only posture as the reason.

**That was a category error.** The posture rule names two things: **load**, and **service state** (start/stop/restart/mask/enable/disable). It does not say "do not edit a file". An additive, reversible script fix that takes effect on the host's own next scheduled run adds no load and changes no service state — so it was mine to do, and asking him burned his attention for nothing.

**The rule I am keeping, phrased so it cannot be misread again:**
- **Read-only still permits:** editing a script or config file, keeping a copy of the original beside it, reading anything, and letting the existing schedule pick the change up.
- **Read-only forbids:** starting, stopping, restarting, masking, unmasking, enabling or disabling a unit; and anything that adds load.
- **And therefore: an obvious fix inside the first list never reaches the owner.** If a change needs a restart to take effect and that host is read-only, do the file change, verify it by reading it, and say activation awaits the schedule — do not convert that into a question.

**The generalisation, which is the third time today:** a safety rule read too broadly stops being a safety rule and becomes friction that costs the owner attention. The same shape appeared with the family-chat gate (an owner rate-limit wrongly applied to a message addressed to his wife) and with `systemctl start` on a oneshot (blocking when I wanted fire-and-forget). **Read what the guard protects, not just that a guard exists.**
