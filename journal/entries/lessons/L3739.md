**L3739 · Never git commit --amend in this repo: a sibling session can move HEAD under you**

MEASURED 2026-10-12 ~03:35Z, ZABZ-YOGA. A sibling session pushed commit 8c00270d to origin/main while
this session was working. This session then ran `git add <two files>` followed by
`git commit --amend --no-edit` to fold a journal-id correction into its own commit - and `--amend`
rewrites *HEAD*, which was no longer this session's commit but the sibling's, already published.

WHAT IT DID: it rewrote a published commit (0c02766d locally), so `git status` read `ahead 1, behind 1`,
and the sibling's commit carried two files that were not theirs. Nothing was lost, but the tree and the
attribution were briefly wrong.

THE RULE: in this estate more than one session shares one repository, so **`git commit --amend` is never
safe** — HEAD may have moved under you between your commit and your correction. Fix a commit that is
still the tip only after PROVING it is the tip (`git log --oneline -1` and compare the hash to the one
you created), never by assuming. `git commit --amend` on a commit that is on `origin` is worse than any
of the things the forbidden list names, because it is invisible until somebody's push is rejected.

THE REPAIR, AND IT USES NO FORBIDDEN COMMAND: `git reset --soft <published-hash>` moves HEAD back to the
published commit while leaving the index alone, so the changes you meant to commit are staged on top of
the *right* commit; commit them normally. Then `ahead 1, behind 0`. `--soft` never touches the working
tree and never rewrites a published object.

HOW TO CHECK BEFORE AMENDING: `git log --oneline -1` and `git branch -r --contains <your-hash>`.
