**L3739 · In lpt-hub sync records, references.workOrderId is a SECRETARY task id, not a production order id**

**In lpt-hub sync records, `references.workOrderId` is a SECRETARY id, not a production order id — so a record that looks linked can match nothing.**

Measured 2026-10-13 on ZABZ-TECH.

`docs/customer-operations/CROSS_REPO_CUSTOMER_SYNC_CONTRACT.md:45-50` gives the preferred matcher order as `references.workOrderId`, then `references.orderNumber`, then `references.ticketNumber`, then `customer.phone` — i.e. `workOrderId` is presented as an **operational** matcher, so any reader expects the production `orders.id`. Corpus-wide, it is not that.

Eight records sampled in `docs/customer-operations/sync-records/`, all eight with both keys present: **every one** has `references.workOrderId` != `references.productionOrder.orderId`. Two of them resolve exactly to a live **`tasks.id` on the authority**:

- `2026-06-07-canon-sx740-nahem.json` — workOrderId **2899**, prod.orderId 1573. `tasks.id` 2899 is *"LPT Customer - Moshe Nahem: Canon SX740 Lens Replacement"*.
- `2026-06-01-kaplin-jelly2-photo-recovery.json` — workOrderId **3134**, prod.orderId 1585. `tasks.id` 3134 is *"Rubin - Gateway GWtn141-10BK battery replacement"*.
- `2026-08-24-q6-battery-7326783677.json` (the Rosenbaum Q6) — workOrderId **13405**, prod.orderId 2711. `tasks.id` 13405 is *"Order battery for LG Q6 case"*.

**Why it bites.** Production order ids in this estate are four digits and secretary task ids are four and five, so the two collide in range. A matcher that resolves `references.workOrderId` against `orders.id` gets a **silent no-match** — which reads exactly like "this case has no order", the failure class behind the whole reverse-gap family (`sync-health-audit.py`, `audit.py` C11).

**What to do.**

- Never read `references.workOrderId` as the production order id. For the real order, use `references.productionOrder.orderId` / `.orderNumber`, or `workflow.orderNumber` / `.orderId`.
- Do **not** "fix" one record by rewriting its `workOrderId`: that makes it disagree with the other ~380 and can break whatever currently depends on the convention. Populate `references.orderNumber` and `references.ticketNumber` instead — both real production values, both in the matcher order — and leave `workOrderId` alone.
- Repairing the convention is one corpus-wide job (a backfill with a before/after count), not a per-record edit. Not started.
