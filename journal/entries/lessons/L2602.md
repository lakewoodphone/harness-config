**L2602 · A git worktree add killed by the harness timeout is locked, indexless and missing files - it looks fine and is unusable**

A `git worktree add` killed by the harness at its 180 s timeout leaves the worktree
LOOKING fine and being UNUSABLE. Measured on ZABZ-YOGA, 2026-09-28, branch
`lpt/cardhook-20260925` from `origin/test`:

What the corpse looks like
- `git worktree list` shows the worktree, at the right sha — but marked **locked**,
 and the lock file contains the single word `initializing`.
- The staging area (`index`) was never written: `git status --porcelain` reports
 **every tracked file as `D`** (10,986 rows on this repo), so `git diff` and
 `git commit` are both meaningless.
- A zero-byte `index.lock` sits in the worktree's gitdir
 (`.git/worktrees/<name>/index.lock`), which makes any `git reset` fail with
 "another git process seems to be running".
- The **working tree is also incomplete** — this is the part that bites. The
 checkout was killed partway, so ~1,710 of 10,907 files were never written to
 disk. `git reset --mixed HEAD` fixes the INDEX and leaves those files missing,
 so a later `git diff --name-status` shows them as deletions.

The recovery (this order, verified)
1. Confirm no `git` process is alive (`Get-Process git`).
2. `git worktree unlock <path>` — the lock reason `initializing` is proof the
 process that took it is gone.
3. Delete the zero-byte `<gitdir>/index.lock`.
4. `git reset --mixed HEAD` to rebuild the index. Expect a very slow first run
 (~119 s here) because it refreshes every path.
5. `git checkout -- .` to restore the files the killed checkout never wrote.
 Only then is `git status` empty.
6. Spot-check the file count, not just the status — an index that disagrees with
 the tree can report clean while files are absent.

Why it matters beyond the mechanics
- A "clean" worktree that silently lacks 1,710 files will produce green tests for
 code that does not exist and red tests for files that are simply missing. Verify
 the worktree before trusting any result that comes out of it.
- Do not re-run `git worktree add`: the directory exists, so it fails.
- The lock file means `git worktree remove` will also refuse, so cleanup of a
 corpse needs `unlock` first too.

Same root cause as the moving-ref trap: a harness timeout does not roll back a git
operation, it only stops the process. Any mutating git command killed mid-flight
must be re-verified, never assumed.
