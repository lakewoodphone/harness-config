**L3196 · L: building a Hyper-V lab that actually isolates - seven things this cost hours to learn**

EVIDENCE: 2026-09-30, building the detonation lab on ZABZ-TECH. Every item below was learned by measuring, after getting it wrong first.

1. HYPER-V'S 'DEFAULT SWITCH' IS NOT AN ISOLATION BOUNDARY. Its type reports as Internal, which reads as safe, but it NATs to the host's real network. A guest on it can reach the office LAN and Tailscale - measured here, and this host holds an active Tailscale session to secratary. The alternative, Windows Sandbox, takes the host network stack with no isolation control at all. The only correct construction: New-VMSwitch -SwitchType Internal with NO -NetAdapterName (no uplink), a host-side address in a dead range, and host firewall rules blocking the subnet in both directions.

2. POWERSHELL DIRECT SOLVES THE ISOLATION-VS-AUTOMATION CONFLICT. Invoke-Command -VMName reaches the guest over the VM bus, not the network. So analysis can be driven inside a guest that has no route anywhere. This is the single most useful fact of the session and it makes the whole design workable.

3. DON'T CONCLUDE A FILE IS CORRUPT FROM ONE BOOT FAILURE. A Windows 11 ISO appeared to fail boot in Gen2 with worker event 18603. I spent a long time on that conclusion. Then the owner clicked through Setup himself and it booted fine - the ISO was never broken. My test windows were 60-90 seconds and the setup loader needs longer. LESSON: absence of a result inside my polling window is not a negative result. Same class of error as reporting a timed-out search as 'no record exists' (L3191).

4. HYPER-V WANTS A VHD, NOT A RAW FLOPPY. Add-VMFloppyDiskDrive does not exist in this Hyper-V module. Hand-rolling a VHD footer produced 'file is corrupted and unreadable'. The route that works with zero risk: New-VHD, Mount-VHD, Initialize-Disk, New-Partition, Format-Volume, copy the file, Dismount-VHD. Built and verified in one try after two failures.

5. INTERNAL NVME IS 72x FASTER THAN THE USB STICK. Measured on this host: C: write 1015.6 MB/s, D: (USB SanDisk) 14.1 MB/s. A DISM image apply that was running at roughly 1 percent per minute on USB completed in about 4 minutes on NVMe. Never build a VM on removable media.

6. A RAW DISM APPLY NEEDS /Apply-Unattend OR SPECIALIZE FAILS. Applying install.wim and then dropping an unattend into System32\\Sysprep is not enough. The specialize pass died with:
 capisp.dll::SamConnect failed: c00000dc (STATUS_REGISTRY_CORRUPT)
 'Windows Setup could not configure Windows to run on this computer's hardware'
 because the Security Account Manager never initialises. The fix is dism /Apply-Image ... /Apply-Unattend:<file>, applying the answer file WITH the image. The answer file must also carry the passes that matter - specialize and oobeSystem - not oobeSystem alone.

7. MEMORY OVERCOMMIT HARD-CRASHED THIS HOST. Observed at 76.97 GB committed against 63.6 GB physical, and the machine went down; it rebooted at 16:59. Contributing cause found: eleven stray pwsh processes holding 10.03 GB between them, one of them at 9.4 GB. Hyper-V will happily 'start' a VM it cannot commit memory for, and the guest then never runs (0 percent CPU, 0 MB memory demand, disk never grows) - which is exactly what it looked like and why it was mistaken for a boot problem. RULES: check free physical BEFORE starting a VM; keep the lab guest at 4 GB; kill long-lived stray shells; and treat 'VM Running but memoryDemand=0' as a memory-commit failure, not a boot failure.

WHAT MADE THE DIFFERENCE IN THE END: measuring instead of assuming. The isolation properties were verified by reading them back (SwitchHasUplink=False, VMUsesLabSwitch=True, VMHasOtherAdapter=False, 2 firewall rules, no default route on the lab subnet). Every wrong turn above came from believing a plausible story rather than checking.
