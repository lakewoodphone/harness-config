## iOS asset downloads (dictionaries, MobileAsset) are invisible to the managed resolver and the managed PAC — host lists cannot block them

Measured 2026-10-22 on DRN 2007 (iOS 26.x, supervised, DNS profile + webtrap PAC + restrictions installed), against the live filter on waze-mdm-01. Full record: `personal-secretary-mvp/deploy/waze-mdm/docs/2026-10-22-dictionary-redownload-investigation.md`; handoffs `H12227` and its successor.

**The rule.** When a flow on a supervised iPhone must be stopped, ask first *which component sees it*. A MobileAsset fetch (dictionary = one) is issued by a system daemon that does not use the device's managed resolver and does not honour the device's PAC. Consequences:

- The DNS allowlist and blocklist are irrelevant to it — including a 42-name skeleton that refuses **every** Apple name.
- The pac's per-host rules are irrelevant to it too, even with the served file changed and a reboot forcing a refetch.
- Only a socket-level control sees it: a Network Extension content filter (`com.apple.webcontent-filter`, `FilterType=Plugin`, signed, Apple entitlement). That is a project, not a config change.

**Do not** spend another night blocking Apple hostnames to stop a dictionary (or any Apple *asset*) download. The download requires network (airplane mode stops it), which is what makes it look like a network-policy problem; it is not one.

**Two measurement traps that made four owner retests worthless, both worth more than the finding:**
1. **A DNS block tested against a warm cache measures nothing.** iOS keeps resolved addresses and live connections; airplane mode drops connections but does not clear the resolver cache. A DNS negative is only a measurement if the phone was **rebooted** between the change and the tap, and preferably if the block has been up longer than the CDN TTL. Two negative results here were produced entirely by cache reuse and were reported to the owner as if they were findings.
2. **`docker compose up --force-recreate` deletes the container and its log.** Twice this destroyed the exact tap window that had just been produced for me. Dump first: `docker logs <c> > /tmp/log-$(date -u +%H%M%S).txt`.

**Two more, cheap but repeatable:**
3. `doh_filter.py` checks **allow before block**, so a name on the blocklist that is also on the allowlist resolves. Being on a blocklist is not evidence of being blocked — verify with `docker inspect` (`ALLOWED=n BLOCKED=m`) *and* with a live query, never with the list alone.
4. A **dead-man restore timer and a manual `--force-recreate` collide** on the container name and can leave the service down (took the production filter down ~2 min on 2026-10-22). `pgrep -f env_before_deny` before touching a container that a timer owns.
