**L3246 · The DSH pin has been stuck at 0.1.5-rc.1 since 2026-09-23 because harness-config stands on the version seam, and analyze therefore reports BREAKS for every candidate**

MEASURED 2026-10-05 on ZABZ-TECH. `dsh-update/state/pin.json` has said `0.1.5-rc.1` since
2026-09-23 and nothing has been promoted since — not because the tools were missing, but because
`harness-config` is standing on the version seam and `analyze` therefore reports BREAKS for EVERY
candidate, old or new.

THE EVIDENCE, read from the tree:

* `profiles/web/cordis.patch.yml` (the REPO copy): 1624 lines, and it names the 0.1.7-line packages at
 least six times — `@deepseek-ai/dsh-agent-preset` at lines 301, 485, 980 and
 `@deepseek-ai/dsh-workflow-ptc` at lines 463, 928, 1481.
* `scripts/make-preset-rows.mjs:121`: declares `@deepseek-ai/dsh-agent-preset` in `dsh.profile.bundles`.
* `presets/*/agent.cordis.yml` (all three): still name `@deepseek-ai/dsh-workflow-worker-thread` —
 the 0.1.5 name — because commit 60b3724 on 2026-10-04 deliberately pinned the presets BACK to the
 0.1.5 names after they broke new-session creation on a machine still running 0.1.5.
* `~/.dsh/profiles/web/cordis.patch.yml` (the LIVE copy): 252 lines, and it names NEITHER set — no
 coupled name at all.

So the repo's profile patch is on the NEW names, the repo's presets are on the OLD names, and the live
profile is on neither. `sync.py`'s version guard does its job and SKIPS the two coupled scopes, so
nothing breaks in production — but `analyze`, which scans the REPO, reports:

 0.1.5-rc.3 BREAKS=3 dsh-agent-preset (repo profile row), dsh-agent-preset (bundle decl),
 dsh-workflow-ptc (repo profile row)
 0.2.0-rc.2 BREAKS=2 dsh-agent-presets at profiles/mesh/cordis.patch.yml:93,
 dsh-workflow-worker-thread in all three presets
 0.1.7-rc.2 BREAKS=1 + patch-effect BREAKS=2

and `verify` fails G2 with "LOST (our patch silently stopped applying): agent-preset-registry".

CONSEQUENCE: there is no candidate — including the same-line `0.1.5-rc.3` — for which `promote` can
pass condition 2 (the diff verdict is not BREAKS). The half-migration is the whole blocker, and it is
invisible from `status` alone because each half looks reasonable on its own. `check-version-coupled-
config.py` names this exact state in its own header: "the machine is standing on the seam".

WHAT IT MEANS FOR THE NEXT SESSION: the only two coherent end-states are
(a) roll all three repo surfaces back to the 0.1.5 names and promote a same-line version, or
(b) complete the migration for the 0.1.7+ line — migrate the three presets to registry rows with
`scripts/make-preset-rows.mjs` AND prove the candidate engine actually composes those rows, because on
0.1.7+ `~/.dsh/.agent-presets/` is not read at all.
(b) is the one worth doing: the repo's profiles and scripts are ALREADY on the new names, so the
remaining work is the presets plus the wiring, and `switch-engine.ps1`'s precondition 2 only greps
`.agent-presets/*/agent.cordis.yml` for a name — it would pass a staged home whose presets are dead on
the target engine. That grep is a proxy, not a proof, and the proof has to be a composed tree.
