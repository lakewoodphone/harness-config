**L2913 · Measure which rate-limit policy a route resolves to before believing its budget name**

kosher-filter-ai, 2026-09-28, kf0928/server-tests-green. A brief stated that POST /admin/households/{id}/admins draws settings.rate_limit_admin_write_per_minute (20/min, burst 4). Instrumenting TokenBucketLimiter.check_many printed rate=30 burst=5 for every call: admin_household_add_admin is in neither _ADMIN_WRITE_ACTIONS nor _ADMIN_READ_ACTIONS in app/rate_limit_policy.py, so resolve_admin_rate_limit_policy falls through to its final branch, _policy(settings.rate_limit_admin_per_minute, burst=5). The write budget is never consulted for that route. A fix built on the brief's statement would have patched the wrong setting and changed nothing.

Same run, the key: build_admin_rate_limit_keys keys on the authenticating operator PLUS the action name (admin:actor:admin:admin_household_add_admin), never on the household or tenant. So seeding N households with the same super-admin credentials spends one shared bucket, while each household's own /owner/level calls get a fresh per-household bucket. When a test module's setup starts getting 429s, instrument check_many first: which setting, which key, and whether the bucket is empty at the start of the failing test decide the fix.
