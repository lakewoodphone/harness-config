**L3458 · uutils du rejects --max-depth=0; PowerShell here-strings break the last line of a remote bash block**

On a machine whose `du` is uutils coreutils (secratary-ts and secratary-cloud both report `du (uutils coreutils) 0.8.0`), `du -shx --max-depth=0 <dir>` FAILS with `du: summarizing conflicts with --max-depth=0` and prints NOTHING on stdout. It does not error loudly enough to stop a script, so a loop over ten roots silently returns ten blank lines and looks like "these directories are empty" rather than "this command is invalid".

USE `du -shx <dir>` instead (no --max-depth). To size a directory's children, loop: `for d in dir/*; do printf "%s %s\n" "$(du -shx "$d" | cut -f1)" "$d"; done`.

Second trap, same session, same class: piping a PowerShell here-string into `ssh host "bash -s"` sends CRLF. Bash then carries a trailing `\r` into the LAST command of the block, so `cut -d' ' -f1 /proc/loadavg` becomes `cut ... /proc/loadavg\r` and fails with `/proc/loadavg\r: No such file or directory` - WHILE every earlier line in the same block succeeded. A load check that fails silently at the end of a script is a load check you believe when you should not.

FIX: build the block as a PowerShell array and join with "`n" (not a here-string, which keeps CRLF), or run `$s -replace "`r",""`. Portable rule: never author a remote script as a here-string.

Why it matters here: this workstream's whole discipline was "check the office load around anything that touches its disk" (RULE 1 of the migration brief). Both traps attack exactly that check.
