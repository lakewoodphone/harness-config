**L · Widening the model retry budget from 2 to 3: a 1.5-second window was losing whole turns on the owner's phone**

WHAT HE SAW, 2026-10-13, and reported as *"what's this error I just got"*: on his phone the turn rendered
**"This turn failed · DeepSeek Messages · TRANSPORT"** with "Retried model request (2/2)". His message was
lost and had to be re-sent.

ROOT CAUSE, read from the session ledger, not guessed. His phone session
(`~/.dsh/sessions/--home-zabz-phone--/session-3064a8ca-.../session.v4.jsonl.zstd`) carries
`llm/retry` events: turn 4 step 1, provider `deepseek-official`, failure
`{"message":"DeepSeek Messages transport failed","code":"TRANSPORT"}`, retry 1 at **515 ms**, retry 2 at
**932 ms**, then nothing -- and the turn died. The policy was `normal/2` with `initialDelayMs 500`, so the
entire retry window was **~1.5 s**. Any connectivity blip longer than that costs a whole turn.

HOW RARE, measured rather than assumed: scanning 477 session files from the last 21 days on this host gave
**22 TRANSPORT failures, 21 of which recovered on the FIRST retry** and never produced a second event. Exactly
one -- his -- exhausted the budget. So the policy was right 21 times out of 22 and still failed him; the fix
is not "retry harder in general", it is "the tail is uncovered".

THE FIX (shipped): `settings/base.yaml` -> `maxRetries: 3`, `initialDelayMs: 750`, `maxDelayMs: 6000`.
Delays become ~0.75 / ~1.5 / ~3.0 s -- a **~5.3 s coverage window**, which clears the observed failure with
room, while a genuinely dead provider still fails in seconds (the 2-retry choice had been bounded against a
2026-09-14 outage and a "multi-minute stall"; 5.3 s is not that). `jitterRatio` unchanged. The rationale in
base.yaml was rewritten to carry this measurement, so nobody "simplifies" it back.

**HOW TO RUN THE SETTINGS PIPELINE ON THE AUTHORITY -- the step that cost time:** `merge-settings.mjs`
resolves the `yaml` package from a fixed candidate list and does **not** search `/opt/dsh-phone`, so it dies
with `cannot resolve a usable "yaml" package` even though `yaml@2.9.1` is sitting at
`/opt/dsh-phone/node_modules/yaml`. It honours `DSH_INSTALL`: export **`DSH_INSTALL=/opt/dsh-phone`** and it
runs. Full sequence, and it must be done in this order:

 export PATH=/usr/local/node22/bin:$PATH DSH_INSTALL=/opt/dsh-phone
 node scripts/merge-settings.mjs settings/base.yaml settings/machines/ZABZ-TECH.yaml /tmp/m.yaml
 node dsh-update/tools/settings-to-entries.mjs --settings /tmp/m.yaml --install profiles/web/cordis.patch.yml
 node dsh-update/tools/settings-to-entries.mjs --settings /tmp/m.yaml --install profiles/web/cordis.patch.yml --check

**`profiles/web/cordis.patch.yml` IS GENERATED FROM `ZABZ-TECH.yaml`, NOT FROM THE BASE ALONE.** Merging with
`SECRATARY.yaml` reports false DRIFT, because `agent-loop.maxParallelToolCalls: 20` is set in the ZABZ-TECH,
LAKEWOOCHSMINI and DESKTOP-FGV6KMH machine files but **not** in SECRATARY's -- so regenerating from the wrong
machine silently **deletes** that row. Always `--check` first and prove the diff is only yours; the good
outcome is `UP TO DATE` and a one-line diff.

EVIDENCE: provider reachability re-tested from the authority immediately after the failure -- three calls to
api.deepseek.com all connected in 2.7-3.3 ms with 320-390 ms total, so the provider was healthy again within
seconds and this was a transient path failure, not an outage. Commit carrying the change: see the same-day
harness-config commit touching settings/base.yaml + profiles/web/cordis.patch.yml.
