**L1959 · Fannning out by file is not enough - partition mutation rights, and never rename a directory a peer is still reading**

**What happened (2026-09-17).** Two agents were fanned out over one photo folder. One was told to rename `jpg/*.jpg` to descriptive names; the other was mid-task making native-resolution crops and had been given a brief that addressed frames as `jpg/IMG_0896.jpg`. The renamer ran while the cropper was still working, and every plain path in the cropper's instructions stopped existing. It reported the collision itself, correctly: *"jpg/ was RENAMED underneath me by another agent mid-task ... any instruction that addresses jpg/IMG_08xx.jpg by name is now broken, and two agents writing that directory at once is a collision waiting to happen."* Nothing was lost here because the crops derived from `original/`, not from `jpg/` — which was luck, not design.

**The rule.** Partitioning a fleet **by file** is not enough. Partition by **mutation rights**: for each directory, decide whether it is read-only or written, and never let two agents hold write rights to the same directory — and never let one agent *rename or move* anything while a peer may still be reading it by name. Renames are the worst case, because they break paths that were valid when a brief was written. Where a rename is needed, either run it as a final serial step after every reader has stopped, or give the readers a stable path (here: `original/`) and treat the derived directory as disposable.

**Detection**: after a fan-out, re-verify that every file an agent claimed to open still exists under the name it used. An agent that succeeds despite a broken brief is a lucky sample, not a passing test.
