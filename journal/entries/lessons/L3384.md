**L3384 · Every mesh dispatch was dying on a node whose roster row still said dispatchable: the broker logs a clean place/done either way, and that is how the whole fleet silently went local**

**Recorded 2026-10-08 (ZABZ-YOGA). The whole fleet was silent for hours and the instrument said
healthy, because the broker only ever reports that it *placed* work.**

**What happened.** Every mesh dispatch failed. The broker log was clean:
`place -> zabz-tech position=0 tier=fits` eight times at 02:42:31-02:42:36Z, each `done -> released`
within seconds. From the Yoga, all eight `subagent` calls returned "the remote one-shot exited 1 and
produced no final message". So nothing looked broken at the placement layer, and every session did its
work **locally** — which is why the laptop became unusable (the owner: *"the yoga is getting more and
more sluggish cuz all of you stopped offloading the hard work to the mesh ... why do you keep skipping
over and ignoring a massive issue"*). I had seen the first lost child earlier and written it down as a
bullet instead of treating it as a root cause. That was the failure the owner named.

**The diagnosis, measured, in the order that found it.**

1. `mesh-broker.service` on the authority is **active**, port 3091 listening, `GET /place` -> 405
 (POST-only). The broker was never the problem.
2. Its roster had **`zabz-tech` `dispatch.v1: true`, `measuredAt: 2026-09-16`** — a 22-day-old
 measurement, while `zabz-tech-linux` (verified 2026-09-17) worked.
3. Running the primitive **by hand on the node** produced the real error. First attempt was wrong and
 worth recording: `ssh zabz-tech 'dsh --profile headless ...'` -> *"dsh is not recognized"*. That is
 **expected** on Windows — `plugin-remote-fanout/lib/nodes.js` documents that ZABZ-TECH has no `dsh`
 executor and uses the **interpreter form** (`node <bin.js>`). I called it too early; the correction
 is half the value of this entry.
4. The interpreter form, run through ssh: DSH loads, the MCP server inside it answers
 `ListToolsRequest`, and then the process **exits 1** with
 `PermissionError: [Errno 13] Permission denied: 'C:\Users\ezabz\Code\personal-secretary-mvp\data\logs\mcp-launcher.log'`
 from `scripts/vscode-update/mcp_launcher.py`, whose copy on that node opens the log
 **unconditionally** after computing `missing = [keys absent from the repo's .env]`.
5. The file is **not** the problem: a plain ssh session appends to it (ACL grants the user FullControl).
 So it is the child's execution context, and the failing repo is a *different session's* live checkout
 (branch `integrate/dialpad-reconcile-20261007`, 43 dirty files) — repairing it in place was not an
 option.

**The fix, and it is the design's own recovery.** `dispatch.v1` exists precisely to carry "measured not
to work" (`nodes.json` `_transport_comment`: *"The broker ranks false below true ... and still places
there when it is the only candidate (queue, never amputate)"*). So `zabz-tech` was set to
**`v1: false, measuredAt: 2026-10-08`** with the evidence above, the roster was validated (loader
invariant `node == fqdn.split('.')[0]` holds), backed up (`nodes.json.bak-20261008T024918Z`), installed
to `/home/zabz/mesh-broker/nodes.json` (sha `6e1a491b…`), and `mesh-broker.service` restarted.
`zabz-tech-linux` was re-verified working the same night
(`dsh --profile headless 'Reply with exactly LINUX-MESH-OK'` -> `LINUX-MESH-OK`, exit 0).

**Verified, not asserted.** The next real dispatch:
`placement = broker -> node "zabz-tech-linux", position 0 (tier fits), score 4`;
`pressure = OK — route-remote — the LOCAL option was declined and offered to the mesh as excluded`;
`transport host = zabz-tech-linux (recorded by the target shell before the agent started)`;
`credential = the executor sources /etc/dsh-worker.env itself`; `exit = 0 in 20057 ms`.

**What to carry forward.**

- **A placement is not a run.** The broker reporting `place` and then `done` says the lease was handed
 out and returned; it says nothing about whether a child produced a token. The only proof of a
 dispatch is the target's own `transport host` line plus a non-empty final message. When fan-out
 "works" and nothing changes, read the child's stderr, not the broker's log.
- **A stale `dispatch.v1` is a silent capacity leak.** It was true once, and nothing re-measures it.
 Every session that trusted it fell back to local work and made the laptop worse. Re-measure it when a
 node's dispatch path changes underneath — a plugin, a launcher, a checkout.
- **When you see ONE lost child, that is not an anecdote.** I watched a subagent vanish with no
 registry entry earlier in the same session and filed it as a note. It was the same defect, and the
 cost of not investigating it was paid by the owner, on his own machine, for hours.
- **A logging failure must never abort a server.** That one line in `mcp_launcher.py` is what turned a
 missing-key warning into eight dead dispatches and a degraded laptop. Still to fix, in that repo,
 when its checkout is not mid-work.
