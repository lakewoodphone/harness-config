**L3384 · The office came back and corrected me twice: it never lost power, and the offsite copy I alarmed about was never the real one**

GOAL: the office came back at ~14:21Z on 2026-10-06, and the return corrected two things I had told the owner during the night. Both corrections are mine, and both matter more than any code I wrote tonight.

CORRECTION 1 - THE OUTAGE WAS NOT A POWER LOSS. For twelve hours I told him the four wired machines had lost power. The machine's own evidence says otherwise: the secretary box took its six-hourly snapshots all night (20261006T000001Z, 20261006T060001Z, 20261006T120001Z, each with a healthy database) and its 05:10 offsite job ran far enough to compress 5.2 GB before it failed to reach the network. The host was RUNNING the whole time. What was lost was the NETWORK PATH shared by those four machines - no internet, no Cloudflare tunnel, no Tailscale - while the Home Assistant host stayed reachable because it is on a different path. The outside monitor was right that the company was unreachable; it was wrong that the company was down. I read "530 on the public URL" and "Tailscale offline" and inferred "the machines are off", when the data to disprove it was sitting in a directory listing I never looked at. A reachability failure and a liveness failure are different failures, and the heartbeat cannot tell them apart because it only sees the public surface.

CORRECTION 2 - THE COMPANY HAD AN OFFSITE COPY ALL ALONG, and I alarmed about its absence for twelve hours. The real copy is a 5.1 GB object at lpt-authority-backups/authority/secretary.db.gz, uploaded daily at 05:10 by ~/bin/push-db-offsite.sh with a .sha256 sidecar and a size check. What I was monitoring was a restic repository I had built THAT SAME NIGHT, which was empty because it had never been used - and because it said "no offsite copy", I told the owner the company's data existed in one place. It did not; it was 33 hours stale, which is a completely different thing to be alarmed about. THE LESSON: before alarming about the absence of a protection, verify that the protection you are checking is the one the system actually relies on. A monitor that reads a file nobody else writes is not a monitor, it is an opinion with a cron entry. I built the replacement in the same evening - the office reports the real object's size and LastModified to the vault every 30 minutes, and the heartbeat alarms on the AGE OF THE REAL OBJECT - but that is a fix for the symptom; the disease was never asking where the real copy lived.

ALSO FIXED, FOUND THE SAME WAY: a second false alarm went out at 14:24 - "the API key guard is NOT enforcing ... ~350 endpoints may be readable by anyone" - on a 307. That was the dashboard redirecting the probe to its login page, a request that never reached the API. The check had been written as "401/403 means fine", so every redirect looked like exposure; it now asks the only question that matters, "did protected data come back?", and only a 2xx counts as exposed.

RULES: (a) reachability is not liveness - a 530 on a public URL proves the path is broken, never that the host is off; look for the host's own evidence (snapshots, logs, cron output) before naming a cause; (b) verify that the thing you are monitoring is the thing that matters, by finding who WRITES it - a monitor's own state file proves only that the monitor ran; (c) when a check's "safe" branch is an allow-list of two status codes, it will misreport everything else, including redirects from a login page; write down what exposure actually looks like (data returned) and test for that.
