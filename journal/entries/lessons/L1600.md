**L1600 · Verifying a bind-mounted Caddyfile secret: five traps that make an unapplied change look green**

Context: moving a literal bcrypt hash out of a bind-mounted Caddyfile into the container environment on waze-mdm-01 (2026-09-15). Each trap below makes a broken or unapplied change look verified.

1. A bind-mounted SINGLE FILE is pinned to an inode. `sed -i`, `install`, `mv` and most editors write a NEW inode; the container keeps serving the old file, and the host copy then looks correct while the gate does not. Fix: write in place (`open(path,'w')` truncates, same inode — verify with `stat -c %i` before/after) AND `docker compose up -d --force-recreate caddy`. A plain `up -d` prints "Running" and does nothing, and `caddy validate`/`caddy reload` still validate the OLD file.
 Proof that it is really applied: `docker exec <ctr> md5sum /etc/caddy/Caddyfile` must equal `md5sum /opt/.../Caddyfile` (here 823d6271feec203dddfa71b450956827).

2. `docker compose config` escapes `$` as `$$` in its output. Comparing its rendered value against the `.env` value reports a false MISMATCH for a correct single-quoted hash; unescaping first (or believing only the in-container value) is required.

3. A changed service `environment:` is NOT applied by `up -d` — the container must be recreated. So "the container has the variable" is only true after `--force-recreate`.

4. `caddy:2` has NO ENTRYPOINT (it has `CMD ["caddy","run",...]`). `docker run --rm caddy:2 validate --config ...` fails with `exec: "validate": executable file not found in $PATH`; the command must be `docker run --rm caddy:2 caddy validate --config ...`. Pre-flight-validate the new file in a throwaway container with `--env-file` built from the real `.env` (values unquoted, file mode 600, deleted after) BEFORE touching the live container — that keeps the live gate untouched if the config is invalid.

5. The Caddy admin API answers on 127.0.0.1:2019 inside the container, NOT on `localhost` (Alpine resolves localhost to ::1 and the connection is refused). `docker exec <ctr> wget -qO- http://127.0.0.1:2019/config/` returns the RUNNING config — that is the only place that proves which hash the live process actually loaded, and it is what turns "the file looks right" into "the gate is byte-identical to before".

VERDICT RULE: prove a credential move with byte-identity of the credential at every layer — file on host == file in container == container environment == running server's loaded config — comparing sha256 digests and printing only MATCH/MISMATCH. An identical bcrypt hash accepts exactly the same password set, which is stronger than any single successful login test.
