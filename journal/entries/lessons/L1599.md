**L1599 · Docker Compose interpolates values inside .env - an unquoted bcrypt hash is silently destroyed**

WHY IT MATTERS: moving a secret into `.env` so compose can pass it (`environment: X: ${X}`) looks safe and is not. Docker Compose parses `.env` WITH interpolation, so a bare bcrypt hash is silently destroyed before it ever reaches the container. The container then holds a wrong credential — for a Caddy `basic_auth` that means the gate refuses every login, or Caddy fails to start and takes every site on that Caddy down with it. The failure appears at deploy time, far from the edit that caused it.

MEASURED on waze-mdm-01, Docker Compose v5.1.3, 2026-09-15, by running a real container and hashing the variable INSIDE it (`docker compose run --rm t sh -c 'printf "%s" "$VAR" | sha256sum'`):

 bare VAR=$2a$14$ABCDEF... -> MISMATCH, resolved value 8 chars instead of 54
 (`$ABC...` was eaten as a variable name and expanded to empty)
 escaped VAR=$$2a$$14$$ABCDEF... -> MATCH, but breaks `set -a; . .env` and `docker run --env-file`
 quoted VAR='$2a$14$ABCDEF...' -> MATCH, and stays correct for shell sourcing and python-dotenv
 double-quoted VAR="$2a$..." -> MISMATCH (same corruption as bare)

RULE: every `.env` value containing `$` gets single quotes unless it is deliberately an interpolation. And never judge the result from `docker compose config` — it renders `$` back as `$$`, so a correct value and a corrupted one can look alike; the only trustworthy check is the value inside the container.

EVIDENCE: helper `/tmp/dsh_bcrypt.py` on waze-mdm-01 (`composecheck`, `envval` modes) — compares sha256 digests and prints only MATCH/MISMATCH, never the value.
