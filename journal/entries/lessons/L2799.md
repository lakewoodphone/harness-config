**L2799 · A guard that walks the loaded alembic ScriptDirectory cannot detect a duplicate revision id - it passes on the broken tree**

**Measured 2026-09-28, on the new guard for the P0 in `L2797`.**

The obvious way to find two migration files sharing a revision id is to walk the loaded
`ScriptDirectory` and count the ids. **It does not work.** Alembic keys its revision map *by id*, so
when two files declare `revision = "20260915_01"`, the walk yields that id **once**, no duplicate is
found, and the test passes on the broken tree.

Proven both ways, not reasoned: with the duplicate deliberately restored, the counting-the-walk
version printed **1 passed** for the duplicate check, while
`test_the_script_directory_has_exactly_one_head` failed. After changing the check to parse the
`revision = "..."` declaration out of the migration **files**, **both** tests failed on the broken
tree and both pass on the fix.

**The general rule this is an instance of.** A guard that reads a *normalised* view of the data cannot
detect a defect that the normalisation erases. So: detect the duplicate in the raw source, then
separately assert that the normalised view is what the application actually needs — two different
claims, two different reads.

**And the habit that found it:** run the guard against the defect it is supposed to catch, every time.
The first version of this test passed on the broken tree, which means it was decoration. A guard that
cannot fail is worse than no guard, because it looks like coverage — the same shape as the screenshot
wiring guard that stayed green on a dead feature (`L2786`) and the six Windows live-driver tests that
`SKIP` and read as "87 passed" (`docs/audits/kf0928/windows-merge.md`).
