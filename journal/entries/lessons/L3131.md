**L3131 · crontab refuses an unparseable file and keeps the old one - a safe failure I will not gamble on a third time**

ROUND 16, 2026-09-30 16:01Z. I tried to change the fan-out from every 5 minutes to every minute, to pick up expiring gates sooner. Measured reason it is worth doing: at 16:00:04 the guard skipped while wake-nextclaim reported the earliest gate at 16:00:09 - five seconds later - so nothing could claim until the 16:05 tick, and with 11 rows gated and 23 ledger items waiting, the tick rate is the binding constraint on how fast a freed row is claimed. The guard added today is what makes it cheap now: an idle tick costs one stats read and a skip line, where before it started a dispatcher that claimed nothing and wrote a line that read like a failure. THE ATTEMPT FAILED AND FAILED SAFELY. The piped script carried CRLF, the sed did not match, and crontab answered: line 58 bad command - errors in crontab file, can't install. Verified afterwards that the live crontab is UNCHANGED - the original */5 line is still there and the every-minute count is 0 - so crontab refused the input and kept the working file, which is the right behaviour and a property worth knowing. I STOPPED THERE RATHER THAN RETRYING A THIRD TIME. Two CRLF-caused failures in this session are enough to establish the pattern, and a mangled crontab would stop the company outright: a botched write here is not a small error, it is every release, every source and every guard at once. NEXT ATTEMPT, WITH THE METHOD THAT CANNOT GO WRONG: write the new crontab to a FILE with LF endings, print it and count its lines, diff it against crontab -l, and only then install it with crontab <file> - never through a pipe from a PowerShell-written script.
