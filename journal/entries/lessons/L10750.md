**L10750 · A build that degrades quietly and a build that works both exit 0: name the cause, then read the artifact**

A build that fails and a build that silently produces the wrong artifact look the same if you only
read the exit code. Measured twice in one session, 2026-10-20, on phone-and-tech-full:

`cd frontend && pnpm build` exits 0 either way. With `VITE_API_URL` unset it bakes an API origin that
is not there; the bundle throws `FATAL: VITE_API_URL is not set` at boot and paints nothing. Before
this session that only mattered to a human looking at a blank page. Now that the build also captures
each public page's rendered text into its document, the same unset variable made every one of 14
documents degrade to head-only -- 0 characters of body -- while the build said `wrote 14 documents`
and exited 0. I ran it, saw the numbers, and rebuilt twice before looking at the cause.

Two rules from it:
1. When a build has a "degrade quietly" path, the message must name the cause it found, not the
 symptom it saw. The generator now prints "the body capture failed because VITE_API_URL is not set"
 plus the fix (`pnpm build:frontend:static`, which needs no deploy variable) instead of "the capture
 failed". A warning that cannot say why is a warning somebody will misread as a different bug.
2. Verify the artifact, not the exit code. The check that settles this is reading the emitted file:
 `bodyBytes=11,459 visibleTextChars=2,051` on `dist/screen-repair/index.html`, and the text reads
 "Screen Repair in Lakewood, NJ — Fast Screen Repair — Cracked or broken screen?". A generator
 summary line is a claim about what it intended.

Corollary worth keeping: the deploy path (`scripts/build-tools/build-frontend.mjs`) is the one that
must FAIL on this, and it does -- it re-runs the generator's `--check` on the emitted files. A plain
`pnpm build` warns. That asymmetry is deliberate: a deploy must never ship a crawler-blind document,
and a developer build must never be blocked by a missing deploy variable.
