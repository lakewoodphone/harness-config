**L3424b · The owner channel had three gates, and my first version reported success through all of them**

WRITTEN 2026-10-13 on secratary, completing the owner-attention pipeline.

`send_owner_update()` in `personal-secretary-mvp` does NOT mean "sent". It
returns a dict, and the message passes through three independent gates before
anything leaves the box:

1. **the interpreter** - `send_owner_update` imports `app.sms_service`, which
 imports `twilio`. The system `/usr/bin/python3` on secratary has no twilio.
 The app's own venv does. A systemd unit that runs the pipeline with the
 system interpreter can build a perfect digest and never deliver it.
2. **the urgency threshold** - `get_owner_sms_min_urgency(settings)` reads
 `owner_sms_min_urgency`, and on this box it is **`urgent`**, not `normal`.
 A `normal` digest is refused `below_owner_sms_threshold`.
3. **the length limit** - one owner text is **320 characters**
 (`app/owner_text.py`). A 1201-character digest is refused `too_long`.

Then a fourth, which is not a gate but a trap: the rate floor. Two sends inside
a few seconds earns `rate_floor` on the second one.

EVERY refusal is silent to a naive caller. My first version did:

 send_owner_update(body, reason="owner_attention_digest")
 print(f"sent {len(body)} chars to {dest}")

and printed `sent 1201 chars to +18483897895` while the row sat in
`owner_message_queue` with status `held` and `sms_log` had no new row at all.
That is a FALSE DELIVERY REPORT, and it is the same defect class this estate
has paid for before - a stale database believed, a health check that answered
from the wrong place. The log said delivery; three tables disagreed.

THE RULE. A caller that sends must read the RESULT DICT and report what it
says: `ok` with no `held`/`suppressed` is sent; `held` is held and the caller
must say so and name the queue id; anything else is an error. Never print
"sent" from the fact that the call returned. Verified after the fix:

 HELD, NOT SENT to +18483897895: owner surface refused it
 (reason=below_owner_sms_threshold, urgency=normal, queue_id=2577)

then, once the body was cut to 320 chars and the urgency raised to match the
configured threshold:

 SENT 237 chars to +18483897895 (urgency=urgent)
 sms_log id 4106 | to_number +18483897895 | status queued

Also: a unit whose script exits non-zero on a *healthy* refusal gets marked
failed by systemd and the timer looks broken. `SuccessExitStatus=0 2 3` is the
fix, with the exit codes documented in the unit.
