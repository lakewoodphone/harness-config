**L1903 · git refuses a fast-forward when untracked files collide with incoming tracked paths, even byte-identical**

MEASURED 2026-09-17 14:0xZ, ZABZ-YOGA, a scratch repo in %TEMP% (created, exercised and deleted in one command).

 untracked sub/f.txt whose content is IDENTICAL to the blob the ff-merge would write:
 error: The following untracked working tree files would be overwritten by merge: sub/f.txt
 Please move or remove them before you merge. Aborting exit 1
 same case with DIFFERING content: the same error, the same exit 1.

So "the content is the same, git will be fine" is FALSE. This is a SECOND, independent wall from
"origin/master holds older blobs" (docs/mesh/99 §3.2) -- and it is the one that actually blocks a machine
whose package directory is untracked end to end.

READ-ONLY DETECTOR, no state change: git read-tree -n -u -m HEAD <tip>
 -> exit 128, names one offending path, writes nothing. Run it before deciding a sync is safe.

THE REPAIR, in this order, and it is reversible:
 1. collision set = (git ls-files -o --exclude-standard) INTERSECT (git ls-tree -r --name-only <tip>)
 2. per path: disk blob vs incoming blob (git hash-object / git rev-parse) -> IDENTICAL or DIFFERS
 3. copy every collision path byte for byte OUTSIDE the repo, then RE-HASH the copies and compare to the
 originals (a copy nobody verified is not a backup)
 4. remove the collision files -- never one the incoming commit does not track
 5. git merge --ff-only <the SHA you captured>, not the ref, because the ref moves under live pushes
 6. if HEAD != tip afterwards: restore every file from the copies and exit non-zero
 7. re-read the blobs, and diff each DIFFERS file against its preserved copy to PROVE which revision is newer

backup verified 0 errors, merge exit 0, all 28 written from the commit. Evidence: docs/mesh/103 §2.
