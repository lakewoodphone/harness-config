**Hand a document over as a FILE, not as a laptop-local URL - the server died invisibly and the promise outlived it**

2026-09-30, ZABZ-TECH. Asked to "pull up" the Chol Hamoed record, I started `python -m http.server 8791 --directory ~/code/home/trips` as a background job and gave the owner the address. The job was later reaped with exit code 4294967295 (-1, a kill, not a crash). Its entire access log was ONE line: my own verification GET at 10:51. He never opened it.

The failure is not the dead process, it is the shape of the deliverable. A background job on a laptop:
- dies when the job is reaped or the machine sleeps, silently, with no listener;
- is reachable only from that one host;
- and leaves an address in the owner's head that returns nothing, which is the same class as every other reading that cannot distinguish two states - a dead server and a live one look identical from the URL alone.

**RULE: when the deliverable is a document, deliver the FILE** - write it into the repo, commit and push it to both remotes, and use `present` so it is clickable. Offer a served page only when the owner asks for one, and then say plainly that it lives only as long as the job does. The `home` repo already carries `trips/chol-hamoed-5787-trip-options.html`, so the browsable page existed as a file the whole time and needed no server.

Tags: deliverables, servers, silent-failure.
