**L3925 · A reminder that reports the wrong number is worse than none: the middle coverage band**

**L · A reminder that reports the wrong number is worse than no reminder — and the middle coverage band is where that happens.**

Owner request, 2026-10-14: *"shoot me a text when you get an email about autopay, maybe 2 days before
it's due."* Built: `harness-config/scripts/card-due-watch.py`, daily 13:00 UTC on the authority via
`cron-wrap.sh card-due-watch`, with `scripts/test_card_due_watch.py` and
`settings/finance/card-funding-accounts.tsv`. Recorded run `2026-10-14T14:04:48Z card-due-watch 0 34`.

### THE NEAR-MISS THAT MATTERS, CAUGHT IN A REPLAY

The first version compared the balance to the **minimum** and printed, for card `9650`:

 It draws from Chase checking ...9730 ... which held 72.47 ...
 That covers the minimum.

72.47 does beat the 40.00 minimum. **The autopay on that card took 2,380.06 and emptied the account.**
A reminder that says "covered" while the account is about to be overdrawn is worse than no reminder,
because it is a green light built on the wrong number — the same class of failure as reporting a crisis
that does not exist.

**The generalisable rule: when one quantity has a floor and a ceiling, never test against the floor and
call it coverage.** The fix is three bands with the middle one carrying the warning:

| band | condition | what it says |
|---|---|---|
| covered | balance >= statement | covered |
| **at risk** | minimum <= balance < statement | covers the minimum ONLY; an autopay set to the statement or interest-saving balance will bounce |
| short | balance < minimum | not enough even for the minimum |

The middle band is the one that bit him, and it is the one a naive implementation passes.

### TWO SOURCE TRAPS, BOTH HIT FOR REAL IN ONE RUN

1. **`email_catalog` cannot answer a monthly question.** It holds **732 rows and every `internal_ts` is
 NULL** — so a query bounded by that column returns nothing, which reads as "no statements" when it
 means "no timestamps". Unfiltered it is still only what the last sync upserted (~222 messages), so
 the August/September statements carrying the due dates had aged out. **Gmail itself, through the
 app's own `/gmail/search?q=&all_accounts=true`, is the complete source** and the app already holds
 the credentials.
2. **`email_catalog` is not in the app's `secretary.db`** — it lives only in the 28 GB
 `/root/authority.db`. Pointing at the app DB fails with *no such table*, which is a clean failure;
 pointing at the right DB with the wrong column is a silent one.

### FUNDING ACCOUNTS ARE EARNED, NEVER GUESSED

The issuer's "automatic payment is scheduled" email says only *"from your account"* — it never names it.
So the mapping is maintained separately and a row is added only when a bank debit and a card credit
match **amount-for-amount, opposite signs, same originator `CO ID:XXXXX39224`**:

- `9650` → `personal-checking` (9730)
- `3929`, `5578`, `7542` → `lpt-boa-checking` (7930) — five independent matches

A card with no row is **reported as unmapped**. A wrong funding account is worse than no reminder.

### A COUNT IN A TEST IS NOT AN INVARIANT

The first test asserted `len(funding_map) == 2`. Adding two cards broke it, which teaches the next reader
to edit the number rather than read the failure. It now asserts the substantive thing: a card with no
evidence is **absent**, not defaulted to something plausible.

### ALSO: `textsend.py notify` IS THE SANCTIONED WAY TO TEXT HIM

`textsend.py`'s own header says the owner is *not* texted by the send path (kill switch, after the CEO
sent 28+ "URGENT" texts) and that owner notifications go through the app. The `notify` subcommand POSTs
`/tools/notify-owner` and is gated: a body that reads like a self-test is **refused**, a real
human-addressed body passes. Dry run is the default; `--send` is required. Never build a second path to
his phone.
