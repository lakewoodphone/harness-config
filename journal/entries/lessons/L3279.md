**L3279 · A guard is disabled by the fix that satisfies it; a half-migrated id/name pair passes every guard; and the four-call recipe for proving a preset mounts**

**L(new) · A guard can be disabled by the very fix that satisfies it, and a HALF-migrated version-coupled pair is invisible because every guard checks the package NAME and none checks the row id**

**Measured 2026-10-05 on ZABZ-TECH (engine 0.2.0-rc.2) and ZABZ-YOGA.**

**1. An anchor repair silently disabled the version-coupled guard.** `profiles/node_modules` in
`$DSH_HOME` is the MODULE ANCHOR composition rows resolve against. On ZABZ-TECH it had been a stale real
tree of the OLD 0.1.5 packages while the pin and the running engine were already 0.2.0-rc.2; it was
repaired (H3161) by renaming the stale tree aside and creating a **junction** to
`dsh-update\vendor\prefix\0.2.0-rc.2\node_modules`. The engine is fine with that. Python is not:
`check-version-coupled-config.py` now dies with `OSError: [WinError 448] The path cannot be traversed
because it contains an untrusted mount point: 'C:\Users\ezabz\.dsh\profiles\node_modules\@deepseek-ai'`,
so `sync.py` reports `presets: SKIPPED ... the version check did NOT run` and `profiles:` likewise —
**both version-coupled steps stop being delivered, from a change that made the machine MORE correct.**
On ZABZ-YOGA the same anchor is a real directory holding one junction per package, which is the shape
the guard's own comment documents (`check-version-coupled-config.py:135-142`). Two rules: a fix to a
lookup path must be re-measured through every consumer of that path, not just the engine; and a
junction is traversable by Node and not by Python, so the two halves of this harness do not agree about
what a usable path is. Note the guard DID report this — the `skipped` field and the `SKIPPED (not
applied)` detail added on 2026-10-04 (`L3257` rule 2) are what made it visible instead of a silent
`clean`. That fix has now paid for itself once.

**2. The row id and the package name are a PAIR, and no guard checks the pair.** A migration commit
(`92f933f`, "finish the 0.1.7-line migration") rewrote the package string `dsh-workflow-worker-thread`
-> `dsh-workflow-ptc` everywhere it appeared and left `- id: workflow-worker-thread` untouched, because
the row id has no `dsh-` prefix to match on. Result, in all three presets on both the repo and the live
home: `- id: workflow-worker-thread` / `name: '@deepseek-ai/dsh-workflow-ptc'`. It MOUNTS, so nothing
failed, nothing was logged, and both guards passed: `preset-package-gate.ps1` checks that every
`@deepseek-ai` NAME resolves, `switch-engine.ps1`'s precondition 2 checks that the staged home names
`@deepseek-ai/dsh-workflow-ptc` as a QUOTED row and does not name the removed package. Neither looks at
the row id, and the id is what decides whether our row overrides the layer the engine already mounts or
sits beside it as a second instance. **Guard the pair, not the name**: assert the row's `id` and its
`name` together against the installed engine's own mounted rows, and take both verbatim from
`dsh-base/cordis.patch.yml` / `dsh-web-app/presets/cordis.patch.yml` rather than from the migration
notes. Fixed on ZABZ-TECH as `6d686e4`.

**3. "Does a preset actually mount?" is four HTTP calls, and it should never again be left to a browser
or a human.** `POST /api/session/create` is the picker's own call and it answers `ok:true/false` in the
body (never in the status — `L3058`). To make the call the token has to be exchanged for the cookie,
and neither step is obvious: the launch token for the CURRENT engine is the newest
`~/.dsh/multi-window/logs/3099-*.log` (the plain `3099.log` is stale — it held the PREVIOUS process's
token and produced a 401), the exchange is `GET /?token=<tok>` which answers `303` with an
authority-bound `dsh-auth-*` cookie, the RPC channel is `POST /api/<method>` (not `/api`, and not a
WebSocket) with `content-type: application/json`, and the body is the client's envelope
`{"type":"client-request","rpcId":..,"method":"session/create","payload":{"args":{"request":{"cwd":..,"agentPreset":..}}}}`.
`POST /api` returns a bare `404 not found` and unauthenticated calls return `401 unauthorized`, so a
wrong endpoint looks like a wrong credential. Any session created this way must be MOVED out of the
store afterwards, never left in his session list, and the sentinel cwd
(`C:\__dsh_verify_does_not_exist__`) is what makes it safe to remove exactly those.
