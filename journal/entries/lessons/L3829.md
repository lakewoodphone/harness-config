**L3829 · collected 0.00 is not non-payment - a Stripe Terminal payment lands unlinked, and the Senzer 50 was paid 72 seconds before the call that said so**

**Measured 2026-10-15 on WO26100812736 (Senzer), ZABZ-TECH.** This corrects **H3631**, written the same
session, which says nothing had been paid on that order.

The owner said four words — *they already paid 50* — after I had printed a label reading NOT PAID and written two
production notes saying nothing had been paid. Everything that claim rested on was one reading: `lpt ticket`
printing `collected USD 0.00`. That figure is not payment truth.

**What was actually there.** `payment_transactions` id **3382**: amount **53.31** (= 50 × 1.06625, the shop's own
tax gross-up), status SUCCEEDED, metadata `{transactionType: terminal, staffNote: diagnosis, readerId tmr_…}`,
`stripePaymentIntentId pi_3UQqTxLnlgYj1gmT0Ee9C8jD`, created 2026-10-15 15:22:17 UTC — with **`orderId` NULL and
`customerId` NULL**. A Dialpad call **72 seconds later** (6360551071195136, 2026-10-15 15:23:29 UTC, 28.9 s) has
the customer saying he gave the 50 for the computer that morning. The row now links to order 3015 by
`lpt-link-payment` and the order reads `collected 53.31`.

**The rule — and it is NOT new.** It is in `lpt-ops/docs/writes.md`, which I had read earlier in the same session:
**`collected 0.00` is not evidence of non-payment; it is evidence that no LINKED row exists.** A Stripe Terminal
payment lands unattached, and this shop takes diagnosis fees at the terminal. So *before writing anywhere that a
customer has not paid*, query `payment_transactions` for an unlinked row of the right amount and date
(`orderId is null`, the date window, and the amount **grossed up** — 50 pre-tax lands as 53.31 on this shop's
6.625 % rate). An empty money figure is a refusal, not health.

**Why the failure was expensive.** The wrong claim reached two production notes (4098, 4109), a **printed label**
the counter reads, and every message of the session. Repairing it took a correction note (4110), a money write
(`lpt-link-payment`), a second label, and four file edits. The customer-facing cost is the one that matters: a
document at the counter saying NOT PAID, with the money already in the till.

**Also measured, same session — a tool defect worth knowing.** `python bin/lpt-link-payment` run on Windows exits
**1** with `cannot read a DSN from /home/zabz/personal-secretary-mvp\.env` — it builds a Windows path for a POSIX
path. Its documented home is the office box, where it lives at `/home/zabz/bin/lpt-link-payment`:
`ssh secratary-ts 'python3 ~/bin/lpt-link-payment --order WO… --payment-id N [--apply]'`. Not fixed in the checkout.

**Correction protocol that worked, and is worth reusing.** The two wrong production notes were left standing and a
new note cites them by id; the case file's dated sections were annotated in place with a forward-pointing
`CORRECTED` line rather than rewritten; and only front-matter **state** (`price: 50`, `payment_state: paid`) was
rewritten, because state describes now.
