**L1974 · assert the body, not the status: the same /health URL returned ok=true and ok=false under HTTP 200 four minutes apart**

**Rule.** A liveness check that asserts only the HTTP status cannot fail. Assert the body,
because the same URL can carry opposite verdicts under the same 200.

**Evidence, measured 2026-09-18 on `secratary.tail93e6e6.ts.net:8002/health`.** At 02:06Z it
returned HTTP 200 with `ok:true` and `database.ok:true`. At 02:20Z and again at 02:21Z - on
three distinct network paths (tailnet, api.abletelsolutions.com, ai.abletelsolutions.com) -
it returned HTTP 200 with `ok:false` and
`database.error:"db check timed out (lock contention); api still responsive"`. At 02:24Z it
was `ok:true` again. The status was 200 throughout, so a status-only check called all four
observations green while the API was telling anyone who read the body that its database had
not answered `SELECT 1`. An independent read-only query through the secretary MCP server
(`SELECT COUNT(*) FROM tasks`) answered immediately during the failing window
(25,908 tasks / 20,130 memories), so this was genuine write contention inside the 2s bound,
not a dead or hard-locked database - and it is exactly the transient a port check and a
`systemctl is-active` both sleep through.

**Why it matters here specifically.** This is the P41 failure mode in its purest form: green
wherever anyone was looking, degraded where the service itself said so. The first scheduled
run of a probe is the only thing that will ever see a four-minute window like this one.
`app/main.py:1457-1463` deliberately returns a degraded 200 rather than hanging, which is
correct for the watchdog and invisible to every check that does not read the body.
