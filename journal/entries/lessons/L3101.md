**L3101 · Confirmed with the package own transport: sh -s stdin delivery hangs from the office desktop, and it is not the client version**

**L-new · Confirmed: the `sh -s` stdin delivery hangs from the office desktop, and it is not the client version**

MEASURED 2026-09-29, closing the hypothesis filed as pain `P2670` in the same session. The load lane
reported it with a hand-rolled probe and said the cause was unestablished; this run used the package's
**own** `createSshTransport` and `buildPosixScript`, so the ambiguity in that probe is gone.

**The measurement.** From `zabz-tech`, dispatching a POSIX child to two different Linux targets:

| target | framed | host | ms | stderr |
|---|---|---|---|---|
| `zabz-tech-linux` | false | undefined | **300 017** (the full bound) | (empty) |
| `secratary` | false | undefined | **300 031** (the full bound) | (empty) |

Both hung to the timeout and returned nothing at all. From ZABZ-YOGA, in the same session and on the
fixed code, the identical shape returned a real turn from both of the same targets — `zabz-tech-linux`
exit 0 in 5176 ms, `secratary` exit 0 in 5080 ms.

**The version hypothesis is refuted.** Both Windows machines run `OpenSSH_for_Windows_10.0p2,
Win32-OpenSSH-GitHub, LibreSSL 4.2.0`, and both invoke `C:/Program Files/OpenSSH/ssh.exe`. So the
difference is not the client build. It is also not the target: the same two targets answer fine from the
other client.

**What the shape is.** For a POSIX target `remoteArgv` returns `['sh', '-s']` and the transport spawns
ssh with `stdio: ['pipe', <out file fd>, <err file fd>]`, then `child.stdin.end(script)`. Empty stderr
with a full-length hang is what it looks like when the remote `sh -s` never sees EOF on its stdin —
consistent with the client not closing the pipe it was handed, on that machine only.

**What would fix it, and why it is the right shape.** Remove stdin from the path entirely: deliver the
POSIX program the way the Windows path already delivers its own — as an encoded argv that the target
decodes, or as a file written to the target and then executed. A base64 argument decoded remotely
(`base64 -d | sh`) reintroduces no quoting hazard because base64 contains nothing a shell reads, **but it
does reintroduce an argv ceiling**, so a file on the target is the more robust of the two and is the
change to prefer. Until that lands, a fan-out *from the office desktop* to the three POSIX nodes of this
mesh is dead, which is half the mesh seen from the machine with the most headroom.

**The durable rule.** A transport that is verified from ONE machine is verified from one machine.
`docs/mesh/70-remote-fanout-proof.md` and every proof since ran from ZABZ-YOGA, and this defect lived
behind that single vantage point. Where a mesh has five nodes and four clients, a proof names its client.
