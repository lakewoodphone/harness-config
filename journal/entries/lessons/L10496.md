**L10496 · The running engine owns its settings document and rewrites it from memory: a config fix applied under a live engine is reverted, and that is why two correct fixes did not reach the owner's screen**

MEASURED 2026-10-19 on ZABZ-TECH. This is the thing that made two correct fixes vanish and made me tell the owner
twice that something was fixed when his machine still failed. It is not a subtle one and it should have been
obvious: **the running DSH engine OWNS its settings document and rewrites it from memory.**

EVIDENCE.
- 18:49Z: I corrected `~/.dsh/profiles/web/cordis.patch.yml` (ctx.webRuntime -> ctx.webStartup) and verified the
 edit by reading the file back. At 19:02Z the same file carried `ctx.webRuntime` again, with mtime 19:02:22 --
 the engines were running the whole time.
- 19:00Z: I regenerated the preset rows into that same file (`make-preset-rows --install --install-target`) and
 the tool PROVED "outside the block: byte-identical". By 19:20Z the file carried `{{cwd}}` three times again.
- The same directory holds `cordis.patch.yml.bak-<timestamp>` siblings written every 15-60 minutes all day: that
 is the writer. `profiles/web/package.json` declares `"patchReload": "live"`, and `dsh-config-editor`'s
 `documentPath` IS this file (FINDINGS.md round 5 measured exactly that). So the file is a live document with
 two owners, and the engine's in-memory copy wins.
- Proof of the fix once the order was right: engines stopped -> edit -> `make-preset-rows --install` ->
 `--dump-config` with the 0.2.1 binary reported `rows=421 ctx.webRuntime=0 {{cwd}}=0` -> start one engine ->
 3099 up, pid 51028, 0.2.1-rc.2, live patch `webRuntime(code)=0 webStartup(code)=2 cwd-tokens=0`, and the owner
 confirmed the GUI working.

THE RULE. Any change to a file the engine owns (the profile patch, settings under it, and the preset rows spliced
into it) must be made with **every engine on that machine stopped**, and followed by a start. Editing it under a
running engine is not "a race you might lose": the engine rewrites the whole document on its own cadence, so the
edit is simply gone, and the file's mtime afterwards is the engine's, not yours. Verify by reading the file back
with NO engine running, then start, then read it again.

WHAT I DID WRONG, so the next session does not repeat it: I treated "the file says webStartup now" as the fix,
twice, without checking whether a process could overwrite it -- on a machine where I had just restarted the
engine twice. And I restarted the engine BEFORE finishing the config edits, which built the very window that
reverted them. Order matters: stop -> edit -> verify on disk -> compose-check -> start -> verify again.

HOW THIS SHOWS UP TO THE OWNER: "This turn failed: unknown prompt variable {{cwd}}", or a boot error
`cannot get property "webRuntime" without inject`, on a machine where the file on disk looks correct.
If the file looks correct and the error persists, the running engine is holding an older document: stop it,
re-read the file, and start it again.
