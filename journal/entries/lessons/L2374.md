## 0.1.7-rc.1 adds a v3-to-v4 session-format codec and NO reverse codec: promoting it is a one-way door on 1,095 logs

MEASURED 2026-09-24 (ZABZ-TECH), by diffing the installed package name sets of `0.1.5-rc.1` (240
packages) against `0.1.7-rc.1` (277 packages):

- **New in 0.1.7-rc.1: `@deepseek-ai/dsh-session-format-v3-to-v4`.**
- No v4-to-v3 codec appears in either the added or the removed list.
- The live home holds **1,095** session files, and **all 1,095 are `session.v3.jsonl.zstd`**.
- `@deepseek-ai/dsh-session-format-catalog` declares `currentVersion: 3` on both lines.

CONSEQUENCE: promoting `0.1.7-rc.1` upgrades the session log format as logs are written after the
upgrade. Rolling back to a 0.1.5-line engine then leaves it **unable to read the history written in
the meantime**. It is not a reason to refuse, and upstream is plainly moving to v4 — but it is a
deliberate decision rather than a side effect, and it is the one part of this upgrade that cannot be
undone by `rollback`.

WHAT TO DO: take a copy of the session store before the first boot on the new format, so the
irreversible step is bounded by something a human can restore. A gate that reads `currentVersion` and
the codec list from both installs and refuses (or loudly flags) a candidate whose writer is newer is
specified as G8 in `harness-config/dsh-update/SPEC.md` and is **not yet implemented** — until it is,
this fact has to be checked by hand, and this entry is how.

This is the general shape to remember: **the riskiest part of a harness upgrade is not the code, it
is the format the code writes to disk.** `SPEC.md` C8 predicted it; the package diff is what confirmed
it.
