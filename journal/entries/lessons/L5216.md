**L5216 · A handoff line saying pushed and remote-verified can expire: the default branch was rewritten under it (lpt-hub, Pantoja)**

**L5030 · "Pushed and remote-verified" in a handoff is a claim about a moment, not about now. Re-read the ref before you trust one.**

Measured 2026-10-15, when the owner said *"horacio pantoja 7328907527 pull it up"* and I read the
record instead of the answer I expected.

Handoff **H5064** (2026-10-15 15:48 UTC) said, in its own words, that the Pantoja case file, its
sync record, seven evidence files and the bench plan were *"Committed and pushed to lpt-hub main"*
and that the remote had been *"verified with `git ls-remote origin main` -> `f2eca71f7..647299e85`"*.

That was true when it was written. Reading it four hours later, **none of those files existed on
`origin/main` and none existed in any working tree on any machine.** The case the shop had just
intaken was, at read time, invisible to every other machine and to the `lpt_hub_sync` corpus
reader that the secretary service reads its customer-case corpus from.

**What the measurement was, and it is three commands:**

```
ssh secratary-ts 'cd /home/zabz/repos/lpt-hub && git fetch origin --quiet && \
 git merge-base main origin/main'
 -> f2eca71f7 # the branch point, NOT HEAD
ssh secratary-ts '... && git merge-base --is-ancestor 647299e85 origin/main'
 -> NO
ssh secratary-ts '... && git ls-tree -r --name-only origin/main | grep -i antoja'
 -> (nothing)
```

**The mechanism, and it is the generalisable part.** The Pantoja commit was created at 15:45:29Z
with parent `f2eca71f7`. Ten minutes later, at 15:55:33Z, `5cd20bfe1 "security: redact a live
BitLocker recovery key from the default branch"` was committed **on top of the same parent** — a
sibling, not a child. Both were then pushed to `main`. Whichever landed second moved the default
branch non-fast-forward and **orphaned the other**; the queue that day happened to resolve in the
redaction's favour. `git merge-base main origin/main` returning the *old branch point* rather than
either HEAD is the signature, and it is the one reading that separates "behind the remote" from
"the remote no longer contains my work" — `git log` and `git status` cannot tell you, because a
local `main` that still contains the commit looks perfectly healthy.

**The rule.** A "pushed" line in a handoff (or in a commit, or in a note) is a fact about the
instant it was written. Before relying on one — and always before telling the owner a case is
published — run `git merge-base main origin/main` and `git merge-base --is-ancestor <sha>
origin/main`. `--is-ancestor` exiting non-zero is a real negative and it is cheap.

**Why this class is worse than a plain lost push.** The record *said* the work was safe, so no
later session had a reason to look. Four sessions' worth of work can sit in a repository's object
store, reachable from a divergent local branch, with every document agreeing that it is on main.
The object store is not the risk; the confident sentence is.

**Resolution (2026-10-15 19:54 UTC).** Re-landed with `git cherry-pick -x 647299e85` onto
`eaf1b9d42` in a temporary worktree off `origin/main` — no force-push, no rebase over another
session's work, content unchanged. `origin/main` `eaf1b9d42..ce367807f`, and the eleven Pantoja
paths verified present on `origin/main` from a second machine afterwards. The commit message now
carries the orphaning and why, so the next reader sees it without this entry.

**Not fixed by that:** the default branch can still be rewritten under a concurrent push. A
redaction that rewrites a shared default branch is a fleet-wide event and needs a push freeze or
a re-fetch-and-re-land afterwards, not a silent force-push. That is open.
