**L510 · A local commit silently blinds a machine: autosync is fast-forward-only**

A machine that makes a local commit stops receiving configuration, silently.

scripts/autosync.ps1 is deliberately fast-forward-only and refuses to merge or rebase ("a divergence is reported, not resolved by guesswork"; "stashes, resets, cleans or force-pushes - this business has lost data twice"). So the moment ANY machine holds a commit the remote does not have, `pull --ff-only` refuses, the run ends attention/exit 1, and that machine keeps its OLD settings.yaml, OLD presets and OLD launcher - indefinitely, because nothing alerts anyone (the P40/P55 gap).

MEASURED TWICE IN ONE HOUR on 2026-09-14:
- ZABZ-TECH was `master...origin/master [ahead 1, behind 11]` with LastTaskResult 1. Its stray commit was journal-only (275ff32, +56 lines of handoff). It would have missed every future config change.
- ZABZ-YOGA became `[ahead 2, behind 2]` while another session committed two deepseek-proxy commits locally. A machine that cannot fast-forward also cannot receive a failover-watch model flip, so this is not cosmetic: the watch would move the fleet and the blind machine would stay on the dead model.

THE REPAIR THAT WORKED, twice, without losing anything:
1. `git branch pre-reconcile-<host>-<date>` - a reversible snapshot before touching history.
2. Commit pending work first (`git add journal && git commit -m ...`) so it is inside the rebase.
3. `git fetch origin`, then `git rebase origin/master` (add `--autostash` when another session holds unstaged files; it reports "Created autostash" and "Applied autostash").
4. Resolve conflicts ONLY in GENERATED files by taking the upstream side: journal/index/entries.tsv and journal/state/owner-questions.md are regenerated by the journal tool, so hand-merging them is pointless and risky. The append-only log shards auto-merged themselves.
5. `git push origin master`, then trigger the machine's sync task and require LastTaskResult 0 and `master...origin/master` with no ahead/behind.

GOTCHAS: `git rebase --continue` opens an editor and hangs over ssh - use `git -c core.editor=true rebase --continue`. And a machine whose journal tools are mid-migration by another session cannot write the journal at all: this session hit `KeyError: 'legacy_id'` and 463 check errors purely because journal/tools/journal.py and journal/index/* were uncommitted work in progress in the same working tree. Write from a clean checkout instead.

WHAT WOULD FIX IT SYSTEMICALLY: autosync should surface divergence into a channel that actually reaches the owner, and should preserve local commits automatically (push them to a side branch, or attempt a rebase with the generated-file rule built in) instead of leaving the machine blind. Until then, `git status --short --branch` on every machine is part of any audit, not an optional check.
