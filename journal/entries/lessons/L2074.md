# Dialpad's public API cannot write `allow_ai_training` — the admin UI's own internal endpoint can

Measured 2026-09-20 on ZABZ-YOGA + the authority. The task was to switch off company-level AI training
on Lakewood Phone & Tech's Dialpad account. Three things were tried, in order, and only the third works.

## 1. The read is a public endpoint, and it is the cheap proof

```
GET https://dialpad.com/api/v2/company (Authorization: Bearer <DIALPAD_API_KEY>)
-> 200 {"id": "5272393147203584", "name": "Lakewood Phone & Tech", "account_type": "pro",
 "settings": {"allow_ai_training": true, "has_callai": true}}
```
Key: `DIALPAD_API_KEY` in `~/personal-secretary-mvp/.env` on the authority. This endpoint is the
read-back that proves any change, so always take it before and after.

## 2. The obvious write is a trap: 200 OK and nothing happens

The documented endpoint is `PUT /api/v2/company/settings`, and its **only** documented parameter is
`has_callai` ("If Call AI setting should be enabled/disabled"). Passing the field we actually wanted:

```
PUT https://dialpad.com/api/v2/company/settings?allow_ai_training=false -> HTTP 200,
 response body still {"allow_ai_training": true, "has_callai": true}
```
**A 200 with the value unchanged.** The parameter is accepted syntactically and ignored semantically.
`PATCH /api/v2/company` is a flat `404 No endpoint found`.

**And the near-miss worth recording:** sending `has_callai=false` instead would have "worked" — it
would have disabled Dialpad AI itself (transcription, recaps), a much larger change than the one asked
for, and it would have looked like success. The documented parameter was the wrong one; taking the
documented path on faith would have broken a feature the shop runs on while reporting the privacy fix.

## 3. What actually works: the admin UI's internal endpoint, through the session we already hold

The company already drives an authenticated Dialpad admin Chrome profile for the webcrawler
(`<repo>/data/dialpad/chrome_profile`, see `app/services/dialpad_webcrawler.py`). Opening
`https://dialpad.com/companyaisettings` in that profile shows the real control — checkbox
**"Allow Dialpad AI features to improve based on my conversations"** (`input[data-qa="toggle-ai-learning"]`)
under Company Settings -> AI Settings -> General AI Settings, already CHECKED. Clicking it saves with
no Save button, by firing its own call:

```
PUT https://dialpad.com/api/ai_settings/company body: {"allow_ai_training": false}
```
Read back: `allow_ai_training: false`, `has_callai: true`. One write request, one key in the payload.
The switch above it, "Allow AI to be used company-wide", stayed ON.

## The durable rules

1. **Before telling the owner a setting cannot be changed, check whether the vendor's own UI changes it
 — and how.** The UI's private endpoint is the ground truth for what is writable; the public API
 reflects only what the vendor chose to expose. Here the public API was the *only* documented path and
 it silently no-ops.
2. **A 200 is not a change.** Re-read the value after every write, from an independent surface, and
 compare. This is the same failure as "configured is not working", one layer down.
3. **Verify the field's semantics from the vendor's own documentation before writing it**, and prefer
 the company level when the doc says lower levels inherit: company-level OFF is the only level below
 which nobody can re-enable it.
4. **A browser session the company already owns is infrastructure.** The crawler's logged-in profile did
 in one click what the API could not do at all — and it is the reason this did not need the owner's
 login.
5. Unverified, left open: a second, near-identically-worded checkbox exists in the DOM but is
 `visibility:hidden`, 0x0, non-rendered, and still `true`. It was never clicked, so whether it is a
 separate persisted setting is **unknown**.
