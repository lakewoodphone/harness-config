**L12262 · E4610 615196187: WRITE_SECURE_SETTINGS missing in techmode was the real blocker for PTT+ disable**

FIXED 2026-10-22, handset returned to the customer the same day.

Symptom the owner reported: pressing the side/PTT button ran Verizon PTT+ talk-to-text instead of Voice Access. The filter was supposed to disable PTT+ and had not.

ROOT CAUSE (two layers, both measured)
1. com.android.cts.techmode (Tech Mode 2.0.0, vc20) requests android.permission.WRITE_SECURE_SETTINGS but was installed WITHOUT it on 2026-03-13. Every unlock died on the first write:
 E TechModeManager: Unable to write global setting adb_enabled: Permission denial: writing to settings requires:android.permission.WRITE_SECURE_SETTINGS
 at TechModeManager.enableTechnicianMode(TechModeManager.java:146)
 So Tech Mode could never enable ADB, and the phone could not be worked on in tech mode at all.
2. With that unfixed, `pm disable-user --user 0 com.verizon.pushtotalkplus` was rejected with
 SecurityException: Shell cannot change component state for com.verizon.pushtotalkplus/null to 3
 and the package self-healed (dumpsys: enabled=1, lastDisabledCaller: android).

WHAT ACTUALLY FIXED IT, IN THIS ORDER
 adb shell pm grant --user 0 com.android.cts.techmode android.permission.WRITE_SECURE_SETTINGS
 (owner then entered the Tech Mode code 092246 on the handset and it accepted)
 adb shell pm disable-user --user 0 com.verizon.pushtotalkplus
 adb shell pm disable-user --user 0 com.verizon.verifypttapitestpreload

VERIFIED AFTER
 Package com.verizon.pushtotalkplus new state: disabled-user
 com.verizon.pushtotalkplus enabled=3 lastDisabledCaller=shell:2000
 com.verizon.verifypttapitestpreload enabled=3 lastDisabledCaller=shell:2000
 ptt_app_setup=1 ptt_application_enabled=1
Owner then pressed the physical side button and confirmed it works. That press is the only valid proof: injected `input keyevent 285` only produces WindowManager "Send ptt key for ptt application whenever." and does not exercise the app-facing relay, and `am broadcast -a com.kodiak.intent.action.PTT_BUTTON` is refused for uid 2000 (protected broadcast), so no shell test of the relay exists.

THE BLOCKER ORDER IS THE WHOLE LESSON
Granting WRITE_SECURE_SETTINGS is what made both the Tech Mode unlock AND the PTT+ disable possible. Any handset whose techmode lacks that permission cannot be filtered reliably afterwards, and the symptom looks like a PTT/package-protection problem, not a permission problem. Check `dumpsys package com.android.cts.techmode | grep WRITE_SECURE_SETTINGS` FIRST on any handset that will not cooperate.

LEFT BROKEN ON THIS UNIT WHEN IT WENT BACK TO THE CUSTOMER (not fixed, no longer reachable)
- com.android.webview is enabled=3 DISABLED_USER (lastDisabledCaller shell:2000). cli/configs/bloatware/full.yaml lists it under preserve_packages because SmartList needs it. The March filter on this unit predates that rule, so SmartList/browser behaviour on that phone is suspect.
- All LP&T apps are the 2026-03-13 14:56-14:58 build. com.android.cts.keysminimal is 4.0.0 and declares NO com.kodiak.intent.action.PTT_BUTTON receiver (only BootCompletedReceiver + MinimalService), unlike the May 2026 builds. It worked once PTT+ was gone only because the platform PTT route relays elsewhere, but that build should still be brought current on the next bench visit.
