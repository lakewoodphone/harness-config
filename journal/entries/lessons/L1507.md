**L1507 · A patch script must accumulate on a running copy; PATCH OK is a claim about text, not behaviour**

**A patch script that writes every replacement from ONE validated snapshot silently keeps only the
last edit per file.**

Measured today, on my own tooling. `patch-owner-message-shelf-life.py` had two edits in
`app/database.py` and three in `app/services/lifecycle_sweep.py`. It validated every anchor
(`count == 1`), printed `ok` for all five, and printed `PATCH OK`. The result: `lifecycle_sweep.py`
called `_expire_stale_owner_messages(conn, _db_lock, db_url)` with **no definition of it anywhere**
and `database.py` had lost the `status_note` column. Cause: it read each file once into `plans`,
then wrote `text.replace(old, new, 1)` from that same stale string for every edit, so each write
clobbered the previous one.

It was caught only because the very next thing I did was behavioural -- the new test failed with
`ImportError: cannot import name '_expire_stale_owner_messages'`. `PATCH OK`, `py_compile`, and
five `ok` lines all said the work was done. They were all true and the file was wrong.

The rule: accumulate edits on a running copy of the text (or re-read the file before each edit),
and treat "the patch applied" as a claim about *text*, never about *behaviour*. Every patch ends
with a behavioural gate -- import the module, run the test, read the value. This is the same class
as the three hand-typed timestamp filters and the two hung `$(...)` here-strings earlier in this
session: what is checked is where the mistake is; the mistake was where nothing was checked.

Fix applied: rewrote the patches to accumulate per file and write once
(`patch-owner-message-shelf-life-2.py` and everything after it), and the file is now correct in the
tree and committed (`a6b08392`).
