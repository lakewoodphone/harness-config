**L1512 · A reply that lives only on a vendor portal is invisible to a mail-shaped pipeline, and a task auto-created from a notification will be closed against the notification**

A support reply that exists **only on a vendor's web portal** is invisible to every mail-driven pipeline we run,
and an auto-created follow-up task will be closed against the *notification* rather than against the *resolution*
— so the actual question is lost silently and looks like work that got done.

Evidence (all read 2026-09-15, one session):
- RattleByte agent Eriks replied to ticket **#188880** and closed it in the same minute (2026-09-12, portal time
 09:16). That reply was written into the osTicket database and to the portal page — and nowhere else.
- `email_triage_log.id 2965` ingested only the **auto-created-ticket notification**
 (`message_id 1a094aafde65d7fb`, `2026-09-12T08:38:50Z`, `action_taken=task_created`).
- `email_thread_state` thread `1a094aafde65d7fb`: `message_count=1`, `needs_response=1` — one message in, still
 flagged as needing a response, and it stayed that way for three days. **`needs_response=1` was the warning and
 nothing read it.**
- Gmail `in:anywhere rattlebyte|188880|BD84` over all four connected accounts found no agent reply.
 Root cause of the delivery gap: osTicket addressed the ticket to `info@lakewoodphoneandtech.com`, and that
 address is **not** one of the four connected Gmail accounts.
- Task `24658` was created 08:38:50Z and marked **done 09:07:57Z — 29 minutes later, nine minutes before the
 agent's reply**. Nothing verified that the *substance* had been handled; the notification being ingested was
 treated as the work being done.

Two independent failure modes compounded: **(1) an outbound task was closed on ingestion, not on resolution**, and
**(2) a counterparty reply that never became an email had no path into the system at all.**

What to do about it, in order of cost:
1. When a task is auto-created from an inbound notification, it must not auto-close on the *next* inbound or on a
 timer. Close it only on evidence of resolution. A task sourced from `email_triage_log` should carry the
 `message_id` it came from so that closing it can be gated on "a reply was actually sent or received".
2. `email_thread_state.needs_response = 1` older than ~24h is a cheap, high-signal alarm. Nothing currently reads
 it. Any task/thread with `needs_response=1` and no draft should surface to the owner or to a worker.
3. Support portals (osTicket, Zendesk, Freshdesk, warranty portals) are **not** email. When a vendor's support
 flow is portal-based, either connect the portal or record in the case file that the portal is the only channel —
 so the next session does not wait for an email that will never come.
4. Every alias the business receives mail at must resolve to a connected account. `info@lakewoodphoneandtech.com`
 is the customer-facing address on the website and on vendor orders; if it is not connected, replies to it die.

Corollary worth keeping: **an empty mailbox search is not evidence that a vendor never replied.** Search the
vendor's own portal before concluding they went quiet. This session's first instinct was "the vendor ignored us
for three days"; the truth was the opposite — the vendor replied in six minutes and we then ignored *them*.
