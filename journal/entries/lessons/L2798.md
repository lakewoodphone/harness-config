**L2798 · A stale .git/index.lock silently freezes an autonomous checkout, and a frozen checkout looks identical to a healthy project**

**L2618 · A stale `.git/index.lock` silently freezes an autonomous checkout, and a frozen checkout looks identical to a healthy project**

Recorded 2026-09-28 (ZABZ-YOGA), from the daily wake loop's two project checkouts on `secratary`.

THE FAILURE, TWICE, IN THE SAME SHAPE
The loop revives a working session each day for named projects. Each has a git checkout on the server.
Both were found crippled:

| project | repo | was at | behind | stale lock |
|---|---|---|---|---|
| `lpt-website` | `/home/zabz/repos/phone-and-tech-full` | `057cea451` (**2026-08-24**) | **426 commits** | `.git/index.lock`, 0 bytes, **2026-09-16 00:30** |
| `kosher-ai-filter` | `/home/zabz/repos/kosher-filter-ai` | `d225385` (2026-09-06) | **222 commits** | `.git/index.lock`, 0 bytes, **2026-09-20 15:30** |

Both locks had **no git process behind them** — debris from a crashed git operation, one of them twelve
days old. The registry (`~/bin/sources/projects.json`) recorded the LPT one's staleness in its own notes
as if it were simply the project's current state (`"HEAD 057cea451 2026-08-24"`), which is how a frozen
checkout gets read as a fact about the world rather than as a fault.

WHY IT COMPOUNDS, AND WHY NOTHING NOTICED
1. **Every git WRITE fails.** A shift's work cannot be committed or pushed. Measured: in the kosher
 checkout a shift's edit sat uncommitted for **six days** — and it was only luck that it did not
 matter, because upstream later landed a *better* version of the same change (it corrected "WinDivert
 2.3" to "2.2.2; no 2.3 exists"). That outcome was not safety; it was a coin flip.
2. **The checkout never advances**, so each day's one release is spent working against code that no
 longer exists. The LPT shift was editing an August tree while `origin/test` had moved 426 commits.
3. **It is invisible.** `project-keepalive` reported `suppressed project-daily-cap 1/1` — a perfectly
 healthy-looking line — while the repo underneath was unusable. This is the same failure class as the
 rest of this system's expensive history: *a live-looking thing read as work-happening.* The owner's
 phrasing is the test to apply: **the website is supposed to get materially better every day; when it
 does not, something is being reported as healthy that is not.**

THE RULE
- **Before believing a project is stalled, or that it is fine, look at its checkout**:
 `ls .git/index.lock`, `git rev-parse --short HEAD`, `git log -1 --format=%cd`, and
 `git rev-list --count HEAD..origin/HEAD`. Three commands, and they distinguish "the project has no work
 to do" from "the project cannot do work".
- **A stale lock is moved aside, never deleted** (`mv .git/index.lock .git/index.lock.stale-<date>`), and
 only after confirming no git process is running. A lock held by a *live* git operation is normal — that
 distinction is the whole of the fix and it is easy to get wrong in the other direction.
- **A dirty working tree older than a day is unlanded work, not scratch.** Preserve it to a writable path
 before touching anything, then decide whether it still applies. On the kosher checkout it did not — and
 checking that cost one `grep`, where blindly re-applying it would have reverted a correction.
- **The alarm matters as much as the fix.** A guard now exists as a wake source (`checkout-health.py`) so
 that a locked or stale checkout raises ONE flag per project per day, with the exact fix and the evidence
 in the prompt. Without it this recurs silently the next time a git operation dies mid-write.
- **`/root` is not writable as `zabz`** on `secratary`; use `/home/zabz/` for preserved files. (Cost me a
 failed preservation attempt before I checked.)

BOTH WERE FIXED 2026-09-28, with the fast-forwards and the preserved files recorded: LPT now at
`5dd8f6b98` then `a3111f29a`, 0 behind; kosher at `e02538f`, 0 behind, dirty tree resolved and the
stranded copy kept at `/home/zabz/kosher-unlanded-20260928T171217Z/` plus `stash@{0}`.

EVIDENCE: the lock timestamps and sizes quoted above; `git rev-list --count HEAD..origin/...` before and
after; the `project-keepalive` stderr lines; the unlanded diff (769 bytes) and its supersession by
`git show origin/main:windows/README.md`. All read 2026-09-28 ~17:05-17:15 UTC.
