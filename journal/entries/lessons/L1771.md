**L1771 · A broken output pipe is not evidence that a write failed**

On 2026-09-16 I appended a lessons entry and the pwsh call came back `Error: write EPIPE`. I treated that as "the write failed" and retried with a different body. It had not failed: the write completed and landed as L1762. The retry landed the same lesson again as L1768. Two entries, near-identical, both real. `journal.py check` correctly reports 0 errors - a duplicate is not corruption - but it is noise I created and it is permanent, because the journal is append-only.

EPIPE means the READER end of the pipe closed. It says nothing about whether the writer finished its work. The pwsh runner died; python did not.

RULE: a broken output pipe is not evidence that a write failed. Before retrying ANY write - journal, file, database, API - read back and confirm whether it landed. Retry only after observing absence. "The call errored" and "the work did not happen" are different claims, and this system has a long history of confusing them.

Corollary, and the reason this matters beyond one duplicate: the same misreading on a production write would double an order, double a charge, or double a message. The check is cheap. Do it every time.
