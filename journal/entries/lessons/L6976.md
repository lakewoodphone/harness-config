**L6976 · 871 rows in a table had a NULL primary key - SQLite allows it for TEXT keys, and the consequence was silence rather than an error**

Measured 2026-10-16 on /root/accounting-data/live/accounting.db. 871 rows of transaction_categories had id IS NULL, 418 of them on ACTIVE transactions. The schema is 'id TEXT PRIMARY KEY' and SQLite permits NULL in a non-INTEGER PRIMARY KEY - so the table accepted rows with no identity and reported nothing. Every one was written on a single day (2026-06-26) and every one was the ONLY category row for its transaction, so nothing was shadowed and no total was wrong. The consequences were all of the silent kind: cfo-enrich-justifications.py updates by id, so those rows could never be enriched by that path; any audit keyed on id could not see them; and the enrichment report's 'rows with no findable rule: 950' sat unchanged while 418 active rows were unreachable. Repaired by assigning a uuid4 to each, with the proof that matters: a sha256 over every (transaction_id, entity_id, category_id, justification, assigned_at) triple is identical before and after (0561f9aaa72183305f26c2d9), rows 8665/8665, 0 duplicate ids introduced, quick_check ok, after a timestamped cp -a backup. Also repaired in the same pass: 294 transactions with a NULL account_id, of which 166 had a duplicate parent whose account is known, so the account was copied rather than guessed; the remaining 128 have no parent and are named rather than hidden. AND THE HYPOTHESIS I HAD IS NOT CONFIRMED: I expected the id repair to unblock the enrichment, and measured after the repair the queue is still 0, so it bought addressability and integrity rather than a classification gain. The general rule: a schema that PERMITS a NULL where the design means 'every row has an identity' will produce silent unaddressable rows, so check for NULL primary keys by query - 'id is null' - rather than assuming a PRIMARY KEY implies presence. On SQLite that means TEXT/other-typed PKs specifically; INTEGER PRIMARY KEY cannot be NULL, which is why the trap is easy to miss.
