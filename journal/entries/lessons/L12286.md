**L12286 · An address-book label is not a verified recipient - the comms record is**

**An address-book label is not a verified recipient. The comms record is.**

The staged PIN rotation on the authority was built on 2026-10-18/19 to text the parents' new door
code to two numbers: +17326745878 and +17326747491. The first is real — 106 communications, address
book "Mom Zabrowsky". The second was labelled **"Totty"** in the address book and had **four**
communications in the whole record. Its most recent inbound message to us, 2026-09-09, reads:

 "I believe you sent this message to the wrong number"

and the June 2026 call transcript has the holder saying *"somebody bought my phone to call and he's
not with me anymore so I don't even know who it is."*

The script was never run (staged inert), so nothing leaked. But it was one `systemctl enable --now`
away from mailing a household door code to a stranger **every fourteen days, forever**, and rolling
back if Twilio refused — the rollback would have protected the delivery, never the secret.

**The rule.** Before a phone number, an address or a mailbox becomes a recipient of anything
sensitive, prove it belongs to the person you think: `ps_comms_person <number>` and read the actual
messages, not the label. An address-book entry is a claim somebody typed once. In this record the
label said "Totty" and the messages said "wrong number"; only one of those can lock somebody out.

**The same test applies to a recipient I inherit from a previous session.** The label was in a
docstring, in a decision entry, and in a README — three copies of the same unverified claim, which is
exactly how an estate convinces itself a fact is checked. It was none of those things.

Measured while auditing the PIN rotation, 2026-10-22. The father's number is now a configured value
(`PHOENIX_FATHER_PHONE`) that refuses anything that is not E.164, and defaults to *absent* rather
than to a guess.
