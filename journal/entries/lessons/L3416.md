**L3416 · A live pid is not a live service - prove a lock owner by reachability, never by process.kill(pid,0)**

Measured ZABZ-YOGA 2026-10-02 to 2026-10-08, six days, completely silent.

`dshw-proxy.mjs` guarded single-instance with `process.kill(pid, 0)` on the pid written in
`%TEMP%\dshw-proxy-3200.lock`. That lock was written 2026-10-02 by the proxy that was then serving
3200, pid 21464. The machine rebooted; Windows handed pid 21464 to Intel's DSATray.exe. From then on
every start logged "another proxy holds ... and is alive - exiting without binding (single instance)"
while NOTHING listened on 3200. `origins-start-errors.log` grew to 3.8 MB of these refusals; its last
write is 20:43:13, the second the lock was taken over.

RULE: a pid number proving liveness proves only that SOME process holds that number. When the owner is
a service, the proof is that the service answers. `acquireLock` now honours a live pid only while the
lock is younger than a 30 s grace window (which is the start race it was written for), and past that it
takes the lock over with a log line naming the reused pid - it is only reached at all after
`alreadyRunning()` has already said nothing answers on the base port, so "alive" there is by
construction not this service.

DIAGNOSTIC: if a lock names a live pid while the base port refuses connections, this fault is present
and `tasklist /FI "PID eq <pid>"` names the innocent program. Checked 2026-10-08: 21464 = DSATray.exe.
