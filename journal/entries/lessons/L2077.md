# A policy number written twice is a policy that silently doesn't apply — and a mesh child that waits for a tick dies unreported

Two rules from the same session, both measured on 2026-09-20.

## 1. The looser copy wins, and nothing says so

The owner approved **4 autonomous releases/day**. I changed the default in `wake.py` (the store's own
guard) from 8 to 4 and verified it: `wake.py stats` reported `max_per_day: 4`, `caps_in_force:
["daily_cap: 4/4 releases today"]`. I treated that as done.

It was not. `wake-dispatch.sh:77` carried its **own** `MAX_PER_DAY=${WAKE_MAX_PER_DAY:-8}`, and that is
the number the dispatcher actually gated on — its own `--dry-run` printed `releases today 5/8` while the
store reported 4/4. **Five releases went out that day against a limit of four**, and every check I had
run said the limit was in force.

The rule: **when a policy number appears in two places, it is enforced in neither reliably — the looser
copy always wins, and it wins quietly.** So when a limit is set:
1. say which file OWNS the number and make the other one a copy that names the owner;
2. add a comparison that runs on the same cadence as the enforcement and **warns on mismatch**;
3. put the warning on every channel an operator might look at — `log` alone was useless here because the
 dispatcher deliberately suppresses its log during a dry run, and a dry run is exactly when someone is
 checking the bounds;
4. and verify the *enforcement path*, not just the artifact you edited. `wake.py stats` agreeing with
 itself proved nothing about what the dispatcher would do.

## 2. A mesh child that must wait for a scheduled event will be killed at the turn cap, with no report

job 8 was fixing the dispatcher's timeout. Its last recorded thought was *"Now, wait for the tick."* It
then died with `the remote turn did not finish within 1800000 ms and the ssh client was killed` — **killed
by the very cap it was working on**, having already written the fix into the file. Its work was saved
only because the edit was on disk; the report never arrived, and the change was unattributed until I read
the file myself.

The mesh child-turn cap and the dispatcher's own bound are both 1800 s, so a child that watches a
5-minute cron tick and then waits for a session to finish can exceed the cap and die with **no output at
all** — `job_output` returns nothing, exactly like the missing-`MESH-HOST` failure (L2070).

Rules:
- **Never brief a mesh child with a task whose completion depends on waiting for a scheduled event.** If
 the deliverable needs a real release to fire, either run it outside the cap or split it: the child
 changes the file and states the bound arithmetic; a later session proves it end-to-end.
- **Prefer doing transport and dispatch surgery in a session that is not under the cap** — which is
 where I finished this one.
- When a mesh job dies without a report, **read the artifact before re-dispatching**: the work may
 already be on disk, and re-running it would double-apply. Check for a `.bak`, `bash -n`, and a rendered
 dry run.
