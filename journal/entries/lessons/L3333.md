**L3333 · subagent mesh failed silently: exit 0 with no completion frame, and the brief assumed the wrong node**

# `subagent` (mesh) failed silently: exit 0, no completion frame, work lost

**Date:** 2026-10-05
**Project:** phone-and-tech-full hours rollout

## What happened

I dispatched two `subagent` calls to fan out a four-surface update. Both reported **failed** with the
same diagnostic:

```
the remote process exited 0 but printed no completion frame — the target profile did not run
(stderr tail: )
--- child final message ---
FANOUT_TRANSPORT_HOST_caa62799=ZABZ-TECH
FANOUT_TRANSPORT_CWD_caa62799=C:\Users\ezabz
FANOUT_BEGIN_caa62799
```

Read that carefully, because it tells you two things that the word "failed" hides:

1. **The child DID run, on ZABZ-TECH** — the transport recorded the host and started the frame
 (`FANOUT_BEGIN`). This was a real remote dispatch, not a routing refusal.
2. **Its answer never came back.** The frame was opened and never closed, so no result, no partial
 output, nothing to collect.

`mesh_children` showed the corresponding children as `[settled]` on node `zabz-tech`, with outbox
paths — meaning the durable half exists on the target, but nothing was surfaced to me.

## Two separate problems, and the second is mine

**Problem 1 — the transport.** A child that opens a frame and never closes it leaves the parent with
no way to know whether the work happened. "exit 0" plus "no completion frame" is the worst possible
combination: success code, no payload. The outbox on the target is the place to look, and I did not
have time to chase it before the owner needed the work done.

**Problem 2 — my brief assumed the wrong machine.** ZABZ-TECH reported `CWD=C:\Users\ezabz`, and its
`personal-secretary-mvp` is on `master` at a completely different commit with **no sign files in
`docs/marketing/assets`**. My frontend brief told the child to edit paths under
`phone-and-tech-full/frontend/...` on a machine whose checkout of that repo may not even be at the
same commit. So even a child that had returned a frame could have edited the wrong tree.

**A mesh dispatch that lands on a different node is not just a transport detail — it changes what
"the repo" means.** The brief has to state the node and the expected HEAD, or the child can do
plausible work against the wrong checkout.

## What I did instead

Did the work myself on the machine that owns the checkout, and reported it as local. The four
surfaces and the code fix are in `2ec3358f3`, pushed to `fix/hours-walkin-20260916`.

## The durable rules

1. **Before dispatching a fleet, confirm the target node's working copy is the one you mean** — host
 and HEAD, not just a path. `mesh_children` gives you the host after the fact; check it before.
2. **Read the diagnostic, do not skim it.** "exit 0 but no completion frame" means the child ran and
 its answer was lost — not that the child never started. The difference decides whether you re-run
 it or go read its outbox.
3. **When the mesh is unavailable, say so and mark the fallback.** A result produced locally while a
 reader believes it came from a fleet is a lie about where work happened.
4. **If the fleet fails, do the work.** Fan-out is an optimisation. The owner needed the hours fixed,
 not a report about transport.
