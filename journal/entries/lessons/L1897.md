**L1897 · A host-plane activation has three parts (package, live layer, running engine), and an uncommitted live layer is reverted by autosync every 15 minutes**

MEASURED 2026-09-17 on ZABZ-YOGA while writing the idle restart window (docs/mesh/100-restart-when-idle.md).

A host-plane row is activated in THREE places, and a restart only refreshes one of them:
 1. the package - ~/.dsh/profiles/<p>/node_modules/<name> (a junction into the checkout)
 2. the rows - ~/.dsh/profiles/<p>/cordis.patch.yml (the layer the loader applies last)
 3. the running engine - which read (1) and (2) at boot

"Installed but inert until the engine restarts" was the brief. It was HALF true: the package was
linked and current (junction into the checkout, lib/broker-client.js present), and the rows were NOT
in the live layer. `dsh --profile web --dump-config`, filtered to the row, had no placement keys.

The chain, each link observed:
 * live layer : 10928 bytes, written 09:47:17, sha256 850734E8..., no `placement:`/`brokerSsh`/`brokerUrl`
 * this checkout: 12598 bytes, edited 09:31:11, carries all three (lines 135/137/138)
 * live == `git show HEAD:profiles/web/cordis.patch.yml`, BYTE FOR BYTE
 * ~/.dsh/.../cordis.patch.yml.bak-20260917-134717 holds 12598 bytes with content mtime 09:31:11 -
 the placement version, displaced at 13:47:17Z = 09:47:17 local
 * autosync.ps1:358-380 exports HEAD to %TEMP% and runs sync.py FROM THE SNAPSHOT
 ("the apply now runs against a snapshot of HEAD ... committed changes land")
 * sync.py:184-187 is the only writer that names a backup <file>.yml.bak-<UTC stamp>, copying
 REPO/profiles/<name>/cordis.patch.yml over the live layer
 * task PersonalSecretary-HarnessSync: last run 09/17 09:47:02, repeats EVERY 15 MINUTES
 * reconstruction: rows written to the working tree 09:31 -> installer applied them live 09:32:40
 (its own local-stamped .bak-20260917-093240) -> autosync reverted them 09:47:17

THE RULE: sync.py applies from a HEAD snapshot, so an UNCOMMITTED change to a live layer is temporary
by design. Anything that must be present in ~/.dsh at a future boot has to be COMMITTED, not merely
written to the working tree. A "I installed it" claim about ~/.dsh is therefore a claim with a
15-minute expiry until the file is on HEAD.

Also measured in the same pass, and it is the same class of mistake: `mesh-provider-install.ps1
-Check` (read-only, exit 1, "0 change(s) (check only: nothing was written)") reported TWO stale
things - the live patch layer AND the deployed `zabz` preset - so the activation had a third part
(the preset's tool-subagent-remote row) that neither the brief nor the restart alone would have
covered.
