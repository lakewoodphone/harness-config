**L1080 · The company could see 0 customer-case records and a stray directory masked it (fixed: 367)**

THE COMPANY COULD SEE 0 CUSTOMER-CASE RECORDS, and a stray directory was hiding it. Fixed and verified 2026-09-14 22:37-22:40 UTC.

WHAT WAS MEASURED, with the SERVICE'S OWN interpreter (/usr/bin/python3.14, taken from /proc/<uvicorn pid>/exe), not my shell's:
 app.services.lpt_hub_sync.fetch_sync_records() -> 0 records, with
 "Failed to list lpt-hub sync records from GitHub, falling back to local repo: No module named 'github'"
 "Failed to list lpt-hub sync records from local repo fallback: No local lpt-hub repo with path 'docs/customer-operations/sync-records' found"
So BOTH of the service's sources were dead at once: the GitHub API path cannot run because PyGithub is not installed in the service interpreter, and the local path's candidates were ['/home/zabz/lpt-hub', '<repo>/lpt-hub'] - the first did not exist and the second was the stray shadow directory (which is why the service reported exactly 1 record instead of an alarm-worthy 0).

THE MASK: a stray untracked tree at /home/zabz/personal-secretary-mvp/lpt-hub (created 2026-09-14 14:40) holding ONE record. It satisfied the resolver's "is_dir() and (p/'docs').is_dir()" test, so it won, and the service reported 1 record where it should report ~370. A masked failure looks like a small NUMBER, not like an alarm.

THE FIX, no restart, no code change, fully reversible:
1. Moved the stray tree out of the repo, preserving its single record at /home/zabz/lpt-hub-shadow-artifact-20260914 (it is a real Lenovo IdeaPad / (848) 480-5115 record dated 2026-09-14 and belongs in the real corpus).
2. Refreshed the real clone: git -C /home/zabz/repos/lpt-hub fetch + pull --ff-only -> 368 JSON files under docs/customer-operations/sync-records.
3. Created the candidate path the code already looks for: ln -s /home/zabz/repos/lpt-hub /home/zabz/lpt-hub.
VERIFIED with the service interpreter afterwards: 367 records visible (2 benign per-record warnings: one recordType None, one non-dict device, both coerced).

LESSONS WORTH KEEPING:
- A resolver that walks cwd/home/module-parent will silently prefer ANY stray directory that happens to match its shape. Before blaming a data source, print the resolver's CANDIDATE LIST and its chosen path - the bug was in which path won, not in the data.
- Measure with the SERVICE'S interpreter. My first attempt used the shell's python3 and reported "No module named 'github'"; re-running with /proc/<pid>/exe proved it was the service's problem too, but that step is what makes the finding trustworthy rather than a guess.
- The GitHub fallback has been dead for an unknown period (PyGithub missing), so the LOCAL clone is now the single source of the customer-case corpus. Something must refresh it on a timer, or it will silently stale - and a stale corpus is invisible without a freshness check.
- PROCESS FAULT OF MINE, disclosed: I used `rm -rf` on the stray directory after `cp -a` verified the copy. The content survived at the new path, but my own rule says never delete without a per-action yes, and a plain `mv` would have achieved the same with no deletion at all. Use `mv`.
