**L1754 · The merge key is the index the system enforces, not the column that is convenient**

EVIDENCE: 2026-09-16, ZABZ-YOGA. I designed the cross-store communications merge on `uuid`: both tables have it, it is non-null on every row in both, and it produced a clean exact answer (111,749 shared, 621 container-only, 5,144 ghost-only). It was the obvious key and it was the wrong one.

WHAT E2 MEASURED: the pair `(customerId, metadata->>'external_ref')` is the real cross-store identity, because both stores carry the same partial unique index `idx_communications_unique_external_ref` on exactly that pair. Measured at 2026-09-16T18:23:04Z: container distinct pairs 104,610, ghost 109,706, matched 104,610, **only_container 0**, only_heroku 5,096. The container is a **strict subset** on the pair key.

THE CONSEQUENCE I HAD MISSED: my 621 "container-only" uuids are not new messages at all. They are **the same logical messages present in the ghost under a different uuid**. Merging on uuid would have inserted duplicates of messages the customer record already held — the one error in this whole effort that corrupts customer records rather than merely annoying us, and it would have looked correct in every count I ran.

RULES EARNED
1. **A unique index on both stores is a stronger statement about identity than a populated column on both stores.** `uuid` was unique in each store independently (so it looked authoritative) but it is not the cross-store key. The schema said which field the system treats as the identity; I inferred from the data instead of reading the constraint.
2. **Index the pivot, not the proxy.** When two datasets disagree, the join key should be the one the system itself enforces uniqueness on, not the one that happens to be non-null and convenient.
3. **Two independent diffs disagreeing is a signal about the KEY, not about the data.** E2 first measured 622 container-only on uuid and 0 container-only on the pair. That gap was the finding; either number alone would have been believed.
4. **A subset result is a gift: it means the merge is an insert-only reconciliation with no conflict resolution at all.** zero container-only rows = nothing on the live store can be overwritten. Worth checking for deliberately, because it converts a hard merge into a safe one.

STILL OPEN FROM THIS: the pair key cannot reach the communications rows that carry no `external_ref` at all — E2 counts **7,761** such rows. Those need their own rule; they are exactly the rows hand-entered or written by the website itself rather than by our Dialpad push, so they are likely the most valuable ones. This is unresolved and must not be silently dropped from the cutover plan.

ALSO: the ghost is still being written while we measure it (116,893 -> 117,208 across 65 minutes). Every count of it is a live number and must carry its timestamp, or a later reader will compare two numbers taken an hour apart and conclude the merge lost data.
