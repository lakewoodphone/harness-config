**L3520 · The guard is on main and on ONE laptop - not on the office box it is about. 'On main' is not 'on the machines'**

**"The guard is on main" is NOT "the guard is on the machines". Measured: it has reached exactly one
machine, and it is the one where it was written.**

WHAT I CLAIMED, AND WHAT IS TRUE. After landing `bc19941` I wrote that the guard "reaches every machine
on the next harness-config sync". I verified only that it was on `main` - a different claim. Measured
2026-10-11 ~21:22Z:

| machine | `scripts/mesh/guard-service-state.sh` | `host-posture.tsv` | the tests |
|---|---|---|---|
| **ZABZ-TECH** (where it was authored) | **PRESENT** | PRESENT | PRESENT |
| `secratary-cloud` (the authority) | **ABSENT** | ABSENT | ABSENT |
| `secratary` (the office box, the one it is about) | **ABSENT** | ABSENT | ABSENT |
| `zabz-tech-linux` (the bench) | **ABSENT** | ABSENT | ABSENT |

WHY, and each cause is different:
- **The office box cannot get it by pulling.** Its `harness-config` checkout is **40 behind / 5 ahead of
 origin/main** - diverged, so a normal fast-forward is refused. That is the same divergence that
 rejected the guard workstream's push in the first place.
- **The cloud authority has no `harness-config` checkout at all** - only `/opt/company`. So there is no
 path by which a pull could deliver it.
- **The bench** has a checkout but has not taken the commit.
- **ZABZ-TECH has it only because it is where the work happened.**

SO THE HEADLINE OF THE GUARD WORK IS NOT YET TRUE. The rule, the posture file and the guard exist in the
repository and on one laptop. **The machine the incident was about - the office box - does not have the
guard that would have stopped it**, and neither does the authority.

WHAT TO DO NEXT, in order:
1. **Find the actual distribution mechanism** before inventing one (AGENTS.md §0). `harness-config`
 syncs by git; there is an `autosync.sh` convention and a `diverged-<host>-<date>` side-ref convention
 already in use, which is how the guard workstream preserved its commit. Read those first.
2. **The office box is the special case**: it is frozen and read-only, so delivering the guard there is
 itself a write requiring a decision - except that `MISSION-READ-FIRST.md` was already accepted as "the
 only permitted write", and a file that prevents a repeat of the incident is the same kind of thing.
 Ask before writing.
3. **The cloud authority needs a checkout or a placement.** `/opt/company` is the app, not the config
 repo; decide deliberately where config lives there rather than dropping the file somewhere convenient.
4. **Prove it per machine after delivering**: run the guard on each host and show `secratary` -> exit 2,
 `secratary-cloud` -> exit 0. On the office box that is a read-only invocation, so it is safe.

THE GENERAL RULE, and it is the same shape as everything else that went wrong today: **verify the thing
you are actually claiming, at the place the claim is about.** "It is in the repo" and "it is on the host"
are two different measurements, and only one of them protects a machine.
