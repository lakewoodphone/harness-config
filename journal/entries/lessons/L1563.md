**L1563 · Prove the key is a key before believing an alarming repetition**

**Rule.** When a query returns an alarming *repetition* — the same thing hundreds of times, the same file
proposed 30 times, the same error on 40 days — do not report the repetition until you have proved that the
column you counted on is a real identity, and that the store does not re-insert.

**Why.** On 2026-09-15 I found that customer `7328333965` appeared to have received the identical
"completed and ready for pickup" SMS **242 times** over 43 days, up to 20 in one day. It was a plausible,
serious customer-harm story. I tested the artifact hypothesis in the obvious way — `count(distinct
message_id) = 242` for 242 rows, `count(distinct created_at) = 240` — and it *appeared* to survive. I was
one sentence from telling the owner his business was spamming a customer.

What killed it was the clincher query: the same grouping across the whole table returned *"Sure"* appearing
**739 times** to one customer, *"You can come by"* 543, over an identical 43-day span. 739 sends of the
word "Sure" is not a thing that happened. **127,784 rows collapse to 18,585 distinct (thread, body) pairs —
6.9× duplication** — and `message_id` is `ptf-comm-NNNNN`, which increments *per row*, so its uniqueness was
guaranteed by construction and proved nothing. The test was circular: I had used the artifact's own property
as evidence against the artifact.

**The generalisable form.** A unique-per-row id and a fresh-looking timestamp on every copy are exactly what
a re-insertion artifact *produces*. So:

1. Check `count(*)` against `count(distinct <the-thing-that-should-be-unique>)` **on the whole table**, not
 on the alarming subset.
2. Confirm the candidate key is assigned by the *source* (a provider id, a content hash), not by the
 database (a row id, a sequence).
3. Look for a sibling/independent store holding the same corpus and compare totals. 127,784 vs 6,194 is the
 whole answer.
4. Ask what the *smallest plausible true count* is, and whether your query could produce the same number if
 the truth were that small.

**Same lesson, second proof, same day.** I concluded the business had no working backups because its backup
cron wrote into a directory that does not exist. Checking all four candidate paths and reading the script
took one command and found a correct, 165 GB, online-backup-API system. Two near-miss false alarms in one
session, both avoided by one extra command rather than by better judgement.

**Corollary for this system specifically.** `dialpad_sms_cache` (127,784 rows / 18,585 distinct pairs) and
any other crawler-populated store must be deduped before it is counted to the owner. The journal's own
"texts 127,678" headline is inflated for the same reason.
