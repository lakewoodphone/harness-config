**L3380 · A fence that is never armed is not a fence: the survivor bootstrapped fine and would have written without proving leadership**

GOAL ROUND 26, third round in a row finding the same class of defect in a different link. The survivor's bootstrap built deps, code, venv, secrets, the systemd unit, the tunnel connector - and NEVER ARMED THE FENCE. survivor.env does not set COMPANY_FENCING, so a freshly bootstrapped survivor ran may_send() = (True, 'fencing-disabled'): it would transmit without ever proving it holds the lease. The reason this is easy to miss is precisely why it is dangerous: SURVIVOR_MODE holds every send anyway, so nothing LOOKS wrong - right up until the survivor is promoted and that hold is lifted, at which point an unfenced survivor beside a returning office is TWO WRITERS, which is the single failure this whole two-host design exists to prevent. The bootstrap mentioned arming in a closing note to the operator, and a note is not a stage. FIXED: stage_leadership, run last by --install, which generates the lease key ON the survivor (only the PUBLIC half crosses to the arbiter, authorized by one printed command), installs the renewer, sets COMPANY_FENCING=1 with a stable COMPANY_HOST_ID, installs the */2 cron, attempts the first acquire, and then proves the outcome - a lease file with a holder and epoch, or an explicit 'another host leads, this host is a FOLLOWER', which is a correct state rather than a failure. AND THEN I TESTED THE CHAIN ON TWO REAL HOSTS instead of simulating it: Box 1 stood in for a survivor and Box 2 is the real arbiter, and the whole sequence behaved - GRANTED epoch 7 over ssh, the lease file written by the far host, the arbiter confirming HELD with 297s remaining, a THIRD PARTY refused ('REFUSED: waze-mdm-01 holds the lease'), the app agreeing (may_send True, current_epoch 7), the fencing token refusing the previous epoch (epoch_is_fresh(6)=False), and the same lease aged ten minutes refused as stale ('not been refreshed in 600s, limit 300s'). Left exactly as found: lease released, stand-in key revoked with the file backed up. RULES: (a) an ARMED safety mechanism and an INSTALLED one are different facts - check the switch, not just the binary; (b) when a second, unrelated gate masks a missing one (SURVIVOR_MODE hiding an unarmed fence), the missing one is invisible until the mask is removed, so test the state that exists AFTER promotion, not the state you are in; (c) prefer generating a key where it is used and authorizing its public half elsewhere, because a private key that never travels cannot leak in transit.
