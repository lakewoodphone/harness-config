**L2076 · A cost meter that prints 0 hides spend: model_usage cannot price a wake release, the release-to-session link does not exist, and an unreadable store must exit non-zero rather than print a number**

# A cost meter that prints 0 is a meter that hides spend — and the app's own ledger cannot price a wake release

Measured 2026-09-20, building the wake system's cost measurement. Three findings, each with the evidence
that produced it.

## 1. `model_usage` does NOT contain a wake release's usage

The obvious join — price releases from the app's own billed ledger — is wrong. Measured:
- the window of release #6 (2026-09-19 04:05–04:17Z) holds ONE `model_usage` row, `agent_id=orchestrator`,
 **empty `session_id`**;
- the window of release #5 holds **zero** rows, though that session demonstrably exists;
- `model_usage` has **zero rows at or after 2026-09-20 00:00Z**, while four releases ran that day.
A wake release is a headless DSH turn on a Windows node; its usage is recorded **there**, in
`<DSH_HOME>/storages/session_projcache/sessions/<sessionId>.json` under
`record.rows.tokenUsage.val.totals`. The app ledger is a different pipe. **Never price machine work from
the app's ledger**; go to the artifact the work itself produced.

## 2. There is no stored link from a release to the session it started, and that is the whole design

`wake-dispatch.sh` records only a run token in staging filenames, and `wake-out-*.txt` carries
`WAKE_EXIT_CODE` / `cost=none`. There is no recorded session id. Any mapping is therefore **derived**, and
a derived mapping must state its evidence per row or it is a guess. The honest fix is cheap and known: have
the dispatcher write a `wake-session-<release id>` sidecar as it starts the turn (`wake-cost.py` already
reads that sidecar). Until then, exactness is unavailable and must be labelled as such.

## 3. A cost meter read from the wrong host printed 0 tokens and did not complain

Running the same tool from the authority (where cron will run it) produced 9 rows, **every one
`session=- (none) tokens=0 cost=unsourced`**, and a summary reading `4 release(s), 0 token(s)`. Run on the
node that holds the store, the same tool read `uncachedInputTokens=84254, outputTokens=85685,
cacheReadTokens=6506240` for one session and 25,435,976 tokens across the day. The authority can reach
that node (`ssh -o BatchMode=yes desktop-ts hostname` works from secratary), so this was a swallowed
failure, not an unreachable host.

**The rule, and it is the same rule as P3 and every "empty result is not evidence of health" lesson in
this journal:** a meter has exactly three states and must never conflate them —
- **unmapped** — this release has no resolvable session (an honest gap in the mapping);
- **unreadable** — the store could not be read (ssh failed, path missing, permission): exit non-zero with
 the reason, **never a number**;
- **genuinely zero** — a session that really recorded no usage, and which must say why it is legitimately
 zero.

A zero that means "I could not see" is worse than an error, because it is the number that would let this
system spend money unnoticed — the exact thing the owner asked to be protected from (*"we can't waste
hundreds or thousands of dollars on stuff that don't need to happen"*).

## 4. The cost is real and, tonight, unpriceable — and that is stated, not hidden

Today's four releases burned **25,435,976 tokens** (top spender #8, 9,654,201). Dollars are **unsourced**:
no record on this mesh says which `(provider, model)` a wake session ran on, and the two pipes for the same
model differ **5.5x**, so defaulting either would be inventing a rate. `wake-tuner.py` prints exactly that
in its digest rather than a plausible dollar figure — which is the behaviour to keep.

## 5. A hardcoded source list means an installed source runs never

`run-wake-sources.sh` listed its sources by hand, so `project-keepalive.py` and `wake-tuner.py` sat
installed and unscheduled until each was added to that loop. **An installed file is not a running source.**
Both are now in the list and both demonstrably ran in the 2026-09-20T03:00Z cycle (`sources.log` lines 582,
583, 585). Worth changing the runner to a glob with an explicit exclude list so the next source cannot be
silently dormant.
