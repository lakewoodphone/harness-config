**L12480 · per_phone flip on lpt-apps: the canary skips instead of failing, and the sequence that worked**

Transferable facts from the 2026-10-21 production flip of /opt/filter-broker on lpt-apps from LPT_WS_AUTH_MODE=global to per_phone.

1. THE TRAP. In per_phone mode the canary does not fail when it has no credentials: server/app/canary.py ~648-675 records every check as status="skipped", reason="missing_phone_canary_credentials". The only live monitor goes quiet while still looking green. Mint the canary credential in the SAME change as the mode flip, and after the restart assert a NEW canary_probes row whose status is pass and whose detail does NOT contain missing_phone_canary_credentials. The scheduler calls run_canary_probe_once immediately on startup and only then sleeps LPT_CANARY_PROBE_INTERVAL_SECONDS (3600 here), so a restart yields a fresh row within seconds; no hour-long wait is needed.

2. CONTRACT. SOCKS per_phone is RFC1929: username = phone_id, password = token. The token is minted by POST /pairing/phone_tokens/rotate?phone_id=<id> authenticated with header X-Webhook-Secret = LPT_WEBHOOK_SECRET (no operator session needed). Response gives token, token_type=phone_api_key, key_id. It lands in phone_api_keys, not phone_tokens: token format lptpk_<random>.<secret>, verified by sha256(secret) == secret_hash through resolve_phone_token_context. A wrong token, the old global token, a new global token, and a mismatched phone_id were all refused with SOCKS 0101; the canary token was accepted and its CONNECT to a denied domain returned 0x02.

3. SEQUENCE THAT WORKED. Mint while still global (so the credential exists before enforcement) -> cp .env .env.bak-<ts> -> edit .env: LPT_WS_AUTH_MODE=per_phone, LPT_CANARY_PROBE_PHONE_ID=canary, LPT_CANARY_PROBE_PHONE_TOKEN=<minted>, LPT_WS_AUTH_TOKEN=<openssl rand -hex 32> -> docker compose -f docker-compose.yml -f docker-compose.ha.yml up -d --no-deps --force-recreate broker broker_b -> poll docker ps to healthy (20s) -> verify GET /health?deep=true auth_mode, the fresh canary row, live SOCKS accept/refuse, and docker exec env.

4. BOTH broker containers (lpt_filter_ai_api, lpt_filter_ai_api_b) bind the same /opt/filter-broker/data (same inode, same sha256), i.e. one broker.sqlite3. They share the .env, so both must be recreated; the HA twin opens the DB mode=ro.

5. BLAST RADIUS before rotating LPT_WS_AUTH_TOKEN: grep every /opt/*/.env for the name. Only filter-broker used it; filter-site and personality-test use unrelated SITE_*/LPT_SSO secrets. The token is also a fallback for dashboard tickets only when LPT_WEBHOOK_SECRET is empty, which it is not.

6. MODEL CATALOG. The personality-test image is Next standalone and contains no scripts/, and the host has no node. Run the project verifier from a throwaway container with the checkout mounted: docker run --rm --env-file /opt/personality-test/.env -v /opt/personality-test:/work:ro -w /work --entrypoint node personality-test:<sha> /work/scripts/verify-model-chain.mjs --action question,report. It resolves the live gateway catalog (26 models, v1) and probes each rung; RESULT: PASS with every rung served as requested is the evidence that models are resolved at runtime, not hardcoded.
