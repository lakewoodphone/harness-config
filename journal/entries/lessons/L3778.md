**L3778 · A cutover leaves the configuration that names the old host, and that configuration is not in the repo**

**L — A CUTOVER LEAVES THE CONFIGURATION THAT NAMES THE OLD HOST, BECAUSE THAT CONFIGURATION IS NOT IN THE REPO.**

The authority moved office -> cloud at 2026-10-11 05:43:36Z. The migration's own documents cover the hosts
(docs/mesh/122,126,127,128,131,141,159), `host-posture.tsv` covers service state, and the phone path was
re-measured the same week. **The LPT shop profile still pointed at the frozen office box**, because it lives
on a third host (`/opt/waze-mdm/profiles/shop-store.mobileconfig`) in another product's MDM, and it is not
in any of those documents.

It was found on 2026-10-13 the way these are always found — the owner reported a grey icon — not by a check.
Two days of a shop device wearing a clip that could not load, while `grep` for `secratary.tail93e6e6` across
`harness-config` returns 40 hits and none of them is this file.

**The rule.** After any migration, the list of things to update is not "the code" and not "the hosts": it is
**every stored absolute that names the old side**, wherever it lives — MDM profiles, web clips, allow-lists,
bookmarks, content filters, saved shortcuts, cron targets, monitoring. Enumerate them by asking the *other*
systems what address they dial (`tailscale status` on each device, the MDM device list, the gate's own log),
not by grepping a repo. **A grep answers "where do we say this", never "who dials it".**

And note the trap that makes this invisible: `secratary` is a **prefix** of `secratary-cloud`, so a search
for the old name "finds plenty" and a search for the new one looks healthy either way. Only reading the
file settles it.
