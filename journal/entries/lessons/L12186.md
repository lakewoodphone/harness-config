**L12186 · A record id minted at save time is why one assessment attempt became nine rows**

Measured on the personality-test integrate/100pct build (staging, 2026-10-22): one person, one Start, 125 answers, 27 PUT /api/persistence all 200 and no 409s, and NINE assessment_session_records rows for that attempt (3,3,4,5,6,6,7,7,8..17 answers between them), none complete, none carrying the report that the browser rendered. Cause was identity, not the network: buildSessionRecordId() minted session-<Date.now()>-<random> at save time, so 'which row is this attempt' lived only in the registry the caller held; the save path reads a React ref that is refreshed only by a settled response, and commitRegistry deliberately discards a settled response whenever a newer write has started (writeId check), so during continuous answering the ref stayed empty and every save minted a new row. Second half found while proving it: the write queue never drops an enqueued commit, so the backlog grew without bound and the payloads that landed were older copies of the attempt (screen at Question 18, body carrying 5 answers), which is why the finished run was never the stored version. Fix that worked: derive the record id from the attempt's startedAt (the library's (library_key, record_id) primary key then collapses duplicates), adopt the upsert result synchronously before issuing the write, keep only the newest superseded commit and issue it when the wire is free, and serialise the live session at issue time rather than at schedule time. After the fix the same harness produced exactly one row: session_status=complete, answered_count=119, finalReport present, report rendered, and the attempt survived a reload mid-run as one record. General lesson: de-duplicating an attempt client-side is impossible if its id is minted at write time; derive identity from the thing itself.
