**L2135 · L2148 - the full test suite cannot run on this box: ~6 hours, and it starves production while it runs**

Measured 2026-09-20 on the authority, and it resolves an open question about what "verified by tests" can
mean here.

**The measurement.** The repo's suite is 2,993 test functions across 231 files. Run in full:

 started 18:01:08 reached 8% at 18:07:09 -> ~45 s per 1%, ~6 hours for the suite

**And it harmed production while running.** With the suite going:

 load average 7.88 on 4 physical cores
 free memory 500 MB (from ~5 GB), and 1.8 GB already in swap
 /health timed out at 15 s, twice; one check returned connection-refused
 autopilot run_once exceeded its 600 s ceiling and was abandoned
 database `_get_conn: _db_lock contended` logged repeatedly
 run_count stuck: no tick completed in the window

**I stopped it.** Verification that takes six hours and starves the system it is verifying is worse
than targeted verification, and the cost is not hypothetical - it was measurable in the same window.

**The decision, stated so it is not relitigated:** the full suite is not runnable on the authority as a
routine step. Verification is instead (a) targeted selections covering every file a change touched,
(b) behavioural tests against fixtures, and (c) the outcome monitor's own measurements on live data.
That is what has been used all session, and every targeted run has passed. If a whole-suite run is ever
genuinely needed, it belongs on ZABZ-TECH (32 cores, 64 GB) against a checkout, not on the 4-core
production box.

**Evidence the targeted approach is adequate rather than merely convenient.** Every defect fixed this
session was verified twice - once by a test, once by a measurement on the live system: repo paths by
`_resolve_repo_path` returning real directories (9/9) and missing-path blocks falling 50 -> 2; the
completion gate by post-fix sessions completing exactly when their task was closed (3/3) and never when
open; `mashgiach` by lock errors 62 -> 0 and by persisted row counts (382, 466, 31/31). A green suite
would not have told me any of that, and a 6-hour suite would have told me much less than the two
queries that produced it.

**Also worth recording:** the 4 pre-existing `test_ai_gateway.py::test_delegate_worker_*` failures were
confirmed again in isolation (`4 failed, 94 passed`) - they raise
`RuntimeError: No reachable upstream for deepinfra/...` and need live provider credentials. They are
not regressions and should not be re-investigated.
