**L3553 · Apple's webcontent-filter: AutoFilterEnabled makes PermittedURLs inert, so the shop devices' 'whitelist' restricts nothing**

**Measured claim, with its source.** Apple's `com.apple.webcontent-filter` payload: *when Automatic
Filtering (`AutoFilterEnabled: true`) is enabled, `PermittedURLs` does **not** operate as a safelist — it
exists only to allow sites that the automatic filter categorises as "Adult" but that must be allowed.*
Source: Jamf's summary of the payload, read 2026-10-08
(https://support.jamf.com/en/articles/11025702-what-does-the-built-in-web-content-filter-in-jamf-school-do),
which cites https://developer.apple.com/documentation/devicemanagement/webcontentfilter.

**What that means for us.** The LPT shop devices carry exactly
`FilterType: BuiltIn` + `AutoFilterEnabled: true` + three `PermittedURLs`
(`lakewoodphoneandtech.com`, `/staff-intake`, `secratary.tail93e6e6.ts.net/`)
— so the filter does **not** restrict those devices to the shop's own sites. They can browse the open web
through Apple's adult-content filter. The profile's own build script says the point of adding it was that
"Safari on those devices was an unrestricted browser to the open internet" — that intent is not achieved by
this payload shape.

**And the fleet's own evidence for the opposite is not evidence.** The shop-device runbook
(`deploy/waze-mdm/docs/lpt-shop-device-runbook.md` §5) records "Verified on a device 2026-10-07:
non-permitted sites return 'restricted website'". Under Apple's automatic filter, a *restricted website*
block page is exactly what you get for a site Apple's auto-filter dislikes — it says nothing about the
permitted list being enforced. A block page can never prove a safelist; only a *permitted* page failing
(or a control site loading) can.

**Consequence to remember before trusting any "whitelist" claim in this estate:** making it a real
safelist is one key (`AutoFilterEnabled: false`), and it will also block every host the site needs that is
not listed — measured on the live site 2026-10-08: `api.lakewoodphoneandtech.com` (all data; a different
host from the site itself), `fonts.googleapis.com`, `fonts.gstatic.com`, `js.stripe.com`,
`m.stripe.network`, `m.stripe.com`, `static.cloudflareinsights.com`. Turning the key without that host list
breaks card payments and the API on the counter device.

**The general lesson:** a security control is not in place because a profile that looks like it is
installed. Prove the control's *effect* on the device, or say it is unproven.
