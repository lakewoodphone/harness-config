**L3737 · A placement broker that cannot read the fleet still answers, and its answer looks like a decision**

MEASURED 2026-10-12 03:18Z, ZABZ-YOGA, after the cloud cutover. The staged cloud broker had been
"staged but not started" since 2026-10-11 13:27, and the reason nobody noticed it could not work is
the shape of its failure.

`mesh-broker` reads each node through the node's gate (`GET /mesh/capacity`). The gate
(`scripts/phone-gate.py`) refuses any tailnet device not named in `phone-gate-allow.txt`, and the
cloud authority was never named. So from the cloud:
 HTTP/2 403 "Not signed in" on every route of every node;
 GET /nodes?fresh=1 -> reads 5 failures 5, all five `reason: HTTP 403`;
 POST /place -> node=zabz-tech position=1 blockedBy=["unreachable","no-free-slots"].

THE LESSON: the broker is built to never refuse — queue, never amputate — so with zero readings it
produced a perfectly well-formed placement with a full rationale, and that answer is indistinguishable
from a real one unless you read `blockedBy` and the per-node reasons. A control plane whose input is
all-missing must be treated as down, not as a queue. Any future host added as a broker or dispatcher
must be TESTED AGAINST A LIVE NODE READ and not just `systemctl is-active`.

HOW TO CHECK IT IN ONE COMMAND (from the broker's own host):
 curl -s http://127.0.0.1:3091/nodes?fresh=1 | grep -c unreachable # must not be every node
