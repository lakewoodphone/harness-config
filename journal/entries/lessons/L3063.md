**L-new · A mesh brief longer than about 11,400 characters cannot be dispatched at all on a Windows target: spawn ENAMETOOLONG**

MEASURED 2026-09-29 on ZABZ-YOGA, and then suffered live in the same session.

**The measurement.** `ssh-transport.js:63-66` delivers the child program to a Windows target as
`powershell -NoProfile -NonInteractive -EncodedCommand <base64>`, where the base64 is the UTF-16LE
encoding of the whole generated script — including the task and the 700-char task preamble. Base64 of
UTF-16LE is about **2.67 characters per input character**, and it goes into ssh's argv, and Windows
bounds a process command line at **32,767 characters**. Measured with the package's own builders:

| task characters | encoded payload | argv length | result |
|---|---|---|---|
| 4,000 | 12,316 | 12,527 | ok |
| 8,000 | 22,984 | 23,195 | ok |
| 10,000 | 28,316 | 28,527 | ok |
| 12,000 | 33,648 | 33,859 | **OVER-LIMIT** |

So the ceiling is about **11,400 characters of task**, and it is not a soft degradation: `spawn` throws

```
could not launch the ssh transport (C:/Program Files/OpenSSH/ssh.exe ... desktop-ts): spawn ENAMETOOLONG
```

and **the child never starts**. Nothing is dispatched, no node is used, and the run costs a full failure.

**It was then reproduced by accident, on the dispatch of the brief that was written to fix it.** The
child-identity lane's brief was about 11,500 characters and its run settled as failed with exactly that
diagnostic. The one useful thing about this failure mode is that it is honest: unlike the empty-host
refusal it names the real cause.

**Why this matters more than it looks.** The mandated agent-brief contract — repo root, shared context,
read-first list, exclusive file scope, git rules, the test command, the definition of done as commands,
and the report format plus honesty clause — plus a real task description, **routinely exceeds 11,400
characters**. So the fleet's own standard of a well-written brief is above the size at which the transport
stops working. A manager who briefs properly gets `ENAMETOOLONG`; a manager who briefs thinly gets work
that goes wrong for lack of context. That is a structural trap, not an occasional mistake, and it silently
caps how much context a child can be given.

**The fix.** Do not put a large payload in an argv word. Deliver the task by a file on the target and have
the generated program read it, or deliver the whole script on stdin on the Windows path too. Until then:
a generated program on the Windows path must **refuse** a task whose encoded payload would exceed the
documented limit, with a diagnostic that says the task is too large for the transport — never a mystery
exit, and never a truncation.

**The POSIX path is not the same.** On `sh -s` the script travels on stdin, so only the task is an argv
word and there is no 2.67x expansion. Do not reason about the ceiling from the Linux case.
