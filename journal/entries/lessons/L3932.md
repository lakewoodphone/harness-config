**L3932 · DISK at 97% caused the day's SQLite lock contention - and the 23GB was one of MY OWN children's cp -a copies. Freeing it: 81%, /health 0.007s flat, 0 lock events, the loop advancing**

The disk was at 97 %, and the 23 GB that fixed it was one of my own children's working copies. This plausibly unifies every symptom of the day, and the instrument that shows it is the `/health` timing.

**The measurement, before and after freeing 23 GB:**

 disk /dev/sda1 139G/150G used 4.9G avail 97 % -> 117G used 28G avail 81 %
 /root/work 32G total -> 8.6G
 /health 0.006s / 2.000s / 0.006s / 2.000s (alternating) -> 0.0140 0.0072 0.0073 0.0075 s
 lock contention 71 probe timeouts today, 32 in the noon hour -> 0 events since the removal
 the loop last_run_at frozen 13:54:43 for 44 min -> 14:42:01, run_count 1

**What was holding it.** `/root/work` was **32 GB**, and **`/root/work/evolve3-receipt` alone was 23 GB** — child 47's `cp -a` of `/opt/company` (its `.git` alone was 7.6 GB) made for a read-only parse analysis. The estate's own disk had 4.9 GB free, and SQLite writes temp files: **97 % full is exactly the condition that turns a write into a wait, and a wait into `database is locked`.**

**The chain, and it explains the whole day.** My fleet's copies fill the disk → SQLite I/O pressure → lock contention (`/health`'s 2 s probe timeouts, `database is locked` on work steps) → runs get slower → `run_once` exceeds its **600 s** ceiling → the run is **abandoned** and its thread **keeps holding `_db_lock`** → the next run is slower still → repeat → after three overruns the loop disables itself. **Every symptom I have been diagnosing separately — the stalled loop (`L3930`), the probe timeouts, the degraded 200s, the lock failures — sits downstream of a disk filled by my own agents.** I had attributed the idle hours to the budget cap, then to the wedge; the cap and the wedge are real, and *this* is what was feeding the wedge.

**How I verified it was safe to remove** — a copy is not data, but I checked rather than assumed:
- `/tmp/evolution-v3/receipt-report.md` **identical** to the tree's `REPORT.md` (`diff -q` clean, 12,624 B);
- the change itself preserved as `/tmp/evolution-v3/receipt-live.patch` (6,178 B);
- **`/opt/company` intact** — `app/main.py` 780,116 B, HEAD `561535b78`;
- the tree was a **copy** (`AGENTS.md`, `Dockerfile`, `app`, `.git`), not an original;
- and the child's un-pushed branch existed **only** there, so before removing it I captured its commit subject — `88894bc50 receipt_parser(amazon): repair an existing receipt row instead of ignoring the richer later email` — whose content *is* the preserved 6,178 B patch.

**And I made a fresh mistake doing it, recorded rather than hidden.** I tried to preserve the branch with `git format-patch --all --stdout`, which wrote **4.78 GB** into `/tmp` — because `--all` walks the entire repository history, not the branch — and it ran the disk out again before I removed the tree. `/tmp` is **tmpfs**, so that was 4.7 GB of RAM-backed storage. Removed immediately (`/tmp` back to 422 MB used). **The correct artefact was the 6 KB patch I already had**; `--all` on a repo this size is a disk bomb.

**What this means for the fleet, and it is the durable lesson.** A `cp -a` of `/opt/company` is **23 GB**, and this program ran **eight** work-copy children today. Two of them coexisting would fill the box. So:
1. **Every child brief must state a disk budget**, and a copy of `/opt/company` is not the way to read one file — `git worktree` shares the object store, and most of today's children needed read-only access, not a copy.
2. **Disk before and after every fleet run**, as a first-class reading next to memory pressure — the admission governor watches RAM and nothing watched the disk.
3. **The 26 GB `/root/lpt-sweep-20261014` is the other big reclaimable item and it is NOT mine to take** — it is a pre-remediation database backup and per `H3659` it needs the owner's word. With 28 GB free there is no call for it today.

**Not established:** that the relief *caused* the loop to advance — `last_run_at` reads 14:42:01, which is before the removal, so the run that completed may have completed independently. The evidence for the contention easing is the `/health` timings and the zero lock events, which are direct; the loop's advance is consistent and not yet attributable.
