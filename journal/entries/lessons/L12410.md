**L12410 · A dotenv value may be quoted, and a reader that keeps the quotes goes blind while still printing a result**

A dotenv value may be quoted, and a reader that keeps the quotes goes blind while still printing
a result.

MEASURED 2026-10-28. /root/personal-secretary-mvp/.env was rewritten at 07:23:53Z and
DATABASE_URL came back quoted:

 DATABASE_URL='sqlite:////root/authority.db' # after 07:23:53Z
 DATABASE_URL=sqlite:////root/authority.db # identical value in .env.bak-20261019T222924Z

/root/bin/text-health.py read the line, split on '=', and KEPT the quotes. Its prefix strip
("sqlite:///", "sqlite://", "file:") therefore never matched, _resolve_app_db() returned
Path("'sqlite:////root/authority.db'") -- a relative path -- and six of the channel's checks
failed with `unable to open database file`. C1 failed with
`invalid literal for int() with base 10: "'20'"`, the same class on a number.

THE DANGEROUS DIRECTION: the app was never affected (pydantic-settings strips quotes). Only the
monitor broke, and it still exited with a plausible `RESULT: 20 check(s), 8 FAIL`, which reads
as a problem with the text channel rather than with the parser. runs.log pinned the minute:
2026-10-28T07:15:03Z was 0 FAIL, 07:30:02Z was 8 FAIL. Blind for about nine hours.

WHAT TO DO NEXT TIME: when a monitor's failures cluster on ONE error string -- `unable to open
database file`, `no such table`, an int() on a quoted number -- suspect the monitor's own
connection before the thing it watches, and ask what WROTE the file it parses and when. Here a
.env rewrite eight minutes before the first failure was the answer.

FIX: a `_dotenv_value()` helper that strips matching outer quotes, applied at all three call
sites (_resolve_app_db from env, _resolve_app_db from .env, and C1's ceiling read). Result:
20 checks, 0 FAIL, rc=0. The fix belongs in the reader and not in the .env -- a dotenv file is
allowed to quote its values, and hardening the reader survives the next rewrite.
