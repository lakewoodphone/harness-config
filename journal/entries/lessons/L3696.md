**L3696 · Correction to L3695: the audit never flagged this record - a correct caseId hides a broken sourcePath, and I cited C14 without reading both sides of the fix**

Correction to **L3695** ("A sync record's sourcePath must name the case .md"), written the same session after testing the claim instead of believing it. The rule in L3695 stands and the fix was right; one piece of its evidence was wrong.

**What L3695 got wrong:** it said this record was "counted among **C14-record-cannot-find-its-case INFO=208**" by `tools/customer/audit.py`. It was not. C14 is a name-token matcher that only lists a record when nothing matches it by **stem, caseId or sourcePath** — and this record's `caseId` (`lg-old-phone-shwartz-2026-08-12`) equals the case filename stem exactly, so it was never an orphan and never in that list. Measured: C14 read INFO=208 before the fix (at 62a9a7643) and **INFO=208** after it (at 433e56c23) — unchanged, which is what exposed the error. Grepping the post-fix audit for the case id and the customer name returns nothing, and that was true before the fix too.

**What is actually true, and was measured:** the weak link was in the **case index**, not the audit. `lptcase.py show "7326204948"` printed `linked by: caseId-fallback` before the fix and `linked by: sourcePath-basename` after it — the sourcePath rule is the intended one and `caseId-fallback` is that tool's documented last resort.

**The transferable part:** a record with a correct `caseId` can hide a broken `sourcePath` for a long time, because every reader has a fallback. The way to see it is the link *rule* a tool prints, not whether the link resolved. And: when a count is the evidence for a fix, read the same count on both sides of the fix — I only grepped for the record, which cannot distinguish "fixed" from "never was there".
