**L1480 · Running the tests you wrote is not a gate: the full suite found nine regressions of mine, and a worktree attributes them**

Running the tests you wrote is not a gate: the full suite found nine regressions of mine

WHAT HAPPENED: across this session I added nine test files and ran those, plus the suites
adjacent to whatever I was touching. Every one passed, every time, and I reported each
change as verified. Then I finally ran `pytest tests/` on the whole tree:

 21 FAILED, 153 errors

Nine of those failures were mine, in files I had never run:

 * tests/test_work_mode_action_syntax.py -- 8 failures. My prompt change called
 `self._consecutive_readonly_steps(...)`, and that file builds the subject as
 `types.SimpleNamespace`, which cannot carry a method. The AttributeError named my line
 directly.
 * tests/test_work_session_stops_reading.py -- asserted the source text
 `self._readonly_steps = 0`, the counter I had deliberately deleted that same night.

The 153 "errors" turned out to be whole-suite interference: test_work_generation.py passes
94/94 alone. So the suite is not merely red, it is red in a way that changes depending on
what runs alongside what -- which means a green-looking targeted run says very little.

THE ATTRIBUTION TECHNIQUE, which is the reusable part: `git worktree add --detach /tmp/wt
<last-commit-claiming-a-green-suite>` and run the suspect files THERE. It separates "I broke
this" from "this was already broken" without touching the working tree, in one command. It
immediately showed that 8 failures were pre-existing (ai_gateway 3, config_contract 3,
vscode_chat_extractor 1, assistant_chat_prompt_profiles 1) and that two others DID pass at
that commit, so they were regressions inside the window -- and then that both were stale
tests for deliberate changes by another session (53739081 "stop recording unfinished work as
completed" and the 2026-09-14 breaker cooldown), not mine.

HABITS:
 1. Run the whole suite before claiming a change is verified. Targeted runs are for
 iterating, not for the claim.
 2. When the suite is red, do not guess at ownership: worktree at the last green commit,
 run the same files, compare. Attribution by reasoning about which strings exist in
 app/ took me three attempts and got one answer wrong.
 3. A test asserting SOURCE TEXT (e.g. `"self._readonly_steps = 0" in source`) pins an
 implementation and will fail the moment the mechanism legitimately changes. Prefer
 asserting behaviour or the new mechanism's own contract.
