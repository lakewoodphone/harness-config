**L3810 · A mesh child that fails on zabz-tech succeeds on the reroute - read the broker's own trace before declaring the mesh dead**

Measured 2026-10-14. Three subagent calls (the mesh) launched together for web sourcing all came back failed with 'the remote one-shot exited 4294967295 and produced no final message ... ORPHANED'. I reported the mesh as unusable and did the work myself. That was too fast. A fourth call, launched later, SUCCEEDED - and its own broker trace says exactly why the first three died: 'attempt 1 = node zabz-tech - node-specific - the node is the problem ... REROUTING IN 15491 ms; attempt 2 = node zabz-tech-linux - none - the run succeeded'. So the failure was ONE NODE (zabz-tech), not the mesh, and the broker reroutes on its own - a child launched while zabz-tech is the ranked node can die on attempt 1 if the reroute budget or the 45-minute ceiling runs out, and the message reads like the mesh itself is down. WHAT TO DO INSTEAD: on a subagent failure, read the job output for the 'attempt 1/attempt 2' lines and the 'retry budget' before concluding anything; a failure naming a node and no successful retry means relaunch (the ranked node may change) rather than fall back. Cheap probe: launch ONE child first and read its trace before launching a fleet. The three dead children together cost ~15 minutes of my own context doing sourcing by hand that the fourth child then did better.
