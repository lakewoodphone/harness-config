**L3377 · Rehearse the DR path you cannot test in anger - the seed script failed twice in ten minutes, both times in ways only a real snapshot would reveal**

GOAL ROUND 23. I wrote survivor-seed.sh (the vault restores the newest company snapshot and PUSHES the database and .env to a fresh survivor) and then did the obvious thing: ran it. It failed TWICE, and neither failure was visible by reading it. (1) It picked the NEWEST snapshot, which in a real repository was my 10 KB state-separation test payload with no database in it, and aborted. Fix: newest-first, but stop at the first snapshot that ACTUALLY YIELDS A DATABASE, logging what was skipped - a seed that trusts 'newest' will one day seed an empty company. (2) Having fixed that, it skipped a perfectly good 620 MB snapshot too, and the reason is structural: the offsite payload is a TAR INSIDE THE SNAPSHOT (the office streams 'tar -cf -' into 'restic backup --stdin --stdin-filename <stamp>.tar'), so a restore yields a tar and nothing loose. My script looked for a loose secretary.db, so it treated every good snapshot as empty. Fix: unpack the payload, then look. (3) Run three found it: snapshot afd1d1bb, 620,511,232 bytes, sha256 80f9ecf7...abc5d - byte-for-byte the same value the round-15 drill verified, which is the cross-check that tells me the seed path is honest. BOTH bugs would have surfaced at 3am on the one night the survivor was needed, in the one path that has to work, and neither would have been found by reading the code or by a unit test - only by pointing it at the real repository. THE SAME ROUND, A SECOND DISCOVERY OF THE SAME KIND: reasoning about what a PROMOTED survivor reports exposed a false alarm I had shipped - a survivor runs with its autopilot OFF by design, so it answers ok=true with loop_running_ok=false FOREVER, which is exactly the fingerprint of the 2026-07-22 thirteen-day silence, and the loop-dead alert did not exempt it. A correctly-behaving standby would have texted the owner 'the work loop is not running' every six hours. Fixed to be mode-aware like the mute probe, and verified both ways: mode=primary + idle fires the alarm, mode=survivor + idle fires nothing. RULES: (a) a backup/restore path must be exercised against the REAL repository, because the shape of what it finds (a tar, a test snapshot, an incomplete payload) is exactly what reading the code cannot tell you; (b) when you add an alarm, enumerate the hosts that will legitimately look broken - a standby is idle on purpose, and an alarm that cries wolf about correct behaviour is how a channel dies; (c) prefer 'the newest one that actually contains the thing' to 'the newest'.
