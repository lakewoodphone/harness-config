**L3645 · I deployed a worker's artifact while it was still improving, and the live clock would have run the stale one**

Measured 2026-10-13. The near-miss is the lesson; nothing broke, because the worker read my deployment
back and said so.

WHAT HAPPENED. A fleet worker produced `PATCH-marketplace-orders.patch`. I took the file as it stood
at 02:25, applied it to production at 02:36, ran its sync against the live ledger at 02:42, and
installed its systemd timer (next fire 05:13 UTC). The worker kept working for another ~40 minutes:
it was audited by an adversarial verifier on the mesh, fixed the defects that verifier earned, and
rewrote the patch. Its final report opens with the warning:

 "the deployed revision is one behind this patch and the clock is live ... Production has 71633
 bytes of marketplace_order_sync.py at 02:36:12 against the final 75404 ... Apply
 PATCH-marketplace-orders.patch and commit before that run"

Three real fixes were missing from what I shipped: the eBay return gate (returns were being booked as
orders), the provenance union (a later run could erase which mailbox an order came from), and the
item-write authority gate. The timer would have run the stale code unattended at 05:13.

FIXED. Compared production against the verifier-checked clone file by file (two of five differed),
backed both up with a `.bak-preFinal-` stamp, swapped them, and proved `py_compile` plus a live
import of both modules. The three unchanged files were left alone. The clock now runs the audited
revision.

RULES.
1. **A fleet artifact is not frozen when it first appears.** I treated "the patch file exists" as
 "the patch is done". For a long-running worker the artifact keeps moving, and the dangerous
 moment is not the merge - it is the first unattended run of what was merged.
2. **A SCHEDULE turns a stale artifact into a recurring one.** Installing a clock is what converted
 "slightly old code" into "code that will run the wrong thing every night at 05:13". Before
 enabling any timer, re-diff the deployed files against the worker's final output. If the worker
 has not finished, either wait or do not install the clock yet.
3. **Read the worker's OPEN RISK line before acting on its DoD.** The worker had put the exact hazard,
 with byte counts, at the top of its report. The information existed and I had to be told - which
 is why the risk section is read FIRST, not last.

STILL OUTSTANDING FROM THE SAME REPORT, recorded so it is not lost: `amazon_orders` now carries a
third `account_label` value `'email'` (235 rows) alongside `personal` and `business`, so any reader
filtering on `'personal'` silently misses the newer orders. Checked: `cfo-resolve.py` is the only
reader, and it matches on amount and date rather than label, so nothing is broken today. A future
reader that filters by label would be.
