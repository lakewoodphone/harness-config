# L — An evidence rung that must name a category can never suppress an ask, and the join key you assume is the one you must test

Two findings from making charge questions self-serve on 2026-10-15. Both are transferable.

## 1. `solved` required a category, so five pieces of evidence the estate already owned suppressed nothing

`merchant_resolve._finish()` decided:

```python
if source == "ask-answer":
 is_solved = not category or bool(solved) # his own answer IS the resolution
else:
 is_solved = bool(solved and entity and category)
```

The `ask-answer` exemption existed because *"asking him again is the defect, and not asking is the
whole point"*. But every OTHER way of knowing was gated on naming a ledger category — and the
resolver's own comments elsewhere forbid inventing one (`NEVER ASSERT A CATEGORY THE LEDGER CANNOT
FILE`). So an identification that named no category returned `solved=False`, `cfo-ask` composed a
question, and **the estate texted the owner about charges it could already identify**.

Measured: the `newegg` alias existed at confidence **0.97**, learned from the owner's own answer —
and `category` was empty because his answer named no category the ledger holds, so the charge he had
already explained stayed askable. Same shape for `owner-text` and `order-match`.

**Rule.** When a pipeline's success condition is "identified", do not gate it on a *second*, usually
absent property (a category, a label, a normalised name). Gate it on the identification, and carry
the missing second thing as evidence. A gate that can only be satisfied by a value the producer is
forbidden to invent is a gate that never opens, and it fails *silently into answering* — the worst
direction, because the work looks done.

**Corollary.** `planned_rows` must stay empty when the category is empty. Solving without a category
suppresses the ask; it must not also writes a filing under a made-up label. Both properties were
verified together: nine live merchants resolve, and `category='' planned_rows=0` on all of the new
sources.

## 2. `purchases.matched_transaction_id` joins `transactions.external_transaction_id`, not `transactions.id`

A subagent reported that `purchases` held "the exact Plaid id of this charge". The number was right
and the column was wrong. `transactions.id` is a **UUID**
(`4b550706-cd12-44d8-9742-758c1043a3f3`); the purchases row holds the provider's id
(`Rzagj969nZILgjOoM8J8haNrQvJP89urAoEQAg`), which lives in `external_transaction_id`.

Measured on the wrong key: **0 rows.** On the right key: **2,173** of the 2,401 `matched` rows.

**Rule.** A join between two stores written by different components is an **assumption about a column
name**, and it fails as an empty result, which reads exactly like "we hold no record of this". Test
the join and print its cardinality before you build anything on it — `SELECT COUNT(*) ... JOIN ...`
on both candidate keys costs one query. A join that returns 0 is a **refusal to answer**, not an
absence, and must never be reported as one.

**And check which database answered.** `~/personal-secretary-mvp/data/secretary.db` is 1.8 MB, exists,
and holds **0** `purchases` rows, while `/root/authority.db` — the app's own
`DATABASE_URL=sqlite:////root/authority.db` — holds 4,205. Resolve the path from the app's env and
assert the table exists, so a stale mirror cannot answer "no match" for the authority.
