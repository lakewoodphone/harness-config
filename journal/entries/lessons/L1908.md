**L1908 · A refresh job that fast-forwards to a stale ref reports health while the corpus goes stale**

## What broke

The authority's `lpt-hub` clone (`secratary:/home/zabz/repos/lpt-hub`) is the corpus the whole
company reads: `app/services/lpt_hub_sync.py` resolves its local candidate roots first, and
everything downstream — the hub↔WO linker, the production push, the reconciliation — reads that
directory. On 2026-09-17 it held **373** sync records while the true `origin/main` held **381**.

`harness-config/scripts/lpt-hub-refresh.sh` (cron `*/15`) was supposed to prevent exactly that.
It had two independent faults, and the second is the dangerous one.

**Fault 1 — the fast-forward could never succeed.** The script did `git fetch --quiet origin`
then `git merge --ff-only origin/main`, and recorded `ff=refused` on failure. But the secretary
*commits into the clone it is refreshing* (`chore(secretary): link <case> to WO<n>`), so local
`main` is permanently ahead of origin by one or more of its own commits. `merge --ff-only`
refuses by definition as soon as that is true. Over the 957-line log: `ff=ok` 146,
`ff=refused` 74, first refusal `2026-09-15T17:15Z`, latest `2026-09-17T15:15Z` — wedged 46
hours. Git's own words in the log: `fatal: Not possible to fast-forward, aborting`.

**Fault 2 — and this is the one that actually hid it — the fetch's exit status was never
checked.** So when the remote-tracking ref failed to update, the following
`merge --ff-only origin/main` happily fast-forwarded to a **local, stale ref**. Measured: the
authority's `origin/main` was frozen at `12368820e` (ref mtime `15:15:02Z`) while the true remote
head, per `git ls-remote`, was `811eca39d`. The clone was 53 commits and 8 records behind origin
**while the script reported `ff=ok`** on some runs. A fast-forward to a stale ref is
indistinguishable from success unless you check the ref moved.

**Fault 3 — the failure surface was unread.** The script wrote `"fast_forward":"refused"` into
`status.json`, and nothing consumed it: `grep -rIl "lpt-hub-refresh"` found only the script
itself, `lpt-recon.py` and a backup copy. A 46-hour outage produced no alert. Its `Permission
denied` cron lines were a third, separate fault — the file was `100644` in git, kept executable
on secratary only by a hand `chmod`.

## The rule

**A refresh/verify job must prove the ref it synced to is the remote's current ref, and must
have a consumer that fails on it.** Specifically:

1. Check the fetch's exit status.
2. Never fast-forward blindly — cross-check `git ls-remote origin refs/heads/main` and report
 `ref-stale` when the remote has commits the local ref lacks.
3. Prefer `rebase --autostash` over `--ff-only` for a clone that also *writes*: replaying your
 own commits is non-destructive, while `--ff-only` is guaranteed to fail and therefore
 guaranteed to be ignored.
4. Emit a machine-readable `status`/`rc` and make a checker exit non-zero on it.

## The fix, verified

`harness-config/scripts/lpt-hub-refresh.sh` rewritten: checked fetch, `--ff-only` then
`rebase --autostash` fallback, `ls-remote` staleness cross-check, `status`/`rc` in status.json,
exit non-zero on failure, mode `100755` in git. Deployed and run twice on secratary:
`status":"ok","rc":0,"records":381,"behind":0,"ahead":0,"head":"811eca39d"`, exit 0 both times,
idempotent. Also fixed `lpt-recon-check.sh`'s mode in git (was `100644`, invoked directly by
cron).

## A mistake I made in the same session, recorded because it is the same failure class

I first reported "9 customer records invisible to the company" on the strength of a `cat-file -e`
loop whose exit code was overwritten by a later command in the same pipeline, so the check
reported success unconditionally. Re-verified properly: `origin/main` on the authority was
exactly `12368820e`, `0 0` divergence, and the nine files were genuinely **absent**. The final
conclusion (9 missing records) survived, but the evidence for it did not, and an auditor could
have caught me. **Never derive a boolean from `$LASTEXITCODE`/`$?` after another command has run;
capture it on the same statement, or parse structured output.**
