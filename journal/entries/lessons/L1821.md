**L1821 · Windows mesh dispatch: ssh.exe hangs on a stdout pipe, and ZABZ-YOGA's sshd cannot traverse the symlinks DSH bundle resolution needs**

Two measured Windows traps, 2026-09-17, found while building packages/plugin-remote-fanout.

1. Win32-OpenSSH's ssh.exe DOES NOT EXIT when its stdout is a pipe. The remote command runs, its output arrives, and the client then waits forever. Measured on ZABZ-TECH against ZABZ-YOGA with `ssh laptop-ts hostname`: stdio ['ignore'|'pipe'|'inherit','pipe','pipe'] -> output "zabz-yoga" received, client still alive at 20 s; stdio ['ignore',<file fd>,'pipe'] -> exit 0 in 1075 ms; stdio ['ignore',<file fd>,<file fd>] -> exit 0 in 1049 ms. So redirect BOTH streams to temp files whenever we drive ssh from Node or PowerShell, and never trust the client's exit: settle on the work's own completion frame. Evidence: docs/mesh/70-remote-fanout-proof.md 4.1/4.2.

2. A process launched by ZABZ-YOGA's sshd CANNOT TRAVERSE the symlinks in ~/.dsh/profiles/node_modules, and that directory is how a DSH profile resolves its bundles (dsh-app-boot healProfilesModuleFallback). Same probe binary, same node: locally lstat says symlink=true and reading through it works and require.resolve finds the package; over ssh lstat still sees the link but reading THROUGH it fails with UNKNOWN (-4094) and require.resolve gives MODULE_NOT_FOUND, so `ssh laptop-ts dsh --profile headless "<task>"` dies with "plugin tree failed to load ... loader entries failed to apply". ZABZ-TECH's sshd session has no such problem (its mesh-profile parent booted over ssh and loaded the plugin). Consequence: the mesh's working ssh direction today is laptop -> desktop, NOT desktop -> laptop. Do not plan ssh placement into ZABZ-YOGA until either accepts carries the fact or the v2 route exists. Evidence: docs/mesh/70-remote-fanout-proof.md 4.4.

Two smaller ones from the same session: (a) do NOT pre-create $DSH_HOME/profiles/node_modules - dsh-app-boot owns it and mkdir over a junction there throws UNKNOWN; (b) @deepseek-ai/dsh-agent-presets is a ROW, not a bundle (it declares no dsh.bundle), and a !!js expression in a patch must be double-quoted because every ternary contains ": " which breaks YAML.
