**L12223 · CI outage is a spending-limit fuse, the watchdog sits on it, and a loop file is not a disk**

**The CI outage is a spending-limit fuse that keeps being re-lit, and every session re-diagnoses it instead of escalating it once.**

Measured 2026-10-21 on ZABZ-TECH, read-only against `lakewoodphone/phone-and-tech-full` plus measurement over `ssh secratary-cloud`.

## 1. The refusal, verbatim
A job refused at start has `conclusion: failure`, `steps: 0`, `runner_name: ""`, labels `ubuntu-*`. Its check-run annotation is exactly:

`The job was not started because recent account payments have failed or your spending limit needs to be increased. Please check the 'Billing & plans' section in your settings`

Read from `gh api repos/.../check-runs/119235776046/annotations`. **A refused job bills 0 minutes**, so any cost estimate anchored on an outage reports near-zero spend (this is L3882's anchor trap, still live).

## 2. The block has edges, and they are sharp
From 2,875 job rows across 575 runs (2026-10-20 05:32Z .. 2026-10-21 12:59Z):

| window (UTC) | hosted jobs that STARTED | refused |
|---|---|---|
| 10-20 05:32 -> 15:12 | **0** | 662 |
| 10-20 15:12 -> 10-21 05:25 | 985 | 0 |
| 10-21 ~05:25 -> 12:59 | **0** | 33 |

Zero hosted jobs started for 9.7 hours, then hosted resumed, then refused again. That is a fuse being reset and re-blown, not a flake. Last successful deploy: `2026-10-21T05:24:43Z` (test) / `04:55:28Z` (main) — the block resumes in the same half-hour.

## 3. The mechanism that was built to catch it cannot run during it
Commit `ci(gate): the daily check reads job annotations, so billing cannot look quiet (#569)` exists, and `Maintenance & Scheduled Tasks` has 7 jobs — all on `ubuntu-latest`. **The watchdog sits on the same fuse it watches**, so during the outage the watchdog is refused too. Measured: maintenance run 39557157587 failed with 0-step refusals on 2026-10-21 06:43Z.

## 4. Cost after the 02:36 restructure (measured, not modelled)

## 5. The self-hosted runner works, and its isolation is real
Two registrations `ci-cloud-1/2` in ONE systemd-nspawn container on `secratary-cloud` (`--private-users=524288`, own netns on `ci-br0`, `CPUQuota=300%`, `MemoryMax=8G`, `MemorySwapMax=0`, `Nice=19`, `IOSchedulingClass=idle`, `OOMScoreAdjust=500`).
- Isolation vs the authority PROVEN: `127.0.0.1:8002` refused, `/root/authority.db` absent, no tailnet, no ssh binary, egress only through a domain-allow-listed squid.
- Job isolation DISPROVEN: one PID namespace, so each shard's `pkill -f vitest` kills its neighbour. That is why `pr-precheck.yml` has `max-parallel: 1` + `concurrency: lpt-ci-frontend-shards`. Concurrency is mechanically 2, safely 1.
- Reliability: 11 of 74 self-hosted job failures, ALL in 02:15-02:25Z bring-up; after 02:30, zero self-hosted failures.
- **It cannot absorb the hosted jobs**: no Docker socket (backend shards need postgres/redis `services:`), and `pypi.org` + the Playwright CDN are not in the squid allow-list.

## 6. The authority's disk was the real hazard, and it is now defused
The CI disk is a 40 GiB **loop FILE** `/srv/ci/disk.img` on `/dev/sda1` — the same filesystem as the 31.75 GiB `/root/authority.db`. Mount options `rw,nosuid,nodev,noatime` = **no discard**, and the loop has no discard flag, so freed blocks are never returned. Measured: 75.1 GiB written since 02:11Z -> 23.86 GiB allocated for 8.6 GiB live. At 91% host, its 40 GiB ceiling exceeded the 21 GiB of free space backing it.

**Fixed by measurement, not by argument:** `fstrim -v /srv/ci/disk` -> `30.5 GiB trimmed`, rc=0. Allocated 23.86 -> **8.99 GiB**; host `/` 91% -> **84%**; free 21.0 -> **35.9 GiB**; inside the loop still 8.5 GiB used (no data touched); `company-api /health` 200 in 0.32s throughout.

`fstrim.timer` already exists and is enabled — but it is **weekly** (next 2026-10-26) for a filesystem writing ~2 GiB/h. The mechanism exists; its period is wrong by two orders of magnitude. Do not add a parallel timer; add a 6-hourly trim for this mount or give CI a real volume.

## 7. The transferable rules
1. **A metered budget is a single point of failure for a production gate.** A spending limit does not degrade CI, it stops it — and `enforce_admins=true` means the owner cannot merge past it either.
2. **Never put the watchdog on the fuse it watches.** Check the gate from somewhere that does not need the gate.
3. **A loop file is not a disk.** "Separate disk" that is a sparse file on the database's filesystem isolates nothing; only `discard`/hole-punching and a trim schedule make it steady-state, and a real volume removes the class.
4. **Fanning agents onto one shared 5,000/hour API bucket trips the secondary rate limit.** Six children paginating `gh api` at once zeroed it in ~40 minutes; a refused call is not a negative and silently corrupts a census.
