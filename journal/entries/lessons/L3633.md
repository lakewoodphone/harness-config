**L3633 · On Windows ssh.exe never exits while its stdout is a PIPE, and never sends EOF on a redirected stdin**

**L3444 · 2026-10-12 · On Windows, `ssh.exe` never exits while its stdout is a PIPE — and never sends EOF on a redirected stdin. Both break every CLI that shells out to ssh.**

Found while making the Waze fleet CLI (`scripts/waze/{onboard,ota,diagnose}.py`) runnable on the shop's
Windows machines, where every database-touching step died with `subprocess.TimeoutExpired` after 40 s.
Two independent Win32-OpenSSH defects, isolated by measurement on ZABZ-YOGA, not inferred.

**A — stdout must be a FILE, not a pipe.** `ssh <host> echo hello` with `stdout=subprocess.PIPE`: the
bytes arrive in the pipe at **0.76 s**, and the process then **never exits**. A probe given a **900 s**
budget was still waiting at **900.03 s** with the TCP session ESTABLISHED. The same command with stdout
redirected to a real file prints `debug1: Exit status 0` and exits **0 in 0.68-0.90 s**. The
`-vvv` trace stops after `chan_shutdown_write` and never reaches `output drain -> closed`.
Reproduces on **both** binaries on the box (Program Files 10.0p2 and System32 9.5p2), against three
different hosts, and it needs the remote command to actually **write** something: `ssh <host> true` with
stdout a pipe exits 0 in 0.6-0.8 s, `ssh <host> echo hello` hangs. `ssh -G` opens no session channel and
is never affected — which is exactly why the CLI's own `resolve_ssh_destination()` probe never hung and
why the first diagnosis ("`-o ConnectTimeout` is being ignored") was a red herring: `ssh -G -o
ConnectTimeout=7` does report `connecttimeout 7`.

**B — stdin must not be NUL or a fresh temp file.** With stdout already a real file, so A is out of the
picture: `ssh <host> cat` **hangs** with `stdin=DEVNULL` and **hangs** with `stdin=tempfile.TemporaryFile()`,
but **exits 0 in 0.73 s** when stdin is an existing on-disk file. Same for `ssh <host> psql -f -`
(DEVNULL hangs, existing file exits 0 in 0.81 s), while `psql -c 'select 1'` and `hostname` — which read
no stdin — exit in ~0.9 s. So the discriminator is exactly *"the remote program reads stdin"*: ssh never
hands it EOF. `CREATE_NEW_CONSOLE` does not help, so it is not about having a console. Upstream match:
PowerShell/Win32-OpenSSH#1330, whose maintainer writes *"The IO on /dev/null ... is somehow getting hung
when NUL is explicitly redirected"*.

**The shape of the fix, and it is the transferable part:** stdout to a real temp file, `stdin=DEVNULL`,
and anything that must reach the remote program's stdin delivered by a **remote-side quoted heredoc**
(`cmd <<'DELIM'`). The heredoc takes ssh's stdin out of the data path entirely, so there is nothing left
to hang; a random delimiter and quoting mean no expansion. Nothing system-wide changes — `BatchMode` and
host-key checking are untouched, so the security posture is identical.

**Why this is a rule and not an anecdote:** `capture_output=True` is the idiomatic way to call a
subprocess and it is **wrong for ssh on Windows**, silently, in a way that looks like the *remote* host
timing out. Any code on this mesh that shells out to ssh with `capture_output=True`, or that feeds data
down ssh's stdin, has this bug today. `scp_put()` in the same file still has half of it.

**Verified after the fix** — on ZABZ-YOGA and again on the Linux authority: `endpoints` 0.1 s,
`token-check` 0.5 s (66 devices), `devices 2001 2003` 4.6 s, `sql "select count(*) from fleet_devices"`
1.0 s → 66, `ota.py diagnose 2001` 3.0 s, all exit 0.
