**L5027 · Committed is not running: check ancestry before repeating 'fixed' (website_db ORDER_STATUSES)**

**A fix that is committed is not a fix that is running — check ancestry before repeating "fixed".**

2026-10-15, working the Pantoja intake. The canonical work-order-create path is
`app.services.website_db.create_order`, and the H3341 handoff (2026-10-08) ends with:
"**Fixed.** (1) `website_db.py` now reads the vocabulary from the enum at call time
(`_live_order_statuses`) and defaults to `AWAITING_DIAGNOSIS` (2) ...".

Measured today on the file the write path actually imports
(`/home/zabz/personal-secretary-mvp/app/services/website_db.py`, sha256
`cf868e71a5d43dad19f6ff8f147b9d6c7d70f0c9c609a5955e1ff7d23f33360b`, read 2026-10-15):

- `grep -n "_live_order_statuses"` → **no match**. The function is not there.
- line 1061 is a hardcoded `ORDER_STATUSES` set that lacks `AWAITING_APPROVAL` and
 `AWAITING_PAYMENT` and still carries `CHECKED_IN`, `IN_REPAIR`, `COMPLETED`; line 1191 still
 defaults to `status = (status or "CHECKED_IN")`.
- `git log -S"_live_order_statuses" --all` → one commit, `99bf51e48` ("Shop repair statuses: match
 the live OrderStatus enum, and read it from the store").
- `git merge-base --is-ancestor 99bf51e48 HEAD` → **NO**. The fix is not in the running tree's
 lineage at all.
- The newest commit touching the file is `2f478ba0c` (2026-10-15 14:58:42Z, "preserve: the live
 company app/ tree as it runs on 2026-10-15 — a snapshot of production, not a reviewed change"),
 and its diff for this file is unrelated (it adds a `reason` parameter to `update_order`). The
 parent lacks `_live_order_statuses` too — **so the snapshot did not revert the fix**; the fix was
 never on this lineage.

Rules that follow. (a) **Before repeating "fixed" from a handoff, check the ancestry of the
symbol**: `git log -S<symbol> --all`, then `git merge-base --is-ancestor <commit> HEAD`. "The fix
is committed" and "the fix is what runs" are different sentences and must never be the same one.
(b) The obvious story here — "a preserve-the-live-tree commit reverted it" — was wrong, and reading
the diff killed it in one command. A wrong hypothesis that gets measured immediately costs nothing.

Second, on the same path: `create_order` **returns `{"ok": false}` while the process exits 0** when
no `pg_url` is passed, because running the app's venv python directly does not load `.env`. The
first attempt printed `website_db: no Postgres URL configured` and `rc=0`. A caller that checks only
the exit code concludes it wrote an order and wrote nothing — pass `pg_url` explicitly from
`PHONE_TECH_FULL_DATABASE_URL` and assert on `ok`, never on the exit code. (Same class as the
harness's own "a non-zero exit sets no error flag": here a zero exit hid a failure.)
