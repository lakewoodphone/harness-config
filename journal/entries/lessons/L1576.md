## L1559 - `docker compose up -d` drops a hand-attached network, and the symptom is a 502 from a healthy container

**What happened, 2026-09-15 20:12Z.** I redeployed the rentals app with
`docker compose up -d --build` on lpt-apps-01. The build succeeded, the container came up, Next
logged `Ready in 292ms`, and `curl http://127.0.0.1:3007/api/health` returned 200 from the box.
`https://rentals.lakewoodphoneandtech.com` returned **502 for about a minute**.

**Cause.** Caddy reverse-proxies `lakewood-rentals:3000` over the shared `lpt_default` network. The
recreated container was attached only to `lakewood-rentals_default`. The old container had been on
`lpt_default` because someone ran `docker network connect` by hand at the original deploy - that
membership is in no compose file, so every recreate silently drops it. The siblings show what
correct looks like: `personality-test` and `chumash-timeline` are each on their own project network
**plus** `lpt_default`, and `caddy` is on `caddy_default lpt_default personality-test_default`.

**Fixed live** with `docker network connect lpt_default lakewood-rentals`; the compose file must
declare it externally so a recreate cannot drop it again.

**The rule.** "The container is running" and "the service is reachable" are different readings - and
for anything behind a proxy, only the *public URL* proves the second. A deploy's verification must
end with an HTTP request through the real entry point, plus an explicit assertion that the container
is attached to the network its proxy can resolve it on. A container that is healthy but unreachable
looks exactly like an outage to every user, and no amount of container-state checking will say so.
