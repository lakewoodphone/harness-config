**L3418 · Edge honours --window-size but NOT --window-position when handing off to an already-running profile - the manifest grid does not survive**

Measured ZABZ-YOGA 2026-10-08 21:13.

Open-SlotWindow passes `--window-position=700,0` (slot 2's configured position) and
`--window-size=700,440` to Edge. The window that appeared measured `x=0 y=0 w=700 h=440` by
GetWindowRect - size honoured, position IGNORED, landing on top of the slot-1 window that was
already at 0,0. Same run, same profile (_shared), handed off to the already-running browser process.

This CONTRADICTS the comment sitting above those arguments in Open-SlotWindow, which says the
geometry "only takes effect because each window has its own --user-data-dir" is wrong and that "Edge
applies --window-size/--window-position to the window it opens" (claimed verified 2026-09-18). What
holds is the shape of the launch, not the claim: with a shared profile and a live browser, size is
applied and position is not, so the manifest's 4x2 grid does not survive a handoff - new windows
stack at 0,0.

Consequence for anyone reading a screenshots-based layout: do not assume slot N is where windows.json
says. If the grid matters, the launcher has to move the window itself after it appears (SetWindowPos
on the handle it just created), or the browser must be started fresh per window. Nothing was changed
for this yet - it is recorded so the next person does not trust the comment.
