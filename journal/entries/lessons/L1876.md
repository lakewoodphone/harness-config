WARNING - A FILE THAT IS IDENTICAL ON TWO MACHINES PROVES NOTHING ABOUT LOCATION.
C:\Windows\win.ini is byte-identical on ZABZ-YOGA and ZABZ-TECH (sha256
6B3D6E268DCB76E175A7DB3D9E031349AB2C32654C7E57581A851E64DD6214AB on both). A child quoting its first
line looks like location evidence and is not. Always pick a per-machine witness and have the CHILD print
a hash of it: C:\Windows\System32\drivers\etc\hosts, or a file that exists on one machine only.

MEASURED, rpc shapes through the phone gate on the resident engine (read this before writing a script):
- GET http://127.0.0.1:3086/ mints the cookie; a cold read of the engine directly is 401. Use -NoProxy.
- POST /api/<method> with {type:'client-request', rpcId:<uuid>, method:'<method>', payload:{args:<hashtable>}}.
 args maps by PARAMETER NAME: session/create and session/prompt take `request`, session/list takes `_request`.
- GET /api/session/list and GET /api/tools do NOT exist (404 from the engine, not from the gate); only the
 POST-RPC form works.
- A WebRequestSession serialised with Export-Clixml cannot be re-imported into -WebSession
 ("Deserialized.Microsoft.PowerShell.Commands.WebRequestSession"). Store the cookie NAME and VALUE as
 strings and pass them as a `Cookie` header.

MEASURED, the counters, 45 samples across two dispatches plus an idle window (all on ZABZ-YOGA):
- engine /healthz sessions.subagents reads 0 in EVERY sample, including samples with
 agentLoopsRunning: 3. It is blind to a dispatched child - it counts only the RESIDENT engine's own
 subagent rows. This confirms 84-calibration.md 5.2 directly.
- agentLoopsRunning is NOT blind to a dispatch, but what it rises by is the PARENT's loop (1 -> 2 -> 3),
 not the child's. Do not read it as a child counter either.
- The reliable "where did the work run" counter is the CLIENT's node.exe process count: 11 in every
 fleet sample of both runs; the child's process boot happened on the target.
- Commit on the client is NOT provably flat and a test that runs inside the resident engine cannot make
 it so: run 2's fleet window moved +0.886 GiB (range 1.612 GiB) while a 58 s idle window on the same
 machine with nothing dispatched moved 1.244 GiB of range and -0.888 GiB net. The cause is identifiable:
 the acceptance session's OWN parent loop (session-e34dd061) was generating steps in the same window,
 and the sampler itself costs one Get-Counter + one healthz + one session/list per sample. Record the
 commit numbers and say "consistent with the machine's own noise", never "flat".
