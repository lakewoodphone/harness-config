**L12272 · An active health check on a single upstream is an outage amplifier: a 60s interval turned every deploy into a minute of 503s - and my own hardened gate refused to certify it**

A defect I introduced today, caught by a gate I also introduced today. Worth recording because the shape recurs.

WHAT HAPPENED. Installing the versioned Caddyfile brought `health_uri /api/health?scope=liveness` to the live edge for the
first time - the repo had carried those health checks since 2026-10-21 but the edge never received them. They came with
`health_interval 60s`. Caddy's active health checker marks a SINGLE upstream DOWN when a check fails, and with a 60-second
interval the next check is up to a minute away. A deploy recreates the container, the check fails during the restart, and
Caddy serves 503 to EVERY visitor until the next probe. Measured: after deploying f451876, `/api/persistence`,
`/api/assess`, `/api/feedback` and even `GET /` all returned 503; `docker ps` said `Up 24 seconds (healthy)` and
`curl 127.0.0.1:3006/api/health` returned 200 the whole time. 45 seconds later the public site returned 200 with no action.

CONSEQUENCE THAT MADE IT VISIBLE: the deploy script's anonymous-lockout probe (which I hardened this morning so it can no
longer pass silently) failed every check and exited non-zero - "AT LEAST ONE CHECK FAILED". So the gate did its job: it
refused to certify a deploy while the site was serving 503. Without that hardening this would have shipped as a green deploy
with a minute of downtime nobody looked at.

FIX. `health_interval 5s`, `health_timeout 2s` on both personality vhosts. Validated with `--adapter caddyfile` (a .new
suffix makes Caddy assume JSON and fail - use the adapter flag), reloaded, verified: public 200 and ALL ANONYMOUS CHECKS PASS.
Committed e66a97e with the Caddyfile in the repo updated to match.

RULES WORTH CARRYING.
1. An active health check on a SINGLE upstream is an outage amplifier: its interval is the worst-case outage you accept on
 every restart. Choose the interval as a downtime budget, not as a courtesy.
2. Deploying is a restart. Any edge configuration that reacts to a restart must be sized for the restart, and the probe that
 validates the deploy must run AFTER the edge has recovered, not during it.
3. A gate that can fail is only useful if you read its output: this one printed 13 FAIL lines and the deploy script exited 1,
 and the deploy itself had already happened. Say plainly in any report that a failed gate after a completed deploy is an
 OUTAGE finding, not a deploy finding.
