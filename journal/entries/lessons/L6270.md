**L6270 · A credential move is a permission change: two bugs a probe caught that would have failed the first real deploy**

Two real bugs in my own new code, caught before shipping, by one throwaway workflow that ran the
real step text against the real secrets. Both would have failed on the FIRST real deploy, and both
would have read as something other than what they were.

MEASURED 2026-10-16, building the GitHub-hosted deploy path for lpt-website. A probe workflow
(`on: push` to the working branch) ran the exact "Materialise the deploy credentials" step and then
ssh'd to the deploy target. It failed twice, each time for a different reason:

 1. `cut: /etc/lpt-deploy/env: Permission denied` - the step wrote the credential file
 `sudo install -m 600 -o root -g root`. But every step that READS that file sources it
 (`set -a; . "$ENV_FILE"; set +a`) as the UNPRIVILEGED runner user. On the box being replaced
 the file was owned by `ghrunner` - the same user the runner ran as - so this failure mode
 could not exist there and did not occur to me.
 2. Still denied after fixing the file's owner, because `sudo install -d -m 750 /etc/lpt-deploy`
 created the DIRECTORY as `root:root 750`, which grants a non-root user no access at all, so a
 file owned by the job user inside it was still unreachable.

WHY THIS IS THE GENERAL LESSON, AND NOT A STORY ABOUT ONE FILE. Both bugs sat behind a step that
reported **success**. The materialise step printed "credentials materialised" and went green; the
failure appeared one step later as `Permission denied`, in a workflow whose next failure mode is
`MISSING: <SECRET> is empty` - so the natural reading of a red deploy here is "a credential is
missing", and the actual cause was file permissions. **A step that succeeds while leaving the thing
it produced unreadable is worse than one that fails.**

THE RULE: when you move a credential's LOCATION, re-measure the contract around it - who writes it,
who reads it, and AS WHICH USER. Ownership and directory traversal are part of the interface. And
when you build a new path for something that must work unattended, run its real step text against
its real inputs once BEFORE shipping, on the platform that will run it.

THE TWO FACTS WORTH REUSING:
 * `os.replace`/`install` style moves hand the destination the SOURCE's mode and owner - check both.
 (Same shape as L5920: `os.replace(tmp, target)` stripped a 0755 script's execute bit.)
 * `install -d -m 750 <dir>` with no `-o`/`-g` is `root:root 750`, and **750 gives "other" no
 traverse** - so a non-root process cannot reach anything inside it however the file is owned.
 If an unprivileged job must read from a directory, the directory needs `-o "$(id -un)"`,
 not just the file.

AND THE PROBE WAS WORTH ITS COST FOR A THIRD REASON: GitHub's own annotation on that first run
said *"The ubuntu-latest label will migrate to Ubuntu 26 beginning October 19, 2026"* - three days
away. Reading the run's output rather than just its conclusion is what caught it, and the image is
now pinned to `ubuntu-24.04` so the deploy cannot be broken by an unannounced platform move.
