**L1573 · PowerShell to ssh: pass multi-line scripts on stdin, never as an argument, and never end a line with 2>&1**

**Rule.** From PowerShell on Windows, never pass a multi-line shell script to `ssh <host> "bash -s"` as an
*argument*, and never let a script line end in `2>&1` or contain unescaped `$( )` when the string travels
through a PowerShell double-quoted argument. Write the script to a file and pipe it, or use one single-line
command.

**Evidence, 2026-09-15 (ZABZ-TECH), three failures in one session, all self-inflicted:**

1. `ssh secretary "cd repo && ..." @'...'@` — a here-string placed *after* the remote command becomes an
 argument to `bash -s`, not stdin. `bash -s <arg>` sets `$0` and then **reads stdin forever**. The call
 hung and was killed at the 120 s timeout. The fix is `Get-Content -Raw file | ssh host "bash -s"`.
2. Piping a multi-line script whose lines end in `2>&1` produced
 `bash: line 12: 1: ambiguous redirect`. The redirect was mangled on the way through, so the command
 ran half-parsed. Two separate calls died this way, including one that silently lost a whole query.
3. `ssh host "echo \"$(grep -c x /f)\""` — PowerShell evaluated `$(...)` **locally**, so the command ran
 against the Windows filesystem and returned `grep: The term 'grep' is not recognized`. The remote host
 was never asked. The correct escape is `\$(...)` inside a double-quoted argument, or better: put the
 script in a file.

**Why it is expensive here.** Every one of these looks like a *remote* failure in the transcript, so the
instinct is to debug the remote side — and I did spend calls re-running things. It is the same shape as this
system's recorded worst habit: a check that reports failure for a reason that has nothing to do with what it
claims to be checking. The journal already carries the sibling (`$LASTEXITCODE` read after a pipeline
reports the last command's code), so this is a family, not an incident.

**How to apply.**
- Multi-line remote work: **write a local `.sh`, pipe it with `Get-Content -Raw | ssh host "bash -s"`.**
 (Adding a `sed 's/\r$//'` on the remote side is wise because Windows tools may introduce CRLF.)
- One-off remote queries: one line, no `2>&1`, no nested `$( )`.
- If a remote command fails in a way that does not match the command you wrote, suspect the transport
 before you suspect the host.
