**L3752 · A memory ceiling tight enough to kill the job is not a guard - measure the unit's real need before setting one**

## 2026-10-12, secratary-cloud

I set MemoryMax=3.5G on transcript-archive-pull to stop it from OOM-killing the host
(14 kills in 24h, one unclean hard reset). It worked - and it killed three consecutive
passes, because that unit needs roughly twice 3.5 GB when it has real work to pull.
A guard that prevents the job from ever finishing is not protection; it is a second
outage with a different name.

The first pass after raising it to 6 GB: Result=success, MemoryPeak=106,725,376 bytes
(102 MB), 2 min 27 s, and it removed two spools whose ingests were recorded ok=1.

MEASURED FACTS, so the next session does not have to re-derive them:
 * The unit's memory is BIMODAL, not steadily large: 102-313 MB when the archive is
 near current, 7.4 GB when it ingests one of the 50 MB+ Copilot chat files
 (AGENTS.md section 1 records 14 such files; a 50 MB .jsonl.zstd expands to
 multi-gigabyte text).
 * Harnessing it: transcript-archive-server.py:decompress_zstd(raw: bytes) holds the
 compressed object AND then b\"\".join()s the whole decompressed text. The subprocess
 fallback uses capture_output - same shape. That is the 7.4 GB, in one function.
 * company-api from a cold start: 1.5 GB -> 2.8 GB in five minutes, then 37 MB/min
 decaying to 15-20 MB/min. It settles around 3.3 GB. LARGE WORKING SET with slow
 growth - a leak was NOT established, and that is worth saying plainly rather than
 repeating as fact.

RULE: before capping a unit, sample its own MemoryCurrent across at least one full
work cycle ('not set' is what systemctl prints for an inactive unit - guard the
arithmetic). Set the ceiling above the observed real peak, not at a number that feels
safe on a box that is in trouble. scripts/archive-pass-watch.sh does the sampling.
