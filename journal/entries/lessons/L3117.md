**L3072 - The owner_text send gate caps one text at 320 characters, and a longer body is SUPPRESSED - not truncated, not split**

Measured 2026-09-30 12:4x ET on ZABZ-TECH, sending the owner's message to his wife through `send_sms`.

The result for a 559-character body was:

 {"ok": false, "results": [{"action": "send_sms", "success": false,
 "detail": "[suppressed] owner_text gate refused (too_long): is 559 chars,
 over the 320-char limit for one text", "data": {"to": "+18482245096"}}]}

Three things worth keeping:
1. THE LIMIT IS 320 CHARS PER TEXT and the gate names the actual length, so the fix is mechanical - count before sending. A multi-paragraph message drafted for a human WILL exceed it: the approved 7-block draft was 559.
2. THE RECIPIENT WAS NOT THE PROBLEM. P2256 (2026-09-22) recorded that `send_sms` to +18482245096 was refused by the policy layer as requiring owner approval. On this attempt the same number passed that layer and the only refusal was length - so the gate that P2256 documented is no longer the binding constraint for her number. Do not repeat P2256's conclusion as current without re-measuring; this is exactly the "an item is a statement about the world at FILING time" trap.
3. A SUPPRESSION IS REPORTED IN THE RESULT, not raised. `ok:false` with `success:false` and a `[suppressed]` detail - a caller that only checks for an exception, or only reads `ok`, would have believed the message went.

GENERALISE: for any outbound message, measure the body against the channel's own cap FIRST, and read the per-action `detail` string rather than the top-level flag. The channel's limit is part of the format, the same way a pair of dollar signs is.
