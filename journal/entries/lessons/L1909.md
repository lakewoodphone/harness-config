**L1909 · Two real customers are silently dropped by the sync-record reader: a snake_case record_type and a string device**

## What it is

Two records in `docs/customer-operations/sync-records/` are **silently dropped** by the reader
`app/services/lpt_hub_sync.py`, so their customers are invisible to the running company even though
the records exist, parse as valid JSON, and name a real person with a real phone number.

Reproduced live on 2026-09-17 by calling the service's own loader on the authority:

```python
from app.services import lpt_hub_sync as m
recs = m.fetch_sync_records() # -> 380 of 381 files
```

stderr, verbatim:

```
Sync record lp140wfh-screen-gutterman-2026-09-01.json has wrong recordType: None
Sync record samsung-tab-s7-customer-2026-08-24.json has non-dict device (str) — coercing to {}
```

## The two records, exactly

**`lp140wfh-screen-gutterman-2026-09-01.json`** — customer **Gutterman**, phone `+17326301660`,
device a laptop needing a replacement LCD panel. It carries `record_type` (snake_case) where the
reader requires `recordType` (camelCase), so `recordType` reads as `None` and the record is
rejected. Its top-level keys are:

`customer, date, device, notes, order, panel_confirmation_note, quote_needs, quote_status,
record_type, service_tag, shipped_panel_module, sourcing_options, task_id`

— i.e. it is a **different schema entirely**, not a typo'd one: no `caseId`, no `version`, no
`updatedAt`, no `sourcePath`, and no `references` matcher.

**`samsung-tab-s7-customer-2026-08-24.json`** — customer name `TBD (customer_name_unknown)`, phone
`+13479885577`, a Galaxy Tab S7. It has the right `recordType: customer-case-sync-record` and a
`caseId: samsung-tab-s7-screen`, but is missing `version`, `updatedAt` and `sourcePath`, and its
`device` is a **string** where the schema requires an object (`"device": {"summary": ...}`), so the
reader coerces it to `{}` and loses the device description.

## Why this matters more than a schema nit

`GAPS-2026-09-16.md §D4` recorded that one non-conforming record "silently dropped by the reader"
was hiding customer Gutterman. It is still true. The failure is silent **by construction**: the
loader logs a warning to stderr and returns `[]`-style degradation, and an empty result is
indistinguishable from a genuinely empty corpus. A shop that asks "do we have anything for
Gutterman?" gets nothing back and no error.

This is the concrete case behind the owner's complaint that sync is unreliable: the record exists,
the customer is real, and the system answers "nothing found".

## The rule

**A record the reader rejects must be reported as a drift, never dropped in silence.** Two
requirements follow, both of which the replacement tool implements:

1. **Validation at write time** — refuse to write a record that the reader would reject
 (`recordType`, `version`, `caseId`, `sourcePath`, a `references` matcher, `operational`
 non-empty, `device` as an object). `tools/customer/record.py` validates before writing and
 raises `RecordInvalid` with the findings; `tools/case-index/lptcase.py:2613-2615` currently
 writes records its own schema rejects (`internalSummary: ""`, `nextAction: ""` against
 `minLength: 1`), so every scaffolded case is born non-conforming.
2. **A verify that counts rejections** — `customer verify` must report
 `records_rejected_by_reader: N` with the reason per record, and exit non-zero. Today the only
 signal is a stderr line nobody reads.

Note the pattern this is an instance of: the schema was already weakened twice to accommodate
writers (the `pricing` and `referral` blocks carry comments saying they are deliberately left open
because "records were already carrying this block and the closed root schema rejected them").
Weakening the schema to match the writers is how two real customers were lost. The fix is one
writer plus validation, not a looser schema.
