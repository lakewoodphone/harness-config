# A mesh child's whole report is discarded if it does not open with `MESH-HOST: <hostname>`

Measured 2026-09-20 on ZABZ-YOGA.

I dispatched a mesh child (tool `subagent`, the remote provider) with a completely normal brief. The
child ran the whole task and then finished, and the job settled:

 [status: failed, error; diagnostic: the child did not begin its report with
 "MESH-HOST: <hostname>" — its location is unproven, so the run is not reported as complete]

and `job_output` returned **no output at all** — not the report, not an error, nothing. The work was
gone and had to be re-dispatched.

**The rule the harness is enforcing, and it is right to enforce it:** on the mesh, a result's
*provenance* is part of the result. A remote child's location is unproven unless the child says where
it ran, and an unproven location makes the run un-reportable — it is the same principle as P3
("reading the wrong data and believing it"), applied to *where the work happened*.

**What this means for every brief I write:**

1. The **first instruction** of a mesh brief is the output contract, stated before the task:
 *"FIRST LINE OF YOUR FINAL REPORT MUST BE EXACTLY: `MESH-HOST: <hostname>`. No preamble before
 it. A report that does not begin with that marker is discarded as unproven-location."*
2. A structure asked for at the *end* of a long brief is not reliably followed; the marker must be
 the first thing the child reads.
3. Check the marker first when a mesh job reports. No marker -> re-dispatch, and say in the report
 that the first run was void rather than quoting anything from it.
4. This is a **harness-enforced** rule, not a convention — a brief without it can burn a child's
 whole turn for zero information, and the failure looks like an infrastructure error rather than
 a missing sentence in a prompt.

Recorded because the cost is invisible in the wrong direction: the child believes it reported, and
the parent sees an empty result.
