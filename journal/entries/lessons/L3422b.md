**L3422b · A systemd timer that is enabled but not started has an EMPTY next-elapse and will never fire**

MEASURED 2026-10-13 on secratary, and it is exactly the trap the LPT books deploy README
warns about.

`systemctl enable lpt-books-nightly.timer` creates the timers.target.wants symlink and reports
success. `systemctl list-timers lpt-books-nightly.timer --all` then prints NEXT `-` LEFT `-`
and `systemctl show ... -p ActiveState` reads `inactive`. That is an installed-looking timer
that will never fire. `enable` alone does not start a timer; `enable --now` does.

Proof lines, same unit, two minutes apart:
 before: ActiveState=inactive NextElapseUSecRealtime= NEXT -
 after : ActiveState=active NextElapseUSecRealtime=Tue 2026-10-13 07:26:59 UTC

The other half, also measured the same night: `OnCalendar=*-*-* 00:10,06:10,12:10,18:10:00 UTC`
is INVALID. `systemd-analyze verify` says `Failed to parse calendar specification` and the unit
refuses to start with `Timer unit lacks value setting`. systemd wants one OnCalendar line per
time, each with its own seconds field.

So after installing any timer, the verification is three commands, not one:
 systemd-analyze verify /etc/systemd/system/<name>.timer
 systemctl list-timers '<name>' --all --no-pager # NEXT must be a real timestamp
 systemctl show '<name>.timer' -p ActiveState -p NextElapseUSecRealtime

And a fourth for anything that must actually run: start the service ONCE by hand and read the
run log, because a timer that fires into a broken service is the same outage with a schedule.
