**L3642 · A dry run that applies a different guard than the real run is not a preview, and it cost me a false number**

Measured 2026-10-13 on the statement backfill importer
(`/opt/company/app/services/statement_csv_import.py`). This is the highest-value kind of finding:
a tool that reports a number the operator will act on, and reports it wrongly.

THE OBSERVATION THAT CAUGHT IT. I dry-ran six Chase statement exports against the live ledger and
got, per file: chase9650 two-year export `inserted 541`, chase3929 `209`, chase7542 `66` and `66`,
chase9680 `92`, chase-college-9730 `72` - about 1,046 transactions of "recoverable" history. I then
ran the SAME commands WITHOUT `--dry-run` and every one returned `inserted: 0`, with
`skipped_cross_source` equal to the file's whole row count. The ledger's transaction count did not
move: 8,648 before, 8,648 after.

THE CAUSE. The two code paths used different duplicate guards:

 dry run (line ~275): WHERE account_id = ? AND transaction_date = ? AND amount_cents = ?
 real run (line ~340): WHERE account_id = ? AND transaction_date = ? AND ABS(amount_cents) = ?

Sign-sensitive versus sign-insensitive. The real guard is the correct one and its own comment says
why: canonical_hash embeds the description, so the same physical transaction from two sources hashes
differently, and this estate already holds 91 (account, date, |amount|) collisions on lpt-chase-5578
alone. A sign-sensitive guard had previously added 45 rows there where only 12 were genuinely new.
The preview was the defect - it over-reported by exactly the rows the real guard refuses.

WHAT IT WOULD HAVE COST. An operator reading "1,046 recoverable" would either report a recovery that
never happened, or, believing the preview, reach for `--allow-same-day-duplicates` to force the
insert - which is the flag that writes the duplicate rows this guard exists to prevent. A wrong
preview is worse than no preview, because it manufactures the justification for disabling the guard.

THE FIX. The dry-run query now uses `ABS(amount_cents)` too, so the preview and the real run answer
the same question. Re-measured after the fix: every one of the six files reports `inserted 0`.

WHAT THAT SECOND MEASUREMENT MEANS, and it is the real news: **the ledger is more complete than the
coverage matrix suggested.** These statements add nothing - the books already hold those rows, via
Plaid and via earlier imports. So the 21 reconciliation disagreements are NOT missing statement rows
on these accounts; they are more likely bad balance readings or missing Plaid-side rows. That is a
different investigation than the one I was about to run.

RULE. When a tool has a preview mode, the FIRST thing to prove about it is that preview and real
answer the same question. Run both on the same input and compare, before trusting either number.
