**L4067 · The EPIPE crash reproduces LOCALLY in 70 seconds on one trivial file - the pool is ruled out and the loop is now cheap**

**The EPIPE crash reproduces LOCALLY in ~70 seconds, deterministically, on one trivial test file — which turns a 15-minute-per-cycle CI investigation into a 70-second loop, and rules the pool out.**

This is the most useful thing to come out of the CI investigation, and it was found only after the CI
cycles had already ruled several things out.

THE REPRODUCTION. In `C:\Users\ezabz\code\_w33-faqcredit` (branch off `origin/test` at `7339439a7`):

```
pnpm test:frontend:one -- frontend/src/brand/__tests__/brand-assets.test.ts
 -> exit 0
 -> Test Files 1 passed (1) Tests 60 passed (60)
 -> Duration 68.24s (transform 2.08s, setup 12.58s, import 348ms, tests 228ms, environment 48.83s)
 -> [vitest-pool]: Timeout terminating threads worker for test files .../brand-assets.test.ts.
```

**Read what those numbers say.** The tests took **228 ms**. Environment took **48.83 s** and setup
**12.58 s**. Then the worker **would not terminate**. A file that does nothing but assert string
constants still produces the wedge.

WHAT THIS RULES OUT, and it is now measured rather than argued:

- **It is not the pool.** The line above was produced with `pool: 'threads'`. With `pool: 'forks'` the
 same single file also wedges (and in CI that wedge escalates to the unhandled EPIPE). The `threads`
 experiment was reverted; `frontend/vitest.config.ts` is unchanged at `pool: 'forks'`.
- **It is not a heavy or misbehaving test.** 60 assertions on string constants wedge the worker.
- **It is not memory pressure, worker count, `maxWorkers`, a specific test file, or the JS heap cap.**
 One worker, one trivial file.
- **It is not CI-specific.** The wedge is local and deterministic; only the *escalation* to an
 unhandled `write EPIPE` is CI-specific.

WHAT IT IS: **a worker whose event loop never empties after its file finishes.** Vitest waits
`teardownTimeout` (3 s locally, 30 s in CI), gives up, and then something sends to the dead worker —
which is `PoolRunner.stop` -> `ForksPoolWorker.send` -> `ChildProcess.target.send`, the unhandled EPIPE
that kills the whole process before it can print a summary.

AND THE REPOSITORY ALREADY KNOWS THIS, in its own comments — which is why it has two force-exit escape
hatches and a pile of global mocks:

- `frontend/vitest.config.ts`: *"with pool: 'forks', orphaned handles in worker processes can prevent
 the main Vitest process from exiting cleanly"*;
- `frontend/src/reporters/force-exit-reporter.ts`: *"Ably/Twilio SDKs open persistent WebSocket/TCP
 connections (3 Socket handles) that keep the Node.js event loop alive after tests complete"*;
- `frontend/src/test-setup.ts`: *"GLOBAL SDK MOCKS - PREVENT SOCKET/WEBSOCKET CONNECTIONS"*, plus a
 `[CI test-setup] Delayed cleanup: closed 1 more Socket(s)` message that appears in the CI logs.

**So the diagnosis is: the SDK mocks stop the sockets CONNECTING but something still leaves the event
loop non-empty, and every fix so far has been a global escape hatch at the END of the run rather than a
per-file close. The two force-exits cannot help, because the run never reaches the end - the process dies
at a per-file teardown (see L4000).**

THE NEXT STEP, and it is now cheap: with a ~70 s loop, bisect `frontend/src/test-setup.ts` and
`test-setup.ci.ts` for the handle that survives. Candidates visible in the file: the global
`WebSocket` mock (line ~792), the Ably mock (~36), the Twilio Voice mock (~121), and whatever the
`afterAll` at line 538 does and does not close. **Run the single file after each removal and watch for
`Timeout terminating forks worker` to disappear.** That is the whole test.

DO NOT re-run CI cycles to investigate this. The CI tells you the escalation; the laptop tells you the
cause.
