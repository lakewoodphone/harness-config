**L3423 · A generated .cmd launcher must CALL a config line that is already a whole set statement - call set "%%L" defines a variable named 'set'**

**A generated Windows `.cmd` launcher must CALL a config line that is already a whole `set`
statement. `call set "%%L"` silently defines a variable named after the word `set`.**

`install.ps1` writes `env.cmd` containing whole statements (`set LPT_AUTHORITY_SSH=secratary-ts`,
`set LPT_PYTHON=…`) and the launcher read them with:

```
for /f "usebackq delims=" %%L in ("%LPT_CONFIG_CMD%") do ( call set "%%L" )
```

With `%%L` = `set LPT_AUTHORITY_SSH=secratary-ts` that expands to
`set "set LPT_AUTHORITY_SSH=secratary-ts"`, which cmd accepts and defines a variable whose **name is
`set LPT_AUTHORITY_SSH`**. The real `LPT_AUTHORITY_SSH` is never set, so `transport.py` falls back to
its default `secratary` — the **office LAN alias** — and every installed machine reported
`DOWN operational … ssh exit 255: banner exchange: Connection to UNKNOWN port -1: Connection timed
out` while `ssh secratary-ts hostname` answered in under a second from the same shell.

This is the failure shape to remember: **a config that is silently ignored looks exactly like an
unreachable server.** The fix is `call %%L`, and the diagnosis is worth repeating — when a tool says a
host is unreachable, run the tool's own ssh command by hand before believing it.

Finding it took two wrong turns worth recording:

- `lpt doctor` blamed the store. `lpt doctor` was right about what it could reach and wrong about
 why. The **route is part of the answer**, which is why `transport.py` prints it, and it printed
 `ssh secratary` while the working alias was `secratary-ts`.
- `install.ps1`'s own probe reported *"no ssh alias answered"* for `secratary-ts`, which does answer:
 the probe runs its ssh from inside the installer's process. Re-run the probe's exact command
 (`ssh -o BatchMode=yes -o ConnectTimeout=8 secratary-ts hostname`) by hand before believing the
 installer.
