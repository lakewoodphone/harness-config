**L1880 · synced counters counted no-ops as writes (1166 claimed, 0 rows across three runs) and r[0] on a RealDictRow raises KeyError(0) whose str is '0' - so an except that returns [] made my dedup guard inert for a day**

LESSON: `synced` counts and Python row access both lie in this codebase, and both lies are silent.

EVIDENCE, all measured 2026-09-17 on production (Heroku `PHONE_TECH_FULL_DATABASE_URL`)

1. **A `synced` counter that counts a no-op as a success.**
 `website_db.insert_communication` returns `{"ok": True, "skipped": "duplicate"}` for a row it did
 NOT insert, and every caller does `if result.get("ok"): synced += 1`. Measured consequence:
 **three consecutive clock runs each reported `calls synced 320, sms synced 846` while the
 `communications` table stayed at exactly 117,584 rows.** 1,166 claimed writes per run, zero rows.
 After the fix, same run, same candidates: `synced=0, skipped_dedup=320 / 846`.
 *Rule:* when a function can succeed without doing the thing, its caller must distinguish them, and
 **the only proof of a write is a row count**, not a return value and not an exit code.

2. **`r[0]` on a `psycopg2` `RealDictRow` raises `KeyError(0)`, whose `str()` is `"0"`.**
 `_get_pg_connection` uses `cursor_factory=RealDictCursor`, so `fetchall()` yields dicts keyed by
 column name. My `[(r[0], r[1]) for r in cur.fetchall()]` raised on every call; an `except` caught it,
 logged `"ref lookup failed for ...: 0"` and **returned an empty list** — which reads exactly like
 "no rows found". So a dedup guard I wrote to prevent a duplicate class was **inert in production for
 a day**, and the symptom (the log line) looked like a legitimate empty result.
 *Rules:* index dict rows by column name; **an `except` that returns an empty collection turns a
 crash into a plausible answer** — that is the most dangerous shape in this system, because an empty
 result is indistinguishable from health. And when a log line says an operation failed, `"0"` is a
 `KeyError`, not a count.

3. **`NULL = anything` is never true in SQL, and this is not a footnote here.**
 `_communication_exists` dedups with `WHERE "customerId" = %s AND external_ref = %s`. A row stored
 with `customerId IS NULL` (because the phone matched no customer) is invisible to that check, so when
 a customer later appears for that phone the sync **inserts a second row**. That produced six
 duplicate pairs in production. `IS NOT DISTINCT FROM` is the correct operator for a dedup key.

4. **The three lies compound, and the compounding is the actual danger.** Because (2) was inert, the
 guard in (3) never ran; because (1) counted no-ops as writes, the clock reported success the whole
 time. Net effect: a customer-facing pipeline that reported work it was not doing, guarded by a
 check that never executed, and the only thing preventing duplicates was a third mechanism nobody
 had credited. **Each defect was invisible on its own.** Only a row count across three runs exposed it.

HOW TO APPLY THIS

- Verify a write pipeline by **counting rows before and after**, and by checking that a counter
 *decreases* when it should (here, that `synced` fell to 0 while `skipped_dedup` rose to the candidate
 count). A counter that never moves is not evidence of health.
- Never let an `except` return `[]`, `{}`, `None` or `0` on a lookup that a guard depends on. Either
 raise, or return a sentinel the caller must handle; a silent empty is how a guard dies unnoticed.
- When code touches Postgres through this app's helpers, assume `RealDictRow`. Index by name.
- Treat "runs, exits 0, produces nothing" as a **first-class failure mode of this system** — it is the
 same shape as the dead `autopilot` trigger (no successful run since 2026-08-20) and the
 `dialpad_ui_voicemail_row` table (3,036 rows, stale to 2026-06-14).
