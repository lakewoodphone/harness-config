**L2090 · pkill -f kills your own ssh session when the pattern is in the command line you sent**

**L · 2026-09-20 · ZABZ-YOGA — `pkill -f` kills your own ssh session when the pattern is in the command line you sent**

**What happened.** Killing a runaway `cp` on the authority:

```
ssh secratary-ts "ls -la ...; pkill -f 'cp /home/zabz/personal-secretary-mvp/data/secretary.db'; sleep 3; ..."
```

The remote side runs the command as `bash -c "<the whole line>"`, so the **bash process's own command line
contains the pattern**. `pkill -f` matched it and killed the shell that was running the command: the output
stopped after `CONNECTED` and the file listing, and the ssh session exited 1 with no error. The `cp` was
killed too, so the tool did part of its job — but every command after it was silently lost, including the
cleanup and the verification, and it looked like a network failure.

**The rule.** When killing by pattern over ssh, make the pattern not match its own command line:
- bracket one character — `pkill -f 'oq-tes[t]'` matches `oq-test.db` but not the literal string in the
 shell's argv;
- or kill by pid (`pgrep -f 'pat[t]ern' | xargs -r kill`) after listing it;
- or put the pattern in a file/env var the command line does not spell out.

**Second half of the same trap: a silent partial success.** The command *did* kill the process, so the
session looked like a transport failure while the intended side effect had happened. After any remote
command that dies mid-flight, re-read the *state it was supposed to change* rather than re-running it
blindly — here, `pgrep -af 'oq-tes[t]'` and `ls -la` — because "the ssh session died" and "nothing
happened" are different facts.
