**L6243 · A USB stick 10x slower on many files than on a sequential probe: vm.dirty_bytes tuning doubles it (27h -> 5h), and nr_requests is clamped to 1 on usb-storage/BOT**

**L · A stick that measures 19 MB/s sequentially can be DOUBLED on a many-file copy by tuning the kernel's dirty-page limits. And on a `usb-storage` (BOT) device, `nr_requests` is a dead end.**

Measured 2026-10-15, Raitzik delivery, medium = **PNY "USB 3.2.1 FD" 248 GB, exFAT, 128 KiB clusters,
`usb-storage` (BOT) driver, `queue_depth=1`**.

**The puzzle.** The medium probe — 6 GB `dd oflag=direct`, sampled every 10 s from the kernel counter —
gave **19.1 MB/s with zero stalled windows**. The real delivery through `rsync` gave **1.4 then 2.5 MB/s**,
a **27-hour** projection for 241 GB. Over the same 90-second window the *source* (an SSD on USB) read
**0.0 MB/s** while the stick wrote 2.5 MB/s with **1.7 GB dirty**: rsync was fully read-ahead, so the copy
was gated entirely on the medium's write path, and it was **not** a small-file phase — the open file was a
single **305 MB** blob.

**The A/B, run on an idle device, each measured from `/sys/block/sdd/stat` field 7 plus the dirty drain:**

| pattern | MB/s |
|---|---|
| one 256 MB file, buffered | 5.4 |
| one 256 MB file, `O_DIRECT` | 9.8 |
| 512 x 512 KB files, buffered | 5.7 |
| **512 x 512 KB files, `vm.dirty_bytes=16M` + `vm.dirty_background_bytes=8M` + `rotational=0`** | **12.8** |
| one 256 MB file, same tuning | 11.6 |
| **the real delivery, with the tuning live** | **13.1 → 14.8** |

**27 hours became about 5.** The win is the dirty-page limit: with a big dirty allowance the kernel
buffers ~1.7 GB and then flushes it in inode order, which on a cacheless medium is scattered
read-modify-write; with a 16 MB limit the flusher has to keep up with the writer and the LBAs stay
close to write order.

**`nr_requests` is not a lever here.** The doc's §7 test says "raise `nr_requests`", but on this device
writing 128 was **clamped to 1** by the kernel, because the stick is on `usb-storage` (BOT) — one command
in flight, no queue to deepen. That advice only applies to a **UAS** bridge. Check which driver you have
before spending time on it: `lsusb -t` shows `Driver=uas` or `Driver=usb-storage`.

**Rules to carry:**
1. **Before blaming a medium, tune and re-measure on an IDLE device.** Both counters: sectors written
 from `/sys/block/<dev>/stat` field 7, and the dirty drain from `/proc/meminfo`.
2. **Set `vm.dirty_bytes=16777216` and `vm.dirty_background_bytes=8388608` for a large many-file copy onto
 flash, and `rotational=0`.** Measure before and after; do not assume it helps every medium.
3. **Restore the sysctls afterwards — and know that `dirty_bytes=0` is REFUSED while `dirty_ratio` is 0**
 (writing a non-zero `dirty_bytes` zeroes `dirty_ratio`). The working restore order is
 `dirty_background_bytes=0`, then `dirty_ratio=20`, then `dirty_bytes=0`, then read all three back to
 prove it. A shop bench with a global VM tuning left behind affects every later job.
4. **The copy's own progress line is not the measurement** (it counts page-cache bytes), and neither is
 `df` used-space: at one point the stick showed 2.2 GB "used" while the device had received ~100 MB.
