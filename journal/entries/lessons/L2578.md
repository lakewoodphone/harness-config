**L2578 · Health 200 while the database refused every write: a read-only health check cannot see a company unable to record anything**

**L · 2026-09-25 · ZABZ-YOGA — `/health` answered 200 for over an hour while the database refused every write: a read-only health check cannot see the company being unable to record anything**

**Measured.** At 2026-09-25 03:35Z a one-row `UPDATE` probe on the authority's database could not take the write lock in 8 seconds, and 10 seconds on a second attempt; a third attempt after killing my own process failed identically. Meanwhile:

- `curl http://127.0.0.1:8002/health` → **200**, `{"ok": true, "database": {"ok": true}}` — because the DB probe in `/health` only reads.
- `error_log` held only five `database is locked` rows for the whole previous evening (18:31, 19:08, 19:59, 20:50, 21:00) — periodic, not continuous, and nothing at all from the window in which *nothing* could be written.

**The holder, found without guessing.** `/proc/locks` maps POSIX locks to pids and inodes:

```
8: POSIX ADVISORY WRITE 1880535 fc:01:4719397 120 120
```

`1880535` was the uvicorn process, `4719397` was `secretary.db-shm`, and byte 120 is SQLite's **WAL write lock**. A single pool connection inside the API had an open write transaction and never committed or rolled back. Everything else — my scrub, agent writes, ingest — was locked out for the life of that process (started 01:47Z, lock still held at 03:35Z). Restarting the service released it instantly: the same probe then succeeded in **0.02 s**.

**The rules.**
1. **A health check that only reads cannot prove health.** For any database, "can I write?" is a different question from "can I read?", and it is the one that matters for a company that records customers. Probe it: `BEGIN IMMEDIATE` then `ROLLBACK` takes the write lock and changes nothing. That is now kernel check 17, `db_writable` (`ceo-kernel` `94790ff`), HIGH when it cannot.
2. **`/proc/locks` names the holder.** When writes block and no process admits it, match the file's inode against `/proc/locks` and read the pid — `stat -c %i secretary.db-shm`, then the entry whose range starts at 120. This turned "SQLite is contended" into "this process, holding this lock, since this restart".
3. **The second-order damage is worse than the outage.** `error_log` under-reporting meant the failure had no history; a session that reads only `error_log` would conclude the database was healthy. A lock that is *held* writes no error — the refusal happens in the other processes, in code paths (P264's inbound SMS, my scrub) that treat `database is locked` as a transient and retry.
