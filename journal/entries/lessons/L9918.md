**L9918 · A service stopped and still stopped is a maintenance window: read ps for VACUUM/backup before restarting, and a quiet monitor is evidence**

## 2026-10-19 · ZABZ-YOGA · a service that is stopped and comes back stopped is a maintenance window, not an outage

Found company-api inactive on the authority, called it an outage, restarted it. Then it was inactive again eight minutes later, and I restarted it again. Both restarts landed **inside another session's 34 GB database compaction**, which had stopped the API deliberately so that it could `VACUUM INTO` a copy with no writers. The script's integrity gate then detected that the copy no longer matched the database, refused to swap, cleaned up and restarted the units. The database was never replaced and nothing was corrupted - but ten minutes of a 34 GB job was thrown away, by me.

THE TELL I MISSED, and it is cheap to check:

 ps -eo pid,etime,cmd | grep -E "compact|VACUUM|backup|restore|integrity"

The very first look showed `sqlite3 /root/authority.db VACUUM INTO '/root/authority.db.compact-tmp'` running with the same start time as the stop. That is the answer to "who stopped this", and it was printed on the same screen as the wrong conclusion.

SECOND TELL: the unit did not stay down by accident. `r4-liveness-probe` and `estate-monitor` did NOT escalate, because a clean stop by a maintenance job is not a fault they are meant to page on. A monitor that stays quiet is evidence, not absence of evidence.

THIRD TELL, and the one that should have stopped me: `systemctl stop` appears in exactly one script on this host - `compact-authority-db.sh` - and it restarts every unit on every exit path. If the API is down and that script is running, the API is coming back.

WHAT TO DO INSTEAD: when a unit is down on a host someone else is working on, run the `ps` check, read the maintenance script's own phase, and WAIT. Restarting a service during a database copy is not a neutral act - it invalidates the copy and wastes the job. If the outage is genuinely long, say so in the report and leave the database alone.
