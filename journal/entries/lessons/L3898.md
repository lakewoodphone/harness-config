**L3898 · Production write path: lpt-write is python3-only, help text lies, and the sync schema is stricter than the corpus**

Measured 2026-10-20 on ZABZ-TECH while reopening WO2608190005 for mrs woldiger (S20 FE, 85 port fix). Five things that cost time and will cost it again.

1. `lpt --help` advertises `lpt note add` and `lpt status set`. The installed shim's argparse accepts only doctor/ticket/case/wo/order/customer/cust/sql/photos - "invalid choice: 'status'". The help text documents two write verbs that do not exist in the reader. Do not follow it.

2. The writer exists only on the authority: /root/code/lpt-ops/bin/lpt-write, mode -rw-r--r-- (no exec bit), so calling it directly gives "Permission denied". Run it as `python3 bin/lpt-write ...` from /root/code/lpt-ops. Its own docstring says the guard is that you must NAME it, not that it is unrunnable - the missing +x is not the control.

3. Writes are dry-run by default and --apply is the only way to write. The dry run prints the real SQL and parameters; read it before applying.

4. Two misleading read-backs. (a) update_order HARDCODES the order_status_history reason as "Auto-updated by secretary reconciliation (confidence: 0.95)"; your --reason lands only in /root/lpt-ops/audit/writes.jsonl. (b) The note command's second-opinion read prints "NOT CONFIRMED: LPT_DB_A_DSN is set but psycopg2 is not installed on this machine" - that is the second opinion failing to run, NOT the write failing. Verify independently with `lpt ticket <WO>` from the client.

5. CUSTOMER_CASE_SYNC_RECORD.schema.json is much stricter than the existing corpus. additionalProperties:false at top level AND inside customer. `parts` is NOT a legal top-level key (373-byte gap: the older records carry it and are schema-invalid). `productionCustomerId` is not legal inside customer. Legal pricing keys are quoted/currency/quotedDate/structure/approvedByCustomer/paid/paidAmount/paidSource/usbCharge/usbChargeNotes/lineItems/note - so the older quoteTotal/partCost/labor shape is invalid too. references.workOrderId must be the INTEGER order id, not the "WO..." string.

Also: piping a Windows-authored .sh through `ssh host "bash -s"` dies with `bash: line N: $'\r': command not found` (exit 1) AFTER the remote commands have already run. Write the script with LF, or sed -i 's/\r$//' first. The exit 1 is the CR, not the work.

Worked and verified: `python3 bin/lpt-write status set --order WO2608190005 --status AWAITING_PARTS --reason "..." --apply` moved CLOSED -> AWAITING_PARTS, ledger seq 496, and `lpt ticket` then showed [AWAITING_PARTS] with the note count 3 -> 4. Read allowed statuses live: AWAITING_DIAGNOSIS, AWAITING_APPROVAL, AWAITING_PARTS, AWAITING_PAYMENT, READY_FOR_PICKUP, CANCELLED, UNFIXABLE, CLOSED.
