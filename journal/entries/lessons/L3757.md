**L3757 · A patch made against stale bytes is SUPERSEDED, not pending: re-measure the target's hash at install time (W6 owner-queue case)**

WHAT HAPPENED. W6 delivered three patches for the owner-queue intake defect (D-entry and
docs/owner-queue/). I went to install them and found two independent reasons not to install
two of the three:

1. THE PATCHES ARE AGAINST STALE BYTES. W6's README records the pristine sha256 of each
 target as it fetched them (read-only) at 2026-10-12 21:1xZ:
 owner-queue.py 183beb4731d7d3b205c053ebb253f2f15c220f54c8cf02e5e99e3cda262cf572
 wake-balance.py 66c5892d79fe564323e9125209472fad140d7b9875711ea8d69c83603fba5732
 Measured on the authority 2026-10-13T01:34Z:
 owner-queue.py e3086d0fcd1047968e99807621c5735399dce358f814ecbed7103664a29bdc73
 wake-balance.py 1f60cac40ee700f4e0e35720ac95c043f5e8067612b7042f32f797f29bd614c4
 Both MOVED between the two readings. They are not the files W6 patched, so the patches are
 SUPERSEDED, not pending. A patch does not carry the right to be applied; it carries a claim
 about a tree, and the claim expires when the tree moves.

2. THE INSTALL INSTRUCTIONS ARE WRONG ABOUT THE STRIP LEVEL. Every header reads
 `--- a/root/bin/owner-queue.py` / `+++ b/root/bin/owner-queue.py`. The README says
 `cd /root/bin && patch -p1 < ...`, which looks for `root/bin/owner-queue.py` under
 /root/bin and cannot find it (it needs -p3, or -p1 from `/`). Following the instruction
 literally made patch SKIP 0001 and 0002 -- and made 0003, whose header is the same shape,
 silently create `/root/bin/tmp/w6/owner-queue-sweep.py` instead of the target path.
 HARNESS RULE, and it is general: an installer that reads a path is not evidence that the
 path is right. Verify where a file ACTUALLY landed (`ls`) before believing `patch` or
 `install` succeeded; `patch` in particular reports success while writing elsewhere.

3. WHAT THE LIVE CODE ALREADY DOES, which is why 0001/0002 are moot. A duplicate `add` of the
 exact balance question printed "existing: ... answer: Same question as 288/308/313,
 answered by the owner 2026-10-08 ... Nothing was written." So the deployed owner-queue.py
 already refuses an exact duplicate and writes nothing, and the deployed wake-balance.py
 guard already declines to re-ask. The defect W6 measured was real when measured; by now the
 live code has moved past it.

WHAT I ACTUALLY DID
 * did NOT install 0001 or 0002 (superseded); left backups of the live files in place.
 * DID install 0003's result as a NEW file, because a new file cannot be superseded:
 /root/bin/owner-queue-sweep.py (sha256 3dff3f638c1c69ebf97244f24a67d73952b9fa97155b79e550cf4cb8970fd98e,
 py_compile OK, `--help` runs). It is the bulk-intake guard: one shop RULE -> one question,
 requires a stable `subject`, refuses a subject-less raw row, caps a run at --max-rows 3.
 * removed the stray /root/bin/tmp I had created, only after `cmp -s` proved the file in it was
 byte-identical to the deliverable I installed.
 * closed the last balance re-ask (#444) with evidence: rows 288/308/313 RESOLVED, the owner
 answered on 2026-10-06/07; 334/429/433/440/442 already dismissed 2026-10-13. The whole
 `question like 'The prepaid AI balance is low%'` family is now closed -- 3 resolved,
 6 dismissed, 0 pending.

THE RULE THIS ADDS, worth carrying to every future fleet:
 * Record, in the deliverable, the sha256 of every file the patch was made against.
 * At install time, RE-MEASURE those hashes. Equal -> apply. Different -> the patch is
 SUPERSEDED; re-derive it against the current bytes, or establish that the live code already
 does the job (which is what happened here). Never "make it apply" with fuzz.
 * A fleet's output is a claim about the estate at the moment each child read it. Between the
 read and the install, other sessions write. Treat every child deliverable as having an
 expiry, and the hash is the expiry date.

Citing: docs/owner-queue/README.md (the wrong -p1 instruction and the stale pristine hashes),
docs/owner-queue/INTAKE-QUANTIFIED.md, and HAZARD H6 in docs/agent-brief-template-mesh.md
("your working tree is not the base") -- this is the same error approached from the other side:
there, the patch was made against a tree that was too OLD; here, the target had moved FORWARD.
