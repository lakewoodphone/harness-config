**L3717 · lpt-hub's live clone is on the FROZEN anchor, so the push tool and drift verifiers read a stale mirror - a pushed commit is not visible to them**

MEASURED 2026-10-12. lpt-hub's live working clone is `~/repos/lpt-hub` on **secratary**, and `secratary`/`secratary-ts` is the FROZEN ROLLBACK ANCHOR (host-posture `read-only` since the 2026-10-11 cutover; the authority is `secratary-cloud`).

But the two things that consume lpt-hub - `~/personal-secretary-mvp/scripts/lpt-sync-to-production.py` and `scripts/sync-health-audit.py` - RUN on that frozen box and resolve the hub through `_resolve_lpt_hub_root()` (env `LPT_HUB_LOCAL_REPO_PATH` first, else a search). That clone is STALE: it measured `e93dc53d` (2026-10-12 15:30) while origin/main was `513e28cef`/`785306cc0` and my own commit landed as `018aaf0d9`. Its `git fetch` did not update it either, so `git rev-list --left-right --count origin/main...HEAD` printed `0 0` there and looked clean - it was comparing against a stale remote-tracking ref. A local clone that reports 0/0 is not evidence of currency; `git rev-parse origin/main` versus the remote is.

CONSEQUENCES, both real today:
1. A case committed and pushed from a laptop **cannot be verified end-to-end** by the push tool or the drift verifiers, because they read the anchor's stale copy. I could confirm the guard's code path and the record's fields, but not run the tool against the corrected record. Say that plainly rather than implying a run happened.
2. Do not "fix" it by pulling on the anchor - writing there is forbidden. The honest options are to bring the labeler/tooling or the hub mirror to the authority deliberately, or to point `LPT_HUB_LOCAL_REPO_PATH` at a current clone that lives on a writable host. That is a decision about the anchor, not something to improvise.

Also: `_resolve_lpt_hub_root` prefers `LPT_HUB_LOCAL_REPO_PATH`, which is the only lever available to make a verifier see current records without touching the frozen clone.
