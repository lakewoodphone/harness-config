**L3694 · D01-2770781-9853015 is an Amazon digital order, not a broken join**

2026-10-13. Closed the loose end from item 66. `D01-2770781-9853015` is not a defect and not a mystery: it
is an Amazon DIGITAL order.

THE ROW:
 order_id D01-2770781-9853015
 account_label business
 order_date 2026-06-30
 total_amount 5.82
 item_count 0
 ship_to Eliyahu Zabrowsky

It is the ONLY order in `amazon_orders` whose id does not match the physical `111-XXXXXXX-XXXXXXX` shape,
and the `D01-` prefix is Amazon's own marker for a DIGITAL order - a Kindle title, an app, a subscription -
which is why `item_count` is 0 and why `first_item_text` holds the BUYER's name rather than a product. There
is no physical shipment to describe.

WHY IT DOES NOT LINK TO `marketplace_orders`, and this is the useful part. The canonical store is built by
parsing Amazon's PHYSICAL order confirmations out of Gmail; a digital order never sends one in that shape.
So the one unlinked business order is not a hole in the join, it is a class of order the pipeline was never
built to cover - worth knowing before a future session treats `68 of 69 linked` as a defect to chase. One
order, 5.82.

AND IT VALIDATES THE MIGRATION RATHER THAN DISCOUNTING IT. The shift put 69 rows in `order_spending_class`
and flagged that one of them does not join; I read it and found it is correct as it stands, so the class
table needs no exception, no exclusion and no note. **A gap that is understood is worth more than a gap
that is closed, because the next session can tell the two knots apart.**
