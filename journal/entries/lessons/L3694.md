**L3694 · The sync push tool cannot update an order a record already links to, and its dry run says it would**

The push tool **cannot** update an order a sync record already links to, and its own dry run says it can.

`evaluate_push_guard` Rule 1 returns `kind="linked_order"` for any record that names a live production order, and `push_to_production` returns early on that kind (lpt-sync-to-production.py ~line 1681) **before** the "known order id" update path (~line 1730). So Step 2a is unreachable for a linked record — which is every record that has ever been pushed. Meanwhile `print_guard_decision` prints, of exactly that decision:

> `(a real run would UPDATE this already-linked order — that path is unchanged)`

Measured 2026-10-12: `--push-only lg-old-phone-shwartz-2026-08-12.json --dry-run` -> `Decision: SKIP / Reason: record already references live production order WO26081312596 ... via workflow.orderId`.

Consequences, both real:
1. `pricing.quoteTotal` in a sync record does **not** correct `orders.total` for a case already in production — the code at line 1738 that updates total is on the unreachable path. Use `lpt-write total set`.
2. Do **not** "fix" it by deleting `workflow.orderId` so the guard stops seeing the link: the record then falls through to Rule 2 / dedup and can **create a duplicate order** for a case that already has one.

Fix direction (not made): make the update path reachable — treat `linked_order` as an update when the linked order id is the one the record already claims, and correct the dry-run text so the printed decision and the real behaviour are the same sentence.
