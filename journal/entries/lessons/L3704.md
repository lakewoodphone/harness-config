**L3704 · The shop's label printer can only be driven from the FROZEN anchor: print there, never write there**

Measured 2026-10-12 while printing a shop label for ticket-less device 848-525-8975.

THE PRINT HOST IS THE FROZEN ANCHOR. `secratary` and its ssh/tailnet alias `secratary-ts` are the
SAME box, and `harness-config/settings/machines/host-posture.tsv` (lines 30-33) designates it
`frozen` / READ-ONLY - it is the rollback anchor left behind by the 2026-10-11 cutover, and the
authority is now `secratary-cloud`. Printing from it is the only route that exists: the printer
(192.168.50.60) is an office-LAN device and `secratary-cloud` cannot reach it at all
(`curl http://192.168.50.60/general/status.html` from the authority -> `000`, and it has no
`lpt-label` installed, and no `~/lpt-ops`). Reading and printing there is fine; writing there is not.

THE MISTAKE, so it is not repeated: I deployed the newer `label_printer.py` (commit f40f0e6: uniform
body size, DP word wrap, `!` headline, `--roll-mm`) into `~/lpt-ops/lpt_ops/` on that box before
checking posture. Reverted the same session to the exact prior bytes - sha256
8aff9dd1f52bfdf546c2015d932307515a34c800147a19f2323c3e8570b76437, verified - with the backup kept at
`label_printer.py.bak-pre-headline-20261012`, and my `/tmp` scratch removed. No service state, no
cron, no database was touched on that box.

THE READ-ONLY ROUTE TO CURRENT CODE, verified byte-identical to the reverted deploy's output
(sha256 0483d786..., 33.2 mm of tape, nothing written outside /tmp):

 ssh secratary-ts 'PYTHONDONTWRITEBYTECODE=1 \
 /home/zabz/.local/lib/lpt-label/venv/bin/python \
 /home/zabz/code/lpt-ops/bin/lpt-label print - --dry-run --out /tmp/x.png' < /tmp/x.json

`~/lpt-ops` is a plain copy (not a checkout) and is a revision behind; `~/code/lpt-ops` is a real git
checkout on the same box and already carries f40f0e6. Running the entry script from the checkout with
the venv the wrapper already uses needs no write, provided bytecode is suppressed.

PROOF CORRECTION - the previous advice was wrong. The old rule said a print is proven by the printer's
status page going READY -> PRINTING -> READY. Measured: the page's own Auto Refresh Interval is
60000 ms, and a poll loop run concurrently with a 33 mm job (60 samples, 150 ms apart) read `READY`
in EVERY sample; the page also read READY immediately before and after. The only counter is
`Total Print Length(m)` on `information.html`, an integer metre (11), which a 33 mm label cannot
move. So the honest claim after sending a job is: printer identified as QL-820NWB serial H3G354844,
state READY, 29 mm roll loaded, transport accepted it (`instructions_sent: true`) - and tape is
proven by the roll or by the person standing at the printer, never by the network reading.

The skill that sent me there has been corrected in the same session:
`harness-config/presets/zabz/skills/lpt-label-printing/SKILL.md` - 1 (posture warning), 2 (proof),
4 (`!` needs the newer renderer), 6 (new: the read-only route above).
