**L1602 · Prove an auth gate with a request, not with a hash comparison - and 'caddy hash-password' needs --plaintext**

Rotating the fleet-dashboard password exposed two things worth keeping, and the second one is
the more dangerous.

1. `caddy hash-password` without `--plaintext` expects an interactive TTY: piping the value in
 returns "Error: EOF" and an empty hash. My script refused on the empty output (length 0)
 instead of writing it, which is the guard behaving. Use `caddy hash-password --plaintext
 "$PW"` - the value passes through that one container's argv for milliseconds.

2. A verifier that can be wrong is worse than no verifier. My first attempt rotated the
 password CORRECTLY - a login with the new password returned 200 and a wrong password 401 -
 and then rolled it back, because a belt-and-braces check failed: I extracted the effective
 bcrypt hash from Caddy's admin API with a grep and compared fingerprints, and the extraction
 is unreliable (the running config's encoding of the hash does not survive a naive pattern).
 The rollback was correct behaviour on bad information, and it cost a second rotation.
 The same trap bit a subagent earlier the same hour from the other direction: `docker compose
 config` re-escapes `$` as `$$`, faking a MISMATCH.

 Rule: when verifying an auth gate, prove it with a REQUEST, not with a string comparison of
 the credential. "New password -> 200, wrong password -> 401, no credentials -> 401, and the
 same login from a second machine" is a complete proof and needs no fingerprinting. A digest
 comparison across layers is useful for detecting drift after the fact, but it must never gate
 an action on its own.

Also worth noting for anyone repeating this: bcrypt is the one secret where the value in .env
MUST be single-quoted, because Compose interpolates an unquoted `$2a$14$...` down to 8
characters (agent lesson L1599). The rotation is otherwise unremarkable, and the plaintext was
never printed - the only copy is the owner's ACL-restricted password file.
