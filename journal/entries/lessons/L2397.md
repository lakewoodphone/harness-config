**L2397 · Owner-number checks are duplicated in two places and one of them was wrong - an action aimed at the owner is not an external action**

Found and fixed 2026-09-23 in personal-secretary-mvp, while the owner asked why a text to his own cell needed approval.

THE DEFECT. app/policy.py _requires_approval implemented the owner exemption as a plain string equality against owner_phone_number ONLY:

 owner = str(getattr(settings, 'owner_phone_number', '') or '').strip()
 if owner and target == owner: return False

Every other owner check in the codebase uses pp/services/owner_notifications.is_owner_number(), which knows owner_phone_number, owner_notify_number, wilio_forward_to_user and owner_alt_phone_numbers, and compares the last 10 digits so 'tel:+1...' and bare digits also match. So the exemption recognised exactly one of the owner's numbers. A second, independent guard in app/chat_action_runtime.py (the 'external SMS requires approval' gate, ~line 1967) DID use is_owner_number - the two disagreed.

WHY IT SURFACED, because this is the reusable part. Effective settings are not .env. A settings_overrides table row sms_send_external_requires_approval = 'true' (written 2026-05-04) overrides SMS_SEND_EXTERNAL_REQUIRES_APPROVAL=false in .env, and pp/main.py:_apply_effective_settings_from_overrides() sets those onto the settings singleton at runtime. So reading .env - or even importing settings in a fresh process - gives the WRONG answer about production behaviour. A fresh process said False; production enforced True. That single fact accounted for an hour of contradiction.

REPRODUCTION THAT SETTLED IT (do this, do not reason about it). Load the live overrides, apply them exactly as the app does, then run the gate for each candidate number:
 overrides = _load_settings_overrides_from_db(); _apply_effective_settings_from_overrides(overrides)
 for n in ('+17325691594','+18483897895','+18482245096'): get_policy_enforcer().check('send_sms', {'to': n}, settings=settings)
Before the fix: primary -> allowed/policy_passed; the other two -> allowed=False, requires owner approval. After: all three allowed/policy_passed. The differing decision for two numbers in ONE run with ONE settings object is the proof the fault is code, not configuration.

DEPLOYED: commit 08498861, API restarted 2026-09-23 14:49:38 UTC, verified end-to-end by send_sms to +18483897895 -> SID SM1d53fdc54fc95f4fe2d873dedc44351c, sms_log id 905 status sent.

THE TRANSFERABLE RULES.
1. An action whose target is the owner is not an external action. Any code that asks 'is this external / does this need approval / is this risky' must ask is_owner_number(), never compare against owner_phone_number.
2. When two guards enforce the same concept, one of them is eventually wrong. Here two owner checks existed with different rules; only the difference in their behaviour revealed the bug.
3. To know what production does, apply production's effective settings first. .env is a default, not the truth, whenever a settings_overrides table exists. A fresh import settings is NOT a reproduction of the running service.
4. Two further limits found on the same path, both intentional and both working: send_sms carries an owner rate limit of 2/day/UTC unless the send is an owner_direct_request, and get_owner_sms_min_urgency is set to 'urgent' in overrides. Those are not defects - but any explicit-send path that does not set the direct-request flag can be silently eaten by them, which is the same class of failure.
