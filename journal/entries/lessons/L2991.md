**L2991 · Two guards tonight ran, returned success, and recorded nothing - the anti-repeat stamp failed inside a swallowed usage error, and the queue it wrote to is write-blocked**

MEASURED 2026-09-28 23:09Z, in the final round of the objective. Two guards now exist that did not this morning,
and both were absent in the same way: the code that enforced them RAN and RETURNED SUCCESS while recording
nothing.

GUARD 1 - THE ANTI-REPEAT GUARD. The reply path was supposed to stamp a question as asked so it was never put
to the owner twice. Measured:
 * the stamp called `owner-queue.py defer` WITHOUT its required `--until`, so the call exited with a usage
 error, `capture_output=True` swallowed it, nothing was recorded, and the selector would pick the SAME
 question again. Had sending been restored as-is, the owner would have received #164 on every text he sent -
 the exact shape he has complained about twice.
 * and fixing the argument would not have been enough, because the queue itself is WRITE-BLOCKED: it lives
 inside the 13 GB app database, whose write lock `uvicorn` holds (reads 0.00s, writes `database is locked`
 after 12.02s, three of three attempts).
FIX: `~/.sms-inbox/offered.db` - a store we own, no other writers, instant writes. Verified `#164 already
offered? True`, `#166 False`.

GUARD 2 - THE STAMP NOW READS ITS OWN RESULT. If the stamp fails it prints that the question WILL repeat. A
guard whose effect is never checked is not a guard - which is precisely the defect that let a
supposedly-intercepted test send the owner two duplicate texts and claim it had sent none. That mistake is
recorded as P2735, and the correction was not another script but doing the boring thing: prove the guard where
the code runs, and read the result.

WHY THIS GENERALISES, and it is the eleventh instance of the family recorded tonight. Each time, the mechanism
was real, the code executed, no error surfaced, and nothing happened. The instances: a cap read twice with two
defaults; a money ceiling against a hardcoded 0.0, then against an 18-hour-stale file; 27 rows filed and never
consumed; a discovery deadlock; a lease reaper that did not exist; `claim` answering `blocked_by: null` on a
FULL queue; the contract telling shifts to send with an ungated flag; a skill saying cost was unmeasured; owner
texts filed at priority 3; the runner's 1800s bound nobody had been told about; and now a stamp that failed
inside a swallowed usage error. **The common shape is not a crash. It is a success report with no effect.**

THE TEST THAT NEW CODE HERE OUGHT TO PASS, written down so it is not rediscovered: after adding a mechanism,
PROVOKE the condition it guards and read the evidence it claims to leave. `reap` returned 0 all evening and had
never freed anything until a lease was planted; the stamp returned True and had never stamped anything until
#164 was checked afterwards.
