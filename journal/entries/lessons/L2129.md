**L2129 · L2135 - CORRECTION: the mashgiach fix saved the findings and increased contention fan-out; I verified its own goal and not the lock it now holds**

Measured 2026-09-20 on the authority, and it corrects an earlier claim of mine the same day.

**What I reported at 17:14.** "0 lock errors since the restart; the mashgiach fix is holding."

**What is true at 17:22.** **66 lock errors**, and **62 of them are `app.services.mashgiach`**, all in
the single minute 17:22. The spike is one `daily_scan` run.

**Why, and it is a direct consequence of my fix.** Before, `_log_finding` committed each of ~62
findings as its own write transaction. That was wrong (every commit re-attempted a snapshot upgrade
and many failed) - but it also meant the write lock was held in tiny bursts. My fix took
`BEGIN IMMEDIATE` once and held it for the entire scan. The findings now persist correctly (382 rows,
verified), and in exchange one writer now holds the write lock across a 62-insert loop, so the other
writers on the box fail while it runs.

**So the honest scorecard for that change: it stopped silent data loss and it increased contention
fan-out.** Both are real. The first was the measured defect; the second I did not anticipate and did
not measure for - I checked that findings persisted, not that other writers still could.

**The missing step, identified and not yet done:** batch the inserts instead of looping them -
one `INSERT` per finding became one transaction containing all of them, or a single `executemany`.
That keeps the durability win (one commit, no snapshot upgrade) while shortening the lock window from
"the whole scan" to "one statement". It is the obvious next move and it is small.

**The generalisable lesson.** A fix that changes *when* a lock is held changes *who else can run*. I
verified the fix against its own goal ("do findings persist?") and never against the resource it
holds ("can anyone else write?"). **When a change alters transaction scope, the acceptance test has to
include a competing writer** - not just the operation's own success. This is the second time today
that a change which looked correct in isolation had an effect I only found by measuring the wider box,
and the earlier one (L2131) was the same shape: local correctness, unmeasured blast radius.

**Also corrected:** I said `lifecycle_sweep` appeared fixed. It has failed once in this window. The
earlier reading was a 6-minute quiet period, and I was careful to flag it as weak - it was, and it did
not hold. The write contention on this database is a WORKLOAD property (six writers, one 9.9 GB file,
no scheduler - P2132), not something any single code change removes.
