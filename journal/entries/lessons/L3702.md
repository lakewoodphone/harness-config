**L3702 · The owner decision queue exists separately on each host - filing one on secratary writes to the frozen rollback anchor**

Measured 2026-10-12 on ZABZ-TECH.

I filed an owner question with

 ssh secratary "python3 ~/bin/owner-queue.py add --from-json -"

and it came back `queued #448`. That row did **not** go to the company's queue. It went into the
**office box's** own `personal-secretary-mvp/data/secretary.db`, and since the 2026-10-11 05:43:36Z
cutover that host is the **FROZEN rollback anchor** — read-only, no writers, per AGENTS.md §5 and
Rule 2 of `docs/mesh/131-MIGRATION-BRIEF.md`. So I wrote into the one machine that is supposed to
receive nothing, on the exact class of defect that put 5,129 rows into it on 2026-10-11.

**Proof that the two hosts are not the same queue**, read the same minute:

- `ssh secratary "owner-queue.py list --all"` → **#448 = my Rahimi/Mizrachi question**
- `ssh secratary-cloud "owner-queue.py list --all"` → **#448 = a different row entirely**
 ("The authority box (secratary-cloud, 2 vCPU / 7.7 GB) can no longer hold its own…", filed by
 another session the same day)

Each host resolves `DEFAULT_DB` to its **own** `secretary.db`, and both allocate ids from their own
maximum — so the same id means two different questions, and the row I filed is invisible to the
authority that every other machine reads.

**What I did to repair it.** Re-filed the question on the authority as **#450** and recorded his answer
there (`answer 450` → `#450 -> answered`). The stray #448 on the office box was **left in place and
named here rather than deleted** — deleting it is another write to a host that should receive none, and
whoever owns the anchor should decide, not me. It is one row in `owner_decision_queue`, not customer
data, and it is recorded.

**The root cause is a harness defect, not only my mistake.** The command came from the session's own
system prompt, and that prompt was assembled from the **stale deployed preset**
`C:\Users\ezabz\.dsh\.agent-presets\zabz\agent.cordis.yml`, which reads *"on `secratary` only … ssh
secratary-ts"*. The repo already said the right thing in
`harness-config/presets/zabz/agent.cordis.yml` and `profiles/web/cordis.patch.yml` — *"on the authority
only … ssh secratary-cloud"* — so **the machine's deployed preset is behind the repo**, and this
machine's sessions have been reading the old wording.

Fixed in the repo the same hour: `AGENTS.md` §3, `scripts/make_zabz_preset.py`,
`journal/scripts/make_zabz_preset.py`, `journal/presets/zabz/agent.cordis.yml` — all four now name the
authority and `secratary-cloud`, so nothing can regenerate the old text. **The deployed copy on each
machine still has to be refreshed**; until it is, a session that starts there gets the old instruction.

**The rule.** Write an owner question only on the authority:
`ssh secratary-cloud "python3 ~/bin/owner-queue.py add --from-json -"`. Read it there too. If the two
hosts disagree, the cloud one is the queue — and `secratary` is a prefix of `secratary-cloud`, which is
precisely how this gets confused.
