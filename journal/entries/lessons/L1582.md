**L1582 · git stash push -- <path> silently no-op'd, then git checkout HEAD destroyed the edits**

Lesson, measured 2026-09-15 while fixing the fleet-api silent failures. Cost: I lost ~15 minutes of edits and had
to reapply nine edits by hand from a transcript.

`git stash push -- <path>` followed by `git checkout HEAD -- <path>` is NOT how you show "before vs after" for one
file. Two independent traps fired in the same command:

1. `git stash push -- <path>` silently did nothing (the subsequent `git stash list` was empty), so there was no
 stash to `git stash pop`.
2. `git checkout HEAD -- <path>` then reverted the file to HEAD — which is exactly the "before" state I had asked
 for, destroying my "after" edits with no warning and no undo.

The right pattern, which I will use from now on:

 Copy-Item fleet_api.py fleet_api.py.fixed # keep the new version outside git's reach first
 git checkout HEAD -- fleet_api.py # now the BEFORE run is safe
 # run the before tests, quote the line
 Copy-Item fleet_api.py.fixed fleet_api.py -Force # restore
 Remove-Item fleet_api.py.fixed

Or, better, `git diff > fix.patch` before touching anything: a patch file on disk cannot be stashed away by
accident, and `git apply fix.patch` is the restore. A stash is a mutable ref with a two-step failure mode; a file
is not.

The general rule this is an instance of: before any step that can revert work, take the copy that cannot be
reverted by the same mechanism. And prove the safety net exists (`Test-Path` the copy, or `git stash list`) BEFORE
running the destructive step, not after.
