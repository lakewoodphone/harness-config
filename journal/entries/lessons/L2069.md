**L2069 · Three silent-drop faults in one day are one fault: a long-lived connection with nothing that notices it died**

**L · Three silent-drop faults in one day, and they are one fault: a long-lived connection with nothing that notices it died**

MEASURED 2026-09-20 on ZABZ-YOGA. Three separate components failed the same way within a few hours, each
reported as an unrelated symptom, each fixed the same way.

THE THREE:
1. **The spliced WebSocket** in `multi-window/dshw-proxy.mjs`. The owner: *"it just says thinking and I have
 to refresh the page, and I see that really you thought a lot and it didn't stream in."* The proxy piped
 client↔engine with **no timeout and no keepalive**, so when the tailnet dropped the flow the client's
 socket stayed ESTABLISHED, the WebSocket never closed, and the UI waited forever. Fixed with
 `setKeepAlive(true, 15000)` on both legs. (journal W219)
2. **The dispatch ssh hop** in `profiles/web/cordis.patch.yml`. Children died with `Read from remote host
 zabz-tech.tail93e6e6.ts.net: Connection timed out` — `subagent-1`, `subagent-11`, `subagent-17`, and
 then two more workstreams the same evening. The hop carried `ConnectTimeout=25`, which bounds the
 **handshake** and is useless here because these died **minutes in**, while the remote side was thinking.
 No `ServerAliveInterval` at all. Fixed with `ServerAliveInterval=15` + `ServerAliveCountMax=4`.
3. **A pipe instead of a file**, from earlier in the same programme: `dshw up`'s output piped into a
 PowerShell pipeline made `engine-reload.ps1` wait for the **engine** to exit, which it never does — the
 script hung, its scheduled task sat in `Running`, and an orphan held the engine's stdout. Fixed by
 redirecting to files. (L2063)

WHY THEY ARE ONE FAULT. All three are a long-lived connection over a path that can drop **silently**, with
nothing at either end whose job is to notice. A dropped TCP flow through a NAT or a relay sends **no FIN** —
so `close` never fires, `error` never fires, and every layer above waits forever on a stream that will never
deliver another byte. **The symptom is always "nothing happens", and nothing happens because nothing was
listening for the one event that never came.**

AND THE ENVIRONMENT MAKES IT LIKELY RATHER THAN POSSIBLE: the laptop reaches the office **only via a
Tailscale DERP relay** (measured, `docs/mesh/113`). Every long-lived connection in this system crosses that
path — the browser's WebSocket, every ssh hop, every splice.

THE RULE, and it generalises past this machine: **any connection expected to outlive its own traffic needs a
liveness probe that is not the traffic.** TCP keepalive on a socket, `ServerAliveInterval` on an ssh hop, a
file instead of a pipe where the child outlives the parent. And when a component's failure mode is
"silently stops", the fix is not a longer timeout — **a timeout bounds how long you wait before giving up,
not whether you ever notice.**

THE SECOND RULE, learned the hard way an hour earlier: **do not restart a dependency of everything without
first proving you can put it back.** I killed the origins proxy to deploy fix 1 and `dshw ensure` answered
`Access is denied`, leaving all 24 origin ports dead and every window with them. Recovered in ~3 minutes by
starting the proxy directly from its own documented usage line. Before the engine reload that follows, the
proxy was checked healthy first — ports listening, engine answering through it — precisely because of that.

AND THE THIRD: **a fix that needs a restart is not a fix until the restart happens.** Both of today's
connection fixes are composition-time or process-lifetime configuration, so they sat committed and inert
until the engine and proxy were reloaded — and two workstreams died against the un-fixed transport in the
gap. When a fix lands, name the reload it needs and do it in the same breath, or the next child pays.
