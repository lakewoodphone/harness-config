**L1587 · A defect fixed at one layer was re-introduced one layer up by the failure handler, and both layers' tests passed**

A defect class fixed at one layer was re-introduced one layer up, by the very
code that was supposed to handle its failure.

The clients workstream stopped `twilio_client.send_message` from retrying a POST
whose outcome is unknown, because a second POST can put the same text on every
family member's phone twice and bill twice. It raised `AmbiguousSendError`
instead.

But hub.py's `except Exception` then did exactly what had just been made
impossible: it queued the message to the durable outbox, and the outbox's next
flush POSTed it again. `flush_outbox`'s own handler scheduled another attempt as
well. The transport-layer guarantee was re-implemented as a duplicate two layers
up, and every test in both tracks passed — each layer was internally consistent
and each was correct about its own contract.

WHY THE TESTS MISSED IT
Both tracks tested their own contract. Tests that assert "an ambiguous POST is not
retried" pass while the caller retries it; tests that assert "a failed send is
queued for retry" pass while the queue re-sends something that may already have
been delivered. The defect lived exactly in the join, which neither track owned.

WHAT FIXED IT
Recording the outcome honestly instead of retrying it: a new `unconfirmed`
status, ranked with the merely-attempted states so a real Twilio callback can
still correct the row, and never queued for another attempt. The message is not
silently dropped - it gets a row and the admin is told, so a possible loss is
visible rather than hidden behind a possible duplicate.

THE RULE
When you fix a defect class at one layer, walk the call stack and ask what each
CALLER does with the new signal. A changed exception type, a new return value, or
a new status is a new input to code someone else wrote, and their `except
Exception` will treat it as the old thing. The integration step is where that
gets caught, which is why integration is serial and gated - and why the manager
should test the join, not only re-run each track's own tests.

Balance struck deliberately: never double-send; accept a possible single loss on
a confirmed-ambiguous outcome, and make it visible. A duplicate is seen by the
whole family and billed twice; a silent loss is one message, announced.
