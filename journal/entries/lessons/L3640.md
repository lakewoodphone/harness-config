**L3640 · A repo that exists is not a feed that works: five finance pulls died on Windows paths inside a checked-out repo**

Measured 2026-10-13 on the cloud authority, and it cost five finance sources.

THE SYMPTOM. `finance-freshness` named five dead pulls, all with one message:
`quickbooks-agent repo not found at /opt/company/domains/finance/quickbooks-agent`. That read as
ONE missing dependency. It was four independent faults stacked, and only the first was a missing repo.

LAYER 1 - the repo really was absent. `amazon_sync` 23 success / 49 fail, `ebay_sync` 25/49,
`paypal_sync` 37/42, last successes clustered at 2026-09-10. The source is only 3.1 MB / 382 files
once `node_modules` is excluded, and `npm install --omit=dev` added 265 packages in 3 seconds. So
the "we cannot deploy a Node app to a 4-core VPS" instinct was wrong; it was cheap.

LAYER 2 - the npm scripts hardcoded a Windows interpreter. With the repo present the pull still
failed, now with:
`sh: 1: C:/Users/ezabz/Code/personal-secretary-mvp/.venv/Scripts/python.exe: not found`
Eleven scripts had that literal prefix. A Linux host cannot execute it.

LAYER 3 - the Python ingest scripts loaded their credentials from hardcoded paths.
`saas_billing_ingest.py` looked at `<repo>/../../personal-secretary-mvp/.env` and then
`C:/Users/ezabz/Code/personal-secretary-mvp/.env`. Neither exists here, so `_env` was EMPTY and the
script printed "OPENAI_API_KEY not set - skipping", "TWILIO_ACCOUNT_SID ... skipping",
"PAYPAL_CLIENT_ID ... skipping", inserted zero rows, and **exited 0**. The credentials were sitting
in `/opt/company/.env` the whole time - 302 keys including TWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN,
PAYPAL_CLIENT_ID, PAYPAL_CLIENT_SECRET, OPENAI_API_KEY. `paypal_ingest.py` had the same shape.

LAYER 4 - the ledger path was a Windows literal. After fixing the env, both scripts authenticated
for real (PayPal: "Fetched 759 raw records from API") and then died on
`sqlite3.OperationalError: unable to open database file`, because `DB_PATH` was
`C:/Users/ezabz/accounting-data/live/accounting.db`. Three scripts.
Fixed by making DB_PATH honour `ACCOUNTING_DB_PATH` and fall back to the live ledger.

THE RESULT, measured: PayPal spend 749 -> 751 rows, newest 2026-10-08 -> 2026-10-11, freshness age
94.7h -> 0.0h. Twilio spend 278 -> 316 rows, newest 2026-08-01 -> 2026-10-01, age 1635.6h -> 0.0h.
Both on a clock (PayPal via the autopilot, Twilio/OpenAI via a new `finance-saas-sync` cron at
05:17). `finance-freshness` now reports those three sources OK.

THE RULES.
1. `exit 0` with "skipping" is the most dangerous output a feed can produce. Every one of these
 scripts returned success while inserting nothing. A pull that cannot find its credentials must
 fail loudly - the estate already learned this in the CFO's own `sync_transactions()` returning
 `{"error": ...}` and the autopilot reading `.get("added", 0)` off it and recording success.
2. When porting a repo from Windows to Linux, grep for the drive letter. `C:/Users/` in .ts, .py,
 .json and .sh is the whole failure. Count found: one literal in eleven npm scripts, two env-path
 fallbacks, three DB paths - and every one produced a different misleading error.
3. "Repo not found" from a service that shells out is a symptom, not a diagnosis. The service found
 the repo on the second attempt and the error message did not change, because the next fault was
 inside the repo.

NOT EVERYTHING WAS FIXABLE. Playwright 1.55.1 refuses this host outright:
`ERROR: Playwright does not support chromium on ubuntu26.04-x64` (Ubuntu 26.04.1 LTS). The
Amazon/eBay browser scrapers therefore cannot run here at all, and no amount of npm install changes
that. The correct replacement is the email/receipt path - which is what the owner proposed in the
first place ("probably even easier for my emails").
