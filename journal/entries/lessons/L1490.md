**L1490 · A rule in one surface is not a rule: check the surface the caller actually reads**

A rule in one surface is not a rule: check the surface the caller actually reads

The task-closure gate (48h / in_progress 7 days / force='true') was documented in the tool
description for `close_task` and absent from the work prompt, which is the surface that
instructs work sessions to call update_task(status="done"). The model was told to use the gated
path by instructions that omitted the gate, so it hit the refusal with no way to know it existed,
repeated the identical call seven times, and ran out of budget.

This is not a documentation gap in the ordinary sense: the knowledge EXISTED and was correct. It
was attached to a different entry point than the one being used. When a behaviour is refused for
a reason the caller cannot see, the caller does not infer the rule -- it retries, or it works
around the guard, and both look like stupidity from the outside.

THE HABIT: when you find a guard that matters, find every surface that leads a caller to it and
check the rule is stated on the one they read. Grep for the CALL, not for the rule:
`grep -rn 'status.*done' app/` finds the instructions; `grep -rn 'force' app/*.py` finds only the
implementation.

A SECOND HABIT, from the same find: a refusal that repeats forever is worse than a refusal. The
prompt now says out loud that repeating the call cannot work, because that is the behaviour it
was actually producing.
