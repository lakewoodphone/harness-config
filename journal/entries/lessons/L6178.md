**L6178 · Store devices have no terminal state, and a device name cannot be taken back**

## 2026-10-13 ~20:05Z · ZABZ-TECH · Round 2: the iPad was never broken, and a name that cannot be taken back

**DRN 2003 (the shop iPad, `W534270H7X`) is complete and always was.** Read from the device's own
`InstalledApplicationList` today: **43 apps, including all three the shop runbook requires — Waze
(`com.waze.iphone`), Tailscale (`io.tailscale.ipn.ios`) and Dialpad (`co.switch.Switch`)** — plus
Google Maps. It wears the full `shop-store` profile (acknowledged 2026-10-07), its queue is empty
(`depth=0`), and it answers a fresh query on the first attempt. The fleet monitor has been alerting
`stuck_deploying` on it for **5.9 days** over nothing.

**Why it can never leave that state — and this is the finding, not the label:** every writer of
`state='deployed'` in the fleet-api is **kiosk-family** (`/lockdown`, `/edit-window-close`,
`/remove-lockdown`, `/soft-kiosk`, `/refresh-close`). `/deploy` is the only path a *store* device
takes and it sets `deploying` — **so a store device has no terminal state by construction, and the
stuck-state alert fires on it forever.** DRN 2001/2002 only escape because their `deployed` label is
a leftover from their September life as kiosk test units, not because anything settled them.

**Consequence, and the reason I did not just fix the row:** correcting `state` to `deployed` by hand
would silence the alert and hide the gap, and the next store device through `/deploy` would strand
identically. The real fix is one of two lines in the store-device path — set a terminal state after
`install-profile` for `device_class='store_device'`, or exclude store devices from the
`stuck_deploying` check. **Both are production fleet-api edits, and §10 of the shop-device runbook
records that the live container's `fleet_api.py` is ~260 lines AHEAD of git** (the store-wallpaper
feature exists only in production; a rebuild would lose it). So this is reconcile-then-deploy work,
not a blind edit — recorded, not papered over.

**Two facts about device names, one of which is a trap:**

1. **The shop runbook §9 is wrong.** It says names are derived as `LPT STORE {drn − 2000}` and that
 "the code says `LPT STORE {n}`". The code — `_device_name_for_site()` in `fleet_api.py` — returns
 **`LPT {drn}`** (2001 → `LPT 2001`), with a comment saying it is deliberately NOT sequence-based.
 Anyone reasoning from the runbook would expect a different name on the device than the one that
 actually arrives.
2. **A device name, once applied, cannot be taken back.** `set-device-name` refuses any value other
 than the canonical one, so `ota.py device-name 2004` would stamp `LPT 2004` on a unit that is
 going to a *customer*, and there is no API path to undo it. The onboarding runbook deliberately
 omits the step, so nothing has gone wrong — **and I have deliberately not applied a name to any
 of the five units.** What a sold unit should be called (its fleet number? the brand? nothing?) is
 a customer-facing choice with an irreversible consequence, so it is queued for the owner rather
 than decided here.

**Pre-flight that passed:** the `telnyx-apn` profile on disk carries **no `Username`/`Password` keys
at all** (just `APN=data00.telnyx` and the protocol masks), which is the documented fix for the
`Error 1000 "profile 'LPT Telnyx APN' is invalid"` pitfall. So when a SIM exists, the APN install
should fail only for the other documented reason — no SIM physically present.
