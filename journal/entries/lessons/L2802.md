**L2802 · A UI complaint is answered by the renderer, not by COUNT(*) on the column**

A UI complaint ("most rows say Device not recorded") is never answered by counting NULLs in a
column. Find the renderer first, read the branch that produces the string, and re-express THAT
branch as the query.

Measured 2026-09-28: the Work Orders hub Device cell is `describeDevice()` in
`workOrderRowFacts.ts:215`, falling back through `deviceInfo.brand/model` -> a prepared string
(the order `title`) -> an informative `title` -> the literal `Device not recorded`.
`orders."deviceInfo"` NULL was 237 rows; "no brand AND no model" was 244; what the owner was
actually looking at was 173, because 71 of those 244 had a title that named the device and
therefore never rendered as "not recorded". Three different numbers, and only the third is the
complaint.

And verify the fix through the SAME function, not through a re-implementation. The final
before/after (173 -> 71) came from importing the hub's own `describeDevice` and running it over
the live rows; the SQL predicate was only used to find candidates. A SQL copy of the rule can
disagree with the rule, and then the report is wrong in the direction that flatters it. Same
trick measured the blast radius of editing that function: run the old body and the new body over
all 595 rows and diff the output — 52 cells changed, 0 regressed, which is what made a frontend
edit defensible at all.
