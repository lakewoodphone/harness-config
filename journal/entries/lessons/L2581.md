**L2581 · Dollar signs are a delimiter in three different layers of this system - name the parser before you write money into a surface**

**L · 2026-09-25 · ZABZ-YOGA — `$` is a delimiter in three different layers of this system; ask who parses your text before you write money into it**

**Measured, three separate failures, one class.** Every one of them silently ate the currency out of text
the owner was meant to act on, and each was found only because someone looked at the *rendered result*
rather than at the data.

**1. The database / the queue CLI (P265, 2026-09-17).** `owner_decision_queue` row #79 lost **every dollar
figure** on the way in: `up to $2,000 per violation` stored as `up to \,000`, `min $60` as `min \`. Two
independent writers did it, and the row still read like a sentence, so nobody noticed the numbers were
missing. The fix was already the right one and is now enforced: **bound parameters, never interpolation**,
plus a guard and a `lint` in `~/bin/owner-queue.py` that refuses a suspect string at insert time.

**2. The DSH Web renderer (2026-09-25, this session's own output).** A message containing two dollar
amounts rendered every word between them as LaTeX:

```
wrote: One honest gap: the $100 is a **shop expense**, not a customer receipt, so it doesn't
 change his `payment_state` ($320 in, $1,600 on success).
showed: One honest gap: the $100isa**shopexpense**,notacustomerreceipt,soitdoesn'tchangehis
 `payment_state`($320 in, $1,600 on success).
```

Spaces dropped, the hyphen rendered as U+2212 MINUS, the `**` printed literally, all in the math font. A
second message's quoted line did the same: `"$320 deposit paid 2026-09-17 + $100 open-cover fee"` came out
as `"320depositpaid2026-09-17+100"`. Cause: the frontend bundle carries `micromark-extension-math`, whose
`singleDollarTextMath` option **defaults to true** and the caller passes no options. Reproduced against the
real library on the same two strings: with `true`, `micromark` consumes the span between the dollars and the
words disappear from the text output; with `false`, the identical input renders with both amounts intact,
`**shop expense**` as bold and `` `payment_state` `` as code.

**3. The same trap is one keystroke away in any template, log line or shell call** — which is what (1) was,
and why the rule below is about surfaces, not about SQLite.

**The rules.**
1. **Before writing text that carries money into a surface, name the parser.** `$` means "expand a
 variable" to a shell, "start math" to a LaTeX-flavoured markdown renderer, "bind a parameter" to SQLite,
 and "money" to a human. Wherever the author's intent and the parser's meaning disagree, the text loses.
2. **Prefer a transport where `$` is inert**: bound parameters for SQL, a JSON payload or a file for a CLI,
 and — for a renderer — a configuration that treats a single `$` as text.
3. **A default that is wrong for the deployment is a bug, not a preference.** LaTeX conventions are right
 for a maths notebook and wrong for a shop whose sentences are full of prices. `singleDollarTextMath`
 is now OFF in every DSH web bundle (single byte flip, `$$…$$` display math still works), applied by
 `harness-config/scripts/patch-dsh-web-currency-math.py` and watched by kernel check 18
 (`web_currency_math`), because the patch lives in a *build artifact* and a DSH upgrade would otherwise
 bring the bug back silently.
4. **Verify money by looking at the rendered output, not at the record.** All three failures stored or
 emitted something that read plausibly. The screen is the only place the loss is visible.
