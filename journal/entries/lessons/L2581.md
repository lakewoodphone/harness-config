**L2581 · A step that has never once succeeded is not a working step - and an unreadable sensor is not a negative reading**

**A step that has never once succeeded is not a working step — and an unreadable sensor is not a negative reading.**

Two failures, same shape, found together on 2026-09-25 while chasing a report that
the Shabbat power-down had cut HA with the interior door still locked.

1. `home_assistant.shutdown()` called one hardcoded service,
 `homeassistant.shutdown`, and it was answered **HTTP 400 on every run since the
 automation went live** (`journalctl -u secretary-api`, 21:03:59: `Graceful HA
 shutdown failed: 400 Client Error: Bad Request`). The orchestrator treated it as
 best-effort and cut the plug 10 s later, so the step's own failure was the only
 thing keeping the sequence working, and HA was hard-cut every week — its
 recorder DB never flushed. **A call whose error is logged and ignored looks
 identical to a call that works, in every summary.** Try the known service names,
 return ok only for one that actually answered, and name it.

2. The pre-cut door gate read the maglock through HA and treated any falsy answer
 as "the door is locked, abort". Once the graceful stop starts *working*, HA is
 down at that moment, so every future power-down would have aborted and the plug
 would never be cut again. Three facts were being collapsed into two:
 `reads unlocked` / `reads locked` / `cannot be read because we just stopped its
 controller`. The third is not evidence of a lockout — a controller that is off
 cannot re-lock the relay, and the only thing that re-locks it (HA's tamper
 automation) was disabled and proven held 15 s earlier. Read the tri-state, name
 the basis you cut on, and refuse only on a basis that is sound.

Corollary that outlives both: when the repair for a watchdog is "it only works
because the good path is broken", say so in the code, because the next agent will
fix the broken path and silently break the good one.
