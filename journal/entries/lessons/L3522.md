**L3522 · Windows Search and Defender throttle bulk copies to removable media by about 6x - exclude the target and stop WSearch, then PUT BOTH BACK automatically**

**Measured 2026-10-11** copying a 207 GiB delivery of 149,000 files to a USB stick on ZABZ-TECH.

| | CPU burned | effect |
|---|---|---|
| `SearchIndexer` (Windows Search) | **10,388 CPU-seconds** | indexing every file as it landed |
| `MsMpEng` (Defender real-time) | **4,046 CPU-seconds** | scanning every file as it landed |

The copy decayed from ~8 MB/s to **3.57 MB/s** as those two built up. Adding a Defender exclusion for the target drive and stopping `WSearch` took it to **22.48 MB/s — about 6x**, turning a 16-hour job into 2-3 hours.

```
Add-MpPreference -ExclusionPath "D:\" # elevated
Stop-Service WSearch
```

**Neither may be left in place.** A drive excluded from real-time protection is a security hole and a stopped search service is a broken machine. `lpt-hub/scripts/customer-operations/restore-after-copy.ps1` is a scheduled task that does nothing while a copy is running, restores both the moment the copier exits, and unregisters itself — so the restore cannot be forgotten and does not depend on any session being open.

**And the diagnostic lesson:** the first instinct was "the stick is slow". Disk counters showed ~3.5 MB/s on a drive that does 15-22 MB/s, and the drive was being scanned and indexed on arrival. **Before blaming hardware for a throughput collapse, check what else is touching every file.**

This is the third wrong-cause conclusion for the same slow copy in one afternoon (see L3512 for the other two: a 200 MB write that only measured the write cache, and blaming `/MT` for what was really robocopy's attribute retries). The pattern worth taking: **a throughput number without the regime and the competing load is not a measurement.**
