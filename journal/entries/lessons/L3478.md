**L3478 · Reading code does not test it against the world - a device-state simulation found what three careful reads did not**

**Lesson, measured 2026-10-09 (round 10).** Two rounds of *reading* the schedule
programmer did not find a bug that one *simulation against the real device* found
immediately.

## What happened

Round 9 rewrote `_program_coming_weekend` to create-before-prune. I read that
rewrite carefully twice — once while writing it, once while reviewing the diff —
and in round 10 I read it again to check the ordering. Every reading concluded it
was correct.

It was not. The OFF cron was added to the `wanted` set unconditionally, while the
code deliberately does not write that OFF job unless
`shabbat_device_off_schedule` is on. `wanted` is what the prune treats as "ours
and current", so it described jobs that did not exist. The visible symptom was a
create-check claiming `would CREATE: ['15 13 16 10 *', '26 13 9 10 *', '5 13 23 10 *']`
— three OFF jobs it would never create.

I found it in the first run of a script that took the **device's actual current
timespecs**, evaluated the code's logic at tomorrow's 10:00, and printed what it
would create and delete. The wrong entries appeared instantly.

## The rule

**When logic depends on external state, execute it against that state; do not
reason about it.** Reading a function proves it says what you intended. It does
not prove it agrees with the world.

Concretely, for anything that compares what-is against what-should-be:
run it against the live store and print both sides. The mismatch is visible in
one line, and it is invisible to any amount of reading — the code was internally
consistent and only wrong about reality.

## Why it is worth recording

Rounds 3 through 10 all found defects by *running* something rather than reading
it: the stale staged file (a hash comparison), the wrong journal id (reading the
tool's output), the rejected journalctl window (a count that could not be
non-zero), and now this. The one round where I trusted careful reading — twice —
produced a bug that shipped to a host that will run it mid-Shabbat.

A related trap in the same check: the first version of my simulation computed
`wanted` **itself** rather than calling the code, so it reproduced my assumption
instead of testing it, and kept printing the wrong answer after the fix. A
simulation must derive its expectation from the code under test, or it is only
checking itself.
