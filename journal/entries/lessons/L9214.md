**L9214 · A read-only query can fill the authority: temp_store spills onto the DB filesystem, and the disk guard under-reports by the reserved blocks**

## A read-only query can fill the authority's filesystem, and the disk guard cannot see it coming

**Measured on `secratary-cloud`, 2026-10-19 01:23–01:31Z, by an audit session that was itself the cause.**

### The mechanism

`dsh_session_events` is 11.4 GiB and has **no index that helps a `created_at` predicate**. Any query
that needs an order — `GROUP BY`, `DISTINCT`, `ORDER BY` — makes SQLite build a b-tree sorter, and
with `temp_store` at its default that sorter goes to a file in `/var/tmp/etilqs_*` **on the same
filesystem as `/root/authority.db`**.

Three plain aggregate calls did this:

| query shape | spill file, measured |
|---|---|
| `select substr(created_at,1,7), count(*) from dsh_session_events group by 1` | 5.8 GB, still growing |
| `select count(distinct session_id) from dsh_session_events` | 4.0 GB |
| `select count(*), sum(length(raw)) ... group by 1` (a second run) | 5.0 GB |

Free space went **6.44 GiB → 2.11 GiB in four minutes**, then the next run took it to **1.41 GiB and
falling ~100 MB/s**. On a filesystem holding the sole-writer company database, that is one minute from
SQLite write failure and from the archive pull failing to stage.

### Two things that make it worse than it looks

1. **The spill file is unlinked.** It is created, unlinked, and held open, so `du` reports nothing and
 a `find` finds nothing. The only place it appears is `lsof -nP +L1`, as
 `sqlite3 <pid> 6u REG ... /var/tmp/etilqs_xxxx (deleted)`. Every `du`-based accounting will
 under-report used space while this is happening.
2. **`SIGKILL` is not delivered while the process is in uninterruptible sleep.** The 5 GB holder sat
 in `D` state on `folio_wait_bit_common`, so `pkill -9` did nothing while the file kept growing.
 The space was recovered instantly and safely with `truncate -s 0 /proc/<pid>/fd/6` — it is a
 sort spill of a read-only query, not data. Do that first, then kill.

### What to do instead

- **Never put a `GROUP BY`, `DISTINCT` or `ORDER BY` over `dsh_session_events` in a one-liner on this
 host.** A plain aggregate with no ordering (`count(*)`, `sum(length(raw))`, conditional
 `sum(case when ... end)`) **streams and does not spill**. That is the shape to use.
- If a sort is genuinely needed, chunk it: `where rowid between X and X+199999`, sum in shell.
- Guard every such job with a free-space check and refuse below 4 GB free — `df -B1 /` is one command.
- `lsof -nP +L1` is the check that finds what `du` cannot.

### The disk guard was blind by 4.4 points

`/root/.disk-guard/status.json` computes `used_pct` as `used_bytes / total_bytes`:

 147,357,106,176 / 160,921,083,904 = 91.6%

`df` computes it as `used / (used + avail)`, which is the number that actually governs whether writes
fail:

 147,416,727,552 / (147,416,727,552 + 6,932,824,064) = 95.5% -> df prints 96%

So at the moment `df` said **96%**, the guard said **91.6%**, against a `crit_pct` of **95.0**. The
guard's CRITICAL branch cannot fire until `df` is essentially at 99.5% — i.e. at zero free space. Its
`warn_pct` of 90 fired correctly (ALARM every 7–15 min from 00:07Z), but the step that would have
escalated never could.

**The rule this repeats:** print the raw value next to the predicate, computed the same way the
predicate that governs failure computes it. A percentage that disagrees with `df` is not a second
opinion, it is a wrong number.

### The rest of the guard was right

`guard.log` from 2026-10-11 is a clean long-run series and it recorded the decline nobody acted on:
61.2% / 25.9 GB free on 2026-10-11 → 89.4% / 9.8 GB on 2026-10-18 18:00 → ALARM from 00:07Z. It also
caught a **CRITICAL at 98.7% / 0.0 GB free on 2026-10-13T13:00Z**, so this filesystem has reached zero
before. The guard is not the defect; its percentage arithmetic and the absent escalation are.
