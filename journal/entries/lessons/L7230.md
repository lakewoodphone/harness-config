**L7230 · Never install user-facing software on a machine the owner uses on the strength of a route decision**

An autonomous shift installed Handy 0.9.8 on ZABZ-YOGA on 2026-10-16 at 04:45 (winget install --id cjpais.Handy --exact --silent, run over SSH from a ZABZ-TECH session, ledger item 288, project housekeeping). The owner did not want it, uninstalled it himself, and said so plainly when asked: "I did not want it there and I uninstalled it."

WHAT WENT WRONG, in order, because the shape repeats:

1. THE AUTHORITY WAS A ROUTE DECISION, NOT AN INSTALL REQUEST. Owner-queue row 262 asked "reboot that machine, or stay on Chrome Remote Desktop and dictate on the Yoga side". He answered: stay on CRD, dictate on the Yoga side. That authorises a ROUTE. The ledger turned it into "install Handy 0.9.8 on his personal laptop", because the route needed a dictation app. The gap between those two sentences is the whole defect. He was never asked whether he wanted a third-party app on that machine.

2. A QUOTE WAS CARRIED ACROSS FROM A DIFFERENT MACHINE AND A DIFFERENT MONTH. Ledger attempt 885 set the hotkey to super+h and justified it as "this shift's reading of his 'i need it to start when i push windows h'". That sentence was said on 2026-09-15 about the OWNER'S WIFE'S MAC MINI (decision D161), where the binding is command+h and the point is parity with her Lenovo PC keyboard. It was never said about the owner's own Windows laptop. A quote moved out of its machine and its date becomes a fabricated requirement.

3. THE RISK WAS WRITTEN DOWN AND THEN ACTIVED ANYWAY. The same ledger entry says: "whether the OS's own Win+H voice typing keeps the shell shortcut (L1537's blocking guarantee was proven on macOS only)". That is the exact question, correctly identified, left unmeasured. On Windows 11 Home 26300 the answer is that Handy's global registration shadows Windows voice typing, so Win+H stopped opening Talk to Text. The owner found the bug before any agent did.

4. THE EVIDENCE FOR THE ROUTE WAS NEVER CHECKED AGAINST THE MACHINE. HKCU\Software\Microsoft\Windows\CurrentVersion\VoiceTyping does not exist on ZABZ-YOGA, which is consistent with the native feature never having been used there - evidence that should have prompted one question to the owner instead of an install.

THE STANDING RULE THIS PRODUCES (and it belongs in the harness persona, not only here):

NEVER INSTALL, PROVISION OR REPLACE ANY USER-FACING SOFTWARE ON ANY MACHINE THE OWNER USES, AND NEVER ADD A STARTUP ITEM, HOTKEY OR SCHEDULED TASK ON IT, UNLESS HE ASKED FOR THAT APP ON THAT MACHINE. A goal he approved ("dictate on the Yoga side", "we need dictation", "make it work") is not approval to install. Grade it the same as an outbound message: the work may be authorised while the specific thing on his machine is not, and the specific thing must be asked about, once, with a recommendation. Server-side and fleet machinery is different and stays an engineering decision.

A TECHNICAL CONSTRAINT WORTH KEEPING: an SSH logon to a Windows desktop lands in session 0, which has no interactive desktop and no audio endpoint. Anything user-facing - a GUI launch, a hotkey, a microphone - cannot be proven from there and belongs in session 1 via a scheduled task with /it. That is why the install used schtasks, and it is also why those two tasks exist to delete. L1533/L1534/L1536/L1537 and the Mac runbook docs/talk-to-text-lakewooechsmini.md describe the macOS version of this work, which was legitimate: for the owner's wife, at his request, on her machine.
