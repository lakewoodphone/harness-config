**L3231 · MCP rows: what I measured on 2026-10-02 - the give-up budget, its arithmetic, and why raising attempts does not leak servers**

AUDITED, measured on ZABZ-YOGA and secratary, 2026-10-02. Acting on this entry needs no
re-derivation.

1. THE BUDGET, exactly. @deepseek-ai/dsh-mcp-client/lib/index.js: delays are
 initialDelayMs * 2^(attempt-1) capped at maxDelayMs, and it gives up when
 failedAttempts > maxAttempts. Defaults (initialDelayMs 500, maxDelayMs 30000,
 maxAttempts 10) therefore mean 0.5+1+2+4+8+16+30+30+30 = ~121 s of delays, and the
 give-up happens on the attempt AFTER the tenth delay, so call it ~2.5 minutes of
 transport trouble. On give-up it disposes every registered tool and stops
 (index.js:567-574). Nothing re-registers them short of an HMR reload or a Host restart.

2. RAISING maxAttempts DOES NOT ACCUMULATE PROCESSES. This was the question that decided
 whether a larger budget is safe, and it is now measured rather than assumed. With 60
 attempts the connector is restarted up to 60 times, each spawning an ssh plus a remote
 python; if those survived their ssh parent, one bad afternoon would leave dozens of
 65 MB servers behind. Driven directly: baseline MCP servers on secratary 7, spawn one
 connector -> 8, kill the ssh client -> back to 7 within 8 s. The remote server exits
 with its ssh parent, so an attempt costs nothing when it fails. A 60-attempt budget is
 safe on this transport.

3. WHAT THE RAISED BUDGET NOW COVERS (committed as reconnect:
 { maxAttempts: 60, maxDelayMs: 30000 } on all six MCP rows): delays run
 0.5..30 then 30 s to the cap, so roughly 0.5+1+2+4+8+16+ 55*30 = ~27.5 minutes before
 give-up. A short blip still recovers in 0.5-2 s. A machine reboot (measured here: a
 13-minute gap between the engine coming down at 10:54 and the watchdog's ensure at
 11:07) now falls inside the budget in the ordinary case, where 121 s did not.

4. THE REMAINING GAP IS VISIBILITY, NOT TIME. Every MCP row carries
 failOnStartupError: false, so the give-up is a ctx.logger.error nobody reads; the owner
 sees only "Tools updated / N removed" in the GUI, which reads like a cosmetic notice.
 A 27-minute budget does not make an engine that has been up for days with a dead
 connector any less silent. The fix belongs in the harness (surface the give-up as an
 owner-visible system message) and is NOT done - P2824 carries it.

5. MCP ROW CONFIG IS A BOOT-TIME LAYER. The composed config is generated at engine boot
 (dsh-update/lib/compose.mjs), so an edited patch row takes effect on the NEXT engine
 start, never in the running one. Confirmed by composing the web profile by hand:
 dsh-update/lib/compose.mjs --profile web --out <file> produced 197 rows in ~0.5 s and
 the output already carried "maxAttempts": 60 from the patch - i.e. that command is the
 cheap way to answer "what will the next boot actually load" without restarting.
