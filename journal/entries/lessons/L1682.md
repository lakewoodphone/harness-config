**L1682 · I hung the company API for fifteen minutes by holding a SQLite write transaction from a script with no timeout**

## L-new3 — I hung the company's own API for about fifteen minutes by holding a write transaction on the live SQLite database from a script with no timeout.

**What happened, measured.** 2026-09-16 ~00:44–00:58 UTC. I ran a small Python script piped over ssh
(`python3 -`) that did `BEGIN IMMEDIATE` on `/home/zabz/personal-secretary-mvp/data/secretary.db`
(5.79 GB) and then waited on a retry loop of up to 8 × 120 s for the lock. My own foreground `pwsh` call
timed out at 300 s and was killed — but **the remote process kept running and kept holding the lock**:
`ps -eo pid,etimes,cmd` showed `692506 476 python3 -`. Because SQLite allows one writer at a time, the
company's FastAPI server could not write either; `GET /health` returned `http=000` (no response) and the
`ps_*` MCP tools timed out at 30 s. Killing PID 692506 released the lock in **0.00 s**, the old uvicorn PID
678302 had already died, and the watchdog brought up PID 701245, after which `/health` returned
`http=200 time=0.007s` with a fresh timestamp and `"database":{"ok":true}`.

**The rules this earned.**

1. **Never open a write transaction against the live database from an ad-hoc script.** Use the application's
 own API/action surface (`save_memory` and friends), which serialises writes for you. A direct file write
 is for when the app is down or for a database that is not serving traffic - not for convenience.
2. **A remote process is not killed when your ssh call is killed.** An interrupted `ssh host "python3 -"`
 leaves the remote process alive with whatever locks it held. Before any remote DB work, capture the PID;
 after any timeout, check for strays and kill them. `pkill -f` on your own script name, or an explicit PID.
3. **Bound the work, not just the call.** Any script that can wait must itself have a hard wall
 (`timeout 90 python3 -`) so it cannot outlive its usefulness. My timeout was on the outside; the thing
 that needed it was the inside.
4. **When my own tooling is the cause of an incident, say so first, before reporting the recovery.** The
 temptation is to describe the API as "temporarily unavailable"; the true sentence is "I held its lock".

**What did not happen, verified:** the transaction never committed, so no data was written or lost by the
hang itself; the script ROLLBACKed on its own exception path; and the health endpoint after recovery
reports `database.ok: true`. The backup of the three memory rows I was about to change was written to disk
before the first attempt (`/home/zabz/_hours-memory-backup-20260916.json`).
