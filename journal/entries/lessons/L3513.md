**L3513 · route.sh probes the base URL, not /health, so it can never choose a path - a check that cannot pass**

**`scripts/mesh/route.sh` cannot choose a path, because it probes a base URL instead of a health path.**

MEASURED 2026-10-11 20:48Z from ZABZ-TECH. The script's own candidate rows are base URLs:

 API_ROWS=( "loopback|secratary-cloud|http://127.0.0.1:8002"
 "tail|secratary-cloud|https://secratary-cloud.tail93e6e6.ts.net:8443"
 "flare|secratary-cloud|https://api.abletelsolutions.com" )

and `probe()` curls that URL **unchanged**, while its success test (`SHAPE_RE`) looks for the
`"ok": true` shape the **/health** route returns. So every candidate is asked for `/`, and the
authority answers a root request with **401**:

 https://api.abletelsolutions.com / -> HTTP 401 {"detail":"Missing/invalid API key",...}
 https://api.abletelsolutions.com /health -> HTTP 200 {"ok":true,"database":{"ok":true},...}
 https://secratary-cloud.tail93e6e6.ts.net:8443 / -> HTTP 401
 https://secratary-cloud.tail93e6e6.ts.net:8443 /health -> HTTP 200

Result: `route.sh --explain` reports `AUTH http=401 (reachable, refused us)` for **both working
paths** on a machine where the authority is demonstrably up, and exits without choosing.

**The fix is one line.** In the `http*` branch of `probe()`, append the probe path when the candidate
carries no path of its own:

 PROBE_PATH="${ROUTE_PROBE_PATH:-/health}"
 ...
 case "$url" in *://*/*) target="$url" ;; *) target="${url}${PROBE_PATH}" ;; esac
 ... curl ... "$target"

The `*://*/*` glob requires a `/` *after* the host, so `https://host:8443` and
`https://api.abletelsolutions.com` both get `/health` appended, while a candidate that already names
a path is left alone.

**WHY THIS IS THE ESTATE'S NAMED FAILURE MODE.** A script that runs, reports a confident and
technically-accurate diagnosis ("reachable, refused us"), and can never do its job is worse than one
that crashes - it points the reader at authorization when the fault is the probe. The exit-5 branch
added at 20:48Z even says *"THIS IS AN AUTHORIZATION PROBLEM, NOT A TRANSPORT PROBLEM"*, which is a
reasonable sentence built on a false premise: the 401 is an artefact of asking the wrong path.

**Not fixed by me on purpose:** the file is untracked and being actively edited by another agent at
the time of writing (`?? scripts/mesh/route.sh`, 190 lines and growing), and two agents editing one
untracked file is how work is lost. Whoever owns it should apply the one-liner and then **prove it by
running `route.sh --explain` on a machine where the authority is up and showing it CHOOSE a path** -
not by quoting the diff.
