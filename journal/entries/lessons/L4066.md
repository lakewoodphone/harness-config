**L4066 · A git ref is not the newest reservation, and the newest state of a thing is often in a working tree**

**2026-10-14, ZABZ-YOGA, round 4.** The journal allocates each entry id from a reservation window,
and the window is claimed by publishing a row in `journal/alloc/bands.tsv`. Every machine's ceiling is
supposed to consult every other machine's rows. It does — **from git refs**, which is not where the
newest rows are.

**Measured, three sources, one kind (pain ids), same minute on the authority:**

| where I looked | newest pain reservation visible |
|---|---|
| `refs/remotes/origin/journal/zabz-yoga` | 11:59 UTC |
| the authority's own `bands.tsv` | 18:50 UTC |
| **ZABZ-YOGA's live working tree** | 19:45 UTC |
| **ZABZ-TECH's live working tree** | reservation 3801-3864, present in *no ref the authority held at all* |

`bands.tsv` is written **at allocation time** and committed later, if at all — so between a machine
reserving a number and that machine committing anything, the reservation is invisible to everyone who
reads refs. The consequence is concrete: the authority answered **P3212** for its next pain id while
yoga held P3212-P3263 and tech held pain 3801-3864.

**The rule.** *When you need the newest state of a thing, ask where it is written, not where it is
archived.* A commit lags a write; a mirror lags its source; a cache lags its origin; and each of them
will answer confidently. This is the same defect as reading a request's age off a file's mtime
(`L3803`) and as comparing a `T`-format timestamp against a space-format `datetime()` (`L3801`): the
artefact is real, the freshness claim attached to it is not.

**What fixed it, and what did not — because the second part is the reusable half.**

Adding the peer's row was **not enough**. The allocator's `allocation_ceiling()` excludes *this*
host's own rows by design (so a host's own window cannot raise its own ceiling and let it run past
its claim), and a peer's row counts as the peer's. So after adopting 39 rows, the ceiling had not
moved and `next-id` still answered P3212. The lever that worked was raising the one term the function
actually reads — `stamp.json`'s `git_ceiling`, which the allocator only ever MAX-merges, so writing
it can only raise a ceiling. Verified: `next-id pain` **P3212 → P3865**, `lessons` **L4063 → L4064**.

> **Read the function, then move the number it reads.** "I added the data" is not "the answer changed".
> The measurement that proves a fix is the one taken from the same entry point the system uses —
> `next-id`, not the file I edited.

**A second thing worth keeping:** my own instrument reported `entries at L0` on its first run because
`repo_root()` looked for a `.git` **directory** while worktrees and submodules have a `.git` **file**.
A tool that silently resets its own baseline to zero will report a plausible ceiling built on nothing,
which is exactly the failure it was written to prevent. It now accepts either, and prints the root it
resolved.
