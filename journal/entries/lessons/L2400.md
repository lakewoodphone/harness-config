**L2400 · The owner's media preferences live in four places and the freshest one lied - freshness is not authority**

MEASURED 2026-09-23. The owner asked for his TV/movie preferences, then asked what to watch. I answered from the freshest-looking file I found first -- movie-preferences.md in the VS Code Copilot memory store (written 2026-05-31, 20 lines), which carried a "Watch Queue" line: Person of Interest, "starting Season 1", added 2026-05-31. I recommended it. His reply: "i already watched a bunch of it and eventually got bored, you have that documented already."

He was right, and the document was one directory away the whole time. The real record is lpt-hub/research/miscellaneous/tv-movie-taste-profile.md -- 20 KB, last written 2026-03-29, with a full section list: Golden Formula (five sections), Confirmed Taste Anchors (nine shows, each with why it worked), Known Anti-Patterns (four shows, each with why it FAILED), movie heuristics, trailer test, 15-minute filter, six mood lanes, vetting protocol, version history. And the instruction file that points straight at it, research/.github/copilot-instructions.md line ~100 ("TV & Movie Recommendations - Location: research/miscellaneous/tv-movie-taste-profile.md ... Hall of Fame ... Drop List analysis ... When to check: user asks 'what should I watch tonight?'"), names that exact trigger. I never read it.

THE RULE: the owner's preferences are now documented in FOUR places, none of which knows about the others, and they disagree:

 1. lpt-hub/research/miscellaneous/tv-movie-taste-profile.md -- RICHEST (20 KB, structured, drop list + why), 2026-03-29. In the shop repo (lpt-hub), not in the research vault it is referenced from.
 2. research/.github/copilot-instructions.md -- the POINTER. Names exact triggers and the exact path in (1). Stale path: it says research/miscellaneous/... but the file actually lives at research/research/miscellaneous/ and lpt-hub/research/miscellaneous/. Two copies exist with different sizes (14,046 vs 20,227 bytes) -- hash before trusting either.
 3. VS Code Copilot memory store, movie-preferences.md -- written 2026-05-31, SHORTEST, and currently the most-recently-written, which is exactly why I trusted it. Its watch queue held a show that had already been dropped.
 4. authority DB memories -- had NOTHING until today (memory_search "tv show movie preferences" = 0 rows).

WHAT I GOT WRONG, and the generalisable half of it: I ranked sources by freshness and by which one my search surfaced first, not by which one is authoritative. A 20-line cache file written later beat a 20 KB structured record written earlier, and the cache happened to contain one stale line -- so I re-recommended a show the owner had already dropped. Freshness is not authority. Authority is the structured record with a drop list and reasons; a cache that restates it is a cache, and a cache can carry a stale line.

SECOND RULE, cheap and permanent: a WATCH QUEUE records an INTENTION, never evidence that a show is unwatched. "Starting Season 1" means someone intended to start it -- it does not mean they did, and it does not mean they did not finish it or drop it. Before recommending any title from a queue, look for a drop note for that title. The profile's Known Anti-Patterns section is where drops belong; if a title is queued and dropped, the drop wins and the queue line must be struck.

WHAT I CHANGED (2026-09-23, all verifiable):
- lpt-hub tv-movie-taste-profile.md: added a `### Person of Interest` anti-pattern entry with why it failed and the warning it creates, plus a status note; version history bumped v2.1 -> v2.2.
- Copilot memory movie-preferences.md: Watch Queue emptied; added a "Dropped / Bored Out" section with Person of Interest and the rule that a queue line is not evidence of unwatched.
- authority DB memories: new row (id 21145, category=preferences, importance=9) superseding 21143, naming lpt-hub's profile as the SOURCE OF TRUTH and carrying the drop note. NOTE: `save_memory` via ps_action FAILED ("Failed to record memory via unified memory service", error_log id 1356) -- underlying cause was `sqlite3.OperationalError: database is locked` at app/services/unified_memory.py:196, and the direct POST /ceo/db/memories took ELEVEN attempts over ~60 s before it landed. A one-row insert needing 11 tries is the six-writers-on-one-SQLite problem (P2127/P342), not a fluke.

WHAT IS STILL BROKEN AND SHOULD BE BUILT: there is NO tracked watch record anywhere. authority DB `watch_history` = 0 rows; `ps_watch_videos`/`watch_rooms`/`watch_bookmarks` are an unrelated YouTube-ish feature; HA only knows `media_player.control_room` exists. So every future recommendation rests on a 2026-03-29 snapshot plus one honest correction. The fix is not a bigger document -- it is a one-line capture ("watched X, thought Y") that appends to a durable store and is read before any recommendation. The owner was asked and has not answered; do not build it unasked.

LESSON FOR THE NEXT SEAT: when asked for anything about the owner's personal tastes, read the POINTER file first (research/.github/copilot-instructions.md), then the richest record it names, and only then any cache. Do not reach for grep-and-stop at the first plausible file. The single worst failure mode this seat has is a confident answer from the wrong copy.
