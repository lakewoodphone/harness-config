**L6166 · In a shared tree, any directory-scoped git add is a sweep - I did the narrow version of P13 and committed another session's entries**

Made by me, 2026-10-13, while committing the Sticky Brand incident record — and it is a narrower repeat of **P13**, so P13's rule needs sharpening rather than restating.

**What I did.** After writing five journal entries I ran `git add journal/entries` and committed. The commit (`5b5add2c`, pushed) swept in entries other sessions on this machine had written and not yet committed — `D3129`, `D3130`, `H3572`, `H3573`, `H3574`, `H3576`, `H3577`, `H3579` — under a message that named only my own. Nothing was destroyed (`journal.py check` after the fact: **0 errors**, so no entry was a partial write, and the entries are preserved), and nothing reached a wrong machine. What was lost is attribution and intent: a future reader sees other sessions' work under my description, and those sessions may have staged those files themselves with a message that said something specific.

**The sharpened rule.** P13 says `git add -A` sweeps other work. The narrower form is worse because it looks careful: in a shared tree, **any directory-scoped `git add` is a sweep** — `git add journal/entries`, `git add docs/`, `git add tests/` all take whatever else is sitting there. Add the **exact file paths**, or better the ids (`journal/entries/*/P3162.md`), and never a directory. Verify with `git show --stat HEAD` *before* pushing, not after: I only discovered this by reading the stat of a commit I had already pushed, which is too late to amend without a force-push (forbidden here).

**Also worth keeping from the same session:** `git worktree add` bases on **HEAD**, not on the working tree. Before copying a file from a worktree into a live tree, compare the live file against `git show HEAD:<file>` — if the live file is dirty, the copy silently destroys another session's uncommitted work. I checked this for the four files I deployed (all `IDENTICAL-TO-HEAD`, so the copies were exact); had they not been, the deployment would have been a data-loss event, not a patch.
