**L3352 · iOS com.apple.webcontent-filter: PermittedURLs is an exception list, not a whitelist; AllowListBookmarks is the whitelist**

`PermittedURLs` in `com.apple.webcontent-filter` is NOT a whitelist. It is an exception list layered on
top of Apple's automatic adult-content filter. Ordinary non-adult browsing still works.

Apple's own words (Device Management reference, and the machine-readable schema in
`apple/device-management`, `mdm/profiles/com.apple.webcontent-filter.yaml`):

> "`PermittedURLs` — An array or URLs that are accessible whether or not the automatic filter allows
> access. Use when `FilterType` is `BuiltIn`. Requires that `AutoFilterEnabled` is `true`."

Apple's Deployment Guide says it from the operator's side, for the setting labelled "Allowed URLs":

> "Add URLs to this list to permit access to certain websites, even if they're considered adult by the
> automatic filter. If you leave this list empty, access is permitted to all nonadult websites except
> for those listed in Denied URLs."
> — https://support.apple.com/guide/deployment/web-content-filter-payload-settings-depc77c9609/web

THE KEY THAT IS A WHITELIST is `AllowListBookmarks` (iOS 14.5+; `WhitelistedBookmarks` before that),
surface-labelled "Specific Web Sites Only". Apple's legacy reference is explicit: "If present, these URLs
are added to the browser's bookmarks, and the user is not allowed to visit any sites other than these."
Each array item is a dictionary with REQUIRED `URL` and `Title`. Apple's published hole: `.apple.com` and
`.icloud.com` hosts stay reachable even when not listed.

Second correction from the same research: `FilterBrowsers` and `FilterSockets` are documented
"Use when `FilterType` is `Plugin`" — they are not switches that extend the `BuiltIn` filter to app web
views or to sockets. `FilterSockets = true` additionally requires `FilterDataProviderBundleIdentifier`
("Required if `FilterSockets` is `true`"), so setting it in a `BuiltIn` payload makes the payload
non-conformant and buys nothing. A `BuiltIn` filter is a WebKit web filter; it never sees raw sockets.

Both misreadings were already written into our own docs and had to be corrected:
- `deploy/waze-mdm/docs/family-phone-drn39-plan.md:102-104,109-110` — claimed her phone gets a
 "whitelist" with `FilterBrowsers=true` applying to in-app web views, concluding "browsing is restricted
 to the whitelist". It is not. The phone browses the ordinary web, minus adult content.
- The generator `deploy/waze-mdm/scripts/build-family-filtered-profile.py:46,145` sets `PermittedURLs` and
 calls it a whitelist in its own comment.

Our own hardware already proved Apple's text before we read it: with
`PermittedURLs = ["https://mdm.abletelsolutions.com/*"]` the phone still reached the ChatGPT signup flow
from Settings, and only the supervised PAC proxy blocked it (`KIOSK_OPTIONS.md:435` and `:77`). When a
docs claim and a physical measurement disagree, the measurement was already there — read it first.

Corroboration for the non-whitelist reading, both vendor docs, fetched 2026-10-05:
- Jamf: "the Permitted URLs field does not operate as a safelist (only allowing sites in the list)" —
 https://support.jamf.com/en/articles/11025702-what-does-the-built-in-web-content-filter-in-jamf-school-do
- Cisco Meraki separates the modes: "Auto-filter: Web content automatically blocked based on filters
 pre-defined by Apple. Allow list bookmarks: Only allow access to specific websites/URLs."

Naming trap that caused the confusion: Jamf's own UI label "Allow List Bookmarks" is described with
"Allowed URLs" (exception-list) semantics, while Apple's schema makes `AllowListBookmarks` the whitelist.
Trust Apple's key-level schema over a vendor's UI label.
