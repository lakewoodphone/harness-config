**L3352 · The comms duplicate writer is identifiable: session_id 'ptf-thread-<phone>' re-inserts messages the Dialpad path already stored under the message id**

**Recorded 2026-10-08 (ZABZ-YOGA), from watching one real outbound SMS land. This is the mechanism
behind pain P2862, and it names the fix.**

A message was sent to a customer at 2026-10-08 00:44Z (Dialpad id `5107696553730048`). `dialpad_sms_cache`
on `secratary` holds **two rows for that one message id**:

| id | session_id | created_at | fetched_at | lag |
|---|---|---|---|---|
| 1124524 | `5107696553730048` | 2026-10-08T00:44:18.761Z | 2026-10-08T00:44:19.573Z | **0.8 s** |
| 1124532 | `ptf-thread-8455218536` | 2026-10-08T00:44:21.880Z | 2026-10-08T00:45:04.737Z | 43 s |

**Two writers, two keys.** The websocket path keys the row on the **Dialpad message id**. The website's
thread ingest keys it on the **thread** (`ptf-thread-<phone>`) and writes the message again — so it has
nothing to dedupe against and cannot ever know it has already stored that message. Re-polling the same
thread therefore re-appends the last N messages with fresh timestamps, which is exactly the shape
measured for mrs vahab: four real messages, 168 rows, copies up to 44 each, each copy carrying `ptf-*`
ids beside the original Dialpad ids.

**The fix, concretely.** The `ptf-thread-*` writer already holds the Dialpad message id in the payload
it is storing — it must, because the row it writes carries `message_id=5107696553730048`. So it needs an
idempotency key on `(message_id, direction)` rather than a fresh insert per poll, which is the same
"one writer, one key" rule the PBP work needed for `orders`. Nothing else about the ingest has to change.
Then dedupe the rows already written.

**Why it stayed invisible.** `lpt ticket` folds duplicates for display and says so in passing ("110 for
the customer; showing 9 distinct; 101 duplicate row(s) folded away"), and the folding is presented as a
feature. A reader sees a clean timeline and a large number explained away. The tool that people look at
was absorbing the defect instead of surfacing it — which is the general lesson: **when a reader silently
collapses duplicates, nothing upstream ever gets fixed, because the symptom is invisible from the only
view anyone uses.** If a dedupe exists, it should also increment a counter that shows up somewhere an
operator reads.

**Until the writer is fixed:** dedupe by content before answering anything about how much contact a
customer has had, and never read a comms row count or a "last contacted" date as a measure of contact.
Both `WO2607160004` and `WO2607240002` looked "recently active" to me tonight purely from re-ingested
copies.
