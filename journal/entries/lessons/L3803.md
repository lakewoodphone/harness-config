**L3803 · CORRECTION of L3799: the failure-class shift is NOT attributable to the budget change, and the measurement boundary was wrong**

`L3799` is WRONG. It attributed a failure-class shift to the company's budget change, and the attribution fails twice over. Corrected here rather than edited, because the record of having been wrong is worth more than a clean entry.

**What `L3799` says:** that the 07:23Z edit of `/opt/company/app/autopilot.py` raised the work budget and added evidence-based completion, and that this "moved the failure class": `STEP_BUDGET_EXHAUSTED` 32 sessions → 5 and `STALLED_REPEATING_OUTPUT` 9 % → 38 %, with `work_sessions` split at 07:23:00.

**Why it is wrong:**

1. **The 07:23 edit was not the budget change.** `diff autopilot.py.bak-item80-20261014T072225Z autopilot.py` → **69 changed lines**, none of them `_WORK_MAX_STEPS` and none of them the `[ARTEFACT:]`/`[OUTBOUND:]`/`[TASK-CLOSED-BY-SESSION:]` markers. It is a **calendar-pinned daily-reconciliation gate** (ledger items 80/173) whose own comment records the measurement behind it: *"last run 20.87h old, ZERO ok rows for today - the old gate said SKIP; and 2026-10-12 got no run at all (36h between run 294 at 10-11T14:45Z and run 295 at 10-13T02:49Z)."* A real fix, a different one.
2. **The budget change was already live before it.** `grep -nE "_WORK_MAX_STEPS =" autopilot.py.bak-item80-20261014T072225Z` → **`2875: _WORK_MAX_STEPS = 20`**, and the same backup contains 5 occurrences of the evidence markers. So P1/P4 predate 07:23 (most plausibly the "446-line uncommitted production fix" preserved at 01:58Z, `H3648`); their landing time is NOT established.
3. **The split point was invalid even for the right file.** A Python edit takes effect when the PROCESS loads it, not when the file is written. `systemctl show company-api -p ExecMainStartTimestamp` → **11:58:34Z**; `journalctl -u company-api` shows boot 01:14:09, a scheduled restart at **05:35:38** (NRestarts counter 1), then 11:58:34. The process that lived from 05:35 to 11:55 **never loaded the 07:23 file**, so both halves of my table ran identical code.

**What survives:** the time series itself (65 sessions 00:00-07:23 with 25 completed, 32 budget-exhausted, 6 stalled; 26 sessions 07:23-11:50 with 8 completed, 5 budget-exhausted, 10 stalled). The completion difference is inside noise at n=26. The failure MIX moved and the outcome did not, **and the cause is unknown.** The only defensible conclusion is that `STALLED_REPEATING_OUTPUT` is the largest residual failure class in the latest window, so P3 is the right thing to build next.

**Also wrong in the same entry, corrected:** it repeated the company figures from a rolling window that was itself defective (`L3801`) — ~123 USD per 7 days and ~17.5 USD/day are the corrected numbers, not 140.42 and 20.06.

**The general rule, which is the point of writing this down:** *the boundary of a behavioural measurement is when the running process picked the code up, not when the file was written.* Before splitting any time series on a file mtime, read `ExecMainStartTimestamp` (systemd) or the process start time, and confirm that the boundary you are splitting on is a boundary the running code crossed.

**Three self-corrections in one session, all the same shape:** the predicate matched a denial (`L3796`), the output window straddled two timestamp formats (`L3801`), and now the boundary was an mtime rather than a process start. None of the three was a wrong opinion — each was a **number that looked right**. That is the measured `wrong-data` failure the owner's own corpus ranks first at 12 % of sessions, and the reason the audits keep finding it is that every one of these errors was invisible in the result and visible only in the predicate.
