**L1773 · reminders.recurrence was a decoy, create_event had no recurrence, and the real recurring mechanism is standing_work_orders cron**

TWO DECOY FIELDS THAT LOOK LIKE THEY WORK AND DO NOT — measured 2026-09-16 on ZABZ-YOGA against the secratary live DB.

1. `reminders.recurrence` is decorative.
 `app/database.py` `create_reminder()` accepts `recurrence`, and the column exists, but grep across the whole repo found NO caller that passes it and NOTHING that reads it. Live check on `/home/zabz/personal-secretary-mvp/data/secretary.db` (secratary, 2026-09-16 19:48Z): 406 reminder rows, `recurrence` non-NULL on **0** of them. A row marked 'monthly' would have been parked at status='sent' after its first delivery and never returned.
 Fixed by commit 85f9728ad (branch `fix/recurring-reminders-rebased`, pushed to origin): `normalize_recurrence()` + `next_occurrence()` in database.py, `mark_reminder_delivered()` re-arms a recurring row, and the token is plumbed through the `schedule_reminder` chat action, `POST /api/v1/reminders`, and the two tool schemas. 15 new tests, 194 passing.

2. The working recurring mechanism was already there and is somewhere else.
 `app/services/work_orders.py` `_advance_schedule()` supports `schedule_type` in {interval, daily, cron} and uses `croniter` for cron. `schedule_type='cron'` + `cron_expression='0 9 15 * *'` is already "9am on the 15th of every month", fully consumed by `process_standing_work_orders()` on every autopilot tick. Before adding recurrence to a table, check `standing_work_orders` first.

3. `google_calendar.create_event()` has NO `recurrence` parameter.
 `app/services/google_calendar.py:462` builds the request body at ~496-548 and inserts at ~576; nothing sets `body["recurrence"]`, although Google's API accepts it there. Also: `_simplify_event()` (line 781) DROPS the `recurrence` field, so `list_events()` can never show you a rule — verify recurrence with a raw `events().get()` or `events().instances()`, never through the wrapper.
 A standalone, idempotent creator now exists: `scripts/calendar-create-recurring-event.py`. It reuses `_build_service`/`_resolve_account`/`_calendar_id`, refuses to run when `is_mock_outbound_enabled()`, scans for an existing event with the same summary+RRULE before inserting so a re-run cannot duplicate, and prints the read-back.

4. `is_mock_outbound_enabled()` (`app/services/shadow_outbound.py:16`) is just `os.environ.get("MOCK_OUTBOUND_COMMS") == "True"`. When true, `create_event()` returns id `calendar_mock_shadow` and writes nothing. Always check the env of the *live process*, not just `.env`: on secratary it is unset in both, and `is_mock_outbound_enabled()` returned False inside a real creating process on 2026-09-16.

5. `pytest.ini` sets `--basetemp=.pytest-tmp-next`, and that folder can be OS-locked on Windows, producing `PermissionError [WinError 5]` on every `tmp_path` test. This is pre-existing and documented in `docs/drn/2026-07-08-reliability-api-endpoints.md`. Workaround: `--basetemp=.pytest-cache-local\tmp-<name>`, and `mkdir` the parent first or pytest fails with FileNotFoundError.

6. The secratary checkout is NOT the same history as origin/master. `/home/zabz/personal-secretary-mvp` is at c239a9b1, which is not fetchable from origin, on branch `master`, with 20+ uncommitted modified files including `app/main.py`. Do not overwrite files there to deploy a change; rebase onto current origin/master and let the normal deploy path carry it.
