**L1556 · A verification is not valid until you have watched it fail on a known-bad input: my esbuild syntax check never ran, and LASTEXITCODE after a pipeline reports the wrong command**

**Evidence, 2026-09-15, round 7.** Two rounds of this record claimed that edited files had been
"`esbuild --loader=ts` syntax-checked". The check never ran. It was discovered while trying to use the same
check again and getting a contradictory result.

## The two faults

1. **`esbuild` is not installed in the worktree.** `npx --no-install esbuild` fails on *every* input, including
 an untouched file, because the package cannot be resolved.
2. **I read `$LASTEXITCODE` after a pipeline.** The command was
 `npx ... esbuild ... 2>&1 | Select-Object -First 3`, and `$LASTEXITCODE` then reports **`Select-Object`'s**
 exit code. So the pipeline "succeeded" unconditionally.

Together: **a check that reports success unconditionally, on a tool that was never running.** Round 5 recorded
OK for six files and round 7 recorded FAIL for ten — both from the same non-check, so neither carried
information.

## How it surfaced, and the rule

Round 7 reported FAIL for files that had **passed in round 5 without being touched in between**. An invariant
that flips with no intervening change is a **broken check**, not a broken file. That is the tell.

**RULE: a verification is not valid until you have watched it fail on a known-bad input and pass on a
known-good one.** The cheap proof, for any checker, is a two-file control — here: `const x: = 1` must FAIL
(it did, `1:10 Type expected.`), an untouched real file must PASS (it did). I ran that **before** trusting a
single result, and then the real check reported **ALL PARSE** for all twelve files edited across every round.

**Second rule:** `$LASTEXITCODE` after a pipeline is the exit code of the **last** command in it. Run the
command you care about bare, or read `$?` immediately after it alone.

## What this is a second instance of

The PART-122 lesson was: *a warning emitted by a test harness is a claim about the harness until the harness
is checked.* This is the same failure one level out — **a green line from a verification tool is a claim about
the tool.** Both cost time; both were cheap to settle; both had been trusted because the output *looked* like
the thing being verified.

## Scope of the correction

- Handoff **H265** and PART-124's §4/§6 repeat the invalid claim. Superseded by this note.
- **The round-5 change is unaffected.** Its real evidence was the test suite (116 passed, and the new assertion
 deliberately broken to confirm it fails), which used no pipeline and a validated control. The syntax claim
 was decoration on a verification that stood on its own — which is exactly why the change is still sound and
 the claim was still wrong.
