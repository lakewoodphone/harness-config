**L1916 · Committing a file makes it branch-owned, so checking out another branch DELETES it from disk**

# L1912 — committing a file makes it branch-owned, so checking out another branch DELETES it from disk

## What happened

Working on the authority's `personal-secretary-mvp` checkout, I found seven customer-path files
that existed only in the working tree (most importantly `scripts/lpt-sync-to-production.py`, the
live production bridge, 89,945 bytes, uncommitted). To make them survivable I staged and committed
them **on a new branch** `rescue/authority-customer-sync-20260917` (`d9b33c9b`) and pushed it.

Then I switched the checkout back to `master` — reasoning, correctly, that the running service
resolves its cwd and I should not leave the host on a surprising branch.

**Every one of those seven files vanished from disk.**

## Why — and why it is not obvious

`git checkout <branch>` removes files that are **tracked on the current branch but absent on the
target branch**. Once I committed them, they were no longer untracked; they were files this branch
owned. `master` does not contain them, so git deleted them — the standard, intended behaviour,
identical to the `git rm` in the other direction. The rule I had in mind — *"a checkout never
deletes untracked files"* — was true and irrelevant, because committing had changed what they were.

The trap is that the safer action (making work durable) silently changed the class of those files,
and the next innocuous action (restoring the branch) then destroyed them.

## What saved it

**The commit came first.** Everything was recoverable from `d9b33c9b`, which was already pushed to
`origin`. Recovery was `git checkout rescue/authority-customer-sync-20260917 -- <paths>`, then
verification that every file's md5 matched the branch.

The near-miss: had I run `git checkout master` **before** committing — the natural order if I had
been "tidying up" first — all seven files would have been unrecoverable, including a 76 KB
customer-stall watchdog and 60 KB of production sync logic that exist nowhere else.

## The rule

1. **Make work durable before changing anything about the tree.** Commit to a branch and push, in
 that order, before any `checkout`, `switch`, `clean`, `stash`, or reset.
2. **Switching branches is not a no-op on a tree that held untracked work you have since
 committed.** Ask "what does the target branch *not* have?" before switching.
3. **After any branch change on a machine that runs something, verify the files, not the branch.**
 `systemctl is-active` said `active` and the script's own md5 was fine only because I checked —
 the process had it loaded in memory and would have reported healthy while the on-disk copy was
 a 60 KB older version.
4. **A checkout that reverts a tracked file to HEAD is the same hazard in miniature.** On `master`,
 `lpt-sync-to-production.py` was *unmodified* relative to a HEAD that predates the fix, so
 `checkout master` restored master's 28,797-byte version over the live 89,945-byte one. "Clean
 per `git status`" did not mean "current".

## Evidence

- `git show rescue/authority-customer-sync-20260917:<path> | md5sum` compared against
 `md5sum < <path>` for seven files — all MATCH after restore, and the four critical ones MISMATCH
 (file absent) before it.
- `git status --porcelain | wc -l` → 167 before, 167 after; the tree was left in its original shape.
- `systemctl is-active secretary-api` → active, before and after.
- Branch `rescue/authority-customer-sync-20260917` = `d9b33c9b`, pushed to
 `origin/rescue/authority-customer-sync-20260917`.
