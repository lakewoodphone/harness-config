**L3844 · Three traps: comms phone columns, the two order-status gates, and lptcase new's filename**

Three tool traps hit while creating one work order (Zombeck, WO26101812752), all measured 2026-10-18:

1. `communications` HAS NO `fromNumber`/`toNumber`/`phone`. The real columns are `phoneNumberFrom`, `phoneNumberTo`, `contactPhone` (plus `content`, `contactName`). A search on the wrong names returns 0 ROWS AND EXITS CLEAN, so it looks like a real negative. Proof it was wrong: `select count(*) filter (where coalesce(to_jsonb(communications)->>'fromNumber','') <> '')` on operational returned 0 of 96,027 rows. Lesson, general: before believing a zero, count how many rows carry the field you filtered on. Same family as L3796/L3798.

2. `lpt-write order create --status AWAITING_APPROVAL` is REFUSED, and correctly: gate 1 is the database's orders.status enum (has AWAITING_APPROVAL), gate 2 is website_db.ORDER_STATUSES (does not). The intersection is only AWAITING_DIAGNOSIS, AWAITING_PARTS, CANCELLED, READY_FOR_PICKUP, UNFIXABLE. So an order whose diagnosis is finished is created `AWAITING_DIAGNOSIS` and then moved with `lpt-write status set`, which validates against the database enum alone. Also: `customer create` has no `--reason` flag (order create does), and `total`/`--amount` are always PRE-tax (6.625% lands on top; 150 -> 159.94).

3. `lptcase.py new <slug> --name --phone --device` CONCATENATES device+name+phone+date onto the slug argument, so a descriptive --device produced a 130-character filename with the date twice. Pass a short slug and a one-word --device, or rename both the case file and its sync record in the same minute (nothing references them yet). The standard says never rename an existing file - true for a file that has been read by anything, not for one 10 seconds old.
