**L222 · 2026-10-21 · A router that infers a capability from prose will route prose to the only model that declares it — exclude the provider, then prove it with a live call, not a config diff.**

The revoked Google key did not stop 3,627 calls in 7 days: **2,692 of 2,709 Google routing decisions carried `needs_vision=1`** because the router sets that flag from message *keywords* (`image`, `label`, `scan`, `photo`, `receipt`…), so ordinary department and VS Code text ("scan this label") demanded a vision-declaring lane, and `gemini-3.5-flash-lite` ($2.50/M) was the cheapest one. Max prompt was 16.4k tokens and **zero** calls crossed the 150k long-context bonus, so the "long-context Gemini" path was never the reason. Fixed with the gateway's own supported lever — `AI_GATEWAY_EXCLUDE_PROVIDERS=google` (`app/config.py:1326` → `ai_gateway._excluded_providers()` → `gateway_available_providers()` → `smart_router._build_candidates()`), **not** `AI_GATEWAY_PROVIDER_PREFS_JSON`: that JSON is parsed by `_provider_prefs_for()` but applied only `if provider == "openrouter"`, and OpenRouter was removed in June 2026, so shaping it would have changed nothing while looking like a fix. `.env` alone is not live config — `main.py` builds `Settings()` once at import — so the change was applied to the running singleton through `POST /settings {"apply":true}` (no restart) and written to `.env` for the next start.
*Proven live:* plain `secretary-fast` → 200 `deepseek/deepseek-flash` "17 × 23 is 391"; a 64×64 solid-red PNG (zlib+struct, no PIL) on the same alias → 200 "Red / Vision confidence: high"; `model_usage` 357955/357956 `provider=deepseek success=1`; `/v1/models` 33 → 26 models and 7 → 0 Google ids. The block was a **capability flag, not the model**: `deepseek/deepseek-flash` answers images while `deepseek/deepseek-v4-flash` carries `supports_vision: False`.
*Rules:* (a) excluding a provider does **not** close a literal-id pin — `prepare_request()`'s catalogue-pin branch (`ai_gateway.py:2314`) checks only `provider == "deepseek"`; measured: pinning `google/gemini-3.5-flash-lite` still left the box and returned 502 (upstream 400) until the effective `google_api_key` was blanked in the settings layer, which makes `_resolve_upstream()` refuse with no outbound call; (b) to bring Google back: `POST /settings {"remove_keys":["google_api_key","ai_gateway_exclude_providers"],"apply":true}`, delete the env line, confirm the ids return in `/v1/models`, then make one live call; (c) a keyword-derived `needs_vision` turns "cheapest vision lane" into a routing policy nobody wrote — count `needs_vision` per provider before believing a provider was needed for capability. → `docs/GATEWAY-GOOGLE-EXCLUDED.md`

*Amended 02:42Z, same session, visibly rather than quietly:* applying the exclusion exposed a latent bug - `_gateway_fallback_candidates()` (`ai_gateway.py:4536`) calls `route_request()` **without** `direct_deepseek_enabled`, so once Google was gone every `secretary-fast` request logged `smart_router outage: no_eligible_model` (all DeepSeek ids rejected `direct_deepseek_disabled`) while the primary call succeeded on the very lane the fallback could not see. One-line fix at `ai_gateway.py:4541`, published by atomic rename, then `systemctl restart company-api` at 2026-10-21T02:39:38Z (9 s to `/health` 200, PID 2226115 -> 2392846); **0** such errors afterward. The setting needed no restart; the code did. `secratary` was never contacted.
