**L12172 · An empty wake ledger is an unfiled project, not a finished one - the personality loop idled for six nights that the owner believed were worked**

MEASURED 2026-10-21. The owner asked whether the personality system was being worked on every night. It had not been touched since 2026-10-15T17:48Z, and the wake machinery was healthy the whole time.

The ledger (/root/work/work.db) held 13 personality-system items, every one `done`, zero `todo`. The wake log shows the project being queued and then refused, correctly:
2026-10-16T06:38:04Z refused 1 queued project packet(s) that could only answer nothing-todo: cfo, personality-system, rental-system
2026-10-19T00:14:03Z refused 1 queued project packet(s) ...
2026-10-20T00:11:03Z refused 2 queued project packet(s) ...
The last real shift (2026-10-15T17:48Z) ended with claim-next answering nothing-todo and the contract telling it not to invent work. So the loop did exactly what it is designed to do: it asked for work, was told there was none, and refused to spend $0.09 to discover that again.

The failure is upstream of the loop and it is mine. Closing the last item is treated as "the project is finished", but "finished" here meant "nothing left in a list I wrote", not "the product is complete": the report had only ever been generated for synthetic personas, no session record had ever reached a completed state, and the known quality limits in docs/REPORT-QUALITY.md (one model measured, explanation and reflection never invoked, repetition gate blind to paraphrase) were all still open. None of that had a row, so none of it existed as far as the waker was concerned.

The rule that follows: an EMPTY LEDGER IS NOT A FINISHED PROJECT, IT IS AN UNFILED ONE. For any project the owner has said must be worked on continuously, the nightly loop's supply of work is part of the project - check `state,count` before believing a quiet project is a done one, and when the queue is empty, read the product's own verification docs for measured gaps and file them. A prose `remaining` list in the state file (personality-system.json still said work_remaining: true) does not feed the loop; only rows do.

Detect it next time with one query, not a story: `sqlite3 "file:/root/work/work.db?mode=ro" "select state,count(*) from work_item where project='<p>' group by state"` plus the last three lines of the wake log mentioning the project. A project with done>0 and todo=0 that the owner believes is active is a filing failure, not an idle project.
