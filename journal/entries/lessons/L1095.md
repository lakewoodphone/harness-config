**L1095 · A DSH window costs what its running agent costs, not what the window costs; the engine is not the bottleneck and threads/cores cannot help it**

Cost of a DSH window is a function of whether ITS AGENT IS RUNNING, not of the window count. Measured
2026-09-14 on ZABZ-YOGA with 10 windows open and all 10 sessions running=true:

- The engine is NOT the bottleneck and does not degrade with windows. With 10 windows attached its
 cheap-call latency was p50 5.8 ms / p95 16.6 ms, and an 8-way burst p50 31.0 ms -- FASTER than the
 one-window baseline measured on 2026-09-11 (p50 11.9 ms / p95 99 ms). 13 OS threads, ~0.08 of one
 core, private memory oscillating 1307->1441->1390 MB in two minutes (busy, not leaking).
- Per window: agent generating = 1.0-1.1 of one core and ~750 MB private; window quiet = 0.24-0.28 of
 one core. Ten quiet windows ~ 2.5 cores; ten generating agents ~ 7 cores of 22, plus 90 Edge
 processes and 7.7 GB private.
- The tight resource is COMMIT, not CPU: 28.6-28.8 GB of 31.61 GB physical, ~2.8 GB headroom, draining
 ~370 MB/min with ten agents running. Not paging yet (1.6-10 pages/s, pagefile 0.13 GB used, disk
 idle, CPU boosting at 132% of nominal). Crossing physical is the tripwire where it will really slow.
- Fixed overhead that has nothing to do with windows: Playwright MCP's headless Chrome (22 processes,
 1,740 MB, alive whether or not browser automation is used), personal-secretary uvicorn (2,461 MB and
 ~0.22 of a core continuously), TextInputHost (1,195 MB -- abnormal for an input host).

MEASUREMENT DISCIPLINE that these numbers depend on, learned the hard way this session:
1. Summing WorkingSet across ~90 Chromium processes DOUBLE-COUNTS shared pages; report private bytes.
 Working set said 9.2 GB where private said 7.7 GB for the same 90 processes.
2. A cumulative CPU-seconds column says nothing about now. Take a DELTA over an interval. Three
 windows were at 104%/113%/103% of a core in a 20 s delta while the machine-wide load counter read
 17-38%; a per-process CPU ranking by cumulative time would have ranked them by how long they had
 been open, not by what they were doing.
3. In PowerShell, $pid and $args are read-only automatic variables. A foreach that uses $pid dies
 mid-loop and silently reports zeros; a function parameter named $args produces a malformed request.
 Both cost a measurement cycle here.

because a second `dsh web` on one DSH_HOME corrupts the session log. Any future "would more engines /
threads / cores help" question is answered by that entry plus docs/multi-window/PERFORMANCE-MEASURED.md,
