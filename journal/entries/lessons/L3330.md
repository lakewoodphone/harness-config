**L3330 · For a v2-signed APK, absence of META-INF/*.RSA is not evidence of being unsigned - the signature is in the APK Signing Block**

For an Android release APK built by AGP, "there is no `META-INF/*.RSA` / `*.SF`" is NOT evidence that
the APK is unsigned, and searching for those files is not a valid positive signing test.

AGP signs with APK Signature Scheme v2/v3, which stores the signature in the **APK Signing Block** -
a section immediately before the ZIP central directory, outside the ZIP entry table entirely. It
creates no META-INF entries at all. So a correctly v2-signed APK looks exactly like an unsigned one
to an agent that greps the ZIP entries.

Measured 2026-10-05 (kf1005/android-signed, app-release.apk, 254,259,211 bytes, minSdk 29):

 apksigner verify --verbose
 Verifies
 Verified using v1 scheme (JAR signing): false <- so indeed no META-INF/*.RSA
 Verified using v2 scheme (APK Signature Scheme v2): true
 ZIP entries: 1102, META-INF/*.RSA|*.SF: NONE

The real positive checks, in order of strength:
 1. `apksigner verify --print-certs <apk>` - exit 0 plus the signer certificate.
 2. The certificate it prints must be dug from the KEYSTORE independently (`keytool -list -v`)
 and the two SHA-256 digests compared; a verify that passes proves *a* key signed it, not *yours*.
 3. To prove the signing block physically exists, scan the tail of the file for the ASCII magic
 `APK Sig Block 42`. In the APK above it sits 77,267 bytes from EOF.

docs/audits/kf0928/android-enrolment.md section 2.2 states the negative version of this ("unsigned
because no LPT_RELEASE_* keystore properties") and is correct; docs/audits/kf0928/android-qr-provisioning.md
line 154 proposes `META-INF/*.RSA` as a *fallback* for reading the signing certificate. That fallback
cannot fire on a v2-only APK, so the QR payload script's signature checksum silently depends on
`apksigner` alone being present.
