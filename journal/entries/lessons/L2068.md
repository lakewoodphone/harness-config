**L2068 · A repair that never verifies its write logs a lie forever; a probe with no applicability check invents a crisis**

A "repair" that never verifies its own write will report success forever, and a
probe that cannot be measured from where it runs will report failure forever.
Both were live at once on 2026-09-19 and produced a crisis that did not exist.

WHAT HAPPENED
`personal-secretary-mvp/scripts/watchdog.ps1` `Ensure-MeshIngress` (runs every
15s) published this node's API on a hardcoded office-LAN address and created a
firewall rule. Neither could ever succeed on ZABZ-YOGA, and the code could not
tell.

WHY IT LIED (three independent mechanisms, any one of them enough)
1. `$ErrorActionPreference = 'Continue'` (line 11). A cmdlet's "Access is
 denied" is a NON-TERMINATING error, so it never reaches the `catch`. Control
 fell straight through to `Log "firewall rule created"`.
2. `netsh` reports failure through its EXIT CODE and stderr, which the code
 never read. `& netsh ... | Out-Null` then logged "repaired" unconditionally.
3. The listen address (192.168.50.138) is the DESKTOP's. This laptop is a
 different machine on a different network. The operation was impossible by
 construction, not merely unauthorized.

MEASURED COST
- 29,773 of 31,109 watchdog.log lines (95.7%) were a false
 "portproxy repaired" + "firewall rule created" pair, re-fired every 15s with
 no backoff. Log was 3.1 MB and ~96% falsehood.
- `netsh interface portproxy show v4tov4` was EMPTY and
 `Get-NetFirewallRule -DisplayName 'Personal Secretary API 8002 (mesh LAN)'`
 did not exist, the whole time the log claimed both were repaired.
- The repair also needed elevation, which the process never had.

THE READ-SIDE TWIN
`scripts/ai_platform/mesh_status.py` `_local_node()` probed
`http://192.168.50.138:8002/health` with no applicability check, while its
secretary counterpart HAS a Tailscale fallback. So any node off the office LAN
reported a permanent violation "desktop API not reachable on LAN
192.168.50.138:8002 (portproxy/firewall broken)" and the watchdog wrote an
`activity_log` row every 30 minutes — 150 of them. Verified by SSH during the
"violation": the desktop's portproxy existed and it WAS listening on
192.168.50.138:8002. The reported fault did not exist.

RULES EARNED
1. Never log success from the code path that issued the write. Read the state
 back and log what you observed, not what you attempted.
2. A write that can fail silently must be checked explicitly: `-ErrorAction
 Stop` for cmdlets (otherwise `catch` is dead code), and `$LASTEXITCODE` for
 native tools like netsh. `$ErrorActionPreference='Continue'` makes `catch`
 optional-looking and useless.
3. A repair must first prove it APPLIES to this host — check that it owns the
 address/target before attempting anything.
4. A permanently failing repair must back off (900s here), never retry every
 loop. A repair that cannot succeed and does not know it is an infinite loop
 that lies.
5. A probe must return "not applicable" (None) when it cannot be measured from
 here, and only False when it measured a real failure. `if not x` collapses
 those two into one and invents crises. This is the same failure class as the
 stale-database false crisis: a reading reported without its provenance.
6. Record WHOSE reading it is. mesh_status.py's "desktop" block is measured on
 whichever node runs the script, so drift is now attributed with a
 `hostname` field instead of an assumption.

FIXED
commit 7d4588e8a (branch feat/owner-direct-request-sms). After restart:
0 false lines, exactly 1 honest line, "Mesh ingress not applicable on this
node: 192.168.50.138 is not a local address. Skipping repair (owned by the
desktop)."
