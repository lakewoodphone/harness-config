**L1670 · A kill switch's coverage lives in the deployed artifact; autonomy lives in the caller graph**

## Rule

**A kill switch's coverage is a property of the deployed artifact, and whether a write path is a
hazard depends on its caller graph — not on its existence. Measure both before calling something an
emergency or a fix.**

## What happened

Two rows were filed `critical` within 60 seconds of each other (2026-09-15 22:33–22:34Z) about AI
writes in the lpt production backend: no server-side approval, and — the correction — a kill switch
read in "only three places", none of them the `ai-workspace` service, whose write actions include
sending customers text messages.

Both halves of that are the kind of claim that must be checked against the *running* system:

1. **Coverage.** `grep` over the built tree inside the running container
 (`lpt-lpt-backend:priceguard-20260915-222840`, code at `/app/backend/dist`) found the autopilot
 token in `services/ai-tools/*` and `trpc/routers/adminSettings.js`, and in **no** file under
 `services/ai-workspace/` — so the switch really does not gate the workspace. (Source said three
 files; the build says four. The build is what runs.)
2. **Caller graph.** The workspace's apply services are reachable only through
 `trpc/routers/ai-workspace.router.js`, 8/8 sampled procedures `protectedProcedure`; no timer
 inside the workspace services; and the customer-SMS service's only caller is the workspace
 prompt-planner, itself reached from that router. So those writes require a signed-in person. The
 *exists* claim was true; the *unattended* implication was not.

Without step 2 I would have reported an uncontrolled customer-texting robot and might have taken a
much more destructive action (stopping a customer-facing service) on the strength of it. Without step
1 I would have believed one flag made production safe, which it did not.

## The trap in this exact shape

A first grep returned **nothing at all** for a string the container demonstrably used, because I
guessed the code root (`/app/dist`) instead of reading it (`/proc/1/cmdline` → `node dist/index.js`
from `/app/backend`). An empty grep is a refusal, not a pass — it is the same failure as reading a
stale database and reporting health. The control test (a string that *must* exist) is what exposed
it; without a control, "no hits" would have read as "no problem".

## Also worth keeping

Changing a compose service's environment requires **recreate**, not restart: `docker restart` reuses
the container's environment, so the edit would have looked applied and changed nothing. Verify by
reading the variable from *inside the new container*, and then independently a second time.

## Evidence

- Container env before/after: `AI_AUTOPILOT_WRITES_ENABLED=true` → `false`, `FEATURE_AI_AUTOPILOT=true`
 → `false`; `docker inspect` `running healthy` since 2026-09-15T23:01:58Z.
- Oddly-shaped control that disproved my own grep: `ls /app/dist` → `No such file or directory`.
- `curl` from the authority: `api.lakewoodphoneandtech.com/health` → 200, root → 200.
- Decisions entry `D192`; queue rows #61/#62 answered with this reasoning on the rows.
