**L5284 · `DEPLOY OK` proves the stick matches a checkout, not that the checkout is the mainline. The access kit is 12 commits ahead of `master` and its own gate says PASS.**

Measured 2026-10-15 on ZABZ-TECH, preparing to open a live-access window on a customer machine.

**The gate passed and told me nothing about the thing I needed.** The kit's acceptance test A1 is
`Deploy-LptAccessKit.ps1 -Drive D`, which copies an allow-list and then hash-compares what it wrote.
Run today it printed, for all 21 files, `SAME`, and ended:

```
DEPLOY OK - every deployed file hash-matches the repo (A1 PASS)
```

That is a comparison between **the stick and one working tree**. It cannot see whether the working
tree it was handed is the repo's mainline, and it does not try. Measured on the same clone minutes
later:

```
git rev-parse HEAD -> df642e9f2a80d558b7d28e9aa08c9f77e7930466 (DETACHED)
git merge-base --is-ancestor df642e9f origin/master -> NO
git merge-base --is-ancestor a08a7e57 origin/master -> NO
git for-each-ref --contains HEAD --format='%(refname)'
 -> refs/remotes/origin/zabz/usb-kit-hardening-20261005
 refs/remotes/origin/fix/dialpad-backfill-cursor-20261006
 refs/stash
git log --oneline origin/master..HEAD -- tools/lpt-access-kit -> 12 commits
```

Those 12 commits include the registry-hives folder bug that the first real Deep run exposed, the
handoff defect that conflated *"the tier was available"* with *"access exists"*, and the four
fire-and-forget launcher icons. `origin/master` is `9979b3e11`. **The deployed stick is correct —
it carries the fixes — and the next person to run `Deploy-LptAccessKit.ps1` from a `master` checkout
will ship a kit that is missing all twelve, with the gate still saying `A1 PASS`.**

**This is the exact defect the kit was built to remove.** Its `Deploy-LptAccessKit.ps1` header,
written 2026-10-05, says so in its own words: *"the USB copy of `Collect-PcDiagnostics.ps1` was
25,727 bytes against the repo's 20,354 ... the stick was AHEAD of the repo it was supposed to be
built from. So this script deploys an explicit allow-list and then MEASURES what it wrote."* It
measured, and the drift is back — because "the repo" in that sentence means *whatever checkout you
are standing in*, and the fix only ever compared the stick to that.

**The second reading, and it changes the test.** `origin/master`'s copy of
`teardown/Install-Destructor.ps1` **does** contain `RemoveAuthorizedKeyLine` — while its introducing
commit `a08a7e57` is *not* an ancestor of `master`. The same change reached the default branch by a
different route. So **commit identity is not a test of whether a fix is present on this repo; the
file content is.** Any check written as `merge-base --is-ancestor <sha>` would have reported this fix
absent when it is present. Compare bytes, or grep the file.

**Related, re-measured the same hour.** **P2852** (the teardown could not remove the SSH key line it
added, so our public key survived in the customer's `administrators_authorized_keys`) has a **code
path now** — `Remove-AuthorizedKeyLine` at `teardown/Install-Destructor.ps1:644`, the plan action at
:355-360, the dispatch at :802-803, and the fix is described at :118-119. But it has **never been
exercised**: acceptance tests **A3, A4, A5 and A7 have never been run** — they need an elevated
shell, a reboot and a second vantage point, and `Invoke-Acceptance.ps1` says so rather than skipping
quietly. This stick's own launcher log holds exactly two runs, both `mode=Quick`, and **no access
window has ever been opened from it.**

So P2852 stays **open**, not closed: *the action now has a code path* and *the action has been shown
to work* are different sentences, and only the first one is measured.

**The rule.** When a gate compares two things, say which two. `A1 PASS` answers "does the stick match
this checkout", and a reader under time pressure will hear "the stick is the good kit". Before
trusting a deploy gate, ask what its other side is — and if the answer is "a working tree", check
that the working tree is on the mainline, by content and not by SHA. Same family as **L5216**, where
a handoff said *pushed and remote-verified* and the ref had been rewritten underneath it.

**Not fixed here.** Landing those 12 kit commits on `master` is a real task needing care (neither
containing branch is kit-specific), and it was not on the critical path: the deployed stick is the
fixed one, verified by hash. Open.
