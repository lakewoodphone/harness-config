**L3656 · D2655's exclusion does not work: zeroed FTS pages cannot be rebuilt, measured on a copy**

2026-10-13. I recommended implementing D2655 in queue row #472 and called it "free". I then tested
the mechanism, and it does not work. Recording the test rather than the intention.

WHAT D2655 SAYS. Exclude the FTS5 shadow tables (`_fts`, `_fts_data`, `_fts_content`, `_fts_docsize`,
`_fts_idx`) from backup snapshots - 11.99 GiB of the authority's 23.66 GiB database - and
"rebuild on restore", because they are derivable from `dsh_session_events.raw`.

WHY IT CANNOT BE DONE THAT WAY. The offsite backup does not dump tables; it streams the raw page
image through SQLite's `sqlite_dbpage` virtual table, in order, inside one read transaction, and the
verifier checks the stream length against `page_size x page_count`. So excluding a table can only
mean replacing its pages with something of the same length - zeros - and keeping page_count intact.

MEASURED, on a throwaway copy, not asserted. A small database with one FTS5 table; zeroed exactly the
pages `dbstat` attributes to its shadow tables; reopened:
 PRAGMA quick_check(1) -> DatabaseError: vtable constructor failed: docs_fts
 select count(*) from raw_docs -> 2 (the ordinary table is fine)
 select count(*) from docs_fts -> DatabaseError: vtable constructor failed: docs_fts
 INSERT INTO docs_fts(docs_fts) VALUES('rebuild') -> FAILED, same error
**The rebuild does not rescue it.** The vtable cannot be constructed at all once its shadow pages are
zeroed, so the recovery step D2655 assumes is unavailable, and the restored database would fail a
quick_check and lose the FTS table permanently. Implementing D2655 as written would have produced
backups that are shorter AND unrestorable in the one respect the decision was about. A test on a
throwaway cost two minutes; discovering this after a restore attempt would have cost the corpus.

CORRECTING MY OWN RECOMMENDATION. #472 says implementing D2655 "is free" and is "the prerequisite for
the check". Both halves are wrong. It is not free - it is a change to a 23 GiB database or to a
592-line backup that currently works - and it would NOT by itself let the integrity check run, since
even an 11.7 GiB snapshot does not fit in the 9.0 GB free. I recommended it too fast, and the test
above is why the recommendation is being withdrawn rather than executed.

WHAT WOULD ACTUALLY WORK, for whoever picks this up:
 1. Declare the FTS table with `content=` pointing at a real table (external-content FTS5), so the
 `_content` shadow table is not materialised at all. That removes the 8.47 GiB duplicate from the
 LIVE database, and the page stream then carries the saving automatically with no exclusion logic
 and no restore step. It requires dropping and recreating the FTS table - a schema migration.
 2. Or a logical dump that skips the shadow tables, which is a different backup mechanism from the
 page stream and would give up the byte-for-byte verifiability the current one has.
 3. Or grow the disk.
Option 1 is the only one that shrinks the live database without deleting a row, which is what D2655
requires.

METHOD, again. **A recommendation is a claim, and a claim about a mechanism can be tested cheaply
before it is acted on.** I had the shape of a fix and the authority of a prior decision behind it, and
neither substitutes for running it once on a copy.
