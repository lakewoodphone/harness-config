**L3707 · When a record and its schema disagree, measure which side is wrong before fixing either**

## L — When a record and its schema disagree, measure which side is wrong before "fixing" either

Learned 2026-10-12 on the Shlesinger X201 sync record, which failed validation with three errors:
a root `source` key the closed schema rejects, a missing `updatedAt`, and a missing
`operational.nextAction`.

The tempting move is to delete the offending key from the one file in front of you and move on. That
is how a real convention gets quietly destroyed. The disciplined move is one query across the
corpus first, and it changed the answer completely:

 sync records 413
 carry a root `source` key 19
 missing updatedAt 7
 missing operational.nextAction 13

So all three are recurring, not personal to this file. And then the shape check decided it:

 root source, as an object {machine, recordedAt, tool} 3
 root source, as a plain string 16

Three different shapes means there is no settled convention to bless — the writers disagree with
each other as well as with the schema. That is a writer/schema reconciliation job, not a
one-file edit, and it is now recorded rather than guessed at.

**The rule.** A schema is a contract with 413 parties. Before you edit one record to satisfy it, or
edit the schema to admit one record, count how many parties are on each side and check that the
"correct" shape is actually consistent. `/memories`-style discipline applies to JSON schemas too.

**Corollary, and the reason this file was worth reading:** the honest fix is sometimes "neither —
this is a real defect worth its own workstream", and saying that is better than a fast edit that
makes one file validate while hiding a 19-file disagreement.
