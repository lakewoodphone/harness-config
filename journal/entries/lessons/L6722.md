**L6722 · the convergence job now measures the fork on every run, with the previous number beside it - and the delta path was proved by running it twice**

**The convergence job now measures the fork on every run, so the number stops depending on someone
remembering to ask for it.**

The job already collected every tree; the one instrument it was missing was the fork itself. It is now
recorded in the same status file as everything else, **with the previous run's number beside it**:

```
[03:23:46Z] entries 5149 -> 5151 (+2) pull rc=0
[03:23:46Z] check: -- 0 error(s)
[03:23:46Z] fork across the collected trees: 336 colliding ids (no previous reading)
status: {"result":"converged","detail":"added 2 (entries 5149 -> 5151)","added":2,
 "fork_colliding":336,"free_mb":31193}

[03:27:38Z] entries 5152 -> 5153 (+1) pull rc=0
[03:27:38Z] fork across the collected trees: 336 colliding ids (previous run: 336)
```

**The delta path was proved by running it twice**, not by reading the code — the first run could only say
`(no previous reading)`, and the second had a number to compare against. A field that has only ever been
written is not a field that has been read.

**It is recorded, not alarmed on, and that is deliberate.** The count is *expected* to be non-zero: 336
across the machine trees on 2026-10-16, frozen. A monitor that fired on non-zero here would be the same
false-positive class as the no-loss gate that reported 14 phantom losses earlier tonight. **What matters
is the change**, which is why the previous value is read first and printed beside the current one.

**Three consecutive clean runs** (03:16, 03:23, 03:27), each `pull rc=0`, `check 0 error(s)`, exit 0 —
that is the first time the job has run repeatedly without a failure, and it is running only by hand.

**Still not scheduled.** The line is in the job's own header, commented, with its base64 beside it.
