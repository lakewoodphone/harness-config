**L1485 · Guarding a production-writing tool: audit what the guard still lets through**

LESSON 1 — a guard that compares an order TITLE to a record is blind whenever the
order title is a placeholder. Production holds many orders literally titled
"Repair - <phone>" (the older intake path wrote no device text), so token overlap
against them can never reach any threshold. Evidence: after implementing the
required >=3-token rule, the audit showed 17 of the 30 records it called CREATE
already had a sibling sync record on the same phone that linked a live order, and
13 of those agreed with that sibling on >=3 DEVICE-SUMMARY tokens (up to 48).
Comparing record-to-record instead of record-to-order is what closes it. Always
audit a new guard for what it still lets through (false negatives) before
believing its counts.

LESSON 2 — use device-summary tokens only for record-vs-record matching, not
device+prose. Measured counterexample: a Dell Latitude 3540 record and an
unrelated Canon SX740HS record share a phone, and their PROSE summaries collide
on "awaiting part replacement ordered" (4 tokens) — device+prose would wrongly
refuse the Dell. Device-only overlap for that pair is 0. Choosing the narrower
field turned a false positive into a correct CREATE.

LESSON 3 — a record whose device text field is empty can never be matched by ANY
token rule, so the guard silently waves it through. Legacy sync records store
identity in device.brand/model/modelNumber/storage, not device.summary. When
building any text-matching safety net, first measure how many inputs have EMPTY
comparison text; 3 of 30 did, and they were not findable by the rule as first
written.

LESSON 4 — replicate the write path's lookup set, then widen it, never narrow it.
website_db.create_customer matches phones with a substring LIKE and takes
fetchone(); it over-matches (four customer rows for 3479333365) AND under-matches
(stored '347-998-0486' does not contain a record's '+13479980486', so it would
create a duplicate customer). A read-only guard must see the union of the LIKE
match and a digits-only comparison, over every row — otherwise the guard inherits
exactly the blind spot it exists to cover.

LESSON 5 — prove "read-only" at the server, not by convention. Opening the
session with options="-c default_transaction_read_only=on" and asserting
SHOW default_transaction_read_only == 'on' makes a stray write impossible rather
than merely unintended, and gives a testable claim
(psycopg2.errors.ReadOnlySqlTransaction on a CREATE TEMP TABLE probe). Then still
count rows before/after with a 6-second no-op CONTROL snapshot in between, so an
unrelated delta from the live server cannot be mistaken for the tool's.

LESSON 6 — before promising a push, check the branch is not diverged. `git push`
on a clone that is ahead N / behind M is rejected (non-fast-forward) and the fix
is not mergeable by whoever notices it: this clone of personal-secretary-mvp was
41 ahead / 134 behind, with the 41 belonging to other sessions. Commit locally,
attempt the push, and report the exact remedy instead of merging someone else's
unpushed history.
