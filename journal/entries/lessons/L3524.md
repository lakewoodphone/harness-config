**L3524 · A verification tool must discover its target: --check-card reported a clean card while checking zero files**

Found on a real returned card, 2026-10-11, holding 14,953 files, and it is the more serious
class of failure this system keeps re-learning: **a check that reports health it never
established**.

`GO.EXE --check-card` is the command for verifying a delivered card on the shop machine,
away from the customer's laptop. It built its job-folder path from
`Environment.MachineName` — the machine it was RUNNING on — instead of looking at what was
actually on the card. On ZABZ-TECH, against a card written by LAPTOP-MLRM7RD8:

- it found no `LPT-ZABZ-TECH` folder, so the ledger it read contained **zero entries**;
- and it printed *"the card still holds every one of them"* over those zero files, exit 0;
- and the writability probe ran first, so **checking the card created a stray empty job
 folder on it** — a read-only command that wrote.

Three rules fell out of it, all now enforced in the tool and tested (cases I/J/K of
`run-tests.ps1`):

1. **A tool that runs on a different machine than the one that produced the data must
 discover its target, never assume it.** Enumerate every `LPT-*` job folder and check
 each; do not derive the name from `MachineName`.
2. **Zero is not success.** An empty result — no job folder, an empty ledger, no files
 checked — is a refusal. Print what was not established and exit non-zero. The same rule
 applies to a partial record: "1 folder could not be read" must never end in `VERIFIED`.
3. **A read-only check must not write.** The probe now runs only on the copy path.

Generalised: whenever a verification's scope comes from an identifier the verifier supplies
itself (a hostname, a session id, a "current" pointer), verify that the identifier resolved
to something real before believing the verdict. `--check-card` on the card it was built from
worked perfectly — the bug only existed across the boundary the command was written for.
