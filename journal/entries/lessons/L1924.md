**L1924 · Windows: copying a profile node_modules duplicates junctions and silently tests an older plugin**

## The rule

**On Windows, never build a test home by copying a profile's `node_modules`. Junctions do not copy
as their contents, and the failure is silent and looks like a code fault.**

## What was measured, 2026-09-17, on `zabz-tech`

1. `Copy-Item -Recurse <real>\profiles\web\node_modules <scratch>\...` copies each `dsh-plugin-*`
 junction **as a junction**, so the copied tree has **no `lib/` at all**. The engine then resolves
 `dsh-plugin-remote-fanout` to a *different, older* copy — measured `lib/index.js` 4391 B,
 `package.json` version `0.1.0`, no `resolvePlacementMode` — and runs pre-placement code while
 everything reports success. Three runs of a placement proof produced "child exited 255, no ledger
 record" and it looked like the package was broken.
2. `robocopy /E /XJ` is the *opposite* wrong answer: `/XJ` **drops** the reparse points instead of
 dereferencing them, leaving a 5-entry `node_modules` and an engine that dies with
 `cannot resolve profile bundle "dsh-plugin-attention"`.
3. A **junction** of the profile's `node_modules` for a task-run process **does not traverse** here:
 `cmd /c type <link>\lib\index.js` → `The path cannot be traversed because it contains an untrusted
 mount point.` — the same class `70-remote-fanout-proof.md` §4.4 and `90` §3 recorded. The working
 laptop fixture only worked because its scratch home shares the real `node_modules` through a
 junction that *does* traverse.

## What to do instead

Ask where the bundle names actually resolve from before copying anything: `resolveBundleDir` anchors
on the **dsh installation** first and the **profile directory** second, so a bundle can be resolved
from a copy nobody intends to use. To prove a switch:
`node -e "createRequire('<profile>/package.json').resolve.paths('dsh-plugin-remote-fanout')"` and check
each candidate for `package.json`. **Read the file you are about to run and assert its content**
(`resolvePlacementMode` in `index.js`, the version in `package.json`) — a version number that looks
right is not the revision under test.

## The generalisation

A test fixture that shares the thing under test can pass for the wrong reason, and a fixture that
*copies* it can silently test a different revision. State which one you built, and assert the content
of the code path you claim to have exercised.
