**L2604 · A vitest/esbuild transform can leave a module-scope const as a free identifier, so a guard silently returns false**

In the backend's vitest setup, a module-scope `const` read INSIDE an exported
function can arrive as `undefined` at runtime, and the failure looks like a logic
bug in the function rather than a build artefact. Measured on ZABZ-YOGA,
2026-09-28, `card-payment-completion.service.ts`.

The tell
- `git diff` and `tsc --noEmit` are both clean. The function's own runtime source
 reads correctly, e.g. `String(isCardInPageMetadata)` printed:
 return metadata?.[CARD_IN_PAGE_SOURCE] === "card_in_page" && ...
 i.e. **the const is still a bare free identifier**, not the inlined literal
 `"card_in_page"`.
- So the comparison is `metadata?.[undefined] === 'card_in_page'`, which is false
 for every input, and the gate silently rejects everything.
- The test result is a dead giveaway: the tests asserting "this IS ours" fail while
 the tests asserting "this is NOT ours" pass. When a predicate only ever returns
 `false`, look at the build before the logic.

Diagnosis that worked (fast, no guessing)
A temporary probe test with `console.log` of the constant, `typeof` the function,
the argument, and `String(fn)` found it in two runs. Four guesses at the logic cost
more than the probe did.

The fix
Write the literal where the comparison happens instead of reading the module-scope
binding, and say why in a comment. `metadata?.['source'] === 'card_in_page'` depends
on nothing but its argument, which is what a guard called from a webhook handler
should do anyway.

Note for the harness file policy: `read` showed the file correctly, so this is not
a stale-read problem — it is an esbuild/vitest transform artefact. Do not chase it
in the source text; chase it at runtime.

Corollary: exporting a const and then using it in a hot guard is latent fragility.
Inline the literal in the guard and keep the exported const for callers.
