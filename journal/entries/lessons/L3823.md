**L3823 · The capability was already installed; diagnose the environment, and make the tool grasp the fix**

**L · Diagnosing the environment is not the same as fixing it, and the fix may already be installed**

For hours, every attempt to read a session hit:

 local node has no zstd decoder (needs node >= 22.15 for zlib.zstdDecompressSync)

and I treated that as "this machine cannot do it", routed the whole job through ssh to another
machine, and never once asked **what else is installed here**. The answer was sitting at
`/usr/local/node22/bin/node` — **v22.23.2, with a working decoder, and it is the very binary the DSH
web server runs on** (`ps` showed it plainly). `node` on PATH was `/usr/bin/node` v20. `which node`
and `node --version` both return the PATH answer and neither tells you about a second install;
`find / -maxdepth 5 -type f -name node` finds it in seconds.

**The rule: when a tool refuses for an environmental reason, the environment is the thing to fix, and
the first question is "is the capability already present somewhere on this box".** A blocked tool read
as a permanent limitation is how a five-minute symlink becomes a multi-session detour.

**L · An error message that says what is wrong and not how to fix it is half a message**

`needs node >= 22.15` is true, and useless: it does not say which candidates were tried, which ones
would work, or that one of them is already installed. The message cost hours. So, concretely:

* the failure text now prints `running ${process.version} (${process.execPath})`, every candidate it
 tried, and the exact `export DSH_NODE=...` that fixes it;
* `doctor` names the interpreters that DO have the decoder instead of only reporting a boolean;
* the tools **self-elevate** rather than explain: if the interpreter cannot do the job, they re-exec on
 the first candidate that demonstrably can, testing capability rather than parsing a version string.

**A tool should reach for the fix before it reports the problem.** Capability-fallback, then a message
that names the remedy. A bare "requirements not met" is a decision to stop.

**L · Ranking by term count finds the longest file, not the best answer**

`find "bluetooth"` — looking for the session that had just changed the Bluetooth profile — returned a
page of `=== mesh mailbox` sessions at **300–1019** while the real session scored **61** (and 2 on
another query). Raw occurrence count measures file length and verbosity: those mailboxes are 0.2–1 MB
dumps that paste runtime context repeatedly, so a word appears hundreds of times whether or not
anything happened in them.

Changed to `1 + log2(count)` per term. Same query, same corpus: noise collapses to ~9–12, the real
session ranks third. **For a term-frequency search over heterogeneous document sizes, dampen the
count — presence is the signal, repetition is mostly length.**

And a search that reads only the first 256 KB of each file must not print its top 10 as the answer:
it now states how many matches were read only to the head and that `--full` is the only complete
answer. Measured: the correct session does not appear in the default head-read page at all.

**L · "It is on another machine" was never the problem — three of four causes were local**

The session was on `zabz-tech`, reachable, and `find` returned it on two separate queries. The causes
were a stale node on PATH, a ranking that buried it, and a per-host node-PATH gap on the mac mini —
all of them ours. Worth recording because the tempting story ("sessions are scattered across machines,
of course it is hard") was false and would have hidden three fixable defects. **Before attributing a
failure to architecture, prove that the architecture is where it broke.**

**L · The same `command not found` had a fix in one code path and not another**

The mac mini has node v24.19.0 at `/usr/local/bin/node`; a non-interactive zsh there has no PATH entry
for it. `sessions.mjs` **already knew this** — the inventory path carried a retry searching the usual
install locations, with a comment dated 2026-10-09 naming the mac mini. The session-*file* read path
did not, so **57 sessions across the fleet were unreadable for a defect that had already been solved
in a sibling function**. Fixing one call site of a failure is not fixing the failure: the resolution
now lives in one shared, cached helper and every remote read goes through it.
