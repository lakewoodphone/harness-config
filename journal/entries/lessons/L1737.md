**L1737 · An auth gate written as a substring match on the request path is invisible to a guard census**

**Recorded 2026-09-16 after the LPT website-redo audit. Evidence: `_lpt-audit/LPT-WEBSITE-REDO-AUDIT-2026-09-16.md`.**

The customer login does not fail because of a feature flag. It fails because
`backend/src/trpc/context.ts:106-116` gates every CUSTOMER token on a substring match of the request path against
three prefixes, and the portal's own auth procedures are not among them. Two separate auditors (W2, W4) each
found part of this and neither connected it to the sign-in path because each was scoped to one half.

**The generalisable rule, and it is the same one that produced the "portal ships in production" error:**
*an authentication gate written as a substring match on a URL is invisible to a reader who is looking at
procedures and guards.* The guard chain reads correctly (`customerProcedure` is on all three procedures); the
refusal happens one layer up, before the guard runs, on a path whitelist. So a code reader checking "does this
router use the right guard?" gets a false green.

**Corollary for anyone auditing an auth surface:** check the refusal paths that run BEFORE the guard, not only
the guard itself. Search for string-matching middleware, allowlists, and any `context.ts`-level branch on
`req.path`/`req.url`/`originalUrl`. A procedure being correctly guarded says nothing about whether a call can
reach it.

**And the second-order lesson on reporting:** three documents in this repo asserted the sign-in surface worked or
was merely flagged off. The way to avoid that is not more documents - it is to trace one real call from the
button to the handler, which is what found this. Reading procedures is not tracing a call.
