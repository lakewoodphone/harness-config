**L1567 · PowerShell expands backtick-0 to NUL inside a double-quoted replacement string - and this session produced FOUR checks that gave confident answers while structurally unable to be right**

**Evidence, 2026-09-15, round 12.** I corrupted the same manifest file twice in one round and aborted a repair once. The mechanism of the first is worth keeping because it is silent.

## The NUL byte

I edited a manifest with PowerShell:

```powershell
$c.Replace($old, "...RECURRENCE CLOSED `0d245bcc3...") # wrote a NUL where the 0 was
```

**PowerShell expands a backtick-escape inside a double-quoted string, and `` `0 `` is NUL.** So the commit hash `0d245bcc3` was written as `<NUL>d245bcc3`. `Set-Content -NoNewline` stored it faithfully, and the file then failed a later edit with `Error: cannot edit ... binary file` — the only reason I found it.

**RULE: in PowerShell, never write a literal string containing a backtick-escaped character into a replacement value.** For content edits, do them in Python or with a here-string that is single-quoted, and **verify the artefact afterwards rather than the command's exit code**. A `0` that becomes NUL is invisible in a diff, survives a read as a black diamond, and breaks tools that check for binary content.

## The aborted repair

My first repair script matched a three-line block including newlines, and the file used different line endings than the pattern. It raised, wrote nothing, and the surrounding shell reported the failure — which is the good outcome. **The fix: match each row independently and assert exactly one match per pattern.** A repair that silently matches nothing is worse than one that crashes.

## The broken check

My "are there duplicate rows?" check split lines on `|` and compared the **first** field — but rows have different column counts, so different statuses collapsed to the same token and it reported `13 unique` for 15 rows. **A verification that produces a wrong number is worse than no verification**, because it is trusted. I replaced it with a regex over the whole text that prints all 15 statuses individually.

## The pattern across all of today

This is the **fourth** self-inflicted verification defect in this session, after the `esbuild` check that never ran, the census read from a stale tree, and the mention-count that mistook existence for connectivity. They share one shape:

> **The check produced a confident answer while being structurally incapable of producing a correct one.**

The defence that worked every time was a **control**: a deliberately broken input that must fail, an untouched file that must pass, a printed list inspected row by row. **Run the control before trusting the result** — and when a number surprises me, suspect the instrument first.
