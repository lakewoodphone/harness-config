**L1941 · Never draw an IP conclusion from a bare curl - a WAF 403s any default client, so a table of bare-curl 403s is a table of nothing**

I diagnosed a site as blocking the shop and I was wrong for about ten minutes, because I ran the breadth test with
BARE CURL. Bare curl got 403 from eBay, MobileSentrix, Injured Gadgets and laptopscreen.com's sister site - which
reads exactly like a flagged or banned IP. Re-running the identical test with a browser User-Agent and the SAME
client on two networks showed the opposite: the shop's machine gets 200 / 2.3 MB from injuredgadgets.com while the
AWS VPS gets 403, the sister site is 200 from both, and eBay/MobileSentrix are 403 from both. The 403s were
User-Agent blocks. Only ONE site behaved differently by client IP.
RULE: NEVER draw an IP conclusion from a bare curl. A modern WAF answers a default curl/UA with 403 regardless of
who is asking, so a table of bare-curl 403s is a table of nothing. Always send a real browser User-Agent AND
Accept/Accept-Language, and always run the same client against two networks, before saying "our IP is being
blocked". The tell in this case was that one site was blocked for the shop and served to the datacenter while
another was served to the shop and blocked for the datacenter - a genuine IP block does not do both.
Related trap from the same hour: bare curl also returned 200 with size_download=0 for the real anomaly, which is
correct data but easy to misread as "the site is empty for everyone". The size column, not the status column, is
where the answer was, in both directions.
