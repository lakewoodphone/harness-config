**L2591 · CORRECTION to L2590: the engine reads session HEADERS, not whole files - and the slow scan was a degrading process, not the corpus**

CORRECTS L2590, WHICH WAS WRONG ABOUT THE CAUSE. Its numbers were real; its
explanation was not. Read this before acting on that entry.

L2590 claimed the engine "reads every file IN FULL" when listing sessions, and
that the 6,623 ms `list_agents` scan was that cost. Both claims are now falsified.

WHAT THE CODE ACTUALLY DOES
`dsh-session-persistence-jsonl/lib/index.js:3125 readFirstZstdLine` reads 8 KiB
chunks and returns as soon as the FIRST zstd frame decodes (:3140, :3146) - the
header only, ~252 bytes decompressed. There is no whole-file read on any listing
path. Verified in the copy that is running here (dsh 0.1.5-rc.1, subpackages
0.1.5-rc.2), not taken on report.

WHAT IT ACTUALLY COSTS
Measured on this machine's own 843-session corpus, replicating the real read
path (open + read 8 KiB + decompress the first frame, serial, async):
 263 ms total, 0.31 ms per session, 6.5 MB read.
And the engine's own counter, on a HEALTHY engine (pid 21440): `lastScanMs` =
**1,165 ms**. On the DEAD engine (pid 12680) the same corpus reported
**6,623 ms** with a max event-loop lag of 13,210 ms.

So the identical work took 5.7x longer in one process than the other. The corpus
was never the cause; the PROCESS was degraded, and it then crashed.

THE MISTAKE WORTH KEEPING
I had a probe that read all 837 files in full and finished in 6,437 ms, matching
the engine's 6,623 ms to within 3%. That agreement felt like proof and was pure
coincidence - two unrelated mechanisms landing in the same range. I then wrote
"cost is proportional to BYTES on disk" into a handoff as if measured.

Corroboration that was available and that I should have weighted more: the same
work is done by nothing else on the machine, and the engine's counter did not
grow smoothly with the corpus (685 rows -> 12.4 s and 803 rows -> 2.9 s on
different days). A cost that does not track its supposed input is not caused by
it.

RULES
1. Never infer a code path from a timing match. Read the path, or reproduce it.
2. Before blaming data volume, re-measure the SAME operation on a freshly
 started process. A long-lived process is a variable, and it was the whole
 story here: 17h uptime, heap 692 MB, lag max 13,210 ms.
3. A single accidental numeric agreement is not evidence. It is a coincidence
 until the mechanism is shown.
