**L1877 · A probe that reports a clean zero for something that exists is broken, not a finding**

RESOLUTION of the contradiction recorded earlier today. The original claim was RIGHT. My retraction was the error. Recording both, because the retraction cost credibility and the reason it happened is the lesson.

THE VALIDATED ANSWER (probe `_scratch/probe-remote.sh`, run against `lpt-apps` 2026-09-16 ~20:0xZ)
The probe self-tests first — it proves it can say PRESENT (literal `abc`, len 3), ABSENT_OR_EMPTY (empty string, and an unset variable) — and refuses to print SAME when either side is empty. Only then does it report:

 JWT_SECRET SAME prod=e640ee40a75b test=e640ee40a75b
 JWT_REFRESH_SECRET SAME prod=a5053d4140c9 test=a5053d4140c9
 ENCRYPTION_KEY SAME prod=8671d713b671 test=8671d713b671
 LPT_SSO_SHARED_SECRET DIFFER prod=3d4e5cd38044 test=983581cee45a

Read from `/proc/1/environ` **inside each container**, which is the process's own environment, not `printenv`. Corroborated by a different route: the container's value and the host file value match (`JWT_SECRET` container/file both `e640ee40a75b`; `ENCRYPTION_KEY` both `8671d713b671`; `DATABASE_URL` both `7261d5cfe6db`).

So: **production and test genuinely share `JWT_SECRET`, `JWT_REFRESH_SECRET` and `ENCRYPTION_KEY`.** A test-issued refresh cookie is cryptographically valid against production. That is a real hole, and it is mine to fix.

ALSO SETTLED, AND IT EXPLAINS AN OUTAGE THE OWNER ALREADY REPORTED
`LPT_SSO_SHARED_SECRET` DIFFERS between prod and test. Queue row #55 recorded that `chumash-timeline` presents the **test** backend's secret while the live IdP and `lakewood-rentals` share the production one, and that every `chumash-timeline` login therefore ends in 403 rendered as `oauth=error` — no user can sign in at all. This measurement is the confirmation of that diagnosis from the live processes, and it means the fix is deterministic: give `chumash-timeline` the production value, or move to per-app credentials.

CONFIG FACTS ESTABLISHED (the earlier probes got these wrong too)
- `/opt/lpt/docker-compose.yml` **exists** (105-line `.env`, project `lpt`, working dir `/opt/lpt`), and `/opt/lpt-test/docker-compose.yml` likewise (112-line `.env`, project `lpt-test`). An earlier probe reported both compose files absent and `/opt/lpt/.env` absent — because that probe ran **on `secratary`, which has no docker**, so every `docker` call and `docker exec`-based read returned nothing. The empty results were then misread as absence.

WHY THE RETRACTION HAPPENED, AND THE RULE
I ran probe A by shelling `docker exec` out to the wrong host, got empty output, and concluded the earlier reading was unreliable. Then I wrote a "corrected" probe that ran entirely on the wrong host and returned *zero containers* — which I should have read as "the probe is broken", but I read as "the facts are unknown". **A probe returning a clean zero for something that certainly exists is a broken probe, not a finding.**

RULES EARNED
1. **A probe's first job is to produce a known-positive.** Any reading where an entity you know exists comes back missing is a probe failure. Check that before checking anything else.
2. **Establish WHERE a command runs before believing WHERE its answer came from.** `secratary` has no docker; `lpt-apps` does. Two of my four probes silently ran in the wrong place.
3. **Retracting a correct conclusion is as costly as asserting a wrong one.** I destabilised a true finding because I trusted a fresh broken probe over an older one that had actually printed lengths and hashes. Correcting an error is right; correcting into an error is not.
4. **The empty-string SHA-256 guard (L1759) was a real defect and remains a real rule** — it is now enforced in the working probe. It was not, however, the defect that produced the original numbers.
