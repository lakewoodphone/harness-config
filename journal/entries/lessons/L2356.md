**L2356 · L — A classifier is unverified until measured on labelled real cases: the same prompt scored 6/10 with reasoning off and 10/10 on**

**Measured 2026-09-23 on the family chat, and it changed the implementation.**

I built a content classifier so Chip answers when a family member talks to him. The prompt looked good, the unit tests passed (they stub the model), and I nearly shipped it. Then I ran the real thing against ten labelled messages drawn from the family's own traffic - both messages from tonight plus five controls - and the production configuration scored **6/10**, missing EVERY implicit address:

```
current/think-off: 6/10
 MISS exp=chip got=other 'Hey chip, everything will be fine. Good things... breathe in...'
 MISS exp=chip got=other "What about my kids birthdays? I've got 2 birthdays today! Not nice..."
 MISS exp=chip got=other 'hey what about me'
 MISS exp=chip got=other 'who has the tallis bag?'
current/think-on: 10/10 (same prompt, same cases, reasoning enabled)
```

The single difference was `thinking: {"type": "disabled"}`. The same prompt with reasoning ON answered every case correctly, with no false positives on the "not addressed" controls. The reasoning was the decision; a one-word answer is not a cheap answer.

**The rules this earns:**

1. **A classifier is not verified until it is measured against labelled real cases.** Unit tests that stub the model prove the plumbing, not the judgement. `cls_prompt_lab.py` (10 cases, confusion table per prompt variant) is the pattern; write its sibling before trusting any new classifier prompt.
2. **Reasoning OFF is a trap for judgement calls.** With thinking disabled and a small budget, `deepseek-flash` will confidently return the wrong label. It is fine for rewrites and extraction (where this codebase already used it) and wrong for decisions. Corollary, already documented in this file: with thinking ON, `max_tokens` must cover the thinking AND the visible answer - a 128-token ceiling returned empty content.
3. **Substring keyword matching on a trigger list is a silent liar.** The shipped list contained `ai`, so `_keyword_hit` matched "said", "wait", "email", "Lchaim", "Raitzik", "Shaina", "Faiga", "Bais", "details", "rain". Measured on the live log: 24 keyword-matched turns, 15 of them ordinary names and words, and only 4 got a reply - the gate fired on the wrong things and under-delivered on the right ones. Word boundaries now.
4. **The most dangerous sentence in this repo is "it's implemented".** What made the difference here was one adversarial measurement after the code was green: the feature would otherwise have shipped in exactly the state the owner complained about.

Corollary for the next agent: when a change is about BEHAVIOUR (does he answer? is it addressed?), the money question is not "does the code run" but "on real inputs, what fraction does it get right, and which ones does it miss". Print the misses, not the score.
