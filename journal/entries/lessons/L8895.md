**L8895 · A backtick in a PowerShell argument is an escape character - write bodies to a file**

## A backtick in a PowerShell argument is an escape character — write bodies to a file

Measured 2026-10-18, twice within ten minutes, on my own journal entries.

I passed a body as a PowerShell double-quoted argument. In PowerShell a backtick is the escape
character, so every markdown code span was interpreted:

 `chat:vscode` -> \chat:vscode\ (the wrapping backticks lost)
 `files:local` -> \iles:local\ (backtick-f = FORM FEED; the f was eaten)
 `adb shell` -> <BEL>db shell (backtick-a = BEL)
 `research` -> <CR>esearch (backtick-r = carriage return)

The entry was written with control characters where prose should be, and the journal's own `check`
caught it as `metadata sha=… does not match the body` — which is how the corruption was noticed
rather than trusted. Repaired by deleting the entry and re-appending the same content through
`--body-file`.

**Then I did it again**, immediately, while writing the lesson about it — because the fix is a habit,
not a fact. The second occurrence is the more useful evidence: knowing the rule did not prevent the
error; only passing a file does.

**The rule:** any text containing backticks, dollar signs or quotes goes into a FILE first and is
passed by path — `--body-file`, `--from-json FILE`, `scp`. This is the same class as the repo rule
against inlining multi-hop ssh commands, and for the same reason: the shell is a parser, and it will
parse your prose.

**The second rule:** when writing to the journal, `check` is not optional. It is the only thing that
turned a silently corrupted entry into a repairable one, both times.
