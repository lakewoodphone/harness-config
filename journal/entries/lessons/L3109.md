**L3109 · A model id the gateway does not recognise is served by a DIFFERENT model, with HTTP 200 and no warning**

A named model could be answered HTTP 200 and never be the model that served it.

MEASURED 2026-09-30 against the live gateway on the authority (POST /v1/chat/completions,
reading the response `model` field AND the `model_usage` row it wrote):

 deepseek-v4-flash -> deepinfra/deepseek-ai/DeepSeek-V4-Flash-0731 correct, by luck
 deepseek-v4-pro -> deepinfra/deepseek-ai/DeepSeek-V4-Flash-0731 WRONG, silently
 deepseek-v3.2 -> deepinfra/deepseek-ai/DeepSeek-V4-Flash-0731 WRONG, silently
 deepseek-r1-0528 -> deepinfra/deepseek-ai/DeepSeek-V4-Flash-0731 WRONG, silently
 gpt-4o-mini -> deepinfra/deepseek-ai/DeepSeek-V4-Flash-0731 WRONG, silently
 secretary-smart -> deepseek/deepseek-v4-pro correct
 secretary-auto -> deepinfra/deepseek-ai/DeepSeek-V4-Flash-0731 correct by policy

CAUSE. In `prepare_request`, `if requested_model in sr._CAPABILITY_DB` selects the direct
pin. A short id is NOT in `_CAPABILITY_DB`, so it fell through to `sr.route_canonical_request`,
which picked the cheapest capable model for the task and said nothing. Every request
therefore answered 200, named a model, and ran on DeepSeek V4 Flash.

WHY IT MATTERS. The app's own `model_tier1/2/3` and `mem0_llm_model` defaults, and the
authority `.env`, all name exactly those ids. That is why the app's three tiers have never
been three different models, and why "the company" and "the responder" behaved like the
same weak brain: they were.

THE COMPANION DEFECT. `GET /v1/models` did not list the ids the inference endpoint
accepted: 38 ids, and `deepseek-v4-flash` was not among them. A caller obeying the standing
rule "validate every configured id against the catalog and drop what is not listed" would
have dropped working configuration.

FIX (deployed and verified live, app/services/ai_gateway.py):
 * `_LEGACY_SHORT_MODEL_IDS` resolves a short id to its canonical id before pinning.
 * `build_models_payload` appends those aliases as `kind: legacy_alias` rows, so the
 catalogue and the endpoint agree. Live: 38 -> 42 ids.
 * An id that is neither canonical nor a route alias is no longer served silently on
 whatever smart routing picked: it is served on the settings' OWN default route and
 logged at WARNING.

VERIFIED AFTER RESTART, on the live gateway:
 deepseek-v4-pro -> deepinfra/deepseek-ai/DeepSeek-V4-Pro-0813
 deepseek-v4-flash-> deepinfra/deepseek-ai/DeepSeek-V4-Flash-0731
 catalog GET /v1/models -> 42 ids, all four short ids listed as legacy_alias.

THE GENERALISED LESSON: an HTTP 200 that names a model is not evidence that the model
served the request. Read what the gateway recorded as the serving model, not what the
caller asked for and not what the response claims.
