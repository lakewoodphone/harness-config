**L3517 · A supplier can serve YOUR network an empty 200 - robots.txt is the control that separates a block from an outage**

MEASURED 2026-10-11, from ZABZ-TECH (shop), SECRATARY (shop LAN), HETZNER (German datacenter)
and the home laptop. The supplier is laptopscreen.com.

 from the shop's public IP (71.104.140.242, Verizon FiOS, AS701, Lakewood NJ):
 /robots.txt -> HTTP 200, 774 bytes, the real file
 / -> HTTP 200, 0 bytes
 /English/ -> HTTP 200, 0 bytes
 /English/model/HP/ELITEBOOK~840~G5 -> HTTP 200, 0 bytes
 ... plus every variant tried: ?set_currencyUSD, the French and Spanish
 locales, %20 instead of ~, a trailing slash, a Google referer, and a
 DIFFERENT model (840 G4) - all HTTP 200, 0 bytes.
 Response headers show the origin answering: set-cookie PHPSESSID, x-powered-by
 PleskLin, server cloudflare, cf-cache-status DYNAMIC, cf-ray ...-EWR.
 from HETZNER (datacenter IP):
 the same model page -> HTTP 403, 5,766 bytes, cf-mitigated: challenge,
 <title>Just a moment...</title> - Cloudflare's JS challenge.

So: the site is UP (statics serve, and an outside network gets a real, different
response), and it is deliberately DEGRADING our network - it hands our IP an empty
200 from its own PHP app, past Cloudflare. The owner's own Chrome on the shop
network got the same blank page, which is consistent and is the point: this is not
his computer.

WHAT SEPARATES THE TWO DIAGNOSES, AND IT IS ONE REQUEST:
 fetch a static file on the same host (robots.txt, an image, a .css) alongside the
 failing page. Static serves + dynamic empty = WE are being served a block, not an
 outage. Static ALSO empty = the host or the path is gone, or the network is
 filtering the domain. Do this BEFORE telling anyone a site is down, and before
 telling them to clear cookies or try another browser.
