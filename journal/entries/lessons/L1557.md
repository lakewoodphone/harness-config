**L1557 · A world-readable-by-URL judgement is only safe if the URL cannot address anything but the intended object**

## L1552 - A "world-readable by URL is fine" judgement is only safe if the URL cannot address anything but the intended object

**Evidence, 2026-09-15.** The rentals photo-serving route built its S3 key directly from the URL path, and the app's bucket was the shared restic backup repository (`R2_BUCKET=psm-backups`). Two audits independently proved unauthenticated reads of `config` and a `data/...` blob, and the backup script writes `pg_dump` of every database plus a copy of every `/opt/*/.env` into that same bucket. The 2026-09-06 audit had graded "photos are world-readable by URL" as *acceptable for public listings* and moved on.

**The rule.** When reviewing a public read endpoint, do not ask "is this object public?" - ask "what set of objects can this endpoint *address*?" An unauthenticated proxy is only as narrow as its key allowlist. If the key is derived from user input and the store holds anything but the intended objects, the blast radius is the store, not the object.

**Corollary.** Bucket/credential reuse for convenience is the actual defect, and it is invisible in code review because the route looks correct in isolation - the wrongness lives in an env value (`R2_BUCKET`) set on a server. Checking a route's security requires reading its *deployed configuration*, not just its source. The follow-on: an exposure with no access log has no detectable age, so the only honest remediation is rotation, never "it was probably not read".

**Applied:** edge block verified live (404 where it was 200) within the same session; app-side allowlist and a dedicated bucket queued as the real fix.
