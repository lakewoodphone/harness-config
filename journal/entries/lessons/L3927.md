**L3927 · The BoA staleness alarm is ONE PENDING transaction, and the ingest contradicts itself about whether pending rows belong in the ledger - my claim moved three times and each step corrected the last**

The BoA staleness warning is fired by **one pending transaction**, and the code that should have carried it contradicts itself. This entry exists mostly to record how the claim moved, because each step was a correction of the previous one and the last is not the first.

**The three stales, in the order I told them:**

1. **"Four days the ledger never got."** Wrong. From `plaid_transactions` I inferred a four-day gap; 10-10, 10-11 and 10-12 simply had **no transactions on that account**.
2. **"One transaction is missing."** Closer, and still wrong about the cause. The single row after 10-09 is:
 `ZZQpqJqQ9PCDZbxqKVrphbd3XR1eJ8Uzvnx3R | 2026-10-13 | ACH CREDIT STRIPE TRANSFER ON 10/13 | -900.30 | pending=1 | mask 7930`
3. **Measured:** the account holds **359 posted transactions ending 2026-10-09** and **one pending one on 2026-10-13**, and that pending row is **not in the ledger**. So the warning is not about a missing day, a broken ingest, or a dropped batch: it is about a **pending** transaction and whether pending rows belong in the ledger.

**And that is where the code contradicts itself.** `ingest_plaid_transactions` carries the docstring `"""Ingest all pending Plaid transactions into accounting.db."""` (line 232), a counter named `skipped_pending` (line 316), and a helper `_txn_pending_link` described as *"the transaction_id of the pending row this posted txn supersedes"* — while the rolling-window comment (lines 273-279) says the window exists precisely so the update path *"can fix pending->posted transitions"*. Today's log says `Plaid ingest complete: 8 ingested, 2 skipped`. **A function whose stated purpose is to ingest pending transactions, which counts the ones it skips, and whose output does not contain the pending row it was looking at, is telling two stories.** Which of them is the intent is a one-question read of that file — not a guess I should make from outside it.

**Why the sequence matters more than the answer.** The `plaid_transactions`/`lpt-boa-checking` mismatch looked like a broken bridge; the honest cause was a **pending** row. Had I stopped at step 1 I would have reported a four-day ingest outage that does not exist, and at step 2 an unexplained missing transaction that has a mundane explanation. **Both readings came from real queries against real tables — the defect was never the data, it was that I inferred a cause from a symptom thrice before reading the writer.** That is the same failure as the `main.py:1546` misread earlier in this session, in a new dress: *a reading is not evidence about a mechanism until you have read what produces it.*

**What is established, and what is not.**
- Established: the ingest runs nightly (`04:30:12`, `8 ingested, 2 skipped`); accounts refresh (`updated_at 2026-10-14T04:30:12`); the account's last posted transaction is 2026-10-09; exactly one pending row exists; it is absent from the ledger.
- Established: the health warning is therefore **true of posted activity and misleading as a staleness alarm** — it fires on a benign condition, which is the same "monitor nobody reads" shape as the permanently-failing test fixed earlier today.
- **Not established:** whether skipping the pending row is intended. The code says both. Reading that one function's intent is the next step, and it is small.
- **Not established:** whether other accounts have pending rows treated the same way. That is a query, not an argument.
