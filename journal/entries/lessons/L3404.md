**L3404 · Read the path before believing 'file is not a database'**

**A relative database path in a settings object turns a working-directory mistake into a corruption
scare, so read the PATH before believing the ERROR.** 2026-10-08: `~/bin/website-comms-push.py` run from
`/home/zabz` answered `payload build failed: DatabaseError: file is not a database`. Read at face value
that is the company's 22 GB SQLite store being corrupt - a five-alarm finding, and I wrote it into a
handoff as one. The truth: `app.config.settings.database_url` is the relative
`sqlite:///data/secretary.db`, so from any directory other than the repo it opens a different file
entirely; run the way its own cron runs it (`cd "$REPO"` first, `website-comms-push-cron.sh:36`) it
answers `ok: true`, 0 errors. Nothing was wrong.

Rule, and it generalises past this script: when a tool fails in a way that accuses DATA - corruption, a
missing table, an empty result - establish WHAT IT OPENED before you diagnose the data. Print the
resolved path, resolve it against the process's working directory, and run the tool the way its
scheduler runs it. An error message is a claim by the program about the file it thinks it has, not a
fact about the file on disk. And when the accusation is this loud, the cost of one `cd` is nothing
against the cost of telling the owner his company database is broken.

Corollary for the record itself: the correction is a NEW entry citing the old one (H3384 -> the
correction handoff), because a handoff that quietly changes its mind is worse than one that was wrong.
