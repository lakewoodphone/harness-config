**L3847 · df reported 944 GB free on a device that did not exist - a stale NTFS-3G mount answers statfs from cache**

**Measured 2026-10-18 on `zabz-tech-linux` (the office Linux bench), kernel 6.8.0-111.**

I asked this machine whether the 6 TB staging vault had room, and it said yes:

```
$ df -h /mnt/lpt-recovery-dest
/dev/sda2 5.5T 4.6T 944G 84% /mnt/lpt-recovery-dest
```

**`/dev/sda` did not exist.** The drive had fallen off the USB bus hours earlier:

```
$ sudo smartctl -H /dev/sda -> Smartctl open device: /dev/sda failed: No such device
$ ls -l /dev/sd* -> No such file or directory
$ ls -la /mnt/lpt-recovery-dest -> ls: reading directory ...: Input/output error
$ grep lpt-recovery /proc/mounts -> (nothing)
$ sudo dmesg | grep sda
 device offline error, dev sda, sector 6292144 op 0x1:(WRITE) ...
 Buffer I/O error on dev sda2, logical block 782420, lost async page write
```

Only the **directory read** failed. `df` answered from the stale superblock in page cache with a
number that was rounded, plausible, in the right units and completely fictional. It reported 944 GB
of free space on a device that was not plugged in.

**Rules:**

1. **On any FUSE / network / removable mount, `df` is not evidence the device exists.** To prove a
 mount is live, in this order: read the directory (`ls`), read a known file, and confirm
 `/proc/mounts` and `lsblk` agree with what `df` printed. Four cheap commands; one of them is the
 one that lies.
2. **A near-full root filesystem makes this worse, not better.** Root was 97% full (430G of 468G,
 15G free), so the only plausible staging target *was* the phantom volume. The healthy-looking
 number was the one that would have been acted on.
3. **`fuser -m` on a stale mount listed ~250 PIDs** as holders. Minutes later there were no `D`-state
 processes at all and the mount was gone from `/proc/mounts`. A long holder list is not evidence of
 live work either - check `ps -eo stat` for `D` before believing anything is actually writing.

The general shape, and it is the same one as L3796/L3798: **ask what writes the field you are
trusting.** `df` reads a cached superblock that nothing invalidates on a USB disconnect. The
kernel's `device offline error` is the fact; the free-space figure is the opinion.
