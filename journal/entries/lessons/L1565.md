**L1565 · The desktop secretary API's LAN ingress is a netsh portproxy, and it dies silently when iphlpsvc stops**

MEASURED 2026-09-15 on ZABZ-TECH while restarting the API to pick up a rotated credential. restart-api.ps1 starts uvicorn with --host 127.0.0.1 on purpose (line 111), so after the restart Get-NetTCPConnection -LocalPort 8002 showed ONLY 127.0.0.1 and http://192.168.50.138:8002/health was 'actively refused'. Before the restart there had been a listener on 192.168.50.138:8002 owned by an svchost - not by python.

DIAGNOSIS
-
etsh interface portproxy show v4tov4 contained 192.168.50.138:8002 -> 127.0.0.1:8002, so the LAN address is a portproxy, never a direct app bind.
- Get-Service iphlpsvc was Stopped. The portproxy is implemented by IP Helper; with IP Helper stopped the proxy stops listening even though the rule is still configured and the firewall rule 'Personal Secretary API 8002 (mesh LAN)' is still enabled.
- Fix: Start-Service iphlpsvc. Within 3 seconds the 192.168.50.138:8002 listener came back (owned by a new svchost) and LAN /health returned 200.

RULE
- The desktop API is reachable on the LAN only while BOTH hold: the portproxy entry AND a running IP Helper service. When LAN reachability is the question, check those two before touching the app, and do not 'fix' the app by rebinding it to 0.0.0.0 - that is not how this machine is wired.
- A loopback-only listener on this machine is the CORRECT state, not a regression. The mesh ingress in scripts/watchdog.ps1 (Ensure-MeshIngress, ~line 935) is what maintains it; it repairs the portproxy and firewall but does not start iphlpsvc.
