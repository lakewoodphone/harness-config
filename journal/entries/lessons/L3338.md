**L3338 · L: A generated input goes stale and silently corrupts the output - refresh case-phones.json before every queue build**

MEASURED 2026-10-05, round 4 of the contact-queue goal.

WHAT HAPPENED
I wrote 54 backfilled case files, re-ran the work-list builder, and it still reported
"154 open items without a case file" and "56 needing a case file" - identical to before. The
files existed. The report was wrong.

WHY
build_contact_queue.py and build_worklist.py read `case-phones.json`, a snapshot of which
phone numbers already have a case file. That file was generated BEFORE the 54 case files were
written. Nothing regenerated it. So the builder kept scoring every backfilled customer as
"no case file", and the output looked authoritative while being a picture of the past.

THE FIX
refresh_case_phones.py rebuilds case-phones.json from the case index and writes a
case-phones.stamp recording the index mtime, the regeneration time, the case count and the
phone count. The correct order is:

 lptcase.py index # on ZABZ-TECH, which owns the repo
 refresh_case_phones.py # on secratary
 build_contact_queue.py
 build_worklist.py

After the refresh: open_ring_credible 75 -> 91, open_ring_unverified 53 -> 38,
needing_case_file 56 -> 0.

THE RULE
Any hand-built input snapshot must carry its own timestamp and its source's mtime, and a
generator that consumes one must be run after refreshing it. A stale input does not fail
loudly; it produces a confident, plausible, wrong answer - the same failure mode as reading
a stale database copy, which is the worst failure in this system''s history.

ALSO RECORDED
A ring-count rule kept re-flagging two numbers the phone system labels as non-people
("800 Service" 8337022125, "MP3 Port Ticket #1280" 8482857198) as needing a case file, after
I had deleted their files. Repeat rings are what robocallers do, so a count-based rule cannot
distinguish them. They are now named once in a NOT_PEOPLE exclusion set in build_worklist.py.
