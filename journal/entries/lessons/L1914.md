**L1914 · A concurrent session's 'git commit -a' in a shared checkout swept my unstaged edits into its commit - verify 'git show --stat HEAD', not just your 'git add'**

**In a shared checkout, another session's git commit -a commits YOUR uncommitted edits under ITS message. Stage and commit immediately, then prove what the commit contained.**

Measured 2026-09-17 in C:\Users\ezabz\Code\lpt-hub (ZABZ-TECH working directory, shared by concurrent sessions):

1. I edited three files (two sync records + one case file) and left them **unstaged** while I ran a verification step.
2. A concurrent session working the fishman case ran a commit that swept all three into **36fcffec6 case(fishman 347-534-6208): deposit paid - ship job ... RETRACT the wrong failure-cost model** - a commit whose message has nothing to do with them.
3. My own git add then found only the fourth file dirty; my commit reported **1 file changed** where I intended four. Nothing was lost (the content is in origin, blob hashes verified local == remote), but the attribution and the commit boundary were wrong, and I did not notice until I read git show --stat HEAD.

The check that catches it, every time: after git add, run git status --short on the exact paths, and after git commit, read **git show --stat HEAD** and confirm the file list is what you intended. git commit reporting fewer files than you staged is the only signal you get.

The same lesson generalises beyond git: **in a shared working directory, an uncommitted edit is not yours yet.** Uncommitted state is a race with every other session on the machine. For anything that must survive, commit it, or work in your own git worktree.

Cost when it goes wrong: my three-file fix exists but reads as part of another agent's work - so the next session auditing that case cannot tell who changed it or why, and the journal entry that should have explained it was not on disk yet.
