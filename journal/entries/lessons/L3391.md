**L3391 · Win32-OpenSSH multiplexing is broken here - root cause of P2251**

**Win32-OpenSSH multiplexing is broken on ZABZ-YOGA. That is the root cause of P2251, and it means
the fix is not "re-enable ControlMaster".**

The owner asked whether we had built "a way more stable ssh that doesn't time out - some sort of
constantly open port that is way faster". Two different things get conflated:

1. **Transport v2 (`POST /mesh/run`, `packages/plugin-mesh-http`) is real and live.** It replaced the
 per-dispatch ssh for **agent turns**. Verified tonight on this laptop: `GET
 http://127.0.0.1:3099/mesh/health` and `:3086` both answer 200, `node: zabz-yoga-1`, HMAC secret
 configured, `maxConcurrent` 5 (cpu-bound), `refuseWhenFull:false` so it **queues** rather than
 refusing. That is the "constantly open port" - the node's engine is already listening.
2. **But it carries agent dispatches, not shell commands.** Deploying files still pays ssh.

And the ssh-level speedup is **not available here**:

 ssh -V -> OpenSSH_for_Windows_10.0p2
 with ControlMaster=auto -> "debug1: getpeername failed: Not a socket"
 "getsockname failed: Not a socket", rc=-1, no socket on disk
 plain ssh, same host -> "plain-ok"

`ControlPath` in `~/.ssh` and in `%TEMP%` both failed identically; plain ssh works. So the
"ControlMaster socket that got wedged" in P2251 was never a flaky mux - **the mux does not work on
this platform**. Measured cold ssh round trip to the authority: 945-2396 ms.

**Consequences.** Do not re-enable ControlMaster on Windows. Batch shell work into one ssh call,
and prefer the API/MCP (`ps_action`, the `ps_*` tools) for *reads* - those are one HTTP call to the
already-running service and cost no ssh at all. Reserve ssh for writes and execution on the far side.
Extending the mesh route to carry a bounded shell command is possible but is a new attack surface
and is not needed while batching works.
