**L6232 · A payment link captures the price when it is MINTED, so a re-priced order keeps charging the old amount - and the API has no way to cancel or expire a payment transaction**

**MEASURED 2026-10-14 on the live shop, from the owner looking at the actual payment page and asking "why does it still say 75 here".**

**The mechanism.** A payment page shows the amount on the **payment transaction**, not the amount on the order. The pay-notice rail reuses an existing PENDING link rather than minting a new one - its own comment says why (*"two live links for one debt is how a customer pays twice"*) - so when an order is re-priced after a link was minted, **the text and the button disagree**. Verified: order 3018 held exactly one transaction, `id 3380, amount 75.00, PENDING`, minted at 17:06 when the order said 75; after the order was corrected to 79.97, a fresh draft carried the correct 79.97 text and the **same** page URL, which still charged 75.00.

**The sequence rule that prevents it: price the order first, mint the link second.** The manager did it backwards - created the draft (which mints) and then corrected the total - and the result was a link bound to a number nobody wanted. **A link is an invoice; it captures the price at the moment it is created.**

**The gap underneath, which is worse than the mistake:** there is **no procedure in the API to cancel or expire a payment transaction or its link.** `CANCELLED` exists in the status enum and `isPaymentOutstanding` honours it, but nothing in `payments.*` or `paymentLinks.*` sets it, and `paymentLinks.createPaymentLink` takes only a `paymentId`, so a new amount means a new transaction while the old one stays PENDING forever. **So any re-priced order keeps a live link at the old amount, and reuse-before-mint will keep offering it.** Cancelling the row alone would not be enough either - the minted link has a Stripe object behind it, so a database-only cancel leaves the payable side alive.

**What saved it: the link had never been sent.** It existed only inside a dismissed draft and one refused send. The lesson is not "be careful" - it is that **an unsent link is the only forgiving state**, and the reason to keep the draft-then-approve gate is exactly that the mistakes happen before anything reaches a customer.

Next: mint a correct transaction for the new amount and send that link, and build the cancel/expire path in the API so a re-priced order cannot strand a live link.
