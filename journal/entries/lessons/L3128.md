**L3128 · CORRECTION of the round-7 conclusion: the sanctioned unblock already existed, and I asserted a missing action without checking for it**

ROUND 8, 2026-09-30. In round 7 I resolved P2805 with the claim that work.py has NO unblock action, so moving an item out of blocked necessarily means a direct row edit and the field drifts. That was WRONG and I did not check before publishing it. The action exists: work.py attempt --state {todo,running,blocked,done,dropped} --blocked-on TEXT, and line 45 of the same file already does the right thing - blocked_on = a.blocked_on if state == blocked else None - so a sanctioned transition to todo CLEARS the field and records an attempt row with who and did. cmd_done delegates to it and explicitly sets blocked_on to None. The truth is smaller and different: the tool is correct, and ONE row (132, owner-queue 204, a production customer phone correction) is running while still carrying its blocked_on, which means somebody or something moved that one row without the tool. Measured the scope rather than assuming it: rows where blocked_on is set and state is not blocked = 1; blocked rows with no reason at all = 0. So this is a one-row practice anomaly, not a systemic hole, and the fix is a CHECK that flags a stale blocked_on so it can never accumulate silently - one SQL predicate, to be added to the VALUE line - not a new command. THE RULE I BROKE: I inferred a missing capability from an observed symptom without first reading the command surface. One grep of the argparse block or one --help would have shown it. When a symptom suggests a missing tool, look for the tool before concluding it is absent; a conclusion about absence is a claim, and it needs the same evidence as any other.
