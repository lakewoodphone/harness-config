**L3705 · The authority had two lpt-ops checkouts and lpt-label ran the stale one; install-label.sh is the fix**

The authority had TWO lpt-ops checkouts, and the name `lpt-label` ran the STALE one.

Measured 2026-10-12 on secratary:
- `/home/zabz/lpt-ops` — **not a git repository** — `lpt_ops/label_printer.py` = 756 lines, `grep -c HEADLINE_MARK` = 0.
- `/home/zabz/code/lpt-ops` — git, HEAD 71813b6 — 881 lines, HEADLINE_MARK present (commit f40f0e6 "labelled: uniform body size, word wrap, !headline lines, --roll-mm override").
- `/usr/local/bin/lpt-label` -> `/home/zabz/.local/bin/lpt-label`, whose `entry=` line read `/home/zabz/lpt-ops/bin/lpt-label`: the launcher installed 2026-10-08 from the stale copy.

Consequence, observed: the same JSON dry-run through the launcher rendered every `!headline` line with a LITERAL "!" and sized each line individually; through `~/code/lpt-ops/bin/lpt-label` it rendered bold headlines with no "!" and wrapped the body. A session that used the git checkout explicitly (the levy_848 label earlier the same day) had a correct label, which is what made the drift invisible to the eye.

The fix is the installer, not an edit: `bash /home/zabz/code/lpt-ops/install-label.sh` (idempotent; reuses the venv, rewrites the launcher, re-symlinks, then runs `lpt-label find` as its own proof). It now reads `entry=/home/zabz/code/lpt-ops/bin/lpt-label`.

Rule for next time: before trusting a label print, `grep -m1 '^entry=' /usr/local/bin/lpt-label` and check that checkout's `label_printer.py` line count. And do NOT delete `/home/zabz/lpt-ops`: the write path uses it as its landing directory (`HELPER_REMOTE=~/lpt-ops/lpt_ops/write_helper.py`, pushed by sha from the caller's checkout) — a non-git directory there is expected.
