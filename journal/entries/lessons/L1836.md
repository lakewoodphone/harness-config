**L1836 · A Home Assistant shell_command containing Jinja runs without a shell**

A Home Assistant `shell_command` that contains Jinja (`{{ ... }}`) is rendered and then `shlex`-split — it is executed **without a shell**. Shell operators therefore become literal arguments to the program.

Evidence, 2026-09-15. The command

 nohup python3 /config/timeline_tools/phoenix-clip.py --event {{ event_name }} ... >>/dev/null 2>&1 &

produced, on every trigger:

 ERROR [homeassistant.components.shell_command] Error running command:
 `nohup python3 ... --event {{ event_name }} ... >>/dev/null 2>&1 &`, return code: 2

and the capture never ran once. Return code 2 was python's argparse rejecting `>>/dev/null`, `2>&1` and `&` as stray arguments, because `nohup` received them verbatim. Nothing executed and the automation reported success (`HTTP 200` on the service call).

Confirmed in `homeassistant/components/shell_command/__init__.py`: the handler branches on `if rendered_args == args:` — the "no template used" path runs the string through a shell, the template path does `shlexed_cmd = [prog, *shlex.split(rendered_args)]` and execs the program directly.

Consequences to act on:
- Never put `&`, `|`, `&&`, `>`, `>>`, `2>&1` or `;` in a `shell_command` that also contains a template.
- Detaching a long capture needs the no-shell-free form: a fixed command string with the event name baked in, one `shell_command` per event.
- `shell_command` is NOT reloadable (`POST /api/services/shell_command/reload` returns HTTP 400); it needs a core restart. `automation.reload` does work, which is why automations picked up the change immediately while their commands did not exist yet — a window where every triggered automation calls a missing service.
