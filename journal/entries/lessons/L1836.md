**L1836 · Apple has no MDM call blocker; allowEnablingRestrictions is the Screen Time gate and allowScreenTime is not a real key**

## Lesson — the Screen Time restriction gate, and the key that does not exist

Apple's Restrictions payload (`com.apple.applicationaccess`) has **no `allowScreenTime` key**. Read from Apple's own reference on 2026-09-17: 210 keys, no match for `allowScreenTime`, and no key anywhere that blocks voice calls. Our kiosk profiles set `allowScreenTime` false/true anyway; iOS tolerates the unknown key and it does nothing.

The real gate is **`allowEnablingRestrictions`**. Apple: *"If false in iOS 12 and later, the system disables the Enable ScreenTime option in the ScreenTime UI in Settings and disables ScreenTime if already enabled."* Supervised-only, default true. That one key is why Screen Time was unavailable across the DRN fleet.

Also not an MDM control: **Screen Time Communication Limits**. No Restrictions key, no Screen Time payload (the only Screen-Time-ish payload key, `ParentalControlsTimeLimits`, is macOS-only), no declarative configuration, and no `ScreenTime` item in the Settings command's documented item list (`/documentation/devicemanagement/settingscommand/command-data.dictionary/settings-data.dictionary`). Therefore fleet-api's `POST /fleet/devices/{drn}/screen-time` endpoint is a **dead stub**: it posts an invalid `Item: ScreenTime` plist at the MDM gateway that was removed on 2026-07-22. Do not call it; it cannot work.

Corollary: `blockedAppBundleIDs` may not contain `com.apple.mobilephone` or `com.apple.Preferences`. Apple's deployment guide: *"Any apps other than Settings or Phone (on iPhone) can be placed on either an approved list or a disapproved one."* That is what the 2026-05 `MCPayloadErrorDomain 2004` rejection was. Do not retry that experiment.
