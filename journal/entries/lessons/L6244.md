**L6244 · Green required check over a red suite; two seed files that abort each other; my own idempotency bug**

**Lessons from the 2026-10-14 diagnostic-credit correction: a green required check over a red suite, two seed files that abort each other, and my own idempotency bug.**

**L-A · THE REQUIRED CI CHECK PASSES WHILE THE TEST SHARDS ARE RED. Reproduced from the workflow file,
not inferred.** `pr-precheck.yml` removed the `is_copilot` gate from the test JOBS on 2026-10-14
(lines 647-655: they now run for every non-draft PR) but the AGGREGATOR still blocks on their results
only inside `if [[ "$is_copilot" == "true" ]]` (lines 955-973). For a human PR it prints
"Human PR - the backend/frontend test suites do NOT run anywhere in CI for a human PR" — now simply
untrue — and falls through. The required job `ci-validation-pr` (lines 1021-1068) checks only
`detect-changes.result` and `aggregator.result`. **Consequence: `CI Validation (PR Pre-Check)` goes
green over red shards, and that is the context branch protection enforces.** Measured by a child on
9 runs on 2026-10-14 (PRs 426/427/428/429/430/437): shards red, gate success, every time.
**Do not simply flip the gate on** — the frontend shards fail 36/36 on a runner bug (below), so
turning it on before fixing the runner halts every merge. Fix the runner first, then open the gate.

**L-B · THE FRONTEND SHARD FAILURE IS THE RUNNER, NOT THE TESTS.** 36/36 frontend shard failures in
7 days carry `Error: write EPIPE, errno: -32`, and the stack is entirely inside vitest's pool
teardown (`PoolRunner.stop` -> `ForksPoolWorker.send` -> `ChildProcess.target.send`), preceded by
`Timeout terminating forks worker` / `Failed to terminate forks worker`. **There is no vitest summary
block anywhere in those logs**, so the process died before it could report. **No frontend shard job
concluded `success` in 7 days**, so a red suite and a broken runner are literally the same signal.
**Lead not yet tested:** the repo sets `test.poolOptions` in `frontend/vitest.config.ts`, and vitest
4.1.10 prints *"`test.poolOptions` was removed in Vitest 4. All previous `poolOptions` are now
top-level options"* — so the forks guidance may be silently ignored. A/B `singleFork`/`isolate` at
top level. Also: the frontend job never calls `scripts/ci/run-test-shard.mjs` and never mkdirs
`ci-artifacts/test/`, and `if-no-files-found` defaults to `warn`, so the empty upload is a plain
misconfiguration that cannot fail.

**L-C · TWO SEED FILES WERE THE SAME COPY AND HAD DRIFTED, AND THE GUARD ABORTS ON THAT.**
`backend/prisma/seed.ts` (7 pricing rows) and `scripts/seed-all-faqs.ts` (all 27) had drifted on
`quote-before-repair` and on all five bullets of `how-we-differ` (hyphen vs em dash).
`faq-seed-guard.ts` fingerprints question/answer/category, so whichever ran second saw the other as a
HAND EDIT and aborted the whole run. Nothing detected it because every existing FAQ test used
fixtures instead of reading the real seed files. Fixed, and now enforced by
`backend/src/__tests__/faq-seed-agreement.test.ts`. **When two files hold one piece of copy, the check
must read the files, not a fixture.**

**L-D · MY OWN IDEMPOTENCY BUG: a replacement that CONTAINS its search string applies twice.** I
wrote a patch script whose idempotency test was "if the search string is gone, it already applied".
For `1. **$50 Diagnostic** - per item, non-refundable, credited toward the repair` the replacement
BEGINS with the search string, so after applying it the search string was still present, and a re-run
doubled it ("...non-difficult diagnostic on a non-difficult diagnostic"). Caught by grepping the
result, not by the script. **A patch script must assert its own match count on every run and must be
checked by reading the diff — a prefix-overlapping replacement defeats "is it already applied".**

**L-E · PowerShell `| Select-Object` DISCARDS THE EXIT CODE.** `pnpm ... | Select-Object -Last 20`
prints the tail and exits 0, so a failing typecheck reads as success. Capture `$LASTEXITCODE`
immediately after the command and redirect to a file, or the "verification" is worthless.

**L-F · THE HANDOFF'S OWN NUMBERS CAN BE WRONG — CHECK THEM.** HANDOFF-2026-10-14 §5 said "176
unclaimed wakes ... it should drain; confirm it does". Measured 2026-10-14T13:14Z from
`/root/.sms-inbox/inbox.db`: `new` = **61** (a population `GROUP BY`, no LIMIT), and it **cannot**
drain today — `/root/.sms-inbox/wake-caps-effective.json` reads
`caps_in_force: ["daily_cap: 150/150 releases today"]`, `released_today: 150`, and `wake_budget`
for 2026-10-14 reads released=150. It is GATED, not draining, until 2026-10-15T00:00Z. The "176" may
be a workstream number, not a count: the restored cron block is marked `# >>> 176-wake-loop-restore`.
**Also: `wake.py stats` run from an ordinary shell prints `max_per_day: 500` and an empty
`caps_in_force` because it does not inherit cron's env — it reports room to spare while nothing can
run. `autonomy-status.sh` was fixed for this; `wake.py stats` was not.**

**L-G · `lpt doctor` DOES NOT EXIST.** `lpt.exe` on PATH from `Python312\Scripts` is the FLEET-PHONE
tool, a different program. The Lakewood tools are `C:\Users\ezabz\bin\lpt.cmd` (reads) and
`lpt-write.cmd` (writes), generated by `lpt-ops/install.ps1`. And the FAQ table is NOT on the
authority: it is Postgres on the RDS the deployed `lpt-backend` uses, reachable with
`lpt sql` / `lpt-write` — searching `.db` files for an `faq` table will never find it.

**L-H · THE RESIDUAL `VITE_STRIPE_TERMINAL_READER_ID` IS LIVE CODE, NOT A COMMENT.** Reproduced
myself: the production bundle `/assets/index-xp9AwB_D.js` is 3,853,409 bytes, sha256
`DF00A490A299D0E7D2453BBA988D5B94F66911CEB69AD93FE8AB09B38DB6A0B6`, and the literal appears exactly
once at byte 1208901. It is a live runtime constant read by a helper, and the baked env objects do
NOT contain the key, so the lookup always misses and `configured` is always false. The sentence
"No card reader is configured, so take the card on this keyboard." is produced by an expression that
branches on `configured`, so it is reachable **regardless of whether a reader is online**. It renders
only on the auth-gated `/admin/waze/sell` surface. The two work-order/counter callers DO ask the
registry (`getReaders`). **Deleting the literal would not fix it — the path never consults the
registry at all.**
