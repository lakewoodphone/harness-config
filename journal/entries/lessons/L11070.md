**L11070 · 0.2 preview notice: Continue cannot save because the acknowledgement lives in a generated settings block - pin welcomeNoticeVersion to the client's exact WELCOME_NOTICE_VERSION (2026-09-28.1) in the settings source instead**

The phone showed the 0.2 "Preview Notice" on every new session, and its Continue button failed with "The
acknowledgement could not be saved. Please try again."

MECHANISM: `dsh-client-ui-settings-models/lib/client.js:3058` declares `WELCOME_NOTICE_VERSION = "2026-09-28.1"` and
compares the stored `welcomeNoticeVersion` for EXACT equality. This estate pinned that field to `2026-08-13.1`, so the
notice believed it had never been acknowledged. Continue writes the new value into the settings document — and that
document's `ui-settings-general` entry lives inside the GENERATED `settings-from-yaml` managed block (written by
`dsh-update/tools/settings-to-entries.mjs`), which is why the save is refused.

FIX, durable rather than a workaround: set `welcomeNoticeVersion` to `2026-09-28.1` in the settings SOURCE and in the
live patch, so the value is already equal and nothing needs saving. Done on the phone engine
(`/root/.dsh/profiles/web/cordis.patch.yml` line 2709) and in the repo (`settings/base.yaml:8`). Restarted; composed
value now reads `welcomeNoticeVersion: 2026-09-28.1`; engine active, 0.2.1-rc.2, 401, gate 200.

GENERAL LESSON: when a UI notice's "acknowledge" write fails, do not fight the write — ask what the notice compares
against and pre-satisfy it in the settings source. A generated block is not a writable document, and a value the
generator owns must be changed at the generator.
