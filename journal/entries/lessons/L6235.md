**L6235 · CORRECTS L3809: orders has no subtotal/tax/taxRate columns at all - I read three keys that do not exist and reported their absence as NULL, the second time in one evening. An absent column is a fact about my query, not about the row.**

**CORRECTS L3809, which was written on a wrong premise. Owner, 2026-10-14: *"no tax comes after 75... its supposed to be computed automatically."***

**What L3809 got wrong.** It said the order stored `total = 75.00` with **`subtotal`, `tax` and `taxRate` all NULL** and that the fix was to make the creation path populate them. **`orders` has no such columns.** `backend/prisma/schema.prisma` `model Order` carries `total` alone; the only `subtotal + taxAmount + total` trio in the whole schema is on `quotes`. So the manager queried three keys that do not exist, saw NULL for each, and reported them as missing values. **That is the second time in one evening that an absent column was read as a null value** - the first was `payment_pages.stripePaymentLinkId`, which likewise does not exist (the Stripe link id lives in the page's `metadata`). **An empty result is a refusal, not health** - and specifically: *a column that does not exist and a column that is null are different facts, and only one of them is a finding.*

**What is actually true, measured.** `orders.total` **is** the tax-inclusive figure by design - `total = discountedSubtotal + taxAmount`, persisted by `saved-final-total.service.ts`. `lpt-write total set` was corrected for that on 2026-10-12 (`869a97f`): it takes the **pre-tax** figure and computes the tax. **`order create` was left handing the typed figure straight to `create_order`**, so a job typed at creation as 75.00 stored **75.00** while the same 75.00 through `total set` stored **79.97** - orders were born owing the pre-tax number. That is the real defect, it is now fixed (`lpt/order-create-tax-20261014`, `9f067fc`, red-first: seven tests failed against `main` with `assert '75.00' == '79.97'`), and the arithmetic now lives in one `split_total()` called by both doors with the rate read from `pricing_config.taxRate` rather than baked in.

**The transferable lesson, which is about the manager and not about tax:** twice this evening a defect was declared from a query whose keys did not exist, and both times the wrong finding was reported with confidence to the owner. **Before reporting a missing value, prove the thing that holds it exists**: `information_schema.columns` for a column, `to_jsonb(row) ? 'key'` for a key. A NULL is a fact about a row; a missing column is a fact about my query, and confusing them produces confident nonsense.
