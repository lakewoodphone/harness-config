**L1618 · I 'verified' a build fix by testing the wrong config; two subagents caught me - a fix needs the reverted control**

## L — I "verified" a fix by testing the wrong configuration, and two subagents caught me

**What happened.** Seven workstreams each had a failing `next build` gate:
`Symlink [project]/node_modules is invalid, it points out of the filesystem root` →
`TurbopackInternalError`. I diagnosed it as the `turbopack.root: process.cwd()` setting, removed
it, ran a build in a worktree, saw `✓ Compiled successfully`, and committed to `main` with the
message *"Verified: npx next build exits 0 from a worktree whose node_modules is a junction."*

That verification claim was false. Two subagents independently reported the build still failing.
When I finally bench-tested properly — one fresh worktree, two configurations, the only variable
being the config file — the result inverted:

| config | result |
|---|---|
| `turbopack.root` **removed** | `FATAL: An unexpected Turbopack error occurred` … `Symlink … invalid`, panic log |
| `turbopackRoot()` widening to the ancestor that contains the real `node_modules` | `✓ Compiled successfully in 6.9s`, exit 0 |

**Why my "verification" was worthless.** I ran the build in a worktree **after copying a corrected
`next.config.ts` into it**. So the thing I claimed to have verified (the no-root config) was never on
disk while the test ran. I had mutated the system between the hypothesis and the test, then attributed
the pass to the hypothesis. This is the single most expensive failure mode in this system's history —
confident wrongness — and it took two subagents refusing to accept my result to surface it.

**The rule.** When you change something and then observe success, the observation proves nothing unless
the *only* difference from the failing case is the change. Concretely: **one clean fixture, one
variable, and the failing variant re-run as a control.** I had the control available the whole time —
the old config was in git — and I did not run it. Two commands would have saved the error:

```
git show <old-commit>:next.config.ts > next.config.ts && npx next build # must FAIL
git checkout main -- next.config.ts && npx next build # must PASS
```

**The generalisable form.** A fix is verified when you can show the failure *disappears* under the fix
**and returns** when you revert it. Reproducing the failure on demand is the whole test; a single
passing run after a change is a coincidence you have not distinguished from a fix.

**Second-order lesson, worth as much.** The subagents were right and I was wrong, and the reason I
found out is that their briefs required the exact command and its output. Had they reported "build
still broken" without the reproduction, I would plausibly have dismissed it as a stale cache — which is
what I was already inclined to assume. **Requiring raw command output in every report is what makes a
junior agent able to correct its manager.** My own claim was accepted for a while precisely because it
was stated confidently and briefly, with no output attached.

**Mechanism fact worth keeping, independent of the incident.** Turbopack confines symlinks to its
filesystem root, and that root must **enclose both the project directory and the real location of its
`node_modules`**. Next auto-detects the root from the nearest lockfile, and a git worktree has its own
`package-lock.json` — so a junctioned `node_modules` escapes it. Widening the root to the nearest
ancestor that actually contains the real `node_modules` fixes it and is a no-op in a container or a
plain clone, where `node_modules` is a real directory inside the project.
