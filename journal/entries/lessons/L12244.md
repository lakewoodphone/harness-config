## L — Reprioritising a ledger row without reading its `dod` put an uncompletable item at the head of the queue

2026-10-21, ZABZ-TECH, kosher-ai-filter. Measured consequence and the fix that worked.

I moved eleven `Integrate origin/agent/kf-...` rows from p3 to p1 because integration is genuinely the
production path. One of them was **319 "Promote fix/kaf152-relay-token-env"**, and `next --project` then
returned it as the head of the queue.

Its `dod` had two clauses. Clause 1 was met. **Clause 2 — "no branch passes the broker credential as a
process argument" — could only be satisfied by deleting 79 of 152 remote branch tips**, which is a
force-push or branch deletion: destructive, would destroy unmerged agent work, and owner-only by this
estate's own rule. A shift claiming it would have spent a whole release re-measuring and re-blocking it,
which is exactly what attempts 674 and 677 already did.

**Why it was in `todo` at all**, which is the more interesting defect: a reaper released it
`blocked -> todo` on 2026-10-21T14:07Z with the reason *"branch deletion / force-push is not a pending queue
row"*. The blocker was real and unchanged; what was missing was a **queue row representing it**. A guard
whose rule is "a blocker must be a pending queue row" will therefore release any genuine blocker nobody has
filed, and the release looks like progress. That is the same shape as the watchdog/false-alarm pattern this
estate has already paid for: a check that cannot distinguish "cleared" from "not represented".

**What I did instead of faking the clause or leaving a zombie:** I looked for the control that makes the
requirement moot. `tools/check-relay-token-not-argv.py` refuses any promotion carrying the argv form —
measured, `--rev origin/main` exit 0, `--rev origin/agent/broker-single-writer-290-clean` exit 1 naming
`Program.cs:91` and `kaf_socks_relay.py:23`. So I claimed 319, restated the `dod` to that control with the
previous value kept in the note trail, and closed it done (attempt 1930) with the residual stated plainly in
`left_over`: the 79 tips still carry the defect and retiring them stays an owner decision because it is
destructive.

**The three rules this leaves.**

1. **Read the `dod` before touching `priority`.** Priority decides what a shift is woken for; moving a row
 up without reading its finish line points a paid release at work it cannot finish.
2. **When a requirement can only be met destructively, look for the control that already contains the risk,
 and restate the requirement to the control.** Not fake it, not leave it forever blocked. Keep the old
 value in the trail.
3. **A blocker that is real but unfiled will be released by any guard that demands a filed blocker.** Filing
 the owner row is the fix; discovering it after a wasted release is the cost.
