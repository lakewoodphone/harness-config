**L12369 · A card charge that never reached Stripe was invisible: nothing compared the two ledgers**

**What this session proved, all read from production on 2026-10-25.** `docker logs lpt-backend` at 19:59:36Z shows `prisma.order.create()` failing twice on the `orderNumber` unique constraint before succeeding; the live `orders` table then holds SALE order WO2610250003 (#3241, 10.66, READY_FOR_PICKUP / PENDING) and Stripe holds `pi_3UUXZtLnlgYj1gmT0JWKTiu3` for it in `requires_payment_method` — **no card was ever attached to that intent and no rows exist in `payment_transactions`.** Production was serving commit `63ef0c67dc34` (branch main, per `/opt/lpt/.deployed.json`), i.e. the 2026-10-22 build.

**Two lessons that outlive the bug:**

- **A charge that never reaches Stripe is invisible unless something compares the two ledgers.** Nothing here did. `scripts/ops/reconcile-card-money.mjs` now runs every 30 minutes on `lpt-apps` and reports an abandoned counter card box whose SALE order is still unpaid — which is exactly WO2610200001 (#3142, 15.99) from 2026-10-20, the same failure a week earlier, sitting on the books unremarked for five days.
- **Two columns write a card payment's Stripe id** (`stripePaymentIntentId` from the counter's card box, `stripeChargeId` from the plan/charge paths). A checker that reads only one reports live, correctly-recorded money as missing — the first run of this script called $469.94 of real, recorded charges "no row". Ask what writes the field before filtering on it.

**What the fix does, and what it does not do.** It stops a settled sale from closing the sheet and destroying the receipt, and it installs the reconciliation. It does **not** explain why the typed card never reached Stripe: the intent stayed `requires_payment_method` with no error attached, which means `confirmCardPayment` was never called with a card, and the browser side of that is not visible from the server. That is the next thing to pin down, with the operator's on-screen sentence or a browser run of the flow.
