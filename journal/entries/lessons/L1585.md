**L1585 · A fix that logs success but is not persisted to the file the consumer reads is not a fix**

MEASURED 2026-09-15 (ZABZ-TECH) during the W4 integration.

The retirement code logged success three times on startup -- subsystem_presence: retired 'boa_sync', plus balance_capture and spending_report -- and its tests passed. It read as done. But data/autopilot_state.json kept its PRE-RESTART mtime and still read ailed / consecutive_failures=114. The retirement had happened IN MEMORY ONLY: it is wired 'before every state save', no save followed inside the observation window, and utopilot_interval_sec defaults to 3600 s. The consumer that manufactures the tasks (app/assistant_chat.py:2282-2320) reads the FILE. So the phantom generation would have continued for up to an hour while the log said retired.

RULE: when a fix's effect travels through a file, cache or store that a DIFFERENT component reads, verifying the fix means reading THAT artifact -- not the log line and not the test. Ask, for every fix: who reads the thing I changed, and from where? A log line proves the code ran, not that the state moved.

SECOND RULE, from the same finding: when you fix a data-shaped bug by teaching a READER to ignore a status, ask what WRITES that status, and whether it can still write it for a thing that does not exist. The consumer's own comment at assistant_chat.py:2294 records that stale failure entries for amazon_sync/ebay_sync already caused this exact phantom-task bug and were 'fixed' by skipping three statuses -- so it recurred for boa_sync and spending_report. The durable fix is at the writer (refuse to record a failure for a subsystem that is not installed), and that is what W4 added.
