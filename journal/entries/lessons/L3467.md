**L3467 · journalctl -u does NOT follow a systemd unit alias - an alias makes systemctl status look right and leaves every journal-reading monitor blind**

WHAT. `journalctl -u <alias>` does NOT follow a systemd unit alias. Measured, 2026-10-11 on
`secratary-cloud`, because it was the obvious cheap fix and it does not work.

TEST. A unit alias is a symlink in `/etc/systemd/system`:

 ln -sfn /etc/systemd/system/company-api.service /etc/systemd/system/secretary-api.service
 systemctl daemon-reload

RESULT.

 before alias: journalctl -u company-api --since "7 days ago" -o cat | wc -l -> 2499
 before alias: journalctl -u secretary-api --since "7 days ago" -o cat | wc -l -> 0
 after alias: journalctl -u secretary-api --since "7 days ago" -o cat | wc -l -> 0
 `systemctl is-active company-api` -> active (the alias never touched the running unit)

`journalctl -u` matches the journal's own `_SYSTEMD_UNIT` field, which is the canonical unit name, so an
alias makes `systemctl <verb> secretary-api` work while `journalctl -u secretary-api` still returns
nothing. The alias was removed immediately (`rm -f` + `systemctl daemon-reload`); `daemon-reload` does
not restart a running service.

THE RULE. Do not use unit aliases to paper over a renamed or relocated unit. Two lessons, and the second
is the one that generalises:
 1. `journalctl -u old-name` returning 0 lines is NOT evidence that nothing happened — it is evidence
 that the name is wrong. Always confirm a non-zero line count against the unit you believe is
 producing the events before believing a zero.
 2. An alias is a trap in a migration, because it makes `systemctl status` and `systemctl show` look
 right while leaving every journal-reading monitor blind. **Rename at the source (the script, via an
 env var the deployment sets) or translate the name explicitly; do not alias.**
