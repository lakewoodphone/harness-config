**L3826 · A case file and its credential companion can land on different branches; main then carries a record whose case file it does not have**

**A case file and its credential companion can land on DIFFERENT branches, and `main` will then
carry a record whose case file it does not have.**

Measured 2026-10-14 on the Mendelowitz iPhone walk-in (WO-less; phone 2015667853), while pulling
the case up for the owner.

`.gitignore` is not the only way case work goes missing. Two sessions worked this one case on
2026-10-13 and pushed to different refs:

- `_credentials-mendelowitz-2026-10-13.md` **and all six intake photographs** → `main`
 (`6f5c6083c`, `ad55e2621`).
- `iphone-mendelowitz-2015667853-2026-10-13.md`, its sync record, and
 `sops/IPHONE-APPLE-ID-SIGN-OUT-RESTRICTIONS-SOP.md` → **only**
 `shift/lpt-sync-20261013-linker-parity`, which never reached `main`.

So on `main` the case read **closed** with no case file under it, and the newest case file that
existed anywhere still read `waiting` — "blocked on a Screen Time passcode" — a state that had
stopped being true hours after it was written. A reader on `main` could not see the case at all; a
reader on the branch saw a stale one.

**The detection is three commands and none of them is a grep of a working tree:**

```
git ls-tree -r --name-only origin/main -- docs/customer-operations/cases | wc -l # 298 vs the
 # case you are holding
git cat-file -e origin/main:<path> # a path "on disk but not in 'origin/main'" is the tell
git merge-base --is-ancestor <the commit that added the file> origin/main # rc 1 = not on main
```

`lptcase.py` will happily index the case file it finds in **your** working tree, so a local
`lptcase show` is evidence about your checkout, not about `main`. Its own banner is the honest part:
read the "N commits behind / ahead of origin/main" line and the branch name in `git status -sb`
first — and note that behind/ahead **against `origin/main` while checked out on a shift branch** is a
meaningless comparison, not a staleness measure.

**The fix that was right:** a detached worktree off `origin/main` (never the branch another session
is sitting in), the three files copied in, the case file's front-matter and status brought into
agreement with the closed credential record, and a fast-forward `git push origin HEAD:main`
(`8bea58004..1cb9ebe76`). Verified by reading it back **out of `origin/main`, not off the disk** —
`git grep -n '^status:' origin/main -- ...` now returns `closed` for both files.

**Left no count worse** (measured, two worktrees, same index): case files 287 → 288,
`duplicate-phone` 21 → 22 — and that one is the *credentials-companion* shape, which already occurs
11 more times in the corpus (`_credentials-tzipporah-tchiprout` shares a phone with two case files).
All other classes identical: `sync-record-without-case` 222, `case-without-sync-record` 99,
`extraction-warnings` 147.

**A second, separate defect found in the same file and worth the same treatment:** the intake line
read *"do not create a new Apple ID"*. The customer's own handwritten slip — photographed at intake,
transcribed in §5 of the credential file — lists **`- new apple ID`** as a *requirement*, and a new
Apple ID is exactly what the owner created and handed him. An early misreading of the customer's
wishes was sitting in the case file as if it were a constraint. The wrong line stays, with the
correction beside it, which is the only way a later reader can tell which one was believed when.
