**L3381 · I killed the harness three times with 'Get-Process node | Stop-Process': a cleanup by process NAME takes out the engine serving the conversation**

GOAL ROUND 27, and the owner asked me point-blank 'what keeps happening'. The answer was mine. Three tool calls came back as 'interrupted after it was recorded, but no result was durably recorded', and the cause was one line I had written into a cleanup step: Get-Process node -ErrorAction SilentlyContinue | Stop-Process -Force. I intended it to clear the stray Next.js dashboard I had started for a test. What it actually matches on this machine: pid 4292 'dsh web' - THE ENGINE SERVING THIS WEB GUI on port 3099; pid 34080 dshw-proxy.mjs, the multi-window proxy; pid 15220 the local SUBPROCESS RUNNER that executes my own tool calls; and three MCP servers (playwright, mcp-remote, firecrawl). So the call was recorded, and then the very process that would have durably written its result was killed - which is exactly what the error message said, and I read it three times without understanding it. The harness is supervised, so the engine restarted within seconds (their creation times cluster right after each kill), which is why the session survived at all instead of ending. THE LESSON, in the smallest possible form: never kill by process NAME on a machine that runs the thing you are talking through. Kill by the PID THAT OWNS THE PORT you started - I already knew the port (3000) and had a one-line way to get its owner. RULES: (a) a pattern-based kill is a shotgun pointed at everything that matches, including the harness, the tool-call runner and the MCP servers; (b) when a tool result is 'unknown', the cause is usually ON THIS SIDE - I assumed flaky infrastructure for three rounds of interruptions before checking what my own command had matched; (c) after any kill, list what is still running and what is listening, because 'the process is gone' and 'the RIGHT process is gone' are different facts. Also worth recording separately so the two are not blurred: an earlier 4-hour gap (02:31 to 06:41) was the session being IDLE, not these kills - the engine restarted in seconds each time, so the two have nothing to do with each other.
