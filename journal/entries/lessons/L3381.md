**L3381 · For a content index freshness is content, not file mtime - measured wrong in both directions**

## L-new · For a content index, freshness is content — not file mtime. Measured wrong in both directions on the same tool

**Both failures happened within one hour on 2026-10-08, on `fa journal` (find-anything).**

1. **mtime fresh, content stale.** The authority's journal index read "29 minutes old" while its corpus
 stopped in September: the file had been rewritten by an autocommit on a checkout that was behind.
 `fa journal vahab` answered *no match* for a customer whose case was written that night, with a
 freshness note that made the answer look trustworthy.
2. **mtime stale, content correct.** After the entries were pushed and the index regenerated, the same
 index — whose content was exactly current — reported `STALE: ... age 4061s > max-age`, and the tool
 refused to trust its own correct answer. The reason: this index is written when the journal
 *changes*, so an up-to-date index can be hours old on disk.

The fix is to test the thing that matters: count both sides. `fa journal` now compares the index's entry
count against the number of entry files on disk and says `INDEX BEHIND: N in the index vs M on disk`
(exit 3) only when they disagree; an explicit `--max-age` still asks for the age test, and the age is
still printed as context. The comms index and the path/ctags indexes keep age ceilings, because those
*are* rewritten on a clock (30 min and 15 min).

**Rules that survive this.** (a) A file mtime answers "when was this written", never "is this current" —
publish what the index *covers*, not how old it looks. (b) A staleness threshold must be longer than the
refresh interval, or it cries wolf on a healthy system and trains readers to ignore it: a 300 s ceiling
against a 30-minute refresh put STALE on every business-data answer. (c) When a freshness test fires,
ask whether the *test* is wrong before deciding the data is.
