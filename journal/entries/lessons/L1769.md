**L1769 · lpt: the computer-finder questionnaire is blocked at createContext, before any procedure guard**

The questionnaire router (backend/src/trpc/routers/laptop-preference.ts) has been customerProcedure on all three procedures since 03acd5cea, and that is correct. It still cannot submit.

Two independent gates sit in front of it:
1. createContext -> isCustomerAccessibleTrpcRequest (backend/src/trpc/context.ts:106-118) allows a CUSTOMER token only for customerPortal./customerAccount./auth.refresh, and throws FORBIDDEN at context.ts:164-167.
2. customerProcedure (context.ts:511).

Routers are registered under the keys customerPortal, customerAccount, google, laptopPreference (backend/src/trpc/index.ts:122,124,126,192). So POST /api/trpc/laptopPreference.upsertMy matches no allowlist entry and dies at gate 1.

MEASURED by execution, not by reading: backend/src/trpc/__tests__/customer-token-allowlist.test.ts drives the real createContext with a CUSTOMER token and prints 'GAP PRESENT: ... refused at context.ts:164-167'.

WHY IT SURVIVED: the router tests build a mock context via createCaller(), which never executes createContext, and trpc-router-guards.test.ts asserted guard TEXT. A guard allowlist keyed on request paths and a router registry keyed on names are two lists that nothing compares. Any new customer-facing router hits this.

RULE: when a customer-tier feature 'cannot submit', check the path allowlist in createContext BEFORE the procedure guard, and test it by executing createContext, not by inspecting the guard.
