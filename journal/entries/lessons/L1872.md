**L1872 · NanoMDM never clears enrollment_queue.active - count queue depth by the retrieval predicate, not by the flag**

## Lesson — NanoMDM never clears `enrollment_queue.active`, so queue depth must be counted by the retrieval predicate

Measured 2026-09-17 on the waze-mdm fleet.

NanoMDM's own retrieve-next-command SQL (extracted from the running `nanomdm` binary, `/app/nanomdm`, with `docker cp` + `strings`) is:

```
... FROM enrollment_queue AS q
 INNER JOIN commands AS c ON q.command_uuid = c.command_uuid
 LEFT JOIN command_results r ON r.command_uuid = q.command_uuid AND r.id = q.id
WHERE q.id = $1 AND q.active = 1
 AND (r.status IS NULL OR (r.status = 'NotNow' AND NOT $2))
ORDER BY q.priority DESC, q.created_at LIMIT 1;
```

Two consequences that matter:

1. **A row whose command reached a terminal status is never offered again, whatever `active` says.** `active` is not the boundary; the `command_results` join is. So "queue depth = count of active rows" is wrong, and it is wrong in the safe-looking direction — it inflates.
2. **NanoMDM does not clear `active` on acknowledgement.** Fleet-wide: 8,668 queue rows, 570 active, of which **394 already carry an Acknowledged/Error result**; only 177–179 have no result row. `max(updated_at) WHERE NOT active` = 2026-09-15 19:25Z (one bulk clear); every active row is untouched since insert.

The defect was in `PGDeviceInspector.get_queue_health` (`deploy/waze-mdm/fleet-api/nanomdm_client.py`): it counted `COUNT(*) … WHERE active = true` as `depth` while already computing the correct `pending` and `notnow` fields it then ignored. `/fleet/health.queue_issues` sums `depth`, so the fleet's headline health number was ~3x its real work and permanently red — which is how a number stops being read.

Fix (shipped 2026-09-17, verified live): `depth` = `COUNT(*) FILTER (WHERE status IS NULL OR status = 'NotNow')`, with `terminal` reported separately so the inflation stays visible, and an unreadable queue now returns `None` (a refusal) instead of a healthy-looking `0`. `/fleet/health` went **541 → 179** (the intermediate 578 was the pre-fix reading after a midnight batch). Tests: `deploy/waze-mdm/fleet-api/test_queue_health.py` (4 passing).

Deploy note: `nanomdm_client.py` was byte-identical in repo and host, so this fix carried no merge risk. It reached production by `docker cp` + restart (see the deploy lesson) and is committed in the repo; `fleet_api.py` still needs the repo/host merge.
