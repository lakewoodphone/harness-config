# L1918 — the dangerous writer was the third one, and it was found only after two safe ones were named

## What was true

`daily_reconciliation.py:703-710` called `link_records_to_orders` with
`dry_run=bool(getattr(settings, "reconciliation_dry_run", False))`, and `reconciliation_dry_run` was
False. That value flowed into `lpt_hub_link_orders.py:452`'s `if dry_run: continue` guard, past it, to
`_gh_write_file(..., branch=_BRANCH)` with `_BRANCH = "main"` (:35, write at :458-469). The caller is
the daily reconciler: unattended, every 24 hours. So every newly-matched customer case record — name,
phone, device — was written straight to the lpt-hub repo's **main** branch through the GitHub Contents
API, no PR, no branch, no review.

## Why it stayed hidden

Three modules in that repo set `branch="main"`. The audit checked two of them
(`lpt_hub_backfill.py`, `lpt_hub_phone_updates.py`), found both correctly dormant, and reported the
risk as latent. Only on re-checking did it find the third — `lpt_hub_link_orders.py` — which is the
only live one. Its own words: *"I MISSED that lpt_hub_link_orders.py:35 also sets _BRANCH = 'main' ...
THAT one is live."*

**The rule: a shared dangerous PATTERN must be enumerated exhaustively, not sampled.** Finding two
instances dormant is not evidence about a third. The right move is one search for every occurrence of
the pattern (`branch=\"main\"`, `_BRANCH`, `--force`, `dry_run.*False`) and a verdict per instance,
because the risk lives in the instance nobody looked at.

## The safe default already existed

`link_records_to_orders`' own signature is `dry_run: bool = True` (lpt_hub_link_orders.py:288). The
function was already safe. The **caller** overrode it. So before hardening a function, check whether
the unsafe behaviour is the function's or its caller's — adding a flag where a caller should simply
have honoured the existing default adds a knob instead of removing a hazard.

## The provenance failure that fed it

The same audit had ALSO reported `reconciliation_auto_merge: True` as the headline defect, and had to
withdraw it: the value is `False` at `config.py:381`, fixed earlier the same day. The checkout moved
mid-audit (HEAD 2026-09-15 → 2026-09-17 12:14) and the read had caught the pre-fix file.

So a finding resting on a config default or a line number is only as good as the commit it was read
at. **Pin HEAD at the start of an audit and re-verify config-derived findings against the current tree
before anyone acts on them.** The auditor reached this conclusion itself and stated that the corrected
finding was worse than the one it replaced — which is the behaviour to keep.

## Evidence

- The fix: psm `1dd89830`; new `lpt_hub_linker_write_to_main: bool = False` at `config.py:395`;
 caller now `dry_run=not _linker_may_write`. Verified on the authority by reading the deployed
 source: default `False`, and `dry_run=not _linker_may_write` present.
- The three writers: `lpt_hub_backfill.py:24`, `lpt_hub_phone_updates.py:11`,
 `lpt_hub_link_orders.py:35` — the third called from `daily_reconciliation.py:699-710`.
