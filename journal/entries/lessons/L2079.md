# A mesh child's host is chosen by the broker - a brief pinned to one machine's filesystem burns the child's whole turn

Measured 2026-09-20 ~07:25Z on ZABZ-YOGA, first dispatch of the session.

I briefed a `subagent` call to work in the LIVE tree `/home/zabz/personal-secretary-mvp` on the Linux
authority (secratary). The mesh placed it on **ZABZ-TECH** (a Windows desktop) and the child spent its
entire turn discovering it was on the wrong OS: the provider's own report says
`transport host = ZABZ-TECH`, `transport cwd = C:\Users\ezabz`, and it printed only grep bookkeeping
before dying:

```
exit = none (timed out) in 1800114 ms
the remote turn did not finish within 1800000 ms and the ssh client was killed
lease mu9hva6m-1tys9-1h-05ffa95c COULD NOT be released (broker-error: unknown)
```

**The rule.** `subagent` placement is the broker's decision, not the brief's. When a task is rooted in a
specific host's filesystem, do NOT write the brief as if the child is already there. Either
(a) have the child ssh to the named host itself as its first act and verify `hostname` before touching
anything, or (b) do the work on that host directly via ssh from here. Option (b) is usually cheaper for
anything small, because an ssh round trip costs seconds and a mis-placed child costs its whole turn cap.

**Also measured, and worth knowing before briefing anything long:** the remote child-turn cap is
1800000 ms (30 min), and the diagnostic for hitting it reads like a transport failure
(`ssh client was killed`) even when the transport was fine and the child was working. Do not read that
marker as "the mesh is down" — read the `exit =` line and the `transport host` line first. A timed-out
lease reports `COULD NOT be released (broker-error: unknown)` and the broker reclaims it at TTL, so a
killed child is not a leaked slot.
