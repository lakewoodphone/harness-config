**L1605 · Check that a command RAN before checking what it said - a crashed run filtered for failure counts reports zero, which is exactly what a passing run reports**

**Evidence, 2026-09-16, round 17.** Two measurements and one near-miss.

## The near-miss, first, because it nearly fooled me

I tried to run the suite single-threaded with `--poolOptions.forks.maxForks=1`. **That flag does not exist in vitest 4.** The run died immediately with `CACError: Unknown option`, and then my output filter — `Select-String -Pattern '^ ❯ src.*failed' | Measure-Object` — reported **`0`**, which reads exactly like a clean run.

**A crashed command, filtered for failure counts, produces the same output as a passing one.** The filter asks "how many failures were reported"; a command that never ran reports none. I only caught it because I looked at the raw tail to confirm the run had happened, and found a stack trace.

**RULE: check that a command RAN before checking what it said.** For any suite or scan, assert something that must be true of a real run — a total count, a duration, a non-zero number of items collected. "No failures reported" and "nothing was reported" are the same output and opposite meanings. This is the tenth instrument fault this session and the **second** where a crash read as health (the first was the `esbuild` check that was never installed).

## The measurement that matters

| Command | Failures |
|---|---|
| full suite, default 8 forks | **38 failures / 22 files** |
| full suite, `--maxWorkers=1` | **9 failures / 6 files** |

So there are **two** problems, and they must be reported separately:

- **9 deterministic failures** — real test defects that survive serialisation. These are fixable assertions and I fixed five of them.
- **~29 concurrency-induced failures** — files that pass alone and under one worker but fail when eight forks run at once. A suite-hygiene bug with a different cause and a different fix (shared mutable state, or resource starvation — the `errorLogger` file took 122 s in the concurrent run).

**Reporting them as one number is what made this invisible for two rounds.** 21, 25, 38, 9 — all true, none comparable, because the command varied. The number was never a property of the code.

## What the five fixed failures taught

Both files were failing **because this audit's own changes landed**:

- `terminal.error-handling` called `createCaller({})` with an empty context and expected a *configuration* error. The guard now rejects that before the handler — so the test had been passing for a reason that no longer existed.
- `google.router` expected `revokeAllForUser(1)` and got `revokeAllForUser(1, null)` — the exact shape of round 5's `exceptToken` fix.

**A test that fails because a deliberate change landed is the change being visible.** That is the outcome to want, and it is worth saying in the record: these were not regressions, they were the audit showing up in CI.
