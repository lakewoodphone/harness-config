**L3104 · Brief read-only lanes with the DEPLOYED tree, not a local checkout - and strip CR before piping a script over ssh**

Three separate read-only subagents were briefed with the LOCAL repo path (C:\Users\ezabz\code\personal-secretary-mvp) and each returned findings that were WRONG ABOUT PRODUCTION because that local branch has diverged from the live tree on secratary (/home/zabz/personal-secretary-mvp, branch hk/20260929-w10-seed-bc28-date).

Concrete false claims they produced:
 - "the daily quota is dead code, get_db_connection does not exist" -- FALSE on production, where get_db_connection is defined and the quota fires. I had already watched it fire.
 - "owner_text.gate() is called from nowhere" -- FALSE on production, where sms_service.py calls it in 8 places.
 - "app/owner_text.py is untracked and orphaned" -- true of the LOCAL branch only.

Cost: I nearly acted on a "dead code" finding that would have led me to rewrite a working quota.

THE RULE: when the question is "what is the running system doing", brief the agent with the path of the tree that is actually DEPLOYED, and have it state the path and the git HEAD it read. A local checkout is not the system. Two trees claiming the same project name is exactly how a confident wrong answer gets produced.

ALSO MEASURED, same session: PowerShell here-strings piped into ssh arrive with CR line endings, which silently corrupts shell arguments -- `grep ... app/config.py` failed as "app/config.py\n: No such file or directory", and a second command was mangled into `cp ... \/app/...`. The reliable pattern is: write the script with the file tool, strip CR (`-replace "`r",""`), then pipe it to `ssh host "bash -s"`. Every inline multi-command heredoc attempted this session failed at least one command.
