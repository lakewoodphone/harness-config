**Fault 1 — the work supply bridge has never run.** `roadmap-supply` writes `FAILED rc=1` for
kosher-ai-filter on **every hourly tick** (`cannot read the project repo for kosher-ai-filter:
'/home/zabz/repos/kosher-filter-ai'`; 27 lines on 2026-10-13, latest 2026-10-16T01:07:01Z in
`/root/.sms-inbox/sources.log`). That is why the ledger reached 0 todo and every shift since 10-13 has
invented its own next item. Filed as **kosher item 383**, whose DoD explicitly forbids the naive fix:
creating that path expires checkout-health's "declared remote-only" note and makes the sensor start
measuring a stale shallow clone instead of the real tree. The authority CAN read the repo over https
(`git ls-remote` -> `ad3ade4a...`), so the fix is available; it needs the runner to pass `--repo`
(a mapping-file key plus a line in `roadmap-supply.py`), in `harness-config`, not edited on the host.

**Fault 2 — one malformed state file killed the whole source.** `project-keepalive` raised
`SIGNAL UNREADABLE -- project 'lpt-website': 'remaining' must be a list` at 00:37:01Z and 01:07:01Z and
exited 1, discarding the run — so the 7 projects AFTER lpt-website in the registry got no flag at all.
An lpt-website shift had rewritten `remaining` as a JSON string at 01:13Z. I repaired the data
(backup `/home/zabz/.wake-projects/lpt-website.json.bak-remaining-type-20261016T011839Z`), proved with
`project-keepalive.py --dry-run` that kosher and lpt-website flag again, and filed the per-project
isolation fix as **housekeeping item 384**. The writer is a language model and will do it again: the
data fix alone is not the fix.

**What this teaches, beyond the two faults:** every component reported health while kosher's automated
work supply had been dead for three days — the failure was one `FAILED rc=1` line per hour in a log
nobody reads. When asked "is X being worked on", read the SUPPLY (the source's per-project verdict
lines) and not only the OUTPUT (commits, closed items). The output looked excellent.
