**L3060 · A compiled file is not a running file: I crash-looped the live owner path, and only an end-to-end test on an isolated copy found it**

MEASURED 2026-09-29, in one session, on the AI text line. Two lessons, both about how I find out I
am wrong, plus one about a transport that eats a fleet.

## 1. I SHIPPED A CRASH INTO THE LIVE OWNER PATH, AND ONLY AN END-TO-END TEST FOUND IT

While wiring the owner's own text through the tool loop I wrote, inside the owner branch:

 _brain_decision = dict(decision)

The owner branch binds `_decision` / `_action` (sms-responder.py:583-584). The GENERAL path binds
`decision` / `action` (sms-responder.py:705-706). `decision` is therefore unbound in the owner
branch, and the file compiled cleanly because the name resolves at runtime, not at compile time.

It only fires when the owner sends a text carrying a `work` verdict - the commonest thing he does.
The failure is worse than a traceback: the row was left `state=new` with no decision, so the next
5-minute tick would pick it up and hit the same line again. **A crash loop on every owner text**,
silent in the log because the traceback went to responder.log at the end of a 5-minute cron.

WHAT CAUGHT IT: an end-to-end run of the REAL branch against a THROWAWAY store and a THROWAWAY
ledger, using the two environment overrides that make it possible -
`SMS_INBOX_DB=<copy>` (a `sqlite3 .backup`, not a raw `cp`) and `WORK_DB=<temp>` (work.py honours
it). Every send went through `--dry-run`, which four earlier fixes in the same session had made
genuinely safe. It printed the traceback on the first attempt.

WHAT DID NOT CATCH IT, and this is the point:
 * `python3 -m py_compile` - passed.
 * a module-load smoke test (`sms-responder.py pending`) - passed.
 * a unit test with stubbed side effects - passed, because that test called `_do_work` directly
 and never executed the branch that contains the bad line.
 * the running tick - there were zero inbound texts to decide, so the branch was never reached.

**THE RULE.** A staged file that compiles is not a staged file that runs. When a change adds a call
on a path that only executes under a condition the live store does not currently satisfy, the
verification must CONSTRUCT that condition in an isolated copy. Compile, import and a stubbed unit
test are all blind to an unbound name on an unvisited branch, and the branch here is the one the
owner hits every time he asks for something.

Also worth keeping: the FIRST version of that unit test also failed, and the test was the thing
that was wrong - it fed `holding` straight into `_do_work`, bypassing the branch's own
transformation, so it measured the worker instead of the branch. A failing test is not
automatically a failing patch. Read which of the two is lying.

## 2. A 30-MINUTE MESH CAP PLUS A HANGING SSH WASTED THREE WORKERS

Three workstreams were dispatched. One delivered. Two - the wake-loop honesty work and the git-truth
work - were both killed at exactly 1800000 ms with the diagnostic:

 the remote turn did not finish within 1800000 ms and the ssh client was killed

Their own stderr shows why: **every ssh call to `secratary` prints its output and then hangs.**
One worker wrote its findings before dying - it had correctly diagnosed the cost discrepancy
(`wake-cost.py` reads per-run session files, so each run counts only what that run saw, while
`wake.py` sums the file) - and then spent its remaining budget bisecting which of 14 file paths
made a `sha256sum` loop hang. Another got as far as `test_pyssh5.py` chasing a reliable transfer.
Neither reached a report, so neither produced a usable deliverable.

WHAT WORKS, measured the same hour from the same machines:
 * ONE short command per ssh call, always with `-o BatchMode=yes -o ConnectTimeout=20` and, when
 latency is bad, `-o ServerAliveInterval=15 -o ServerAliveCountMax=3` so a hang becomes a fast
 failure instead of a 90-second stall.
 * For multi-line work: `(Get-Content -Raw script.sh) -replace [char]13, '' | ssh host bash -s`.
 * For file movement: `cmd /c "ssh host cmd > local"` or `scp`, then VERIFY THE SHA BOTH SIDES.
 * Host alias matters: on the office LAN use `secratary-lan`; off-LAN only the tailnet alias works,
 and from ZABZ-TECH `secratary-ts` prints one line and then hangs.

**THE RULE.** Do not hand a worker a 4-part workstream with 30 minutes of budget on a host whose
ssh hangs; it will spend the budget on transport and return nothing. Give it ONE question with a
one-command answer, state the verified invocation style in the brief, and make "one ssh call for
all files" the default rather than a loop of many. The drift test written this session
(`harness-config/scripts/deployed/assert-bin-matches-repo.py`) exists partly because of this: it
compares every file in ONE ssh call.
