**L4064 · CORRECTS L4001: the 300s timeout and the EPIPE are two separate defects - the timeout is fixed, the EPIPE is a per-file worker-teardown death**

**CORRECTS L4001 and pinpoints it: the 300 s timeout and the EPIPE are TWO SEPARATE DEFECTS. The timeout one is fixed; the EPIPE is not, and it is not caused by the timeout.**

L4001 said "EVERY shard was killed by the step's own inner timeout" and that "the EPIPE is a
CONSEQUENCE of the kill". **Half of that is wrong**, and this branch's own CI run disproved it.

DEFECT 1 — FALSE GREEN, REAL, NOW FIXED. The green shard (run 38572929997 job 115884424733,
SUCCESS) had its swallow branch print at 13:44:20.4 having started 13:39:19.9 — **exactly +300.5 s**
— with no vitest summary. So that green was a killed run reported as a pass. Fixed in **PR 443**
(`7339439a7`): inner `timeout` 300 -> 540, job 10 -> 15 min, and the exit-137 branch now emits
warning annotations instead of "Tests completed successfully". Still non-blocking by design.

DEFECT 2 — THE EPIPE, SEPARATE AND UNFIXED. Measured on PR 443's own shard 1/4
(run 38627467515, job 116071992556):

```
19:58:31.8 step starts
20:01:33.77 last file completes: "✓ .../databaseErrorMapping.test.ts (28 tests)"
20:01:33.84 Error: write EPIPE at PoolRunner.stop -> ForksPoolWorker.send -> ChildProcess.target.send
20:01:34.01 the `if: failure()` cleanup step runs
```

**~182 seconds in. Neither timeout is anywhere near. The failure path ran, not the timeout path.**
So the EPIPE is a spontaneous mid-run death, and it happens immediately after a test file completes —
i.e. **at the per-file worker teardown that `pool: 'forks'` + `isolate: true` performs after every
single file.**

WHAT IS SETTLED ABOUT DEFECT 2, WITH EVIDENCE:
- It is **not** the timeout (measured above).
- It is **not** the force-exits (they never print — L4000).
- It is **not** `poolOptions` (a no-op — L3933's surviving half).
- It is **not** a JS heap OOM (no such string in any shard log).
- It **is** in `PoolRunner.stop` -> `ForksPoolWorker.send` -> `ChildProcess.target.send`, and
 `ChildProcess.send` throwing "write EPIPE" as an **unhandled 'error' event** is what takes the whole
 process down before it can print a summary.
- Sometimes it is preceded by `Timeout terminating forks worker` (a 30 s `teardownTimeout` wait) and
 sometimes not; both end in the same unhandled EPIPE.

THE NEXT EXPERIMENT, and why it is the right one: the error is a **ChildProcess IPC** failure. The
`threads` pool uses `worker_threads` and **has no `ChildProcess.send` at all**, so this error class
cannot occur there. The repo pinned `pool: 'forks'` for JSDOM memory reasons; that choice is now
suspect, and switching it is one variable.

**A LOG-READING TRAP I HIT TWICE IN THIS INVESTIGATION, worth more than either defect: GitHub echoes
the whole `run:` block into the log at step start.** So grepping a log for a string that appears in the
script COUNTS THE ECHO AND NOT AN EXECUTION. Both "hanging-process output" (27-30 hits) and
"KILLED BY THE TIMEOUT" (2 hits, timestamped 19:58:31.800, *before* the step start at .814) were the
script being read back to me. **Only count a line whose timestamp is after the step started, or check
that it is not part of the echoed source.** I nearly recorded a fix as having fired when it had not.
