**L4001 · The frontend CI shards have never reported a test result - the step kills them at 300s and calls the kill success; the EPIPE is a consequence**

**The frontend CI shards have NEVER reported a test result: the step kills them at 300 seconds and calls the kill "Tests completed successfully". The EPIPE is a consequence of that kill, not a cause.**

This is the answer to the handoff's §5 "vitest EPIPE worker crash", and it is much larger than the
crash. It also supersedes the framing in `P3199` and retracts the remaining half of `L3933`/`L4000`.

THE CODE, `.github/workflows/pr-precheck.yml` at `origin/test`:

```
826: cd frontend && timeout --signal=SIGKILL 300 pnpm test --shard=... --run --no-watch || {
827: EXIT_CODE=$?
828: if [ $EXIT_CODE -eq 137 ]; then
829: echo "Test process killed by 5-minute timeout (shards 2/3 are known to hang)"
830: echo "Tests completed successfully - this timeout is expected for shards 2/3"
831: exit 0
```

**Line 830 is the defect.** A shard killed by `timeout` exits 0 and tells the log it succeeded.

THE MEASUREMENT — read from the shard the workflow reported **GREEN** (run 38572929997, job
115884424733, "Test Frontend (Shard 1/4)", conclusion SUCCESS):

| reading | green shard | red shard |
|---|---|---|
| step start -> kill branch | 13:39:19.9 -> 13:44:20.4 = **+300.5 s** | - |
| vitest summary `Test Files N` | **ABSENT** | **ABSENT** |
| `Timeout terminating forks worker` | present | present |
| `Failed to terminate forks worker` | present | present |
| `write EPIPE` | absent | present |
| `CI Force Exit Reporter` output | **ABSENT** | **ABSENT** |

**The green and red shards wedge identically. The ONLY difference is whether the pool's IPC happens to
throw on the way down.** So: green means "killed and swallowed"; red means "killed and something threw
first". Neither carries a test result, and the frontend suite has therefore never been gated on anything.

THIS EXPLAINS EVERY EARLIER OBSERVATION AT ONCE:
- why **no shard prints a summary** — the process is killed mid-run, every time;
- why the **force-exit machinery never printed** (L4000) — it is reached at the END of a run that never
 ends; it is not racing anything, it is simply never reached;
- why the crash is **"intermittent"** — the kill is constant, the IPC throw is not;
- why the **victim file name varies** — it is whatever file the worker held when the SIGKILL landed;
- why `--reporter=hanging-process` says nothing — it reports at the end, and there is no end.

THE FIX — PR 443 (`lpt/ci-shard-worker-pressure2-20261014`, commit `b41033475`):
inner `timeout` 300 -> **540**, job `timeout-minutes` 10 -> **15**, and the exit-137 branch now emits
GitHub warning annotations saying the shard was killed before reporting and proves nothing. It is
deliberately **still non-blocking**: turning a kill into a hard failure today would block every merge in
the estate, and the real runtime has to be measured before the shards can be made gating.

**CORRECTING MY OWN LOOSE READING, because it matters:** I first read "4 FAIL lines" in the green shard as
hidden test failures. They are `stderr | src/navigation/search/__tests__/indexBuilder.test.ts >
validateIndexPerformance > should fail validation for slow build` — a test deliberately asserting that
validation DOES fail, printing to stderr as designed. **Expected stderr is not a hidden failure.** Do not
quote a `stderr |` line as a failure.

**THE METHOD LESSON, and it is the one that cost the most time: THE PASSING CASE WAS THE WHOLE ANSWER AND
I READ IT LAST.** I spent rounds reading failing shard logs and building hypotheses about memory, pools
and force-exits. The run I needed was the one shard that PASSED, and it had been sitting in the run list
the whole time. **When a failure is intermittent, diff the passes against the failures — the difference
between them is the cause, and the failures alone can never show it.**
