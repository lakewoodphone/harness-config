## LESSON — `company-api`'s memory grows in ~1 GiB STEPS, not a slope; the top holder is mem0's Chroma HNSW index loaded lazily on first use

**Measured** 2026-10-14 17:10:50Z→17:26Z by the W1 worker on secratary-cloud. Full report:
`/root/_apiwedge-20261014/w1-memory/REPORT.md`.

**The shape of the growth is the finding.** A 60 s sampler on the restarted instance (pid 1078122):
```
17:11:42 809,080 kB 17:21:59 955,724 kB <- +14.3 MB/min drift, non-monotone
17:22:59 1,946,384 kB <- +967 MB IN ONE MINUTE
17:26:01 1,720,076 kB (VmSwap 0 -> 339,612 kB)
```
**Do not model this process as a leak with a rate.** There is a ~14 MB/min drift plus **discrete ~1 GiB
steps**, and the step was caught in the act. Journald either side of it:
```
17:22:13 WARNING mem0.memory.main: The 'chroma' vector store does not support keyword search...
17:22:13 INFO app.services.mem0_service: Mem0 initialised (storage=data/mem0)
17:22:13 INFO mem0.utils.spacy_models: spaCy lemma model loaded
```
Same 60 s interval: a **new 775,072 kB anonymous mapping** appears, threads 30→52, and the glibc main
arena `[heap]` **collapses 267,476 → 6,072 kB** (the allocator returning ~261 MB of FREE memory it had
been holding — retention, not live data).

**Ranked holders, by file identity and not by guess:** mem0's Chroma collection `8d818c8a` HNSW index
**757 MiB** resident, matching `/opt/company/data/mem0/8d818c8a-.../data_level0.bin` at 779,391,952 B
(0.2 % apart) — the fd is open on it. Then the app's own Chroma collection `438471c7` **309 MiB**
(324,223,876 B file, resident 316,684 kB, 0.02 % apart). Then the glibc `[heap]` 238–276 MiB, one
unidentified 103 MiB anon map (**NOT VERIFIED**), and ~470 MB of CPython pymalloc arenas. **There is no
single multi-gigabyte mapping** — the old 5–11.8 GiB readings are many mid-size regions plus allocator
retention.

**Code path:** `app/services/mem0_service.py:155 _get_memory()` → `Memory.from_config(config)` at
**line 227**, configured at 217–223 with `vector_store.provider=chroma, path=data/mem0`. It is a
process-global singleton initialised on the FIRST mem0 extraction, which is why the cost is invisible
for the first ~11 minutes after a restart and then lands all at once.

**Three corrections to files that were confidently wrong:**
- `40-malloc-arena.conf`: correct for its moment, **but no longer the live mechanism.**
 `MALLOC_ARENA_MAX=2` WAS in the wedged process's environment and it still reached 5.06 GB anon. The
 64 MiB-aligned arena signature is now essentially gone (4 maps ≥64 MiB, one of them `[heap]`). The
 mitigation worked on arenas and the process wedged anyway — do not re-apply it and call it fixed.
- `30-memory.conf`: right about the page cache, but it **conflated two meters** (cgroup
 `memory.current` 5.70 GB vs process VmRSS 1.95 GB — a 3.7 GB gap that is all page cache).
- `estate-monitor.py`: `api_rss_gib` emits the MainPID's **VmRSS from /proc** but its `src=` string
 advertised `systemctl show`, which yields cgroup `MemoryCurrent`. At 17:14:03Z the two disagreed
 threefold (0.835 vs 2.848 GiB). Fixed in this session; the value was always right, the label was not.

**And a performance fact worth keeping:** the 2.0 s `/health` response is **not CPU**. `py-spy top`
showed `GIL: 0.00%, Active: 0.00%` with 14 threads — it is SQLite lock waiting (28 `database is locked`
and 13 `Health DB probe timed out` since the restart, from a daily reconciliation writing 7,002 rows
one transaction at a time). Optimising the handler would be fixing the wrong thing.
