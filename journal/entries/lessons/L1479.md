**L1479 · A downloaded file with no row does not exist; and 604 voicemails are recoverable from nowhere**

## The author of a download IS a row, and 604 voicemails are not recoverable from anywhere

Two findings from one afternoon spent chasing "604 voicemails with nothing readable".

### 1. A file on disk with no row is a file that does not exist

The downloader wrote the payload, then inserted the `dialpad_media_file` row — and the insert
died with `sqlite3.OperationalError: database is locked`. `_get_conn` already sets a
10-second busy timeout, and that is not enough: when a connection must **upgrade a read
snapshot to a write** while another connection has committed in the meantime, SQLite returns
SQLITE_BUSY immediately and the busy handler cannot wait it out, because waiting would break
snapshot isolation (`dsh_session_ingest.py:247` says the same thing). The remedy is a fresh
transaction, which means a retry.

The cost of not retrying is not one lost row. The file is on disk, the row is missing, so the
call still looks like it has no audio, and the next pass downloads it again — forever.
Measured: **37 files written, 0 rows recorded, the queue never moved**. After the retry was
added: 88 rows in the first ten minutes, and the same calls stopped repeating.

Rule: **a downloaded artefact is not ingested until its row exists, and the row write is the
part that fails.** Any script that writes a file and then records it needs the record step to
retry, or it manufactures an infinite loop that looks like progress (files on disk keep
growing) while the queue stands still.

### 2. Where 604 voicemails are NOT

916 calls carry a voicemail link. 312 are readable; **604 have nothing**. Verified in three
independent directions, all negative:

* **Dialpad media**: every one of the 604 returns **HTTP 404** from
 `https://dialpad.com/v/<call_id>`; none has a `voicemail_recording_id`; `was_recorded=0` for
 all 916 voicemail calls — this account's voicemail audio was never stored as a recording.
* **Dialpad API**: `transcripts/<call_id>` returns only `{call_id}`; `calls/<call_id>` is a
 404 path outright.
* **Email**: Dialpad *does* email a notification that **contains the transcript** — 248 exist
 in Gmail and 191 matched a call — but **every one of them describes a voicemail that already
 has text**, and searching for any of the 604 by its own number, at both ends of the date
 range, returns nothing.

Their call lengths are 30–40 s (505 of 604 are 30 s+), which fits either "listened to the
30-second greeting and hung up" or "left a message Dialpad did not process" — the data cannot
separate those two, and the write-up should not pretend it can.

So the conclusion is: **those words are not in Dialpad, not in our media and not in email.**
That is a source limitation, not a pipeline gap, and the value of the last two hours is
mostly this paragraph — it stops the next session from re-chasing 604 holes. The reusable
lesson is the *method*: when a gap looks large, enumerate the sources that could hold it and
prove each one empty, rather than improving the pipeline that was never the problem.

### Bonus: the notification email is a fallback worth keeping

`dialpad-voicemail-email-backfill.py` reads those notification emails (paging Gmail properly —
the API returns 100 per call, and the interesting months are 250 messages deep) and writes the
text as a re-transcript with `source='dialpad_voicemail_notification'`, so nothing claims it
came from audio. It recovered nothing today because there was nothing to recover, and it is
the tool that made the negative provable.
