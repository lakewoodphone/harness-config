**L3114 · A sweep keyed on a remote id can never resolve the rows that never got one - and prove your test reads what you think**

**L — A reconciliation sweep keyed on a remote id can never resolve the rows that never got one, and those rows become a permanent phantom backlog. Mark them terminal at write time, and watch for the shape.**

MEASURED 2026-09-30, the family-chat ledger on secratary

- `messages` held **18 outbound rows in status `queued`**, all created 2026-08-19 18:33-20:23, and **none of them had a `twilio_sid`**. Without a SID no status callback can ever arrive, and `reconcile_message_statuses` cannot help by construction - `db.outbound_without_final_status` filters `twilio_sid IS NOT NULL` (db.py:862), which is the *correct* worklist for a sweep that asks the carrier, and simultaneously the reason those 18 rows are unreachable by any automatic mechanism.
- They had been mislabelled for six weeks. Every query of the shape "is anything stuck in queued?" reported a phantom backlog, which is why the earlier P2191 incident was handled by hand (43 rows) and why 18 were back.
- The honest state was already recorded: joining `messages.outbox_id -> outbox.id` showed **all 18 outbox rows at `dropped`**. The repair copied that terminal status onto the message rows (backup `data/family_chat.db.bak-queued-20260930-152450`, 18 rows, 0 left in `queued`).
- A watch was added to `scripts/family_chat_watchdog.py` (commit `bf75e5b9`): an outbound row still in `queued`/`sent` past 20 minutes is a named problem with its count and oldest timestamp. `dropped` is not counted, because it is the honest terminal state.

RULE

A sweep that reconciles our record against a remote system's is only as complete as the join key it uses. Rows that never received that key are invisible to it *forever* - not late, not retried, invisible - so they must be resolved at write time (write the terminal state you already know) or they accumulate silently. And when you build the alarm for the shape, test it against a row you deliberately stuck: this check only earned its place after it was seen to fire.

SECOND RULE, FROM THE FALSIFICATION ITSELF

**Prove your test is reading what you think it is reading.** Two attempts to falsify this check "passed" for the wrong reason: the first stuck a row that was only seconds old (so 20 minutes had not elapsed), and the second edited a database copy while the script still pointed at the live one - the `sed` matched a path string that does not exist in the file (`DB_PATH` is *constructed* from `Path.home()`, not written literally), so it changed nothing and the check correctly reported the healthy live database. Both looked like evidence that the check could not fire. Print the path, then run the test.
