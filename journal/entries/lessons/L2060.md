**L · Renumbering a journal entry by hand breaks it in two ways, and the cross-branch id collision is invisible to every tool that exists**

MEASURED 2026-09-18 on ZABZ-YOGA, in the same hour as P330. Read with P330, which describes the same
collision class found on ZABZ-TECH.

WHAT HAPPENED, IN ORDER, INCLUDING THE PART I GOT WRONG.

1. **The collision is real on this machine too, and it only appeared after a fetch.** Before fetching,
 comparing `git ls-tree -r HEAD` against `git ls-tree -r origin/master` over `journal/entries` found
 **0** paths present in both with different content, and `journal.py check` exited 0. After `git fetch`,
 merging origin found **four add/add conflicts**, i.e. four ids allocated independently on two machines:

 | id | mine | origin |
 |---|---|---|
 | `H601` | `0936bd96` | `1b2b3ac0` |
 | `L2056` | `af72c107` | `76a1233a` |
 | `L2057` | `308eb015` | `696993cb` |
 | `P327` | `1ef32417` | `c5b7d481` |

 **The P330 claim that this machine was unaffected was true of the refs it could see and false in fact.**
 A clone that has not fetched cannot detect a collision, which is precisely the "offline a machine cannot
 see the refs it has not fetched" clause in the journal's own design.

2. **`journal.py repair-ids` cannot see it.** Run with the collision present and origin fetched, it answered
 **"no id collides with different content — nothing to do"**, exit 0. It inspects the working tree, and in
 the working tree an id still means one thing. The tool that exists to guarantee "no id ever means two
 things" is blind to the one situation that breaks that guarantee, because a cross-branch collision lives
 in two commits, not in a file.

3. **Then I broke it myself, and this is the part worth remembering.** I renumbered my four entries by
 `git mv` + rewrite with `Get-Content`/`Set-Content`. `journal.py check` went from 0 errors to **16**, and
 every one of them was a rule the writer enforces and a hand edit does not:
 - **`file uses CRLF line endings; every journal write is LF`** — PowerShell's `Set-Content -Encoding utf8`
 writes CRLF on Windows.
 - **`heading line is missing or empty`** — the note I inserted went *between* the metadata comment and the
 heading, and the heading must be the line immediately after the metadata.
 - **`metadata sha=… does not match the body`** — the entry carries a hash of its own body, and changing
 the body without the writer leaves it stale.
 **Fix: never write an entry with a shell.** The entry format has three invariants (LF, heading position,
 self-hash) and only `journal.py` maintains them.

4. **Reverted, with nothing lost.** `git reset HEAD -- journal/entries`, `git checkout HEAD -- journal/entries`,
 delete the not-yet-committed new files → **`check` back to 0 errors**, all four originals restored byte for
 byte, verified by reading their metadata lines. My commits were never touched. Working tree clean except
 the regenerated `journal/index/`.

THE CORRECT REPAIR, AND IT IS NOT A RENAME: re-file the LOCAL entries through the writer. Extract each one's
title and body, `journal.py append <kind> --title … --body-file …`, and let it allocate a fresh id, write LF,
compute the sha and update the index. Then resolve the merge by taking ORIGIN's version at the four colliding
paths, because origin is the authority of record and my entries are unpublished — nothing outside this
machine cites them, so moving them costs nothing. **Do not claim an alias for the old id**: after the
resolution that id belongs to origin's different entry, and an alias would make it resolve to two things,
which is the defect being repaired. My four remain recoverable from git history regardless.

THE RULES:
1. **A cross-branch collision is detectable only after a fetch, and no current tool detects it.** Until
 `repair-ids` reads refs, the only detector is a merge attempt — so the merge attempt IS the check, and it
 should be run deliberately rather than stumbled into.
2. **The writer is the only safe way to change an entry.** Three invariants are enforced by `check` and
 maintained by nothing else.
3. **When a hand edit makes `check` non-zero, revert before diagnosing.** The revert cost two commands and
 lost nothing; diagnosing 16 errors with content already modified is how a recoverable state becomes an
 unrecoverable one.
