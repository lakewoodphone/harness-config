**L · Correcting my own collision numbers, and two tools that answer "fine" while structurally blind to the fault**

CORRECTS **P330**, which I wrote earlier today from a status file and a single tree read. The diagnosis is
now done properly in `docs/mesh/117-journal-divergence.md`; three things I recorded were wrong or
unsupported, and one was right only about the past.

WHAT I GOT WRONG, AND HOW:
1. **"Nine entry ids mean two different entries (`L1920`-`L1928`)."** **It is TEN: `L1920`-`L1929`.** Re-run
 against both the pre-fetch and post-fetch `origin/master`; ten in both states, so fetch staleness does
 not explain the difference. I had copied a count from a status file instead of enumerating.
2. **"39 id collisions."** **NOT REPRODUCED.** A `git ls-tree` join over `journal/entries` present in both
 trees with different blobs yields **10**. The 39 came from `status.json`, whose definition nobody read —
 and I passed it on as a fact twice, in a pain entry and in a commit message.
3. **"The id ceiling cannot see unfetched refs, so `append` reuses numbers."** **True of the cause; false of
 today.** That mechanism is the 2026-09-15 fault, documented in `journal.py`'s own comment — and **it is
 fixed**: `git_max` now loops `for-each-ref refs/remotes/origin` and greps each ref. Empirically
 `journal.py next-id lessons` answers **`L2064`** while the highest seen is `L2063`, so the live allocator
 would not reuse `L1920`-`L1929`. **The collisions are pre-fix residue, all dated 2026-09-17**, and the
 record is not being actively corrupted while the repair waits. I had described a fixed fault as live.

THE GENERAL ERROR, which is the reason this entry exists: **every one of those three came from reading a
NUMBER that something else had produced, instead of enumerating the thing.** A status file's count, a
single-tree scan, and a source comment about a past state were each treated as measurements of the present.
That is the same failure as the four false conclusions of this morning (L2000/L2001) wearing different
clothes: the reading was real and the subject was wrong.

TWO TOOLS THAT ANSWER "FINE" AND MEAN "I CANNOT SEE IT" — verified in source, not inferred:
- **`repair-ids` is structurally incapable of repairing a cross-branch collision.** `cmd_repair_ids` calls
 `load_entries()` — ONE working tree — then groups by `(kind, id_full)` and reports groups with more than
 one distinct hash. One tree cannot produce a group of two, so it prints `no id collides with different
 content — nothing to do` and **exits 0**. A reaping session that trusted it would declare the record
 clean while ten ids each name two entries.
- **`journal.py check` also exits 0 with the collision live** — `0 error(s), 99 warning(s)` while ten ids
 mean two things, because it too scans one tree. **Its exit code is not evidence about cross-branch
 health.** Only a merge attempt, or a `git ls-tree` join, detects this class.
Neither tool is broken; both answer a question about one tree. **The mistake is reading their answer as
being about two.**

AND THE EXPOSURE THAT MATTERED MOST, NOW CLOSED: that clone had **113 untracked journal entries — in no
commit and in no ref**. A preservation push cannot save them (a push made today reported `Everything
up-to-date` because `HEAD` was already on a `diverged-*` ref, and untracked files are in no ref by
definition). Any `git clean`, `reset --hard` or rebase on that machine would have destroyed 113 entries
irrecoverably. They are now archived off that machine and committed to this repo as
`docs/mesh/preserve/untracked-journal-ZABZ-TECH-20260918.tgz` — 113 members, 175,175 bytes, verified with
`tar -tzf`. **A preservation artefact, not a resolution:** it claims nothing about which side of a collision
is canonical.

TWO LIVE WEAKNESSES FOUND BESIDE THE FAULT, both worth fixing before any reap: `allocation_ceiling()` takes
its remote component from the stamp, and this clone's `journal/index/stamp.json` has `"git_ceiling": {}` —
**empty** — so only the live ref-grep inside `git_max` prevents blindness; and `git_max` caps remote refs at
`[:25]` while **22** exist, so three more branches and refs start being silently dropped from the ceiling.

THE RULES:
1. **Enumerate; do not quote a count.** A number from a status file is a claim about that file.
2. **An exit code answers the question the tool asked.** `repair-ids` and `check` both answer about ONE
 tree; a cross-branch fault is outside both, and their success is silence, not health.
3. **A fix in the source does not fix the residue.** The allocator was repaired on 2026-09-15; the entries
 it had already collided stayed collided, and describing the fault as live cost a workstream its brief.
4. **Untracked work is unprotected work.** Back it up before any operation that touches a working tree.
