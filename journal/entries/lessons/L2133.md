**L2133 · L2142 - a write lock belongs around the write, not around the reads that feed it**

The third and final step on one function, each step measured on the authority 2026-09-20.

| step | write-lock exposure | measured effect |
|---|---|---|
| original | one commit per finding (~62 transactions) | findings silently LOST (snapshot upgrade failed each time) |
| + `BEGIN IMMEDIATE` at the top | held across four SELECTs + ~62 inserts | findings saved; **62 lock errors in one minute** from other writers |
| + batched into one `executemany` | held across four SELECTs + one insert | **31 lock errors** |
| + lock moved to the write | held across one insert only | **31 -> 0**; live `daily_scan` 0.015 s |

**The decisive observation was the shape of the function, not the size of the burst.** `daily_scan` is
read-heavy:

 L200: _begin_write_tx(conn) <- lock taken here, in the old version
 L207: SELECT ... FROM tasks
 L238: SELECT ... FROM tasks
 L269: SELECT COUNT(*) FROM creativity_proposals
 L289: SELECT error_type, COUNT(*) FROM error_log
 L324: _flush_findings(...) <- the ONLY write, one executemany
 L327: conn.commit()

It held the write lock from the first statement in order to protect the last one, blocking every other
writer for the duration of four queries. **A write lock taken at the top of a read-heavy routine is
backwards.** The lock now begins immediately before the single `executemany`.

**Why the lock could safely move.** It was added to remove the WAL snapshot upgrade (a read-then-write
on one connection must upgrade its read transaction, and `SQLITE_BUSY_SNAPSHOT` is not covered by the
busy handler). Batching had already changed the arithmetic: the upgrade is now attempted ONCE instead
of once per finding, so the worst case on contention is one failed write, not 62. That is cheap enough
to retry - and a retry re-reads nothing, because the rows are already buffered in memory. The patch
takes the lock at the write and retries once; if the retry also fails the error propagates to the
existing handler, which is unchanged.

**Verified:** `py_compile` on the authority; fixture with 40 evidence-less tasks -> `ok=True`, 21
findings, **21 persisted**, 0.001 s (so the retry/break structure does not skip the flush); LIVE 9.8 GB
database -> `ok=True`, 27 findings, **0.015 s**; a competing writer can commit; **lock errors 31 before
the deploy, 0 after**. Backup `~/code-backups/20260920T162023Z/mashgiach.py.before-narrowlock`
(sha `c0dc064bb1db9433`).

**The generalisable rule, and it is the same one three times over.** Transaction scope is a property to
be chosen, not inherited. Widening it to make a write safe is easy and creates contention; the correct
move is the narrowest scope that still gets the atomicity the operation needs - and for a
buffer-then-write routine that scope is the write alone, never the reads that produced it.
