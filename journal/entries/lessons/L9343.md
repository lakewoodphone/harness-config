## L — before adding a rule to a contract, measure that the contract is read

Measured 2026-10-19 on `secratary-cloud`, while doing handoff §7 item 5.4 for the kosher-filter-ai
repository: *"wire the checker into the wake system's definition of done — this is the single most
important item in the run."*

The task assumed a per-project DoD contract exists and can be extended. It does not exist. Three
commands settled it:

```
$ python3 -c "import json;d=json.load(open('/root/bin/sources/projects.json'));print(sorted(d['projects'][0]))"
['budget_note','builder_hosts','case','cooldown_seconds','dirty_ignore','enabled','id',
 'ignore_blocked_ledger','ignore_blocked_ledger_reason','integration_branch','max_flags_per_day',
 'notes','repo','repo_declared_note','repo_host','repo_remote_path','state_file','title']

$ grep -rl "definition_of_done" /root/bin /home/zabz/bin
(no output)

$ ls -l /root/bin/sources/projects.json -> 66036 bytes, no definition_of_done for any project
```

The field exists in `harness-config/settings/wake/projects.json` (schema `wake-projects/2`), which is
an authored superset **that was never installed**. The live registry is a different shape, and no
script in `/root/bin` reads the field at all.

I found this only because I edited the field, committed it, and then went to verify it was in force.
The edit was correct, the commit was clean, the diff was one line — and it changed nothing, because
the file is not the file the loop reads. **A change to a contract that is not Read is indistinguishable
from no change except that it feels like progress.**

There is a second-order trap here worth naming: four copies of that registry exist —
`settings/wake/` 15,706 B, `scripts/wake/sources/` 19,357 B, `scripts/deployed/bin/sources/` 22,676 B,
and live `/root/bin/sources/projects.json` 66,036 B — and **none is a superset of another**. That is
the same fault this estate has hit with `harness-config` itself (`P3164`: two `main` lineages that
were not supersets, and a fix nearly reverted the version that runs). "There is one registry" is a
belief, not a measurement.

**What I did instead**, because the ledger IS read by every shift (`ledger_driven: true`,
`work.py claim-next`): filed **ledger item 667** with `python scripts/check_docs_index.py` as its
definition of done, and left the registry clause in place, committed, for the day the superset is
installed. The requirement now lives where the loop looks.

**Still open, and honestly so:** a *standing* requirement that fires whether or not a shift claims
that item belongs in the loop's own code (`checkout-health.py` or the keepalive, run the three
checkers against the checkout it is about to wake). That is a change to a running service on the
authority and is the owner's call, not a session's.

**The rule, generalised.** Three steps before "add it to the contract": (1) find the file or field
the consumer actually reads, with a grep for the field name in the running code; (2) prove the value
you are about to write is consumed, by finding one line that reads it; (3) if nothing reads it, the
requirement must go somewhere that is read — usually the ledger item's own DoD, which a shift executes
— and the gap must be written down rather than closed on paper. "I added it to the config" is a claim
about a file. "It is in force" is a claim about behaviour, and only the second one is the work.
