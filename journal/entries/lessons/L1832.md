**L1832 · A canonical document kept only in a gitignored scratch folder is one deleted file from gone**

**Rule.** A canonical document kept only in a gitignored scratch folder is **one deleted file away from gone**. If a
file is the authority for a project — the design every other document derives from — it belongs in git, and the
proof that it is safe is that it can be recovered **from a fresh clone**, not that it "exists on my machine".

**Measured evidence (2026-09-17).** The Shlock project's canonical design (`_shlock-canvas-design.md`, its own
header: *"This is the canonical, single source of truth"*) and its v3 fabrication spec lived **only** in
`_scratch/` on one Windows machine, deliberately gitignored. On **2026-08-08** a VS Code session ran
`Remove-Item "…\_scratch\_shlock-canvas-design.md"` and returned **exit 0**. It was re-created six days later and
survived only because of that, plus an earlier revision sitting in VS Code's local `History` store. Recovering it
took **six parallel searches** across two Windows machines, `secratary`'s 16 git repos (reachable objects,
deleted-path history, stashes, dangling blobs), a 7.27 GB database, four mail accounts and every mesh node — and
the project's own README had been pointing at that file as the source of truth for months. Two other files named
as sources of truth (`shlock-current-content.txt`, `Shlock-Field-Guide.docx`) were never found at all, and the
path the README gave for the second — `OneDrive\Desktop` — **does not exist**.

**Why the ignore rule felt reasonable.** `_scratch/` is where generated evidence, big binaries and working files
go; the project documented the intent explicitly ("the drawings, generator and email record were never backed
up… these two files are the minimal durable backup of what was actually sent"). The mistake was applying the
rule to the **sources** rather than to the **byproducts** of a document that was the project's authority.

**What to do instead.**
1. For any project with a design authority, check it is reachable from a clone: `git log --all --oneline -- <path>`.
 An empty result is not proof it is tracked — check `git check-ignore -v <path>` too, which is what would have
 caught this immediately.
2. Commit the sources — design doc, spec, generators, and any irreplaceable imagery — even when they are
 scratch-flavoured. 18 MB in a docs repo is nothing against the cost of a six-agent recovery.
3. Prefer committing a **copy** under a dated name in the repo's document tree over un-ignoring the scratch
 path, so the working folder stays dirty and the record stays clean. Shlock now does this:
 `lpt-hub/research/miscellaneous/shlcok-source/` (commit `9a8815799`), with a README explaining why.
4. When a file is deleted, VS Code's `User/History/<hash>/` usually still holds a full snapshot keyed by an
 `entries.json` `resource` URI — that store survives file deletion and is the fastest recovery path.
5. Do not let a *second-hand* reference become the record. For months the project's memory file and README
 pointed at `shlock-current-content.txt` as the mechanism design; no chat, repo or backup on any host ever
 contained it. A pointer to a file nobody can open is a broken citation, not a source.
