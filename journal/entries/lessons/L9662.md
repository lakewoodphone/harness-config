**L9662 · A placeholder count took the queue's mail ingest down; starting the unit is the proof**

Lesson: the queue's email channel was down for ~40 minutes and only the unit's journal knew.

Measured 2026-10-19 15:45Z. `systemctl start lpt-owner-queue.service` exited 1 with
 sqlite3.OperationalError: 21 values for 20 columns
 owner-queue-ingest-mail.py:1243 (the suppressed-verdict INSERT)
One stray placeholder in a hand-written INSERT. The path only runs when a suppression rule fires
on a message, which is why it survived every run until one did. The whole mail ingest aborted;
GV kept flowing, so the queue looked half-alive.

What made it findable was the unit's own exit code - and what made it invisible was that nobody
reads `systemctl --failed` on a timer. Note also that ExecStartPost (health) does NOT run when
ExecStart fails, so the freshness check that exists to catch a quiet channel had no chance to run
here: the failure mode it cannot see is "the reader crashed", only "the reader went quiet".

Two habits worth keeping:
1. When you touch a table, run one INSERT with a real row before the timer does. A placeholder
 count is invisible to py_compile and to review, and the failing branch may be the rare one.
2. After editing a script that a timer runs, START THE UNIT and read Result/ExecMainStatus. It
 takes 35 seconds and it is the only proof the new code runs on the path the timer takes.
