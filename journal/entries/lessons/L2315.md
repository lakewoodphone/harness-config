## LESSON 3 — owner-queue row #121's whole premise was wrong: the $11/month is US Mobile phone service, not the filter. Acting on either prepared playbook would have damaged real customers (measured 2026-09-22 00:20-00:45Z)

WHAT THE ROW SAID, AND WHAT IS TRUE.

The row asked: "Two live Stripe customers are each charged 11.00 USD per month for the filter ... Is the filter product actually selling to these people, or are those two subscriptions strays to cancel?" Both prepared answers would have been wrong:

- **Playbook A** ("wire up the filter") would have set `metadata.tenant_id` on two subscriptions and created tenant rows in the filter app — for a charge that is **not the filter**. The filter's own recurring price is **$7.00/mo "Lakewood Filter - per device" (created 2026-09-14, 0 subscribers)**. The $11 price is **"Us Mobile Service Monthly"** — the cellular line. The Stripe invoice line is verbatim `1 × Us Mobile Service Monthly (at $11.00 / month)`. Wiring a filter tenant onto a US Mobile seat would make the filter app count and eventually suspend customers who are not filter customers at all.
- **Playbook B** ("cancel the strays and refund") would have cancelled the phone service of two **real, active shop customers**. Both are in `lpt_prod.customers`: mrs greenwood (id 1752, ticket 1652, order WO2607020002) and avrohom newman (id 1823, order WO2607160003 written 2026-07-16 17:02Z, five minutes *after* the subscription was created). $66.00 collected over 3 charges each, all paid, refunded=false, current through 2026-10-16.

The filter app's DB confirms the product has never operated for anyone: `tenants` 0, `phones` 0, `households` 0, `billing_provider_events` 0, and **every one of the 23 hits on `/webhook/billing/stripe` in the container logs is 400/401 — not one 200.** "Never a successful webhook" was true. "Two customers paying for the filter" was false.

**THE TRANSFERABLE RULE — a billing anomaly rows is not a premise until the CHARGE ITSELF is identified.** The row was written from the correlation "two Stripe subscriptions exist AND the filter records nothing" and never checked which product the price id belonged to. One read of the price object would have prevented both playbooks. When a queue row proposes to change or cancel billing, the first fact required is the **price id and its product name**, quoted from the provider — not the guess from the surrounding narrative. This is the same failure class as `P3 — Reading the wrong data and believing it`: an anomaly plus a plausible story is not evidence.

**ALSO: the wrong actor was proposed for the fix.** The defect is in the **handler**, which keys off `metadata.tenant_id` for any charge on the account, so a non-filter charge can never be ingested correctly (400/401 forever). That is a code fix owned by this seat, not a decision for the owner — row #121 should be resolved as *answered by measurement*, with the handler fix filed as work, and only the genuine question left (whether the filter product launches at $7, and whether the filter app should exist at all).

**RESIDUAL GAP, NAMED.** Whether Stripe's own "Resend" re-serialises `subscription_details.metadata` is unverified; the resolving test is a **test-mode** subscription with metadata set, a resent test event, and the handler's status code read. Do not run Playbook A's live resend before that test.
