**L3358 · Twice in one night I claimed a gap without reading the file - the pattern, not the instance, is the lesson**

NIGHT OF 2026-10-05/06, TWO INSTANCES OF THE SAME DISCIPLINE FAILURE. (1) I recorded that app/services/autonomy.py:212 carried the identical unfixed defect to the outbound_buffer bug; reading it showed it re-checks sqlite_master before trusting its flag and was already safe (corrected in annex K, pinned by tests/test_table_init_cache.py). (2) I wrote into deploy/hosting-migration/survivor.env that 'there is no existing timeout flag for the HA client' and proposed adding one; app/services/home_assistant.py already has a 3s connect timeout, a 15s per-request timeout, a 5s DNS cap and a 25s hard wall-clock cap through a thread pool - it was built for exactly the unreachable-HA case I was inventing a fix for. BOTH instances came from the same move: I inferred a gap from a shape (a similar variable name; a client I assumed was naive) and wrote it into a durable document before reading the code. Both claims were plausible, both were wrong, and both had already been written where a future session would believe them. THE RULE, stated so it can be checked: before recording a gap, DEFECT, or 'this needs building' claim, either (a) read the file or run the thing, or (b) label it explicitly as an unverified suspicion in the same sentence. A claim in a handoff or an annex is a fact to whoever reads it next - that is exactly why the system's most expensive historical failures were confident errors, and why L3355 (same-shaped code is not the same defect) needed this second instance to become a pattern rather than an anecdote. COST WHEN I SKIP IT: a future session builds something that already exists, or arms a fix for a problem that is not there.
