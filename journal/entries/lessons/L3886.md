# Observed once: `work.py add` answered `unknown-project` for a project that exists, and the same call worked seconds later

2026-10-20, on the authority, while filing a ledger item:

```
$ python3 /root/bin/work.py add --from-json -
error:unknown-project {"hint": "register it first: work.py project add --id kosher-ai-filter ...",
 "project": "kosher-ai-filter"}
```

Seconds later, the identical call succeeded (`item-filed {"id": 805, ...}`), and so did the flag form
(`--project kosher-ai-filter --title ...` -> `item-filed {"id": 803, ...}`). At the moment of the failure the
project row existed: `SELECT * FROM project` listed `kosher-ai-filter` with 177 items against it, and items
784/795/797/800/801 all still read `project = kosher-ai-filter`.

**Not reproduced, and the obvious explanation is ruled out:** nothing in `/root/bin` issues `DELETE FROM
project` (`grep -rn 'DELETE FROM project' /root/bin --include=*.py` -> nothing), and the only writers that
mention the table are `work.py` itself and `seed-discovery-items.py`.

## Why it is worth writing down rather than shrugging at
`cmd_add` refuses with `unknown-project` when a `SELECT id FROM project WHERE id=?` returns nothing. So either
that read saw a database state in which the row was absent, or it saw a DIFFERENT database. Two consequences
if it recurs:

- a woken shift that files its follow-up item gets a refusal that reads like a configuration error, so it will
 either stop or re-register a project that already exists;
- every item filed during such a window is lost silently, because `add` exits non-zero and the shift's habit is
 to read the first word of the output.

## What would settle it
On recurrence, capture `PRAGMA database_list` and `SELECT count(*) FROM project` in the same process that
failed, plus `ls -la /root/work/work.db*` (a `-wal` that is being checkpointed, or a second `work.db` on the
path, would both fit). Until then this is one observation with an exact error string, not a diagnosis - and
`error:` from `work.py` is never quiet, which is why it was noticed at all.

## The cost, so far
Two probe items (803, 804) were filed while establishing that the tool worked, and both are retired as
`dropped` with a note rather than left in the queue. That is the cheap version of this outcome.
