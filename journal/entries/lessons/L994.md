**L994 · 2026-09-14 · A monitor must not need the thing it monitors in order to report that thing's failure — and "needs admin" is a claim about the fix, not about the problem**

The attention badge tells the owner what the company is reporting. Its *unreachable* state said
"findings unavailable" — from a script that is **fetched from the authority**. So when the laptop's
Tailscale tunnel died after a reboot, the badge could not report its own failure; the pill simply
**disappeared and said nothing**. The owner's words: *"I think I saw the badge earlier today but I don't
see it now."* This is the founding failure of the subsystem (P55: the alert about the dead channel was
sent through the dead channel) reproduced one level up, by me, hours after writing the document about it.
Separately, `Restart-Service Tailscale` returned *"Cannot open 'Tailscale' service"* and I almost handed
the owner a task on that basis — but the isolation was fixed entirely at user level: launching the GUI
finished the daemon's handshake (`NoState → Running`), and `tailscale set --accept-dns=true` restored
MagicDNS (`CorpDNS` was false, so the hostname did not resolve *even with the tunnel up*).
*Rules:* (a) the code path that reports a failure must live somewhere that does not depend on the failed
thing — ship a local voice, even a tiny one, and let it retry; (b) audit every "cannot report X" state for
this circularity, because it is invisible until the day X fails and the only symptom is silence; (c) when
access is denied for **one route**, do not conclude the *problem* needs privilege — enumerate the
user-level routes (a GUI process, a `set` flag) before telling the owner anything is his to do; (d) a
working tunnel is not a resolvable name: check DNS separately from connectivity, because "No such host is
known" and "connection timed out" have different fixes and I initially treated them as one fault.
