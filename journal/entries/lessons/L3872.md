**L3872 · A process started over ssh on Windows dies when the session closes - use Task Scheduler**

**A process started over ssh on Windows dies when the ssh session closes — use Task Scheduler, not `Start-Process`.**

Measured 2026-10-19 while backfilling a search index from two workstations. On ZABZ-TECH I launched the
backfill locally and it ran for hours. On ZABZ-YOGA I launched the same script through
`ssh laptop-ts 'Start-Process cmd.exe -ArgumentList "/c C:\\...\\bf3.cmd" -WindowStyle Hidden'`, and it
died silently at the end of the first chunk: the log stopped mid-run with **no traceback and no exit
line**, because the parent cmd.exe was killed when my ssh connection closed. The Windows OpenSSH
session owns a job object and terminates the tree.

The reliable form on Windows is a scheduled task, which is owned by the Task Scheduler service and
survives:

 schtasks /Create /TN "usearch backfill" /TR "cmd /c C:\path\job.cmd" /SC ONCE /ST 23:59 /F /RL HIGHEST
 schtasks /Run /TN "usearch backfill"
 schtasks /Query /TN "usearch backfill" /V /FO LIST | findstr /i "Status Last"

On Linux the equivalents that survived the same test were `setsid nohup … &` (the authority) and
`systemd-run --unit=…` where a unit is wanted; plain `nohup … &` inside an `ssh 'command'` is not enough
if the session's process group is cleaned up.

**The tell is a log that stops without an ending**: a finished run prints its summary line, a crashed
run prints a traceback, and a killed run prints nothing after its last progress line. Before concluding
"the job is still going", check that the process exists — `Get-CimInstance Win32_Process`,
`pgrep -af` — rather than assuming silence means work.

Refs: `unified-search/scripts/backfill.py`; the two run logs `bf-tech.log` (survived) and `bf3.log`
(killed, then re-run under Task Scheduler).
