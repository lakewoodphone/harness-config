**L3501 · Extended \\?\ paths are rejected in .NET Framework legacy path mode; the app config is the escape**

Measured 2026-10-11 on ZABZ-TECH, both ways round, before anything was put on a card:

- From an app **targeting .NET Framework 4.0**, `Directory.CreateDirectory(@"\\?\S:\x")`
 throws `ArgumentException: Illegal characters in path` for EVERY "\\?\" path, and a
 288-character path without the prefix throws `PathTooLongException`. Windows PowerShell
 5.1 accepted the same "\\?\" string, which is what made this look like it worked.
- With `GO.EXE.config` next to the exe containing
 `<AppContextSwitchOverrides value="Switch.System.IO.UseLegacyPathHandling=false;Switch.System.IO.BlockLongPaths=false" />`
 the prefixed path works AND the 288-character path copies.

So: the `.config` is a hard requirement of the exe, not a nicety, and it can go missing.
The code therefore **only** prefixes a path of 240 characters or more. Short paths — which
is every path on almost every machine — are handed to the framework as-is, so losing the
config degrades one deep OneDrive folder into `DID-NOT-ARRIVE.txt` instead of stopping the
tool dead. Tested both ways (test case H).

Corollary worth keeping: `csc` stamps a fresh module GUID each build, so the exe is **not**
byte-reproducible. Record the sha256 of the artefact the test suite actually passed against
and ship that one; do not rebuild and assume.
