**L1814 · A killed scheduled task leaves orphaned children that keep the lock, so the next run fails for a reason unrelated to the fix**

Measured 2026-09-16: Task Scheduler's ExecutionTimeLimit killed the `DSH unified-search
refresh` task at 17:15, and the python grandchildren survived as orphans -- the parent held
the SQLite write lock for 139 more minutes and one child had burned 7,645 CPU-seconds (2.1
hours of a pinned core). The NEXT tick then fails with `database is locked` even after the
code is fixed, which reads exactly like the fix not working.
RULE: after killing or timing out a task, list the process tree and reap the descendants before
judging the next run; and prefer a wrapper that records the exit code so an orphaned child is
visible rather than merely slow. On this machine: `Get-CimInstance Win32_Process` filtered by
the script path, then Stop-Process on each descendant, then confirm the count is 0.
