**L1488 · An alert with no resolver is not an alert: 143 unresolved down to 6 real ones by requiring evidence of contact**

An alert with no resolver is not an alert, it is a log entry nobody reads. Both halves of that
were live on the Waze fleet and together they made the alert list worthless.

WHAT WAS WRONG, MEASURED 2026-09-14
- 143 unresolved alerts, 56 of them staleness. 53 of those 55 "unreachable over the air"
 claims were about phones that had NEVER been sent anything. A device only answers when
 something is sent to it, and only one device was being swept, so those alerts described our
 monitoring, not the phones. Worse, they drowned the ONE real signal - DRN 26, silent since
 2026-09-11 16:00 - in a list of 53 false positives.
- Nothing had EVER resolved an alert: `resolved` is created as 0 and no UPDATE in the module
 set it. So the list could only grow. 87 alerts from 2026-07-12 were still open 65 days
 later, saying "stale - last seen: never" about phones that were fine.

WHAT FIXED IT
1. Staleness now requires evidence of prior contact. Never answered -> no staleness claim, and
 it is counted separately (`no_contact_evidence_exempt`) so "no alert" cannot be misread as
 "checked and fine". On a failed lookup the code keeps alerting on everything, so the
 failure is loud rather than making the fleet look healthy.
2. Alerts are closed when the claim stops being true: exempt, never contacted, or freshly
 seen. Legacy-format duplicates are closed while the current alert is kept. Orphan alerts
 for DRNs no longer in the fleet (12, 22) are closed because the per-device loop can never
 visit them.
Result: 143 unresolved -> **6**, one per device that has replies on record and has gone quiet
(DRN 3, 13, 26, 32, 45, and the LPT test phone). 146 resolved.

RULES
(a) An alert must have a condition that CLEARS it, or it is not an alert. If you cannot say
 what makes it go away, you are writing a log.
(b) Never assert absence of a thing about something you never contacted. "Silent" requires
 having been asked. This is the third time in one session that a count reflected our own
 behaviour rather than the world's: the missing ProfileList history, the frozen
 `last_seen`, and now the staleness alerts.
(c) Report the exemptions as counts. A device with no alert because it was never contacted
 must not be indistinguishable from a device with no alert because it is healthy.
(d) When a fix like this lands, the count should collapse and the survivor set should be
 inspectable one line at a time. If it does not, the fix is wrong - not the data.
