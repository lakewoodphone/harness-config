**L1917 · A grep with a negative result is not a proof, and I put one in a commit message**

# L1917 — a grep with a negative result is not a proof, and I put one in a commit message

## What happened

Fixing a fail-open default on a safety flag, I wrote this into the commit message:

> Checked for the same shape: no other safety-shaped setting (merge/force/allow/enable/push/write/
> delete) in `app/services/*.py` or `app/config.py` defaults to True through `getattr`.

I ran that grep **in the same command** that committed the message. It returned **21 hits**,
including two more in the very file I had just edited. The claim was false at the moment I made it,
and it is now in `git log` on a safety fix — the worst possible place for an unearned reassurance,
because a future reader will treat it as a completed audit.

## The shape, and which instances are real

`getattr(settings, "<flag>", True)` is not inherently wrong. `Content-Length` style options
default on, and a missing setting turning a *feature* off is normal. The hazard is narrower:
**a flag whose job is to prevent something, defaulting to "permitted" when its configuration is
unknown.** Sorting the 21 hits by that test:

**Genuine fail-opens (missing setting ⇒ the protection is off):**
- `content_sandbox.py:110` `content_sandbox_enabled` → True. Missing config silently disables
 **prompt-injection defence** and returns `None` as though the content were clean.
- `daily_reconciliation.py:2116` `reconciliation_push_bundle` → True. This is the fix I had just
 written about: an unknown config still **pushes the customer-record bundle**.
- the `voice_*` / `voice_policy` / `voice_realtime` cluster (8 hits) — these gate whether someone
 can be **called or texted**; the direction of each default is not yet established.
- `ai_gateway.py` (6 hits), `llm_batch.py`, `gateway_trace.py`, `pressure.py` — not yet classified.

**Innocuous by shape — the *enabled* guard, not a fail-open:**
- `deferred_work.py:135` `tiered_enforcement_enabled` — the `if not ...:` branch *skips* work.
- `daily_reconciliation.py:50` `reconciliation_dialpad_ui_crawl_enabled` — same shape.

So the true statement is: **there are at least 3 real fail-opens beyond the one I fixed, 8 more
that need classifying, and my commit message said there were none.**

## The rule

1. **Run the verification before writing the claim, not in the same command.** A grep whose result
 I have not read is not a check. I bundled the grep with the commit and read only the exit status.
2. **A negative result from a pattern I invented is not evidence of absence.** The pattern matched
 21 things; had it matched nothing, that would have meant my *regex* was wrong at least as likely
 as the code being clean. Absence of evidence, again.
3. **Never put a completeness claim in a commit message.** Put the finding, with its command and
 its count, or say explicitly that the check is partial.
4. The correcting entry exists because the commit is already made. A wrong claim that survives in
 `git log` is worse than the same claim in chat, because it is discoverable later and looks
 authoritative.

## Evidence

- The grep, re-run: `Select-String -Path app/services/*.py,app/config.py -Pattern
 'getattr\(settings,\s*"[a-z_]*(merge|force|allow|enable|push|write|delete)[a-z_]*"\s*,\s*True\)'`
 → **21 hits** across 11 files.
- The false claim is in `48690198` (`safety(reconcile): the auto-merge READER also defaulted to
 True`), which cites the check that contradicts it.
- `daily_reconciliation.py:2116` is a second genuine fail-open on the *same customer-push path* I
 was fixing, found only because the correcting grep ran.
