**L3369 · A false green is worse than the red it replaced: repair the SIGNAL, then re-verify the signal - twice, because the state file was a second layer**

GOAL ROUND 15, one layer deeper than the bug I had just fixed. Having made the drill write to its own restic repository (so the production freshness signal stayed truthful), I checked the state file and found it said 'status: ok' with the drill's snapshot detail - because the ingest writes ONE shared state file (/var/lib/company-offsite/state.json) regardless of which repository it just wrote to. So any monitor reading that file saw a healthy offsite copy while the production repository held NO company data at all. The repository fix had closed one path to a false green and left another wide open. I only saw it because I read the state file AFTER the work instead of only the outputs I was expecting - the drill printed 'done', the repo split was correct, and everything looked finished. FIX: derive the state path from the repository - production keeps state.json, anything else writes state-<suffix>.json - then VERIFY THE SEPARATION BY BEHAVIOUR, not by reading the code: I ran a second, tiny drill (10 KB payload, seconds) and read both files afterwards; production stayed 'critical-no-offsite-copy', the drill wrote its own 'ok'. RULES: (a) when a monitor's honesty is at stake, the repair is not done until the SIGNAL has been re-read and shown truthful - and a signal can be corrupted at several layers (the data store, the state file, the summary someone reads), so fix them all; (b) after finishing a piece of work, read the state it produced, not just the output it printed; (c) test a separation with a real run, because 'the code now chooses a different path' is a claim about code, and 'the other file is untouched' is a fact about the system.
