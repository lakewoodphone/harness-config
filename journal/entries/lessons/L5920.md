**L5920 · os.replace(tmp,target) strips the execute bit - and existence is not executability**

`os.replace(tmp, target)` hands the target the TEMP file's mode. A temp file written with a bare
`open(path, "w")` is 0644 under a normal umask, so this one shape silently strips the execute bit
off an executable script — and the only symptom is that an invocation BY PATH dies with 126
"Permission denied", which nothing in a cron loop ever does.

MEASURED 2026-10-16 on secratary-cloud. `heartbeat-is-not-a-death.py` patched
`/root/bin/autonomy-status.sh` at 2026-10-14T14:26:57Z:

 -rw-r--r-- 1 root root 18805 Oct 14 14:26 autonomy-status.sh <- live file, bit gone
 -rwxr-xr-x 1 root root 18805 Oct 14 14:26 autonomy-status.sh.bak-heartbeat-alive-...Z

The backup kept 0755 and the live file lost it, because the script does `shutil.copy2(TARGET,
backup)` (metadata preserved) BEFORE `os.replace(tmp, TARGET)` (mode taken from tmp). Timestamps
match to the second, which is what identified the culprit. For 35 hours the ONE read-only command
that answers "what is the system doing" — the first command the secretary-wake skill tells every
session to run, at the only path `/home/zabz/bin` (a symlink to `/root/bin`) — exited 126.

WHAT TO DO. After writing a temp file that will replace an executable, copy the mode across before
the replace and then VERIFY it:

 mode = os.stat(TARGET).st_mode & 0o7777
 ... write tmp ...
 os.chmod(tmp, mode)
 os.replace(tmp, TARGET)
 if os.stat(TARGET).st_mode & 0o7777 != mode: refuse()

PROVEN by planting the condition, both copies started 755:
 old script -> 644 (stripped) new script -> 755 (preserved) identical output, exit 0.
The fix is now in `/root/bin/heartbeat-is-not-a-death.py`.

TWO THINGS NOT TO OVERCLAIM, because I checked them and they were false:
 * The sensor did NOT go blind. `sources/drift-check.py` invokes it as `["bash", script]`, so it
 ran throughout and reported `quiet`, exit 0. An exec bit is not needed to be read by bash.
 * The estate has 11 files using `os.replace`; 8 have no `chmod` anywhere, but only this one
 targets an executable. The other seven replace JSON data, where 0644 is correct. A sweep that
 reported "8 files have this bug" would have been wrong.

AND THE GUARD THAT SHOULD HAVE CAUGHT IT: `restore-wake-loop.sh` — the script whose whole job is to
restore the wake loop — tests `[ -e "$BIN/$f" ]` and reports `have autonomy-status.sh`. Existence is
not executability. If a check matters, test the property you actually need, not a proxy for it.
