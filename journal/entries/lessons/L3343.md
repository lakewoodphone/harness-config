## Lesson: a session log read that returns only the first zstd frame is not a log read

`~/.dsh/sessions/**/session.v*.jsonl.zstd` are CONCATENATED zstd frames — one frame per flush. Measured
2026-10-05 on a 227,526-byte ZABZ-YOGA session file: Node's `zlib.zstdDecompressSync` returned **198 bytes**,
and `createZstdDecompress()` streamed 297 bytes then died with `ZSTD_error_prefix_unknown`. Both stop at the
first frame boundary. The real content of that file is **868,581 bytes**.

Consequence: any scan built on those two calls reports "0 matches" for text that is definitely there. I nearly
wrote "no session log contains this error" from exactly that, on a machine whose ledger holds 86 occurrences —
a confident wrong answer of the kind that has cost this fleet the most. `/usr/bin/... zstdcat` and Python
`zstandard.ZstdDecompressor().stream_reader()` walk every frame; use them.

The same shape of mistake is available with `zlib.createGunzip` on multi-member gzip, and with any "read the
first record and assume the rest" parser. **Rule: when a scan returns nothing, prove the reader can see
something before believing the emptiness.** A refusal is a correct answer; an empty result from a broken
reader is not.

Evidence: `_dsh-diag/zstdscan.py` (works, 2494 files, 86 hits), `_dsh-diag/scan2.mjs` (silently 0 hits on the
same tree), `_dsh-diag/session-census.mjs` (reported 2494 files, all "empty", all wrong).
