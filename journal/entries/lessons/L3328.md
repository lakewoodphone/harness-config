**L3328 · New-Item -Force on an existing registry key deletes its values - and when a value you set keeps disappearing, suspect your own tooling first**

`New-Item -Path <existing registry key> -Force` DELETES EVERY VALUE IN THAT KEY. Never use it as a "make sure the key exists" line.

MEASURED 2026-10-05 on ZABZ-TECH, twice, directly:
 before: AVC444ModePreferred=0 ZabzMarker3=99
 New-Item -Path 'HKLM:\SOFTWARE\Policies\Microsoft\Windows NT\Terminal Services' -Force | Out-Null
 after: BOTH GONE
The values were not "deleted by something", the key was not being refreshed by a policy, and there was no mystery process: the guard script itself wiped the key on every run and re-added the four values it knew about. WRITE IT AS `if (-not (Test-Path $key)) { New-Item -Path $key | Out-Null }` - create only when absent, never with -Force.

THE COST OF NOT KNOWING THIS: an hour spent hunting a phantom deleter (policy refresh? MDM? another agent's session? the local Registry.pol?) while the answer was in the second line of the script doing the reporting. And real damage: the key was bare for a window on EVERY run, so any RDP session created in that window received none of the policies the guard existed to enforce. A guard that damages the thing it guards is worse than no guard, because it also produces confident evidence that something else is at fault.

THE GENERAL RULES, which outlive the registry:
1. When a value you set keeps disappearing, suspect your own tooling FIRST. The tells were there: the same four names "missing" on every run at exactly the tool's own cadence, while an untouchable marker value survived for a while.
2. Prove a repair with a value the tool does not know about. Plant a marker, run the tool twice, and watch the marker survive. That is the check that distinguishes "it is fixed" from "it looks fixed".
3. A watchdog must be able to say "everything is in place" and mean it. If it reports a repair on every single run, either the world is broken or the watchdog is.
4. Two of tonight's three regressions were in the guards themselves (an auto-reconnect wrapper that relaunched on a cancelled dialog, eight times in ninety seconds, and this enforcer that wiped the key it enforced), not in the systems they protected.
