**L10881 · Phone engine 0.2.1 DONE: the seven failures were ExecStartPre, not the engine - repair-phone-engine.sh --check needs a pnpm-layout canonical dsh-scope and an npm-flat profile makes it exit 2, so the unit cycled in activating and never wrote a log; a foreground run skips that gate, which is why my proof was misleading**

DONE 2026-10-20 12:49Z (box time). The owner's phone engine is on **0.2.1-rc.2**, and it stays up.

MEASURED, twice: unit `phone-engine.service` active with **restarts 0**; engine `--version` = 0.2.1-rc.2;
`http://127.0.0.1:3089/` = **401** (up, auth required); phone gate `3086` = **200**, `/mesh/health` = 200,
`/dsh-phone-mobile.css` = 200 (the phone layer is being served); compose on the live home = **421 rows**. A fresh
`systemctl restart` came back to 401/200 in **5 seconds**, so this is a stable state, not a lucky boot. Previous
tree kept at `/opt/dsh-phone.prev-0.2.0-rc.2-20261020T124925Z`.

THE CAUSE OF SEVEN FAILED ATTEMPTS, and it was never the engine: the unit runs
`ExecStartPre=/usr/local/bin/repair-phone-engine.sh --check`. That gate requires the engine's `dsh-scope` and
`profiles/web/node_modules/.pnpm/@deepseek-ai+dsh-scope@*/node_modules/@deepseek-ai/dsh-scope` to resolve to the SAME
inode, and **exits 2 when that canonical path does not exist**. Every attempt installed the profile with `npm`, which
produces a flat tree with **no `.pnpm` directory at all** — so the gate found nothing, exited 2, systemd logged
`Control process exited, code=exited, status=2/INVALIDARGUMENT`, and the unit cycled in "activating" forever. The
engine never started, which is why no startup log was ever written and why every diagnostic came back empty.

AND THE REASON I COULD NOT SEE IT: a **foreground run skips ExecStartPre**. That is exactly what I used as my
"proof" that the engine worked — it booted and served on 3092/3093 — while the unit, which runs the gate first,
could never start. A control that does not include the gate is not a control for a unit that has one.

THE FIX, and it is honest rather than a bypass: after `npm install` at 0.2.1, create the canonical path the gate
looks for as a **symlink to the profile's own installed copy**
(`.pnpm/@deepseek-ai+dsh-scope@0.2.1-rc.2/node_modules/@deepseek-ai/dsh-scope -> ../../../../../@deepseek-ai/dsh-scope`).
Both paths then resolve to one file, which is the property the gate actually asserts (two copies of dsh-scope is
what produced "every prompt rejected as session/agent-busy" on 2026-10-12). `repair --check` then exits 0, the
repair unified the engine's copy, and the unit started on the first try.

TWO MISTAKES OF MINE IN THIS WINDOW, both now rules:
 * a rollback restored the tree and package.json but NOT the profile patch I had rewritten, so the phone served
 **404 where it had served 401** — up but wrong. A switch script must back up EVERY file it modifies.
 * an early exit path in one script said "REFUSED" and returned without restoring, leaving the unit stopped and an
 empty profile. Every refusal path must call the same restore function as a failure path.

RECORDED FOR THE NEXT HOST: on this estate a DSH unit may have an `ExecStartPre` that gates module identity. Before
"proving" an upgrade in a foreground run, read the unit's `ExecStartPre` and run it — otherwise the proof and the
unit are testing different things.
