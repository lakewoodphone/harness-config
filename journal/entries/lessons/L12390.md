**L12390 · A ticket has an id AND a number, and to_jsonb returns null for a column that does not exist - I wrongly corrected production over it**

## The trap: a ticket has two numbers, and `to_jsonb` returns `null` for a column that does not exist

Measured 2026-10-27 on WO26102712779 (Adam Notarfrancesco, HP ProBook 450 G2 data recovery).

Production note 4667 said "ticket 12779". I queried `select id from tickets where id in (2846,12779)` and got **one row** (2846), and separately read `to_jsonb(tickets)->>'ticketNumber'`, got `null`, and concluded the note was wrong: "the ticket id is 2846, no ticket 12779 exists, 12779 is just the sequence in the WO number." I then wrote that conclusion into production as a **correction note**, and wrote it into the case file and the diagnostic log.

**It was wrong.** `tickets` carries both:

```
id 2845 number 12778 createdAt 2026-10-26T17:15:15 (Frankel, WO26102612778)
id 2846 number 12779 createdAt 2026-10-27T15:16:53 (this order, WO26102712779)
```

`orders.ticketId` holds the **id** (2846). The work-order number embeds the **number** (12779). The staff-facing ticket number was correct all along, and note 4675 had to retract 4673 and half of 4674.

**Two mechanical causes, both reusable lessons:**

1. **`to_jsonb(row)->>'col'` returns `null` for a column that does not exist.** I read that `null` as "no ticket number recorded" when the column is simply named `number`. A `null` from `to_jsonb` is not evidence of absence — it is indistinguishable from a missing column. `select jsonb_object_keys(to_jsonb(tickets))` lists the real columns in one call and would have caught it. Do that before concluding anything from a `null` you got that way.
2. **The field I filtered on is not the field the record means.** `tickets.id` is a surrogate FK target. `tickets.number` is the identity a human uses and that the WO number encodes. Rule 8 of the surface (measurement rule): print the raw value next to the predicate and ask what WRITES the field. `lpt ticket` prints `ticketId`, so the id looks canonical — it is not the number.

**The rule, for the shop's record:** the ticket number is `tickets.number`, `orders.ticketId` is the FK to `tickets.id`, and the WO number is `WO + YYMMDD + tickets.number`. Both are true at once; neither substitutes for the other. Verify with:

```sql
select o.id, to_jsonb(o)->>'orderNumber' as wo, to_jsonb(o)->>'ticketId' as fk,
 to_jsonb(t)->>'number' as ticket_number
from orders o join tickets t on t.id = o."ticketId" where o.id = 3245;
```

## Related trap, same session: a production note can cite files that were never written

Note 4667 named `docs/customer-operations/cases/hp-probook-450-g2-notarfrancesco-2017886740-2026-10-27.md` and `hardware-diagnostics/hp-probook-450-g2-notarfrancesco-diagnostic-2026-10-27.md`. **Neither existed.** `lptcase find` matched 0 of 315 cases; `ps_search what=all fresh=true` over the whole estate returned 0 hits; a repo-wide glob for the name and the drive serial found nothing, and no commit in any ref mentioned them. The intake session wrote the paths into the note and never wrote the files.

**So: a path inside a production note is a claim, not a fact.** Check it the same way you check a number — `lptcase find`, then `ps_search what=files/docs fresh=true`. Cheapest tell: `lptcase find "<name>"` returning NO CONFIDENT MATCH for a customer who has a note in production means the case file is missing, not that the customer is new.

## Third trap: pushing from a shared working tree

`git pull --no-rebase origin main` aborted with **rc=2** — *"Your local changes to the following files would be overwritten by merge: docs/customer-operations/cases/qin-phone-water-damage-frankel-…md"* — because a **different session** had uncommitted edits to a file upstream had also changed. The merge aborted cleanly and nothing was lost.

**Do not stash or commit another session's uncommitted work to get your own push through.** The safe move that loses nothing: commit only your own paths, then `git push origin HEAD:refs/heads/case/<slug>-<date>` so the work is durable and reviewable on the remote, and report the main-push blocker. Also: `git push -u` sets upstream tracking on the branch that happens to be checked out — if that is another session's branch, restore it (`git branch --set-upstream-to=origin/<branch>`) or you have silently re-pointed their branch.
