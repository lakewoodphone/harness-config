**L1081 · A build's own count is not coverage: the auditor must import the indexer's rules**

## A build's own count is not coverage — the indexer and the auditor must share one rule

`commsindex.py index` reported "174,622 communications" and that number was believed for six hours.
Comparing the built index against its source on 2026-09-14 produced three different losses, none of
which any count would have shown:

* `dialpad_ui_history_row.row_key` is **not unique** (10,703 rows, 4,746 distinct keys, 145 of them
 with different text). The index keyed on it, so `INSERT OR REPLACE` silently kept one row per key:
 5,716 re-captures collapsed — correct — **and 215 rows of text that existed nowhere else, dropped**.
* `dialpad_sms_cache` holds 2,744 byte-identical duplicate rows (webhook path and thread-crawler
 path both store the same message id). Collapsing is right; doing it *silently* means deliberate
 de-duplication and data loss look identical in the output.
* 1,192 voicemails have a recording and no transcript, and the extractor skipped them by design, so
 "who left a voicemail in July" had no answer.

The fix that made this class of bug stop recurring: **the auditor imports the indexer's extractors and
its de-duplication key** instead of re-implementing them. `comms-coverage.py` replays what
`commsindex.py` would write and compares it with what the index holds — so a rule change cannot land
in one and not the other, and any row the index chose to collapse is reported as a collapse, not as a
loss. Its exit code is non-zero when they disagree, which is what lets cron gate on it.

Rule for anything that claims completeness: **never verify a build against itself.** Replay the input
through the same rules and diff. And make the deliberate collapses *visible numbers*.

## Two FTS5 traps that silently corrupt a rebuilt index

* `DELETE FROM <fts5 table>` does **not** remove its shadow rows. Re-inserting under a reused rowid
 appended a second entry: the index held 175,885 FTS rows against 166,192 base rows, with **9,693
 pointing at rowids that no longer existed**. `DROP TABLE` + recreate, or de-duplicate before insert;
 the second fix is better, because the three tables then agree *by construction*.
* `INSERT OR REPLACE` on a row with a unique index gives the replacement a **new rowid**. So any side
 table keyed on rowid drifts from the base table on every rebuild. De-duplicating in Python before
 the insert loop (bounded per source table, so memory is fine) removes the whole class.

Rowid drift is invisible in counts. It shows up only as duplicate or stale *search results*, so it is
found by reading results, not by reading schema.
