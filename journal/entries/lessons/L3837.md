**L3686 · Two work orders for one job: the order that owns the intake case is canonical, and repointing a sync record moves a regression test**

## The rule

When one job is carried by two work orders, the canonical one is **the order that owns the intake
case** — not the newer one, and not the one with the richer note. Everything else follows: the
duplicate is the row created by a sync/robot tool, and its status should be **CANCELLED** with a
cross-referencing note, never UNFIXABLE, which reads as a repair outcome and hides the duplicate.

Measured 2026-10-12 on the Lichtenstein SD card (customer id 1299, +18482878029):

- `WO2608170001` (id 2707, ticket 2377, intake 2026-08-17) — the intake case
 `9202fe6d-0cef-40fc-b323-6b5fb6c9cc0d` is `promoted->2707` onto it. **Canonical.**
- `WO26091512708` (id 2873, ticket 2543, created 2026-09-15 by `cli_lpt_sync_to_production`) — the
 duplicate. Its own issue text is the portal summary "Working on it; will be in touch with status.",
 which is what a robot writes.
- The **richer** note was on the duplicate (2026-10-08 RESOLUTION, the only one quoting the decline),
 which is exactly why "keep the better note" is the wrong tiebreak. Notes survive cancellation, so
 cancelling the richer row loses nothing.

## Repointing a record breaks a regression test — that is a signal, not a surprise

`tests/test_lpt_sync_precreate_guard.py::INCIDENT_RECORDS` maps each of the eight records from the
2026-09-15 duplicate-order incident to the order the guard *names* for it. Giving
`sd-card-lichtenstein-2026-08-24.json` the production link it never had
(`workflow.orderNumber`/`orderId` + `references.productionOrder` -> WO2608170001) changed the guard's
answer from `kind=overlap` naming the duplicate WO26091512708 to `kind=linked_order` naming
WO2608170001. The expectation had to move with it.

**So: before repointing any sync record, grep the test directory for its filename.** A record's link
is read by a test as well as by the push tool. Verified after the change:
`LPT_SYNC_DB_TESTS=1 ./.venv/bin/python3 -m pytest tests/test_lpt_sync_precreate_guard.py -q`
-> **64 passed**.

## What the six homes actually read, confirmed again 2026-10-12

`lpt-sync-to-production --dry-run-all` is the authoritative per-record verdict. After the repair all
three Lichtenstein records SKIP for the same reason and name the same order: `record already
references live production order WO2608170001 (ID 2707, status UNFIXABLE, created 2026-08-17) via
workflow.orderId`. Before, `sd-card-lichtenstein-2026-08-24.json` had **no** production link at all —
`references.workOrderId` held `13398`, a secretary task id, which `_iter_production_order_refs`
ignores by design (`test_secretary_side_ids_are_not_treated_as_production_orders`). A record can look
linked to a human and be invisible to every verifier.

## The money rule, applied to this case

One card, no lab work ordered, the lab route refused: quoted 0, collected 0, on both orders. The
failed standard attempt is not chargeable. Do not invoice a job because a row is priced.
