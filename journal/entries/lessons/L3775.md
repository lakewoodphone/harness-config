## L2xxx — A stale git clone is the same failure mode as reading the wrong database

**Measured 2026-10-07.** Sweeping the 300DDR lab cases, I read the Golembick case file from the local `lpt-hub`
clone and reported **0 collected, `payment_state: uncollected`** — and wrote that into a new board file. Origin
already carried the correction: **160 paid on 2026-09-08 against an agreed 660.** The local clone was behind, so
the file I read was *plausible, self-consistent, and three days old*, and it produced a confident wrong number
about money the shop had already taken. Caught only because the push was rejected and the rebase surfaced the
conflict. The commit that fixed it is `00cc919a4`.

**The rule.** Any claim about a case's *current money state* or *open/closed status* must come from a tree that
has been fetched in the same session — `git fetch` before reading, or read the file through the case index after
a fetch. A clone's age is not visible in its contents; the file looks exactly as authoritative stale as fresh.

**Why this is the same as P3.** P3 is "reading the wrong data and believing it". A stale working copy is a wrong
data source that *looks* like the right one, which is worse than an obviously foreign database: there is no
provenance signal at all. The mitigation is the same as everywhere else: **state the source and its age before
believing a number**, and for money, never state a figure without having fetched.

**Cheap check to run before any financial assertion about a case:** `git -C <repo> fetch -q && git -C <repo>
status -sb` — `behind N` is the answer, and it costs one call.
