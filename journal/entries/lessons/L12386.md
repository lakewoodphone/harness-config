**L12386 · CORRECTION: shell_command uses a real shell UNLESS the command contains Jinja - so the prune was never broken, it just never ran**

**CORRECTION · 2026-10-26 18:55 UTC · I got the `shell_command` rule half wrong, and the half I got wrong was the half I generalised from**

Corrects `H12471` (the Phoenix alarm handoff) and `L12385` (the shell_command lesson). Both entries stay as
written; this is the correction that cites them.

**What I claimed.** "`shell_command` has no shell" — full stop — and therefore two commands were broken by the
same defect class: `phoenix_verify_evidence_files` (`FileNotFoundError: 'for'`) and
`phoenix_prune_intrusion_evidence` (retention never ran, 48 files, oldest 40 days).

**What is true.** Home Assistant 2025.10.3, `components/shell_command/__init__.py`, read inside the core
container (`docker exec homeassistant sed -n '45,95p' ...`) — it branches:

```python
prog, args = cmd.split(" ", 1)
args_compiled = template.Template(str(args), hass)
rendered_args = args_compiled.async_render(variables=service.data, parse_result=False)
if rendered_args == args:
 create_process = asyncio.create_subprocess_shell(cmd, ...) # NO template -> a real shell
else:
 shlexed_cmd = [prog, *shlex.split(rendered_args)]
 create_process = asyncio.create_subprocess_exec(*shlexed_cmd, ...) # ANY Jinja -> no shell
```

So the rule is: **a shell_command containing any Jinja runs with no shell; one containing none runs under a
real shell.** The verify command contained `{{ files }}` and broke. The prune command contains no Jinja, so it
ran under `/bin/sh` and would have worked — proved empirically on the host with four synthetic files
(2026-08-01, 2026-09-16, 2026-10-01, 2026-10-26): the ORIGINAL prune command under `sh -c` kept only
2026-10-26. `xargs -r` also exists in that BusyBox (`xargs -r true` -> exit 0), so that part was never broken
either.

**Why retention really did not run:** the prune is step 7 of `phoenix_intrusion_evidence_and_page`, and the
script aborted at step 5 on the verify defect. One defect, two symptoms. Not two defects.

**How the wrong claim happened, because this is the reusable part.** I saw two things not happening, both
inside the same script, and inferred one shared cause. That is correlation wearing a mechanism's clothes. The
adversarial child reviewing my fix pushed on exactly this ("does the prune even take the same branch?"), and
the source settled it in one read. The measurement rule exists for this: print the raw value next to the
predicate. I never read the branch condition; I read a list of symptoms.

**What survives.** The verify fix is right and proven (`PHOENIX_EVIDENCE_OK <path>`, rc 0, via
`POST /api/services/shell_command/phoenix_verify_evidence_files?return_response`). Retention was exercised for
the first time and worked (42 files, 0 older than 14 days). Sweep of the entire config: **9 `shell_command`
definitions, exactly 1 templated** — the broken one. `bash -c` is kept on both commands, not as a repair of a
broken prune but because the execution mode depends on an invisible property of the string, one edit away from
flipping.

**The rule I will carry:** when two steps fail, read the code that decides how each one runs before naming a
shared cause. "Same class" is a claim about a mechanism, and it needs a mechanism's evidence.
