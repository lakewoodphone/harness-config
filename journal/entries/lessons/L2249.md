**L2249 · A boot-scoped question needs a boot-scoped query - a watcher reported a healthy boot as broken**

**A boot-scoped question needs a boot-scoped query. Reading "the last N events" and then judging *this* boot is how a healthy system gets reported broken.**

Measured on ZABZ-TECH, 2026-09-20. The boot watcher `C:\Users\ezabz\Code\_diag\boot-watch.ps1` was written to answer exactly one question at each boot: *did Windows Hello survive this boot?* It answered by taking the last 40 `Microsoft-Windows-HelloForBusiness/Operational` events and flagging failure if any `7002`/`3611` was among them.

On the boot at **15:38:49** the machine was genuinely healthy — the log recorded `[8002] Successfully loaded an existing hardware Windows Hello container. ID: {51750de2-…} State: Okay` with `PIN protector = true`, and the VSM key blob was present and uncorrupt (`BlobSize=723`, `UefiBlobIsCorrupt=0`), and the pre-bootmgr window was 25 s. The watcher printed:

```
>>> RESULT: HELLO FAILING THIS BOOT (PIN will need re-set)
```

because the unfiltered window still contained the container deletion at **15:30:35** — *eight minutes before this machine had even rebooted*. The deletion that had happened to the previous boot was being charged to the next one.

This is not a cosmetic bug. It is the difference between "the fix I just applied worked" and "the fix failed", and it was wrong in the direction that costs the most: it manufactures a failure. The first watcher version also counted a stale orphan container (`{16596639-…}`, on disk since 2026-02-09, fails `0xD000A002` on *every* boot and belongs to no user) as the user's Hello failing — a second independent way to produce the same false negative.

THE RULE: when the thing you are measuring is "what happened *during this boot*", every event query must be filtered `TimeCreated >= LastBootUpTime` (and any known-permanent-failure artefact must be excluded by name). "The last N events" is a *recency* filter, not a *boot* filter, and the two only coincide when the machine has been up long enough that nothing older is in range — i.e. exactly when you least need the watcher.

Corollary, and the reason this was worth writing down: a watcher's verdict is itself a claim. The first session on this machine was steered by the versions of these lines, and re-read them as evidence the firmware fix had failed. Fix the instrument before believing its reading.

FIXED SAME DAY: both bugs corrected in `boot-watch.ps1` (backup `boot-watch.ps1.bak-20260920`), verdict now driven by an `8002 … State: Okay` load of a non-orphan container plus the absence of `3611`/`7002` **in this boot's window**, emitting one line `>>> RESULT: HELLO <verdict> | VSM key <verdict>`. Self-tested against the live log without rebooting: `HEALTHY`. Documented in `harness-config/docs/mesh/117-zabz-tech-hello-and-boot.md`.
