**L3326 · L: A frozen sync cursor reports ok forever, and a guard keyed on the wrong column hides real rows**

DIAGNOSED AND FIXED 2026-10-05 on secratary, in
personal-secretary-mvp/app/services/dialpad_sms_backfill.py. Two independent faults,
both of which report success.

FAULT 1 - THE CURSOR COULD NEVER ADVANCE
 if secretary_db_url and stats["stored"] > 0: # advance only if rows stored
 last_created = MAX(created_at) FROM dialpad_sms_cache # read from OUR cache
 An empty pass left the cursor untouched, so every later incremental pass asked
 production for rows newer than a timestamp already past the newest row it had.
 Measured: backfill_cursor pinned at 2026-09-20T20:09:32Z for 15 days, cron
 logging `read: 0 ... ok` every 30 minutes, no error.
 Fixed: take the cursor from production''s own MAX("createdAt"); advance even when
 nothing was stored; never move it backwards; normalise both sides to UTC before
 comparing (production returns a naive datetime, the stored cursor is aware, and
 the comparison raises TypeError, not ValueError).

FAULT 2 - THE GUARD EXCLUDED EVERYTHING REAL
 AND coalesce("metadata"->>'source','') <> 'dialpad_sync'
 Every row the website writes carries source='dialpad_sync'. Measured across all
 time: 110,819 SMS rows WITH metadata->>'external_ref' (ours, minted as
 'dialpad:sms:<id>' by our own export) and 7,091 WITHOUT (genuine webhook rows).
 The guard threw away genuine rows too. It survives today only because the
 website''s webhook has written ZERO rows since 2026-09-20.
 Fixed: skip a row only when its external_ref is one we minted, tested with
 strpos() - a literal '%' in a psycopg2 query is parameter syntax and corrupts
 argument binding, which surfaced as IndexError: list index out of range.

THE TRAP I FELL INTO WHILE DIAGNOSING
I saw "828 rows newer than the cursor" and reported them as 828 missing customer
messages. They were copies of OUR OWN data exported the other way. The evidence was
in the row metadata all along (external_ref of our own minting). Count rows by where
they CAME FROM before calling them missing.

HOW TO SPOT THIS CLASS OF BUG
A sync that reports ok and does nothing is worse than one that fails. Check the
cursor''s updated_at, not just the job''s exit status; if updated_at is old while the
job runs on schedule, the cursor is frozen. And when a guard excludes rows, measure
what it excludes on both sides before trusting it.
