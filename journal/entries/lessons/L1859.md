## The Screen Time procedure WAS written down — in a tool's --help string, marked "do not use for production"

Found 2026-09-17 by mining the MDM host: `/opt/waze-mdm/operator-tools/scripts/waze_kiosk_mode.py:555-571` carries the whole method as help text:

> *"Settings → Screen Time → 'This is My Child's Device' → Communication Limits → Contacts Only (leave contacts list empty) → set a Screen Time passcode … blocks ALL cellular voice calls in both directions"*

with the standing prefix **"Lab-only flag … Do not use for production Waze phones."** It was used on production DRN 48 and 54 on 2026-09-17. That is what the owner meant by "you've done this before": the method is ours, documented in the tool, and it is the only place in the tree where a claim that communication limits block calls in both directions is written down.

Four things this settles, each with the evidence behind it:

1. **The MDM half is exactly two booleans, and that is all it can ever be.** Comparing every July callblock file with today's DRN 48/54 variant: the entire delta is `allowEnablingRestrictions false→true` and `allowScreenTime false→true`. Nothing else. Apple's own schema (`com.apple.applicationaccess.yaml`, fetched 2026-09-17) contains `allowEnablingRestrictions` — titled "Allow Configuring Restrictions or ScreenTime" — and does **not** contain `allowScreenTime` anywhere. Within a minute of *me* fetching the docs audit, a second agent fetched the same file from the source repository: same conclusion.
2. **iOS never once complained about those keys.** Across the whole send history there is **no `MCPayloadErrorDomain` record at all** — the keys are accepted and inert, not rejected. Which means "it installed fine" was never evidence that a restriction took effect.
3. **The July A/B that was supposed to settle call blocking was null by construction.** `waze-callblock-fixed` and `waze-callblock-noblock` have **identical** ordered key/value pairs of the `com.apple.applicationaccess` payload (192 pairs each, no difference) — the treatment and the control are the same profile. Their only deltas are a description string, a UUID and notification ordering. Whatever that experiment concluded, it could not have concluded anything about calls. Four months of belief rests on a test that compared a file with itself.
4. **The send log is deleted weekly.** `/etc/cron.weekly/cleanup-waze-commands` runs `DELETE FROM commands WHERE created_at < NOW() - INTERVAL '30 days';`, which is why `commands`/`command_results` reach back only to 2026-08-14 and why nobody can now say whether a July profile install succeeded. Any future "what did we actually send and what did the device say" question has a 30-day horizon unless that job changes.

Incidental, same host: `/etc/cron.hourly/check-waze-health` probes the container `waze-mdm-mdm-gateway-1`, which was deleted on 2026-07-22, so it reports UNHEALTHY hourly — a standing false alarm nobody reads. A plaintext IKEv2 PSK sits in the nanomdm volume (`callblockvpn` profile) and must be treated as disclosed. And the fleet-api log carries `billing-endpoint persist failed: syntax error at or near "AUTOINCREMENT"` — SQLite DDL being run against Postgres.
