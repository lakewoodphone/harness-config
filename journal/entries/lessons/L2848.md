**L2848 · Reaching the authority: MagicDNS fails intermittently from ZABZ-TECH; the tailnet IP and the LAN IP both work, and the default ssh key is refused**

MEASURED 2026-09-28, this machine (ZABZ-TECH, the i9 desktop at the office), between 18:15Z and 18:35Z.

WHAT HAPPENED. `ssh secratary-ts` - the alias the whole mesh and the wake dispatcher use - failed with
"connect to host secratary.tail93e6e6.ts.net port 22: Connection timed out" FOUR times in 20 minutes.
It worked at 18:17Z, 18:19Z and 18:20Z in between. `ssh secratary-ts` is MagicDNS; `tailscale status`
stayed healthy throughout; the authority itself reported its own tailscaled "active" and showed both
peers "active; relay nyc". So the failure was NAME RESOLUTION/reachability of the tailnet name from
this host, not a dead peer.

THE TELL, AND THE FIX. `Permission denied (publickey)` at 192.168.50.77 is a SUCCESSFUL TCP
connection - a refused key, not a dead host. The office LAN answers:
 `ssh -o IdentitiesOnly=yes -i ~/.ssh/zabz-tech-ed25519 zabz@192.168.50.77` -> `hostname` = secratary.
`ha-mesh-key` also works; the DEFAULT ~/.ssh/id_ed25519 is REFUSED by the authority. The stable
tailnet IP 100.84.72.88 also works directly. So the durable facts are:
 * authority tailnet IP 100.84.72.88 (never needs DNS)
 * authority office LAN 192.168.50.77 (works from the office)
 * authority accepts ~/.ssh/zabz-tech-ed25519 and ~/.ssh/ha-mesh-key
 * authority REFUSES ~/.ssh/id_ed25519
Added to this machine's ~/.ssh/config (backup: config.bak-pre-autonomy-20260928):
 Host secratary-ip -> 100.84.72.88 + zabz-tech-ed25519 + IdentitiesOnly yes
 Host secratary-lan -> 192.168.50.77 + zabz-tech-ed25519 + IdentitiesOnly yes
Both verified: `ssh secratary-ip` and `ssh secratary-lan` both return hostname secratary.

WHY THIS MATTERS FOR THE AUTONOMY BUILD, and is a lesson not a footnote.
1. The dispatcher's entire path to the desktop is `ssh`. A flaky name takes the whole activation
 system down with no error that looks like a network error - `subagent` reported it as
 `broker-unreachable` and three separate audits failed before they started.
2. Three `subagent` dispatches (the mesh provider) failed at 18:18Z with
 "remote-ssh: broker-unreachable ... ssh exited 255" WHILE the broker was up on 127.0.0.1:3091 and
 answering (GET -> {"error":"POST /place, not GET /place"}). The broker's own ssh hop was the
 failure. Retried 2 minutes later, all three succeeded. Nothing changed but time.
3. Therefore: in an autonomous system, "a call failed" must be classified. Transient unreachability
 must never be recorded as a work failure - the wake system already conflates these (7 releases
 recorded `failed` that really ran and burned tokens; release 49 recorded `failed` after being
 killed at the 2100 s bound). Retry-with-backoff on the TRANSPORT, and reserve "failed" for the
 WORK.

ACTION FOR THE AUTONOMY DRIVER: use a node-address list per target (name, tailnet IP, LAN IP) and
try them in order, so no single resolution path can halt activation.
