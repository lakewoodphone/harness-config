**L2912 · FastAPI's lifespan rebuilds app.state.limiter, so a test fixture cannot reset it**

Measured on kosher-filter-ai (kf0928/server-tests-green, 2026-09-28), server/.venv python, one process, two 'with TestClient(app) as client:' contexts, 24 admin writes in each.

app/main.py:313 sets fastapi_app.state.limiter = TokenBucketLimiter() INSIDE the lifespan, and TestClient enters the lifespan on __enter__. So a per-test autouse fixture that installs a fresh limiter (or clears app.state.limiter._buckets) BEFORE the client is opened is discarded when the context manager starts, and the fixture becomes a no-op that looks like a fix.

Probe output: context 1 limiter id 2590048750288, buckets {'total': 1}; context 2 limiter id 2590047120048, 'same object as limiter1: False', buckets seen before any call {'total': 0}. Every context already starts with a brand-new empty limiter.

What to do instead when a test module exhausts a bucket: find the setting that actually binds the route (measure it - instrument TokenBucketLimiter.check_many and read rate=/burst=) and raise THAT for the module with monkeypatch.setattr, then give any rate-limit test its own explicit low budget. Resetting state is the right shape when the expensive objects survive between tests, which is measured per object, never assumed.
