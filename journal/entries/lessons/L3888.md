**L3888 · A Stripe refund is invisible to the shop's own books: the refunds table has never held a row**

Measured 2026-10-20 on the operational store (dsn d5oq83veii4rlb, `ssh secratary-cloud`), while analysing a
229.24 phone-rental deposit the owner partially refunded the same day.

**The finding.** `select count(*) from refunds` returns **0**. Not zero today - zero ever. The table exists
and is fully shaped for the job:

```
refunds(id, uuid, "paymentTransactionId", amount, reason, status, "stripeRefundId",
 "processedBy", "createdAt", "updatedAt", currency, description,
 "failureReason", metadata, "processedAt")
```

Nothing writes it. And `payment_transactions` carries one type only, across all 448 rows: `PAYMENT`
(74,223.02 in total). There is no `REFUND` row of any kind.

**So a refund is invisible to the shop's own books.** The Stripe screen showed payment
pi_3USfr1LnlgYj1gmT1xR9GN22 for 229.24 at 12:25 PM and a 149.27 refund at 1:22 PM. Production row 3409 is
still `SUCCEEDED 229.24`, unchanged, with no refund anywhere. Anyone totalling takings from
`payment_transactions` overstates them by every refund ever given - which on this one transaction is 149.27
of a 229.24 receipt, 65%.

**It compounds with two documented gaps.** A Terminal/link-free payment row also carries `orderId` null,
`customerId` null and `stripeChargeId` null (3409: all three), so it cannot be joined to a customer at all,
and `lpt-record-payment`'s de-duplication on `stripeChargeId` cannot see it - the same money can be recorded
twice. And **there is no rental, lease, loan or borrow table anywhere in the schema** (count 0), so a
phone-rental deposit has no record to attach to even in principle.

**Rules that follow.**
- Never reconcile the shop's money from `payment_transactions` alone. It knows payments and not refunds, so
 it can only ever overstate. The Stripe screen is the authority on refunds until something writes `refunds`.
- When a refund matters to a case, the **case note is the only place it survives** today - note 4546 on
 WO2606290006 carries this one, with the fee arithmetic and the open question.
- The Stripe processing fee is **not returned** on a refund: kept-net = payment - fee - refund. Refunding to
 leave a round number must add the fee back, or the shop keeps that much less than it meant to.
- A rental deposit is not repair money. Do not link it to a repair order to "get it into the system".
