**L3106 · The copy-deploy did NOT delete those modules, and the CRLF was my own transfer - two confident inferences contradicted by measurement**

TWO CORRECTIONS from 2026-09-29, both about trusting an inference over a measurement.

(1) THE DELETION CAUSE IS UNIDENTIFIED, AND THE COPY-DEPLOY IS REFUTED.
I had implied - and an audit lane initially repeated - that the copy-deploy deleted the ten missing modules. The measured counter-evidence: every run of the deploy_by_copy family creates a pre-copydeploy-<ts> directory unconditionally before touching anything, and THERE IS NO pre-copydeploy-20260929* DIRECTORY. The newest is pre-copydeploy-20260928T202359Z. So that family did not run on 2026-09-29, the day the modules were found missing. The family also contains no rm, no --delete, no tree-sync, no git reset and no git clean - it only copies forward and SKIPS paths absent from the source.
The nearest capability found was SIX BRANCH SWITCHES in the live tree's reflog during 2026-09-29, because `git checkout <branch>` removes tracked files absent from the target branch. But the deleted modules were UNTRACKED (no committed deletion exists for them in `git log --all --diff-filter=D`), and a branch switch does not remove untracked files. So that is a hypothesis that does not fit the evidence either.
CONCLUSION, stated as fact: the operation that deleted those files is NOT in any deploy script that could be found, and its cause remains UNIDENTIFIED. Do not repeat the copy-deploy attribution; it is contradicted by a directory listing.

(2) THE CRLF BLAME WAS MINE, NOT THE DEPLOY SCRIPTS'.
An audit lane reported CRLF line endings on the deploy scripts and cited "$'\r': command not found" in their .out logs. Sound measurement - `tr -cd '\r' < file | wc -c`, because `grep -c` prints 0 AND exits non-zero so `|| echo 0` yields two lines and an unreliable count - shows deploy_by_copy.sh, _v2, _v3, deploy.sh and verify_v2.sh all have CRs=0. They were clean all along.
The stray CR is introduced by MY OWN transfer method: piping a file to `ssh host "cat > target"` leaves exactly one CR (CRs=1) in the written file, and that is the source of the `$'\r'` line I saw at the end of nearly every remote script I ran this session.
FIX, now part of the pattern: after any `cat >` transfer, run `sed -i 's/\r$//' target` and verify with `tr -cd '\r' | wc -c` returning 0. Do not use `grep -c` to count carriage returns.

THE GENERALISABLE RULE, and the one worth keeping: a log line is evidence about the LOG, not about the file. Two of my own confident statements today came from reading symptoms (a log message, a status string) instead of measuring the thing itself. `file`, `tr | wc -c`, `ls`, and running the command are measurements; everything else is inference.
