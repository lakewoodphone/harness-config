**L3464 · Four transcript-archiving defects with one shape: they cannot report their own failure**

**Three ways this estate has already lost transcript archiving, all found on the same day, none of which fails loudly. Fix the pattern, not the instance.**

1. A READ MUST NOT INVENT WHAT IT READS, AND A WRONG PATH MUST NOT LOOK HEALTHY.
`transcript-archive-server.py`'s `connect()` creates the database when it is missing -- right for an ingest, wrong for every read. On `secratary-cloud` with the default path (the office box's, absent there), `--stats` printed `ok: true, objects: 0, arrivals: 0` -- a clean bill of health for a path holding nothing -- and `--cursor-out` returned an EMPTY cursor, which would have made the client re-send the whole corpus. Guarded: `--stats/--check/--read/--cursor-out` now refuse with exit 3 when the database does not exist. Applied 2026-10-11.

2. A MACHINE'S NAME AND ITS ADDRESS ARE DIFFERENT THINGS, AND CONFLATING THEM SILENTLY MARKS A MACHINE CURRENT FOREVER.
`transcript-archive-pull.py` hardcoded `"secratary": {"alias": "local"}` because the office box WAS the archive host. Run from the new authority, that made the pull archive the AUTHORITY'S OWN files under the office box's name and write `machine_contact(secratary, files_seen=0, newest_source_mtime=0.0)`. `--check` compares newest source mtime against newest archived mtime, so a source mtime of ZERO is older than everything: the office box -- the one holding the only copy -- would have read as perfectly current, permanently. Fix: per-host alias overrides (`TRANSCRIPT_ALIAS_<MACHINE>`), so identity is stable and location is not.

3. AN EXIT CODE IS NOT A MONITOR.
The pull died on every machine from 2026-10-10 and the runner exited 3 every hour. Only a GAP (check exit 1) raised `ALARM` or filed a journal entry, so nothing watched the thing that was actually broken; `~/.cron-status/runs.tsv` had `rc=3` in it once an hour and nobody reads it. Now a failed pull AND a check that returns an exit code it does not define both raise `ALARM` and file one guarded pain entry. Same family as AGENTS.md section 1 trap 2 (`LastTaskResult=0` for 21 days): a scheduler's own status is not evidence it did anything.

4. AND A FOURTH, ON A DIFFERENT MACHINE, SAME SHAPE.
`zabz-tech-linux` ran `push-dsh-sessions.mjs --transport http` every 30 minutes from cron, queued 301 sessions / 6,881 rows every time, and had EVERY batch refused with `no token` for six days -- because none of the five `.env` paths the shipper reads existed on that box. The authority's last row from it was 2026-10-05T03:30:02Z. The log held the word REFUSED in caps every 30 minutes and no alert was wired to it. Fixed by writing `~/code/harness-config/.env` (600) with `DSH_SESSION_INGEST_TOKEN`; the authority then accepted `shipped: 301 session(s), 6881 new row(s)`.

GENERAL RULE: for anything whose job is to keep a copy current, prove it by the ROW DELTA or ARRIVAL COUNT at the destination, never by the exit code or the scheduler's status; and make the failure path raise the alarm, not just exit nonzero.

EVIDENCE: `docs/mesh/134-ARCHIVE-CONTINUITY.md`; journal P2944, P2945.
