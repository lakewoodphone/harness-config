THE HARDCODED THING, FOUND. `sms-responder.py:cmd_run` had this, and its own comment condemned it while
missing the point:

 # It runs BEFORE the classify/decide path because the classification costs a model call and the ledger
 # filing does not need one: "the owner asked for something" is not a judgement call, it is a fact about
 # the sender.
 if allow == "auto" and _is_owner_number(perm, r["from_number"]):
 filed = _file_owner_request(conn, r, body); _reply_with_top_question(conn, r["from_number"]); continue

So the MODEL WAS NEVER CONSULTED for the owner. "The owner asked for something" is not a fact about the sender:
his message may be an ANSWER, a greeting, a correction, a complaint or a request, and telling those apart is
exactly the judgement a model is for. Measured cost: he answered questions in plain English and the system,
unable to read any of it, filed each answer as NEW work and asked him a different question. A question loop
produced by never understanding a word he said.

FIXED: the owner branch now goes to the model FIRST with the conversation in context - the open questions, what
we asked him and when (from `offered.db`), his thread - and files only after the judgement. Tested against his
real messages: "the library I actually still have the books in my house... as for escape 101 I don't use that
company anymore" -> `work`, "Two open items need checking: the library books/fees and the Escape 101 account
status"; "I will pay Weinberg in cash after the holiday" -> `record`, "informing me of decisions already made";
"check the credit card statements" -> `work`, "Needs to check credit card statements to see if the toll was
already paid". Model: secretary-auto -> DeepSeek V4 Flash, resolved at runtime, never a literal.

AND THE AUDIT SHOWED THE SERVER WAS ALREADY RIGHT AND I WAS THE OFFENDER. The AI server had ALREADY recorded his
Weinberg answer as a task and a goal (assigned to dept_finance, 03:20Z), and `owner_decision_queue` already
answers rows in his own words with defer dates (#78, #110, #124). The parallel machinery - my
`close-answered-questions.py`, the word-overlap matcher I started writing, `check-text-status.py` - was MINE,
beside the system. The matcher scored 0.04-0.11 on his real replies and I nearly shipped it.

ALSO ROOT-CAUSED AND FIXED: fleet_location_poll, 410 consecutive failures, regressed 177 -> 306 -> 402 -> 410
"despite prior fixes". It GETs FLEET_API_URL=http://87.99.141.172:8003, which refuses every connection; that
host is not this machine (public IP 71.104.140.242), nothing owns port 8003, `mdm_devices` does not exist,

gate: `ABM_LOCATION_POLL_ENABLED=false`, proven with a fresh `Settings()` returning False. Cost of not finding
it: 89 work sessions since 2026-09-16, 48 failed, chasing a one-line config problem.

AND THE CHURN ENGINE, which is a real defect the owner should know about: `app.database.update_task` REFUSES to
mark a task completed when 3+ of its recent work sessions failed and none succeeded - a sound guard against fake
completions - BUT IT RETURNS HTTP 200 REGARDLESS. So the refusal is invisible, the task stays `in_progress`, and
the scheduler re-fires it forever. A task that fails three sessions can never leave the queue. Only a
non-"completed" terminal transition (`cancelled`) takes, which is how the five-task cascade was finally closed.
The systemic fix belongs in the database layer: a refused transition must be reported in the response, and there
must be a supported way to retire a task that cannot succeed.
