**L1988 · In a shared browser profile only the FIRST window appears in the process table**

MEASURED 2026-09-18, ZABZ-YOGA. With two DSH windows open on ONE --user-data-dir, the process table showed:
 pid 27072 (browser root) --app=http://127.0.0.1:3200/?token=...
 + 9 children, ALL of type crashpad-handler / gpu-process / utility / renderer, NONE carrying an --app= or any URL.
The second window (origin 3201) existed ONLY as an anonymous --type=renderer child. Chromium hands the second launch to the existing browser process and the launching msedge.exe exits immediately.

CONSEQUENCE: any per-window count built on "a process whose command line contains --app=<url>" finds exactly ONE window per profile - so in shared mode it finds one window in TOTAL and reports every other slot as empty. dshw new then re-opens slot 1 forever and dshw restore duplicates every window.

FIX: the alias ORIGIN is the per-window identity, and the only place it is observable is the proxy: a live window keeps streaming connections open on its own port ($events / session/follow). Verified: the two windows each held 2 established connections on 3200 and 3201. Exposed as GET /__dshw/open -> {"ports":[3200,3201]}.

TRAP: the liveness probe must EXCLUDE ITS OWN CONNECTION. The launcher asks on one of those very ports, so the first version reported openPorts:[3200] with every window CLOSED - and 3200 is slot 1'"'"'s origin, which would have read as permanently open and never reused.
