**L3359 · Boot the thing: a config flag is not a behaviour, and only running it showed the survivor would still tick**

GOAL ROUND 5, and the most valuable finding of the whole build so far, found ONLY by actually booting the survivor configuration. I had built survivor mode as a code gate on the outbound senders (SMS/email hold-and-queue, flush refuses to drain) plus a configuration overlay (deploy/hosting-migration/survivor.env) that set AUTOPILOT_DEFAULT_ENABLED=false and every per-subsystem flag I could find. I had tested the senders behaviourally and the config by parsing it. Then I booted the real app with that exact overlay against a fixture copy of the dev database, and /health said mode=survivor - correct - and autopilot_enabled=TRUE - wrong. CAUSE: AUTOPILOT_DEFAULT_ENABLED only changes a DEFAULT, and app/autopilot.py::_load_state() restores enabled from data/autopilot_state.json afterwards; that file said enabled:true and wins. That file travels WITH the replicated database, so on a real standby it will normally say true - i.e. the common case, not an edge case. CONSEQUENCE IF I HAD NOT BOOTED IT: the standby would have ticked, spending money and taking actions from a divergent context, while my 'survivor mode' document claimed it ran no autonomous work. The outbound gate would have stopped it SENDING, which is exactly why the bug was invisible to the sender tests I was proud of. FIX: a code gate at every place the loop can switch on - _survivor_blocks_autonomy() checked in enable(), in start_thread(), and in _load_state() (which now ignores a persisted enabled=true and logs it). VERIFIED END TO END, not by unit test: re-booted the same configuration and /health now reads mode=survivor, ok=true, autopilot_enabled=False, database.ok=true. Also added tests/test_survivor_autopilot_gate.py (3 tests, including that a NON-survivor still honours persisted enabled:true). RULE: for any reduced/degraded mode, the acceptance test is a BOOT AND A READ OF ITS OWN HEALTH SURFACE, never a config diff. A flag that is set is not a behaviour that happens; the only evidence is the running thing reporting its own state.
