**Lesson (2026-09-17, Goldstein microSD): a card reporting a tiny capacity is a CONTROLLER FIRMWARE
FALLBACK — not a small card, not a fake card, and never a formatting problem. Three checks settle it in
three minutes, and the wrong "fix" destroys the case.**

The customer's story was *"his brother put it in a spy pen and it appears to have been formatted"*, and
that story was believable — a pen camera re-initialising a card is a real behaviour and this shop has
recovered exactly that shape before (Abramczyk, Czermak). The truth was different and better evidenced:

| check | what we measured |
|---|---|
| 1. reported capacity | **121.25 MiB** (127,139,840 B, last LBA 248319 @512 B) — set against any card that could hold a family's photos, absurd |
| 2. **distinct 512-byte blocks in the whole image** | **1 of 248,320** — every address returns the identical block; smallest repeating period 512 B |
| 3. signatures + strings | **0** JPEG/`ftyp`/ID3/RIFF signatures and **0 ASCII strings** in 127 MB |

What that means: an SD controller reads its own configuration area (capacity, geometry, block map, wear
tables) at power-up and **everything depends on that read**. When it fails, the card reports a minimal
built-in default instead of a size, and cannot address its NAND. The memory is normally intact *behind*
a controller that cannot map it — which is why this is a **lab** job (chip-off / monolith read with
Rusolut VNR / PC-3000 Flash class gear plus translation-layer reconstruction), not a software job.
Independently corroborated the same day: [Newcastle "A 32GB Card Reporting
32MB"](https://www.newcastle-datarecovery.co.uk/case-files/a-32gb-card-reporting-32mb.html) and
[Bristol case 045](https://www.bristoldatarecovery.co.uk/case-files/case-file-045-gopro-proposal-microsd-32mb.html)
— both reached this route only after ruling out counterfeits, both read the NAND past the controller.

**The rules that follow, and one of them is a data-destruction rule:**
- **NEVER format, repartition, "resize" or repair the card to the size it claims.** That is the
 internet's favourite advice for this symptom and it writes over the FTL/configuration area a lab
 needs. Bristol states it plainly.
- **`ddrescue`, testdisk undeleting, signature scanning and PhotoRec all do not apply.** They need
 *different* data at *different* addresses; here every address holds one page. Running them looks like
 thoroughness and is pure theatre — worse, imaging 127 MB of one block produced a file that a careless
 reader could mistake for progress.
- **Isolate the reader before blaming the card** (ours was cleared: `05e3:0749` serial `000000001539`,
 the known-good unit that imaged Czermak/Feld/Bakst, and its empty slot correctly reported 0 B). The
 cheap, decisive isolation test: **power-cycle the USB port** (`echo 0 > /sys/bus/usb/devices/<dev>/authorized`,
 sleep, `echo 1`). If the replayed block **changes** across the power cycle while every LBA is identical
 *within* a session, a live NAND page is being read badly — the card, not the bridge. Ours changed:
 `858629d2…` → `1c8ac209…`, same structure, scattered byte differences.
- **Do not read health off a USB bridge.** `smartctl` said "SMART Health Status: OK" on a device whose
 media is unaddressable. A bridge manufactures that answer; it is not evidence.
- A USB card-reader bridge **does not pass SD commands** (`sg_raw` vendor passthrough → `Illegal
 Request / Invalid command operation code`), so the card's CID/CSD — which would give its true size —
 is not readable on the bench. `sg_start --stop/--start` and direct I/O change nothing.
- **"Empty is a refusal."** The absence of a filesystem was not evidence the card was formatted; it was
 evidence we could not address it. Two very different conclusions, and the second only appeared when I
 asked *how many distinct blocks the device returns* rather than *what filesystem is on it*.

Recorded in the playbook's lessons table (two rows) and the case file. This is the shop's first
pen-camera device class and it is a **dead card**, not the format everyone assumed.
