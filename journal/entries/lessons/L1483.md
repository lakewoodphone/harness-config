**L1483 · A fix at one layer does not protect the layer above: check every derived status for false completion**

Fix the lie at every layer, and check the layer above the one you just fixed

The 2026-09-14 work removed a completion lie from work sessions: a session that had not
finished was being recorded as completed, and `_close_unfinished_work_session` now says
failed. On 2026-09-15 the session rows were honest -- task #25106 shows five failures and
no success, plainly -- and the TASK row still said 'done'. The lie had simply moved up a
level: sessions no longer claim to be finished, and the task that owns them was closed as
finished anyway, by a rollup that never looked at whether any work had succeeded.

The lesson is not "check for more bugs". It is: when a status is derived from other rows,
a fix at the level below does not protect the level above. Ask, for every derived state,
what it is derived FROM, and whether that derivation can produce a false positive.

The specific trap here is that "closed" and "finished" are conflated. A task can be closed
for many reasons -- a rollup fired, a parent's children ended, a sweep found it stale --
and only one of them means the work happened. So the guard must name the evidence that
permits the word "done": here, a completed work session, or an active one closing itself.
Absence of failure is not evidence of success, and absence of an open session is not either.

Detector worth reusing: for any row that claims completion, ask which query could have
written it, then check whether that query can run when nothing succeeded. For #25118 the
answer was a goal plan whose updated_at matched the task's completed_at to the microsecond,
which identified the rollup in one comparison.
