**L1904 · on zabz-tech an ssh-spawned process cannot traverse the session-created fanout junction, so a remote compose reports a fault that is not there**

MEASURED 2026-09-17 on zabz-tech, from ZABZ-YOGA.

 $ ssh zabz-tech-ts ... node <dsh>/lib/bin.js --profile web --dump-config
 dump_exit=1, 16 lines: cannot resolve profile bundle "dsh-plugin-remote-fanout" ...
 ... while the junction EXISTS and points at the right place:
 ~/.dsh/profiles/web/node_modules/dsh-plugin-remote-fanout
 -> C:\Users\ezabz\code\harness-config\packages\plugin-remote-fanout (present, 12 files)
 ... and the SAME ssh-spawned reader resolves <junction>\package.json for 8 other plugin junctions and
 NOT for this one. A LOCAL one-shot scheduled task, same profile, same binary, same machine:
 TRAVERSAL OK dsh-plugin-remote-fanout bytes=1152 / dump-config exit=0, 617 lines -- three times
 (14:43:03Z, 14:43:47Z, 14:45:16Z).

99 §2.2 measured the same asymmetry (OK cost/attention/mesh-http, ERR session-link) and concluded it: the
trust attribute is on the JUNCTION, and a junction a session created is the untested one. A network-logon
token does not traverse it; the engine's Interactive logon does.

RULE: never verify a profile composition -- or a boot -- on zabz-tech from an ssh session. It reports a
fault that is not there. Use a LOCAL one-shot task. The proven instrument already on that machine is
'DSH Mesh 99 Verify (once)' -> ~/.dsh/mesh/99/verify-provider-local.ps1 (read-only: it composes and appends
its own log). To register your own use New-ScheduledTaskAction + New-ScheduledTaskTrigger +
Register-ScheduledTask and AVOID the four shapes 99 §2.2 measured to fail (-Force, -Principal, -AtLogOn,
RestartCount).

COROLLARY, cost an extra round trip: --dump-config prints the !!js expression UNEVALUATED, folded as
`!!js >-`. To "read the composed configuration" you read the EXPRESSION; there is no resolved value to read.

Evidence: docs/mesh/103-route-commit-and-sync.md §2.4 and §3.3.
