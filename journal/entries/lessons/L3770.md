**L3770 · E4610 Tech Mode codes and Bluetooth ground truth (serial 616450266, 2026-10-13)**

Ground truth pulled from Kyocera **E4610 serial `616450266`** on the bench 2026-10-13 (Android 7.1.1 / SDK 25, build `1.805VZ.89.a`, product `VZW_E4610`).

## Tech Mode unlock code

- Code = `generateUnlockCode(deviceKey, getInstallTimestamp())`, and **both inputs are displayed on the app screen** (`MainActivity` lines 84-87, 147).
- **The Device Key is derivable from the ADB serial**: this phone showed `990006164502667`, which is exactly `"99000" + serial 616450266 + "7"`. `getOrCreateDeviceKey` falls back to a generated stable 15-digit key when `readImei()` returns nothing — and `getprop ro.ril.oem.imei` / `gsm.baseband.imei` are both empty on this unit, so the fallback is what is in use.
- **The Install ID is not a constant.** `TechModeManager.getInstallTimestamp()` returns `storedWall + seconds-since-install` whenever the wall clock has drifted more than 300 s from that estimate (lines 86-121). A code computed from an Install ID read in an *earlier* session is therefore wrong. Read the Install ID and enter the code **in the same screen session** — this is the same rule the repo's own runbook states, and it is exactly the mistake made on 2026-10-13 (a code was computed against `1783261810`, which the phone no longer reported).
- **Read the real values over ADB instead of trusting the screen**: `adb shell content query --uri content://com.android.cts.techmode/state` returns `device_key=` and `install_timestamp=`; the stored values are also readable with `adb shell run-as com.android.cts.techmode cat /data/data/com.android.cts.techmode/shared_prefs/lpt_tech_mode.xml` (the debug-signed build is `run-as`-able).

## Two broken paths in the repo for reading that code

- `scripts/utilities/README.md` says to run `scripts/utilities/Get-LptTechModeCode.ps1`. **That file does not exist there.** It is at `legacy/scripts/utilities/Get-LptTechModeCode.ps1` and it works.
- `python -m lpt.cli get-tech-code` **cannot run on this machine's default Python**: `cli/lpt/cli.py` line 5 does `from datetime import UTC`, which needs Python 3.11+, and `python` here is 3.10 (`ImportError: cannot import name 'UTC'`).

## Bluetooth ground truth on this E4610

- `ro.bluetooth.hfp.ver = 1.7` — HFP 1.7, i.e. wideband-speech capable. Qualcomm transport `smd`; HSP/HFP/MAP/OPP/PBAP/SAP/NAP flags on.
- Adapter powers up and pairs. Live services when on: **Headset (HFP), A2dp, AvrcpController, Gatt, Pan, Map, Health**. Address `24:29:FE:6C:4B:81`, name `KYOCERA E4610`. It was already bonded to a Windows desktop (`DESKTOP-FGV6KMH`).
- **Tech Mode does not block Bluetooth.** `dumpsys device_policy` shows the only Bluetooth-related restriction is `disableBluetoothContactSharing=true` (PBAP contact sharing). `com.android.bluetooth` is installed and **not** in `pm list packages -d`.
- **No aptX**: no `libbt-aptX*` in `/system/lib` and no codec list in the A2DP dump — SBC only, which is irrelevant for a mono HFP headset.

### Turning Bluetooth on from a shell on this build (harder than it looks)

- `svc bluetooth` **does not exist** on this build — `svc` only offers `help power data wifi usb nfc`.
- `settings put global bluetooth_on 1` writes the setting and the radio **stays off**.
- What works: `am start -a android.bluetooth.adapter.action.REQUEST_ENABLE`, which raises Kyocera AFP's dialog *"An app wants to turn on Bluetooth."* — the **Allow soft key is `input keyevent 1`** (left soft key; a `input tap` on its bounds did not take).
- **Nothing from the shell turned it back off** (`service call bluetooth_manager 5 …` returned without effect, transaction codes for this 7.1 build were not confirmed). Do not keep poking a manager service blindly. The phone was left with Bluetooth **on** and `bluetooth_on=1` set to match.

## Wired audio is real on the E4610

`dumpsys media.audio_policy` declares `AUDIO_DEVICE_OUT_WIRED_HEADSET`, `AUDIO_DEVICE_OUT_WIRED_HEADPHONE` **and `AUDIO_DEVICE_IN_WIRED_HEADSET`** — so the 3.5 mm jack takes a TRRS headset and its microphone has a declared input path. A wired boom-mic headset is a genuine zero-battery fallback.
