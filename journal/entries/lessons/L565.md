**L565 · Never default a value that decides whether to raise an alarm - the default only chooses which wrong claim you make**

A tri-state fact was collapsed into a boolean with a default, and the default turned a
measurement into a false alarm. The page reported "53 DRN devices have checked in before but
not for a week or more - that is an outage" when only five had ever reported at all.

What happened, in order:
1. I added `ever_replied` to the fleet-api and had the tRPC layer default it to `true` when
 the field was absent. That default was chosen deliberately and for a defensible reason -
 it avoids ever labelling a working phone "never reported", which felt like the worse error.
2. I then deployed the fleet-api and the frontend but NOT the tRPC backend, so the field
 arrived `undefined` for every device.
3. Defaulted to true, every device looked like it "had reported", so all 53 went into the
 outage bucket and the live page asserted an outage that did not exist.

Rules:
(a) When a value decides whether to raise an alarm, DO NOT DEFAULT IT. Make it tri-state and
 treat "unknown" as its own case that claims neither. A default here does not make the
 claim safe, it only decides which wrong claim you make.
(b) Both directions were wrong, which is why no default existed: `true` invented an outage,
 `false` would have invented a provisioning failure on a phone that was fine. When both
 defaults are wrong, the absence of a value is information and must survive to the UI.
(c) An absence that cannot be verified must degrade to a REFUSAL - the page says it cannot
 tell - never to an alarm. This is L2 and L196 again, one layer up: an inference that
 cannot be checked is not evidence, and the failure mode of guessing is a confident wrong
 statement rather than a missing one.
(d) Deploy the whole path or none of it. A field that crosses three layers (fleet-api -> tRPC
 -> UI) is not live until the middle layer is rebuilt; I had already proved earlier in the
 same session that the tRPC layer needs its own deploy, and still forgot the middle of the
 chain while verifying the ends.
(e) It was caught only because I looked at the rendered page rather than trusting the
 typecheck and the API read - both were green while the page was telling the owner
 something false. Verifying each layer is not the same as verifying the claim.

Also worth keeping from the same hour: the finding that motivated the field. 65 devices are
enrolled, 8 have ever replied, 48 of the 57 silent ones are marked `deployed`. The dashboard
had been reporting that as "53 silent", which reads as an outage on phones that were never
reachable. Collapsing two populations into one count was the real defect; the default bug was
the second one hiding behind it.
