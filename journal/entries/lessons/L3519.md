**L3519 · A session's sense of elapsed time drifts and will invent an outage - read the clock on the machine that owns the timestamp**

**A session's sense of elapsed time drifts, and it will invent an outage. The box's own clock is the
authority on "now".**

WHAT HAPPENED, 2026-10-11 ~21:17:30Z. Reading the cloud ledger, I saw its newest row was
`2026-10-11T21:17:01Z` and concluded that "the ledger hasn't grown in about 30 minutes" - because my
sense of elapsed time in the session said it was roughly 21:45. I was one check away from reporting that
the cloud authority's scheduler had stopped, which would have been the **second** false outage report of
the day, from the same seat.

The measurement that caught it, one command:

 now (box): 2026-10-11T21:17:30Z
 ledger newest: 2026-10-11T21:17:01Z <- 29 SECONDS old, not 30 minutes
 rows in last 10m: 32
 rows in last 30m: 87
 cron: active / enabled
 api: HTTP 200

Nothing was wrong. My narration had been writing "~21:40" for several turns while the box had advanced
about a minute.

**THE RULE.** Do not reason about "how long ago" from the conversation. **Always read the clock from the
same machine that produced the timestamp, in the same command as the timestamp**, and compute the age
there. A staleness judgement made by comparing a remote timestamp against a locally-assumed "now" is not
a measurement - it is an inference with an unknown error term, and here the error term was 30x the value
being judged.

**WHY THIS IS THE SAME FAILURE AS THE ONE THAT STARTED THE DAY.** This morning an agent looked at a
masked unit and inferred "the company is down". This evening I looked at a timestamp and inferred "the
scheduler has stopped". Both took a real observation and attached a story to it without measuring the
thing that would confirm or kill the story. The fix is identical and cheap: **one command, on the box,
naming both the reading and the clock.** Had I done that this morning, `MISSION-READ-FIRST.md` would have
answered in one line; had I not done it now, I would have filed a second false alarm.

**Corollary worth keeping:** any "X is stale / has not run / has stopped" claim must state the age in
seconds or minutes as computed **on the machine that owns the data**, never as an adjective. "It looks
stale" is not a reading.
