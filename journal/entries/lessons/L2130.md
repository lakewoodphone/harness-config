**L2130 · L2137 - do not name a parameter the same as the variable a call site will pass; a rename pass will collide them**

A self-inflicted bug worth keeping, because the mechanism is general.

Batching `mashgiach`'s finding inserts required renaming the buffer. I wrote the helper as:

 def _log_finding(rows: list[tuple], ...) # correct
 ...
 def _log_finding(pending: list[tuple], ...) # what I actually wrote first

and then renamed the call sites from `conn` to the buffer name with a regex:

 src = re.sub(r"(\n\s+)pending,(\n\s+agent_id=)", r"\1pending_findings,\2", src)

The regex matched the **helper's own parameter declaration** as well as the four call sites, because
both had the same shape: a bare `pending` on its own line followed by `agent_id=`. The helper became:

 def _log_finding(pending_findings: list[tuple], ...) # parameter
 pending.append(...) # body still used `pending`
 return len(pending)

so the body referenced a name that no longer existed, and every `daily_scan` call raised
`NameError: name 'pending' is not defined`.

**The rule: a parameter and the argument a call site passes must not share a name.** If the helper's
parameter is `rows` and the caller's buffer is `pending_findings`, no textual rename can collide
them, because the two names never match. The rename is now `rows` for the parameter and
`pending_findings` for the buffer, and a test asserts the helper's parameter is not named `pending`.

**Also:** the docstring said the word "executemany", and a test asserting `"executemany" not in
source` failed on the PROSE rather than the code. Two of my checks in one round were reading text
instead of meaning. The fix was to strip docstrings and comments with `ast.unparse` before asserting -
`_code_only()` in `tests/test_mashgiach_batched_findings.py`. **When asserting about code, parse it;
do not grep it.**
