**L1513 · lpt-recovery-manager claim wants the case DIRECTORY basename, not the new-case slug**

`lpt-recovery-manager claim <case>` looks up `$CASES_DIR/<case>` and nothing else, so the
case id it wants is the **directory basename created by `lpt-recovery new-case`** — which is
`<YYYYMMDD-HHMMSS>-<slug>`, not the slug.

Measured 2026-09-15 (ZABZ-TECH → linux-pc):
 lpt-recovery new-case newman-3477680413 -> /srv/recovery/cases/20260915-122509-newman-3477680413
 lpt-recovery-manager claim newman-3477680413 --agent $T
 ERROR: case not found (create with new-case first): newman-3477680413
 lpt-recovery-manager claim 20260915-122509-newman-3477680413 --agent $T
 CLAIMED case=20260915-122509-newman-3477680413 by agent=c503…

The error text ("create with new-case first") is misleading — the case *does* exist under the
dated name. Older cases in `/srv/recovery/cases/` break the pattern (e.g. a bare
`czermak-7183147956` directory exists alongside dated ones), which is why the lock list shows
some short ids and some long ones. Read the real directory name from `new-case`'s output and
claim with that; never assume the slug works.

Second thing learned in the same five minutes: `systemd-inhibit` on that bench works when
launched detached as root (`sudo nohup systemd-inhibit --what=idle:sleep --why="..." sleep
14400 &`) and shows up as MODE=block in `systemd-inhibit --list`; that is the cheap fix for the
bench-suspended-mid-rescue failure measured 2026-08-05. Verify with `--list`, not with
`systemctl status systemd-inhibit` (which printed nothing).
