**L2800 · Three measured corrections for the lpt_prod migration: migrate deploy does not refuse on orphan rows, verify from the toolchain that ships the files, and a config table is not the live path**

## Three measured corrections that change how production migrations are planned

Evidence gathered 2026-09-28 17:09–17:30 UTC on `lpt-apps-01`, while preparing (not executing) the
`lpt_prod` migration runbook. Full detail: `C:\Users\ezabz\code\_scratch\prod-migration-runbook.md`.

### 1. `prisma migrate deploy` does NOT refuse on orphan `_prisma_migrations` rows

D2659 and the brief both assumed the five DB-only migration rows ("orphans") block `migrate deploy`
or make it misbehave. Measured on a restored clone of production: **`migrate deploy` applied all
five pending migrations while all five orphans were still present.** No error, no warning, no
refusal. And afterwards — with the orphans restored and nothing pending — `migrate status` still
printed `Database schema is up to date!`.

So the reconciliation used on `lpt_test` (delete the five bookkeeping rows, then deploy) was
**cosmetic, not a prerequisite**. On production the trim is a pure write with no benefit, and it
destroys the only surviving record (checksums + timestamps) that those migrations were ever
applied. **Recommendation recorded in the runbook: do not trim on production.**

### 2. Verify a migration from the toolchain that SHIPS the migration files, not from the app's own container

Production's own container ships **145** migrations; the repository and the test image both ship
**151, verified as an identical set**. Run from `lpt-backend` against `lpt_prod`,

 Database schema is up to date!

for a database that is five migrations behind the repository. A verifier who reaches for the
obvious container will read a clean verdict from the wrong toolchain and conclude success while
nothing happened. Run `migrate status` / `migrate deploy` from the image that has the files
(`lpt-test-backend`, with `DATABASE_URL` rewritten), or copy the files — never from the app being
migrated.

Corollary measured on the same pass: the running production backend was built
2026-09-15T22:28:44Z (`lpt-lpt-backend:priceguard-20260915-222840`), its `schema.prisma` declares
only the OLD `BudgetTier` labels, and `dist/trpc/routers/laptop-preference.js` still compiles
`VALUE_200_400`. Applying the enum rename against an un-rebuilt backend is a latent break — check
the *running binary*, not just the SQL, before calling a migration schema-only.

### 3. A config table is not the live path: check what actually reaches customers before calling a change customer-facing

The A2P migration rewrites `a2p_auto_reply_config.message_template`, and it was flagged as the risky
one because it "rewrites customer-facing SMS text". Measured in `lpt_prod`:

- `a2p_auto_reply_log` has **0 rows**;
- the automatic reply customers actually receive is sent by **Dialpad**, not by this backend —
 `communications.metadata` = `{"provider":"dialpad","source":"dialpad-sms-webhook","targetType":"office"}`
 from `+17326552355`;
- Dialpad's live text already enumerates the correct open days and has since 2026-09-15.

So the migration changes a template that is **not on the live send path**, and its A2P risk is nil
in both directions: it removes no disclosure the old text had, and no registered sample matches
either version. The real, separate finding was that the **live** auto-reply carries no STOP, no
HELP, no "msg & data rates may apply" and no privacy link, while the registration's declared opt-in
text promises all four.

**The transferable rule:** before treating a config row as customer-facing, find the row's actual
readers and the actual delivered traffic (`communications`, provider metadata, delivery status).
"Which code reads this?" and "what did customers receive?" are different questions, and only the
second one is a compliance question.

Method note for anyone repeating this: the strongest rehearsal available is a **fresh dump restored
into a scratch database**, because the test copy is already reconciled and re-running on it proves
nothing. Restorability of the backup was proven this way at the same time (row counts matched
production exactly: 153 / 112,561 / 1). Two script traps worth knowing: `docker exec -i` inside a
script fed to `bash -s` **consumes the rest of the script from stdin** (drop `-i`, or redirect);
and a `sed 's#/lpt_test#<newdb>#'` URL rewrite silently eats the leading slash and produces
"invalid port number" — keep the slash in the replacement.
