**L3930 · The company wedges ITSELF: a 600s run_once is abandoned, the thread keeps holding _db_lock, the next run is slower, and after 3 the loop disables itself needing an explicit re-enable - and a stuck loop is invisible from outside**

The company's loop wedges itself, and its own docstring describes the mechanism. This is very likely the root of the day's stalled hours, the `database is locked` failures and the 71 `/health` probe timeouts — all of which I had been treating as separate symptoms.

**The defect, in the code's own words** (`_note_run_once_overrun`, `autopilot.py:7650`):

> *"Called from `_loop` when run_once exceeds its 600 s deadline and is abandoned (**the worker thread cannot be killed**). An abandoned run keeps holding the process's shared resources — memory and **SQLite/`_db_lock`** — so a second run adds a second holder; a run that overruns repeatedly is **wedged, not slow**. After `_RUN_ONCE_OVERRUN_BREAKER` consecutive overruns the loop is disabled and needs an explicit re-enable."*

So the cycle is closed and self-amplifying:

1. a `run_once` exceeds **600 s** and is **abandoned** — the thread keeps running and **keeps holding `_db_lock`**;
2. the next run is therefore slower (more lock waiting), so it is more likely to overrun;
3. after **3 consecutive** overruns (`_RUN_ONCE_OVERRUN_BREAKER = 3`) the loop **disables itself** and *"needs an explicit re-enable"*.

**Measured today.** Three `ABANDONING it` events and one `Event-driven run_once timed out`. The breaker has **not** tripped (`0` occurrences, `enabled: True`, `consecutive_failures: 0`) — but the loop was **wedged anyway**: `last_run_at` stuck at **13:54:43** for 44 minutes while the log showed activity at 14:05, 14:14 and 14:34, because **an abandoned run never updates `last_run_at`**. `run_count: 6`. And the collateral:

 14:14:27 ERROR run_once timed out after 600s — ABANDONING it (the thread keeps running)
 14:14:27 WARNING run_once failed, backoff 900.0s (x1.0)
 14:15:59 WARNING Owner outbox flush failed: database is locked (autopilot.py:7847 -> :11019)
 14:22:15 WARNING Work step 11 failed: database is locked
 14:34:11 WARNING Event-driven run_once timed out after 600s

**Three findings fall out of it.**

1. **A stuck loop is invisible from outside.** `systemctl is-active` says `active`, `/health` says 200, `enabled` says `True` — and no work happens for 44 minutes. The only signal is `last_run_at` not advancing, and nothing watches that. **This is the same shape as the "degraded 200" and the counter that greps the wrong string: a surface that reports health while the thing is stopped.**
2. **The contention has a cause, and it is self-inflicted.** The 71 probe timeouts (32 of them in the noon hour) and every `database is locked` are downstream of abandoned threads holding `_db_lock` — not of an external load problem. **Which also means the "hours with zero ticks" I attributed to the budget cap earlier today may be partly this**: the cap explains a paused session, and a wedged loop explains a stopped tick, and I have now seen both in the same day.
3. **It is not autonomous.** The docstring is explicit that recovery is *"an explicit re-enable"* — today's remedy was a restart, which I ran at **14:17:59** and again at **14:41:2x**, each time restoring the sweeps within seconds. A company whose loop needs a human to restart it is the opposite of the objective's *"more capable, more autonomous"*, and **nothing in the estate watches for it**.

**And I aborted my own work for it — correctly.** The Amazon receipt backfill I started at 14:19 reads Gmail at **~10 s per message** for ~48 minutes and writes to the same database; the `database is locked` at 14:22 and the 14:34 timeout both fall inside its window. **It is a legitimate contributor to the wedge.** At `[130/289]` it had recovered **+9** totals against a predicted +70, so its marginal value was modest and its interference was not. The restart cleared the wedged run and the backfill in one action. **The 70-row repair is now a recorded, re-runnable task, not a loss** — and it should be run batched, off the tick path, or at night.

**Not established:** whether the three abandons were *consecutive* (the breaker needs consecutiveness, and `consecutive_failures` reads 0, so a successful run reset it at some point); and whether the 600 s ceiling is too small for the work being asked of it — `_WORK_SESSION_TIMEOUT = 300` says a session should be time-boxed well inside the run, so a run taking 600 s means something *outside* the session (Gmail reads at 10 s each, lock waits, check-ins, reconciliation) is consuming it. **The fix is cooperative cancellation — a deadline the long loops can see and return from — because "the worker thread cannot be killed" is the premise the whole cycle rests on.**
