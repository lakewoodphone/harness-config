**L12388 · Shop labels from ZABZ-TECH: the route, the phantom lpt note add, and a doctor line that lies about the anchor**

Four shop hold labels printed tonight for the owner's secretary, from ZABZ-TECH (PowerShell). What transfers to the next session:

THE LABEL ROUTE FROM WINDOWS, in full, because it is four steps and none of them are obvious. (1) Build the job JSON locally with `lines` only (no ticket/customer/device keys, or the work-order branch wins and `lines` are appended differently). (2) `scp` it to the anchor — do NOT pipe it through `ssh` from PowerShell, which has no `<` redirection and may prepend a BOM that breaks the JSON sniff. (3) Dry-run with the NEW renderer read-only: `ssh secratary-ts 'PYTHONDONTWRITEBYTECODE=1 /home/zabz/.local/lib/lpt-label/venv/bin/python /home/zabz/code/lpt-ops/bin/lpt-label print - --dry-run --out /tmp/x.png < /tmp/x.json'`. (4) scp the PNG back and LOOK at it, then print the same command without `--dry-run`, followed by ONE `lpt-label find` — measured tonight, all four prints were caught `PRINTING`/`BUSY` and `READY` afterwards.

`lpt note add` IS ADVERTISED IN `lpt --help` AND DOES NOT EXIST: the argparse choices are doctor/ticket/case/wo/order/customer/sql/photos and it exits 2. Writes are `lpt-write`, which is not on PATH anywhere: it lives at `/root/code/lpt-ops/bin/lpt-write` on the authority, run as `cd /root/code/lpt-ops && python3 bin/lpt-write ...`. Long note bodies: scp the text to the authority and pass `--text "$(cat /tmp/n.txt)"` — command substitution is not re-parsed, so quotes and apostrophes inside the file are safe.

`lpt-write doctor` PRINTS "pushed just now" AND THAT PUSH IS TO THE AUTHORITY, NOT TO THE FROZEN ANCHOR. It reads as if a deploy just happened to `secratary`; measured after the call, `/home/zabz/lpt-ops/lpt_ops/write_helper.py` on the anchor was still mtime 2026-10-25 and its sha unchanged, while `/root/lpt-ops/...` on the authority had mtime = the second doctor ran. Do not panic-revert the anchor on the strength of that line — measure the mtime first.

TICKET IDS ARE NOT TICKET NUMBERS. The Greenfeld Surface labels of 2026-10-18 carried `#2553`; `tickets` id 2553 carries `number` 12718 and was created the same second as the WO2609070001 sync note — a different job. The Surface has no production order and no ticket row at all. A label heading taken from a ticket *id* points at the wrong customer, and nothing in the toolchain warns.
