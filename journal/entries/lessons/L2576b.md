**L2576b · An escalation channel with no reader is worse than no channel: check for the consumer when you add the pipe**

**L · 2026-09-25 · ZABZ-YOGA — An escalation channel with no reader is worse than no channel: check for the consumer when you add the pipe (three instances now)**

**Measured.** `agent_questions` held **12 pending rows** on 2026-09-25, the oldest filed 2026-09-22T15:28Z, and **nothing reads or answers that table**: no endpoint in `app/main.py`, no contract function, no consumer anywhere in the app — while `status` allows `answered`/`dismissed`/`expired` and the history shows **97 answered, 97 dismissed, 313 expired, the newest of any of them 2026-06-27**. So a working answering path existed and stopped, and for three months every question an agent filed went into a hole. Meanwhile the kernel's `attention_debt` check counted the backlog as *the owner's* attention debt — it read **"owner-attention debt: oldest question 2d old"** and put a HIGH red badge in front of him for questions addressed to the supervisor, filed by agents that were long gone.

**Why it is worse than no channel.** With no channel the agent knows it must ask in the open (a task, a queue row, a message). With a write-only channel the agent *believes* it has escalated and stops — the question is spent, and the cost lands on whoever reads the count later. `attention_debt` was faithfully reporting 12 rows; nothing was wrong with the count, only with the assumption that a row in a table reaches a human.

**The rule.** When adding a channel — a table, a queue, a webhook, a notification kind — name the **reader** in the same commit: the function, endpoint, check or surface that consumes it, and what it does with an item it cannot handle. If there is no reader, either do not create the channel, or make the *filing* action fail loudly. A kernel finding counts as a reader only if someone acts on it.

**Three instances of the same class in this system, all found the same way (a count that was true and a promise that was not):**
1. `owner_message_queue` + the in-app reminder channel — delivered, marked `sent`, rendered by nobody (P148; fixed by routing it to the surface the badge reads).
2. The DSH session shipper — a run with nothing to ship left no trace, so an idle fleet and a dead shipper looked identical (L2085, fixed with a heartbeat).
3. `agent_questions` — this one: filed, never read, counted as the owner's debt.

**What was done.** All 12 were answered with bound parameters on 2026-09-25 (each answer carries the decision and its reason in `status_note`), and `~/bin/agent-questions.py` exists so any session can list or answer them in one command instead of writing SQL by hand.
