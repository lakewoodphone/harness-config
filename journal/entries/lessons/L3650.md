**L3650 · Three marketplace suspicions, three clean measurements - and one decision I re-derived that was already documented**

2026-10-13. Three suspicions about the marketplace store, each chased to a measurement. All three
came back CLEAN, which is the result worth writing down - a future session should not re-open these.

1. "THE PARSER DOESN'T MODEL MULTI-ORDER EMAILS." It does, and it did before I looked.
 `parse_ebay_orders_from_email`'s own docstring describes the exact email I had just rediscovered:
 "a single 'Your order is confirmed' email carried four items across four different order numbers
 (21-15155-16873/74/75 and a fourth) under ONE 'Total charged to' of $92.45 ... The charge the bank
 sees is the checkout, not the sub-order, so splitting by order number would produce four amounts
 that never appear on a statement." One row per EMAIL, keyed on the sorted order-number set. I
 spent a round and a half re-deriving a design decision that was already written down in the file
 I was about to change. READ THE FUNCTION'S DOCSTRING BEFORE DECIDING IT IS WRONG.

2. "COMBINED ROWS AND LEGACY PER-ORDER ROWS DOUBLE-COUNT." They do not. 11 combined rows cover 26
 order numbers; 23 plain rows sit on those numbers. Measured: **0 of the 23 share a Gmail message
 with their combined row** (different emails - confirmation vs shipping notice), and **0
 transactions carry both a plain and a combined reference**. 437 marketplace evidence rows sit on
 424 distinct transactions and the overlap contributes no double-count.

3. "13 TRANSACTIONS CARRY TWO MARKETPLACE MATCHES, SO THE MATCHER OVER-MATCHES." It does not, and
 it labels the difference. Confidence across all 437 rows: 375 medium, 62 high. In every one of
 the 13 pairs the reading is unambiguous -
 txn 95.18 | order ...85631 $94.85 medium | order ...62424 $95.18 HIGH <- exact wins
 txn 89.12 | order ...33023 $89.12 HIGH | order ...99699 $87.95 medium <- exact wins
 and each note names the delta in full: "ebay order 21-13250-62424 on 2025-06-30 for $95.18
 matched to a $95.18". The one pair with no winner is two Amazon orders at exactly $10.65 on
 adjacent dates - irreducible ambiguity, both correctly `medium`, and no rule could separate them
 without the receipt.

WHAT REMAINS TRUE from the earlier rounds, unchanged: 125 orders still carry no total and no items
because the emails matched for them are shipping notices that contain neither, and recovering a
multi-order confirmation's total onto individual orders is refused by design (P3002). 546 of 671
orders have totals.

METHOD NOTE worth keeping: each of the three suspicions was settled by one query that could have
come back either way - shared message ids, shared transaction ids, confidence labels. None needed a
code change. Cheaper than a fix, and it leaves the code alone.
