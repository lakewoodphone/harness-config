**L3604 · Porting a job means porting its data path - the app is the one source of truth for the database**

MEASURED 2026-10-11 on secratary-cloud, migration workstream 138.
dialpad-recording-gap.py and dialpad-transcript-gap.py both compute ROOT = Path(__file__).resolve().parents[1] and then DB = ROOT/'data'/'secretary.db'. From /opt/company that is /opt/company/data/secretary.db - 1,826,816 bytes, mtime 2026-10-11 01:18 - whose only dialpad tables are dialpad_sms_cache and dialpad_transcript_cache. Measured: sqlite3 /opt/company/data/secretary.db "select count(*) from dialpad_call_full;" -> Error: in prepare, no such table: dialpad_call_full. The live authority is /root/authority.db, 23,707,291,648 bytes: dialpad_call_full 13,995 rows, dialpad_media_file 7,069 rows, dialpad_sms_cache 135,421 rows (newest 2026-10-11T04:05:57Z). The app itself is already right: app/services/dialpad_harvester.py resolves settings.database_url in 18 places, and DATABASE_URL in /opt/company/.env is sqlite:////root/authority.db - confirmed independently because the company-api process had /root/authority.db open.
RULE. A script that hardcodes a second answer for 'where is the database' will be wrong again at the next move. Resolve it the way the app does (app.config.settings.database_url, with an env override so a monitor can point one run at a snapshot). A file that EXISTS at the wrong path is worse than a missing one, because 'the script is present and it runs' passes while every run silently does nothing.
SAME HOST, SAME SHAPE. dialpad-harvest-cron.sh and dialpad-sms-harvest-cron.sh open with REPO=/home/zabz/personal-secretary-mvp and exit 1 before doing anything, because that path does not exist on the cloud box. Before declaring a ported job healthy, run it and read where it actually wrote - not that it exited 0.
