**L12382 · A Stripe payment link stayed live for five days because the id was in metadata and the column was null**

2026-10-26, found incidentally while cancelling a stale payment intent on order WO2610200007 (Duestch). payment_pages row 168 had been stopped on 2026-10-21 with payLinkStopReason ORDER_PAID, but its stripePaymentLinkId COLUMN was null - the real id plink_1UT0PKLnlgYj1gmTOZyhzXdt existed only inside the row's metadata blob. So the page read as stopped while the Stripe payment link behind it was still ALIVE for five days, and could have been paid through. It only died today, as a side effect, because payment-cancellation.service.cancelPaymentTransaction reads the metadata fallback (metadata.stripePaymentLinkId) when the column is empty. Two transferable rules. (1) A STOPPED PAGE IS NOT A DEAD LINK: the page row records what our side believes, the Stripe link is a separate object at a separate vendor, and the only proof a link is dead is the deactivation call succeeding (stripeCancelled: true) - not payLinkStopReason, not a status of EXPIRED, not the page reading stopped. (2) ANY CODE THAT STOPS OR READS A LINK MUST FALL BACK TO metadata.stripePaymentLinkId: writing the id into the column is evidently not guaranteed, so a null column means unknown, not absent. That is the same shape as the refusal-dressed-as-a-negative trap: a null read as 'nothing there' when the value was somewhere else. Before trusting ANY statement that a customer cannot pay through an old link, cancel or deactivate it and read the vendor's own acknowledgement. Related: the customer-facing consequence here would have been a double payment on a debt we had already billed, which is the failure the one-live-link-per-debt rule exists to prevent.
