**L1630 · A backslash-u escape inside a SQL string literal is not a character - the trigram index built on it does nothing**

## L — A `\uXXXX` escape inside a SQL string literal is not a character, and an index built on it does nothing

**What was claimed.** A subagent reported that three GIN trigram indexes took free-text search
from **371.8 ms to 0.407 ms** (~900x) and handed over exact DDL, saying it could not apply them
because `db/**` was outside its file scope. It was a good report — measured, reproducible-looking,
explicitly scoped out, with the exact SQL. Exactly the kind of finding worth acting on.

**What is actually true.** None of it survives contact.

**1. The DDL builds an index on an expression that never matches the query.** PostgreSQL does not
interpret `\uXXXX` inside an ordinary string literal. Proven directly:

```
length('שָׁ') -> 3
length(regexp_replace('שָׁ', '[\u0590-\u05FF]', '', 'g')) -> 0 <-- strips EVERYTHING
length(regexp_replace('שָׁ', '[א-ת]', '', 'g')) -> 2
```

So `[\u0591-\u05C7]` is the literal character set `{ \, u, 0, 5, 9, 1, C, 7, - }`, not the niqqud
range. It matches any string containing a backslash, a `u`, or a digit. The reason it *looks* like
it strips niqqud is a coincidence: on a pointed Hebrew word it removes the letters too and leaves
bare consonants, which reads as success. The same class in the **TypeScript** query is fine, because
a JS regex literal `/[\u0591-\u05C7]/` is compiled to real code points before the driver builds the
SQL — so the query and the index are different expressions, and no error is raised anywhere.

**2. Even built on the correct expression, the index is not used.** Rebuilt on the literal
characters, the plan is still `Seq Scan … Execution Time: 464.284 ms`. The reason is structural:
the query is `regexp_replace(col) ILIKE '%term%'` — a **leading wildcard**, wrapped in a **function
call**. A `gin_trgm_ops` index can serve that shape only when the column expression is bare enough
for the planner to rewrite it. A real fix needs a stored stripped column, a `tsvector`, or
`similarity()` — not an index that is silently ignored.

**3. The numbers do not reproduce.** True production cost on `chumash_timeline`: **413 ms** for the
Hebrew-only branch (Seq Scan, 5,846 rows filtered) and **130 ms** for the three-way OR the app
actually sends. The reported baseline was 371.8 ms scratch vs 729.8 ms live — two different
databases compared as if one.

**The rules.**
- **A `\uXXXX` in SQL text is backslash and four characters.** Any schema, migration, index or
 constraint written from JavaScript-style escapes is silently wrong, and wrong in a way that often
 still produces plausible output. Use the literal characters or PostgreSQL's own `U&'…'` /
 `E'…'` form appropriate to the context (`U&'[\+0591-\+05C7]'` is itself rejected in this position,
 which is how I learned the rule).
- **If an index and a query are meant to match, the expressions must be byte-identical, and the
 only evidence that they do is an `EXPLAIN` showing the index being used.** Creating an index
 proves nothing; the plan is the proof.
- **A performance claim is not verified until both the "before" and the "after" are reproduced on
 the same data.** Here the "after" could not be reproduced at all, which is what exposed the whole
 thing. This is the same lesson as the turbopack incident: **reproduce the failure, then reproduce
 the fix, not just the fix.**

**What I did with it.** Reverted my `db/schema.sql` addition, dropped the broken index from the
scratch database, and verified production never received it (`NONE`). The finding is written up and
the real state recorded — 130–413 ms, noticeable but not severe, and **not** a silent wrong-answer
bug. Nothing was shipped. An index that does nothing is worse than no index: it looks like progress,
costs write time, and hides the real fix.
