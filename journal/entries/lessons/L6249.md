**L6249 · secratary-ts IS the frozen anchor, not the authority - and the company credentials table exists with 0 rows and no reader, so 'the customer credential record' has nowhere to point**

Two facts, both measured 2026-10-15, both of which changed what I was about to write down.

## 1. `secratary-ts` is the FROZEN anchor, not the authority

Measured by running `hostname` on each alias:

```
secratary-ts -> secratary 192.168.50.77 user zabz
secratary -> secratary 192.168.50.77 user zabz
secratary-cloud -> secratary-cloud 178.156.194.1 user root
```

`secratary-ts` and `secratary` are **the same box**, and `settings/machines/host-posture.tsv` lines 30–33 mark it **frozen**: *"Office box. Authority moved to secratary-cloud at the 05:43:36Z cutover; this box is the FROZEN ROLLBACK ANCHOR… Do not start, stop, mask, unmask, enable, disable or restart anything on it, and never create a second writer for the company database."* `secratary-cloud` is `writable` and is THE AUTHORITY.

I used `secratary-ts` for all of this session's git work — the shared `lpt-hub` clone at `/home/zabz/repos/lpt-hub`, three detached worktrees in `/tmp`, and staging a customer capture — believing it was the authority. **I did not read the posture file first, and I should have.**

**What that does and does not breach.** The posture text refuses *service state* and a second writer for the company database. It does not refuse filesystem use, and **the estate's own LPT tooling deliberately targets that box**: `lpt-write doctor` reports `authority secratary` and pushes its helper into `~/lpt-ops/`, and the `lpt-sync` shifts commit in the shared clone there. So reading and committing `lpt-hub` there is the house convention, not a breach — no service was started, stopped, masked, unmasked, enabled, disabled or restarted, and no company-database write was made.

**But /tmp on the rollback anchor is the wrong place for a customer credential, and that is exactly where one is now.** That part is a defect, and it is mine.

**The rule for next time, cheap and unconditional: run `ssh <alias> hostname` before using any box for anything that matters, and read `host-posture.tsv` before writing to one.** An alias is not an identity, and `secratary` is a prefix of `secratary-cloud`.

## 2. The company has a credentials table that has never held a credential

`/root/authority.db` (30163152896 bytes, 244 tables) contains:

```sql
CREATE TABLE credentials (
 id INTEGER PRIMARY KEY AUTOINCREMENT,
 service TEXT NOT NULL,
 key_name TEXT NOT NULL DEFAULT 'api_key',
 key_value TEXT NOT NULL,
 notes TEXT DEFAULT '',
 created_at TEXT NOT NULL,
 updated_at TEXT NOT NULL,
 UNIQUE(service, key_name)
);
CREATE INDEX idx_cred_service ON credentials(service);
```

**`select count(*) from credentials` → 0.**

A purpose-built store, empty, with no evidence that anything reads it. That is why every "keep it with the customer credential record" instruction in this estate currently has nowhere to point — and it is why the answer to *"where do device credentials live"* has been a shrug for at least as long as this case has existed.

**An unread store is worse than a file**, because a write into it produces the feeling of having recorded something. So the empty table is **not** yet a safe home for the Ullman recovery key. What has to exist first is one reader — something that, given a work order or a machine serial, answers *"is there a credential for this, and where"* — and only then does writing into it mean anything.
