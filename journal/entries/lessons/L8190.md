**L8190 · A decision in a row context does not leave the pending set**

OWNER DECISIONS WRITTEN INTO A ROW CONTEXT DO NOT LEAVE THE PENDING SET (measured 2026-10-18). ck sentinel computes actively_waiting as pending rows with no live deferred_until (sentinel.py ~3958-3995), and owner-queue.py list marks them !. Rows #492 and #516 each already carried an OWNER DECISION 2026-10-18 block inside their context field - neither had status or answer set - so the badge reported 2 decisions waiting on him, he read it, and asked what 2 decisions do you need from me. The count is not wrong about the table, it is wrong about the world. What writes status=answered is owner-queue.py answer ID --answer, and nothing else does. Rule: the moment he answers a queued row, run answer with his verbatim words in the same turn; it also mirrors them into journal decisions/ (D6785, D6786 here). THE OTHER HALF, and the more useful one: an answered row can still owe HIM a FACT rather than a decision - #492 needs the NJ Premier employer account number that nj-portal-state.json cannot separate from the sales-tax 392119233-000, and #516 needs whether the Auman WD SN740 is retired or wiped. Asking those as decisions is what makes the badge lie twice. File the work (task 29246, due 2026-10-25) and ask the fact once.
