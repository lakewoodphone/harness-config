**L8190 · Never rewrite a running shell script in place: bash reads by byte offset, so a live instance runs a mixture of both versions**

MEASURED 2026-10-18 on the authority, over three rounds. wake-dispatch.sh was patched four times while dispatchers were executing it, each time by truncating and rewriting the same inode (python io.open(path, w)). Bash does not load a script into memory; it reads incrementally by byte offset. Rewriting shifts every later line to a new offset, so a running instance executes whatever now sits at the offset it expects -- a mixture of old and new, including states no single version can produce. The symptoms were three lease kills that printed impossible diagnostics: reason=unknown, then decision=unset rc=unset, then hbrc=unset (a variable assigned on the line above the log). Three rounds of instrumentation chased this artifact; s75a even proposed an interrupt hypothesis, now retracted. Every one of those kills fell within a minute of an in-place edit. THE RULE: publish by atomic rename. Write path.new, bash -n it, then mv path.new path -- the new file gets a new inode, running instances keep the one they opened and finish on consistent code. Same for wake.py, sources, and anything cron or a shift may be mid-way through. A deployment that changes bytes under a live reader is not a deployment, it is a race whose failures look like defects in the code being deployed.
