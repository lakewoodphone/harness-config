**L3438 · Three transport and deployment traps: scp -O never exits on Windows, uncommitted harness-config on the authority is reverted by autosync, and pushing around the journal needs a scratch worktree**

Three facts that cost most of a session on 2026-10-09. Each is measured, each will bite again.

**1. `scp -O` transfers correctly to a Windows node and then NEVER EXITS.**
`secratary` → `zabz-yoga-1`: `scp -O` moved a 384 MB tar (764 members, valid, byte count exact) and was still running at **900 s**. Waiting for its exit wastes the whole timeout on every round, which over tens of gigabytes is the difference between an afternoon and a week. `push-dsh-sessions.mjs` already documents the same pathology for `ssh` ("does not reliably exit after the remote command completes, seen on both workstations") and solves it by killing the child the moment its reply parses. **The rule: poll the destination and end the transfer when the bytes are there, then verify the local size against the remote's — the arrived file IS the reply.**
Also: legacy scp needs **forward slashes**. `zabz-yoga-1:C:/Windows/Temp/x.tar` works; `zabz-yoga-1:C:\Windows\Temp\x.tar` fails with `protocol error: filename does not match request`.
And: a Windows OpenSSH target here has **no sftp subsystem** — plain `scp` dies with `subsystem request failed on channel 0`, so `-O` is not an optimisation, it is the only path.

**2. On `secratary`, an uncommitted file in `~/code/harness-config` is not a deployment — `autosync.sh` reverts it.**
Measured: a script `scp`'d to `/home/zabz/code/harness-config/scripts/` was back to its old content within the hour, while `ls` had shown the new size minutes earlier. Every round of "edit locally, copy, test" silently tested the OLD code, and the resulting errors pointed at the wrong layer three times. **To deploy anything to the authority's harness-config: `scp` it and then COMMIT it in that clone (`/home/zabz/harness-config` is a symlink to `/home/zabz/code/harness-config`).** Verify with `grep -c` for a string only the new version contains, never with `ls` timestamps.

**3. `git push` from a workstation harness-config is entangled with the journal; use a scratch worktree.**
`origin` is `/home/zabz/harness-config.git` on the authority, where a cron (`journal-commit.sh && autosync.sh`) commits every 15 minutes. `git pull --rebase` fails ("please move or remove them" over other sessions' untracked `journal/entries/*.md`) and `git merge --ff-only` fails ("Not possible to fast-forward"). Rebasing or resetting to fix it would sweep or discard other sessions' work — exactly pain P13. **The clean path: `git worktree add --detach <tmp> origin/main`, copy only your own files in, commit there, `git push origin HEAD:main`.** The dirty working tree is never touched. Note `origin` has two push URLs (the authority and a GitHub mirror); the mirror can fail without failing the push, so read the `refs` line, not the exit code.
