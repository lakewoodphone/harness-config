**L1535 · A ref is safe to delete when reachability proves it, not when the name looks like debris**

**A ref is only safe to delete when you can prove nothing else needed it -- and "nothing else" is a
reachability question, not a naming question.**

Measured 2026-09-15. The hub held 42 branches and the tempting move was obvious: thirty of them were
`zabz-audit-20260914-rN`, so a pattern delete would have removed them in one line. It would also have
been wrong by luck rather than by reasoning -- for five of the refs the branch *was* the only thing
keeping the commits reachable, and two of those five were from this session.

The classification that made it safe is a two-line idea: a branch is redundant when its tip is an
ancestor of another branch or of master, and unique otherwise. 42 -> 2 + 34 + 5. Only the first two
classes were deleted, and every sha was written down first, which converts "I was careful" into "it is
recoverable".

Rules:
- **Reachability, not naming.** Branch names are how humans remember; reachability is what git actually
 guarantees. Any cleanup of refs should be decided on the latter, and the tool should refuse when it
 cannot identify the trunk.
- **Record before you remove, in the same breath.** The keep-file is what makes a lossless operation
 *verifiably* lossless later, by someone who was not here.
- **Re-run the audit after acting.** It reported 6 branches and "nothing redundant" from a different
 machine, which is the only evidence that the operation did what it claimed.
