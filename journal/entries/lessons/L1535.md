**L1535 · In lpt_prod the column is camelCase unless the Prisma model says @map, and one table mixes both**

Evidence, 2026-09-15, PART-117: I wrote three SQL blocks by reading backend/prisma/schema.prisma and most statements failed. In lpt_prod:

- **camelCase in the database:** users.customerId, sessions.userId, sessions.customerId, sessions.isMfaVerified, sessions.deviceHash, sessions.expiresAt, refresh_tokens.isRevoked, security_events.eventType, customers.isActive, customers.stripeCustomerId, mfa_backup_codes.isUsed, user_devices.isTrusted, user_mfa_settings.isMfaEnabled.
- **snake_case in the database (because the model says `@map`):** users.google_id, google_email, google_linked_at, and the whole of `customer_login_codes` (destination_hash, code_hash, expires_at, sent_at, used_at, is_used, created_at, updated_at).
- users.phone and users.email are single words, so they give no hint either way.

**The same table mixes them:** `users` has `google_id` sitting next to `customerId`.

RULE: never write a query from schema.prisma. Ask the database once:

 SELECT table_name, string_agg(column_name, ', ' ORDER BY ordinal_position)
 FROM information_schema.columns WHERE table_schema='public' GROUP BY table_name;

That one query replaces the whole round of failures. The psql error does help if read — it prints `Perhaps you meant to reference the column "users.customerId"` — so the cheap fix is to read the hint, not to guess again.

**How to run a read-only query against production from a machine that is not lpt-apps** (verified 2026-09-15):

1. `ssh lpt-apps` — the alias resolves; key `~/.ssh/id_ed25519_lpt-apps`. (Direct `root@2.28.33.58` with the mesh key is refused.)
2. `scp x.sql lpt-apps:/tmp/` then `docker cp` it into `lpt-postgres`.
3. `docker exec lpt-postgres sh -lc 'PGPASSWORD="$(printenv DATABASE_URL | sed -E "s#.*://[^:]+:([^@]+)@.*#\1#")" psql -h 127.0.0.1 -U lpt -d lpt_prod -f /tmp/x.sql -q'`

Using the container's own `DATABASE_URL` avoids hunting for credentials, and `-f /tmp/file.sql` sidesteps PowerShell quoting entirely. There is no `postgres` role — do not try `psql -U postgres`.
