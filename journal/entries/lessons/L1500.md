**L1500 · A blocked-by-design state looks exactly like a broken state: find the switch at the path the code computes**

A blocked-by-design state looks exactly like a broken state: look for the switch, and read it

Three times in one session, the honest answer to "why does X never happen" was "because someone
turned X off", and each time the switch said so in its own contents:

 * `data/OWNER_SMS_KILL_SWITCH` -- "While this file exists, ALL owner SMS are blocked. The CEO
 was stuck in a loop sending 28+ URGENT texts." Created 2026-07-14 at the owner's request.
 I had already constructed "42 urgent alerts are being starved by a broken flush" and written
 most of that story down before checking.
 * H217's "the supplier watchdog does not exist" -- it existed and was scheduled (L1487).
 * P5's "work silently vanishing" -- 27 of 28 agents were live and nothing was stranded.

WHAT I DID WRONG, specifically: I looked for the kill switch at
`~/.personal-secretary/owner-sms-kill-switch`, found nothing, and concluded nothing blocked the
flush. The code's path is `data/OWNER_SMS_KILL_SWITCH` under the repo. A negative result from a
path I invented is not evidence about the system -- it is evidence about my guess.

THE HABIT: before reporting "X never happens" as a defect, (1) list the OFF SWITCHES for X and
check each at the path the CODE computes, not the path that seems natural; (2) read the switch's
own contents, because a hand-made switch often carries its reason and its date; (3) only then
look for a bug. And when the switch is deliberate, the finding is not "this is broken" but "this
is off, here is what is accumulating behind it, and whether to turn it back on is a decision, not
a fix".
