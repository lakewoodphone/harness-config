**L2786 · A source-scan guard can be satisfied by a comment; scan code lines outside the owning package**

A SOURCE-SCAN guard that matches raw file text can be satisfied by a COMMENT.

Measured 2026-09-28 on `kosher-filter-ai` (fleet kf0928/shot-verify). A merged WIP added a
"does production code call the entry point" scan for the dead MediaProjection consent path.
Three holes, each measured by reverting one file and re-running:

1. `MainActivity.kt` reverted to pre-merge (deleting the activity-result launcher, i.e. the only
 thing that can show the system dialog) -> both original scan assertions STAYED GREEN, because
 `ScreenshotConsent.kt` itself names `startWithConsent(` and `createScreenCaptureIntent(`.
2. Replacing the real `createScreenCaptureIntent()` call with a stub -> the scan STAYED GREEN on a
 KDoc sentence at `ScreenshotConsent.kt:17` that names the API.
3. A pre-merge tree with the consent object removed -> scan correctly FAILED (so it was not vacuous;
 it reported 133 sources).

Rule: a scan must (a) require the caller to live OUTSIDE the package that owns the API, and (b) match
code lines only - skip `//`/`*`/`/*` lines and strip a trailing `//`, ignoring `//` inside string
literals so `wss://` is not mistaken for a comment. Both added in
`ScreenshotServiceConsentWiringTest.mentionsCode`/`codePart`.

Corollary, same run: "granted consent persists where the service reads it" was the wrong question -
the service is handed the platform result as Intent extras and never reads the prefs mirror; the
prefs are the dashboard's view. Verify what the code reads, not what the doc says persists.
