**L2786 · A store-writing test command must carry SMS_INBOX_DB, or it files into the owner's live queue**

WHAT I DID WRONG (2026-09-28T17:23Z). While proving dedup I ran

 python3 /home/zabz/bin/wake.py flag --subject 'checkout-health:ch-test:20260928' \
 --prompt 'duplicate of an already-live row' --json

WITHOUT `SMS_INBOX_DB=/tmp/ch-test-store.db`. wake.py then resolved the LIVE
store (~/.sms-inbox/inbox.db) and filed a real row (id 67, source=manual,
state=new, result `capped` because the day was at 4/4 releases).

WHY IT DID NOT COST A SESSION, and this is measurement, not luck: a `capped` row
is never released while the cap is in force (wake-dispatch.sh logged
`daily cap reached (4/4) - not releasing` for every run from 16:25Z to 17:20Z),
the release counter did not move (wake_budget stayed 2026-09-28|4|1), and
`grep -c ch-test ~/.sms-inbox/wake-dispatch.log` = 0. Had I left it, it would
have been claimed after 00:00Z and spent one of tomorrow's four releases on a
prompt that said only "duplicate of an already-live row".

CLEANED UP at 17:24Z with a target-specific delete on the live store:
 delete from wake where subject='checkout-health:ch-test:20260928'
 and source='manual' and prompt='duplicate of an already-live row';
verified after: 0 rows matching 'checkout-health:%', 0 matching '%ch-test%',
budget still 4.

THE RULE: every test of a store-writing path sets BOTH overrides on the same
command line (`SMS_INBOX_DB` and, where relevant, `WAKE_PAUSE_FILE`), and the
command is echoed with the env in the transcript. `wake.py` has no verb that
withdraws a row, so the cleanup needed raw sqlite3 - a write the store's own
design otherwise discourages.

**L2786 · A source-scan guard can be satisfied by a comment; scan code lines outside the owning package**

A SOURCE-SCAN guard that matches raw file text can be satisfied by a COMMENT.

Measured 2026-09-28 on `kosher-filter-ai` (fleet kf0928/shot-verify). A merged WIP added a
"does production code call the entry point" scan for the dead MediaProjection consent path.
Three holes, each measured by reverting one file and re-running:

1. `MainActivity.kt` reverted to pre-merge (deleting the activity-result launcher, i.e. the only
 thing that can show the system dialog) -> both original scan assertions STAYED GREEN, because
 `ScreenshotConsent.kt` itself names `startWithConsent(` and `createScreenCaptureIntent(`.
2. Replacing the real `createScreenCaptureIntent()` call with a stub -> the scan STAYED GREEN on a
 KDoc sentence at `ScreenshotConsent.kt:17` that names the API.
3. A pre-merge tree with the consent object removed -> scan correctly FAILED (so it was not vacuous;
 it reported 133 sources).

Rule: a scan must (a) require the caller to live OUTSIDE the package that owns the API, and (b) match
code lines only - skip `//`/`*`/`/*` lines and strip a trailing `//`, ignoring `//` inside string
literals so `wss://` is not mistaken for a comment. Both added in
`ScreenshotServiceConsentWiringTest.mentionsCode`/`codePart`.

Corollary, same run: "granted consent persists where the service reads it" was the wrong question -
the service is handed the platform result as Intent extras and never reads the prefs mirror; the
prefs are the dashboard's view. Verify what the code reads, not what the doc says persists.
