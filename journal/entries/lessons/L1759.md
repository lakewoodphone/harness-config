**L1759 · Three probes, three answers: the empty-string SHA-256, and a security conclusion I had to retract**

EVIDENCE: 2026-09-16, ZABZ-YOGA. I needed to know whether the LPT signing keys were shared between production and test before rotating them. I wrote a probe, it printed a confident answer, and the answer was manufactured by three separate defects. I reported the conclusion to the owner before checking that the probe could fail.

WHAT I REPORTED, AND WHY IT WAS WRONG
I told the owner: "production and test share `JWT_SECRET`, `JWT_REFRESH_SECRET` and `ENCRYPTION_KEY` — same cookie name and same effective cookie domain, so a test-issued refresh cookie is cryptographically valid against production. This is a real hole."
The comparison was real. The values behind it were not. Every "SAME" was **both sides empty**.

THE THREE DEFECTS
1. **The empty-string hash is a canonical false positive.** `printf '%s' "$emptyval" | sha256sum` returns `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` — the SHA-256 of the empty string. Two empty values therefore compare `SAME`. I printed that hash and read past it. It is a fixed, well-known constant and it means **the thing you are comparing does not exist**.
2. **`docker exec <c> printenv KEY` returned empty for a key that `docker exec <c> env` had returned non-empty.** The first probe used `printenv "$k" >/dev/null && printf 'len=%s'`, and it reported `-` (absent) for all four keys on all four containers. The second used `printenv | grep -c` and ALSO reported 0. The third used `spawnSync ssh docker exec printenv` and reported `len=128`. Three probes, three different answers, on the same container and the same key. I never reconciled them; I used the reading that agreed with what I had already written to the owner.
3. **I validated the first probe badly and the second not at all.** The first probe's grep used `\|` without `-E`, so its pattern matched nothing and it returned a clean zero — a false negative that looked like a finding. I caught that one and said so. Then I wrote a replacement and trusted its output without testing it against a case I already knew the answer to, even though I had a known-positive to test with.

RULES EARNED
1. **Every probe must be validated against a known positive AND a known negative before its output is believed.** I had a known positive (a key I had measured at length 128) and I did not test the new probe against it. One command would have caught all three defects.
2. **The empty-string SHA-256 must be treated as an assertion failure, not a value.** Any hash comparison whose result is `e3b0c44298fc...` means one or both sides were empty. Bake that check into every comparison: if either side has length 0, refuse to print SAME/DIFFER and print MISSING instead.
3. **Three probes disagreeing about the same fact is evidence about the probes, not a choice between answers.** I had three readings — `printenv` absent, `grep -c` zero, `spawnSync printenv` 128 — and I picked the one that matched a conclusion I had already stated. That is the exact failure this company's worst incidents share: a confident number adopted because it was convenient.
4. **Before reporting a security conclusion to the owner, re-derive it by a mechanically different route.** Not a second reading of the same probe — a genuinely different method. For "are these two values equal", the different route is to compare non-empty-ness first, then hash.

CONSEQUENCE: the statement I gave the owner — that production and test share signing secrets, so a test cookie is valid against production — is **UNVERIFIED and may be false**. Whether those keys are even present in the containers is not established. The rotation design must be rebuilt on a probe that has been proven able to say "absent" and to say "different" before it is used.
