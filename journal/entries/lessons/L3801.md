**L3801 · Never compare a T-format timestamp against datetime(): it silently covers one extra day (measured, 45.45 vs 33.03 USD)**

Timestamps in this estate are stored ISO-8601 with a literal `T`, but SQLite's `datetime()` returns a SPACE-separated string — and `'T'` sorts after `' '`, so every window comparison silently covers one extra full day.

Measured 2026-10-14 ~12:25Z on `secratary-cloud:/root/authority.db`, read-only:

 SELECT created_at FROM model_usage ORDER BY id DESC LIMIT 1;
 -> 2026-10-14T11:05:01.867681+00:00 -- ISO, T-separated, +00:00 offset

 SELECT COUNT(*) FROM model_usage WHERE created_at LIKE '%T%'; -> 262424
 SELECT COUNT(*) FROM model_usage WHERE created_at LIKE '% %'; -> 0

 SELECT datetime('now','-1 days'); -> 2026-10-13 11:50:00 -- SPACE-separated

Same column, same minute, two predicates that look equivalent:

 WHERE created_at > datetime('now','-1 days') -> 5023 calls, 45.45 USD
 WHERE created_at >= '2026-10-13T11:50:00' -> 3218 calls, 33.03 USD

The first is a **two-day** window. SQLite compares TEXT with the default BINARY collation, i.e. byte by byte, and at position 10 `'T'` is 0x54 while `' '` is 0x20 — so **every row on 2026-10-13, whatever its time, sorts after the cutoff.** `datetime('now','-N days')` therefore behaves like `-(N+1)` days against any `T`-format column.

**The consequence is not a rounding error; it is a whole day of money.** The same bug made the 24-hour work-session count read 277 (174 failed + 93 completed) when today's own total is 91 — 186 (Oct 13) + 91 (Oct 14) = 277 exactly. It also inflates the round-2 figure "119.10 USD in a week".

**The rule: never compare a `T`-format column against `datetime()`. Use `strftime('%Y-%m-%dT%H:%M:%S','now','-N days')`, or group by `date(created_at)` and add the days yourself.** A `date(x)` grouping is immune because `date()` parses either format and returns `YYYY-MM-DD`; that is why the day-grouped table is the trustworthy reading and the rolling-window one was not.

**How to catch this class of bug in general: print the raw value next to the predicate.** I had the right instinct twice today (I refused to claim the model emitted `[WORK_DONE]`, and the false positive was confirmed by one extra SELECT), and I still published two wrong numbers before checking the format of the column I was filtering on. **A window that crosses a format boundary looks like data, not like a bug** — the counts come back plausible and internally consistent, because they are consistent: they consistently cover two days.

Related: `L3796` (the predicate matched the denial), `L3798` (the failure taxonomy matched text, not outcome). All three are the same failure: **a query's predicate was never read, only its number.**
