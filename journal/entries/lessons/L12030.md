**L12030 · Her laptop: the launcher picked the 0.1.5 tree, the config was newer than the running engine, and the open window held a dead token — three layers, all measured**

HER LAPTOP (DESKTOP-FGV6KMH, user cheve), 2026-10-21 ~02:20-02:45Z, on the owner's report that DSH "stopped working". Reached only through the exec API (https://yocheved-cmd.abletelsolutions.com, CF Access service token + X-Auth-Token) driven from ZABZ-TECH — she is NOT on the tailnet and nothing on the home LAN answers.

WHAT WAS ACTUALLY WRONG, three layers, each measured:

1. TWO INSTALL ROOTS, AND THE LAUNCHER CAN PICK THE WRONG ONE. `C:\Users\cheve\.dsh\engine` is 0.2.0-rc.2 (her running engine since Oct 17, correct). `C:\Users\cheve\dsh` is 0.1.5-rc.1. Her machine config `windows.json` carried NO `dshInstall`, so `dshw.ps1` resolved its own candidate list; on a restart it chose `C:\Users\cheve\dsh` (0.1.5), which then could not import `@deepseek-ai/dsh-agent-preset` — a 0.2.x package her profile rows name — and died at startup: `Cannot find package '@deepseek-ai/dsh-agent-preset' imported from C:\Users\cheve\.dsh\profiles\web`. Evidence: `3099-20261020-223454.err.log` (11,714 B, that stack), and her two engine processes on 22:34/22:35 with 0-byte logs before the fix. FIXED by setting `dshInstall: C:\Users\cheve\.dsh\engine` in her machine config (backup `*.bak-dshinstall` kept).

2. HER CONFIG IS NEWER THAN ANY SUCCESSFULLY-COMPOSED ENGINE. `profiles/web/cordis.patch.yml` mtime 2026-10-18T01:32:38Z, `settings.yaml` 01:28:43Z; the engine that had been serving since 2026-10-17T21:25:12Z loaded the profile BEFORE those files were written. Its own startup log records the failed reload: `hmr: config reload at %C failed ... profiles\web\package.json` then `HMR is disposed`. So the process and the disk disagreed for three days. This is the class `harness-sync` itself names ("Restart the profile for a settings change to take effect") and nobody restarts her engine, because the watchdog's `ensure` only starts it when the port is dead.

3. THE WINDOW SHE HAD OPEN CARRIES A DEAD TOKEN, AND THE LAUNCHER NEVER CHECKS. The web app authenticates with the `?token=` in the URL the engine printed at ITS start; `open.cmd` asks only "is a window open?" (`windowcount.ps1` = 1) and, when the answer is yes, calls `ensure` and prints "The assistant is already open". A window opened before the last engine restart therefore shows an auth error forever, and every later click confirms "already open". Measured: the window's title is "… — DeepSeek Harness", the engine serves 200/35,846 B on its CURRENT token, and `windowcount=1`.

WHAT I DID (all on her box, as her user through a temporary scheduled task, removed afterwards): set `dshInstall`; stopped only `node …@deepseek-ai…bin.js` processes; started one through `dshw.ps1 ensure` with her config; verified 0.2.0-rc.2 listening on 3099, page 200, and a real headless turn answering `ok`. A window still has to be reopened by her — closing it and clicking the shortcut is the whole action, because `windowcount` 0 is what makes the click open a fresh window with the current token.

MEASUREMENT NOTE THAT COST TIME: `GetWindowTextW` marshalled without `CharSet = Unicode` returns ONE character per title ("F", "*"), so a window-matching script saw no harness window and reported "closing 0". A P/Invoke that silently returns garbage is indistinguishable from "no window" — check that the enumerator can print a full title before acting on it.

ALSO FOUND, not caused by tonight: her repo checkout is FROZEN — the hourly updater logs `LOCAL COMMITS EXIST HERE - c903c79aba7e… is not an ancestor of d17d4f1e…; nothing was changed`, so `harness-sync` re-applies the same config every hour and nothing new ever lands. Her `research-offload` MCP row also still points at `C:\Users\cheve\code\harness-config\packages\research-offload\server.mjs` (exists) while the row's *declared* bundle is absent, and an `mcp-fetch-server` child dies with EPIPE in her err log.

OPEN, for the next session: (a) the launcher must validate the open window's token against the live engine and reopen when it is stale — that is the durable fix for "DSH stopped working" after every restart; (b) `dshw` must refuse (or at least print) an install root that cannot resolve the profile's rows, instead of silently picking the older tree; (c) her delivery is stalled by local commits and needs a decision on rebasing them; (d) `profileMode shared` + 6 recorded slots vs 1 real window is bookkeeping drift worth one pass.
