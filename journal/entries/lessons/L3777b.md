**L3777b · A shared checkout can switch branches under you mid-session - check before committing, verify after pushing, recover in a worktree**

**L · A shared checkout can switch branches under you mid-session, so `git commit` lands on somebody else's branch - check before you commit, verify after you push**

WHAT HAPPENED, 2026-10-13, on the authority. I made three commits in the shared checkout at
`/root/code/harness-config` and pushed all three to the canonical remote (`vault`) successfully. Then a
fourth commit -- the model retry-budget fix -- **would not push**: `! [rejected] main -> main
(non-fast-forward)` three times in a row, with the error hint "a pushed branch tip is behind its remote
counterpart", even though `git merge-base --is-ancestor <remote-head> HEAD` reported YES and the remote repo
itself confirmed the ancestry was fine.

THE CAUSE, and it was nowhere near the remote: **the shared working tree had been switched onto another
session's branch.** `git symbolic-ref HEAD` returned `refs/heads/hk/28-refresh-deployed-sources-20261013`
while `git rev-parse main` pointed at an unrelated, diverged commit (`c6d329d`). So `git commit` had put my
work on *that* branch, not on `main` -- and `git push vault main` was pushing the stale local `main`, which
genuinely was not a fast-forward. Three pushes and a lot of remote forensics on a problem that was entirely
local.

Worse, it is silent: `git commit` prints a normal success line and says nothing about which branch it went to.
Only `git branch --contains <sha>` reveals it: `* hk/28-refresh-deployed-sources-20261013`.

THE RULES, so the next session loses no time:
1. **Before committing in a shared checkout, read `git branch --show-current`.** If it is not the branch you
 intend, you are about to commit onto someone else's work. This is the same failure class as pain P13
 (concurrent sessions share one repo).
2. **After pushing, verify the commit is actually on the published head** -- not that the push printed ok:
 `git fetch vault main && git merge-base --is-ancestor <sha> vault/main`.
3. **When a push is rejected non-fast-forward and the ancestry really is an ancestor, stop looking at the
 remote: the odds are you are on the wrong local branch.**
4. **RECOVER IN A SEPARATE WORKTREE, never in the shared tree.** This worked first try and disturbed nobody:
 `git worktree add -b fix/<name> /root/<name> vault/main` then `cherry-pick <sha>` then
 `git push vault HEAD:main`. It rebuilds the change on the *published* main, so the push is a clean
 fast-forward (`cec2e1d..e707183`). Then `git worktree remove` and delete the branch.
5. **Do not "fix" the shared checkout's local `main`** to make a sync sentinel go green while other sessions
 are active. My work was published and correct; local `main` being diverged is the shared-checkout problem,
 and force-moving it under a live session is how work gets destroyed.

EVIDENCE: `git push vault HEAD:main` -> `cec2e1d..e707183 HEAD -> main`, then
`git merge-base --is-ancestor e707183 vault/main` -> true. The three earlier commits from the same session
(`1a189c3`, `021c3c6`, `310ce87`) were already ancestors of `vault/main`, so nothing was lost -- verified,
not assumed.
