**L6219 · A future-dated message silently kills a timestamp watermark**

Evidence: 2026-10-14, building an incremental Gmail->usearch adapter for /root/mail-archive/chevedy
(25,889 messages). The adapter advanced its watermark with max(internal_date) over everything it emitted.

One message in that mailbox is deliberately FUTURE-DATED: id 1e98518c20dfdd26, subject "Happy tenth
aniversary", header date 2036-08-16. The watermark therefore jumped to 2036-08-16, so every
subsequently arriving message - all of them dated 2026 - compared as OLDER than the watermark. The
sync would have emitted nothing, forever, while still exiting 0. Nothing would have looked broken:
the cron reports rc=0, the state file says last_ok, and the index simply stops growing.

Fix applied in unified-search/adapters/mail/sync.py: the watermark only advances on messages whose
internal_date <= now; a future-dated message is re-emitted every run instead, which is idempotent
because the document id is stable.

RULE: any high-water mark derived from a timestamp must be clamped to "now", and any source must be
assumed to be able to contain a date in the future. Same shape as this estate's repeated "a refresh
job cannot report that it has stopped running" failures - the fix has to be that the watermark
cannot be poisoned, not that someone remembers to look at it.
