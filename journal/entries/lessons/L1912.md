# LPT customer texts are signed `- Daniel` — the runbook said the opposite, and it cost us unsigned sends

## The rule
Every customer text from Lakewood Phone & Tech goes out **signed `- Daniel`**. The send script
appends it automatically from `agent_sms_signature` (`personal-secretary-mvp/app/config.py` L399,
default `Daniel`). **Pass no signature flag.** `--no-signature` only on an explicit per-message
owner instruction; `--signature <name>` never.

## What went wrong
`lpt-hub/docs/customer-operations/CUSTOMER-SMS-RUNBOOK.md` §0.3 read "No signature" and §3 said
"Always pass `--no-signature` unless the message is genuinely from Daniel". Every agent session that
followed the runbook therefore stripped the sign-off on purpose. Owner, 2026-09-17, verbatim:
*"make sure first it has the daniel signature, some messages sent yesterday from you didn't have it."*

Corroborating trail (the same choice made independently in three places): the Halon draft was
previewed `--no-signature`; `cases/sony-video8-hi8-8mm-players-levi-7325754823-2026-09-16.md`
records "Preview verified 2026-09-17 — no signature appended"; the runbook itself was the
instruction source for both.

The shop's own convention was never in doubt: dozens of case files record customer SMS signed
`- Daniel` (`wajsfeld-charging-port-7322283232-2026-09-09.md`,
`debban-pc-compromised-7329663107-2026-09-09.md`, `pixel-6a-bloch-2026-09-02.md` — "Use `Daniel`
sign-off"), and the append-only case-file bodies carry the sign-off verbatim.

## The fix (applied 2026-09-17, pushed `5d8b9ced8`)
- Runbook §0.3, the §1 fast-path commands, the §2 voice table and the §3 trap row all now say: the
 signature is the default, absent only on an explicit owner instruction.
- The Levi case's unsent draft carries an inline correction so the next session re-previews without
 the flag.
- `scripts/send-lpt-sms.ps1` was checked and is fine — it only adds `--no-signature` under an
 explicit `-NoSignature` switch. The defect was documentation, not code.

## The transferable lesson
When an agent's output violates what the owner plainly wants, check the instruction file the agent
was following before hunting for a code bug. Here the "trap" the runbook warned about (a message
signed as a real staff member) was itself the wrong call, and the guard it installed became the
defect. A rule written from one incident, without checking the corpus of real sends, can invert the
house convention for every session that reads it.

## Evidence-date caveat worth keeping
In `dialpad_sms_cache`, `created_at` is the **harvest** time, not the send time — rows for different
customers share the same second (five rows at `2026-09-16T17:31:2x`). Only the message id returned by
the send itself dates a send. Do not build a send chronology from that column.
