**L1772 · A control that blocks a channel also blocks the owner's own request**

`data/OWNER_SMS_KILL_SWITCH` on secratary blocks ALL owner SMS. Created 2026-07-14 at the owner's request after the CEO looped and sent him 28+ "URGENT" texts. Re-enabling requires deleting the file and restarting. `sms_service.py:718` raises it; `owner_sms_kill_switch.py` resolves the path (env override `OWNER_SMS_KILL_SWITCH_PATH` for tests); `autopilot.py:245` surfaces it.

CONSEQUENCE OBSERVED 2026-09-16: the owner asked, in plain words in the live conversation, "text my personal number the short list". The send was refused. The list never reached his phone.

THE DEFECT, and it is a design defect not a bug: the switch was built to stop UNSOLICITED AUTONOMOUS spam, but it is implemented as a blanket channel block, so it also stops a message the owner explicitly requested seconds earlier. A control should encode intent (autonomous vs owner-requested), not merely a channel. A blanket block silently converts "we must not spam him" into "we cannot reach him at all", and the second is not what he asked for.

The correct fix is additive: keep autonomous owner SMS blocked, and allow a send that carries an explicit owner-requested marker in the current conversation. Do NOT delete the switch - it was earned, and the failure it prevents is real.

Related design consequence, and it accidentally vindicated an earlier choice: because owner SMS is dead, any reminder that must reach his phone CANNOT use SMS. The monthly anniversary reminder was put on Google Calendar (W188), which is unaffected. Anything important for this owner should prefer Calendar/phone notification over SMS while this switch stands.

Also worth knowing: `assistant_chat.py:3142` states send_sms is owner/personal-assistant ONLY - customer messages must use `dialpad_send_sms`. `gv_send_sms` (Google Voice) is a separate channel; using it to deliver an owner SMS would circumvent this control's purpose, so do not.

Evidence: kill switch read on secratary 2026-09-16 19:58 UTC (file mtime Jul 20 17:57), refused send at 19:57 UTC for +17325691594.
