**L3446 · A kernel DNS capture with a dead upstream makes a node a non-worker, and it re-arms itself three ways**

## L — A kernel-level DNS capture with a dead upstream turns one machine into a non-worker, and it re-arms itself

MEASURED 2026-10-09 on ZABZ-TECH. Every mesh child dispatched to that node died with
`dsh: TRANSPORT: DeepSeek Messages transport failed` and produced no report. The
cause was not the mesh and not the node's hardware.

WHAT WAS INSTALLED (built from C:\Users\ezabz\code\kosher-filter-ai, `lpt-filter-ai`):
 KosherFilterService C:\Program Files\KosherFilter\KosherFilterService.exe Running AUTO_START LocalSystem
 KosherFilterDnsRelay C:\Program Files\KosherFilterRelay\KafDnsRelayService.exe Running AUTO_START LocalSystem
 WinDivert driver C:\Program Files\KosherFilter\WinDivert64.sys Running

THE MECHANISM, from its own config:
 KosherFilter\appsettings.json DnsInterception.Enabled=true, Filter="udp.DstPort == 53 or udp.SrcPort == 53"
 KosherFilterRelay\appsettings.json UpstreamHost=2.28.33.58, UpstreamPort=1080 (a SOCKS5 relay on a Hetzner box)
So EVERY DNS query was captured at the kernel and tunnelled to an upstream that was
not answering. The relay's own event log, every few seconds:
 relay-err: OSError: [WinError 10051] ... unreachable network
 Relay child exited with code 1; restarting in 5s.

MEASURED SYMPTOM on that node: www.google.com, microsoft.com, cloudflare.com,
tailscale.com, api.deepseek.com, mcp.jina.ai -> ALL ENOTFOUND; a query straight at
1.1.1.1 and 8.8.8.8 -> both FAIL. DNS was not filtered, it was GONE. That is why a
fresh child process could not reach the model API, and it is why a placement fix
CANNOT be validated while a node's DNS is broken.

WHY DELETING IT NEVER STUCK (the owner had done it ~5 times), three independent
re-arm mechanisms, all shipped behaviour:
 1. windows/install-dns-relay-service.ps1:99 sc.exe create ... start= auto
 2. the same script:101 sc.exe failure ... actions= restart/5000/restart/5000/restart/5000
 3. windows/FilterService/Tamper/ServiceRestarter.cs + ManagementWmiWatcher.cs (it watches for its own removal)
Deleting files removes none of those. The correct inverse is the repo's own
windows/scripts/uninstall-service.ps1: stop, wait, sc delete, then -RemoveFiles.

RULE TO KEEP: a boot-start service plus a tamper restarter is not removable by
deleting files, and a resolver that accepts TCP/53 while failing every public query
is not "filtered", it is broken. Check which machine can resolve before blaming the
mesh.
