**L3732 · A zero from a source that CANNOT hold the answer is not a negative: the estate missed two filed tax returns because it searched an inbox index that does not cover the personal mailbox**

THE ESTATE SEARCHED AN INDEX THAT COULD NOT HOLD THE ANSWER AND READ THE ZERO AS A NEGATIVE.
Found 2026-10-13 on ZABZ-TECH while answering the owner's question "what is this 2025 returns
deadline, for what and where".

THE CASE. `/opt/company/docs/finance/2025-tax-filing-guide.md` carried a banner, flagged
2026-09-22, reading UNVERIFIED CLAIM: the file says the 2025 federal and NJ returns were FILED, but
a search of the authoritative database on `secratary` (`email_triage_log`, `memories`,
`plaid_transactions` in `data/secretary.db`) held ZERO FreeTaxUSA acceptance, receipt or account
emails. The banner concluded the contradiction STANDS. On 2026-10-13 a tax pipeline created that
morning (`/root/bin/tax-deadlines.py`, cron 06:17, feeding `tax-deadlines-to-queue.py`, cron 06:23)
turned the same reminder into owner-queue row #475, a critical two-day clock, on the strength of
that banner.

THE FACT. Both returns were filed and ACCEPTED on 2026-07-19. Two emails, both in
eliyahuzabrowsky@gmail.com, found in one search:
 Federal support@support.freetaxusa.com -> 2026-07-19 13:34:27 UTC, Gmail 19f7a95e50636f56,
 "Update: 2025 Federal Tax Return Accepted" - "Congratulations! The IRS has accepted
 your tax return."
 New Jersey same sender -> 2026-07-19 16:01:29 UTC, Gmail 19f7b1c7e2537d5b, "Update: 2025 New
 Jersey Tax Return Accepted" - "The New Jersey Division of Taxation has accepted your
 New Jersey tax return."
Corroborated the same day by the FreeTaxUSA account creation (03:14 UTC, 19f785e0ee34fe02), order
receipt 19146146 in ezabz68@gmail.com (19f78c58ec68c1a5), and the NJ filing fee 15.99 in the
accounting ledger (authorized 07-19, posted 07-20).

WHY IT WAS MISSED, AND THIS IS THE WHOLE LESSON. `email_triage_log` on the authority is an index of
what the triage pipeline happened to ingest. It does not contain the owner's personal Gmail. So the
search asked a source that CANNOT hold the answer, got zero, and reported the zero as evidence of
absence - and then a second system built on that report turned it into a critical owner question
with a deadline. Two independent-looking artifacts, one wrong belief, and the error compounded
because the second one cited the first as if it were a measurement.

THE RULE. An empty result is a refusal, not health, and the test is not "did I search" but "could
the thing I searched have contained it". Concretely, before treating a zero as a negative:
 * name the source and say what it covers - and if it is an index, a cache, a replica or a
 triage log, say so, because all of those are narrower than the thing they copy;
 * if the source cannot hold the answer, the correct report is NOT "not found" but "not
 searched" - those are different sentences and must never be the same one;
 * search the primary source before recording a contradiction. Here that was five Gmail accounts,
 of which the answer was in the second one tried. Five connected accounts all reachable
 through the same tool; there was never a reason to ask only the index.
 * and when a report feeds an alert or a queue row, the alert inherits the report's uncertainty -
 a critical priority does not launder a weak measurement.

WHAT WAS CORRECTED, so the next session does not re-derive any of it.

 banner (the banner itself says "do not edit this line; add a new dated line below it"), with
 both message ids, both verbatim acceptance sentences, the corroborating evidence, and the
 reason the earlier search failed. Committed 47c72b2d in /opt/company.
 * owner-queue #475 resolved with the evidence, not dismissed.
 * Row #481, the pipeline's duplicate of the same obligation, was already resolved.

is a primary source, whereas #475 rested on an index that could not. A portal reading is credible
evidence of non-filing; an absent email in a triage log is not.
