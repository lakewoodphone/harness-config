**L1669 · Four reconciliation rules earned 2026-09-15: a 'broken tool' is usually a wrong expectation; a record's link IS the idempotency guard; two tables in one DB are not one corpus; 'duplicate' rows can be two halves of one event**

**Four rules earned in the 2026-09-15 production reconciliation. Each one cost something real today.**

**1. When a test says the tool is broken, verify the EXPECTATION first.** Axis E reported that this
laptop's Python `re` module was broken: `re.match(r"^WO\d{6}\d{5}$", "WO2512190001")` returned None.
That is true — and it is CORRECT. `WO2512190001` is a 12-character string; the pattern requires
`WO` + 6 digits + 5 digits = 13. `WO26091512712` (13 chars, 11 digits) matches. I tested the same
pattern on ZABZ-YOGA (3.12.10) and secratary (3.14.4): identical, correct behaviour on every case,
including the FORBIDDEN/WHERE_REQUIRED regexes my own apply gate depends on. The module was fine; the
test string was not a valid WO under the pattern being tested. Axis E caught a real symptom honestly
(it got a bogus "491 orders do not match the WO format") and handed me the wrong cause with
confidence. **A broken-environment theory is the most seductive wrong answer there is**, because it
explains the observation and requires no further work. Test the instrument against a known-good input
before you blame it.

**2. A record's link back to what it created IS the idempotency mechanism — verify the LINK, not just
the row.** The push tool created production order WO26091512714 for the Chaya Brodie case, then
refused its own in-place write-back (`ERROR: ... the edited text did not verify ('references')`), so
`references` stayed null. The order existed; the guard that prevents a second one did not. Re-running
the push would have created a duplicate order for the same customer — in the customer-facing record of
record. Three sibling pushes wrote their link and were safe; the log line for the fourth said
`Push complete!` anyway. **"The write succeeded" and "the operation is complete" are different
claims**, and a tool that logs success after a failed bookkeeping step will hide it. Check the artifact
the guard actually reads, and re-run the guard to prove the repair.

**3. Two tables in one database are not one corpus until you prove it.** The brief I wrote called
`call_log`/`sms_log` a stale copy of the Dialpad tables and proposed backfilling it. Axis B measured
and refused: `call_log.to_number` is `+17324447361` ×50 — the secretary's **own AI line** — while the
Dialpad business line is `+17326552355`, and `sms_log.id=882` says so verbatim in its own error text
("*LPT customer SMS = Dialpad only*"). A backfill would have **conflated** two telephone lines, making
every reader confidently wrong instead of visibly empty. The ID-level intersection with every Dialpad
id column was **0 of 70, four ways**. **"This is a stale copy of that" is a hypothesis, not a
description** — and the cheap way to test it is a join on identity, which here returned zero.

**4. Rows the index calls duplicates may be two halves of one event that each hold something the other
lacks.** `.fsearch` publishes `collapsed_duplicates: 12029`, and the obvious reconciliation is to
delete them. Axis D diffed 36 columns across all 2,275 call pairs: **0 pairs have byte-identical media
columns**, 1,382 have each leg holding a recording the other does not, and 99.9% are joined by an exact
operator/entry-point call id — they are the **operator leg and the admin leg of one conversation**.
2,282 of the collapsed rows are whole call rows each holding a distinct recording. A delete would have
destroyed customer audio while the report said "duplicates collapsed". For `dialpad_sms_cache` the same
question resolved the other way (2,744 groups / 5,488 rows, differing ONLY in `session_id`, **0 groups**
with differing body text) — so the honest output is a **view** for both, and a delete for neither.

**Bonus, same day, same family:** an inherited alarm — *"reconciliation has failed every run since
2026-08-23, 33 consecutive 600 s timeouts"* — was **false**: 22 runs succeeded in that window, the
timeouts are a configured 1500 s bound, and the genuinely dead trigger is `autopilot` (nothing since
2026-08-20). A prior session's alarming finding had been copied forward for hours. Re-measure an
inherited alarm before repeating it.
