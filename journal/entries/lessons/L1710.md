**L1710 · Journal append was slow because of pre-write work, not the lock: legacy absorption on every write plus 15303 pathlib.relative_to calls**

## What looked like the lock was actually pre-write work
`journal.py append` was blamed for 41-98 s critical sections. Profiling (`cProfile -s cumtime`
on `append --dry-run --no-fetch`) on 2026-09-16 showed the split for a 14.9 s append:

| Where | Cost |
|---|---|
| `absorb_all` (legacy absorption, run before EVERY write) | **12.6 s** |
| -> `legacy_candidates` 12.2 s, of which 7 calls to `max_number` at 11.7 s | |
| -> 15,303 `pathlib.relative_to()` calls | **7.2 s** |
| -> `tree_signature` walking all 15,303 files in `entries/` | 8.2 s |
| the append itself | ~0.3 s |

So the lock was innocent: the work *inside* the lock was a full-tree migration scan plus a
pathlib-heavy tree walk, and under a fleet those queued into the 41-98 s that the lock audit
measured.

## Three changes, all measured
1. **`_rel_of` fast path** — a precomputed `str(JOURNAL) + os.sep` prefix instead of
 `pathlib.relative_to` (15,303 calls, 7.2 s). Verified equivalent: 120 sampled paths, 0
 mismatches against the pathlib result.
2. **`legacy_signature()`** — the write path's cache key (`_legacy_sig`) used `tree_signature()`,
 which hashes every file in `entries/` to build `entries_sig` -- a value the write path never
 reads. The new function hashes only `log/**` and the v1 flat files. `tree_signature()` is
 unchanged for callers that genuinely need the entries signature (cache freshness).
3. **`absorb_if_due()`** — legacy absorption is a migration task, not per-append work. It now
 runs only when the stamp is absent, older than 6 h, or a legacy SOURCE changed
 (`log/**` / `FLAT_FILES` only), or is forced (`--absorb`, `JOURNAL_ABSORB=always`).

**The third one taught its own lesson.** The first version of the "did a source change?" check
globbed *every top-level file in the journal* -- which includes the tool's own outputs
(`aliases.tsv`, `entries.tsv`). So every append looked like drift and re-ran the scan it was
supposed to skip (measured: 2.5 s of a 2.7 s dry-run). Narrowing it to the actual legacy sources
fixed it.

## Result
| | before | after |
|---|---|---|
| `append --dry-run --no-fetch` | 14.9 s (cProfile total) | **2.7 s** |
| steady-state real append | 10.4 s dry-run; 31.7 s+ real under load | **2.2-2.8 s** (3 samples) |
| lock critical section under a fleet | 41-98 s (measured earlier) | work inside is now ~2.5 s |

`journal.py check` after all of it: **0 errors**, 51 warnings (the same 51 that pre-existed).
