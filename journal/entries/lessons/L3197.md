**L3197 · Two supervisors booting one engine is the whole yoga error; guard it with a named mutex, not a smarter retry**

ZABZ-YOGA, 2026-09-30 19:08-19:13: the owner clicked the Desktop DSH shortcut and got a raw Node stack trace ending in EADDRINUSE 127.0.0.1:3099. Six consecutive failed boots, each one a 14 KB stderr dump. Root cause was NOT a broken plugin tree, a missing package, or a dead engine: FOUR supervisors call dshw.ps1 ensure on a timer (Engine Watchdog 1m, Engine Vitals 5m, Window Fleet Watchdog, plus the shortcut itself) and none knew about the others. When the engine was down they each waited the same 40s and the loser died on the port. The engine was simply being started twice. FIX (multi-window/dshw.ps1, Ensure-Engine): a machine-wide named mutex Global\dsh-engine-ensure around the decide-and-start step, an abandoned-mutex catch so a killed supervisor cannot wedge the fleet, a re-probe under the lock, and the boot loop moved to Invoke-EngineBoot so Ensure-Engine can own the lock across returns. The second supervisor now WAITS and reports the winner's result instead of crashing. LESSON: when a launcher is driven by several independent timers, 'is it up, and if not start it' is a critical section; a retry policy cannot fix a race. Also: the stack trace the owner sees is the worst possible surface for this class - it looks like a broken install.
