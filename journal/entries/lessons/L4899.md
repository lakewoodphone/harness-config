**L4899 · /root/bin revert: five job mechanisms eliminated with commands, and the remaining explanation is a concurrent session - do not re-check them**

Another session reported that `/root/bin/cfo-ask.py`, `charge_msg.py` and `merchant_resolve.py` were reverted to their pre-change originals (mtimes 2026-10-14, every marker gone) while its other fixes survived, and that "no job admits to it". It checked crontab, cron-script-guard, the /opt/company canonical copies and journald. **I checked the five mechanisms it did not, and all five are eliminated with a command:**

1. `lpt-deploy-drift.py` (cron `:17` hourly) -- **read-only**. `grep -nE "shutil\.copy|write_text|write_bytes|os\.replace|restore"` matches only `open(STATE, "w")`, its own state file.
2. `assert-bin-matches-repo.py` -- **assert only** (same grep, no output) and **not scheduled at all** (`crontab -l | grep -c assert-bin-matches-repo` -> 0). It also cannot even run from here: `ssh secratary-lan` -> name resolution failure, a stale alias.
3. A canonical-copy restore from `scripts/deployed/bin/` -- **the three files are not in the canonical copy**: `cfo-ask.py`, `charge_msg.py`, `merchant_resolve.py` all report `canonical=ABSENT`.
4. `prune-backups.sh` (cron 05:45) -- its own header: "deletes ONLY directories whose name it can date, under the one ROOT it is given", i.e. `/var/lib/authority-snapshots`. It does not touch `/root/bin`.
5. `disk-guard.py` (cron `*/15`) -- its own header: "delete, move or truncate anything. It measures and reports."

WHAT IS LEFT: `/root/bin/*.bak-*` siblings exist for all three (mtimes 2026-10-11 to 2026-10-14), so a restore-from-backup is the right SHAPE -- but no scheduled job performs one. **The remaining explanation is another concurrent AGENT SESSION.** Several ran here in the same hour (three other sessions committed in this repo while I worked), and a session that treats a `.bak` as the good copy, or that rolls back a change it judged wrong, is indistinguishable from a job in the file mtime.

THE TEST THAT WOULD SETTLE IT, for the next session: put an inotify watch on the three paths (`inotifywait -m -e close_write,moved_to /root/bin/cfo-ask.py ...`) and let a day pass, or grep the concurrent sessions' transcripts for a write to `/root/bin`. Do not re-check the five mechanisms above; they are done.

THIS IS THE P13 FAMILY, EXTENDED. P13 is "concurrent sessions share one repo and `git add -A` sweeps each other's work". This is the same defect one layer out: concurrent sessions share DEPLOYED files that no repo owns, so a revert leaves no trace in any commit. The corrective pattern is the one this round's deploys used -- stage, `py_compile`, back up, `cmp`, and COMMIT in the repo that owns the file -- because a change that exists only in a deployed path has no history to be recovered from.
