**L1463 · ps_action save_memory silently drops category/importance/type/tags arguments — verify the row in secretary.db**

**Evidence:** 2026-09-14, `ps_action save_memory` was called with `category=owner_context`,
`importance=8`, `memory_type=fact`, `tags_json=[...]`, `agent_id=orchestrator`,
`source=owner_photo_record`. The action returned `{"success": true}` and wrote memory id **19173**
with `importance=3`, `memory_type=observation`, `tags_json=["owner_context","from_chat"]`,
`source=owner_context`. Every field I cared about came back with a default.

**Rule:** a success response from an action is not evidence that its parameters took effect. After any
write through `ps_action`, read the row back (`sqlite3` read-only on `data/secretary.db`, which is
WAL so a read-only connection sees committed writes) and correct it in place if needed — the write
itself is safe: the table is WAL, `sqlite3.connect(path, timeout=30)` + `commit()` is fine while the
service runs. Re-read in a **fresh** connection to prove durability. Same suspicion applies to any
generic `create_task`/`save_memory`-shaped action: check what actually landed, including
auto-"downgraded priority" notices.
