**L1915 · Never pass a journal body through a PowerShell here-string - a backtick arrives as ESC; use --body-file**

**Never pass a journal body through a PowerShell here-string. Write the body to a file and use `--body-file`.**

Measured 2026-09-17, writing four entries (`D254`, `L1914`, `P247`, `H474`) from `pwsh` with `@"..."@`:

- **A backtick is PowerShell's escape character, not markdown.** `` `e9bc02082` `` in my text arrived in the file as **ESC (0x1b) + `9bc02082`**: the opening backtick was consumed escaping the `e`, and the closing backtick was consumed escaping the following `.` and `;`. Two entries (`H474` lines 10 and 30) went into the journal with literal ESC bytes inside the text, and `check` could not see it — a corrupt byte is not a malformed entry.
- **Three of the four entries then failed `check` with `metadata sha=... does not match the body`.** I could not reproduce the recorded sha from the file with any of the candidates I tested (heading with and without the id prefix, `\$` unescaping, ESC removal), so the append path computed the sha over something other than what it wrote and **I have not identified the mechanism** — that is an open question, not a solved one. The repair that made `check` green was to rebuild each file with the tool's own `journal.entry_bytes()`, which is the definition of a well-formed entry, so marker, heading, normalised body and sha are canonical by construction.
- The rule costs nothing to follow: `--body-file <path>` where `<path>` was created by the `write` tool, which writes the bytes you actually typed. `--body` through a shell is the only path that can silently mutate your words.

Related, and the reason this was caught at all: `journal.py check` exits non-zero on a real error, and the error it reported was mine to fix before the session ended. An entry that is both corrupt and sha-mismatched is caught by the sha half; an entry with only the ESC corruption would have been caught by nothing, which is the part worth remembering.
