**L1701 · MCP servers cost four processes each and their discarded generations were never reaped - direct node plus a reaper**

## The waste, measured on ZABZ-YOGA (2026-09-15, engine up 28 h)
Every MCP server ran behind four process layers — `python launcher -> cmd.exe -> npx-cli.js ->
cmd.exe -> server` — and the engine held **three complete generations of every server at once**
(3 x {firecrawl, context7, jina, fetch, playwright}): 9 `npx` shims, 15 `cmd` shims, ~1 GB, all
alive at the same moment. The independent source audit put the reclaimable total at ~2.1 GB of
server residue plus ~0.9 GB of `npx-cli.js` shims.

Two independent causes, both established by reading code, not by inference:
1. **`npx` as transport.** On Windows `cross-spawn` wraps a `.cmd`, so one server costs four
 processes, and `npx-cli.js` (~100 MB) stays resident for the server's whole life. npm reuses a
 cached install **only when the name and the exact version match** — so `@latest` forces a
 registry round trip on every start (measured here: `npx --version` 4061 ms, `node -v` 964 ms
 under load).
2. **MCP children are spawned by the SDK via `cross-spawn`, not through
 `dsh-subprocess-local`** — so they are **outside any Windows Job object** and nothing reaps a
 discarded generation. MCP is mounted **once per host process** (not per session), and every
 preset remount leaves the previous generation running forever. `ChildProcess.kill()` does not
 kill a process tree on Windows — that is documented Node behaviour, so the leak is the default,
 not a surprise.

## What was changed
- The five packages are installed once into a stable per-machine location,
 `C:\Users\ezabz\.dsh\tools\mcp` (316 packages; entry points verified for all five), and every
 row now invokes **`node <absolute entry point>` directly**. The two `npx.cmd` preset rows
 (`mcp-fetch`, `mcp-playwright`) were rewritten; `mcp_launcher.py` now prefers the local install
 for firecrawl/jina/context7 and keeps `npx` only as a fallback. The child DSH spawns is now the
 server itself, so killing it kills the server.
- `NODE_COMPILE_CACHE` set machine-wide (`%LOCALAPPDATA%\node-compile-cache`): a cold
 `node -e "require('fs')"` measured **1608 ms**, the same command warm **446 ms** — paid once per
 tool call, per subagent, per MCP start.
- `harness-config\scripts\dsh-reap.ps1` — a reaper with two provable rules: (1) harness processes
 (node/cmd/conhost/pwsh matching the npx cache, `dsh-subprocess-local`, or an MCP path) whose
 parent PID no longer exists; (2) for each MCP package, keep the newest generation of the whole
 chain and reap older ones. It never touches the engine — which is *parentless* in practice
 because its launching terminal closed, and would otherwise be the first thing eaten — never
 touches a browser, and never touches anything without a harness command line. Report-only by
 default.
- Applied on 2026-09-15: 4 stale MCP generations reaped (2 fetch, 2 playwright), engine protected,
 zero false positives among 28-30 candidates.

## Why this is waste and not capability
No tool, provider, model, agent or parallelism setting was removed. The knobs that would cap what
an agent can do — `agent-loop.maxParallelToolCalls` (currently 20) and
`workflow-worker-thread.maxConcurrentAgents` (default `min(16, cores-2)`) — were deliberately left
untouched.
