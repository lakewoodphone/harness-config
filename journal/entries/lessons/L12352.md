1. ONE h1 PER DOCUMENT IS AN ORDER QUESTION, NOT A COMPONENT QUESTION.

`L12351` measured two h1s on `/` for every signed-in visitor. The useful reframing:
the level is not a property of a heading, it is a consequence of which block leads.
So `resolveHomeHeadingLevel` derives from `resolveHomeOrder` and one component
(`PageHeading`) renders all three headings that can lead the page - the marketing
title, the launchpad's "Discover Your Path" and the attempt shell's title. Demoting
only the marketing would have produced ZERO h1s in two states (a saved draft offered,
where the launchpad leads; and an attempt on screen that is not a saved record yet,
because `resume-drafts.ts` needs 13 answers so the published count is 0). Check the
count in EVERY state, not just the measured one - an invariant that is true in the
photographed state and false one state over is not an invariant.

Styling survived the tag change because every size/weight on those headings is a
Tailwind utility on the element and `globals.css` has no `h1`/`h2` rule (checked:
no heading selectors in the file). Two headings on this page had their proportions
set by class, so h1->h2 changed nothing anyone can see.

2. THE CHEAPEST WAY TO MOVE 430 LINES OF JSX WITHOUT LOSING ONE OF THEM.

The attempt shell is 4,000+ lines and cannot be rendered in a vitest (node env, no
DOM, and `next build` is unavailable). Splitting its return into named parts by hand
is where a transcription error would hide, because no test renders it. What worked:
a throwaway node script (outside the repo) that cut the blocks BY LINE RANGE,
asserted the first and last line of every range by content BEFORE writing anything,
dedented them uniformly, and re-emitted them as `const` parts; then a second script
that compared the multiset of trimmed removed lines against added lines in
`git diff -U0`. Result: 173 removed / 217 added, and every removed line had an
identical added counterpart except 7, each of which was the intended change (the
wrapper `<div>` twice, `<h1>`/`</h1>`, one `)}`, one `</div>`, and the body's ternary
opening brace). That diff check is worth keeping: it turns "I moved code" from a
claim into an arithmetic fact.

3. WHERE A FOLD FIX HAS TO STOP: A WARNING OUTRANKS A FOLD.

The report view's headline was 56 px below the fold behind ~1,000 px of chrome. Three
of the four blocks above it were safe to move. The save status card was not, in two
states: `failed-local` and `unconfirmed-local` are where the reason, the two controls
that clear a paused save and the "sign in again" control live, and the header
paragraph points at it by name ("the box beside this"). So the reorder is refused in
those states (`resolveAttemptReadOrder`) and the headline stays 56 px low on purpose.
When a fold fixes something by demotion, ask which state makes the demoted thing the
one thing the person needs.

re-measures this in a browser should read y of the report headline at 1440x1200 with
scrollY 0, on the REMOTE path (navigator.webdriver overridden - `L12300`).
