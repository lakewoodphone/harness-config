**L2085 · An alarm that fires on an idle fleet is not a monitor: separate CHANGE, CONTACT and PRESENCE before calling silence a failure**

**L · 2026-09-20 · ZABZ-YOGA — An alarm that fires on an idle fleet is not a monitor: separate CHANGE, CONTACT and PRESENCE before you call silence a failure**

**Measured evidence.** At 2026-09-20T14:35:02Z the kernel's `session_archive` check went **HIGH**: *"no
machine has shipped a session in 3.0h: 867 session(s) last seen 5.4h ago; 741 session(s) last seen 5.5h
ago …"*. The shipping path was **not broken**. `dsh_session_exports` recorded `zabz-tech:ca37830cbbe4b177`
at **09:10:31Z** and `zabz-yoga:60de5420baac6a3a` at **14:35:36Z**, and the run between them had nothing
to ship because **no session file changed anywhere** — Yom Kippur, the owner offline, the last session
ending at 08:08Z. The badge was red for six hours of a holiday.

**Why it happened.** `dsh_sessions.updated_at` is the time a session *changed*, and the shipper only
records an export when there is something new, so on the authority "a session changed" was being read as
"the shipper ran". Those are different facts, and the rule *"alarm when NO machine is fresh"* cannot tell
an idle fleet from a dead shipper: both are silence.

**The rule.** A liveness check needs a **positive signal** — something that advances on every successful
run whether or not there is work. For the archive that is a heartbeat export (`session_count = 0`) posted
on every run; for the mail harvest it is a timestamp file. Then keep three facts apart:

| signal | source | answers |
| --- | --- | --- |
| CHANGE | `dsh_sessions.updated_at` | a session file changed at some point |
| CONTACT | `dsh_session_exports.received_at`, heartbeat rows only | the shipper ran |
| PRESENCE | `next_stage_node_reports` (the company's own node agents) | is this machine up? |

Severity then follows one sentence: **HIGH only for a machine that is UP whose last heartbeat is older
than the window** — that is the defect worth waking for. A fleet that is off is INFO and says so. A
machine with no heartbeat yet is reported **unmeasured** and is never read as health, so silence with no
positive signal cannot masquerade as either health or a false alarm.

**Corollary, and the reason this is a lesson and not a changelog entry.** This check had already been
reworked twice for the same class of error (2026-09-14 and 2026-09-15, handoffs H59/H341): each version
inferred the health of a *path* from the age of *data*. Any monitor whose input is "rows that exist"
must be asked what it would print if the pipeline were perfect and simply had nothing to say. If the
answer is "the same thing it prints when the pipeline is dead", it is not measuring the pipeline.
