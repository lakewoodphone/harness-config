**L1474 · Freshness has two halves: the index can be current while the database is not being fed**

## A fresh index over a database nobody is feeding reports "ok" forever

`health` said `ok` and `index_age_hours: 0.15` while the whole point of the surface — the
data — could have stopped hours earlier. That is P29 exactly: the SMS crawler worked, the
index would have been rebuilt on time and complete, and texts would still have arrived a
day late with every light green.

So `health` now reports **two** ages per channel: how old the index is, and how old the
newest communication in it is.

```
comms index: 166,902 communications (0.16h old)
 sms 125,786 newest 0.3h ago
 call 10,355 newest 2.4h ago
 voicemail 2,325 newest 3.5h ago
 email 2,846 newest 0.4h ago
 message 20,683 newest 2092.9h ago (supplementary: UI crawl, frozen by design)
```

Three design choices, each to avoid a known failure:
* **Budget only the channels that flow daily** (sms, call: 30 h). Voicemail and email are
 quiet for days in a real business; a budget there is a standing false alarm, and a
 standing false alarm is how a surface stops being read (P40, P51).
* **Label the frozen channels.** `message` and `history` come from the Playwright UI crawl
 that stopped in June; texts and calls are covered by the REST harvest and the webhook, so
 2,093 hours is not a data loss. Unlabelled, an old number reads as a broken system.
* **Say which failure it is.** The problem text reads "the index is current but the
 database is not being fed (P29)", because that is a different fault from a stale index
 and a different fix.

## Probe the far end before believing an old date is a gap

The oldest stored call was 2025-10-20, and the obvious worry is that harvesting simply
never reached further back. Probed directly, with 7-day windows in 2024-10, 2025-01,
2025-04, 2025-07 and 2025-09, each via the real harvest path:

```
2025-01-06 .. 2025-01-13: read=0 stored=0 errors=0
2025-04-07 .. 2025-04-14: read=0 stored=0 errors=0
2025-07-07 .. 2025-07-14: read=0 stored=0 errors=0
2025-09-08 .. 2025-09-15: read=0 stored=0 errors=0
2024-10-07 .. 2024-10-14: read=0 stored=0 errors=0
```

Zero reads **and zero errors** — the API answered, and the answer is that there is nothing
there. So the oldest call is the account's first call, not the harvest's horizon, and "all
time" is complete for calls. One probe, and a permanent fact: a date range ending at a
round-looking boundary is not evidence of a gap, and a gap is not a gap until the source
says so.

## A voicemail's only URL is the one the downloader never read

916 calls carry a `voicemail_link`; only 312 have a transcript, and **693 had no audio at
all**. The reason is structural, not a bug in the fetching: the downloader builds its URL
list from `recording_url` and `admin_recording_urls`, and a voicemail call usually has
**neither** — its only media URL is `https://dialpad.com/v/<call_id>`. So voicemail audio
was unreachable by construction, and the index could only ever show a number and a date.

The existing `kind='voicemail'` media rows proved the URL works (they were fetched from
exactly that path), so `voicemail_link` is now one of the downloader's source URLs and the
transcriber accepts any audio kind instead of recordings only. Effect measured live: 693 →
682 voicemail calls without audio within a minute, and falling.

Lesson: when a fetch "has never worked", check whether the field it reads *can* be empty for
that class of record. A structurally absent input produces a silent, permanent hole that
looks like a rare event — and it is why an evening's voicemails indexed as phone numbers
while every surface stayed green.
