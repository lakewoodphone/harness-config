**L6718 · A negative is only as wide as the search that produced it, and test the capability the task needs - not a proxy for it**

**I tested a proxy for the capability the task needed, reported a strong conclusion from it, and was
wrong in the direction that matters: I told the owner a credential did not exist when what I had
measured was that a credential under ONE NAME did not exist.**

THE SEQUENCE, MEASURED 2026-10-16, building the LPT website's deploy path.

1. The deploy needs a token with Account -> Cloudflare Pages -> Edit, to be stored as the repository
 secret CLOUDFLARE_API_TOKEN. I searched the estate for that name, found nothing, and reported for
 THREE ROUNDS that no Cloudflare credential existed anywhere reachable, and that minting one was an
 owner-only action.
2. The owner corrected it: *"we already have a cloudflare token that can create other tokens."*
 He was right. `/opt/company/.env` carries **`CF_API_TOKEN`** - a DIFFERENT NAME. **I had searched
 for the name the website's own docs use instead of the name the estate actually stores.** Searching
 for a string is not searching for a thing.
3. Having found two tokens, I tested them against **token management** (`/accounts/{id}/tokens/...`,
 `/user/tokens/...`) and reported that neither can create tokens. All 403.
4. But **the deploy does not need a token that can create tokens.** That framing came from my own
 owner-queue wording, not from the deploy. The deploy needs a token that can reach **Pages**. I had
 never tested that. Testing it took one call:

```
 /opt/company/.env waze-mdm-01:/opt/waze-mdm/.env
 len=40 a444bbb61e20 len=53 158bcc552b87 (both active)
/user/tokens/verify 200 ok 200 ok
/accounts/{id}/pages/projects 403 code 10000 403 code 10000
/accounts/{id}/r2/buckets 403 code 10000 403 code 10000
/accounts/{id}/workers/scripts 200 ok (0) 200 ok (0)
/zones/{zone}/dns_records 200 ok (1) -
/accounts/{id}/tokens 403 code 9109 403 code 9109
```

So both estate tokens are scoped to **Workers + DNS** and neither can reach Pages. The token question
is real - but I only know that now, and I knew it from ONE probe of the right endpoint, which I could
have run four rounds ago.

**THE TWO RULES.**
 * **Test the capability the task needs, not a proxy for it.** "Can it manage tokens" is not "can it
 deploy Pages" and neither is "is it valid". A capability matrix is cheap; state the endpoint the
 WORK requires and prove that one.
 * **A negative is only as wide as the search that produced it.** "No `CLOUDFLARE_API_TOKEN` exists"
 and "no Cloudflare credential exists" are different claims, and I stated the wider one from the
 narrower evidence. When reporting absence, report the SCOPE with it - the name searched, the
 hosts searched, the pattern used - so the reader can tell a real negative from an unsearched corner.

**ALSO WORTH KEEPING:** the account id is now confirmed twice and independently - the
`abletelsolutions.com` zone resolves to `3fe00f424ec43810af16b55df54200a3`, and
`CUSTOMER_BACKUP_R2_ACCOUNT_ID` on the deploy target gives the same value - and each token's own id is
readable from `/user/tokens/verify` (`9520cec800b9994e6ec42a8a55d1265f` and
`a7537bf3ffd4555e8710ccf16b03d419`), so a token can always be named without printing it.
