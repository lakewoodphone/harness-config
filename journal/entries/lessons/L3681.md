**L3681 · The CFO's ears were not on a clock: registered an await so his reply is processed**

2026-10-13. The CFO had a mouth on a clock and no ears on a clock. His replies would have sat
unprocessed. Fixed with the estate's own primitive.

THE GAP, found by reading the crontab against the tools that exist:
 cfo-ask every 30 min, --send asks the owner questions MOUTH
 cfo-apply-rules 7,37 applies answered rules HANDS
 cfo-clarify NOT SCHEDULED matches an inbound REPLY MISSING
`cfo_clarify.py` takes `--match TEXT` (dry) and `--answer --ref REF --text TEXT` (record and learn the
rule), and NOTHING feeds it. So the two open questions - newegg 362.51 and polka dot 299.00 - would
have been answered by the owner into the inbox, and the answer would have sat there until a human
opened a session and thought to run the tool. The CFO would have kept asking, the ledger would have
kept reading `answered=0`, and nothing would have looked broken. **A silent ear and an idle ear print
the same line**, which is the exact failure the wake skill records for the responder reading the wrong
store from April to September.

THE FIX, in the estate's own idiom rather than new code in a live path. The flagship pattern is
`await`: "every time you send something and expect something back, register what to do when the answer
arrives." Registered:
 python3 ~/bin/wake.py await +18483897895 --name 'Eliyahu (owner)' --until 2026-10-20
 --what "Run cfo_clarify.py --status ... match his reply ... record it ... verify answered=1
 and --owner-rules >= 1"
 -> awaiting Eliyahu (owner) (+18483897895); active awaits 6 -> 7
So his reply now matches the await, files a flag, and revives a headless session that is TOLD to do the
work. The skill prefers a separate process over editing the live send path, and `await` is exactly
that: no new code sits in the path that texts a human.

WHY NOT JUST ADD A CRON. A cron running `cfo_clarify --answer` would be the structural fix - the ears
on the same clock as the mouth - but `--answer` LEARNS A DURABLE RULE and that is a write with
consequences, driven by free text from a phone. `await` routes it through a session that can read the
question, read the reply, and judge whether they match, which matters because the matcher has already
been wrong once this month (it filed replies under the oldest open question regardless of content,
fixed 2026-10-13 with merchant-name disambiguation). **Automate the wake-up, not the judgement.**
