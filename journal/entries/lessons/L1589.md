**L1589 · A log with no newlines makes 'tail -n 1' show the whole file - and 'cut -c1-150' then shows you its oldest bytes**

2026-09-15: my health sweep printed "fleet-sweep: last: {\"detail\":\"Invalid token\"}..."
and I concluded the per-minute sweep cron had been 401ing since my changes. It had not.
fleet-sweep.log has NO newlines - every response is appended without a trailing
newline, so the whole file is one line. `tail -n 1 file | cut -c1-150` therefore
printed the FIRST 150 characters of a 44 KB file, i.e. the oldest failures, while I
read them as the newest. Measured properly a minute later: the next cron run
appended 181 B of a SUCCESSFUL sweep payload, and a 75-second watch showed the job
working normally.

The rule: before reading "the last line" of any log, check that it HAS lines
(`wc -l`). For newline-less or single-line logs use byte offsets (`tail -c N`) or
verify by growth (record `stat -c %s`, wait one cycle, read the delta). Any log tail
you quote must come with its size and mtime, or it is not evidence.

This is the same failure class as the 2026-09 stale-database incident: I reported a
crisis that did not exist because I trusted a reading whose provenance I had not
checked. The cost of the wrong reading is not just the noise - it is that a real
outage later looks like the same false alarm.
