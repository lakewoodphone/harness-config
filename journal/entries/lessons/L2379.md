**L2379 · lptcase.py new scaffolded a sync record that FAILED the repo's own schema — every new case was born invalid**

## L2405 · 2026-09-24 · lptcase.py new produced a schema-invalid sync record for every new case

MEASURED. `tools/case-index/lptcase.py new <slug>` writes the case file AND, since a 2026-09-14
change, a matching sync record "so a new case is not born an orphan". The record it wrote carried
four keys `CUSTOMER_CASE_SYNC_RECORD.schema.json` forbids — it sets `additionalProperties: false`
at the root and inside `operational`, `references` and `customer`:

```
INVALID -> (root) Additional properties are not allowed ('issue', 'nextAction' were unexpected)
```

The four were root `issue` and `nextAction`, `operational.quoteStatus`, and `references.phone`.
Two further keys were schema-legal but empty, and the schema requires `minLength: 1` on
`operational.internalSummary` and `operational.nextAction` — so even after deleting the illegal
keys the record would still fail. Confirmed on all three cases scaffolded 2026-09-24.

WHY IT MATTERS AND WHY IT WAS INVISIBLE. The record still PARSES and the push tool reads the
fields it needs by name, so the push worked and nothing failed loudly. What was silently wrong is
the contract every other consumer relies on: the schema is the documented interface, and a record
that fails it is rejected by anything that validates. A scaffolder that manufactures invalid
records makes the malformed case the DEFAULT, and the standard it points at ("every new case file
is written this way") untrue from birth.

FIXED in the same session (lpt-hub 2657c06da): the scaffold now emits only schema keys, puts the
phone in `customer.phone` (which the schema's `anyOf` already accepts as a matcher — `references`
has no place for it), drops the duplicate `relatedPaths` phone, and fills `internalSummary` /
`nextAction` with a true, non-empty default. Verified by scaffolding into a throwaway repo
(`--repo /tmp/...`) and validating with jsonschema: passes.

RULE. When a tool scaffolds an artifact that another schema validates, the test is not "does it
run" but "does a freshly scaffolded one VALIDATE". Validate the scaffold in a temp repo; never
against the live corpus.

RULE. `additionalProperties: false` cuts both ways: adding a helpful field to a record is a schema
change, not a free extra. Before adding a key to a sync record, check the schema has it.
