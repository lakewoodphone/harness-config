**L10366 · Dead config looks exactly like a control, and I duplicated a module constant while fixing one**

## 2026-10-19T23:55Z · ZABZ-YOGA · dead config looks exactly like a control

`ROUTING_QUALITY_FLOOR` was documented in `cost_routing` as *"informational; enforced by smart_router's
capability checks"*. Nothing read it. The phrase "enforced elsewhere" was the tell: it is what a setting
says when it is doing nothing.

This is the **second inert control found the same night**, after the exemption list keyed on the wrong
identifier. Both looked present. Both were documented. Neither could fire. That is not two coincidences;
it is one habit - writing the control and the explanation together, then testing the control in isolation
from the caller that runs it.

### Now it is read, and it can only tighten

`smart_router._quality_floor()` reads it; the equivalence yield refuses to promote an alternative whose
quality class is below the floor. It may **raise** the bar above the direct candidate's own class and may
never lower it, because a setting that silently permits a worse model is worse than no setting at all.
An unreadable value is logged and ignored rather than obeyed.

### And I broke the module while fixing it

My first version added a **second** `_QUALITY_RANK` map - `low:1 … highest:4` - without checking that the
module already had one at `low:0 … highest:3`. Python takes the later definition, so my copy re-ranked
**every other user of that map in the file**, and turned "unknown quality class" from *equal to low* into
*below low*.

The tests passed, because they were written against the duplicate. What caught it was the port script
refusing with `already patched` - a guard built for a different purpose entirely.

**Rules:**
1. Before defining a module-level constant, grep the module for it. `_QUALITY_RANK` is a name, and names in
 a 2,800-line file are not unique by assumption.
2. A test written alongside a change agrees with the change; it cannot catch a mistake the change introduced
 unless it asserts the *invariant* rather than the new value. There is now a test asserting exactly one
 definition of the map exists.
3. When two maps of the same concept exist, one of them is a bug waiting for a merge. Prefer reading the
 existing one and failing loudly over adding a second.
