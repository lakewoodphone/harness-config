# The roadmap supply dedupes inside ONE project, so a register path whose ledger item lives under another project is refiled

Measured 2026-10-20 while pointing the roadmap supply at the five new phase-6 register paths.

`split_candidates()` compares a candidate against `ledger_live(work.db, args.project)` - the live items of **the
project being supplied**. Ledger item 643 ("Reconcile the authority running wake scripts…") is filed under
`housekeeping`. A mapping row for roadmap path `X-P6-01` in the `kosher-ai-filter` mapping therefore cannot match
it, and the dry run said so plainly:

```
new=1 filed_this_run=1
filed: Reconcile the authority running wake scripts with their harness-config forks (live/ snapshot, 2026-10-18)
```

That is a duplicate of real work, created by a correct mechanism given a wrong input. The same dry run listed
806 and 807 as `live`, because those two are in the right project.

## The rule
**A roadmap path's ledger item and the mapping row that points at it must be in the same project, or the row is
`not_filed` with the mismatch named.** A cross-project row is not a small bookkeeping slip: it manufactures the
exact duplicate this source exists to prevent, and it does it silently in a `--dry-run` that otherwise looks
clean.

## How to check before trusting a mapping change
```
python3 /root/bin/sources/roadmap-supply.py --project <p> --dry-run
```
Read `new=` and the `filed:` lines, not just the exit code. `new=1` on a project whose queue is quiet is either
genuinely new work or this trap; the `filed:` line names which, and the fix is `not_filed` plus the reason, or
moving the ledger item to the project that owns the path.

## What was done
`X-P6-01`'s mapping row is `not_filed` with the reason recorded; the register item now states the mismatch in its
own body so the next reader meets it before refiling. The dry run is back to `new=0 filed_this_run=0 already=2
id_keyed=52`.
