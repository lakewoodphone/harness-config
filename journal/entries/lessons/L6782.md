**L6782 · A metric your own writer degrades needs the fix at the writer, not a mop-up tool**

Measured 2026-10-16 on the CFO ledger. cfo-provenance.py read P2 (a category carrying a substantive reason) at 83.0 percent while the enrichment tool planned 53 rows it had already been run over. The cause was structural: the engine's own writer emits template justifications - cfo_resolve:rule CR-aa... (Subscriptions, conf=0.85) merchant='desc:soundiiz premium' - 426 of them from that one writer, newest the same morning. So every row the loop resolved pulled the metric down a little, and a separate tool existed to mop up afterwards with no clock on it. The reason was already IN the writer's hand: the resolution's own evidence[] and the rule's evidence[] both carry a human sentence and its reference, and neither path wrote it. One _why_clause() helper, shaped exactly like the clause the enrichment appends, now appends it at birth in both paths, before the 300-character cut. Verified on real data: before, 'cfo_resolve:rule CR-43f1d550f2ff (Government Fees, conf=0.85) merchant=nj motor vehicle...'; after, '... merchant=desc:soundiiz premium | why: Plaid category hint(s): ... (rule CR-aaa4fdc84483)', with a direct --apply-rules run writing 4 rows all carrying the clause. The general rule: when a quality metric decays as a by-product of doing the work, do not schedule a cleanup - find the writer that produces the low-quality artefact and have it produce the good one, because a cleanup tool is a second thing that can stop running and nothing will notice. The enrichment tool stays for the pre-existing backlog, where it took the count to zero.
