**L3407 · An aggregate mismatch is a question, not a finding - check the specific item**

**An aggregate mismatch is a question, not a finding: check the specific item before escalating.** Twice
in one session on 2026-10-08 I read a summary as a fact about data and was wrong both times.

 * `website-comms-push.py` answered `file is not a database` and I wrote "the company database may be
 broken" into a handoff. It was a **working-directory** bug: `settings.database_url` is the relative
 `sqlite:///data/secretary.db`, so run from `/home/zabz` it opens a different file. Run the way cron
 runs it, it answers `ok: true`, 0 errors. (L3404)
 * `tools/case-index/lptcase.py` warned `CASE COUNT MISMATCH: 278 case file(s) on disk, 279 tracked by
 git. A gap like this is exactly what a reparse point or a partial copy looks like` - a sentence
 written to raise an alarm about lost customer data. The named file **exists**, 45 KB, modified the
 same evening by another session still working on it. The two numbers were counting different sets
 (`*.md` on disk versus every tracked path, images included) and my own `comm` comparison mis-sorted.

Rule: when a count or a summary disagrees, **name the specific item** and look at that item. `ls` the
file, `grep` the row, `git log` the path. An aggregate is a detector, never evidence; and an alarm about
lost customer data costs the owner's attention every time it is wrong, which is the most expensive
resource in this system.

Evidence: `test -e <the kramer case>` -> exists, 45198 bytes; `git status --porcelain` clean for it;
H3385 (the push correction) and H3388 (the non-finding).
