**L2251 · Windows Hello wipes itself when a Secure Boot DBX update and a firmware update land together (Microsoft-documented; remedy is re-registration)**

**Windows Hello wipes itself when a Secure Boot DBX update and a BIOS/UEFI firmware update land together — Microsoft documents it, and the remedy is simply to re-register Hello.**

This is the root cause of ZABZ-TECH's "every restart I have to reset the PIN", established 2026-09-20 after firmware was brought fully current and the symptom stopped.

Microsoft, Windows Commercial Support / Directory Services, 2025-11-12 — [cannot validate VSM when multiple PCRs changed](https://jpwinsup.github.io/blog/2025/11/12/ActiveDirectory/WindowsHello/cannot-validate-VSM-when-multiple-PCRs-changed/):

> This problem can occur when a **Secure Boot DBX update and a BIOS/UEFI firmware update are performed at the same time** during Windows Update. […] Windows Hello information is protected by VSM (Virtual Secure Mode). Retrieving it performs an integrity check using special TPM register information (PCRs). If the Secure Boot DBX update and the BIOS/UEFI firmware update happen simultaneously, **several PCR values change at once**, the integrity check fails, the information cannot be retrieved, and this problem occurs.

What that means mechanically, and it is the part worth carrying forward:

- The user-visible symptom is `[7002] Failed to load an existing Windows Hello container. Error: 0xD000A002`, and then Windows' own OOBE broker deletes the container (`[3611] … userOOBEBroker.exe`) so a new PIN must be created. **The wipe is Windows reacting correctly to an unreadable container** — it is not corruption of the PIN and not something to "repair".
- At the firmware layer the same event reads `UefiBlobIsCorrupt: 1` and `BlobFromUefiVariableSize: 0` on the VSM key package (`Microsoft-Windows-Kernel-Boot/Operational` event 85). **This is a symptom of an already-failed integrity check, not evidence that a UEFI variable has gone bad** — which is why chasing "repair the corrupt UEFI variable" (or blaming the NVRAM store being full, or the BIOS self-healing, or Absolute Persistence) is the wrong tree. It cost most of a day here.
- **It is a one-time event per firmware change, not a recurring fault.** Microsoft's own remedy: after it occurs, re-register Windows Hello (Settings → Accounts → Sign-in options → set up PIN/biometrics) and it works. So repeated PIN resets are explained by *repeated firmware application*, not by a broken machine — the fault recurred here because Windows Update kept offering firmware and each application was another PCR change.
- Microsoft states there is **no mechanism in Windows** to prevent the two updates from landing together. Their stated prevention is to keep password sign-in enabled so a broken Hello cannot lock you out — `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\PasswordLess\Device :: DevicePasswordLessBuildVersion = 0` (**2 = "only allow Windows Hello sign-in"**). Verify this stays 0 on any machine where Hello has ever broken. On ZABZ-TECH it is 0, which is why the owner could always recover.
- Practical consequence for any Windows box: when a Lenovo/HP/Dell OEM firmware update arrives, **expect one Hello re-registration**, and if two firmware updates are pending, apply them one per boot rather than together.

Evidence of resolution on ZABZ-TECH: firmware went `M4WKT56A` (2025-06-02) → `M4WKT5CA` (2026-07-07) and TPM `15.23.17664.0` → `15.24.18954.0`; Windows Update then offered **zero** firmware; two consecutive boots (15:33, 15:38) came up with `BlobSize=723 / corrupt=0`, VSM cached-copy unseal `0x0`, and `[8002] … State: Okay`, and the pre-bootmgr window fell from **166–178 s to 25 s**.
