**L11967 · An answer that asks for work must become work: the first live reply was an instruction and the channel dropped it**

Measured 2026-10-21 on the first live decision-channel send.

The first question the channel texted him was "NJ payroll tax NJ-927/927-W due in 9 days for Lakewood Phone & Tech LLC. Want me to file NJ-927/927-W?" He answered three minutes later:

 "Make sure all the information is fully documented and ready for me to file and you'll walk [me through it]."

That is not an answer to a yes/no question. It is an INSTRUCTION, and it arrived through a channel whose whole design assumed answers were terminal: the row is marked answered, the turn closes, the next question goes, and NOTHING anywhere turned "document it so I can file it" into work. The answer was consumed as data and the request inside it was dropped.

The fix at the time was one ledger item (cfo #941) filed by hand from the session that saw it. That is not a mechanism -- it worked because I happened to be watching, which is the definition of the failure this estate keeps fixing (a monitor that needs someone to be looking).

THE RULE, for whoever builds the next piece of this channel:
 * a row whose answer contains an instruction ("make sure", "document", "send", "file", "prepare", "check", "walk me through") must create a WORK ITEM, not just a closed row;
 * the test is not sentiment, it is whether the answer names an action that has not happened;
 * until that exists, every answer of this kind is silently dropped, and the channel teaches him that answering produces nothing -- which is how a working channel becomes an ignored one.

Also worth recording: I ran `decision-answer-capture.py` WITHOUT `--apply`, saw "1 inbound reply inside the window", and could have reported the answer as captured. Nothing was written. "Found the answer" and "recorded the answer" are different sentences, and the dry run printed the one that looked like success.
