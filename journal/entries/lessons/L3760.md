**L3760 · Check the WRITE side of a precedence ladder, not just the read: rung 1 can have no writer at all**

MEASURED 2026-10-13 on secratary-cloud, while building the CFO clarification loop (fleet brief
owner-ask-loop; handoff H3594).

1. THE TOP-RANKED STORE IN A LADDER CAN HAVE NO WRITER.
 merchant_resolve.resolve() consults rung 1 first and gives it the highest confidence in its whole
 table (CONF_ALIAS 0.97 > vendor-list 0.93 > answered-ask 0.92 > ledger 0.90 > one-prior 0.80 >
 receipt 0.70; merchant_resolve.py:105-110, rung order at :646-652). Its store is
 ~/.cfo-asks/aliases.db. That file did not exist, and the ONLY code anywhere claiming to write it
 is sms-responder.py:791 - `hasattr(decide_mod, "write_alias")` - and write_alias is defined in NO
 file reachable from the cloud box (grep -rn "write_alias" over /root/bin,
 harness-config/scripts, app and scripts returns exactly that one guarded call site, twice on two
 adjacent lines). A hasattr-guarded call to a function that has never existed reads, in a diff, as
 a working path. LESSON: when a brief says "the engine already gives X the highest precedence",
 grep for the WRITE, not the read. `grep -rn "<writer_fn>"` returning only a hasattr guard is a
 store with no writer, not a wired path. Then check the reader's own file-existence guard, because
 a reader that returns "no store yet" quietly is how an empty rung looks healthy.

2. A hasattr GUARD IS NOT EVIDENCE THAT A PATH IS MOUNTED - CHECK THE SIBLINGS IT LOADS.
 sms-responder.py carries a documented "four-way contract, wired in" block (lines 687-...). On the
 cloud it is INERT: HERE = Path(__file__).resolve().parent is /root/bin (line 58), and
 /root/bin/textctx.py and /root/bin/textdecide.py DO NOT EXIST, so _load() returns None for both
 and _asks_for() returns []. On top of that, `grep -rn "def recent_asks" /root/bin
 /root/code/harness-config/scripts` finds NO definition anywhere - so a file appearing would still
 not help. Two independent reasons for one silent no-op. LESSON: for any *_load("x","x.py")
 pattern, ls the directory the module computes for itself and grep for the function it calls.
 "The code contains it" and "the code runs it" are different claims.

3. A READ-ONLY OPEN OF A WAL-MODE SQLITE DATABASE STILL CREATES FILES BESIDE IT.
 `sqlite3 "file:/root/accounting-data/live/accounting.db?mode=ro" "..."` left
 accounting.db-shm (32768 bytes) and accounting.db-wal (0 bytes) in
 /root/accounting-data/live/, and did the same beside /root/.cfo-asks/asks.db. The database files
 themselves were untouched (size, mtime and sha256 all unchanged). LESSON: when a brief says
 "read-only", a mode=ro *connection* is still not a zero-footprint act - report the -wal/-shm
 side effect rather than let an auditor find it and wonder whether the file was written.

4. POWERSHELL DID NOT JOIN A QUOTED VARIABLE TO AN ADJACENT BARE WORD HERE, AND scp SAID SO BADLY.
 `scp "$d\new\f.py" "$h"f.py` with $h = 'host:/path/' passed TWO arguments, so scp tried a LOCAL
 file named f.py and printed `f.py: No such file or directory` - which reads like the remote path
 is missing, not the local one. Cost two round trips. Use a single interpolated string
 ("secratary-cloud:$rb") or "${h}f.py". Same family as the measured hazard that ssh stdout through
 a PowerShell pipe stalls: on this host, build one string rather than rely on argument-adjacency.
