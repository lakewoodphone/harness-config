**L3495 · The gallery BlobCache is self-labelled: a deleted video's frame, id and date come back from an unrooted phone (BlobCache = key_bytes + JPEG)**

Measured 2026-10-11 on a Coosea SL006 handset (Android 12, FBE, no root) while hunting one deleted video.
The bytes were unrecoverable - but the phone named every deleted file, dated it, and still held a decoded
frame of each. Every claim below has a command that produced it; the tools are in
`lpt-hub/tools/phone-scan/` and the case record is WO26100812738.

**1. `MediaStore._id` is AUTOINCREMENT, so a deleted row leaves a permanent HOLE and its neighbours date
it.** `adb shell content query --uri content://media/external/file --projection _id:_data:media_type:date_added:date_modified:_size`
then look for missing ids (`tools/phone-scan/id_holes.py`). Print the holes as BLOCKS: a single hole is one
deleted file, a long block is a bulk delete or a whole volume's rows going missing. Two limits to state out
loud: a hole above the highest surviving id is INVISIBLE (if the deleted file was the newest thing on the
volume, its id is simply gone), and a missing id can also be a row that was re-created under a new id
after a move or rename. Parse tolerantly - `_data`, `media_type` and `_size` are NULL for directory rows,
and one silently dropped row becomes a confident fake hole (this bit me; the first run invented ~15).

**2. The gallery's `bookmark.0/.1/.idx` is a list of every video the owner actually PLAYED, by URI.**
Gallery2's `Bookmarker` (inner class of `MoviePlayer.java`) stores playback position per item, keyed by
`String.hashCode()` of the content URI, value = `writeUTF(uri) + int position + int duration`. So a plain
string scan of the file yields `content://media/external/video/media/<id>` for every video ever watched -
and an id that is ALSO a hole in (1) is a deleted video, named. Two independent records agreeing is what
turns a hole into a finding.

**3. THE ONE THAT PAYS: the image cache stores each frame as `key_bytes + JPEG`, and the key is the label.**
`com.android.gallery3d`'s `imgcache.0` (`/sdcard/Android/data/com.android.gallery3d/cache/`) is an AOSP
Gallery2 `BlobCache`: index header 32 bytes (magic `0xB3273030`, maxEntries, maxBytes, activeRegion,
activeEntries, activeBytes, version, adler32), then TWO hash tables of `maxEntries * 12` bytes, each entry
= 8-byte key + 4-byte offset (0 = free), and data files whose blobs are `20-byte header + key_bytes +
value`. `ImageCacheService.putImageData` puts the KEY BYTES in front of the JPEG, and the key is
`GalleryUtils.getBytes(path.toString() + "+" + timeModified + "+" + type)` = **UTF-16LE of
`/local/video/item/<MediaStore _id>+<date_modified_seconds>+<type>`** (type 1 = thumbnail, 2 =
microthumbnail). **So you do not need to solve the CRC-64 key at all**: scan the data file for the UTF-16LE
bytes of `/local/`, decode the label, and the JPEG starts immediately after it. Every cached frame is
self-labelled, including frames of files that no longer exist - which is how a deleted video's picture, its
MediaStore id and its true `date_modified` all came back from a phone with no root and no recoverable data.
On this handset: 1,259 blobs, 1,259 labels, 121 of them for ids that no longer exist.

**4. What this is worth, said honestly.** A cached frame is a PICTURE of the lost video, not the video. It
proves the file existed, names it, dates it, and lets the customer identify which one they mean. It never
gives back the bytes. On an FBE device the bytes are gone for good - and the frame is the ceiling, not a
step towards more.

**5. Corollary that generalises past phones.** A cache written by an app that had the file is a record of
the file, and caches are not cleaned when a row is deleted. `.thumbnails/<id>.jpg` IS cleaned by
MediaProvider on delete (all 5 survivors belonged to live videos); the gallery's own BlobCache is not. Look
for the CACHE the display path wrote, not the index the database maintained.

**6. Two more traps from the same session.** (a) `find /sdcard ...` returns nothing at all - `/sdcard` is a
symlink toybox `find` will not follow, silently (see L3492); always search `/storage/emulated/0`. (b) This
handset boots with no usable RTC and reports 2024-11-13; file mtimes are still trustworthy because their
FILENAMES carry the same date and minute - date a device's history from filename-vs-mtime agreement, never
from a clock reading taken now.
