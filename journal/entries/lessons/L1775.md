**L1775 · ServerAliveInterval does not save you from a hanging REMOTE command - two ssh sessions sat open 24 minutes because the TCP session was alive and the far side was stuck**

MEASURED 2026-09-16, while five design agents measured the mesh: two ssh connections (pids 22636, 26992) stayed open for **23.6 minutes at 0.1 s of CPU**. They were not working and not transferring; they were hung. ~/.ssh/config already had \ConnectTimeout\, \ServerAliveInterval 15\ and \ServerAliveCountMax 3\ - so the usual advice was already in place and did not help, because **keepalives detect a dead PEER, not a stuck REMOTE COMMAND**: if the far side is blocked (waiting on input, a wedged command, a lock, a full pipe) the TCP session is perfectly healthy and keepalives never fire. I killed both; an agent whose tool call was blocked on one cannot make progress, retry a different node, or write its deliverable until the call returns.

RULES THAT FOLLOW
1. Every ssh command that crosses this mesh carries a **remote-side** bound: a timeout in the remote command itself ( imeout 20 ... on Linux/macOS; a bounded job or an explicit timeout in the PowerShell command on Windows), or a local wrapper that kills it. Local ssh options alone are not enough.
2. Prefer -o BatchMode=yes PLUS a bounded remote command; never an unbounded read (no \-Wait\, no interactive prompt, no \ ail -f\, no bare \Get-Content\ on a pipe that may never close).
3. A hung tool call is invisible from the agent's own logs (its heartbeat keeps ticking) - so when a fleet stalls, look for **old processes with near-zero CPU**, not for stale session logs. That is the diagnostic: 24 minutes and 0.2 s of CPU is a hang, not work.
4. When it happens: kill the hung client. It is a blocked call, not a job in flight; killing it lets the agent retry or move on.
Recorded here because the same trap will hit any fleet that measures the mesh, and the failure looks like 'the agents are slow' rather than 'the agents are blocked'.
