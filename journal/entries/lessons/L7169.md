**L7169 · Correcting P7051 - the channel explains the urgency label, not the timing**

P7051, filed earlier the same day, says the anniversary reminder died because its delivery channel was `dashboard`. Half right, and the wrong half matters.

WHAT P7051 GOT RIGHT: on the `dashboard` branch `personal_ops` sets `urgency="urgent" if priority in ("urgent","high") else "normal"` from the reminder's own priority column, so the row lands `normal`; the `sms`/`both` branch goes through `send_owner_update` and `_infer_owner_update_urgency`, which returns `urgent` for any reason starting `reminder:`. Verified live by calling both predicates: all twelve new rows classify `urgent` and pass `owner_sms_allowed`.

WHAT P7051 IMPLIED AND THE DATA REFUTES: that the channel alone caused the miss. Reminders 589, 530 and 534 were ALSO `delivery_channel='dashboard'`, `priority='normal'` — and their queue rows SENT (row 2589 at 2026-10-13T13:00:11Z, 2599 at 14 Oct 13:15, 2600 at 14 Oct 14:41). The newest `sent_at` on the entire queue is 2600 at 2026-10-14T14:41:10Z, and the first recent `owner_sms_held` activity row is 2601 at 2026-10-14T17:28:53Z. So the urgency gate became EFFECTIVE in the flush inside that three-hour window on 14 October: the same row shape passed before it and fails after it. Which change flipped it is NOT established — the autopilot state backups at 14 Oct 13:59Z and 15:50Z bracket it and nothing else I read does.

LESSON: "the field that explains the value" and "the event that changed the behaviour" are two different measurements, and I reported the first as the second. When a threshold "has always been set to X", that is a statement about configuration — check whether the code path that READS it was running at the time the behaviour changed. A setting is not a fact about a process; the process is the fact.
