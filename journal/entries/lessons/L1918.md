**L1918 · The customer CLI quotes every front-matter scalar ON PURPOSE and appends --activity sections at EOF - read the tool's own comment before 'fixing' its output**

**The customer CLI's front-matter emitter quotes every scalar ON PURPOSE, and its `--activity` sections land at EOF outside `## Activity`. Both facts cost a hand-repair if you do not know them.**

Measured 2026-09-17 on `tools/customer/cli.py` (the repo's declared single write path, `lpt-hub`):

- **`_yaml_scalar` (`tools/customer/store.py:714`) double-quotes every string deliberately**, with the reason in its own docstring: an unquoted `null` / `yes` / `no` / `on` / `off` / bare `2026-09-14` re-parses as a different type. So after one `customer edit`, a legacy case file's front-matter goes from `price: 180` to `price: "180"` and `opened: 2026-09-10` to `opened: "2026-09-10"`.
 **I de-quoted it back by hand, twice, before reading the docstring** - i.e. I reverted a documented decision because the diff looked noisy. That is the lesson: when a tool's output surprises you, read the tool's own comment before "fixing" its output, because the surprise is often a deliberate invariant and the hand-fix is the bug. Whether the corpus should be quoted (the tool's round-trip safety) or bare (all 186 existing case files, and a numeric `price`) is a real decision that needs to be made ONCE and recorded; what it must not be is a per-session hand-edit.
 Consequence to be honest about: whichever style wins, the first edit of any legacy case file churns its whole front-matter block, so that edit's diff no longer shows only the fact that changed.
- **`--activity` appends the new dated section at end of file**, which puts it under whatever heading happens to be last (`## Open question for the owner`, `## Bench notes`) rather than inside `## Activity` with its siblings. Fixing it is a move, not a rewrite - but nothing in the tool says so, and the file looks fine to a reader who does not check the heading order.

Both are cheap to fix in `store.py` (quote only when the value would re-parse as a non-string; insert the section before the trailing non-Activity headings) and neither is mine to edit while that file's author has it in flight. Recorded here so the next session does not spend the same hour.

The tool itself is excellent at the thing that matters: `--expect-digest` refused nothing but would have, and it reported `record: stale` honestly after my hand-maintained mirror diverged.
