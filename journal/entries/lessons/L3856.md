**L3856 · CORRECTION to L3855: an unelevated filtered-admin token still held WriteDAC on the profile folder - attempt the operation, never infer a blocker from whoami**

CORRECTION to L3855, which said the transferred profile could not be fixed because the session is not elevated. That conclusion was wrong, and it was wrong in a way worth keeping: I inferred "cannot" from `whoami /groups` instead of attempting the operation.

WHAT L3855 CLAIMED. "Clearing it needs elevation (`takeown /F E:\Users /R /A /D Y` then `icacls E:\Users /grant ...`), and an unelevated DSH session cannot do it: `whoami /groups` shows BUILTIN\Administrators as 'Group used for deny only' and approval prompts are disabled, so this is an escalate-to-owner item, not a retry."

WHAT ACTUALLY HAPPENED, 2026-10-19, on the Schreiber drive mounted as E: on ZABZ-TECH. The owner said "I'm pretty sure you have admin permissions." The token measurements he was arguing against were all correct and unchanged: `whoami` = zabz-tech\ezabz, Mandatory Label = Medium (S-1-16-8192), BUILTIN\Administrators present but "Group used for deny only", `IsInRole(Administrator)` = False, and no SeTakeOwnership / SeRestore / SeBackup / SeSecurity in `whoami /priv`. And yet:

 icacls E:\Users\User /grant '*S-1-5-32-545:(OI)(CI)(RX)' -> exit 0, "Successfully processed 1 files; Failed processing 0 files"
 icacls E:\Users\LogMeInRemoteUser /grant '*S-1-5-32-545:(OI)(CI)(RX)' -> exit 0
 icacls E:\Users /grant '*S-1-5-32-545:(OI)(CI)(RX)' -> exit 5, "Access is denied"
 Get-ChildItem E:\Users\User -> 34 entries (before: "Access is denied")

THE RULE, and it is the general one. **Write-DAC is a per-object right, not a property of the token.** A filtered, medium-integrity, non-elevated administrator token can still hold WRITE_DAC on an object whose own DACL grants it, and a Windows profile folder is exactly such an object — and it can equally lack it on the parent, which is why the same command succeeded on E:\Users\User and was refused on E:\Users. So: **never answer "can I make this change" from whoami, IsInRole, the integrity label or the privilege list. Attempt the actual operation on the actual object and read the exit code.** The token tells you what is plausible; only the operation tells you what is true. Inferring a hard blocker from group membership cost the owner a round trip and produced a wrong written record that then had to be corrected in three places (production note, case file, sync record).

SECOND CORRECTION, same job. **Never plan `takeown /R` or `icacls /T` on a Windows user profile.** Profiles carry legacy junctions — `Application Data`, `My Documents`, `Local Settings`, `Cookies`, `Recent`, `SendTo`, `PrintHood`, `NetHood` — that point back into the same tree, so a recursive walk can cross or loop them. Neither flag was needed: an `(OI)(CI)` ACE set on the profile root inherits to every child that has inheritance enabled, which is essentially all of them. Grant at the root, let inheritance do the work, then MEASURE the completeness of that inheritance instead of assuming it: walking all 6,521 directories under the profile showed 3 lacking the grant, all AppData caches (Intel ShaderCache, Microsoft Installer). That measurement is what turns "should work" into "works".

WHAT THE VERIFICATION LOOKED LIKE, for reuse. Volume used space before and after the permission change: 326.3 GiB both times, identical — that is the no-data-loss reading, cheap and unambiguous, and it is better than hashing 255 GiB. Payload counted: 255.72 GiB / 28,438 files (Desktop 176.13 GiB / 20,019 — the Desktop is nearly always the bulk, and it is what the Greenfeld job once silently dropped). Content access proven by opening real files, not by listing them: `.docx`/`.xlsx` read `50 4B 03 04`, and nested Desktop items up to 49.4 MB hashed with SHA-256. And the honest limit of the record: the profile's ACL could not be read BEFORE the change, so which single entry opened it cannot be claimed — only the ACL as it reads afterwards, in which the one portable entry is `BUILTIN\Users` (a machine-local SID like zabz-tech\ezabz exists on no other PC).
