**L1923 · Never run a markdown-emphasis stripper over a machine-readable field value - the underscore bug in lptcase**

**Lesson (2026-09-17): never run a markdown-emphasis stripper over a machine-readable field
VALUE — it silently deletes the underscores that enum names are made of, and the failure is a
wrong status, not an error.**

`tools/case-index/lptcase.py` line 739 did
`raw_status = re.sub(r"[*_`]", "", raw_status).strip()` — reasonable-looking, because a status is
often written `**Status:** CLOSED`. But that same substitution also runs over the **front-matter**
value, so `status: in_progress` arrived at `canonical_status()` as `inprogress`, matched no key in
the table, and fell through to the default `"other"`. Measured on the Goldstein intake: **every**
`in_progress` case in the corpus (16 of 187) was being reported as `other`, and `lptcase open` /
dashboard views grouped them under the wrong heading. No test caught it because the test corpus
used `ready`/`closed`/`quoted` — none of them contains an underscore.

Fixes applied: the stripper now removes `*` and backtick only (markdown emphasis), the underscore
is left alone, and `"inprogress"` was added as a belt-and-braces key so a value that lost its
underscore upstream still canonicalizes instead of degrading to `other`. Regression test added
end-to-end (`test_front_matter_in_progress_status_keeps_its_underscore`); 87 tests pass; the corpus
now reports 17 in_progress.

The general rule, which is bigger than this bug: **value-level normalisation must be stricter than
prose-level normalisation.** Anything that cleans up human prose (emphasis removal, whitespace
collapse, punctuation folding) must never be pointed at a field whose value is an identifier. If a
status field ever looks wrong, check the normalisers between the file and the reader before
believing the file.
