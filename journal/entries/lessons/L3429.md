**L3429 · Reading a session: the store is two places, the file is a thousand zstd frames, and the copy is not the original**

MEASURED 2026-10-09, ZABZ-YOGA, while building scripts/sessions.mjs.

1. THE FILE IS ONE ZSTD FRAME PER APPENDED EVENT, not one stream. The 1.4 MB
 phone session 99f5c499 is 1,083 frames. `zlib.zstdDecompressSync(buf)` returns
 only the first (~200-byte header) frame, and Python
 `ZstdDecompressor().stream_reader(f)` behaves the same way -- so the session
 renders as EMPTY and looks like it does not exist. Split on the zstd magic
 `28 b5 2f fd`, decode each frame, and widen the window when a magic sequence
 occurs by chance inside compressed data. Frames that still fail must be COUNTED:
 a partially decoded transcript is a transcript with a hole in it.

2. THE STORE IS TWO PLACES. `$DSH_HOME/sessions/<slugified-cwd>/<dir>/` and
 `$DSH_HOME/sessions-archive/<slug>/<dir>/` (moved there by
 scripts/session-corpus.mjs). A reader that knows only the live tree answers "no
 such session" for a session that exists. Also: the format version differs per
 machine (v3 here, v4 there) -- match /^session\.v\d+\.jsonl\.zstd$/, never a
 literal v3.

3. THE DECODING MACHINE IS NOT THE STORING MACHINE. `secratary` runs node
 v20.20.2, where `zlib.zstdDecompressSync` is `undefined` (needs node >= 22.15),
 and a python3 with no `zstandard` module. So decode LOCALLY, on the caller's
 machine, and never make zstd a remote dependency. `ssh host hostname` proved
 the point cheaply: the same node runs DSH perfectly and cannot decompress a
 session at all.

4. THE AUTHORITY DB IS A LAGGED COPY, NOT THE ORIGINAL. Ingest runs every 30 min;
 at 2026-10-09 02:15Z dsh_sessions' newest phone session started 01:27Z while the
 file store already had one at 01:42Z. `dsh_session_events.created_at` is INGEST
 time, not event time (one session carries 24 distinct values), and the
 /owner/dsh-sessions/search endpoint returns `Missing/invalid DSH session ingest
 key` without the token -- which reads exactly like "no results" and is not.
 Ground truth is the file.

5. GUI CHATS AND SUBAGENTS SHARE THE STORE. A directory named `session-<uuid>` is a
 chat the owner had; a bare `<uuid>` is a subagent -- and a fleet of subagents
 dominates by count (32 sessions on secratary in 3 days, 4 of them real chats).
 That prefix is only a CONVENTION: the transcript header's `origin` /
 `parentSession` is the authority, and a reader must print the header value, not
 the guess.
