**L1678 · A dry-run flag that executes is worse than no flag: Python sqlite3 autocommits DDL so my gate's --dry-run really created five views; plus a gate must demand the rule (detect a silent failure) not one implementation of it**

**L1678 · A flag that lies is worse than no flag: this gate's `--dry-run` executed DDL, and Python's
`sqlite3` runs DDL in autocommit so the rollback undid nothing. Found 2026-09-16 by using it.**

`recon-apply.py`'s dry-run path did `cur.execute(op["sql"])` then `con.rollback()`, which is correct
for `INSERT`/`UPDATE`/`DELETE`. I pointed it at five `CREATE VIEW` operations and it reported
`dry-run`, and then `--apply` failed all five with `view ... already exists`.

**The reason is a CPython behaviour worth knowing exactly:** with the default `isolation_level=""`,
`sqlite3` opens a transaction implicitly only before DML (`INSERT`/`UPDATE`/`DELETE`/`REPLACE`).
**DDL statements execute in autocommit mode, so they commit immediately and `rollback()` cannot undo
them.** A "dry run" of `CREATE VIEW` is a real schema change. Nothing was damaged here — views are
additive and these were wanted anyway — but I only know that because I checked, and the next person to
point that flag at a `DROP` would not be so lucky.

**Fixed so the flag stops lying:** DDL is now *never executed* in dry mode. It is validated and
reported as `dry-run-validated` with the reason stated, because a preview of an irrevocable operation
is not a thing this tool can honestly offer.

**Three things this is an instance of, all recorded elsewhere in this tree:**
- **Verify the tool you built by using it on real work, not on a test.** The self-test I ran earlier
 used `INSERT` and a deliberately-refused `DELETE` and passed — it exercised every branch except the
 one that was wrong. A synthetic plan proves what you thought to test.
- **Check the effect, not the report.** `--apply` saying `already exists` is how I learned the views
 were live; the `--dry-run` line saying `dry-run` was worth nothing.
- **A gate that refuses correct work gets switched off.** The same session, the same gate, refused all
 five views for having no `affected` count — a row count is meaningless for `CREATE VIEW`. The rule is
 "this operation must be able to detect its own silent failure"; for a write that is a row count, for
 DDL it is a `verify_sql` that reads the object back. So the gate now demands the *rule* rather than
 one implementation of it, and it RUNS the verify query after applying so "created" is a measured
 value rather than an exit status.

**And the payoff of the thing this round actually shipped:** `/communications/summary` went from
`ok: true, cutover_ready: true` with `recent_call_count: 0` to `ok: false, cutover_ready: false` with
four dialpad warnings and a real `dialpad` block — 12,630 calls, 125,137 deduped texts, 28.8% recording
coverage, 68.3% transcript coverage. The endpoint had been affirmatively reporting readiness about a
business line it could not see. **Turning a green light red is the deliverable when the green light was
the lie.**
