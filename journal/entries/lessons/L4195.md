## A label and its payload must be read by ONE rule — three shapes, measured on the staff filter surfaces

Fixed on 2026-10-14 (PR 444, repo `phone-and-tech-full`). All three shapes came from the same
root: **a control whose label is written in one place and whose payload is decided in
another**. Each one is reproducible in the source, and each has a mechanical test that
fails if it returns.

### Shape 1 — the value the server does not have (the quotes `Pending` tab)

`QuoteListPage` sent `status: 'PENDING'` to `repairQuote.list`. `QuoteStatus` is
`backend/prisma/schema.prisma:5429-5435` = DRAFT, SENT, ACCEPTED, REJECTED, EXPIRED,
CONVERTED. **`PENDING` is 14 lines below it, in `CustomerQuoteStatus` (`:5443-5447`) — the
enum for a DIFFERENT model** (`Quote`, not `RepairQuote`). `z.nativeEnum(QuoteStatus)` refused
the value, so the tab showed an empty table forever and `stats.pending` was a hard 0.

**Transferable:** when a label needs a value the server's enum does not have, read the
NEIGHBOURING enums before inventing a mapping — a schema file with two similar enums is where
a borrow looks correct in review. Then make the test read the enum out of the schema, so the
frontend list cannot drift again:

```ts
const block = new RegExp(`enum\\s+${name}\\s*\\{([^}]*)\\}`).exec(schema)
```
Two existing tests in this repo already did exactly this (`work-order-status.test.ts`,
`OrderManagementInterface.status-filter.test.tsx`) — copy the house pattern instead of
inventing a guard.

### Shape 2 — the count taken from the filtered payload (all five quotes cards)

`stats` was built from the ALREADY-status-filtered response
(`QuoteListPage.tsx:548-558`), so on any status tab all five cards printed that tab's numbers
under the whole list's labels. `Total Quotes` showed the accepted count while Accepted was
selected. The audit that found this reported ONE card; the defect was five.

**Transferable:** a count and the list it labels must come from the same set. Fix it by
fetching once without the filter, applying the filter to the rows, and asserting the
invariant that makes drift impossible:

```ts
expect(counts.ALL).toBe(quotes.length)
expect(counts.ALL).toBe(sumOfEveryStatusCount)
```
**And when someone reports one lying control, look at the siblings before you fix it** — the
under-report was the more expensive half of this defect.

### Shape 3 — the control fed a payload its parent already narrowed (FAQ `All Status`)

`FaqTable` carried its own `All Status` select, and `FaqManagementPage.tsx:60-65` handed it
`filteredFaqs` — already narrowed to the page's tab. Under Published, `All Status` and
`Drafts` could only ever return an empty table.

**Transferable:** one control per dimension. Two controls for one dimension is only safe when
they are two views of ONE state (which is what the counter fix of the same day did with its
chip + radio). Here the honest move was to REMOVE the duplicate rather than re-point it,
because re-pointing means the select must be able to switch the page's tab, and "All Status"
on the table would then swap the table for a different component.

### The structural fix, which generalises

`quote-status-scope.ts` holds `QUOTE_STATUSES`, `quoteMatchesTab`, `countQuotesByTab` and
`isConvertibleQuoteStatus`. The page sends **no status at all**, counts every tab from the
complete response, and filters the rows with the same function — so a count and the list it
labels cannot disagree. The original defect was two readers of one idea; the fix is one
reader and no second copy.

**Find every surface.** The same retired `PENDING` also sat in
`components/quotes/QuotePreviewDrawer.tsx:119` (so the drawer's Convert button could never
appear on a real quote) and the same counting defect sat in an UNMOUNTED component
(`RepairIntakeCaseCreatePanel`). `grep` the value across the repo and fix every surface at
once — `AGENTS.md` §6.3 exists because a fact stated in three places has three ages.
