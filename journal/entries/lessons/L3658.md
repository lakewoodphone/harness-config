**L3658 · Correcting P3007: the rule path works, the resolver works, and my harness was the bug**

2026-10-13. Two corrections to P3007, both mine. P3007 said his answer "cannot teach the system
anything" and called the plain-words-to-category resolver "the missing piece". The resolver works and
the rule path works. I overstated a narrow defect into a broken feature.

WHAT IS ACTUALLY TRUE, proved end to end on copies with the REAL ledger as the category source:
 "yes, AI & API Services" -> category 'AI & API Services' rule_created=True
 "yes, Office & Shipping" -> category 'Office & Shipping' rule_created=True
 "yes" -> no rule, because the QUESTION's suggestion was 'shop supplies'
 "shop supplies" -> no rule, because it is not a category
and the rules file gained two rows, each `created_by: "owner"`, confidence 0.99, carrying the question
and his answer as evidence. So the objective's "answers persisted as durable rules" is IMPLEMENTED and
works the moment the answer names, or agrees with, a category the entity holds.

THE NARROW DEFECT THAT REMAINS, and it is real but small: the question he was sent at 03:30 carries
`suggest_category='shop supplies'`, which is not a category for lpt (measured: `select count(*) from
categories where lower(name)='shop supplies'` is 0, and no lpt category mentions supplies at all - the
lpt list is 33 names including "Merchandise & Inventory", "Office & Shipping", "Materials &
Equipment"). So an unqualified "yes" to THAT message files nothing. The cause was the bare-body
fallback hardcoding that phrase, which W... fixed at source; the live row still carries it because the
question has already been sent.

THE SECOND CORRECTION, and the one worth keeping. While testing I concluded the path IGNORED his own
words - I sent "yes, AI & API Services", an exact category name, and got the suggestion branch back.
I was about to report that as a bug when I checked the resolver directly and it matched perfectly. The
fault was in MY HARNESS: I had passed the asks-store copy as `acct_db`, and `acct_db` is the
ACCOUNTING database the resolver reads categories from. Pointed at the asks store it finds no
categories, so EVERY phrase failed to resolve and every answer looked broken. One wrong keyword
argument made a working feature look catastrophically broken, and the only thing that caught it was
testing the unit directly against the same call the end-to-end test was making.

RULES I AM KEEPING FROM THIS.
1. **When a test says a whole feature is broken, test the smallest unit inside it before reporting.**
 A blanket failure is more often the harness than the code, because real code rarely fails
 everywhere at once.
2. **Correct an overstatement as loudly as an error.** P3007's "cannot teach anything" was wrong in
 the direction that makes things look worse, and a future session reading it would rebuild a
 resolver that already exists.
3. Name the database a parameter expects, in the test as well as in the code. `acct_db` looked
 harmless next to `path`.
