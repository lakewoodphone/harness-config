**L1812 · Reading tiny print off phone photos (crop+upscale, EXIF orientation) and fetching Gmail attachments when no action can (relative gmail token dir)**

**Two techniques, both proven 2026-09-16 while reading Eliyahu's contact-lens vials off phone photos.**

### 1. Reading tiny print on a curved vial: crop + upscale, don't trust the downscale

The harness downscales any image it hands the model (~1773 px on the long edge, ~692 px preview). A
pharmacy label on a 20 mm vial photographed at arm's length is unreadable at that size — and *guessing*
digits off a scaled photo is exactly how "CYL -0.075" and a wrong eye assignment get written into a
record. What worked, on Windows, no extra installs:

1. `Add-Type -AssemblyName System.Drawing`; open the JPEG; read **EXIF 0x0112** and `RotateFlip`
 accordingly — iPhone photos are stored landscape with orientation 6, so raw `Width/Height` are
 transposed relative to what the model shows. **After rotating, re-read `$bmp.Width/$bmp.Height`**;
 computing the rotated size by hand transposed the crop and produced four useless images.
2. Crop a *fractional* box of the corrected frame and redraw it at 5-8x with
 `InterpolationMode::HighQualityBicubic` into a new Bitmap.
3. Read the crop. A 0.24 x 0.075 box of a 3024x4032 frame at 8x gives ~6300x2400 px, which survives the
 harness downscale and renders label text **larger than the original pixels**.
4. Read the same field in **two or three different photos** before believing it. `D` vs `S` (OD vs OS)
 is the whole answer on a lens label; only agreement across angles makes it safe.

Script kept at `~/code/_scratch/crop-tight.ps1` (parameterised: Names, X0/X1/Y0/Y1, Scale, Dest, Out).

### 2. Getting a Gmail attachment: there is no action for it

- `ps_action gmail_search` **works and takes an `account` parameter** — `account:
 "lakewoodphoneandtech@gmail.com"` searched that mailbox when the default `primary` returned 0 rows.
 (`account: "all"` is not mapped and fails.) It reaches live mail that the `email_catalog` table does
 not contain at all.
- **No action can read a message body or download an attachment**: `gmail_get_message` exists but
 "has no `run()` function"; `gmail_read_message` is only `GET /gmail/messages/{id}` in `app/main.py`.
- The working path is a script run **on the authority**:
 `_build_service(settings, account)` → `users().messages().get(format="full")` → walk
 `payload.parts` → `users().messages().attachments().get()` → base64url-decode and save, then `scp`
 back.
- **Trap, cost me one failed run:** `settings.gmail_tokens_dir` is the *relative* path
 `data/gmail_tokens`. Run the script with `os.chdir("/home/zabz/personal-secretary-mvp")` first, or
 every account reports "not authenticated" while the token files sit right there on disk. A relative
 config path plus a non-root cwd looks exactly like a missing credential — it is not.
