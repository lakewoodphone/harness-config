**A forced run must clear every gate the scheduled run checks -- and the result must distinguish
"ran" from "quoted an old status".**

Measured 2026-09-15, minutes after shipping the first version of P149's fix. I added the syncs to
the on-demand dispatch, cleared the in-memory day guard I had found by reading
`_maybe_sync_amazon_transactions`, and called it. The response was:

 {"ok": false, "ran": false, "status": "ok",
 "detail": "eBay sync complete -- 0 new transactions ingested into accounting.db."}

`status: ok` and a detail line describing a successful sync -- from the run at 14:47, quoted out of
`subsystem_health`. Nothing had run. The gates I had not read were a **persisted** `last_ran_at`
checked by a restart-safe guard ("if the sync already ran today, in this process OR a previous
one, skip"), which is invisible from the in-memory attribute, and the scheduled hour (`04:15`),
which would block any manual run before it. Clearing all three fixed it, and the restore path keeps
the daily schedule where it was (`ebay_sync_time` still 04:15 afterwards).

Rules:
- When adding an on-demand path for something scheduled, enumerate the gates by reading the
 scheduled path end to end; do not infer them from the first `return` you find.
- Report **whether the work happened**, from a marker that changes only if it did -- not from the
 status field, which is sticky and will happily describe the previous run. This is L1515 once
 more (a representation is not the value), and it nearly produced a "verified" claim for work that
 never ran.
- A manual trigger that declines should name its gate ("disabled", "breaker_tripped"), because a
 silent no-op is indistinguishable from a successful one at the call site.
