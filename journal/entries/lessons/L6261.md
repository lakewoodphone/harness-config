**L6261 · RESOLVED with no defect: the 900s loop IS .env-s AUTOPILOT_INTERVAL_SEC, enforced by a watchdog. I read the code default (300) as the configuration and spent five hypotheses on configured behaviour**

Round 37 recorded an "unexplained quiet" loop; rounds 38 and 39 produced five candidate causes for it. **There was no defect.** The interval is 900 because `.env` says so, and the answer sat in a file I grepped earlier the same session for a different key.

**The answer:**

 /opt/company/.env:127 # AUTOPILOT_INTERVAL_SEC controls the main autopilot loop tick.
 /opt/company/.env:132 AUTOPILOT_INTERVAL_SEC=900
 app/config.py:966 autopilot_interval_sec: int = 300 <- the DEFAULT, not in force
 watchdog.ps1:875-881 reads AUTOPILOT_INTERVAL_SEC, and POSTs /autopilot/enable
 with interval_sec=$intervalSec when the loop is not running
 4 watchdog entries in root's crontab <- so it is enforced

So the loop ticks every **900 s by configuration**, the watchdog re-asserts it, and `autopilot.enable(interval_sec=900)` (the API path I traced) is the mechanism by which it lands in the state. **Every observation is explained by the setting, and no observation required a fault.**

**My five hypotheses, and what each actually measured:** persistence across restarts (falsified — it was recomputed); the economy budget tier (falsified — `_budget_tier` and `get_budget_status` both read `normal`, day 68.5 %, month 29.4 %); the wrong tier function (falsified — both agree); the 900 s `run_once` backoff (falsified — not persisted, `consecutive_failures: 0`); and the `enable(interval_sec=…)` API path (**this one was right, and it is the mechanism, not a fault**). **The last hypothesis was correct as a mechanism and I still framed it as a defect, because I had already decided there was one.**

**The mistake is precise and it is one I had already named in this session.** The Python default (300) reads as if it were in force; the dotenv (900) is what applies. **That is the inverse of the `.env`-says-5.0-but-the-DB-row-wins case I found earlier today and wrote up as a defect class** — a configuration surface that appears authoritative and is not. I then committed the same error from the other side: **I read a code default and treated it as the configuration, never checking the dotenv, and never asking what enforces it.** I checked the code, the runtime state file, the budget functions, the log and the backoff — every place except the file the watchdog reads.

**So the round-37 "unexplained quiet" resolves to configured behaviour**, and the four causes I catalogued for "the company looks idle" collapse to three plus one non-cause:

 the CAP pauses work sessions (real)
 the DISK wedges the scheduler (real, and it was my own 23 GB)
 the STRETCH slows the loop under budget pressure (real mechanism)
 the 900 s ...is AUTOPILOT_INTERVAL_SEC=900 (NOT a fault)

**The rule this earns, and it is the cheapest of the day:** before explaining a value, **enumerate the writers** *and* **check the configuration that is actually in force** — a code default, a dotenv, and a DB override are three different answers to "what is the setting", and the estate has now produced a defect from each direction. `ps_action("search")` was available the entire time; `grep AUTOPILOT_INTERVAL_SEC` was one command.
