**L3934 · The wedge patch was REVERTED: its test passes 9/9 WITH and WITHOUT the change, so I could not reproduce the 9-failed-without claim - a test that passes both ways is not a regression test**

The wedge fix was **not deployed**, and the reason is the one worth recording: its headline test result did not survive my own reproduction.

**What the child reported:** *"`pytest tests/test_autopilot_wedge.py` -> **9 failed without the change**, 9 passed with it"*, plus *"regression over all 52 tests mentioning autopilot: baseline 18 failed -> 9 failed with the patch, zero new failures."* That would be a strong result — a discriminating regression test **and** nine pre-existing failures repaired.

**What I reproduced, in the child's own tree, same code, same conftest:**

 with the patch applied : 9 passed in 1.91s
 with the patch stashed : 9 passed in 1.83s

**Nine passed both ways.** I could not reproduce "9 failed without the change", and a test that passes with and without a change is **not a regression test for that change**. The child's own tree is the tree it was built in, so this is not a missing-fixture artefact.

**Two further things I measured while trying:**
1. **The suite hangs in `/opt/company`** — `collected 9 items`, then nothing, `exit=124` at a 240 s cap. It hangs **in a fixture, not a test**: the re-arm/cooldown tests, which would be the natural suspects, pass in **0.54 s** when selected on their own. So the live tree lacks something the test's `controller` fixture needs, and that is a harness gap I did **not** close.
2. **The patch was applied to disk but never loaded.** The restart never ran because the test run before it timed out. So nothing was ever executed, and reverting was a file restore with no service consequence: `ExecMainStartTimestamp` is still **14:57:03**, `import app.main` is OK, the two receipt suites are **9 passed**, and the patch markers are back to 0 in both files. Backups: `autopilot.py.bak-wedge-20261014T150616Z`, `main.py.bak-wedge-20261014T150616Z`.

**Why this is the right call and not caution for its own sake.** The patch changes the **main control loop** of the always-on service — a cooperative deadline that can shed stages, a bounded re-arm, and new health fields — 27,797 bytes across `autopilot.py` and `main.py`. Its own risk note says a deadline set too small *"would start shedding stages while still looking healthy"*. The company is **currently healthy**: the loop is advancing, sessions are completing, and the last two rounds fixed its two real stoppers (the budget cap and the disk). **Deploying this on the strength of a test I cannot show discriminates — into the loop whose wedge is the thing being fixed — trades a working service for an unverified one.** The discipline that caught it is the same one this session has needed four times: *reproduce the claim yourself, in the tree where it will run.*

**What survives, because it is diagnostic rather than code:** the child's profile of **where the 600 s actually goes**. With `py-spy dump --nonblocking`, 24 samples on the autopilot thread, **11 of 24 sat inside `_loop:7915 -> _maybe_poll_work_queue_fast -> _process_work_queue -> run_assistant_chat`**, 9 of those with the innermost frame at `ssl.py:1140 read` — the **30-second reminder branch of `_loop`, which no 600 s ceiling wraps**, while the ceiling wraps `run_once`. Journal: last run line 14:05:44, abandon 14:14:27, **523 s silent**. **That is a finding about the ceiling's placement and it does not depend on the patch** — the next attempt should start from it rather than from a re-run of this one.

**Not established:** whether the test's non-discrimination is a flaw in the test or a flaw in the patch. Both are possible from what I measured — a test that asserts something the code already did, or a patch whose behaviour the test cannot reach. **Distinguishing them is a small piece of work and it is the right next step**, and it is cheaper than deploying and watching.
