**L3924 · The Amazon receipt gap is DISCOVERY not parsing: 289 receipts match the query and only 30 are read (max_emails=30), while eBay has no date bound - measured before touching the 69KB parser**

The Amazon receipt gap is a **discovery limit, not a parser defect** — measured, before any code was touched.

**The measurement (child 47, read-only Gmail probe through the app's own `gmail_service`):**

 amazon query from:amazon.com (delivered OR shipped OR ordered) newer_than:90d -> 289 messages
 the caller max_emails=30 -> 30 read
 ebay order (NO date bound) -> 130
 ebay general newer_than:90d (+50d) -> 146, caller passes 50+50

**289 Amazon receipts match the query and only 30 are ever examined — about 10 % coverage**, which is precisely the shape measured in `purchases`: 113 Amazon rows against 3,934 eBay rows, with only 10 of the 113 carrying items. **And the reason eBay is healthy while Amazon is not is now visible in one line: eBay's query carries no date bound and its batch is 50+50; Amazon's is clamped to `newer_than:90d` and a batch of 30.**

**Why this matters more than the count.** The failure looked like a parser problem — 8.8 % of Amazon rows carry items against eBay's 97.7 % — and the obvious repair would have been to rewrite Amazon item regexes inside a 69,695-byte parser that already documents four past defects in its own comments. **That would have been work on the wrong thing.** The parser was never given the messages. Taking the two minutes to measure *how many messages the query returns versus how many are read* is the whole difference between fixing the pipeline and tuning a component that is not the constraint.

**It also settles the two questions I could not answer from the table alone:** whether Amazon was failing to find the emails or failing to parse them (**finding**), and whether `days_back=90` explained a window starting 2026-07-02 (**it does** — 90 days back from today is exactly that date; the table's eBay rows go back to 2026-07-02 for the same reason, not because of a data loss).

**The fix is therefore a batch/query change, not a parser change**, and the child is building it with a measured recovery count against a **copy** of the database rather than an estimate. **Not yet done, and I am not claiming it:** the exact new values depend on how long `read_message` takes at volume — the caller's own comment says *"small batch — read_message is slow"*, so 289 messages is not free and the right answer may be a backfill plus a smaller steady-state batch rather than simply 30 → 300. That trade-off is the child's next measurement.

**And the two `*_sync` subsystems stay retired.** Nothing about this revives `amazon_sync`/`ebay_sync`: those are the browser scrapers, and the capability lives here, in `receipt_parser.py`, reading email — which is what the owner said it should do.
