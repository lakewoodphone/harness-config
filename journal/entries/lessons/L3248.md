**L3248 · The mesh dies because a dispatched child's task begins with '---', and the fix needs TWO '--' separators, not one: the launcher and the booted app each consume one**

MEASURED 2026-10-05, and it matters because the mesh is how work fans out.

A meshed child was rejected before it started:
 error: unknown option '--- mesh mailbox (read this before the task) --- MESH_MAILBOX={dir:...}'
 exit = 1 in 3130 ms

CAUSE. A dispatched child's task IS the mailbox preamble, which OPENS WITH `---`. The task is handed
to `dsh` as one argv word. The LAUNCHER does not reject it -- it forwards it as an operand. The BOOTED
APP does: `@deepseek-ai/dsh-headless/lib/startup.js:21` declares `.argument('[task...]')` with no
`allowUnknownOption()`, so a word beginning with `-` is classified as an unknown option and the run
ends before a turn exists. (Same class as a task that is a bulleted list, a diff, or a `--flag`.)

HOW MANY SEPARATORS. `--` is the fix, but the argv is parsed TWICE -- once by the launcher, once by
the app -- and commander's literal branch drops ONE `--` per parse (`commander@15` lib/command.js
:1789-1793). So ONE separator is consumed by the launcher and the app still receives a dash-leading
word. The task needs `-- --`. Measured by driving the REAL dsh-headless startup provider and reading
the published `headlessStartup.task`:
 zero separators -> app publishes nothing, exit 1, `unknown option '--- mesh mailbox`
 one separator -> launcher swallowed it, app still gets the dash-leading word, same failure
 two separators -> app publishes the task BYTE FOR BYTE, exit null
Proof: `scripts/mesh/tests/dsh-dash-task-argv.test.mjs`, 5/5, spawns the real bin.js and the real
dsh-headless/dsh-cmdline parse; no profile boots and no engine is started.

NOT SETTLED BY A `--dump-config` PROBE. I tried to confirm this with
`node bin.js --profile headless --dump-config -- <task>`; that path ACCEPTS the dash-leading word as an
app argument in all three cases and therefore cannot see the failing parser. `--dump-config` intercepts
BEFORE the headless app's own commander program. A probe that does not reach the layer that fails is
not evidence about it -- which is why the measurement above drives the real startup provider instead.

STILL OPEN, found on the same pass and NOT fixed: `packages/plugin-remote-fanout/bin/mesh-run.mjs:462`
spawns `['--profile','mesh','headless',prompt]`, and `headless` is not a subcommand of the installed
dsh-headless, so every mesh-run dispatch hands the dispatcher a task with a stray leading word
(`headless do the thing`). Dropping a word changes what the dispatched agent is told, so it is its
owner's call, not a mechanical edit.

CONCURRENT WORK, AND WHY THIS NOTE EXISTS. While this session measured the defect, ANOTHER live session
was fixing the same file in the main tree -- uncommitted, and using a SINGLE `--`
(`packages/plugin-remote-fanout/lib/remote-script.js`, `export const END_OF_OPTIONS = '--'`, and the
POSIX twin `shellWord(END_OF_OPTIONS)` once). That fix does not fix the reported failure for the case
that actually broke, because the task IS the `---` preamble. The reference fix with two separators is
on branch `fleet/dsh-meshfix` (worktree C:\Users\ezabz\Code\_worktrees\hc-dsh-mesh, commit 8e036ba) and
it deliberately was NOT integrated over the other session's in-flight work. Delta to apply: make
END_OF_OPTIONS a doubled separator, and the same in Start-AgentFleet.ps1:156.
