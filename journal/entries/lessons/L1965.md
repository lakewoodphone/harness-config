**L1965 · A 403 from a plain urllib check is not downtime - it is usually the user-agent being blocked**

MEASURED 2026-09-17, and it nearly produced a false crisis report - the single worst failure class in this system's history.

WHAT HAPPENED: checking whether the shop's Netlify sites were affected by an out-of-credits account, python urllib.request returned HTTP 403 for https://lakewoodphoneandtech.com and https://test.lakewoodphoneandtech.com. 403 reads like 'forbidden/down'. It was not. Re-requesting the SAME URLs with a browser User-Agent returned HTTP 200 from server=cloudflare. The sites were up the whole time; urllib's default User-Agent (Python-urllib/3.x) is simply refused by Cloudflare-style WAFs.

RULE: before reporting any site as down, re-check with a browser User-Agent AND Accept header, and record the server header. Only believe a failure that survives that. A 403 with server=cloudflare is a bot block until proven otherwise; a 5xx or a connection error is much stronger evidence of real trouble. The same applies to any HTTP probe written in a script rather than a browser.

ALSO LEARNED IN THE SAME CHECK, and the reason the distinction mattered: an out-of-credits Netlify account BLOCKS NEW DEPLOYS but does NOT take existing published deploys down. All 7 published sites on the account were still serving normally. So 'deploys are blocked' and 'the site is down' are different claims and must not be merged - the first was true, the second was false and would have been alarming.

COROLLARY ON EMPTY/NEGATIVE RESULTS: one site on the account (papaya-palmier-5c4ba0, linked from personal-secretary-mvp/.netlify/state.json) genuinely returned 404 - but the API showed published_deploy=False, so it is a linked site that was never published, not a broken deployment. Distinguish 'nothing was ever there' from 'what was there is gone' before reporting either.
