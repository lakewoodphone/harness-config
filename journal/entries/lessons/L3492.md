**L3492 · Android scans: find /sdcard silently finds nothing, and on FBE a deleted file is cryptographically gone - check ro.crypto.type and the f2fs mount options before promising anything**

Measured on the IRIS Easy Flip (Coosea SL006-CC, Android 12, MediaTek MT6739WW) while scanning it for a
deleted video, 2026-10-11. Four rules, each of which cost a real answer in that session.

**1. `find /sdcard ...` returns NOTHING on Android, and it is silent about it.** `/sdcard` is a symlink
to `/storage/self/primary`; toybox `find` does not follow symlinks without `-L`, so it never descends
and prints no error and no warning. Two of my own early answers - "no `.trashed-*` files anywhere" and
"no `.thumbnails` directories" - were false negatives: `.thumbnails` exists under `Movies/`, `Pictures/`
and `Music/`, and I had already *listed one* in the same session. **Search an Android volume by its real
path: `/storage/emulated/0`.** `ls` and `content query` are unaffected. The general form of the trap: an
empty result from a tool that cannot traverse is not evidence of absence.

**2. On a file-based-encryption Android, a deleted file is CRYPTOGRAPHICALLY unrecoverable - not low
odds, impossible - and you can prove it in two commands before promising anyone anything.**
- `getprop ro.crypto.type` -> `file` (FBE). Each file's content key is wrapped in that file's own
 metadata; deleting the file destroys the wrapped key while the master key stays in the kernel keyring.
 A raw dump through *any* route - rooted, chip-off, ISP, a data-recovery lab - is ciphertext whose key
 no longer exists. The same wall already closed the Samsung S21 and the Quin factory-reset cases.
- `cat /proc/mounts | grep f2fs` -> `discard` present (and `alloc_mode=reuse`) means freed segments are
 trimmed and handed straight back for reuse.
So on such a device: no undelete, no lab referral, no quote. This is the check that turns "0-5%" into
"impossible", and it costs two minutes.

**3. Never root-and-unlock to chase deleted data. `fastboot flashing unlock` WIPES userdata**, so the
"unlock the bootloader" step that every SL006/MTK how-to page recommends destroys the exact evidence the
job exists to find - and with FBE it would not have helped anyway. On this handset there was no root path
at all: user build (`ro.debuggable=0`), `shell` cannot read `/dev/block/dm-6` (`brw------- root root`).

**4. A phone's clock can be badly wrong, and its *files* can still be trustworthy.** This handset booted
with no usable RTC and reported `Wed Nov 13 01:59 EST 2024` against a host date of 2026-10-11, stamping
its standard media directories with 2024-11-13 on the way up. But the 2026 mtimes are good, because the
filenames carry the same date to the minute (`IMG_20261007_192147_318.jpg` at 19:21). So: date a device's
history from filename-vs-mtime agreement, never from a clock reading taken now. A directory's own mtime
is still the best "something was added or removed then" marker available without root - on this handset
`DCIM/Camera` read 2026-10-07 23:36 while its newest file was 19:21, which dates the deletion.

**What survived on the handset, and it was not the video:** `com.android.gallery3d`'s BlobCache
(`imgcache.0`, 51.5 MB) still held 1,259 decoded JPEG thumbnails, pullable with one `adb pull`; carving
them is 40 lines (`lpt-hub/tools/phone-scan/carve_blobcache.py`). The gallery's `bookmark.0/1` holds no
readable paths, `.thumbnails` had already been cleaned by MediaProvider when it deleted the rows (all 5
survivors belonged to live videos), and a 596-row MediaStore reconciliation found no orphaned row - so
nothing named the deleted file. On a phone, caches can prove a file existed and can hand back a *picture*
of it; they never hand back the file.
