## LESSON — `--basetemp` has now produced two false failure sets in one session; put it outside the repo, always

**What happened, twice in the same round.**

1. A full suite run reported **24 failures** where the author of the change had reported 5. Nineteen
 of mine were caused by pointing `--basetemp` INSIDE the repo. `test_pilot_capture.py` has its own
 guard, and the failure message says exactly what happened once you read it:

 error: refusing to capture frames into the repository at
 C:\Users\ezabz\code\_scratch\kf-speed\.btone\test_an_unknown_serial_is_refused0
 ... or: pass --allow-in-repo

 With the temp dir outside the repo: **38 passed**. The suite was never broken.

2. Earlier in the same session, twice more, pytest errored because the `--basetemp` PARENT directory
 did not exist - an error that presents as a collection/code failure rather than a path problem.

**Why this belongs in the journal rather than in a scratch note.** Both times the output looked like
a regression in somebody else's work, and the second time it was one keystroke from being reported as
"the lane's suite does not pass". A wrong red is as expensive as a wrong green: it points at innocent
code and it costs the credibility of the next real red. The whole reason the constitution insists on
reproducing every claim is that instruments lie - and the cheapest lie available is a badly chosen
argument.

**The rule.** On this host, run pytest as:

```powershell
$outside = Join-Path $env:TEMP "kf-basetemp" # OUTSIDE any git worktree
New-Item -ItemType Directory -Force -Path $outside | Out-Null
python -m pytest -q --basetemp="$outside\<run-name>" <paths>
```

- The parent must EXIST before pytest runs.
- It must NOT be inside the repository, because at least one test in this repo asserts that a CLI
 refuses to write there, and a few others inspect their own paths.
- When a run's failure count disagrees with whoever wrote the change, suspect the harness before the
 code, and change one variable at a time. Here, moving the temp dir alone took 24 failures to 0.

**And the meta-rule this is an instance of:** when a reading surprises you, ask what ELSE the
instrument is measuring. A fresh `docker exec` process measures the constructor, not the server
(`L3335`). A temp dir inside the repo measures the repo guard, not the tests (this entry). Neither
instrument was broken; both were answering a different question than the one asked.
