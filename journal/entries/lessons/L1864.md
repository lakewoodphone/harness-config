**L1864 · A hot-patched container can hold code that exists in no image - rebuild after docker cp or the next recreate silently reverts the fix**

Mechanism, measured 2026-09-17 on the waze-mdm host: docker cp wrote the fixed nanomdm_client.py into the RUNNING fleet-api container (started 04:00:53Z, restart at 04:01:40Z), and the running container then carried md5 00df224d while the image fleet-api:local still carried the old a5c44ccf. The code directory is not bind-mounted (only profiles/, wallpapers/source and two volumes are), so nothing but the container's writable layer held the fix: any docker compose up --force-recreate, docker rm, or host reboot that recreates the container would have silently reverted a live fix, and the correct image existed nowhere. Fix: after any docker cp hot patch, run docker compose build <service> from the host build context (which must already contain the same file) and verify the image's copy by hash - docker run --rm --entrypoint md5sum <image> /srv/<file> must equal the running container's. Done 2026-09-17: image rebuilt, both now 00df224d, running container untouched and /fleet/health verified after.
