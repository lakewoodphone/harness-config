**L1614 · An unreadable table must answer 503, never ok:true/total:0 — and check namespace-package shadowing**

The single most useful rule from this job: **a route that cannot read its table must answer 503, never `{"ok": true, "total": 0}`.**

Evidence: `deploy/fleet-dashboard` in integrated mode with a missing/empty `secretary.db` answered `GET /api/v1/fleet/devices → 200 {"ok": true, "total": 0}` and `GET /api/health → 200 {"ok": true}` while `locations/latest` and `poll` raised. The UI then rendered "0 devices" with a fresh "Last updated" timestamp every 30s, and health said ok. An empty result is a refusal, not evidence of health. Fix shape that worked: a `db_failure(exc, source=...)` helper returning `{ok:false, error, measured:false, note:"...this value is unknown — not zero"}` at 503.

Two more durable mechanics:

1. **Partial success must not be 2xx-with-ok-true and must not be silent.** `207` + `ok:false` + per-device `failures` keeps transport semantics honest while a client that only checks `res.ok` still cannot read "3 of 65" as success.

2. **If a backend answers HTTP 200 with a failure marker in the body, the frontend will lie about it.** `fetchJson` only threw on `!res.ok`; the routes always returned 200. Result: clicking "Erase Device" with NanoMDM unreachable toasted `✓ erase-device` and a JSON blob ending `"ok": false`. Two-sided fix: routes must fail the status code AND clients must read the body's `ok`. An `ApiError` class that carries the parsed body keeps the per-device failures visible on a 502.

Python packaging gotcha worth keeping: `deploy/fleet-dashboard/backend/routes/` and `services/` had **no `__init__.py`**, so they were namespace packages and an unrelated `routes` package installed in site-packages (`%APPDATA%\Roaming\Python\Python313\site-packages\routes`) won the import — `from routes.health import ...` failed with `ModuleNotFoundError: No module named 'routes.health'`. Adding `__init__.py` to both made them regular packages found in the first `sys.path` entry. Namespace packages lose to any regular package later on the path; if a subdirectory imports "for no reason", check for a shadowing installed package before anything else.
