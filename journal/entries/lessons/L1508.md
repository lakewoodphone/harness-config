**L1508 · An alert is a lifecycle, not a row: age it on the observation clock, clear it where you raise it, never measure a closed channel**

**An alert is a lifecycle, not a row. Age it on the observation clock, clear it on the same signal
that raised it, and never measure a channel the owner deliberately closed.**

Four separate failures, all measured on 2026-09-15, all the same disease -- something that was true
once stays on the record forever and makes every reader of that record blind:

1. **No ageing code at all.** `owner_message_queue` had none; the `expired` rows in it came from
 one-off scripts. So 163 undelivered rows accumulated, 40 of the 42 urgent/critical ones were
 daily briefings from 2026-08-06 onward, and the badge read "7 critical, 35 urgent held" --
 CRITICAL -- for five weeks. An alarm that can never go green is an alarm that gets ignored.
2. **Age on the wrong clock.** The clock must be `COALESCE(last_seen_at, created_at)`, where
 `last_seen_at` means "when was this condition last observed" (it is stamped only on a dedup hit).
 `created_at` alone would expire a sync breaker that is firing right now; and I had written
 `record_owner_message_send_failure` to stamp `last_seen_at` yesterday, which is not
 re-observation -- a five-week-old briefing that failed to send would have looked freshly seen and
 the new policy would have died on its first day.
3. **Clear it where you raise it.** `amazon_sync` and `ebay_sync` raised `sync_needs_login` rows at
 16:49 on 2026-09-14 and nothing ever cleared one; the sessions were re-authenticated and a sync
 ran hours later while both `urgent` rows still sat `held`, telling the owner to fix something
 already fixed. The emitters already funnelled through one place (`_record_subsystem`), so the
 clear is bound there -- two call sites would have drifted, one cannot.
4. **A channel the owner closed is not a health signal.** `check_delivery` read `MAX(sent_at)`, so
 with owner SMS off (his decision, 2026-07-14, reconfirmed 2026-09-15) the only thing that could
 advance it was a send *escaping* the kill switch -- which happened twice at 00:59 and produced
 "owner delivery flowing (newest 12.8h ago)". Closing that escape path would have flipped the same
 check to a permanent CRITICAL "nothing delivered to the owner for 1d". Both readings are false.
 Measure the channel he chose, name the decision in the summary with the switch file's own path
 and mtime, and keep CRITICAL for the one thing that is real: no channel to him at all.

Corollary worth keeping: an empty result and a healthy result are different answers, and a *stale*
"all clear" is worse than a fresh complaint -- the false green at 00:59 was built on the two sends
that had defeated the owner's own switch.
