**L3625 · never raise a worker count before reading the startup hook - the authority would have started N copies of the autonomous company**

## 2026-10-12 13:35 UTC · ZABZ-YOGA · the authority cannot be scaled by adding uvicorn workers - the startup hook launches the autonomous company loop, and AutopilotController already has the start/stop API to fix it

**Why this was investigated.** The owner asked why the mesh caps near 10 agents when the hardware
could run far more, and whether Postgres would help. The estate's binding answer is NOT the database
engine - it is that the company server is **one web process**, and I nearly executed the standard fix
(`--workers N`) without checking what the startup hook does. The check took one command and would have
been a production incident.

**The measured facts** (`/opt/company`, 2026-10-12 13:30Z):

| what | reading |
|---|---|
| the unit | `ExecStart=/opt/company/.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8002 --proxy-headers --forwarded-allow-ips=127.0.0.1` - **no `--workers`, so exactly one process** |
| the global lock | `app/database.py:27` `_db_lock = threading.RLock()`, acquired at **815 call sites**; a 2.0 s acquisition with an unbounded blocking fallback and a `_db_lock contended ... waiting` log line |
| database | `PRAGMA journal_mode` = **wal** (already correct) |
| what startup does | `app/main.py:1013` `@app.on_event("startup") def startup_identity_seed()` - and at module level `app/main.py:546` **`autopilot = AutopilotController(...)`** with per-N-tick cadences: `company_tick_every=3`, `evolution_every=6`, `optimize_every=12`, `ceo_tick_every=1`, `llm_checkin_every=1`, `world_context_every=1` |
| the module-level singletons | 6 `threading` locks/semaphores in `app/main.py` assume one process |

**The finding.** `--workers N` on that unit would start **N copies of the autonomous company** - N
autopilot loops, N evolution sweeps, N CEO ticks, N world-context refreshes, all against the one
authority database. **A PID file does not prevent it**: `app/main.py:1030` calls `_write_pid_file()`
inside a `try/except` that only logs a warning on failure, so it records the pid, it does not gate the
start. This is the estate's own "two writers on one database" hazard in a form the guard cannot see.

**The fix already exists and is small.** `AutopilotController` exposes `start_thread()` (`app/autopilot.py:2175`)
and `stop()` (`:2240`) - a clean start/stop interface. So the shape is: gate the autopilot launch on an
environment flag (default on, so nothing changes until asked), run the loop as its **own systemd unit**,
then scale the web process independently. Still to establish before proposing it as done: which of the
6 module-level locks in `app/main.py` are genuinely shared state versus per-request, and whether any
in-process cache the autopilot writes is read by request handlers (that would need a shared store).

**The general rule.** *Before raising a web server's worker count on a monolith, read the startup hook.*
A `@app.on_event("startup")` that launches background work turns a scale-up into a duplicate-writer
incident, and it is a one-command check. **Never scale a process whose boot sequence has side effects.**

**Related, and deliberately not conflated:** Postgres does not fix this. The lock is in the application
and the loop is in the same process; changing the storage engine leaves both exactly where they are.
Postgres would answer a different question (genuine multi-writer concurrency), not this one.
