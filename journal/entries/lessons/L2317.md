**L2317 · A reminder/task write through the action registry is lost during a SQLite lock burst — retry directly with a 25s busy_timeout**

### L2317 — The action path gives up on a locked write in seconds; a direct connection with a long busy_timeout gets through

**The rule:** when you must write a reminder, a task, or any other row into the authority's SQLite
store and the action path answers `database is locked`, *do not treat that as the answer and do not
report it as "could not"* — open the file yourself with `sqlite3.connect(db, timeout=25,
isolation_level=None)`, `PRAGMA busy_timeout=25000`, `BEGIN IMMEDIATE`, an **idempotency check inside
the transaction**, then `COMMIT`, and retry in a loop with a 2 s gap for up to ~30 minutes. Make the
check-inside-transaction exact ("does a row with this scheduled_time and this amount already
exist?"), because the retry loop is a race and you will re-enter it after a success whose output you
did not read yet.

**Measured 2026-09-22, authority `~/personal-secretary-mvp/data/secretary.db` (10.2 GB, WAL):**
- `ps_action schedule_reminder` → `success: false — Failed to save DB reminder: database is locked
 (failed after 3 attempts)`; `ps_action create_task` → `Database error creating task`. Both, twice.
- A bare `BEGIN IMMEDIATE` with `timeout=45` failed after **45.1 s** of waiting.
- `journalctl -u secretary-api`: **41** `database is locked` events in the 10 minutes around it.
- The retry loop (25 s busy timeout, 2 s between attempts) succeeded on **attempt 3** — and the same
 file accepted **12/12** instant `BEGIN IMMEDIATE` acquisitions two minutes later.

**Why the retry loop is not optional:** the burst is transient and short-lived, and the action path's
three attempts are spaced in milliseconds, so it fails inside a window in which any patient writer
would have won. The failure is also **silent to the owner**: a reminder that was never written looks
exactly like a reminder that will fire, and a "remind me" he asked for is then simply gone. This is the
same shape as P264 ("each failure is silent and looks like nothing happened") and P2127 (six writers,
no scheduling) — the durable fix is per-writer busy_timeout + retry wrapper, and the reason it is
worth doing is that the *lost* artifact is the owner's own instruction.

**Don't forget:** after inserting directly you have bypassed the action's own side effects, so verify
by reading the row back (and, for a reminder, confirm it is not suppressed by the closed-task guard in
`app/services/personal_ops.py` — that guard only retires a reminder that names `#<task id>`s which are
all terminal *and* asks to close them).

**Evidence:** H2235 (the NJ DOL reminder, inserted this way: `OK attempt=3`), the log lines quoted
above, script `/home/zabz/phone/nj-dol-reminder-write.py`.
