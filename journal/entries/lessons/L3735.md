**How I got it wrong.** I ran `crontab -l` and grepped for `offsite`, got nothing,
and concluded "not scheduled". The job is a **systemd timer**, which is invisible to
`crontab -l` — and the evidence of the successful run was in
`/var/lib/authority-backup/last-run`, a file I had not opened. Two cheap checks
would each have caught it: `systemctl list-timers --all`, and reading the state file
of the thing I was about to call absent.

**Rule: on this estate, "is this scheduled?" is never answered by `crontab -l`.**
Both schedulers are live and the split is arbitrary — the authority's cron runs
`sms-inbox`, `journal-commit`, `family-chat-watchdog` and `prune-backups`, while its
**timers** run the offsite backups, `estate-monitor`, `company-outcome-monitor`,
`authority-deadman`, `transcript-archive-pull` and `fa-index`. Ask both. Same for
"is this service running": `systemctl is-active` and `ps` disagree whenever a unit
is masked, because a masked unit leaves the process running and the *next* start is
what gets blocked.
