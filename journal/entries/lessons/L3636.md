**L3636 · Verify the fleet's target access from the node the broker actually picks, before dispatching the fleet**

Measured 2026-10-13. Five of six mesh children were dispatched against a target the node they landed
on could not reach, and every one of them spent its whole budget discovering that. The broker
reported `exit = 0` and "the run succeeded" for all five: transport success is not task success.

WHAT I DID WRONG. I verified `ssh secratary-cloud` worked from MY machine, and inferred it worked
from the fleet's machines. It did not. The one probe I ran before dispatching landed on
`zabz-tech-linux`, and I read its answer as a statement about the fleet rather than about one node.

RULE, in order:
 1. Send ONE probe child. Read the node it landed on out of the placement line. That node — not
 the node you hoped for — is the fleet's environment until you change it.
 2. From THAT node, prove the exact access every child will need.
 3. Only then dispatch the rest. If placement is not deterministic, either fix the access on every
 candidate node or brief the access check as step 0 with a hard stop.
 4. A child that cannot reach its target is `COULD NOT ASK` — never a negative finding, and never
 a reason to improvise a fourth path.

COST OF SKIPPING IT: five children, roughly fifty minutes of wall clock, zero deliverable. The
fallback that worked was `subagent_local` on the machine that already had access — which is a real
option, but every result from it must be marked LOCAL, because it is not where the work was meant
to run.
