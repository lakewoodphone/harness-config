**L6398 · A rollback that is itself forbidden is not a rollback - and a dead runner left registered turns a fast failure into a slow wait (corrects D5953)**

**CORRECTS D5953, filed the same day.** D5953 said the offline `secratary-lpt` runner registration was
"left in place ... it preserves the rollback: powering `secratary` back on restores the old path".
Both halves were wrong, and the second half refutes the first.

**1. A rollback that is itself forbidden is not a rollback.** `secratary` is FROZEN by
`settings/machines/host-posture.tsv` - "Do not start, stop, mask, unmask, enable, disable or restart
anything on it". Restoring the old deploy path therefore requires reversing a deliberate owner
decision before it can even be attempted. I called a registration "an option preserved" when the
way to use it was closed. That is a decision dressed up as caution.

**2. Keeping it had a real cost, in the opposite direction from what I claimed.** With a runner
registered under labels `self-hosted, linux, x64, lpt-deploy` but OFFLINE, a workflow that
re-introduced those labels does not fail - GitHub QUEUES the job waiting for a matching runner, for up
to 24 hours, looking like a capacity problem. Deregistered, the identical mistake fails immediately
with "no runner matching the labels". **A dead execution target left in place converts a loud failure
into a quiet wait** - the exact failure shape this estate keeps paying for.

RETIRED, WITH THE WAY BACK MEASURED (2026-10-16):
```
git grep -n -E "runs-on:.*(self-hosted|lpt-deploy)" origin/test -- .github/workflows/
 -> exit 1, 0 matches nothing on test can use it
DELETE /repos/lakewoodphone/phone-and-tech-full/actions/runners/21 -> HTTP 204
GET .../actions/runners -> total_count: 0
POST .../actions/runners/registration-token -> HTTP 201
```
The last line is the part that makes this safe rather than merely tidy: **re-registration is one API
call**, so "retire" does not mean "destroy the option". `deploy/runner-provision.sh` stays in the tree
under a SUPERSEDED banner for the same reason.

**THE GENERAL RULE.** Before calling something "kept as a rollback", state the action that would
actually use it and check that action is permitted. If it is forbidden, nothing was preserved - and
an inert-but-registered resource is worse than an absent one, because it changes a fast failure into
a slow wait. And when you retire something, MEASURE the way back in the same breath; "retired" and
"recoverable" are two different claims and only one of them is free.

The objective asked for this retirement and I had skipped it on reasoning that did not survive being
written down. **Check a decision against the objective it serves, not only against its own internal
story.**
