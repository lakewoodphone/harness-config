**L1539 · docker compose env_file is read at container creation, so 'I changed the config and restarted it' proves nothing - check printenv inside the running container**

**The bug this prevents:** `docker restart lpt-backend` looks like it re-reads the configuration and does not. Compose passes `env_file:` at **container creation**; `restart` reuses the existing container's environment. So a change to `/opt/lpt/.env` plus a `restart` produces a service that is up, healthy, and still running the old values — the exact "it looks fine and isn't" shape. Use `docker compose up -d <service>`, which recreates the container.

Verified 2026-09-15 on `lpt-apps`: adding five `GOOGLE_*` variables to `/opt/lpt/.env`, then `docker compose up -d lpt-backend` -> `Recreated` + `Started` + healthy, and `docker exec lpt-backend printenv` showed all five. The compose file (`/opt/lpt/docker-compose.yml:45`) uses `env_file: /opt/lpt/.env` plus an `environment:` block that hard-overrides `NODE_ENV`, `PORT`, `DATABASE_URL` and `REDIS_URL` — so put a new value in the right one of the two, or the `environment:` block wins silently.

**The general rule, which is the reason to remember this:** if a service's behaviour depends on configuration supplied at creation, then *"I changed the config and restarted it"* is not evidence — `printenv` inside the running container is. Same family as L203 (a test that exercises nothing) and P3 (reading the wrong data): an action that appears to apply a change, with nothing checked afterwards.

**A second, smaller thing from the same change, worth one line:** when a service must be both *reachable* and *enabled*, verify the two separately. `/api/auth/google/status` returning `{"enabled":true}` proves the gate opened; `/api/auth/google/start` returning a 302 with a correctly-formed `redirect_uri` and PKCE challenge proves the flow actually starts. The first alone would have passed while the second was misconfigured.
