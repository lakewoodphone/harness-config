**L1473 · A terminal condition must not be one blessed action name: ask_owner and update_task(blocked) are the same intent**

A terminal condition must not be one blessed action name

Session #25105 asked for ~$70 of DHL import duty to be paid, and spend is hard-gated
to the owner. Two consecutive sessions expressed the same correct hand-off, two
different ways:

 75408: called ask_owner -> still failed at 5/5 for lacking [WORK_DONE]
 75409: avoided ask_owner (the model does not want to spam the owner; there is also
 an SMS ban) and marked its task blocked via update_task -> also failed

I fixed the first by keying the terminal condition on ask_owner. That was one
expression of the intent treated as the whole of it, so the second session was still
graded a failure for behaving correctly. _handoff_action now accepts either route.

Two habits to carry forward:
 1. When a terminal or success condition is detected from an action, enumerate how
 else that same intent can be expressed before trusting the condition. A single
 blessed verb is a magic string with extra steps.
 2. The action dict's params arrive flat or nested depending on the path and that
 shape is not documented anywhere. Reading only one shape fails silently --
 the same defect class as the accounting path and the docstring regex, one
 layer lower. Read both, and test both.
