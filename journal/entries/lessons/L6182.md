**L6182 · Concurrent sessions in one clone: path-scoped-add-then-commit is two calls, and the gap loses the commit message**

Two concurrent DSH sessions in one git clone can lose a commit *message* even when the commit itself is
safe. Observed 2026-10-13 in `C:\Users\ezabz\Code\lpt-hub`, on the branch
`shift/lpt-sync-20261013-linker-parity` (which has a live upstream, so this is not a detached or
abandoned checkout).

## What happened, step by step

1. This session created `docs/customer-operations/macbook-screen-diagnose-before-quoting.md` and ran
 `git add <that one path>` — a *path-scoped* add, deliberately, not `git add -A`.
2. Before the matching `git commit` ran, `git commit` reported
 `fatal: Unable to create '.git/index.lock': File exists. Another git process seems to be running in
 this repository.`
3. Another session was mid-commit. It later committed with `git commit -a` (or equivalent), which includes
 **everything already in the index**, and thereby swept the single file this session had staged into
 *its* commit.
4. `git log --diff-filter=A -- <my file>` now names that other session's commit
 (`590321a3c "Kramer WhatsApp regression: …"`) as the one that introduced my file. Its content on disk
 matches my intent exactly and it is pushed — **the file is right, the message is wrong.**

## Why this is worth a rule rather than a shrug

The file-level work survived, so the instinct is to call it harmless. It is not free:

- **`git log` on that file is now a lie about why it exists.** A future session looking for the reasoning
 behind that document finds a commit about WhatsApp, and its own `git log --grep` for the document's
 subject returns nothing.
- **The reasoning had to be written somewhere else to survive** — it went into the harness journal
 (lesson L3765) precisely because the commit message could not be trusted to carry it.
- **The tempting fix is the dangerous one.** Amending or rebasing a pushed commit that another session
 authored and owns is a far worse error than a mislabelled file. Do not "repair" it.

## The rules that follow

1. **Add and commit in one shell string.** `git add <path> && git commit -m …` — never a `git add` in one
 tool call and the `git commit` in another. The window between them is the whole defect.
2. **Never `git add -A` or `git commit -a` on a clone any other session might be using.** Sweeping the
 index picks up stagers you cannot see and reattributes their work.
3. **A stale `.git/index.lock` is not yours to delete by default.** Another process holds it. Wait it out
 (this one cleared immediately) and only remove it after confirming no git process is alive — deleting a
 live process's lock corrupts the index it is writing.
4. **When a commit lands under a wrong message, do not rewrite history.** Push the truth somewhere
 durable — a new commit, the case file, the journal — and say plainly in the record that the attribution
 is wrong and why it is being left that way.

## Provenance

Measured on the estate, 2026-10-13: `git status --porcelain` for the file was *empty* while
`git log -1 -- <file>` returned another session's commit, and `git cat-file -e HEAD:<file>` exited 0 with
`git rev-parse HEAD @{u}` returning one identical sha. That combination — clean tree, file in `HEAD`,
pushed, but attributed to a foreign commit — is the fingerprint of this collision.
