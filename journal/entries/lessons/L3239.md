# CORRECTION — there is no uncategorised-charge gap, and the count was never wrong

Two entries from earlier in this session are wrong and are corrected here. Both were mine, and
both were caused by counting rows without first asking whether the rows were **real**.

## What I claimed

 * `P2832` — "one answered vendor is fragmented across four-plus merchant strings, so it keeps
 being asked about as if new (**5 of 25 charges still uncategorised**)".
 * `H3139` — "the vendor count is wrong (14 where a direct count says 25) … do not trust it".

## What is actually true, measured 2026-10-02

 300 Data Recovery, all spellings, ALL rows (what `LIKE '%data rec%'` sees) : 25
 of those, DUPLICATES already superseded by a canonical row : 11
 REAL charges : 14
 of the 14, categorised : 14
 UNCategorised : 0
 duplicates whose ORIGINAL is categorised : 11 of 11

**Every real data-recovery charge is filed. The vendor is fully accounted for.**

The five rows I called "uncategorised" are all `duplicate_of_transaction_id IS NOT NULL`:

 sq 300 data recovery 2025-06-11 300.00 dup of an origin filed as 300.00
 sq 300 data recovery 2025-06-13 25.00 dup of an origin filed as 25.00
 sq 300 data recovery gosq com ca 2026-06-25 100.00 dup of "data recovery" 100.00
 sq 300 data recovery gosq com ca 2026-06-25 300.00 dup of "data recovery" 300.00
 300 data recovery los angeles ca 2026-07-09 520.00 dup of "data recovery" 520.00

A duplicate row legitimately carries no category — the canonical row is the accounting record.
So they were never work to do.

## And the tool was right

`vendor-aliases` reports **14**, which is the non-duplicate count. It is correct, and it is
correct *because* it filters `duplicate_of_transaction_id IS NULL` while my reference count
(`LIKE '%data rec%'`) did not. **I called my own tool wrong on the strength of a count that
was the sloppier of the two.** The containment/`LIKE`-style matching I then added "to fix it"
was unnecessary; the exact-equality version had been matching correctly all along.

## The rule this is the fourth instance of today

Count the **entities**, not the rows. `P2828` was a `MAX()` over two date formats; this is a
`COUNT(*)` over a table that holds superseded duplicates; both produced a precise number that
was measuring something other than what I thought. Before quoting a figure, ask **what set of
rows it counts** — and when a count disagrees with a trusted-looking reference, check the
reference's own filter before assuming the tool is wrong.

Corrections applied to: the tool's own output (its "APPROXIMATE AND UNVERIFIED" banner is now
wrong and has been removed), this journal as `P2832` and `H3139` are superseded, and the
round-20 write-up.
