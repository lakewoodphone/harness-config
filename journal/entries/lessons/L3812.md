**L3812 · Three quoted numbers were wrong: a tag near the population base rate measures the reader, and a number is right only for the scope it was counted in**

Three numbers this program has been quoting are wrong, each in a different way, and the difference between the ways is the lesson.

**1. `tool-failure` 67.3 % is not an upper bound — it is reader salience.** Round 2 recorded it as a loose upper bound on the hypothesis that the corpus's failure patterns over-match. An independent verifier (`06-friction-evidence.md` §16) tested the sharper question — *how many owner sessions contain a tool failure at all?* — and measured **989 of 1,093 (90.5 %)**. So the tag is not identifying a subset; the class is near-universal, and **a per-session boolean cannot rank a class that 90 % of sessions exhibit.** The correct reading of round-1's 10.2 % is the reverse of what was assumed: 10.2 % was a *reading* of salience too, not a lower bound on occurrence. **When a tag's base rate approaches the population, the tag is measuring the reader.** Corrected in `07-pain-register-v2.md`.

**2. `pwsh` 40.9 % — right number, wrong scope.** The figure is the **owner-session** subset: 70,256 of 171,963 calls. **Corpus-wide it is 37.93 %** (167,113 of 440,543). Both numbers are correct for their own scope and my sentence was not — the same defect as a query whose predicate nobody read, which is the failure this whole session keeps finding. `171,962` is a *scoped* count, and quoting it as the denominator of every tool call was wrong.

**3. The `~700 ms` shell cost is now a measurement DISPUTE, not a correction, and I am recording it as unresolved.** Round 1 measured "a trivial `pwsh` call costs ~700 ms" and decomposed it (start-up 78 %, the Job-owner runner 19 %, everything else under 3 %) — an **end-to-end tool call**. The verifier re-measured `pwsh` start-up alone and got **154.0 ms bare / 195.8 ms with capture (n=12)**, and called the 700 ms figure refuted. **Those are not the same quantity**: one is a whole tool call including the harness's runner process and output capture, the other is process start-up. Neither measurement disproves the other. **What would settle it is one clean measurement of the whole tool call end to end, on the node it is claimed for, with the method stated** — and until that exists, the estate should keep the *rule* ("batch shell work; prefer in-process file tools") and stop quoting a number. This is the third time in one day that a figure was disputed because two different quantities shared a name.

**Also corrected in the same pass, in `06-friction-evidence.md` §16.3** (both were in an earlier report of that same file and did not reproduce): "5,182 of 6,927 (74.8 %)" → **4,922/4,924 = 71.1 %**; "deduplicated 4,512" → **4,541**. Everything else in that report reproduced exactly, including 84,050 failure rows, 30,202 `exit_nonzero` of which **7,438 read `exit code: 0`**, 70,256/171,963, and 4,544 owner turns.

**The method note worth keeping.** The verifier's first pass reported **26 of 98 quotes as unverifiable** — and the fault was its own matcher, not the report: a newline renders in that corpus as ` / `, not `/`. It derived the rendering rule by dumping raw turns instead of assuming it, then re-ran and got **98/98**. **When a check fails, the first suspect is the check.** Round 1's own lesson was the same and cost it two retractions.
