**L3812 · git add <directory> swept another session's uncommitted case edits into my commit - stage named files, then read the commit's own stat**

## 2026-10-14, ZABZ-TECH. `git add <directory>` swept another session's live work into my commit.

While answering customer texts I staged one new case file with:

 git add docs/customer-operations/cases/ docs/customer-operations/sync-records/

**Five files went in, not one.** The other four were edits made minutes earlier by a different
session in the same working tree: two `SUPERSEDED` corrections on `abramczyk-sd-card-...` and
`kyocera-flip-phone-verizon-branded-spitzer-...`, a 53-line update to the Weinreb Pavilion case and
its sync record. Nothing was lost, and nothing was overwritten - they were uncommitted and are now
committed - but they are attributed to my message (*"Smart Bass 8.0 MP3 inquiry: case opened and
answered"*), which is a false history for anyone reading `git log` on those files.

**THE RULE.** `lpt-hub/docs/customer-operations/` is the busiest directory in this estate and more
than one session writes to it concurrently. **`git add` a named file, never a directory, and run
`git show --stat HEAD` immediately after committing.** A pathspec that is a folder is an invitation
to take somebody else's work; the earlier commits this session used exact paths and swept nothing.

This is P13's shape (concurrent sessions share one repo and `git add -A` sweeps each other's work)
arriving through a directory pathspec rather than `-A`. The detection is the same and it is one
command: read the commit's own stat before moving on.

**Cost when it is worse than attribution:** a session mid-edit commits half-written prose, or a
`--amend`/rebase later rewrites someone else's work. Neither happened here.
