**L4065 · A base64 payload that arrives wrapped in whitespace is a different payload, and three silent failures said so**

**2026-10-14, ZABZ-YOGA, round 4.** I installed a cron line three times. Each attempt failed with
crontab's own message, *"command too long"*, and none of them told me why. The cause was in my
transport, not in crontab.

**What happened.** I built a base64 payload with PowerShell and passed it into a nested `ssh`:

```powershell
$cmd = 'cd /root/code/harness-config && /usr/bin/python3 journal/tools/journal-ceiling-refresh.py --claim-gap --raise-cache >> /var/log/journal-ceiling-refresh.log 2>&1'
$b64 = [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes($cmd))
$r = @'
<installer python that does: line = "*/15 * * * * cron-wrap.sh journal-ceiling-refresh " + sys.argv[1]>
'@
ssh secratary-cloud "python3 -c `"import base64,sys;exec(base64.b64decode(sys.argv[1]).decode())`" $b64r $b64"
```

The installer reported `payload length: 2700` for a payload that is 216 characters. **PowerShell had
wrapped the base64 token across lines**, and the here-string turned one token into a multi-line
argument, so the concatenated line was built across the wrap.

**How it presented, which is the part worth keeping.** Not as a transport error. As:
* attempt 1 — line length 1409, "command too long" (my replacement loop appended the line twice);
* attempt 2 — line length 1369, same message;
* attempt 3 — payload 2700 characters, and an assertion I had just written *refused to install*,
  which is the only reason the fourth attempt was diagnosed instead of being blamed on crontab.

**The rule.** A payload travelling between shells carries a shape, and the shape is checkable:
**base64 contains no whitespace, so any whitespace in a base64 argument means it was wrapped.** So
the installer now refuses a payload containing whitespace, refuses a line over crontab's 998-character
limit, and refuses to schedule a command that does not exit 0 — probing the command first and
printing `PROBE_RC`. It then installs via `crontab -`, reads the crontab back, and decodes the line it
actually wrote:

```
payload length after strip: 216
replacement line length     : 281
probe of the command        : PROBE_RC=0
job lines after edit        : 1   longest line in crontab: 597
install rc                  : 0
```

**Why this generalises beyond cron.** The estate's dominant failure is not a wrong answer; it is a
*wrong answer that looks like the right one*. Three attempts produced "command too long" — a message
about the destination — while the defect was in the source. The fix that made it visible was not
care, it was an **assertion on the artefact's own invariants** before it was used. Same shape as
`L3801` (a timestamp comparison that silently covered an extra day), `L3803` (a measurement split on
an mtime instead of a process start), and this round's `L3946` (a git ref believed to be the newest
reservation when the working tree was eight hours ahead).

**Corollary for scheduled jobs.** *A job that cannot run is worse than no job, because it looks like
coverage.* The job I was replacing had been installed for hours, ran every 15 minutes, and did
nothing — it ran `journal.git_max()` in a separate interpreter and discarded the result. Nothing
reported it, because nothing checked that its output changed anything. Probe the payload, then
schedule it.
