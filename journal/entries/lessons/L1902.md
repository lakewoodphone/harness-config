**L1902 · A node's credential may live only in its login/worker environment — invoke the wrapper by name, never an interpreter path**

MEASURED 2026-09-17 on zabz-tech-linux (docs/mesh/102-linux-dispatch.md).

The rule: when a node is provisioned with a launcher (a wrapper on PATH, e.g. /usr/local/bin/dsh), a dispatcher MUST invoke THAT by name. Naming an interpreter+bin.js pair bypasses it, and the wrapper is the only thing that sources the worker credential file.

Evidence:
- dsh --profile headless 'Reply with exactly: LINUX NODE OK' over ssh -> exit 0 in 3s. The node works.
- /usr/local/bin/node .../bin.js --profile headless '<task>' -> exit 1, 'dsh: MISSING_CREDENTIAL: llm-deepseek: no API key for provider route deepseek-official'. Even with the interpreter path CORRECTED.
- The same wrapper under 'env -i PATH=... sh -s' with HOME UNSET and DEEPSEEK_API_KEY absent -> EXECUTOR UNDER EMPTY ENV OK, exit 0. It resolves \C:\Users\ezabz with a getent fallback and sources /etc/dsh-worker.env (root:zabz 0640) itself.
- The shipped table also had a version-stamped nodeExe (/home/zabz/.local/node-v24.12.0-linux-x64/bin/node) that did not exist: exit 127.

So: 'the node cannot run children' and 'our invocation cannot launch a child there' are different facts, and a roster flag recorded the second as the first. A hardcoded interpreter path is the failure mode; a wrapper NAME is not (it cannot rot with a version).

Second, transferable: a fixed target's invocation must also reach the CHILD ENGINE, not just the dispatcher's environment. The child boots its own provider from its own profile copy; without the passthrough (MESH_NODE_COMMAND) the child silently falls back to the interpreter form and dies MISSING_CREDENTIAL (measured live, 14:45:40Z). Re-run install-mesh-profile.mjs after adding a node.
