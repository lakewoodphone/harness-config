## Removing a large FTS5 index costs its size in WAL, once — and per-document operations cost hours

**Measured on `secratary-cloud`, 2026-10-19 02:03–02:28Z, while converting
`dsh_session_events_fts` (16.4 GiB, the index over 2.7M session-event rows) to external content.**

There are only three ways to remove that index, and each has a hard, measured cost:

| method | measured | verdict |
|---|---|---|
| `DROP TABLE` in one transaction | WAL reached **5.65 GB and free space fell 14.9 → 3.87 GB at roughly 50% complete**; aborted | needs ~11.6 GB of WAL in one transaction, i.e. **~20 GB free** once routine churn (5 GB during four minutes) is allowed for |
| `DELETE FROM <fts> WHERE rowid …` in batches | **67 documents/second** → 2.69M documents = **11 hours** | not viable |
| `DELETE FROM <fts>_data/_content/…` directly | `table dsh_session_events_fts_data may not be modified` | impossible: FTS5 protects its shadow tables |

**The rule:** SQLite journals every freed page, so *freeing* N bytes of index costs N bytes of WAL
in a single transaction, no matter which statement does it. Splitting it makes the total work the
same but bounds the WAL — except the virtual table will not split cheaply (67 rows/s), and the
shadow tables refuse writes. So on a filesystem with less than roughly twice the index size free,
**a large index cannot be removed at all.** Plan the free space before planning the migration.

Four things that made this harder than it needed to be, all worth knowing:

1. **`PRAGMA integrity_check` pins the WAL.** A stray 8-minute integrity check from an earlier
 agent was still running; its read snapshot stopped the checkpointer advancing, so the WAL grew
 faster than the write itself required. Kill stray readers *before* a write-heavy operation, and
 check `lsof` for them.
2. **A `TEMP` table does not survive between `sqlite3` invocations.** Each call is a new
 connection, so a repair that builds a temp table in one statement and uses it in the next fails
 with an empty table. Put the whole sequence in one process (or one heredoc).
3. **`/tmp` on this host is a 2 GiB tmpfs with ~640 MB free.** Scratch databases and test files
 must go to `/var/tmp` or `/root`; a 300 MB synthetic DB "succeeded" until the tmpfs filled.
4. **Bulk build is fast; per-row work is not.** `INSERT INTO fts SELECT … WHERE rowid BETWEEN`
 ran at ~20,000-40,000 rows/s. Any statement that touches one document at a time ran at ~65/s —
 a 300x difference. Design for bulk.

**Recovering from a partial removal** (this was actually needed): the index lost 10,345 documents
when the batched delete was abandoned mid-run. Because FTS5 forbids writing its shadow tables, the
repair had to go through the virtual table, and identifying the missing rows needed an anti-join on
`(source_machine, session_id, ordinal)` — which cannot be indexed on `_content`. The fix: copy the
identity columns into a `TEMP` table, index *that*, and anti-join against it in one connection.
Result: `base = content = docsize = 2,711,725` exactly. **The index is derived; a failed migration
costs a rebuild and some careful repair, never a row of data.**
