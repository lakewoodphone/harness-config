## L — An unmerged branch's tests are run by nothing, so they rot until merging it would break main

2026-10-21, ZABZ-TECH, kosher-filter-ai. Found while preparing a merge that looked trivial.

`origin/main` was an **ancestor** of the branch (`git merge-base --is-ancestor` rc=0): a pure fast-forward,
zero conflicts, nothing to resolve. The docs gate on the merged tree was green at 18/18. Everything said
merge. **Then I ran the one test file the branch adds, and two of its five tests failed.**

`server/tests/test_modesty_meter.py` asserted two things the owner had since overruled:

- that an unknown attribute **fails** the frame. The code quotes his reversal — *"if it's cut off at a
 certain point then nothing past it is a problem"* — and explains that escalating unknown would block every
 head-and-shoulders portrait online. The test encoded the superseded behaviour.
- that `Observations` accepts `hair_covered` (a field removed when uncovered hair stopped being a rung) and
 that `neckline="collarbone"` is valid (it is not; the vocabulary is `deep | ordinary | covered`).

So the branch carried **23 commits whose own test file was red**, and had done since it was written. Nothing
ran it: CI runs on the branch only if a PR opens, the wake shifts work other items, and the journal said the
work was "committed and pushed" — which was true and did not mean runnable.

**The transferable point: integration debt and test rot are the same defect seen from two sides.** A branch
nobody merges is a branch nobody tests, and it rots silently in the direction of "merging this breaks main".
The cost is not the merge; it is discovering at merge time that the merge was never safe. The fast-forward
looked free and was carrying two failures.

**What to do about it, concretely:** before calling any branch mergeable, run **the tests that branch adds**
— not the whole suite, just the files it introduces. It is one command and it takes seconds, and it is the
only gate that catches rot rather than conflict. `git diff --name-only origin/main...<branch> -- 'tests/*'`
then run those files.

Second, smaller rule: when a test fails, check whether it is testing the **code** or a **ruling the code has
since reversed**. Two of these three failures were the test being stale, not the product being wrong — and
"fix the code to satisfy the test" would have re-introduced a bug the owner had explicitly rejected. The
code carried his words and the date; that is what decided it.
