## L — The mesh's availability was one process on one machine, and the fix is redundancy not repair

MEASURED 2026-10-09 from ZABZ-YOGA, reproduced twice:
 remote-ssh: broker-unreachable: the placement broker could not be reached at
 secratary-ts:http://localhost:3091/place — ssh exited 255: ssh: connect to host
 secratary.tail93e6e6.ts.net port 22: Connection timed out
while zabz-yoga-1 and zabz-tech both answered GET /mesh/health in 0.13 s / 0.20 s
with 8 free slots and nothing in flight. The `subagent` tool (the mesh provider)
could not start a single child, so every larger job silently became serial.

ROOT CAUSE, and it is architectural not accidental: lib/broker-client.js hard-wires
BOTH the machine (sshTarget default 'secratary-ts') and the URL
('http://localhost:3091', loopback-only, so only that machine can answer), and
lib/placement.js is written so a broker that cannot be reached is "a reported
broker-unreachable error, not a default". One process on one node was therefore the
only thing that could ever say where work goes.

THE FIX THAT WORKS: every node already answers GET /mesh/health over the tailnet,
unauthenticated, publishing its own concurrency decision, binding term, in-flight
count and queue. So a dispatcher can SEE the fleet with no broker. New:
lib/failover-placement.js (pure ranking), lib/node-probes.js (direct reads),
lib/failover-placer.js (wraps the real broker placer; branches ONLY on
broker-unreachable). The broker is still asked first and still used as-is; a live
broker with a BAD answer still throws, because probing around it would hide a bug.

RULE TO KEEP: an unreachable node is recorded `unreachable`, never scored as full,
busy or bad. Absence of evidence is not evidence of absence.
