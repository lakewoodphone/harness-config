**L11840 · Owner-queue ingests: our own mail counted as inbound, and an explain mode that writes**

Two owner-queue ingest defects found and fixed on 2026-10-21, both from the owner asking why
the queue looked different from what he was texted. Recorded because each one will recur.

## 1. The mail ingest treated our own outbound mail as inbound

`/root/bin/owner-queue-ingest-mail.py`, `recipient_verdict()` line 292: `if owner_hit: return None`,
where `owner_hit` is built from `To`/`Cc` only. `From` was never compared to any sending identity, so
a copy of our own letter — Gmail delivers outbound through the send-as aliases back into
lakewoodphoneandtech@gmail.com — was classified "HIS" and went to the judge as if a supplier had
written to us.

Symptom the owner actually felt: queue rows #705 and #726 asked him to supply an RMA number, return
address and paperwork for the MobileSentrix Surface panel. Those were our own two emails (sent 15 Oct
and 18 Oct), ingested as requests. Measured population: 10 self-addressed messages in a 7-day window
(6 from info@, 3 from businessorders@, 1 personal-to-personal), and 4 queue rows all-time — #705,
#706, #726, #875 — every one already resolved.

Fix: `OWN_SENDING_DOMAINS` (env-overridable, default lakewoodphoneandtech.com) and a rule before the
old branch that drops a message whose `From` is an owner address or an address at our own sending
domain, delivered to an owner account, with the reason printed as "SELF-ADDRESSED". Published by
atomic rename, 76,125 -> 77,340 bytes, hash 22146006... -> 8a3b414a... Proven both ways: the exact
#705 and #726 envelopes now return `drop / rule:self-addressed`; Techloq and Adeena still pass to the
judge and still produce rows.

## 2. `--explain` is documented write-free and it writes

The child found that the deployed `--explain` path still calls `record_rule_verdict()` / INSERT and
commits, despite the usage text saying "print every verdict, write nothing". It ran both explain
passes against a temporary copy of the database (`/tmp/oq-dryrun-*.db`) with `--max-judge 0`, and
proved production was untouched by reading `max(judged_at)` before and after (2026-10-21T01:14:06Z,
unchanged).

This matters beyond the one script: a dry-run flag that mutates is how a "read-only" investigation
silently changes the thing it is measuring. Any future explain/dry-run work on this ingest must
assume it writes until proven otherwise on a copy.

## 3. Repo copies of these scripts lag the deployed files, and the paths differ

- `owner-ask.py`: repo 31,490 B (2026-10-16) vs deployed 32,171 B (2026-10-21 00:13) — 681 bytes of
 live change are not in the repo.
- `owner-queue-ingest-mail.py`: repo worktree copies 74,068 B (dd1079a4...) vs deployed 76,125 B
 before my patch (22146006...), with four deployed-only hunks including unjudged-verdict handling
 and a 20-column INSERT placeholder fix.
- `owner-queue-ingest-gv.py`: local repo copy 38,318 B vs deployed 47,556 B.
- On the authority, `/root/code/harness-config/scripts/owner-queue/` does not exist at all; the only
 repo copies are worktrees at `/root/wt-oq-rules/` and `/root/wt-hk692/`.

Consequence: deploying from a repo copy silently reverts live fixes. Anyone about to edit one of
these must hash it against the deployed file first, and patch the same anchors in both rather than
copying one over the other.
