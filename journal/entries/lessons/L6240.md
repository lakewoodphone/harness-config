**L6240 · CORRECTION of L3817's mechanism: git_max reads ONE configured ref, not any ref - a fetched foreign ref changed nothing**

`L3817` named the right fault and described the wrong mechanism. The experiment below sharpens both, and the correction matters because the wrong mechanism implies a fix that does not work.

**What `L3817` said.** That `git_max(kind, fetch)` — *"Highest number visible in any local or remote git ref"* — runs `git fetch --all` and searches refs, so cross-host id visibility is empty because ZABZ-YOGA's fetch source (`origin` = `secretary-ts`, the FROZEN rollback anchor) can never deliver a new commit. I took the docstring's "**any** local or remote git ref" at face value.

**The test that falsified it.** Push this machine's journal to the shared live remote, then fetch it *into a remote-tracking ref* on the authority, and run `next-id`:

 ZABZ-YOGA git push offsite HEAD:refs/heads/journal/zabz-yoga -> exit 0
 authority git fetch <github> journal/zabz-yoga:refs/remotes/offsite/journal/zabz-yoga -> exit 0
 authority next-id pain BEFORE # highest seen: P3198 ... git @ 3d565e81 P3198
 authority next-id pain AFTER # highest seen: P3198 ... git @ 3d565e81 P3198

**That first result was insensitive, not negative, and I said so at the time:** yoga's ceiling (P3188) is *lower* than the authority's (P3198), so the authority seeing it could not change the maximum. I then tested the direction that matters — can the machine with the LOWER ceiling see the HIGHER one:

 ZABZ-YOGA before # highest seen: P3188 # reserved through P3194 for ZABZ-YOGA
 git fetch secratary-cloud:/home/zabz/code/harness-config \
 hk/182-wake-family-key:refs/remotes/cloud/hk-182 -> exit 0
 ZABZ-YOGA after # highest seen: P3188 # reserved through P3194 for ZABZ-YOGA

**The ceiling did not move.** The authority's branch was fetched into this repo as `cloud/hk-182`, reachable by `git rev-parse`, and `git_max` did not see it. **So the mechanism is not "any ref".** It reads a *specific, configured* ref — the sync remote's branch (`origin/<branch>`), which is the `git @ <sha>` the output prints. For ZABZ-YOGA that ref lives on `secretary-ts`, and a ref on the FROZEN rollback anchor can never advance. **The conclusion of `L3817` survives exactly; the mechanism becomes: not "the fetch brings nothing useful", but "the one ref that is read is defined to be immutable".**

**Why the distinction changes the fix.** "Any ref would do" implies: publish the journals to GitHub and fetch — which is what I did, and it did nothing. "One configured ref is read" implies the fix must make **the sync remote's own branch** advance, or change which ref is read. The estate's `AGENTS.md` §6.1 records `origin` as a *diverged two-URL remote* that fetches from the frozen office box and pushes to GitHub — so the ref that decides every id on this machine is fetched from a host that is, by design, never written to again.

**A second, cheaper thing the same test bought.** The push to GitHub **succeeded** (`* [new branch] HEAD -> journal/zabz-yoga`, exit 0) and the authority **reached GitHub** (`git ls-remote` exit 0). So a shared live remote exists and both hosts can use it — the missing piece is not connectivity, it is that the allocator reads the wrong ref. The `ls-remote` also showed `diverged-ZABZ-YOGA-20261008` … `-20261012`, so pushing diverged journals to GitHub is already the practice on this estate.

**The rule this is another instance of, and it is now the fourth today:** *a docstring is a claim about behaviour, not behaviour.* I read "any local or remote git ref" and built a diagnosis and a fix on it. The test that settled it was three commands and one direction change — and the first version of the test was worthless because I compared a lower ceiling against a higher one and could not have seen a change if one had occurred. **A test whose subject cannot move is not a negative result.**
