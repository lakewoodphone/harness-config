**L2128 · L2133 - a dynamically created tool was declared a REQUIRED TOOL, so the harness forced the agent to call a function whose required argument could never be supplied**

Measured 2026-09-20 on the authority. `alibaba_onetalk_automation` was **blocked 48-51 times in 7 days**
and **executed successfully 0 times in 14 days**. Three separate things were each true, and the defect
is the combination:

1. **The written function needs an argument the model is not allowed to pass.**
 `data/tools/alibaba_onetalk_automation.py` (a tool the company created for itself) begins:

 def run(action: str, onetalk_url: Optional[str] = None, api_key: Optional[str] = None, ...):
 if not onetalk_url:
 return {"ok": False, "result": None, "error": "onetalk_url is required"}
 if not api_key:
 return {"ok": False, "result": None, "error": "api_key is required"}

 But the schema the model is given (`department_tools.py:450`) exposes only `action`, `dry_run`,
 `sync_limit`, `follow_up_days`, with `"required": ["action"]` and
 **`"additionalProperties": False`** - so the model is *structurally forbidden* from passing
 `onetalk_url` or `api_key`.

2. **Nothing else supplies them either.** `grep -rn onetalk_url` across the whole tree finds it in
 exactly one file: the tool's own source. No `config.py` field, no `.env` key. The function's own
 defaults are `None`, so the first `if not onetalk_url` is always taken.

3. **The harness then ORDERS the agent to call it.** `app/services/work_orders.py` puts
 `"REQUIRED TOOL: alibaba_onetalk_automation"` into the *step descriptions* of the
 `seed_alibaba_procurement_cycle` standing work order (steps 1 and 2, every 12 hours), and
 `agent_worker` extracts that text via `_extract_required_tools` and enforces it as a gate. The
 agent is not merely offered a broken tool; it is instructed, twice per cycle, to call one whose
 success is impossible.

**The generalisable rule.** A tool that the system writes for itself has TWO interfaces that must
agree: the Python signature and the JSON schema advertised to the model. Nothing checks that they do.
The schema is what the model sees, the signature is what runs, and the harness's REQUIRED-TOOL gate
trusts the schema's promise while the code enforces the signature's requirement. Where they disagree,
every call is refused - for ever, silently, at 5.6 % of all blocked tool calls.

**Two things worth doing, neither of them "add a timeout" or "retry".** (a) Validate signature against
schema when a dynamic tool is registered, and refuse to advertise one that disagrees. (b) Treat a
"REQUIRED TOOL" declaration as a claim to be verified at load time - a step that requires a tool
which cannot succeed should fail loudly when the work order is registered, not every 12 hours at 4am.

**What I did NOT do: guess a URL.** `onetalk_url` and `api_key` are values only the owner can supply
(an Onetalk/Alibaba endpoint and credential). Inventing one would have produced a tool that makes
authenticated calls to a guessed host. The correct disposition is recorded in P2133 for the owner.
