**L1774 · OWNER_PHONE_NUMBER is Google Voice; the line he reads is OWNER_NOTIFY_NUMBER**

2026-09-16: I sent the owner his anniversary errand list to `OWNER_PHONE_NUMBER` (+17325691594). Twilio reported `delivered`. He replied: "i think you sent it to my google voic number instead of my personal one." He was right. The message went to a line he does not read - which makes "delivered" a success that fails.

WHAT THE NUMBERS ACTUALLY ARE:
- `+17325691594` = **Google Voice #1**. `OWNER_PHONE_NUMBER`. Google Voice, and the Dialpad main-line failover.
- `+18483897895` = **his real line**. `OWNER_NOTIFY_NUMBER`. Apple Watch cellular / primary; family-chat admin; the line every recent inbound call comes FROM.

EVIDENCE (all in-repo, one doc written the SAME DAY):
- `docs/operations/security-program/2026-09-16-security-alert-roster-change.md` table: `+17325691594` -> "Owner (Zabz) - Google Voice #1", `+18483897895` -> "Owner's second phone".
- `audit-logs/2026-06-07_205557.md`: "Owner's active line is the Apple Watch cellular number `+18483897895` (every recent inbound call is FROM it), but the system used the Google Voice number `+17325691594` for BOTH owner recognition and outbound notifications." The same audit added `OWNER_NOTIFY_NUMBER` to fix exactly this.
- `app/services/gv_email_handler.py:85` maps `+17325691594` (a *voice* handler).
- `scripts/server/owner-attention-digest.sh:68`: "GV numbers: account1 eliyahuzabrowsky = 17325691594".
- `app/services/voice_realtime.py:622`: "Zabz's phone number is: +18483897895".
- `tests/test_family_chat.py`: `db.add_member("+18483897895", "Eliyahu", device="iphone", admin=True)`.

RESENT to `+18483897895`: delivered, SID SMb0c00d3b1a8a274ffd9861078bb57343, 5 segments, dateSent 2026-09-16T20:02:32Z.

RULE: when the owner says "text me", "notify me", "call me", the target is **the line he reads**, not the variable that happens to be named `OWNER_PHONE_NUMBER`. Resolve it via `owner_notify_target()` / `OWNER_NOTIFY_NUMBER` and honour `OWNER_ALT_PHONE_NUMBERS`. If there is any doubt about which line, ASK - it costs him one word, and a wrong-line notification is silently useless.

WHY THIS KEEPS HAPPENING, and the real lesson: the name `OWNER_PHONE_NUMBER` asserts "this is the owner's phone". The value is a Google Voice line he does not monitor. Nothing errored, nothing logged a warning, the send returned success - the field name simply lied. This is the same shape as the decorative `recurrence` column (L1762/L1768): a name promising semantics the value does not have. Distrust self-describing field names; verify what the value is by reading where it is used and observed. A delivered message to an unread number is the exact failure the provenance rule exists to prevent - the reading was correct and the meaning was wrong.
