**L3649 · When two different subjects yield the SAME extracted number, the number is not from the subject**

2026-10-13. I spent this round trying to recover order totals for 125 marketplace orders whose
matched emails are shipping notices, and I abandoned it. The detection that stopped me is the part
worth keeping.

THE TASK, and why it looked easy. 125 orders have no total because the parser matched
"OUT FOR DELIVERY: <item>" style mail, which never carries an amount. The item name IS in those
subjects, so searching the mailbox for a confirmation by title should find the email that does.
It does: `from:ebay.com "The Apartment"` returns 5 messages and the last one is
"Your order is confirmed", 113,940 characters, with 11 dollar-shaped figures in it.

THE THREE ATTEMPTS, each measured against the same two orders.
 1. Labelled regex ("total:" immediately before the figure) -> matched NOTHING. 0 recovered.
 2. First line-scoped "total" line, else page maximum -> BOTH orders returned 92.45.
 3. Read the lines AFTER the "Order total:" anchor, 20 deep -> BOTH orders returned 82.42.

THE TELL, and it is the point. Two different orders - "This Is Not a" and "The Apartment (USED,
Blu-ray)" - produced the SAME number, twice, at two different values. Two unrelated used DVDs do
not cost the same to the penny. What was being scraped was a figure from a template block that both
emails share (a promotion, a related-items strip, a footer), and the value CHANGED between attempts
only because widening the line window moved which block got hit. A single order returning a
plausible number would have passed every check I had; it was the second order agreeing that exposed
it.

WHAT IS ACTUALLY GOING ON, for whoever picks this up. The extracted body is raw HTML. In it:
 L1733: ...class="title mb8">Order total:</h3>
 L1753: Total charged to
The label and its figure are separated by a table-cell block, so line proximity cannot associate
them, and the page contains many other money-shaped numbers. This needs the body parsed as HTML
(cell structure, or the message's text/plain alternative) rather than as lines. That is a real
parsing job, not a regex patch.

WHAT I DID INSTEAD OF SHIPPING IT. Two rows written by attempt 3 were reverted
(`total_kind='recovered_from_confirmation'` set back to NULL), the store is back at 671 orders /
125 without a total, and the script is parked at `/root/recover_order_totals.py.ABANDONED-20261013`
so no clock can pick it up. The 19 totals derived from line items in `W2746` are untouched and
still correct - those came from the item rows themselves, not from page scraping.

RULES.
1. **A scraped number needs a cross-subject control.** Pick two records that should differ, and
 check the extraction differs too. If it agrees, you are reading the page, not the record.
 Cheaper than eyeballing and it catches exactly this class.
2. **Widening a pattern re-aims it.** Each attempt here "worked" - it returned a number - and each
 one was reading a different part of the page. Progress that consists of a different plausible
 value is not progress; it is motion.
3. **Revert before you investigate further.** The wrong values lived in the ledger for minutes, not
 hours, because the revert is one UPDATE and the diagnosis is many minutes. Write-then-diagnose
 is only safe when undo is that cheap - and here it was, which is why trying was affordable.
