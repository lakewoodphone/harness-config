**L3634 · A flag can be missing from the repo you grepped and present in the service that owns it**

**L3634 · 2026-10-12 · A flag can be missing from the repo you grepped and present in the service that owns it — `WAZE_USAGE_NOTIFICATIONS` exists, in the fleet API, not the web backend.**

**What was claimed.** A billing rehearsal child reported, as a FALSIFIED verdict, that
`WAZE_USAGE_NOTIFICATIONS` "does not exist in the code at all — it is described as a disabled switch in
three documents and is unimplemented", based on `grep -rn WAZE_USAGE_NOTIFICATIONS backend/src
frontend/src` in `phone-and-tech-full` returning zero hits. On that basis it recommended reclassifying the
feature as unbuilt.

**What is true.** The flag is real and load-bearing, in the **fleet API** on `waze-mdm-01`:

```
/opt/waze-mdm/fleet-api/fleet_api.py:91
USAGE_NOTIFICATIONS_ENABLED = os.environ.get("WAZE_USAGE_NOTIFICATIONS", "0") == "1"

:1861 if USAGE_NOTIFICATIONS_ENABLED:
:1863 for pct in (int(CAP_WARN_FRACTION * 100), 100):
:1865 await client.create_usage_notification(row[2], pct)
```

It gates registering Telnyx per-SIM usage-alert thresholds at the warning band and at the cap when a
customer changes their cap. Default off, for the reason its own comment gives and which survives the
correction: the account has never held a usage notification, so the multi-notification semantics are
unverified and a cap change is a customer-visible action on a live device.

**The distinction the wrong verdict erased, and it is the one that matters to the product.** There are
TWO warning paths and only one of them is off:
- **`cap_band` / `cap_message` / `warn_at_percent`**, computed by the fleet API from the usage ledger and
 rendered by the customer's device page — **working today**. A live read of
 `/api/waze/device/FFYGNQ8AN72J` returned `"cap_band": "ok"`, `"warn_at_percent": 80`.
- **`create_usage_notification`**, the push into Telnyx so the customer is told without opening a page —
 **off**, behind the flag.

So "the customer only learns they are about to lose data by opening the page" is TRUE, and "there is no
such switch" is FALSE. A future session acting on the wrong verdict would have stopped looking for the
one call that needs verifying before the push warning can be enabled.

**The rule.** A negative grep is evidence about the tree you searched and nothing else. Before converting
it into "this does not exist", name the process that would have to contain it: this flag is read by a
Python service on another host, in a different repository, deployed as a container — three separate
reasons a grep of the TypeScript web backend could not have found it. The cheap check that settles it is
`grep` on the running container, not on a checkout.
