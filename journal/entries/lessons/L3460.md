**L3460 · sqlite3 .backup cannot write to a FIFO - stream a consistent copy through the sqlite_dbpage virtual table**

`sqlite3 .backup <fifo>` CANNOT work, and a design built on it will never ship. MEASURED on secratary-cloud 2026-10-11, sqlite3 3.46.1 (Debian):

 $ mkfifo -m 600 /tmp/t.fifo; sqlite3 /tmp/t.db ".backup /tmp/t.fifo"
 Error: cannot open "/tmp/t.fifo" (backup_rc=1, output 0 bytes)

The unix VFS refuses to open a non-regular file as a database, and the pager writes with pwrite(), which a pipe cannot serve. The claim that ".backup writes front-to-back and never seeks, so a FIFO is legal" is false, and it had been written into a script header as "VERIFIED empirically" without ever being run.

WHAT WORKS INSTEAD, also measured on that host: SQLite's `sqlite_dbpage` virtual table (ENABLE_DBPAGE_VTAB is compiled in on Debian's build) read inside ONE read transaction gives the same consistent snapshot `.backup` uses, and it streams:
* `SELECT data FROM sqlite_dbpage ORDER BY pgno` -> `EXPLAIN QUERY PLAN` = SCAN sqlite_dbpage VIRTUAL TABLE INDEX 0, no temp B-tree, nothing materialised
* a 200,302,592 B database streamed page-by-page is BYTE-IDENTICAL to the file (`cmp`)
* a WAL database with uncheckpointed content restores to PRAGMA integrity_check=ok with every row
* throughput on the live 23.6 GB authority DB: 819,200,000 B in 2.294 s (~357 MB/s)

That makes a zero-extra-disk offsite backup possible on a box that cannot hold a second copy of its own database.
