**L2355 · Case-file front matter is an enum: a bare status: parts was unreadable to the index and silently became other**

Front matter in an lpt-hub case file is a machine-readable enum, and a value the Case File
Standard itself mandates can be unreadable to the tool that reads it.

MEASURED 2026-09-22. `tools/case-index/lptcase.py:canonical_status()` matched only PHRASES:
`("parts", ("parts ordered", "awaiting parts", "parts arrived", "waiting for parts"))`. So a
file declaring the bare `status: parts` - the exact value Case File Standard section 3 lists -
fell through the table to `other`. Seven case files were mis-reported. Worse, the phrase list
was partly dead anyway: "awaiting parts" contains "awaiting", and the `waiting` tuple is
checked first, so those phrases could never reach `parts` either.

FIX APPLIED: an exact match against the section 3 enum now wins before the phrase table.
`STANDARD_STATUS_VALUES = new, quoted, parts, in_progress, waiting, ready, closed, unfixable,
other`. Effect on 193 cases: `other` 63 -> 56, `parts` 0 -> 7, every other bucket unchanged.
The file already carried a comment about the identical failure mode for in_progress (the
"2026-09-17 bug"), which is why the shape was recognisable.

RULES FOR A FUTURE SESSION:
- Write only a value from section 3. Nothing else. `status: ordered-awaiting-delivery`, which
 I wrote first and had to change, is not a status; it was me inventing vocabulary for a field
 that already had one.
- WHEN ADDING A STATUS VALUE, add it to the enum in CASE-FILE-STANDARD.md section 3 AND to
 STANDARD_STATUS_VALUES. Both, or the index and the standard disagree and the index wins
 silently.
- `payment_state` is a separate enum (uncollected | paid | partial | refunded | waived |
 quoted | unknown) and is the right place for "not paid yet", NOT `status`.
- VERIFY, do not assume: after editing front matter, run
 `lptcase.py find "<phone>"` and read the `status` column. It shows status_canonical, which is
 what every other tool sees - not the raw value you typed.

RELATED, SAME CASE: lpt-hub had TWO sync records for one case
(`2026-09-14-weitman-laptop-sourcing.json` LF + trailing newline, and
`14in-laptop-weitman-8483336341-2026-09-14.json` CRLF + no trailing newline). They were the
same 548-line document with one having a later `updatedAt` and a production linkage the other
lacked; the case file's front matter pointed at the older one. Lesson: when updating a case,
check for a second record by caseId before assuming one file is the mirror, and preserve each
file's own line-ending convention when writing (a json round-trip gate caught the CRLF
difference and refused to write - keep that gate).

**L2355 · L: on this record, a new symptom the owner reports in passing outranks another test result - same-evening append, and the escalation thresholds restated in the same entry**

**WHAT:** 2026-09-23 evening the owner reported, conversationally, that a coughing fit made him pull over and vomit (dry retching, then a little yellow liquid = bile, on a day he had eaten nothing). It was the third message in a row about his understanding of viral illness, not a request.

**WHY IT MATTERS AS A RULE:** the useful move was not to answer the question he asked and stop. It was to (a) recognise a change in the *character* of the cough - 'dry cough' in section 22.2 became **paroxysmal with post-tussive vomiting**, which is a different clinical object and the classic adult description of pertussis, (b) write it into the record the same evening as a NEW dated section (s32), never editing 22.2, and (c) restate the escalation thresholds *in the same entry*, because s19's intake loop and s13's dehydration were both live again on the same night.

**MEASURED:** the record went 2007 -> 2065 lines in one append; the file's own rule (README rule 2, append never rewrite) is what makes a symptom log usable - s32 can be read on its own without trusting any earlier summary.

**ALSO:** 'bile on an empty stomach' is the single most misread observation in this class of report. Yellow vomit with nothing in it is not a finding; it is the confirmation that he had eaten nothing. Write the reading next to it so nobody - including a future session - treats the colour as an alarming discovery.

**TIES TO:** L2184 (the missing measurement is the finding), s19 (three days of almost no intake), s24.2 (188 -> 182 lb), task 26714 (tonight's fluids check) and 26704 (the LabCorp result).
