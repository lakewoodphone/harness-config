**L1514 · FAT drives with Hebrew names: the default mount shows ??? and a copy under it destroys the names; also pkill -f kills your own ssh shell**

Three separations, all measured 2026-09-15 on the Newman "two flash drives have a virus" intake.

**1. `pkill -f <pattern>` over SSH kills your own shell when the pattern appears in your command line.**
I ran (single ssh call) `pkill -f "ddrescue /dev/sdc"; pkill -f "ddrescue /dev/sdi"` to stop two
imaging jobs. The remote `bash -c '<the whole command>'` contains that literal string in its own
argv, so pkill matched it and the session died mid-script: **no output, exit 1**, and I could not
tell what had actually happened. The kills I wanted did happen, but so did one I did not. Fix: kill
by pid (`pgrep -f X | grep -v $$ ...`), or target tmux sessions, or use a pattern that cannot match
your own argv. Never trust `pkill -f` as a fire-and-forget step in an ssh one-liner.

**2. Wait for the data, not for the insurance copy — and know which one is which.**
Two ddrescue images (30.8 GB each) plus an rsync of the real data all ran against one xHCI
controller: total throughput ~13-15 MB/s spread over three readers, which would have finished the
customer's copy in ~90 min. Stopping the ddrescue jobs (mapfiles kept → fully resumable) let the copy
run at ~8 MB/s with the device to itself. Rule: on healthy media the customer's data is the
deliverable and the full-surface image is insurance; image after the copy, not before it — and never
in parallel on the same controller. The SOPs say "image first" because the SOPs are written for
*failing* media.

**3. FAT drives holding Hebrew (or any non-Latin-1) filenames are destroyed by the default mount.**
`sdc1`/`sdi1` auto-mounted with `iocharset=iso8859-1`, which rendered real names as `???`:
`Music/אלול זמן תשפ''ב-תשפ''ג (סוכה)` became `Music/???? ??? ???''?-???''? (????)`. That is a
*display* artifact — but a file copy performed under it would have written the `???` names to disk,
collapsed distinct names into collisions, and looked like a successful copy. The data was never in
danger; the *names* were. Always `mount -o ro,iocharset=utf8` for FAT/exFAT before listing or copying,
and treat a `???` listing as a wrong mount, not as damage. Same class of bug as reading the wrong
database: the reading was believed because it looked plausible.
