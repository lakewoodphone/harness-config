**L2507 · A DSH install is a set of versions; dsh --version reports only the launcher**

## A DSH install is a SET of versions, and `dsh --version` describes only the launcher

MEASURED 2026-09-23 (ZABZ-TECH), by reading every `package.json` under
`%LOCALAPPDATA%\npm-cache\_npx\1e7f6d9597241db0\node_modules\@deepseek-ai\`:

- `node .../@deepseek-ai/dsh/lib/bin.js --version` prints **`0.1.5-rc.1`**.
- The install holds **240** `@deepseek-ai/*` packages. **230 of them are `0.1.5-rc.2`.**
 Exactly **one** package is `0.1.5-rc.1`: the `dsh` launcher itself.
- The remainder are their own lines: cordis `4.0.2`, cordis-plugin-hmr `1.0.17`,
 cordis-plugin-timer `1.1.4`, schemastery `3.18.2`, cosmokit `1.8.3`, node-addon-system `0.1.2`.
- Cause: `@deepseek-ai/dsh@0.1.5-rc.1` declares its dependencies as `^0.1.5-rc.1`, and npm resolved
 them to the highest matching prerelease (rc.2).

WHY IT MATTERS: the version string is not the identity of the engine. Two installs that both report
`0.1.5-rc.1` can differ in 230 packages, so any check that compares version strings -- a pin, an
"is it newer" test, a changelog lookup, `dsh --version` in a health probe -- is answering a
different question than the one being asked.

WHAT TO DO INSTEAD: record and compare the **per-package version map**, and diff **surfaces**
(`package.json` exports, the composed plugin tree, which rows a patch applied to) rather than
numbers. `dsh-update/state/pin.json` therefore carries `packageVersions` plus a sha256 of it, and
`dsh-update/SPEC.md` treats the `contractSha256` -- not the version -- as what a verify result is
bound to.

GENERALIZATION: this is the same class of error as reading a stale database replica and believing
it (LESSONS L51 / PAIN P22). A convenient summary field was trusted where the underlying set was
available and cheap to read.
