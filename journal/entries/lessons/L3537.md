**L3537 · PowerShell arg-passing: never name a parameter Args; never splat a string; Mandatory [string] rejects arrays**

Three separate ways a PowerShell helper silently or loudly fails to pass arguments, all measured on pwsh 7.6.6 (2026-10-08, ZABZ-YOGA):

1. A parameter named `$Args` never binds. `param([string[]]$Args)` receives NOTHING - not positionally and not by name - and the body's `$Args` resolves to the automatic unbound-arguments variable (empty). The function then runs its program bare. `param([string[]]$AdbArgs)` binds normally.
2. Splatting a STRING passes one argument PER CHARACTER: `$s = 'shell getprop'; & adb @s` gives adb the single argv entry 's'. Splat only arrays of argv tokens. This is why a `[string]$Command` parameter splatted with `@Command` always fails.
3. `[Parameter(Mandatory = $true)][string]$p` REFUSES an array argument; without Mandatory, `[string]$p` accepts @('a','b') and coerces it to 'a b'. So a Mandatory string parameter is stricter than it looks.

Verification pattern that catches all three without running the script: parse with the PowerShell AST, find the FunctionDefinitionAst, read Body.ParamBlock.Parameters for the real names and types, Invoke-Expression its Extent.Text, then call it and compare against a known device answer. Note FunctionDefinitionAst.Parameters is EMPTY for `function f { param(...) }` - the declarations live in .Body.ParamBlock.Parameters.
Also: run each helper's proof in its OWN pwsh process. Redefining same-named helpers with Remove-Item/Invoke-Expression inside one process gave a stale live definition twice and produced a wrong proof result.
