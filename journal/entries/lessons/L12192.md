**L12192 · A scoping fix can blind its own consumer - make the reader ask a named question and say which one it answered**

2026-10-22, fx-admin (C:\\Users\\ezabz\\code\\_pt_wt\\fx-admin, commit cc0c474). Commit 19e84aa correctly made GET /api/feedback namespace-scoped (free text readable only when a namespace is named). Its only consumer, src/app/feedback-admin/page.tsx, kept calling ?limit=100 with no namespace, which resolves to the default production library - empty on the live box, because participants write into user:<digest>. The owner's page said 'No feedback yet.' for a day with real feedback one namespace over. Two transferable facts. (1) A security fix that narrows a read has a consumer list, and a consumer that omits the new required parameter does not fail - it silently reads the narrowest scope. Grep the consumers of the route before calling the scoping done. (2) The page could not distinguish 'empty table' from 'wrong namespace', which is why nobody noticed. Any read whose scope is implicit must return the scope it used, so an empty answer can be questioned. The fix is a NAMED cross-namespace read (?scope=all, behind the existing requireOperator, parsed fail-closed so an unrecognised scope is 400 and not a silent fallback), not a return to an unscoped default.
