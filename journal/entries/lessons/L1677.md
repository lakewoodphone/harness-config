**L1677 · A proposed fix can be wrong while being right about the defect: check the precondition (A-007 would have created the duplicate it prevented); and a check that fails permanently must be reclassified or it becomes decoration**

**L1670 · Two rules from ending the 12-hour website silence, 2026-09-15.**

**1. A proposed fix can be wrong even when it is right about the defect — check the fix's own
precondition.** Axis A correctly found that the Weingarten case record carried the literal string
`"PENDING"` as its phone, and correctly reasoned that a push would insert a third duplicate customer
(production already holds two Weingarten rows at (917) 902-6334, and `create_customer` skips its phone
lookup entirely when the phone cannot normalise — `website_db.py:889-905`). Its proposed fix, A-007, was
to set the phone to `9179026334`, conditional on *"the case file must confirm it"*.

I read the case file. It says `- **Phone:** PENDING (need number to create backend contact/work order)`
— the number was **never captured** — and the case is **CLOSED (2026-09-02)** with the owner's own
decision *"no fix"*. So the precondition fails: there is no phone to set, no contact, no order and no
work. Applying A-007 would have manufactured the exact duplicate it existed to prevent, using a surname
as the only evidence.

**The general rule: an operation's precondition is part of the operation.** A plan that says "do X, if Y"
must have Y actually checked before X runs, and the honest output when Y fails is not "X with a caveat"
but "this record's correct state is *not pushable*". Three of the six remaining case pushes were held
for this class of reason, and pushing any of them would have written a bad customer row into the
customer-facing record of record.

**2. A check that fails permanently is not a check — reclassify it or it becomes decoration.**
My own `lpt-recon.py` FAILed on `dialpad_sms_cache` because 127,880 rows held only 125,136 distinct
`message_id`. Axis D had already measured the same rows and found that **all 2,744 duplicate groups
differ ONLY in `session_id`** (the same message stored under both its raw id and `ptf-thread-<phone>`)
with **0 groups differing in `body_text`** — so dedup by `message_id` discards no distinct text and the
row count is not a defect at all. A light that is red every single run teaches its reader to ignore it,
which is the same failure as a job that runs, exits 0 and produces nothing.

So the check now fails **only** on `COUNT(DISTINCT body_text) > 1` for a single `message_id` — i.e. on a
genuine content conflict — and reports the row counts as information. That is the general shape: a check
should fail on the thing that would actually be wrong, not on a stable property of correct data.
Two adjacent cases, same session: `dedup.dialpad_call_full` passes because `call_id` is unique while the
indexer collapses by a *different* key, so the check says so in its own output rather than implying
everything is clean; and `identity.gap` counts unnormalised addresses (4,255) where axis C's normalised
comparison gives the authoritative 1,463 — so it is labelled informational with that stated, and it is
watched for movement rather than used as a verdict.

**Also earned, and cheap:** the freshness signal must measure the clock of the thing it claims to watch.
The 11.5-hour silence survived because the only staleness check read `MAX(dialpad_sms_cache.fetched_at)`
— the LOCAL receive time, which the live webhook kept refreshing — instead of the website's own
`website_sync_cursor.last_synced_at`. The watchdog was watching the clock that could not go wrong.
