**L3421 · Card-number scanning: 15 digits is an IMEI, and a scrub that catches identifiers destroys real evidence**

**Scanning for card numbers: 15 digits is an IMEI, not a card. And a scrub that catches identifiers
is worse than none, because it destroys the only handle on a real event.**

The shop's own message log holds **187 rows across 9 customer files** containing what a customer
types as a card number (measured 2026-10-09 with the pattern below), from 2026-05-20 to 2026-09-20.
Two false-positive classes cost real time here before the pattern was tightened:

- **A loose pattern `(?:\d[ -]?){13,19}` matched a phone number glued to a year.** Case-file ids like
 `text-unknown-7325692764-2026-09-20` read as a 15-character digit run, and 17 analyst verdicts were
 flagged as carrying card data when they carried a filename.
- **A bare 16-digit run is also a Dialpad message id, a Dialpad call id, and a vendor ticket.** Three
 genuine identifiers were destroyed as "card numbers" on the first pass, including
 `Dialpad call_id 5547303011393536`.
- **15 digits is an IMEI** (the IRIS Easy Flip reads `350825534050303`). Redacting one throws away the
 only device identifier some orders have.

The rule that works:

```
CARD_RE = (?<!\d)(?:\d{4}[ -]){3}\d{4}(?!\d) | (?<!\d)\d{16,19}(?!\d)
```

plus a marker check on the 24 characters before a match — `dialpad`, `call_id`, `message id`,
`ticket`, `imei`, `serial`, `s/n`, `stripe`, `pi_`, `order id` — which means `find_card_numbers`
returns **identifiers out, cards in**.

Two structural consequences worth keeping:

1. **Scrub at the boundary, refuse at the writer.** An analyst that copies a PAN into
 `proposed_note` would otherwise have it written back onto a work order. `merge` scrubs every field
 of every verdict before it travels; `apply` refuses a note containing one. Belt and braces, because
 the first has already fired once (order 2082) and the second never has to.
2. **A scan reports a count, never a value.** The register can say "187 rows across 9 customer files"
 and must never print one. There is a test that asserts the register contains no card digits.
