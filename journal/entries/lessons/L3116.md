**L3116 · A dry run that deletes is worse than no dry run: read the label as a claim and verify it**

MEASURED 2026-09-30, in my own code, while restoring the backup retention script.

The first version parsed arguments as `ROOT="${1:-}"` with a positional check for `--dry-run`.
Invoked as `prune-backups.sh /root --dry-run`, it printed

 prune-backups: 21 backup(s) present, keeping 15, removing 6 (~82 GB), DRY RUN
 removed 20260929T060001Z
 ...

and DELETED all six. The DRY RUN label came from `${DRY_RUN:+...}` on a variable that happened
to be set by a different branch, while the delete loop tested the same variable that was
unset. Two reads of one control, disagreeing - the exact defect class this whole session was
about, committed inside the fix.

WHY IT MATTERED LESS THAN IT COULD HAVE: the deletions were authorised by a documented policy
(F7, one per day inside a week, one per week inside a month), the affected volume had 82 GB of
redundancy, and a full SQL dump of the affected table had been taken first. It was still a
destructive action taken under a label that said it was not destructive.

THE RULES THAT FOLLOW:
 * A destructive script's argument parsing must be an explicit scan over "$@", not positional
 defaults. The parser is the safety mechanism.
 * Print what the script is ABOUT TO DO and what it DID as different words. "DRY RUN - nothing
 will be deleted" cannot be misread; "DRY RUN" next to "removed" can.
 * Read the output, not the label. The only reason this was caught is that the "removed" lines
 and the DRY RUN banner appeared in the same screen of output.
 * Before any delete, take a restorable dump of what is affected - even when the delete is
 "just files", and especially when the script claims it is a dry run.
