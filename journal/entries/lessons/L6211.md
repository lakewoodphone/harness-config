# Before delegating a build, verify which PATH is live — here `/root/personal-secretary-mvp` was a symlink, and the service ran from `/opt/company`

**Rule.** "Where does this run from" is a fact you must read, never infer. On `secratary-cloud`:

```
WorkingDirectory=/opt/company # systemctl cat company-api.service
/root/personal-secretary-mvp -> /opt/company # a SYMLINK
stat -c '%i %n' /opt/company/app/sms_service.py /root/personal-secretary-mvp/app/sms_service.py
 -> the SAME inode 150123
```

I almost reported the app-side work as undeployed because the service's `WorkingDirectory` was not the
path the brief had named. The symlink made the two identical. **Both readings were wrong in opposite
directions** and only `stat` of the resolved file settled it. Related: the exit-code-0 trap — a
deployment can be on disk and **not in the running process**; compare `ps -o lstart=` against each
edited file's mtime before claiming a change is live. Measured here: the process started 01:14:19,
`sms_service.py` was written 01:16:09, so the relay wiring was on disk and absent from memory until the
recorded restart at 01:43:59.

**Why it matters.** `docs/parallel-agent-orchestration` P3141/P3139 already warn that children land on
nodes without the repo. This is the same failure one level down: the child landed on the right *host*
and the right *repo path*, and the process still did not have its bytes.
