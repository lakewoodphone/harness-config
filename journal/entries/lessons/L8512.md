**L8512 · A test against a copy of the database still wrote to the real journal: two fake owner answers in the append-only record**

**L · A test against a copy of the database still writes to the real journal. The append-only record got two fake owner answers.**

2026-10-18, auditing the owner queue. To prove that `answer 631 --with 645` closes two rows that are
the same matter, I ran it against `/tmp/oq-e2e.db` -- a throwaway copy of the reader's tables, built
on purpose so the test could not touch production.

It closed the rows (correct), wrote the feedback rows (correct) -- and called `_journal_copy()`, which
resolved the journal from the *environment*, not from the database it was writing to, and appended
**D7041** and **D7042** to the authority's append-only decisions log, recording an owner answer that
reads exactly like a real one: *"His answer: paid it today, both alerts same card"*. He never said it.
Nothing about that Chase account was paid.

The append-only rule means D7041/D7042 can only be corrected, never removed -- so a test run has put
two entries into the company's permanent decision history that a future session could cite as his
judgement. (Corrected by D7043, which states they are void and why.)

**The rule:** when a tool writes to more than one store, the stores must be chosen from the SAME
scope. A sandbox database with a live journal is not a sandbox -- it is a live journal with a
throwaway queue. `_journal_copy()` now refuses unless the database it is closing is `authority.db`
by realpath, and says so out loud when it refuses. Verified by re-running the identical test: rows
closed, no entry, one line of explanation.

Corollary, and it is the one that would have saved me: **before running a write path "safely", find
every store that path touches** -- `grep` the function for file paths, subprocess calls and env
lookups -- not just the database it takes as an argument.
