**L7231 · Correcting D6213: verify a file's identity on disk after writing it, not from the script's own pre-write numbers**

D6213 recorded the wake-contract file as 64948 bytes. That number came from the editing script's own print statement, which reported the size from the buffer it was about to write, not from the filesystem afterwards. Read back from disk in the same session: 64968 bytes, md5 262035f01a648864986e008e5614692b, mtime 2026-10-16 15:26. The content is correct and verified - rules 1..8 in order, the new rule 5 present and idempotent, every cross-reference consistent (close -> rule 8, owner-queue -> rule 7), bash -n exits 0 - but the byte count in the entry is wrong by 20 bytes and the entry is append-only, so the correction lives here rather than as an edit.

THE RULE: after writing a file, re-read its size and hash FROM DISK and quote those, never the numbers your own tool printed. A tool's success message describes its intent; stat and md5sum describe the artefact. This is the same defect as reporting a service healthy because you started it.

ALSO, second occurrence of the same harness bug, now with a reproducible shape: in a here-string script piped to the authority, a command that expands a shell variable into a path produced 'grep: /root/bin/wake-dispatch.sh\n: No such file or directory' - the filename arrived with a newline attached. It has now hit grep twice, sed twice, cat and head. It is intermittent and it only affects lines that expand a variable or carry a quoted pattern; the same command written with a literal path succeeds. Until it is fixed, prefer literal paths in remote one-liners over variable expansion.
