**L3606 · A file piped to another machine is not verified until both sides print the same sha256 (base64 it)**

**The rule.** Never believe an artifact copied to another machine because the command exited 0. Hash both
sides, and when they differ, hash the **content** again after normalising line endings before concluding
anything — a mismatch has at least two causes and they need different fixes.

**What happened, 2026-10-11, twice in one session:**

1. `Get-Content <file> -Raw | ssh host 'cat > /dest'` produced a file of **27409** bytes on the remote
 against **27407** locally, and a different sha256. PowerShell re-encoded the stream on the way through
 the pipe (CRLF, and whatever else it decided). The transfer *looked* perfect — `head -c 90` printed the
 right first line and the file was readable.
2. The fix: `[Convert]::ToBase64String([IO.File]::ReadAllBytes($src))` piped to `base64 -d` on the remote.
 Both sides then reported **the same sha256 and the same byte count**, which is the only acceptable proof.

**The subtlety that costs a wrong conclusion:** after the first attempt I normalised CRLF→LF locally and
still got a different hash (`643a99bc…` vs `18b57775…`) at different byte counts (27257 vs 27409). So this
was **not** a line-ending difference — 152 bytes of real content had changed. Had I stopped at "it's
probably CRLF" I would have shipped a corrupted deliverable to the authority and reported it as verified.

**Do it this way:** for any file that must arrive byte-identical on another machine (an audit, a report, a
script another host will execute), transfer base64 and compare `sha256sum` output on both sides. A text
pipe through a PowerShell → ssh boundary is lossy, and the loss is silent.
