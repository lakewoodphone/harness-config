**L4704 · Both home routers answer their own JSON API - reading them found in minutes what a night of laptop tests missed: the phones are on 2.4 GHz at 11-26 Mbps, and the house runs on the cellular gateway while Fios bills at the same address**

Measured 2026-10-15 on the owner's home network. Two things came out of it that a full night of laptop-side testing had missed, and both took minutes once the routers themselves were read.

1. THE PHONES ARE ON 2.4 GHz. `getDeviceDetails` on the CHR30A lists every client with the band the router sees it on:

 a phone, randomised MAC 62:3E:76:55:36:D6 2.4 GHz 20 MHz 11.0 Mbps PHY RSSI -69 active 10-15 10:34
 "iPhone" 2.4 GHz 20 MHz 25.8 Mbps PHY RSSI -67
 zabz-yoga (Wi-Fi) 6 GHz 160 MHz 2268.5 Mbps PHY RSSI -40

 Two hundred times apart, on one network, at one moment. A device sitting at 11-26 Mbps of PHY on 2.4 GHz is slower than the cellular uplink's worst minute, so every bandwidth measurement taken from the laptop ("the path is healthy, no loss, 269 Mbps aggregate") is true and irrelevant to what the owner experiences on his phone. 6 GHz carries roughly 10 dB more path loss than 2.4 GHz, which is why the client picks 2.4 on its own and why the real fix is distance or removing 2.4 from the main SSID, not a router toggle.

2. THE HOUSE RUNS ON THE CELLULAR GATEWAY WHILE FIBER IS BILLED. `getRouterDetails` on the CHR30A: ipv4AddressWan `192.168.12.245`, gatewayIPAddress `192.168.12.1`, ipv4AddressingType DHCP. That 192.168.12.1 is the T-Mobile TMO-G4AR gateway - it answers `<title>T-Mobile Gateway</title>` and its own API. Meanwhile Verizon Fios 300 Mbps was installed at this house on 2026-09-14, order NJ12338123101, 30 a month, ONT serial ALCLECEF1FB204, and the ONT is in the house. So the fiber is not in the path and the cellular link is, at 85 a month.

THE RECIPE, so this is never again a guessing game. Both home routers serve a React bundle and a JSON API behind it.

 CHR30A (Verizon, https://192.168.1.1) - two-step login, admin password 6CVBTT3B3 (recorded in personal-secretary-mvp/docs/network/verizon-fios-home-2026-09-14/):
 POST /CRSP/open/login with header "Authorization: Basic base64('admin:PASSWORD')" and body {"keepMeSignIn":false} -> sets authToken cookie
 POST /CreateXSRFToken -> returns x-xsrf-token header and cookie
 POST /CRSP/<endpoint> with header "x-xsrf-token: <token>" and body {} -> works
 Every endpoint is POST; a GET returns 405. Without the xsrf header, authenticated calls return 403. 163 endpoints; getRouterDetails, getNetworkConnections, getDeviceDetails, getRadioSettings, getIpv6Configuration, getARPTable are the useful reads.
 TMOBLE TMO-G4AR gateway (http://192.168.12.1) - READS ARE OPEN: GET /TMI/v1/gateway?get=signal and ?get=all give band, bars, RSRP/RSRQ/RSSI/SINR, APN, hasIPv6, uptime. Writes are token-gated.
 Finding the paths on any such appliance instead of guessing: fetch /static/js/main.<hash>.js and regex the quoted paths out of it.

WHY THIS IS THE LESSON AND NOT THE MEASUREMENT: on 2026-10-14 I measured this link for three hours from the laptop - pings, MTU bisect, parallel streams, YouTube fetches, a variance battery - and concluded the path was healthy and the phone's problem was not reproducible. The phone's problem was one HTTP call away the whole time, in a device I had never asked. Reach for the appliance's own API before building a battery of client-side tests; the client can only see the path it walks, and the access point knows which radio every client is on.
