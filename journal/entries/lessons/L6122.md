**L6122 · A hardcoded reason string is a constant, not a fact - and a cron job cannot act while cron is dead**

Correction to what I reported earlier in this session, and two mechanisms I had wrong. Measured
2026-10-11 by a fan-out child with the writes ledger in hand.

**1. THE `reason` STRING ON A STATUS MOVE IS NOT EVIDENCE OF WHO MOVED IT.**
I read `order_status_history` and told the owner the reconciliation was "walking orders backwards",
because every row's reason said *"Auto-updated by secretary reconciliation"*. That reading is wrong.
`website_db.update_order` **hardcodes** that string (line ~772) and **discards the caller's real
reason**. `/home/zabz/lpt-ops/audit/writes.jsonl` shows **four of the seven C07 rows were deliberate
human corrections** made through `lpt-write status set`, each carrying a real `reason_given` the
writer then threw away — `WO26100812732` 18:02:11 *"Redo did not cure the fault"*,
`WO26082712672` 18:14:48 *"Replacement battery GJKNX ordered"*, `WO26091512710` 03:22:04 explicitly
undoing *"an automatic reconciliation move with no completion event"*.
**Rule: when a writer hardcodes its own audit string, that string is a constant, not a fact. Read the
writes ledger to learn who acted.** This is the same class of error as reading a fresh file mtime as
fresh content — the field describes the writer, not the act.

**2. A CRON-DRIVEN JOB CANNOT HAVE ACTED WHILE CRON WAS DEAD.** All four of today's moves fell inside
`cron.service`'s dead window (Inactive 04:01:34Z, Active 19:04:08Z, `NRestarts=0`). Whoever made them,
it was not a cron reconciliation — it was the CLI on ZABZ-TECH. **Rule: before blaming a scheduled
job for something that happened in a window, check the scheduler was alive in that window.**

**3. THE TWO MECHANISMS THAT DO EXIST, both now guarded.** `website_db.update_order` wrote whatever
status it was handed with no comparison to the row's current status, and
`open_work_order_reconciliation.classify_open_work_order` picks a target from evidence *signals*
without reading the current status, testing `ready_for_pickup` (conf 0.92/0.90) **before**
`awaiting_parts` (0.90) — so the same order flips both ways as the window moves. Guard added in
`personal-secretary-mvp` commit `2667899`: `is_status_regression()` (deliberately the audit's own
`rank_anomalies` predicate and clause order, so writer and verifier cannot drift) plus a refusal in
`update_order` unless `allow_status_regression=True`, and an optional `reason=` stored verbatim.
Live proof: `WO2610090001` READY_FOR_PICKUP -> AWAITING_PARTS returned `ok=False` and the row's
status and `updatedAt` were byte-identical afterwards.

**4. THE BACKUP TIMER WAS DISABLED BY HAND, and that places the actor.** `secretary-backup.timer` is
disabled and inactive because an operator ran `sudo systemctl stop` at 03:26:23Z and `disable` at
03:44:29Z; its last run was killed by SIGTERM after 19 minutes holding the database. That is the same
night, the same motive and almost certainly the same actor as the 04:03:33Z burst that masked cron:
**something on the authority decided the database was too locked and took the writers down, one
service at a time.** Still unnamed, but its behaviour is now consistent across two independent events.

**5. WHAT WAS NOT ACTUALLY BROKEN.** `transcript-archive-pull.py` never opens `secretary.db` — `fuser`
and `lsof` list no archive pid and the script has zero sqlite references — so the archive was not the
cause of the Dialpad contention; it is SQLite WAL single-writer contention among `secretary.db`
writers. And **"about one call per run is lost" is refuted**: the harvester keeps no persisted
watermark and every failed `call_id` was present in `dialpad_call_full`, delayed one to two runs.
