**L9728 · Learned is not usable: 10 of 11 self-learned aliases named a category the ledger could not file, and the store looked healthy**

"Learned" is not the same as "usable": check that what a self-evolution hook writes is a vocabulary the consumer can actually resolve.

The owner text channel's self-evolution hook writes his answers into `~/.cfo-asks/aliases.db`, and the asker reads that store before asking again. Measured 2026-10-19: **10 of 11 learned rows could never be filed.** Five named the category `personal` or `unknown`, five named no category at all. `category_id_for()` returns "" for a name the `categories` table does not hold, so every one of those rows resolved a charge as ANSWERED and filed nothing - and the same charge came back weeks later, which is exactly the "Didn't we file a few days ago?" loop.

The store looked healthy. It had rows. It had evidence. It had timestamps. It was 91% inert.

TWO MECHANISMS WORTH CARRYING:

1. **A word the owner uses is not a row in your table.** "personal" is not a category - it is which ENTITY a charge belongs to, and the ledger already carries `entity_id` for that. The code mapped his word onto a category because both were strings, and produced rows that were semantically wrong AND unfilable. When absorbing free text into a controlled vocabulary, resolve the term against the vocabulary at write time and refuse what does not resolve.

2. **A name is not a key.** The same table held 44 names appearing more than once with different ids (29 harmless, **15 genuinely split** - Credit Card Payment 59/49, Materials & Equipment 226/54). `SELECT id ... WHERE name = ? LIMIT 1` with no ORDER BY meant the same kind of charge could be filed under different ids on different days while reading identically on screen. Prefer the id already in use, tie-break deterministically, and say when a name is ambiguous.

THE INSTRUMENT is the durable part: `text-health.py` J1 - "every learned alias names a category the ledger can file" - runs with the channel's other 16 invariants. It reports the whole backlog every run and FAILS only on a regression inside the window, because a gate that is red for last week's rows is a gate every later session learns to ignore.

AND THE TEST CAN ENCODE THE DEFECT. `test-attribute-reply.py` case 14 asserted `build_alias` produces category `"shop supplies"` - a name the ledger does not hold either. The suite was green on exactly the bug it should have caught. When you find a broken row, grep the tests for the broken value.
