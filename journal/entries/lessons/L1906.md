**L1906 · A node capability must live in ONE module: the same rotted path was fixed in one package and left in another**

A node capability must live in ONE module. On 2026-09-17 the same rotted interpreter path
(`/home/zabz/.local/node-v24.12.0-linux-x64/bin/node`, which does not exist on that machine) sat in
TWO tables: `plugin-remote-fanout/lib/nodes.js` (fixed that day, docs/mesh/102) and
`plugin-mesh-http/bin/mesh-dispatch.mjs:113` (found, reported, untouched — docs/mesh/102 §7). A copy
is not a variant; it is a second item with its own lifetime and no mechanism to notice the other.

Fixed 2026-09-17 (docs/mesh/104): `mesh-dispatch.mjs` now imports `NODES` and
`resolveNodeInvocation()` from `packages/plugin-remote-fanout/lib/nodes.js` and derives a VIEW
(`{ssh, label, hosts, shell, cwd, invocation, invocationNote}`) — no re-declared fields, `label` is
the table's own key. Two things made the fix more than a rename:

* the v1 program is now a PURE FUNCTION (`buildV1Program({facts, task})`), so the string that rotted
 is a value the suite asserts on instead of a string built inside a spawned promise;
* the executor form came with it. Correcting the PATH alone would have left the node dying
 `MISSING_CREDENTIAL`, because naming an interpreter bypasses the `dsh` wrapper that sources the
 credential (docs/mesh/102 §2 row 1). A "correct it identically" fix would have replaced one broken
 invocation with a different broken invocation.

EVIDENCE: `node bin/mesh-dispatch.mjs -Node zabz-tech-linux -Transport v1` -> `ok:true,
childExitCode:0, childHosts:["zabz-tech-linux"], disagreements:[], meshHostLines:1, ms:5776`;
`npm test` in plugin-mesh-http -> 40 tests, 40 pass, 0 fail (36 before, 4 new); `npm run verify`
exit 0.

RULE: when two packages need the same facts, one EXPORTS and the other derives a view. If you are
about to copy a table, ask which of the two copies has a test that would fail when the other rots.
