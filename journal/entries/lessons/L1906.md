**L1906 · dialpad_sms_cache.created_at is the sync time; and never infer silence from the absence of SMS**

Two data traps in the comms tables, both measured 2026-09-17 while pulling the Weitman case (848) 333-6341.

**1. `dialpad_sms_cache.created_at` is the SYNC time, not the message time.** Every sync re-inserts old messages as new rows with a new `id` and a new `created_at`, so the table reads backwards. Measured on the authority: the 2026-09-09 exchange was stamped `created_at` 2026-09-17T11:46, and the same body text appears four or more times with different ids ("We do not have cheaper than \$390" at ids 1109222, 1109280, 1109649). Ordering this table by `created_at DESC` returns the OLDEST messages as the newest. RULE: order `dialpad_sms_cache` by `message_id`, de-duplicate by it before counting, and never answer "when did we last contact this customer" from `created_at`. `dialpad_call_full.date_started_ms` is a real epoch-ms event time and can be trusted.

**2. Do not infer silence from the absence of SMS.** The same case file said, in three separate places, "nobody has called her" and "the phone call still has not happened". `dialpad_call_full` holds three connected calls to that number: 2026-09-15 15:32Z (358 s), 2026-09-15 15:44Z (171 s), 2026-09-16 21:23Z (63 s). Worse, a sourcing session wrote that claim into the file at 16:28 ET on 2026-09-15 — *during* the window in which two of the three calls happened — because it never queried the call table. RULE: before writing or repeating "nobody contacted X" or "no reply", query `dialpad_call_full` for the phone in the same breath as the SMS table. A silence claim is a measurement, not a default.
