**L2986 · Version guard verified both ways: weak-source labelling on fallback, and a correct REFUSAL when two engines make the answer ambiguous**

## The hardened version guard is verified from two sides, and it correctly REFUSES when it cannot tell which engine is running

MEASURED 2026-09-28 (ZABZ-TECH). `scripts/check-version-coupled-config.py` was rewritten after the live
incident (P2733) so that the engine that is RUNNING wins over configured knobs.

VERIFIED, fallback path -- and this is the fix for the incident's root cause:
```
 engine root : <candidate prefix> (from dshInstall in <fixture windows.json> -- WEAK: no running engine found)
 engine : 0.1.7-rc.2 (@deepseek-ai/dsh/package.json)
 found via : CONFIGURATION ONLY (WEAK: no running engine found) -- no engine process was found among
 the 42 node process(es) scanned
 configured : dshInstall -> <candidate> (0.1.7-rc.2) [USED -- no running engine was found, so this
 reading is WEAK]
 configured : $DSH_HOME/profiles -> <npx install> (0.1.5-rc.1) [USED -- no running engine was found,
 so this reading is WEAK]
```
It quotes its own reasoning: *"A configured path is where the launcher expects the engine, not evidence
of what is executing, so this reading is weaker than a running process and the report says so."* That is
precisely the sentence whose absence caused the incident.

VERIFIED, ambiguity path. With a `dshInstall` fixture present AND two engines running, it refused:
```
 check-version-coupled-config: TWO DIFFERENT ENGINES ARE RUNNING and this check cannot say which one a
 new session would mount on. Refusing to judge the version-coupled config against either:
 0.1.5-rc.1 ...\npm-cache\_npx\1e7f6d9597241db0 (pid 26856, web engine on port 3099)
 0.1.7-rc.2 ...\dsh-update\vendor\prefix\0.1.7-rc.2 (pid 29812, web engine on port 3422)
 ... Until then the two steps that depend on this answer -- presets and profile patch layers -- must
 not be applied.
```
**This is the guard doing its job rather than a defect**, and it surfaced something I had not noticed:
engine processes left running on ports 3401/3422/3423 by concurrent staged-boot tests. It exits 2, which
`sync.py` must treat as "the check did not run" and therefore SKIP the two coupled steps -- so ambiguity
fails safe. The incident case (single running engine + a transient `dshInstall`) could not be exercised
at that moment BECAUSE of those test engines; re-run it when the machine is quiet.

A DESIGN CONSEQUENCE OF THE FIX, which the switch must respect: with the running engine winning, **a
sync can never apply the version-coupled config while the OLD engine is running** -- it will always
skip, correctly. So the switch cannot rely on `sync.py` to install the migrated presets and profile
layers; it must write those files itself, from the staged copies it already records, with its own
rollback. `sync.py` keeps owning everything else (settings, skills, client plugins).

AND A NEW PRACTICAL LIMIT WORTH KNOWING: any staged-boot test that leaves an engine listening on
3400-3500 will make this checker refuse on the NEXT test until it exits. Tests must clean up after
themselves, and a `doctor`-style sweep for stray engines in that range would be a good addition.
