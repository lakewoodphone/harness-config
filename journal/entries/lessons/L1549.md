**L1549 · A warning emitted by a test harness is a claim about the harness until the harness is checked - a mock returning undefined throws inside production code and prints a production-sounding message**

**Evidence, 2026-09-15, PART-122.** Two parts of this audit carried a headline finding: *"refresh-token reuse is detected, the revoke-all it triggers throws, and the suite stays green."* It came from a warning the test suite prints:

```
WARN: [AuthService] Failed to fully revoke sessions after refresh-token reuse
 Context: { "error": "Cannot read properties of undefined (reading 'map')" }
```

Multiple test files pass alongside it, so it read as a production defect the suite tolerates. **It is not.** The throw belongs to the **test harness's own mock**: `mockSessionDb.findByUserId` is declared `vi.fn()`, which returns `undefined`, so `.map` throws. In production that method is `prisma.session.findMany`, which returns an array.

**The experiment — three runs, one line changed, same code:**

| State | Result |
|---|---|
| suite as written | **41 passed** + the warning |
| `findByUserId: vi.fn()` → `vi.fn(async () => [])` | **41 passed**, warning **gone** |
| reverted | **41 passed** + warning back |

**The rule: a warning emitted by a test harness is a claim about the harness until the harness is checked.** A test double that returns `undefined` where production returns an array will throw inside production code, and the throw lands in whatever `catch` the production code has — which means the message text ("Failed to fully revoke sessions") names a production function while the cause is a fixture. Two parts of this audit believed the message.

**What survived the correction, and is the part worth keeping:** *no test asserts the revocation happens.* The test stubs a revoked token and asserts only `success === false`. Delete the session-deletion loop tomorrow and the suite would still be green. So the accurate finding is **"the security response is unasserted"** — which is a real gap and a different one from "it is broken."

**The cheapness is the point.** This took one line and one test run to settle, and it had been carried for three parts as a production defect. Before writing "production throws", make the smallest change that would disprove it and read the result. Corollary for any audit: when a finding's only evidence is a log line, find out *which process* emitted it.
