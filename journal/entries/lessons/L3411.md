## A backlog at a fixed priority is never reached when every discovery files at the top, and a duty given read-only tools can never produce an artifact

Two independent traps, both found on 2026-10-09 while answering the owner's question about the
kosher filter, and both generalise past that project.

**1. Self-filed urgency starves a standing backlog.** `~/bin/work.py _pick_next` orders by
`priority ASC` first. A shift is told to file the work it discovers; it files what it just found at
priority 1 (two items on 2026-10-08, two more on 2026-10-09). The project's real product backlog sat
at priority 5–7 and was therefore **unreachable by construction** — 162 Integrate attempts and 90
Windows attempts in 14 days against **3 Android attempts (newest 2026-09-29) and zero iOS attempts,
ever**. Nobody had to make a wrong decision for the phone platforms to be abandoned; an ordering
rule plus an incentive to file is enough.

*The durable fix is not "work harder".* It is (a) put the standing backlog at the top, and (b) know
the tie-break: `created_at ASC` means an **older** item at the same priority wins, so promoting the
phone items also makes them beat the next p1 item filed tomorrow. Then write the rule down where the
filer reads it (the shift contract, STEP 5), or the starvation returns the moment a new discovery is
filed.

**2. A duty and a toolset are a contract, and this one was never satisfiable.**
`seed_eng_filter_ai_daily_push` asked for "artifact-backed code, tests, calibration output" in
`lakewoodphone/kosher-filter-ai`. The session it ran on had read-only repo/GitHub tools, no shell,
no write, and a 5-step budget. Result: 30 runs, 0 successes, 0 artifacts, two quarantines, and the
last three all ending at `planned_step_budget_reached_without_artifact`. It ran every day for a
month and did nothing, and **the failure looked like a transient to every monitor in the system** —
"failed" with a stale-sweep message is indistinguishable from "flaky".

**Ask of any new automation, before believing it:** read the tools it will actually hold, the
budget it will actually get, and the artifact it is required to produce. If those three cannot
produce the thing, the duty is a promise, not a plan — and a promise that fails daily is worse than
no automation, because the owner acts on it. The check is one line: `work.py`/`work_order_executions`
history shows whether it has *ever* succeeded.
