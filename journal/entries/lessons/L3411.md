**L3411 · LPT counter on test: queue endpoint 400s on AWAITING_PAYMENT, updateStatus 500s, and one click fires three mutations**

Measured 2026-10-08, signed in at 414x896 and 1440x900 on test.lakewoodphoneandtech.com.

1. THE COUNTER QUEUE DOES NOT LOAD ON TEST. `repairIntakeCases.list,workOrders.getAll`
 returns a 207 batch whose second part is an error:
 `[{"error":{"message":"[{\"code\":\"invalid_value\",...\"path\":[\"statuses\",3],...}]",
 "data":{"code":"BAD_REQUEST","httpStatus":400,"path":"workOrders.getAll"}}]`
 The frontend sends `statuses:[AWAITING_DIAGNOSIS,AWAITING_APPROVAL,AWAITING_PARTS,
 AWAITING_PAYMENT]` and the deployed backend's enum does NOT contain AWAITING_PAYMENT
 (it has CHECKED_IN, AWAITING_DIAGNOSIS, AWAITING_PARTS, IN_REPAIR, READY_FOR_PICKUP,
 COMPLETED, CANCELLED, UNFIXABLE, AWAITING_APPROVAL). Classic stale-frontend vs
 newer-backend vocabulary split. The page shows a raw Zod blob to the user - the
 error is not humanised.

2. CHANGING A STATUS ON TEST IS BROKEN. `POST .../workOrders.updateStatus` returns 500:
 `[{"error":{"message":"Cannot reopen COMPLETED work order: reopenReason is required",
 "code":-32603,"data":{"code":"INTERNAL_SERVER_ERROR","httpStatus":500,
 "path":"workOrders.updateStatus"}}]`
 One click fired THREE identical mutations. Good news: the UI did NOT claim
 "Status changed" - it stayed silent, so the confirm-only-after-the-server rule holds.

3. The counter detail page (`/work-orders?order=67`) still renders fully even while the
 queue endpoint is down - it is worth knowing that a broken list does not imply a
 broken detail view.
