## L-new · The preset's own skill directory registers nothing here — mirror skills into the user root

**Measured on ZABZ-YOGA 2026-10-08, one engine, one hour, three probes.** The `fast-search` skill lived in
the repo, in three presets, and in **no agent's catalog** — which is why the owner's "can you test the
faster search tools" cost a whole session of archaeology.

| probe | result |
|---|---|
| `zz-preset-probe/SKILL.md` placed **only** in `~/.dsh/.agent-presets/zabz/skills/` | never appears — not in the running session, not in a fresh local agent |
| the same file placed **only** in `~/.dsh/skills/` | appears in the running session's catalog **within seconds, no restart** (watched root) |
| the preset row's `customSkillDirs` rewritten from the `!!js` baseUrl expression to a literal absolute path | still nothing |
| `!!js process.platform !== 'win32'` in the same file | works — that platform's MCP rows mount |

So it is not the expression (the loader evaluates `!!js` with `with (ctx) { eval(expr) }`, and
`ctx.baseUrl` resolves): **the preset's skill provider does not activate in this composition.** An open
question, but not worth blocking on, because the user root works and is live.

**The rule:** `presets/*/skills` is the source of truth; `$DSH_HOME/skills` is the generated install
target, written by `sync.py:plan_skills()` with explicit precedence (zabz → cordis-bg → yocheved),
conflicts reported, and a manifest so a skill deleted from the repo is deleted here and a skill we did
not install is left alone. Documented with the check in `docs/skill-wiring.md`.

Acceptance test for any skill change: a fresh agent's `<available_skills>` block. If it is not there, it
is not wired, whatever the repo says.
