**L3714 · Never fix one broken escape with a whole-file regex - it repairs the legitimate ones too and silently invalidated a sync record**

Never fix one broken escape with a whole-file regex - it repairs the legitimate ones too, and on
2026-10-12 that turned a valid sync record into invalid JSON.

**What the file held.** The case file's front matter and the sync record's `device.summary` both
carried a mangled escape where a plain inch-mark belonged: `(16` followed by seven backslashes and
a quote.

**What I ran.** `[regex]::Replace($c, '16\\+"', '16-inch"')` over both whole files. In the `.md` it
matched the one broken site. In the `.json` it matched **four**: the broken one *and* three
perfectly valid escaped inch-marks - `"LG Gram 16T90P 16\" 2 in 1 Touch..."`, `16T90Q (2022) 16\"
2-in-1`, `Same 16\" 2-in-1 touch 2560x1600`. All four were rewritten, and the JSON became
unparseable: `"summary": "...(16-inch" Tiger Lake, ~2021, i7-1165G7)"`.

**Recovery, and the pattern that works.**
```powershell
$q = [char]34; $bs = [char]92
$n = [System.IO.File]::ReadAllText($p).Replace('16-inch' + $q, '16' + $bs + $q)
```
A literal `.Replace`, not a regex, restoring the escape everywhere it had been eaten; then
`json.load` + `jsonschema.validate` proved the record valid again, and the .md's front matter
parses because `16\"` is legal inside a YAML double-quoted scalar.

**Rules.** (1) On a file whose syntax uses escapes, match the broken region by its surrounding
context (here `" Tiger Lake`), never by the escape itself. (2) "One or more backslashes" is true of
every legitimate escape in the file. (3) Parse-validate after any text-level repair:
`json.load` for JSON, `lptcase check`/`find` for case front matter. (4) Writing `[char]34` and
`[char]92` instead of `\"` and `\\` also sidesteps the Windows PowerShell-to-native-command quoting
trap that eats embedded double quotes.
