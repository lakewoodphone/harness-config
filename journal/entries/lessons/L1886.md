**L1886 · On a shared repo, read origin/main and the remote branches BEFORE starting - a parallel session was doing the same camera/evidence job, better informed**

Before starting work on a shared repository, read `git log origin/main` and the remote branches. A parallel session may already be doing the same job, better informed.

MEASURED 2026-09-17. `ha-config` local `main` ended the session **12 ahead and 16 behind
`origin/main`**. The 16 upstream commits were a parallel session working the SAME camera/evidence
problem and touching the SAME files (`configuration.yaml`, `scripts.yaml`,
`packages/phoenix_timeline.yaml`, `packages/phoenix_snapshot_cameras.yaml`, `timeline_tools/*`).
Their commits included:
 508216d docs(ha): the camera evidence path is fixed and proven - port 443, empty channels,
 orphaned entity names
 88aa065 docs(ha): the NVR credential is correct - the NVR refuses the HA host's source IP
 f148cf1 fix(ha): stop the snapshot scripts locking the NVR out of its own account
 9d6d956 fix(ha): trip the snapshot breaker at 3, not 5

That document already contained the mechanism for the exact defect I spent hours on: **the config
entry `port` must be `443`. On `80` the NVR answers 302 to https, and aiohttp DROPS the digest
authorization on that redirect, so every snapshot arrives unauthenticated and returns 500.** The same
audit also recorded that the component's `unique_id` scheme changed from a hash to the NVR serial,
producing a second entity generation (`_main_2`, `_sub_4`) with 96 orphaned entities, and that the
fix was removing the dead entity and renaming the live twin onto the clean name - which is exactly
what I then independently re-derived and re-applied.

Two costs of not checking first:
1. Duplicated work: the entity rename was re-invented rather than read.
2. Worse, the live host looked "ahead of the repo" all session, and I could not explain why. That is
 the signature of a parallel deployed session, and it is visible in one command.

This is the same class of failure as "an agent's report is a claim, not evidence", one level up:
**the repository is a claim about the system too, and so is your local branch.** For a shared repo,
the remote is part of the evidence base.

RULES:
1. `git fetch && git log --oneline HEAD..origin/main` and `git ls-remote --heads origin` BEFORE
 designing work on a shared repo, not after.
2. If local and origin have diverged while you were working, treat the merge as a design task with
 the other side's findings in hand. Never merge mechanically across heavy overlap.
3. Preserve rather than reconcile when pausing: push your work to a NEW branch and leave origin/main
 alone. That is what `session/2026-09-17-ha-audit-fleet` is.
4. "The live system is ahead of the repo" is a symptom with a cause. Find the cause before acting on
 the symptom - I let it push me into writing repo config from a stale base, which W3 then had to
 correct by syncing the repo up to live byte-exactly FIRST.
