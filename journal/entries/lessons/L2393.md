**L2393 · lptcase: a canonical status with no literal key for itself silently reads as other - 7 cases were mis-bucketed**

Measured 2026-09-22, lpt-hub tools/case-index/lptcase.py on ZABZ-YOGA.

canonical_status() maps free text onto the enum in CASE-FILE-STANDARD.md section 3 through a table of (canonical, keyword tuple) pairs. The `parts` row listed only the PHRASES - "parts ordered", "awaiting parts", "parts arrived", "waiting for parts" - and not the bare canonical value `parts` itself. So a front-matter `status: parts` fell through the whole table to `other`.

Consequences, and why this mattered more than one case:
- 7 real cases carry `status: parts` on disk, and EVERY one of them was reported as `other`. `lptcase.py open` showed other=58; after the one-word fix it is other=51, parts=7.
- `other` was the largest non-empty bucket, so a session reading the open list could not tell "awaiting a part" from "genuinely none of the above".
- The module's OWN status_order at the bottom of the file lists `parts`. The value was always intended to be first-class; only the canonicalization table forgot it.

This is the same shape as the documented 2026-09-17 bug in the same function, where `in_progress` lost its underscore upstream and fell to `other`. The rule that generalizes: when a canonicalization table maps free text to an enum, every enum value must also be a literal key for itself. Check that first whenever a status reads as `other`/`unknown`.

Fix: added "parts" to the tuple. 88 tests pass (--basetemp into the repo; plain pytest on Windows dies with PermissionError on its own tmp symlink during cleanup and reports exit 1 even when every test passed - use --basetemp, and do not read that exit code as a test failure).

Verification: lptcase.py open --json bucket counts before/after, and `show "rosenberg c930"` now prints "state parts" where it printed "state other".
