**L1586 · Making a producer honest is not enough: a consumer's 'fallback = 0' silently re-creates the lie**

Found 2026-09-15 by the portal-integration agent on phone-and-tech-full origin/test
0c8786068, and reproduced independently:

backend/src/services/waze/waze-device.service.ts:287
 function toNumber(value: unknown, fallback = 0): number
used at :334-336 for consumed_data_mb / remaining_mb / percent_used, and at :340
 capBand: (VALID_BANDS.has(band) ? band : 'ok')
With the fleet-api's new fail-loud contract (a failed Telnyx read returns null plus
usage_known:false), this coercion turns "we do not know" into "0 MB used, ok" - an
empty plan rendered as a healthy one, to a paying customer. `usage_known` had 0 hits
on the branch, so the signal was dropped entirely.

The transferable lesson: a producer that starts telling the truth changes nothing if
the consumer coerces the honest value back into a plausible one. `fallback = 0` was
written when 0 was the only failure representation; once null exists, the default
silently re-creates the lie. When a contract gains a null, grep every consumer for
`|| 0`, `?? 0`, `Number(x)`, `parseInt`, and a `Set.has(x) ? x : <happy default>`
pattern - that last one is how an "unknown" band became "ok".

Related: the same effect exists in the repo's own tests - a green suite that asserts
the fallback stays 0 will defend the bug. Check what the tests assert, not just that
they pass.
