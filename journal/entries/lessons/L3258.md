**L3258 · owner-queue.py --db is a global option, and passing settings.database_url to it silently creates an empty database**

﻿MEASURED 2026-10-05 against ~/bin/owner-queue.py.

TRAP 1 -- --db IS A GLOBAL OPTION. It is registered on the top-level parser
(line ~897), before the subparsers, so it must PRECEDE the subcommand:

 owner-queue.py --db PATH add --from-json - # works
 owner-queue.py add --from-json - --db PATH # exit 2: unrecognized arguments

The sweep's first real run filed nothing and said so in plain words, which is
how this was caught rather than silently swallowed.

TRAP 2 -- NEVER PASS settings.database_url TO IT. The CLI hands `--db` straight
to sqlite3.connect(path), while app/config.py:881 is
`database_url: str = "sqlite:///data/secretary.db"` -- the URL form. sqlite3 would
CREATE a brand-new empty database at that literal filename, the CLI would print
"queued #1" and exit 0, and the caller would report success while the question
went somewhere nobody reads.

The fix is a converter (owner_attention_sweep._db_path_from_url) plus an
existence check that REFUSES to file when the resolved path is not a real file.
The app's own connect_db() accepts both forms, so only the CLI needs converting.

TRAP 3 -- THE CLI HAS A GUARD I DID NOT. It matches against RESOLVED rows too and
refuses with exit 4 and the prior answer printed. It caught my sweep selecting
the NY toll obligation when the owner had already answered it as #166. Defensive
depth works: my sweep now checks answered rows itself as well.
