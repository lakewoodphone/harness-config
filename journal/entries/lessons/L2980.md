**L2980 · Priority is a statement about value: integration outranks new work, and a definition of done that does not name the steps is a wish - three shifts built on stale git locks while a finished branch sat unmerged**

MEASURED 2026-09-28 evening, on the ledger, while three concurrent shifts were running.

WHAT I FOUND: every integration item had been filed at priority 3 - level with ordinary work - and the
three shifts running at 19:26Z went to `checkout-health:*` repair rows instead. So the system was busy
on stale git locks while a branch a shift had created TWO HOURS EARLIER (2398 insertions, 89 files,
112 tests passing) sat unmerged with nobody asked to merge it.

PRIORITY ORDER IS A STATEMENT ABOUT VALUE, and mine was wrong in two ways:
 1. INTEGRATING FINISHED WORK OUTRANKS STARTING NEW WORK. An unmerged branch is finished work that is
 invisible, and the next shift redoes it. Measured in this system already: three consecutive
 lpt-website shifts worked one unmerged fix. So integration items are priority 2, and a branch a
 shift created TODAY is priority 1.
 2. A DEFINITION OF DONE THAT DOES NOT NAME THE STEPS IS NOT A CONTRACT, it is a wish. The items said
 what would PROVE the merge and nothing about the SHAPE of it, so a shift would have re-derived
 the sequence - in a repo where the registry note records that a careless merge deleted 19,296
 lines ("NEVER MERGE origin/fix/holiday-closure-notice AS A BRANCH"). `prioritize-integration.py`
 now writes the exact sequence into each item (`checkout -B`, `merge --no-ff`,
 re-run the tests, and the guard `git diff --diff-filter=D --name-only <base> HEAD` MUST BE EMPTY)
 so the work is mechanical rather than interpretive.

THE RULE: when a system is busy and the valuable thing is not moving, suspect the PRIORITY before the
throughput. I had already removed the throughput limit (three shifts at once). The remaining problem
was that the queue was in the wrong order.
