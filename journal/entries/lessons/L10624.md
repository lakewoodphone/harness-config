**L10624 · Phone engine 0.2.1: two clean rollbacks; the tree swap and the credential format were solved, and the last blocker is a missing webStartup provider in a home whose pnpm tree is still pinned at 0.2.0**

ATTEMPTED TWICE, ROLLED BACK TWICE, 2026-10-20 03:55-04:00Z on secratary-cloud. The owner's phone engine is still on
0.2.0-rc.2 and serving (HTTP 401). What each attempt proved, and what is left.

CANDIDATE: /opt/dsh-phone.failed-021-20261020T035719Z = 0.2.1-rc.2, and the tree swap itself is fine — the unit
runs 0.2.1 and boots far enough to compose the profile.

ATTEMPT 1 failed with `status=2/INVALIDARGUMENT`, and the engine's own stdout said why:
 scope: TWO COPIES - /opt/dsh-phone/node_modules/@deepseek-ai/dsh-scope vs
 /root/.dsh/profiles/web/node_modules/.pnpm/@deepseek-ai+dsh-scope@0.2.0-rc.2.../dsh-scope
After the tree rename the profile's `@deepseek-ai` symlink still pointed at the old path. The unit's
`ExecStartPre=repair-phone-engine.sh --check` only REPORTS that (exit 2, "wrong"); the repair is the same script
without `--check`.

ATTEMPT 2 added the repair step (and moved the two BARE credential keys out of ~/.dsh/.credentials.yaml into
/etc/phone-engine.env, mode 600, wired via EnvironmentFile — because 0.2.1 requires `<scope>/<id>` credential keys
and the phone's store had bare `DEEPSEEK_API_KEY`/`DEEPINFRA_API_KEY`). That cleared BOTH of those: the log now says
`scope: one copy`, and the credentials include no longer throws. It then failed on the next layer:

 error: StartupError: dsh: startup failed: 1 required plugin did not activate
 Plugin Missing services
 webserver (required) webStartup

So on 0.2.1 the REQUIRED `webserver` plugin waits for a `webStartup` service that **nothing in this home provides**,
and everything downstream (open-in-app, directory-picker, client-hmr, ui-deliverables) waits behind it. That is the
same family as the `webRuntime -> webStartup` rename: 0.2.0 had a provider of that service in this composition;
0.2.1 does not get one here.

MOST LIKELY CAUSE, and the next thing to prove rather than guess: this home's profile carries its OWN pnpm tree
pinned at 0.2.0-rc.2 (`.pnpm/@deepseek-ai+dsh-scope@0.2.0-rc.2...`, and package.json pins ~70 packages at
0.2.0-rc.2). The repair script only symlinks `@deepseek-ai` at the profile root, so the provider package that would
register `webStartup` can still resolve to the 0.2.0 copy from `.pnpm` — the same "two versions, one home" defect
that produced the scope error, one layer down. The real fix is to rebuild that profile tree at 0.2.1 (update the
pins, install, then swap the engine), not to add another flag.

WHAT THE ATTEMPTS LEFT BEHIND, all reversible and all restored: tree at /opt/dsh-phone.prev-0.2.0-rc.2-20261020T035530Z
and a second at ...T035800Z (the second attempt's), the unit, credentials and patch each with .bak-phone021* copies,
and the keys moved to /etc/phone-engine.env (still there, harmless and unused while the unit has no EnvironmentFile
after rollback).
