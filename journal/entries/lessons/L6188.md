**L6188 · A repair script must classify before it fixes - 39 broken chats were really 10, and 29 of them were not broken**

## A repair script that reports what it would change is a repair script that can over-report - classify before you fix

Kramer WhatsApp case, 2026-10-13. I told the owner "**39 chats**" were numbering a new message inside their
own history. The truth is **10**, and the difference matters because 29 of those 39 were not broken at all.

What happened: my query selected every chat whose `ZWACHATSESSION.ZMESSAGECOUNTER` was at or below
`max(MAX(ZSORT), COUNT(*))`. In 29 chats the allocator was already correct (`counter == MAX(ZSORT)+1`) and the
row count merely exceeded the top sort key, because 1,488 messages share a `ZSORT` with another message. Those
chats needed nothing. I was about to change 29 correct values on a customer's phone and describe them as faults.

Classified properly the three sets are clean and disjoint:

 BROKEN counter <= max(ZSORT) -> a new send is numbered inside the history (10)
 defensive counter > max(ZSORT), < count -> allocator fine, only duplicate-ZSORT rows (29)
 correct counter == max(ZSORT) + 1 (563)

**The rule:** a repair tool must name the class it is about to change and default to changing only the class it
can prove, with the rest listed and behind a flag. "39" and "10" are the same command with a different
predicate — and on somebody else's data the difference is the difference between a repair and a new fault.

**And the second thing, which is the answer to a question the owner asked:** the blast radius is now measured,
not reasoned. Of 602 conversations holding messages, 599 received her recovered history and **10** of those are
broken; the **3** that received none are all correct, so **a brand-new person messaging her is unaffected**.
Eight of the ten are **group chats** — her vendor groups — which is why it reads as broad. And inside a broken
chat it is **every** message she sends, not some: the counter advances by one per message, so sends land at
5, 6, 7 … until the counter passes the recovered history. `lag` — `topZSORT + 1 - counter` — is how many
messages that takes, and it ranges from 35 (Joys Jewish Toys, so it self-corrects) to 214,749,717
(Jasmyn Vendors, so it never does).

Evidence: `_scratch/kramer-scope.py`; `repair-merged-whatsapp-store.py` (now classifies BROKEN vs defensive,
repairs BROKEN by default, `--also-defensive` for the rest, verified on a copy on mac-mini-ts);
lpt-hub case file blast-radius table and run log DO-NOT-REPEAT #18 correction.
