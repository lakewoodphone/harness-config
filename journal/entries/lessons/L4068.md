# L4068 — I filed a pain about a defect I had not read the artefact for, and the artefact refuted it

**2026-10-14, ZABZ-YOGA, round 4.** I filed `P3866`, titled *"the company's own repair refused to
close, and the markers that were rebuilt on every run"*, claiming that a bookkeeping sweep was
re-creating the same rows on every run so the backlog could never be drained and its rise was an
artefact of the loop. I had not opened the file. I removed the entry after reading it.

**What the artefact actually said.** `journal/state/work-order-backlog-residual-2026-10-14.md`,
mtime `2026-10-14 10:05:21`, titled *"(round 2)"*, and its own first paragraph:

> *"The 2026-10-09 sweep filed 108 questions to the owner. **80 were still open.** As of this writing
> **32 remain**: 20 physical checks and 12 decisions."*

So it is a **dated snapshot**, not a regenerated document; it states its own date in the filename and
the heading; and the backlog was **shrinking 80 → 44 → 32**, with the reductions itemised — *"29
record-decided rows, then 385, 386, 387, 388, 406, 414, 411, 412, 357 and 413 individually, plus 74
payment-reconciliation corrections"*. The state I was interpreting as a growing queue was a record of
work being completed.

**What actually misled me, because that is the reusable part.** I saw the residual state file and the
owner-question mirror both change during the day and read that as growth. Neither file's *content*
says growth. I inferred a trend from the fact that a file had been **written**, which is the same
mistake as reading a deployment boundary off a file's mtime (`L3803`) and a record's freshness off an
index age (`L3801`). **A file's mtime is not its content, and a file existing is not a trend.**

**The rule I am adding to how I file a pain.** A `pain` entry is a claim, and a claim about a document
requires having read that document. Before filing: name the artefact, its path, and — for a
"it keeps happening" claim — the two observations that show it happening twice. I had **zero**
observations; I had one inference from a timestamp. Had this reached the owner it would have been a
manufactured engineering fault, which is the exact class this estate measured at 383 of 595
"owner questions".

**A second, honest version of the same suspicion, which I am NOT filing as a pain** because I have not
measured it either: several sweeps in this estate have a *cursor* or a *discovery cache* whose pinned
state makes a later fix look like a no-op — that is real, recorded (`L3936`, the receipt backfill's
state pinned the discovered id list), and already closed by the work that found it. If the residual
files regrow I will measure it with the idempotency check — *run the sweep twice on an unchanged input
and diff the count* — rather than assert it.
