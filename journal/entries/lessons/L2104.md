# L2105 — the local lpt-hub checkout is the owner's live work surface; never sync it

## What happened

At the end of round 4 I found the local `lpt-hub` at `56d8449f8` reporting `4 2` against
`origin/main`, and my first instinct was to fast-forward it so the repos "agreed". That would have
been a mistake twice over.

**What the divergence actually was.** The 2 local-only commits are the owner's case work — both
`case(unihertz Jelly Max / Moshe Orebin)`, pricing basis and NFC/touchscreen findings, dated
2026-09-17. The 4 origin-only commits are mine, pushed from the authority's clone. And the working
tree carries 5 uncommitted files including a **brand-new case file the owner is writing right now**
(`sd-card-goldstein-8482104005-2026-09-17.md` plus its sync record), and modified
`tools/case-index/lptcase.py` + its tests.

So `git merge --ff-only origin/main` would have failed (correctly), and the "fix" for that — a rebase
or a hard reset — would have moved or destroyed uncommitted work in the checkout he is actively
using. This is the same hazard as **L1916** earlier the same session, where a `git checkout` deleted
seven files, and it recurred in a milder form because I looked before I acted.

## The rule

1. **A repo the owner has open is not a deployment target.** Do work in the authority's clone
 (`/home/zabz/repos/lpt-hub`) and push from there. The local checkout is a consumer, and it stays
 however he left it.
2. **`4 2` divergence is not a problem to fix.** Two independent writers on one branch is the normal
 state of this repo — he commits case work, agents commit tooling. Neither is stale.
3. **Before touching any working tree, read `git status` first.** The uncommitted new case would have
 been invisible in `git log` alone, and it is the thing most at risk.
4. **Verify byte-identity instead of syncing.** What actually needed checking was whether my artifacts
 existed and matched on the remote. `git cat-file -s origin/main:<path>` vs the file on disk answered
 that in one command: `audit.py` is 37,729 bytes in both places, byte-identical, with the
 `per_order` dedup and `GONE_MARKER` fixes present. Nothing needed doing.

## The stale-ref trap that started this

The push from the authority printed `c5cb55f72..9ed3018c1 main -> main` — success. But my local
`origin/main` ref was still at `c5cb55f72`, so a local `git cat-file -e origin/main:<page>` reported
the operator page **MISSING** and I briefly believed I had lost a commit I had just pushed.

`git ls-remote origin refs/heads/main` is the answer: it asks the remote, not a cache, and showed
`9ed3018c1`. **A local remote-tracking ref is a cache with an age; `ls-remote` is the fact.** This is
the same provenance rule as everywhere else — state where a reading came from and when it was written.

## Evidence

- `git -C lpt-hub ls-remote origin refs/heads/main` → `9ed3018c1bbbf799a788190cf7e4650e2b9052ee`.
- `git cat-file -s origin/main:tools/customer/audit.py` = 37729 = the file on disk; all four artifacts
 (audit/repair/dialpad/operator page) confirmed present on `origin/main`.
- The owner's uncommitted work, untouched: `?? docs/customer-operations/cases/sd-card-goldstein-8482104005-2026-09-17.md`
 and its sync record.
