**L1491 · Editing a repo file on Windows with the file tools writes CRLF, and git then reports the whole file as rewritten**

Found the hard way on 2026-09-15 while fixing scripts/lpt-sync-to-production.py in
personal-secretary-mvp (a Linux repo on secratary).

WHAT HAPPENED. I read the file off secratary with scp, edited it with the local
file tools, and scp'd it back. All three files came back with CRLF endings, so
`git diff --stat` said:

 scripts/lpt-sync-to-production.py | 3889 ++++++++++++++++++--------------
 3 files changed, 2738 insertions(+), 1718 deletions(-)

That is not a big change, it is every line changed. The real diff was 35 hunks /
1095 insertions / 75 deletions. `file <path>` is the proof, and it says it
plainly: "with CRLF line terminators".

WHY IT IS DANGEROUS, beyond an ugly diff:
 * a reviewer (or the next agent) cannot see what actually changed, which is
 exactly the condition that hides a bad edit;
 * `git diff --stat` is the first thing anyone checks for blast radius, so a
 bogus 3889-line stat invites either a needless revert or blind acceptance;
 * the target repo may or may not have core.autocrlf set, so the damage is
 silent until a diff is read.

THE FIX, and it is two commands:
 1. after editing locally, before scp:
 python -c "from pathlib import Path; p=Path(F); p.write_bytes(p.read_bytes().replace(b'\r\n', b'\n'))"
 2. after scp, verify — do not assume:
 file <path> # must NOT say "CRLF line terminators"
 git diff --stat # must be a plausible size, not the file size

RULE: when handing an edited file to a Linux repo, normalise to LF and then
prove it with `file` + `git diff --stat` BEFORE staging. A diffstat that is
roughly equal to the whole file is a line-ending bug, not a large change.
