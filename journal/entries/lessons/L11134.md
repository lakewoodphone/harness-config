**L11134 · A live Prisma process caches enum labels, and aligning the repo to a stray database value is how a picker gains a status nobody designed**

A long-running Prisma process caches the database's enum labels, and an `ALTER TYPE ... ADD VALUE`
does not reach it.

Measured 2026-10-20 on the LPT production backend. Two true statements at the same time:

- from a fresh connection inside the same container, `pg_enum` for `OrderStatus` returned eight
 values ending `CANCELLED, UNFIXABLE, CLOSED`;
- the running process (up 14 hours) logged `Value 'CLOSED' not found in enum 'OrderStatus'` on
 `prisma.order.groupBy()` and `prisma.repairIntakeCase.findMany()`, wrapped in
 `PrismaClientUnknownRequestError` — the *engine*, not the query text, refusing.

The value was added to the database after the process started. Prisma reads the enum list when it
connects and keeps it; a pooled connection from before the change refuses any query that names the
new label. **The fix is a reconnect — a restart or a redeploy — not a migration and not a code
change.** A restart of the container re-introspects and the same query works.

Two traps that follow, and the second is the expensive one:

1. Do not read `PrismaClientUnknownRequestError` as "the database said no to my data". The engine
 rejects a query whose *vocabulary* it does not recognise, before anything is read. Nothing was
 corrupt, and no row was missing.
2. **Do not "align the repo to the database" reflexively.** I assumed the drift was ours and added
 `CLOSED` to `OrderStatus` in `schema.prisma` plus an idempotent migration, then followed the
 compiler through three `Record<OrderStatus, …>` maps and the canonical `ORDER_STATUS_VALUES`
 tuple. Typecheck went green. The backend suite then failed in four places, each one saying the
 same thing: *"the vocabulary is exactly the seven settled states"*. The seven states are the
 shop's actual workflow — every picker, queue, transition and count is built on them — and
 `CLOSED` is a stray eighth value in the database that no code writes or reads. Aligning the code
 to a stray value would have quietly added a status to a picker that staff choose from.

So the order is: **read what the value MEANS in the product before making the types agree with it.**
A green typecheck after a schema change proves the types are total, not that the change is right.
Both reverts are in the carrier, and the question "what is CLOSED doing in production's OrderStatus"
now belongs to the owner, because the answer decides the shop's status vocabulary.
