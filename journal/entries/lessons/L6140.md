**L6140 · work.py add now takes --from-json: the same mangled definition of done twice in one night**

2026-10-13. I made the same mistake twice in one night, so I fixed the tool instead of the instance.

THE RECURRENCE. Filing ledger items through pwsh -> ssh -> base64 -> bash mangled a definition-of-done
into `chr()` soup TWICE: item 65, and then item 71 three hours later. Both items looked filed and both
were unreadable to the shift that would claim them - **an item with an unusable bar is worse than no bar,
because it looks like work** (the lesson I had already written down as L3682/H3598 and then broke again).

THE MECHANISM. `work.py add` took `--dod` as a shell argument, and a dod is a shell command with quotes
inside it. The estate already had the answer in the tool next door: `owner-queue.py add --from-json`, whose
help text says "text never passes a shell". So `work.py add` now takes `--from-json` too, reading
project/title/dod/why/priority/owner_row/source from a file (or `-` for stdin) and leaving the flags
optional. Selftested with a dod containing parentheses, double quotes AND apostrophes - it arrived
verbatim - then closed the selftest and item 71 as dropped, with the reason recorded on each, and refiled
cleanly as item 73.
Backup: /root/work.py.bak-fromjson-20261013T065958Z.

A LESSON ABOUT LESSONS, which is the part worth keeping. I had already written down "an item with an
unusable definition of done is worse than no item" and still produced one, because the lesson was about
the SYMPTOM and I never removed the CAUSE. The cause was that a text field with shell metacharacters was
being passed through a shell. **A lesson that only says "be careful" is not a fix; a lesson that changes
the interface is.** The estate's own tool had the better interface all along and I did not look.

4/5,377.06. **A spending category receiving deposits is a bucket that has lost the thread of what it is
