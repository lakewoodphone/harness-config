**L3350 · A claimed offsite backup is a job, an object and a size - a plan is none of the three**

A claimed offsite backup is a **job**, an **object** and a **size**. A plan is none of the three.

**Rule.** Before any design relies on "we have offsite backups", demand all three: the job that moves
the data (name the script and the line that reads the source), the object where it lands (name the
bucket and list its prefixes), and the size and age of the newest object. If all three cannot be
produced, the correct statement is "there is no offsite copy", not "there is an offsite backup" —
because the second one stops people from fixing it.

**Evidence, 2026-10-06 (F:ERRATUM 1).** The resilience package asserted that the company's 12.17 GB
authority database was copied nightly to Cloudflare R2, citing a real and careful access-review
document. It was not. Four readings settled it: (1) the only restic jobs in the repo —
`hetzner-backup.sh`, `lpt-apps-backup.sh` — dump *their own box* and never reference the secretary;
(2) R2's own object map puts the restic repo at `psm-backups/lpt-apps`, described in the review itself
as "Box 2 restic repo"; (3) `C:\Users\ezabz\secretary-backups-offsite` exists on the laptop and holds
**0 bytes**; (4) the decision log has F1 "Offsite crash-consistent backups" marked **DEFERRED** by the
owner on 2026-08-30, and the gap had been written down on 2026-07-10: *"No off-site backup exists (all
backups are on the same machine)."* The only copy of the authority's data was on the disk of the
machine that was switched off.

**How the false belief was manufactured — the transferable part.** The access-review document
describes where the **Box 2** backup lands. The evolution plan describes a **proposed** pipeline
("VACUUM INTO → restic → R2"), written as a plan. Reading the two together produced a pipeline that
exists in neither. Proximity of two documents is not evidence of a link between them. **For every
asset, follow the bytes**: source path → script → destination, one hop at a time, and read the script
that is supposed to do the copying.

**Corollary — the same mistake hides the detection layer.** Nothing monitors the company's own backup.
`monitor-hetzner-backups.sh` checks the two Hetzner boxes (its own alert reads "Hetzner boxes stale
>26h") and writes to a log the 2026-09-28 analysis recorded as not existing. Twice (2026-08-30,
2026-09-28) the 6-hourly job produced partial, unusable snapshots — one was a truncated 5.16 GB
database with no tarballs — and nothing said so. A backup that fails quietly is worse than none,
because it is trusted.

**Corollary 2 — a monitor inside the thing it monitors cannot report its death.** The 2026-08-30
decision put health checks in a cron *on the secretary*, surfacing into the owner queue *on the
secretary*; the only external monitor was a GitHub Action that "did not run during the outage window"
and opens a GitHub issue rather than telling anyone. Heartbeats and backup-freshness alerts must live
on a different host, a different provider or a different path from the thing watched.

**Corollary 3 — durable configuration kept on one machine is lost configuration.** The live
backup-retention policy on the box was changed 2026-09-28 and never committed; the repo still
implements the older, fatter policy that filled the disk to 100 % and made SQLite core-dump with
SIGBUS for days. A rebuild from the repo would silently restore the configuration that caused the last
three incidents. Change a policy on a box → commit it in the same hour.
