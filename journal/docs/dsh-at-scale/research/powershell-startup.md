# PowerShell 7.x (`pwsh`) startup latency on Windows — cited research

Labels: **[OFFICIAL]** Microsoft Learn / PowerShell-team. **[REPO]** PowerShell or dotnet GitHub. **[VENDOR]** vendor marketing. **[COMMUNITY]** user report or third-party benchmark.

---

## 1. What dominates `pwsh` cold start

- **[OFFICIAL]** Microsoft defines three phases — (1) process creation, (2) SessionState initialization, (3) profile processing — the frame for any breakdown: [Troubleshoot PowerShell startup issues](https://learn.microsoft.com/en-us/powershell/scripting/dev-cross-plat/performance/startup-performance).
- **[OFFICIAL]** Phase 1 is host window, host process, and "Prepare .NET" (PowerShell "needs to fully load"). On first startup after install or upgrade, "PowerShell and .NET run optimization tasks… Startup will take longer during this first-time optimization": [startup-performance](https://learn.microsoft.com/en-us/powershell/scripting/dev-cross-plat/performance/startup-performance).
- **[OFFICIAL]** Phase 2 is config files (`powershell.config.json`, PSSession configuration), Group Policy / WDAC checks, then loading **the default modules — `Microsoft.PowerShell.Core` and `PSReadLine`** — plus modules and assemblies named in the PSSession configuration: [startup-performance](https://learn.microsoft.com/en-us/powershell/scripting/dev-cross-plat/performance/startup-performance).
- **[REPO]** Best published breakdown, with hardware named: Microsoft's daxian-dbw moved type initializers for `Compiler`, `CachedReflectionInfo`, `ExpressionCache` ("lots of reflection operations") to a background thread and reordered `LanguagePrimitives`/`TypeAccelerators`. BenchmarkDotNet, `pwsh.exe -noprofile -c echo 1`, warm startup with module-analysis cache pre-populated, Release + R2R images, **Windows 11 (10.0.22621.521), Intel Xeon W-2235 3.80 GHz, 12 logical / 6 physical cores, .NET 7 RC**: **557.2 ms → 386.3 ms (~30% faster)**: [PowerShell PR #18195](https://github.com/PowerShell/PowerShell/pull/18195).
- **[REPO]** Per-component wins attributed by a collaborator: `powershell.config.json`/Newtonsoft read "expected perf win 50–100 ms"; `microsoft.applicationinsights` lazy init "30 to 100 ms"; `InitialSessionState..cctor()`/`GetAppLockerPolicy()` "~10-30 ms"; `string.ToLowerInvariant()` in `CommandLineParser.GetSwitchKey()` at **26 ms**. Host: Windows 10.0.18363, PS 7.2.0-preview.1, PerfView trace. The same thread warns that `EventSource.CreateManifestAndDescriptors()` shows up only *because* PerfView collects ETW — in real startup it is never called, so it is a tracing artefact, not cost: [issue #14268](https://github.com/PowerShell/PowerShell/issues/14268), [caveat comment](https://github.com/PowerShell/PowerShell/issues/14268#issuecomment-739464805).
- **[OFFICIAL]** First-run cost is not JIT-only: the **ModuleAnalysisCache** must be built, and Microsoft names it as a discrete deletable artefact (`ModuleAnalysisCache-*`, `StartupProfileData-*` under `%LOCALAPPDATA%\Microsoft\PowerShell`): [startup-performance](https://learn.microsoft.com/en-us/powershell/scripting/dev-cross-plat/performance/startup-performance).
- **[OFFICIAL]** Profile numbers from the PowerShell team: Steve Lee averaged `pwsh -noprofile -command 1` over 100 runs at **1176 ms** and took his profile from **1465 ms to 217 ms**. No CPU/RAM published — one developer's desktop, not a comparable baseline: [Optimizing your $Profile](https://devblogs.microsoft.com/powershell/optimizing-your-profile/).
- **[COMMUNITY]** A single `Set-PSReadLineOption` line in a profile was reported to delay startup by **over 100 ms** (PS 7.4.2, PSReadLine 2.3.5, Windows 10.0.22621); still open: [PSReadLine issue #4022](https://github.com/PowerShell/PSReadLine/issues/4022).
- **[COMMUNITY]** Pathological outliers, environment-specific, not hardware baselines: `Measure-Command {pwsh -command "exit 0"}` at **147 s** and `-noprofile` at **145 s** on one Windows 11 box, fixed by `POWERSHELL_TELEMETRY_OPTOUT=1` + `POWERSHELL_UPDATECHECK=Off` (→ 1419 ms / 1060 ms); another reporter saw 15 s of prompt delay with an empty profile. Disk state can dominate too: on Win11 24H2, **600–650 ms** with HDDs already spinning versus **6000–8000 ms** parked, despite `pwsh`, `Documents` and `AppData` all on SSD: [PowerShell issue #24710](https://github.com/PowerShell/PowerShell/issues/24710), [disk comment](https://github.com/PowerShell/PowerShell/issues/24710#issuecomment-2661137487).
- **[COMMUNITY]** Same class: `pwsh.exe -NoProfile` at ~180 s after a .NET update, logged as `Loading personal and system profiles took 180574ms`, slowness persisting after startup and unfixed by `-NonInteractive`, telemetry/update opt-outs or reinstall: [issue #23830](https://github.com/PowerShell/PowerShell/issues/23830).

## 2. Supported ways to avoid paying the cost per command

- **[OFFICIAL]** `-NoProfile` / `-nop`: "Doesn't load the PowerShell profiles." That is the whole documented contract — nothing about modules, PSReadLine, or assembly load. Microsoft's own first diagnostic is `pwsh -NoProfile`: [about_Pwsh](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_pwsh), [startup-performance](https://learn.microsoft.com/en-us/powershell/scripting/dev-cross-plat/performance/startup-performance).
- **[OFFICIAL]** `-NonInteractive` / `-noni`: creates "sessions that shouldn't require user input… Any attempts to use interactive features, like `Read-Host` or confirmation prompts, result in statement terminating errors rather than hanging." The parameter docs do **not** call it a performance switch: [about_Pwsh](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_pwsh).
- **[OFFICIAL] — but it does change startup cost.** "For *interactive* PowerShell sessions, PowerShell loads the PSReadLine module automatically. PSReadLine is a signed module. PowerShell must verify the digital signature… the default timeout for CRL checks is 15 seconds… every time PowerShell loads a signed module, it can take up to 15 seconds to timeout," and the prescribed test is to "start PowerShell 7 in *non-interactive* mode: `pwsh.exe -noninteractive`". So `-NonInteractive` avoids the interactive path that loads PSReadLine and its signature/CRL check; it is not documented as skipping assembly load, JIT, or module-directory scanning: [startup-performance](https://learn.microsoft.com/en-us/powershell/scripting/dev-cross-plat/performance/startup-performance).
- **[REPO/COMMUNITY]** Corroboration: a collaborator advised "If you think it is PSRL you can run without it by `pwsh -NoInteractive`," and the reporter replied "yes, using `pwsh -NonInteractive` works instantly" (from ~10 s), while `-NoProfile` changed nothing: [issue #14266](https://github.com/PowerShell/PowerShell/issues/14266#issuecomment-758771885).
- **[OFFICIAL]** `-NoLogo` / `-nol`: "Hides the banner at startup of interactive sessions." No cost claim. `-WindowStyle <Normal|Minimized|Maximized|Hidden>` is Windows-only and "Sets the window style for the session" — no documented effect on any startup phase: [about_Pwsh](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_pwsh).
- **[OFFICIAL]** `-File` is the default when command-line values are present with no switch; the script runs "in the local scope ('dot-sourced') of the new session"; **`-File` must be last**; since 7.2 it accepts only `.ps1` on Windows. `-Command` takes `-`, a scriptblock, or a string; a **string** must be last, and a **scriptblock** only works when `pwsh` is launched *from another PowerShell host*: [about_Pwsh](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_pwsh).
- **[OFFICIAL]** `pwsh -Command -` reads statements from stdin and executes them **one at a time, as though typed at the prompt**, not exiting until stdin closes "unless you use the `-NoExit` parameter" (`-File -` behaves alike) — so stdin mode saves per-*statement* process creation, not per-*process* session initialisation: [about_Pwsh](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_pwsh).
- **[COMMUNITY]** Two env vars remove *network* cost from startup and are the reported fix for the §1 outliers — `POWERSHELL_TELEMETRY_OPTOUT` and `POWERSHELL_UPDATECHECK`; effect size is user-measured: [issue #24710 comment](https://github.com/PowerShell/PowerShell/issues/24710#issuecomment-2564927091).

## 3. `PSModulePath` scanning and module auto-loading

- **[OFFICIAL]** "[`$Env:PSModulePath`] contains a list of folder locations. PowerShell **recursively searches each folder** for module (`.psd1` or `.psm1`) files," and auto-loading requires the module to live in one of those locations: [about_PSModulePath](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_psmodulepath).
- **[OFFICIAL]** `$PSModuleAutoLoadingPreference` "doesn't exist by default"; absent, behaviour equals `All`. Values are `All`, `ModuleQualified`, `None` — and `None` "Disables the automatic importing of modules. To import a module, use the `Import-Module` cmdlet": [about_Preference_Variables](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_preference_variables).
- **[OFFICIAL]** The two mechanisms are independent: `-NoProfile` skips profile files only, while `$PSModuleAutoLoadingPreference` is a *variable* normally set *by* a profile — which is why setting it in a profile is defeated by `-NoProfile`. The documented session-wide route is the profile: [about_Profiles](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_profiles).
- **[OFFICIAL]** Discovery cost, stated plainly: "**Command auto-discovery analyzes each module to determine which commands the module exports and this analysis can be expensive.** The results of module analysis are cached per user, but the cache isn't available on first run, which is a typical scenario with containers": [module authoring considerations](https://learn.microsoft.com/en-us/powershell/scripting/dev-cross-plat/performance/module-authoring-considerations).
- **[OFFICIAL]** The main avoidable trigger: `Get-Module -ListAvailable` enumerates everything installed under `PSModulePath`; Microsoft explicitly notes **`Get-Command` with a wildcard imports nothing**, so wildcard discovery is the cheap form: [about_Modules](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_modules).
- **[OFFICIAL]** Manifest quality changes that analysis cost: wildcards (or an *omitted* entry, which equals `*`) in `AliasesToExport`, `CmdletsToExport`, `FunctionsToExport` force the expensive path; explicit arrays and explicit `@()` avoid it. Module *kind* also sets the order of magnitude: binary loads fastest, script "a bit more slowly", and **CDXML "roughly an order of magnitude slower"** than binary: [module authoring considerations](https://learn.microsoft.com/en-us/powershell/scripting/dev-cross-plat/performance/module-authoring-considerations).
- **[OFFICIAL]** `$Env:PSModulePath` is **reconstructed on every PowerShell start**, including User/Machine merge semantics and prepending of the PS7 User, System and `$PSHOME` paths: [about_PSModulePath](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_psmodulepath).
- **[OFFICIAL]** Two documented delays that look like "PSModulePath is slow" but are not scanning: a redirected/OneDrive `Documents` folder, and cloud-only files — the latter got `PSModuleAutoLoadSkipOfflineFiles`, so discovery skips files marked not-fully-on-disk: [What's New in PowerShell 7.4](https://learn.microsoft.com/en-us/powershell/scripting/whats-new/what-s-new-in-powershell-74).
- **Is emptying `PSModulePath` safe/advisable? No.** **[OFFICIAL]** Auto-loading only works for modules inside it, and the documented failure mode is concrete: when shared module names resolve to versions that cannot be loaded, "**cmdlets from those modules fail with a `CommandNotFoundException`**". Narrowing it is supported, but official advice is "For most situations, you should be installing modules in the default module locations": [about_PSModulePath](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_psmodulepath).

## 4. ReadyToRun / crossgen / NGen, caching, and runtime knobs

- **[REPO]** PowerShell 7 ships **ReadyToRun (R2R)** images. A collaborator: "We benefit from ReadyToRun (R2R) - all assemblies is crossgened"; the 7.2 work list records "All shipped assemblies are R2R images now," with modern CrossGen2/`dotnet-pgo` as remaining upside: [issue #14266 comment](https://github.com/PowerShell/PowerShell/issues/14266#issuecomment-735351583).
- **[OFFICIAL]** The team uses `-CrossGen` at build time when it needs symbols, confirming R2R is the shipped configuration: [PowerShell `tools/performance` README](https://github.com/PowerShell/PowerShell/tree/master/tools/performance).
- **[OFFICIAL] .NET knob semantics:** `DOTNET_ReadyToRun` (`1`/`0`) defaults on when R2R data exists — "**Disabling this option forces the runtime to JIT-compile framework code**," so `=0` makes startup *slower*; `DOTNET_TieredCompilation`, `DOTNET_TC_QuickJit`, `DOTNET_TC_QuickJitForLoops` — "Enabling quick JIT **decreases startup time** but can produce code with degraded performance characteristics," and with quick JIT off but tiering on, only pre-compiled (R2R) code participates; `DOTNET_TieredPGO` enables dynamic PGO ".NET 6 and later" via tier-0 instrumentation, with **no default stated and no official PowerShell-specific claim**: [runtime config — compilation](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/compilation).
- **[OFFICIAL]** Where these live, and the precedence trap: `runtimeconfig.json` / MSBuild property / `DOTNET_` environment variable / `AppContext.SetSwitch`, and **"Starting in .NET 9, environment variables take precedence over both MSBuild properties and `runtimeconfig.json` settings."** PowerShell 7.5 is .NET 9 and 7.4 is .NET 8, so the same variable wins differently between them: [.NET runtime config options](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/), [env var precedence](https://learn.microsoft.com/en-us/dotnet/core/compatibility/deployment/9.0/envvar-precedence), [What's New in PowerShell 7.5](https://learn.microsoft.com/en-us/powershell/scripting/whats-new/what-s-new-in-powershell-75).
- **Can caches be pre-warmed? [OFFICIAL] Yes, and the artefacts are named.** Startup is slow "during the first startup after installation, upgrade, or if the cache is empty"; the files are `ModuleAnalysisCache-*` and `StartupProfileData-*` under `$env:LOCALAPPDATA\Microsoft\PowerShell`, and "The cached data is recreated the next time you start PowerShell." A **corrupted** cache is a documented cause of slow start and of command-discovery and module-load failure. So after install or upgrade, run the exact command shape you intend to measure once — same `-NoProfile` posture, same `PSModulePath` — before measuring: [startup-performance](https://learn.microsoft.com/en-us/powershell/scripting/dev-cross-plat/performance/startup-performance).
- **[OFFICIAL]** PowerShell 7.5's documented performance improvement is **not** startup-related — it optimises `+=` on object arrays (PR #23901), with before/after tables in the release notes (10,240 elements: 1668.13 ms → 104.73 ms), so do not cite 7.5 as a startup win: [What's New in PowerShell 7.5](https://learn.microsoft.com/en-us/powershell/scripting/whats-new/what-s-new-in-powershell-75).
- **`DOTNET_EnableWriteXorExecute`:** no official Learn page was locatable; the nearest primary source is the runtime repo, e.g. [dotnet/runtime issue #97765](https://github.com/dotnet/runtime/issues/97765).

## 5. Keeping a process warm instead of starting one per command

- **[OFFICIAL]** Supported in-process hosting is `System.Management.Automation.Runspaces`: a runspace is "the operating environment for the commands that are invoked by a host application… the commands and data that are currently present, and any language restrictions that currently apply." A host may use a default runspace with all core commands, or a custom one built from an `InitialSessionState`: [Creating Runspaces](https://learn.microsoft.com/en-us/powershell/scripting/developer/hosting/creating-runspaces).
- **[OFFICIAL] — the startup-cost lever.** `InitialSessionState.CreateDefault()` "creates an `InitialSessionState` with all of the built-in commands loaded, while the **`CreateDefault2()` method loads only the commands required to host PowerShell**". `CreateDefault2` plus exactly what you need is the documented cheaper-to-open warm host: [Creating an InitialSessionState](https://learn.microsoft.com/en-us/powershell/scripting/developer/hosting/creating-an-initialsessionstate).
- **[OFFICIAL]** `RunspacePool` is documented with min/max sizing, including a `CreateRunspacePool(InitialSessionState)` overload, a parameterless overload giving max 1 / min 1, and remote `RunspaceConnectionInfo` overloads: [RunspaceFactory.CreateRunspacePool](https://learn.microsoft.com/en-us/dotnet/api/system.management.automation.runspaces.runspacefactory.createrunspacepool).
- **[OFFICIAL]** `-NoExit` / `-noe`: "Doesn't exit after running startup commands." It keeps *that* process alive; it does not pool or reuse it: [about_Pwsh](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_pwsh).
- **[OFFICIAL] State preserved by remoting — the important caveat:** "**Profile scripts aren't run for remote sessions**" and "the `$PROFILE` automatic variable isn't populated in remote sessions," so a remote session does *not* inherit interactive profile state; run it explicitly with `Invoke-Command -Session $s -FilePath $PROFILE`: [about_Profiles](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_profiles).
- **[OFFICIAL]** `-CustomPipeName` "Specifies the name to use for an additional IPC server (named pipe) used for debugging and other cross-process communication… Typically used with the **CustomPipeName** parameter on `Enter-PSHostProcess`." `-SSHServerMode` / `-sshs` is "Used in `sshd_config` for running PowerShell as an SSH subsystem. **It isn't intended or supported for any other use**." `-ConfigurationName` selects a registered endpoint and `-ConfigurationFile` applies a `.pssc` session configuration — the documented route to a deliberately minimal session state: [about_Pwsh](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_pwsh).

## 6. Windows 11 and modern hybrid / many-core CPUs

- **[OFFICIAL]** QoS governs which class of core a thread lands on: "On platforms with heterogeneous processors, the QoS of a thread **may restrict scheduling to a subset of processors, or indicate a preference for a particular class of processor**." `Low` "On battery… **schedules to efficient core**", as do `Utility` (Win11 22H2) and `Eco` (Win11). Classification by window state: In Focus → High, **Visible → Medium, Minimized or Fully Occluded → Low**: [Quality of Service (Win32)](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service).
- **[OFFICIAL] — the benchmarking trap, directly relevant here.** Microsoft warns: "This feature should be disabled when testing on battery (for example, running performance benchmarks). **Automated tests lacking user input may trigger this feature, lowering QoS and skewing results.**" The switch is `HKLM\SYSTEM\CurrentControlSet\Control\Power\PowerThrottling` → `DisableUserPresenceQos = 1`. Any `pwsh` startup benchmark run headless, hidden, or without user input can hit this distortion: [Quality of Service (Win32)](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service).
- **[OFFICIAL]** Logical-core count does change .NET's scheduling config: `DOTNET_Thread_UseAllCpuGroups` is "**enabled by default on Windows 11 and later versions, and disabled by default on Windows 10 and earlier versions**"; it affects what `Environment.ProcessorCount` returns, and `DOTNET_Thread_AssignCpuGroups` (default enabled) tries to "fully populate a CPU group that is already in use before utilizing a new CPU group." The GC must also be configured for all CPU groups: [threading](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/threading), [GC](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/garbage-collector).
- **[VENDOR]** Intel's framing — no latency figures and no PowerShell measurements; the article is about benchmark *scores*: "While Windows 10 performs great with Intel Core Processors with performance hybrid architecture, upgrading to Windows 11 will allow your system to use the full capabilities of Intel Thread Director to send the right workload to the right core at the right time": [Intel KB 000088749](https://www.intel.com/content/www/us/en/support/articles/000088749/processors/intel-core-processors.html).

## 7. What is NOT established

- **A published ms delta for `-Command` vs `-File` vs `-Command -` / stdin.** No official or measured source found; §2 covers behaviour, not timing: [about_Pwsh](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_pwsh).
- **A measured ms cost for a long `PSModulePath`, and whether trimming it yields a startup win.** Microsoft states that discovery recursively searches every folder and that "command auto-discovery… can be expensive", but quantifies neither ms-per-entry nor a before/after, and the §3 breakage is documented without a measured benefit: [module authoring considerations](https://learn.microsoft.com/en-us/powershell/scripting/dev-cross-plat/performance/module-authoring-considerations).
- **`AnalyzeModuleManifest` specifically, and a measured cost for `Get-Module -ListAvailable`.** Public docs describe the cost of module analysis and identify `Get-Module -ListAvailable` as enumerating all `PSModulePath` modules, but the internal API name is not publicly documented and no number is published: [about_Modules](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_modules).
- **`DOTNET_EnableWriteXorExecute` and `DOTNET_TieredPGO` effects on `pwsh` startup.** No Learn page for `EnableWriteXorExecute` was locatable, and the compilation page states no default for `DOTNET_TieredPGO` and makes no PowerShell-specific claim — so any claim that either measurably changes `pwsh` startup is currently unverified: [runtime config — compilation](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/compilation).
- **`pwsh -s` server mode.** No such switch is documented for PowerShell 7; the documented server-adjacent switches are `-SSHServerMode` (explicitly "not intended or supported for any other use") and `-CustomPipeName` (an IPC named pipe), so verify against a released `pwsh -?` on the target machine rather than from docs: [about_Pwsh](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_pwsh).
- **Startup-cost scaling with logical processor count, and E-core/P-core effects on `pwsh` specifically.** No measurement found; what exists is policy-level (QoS core selection, CPU-group defaults) and vendor framing — not a PowerShell latency measurement: [Quality of Service (Win32)](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service).
